# SQuaLity experiment on 2026-10-05

SQuaLity `a471c3f0e0f7faa0faad8d103da9043af6ce57e1` parsed SQLite SQLLogicTest `c67f97bf3ca7e590d12e073408bcacaf2ff0f3a0` and DuckDB `96df096fb00184f615770231fcb61884c97d77eb`. The profile comparison used ClickHouse master `392f555ff7db8217ad5b8929560575041e97823e` (ARM, version `26.10.1.1602`), the newest completed master build when the run began. The SQLite and DuckDB samples were rerun on newer master `2cf1c54ffcb2d553aaed4650e9c371f8d62356ba` (version `26.10.1.1607`). Tests ran on the `dev` VM in dedicated servers. Raw JSONL and logs are at `/home/ubuntu/clickhouse/tmp/squality/results` and `/home/ubuntu/clickhouse/tmp/squality/build` there.

This was a bounded pilot, not a full-corpus run. The [SQuaLity paper](https://suyang.zone/assets/pdf/sigmod25.pdf) reports 7,475,920 source test cases: 7,406,130 SQLite, 36,677 PostgreSQL, and 33,113 DuckDB. The later suite revisions downloaded for this experiment contain 622 SQLite `.test` files with 7,195,342 textual `query` records and 225,371 `statement` records, plus 4,391 DuckDB `.test` files with 31,808 `query` and 34,842 `statement` records. These textual counts precede runner conditions and are not counts of independently runnable ClickHouse tests. Only five SQLite files and a seeded 750-file DuckDB sample were attempted here, with per-file record caps. The query-pass column below counts matches, not all executed queries.

| Suite and bound | Query pass | Result mismatch | Main limit |
| --- | ---: | ---: | --- |
| SQLite `select*.test`, five files, first 1,000 records each, default profile (`26.10.1.1602`) | 915 | 1,992 | One file stops at `PRIMARY KEY` with `Memory` |
| Same SQLite files, SQL profile (`26.10.1.1602` and `26.10.1.1607`) | 2,007 | 900 | Same `PRIMARY KEY` stop |
| SQLite random `select`, ten seeded files, first 100 records each | 656 | 21 | Nine file limits, 117 source condition skips |
| DuckDB SQL, 750 seeded files, first 50 records each (`26.10.1.1607`) | 279 | 21 | 315 files need unsupported harness features; 291 setups blocked |

The combined SQL profile converted 1,095 SQLite mismatches into passes and introduced three mismatches, a net improvement of 1,092 passes on the identical 2,907 executed query records. All 900 remaining mismatches in this sample agree with the SQLite reference result, so they are real cross-engine differences rather than bad expected hashes. The 21 random SQLite mismatches all involve integer `/`: SQLite divides integers before later arithmetic, while ClickHouse `/` produces a floating result. There is no session setting for SQLite-style integer division.

The DuckDB sample also has 1,080 SQL exceptions, 261 expected errors, 18 statements expected to fail that succeeded, 357 passed statements, 39 skipped DuckDB settings, 22 excluded plan checks, 23 missing-fixture exclusions, and two blocked database-admin tests. Most exceptions are syntax, unsupported functions, or engine-specific DDL. DuckDB plan expectations and data fixtures are not portable. The prior master returned 278 passes and 22 mismatches. The one changed result is the row order of `SELECT 1 UNION ALL SELECT 'asdf'` without `ORDER BY`; it is not evidence of a correctness fix. An earlier trial let `DETACH DATABASE system` from DuckDB's suite affect the dedicated server; the adapter now blocks database-admin commands, and the reported sample ran on a fresh protected server.

One DuckDB case gives a concise, reproducible `GROUPING` discrepancy with no setup tables:

```sql
SELECT grouping(1 + 1, 2 + 0), count(*)
FROM (VALUES (1), (2)) AS t(x)
GROUP BY GROUPING SETS ((1 + 1), (2 + 0), ())
ORDER BY 1;
```

ClickHouse masters `392f555ff7db8217ad5b8929560575041e97823e` and `2cf1c54ffcb2d553aaed4650e9c371f8d62356ba` return `(0, 2), (0, 2), (3, 2)`; DuckDB and its source test return `(1, 2), (2, 2), (3, 2)`. Replacing the two constant expressions with distinct column expressions `x + 1` and `x + 2 - 1` produces the expected masks in both engines. This points to constant folding merging two syntactically distinct grouping keys before `GROUPING` calculates its bits. The finding is tracked in [ClickHouse issue #124098](https://github.com/ClickHouse/ClickHouse/issues/124098). [ClickHouse issue #117904](https://github.com/ClickHouse/ClickHouse/issues/117904) concerns lost duplicate keys in `CUBE` and `ROLLUP`; this explicit `GROUPING SETS` mask case is related but distinct.

Two other differences are already explained by ClickHouse semantics. With an unaliased outer table `t1`, a subquery `FROM t1 AS x WHERE x.b < t1.b` binds `t1.b` to its own input in ClickHouse, returning zero counts; explicitly aliasing the outer table as `y` and using `y.b` returns the expected correlated result. `CASE NULL WHEN NULL THEN 444 ELSE 555 END` returns `444` in ClickHouse and `555` in SQLite. ClickHouse [test `04259_case_with_expression_null_equals_null_101262.sql`](../../tests/queries/0_stateless/04259_case_with_expression_null_equals_null_101262.sql) explicitly preserves this latter behavior, so it is a dialect difference rather than an unrecognized regression.

The DuckDB added-column case shows that `Memory` returns old rows with `l=0` after `ALTER TABLE test ADD COLUMN l INTEGER DEFAULT 3`; `MergeTree` returns `l=3`, matching DuckDB. [ClickHouse issue #69331](https://github.com/ClickHouse/ClickHouse/issues/69331) describes a related longstanding difference in `Memory` default handling. Using `MergeTree` addresses that case without a ClickHouse code change. For index tests, `MergeTree`, `data_type_default_nullable=0`, and `allow_create_index_without_type=1` allow ordinary setup, but `UNIQUE` indexes block the sampled files before any query checks.

The adapter can detect wrong results and isolate a useful `GROUPING` candidate, but the DuckDB suite currently has a low portable-query yield. The SQLite randomized sample is a cleaner source of additional result checks once integer-division cases are classified as a known dialect difference. No ClickHouse engine changes were made.

## Uncapped source-file pass on 2026-10-06

The same ClickHouse master `2cf1c54ffcb2d553aaed4650e9c371f8d62356ba` (`26.10.1.1607`) was run on the `dev` VM with a dedicated 16 GiB server limit. The runner attempted every downloaded source file with no file or record caps: 622 SQLite files in 12 shards, 4,391 DuckDB files in four shards, and 241 PostgreSQL regression SQL files in four shards. Each query retained the runner's five-second and 1 GiB limits, with at most two ClickHouse threads. PostgreSQL came from `postgres/postgres` revision `e7ef2cf256cc135da018899202d7c4ce167e0699`. Each shard completed with a zero exit status. The SQLite wall time was 2,800 seconds for the slowest shard. Outputs, checkpoints, and logs are under `/home/ubuntu/clickhouse/tmp/squality/results` and `/home/ubuntu/clickhouse/tmp/squality/build` on `dev`.

| Source suite | Files attempted | JSONL records | Matching queries | Result mismatches | SQL exceptions | Blocked setups |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| SQLite | 622 | 5,302,240 | 3,718,518 | 104,600 | 48,175 | 226 |
| DuckDB | 4,391 | 16,745 | 1,829 | 503 | 6,644 | 1,572 |
| PostgreSQL | 241 | 2,648 | 118 | 16 | 1,545 | 169 |

These are runner outcomes, not counts of distinct SQL statements or ClickHouse bugs. SQLite also had 1,424,882 source-condition skips and 5,835 passing setup statements. Its 226 blocked setups left 2,104,118 parsed records unreached, predominantly in index files. Of the 104,600 SQLite result mismatches, 103,112 SQL strings contain `/`; sampled failures show the known SQLite integer-division difference. This lexical grouping is not individual root-cause triage. Most of the other mismatches are in `select1.test`, `select2.test`, and `select3.test`, where the pilot identified correlated-name and `CASE NULL` semantic differences. All recorded SQLite result mismatches agreed with the SQLite reference oracle; none were classified as an oracle mismatch.

The SQL compatibility profile was applied throughout. At the time of the full pass, it did not yet include `allow_create_index_without_type=1`; that setting was added to the preset after a targeted run attempted all 12 SQLite evidence files and recorded 51 query passes and six mismatches. Those results overlap the main pass and are not added to the table. For SQLite index files, `default_table_engine=MergeTree`, `data_type_default_nullable=0`, and `allow_create_index_without_type=1` let `index/view/100/slt_good_1.test` run all 7,122 records: 3,270 setup statements and 3,852 matching queries, with no errors. Most of the other 214 index files use `UNIQUE` indexes, whose semantics the adapter cannot provide; a setting cannot make ignoring uniqueness a valid result oracle. The nonnullable default can change source behavior and was used only in this targeted index run.

DuckDB's full pass also recorded 1,851 files excluded for unsupported harness directives, 164 missing-fixture exclusions, 92 plan-oracle exclusions, and seven harness errors from raw non-UTF-8 result bytes. All seven affected files were rerun after the adapter classified those bytes as `unsupported_result_encoding`; the targeted reruns produced nine such classifications and zero harness errors. The 503 result mismatches require case-by-case triage. The `GROUPING` discrepancy tracked in [issue #124098](https://github.com/ClickHouse/ClickHouse/issues/124098) remains the confirmed ClickHouse bug found by this experiment.

The PostgreSQL parser provided 118 matching query comparisons, but those regression files depend on shared setup tables, data files, and `psql` commands. The isolated-file adapter does not reproduce that shared environment. Its 169 blocked setups and 29 excluded `psql` inputs explain why attempting all 241 files reached few of the paper's PostgreSQL cases. The 16 result mismatches include output formatting, `NULL` rendering, ordering, and dialect differences; none has been established as a ClickHouse bug. This pass demonstrates that SQLite contributes the bulk of portable coverage and that the current PostgreSQL adapter needs source-harness support before its corpus can be used as a broad oracle.
