`clickhousectl`(별칭 `chctl`)은 로컬 개발부터 ClickHouse Cloud까지 아우르는 ClickHouse 공식 CLI입니다. 터미널에서 직접 사용하는 사람은 물론 스크립트와 코딩 에이전트에서도 사용할 수 있습니다.

`clickhousectl`로 다음 작업을 수행할 수 있습니다.

* 로컬 ClickHouse 버전 설치 및 전환, 격리된 로컬 서버 실행, SQL 실행
* Docker 기반 Postgres 로컬 실행
* ClickHouse Cloud 서비스 생성, 구성, 확장, 백업 및 쿼리
* [ClickHouse Managed Postgres](/ko/products/managed-postgres/overview) 서비스 생성, 모니터링, 구성 및 복원
* 객체 스토리지, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB, BigQuery를 소스로 하는 ClickPipes 생성 및 운영
* [자체 관리형 ClickHouse Observability](/ko/clickstack/self-configured/deployment/managed) 서비스의 소스, 대시보드, 알림, 웹훅, 저장된 검색 및 역할 관리
* 실행 가능한 사용자 정의 함수(Executable UDFs)의 로컬 개발 및 ClickHouse Cloud 배포
* 조직 구성원, 초대, API 키 및 역할 관리
* 공식 ClickHouse agent skills를 코딩 에이전트에 설치

이 페이지에서는 대표적인 예시를 소개합니다. 모든 명령어와 플래그에 대한 공식 참고 자료는 `clickhousectl <command> --help`입니다. 대부분의 명령어는 도움말 끝에 `CONTEXT FOR AGENTS` 블록이 있으며, Cloud 명령어는 여기에 필요한 API Key 권한도 함께 나열합니다. 작업별 안내는 각 섹션의 가이드 링크를 참고하십시오. Cloud 중심의 개요는 [ClickHouse CLI](/ko/products/cloud/features/cli)를 참고하십시오.

## 설치 {#installation}

`clickhousectl`은 ARM64 및 x86&#95;64 아키텍처의 MacOS와 Linux에서 실행됩니다.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

설치 스크립트는 `~/.local/bin/clickhousectl`을 설치하고 `chctl` 별칭을 생성합니다. `~/.local/bin`이 `PATH`에 포함되어 있는지 확인하십시오.

패키지 매니저로 설치할 수도 있습니다.

| 도구                                | 명령                              |
| --------------------------------- | ------------------------------- |
| npm                               | `npm install -g clickhousectl`  |
| uv                                | `uv tool install clickhousectl` |
| pipx                              | `pipx install clickhousectl`    |
| pip                               | `pip install clickhousectl`     |
| cargo-binstall                    | `cargo binstall clickhousectl`  |
| Cargo, 소스 코드로부터 빌드 (Rust 1.94.1+) | `cargo install clickhousectl`   |

`chctl` 별칭은 설치 스크립트와 npm으로 설치한 경우에만 생성됩니다. 기존 설치를 업데이트하려면 `clickhousectl update`를 실행하십시오([자체 업데이트](#self-update) 참조). npm, uv, pipx, pip으로 설치한 경우에는 업데이트하는 대신 해당 패키지 매니저의 업그레이드 명령을 출력합니다.

### 셸 자동 완성 {#shell-completions}

Tab 키로 명령어, 플래그, 로컬 서버 이름, 설치된 버전을 자동 완성하려면 셸 시작 파일에 다음 한 줄을 추가하십시오. 이 한 줄로 `clickhousectl`과 `chctl`이 모두 등록됩니다.

```bash
eval "$(clickhousectl completions bash)"   # ~/.bashrc
eval "$(clickhousectl completions zsh)"    # ~/.zshrc, after compinit
clickhousectl completions fish | source    # ~/.config/fish/config.fish
```

자동 완성은 Tab 키를 누를 때마다 설치된 CLI를 실행하므로 `update` 후에도 항상 최신 상태가 유지됩니다.

## 요구 사항 {#requirements}

* Docker(로컬 Postgres를 사용하는 경우에만 필요)
* Cloud 명령어를 사용하려면 [ClickHouse Cloud](https://clickhouse.com/cloud) 계정이 필요합니다. 읽기 명령어는 브라우저 기반 OAuth(`cloud auth login`)로 실행할 수 있습니다. 리소스를 생성하거나 변경하려면 [API Key](/ko/products/cloud/features/admin-features/api/openapi)가 필요합니다. 자세한 내용은 [인증](#authentication)을 참조하십시오.

## 로컬 {#local}

Git에서 `.git/`이 있는 디렉터리가 프로젝트 루트이듯이, `.clickhouse/`가 있는 디렉터리가 프로젝트 루트입니다. 로컬 명령어는 현재 디렉터리 또는 그 상위 디렉터리 중 가장 가까운 프로젝트 루트를 사용하므로 프로젝트의 어느 하위 디렉터리에서든 실행할 수 있으며, 프로젝트 외부에서는 현재 디렉터리를 사용합니다. 스크립트나 CI 작업 등에서 프로젝트 루트를 명시적으로 지정하려면 `CLICKHOUSECTL_PROJECT_DIR`을 설정하십시오. 각 프로젝트의 서버 데이터는 `.clickhouse/`에 저장되며, ClickHouse 바이너리는 `~/.clickhouse/`에 두고 전역으로 공유합니다. 전체 워크플로는 [로컬 개발 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md)를 참조하십시오.

### 설치 및 버전 선택 {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
clickhousectl local install --binary ~/ClickHouse/build/programs/clickhouse   # A build of your own
```

| 셀렉터           | 의미                                              |
| ------------- | ----------------------------------------------- |
| `latest`      | 최신 ClickHouse 빌드. 설치, 사용, 시작 시마다 원격으로 확인합니다(권장) |
| `stable`      | 최신 안정 릴리스                                       |
| `lts`         | 최신 장기 지원(LTS) 릴리스                               |
| `26.8`        | 일치하는 최신 릴리스                                     |
| `26.8.1.1760` | 정확한 버전                                          |

`local use`는 필요하면 해당 버전을 설치하고, 이후 서버를 시작할 때 사용할 기본 버전으로 설정한 다음 `~/.local/bin/clickhouse`에 심볼릭 링크를 생성합니다. 따라서 `clickhouse client`와 `clickhouse local`을 `PATH`에서 바로 사용할 수 있습니다. 심볼릭 링크를 생성하지 않으려면 `--no-global`을 지정하십시오. 해당 경로에 일반 파일이 이미 있으면 변경하지 않습니다.

`local remove`는 기본 버전이나 어떤 프로젝트에서든 실행 중인 서버가 사용하는 버전은 제거하지 않습니다. `--force`를 지정하면 해당 서버를 중지한 뒤 버전을 제거하며, 기본 버전 설정과 심볼릭 링크도 함께 삭제합니다.

`local install --binary <path>`는 직접 빌드한 ClickHouse 바이너리를 복사하여 해당 바이너리가 보고하는 버전으로 설치합니다. 따라서 다른 설치 버전과 마찬가지로 `local use` 또는 `--version`으로 선택할 수 있습니다. 다시 빌드한 바이너리는 대개 동일한 버전을 보고하므로, 설치된 사본을 대체하려면 `--force`를 지정하십시오.

### 프로젝트 초기화 {#initializing-project}

```bash
clickhousectl local init
```

`init`은 현재 디렉터리(또는 `CLICKHOUSECTL_PROJECT_DIR`이 설정된 경우 해당 경로)를 프로젝트 루트로 지정합니다. 이 명령은 런타임 데이터를 저장할 `.clickhouse/` 디렉터리(git 무시 대상)를 생성하고, 커밋 가능한 스캐폴드인 `clickhouse/`(`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`, `config.d/`)와 `postgres/`(`tables/`, `views/`, `functions/`, `queries/`, `seed/`)도 함께 생성합니다. 다시 실행하면 누락된 항목만 생성되므로, 프로젝트를 클론한 후 한 번 실행하십시오. `init` 없이 서버를 시작해도 정상적으로 동작하며, 이 경우 현재 디렉터리에 `.clickhouse/`가 생성됩니다.

### 로컬 서버 실행 {#managing-servers}

```bash
clickhousectl local clickhouse start dev --version latest   # Background start; waits for readiness
clickhousectl local clickhouse start dev --no-wait          # Return after spawning
clickhousectl local clickhouse start dev --foreground       # Run in the foreground
clickhousectl local clickhouse start dev --http-port 8124 --tcp-port 9001
clickhousectl local clickhouse list                         # ClickHouse servers in this project
clickhousectl local clickhouse list --global                # Servers across all projects
clickhousectl local status                                  # Every ClickHouse server and Postgres instance in this project
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse stop-all                     # Stop every ClickHouse server in this project
clickhousectl local clickhouse remove dev                   # Permanently delete a stopped server's data
```

`local ch`는 `local clickhouse`의 축약형이며, 이전 이름인 `local server`도 별칭으로 계속 사용할 수 있습니다. 이름이 지정된 각 서버는 `.clickhouse/servers/<name>/data/`에 자체 데이터를 보관하며, 서버를 중지해도 데이터는 유지되어 다음에 시작할 때 다시 사용됩니다. 이름 없이 시작하면 `default`가 사용되며, `default`가 이미 실행 중이면 새 이름이 생성됩니다. 기본 포트는 HTTP 8123과 TCP 9000이며, 해당 포트가 사용 중이면 비어 있는 포트가 할당됩니다.

기존 서버를 대상으로 동작하는 명령어(`stop`, `client`, `dotenv`, `local client`, `local udf --server`)는 이름을 생략하면 `default`를 선택하고, `default`가 없으면 프로젝트에서 해당 엔진의 유일한 서버를 선택합니다. 서버가 여러 개이고 그중 `default`라는 이름의 서버가 없으면 `server_selection_required` 오류와 함께 실패하며 서버 이름 목록을 표시합니다. `remove`는 대상을 추측하지 않으며, 이름 없이 실행하면 `default`만 제거합니다. 스크립트에서는 이름을 명시적으로 지정하십시오.

`--version`은 기본값을 변경하지 않고 해당 시작에만 사용할 버전을 선택합니다. 버전을 지정하지 않았고 기본값도 없는 상태에서 시작하면 `latest`가 설치되지만 기본값으로 설정되지는 않습니다. 기본값으로 설정하려면 먼저 `local use latest`를 실행하십시오.

### 로컬 클라이언트로 SQL 실행하기 {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client`는 이름으로 지정한 서버에, 해당 서버를 실행하는 것과 동일한 ClickHouse 바이너리를 사용해 연결합니다. 이름을 지정하지 않으면 위의 선택 규칙을 따릅니다. `--` 뒤의 인수는 수정 없이 그대로 `clickhouse client`에 전달됩니다. 출력과 종료 상태는 JSON 모드에서도 `clickhouse client`가 반환하는 값이므로, 스크립트를 작성할 때는 SQL 출력 형식을 직접 지정하십시오.

### 사용자 정의 서버 구성 {#custom-config-files}

부분 XML 또는 YAML 구성 파일로 다음 세 위치에서 내장 기본값을 재정의할 수 있습니다.

| 위치                              | 적용 대상                                     | 적용 시점                   |
| ------------------------------- | ----------------------------------------- | ----------------------- |
| `~/.clickhouse/config.d/`       | 이 머신의 모든 서버                               | 서버를 시작할 때마다             |
| 프로젝트 루트의 `clickhouse/config.d/` | 프로젝트의 모든 서버. 저장소에 커밋하면 다른 사용자와 공유할 수 있습니다 | 서버를 시작할 때마다             |
| `~/.clickhouse/configs/`        | 해당 구성을 지정하여 시작한 서버                        | `--config NAME`을 사용할 때만 |

```bash
cat > clickhouse/config.d/logging.xml <<'XML'
<clickhouse>
    <logger><level>debug</level></logger>
</clickhouse>
XML
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local clickhouse configs          # List both config.d directories and the named configs
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse start dev --config analytics
```

시작할 때마다 이 파일들을 테이블에 나열된 순서대로 머지하며, 뒤에 오는 파일이 우선합니다. 따라서 각 파일에는 변경할 설정만 넣으면 됩니다. 파일을 편집하거나 `--config`를 제거한 내용은 다음 시작 시 반영됩니다. 관리되는 데이터 경로와 포트는 항상 구성 값보다 우선합니다.

### 연결 정보를 dotenv 파일에 저장하기 {#dotenv}

```bash
clickhousectl local clickhouse dotenv dev                                     # Writes .env
clickhousectl local clickhouse dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv`는 실행 중인 서버의 실제 포트를 읽어 `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_HTTP_PORT`를 기록하며, 사용자, 비밀번호, 데이터베이스를 함께 전달하면 이 값도 기록합니다. 기존 파일에 있던 다른 줄은 그대로 유지됩니다. 파일은 애플리케이션의 dotenv 로더로 불러오십시오. 출력된 프리뷰는 절대 `eval`로 실행하지 마십시오.

### 로컬 Postgres {#local-postgres}

로컬 Postgres는 Docker에서 실행되므로 Docker가 실행 중이어야 합니다. Postgres 17과 18을 지원하며, `18-alpine`과 같은 이미지 태그도 사용할 수 있습니다. 새 인스턴스는 기본적으로 18 버전을 사용합니다.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres list                       # Postgres instances in this project
clickhousectl local postgres stop app
clickhousectl local postgres stop-all                   # Stop every Postgres instance in this project
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

`local pg`는 `local postgres`의 약어입니다. 인스턴스는 이름과 주 버전으로 식별됩니다. 중지된 인스턴스를 재개하면 기존의 포트, 사용자, 비밀번호, 데이터베이스를 그대로 사용하므로 생성 시 지정한 플래그는 재개 시 적용되지 않습니다. 비밀번호를 직접 지정하지 않으면 무작위 비밀번호가 생성됩니다. `.env.local`에는 비밀번호가 포함되어 있으므로 버전 관리 대상에서 제외하십시오.

### 로컬 사용자 정의 함수(UDFs) {#local-udfs}

`local udf`는 `clickhouse/udfs/<name>/`에 있는 [실행 가능한 사용자 정의 함수(UDFs)](/ko/reference/functions/regular-functions/udf#executable-user-defined-functions)를 로컬 서버에 배포합니다. `cloud udf`는 같은 디렉터리를 Cloud에 업로드합니다([Cloud의 사용자 정의 함수(UDFs)](#cloud-udfs) 참조).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local clickhouse start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

`init`을 제외한 모든 명령어는 `--server <name>` 옵션을 지원합니다. 이 옵션을 생략하면 [선택 규칙](#managing-servers)에 따라 서버가 결정됩니다. `deploy`는 Cloud와 동일한 방식으로 `udf.json`을 검사합니다. 서버가 실행 중이면 함수를 다시 로드한 후 함수가 정상적으로 로드되었는지 확인합니다. `native` 런타임은 Linux amd64 또는 arm64 호스트에서만 로컬 배포가 가능합니다. 자세한 내용은 [사용자 정의 함수 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)를 참조하십시오.

## 인증 {#authentication}

Cloud 명령어는 다음 두 가지 인증 정보 유형 중 하나를 사용합니다.

| 인증 정보         | 권한                                                          | 저장 위치                                                                |
| ------------- | ----------------------------------------------------------- | -------------------------------------------------------------------- |
| 브라우저 기반 OAuth | 사용자 아이덴티티: 사용자가 속한 모든 조직에서 읽기 전용 Cloud 작업 및 읽기 전용 SQL 사용 가능 | `~/.clickhouse/tokens.json`, 전역으로 저장되며 여러 프로젝트에서 공유됨                 |
| API Key       | 하나의 조직으로 범위가 제한됨. 읽기 및 쓰기 작업 가능 여부는 키에 부여된 역할에 따라 결정됨       | 저장 시 프로젝트 루트의 `.clickhouse/credentials.json`에 저장되며, 모든 하위 디렉터리에서 인식됨 |

아직 ClickHouse Cloud 계정이 없다면 `clickhousectl cloud auth signup` 명령을 실행하십시오. 브라우저에서 가입 페이지가 열립니다.

### OAuth 로그인 {#oauth-login}

```bash
clickhousectl cloud auth login
```

이 명령을 실행하면 OAuth 디바이스 흐름(device flow)을 진행할 수 있도록 브라우저가 열립니다. 토큰은 `~/.clickhouse/tokens.json`에 전역으로 저장되며 자동으로 갱신됩니다.

<Note>
  OAuth는 **읽기 전용**입니다. 리소스를 생성하거나 변경하려면 [API Key](#api-key)로 로그인하십시오.
</Note>

### API Key {#api-key}

명령어 실행에 필요한 역할을 부여해 [API Key를 생성](/ko/products/cloud/features/admin-features/api/openapi)한 다음 저장하십시오. 대화형 프롬프트를 사용하면 시크릿이 셸 이력에 남지 않습니다.

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

로그인하면 키를 검증한 뒤 해당 키가 속한 아이덴티티를 출력합니다. API에서 거부한 키는 저장되지 않으며, 명령은 종료 코드 4로 종료됩니다. API에 연결할 수 없으면 경고를 표시하고 키를 저장합니다.

CI 및 기타 자동화 환경에서는 키를 저장하지 말고 시크릿 매니저를 통해 주입하십시오.

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

개발 환경에서는 CLI가 현재 디렉터리의 `.env` 파일에서도 이러한 변수를 읽으며, 현재 디렉터리에 해당 파일이 없으면 [프로젝트 루트](#local)의 파일에서 읽습니다. `.env` 파일은 버전 관리 대상에서 제외하십시오.

### 자격 증명 확인 및 삭제 {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami`는 두 가지 인증 정보 유형 모두에서 동작하며, 자격 증명이 거부되면 종료 코드 4를 반환합니다. `status`는 유효한 자격 증명이 하나도 없어도 종료 코드 0을 반환할 수 있으므로, 액세스 가능 여부를 확인하려면 `whoami`를 사용하세요. 로그아웃해도 환경 변수가 해제되거나 `.env`가 수정되지는 않습니다.

### 인증 정보 우선순위 {#credential-precedence}

다음 순서대로 확인하여 가장 먼저 사용 가능한 소스를 사용합니다.

1. `--api-key` 및 `--api-secret` 플래그
2. 프로젝트 루트의 `.clickhouse/credentials.json`
3. export된 환경 변수
4. 현재 디렉터리의 `.env`에 정의된 변수(없으면 프로젝트 루트의 `.env`)
5. 전역 OAuth 토큰

어떤 `cloud` 명령이든 `--debug`를 지정하면 선택된 인증 정보 소스와 API URL이 stderr에 출력됩니다.

```bash
clickhousectl cloud clickhouse list --debug
```

### 조직 선택 {#organizations}

조직 단위 명령어는 자격 증명으로 접근할 수 있는 조직이 정확히 하나일 때만 해당 조직을 자동으로 선택합니다. 그렇지 않은 경우 `--org-id`를 지정하거나, `--org-name`에 정확한 조직 이름을 지정하십시오. 둘 다 지정하지 않으면 명령은 종료 코드 2로 종료되며 각 조직의 ID와 이름을 표시합니다:

```bash
clickhousectl cloud org list
clickhousectl cloud clickhouse list --org-id <org-id>
clickhousectl cloud clickhouse list --org-name "My Org"
```

대부분의 리소스 명령은 위치 기반 ID 또는 정확한 `--name`을 인수로 받습니다. 권한, 제한된 키, 로그아웃 시 정리 작업에 대한 자세한 내용은 [인증 및 액세스](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md)를 참고하십시오.

## Cloud {#cloud}

Cloud 명령어는 [ClickHouse Cloud API](/ko/products/cloud/features/admin-features/api/api-overview)를 호출합니다. 생성 및 업데이트 요청은 API가 요청을 수락하는 즉시 반환되므로, 리소스가 원하는 상태에 도달할 때까지 `get`을 폴링하세요.

### 서비스 {#services}

`cloud clickhouse`는 ClickHouse Cloud 서비스를 관리하는 명령입니다. `cloud ch`는 이 명령의 축약형이며, 이전 이름인 `cloud service`도 별칭으로 계속 사용할 수 있습니다.

```bash
clickhousectl cloud clickhouse create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud clickhouse create --name app-dev \
  --ip-allow 203.0.113.10/32 --dotenv .env.local          # Password goes only to the file
clickhousectl cloud clickhouse list
clickhousectl cloud clickhouse get <service-id>
clickhousectl cloud clickhouse start <service-id>
clickhousectl cloud clickhouse stop <service-id>
clickhousectl cloud clickhouse wake <service-id>             # Wake an idle service
clickhousectl cloud clickhouse reset-password <service-id>
clickhousectl cloud clickhouse delete <service-id>           # Must be stopped; --force stops it first
```

생성 시 표시되는 초기 비밀번호는 한 번만 반환되므로 반드시 저장해 두십시오. `--dotenv [file]`(기본값 `.env`)을 사용하면 비밀번호는 해당 파일에만 기록되며, 터미널이나 JSON 출력에는 표시되지 않습니다. 생성 명령은 프로비저닝이 완료되기 전에 반환되므로, 상태가 `running`이 될 때까지 `get`을 반복해서 실행하십시오. **`--ip-allow`를 생략하면 모든 IP(`0.0.0.0/0`)가 허용됩니다.** 각 엔트리는 `IP_OR_CIDR=DESCRIPTION` 형식으로 지정합니다. `--region`에는 프라이빗 리전을 포함한 모든 리전 ID를 지정할 수 있으며, 유효성은 Cloud에서 검사합니다. `--backup-id`로 백업(backup)을 새 서비스에 복원하거나, `--byoc-id`로 서비스를 BYOC 인프라에 배치할 수 있습니다.

실행 중인 서비스에 연결하려면 다음과 같이 하십시오:

```bash
clickhousectl cloud clickhouse client <service-id>                     # Interactive clickhouse client
clickhousectl cloud clickhouse client --name analytics -q "SELECT version()"
clickhousectl cloud clickhouse dotenv <service-id> --local             # Write .env.local, without a password
```

`client`는 네이티브 TLS 프로토콜로 `clickhouse client`를 실행하고 브라우저를 통해 Cloud 사용자로 로그인하므로 서비스 비밀번호가 필요하지 않습니다. 이 명령은 설치된 ClickHouse 25.12 이상 버전(`clickhousectl local install latest`)을 사용하며 브라우저에서 사람이 직접 로그인해야 하므로, CI 및 에이전트 환경에서는 [`query`](#query-api)를 사용하십시오. `dotenv`는 `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_HTTP_PORT`, `CLICKHOUSE_USER`, `CLICKHOUSE_SECURE`를 기록하며 이 키들만 교체하므로, `create --dotenv`로 기록된 비밀번호는 그대로 유지됩니다.

서비스 업데이트, 확장 및 구성:

```bash
clickhousectl cloud clickhouse update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud clickhouse update <service-id> --deletion-protection true
clickhousectl cloud clickhouse profile list --region us-east-1
clickhousectl cloud clickhouse scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud clickhouse scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud clickhouse scale <service-id> --profile v1-highmem-s
clickhousectl cloud clickhouse settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud clickhouse upgrade-window set <service-id> --weekday 0 --start-hour 6
```

레플리카당 메모리는 4 GB의 배수로 지정하며, 무료 서비스는 최대 120 GB, 유료 서비스는 최대 356 GB까지 설정할 수 있습니다. 레플리카는 최대 50개까지 사용할 수 있습니다. 조직 및 웨어하우스(warehouse) 제한에 따라 이 값이 더 낮아질 수 있습니다. 수평 자동 확장을 사용하려면 조직에서 해당 기능이 활성화되어 있어야 합니다. `scale --profile`은 Enterprise 및 BYOC 조직에서 인스턴스 프로파일을 변경합니다. `update`는 전달한 플래그에 해당하는 항목만 변경합니다.

삭제 방지(`create --deletion-protection` 또는 `update --deletion-protection true|false`)가 설정된 서비스는 `--force`를 지정하더라도 `delete`가 오류 코드 `deletion_protected`를 반환하며 삭제를 거부합니다. 서비스를 삭제하려면 먼저 이 설정을 해제하십시오.

그 밖의 서비스 명령 그룹으로는 `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (베타), `jwt-provider` (베타, Enterprise 티어), `snapshot` (베타), `private-endpoint`, `query-endpoint`, `backup-config`, `prometheus`가 있습니다. 자세한 내용은 [클라우드 서비스 생성 및 운영](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md)을 참조하십시오.

### 쿼리 API {#query-api}

`cloud clickhouse query`는 로컬 `clickhouse` 바이너리나 서비스 비밀번호 없이 HTTP를 통해 SQL 문(SQL statement) 하나를 실행합니다.

```bash
clickhousectl cloud clickhouse query <service-id> --query "SELECT version()"
clickhousectl cloud clickhouse query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud clickhouse query <service-id>
```

* **OAuth**는 사용자 본인의 아이덴티티로 쿼리를 실행하며, 읽기 전용 SQL 액세스 권한을 가집니다. 서비스에는 아무것도 바인드되지 않습니다.
* **API Key:** 쿼리는 항상 활성 API Key를 사용합니다. 필요한 경우 clickhousectl이 해당 키를 서비스의 쿼리 API 엔드포인트에 추가하며, 엔드포인트가 없으면 `sql_console_admin` 역할로 엔드포인트를 생성합니다. 기존 역할, 오리진(origin) 및 다른 키 바인딩은 그대로 유지되며 새 키는 생성되지 않습니다. 이 동작 대신 실패 처리하려면 `--no-auto-enable`을 지정하십시오.

바인딩은 쓰기(write) 작업이므로 읽기 전용 API Key는 자기 자신을 바인드할 수 없습니다. 이 경우 쿼리는 `query_key_bind_forbidden`과 함께 종료 코드 1로 종료되며 아무것도 변경되지 않습니다. 쓰기 액세스 권한이 있는 키로 `query-endpoint create <service-id> --role <role> --open-api-key <key-id>`를 실행하여 한 번만 바인드하십시오(서비스에 아직 엔드포인트가 없으면 `--allowed-origins '*'`도 추가하십시오).

쿼리 API는 요청당 하나의 SQL 문만 허용합니다. SQL이 계속 실행 중이더라도 약 30초 후 타임아웃될 수 있으므로, 쓰기 작업을 재시도하기 전에 결과를 확인하십시오. 여러 SQL 문으로 구성된 스크립트, 대량 적재(bulk loads), 오래 실행되는 쿼리에는 [`cloud clickhouse client`](#services)를 사용하십시오. 서비스 IP 허용 목록은 직접 연결에만 적용되며, 프록시를 거치는 쿼리 API 경로에는 적용되지 않습니다. 유휴 상태의 서비스에 쿼리를 실행하면 서비스가 깨어납니다. 중지된 서비스는 `cloud clickhouse start`로 시작해야 합니다.

서비스의 쿼리 API 엔드포인트, 이름이 지정된 SQL 엔드포인트 및 저장된 쿼리(saved queries)를 관리하는 명령은 다음과 같습니다:

```bash
clickhousectl cloud clickhouse query-endpoint get <service-id>
clickhousectl cloud clickhouse query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create`는 엔드포인트에 연결된 모든 키의 역할을 교체합니다. 자세한 내용은 [SQL 및 쿼리 API 동작](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md)을 참조하십시오.

### Managed Postgres {#postgres-services}

`cloud postgres`(별칭 `cloud pg`)는 [ClickHouse Managed Postgres](/ko/products/managed-postgres/overview)를 관리합니다. GCP 지원은 비공개 프리뷰 단계입니다.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> --ha-type sync --standby-count 2
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres update <postgres-id> --deletion-protection true
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

AWS 크기로는 `m6gd.large`, `c6gd.xlarge`, `r6gd.xlarge` 등이 있습니다. GCP에서는 `--provider gcp`와 함께 GCP 리전과 `c4-standard-lssd-4` 같은 크기를 지정하십시오.

`create` 실행 시 반환되는 비밀번호와 연결 문자열(Connection String)을 저장해 두십시오. 이후 `get` 응답에는 자격 증명이 포함되지 않으며, 새 자격 증명은 `reset-password`로만 발급받을 수 있습니다. `psql`로 연결할 때는 `sslmode=verify-full`과 인증 기관(CA) 파일을 사용하십시오.

**create 시 액세스 플래그를 생략하면 Postgres(5432)와 PgBouncer(6432)에 대해 모든 IPv4 및 IPv6 주소가 허용됩니다.** 규칙마다 `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]`를 하나씩 지정하거나, 규칙을 두지 않으려면 `--block-public-access`를 지정하십시오. 규칙을 하나라도 지정하면 나열된 규칙만 적용됩니다.

`--standby-count`는 `create` 또는 `update` 시 핫 대기 인스턴스(Standbys)의 수를 설정합니다. `--ha-type none`은 0, `async`는 1, `sync`는 1 또는 2를 지정할 수 있습니다. 해당 기능이 제공되는 조직에서 삭제 방지가 켜져 있으면, `--deletion-protection false`를 설정하기 전까지 API가 `delete`를 거부합니다. AWS에서 프라이빗 연결을 구성하려면 `private-endpoint`(create, get, update, delete)로 PrivateLink 엔드포인트 서비스(베타)를 관리하십시오. 각 VPC 엔드포인트는 `private-endpoint update --add-vpc-endpoint`로 승인해야 연결할 수 있습니다.

모니터링 및 복구:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query`는 OAuth만 지원하므로, 우선순위가 더 높은 API Key 소스가 활성화되어 있으면 실패합니다. 모니터링에는 `metrics`, `slow-queries`, `prometheus`를 사용하며, `logs`, `metrics`, `slow-queries`, `backup list`에서는 ID 대신 `--name`도 사용할 수 있습니다. `restore`는 `--ip-allow` 또는 `--block-public-access`를 지정하지 않으면 원본 서비스의 현재 IPv4 액세스 규칙을 복원된 서비스에 그대로 복사합니다. 복원 및 레플리카 생성 시에는 비밀번호가 반환되지 않습니다. `promote`와 `switchover`는 요청이 수락되는 즉시 반환됩니다. promote 후에는 레플리카가 `isPrimary: true`를 보고할 때까지 `postgres get --json`을 폴링하십시오. 자세한 내용은 [Managed Postgres 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md)를 참조하십시오.

### ClickPipes {#clickpipes}

`cloud clickpipe`는 객체 스토리지, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB, BigQuery에서 데이터를 수집합니다. ClickPipe 생성과 스키마 탐색(schema discovery)을 하려면 API Key와 실행 중인 대상 서비스가 필요합니다. 소스마다 전용 `clickpipe create <source>` 하위 명령이 있으며, `--help`를 붙여 실행하면 사용 가능한 플래그를 확인할 수 있습니다.

다음은 IAM role을 사용하여 S3에서 파일을 로드하는 예시입니다. 먼저 스키마를 탐색하여 검토한 다음, 저장된 탐색 결과로 파이프를 생성하십시오.

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" --json > discovery.json
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --columns-from discovery.json
```

`--columns-from`은 발견된 필드를 대상 컬럼으로 변환하므로, 먼저 파일을 편집하여 필요 없는 필드를 삭제하십시오. 객체 스토리지, Kafka, Kinesis, Pub/Sub ClickPipe를 생성하려면 `--columns-from`과 하나 이상의 `--column name:type` 중 하나 또는 둘 다를 지정해야 합니다. `--column`으로 지정한 컬럼은 파일에서 가져온 컬럼에 추가됩니다.

CDC로 Postgres를 복제합니다. TLS는 기본적으로 검증됩니다. Managed Postgres 소스는 해당 인증 기관(CA)을 내보낸 후 전달하십시오:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud clickhouse query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping`은 `ReplacingMergeTree` 테이블을 생성하므로, 현재 상태(state)는 `FINAL WHERE _peerdb_is_deleted = 0`으로 조회하십시오. Postgres 및 MySQL 파이프를 생성할 때 `--use-json-native-format true`를 지정하면 JSON 열(JSON columns)을 `String` 대신 ClickHouse 네이티브 `JSON` 타입으로 저장할 수 있습니다(ClickHouse 25.3 이상이 필요하며, 조직에서 이 기능이 활성화되어 있어야 합니다). Kafka 파이프도 객체 스토리지와 동일한 패턴을 따릅니다. 동일한 소스 플래그로 `clickpipe schema-discover kafka`를 실행한 다음, `--column` 또는 `--columns-from`으로 컬럼을 전달하십시오.

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

BigQuery 파이프는 기본적으로 스냅샷을 실행합니다. CDC를 사용하려면 `--replication-mode cdc`와 `--replication-method`를 지정하고, `--table-mapping-json`에 테이블별 워터마크(watermark) 컬럼 또는 이벤트 함수를 전달하십시오. 동기화 일정은 `--sync-cron` 또는 `--sync-interval-seconds`로 설정합니다. 기존 파이프는 다음과 같이 관리합니다.

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

CDC 파이프는 `update` 전에 반드시 `Paused` 상태여야 합니다. 파이프를 중지하고 `Paused` 상태가 될 때까지 `get`으로 폴링한 다음 업데이트하십시오. 업데이트 과정에서 서비스가 파이프를 재개할 수 있으므로, `get`에 여전히 `Paused`가 표시되는 경우에만 `start`를 실행하십시오. `--start-paused`는 객체 스토리지, Kafka, Kinesis, Pub/Sub에서 사용할 수 있습니다. 그 밖의 명령 그룹으로는 `cdc-scaling`, `context get`(GCP 워크로드 아이덴티티 준비 상태 및 주체), `reverse-private-endpoint`가 있습니다. 자세한 내용은 [ClickPipes 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) 및 [ClickPipe 구성 참고 문서](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md)를 참조하십시오.

### ClickStack {#clickstack}

`cloud clickstack`은 기존 [자체 관리형 ClickHouse Observability](/ko/clickstack/self-configured/deployment/managed) 서비스의 소스, 대시보드, 알림, 웹훅, 저장된 검색 및 역할을 관리합니다. 리소스는 JSON 파일로 지정합니다(`--file`, stdin을 사용하려면 `-`). 읽기 작업은 OAuth를 지원하지만, 쓰기 작업에는 API Key가 필요합니다.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**ClickStack을 업데이트할 때마다 리소스 전체가 대체됩니다.** `get --json`으로 현재 상태를 저장한 다음, 변경된 필드만이 아니라 전체 정의를 전송하십시오. 자세한 내용은 [ClickStack 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md)를 참조하십시오.

### Cloud의 사용자 정의 함수(UDFs) {#cloud-udfs}

`cloud udf`는 조직 범위의 실행 파일 기반 UDF와 그 버전, 그리고 서비스 ATTACH를 관리합니다. `deploy`는 `local udf`로 테스트한 디렉터리를 업로드하고 빌드가 끝날 때까지 기다린 다음, 해당 버전을 ATTACH하고 배포가 완료될 때까지 대기합니다.

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud clickhouse query <service-id> --query "SELECT my_udf(1)"
```

각 단계를 직접 실행하려면 `udf create`, `udf version create`, `udf attach`(유휴 상태인 서비스에는 `--wake` 사용), `udf detach`, `udf delete`를 사용하십시오. 이 명령들은 요청이 수락되는 즉시 반환되므로, `udf get` 및 `udf attachment get`을 폴링하여 상태를 확인하십시오. 읽기 작업은 OAuth를 지원하지만, 쓰기 작업에는 API Key가 필요합니다. 자세한 내용은 [사용자 정의 함수 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)를 참조하십시오.

### 조직 및 액세스 {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

`cloud org` 하위 명령은 위치 기반 ID 대신 `--org-id`를 사용합니다. `org usage`는 최대 31일까지만 조회할 수 있습니다. `org`에는 `quota`, `balance`, `notification-types`, `role`(사용자 정의 조직 역할), `preview`(프리뷰 기능 조회 및 토글, 베타), `byoc`(BYOC 인프라. ClickHouse 직원의 액세스 허용 시점을 제어하는 `byoc access` 포함, 베타)도 있습니다. 알림 기능은 베타입니다.

멤버, 초대 및 API 키 관리:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

`member notification-settings`(베타)는 멤버 본인의 알림 재정의를 조회하고 업데이트합니다. 서비스 생성과 달리 **`key create`에서 `--ip-allow`를 생략하면 모든 네트워크 액세스가 거부됩니다**. 시크릿은 한 번만 표시됩니다. `key list`는 `--all`을 지정하지 않으면 한 페이지만 반환합니다. `key update`에서는 생략한 플래그의 기존 설정이 그대로 유지되며, `--clear-expiry`, `--clear-roles`, `--clear-ip-allow`를 지정하면 해당 설정이 제거됩니다.

### 백업 {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud clickhouse create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud clickhouse backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
```

복원 시 항상 새 서비스가 생성됩니다. `cloud backup bucket`(get, create, update, delete)은 공급자별 JSON 파일을 사용하여 사용자가 직접 관리하는 백업(backup) 버킷을 구성합니다. 자세한 내용은 [클라우드 서비스 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore)의 백업 섹션을 참조하십시오.

## JSON 출력 {#json-output}

로컬, Cloud, `skills`, `update`, `telemetry` 명령어 등 구조화된 데이터를 반환하는 명령어는 `--json` 옵션을 지원합니다:

```bash
clickhousectl cloud clickhouse list --json
clickhousectl cloud key list --all --json
clickhousectl local clickhouse list --json
```

CLI가 코딩 에이전트(Claude Code, Cursor, Codex, Gemini CLI, Goose, Devin 또는 `AI_AGENT`를 설정하는 모든 도구)를 감지하면 자동으로 JSON을 선택합니다. SQL 및 네이티브 클라이언트(native client)는 각각 고유한 포맷을 유지합니다. `cloud clickhouse query`는 JSON 모드에서 `JSONEachRow`를 반환하며, `local client` 출력은 항상 네이티브 포맷입니다. 쿼리 출력을 파싱하는 스크립트에서는 `--format`을 명시적으로 지정해야 합니다. 에이전트가 감지된 상태에서도 사람이 읽기 쉬운 출력 포맷을 유지하려면 `CLICKHOUSECTL_AUTO_JSON=0`을 설정하십시오. 이때도 `--json`을 명시하면 JSON이 선택됩니다.

`clickhouse create`, `postgres create`, `clickpipe start`와 같은 비동기 Cloud 명령어는 JSON 출력에 `next` 객체를 추가하여 실행할 폴링 명령을 지정합니다. 여기에는 `command`(실제 ID 및 `--org-id` 포함), 확인할 `field`, 완료를 나타내는 `until` 값, 실패를 나타내는 `fail_on` 값, 권장 폴링 간격인 `interval_seconds`가 포함됩니다. 명령어 자체는 API가 요청을 수락하는 즉시 반환됩니다.

JSON 모드에서는 런타임 오류가 일관된 `code`와 `message`를 포함하는 객체로 stderr에 출력됩니다:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

메시지가 아닌 `error.code`를 기준으로 분기하십시오. 사용법 오류는 텍스트로만 출력되며, 종료 코드는 2이고 아무것도 전송되지 않습니다. 출력 구조와 오류 코드는 [자동화 및 출력 계약](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md)을 참조하십시오.

## 종료 코드 {#exit-codes}

| 코드  | 의미                                                                                |
| --- | --------------------------------------------------------------------------------- |
| `0` | 성공. 비동기 Cloud 작업에서는 요청이 수락되었다는 의미이며, 작업이 완료되었다는 의미는 아닙니다                          |
| `1` | 오류. 요청 거부를 나타내는 HTTP 403도 포함됩니다(코드 `http_4xx`)                                    |
| `2` | 사용법 오류. 유효하지 않은 플래그 값이나 파싱 후 검사 단계에서 확인되는, 처리에 성공할 수 없는 입력이 포함됩니다. 아무것도 전송되지 않습니다 |
| `3` | `skills` 선택기와 같은 대화형 프롬프트가 취소되었습니다                                                |
| `4` | 인증이 필요하거나 거부되었습니다. OAuth를 사용한 쓰기 시도도 포함됩니다                                        |

`local client`, `local postgres client` 등 네이티브 클라이언트로 제어를 넘기는 명령은 해당 클라이언트의 종료 상태를 그대로 전달합니다.

## 에이전트 스킬 {#skills}

코딩 에이전트에 [공식 ClickHouse agent skills](https://github.com/ClickHouse/agent-skills)를 설치하십시오:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

Skills는 기본적으로 현재 프로젝트에 설치되며, `--global`을 사용하면 홈 디렉터리에 설치됩니다. 공유 디렉터리인 `.agents/skills/`는 항상 포함됩니다. 터미널이 없는 환경에서는 `--agent`, `--all` 또는 `--detected-only`를 지정해야 합니다. 지원되는 에이전트 이름을 확인하려면 `clickhousectl skills --help`를 실행하십시오.

```bash
clickhousectl search ip allow                   # Find commands and flags by keyword
clickhousectl search idle timeout --limit 10
clickhousectl feedback "cloud clickhouse create should accept a --wait flag"
```

`search <words>`는 명령어 이름, 설명, 플래그 및 에이전트 컨텍스트를 검색하여 가장 잘 일치하는 명령어를 나열합니다(기본 5개). 일치 항목이 없으면 결과를 출력하지 않고 종료 코드 0으로 종료됩니다.

`feedback`은 별도의 입력 요청이나 확인 절차 없이 clickhousectl 팀에 짧은 메시지(최대 500자)를 보냅니다. CLI로 수행하지 못한 작업이나 기대했던 동작을 알리는 데 사용하십시오. `--json`과 같은 옵션은 메시지 앞에 지정하고, 자격 증명, SQL, 호스트 이름 또는 개인 정보는 포함하지 마십시오. Cloud 자격 증명을 사용하면 해당 자격 증명이 속한 조직의 ID가 메시지에 포함됩니다. [피드백으로 전송되는 정보](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/feedback.md)를 참조하십시오.

## 자체 업데이트 {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

`update`는 설치 스크립트, 다운로드 또는 Cargo로 설치한 프로그램을 교체합니다. npm, uv, pipx 및 pip로 설치한 경우에는 종료 코드 1로 종료하고, 대신 실행할 패키지 관리자의 업그레이드 명령을 출력합니다.

CLI는 백그라운드에서도 24시간에 최대 한 번 업데이트를 확인하며(확인에 실패하면 1시간 후 재시도), 새 버전이 있으면 알림을 출력합니다. 업데이트 확인과 알림을 끄려면 `CLICKHOUSECTL_NO_UPDATE_CHECK=1`을 설정하십시오.

## 텔레메트리 {#telemetry}

`clickhousectl`은 개발 방향을 정하는 데 활용하기 위해 익명 사용 데이터를 수집합니다. 처음 실행할 때는 안내만 표시하고 데이터를 전송하지 않습니다. 수집을 비활성화하지 않으면 이후 실행부터 수집이 시작됩니다.

각 이벤트에는 다음이 포함됩니다.

* 명령 경로와 명시적으로 전달한 플래그 및 인수의 **이름**(값은 포함되지 않음)
* 실행 결과와 종료 코드
* 명령을 잘못 입력했을 때 CLI가 제안한 명령 또는 플래그 이름(실제로 입력한 내용은 포함되지 않음)
* 런타임 실패 시 사전에 정해진 범주로 제한된 정보: 실패 단계와 유형, 허용 목록에 있는 HTTP 상태 코드, 재시도, 프로비저닝 상태 및 소요 시간 범주
* CLI 버전, OS 및 아키텍처, CI 환경에서의 실행 여부, 감지된 코딩 에이전트

인수 값, SQL, 자격 증명, 리소스 식별자, `--` 뒤의 인수 및 오류 메시지는 절대 기록되지 않습니다. 설치 ID나 기기 ID도 없습니다.

수집을 비활성화하려면:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

`CHCTL_TELEMETRY_DEBUG=1`로 설정하면 아무것도 전송하지 않고 payload를 stderr에 출력합니다. 텔레메트리 수집을 거부해도 [`feedback`](#search-and-feedback) 명령은 계속 사용할 수 있으며, 이 명령은 실행할 때만 데이터를 전송합니다. 자세한 내용은 [텔레메트리 세부 정보](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md)를 참고하십시오.
