ClickHouse는 [`TimeSeries`](/ko/reference/engines/table-engines/integrations/time-series) 테이블을 기반으로 Prometheus HTTP API를 구현합니다. 하나의 핸들러에서 remote write, remote read, 인스턴트 PromQL 쿼리, 시간 범위 PromQL 쿼리를 모두 처리합니다.

Prometheus 서버가 스크레이프할 수 있도록 ClickHouse 자체 메트릭을 노출하려면 [Prometheus 메트릭 엔드포인트](/ko/concepts/features/connect-to-clickhouse/prometheus/metrics)를 참조하십시오.

## 사전 요구 사항 {#prerequisites}

설정 단계는 ClickHouse Cloud와 자체 관리형 ClickHouse 간에 차이가 있습니다. 사용 중인 배포 환경에 해당하는 섹션을 참고하십시오.

### ClickHouse Cloud {#prerequisites-cloud}

<Note>
  ClickHouse Cloud의 PromQL 지원은 비공개 프리뷰 단계입니다. 비공개 프리뷰에 참여하는 서비스에는 이미 `enable_time_series_table` 설정과 Prometheus API 엔드포인트가 구성되어 있습니다. 그 외의 ClickHouse Cloud 서비스에는 이 구성이 없으며, 해당 서비스에서는 이 기능을 직접 활성화할 수 없습니다. 다음 섹션에 나오는 `SET enable_time_series_table` SQL 문과 `http_handlers` 구성은 자가 관리형 배포에 적용됩니다.
</Note>

비공개 프리뷰에 참여하는 서비스를 사용한다면 [TimeSeries 테이블 생성](#create-a-timeseries-table) 단계로 진행하십시오. 해당 서비스는 [엔드포인트 표](#configure-prometheus-api)에 나열된 엔드포인트 경로를 제공합니다.

### 자가 관리형: TimeSeries 설정 활성화 {#enable-the-timeseries-setting}

테이블을 생성하고 액세스하는 사용자에게 `enable_time_series_table` 설정을 활성화하십시오:

```sql
SET enable_time_series_table = 1;
```

HTTP API 요청을 사용하려면 API 사용자의 프로필에서 `enable_time_series_table`을 활성화하세요.

### 자가 관리형: Prometheus API 엔드포인트 구성 {#configure-prometheus-api}

ClickHouse의 기본 HTTP 포트에 접두사 기반으로 라우팅되는 핸들러 1개를 구성하십시오.

```xml
<http_handlers>
    <defaults/>
    <rule>
        <url_prefix>/prometheus/api/v1</url_prefix>
        <handler>
            <type>prometheus_api_v1</type>
        </handler>
    </rule>
</http_handlers>
```

`<defaults/>`는 `/ping` 같은 엔드포인트와 SQL 요청을 처리하는 내장 핸들러를 그대로 유지합니다. 위의 접두사를 사용하면 하나의 핸들러로 다음 엔드포인트를 노출합니다:

| 엔드포인트                                    | 용도                      |
| ---------------------------------------- | ----------------------- |
| `/prometheus/api/v1/write`               | Prometheus remote write |
| `/prometheus/api/v1/read`                | Prometheus remote read  |
| `/prometheus/api/v1/query`               | 인스턴트 PromQL 쿼리   |
| `/prometheus/api/v1/query_range`         | 시간 범위 PromQL 쿼리         |
| `/prometheus/api/v1/format_query`        | PromQL 표현식 서식 지정        |
| `/prometheus/api/v1/series`              | 시계열 메타데이터               |
| `/prometheus/api/v1/labels`              | 레이블 이름                  |
| `/prometheus/api/v1/label/<name>/values` | 레이블 값                   |
| `/prometheus/api/v1/metadata`            | 메트릭 그룹 메타데이터            |
| `/prometheus/api/v1/federate`            | 최신 표본(sample) 페더레이션             |

이 예시에서는 핸들러에 `database`와 `table`을 지정하지 않습니다. 따라서 각 요청에서 `table` 쿼리 매개변수(query parameter)를 지정해야 합니다(단, `/format_query`는 주어진 PromQL 표현식을 파싱하기만 하므로 테이블이 필요하지 않습니다). 요청에서 `database`를 함께 지정하거나, `prometheus.metrics`처럼 데이터베이스 이름을 포함한 테이블 이름(table name)을 사용할 수도 있으며, 데이터베이스를 생략하면 `default`가 사용됩니다. 이렇게 하면 하나의 핸들러로 여러 `TimeSeries` 테이블을 처리할 수 있습니다.

모든 요청에 하나의 고정된 테이블을 사용하려면 핸들러에서 다음과 같이 구성하십시오:

```xml
<handler>
    <type>prometheus_api_v1</type>
    <database>prometheus</database>
    <table>metrics</table>
</handler>
```

핸들러에 구성된 테이블(table)은 요청 매개변수로 재정의할 수 없습니다.

라우팅 및 핸들러 설정:

| 이름           | 기본값 | 설명                                                                                                                          |
| ------------ | --- | --------------------------------------------------------------------------------------------------------------------------- |
| `url_prefix` | 없음  | 구성된 접두사로 시작하는 모든 요청 경로에 일치하는 규칙 필터(filter)입니다.                                                                              |
| `table`      | 없음  | `TimeSeries` 테이블의 이름입니다. 생략하면 요청에 `table` 쿼리 매개변수(query parameter)를 반드시 제공해야 합니다. 구성된 이름에는 데이터베이스(database) 이름을 포함할 수 있습니다. |
| `database`   | 없음  | 테이블이 속한 데이터베이스입니다. 요청의 쿼리 매개변수로 지정할 수 있습니다. 생략하면 ClickHouse는 `table` 값에 포함된 데이터베이스 이름을 사용하며, 포함되어 있지 않으면 `default`로 폴백합니다.  |

### TimeSeries 테이블 생성 {#create-a-timeseries-table}

데이터베이스와 `TimeSeries` 테이블을 생성합니다.

```sql
CREATE DATABASE prometheus;
CREATE TABLE prometheus.metrics ENGINE = TimeSeries;
```

## remote write로 메트릭 수집하기 {#remote-write}

ClickHouse는 [Prometheus 원격 쓰기(remote-write) 프로토콜](https://prometheus.io/docs/specs/remote_write_spec/)을 지원합니다. Prometheus가 이 핸들러로 데이터를 쓰도록 다음과 같이 구성하십시오.

```yaml
remote_write:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/write?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

Prometheus는 표본(sample)을 `prometheus.metrics` 테이블(table)로 전송합니다.

ClickHouse는 동시에 들어오는 여러 remote-write 요청의 데이터를 배치로 묶어 더 적은 수의 파트에 저장하기 위해 [비동기 삽입(asynchronous inserts)](/ko/reference/settings/session-settings/async-insert#async_insert)을 사용합니다. 비동기 삽입은 기본적으로 활성화되어 있으며, URL 또는 사용자 프로필의 `async_insert` 설정으로 활성화하거나 비활성화할 수 있습니다.

ClickHouse는 [`wait_for_async_insert`](/ko/reference/settings/session-settings/wait-for#wait_for_async_insert) 설정과 관계없이 데이터가 `TimeSeries` 테이블의 모든 내부 테이블(tables)에 플러시된 후에만 비동기 remote-write 요청에 확인 응답을 보냅니다. remote-write 프로토콜은 확인 응답을 받은 쓰기(write)가 영구 저장되었다고 간주하기 때문입니다. 플러시가 실패하면 요청은 오류를 반환하고 Prometheus가 재시도합니다.

각 요청이 플러시를 기다려야 하므로 비동기 삽입을 사용하면 단일 전송자의 쓰기 속도가 제한됩니다. Prometheus는 remote-write 세그먼트마다 요청을 하나씩 전송합니다. 여러 세그먼트가 동시에 전송하면 적응형 플러시 타임아웃이 [`async_insert_busy_timeout_max_ms`](/ko/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms)까지 늘어납니다. 단, 대기 중인 요청의 데이터 크기가 먼저 [`async_insert_max_data_size`](/ko/reference/settings/session-settings/async-insert#async_insert_max_data_size)에 도달하면 그 전에 플러시됩니다. 요청은 해당 배치가 플러시될 때까지 기다리며, 이 대기 시간은 배치 시작 시점부터 최대 해당 타임아웃만큼 걸릴 수 있습니다. 따라서 부하가 지속되면 각 세그먼트의 쓰기 속도는 대략 `samples per request / async_insert_busy_timeout_max_ms`가 됩니다. Prometheus는 기본적으로 요청당 최대 2,000개의 표본(sample)을 전송합니다. 이 속도를 높이려면 다음과 같이 설정하십시오.

* [`remote_write`](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write)의 `queue_config`에서 `max_shards`(기본값 50) 또는 `max_samples_per_send`를 늘리십시오. Prometheus는 전송이 밀리면 자동으로 세그먼트 수를 `max_shards`까지 늘립니다.
* URL 또는 사용자 프로필에서 `async_insert_busy_timeout_max_ms`를 낮추십시오. 예를 들어 `&async_insert_busy_timeout_max_ms=50`으로 설정합니다. 그러면 플러시가 더 자주 수행되며, 플러시할 때마다 내부 테이블에 새 파트가 생성됩니다.
* `async_insert=0`으로 비동기 삽입을 비활성화하십시오. 그러면 각 요청이 내부 테이블에 별도의 파트를 생성합니다.

## PromQL로 쿼리하기 {#promql-query-support}

instant-query 엔드포인트를 사용하면 특정 시점을 기준으로 PromQL 표현식을 평가할 수 있습니다:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

시간 범위에 대해 표현식을 평가하려면 범위 쿼리(range-query) 엔드포인트를 사용하십시오.

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

쿼리 엔드포인트는 폼 body로 전달된 매개변수도 받을 수 있습니다. `--get`을 지정하지 않으면 curl은 매개변수를 `application/x-www-form-urlencoded` 형식으로 `POST`를 통해 전송합니다.

```bash
curl --user default:<password> \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

PromQL 표현식을 평가하지 않고 파싱하고 포맷하려면 format-query 엔드포인트를 사용하십시오:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/format_query" \
  --data-urlencode "query=sum by(job)(http_requests_total{code=\"200\"})/2"
```

표현식은 구문 분석된 쿼리(parsed query)를 다시 직렬화한 형태로 반환됩니다. 이때 공백 문자는 정규화되고, 주석은 제거되며, 불필요한 괄호는 삭제되고, 기간(duration)은 파서가 허용하는 단위로 출력됩니다. 예: `sum by (job) (http_requests_total{code="200"}) / 2`. 기간은 초 단위 숫자로 변환되지 않고 원래 단위를 그대로 유지하므로 `rate(x[5m])`는 `rate(x[5m])`로 반환됩니다. 하나의 단위로 나누어떨어지지 않는 기간은 필요한 단위를 모두 사용해 표기되므로 `rate(x[90s])`는 `rate(x[1m30s])`로 반환됩니다. 이 엔드포인트는 표현식을 평가하지 않으므로 `database` 및 `table` 매개변수가 필요하지 않습니다.

HTTP API, `promql` 방언, 테이블 함수에서 사용하는 함수 및 집계 연산자 목록은 [지원되는 PromQL 기능](/ko/reference/functions/table-functions/prometheusQueryRange#supported-promql-features)을 참고하십시오.

그 밖의 요청 매개변수는 ClickHouse 설정으로 적용됩니다(예: `max_execution_time=10`). 쿼리 엔드포인트는 VictoriaMetrics 및 Thanos의 일부 매개변수도 지원합니다. `nocache=1`은 `use_query_cache=0`을 설정하고, `partial_response=false`는 `skip_unavailable_shards=0`을 설정하며, `dedup=false`, `trace`, `round_digits`는 무시됩니다. `extra_label` 및 `extra_filters`는 ClickHouse가 이러한 필터를 적용하지 않으므로 오류와 함께 거부되며, `dedup=true` 및 `partial_response=true`는 ClickHouse가 Thanos의 중복 제거나 부분 응답을 구현하지 않으므로 거부됩니다.

### Grafana {#grafana}

기준 URL이 `/api/v1` 앞에서 끝나도록 Prometheus 데이터 소스를 구성하세요.

```yaml
apiVersion: 1
datasources:
  - name: ClickHouse Prometheus
    type: prometheus
    access: proxy
    url: https://clickhouse.example.com:8443/prometheus
    basicAuth: true
    basicAuthUser: default
    jsonData:
      httpMethod: POST
      customQueryParameters: database=prometheus&table=metrics
    secureJsonData:
      basicAuthPassword: <password>
```

Grafana는 이 기준 URL 끝에 `/api/v1/query` 또는 `/api/v1/query_range`를 붙이고, 각 요청에 `customQueryParameters`를 추가합니다.

`httpMethod: POST`를 사용하면 Grafana는 쿼리 매개변수를 요청 body에 담아 전송합니다. ClickHouse는 요청 body와 URL 쿼리 문자열을 모두 읽으므로 이 경우에도 `customQueryParameters`가 적용됩니다. URL에는 길이 제한이 있으므로 긴 PromQL 표현식에는 `POST`를 사용하십시오.

<Note>
  구현된 엔드포인트는 쿼리 엔드포인트인 `/api/v1/query`, `/api/v1/query_range`, `/api/v1/format_query`, 메타데이터 엔드포인트인 `/api/v1/series`, `/api/v1/labels`, `/api/v1/label/<name>/values`, `/api/v1/metadata`, 그리고 [페더레이션](#federation) 엔드포인트인 `/api/v1/federate`뿐입니다. `/api/v1/series`에는 `match[]` 시계열 셀렉터가 최소 1개 필요하며, 선택 사항인 `start`, `end`, `limit` 매개변수를 지원하고, 각 셀렉터와 일치하는 시계열의 유니온(union)을 반환합니다. `/api/v1/labels`는 동일한 매개변수를 받되 `match[]`는 선택 사항이며, 일치하는 시계열의 레이블 이름을 정렬하여 반환합니다(셀렉터를 지정하지 않으면 모든 시계열이 대상입니다). `/api/v1/label/<name>/values`는 `/api/v1/labels`와 동일한 매개변수를 받으며, 특정 레이블 하나의 값을 정렬하여 반환합니다. 이때 `[a-zA-Z0-9_]` 이외의 문자가 포함된 레이블 이름은 `<name>`에 Prometheus의 `U__...` 이스케이프 처리를 적용하여 지정할 수도 있습니다. 이 엔드포인트들은 Grafana Prometheus 데이터 소스가 레이블 탐색, 템플릿 변수, 쿼리 빌더 자동 완성에 사용하는 기능을 모두 지원합니다.
</Note>

### SQL 진입점 {#sql-entry-points}

ClickHouse는 HTTP API, `promql` 방언, 그리고 [`prometheusQuery`](/ko/reference/functions/table-functions/prometheusQuery) 및 [`prometheusQueryRange`](/ko/reference/functions/table-functions/prometheusQueryRange) 테이블 함수에서 모두 동일한 PromQL 컨버터를 사용합니다.

다음과 같이 `clickhouse-client`에서 PromQL을 직접 실행할 수 있습니다:

```bash
clickhouse-client \
  --dialect promql \
  --promql_database prometheus \
  --promql_table metrics \
  --query 'rate(http_requests_total[5m])'
```

테이블 함수(table functions)를 사용하면 SQL 쿼리(SQL query)에 PromQL을 포함할 수 있습니다:

```sql
SELECT *
FROM prometheusQuery(
    prometheus.metrics,
    'rate(http_requests_total[5m])',
    now()
);
```

## 메트릭 메타데이터 쿼리 {#metadata}

`/prometheus/api/v1/metadata` 엔드포인트는 `TimeSeries` 테이블의 `Metrics` target table에 저장된 메트릭 메타데이터, 즉 각 메트릭 그룹의 유형, 도움말 텍스트, 단위를 반환합니다. 이 엔드포인트는 URL 쿼리 문자열에서 다음 Prometheus 매개변수를 지원합니다.

| 매개변수(Parameter)    | 설명                                                               |
| ------------------ | ---------------------------------------------------------------- |
| `metric`           | 지정한 메트릭 그룹의 메타데이터만 반환합니다.                                       |
| `limit`            | 반환할 메트릭 그룹 수를 제한합니다. 음수 값은 제한 없음을 의미하며, 0이면 메트릭 그룹을 반환하지 않습니다. |
| `limit_per_metric` | 메트릭 그룹별로 반환할 메타데이터 객체 수를 제한합니다. 0과 음수 값은 제한 없음을 의미합니다.          |

기본 `Metrics` target table은 메트릭 그룹 이름으로 정렬된 `ReplacingMergeTree`이며, 메트릭 그룹별로 가장 최근에 기록된 메타데이터 엔트리를 유지합니다. 그룹당 여러 엔트리가 반환되는 것은 target table에 해당 엔트리가 저장되어 있을 때뿐입니다. 즉, 파트가 머지되기 전이거나 엔트리를 보존하는 엔진으로 테이블을 정의한 경우에만 반환됩니다.

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/metadata" \
  --data-urlencode "metric=http_requests_total" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

## 메트릭 페더레이션 {#federation}

ClickHouse는 `/prometheus/api/v1/federate` 경로에서 [Prometheus 페더레이션](https://prometheus.io/docs/prometheus/latest/federation/) 엔드포인트를 지원합니다(`query` 유형의 핸들러가 처리하는 경로 중 `/federate`로 끝나는 모든 경로에서도 지원합니다). `match[]` 셀렉터와 일치하는 각 시계열에 대해 최근 5분 동안의 표본(sample) 중 가장 최신 표본(sample)을 Prometheus 텍스트 형식으로 반환하므로 Prometheus 서버에서 이를 스크레이프할 수 있습니다:

```yaml
scrape_configs:
  - job_name: clickhouse-federate
    honor_labels: true
    scheme: https
    metrics_path: /prometheus/api/v1/federate
    params:
      'match[]': ['{job="node"}']
      table: ['prometheus.metrics']
    static_configs:
      - targets: ['clickhouse.example.com:8443']
```

## remote read로 메트릭 읽기 {#remote-read}

ClickHouse는 `/prometheus/api/v1/read` 엔드포인트에서 [Prometheus remote-read 프로토콜](https://prometheus.io/docs/prometheus/latest/querying/remote_read_api/)을 지원합니다.

동일한 `TimeSeries` 테이블에서 데이터를 읽도록 Prometheus 서버를 다음과 같이 구성하십시오.

```yaml
remote_read:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/read?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

## 기록 규칙 {#recording-rules}

ClickHouse는 Prometheus 규칙 파일을 평가하지 않습니다. 대신 [갱신 가능 구체화 뷰](/ko/reference/statements/create/view#refreshable-materialized-view)로 [기록 규칙(recording rule)](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/)과 같은 작업을 수행할 수 있습니다. 갱신 가능 구체화 뷰는 일정에 따라 PromQL 표현식을 평가하고 그 결과를 `TimeSeries` 테이블 끝에 추가합니다. 다음 뷰는 1분마다 `sum by (job) (rate(http_requests_total[5m]))`를 `job:http_requests:rate5m`으로 기록합니다.

```sql
CREATE MATERIALIZED VIEW prometheus.job_http_requests_rate5m
REFRESH EVERY 1 MINUTE APPEND TO prometheus.metrics (tags, samples) AS
SELECT
    mapUpdate(CAST(tags, 'Map(String, String)'), map('__name__', 'job:http_requests:rate5m')) AS tags,
    [(timestamp, value)] AS samples
FROM prometheusQuery(prometheus.metrics, 'sum by (job) (rate(http_requests_total[5m]))', toStartOfMinute(now()));
```

갱신할 때마다 현재 분의 시작 시점을 기준으로 표현식을 평가하고, `mapUpdate`로 메트릭 이름을 설정한 뒤, 결과(result)의 각 시계열마다 표본(sample) 하나를 끝에 추가합니다. 같은 맵에 추가 레이블을 넣을 수도 있습니다(예: `map('__name__', 'job:http_requests:rate5m', 'team', 'web')`). 기록된 시계열은 다른 메트릭과 동일한 방식으로 쿼리할 수 있습니다.

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=job:http_requests:rate5m" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

마지막 평가 시간과 오류는 [`system.view_refreshes`](/ko/reference/system-tables/view_refreshes)에서 확인할 수 있습니다.

뷰(view)는 다음과 같은 점에서 Prometheus 기록 규칙(recording rule)과 다릅니다.

* 평가 시점은 갱신이 실행되는 시점의 `now()`입니다. 뷰는 일정에 따른 갱신 외에도 생성 직후(`EMPTY`로 생성한 경우 제외), 갱신이 조정되지 않는 경우 서버 재시작 후(Replicated 또는 Shared 데이터베이스(database) 외부에 있는 뷰나 `all_replicas = 1`로 설정된 뷰는 마지막 갱신을 기억하지 않음), 그리고 예정된 갱신을 놓친 뒤 `SYSTEM START VIEW`로 재개될 때에도 갱신됩니다. 이러한 갱신으로 인해 예정된 갱신 사이에 표본(sample)이 추가되지 않도록 예시처럼 `now()`를 인터벌 단위로 내림하십시오. 그래도 추가 갱신으로 인해 동일하게 반올림된 타임스탬프에 두 번째 표본(sample)이 기록될 수 있습니다. 5분 단위 규칙에는 `toStartOfInterval(now(), INTERVAL 5 MINUTE)`를 사용하십시오.
* 누락된 평가는 나중에 보충되지 않습니다. 서버가 중단되었거나 뷰가 정지된 후에는 뷰가 현재 인터벌만 평가하며, 그 이전 인터벌은 빈 상태로 남습니다. 갱신이 인터벌보다 오래 걸릴 때도 마찬가지입니다.
* 결과에서 빠진 시계열에는 staleness 마커가 붙지 않으므로, 쿼리는 lookback 기간(기본값 5분) 동안 해당 시계열의 마지막 기록 값을 계속 반환합니다.
* 규칙 파일이 없으며, 각 규칙은 별도의 뷰로 존재합니다. 규칙은 `/api/v1/rules`에 나열되지 않습니다.
