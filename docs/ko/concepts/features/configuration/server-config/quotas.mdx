<Info>
  **ClickHouse Cloud의 QUOTA**

  ClickHouse Cloud에서도 QUOTA를 지원하지만, [DDL 구문](/ko/reference/statements/create/quota)을 사용해 생성해야 합니다. 아래에 설명된 XML 구성 방식은 **지원되지 않습니다**.
</Info>

QUOTA를 사용하면 일정 기간 동안의 리소스 사용량을 제한하거나 리소스 사용을 추적할 수 있습니다.
QUOTA는 사용자 구성 파일에 설정되며, 일반적으로 &#39;users.xml&#39;을 사용합니다.

시스템에는 단일 쿼리의 복잡성을 제한하는 기능도 있습니다. [쿼리 복잡성 제한](/ko/concepts/features/configuration/settings/query-complexity) 섹션을 참조하십시오.

쿼리 복잡성 제한과 달리, QUOTA에는 다음과 같은 특징이 있습니다.

* 단일 쿼리를 제한하는 대신, 일정 기간 동안 실행할 수 있는 쿼리 집합에 제한을 둡니다.
* 분산 쿼리 처리 중 모든 원격 서버에서 사용된 리소스를 집계합니다.

이제 QUOTA를 정의하는 &#39;users.xml&#39; 파일의 섹션을 살펴보겠습니다.

```xml
<!-- Quotas -->
<quotas>
    <!-- Quota name. -->
    <default>
        <!-- Restrictions for a time period. You can set many intervals with different restrictions. -->
        <interval>
            <!-- Length of the interval. -->
            <duration>3600</duration>

            <!-- Unlimited. Just collect data for the specified time interval. -->
            <queries>0</queries>
            <query_selects>0</query_selects>
            <query_inserts>0</query_inserts>
            <errors>0</errors>
            <result_rows>0</result_rows>
            <read_rows>0</read_rows>
            <execution_time>0</execution_time>
        </interval>
    </default>
</quotas>
```

기본적으로 QUOTA는 사용량을 제한하지 않으면서 매시간 리소스 사용량을 추적합니다.
각 인터벌별로 계산된 리소스 사용량은 각 요청 후 서버 로그에 출력됩니다.

```xml
<statbox>
    <!-- Restrictions for a time period. You can set many intervals with different restrictions. -->
    <interval>
        <!-- Length of the interval. -->
        <duration>3600</duration>

        <queries>1000</queries>
        <query_selects>100</query_selects>
        <query_inserts>100</query_inserts>
        <written_bytes>5000000</written_bytes>
        <written_rows>100000</written_rows>
        <errors>100</errors>
        <result_rows>1000000000</result_rows>
        <read_rows>100000000000</read_rows>
        <execution_time>900</execution_time>
        <failed_sequential_authentications>5</failed_sequential_authentications>
    </interval>

    <interval>
        <duration>86400</duration>

        <queries>10000</queries>
        <query_selects>10000</query_selects>
        <query_inserts>10000</query_inserts>
        <errors>1000</errors>
        <result_rows>5000000000</result_rows>
        <result_bytes>160000000000</result_bytes>
        <read_rows>500000000000</read_rows>
        <result_bytes>16000000000000</result_bytes>
        <execution_time>7200</execution_time>
    </interval>
</statbox>
```

&#39;statbox&#39; QUOTA의 경우, 제한은 매시간 및 24시간마다(86,400초) 설정됩니다. 시간 인터벌은 구현에 따라 정의된 고정 시점을 기준으로 계산됩니다. 즉, 24시간 인터벌이 반드시 자정에 시작되는 것은 아닙니다.

인터벌이 끝나면 수집된 모든 값이 초기화됩니다. 다음 1시간 동안의 QUOTA 계산이 다시 시작됩니다.

제한할 수 있는 항목은 다음과 같습니다:

`queries` – 총 요청 수입니다.

`query_selects` – 총 select 요청 수입니다.

`query_inserts` – 총 insert 요청 수입니다.

`errors` – 예외를 발생시킨 쿼리 수입니다.

`result_rows` – 결과로 반환된 총 행 수입니다.

`result_bytes` - 결과로 반환된 행의 총 크기입니다.

`read_rows` – 모든 원격 서버에서 쿼리를 실행하기 위해 TABLES에서 읽은 source 행의 총수입니다.

`read_bytes` - 모든 원격 서버에서 쿼리를 실행하기 위해 TABLES에서 읽은 총 크기입니다.

`written_bytes` - 쓰기 작업의 총 크기입니다.

`written_rows` - `INSERT` 쿼리로 기록된 행의 총수입니다.

`execution_time` – 총 쿼리 실행 시간(초, wall time)입니다.

`failed_sequential_authentications` - 연속 인증 오류의 총횟수입니다.

`queries_per_normalized_hash` – 개별 정규화된 쿼리(normalized query)의 최대 실행 횟수입니다. 정규화된 쿼리는 리터럴(literals)을 자리표시자로 대체한 쿼리이므로, `SELECT 1`과 `SELECT 2`는 동일한 정규화된 쿼리로 간주됩니다. 이 제한은 서로 다른 정규화된 쿼리 패턴(normalized query pattern)마다 개별적으로 추적됩니다.

위에서 미리 정의한 항목 외에도, 이벤트 이름을 태그로 사용하여 모든 프로파일 이벤트(Profile Event)([system.events](/ko/reference/system-tables/events) 테이블 참조)에 제한을 설정할 수 있습니다. 예시는 다음과 같습니다.

```xml
<interval>
    <duration>86400</duration>
    <!-- At most 100000 S3 GET requests and 50 failed queries per day. -->
    <S3GetObject>100000</S3GetObject>
    <FailedQuery>50</FailedQuery>
</interval>
```

동일한 내용을 DDL 구문으로 표현할 수도 있습니다.

```sql
CREATE QUOTA s3_reads FOR INTERVAL 1 day MAX S3GetObject = 100000, FailedQuery = 50 TO my_user;
```

미리 정의된 양과 달리, 프로파일 이벤트(profile events)는 쿼리가 종료되는 시점(성공 또는 오류 여부와 관계없이)에 쿼리당 한 번 집계됩니다. 즉, 한도를 초과한 쿼리도 끝까지 실행될 수 있으며, 이후의 쿼리는 해당 인터벌이 끝날 때까지 거부됩니다. 사용량은 [system.quotas&#95;usage](/ko/reference/system-tables/quotas_usage) 테이블의 `profile_events` 컬럼에서 확인할 수 있습니다. 쿼리 외부에서 누적된 프로파일 이벤트(예: 백그라운드 머지로 인한 이벤트)는 쿼터에 집계되지 않습니다.

분산 쿼리(Distributed Query)에서는 원격 서버가 initiator에 보고하는 프로파일 이벤트가 로컬 프로파일 이벤트와 함께 쿼리를 시작한 사용자의 쿼터에 집계됩니다. 원격 서버는 쿼리 자체, 해당 쿼리의 `SETTINGS` 절, 또는 원격 서버에 있는 사용자의 설정 제약 조건에 지정된 `send_profile_events` 설정과 관계없이 분산 쿼리에 대해 항상 이러한 보고를 전송하므로, 사용자가 이를 끌 수 없습니다. 여기에는 `Distributed` 테이블 또는 `remote` 테이블 함수에 대한 동기 `INSERT`도 포함되며, 이때 원격 서버는 모든 데이터를 수신한 후 프로파일 이벤트를 보고합니다. `distributed_foreground_insert = 0`인 `Distributed` 테이블의 백그라운드 전송은 어떤 사용자 쿼리에도 속하지 않으므로 집계되지 않습니다. [비동기 삽입(asynchronous inserts)](/ko/reference/settings/session-settings/async-insert#async_insert)의 지연된 플러시는 `SYSTEM FLUSH ASYNC INSERT QUEUE`처럼 플러시를 강제하는 쿼리가 아니라 삽입을 제출한 사용자의 쿼터에 집계되며, 삽입을 검사할 때 사용한 것과 동일한 버킷에 집계됩니다(`ip_address` 또는 `forwarded_ip_address`를 키로 하는 쿼터는 클라이언트 주소의 버킷, `normalized_query_hash`를 키로 하는 쿼터는 제출된 `INSERT`의 버킷). 분산 `INSERT`를 수신한 원격 서버가 이를 비동기 삽입으로 큐에 넣으면, 해당 서버의 지연된 플러시는 그 서버에서 initiator가 접속에 사용하는 사용자의 쿼터에 집계되며 initiator에는 보고되지 않습니다. 중복 집계는 발생하지 않습니다. 분산 `INSERT`의 initiator가 원격 서버로 전송하는 행은 `InsertedRows` 및 `InsertedBytes`에 한 번만 집계되며, 원격 서버가 그 외에 추가로 기록하는 데이터(예: materialized view의 대상 테이블에 기록하는 데이터)는 별도로 추가 집계됩니다.

하나 이상의 시간 간격에서 한도를 초과하면, 어떤 제한을 초과했는지, 어느 인터벌에 해당하는지, 새 인터벌이 언제 시작되는지(언제 다시 쿼리를 보낼 수 있는지)를 알려 주는 메시지와 함께 예외가 발생합니다.

<Note>
  **쿼터 집계에서 제외되는 쿼리**

  쿼터가 소진된 상태에서도 쿼터 구성과 사용량을 확인할 수 있도록, 다음 시스템 테이블 중 하나만 읽는 `SELECT` 쿼리는 쿼터에 집계되지 않으며 쿼리 복잡도 제한도 적용되지 않습니다.

  * `system.quotas`
  * `system.quota_limits`
  * `system.quota_usage`
  * `system.quotas_usage`
  * `system.one`
</Note>

쿼터는 &quot;할당량 키(quota key)&quot; 기능을 사용하여 여러 키의 리소스 사용량을 각각 독립적으로 보고할 수 있습니다. 다음은 그 예시입니다.

```xml
<!-- For the global reports designer. -->
<web_global>
    <!-- keyed – The quota_key "key" is passed in the query parameter,
            and the quota is tracked separately for each key value.
        For example, you can pass a username as the key,
            so the quota will be counted separately for each username.
        Using keys makes sense only if quota_key is transmitted by the program, not by a user.

        You can also write <keyed_by_ip />, so the IP address is used as the quota key.
        (But keep in mind that users can change the IPv6 address fairly easily.)

        Instead of <keyed_by_ip /> you can use <keyed_by_forwarded_ip />, so the address
        from the X-Forwarded-For header is used as the quota key.

        For both <keyed_by_ip /> and <keyed_by_forwarded_ip /> you can additionally specify
        <ipv4_prefix_bits> and <ipv6_prefix_bits> to group clients by subnet instead of by a
        single address: the IP address is masked to the given prefix length before being used
        as the quota key. For example, <ipv4_prefix_bits>24</ipv4_prefix_bits> shares one bucket
        across a /24 IPv4 subnet, and <ipv6_prefix_bits>64</ipv6_prefix_bits> across a /64 IPv6
        subnet. These elements can only be used together with <keyed_by_ip /> or
        <keyed_by_forwarded_ip />.
    -->
    <keyed />
</web_global>
```

정규화된 쿼리 해시를 기준으로 쿼터를 설정할 수도 있으며, 그러면 서로 다른 각 쿼리 패턴에 독립적인 쿼터 버킷이 할당됩니다. XML 구성에서는 이를 `<keyed_by_normalized_query_hash />`로 작성합니다:

```xml
<my_quota>
    <keyed_by_normalized_query_hash />
    <interval>
        <duration>3600</duration>
        <queries>100</queries>
    </interval>
</my_quota>
```

같은 내용은 DDL 구문으로도 표현할 수 있습니다:

```sql
CREATE QUOTA my_quota KEYED BY normalized_query_hash FOR INTERVAL 1 hour MAX queries = 100 TO my_user;
```

이 예시에서는 서로 다른 각 정규화된 쿼리를 시간당 최대 100회까지 실행할 수 있습니다. `SELECT number FROM numbers(1)`와 `SELECT number FROM numbers(2)`는 동일한 버킷을 공유하지만(정규화된 형식이 같기 때문), `SELECT number, number FROM numbers(1)`는 별도의 버킷을 사용합니다.

이 쿼터는 구성의 &#39;users&#39; 섹션에서 사용자에게 할당됩니다. &quot;접근 권한&quot; 섹션을 참조하십시오.

분산 쿼리 처리에서는 누적된 값이 요청을 보낸 서버에 저장됩니다. 따라서 사용자가 다른 서버로 이동하면 해당 서버의 쿼터는 &quot;처음부터 다시&quot; 시작됩니다.

서버를 재시작하면 쿼터가 재설정됩니다.
