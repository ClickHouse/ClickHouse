ClickHouse에서 처리되는 데이터는 일반적으로 ClickHouse 서버가 실행 중인
머신의 로컬 파일 시스템에 저장됩니다. 이를 위해서는 대용량 디스크가 필요하며,
비용이 많이 들 수 있습니다. 데이터를 로컬에 저장하지 않도록 다음과 같은 스토리지 옵션을 지원합니다:

1. [Amazon S3](https://aws.amazon.com/s3/) 객체 스토리지.
2. [Azure Blob Storage](https://azure.microsoft.com/en-us/products/storage/blobs).
3. 지원되지 않음: Hadoop 분산 파일 시스템([HDFS](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html))

<br />

<Note>
  ClickHouse는 외부 테이블 엔진도 지원합니다. 이는 이 페이지에서 설명하는
  외부 스토리지 옵션과는 다르며, 일반적인 파일 포맷(예: Parquet)으로 저장된 데이터를
  읽을 수 있게 해줍니다. 이 페이지에서는 ClickHouse `MergeTree` 계열 또는 `Log` 계열 테이블의
  스토리지 구성을 설명합니다.

  1. `Amazon S3` 디스크에 저장된 데이터를 사용하려면 [S3](/ko/reference/engines/table-engines/integrations/s3) 테이블 엔진을 사용합니다.
  2. Azure Blob Storage에 저장된 데이터를 사용하려면 [AzureBlobStorage](/ko/reference/engines/table-engines/integrations/azureBlobStorage) 테이블 엔진을 사용합니다.
  3. Hadoop 분산 파일 시스템(지원되지 않음)에 저장된 데이터를 사용하려면 [HDFS](/ko/reference/engines/table-engines/integrations/hdfs) 테이블 엔진을 사용합니다.
</Note>

## 외부 스토리지 구성 {#configuring-external-storage}

[`MergeTree`](/ko/reference/engines/table-engines/mergetree-family/mergetree) 및 [`Log`](/ko/reference/engines/table-engines/log-family/log)
계열 테이블 엔진은 각각 `s3`, `azure_blob_storage`, `hdfs`(지원되지 않음) 유형의 디스크를 사용해 데이터를 `S3`, `AzureBlobStorage`, `HDFS`(지원되지 않음)에 저장할 수 있습니다.

<Note>
  `s3` 디스크 유형은 Alibaba Cloud Object Storage Service와 같은 S3-compatible 객체 스토리지 제공업체와도 사용할 수 있습니다. `endpoint`는 해당 제공업체의 S3-compatible 엔드포인트로 구성하고, 제공업체별 compatibility 요구 사항도 고려하십시오.
</Note>

디스크를 구성하려면 다음이 필요합니다.

1. `type` 섹션: 값은 `s3`, `azure_blob_storage`, `hdfs`(지원되지 않음), `local_blob_storage`, `web` 중 하나여야 합니다.
2. 특정 외부 스토리지 타입에 대한 구성.

ClickHouse 24.1 버전부터는 새로운 구성 옵션을 사용할 수 있습니다.
이 경우 다음을 지정해야 합니다.

1. `object_storage`로 설정한 `type`
2. `s3`, `azure_blob_storage`(`24.3`부터는 `azure`도 가능), `hdfs`(지원되지 않음), `local_blob_storage`(`24.3`부터는 `local`도 가능), `web` 중 하나인 `object_storage_type`

<br />

필요에 따라 `metadata_type`을 지정할 수 있습니다. 기본값은 S3, Azure, HDFS 및 로컬 객체 스토리지에서는 `local`이고, 웹 스토리지에서는 `web`입니다. 호환성용 디스크 유형인 `s3_plain`과 `s3_plain_rewritable`은 각각 `plain` 및 `plain_rewritable` 메타데이터를 사용합니다.
`plain` 메타데이터 타입의 사용법은 [plain storage section](/ko/concepts/features/configuration/server-config/storing-data#plain-storage)에 설명되어 있습니다. `web` 메타데이터 타입은 `web` 객체 스토리지 타입에서만 사용할 수 있습니다. `local` 메타데이터 타입은 메타데이터 파일을 로컬에 저장하며(각 메타데이터 파일에는 객체 스토리지의 파일에 대한 매핑과 해당 파일의 추가 메타 정보가 포함됨)입니다.

예시:

```xml
<s3>
    <type>s3</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3>
```

다음 구성과 동일합니다(`24.1` 버전부터):

```xml
<s3>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>local</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3>
```

다음과 같은 구성:

```xml
<s3_plain>
    <type>s3_plain</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

다음과 같습니다:

```xml
<s3_plain>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

전체 스토리지 구성의 예시는 다음과 같습니다:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
        </disks>
        <policies>
            <s3>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3>
        </policies>
    </storage_configuration>
</clickhouse>
```

버전 24.1부터는 다음과 같은 형식이 될 수도 있습니다:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>object_storage</type>
                <object_storage_type>s3</object_storage_type>
                <metadata_type>local</metadata_type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
        </disks>
        <policies>
            <s3>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3>
        </policies>
    </storage_configuration>
</clickhouse>
```

모든 `MergeTree` 테이블에 특정 유형의 스토리지를 기본 옵션으로 설정하려면,
설정 파일에 다음 섹션을 추가하십시오:

```xml
<clickhouse>
    <merge_tree>
        <storage_policy>s3</storage_policy>
    </merge_tree>
</clickhouse>
```

특정 테이블에 사용할 스토리지 정책을 지정하려면,
테이블 생성 시 설정에서 이를 정의할 수 있습니다:

```sql
CREATE TABLE test (a Int32, b String)
ENGINE = MergeTree() ORDER BY a
SETTINGS storage_policy = 's3';
```

`storage_policy` 대신 `disk`를 사용할 수도 있습니다. 이 경우 설정 파일에 `storage_policy` 섹션이
필요하지 않으며, `disk` 섹션만 있으면 충분합니다.

```sql
CREATE TABLE test (a Int32, b String)
ENGINE = MergeTree() ORDER BY a
SETTINGS disk = 's3';
```

## `refresh_parts_interval` 및 `table_disk` {#refresh-parts-interval-and-table-disk}

이 설정은 파트가 외부에서 작성될 수 있고, 스토리지에서 메타데이터 탐지를 다시 갱신해야 하는 비복제 MergeTree 테이블을 위한 것입니다.

`MergeTree` 설정 `refresh_parts_interval`은 읽기 전용 디스크에서 기본 스토리지의 데이터 파트 목록을 주기적으로 갱신할 수 있게 합니다(예: 외부에서 작성된 파트를 감지하기 위해). 여기서 중요한 차이는 **레플리카 간 공유 메타데이터**와 **레플리카 로컬 메타데이터**(예: 레플리카별 로컬 메타데이터를 사용하는 S3)입니다. 메타데이터가 공유되는 경우에만 새 파트가 모든 레플리카에 표시됩니다. 객체 스토리지를 사용한다고 해서 메타데이터까지 공유된다는 의미는 아닙니다.

* **객체 스토리지(예: `disk = 's3'`)는 공유 메타데이터를 의미하지 않습니다.** 메타데이터가 기본값처럼 레플리카별로 로컬에 저장되면, 각 레플리카는 객체 스토리지의 블롭을 가리키는 포인터를 독립적으로 관리합니다. 한 레플리카에서 발생한 변경 사항은 다른 레플리카에 보이지 않습니다. 이 경우 각 레플리카가 읽는 메타데이터가 레플리카 로컬이므로, `refresh_parts_interval`을 사용해도 새 파트가 레플리카 간에 표시되지 않습니다.

* **자동 파트 갱신이 작동하려면 읽기 전용 디스크와 writer의 메타데이터에 대한 액세스가 필요합니다.** [`table_disk`](/ko/reference/settings/merge-tree-settings/table#table_disk)는 디스크가 하나의 테이블 데이터를 직접 가리킨다는 것을 나타낼 뿐, 디스크를 읽기 전용으로 만들지는 않습니다. 읽기 전용 액세스는 디스크 정의에 `read_only=true`를 지정하는 등의 방법으로 별도로 구성하고, 지원되는 메타데이터 타입을 사용하십시오.

* **전역적으로 정의된 디스크**(예: `storage_configuration`에서 `disk = 's3'`)와 기본 로컬 메타데이터를 사용하는 경우, 각 레플리카는 자체 메타데이터 상태를 가집니다. 블롭이 S3에 있더라도 `refresh_parts_interval`의 관점에서는 해당 스토리지가 공유된 것으로 간주되지 않으므로, ClickHouse 외부 또는 다른 레플리카에서 생성된 새 파트는 감지되지 않습니다.

자동 파트 갱신을 사용하려면 리더가 writer의 메타데이터를 볼 수 있어야 하며 읽기 전용 디스크를 사용해야 합니다. S3 버킷을 공유하는 것만으로는 로컬에 저장된 메타데이터가 공유되지 않습니다.

<Note>
  `refresh_parts_interval`은 ReplicatedMergeTree 테이블에는 사용되지 않습니다.
  복제된 테이블은 이미 복제 메커니즘을 통해 파트를 동기화합니다.
  이 설정은 파트가 외부에서 작성되고 메타데이터 갱신이 필요한 비복제 MergeTree 테이블에만 적용됩니다.
</Note>

## 동적 구성 {#dynamic-configuration}

설정 파일의 구성에서 디스크를 미리 정의하지 않고도 스토리지 구성을 지정할 수 있으며,
대신 `CREATE`/`ATTACH` 쿼리 설정에서 구성할 수도 있습니다.

다음 쿼리는 URL에 저장된 읽기 전용 테이블을 연결(ATTACH)합니다.

```sql highlight={20-23}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=web,
    endpoint='https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/'
  );
```

아래 예시에서는 외부 스토리지에 캐시를 추가합니다.

```sql highlight={20-28}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=cache,
    max_size='1Gi',
    path='custom_disk_cache/',
    disk=disk(
      type=web,
      endpoint='https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/'
      )
  );
```

위에서 강조 표시된 설정을 보면 `type=web` 디스크가
`type=cache` 디스크 내부에 중첩되어 있음을 알 수 있습니다.

<Note>
  이 예시에서는 `type=web`을 사용하지만, 로컬 디스크를 포함해 어떤 디스크 유형이든 동적으로 구성할 수
  있습니다. 로컬 디스크를 사용하려면 경로 인수가 서버 설정
  `custom_local_disks_base_directory` 안에 있어야 하며, 이 설정에는 기본값이 없습니다.

  동적 캐시 디스크를 사용하려면 서버에서 `filesystem_caches_path` 또는 `custom_cached_disks_base_directory`를 구성하십시오. 상대 캐시 경로는 해당 디렉터리를 기준으로 해석되며, 절대 경로도 반드시 해당 디렉터리 안에 있어야 합니다.
</Note>

`disk`의 각 인수는 한 번만 지정할 수 있습니다. 단, 디스크가 목록으로 읽어 들이는 인수는 예외이며,
`s3` 디스크의 `header`와 `access_header`, 그리고 `encrypted` 디스크의 `key`와 `key_hex`가 이에 해당합니다.

설정 파일 기반 구성과 SQL로 정의한 구성을 함께 사용하는 것도
가능합니다:

```sql highlight={20-25}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=cache,
    max_size='1Gi',
    path='custom_disk_cache/',
    disk='web'
  );
```

여기서 `web`은 서버 설정 파일에 정의된 디스크입니다:

```xml
<storage_configuration>
    <disks>
        <web>
            <type>web</type>
            <endpoint>https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/</endpoint>
        </web>
    </disks>
</storage_configuration>
```

### S3 스토리지 사용 {#s3-storage}

#### 엔드포인트 및 인증 {#required-parameters-s3}

| 매개변수                | 설명                                                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `endpoint`          | `path` 또는 `virtual hosted` [방식](https://docs.aws.amazon.com/AmazonS3/latest/dev/VirtualHosting.html)의 S3 엔드포인트 URL입니다. 데이터 저장용 버킷과 루트 경로를 포함해야 합니다. |
| `access_key_id`     | S3 액세스 키 ID입니다. 자격 증명 provider를 사용하는 경우에는 선택 사항입니다.                                                                                                 |
| `secret_access_key` | S3 시크릿 액세스 키입니다. 명시적으로 제공된 인증 정보를 사용할 때 `access_key_id`와 함께 지정합니다.                                                                                  |

S3 기본값은 릴리스마다 변경되어 왔습니다. `23.4`에서는 `use_environment_credentials`가 `false`에서 `true`로, `23.5`에서는 `connect_timeout_ms`가 `10000`에서 `1000`으로, `22.10`에서는 `request_timeout_ms`가 `5000`에서 `30000`으로 변경되었습니다. 명시적으로 구성한 값은 이러한 기본값 변경의 영향을 받지 않습니다.

명시적으로 제공된 인증 정보가 자격 증명 provider보다 우선합니다. 임시 자격 증명을 명시적으로 사용하는 경우 `session_token`을 설정하십시오. `use_environment_credentials=true`로 설정하면 ClickHouse는 환경, AWS 자격 증명 파일, 웹 아이덴티티 또는 인스턴스/컨테이너 역할(role)에서 자격 증명을 가져올 수 있습니다. 즉, 이 옵션은 환경 변수만이 아니라 provider 연쇄 전체를 활성화합니다.

웹 아이덴티티(`AWS_ROLE_ARN` 및 `AWS_WEB_IDENTITY_TOKEN_FILE` 환경 변수)를 사용하는 경우, ClickHouse는 `AWS_DEFAULT_REGION` 또는 AWS 프로필에 설정된 리전의 AWS STS에 자격 증명을 요청합니다. 둘 다 리전을 설정하지 않으면 디스크의 리전, 즉 `region` 매개변수 또는 엔드포인트에서 추출한 리전(예: `https://s3.eu-central-1.amazonaws.com/`의 경우 `eu-central-1`)을 사용합니다. 디스크에도 리전이 없거나 `remote_url_allow_hosts`가 해당 리전의 STS 엔드포인트(`sts.eu-central-1.amazonaws.com`)를 허용하지 않으면 `us-east-1`의 STS를 호출합니다. 항상 특정 리전의 STS를 호출하려면 `AWS_DEFAULT_REGION`을 설정하십시오. `AWS_REGION` 환경 변수로는 STS의 리전이 설정되지 않습니다.

### Plain Storage 사용 {#plain-storage}

`22.10`에는 한 번만 쓸 수 있는 저장소를 제공하는 새로운 디스크 유형 `s3_plain`이 도입되었습니다.
이 디스크 유형의 구성 매개변수는 `s3` 디스크 유형과 동일합니다.
`s3` 디스크 유형과 달리 데이터를 있는 그대로 저장합니다. 즉,
무작위로 생성된 블롭 이름 대신 일반 파일 이름을 사용하며
(ClickHouse가 로컬 디스크에 파일을 저장하는 방식과 동일) 로컬에
메타데이터를 저장하지 않습니다. 예를 들어, `s3`의 데이터에서 파생됩니다.

이 디스크 유형은 기존 데이터에 대해 머지를 실행할 수 없고
새 데이터를 삽입할 수도 없으므로 테이블의 정적 버전을 유지할 수 있습니다.
이 디스크 유형의 활용 사례 중 하나는 여기에 백업(backup)을 생성하는 것이며, 이는
`BACKUP TABLE data TO Disk('plain_disk_name', 'backup_name')`를 통해 수행할 수 있습니다. 이후
`RESTORE TABLE data AS data_restored FROM Disk('plain_disk_name', 'backup_name')`를 실행하거나
`ATTACH TABLE data (...) ENGINE = MergeTree() SETTINGS disk = 'plain_disk_name'`를 사용할 수 있습니다.

구성:

```xml
<s3_plain>
    <type>s3_plain</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

`24.1`부터 `plain` 메타데이터 타입을 사용해 모든 객체 스토리지 디스크(`s3`, `azure`, `hdfs` (지원되지 않음), `local`)를
구성할 수 있습니다.

구성:

```xml
<s3_plain>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

### S3 Plain Rewritable Storage 사용 {#s3-plain-rewritable-storage}

새 디스크 유형 `s3_plain_rewritable`는 `24.4`에서 도입되었습니다.
`s3_plain` 디스크 유형과 마찬가지로, 메타데이터 파일을 위한 추가 저장소가
필요하지 않습니다. 대신 메타데이터는 S3에 저장됩니다.
`s3_plain` 디스크 유형과 달리, `s3_plain_rewritable`는 머지를 실행할 수
있으며 `INSERT` 작업을 지원합니다.
테이블 복제는 지원되지 않습니다.
[뮤테이션](/ko/reference/statements/alter/index#mutations)과 `ALTER` 작업은
`enable_hard_links`로 하드 링크가 비활성화되지 않은 경우에 지원됩니다. 아래를 참고하세요.

이 디스크 유형의 사용 사례 중 하나는 비복제 `MergeTree` 테이블입니다. `s3`
디스크 유형도 비복제 `MergeTree` 테이블에 적합하지만, 테이블의 로컬 메타데이터가
필요하지 않다면 `s3_plain_rewritable`
디스크 유형을 선택할 수 있습니다. 예를 들어 시스템 테이블에 유용할 수 있습니다.

구성:

```xml
<s3_plain_rewritable>
    <type>s3_plain_rewritable</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain_rewritable>
```

와 같습니다

```xml
<s3_plain_rewritable>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain_rewritable</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain_rewritable>
```

`24.5`부터는 `plain_rewritable` 메타데이터 타입을 사용해
모든 객체 스토리지 디스크(`s3`, `azure`, `local`)를 구성할 수 있습니다.

#### 메타데이터 스냅샷 {#plain-rewritable-metadata-snapshot}

`plain_rewritable` 디스크의 메타데이터는 객체 스토리지에 디렉터리마다
`prefix.path` 객체로 저장됩니다. 이 객체들로부터 메모리 내 상태를 구성하려면
메타데이터 디렉터리를 목록 조회하고, 모든 `prefix.path`를 읽고,
모든 디렉터리를 목록 조회해야 하므로, 테이블이 하나뿐인 디스크라도
수만 건의 요청이 발생합니다.

이 과정을 빠르게 하기 위해, 데이터를 쓰는 디스크는 같은 위치를 가리키는
읽기 전용 디스크(`readonly`가 `true`로 설정되었거나, `read_only`를 `true`로
설정하여 연결된 디스크)를 위해 전체 상태의 간결한 스냅샷을
`__meta/snapshot.bin`(`ZSTD`로 압축된, 버전이 명시된 바이너리 형식)에 함께 기록합니다.

읽기 전용 디스크는 단 한 번의 요청으로 스냅샷에서 전체 상태를 로드하며,
주기적인 갱신(`MergeTree` 설정 `refresh_parts_interval` 참조) 시에는
스냅샷을 확인하여 재작성된 경우에만 다시 읽습니다. 메타데이터 디렉터리를
목록 조회하거나 `prefix.path`를 읽는 일은 전혀 없습니다. 유일한 목록 조회는
완료되지 않은 연산의 마커를 대상으로 하는 단 한 번의 요청이며, 이를 통해
writer가 현재 대체하고 있는 파일은 백업(backup)에서 읽습니다. 읽기 전용 디스크는 원래
`MergeTree` 테이블의 오래된 파트의 수명에 의존하여 지연된 상태로 동작하며,
스냅샷도 같은 종류의 지연된 상태입니다. 즉, writer의 변경 사항은 writer가
스냅샷을 재작성하는 시점에 리더에게 반영됩니다.
여기에는 writer가 대체했거나 제자리에서 재작성한 파일도 포함됩니다. 스냅샷이
재작성되기 전까지 리더는 이 파일들을 이전 크기와 블롭 기준으로 인식하며, 해당 블롭은
이미 덮어쓰였거나 삭제되었을 수 있습니다. 이는 객체 스토리지를 목록 조회하는
리더가 다음 갱신 전까지 파일을 인식하는 방식과 정확히 같습니다. 스냅샷으로 인해 이 시간 범위가
늘어나는 것은 최대 `metadata_snapshot_write_delay_ms`뿐입니다.
스냅샷이 없거나(예: writer에서 비활성화되었거나 writer가 이전 버전을 실행 중인 경우)
읽을 수 없는 경우에만 읽기 전용 디스크가 객체 스토리지를 목록 조회합니다.

writer는 항상 최신의 정확한 상태를 유지해야 하므로 스냅샷을 절대 읽지 않습니다.
시작 시 평소처럼 객체 스토리지를 목록 조회한 뒤 스냅샷을 기록합니다.
`metadata_snapshot_enabled`가 `false`로 설정된 writer는 시작 시 이전에 남아 있던
스냅샷을 삭제하여, 읽기 전용 디스크가 오래된 상태를 계속 사용하지 않도록 합니다.
스냅샷을 읽을 수 없거나 완료되지 않은 연산의 마커가 잘못된 형식이면, 읽기 전용
디스크는 객체 스토리지를 목록 조회하며, 해당 스냅샷은 재작성될 때까지 사용하지 않습니다.

스냅샷은 객체를 원자적으로 대체하는 객체 스토리지에서만 사용되므로, 읽기 전용
디스크가 부분적으로 기록된 스냅샷을 읽는 일은 없습니다. 해당 스토리지는
`S3`, Azure blob storage, 로컬입니다. `HDFS` 및 Azure Data Lake Storage
Gen2 엔드포인트(예: OneLake)에서는 스냅샷을 기록하지도 읽지도 않으며,
디스크는 스냅샷이 없을 때와 마찬가지로 객체 스토리지를 목록 조회합니다. 이러한 스토리지에 이전부터
남아 있던 스냅샷은 writer가 시작 시 삭제합니다.

| 설정                                 | 설명                                                                                                                                                                                    | 기본값    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| `metadata_snapshot_enabled`        | 수정 후 스냅샷을 기록하거나(객체 스토리지가 쓰기 가능한 경우), 객체 스토리지를 목록 조회하는 대신 스냅샷에서 상태를 로드합니다(객체 스토리지가 읽기 전용인 경우).                                                                                         | `true` |
| `metadata_snapshot_write_delay_ms` | 수정 사항이 있는 동안 스냅샷은 백그라운드에서 재작성되며, 재작성 간격은 지정된 밀리초보다 짧아지지 않습니다. `0`이면 매 수정 직후 커밋하는 스레드에서 스냅샷을 재작성하므로, 모든 커밋의 비용이 디스크 전체의 메타데이터를 직렬화하는 비용만큼 커집니다. 스냅샷은 서버 종료 시에도 기록되며, 디스크가 비면 즉시 삭제됩니다. | `1000` |

두 설정 모두 디스크가 생성될 때만 읽힙니다. 변경 사항은 서버를 재시작해야
적용되며, `SYSTEM RELOAD CONFIG`로는 적용되지 않습니다. 디스크의 역할도
마찬가지입니다. 스냅샷을 기록할지 읽을지는 디스크 생성 시 `readonly`에 따라
결정되므로, `readonly`를 변경할 때도 서버를 재시작해야 합니다.

이전 버전은 `__meta/snapshot.bin`을 무시하므로 이 파일을 읽지도, 재작성하거나
삭제하지도 않습니다. 따라서 읽기 전용 디스크는 계속 새 버전으로 실행하면서
writer만 스냅샷을 지원하지 않는 버전으로 다운그레이드하는 경우, writer가 남긴 스냅샷을
폐기해야 합니다. 그렇지 않으면 읽기 전용 디스크가 이 스냅샷을 계속 사용하여 다운그레이드
이후의 변경 사항을 보지 못합니다. 새 버전의 writer를 중지한 후 이전 버전을
시작하기 전에 `__meta/snapshot.bin`을 삭제하거나, 읽기 전용 디스크에서
`metadata_snapshot_enabled`를 `false`로 설정하고 재시작하여 객체 스토리지를
목록 조회하도록 하십시오.

```xml
<s3_plain_rewritable>
    <type>s3_plain_rewritable</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
    <metadata_snapshot_write_delay_ms>10000</metadata_snapshot_write_delay_ms>
</s3_plain_rewritable>
```

[system.events](/ko/reference/system-tables/events)의 `DiskPlainRewritableSnapshotRead`, `DiskPlainRewritableSnapshotWritten`
및 `DiskPlainRewritableSnapshotWriteFailed` 이벤트를 통해
스냅샷 사용 현황을 확인할 수 있습니다.

#### plain rewritable 디스크의 하드 링크(Hard Link) {#plain-rewritable-hard-links}

`MergeTree` 테이블의 `ALTER` 작업과 뮤테이션은 변경되지 않은 파일을 복사하지 않고
하드 링크를 통해 원본 파트와 뮤테이션이 적용된 새 파트 간에 공유합니다.
`enable_hard_links` 설정(기본값 `1`)을 활성화하면 `plain_rewritable` 메타데이터를
사용하는 디스크에서도 실제 하드 링크를 생성할 수 있으며, 이에 따라 이러한 작업을
사용할 수 있습니다. `26.10` 이전 버전의 서버에서도 디스크를 읽을 수 있도록 유지하려면 `0`으로 설정하십시오.
이 경우 하드 링크는 복사로 에뮬레이션되며, 데이터를 수정하는 `ALTER` 작업과 뮤테이션은 지원되지 않습니다.

```xml
<s3_plain_rewritable>
    <type>s3_plain_rewritable</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
    <enable_hard_links>0</enable_hard_links>
</s3_plain_rewritable>
```

하드 링크(hard link)를 사용하면 디렉터리의 메타데이터에 해당 디렉터리의 파일과 각 파일을 저장하는
객체의 키가 명시적으로 나열되므로, 파일이 다른 디렉터리의 접두사 아래에 저장된 객체를
참조할 수 있습니다. 다음 사항을 고려하십시오.

* `enable_hard_links` 설정을 지원하지 않는 서버는 이 형식의 디렉터리를 읽을 수 없으며,
  디렉터리의 메타데이터 전체를 논리 경로로 읽습니다. 따라서 이러한 디렉터리가 있는 디스크는
  해당 버전으로 다운그레이드하면 읽을 수 없으며, 해당 버전과 공유할 수도 없습니다. 하드 링크가
  한 번도 생성되지 않은 디렉터리는 이전 구조를 유지하므로, 하드 링크를 생성하는 첫 작업(뮤테이션,
  `ALTER`, `FREEZE` 또는 Backup)이 수행되기 전까지는 이전 버전의 서버에서도 디스크를 읽을 수 있습니다.
  설정을 다시 비활성화하더라도 기존 디렉터리가 원래 형식으로 되돌아가지는 않습니다.
* 이 설정은 디스크가 생성될 때에만 읽힙니다. 변경 사항은 서버를 재시작해야 적용되며,
  `SYSTEM RELOAD CONFIG`로는 적용되지 않습니다.
* 마지막 링크가 제거된 객체는 두 단계로 삭제됩니다. 먼저 디렉터리의 메타데이터가
  재작성된 후 객체가 삭제됩니다. 그 사이에 서버가 강제 종료되면 객체는
  어디에서도 참조되지 않은 채 버킷에 남으므로 수동으로 삭제해야 합니다.

### Azure Blob Storage 사용하기 {#azure-blob-storage}

`MergeTree` 계열 테이블 엔진은 `azure_blob_storage` 유형의 디스크를 사용해
[Azure Blob Storage](https://azure.microsoft.com/en-us/services/storage/blobs/)에 데이터를 저장할 수 있습니다.

다음 프래그먼트를 서버 구성의 `clickhouse` 요소 안에 추가하십시오. 서버 환경에 `AZURE_STORAGE_ACCOUNT_KEY`를 설정하고, 계정 이름과 컨테이너 이름을 실제 값으로 대체하십시오.

```xml
<storage_configuration>
    <disks>
        <blob_storage_disk>
            <type>azure_blob_storage</type>
            <storage_account_url>https://account.blob.core.windows.net</storage_account_url>
            <container_name>container</container_name>
            <account_name>account</account_name>
            <account_key from_env="AZURE_STORAGE_ACCOUNT_KEY"/>
            <metadata_path>/var/lib/clickhouse/disks/blob_storage_disk/</metadata_path>
            <skip_access_check>false</skip_access_check>
        </blob_storage_disk>
    </disks>
</storage_configuration>
```

#### 연결 매개변수 {#azure-blob-storage-connection-parameters}

| 매개변수                       | 설명                                                                                                                                                                                  | 기본값  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| `storage_account_url`      | Azure Blob Storage 스토리지 계정 URL입니다. `connection_string` 또는 `endpoint`를 지정하지 않은 경우 필수입니다. 예시: `https://account.blob.core.windows.net` 또는 `http://azurite1:10000/devstoreaccount1`입니다. | -    |
| `container_name`           | `storage_account_url` 또는 `connection_string`과 함께 사용할 때 필수입니다. 그 외에는 `endpoint`에 포함하여 지정합니다.                                                                                         | None |
| `container_already_exists` | 컨테이너 생성 동작을 제어합니다: <br />- `false`: 새 컨테이너를 생성합니다 <br />- `true`: 기존 컨테이너에 직접 연결합니다 <br />- 설정되지 않음: 컨테이너가 있는지 확인한 후, 필요하면 생성합니다                                                    | -    |

`24.3` 이전 버전에서는 `container_name`을 생략하면 `default-container`가 사용되었습니다.

인증 방식은 하나만 선택됩니다. `account_name`과 `account_key`가 모두 있으면 Shared Key를, 그렇지 않으면 `connection_string`을, 그렇지 않고 `use_workload_identity=true`(기본값 `false`)이면 Workload Identity를, 그 외에는 관리 ID(Managed Identity)를 사용합니다. 인증에 실패해도 다른 방식으로 폴백되지 않습니다. `24.7` 이전 버전에서는 연결 문자열(Connection String)이 Shared Key보다 우선 적용되었습니다.

인증 매개변수:

| 매개변수                | 설명                                                |
| ------------------- | ------------------------------------------------- |
| `connection_string` | 연결 문자열(Connection String)을 사용한 인증에 사용합니다.                 |
| `account_name`      | Shared Key를 사용한 인증에 사용합니다(`account_key`와 함께 사용).  |
| `account_key`       | Shared Key를 사용한 인증에 사용합니다(`account_name`과 함께 사용). |

| 매개변수                              | 설명                                                                                                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `min_bytes_for_seek`              | 지정할 수는 있지만 현재 읽기 버퍼(read buffer)에서는 사용되지 않습니다. 대신 [`remote_read_min_bytes_for_seek`](/ko/reference/settings/session-settings/other#remote_read_min_bytes_for_seek)를 사용하세요. |
| `max_single_read_retries`         | Blob Storage에서 데이터 청크를 읽을 때의 최대 재시도 횟수입니다.                                                                                                                              |

| `thread_pool_size`                | 디스크의 복사용 스레드 풀에서 사용하는 최대 스레드 수입니다.                                                                                                                                      |
| `max_inflight_parts_for_one_file` | 단일 객체에 대해 동시에 업로드할 수 있는 파트의 최대 수입니다.                                                                                                                                    |

읽기 시도 제한에는 최초 시도가 포함되며, Azure SDK의 재시도와는 별도로 적용됩니다.

#### 기타 매개변수 {#azure-blob-storage-other-parameters}

</Info>

## HDFS 스토리지 사용(지원되지 않음) {#using-hdfs-storage-unsupported}

이 예시 구성은 다음과 같습니다:

* 디스크 유형은 `hdfs`입니다(지원되지 않음)
* 데이터는 `hdfs://hdfs1:9000/clickhouse/`에 저장됩니다

참고로 HDFS는 지원되지 않으므로 사용 시 문제가 발생할 수 있습니다. 문제가 발생하면 수정 사항을 반영한 Pull Request를 보내주십시오.

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <hdfs>
                <type>hdfs</type>
                <endpoint>hdfs://hdfs1:9000/clickhouse/</endpoint>
                <skip_access_check>true</skip_access_check>
            </hdfs>
            <hdd>
                <type>local</type>
                <path>/</path>
            </hdd>
        </disks>
        <policies>
            <hdfs>
                <volumes>
                    <main>
                        <disk>hdfs</disk>
                    </main>
                    <external>
                        <disk>hdd</disk>
                    </external>
                </volumes>
            </hdfs>
        </policies>
    </storage_configuration>
</clickhouse>
```

HDFS는 일부 예외적인 상황에서는 작동하지 않을 수 있다는 점을 유의하십시오.

### 데이터 암호화 사용 {#encrypted-virtual-file-system}

[S3](/ko/reference/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-s3), [HDFS](#using-hdfs-storage-unsupported)(지원되지 않음) 같은 외부 디스크나 로컬 디스크에 저장된 데이터를 암호화할 수 있습니다. 암호화 모드를 사용하려면 설정 파일에서 유형이 `encrypted`인 디스크를 정의하고, 데이터가 저장될 디스크를 선택해야 합니다. `encrypted` 디스크는 쓰여지는 모든 파일을 실시간으로 암호화하며, `encrypted` 디스크에서 파일을 읽을 때는 자동으로 복호화합니다. 따라서 `encrypted` 디스크도 일반 디스크처럼 사용할 수 있습니다.

다음 구성은 `storage_configuration` 안에 넣어야 합니다. 예시 키는 필요한 길이의 자체 키로 교체하십시오.

```xml
<disks>
  <disk1>
    <type>local</type>
    <path>/path1/</path>
  </disk1>
  <disk2>
    <type>encrypted</type>
    <disk>disk1</disk>
    <path>path2/</path>
    <key>_16_ascii_chars_</key>
  </disk2>
</disks>
```

예를 들어, ClickHouse가 일부 테이블의 데이터를 `disk1`의 파일 `store/all_1_1_0/data.bin`에 기록하면, 실제로 이 파일은 물리 디스크의 `/path1/store/all_1_1_0/data.bin` 경로에 기록됩니다.

동일한 파일을 `disk2`에 기록하면, 실제로는 물리 디스크의 `/path1/path2/store/all_1_1_0/data.bin` 경로에 암호화된 상태로 기록됩니다.

#### 필수 매개변수 {#required-parameters-encrypted-disk}

| 매개변수   | 유형     | 설명                                                                                    |
| ------ | ------ | ------------------------------------------------------------------------------------- |
| `type` | String | 암호화된 디스크를 생성하려면 `encrypted`로 설정해야 합니다.                                                |
| `disk` | String | 기저 스토리지로 사용할, 미리 구성된 디스크의 이름입니다.                                                      |
| `key`  | String | 암호화 및 복호화에 사용할 키입니다. `key_hex`를 사용해 16진수로 지정할 수 있습니다. `id` 속성을 사용하면 여러 키를 지정할 수 있습니다. |

#### 선택적 매개변수 {#optional-parameters-encrypted-disk}

| 매개변수             | 유형     | 기본값                          | 설명                                                                                                               |
| ---------------- | ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `path`           | String | 루트 디렉터리                      | 기반 디스크의 상대 디렉터리이며, 비어 있지 않은 경우 `/`로 끝나야 합니다.                                                                     |
| `current_key_id` | UInt64 | 키가 하나뿐이고 그 ID가 `0`인 경우에만 `0` | 암호화에 사용할 키를 선택합니다. 키가 여러 개인 경우 현재 키를 명시적으로 지정해야 합니다. 구성된 모든 키는 계속 복호화에 사용할 수 있습니다.                               |
| `algorithm`      | Enum   | `AES_128_CTR`                | 암호화 알고리즘입니다. 옵션: <br />- `AES_128_CTR` (16바이트 키) <br />- `AES_192_CTR` (24바이트 키) <br />- `AES_256_CTR` (32바이트 키) |

디스크 구성 예시:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <disk_s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
            </disk_s3>
            <disk_s3_encrypted>
                <type>encrypted</type>
                <disk>disk_s3</disk>
                <algorithm>AES_128_CTR</algorithm>
                <key_hex id="0">00112233445566778899aabbccddeeff</key_hex>
                <key_hex id="1">ffeeddccbbaa99887766554433221100</key_hex>

            </disk_s3_encrypted>
        </disks>
    </storage_configuration>
</clickhouse>
```

### 로컬 캐시 사용 {#using-local-cache}

`cache` 디스크는 S3, Azure, `web` 등의 객체 스토리지 디스크를 래핑하며, 캐시된 데이터를 로컬 파일 시스템에 저장합니다. 일반 `local` 디스크나 `encrypted` 래퍼는 래핑할 수 없습니다. 기반 디스크는 캐시 디스크보다 먼저 정의하십시오.

현재 버전에 권장되는 구성은 다음과 같습니다:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
            <cache>
                <type>cache</type>
                <disk>s3</disk>
                <path>s3_cache/</path>
                <max_size>10Gi</max_size>
            </cache>
        </disks>
        <policies>
            <s3_cache>
                <volumes>
                    <main>
                        <disk>cache</disk>
                    </main>
                </volumes>
            </s3_cache>
        </policies>
    </storage_configuration>
</clickhouse>
```

버전 `22.3`–`22.7`에만 해당하는 이전 구성입니다. 현재 구성에서는 이 `data_cache_*` 키를 사용하지 말고, 위와 같이 별도의 `cache` 디스크를 사용하십시오:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
                <data_cache_enabled>1</data_cache_enabled>
                <data_cache_max_size>10737418240</data_cache_max_size>
            </s3>
        </disks>
        <policies>
            <s3_cache>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3_cache>
        </policies>
    </storage_configuration>
</clickhouse>
```

파일 캐시 **디스크 구성 설정**(공통 설정):

이 설정은 디스크 구성 섹션에 정의해야 합니다. 이 표에는 자주 사용하는 캐시 디스크 설정 항목만 나열되어 있으며, 구성에서 허용되는 모든 키가 포함되어 있지는 않습니다. 런타임 값과 전체 설정 목록은 [`system.filesystem_cache_settings`](/ko/reference/system-tables/filesystem_cache_settings)에서 확인할 수 있습니다.

| 매개변수                                        | 유형      | 기본값        | 설명                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------- | ------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`                                      | String  | *          | **필수**. 캐시 디렉터리입니다. 상대 경로는 `filesystem_caches_path`를 기준으로 해석되며, 이 설정이 없으면 `<path>/caches/`를 기준으로 해석됩니다. `filesystem_caches_path`가 설정되어 있으면 절대 경로도 해당 디렉터리 내부를 가리켜야 합니다.                                                                                                                                                                                                                                                                                         |
| `max_size`                                  | 크기      | -          | 바이트 또는 읽기 쉬운 형식(예: `10Gi`)으로 지정하는 최대 캐시 크기입니다. `max_size_ratio_to_total_space`가 설정되지 않은 경우 **필수**이며, 두 설정은 함께 지정할 수 없습니다. 한도에 도달하면 파일은 `cache_policy`에 지정된 정책(기본값 SLRU)에 따라 제거됩니다. `ki`, `Mi`, `Gi` 포맷을 지원합니다(v22.10부터).                                                                                                                                                                                                                                        |
| `max_size_ratio_to_total_space`             | Double  | *          | `max_size` 대신 사용할 수 있는 설정으로, 전체 디스크 공간 중 캐시 크기로 사용할 비율이며 `(0, 1]` 범위로 지정합니다. `max_size`가 설정되지 않은 경우 **필수**입니다. `max_size`와 함께 지정할 수 없습니다.                                                                                                                                                                                                                                                                                                                       |
| `cache_policy`                              | Enum    | `SLRU`     | 캐시 eviction 정책입니다. 가능한 값: `LRU`, `SLRU`(기본값), `SLRU_OVERCOMMIT`, `LRU_OVERCOMMIT`. 오버커밋 정책은 분산 캐시를 지원하는 빌드에서만 사용할 수 있으며 `use_split_cache`와 함께 사용할 수 없습니다(두 경우 모두 시작 시 거부됩니다).                                                                                                                                                                                                                                                                                   |
| `slru_size_ratio`                           | Double  | `0.6`      | `SLRU` / `SLRU_OVERCOMMIT`에서 보호(protected) 캐시와 수습(probationary) 캐시의 비율입니다.                                                                                                                                                                                                                                                                                                                                                                                      |
| `reserve_granularity`                       | 크기      | `4Mi`      | 파일 세그먼트 다운로드를 위해 공간을 예약할 때 최소 이 바이트만큼 미리 예약합니다(최대 파일 세그먼트 크기까지). `0`이면 요청된 크기만큼만 예약합니다.                                                                                                                                                                                                                                                                                                                                                                         |
| `cache_on_write_operations`                 | 불리언     | `false`    | `INSERT` 쿼리와 백그라운드 머지에 대해 write-through 캐시를 활성화합니다. 또한 쓰기 작업에 사용되는 설정에 `enable_filesystem_cache_on_write_operations=true`를 지정해야 합니다.                                                                                                                                                                                                                                                                                                                            |
| `cache_hits_threshold`                      | Integer | `0`        | 더 이상 사용되지 않으며 효과가 없습니다.                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `enable_bypass_cache_with_threshold`        | 불리언     | `false`    | 큰 읽기 범위에서는 캐시를 건너뜁니다.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `bypass_cache_threshold`                    | 크기      | `256Mi`    | 이 값을 초과하는 읽기 범위 크기에서는 캐시를 우회합니다(`enable_bypass_cache_with_threshold` 필요).                                                                                                                                                                                                                                                                                                                                                                                       |
| `max_file_segment_size`                     | 크기      | `32Mi`     | 바이트 또는 읽기 쉬운 형식으로 지정하는 단일 캐시 파일의 최대 크기입니다. `SLRU` / `SLRU_OVERCOMMIT`에서는 각 SLRU 큐의 크기인 `max_size * min(slru_size_ratio, 1 - slru_size_ratio)`(`use_split_cache` 사용 시에는 각 파트의 크기)를 초과할 수 없으며, 더 큰 값은 거부됩니다.                                                                                                                                                                                                                                                      |
| `boundary_alignment`                        | 크기      | `4Mi`      | 캐시 내 파일 세그먼트 경계의 정렬 단위입니다. `max_file_segment_size`를 초과할 수 없습니다(더 큰 값은 시작 시 거부됩니다).                                                                                                                                                                                                                                                                                                                                                                              |
| `max_elements`                              | Integer | `10000000` | 캐시 파일의 최대 개수입니다.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `load_metadata_threads`                     | Integer | `16`       | 시작 시 캐시 메타데이터를 로드하는 데 사용할 스레드 수입니다.                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `background_download_threads`               | UInt64  | `5`        | 파일 세그먼트를 백그라운드에서 다운로드하는 데 사용할 스레드 수입니다. `0`이면 백그라운드 다운로드가 비활성화됩니다.                                                                                                                                                                                                                                                                                                                                                                                              |
| `background_download_queue_size_limit`      | UInt64  | `5000`     | 백그라운드 다운로드 큐에서 대기할 수 있는 세그먼트의 최대 개수입니다. `0`은 제한이 없음을 의미하며, 큐가 비활성화되는 것은 아닙니다. 백그라운드 다운로드 자체는 `background_download_threads`가 `0`일 때만 비활성화됩니다.                                                                                                                                                                                                                                                                                                                    |
| `background_download_max_file_segment_size` | 크기      | `4Mi`      | 세그먼트를 백그라운드에서 어디까지 프리페치할지 정하는 임계값이며, 정렬 단위에 맞춰 올림됩니다. 다운로드 크기는 `boundary_alignment` 단위로 올림되므로 엄격한 상한은 아닙니다(예: `boundary_alignment`가 `4Mi`이면 `1Mi`로 설정해도 `4Mi`를 다운로드합니다).                                                                                                                                                                                                                                                                                        |
| `load_metadata_asynchronously`              | 불리언     | `false`    | 서버 시작 시 캐시 메타데이터를 비동기로 로드합니다.                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `use_real_disk_size`                        | Boolean | `false`    | 캐시 예약량을 예약된 바이트 수가 아닌 파일 시스템 블록 단위로 정렬하여 계산합니다. 이 값은 디스크상의 예약 점유량에 근사하지만 실제 할당된 크기와 정확히 일치하지는 않으며, `system.filesystem_cache_settings`에 표시되는 이 캐시의 `current_size`에 영향을 줍니다. 프로세스 전체 `FilesystemCacheSize` 메트릭과 eviction 크기 관련 프로파일 이벤트(profile events)는 모든 캐시에 대해 합산되므로, 모든 캐시가 동일한 모드를 사용할 때만 예약 점유량을 균등하게 반영합니다. `system.filesystem_cache`의 세그먼트별 `size`는 여전히 논리적 범위 크기를 나타냅니다. 부분적으로 기록된 세그먼트의 바이트 수를 확인하려면 `downloaded_size`를 사용하십시오. 이 설정을 변경하려면 재시작해야 합니다. |
| `use_split_cache`                           | Boolean | `false`    | 파일을 시스템/데이터로 분리해 사용합니다. `SLRU_OVERCOMMIT` 또는 `LRU_OVERCOMMIT`과 함께 사용할 수 없습니다.                                                                                                                                                                                                                                                                                                                                                                                   |
| `split_cache_ratio`                         | Double  | `0.1`      | split&#95;cache에서 시스템 세그먼트가 전체 캐시 크기에서 차지하는 비율입니다.                                                                                                                                                                                                                                                                                                                                                                                                              |

> **참고**: 크기 값은 `ki`, `Mi`, `Gi` 등의 단위를 지원합니다(예: `10Gi`).

## 파일 캐시 쿼리/프로필 설정 {#file-cache-query-profile-settings}

| 설정                                                            | 유형  | 기본값                     | 설명                                                                                      |
| ------------------------------------------------------------- | --- | ----------------------- | --------------------------------------------------------------------------------------- |
| `enable_filesystem_cache`                                     | 불리언 | `true`                  | `cache` 디스크 유형을 사용하는 경우에도 쿼리별로 캐시 사용을 활성화하거나 비활성화합니다.                                   |
| `read_from_filesystem_cache_if_exists_otherwise_bypass_cache` | 불리언 | `false`                 | 활성화하면 데이터가 있을 때만 캐시를 사용하며, 새 데이터는 캐시되지 않습니다.                                            |
| `enable_filesystem_cache_on_write_operations`                 | 불리언 | `false` (Cloud: `true`) | write-through 캐시를 활성화합니다. 캐시 구성에서 `cache_on_write_operations`를 설정해야 합니다.                |
| `enable_filesystem_cache_log`                                 | 불리언 | `false`                 | `system.filesystem_cache_log`에 상세한 캐시 사용 로깅을 활성화합니다.                                    |

#### 캐시 명령어 {#cache-commands-file-cache}

##### 파일 시스템 캐시 지우기 {#system-clear-filesystem-cache-on-cluster}

해제 가능한 캐시 엔트리를 축출하려면 [`SYSTEM CLEAR FILESYSTEM CACHE`](/ko/reference/statements/system#drop-filesystem-cache)를 사용하십시오. 특정 캐시를 지우려면 `SYSTEM CLEAR FILESYSTEM CACHE 'cache'`를 사용하십시오. 이름을 생략하면 모든 캐시가 지워지며, 두 형식 모두 뒤에 `ON CLUSTER cluster_name`을 붙일 수 있습니다.

##### `SHOW FILESYSTEM CACHES` {#show-filesystem-caches}

서버에 구성된 파일 시스템 캐시 목록을 표시합니다.
(`22.8` 이하 버전에서는 이 명령의 이름이 `SHOW CACHES`입니다)

```sql title="Query"
SHOW FILESYSTEM CACHES
```

```text title="Response"
┌─Caches────┐
│ cache     │
└───────────┘
```

##### `DESCRIBE FILESYSTEM CACHE '<cache_name>'` {#describe-filesystem-cache}

| ------------------------- | ---------------------- | ----------------------------------------------------------------------------------------- |
| `FilesystemCacheSize`     | `FilesystemCacheBytes` | `CachedReadBufferReadFromSourceBytes`, `CachedReadBufferReadFromCacheBytes`               |
| `FilesystemCacheElements` | `FilesystemCacheFiles` | `CachedReadBufferReadFromSourceMicroseconds`, `CachedReadBufferReadFromCacheMicroseconds` |
|                           |                        | `CachedReadBufferCacheWriteBytes`, `CachedReadBufferCacheWriteMicroseconds`               |
|                           |                        | `CachedWriteBufferCacheWriteBytes`, `CachedWriteBufferCacheWriteMicroseconds`             |

### 정적 Web 스토리지 사용(읽기 전용) {#web-storage}

이 디스크는 읽기 전용 디스크입니다. 데이터는 읽기만 가능하며 수정되지는 않습니다. 새 테이블은 `ATTACH TABLE` 쿼리로 이 디스크에 로드됩니다(아래 예시 참조). 로컬 디스크는 실제로 사용되지 않으며, 각 `SELECT` 쿼리는 필요한 데이터를 가져오기 위해 `http` 요청을 보냅니다. 테이블 데이터를 수정하려는 모든 작업은 예외를 발생시키므로, 다음과 같은 쿼리 유형은 허용되지 않습니다: [`CREATE TABLE`](/ko/reference/statements/create/table),
[`ALTER TABLE`](/ko/reference/statements/alter/index), [`RENAME TABLE`](/ko/reference/statements/rename#rename-table),
및 [`TRUNCATE TABLE`](/ko/reference/statements/truncate).
Web 스토리지는 읽기 전용 용도로 사용할 수 있습니다. 예를 들어 샘플 데이터를 호스팅하거나 데이터를 마이그레이션할 때 사용할 수 있습니다. `clickhouse-static-files-uploader`라는 도구는 지정한 테이블의 데이터 디렉터리를 준비합니다(`SELECT data_paths FROM system.tables WHERE name = 'table_name'`).
필요한 각 테이블마다 파일 디렉터리가 생성됩니다. 이 파일들은
예를 들어 정적 파일을 제공하는 웹 서버에 업로드할 수 있습니다. 이 준비가 끝나면,
`DiskWeb`를 통해 이 테이블을 어느 ClickHouse 서버에서나 로드할 수 있습니다.

이 예시 구성에서는:

* 디스크 유형은 `web`입니다
* 데이터는 `http://nginx:80/test1/`에서 호스팅됩니다
* 로컬 스토리지의 캐시를 사용합니다

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <web>
                <type>web</type>
                <endpoint>http://nginx:80/test1/</endpoint>
            </web>
            <cached_web>
                <type>cache</type>
                <disk>web</disk>
                <path>cached_web_cache/</path>
                <max_size>100000000</max_size>
            </cached_web>
        </disks>
        <policies>
            <web>
                <volumes>
                    <main>
                        <disk>web</disk>
                    </main>
                </volumes>
            </web>
            <cached_web>
                <volumes>
                    <main>
                        <disk>cached_web</disk>
                    </main>
                </volumes>
            </cached_web>
        </policies>
    </storage_configuration>
</clickhouse>
```

<Tip>
  웹 데이터셋을 정기적으로 사용할 예정이 아니라면, 스토리지는 쿼리 내에서 일시적으로 구성할 수도 있습니다. [동적 구성](#dynamic-configuration)을 참조하고
  설정 파일 편집은 건너뛰십시오.

  GitHub에는 [데모 데이터세트](https://github.com/ClickHouse/web-tables-demo)가 호스팅되어 있습니다. 직접 테이블을 웹
  스토리지용으로 준비하려면 [clickhouse-static-files-uploader](/ko/concepts/features/tools-and-utilities/static-files-disk-uploader) 도구를 참조하십시오.
</Tip>

이 `ATTACH TABLE` 쿼리에서는 제공된 `UUID`가 데이터 디렉터리 이름과 일치하고, 엔드포인트는 GitHub 원본 콘텐츠의 URL입니다.


#### 필수 매개변수 {#static-web-storage-required-parameters}

| 매개변수       | 설명                                        |
| ---------- | ----------------------------------------- |

#### 선택적 매개변수 {#optional-parameters-web}

`web` 객체 스토리지 백엔드는 `endpoint` 매개변수만 읽습니다. 웹 전용 선택적 매개변수는 없으며, 일반 디스크 옵션도 적용됩니다.

연결 또는 읽기 시간 제한과 관련해서는 [`http_connection_timeout`](/ko/reference/settings/session-settings/http#http_connection_timeout) 및 [`http_receive_timeout`](/ko/reference/settings/session-settings/http#http_receive_timeout)을 확인하십시오. 이 설정들은 쿼리/프로필 설정이며, `web` 디스크 구성 내부의 키가 아닙니다. 쿼리 외부의 요청에는 전역 컨텍스트 설정이 사용됩니다. 웹 데이터 리더는 연결 시간 제한과 수신 시간 제한 모두에 최소 20초를 적용하므로, 더 작은 값을 지정해도 데이터 읽기 시간 제한이 그보다 짧아지지 않습니다.

업로드할 파일을 가져오려면 다음을 실행하십시오:
`clickhouse static-files-disk-uploader --metadata-path <path> --output-dir <dir>` (`--metadata-path`는 쿼리 `SELECT data_paths FROM system.tables WHERE name = 'table_name'`로 확인할 수 있습니다).

`endpoint`로 파일을 로드할 때는 반드시 `<endpoint>/store/` 경로에 로드해야 하지만, 구성에는 `endpoint`만 포함되어야 합니다.

서버 시작 시 테이블을 로드하는 과정에서 디스크의 URL에 연결할 수 없으면 모든 오류가 포착됩니다. 이 경우 오류가 발생했다면 `DETACH TABLE table_name` -&gt; `ATTACH TABLE table_name`을 통해 테이블을 다시 로드해 다시 표시되도록 할 수 있습니다. 서버 시작 시 메타데이터가 성공적으로 로드되었다면 테이블을 즉시 사용할 수 있습니다.

초기 시도를 포함한 HTTP 읽기 시도 횟수를 제한하려면 [`http_max_tries`](/ko/reference/settings/session-settings/http-max#http_max_tries)를 사용하십시오. 재시도 간 초기 및 최대 지연 시간을 구성하려면 [`http_retry_initial_backoff_ms`](/ko/reference/settings/session-settings/http-retry#http_retry_initial_backoff_ms) 및 [`http_retry_max_backoff_ms`](/ko/reference/settings/session-settings/http-retry#http_retry_max_backoff_ms)를 사용하십시오.

### zero-copy 복제(프로덕션 환경에서는 아직 사용할 수 없음) {#zero-copy}

`S3` 및 `HDFS`(미지원) 디스크에서 zero-copy 복제를 사용할 수는 있지만, 권장되지는 않습니다. zero-copy 복제는 데이터가 여러 머신의 원격 스토리지에 저장되어 있고 이를 동기화해야 할 때, 데이터 자체는 복제하지 않고 메타데이터(데이터 파트의 경로)만 복제하는 방식입니다.

<Info>
  **zero-copy 복제는 프로덕션 환경에서 아직 사용할 수 없습니다**

  ClickHouse 버전 22.8 이상에서는 zero-copy 복제가 기본적으로 비활성화되어 있습니다. 이 기능은 프로덕션 환경에서 사용하는 것을 권장하지 않습니다.
</Info>
