ClickHouse는 지원되는 거의 모든 [입력 형식](/ko/reference/formats/index)에서 입력 데이터의 구조(structure)를 자동으로 파악할 수 있습니다.
이 문서에서는 스키마 추론이 사용되는 경우, 입력 형식별 스키마 추론 동작 방식, 그리고 스키마 추론을 제어하는 설정을
설명합니다.

## 사용법 {#usage}

스키마 추론은 ClickHouse가 특정 데이터 포맷의 데이터를 읽어야 하지만 구조(structure)를 알 수 없을 때 사용됩니다.

## 테이블 함수 [file](/ko/reference/functions/table-functions/file), [s3](/ko/reference/functions/table-functions/s3), [url](/ko/reference/functions/table-functions/url), [hdfs](/ko/reference/functions/table-functions/hdfs), [azureBlobStorage](/ko/reference/functions/table-functions/azureBlobStorage). {#table-functions-file-s3-url-hdfs-azureblobstorage}

이러한 테이블 함수에는 입력 데이터의 structure를 지정하는 선택적 인수 `structure`가 있습니다. 이 인수를 지정하지 않거나 `auto`로 설정하면 structure는 데이터에서 자동으로 추론됩니다.

**예시:**

`user_files` 디렉터리에 다음 내용이 담긴 JSONEachRow 포맷의 파일 `hobbies.jsonl`이 있다고 가정합니다:

```json
{"id" :  1, "age" :  25, "name" :  "Josh", "hobbies" :  ["football", "cooking", "music"]}
{"id" :  2, "age" :  19, "name" :  "Alan", "hobbies" :  ["tennis", "art"]}
{"id" :  3, "age" :  32, "name" :  "Lana", "hobbies" :  ["fitness", "reading", "shopping"]}
{"id" :  4, "age" :  47, "name" :  "Brayan", "hobbies" :  ["movies", "skydiving"]}
```

ClickHouse는 structure를 따로 지정하지 않아도 이 데이터를 읽을 수 있습니다.

```sql
SELECT * FROM file('hobbies.jsonl')
```

```response
┌─id─┬─age─┬─name───┬─hobbies──────────────────────────┐
│  1 │  25 │ Josh   │ ['football','cooking','music']   │
│  2 │  19 │ Alan   │ ['tennis','art']                 │
│  3 │  32 │ Lana   │ ['fitness','reading','shopping'] │
│  4 │  47 │ Brayan │ ['movies','skydiving']           │
└────┴─────┴────────┴──────────────────────────────────┘
```

참고: `JSONEachRow` 포맷은 파일 확장자 `.jsonl`을 통해 자동으로 결정되었습니다.

자동으로 결정된 structure는 `DESCRIBE` 쿼리로 확인할 수 있습니다:

```sql
DESCRIBE file('hobbies.jsonl')
```

```response
┌─name────┬─type────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ id      │ Nullable(Int64)         │              │                    │         │                  │                │
│ age     │ Nullable(Int64)         │              │                    │         │                  │                │
│ name    │ Nullable(String)        │              │                    │         │                  │                │
│ hobbies │ Array(Nullable(String)) │              │                    │         │                  │                │
└─────────┴─────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## 테이블 엔진 [File](/ko/reference/engines/table-engines/special/file), [S3](/ko/reference/engines/table-engines/integrations/s3), [URL](/ko/reference/engines/table-engines/special/url), [HDFS](/ko/reference/engines/table-engines/integrations/hdfs), [azureBlobStorage](/ko/reference/engines/table-engines/integrations/azureBlobStorage) {#table-engines-file-s3-url-hdfs-azureblobstorage}

```sql

```


## clickhouse-local {#clickhouse-local}

`clickhouse-local`에는 입력 데이터의 structure를 지정하는 선택적 매개변수 `-S/--structure`가 있습니다. 이 매개변수를 지정하지 않거나 `auto`로 설정하면 데이터로부터 structure가 추론됩니다.

**예시:**

`hobbies.jsonl` 파일을 사용해 보겠습니다. `clickhouse-local`을 사용하여 이 파일의 데이터를 다음과 같이 쿼리할 수 있습니다.

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='DESCRIBE TABLE hobbies'
```

```response
id    Nullable(Int64)
age    Nullable(Int64)
name    Nullable(String)
hobbies    Array(Nullable(String))
```

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='SELECT * FROM hobbies'
```

```response
1    25    Josh    ['football','cooking','music']
2    19    Alan    ['tennis','art']
3    32    Lana    ['fitness','reading','shopping']
4    47    Brayan    ['movies','skydiving']
```

## 삽입 테이블의 structure 사용하기 {#using-structure-from-insertion-table}

테이블 함수 `file/s3/url/hdfs`를 사용하여 테이블에 데이터를 삽입할 때,
데이터에서 structure를 추출하는 대신 삽입 테이블의 structure를 사용할 수 있습니다.
스키마 추론에는 시간이 걸릴 수 있으므로 이 방식을 사용하면 삽입 성능이 향상될 수 있습니다. 또한 테이블에 최적화된 스키마(schema)가 있으면
타입 간 변환이 수행되지 않으므로 유용합니다.

이 동작은 특수 설정 [use&#95;structure&#95;from&#95;insertion&#95;table&#95;in&#95;table&#95;functions](/ko/reference/settings/session-settings/use#use_structure_from_insertion_table_in_table_functions)로
제어합니다. 이 설정의 가능한 값은 3가지입니다.

* 0 - 테이블 함수가 데이터에서 structure를 추출합니다.
* 1 - 테이블 함수가 삽입 테이블의 structure를 사용합니다.
* 2 - 삽입 테이블의 structure를 사용할 수 있는지, 아니면 스키마 추론을 사용할지 ClickHouse가 자동으로 결정합니다. 기본값입니다.

**예시 1:**

다음과 같은 structure로 `hobbies1` 테이블을 생성합니다.

```sql
CREATE TABLE hobbies1
(
    `id` UInt64,
    `age` LowCardinality(UInt8),
    `name` String,
    `hobbies` Array(String)
)
ENGINE = MergeTree
ORDER BY id;
```

이어서 `hobbies.jsonl` 파일의 데이터를 삽입합니다:

```sql
INSERT INTO hobbies1 SELECT * FROM file(hobbies.jsonl)
```

이 경우 파일의 모든 컬럼이 변경 없이 테이블에 삽입되므로, ClickHouse는 스키마 추론 대신 삽입 테이블의 structure를 사용합니다.

**예시 2:**

다음과 같은 structure로 `hobbies2` 테이블을 생성해 보겠습니다.

```sql
CREATE TABLE hobbies2
(
  `id` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

그런 다음 `hobbies.jsonl` 파일의 데이터를 삽입합니다:

```sql
INSERT INTO hobbies2 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

이 경우 `SELECT` 쿼리(`SELECT` query)의 모든 컬럼이 테이블에 존재하므로, ClickHouse는 삽입 테이블의 structure를 사용합니다.
이 방식은 JSONEachRow, TSKV, Parquet 등 컬럼의 부분 집합 읽기를 지원하는 입력 형식에서만 동작합니다(예를 들어 TSV 형식에서는 동작하지 않습니다).

**예시 3:**

다음과 같은 structure로 `hobbies3` 테이블을 생성합니다:

```sql
CREATE TABLE hobbies3
(
  `identifier` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY identifier;
```

이어서 `hobbies.jsonl` 파일의 데이터를 삽입합니다:

```sql
INSERT INTO hobbies3 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

이 경우 `SELECT` 쿼리(`SELECT` query)에서 `id` 컬럼을 사용하지만 테이블에는 이 컬럼이 없으므로(대신 이름이 `identifier`인 컬럼이 있음),
ClickHouse는 삽입 테이블의 structure를 사용할 수 없으며 스키마 추론이 사용됩니다.

**예시 4:**

다음 structure로 `hobbies4` 테이블을 생성해 보겠습니다:

```sql
CREATE TABLE hobbies4
(
  `id` UInt64,
  `any_hobby` Nullable(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

그런 다음 `hobbies.jsonl` 파일의 데이터를 삽입합니다:

```sql
INSERT INTO hobbies4 SELECT id, empty(hobbies) ? NULL : hobbies[1] FROM file(hobbies.jsonl)
```

이 예시에서는 테이블에 삽입하기 위해 `SELECT` 쿼리에서 `hobbies` 컬럼에 일부 연산을 수행하므로, ClickHouse는 삽입 테이블의 structure를 사용할 수 없으며 대신 스키마 추론을 사용합니다.

## 스키마 추론 캐시 {#schema-inference-cache}

대부분의 입력 형식에서 스키마 추론은 데이터의 structure를 파악하기 위해 일부 데이터를 읽으며, 이 과정에는 시간이 걸릴 수 있습니다.
ClickHouse가 동일한 파일에서 데이터를 읽을 때마다 같은 스키마를 반복해서 추론하지 않도록 추론된 스키마(inferred schema)를 캐시에 저장하며, 이후 동일한 파일에 다시 액세스하면 ClickHouse는 캐시에 저장된 스키마를 사용합니다.

이 캐시를 제어하는 전용 설정은 다음과 같습니다.

* `schema_inference_cache_max_elements_for_{file/s3/hdfs/url/azure}` - 해당 테이블 함수에 대해 캐시되는 스키마의 최대 개수입니다. 기본값은 `4096`입니다. 이 설정은 서버 설정에서 지정해야 합니다.
* `schema_inference_use_cache_for_{file,s3,hdfs,url,azure}` - 스키마 추론 시 캐시 사용 여부를 켜거나 끕니다. 이 설정은 쿼리에서 사용할 수 있습니다.

파일의 스키마는 데이터를 수정하거나 포맷 설정을 변경하면 달라질 수 있습니다.
따라서 스키마 추론 캐시는 파일 소스, 형식 이름, 사용된 포맷 설정, 파일의 마지막 수정 시간을 기준으로 스키마를 식별합니다.

참고: `url` 테이블 함수에서 url로 액세스하는 일부 파일에는 마지막 수정 시간 정보가 없을 수 있습니다. 이러한 경우를 위해 전용 설정
`schema_inference_cache_require_modification_time_for_url`이 제공됩니다. 이 설정을 비활성화하면 해당 파일에 대해 마지막 수정 시간 없이도 캐시의 스키마를 사용할 수 있습니다.

또한 현재 캐시에 있는 모든 스키마를 보여주는 시스템 테이블 [schema&#95;inference&#95;cache](/ko/reference/system-tables/schema_inference_cache)와, 모든 소스 또는 특정 소스의 스키마 캐시를 비울 수 있는 시스템 쿼리(system query) `SYSTEM CLEAR SCHEMA CACHE [FOR File/S3/URL/HDFS]`
도 제공됩니다.

## 텍스트 형식 {#text-formats}

텍스트 형식에서는 ClickHouse가 데이터를 행 단위로 읽고, 포맷에 따라 열 값(column values)을 추출한 다음,
몇 가지 재귀 파서와 휴리스틱을 사용하여 각 값의 타입을 결정합니다. 스키마 추론 시 데이터에서 읽는 최대 행(rows) 수와 바이트 수는
`input_format_max_rows_to_read_for_schema_inference`(기본값 25000) 및 `input_format_max_bytes_to_read_for_schema_inference`(기본값 32Mb) 설정으로 제어합니다.
기본적으로 모든 추론된 타입은 [Nullable](/ko/reference/data-types/nullable)이지만, `schema_inference_make_columns_nullable` 설정으로 이를 변경할 수 있습니다([설정](#settings-for-text-formats) 섹션의 예시 참조).

### JSON 형식 {#json-formats}

JSON 형식에서 ClickHouse는 JSON 사양에 따라 값을 파싱한 다음, 해당 값에 가장 적합한 데이터 타입(data type)을 찾습니다.

JSON 형식에서 스키마 추론이 어떻게 동작하는지, 어떤 타입을 추론할 수 있는지, 그리고 어떤 전용 설정을 사용할 수 있는지 살펴보겠습니다.

**예시**

이하 예시에서는 [format](/ko/reference/functions/table-functions/format) 테이블 함수를 사용합니다.

정수(Integers), 부동 소수점 자료형(Floats), 불리언 값, Strings:

```sql
DESC format(JSONEachRow, '{"int" : 42, "float" : 42.42, "string" : "Hello, World!"}');
```

```response
│ bool   │ Nullable(Bool)    │              │                    │         │                  │                │

```

날짜, DateTimes:

```response
└────────────┴─────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

배열:

배열에 `null`이 포함되어 있으면 ClickHouse는 나머지 배열 요소(array elements)의 타입을 사용합니다:



이름이 지정된 튜플:

`input_format_json_try_infer_named_tuples_from_objects` 설정이 활성화되어 있으면, ClickHouse는 스키마 추론 시 JSON 객체에서 named tuple을 추론하려고 시도합니다.
이렇게 생성된 named tuple에는 샘플 데이터 내 대응되는 모든 JSON 객체의 원소가 모두 포함됩니다.

```sql
SET input_format_json_try_infer_named_tuples_from_objects = 1;
DESC format(JSONEachRow, '{"obj" : {"a" : 42, "b" : "Hello"}}, {"obj" : {"a" : 43, "c" : [1, 2, 3]}}, {"obj" : {"d" : {"e" : 42}}}')
```

이름 없는 Tuple:


##### input_format_json_try_infer_named_tuples_from_objects {#input_format_json_try_infer_named_tuples_from_objects}

##### input_format_json_use_string_type_for_ambiguous_paths_in_named_tuples_inference_from_objects {#input_format_json_use_string_type_for_ambiguous_paths_in_named_tuples_inference_from_objects}

이 설정을 활성화하면 JSON 객체에서 named tuple을 추론할 때(`input_format_json_try_infer_named_tuples_from_objects`가 활성화된 경우) 모호한 경로가 있으면 예외를 발생시키는 대신 String 타입을 사용합니다.
따라서 모호한 경로가 있더라도 JSON 객체를 이름이 지정된 Tuple(named tuple)로 읽을 수 있습니다.

기본적으로 비활성화되어 있습니다.

**예시**

설정이 비활성화된 경우:

```sql title="Query"
SET input_format_json_try_infer_named_tuples_from_objects = 1;
SET input_format_json_use_string_type_for_ambiguous_paths_in_named_tuples_inference_from_objects = 0;
DESC format(JSONEachRow, '{"obj" : {"a" : 42}}, {"obj" : {"a" : {"b" : "Hello"}}}');
```

##### input_format_json_infer_incomplete_types_as_strings {#input_format_json_infer_incomplete_types_as_strings}

이 설정을 활성화하면 스키마 추론 시 데이터 표본(sample)에 `Null`/`{}`/`[]`만 포함된 JSON 키에 String 유형을 사용할 수 있습니다.
JSON 형식에서는 관련 설정이 모두 활성화되어 있으면(기본적으로 모두 활성화되어 있음) 어떤 값이든 String으로 읽을 수 있습니다. 따라서 유형을 알 수 없는 키에 String 유형을 사용하면 스키마 추론 시 `Cannot determine type for column 'column_name' by first 25000 rows of data, most likely this column contains only Nulls or empty Arrays/Maps`와 같은 오류를 방지할 수 있습니다.

```sql title="Query"
SELECT * FROM format(JSONEachRow, '{"obj" : {"a" : [1,2,3], "b" : "hello", "c" : null, "d" : {}, "e" : []}}');
```

```markdown title="Response"
│ obj  │ Tuple(a Array(Nullable(Int64)), b Nullable(String), c Nullable(String), d Nullable(String), e Array(Nullable(String))) │              │                    │         │                  │                │
└──────┴────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘

┌─obj────────────────────────────┐
│ ([1,2,3],'hello',NULL,'{}',[]) │
└────────────────────────────────┘
```

### CSV {#csv}

CSV 형식에서 ClickHouse는 구분 기호에 따라 행에서 열 값(column values)을 추출합니다. ClickHouse는 숫자와 문자열(strings)을 제외한 모든 유형이 큰따옴표로 감싸져 있다고 가정합니다. 값이 큰따옴표로 감싸져 있으면 ClickHouse는 재귀 파서를 사용하여 따옴표 안의
데이터를 파싱한 다음, 해당 값에 가장 적합한 데이터 유형(data type)을 찾습니다. 값이 큰따옴표로 감싸져 있지 않으면 ClickHouse는 이를 숫자로 파싱하려고 시도하며,
숫자가 아니면 문자열로 처리합니다.

ClickHouse가 파서와 휴리스틱을 사용해 복합 유형을 판별하지 않도록 하려면 `input_format_csv_use_best_effort_in_schema_inference` 설정을 비활성화하십시오.
그러면 ClickHouse는 모든 컬럼을 문자열(strings)로 처리합니다.

`input_format_csv_detect_header` 설정이 활성화되어 있으면 ClickHouse는 스키마(schema)를 추론할 때 컬럼 이름(Column Names)(경우에 따라 유형도 포함)이 담긴 헤더를 감지하려고 시도합니다. 이 설정은 기본적으로 활성화되어 있습니다.

### TSV/TSKV {#tsv-tskv}

TSV/TSKV 포맷에서 ClickHouse는 탭 구분 기호에 따라 행에서 컬럼 값을 추출한 다음, 재귀 파서로 추출된 값을 파싱하여 가장 적합한 유형을 결정합니다. 유형을 결정할 수 없으면 ClickHouse는 이 값을 String으로 처리합니다.

### CustomSeparated {#custom-separated}

CustomSeparated 포맷에서 ClickHouse는 먼저 지정된 구분 기호에 따라 행에서 모든 열 값(column values)을 추출한 다음, 이스케이프 규칙에 따라
각 값의 데이터 유형(data type)을 추론합니다.

`input_format_custom_detect_header` 설정이 활성화되어 있으면 ClickHouse는 스키마(schema)를 추론할 때 컬럼 이름(Column Names)(경우에 따라 유형 포함)이 담긴 헤더를 감지하려고 시도합니다. 이 설정은 기본적으로 활성화되어 있습니다.

**예시**

```sql
SET format_custom_row_before_delimiter = '<row_before_delimiter>',
       format_custom_row_after_delimiter = '<row_after_delimiter>\n',
       format_custom_row_between_delimiter = '<row_between_delimiter>\n',
       format_custom_result_before_delimiter = '<result_before_delimiter>\n',
       format_custom_result_after_delimiter = '<result_after_delimiter>\n',
       format_custom_field_delimiter = '<field_delimiter>',
       format_custom_escaping_rule = 'Quoted'

DESC format(CustomSeparated, $$<result_before_delimiter>
<row_before_delimiter>42.42<field_delimiter>'Some string 1'<field_delimiter>[1, NULL, 3]<row_after_delimiter>
<row_between_delimiter>
<row_before_delimiter>NULL<field_delimiter>'Some string 3'<field_delimiter>[1, 2, NULL]<row_after_delimiter>
<result_after_delimiter>
$$)
```

```response
┌─name─┬─type───────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ c1   │ Nullable(Float64)      │              │                    │         │                  │                │
│ c2   │ Nullable(String)       │              │                    │         │                  │                │
│ c3   │ Array(Nullable(Int64)) │              │                    │         │                  │                │
└──────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Template {#template}

Template 형식에서 ClickHouse는 먼저 지정된 템플릿에 따라 행에서 모든 열 값(column values)을 추출한 다음, 각 값의 이스케이프 규칙에 따라
데이터 유형(data type)을 추론하려고 시도합니다.

**예시**

다음 내용이 담긴 `resultset` 파일이 있다고 가정합니다:

```bash
<result_before_delimiter>
${data}<result_after_delimiter>
```

또한 다음 내용이 담긴 `row_format` 파일도 있습니다:

```text
<row_before_delimiter>${column_1:CSV}<field_delimiter_1>${column_2:Quoted}<field_delimiter_2>${column_3:JSON}<row_after_delimiter>
```

그런 다음 다음과 같은 쿼리를 실행할 수 있습니다.

```sql
SET format_template_rows_between_delimiter = '<row_between_delimiter>\n',
       format_template_row = 'row_format',
       format_template_resultset = 'resultset_format'

DESC format(Template, $$<result_before_delimiter>
<row_before_delimiter>42.42<field_delimiter_1>'Some string 1'<field_delimiter_2>[1, null, 2]<row_after_delimiter>
<row_between_delimiter>
<row_before_delimiter>\N<field_delimiter_1>'Some string 3'<field_delimiter_2>[1, 2, null]<row_after_delimiter>
<result_after_delimiter>
$$)
```

```response
┌─name─────┬─type───────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ column_1 │ Nullable(Float64)      │              │                    │         │                  │                │
│ column_2 │ Nullable(String)       │              │                    │         │                  │                │
│ column_3 │ Array(Nullable(Int64)) │              │                    │         │                  │                │
└──────────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### 텍스트 형식 설정 {#settings-for-text-formats}

#### input_format_max_rows_to_read_for_schema_inference/input_format_max_bytes_to_read_for_schema_inference {#input-format-max-rows-to-read-for-schema-inference}

이 설정은 스키마 추론 시 읽을 데이터의 양을 제어합니다.
더 많은 행/바이트를 읽을수록 스키마 추론에 걸리는 시간은 늘어나지만, 타입을
올바르게 판단할 가능성은 높아집니다(특히 데이터에 널 값(nulls)이 많은 경우).

기본값:

* `input_format_max_rows_to_read_for_schema_inference`: `25000`
* `input_format_max_bytes_to_read_for_schema_inference`: `33554432` (32 Mb)

#### column_names_for_schema_inference {#column-names-for-schema-inference}

명시적인 컬럼 이름(Column Names)이 없는 포맷에서 스키마 추론에 사용할 컬럼 이름 목록입니다. 지정한 이름은 기본값인 `c1,c2,c3,...` 대신 사용됩니다. 형식은 `column1,column2,column3,...`입니다.

**예시**

```sql
DESC format(TSV, 'Hello, World!    42    [1, 2, 3]') settings column_names_for_schema_inference = 'str,int,arr'
```

```response
│ int  │ Nullable(Int64)        │              │                    │         │                  │                │

└──────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

#### schema_inference_hints {#schema-inference-hints}

스키마 추론 시 자동으로 결정된 타입 대신 사용할 컬럼 이름(Column Names)과 타입의 목록입니다. 포맷: &#39;column&#95;name1 column&#95;type1, column&#95;name2 column&#95;type2, ...&#39;.

```response
│ status  │ Nullable(String)        │              │                    │         │                  │                │
│ hobbies │ Array(Nullable(String)) │              │                    │         │                  │                │
```

#### schema_inference_make_columns_nullable $ {#schema-inference-make-columns-nullable}

NULL 허용 여부에 대한 정보가 없는 포맷에서 스키마 추론 시 추론된 타입을 `Nullable`로 만들지 여부를 제어합니다. 가능한 값:

* 0 - 추론된 타입은 `Nullable`이 되지 않습니다.
* 1 - 모든 추론된 타입이 `Nullable`이 됩니다.
* 2 또는 &#39;auto&#39; - 텍스트 형식에서는 스키마 추론 중 파싱되는 표본(sample)에서 컬럼에 `NULL`이 포함된 경우에만 추론된 타입이 `Nullable`이 됩니다. 강타입(strongly-typed) 포맷(Parquet, ORC, Arrow)에서는 NULL 허용 여부 정보를 파일 메타데이터에서 가져옵니다.
* 3 - 텍스트 형식에서는 `Nullable`을 사용하고, 강타입 포맷에서는 파일 메타데이터를 사용합니다.

기본값: 3.

**예시**

```sql
SET schema_inference_make_columns_nullable = 1;
DESC format(JSONEachRow, $$
                                {"id" :  1, "age" :  25, "name" : "Josh", "status" : null, "hobbies" : ["football", "cooking"]}
                                {"id" :  2, "age" :  19, "name" :  "Alan", "status" : "married", "hobbies" :  ["tennis", "art"]}
                         $$)
```

```response
│ id      │ Nullable(Int64)         │              │                    │         │                  │                │
```

#### input_format_try_infer_integers {#input-format-try-infer-integers}

<Note>
  이 설정은 `JSON` 데이터 타입에는 적용되지 않습니다.
</Note>

이 설정이 활성화되면 ClickHouse는 텍스트 형식의 스키마 추론 시 부동 소수점 수 대신 정수(integer)로 추론을 시도합니다.
샘플 데이터에서 해당 컬럼의 숫자가 모두 정수이면 타입은 `Int64`가 되고, 부동 소수점 수가 하나라도 있으면 타입은 `Float64`가 됩니다.

기본적으로 활성화되어 있습니다.

**예시**

```sql
SET input_format_try_infer_integers = 0
DESC format(JSONEachRow, $$

                                {"number" : 2}
```

#### input_format_try_infer_datetimes {#input-format-try-infer-datetimes}

이 설정이 활성화되면 ClickHouse는 텍스트 형식에 대한 스키마 추론 시 문자열 필드(String Fields)에서 `DateTime` 또는 `DateTime64` 타입을 추론하려고 시도합니다.
샘플 데이터에서 컬럼의 모든 필드가 날짜 및 시간(Datetime)으로 파싱되면 타입은 `DateTime` 또는 `DateTime64(9)`(소수 부분이 있는 값이 하나라도 있는 경우)가 되며,
하나 이상의 필드가 날짜 및 시간으로 파싱되지 않으면 타입은 `String`이 됩니다.

기본적으로 활성화되어 있습니다.

```sql
SET input_format_try_infer_datetimes = 0;
```

```sql
SET input_format_try_infer_datetimes = 1;
```

## 자기 설명형 포맷 {#self-describing-formats}

자기 설명형(self-describing) 포맷은 데이터 구조에 대한 정보를 데이터 자체에 포함합니다.
이 정보는 설명이 담긴 헤더일 수도 있고, 바이너리 타입 트리나 일종의 테이블일 수도 있습니다.
이러한 포맷의 파일에서 스키마(schema)를 자동으로 추론하기 위해 ClickHouse는 타입 정보가 담긴 데이터 일부를 읽어
이를 ClickHouse 테이블(table)의 스키마로 변환합니다.

### -WithNamesAndTypes 접미사가 붙은 포맷 {#formats-with-names-and-types}

ClickHouse는 -WithNamesAndTypes 접미사가 붙은 일부 텍스트 형식을 지원합니다. 이 접미사는 실제 데이터 앞에 컬럼 이름(Column Names)과 타입을 담은 행(rows) 2개가 추가로 포함되어 있음을 의미합니다.
이러한 포맷에 대해 스키마 추론을 수행할 때 ClickHouse는 처음 2개의 행(rows)을 읽어 컬럼 이름(Column Names)과 타입을 추출합니다.

**예시**

```sql
DESC format(TSVWithNamesAndTypes,
$$num    str    arr
UInt8    String    Array(UInt8)
42    Hello, World!    [1,2,3]
$$)
```

```response
┌─name─┬─type─────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ num  │ UInt8        │              │                    │         │                  │                │
│ str  │ String       │              │                    │         │                  │                │
│ arr  │ Array(UInt8) │              │                    │         │                  │                │
└──────┴──────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### 메타데이터가 포함된 JSON 포맷 {#json-with-metadata}

일부 JSON 입력 포맷([JSON](/ko/reference/formats/JSON/JSON), [JSONCompact](/ko/reference/formats/JSON/JSONCompact), [JSONColumnsWithMetadata](/ko/reference/formats/JSON/JSONColumnsWithMetadata))에는 컬럼 이름(Column Names)과 타입 정보를 담은 메타데이터가 포함되어 있습니다.
이러한 포맷에서 스키마 추론을 수행할 때 ClickHouse는 이 메타데이터를 읽습니다.

**예시**

```sql
DESC format(JSON, $$
{
    "meta":
    [
        {
            "name": "num",
            "type": "UInt8"
        },
        {
            "name": "str",
            "type": "String"
        },
        {
            "name": "arr",
            "type": "Array(UInt8)"
        }
    ],

    "data":
    [
        {
            "num": 42,
            "str": "Hello, World",
            "arr": [1,2,3]
        }
    ],

    "rows": 1,

    "statistics":
    {
        "elapsed": 0.005723915,
        "rows_read": 1,
        "bytes_read": 1
    }
}
$$)
```

```response
┌─name─┬─type─────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ num  │ UInt8        │              │                    │         │                  │                │
│ str  │ String       │              │                    │         │                  │                │
│ arr  │ Array(UInt8) │              │                    │         │                  │                │
└──────┴──────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Native {#native}

## 강타입 바이너리 형식 {#strong-typed-binary-formats}

이러한 포맷에서는 직렬화된 각 값에 해당 값의 타입 정보(경우에 따라 이름 정보도)가 포함되지만, 테이블 전체에 대한 정보는 포함되지 않습니다.
이러한 포맷에서 스키마 추론을 수행할 때 ClickHouse는 데이터를 행 단위로 읽고(최대 `input_format_max_rows_to_read_for_schema_inference`개 행 또는 `input_format_max_bytes_to_read_for_schema_inference` 바이트까지), 데이터에서
각 값의 타입(경우에 따라 이름도)을 추출한 다음 이 타입들을 ClickHouse 타입으로 변환합니다.

### MsgPack {#msgpack}

MsgPack 포맷에는 행 사이에 구분자가 없으므로, 이 포맷에서 스키마 추론을 사용하려면 `input_format_msgpack_number_of_columns` 설정으로 테이블의 컬럼 수를
지정해야 합니다. ClickHouse는 다음과 같은 자료형 대응 관계(type matches)를 사용합니다.

| MessagePack 데이터 타입 (`INSERT`)                                      | ClickHouse 데이터 타입(ClickHouse data type)      |
| ------------------------------------------------------------------ | -------------------------------------------- |
| `int N`, `uint N`, `negative fixint`, `positive fixint`            | [Int64](/ko/reference/data-types/int-uint)      |
| `bool`                                                             | [UInt8](/ko/reference/data-types/int-uint)      |
| `fixstr`, `str 8`, `str 16`, `str 32`, `bin 8`, `bin 16`, `bin 32` | [String](/ko/reference/data-types/string)       |
| `float 32`                                                         | [Float32](/ko/reference/data-types/float)       |
| `float 64`                                                         | [Float64](/ko/reference/data-types/float)       |
| `uint 16`                                                          | [Date](/ko/reference/data-types/date)           |
| `uint 32`                                                          | [DateTime](/ko/reference/data-types/datetime)   |
| `uint 64`                                                          | [DateTime64](/ko/reference/data-types/datetime) |
| `fixarray`, `array 16`, `array 32`                                 | [Array](/ko/reference/data-types/array)         |
| `fixmap`, `map 16`, `map 32`                                       | [Map](/ko/reference/data-types/map)             |

기본적으로 모든 추론된 타입은 `Nullable`로 감싸지며, 이 동작은 `schema_inference_make_columns_nullable` 설정으로 변경할 수 있습니다.

### BSONEachRow {#bsoneachrow}

BSONEachRow에서는 데이터의 각 행이 BSON 문서(document)로 표현됩니다. 스키마 추론 시 ClickHouse는 BSON 문서를 하나씩 읽어 데이터에서
값, 이름, 타입을 추출한 다음, 아래의 자료형 대응 관계(type matches)에 따라 이 타입들을 ClickHouse 타입으로 변환합니다.

| BSON 유형                                                                                                 | ClickHouse 타입                                                                                             |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `\x08` boolean                                                                                          | [Bool](/ko/reference/data-types/boolean)                                                                     |
| `\x10` int32                                                                                            | [Int32](/ko/reference/data-types/int-uint)                                                                   |
| `\x12` int64                                                                                            | [Int64](/ko/reference/data-types/int-uint)                                                                   |
| `\x01` double                                                                                           | [Float64](/ko/reference/data-types/float)                                                                    |
| `\x09` datetime                                                                                         | [DateTime64](/ko/reference/data-types/datetime64)                                                            |
| 바이너리 하위 유형(binary subtype)이 `\x00`인 `\x05` binary, `\x02` string, `\x0E` symbol, `\x0D` JavaScript code | [String](/ko/reference/data-types/string)                                                                    |
| `\x07` ObjectId,                                                                                        | [FixedString(12)](/ko/reference/data-types/fixedstring)                                                      |
| UUID 하위 유형이 `\x04`이고 size = 16인 `\x05` binary                                                           | [UUID](/ko/reference/data-types/uuid)                                                                        |
| `\x04` array                                                                                            | [Array](/ko/reference/data-types/array)/[Tuple](/ko/reference/data-types/tuple) (중첩 타입(nested types)이 서로 다른 경우) |
| `\x03` document                                                                                         | [Named Tuple](/ko/reference/data-types/tuple)/[Map](/ko/reference/data-types/map) (String 키를 사용하는 경우)           |

기본적으로 모든 추론된 타입은 `Nullable`로 감싸지며, 이는 `schema_inference_make_columns_nullable` 설정으로 변경할 수 있습니다.

## 스키마 추론 모드 {#schema-inference-modes}

여러 데이터 파일에 대한 스키마 추론은 `default`와 `union`의 2가지 모드로 동작할 수 있습니다.
모드는 `schema_inference_mode` 설정으로 제어합니다.

### 기본 모드 {#default-schema-inference-mode}

기본 모드에서 ClickHouse는 모든 파일의 스키마(schema)가 동일하다고 가정하고, 추론에 성공할 때까지 파일을 하나씩 읽으며 스키마를 추론합니다.

예시:

다음과 같은 내용의 파일 3개 `data1.jsonl`, `data2.jsonl`, `data3.jsonl`이 있다고 가정합니다.

`data1.jsonl`:

```json
{"field1" :  1, "field2" :  null}
{"field1" :  2, "field2" :  null}
{"field1" :  3, "field2" :  null}
```

`data2.jsonl`:

```json
{"field1" :  4, "field2" :  "Data4"}
{"field1" :  5, "field2" :  "Data5"}
{"field1" :  6, "field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field1" :  7, "field2" :  "Data7", "field3" :  [1, 2, 3]}
{"field1" :  8, "field2" :  "Data8", "field3" :  [4, 5, 6]}
{"field1" :  9, "field2" :  "Data9", "field3" :  [7, 8, 9]}
```

다음 3개의 파일에 스키마 추론을 적용해 보겠습니다:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='default'
```

```response title="Response"
┌─name───┬─type─────────────┐
│ field1 │ Nullable(Int64)  │
│ field2 │ Nullable(String) │
└────────┴──────────────────┘
```

보시다시피 `data3.jsonl` 파일의 `field3`가 없습니다.
이는 ClickHouse가 먼저 `data1.jsonl` 파일에서 스키마(schema)를 추론하려 했으나 `field2` 필드에 널 값(nulls)만 있어 실패했고,
이어서 `data2.jsonl`에서 스키마 추론에 성공하여 `data3.jsonl` 파일의 데이터는 읽지 않았기 때문입니다.

### 유니온 모드(union mode) {#default-schema-inference-mode-1}

유니온 모드(union mode)에서 ClickHouse는 파일마다 스키마(schemas)가 다를 수 있다고 가정하므로, 모든 파일의 스키마를 추론한 다음 이를 하나의 공통 스키마(schema)로 합칩니다.

다음과 같은 내용의 `data1.jsonl`, `data2.jsonl`, `data3.jsonl` 파일 3개가 있다고 가정해 보겠습니다.

`data1.jsonl`:

```json
{"field1" :  1}
{"field1" :  2}
{"field1" :  3}
```

`data2.jsonl`:

```json
{"field2" :  "Data4"}
{"field2" :  "Data5"}
{"field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field3" :  [1, 2, 3]}
{"field3" :  [4, 5, 6]}
{"field3" :  [7, 8, 9]}
```

이 3개의 파일에 스키마 추론을 적용해 보겠습니다:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='union'
```

```response title="Response"
┌─name───┬─type───────────────────┐
│ field1 │ Nullable(Int64)        │
│ field2 │ Nullable(String)       │
│ field3 │ Array(Nullable(Int64)) │
└────────┴────────────────────────┘
```

보시는 바와 같이 모든 파일의 모든 필드가 포함되어 있습니다.

참고:

* 일부 파일에는 결과 스키마(schema)의 컬럼 중 일부가 없을 수 있으므로, 유니온 모드(union mode)는 컬럼의 부분 집합 읽기를 지원하는 포맷(JSONEachRow, Parquet, TSVWithNames 등)에서만 지원되며, 그 외의 포맷(CSV, TSV, JSONCompactEachRow 등)에서는 동작하지 않습니다.
* ClickHouse가 파일 중 하나에서 스키마를 추론하지 못하면 예외가 발생합니다.
* 파일 수가 많으면 모든 파일에서 스키마를 읽는 데 시간이 오래 걸릴 수 있습니다.

## 자동 포맷 감지 {#automatic-format-detection}

데이터 포맷이 지정되지 않았고 파일 확장자로도 판단할 수 없는 경우, ClickHouse는 파일 내용을 바탕으로 파일 포맷을 감지합니다.

**예시:**

다음과 같은 내용의 `data`가 있다고 가정합니다:

```csv
"a","b"
1,"Data1"
2,"Data2"
3,"Data3"
```

포맷이나 structure를 지정하지 않고도 이 파일을 조회하고 쿼리할 수 있습니다:

```sql
:) desc file(data);
```

```response
┌─name─┬─type─────────────┐
│ a    │ Nullable(Int64)  │
│ b    │ Nullable(String) │
└──────┴──────────────────┘
```

```sql
:) select * from file(data);
```

```response
┌─a─┬─b─────┐
│ 1 │ Data1 │
│ 2 │ Data2 │
│ 3 │ Data3 │
└───┴───────┘
```

<Note>
  ClickHouse는 일부 포맷만 감지할 수 있고 감지 과정에도 시간이 걸리므로, 항상 포맷을 명시적으로 지정하는 것이 좋습니다.
</Note>
