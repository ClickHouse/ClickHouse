JOIN 메모리는 두 가지 그룹의 설정으로 제어됩니다. 대부분의 알고리즘에서는 JOIN 상태가 지나치게 커지면 하드 메모리 제한에 따라 쿼리가 중단됩니다. 반면 디스크 유출 임계값(spill threshold)에 도달하면 JOIN 상태의 일부가 디스크에 기록되므로 쿼리를 계속 실행할 수 있습니다.

## 하드 메모리 제한 {#hard-limits}

* [`max_rows_in_join`](/ko/reference/settings/session-settings/max-rows#max_rows_in_join)은 JOIN의 오른쪽 데이터 구조(일반적으로 해시 테이블)에 들어가는 행(rows) 수를 제한합니다.
* [`max_bytes_in_join`](/ko/reference/settings/session-settings/max-bytes#max_bytes_in_join)은 동일한 데이터 구조의 크기를 바이트 단위로 제한합니다.
* [`join_overflow_mode`](/ko/reference/settings/session-settings/join#join_overflow_mode)는 두 제한 중 하나에 도달했을 때 수행할 동작을 정의합니다.

두 제한은 [`Join` 테이블 엔진](/ko/reference/engines/table-engines/special/join)에도 적용됩니다. 쿼리에 JOIN이 여러 개 포함되어 있으면 ClickHouse는 각 JOIN마다 제한을 검사합니다.

디스크로 유출하는 알고리즘을 포함한 해시 기반 알고리즘에서는 제한에 도달하면 쿼리가 중단되며, 이로 인해 JOIN이 디스크로 유출(spill)되는 일은 없습니다. 따라서 제한을 디스크 유출 임계값(spill threshold) 이하로 설정하면 일반적으로 JOIN이 디스크로 유출되기 전에 쿼리가 중단됩니다.

다음 두 설정으로 이 동작을 변경할 수 있습니다.

* [`enable_adaptive_memory_spill_scheduler`](/ko/reference/settings/session-settings/enable#enable_adaptive_memory_spill_scheduler)는 쿼리에 메모리 압력이 발생하면 해당 조건을 충족하는 프로세서를 디스크로 유출합니다. JOIN에는 이미 디스크 유출이 가능한 JOIN에만 적용됩니다. 즉, 0이 아닌 [디스크 유출 임계값](#spill-thresholds)이 설정된 `hash`, `parallel_hash` 또는 `auto` JOIN, `grace_hash` JOIN, 그리고 임시 저장소가 구성된 경우의 블록 중첩 루프 폴백이 이에 해당합니다. 이러한 JOIN은 디스크 유출 임계값이나 하드 메모리 제한에 도달하기 전에도 디스크로 유출될 수 있습니다.
* [`legacy_join_size_limits_trigger_spilling`](/ko/reference/settings/session-settings/other#legacy_join_size_limits_trigger_spilling)은 26.10 이전 버전의 동작을 복원합니다. 이전 버전에서는 하드 메모리 제한에 도달하면 쿼리를 중단하는 대신, 이미 디스크에서 실행 중인 JOIN 부분을 디스크로 추가 유출합니다. 이 설정을 사용하면 `grace_hash`는 디스크 유출 임계값을 무시하고 하드 메모리 제한만을 기준으로 디스크 유출을 수행합니다. `hash`와 `parallel_hash`는 여전히 디스크 유출 임계값에서 유출을 시작하며, 인메모리 단계에서는 하드 메모리 제한을 계속 상한으로 취급합니다.

다른 알고리즘에서는 제한이 다르게 동작합니다.

* [`ie_join`](/ko/concepts/features/operations/select/join-algorithms#ie-join)에서는 양쪽 입력을 합친 누적량에 제한이 적용됩니다.
* [블록 중첩 루프 폴백](/ko/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback)에서는 디스크로 유출된 블록을 포함하여 구체화된(materialized) 오른쪽 입력 전체에 제한이 적용됩니다.
* [`partial_merge`](/ko/concepts/features/operations/select/join-algorithms#partial-merge)에서는 제한에 도달해도 쿼리가 중단되지 않고 실행 전략이 바뀝니다. 즉, JOIN이 정렬된 오른쪽 블록을 디스크에 쓰기 시작합니다.

## 디스크 유출 임계값(spill threshold) {#spill-thresholds}

* [`max_bytes_before_external_join`](/ko/reference/settings/session-settings/max-bytes#max_bytes_before_external_join)은 해시 기반 JOIN의 오른쪽 입력에 대한 디스크 유출 임계값을 바이트 단위의 절대값으로 설정합니다.
* [`max_bytes_ratio_before_external_join`](/ko/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join)은 사용자 및 서버 메모리 제한 내에서 남아 있는 메모리 대비 비율로 디스크 유출 임계값을 설정합니다. 메모리 제한이 구성되어 있지 않으면 이 비율은 효과가 없습니다.

두 설정을 모두 지정하면 계산된 임계값 중 더 작은 값이 적용됩니다. 이 임계값은 `hash`, `parallel_hash`, `grace_hash`, `auto` 값, 그리고 블록 중첩 루프 폴백에 적용되며, 임시 데이터 경로가 구성되어 있어야 합니다.

## 스필 동작 방식 {#how-spilling-works}

디스크 유출(spill)이 가능한 알고리즘은 각각 자신의 상태 중 서로 다른 부분을 임시 파일에 기록합니다.

* **`hash` 및 `parallel_hash`.** JOIN은 해시 테이블(hash tables)을 메모리에 구축합니다. 오른쪽 입력이 디스크 유출 임계값(spill threshold)을 초과하면 JOIN은 `grace_hash`로 전환됩니다. 오른쪽 행은 조인 키의 해시에 따라 버킷으로 분할되며, 버킷 하나는 메모리에 유지되고 나머지 버킷은 임시 파일에 기록됩니다. 왼쪽 행도 동일한 해시 함수로 분할됩니다. 인메모리 버킷에 해당하는 행은 즉시 조인되고, 나머지 행은 임시 파일에 기록됩니다. 왼쪽 입력을 모두 읽은 후 ClickHouse는 남은 버킷 쌍을 하나씩 로드하여 조인합니다.
* **`grace_hash`.** JOIN은 첫 번째 블록부터 동일한 절차를 따릅니다. 버킷의 해시 테이블이 임계값을 초과하면 버킷 수가 `grace_hash_join_max_buckets`까지 두 배씩 늘어납니다. 이 최대값을 초과하면 쿼리가 오류와 함께 실패합니다.
* **`full_sorting_merge`.** 각 입력의 정렬 작업이 `max_bytes_before_external_sort` 또는 `max_bytes_ratio_before_external_sort`를 초과하면 정렬된 블록을 임시 파일에 기록합니다. 이후 정렬된 파일들을 머지합니다.
* **`partial_merge`.** 오른쪽 입력이 하드 메모리 제한에 도달하면 정렬된 오른쪽 블록과 해당 MinMax 인덱스가 임시 파일에 기록됩니다.
* **블록 중첩 루프(Block nested loop) 폴백.** 오른쪽 블록을 메모리에서 압축해 두었다가, 디스크 유출 임계값에 도달하면 임시 파일에 기록합니다.

[`direct`](/ko/concepts/features/operations/select/join-algorithms#direct) 및 [`ie_join`](/ko/concepts/features/operations/select/join-algorithms#ie-join) 알고리즘은 디스크로 유출하지 않습니다.

임시 파일은 [`tmp_path`](/ko/reference/settings/server-settings/settings/tmp#tmp_path), [`tmp_policy`](/ko/reference/settings/server-settings/settings/tmp#tmp_policy) 또는 [`temporary_data_in_cache`](/ko/reference/settings/server-settings/settings/temporary-data#temporary_data_in_cache) 서버 설정으로 구성된 스토리지에 기록됩니다. 임시 파일을 읽고 쓰는 과정에서 디스크 I/O가 추가로 발생하므로, 스필이 발생하는 JOIN은 메모리에서만 수행되는 동일한 JOIN보다 느립니다.

`ExternalJoinWritePart`, `ExternalJoinCompressedBytes`, `ExternalJoinUncompressedBytes` 프로파일 이벤트(profile events)는 JOIN이 기록한 임시 파일 수와 해당 파일에 담긴 데이터 양을 보여 줍니다. 이 이벤트는 [`system.query_log`](/ko/reference/system-tables/query_log)의 `ProfileEvents` 컬럼에서 확인할 수 있습니다.
