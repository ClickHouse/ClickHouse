이 페이지에서는 ClickHouse가 JOIN을 계획하고 실행하는 방식을 설명합니다. 실행 단계, 비용 기반 JOIN 순서 최적화, 쿼리 플래너 최적화, 런타임 필터링을 다룹니다.

## 빌드 단계와 탐색 단계 {#build-and-probe-phases}

대부분의 JOIN 알고리즘은 두 단계로 실행됩니다.

* **빌드 단계.** ClickHouse는 한쪽 입력을 모두 읽어 해시 테이블이나 정렬된 블록(blocks)의 집합처럼 매칭이 가능한 데이터 구조에 저장합니다. 이 입력을 빌드 측(build side)이라고 합니다.
* **탐색 단계.** ClickHouse는 나머지 입력을 블록 단위로 스트리밍하면서 각 행을 빌드 단계에서 만든 데이터 구조와 매칭합니다. 이 입력을 탐색 측(Probe Side)이라고 합니다.

탐색 단계는 빌드 단계가 끝나야 시작됩니다. 따라서 JOIN에 필요한 메모리는 주로 빌드 측의 크기에 따라 결정됩니다.

기본적으로 JOIN의 오른쪽이 빌드 측이고 왼쪽이 탐색 측입니다. 다만 일부 알고리즘은 이 모델과 다르게 동작합니다. [`direct` 알고리즘](/ko/concepts/features/operations/select/join-algorithms#direct)은 오른쪽이 이미 키-값 구조로 존재하므로 빌드 단계가 없습니다. [`full_sorting_merge` 알고리즘](/ko/concepts/features/operations/select/join-algorithms#full-sorting-merge)은 두 입력을 모두 정렬한 뒤 머지합니다. [`inequality` 알고리즘](/ko/concepts/features/operations/select/join-algorithms#inequality)은 두 입력을 모두 누적한 뒤 조인합니다.

## 쿼리 플래너 동작 {#query-planner-behavior}

쿼리 플래너는 알고리즘이 실행되기 전에 2번의 패스를 거쳐 쿼리 실행 계획(query plan)을 변환합니다. 첫 번째 패스에서는 더 이상 적용할 규칙이 없을 때까지 로컬 상향식 규칙을 반복해서 적용하고, 계획 전체에서 사용하지 않는 컬럼(column)을 제거한 다음 로컬 규칙을 다시 적용합니다. 두 번째 패스에서는 정해진 순서에 따라 계획 전체를 대상으로 분석과 변환을 수행합니다.

플래너는 설정에서 활성화되어 있고 쿼리에 적용 가능한 JOIN 관련 최적화를 다음 순서로 적용할 수 있습니다.

**첫 번째 패스:**

1. `ON` 조건이 상수 false로 축약되는 JOIN에 단락 평가를 적용합니다.
2. 필터 표현식(filter expression)을 분리하고 논리적 `JOIN` `ON` 조건을 추출한 다음, 표현식과 필터(filter)를 병합합니다.
3. `OR`로 연결된 `JOIN` 조건의 부분 푸시다운을 포함하여 필터를 JOIN 아래로 푸시다운합니다.
4. JOIN 바로 위의 필터가 일치하지 않는 행을 항상 제외하면 외부 조인(outer JOIN)을 `INNER` JOIN으로 변환합니다.
5. 변환 조건을 충족하는 `INNER` JOIN을 `IN` 서브쿼리로 변환합니다.
6. JOIN 위의 동등 비교 필터를 `JOIN` 조건에 병합하며, 이 과정에서 `CROSS` JOIN 또는 쉼표 조인(comma join)을 `INNER` JOIN으로 변환합니다.
7. JOIN 이후에 적용되는 필터를 기준으로 `ANY` JOIN을 `SEMI` JOIN 또는 `ANTI` JOIN으로 변환합니다.
8. 정렬 키가 보존되는 쪽의 컬럼만 참조하면 `ORDER BY ... LIMIT` 상위 K개 연산을 `LEFT` JOIN 또는 `RIGHT` JOIN 아래로 푸시다운합니다.

**두 번째 패스:**

1. 계획에서 더 상위에 있는 필터나 해당 JOIN을 감싸는 JOIN의 조건에 따라 외부 조인을 `INNER` JOIN으로 전이적으로 변환합니다.
2. 동등 조인 키를 통해 필터 프레디케이트를 반대쪽 입력으로 전파합니다.
3. 프라이머리 키(primary key)와 행 수 제한을 분석하고, 쿼리 조건 캐시를 설정하며, 텍스트 인덱스 분석(Index Analysis)을 수행합니다.
4. 조인 순서(Join Order)를 최적화하고 build-side를 자동으로 선택합니다.
5. 런타임 JOIN 필터를 삽입하고, 더 이상 사용되지 않는 컬럼을 제거하며, 런타임 필터(runtime filter)를 읽기 단계 쪽으로 푸시다운하고 읽기 시점의 인덱스 분석에 사용하도록 등록합니다.
6. 푸시다운된 필터와 런타임 필터를 `PREWHERE`로 이동할 수 있는 `PREWHERE` 최적화를 수행합니다.
7. JOIN에 대한 `LIMIT` 쿼리에 지연 구체화(lazy materialization)를 적용하고, JOIN을 통한 순서대로 읽기와 분산 조인 계획 수립(join planning)을 수행합니다.
8. 논리적 조인 단계를 물리적 조인 알고리즘(join algorithms)으로 변환한 다음, 물리적 조인 단계에 지연 컬럼 인덱싱을 적용합니다.
9. 조건을 충족하는 `MergeTree` JOIN을 프라이머리 키 범위별로 세그먼트 분할하고, 런타임 필터를 이용한 범위 가지치기를 위해 seal 완료 후에만 실행되는 프로브 읽기를 표시하며, `parallel_full_sorting_merge` JOIN을 세그먼트 분할합니다.

## 조인 순서 최적화 {#multi-table-join-reordering}

같은 서브쿼리 안에서 여러 테이블을 조인하는 쿼리의 경우, 비용 기반 조인 순서 최적화기가 테이블의 실행 순서를 결정합니다.

### JOIN 순서가 중요한 이유 {#why-join-order-matters}

동일한 테이블(tables)을 서로 다른 조인 순서(Join Order)로 조인하면 최종 결과(result)는 같지만, 중간 결과와 build-side 해시 테이블의 크기는 크게 달라집니다. 선택도가 높은 테이블과 조인하기 전에 큰 테이블끼리 조인하면 대규모 중간 결과가 생성되며, 이후 조인 단계에서 이를 해싱하고 탐색해야 합니다. 선택도가 높은 테이블을 먼저 조인하면 초기 단계부터 중간 행 수(row count)를 줄일 수 있습니다.

가능한 JOIN 트리의 수는 테이블 수에 따라 급격히 증가합니다. 테이블이 `n`개이면 왼쪽 편향(left-deep) JOIN 순서는 `n!`개이고 부시형(bushy) JOIN 트리는 `(2n - 2)! / (n - 1)!`개입니다. 테이블이 10개이면 왼쪽 편향 순서는 3,628,800개, 부시형 트리는 17.6십억 개 이상입니다. 테이블이 12개이면 부시형 탐색 공간에 포함되는 트리는 28조 개에 육박합니다.

비용 기반 JOIN 최적화기는 이 문제를 세 가지 구성 요소로 나누어 처리합니다.

* **탐색 공간:** 쿼리의 의미를 유지하는 논리적으로 동등한 JOIN 트리의 집합입니다.
* **비용 모델(Cost Model):** 중간 행 수를 추정하고 각 후보 계획에 수치화된 비용을 할당하는 함수입니다.
* **탐색 전략:** 탐색 공간에서 후보 계획을 열거하고 비용이 낮은 트리를 선택하는 알고리즘입니다.

### 비용 모델과 카디널리티 추정 {#cost-model-and-cardinality-estimates}

비용 모델(Cost Model)은 각 후보 JOIN 노드에 대해 두 입력의 비용 합계에 JOIN 단계 자체의 추정 출력 카디널리티(cardinality)를 더하여 누적 비용을 계산합니다.

출력 카디널리티를 추정하기 위해 최적화기는 먼저 `JOIN` 조건의 선택도(Selectivity)를 추정합니다.

* 컬럼 통계(Column Statistics)를 통해 동등 프레디케이트의 두 키 모두에 대한 고유 값(distinct values) 개수를 알 수 있으면, 선택도는 `1 / max(NDV_left, NDV_right)`로 추정됩니다. 두 입력이 여러 동등 프레디케이트로 연결되어 있으면 최적화기는 그중 가장 작은 선택도를 사용합니다.
* equi-JOIN에 대해 신뢰할 수 있는 고유 값 통계를 사용할 수 없고 두 입력의 행 수(row count)를 모두 알고 있으면, 최적화기는 외래 키와 기본 키 간의 매칭으로 간주하고 조인된 행 수를 `max(left_rows, right_rows)`로 추정합니다.
* 두 입력을 연결하는 동등 프레디케이트가 없으면 최적화기는 카테시안 곱인 `left_rows * right_rows`로 추정합니다.

이후 출력 카디널리티는 JOIN 유형에 따라 조정됩니다.

* `INNER` JOIN은 조인된 행 추정치를 사용하며, 하한은 1입니다.
* `LEFT`, `RIGHT`, `FULL` JOIN은 추정치의 하한을 각각 왼쪽 입력 크기, 오른쪽 입력 크기, 두 입력 크기의 합으로 설정합니다.
* `SEMI` 및 `ANTI` JOIN은 보존되는 쪽을 기준으로 하한을 설정하지 않습니다. 대신 equi-JOIN 선택도와 보존되지 않는 입력의 크기로부터 매칭 비율을 추정한 뒤, `SEMI` JOIN은 보존되는 입력에 이 매칭 비율을 곱하고 `ANTI` JOIN은 그 나머지 비율(1 - 매칭 비율)을 곱합니다.

버전 26.10부터는 조인되는 테이블을 JOIN 키 순서대로 읽을 수 있고 [`query_plan_join_order_use_interesting_orders`](/ko/reference/settings/session-settings/query-plan#query_plan_join_order_use_interesting_orders)가 활성화되어 있으면, `dpsub`가 `hash`의 빌드 및 프로브 작업과 `full_sorting_merge`의 정렬 및 머지 작업을 모델링하여 비용에 따라 둘 중 하나를 선택하고, 정렬된 출력을 이후 JOIN에서 재사용할 수 있는 계획을 우선적으로 선택합니다.

### 검색 알고리즘 {#search-algorithms}

[`query_plan_optimize_join_order_algorithm`](/ko/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_algorithm) 설정에는 플래너가 순서대로 시도할 검색 알고리즘을 쉼표로 구분하여 지정합니다. 26.10 버전부터 기본값은 `dpsub,greedy`입니다.

* **`dpsub`:** 테이블(table)의 부분 집합을 대상으로 하는 상향식 동적 계획법 알고리즘입니다. 개별 테이블(tables)에서 시작하여 크기가 작은 순서대로 테이블 부분 집합을 열거하고, 각 부분 집합을 유효한 JOIN 간선으로 연결된, 서로 겹치지 않고 비어 있지 않은 두 부분 집합으로 나눕니다. 그런 다음 비용 모델(Cost Model)로 각 후보를 평가하고, 모든 테이블에 대한 계획을 구성할 때까지 부분 집합별로 비용이 가장 낮은 계획을 유지합니다. `dpsub`는 bushy 트리와 left-deep 트리를 모두 고려하며, 충돌 감지기와 함께 사용하면 INNER JOIN 이외의 조인도 지원합니다. JOIN 그래프당 테이블 수는 최대 12개로 제한됩니다.
* **`greedy`:** 개별 테이블에서 시작하여 이전 결정을 재검토하지 않고 비용이 가장 낮은 유효한 쌍을 반복적으로 결합하는 휴리스틱 알고리즘입니다. 다항 시간에 실행되며 JOIN 그래프의 최대 크기인 테이블 64개까지 처리할 수 있습니다.

[`query_plan_optimize_join_order_limit`](/ko/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_limit) 설정은 단일 JOIN 그룹으로 평탄화되는 테이블 수를 제한하며, 최대 64까지 지정할 수 있습니다. 이 제한보다 많은 테이블을 조인하는 쿼리는 여러 그룹으로 분할되어 그룹별로 최적화됩니다. `0`으로 설정하면 조인 순서(Join Order) 최적화와 build-side 선택이 모두 비활성화됩니다. `1`로 설정하면 여러 테이블의 순서 재배치는 비활성화되지만 두 테이블 간 build-side 선택은 계속 허용됩니다. 기본 제한값인 `10`에서는 각 그룹에 최대 10개의 테이블이 포함되므로 `dpsub`는 테이블이 10개 이하인 모든 최적화 대상 그룹을 최적화합니다. `query_plan_optimize_join_order_limit`를 `12`로 높이면 `dpsub`가 테이블이 최대 12개인 그룹을 최적화할 수 있습니다. 12보다 높이면 테이블이 12개를 초과하는 그룹은 `greedy`로 폴백됩니다.

**폴백 동작:**

* 평탄화된 JOIN 그래프가 `dpsub`의 테이블 12개 제한을 초과하거나 알고리즘이 지원하지 않는 JOIN 유형을 만나면, 플래너는 `query_plan_optimize_join_order_algorithm`에 지정된 다음 알고리즘으로 폴백합니다. 기본적으로 다음 알고리즘은 `greedy`입니다.
* `query_plan_optimize_join_order_limit`를 12보다 높게 설정한 상태에서 충돌 감지기를 위해 INNER JOIN 이외의 조인을 평탄화할 때 테이블 수가 12개를 초과하게 되면, 플래너는 충돌 감지기용 평탄화(flattening)를 비활성화하여 `greedy`가 나머지 INNER JOIN 하위 그래프를 계속 최적화할 수 있도록 합니다.
* `query_plan_optimize_join_order_algorithm`에 지정된 알고리즘이 모두 실패하면 오류가 발생하고 쿼리가 실패합니다.

### 비내부 JOIN 재정렬과 충돌 감지기 {#reordering-non-inner-joins}

`INNER` JOIN은 교환 법칙과 결합 법칙을 모두 만족하므로, 연결된 `INNER` JOIN을 어떤 방식으로 괄호로 묶더라도 결과는 동일합니다. 반면 외부 JOIN, `SEMI` JOIN, `ANTI` JOIN은 결합 법칙과 교환 법칙의 항등식을 모두 만족하지는 않으므로, 유효성 검사 없이 재정렬하면 잘못된 결과가 반환될 수 있습니다.

비내부 JOIN을 안전하게 재정렬하기 위해 ClickHouse는 [`query_plan_optimize_join_order_conflict_detector`](/ko/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_conflict_detector) 설정으로 선택하는 충돌 감지기를 사용합니다. 허용되는 값은 감지기를 비활성화하는 `''`, CD-A를 사용하는 `a`(정확하지만 일부 유효한 계획을 누락함), CD-C를 사용하는 `c`(정확하고 완전하며 버전 26.10부터 기본값)입니다. 충돌 감지기는 SIGMOD 2013 논문 [On the Correct and Complete Enumeration of the Core Search Space](https://dl.acm.org/doi/10.1145/2463676.2465314)의 알고리즘을 구현합니다.

감지기는 열거를 시작하기 전에 원래 JOIN 트리의 인접한 연산자(operators)들을 네 가지 대수적 속성에 비추어 분석합니다. 그리고 연산자 쌍에 대해 성립하지 않는 각 항등식으로부터, 다른 JOIN 연산자를 적용하기 전에 어떤 테이블이 이미 조인되어 있어야 하는지를 지정하는 충돌 규칙을 생성합니다. `dpsub` 열거 과정에서는 충돌 규칙을 위반하는 후보 분할이 모두 폐기됩니다.

**지원되는 JOIN 유형 및 제외 사항:**

* `dpsub`와 충돌 감지기가 활성화된 경우, `ALL` 엄격성을 갖는 `INNER`, `CROSS`, 쉼표, `LEFT`, `RIGHT`, `FULL` JOIN과 `LEFT` 및 `RIGHT` `SEMI`, `ANTI` JOIN이 다중 테이블 재정렬 대상이 되며, 외부 JOIN, `SEMI` JOIN, `ANTI` JOIN의 양쪽 모두가 포함됩니다.
* 충돌 감지기가 없거나 `greedy`가 그래프를 계획하는 경우, `INNER`, `CROSS`, 쉼표 JOIN, 그리고 `ALL` 엄격성을 가지며 비보존 측이 단일 테이블인 `LEFT` 또는 `RIGHT` JOIN만 3개 이상의 테이블에 걸쳐 재정렬됩니다. 이 모드에서 `FULL`, `SEMI`, `ANTI` JOIN은 그래프를 2개의 테이블로 제한하는 최적화 장벽 역할을 합니다.
* `ANY` JOIN은 두 테이블 간 build-side 선택으로 제한되며 다중 테이블 재정렬 대상이 아닙니다.
* `ASOF` JOIN, `PASTE` JOIN, `GLOBAL` 및 `LOCAL` JOIN, 잔여 필터(filter)가 있는 JOIN, 그리고 `join_use_nulls = 1`에서 비`Nullable` 컬럼을 `Nullable`로 변경하는 외부 JOIN은 다중 테이블 재정렬 대상이 아닙니다.

**NULL 거부 조건의 역할:**

외부 JOIN의 일부 항등식은 프레디케이트가 NULL 공급 측의 `NULL` 값을 거부하는 경우에만 성립합니다. 예를 들어, 인접한 두 `LEFT` JOIN은 중간 테이블의 컬럼이 `NULL`일 때 두 번째 `ON` 프레디케이트가 참이 될 수 없는 경우에만 재결합할 수 있습니다. `join_use_nulls = 0`에서는 매칭되지 않은 행에 `NULL` 대신 타입의 기본값이 채워지므로, NULL 거부 규칙은 관련 컬럼이 `Nullable` 타입인 경우에만 적용됩니다.

**유효하지 않은 재정렬과 유효한 재정렬 예시:**

`join_use_nulls = 1`인 상태에서 `customers`, `orders`, `payments`를 대상으로 하는 다음 쿼리를 살펴보십시오.

```sql
SELECT customers.id, orders.id, payments.order_id
FROM customers
LEFT JOIN orders ON customers.id = orders.customer_id
INNER JOIN payments ON orders.id = payments.order_id
SETTINGS join_use_nulls = 1;
```

다음의 단순화된 논리 계획은 Plan A에서 작성된 순서를, Plan B에서 재정렬 후보를 보여줍니다.

Plan A, 원본:

```text
Inner join [orders.id = payments.order_id]
├── Left outer join [customers.id = orders.customer_id]
│   ├── Scan customers
│   └── Scan orders
└── Scan payments
```

계획 B: 계획 A의 순서를 유효하지 않은 방식으로 변경한 계획:

```text
Left outer join [customers.id = orders.customer_id]
├── Scan customers
└── Inner join [orders.id = payments.order_id]
    ├── Scan orders
    └── Scan payments
```

주문이 없는 고객이라면 Plan A는 `orders` 컬럼이 `NULL` 값으로 채워진 행을 생성한 뒤, `NULL`은 어떤 결제와도 일치하지 않으므로 `INNER` JOIN에서 해당 행을 제거합니다. 반면 Plan B는 `orders`와 `payments`를 먼저 조인한 뒤 `LEFT` JOIN에서 해당 고객을 유지합니다. `LEFT` JOIN 뒤에 `INNER` JOIN이 오면 결합 방향(associativity)이 성립하지 않으므로, 충돌 감지기는 Plan B를 거부합니다.

JOIN 유형을 반대 순서로 작성하면 재정렬이 유효합니다.

```sql
SELECT customers.id, orders.id, payments.order_id
FROM customers
INNER JOIN orders ON customers.id = orders.customer_id
LEFT JOIN payments ON orders.id = payments.order_id
SETTINGS join_use_nulls = 1;
```

계획 C, 원본:

```text
Left outer join [orders.id = payments.order_id]
├── Inner join [customers.id = orders.customer_id]
│   ├── Scan customers
│   └── Scan orders
└── Scan payments
```

계획 D (계획 C를 유효하게 재정렬한 계획):

```text
Inner join [customers.id = orders.customer_id]
├── Scan customers
└── Left outer join [orders.id = payments.order_id]
    ├── Scan orders
    └── Scan payments
```

`INNER` JOIN 뒤에 `LEFT` JOIN이 오면 결합 법칙(associativity)이 성립하므로 Plan C와 Plan D는 동일한 행을 생성하며, 충돌 감지기는 Plan D를 허용합니다.

**SEMI JOIN 재정렬 예시:**

`big`과 `mid`는 서로 일치하는 키를 많이 공유하고, `tiny`에는 소수의 키만 포함된 쿼리를 살펴보겠습니다.

```sql
SELECT sum(big.v + mid.v)
FROM big
INNER JOIN mid ON big.k = mid.k
LEFT SEMI JOIN tiny ON big.k = tiny.k;
```

충돌 감지기가 없으면 `LEFT SEMI` JOIN이 `big INNER JOIN mid` 위에 고정된 채로 남으므로, ClickHouse는 `tiny`로 필터링하기 전에 `big`과 `mid`의 `INNER` JOIN 전체를 먼저 평가합니다. 충돌 감지기를 활성화하면 `dpsub`가 `LEFT SEMI` JOIN을 `INNER` JOIN 아래로 내려 `big`을 먼저 필터링합니다.

### CROSS JOIN 위치 {#cross-join-placement}

`CROSS` 조인에는 동등 조건(equality condition)이 없으므로 조인 그래프에 프레디케이트 간선을 추가하지 않습니다. 최적화기는 재정렬 중에도 그래프가 연결된 상태로 유지되도록 `CROSS` 조인의 양쪽 입력 사이에 선택도(Selectivity)가 `1`인 명시적 간선을 추가합니다. 이를 통해 `dpsub`는 중간 비용이 가장 낮은 위치에 카티션 곱을 배치할 수 있으며, ClickHouse는 해당 작업을 여전히 `CROSS` 조인으로 실행하고 보고합니다.

### 추이적 프레디케이트 {#transitive-predicates}

[`enable_join_transitive_predicates`](/ko/reference/settings/session-settings/enable-join#enable_join_transitive_predicates)가 활성화되어 있으면 최적화기는 JOIN 순서를 탐색하기 전에 `ON` 조건의 동치 클래스에서 추이적 동등 프레디케이트를 추론합니다. 예를 들어 `a.k = b.k`와 `b.k = c.k`에서 `a.k = c.k`를 도출하므로, 탐색 전략은 `a`와 `c` 쌍을 카티션 곱(cross product)으로 처리하지 않고 두 테이블을 직접 조인하는 방안을 고려할 수 있습니다. 이 설정은 버전 26.4에서 도입되었으며, 버전 26.6부터 기본으로 활성화되어 있습니다.

## 빌드 측 자동 선택 {#automatic-build-side-selection}

버전 24.12부터 플래너는 JOIN의 두 입력을 스왑하여 더 작은 입력이 빌드 측(build side)이 되도록 할 수 있습니다. 플래너는 두 입력의 예상 행 수(row count)를 비교하여 왼쪽 입력이 더 작을 것으로 예상되면 해시 기반 JOIN에서 두 입력을 스왑합니다. 이 동작은 [`query_plan_join_swap_table`](/ko/reference/settings/session-settings/query-plan#query_plan_join_swap_table) 설정으로 제어합니다.

입력이 스왑되면 `LEFT` JOIN은 `RIGHT` JOIN으로 실행되고, 반대로 `RIGHT` JOIN은 `LEFT` JOIN으로 실행됩니다. 스왑된 순서는 `EXPLAIN` 출력에서 확인할 수 있습니다.

`dpsub` 비용 모델(Cost Model)은 입력이 왼쪽과 오른쪽 중 어디에 있든 JOIN에 동일한 비용을 할당하므로, 빌드 측 방향은 JOIN 재정렬이 트리 구조를 선택한 후에 결정됩니다. `INNER`, `CROSS`, `ALL` 외부 JOIN에 대한 해시 JOIN에서 `dpsub`는 예상 행 수가 더 작은 입력을 빌드 테이블로 사용하도록 오른쪽에 배치하고, 이에 맞춰 `LEFT` JOIN과 `RIGHT` JOIN을 서로 바꿉니다. 예상 행 수가 같거나 예상값을 사용할 수 없으면 더 많은 테이블을 포함하는 입력을 왼쪽에 배치합니다.

`ANY`, `SEMI`, `ANTI` JOIN에서는 `dpsub` 내부의 탐색 후 방향 결정 단계가 입력을 뒤집지 않으며, `SEMI` 및 `ANTI` JOIN은 쿼리에 작성된 방향으로 되돌립니다. 그 직후 플래너가 선택된 트리로부터 논리적 조인 단계를 구성할 때, 빌드 측 선택 패스는 여전히 `ANY`, `SEMI`, `ANTI` JOIN의 입력을 스왑하여 더 작은 입력을 오른쪽에 배치할 수 있으며, 이때 `LEFT`는 `RIGHT`로, `RIGHT`는 `LEFT`로 바뀝니다. 단, 다음 경우에는 이 스왑을 건너뜁니다. `ANY` JOIN에서 [`join_any_take_last_row`](/ko/reference/settings/session-settings/join#join_any_take_last_row)가 활성화된 경우, [`join_algorithm`](/ko/reference/settings/session-settings/join#join_algorithm)에 원래 방향과 반전된 방향을 모두 지원하지는 않는 `partial_merge` 등의 병합 알고리즘이 포함된 경우, 최적화기가 `full_sorting_merge`를 선택한 경우, 또는 `query_plan_join_swap_table`이 `false`로 설정된 경우입니다.

## 카디널리티(cardinality) 추정과 통계 {#use-of-column-statistics}

비용 기반 최적화기(Cost-Based Optimizer)는 행 수 추정치와 선택도(Selectivity) 추정치를 바탕으로 다음 네 가지를 결정합니다.

* **JOIN 순서:** [`query_plan_optimize_join_order_limit`](/ko/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_limit)에 따라 기본적으로 최대 10개의 테이블로 구성된 그룹 단위로 비용이 가장 낮은 JOIN 순서를 선택합니다. 이보다 큰 쿼리는 여러 그룹으로 분할하여 그룹별로 최적화하며, 제한값을 12보다 크게 설정한 상태에서 그룹의 테이블 수가 12개를 초과하면 `greedy`로 폴백합니다.
* **JOIN 빌드 측(build side):** [`query_plan_join_swap_table`](/ko/reference/settings/session-settings/query-plan#query_plan_join_swap_table)에 따라 추정 크기가 더 작은 입력을 해시 JOIN의 빌드 측에 배치합니다.
* **JOIN 알고리즘:** 조인 대상 테이블을 조인 키 순서로 읽을 수 있으면 비용을 기준으로 `hash`와 `full_sorting_merge` 중 하나를 선택하며, [`query_plan_join_order_use_interesting_orders`](/ko/reference/settings/session-settings/query-plan#query_plan_join_order_use_interesting_orders)에 따라 정렬된 출력을 이후 JOIN에서 재사용할 수 있는 계획을 우선합니다.
* **필터 순서:** `WHERE` 조건을 [`PREWHERE`](/ko/optimize/prewhere)로 옮기고, 압축된 컬럼 크기와 추정 선택도를 기준으로 조건을 정렬하여 비용이 낮고 선택도가 높은 조건부터 실행되도록 합니다.

컬럼 통계(Column Statistics)가 없으면 플래너는 프라이머리 인덱스를 바탕으로 행 수를 추정하므로 추정치가 부정확할 수 있습니다. [컬럼 통계](/ko/reference/engines/table-engines/mergetree-family/mergetree#column-statistics)가 있으면 플래너는 필터 선택도와 조인 키 카디널리티를 모두 추정할 수 있습니다.

### 자동 통계 수집 및 기본 타입 {#automatic-statistics-collection}

`MergeTree` 테이블은 파트가 머지될 때 각 데이터 파트(data part)의 컬럼 통계(Column Statistics)를 자동으로 수집합니다. [`materialize_statistics_on_insert`](/ko/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert)가 활성화되어 있으면, 크기가 [`materialize_statistics_on_insert_max_table_size`](/ko/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert_max_table_size)를 초과하지 않는 테이블은 삽입 시에도 통계가 수집되므로 `ANALYZE`를 수동으로 실행할 필요가 없습니다. 최적화기가 이러한 통계를 사용할지 여부는 [`use_statistics`](/ko/reference/settings/session-settings/use-statistics#use_statistics) 설정으로 제어합니다.

[`auto_statistics_types`](/ko/reference/settings/merge-tree-settings/other#auto_statistics_types) 테이블 설정(table setting)은 적합한 컬럼에서 자동으로 수집할 통계 유형을 지정합니다. 버전 26.7부터 기본값은 `basic`과 `uniq_v2`이며, 버전 26.4에서 자동 수집 대상이 되었던 `minmax`와 `uniq`를 대체합니다.

* **`basic`:** 숫자 및 시간 컬럼의 최솟값과 최댓값, 기본값 및 `NULL` 값의 개수, 문자열의 총 바이트 길이, `Nullable`이 아닌 정수(integer) 및 `Decimal` 컬럼의 정확한 합계를 추적합니다.
* **`uniq_v2`:** 컬럼의 고유 값(distinct values) 개수를 추정합니다.

선언 구문, `ALTER TABLE` 명령어, 지원되는 데이터 타입은 [컬럼 통계](/ko/reference/engines/table-engines/mergetree-family/mergetree#column-statistics)를 참조하십시오.

### 기타 추정 소스 {#other-estimate-sources}

`MergeTree` 컬럼 통계(Column Statistics)와 프라이머리 인덱스 추정 외에도 JOIN 순서 최적화기는 다음 두 가지 카디널리티(cardinality) 추정 소스를 추가로 사용할 수 있습니다.

* **수집된 해시 테이블 통계:** [`use_hash_table_stats_for_join_reordering`](/ko/reference/settings/session-settings/use#use_hash_table_stats_for_join_reordering)으로 제어하며, 버전 26.1부터 사용할 수 있습니다. [`collect_hash_table_stats_during_joins`](/ko/reference/settings/session-settings/collect-hash#collect_hash_table_stats_during_joins)가 활성화되어 있으면 ClickHouse는 실행된 JOIN 하위 계획에서 측정한 build-side 행 수를 캐시합니다. 이후 일치하는 하위 계획이 다시 실행될 때 캐시된 행 수가 정적 추정치보다 작으면 플래너는 측정된 행 수를 사용하여 조인 순서를 재배치합니다.
* **데이터 레이크 메타데이터 통계:** [`use_datalake_metadata_statistics`](/ko/reference/settings/session-settings/use#use_datalake_metadata_statistics)로 제어하며, 버전 26.11부터 `use_statistics`가 활성화된 경우 Apache Iceberg 테이블에서 사용할 수 있습니다. 플래너는 파티션 및 min-max 프루닝 후 남은 Iceberg 매니페스트 파일에서 행 수, 값의 최솟값과 최댓값, NULL 비율을 읽습니다. [`use_iceberg_table_statistics_ndv`](/ko/reference/settings/session-settings/use-iceberg#use_iceberg_table_statistics_ndv)도 활성화되어 있으면 `metadata.json`에 있는 Iceberg 테이블 통계에서 고유 값 개수도 읽습니다.

## 필터 푸시다운 {#filter-pushdown}

[`query_plan_filter_push_down`](/ko/reference/settings/session-settings/query-plan#query_plan_filter_push_down)이 활성화되면 플래너는 `WHERE` 조건을 JOIN 아래로 내려 빌드 및 탐색 단계 전에 각 입력을 먼저 필터링합니다.

* 한 입력의 컬럼만 참조하는 조건은 해당 입력에 적용됩니다.
* `LEFT` JOIN에서는 조건이 오른쪽 입력으로 푸시되지 않습니다. `RIGHT` JOIN에서는 조건이 왼쪽 입력으로 푸시되지 않습니다.
* 한 입력의 조인 키에 대한 조건은 다른 입력에도 적용할 수 있습니다. 일치하는 모든 행에서 두 입력의 키 열(Key Columns) 값이 같기 때문입니다.
* 딕셔너리처럼 이미 채워진 오른쪽 입력이나 `ASOF` JOIN의 오른쪽 입력에는 조건이 푸시되지 않습니다.

다음 두 가지 최적화는 JOIN과 관련된 필터 푸시다운의 적용 범위를 확장합니다.

* **동등 조인(equi-JOIN) 간 프레디케이트 전파:** [`query_plan_propagate_predicate_across_join`](/ko/reference/settings/session-settings/query-plan#query_plan_propagate_predicate_across_join)로 제어합니다. 버전 26.9부터 `MergeTree` 기본 키(primary keys)에 지원되며, 버전 26.11에서는 Parquet 읽기로 지원 범위가 확장되었습니다. 인덱스 분석(Index Analysis) 전에 플래너는 동등 조인의 한쪽 조인 키를 상수와 비교하는 필터(filter)의 논리 조건 항을 다른 쪽으로 복사합니다. 이를 통해 양쪽 입력 모두에서 프라이머리 키 또는 Parquet 행 그룹 프루닝을 수행할 수 있습니다.
* **논리합 푸시다운:** [`use_join_disjunctions_push_down`](/ko/reference/settings/session-settings/use#use_join_disjunctions_push_down)으로 제어합니다. 버전 25.10에 도입되었으며 버전 26.1부터 기본적으로 활성화됩니다. `OR`로 연결된 `JOIN` 조건에서 모든 분기가 동일한 입력에 대한 결정적 프레디케이트를 하나 이상 포함하면, 플래너는 해당 입력에만 적용되는 논리합 필터를 추출하여 JOIN 전에 해당 입력으로 푸시다운합니다.

## 런타임 JOIN 필터 {#runtime-join-filters}

[`enable_join_runtime_filters`](/ko/reference/settings/session-settings/enable-join#enable_join_runtime_filters)가 활성화되면 ClickHouse는 빌드 단계에서 수집한 키를 사용하여 행이 JOIN에 도달하기 전에 프로브 측을 필터링합니다. 이 기능은 버전 26.2부터 기본적으로 활성화되었습니다.

`INNER`, `RIGHT`, `SEMI`, `ANTI` JOIN을 포함하여 조건을 충족하는 해시 기반 JOIN에서는 ClickHouse가 해시 테이블을 채우는 과정에서 build-side 동등 키로 런타임 필터(runtime filter)를 생성합니다. 플래너는 이 필터를 프로브 하위 트리에 연결하고 `PREWHERE`를 포함하여 프로브 측 스토리지 읽기 단계에 최대한 가깝게 푸시다운합니다. 따라서 일치하지 않는 프로브 행은 해시 테이블을 조회하기 전에 제거됩니다. `LEFT ANTI` JOIN에서는 필터가 build-side에 키가 존재하는 행을 제외하고, `NULL` 키를 가진 행은 통과시킵니다.

런타임 필터는 고유한 build-side 키의 개수와 유형에 따라 내부 표현 방식을 조정합니다.

* **정확한 집합(set):** 필터는 처음에 고유한 키 값으로 이루어진 정확한 집합으로 시작합니다. 빈 집합은 상수 마스크로 평가되며, 값이 하나뿐인 비`Nullable` 집합은 직접 동등 비교로 최적화됩니다.
* **밀집 비트셋 또는 블룸 필터:** 고유 키의 개수나 바이트 수가 정확한 집합의 한도를 초과하면, 포지티브 필터는 8비트 및 16비트 정수 키에서는 밀집 비트셋으로, 그 밖의 연속 키 유형에서는 블룸 필터로 전환됩니다. `LEFT ANTI` JOIN 필터는 근사 블룸 필터로 전환되지 않습니다. 거짓 양성이 발생하면 유지되어야 할 행이 제거되기 때문입니다.
* **비활성화:** 포지티브 정확 집합이 블룸 필터 대체 수단 없이 한도를 초과하거나, 블룸 필터가 최대 설정 비트 비율을 초과하거나 초과할 것으로 예측되면 런타임 필터는 영구적으로 비활성화됩니다. 프로브 중 필터를 통과하는 행의 비율이 통과 비율 임계값을 초과하면, ClickHouse는 설정된 블록 수만큼 필터를 일시적으로 건너뛴 후 다시 평가합니다. 또한 예상 프로브 측 행 수가 최소 프로브 행 임계값 이하이면 ClickHouse는 런타임 필터를 생성하지 않습니다.

**그래뉼 가지치기(Granule pruning):**

[`enable_join_runtime_filters_index_analysis`](/ko/reference/settings/session-settings/enable-join#enable_join_runtime_filters_index_analysis)와 [`use_skip_indexes_on_data_read`](/ko/reference/settings/session-settings/use-skip-indexes#use_skip_indexes_on_data_read)가 활성화되면, ClickHouse는 완성된 런타임 필터를 사용하여 `MergeTree` 프로브 읽기에서 그래뉼을 프루닝합니다. 이 설정은 버전 26.10부터 기본적으로 활성화되었습니다. 런타임 필터가 키의 정확한 집합을 유지한 경우 ClickHouse는 `IN` 프레디케이트를 구성하고, 그렇지 않으면 최솟값부터 최댓값까지의 키 범위 프레디케이트를 구성합니다. 프루닝은 기본 키에 포함되거나, `minmax`, `set`, `bloom_filter` 스킵 인덱스가 적용되거나, 전역 행 인덱스 `_part_starting_offset + _part_offset`와 같은 프로브 키에 적용됩니다. Apache Iceberg 테이블에서는 런타임 필터로 데이터 파일, Parquet 행 그룹, Parquet 페이지도 프루닝할 수 있습니다.

런타임 필터 튜닝 설정의 전체 목록은 [JOIN 설정의 쿼리 플래너 섹션](/ko/concepts/features/operations/select/join-settings#query-planner)을 참조하십시오.

## JOIN 계획 검사 {#inspecting-the-join-plan}

쿼리에 `EXPLAIN actions = 1`을 실행하면 JOIN 순서, 유형, 엄격성, 빌드 측(build side), 행 추정치, 선택된 알고리즘을 확인할 수 있습니다. 버전 26.7부터는 일반 `EXPLAIN`이 기본적으로 작업 어노테이션이 포함된 Pretty 포맷으로 렌더링됩니다. `EXPLAIN actions = 1`을 명시적으로 작성하면 이전 버전과 현재 버전 모두에서 동작합니다.

`EXPLAIN actions = 1` 출력에서 각 `Join (JOIN FillRightFirst)` 단계에는 다음 항목이 표시됩니다.

* 각 테이블의 실행 순서와 예상 행 수를 요약한 기호 표현식
* 빌드 측 스왑 또는 재작성 이후 실제로 실행된 JOIN 유형, 엄격성, 물리적 알고리즘을 보여 주는 `Type`, `Strictness`, `Algorithm` 줄
* 예상 비용, 선택도(Selectivity), 출력 행(output rows), 왼쪽 및 오른쪽 입력 행 수
* 2개의 자식 분기. 첫 번째 자식은 왼쪽 프로브 입력이고, 두 번째 자식은 오른쪽 빌드 입력입니다.
* 런타임 필터(runtime filter)가 구축되고 적용되는 위치를 보여 주는 `BuildRuntimeFilter` 단계와 `Runtime filters` 어노테이션

최적화기의 추정치를 실제 실행 결과와 비교하려면 [`EXPLAIN ANALYZE`](/ko/reference/statements/explain#explain-analyze)를 실행하십시오. `EXPLAIN ANALYZE`는 쿼리를 실행하고 단계별 런타임 메트릭을 보고합니다. JOIN 단계에서는 예상 비용과 실제 비용, 선택도, q-error를 포함한 출력 행 수, 왼쪽 및 오른쪽 입력 행 수 등 [예상 메트릭과 실제 메트릭을 비교합니다](/ko/reference/statements/explain#explain-analyze-join-estimation).
