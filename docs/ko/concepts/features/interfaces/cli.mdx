`clickhousectl`(별칭 `chctl`)은 로컬 개발부터 ClickHouse Cloud까지 아우르는 ClickHouse 공식 CLI입니다. 터미널에서 직접 사용할 수 있을 뿐 아니라 스크립트와 코딩 에이전트에서도 활용할 수 있습니다.

`clickhousectl`로 다음 작업을 수행할 수 있습니다.

* 로컬 ClickHouse 버전 설치 및 전환, 격리된 로컬 서버 실행, SQL 실행
* Docker 기반 Postgres를 로컬에서 실행
* ClickHouse Cloud 서비스 생성, 구성, 확장, 백업 및 쿼리
* [ClickHouse Managed Postgres](/ko/products/managed-postgres/overview) 서비스 생성, 모니터링, 구성 및 복원
* 객체 스토리지, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB, BigQuery를 소스로 하는 ClickPipes 생성 및 운영
* [Managed ClickStack](/ko/clickstack/deployment/managed) 서비스의 소스, 대시보드, 알림, 웹훅, 저장된 검색 및 역할 관리
* 실행 가능한 사용자 정의 함수(Executable UDFs)를 로컬에서 개발하여 ClickHouse Cloud에 배포
* 조직 구성원, 초대, API 키 및 역할 관리
* 공식 ClickHouse agent skills를 코딩 에이전트에 설치

이 페이지에서는 대표적인 예시를 소개합니다. 모든 명령과 플래그에 대한 정확한 정보는 `clickhousectl <command> --help`에서 확인하십시오. 대부분의 명령 도움말은 끝부분에 `CONTEXT FOR AGENTS` 블록이 있으며, Cloud 명령은 여기에 필요한 API Key 권한도 함께 표시합니다. 작업별 안내는 각 섹션의 가이드 링크를 참고하십시오. Cloud 중심의 개요는 [ClickHouse CLI](/ko/products/cloud/features/cli)를 참조하십시오.

## 설치 {#installation}

`clickhousectl`은 ARM64 및 x86&#95;64 아키텍처의 macOS와 Linux에서 실행됩니다.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

설치 스크립트는 `~/.local/bin/clickhousectl`을 설치하고 `chctl` 별칭을 생성합니다. `~/.local/bin`이 `PATH`에 포함되어 있는지 확인하십시오.

패키지 매니저를 사용하여 설치할 수도 있습니다.

| 도구                              | 명령                              |
| ------------------------------- | ------------------------------- |
| npm                             | `npm install -g clickhousectl`  |
| uv                              | `uv tool install clickhousectl` |
| pipx                            | `pipx install clickhousectl`    |
| pip                             | `pip install clickhousectl`     |
| cargo-binstall                  | `cargo binstall clickhousectl`  |
| Cargo, 소스 코드로부터 빌드 (Rust 1.94+) | `cargo install clickhousectl`   |

`chctl` 별칭은 설치 스크립트와 npm으로 설치한 경우에만 생성됩니다. 기존 설치를 업데이트하려면 `clickhousectl update`를 실행하십시오([자체 업데이트](#self-update) 참조).

## 요구 사항 {#requirements}

* Docker(로컬 Postgres를 사용하는 경우에만 필요)
* Cloud 명령어를 사용하려면 [ClickHouse Cloud](https://clickhouse.com/cloud) 계정이 필요합니다. 읽기 명령어는 브라우저 OAuth(`cloud auth login`)만으로 사용할 수 있습니다. 리소스를 생성하거나 변경하려면 [API Key](/ko/products/cloud/features/admin-features/api/openapi)가 필요합니다. 자세한 내용은 [인증](#authentication)을 참조하십시오.

## 로컬 {#local}

로컬 명령어는 현재 디렉터리를 기준으로 동작합니다. 각 프로젝트의 서버 데이터는 `.clickhouse/`에 저장되며, ClickHouse 바이너리는 `~/.clickhouse/`에 두고 전역으로 공유합니다. CLI는 상위 디렉터리를 탐색하지 않으므로 로컬 명령어는 반드시 프로젝트 루트에서 실행하십시오. 전체 워크플로는 [로컬 개발 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md)를 참고하십시오.

### 설치 및 버전 선택 {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
```

| 셀렉터           | 의미                                              |
| ------------- | ----------------------------------------------- |
| `latest`      | 최신 ClickHouse 빌드로, 설치·사용·시작할 때마다 원격으로 확인합니다(권장) |
| `stable`      | 최신 안정 릴리스                                       |
| `lts`         | 최신 장기 지원(LTS) 릴리스                               |
| `26.8`        | 일치하는 최신 릴리스                                     |
| `26.8.1.1760` | 정확히 지정한 버전                                      |

`local use`는 필요하면 해당 버전을 설치하고, 이후 서버를 시작할 때 사용할 기본 버전으로 설정한 뒤 `~/.local/bin/clickhouse`에 심볼릭 링크를 생성합니다. 따라서 `clickhouse client`와 `clickhouse local`을 `PATH`에서 바로 사용할 수 있습니다. 심볼릭 링크를 생성하지 않으려면 `--no-global`을 지정하세요. 해당 경로에 일반 파일이 이미 있으면 그대로 둡니다.

`local remove`는 기본 버전이나, 어느 프로젝트에서든 실행 중인 서버가 사용하는 버전은 제거하지 않습니다. `--force`를 지정하면 해당 서버를 중지하고 버전을 제거하며, 기본 버전 설정과 심볼릭 링크도 함께 삭제합니다.

### 프로젝트 초기화 {#initializing-project}

```bash
clickhousectl local init
```

`init`은 선택 사항입니다. 이 명령은 런타임 데이터용으로 git에서 무시되는 `.clickhouse/` 디렉터리를 생성하고, 커밋할 수 있는 SQL 스캐폴드인 `clickhouse/`(`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`)와 `postgres/`(`tables/`, `views/`, `functions/`, `queries/`, `seed/`)도 함께 생성합니다. 다시 실행하면 없는 항목만 생성합니다.

### 로컬 서버 실행 {#managing-servers}

```bash
clickhousectl local server start dev --version latest   # Background start; waits for readiness
clickhousectl local server start dev --no-wait          # Return after spawning
clickhousectl local server start dev --foreground       # Run in the foreground
clickhousectl local server start dev --http-port 8124 --tcp-port 9001
clickhousectl local server list                         # Servers in this project
clickhousectl local server list --global                # Servers across all projects
clickhousectl local server stop dev
clickhousectl local server stop-all                     # Stop all ClickHouse and Postgres servers in this project
clickhousectl local server remove dev                   # Permanently delete a stopped server's data
```

이름이 지정된 각 서버는 `.clickhouse/servers/<name>/data/`에 자체 데이터를 보관하며, 서버를 중지해도 데이터는 다음 시작을 위해 그대로 유지됩니다. 이름을 지정하지 않으면 첫 번째 서버의 이름은 `default`가 되며, `default`가 이미 실행 중이면 새 이름이 자동으로 생성됩니다. 기본 포트는 HTTP 8123과 TCP 9000이며, 해당 포트가 이미 사용 중이면 비어 있는 포트가 할당됩니다.

`--version`을 사용하면 기본 버전을 변경하지 않고 해당 시작에만 적용할 버전을 선택할 수 있습니다. 버전을 지정하지 않고 기본 버전도 설정되지 않은 상태에서 시작하면 `latest`가 설치되지만 기본 버전으로 지정되지는 않습니다. 이를 기본 버전으로 지정하려면 먼저 `local use latest`를 실행하십시오.

### 로컬 클라이언트로 SQL 실행하기 {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client`는 서버를 실행하는 것과 동일한 ClickHouse 바이너리로 지정한 이름의 서버에 연결합니다(기본 이름: `default`). `--` 뒤에 오는 인수는 그대로 `clickhouse client`에 전달됩니다. JSON 모드에서도 출력과 종료 상태는 `clickhouse client`가 반환하므로, 스크립트에서 사용할 때는 SQL 출력 형식을 직접 지정하십시오.

### 사용자 정의 서버 구성 {#custom-config-files}

일부 설정만 담은 XML 또는 YAML 구성 파일을 `~/.clickhouse/configs/`에 넣고, 서버를 시작할 때 이름으로 해당 구성을 지정하십시오:

```bash
mkdir -p ~/.clickhouse/configs
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local server configs
clickhousectl local server stop dev
clickhousectl local server start dev --config analytics
```

이 파일은 기본 제공 기본값 위에 덧씌워지므로 변경할 설정만 포함하면 됩니다. 이 선택은 저장되지 않으므로, 이후 `--config` 없이 시작하면 오버레이가 제거됩니다. 관리형 데이터 경로와 포트는 항상 구성 설정값보다 우선합니다.

### 연결 정보를 dotenv 파일에 저장하기 {#dotenv}

```bash
clickhousectl local server dotenv dev                                     # Writes .env
clickhousectl local server dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv`는 실행 중인 서버의 실제 포트를 읽어 `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_HTTP_PORT`를 기록하며, 사용자, 비밀번호, 데이터베이스를 함께 지정하면 이 값들도 기록합니다. 기존 파일에 있던 다른 줄은 그대로 유지됩니다. 이 파일은 애플리케이션의 dotenv 로더로 불러오십시오. 출력된 프리뷰를 `eval`로 실행해서는 안 됩니다.

### 로컬 Postgres {#local-postgres}

로컬 Postgres는 Docker에서 실행되므로 Docker가 실행 중이어야 합니다. Postgres 17과 18을 지원하며, `18-alpine`과 같은 이미지 태그도 사용할 수 있습니다. 새 인스턴스는 기본적으로 18 버전을 사용합니다.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres stop app
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

인스턴스는 이름과 주 버전으로 식별됩니다. 중지된 인스턴스를 재개하면 기존 포트, 사용자, 비밀번호, 데이터베이스를 그대로 사용하므로, 생성 시 지정한 플래그는 재개할 때 적용되지 않습니다. 비밀번호를 직접 지정하지 않으면 임의의 비밀번호가 생성됩니다. `.env.local`에는 비밀번호가 포함되어 있으므로 버전 관리 대상에서 제외하십시오.

### 로컬 사용자 정의 함수(UDFs) {#local-udfs}

`local udf`는 `clickhouse/udfs/<name>/`에 있는 [실행 가능한 사용자 정의 함수(Executable UDFs)](/ko/reference/functions/regular-functions/udf#executable-user-defined-functions)를 로컬 서버에 배포합니다. `cloud udf`는 같은 디렉터리를 Cloud에 업로드합니다([Cloud의 UDFs](#cloud-udfs) 참조).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local server start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

`init`을 제외한 모든 명령은 `--server <name>` 옵션을 받습니다(기본값: `default`). `deploy`는 Cloud와 동일한 방식으로 `udf.json`을 검사합니다. 서버가 실행 중이면 함수를 다시 로드한 뒤 함수가 정상적으로 로드되었는지 확인합니다. `native` 런타임은 Linux amd64 또는 arm64 호스트에서만 로컬 배포가 가능합니다. 자세한 내용은 [사용자 정의 함수 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)를 참조하십시오.

## 인증 {#authentication}

Cloud 명령어는 다음 두 가지 인증 정보 유형 중 하나를 사용합니다.

| 인증 정보      | 권한                                                          | 저장 위치                                                 |
| ---------- | ----------------------------------------------------------- | ----------------------------------------------------- |
| 브라우저 OAuth | 사용자 본인의 아이덴티티: 소속된 모든 조직에서 읽기 전용 Cloud 작업 및 읽기 전용 SQL 사용 가능 | `~/.clickhouse/tokens.json`, 전역으로 저장되며 모든 프로젝트에서 공유됨  |
| API Key    | 하나의 조직으로 범위가 제한됨. 읽기 및 쓰기 가능 여부는 키에 부여된 역할에 따라 결정됨          | 저장 시 `.clickhouse/credentials.json`, 해당 프로젝트에 로컬로 저장됨 |

아직 ClickHouse Cloud 계정이 없다면, `clickhousectl cloud auth signup`를 실행하면 브라우저에서 가입 페이지가 열립니다.

### OAuth 로그인 {#oauth-login}

```bash
clickhousectl cloud auth login
```

브라우저가 열리고 OAuth 디바이스 흐름이 진행됩니다. 토큰은 `~/.clickhouse/tokens.json`에 전역으로 저장되며 자동으로 갱신됩니다.

<Note>
  OAuth는 **읽기 전용**입니다. 리소스를 생성하거나 변경하려면 [API Key](#api-key)로 로그인하세요.
</Note>

### API Key {#api-key}

명령어 실행에 필요한 역할을 부여하여 [API Key를 생성](/ko/products/cloud/features/admin-features/api/openapi)한 후 저장하십시오. 대화형 프롬프트로 입력하면 시크릿이 셸 이력에 남지 않습니다:

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

로그인하면 키를 검증하고 해당 키가 속한 아이덴티티를 출력합니다. API가 거부한 키는 저장되지 않으며, 명령은 종료 코드 4로 종료됩니다. API에 연결할 수 없으면 경고와 함께 키가 저장됩니다.

CI 및 기타 자동화 환경에서는 키를 저장하지 말고 시크릿 매니저를 통해 주입하십시오:

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

개발 환경에서는 CLI가 현재 디렉터리에 있는 `.env` 파일에서도 이 변수들을 읽습니다. `.env` 파일은 버전 관리 대상에서 제외하십시오.

### 자격 증명 확인 및 삭제 {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami`는 두 가지 인증 정보 유형 모두에서 작동하며, 자격 증명이 거부되면 종료 코드 4를 반환합니다. `status`는 유효한 자격 증명이 하나도 없어도 종료 코드 0을 반환할 수 있으므로, 액세스 가능 여부를 확인하려면 `whoami`를 사용하십시오. 로그아웃해도 환경 변수가 해제되거나 `.env` 파일이 수정되지는 않습니다.

### 인증 정보 우선순위 {#credential-precedence}

다음 중 먼저 확인되는 소스가 사용됩니다.

1. `--api-key` 및 `--api-secret` 플래그
2. `.clickhouse/credentials.json`
3. 내보낸(export) 환경 변수
4. 현재 디렉터리의 `.env`에 정의된 변수
5. 전역 OAuth 토큰

어떤 `cloud` 명령이든 `--debug`를 지정하면 선택된 인증 정보 소스와 API URL이 stderr로 출력됩니다.

```bash
clickhousectl cloud service list --debug
```

### 조직 선택 {#organizations}

조직 범위의 명령어는 자격 증명으로 접근할 수 있는 조직이 정확히 하나인 경우에만 해당 조직을 자동으로 선택합니다. 그렇지 않으면 `--org-id`를 지정하거나, `--org-name`에 정확한 조직 이름을 지정하십시오.

```bash
clickhousectl cloud org list
clickhousectl cloud service list --org-id <org-id>
clickhousectl cloud service list --org-name "My Org"
```

대부분의 리소스 명령은 위치 인수로 ID를 받거나 정확한 `--name` 값을 받습니다. 권한, 제한된 키, 로그아웃 시 정리 작업에 대한 자세한 내용은 [인증 및 액세스](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md)를 참조하십시오.

## Cloud {#cloud}

Cloud 명령은 [ClickHouse Cloud API](/ko/products/cloud/features/admin-features/api/api-overview)를 호출합니다. 생성 및 UPDATE 요청은 API가 요청을 수락하는 즉시 반환되므로, 리소스가 필요한 상태에 도달할 때까지 `get`을 폴링하십시오.

### 서비스 {#services}

```bash
clickhousectl cloud service create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud service list
clickhousectl cloud service get <service-id>
clickhousectl cloud service start <service-id>
clickhousectl cloud service stop <service-id>
clickhousectl cloud service wake <service-id>             # Wake an idle service
clickhousectl cloud service reset-password <service-id>
clickhousectl cloud service delete <service-id>           # Must be stopped; --force stops it first
```

생성 시 표시되는 초기 비밀번호는 한 번만 반환되므로 반드시 저장하십시오. 생성 명령은 프로비저닝이 완료되기 전에 반환되므로, 상태가 `running`이 될 때까지 `get`을 반복해서 실행하십시오. **`--ip-allow`를 생략하면 모든 IP(`0.0.0.0/0`)가 허용됩니다.** 엔트리는 `IP_OR_CIDR=DESCRIPTION` 형식으로 지정합니다. `--backup-id`를 사용하면 백업(backup)을 새 서비스로 복원할 수 있으며, `--byoc-id`를 사용하면 서비스를 BYOC 인프라에 배치할 수 있습니다.

서비스 업데이트, 확장 및 구성:

```bash
clickhousectl cloud service update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud service profile list --region us-east-1
clickhousectl cloud service scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud service scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud service settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud service upgrade-window set <service-id> --weekday 0 --start-hour 6
```

레플리카당 메모리는 4 GB 단위로 지정하며, 무료 서비스는 최대 120 GB, 유료 서비스는 최대 356 GB까지 설정할 수 있습니다. 레플리카는 최대 50개까지 지원됩니다. 조직 및 웨어하우스(warehouse) 제한에 따라 이 값이 더 낮아질 수 있습니다. 수평 자동 확장을 사용하려면 조직에 해당 기능이 활성화되어 있어야 합니다. `update`는 지정한 플래그만 변경합니다.

그 밖의 서비스 명령 그룹으로는 `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (베타), `snapshot` (베타), `private-endpoint`, `backup-config`, `prometheus`가 있습니다. 자세한 내용은 [Cloud 서비스 생성 및 운영](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md)을 참조하십시오.

### 쿼리 API {#query-api}

`cloud service query`는 로컬 `clickhouse` 바이너리나 서비스 비밀번호 없이 HTTP를 통해 SQL 문(SQL statement) 하나를 실행합니다.

```bash
clickhousectl cloud service query <service-id> --query "SELECT version()"
clickhousectl cloud service query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud service query <service-id>
```

* **OAuth**는 사용자의 아이덴티티로 쿼리를 실행하며, 읽기 전용 SQL 액세스 권한만 가집니다. 서비스에는 아무것도 바인딩되지 않습니다.
* **API Key:** 첫 호출 시 clickhousectl은 사용자의 API Key를 서비스의 Query API 엔드포인트에 추가하며, 엔드포인트가 없으면 `sql_console_admin` 역할로 생성합니다. 기존 역할, 오리진(origin) 및 기타 키 바인딩은 그대로 유지되며, 새 키는 생성되지 않습니다. CLI가 엔드포인트를 변경하면 stderr에 `Binding the authenticated API key to the Query API endpoint for service '<name>'...`를 출력합니다. 이 동작 대신 실패 처리하려면 `--no-auto-enable`을 지정하십시오.

이전 CLI 버전에서 저장한 서비스별 키가 있으면 해당 서비스에서는 여전히 이 키가 우선 적용됩니다. API가 이 키를 거부하면 `cloud service repair-query-key <service-id>`를 실행하여 명시적으로 대체할 수 있습니다.

쿼리 API는 요청당 하나의 SQL 문만 허용합니다. 약 30초가 지나면 SQL이 계속 실행 중이더라도 요청이 시간 초과될 수 있으므로, 쓰기 작업을 재시도하기 전에 결과를 확인하십시오. 여러 SQL 문으로 구성된 스크립트, 대량 적재(bulk loads), 장시간 실행되는 쿼리에는 `clickhouse client`를 사용하십시오. 서비스 IP 허용 목록은 직접 연결에만 적용되며, 프록시를 거치는 쿼리 API 경로는 제한하지 않습니다. 유휴 상태의 서비스에 쿼리를 실행하면 서비스가 자동으로 깨어나지만, 중지된 서비스는 `cloud service start`로 시작해야 합니다.

서비스의 Query API 엔드포인트, 이름이 지정된 SQL 엔드포인트 및 저장된 쿼리(saved queries)를 관리합니다:

```bash
clickhousectl cloud service query-endpoint get <service-id>
clickhousectl cloud service query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create`는 해당 엔드포인트에 연결된 모든 키의 역할을 교체합니다. 자세한 내용은 [SQL 및 쿼리 API 동작](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md)을 참조하십시오.

### Managed Postgres {#postgres-services}

`cloud postgres`는 [ClickHouse Managed Postgres](/ko/products/managed-postgres/overview)를 관리합니다. 이 명령어는 베타 단계이며, GCP는 비공개 프리뷰로 제공됩니다.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

AWS 크기로는 `m6gd.large`, `c6gd.xlarge`, `r6gd.xlarge` 등이 있습니다. GCP에서는 `--provider gcp`와 함께 GCP 리전 및 `c4-standard-lssd-4`와 같은 크기를 지정하십시오.

`create` 실행 시 반환되는 비밀번호와 연결 문자열(Connection String)을 반드시 저장하십시오. 이후 `get` 응답에는 자격 증명이 포함되지 않으며, 새 자격 증명은 `reset-password`로만 발급받을 수 있습니다. `psql`로 연결할 때는 `sslmode=verify-full`과 CA 파일을 사용하십시오.

**create 시 액세스 플래그를 생략하면 Postgres(5432)와 PgBouncer(6432)에 모든 IPv4 및 IPv6 주소의 접근이 허용됩니다.** 규칙마다 `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]`을 하나씩 지정하거나, 규칙을 하나도 두지 않으려면 `--block-public-access`를 지정하십시오. 규칙을 하나라도 지정하면 나열된 규칙만 적용됩니다.

모니터링 및 복구:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query`는 OAuth만 지원하므로, 우선순위가 더 높은 API Key 소스가 활성 상태이면 실패합니다. 모니터링에는 `metrics`, `slow-queries`, `prometheus`를 사용합니다. `restore`는 `--ip-allow` 또는 `--block-public-access`를 지정하지 않으면 원본 서비스의 현재 IPv4 액세스 규칙을 복원된 서비스에 그대로 복사합니다. 복원 및 레플리카 생성 시에는 비밀번호가 반환되지 않습니다. `promote`와 `switchover`는 요청이 수락되는 즉시 반환됩니다. promote 후에는 레플리카가 `isPrimary: true`를 보고할 때까지 `postgres get --json`을 폴링하십시오. 자세한 내용은 [Managed Postgres 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md)를 참조하십시오.

### ClickPipes {#clickpipes}

`cloud clickpipe`는 객체 스토리지, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB, BigQuery에서 데이터를 수집합니다. ClickPipe를 생성하거나 스키마 탐색(schema discovery)을 수행하려면 API Key와 실행 중인 대상 서비스가 필요합니다. 소스마다 전용 `clickpipe create <source>` 하위 명령이 있으며, `--help`를 붙여 실행하면 해당 명령의 플래그를 확인할 수 있습니다.

IAM role을 사용하여 S3에서 파일을 로드합니다. 먼저 스키마(schema)를 탐색한 다음 컬럼을 선택하세요.

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN"
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --column 'event_id:Int64' --column 'event_type:String'
```

CDC를 사용하여 Postgres를 복제합니다. TLS는 기본적으로 검증됩니다. Managed Postgres 소스라면 해당 인증 기관(CA) 인증서를 내보낸 후 다음과 같이 전달하세요:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud service query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping`은 `ReplacingMergeTree` 테이블을 생성하므로, 현재 상태를 조회하려면 `FINAL WHERE _peerdb_is_deleted = 0`을 사용하십시오. Kafka 파이프도 같은 패턴을 따릅니다. 동일한 소스 플래그로 `clickpipe schema-discover kafka`를 실행한 다음, 컬럼을 전달하십시오:

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

BigQuery 파이프는 기본적으로 스냅샷을 실행합니다. CDC를 사용하려면 `--replication-mode cdc`와 `--replication-method`를 지정하고, `--table-mapping-json`에 테이블별 워터마크(watermark) 컬럼 또는 이벤트 함수를 지정하십시오. 동기화 일정은 `--sync-cron` 또는 `--sync-interval-seconds`로 설정합니다. 기존 파이프는 다음 명령으로 관리합니다:

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

CDC 파이프는 `update` 전에 `Paused` 상태여야 합니다. 파이프를 중지하고 `Paused` 상태가 될 때까지 `get`으로 폴링한 다음 업데이트하세요. 서비스가 업데이트 과정에서 파이프를 재개할 수 있으므로, `get`에 여전히 `Paused`로 표시되는 경우에만 `start`를 실행하세요. `--start-paused`는 객체 스토리지, Kafka, Kinesis, Pub/Sub에서 사용할 수 있습니다. 그 밖의 명령 그룹으로는 `cdc-scaling`, `context get`(GCP 워크로드 아이덴티티 준비 상태 및 주체), `reverse-private-endpoint`가 있습니다. 자세한 내용은 [ClickPipes 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) 및 [ClickPipe 구성 참고](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md)를 참조하세요.

### ClickStack {#clickstack}

`cloud clickstack`은 기존 [Managed ClickStack](/ko/clickstack/deployment/managed) 서비스의 소스, 대시보드, 알림, 웹훅, 저장된 검색 및 역할을 관리합니다. 리소스는 JSON 파일로 전달합니다(`--file` 사용, stdin에서 읽으려면 `-` 지정). 읽기 작업은 OAuth 인증을 지원하지만, 쓰기 작업에는 API Key가 필요합니다.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**ClickStack을 업데이트할 때마다 리소스 전체가 대체됩니다.** `get --json`으로 현재 상태를 저장한 후, 변경된 필드만이 아니라 전체 정의를 전송하십시오. 자세한 내용은 [ClickStack 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md)를 참조하십시오.

### Cloud의 사용자 정의 함수(UDFs) {#cloud-udfs}

`cloud udf`는 조직 범위의 실행 가능한 사용자 정의 함수(Executable UDFs)와 그 버전, 그리고 서비스 ATTACH를 관리합니다. `deploy`는 `local udf`로 테스트한 디렉터리를 업로드하고 빌드가 완료될 때까지 대기한 다음, 해당 버전을 ATTACH하고 배포가 완료될 때까지 대기합니다:

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud service query <service-id> --query "SELECT my_udf(1)"
```

각 단계를 직접 실행하려면 `udf create`, `udf version create`, `udf attach`(유휴 상태인 서비스에는 `--wake` 사용), `udf detach`, `udf delete`를 사용하십시오. 이 명령들은 요청이 수락되면 바로 반환되므로 `udf get` 및 `udf attachment get`을 폴링하여 진행 상태를 확인하십시오. 읽기 작업은 OAuth를 지원하지만, 쓰기 작업에는 API Key가 필요합니다. 자세한 내용은 [사용자 정의 함수 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)를 참조하십시오.

### 조직 및 액세스 {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

`cloud org` 하위 명령은 위치 기반 ID가 아니라 항상 `--org-id`로 대상을 지정합니다. `org usage`로 조회할 수 있는 기간은 최대 31일입니다. `org`에는 `quota`, `balance`, `notification-types`, `role`(사용자 정의 조직 역할), `byoc`(BYOC 인프라) 하위 명령도 있습니다. 알림 기능은 현재 베타입니다.

구성원, 초대 및 API 키 관리:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

**`key create`에서 `--ip-allow`를 생략하면 모든 네트워크 액세스가 거부됩니다.** 이는 서비스 생성 시의 동작과 다릅니다. 시크릿은 한 번만 표시됩니다. `key list`는 `--all`을 지정하지 않으면 한 페이지만 반환합니다. `key update`에서 생략한 플래그는 기존 설정이 그대로 유지되며, `--clear-expiry`, `--clear-roles`, `--clear-ip-allow`를 지정하면 해당 설정이 제거됩니다.

### 백업 {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud service create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud service backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
clickhousectl cloud backup bucket get <service-id>
```

복원 시에는 항상 새 서비스가 생성됩니다. `cloud backup bucket`(get, create, update, delete)은 provider별 JSON 파일을 기반으로 사용자 소유 백업 버킷(bring-your-own backup bucket)을 구성합니다. 자세한 내용은 [클라우드 서비스 가이드](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore)의 백업 섹션을 참조하십시오.

## JSON 출력 {#json-output}

로컬, Cloud, `skills`, `update`, `telemetry` 명령어를 비롯하여 구조화된 데이터를 반환하는 명령어는 모두 `--json` 옵션을 지원합니다.

```bash
clickhousectl cloud service list --json
clickhousectl cloud key list --all --json
clickhousectl local server list --json
```

CLI는 코딩 에이전트(Claude Code, Cursor, Codex, Gemini CLI, Goose, Devin 또는 `AI_AGENT`를 설정하는 모든 도구)를 감지하면 자동으로 JSON을 선택합니다. 단, SQL 및 네이티브 클라이언트는 자체 포맷을 그대로 사용합니다. `cloud service query`는 JSON 모드에서 `JSONEachRow`를 반환하며, `local client`의 출력은 항상 네이티브 포맷입니다. 쿼리 출력을 파싱하는 스크립트에서는 `--format`을 명시적으로 지정해야 합니다.

JSON 모드에서 런타임 오류는 변경되지 않는 `code`와 `message`를 포함한 객체 형태로 stderr에 출력됩니다:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

메시지가 아닌 `error.code`를 기준으로 분기하십시오. 사용법 오류는 텍스트 형식 그대로 출력되며 종료 코드 2를 반환합니다. 출력 형태와 오류 코드는 [자동화 및 출력 계약](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md)을 참고하십시오.

## 종료 코드 {#exit-codes}

| 코드  | 의미                                            |
| --- | --------------------------------------------- |
| `0` | 성공. 비동기 Cloud 작업은 요청이 완료된 것이 아니라 접수되었음을 의미합니다 |
| `1` | 오류                                            |
| `2` | 사용법 오류(유효하지 않은 플래그 값 포함)                      |
| `3` | 취소됨                                           |
| `4` | 인증이 필요하거나 거부됨(OAuth로 시도한 쓰기 작업 포함)            |

`local client`, `local postgres client` 등 네이티브 클라이언트로 제어를 넘기는 명령은 해당 클라이언트의 종료 상태를 그대로 반환합니다.

## 에이전트 스킬 {#skills}

[공식 ClickHouse agent skills](https://github.com/ClickHouse/agent-skills)를 코딩 에이전트에 설치하십시오:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

Skills는 기본적으로 현재 프로젝트에 설치되며, `--global`을 지정하면 홈 디렉터리에 설치됩니다. 공유 `.agents/skills/` 디렉터리는 항상 포함됩니다. 터미널이 없는 환경에서는 `--agent`, `--all`, `--detected-only` 중 하나를 반드시 지정해야 합니다. 지원되는 에이전트 이름은 `clickhousectl skills --help`를 실행하여 확인하세요.

## 자체 업데이트 {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

CLI는 백그라운드에서 최대 24시간에 한 번씩 업데이트를 확인하며, 새 버전이 있으면 알림을 표시합니다.

## 텔레메트리 {#telemetry}

`clickhousectl`은 개발 방향을 정하는 데 참고하기 위해 익명의 사용량 데이터를 수집합니다. 처음 실행할 때는 안내 메시지만 표시하고 아무것도 전송하지 않으며, 비활성화하지 않으면 그다음 실행부터 수집이 시작됩니다.

각 이벤트에는 다음 정보가 포함됩니다.

* 명령 경로와 명시적으로 전달된 플래그 및 인수의 **이름**(값은 절대 포함되지 않음)
* 실행 결과 및 종료 코드
* 명령을 잘못 입력한 경우 CLI가 제안한 명령 또는 플래그 이름(실제로 입력한 내용은 절대 포함되지 않음)
* 런타임 실패 시 범위가 제한된 범주 정보: 실패 스테이지 및 유형, 허용 목록에 포함된 HTTP 상태, 재시도·프로비저닝 상태·소요 시간 범주
* CLI 버전, OS 및 아키텍처, CI 환경에서의 실행 여부, 감지된 코딩 에이전트

인수 값, SQL, 자격 증명, 리소스 식별자, `--` 뒤의 인수, 오류 메시지는 절대 기록되지 않습니다. 설치 ID나 기기 ID도 사용하지 않습니다.

수집을 거부하려면 다음과 같이 하십시오.

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

`CHCTL_TELEMETRY_DEBUG=1`을 설정하면 데이터를 전송하지 않고 payload를 stderr에 출력합니다. 자세한 내용은 [텔레메트리 세부 정보](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md)를 참조하십시오.
