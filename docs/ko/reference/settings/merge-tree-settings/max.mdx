## max_avg_part_size_for_too_many_parts {#max_avg_part_size_for_too_many_parts}

<SettingsInfoBlock type="UInt64" default_value="1073741824" />

&#39;parts&#95;to&#95;delay&#95;insert&#39; 및
&#39;parts&#95;to&#95;throw&#95;insert&#39;에 따른 &#39;too many parts&#39; 검사는 해당
파티션의 평균 파트 크기가 지정된 임계값보다 크지 않은 경우에만 활성화됩니다. 평균
파트 크기가 지정된 임계값보다 크면 INSERT는 지연되거나 거부되지
않습니다. 따라서 파트가 더 큰 파트로 성공적으로 머지되면 단일
서버의 단일 테이블에 수백 테라바이트의 데이터를 저장할 수 있습니다. 이는
비활성 파트 또는 전체 파트의 임계값에는 영향을 주지 않습니다.

## max_concurrent_queries {#max_concurrent_queries}

<SettingsInfoBlock type="UInt64" default_value="0" />

MergeTree 테이블과 관련된 쿼리를 동시에 실행할 수 있는 최대 개수입니다.
쿼리는 다른 `max_concurrent_queries` 설정의 적용도 받습니다.

Possible values:

* 양의 정수.
* `0` — 제한 없음.

기본값: `0` (제한 없음).

**예시**

```xml
<max_concurrent_queries>50</max_concurrent_queries>
```

## max_file_name_length {#max_file_name_length}

<SettingsInfoBlock type="UInt64" default_value="127" />

해싱하지 않고 파일 이름을 그대로 유지할 수 있는 최대 길이입니다.
이 설정은 `replace_long_file_name_to_hash` 설정이 활성화된 경우에만 적용됩니다.
이 설정값에는 파일 확장자의 길이가 포함되지 않습니다. 따라서
파일 시스템 오류를 방지할 수 있도록 여유를 두고 최대 파일 이름 길이(보통 255
바이트)보다 작게 설정하는 것이 좋습니다.

## max_table_size_bytes_compressed {#max_table_size_bytes_compressed}

<SettingsInfoBlock type="UInt64" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "테이블의 모든 활성 및 비활성 데이터 파트에서 압축된 총 바이트 수를 제한하는 새로운 설정입니다."}]}]} />

테이블의 모든 활성 및 비활성 데이터 파트에서 압축된 총 바이트 수(디스크상 크기)가 이 값을 초과하면 `Table size limit exceeded` 예외가 발생하며 `INSERT`가 중단됩니다. 이 설정은 디스크 사용량을 제한하기 위한 것이므로 비활성 파트도 계산에 포함됩니다. 비활성 파트는 백그라운드에서 제거되므로(`old_parts_lifetime` 설정 참고) 시간이 지나면 관찰되는 크기가 줄어들 수 있습니다. 제한은 `INSERT` 시작 시와 백그라운드 머지 및 뮤테이션 결과를 포함한 새 데이터 파트가 작업 집합에 커밋될 때 확인됩니다. materialized view에서 수행하는 삽입도 확인됩니다. 복제된 fetch에서는 제한을 확인하지 않으므로 여러 레플리카에 병렬로 삽입할 경우 제한을 초과할 수 있는 race condition이 발생할 수 있습니다. 빈 데이터 파트의 커밋은 항상 허용되므로, 예를 들어 `TRUNCATE` 또는 `ALTER TABLE ... DROP
PARTITION`을 사용해 제한을 초과한 테이블에서 데이터를 제거할 수 있습니다.

가능한 값:

* 양의 정수.
* 0 — 제한 없음.

다중 테넌트, 임시 및 데모 서비스에 유용합니다.

## max_table_size_rows {#max_table_size_rows}

<SettingsInfoBlock type="UInt64" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "테이블의 활성 데이터 파트에 포함된 총 행 수를 제한하는 새로운 설정."}]}]} />

테이블의 활성 데이터 파트에 포함된 총 행 수가 이 값을 초과하면 `INSERT`가
`Table size limit exceeded` 예외와 함께 중단됩니다. 이 제한은 `INSERT` 시작 시점과
새로운 데이터 파트가 작업 집합에 커밋될 때 검사되며, 백그라운드 머지 및
뮤테이션의 결과도 검사 대상에 포함됩니다(따라서 테이블 크기를 제한 이상으로 늘리는 뮤테이션은
완료되지 못하고 재시도됩니다). materialized view가 수행하는 삽입도 검사 대상입니다.
복제된 fetch에는 이 제한이 적용되지 않으므로, 여러 레플리카에 병렬로 삽입할 때
제한을 초과하게 되는 race condition이 발생할 수 있습니다. 빈 데이터 파트의 커밋은
항상 허용되므로, 제한을 초과한 테이블에서도 `TRUNCATE`나
`ALTER TABLE ... DROP PARTITION` 등으로 데이터를 삭제할 수 있습니다.

가능한 값:

* 양의 정수.
* 0 — 무제한.

다중 테넌트, 임시, 데모 서비스에 유용합니다.
