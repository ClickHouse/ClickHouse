## s3_upload_checksum_algorithm {#s3_upload_checksum_algorithm}

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": ""},{"label": "S3 업로드에 사용할 checksum 알고리즘을 선택하는 새로운 설정."}]}]} />

ClickHouse가 `S3`로 데이터를 업로드할 때 사용하는 checksum 알고리즘입니다. `CRC32`와 `SHA256`은 유연한(flexible) `x-amz-checksum-*` header로 전송되고, `MD5`는 `Content-MD5` header로 전송됩니다.

기본값은 비어 있으며, 이 경우 ClickHouse는 AWS SDK가 `Content-MD5`를 계산하도록 맡깁니다. FIPS 모드에서는 `MD5`를 사용할 수 없어 SDK가 이를 조용히 생략하며, 그 결과 업로드에 checksum이 전혀 포함되지 않습니다. 이런 경우에는 `CRC32` 또는 `SHA256`을 지정해 유연한 checksum을 붙이십시오. 이 설정이 적용되는 곳에서는 명시적인 `MD5`가 거부됩니다.

`S3Express`가 아닌 버킷에서는 `s3_disable_checksum`이 이 설정을 무효화합니다. 이 설정은 `S3` 클라이언트가 생성되는 시점에 적용되므로, `s3` 테이블 함수나 `BACKUP ... TO S3`처럼 쿼리 범위에서 사용되는 경우에 반영됩니다. 반면 이후에 쿼리 단위로 실행하는 `SET`은 `S3` 디스크처럼 이미 생성되어 장기간 유지되는 클라이언트를 다시 구성하지 않습니다.

`S3Express` 버킷은 유연한 checksum을 요구하며 `Content-MD5`를 허용하지 않습니다. 명시적인 `CRC32` 또는 `SHA256`은 그대로 사용되고, 값이 비어 있으면 `CRC32`가 사용되며, 명시적인 `MD5`는 거부됩니다.

`GCS` endpoint(`storage.googleapis.com`)는 이 설정을 완전히 무시하고 SDK의 `Content-MD5` 동작을 그대로 유지합니다. `GCS`가 AWS `x-amz-checksum-*` header를 포함한 `SigV4` 서명 요청을 거부하기 때문입니다.

서버 측 복사는 이 설정을 무시합니다.

## s3_upload_part_size_multiply_factor {#s3_upload_part_size_multiply_factor}

<SettingsInfoBlock type="UInt64" default_value="2" />

단일 쓰기로 S3에 업로드된 파트 수가 `s3_multiply_parts_count_threshold`개에 도달할 때마다 `s3_min_upload_part_size`에 이 계수를 곱합니다.

## s3_upload_part_size_multiply_parts_count_threshold {#s3_upload_part_size_multiply_parts_count_threshold}

<SettingsInfoBlock type="UInt64" default_value="500" />

이 개수의 파트가 S3에 업로드될 때마다 s3&#95;min&#95;upload&#95;part&#95;size에 s3&#95;upload&#95;part&#95;size&#95;multiply&#95;factor를 곱합니다.
