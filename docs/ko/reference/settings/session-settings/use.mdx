## use_columns_cache {#use_columns_cache}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "0"},{"label": "MergeTree 테이블에서 컬럼 캐시를 활성화하는 새 실험적 설정이며, 기본적으로 비활성화되어 있습니다."}]}]} />

컬럼 캐시 사용 여부를 지정합니다. 0 또는 1을 사용할 수 있으며, 기본값은 0(비활성화)입니다.
컬럼 캐시는 `MergeTree` 테이블에서 역직렬화된 컬럼을 저장하므로, 자주 사용되는 데이터를 반복해서 압축 해제하고 역직렬화하는 작업이 사라집니다. 따라서 동일한 데이터에 반복적으로 실행되는 쿼리의 지연 시간을 크게 줄일 수 있습니다. 캐시는 테이블 UUID, 데이터 파트 이름, 컬럼명, 그리고 약 65536개 행으로 구성된 연속 그래뉼의 스트라이프(stripe)를 키로 사용합니다.

엔트리는 테이블 UUID를 키로 사용하므로, 캐시는 `Atomic`, `Replicated`, `Shared`(ClickHouse Cloud의 기본 데이터베이스 엔진)처럼 UUID를 할당하는 데이터베이스의 테이블에서만 동작합니다. 레거시 `Ordinary` 데이터베이스의 `MergeTree` 테이블은 UUID가 nil이므로 별도의 알림 없이 이 설정을 무시합니다.

캐시는 프로젝션의 파트를 포함하여 wide 파트와 compact 파트 모두에 적용됩니다.

하나의 엔트리에는 한 스트라이프 내의 연속된 그래뉼 범위가 저장됩니다. 그래뉼은 첫 번째 행부터 마지막 행까지 모두 읽힌 후에만 캐시에 저장되고, 읽기는 그래뉼 단위로 캐시에서 처리되며, 서로 다른 읽기가 기록한 범위는 하나로 머지됩니다. 따라서 파트를 서로 다른 마크 범위로 나누어 읽더라도 엔트리를 공유할 수 있습니다.

캐시는 로컬 파일 시스템(`file` 테이블 함수 및 `File` 테이블 엔진)이나 객체 스토리지(`s3`, `azureBlobStorage` 및 해당 테이블 엔진)에서 읽는 `Parquet` 파일과 데이터 레이크 테이블에도 적용됩니다. 이 경우 하나의 엔트리에는 한 row group에 속한 컬럼의 65536개 행 단위 청크가 저장되며(row group의 마지막 청크는 이보다 짧을 수 있음), 파일 경로, 파일 버전(객체의 ETag 또는 로컬 파일의 수정 시간, inode, 크기), 파일의 컬럼, 그리고 해당 컬럼을 읽을 때 사용하는 유형이 키로 사용됩니다. 캐시를 사용하는 row group은 블록 크기 설정과 관계없이 이 청크 단위로 읽힙니다. 청크는 필터가 적용되기 전에 모든 행을 읽은 경우에 한해, 디코딩되는 즉시 복사 없이 캐시에 기록됩니다. `PREWHERE`를 사용하면 필터에 사용되는 컬럼은 이 조건을 충족하지만, 나머지 컬럼은 필터를 통과한 행만 읽습니다. row group의 컬럼은 모든 청크가 캐시에 있을 때만 캐시에서 제공되므로, 청크를 모두 기록할 수 없는 컬럼은 이미 기록된 청크도 캐시에서 다시 제거됩니다. 로컬 파일은 버전만으로 내용을 식별할 수 있도록, 몇 초 동안 수정되지 않은 경우에만 캐시됩니다.

## use_concurrency_control_for_max_threads {#use_concurrency_control_for_max_threads}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "1"},{"label": "동시성 제어(concurrency control)에서 공정하게 배분된 CPU 슬롯 수를 기준으로 쿼리의 병렬 처리 수준을 결정하는 새로운 설정"}]}]} />

쿼리의 병렬 처리 수준(쿼리 계획 수립 시 사용되는 스트림 및 스레드 수)을 CPU 코어 수 대신 서버 동시성 제어(concurrency control)에서 공정하게 배분된 CPU 슬롯 수를 기준으로 결정합니다. 공정 배분량은 슬롯 한도(`concurrent_threads_soft_limit_num` 및 `concurrent_threads_soft_limit_ratio_to_cores` 전역 서버 설정 참조)를 현재 실행 중인 파이프라인과 새 쿼리에 균등하게 나눈 값입니다.

이 방식에서는 여러 쿼리가 동시에 실행될 때 각 쿼리가 더 적은 수의 스트림으로 계획됩니다. 따라서 메모리 사용량이 줄고, 스레드별 부분 결과(예: 집계 상태(aggregation states))를 머지하는 데 드는 CPU도 줄어들어 전체 처리량이 증가합니다. 서버가 유휴 상태일 때 계획된 쿼리는 기존과 마찬가지로 모든 CPU 코어를 사용합니다.

공정 배분량은 쿼리 계획을 수립할 때 쿼리당 한 번만 산정합니다. 따라서 쿼리의 모든 부분(서브쿼리, 집합(set), 조인된 테이블)이 동일한 수의 스트림으로 계획됩니다.

이 설정은 `max_threads`가 `auto`(명시적으로 설정되지 않음)이고 `use_concurrency_control`이 활성화된 경우에만 적용됩니다.

## use_constant_folding_in_index_analysis {#use_constant_folding_in_index_analysis}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.7"},{"label": "0"},{"label": "MergeTree 인덱스 분석 중 파트별 필터 프레디케이트에 파티션 수준 상수 폴딩을 적용하여, 분기가 파티션 값에 따라 달라지는 필터의 프루닝을 개선하는 새로운 설정입니다."}]}]} />

파트별 프라이머리 키와 스킵 인덱스를 분석할 때 파티션 수준 상수를 필터 프레디케이트에 대입합니다.

파티션 키가 필터에서 프라이머리 키 또는 스킵 인덱스 컬럼과 함께 사용되면, 인덱스 분석 시 각 파트 내에서 파티션 값을 개별적으로 폴딩할 수 있습니다. 이는 분기가 서로 다른 파티션을 대상으로 하는 논리합 필터에서 특히 유용합니다. 예를 들어, `PARTITION BY a`와 `ORDER BY b`가 있는 경우:

```sql
SELECT * FROM t WHERE (a = 1 AND b >= 1) OR (a = 2 AND b > 10) OR (a = 3 AND b > 10)
```

파티션 `a = 1`의 파트에서는 조건이 `b >= 1`로 축약되고, 파티션 `a = 2` 및 `a = 3`에서는 `b > 10`으로 축약되므로, 각 파트는 실제로 적용되는 프레디케이트를 기준으로 분석됩니다.

가능한 값:

* 0 — 비활성화됨.
* 1 — 활성화됨.
