## external_storage_push_down_limit {#external_storage_push_down_limit}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "1"},{"label": "안전한 경우 쿼리의 `LIMIT`을 외부 데이터베이스로 전송되는 쿼리에 푸시다운하는 새로운 설정입니다. previous_value=false이므로 `compatibility`를 26.10 이전 버전으로 설정하면 기존 동작(푸시다운 없음)이 복원됩니다."}]}]} />

쿼리의 `LIMIT` 절을 외부 데이터베이스(MySQL, PostgreSQL, SQLite 등)로 전송되는 쿼리에 푸시다운할 수 있도록 허용합니다.

범용 ODBC/JDBC 브리지는 원격 `LIMIT` 구문을 노출하지 않으며, 지원되는 데이터베이스 중 일부는 `LIMIT` 절을 아예 허용하지 않으므로 이들 브리지에서는 푸시다운이 수행되지 않습니다.

`LIMIT`은 안전성이 보장되는 경우, 즉 논리적으로 `LIMIT`보다 먼저 적용되는 모든 절이 변경 없이 외부 쿼리에 그대로 복사되는 경우에만 푸시다운됩니다. 구체적으로, 쿼리는 단일 테이블에 대한 단순한 `SELECT`여야 하며 다음 조건을 충족해야 합니다.

* `JOIN`, `ARRAY JOIN`, `SAMPLE`, `FINAL`이 없어야 합니다(이들이 있으면 행이 로컬에서 삭제되거나 변환될 수 있으므로 사전 제한이 바람직하지 않습니다).
* `WHERE` 절이 있다면 완전히 호환되어 재작성된 쿼리에 변경 없이 복사되어야 합니다(그렇지 않으면 원격 `LIMIT` 이후에 수행되는 필터링으로 인해 일부 행이 누락됩니다).
* 데이터 재정렬, 집계 또는 필터링으로 인해 원격 사전 제한 로직이 깨질 수 있는 다른 절이나 수정자(`DISTINCT`, `GROUP BY`, `ORDER BY`, `LIMIT BY`, `WITH TIES` 등)가 없어야 합니다.
* `OFFSET`은 허용됩니다. `OFFSET`은 로컬에서 적용되므로 건너뛰는 행도 함께 읽어야 하며, 외부 데이터베이스로 전송되는 제한 값은 `offset + length`입니다.
* `SELECT` 목록은 소스 행 하나를 결과 행 하나에 대응시켜야 합니다. 즉, 집계 함수, 윈도우 함수 또는 `arrayJoin`(`unnest`라고도 표기)을 포함하지 않아야 합니다(이들은 외부 테이블에서 읽은 모든 행을 대상으로 로컬에서 평가됩니다).
* 외부 테이블에서 읽은 행에 대해 로컬에서 추가로 적용되는 필터(행 정책(row policy) 또는 `additional_table_filters` 등)가 없어야 합니다(이러한 필터는 `LIMIT`보다 먼저 실행되므로, 원격에서 미리 제한하면 필터를 통과했을 행까지 버려질 수 있습니다).

이를 통해 외부 데이터베이스에서 읽고 전송하는 데이터의 양을 줄일 수 있습니다. 호환성 문제가 발생하면 이 설정을 비활성화하여 이전 동작으로 되돌리십시오.
