## min_compress_block_size {#min_compress_block_size}

<SettingsInfoBlock type="UInt64" default_value="65536" />

[MergeTree](/ko/reference/engines/table-engines/mergetree-family/mergetree) 테이블에 적용됩니다. 쿼리 처리 시 지연 시간을 줄이기 위해, 크기가 `min_compress_block_size` 이상이면 다음 마크를 기록할 때 블록을 압축합니다. 기본값은 65,536입니다.

압축되지 않은 데이터가 `max_compress_block_size`보다 작은 경우, 실제 블록 크기는 이 값보다 작아지지 않으며 한 마크에 해당하는 데이터 양보다도 작아지지 않습니다.

예시를 살펴보겠습니다. 테이블 생성 시 `index_granularity`를 8192로 설정했다고 가정합니다.

UInt32 유형의 컬럼(값당 4바이트)을 기록한다고 가정해 보겠습니다. 8192개 행을 기록하면 총 데이터 크기는 32KB가 됩니다. min&#95;compress&#95;block&#95;size = 65,536이므로 압축 블록은 마크 2개마다 하나씩 생성됩니다.

String 유형의 URL 컬럼(값당 평균 크기 60바이트)을 기록한다고 가정해 보겠습니다. 8192개 행을 기록하면 평균적으로 500KB에 약간 못 미치는 데이터가 됩니다. 이는 65,536보다 크므로 압축 블록은 각 마크마다 하나씩 생성됩니다. 이 경우 디스크에서 단일 마크 범위의 데이터를 읽을 때는 추가 데이터가 압축 해제되지 않습니다.

<Note>
  이 설정은 전문가 수준의 설정이므로 ClickHouse를 막 사용하기 시작한 경우에는 변경하지 않는 것이 좋습니다.
</Note>

## min_marks_per_part_to_load_statistics {#min_marks_per_part_to_load_statistics}

<SettingsInfoBlock type="UInt64" default_value="64" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "64"},{"label": "프라이머리 키 분석 후 읽을 양이 적은 경우 통계 로딩을 건너뛰는 새로운 설정입니다."}]}]} />

파트 프루닝과 `PREWHERE` 조건 순서 결정에 사용할 컬럼 통계(Column Statistics)를 로드하기 위해, 프라이머리 키 분석 후 남아 있어야 하는 읽을 마크의 최소 개수입니다. 이 값은 통계가 아직 메모리에 없는 데이터 파트(data part)당 기준으로 적용됩니다.

통계를 이용해 `min`, `max`, `count`를 계산하는 기능(`use_statistics_for_min_max_aggregation` 참조)은 읽기 자체를 대체하므로 이 설정의 영향을 받지 않습니다.

가능한 값:

* 0 — 읽기 크기와 관계없이 통계를 로드합니다.
* 양의 정수 — 데이터 파트당 마크 수입니다.

## min_outstreams_per_resize_after_split {#min_outstreams_per_resize_after_split}

<SettingsInfoBlock type="UInt64" default_value="24" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.6"},{"label": "24"},{"label": "새 설정입니다."}]}]} />

파이프라인 생성 중 분할 작업이 수행된 후 `Resize` 또는 `StrictResize` 프로세서의 최소 출력 스트림 수를 지정합니다. 결과 스트림 수가 이 값보다 적으면 분할 작업은 수행되지 않습니다.

### Resize Node란 무엇입니까 {#what-is-a-resize-node}

`Resize` 노드는 쿼리 파이프라인에서 파이프라인을 통해 흐르는 데이터 스트림 수를 조정하는 프로세서입니다. 여러 스레드나 프로세서에 작업 부하를 고르게 분산하기 위해 스트림 수를 늘리거나 줄일 수 있습니다. 예를 들어, 쿼리에 더 높은 병렬성이 필요하면 `Resize` 노드는 단일 스트림을 여러 스트림으로 분할할 수 있습니다. 반대로 여러 스트림을 더 적은 수의 스트림으로 머지하여 데이터 처리를 통합할 수도 있습니다.

`Resize` 노드는 데이터 블록의 구조를 유지하면서 데이터가 각 스트림에 고르게 분산되도록 합니다. 이는 리소스 활용도를 최적화하고 쿼리 성능을 향상하는 데 도움이 됩니다.

### Resize 노드를 분할해야 하는 이유 {#why-the-resize-node-needs-to-be-split}

파이프라인 실행 중에는 중앙 허브 역할을 하는 `Resize` 노드의 ExecutingGraph::Node::status&#95;mutex에서 경합이 심하게 발생하며, 특히 코어 수가 많은 환경에서 더욱 두드러집니다. 이러한 경합은 다음과 같은 문제를 초래합니다.

1. ExecutingGraph::updateNode의 지연 시간이 증가하여 쿼리 성능에 직접적인 영향을 줍니다.
2. 스핀 잠금 경합(native&#95;queued&#95;spin&#95;lock&#95;slowpath)으로 인해 과도한 CPU 사이클이 낭비되어 효율이 저하됩니다.
3. CPU 활용률이 낮아져 병렬성과 처리량이 제한됩니다.

### Resize 노드가 분할되는 방식 {#how-the-resize-node-gets-split}

1. 분할이 가능한지 확인하기 위해 출력 스트림 수를 검사합니다. 즉, 각 분할 프로세서의 출력 스트림 수가 `min_outstreams_per_resize_after_split` 임계값 이상이어야 합니다.
2. `Resize` 노드는 더 작은 `Resize` 노드들로 나뉘며, 각 노드는 동일한 수의 포트를 갖고 입력 및 출력 스트림의 부분 집합을 처리합니다.
3. 각 그룹이 독립적으로 처리되므로 잠금 경합이 줄어듭니다.

### 임의의 입력/출력을 갖는 Resize 노드 분할 {#splitting-resize-node-with-arbitrary-inputsoutputs}

경우에 따라 입력/출력 수가 분할된 `Resize` 노드 수로 나누어떨어지지 않으면, 일부 입력은 `NullSource`에 연결되고 일부 출력은 `NullSink`에 연결됩니다. 이렇게 하면 전체 데이터 흐름에 영향을 주지 않고 분할할 수 있습니다.

### 설정의 목적 {#purpose-of-the-setting}

`min_outstreams_per_resize_after_split` 설정은 `Resize` 노드 분할이 실질적인 의미를 갖도록 하고, 너무 적은 수의 스트림이 생성되어 병렬 처리가 비효율적으로 이루어지는 상황을 방지합니다. 출력 스트림의 최소 개수를 강제함으로써 이 설정은 병렬성과 오버헤드 간의 균형을 유지하는 데 도움이 되며, 스트림 분할 및 병합이 포함된 시나리오에서 쿼리 실행을 최적화합니다.

### 설정 비활성화 {#disabling-the-setting}

`Resize` 노드의 split을 비활성화하려면 이 설정을 0으로 설정합니다. 그러면 파이프라인 생성 중 `Resize` 노드가 분할되지 않아 더 작은 노드로 나뉘지 않고 원래 구조를 유지합니다.

오른쪽 행 수 추정치가 있는 해시 조인은 정확한 키를 사용하는 해시 테이블이 CPU의 L2 캐시보다 대략 클 때, 또는 이 설정이 0일 때에만 `String` 키를 패킹합니다(`enable_packed_string_keys_in_hash_join` 참조). 테이블 크기는 오른쪽 행 수에 행 하나의 바이트 수를 곱한 값입니다. 행 하나의 크기는 32바이트 셀에 키의 평균 길이를 더한 값이며, 길이를 알 수 없으면 0을 더합니다. 규모가 작은 조인은 키를 패킹해도 얻는 이점이 적으며, 오히려 느려질 수 있습니다.

15바이트를 초과하는 패킹된 키는 왼쪽의 모든 행에 대해 해시됩니다. 일치 항목이 있는 행을 주로 통과시키는 런타임 필터를 사용하는 조인(`enable_join_runtime_filters` 참조)은 일치하는 행만 해시하므로 최솟값이 필요하지 않습니다. 이러한 필터가 없으면 이 설정이 오른쪽 행의 최소 개수가 됩니다. 이 설정은 키의 평균 길이가 15바이트를 초과할 때와 길이를 알 수 없을 때 적용됩니다. 길이를 알 수 없으면 긴 키로 간주하기 때문입니다. 길이는 키의 `basic` 컬럼 통계(Column Statistics)로 알 수 있습니다. `MergeTree` 테이블은 기본적으로 이 통계를 수집합니다(`auto_statistics_types` 참조).

키가 `Memory` 테이블의 컬럼이거나, 서브쿼리의 집계 함수 결과이거나, `concat(k, 'x')` 또는 `hex(k)`처럼 `ON` 안의 표현식 결과이면 통계가 없습니다. `OR`를 사용하는 조인은 통계를 사용하지 않습니다. 컬럼을 그대로 전달하기만 하거나 해당 컬럼으로 그룹화하는 서브쿼리는 통계를 유지합니다.

`SEMI` 및 `ANTI`를 제외한 `LEFT` 조인과 `FULL` 조인은 왼쪽의 모든 행을 유지하므로 런타임 필터가 적용되지 않습니다. `LEFT ANTI` 조인의 필터는 일치 항목이 없는 행을 통과시키므로 여기에 해당하지 않습니다.

`collect_hash_table_stats_during_joins`가 활성화되어 있으면 행 수는 동일한 조인을 이전에 실행했을 때의 오른쪽 행 수입니다. 그렇지 않으면 쿼리 최적화 도구(Query Optimizer)의 추정치를 사용하며, 이 추정치는 `parallel_hash_join_threshold`에서도 사용됩니다. 최적화기 추정치가 없으면 이 서버가 오른쪽 테이블(right table)을 직접 읽을 때의 추정치를 사용합니다. 둘 다 없는 조인은 쿼리를 계획한 서버가 오른쪽 행 수를 이 최솟값보다 작게 추정하지 않는 한 키를 패킹합니다. 분산 쿼리(Distributed Query)의 각 서버는 자체 추정치, 통계, 캐시 크기를 기준으로 결정합니다.

0이면 모든 조인의 키를 패킹합니다.
