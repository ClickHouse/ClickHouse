## iceberg_insert_commit_retry_initial_backoff_ms {#iceberg_insert_commit_retry_initial_backoff_ms}

<SettingsInfoBlock type="UInt64" default_value="10" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "10"},{"label": "새 설정입니다. 동시 커밋과의 경쟁에서 실패한 Iceberg `INSERT` 커밋을 즉시 재시도하는 대신 지수적으로 증가하는 범위에서 무작위로 정한 시간만큼 지연한 후 재시도합니다."}]}]} />

동시 커밋과의 경쟁에서 커밋에 실패한 Iceberg 테이블(Iceberg table)의 `INSERT`를 처음 재시도하기 전까지 대기하는 시간의 상한입니다.
상한은 재시도할 때마다 2배로 증가하며, 최대 `iceberg_insert_commit_retry_max_backoff_ms`까지 증가합니다. 각 지연 시간은
0부터 상한 사이에서 무작위로 선택되므로, 동일한 경쟁 상태에서 실패한 writer들이 동시에 재시도하여 다시 충돌하는 것을 방지합니다.
최신 메타데이터(metadata)를 조회하기 전에 지연이 적용되므로, 동시 writer가 많을 때 메타데이터
디렉터리의 목록을 조회하는 빈도도 제한합니다. `0`이면 지연 없이 재시도합니다.

삽입 작업 시 Iceberg Parquet 데이터 파일의 최대 바이트 수입니다.

기본값은 Iceberg 테이블 속성 `write.target-file-size-bytes`의 문서화된 기본값(512 MiB)을 따릅니다.
https://iceberg.apache.org/docs/1.5.2/configuration/ 을 참조하십시오. 이 제한은 지금까지 기록된 파일의 크기,
즉 압축된 크기와 비교됩니다. 따라서 아직 완료되지 않은 Parquet 행 그룹(row groups)이나 인코딩 중인 행 그룹처럼 writer가 아직 버퍼에 보관하고 있는
데이터만큼 파일 크기가 이 제한을 초과할 수 있습니다. 또한 `iceberg_insert_max_rows_in_data_file`은 파일 크기와는
별개로 파일을 제한합니다.

완료될 때까지 업로드 버퍼를 유지하므로, 값을 높이면 메모리 사용량이 늘어나는 대신 업로드 지연 시간의 영향을 더 많이 줄일 수 있습니다. `0`으로 설정하면 각 데이터 파일의 업로드가 완료될 때까지 기다린 후
다음 파일을 씁니다.

## iceberg_insert_single_manifest_for_all_partitions {#iceberg_insert_single_manifest_for_all_partitions}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "새 설정입니다."}]}]} />

파티션으로 구분된 Iceberg 테이블(Iceberg table)에 `INSERT`를 수행하면, 파티션마다 manifest 파일을 하나씩 쓰는 대신 Spark
및 PyIceberg처럼 해당 `INSERT`가 대상으로 하는 모든 파티션에 대해 manifest 파일을 하나만 씁니다. 이 동작은 삽입 스트림 단위로 적용됩니다. 각 스트림은 자체 manifest를 포함한 자체
스냅샷을 커밋하므로, `INSERT`가 정확히 하나의 manifest만 쓰는 것은 `max_insert_threads = 1`인 경우뿐입니다.
또한 이 설정을 사용하면 `OPTIMIZE TABLE ... MANIFEST`가 서로 다른 파티션의 manifest도 하나로 머지합니다.
`ALTER TABLE ... DROP PARTITION`으로는 다른 파티션과 manifest를 공유하는 파티션을 삭제할 수 없습니다.
