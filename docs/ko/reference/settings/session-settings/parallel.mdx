## parallel_distributed_insert_select {#parallel_distributed_insert_select}

<SettingsInfoBlock type="UInt64" default_value="2" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.7"},{"label": "2"},{"label": "기본적으로 병렬 분산 `INSERT ... SELECT`를 활성화"}]}]} />

병렬 분산 `INSERT ... SELECT` 쿼리를 활성화합니다.

`INSERT INTO distributed_table_a SELECT ... FROM distributed_table_b` 쿼리를 실행할 때, 두 테이블이 동일한 클러스터를 사용하고 둘 다 [복제된](/ko/reference/engines/table-engines/mergetree-family/replication) 테이블이거나 복제되지 않은 테이블이면, 이 쿼리는 각 세그먼트에서 로컬로 처리됩니다.

가능한 값:

* `0` — 비활성화됩니다.
* `1` — `SELECT`는 Distributed 엔진의 기반 테이블에서 각 세그먼트별로 실행됩니다.
* `2` — `SELECT`와 `INSERT`는 Distributed 엔진의 기반 테이블에서/로 각 세그먼트별로 실행됩니다.

v25.4부터 `ReplicatedMergeTree` 또는 `SharedMergeTree` source의 `INSERT ... SELECT`도 레플리카 전반에서 병렬화할 수 있습니다. 이를 활성화하려면 다음을 설정하십시오:

* `parallel_distributed_insert_select = 2`
* `enable_parallel_replicas = 1`

<Note>
  재작성된 쿼리는 `SELECT`의 모든 표현식(서브쿼리, 사용자 정의 함수(UDFs) 등)을 포함하여 클러스터 구성의 자격 증명으로 세그먼트에서 실행됩니다. 이는 `GLOBAL`이 아닌 `IN`의 서브쿼리 등 세그먼트 측에서 이루어지는 다른 처리와 동일한 신뢰 모델입니다. 세그먼트 측 읽기를 호출한 사용자의 권한으로 인가해야 한다면 서버 간 시크릿(클러스터 구성의 `secret` 원소)을 구성하십시오.
</Note>

## parallel_hash_join_threshold {#parallel_hash_join_threshold}

<SettingsInfoBlock type="UInt64" default_value="100000" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.5"},{"label": "100000"},{"label": "새로운 설정"}]}, {"id": "row-2","items": [{"label": "25.4"},{"label": "0"},{"label": "새로운 설정"}]}, {"id": "row-3","items": [{"label": "25.3"},{"label": "0"},{"label": "새로운 설정"}]}]} />

`INNER`, `LEFT`, `RIGHT` 또는 `FULL` 해시 조인에서 이 임계값은 해시 테이블을 구축하는 방식을 결정합니다.
오른쪽 테이블(right table)의 추정 행 수가 임계값보다 작으면 조인은 해시 테이블을 하나의 스레드에서 단일 파트로 구축합니다.
추정 행 수가 임계값 이상이거나 추정치가 없으면 조인은 해시 테이블을 여러 파트로 분할하고, 최대 `max_threads`개의 스레드가 이를 동시에 채웁니다(`max_threads = 1`이면 스레드 하나).
`0`으로 설정하면 해시 테이블을 항상 분할합니다.
`hash_join_layout`이 `serial` 또는 `parallel`로 설정되어 있으면 이 임계값은 사용되지 않으며, 조인은 추정치와 관계없이 단일 파트로 구축하거나 해시 테이블을 분할합니다.
추정치는 쿼리 실행 계획(query plan) 또는 동일한 조인을 이전에 실행했을 때 수집된 통계에서 가져옵니다(`collect_hash_table_stats_during_joins` 참조).
데이터 파트가 없는 `MergeTree` 테이블처럼 비어 있음이 확실한 오른쪽 테이블에 대해서는 쿼리 실행 계획이 행 수를 0으로 추정합니다.
`ASOF` 조인에는 추정치가 제공되지 않으며, `query_plan_optimize_join_order_limit = 0`이면 모든 조인에 추정치가 제공되지 않습니다.

## parallel_non_joined_rows_processing {#parallel_non_joined_rows_processing}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.2"},{"label": "1"},{"label": "RIGHT/FULL `parallel_hash` 조인에서 조인되지 않은 행을 병렬로 처리할 수 있도록 하는 새로운 설정입니다."}]}]} />

RIGHT 및 FULL JOIN 수행 중 오른쪽 테이블의 조인되지 않은 행을 여러 스레드가 병렬로 처리할 수 있도록 합니다.
오른쪽 테이블이 커서 해시 테이블을 여러 스레드에서 구축하는 해시 조인에서 조인되지 않은 행 처리 단계의 속도를 높일 수 있습니다(`parallel_hash_join_threshold` 참조).
비활성화하거나 해시 테이블을 하나의 스레드에서 구축하는 경우 조인되지 않은 행은 단일 스레드에서 처리됩니다.
어떤 경우든 조인되지 않은 행은 정해진 순서 없이 출력됩니다. 쿼리 결과의 순서가 일정해야 한다면 `ORDER BY`를 사용하십시오.
