## ssd_cache {#ssd_cache}

`cache`와 유사하지만, 데이터는 SSD에 저장하고 인덱스는 RAM에 저장합니다. 업데이트 큐와 관련된 모든 캐시 딕셔너리 설정은 SSD 캐시 딕셔너리에도 적용할 수 있습니다.

캐시 내용은 서버마다 로컬에 보관되며, 서버가 재시작되거나 교체되면 사라집니다. 삽입 시점 보강을 안정적으로 수행해야 한다면 `ssd_cache` 또는 `complex_key_ssd_cache`를 사용하지 마십시오. 캐시가 비어 있으면 삽입이 딕셔너리 소스 조회에 의존하게 됩니다. ClickHouse Cloud에서는 자동 스케일링과 관리형 노드 교체로 인해 이러한 상황이 발생할 가능성이 더 높습니다. 대신 각 서버에 전체 딕셔너리를 로드하는 레이아웃을 사용하십시오. 자세한 내용은 [딕셔너리 모범 사례](/ko/concepts/features/dictionaries/best-practices#cache-dictionaries-in-ingestion-path)를 참조하십시오.

`cache`와 마찬가지로 이 레이아웃은 어떤 키가 존재하는지 기록하지 않으므로, 이를 `SELECT ... FROM <dictionary>`로 테이블처럼 읽으면 현재 보관 중인 셀 가운데 값을 가진 셀만 반환합니다. 즉, 캐시에 없는 키는 발견할 수 없으며, 조회했지만 소스에서 찾지 못한 키를 기록하는 기본값 셀은 건너뜁니다. 만료된 상주 셀은 여전히 소스에 다시 요청됩니다. [cache](/ko/reference/statements/create/dictionary/layouts/cache)를 참조하십시오.

딕셔너리 키는 [UInt64](/ko/reference/data-types/int-uint) 타입입니다.

<Tabs>
  <Tab title="DDL">
    ```sql
    LAYOUT(SSD_CACHE(BLOCK_SIZE 4096 FILE_SIZE 16777216 READ_BUFFER_SIZE 1048576
        PATH '/var/lib/clickhouse/user_files/test_dict'))
    ```
  </Tab>

  <Tab title="설정 파일">
    ```xml
    <layout>
        <ssd_cache>
            <!-- 바이트 단위의 기본 읽기 블록 크기입니다. SSD의 페이지 크기와 같게 설정하는 것이 좋습니다. -->
            <block_size>4096</block_size>
            <!-- 바이트 단위의 최대 캐시 파일 크기입니다. -->
            <file_size>16777216</file_size>
            <!-- SSD에서 요소를 읽기 위한 바이트 단위의 RAM 버퍼 크기입니다. -->
            <read_buffer_size>131072</read_buffer_size>
            <!-- SSD로 플러시하기 전에 요소를 모아 두기 위한 바이트 단위의 RAM 버퍼 크기입니다. -->
            <write_buffer_size>1048576</write_buffer_size>
            <!-- 캐시 파일이 저장될 경로입니다. -->
            <path>/var/lib/clickhouse/user_files/test_dict</path>
        </ssd_cache>
    </layout>
    ```
  </Tab>
</Tabs>

## complex_key_ssd_cache {#complex_key_ssd_cache}

이 저장소 유형은 복합 [키](/ko/reference/statements/create/dictionary/attributes#composite-key)와 함께 사용됩니다. `ssd_cache`와 유사합니다.
