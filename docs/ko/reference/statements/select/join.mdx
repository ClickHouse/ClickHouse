`JOIN` 절은 각 테이블에 공통으로 존재하는 값을 사용해 하나 이상의 테이블에서 컬럼을 결합하고, 그 결과로 새 테이블을 만듭니다. 이는 SQL을 지원하는 데이터베이스에서 흔히 사용되는 연산이며, [관계대수](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators)의 조인에 해당합니다. 하나의 테이블을 자기 자신과 조인하는 특수한 경우는 보통 &quot;self-join&quot;이라고 합니다.

**구문**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

`ON` 절의 표현식과 `USING` 절의 컬럼을 &quot;JOIN 키&quot;라고 합니다. 별도로 명시하지 않는 한, `JOIN`은 JOIN 키가 일치하는 행들로 [카테시안 곱](https://en.wikipedia.org/wiki/Cartesian_product)을 생성하므로, 원본 테이블보다 훨씬 많은 행이 결과에 포함될 수 있습니다.

이 페이지에서는 `JOIN` 절의 구문과 의미 체계를 설명합니다. ClickHouse에서 JOIN이 실행되는 방식, JOIN 유형, 설정, 메모리 고려 사항 및 최적화에 대해서는 [관련 콘텐츠](#related-content)를 참조하십시오.

## 지원되는 JOIN 유형 {#supported-types-of-join}

모든 표준 [SQL JOIN](https://en.wikipedia.org/wiki/Join_\(SQL\)) 유형을 지원합니다:

| 유형                 | 설명                                                                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | 일치하는 행만 반환됩니다.                                                                                                                                                                        |
| `LEFT OUTER JOIN`  | 일치하는 행과 함께 왼쪽 테이블의 비일치 행도 반환됩니다.                                                                                                                                                      |
| `RIGHT OUTER JOIN` | 일치하는 행과 함께 오른쪽 테이블의 비일치 행도 반환됩니다.                                                                                                                                                     |
| `FULL OUTER JOIN`  | 일치하는 행과 함께 양쪽 테이블의 비일치 행도 반환됩니다.                                                                                                                                                      |
| `CROSS JOIN`       | 전체 테이블의 카테시안 곱을 생성합니다. JOIN 키는 지정하지 **않습니다**.                                                                                                                                         |
| `NATURAL JOIN`     | 두 테이블에서 이름이 같은 모든 컬럼을 기준으로 자동으로 조인합니다. 각 공통 컬럼은 결과에 한 번만 나타납니다. `INNER`(기본값), `LEFT`, `RIGHT`, `FULL` 변형을 지원합니다. 컬럼 목록이 자동으로 도출된다는 점만 제외하면 `JOIN ... USING (col1, col2, ...)`와 동일합니다. |

* 유형을 지정하지 않은 `JOIN`은 `INNER`를 의미합니다.
* `OUTER` 키워드는 생략할 수 있습니다.
* `CROSS JOIN`의 대체 구문으로, [`FROM` 절](/ko/reference/statements/select/from)에서 여러 테이블을 쉼표로 구분해 지정할 수 있습니다.
* `NATURAL JOIN`에 일치하는 컬럼이 없으면 `CROSS JOIN`처럼 동작합니다.

ClickHouse에서 추가로 지원하는 JOIN 유형은 다음과 같습니다:

| 유형                                                  | 설명                                                                                                                                                                                 |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | 카테시안 곱을 생성하지 않고 JOIN 키에 대해 허용 목록을 적용합니다.                                                                                                                                           |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | 카테시안 곱을 생성하지 않고 JOIN 키에 대해 거부 목록을 적용합니다.                                                                                                                                           |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | 표준 `JOIN` 유형의 카테시안 곱을 부분적으로(`LEFT` 및 `RIGHT`의 반대편) 또는 완전히(`INNER`) 비활성화합니다. `ANY FULL JOIN`은 지원되지 않습니다.                                                                            |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | 정확히 일치하지 않는 조건으로 시퀀스를 조인합니다. [ASOF JOIN 사용법](#asof-join-usage)을 참조하십시오.                                                                                                            |
| `PASTE JOIN`                                        | 두 테이블을 가로로 이어 붙입니다. [PASTE JOIN 사용법](#paste-join-usage)을 참조하십시오.                                                                                                                   |
| `INNER JOIN LATERAL`, `LEFT JOIN LATERAL`           | 왼쪽에 있는 테이블의 컬럼을 참조하는 서브쿼리를 조인합니다. 실험적 기능이며 [`enable_lateral_join`](/ko/reference/settings/session-settings/enable#enable_lateral_join)이 필요합니다. [LATERAL JOIN](#lateral-join)을 참조하십시오. |

각 JOIN 유형과 엄격성에 대한 다이어그램은 [ClickHouse에서 JOIN 사용하기](/ko/concepts/features/operations/select/joining-tables#join-types-and-strictness)에서 확인할 수 있습니다.

<Note>
  `semi_join_include_columns_from_both_sides` 또는 `anti_join_include_columns_from_both_sides` 설정을 비활성화하면, 조인 결과가 만들어진 이후에 해석되는 표현식에서는 해당 조인의 보존되는 쪽 컬럼만 노출됩니다.

  * `LEFT SEMI JOIN` 및 `LEFT ANTI JOIN`은 왼쪽 컬럼만 노출합니다.
  * `RIGHT SEMI JOIN` 및 `RIGHT ANTI JOIN`은 오른쪽 컬럼만 노출합니다.
  * 이 동작은 `SELECT`, `PREWHERE`, `WHERE`, `GROUP BY`, `HAVING`, `QUALIFY`, `ORDER BY`, `LIMIT BY` 등의 절에 적용되며, `t1.*`와 같은 한정된 와일드카드에도 적용됩니다.
  * 같은 `JOIN`의 `ON` 표현식에서는 여전히 양쪽을 모두 참조할 수 있습니다.

  이 설정이 활성화되어 있으면(기본값) ClickHouse는 레거시 동작을 유지합니다. 즉, 양쪽 모두에 접근할 수 있으며 `SELECT *`는 두 테이블의 컬럼을 모두 확장합니다.
</Note>

모든 JOIN 알고리즘이 JOIN 유형과 엄격성의 모든 조합을 지원하는 것은 아닙니다. 지원되는 조합은 [알고리즘별 지원 JOIN 유형](/ko/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm)에서 확인할 수 있습니다.

### `CROSS JOIN`을 `INNER JOIN`으로 재작성 {#cross-join-rewrite}

`CROSS JOIN` 또는 쉼표로 구분된 테이블 목록을 사용하는 쿼리의 `WHERE` 절에 테이블 간 동등 조건이 있으면, ClickHouse는 이 조건을 조인 키로 사용하는 `INNER JOIN`으로 해당 JOIN을 재작성할 수 있습니다. 이 재작성 동작은 [`cross_to_inner_join_rewrite`](/ko/reference/settings/session-settings/other#cross_to_inner_join_rewrite) 설정으로 제어합니다.

* `0`: 재작성이 비활성화됩니다.
* `1`: `WHERE` 절에 테이블 간 동등 조건이 있으면 쉼표로 구분된 테이블 목록 또는 `CROSS JOIN`을 재작성합니다. 그렇지 않으면 JOIN은 `CROSS JOIN`으로 실행됩니다.
* `2`: `1`과 동일하지만, 쿼리에 `WHERE` 절이 있는데 쉼표로 구분된 테이블 목록을 재작성할 수 없으면 쿼리가 `INCORRECT_QUERY` 오류로 실패합니다. `CROSS JOIN` 키워드로 작성된 JOIN은 재작성할 수 없더라도 `CROSS JOIN`으로 실행됩니다.

값이 `0`이더라도 [`query_plan_merge_filter_into_join_condition`](/ko/reference/settings/session-settings/query-plan#query_plan_merge_filter_into_join_condition)으로 제어되는 쿼리 실행 계획(query plan) 최적화에 의해 동등 필터(filter)가 JOIN에 병합되어 `INNER JOIN`으로 실행될 수 있습니다.

## `ON` 절의 조건 {#on-section-conditions}

`ON` 절에는 `AND` 및 `OR` 연산자로 결합된 여러 조건을 포함할 수 있습니다. JOIN 키를 지정하는 조건은 다음 요구 사항을 충족해야 합니다.

* 왼쪽 테이블과 오른쪽 테이블을 모두 참조해야 합니다
* 동등 연산자를 사용해야 합니다

그 밖의 조건에서는 다른 연산자를 사용할 수 있으며, 쿼리의 왼쪽 테이블이나 오른쪽 테이블 중 하나만 참조하거나 둘 다 참조할 수 있습니다.

전체 복합 조건이 충족되면 행이 조인됩니다. 조건이 충족되지 않더라도 `JOIN` 유형에 따라 행이 결과에 포함될 수 있습니다. 같은 조건을 `WHERE` 절에 넣었는데 조건이 충족되지 않으면, 행은 항상 결과에서 필터링됩니다.

`OR`로 결합된 JOIN 키는 [`hash`](/ko/concepts/features/operations/select/join-algorithms#hash) 알고리즘에서만 지원되며, 이 알고리즘은 JOIN 키가 포함된 각 `OR` 인수마다 별도의 해시 테이블을 생성합니다.

<Note>
  동등 연산자(`=`)를 사용한 조건만 JOIN 키가 됩니다. 서로 다른 테이블의 컬럼 간에 다른 연산자를 사용하는 것도 지원되지만, 동등 조건이 하나도 없으면 JOIN 시 모든 행 쌍을 검사해야 합니다. 자세한 내용은 [임의의 ON 조건을 사용하는 조인](#join-with-an-arbitrary-on-condition)을 참조하십시오.
</Note>

**예시**

`table_1` 및 `table_2`를 가정해 보겠습니다.

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

하나의 조인 키 조건과 `table_2`에 대한 추가 조건이 포함된 쿼리:

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

결과에는 이름이 `C`이고 text 컬럼이 비어 있는 행도 포함됩니다. 이는 `OUTER` 조인을 사용했기 때문에 결과에 포함된 것입니다.

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

`INNER` 유형의 조인에서 여러 조건을 사용하는 쿼리:

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```response title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴────────┴────────┘
```

조인의 `INNER` 유형과 `OR` 조건을 사용하는 쿼리:

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

조인 유형이 `INNER`이며 조건에 `OR`와 `AND`를 사용하는 쿼리:

<Note>
  `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c`와 같이 단일 테이블의 컬럼을 사용하는 같지 않은 조건은 해당 테이블에만 적용됩니다. `t1.b > 0`은 `t1`의 컬럼만 사용하고 `t2.b > t2.c`는 `t2`의 컬럼만 사용합니다.
  `t1.a = t2.key AND t1.b > t2.key`와 같이 서로 다른 테이블의 컬럼을 비교하는 같지 않은 조건도 지원됩니다. 아래 섹션을 참조하십시오.
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## 서로 다른 테이블의 컬럼에 대한 부등 조건 JOIN {#join-with-inequality-conditions-for-columns-from-different-tables}

`ON` 절에는 동등 조건뿐 아니라 서로 다른 테이블의 컬럼을 다른 연산자로 비교하는 조건도 포함할 수 있습니다. 이러한 조건은 `ALL`, `ANY`, `SEMI`, `ANTI` 엄격성에서 해당 엄격성이 허용하는 모든 JOIN 유형에 대해 지원됩니다. `ASOF` 엄격성에서는 지원되지 않습니다.

`ON` 절에 부등 조건과 함께 두 테이블 간의 동등 조건이 있으면, 동등 조건이 JOIN 키가 되고 부등 조건은 이 키로 매칭된 행에 대해 검사됩니다. 이러한 혼합 조건은 [`hash`](/ko/concepts/features/operations/select/join-algorithms#hash), [`parallel_hash`](/ko/concepts/features/operations/select/join-algorithms#parallel-hash) 및 [`grace_hash`](/ko/concepts/features/operations/select/join-algorithms#grace-hash) 알고리즘에서 실행됩니다. [`join_algorithm`](/ko/reference/settings/session-settings/join#join_algorithm)에서 [`ie_join`](/ko/concepts/features/operations/select/join-algorithms#ie-join)이 이들 알고리즘보다 앞에 나열되어 있고 `ON` 절에 두 개의 부등 조건이 있으면, 대신 `ie_join`이 JOIN을 실행하며 동등 조건은 필터(filter)로 적용됩니다.

`ON` 절에 두 테이블 간의 동등 조건이 없으면 매칭에 사용할 JOIN 키가 없습니다. 이러한 JOIN은 조건이 한 쌍의 부등 조건이면 [`ie_join`](/ko/concepts/features/operations/select/join-algorithms#ie-join)으로 실행되고, 그렇지 않으면 [블록 중첩 루프 조인(block nested loop join)](#join-with-an-arbitrary-on-condition)으로 실행됩니다.

조인 중 평가되는 조건에는 행 수를 유지해야 하므로 `arrayJoin`을 포함할 수 없습니다. 대신 서브쿼리에서 `ARRAY JOIN`을 사용하십시오.

**예시**

테이블 `t1`:

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

테이블 `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response
key1    a    1    1    2    key1    B    2    1    2
key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
key1    e    5    5    5            0    0    \N
key2    a2    1    1    1            0    0    \N
key4    f    2    3    4            0    0    \N
```

## 임의의 ON 조건을 사용하는 JOIN {#join-with-an-arbitrary-on-condition}

`ON` 절에는 범위 검사, 산술 비교, 스칼라 함수 호출 등 두 테이블의 컬럼에 대한 임의의 불리언 표현식을 사용할 수 있습니다. 두 테이블 간의 동등 비교가 없으면 행을 매칭하는 데 사용할 JOIN 키가 없습니다. 부등 조건 한 쌍으로 이루어진 조건은 [`join_algorithm`](/ko/reference/settings/session-settings/join#join_algorithm)에 `ie_join` 알고리즘이 포함되어 있기만 하면 첫 번째 위치가 아니더라도 `ie_join`으로 실행됩니다. 다른 어떤 `join_algorithm` 값으로도 이러한 조건을 실행할 수 없기 때문입니다. 26.8 버전부터는 `join_algorithm`의 기본값에 `ie_join`이 포함되어 있습니다. 그 밖의 조건은 [블록 중첩 루프 조인(block nested loop join)](https://en.wikipedia.org/wiki/Nested_loop_join)으로 실행됩니다. 이 방식에서는 오른쪽 테이블을 구체화한 다음, 모든 행 쌍에 대해 조건을 평가합니다. `ALL INNER JOIN`은 해당 조건을 필터로 사용하는 `CROSS JOIN`과 동일한 형태로 실행됩니다.

블록 중첩 루프 조인은 `ASOF JOIN`, `PASTE JOIN`, `ANY FULL JOIN`을 제외한 모든 JOIN 유형과 엄격성을 지원합니다. 이 알고리즘은 `join_algorithm`에 지정할 수 있는 값이 아니며, 다른 어떤 알고리즘으로도 조건을 실행할 수 없을 때에만 사용되는 최후의 수단입니다. `EXPLAIN` 출력에서는 `BlockNestedLoopJoin` 단계로 표시됩니다. [`allow_block_nested_loop_join`](/ko/reference/settings/session-settings/allow#allow_block_nested_loop_join)이 비활성화되어 있으면 이 알고리즘이 필요한 쿼리는 `INVALID_JOIN_ON_EXPRESSION` 오류와 함께 거부됩니다.

**예시**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

일치하는 항목이 없는 행은 다른 모든 JOIN과 마찬가지로 [`join_use_nulls`](/ko/reference/settings/session-settings/join#join_use_nulls)에 따라 채워집니다. 위의 예처럼 기본값으로 채워지며, 이 설정이 활성화되어 있으면 `NULL`로 채워집니다.

**엄격성**

`ANY`와 `SEMI`는 일반적으로 JOIN 키를 공유하는 행 그룹마다 1개의 행을 유지합니다. 여기서는 그러한 그룹이 없으므로, JOIN을 주도하는 테이블의 행마다 1개의 행을 유지합니다. 즉, `LEFT ANY`와 `LEFT SEMI`는 각 왼쪽 행을 최대 한 번, `RIGHT ANY`와 `RIGHT SEMI`는 각 오른쪽 행을 최대 한 번 출력합니다. `ANY INNER`는 양쪽을 동시에 제한합니다. 두 테이블의 각 행은 최대 한 번만 사용되므로, 결과의 행 수는 더 작은 테이블의 행 수를 넘지 않습니다. 이러한 결과를 구성하는 쌍은 `ANY`가 의미하는 대로 임의로 정해지며, 동일한 쿼리를 두 번 실행해도 달라질 수 있습니다. `ANY INNER`에서는 이 특성이 행 수에까지 적용됩니다. 행을 어떤 순서로 검사하든 양쪽의 각 행을 탐욕적으로 짝짓다 보면 짝을 찾지 못한 행의 수가 달라질 수 있으므로, JOIN 키가 없는 `ANY INNER` JOIN에 대한 `count()` 결과는 재현할 수 없으며 스레드 수와 오른쪽 테이블의 물리적 순서에 따라 달라집니다.

**성능**

블록 중첩 루프 조인은 모든 행 쌍을 검사하므로, [블록 중첩 루프 폴백](/ko/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback)에서 설명한 것처럼 비용이 두 테이블 행 수의 곱에 비례하여 증가합니다. 구체화된 오른쪽 테이블에는 [JOIN 메모리 관리 및 스필](/ko/concepts/features/operations/select/join-memory-management)에서 설명한 하드 메모리 제한과 디스크 유출 임계값(spill threshold)이 적용됩니다.

## JOIN 키의 NULL 및 NaN 값 {#null-values-in-join-keys}

`NULL`은 자기 자신을 포함해 어떤 값과도 같지 않습니다. 한 테이블에서 JOIN 키의 값이 `NULL`이면 다른 테이블의 `NULL` 값과 일치하지 않습니다. JOIN 키가 [널 허용](/ko/reference/data-types/nullable) 컬럼이면 키 중 하나 이상이 [NULL](/ko/reference/syntax#null)인 행은 조인되지 않습니다.

**예시**

테이블 `A`:

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

테이블 `B`:

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

`A` 테이블의 `Charlie`가 있는 행과 `B` 테이블의 점수 88인 행은 JOIN 키에 `NULL` 값이 있기 때문에 일치하지 않습니다.

일치하는 항목이 없는 행은 [빈 셀 또는 NULL 셀 처리](#processing-of-empty-or-null-cells)에 설명된 대로 `score` 컬럼에 `0` 값을 갖습니다.

`NULL` 값을 서로 일치시키려면 `isNotDistinctFrom` 함수로 JOIN 키를 비교하십시오.

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

float JOIN 키의 `NaN` 값에는 위의 `NULL` 규칙이 적용되지 않습니다.
두 `NaN` 값을 스칼라 방식으로 비교하면(`NaN = NaN`) 결과는 `0`입니다. 그러나 JOIN 키는 스칼라 의미 체계로 비교되지 않으므로 `NaN` 키가 일치할 수 있습니다.
실제로 일치하는지는 정해져 있지 않으며, JOIN 알고리즘, 키 유형 및 세션 설정에 따라 달라집니다.
`NaN` 키가 일치하지 않도록 하려면 `NULL` 값으로 매핑하십시오. 예: `ON if(isNaN(A.id), NULL, A.id) = B.id`.
`ASOF JOIN`에서는 가장 가까운 일치 항목의 컬럼을 정렬 순서로 비교하는데, `NaN` 값에는 정렬 순서가 정의되어 있지 않습니다.

## 암시적 타입 변환 {#implicit-type-conversion}

왼쪽 테이블과 오른쪽 테이블의 JOIN 키 타입이 서로 다르면 ClickHouse는 비교하기 전에 두 키를 최소 공통 상위 타입으로 변환합니다. 이는 모든 JOIN 유형과 엄격성에 적용됩니다.

* `ON`을 사용하면 변환은 비교에만 적용됩니다. 키 컬럼은 결과(result)에서 원래 타입을 유지합니다.
* `USING`을 사용하면 병합된 컬럼은 결과에서 공통 타입을 가집니다. `semi_join_include_columns_from_both_sides` 또는 `anti_join_include_columns_from_both_sides`가 비활성화되어 있으면 `SEMI JOIN` 또는 `ANTI JOIN`의 병합된 컬럼은 보존되는 테이블의 타입을 유지합니다.

키 타입에 공통 상위 타입(common supertype)이 없고 두 타입이 모두 정수 타입이거나 정수 타입의 튜플이면(`UInt64`와 `Int64`가 이에 해당), ClickHouse는 두 키를 양쪽 키 타입에 공통으로 속하는 값을 담을 수 있는 타입으로 변환합니다. `UInt64`와 `Int64`라면 이 타입은 `UInt64`입니다. 이 타입으로 표현할 수 없는 키 값(Key value)은 어떤 값과도 일치하지 않습니다. 이 변환은 `isNotDistinctFrom`을 제외한 `ON`의 동등 조건과 `INNER JOIN` 또는 `SEMI JOIN`의 `USING`에 사용됩니다. `ASOF JOIN`의 최근접 일치 조건, `ie_join`이 실행하는 비동등 조건, 그 밖의 JOIN에서의 `USING`에는 사용되지 않습니다. 이들의 결과 컬럼은 일치 항목이 없는 값도 담아야 하기 때문입니다. 이 변환은 버전 26.9부터 사용할 수 있습니다.

키 타입에 공통 상위 타입이 없고 이 변환도 적용되지 않으면(`String`과 `Int32`, 또는 `UInt64`와 `Float64`가 이에 해당) 쿼리는 `NO_COMMON_TYPE`과 같은 예외를 발생시키며 실패합니다.

**예시**

테이블 `t_1`을 살펴보겠습니다:

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

그리고 `t_2` 테이블:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

쿼리

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b) ORDER BY ALL;
```

다음 집합을 반환합니다:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## ASOF JOIN 사용 {#asof-join-usage}

`ASOF JOIN`은 정확히 일치하는 항목이 없는 레코드를 조인합니다. `ASOF`는 `INNER` 또는 `LEFT` JOIN과 함께 사용되는 JOIN 엄격성이며, JOIN 알고리즘이 아닙니다.

`ASOF JOIN`을 사용하려면 두 테이블 모두에 가장 가까운 일치 기준이 되는 컬럼이 필요합니다. 이 컬럼은 다음 조건을 충족해야 합니다.

* 순서가 정의된 타입이어야 합니다.
* [`hash`](/ko/concepts/features/operations/select/join-algorithms#hash) 알고리즘에서는 다음 타입을 사용할 수 있습니다: [Int, UInt](/ko/reference/data-types/int-uint), [Float](/ko/reference/data-types/float), [Decimal](/ko/reference/data-types/decimal), [Date](/ko/reference/data-types/date), [Date32](/ko/reference/data-types/date32), [DateTime](/ko/reference/data-types/datetime), [DateTime64](/ko/reference/data-types/datetime64), [Time](/ko/reference/data-types/time), [Enum](/ko/reference/data-types/enum), [Bool](/ko/reference/data-types/boolean), 그리고 이들 타입의 [Nullable](/ko/reference/data-types/nullable). `String`, `Time64` 등 그 밖의 타입은 `BAD_TYPE_OF_FIELD` 오류와 함께 거부됩니다.
* [`full_sorting_merge`](/ko/concepts/features/operations/select/join-algorithms#full-sorting-merge) 알고리즘에서는 `String` 등 그 밖의 비교 가능한 데이터 타입(comparable types)도 사용할 수 있습니다.
* `hash` 알고리즘에서는 `JOIN` 절의 유일한 컬럼일 수 없으며, 최소 하나의 동등 조건이 필요합니다. `full_sorting_merge` 알고리즘에는 이 요구 사항이 없습니다.

구문 `ASOF JOIN ... ON`:

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

등가 조건은 개수 제한 없이 사용할 수 있으며, 가장 가까운 일치 조건은 정확히 하나만 사용할 수 있습니다. 예를 들어, `SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t`.

가장 가까운 일치에 지원되는 조건: `>`, `>=`, `<`, `<=`.

구문 `ASOF JOIN ... USING`:

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

`ASOF JOIN`은 동등 조건으로 조인할 때 `equi_columnX`를 사용하고, `table_1.asof_column >= table_2.asof_column` 조건에서 가장 가까운 값을 기준으로 조인할 때는 `asof_column`을 사용합니다. `asof_column` 컬럼은 항상 `USING` 절의 마지막에 위치합니다.

예시로, 다음 테이블을 살펴보겠습니다.

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

`ASOF JOIN`은 `table_1`의 사용자 이벤트 타임스탬프를 기준으로, 가장 가까운 일치 조건에 맞으면서 `table_1`의 이벤트 타임스탬프와 가장 가까운 타임스탬프를 가진 `table_2`의 이벤트를 찾을 수 있습니다. 같은 타임스탬프 값이 있으면 그것이 가장 가까운 값으로 선택됩니다. 여기서 `user_id` 컬럼은 동등 조건 조인에 사용할 수 있고, `ev_time` 컬럼은 최근접 일치 조인에 사용할 수 있습니다. 이 예시에서는 `event_1_1`은 `event_2_1`과 조인할 수 있고 `event_1_2`는 `event_2_3`과 조인할 수 있지만, `event_2_2`는 조인할 수 없습니다.

<Note>
  JOIN 알고리즘 중에서는 [`hash`](/ko/concepts/features/operations/select/join-algorithms#hash)와 [`full_sorting_merge`](/ko/concepts/features/operations/select/join-algorithms#full-sorting-merge)만 `ASOF` 엄격성을 지원합니다. 자세한 내용은 [알고리즘별 지원 JOIN 유형](/ko/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm)을 참고하십시오.
  [Join](/ko/reference/engines/table-engines/special/join) 테이블 엔진에서는 `ASOF`가 **지원되지 않습니다**.
</Note>

## PASTE JOIN 사용법 {#paste-join-usage}

`PASTE JOIN`의 결과는 왼쪽 서브쿼리의 모든 컬럼 뒤에 오른쪽 서브쿼리의 모든 컬럼이 이어지는 테이블입니다.
행은 원본 테이블에서의 위치를 기준으로 대응됩니다(행 순서가 정의되어 있어야 합니다).
서브쿼리가 반환하는 행 수가 서로 다르면 초과된 행은 잘립니다.

예시:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

참고: 이 경우 병렬로 읽으면 결과가 비결정적일 수 있습니다. 예시는 다음과 같습니다:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## LATERAL JOIN {#lateral-join}

`JOIN LATERAL`을 사용하면 조인 오른쪽의 서브쿼리에서 왼쪽에 있는 테이블
표현식(Expressions)의 컬럼을 참조할 수 있습니다. 결과(result)는 서브쿼리가 참조하는 왼쪽 열 값(column values)의 고유한 조합마다
서브쿼리를 평가한 뒤, 그 결과를 해당 조합을 가진 모든 왼쪽 행에 조인한 것과 같습니다.

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

`ON true` 프레디케이트는 다른 `INNER` 또는 `LEFT JOIN`과 마찬가지로 필수이며, 생략하면 구문 오류가 발생합니다.

이 기능은 버전 26.10부터 사용할 수 있습니다. Experimental 기능이며 기본적으로 비활성화되어 있으므로,
[`enable_lateral_join`](/ko/reference/settings/session-settings/enable#enable_lateral_join) 설정으로 활성화하십시오.

래터럴 서브쿼리는 왼쪽 행마다, 또는 고유한 조합마다 한 번씩 실행되는 방식이 아닙니다. 다른 상호 연관된
서브쿼리와 마찬가지로, 모든 왼쪽 행을 대상으로 하는 단일 쿼리로 비상관화(decorrelation)됩니다. 서브쿼리가 집계를 수행하면 서브쿼리에서 참조하는 왼쪽 컬럼이
`GROUP BY` 키에 추가되고, `LIMIT`이 있으면 이 컬럼들을 기준으로 하는 `LIMIT ... BY`로 바뀌며,
서브쿼리의 결과는 이 컬럼들을 기준으로 왼쪽 행과 조인됩니다. 상관 조건이 `orders.user_id = u.id`와 같은 단순 동등 조건이면
왼쪽 컬럼을 서브쿼리에서 값이 같은 컬럼으로 대체할 수 있으며
(`correlated_subqueries_substitute_equivalent_expressions`, 기본적으로 활성화됨), 이 경우 서브쿼리가
왼쪽 행을 읽지 않아도 될 수 있습니다. 다만 항상 그런 것은 아닙니다. 예를 들어 `GROUP BY`가 없는 집계(`count` 등)는
일치하는 행이 없는 왼쪽 값에 대해서도 결과를 생성해야 하므로 여전히 고유한 왼쪽 값을 읽습니다. 고유한 왼쪽 값이
서브쿼리에 전달되는 경우 기본 설정에서는 항상 인메모리 버퍼를 거치며, 이러한 버퍼가 실제로 사용될 때에만
조인이 항상 해시 조인으로 수행됩니다. 동등 조건 치환으로 왼쪽 행을 읽지 않게 되거나 버퍼가 비활성화된 경우
(`correlated_subqueries_use_in_memory_buffer = 0` 또는 `correlated_subqueries_default_join_kind = 'left'`) 등
그 밖의 모든 경우에는 `join_algorithm` 설정에 따라 알고리즘이 선택됩니다. 예를 들어 `LIMIT`이 있는 래터럴 서브쿼리에 `EXPLAIN`을 실행하면
`LimitBy (LIMIT BY for decorrelated correlated subquery)` 단계 위에 `Join` 단계가 표시되며, `LIMIT`이 없는
서브쿼리에는 이 단계가 나타나지 않습니다.

현재는 다음 부분 집합만 지원되며, 그 외의 경우는 오류와 함께 거부됩니다.

* `INNER JOIN LATERAL`과 `LEFT JOIN LATERAL`만 지원됩니다. `RIGHT`, `FULL`, `PASTE`, `NATURAL` 조인은 지원되지 않으며, `LATERAL`은 `CROSS` 조인이나 쉼표 조인과는 함께 사용할 수 없습니다.
* 기본 `ALL` 엄격성만 지원됩니다. `ANY`, `SEMI`, `ANTI`, `ASOF`는 지원되지 않습니다.
* `ON true`(`ON 1`도 허용됨) 이외의 조인 프레디케이트는 사용할 수 없습니다. `USING`은 지원되지 않으며, 프레디케이트를
  생략할 수도 없습니다. 양쪽을 연관시키는 필터는 lateral 서브쿼리의 `WHERE` 절에 작성하십시오.
* `GLOBAL` 및 `LOCAL` 조인 수정자는 지원되지 않습니다.
* lateral 서브쿼리는 왼쪽의 컬럼을 하나 이상 참조해야 합니다. 상관관계가 없는 서브쿼리에는
  일반 조인을 사용하십시오.
* lateral 서브쿼리는 왼쪽 값마다 개별적으로 평가되는 것이 아니라 비상관화(decorrelation)되므로,
  `rand`나 `generateUUIDv4`처럼 쿼리 내에서 비결정적인 함수나,
  `generateRandom`처럼 무작위 행을 생성하는 테이블 함수를 포함해서는 안 됩니다.
  `now`처럼 쿼리 내에서 값이 일정한 함수는 사용할 수 있습니다.
* lateral 테이블 표현식으로는 서브쿼리만 지원됩니다. PostgreSQL의 테이블 소스 형식인
  `LATERAL unnest(...)`와 `CROSS JOIN UNNEST(...)`는 지원되지 않습니다. 대신
  [`ARRAY JOIN`](/ko/reference/statements/select/array-join) 절을 사용하십시오.
* lateral 서브쿼리의 `GROUP BY`와 `ORDER BY`는 모든 왼쪽 값을 합쳐 한 번만 실행되므로,
  `max_rows_to_group_by`, `max_rows_to_sort`, `max_bytes_to_sort` 제한은 하나의 왼쪽 값이 아니라
  모든 왼쪽 값의 행을 합산하여 계산합니다. 이 제한은 `throw` 오버플로우 모드에서만 지원되며, `any`와 `break`는 거부됩니다.
* 비상관화된 서브쿼리의 결과는 단일 조인을 통해 왼쪽 행과 매칭됩니다. 다른 해시 조인과 마찬가지로
  `max_rows_in_join`과 `max_bytes_in_join`은 이 조인에서 메모리에 유지되는 쪽을 제한하며,
  어느 쪽을 유지할지는 플래너가 결정합니다. 앞서 설명한 인메모리 버퍼가 실제로 사용되는 경우에는
  lateral 서브쿼리를 평가하기 전에 왼쪽 행을 모두 읽어야 하므로 `JOIN LATERAL`의 왼쪽이 유지됩니다. 그 외의 경우에는 비상관화된 서브쿼리의 결과가 유지될 수 있습니다. 이 제한은 항상
  `join_overflow_mode`가 `throw`인 것처럼 적용됩니다. `break`를 사용하면 조인이 관련 없는 왼쪽 행을 아무 경고 없이 누락시키기 때문입니다.

**예시**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS enable_lateral_join = 1;
```

## 분산 JOIN {#distributed-join}

분산 테이블이 포함된 JOIN을 실행하는 방법은 두 가지입니다.

* 일반 `JOIN`을 사용하면 쿼리가 원격 서버로 전송됩니다. 오른쪽 테이블을 만들기 위해 각 서버에서 서브쿼리가 실행되며, 이렇게 만들어진 테이블로 조인이 수행됩니다. 즉, 오른쪽 테이블은 각 서버에서 각각 구성됩니다.
* `GLOBAL ... JOIN`을 사용하면 먼저 요청 서버가 서브쿼리를 실행해 조인의 한쪽을 계산하고, 그 결과를 임시 테이블에 수집합니다. 그런 다음 이 임시 테이블이 각 원격 서버로 전달되고, 전송된 임시 데이터를 사용해 각 서버에서 쿼리가 실행됩니다. `LEFT` 및 `INNER` 조인의 경우 오른쪽 테이블이 서브쿼리로 계산됩니다.

`ALL`, `ANY`, `SEMI` 또는 `ANTI` 엄격성을 사용하는 `GLOBAL RIGHT JOIN`에서 왼쪽 테이블이 2개 이상의 세그먼트로 구성된 `Distributed` 테이블이면, ClickHouse는 유지되는 오른쪽 테이블의 행이 한 번만 반환되도록 양쪽을 스왑하여 JOIN을 `LEFT JOIN`으로 실행합니다. 이때 왼쪽 테이블이 서브쿼리로 계산되며, 오른쪽 테이블은 여러 세그먼트로 구성된 `Distributed` 테이블이면 해당 세그먼트에서 읽고, 그렇지 않으면 요청 서버에서 읽습니다. 이 방식으로 스왑할 수 없는 `GLOBAL RIGHT JOIN` 또는 `GLOBAL FULL JOIN`은 요청 서버에서 실행됩니다. 이 동작은 버전 26.9부터 적용됩니다.

`GLOBAL`을 사용할 때는 주의하십시오. 자세한 내용은 [분산 서브쿼리](/ko/reference/statements/in#distributed-subqueries) 섹션을 참조하십시오.

## 빈 셀 또는 NULL 셀 처리 {#processing-of-empty-or-null-cells}

outer JOIN의 결과(result)에서 일치 항목이 없는 행은 상대 테이블의 컬럼이 비어 있습니다. [`join_use_nulls`](/ko/reference/settings/session-settings/join#join_use_nulls) 설정은 ClickHouse가 이러한 셀을 채우는 방식을 결정합니다.

* `0`: 셀을 컬럼 타입의 기본값으로 채웁니다.
* `1`: 셀을 `NULL`로 채우고, 해당 컬럼의 타입을 [Nullable](/ko/reference/data-types/nullable)로 변환합니다. `Array`처럼 `Nullable`로 감쌀 수 없는 타입의 컬럼은 기존 타입을 유지하고 기본값으로 채워집니다. `FULL` JOIN에서는 하나로 합쳐진 `USING` 컬럼도 `Nullable`로 변환됩니다.

[JOIN 키의 NULL 및 NaN 값](#null-values-in-join-keys)에서 설명한 것처럼, JOIN 키 중 하나라도 `NULL`인 행은 조인되지 않습니다.

## USING 절 {#using-clause}

`USING` 절은 조인 기준이 되는 하나 이상의 컬럼을 지정하고, 해당 컬럼들이 서로 같다는 동등 조건을 설정합니다.

* 각 컬럼은 왼쪽 테이블 표현식과 오른쪽 테이블 표현식 모두에 같은 이름으로 존재해야 합니다. 서브쿼리에서 별칭을 사용하면 컬럼에 같은 이름을 부여할 수 있습니다.
* `USING` 절에는 컬럼 이름만 지정할 수 있습니다. 표현식(Expressions)은 지원되지 않습니다.
* 열 목록(column list)은 괄호로 감싸도 되고 감싸지 않아도 됩니다.
* `USING` 절의 각 컬럼은 결과에 한 번만 나타납니다. 해당 컬럼의 유형은 [암시적 타입 변환](#implicit-type-conversion)을 참고하십시오.
* 그 밖의 컬럼은 두 테이블에서 같은 이름을 가질 수 있습니다. `SELECT *`는 오른쪽 테이블의 컬럼 앞에 테이블 이름 또는 별칭을 붙여 한정하며, [`single_join_prefer_left_table`](/ko/reference/settings/session-settings/other#single_join_prefer_left_table)이 활성화되어 있으면 한정되지 않은 이름은 왼쪽 테이블의 컬럼으로 해석됩니다.
* [`analyzer_compatibility_join_using_top_level_identifier`](/ko/reference/settings/session-settings/analyzer-compatibility#analyzer_compatibility_join_using_top_level_identifier)가 활성화되어 있으면, `USING`의 컬럼명은 쿼리 내 같은 이름의 별칭(예: `SELECT` 목록의 별칭)을 기준으로 해석됩니다.

## 예시 {#examples}

다음 쿼리는 카운터별 hits 수와 카운터별 visits 수를 조인합니다. `ANY LEFT JOIN`은 왼쪽 서브쿼리의 각 행을 한 번씩만 반환하며, visits가 없는 카운터에는 기본값 `0`이 할당됩니다.

```sql title="Query"
SELECT
    CounterID,
    hits,
    visits
FROM
(
    SELECT
        CounterID,
        count() AS hits
    FROM VALUES('CounterID UInt32', 1, 1, 1, 2, 2, 3)
    GROUP BY CounterID
) AS h
ANY LEFT JOIN
(
    SELECT
        CounterID,
        sum(Sign) AS visits
    FROM VALUES('CounterID UInt32, Sign Int8', (1, 1), (1, 1), (1, -1), (2, 1), (4, 1))
    GROUP BY CounterID
) AS v USING (CounterID)
ORDER BY hits DESC;
```

```response title="Response"
┌─CounterID─┬─hits─┬─visits─┐
│         1 │    3 │      1 │
│         2 │    2 │      1 │
│         3 │    1 │      0 │
└───────────┴──────┴────────┘
```
