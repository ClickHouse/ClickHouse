이 페이지에서는 `KILL QUERY`, `KILL MUTATION`, `KILL TRANSACTION` 및 `KILL PART_MOVE_TO_SHARD` SQL 문을 설명합니다.

기본적으로 현재 실행 중인 `KILL` SQL 문을 제외했을 때 `WHERE` 표현식에 해당하는 대상 행이 `system.processes`에 남아 있지 않으면 `KILL QUERY`가 `NOTHING_TO_KILL` 예외를 발생시키고, `WHERE` 표현식과 일치하는 행이 `system.mutations`에 하나도 없으면 `KILL MUTATION`이 예외를 발생시킵니다. 일치하는 항목이 없어도 예외 없이 반환되도록 하려면 [`kill_throw_if_noop`](/ko/operations/settings/settings#kill_throw_if_noop)를 `false`로 설정하십시오.
`KILL TRANSACTION` 및 `KILL PART_MOVE_TO_SHARD`는 일치하는 항목이 없어도 예외를 발생시키지 않고 빈 결과(result)를 반환합니다.
`ON CLUSTER`로 실행하면 일치 결과가 호스트 간에 집계되지 않으므로, 일치하는 항목이 없어도 예외가 발생하지 않습니다.

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

현재 실행 중인 쿼리를 강제로 종료하려고 시도합니다.
종료할 쿼리는 `KILL` 쿼리의 `WHERE` 절에 정의된 조건에 따라 system.processes 테이블에서 선택됩니다.

예시:

먼저, 아직 완료되지 않은 쿼리 목록을 확인해야 합니다. 다음 SQL 쿼리는 가장 오래 실행 중인 쿼리부터 보여줍니다.

단일 ClickHouse 노드의 목록:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

ClickHouse 클러스터 목록:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

쿼리를 강제 종료하세요:

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  ClickHouse Cloud 또는 자가 관리형 클러스터에서 쿼리를 종료하는 경우, 모든 레플리카에서 쿼리가 종료되도록 반드시 `ON CLUSTER [cluster-name]` 옵션을 사용하십시오.
</Tip>

읽기 전용 사용자는 자신의 쿼리만 중지할 수 있습니다.

`system.processes`에 대한 `SELECT` 권한을 부여받지 않은 사용자도 쿼리 ID를 지정하면 자신의 쿼리를 취소할 수 있습니다:
`KILL QUERY WHERE query_id = '<id>'`. 이 권한과 `KILL QUERY` 권한이 모두 없는 사용자가 자신이 실행하지
않은 쿼리의 ID를 지정하면 쿼리가 취소되지 않으며, 기본적으로 `NOTHING_TO_KILL` 예외가 발생합니다.
[`kill_throw_if_noop`](/ko/operations/settings/settings#kill_throw_if_noop)가 `false`로 설정되어 있으면 예외 대신 결과 행을 반환하지 않습니다.
반면 `KILL QUERY` 권한은 있지만 해당 `SELECT` 권한이 없는 사용자는 `SELECT` 권한이 없으므로 요청이 거부됩니다.
다른 `WHERE` 조건과 `ON CLUSTER`에는 위에서 설명한 권한이 계속 필요합니다.

기본적으로는 쿼리의 비동기 버전(`ASYNC`)이 사용되며, 이 버전은 쿼리가 중지되었다는 확인을 기다리지 않습니다.

동기 버전(`SYNC`)은 모든 쿼리가 중지될 때까지 기다리며, 각 프로세스가 중지될 때마다 해당 정보를 표시합니다.
응답에는 `kill_status` 컬럼이 포함되며, 이 컬럼은 다음 값을 가질 수 있습니다:

1. `finished` – 쿼리가 성공적으로 종료되었습니다.
2. `waiting` – 쿼리에 종료 신호를 보낸 후 쿼리가 끝나기를 기다리는 중입니다.
3. 그 밖의 값은 쿼리를 중지할 수 없는 이유를 설명합니다.

테스트 쿼리(`TEST`)는 사용자의 권한만 확인하고 중지할 쿼리 목록을 표시합니다.

## KILL MUTATION {#kill-mutation}

오랫동안 실행 중이거나 완료되지 않은 뮤테이션이 있으면 ClickHouse 서비스가 원활하게 실행되지 않고 있음을 나타내는 경우가 많습니다. 뮤테이션은 비동기적으로 처리되므로 시스템의 사용 가능한 리소스를 모두 소모할 수 있습니다. 다음 중 하나를 수행해야 할 수 있습니다.

* 새 뮤테이션, `INSERT`s, `SELECT`s를 모두 일시 중지하고 뮤테이션 큐가 모두 처리될 때까지 기다립니다.
* 또는 `KILL` 명령을 보내 이러한 뮤테이션 중 일부를 수동으로 강제 종료합니다.

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

현재 실행 중인 [뮤테이션](/ko/reference/statements/alter/index#mutations)을 취소하고 제거합니다. 취소할 뮤테이션은 `KILL` 쿼리의 `WHERE` 절에 지정된 필터를 사용해 [`system.mutations`](/ko/reference/system-tables/mutations) 테이블에서 선택됩니다.

테스트 쿼리(Test query)(`TEST`)는 사용자 권한만 확인하고 강제 종료할 뮤테이션 목록을 표시합니다.

예시:

완료되지 않은 뮤테이션 수를 `count()`로 구합니다:

단일 ClickHouse 노드의 뮤테이션 수:

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

레플리카로 이루어진 ClickHouse 클러스터의 뮤테이션 수:

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

완료되지 않은 뮤테이션 목록을 조회합니다:

단일 ClickHouse 노드의 뮤테이션 목록:

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

ClickHouse 클러스터의 뮤테이션 목록:

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

필요에 따라 뮤테이션을 강제 종료하십시오:

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

이 쿼리는 뮤테이션이 멈춰 완료될 수 없을 때 유용합니다(예: 뮤테이션 쿼리의 일부 함수가 테이블에 저장된 데이터에 적용될 때 예외를 발생시키는 경우).

뮤테이션으로 이미 적용된 변경 사항은 롤백되지 않습니다.

<Note>
  [system.mutations](/ko/reference/system-tables/mutations) 테이블의 `is_killed=1` 컬럼(ClickHouse Cloud 전용)은 뮤테이션이 완전히 종료되었음을 반드시 의미하지는 않습니다. 뮤테이션이 오랜 시간 동안 `is_killed=1` 및 `is_done=0` 상태로 남아 있을 수 있습니다. 이는 장시간 실행 중인 다른 뮤테이션이 강제 종료된 뮤테이션을 가로막고 있을 때 발생할 수 있습니다. 이는 정상적인 상황입니다.
</Note>

## KILL TRANSACTION {#kill-transaction}

도입 버전: v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  이 SQL 문은 실험적 기능 모음에 속합니다.
  실험적 트랜잭션 지원을 활성화하려면 다음 설정을 [구성 파일](/ko/concepts/features/configuration/server-config/configuration-files)에 추가하십시오:

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  자세한 내용은 [트랜잭션(ACID) 지원](/ko/concepts/features/operations/insert/transactions#transactions-commit-and-rollback) 페이지를 참조하십시오.
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

`WHERE` 절로 [`system.transactions`](/ko/reference/system-tables/transactions) 테이블에서 선택한 실행 중인 [트랜잭션(Transactions)](/ko/reference/statements/transactions)을 롤백합니다.
강제 종료된 트랜잭션의 세션은 [`COMMIT`](/ko/reference/statements/transactions#commit)에서 설명한 것처럼 쿼리가 실패한 이후와 같은 상태가 됩니다. 즉, `ROLLBACK`을 실행하기 전까지 `COMMIT`을 실행하면 `INVALID_TRANSACTION` 예외가 발생합니다.

이 SQL 문을 실행하려면 `KILL TRANSACTION` 권한(privilege)과 `system.transactions`에 대한 `SELECT` 권한이 필요합니다.
응답에는 `kill_status` 컬럼이 포함되며, 롤백된 트랜잭션에 대해서는 이 값이 `waiting`입니다. 그 뒤에는 `system.transactions`의 `tid`, `tid_hash`, `elapsed`, `is_readonly`, `state` 컬럼이 이어집니다.

테스트 쿼리(Test query)(`TEST`)는 사용자의 권한만 검사하고 롤백할 트랜잭션 목록을 표시합니다.

예시:

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

도입 버전: v21.11.0

<ExperimentalBadge />

<Note>
  세그먼트 간 파트 이동은 실험적 기능으로, MergeTree 설정 [`part_moves_between_shards_enable`](/ko/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable)을 통해 테이블별로 활성화할 수 있습니다.
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

`ALTER TABLE ... MOVE PART ... TO SHARD`로 시작된 세그먼트 간 파트 이동 작업 중 `WHERE` 절로 [`system.part_moves_between_shards`](/ko/reference/system-tables/part_moves_between_shards) 테이블에서 선택한 작업을 취소합니다.
취소된 이동 작업은 백그라운드에서 롤백되며, `system.part_moves_between_shards`의 `state` 값은 `CANCELLED`로 바뀝니다.
`SOURCE_DROP` 상태에 도달한 이동 작업은 더 이상 취소할 수 없으며 끝까지 실행됩니다.

이 SQL 문을 실행하려면 `system.part_moves_between_shards`에 대한 `SELECT` 권한이 필요합니다. 또한 이동 작업을 취소하려면 해당 테이블에 대한 `ALTER MOVE PARTITION` 권한(privilege)과 `MOVE PARTITION BETWEEN SHARDS` 권한(privilege)이 필요합니다.
`ON CLUSTER`를 사용하면 `*.*`에 대해 두 이동 관련 권한(privilege)이 모두 필요합니다.
응답의 첫 번째 컬럼은 `kill_status`이며, 취소된 이동 작업은 `waiting`, 더 이상 취소할 수 없는 이동 작업은 `cant_cancel` 값을 가집니다. 그 뒤로 `system.part_moves_between_shards`의 `database`, `table`, `task_name`, `task_uuid`, `part_name`, `to_shard`, `state` 컬럼이 이어집니다.

테스트 쿼리(Test query)(`TEST`)는 취소할 이동 작업 목록만 표시합니다. `SYNC` 수정자는 지원되지 않으며, 사용하면 `NOT_IMPLEMENTED` 예외가 발생합니다.

예시:

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
