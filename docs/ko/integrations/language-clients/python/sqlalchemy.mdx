ClickHouse Connect에는 core driver를 기반으로 한 `clickhousedb` SQLAlchemy 방언이 포함되어 있습니다. 동기 방언은 SQLAlchemy 1.4.40 이상(2.x 포함)을 지원하며, Core 쿼리, ClickHouse DDL, 리플렉션, 간단한 ORM 삽입에 중점을 둡니다. 비동기 방언을 사용하려면 SQLAlchemy 2.0.44 이상이 필요합니다.

package extra를 사용하여 SQLAlchemy 의존성을 설치하십시오:

```bash
pip install "clickhouse-connect[sqlalchemy]"
```

## SQLAlchemy로 연결 {#sqlalchemy-connect}

`clickhousedb://` 또는 `clickhousedb+connect://` URL 형식 중 하나를 사용해 엔진을 생성합니다:

```python
from sqlalchemy import create_engine, text

engine = create_engine(
    "clickhousedb://user:password@host:8123/mydb?compression=zstd"
)

with engine.connect() as conn:
    version = conn.execute(text("SELECT version()")).scalar_one()
    print(version)
```

`clickhouse-sqlalchemy`도 함께 설치되어 있다면 이러한 명시적 URL 형식을 사용하십시오.
`clickhouse_connect.cc_sqlalchemy`를 가져와도 해당 패키지의 `clickhouse://`
등록은 그대로 유지됩니다. 설치된 다른 provider로 인해 ClickHouse Connect의 별칭을
등록할 수 없는 경우, import 시 명시적 ClickHouse Connect URL 사용을 권장하는
`UserWarning`이 발생합니다. 기존 런타임 등록은 경고 없이 그대로
유지됩니다. 다른 provider가 `clickhouse://`를 점유하고 있지 않다면, 이 import를 통해
해당 형식을 ClickHouse Connect 호환용 별칭으로 사용할 수 있습니다.

### ClickHouse 세션 ID {#sqlalchemy-session-ids}

동기(synchronous) 방언과 비동기(async) 방언 모두에서 풀의 각 연결은 기본적으로 고유한 ClickHouse 세션 ID를 생성합니다. 해당 연결의 요청이 동일한 ClickHouse 서버 프로세스에 도달하면 `SET`으로 변경한 설정과 임시 테이블이 그 연결에서 계속 유지됩니다. 이름이 지정된 세션의 상태와 동일 세션 중복 검사는 프로세스 내에서만 적용됩니다. 하나의 서버 프로세스에서 동일한 사용자와 세션 ID로 요청이 겹쳐 들어오면, 해당 요청은 큐에서 대기하지 않고 서버 코드 373과 함께 즉시 거부됩니다. 고정된 `session_id`를 구성하는 경우 `pool_size=1, max_overflow=0`을 사용하거나, 요청이 ClickHouse에 도달하기 전에 액세스를 직렬화하십시오. ClickHouse Cloud를 비롯한 로드 밸런싱 배포 환경에서는 동일한 세션 ID를 가진 요청이 서로 다른 서버로 전달될 수 있으므로, 고정된 `session_id`를 분산 상태나 분산 뮤텍스로 사용하지 마십시오.

### 비동기 연결 {#sqlalchemy-async-connections}

비동기 방언은 SQLAlchemy 2.0.44 이상이 필요하며, ClickHouse Connect의 네이티브 `AsyncClient`를 사용합니다. 필요한 의존성을 설치한 후 `clickhousedb+async://` URL로 비동기 엔진을 생성하세요.

```bash
pip install "clickhouse-connect[sqlalchemy-async]"
```

```python
import asyncio

from sqlalchemy import text
from sqlalchemy.ext.asyncio import create_async_engine


async def main():
    engine = create_async_engine(
        "clickhousedb+async://user:password@host:8123/mydb"
    )
    try:
        async with engine.connect() as conn:
            version = (await conn.execute(text("SELECT version()"))).scalar_one()
            print(version)
    finally:
        await engine.dispose()


asyncio.run(main())
```

결과는 버퍼링됩니다. 서버 측 커서(cursor)가 비활성화되어 있으므로 `AsyncConnection.stream()`을 호출하면 `InvalidRequestError`가 발생합니다. SQLAlchemy는 `AsyncSession.stream()` 호출을 허용하지만, 방언(dialect)이 전체 결과를 버퍼링한 후에 반환합니다. 대용량 결과를 처리하려면 네이티브 `AsyncClient` 스트리밍 메서드를 사용하십시오. SQLAlchemy 연결이 체크아웃되어 있는 동안에는 원시(raw) 네이티브 클라이언트에 `driver_connection`으로 접근할 수 있습니다.

```python
async def stream_events(engine):
    async with engine.connect() as conn:
        raw_connection = await conn.get_raw_connection()
        client = raw_connection.driver_connection
        async with await client.query_rows_stream("SELECT * FROM events") as rows:
            async for row in rows:
                print(row)
```

SQLAlchemy 연결과 해당 원시(raw) 클라이언트를 동시에 사용하지 마십시오. SQLAlchemy 연결 블록을 벗어나기 전에 원시 클라이언트 스트림을 완료하고, 연결이 풀로 반환된 후에는 원시 클라이언트를 계속 보관하지 마십시오. 빌려온 클라이언트의 수명 주기는 SQLAlchemy가 관리하므로 `client.close()`나 그 밖의 비공개 수명 주기 메서드를 절대 호출하지 마십시오. 연결 동시성은 SQLAlchemy의 풀이 관리합니다. 풀에 속한 각 연결은 하나의 네이티브 비동기 클라이언트를 소유하며, aiohttp 커넥터 제한은 기본적으로 전체 연결 1개, 호스트당 연결 1개로 설정됩니다. 이러한 전송 설정을 재정의하려면 URL 또는 `connect_args`에서 `connector_limit`, `connector_limit_per_host`, `keepalive_timeout`을 설정하십시오. `pool_pre_ping=True`를 사용하면 SQLAlchemy는 풀에서 연결을 체크아웃할 때 재사용되는 연결을 `SELECT 1`로 확인합니다.

현재 비동기 SQLAlchemy executemany 삽입은 드라이버의 Native 대량 삽입 프로토콜을 사용하지 않고 매개변수 세트마다 HTTP 요청을 하나씩 전송합니다. 따라서 이 방식은 소규모 배치에만 사용하십시오. 대량 데이터를 처리할 때는 앞서 설명한 풀 소유 `driver_connection` 접근 패턴을 사용하고, SQLAlchemy 연결을 풀에 반환하기 전에 `client.insert()`를 await하십시오. 비동기 executemany는 쿼리 매개변수 바인딩을 사용하므로, 시간대 정보가 없는(naive) `datetime` 값은 동기 Native executemany에서 사용하는 `naive_datetime_insert` 설정이 아니라 `naive_datetime_binding`을 따릅니다. 타입이 지정된 SQLAlchemy `DateTime64` 바인딩은 클라이언트 측 매개변수와 서버 측 매개변수 모두에서 소수 초를 보존합니다. 반면 `exec_driver_sql()`에 전달되는 타입이 지정되지 않은 `%s` 또는 `%(name)s` 매개변수는 naive `datetime` 값을 기본 방식대로 초 단위(소수점 이하 제외)로 포맷합니다. 시간대가 모호하지 않도록 하려면 시간대 정보가 포함된 값을 사용하십시오. Native 대량 삽입 방식이 필요하면 `client.insert()`를 사용하십시오.

비동기 엔진은 해당 엔진을 사용하는 이벤트 루프에서 생성하고 해제하십시오. 체크아웃한 모든 연결을 반환한 다음, 종료 시점 및 다른 이벤트 루프에서 엔진을 사용하기 전에 `engine.dispose()`를 await하십시오. 엔진을 소유한 루프가 이미 닫혔다면 재사용하기 전에 현재 루프에서 `engine.dispose()`를 await하십시오. 소유 루프가 닫힌 뒤에야 정리가 시작되면 aiohttp가 닫히지 않은 전송이 있다고 보고할 수 있으므로, 가능하면 엔진을 옮기기 전에 해제하십시오. 풀링된 비동기 엔진을 다른 이벤트 루프로 옮길 때 `pool_pre_ping=True`로 해제를 대신할 수는 없습니다. 루프에 바인딩된 연결을 남기지 않고 여러 이벤트 루프에서 하나의 엔진을 공유하려면 `poolclass=NullPool`을 설정하십시오. 연결이 아직 체크아웃된 상태에서 해제가 실행되면, 방언(dialect)은 해당 연결이 반환되거나 가비지 컬렉션될 때 연결을 닫습니다. 동기 코드에서는 `engine.sync_engine.dispose()`를 호출하지 마십시오. 이 경우 SQLAlchemy는 비동기 연결 정리를 await할 수 없으므로, 풀링된 전송을 닫지 못하고 오류만 로그로 남길 수 있습니다.

URL 쿼리 매개변수에는 ClickHouse 설정, `compression`, `query_limit`, 타임아웃과 같은 ClickHouse Connect 클라이언트 옵션, 또는 `ca_cert`와 같은 HTTP/TLS 옵션을 포함할 수 있습니다. 필요한 경우 ClickHouse 설정 앞에 `ch_`를 붙이면 해당 설정을 강제로 서버 설정으로 처리할 수 있습니다(예: `ch_http_max_field_name_size=99999`).

사용 가능한 클라이언트 옵션은 [연결 인수 및 설정](/ko/integrations/language-clients/python/driver-api#connection-arguments)을 참조하십시오.

DDL 및 검사(inspection)와 같은 동기 SQLAlchemy 헬퍼는 `AsyncConnection.run_sync()`를 통해 실행하십시오:

```python
from sqlalchemy import inspect


async def prepare_schema(engine, metadata):
    async with engine.begin() as conn:
        await conn.run_sync(metadata.create_all)
        return await conn.run_sync(
            lambda sync_conn: inspect(sync_conn).get_table_names()
        )
```

### 쿼리별 설정 {#sqlalchemy-per-query-settings}

SQLAlchemy 실행 옵션을 통해 ClickHouse 설정을 전달할 수 있습니다. 설정은 engine, connection 또는 statement에 지정할 수 있습니다. 동일한 키가 있는 경우 statement 값이 connection 또는 engine 값보다 우선합니다.

```python
from sqlalchemy import text

stmt = text("SELECT getSetting('max_threads')").execution_options(
    settings={"max_threads": 2}
)

with engine.connect() as conn:
    value = conn.execute(stmt).scalar_one()
```

### 쿼리별 읽기 포맷 {#sqlalchemy-per-query-read-formats}

SQLAlchemy 실행 옵션에서 `query_formats`를 사용해 엔진, 연결 또는 statement에 ClickHouse 읽기 포맷을 설정합니다. statement 포맷이 먼저 적용되므로 일치하는 연결 또는 엔진 키와 와일드카드보다 우선합니다.

```python
from sqlalchemy import text

stmt = text("SELECT user_uuid FROM users").execution_options(
    query_formats={"UUID": "string"}
)

with engine.connect() as conn:
    rows = conn.execute(stmt).all()
```

### 오류 처리 {#sqlalchemy-error-handling}

SQLAlchemy 연결을 통해 드라이버에서 발생하는 오류는 `clickhouse_connect.dbapi`에서 내보내는 DB-API 클래스를 사용합니다. 이 클래스들은 `clickhouse_connect.driver.exceptions`의 대응 클래스와 동일한 클래스 객체이므로, SQLAlchemy는 이를 해당하는 `sqlalchemy.exc.DBAPIError` 하위 클래스로 래핑합니다. `StreamFailureError`는 `OperationalError`의 일종이므로 `sqlalchemy.exc.OperationalError`로 래핑됩니다.

테이블이 존재하지 않으면 컬럼 검사와 테이블 리플렉션(Reflection) 시 `sqlalchemy.exc.NoSuchTableError` 예외가 발생합니다. 이 예외는 `sqlalchemy.exc.NoResultFound`도 상속하므로 기존 핸들러에서도 그대로 포착됩니다. 예외 메시지는 `Table <database>.<table_name> does not exist`입니다.

SQL 실행에는 드라이버의 [HTTP 재시도 정책](/ko/integrations/language-clients/python/driver-api#http-retries)이 적용됩니다. Native 대량 삽입에는 [삽입 재시도 정책](/ko/integrations/language-clients/python/advanced-inserting#insert-retries-and-deduplication)이 적용됩니다.

호출자 측의 취소로 인해 명시적으로 호출한 `AsyncConnection.invalidate()`가 중단될 수 있다면, 무효화를 별도로 소유한 작업(task)에서 실행하고, 취소를 전파하기 전에 해당 작업이 완료될 때까지 기다리십시오. 이렇게 하면 SQLAlchemy가 연결 레코드 정리 작업을 끝까지 마칠 수 있습니다:

```python
import asyncio


async def invalidate_safely(connection):
    invalidate_task = asyncio.create_task(connection.invalidate())
    cancellation = None
    while not invalidate_task.done():
        try:
            await asyncio.wait({invalidate_task})
        except asyncio.CancelledError as ex:
            cancellation = ex
    if cancellation is not None:
        try:
            invalidate_task.result()
        finally:
            raise cancellation
    invalidate_task.result()
```

무효화 작업이 아직 실행 중일 때는 연결을 사용하지 마십시오. 직접 호출한 `await connection.invalidate()`가 취소되어 `connection.invalidated`가 여전히 false라면, 연결을 사용하거나 닫기 전에 `connection.invalidate()`를 다시 await하여 정리를 완료하십시오.

### 서버 측 매개변수 {#sqlalchemy-server-side-parameters}

SQLAlchemy는 일반적으로 매개변수를 클라이언트 측에서 렌더링합니다. 엔진을 생성할 때 ClickHouse 서버 측 매개변수를 사용하도록 설정하십시오:

```python
engine = create_engine(
    "clickhousedb://user:password@host:8123/mydb",
    server_side_params=True,
)
```

비동기 방언에서는 `create_async_engine()`에 동일한 `server_side_params=True` 인수를 지정하십시오.

이 모드에서는 바인딩된 모든 값이 ClickHouse와 호환되는 SQLAlchemy 타입이어야 합니다. 지원되는 `IN` 목록은 타입이 지정된 ClickHouse `Array` 매개변수로 변환됩니다. 컴파일러는 호환되는 타입을 추론할 수 없거나 바인딩을 안전하게 처리할 수 없는 경우 `CompileError`를 발생시킵니다.

바인딩 이름은 ClickHouse ASCII BareWord 이름이어야 합니다. core driver가 원시 바이너리 쿼리 매개변수용으로 예약하므로 `$`로 시작하고 끝나는 이름은 거부됩니다.

## Core 쿼리 {#sqlalchemy-core-queries}

이 방언은 조인, 필터, 정렬, LIMIT 및 OFFSET, `DISTINCT`, 복합 SELECT를 포함한 SQLAlchemy Core `SELECT` 쿼리를 지원합니다.

SQLAlchemy `union()`, `intersect()`, `except_()`는 ClickHouse `UNION DISTINCT`, `INTERSECT DISTINCT`, `EXCEPT DISTINCT`로 컴파일됩니다. 이에 대응하는 `union_all()`, `intersect_all()`, `except_all()`은 해당 `ALL` 연산자로 컴파일됩니다. 이 명시적 매핑은 ClickHouse 집합 연산의 기본값과 관계없이 SQLAlchemy의 중복 처리 의미를 유지합니다.

```python
from sqlalchemy import MetaData, Table, select

metadata = MetaData(schema="mydb")
users = Table("users", metadata, autoload_with=engine)
orders = Table("orders", metadata, autoload_with=engine)
events = Table("events", metadata, autoload_with=engine)

stmt = (
    select(users.c.name, orders.c.product)
    .select_from(users.join(orders, users.c.id == orders.c.user_id))
    .order_by(users.c.name)
    .limit(10)
)

with engine.connect() as conn:
    rows = conn.execute(stmt).all()
```

명시적인 `WHERE` 절이 필요한 경량 `DELETE`를 지원합니다:

```python
from sqlalchemy import delete

stmt = delete(users).where(users.c.name.like("%temporary%"))
with engine.connect() as conn:
    conn.execute(stmt)
```

### 리터럴 렌더링 {#sqlalchemy-literal-rendering}

SQLAlchemy가 `literal_binds` 또는 `literal_execute`를 통해 바인딩된 값을 인라인으로 삽입하면, 방언은 일반 String 타입과 ClickHouse 타입에 ClickHouse 인용 규칙을 사용합니다. 이는 `TypeDecorator` 래퍼와 `with_variant()` 선택에도 적용됩니다. 다른 바인딩된 매개변수가 남아 있어도 문자열 값의 퍼센트 기호와 백슬래시는 유지됩니다.

ClickHouse `DateTime64` SQLAlchemy 타입이 지정된 Python `datetime` 값은 클라이언트 측 매개변수와 인라인 리터럴에서 마이크로초가 유지되며, 널 허용 값과 배열 및 튜플 안에 중첩된 값도 마찬가지입니다. 정밀도는 ClickHouse가 선언된 값에 따라 적용합니다. Python `datetime`은 소수점 이하 최대 6자리까지 제공합니다. 일반 `DateTime` 값은 초 단위 포맷이 그대로 유지됩니다. `text()` SQL 문에서 소수 초를 보존하려면 `bindparam("ts", type_=DateTime64(6))`와 같이 타입을 명시적으로 지정하십시오.

`DateTime64(9)`로 바인딩된 `pandas.Timestamp` 값은 매개변수와 인라인 리터럴에서 나노초가 유지됩니다.

SQLAlchemy 컬럼 타입은 서버 스키마와 일치해야 합니다. 서버의 `DateTime` 컬럼에 `DateTime64`를 선언하면 소수 초가 렌더링되어, 삽입 시와 `IN` 비교에서 변환 오류가 발생할 수 있습니다.

SQLAlchemy 2.x에서 ClickHouse `Tuple` 항목을 포함하는 일반 `sqlalchemy.ARRAY` 타입을 인라인 리터럴로 사용하려면 `dimensions=1`(중첩 배열이라면 그에 맞는 더 높은 차원 수)을 지정해야 SQLAlchemy가 각 튜플을 하나의 항목으로 처리합니다. SQLAlchemy 1.4는 일반 `ARRAY` 타입의 인라인 리터럴을 지원하지 않습니다.

타입이 지정된 named `Tuple` 매개변수에는 키가 선언된 필드와 정확히 일치하는 딕셔너리를 전달할 수 있습니다. 클라이언트는 바인딩된 매개변수와 인라인 리터럴에서 선언된 필드 순서를 따르며, 배열이나 다른 튜플 안에 있는 named tuple에도 동일하게 적용됩니다. 이는 동기 삽입과 비동기 삽입, 조건자, 두 가지 매개변수 모드 모두에 적용됩니다. 필드가 누락되거나 불필요한 필드가 있으면 쿼리 매개변수(query parameter) 바인딩 시 `ProgrammingError`가 발생합니다. Native 대량 삽입은 기존 처리 방식을 그대로 유지합니다. 타입이 지정되지 않은 `exec_driver_sql()` 매개변수에 전달된 딕셔너리는 설정된 JSON 또는 맵 서식을 그대로 따릅니다.

`Map` 값 안의 named tuple을 사용하려면 `common.set_setting("dict_parameter_format", "map")`을 설정하십시오. 이렇게 하면 바인딩된 매개변수와 인라인 리터럴에서 맵 안에 있는 타입이 지정된 `DateTime64` 값의 소수 초도 보존됩니다.

이름이 지정된 datetime 매개변수를 재사용할 때 소수 부분을 보존하려면, 해당 매개변수가 사용되는 모든 위치에 호환되는 `DateTime64` 바인드 타입을 지정해야 합니다. 타입이 지정되지 않은 위치가 있거나 타입이 충돌하면 초 단위 포맷이 유지됩니다. 각 `bindparam`에 `type_=DateTime64(6)`를 설정하거나, 서로 다른 매개변수 이름을 사용하여 각각 적절한 타입을 지정하십시오.

재사용된 바인드 이름에서 named `Tuple`이 사용되는 위치마다 서로 다른 필드 이름을 선언한 경우에도 마찬가지입니다. 이때 클라이언트는 해당 이름을 위치 기반으로 처리하므로 딕셔너리 값의 순서가 재정렬되지 않고, 서버에서 이를 거부합니다. 서로 다른 매개변수 이름을 사용하거나 위치 기반 튜플을 전달하십시오.

### 이름이 지정된 Tuple {#sqlalchemy-named-tuples}

named tuple 필드는 `elements` 매핑으로 선언합니다. 키는 비어 있지 않은 문자열이어야 하며, 값으로는 ClickHouse SQLAlchemy 타입 클래스나 구성된 인스턴스를 지정할 수 있습니다. 필드는 매핑의 순회 순서를 그대로 유지하며, 이름은 자동으로 인용 부호로 감싸집니다.

```python
from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import String, Tuple, UInt32

details_type = Tuple(elements={"user_id": UInt32, "display name": String()})
# Tuple(`user_id` UInt32, `display name` String)
```

이름이 없는 튜플(tuples)에는 `Tuple(UInt32, String)` 또는 `Tuple(elements=[UInt32, String])`을 사용하십시오. 위치 기반 원소와 `elements` 키워드는 함께 사용할 수 없습니다.

### JSON 타입 힌트 {#sqlalchemy-json-type-hints}

`typed_paths` 매핑으로 타입이 지정된 JSON 경로를 선언합니다. 경로 타입에는 ClickHouse SQLAlchemy 타입 클래스, 구성된 인스턴스, 또는 ClickHouse 타입 이름 문자열을 사용할 수 있습니다. 타입 이름 문자열은 `Dynamic`처럼 SQLAlchemy 생성자가 없는 타입도 지원하며, 복잡하게 구성된 타입 표현식에도 그대로 사용할 수 있습니다.

타입 이름 문자열에는 ``Array(JSON(`child` UInt32))``처럼 구성된 중첩 JSON 타입을 포함할 수 있습니다. 이러한 문자열에서 인식되는 ClickHouse 타입 이름은 대소문자를 구분하지 않으며, 정규 대소문자 표기로 출력됩니다. 문자열에는 완전한 타입 표현식이 하나만 포함되어야 합니다. 뒤에 남은 텍스트나 형식이 잘못된 중첩 JSON 인수는 거부됩니다.

빈 `Tuple()`은 ClickHouse가 JSON 컬럼의 Native 형식으로 이를 serialize할 수 없으므로 JSON의 타입이 지정된 경로로는 지원되지 않습니다. core driver는 쿼리 및 삽입 컬럼의 모든 위치에서 `Tuple()`을 지원하며, positional 또는 named tuple 내부에 중첩된 경우, `Array` 내부, 그리고 서버에서 활성화된 경우의 `Nullable(Tuple())` 형태가 여기에 포함됩니다.

```python
from sqlalchemy import Column, MetaData, Table

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import JSON, UInt32

events = Table(
    "events",
    MetaData(),
    Column(
        "payload",
        JSON(
            typed_paths={
                "event.id": UInt32,
                "details": "Tuple(id UInt32, label Nullable(String))",
                "attributes": "Variant(String, Array(String))",
            },
            max_dynamic_paths=256,
            max_dynamic_types=16,
            skip_paths=["internal.debug"],
            skip_regexps=[r"^private\."],
        ),
    ),
)
```

단순한 Python 식별자 경로의 경우, 키워드 인수는 `typed_paths`의 축약 표기입니다. 예를 들어 `JSON(user_id=UInt32)`와 같습니다. 점이 포함된 경로, 공백, 백틱, `%2E`로 인코딩된 점, 또는 생성자 옵션과 이름이 겹치는 경우에는 `typed_paths`를 사용하십시오. `SKIP`이라는 이름의 타입이 지정된 경로도 이 매핑을 통해 지원됩니다. `typed_paths`의 키와 `skip_paths`의 값은 디코딩된 이름입니다. 앞뒤에 오는 백틱과 큰따옴표는 미리 적용된 SQL 인용 부호가 아니라 리터럴 경로 문자로 처리됩니다. 원시 타입 문자열 내부에서는 백틱과 큰따옴표가 ClickHouse 식별자 구문으로 해석됩니다.

타입이 지정된 경로는 최대 1000개까지 구성할 수 있습니다. `max_dynamic_paths`는 0에서 10000까지, `max_dynamic_types`는 0에서 254까지 허용합니다. 이 범위는 중첩된 원시 JSON 타입 문자열 내부에도 동일하게 적용됩니다. 명시적인 서버 기본값인 1024와 32는 생성된 DDL에서 생략됩니다. 일반 스킵 경로는 중복이 제거됩니다. 정규식 문자열은 ClickHouse가 RE2 구문을 사용하므로 Python에서 검사하지 않습니다. 중복된 정규식은 그대로 유지됩니다.

ClickHouse가 `SKIP REGEXP`를 위해 해당 토큰을 예약해 두었으므로, 일반 스킵 경로의 이름을 정확히 `REGEXP`로 지정할 수 없습니다. 반면 `REGEXP_foo`와 같은 이름은 유효합니다. 원시 JSON 타입 문자열에서 일반 `SKIP` 피연산자는 하나의 ClickHouse 식별자이거나 점으로 구분된 복합 식별자여야 합니다. 인용되지 않은 복합 식별자는 `REGEXP`로 시작할 수 없으며, 첫 번째 구성 요소가 경로 데이터라면 해당 부분을 인용 부호로 묶으십시오. `SKIP REGEXP`에는 작은따옴표로 묶인 문자열 리터럴이 하나 있어야 합니다. 식별자 부분에 공백이나 구두점이 포함된 경우 백틱이나 큰따옴표로 묶으십시오. 원시 JSON 타입 힌트는 `Variant(...)`를 지원하며, 단독 `Variant`에는 공개 SQLAlchemy 생성자가 없습니다. `Variant` 멤버는 ClickHouse가 사용하는 것과 동일한 정규 이름을 기준으로 정렬되고 중복이 제거됩니다.

생성자는 ClickHouse가 반환하는 것과 동일한 정규 형식으로 인수를 정렬합니다. 리플렉션된 타입, SQLAlchemy 타입 복사본, Alembic 자동 생성은 이 구성을 그대로 보존합니다.

### JSON 서브컬럼 {#sqlalchemy-json-subcolumns}

ClickHouse `JSON`으로 선언되었거나 반영된 컬럼에서 스토리지 기반 서브컬럼 경로의 세그먼트를 한 번에 하나씩 선택하려면 대괄호를 사용합니다:

```python
from sqlalchemy import Column, MetaData, Table, select

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import JSON, UInt32

events = Table(
    "events",
    MetaData(),
    Column("payload", JSON),
)

request_id = events.c.payload["context"]["request"].subcolumn(
    "id",
    type_=UInt32,
)

stmt = select(
    events.c.payload["severity"].label("severity"),
    request_id.label("request_id"),
)
```

`payload["severity"]`는 ClickHouse의 점 표기 식별자 구문으로 컴파일됩니다. 각 부분은 개별적으로 인용되며, 예를 들어 `` `events`.`payload`.`severity` ``와 같습니다. ClickHouse에 저장된 JSON 하위 컬럼을 읽으며 `getSubcolumn`은 호출하지 않습니다. 각 경로 세그먼트에 대해 `[]` 또는 `.subcolumn()`을 한 번씩 연결하십시오. 각 세그먼트는 비어 있지 않은 문자열이어야 합니다.

`.subcolumn()`에 `type_`을 전달하면 점 표기 경로가 SQL `CAST`로 감싸지고 해당 타입이 SQLAlchemy 표현식에 할당됩니다. `type_`이 없으면 `.subcolumn("segment")`는 `["segment"]`와 동일하게 동작합니다.

타입이 지정되지 않은 경로는 ClickHouse의 `Dynamic` 타입을 갖습니다. ClickHouse에서는 `Dynamic` 값을 `ORDER BY` 또는 `GROUP BY`에 직접 사용할 수 없습니다. 이러한 위치에서 하위 컬럼을 사용하려면 `type_`을 전달하십시오.

정적으로 타입이 지정된 코드에서는 `clickhouse_connect.cc_sqlalchemy`에서 `json_subcolumn`을 가져오십시오. 이 도우미 함수도 한 번에 하나의 세그먼트를 받으며 `type_`의 Python 결과 타입을 유지합니다:

```python
from clickhouse_connect.cc_sqlalchemy import json_subcolumn

context = json_subcolumn(events.c.payload, "context")
request = json_subcolumn(context, "request")
request_id = json_subcolumn(request, "id", type_=UInt32)
```

이 예시에서 타입 검사기는 `request_id`를 `ColumnElement[int]`로 봅니다.

공백이나 백틱이 포함된 이름을 비롯해 각 세그먼트는 각각 따옴표로 묶습니다. 백틱을 사용해도 ClickHouse JSON 경로 처리에서 점이 리터럴로 해석되지는 않습니다. `json_type_escape_dots_in_keys`가 활성화된 경우 키의 리터럴 점에는 ClickHouse의 `%2E` 인코딩을 사용하십시오. `a.b`라는 키에는 `payload["a%2Eb"]`로 접근하고, `payload["a.b"]`는 사용하지 마십시오.

### ClickHouse 쿼리 확장 기능 {#sqlalchemy-query-extensions}

정적 타입 검사기가 타입이 지정된 ClickHouse 메서드를 인식할 수 있도록 `clickhouse_connect.cc_sqlalchemy`에서 `select`를 가져오십시오. 표준 `sqlalchemy.select`도 런타임에 이러한 메서드를 제공합니다.

```python
from clickhouse_connect.cc_sqlalchemy import select

stmt = (
    select(events.c.user_id, events.c.event_type)
    .final()
    .prewhere(events.c.event_date >= "2026-01-01")
    .sample(0.1)
    .limit_by([events.c.user_id], 3)
)
```

ClickHouse `Select` 메서드는 다음과 같습니다:

| 메서드                                      | SQL 기능                                                                |
| ---------------------------------------- | --------------------------------------------------------------------- |
| `.final()`                               | 테이블에 적용되는 `FINAL`                                                     |
| `.sample(value)`                         | 분수, 행 수 또는 표현식을 사용하는 `SAMPLE`                                         |
| `.prewhere(expression)`                  | `PREWHERE`; 여러 번 호출하면 `AND`로 결합됩니다                                    |
| `.limit_by(columns, limit, offset=None)` | `LIMIT ... BY`                                                        |
| `.array_join(...)`                       | `ARRAY JOIN`                                                          |
| `.left_array_join(...)`                  | `LEFT ARRAY JOIN`                                                     |
| `.ch_join(...)`                          | `strictness`, `distribution`, `using`, `cross` 옵션을 지원하는 ClickHouse 조인 |
| `.cte(name, materialized=True)`          | `WITH name AS MATERIALIZED (...)`                                     |

SQLAlchemy의 `Select.with_hint()`는 테이블 힌트 API입니다. ClickHouse 방언은 테이블 힌트를 렌더링하지 않습니다. 적용되는 와일드카드 또는 `clickhousedb` 힌트는 `SAWarning`을 발생시키며 생성된 SQL은 변경되지 않습니다. 해당 ClickHouse 절에는 `final()`, `sample()`, `prewhere()` 또는 `limit_by()`를 사용하십시오.

`Select.with_statement_hint()`는 원시 후행 지시문 API입니다. ClickHouse 전용 유효성 검사 없이 제공된 텍스트를 `SELECT` 끝에 추가합니다. `SETTINGS max_threads=1`과 같은 신뢰할 수 있는 정적 SQL에 계속 사용할 수 있습니다:

```python
stmt = select(events.c.id).with_statement_hint("SETTINGS max_threads=1")
```

ClickHouse 설정에는 드라이버가 SQL 텍스트와 별도로 설정을 처리할 수 있도록 실행 옵션을 사용하는 것이 좋습니다:

```python
stmt = select(events.c.id).execution_options(settings={"max_threads": 1})
```

예를 들어, ClickHouse `GLOBAL ANY LEFT JOIN`은 사용자 정의 `FromClause`를 중첩하지 않고 체이닝할 수 있습니다:

```python
stmt = (
    select(events.c.id, users.c.name)
    .select_from(events)
    .ch_join(
        users,
        events.c.user_id == users.c.id,
        isouter=True,
        strictness="ANY",
        distribution="GLOBAL",
    )
)
```

ClickHouse 고차 함수에서는 명시적 `Lambda` 구문을 사용하십시오:

```python
from sqlalchemy import column, func

from clickhouse_connect.cc_sqlalchemy import Lambda, select

stmt = select(
    func.arrayMap(
        Lambda("x", column("x") * 2),
        events.c.metrics,
    ).label("doubled")
)
```

표준 SQLAlchemy `values()` 구문은 공통 테이블 표현식(CTE)에서 사용할 때를 포함해 ClickHouse의 `VALUES` 테이블 함수 구문으로 컴파일됩니다. CTE 형식에는 `Values.cte()`가 추가된 SQLAlchemy 2.0.42 이상이 필요합니다.

### 구체화된 CTE {#sqlalchemy-materialized-ctes}

기본적으로 ClickHouse는 공통 테이블 표현식(CTE)을 인라인하므로, CTE를 두 번 이상 참조하면 참조할 때마다 본문이 한 번씩 실행됩니다. `.cte()`에 `materialized=True`를 전달하면 `WITH <name> AS MATERIALIZED (...)`가 생성되어 본문을 한 번만 계산합니다:

```python
from sqlalchemy import func

from clickhouse_connect.cc_sqlalchemy import select

ranked = (
    select(book.c.book_id, func.row_number().over(order_by=book.c.score.desc()).label("result_rank"))
    .where(book.c.genre == "sci-fi")
    .order_by(book.c.score.desc())
    .limit(100)
    .cte("ranked", materialized=True)
)

stmt = (
    select(book.c.book_id, ranked.c.result_rank)
    .select_from(book)
    .ch_join(ranked, book.c.book_id == ranked.c.book_id, strictness="ANY")
    .where(book.c.book_id.in_(select(ranked.c.book_id)))
    .execution_options(settings={"enable_materialized_cte": 1, "enable_analyzer": 1})
)
```

서버는 키워드가 있고 `enable_materialized_cte=1`로 설정되어 있으며 분석기가 활성화된 경우에만 CTE를 구체화합니다. [쿼리별 설정](#sqlalchemy-per-query-settings)에 나온 대로 statement, connection 또는 engine에 `enable_materialized_cte`를 설정하십시오. 이 기능을 지원하는 모든 서버에서는 분석기가 기본적으로 활성화되므로 `enable_analyzer=1`을 명시적으로 설정하는 것은 방어적 조치입니다. `enable_materialized_cte`는 Experimental ClickHouse 설정입니다. `enable_materialized_cte=0` 또는 `enable_analyzer=0`이면 쿼리는 성공하고 동일한 행을 반환합니다. ClickHouse는 아무런 알림 없이 `MATERIALIZED`를 무시하고 CTE를 다시 인라인 처리하므로, 설정을 빠뜨리면 오류 없이 성능이 저하됩니다. Materialized CTE를 사용하려면 ClickHouse 26.3 이상이 필요합니다. 이전 서버에서는 해당 키워드를 구문 오류로 처리합니다.

표준 `sqlalchemy.select`로 작성한 statement에는 모듈 수준의 `cte()`를 대신 사용하십시오. 이 함수는 첫 번째 인수로 statement를 받고, 그 외에는 `Select.cte()`와 동일하게 동작합니다:

```python
from sqlalchemy import select as sa_select

from clickhouse_connect.cc_sqlalchemy import cte

ranked = cte(sa_select(book.c.book_id), "ranked", materialized=True)
```

이 키워드는 ClickHouse 방언에서만 렌더링되므로, 다른 backend와 공유되는 statement는 해당 backend에서 변경 없이 컴파일됩니다.

ClickHouse는 재귀적 구체화된 CTE를 지원하지 않습니다. `recursive=True`와 `materialized=True`가 모두 설정되면 SQLAlchemy 헬퍼에서 `ValueError`를 발생시킵니다.

## DDL 및 리플렉션 {#sqlalchemy-ddl-reflection}

ClickHouse Connect는 ClickHouse 데이터 타입, 테이블 엔진, 딕셔너리 구문, 데이터베이스 DDL 및 테이블 리플렉션을 제공합니다.

`Inspector.get_table_names()`는 호환성을 위해 모든 종류의 뷰를 포함합니다. `MetaData.reflect()`도 기본적으로 뷰를 포함하며, `only`를 사용하면 이름으로 특정 뷰를 선택할 수 있습니다. 구체화되지 않은 뷰에는 `Inspector.get_view_names()`를, materialized view에는 `Inspector.get_materialized_view_names()`를 사용하십시오. 두 메서드 모두 `schema`를 인수로 받으며, 2.x를 포함한 SQLAlchemy 1.4.40 이상에서 동작합니다. `Inspector.get_view_definition()`은 뷰 또는 materialized view에 저장된 `SELECT`를 반환하며, 테이블이거나 존재하지 않는 이름이면 `NoSuchTableError`를 발생시킵니다. 리플렉션된 뷰에는 엔진이 없습니다. 해당 뷰의 `Table`에는 `view`, `materialized_view`, `window_view`, `live_view` 중 하나로 설정된 `clickhousedb_table_type`이 포함됩니다.

`clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes`의 `Nullable()` 및 `LowCardinality()`는 ClickHouse SQLAlchemy 타입 클래스 또는 인스턴스를 인수로 받으며, 타입 검사 도구가 구체 타입을 그대로 인식할 수 있도록 유지합니다. 예를 들어 `Nullable(String)`은 `String` 인스턴스를 반환하므로 `Column`에 바로 전달할 수 있습니다. 타입 검사 도구는 `[Nullable(String)]`의 타입을 `list[String]`으로 추론합니다. 리스트에 다른 ClickHouse 타입도 포함되어 있다면 `clickhouse_connect.cc_sqlalchemy.datatypes.base`에서 `ChSqlaType`을 가져온 다음 리스트에 `list[ChSqlaType]` 타입 어노테이션을 지정하십시오.

단독 `Variant` 컬럼은 SQLAlchemy 내부 타입을 통해 리플렉션되며, Alembic 자동 생성은 반복적인 타입 변경 없이 해당 컬럼의 정규 원시 타입 이름을 유지합니다. `Geometry` 및 `MultiPoint` 컬럼은 공개 SQLAlchemy 타입으로 리플렉션됩니다.

```python
import sqlalchemy as db
from sqlalchemy import MetaData

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import DateTime64, String, UInt32
from clickhouse_connect.cc_sqlalchemy.ddl.custom import CreateDatabase
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import MergeTree

with engine.connect() as conn:
    conn.execute(CreateDatabase("example_db", exists_ok=True))

    metadata = MetaData(schema="example_db")
    events = db.Table(
        "events",
        metadata,
        db.Column("id", UInt32, primary_key=True),
        db.Column("user", String),
        db.Column("created_at", DateTime64(3)),
        MergeTree(order_by="id"),
    )
    events.create(conn)

    reflected = db.Table("events", MetaData(schema="example_db"), autoload_with=conn)
    assert reflected.engine is not None
```

리플렉션된 컬럼에는 `DEFAULT` 표현식용 `server_default`가 포함됩니다. 리플렉션된
SQLAlchemy 객체는 해당 옵션이 있는 경우 `clickhousedb_codec`,
`clickhousedb_ttl`, `clickhousedb_materialized`, `clickhousedb_alias` 같은 방언별 옵션을 사용합니다.
`Inspector.get_columns()`가 반환하는 공개 딕셔너리에는
해당하는 `clickhouse_*` 키가 그대로 유지됩니다. 이 딕셔너리에서 `server_default`,
`clickhouse_materialized`, `clickhouse_alias`, `clickhouse_ttl` 값은 SQL 문자열입니다.
이 값으로 `Column`을 생성하려면 각 값을 `sqlalchemy.text()`로 감싸십시오.

새 테이블 및 컬럼 선언에는 `clickhousedb_*`를 사용하십시오. 드라이버가 생성하는
메타데이터와 Alembic revision에서도 이 이름을 사용합니다. ClickHouse Connect는 명시적으로 지정된
레거시 `clickhouse_*` 옵션도 읽지만, SQLAlchemy는 이 옵션을 `clickhouse`를 소유한
방언을 기준으로 검사합니다. 여러 방언이 함께 설치된 환경에서는 `clickhouse_engine`, `clickhouse_ttl`, `clickhouse_settings`,
`clickhouse_table_type`, `clickhouse_dictionary_*` 같은 ClickHouse Connect 옵션에서 `ArgumentError`가 발생할 수 있습니다.
이러한 옵션의 이름을 `clickhousedb_*`로 변경하십시오.

ClickHouse Connect는 `clickhousedb`에서만 기본값을 읽습니다. 기본값은
`Table.argument_for("clickhousedb", ...)` 또는
`Column.argument_for("clickhousedb", ...)`로 등록하십시오. `op.add_column(..., clickhouse_settings={...})`와 같은
Alembic 작업 인수는 기존 이름을 그대로 유지합니다.

`DEFAULT`, `MATERIALIZED`, `ALIAS`, `TTL` 절의 문자열 값에는 ClickHouse 문자열 이스케이프가 사용됩니다. Alembic에서 생성된 주석을 포함하여 테이블, 딕셔너리, 컬럼 주석에도 동일한 이스케이프가 적용됩니다.

`order_by`, `partition_by`, `primary_key`, `sample_by`, `ttl` 등의 MergeTree 키 인수는 일반 문자열은 물론 SQLAlchemy 컬럼과 SQL 표현식도 받을 수 있습니다.

`Memory()`, `Log()`, `StripeLog()`, `TinyLog()`, `Null()`, `Set()`은 인수 없이 사용할 수 있으며, Alembic 자동 생성을 거쳐도 변경 없이 그대로 유지됩니다. 기존 딕셔너리 인수도 계속 지원됩니다. 엔진 설정을 지정하려면 `settings={...}`를 사용하십시오.

`SummingMergeTree`와 `ReplicatedSummingMergeTree`는 키워드로만 지정할 수 있는 선택적 `columns` 인수를 지원합니다. 기존 위치 인수의 의미는 그대로 유지되므로 `SummingMergeTree("id")`는 여전히 `ORDER BY id`를 설정합니다.

```python
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import SummingMergeTree

engine_clause = SummingMergeTree("id", columns=("delta", "n_tx"))
# Sum delta and n_tx for rows with the same id.
```

문자열, SQLAlchemy 컬럼, 매핑된 컬럼 속성 또는 이러한 값으로 구성된 비어 있지 않은 리스트나 튜플을 전달하세요. 리스트 및 튜플의 문자열 항목은 식별자로 인용됩니다. 스칼라 문자열은 `"delta"` 또는 `"(delta, n_tx)"`와 같은 원시 SQL(Raw SQL)로 전달됩니다. 서버는 이러한 컬럼을 식별자로 지정해야 합니다. `columns`를 생략하면 ClickHouse가 합산할 컬럼을 선택합니다. 리플렉션과 Alembic 자동 생성은 명시적으로 지정된 컬럼 목록을 유지합니다.

## 삽입 및 기본 ORM 사용 {#sqlalchemy-inserts}

Core 삽입과 간단한 ORM 모델이 지원됩니다. 동기 방언에서는 호환되는 대량 데이터 처리에 Core executemany 삽입을 우선적으로 사용하십시오. 비동기 대량 삽입에는 [비동기 연결](#sqlalchemy-async-connections)에 설명된 네이티브 `AsyncClient.insert()` 경로를 사용하십시오.

```python
with engine.connect() as conn:
    conn.execute(
        events.insert(),
        [
            {"id": 13, "user": "user_1"},
            {"id": 79, "user": "user_2"},
        ],
    )
```

동기 방언에서는 SQLAlchemy 컴파일러가 생성한 일반 Core `executemany` 삽입이 한 번의 Native 대량 삽입(bulk insert)으로 처리됩니다. 비동기 executemany는 [비동기 연결](#sqlalchemy-async-connections)에 설명된 대로 매개변수 집합마다 요청을 하나씩 전송합니다. Raw SQL, 그리고 표현식이나 안전하게 라우팅할 수 없는 기타 의미 체계를 포함하는 삽입은 원래 SQL을 그대로 유지한 채 매개변수 집합마다 한 번씩 실행됩니다. 이때 뒤쪽 매개변수 집합이 실패하더라도 앞선 매개변수 집합으로 기록된 행은 커밋된 상태로 남습니다.

명시적인 다중 행 `insert(events).values([...])` SQL 문에는 딕셔너리 형태의 행, 테이블 컬럼 순서를 따르는 튜플, 행별 SQL 표현식을 사용할 수 있습니다. Pandas `to_sql(method="multi")`도 이 형식을 사용합니다. 이 방식은 행을 정상적으로 삽입하지만, 텍스트 형식의 INSERT 문은 DB-API 커서를 통해 행 수를 `0`으로 보고하므로 반환값은 `0`입니다. SQLAlchemy는 첫 번째 행을 기준으로 컬럼 목록을 결정합니다. 따라서 이후 행에 추가로 포함된 딕셔너리 키나 선택된 컬럼 목록을 벗어나는 튜플 값은 무시됩니다. 반대로 이후 행에 선택된 컬럼의 값이 없으면 컴파일이 실패합니다. 모든 행에 동일한 컬럼을 지정하십시오.

ClickHouse 26.4 이상의 기본 HTTP 폼 제한에서는 `server_side_params=True`가 소규모 명시적 배치에만 적합하며, 다른 필드를 위한 여유분을 고려하면 바인드 값은 약 1000개 미만이어야 합니다. 이 상한은 서버 구성으로 높일 수 있습니다. 동기 방언으로 대규모 일반 배치를 처리하려면 드라이버가 Native 대량 삽입 경로를 사용할 수 있도록 행을 `execute()`의 두 번째 인수로 전달하십시오. 비동기 방식으로 대량 데이터를 처리하려면 네이티브 `AsyncClient.insert()` 메서드를 await하십시오.

```python
import sqlalchemy as db
from sqlalchemy import MetaData
from sqlalchemy.orm import Session, declarative_base

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import String, UInt32
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import MergeTree

Base = declarative_base(metadata=MetaData(schema="example_db"))


class User(Base):
    __tablename__ = "users"
    __table_args__ = (MergeTree(order_by=["id"]),)

    id = db.Column(UInt32, primary_key=True)
    name = db.Column(String)


Base.metadata.create_all(engine)

with Session(engine) as session:
    session.add(User(id=13, name="user_1"))
    session.bulk_save_objects([User(id=79, name="user_2")])
    session.commit()
```

## 뷰와 SQL 함수 {#sqlalchemy-views-functions}

Alembic은 일반 뷰(view)와 SQL 사용자 정의 함수(user-defined function)를 생성, 교체, 삭제할 수 있는 명시적 헬퍼를 제공합니다:

```python
from alembic import op

op.create_clickhouse_view("active_events", "SELECT id FROM analytics.events", schema="analytics")
op.create_clickhouse_view("active_events", "SELECT id FROM analytics.events WHERE id > 13", schema="analytics", or_replace=True)
op.drop_clickhouse_view("active_events", schema="analytics", if_exists=True)

op.create_clickhouse_function("analytics_increment_v1", "(value) -> value + 13")
op.create_clickhouse_function("analytics_increment_v1", "(value) -> value + 79", or_replace=True)
op.drop_clickhouse_function("analytics_increment_v1", if_exists=True)
```

두 create 헬퍼 모두 `if_not_exists=False`와 `or_replace=False`를 인수로 받습니다. 두 값을 모두 `True`로 전달하면 `ValueError`가 발생합니다. SQL 본문은 ClickHouse에 그대로 전달되는 문자열입니다. 이름은 이미 인용 부호로 감싸져 있지 않으면 식별자(identifiers)로 취급되어 인용 부호로 감싸집니다. 함수 이름은 점이 포함되어 있더라도 하나의 식별자로 취급됩니다. SQL 함수는 서버 전역(server-global)으로 적용되므로 함수 헬퍼와 검사 메서드에는 `schema` 인수가 없습니다. 여러 데이터베이스와 마이그레이션(migration) 스트림에 걸쳐 전역적으로 고유하거나 버전이 명시된 함수 이름을 사용하십시오. 이러한 연산(Operations)은 온라인 실행과 오프라인 SQL 렌더링을 모두 지원하며, `run_sync`를 통한 async SQLAlchemy 연결도 지원합니다.

`or_replace=True`는 대체를 명시적으로 요청합니다. ClickHouse는 기존 테이블이나 materialized view를 같은 이름의 일반 뷰(view)로 대체할 수 있으며, 이때 이전 객체의 데이터는 폐기됩니다. `DROP VIEW`는 기반 테이블에는 적용되지 않지만 materialized view는 삭제할 수 있습니다. `IF NOT EXISTS`는 기존 정의를 변경하지 않고 그대로 두며, 그 정의를 검증하지도 않습니다. 대체나 조건부 생성으로는 안전한 다운그레이드를 추론할 수 없으므로, 이전 정의를 사용하여 다운그레이드를 직접 작성하십시오. 삭제 작업에도 다운그레이드 정의를 명시적으로 작성해야 합니다. 정의를 복원하더라도 폐기된 데이터는 복원되지 않습니다. SQL 함수를 대체하려면 `CREATE FUNCTION` 권한과 `DROP FUNCTION` 권한이 모두 필요합니다.

ClickHouse는 뷰 정의(view definition)를 저장할 때 SQL UDF 호출을 전개합니다. 따라서 SQL UDF를 대체해도 이를 사용하는 기존 뷰에는 반영되지 않습니다. 새 정의를 적용하려면 해당 뷰를 재생성하거나 명시적으로 변경하십시오.

일반 뷰는 기존 `get_view_names(schema=...)` 및 `get_view_definition(name, schema=...)` 메서드로 검사합니다. SQL 함수 검사는 ClickHouse 방언에서만 제공되는 기능입니다:

```python
from sqlalchemy import inspect

inspector = inspect(connection)
names = inspector.get_clickhouse_function_names()
create_sql = inspector.get_clickhouse_function_definition("analytics_increment_v1")
```

함수 검사에는 `SQLUserDefined` 함수만 포함되며, 내장 함수와 실행형 함수는 제외됩니다. 이름은 정렬된 상태로 반환됩니다. 정의는 람다 body만이 아니라 저장된 `CREATE FUNCTION` SQL 문 전체이며, 존재하지 않는 이름을 조회하면 `sqlalchemy.exc.NoResultFound` 예외가 발생합니다. 카탈로그(Catalog) 액세스 오류는 그대로 전파됩니다. 사용자 쿼리 포맷이 바이트를 요청하더라도 메타데이터 검사 결과는 텍스트로 유지됩니다. 이 헬퍼는 선언적 뷰(view)나 함수 엔터티, autogenerate 비교, 의존성 기반 순서 지정 기능을 제공하지 않습니다. 명시적 마이그레이션(migration) 연산은 의존성 순서대로 배치하고, 이를 렌더링할 때는 `render_as_batch=False`를 사용하십시오.

## 데이터 스키핑 인덱스 {#sqlalchemy-skip-indexes}

ClickHouse 데이터 스키핑 인덱스는 테이블 인수로 선언합니다. 이 API는 SQLAlchemy가 필요하지만 Alembic 없이도 동작합니다:

```python
from sqlalchemy import Column, MetaData, Table, inspect
from clickhouse_connect.cc_sqlalchemy import ClickHouseIndex, engines, types

metadata = MetaData()
events = Table(
    "events",
    metadata,
    Column("value", types.UInt32),
    Column("label", types.String),
    ClickHouseIndex("value_idx", "value", "minmax"),
    ClickHouseIndex("label_idx", "label", "bloom_filter(0.01)", granularity=4),
    engines.MergeTree(order_by="value"),
)
metadata.create_all(engine)

indexes = inspect(engine).get_clickhouse_indexes("events")
```

인덱스 표현식과 타입은 원시 ClickHouse SQL로 작성합니다. 정의는 변경할 수 없으며, 이름은 테이블 내에서 고유해야 합니다. 선언은 `clickhousedb_indexes` 테이블 옵션에 저장되며, 이 옵션에는 `ClickHouseIndex` 정의의 시퀀스도 지정할 수 있습니다. `Table.to_metadata()`는 이 정의를 그대로 유지하며, `CREATE TABLE`은 이를 인라인으로 렌더링합니다. `if_not_exists`, `first`, `after_index`는 명령형 ALTER 헬퍼에서 계속 사용할 수 있지만, 인라인 생성이나 스키마(schema) 비교에는 영향을 주지 않습니다.

`Inspector.get_clickhouse_indexes()`는 명시적으로 정의된 인덱스에 대해 재적용 가능한 정의를 반환합니다. 리플렉션된 표현식은 중첩된 튜플을 포함한 ClickHouse의 인덱스 표현식 목록을 보존하기 위해 `tuple(...)` 래퍼를 사용합니다. 서버가 생성한 암시적 인덱스는 카탈로그(Catalog)의 `creation` 필드를 기준으로 제외됩니다. 카탈로그 오류가 발생하거나 알 수 없는 분류가 있으면 오류가 발생합니다. 카탈로그는 `creation` 필드를 제공해야 합니다. ClickHouse 릴리스 노트에 따르면 이 필드는 26.1.1.912 및 25.12.2.54 백포트에서 문서화되었습니다. 호환성은 버전 문자열이 아니라 실제 쿼리를 통해 검사합니다.

일반 `Inspector.get_indexes()`는 여전히 빈 목록을 반환합니다. `Table(..., autoload_with=engine)`은 skip-index 카탈로그를 읽지 않습니다. 컬럼과 인덱스를 모두 명시적으로 복사하려면 다음과 같이 하십시오.

```python
inspector = inspect(engine)
reflected = Table(
    "events",
    MetaData(),
    autoload_with=engine,
    clickhousedb_indexes=inspector.get_clickhouse_indexes("events"),
)
```

## 프로젝션 {#sqlalchemy-projections}

Alembic 없이도 SELECT 프로젝션을 테이블 인수로 선언할 수 있습니다:

```python
from sqlalchemy import Column, MetaData, Table, inspect
from clickhouse_connect.cc_sqlalchemy import ClickHouseProjection, engines, types

metadata = MetaData()
events = Table(
    "events",
    metadata,
    Column("value", types.UInt32),
    Column("label", types.String),
    ClickHouseProjection("by_label", "SELECT value, label ORDER BY label, value"),
    engines.MergeTree(order_by="value"),
)
metadata.create_all(engine)

projections = inspect(engine).get_clickhouse_projections("events")
```

`select`는 프로젝션 괄호 안에 들어가는 원시 SQL입니다. 정의는 변경할 수 없으며, 프로젝션 이름은 테이블 내에서 중복될 수 없습니다. `clickhousedb_projections` 테이블 옵션에는 `ClickHouseProjection` 정의의 시퀀스도 지정할 수 있습니다. `Table.to_metadata()`는 선언을 그대로 유지하며, `CREATE TABLE`은 이를 인라인으로 렌더링합니다. 딕셔너리(Dictionaries)에는 프로젝션을 선언할 수 없습니다. `if_not_exists`, `first`, `after_projection`은 명령형 ALTER 헬퍼에서 계속 사용할 수 있으며, 인라인 생성이나 비교에는 영향을 주지 않습니다. 기존 위치 기반 생성자 인수를 포함하여 `clickhouse_connect.cc_sqlalchemy.alembic` 및 `.alembic.operations`에서 가져오는 방식도 계속 지원됩니다.

`Inspector.get_clickhouse_projections()`는 와일드카드, 별칭, 그룹화, 정렬을 유지한 채 저장된 SELECT 정의를 반환합니다. 프로젝션 수준의 `WITH SETTINGS` 및 인덱스 기반 프로젝션 형식은 SELECT 전용 API로 온전히 보존할 수 없으므로 거부됩니다. 카탈로그(Catalog) 조회에 실패한 경우에도 오류가 발생합니다. 일반적인 `Table(..., autoload_with=engine)`은 프로젝션 카탈로그를 읽지 않습니다. 컬럼과 프로젝션을 명시적으로 복사하려면 다음과 같이 하십시오.

```python
inspector = inspect(engine)
reflected = Table(
    "events",
    MetaData(),
    autoload_with=engine,
    clickhousedb_projections=inspector.get_clickhouse_projections("events"),
)
```

검사를 수행하려면 대상 테이블을 조회할 수 있어야 하며 `system.projections`의 `database`, `table`, `name`, `type`, `query`, `settings` 필드에 액세스할 수 있어야 합니다. 이 카탈로그는 ClickHouse 24.9.1.3278 버전에서 추가되었습니다. 다만 카탈로그가 존재한다는 사실만으로 비교 기능이 지원된다고 판단할 수는 없습니다. 드라이버는 카탈로그와 정규화 쿼리를 통해 기능 지원 여부를 확인합니다.

## Alembic 마이그레이션 {#sqlalchemy-alembic}

ClickHouse Connect에는 ClickHouse 스키마 마이그레이션을 위한 Alembic 통합 기능이 포함되어 있습니다. 다음과 같이 설치하십시오:

```bash
pip install "clickhouse-connect[alembic]"
```

비동기 방언으로 마이그레이션을 수행하려면 두 extras를 모두 설치하십시오:

```bash
pip install "clickhouse-connect[alembic,sqlalchemy-async]"
```

async Alembic 프로젝트를 생성한 다음, 자동 생성된 환경 파일을 ClickHouse를 지원하는 예시로 교체하십시오:

```bash
alembic init -t async alembic
```

생성된 `alembic.ini`는 `script_location = %(here)s/alembic`을 사용합니다. 마이그레이션 디렉터리 이름이 `alembic`이면 이 설정을 그대로 유지하고, 그렇지 않으면 `alembic init`에 전달한 디렉터리로 변경하십시오. `alembic/env.py`를 저장소에 포함된 [비동기 Alembic `env.py` 예시](https://github.com/ClickHouse/clickhouse-connect/blob/main/examples/alembic_async/env.py)로 교체한 다음, `alembic.ini`에서 `sqlalchemy.url`을 설정하십시오.

방언 통합을 등록하려면 Alembic의 `env.py`에서 `clickhouse_connect.cc_sqlalchemy.alembic`을 import하십시오. 자동 생성은 테이블 생성 및 제거, 컬럼 추가/수정/삭제, 기본값, 주석, MergeTree 테이블 설정을 포함한 일반적인 테이블 스키마 변경을 지원합니다. 테이블 및 컬럼 이름 변경은 수동 작업을 사용하십시오. 생성된 모든 migration은 적용하기 전에 반드시 검토하십시오.

ClickHouse Cloud에서는 이후의 리플렉션이 모든 레플리카에서 완료된 스키마 변경을 확인할 수 있도록 마이그레이션 엔진 URL에 `alter_sync=2`를 추가하십시오. 이 설정은 연결이 교체되거나 업그레이드 직후 자동 생성이 실행될 때 특히 중요합니다. `select_sequential_consistency=1`은 데이터 읽기에만 적용되며 스키마 변경에는 적용되지 않습니다.

버전 테이블 삽입은 다운그레이드 시 이전에 기록된 revision을 복원할 수 있도록 삽입 중복 제거를 우회합니다. 생성된 오프라인 SQL은 `SETTINGS deduplicate_insert = 'disable'`을 사용하므로 대상 서버에서 해당 설정을 지원해야 합니다. 온라인 마이그레이션은 서버에 최신 설정이 없으면 레거시 `insert_deduplicate = 0` 설정을 사용합니다. 일반 테이블 삽입은 구성된 중복 제거 동작을 그대로 유지합니다.

자동 생성은 메타데이터와 서버 양쪽에 모두 존재하는 테이블에 대해 선언된 테이블 엔진을 서버의 엔진과 비교합니다. 엔진 계열, 위치 기반 엔진 인수, `ORDER BY`, `PRIMARY KEY`, `PARTITION BY`, `SAMPLE BY`, 테이블 `TTL` 변경에 대한 자동 마이그레이션은 지원되지 않습니다. 따라서 차이가 있으면 비어 있거나 오해를 일으킬 수 있는 revision을 작성하는 대신 `UnsupportedTableChangeError`가 발생합니다. 서버의 ALTER 지원 여부와 영향을 받는 데이터를 검토한 후 마이그레이션을 직접 작성하십시오. 이 예외에는 테이블, 옵션, 양쪽 표기를 담은 `TableOptionDrift` 레코드의 `drifts` 튜플이 포함됩니다. 예외를 생성하려면 드리프트가 1개 이상 필요하며, 그렇지 않으면 `ValueError`가 발생합니다. 표현식은 정규화한 후 비교하며, 그래도 텍스트가 다르면 서버의 `formatQuerySingleLine`을 사용해 `INTERVAL 30 DAY`와 `toIntervalDay(30)` 같은 표기 차이를 판정합니다. 따옴표로 묶인 엔진 인수는 디코딩된 문자열 내용을 공백과 구두점까지 포함하여 정확히 비교합니다. TTL 절은 `ALTER TABLE t MODIFY TTL ...` 형태로 포맷되며, `DELETE WHERE`, `TO VOLUME`, `RECOMPRESS` 같은 동작은 그대로 유지됩니다. `MergeTree`와 Cloud의 `Shared*` 및 `Replicated*` 변형은 하나의 계열로 간주되며, 복제 경로 인수는 비교하지 않습니다.

선언된 엔진 `settings`가 서버와 다르면 `op.modify_clickhouse_table_settings(...)`로 렌더링되며, 다운그레이드 시에는 각 설정을 복원하거나 초기화합니다. `system.merge_tree_settings`의 값과 타입을 기준으로 기본값을 확인하고 동등한 불리언 및 숫자 표기를 판별하며, 문자열 설정은 문자열 그대로의 의미를 유지합니다. 모델에 선언되지 않은 설정은 그대로 보존되며, 이전 마이그레이션 이후 모델에서 제거된 설정도 마찬가지입니다. 리플렉션으로는 이러한 설정과 서버가 주입한 설정을 구분할 수 없으므로, 자동 생성은 이를 자동으로 초기화하지 않습니다. 초기화가 필요하면 `op.reset_clickhouse_table_settings(...)`를 명시적으로 사용하십시오. `index_granularity`, `index_granularity_bytes` 같은 읽기 전용 설정은 키와 마찬가지로 비교 대상이 되며, 변경은 거부됩니다. 비교를 건너뛰려면 `context.configure()`에 `clickhousedb_compare_table_options=False`를 전달하십시오.

리플렉션된 뷰(view)와 materialized view는 테이블이 아닙니다. `include_object`가 이를 제외하므로, 자동 생성은 메타데이터에 없는 뷰에 대해 `drop_table`을 제안하지 않습니다. 이들은 일반 뷰 또는 materialized view 헬퍼로 관리하십시오.

`op.alter_column(..., server_default=None)`은 `MODIFY COLUMN ... REMOVE DEFAULT`를 생성하며, 이는 서버가 인식하는 유일한 형식입니다. 컬럼에 `DEFAULT`가 없거나 `MATERIALIZED` 또는 `ALIAS`를 사용하는 경우 서버는 해당 구문을 거부하므로, 기본값이 있을 때에만 삭제를 요청하십시오. 타입만 변경하면 기존 기본값은 유지됩니다. 방언 컬럼 옵션도 동일한 규칙을 따릅니다. 속성을 제거하려면 `clickhousedb_codec=None`, `clickhousedb_ttl=None`, `clickhousedb_alias=None` 또는 `clickhousedb_materialized=None`을 전달하고, 설정하려면 값을 전달하십시오. 이러한 속성만 설정하거나 제거할 때는 `existing_type`이 필요하지 않습니다. TTL, 별칭, materialized SQL 표현식에는 `text(...)`를 사용하십시오(예: `clickhousedb_ttl=text("ts + INTERVAL 7 DAY")`). 전달하지 않은 옵션은 변경되지 않습니다. `clickhousedb_` 이름과 레거시 `clickhouse_` 이름을 모두 사용할 수 있으며, 두 이름이 모두 `alter_column`에 전달되면 `None`을 포함하여 명시적으로 지정한 `clickhousedb_` 값이 우선합니다.

메타데이터에 `AggregateFunction` 상태 버전이 생략되어 있으면, 자동 생성은 리플렉션된 기존 버전을 그대로 받아들입니다. 예를 들어 `AggregateFunction(uniq, UInt32)`는 리플렉션된 `AggregateFunction(1, uniq, UInt32)`와 일치하는 것으로 간주됩니다. 이는 중첩된 타입 내부에서도 동일하게 적용됩니다. 단, 집계 함수, 해당 매개변수 또는 인수 타입이 변경되면 여전히 타입 변경으로 처리됩니다.

메타데이터에 명시한 버전은 리플렉션된 버전과 일치해야 합니다. 버전이 없는 레거시 리플렉션 타입은 명시적 버전 `0`과 일치하는 것으로 간주됩니다. 버전을 생략한다고 해서 서버 업그레이드 후 기존 상태 포맷의 업그레이드가 요청되지는 않습니다. 상태 포맷을 변경하려면 버전을 명시적으로 선언하십시오.

Alembic의 마이그레이션 함수는 여전히 동기 방식으로 동작합니다. 비동기 환경에서는 `AsyncEngine`을 생성하고 `AsyncConnection`을 연 다음, 동기 마이그레이션 함수를 `await connection.run_sync(...)`에 전달합니다. 오프라인 마이그레이션은 `context.configure(url=..., literal_binds=True, dialect_opts={"paramstyle": "named"})`를 직접 호출하며 엔진을 생성하지 않습니다. 저장소에 포함된 [비동기 Alembic `env.py` 예시](https://github.com/ClickHouse/clickhouse-connect/blob/main/examples/alembic_async/env.py)에는 두 경로가 모두 포함되어 있으며, Alembic의 표준 `sqlalchemy.url` 구성을 통해 연결 URL을 읽습니다. 또한 `include_object`, `make_include_name(...)`, `clickhouse_writer`, `version_table` 등 단계별 예시에서 사용한 ClickHouse Alembic 훅과 옵션을 그대로 유지합니다. 비동기 마이그레이션을 실행하거나 정리할 때 `engine.sync_engine`을 사용하지 마십시오.

ClickHouse 전용 `op.*` 헬퍼는 다음을 지원합니다.

* 추가, 구체화, 삭제 작업을 포함한 데이터 스키핑 인덱스
* 추가, 구체화, 삭제 작업을 포함한 프로젝션
* MergeTree 테이블 설정 수정 및 재설정
* 일반 뷰 및 SQL 함수 생성, 교체 및 제거
* materialized view 생성 및 제거
* 딕셔너리 생성, 제거 및 다시 로드

**업그레이드 참고:** Alembic은 기본적으로 명시적인 스키핑 인덱스와 SELECT 프로젝션을 비교합니다. 이전의 명령형 마이그레이션으로만 생성된 객체가 관리 대상 테이블 메타데이터에 없으면 삭제 작업이 생성될 수 있습니다. 업그레이드하기 전에 `ClickHouseIndex` 또는 `ClickHouseProjection`으로 해당 객체를 선언하거나, `include_name` 또는 `include_object`로 관리되지 않는 객체를 제외하거나, `context.configure()`에서 관련 비교를 비활성화하십시오:

```python
context.configure(
    connection=connection,
    target_metadata=metadata,
    clickhousedb_compare_indexes=False,
    clickhousedb_compare_projections=False,
)
```

각 옵션은 해당 카탈로그(Catalog) 읽기와 테이블 삭제 다운그레이드 스냅샷을 건너뜁니다. 편집 시에는 삭제 작업과 추가 작업이 각각 별도로 생성됩니다. 다운그레이드는 정의를 복원하지만, 어느 방향에서도 이전 머티리얼라이즈 상태는 복원되지 않습니다. 프로젝션을 대체하면 기존 프로젝션 파트가 폐기됩니다. 이에 따른 재구성 비용을 검토하고, 기존 파트에 대체 프로젝션을 즉시 적용해야 하는 경우 `MATERIALIZE PROJECTION`을 명시적으로 실행하십시오. 인덱스 머티리얼라이즈 역시 명시적으로 수행해야 합니다.

autogenerate를 지원받으려면 `ClickHouseIndex`로 스킵 인덱스를 선언하거나, 명시적 revision에서 기존 `op.add_clickhouse_index` 및 `op.drop_clickhouse_index` 헬퍼를 사용하십시오. `clickhouse_connect.cc_sqlalchemy.alembic` 및 `.alembic.operations`에서의 import는 계속 지원됩니다. 표준 SQLAlchemy `Index`, `Column(index=True)`, `op.create_index`, `op.drop_index`는 여전히 허용되지 않습니다.

관리형 테이블(managed tables)에서는 기본적으로 선언이 현재 존재하는 명시적 인덱스 집합 전체를 관리합니다. 선언되지 않은 명시적 인덱스에 대해서는 삭제 작업이 생성되며, 이전에 명령형 마이그레이션으로만 생성된 인덱스도 여기에 포함됩니다. 표현식, 인덱스 유형, 매개변수 또는 유효 세분화 수준이 변경되면 삭제 작업과 그 뒤를 잇는 추가 작업이 별도로 생성됩니다. 다운그레이드는 이전 정의를 복원합니다. 렌더링 전에도 `process_revision_directives`에서 작업을 확인할 수 있습니다. 정책 후크는 인덱스 및 프로젝션 편집을 스키마, 테이블, 객체 이름을 기준으로 짝지어야 하며, 작업이 인접해 있다는 점에 의존해서는 안 됩니다. 어느 방향에서도 이전 머티리얼라이즈 상태는 복원되지 않으며, `MATERIALIZE INDEX`도 생성되지 않습니다. 기존 파트에 인덱스를 즉시 적용해야 하는 경우 명시적으로 구체화하십시오.

인덱스 추가, 제거, 편집은 `render_as_batch=False`로 생성하십시오. 이러한 작업의 헬퍼는 Alembic의 지연 배치 큐를 지원하지 않으므로 `render_as_batch=True`를 사용하면 생성 중에 오류가 발생합니다. 테이블 생성 시의 인라인 인덱스와 테이블 삭제 다운그레이드 스냅샷의 인라인 인덱스는 계속 지원됩니다.

테이블 설정(table settings), 프로젝션, 머티리얼라이즈를 비롯해 배치 블록 내부의 다른 사용자 정의 ClickHouse 작업에도 동일한 제한이 적용됩니다. 이러한 작업은 배치 모드 밖에서 생성하십시오.

`op.batch_alter_table()`로 물리적 배치 재생성을 수행하려면 컬럼, 엔진, `clickhousedb_indexes`를 모두 포함하는 완전한 `copy_from` Table을 전달하십시오. 컬럼과 인덱스를 모두 로드하려면 위의 명시적 리플렉션 예시를 사용하고, 오프라인 마이그레이션(migration)에서는 완전한 메타데이터를 제공하십시오. 자동 온라인 재생성은 실행 시점에 인덱스 카탈로그(Catalog)를 읽으며, 명시적 인덱스가 있는 테이블은 테이블을 생성하거나 삭제하기 전에 거부합니다. autogenerate 비교 옵트아웃을 사용해도 이 보호 장치는 우회되지 않습니다.

표준 `include_name` 및 `include_object` 후크는 `type_="index"`를 전달받습니다. 이름 필터는 리플렉션된 후보와 선언된 후보 모두에 적용되므로, 제외된 이름은 계속 관리 대상에서 제외됩니다. 객체 필터는 일반적인 `reflected` 및 `compare_to` 값을 전달받으며, 이때 전달되는 인덱스 객체는 정의 필드와 `.table`을 제공합니다. 예를 들어 Alembic의 표준 비관리 객체 레시피인 `reflected and compare_to is None`은 명령형으로만 관리되는 인덱스를 보호합니다. 테이블 필터는 인덱스 카탈로그를 읽기 전에 적용됩니다. 새로 생성되는 테이블의 인라인 인덱스도 정책 후크보다 먼저 필터링됩니다.

비교 시에는 ClickHouse의 표기 방식과 기본값을 반영하기 위해 서버의 포매팅과 분석 기능을 사용합니다. 표현식 분석에는 현재 테이블, 서버 함수, 설정이 사용되며, analyzer와 예상되는 `EXPLAIN` 출력이 필요합니다. 이 기능은 ClickHouse 26.8에서 검증되었으며, 소스 검토는 26.6 기준으로 수행되었습니다. 카탈로그 필드가 존재한다는 사실만으로 이전 버전 서버에서 비교가 지원된다고 볼 수는 없습니다. 인덱스에 영향을 주는 `ALIAS` 정의가 변경된 경우, 인덱스를 비교하기 전에 명시적인 컬럼 마이그레이션이 필요합니다.

인덱스 편집에서는 같은 리비전에서 추가되는 물리 컬럼을 참조할 수 있습니다. 분석 결과 추가 예정인 새 컬럼이 알 수 없는 식별자로 보고되면, autogenerate는 추가될 컬럼을 사용할 수 있는 상태에서 전체 표현식을 검증한 다음, 인덱스 삭제 및 추가보다 먼저 컬럼 추가를 생성합니다. 오타나 필터로 제외된 컬럼을 비롯한 그 밖의 알 수 없는 식별자는 여전히 `IndexComparisonError`를 발생시킵니다.

`minmax()`, `MinMax()`, `minmax`처럼 유형의 빈 괄호나 대소문자만 다른 경우는 동일하게 취급됩니다. 다만 생략된 유형 인수는 비교 시 확장되지 않습니다. 따라서 서버가 해당 기본값을 사용하더라도 `bloom_filter`와 `bloom_filter(0.025)` 사이에서 변경하면 일회성 삭제 및 추가가 발생할 수 있습니다.

비교 과정에서는 임의의 SQL 표현식이 동등한지 판단하지 않습니다. 정규화에 성공했더라도 결과 형식이 다르면, 표현식이 같은 값을 반환하더라도 autogenerate는 교체 작업을 생성합니다. 이러한 변경 사항을 검토하거나, 해당 인덱스를 명시적 마이그레이션과 필터로 관리하십시오.

카탈로그 접근, 표현식 해석 또는 예상되는 정규화 출력을 사용할 수 없으면 autogenerate는 테이블, 인덱스, 선언된 정의와 리플렉션된 정의, 그리고 원인을 담은 `IndexComparisonError`를 발생시킵니다. 편집 내용은 신중하게 검토하십시오. 삭제와 추가는 트랜잭션으로 묶이지 않는 별도의 문으로 실행되므로, 추가에 실패하면 기존 인덱스가 없는 상태로 남을 수 있습니다.

### 프로젝션 autogenerate {#projection-autogenerate}

Alembic은 기본적으로 관리 대상 테이블의 SELECT 프로젝션(projection)을 비교합니다. 실제 프로젝션 집합은 선언을 기준으로 관리됩니다. 선언되지 않은 프로젝션에 대해서는 삭제 연산이 생성되며, 정의가 변경된 경우에는 삭제 연산과 추가 연산이 각각 생성됩니다. autogenerate는 각 테이블에서 프로젝션 삭제, 컬럼 추가 및 변경, 인덱스 연산, 프로젝션 추가, 컬럼 삭제 순으로 연산을 정렬합니다. 컬럼 삭제는 테이블 비교기가 완료된 후 Alembic이 덧붙입니다. 정책(Policy) 훅에서는 스키마, 테이블, 프로젝션 이름을 기준으로 변경 사항을 짝지으십시오. 삭제와 추가 사이에 다른 연산이 끼어들 수 있습니다. 다운그레이드 시에는 삭제 후 재생성된 테이블의 프로젝션을 포함하여 이전 정의가 복원됩니다. 연산은 렌더링 전에 `process_revision_directives`에 전체 정의를 노출합니다. `MATERIALIZE PROJECTION`은 생성되지 않으며, 업그레이드와 다운그레이드 모두 기존 파트의 이전 구체화 상태를 복원하지 않습니다. 기존 파트에 프로젝션이 즉시 필요하다면 명시적으로 구체화하십시오.

`AggregatingMergeTree` 등 비표준 머지 동작을 사용하는 엔진에서는 `deduplicate_merge_projection_mode='throw'`이면 ClickHouse가 `ADD PROJECTION`을 거부합니다. 원래 인라인으로 선언된 프로젝션의 대체를 포함하여, 프로젝션 추가나 대체를 적용하기 전에 이 값을 명시적으로 `drop` 또는 `rebuild`로 설정하십시오.

`include_name`과 `include_object`에는 `type_="projection"`이 전달됩니다. 이름 필터는 리플렉션된 이름과 선언된 이름 모두에 적용됩니다. 객체 필터에는 `.table`, `reflected`, `compare_to`를 포함한 정의가 전달됩니다. 일반적인 `reflected and compare_to is None` 패턴을 사용하면 명령형으로만 생성된 프로젝션을 보호할 수 있습니다. 테이블 필터는 카탈로그(Catalog)를 읽기 전에 실행되며, 새로 생성되는 테이블의 인라인 정의는 정책 훅보다 먼저 필터링됩니다. 필터링된 프로젝션이나 관련 없는 테이블에 지원되지 않는 정의가 있더라도 비교는 중단되지 않습니다.

비교 시에는 ClickHouse의 CREATE 정규화 방식에 따라 서버의 전체 프로젝션 문법 형식 지정자와 `system.functions`에 있는 대소문자를 구분하지 않는 함수 이름 및 별칭을 사용합니다. 일반 SELECT처럼 실제 테이블을 기준으로 분석하지 않고, 와일드카드와 집계 표현식을 포함한 SELECT 구조를 그대로 유지합니다. 서식, 식별자 따옴표 처리, 대소문자를 구분하지 않는 등록 함수의 표기 차이는 동일하게 취급됩니다. 반면 `sumIf`와 `SumIf`처럼 대소문자를 구분하는 이름은 서로 다른 것으로 구분됩니다. 서식 지정된 정의가 서로 다르면 그룹화 괄호를 무시하는 파싱된 구문 트리도 추가로 확인합니다. ClickHouse 버전과 ClickHouse Cloud에 따라 불필요한 괄호가 일관되지 않게 저장되므로, 불필요한 괄호나 `value + 13`과 `plus(value, 13)` 같은 연산자·함수 표기의 차이는 동일하게 취급됩니다. 그 밖의 구조적 차이가 있으면 삭제 및 추가 연산이 생성됩니다. 비교는 임의의 SQL 동등성을 증명하거나 컬럼 의존성을 검증하지 않습니다. 대체 정의는 같은 revision에서 앞서 추가된 물리 컬럼을 참조할 수 있으므로, 적용하기 전에 변경된 ALIAS 컬럼을 포함한 의존성을 검토하십시오. 잘못된 의존성은 DDL 실행 시점에 실패하며, 삭제와 추가는 트랜잭션으로 묶이지 않은 별도의 구문이므로 추가가 실패하면 기존 프로젝션이 사라진 상태로 남을 수 있습니다.

카탈로그 필드 누락, 카탈로그 접근 오류, 서식 지정 또는 함수 메타데이터를 사용할 수 없는 경우, 프로젝션 수준의 `WITH SETTINGS`, 인덱스 기반 형식에서는 테이블, 프로젝션, 선언된 정의와 리플렉션된 정의, 원인을 담은 `ProjectionComparisonError`가 발생합니다. 정규화에 실패하면 대체 연산을 생성하지 않고 이 진단 오류를 발생시킵니다. 지원되지 않는 프로젝션은 필터링하거나 명시적 마이그레이션으로 관리하십시오. `query_masking_rules`로 인해 카탈로그가 반환하는 SELECT 텍스트가 변경되면 비교 및 재실행 결과를 신뢰하기 어려울 수 있습니다. 영향을 받는 프로젝션에는 명시적 마이그레이션, 필터 또는 비교 제외 옵션을 사용하십시오. 함수 정규화에는 `system.functions`의 `name`, `is_aggregate`, `case_insensitive`, `alias_to` 필드가 필요합니다. 지원 여부는 버전 문자열이 아니라 실제 카탈로그 및 형식 지정자 쿼리를 통해 확인합니다.

프로젝션 추가, 제거, 수정은 `render_as_batch=False`로 생성하십시오. 인라인 CREATE 정의와 테이블 삭제 다운그레이드 스냅샷은 계속 지원됩니다. 물리적 배치 재생성을 하려면 컬럼, 엔진, `clickhousedb_projections`를 모두 포함한 `copy_from` 메타데이터를 제공하십시오. 자동 온라인 재생성은 DDL 실행 전에 프로젝션 카탈로그를 읽어, 프로젝션이 있는 테이블은 처리를 거부합니다. 비교 제외 옵션을 사용하더라도 이 실행 보호 장치는 우회되지 않습니다.

자세한 내용은 [Alembic 작업 예시](https://github.com/ClickHouse/clickhouse-connect/blob/main/clickhouse_connect/cc_sqlalchemy/alembic/WORKED_EXAMPLE.md) 전체를 참조하십시오. `clickhouse-sqlalchemy`에서 마이그레이션하는 사용자는 [마이그레이션 가이드](https://github.com/ClickHouse/clickhouse-connect/blob/main/clickhouse_connect/cc_sqlalchemy/MIGRATING_FROM_CLICKHOUSE_SQLALCHEMY.md)도 함께 참고하십시오.

### 렌더링 전에 생성된 연산 분류하기 {#classify-generated-operations-before-rendering}

ClickHouse 마이그레이션(migration) 연산 클래스 21개는 모두
`clickhouse_connect.cc_sqlalchemy.alembic` 및 해당 `operations` 모듈에서 공개되어 있습니다.
`process_revision_directives`에서 `isinstance`로 이 클래스들을 검사하거나, Alembic의
`Rewriter.rewrites`에 등록하십시오. 기존의 밑줄로 시작하는 이름은 동일한 클래스의 별칭으로 유지되므로,
기존 등록 및 import도 그대로 동작합니다.

공개 검사 필드는 생성자 인수와 일치합니다. 테이블 연산은
`table_name`, `schema`, `clickhouse_settings`를 노출합니다. 단일 인덱스 연산은
`name`을 노출합니다. 추가 연산은 `expression`, `type_`, `granularity`, `if_not_exists`,
`first`, `after_index`도 노출합니다. 프로젝션(projection) 추가 연산은 인덱스 표현식, 유형, 세분화 수준 필드 대신
`select`와 `after_projection`을 노출합니다. 삭제 연산은
`if_exists`를 노출하며, 단일 인덱스나 프로젝션은 이전 정의가 있으면 `existing_index` 또는
`existing_projection`도 노출합니다. 머티리얼라이즈 연산은
`if_exists`와 `partition`을 노출합니다. 그룹화된 추가 연산은 `indexes` 또는
`projections`를 `ClickHouseIndex` 또는 `ClickHouseProjection`의 튜플로 저장합니다. 그룹화된
삭제 연산은 `names`를 튜플로 저장합니다. 그룹화된 연산은 모든 멤버를 검사하십시오.

`ModifyClickHouseTableSettingsOp`는 `settings`와 선택 사항인
`existing_settings`를 노출합니다. `ResetClickHouseTableSettingsOp`는 `names` 튜플을 노출합니다.
이러한 테이블 설정(table settings)은 query-level `clickhouse_settings` 매핑과 다릅니다.
뷰(view) 및 함수 생성 연산은 `name`, `select` 또는 `expression`,
`if_not_exists`, `or_replace`를 노출합니다. 뷰는 `schema`도 노출합니다. 구체화된 뷰(Materialized View)
생성 연산은 `name`, `schema`, `to_table`, `to_schema`, `select`,
`if_not_exists`를 노출합니다. 딕셔너리 생성 연산은 `name`, `schema`, `columns` 튜플,
`primary_key`, `source`, `layout`, `lifetime`, `comment`, `if_not_exists`,
`clickhouse_settings`를 노출합니다. 뷰, 함수, 구체화된 뷰, 딕셔너리 삭제 연산은
`name`과 `if_exists`를 노출하며, 생성자가 허용하는 경우 `schema`와 `clickhouse_settings`도 노출합니다. 딕셔너리 리로드 연산은 `name`과 `schema`를 노출합니다. SQL 조각은
문자열 그대로 유지됩니다. 매핑은 전달된 값을 그대로 유지합니다. 역방향 연산은
이전 정의가 필요하거나 `NotImplementedError`를 발생시킬 수 있습니다. 되돌릴 수 있는 정의라도
구체화된 데이터(materialized data)까지 복원하지는 않습니다.

이 예시는 애플리케이션 정책일 뿐이며, 드라이버 차원에서 안전을 보장하지는 않습니다. 이 예시는
명시적으로 선택한 인덱스 형태나 테이블 설정만 허용하고, 대체 연산과
알 수 없는 연산은 검토 대상으로 넘기며, 독립형 인덱스 삭제, 독립형
프로젝션 삭제 및 파괴적인 기본 제공 연산은 거부합니다. 배포 환경에 맞게 이 규칙을 변경하십시오. 생성 연산이라도
필드 검사가 필요합니다. 뷰에 `or_replace=True`를 지정하면 이름이 겹치는 테이블의 데이터가 사라질 수 있으며, 원시 SQL 본문과 딕셔너리 소스도 검토해야 합니다.

```python
import logging

from alembic.operations import ops
from clickhouse_connect.cc_sqlalchemy import alembic as ch_alembic


def leaves(operation):
    if isinstance(operation, ops.OpContainer):
        for child in operation.ops:
            yield from leaves(child)
    else:
        yield operation


def object_key(operation):
    if isinstance(operation, (ch_alembic.AddClickHouseIndexOp,
                              ch_alembic.DropClickHouseIndexOp)):
        kind = "index"
    elif isinstance(operation, (ch_alembic.AddClickHouseProjectionOp,
                                ch_alembic.DropClickHouseProjectionOp)):
        kind = "projection"
    else:
        return None
    return kind, operation.schema, operation.table_name, operation.name


def classify_tree(tree, direction):
    operations = list(leaves(tree))
    adds = {object_key(op) for op in operations if isinstance(
        op, (ch_alembic.AddClickHouseIndexOp, ch_alembic.AddClickHouseProjectionOp))}
    drops = {object_key(op) for op in operations if isinstance(
        op, (ch_alembic.DropClickHouseIndexOp, ch_alembic.DropClickHouseProjectionOp))}
    replacements = adds & drops
    for operation in operations:
        verdict, reason = "review", "operation needs explicit review"
        if isinstance(operation, (ops.DropTableOp, ops.DropColumnOp, ops.ExecuteSQLOp)):
            verdict, reason = "rejected", "destructive change or opaque SQL"
        elif object_key(operation) in replacements:
            reason = "replacement can discard existing materialization"
        elif isinstance(operation, (ch_alembic.DropClickHouseIndexOp,
                                    ch_alembic.DropClickHouseProjectionOp,
                                    ch_alembic.DropClickHouseIndexesOp,
                                    ch_alembic.DropClickHouseProjectionsOp)):
            verdict, reason = "rejected", "removal requires a separate migration"
        elif direction == "upgrade":
            if isinstance(operation, ch_alembic.AddClickHouseIndexOp):
                if (operation.type_ == "minmax" and operation.expression == "value"
                        and operation.granularity == 1 and not operation.first
                        and operation.after_index is None and not operation.clickhouse_settings):
                    verdict, reason = "allowed", "approved index definition"
            elif isinstance(operation, ch_alembic.ModifyClickHouseTableSettingsOp):
                if (dict(operation.settings) == {"max_bytes_to_merge_at_max_space_in_pool": 107374182400}
                        and not operation.clickhouse_settings):
                    verdict, reason = "allowed", "approved table setting value"
        yield direction, operation, verdict, reason


def review_revision(context, revision, directives):
    # Scope: a single-engine env.py. clickhouse_writer uses singular roots.
    for script in directives:
        if len(script.upgrade_ops_list) != 1 or len(script.downgrade_ops_list) != 1:
            raise ValueError("This policy hook supports one operation stream only")
        findings = [
            *classify_tree(script.upgrade_ops_list[0], "upgrade"),
            *classify_tree(script.downgrade_ops_list[0], "downgrade"),
        ]
        for direction, op, verdict, reason in findings:
            logging.getLogger("alembic.policy").info(
                "%s: %s: %s: %s", direction, type(op).__name__, verdict, reason)
        blocked = [f"{direction}: {type(op).__name__}: {verdict}: {reason}"
                   for direction, op, verdict, reason in findings
                   if direction == "upgrade" and verdict != "allowed"]
        if blocked:
            raise ValueError("Migration requires review:\n" + "\n".join(blocked))
    ch_alembic.clickhouse_writer(context, revision, directives)
```

`context.configure()`에 `clickhouse_writer` 대신
`process_revision_directives=review_revision`을 전달하십시오. 이 후크는 양방향의 검토 결과를 모두 로그로 기록하며, 업그레이드 검토 결과가 있으면 revision 생성을
차단합니다. 다운그레이드 검토 결과는 다운그레이드를 실행하기 전에 별도로
검토해야 하며, 승인된 업그레이드의 쓰기를 차단하지는 않습니다. 이 후크는 중첩된 컨테이너를 순회하며, 인접 여부와 관계없이
유형, 스키마, 테이블, 이름을 기준으로 대체 항목의 쌍을 맞춥니다. 그룹화된 추가 항목과 인식되지 않는
모든 연산은 기본적으로 검토 대상으로 처리됩니다. 이 레시피는 방향마다 하나의 엔진과
하나의 연산 스트림만 지원합니다. 분류기에서 리스트 형태의 루트를 사용하더라도
`clickhouse_writer`가 다중 엔진 후크가 되지는 않습니다. 생성된 트리가 비어 있다는 것은
활성화되어 있고 지원되는 비교에서 변경 사항이 발견되지 않았다는 의미일 뿐입니다. 뷰, 함수,
딕셔너리 및 기타 지원되지 않는 비교 대상에는 여전히 명시적인 마이그레이션이 필요합니다.

## 범위 및 제한 사항 {#scope-and-limitations}

* ClickHouse는 이 HTTP 방언을 통해 전통적인 트랜잭션을 제공하지 않습니다. `engine.begin()` 및 `Session.commit()`은 Python 측 작업을 정리하지만, commit과 rollback은 서버에서는 실제로 아무 작업도 수행하지 않습니다.
* `UPDATE`, 2단계 트랜잭션, 시퀀스, `RETURNING`, 고급 격리 수준은 이 방언에서 구현되지 않았습니다. 필요할 경우 서버 측 뮤테이션에는 명시적으로 ClickHouse SQL을 사용하십시오.
* `Column(..., primary_key=True)`는 SQLAlchemy 객체 아이덴티티를 제공합니다. 하지만 서버 측 고유 제약을 생성하지는 않습니다. 정렬 및 선택적 프라이머리 키 표현식은 테이블 엔진을 통해 정의하십시오.
* ClickHouse는 이러한 제약을 강제하지 않으므로 전통적인 외래 키, 고유 제약, 표준 인덱스 메타데이터는 사용할 수 없습니다.
* ORM 릴레이션 관리, unit-of-work 방식의 업데이트, 캐스케이딩, eager 또는 lazy 릴레이션 loading은 지원되는 ORM 범위에 포함되지 않습니다.
