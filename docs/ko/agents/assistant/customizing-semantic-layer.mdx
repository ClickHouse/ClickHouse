Assistant 채팅 에이전트는 **AGENTS.md**를 통해 고유한 비즈니스 로직, 데이터 구조, 도메인 지식을 이해하도록 사용자 지정할 수 있습니다. AGENTS.md는 에이전트의 시스템 프롬프트 위에서 시맨틱 계층(semantic layer) 역할을 하는 특수한 저장된 쿼리입니다.

AGENTS.md 파일을 생성하면 모든 대화의 시작 부분에 삽입되는 사용자 지정 지침을 제공할 수 있습니다. 이 지침은 조직 고유의 요구 사항, 계산 방식, 규칙에 맞게 SQL 쿼리(SQL query) 생성과 데이터 분석을 유도합니다.

## 작동 방식 {#how-it-works}

Cloud Console에서 &quot;AGENTS.md&quot;(대소문자 구분)라는 이름으로 쿼리를 저장하면 다음과 같이 동작합니다.

1. 메시지가 전송되면 Assistant 채팅 에이전트가 이 파일을 자동으로 로드합니다
2. 파일 내용은 구조화된 콘텐츠 태그로 감싸져 에이전트의 시스템 프롬프트에 삽입됩니다
3. 이 지침은 해당 서비스의 모든 Assistant 채팅 대화에 적용됩니다

## AGENTS.md 생성 {#creating-agents-md}

<Steps>
  <Step title="저장된 쿼리 생성" id="create-query">
    1. Cloud Console에서 새 쿼리를 생성합니다.
    2. 쿼리 이름을 정확히 **&quot;AGENTS.md&quot;**&#xB85C; 지정합니다(대소문자 구분).
    3. 쿼리 텍스트 편집기에 사용자 지정 지침을 작성합니다(실제 SQL을 작성하는 것이 아닙니다).
    4. 쿼리를 저장합니다.
  </Step>

  <Step title="지침 추가" id="add-instructions">
    명확하고 실행 가능한 표현으로 지침을 작성하십시오. 다음 내용을 포함하는 것이 좋습니다.

    * 비즈니스 규칙 및 계산 방식
    * 데이터 구조 관련 안내
    * 도메인별 용어
    * 자주 사용하는 쿼리 패턴(query patterns)
    * 성능 최적화 규칙
  </Step>
</Steps>

## 권장 사항 {#best-practices}

### 컨텍스트를 유한한 리소스로 다루기 {#finite-resource}

컨텍스트는 매우 귀중합니다. 토큰 하나하나가 에이전트의 &quot;주의 예산(attention budget)&quot;을 소모합니다. 작업 기억 용량이 제한된 인간처럼, 언어 모델도 컨텍스트가 커질수록 성능이 저하됩니다. 따라서 원하는 결과를 얻을 가능성을 최대화하는 **신호 가치가 높은 최소한의 토큰 집합**을 찾아야 합니다.

### 적절한 수준 찾기 {#right-altitude}

다음 두 극단 사이에서 균형을 맞추십시오.

* **지나치게 구체적인 경우**: 취약한 if-else 로직을 하드코딩하면 시스템이 깨지기 쉬워지고 유지 관리가 복잡해집니다.
* **지나치게 모호한 경우**: 상위 수준의 지침만으로는 구체적인 신호를 제공하지 못하거나, 공유된 컨텍스트가 있다고 잘못 가정하게 됩니다.

최적의 수준은 동작을 효과적으로 유도할 만큼 구체적이면서도, 모델이 강력한 휴리스틱을 적용할 수 있을 만큼 유연해야 합니다. 사용 가능한 최상의 모델에서 최소한의 프롬프트로 시작한 다음, 관찰된 실패 모드를 바탕으로 명확한 지침을 추가하십시오.

### 구조화된 섹션으로 정리하기 {#structured-sections}

XML 태그 또는 Markdown 헤더를 사용하여 서로 명확히 구분되고 한눈에 훑어보기 쉬운 섹션을 만드십시오:

```xml
<background_information>
Context about your data and domain
</background_information>

<calculation_rules>
Specific formulas and business logic
</calculation_rules>

<tool_guidance>
How to use specific ClickHouse features
</tool_guidance>
```

### 다양하고 전형적인 예시 제공 {#canonical-examples}

예시는 &quot;백 마디 말보다 나은 한 장의 그림&quot;과 같습니다. 모든 예외 사례(edge case)를 프롬프트에 빠짐없이 담으려 하기보다는, 기대하는 동작을 효과적으로 보여 주는 다양한 예시를 엄선하여 핵심적인 예시 모음을 구성하십시오.

### 간결하면서도 빠짐없이 작성하기 {#minimal-complete}

* 자주 필요한 지침만 포함하십시오
* 간결하게 작성하십시오. 컨텍스트가 커질수록 &quot;context rot&quot;으로 인해 성능이 저하됩니다
* 오래되었거나 거의 사용하지 않는 규칙은 제거하십시오
* 원하는 동작을 유도하는 데 필요한 정보는 충분히 제공하십시오

<Tip>
  최소한으로 작성한다는 것이 반드시 짧게 작성한다는 의미는 아닙니다. 에이전트가 기대한 대로 동작하도록 충분히 상세하게 작성하되, 불필요하게 장황한 표현만 피하십시오.
</Tip>

## 예시: 원시 데이터에서 계산한 메트릭 {#example-calculated-metrics}

메트릭을 구하는 데 컬럼을 직접 조회하는 대신 특정 계산이 필요한 경우, 다음과 같이 에이전트에 지침을 제공하십시오:

```xml
<metric_calculations>
IMPORTANT: "active_sessions" is NOT a column. It must be calculated.

To calculate active sessions:
COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions

This counts unique combinations of session and user identifiers.

When the user asks for "active sessions" or "session count", always use this formula:
SELECT
    date,
    COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions
FROM events
GROUP BY date;

</metric_calculations>
```

## 예시: 비즈니스 로직 규칙 {#example-business-logic}

도메인에 특화된 계산 및 분류 방식을 정의합니다:

```xml
<business_rules>
Revenue Calculation:
- Exclude refunded transactions: WHERE transaction_status != 'refunded'
- Apply regional tax rates using CASE expressions
- Use MRR for subscriptions:
  SUM(CASE
    WHEN billing_cycle = 'monthly' THEN amount
    WHEN billing_cycle = 'yearly' THEN amount / 12
    ELSE 0
  END) AS mrr

Traffic Source Classification:
Use CASE expression to categorize:
CASE
  WHEN traffic_source IN ('google', 'bing', 'organic') THEN 'Organic Search'
  WHEN traffic_source IN ('facebook', 'instagram', 'social') THEN 'Social Media'
  WHEN traffic_source = 'direct' THEN 'Direct'
  ELSE 'Other'
END AS source_category

Customer Segmentation:
- Enterprise: annual_contract_value >= 100000
- Mid-Market: annual_contract_value >= 10000 AND annual_contract_value < 100000
- SMB: annual_contract_value < 10000

Always include these categorizations when generating traffic or revenue reports.
</business_rules>
```

## 예시: 데이터 구조의 특이 사항 {#example-data-quirks}

일반적이지 않은 데이터 포맷이나 레거시 스키마(schema) 관련 결정 사항을 문서화하십시오.

```xml
<data_structure_notes>
The user_status column uses numeric codes, not strings:
- 1 = 'active'
- 2 = 'inactive'
- 3 = 'suspended'
- 99 = 'deleted'

When filtering or displaying user status, always use:
CASE user_status
  WHEN 1 THEN 'active'
  WHEN 2 THEN 'inactive'
  WHEN 3 THEN 'suspended'
  WHEN 99 THEN 'deleted'
END AS status_label

The product_metadata column contains JSON strings that must be parsed:
SELECT
    product_id,
    JSONExtractString(product_metadata, 'category') AS category,
    JSONExtractInt(product_metadata, 'inventory_count') AS inventory
FROM products;
</data_structure_notes>
```

## 예시: 도메인 용어 {#example-terminology}

비즈니스 용어를 기술 구현에 매핑하세요:

```xml
<terminology>
When users refer to "conversions", they mean:
- For e-commerce: transactions WHERE transaction_type = 'purchase'
- For SaaS: subscriptions WHERE subscription_status = 'active' AND first_payment_date IS NOT NULL

"Churn" is calculated as:
COUNT(DISTINCT user_id) WHERE last_active_date < today() - INTERVAL 90 DAY
AND previous_subscription_status = 'active'

"DAU" (Daily Active Users) means:
COUNT(DISTINCT user_id) WHERE activity_date = today()

"Qualified leads" must meet ALL criteria:
- lead_score >= 70
- company_size >= 50
- budget_confirmed = true
- contact_role IN ('Director', 'VP', 'C-Level')
</terminology>
```
