새로운 ClickHouse Cloud 배포를 설계하거나 기존 워크로드를 개선할 때 이 플레이북을 활용하십시오. 이 플레이북은 스키마(schema), 쿼리, 수집, 인프라에 관한 결정을 직접 검증할 수 있는 측정 결과와 연결합니다. 스키마 및 쿼리 관련 권장 사항은 대부분 자체 관리형 ClickHouse에도 적용됩니다.

| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |

| 기존 워크로드 개선 | [병목을 진단](#diagnose-the-bottleneck)하고, 한 번에 하나의 요소만 변경한 다음 [결과를 벤치마크](#benchmark-the-result)하십시오.                                                   |
| 느린 쿼리 조사   | [쿼리 최적화(query optimization) 가이드](/ko/guides/clickhouse/performance-and-monitoring/query-optimization)를 참고하여 해당 쿼리의 이력과 실행 계획(Execution Plan)을 검토하십시오. |

## 워크로드 프로파일링 {#profile-the-workload}

현재 지연 시간, 처리량, 리소스 사용량을 기록한 다음 측정 가능한 목표를 정의하십시오. 쿼리 지연 시간, 수집 지연 시간, 데이터 최신성은 서로 구분해야 합니다. 어느 하나를 개선하면 다른 쪽의 작업 부담이 늘어날 수 있습니다.

대표적인 쿼리와 필터(filter) 값, 실행 주기, 동시성, 수집 속도, 데이터 볼륨, 증가 추이, 보존 기간을 파악하십시오. 테넌트 간 차이와 최대 부하도 함께 파악하십시오. 회귀 오류가 발생했다면 데이터, 스키마(schema), 버전, 서비스 크기, 클라이언트 동작의 변경 사항을 기록하십시오.

Cloud에서는 [쿼리 인사이트](/ko/products/cloud/features/sql-console-features/query-insights)를 통해 쿼리 패턴(query patterns)과 리소스 사용량을 확인할 수 있습니다. 사용자 정의 분석이 필요하면 모든 레플리카를 대상으로 [`system.query_log`](/ko/reference/system-tables/query_log)를 쿼리하십시오:

```sql
SELECT
    normalized_query_hash,
    count() AS executions,
    round(avg(query_duration_ms)) AS avg_ms,
    quantile(0.95)(query_duration_ms) AS p95_ms,
    sum(query_duration_ms) AS total_duration_ms,
    avg(read_rows) AS avg_read_rows,
    max(memory_usage) AS max_memory_bytes,
    any(query) AS example_query
FROM clusterAllReplicas('default', merge('system', '^query_log'))
WHERE event_time >= now() - INTERVAL 1 DAY
    AND type = 'QueryFinish'
    AND is_initial_query = 1
    AND query_kind = 'Select'
GROUP BY normalized_query_hash
ORDER BY total_duration_ms DESC
LIMIT 20;
```

이 쿼리는 성공한 쿼리 패턴(query patterns)을 누적 소요 시간 기준으로 순위를 매깁니다. 성공한 실행만으로는 시간 초과나 메모리 한도 예외가 드러나지 않을 수 있으므로, 쿼리 인사이트에서 실패한 쿼리도 함께 확인하십시오. 이 쿼리를 실행하려면 각 레플리카의 시스템 테이블에 대한 액세스 권한이 필요합니다. 로그는 비동기로 플러시되므로 최근 실행 내역이 바로 표시되지 않을 수 있습니다.

`default` 클러스터는 ClickHouse Cloud에서 사용할 수 있습니다. 단일 노드로 배포한 환경에서는 `FROM` 표현식을 `system.query_log`로 대체하십시오. 자세한 분석 방법은 [느린 쿼리 진단](/ko/guides/clickhouse/performance-and-monitoring/diagnose-slow-queries)을 참조하십시오.

## 병목 진단하기 {#diagnose-the-bottleneck}

ClickHouse는 `MergeTree` 데이터를 정렬되고 압축된 파트에 저장합니다. 백그라운드 머지는 여러 파트를 하나로 통합합니다. 희소 기본 인덱스(sparse primary index)를 사용하면 쿼리가 각 파트 내의 그래뉼을 건너뛸 수 있습니다. 효과적인 최적화는 읽어 들이는 데이터의 양이나 해당 데이터를 처리하는 작업량을 줄이는 것입니다.

먼저 테이블 정의(table definition)와 쿼리 실행 계획(query plan)을 확인하십시오. 아래의 테이블과 쿼리를 실제 사용하는 테이블과 쿼리로 대체하십시오:

```sql
SHOW CREATE TABLE database_name.table_name;

EXPLAIN indexes = 1
SELECT column_name
FROM database_name.table_name
WHERE filter_column = 'value';
```

선택된 파트와 그래뉼을 전체 합계와 비교하여 확인하십시오. 그런 다음 쿼리 로그(query log)에 기록된 실제 읽은 행 수, 읽은 바이트 수, 소요 시간, 메모리 사용량(memory usage)과 대조하십시오. 테이블 전체를 집계하는 경우에는 대규모 스캔이 적절할 수 있으므로, 쿼리의 요구 사항에 비추어 판단하십시오.

| 관찰 내용                           | 확인할 항목                                                      | 다음 단계 예시                                                     |
| ------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------ |
| 선택도가 높은 필터인데도 대부분의 그래뉼을 읽음      | `EXPLAIN`의 기본 키 프루닝                                         | 순서 지정 키를 필터에 맞게 조정하거나, 프로젝션(projection) 또는 스킵 인덱스 적용을 검토합니다. |
| 활성 데이터 파트(active parts)가 계속 증가함 | `system.parts` 및 `system.merges`의 삽입 크기, 파티션 fan-out, 머지 활동 | 배치 삽입이나 비동기 삽입(asynchronous inserts)을 사용하거나, 파티션 단편화를 줄입니다.  |
| 반복 실행 시 훨씬 빨라짐                  | 캐시 활동 및 서비스 수명 주기                                           | 콜드 실행과 웜 실행을 구분하여 비교하고, 작업 집합을 줄이거나 반복 작업을 미리 계산합니다.         |
| 조인이 메모리를 과도하게 사용함               | 조인 카디널리티(cardinality), 입력, 알고리즘                             | 입력을 줄이거나, 딕셔너리 사용을 검토하거나, 메모리 사용량이 제한된 알고리즘을 테스트합니다.         |
| 동시성이 높아지면 지연 시간이 증가함            | CPU, 메모리, 수집, 경합 중인 쿼리                                      | 쿼리당 작업량을 줄인 후 스케일링 또는 격리성(isolation)을 검토합니다.                 |

스키마(schema)나 설정을 변경하기 전에 [쿼리 병목 격리](/ko/guides/clickhouse/performance-and-monitoring/isolate-query-bottlenecks)를 참고하여 가설을 검증하십시오.

## 스키마(schema) 설계 {#design-the-schema}

### 정확성을 위한 엔진 선택 {#choose-an-engine-for-correctness}

레코드가 변경되는 방식과 쿼리에서 레코드를 해석해야 하는 방식에 따라 엔진을 선택하십시오.

| 엔진                                                      | 일반적인 용도                                                                              |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `MergeTree`                                             | 일반적인 추가 전용(append-only) 분석.                                                          |
| `ReplacingMergeTree`                                    | 레코드의 여러 버전을 저장하며, 정렬 키를 기준으로 결국 중복 제거가 이루어집니다. 정확성이 필요한 경우 쿼리 시점에 적절한 중복 제거를 적용하십시오. |
| `AggregatingMergeTree`                                  | 집계 상태(aggregate states)를 저장하며, 일반적으로 증분형 materialized view를 통해 데이터가 채워집니다.           |
| `SummingMergeTree`                                      | 합산 가능한 카운터 및 롤업. 아직 머지되지 않은 행(rows)이 있으므로 쿼리에서 여전히 집계가 필요할 수 있습니다.                   |
| `CollapsingMergeTree` 또는 `VersionedCollapsingMergeTree` | 명시적인 상태(state) 레코드와 취소 레코드를 사용하며, 엔진별 쿼리 요구 사항을 따라야 합니다.                             |

백그라운드 머지는 쿼리 실행 전에 모든 버전이나 집계 행이 통합된다는 것을 보장하지 않습니다. 엔진의 의미 체계는 [`MergeTree` 엔진 계열 참고 문서](/ko/reference/engines/table-engines/mergetree-family)에서 확인하십시오.

### 순서 지정 키를 쿼리에 맞추기 {#align-the-ordering-key-with-queries}

테이블의 `ORDER BY`는 물리적 정렬 순서(sort order)를 정의합니다. 프라이머리 키는 기본적으로 정렬 키와 동일하며, 희소 인덱스(sparse index)를 결정합니다. 두 키 모두 고유성을 보장하지는 않습니다.

자주 사용되면서 선택도가 높은 필터에 쓰이는 컬럼을 우선적으로 고려하십시오. 유용한 필터 컬럼 중에서는 카디널리티(cardinality)가 낮은 컬럼을 키 앞쪽에 배치하면 지역성(locality)과 압축 효율이 향상될 수 있습니다. 다만 카디널리티만으로는 컬럼을 키에 포함할 이유가 되지 않습니다.

예를 들어 항상 테넌트와 시간으로 필터링하는 쿼리에는 `(tenant_id, event_time)`이 유리할 수 있습니다. 반면 모든 테넌트를 대상으로 하는 쿼리에는 다른 순서가 필요할 수 있습니다. 접근 패턴상 타당하다면 타임스탬프나 식별자를 선두 컬럼으로 두는 것도 적절합니다.

키는 꼭 필요한 컬럼만으로 간결하게 구성하고, 대표적인 쿼리로 후보 키를 테스트하십시오. `ORDER BY tuple()`은 프라이머리 인덱스 프루닝을 전혀 제공하지 않으므로, 이러한 트레이드오프를 감수하기로 한 경우에만 사용하십시오. 자세한 내용은 [프라이머리 키 선택](/ko/concepts/best-practices/choosing-a-primary-key)을 참조하십시오.

### 의미를 보존하는 타입 사용 {#use-types-that-preserve-meaning}

더 작은 표현 방식을 사용하면 저장소, 메모리, 스캔(Scan) 비용을 줄일 수 있습니다. 단, 정보가 손실되지 않는 범위에서 선택하십시오.

* 향후 증가분까지 고려하여 예상 범위를 충분히 수용하는 정수(integer) 크기를 사용하고, 정확한 십진 연산이 필요하면 `Decimal`을 사용하십시오.
* 반복되는 문자열에는 `LowCardinality(String)`을, 제한된 값 집합에는 `Enum`을 고려하십시오.
* 초 미만 정밀도가 필요하면 `DateTime64`를 사용하고, 그렇지 않으면 `DateTime` 또는 `Date`를 고려하십시오.
* 값이 없다는 것 자체가 별도의 의미를 가지는 경우 `Nullable`을 사용하십시오. 결측값을 0이나 빈 문자열로 대체하는 것은 해당 값이 도메인에서 유효한 기본값인 경우에만 허용됩니다.
* 안정적이고 자주 쿼리되는 필드에는 타입이 지정된 컬럼을 명시적으로 사용하십시오. 구조가 계속 변하는 데이터에는 `JSON`을, 키-값 형태에 적합한 데이터에는 `Map`을 검토하십시오.

변경 후에는 압축된 크기와 쿼리 성능(query performance)을 측정하십시오. 자세한 내용은 [데이터 타입 선택](/ko/concepts/best-practices/select-data-type), [JSON 사용](/ko/concepts/best-practices/json-type), [ClickHouse의 압축](/ko/guides/clickhouse/data-modelling/compression/compression-in-clickhouse)을 참조하십시오.

### 데이터 관리를 위한 파티션 구성 {#partition-for-data-management}

파티션은 보존 기간과 데이터 관리 작업을 기준으로 설계하십시오. 서로 다른 파티션에 속한 파트는 머지되지 않으므로, 파티션 카디널리티(cardinality)가 지나치게 높으면 작은 데이터 파트(small parts)가 많이 생성되어 오버헤드가 증가할 수 있습니다.

파티셔닝을 사용하지 않거나 월 단위 또는 연 단위로 파티셔닝하는 방식이 좋은 출발점이 될 수 있습니다. 데이터 볼륨과 보존 기간상 필요하다면 일 단위 파티션도 적합할 수 있습니다. high-cardinality 식별자(identifiers)를 기준으로 파티셔닝하기 전에 파트의 개수와 크기를 먼저 검토하십시오.

파티션 프루닝은 쿼리에서 파티션 표현식(partition expression)에 조건을 지정할 때 효과가 있지만, 적절한 순서 지정 키(ordering key)를 대신하지는 못합니다. 자세한 내용은 [파티셔닝 키 선택](/ko/concepts/best-practices/partitioning-keys)을 참조하십시오.

### 반복 작업 사전 계산 {#precompute-repeated-work}

| 접근 방식                 | 사용 시점                                                  | 고려 사항                                                                               |
| --------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 증분형 materialized view | 반복되는 집계나 변환을 삽입 시점(insert time)으로 옮길 수 있는 경우           | 대상 테이블 저장소, 삽입 작업, 기존 데이터 백필. 소스 테이블의 모든 변경 사항이 자동으로 반영되는 것이 아니라 새로 삽입된 블록만 처리됩니다. |
| 프로젝션(projection)      | 다른 접근 패턴에 별도의 정렬 순서(sort order)나 지원되는 사전 계산 표현이 필요한 경우 | 저장소 및 삽입 오버헤드, 기존 데이터의 머티리얼라이즈, 쿼리 및 ClickHouse 버전과의 호환성                           |

쿼리가 의도한 프로젝션을 사용하는지 확인하십시오. materialized view의 경우 집계 및 UPDATE 의미 체계를 검사하십시오. 자세한 내용은 [materialized view와 프로젝션 비교](/ko/concepts/features/projections/materialized-views-versus-projections) 및 [데이터 백필](/ko/guides/clickhouse/data-modelling/backfilling)을 참조하십시오.

### 조인 및 스캔 작업 줄이기 {#reduce-join-and-scan-work}

업데이트 모델상 가능하다면 자주 액세스하는 속성은 비정규화하십시오. 키-값 조회에는 딕셔너리 사용을 고려하되, 중복 키와 변경되는 차원(dimensions)에 필요한 동작은 그대로 유지해야 합니다.

그래도 남는 조인은 실행 계획과 입력 카디널리티(cardinalities)를 확인하십시오. 최신 ClickHouse 버전은 조인 순서를 재배치할 수 있으므로, SQL 작성 순서에만 의존하지 말고 실제 빌드 측(build side)을 확인하십시오. 우선 기본 알고리즘을 사용하고, 메모리 사용량이나 실행 시간에서 구체적인 문제가 드러날 때 다른 알고리즘을 테스트하십시오. 지원되는 조인 유형(join type)은 알고리즘마다 다릅니다.

필요한 컬럼만 조회하십시오. 선택도가 높은 필터를 적용하고, `PREWHERE`와 프라이머리 인덱스 프루닝으로 읽기가 줄어드는지 확인하십시오. 데이터 분포와 프레디케이트 특성상 충분히 많은 그래뉼을 건너뛰어 저장소 및 평가 비용을 상쇄할 수 있을 때 스킵 인덱스를 추가하십시오.

[조인 최소화 및 최적화](/ko/concepts/best-practices/minimize-optimize-joins), [데이터 건너뛰기 인덱스(data skipping indices)](/ko/concepts/best-practices/using-data-skipping-indices), [쿼리 최적화(query optimization)](/ko/guides/clickhouse/performance-and-monitoring/query-optimization)를 참조하십시오.

## 수집 및 보존 기간 최적화 {#optimize-ingestion-and-retention}

작은 삽입이 자주 발생하면 머지가 파트를 통합하는 속도보다 파트가 생성되는 속도가 더 빨라질 수 있습니다. client-side 배치 또는 [비동기 삽입(asynchronous inserts)](/ko/concepts/features/operations/insert/asyncinserts)을 사용하는 것이 좋습니다. 행 크기, 처리량, 최신성 요구 사항을 고려하여 배치 크기를 결정한 다음, 활성 데이터 파트(active parts)와 머지 활동을 모니터링하십시오.

기본값을 그대로 가정하지 말고 실제로 적용된 설정을 확인하십시오.

```sql
SELECT name, value, changed
FROM system.settings
WHERE name IN
(
    'async_insert',
    'wait_for_async_insert',
    'async_insert_max_data_size',
    'async_insert_busy_timeout_ms'
);
```

비동기 삽입(asynchronous inserts)을 사용할 때는 `wait_for_async_insert = 1`을 유지하십시오. 그래야 확인 응답이 플러시 완료 후에 반환되어 클라이언트가 플러시 오류를 받을 수 있습니다. `0`으로 설정하면 확인 응답은 버퍼링 여부만 확인하므로, 클라이언트가 성공 응답을 받은 후에도 오류가 발생할 수 있습니다.

타사 수집 도구를 사용하는 경우 일괄 처리, 재시도, 중복 제거, 오류 처리, 백프레셔(backpressure)를 엔드 투 엔드로 검사하십시오. 재시도로 인해 중복이 생기지 않는다고 가정하지 말고 커넥터의 전달 보장 수준을 확인하십시오. 자세한 내용은 [삽입 전략 선택](/ko/concepts/best-practices/selecting-an-insert-strategy)을 참조하십시오.

대규모 뮤테이션을 자주 실행하거나 `OPTIMIZE TABLE ... FINAL`을 일상적으로 실행하지 마십시오. 상당한 양의 재작성 및 머지 작업이 발생할 수 있습니다. 쿼리 정확성 요구 사항을 충족하는 업데이트 전략을 선택하십시오. 지원되는 보존 정책에는 `TTL`을 사용하고, 파티션 전체를 제거해야 할 때는 파티션 수준 삭제를 사용하십시오. Cloud에서는 저장소 계층화에 `TTL ... TO VOLUME`을 사용하지 않습니다.

[뮤테이션 피하기](/ko/concepts/best-practices/avoid-mutations), [optimize final 피하기](/ko/concepts/best-practices/avoid-optimize-final), [TTL로 데이터 관리](/ko/concepts/features/operations/delete/ttl)를 참조하십시오.

## Cloud 리소스 계획 {#plan-cloud-resources}

### 캐시 상태 고려하기 {#account-for-cache-state}

ClickHouse Cloud는 컴퓨트와 객체 스토리지를 분리합니다. 따라서 캐시 상태에 따라 지연 시간이 크게 달라질 수 있습니다. 쿼리 결과 캐시(Query Result Cache)를 비활성화하더라도 반복 실행되는 쿼리는 캐시된 데이터를 읽을 수 있습니다.

첫 실행과 반복 실행의 동작은 따로 측정하십시오. 비교 결과에 영향을 줄 수 있는 서비스 유휴 상태 전환, 크기 조정, 라우팅, 백그라운드 활동도 기록해 두십시오. [자동 유휴 상태 전환](/ko/products/cloud/features/autoscaling/idling)이 적합한지는 요구되는 시작 지연 시간을 기준으로 평가하십시오.

리소스를 늘리기 전에 먼저 프루닝과 사전 집계(pre-aggregation)로 작업 집합을 줄이십시오. 예열이 필요하다면 대표적인 쿼리를 사용하고, 해당 쿼리의 리소스 사용량도 비용 평가에 포함하십시오.

쿼리 결과 캐시는 데이터 캐시와 별개입니다. 애플리케이션의 최신성 요구 사항상 캐시된 결과를 사용해도 되는 경우에만 활성화하십시오. 자세한 내용은 [캐시](/ko/concepts/features/performance/caches/caches) 및 [쿼리 캐시](/ko/concepts/features/performance/caches/query-cache)를 참조하십시오.

### 측정된 워크로드에 맞춘 용량 산정 {#size-for-the-measured-workload}

CPU, 메모리, 동시성, 수집을 함께 평가하십시오. 개별 쿼리뿐만 아니라 최대 부하 상황도 테스트하십시오. 단일 쿼리 기준으로는 목표를 충족하는 서비스라도 쿼리와 수집이 동시에 발생하면 목표를 달성하지 못할 수 있습니다.

수직 확장은 레플리카당 리소스를 조정하고, 수평 확장은 레플리카 수를 조정합니다. 각 방식의 지원 여부와 자동화 수준은 요금제 등급과 프로필에 따라 다릅니다. 기존 시스템 메모리 대비 고정 비율로 용량을 산정하지 말고 [스케일링 개요](/ko/products/cloud/features/autoscaling/overview)와 [서비스 한도](/ko/products/cloud/guides/best-practices/usagelimits)를 참고하십시오.

워크로드와 예산에 맞게 스케일링 상한과 하한을 설정하십시오. 전체 리소스 사용량도 측정하십시오. 쿼리가 더 빠르더라도 컴퓨트를 훨씬 더 많이 사용한다면 비용은 오히려 늘어날 수 있습니다.

### 경쟁하는 워크로드 격리 {#isolate-competing-workloads}

수집, 대화형 쿼리, 배치 분석에 각각 전용 컴퓨트가 필요하다면 [웨어하우스(warehouse)](/ko/products/cloud/features/infrastructure/warehouses)를 사용하십시오. 웨어하우스 내의 서비스는 데이터를 공유하면서도 각각 별도의 컴퓨트 리소스와 엔드포인트를 제공합니다.

애플리케이션과 타사 도구가 의도한 서비스로 연결되도록 라우팅하십시오. 부하가 걸린 상태에서 동시성, 연결 풀링(Connection Pooling), 시간 초과, 재시도 동작을 검사하십시오. 격리된 워크로드와 운영 환경 워크로드를 모두 측정하여 격리가 목표를 달성하는지 확인하십시오.

## 결과 벤치마크 {#benchmark-the-result}

1. **기준값을 저장하십시오.** ClickHouse 버전, 서비스 구성, 테이블 정의(table definition), 설정, 데이터 볼륨, 대표적인 매개변수를 포함한 쿼리 텍스트(query text)를 기록합니다.
2. **워크로드를 통제하십시오.** 데이터와 동시성을 비교 가능한 수준으로 유지합니다. 수집, 머지, 백그라운드 활동을 기록합니다. 애플리케이션 지연 시간을 측정할 때는 클라이언트와 네트워크 경로도 포함합니다.
3. **캐시 시나리오를 구분하십시오.** 최초 실행 결과와 반복 실행 결과를 따로 보고합니다. 실행 성능 개선을 측정할 때는 쿼리 결과 캐시(Query Result Cache)를 비활성화하되, 데이터 캐시의 영향은 계속 고려해야 합니다. 벤치마크를 위해 운영 환경의 공유 캐시를 비우지 마십시오.
4. **한 번에 하나의 요소만 변경하십시오.** 순서 지정 키를 변경하여 읽는 그래뉼 수를 줄이는 것처럼 가설을 명확히 기술합니다.
5. **측정을 반복하십시오.** 변동성을 파악할 수 있을 만큼 충분히 실행합니다. 가장 빠른 실행 결과만 보고하지 말고, 실행 횟수와 함께 분포 또는 백분위수를 보고합니다.
6. **정확성과 트레이드오프를 확인하십시오.** 결과(result), 최신성, 삽입 처리량, 메모리, 저장소, 리소스 활용을 비교합니다. 해당되는 경우 백필 및 머티리얼라이즈 비용도 포함합니다.
7. **대표적인 부하에서 검사하십시오.** 롤아웃 전에 동시성과 수집을 다시 테스트하고, 롤백(Rollback) 계획을 마련해 둡니다.

고객이나 파트너와 결과를 공유할 때는 데이터셋 또는 재현 가능한 생성 방법, 정확한 쿼리, 구성, 측정 프로시저(procedure)를 포함하십시오. 적용 범위도 명시해야 합니다. 특정 워크로드에서 얻은 속도 향상이 전반적인 성능을 보장하지는 않습니다.

재현 가능한 시작점으로는 [쿼리 최적화(query optimization) 실습 예시](/ko/guides/clickhouse/performance-and-monitoring/query-optimization-example)를 참조하십시오.

## 배포 체크리스트 {#deployment-checklist}

* 지연 시간, 처리량, 최신성, 가용성 목표를 정의하십시오.
* 갱신(updates) 및 중복 데이터와 관련된 엔진의 의미 체계와 정확성을 검사하십시오.
* 대표적인 필터로 순서 지정 키(ordering key)를 테스트하고 프루닝 결과를 점검하십시오.
* 데이터 타입, 파티션 수, 데이터 파트 크기, 보존 기간을 검토하십시오.
* 삽입 일괄 처리, 재시도 동작, 병합 부하를 측정하십시오.
* 뷰(view), 프로젝션, 인덱스(indexes)의 이점과 유지 관리 비용을 확인하십시오.
* 캐시 동작, 최대 동시성, 서로 경쟁하는 워크로드(workloads)를 테스트하십시오.
* 스케일링 범위를 구성하고 통합을 적절한 엔드포인트로 라우팅하십시오.
* 재현 가능한 기준값, 모니터링 기준, 롤백(Rollback) 절차를 기록하십시오.
