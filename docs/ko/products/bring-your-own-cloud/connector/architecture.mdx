## 구성 요소 {#components}

ClickHouse Connector는 세 개의 데몬을 실행하며, 모두 `clicklink` 바이너리에 내장되어 있습니다:

* **실행기(executor)** 는 커넥터 엔드포인트로 향하는 아웃바운드 명령 채널을 유지하며, ClickHouse Cloud가 사용자의 클러스터에서 관리하는 서비스에 대해 전송하는 수명 주기 명령을 적용합니다. 해당 명령어에는 생성, 스케일링, 중지 및 시작, 재시작, 백업 및 백업 삭제, 삭제, 그리고 사용자가 승인한 플랫폼 업데이트가 포함됩니다. 모든 작업은 Kubernetes API 호출입니다. ClickHouse에 연결을 열지 않으며, 버킷이나 IAM에 대한 자격 증명도 보유하지 않습니다. 관리형 모드에서만 실행됩니다.
* **스크레이퍼(scraper)** 는 허용 목록에 등록된 ClickHouse 시스템 테이블을 고정된 인터벌로 읽어 그 결과를 로컬에 버퍼링합니다. 이후 인프라 메타데이터 및 상태 정보와 함께 커넥터 엔드포인트로 전송합니다.
* **Troubleshooter** 는 커넥터 엔드포인트로 향하는 아웃바운드 명령 채널을 유지하며, 활성화된 [지원 세션](/ko/products/bring-your-own-cloud/connector/support-sessions) 동안 읽기 전용 진단을 실행합니다. 세션이 활성화되어 있지 않을 때는 아무것도 실행하지 않습니다.

Kubernetes에서는 `clicklink-connector` Helm 차트가 사용자가 선택한 네임스페이스(기본값 `clicklink`)에 데몬을 배포합니다. 실행기는 단일 레플리카 배포로, 명령 상태를 영구 볼륨에 보관합니다. Linux VM에서는 데몬이 권한 없는 `clicklink` 시스템 사용자 권한으로 `clicklink-scraper`, `clicklink-troubleshooter`, `clicklink-executor` systemd unit으로 실행됩니다.

## 연결 {#connections}

커넥터가 생성하는 모든 연결은 아웃바운드입니다. 전체 목록은 다음과 같습니다.

| ------------------------------------------- | ------------------- | -------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 커넥터 엔드포인트(API)                              | 아웃바운드               | HTTPS                | mTLS 클라이언트 인증서 및 HMAC 서명 요청                                                                   | 메트릭, 커넥터 자체 메트릭, 상태를 전송하고, 서비스·인프라·백업 메타데이터를 동기화하며, 클라이언트 인증서를 갱신합니다                                                                                      |
| 커넥터 엔드포인트(API, `clicklink clctl`에서 호출)      | 아웃바운드               | HTTPS                | 커넥터의 mTLS 클라이언트 인증서 및 HMAC 서명 요청                                                              | `clicklink clctl instances create`(`POST /v1/pcm/instances`)를 실행하면 서비스 정의를 제출합니다                                                                          |
| 커넥터 엔드포인트(문제 해결 도구 명령 채널)                   | 아웃바운드               | TLS 기반 WebSocket     | mTLS 클라이언트 인증서 및 HMAC 서명 핸드셰이크                                                                | 지원 세션이 활성화된 동안에만 진단 명령을 전달합니다                                                                                                                             |
| 커넥터 엔드포인트(실행기 명령 채널)                        | 아웃바운드               | TLS 기반 WebSocket     | mTLS 클라이언트 인증서 및 HMAC 서명 핸드셰이크                                                                | 관리형 서비스의 수명 주기 명령을 전달하고 진행 상황과 결과를 반환합니다. 문제 해결 도구 채널과는 분리되어 있습니다                                                                                         |
| 등록 엔드포인트                                    | 아웃바운드               | HTTPS                | 일회용 등록 토큰(토큰 사용 시) 또는 HMAC(최초 인증서 서명 시). mTLS 미사용                                             | 설정 과정에서의 토큰 사용 및 최초 인증서 발급                                                                                                                                |
| ClickHouse 클러스터                             | 아웃바운드, 사용자 환경 내부    | ClickHouse 네이티브 프로토콜 | bcrypt 해시로 저장되는 읽기 전용 전용 사용자 `pcm_scraper` 및 `pcm_troubleshooter`                             | 스크레이프 및 세션 진단을 위한 시스템 테이블 읽기와 스크레이퍼의 로그 테이블 플러시. 실행기는 ClickHouse 연결을 열지 않습니다                                                                              |
| Kubernetes API 서버(프로비저닝된 모든 배포, 두 설치 대상 모두) | 아웃바운드, 사용자 환경 내부    | HTTPS                | 역할(Role)에 바인딩된 ServiceAccount. 관리형 모드에서는 어드미션 정책으로 제한되는 `pcm-executor` ServiceAccount         | 문제 해결 도구의 읽기 전용 워크로드 조회, 서비스 네임스페이스 내 실행기의 수명 주기 쓰기, 승인된 플랫폼 업데이트 중 플랫폼 네임스페이스 내 워크로드 쓰기. Kubernetes 설치 환경에서는 데몬이 자동 갱신된 클라이언트 인증서를 mTLS Secret에 다시 저장합니다 |
| Amazon ECR(실행기, 관리형 모드 전용)                  | 아웃바운드               | HTTPS                | 직접 플랫폼 액세스 시 커넥터 EC2 VM의 인스턴스 프로파일로 수임하는 읽기 전용 풀 역할(role). 기타 ECR 차트 레지스트리에는 환경의 AWS 자격 증명 사용 | 플랫폼 동기화 또는 생성 시 차트를 풀하기 위한 레지스트리 로그인, 플랫폼 업데이트 중 image 존재 여부를 확인하는 `DescribeImages`                                                                       |
| AWS STS(실행기, 관리형 모드 전용)                     | 아웃바운드               | HTTPS                | 직접 플랫폼 액세스에는 커넥터 EC2 VM의 인스턴스 프로파일, 기타 ECR 차트 레지스트리에는 구성된 AWS 자격 증명 체인                        | 직접 플랫폼 차트 로그인 및 image 확인을 위해 읽기 전용 풀 역할(role)을 수임하며, 기타 ECR 로그인용 자격 증명을 제공할 수도 있습니다. 실행기가 호출하는 클라우드 API는 ECR과 STS뿐입니다                                     |
| 컨테이너 레지스트리                                  | 아웃바운드, 클러스터 노드에서 시작 | HTTPS                | 노드 아이덴티티: 등록한 노드 역할(role)에 ClickHouse가 부여하는 읽기 전용 풀 역할(role), 또는 image를 가져온 후에는 자체 레지스트리      | 관리형 서비스 및 플랫폼 구성 요소의 image 풀. 클러스터가 풀하며, ClickHouse는 클러스터에 아무것도 푸시하지 않습니다                                                                                 |
| ID 공급자의 JWKS 엔드포인트(gateway가 활성화된 경우에만)      | 아웃바운드               | HTTPS                | 없음(공개 서명 키)                                                                                   | 세션 gateway에 제시된 OIDC ID 토큰을 검증합니다                                                                                                                         |

모든 API 요청에는 메서드, 경로, 타임스탬프, 본문 해시에 대한 HMAC-SHA256 서명이 담긴 `Authorization` 헤더가 포함됩니다. 따라서 TLS 채널 내부에서도 요청을 재전송하거나 전송 중에 변조할 수 없습니다.

인바운드 측면에서는 각 데몬이 로컬 상태 확인 포트를 하나씩 노출합니다. 스크레이퍼는 8082, 문제 해결 도구는 8084, 실행기는 8086입니다. 이 포트는 `/livez`, `/readyz`, `/healthz`와 함께 `/metrics`에서 데몬의 Prometheus 메트릭을 제공하며, 별도의 메트릭 포트는 없습니다. 실행기의 로컬 명령 API는 루프백에만 바인딩되며, 이를 노출하는 Service는 없습니다. 그 밖의 리스너는 선택적으로 활성화하는 세션 gateway뿐입니다. 자세한 내용은 [지원 세션](/ko/products/bring-your-own-cloud/connector/support-sessions)을 참조하십시오. ClickHouse Cloud는 이들 중 어디에도 연결하지 않습니다.

## 인증서 수명 주기 {#certificate-lifecycle}

커넥터는 스스로 발급받아 관리하는 클라이언트 인증서로 엔드포인트에 인증합니다. 세 데몬 모두 동일한 인증서를 제시합니다.

* **등록.** `clicklink clctl init`은 로컬에서 private key와 인증서 서명 요청(CSR)을 생성합니다. CSR에는 조직 ID가 common name으로, 엔드포인트 호스트가 유일한 DNS SAN으로 담깁니다. private key는 사용자 환경 밖으로 나가지 않습니다.
* **최초 발급.** `init`은 HMAC으로 인증하여 `/v1/pcm/cert/sign` 등록 서명 엔드포인트에 CSR을 제출합니다. 해당 조직에 만료되지 않은 인증서가 이미 있으면 엔드포인트는 409로 요청을 거부합니다. 이 경우 CLI는 기존 인증서로 진행하는 방법과 `--force`로 대체하는 방법을 안내합니다.
* **자동 갱신.** 세 데몬 모두 12시간마다 인증서 수명을 확인합니다. 남은 기간이 10일에 도달하면 `/v1/pcm/cert/renew`(mTLS 및 HMAC)를 통해 30일짜리 갱신 인증서를 요청합니다. Kubernetes에서는 정확한 이름을 지정한 RBAC 권한 부여를 통해 갱신된 인증서가 `clicklink-mtls` 시크릿에 다시 기록되고, VM에서는 각 데몬이 `/etc/clicklink/tls`에 기록합니다. 갱신에는 운영자의 별도 조치가 필요하지 않습니다.

커넥터는 시스템 trust store를 기준으로 엔드포인트의 서버 인증서를 검증합니다. `api.tls.ca_file`(VM) 또는 `api.tls.caFile`(Helm)이 설정되어 있으면, 등록 번들의 CA 체인이 해당 루트 인증서에 추가됩니다.

### 사용자 환경 외부로 전송되는 데이터 {#what-leaves}

* **허용 목록에 포함된 시스템 테이블의 메트릭.** 스크레이퍼의 기본 대상은 `metric_log`, `asynchronous_metric_log`, `tables`, `warnings`, `server_settings`입니다. 허용 목록은 명시적으로 구성되며, 스크레이퍼는 허용 목록에 없는 데이터를 읽지 않습니다.
* **인프라 메타데이터.** API를 통해 동기화되는 서비스, 인프라, 백업 인벤토리입니다. 관리형 서비스의 경우 서비스 상태, 현재 및 예상 레플리카 수, 실행 중인 서버 버전과 구성 버전이 포함됩니다.
* **상태 및 자체 메트릭.** 구성 요소 상태와 커넥터 자체의 운영 메트릭입니다. 실행기의 하트비트는 명령 채널의 연결 여부도 보고합니다. 또한 마지막 플랫폼 업데이트 결과, 플랫폼 구성 요소 버전, 마지막으로 적용한 bundle의 다이제스트도 포함합니다. VM에 설치한 경우에는 Kubernetes 액세스 번들의 상태가 `ok`, `expiring`, `expired` 중 무엇인지, 또는 번들이 없는지도 함께 보고합니다.
* **명령 결과.** 실행기가 실행하는 각 수명 주기 명령에 대해 수렴 중의 진행 상황과 최종 성공 또는 실패 여부를 전송하며, 실패 시에는 오류 메시지도 함께 전송합니다.
* **사용자가 제출한 서비스 정의.** `clicklink clctl instances create`는 환경 ID, 클라우드 및 리전, 서비스 이름, 버킷 이름과 IAM 역할 ARN, 멱등성 키를 전송합니다. 또한 default 사용자 비밀번호의 해시 2개(SHA-256 및 이중 SHA-1)도 전송합니다.
* **지원 세션 출력.** 사용자가 활성화한 세션 동안 실행된 읽기 전용 진단의 결과이며, 마스킹을 거친 후 전송됩니다.

### 기본적으로 외부로 절대 전송되지 않는 항목 {#what-never-leaves}

* **스크레이프 경로의 원본 쿼리 텍스트.** `system.query_log`는 기본 스크레이프 대상에서 제외됩니다. 이 테이블의 쿼리 컬럼에는 리터럴 값이 포함될 수 있고, 그 안에 PII나 시크릿이 담길 수 있기 때문입니다. 이를 다시 추가하는 것은 배포별 재정의입니다. 기본 세션 테이블 허용 목록에는 실행 중인 쿼리의 텍스트를 보여주는 `system.processes`가 포함되어 있습니다. 이를 정리하는 방법은 [지원 세션](/ko/products/bring-your-own-cloud/connector/support-sessions)을 참조하십시오.
* **테이블 데이터와 백업.** 사용자 계정 내의 버킷에 그대로 남아 있습니다. 실행기는 해당 버킷에 대한 자격 증명을 보유하지 않으므로 읽을 수 없습니다.
* **자격 증명.** `init`은 설정 파일에 자격 증명을 기록하지 않습니다. ClickHouse는 커넥터 사용자 비밀번호의 bcrypt 해시만 저장하며, 시크릿은 Kubernetes 시크릿 또는 호스트의 root 전용 읽기 파일에 보관됩니다. 관리형 서비스의 default 사용자 비밀번호는 사용자 측에서 생성되어 한 번만 표시되며, 전송되는 것은 해시뿐입니다. 스크레이프 경로와 동기화 경로 어디에서도 자격 증명을 전송하지 않습니다.
* **마스킹되지 않은 troubleshooter 출력.** Troubleshooter가 반환하는 모든 내용은 외부로 나가기 전에 민감 정보 마스킹 패턴(기본 제공 패턴 및 사용자가 정의한 패턴)을 거칩니다. [지원 세션](/ko/products/bring-your-own-cloud/connector/support-sessions)을 참조하십시오.

## 신뢰 경계 {#trust-boundaries}

* **사용자 환경이 경계입니다.** ClickHouse Cloud는 커넥터가 전송하는 데이터만 수신합니다. 여기에는 스크레이프 결과, 하트비트 및 상태, 명령 결과, 그리고 활성 지원 세션이 반환하는 내용이 포함됩니다. ClickHouse Cloud가 사용자 환경 내부로 먼저 연결을 시작하는 일은 없습니다.
* **세션 gateway는 사용자가 소유합니다.** Ingress를 통해 노출하도록 직접 설정하지 않는 한, 세션 gateway는 사용자 환경 내부에서만 접근할 수 있습니다(Kubernetes에서는 `kubectl port-forward`를 통해, VM에서는 로컬로). ClickHouse Cloud는 세션 gateway에 연결하지 않습니다.
* **ClickHouse 액세스는 읽기 전용입니다.** `pcm_scraper` 및 `pcm_troubleshooter` 사용자가 보유한 권한은 테이블별 `SELECT` 권한, 스크레이퍼의 `READ ON REMOTE`(`clusterAllReplicas()`에 필요), 그리고 스크레이퍼 전용 `SYSTEM FLUSH LOGS` 권한 1개뿐입니다. `INSERT`, DDL 또는 사용자 관리 권한은 부여되지 않습니다. 실행기에는 ClickHouse 사용자가 없습니다. 정확한 목록은 [권한 모델](/ko/products/bring-your-own-cloud/connector/reference/privilege-model)에서 확인할 수 있습니다.
* **스크레이퍼와 Troubleshooter는 사용자의 클러스터를 변경할 수 없습니다.** 이들의 RBAC는 커넥터 네임스페이스와 서비스 네임스페이스의 Roles에서 부여됩니다. 해당 Roles는 워크로드 리소스에 대한 읽기 전용 동사(verb)와, 이름이 정확히 일치하는 커넥터 자체 시크릿에 대한 액세스만 허용합니다. `exec`, `delete`, `patch` 권한은 없습니다.
* **실행기는 `pcm-executor`로서 서비스 네임스페이스의 클러스터 상태를 변경합니다.** 실행기는 서비스 접두사(기본값 `ns-`)가 붙은 네임스페이스를 생성 및 삭제하며, 파드를 재시작하기 위해 파드를 삭제합니다. 해당 네임스페이스 내에서는 ClickHouseCluster, Backup, ScalingOverride 객체와 서비스에 필요한 시크릿, ServiceAccount, Service를 작성합니다. 또한 스크레이퍼에 읽기 액세스를 부여하는 Role과 RoleBinding도 작성합니다. ValidatingAdmissionPolicy는 해당 ServiceAccount가 접두사 범위 밖에서 수행하는 모든 쓰기를 거부합니다. 예외는 모두 실행기의 홈 네임스페이스 내에 있으며, 자체 토큰 갱신, `clicklink-instance-registry` ConfigMap, 그리고 Kubernetes의 경우 mTLS 시크릿에 저장되는 갱신된 클라이언트 인증서가 이에 해당합니다. 이 정책은 평가할 수 없을 때 요청을 차단(fail closed)합니다. 어드미션은 읽기 작업에는 적용되지 않으므로, 해당 리소스 유형에 대한 실행기의 읽기는 접두사로 제한되지 않습니다.
* **실행기는 사용자가 승인한 업데이트 중에만 `pcm-platform`으로서 플랫폼 네임스페이스를 변경합니다.** `clicklink clctl platform approve`는 해당 ID의 토큰을 2시간 유효 기간으로 발급하며, 이 토큰은 갱신되지 않습니다. 실행기는 이 토큰으로 배포, Service, ConfigMap, 시크릿, Job, PodDisruptionBudget만 작성할 수 있습니다. 네임스페이스, CRD, ServiceAccount, RBAC, 웹훅 및 어드미션 구성, PriorityClass, StorageClass는 승인 과정에서 사용자의 자격 증명으로 적용됩니다. 자세한 내용은 [플랫폼 업데이트](/ko/products/bring-your-own-cloud/connector/platform-updates)를 참조하십시오.
* **실행기는 사용자의 버킷이나 IAM에 대한 자격 증명을 보유하지 않습니다.** `clicklink clctl executor prepare`는 서비스의 데이터 및 백업 버킷과 IAM 역할(role)을 생성하고, `clicklink clctl executor teardown`은 이를 제거합니다. 두 명령 모두 사용자의 자격 증명으로 실행됩니다. 이 역할은 해당 서비스의 파드만 신뢰하므로 실행기와 ClickHouse 모두 이 역할을 수임(assume)할 수 없습니다. 실행기의 클라우드 호출 대상은 Amazon ECR과 STS뿐입니다. 플랫폼 동기화나 생성 작업에서 차트를 가져올 때 레지스트리에 로그인하며, 플랫폼 업데이트 중에는 읽기 전용 풀 역할로 image를 검사합니다.
* **네트워크 정책.** Kubernetes에서 차트는 데몬마다 기본 거부(default-deny) NetworkPolicy를 렌더링합니다. 아웃바운드 트래픽은 DNS, 커넥터 엔드포인트용으로 지정한 CIDR, Kubernetes API 서버 CIDR로만 허용됩니다. 스크레이퍼와 Troubleshooter의 정책은 실행기가 관리하는 네임스페이스(실행기가 부여한 레이블로 선택) 또는 사용자가 이름으로 지정한 네임스페이스의 ClickHouse Service에 대한 트래픽도 허용합니다. 실행기의 정책에는 ClickHouse 규칙이 없습니다. 플랫폼 번들의 차트가 Amazon ECR에 있다면 ECR 및 STS 범위(또는 레지스트리 미러)를 `allowEgressCIDRs`에 추가하십시오. 추가하지 않으면 정책을 강제하는 CNI 환경에서 동기화 시 차트를 가져올 수 없습니다. 정책을 강제하는 CNI가 없으면 이 정책은 아무런 효력이 없습니다. 자세한 내용은 [구성](/ko/products/bring-your-own-cloud/connector/configuration)을 참조하십시오.
* **VM의 호스트 보안 강화.** 유닛은 로그인할 수 없는 시스템 사용자로 실행되며, `ProtectSystem=strict`, `NoNewPrivileges`, 읽기 전용 구성 경로가 적용되고 FIPS 모드가 활성화됩니다.

커넥터의 정확한 권한 부여 및 RBAC 규칙은 [권한 모델](/ko/products/bring-your-own-cloud/connector/reference/privilege-model) 참고 문서를 확인하십시오. ClickHouse가 클러스터를 직접 프로비저닝하고 운영하는 경우에는 신뢰 모델이 다르므로 [BYOC 아키텍처](/ko/products/bring-your-own-cloud/overview/architecture) 및 [BYOC 권한](/ko/products/bring-your-own-cloud/reference/privilege) 페이지를 참조하십시오.
