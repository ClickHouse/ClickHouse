Elastic에서 마이그레이션할 때 이러한 개념을 직접 관리할 필요는 없으며, [데이터 마이그레이션 가이드](/ko/clickstack/observability/migration/elastic/migrating-data)를 따르면 됩니다. 이 참고 문서는 이러한 내부 구성 요소를 직접 제어하는 **자체 관리형 ClickHouse Observability** 사용자를 위한 것입니다.
</Note>

## Elastic Stack vs 자체 관리형 ClickHouse Observability {#elastic-vs-clickstack}

Elastic Stack과 자체 관리형 ClickHouse Observability는 모두 관측성 플랫폼의 핵심 역할을 수행하지만, 각 역할에 접근하는 설계 철학은 서로 다릅니다. 이러한 역할은 다음과 같습니다.

* **UI 및 알림**: 데이터 쿼리, 대시보드 구축, 알림 관리를 위한 도구입니다.
* **스토리지 및 쿼리 엔진(query engine)**: 관측성 데이터를 저장하고 분석 쿼리를 처리하는 백엔드 시스템입니다.
* **데이터 수집 및 ETL**: 텔레메트리 데이터를 수집하고 적재 전에 처리하는 에이전트와 파이프라인입니다.

아래 표는 각 스택의 구성 요소가 이러한 역할에 어떻게 대응되는지 보여줍니다.

| **역할**                  | **Elastic Stack**                                      | **자체 관리형 ClickHouse Observability**                                   | **설명**                                                                                                                                                             |
| ----------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **UI 및 알림**             | **Kibana** — 대시보드, 검색, 알림                              | **Observability UI** — 실시간 UI, 검색, 알림                                 | 둘 다 시각화와 알림 관리를 포함한 사용자의 주 인터페이스 역할을 합니다. Observability UI는 관측성 전용으로 설계되었으며 OpenTelemetry 시맨틱과 긴밀하게 결합되어 있습니다.                                                     |
| **스토리지 및 쿼리 엔진**        | **Elasticsearch** — 역색인을 사용하는 JSON 문서 저장소              | **ClickHouse** — 벡터화 엔진을 갖춘 컬럼 지향 데이터베이스                              | Elasticsearch는 검색에 최적화된 역색인을 사용하며, ClickHouse는 구조화된 데이터와 반정형 데이터를 고속으로 분석하기 위해 컬럼형 스토리지와 SQL을 사용합니다.                                                             |
| **데이터 수집**              | **Elastic Agent**, **Beats** (예: Filebeat, Metricbeat) | **ClickHouse Observability Collector** (엣지 + 게이트웨이)                   | Elastic은 커스텀 shipper와 Fleet으로 관리되는 통합 에이전트를 지원합니다. 자체 관리형 ClickHouse Observability는 OpenTelemetry를 기반으로 하므로 벤더 중립적인 데이터 수집 및 처리가 가능합니다.                            |
| **Instrumentation SDK** | **Elastic APM agents** (독점)                            | **OpenTelemetry SDK** (자체 관리형 ClickHouse Observability에서 배포)          | Elastic SDK는 Elastic 스택에 종속됩니다. 자체 관리형 ClickHouse Observability는 주요 언어별 로그, 메트릭, 트레이스용 OpenTelemetry SDK를 기반으로 합니다.                                                |
| **ETL / 데이터 처리**        | **Logstash**, ingest pipeline                          | **ClickHouse Observability Collector** + ClickHouse materialized view | Elastic은 ingest pipeline과 Logstash로 데이터를 변환합니다. 자체 관리형 ClickHouse Observability는 materialized view와 OTel collector 프로세서를 통해 컴퓨트를 삽입 시점으로 옮겨 데이터를 효율적이고 점진적으로 변환합니다. |
| **아키텍처 철학**             | 수직 통합형, 독점 에이전트 및 포맷                                   | 개방형 표준 기반, 느슨하게 결합된 구성 요소                                             | Elastic은 긴밀하게 통합된 생태계를 구축합니다. 자체 관리형 ClickHouse Observability는 유연성과 비용 효율성을 위해 모듈성과 표준(OpenTelemetry, SQL, 객체 스토리지)을 중시합니다.                                        |

자체 관리형 ClickHouse Observability는 개방형 표준과 상호 운용성을 중시하며, 수집부터 UI까지 전 구간이 OpenTelemetry 네이티브입니다. 반면 Elastic은 독점 에이전트와 포맷을 기반으로 긴밀하게 결합된 수직 통합형 생태계를 제공합니다.

**Elasticsearch**와 **ClickHouse**는 각 스택에서 데이터 저장, 처리, 쿼리를 담당하는 핵심 엔진이므로 두 시스템의 차이를 이해하는 것이 중요합니다. 이 두 시스템이 전체 관측성 아키텍처의 성능, 확장성, 유연성을 좌우합니다. 다음 섹션에서는 데이터 모델링 방식, 수집 처리, 쿼리 실행, 스토리지 관리 등 Elasticsearch와 ClickHouse의 주요 차이점을 살펴봅니다.

## Elasticsearch vs ClickHouse {#elasticsearch-vs-clickhouse}

ClickHouse와 Elasticsearch는 서로 다른 기반 모델로 데이터를 구성하고 쿼리하지만, 많은 핵심 개념이 비슷한 역할을 합니다. 이 섹션에서는 Elastic에 익숙한 사용자를 위해 주요 개념이 ClickHouse에서 각각 무엇에 해당하는지 정리합니다. 용어는 다르지만 대부분의 관측성 워크플로는 자체 관리형 ClickHouse Observability에서 그대로 구현할 수 있으며, 대개 더 효율적으로 처리할 수 있습니다.

### 핵심 구조 개념 {#core-structural-concepts}

| **Elasticsearch** | **ClickHouse / SQL** | **설명**                                                                                                                                                                                                                                                                                              |
| ----------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **필드(Field)**     | **컬럼(Column)**       | 특정 타입의 값을 하나 이상 저장하는 데이터의 기본 단위입니다. Elasticsearch 필드는 기본 타입뿐 아니라 배열과 객체도 저장할 수 있습니다. 단, 필드는 하나의 타입만 가질 수 있습니다. ClickHouse도 배열과 객체(`Tuples`, `Maps`, `Nested`)를 지원하며, 하나의 컬럼에 여러 타입을 담을 수 있는 [`Variant`](/ko/reference/data-types/variant), [`Dynamic`](/ko/reference/data-types/dynamic) 같은 동적 타입도 지원합니다. |
| **문서(Document)**  | **행(Row)**           | 필드(컬럼)의 모음입니다. Elasticsearch 문서는 기본적으로 더 유연하여, 데이터에 따라 새 필드가 동적으로 추가됩니다(타입은 데이터로부터 추론됨). ClickHouse 행은 기본적으로 스키마에 종속되므로, 사용자는 행의 모든 컬럼 또는 일부 컬럼을 지정하여 삽입해야 합니다. ClickHouse의 [`JSON`](/ko/guides/clickhouse/data-formats/json/intro) 타입은 삽입된 데이터를 기반으로 반정형 동적 컬럼을 생성하는 동등한 기능을 지원합니다.                   |
| **인덱스(Index)**    | **테이블(Table)**       | 쿼리 실행과 저장의 단위입니다. 두 시스템 모두에서 쿼리는 행/문서를 저장하는 인덱스 또는 테이블을 대상으로 실행됩니다.                                                                                                                                                                                                                                 |
| *Implicit*        | 스키마(SQL)             | SQL 스키마는 테이블을 네임스페이스 단위로 그룹화하며, 주로 액세스 제어에 사용됩니다. Elasticsearch와 ClickHouse에는 스키마가 없지만, 두 시스템 모두 역할과 RBAC를 통해 행 수준 및 테이블 수준 보안을 지원합니다.                                                                                                                                                              |
| **클러스터(Cluster)** | **클러스터 / 데이터베이스**    | Elasticsearch 클러스터는 하나 이상의 인덱스를 관리하는 런타임 인스턴스입니다. ClickHouse에서는 데이터베이스가 논리적 네임스페이스 안에서 테이블을 구성하여, Elasticsearch의 클러스터와 동일한 논리적 그룹화를 제공합니다. ClickHouse 클러스터는 Elasticsearch와 마찬가지로 분산된 노드의 집합이지만, 데이터 자체와는 분리되어 독립적으로 동작합니다.                                                                          |

### 데이터 모델링과 유연성 {#data-modeling-and-flexibility}

Elasticsearch는 [동적 매핑(dynamic mappings)](https://www.elastic.co/docs/manage-data/data-store/mapping/dynamic-mapping)을 통한 스키마(schema) 유연성으로 잘 알려져 있습니다. 스키마를 별도로 지정하지 않으면 문서(document)가 수집될 때 필드가 생성되고 타입이 자동으로 추론됩니다. ClickHouse는 기본적으로 더 엄격하여 테이블을 명시적 스키마(explicit schema)로 정의하지만, [`Dynamic`](/ko/reference/data-types/dynamic), [`Variant`](/ko/reference/data-types/variant), [`JSON`](/ko/guides/clickhouse/data-formats/json/intro) 타입을 통해 유연성을 제공합니다. 이러한 타입을 사용하면 Elasticsearch처럼 컬럼을 동적으로 생성하고 타입을 추론하면서 반정형 데이터를 수집할 수 있습니다. 마찬가지로 [`Map`](/ko/reference/data-types/map) 타입을 사용하면 임의의 key-value 쌍을 저장할 수 있습니다. 단, 키와 값은 각각 단일 타입으로 제한됩니다.

ClickHouse의 타입 유연성 접근 방식은 더 투명하고 제어하기 쉽습니다. 타입 충돌로 인해 수집 오류가 발생할 수 있는 Elasticsearch와 달리, ClickHouse는 [`Variant`](/ko/reference/data-types/variant) 컬럼에 여러 타입이 섞인 데이터를 저장할 수 있으며 [`JSON`](/ko/guides/clickhouse/data-formats/json/intro) 타입을 통해 스키마 진화(Schema Evolution)를 지원합니다.

[`JSON`](/ko/guides/clickhouse/data-formats/json/intro)을 사용하지 않으면 스키마는 정적으로 정의됩니다. 특정 행에 값이 제공되지 않으면 해당 컬럼이 [`Nullable`](/ko/reference/data-types/nullable)로 정의된 경우(자체 관리형 ClickHouse Observability에서는 사용하지 않음) NULL이 되고, 그렇지 않으면 해당 타입의 기본값이 사용됩니다. 예를 들어 `String`은 빈 값이 됩니다.

### 수집 및 변환 {#ingestion-and-transformation}

Elasticsearch는 프로세서(예: `enrich`, `rename`, `grok`)로 구성된 ingest pipeline을 사용하여 인덱싱 전에 문서를 변환합니다. ClickHouse에서는 [**증분 구체화된 뷰(Incremental Materialized Views)**](/ko/concepts/features/materialized-views/incremental-materialized-view)로 유사한 기능을 구현할 수 있습니다. 증분 구체화된 뷰는 수신 데이터를 [필터링하거나 변환](/ko/concepts/features/materialized-views/incremental-materialized-view#filtering-and-transformation)하거나 [보강](/ko/concepts/features/materialized-views/incremental-materialized-view#lookup-table)한 후 그 결과를 대상 테이블에 삽입합니다. materialized view의 출력만 저장하면 되는 경우 `Null` 테이블 엔진에 데이터를 삽입할 수도 있습니다. 이렇게 하면 materialized view의 결과만 보존되고 원본 데이터는 폐기되므로 저장 공간을 절약할 수 있습니다.

데이터 보강을 위해 Elasticsearch는 문서에 컨텍스트를 추가하는 전용 [enrich 프로세서](https://www.elastic.co/docs/reference/enrich-processor/enrich-processor)를 제공합니다. ClickHouse에서는 [**딕셔너리**](/ko/concepts/features/dictionaries/index)를 [쿼리 시점](/ko/concepts/features/dictionaries/index#query-time-enrichment)과 [수집 시점](/ko/concepts/features/dictionaries/index#index-time-enrichment) 모두에서 활용하여 행을 보강할 수 있습니다. 예를 들어 삽입 시 [IP를 위치에 매핑](/ko/guides/use-cases/observability/build-your-own/schema-design#using-ip-dictionaries)하거나 [user agent 조회](/ko/guides/use-cases/observability/build-your-own/schema-design#using-regex-dictionaries-user-agent-parsing)를 적용할 수 있습니다.

### 쿼리 언어 {#query-languages}

Elasticsearch는 [DSL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/querydsl), [ES|QL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/esql), [EQL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/eql), [KQL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/kql)(Lucene 스타일) 쿼리 등 [여러 쿼리 언어(query language)](https://www.elastic.co/docs/explore-analyze/query-filter/languages)를 지원하지만, 조인은 제한적으로만 지원합니다. [`ES|QL`](https://www.elastic.co/docs/reference/query-languages/esql/commands/lookup-join)을 통한 **left outer join**만 사용할 수 있습니다. 반면 ClickHouse는 [모든 조인 유형(join type)](/ko/reference/statements/select/join#supported-types-of-join), [윈도우 함수](/ko/reference/functions/window-functions/index), 서브쿼리(상관 서브쿼리 포함), 공통 테이블 식(CTE)을 포함한 **완전한 SQL 구문**을 지원합니다. 따라서 관측성 신호를 비즈니스 데이터나 인프라 데이터와 연관시켜야 할 때 큰 이점이 있습니다.

자체 관리형 ClickHouse Observability는 손쉬운 전환을 위해 [UI에서 Lucene 호환 검색 인터페이스를 제공](/ko/clickstack/observability/features/search)하며, ClickHouse 백엔드를 통해 완전한 SQL도 지원합니다. 이 구문은 [Elastic 쿼리 문자열](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-query-string-query#query-string-syntax) 구문과 유사합니다. 두 구문의 자세한 비교는 [&quot;자체 관리형 ClickHouse Observability와 Elastic에서의 검색&quot;](/ko/clickstack/observability/migration/elastic/search)을 참고하십시오.

### 파일 형식과 인터페이스 {#file-formats-and-interfaces}

Elasticsearch는 JSON(및 [제한적인 CSV](https://www.elastic.co/docs/reference/enrich-processor/csv-processor)) 수집을 지원합니다. 반면 ClickHouse는 Parquet, Protobuf, Arrow, CSV 등 **70개 이상의 파일 형식**을 수집과 내보내기 모두에 지원합니다. 따라서 외부 파이프라인 및 도구와 더 쉽게 통합할 수 있습니다.

두 시스템 모두 REST API를 제공하지만, ClickHouse는 낮은 지연 시간과 고처리량 통신을 위한 **native protocol**도 함께 제공합니다. 네이티브 인터페이스(native interface)는 쿼리 진행 상황, 압축, 스트리밍을 HTTP보다 더 효율적으로 지원하며, 대부분의 운영 환경에서 수집 시 기본으로 사용됩니다.

### 인덱싱과 스토리지 {#indexing-and-storage}

  </Frame>

세그먼트 분할(sharding) 개념은 Elasticsearch 확장성 모델의 근간입니다. 각 ① [**인덱스**](https://www.elastic.co/blog/what-is-an-elasticsearch-index)는 **세그먼트(shard)**&#xB85C; 나뉘며, 각 세그먼트는 디스크에 세그먼트 형태로 저장되는 물리적인 Lucene 인덱스입니다. 세그먼트는 복원력을 위해 레플리카 세그먼트라고 하는 물리적 복사본을 하나 이상 가질 수 있습니다. 확장성을 위해 세그먼트와 레플리카를 여러 노드에 분산할 수 있습니다. 단일 세그먼트 ②는 하나 이상의 변경 불가능한(immutable) 세그먼트로 구성됩니다. 세그먼트는 Lucene의 기본 인덱싱 구조이며, Lucene은 Elasticsearch의 기반이 되는 인덱싱 및 검색 기능을 제공하는 Java 라이브러리입니다.

<Info>
  **Elasticsearch의 삽입 처리**

  Ⓐ 새로 삽입된 문서는 Ⓑ 먼저 인메모리 인덱싱 버퍼에 들어가며, 이 버퍼는 기본적으로 1초마다 플러시됩니다. 플러시된 문서의 대상 세그먼트는 라우팅 공식으로 결정되며, 해당 세그먼트에 대한 새 세그먼트가 디스크에 기록됩니다. 쿼리 효율성을 높이고 삭제되거나 업데이트된 문서를 물리적으로 제거할 수 있도록, 세그먼트는 백그라운드에서 지속적으로 더 큰 세그먼트로 머지되며 최대 크기인 5 GB에 도달할 때까지 이 과정이 계속됩니다. 다만 더 큰 세그먼트로 머지를 강제로 수행할 수도 있습니다.
</Info>

Elasticsearch는 [JVM 힙 및 메타데이터 오버헤드](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards#each-shard-has-overhead) 때문에 세그먼트 크기를 약 [50 GB 또는 2억 개 문서](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards) 수준으로 설정할 것을 권장합니다. 또한 [세그먼트당 20억 개 문서](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards#troubleshooting-max-docs-limit)라는 하드 제한도 있습니다. Elasticsearch는 여러 세그먼트에 걸쳐 쿼리를 병렬 처리하지만 각 세그먼트는 **단일 스레드**로 처리되므로, 세그먼트를 과도하게 나누면 비용이 커질 뿐 아니라 오히려 역효과가 납니다. 따라서 세그먼트 분할과 확장은 본질적으로 긴밀하게 결합되어 있으며, 성능을 확장하려면 더 많은 세그먼트(및 노드)가 필요합니다.

Elasticsearch는 빠른 검색을 위해 모든 필드를 [**역색인(inverted index)**](https://www.elastic.co/docs/manage-data/data-store/index-basics)으로 인덱싱하며, 집계, 정렬, 스크립트 필드 접근에는 선택적으로 [**doc values**](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/doc-values)를 사용합니다. 숫자 및 Geo 필드는 지리 공간 데이터 검색과 숫자 및 날짜 범위 검색에 [Block K-D 트리](https://users.cs.duke.edu/~pankaj/publications/papers/bkd-sstd.pdf)를 사용합니다.

중요한 점은 Elasticsearch가 원본 문서 전체를 [`_source`](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field)에 저장하는 반면(`LZ4`, `Deflate` 또는 `ZSTD`로 압축), ClickHouse는 별도의 문서 표현을 저장하지 않는다는 것입니다. 데이터는 쿼리 시점에 컬럼으로부터 재구성되므로 저장 공간이 절약됩니다. Elasticsearch에서도 [Synthetic `_source`](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field#synthetic-source)를 사용하면 같은 방식이 가능하지만, 몇 가지 [제한 사항](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field#synthetic-source-restrictions)이 있습니다. 또한 `_source`를 비활성화하면 몇 가지 [영향](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field#include-exclude)이 따르며, 이는 ClickHouse에는 해당되지 않습니다.

Elasticsearch에서는 [인덱스 매핑](https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping.html)(ClickHouse의 테이블 스키마에 해당)이 필드 타입과, 데이터 저장 및 쿼리에 사용되는 자료 구조를 결정합니다.

반면 ClickHouse는 **컬럼 지향(column-oriented)** 방식으로, 모든 컬럼이 독립적으로 저장되지만 항상 테이블의 프라이머리 키/정렬 키 기준으로 정렬됩니다. 이러한 정렬 덕분에 [희소 기본 인덱스(sparse primary index)](/ko/concepts/core-concepts/primary-indexes)를 사용할 수 있으며, ClickHouse는 이를 통해 쿼리 실행 중 불필요한 데이터를 효율적으로 건너뜁니다. 쿼리가 프라이머리 키 필드로 필터링하면 ClickHouse는 각 컬럼에서 관련 부분만 읽으므로, 모든 컬럼에 전체 인덱스가 없더라도 디스크 입출력(IO)을 크게 줄이고 성능을 높일 수 있습니다.

ClickHouse는 [**스킵 인덱스**](/ko/concepts/features/performance/skip-indexes/skipping-indexes)도 지원합니다. 스킵 인덱스는 선택한 컬럼의 인덱스 데이터를 미리 계산해 두어 필터링 속도를 높입니다. 명시적으로 정의해야 하지만 성능을 크게 향상시킬 수 있습니다. 또한 ClickHouse에서는 컬럼별로 [압축 코덱(compression codecs)](/ko/guides/use-cases/observability/build-your-own/schema-design#using-codecs)과 압축 알고리즘을 지정할 수 있는데, 이는 Elasticsearch에서는 지원하지 않는 기능입니다(Elasticsearch의 [압축](https://www.elastic.co/docs/reference/elasticsearch/index-settings/index-modules)은 `_source` JSON 저장소에만 적용됩니다).

ClickHouse도 세그먼트 분할을 지원하지만, **수직 확장**을 우선하도록 설계되어 있습니다. 단일 세그먼트에 **수조 개의 행(rows)**&#xC744; 저장할 수 있으며, 메모리, CPU, 디스크가 허용하는 한 계속해서 효율적으로 동작합니다. Elasticsearch와 달리 세그먼트당 **엄격한 행 수 제한이 없습니다**. ClickHouse의 세그먼트는 논리적 단위로, 사실상 개별 테이블에 해당하며 데이터셋이 단일 노드의 용량을 초과하지 않는 한 분할할 필요가 없습니다. 용량 초과는 일반적으로 디스크 크기 제약 때문에 발생하며, 세그먼트 분할은 ① 수평 확장(scale-out)이 필요할 때에만 도입되므로 복잡성과 오버헤드가 줄어듭니다. 이 경우 Elasticsearch와 마찬가지로 각 세그먼트는 데이터의 일부를 보유합니다. 단일 세그먼트 내의 데이터는 ③ 여러 자료 구조로 이루어진 ② 변경 불가능한(immutable) 데이터 파트의 모음으로 구성됩니다.

ClickHouse 세그먼트 내의 처리는 **완전히 병렬화**되어 있으며, 노드 간 데이터 이동에 따르는 네트워크 비용을 피하려면 수직 확장을 권장합니다.

<Info>
  **ClickHouse의 삽입 처리**

  ClickHouse의 삽입은 **기본적으로 동기식**으로, 커밋이 완료된 후에야 쓰기에 대한 확인 응답이 반환됩니다. 다만 Elastic과 유사한 버퍼링 및 배치 처리가 필요하면 **비동기 삽입(asynchronous inserts)**&#xC73C;로 구성할 수 있습니다. [비동기 데이터 삽입](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse)을 사용하면 Ⓐ 새로 삽입된 행은 먼저 Ⓑ 인메모리 삽입 버퍼에 저장되며, 이 버퍼는 기본적으로 200밀리초마다 한 번씩 플러시됩니다. 여러 세그먼트를 사용하는 경우에는 [분산 테이블](/ko/reference/engines/table-engines/special/distributed)을 통해 새로 삽입된 행을 대상 세그먼트로 라우팅합니다. 그런 다음 해당 세그먼트의 디스크에 새 파트가 기록됩니다.
</Info>

### 분산 및 복제 {#distribution-and-replication}

Elasticsearch와 ClickHouse는 모두 확장성과 장애 허용을 보장하기 위해 클러스터, 세그먼트, 레플리카를 사용하지만, 구현 방식과 성능 특성 면에서 두 시스템의 모델은 상당히 다릅니다.

Elasticsearch는 복제에 **프라이머리-보조(primary-secondary)** 모델을 사용합니다. 데이터가 프라이머리 세그먼트에 기록되면 하나 이상의 레플리카로 동기식으로 복사됩니다. 이 레플리카 역시 중복성을 보장하기 위해 여러 노드에 분산된 완전한 세그먼트입니다. Elasticsearch는 필요한 모든 레플리카가 작업을 확인한 후에만 쓰기 작업에 확인 응답을 보냅니다. 이 모델은 **순차 일관성**에 가까운 수준을 제공하지만, 동기화가 완료되기 전에는 레플리카에서 **더티 읽기(dirty reads)**&#xAC00; 발생할 수 있습니다. **마스터 노드(master node)**&#xB294; 클러스터를 조정하며 세그먼트 할당, 상태, 리더 선출을 관리합니다.

반면 ClickHouse는 기본적으로 **최종 일관성**을 사용하며, ZooKeeper의 경량 대안인 **Keeper**가 이를 조정합니다. 쓰기 작업은 임의의 레플리카로 직접 보내거나, 레플리카를 자동으로 선택하는 [**분산 테이블**](/ko/reference/engines/table-engines/special/distributed)을 통해 보낼 수 있습니다. 복제는 비동기 방식이므로, 쓰기 작업에 확인 응답을 보낸 후 변경 사항이 다른 레플리카로 전파됩니다. 더 엄격한 보장이 필요한 경우를 위해 ClickHouse는 [**순차 일관성**을 지원](/ko/get-started/migrate/postgres/appendix#sequential-consistency)하며, 이때는 쓰기 작업이 모든 레플리카에 커밋된 후에만 확인 응답을 보냅니다. 다만 이 모드는 성능에 영향을 주기 때문에 거의 사용되지 않습니다. 분산 테이블은 여러 세그먼트에 대한 접근을 하나로 통합하여, `SELECT` 쿼리를 모든 세그먼트로 전달하고 결과를 머지합니다. `INSERT` 작업에서는 데이터를 여러 세그먼트에 고르게 라우팅하여 부하를 분산합니다. ClickHouse의 복제는 매우 유연합니다. 모든 레플리카(세그먼트의 복사본)가 쓰기 작업을 받을 수 있으며, 모든 변경 사항은 다른 레플리카와 비동기로 동기화됩니다. 이 아키텍처 덕분에 장애나 유지 보수 중에도 쿼리를 중단 없이 처리할 수 있으며, 재동기화도 자동으로 처리되므로 데이터 계층에서 프라이머리-보조 구조를 강제할 필요가 없습니다.

<Info>
  **ClickHouse Cloud**

  **ClickHouse Cloud**는 단일 **세그먼트가 객체 스토리지를 기반으로 하는** shared-nothing 컴퓨트 모델을 아키텍처에 도입했습니다. 이 모델은 기존의 레플리카 기반 고가용성을 대체하며, **여러 노드가 하나의 세그먼트를 동시에 읽고 쓸 수 있도록** 합니다. 스토리지 및 컴퓨팅을 분리하므로 레플리카를 별도로 관리하지 않아도 탄력적으로 확장할 수 있습니다.
</Info>

요약하면 다음과 같습니다.

* **Elastic**: 세그먼트는 JVM 메모리에 묶인 물리적 Lucene 구조입니다. 세그먼트를 과도하게 나누면 성능이 저하됩니다. 복제는 동기식이며 마스터 노드가 조정합니다.
* **ClickHouse**: 세그먼트는 논리적 단위로 수직 확장이 가능하며, 로컬 실행이 매우 효율적입니다. 복제는 비동기 방식(순차 방식도 가능)이며, 조정 부담이 가볍습니다.

결국 ClickHouse는 세그먼트 튜닝의 필요성을 최소화하여 대규모 환경에서 단순성과 성능을 추구하면서도, 필요할 때는 강력한 일관성 보장을 제공합니다.

### 중복 제거와 라우팅 {#deduplication-and-routing}

Elasticsearch는 문서의 `_id`를 기준으로 중복을 제거하고, 이에 따라 문서를 세그먼트(shard)로 라우팅합니다. ClickHouse는 기본 행 식별자를 저장하지 않지만 **insert-time 중복 제거**를 지원하므로, 실패한 삽입을 안전하게 재시도할 수 있습니다. 더 세밀하게 제어하려면 `ReplacingMergeTree` 등의 테이블 엔진을 사용하여 특정 컬럼을 기준으로 중복을 제거할 수 있습니다.

Elasticsearch의 인덱스 라우팅은 특정 문서가 항상 특정 세그먼트로 라우팅되도록 보장합니다. ClickHouse에서는 **세그먼트 키(shard key)**&#xB97C; 정의하거나 `Distributed` 테이블을 사용하여 이와 비슷한 데이터 지역성(locality)을 확보할 수 있습니다.

### 집계와 실행 모델 {#aggregations-execution-model}

두 시스템 모두 데이터 집계를 지원하지만, ClickHouse는 통계 함수, 근사 함수, 특수 분석 함수(analytical functions)를 포함하여 훨씬 [더 많은 함수](/ko/reference/functions/aggregate-functions/reference-index)를 제공합니다.

관측성 활용 사례에서 집계(aggregations)가 가장 흔히 쓰이는 용도 중 하나는 특정 로그 메시지나 이벤트의 발생 횟수를 세고, 발생 빈도가 비정상적일 때 알림을 보내는 것입니다.

ClickHouse의 `SELECT count(*) FROM ... GROUP BY ...` SQL 쿼리(SQL query)에 해당하는 Elasticsearch 기능은 [terms aggregation](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html)이며, 이는 Elasticsearch [bucket aggregation](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket.html)의 한 종류입니다.

ClickHouse에서 `count(*)`와 함께 사용하는 `GROUP BY`와 Elasticsearch의 terms aggregation은 기능 면에서는 대체로 동등하지만, 구현 방식, 성능, 결과 품질에서는 큰 차이가 있습니다.

Elasticsearch의 이 집계는 조회 대상 데이터가 여러 세그먼트에 걸쳐 있으면 [「top-N」 쿼리의 결과를 추정합니다](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-terms-aggregation#terms-agg-doc-count-error)(예: 건수 기준 상위 10개 호스트). 이러한 추정은 속도를 높여 주지만 정확도를 떨어뜨릴 수 있습니다. [`doc_count_error_upper_bound`를 확인](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#terms-agg-doc-count-error)하고 `shard_size` 매개변수(Parameter)를 늘리면 이 오류를 줄일 수 있지만, 그 대가로 메모리 사용량(memory usage)이 늘어나고 쿼리 성능(query performance)이 저하됩니다.

또한 Elasticsearch는 모든 버킷 집계에 [`size` 설정](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#search-aggregations-bucket-terms-aggregation-size)을 요구하므로, 제한을 명시적으로 지정하지 않고서는 모든 고유 그룹을 반환할 수 없습니다. high-cardinality 집계는 [`max_buckets` 제한](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-settings.html#search-settings-max-buckets)에 걸릴 위험이 있으며, 그렇지 않으면 [복합 집계(composite aggregation)](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-composite-aggregation)로 페이지네이션을 해야 하는데, 이 방식은 복잡하고 비효율적인 경우가 많습니다.

반면 ClickHouse는 별도 설정 없이도 정확한 집계를 수행합니다. `count(*)`와 같은 함수는 구성을 조정하지 않아도 정확한 결과를 반환하므로, 쿼리 동작이 더 단순하고 예측 가능합니다.

ClickHouse에는 크기 제한이 없습니다. 대규모 데이터 세트(datasets)에서도 제한 없이 group-by 쿼리를 실행할 수 있습니다. 메모리 임계값을 초과하면 ClickHouse는 [디스크로 스필(spill)할 수 있습니다](/ko/reference/statements/select/group-by#group-by-in-external-memory). 프라이머리 키의 접두사로 그룹화하는 집계는 특히 효율적이어서, 대개 최소한의 메모리 활용량으로 실행됩니다.

#### 실행 모델 {#execution-model}

위와 같은 차이는 Elasticsearch와 ClickHouse의 실행 모델에서 비롯됩니다. 두 시스템은 쿼리 실행(Query Execution)과 병렬 처리 방식에서 근본적으로 다른 접근법을 취합니다.

ClickHouse는 최신 하드웨어에서 효율을 극대화하도록 설계되었습니다. 기본적으로 ClickHouse는 N개의 CPU 코어가 있는 머신에서 N개의 병렬 실행 경로로 SQL 쿼리를 동시에 실행합니다.

<div className="ch-image-lg">
  <Frame>
    ![ClickHouse 실행](/images/use-cases/observability/clickhouse-execution.webp)
  </Frame>
</div>

단일 노드에서는 각 병렬 실행 경로가 데이터를 독립적인 범위로 분할하므로 여러 CPU 스레드에서 동시에 처리할 수 있습니다. 필터링, 집계, 정렬도 이 방식으로 처리됩니다. 각 레인의 로컬 결과는 최종적으로 머지되며, 쿼리에 limit 절이 있으면 limit 연산자가 적용됩니다.

쿼리 실행은 다음 방식으로 한층 더 병렬화됩니다.

1. **SIMD 벡터화(vectorization)**: 컬럼형 데이터에 대한 연산은 [CPU SIMD 명령어](https://en.wikipedia.org/wiki/Single_instruction,_multiple_data)(예: [AVX512](https://en.wikipedia.org/wiki/AVX-512))를 사용하여 값을 배치 단위로 처리합니다.
2. **클러스터 수준 병렬 처리**: 분산 구성에서는 각 노드가 쿼리 처리(query processing)를 로컬에서 수행합니다. [부분 집계 상태](https://clickhouse.com/blog/aggregate-functions-combinators-in-clickhouse-for-arrays-maps-and-states#working-with-aggregation-states)는 쿼리를 시작한 노드로 스트리밍되어 머지됩니다. 쿼리의 `GROUP BY` 키가 샤딩 키(Sharding Key)와 일치하면 머지를 [최소화하거나 완전히 생략](/ko/reference/settings/session-settings/distributed#distributed_group_by_no_merge)할 수 있습니다.

<br />

이 모델 덕분에 코어와 노드 수에 따라 효율적으로 확장할 수 있으므로 ClickHouse는 대규모 분석에 적합합니다. 또한 *부분 집계 상태*를 사용하므로 서로 다른 스레드와 노드에서 생성된 중간 결과를 정확도 손실 없이 머지할 수 있습니다.

반면 Elasticsearch는 사용 가능한 CPU 코어 수와 관계없이 대부분의 집계(aggregations)에서 세그먼트당 하나의 스레드만 할당합니다. 각 스레드는 세그먼트 로컬 top-N 결과를 반환하며, 이 결과는 코디네이터 역할을 하는 노드에서 머지됩니다. 이 방식은 시스템 리소스를 충분히 활용하지 못할 수 있고, 특히 빈도가 높은 term이 여러 세그먼트에 분산되어 있으면 전역 집계 결과가 부정확해질 수 있습니다. `shard_size` 매개변수(Parameter)를 늘리면 정확도를 높일 수 있지만, 그만큼 메모리 사용량(memory usage)과 쿼리 지연 시간이 증가합니다.

<div className="ch-image-lg">
  <Frame>
    ![Elasticsearch 실행](/images/use-cases/observability/elasticsearch-execution.webp)
  </Frame>
</div>

요약하면, ClickHouse는 더 세분화된 병렬 처리와 하드웨어 리소스에 대한 더 정밀한 제어를 바탕으로 집계와 쿼리를 실행하는 반면, Elasticsearch는 제약 조건이 더 엄격한 세그먼트 기반 실행 방식에 의존합니다.

각 기술의 집계 동작 방식에 대한 자세한 내용은 블로그 게시물 [&quot;ClickHouse vs. Elasticsearch: The Mechanics of Count Aggregations&quot;](https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#elasticsearch)를 참고하십시오.

### 데이터 관리 {#data-management}

Elasticsearch와 ClickHouse는 시계열 관측성 데이터를 관리하는 방식이 근본적으로 다르며, 특히 데이터 보존, 롤오버(rollover), 계층형 스토리지(Tiered Storage)에서 그 차이가 두드러집니다.

#### 인덱스 수명 주기 관리와 네이티브 TTL 비교 {#lifecycle-vs-ttl}

Elasticsearch에서는 장기적인 데이터 관리를 **Index Lifecycle Management (ILM)**&#xC640; **Data Streams**로 처리합니다. 이 기능을 사용하면 인덱스를 롤오버하는 시점(예: 특정 크기나 기간에 도달한 후), 오래된 인덱스를 저비용 스토리지(예: warm 또는 cold 요금제 등급)로 이동하는 시점, 그리고 최종적으로 삭제하는 시점을 제어하는 정책을 정의할 수 있습니다. 이러한 관리가 필요한 이유는 Elasticsearch가 **재샤딩(re-sharding)을 지원하지 않으며**, 세그먼트가 성능 저하 없이 무한정 커질 수 없기 때문입니다. 세그먼트 크기를 관리하고 삭제를 효율적으로 처리하려면 새 인덱스를 주기적으로 생성하고 오래된 인덱스를 제거해야 하며, 이는 사실상 인덱스 수준에서 데이터를 교체하는 방식입니다.

ClickHouse는 이와 다른 방식을 사용합니다. 데이터는 일반적으로 **단일 테이블**에 저장되며, 컬럼 또는 파티션 수준의 **TTL(수명) 표현식**으로 관리됩니다. 데이터를 **날짜별로 파티셔닝**할 수 있으므로 새 테이블을 생성하거나 인덱스 롤오버를 수행하지 않고도 효율적으로 삭제할 수 있습니다. 데이터가 오래되어 TTL 조건을 충족하면 ClickHouse가 자동으로 제거하므로, 교체를 관리하기 위한 별도의 인프라가 필요하지 않습니다.

#### 스토리지 계층과 hot-warm 아키텍처 {#storage-tiers}

Elasticsearch는 **hot-warm-cold-frozen** 스토리지 아키텍처를 지원하며, 이 아키텍처에서는 성능 특성이 서로 다른 스토리지 계층 간에 데이터를 이동합니다. 이는 일반적으로 ILM을 통해 구성되며 클러스터의 노드 역할과 연계됩니다.

ClickHouse는 `MergeTree`와 같은 네이티브 테이블 엔진을 통해 **계층형 스토리지(Tiered Storage)**&#xB97C; 지원합니다. 이러한 엔진은 사용자 정의 규칙에 따라 오래된 데이터를 서로 다른 **볼륨** 간에(예: SSD → HDD → 객체 스토리지) 자동으로 이동할 수 있습니다. 이를 통해 Elastic의 hot-warm-cold 방식을 그대로 구현할 수 있으면서도, 여러 노드 역할이나 클러스터를 관리해야 하는 복잡성은 없습니다.

<Info>
  **ClickHouse Cloud**

  **ClickHouse Cloud**에서는 이 과정이 한층 더 매끄럽습니다. 모든 데이터는 **객체 스토리지(예: S3)**&#xC5D0; 저장되며, 컴퓨트는 스토리지와 분리되어 있습니다. 데이터는 쿼리되기 전까지 객체 스토리지에 그대로 머물러 있다가, 쿼리 시점에 가져와 로컬(또는 Distributed Cache)에 캐시됩니다. 따라서 Elastic의 frozen 계층과 동일한 비용 구조를 유지하면서도 더 나은 성능 특성을 제공합니다. 이 방식에서는 스토리지 계층 간에 데이터를 이동할 필요가 없으므로 hot-warm 아키텍처 자체가 불필요해집니다.
</Info>

### 롤업 vs 증분 집계 {#rollups-vs-incremental-aggregates}

Elasticsearch에서 **롤업(rollups)** 또는 **집계(aggregates)**&#xB294; [**transforms**](https://www.elastic.co/guide/en/elasticsearch/reference/current/transforms.html)라는 메커니즘으로 구현됩니다. transforms는 **슬라이딩 윈도우(sliding window)** 모델을 사용하여 시계열 데이터를 고정된 인터벌(예: 시간 단위 또는 일 단위)로 요약합니다. transforms는 하나의 인덱스에서 데이터를 집계하고 그 결과를 별도의 **롤업 인덱스(rollup index)**&#xC5D0; 기록하는 반복 백그라운드 작업으로 구성됩니다. 이를 통해 카디널리티가 높은 원시 데이터를 반복적으로 스캔하지 않아도 되므로 장기간에 걸친 쿼리의 비용을 줄일 수 있습니다.

다음 다이어그램은 transforms의 동작 방식을 추상적으로 보여줍니다(집계 값을 미리 계산하려는 동일한 버킷에 속한 모든 문서는 파란색으로 표시했습니다):

<div className="ch-image-lg">
  <Frame>
    ![Elasticsearch transforms](/images/use-cases/observability/es-transforms.webp)
  </Frame>
</div>

연속 transforms는 설정 가능한 검사 인터벌 시간(기본값이 1분인 transform [frequency](https://www.elastic.co/guide/en/elasticsearch/reference/current/put-transform.html))에 따라 transform [체크포인트](https://www.elastic.co/guide/en/elasticsearch/reference/current/transform-checkpoints.html)를 사용합니다. 위 다이어그램에서는 ① 검사 인터벌 시간이 지나면 새 체크포인트가 생성된다고 가정합니다. 이때 Elasticsearch는 transforms의 소스 인덱스에서 변경 사항을 검사하여 이전 체크포인트 이후 새로 생긴 `blue` 문서 3개(11, 12, 13)를 감지합니다. 그러면 소스 인덱스에서 기존의 모든 `blue` 문서를 필터링하고, [복합 집계(composite aggregation)](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-composite-aggregation.html)(결과 [페이지네이션](https://www.elastic.co/guide/en/elasticsearch/reference/current/paginate-search-results.html)을 활용하기 위함)을 사용하여 집계 값을 다시 계산합니다(그리고 대상 인덱스에서는 이전 집계 값을 담고 있던 문서가 새 문서로 대체됩니다). 마찬가지로 ②와 ③에서도 변경 사항을 검사하고 동일한 &#39;blue&#39; 버킷에 속한 기존의 모든 문서로부터 집계 값을 다시 계산하는 방식으로 새 체크포인트가 처리됩니다.

ClickHouse는 근본적으로 다른 접근 방식을 취합니다. ClickHouse는 데이터를 주기적으로 다시 집계하는 대신, **삽입 시점에** 데이터를 변환하고 집계하는 **증분 구체화된 뷰(Incremental Materialized Views)**&#xB97C; 지원합니다. 새 데이터가 원본 테이블에 기록되면 materialized view는 새로 **삽입된 블록**에 대해서만 미리 정의된 SQL 집계 쿼리를 실행하고, 집계된 결과를 target table에 기록합니다.

이 모델은 ClickHouse가 [**부분 집계 상태(partial aggregate states)**](/ko/reference/data-types/aggregatefunction)를 지원하기 때문에 가능합니다. 부분 집계 상태는 저장해 두었다가 나중에 머지할 수 있는 집계 함수의 중간 표현입니다. 이를 통해 쿼리가 빠르고 업데이트 비용이 낮은 부분 집계 결과를 유지할 수 있습니다. 데이터가 도착하는 즉시 집계가 이루어지므로 비용이 많이 드는 반복 작업을 실행하거나 오래된 데이터를 다시 요약할 필요가 없습니다.

증분 구체화된 뷰의 동작 방식을 추상적으로 나타내면 다음과 같습니다(집계 값을 미리 계산하려는 동일한 그룹에 속한 모든 행은 파란색으로 표시했습니다):

<div className="ch-image-lg">
  <Frame>
    ![ClickHouse Materialized Views](/images/use-cases/observability/ch-mvs.webp)
  </Frame>
</div>

위 다이어그램에서 materialized view의 원본 테이블에는 동일한 그룹에 속한 `blue` 행 일부(1~10)를 저장하는 데이터 파트(data part)가 이미 있습니다. 이 그룹에 대해서는 뷰의 target table에도 `blue` 그룹의 [부분 집계 상태(partial aggregation state)](https://www.youtube.com/watch?v=QDAJTKZT8y4)를 저장하는 데이터 파트가 이미 존재합니다. ① ② ③ 원본 테이블에 새 행이 삽입되면 삽입마다 그에 해당하는 원본 테이블 데이터 파트가 생성되며, 이와 동시에 새로 삽입된 행의 각 블록에 대해서만 부분 집계 상태가 계산되어 데이터 파트 형태로 materialized view의 target table에 삽입됩니다. ④ 백그라운드 파트 머지 과정에서 부분 집계 상태가 머지되어 증분 데이터 집계가 이루어집니다.

모든 [집계 함수](/ko/reference/functions/aggregate-functions/reference-index)(90개 이상)는 집계 함수 [combinators](https://www.youtube.com/watch?v=7ApwD0cfAFI)와 조합한 경우를 포함하여 [부분 집계 상태](/ko/reference/data-types/aggregatefunction)를 지원합니다.

증분 집계와 관련하여 Elasticsearch와 ClickHouse를 보다 구체적으로 비교한 내용은 이 [예시](https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation#continuous-data-transformation-example)를 참조하십시오.

ClickHouse 접근 방식의 장점은 다음과 같습니다:

* **항상 최신 상태의 집계**: materialized view는 원본 테이블과 항상 동기화됩니다.
* **백그라운드 작업 불필요**: 집계(aggregations)가 쿼리 시점이 아닌 삽입 시점(insert time)에 수행됩니다.
* **향상된 실시간 성능**: 최신 집계 결과가 즉시 필요한 관측성 워크로드(workloads)와 실시간 분석에 적합합니다.
* **조합 가능성**: materialized view를 계층적으로 구성하거나 다른 뷰(view) 및 테이블과 조인하여 더 복잡한 쿼리 가속 전략을 구현할 수 있습니다.
* **서로 다른 TTL**: materialized view의 원본 테이블과 target table에 각각 다른 TTL 설정을 적용할 수 있습니다.

이 모델은 쿼리할 때마다 수십억 건의 원시 레코드를 스캔(Scan)하지 않고도 분당 오류율, 지연 시간, 상위 N개 항목별 분류와 같은 메트릭을 계산해야 하는 관측성 활용 사례에서 특히 효과적입니다.

### 레이크하우스(lakehouse) 지원 {#lakehouse-support}

ClickHouse와 Elasticsearch는 레이크하우스 통합에 대해 근본적으로 다른 접근 방식을 취합니다. ClickHouse는 [Iceberg](/ko/reference/functions/table-functions/iceberg) 및 [Delta Lake](/ko/reference/functions/table-functions/deltalake)와 같은 레이크하우스 포맷에 대해 쿼리를 실행할 수 있는 완전한 쿼리 실행 엔진이며, [AWS Glue](/ko/guides/use-cases/data-warehousing/glue-catalog) 및 [Unity catalog](/ko/guides/use-cases/data-warehousing/unity-catalog)와 같은 데이터 레이크 카탈로그와도 통합됩니다. 이러한 포맷은 [Parquet](/ko/reference/formats/Parquet/Parquet) 파일을 효율적으로 쿼리할 수 있어야 하며, ClickHouse는 Parquet를 완벽하게 지원합니다. 또한 Iceberg 테이블과 Delta Lake 테이블을 모두 직접 읽을 수 있으므로 최신 데이터 레이크 아키텍처와 원활하게 통합됩니다.

반면 Elasticsearch는 내부 데이터 포맷 및 Lucene 기반 스토리지 엔진에 강하게 결합되어 있습니다. 레이크하우스 포맷이나 Parquet 파일을 직접 쿼리할 수 없으므로 최신 데이터 레이크 아키텍처에 편입되기 어렵습니다. Elasticsearch에서는 데이터를 쿼리하기 전에 먼저 자체 독점 포맷으로 변환하여 적재해야 합니다.

ClickHouse의 레이크하우스 기능은 단순한 데이터 읽기에 그치지 않습니다.

* **데이터 카탈로그 통합**: ClickHouse는 [AWS Glue](/ko/guides/use-cases/data-warehousing/glue-catalog)와 같은 데이터 카탈로그와의 통합을 지원하므로 객체 스토리지에 있는 테이블을 자동으로 검색하고 접근할 수 있습니다.
* **객체 스토리지 지원**: 데이터를 이동하지 않고도 [S3](/ko/reference/engines/table-engines/integrations/s3), [GCS](/ko/reference/functions/table-functions/gcs), [Azure Blob Storage](/ko/reference/engines/table-engines/integrations/azureBlobStorage)에 있는 데이터를 쿼리할 수 있도록 기본 지원합니다.
* **쿼리 페더레이션(Query federation)**: [외부 딕셔너리](/ko/concepts/features/dictionaries/index)와 [테이블 함수](/ko/reference/functions/table-functions/index)를 사용하여 레이크하우스 테이블, 기존 데이터베이스, ClickHouse 테이블 등 여러 소스의 데이터를 연계하여 분석할 수 있습니다.
* **증분 로딩**: [S3Queue](/ko/reference/engines/table-engines/integrations/s3queue), [ClickPipes](/ko/integrations/clickpipes/home) 등의 기능을 사용하여 레이크하우스 테이블의 데이터를 로컬 [MergeTree](/ko/reference/engines/table-engines/mergetree-family/mergetree) 테이블로 지속적으로 적재할 수 있습니다.
* **성능 최적화**: [클러스터 함수](/ko/reference/functions/table-functions/cluster)로 레이크하우스 데이터에 대한 쿼리를 분산 실행하여 성능을 높입니다.

이러한 기능 덕분에 ClickHouse는 레이크하우스 아키텍처를 도입하려는 조직에 잘 맞으며, 데이터 레이크의 유연성과 컬럼형 데이터베이스의 성능을 함께 누릴 수 있게 해 줍니다.
