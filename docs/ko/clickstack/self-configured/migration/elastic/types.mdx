<Note>
  이 페이지는 **자체 관리형 ClickHouse Observability**를 다룹니다. 권장 기본 환경인 완전 관리형 ClickHouse Observability에서는 데이터베이스 스키마(schemas)와 타입 매핑(type mapping)이 자동으로 처리됩니다. 따라서 마이그레이션할 때 이러한 내부 구성 요소를 직접 구성할 필요가 없습니다. 시작하려면 [Elasticsearch 마이그레이션 가이드](/ko/clickstack/observability/migration/elastic)를 참고하십시오.
</Note>

Elasticsearch와 ClickHouse는 모두 다양한 데이터 타입을 지원하지만, 기저 스토리지와 쿼리 모델은 근본적으로 다릅니다. 이 섹션에서는 자주 사용되는 Elasticsearch 필드 타입을 대응하는 ClickHouse 타입(있는 경우)에 매핑하고, 마이그레이션(migration)에 참고할 수 있는 배경 정보를 제공합니다. 동등한 타입이 없으면 주석(Comment)에 대안이나 참고 사항을 함께 기재합니다.

### 참고 {#notes}

* **배열**: Elasticsearch에서는 모든 필드가 배열을 네이티브로 지원합니다. ClickHouse에서는 배열을 명시적으로 정의해야 하지만(예: `Array(String)`), `an_array[1]`과 같이 특정 위치의 요소에 접근하고 쿼리할 수 있다는 장점이 있습니다.
* **멀티 필드(Multi-fields)**: Elasticsearch에서는 [동일한 필드를 여러 방식으로](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/multi-fields#_multi_fields_with_multiple_analyzers) 인덱싱할 수 있습니다(예: `text`와 `keyword` 모두). ClickHouse에서는 이러한 패턴을 별도의 컬럼이나 뷰로 모델링해야 합니다.
* **Map 및 JSON 타입** - ClickHouse에서는 `resourceAttributes`, `logAttributes`와 같은 동적 키-값 구조를 모델링할 때 주로 [`Map`](/ko/reference/data-types/map) 타입을 사용합니다. 이 타입은 런타임에 임의의 키를 추가할 수 있으므로 스키마(schema) 없이 유연하게 데이터를 수집할 수 있으며, 개념적으로 Elasticsearch의 JSON 객체와 비슷합니다. 다만 다음과 같은 중요한 제약 사항을 고려해야 합니다.

  * **균일한 값 타입**: ClickHouse [`Map`](/ko/reference/data-types/map) 컬럼은 일관된 값 타입을 가져야 합니다(예: `Map(String, String)`). 타입을 변환하지 않으면 서로 다른 타입의 값을 함께 저장할 수 없습니다.
  * **성능 비용**: [`Map`](/ko/reference/data-types/map)에서는 키 하나에만 접근하더라도 전체 맵을 메모리에 로드해야 하므로 성능이 저하될 수 있습니다.
  * **서브컬럼 미지원**: JSON과 달리 [`Map`](/ko/reference/data-types/map)의 키는 실제 서브컬럼으로 표현되지 않으므로, ClickHouse가 데이터를 효율적으로 인덱싱, 압축, 쿼리하는 데 한계가 있습니다.

  ClickHouse의 [`JSON`](/ko/reference/data-types/newjson) 타입은 동적 속성을 저장할 때 [`Map`](/ko/reference/data-types/map) 대신 사용할 수 있는 대안으로, 위 제약 사항 중 상당수를 해결합니다.

  * **진정한 컬럼형 저장소**: 각 JSON 경로가 서브컬럼으로 저장되므로 효율적인 압축, 필터링, 벡터화된 쿼리 실행이 가능합니다.
  * **혼합 타입 지원**: 서로 다른 데이터 타입(예: 정수, 문자열, 배열)이 타입 변환이나 타입 통합 없이 동일한 경로에 공존할 수 있습니다.
  * **파일 시스템 확장성**: 동적 키(`max_dynamic_paths`)와 타입(`max_dynamic_types`)에 대한 내부 제한이 있으므로, 높은 카디널리티(high cardinality)를 가진 키 집합에서도 디스크의 컬럼 파일(column files)이 급증하지 않습니다.
  * **고밀도 저장**: null 및 누락된 값은 희소(sparse) 방식으로 저장되므로 불필요한 오버헤드가 발생하지 않습니다.

    [`JSON`](/ko/reference/data-types/newjson) 타입은 관측성 워크로드에 특히 적합합니다. 스키마 없는 수집의 유연성과 네이티브 ClickHouse 타입의 성능 및 확장성을 함께 제공하므로, 동적 속성 필드에서 [`Map`](/ko/reference/data-types/map)을 대체하기에 이상적입니다.

    JSON 타입에 대한 자세한 내용은 [JSON 가이드](/ko/guides/clickhouse/data-formats/json/intro)와 [&quot;How we built a new powerful JSON data type for ClickHouse&quot;](https://clickhouse.com/blog/a-new-powerful-json-data-type-for-clickhouse)를 참고하십시오.
