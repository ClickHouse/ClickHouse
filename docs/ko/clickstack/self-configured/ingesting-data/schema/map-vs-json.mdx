[기본 스키마(schema)](/ko/clickstack/self-configured/ingesting-data/schemas)는 리소스, 범위, 로그, 스팬 속성을 `Map(LowCardinality(String), String)` 컬럼으로 저장합니다. ClickHouse는 강력한 타입 지정을 지원하는 [`JSON` 타입](/ko/reference/formats/JSON/JSON)도 제공하며, 자체 관리형 ClickHouse Observability에서는 `Map` 대신 이 타입을 사용하는 기능을 베타로 지원합니다.

**일반적인 관측성 워크로드(workloads)에는 [기본 `Map` 기반 스키마](/ko/clickstack/self-configured/ingesting-data/schemas)를 그대로 사용할 것을 권장합니다.** JSON 타입은 속성 키 집합이 작고 안정적인 워크로드에서 이를 평가해 보려는 사용자를 위해 제공되지만, 범용으로 권장되는 스키마는 아닙니다.

## Map이 권장 기본값인 이유 {#why-map}

관측성 데이터의 대부분은 리소스 속성, 범위 속성, 스팬 및 로그 속성과 같은 속성이 차지합니다. 이러한 속성 집합은 일반적으로 규모가 크고 high-cardinality이며, 고처리량으로 수집됩니다. 이러한 속성에 어떤 스키마(schema)를 선택하느냐가 수집 비용과 저장소 레이아웃(layout)을 좌우하는 가장 큰 요인입니다.

`Map(LowCardinality(String), String)`은 키와 값(keys and values)을 하나의 구조로 저장합니다. 과거 `Map`의 단점은 단일 키 하나를 읽을 때도 맵 컬럼 전체를 읽어야 한다는 점이었습니다. 하지만 이제는 그렇지 않습니다. ClickHouse는 [버킷 분할 맵 직렬화(bucketed map serialization)](/ko/reference/data-types/map#bucketed-map-serialization)를 지원하며, 이 기능은 맵을 여러 버킷으로 분할하여 쿼리가 필요한 버킷만 읽도록 합니다. 여기에 맵 키와 값에 대한 [텍스트 인덱스](/ko/reference/engines/table-engines/mergetree-family/textindexes)를 함께 사용하면([기본 스키마](/ko/clickstack/self-configured/ingesting-data/schemas)도 이렇게 구성되어 있습니다), 새 키가 추가되어도 수집 성능 저하 없이 읽기 시점에 `Map`을 선택적이고 빠르게 조회할 수 있습니다.

실제로는 다음과 같은 이점이 있습니다.

* **키가 늘어나도 안정적인 수집 비용.** 새 속성 키를 추가해도 on-disk 컬럼 레이아웃이 바뀌거나 새 컬럼 파일(column files)이 생성되지 않습니다. 수집 비용은 키 카디널리티(cardinality)가 아니라 데이터 볼륨에 따라 결정됩니다.
* **메타데이터 폭증 없음.** 디스크의 컬럼 파일 수가 고유 속성 키 수에 따라 늘어나지 않습니다.
* **인덱스를 통한 선택적 조회.** 맵 키와 값에 대한 텍스트 인덱스를 사용하면 모든 행을 스캔하지 않고도 포인트 조회를 수행할 수 있습니다.
* **고처리량에서도 예측 가능한 동작.** Map은 추적 및 로그에서 흔히 나타나는, 갑자기 급증하는 스키마리스 속성 집합을 키별 오버헤드 없이 처리합니다.

## JSON을 기본값으로 사용하지 않는 이유 {#why-not-json}

`JSON` 타입은 다른 방식을 취합니다. 삽입 시점(insert time)에 ClickHouse는 발견한 경로마다 강력한 타입 지정 전용 서브컬럼을 동적으로 생성합니다. 이 방식은 읽기 측면에서 매력적입니다. 요청된 서브컬럼만 읽고, 타입이 보존되며, 쿼리 시점에 형변환할 필요가 없기 때문입니다.

대신 그 대가는 수집 시점에 치르게 됩니다. 수많은 동적 서브컬럼을 생성하고 관리하면 쓰기 오버헤드가 발생하고 메타데이터가 복잡해집니다. 관측성 워크로드(workloads)는 일반적으로 속성 집합이 매우 크거나 변동이 심하고 수집 처리량도 높기 때문에 이 오버헤드가 상당합니다. [`max_dynamic_paths`](/ko/reference/data-types/newjson#reading-json-paths-as-sub-columns) 제한으로 초과 경로를 공유 컬럼에 스필하면 피해를 줄일 수 있지만, 공유 컬럼은 전용 서브컬럼보다 액세스 속도가 느립니다. 결국 애초에 JSON을 선택한 이유였던 읽기 시점의 이점이 줄어듭니다.

버킷 분할 맵 직렬화(bucketed map serialization)로 `Map`의 기존 읽기 시점 오버헤드가 대부분 해소되었으므로, 일반적인 관측성 워크로드에서는 `JSON`의 읽기 시점 이점이 더 이상 수집 시점 비용을 상쇄하지 못합니다.

## 그래도 JSON을 고려할 만한 경우 {#when-to-consider-json}

다음 조건이 *모두* 충족된다면 JSON 타입도 적절한 선택이 될 수 있습니다.

* 속성 키 집합이 **작고 안정적**입니다. 즉, 중복 없는 키가 수천 개씩 생기지 않고 새로운 키도 드물게 추가됩니다.
* 수집 처리량이 속성 카디널리티(cardinality)에 비해 **적당한** 수준입니다.
* 쿼리 시점의 형변환 없이 속성에 **강력한 타입 지정 방식으로 액세스**해야 합니다(숫자는 숫자로, 불리언은 불리언으로 유지됨).
* 자체 관리형 ClickHouse Observability에서 **베타 기능**을 운영할 의향이 있으며, 통합 방식이 변경될 수 있음을 감수할 수 있습니다.

이 조건 중 하나라도 충족되지 않는다면 [기본 `Map` 기반 스키마(schema)](/ko/clickstack/self-configured/ingesting-data/schemas)를 계속 사용하세요.

## 베타 상태 {#beta-status}

<BetaBadge />

<Warning>
  **베타 기능으로, 운영 환경에 사용하기에는 적합하지 않음**

  **자체 관리형 ClickHouse Observability**의 JSON 타입 지원은 **베타 기능**입니다. JSON 타입 자체는 ClickHouse 25.3 이상에서 운영 환경에 사용할 수 있지만, 서비스 내 통합은 아직 활발히 개발 중입니다. 따라서 제한 사항이 있거나, 향후 변경되거나, 버그가 있을 수 있습니다.
</Warning>

ClickStack은 버전 `2.0.4`부터 JSON 타입을 베타로 지원합니다.

## JSON 지원 활성화 {#enabling-json-support}

[기본 `Map` 기반 스키마](/ko/clickstack/self-configured/ingesting-data/schemas) 대신 JSON 타입 스키마를 사용하려면 다음 환경 변수를 설정하세요.

| 변수                                                              | 설정 대상                              | 용도                                    |
| --------------------------------------------------------------- | ---------------------------------- | ------------------------------------- |
| `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'` | ClickHouse Observability Collector | JSON 타입을 사용하여 ClickHouse에 스키마를 생성합니다. |

<a id="managed-clickstack" />

자체 관리형 ClickHouse Observability에서 JSON 지원을 활성화하려면 collector를 구성하기 전에 support@clickhouse.com으로 문의하세요. 또한 ClickHouse Cloud의 관측성 UI에서도 이 기능을 활성화해야 합니다.

collector에 `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'`을 설정하세요. 예를 들면 다음과 같습니다.

```shell
docker run -e OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json' -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
```

## Map 기반 스키마에서 JSON으로 마이그레이션 {#migrating-from-map-to-json}

<Warning>
  **하위 호환성**

  [JSON 타입](/ko/reference/formats/JSON/JSON)은 기존 Map 기반 스키마와 **하위 호환되지 않습니다**. 이 기능을 활성화하면 `JSON` 타입을 사용하는 새 테이블이 생성되므로 데이터를 수동으로 마이그레이션해야 합니다.
</Warning>

[기본 Map 기반 스키마(Map-based schemas)](/ko/clickstack/self-configured/ingesting-data/schemas)에서 마이그레이션하려면 다음 단계를 따르십시오.

<Steps>
  <Step title="OTel collector 중지" id="stop-the-collector" />

  <Step title="기존 테이블 이름 변경 및 소스 업데이트" id="rename-existing-tables-sources">
    기존 테이블의 이름을 변경하고 관측성 UI에서 데이터 소스를 업데이트하십시오.

    예시:

    ```sql
    RENAME TABLE otel_logs TO otel_logs_map;
    RENAME TABLE otel_metrics TO otel_metrics_map;
    ```
  </Step>

  <Step title="collector 배포" id="deploy-the-collector">
    `OTEL_AGENT_FEATURE_GATE_ARG`를 설정하여 collector를 배포하십시오.
  </Step>

  <Step title="JSON 스키마 지원 활성화 여부 확인" id="restart-the-hyperdx-container">
    새 데이터 소스를 생성하기 전에 관측성 UI에서 JSON 스키마 지원이 활성화되었는지 support@clickhouse.com에 문의하여 확인하십시오.
  </Step>

  <Step title="새 데이터 소스 생성" id="create-new-data-sources">
    관측성 UI에서 JSON 테이블을 가리키는 새 데이터 소스를 생성하십시오.
  </Step>
</Steps>

### 기존 데이터 마이그레이션(선택 사항) {#migrating-existing-data}

기존 데이터를 새 JSON 테이블로 옮기려면 다음과 같이 진행하십시오.

```sql
INSERT INTO otel_logs SELECT * FROM otel_logs_map;
INSERT INTO otel_metrics SELECT * FROM otel_metrics_map;
```

<Warning>
  약 100억 개 미만의 행(rows)으로 구성된 데이터 세트(datasets)에만 권장됩니다. 이전에 맵(Map) 타입으로 저장된 데이터는 타입 정밀도가 보존되지 않았습니다(모든 값이 문자열(strings)로 저장됨). 따라서 이 기존 데이터는 보존 기간이 만료될 때까지 새 스키마(schema)에서 문자열로 표시되므로, 프론트엔드에서 일부 형 변환이 필요합니다. 새 데이터는 JSON 타입을 통해 타입이 보존됩니다.
</Warning>
