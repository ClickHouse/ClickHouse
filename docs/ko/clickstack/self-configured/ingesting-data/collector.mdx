## 수집기 역할 {#collector-roles-self-configured}

OpenTelemetry 수집기는 두 가지 주요 역할로 배포할 수 있습니다.

* **에이전트(Agent)** - 에이전트 인스턴스는 서버나 Kubernetes 노드 같은 엣지에서 데이터를 수집하거나, OpenTelemetry SDK로 계측된 애플리케이션에서 이벤트를 직접 수신합니다. 후자의 경우 에이전트 인스턴스는 애플리케이션과 함께 실행되거나 애플리케이션과 동일한 호스트에서 실행됩니다(예: 사이드카 또는 데몬셋(DaemonSet)). 에이전트는 데이터를 ClickHouse로 직접 전송하거나 gateway 인스턴스로 전송할 수 있습니다. 전자를 [에이전트 배포 패턴](https://opentelemetry.io/docs/collector/deployment/agent/)이라고 합니다.

* **게이트웨이(Gateway)** - 게이트웨이 인스턴스는 일반적으로 클러스터, 데이터 센터 또는 리전 단위의 독립 실행형 서비스(예: Kubernetes의 배포(Deployment))로 운영됩니다. 게이트웨이 인스턴스는 단일 OTLP 엔드포인트를 통해 애플리케이션(또는 에이전트 역할을 하는 다른 collector)에서 이벤트를 수신합니다. 일반적으로 여러 gateway 인스턴스를 배포하고, 기본 제공 로드 밸런서로 인스턴스 간에 부하를 분산합니다. 모든 에이전트와 애플리케이션이 이 단일 엔드포인트로 신호를 전송하는 구성을 흔히 [게이트웨이 배포 패턴](https://opentelemetry.io/docs/collector/deployment/gateway/)이라고 합니다.

**중요: ClickStack 기본 배포판에 포함된 collector를 비롯한 collector는 [아래에 설명된 gateway 역할](#collector-roles-self-configured)을 수행하며, 에이전트 또는 SDK로부터 데이터를 수신합니다.**

에이전트 역할로 OTel collector를 배포하는 사용자는 일반적으로 ClickStack 버전이 아닌 [collector의 기본 contrib 배포판](https://github.com/open-telemetry/opentelemetry-collector-contrib)을 사용하지만, [Fluentd](https://www.fluentd.org/)나 [Vector](https://vector.dev/) 같은 다른 OTLP 호환 기술을 사용해도 됩니다.

## collector 배포 {#configuring-the-collector-self-configured}

<br />

자체 관리형 ClickHouse Observability로 데이터를 전송할 때는 가능하면 gateway 역할로 ClickStack 공식 배포판 collector를 사용하는 것을 권장합니다. 직접 준비한 collector를 사용하는 경우 [ClickHouse 익스포터](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter)가 포함되어 있는지 확인하십시오.

collector는 Helm(Kubernetes 환경에서 권장) 또는 Docker로 배포할 수 있습니다. 공식 [ClickStack Helm 차트](https://github.com/ClickHouse/ClickStack-helm-charts)는 업스트림 [OpenTelemetry collector Helm 차트](https://github.com/open-telemetry/opentelemetry-helm-charts)를 서브차트로 포함하며, ClickStack 배포판 image가 미리 구성되어 있습니다. collector를 독립형으로 배포하려면 아래와 같이 업스트림 차트를 ClickStack image와 함께 직접 사용할 수 있습니다.

<Tabs>
  <Tab title="Helm">
    업스트림 OpenTelemetry Helm 리포지토리를 추가합니다:

    ```shell
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update
    ```

    ClickStack image와 자체 관리형 ClickHouse Observability 자격 증명을 구성하는 `values.yaml` 파일을 생성합니다:

    ```yaml
    # values.yaml
    mode: deployment

    image:
      repository: docker.clickhouse.com/clickhouse/clickstack-otel-collector
      tag: "2.19.0"

    ports:
      otlp:
        enabled: true
      otlp-http:
        enabled: true

    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "https://your-instance.clickhouse.cloud:8443"
      - name: CLICKHOUSE_USER
        value: "default"
      - name: CLICKHOUSE_PASSWORD
        value: "<password>"
    ```

    차트를 설치합니다:

    ```shell
    helm install clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    운영 환경에 배포할 때는 값을 직접 입력하는 대신 `CLICKHOUSE_PASSWORD`를 Kubernetes 시크릿에 저장하고 `extraEnvsFrom`으로 참조하는 것을 권장합니다.
  </Tab>

  <Tab title="Docker">
    ClickStack 배포판 OTel 커넥터를 독립형 모드로 배포하려면 다음 docker 명령을 실행하십시오:

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```

    <Info>
      **image 이름 변경**

      ClickStack image는 이제 `clickhouse/clickstack-*` 이름으로 게시됩니다(이전: `docker.hyperdx.io/hyperdx/*`).
    </Info>
  </Tab>
</Tabs>

대상 ClickHouse 인스턴스는 환경 변수 `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`로 구성합니다. `CLICKHOUSE_ENDPOINT`에는 프로토콜과 포트를 포함한 전체 ClickHouse Cloud HTTP 엔드포인트를 지정해야 합니다(예: `https://99rr6dm6v3.us-central1.gcp.clickhouse.cloud:8443`).

자체 관리형 ClickHouse Observability 자격 증명을 확인하는 방법은 [여기](/ko/products/cloud/guides/sql-console/connection-details)를 참조하십시오.

<Info>
  **운영 환경용 사용자**

  운영 환경에서는 [적절한 자격 증명](/ko/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured)을 가진 사용자를 사용하십시오.
</Info>

### 구성 수정 {#modifying-otel-collector-configuration-managed-self-configured}

#### 자체 관리형 ClickHouse Observability 인스턴스 구성 {#configuring-managed-clickstack-self-configured}

OpenTelemetry collector는 환경 변수 `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`를 통해 자체 관리형 ClickHouse Observability 인스턴스를 사용하도록 구성할 수 있습니다. 이 환경 변수를 설정하는 방법은 배포 방식에 따라 다릅니다.

<Tabs>
  <Tab title="Helm">
    `values.yaml`의 `extraEnvs` 아래에 있는 해당 엔트리를 재정의한 다음 릴리스를 업그레이드하십시오.

    ```yaml
    # values.yaml
    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```
  </Tab>

  <Tab title="Docker">
    독립형 OpenTelemetry collector image는 환경 변수로 구성할 수 있습니다.

    ```shell
    export CLICKHOUSE_ENDPOINT=<HTTPS ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    ```

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

<ExtendingConfig />

#### Docker Compose {#docker-compose-otel-managed-self-configured}

Docker Compose에서는 위와 동일한 환경 변수를 사용하여 수집기 설정을 수정하십시오:

```yaml
  otel-collector:
    image: clickhouse/clickstack-otel-collector
    environment:
      CLICKHOUSE_ENDPOINT: 'https://mxl4k3ul6a.us-east-2.aws.clickhouse-staging.com:8443'
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      CLICKHOUSE_USER: 'default'
      CLICKHOUSE_PASSWORD: 'password'
      CUSTOM_OTELCOL_CONFIG_FILE: '/etc/otelcol-contrib/custom.config.yaml'
    ports:
      - '13133:13133' # health_check extension
      - '24225:24225' # fluentd receiver
      - '4317:4317' # OTLP gRPC receiver
      - '4318:4318' # OTLP http receiver
      - '8888:8888' # metrics extension
    volumes:
      - ./custom-config.yaml:/etc/otelcol-contrib/custom.config.yaml:ro
    restart: always
    networks:
      - internal
```

## collector 보안 설정 {#securing-the-collector-self-configured}

기본적으로 ClickStack OpenTelemetry 수집기는 오픈 소스 배포판 이외의 환경에 배포되면 보안이 적용되지 않으며, OTLP 포트에서 인증을 요구하지 않습니다.

수집을 보호하려면 collector를 배포할 때 `OTLP_AUTH_TOKEN` 환경 변수로 인증 토큰을 지정하십시오. 설정 방법은 배포 방식에 따라 다릅니다.

<Tabs>
  <Tab title="Helm">
    `values.yaml`의 `extraEnvs`에 `OTLP_AUTH_TOKEN`을 추가한 다음 릴리스를 업그레이드하십시오.

    ```yaml
    # values.yaml
    extraEnvs:
      - name: OTLP_AUTH_TOKEN
        value: "a_very_secure_string"
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    운영 환경 배포에서는 `OTLP_AUTH_TOKEN`과 `CLICKHOUSE_PASSWORD`를 Kubernetes 시크릿에 저장하고 `extraEnvsFrom`으로 참조하는 것을 권장합니다.
  </Tab>

  <Tab title="Docker">
    ```sh
    export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    export OTLP_AUTH_TOKEN="a_very_secure_string"

    docker run \
      -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
      -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
      -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
      -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
      -p 4317:4317 \
      -p 4318:4318 \
      clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

다음 사항도 함께 권장합니다.

* collector가 HTTPS로 ClickHouse와 통신하도록 구성합니다.
* 권한이 제한된 수집 전용 사용자를 생성합니다. 자세한 내용은 아래를 참조하십시오.
* OTLP 엔드포인트에 TLS를 활성화하여 SDK/에이전트와 collector 간 통신을 암호화합니다. 이는 [사용자 정의 수집기 설정](#extending-collector-config)으로 구성할 수 있습니다.

### 수집 사용자 생성 {#creating-an-ingestion-user-self-configured}

자체 관리형 ClickHouse Observability로 데이터를 수집하려면 OTel collector 전용 데이터베이스와 사용자를 생성하는 것을 권장합니다. 이 사용자에게는 [collector가 사용하는 테이블(tables)](/ko/clickstack/self-configured/ingesting-data/schemas)을 생성하고 해당 테이블에 데이터를 삽입할 수 있는 권한이 있어야 합니다.

```sql
CREATE DATABASE otel;
CREATE USER hyperdx_ingest IDENTIFIED WITH sha256_password BY 'ClickH0u3eRocks123!';
GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO hyperdx_ingest;
```

여기서는 collector가 `otel` 데이터베이스를 사용하도록 구성되어 있다고 가정합니다. 이는 `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE` 환경 변수로 제어할 수 있습니다. [다른 환경 변수와 마찬가지로](#modifying-otel-collector-configuration-managed-self-configured) 이 값을 collector에 전달하십시오.

## 처리 - 필터링, 변환 및 정보 보강 {#processing-filtering-transforming-enriching-self-configured}

사용자는 수집 과정에서 이벤트 메시지를 필터링, 변환 및 보강해야 하는 경우가 거의 항상 있습니다. ClickStack 커넥터의 구성은 수정할 수 없으므로, 추가적인 이벤트 필터링 및 처리가 필요한 사용자에게는 다음 중 한 가지 방법을 권장합니다.

* 필터링과 처리를 수행하는 자체 OTel collector를 배포하고, OTLP를 통해 이벤트를 ClickStack 수집기로 전송하여 ClickHouse에 수집합니다.
* 자체 OTel collector를 배포하고 ClickHouse 익스포터를 사용하여 이벤트를 ClickHouse로 직접 전송합니다.

OTel collector로 처리하는 경우, 변환은 gateway 인스턴스에서 수행하고 에이전트 인스턴스에서의 작업은 최소화할 것을 권장합니다. 이렇게 하면 서버에서 실행되는 엣지 측 에이전트에 필요한 리소스를 최소한으로 유지할 수 있습니다. 일반적으로 사용자는 에이전트에서 필터링(불필요한 네트워크 사용 최소화 목적), 타임스탬프 설정(연산자 사용), 그리고 컨텍스트가 필요한 데이터 보강만 수행합니다. 예를 들어, gateway 인스턴스가 다른 Kubernetes 클러스터에 있다면 k8s 데이터 보강은 에이전트에서 수행해야 합니다.

OpenTelemetry는 다음과 같은 처리 및 필터링 기능을 지원합니다.

* **프로세서(Processors)** - 프로세서는 [수신기가 수집한 데이터를 수정하거나 변환](https://opentelemetry.io/docs/collector/transforming-telemetry/)한 후 익스포터로 전송합니다. 프로세서는 collector 구성의 `processors` 섹션에 구성된 순서대로 적용됩니다. 프로세서는 선택 사항이지만, [일반적으로 최소한의 구성을 권장합니다](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor#recommended-processors). ClickHouse와 함께 OTel collector를 사용하는 경우 프로세서를 다음으로 제한할 것을 권장합니다.

* [memory&#95;limiter](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/memorylimiterprocessor/README.md)는 collector의 메모리 부족 상황을 방지하는 데 사용됩니다. 권장 사항은 [리소스 추정](#estimating-resources-self-configured)을 참조하십시오.

* 컨텍스트를 기반으로 데이터 보강을 수행하는 프로세서. 예를 들어, [Kubernetes Attributes Processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/k8sattributesprocessor)는 스팬, 메트릭, 로그의 리소스 속성을 k8s 메타데이터로 자동 설정합니다(예: 이벤트에 소스 pod id 추가).

* 트레이스에 필요한 경우 [tail 또는 head 샘플링](https://opentelemetry.io/docs/concepts/sampling/).

* [기본 필터링](https://opentelemetry.io/docs/collector/transforming-telemetry/) - 연산자로 처리할 수 없는 경우 불필요한 이벤트를 삭제합니다(아래 참조).

* [일괄 처리](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor/batchprocessor) - ClickHouse를 사용할 때 데이터를 배치 단위로 전송하기 위해 필수적입니다. [&quot;삽입 최적화&quot;](#optimizing-inserts-self-configured)를 참조하십시오.

* **연산자(Operators)** - [연산자](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/pkg/stanza/docs/operators/README.md)는 수신기에서 사용할 수 있는 가장 기본적인 처리 단위입니다. 기본 파싱을 지원하므로 Severity 및 Timestamp와 같은 필드를 설정할 수 있습니다. 또한 이벤트 필터링 및 기본 변환과 함께 JSON 및 정규식 파싱을 지원합니다. 이벤트 필터링은 이 단계에서 수행할 것을 권장합니다.

연산자 또는 [transform 프로세서](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/transformprocessor/README.md)를 사용한 과도한 이벤트 처리는 피할 것을 권장합니다. 특히 JSON 파싱은 상당한 메모리 및 CPU 오버헤드를 유발할 수 있습니다. 일부 예외(특히 k8s 메타데이터 추가와 같은 컨텍스트 인식 데이터 보강)를 제외하면, 모든 처리는 구체화된 뷰(Materialized View)와 컬럼을 사용하여 삽입 시점에 ClickHouse에서 수행할 수 있습니다. 자세한 내용은 [SQL로 구조 추출하기](/ko/guides/use-cases/observability/build-your-own/schema-design#extracting-structure-with-sql)를 참조하십시오.

### 예시 {#example-processing-self-configured}

다음 구성은 이 [비구조화 로그 파일](https://datasets-documentation.s3.eu-west-3.amazonaws.com/http_logs/access-unstructured.log.gz)을 수집하는 예시입니다. 이 구성은 에이전트 역할의 collector가 ClickStack gateway로 데이터를 전송할 때 사용할 수 있습니다.

연산자를 사용하여 로그 행에서 구조를 추출(`regex_parser`)하고 이벤트를 필터링하며, 프로세서를 사용하여 이벤트를 배치로 처리하고 메모리 사용량(memory usage)을 제한한다는 점에 유의하십시오.

```yaml file=code_snippets/ClickStack/config-unstructured-logs-with-processor.yaml
receivers:
  filelog:
    include:
      - /opt/data/logs/access-unstructured.log
    start_at: beginning
    operators:
      - type: regex_parser
        regex: '^(?P<ip>[\d.]+)\s+-\s+-\s+\[(?P<timestamp>[^\]]+)\]\s+"(?P<method>[A-Z]+)\s+(?P<url>[^\s]+)\s+HTTP/[^\s]+"\s+(?P<status>\d+)\s+(?P<size>\d+)\s+"(?P<referrer>[^"]*)"\s+"(?P<user_agent>[^"]*)"'
        timestamp:
          parse_from: attributes.timestamp
          layout: '%d/%b/%Y:%H:%M:%S %z'
          #22/Jan/2019:03:56:14 +0330
processors:
  batch:
    timeout: 1s
    send_batch_size: 10000
  memory_limiter:
    check_interval: 1s
    limit_mib: 2048
    spike_limit_mib: 256
exporters:
  # HTTP setup
  otlphttp/hdx:
    endpoint: 'http://localhost:4318'
    headers:
      authorization: <YOUR_INGESTION_API_KEY>
    compression: gzip

  # gRPC setup (alternative)
  otlp/hdx:
    endpoint: 'localhost:4317'
    headers:
      authorization: <YOUR_API_INGESTION_KEY>
    compression: gzip
service:
  telemetry:
    metrics:
      address: 0.0.0.0:9888 # Modified as 2 collectors running on same host
  pipelines:
    logs:
      receivers: [filelog]
      processors: [batch]
      exporters: [otlphttp/hdx]

```

`OTLP_AUTH_TOKEN`을 구성한 경우, 위 예시의 인증 헤더 값으로 해당 토큰을 사용하십시오. 자세한 내용은 [collector 보안 설정](#securing-the-collector-self-configured)을 참조하십시오.

고급 구성에 대한 자세한 내용은 [OpenTelemetry collector 문서](https://opentelemetry.io/docs/collector/)를 참조하십시오.

## 삽입 최적화 {#optimizing-inserts-self-configured}

강력한 일관성(Consistency)을 보장하면서 높은 삽입 성능(insert performance)을 얻으려면, ClickStack 수집기를 통해 관측성 데이터를 ClickHouse에 삽입(inserting)할 때 몇 가지 간단한 규칙을 지켜야 합니다. OTel collector를 올바르게 구성하면 다음 규칙은 어렵지 않게 지킬 수 있습니다. 또한 ClickHouse를 처음 사용할 때 사용자가 흔히 겪는 [문제](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse)도 예방할 수 있습니다.

### 일괄 처리 {#batching-self-configured}

기본적으로 ClickHouse는 삽입을 받을 때마다 해당 삽입의 데이터와 함께 저장해야 하는 기타 메타데이터를 담은 스토리지 데이터 파트(part)를 즉시 생성합니다. 따라서 적은 데이터를 담은 삽입을 여러 번 보내는 것보다 많은 데이터를 담은 삽입을 적은 횟수로 보내면 필요한 쓰기 작업 수가 줄어듭니다. 한 번에 최소 1,000개 행 이상의 충분히 큰 배치로 데이터를 삽입하는 것을 권장합니다. 자세한 내용은 [여기](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance)를 참조하십시오.

기본적으로 ClickHouse의 삽입은 동기식이며, 동일한 삽입에 대해서는 멱등성을 가집니다. MergeTree 엔진 계열의 테이블에서 ClickHouse는 기본적으로 [삽입을 자동으로 중복 제거](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#5-deduplication-at-insert-time)합니다. 따라서 다음과 같은 상황에서도 삽입을 안전하게 처리할 수 있습니다.

* (1) 데이터를 수신하는 노드에 문제가 있으면 삽입 쿼리(insert query)가 타임아웃되거나(또는 더 구체적인 오류가 발생하며) 확인 응답을 받지 못합니다.
* (2) 노드가 데이터를 기록했지만 네트워크 중단으로 인해 확인 응답이 쿼리 송신자에게 반환되지 못하면, 송신자는 타임아웃 또는 네트워크 오류를 받게 됩니다.

collector 입장에서는 (1)과 (2)를 구분하기 어려울 수 있습니다. 그러나 두 경우 모두 확인 응답을 받지 못한 삽입을 즉시 재시도하면 됩니다. 재시도한 삽입 쿼리가 동일한 데이터를 동일한 순서로 포함하고 있다면, 원래의(확인 응답을 받지 못한) 삽입이 이미 성공한 경우 ClickHouse가 재시도된 삽입을 자동으로 무시합니다.

이러한 이유로 ClickStack 배포판의 OTel collector는 [batch processor](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/batchprocessor/README.md)를 사용합니다. 이를 통해 삽입이 위 요구 사항을 충족하는 일정한 크기의 행 배치로 전송됩니다. collector에 높은 처리량(초당 이벤트 수)이 예상되고 삽입마다 최소 10,000개의 이벤트를 전송할 수 있다면, 일반적으로 파이프라인에서 필요한 일괄 처리는 이것만으로 충분합니다. 메모리가 허용한다면 최대 100,000까지의 값을 사용할 수 있습니다. 이 경우 collector는 batch processor의 `timeout`에 도달하기 전에 배치를 플러시하므로, 파이프라인의 엔드투엔드 지연 시간을 낮게 유지하면서 배치 크기도 일정하게 유지할 수 있습니다.

### 비동기 삽입 사용 {#use-asynchronous-inserts-self-configured}

일반적으로 collector의 처리량이 낮으면 작은 배치를 보낼 수밖에 없지만, 사용자는 여전히 데이터가 최소한의 엔드투엔드 지연 시간 내에 ClickHouse에 도달하기를 기대합니다. 이 경우 batch processor의 `timeout`이 만료될 때 작은 배치가 전송됩니다. 이로 인해 문제가 발생할 수 있으며, 바로 이럴 때 비동기 삽입(asynchronous inserts)이 필요합니다. Gateway 역할을 하는 ClickStack 수집기로 데이터를 전송한다면 이 문제는 거의 발생하지 않습니다. 수집기가 집계자 역할을 하여 이 문제를 완화하기 때문입니다. 자세한 내용은 [수집기 역할](#collector-roles-self-configured)을 참조하십시오.

대용량 배치를 보장할 수 없다면 [비동기 삽입(Asynchronous Inserts)](/ko/concepts/best-practices/selecting-an-insert-strategy#asynchronous-inserts)을 사용하여 배치 처리를 ClickHouse에 위임할 수 있습니다. 비동기 삽입을 사용하면 데이터가 먼저 버퍼에 삽입된 후, 나중에 비동기적으로 데이터베이스 스토리지에 기록됩니다.

<div className="ch-image-md">
  <Frame>
    ![비동기 삽입](/images/use-cases/observability/observability-6.webp)
  </Frame>
</div>

[비동기 삽입이 활성화된](/ko/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts) 상태에서 ClickHouse가 ① 삽입 쿼리(insert query)를 수신하면, 쿼리의 데이터는 ② 즉시 인메모리 버퍼에 먼저 기록됩니다. ③ 다음 버퍼 플러시가 발생하면 버퍼의 데이터가 [정렬](/ko/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns)되어 하나의 파트로 데이터베이스 스토리지에 기록됩니다. 데이터베이스 스토리지로 플러시되기 전에는 쿼리로 데이터를 검색할 수 없다는 점에 유의하십시오. 버퍼 플러시 방식은 [구성할 수 있습니다](/ko/concepts/features/operations/insert/asyncinserts).

collector에서 비동기 삽입을 활성화하려면 연결 문자열(Connection String)에 `async_insert=1`을 추가하십시오. 전달을 보장하려면 `wait_for_async_insert=1`(기본값)을 사용할 것을 권장합니다. 자세한 내용은 [여기](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse)를 참조하십시오.

비동기 삽입의 데이터는 ClickHouse 버퍼가 플러시될 때 삽입됩니다. 플러시는 [`async_insert_max_data_size`](/ko/reference/settings/session-settings/async-insert#async_insert_max_data_size)를 초과하거나, 첫 번째 INSERT 쿼리 이후 [`async_insert_busy_timeout_ms`](/ko/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms) 밀리초가 지나면 발생합니다. `async_insert_stale_timeout_ms`가 0이 아닌 값으로 설정되어 있으면, 마지막 쿼리 이후 `async_insert_stale_timeout_ms milliseconds`가 지난 시점에 데이터가 삽입됩니다. 이러한 설정을 조정하여 파이프라인의 엔드투엔드 지연 시간을 제어할 수 있습니다. 버퍼 플러시 조정에 사용할 수 있는 기타 설정은 [여기](/ko/reference/settings/session-settings/async-insert#async_insert)에서 확인할 수 있습니다. 일반적으로는 기본값으로 충분합니다.

<Info>
  **적응형 비동기 삽입 고려**

  사용 중인 에이전트 수가 적고 처리량은 낮지만 엔드투엔드 지연 시간 요구 사항이 엄격하다면 [적응형 비동기 삽입](https://clickhouse.com/blog/clickhouse-release-24-02#adaptive-asynchronous-inserts)이 유용할 수 있습니다. 다만 ClickHouse에서 흔히 볼 수 있는 높은 처리량의 관측성 사용 사례에는 일반적으로 적합하지 않습니다.
</Info>

마지막으로, ClickHouse에 동기 삽입할 때 적용되던 기존의 중복 제거 동작은 비동기 삽입을 사용할 때 기본적으로 활성화되지 않습니다. 필요하다면 [`async_insert_deduplicate`](/ko/reference/settings/session-settings/async-insert#async_insert_deduplicate) 설정을 참조하십시오.

이 기능의 구성 방법에 대한 자세한 내용은 [문서 페이지](/ko/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts) 또는 심층 분석 [블로그 게시물](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse)에서 확인할 수 있습니다.

## 스케일링 {#scaling-self-configured}

ClickStack OTel 수집기는 gateway 인스턴스 역할을 합니다. 자세한 내용은 [수집기 역할](#collector-roles-self-configured)을 참조하십시오. gateway는 일반적으로 데이터 센터별 또는 리전별로 독립 실행형 서비스를 제공하며, 단일 OTLP 엔드포인트를 통해 애플리케이션(또는 에이전트 역할을 하는 다른 collector)으로부터 이벤트를 수신합니다. 보통 여러 collector 인스턴스를 배포하고, 기본 제공 로드 밸런서로 인스턴스 간에 부하를 분산합니다.

<div className="ch-image-lg">
  <Frame>
    ![gateway를 통한 확장](/images/use-cases/observability/clickstack-with-gateways.webp)
  </Frame>
</div>

이 아키텍처의 목적은 계산 집약적인 처리를 에이전트에서 분리하여 에이전트의 리소스 사용량을 최소화하는 것입니다. ClickStack gateway는 원래 에이전트가 수행해야 할 변환 작업을 대신 처리할 수 있습니다. 또한 gateway는 여러 에이전트의 이벤트를 집계하여 ClickHouse로 대규모 배치를 전송하므로 효율적인 삽입이 가능합니다. 이러한 gateway collector는 에이전트와 SDK 소스가 늘어나고 이벤트 처리량이 증가하더라도 손쉽게 확장할 수 있습니다.

### Kafka 추가하기 {#adding-kafka-self-configured}

위 아키텍처에서 Kafka를 메시지 큐로 사용하지 않는다는 점을 눈치챈 분도 있을 것입니다.

Kafka 큐를 메시지 버퍼로 사용하는 것은 로깅 아키텍처에서 흔히 볼 수 있는 디자인 패턴이며, ELK 스택을 통해 널리 알려졌습니다. 이 방식에는 몇 가지 이점이 있습니다. 무엇보다 더 강력한 메시지 전달 보장을 제공하고 백프레셔(backpressure)에 대응하는 데 도움이 됩니다. 메시지는 수집 에이전트에서 Kafka로 전송되어 디스크에 기록됩니다. 이론적으로 클러스터로 구성된 Kafka 인스턴스는 고처리량 메시지 버퍼 역할을 할 수 있습니다. 메시지를 파싱하고 처리하는 것보다 데이터를 디스크에 순차적으로 기록하는 편이 연산 오버헤드가 적기 때문입니다. 예를 들어 Elastic에서는 토큰화와 인덱싱(indexing)에 상당한 오버헤드가 발생합니다. 또한 데이터를 에이전트 밖으로 옮겨두면 소스에서 발생하는 로그 교체로 인해 메시지가 유실될 위험도 줄어듭니다. 마지막으로 메시지 재전송 및 cross-region 복제 기능을 제공하므로 일부 활용 사례에서는 매력적인 선택지가 될 수 있습니다.

그러나 ClickHouse는 데이터를 매우 빠르게 삽입할 수 있으며, 일반적인 사양의 하드웨어에서도 초당 수백만 행을 처리합니다. ClickHouse에서 백프레셔가 발생하는 경우는 드뭅니다. Kafka 큐를 도입하면 아키텍처가 복잡해지고 비용이 늘어나는 경우가 많습니다. 로그에는 은행 트랜잭션(Transactions)이나 기타 미션 크리티컬 데이터만큼의 전달 보장이 필요하지 않다는 원칙을 받아들일 수 있다면, Kafka 도입에 따른 복잡성을 피할 것을 권장합니다.

다만 높은 수준의 전달 보장이나 데이터 재전송 기능(경우에 따라 여러 소스로의 재전송)이 필요하다면, Kafka를 아키텍처에 추가하는 것이 유용할 수 있습니다.

  <Frame>
    ![Kafka 추가](/images/use-cases/observability/observability-8.webp)
  </Frame>
</div>

이 경우 OTel 에이전트가 [Kafka 익스포터](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/kafkaexporter/README.md)를 통해 Kafka로 데이터를 전송하도록 구성할 수 있습니다. 그러면 게이트웨이 인스턴스가 [Kafka 수신기](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/kafkareceiver/README.md)를 사용하여 메시지를 소비합니다. 자세한 내용은 Confluent 및 OTel 문서를 참고하십시오.

<Info>
  **OTel collector 구성**

  ClickStack OpenTelemetry 수집기 배포판은 [사용자 정의 수집기 설정](#extending-collector-config)을 통해 Kafka를 사용하도록 구성할 수 있습니다.
</Info>

## 리소스 추정 {#estimating-resources-self-configured}

OTel collector에 필요한 리소스는 이벤트 처리량, 메시지 크기, 수행하는 처리 작업의 양에 따라 달라집니다. OpenTelemetry 프로젝트는 리소스 요구 사항을 추정하는 데 활용할 수 있는 [벤치마크](https://opentelemetry.io/docs/collector/benchmarks/)를 제공합니다.

[ClickHouse의 경험에 따르면](https://clickhouse.com/blog/building-a-logging-platform-with-clickhouse-and-saving-millions-over-datadog#architectural-overview), 코어 3개와 12GB RAM을 갖춘 ClickStack gateway 인스턴스는 초당 약 60k개의 이벤트를 처리할 수 있습니다. 이는 필드 이름 변경만 수행하고 정규 표현식은 사용하지 않는 최소한의 처리 파이프라인을 전제로 한 수치입니다.

이벤트를 gateway로 전송하고 이벤트에 타임스탬프만 설정하는 에이전트 인스턴스는 예상되는 초당 로그 수를 기준으로 리소스 규모를 산정하는 것을 권장합니다. 다음 근사치를 시작점으로 활용하세요.

| 로깅 속도 | collector 에이전트 리소스 |
| ----- | ------------------ |
| 1k/초  | 0.2CPU, 0.2GiB     |
| 5k/초  | 0.5 CPU, 0.5GiB    |
| 10k/초 | 1 CPU, 1GiB        |

## 스키마(schema) 선택: Map vs JSON {#schema-choice-self-configured}

ClickStack 수집기는 기본적으로 속성을 `Map(LowCardinality(String), String)` 컬럼에 저장하는 테이블을 생성합니다. 이는 관측성 워크로드에 권장되는 스키마입니다. `JSON` 타입 스키마는 베타로 제공되며, 속성 키 집합이 작고 안정적인 워크로드에서 평가용으로 사용할 수 있습니다.

두 스키마의 전체 비교, 각 스키마가 적합한 경우, JSON 타입 스키마를 활성화하는 데 필요한 환경 변수, 마이그레이션(migration) 단계별 안내는 [Map vs JSON 타입](/ko/clickstack/self-configured/ingesting-data/schema/map-vs-json)을 참조하십시오.
