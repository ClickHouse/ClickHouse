<Note>
  이 페이지는 **자체 관리형 ClickHouse Observability**를 다룹니다. 권장되는 완전 관리형 환경은 [여기](/ko/clickstack/observability/overview)의 문서를 참조하십시오.
</Note>

ClickStack을 어느 정도 운영해 보았다면, 기본 스키마(schema)만으로도 별도의 변경 없이 대부분의 관측성 워크로드(workloads)를 처리할 수 있다는 점을 확인했을 것입니다. 이 페이지는 기본 스키마만으로는 더 이상 충분하지 않은 경우, 즉 쿼리 지연 시간이 늘어나기 시작하거나 액세스 패턴이 기본 설정과 달라진 경우를 위한 내용입니다.

실제로 효과를 보는 개선 사항은 대부분 다음 네 가지 최적화로 해결할 수 있으며, 대략 작업량이 적은 순서대로 나열되어 있습니다. 처음 두 가지는 증분 방식으로 적용할 수 있는 국소적인 `ALTER TABLE` 변경입니다. 세 번째는 대시보드에서 같은 집계가 반복해서 실행될 때 효과적입니다. 네 번째는 migration이 필요하므로 작업 부담이 가장 큽니다.

아래 요약은 의도적으로 간략하게 작성했습니다. 각 변경의 근거, 벤치마크, 기존 데이터에 적용하는 방법은 [성능 튜닝](/ko/clickstack/self-configured/managing/performance-tuning)을 참조하십시오.

<Steps>
  <Step title="자주 쿼리하는 속성 구체화하기" id="materialize-attributes">
    `LogAttributes['service.version']`로 필터링하면 ClickHouse는 검사하는 모든 행마다 `LogAttributes` 맵 전체를 로드하고 디코딩해야 합니다. 해당 속성을 `MATERIALIZED` 컬럼으로 승격하면 같은 필터가 단순한 컬럼 읽기로 바뀌어 일반적으로 10배 이상 빨라집니다. 컬럼이 생성되면 ClickStack이 필터를 자동으로 재작성하므로, 저장된 검색과 대시보드는 수정 없이 그대로 동작합니다.

    실제로 자주 쿼리하는 속성만 선택하십시오. 구체화된(materialized) 컬럼마다 스토리지와 삽입 시점(insert time) 비용이 추가되므로, &quot;모두 승격&quot;하기보다는 &quot;사용하는 것만 승격&quot;하는 방식으로 접근해야 합니다.

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    기존 행의 새 컬럼 값은 `ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion`을 추가로 실행하기 전까지 비어 있습니다.

    자세히 알아보기: [자주 쿼리하는 속성 구체화하기](/ko/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes).
  </Step>

  <Step title="스킵 인덱스 추가하기" id="add-skip-indexes">
    스킵 인덱스를 사용하면 ClickHouse가 필터 조건과 일치할 수 없는 데이터 그래뉼을 건너뛰므로, 전체 스캔(Scan)이 필요한 부분만 읽는 소규모 읽기로 바뀝니다. 알아 두면 좋은 유형은 다음 세 가지입니다.

    * 문자열 컬럼과 `mapKeys`/`*AttributeItems` 배열에 대한 **텍스트 인덱스(Text indexes)**(`text(tokenizer = ...)`). 기본 로그 스키마에 이미 포함되어 있습니다.
    * 범위 조건으로 필터링하는 숫자 컬럼에 대한 **Min-max 인덱스**. 트레이스의 `Duration`이 대표적인 예입니다.
    * 텍스트 인덱스를 아직 지원하지 않는 ClickHouse 버전에서 카디널리티(cardinality)가 높은 값의 동등 조회에 사용하는 **Bloom 필터**.

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    스킵 인덱스는 실제로 그래뉼을 걸러낼 때만 평가 비용 이상의 효과를 냅니다. 효과가 있다고 단정하기 전에 대표 쿼리에 `EXPLAIN indexes = 1`을 실행하여 확인하십시오.

    자세히 알아보기: [스킵 인덱스 추가하기](/ko/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes).
  </Step>

  <Step title="반복되는 집계 미리 계산하기" id="materialized-views">
    대시보드에서 같은 집계가 계속 반복 실행된다면(오류율 기준 상위 서비스, 엔드포인트별 p99 지연 시간, 분당 요청 수 등), materialized view를 사용해 삽입 시점에 결과를 계산하고 작은 롤업 테이블에 기록할 수 있습니다. 이후 대시보드는 원시 로그나 trace 대신 롤업 테이블을 조회하므로 비용이 훨씬 적게 듭니다.

    이 방식은 대시보드 사용 빈도가 높고 기반 테이블이 클 때 특히 효과적입니다. 대신 삽입 시점의 CPU 사용량이 다소 늘어나고 관리해야 할 테이블이 하나 더 생깁니다.

    자세히 알아보기: [materialized view 활용하기](/ko/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views).
  </Step>

  <Step title="접근 패턴에 맞는 프라이머리 키 선택하기" id="choose-primary-key">
    프라이머리 키는 디스크에서 행이 정렬되는 방식을 결정합니다. 키의 선행 컬럼으로 필터링하면 ClickHouse가 관련 영역으로 곧바로 이동할 수 있지만, 이러한 컬럼으로 시작하지 않는 필터는 파티션 전체를 스캔합니다.

    기본 로그 키 `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)`는 &quot;서비스 X에서 최근 N분 동안 무슨 일이 있었는가&quot;와 같은 쿼리에 최적화되어 있습니다. 대부분의 쿼리가 다른 컬럼(테넌트 ID, 고객 ID, 리전 등)을 기준으로 한다면, 해당 컬럼으로 시작하도록 프라이머리 키를 변경하는 것이 가장 효과가 큰 개선 방법입니다.

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- otel_logs와 동일한 컬럼
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse에서는 기존 테이블의 프라이머리 키를 직접 수정할 수 없으므로, 단순한 `ALTER`가 아니라 migration이 필요합니다. 성능 튜닝 가이드에서는 새 테이블 생성, 수집 대상 전환, 그리고 기존 대시보드가 이전 데이터와 새 데이터 모두에서 계속 동작하도록 `Merge` 테이블을 사용하는 방법을 단계별로 설명합니다.

    자세히 알아보기: [프라이머리 키 수정하기](/ko/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key).
  </Step>
</Steps>
