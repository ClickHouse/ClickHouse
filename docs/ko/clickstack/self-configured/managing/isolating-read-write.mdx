관측성 워크로드는 동일한 데이터에 대해 서로 매우 다른 두 가지 요구 사항을 가집니다. 수집은 지속적이며 쓰기(write) 작업 위주이고, 백그라운드 머지는 삽입이 완료된 후에도 한참 동안 CPU와 메모리를 소비합니다. 반면 쿼리 부하는 일정하지 않습니다. 대시보드와 검색 사용량은 장애 발생 시 정점에 이르는데, 바로 이때가 느린 응답을 가장 용납하기 어려운 시점입니다.

ClickHouse Cloud [웨어하우스(warehouses)](/ko/products/cloud/features/infrastructure/warehouses)를 사용하면 동일한 데이터를 기반으로 두 워크로드를 별도의 컴퓨트에서 처리할 수 있으므로, 두 워크로드가 CPU와 메모리를 두고 경쟁하지 않습니다.

<ScalePlanFeatureBadge feature="Compute-compute separation" />

웨어하우스는 ClickHouse Cloud 기능이므로, 여기에서 설명하는 구성은 자체 관리형 ClickHouse Observability에 적용됩니다. 분할된 각 서비스는 하나의 데이터 사본을 공유하면서도 용량 산정, 확장, 유휴 상태 전환을 각각 독립적으로 수행합니다.

<Note>
  **격리가 필요한 경우**

  격리는 지속적인 수집이 이루어지는 대규모 배포를 위한 것입니다. 저장된 데이터가 월 약 100 TB 미만이라면 일반적으로 단일 읽기/쓰기 서비스로 두 워크로드를 모두 감당할 수 있으므로 두 번째 서비스는 대개 필요하지 않습니다. [용량 산정 모델](/ko/clickstack/self-configured/managing/estimating-resources)을 사용하여 월별 압축된 데이터 볼륨을 추정하십시오.
</Note>

## 읽기와 쓰기 작업을 분리해야 하는 이유 {#why-isolate}

* **쓰기 작업이 더 이상 읽기 성능을 저하시키지 않습니다.** OpenTelemetry 데이터의 지속적인 수집, 즉 삽입 작업 자체와 그에 뒤따르는 백그라운드 머지는 대시보드 및 검색 쿼리와 CPU 및 메모리를 두고 경합합니다. 수집이 진행되는 동안에는 읽기 지연 시간이 눈에 띄게 늘어날 수 있으며, 수집이 멈추면 다시 회복됩니다.
* **읽기 작업이 더 이상 쓰기 작업을 방해하지 않습니다.** 경합은 양방향으로 발생합니다. 무거운 임시(ad-hoc) 쿼리나 비용이 큰 대시보드 렌더링은 서비스의 메모리를 고갈시켜, 삽입 작업을 단순히 지연시키는 데 그치지 않고 아예 실패하게 만들 수 있습니다.
* **읽기 전용 컴퓨팅은 전적으로 쿼리에만 사용됩니다.** 읽기 전용 서비스는 시스템 테이블을 제외하고는 백그라운드 머지를 수행하지 않습니다. 또한 머지 때문에 계속 활성 상태로 유지될 수 있는 읽기·쓰기 서비스와 달리, 지체 없이 유휴 상태로 전환됩니다.
* **읽기와 쓰기의 용량을 각각 독립적으로 산정합니다.** [용량 산정 모델](/ko/clickstack/self-configured/managing/estimating-resources)은 수집 컴퓨팅 자원과 쿼리 컴퓨팅 자원을 별도로 추정하며, 웨어하우스(warehouse)를 사용하면 각각을 독립된 서비스로 프로비저닝할 수 있습니다. 이 모델의 기준선인 1 QPS를 넘어서면 쿼리 컴퓨팅 자원이 대부분을 차지합니다. 5 QPS 기준의 [계산 예시](/ko/clickstack/self-configured/managing/estimating-resources#worked-example)에서는 수집에 58 vCPU, 쿼리에 290 vCPU가 산정됩니다. 따라서 작은 쓰기 서비스로도 훨씬 큰 읽기 서비스에 데이터를 공급할 수 있습니다.
* **유휴 상태 전환과 자동 스케일링은 서비스별로 구성됩니다.** 각 서비스마다 레플리카 수, 자동 스케일링, 자동 유휴 상태 전환 설정을 별도로 지정할 수 있으므로, 쓰기 서비스는 지속적인 수집을 위해 항상 켜 두고 읽기 서비스는 업무 시간 외에 유휴 상태로 전환할 수 있습니다.
* **저장소가 중복되지 않습니다.** 웨어하우스 내 서비스는 동일한 객체 저장소 폴더와 동일한 테이블을 공유하며, [저장소 요금은 한 번만 청구됩니다](/ko/products/cloud/features/infrastructure/warehouses#pricing).
* **엔드포인트별로 액세스를 제한할 수 있습니다.** IP 액세스 목록은 서비스별로 적용되므로, 쓰기 엔드포인트는 collector에서만, 읽기 엔드포인트는 관측성 UI에서만 접근할 수 있도록 설정할 수 있습니다. 자세한 내용은 [네트워크 접근 제어](/ko/products/cloud/features/infrastructure/warehouses#network-access-control) 가이드를 참조하십시오.

## 아키텍처 {#architecture}

권장 토폴로지는 수집용 읽기-쓰기 서비스 1개와 관측성 UI용 읽기 전용 서비스 1개로 구성된 웨어하우스(warehouse)입니다.

| 서비스   | 유형    | 역할                                                | 클라이언트                                                           |
| ----- | ----- | ------------------------------------------------- | --------------------------------------------------------------- |
| 프라이머리 | 읽기-쓰기 | 수집, 백그라운드 머지, DDL(테이블 생성, TTL, materialized view) | OpenTelemetry collector, ClickPipes, Vector, 관리용 SQL 콘솔 / 클라이언트 |
| 보조    | 읽기 전용 | 검색, 대시보드, 노트북, 알림 평가                              | 관측성 UI                                                          |

토폴로지를 계획할 때는 다음 사항에 유의하십시오.

* 웨어하우스의 첫 번째 서비스는 항상 읽기-쓰기 서비스이며, 서비스 유형은 **생성 시 고정**됩니다. 읽기 전용과 읽기-쓰기 간에 전환하려면 웨어하우스에 새 서비스를 생성하십시오.
* 웨어하우스 내 모든 서비스는 동일한 클라우드 제공업체, 리전, ClickHouse 버전, Keeper를 공유하며 기본 서비스의 업그레이드 일정도 함께 따릅니다.
* 수집에는 읽기-쓰기 서비스를 **하나만** 사용하십시오. 머지는 저장소를 공유하는 모든 읽기-쓰기 서비스에 할당되므로, 한 서비스에서 발생한 삽입의 머지가 다른 서비스에서 실행될 수 있습니다. 이때 해당 서비스가 무거운 쿼리까지 처리하고 있으면, 그 쿼리가 머지와 CPU 및 메모리를 두고 경쟁하게 됩니다. 결과적으로 첫 번째 서비스의 삽입에 대한 머지가 느려지고, 그에 따라 삽입 성능도 저하됩니다. 쿼리 워크로드는 읽기 전용 서비스에서 처리하고, 두 번째 읽기-쓰기 서비스는 [머지를 수집과 분리](#separating-merges)해야 하는 경우에만 추가하십시오.

## 격리된 배포 구성 {#setup}

<Steps>
  <Step title="읽기/쓰기 서비스 준비" id="prepare-read-write-service">
    기존 서비스 또는 새 웨어하우스(warehouse)의 기본 서비스를 수집용으로 사용하고, [용량 산정 모델](/ko/clickstack/self-configured/managing/estimating-resources)에서 산출한 수집 컴퓨팅 자원에 맞게 크기를 조정하십시오.

    이 서비스에서 데이터베이스와 수집 전용 사용자를 생성하십시오. 웨어하우스 내 모든 서비스는 접근 제어를 공유하므로, 여기에서 생성한 사용자는 웨어하우스의 모든 서비스에서 사용할 수 있습니다.

    ```sql
    CREATE DATABASE otel;
    CREATE USER hyperdx_ingest IDENTIFIED WITH sha256_password BY '<strong-password>';
    GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO hyperdx_ingest;
    ```

    `openssl rand -base64 24`와 같은 도구로 비밀번호를 생성하고, 매니페스트나 셸 이력이 아닌 시크릿 매니저에 저장하십시오. 자세한 내용은 [수집 사용자 생성](/ko/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) 가이드를 참조하십시오.

    이 서비스가 이미 웨어하우스(warehouse)에 속해 있다면, 같은 웨어하우스의 다른 서비스가 유휴 상태일 때 데이터베이스 수준 DDL이 응답 없이 멈출 수 있으므로 주의하십시오. 자세한 내용은 [관리 및 DDL](#administration)을 참조하십시오.
  </Step>

  <Step title="웨어하우스(warehouse)에 읽기 전용 서비스를 추가하십시오" id="add-read-only-service">
    ClickHouse Cloud 콘솔에서 방금 준비한 서비스의 더하기 기호(+)를 클릭하여 해당 서비스와 데이터를 공유하는 두 번째 서비스를 생성하십시오. 서비스 유형으로 **읽기 전용**을 선택하고, 용량 산정 모델에서 산출한 쿼리 컴퓨팅 자원에 맞게 크기를 설정하십시오.

    전체 절차는 [웨어하우스(warehouse) 설정 방법](/ko/products/cloud/features/infrastructure/warehouses#setup-warehouses) 가이드를 참조하십시오.
  </Step>

  <Step title="수집 데이터를 읽기/쓰기 서비스로 전송하도록 설정하십시오" id="point-ingestion">
    수집 사용자로 인증하여 **읽기-쓰기** 서비스 엔드포인트로 데이터를 내보내도록 collector를 구성하십시오:

    ```shell
    CLICKHOUSE_ENDPOINT=https://<read-write-service>.clickhouse.cloud:8443
    CLICKHOUSE_USER=hyperdx_ingest
    CLICKHOUSE_PASSWORD=<strong-password>
    HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel
    ```

    자세한 내용은 [수집기 설정 옵션](/ko/clickstack/self-configured/managing/config#otel-collector)을 참조하거나, [Vector](/ko/clickstack/observability/ingesting-data/vector) 및 기타 수집 경로의 동등한 설정을 참조하십시오.

    읽기 전용 엔드포인트로 전송된 쓰기 작업은 거부되므로, collector는 항상 읽기/쓰기 서비스를 대상으로 지정해야 합니다.
  </Step>

  <Step title="관측성 UI를 읽기 전용 서비스에 연결하십시오" id="point-clickstack">
    관측성 UI는 항상 ClickHouse Cloud 콘솔에서 해당 UI를 실행한 ClickHouse 서비스에 연결됩니다. 읽기 전용 컴퓨팅에서 실행하려면 다음 단계를 따르십시오.

    1. ClickHouse Cloud 콘솔에서 읽기 전용 서비스를 선택합니다.
    2. 왼쪽 탐색 메뉴에서 **ClickStack**을 선택합니다.

    이후 UI에서 실행하는 모든 쿼리는 해당 읽기 전용 컴퓨팅에서 실행됩니다. 관측성 UI 내부에서는 별도로 구성할 필요가 없습니다. 자세한 내용은 [읽기 전용 컴퓨팅에서 관측성 UI 사용하기](/ko/clickstack/self-configured/deployment/managed#clickstack-read-only-compute) 가이드를 참조하십시오.

    <Warning>
      **관측성 UI 상태는 서비스별로 관리됩니다**

      대시보드, 저장된 검색, 알림 및 소스는 관측성 UI를 실행한 서비스에 속합니다. 따라서 같은 웨어하우스(warehouse) 내의 두 서비스가 동일한 데이터를 공유하더라도 다른 서비스로는 이어지지 않습니다. [기본 OpenTelemetry 스키마(schema)](/ko/clickstack/self-configured/deployment/managed#adding-data-sources)를 사용하는 소스는 새 서비스에서 자동으로 감지되므로 해당 데이터는 바로 검색할 수 있습니다. 그러나 사용자 정의 소스나 수동으로 구성한 소스를 비롯해 저장한 다른 모든 항목은 다시 만들어야 합니다.

      대시보드를 만들기 전에 관측성 UI를 실행할 서비스를 먼저 정하십시오. 이미 운영 중인 배포를 전환하는 경우, 이전 서비스에서 생성한 알림은 삭제하기 전까지 이전 서비스에서 해당 서비스의 컴퓨트를 사용해 계속 평가된다는 점에 유의하십시오.
    </Warning>
  </Step>

  <Step title="분할 확인" id="verify">
    관측성 UI에서 검색을 실행하거나 대시보드를 연 다음, 쿼리가 어느 서비스에서 실행되었는지 확인하십시오. `system` 테이블은 쿼리를 실행한 노드에 기록되므로, 레플리카가 2개 이상인 서비스에서는 모든 레플리카를 조회하려면 `default` 클러스터 이름과 함께 [`clusterAllReplicas`](/ko/reference/system-tables/overview#querying-across-nodes)를 사용해야 합니다. **읽기 전용** 서비스에서는 다음과 같이 관측성 쿼리가 표시되어야 합니다:

    ```sql
    SELECT
        user,
        query_kind,
        http_user_agent,
        count()
    FROM clusterAllReplicas('default', system.query_log)
    WHERE event_time > now() - toIntervalMinute(10)
      AND type = 'QueryFinish'
      AND is_initial_query = 1
    GROUP BY ALL
    ORDER BY count() DESC;
    ```

    여기서 결과(result)가 비어 있다고 해서 그것만으로 쿼리가 다른 곳으로 전송되었다고 단정할 수는 없습니다. `system.query_log`는 주기적으로(기본값 7.5초마다) 플러시되므로, 검색 직후에 실행한 쿼리에는 해당 쿼리가 아직 나타나지 않을 수 있습니다. 잠시 기다린 후 다시 실행하거나, 권한이 있다면 [`SYSTEM FLUSH LOGS`](/ko/reference/statements/system#flush-logs)로 강제로 플러시하십시오.

    트래픽의 출처는 `user`와 `http_user_agent`를 기준으로 그룹화하여 구분합니다. 이렇게 하면 소스가 어떤 테이블(tables)을 가리키든 관계없이 UI, SQL 콘솔, 그 밖에 엔드포인트에 연결하는 다른 클라이언트를 서로 구분할 수 있습니다. `is_initial_query = 1`을 기준으로 필터링하면 제출된 쿼리마다 행이 하나씩만 남습니다. 분산 실행에서 발생하는 보조 쿼리와 [materialized view](/ko/reference/system-tables/query_views_log)를 평가하는 내부 쿼리는 `is_initial_query = 0`으로 따로 로그에 기록됩니다.

    **읽기-쓰기** 서비스에서 같은 쿼리를 실행하면 수집 사용자의 삽입만 표시되고 관측성 쿼리 트래픽은 표시되지 않아야 합니다.

    `default` 클러스터에는 현재 연결된 서비스의 복제본(replicas)만 포함되므로, 각 서비스에서 차례로 쿼리를 실행해 보는 것이 가장 확실한 검사 방법입니다. 웨어하우스(warehouse) 전체를 집계하여 보려면 대신 `all_groups.default` 클러스터 이름을 사용하십시오.

    ```sql
    SELECT
        hostName() AS host,
        query_kind,
        count()
    FROM clusterAllReplicas('all_groups.default', system.query_log)
    WHERE event_time > now() - toIntervalMinute(10)
      AND type = 'QueryFinish'
      AND is_initial_query = 1
    GROUP BY ALL;
    ```

    이 쿼리를 사용할 때는 두 가지 사항에 유의하십시오. 유휴 상태가 된 서비스는 행(rows)을 반환할 수 없으므로, 전체 결과(result)가 필요하다면 먼저 해당 서비스를 재개하십시오. 또한 `hostName()`은 서비스가 아니라 레플리카를 식별합니다. 따라서 특정 서비스의 활동을 확인하려면 해당 서비스에 직접 쿼리하십시오.
  </Step>
</Steps>

## 머지와 수집 분리하기 {#separating-merges}

매우 높은 수집 속도가 지속되면 삽입 자체보다 머지가 수집 서비스에서 가장 큰 비용을 차지하게 됩니다. 머지는 저장소를 공유하는 모든 읽기-쓰기 서비스에 할당되므로, 다른 용도로 마련한 서비스로 머지 작업이 넘어갈 수도 있습니다.

이러한 배포에서는 머지를 수집 서비스에서 완전히 떼어 내어 다음과 같은 3개 서비스 토폴로지를 구성할 수 있습니다.

| 서비스 | 유형             | 역할                                                                       |
| --- | -------------- | ------------------------------------------------------------------------ |
| 수집  | 읽기-쓰기, 머지 비활성화 | 삽입만 처리                                                                   |
| 머지  | 읽기-쓰기          | 웨어하우스(warehouse)의 모든 백그라운드 병합 및 뮤테이션(background merges and mutations) 실행 |
| 쿼리  | 읽기 전용          | 관측성 UI 제공                                                                |

<Info>
  **지원 요청 필요**

  읽기-쓰기 서비스의 머지 비활성화는 클라우드 콘솔에서 구성할 수 없습니다. 서비스에 적용하려면 [지원팀에 문의하세요](https://clickhouse.com/support/program).
</Info>

이 토폴로지는 수집만으로 서비스가 포화 상태에 이르는 경우나, 두 서비스 모두 쓰기를 수행해야 해서 읽기-쓰기 서비스가 2개 필요한 경우에 고려할 만합니다. 쿼리 워크로드를 읽기만 수행하는 관측성 UI가 전부 처리한다면, 더 단순한 [읽기-쓰기 및 읽기 전용 분리 구성](#architecture)으로 요구 사항을 충족할 수 있으며 이 방식이 더 잘 지원됩니다.

이 토폴로지를 운영할 때는 다음 사항에 유의하십시오.

* **두 읽기-쓰기 서비스 모두 자동 유휴 상태 전환에 의존하지 마십시오.** 머지가 비활성화된 서비스도 웨어하우스의 다른 서비스에서 발생한 삽입으로 인한 파트 다운로드 및 삭제 이벤트를 계속 처리하며, 머지되지 않은 파트 수가 많으면 그것만으로도 유휴 상태 전환이 차단될 수 있습니다. 두 읽기-쓰기 서비스가 항상 활성 상태로 유지된다는 전제로 계획하십시오.
* **두 읽기-쓰기 서비스 모두에서 쿼리를 실행하지 마십시오.** 읽기-쓰기 서비스에서 무거운 `SELECT` 쿼리를 실행하면 머지 작업과 CPU 및 메모리를 두고 경쟁하게 되며, 이는 바로 이 토폴로지가 방지하려는 장애 유형입니다. [위에서](#point-clickstack) 설명한 대로 관측성 UI가 읽기 전용 서비스를 가리키도록 설정하십시오.
* **뮤테이션은 이를 실행하는 서비스에서 추적됩니다.** 관측성 환경에서는 뮤테이션이 드뭅니다. 기본 관측성 스키마는 [`ttl_only_drop_parts = 1`](/ko/clickstack/self-configured/managing/ttl)을 설정하므로, 일반적인 보존 처리는 행을 변경해 제거하는 대신 TTL 머지 중에 만료된 파트 전체를 삭제합니다. 뮤테이션을 생성하는 `ALTER`를 수집 서비스에 제출하면 머지 서비스가 이를 수행하며, 진행 상황은 수집 서비스가 아닌 머지 서비스의 [`system.mutations`](/ko/reference/system-tables/mutations)에 표시됩니다.

## 관리 및 DDL {#administration}

모든 스키마 변경(schema changes)은 **읽기-쓰기** 서비스에서 실행해야 합니다. 여기에는 다음이 포함됩니다.

* 테이블 생성 - 최초 수집 시 ClickStack 수집기가 자동으로 수행합니다
* 보존 기간 변경을 위한 [TTL 수정](/ko/clickstack/self-configured/managing/ttl#modifying-ttl)
* 쿼리 가속을 위한 [materialized view](/ko/clickstack/self-configured/managing/materialized-views) 생성
* [스킵 인덱스, 프로젝션 및 기타 성능 최적화](/ko/clickstack/self-configured/managing/performance-tuning) 추가

사용자, 역할 및 권한 부여는 스키마 변경이 아닙니다. 이들은 웨어하우스(warehouse)의 모든 서비스가 공유하므로 어느 서비스에서든 한 번만 생성하면 됩니다. 앞의 [설정 단계](#prepare-read-write-service)에서는 수집 사용자를 생성합니다. 읽기 전용 서비스에 연결하는 그 밖의 클라이언트는 앞에서 설명한 수집용 권한이 아니라, [관측성 UI에 필요한 권한](/ko/clickstack/self-configured/managing/production#user-permissions)을 가진 별도의 읽기 전용 쿼리 사용자로 인증해야 합니다.

[SQL 콘솔](/ko/products/cloud/features/sql-console-features/sql-console) 또는 [ClickHouse client](/ko/concepts/features/interfaces/client)를 사용하여 읽기-쓰기 서비스에 연결하십시오. 웨어하우스는 저장소와 접근 제어를 공유하므로 변경 사항이 읽기 전용 서비스에 즉시 반영됩니다. [머지를 수집과 분리](#separating-merges)한 경우에는 두 읽기-쓰기 서비스 중 어느 쪽에서든 SQL 문을 실행할 수 있습니다. 단, 뮤테이션(mutation)은 머지 서비스에서 실행되고 추적된다는 점에 유의하십시오.

<Warning>
  **다른 서비스가 유휴 상태이면 데이터베이스 DDL이 멈출 수 있습니다**

  `CREATE`, `RENAME`, `DROP DATABASE` SQL 문은 웨어하우스 내에 유휴 상태이거나 중지된 서비스가 있으면 차단되어 멈출 수 있습니다. 읽기 전용 서비스는 지체 없이 유휴 상태로 전환되므로 이 토폴로지에서는 이 문제가 쉽게 발생합니다. 데이터베이스 수준 SQL 문은 쿼리별 또는 세션 단위로 [`distributed_ddl_task_timeout=0`](/ko/reference/settings/session-settings/distributed-ddl#distributed_ddl_task_timeout)을 설정한 상태에서 실행하십시오.

  ```sql
  CREATE DATABASE otel
  SETTINGS distributed_ddl_task_timeout=0
  ```

  수동으로 중지한 서비스는 다시 시작해야 해당 서비스에서 쿼리를 실행할 수 있습니다.
</Warning>

Materialized view는 삽입 시점에 트리거되므로 읽기-쓰기 서비스에서 실행됩니다. 읽기 전용 서비스는 materialized view의 대상 테이블을 일반 테이블과 동일하게 쿼리하며, 쿼리 가속을 위해 [데이터 소스에 등록된](/ko/clickstack/self-configured/managing/config#materialized-views-settings) 뷰도 마찬가지입니다.

## 에이전트형 워크로드 격리 {#agentic-workloads}

[MCP 서버](/ko/clickstack/observability/mcp)를 통해 연결된 AI 어시스턴트도 대시보드와 마찬가지로 읽기 트래픽에 해당하지만, 부하 패턴은 다릅니다. 인시던트를 조사하는 에이전트는 미리 정해지지 않은 범위를 대상으로 탐색용 쿼리를 짧은 시간에 연달아 대량으로 실행합니다. 에이전트와 UI가 하나의 읽기 전용 서비스를 공유하면, 같은 인시던트에 대응하는 엔지니어가 보고 있는 대시보드가 이러한 급증 부하의 영향을 받게 됩니다.

여기에도 동일한 웨어하우스(warehouse) 패턴을 적용하여 에이전트 전용 읽기 전용 컴퓨팅을 제공하십시오.

<Steps>
  <Step title="두 번째 읽기 전용 서비스 추가" id="agentic-add-service">
    [위의 설정](#add-read-only-service)과 동일한 방법으로 웨어하우스에 읽기 전용 서비스를 하나 더 생성하십시오. 이 서비스는 UI를 제공하는 서비스와 동일한 테이블을 읽으므로 데이터를 복사할 필요가 없습니다.

    그런 다음 [관측성 UI가 읽기 전용 서비스를 가리키도록 설정](#point-clickstack)과 같이 클라우드 콘솔에서 해당 서비스로 관측성 UI를 한 번 실행하십시오. Cloud MCP를 사용하려면 MCP뿐 아니라 관측성 UI도 활성화된 서비스가 필요합니다. 자세한 내용은 [MCP 사전 요구 사항](/ko/clickstack/observability/mcp#managed-prerequisites)을 참조하십시오.

    서비스 규모는 용량 산정 모델의 대시보드 QPS가 아니라 에이전트에서 예상되는 쿼리 부하를 기준으로 정하고, 자동 유휴 상태 전환은 활성화된 상태로 두십시오. 에이전트형 사용은 일반적으로 간헐적이므로 조사가 없는 동안에는 서비스가 유휴 상태로 전환될 수 있습니다.
  </Step>

  <Step title="해당 서비스에서 MCP 활성화" id="agentic-enable-mcp">
    ClickHouse Cloud 콘솔에서 읽기 전용 서비스를 열고 **Connect**를 클릭한 다음 **Connect with MCP**를 선택하여 활성화하십시오. 자세한 내용은 [원격 MCP 서버 활성화](/ko/products/cloud/features/ai-ml/mcp/remote-mcp#enable-remote-mcp-server)를 참조하십시오.
  </Step>

  <Step title="MCP 클라이언트가 해당 서비스를 가리키도록 설정" id="agentic-point-clients">
    Cloud MCP 엔드포인트는 모든 서비스에서 동일하며, 요청은 `x-service-id` 헤더에 따라 라우팅됩니다. 이 헤더가 없으면 요청은 계정에서 사용하는 첫 번째 관측성 서비스로 전달됩니다. 기존 MCP 구성을 복사한 후 새 읽기 전용 서비스의 ID를 담은 헤더를 추가하십시오.

    ```shell
    claude mcp add --transport http clickstack https://mcp.clickhouse.cloud/clickstack \
      --header "x-service-id: <read-only-agent-service-id>"
    ```

    이 헤더는 모든 MCP 클라이언트에서 전달할 수 있습니다. Cursor, VS Code 등에서의 동등한 구성은 [특정 서비스 대상으로 지정](/ko/clickstack/observability/mcp#managed-service-override)을 참조하십시오.
  </Step>
</Steps>

<Warning>
  **MCP는 대상 서비스에 상태를 기록합니다**

  MCP 서버는 쿼리 실행뿐 아니라 대시보드, 알림, 저장된 검색도 생성할 수 있으며, 이러한 상태는 다른 모든 [관측성 UI 상태](#point-clickstack)와 마찬가지로 요청이 라우팅된 서비스에 귀속됩니다. 에이전트가 에이전트용 서비스에서 생성한 대시보드는 엔지니어가 사용하는 서비스에서 실행한 관측성 UI에 표시되지 않으며, 그곳에서 생성한 알림은 해당 서비스의 컴퓨트에서 평가됩니다. 이때 [아래](#isolating-alerts)에서 설명하는 것처럼 에이전트 서비스가 유휴 상태이면 평가가 지연되거나 누락될 수 있습니다. 지속적으로 유지해야 하는 결과물을 생성할 것으로 예상되는 에이전트는 팀이 사용하는 서비스로 라우팅하십시오.
</Warning>

## 알림 {#alerts}

알림은 해당 알림이 생성된 서비스에서 평가되므로, UI와 동일한 컴퓨트에서 실행됩니다. 이 토폴로지에서는 읽기 전용 서비스가 이에 해당합니다.

<Note>
  **자체 관리형 ClickHouse Observability**

  알림을 활성화하려면 **서비스 관리자** 권한이 있는 사용자 중 최소 1명이 관측성 UI에 한 번 이상 로그인해야 합니다. 이때 알림 쿼리를 실행하는 전용 데이터베이스 사용자(database user)가 프로비저닝되며, 이 사용자는 웨어하우스(warehouse) 내 모든 서비스에서 공유됩니다. 자세한 내용은 [자체 관리형 ClickHouse Observability에 대한 액세스 권한 부여](/ko/clickstack/self-configured/deployment/managed#configure-access) 가이드를 참조하십시오.
</Note>

알림 평가는 주기적으로 실행되는 쿼리 워크로드입니다. 읽기 전용 서비스의 용량을 산정할 때 기준이 되는 QPS에 이를 포함하십시오. [용량 산정 모델](/ko/clickstack/self-configured/managing/estimating-resources#refining-sizing-assumptions)은 검색, 대시보드, 알림 쿼리를 하나의 집계 수치로 취급합니다.

### 알림 평가 격리 {#isolating-alerts}

알림은 사용자가 직접 생성하므로 알림 부하를 중앙에서 라우팅할 수 없습니다. 관측성 UI에서 알림을 추가하면 해당 알림은 사용자가 작업 중인 서비스에 추가되며, 그 서비스의 컴퓨트에서 평가됩니다. 서비스의 알림을 다른 곳으로 옮기는 설정은 없습니다.

격리할 수 있는 것은 중앙에서 소유하는 알림, 즉 플랫폼 팀이 조직 전체를 위해 관리하는 알림입니다. 이러한 알림은 대개 가장 자주 평가되는 알림이기도 합니다. 웨어하우스(warehouse)에 이러한 알림 전용 읽기 전용 서비스를 두고, 해당 서비스에서 실행한 관측성 UI에서 알림을 생성하십시오.

| 서비스 | 유형    | 제공 대상                   |
| --- | ----- | ----------------------- |
| 수집  | 읽기-쓰기 | OpenTelemetry collector |
| 쿼리  | 읽기 전용 | 관측성 UI 및 사용자가 직접 생성한 알림 |
| 알림  | 읽기 전용 | 플랫폼 팀이 관리하는 공통 알림       |

<Warning>
  **알림 서비스의 자동 유휴 상태 전환 비활성화**

  서비스에 알림이 구성되어 있다고 해서 서비스가 활성 상태로 유지되지는 않습니다. 유휴 상태의 서비스에서 실행되는 알림 평가는 서비스 재개 때문에 지연되거나 아예 실패하므로, 자동 유휴 상태 전환이 활성화된 알림 서비스에서는 평가가 누락될 수 있습니다. 해당 서비스의 자동 유휴 상태 전환을 끄고 상시 가동을 전제로 계획하십시오. 이는 알림이 평가되는 모든 서비스에 동일하게 적용됩니다. 알림이 UI를 제공하는 서비스에서 실행된다면 해당 서비스 역시 유휴 상태로 전환되도록 두어서는 안 됩니다.
</Warning>

그 밖의 절충 관계는 상태(state)가 서비스별로 관리된다는 점에서 비롯됩니다.

* 공통 알림과 관련 대시보드는 알림 서비스에만 존재하며, 쿼리 서비스에서 작업하는 사용자에게는 표시되지 않습니다. 어느 경우든 알림은 동일한 [대상](/ko/clickstack/observability/features/alerts)으로 전달되므로, 사용자가 잃는 것은 알림 기능 자체가 아니라 알림 정의에 대한 가시성입니다.
* 알림 서비스의 소스는 별도의 객체입니다. [기본 OpenTelemetry 스키마(schema)](/ko/clickstack/self-configured/deployment/managed#adding-data-sources)를 사용하는 소스는 자동으로 감지되지만, 사용자 정의 소스는 알림에서 참조하려면 해당 서비스에서도 따로 구성해야 합니다.

알림 규모가 작아 평가 부하가 대시보드 트래픽에 비해 무시할 수 있을 정도라면 모든 것을 하나의 읽기 전용 서비스에 두십시오. 이 경우에는 두 곳에서 정의를 관리하는 운영 비용이 더 큰 부담이 됩니다.

## 추가 고려 사항 {#considerations}

**자동 유휴 상태 전환.** 유휴 상태가 된 읽기 전용 서비스에 대한 첫 번째 쿼리는 서비스가 시작될 때까지 대기합니다. 따라서 간헐적으로 사용하는 경우 약간의 지연 시간을 감수하는 대신 비용을 절감할 수 있습니다. 알림이 유휴 상태 전환을 막아 줄 것이라고 기대해서는 안 됩니다. [위에서](#isolating-alerts) 설명한 대로, 알림 평가를 맡는 서비스에서는 자동 유휴 상태 전환을 비활성화하십시오. 지속적인 수집이 이루어지면 읽기/쓰기 서비스는 계속 활성 상태로 유지됩니다. 그러나 수집이 간헐적이거나 일정에 따라 이루어지는 경우에는 유휴 기간 이후의 첫 번째 배치도 같은 방식으로 대기하며, 이는 텔레메트리 지연으로 나타납니다.

**백업.** 백업은 기본 서비스에서만 수행되며, 웨어하우스(warehouse) 전체의 데이터를 포함합니다. 백업을 복원하면 기존 웨어하우스와 연결되지 않은 완전히 새로운 서비스가 생성됩니다.

**복제본 수 제한.** 웨어하우스 내 모든 서비스의 레플리카 수를 합산한 값에는 기본적으로 상한이 적용됩니다. 자세한 내용은 [사용 한도](/ko/products/cloud/guides/best-practices/usagelimits)를 참조하십시오.

**관측성을 다른 워크로드와 격리.** 실시간 애플리케이션 분석 등 다른 워크로드를 이미 실행 중인 서비스에 관측성 UI를 추가하는 경우에도 동일한 웨어하우스 기능을 사용하여 관측성 전용 컴퓨트를 할당합니다. 자세한 내용은 [관측성 워크로드 격리](/ko/clickstack/self-configured/managing/estimating-resources#isolating-workloads) 가이드를 참조하십시오.

웨어하우스의 전체 동작 및 제한 사항은 [웨어하우스](/ko/products/cloud/features/infrastructure/warehouses) 가이드를 참조하십시오.
