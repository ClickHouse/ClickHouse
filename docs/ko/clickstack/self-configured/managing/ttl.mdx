## TTL을 이용한 데이터 보존 기간 관리 {#ttl-clickstack}

TTL(Time-to-Live)은 자체 관리형 ClickHouse Observability 환경에서 효율적인 데이터 보존 및 관리를 위한 핵심 기능이며, 방대한 양의 데이터가 지속적으로 생성되는 환경에서 특히 중요합니다. TTL을 사용하면 오래된 데이터가 자동으로 만료되어 삭제되므로, 수동으로 개입하지 않아도 저장소를 최적으로 활용하고 성능을 유지할 수 있습니다. 이 기능은 데이터베이스를 가볍게 유지하고 저장소 비용을 절감하며, 가장 관련성 높은 최신 데이터에 집중하여 쿼리를 빠르고 효율적으로 유지하는 데 필수적입니다. 또한 데이터 수명 주기를 체계적으로 관리하여 데이터 보존 정책을 준수하는 데 도움이 되며, 결과적으로 관측성 솔루션의 전반적인 지속 가능성과 확장성을 높여 줍니다.

**기본적으로 데이터는 30일 동안 보존됩니다. 이를 변경하려면 [&quot;TTL 수정&quot;](#modifying-ttl)을 참조하십시오.**

ClickHouse에서 TTL은 테이블 수준에서 제어됩니다. 예를 들어, 로그의 기본 스키마(schema)는 아래와 같습니다. collector가 테이블을 생성할 때 `${TABLES_TTL}`은 구성된 보존 기간(변경하지 않은 경우 30일)으로 대체됩니다.

ClickHouse의 파티셔닝을 사용하면 컬럼 또는 SQL 표현식(SQL expression)을 기준으로 디스크상의 데이터를 논리적으로 분리할 수 있습니다. 데이터를 논리적으로 분리하면 각 파티션을 독립적으로 처리할 수 있습니다. 예를 들어 TTL 정책에 따라 만료된 파티션을 삭제할 수 있습니다.

위 예시에서 볼 수 있듯이, 파티셔닝은 테이블을 처음 정의할 때 `PARTITION BY` 절로 지정합니다. 이 절에는 하나 이상의 컬럼에 대한 SQL 표현식을 지정할 수 있으며, 그 결과에 따라 각 행이 저장될 파티션이 결정됩니다. 이에 따라 데이터는 디스크상의 각 파티션과 (공통 폴더 이름 접두사를 통해) 논리적으로 연결되며, 파티션별로 개별 쿼리할 수 있습니다. 위 예시에서 기본 `otel_logs` 스키마는 `toDate(Timestamp)` 표현식을 사용하여 일 단위로 파티셔닝합니다. 행이 ClickHouse에 삽입되면 각 행에 대해 이 표현식이 평가되고, 결과에 해당하는 파티션이 존재하면 해당 파티션으로 라우팅됩니다(해당 일자의 첫 번째 행인 경우 파티션이 새로 생성됩니다). 파티셔닝 및 그 밖의 활용 방법에 대한 자세한 내용은 [&quot;테이블 파티션&quot;](/ko/concepts/core-concepts/partitions)을 참조하십시오.

테이블 스키마에는 `TTL toDateTime(Timestamp) + ${TABLES_TTL}`과 `ttl_only_drop_parts = 1` 설정도 포함되어 있습니다. 앞의 절은 구성된 TTL(기본값 30일)보다 오래된 데이터가 삭제되도록 합니다. `ttl_only_drop_parts = 1` 설정은 (행을 부분적으로 삭제하는 대신) 모든 데이터가 만료된 데이터 파트만 만료 처리하도록 합니다. 파티셔닝으로 인해 서로 다른 날짜의 데이터는 절대 &quot;머지&quot;되지 않으므로, 데이터를 효율적으로 삭제할 수 있습니다.

<Warning>
  **`ttl_only_drop_parts`**

  항상 [`ttl_only_drop_parts=1`](/ko/reference/settings/merge-tree-settings/other#ttl_only_drop_parts) 설정을 사용할 것을 권장합니다. 이 설정을 활성화하면 ClickHouse는 파트 내 모든 행이 만료되었을 때 파트 전체를 삭제합니다. TTL이 적용된 행을 부분적으로 정리하는 대신(`ttl_only_drop_parts=0`인 경우 리소스를 많이 소모하는 뮤테이션으로 수행됨) 파트 전체를 삭제하면 `merge_with_ttl_timeout` 시간을 더 짧게 설정할 수 있고 시스템 성능에 미치는 영향도 줄어듭니다. TTL 만료를 수행하는 단위(예: 일)와 동일한 단위로 데이터를 파티셔닝하면, 각 파트에는 자연스럽게 해당 구간의 데이터만 포함됩니다. 따라서 `ttl_only_drop_parts=1`을 효율적으로 적용할 수 있습니다.
</Warning>

기본적으로 TTL이 만료된 데이터는 ClickHouse가 [데이터 파트를 머지](/ko/reference/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage)할 때 제거됩니다. ClickHouse는 데이터 만료를 감지하면 일정 외 머지를 수행합니다.

<Info>
  **TTL 일정**

  앞서 언급했듯이 TTL은 즉시 적용되지 않고 일정에 따라 적용됩니다. MergeTree 테이블 설정 `merge_with_ttl_timeout`은 삭제 TTL이 포함된 머지를 반복하기 전까지의 최소 지연 시간을 초 단위로 지정합니다. 기본값은 14400초(4시간)입니다. 다만 이는 최소 지연 시간일 뿐이며, 실제로 TTL 머지가 트리거되기까지는 더 오래 걸릴 수 있습니다. 값이 너무 낮으면 일정 외 머지가 자주 수행되어 리소스를 많이 소모할 수 있습니다. `ALTER TABLE my_table MATERIALIZE TTL` 명령을 사용하면 TTL 만료를 강제로 실행할 수 있습니다.
</Info>

## TTL 수정 {#modifying-ttl}

TTL은 다음 방법 중 하나로 수정할 수 있습니다.

1. **테이블 스키마(table schemas) 수정(권장)**. 이 방법을 사용하려면 [clickhouse-client](/ko/concepts/features/interfaces/client) 또는 [Cloud SQL 콘솔](/ko/products/cloud/features/sql-console-features/sql-console) 등으로 ClickHouse 인스턴스에 연결해야 합니다. 예를 들어, 다음 DDL로 `otel_logs` 테이블의 TTL을 수정할 수 있습니다.

```sql
ALTER TABLE default.otel_logs
MODIFY TTL TimestampTime + toIntervalDay(7);
```

2. **OTel collector 수정**. ClickStack OpenTelemetry 수집기는 ClickHouse에 테이블이 없으면 테이블을 생성합니다. 이 작업은 ClickHouse 익스포터가 수행하며, 이 익스포터는 기본 TTL 표현식(TTL expression)을 제어하는 `ttl` 매개변수를 제공합니다. 예를 들면 다음과 같습니다.

```yaml
exporters:
 clickhouse:
   endpoint: tcp://localhost:9000?dial_timeout=10s&compress=lz4&async_insert=1
   ttl: 72h
```

### 컬럼 수준 TTL {#column-level-ttl}

위 예시는 테이블 수준에서 데이터를 만료시킵니다. 컬럼 수준에서도 데이터를 만료시킬 수 있습니다. 이 기능을 사용하면 데이터가 오래됨에 따라 조사에 주는 가치에 비해 보존에 드는 리소스 오버헤드가 큰 컬럼을 삭제할 수 있습니다. 예를 들어, 삽입 시점(insert time)에 추출되지 않은 새로운 동적 메타데이터(예: 새로운 Kubernetes 레이블)가 추가될 때를 대비해 `Body` 컬럼을 유지하는 것을 권장합니다. 하지만 일정 기간(예: 1개월)이 지나면 이러한 추가 메타데이터가 유용하지 않다는 점이 분명해질 수 있으며, 그만큼 `Body` 컬럼을 유지할 가치도 줄어듭니다.

다음은 30일 후 `Body` 컬럼을 삭제하는 방법입니다.

```sql
CREATE TABLE otel_logs_v2
(
        `Body` String TTL Timestamp + INTERVAL 30 DAY,
        `Timestamp` DateTime,
 ...
)
ENGINE = MergeTree
ORDER BY (ServiceName, Timestamp)
```

<Note>
  컬럼 수준 TTL을 지정하려면 사용자가 스키마(schema)를 직접 정의해야 합니다. 컬럼 수준 TTL은 OTel collector에서 지정할 수 없습니다.
</Note>
