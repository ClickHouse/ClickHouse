<Note>
  이 페이지에서는 **자체 관리형 ClickHouse Observability**를 다룹니다. 권장되는 완전 관리형 환경에 대해서는 [여기](/ko/clickstack/observability/managing/config)의 문서를 참고하십시오.
</Note>

이 가이드에서는 자체 관리형 ClickHouse Observability의 데이터 소스 설정, 직접 실행하는 collector, 데이터베이스 스키마(database schema) 구성을 설명합니다.

## 사용자 인터페이스 {#hyperdx}

### 데이터 소스 설정 {#datasource-settings}

UI를 사용하려면 관측성(Observability)의 각 데이터 타입/핵심 요소별로 소스를 정의해야 합니다.

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

소스를 구성하려면 **팀 설정 → 데이터 → 소스**를 여십시오. 추가 설정을 표시하려면 **Configure Optional Fields**를 선택하십시오. 아래는 로그 소스의 예시입니다.

<div className="ch-image-md">
  <Frame>
    ![Configure Optional Fields가 강조 표시된 로그 소스 설정](/images/clickstack/source-settings-optional-fields.png)
  </Frame>
</div>

UI가 데이터를 쿼리하려면 각 소스에 테이블과 컬럼 매핑이 필요합니다. OTel 메트릭 소스는 메트릭 유형마다 별도의 테이블을 사용하므로, 수집 중인 메트릭이 들어 있는 테이블을 선택하십시오.

ClickStack과 함께 배포되는 [기본 OpenTelemetry(OTel) 스키마(schema)](/ko/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema)를 사용하면 각 소스의 컬럼이 자동으로 추론됩니다. [스키마를 수정](#clickhouse)하거나 사용자 정의 스키마를 사용한다면 사용자가 이러한 매핑을 직접 지정하고 갱신해야 합니다.

<Note>
  ClickStack 수집기는 번들로 포함된 스키마 마이그레이션(schema migration)을 통해 기본 테이블을 생성합니다. 이 스키마는 [OTel collector용 ClickHouse 익스포터](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter)와 [OpenTelemetry 데이터 모델](https://opentelemetry.io/docs/specs/otel/logs/data-model/)을 기반으로 합니다.
</Note>

다음 표에 소스 설정이 정리되어 있습니다. 추론되는 값은 데이터베이스에 있는 컬럼과 테이블에 따라 달라집니다. 선택 사항인 매핑을 지정하면 트레이스 상관관계 분석 등 관련 기능이 활성화되며, 소스를 저장할 때 반드시 지정할 필요는 없습니다.

#### materialized view {#materialized-views-settings}

materialized view를 로그 및 트레이스 데이터 소스에 등록하면, 조건을 충족하는 집계 쿼리(aggregation queries)를 원본 테이블 대신 사전 집계된 뷰(view)에서 처리합니다. 뷰를 생성하고 등록하는 방법은 [&quot;materialized view&quot;](/ko/clickstack/self-configured/managing/materialized-views)를 참조하십시오.

등록된 각 뷰에는 다음 설정을 구성합니다.

| 설정                       | 설명                                                                                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Database`               | materialized view의 target table이 있는 ClickHouse 데이터베이스(Database)입니다.                                                                                     |
| `Table`                  | materialized view의 target table입니다. 뷰 자체가 아닙니다.                                                                                                         |
| `Timestamp Column`       | target table의 타임스탬프 컬럼입니다.                                                                                                                              |
| `Granularity`            | target table 타임스탬프 컬럼의 시간 버킷(time bucket)입니다(예: `1 minute`). 쿼리의 시간 버킷이 이 값과 같거나 더 큰 경우에만 해당 쿼리에서 뷰를 사용할 수 있습니다.                                        |
| `Minimum Date`           | 선택 사항. 뷰에 데이터가 존재하는 가장 이른 날짜 및 시간입니다. 지정하지 않으면 ClickStack은 원본 테이블에 데이터가 있는 모든 날짜에 대해 뷰에도 데이터가 있는 것으로 간주합니다.                                             |
| `Dimension Columns`      | 뷰에서 사전 집계되지 않아 필터링 및 그룹화에 사용할 수 있는 컬럼 목록이며, 쉼표로 구분합니다.                                                                                                  |
| `Pre-aggregated Columns` | 뷰에서 사전 집계되는 컬럼입니다. 각 항목은 집계 함수(`avg`, `count`, `max`, `min`, `quantile`, `sum` 또는 `histogram`)와 원본 테이블 컬럼을 뷰의 해당 컬럼에 매핑합니다. `count`에는 원본 컬럼이 필요하지 않습니다. |

target table을 선택하면 UI가 뷰 스키마(schema)에서 이러한 설정을 추론합니다. 추론된 값을 검토하고 누락된 필드를 입력하십시오.

#### 메타데이터 materialized view {#metadata-materialized-views-settings}

메타데이터 materialized view는 필터와 자동 완성에 사용되는 필드 디스커버리를 가속화하는 materialized view입니다. 로그 및 트레이스 데이터 소스에서 구성할 수 있습니다.

| 설정                 | 설명                                                   |
| ------------------ | ---------------------------------------------------- |
| `Key Rollup Table` | 선택 사항이며 사용 중단 권고 대상입니다. 원본 테이블에 있는 키를 집계한 롤업 테이블입니다. |
| `KV Rollup Table`  | 원본 테이블에 있는 키/값 쌍을 집계한 롤업 테이블입니다.                     |
| `Granularity`      | 롤업 테이블에서 사용하는 시간 버킷(time bucket)입니다(예: `15 minute`). |

#### 강조 표시할 속성 {#highlighted-attributes}

강조 표시할 속성과 강조 표시할 트레이스 속성은 로그 및 트레이스 데이터 소스에서 구성할 수 있습니다.

* 강조 표시할 속성은 로그 또는 스팬의 세부 정보를 볼 때 각 로그 또는 스팬마다 표시되는 컬럼 또는 표현식입니다.
* 강조 표시할 트레이스 속성은 트레이스 내 각 로그 또는 스팬에서 조회되어 트레이스 워터폴 위에 표시되는 컬럼 또는 표현식입니다.

이러한 속성은 소스 구성에서 정의하며, 임의의 SQL 표현식(SQL expression)을 사용할 수 있습니다. SQL 표현식이 URL 형태의 값을 반환하면 해당 속성은 링크로 표시됩니다. 빈 값은 표시되지 않습니다.

각 속성은 다음 설정으로 구성합니다.

| 설정                  | 설명                                                |
| ------------------- | ------------------------------------------------- |
| `SQL Expression`    | 쿼리할 컬럼 또는 임의의 SQL 표현식입니다. 필수 항목입니다.               |
| `Alias`             | 선택 사항. SQL 표현식 대신 속성에 표시할 레이블입니다.                 |
| `Lucene Expression` | 선택 사항. 이 속성 값으로 검색할 때 사용하는 Lucene 버전의 SQL 표현식입니다. |

예를 들어, 다음 트레이스 소스에는 강조 표시할 속성과 강조 표시할 트레이스 속성이 하나씩 구성되어 있습니다.

### 상관관계 소스 {#correlated-sources}

소스 간 상관관계를 온전히 활용하려면 로그, 트레이스, 메트릭, 세션에 대해 상관관계 소스를 구성해야 합니다. 이렇게 하면 UI에서 관련 데이터를 서로 연관시키고, 이벤트를 렌더링할 때 풍부한 컨텍스트를 제공할 수 있습니다.

* `Logs`: 트레이스 및 메트릭과 연관시킬 수 있습니다.
* `Traces`: 로그, 세션, 메트릭과 연관시킬 수 있습니다.
* `Metrics`: 로그와 연관시킬 수 있습니다.
* `Sessions`: 트레이스와 연관시킬 수 있습니다.

이러한 상관관계를 설정하면 여러 기능을 사용할 수 있습니다. 예를 들어 UI에서 트레이스와 함께 관련 로그를 렌더링하고, 관련 소스 간에 이동할 수 있습니다. 단, 상관관계가 제대로 동작하려면 적절한 ID 및 속성 매핑이 필요하며, 소스를 선택하는 것만으로는 이러한 관계가 생성되지 않습니다.

## OpenTelemetry collector {#otel-collector}

자세한 내용은 [&quot;ClickStack OpenTelemetry 수집기&quot;](/ko/clickstack/self-configured/ingesting-data/collector)를 참조하십시오.

* `CLICKHOUSE_ENDPOINT`
  * **기본값:** 독립형 collector image에서는 *None (필수)*&#xC785;니다.
  * **설명:** 익스포터가 사용하는 ClickHouse 연결 URL입니다.
  * **가이드:**
    * `https://<host>:8443` 또는 `tcp://<host>:9440?secure=true`와 같은 보안 ClickHouse Cloud 엔드포인트를 사용하십시오
    * collector가 ClickHouse로 데이터를 전송하려면 반드시 설정해야 합니다

* `CLICKHOUSE_USER`
  * **기본값:** 마이그레이션 도구에서는 `default`입니다. 독립형 collector에서는 명시적으로 설정하십시오.
  * **설명:** ClickHouse 인스턴스 인증에 사용하는 사용자 이름입니다.
  * **가이드:**
    * 이 사용자에게는 텔레메트리를 삽입할 권한이 필요하며, 스키마 생성 또는 마이그레이션(Migrations)이 활성화된 경우 필요한 데이터베이스 객체를 생성하거나 변경할 권한도 필요합니다
    * 수집 전용 사용자를 별도로 생성하는 것을 권장합니다

* `CLICKHOUSE_PASSWORD`
  * **기본값:** *None (인증이 활성화된 경우 필수)*
  * **설명:** 지정한 ClickHouse 사용자의 비밀번호입니다.
  * **가이드:**
    * 사용자 계정에 비밀번호가 설정되어 있으면 필수입니다
    * 운영 환경 배포에서는 시크릿을 사용해 안전하게 저장하십시오

* `HYPERDX_LOG_LEVEL`
  * **기본값:** 배포 환경에 따라 다릅니다. `info`와 같이 명시적으로 설정하십시오.
  * **설명:** collector의 로그 상세 수준입니다.
  * **가이드:**
    * `debug`, `info`, `warn`, `error` 등의 값을 지정할 수 있습니다
    * 문제 해결 시에는 `debug`를 사용하십시오

* `OTLP_AUTH_TOKEN`
  * **기본값:** *None*. 독립형 image에서만 사용됩니다.
  * **설명:** 독립형 OTLP 수집에 필요한 토큰을 설정합니다. 현재 collector는 `Authorization` 헤더에 이 값을 그대로 넣거나 `Bearer` 접두사를 붙인 형식을 모두 허용합니다. 이전 버전의 collector에서는 접두사 없는 토큰만 허용될 수 있습니다. OIDC 인증이 구성된 경우에는 무시됩니다.
  * **가이드:**
    * collector를 외부에 노출하기 전에 인증을 구성하십시오. 토큰이나 OIDC 구성이 없으면 독립형 OTLP 수신기는 인증되지 않은 요청도 허용합니다.

* `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`
  * **기본값:** 마이그레이션 도구에서는 `default`입니다. 독립형 collector에서는 명시적으로 설정하십시오.
  * **설명:** collector가 텔레메트리 데이터를 기록할 ClickHouse 데이터베이스입니다.
  * **가이드:**
    * 사용자 지정 데이터베이스 이름을 사용하는 경우 설정하십시오
    * 지정한 사용자가 이 데이터베이스에 접근할 수 있는지 확인하십시오

## ClickHouse {#clickhouse}

ClickHouse를 효과적으로 튜닝하려면 [파트](/ko/concepts/core-concepts/parts), [파티션](/ko/concepts/core-concepts/partitions), [세그먼트와 레플리카](/ko/guides/oss/deployment-and-scaling/shards) 같은 핵심 스토리지 개념과 삽입 시점(insert time)에 [머지](/ko/concepts/core-concepts/merges)가 어떻게 이루어지는지 이해해야 합니다. [프라이머리 인덱스](/ko/concepts/core-concepts/primary-indexes), [희소 보조 인덱스(Secondary Indices)](/ko/concepts/features/performance/skip-indexes/skipping-indexes), 데이터 건너뛰기 인덱스(data skipping indices)의 기본 개념과 함께 TTL 기반 수명 주기 등 [데이터 수명 주기 관리](/ko/guides/use-cases/observability/build-your-own/managing-data) 기법도 살펴볼 것을 권장합니다.

[스키마(schema) 사용자 정의](/ko/guides/use-cases/observability/build-your-own/schema-design)도 활용할 수 있습니다. 컬럼 타입을 수정하고, 로그 등에서 새 필드를 추출하고, 코덱과 딕셔너리를 적용하며, 프로젝션으로 쿼리를 가속화할 수 있습니다.

또한 materialized view를 사용하면 [수집 과정에서 데이터를 변환하거나 필터링](/ko/guides/use-cases/observability/build-your-own/schema-design#materialized-views)할 수 있습니다. 단, 데이터는 뷰의 원본 테이블에 기록하고 애플리케이션은 target table에서 데이터를 읽어야 합니다. materialized view를 사용하여 서비스 내에서 [쿼리를 네이티브로 가속화](/ko/clickstack/self-configured/managing/materialized-views)할 수도 있습니다.

자세한 내용은 스키마 설계, 인덱싱(indexing) 전략, 데이터 관리 권장 사항에 관한 ClickHouse 문서를 참조하십시오. 해당 내용 대부분은 자가 관리형 배포에 그대로 적용됩니다.
