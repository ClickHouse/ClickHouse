<Note>
  이 페이지에서는 **자체 관리형 ClickHouse Observability**를 다룹니다. 권장되는 완전 관리형 환경에 대해서는 [여기](/ko/clickstack/observability/getting-started)의 문서를 참고하십시오.
</Note>

이 **가이드는 ClickHouse Cloud 기존 사용자를 대상으로 합니다**. ClickHouse Cloud를 처음 사용한다면 자체 관리형 ClickHouse Observability의 [시작하기](/ko/clickstack/self-configured/getting-started/managed) 가이드를 먼저 참고하십시오.

이 배포 패턴에서는 ClickHouse와 ClickStack UI가 모두 ClickHouse Cloud에서 호스팅되므로, 사용자가 직접 호스팅해야 하는 구성 요소를 최소화할 수 있습니다.

이 배포 패턴은 인프라 관리 부담을 줄여 줄 뿐 아니라, 인증이 ClickHouse Cloud SSO/SAML과 통합됩니다. 또한 자체 호스팅 배포와 달리 대시보드, 저장된 검색, 사용자 설정, 알림 등의 애플리케이션 상태를 저장하기 위해 MongoDB 인스턴스를 프로비저닝할 필요가 없습니다. 이 밖에도 다음과 같은 이점이 있습니다.

* 스토리지와 독립적인 컴퓨트 자동 확장
* 객체 스토리지 기반의 저렴하고 사실상 무제한에 가까운 데이터 보존
* 웨어하우스(warehouses)를 사용한 [읽기 및 쓰기(write) 워크로드(workloads)의 독립적 격리](/ko/clickstack/self-configured/managing/isolating-read-write)
* 통합 인증
* 자동 백업
* 보안 및 컴플라이언스 기능
* 원활한 업그레이드

이 모드에서는 데이터 수집을 전적으로 사용자가 담당합니다. 직접 호스팅하는 OpenTelemetry collector, 클라이언트 라이브러리를 통한 직접 수집, ClickHouse 네이티브 테이블 엔진(Kafka, S3 등), ETL 파이프라인 또는 ClickHouse Cloud의 관리형 수집 서비스인 ClickPipes를 사용하여 자체 관리형 ClickHouse Observability로 데이터를 수집할 수 있습니다. 이 방식은 ClickStack을 가장 간단하면서도 높은 성능으로 운영할 수 있는 방법입니다.

### 적합한 사용 사례 {#suitable-for}

이 배포 패턴은 다음과 같은 시나리오에 적합합니다.

1. ClickHouse Cloud에 이미 관측성 데이터가 있으며, 이를 ClickStack으로 시각화하려는 경우
2. 대규모 관측성 환경을 운영하고 있으며, ClickHouse Cloud에서 실행되는 ClickStack의 전용 성능과 확장성이 필요한 경우
3. 이미 분석 용도로 ClickHouse Cloud를 사용하고 있으며, ClickStack instrumentation 라이브러리로 애플리케이션을 계측하여 동일한 클러스터로 데이터를 전송하려는 경우. 이때는 [웨어하우스(warehouses)](/ko/products/cloud/features/infrastructure/warehouses)를 사용하여 관측성 워크로드(workloads)용 컴퓨트를 격리하는 것이 좋습니다.

### 수집 시작(선택 사항) {#start-ingestion-existing}

            OpenTelemetry로 계측할 기존 애플리케이션이나 인프라가 있다면 &quot;애플리케이션 연결&quot;에 링크된 관련 가이드를 참조하십시오.

            트레이스와 로그를 수집하도록 애플리케이션을 계측하려면 [언어 SDK 가이드](/ko/clickstack/observability/ingesting-data/sdks/index)의 자가 관리형 안내를 따르십시오. SDK는 수집된 데이터를 OpenTelemetry Collector로 전송하며, 이 collector가 gateway 역할을 하여 자체 관리형 ClickHouse Observability로 데이터를 수집합니다.

            로그는 에이전트 모드로 실행되는 [OpenTelemetry 수집기를 사용하여 수집](/ko/clickstack/observability/integration-examples/host-logs#self-managed)할 수 있으며, 수집된 데이터는 동일한 collector로 전달됩니다. Kubernetes 모니터링은 [전용 가이드](/ko/clickstack/observability/integration-examples/kubernetes#self-managed)를 따르십시오. 기타 통합은 [빠른 시작 가이드](/ko/clickstack/observability/integration-examples/index)를 참조하십시오.

          </Tab>

          <Tab title="Vector">
            [Vector](https://vector.dev)는 고성능의 벤더 중립적인 관측성 데이터 파이프라인으로, 유연성이 높고 리소스 사용량이 적어 특히 로그 수집에 널리 사용됩니다.

            ClickStack에서 Vector를 사용할 때는 사용자가 스키마(schemas)를 직접 정의해야 합니다. 이러한 스키마는 OpenTelemetry 규칙을 따를 수도 있고, 사용자가 정의한 이벤트 구조를 나타내는 완전한 사용자 정의 형태일 수도 있습니다.

            <Info>
              **타임스탬프 필수**

              자체 관리형 ClickHouse Observability의 유일한 필수 요구 사항은 데이터에 **타임스탬프 컬럼**(또는 동등한 시간 필드)이 포함되어야 한다는 것입니다. 이 컬럼은 ClickStack UI에서 데이터 소스를 구성할 때 지정할 수 있습니다.
            </Info>

            이하 내용은 ingest pipeline으로 미리 구성된 Vector 인스턴스가 실행 중이며 데이터를 전송하고 있다고 가정합니다.

### 데이터베이스 및 테이블 생성 {#create-database-and-tables}

            Vector를 사용하려면 데이터를 수집하기 전에 테이블과 스키마(schema)를 미리 정의해야 합니다.

            먼저 데이터베이스를 생성하십시오. 이 작업은 [ClickHouse Cloud 콘솔](/ko/products/cloud/features/sql-console-features/sql-console)에서 수행할 수 있습니다.

            예를 들어, 다음과 같이 로그용 데이터베이스를 생성합니다:

            ```sql
            CREATE DATABASE IF NOT EXISTS logs
            ```

            그런 다음 로그 데이터의 structure에 맞는 스키마(schema)를 가진 테이블을 생성하십시오. 아래 예시는 일반적인 Nginx 액세스 로그 형식을 기준으로 합니다.

            ```sql
            CREATE TABLE logs.nginx_logs
            (
                `time_local` DateTime,
                `remote_addr` IPv4,
                `remote_user` LowCardinality(String),
                `request` String,
                `status` UInt16,
                `body_bytes_sent` UInt64,
                `http_referer` String,
                `http_user_agent` String,
                `http_x_forwarded_for` LowCardinality(String),
                `request_time` Float32,
                `upstream_response_time` Float32,
                `http_host` String
            )
            ENGINE = MergeTree
            ORDER BY (toStartOfMinute(time_local), status, remote_addr);
            ```

            테이블은 Vector가 생성하는 출력 스키마(schema)와 일치해야 합니다. [스키마 권장 사항](/ko/concepts/best-practices/select-data-type)을 참고하여 데이터에 맞게 스키마를 조정하십시오.

            ClickHouse에서 [기본 키(primary keys)](/ko/concepts/core-concepts/primary-indexes)가 작동하는 방식을 이해한 후, 액세스 패턴에 맞춰 정렬 키를 선택할 것을 강력히 권장합니다. 프라이머리 키 선택에 관해서는 [ClickStack 전용](/ko/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key) 가이드를 참조하십시오.

### 읽기 전용 컴퓨팅으로 ClickStack 사용하기 {#clickstack-read-only-compute}

ClickStack UI는 읽기 전용 ClickHouse Cloud 서비스만으로 실행할 수 있습니다. 수집 워크로드와 쿼리 워크로드를 분리하려는 경우 이 구성을 권장합니다.

#### ClickStack이 컴퓨트를 선택하는 방식 {#how-clickstack-selects-compute}

ClickStack UI는 항상 ClickHouse Cloud 콘솔에서 ClickStack을 실행한 ClickHouse 서비스에 연결됩니다.

즉, 다음과 같이 동작합니다.

* 읽기 전용 서비스에서 ClickStack을 열면 ClickStack UI에서 실행하는 모든 쿼리가 해당 읽기 전용 컴퓨팅에서 실행됩니다.
* 읽기/쓰기 서비스에서 ClickStack을 열면 ClickStack은 해당 서비스의 컴퓨트를 사용합니다.

읽기 전용 동작을 적용하기 위해 ClickStack에서 별도로 구성할 필요는 없습니다.

#### 권장 설정 {#recommended-setup}

읽기 전용 컴퓨팅에서 ClickStack을 실행하려면 다음 단계를 따르십시오.

1. 웨어하우스(warehouse)에서 읽기 전용으로 구성된 ClickHouse Cloud 서비스를 생성하거나 확인합니다.
2. ClickHouse Cloud 콘솔에서 읽기 전용 서비스를 선택합니다.
3. 왼쪽 탐색 메뉴에서 ClickStack을 실행합니다.

실행이 완료되면 ClickStack UI가 이 읽기 전용 서비스에 자동으로 바인드됩니다.

대시보드, 저장된 검색, 알림 및 소스는 ClickStack을 실행한 서비스 범위로 한정됩니다. 따라서 웨어하우스 내 다른 서비스에 저장된 항목은 여기에서 사용할 수 없으며 재생성해야 합니다. 표준 OpenTelemetry 스키마(schema)를 사용하는 소스는 자동으로 감지되므로 해당 데이터는 바로 검색할 수 있습니다. 반면 사용자 정의 소스나 수동으로 구성한 소스는 자동으로 감지되지 않으므로 다시 설정해야 합니다.

수집 데이터를 보낼 대상, DDL을 실행할 서비스, 알림 동작 방식 등 전체 토폴로지는 [&quot;읽기 및 쓰기 워크로드 분리&quot;](/ko/clickstack/self-configured/managing/isolating-read-write)를 참조하십시오.

### 데이터 소스 추가 {#adding-data-sources}

ClickStack은 OpenTelemetry를 네이티브로 지원하지만 OpenTelemetry 전용은 아닙니다. 필요한 경우 자체 테이블 스키마(table schema)를 사용할 수도 있습니다.

다음은 자동으로 구성된 데이터 소스 외에 데이터 소스를 추가하는 방법입니다.

#### OpenTelemetry 스키마(schemas) 사용 {#using-otel-schemas}

ClickStack은 표준 OpenTelemetry 스키마를 사용하는 테이블을 자동으로 감지하여 로그, 트레이스, 메트릭용 데이터 소스를 생성합니다. 별도의 확인 대화 상자나 수동 소스 생성 작업은 필요하지 않습니다.

자동으로 생성된 소스를 검토하거나 조정하려면 **팀 설정 → 데이터 → 소스**를 열고 해당 소스를 펼치십시오. 아래 예시는 `otel_logs` 테이블의 로그 소스를 보여줍니다.

## 스키마(schema) 선택: Map vs JSON {#schema-choice-map-vs-json}

ClickStack은 기본적으로 속성을 `Map(LowCardinality(String), String)` 컬럼에 저장합니다. 이는 관측성 워크로드(workloads)에 권장되는 스키마입니다. [버킷 분할 맵 직렬화(bucketed map serialization)](/ko/reference/data-types/map#bucketed-map-serialization) 및 맵의 키와 값(keys and values)에 대한 텍스트 인덱스와 함께 사용하면, 동적 JSON 하위 컬럼(JSON subcolumn)에서 발생하는 키별 수집 오버헤드 없이 선택적 조회가 가능합니다.

`JSON` 타입 기반 스키마는 속성 키 집합이 작고 안정적인 워크로드에서 평가할 수 있도록 베타로 제공됩니다. 기본 스키마로 사용하는 것은 **권장하지 않습니다**. 전체 비교 내용과 JSON 지원을 활성화하는 데 필요한 환경 변수는 [Map vs JSON 타입](/ko/clickstack/self-configured/ingesting-data/schema/map-vs-json)을 참조하십시오.
