운영 환경에 ClickStack Open Source를 배포할 때는 보안, 안정성, 구성과 관련된 다음 권장 사항을 고려하십시오.

## 네트워크 및 포트 보안 {#network-security}

기본적으로 Docker Compose는 호스트에 포트를 노출하여 컨테이너 외부에서 액세스할 수 있도록 합니다. 이는 `ufw`(Uncomplicated Firewall)와 같은 도구가 활성화(enabled)되어 있더라도 마찬가지입니다. 이러한 동작은 Docker 네트워킹 스택의 특성 때문으로, 명시적으로 구성하지 않으면 호스트 수준의 방화벽(firewall) 규칙을 우회할 수 있습니다.

**권장 사항:**

프로덕션 환경에 필요한 포트만 노출하십시오. 일반적으로 OTLP 엔드포인트, API 서버, 프론트엔드가 이에 해당합니다.

예시로, `docker-compose.yml` 파일에서 불필요한 포트 매핑을 제거하거나 주석 처리하세요:

```yaml
ports:
  - "4317:4317"  # OTLP gRPC
  - "4318:4318"  # OTLP HTTP
  - "8080:8080"  # Only if needed for the API
# Avoid exposing internal ports like ClickHouse 8123 or MongoDB 27017.
```

컨테이너 격리 및 액세스 보안 강화에 대한 자세한 내용은 [Docker 네트워킹 문서](https://docs.docker.com/network/)를 참조하십시오.

## 세션 시크릿 구성 {#session-secret}

운영 환경에서는 세션 데이터를 보호하고 변조를 방지하기 위해 ClickStack UI의 `EXPRESS_SESSION_SECRET` 환경 변수에 추측하기 어려운 강력한 임의 값을 반드시 설정해야 합니다.

app 서비스의 `docker-compose.yml` 파일에 다음과 같이 추가하십시오:

```yaml
  app:
    image: ${IMAGE_NAME_HDX}:${IMAGE_VERSION}
    ports:
      - ${HYPERDX_API_PORT}:${HYPERDX_API_PORT}
      - ${HYPERDX_APP_PORT}:${HYPERDX_APP_PORT}
    environment:
      FRONTEND_URL: ${HYPERDX_APP_URL}:${HYPERDX_APP_PORT}
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_API_PORT: ${HYPERDX_API_PORT}
      HYPERDX_APP_PORT: ${HYPERDX_APP_PORT}
      HYPERDX_APP_URL: ${HYPERDX_APP_URL}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      MINER_API_URL: 'http://miner:5123'
      MONGO_URI: 'mongodb://db:27017/hyperdx'
      NEXT_PUBLIC_SERVER_URL: http://127.0.0.1:${HYPERDX_API_PORT}
      OTEL_SERVICE_NAME: 'hdx-oss-api'
      USAGE_STATS_ENABLED: ${USAGE_STATS_ENABLED:-true}
      EXPRESS_SESSION_SECRET: "super-secure-random-string"
    networks:
      - internal
    depends_on:
      - ch-server
      - db1
```

`openssl`을 사용하면 강력한 시크릿을 생성할 수 있습니다.

```shell
openssl rand -hex 32
```

시크릿을 소스 관리 시스템(source control)에 커밋하지 마십시오. 운영 환경에서는 환경 변수 관리 도구(예: Docker Secrets, HashiCorp Vault 또는 환경별 CI/CD 구성)를 사용하는 것이 좋습니다.

## 보안 수집 {#secure-ingestion}

모든 수집은 ClickStack 배포판의 OpenTelemetry(OTel) collector가 노출하는 OTLP 포트를 통해 이루어져야 합니다. 기본적으로 이를 위해서는 시작 시 생성되는 보안 수집 API key가 필요합니다. 이 키는 OTel 포트로 데이터를 전송할 때 필요하며, ClickStack UI의 `Team Settings → API Keys`에서 확인할 수 있습니다.

### 수집용 사용자 생성 {#create-a-database-ingestion-user-oss}

ClickHouse 수집을 위해 OTel collector 전용 사용자를 생성하고, 수집 데이터가 특정 데이터베이스(예: `otel`)로 전송되도록 설정하는 것을 권장합니다. 자세한 내용은 [&quot;수집 사용자 생성&quot;](/ko/clickstack/ingesting-data/collector#creating-an-ingestion-user)을 참조하십시오.

## ClickHouse {#clickhouse}

ClickHouse 인스턴스를 직접 관리하는 사용자는 다음 권장 사항을 따라야 합니다.

### 보안 권장 사항 {#self-managed-security}

ClickHouse 인스턴스를 직접 관리하는 경우 **TLS**를 활성화하고, 인증을 적용하며, 액세스 보안 강화를 위한 권장 사항을 반드시 따라야 합니다. 실제 환경에서 발생한 잘못된 구성 사례와 이를 방지하는 방법은 [이 블로그 게시물](https://www.wiz.io/blog/clickhouse-and-wiz)을 참조하십시오.

ClickHouse OSS는 강력한 보안 기능을 기본으로 제공하지만, 이러한 기능을 사용하려면 별도로 구성해야 합니다.

* `config.xml`의 `tcp_port_secure` 및 `<openSSL>`을 통해 **TLS를 사용하십시오**. [guides/sre/configuring-tls](/ko/concepts/features/security/tls/configuring-tls)를 참조하십시오.
* `default` 사용자에 **강력한 비밀번호를 설정**하거나 해당 사용자를 비활성화하십시오.
* 명시적으로 의도한 경우가 아니라면 **ClickHouse를 외부에 노출하지 마십시오**. ClickHouse는 `listen_host`를 변경하지 않는 한 기본적으로 `localhost`에만 바인딩됩니다.
* 비밀번호, 인증서, SSH 키 또는 [외부 인증기](/ko/concepts/features/security/external-authenticators/index)와 같은 **인증 방식을 사용하십시오**.
* IP 필터링과 `HOST` 절을 사용하여 **액세스를 제한하십시오**. [sql-reference/statements/create/user#user-host](/ko/reference/statements/create/user#user-host)를 참조하십시오.
* 세분화된 권한을 부여하려면 **역할 기반 접근 제어(RBAC)를 활성화하십시오**. [operations/access-rights](/ko/concepts/features/security/access-rights)를 참조하십시오.
* [쿼터](/ko/concepts/features/configuration/server-config/quotas), [설정 프로필](/ko/concepts/features/configuration/settings/settings-profiles), 읽기 전용 모드(read-only mode)를 사용하여 **쿼터와 제한을 적용하십시오**.
* **저장 데이터를 암호화**하고 안전한 외부 스토리지를 사용하십시오. [operations/storing-data](/ko/concepts/features/configuration/server-config/storing-data) 및 [cloud/security/CMEK](/ko/products/cloud/guides/security/cmek)를 참조하십시오.
* **자격 증명을 하드코딩하지 마십시오.** [이름이 지정된 컬렉션](/ko/concepts/features/configuration/server-config/named-collections) 또는 ClickHouse Cloud의 IAM 역할을 사용하십시오.
* [시스템 로그](/ko/reference/system-tables/query_log)와 [세션 로그](/ko/reference/system-tables/session_log)를 사용하여 **액세스와 쿼리를 감사하십시오**.

사용자 관리와 쿼리/리소스 제한 적용에 관해서는 [외부 인증기](/ko/concepts/features/security/external-authenticators/index) 및 [쿼리 복잡성 설정](/ko/concepts/features/configuration/settings/query-complexity)도 참조하십시오.

### ClickStack UI의 사용자 권한(User Permissions) {#user-permissions}

ClickStack UI에서 사용하는 ClickHouse 사용자는 `readonly = 2`로 설정해야 합니다. UI는 모든 쿼리에 `date_time_output_format` 등의 자체 설정을 지정하며, 원시 SQL(Raw SQL) 차트도 `readonly = 2`를 설정합니다. 따라서 `readonly = 1` 사용자로 실행하면 이러한 쿼리는 `Cannot modify '...' setting in readonly mode` 오류와 함께 실패합니다. `readonly = 2`로 설정하면 UI에서 `max_rows_to_read`, `read_overflow_mode`, `cancel_http_readonly_queries_on_client_close`도 설정할 수 있습니다. `max_rows_to_read`를 제한하려면 최소 100만 이상으로 허용하십시오. `wait_end_of_query`는 설정이 아닌 HTTP 인터페이스 매개변수이므로 별도로 권한을 부여할 필요가 없습니다.

예시:

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

OSS와 ClickHouse Cloud 모두 `default` 사용자에게는 기본적으로 이러한 권한이 부여되어 있지만, 전용 사용자를 생성하여 사용하는 것을 권장합니다.

## Time To Live (TTL) 구성 {#configure-ttl}

ClickStack 배포 환경에 맞게 [TTL(Time To Live)](/ko/clickstack/managing/ttl)이 [적절히 구성](/ko/clickstack/managing/ttl#modifying-ttl)되어 있는지 확인하십시오. 이 설정은 데이터 보존 기간을 제어하며, 기본값인 30일은 조정이 필요할 수 있습니다.

## MongoDB 가이드라인 {#mongodb-guidelines}

MongoDB 공식 [보안 체크리스트](https://www.mongodb.com/docs/manual/administration/security-checklist/)를 따르십시오.
