<Info>
  **요약**

  이미 OpenTelemetry Collector를 실행 중이라면, 서비스의 시작하기 페이지에서 익스포터 스니펫을 복사하여 collector 구성에 붙여 넣고, 해당 익스포터를 파이프라인에 추가한 후 구성을 다시 로드하세요. 기존 수신기와 프로세서는 그대로 동작하며, 이들이 수집하는 모든 데이터가 ClickHouse Observability로 전송됩니다.

  소요 시간: 약 10분
</Info>

ClickHouse Observability 서비스 생성을 완료했습니다. 이 가이드는 데이터 수집을 담당하는 OpenTelemetry Collector를 환경에서 이미 실행 중인 경우를 위한 것입니다. 예를 들면 다음과 같습니다.

* **인프라 텔레메트리.** 호스트의 CPU, 메모리, 디스크, 네트워크 메트릭 및 디스크에 저장된 로그 파일
* **Kubernetes.** 컨테이너 로그, kubelet 및 클러스터 메트릭, Kubernetes 이벤트
* **기존 메트릭 엔드포인트.** 서비스에서 이미 노출 중인 Prometheus 엔드포인트 스크레이핑
* **[gateway](/ko/clickstack/ingesting-data/collector#collector-roles).** 네트워크 내부에서 SDK와 에이전트 collector로부터 OTLP 데이터를 수신하고 배치 처리한 후 한 곳에서 전달하는 단일 엔드포인트

collector가 어떤 데이터를 수집하든 연결 방법은 동일합니다. 서비스의 관리형 OTLP 엔드포인트를 대상으로 하는 `otlp_http` 익스포터 하나만 추가하면 됩니다. 수신기, 프로세서 및 기존 익스포터는 그대로 유지되므로, 평가 기간 동안 현재 백엔드와 ClickHouse Observability에 데이터를 동시에 전송할 수 있습니다. 이후의 수집, 스키마, 스토리지, 최적화, 확장은 모두 ClickHouse Observability가 처리합니다.

<Note>
  **아직 collector가 없습니까?**

  collector 없이도 시작할 수 있습니다. 애플리케이션에서 OpenTelemetry 데이터를 관리형 엔드포인트로 직접 내보낼 수 있습니다. 자세한 내용은 [OpenTelemetry로 애플리케이션 계측하기](/ko/clickstack/managed-onboarding/instrument-application-serverless)를 참조하세요. 인프라 텔레메트리 수집을 시작하려면 [로컬 로그 및 메트릭](/ko/clickstack/observability/example-datasets/local-data)과 [Kubernetes 모니터링](/ko/clickstack/observability/example-datasets/kubernetes)을 참조하세요. 두 문서 모두 그대로 배포할 수 있는 완전한 collector 구성을 제공합니다.
</Note>

## 사전 요구 사항 {#prerequisites}

* ClickHouse Observability 서비스가 필요합니다. 아직 서비스가 없다면 [시작 가이드](/ko/clickstack/observability/getting-started)를 참고하십시오.
* 구성을 변경하고 재시작할 수 있는 OpenTelemetry Collector가 필요합니다. `otlp_http` 익스포터는 코어 collector에 포함되어 있으므로 벤더 빌드를 포함한 모든 배포판을 사용할 수 있습니다.
* collector 호스트에서 서비스의 텔레메트리 엔드포인트로 포트 `4318`을 통한 아웃바운드 HTTPS 액세스가 허용되어야 합니다.

## collector 연결하기 {#connect-your-collector}

<Steps>
  <Step title="익스포터 구성 복사하기" id="copy-exporter-configuration">
    ClickHouse Observability 서비스를 엽니다. 데이터가 수신되기 전까지는 **Start sending telemetry** 페이지가 표시됩니다.

    <div className="ch-image-lg">
      <Frame>
        ![아직 데이터가 없는 현재 서비스와 Use an existing OpenTelemetry setup, Instrument with AI, Follow setup guides의 세 가지 옵션을 보여 주는 Start sending telemetry 페이지](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    **Use an existing OpenTelemetry setup** 아래에서 **View connection details**를 선택한 다음 **Collector config** 탭을 엽니다. 이 탭에는 해당 서비스에 맞게 미리 작성된 익스포터 블록이 표시됩니다. **Reveal key**를 선택하여 전체 API Key를 표시한 다음 복사 버튼을 클릭하십시오.

    <div className="ch-image-md">
      <Frame>
        ![Collector config 탭이 선택된 Set up OpenTelemetry 대화 상자로, 마스킹된 엔드포인트와 Bearer authorization 헤더가 포함된 otlphttp 익스포터를 보여 줌](/images/clickstack/getting-started/observability-collector-config.png)
      </Frame>
    </div>

    스니펫은 다음과 같은 형태입니다.

    ```yaml
    exporters:
      otlphttp:
        endpoint: https://YOUR_OTEL_ENDPOINT:4318
        headers:
          authorization: Bearer <your-api-key>
    ```

    여기서 두 가지 사항에 유의해야 합니다. 첫째, 엔드포인트는 기본 URL입니다. 익스포터가 신호 경로를 자동으로 추가하므로 `/v1/logs`, `/v1/traces`, `/v1/metrics`를 덧붙이지 마십시오. 둘째, 헤더 값에는 `Bearer` 접두사가 포함됩니다.

    UI에서는 익스포터 이름이 `otlphttp`로 표시됩니다. 최신 collector 릴리스에서는 이 익스포터의 이름이 `otlp_http`이며 `otlphttp`는 더 이상 사용되지 않는(deprecated) 별칭으로 남아 있으므로 두 이름 모두 사용할 수 있습니다. 아래 예시에서는 현재 이름을 사용합니다.

    동일한 값은 언제든지 **팀 설정 → Managed Telemetry**에서 확인할 수 있습니다.
  </Step>

  <Step title="익스포터 추가하기" id="add-the-exporter">
    collector 구성의 `exporters` 섹션에 이 블록을 추가합니다. 키를 환경 변수로 제공하면 구성 파일에 키를 직접 기록하지 않아도 됩니다.

    ```yaml
    exporters:
      otlp_http:
        endpoint: ${env:CLICKSTACK_OTLP_ENDPOINT}
        headers:
          authorization: "Bearer ${env:CLICKSTACK_API_KEY}"
    ```

    구성에 이미 `otlp_http`라는 이름의 익스포터가 있다면 `otlp_http/clickhouse`처럼 다른 이름을 지정하고, 다음 단계에서 그 이름을 사용하십시오.

    collector가 Kubernetes에서 실행된다면 키를 시크릿(Secret)에 저장하고 `extraEnvs` 또는 pod spec을 통해 두 값을 모두 주입하십시오. 이 패턴을 OpenTelemetry Helm 차트로 구성하는 방법은 [Kubernetes 모니터링](/ko/clickstack/observability/example-datasets/kubernetes) 가이드를 참조하십시오.
  </Step>

  <Step title="파이프라인에 추가하기" id="add-to-pipelines">
    ClickHouse Observability로 데이터를 보내려는 모든 파이프라인에 익스포터를 추가합니다. 기존 익스포터를 그대로 두면 두 대상으로 동시에 데이터를 전송할 수 있습니다.

    ```yaml
    service:
      pipelines:
        logs:
          receivers: [otlp, file_log]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        metrics:
          receivers: [otlp, host_metrics, prometheus]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
    ```

    수신기와 프로세서는 변경할 필요가 없으며, 익스포터 목록만 수정하면 됩니다.

    <Info>
      **에이전트 및 gateway 역할**

      각 호스트에서 에이전트 collector를 실행하여 중앙 gateway로 데이터를 전달하는 구조라면 gateway만 변경하십시오. 에이전트는 이전과 마찬가지로 gateway로 데이터를 계속 전송합니다.
    </Info>
  </Step>

  <Step title="다시 로드하고 로그 확인하기" id="reload-and-check">
    collector가 구성을 전달받는 방식(systemd 유닛, Docker `-e` 플래그 또는 Kubernetes 시크릿)에 맞게 collector 환경에서 `CLICKSTACK_OTLP_ENDPOINT`를 엔드포인트 URL로, `CLICKSTACK_API_KEY`를 키로 설정합니다. 그런 다음 collector를 재시작하거나 다시 로드하고, 로그에 내보내기 오류가 있는지 확인하십시오.

    * `401` 또는 `403` 응답은 API Key가 잘못되었거나 `Bearer` 접두사가 누락되었음을 의미합니다.
    * `404` 응답은 대개 `/v1/logs`와 같은 신호 경로가 엔드포인트에 덧붙여졌음을 의미합니다.
    * `no such host` 또는 TLS 오류는 엔드포인트에 오타가 있거나 포트 `4318`의 아웃바운드 연결이 차단되었음을 나타냅니다.

    이제 collector가 기존에 수집하던 모든 데이터가 서비스로도 전송됩니다.
  </Step>
</Steps>

## 데이터 수신 확인 {#confirm-data-is-arriving}

## 아무것도 표시되지 않는 경우 {#if-nothing-shows-up}

* 먼저 collector 로그를 확인하십시오. 인증, 엔드포인트, TLS 관련 문제는 모두 위에 나열된 오류 코드와 함께 이 로그에 기록됩니다.
* 데이터를 받아야 하는 모든 파이프라인의 `exporters`에 `otlp_http`가 포함되어 있는지 확인하십시오. 수신기를 정의했더라도 파이프라인에서 참조하지 않으면 아무것도 수집되지 않습니다.
* collector가 실제로 다시 로드되었는지 확인하십시오. 일부 배포판에서는 새 익스포터를 적용하려면 구성을 다시 로드하는 것만으로는 부족하며 재시작해야 합니다.
* **검색**에서 시간 범위를 넓히고 필터를 모두 제거하십시오. 기본 소스가 **Logs**가 아닌 **Traces**로 설정되어 있을 수 있습니다.
* 서비스 자체의 문제가 아닌지 확인하려면 **팀 설정 → Managed Telemetry**로 이동하여 **Send a Test Log**를 사용하십시오. 이 로그가 **검색**에 표시되면 서비스는 데이터를 정상적으로 수신하고 있으며, 문제는 collector와 엔드포인트 사이에 있습니다.
* collector 단독으로 문제를 확인하려면 [샘플 데이터 전송](#send-sample-data)의 `telemetrygen` generator가 서비스 대신 collector 자체의 OTLP 수신기로 데이터를 보내도록 지정하십시오. 이때 엔드포인트는 스킴(scheme) 없이 `host:port` 형식으로 지정합니다(예: `--otlp-http` 없이 `--otlp-endpoint localhost:4317 --otlp-insecure`). 이 데이터가 도착하면 collector의 익스포터에는 문제가 없으며, 문제는 그 이전 단계(업스트림)에 있습니다.

## collector로 더 많은 데이터 수집하기 {#collect-more}

익스포터를 구성하고 나면 새로 추가하는 모든 수신기의 데이터가 동일한 파이프라인을 거쳐 서비스로 전달됩니다.

* [로컬 로그 및 메트릭](/ko/clickstack/observability/example-datasets/local-data): `file_log` 수신기로 로그 파일을 tail하고 `host_metrics` 수신기로 CPU, 메모리, 디스크, 네트워크 메트릭을 수집하는 전체 구성입니다.
* [Kubernetes 모니터링](/ko/clickstack/observability/example-datasets/kubernetes): 컨테이너 로그와 kubelet 메트릭을 수집하는 데몬셋(DaemonSet)과 클러스터 메트릭 및 이벤트를 수집하는 배포(Deployment)를 OpenTelemetry Helm 차트로 설치합니다.
* **Prometheus 엔드포인트.** 기존 `scrape_configs`를 지정한 [`prometheus` 수신기](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/prometheusreceiver)를 `metrics` 파이프라인에 추가하십시오. 스크레이프된 시계열은 OpenTelemetry 메트릭으로 수집되어 차트 탐색기에 표시됩니다.
* **gateway를 통한 SDK 연결.** `OTEL_EXPORTER_OTLP_ENDPOINT`를 collector 주소(예: `http://otel-collector.observability.svc:4318`)로 설정하여 애플리케이션이 collector로 데이터를 보내도록 하십시오. 데모 앱을 계측하는 과정은 [OpenTelemetry로 애플리케이션 계측하기](/ko/clickstack/managed-onboarding/instrument-application-serverless)에서 안내합니다. 이때 관리형 엔드포인트를 collector 주소로 바꾸고, API Key는 이제 gateway가 제공하므로 제거하십시오.
* **gateway에서의 처리.** [`filter`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/filterprocessor), [`transform`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/transformprocessor), [`resourcedetection`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/resourcedetectionprocessor) 프로세서를 사용하면 텔레메트리가 네트워크를 벗어나기 전에 불필요한 데이터를 삭제하고, 속성을 재구성하고, 클라우드 및 호스트 메타데이터로 태그를 지정할 수 있습니다.

collector 자체의 배포 패턴, 확장 방법, 전체 구성 참고 자료는 [OpenTelemetry Collector 문서](https://opentelemetry.io/docs/collector/)를 참조하십시오.

## 아직 실시간 텔레메트리가 없습니까? 샘플 데이터 전송하기 {#send-sample-data}

collector는 연결되어 있지만 소스에서 들어오는 데이터가 없거나, UI를 탐색하는 데 더 풍부한 데이터가 필요하다면 합성 로그, trace, 메트릭을 한 번에 서비스로 직접 전송하십시오. 이 방법은 collector를 거치지 않고 **Env vars** 탭의 연결 정보를 그대로 사용하므로 값을 다시 입력할 필요가 없습니다.

**Start sending telemetry** 페이지에서 **View connection details**를 열거나 **팀 설정 → Managed Telemetry**로 이동한 다음 **Env vars** 탭을 선택하십시오. **Reveal key**를 선택하고 탭 내용을 복사한 다음, 모든 줄이 export되도록 셸에서 `set -a`와 `set +a` 사이에 붙여넣으십시오.

```shell
set -a
# Paste the Env vars tab here. It looks like this:
OTEL_EXPORTER_OTLP_ENDPOINT=https://YOUR_OTEL_ENDPOINT:4318
OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer <your-api-key>"
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
set +a
```

OpenTelemetry Collector Contrib의 데이터 generator인 [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen)을 Docker 이미지로 실행하세요:

```shell
telemetrygen() {
  docker run --rm \
    ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
}
```

또는 Go를 사용하여 바이너리를 설치하십시오:

```shell
go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
```

간단한 `tg` 헬퍼 함수를 정의합니다. `telemetrygen`의 엔드포인트 플래그는 URL 스킴을 허용하지 않으므로, 이 함수는 `OTEL_EXPORTER_OTLP_ENDPOINT`에서 호스트와 포트를, `OTEL_EXPORTER_OTLP_HEADERS`에서 키를 가져옵니다. OTLP 데이터는 인증서 검증을 수행하는 HTTPS로 전송되며, 한 번 실행할 때마다 20초 동안 동작합니다.

```shell
tg() { local signal=$1; shift; telemetrygen "$signal" \
  --otlp-endpoint "${OTEL_EXPORTER_OTLP_ENDPOINT#*://}" --otlp-http \
  --otlp-header "authorization=\"${OTEL_EXPORTER_OTLP_HEADERS#authorization=}\"" \
  --rate 5 --duration 20s "$@"; }
```

`telemetrygen`을 직접 호출하지 말고 항상 `tg`를 사용하십시오. `telemetrygen`에 전체 `https://` URL을 전달하면 `too many colons in address` 오류가 발생하며 실패합니다.

3개의 서비스에서 실제 환경처럼 다양한 심각도가 섞인 로그를 전송합니다.

```shell
tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="POST"'
tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.status_code="500"'
```

각 명령은 실행이 끝나면 `logs generated` 요약을 출력합니다. 키가 잘못된 경우 오류 메시지에 `401`이 표시되면서 즉시 실패합니다.

trace, 서비스 맵, 메트릭 데이터도 채우려면 아래 명령어를 펼쳐 동일한 셸에서 실행하십시오.

<Accordion title="더 풍부한 텔레메트리 생성(선택 사항)">
  여러 정상 서비스와 함께, 느리고 실패하는 의존성 하나에서 다중 스팬 trace를 전송합니다.

  ```shell
  for svc in frontend checkout cart; do
    tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
      --otlp-attributes 'deployment.environment="production"' \
      --telemetry-attributes "http.route=\"/$svc\""
  done

  tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
    --otlp-attributes 'deployment.environment="production"' \
    --telemetry-attributes 'http.route="/charge"'
  ```

  카운터, 게이지, 히스토그램을 전송합니다.

  ```shell
  tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
  tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
  tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
  ```
</Accordion>

서비스로 돌아가 **Check for data**를 선택한 다음 **Start exploring**을 선택하십시오. **검색**에서 `ServiceName`을 `frontend`, `checkout` 또는 `payment`로, `SeverityText`를 `Error`로 필터링하면 결제 게이트웨이 타임아웃을 찾을 수 있습니다. 더 풍부한 데이터 세트를 생성했다면 **trace** 소스에서 `payment` 트레이스를 열어 자식 스팬과 오류 상태를 확인하고, **차트 탐색기**에서 `http.server.requests`를 차트로 표시하여 메트릭이 정상적으로 수집되는지 확인하십시오.
