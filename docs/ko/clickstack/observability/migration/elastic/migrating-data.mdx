이 가이드는 기본 환경인 **완전 관리형 ClickHouse Observability**로 Elastic에서 마이그레이션하는 방법을 중점적으로 다룹니다. 기반이 되는 스키마(schemas)와 스토리지는 ClickHouse가 관리합니다. 수집 파이프라인은 텔레메트리를 **OpenTelemetry Protocol(OTLP)** 포맷으로 전송해야 하며, Elasticsearch 문서(document)는 완전 관리형 서비스로 직접 가져올 수 없습니다.

자가 관리형 배포 환경에서는 [Elasticsearch와 ClickHouse의 대응 개념](/ko/clickstack/self-configured/migration/elastic/concepts)과 [타입 매핑(type mapping)](/ko/clickstack/self-configured/migration/elastic/types)을 참고하십시오. 자가 관리형 환경의 데이터 마이그레이션 지침은 아래에 별도로 표시되어 있습니다.

## 병행 운영 전략 {#parallel-operation-strategy-self-configured}

관측성 활용 사례를 위해 Elastic에서 ClickHouse Observability로 마이그레이션할 때는 과거 데이터를 마이그레이션하기보다 **병행 운영** 방식을 권장합니다. 이 전략에는 다음과 같은 이점이 있습니다.

1. **위험 최소화**: 두 시스템을 동시에 운영하므로 ClickHouse Observability를 검증하고 사용자가 새 시스템에 익숙해지는 동안에도 기존 데이터와 대시보드에 계속 액세스할 수 있습니다.
2. **자연스러운 데이터 만료**: 대부분의 관측성 데이터는 보존 기간이 제한되어 있으므로(일반적으로 30일 이하), Elastic의 데이터가 만료되면서 자연스럽게 전환됩니다.
3. **마이그레이션 단순화**: 시스템 간에 과거 데이터를 옮기기 위한 복잡한 데이터 전송 도구나 프로세스가 필요하지 않습니다.

<br />

<Info>
  **데이터 마이그레이션**

  자가 관리형 배포에서는 `Elasticsearch` 테이블 엔진을 사용하여 과거 문서를 읽고 ClickHouse 테이블로 복사할 수 있습니다. 자세한 내용은 [데이터 마이그레이션](#migrating-data-self-configured)을 참조하십시오. 이 방식은 완전 관리형 ClickHouse Observability에서 사용하는 OTLP 수집 경로와는 별개입니다.
</Info>

### 구현 단계 {#implementation-steps-self-configured}

<Steps>
  <Step title="이중 수집 구성" id="configure-dual-ingestion-self-configured">
    데이터 수집 파이프라인이 Elastic과 ClickHouse Observability 양쪽에 데이터를 동시에 전송하도록 구성하십시오. 완전 관리형 ClickHouse Observability를 사용하는 경우, 파이프라인은 수집 API Key를 사용하여 관리형 엔드포인트로 OTLP 데이터를 내보내야 합니다. Elasticsearch JSON 문서를 해당 엔드포인트로 전달하는 것만으로는 충분하지 않습니다.

    구현 방법은 현재 수집에 사용 중인 에이전트에 따라 다릅니다. [&quot;에이전트 마이그레이션&quot;](/ko/clickstack/observability/migration/elastic/migrating-agents)을 참조하십시오.
  </Step>

  <Step title="보존 기간 조정" id="adjust-retention-period-self-configured">
    전환 기간 동안 과거 데이터를 계속 사용할 수 있도록 두 시스템의 보존 기간을 검토하십시오. 배포 유형별 지침은 [보존 기간 및 TTL](#retention-and-ttl-self-configured)을 참조하십시오.
  </Step>

  <Step title="검증 및 비교" id="validate-and-compare-self-configured">
    * 두 시스템에 쿼리를 실행하여 데이터 일관성(Consistency)을 확인합니다
    * 쿼리 성능(query performance)과 결과를 비교합니다
    * 대시보드와 알림을 ClickHouse Observability로 마이그레이션합니다. 현재 이 작업은 수동으로 수행해야 합니다.
    * 모든 주요 대시보드와 알림이 ClickHouse Observability에서 예상대로 작동하는지 확인합니다
  </Step>

  <Step title="점진적 전환" id="graudal-transition-self-configured">
    * Elastic의 데이터가 보존 기간에 따라 만료되면서 ClickHouse Observability에 대한 의존도가 점차 높아집니다
    * ClickHouse Observability에 대한 신뢰가 충분히 확보되면 쿼리와 대시보드를 ClickHouse Observability로 전환하기 시작할 수 있습니다
  </Step>
</Steps>

### 장기 보존 {#long-term-retention-self-configured}

더 긴 보존 기간이 필요한 조직은 다음 방법을 고려하십시오.

* Elastic의 모든 데이터가 만료될 때까지 두 시스템을 병렬로 계속 운영하십시오.
* 자가 관리형 배포에서는 [materialized view](/ko/concepts/features/materialized-views/incremental-materialized-view)를 사용하여 집계되거나 필터링된 과거 데이터는 유지하고 원시 데이터는 만료되도록 구성하는 방안을 고려하십시오.

### 마이그레이션 일정 {#migration-timeline-self-configured}

마이그레이션(migration) 일정은 데이터 보존 기간 요구 사항에 따라 달라집니다.

* **30일 보존 기간**: 한 달 이내에 마이그레이션을 완료할 수 있습니다.
* **더 긴 보존 기간**: Elastic의 데이터가 만료될 때까지 병행 운영을 유지하십시오.
* **과거 데이터**: 데이터 가져오기를 계획하기 전에 [데이터 마이그레이션](#migrating-data-self-configured)에서 배포 방식별 안내를 확인하십시오.

## 보존 기간 및 TTL {#retention-and-ttl-self-configured}

<Tabs>
  <Tab title="완전 관리형">
    <BetaBadge label="베타 제공" />

    <Note>
      완전 관리형 ClickHouse Observability는 베타 기간 동안 데이터를 30일간 보존합니다. 보존 기간은 정식 출시(GA) 시점에 변경될 예정이며, 자세한 지침은 추후 안내됩니다.
    </Note>

    30일 보존 기간과 Elastic의 보존 기간을 함께 고려하여 전환 계획을 수립하십시오. 과거 데이터 검색이 더 이상 필요하지 않을 때까지 Elastic을 계속 운영하십시오.
  </Tab>

  <Tab title="자가 관리형">
    ClickHouse는 `MergeTree` 테이블의 [TTL 절(TTL clause)](/ko/clickstack/self-configured/managing/production#configure-ttl-managed)을 사용하여 만료된 데이터를 자동으로 삭제합니다.

    테이블 보존 기간을 마이그레이션(migration) 요구 사항에 맞게 조정하십시오. 예시는 [자가 관리형 운영 환경 TTL 설정](/ko/clickstack/self-configured/managing/production#configure-ttl-managed)을 참조하십시오.
  </Tab>
</Tabs>

## 데이터 마이그레이션 {#migrating-data-self-configured}

<Tabs>
  <Tab title="완전 관리형">
    <BetaBadge label="베타 제공" />

    <Note>
      현재 Elasticsearch에서 완전 관리형 ClickHouse Observability로 과거 데이터를 직접 마이그레이션하는 방법은 없습니다. 관리형 엔드포인트는 Elasticsearch 문서나 JSON 내보내기 파일이 아닌 OTLP 텔레메트리만 수신합니다. 자가 관리형 탭에서 설명하는 `Elasticsearch` 테이블 엔진 워크플로는 완전 관리형 서비스에는 적용되지 않습니다.
    </Note>

    병렬 수집 방식을 사용하여 새 텔레메트리는 **OTLP 포맷**으로 관리형 서비스에 전송하고, 과거 데이터는 Elastic에 그대로 보관하십시오. 관리형 엔드포인트 및 인증 설정은 [OpenTelemetry로 데이터 수집하기](/ko/clickstack/observability/ingesting-data/opentelemetry)를, 수집 옵션은 [에이전트 마이그레이션](/ko/clickstack/observability/migration/elastic/migrating-agents)을 참조하십시오.

    과거 데이터를 반드시 가져와야 한다면 Elasticsearch 문서를 적절한 OpenTelemetry 로그, trace 또는 메트릭으로 변환한 뒤 OTLP로 내보내는 사용자 정의 파이프라인이 필요합니다. 이 가이드에서는 바로 사용할 수 있는 컨버터를 제공하지 않습니다. 백필을 계획하기 전에 관리형 서비스의 보존 기간을 고려하십시오.
  </Tab>

  <Tab title="자가 관리형">
    [`Elasticsearch` 테이블 엔진](/ko/reference/engines/table-engines/integrations/elasticsearch)을 사용하면 Elasticsearch에서 문서를 직접 읽은 다음 `INSERT INTO ... SELECT`로 로컬 ClickHouse 테이블에 복사할 수 있습니다. 내보내기 파일이나 `elasticdump`를 설치할 필요가 없습니다.

    이 엔진은 읽기 전용입니다. `Elasticsearch` 테이블을 생성하면 원격 문서를 쿼리할 수 있지만, 문서가 ClickHouse 스토리지로 복사되지는 않습니다.

    <Note>
      Elasticsearch 통합은 실험적 기능이며, 이를 지원하는 ClickHouse 버전에서 `enable_elasticsearch = 1`을 설정해야 합니다. Elasticsearch 7.12 이상이 필요하며 OpenSearch는 지원하지 않습니다. ClickHouse 서비스가 Elasticsearch 엔드포인트에 접근할 수 있어야 하며, 문서 내용을 읽으려면 인덱스에 `_source`가 활성화되어 있어야 합니다.
    </Note>

    <Steps>
      <Step title="Elasticsearch 인덱스에 연결" id="connect-elasticsearch-self-managed">
        자가 관리형 ClickHouse Cloud 서비스에서 다음 SQL을 실행하십시오. 엔드포인트, 인덱스, 자격 증명은 실제 값으로 바꾸십시오.

        ```sql
        SET enable_elasticsearch = 1;

        CREATE TABLE elasticsearch_source
        ENGINE = Elasticsearch(
            'https://<elasticsearch-host>:9200',
            '<index-name>',
            '<username>',
            '<password>'
        );

        SELECT _index, _id, document
        FROM elasticsearch_source
        LIMIT 10;
        ```

        이 테이블은 각 문서의 `_source`를 `JSON` 타입의 `document` 컬럼으로 노출합니다. 가상 컬럼 `_id`와 `_index`는 원본 문서와 인덱스를 식별합니다. 대상 스키마(schema)를 정하기 전에 샘플 데이터를 확인하십시오.

        이 엔진은 API 키와 명명된 컬렉션(named collection)도 지원합니다. 자세한 내용은 [인증 참고 문서](/ko/reference/functions/table-functions/elasticsearch#authentication)를 참조하십시오.
      </Step>

      <Step title="ClickHouse로 문서 복사" id="copy-documents-self-managed">
        이 예시에서는 관측성 소스를 구성하기 전에 문서를 검토하고 변환할 수 있도록 문서를 스테이징 테이블에 `JSON`으로 저장합니다. `elasticsearch_source`와 동일한 데이터베이스에서 다음 구문을 실행하십시오.

        ```sql
        CREATE TABLE migrated_elasticsearch_documents
        (
            source_index String,
            document_id String,
            document JSON
        )
        ENGINE = MergeTree
        ORDER BY (source_index, document_id);

        INSERT INTO migrated_elasticsearch_documents
        SELECT _index, _id, document
        FROM elasticsearch_source;
        ```

        각 읽기 작업은 Elasticsearch의 point in time을 사용하여 해당 쿼리에 일관된 스냅샷을 제공합니다. 이는 일회성 복사이며 지속적인 복제가 아닙니다. 삽입을 반복하면 행이 다시 추가되며, 정렬 키로 문서 중복이 제거되지 않습니다.

        대용량 데이터를 가져올 때는 엔진의 `query` 인수를 사용하여 작업을 서로 겹치지 않는 배치로 나누십시오. 이때 Elasticsearch Query DSL에서 절대 타임스탬프 경계를 사용하십시오. ClickHouse의 `WHERE` 절은 필터를 Elasticsearch로 푸시다운하지 않습니다. 자세한 내용은 [엔진 예시](/ko/reference/engines/table-engines/integrations/elasticsearch#usage-example)와 [제한 사항](/ko/reference/functions/table-functions/elasticsearch#limitations)을 참조하십시오.
      </Step>

      <Step title="가져온 데이터 매핑 및 검사" id="validate-import-self-managed">
        문서 수와 대표 레코드를 원본 스냅샷과 비교하십시오. 데이터를 검색이나 대시보드에 사용하기 전에 타임스탬프, 누락된 필드, 중첩된 값을 확인하십시오. `JSON` 타입은 타임스탬프를 포함한 값에서 타입을 추론할 수 있으므로 텍스트 표현이 달라질 수 있습니다. 필드 타입을 직접 제어하려면 명시적인 JSON 타입 힌트를 사용하십시오.

        쿼리 패턴과 보존 요구 사항에 맞게 대상 관측성 스키마(schema)를 설계한 다음, `INSERT INTO ... SELECT`를 사용하여 스테이징 테이블에서 필드를 추출하고 변환하십시오. [Elasticsearch와 ClickHouse 개념](/ko/clickstack/self-configured/migration/elastic/concepts), [타입 매핑](/ko/clickstack/self-configured/migration/elastic/types), [스키마 설계 가이드](/ko/guides/clickhouse/data-formats/json/schema)도 함께 참고하십시오.

        문서를 복사해도 OpenTelemetry 스키마로 자동 변환되거나 UI에 소스가 자동으로 구성되지는 않습니다. [구성 옵션](/ko/clickstack/self-configured/managing/config)을 참고하여 테이블과 타임스탬프, 메시지 및 기타 필드 매핑을 구성하십시오.
      </Step>
    </Steps>
  </Tab>
</Tabs>
