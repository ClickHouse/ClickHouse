## Elastic에서 에이전트 마이그레이션(migration) {#migrating-agents-from-elastic-self-configured}

Elastic Stack은 관측성(Observability) 데이터를 수집하는 여러 에이전트를 제공합니다. 구체적으로는 다음과 같습니다.

* [Beats 계열](https://www.elastic.co/beats) - [Filebeat](https://www.elastic.co/beats/filebeat), [Metricbeat](https://www.elastic.co/beats/metricbeat), [Packetbeat](https://www.elastic.co/beats/packetbeat) 등 - 은 모두 `libbeat` 라이브러리를 기반으로 합니다. 이러한 Beats는 Lumberjack 프로토콜을 통해 [Elasticsearch, Kafka, Redis 또는 Logstash로 데이터를 전송](https://www.elastic.co/docs/reference/beats/filebeat/configuring-output)할 수 있습니다.
* [`Elastic Agent`](https://www.elastic.co/elastic-agent)는 로그, 메트릭, 트레이스를 모두 수집할 수 있는 통합 에이전트입니다. 이 에이전트는 [Elastic Fleet Server](https://www.elastic.co/docs/reference/fleet/manage-elastic-agents-in-fleet)를 통해 중앙에서 관리할 수 있으며, Elasticsearch, Logstash, Kafka 또는 Redis로 데이터를 출력할 수 있습니다.
* Elastic은 [OpenTelemetry Collector - EDOT](https://www.elastic.co/docs/reference/opentelemetry) 배포판도 제공합니다. 현재는 Fleet Server로 오케스트레이션할 수 없지만, ClickHouse Observability로 마이그레이션(migration)할 때 더 유연하고 개방적인 경로를 제공합니다.

최적의 마이그레이션(migration) 경로는 현재 사용 중인 에이전트에 따라 달라집니다. 이어지는 섹션에서는 주요 에이전트 유형별 마이그레이션(migration) 옵션을 설명합니다. 전환 과정의 부담을 최소화하고, 가능하면 전환 기간에도 기존 에이전트를 계속 사용할 수 있도록 하는 것이 목표입니다.

## 권장 마이그레이션(migration) 경로 {#prefered-migration-path-self-configured}

가능하면 모든 로그, 메트릭, 트레이스 수집을 [OpenTelemetry (OTel) Collector](https://opentelemetry.io/docs/collector/)로 마이그레이션(migration)하고, collector를 [엣지에 에이전트 역할로](/ko/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured) 배포할 것을 권장합니다. 이 방식은 데이터를 전송하는 가장 효율적인 방법이며, 아키텍처의 복잡성과 데이터 변환을 피할 수 있습니다.

<Info>
  **OpenTelemetry Collector를 사용하는 이유**

  OpenTelemetry Collector는 관측성 데이터 수집을 위한 지속 가능하고 벤더 중립적인 솔루션을 제공합니다. 일부 조직은 수천, 많게는 수만 개에 이르는 Elastic 에이전트 플릿을 운영하고 있습니다. 이러한 사용자에게는 기존 에이전트 인프라와의 호환성 유지가 매우 중요할 수 있습니다. 이 문서는 이러한 환경을 지원하는 동시에, 팀이 OpenTelemetry 기반 수집으로 점진적으로 전환할 수 있도록 돕기 위해 작성되었습니다.
</Info>

## ClickHouse OpenTelemetry 엔드포인트 {#clickhouse-otel-endpoint-self-configured}

에이전트 마이그레이션(migration) 단계를 진행하기 전에 먼저 대상을 구성하십시오. 아래의 Vector 및 EDOT 예시는 OTLP HTTP로 OpenTelemetry 데이터를 전송합니다.

<Tabs>
  <Tab title="완전 관리형">
    <BetaBadge label="베타 서비스" />

    **팀 설정 → 데이터 → Managed Telemetry**에서 OTLP HTTP 엔드포인트와 API Key를 복사하십시오. 그런 다음 Vector 또는 EDOT가 실행되는 환경에 다음 변수를 설정하십시오.

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    엔드포인트는 포트를 포함하여 표시된 그대로 사용하되, `/v1/logs` 접미사는 붙이지 마십시오. 연결 정보는 [OpenTelemetry 데이터 전송](/ko/clickstack/observability/ingesting-data/opentelemetry)을 참조하십시오.
  </Tab>

  <Tab title="자가 관리형">
    [자가 관리형 설정 가이드](/ko/clickstack/self-configured/getting-started/managed)에 따라 수신용 collector를 배포하십시오. 그런 다음 Vector 또는 EDOT가 실행되는 환경에 연결 가능한 OTLP HTTP 엔드포인트와 인증 헤더를 설정하십시오.

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_COLLECTOR_TOKEN'
    ```

    수신용 collector를 `OTLP_AUTH_TOKEN`으로 보호했다면 해당 토큰을 authorization 값으로 사용하십시오. 인증을 비활성화했다면 예시에서 `authorization` 헤더를 생략하십시오. 자세한 내용은 [collector 보안 설정](/ko/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured)을 참조하십시오.

    `localhost`는 송신 측과 수신 측이 동일한 네트워크 네임스페이스를 공유할 때만 사용하십시오. 수신 측에서 TLS를 사용하는 경우 HTTPS 엔드포인트를 사용하고 해당 인증서를 신뢰하도록 구성하십시오.
  </Tab>
</Tabs>

## Beats에서 마이그레이션 {#migrating-to-beats-self-configured}

Beat를 대규모로 배포해 운영 중인 사용자는 ClickHouse Observability로 마이그레이션할 때 기존 Beat 배포를 그대로 유지하고자 할 수 있습니다.

**현재 이 옵션은 Filebeat에서만 테스트되었으므로 로그에만 적합합니다.**

Beats 에이전트는 [Elastic Common Schema (ECS)](https://www.elastic.co/docs/reference/ecs)를 사용하며, 이 스키마는 현재 ClickHouse Observability에서 사용하는 OpenTelemetry 명세에 [병합되는 중입니다](https://github.com/open-telemetry/opentelemetry-specification/blob/main/oteps/0199-support-elastic-common-schema-in-opentelemetry.md). 그러나 두 [스키마(schemas)는 여전히 상당한 차이가 있으며](https://www.elastic.co/docs/reference/ecs/ecs-otel-alignment-overview), 현재로서는 ClickHouse Observability로 수집하기 전에 ECS 포맷의 이벤트를 OpenTelemetry 포맷으로 변환하는 작업을 사용자가 직접 수행해야 합니다.

이 변환에는 [Vector](https://vector.dev)를 사용할 것을 권장합니다. Vector는 경량의 고성능 관측성 데이터 파이프라인으로, Vector Remap Language(VRL)라는 강력한 변환 언어를 지원합니다.

Filebeat 에이전트가 Beats에서 지원하는 출력인 Kafka로 데이터를 전송하도록 구성되어 있다면, Vector가 Kafka에서 해당 이벤트를 소비하고 VRL로 스키마 변환을 적용한 다음 OTLP를 통해 구성된 OTLP 엔드포인트로 전달할 수 있습니다.

또는 Vector는 Logstash에서 사용하는 Lumberjack 프로토콜을 통한 이벤트 수신도 지원합니다. 이 경우 Beats 에이전트가 데이터를 Vector로 직접 전송하고, Vector에서 동일한 변환 과정을 적용한 뒤 OTLP를 통해 구성된 OTLP 엔드포인트로 전달합니다.

두 아키텍처는 아래 그림과 같습니다.

다음 예시에서는 Lumberjack 프로토콜을 통해 Filebeat로부터 로그 이벤트를 수신하도록 Vector를 구성하는 초기 단계를 설명합니다. 또한 인바운드 ECS 이벤트를 OTel 명세로 매핑한 후 OTLP를 통해 구성된 OTLP 엔드포인트로 전송하는 VRL을 제공합니다. Kafka에서 이벤트를 소비하는 경우 Vector Logstash 소스를 [Kafka 소스](https://vector.dev/docs/reference/configuration/sources/kafka/)로 대체하면 되며, 나머지 단계는 모두 동일합니다.

<Steps>
  <Step title="vector 설치" id="install-vector-self-configured">
    [공식 설치 가이드](https://vector.dev/docs/setup/installation/)에 따라 Vector를 설치하십시오.

    Filebeat 에이전트에서 연결할 수 있는 호스트에 Vector를 설치하십시오.

    [Vector를 운영 환경에 배포](https://vector.dev/docs/setup/going-to-prod/)할 때는 아키텍처 및 보안 관련 권장 사항을 참고하십시오.
  </Step>

  <Step title="vector 구성" id="configure-vector-self-configured">
    Vector가 Logstash 인스턴스처럼 동작하면서 Lumberjack 프로토콜로 이벤트를 수신하도록 구성해야 합니다. 이를 위해 Vector에 [`logstash` 소스](https://vector.dev/docs/reference/configuration/sources/logstash/)를 다음과 같이 구성합니다:

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
          # The files below are generated from the steps at https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          # crt_file: logstash.crt
          # key_file: logstash.key
          # ca_file: ca.crt
          # verify_certificate: true
    ```

    <Info>
      **TLS 구성**

      상호 TLS가 필요한 경우 Elastic 가이드 [&quot;Configure SSL/TLS for the Logstash output&quot;](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output)를 참고하여 인증서와 개인 키를 생성하십시오. 생성한 인증서와 개인 키는 위와 같이 구성에 지정하면 됩니다.
    </Info>

    이벤트는 ECS 포맷으로 수신됩니다. 이러한 이벤트는 Vector Remap Language(VRL) 트랜스포머를 사용하여 OpenTelemetry 스키마(schema)로 변환할 수 있습니다. 이 트랜스포머는 다음과 같이 간단하게 구성할 수 있으며, 스크립트는 별도의 파일에 저장합니다:

    ```yaml
    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'
    ```

    이 구성은 위의 `beats` 소스에서 이벤트를 수신합니다. 사용하는 remap 스크립트는 아래와 같습니다. 이 스크립트는 로그 이벤트로만 테스트되었지만, 다른 포맷을 처리하는 기반으로 활용할 수 있습니다.

    <Accordion title="VRL - ECS를 OTel로 변환">
      ```javascript
      # Define keys to ignore at root level
      ignored_keys = ["@metadata"]

      # Define resource key prefixes
      resource_keys = ["host", "cloud", "agent", "service"]

      # Create separate objects for resource and log record fields
      resource_obj = {}
      log_record_obj = {}

      # Copy all non-ignored root keys to appropriate objects
      root_keys = keys(.)
      for_each(root_keys) -> |_index, key| {
          if !includes(ignored_keys, key) {
              val, err = get(., [key])
              if err == null {
                  # Check if this is a resource field
                  is_resource = false
                  if includes(resource_keys, key) {
                      is_resource = true
                  }

                  # Add to appropriate object
                  if is_resource {
                      resource_obj = set(resource_obj, [key], val) ?? resource_obj
                  } else {
                      log_record_obj = set(log_record_obj, [key], val) ?? log_record_obj
                  }
              }
          }
      }

      # Flatten both objects separately
      flattened_resources = flatten(resource_obj, separator: ".")
      flattened_logs = flatten(log_record_obj, separator: ".")

      # Process resource attributes
      resource_attributes = []
      resource_keys_list = keys(flattened_resources)
      for_each(resource_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_resources, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  resource_attributes = push(resource_attributes, attribute)
              }
          }
      }

      # Process log record attributes
      log_attributes = []
      log_keys_list = keys(flattened_logs)
      for_each(log_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_logs, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  log_attributes = push(log_attributes, attribute)
              }
          }
      }

      # Get timestamp for timeUnixNano (convert to nanoseconds)
      timestamp_nano = if exists(.@timestamp) {
          to_unix_timestamp!(parse_timestamp!(.@timestamp, format: "%Y-%m-%dT%H:%M:%S%.3fZ"), unit: "nanoseconds")
      } else {
          to_unix_timestamp(now(), unit: "nanoseconds")
      }

      # Get message/body field
      body_value = if exists(.message) {
          to_string!(.message)
      } else if exists(.body) {
          to_string!(.body)
      } else {
          ""
      }

      # Create the OpenTelemetry structure
      . = {
          "resourceLogs": [
              {
                  "resource": {
                      "attributes": resource_attributes
                  },
                  "scopeLogs": [
                      {
                          "scope": {},
                          "logRecords": [
                              {
                                  "timeUnixNano": to_string(timestamp_nano),
                                  "severityNumber": 9,
                                  "severityText": "info",
                                  "body": {
                                      "stringValue": body_value
                                  },
                                  "attributes": log_attributes
                              }
                          ]
                      }
                  ]
              }
          ]
      }
      ```
    </Accordion>

    마지막으로, 변환된 이벤트를 구성된 OTLP 엔드포인트로 전송합니다. 이를 위해 Vector에서 OTLP 싱크를 구성해야 합니다. 이 싱크는 `remap_filebeat` 변환에서 나온 이벤트를 입력으로 받습니다:

    ```yaml
    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat] # receives events from a remap transform - see below
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```

    배포 환경에 맞는 [연결 변수](#clickhouse-otel-endpoint-self-configured)를 사용하십시오. 이 출력은 로그 레코드를 전송하므로 Vector URI에 `/v1/logs`가 포함됩니다.

    최종 구성 전체는 다음과 같습니다.

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
            #crt_file: /data/elasticsearch-9.0.1/logstash/logstash.crt
            #key_file: /data/elasticsearch-9.0.1/logstash/logstash.key
            #ca_file: /data/elasticsearch-9.0.1/ca/ca.crt
            #verify_certificate: true

    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'

    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat]
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```
  </Step>

  <Step title="Filebeat 구성" id="configure-filebeat-self-configured">
    Filebeat가 Vector로 데이터를 보낼 때 Logstash 출력을 사용하도록 구성하고, 기존 출력 구성은 모두 이 구성으로 대체하십시오. `YOUR_VECTOR_HOST`를 Vector가 실행 중인 호스트로 바꾸십시오. `localhost`는 Filebeat와 Vector가 같은 호스트에서 실행되는 경우에만 사용하십시오. TLS는 Vector 입력 설정과 일치하도록 구성하십시오:

    ```yaml
    # ------------------------------ Logstash Output -------------------------------
    output.logstash:
      # The Logstash hosts
      hosts: ["YOUR_VECTOR_HOST:5044"]

      # Optional SSL. By default is off.
      # List of root certificates for HTTPS server verifications
      #ssl.certificate_authorities: ["/etc/pki/root/ca.pem"]

      # Certificate for SSL client authentication
      #ssl.certificate: "/etc/pki/client/cert.pem"

      # Client Certificate Key
      #ssl.key: "/etc/pki/client/cert.key"
    ```
  </Step>
</Steps>

## Elastic Agent에서 마이그레이션(migration) {#migrating-from-elastic-agent-self-configured}

Elastic Agent는 여러 Elastic Beats를 하나의 패키지로 통합합니다. 이 에이전트는 [Elastic Fleet](https://www.elastic.co/docs/reference/fleet/fleet-server)과 연동되므로 중앙에서 오케스트레이션하고 구성할 수 있습니다.

Elastic Agent를 배포한 사용자는 다음과 같은 여러 마이그레이션(migration) 경로 중에서 선택할 수 있습니다.

* Lumberjack 프로토콜을 통해 Vector 엔드포인트로 데이터를 전송하도록 에이전트를 구성합니다. **현재 이 방식은 Elastic Agent로 로그 데이터만 수집하는 사용자를 대상으로만 테스트되었습니다.** 이 방식은 Kibana의 Fleet UI에서 중앙 집중식으로 구성할 수 있습니다.
* [에이전트를 Elastic OpenTelemetry Collector(EDOT)로 실행합니다](https://www.elastic.co/docs/reference/fleet/otel-agent). Elastic Agent에는 EDOT Collector가 내장되어 있어, 애플리케이션과 인프라를 한 번만 계측하면 여러 벤더와 백엔드로 데이터를 전송할 수 있습니다. 이 구성에서는 OTLP를 통해 미리 구성해 둔 OTLP 엔드포인트로 이벤트를 전달하도록 EDOT collector를 구성하기만 하면 됩니다. **이 방식은 모든 이벤트 유형을 지원합니다.**

아래에서 두 가지 옵션을 모두 살펴봅니다.

### Vector를 통한 데이터 전송 {#sending-data-via-vector-self-configured}

<Steps>
  <Step title="Vector 설치 및 구성" id="install-configure-vector-self-configured">
    Filebeat 마이그레이션에서 설명한 [단계](#install-vector-self-configured)와 동일하게 Vector를 설치하고 구성하십시오.
  </Step>

  <Step title="Elastic Agent 구성" id="configure-elastic-agent-self-configured">
    Elastic Agent가 Logstash 프로토콜인 Lumberjack을 통해 데이터를 전송하도록 구성해야 합니다. 이는 [지원되는 배포 패턴](https://www.elastic.co/docs/manage-data/ingest/ingest-reference-architectures/ls-networkbridge)이며, 중앙에서 구성하거나, Fleet 없이 배포하는 경우에는 [에이전트 설정 파일 `elastic-agent.yaml`을 통해](https://www.elastic.co/docs/reference/fleet/logstash-output) 구성할 수 있습니다.

    Kibana를 통해 중앙에서 구성하려면 [Fleet에 출력(Output)을 추가](https://www.elastic.co/docs/reference/fleet/fleet-settings#output-settings)하십시오.

    <div className="ch-image-md">
      <Frame>
        ![Logstash 출력 추가](/images/use-cases/observability/add-logstash-output.webp)
      </Frame>
    </div>

    이렇게 추가한 출력은 [에이전트 정책(Policy)](https://www.elastic.co/docs/reference/fleet/agent-policy)에서 사용할 수 있습니다. 그러면 해당 정책을 사용하는 모든 에이전트가 자동으로 Vector로 데이터를 전송합니다.

    <div className="ch-image-md">
      <Frame>
        ![에이전트 설정](/images/use-cases/observability/agent-output-settings.webp)
      </Frame>
    </div>

    이 구성에는 TLS 기반 보안 통신 설정이 필요하므로 [&quot;Logstash 출력에 대한 SSL/TLS 구성&quot;](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output) 가이드를 참고할 것을 권장합니다. 이 가이드를 따를 때는 Vector 인스턴스가 Logstash 역할을 대신한다고 보면 됩니다.

    이때 Vector의 Logstash 소스도 상호 TLS를 사용하도록 구성해야 합니다. [가이드에서 생성한](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs) 개인 키와 인증서를 사용하여 입력을 적절히 구성하십시오.

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: true  # TLS를 사용하는 경우 true로 설정합니다.
          # 아래 파일은 https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs 의 단계에 따라 생성됩니다
          crt_file: logstash.crt
          key_file: logstash.key
          ca_file: ca.crt
          verify_certificate: true
    ```
  </Step>
</Steps>

### Elastic Agent를 OpenTelemetry collector로 실행하기 {#run-agent-as-otel-self-configured}

Elastic Agent에는 EDOT Collector가 내장되어 있어, 애플리케이션과 인프라를 한 번만 계측하면 여러 벤더와 백엔드로 데이터를 전송할 수 있습니다.

<Info>
  **에이전트 통합 및 오케스트레이션**

  Elastic Agent와 함께 배포되는 EDOT collector를 실행하면 [에이전트가 제공하는 기존 통합](https://www.elastic.co/docs/reference/fleet/manage-integrations)을 활용할 수 없습니다. 또한 Fleet에서 collector를 중앙 관리할 수 없으므로, 사용자는 [에이전트를 독립형 모드로](https://www.elastic.co/docs/reference/fleet/configure-standalone-elastic-agents) 실행하고 구성을 직접 관리해야 합니다.
</Info>

EDOT collector와 함께 Elastic Agent를 실행하려면 [공식 Elastic 가이드](https://www.elastic.co/docs/reference/fleet/otel-agent-transform)를 따르십시오. 그런 다음 [연결 변수](#clickhouse-otel-endpoint-self-configured)를 사용하여 OTLP HTTP 익스포터를 구성하십시오.

```yaml
exporters:
  otlphttp/clickhouse:
    endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
    headers:
      authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
```

전달할 각 로그, 메트릭 또는 트레이스 파이프라인의 `exporters` 목록에 `otlphttp/clickhouse`를 추가하십시오. 기존 수신기와 프로세서는 그대로 유지하십시오. 병행 수집이 필요하다면 해당 파이프라인에 Elastic 익스포터를 그대로 두고, Elastic으로의 전송을 중단할 시점에 제거하십시오.

익스포터는 기본 엔드포인트를 사용하며, 신호별 경로를 자동으로 끝에 추가합니다. 프라이빗 인증 기관을 사용하는 HTTPS 수신기라면 `tls.ca_file`을 구성하십시오. 해당 수신기에 상호 TLS가 필요하다면 `tls.cert_file`과 `tls.key_file`도 함께 구성하십시오. 이 설정은 Filebeat-Vector 간 TLS 구성과는 별도로 EDOT-OTLP 간 연결을 보호합니다.

## Elastic OpenTelemetry collector에서 마이그레이션 {#migrating-from-elastic-otel-collector-self-configured}

[Elastic OpenTelemetry Collector (EDOT)](https://www.elastic.co/docs/reference/opentelemetry)를 이미 실행 중인 사용자는 에이전트가 구성된 OTLP 엔드포인트로 OTLP를 통해 데이터를 전송하도록 재구성하기만 하면 됩니다. 절차는 앞에서 설명한 [Elastic Agent를 OpenTelemetry collector로 실행](#run-agent-as-otel-self-configured)하는 방법과 동일합니다. 이 방식은 모든 데이터 타입에 적용할 수 있습니다.
