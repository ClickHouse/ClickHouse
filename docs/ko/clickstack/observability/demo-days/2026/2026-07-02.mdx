## OTel 메트릭 테이블 프라이머리 키 최적화 {#otel-metrics-table-primary-key-optimization}

*데모 진행자: [@knudtty](https://github.com/knudtty)*

<Frame>
  <iframe src="https://www.youtube.com/embed/GIwNxRJGQKg" title="YouTube 동영상 플레이어" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

OTel 메트릭 테이블의 프라이머리 키(primary keys)를 검증하고 축소하는 과정을 심층적으로 살펴봅니다. 여기서 유용한 척도는 그래뉼(granule)당 프라이머리 키 바이트 수, 즉 전체 프라이머리 키 크기를 그래뉼 수로 나눈 값입니다. 이 척도는 테이블이 클수록 그래뉼도 자연히 많아진다는 점을 반영하므로 공정하게 비교할 수 있습니다.

기존 스키마(schema)는 그래뉼당 약 148바이트였습니다. 새 스키마는 17바이트 수준으로, 프라이머리 키 크기가 약 9배 줄었으며 운영 환경의 메모리 사용량(memory usage)도 비슷한 비율로 감소했습니다.

스키마 변경(schema changes) 폭은 크지 않습니다. 이제 `MetricName`에 `LowCardinality`를 사용하며, 고유한 메트릭 이름이 엄청나게 많은 경우가 아니라면 문제가 되지 않습니다. 그런 경우라도 극단적인 상황에서만 우려할 정도입니다. 타임스탬프는 나노초 정밀도의 `DateTime64`에서 초 단위 정밀도의 일반 `DateTime`으로 바뀌었으며, 메트릭에는 이 정도로 충분합니다. 나노초 정밀도가 필요하다면 스키마를 직접 변경하여 유지할 수 있습니다.

또한 시간 컬럼에 명시적인 min/max 인덱스(indexes)를 추가하고, 프라이머리 키에 포함되어 있던 전체 속성 맵을 해시로 대체했습니다. 동일한 변경 사항을 모든 메트릭 테이블 스키마(schemas)에 적용했으며, OTel Collector 업스트림에도 반영하는 중입니다.

**관련 풀 리퀘스트:** [#2545](https://github.com/hyperdxio/hyperdx/pull/2545) fix: change metrics PK for better memory usage

이제 숫자 타일의 값 뒤에 추세선 또는 영역 차트를 표시할 수 있습니다. 오랫동안 Grafana에서 인기를 끌어 온 기능으로, 이제 ClickStack에서도 사용할 수 있습니다.

타일의 표시 설정에서 이 기능을 켤 수 있습니다. 기본값은 배경 차트 없음이며, 선 또는 영역 중 하나를 선택할 수 있습니다. 설정은 매우 간단하지만, 대시보드의 완성도가 눈에 띄게 높아집니다.

현재 배경 차트는 선언형 숫자 타일에서만 지원되므로 사용자 정의 SQL은 아직 사용할 수 없습니다. 차트에 표시할 내용을 더 세밀하게 제어하고 싶다는 사용자 의견이 있어, 이를 후속 작업으로 검토하고 있습니다.

## Grafana 플러그인 개선 사항 {#grafana-plugin-improvements}

*데모 진행자: [@alex-fedotyev](https://github.com/alex-fedotyev)*

<Frame>
  <iframe src="https://www.youtube.com/embed/doFNUMZotJU" title="YouTube 동영상 플레이어" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

ClickStack Grafana 플러그인에 곧 추가될 기능을 정리했습니다.

이제 데이터 소스 구성에서 기존의 다중 데이터베이스 설정 외에 단일 테이블 모드도 지원합니다. 운영 환경 로그와 같은 테이블 하나를 지정하면 쿼리 편집기가 탐색에 최적화된 간결한 빌더로 전환됩니다. 서비스 이름 같은 필드에 대한 빠른 필터와 포함/제외 필터링을 제공하며, 필요하면 언제든 SQL도 사용할 수 있습니다.

또한 익숙한 drill-down 패턴을 그대로 따르는 OTel 로그 및 trace용 기본 제공 대시보드도 함께 제공합니다. 로그 대시보드에는 서비스별 개요, 볼륨 차트, 로그 세부 정보가 포함됩니다. Trace 탐색에서는 서비스 뷰, 지연 시간 히트맵, 작업별 분석을 제공합니다. 로그와 트레이스를 스팬 이름별로 그룹화해 한곳에 보여 주는 통합 서비스 대시보드도 있어, 여러 도구를 오가지 않고도 특정 서비스를 조사할 수 있습니다.

이 대시보드는 모두 기본 스키마(schema)에서 별도 설정 없이 바로 동작합니다. 신규 사용자는 즉시 사용을 시작할 수 있으며, 이를 바탕으로 자체 대시보드를 만들 수도 있습니다.

마법사 방식의 새로운 빌더도 2개 추가되었습니다. 변수 빌더를 사용하면 사용자 정의 SQL을 작성하지 않고도 열 값(column values)을 선택할 수 있습니다. 예를 들어, 파드 이름으로 변수를 만들고 반환되는 값을 미리 확인할 수 있습니다.

어노테이션 빌더는 선택한 필드에 대한 변경 감지 쿼리를 기반으로 어노테이션을 생성합니다. 서비스의 버전 속성을 지정하면 해당 값이 변경될 때마다 배포 마커를 추가하므로 SQL을 직접 작성할 필요가 없습니다.

탐색 및 트레이스 보기 기능이 전반적으로 크게 다듬어졌습니다.

가장 눈에 띄게 개선된 부분은 스팬 뷰입니다. 스팬은 서비스 이름별로 색상이 구분되며, 서비스가 바뀔 때마다 여러 색상이 순환하며 적용됩니다. 또한 새로 추가된 미니맵 덕분에 대규모 트레이스도 회색 막대만 빽빽하게 늘어선 화면보다 훨씬 쉽게 파악할 수 있습니다. 원하는 시간 범위를 드래그하여 확대하고, 클릭 한 번으로 보기를 초기화할 수 있습니다. 새로운 이력 스택을 사용하면 여러 트레이스를 오가다가 이전 위치로 돌아갈 수도 있습니다.

선택한 스팬의 펼치기 및 접기 컨트롤이 개선되어 자식 스팬을 일일이 닫을 필요가 없어졌습니다. 아울러 매우 짧은 스팬에 최소 렌더링 너비를 적용하는 커뮤니티 기여 수정 사항도 머지했습니다. 예를 들어 몇 마이크로초짜리 스팬도 끝까지 확대하지 않아도 타임라인에 계속 표시됩니다.

## MCP의 메트릭 쿼리, 대시보드 평가 및 알림 오류 보고 개선 {#metrics-queries-dashboard-evals-and-better-alert-error-reporting-in-mcp}

*데모 진행자: [@brandon-pereira](https://github.com/brandon-pereira)*

<Frame>
  <iframe src="https://www.youtube.com/embed/yjceqgveZr8" title="YouTube 동영상 플레이어" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

이번 주기에는 MCP 서버에 대한 세 가지 개선 사항이 함께 반영되었습니다.

이제 MCP는 기반 데이터에 접근하기 위해 대시보드를 거칠 필요 없이 노트북을 비롯한 여러 곳에서 메트릭 쿼리를 직접 실행할 수 있습니다.

또한 대시보드 구축에 대한 엔드투엔드 평가를 추가했습니다. 현재 약 75%의 케이스를 통과하며, 편법으로 통과하기 어렵도록 방해 요소를 꾸준히 추가하고 있습니다. 실제 환경에서 MCP가 잘못된 대시보드를 생성하면 해당 실패 사례를 평가 세트에 다시 반영할 수 있습니다. 이를 통해 시간이 지나면 원시 SQL(Raw SQL) 소스가 잘못된 쿼리를 생성하는 등의 문제를 반복적인 실패로 굳어지기 전에 포착할 수 있을 것입니다.

이제 도구 오류는 하나의 범용 버킷에 한꺼번에 쌓이지 않고 범주별로 분류됩니다. 사용자가 작성한 잘못된 SQL 쿼리(SQL query)는 데이터베이스 타임아웃과 같은 내부 실패와 구분하여 처리됩니다. 이러한 구분 덕분에 MCP 상태에 대해 더 유용한 알림을 구축할 수 있게 되었습니다.

## OTel collector batch processor 업데이트 {#otel-collector-batch-processor-updates}

*데모 진행자: [@SpencerTorres](https://github.com/SpencerTorres)*

<Frame>
  <iframe src="https://www.youtube.com/embed/rlSm_9ivsQ4" title="YouTube 동영상 플레이어" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

OpenTelemetry는 배칭 기능을 독립형 batch processor에서 익스포터(exporter) 구성으로 옮기고 있습니다. ClickStack 수집기는 이미 두 방식을 모두 지원하고 있었으므로 코드를 변경할 필요가 없었고, 결과적으로 문서만 업데이트되었습니다.

기존 모델에서는 파이프라인에 전용 batch processor를 두어 행(rows)을 버퍼에 저장한 후 익스포터로 전달했습니다. 이 프로세서에는 배치 크기, 최대 배치 크기, 타임아웃 설정이 별도로 있었습니다.

OpenTelemetry가 표준으로 채택하고 있는 모델에서는 배처(batcher)를 프로세서 연쇄에 두지 않고 익스포터와 함께 둡니다. 최소 및 최대 배치 크기, 큐 크기 등 대부분의 개념은 그대로 유지됩니다. 또한 익스포터 기반 구성은 블로킹 동작, 바이트 기반 제한, 영속화를 지원하는데, 이들은 모두 기존 batch processor에서는 제공되지 않던 기능입니다.

이제 문서에서는 익스포터 기반 구성을 권장하며, 기존 batch processor 설정을 마이그레이션하는 방법도 설명합니다. 또한 대부분의 배포에 적합한 기본값으로 최소 5,000개의 행과 짧은 타임아웃을 권장합니다. 잘못된 배칭 구성은 여전히 ClickHouse를 처음 사용할 때 좋지 않은 경험을 하게 되는 가장 흔한 원인 중 하나입니다.

주변 컨텍스트(Surrounding context)를 사용하면 로그 행을 열어 그 시점 전후에 어떤 일이 있었는지 확인할 수 있습니다. 기본적으로 이 컨텍스트는 서비스, 파드 또는 노드 기준으로 그룹화됩니다. 이 방식은 OTel 스키마(schema)를 사용하는 대부분의 배포 환경에서 잘 동작하지만, 사용자 정의 스키마를 사용하면 자체 속성을 기준으로 뷰를 구성할 마땅한 방법이 없었습니다.

이제 OTel 스키마든 사용자 정의 스키마든 관계없이 로그 행의 어떤 속성이든 기준으로 삼아 컨텍스트 뷰를 구성할 수 있습니다. 기존의 서비스, 파드, 노드 옵션은 그대로 제공되며, 텔레메트리 SDK 버전이나 로그 행의 다른 필드를 기준으로도 손쉽게 그룹화할 수 있습니다. 또한 언제든지 선택을 해제하고 처음부터 다시 구성할 수 있습니다.
