ClickHouse Observability는 전적으로 **ClickHouse Cloud** 내에서 실행되며, 동일한 ClickStack 데이터 모델과 사용자 경험을 그대로 유지하면서 완전 관리형 관측성 백엔드를 제공합니다. 자가 관리형 배포는 [자가 관리형 아키텍처](/ko/clickstack/self-configured/architecture)를 참조하십시오.

이 모델에서는 **ClickHouse, ClickStack UI, OpenTelemetry(OTel) 수집 collector**의 호스팅, 운영, 보안을 ClickHouse Cloud가 담당합니다. 사용자는 애플리케이션을 계측하고, 자체 환경에서 관리형 서비스로 텔레메트리를 전송하기만 하면 됩니다.

### OpenTelemetry collector: 데이터 수집 {#open-telemetry-collector-managed}

ClickHouse Observability에는 개방적이고 표준화된 방식으로 텔레메트리를 수집할 수 있는 관리형 OpenTelemetry(OTel) collector가 포함되어 있습니다. 서비스에서 **팀 설정 → 데이터 → Managed Telemetry**를 열어 OTLP 엔드포인트와 API Key를 복사하십시오. 연결 및 인증 방법은 [OpenTelemetry 데이터 전송](/ko/clickstack/observability/ingesting-data/opentelemetry)을 참조하십시오.

collector는 텔레메트리를 효율적인 배치 단위로 ClickHouse Cloud에 내보내며, 각 텔레메트리 신호에 최적화된 테이블 스키마(table schema)를 사용합니다.

수집용 collector는 ClickHouse Cloud에서 관리합니다. 다만 호스트 메트릭이나 Kubernetes 로그 같은 텔레메트리를 수집하여 관리형 엔드포인트로 전달하려면 자체 환경에도 collector가 필요할 수 있습니다.

### ClickHouse Cloud: 엔진 {#clickhouse-cloud}

ClickHouse Observability의 핵심은 ClickHouse Cloud입니다. ClickHouse Cloud는 대규모 실시간 분석을 위해 설계된 컬럼 지향 데이터베이스인 ClickHouse의 서버리스 버전입니다. ClickHouse Cloud는 관측성 데이터의 수집과 쿼리를 담당하며, 다음과 같은 기능을 제공합니다.

* 대량의 이벤트에 대한 빠른 검색
* high-cardinality 텔레메트리의 대규모 수집
* 관측성 데이터에 최적화된 컬럼 지향 압축
* 반정형 JSON 데이터를 네이티브로 지원하여 동적 스키마 진화(Schema Evolution) 가능
* 수백 개의 내장 분석 함수(analytical functions)를 갖춘 강력한 SQL 엔진

ClickHouse Cloud는 관측성 데이터를 와이드 이벤트로 처리하므로, 하나의 통합된 구조 안에서 로그, 메트릭, 트레이스를 심층적으로 상관 분석할 수 있습니다.

또한 ClickHouse Cloud는 ClickHouse 오픈 소스 대비 관측성 측면에서 다음과 같은 여러 이점을 제공합니다.

* 저장소와 독립적인 컴퓨트 자동 확장
* 컴퓨트 용량과 무관하게 텔레메트리를 보존할 수 있는 객체 저장소
* 통합 인증
* 보안 및 컴플라이언스 기능
* 중단 없는 업그레이드

### ClickStack UI: 인터페이스 {#hyperdx}

ClickStack UI는 ClickStack의 사용자 인터페이스로, 다음 기능을 제공합니다.

* 자연어 및 Lucene 스타일 검색
* 실시간 디버깅을 위한 라이브 테일링(live tailing)
* 로그, 메트릭, 트레이스 통합 보기
* 프론트엔드 관측성을 위한 세션 리플레이
* 대시보드 생성 및 알림 구성
* 고급 분석을 위한 SQL 쿼리(SQL query) 인터페이스

ClickHouse 전용으로 설계된 ClickStack UI는 강력한 검색 기능과 직관적인 워크플로를 결합하여 이상 징후를 발견하고 이슈를 조사하며 인사이트를 빠르게 얻을 수 있도록 지원합니다.

ClickHouse Observability에서 UI는 ClickHouse Cloud 콘솔 인증 시스템과 통합되어 있습니다.

### 수집과 쿼리 격리 {#ingestion-query-isolation}

ClickHouse Observability는 수집과 쿼리 실행에 별도의 컴퓨트를 사용합니다. 쓰기 컴퓨트는 유입되는 텔레메트리와 백그라운드 데이터 유지 관리 작업을 처리하고, 읽기 컴퓨트는 검색, 대시보드, 노트북, 알림 쿼리를 처리합니다. 두 컴퓨트는 모두 동일한 기반 객체 스토리지에 액세스합니다.

이처럼 컴퓨트를 분리하면 수집 워크로드와 쿼리 워크로드 간의 리소스 경합이 줄어듭니다. 쓰기 컴퓨트를 일시적으로 사용할 수 없더라도 읽기 컴퓨트는 저장된 데이터를 계속 쿼리할 수 있습니다. 다만 최신 텔레메트리가 지연될 수 있습니다. 반대로 읽기 컴퓨트를 사용할 수 없으면 수집은 계속되지만, 검색과 알림 평가가 중단될 수 있습니다.

### 스케일링 {#scaling}

ClickHouse Cloud는 워크로드(workloads)의 변화에 맞춰 용량을 관리합니다. 관리형 collector는 수집 트래픽을 처리하기 위해 수평 확장되며, 쓰기 컴퓨트와 읽기 컴퓨트는 서로 독립적으로 스케일링되고 저장소와도 독립적으로 스케일링됩니다.

스케일링은 즉시 이루어지지 않습니다. 수집량이 갑자기 늘어나면 새 텔레메트리가 검색 가능해지기까지 시간이 더 걸릴 수 있으며, 쿼리가 급증하면 용량이 조정되는 동안 응답 시간이 길어질 수 있습니다. 워크로드를 분리하면 한 워크로드가 다른 워크로드에 미치는 영향을 줄일 수 있습니다.

### 수집 버퍼링 및 복구 {#ingestion-buffering-recovery}

관리형 collector는 먼저 텔레메트리를 ClickHouse에 기록하려고 시도합니다. ClickHouse가 일시적으로 쓰기 작업을 받을 수 없으면, 수집 파이프라인은 나중에 재적용할 수 있도록 배치를 Amazon S3에 저장할 수 있습니다. 이 임시 수집 버퍼는 ClickHouse가 텔레메트리 저장에 사용하는 객체 스토리지와는 별개입니다. 쓰기 작업이 재개되면 버퍼에 저장된 데이터가 ClickHouse로 수집됩니다.

복구 중에는 백로그가 처리되는 동안 최근 텔레메트리가 늦게 표시되거나 순서가 뒤바뀌어 표시될 수 있습니다. 이 버퍼링은 일시적인 쓰기 중단 상황의 복구를 지원하지만, cross-region 장애 조치(failover)를 제공하거나 모든 장애 상황에서 전달을 보장하지는 않습니다.

collector가 중지될 때 해당 collector의 메모리에만 남아 있던 데이터나, ClickHouse와 S3 어디에도 기록하지 못한 배치 등 일부 데이터는 여전히 손실될 수 있습니다. 데이터를 전송하는 에이전트와 collector가 실패한 내보내기를 재시도하도록 구성하고, 지원되는 경우 영구 큐를 사용하여 중단 중에도 텔레메트리가 보존되도록 하십시오.
