<Info>
**TL;DR**

Add your service's Datadog-compatible endpoint to the Datadog Agents you already run, either next to Datadog or in place of it, and restart them. Your logs, traces, and metrics appear in ClickHouse Observability. There is no collector to deploy and nothing to change in your applications.

Time required: about 15 minutes
</Info>

You have created your ClickHouse Observability service, and your telemetry already flows through Datadog Agents. You do not have to replace those agents, or touch your applications, to see what the service does with your own data.

ClickHouse Observability includes a Datadog-compatible endpoint. It accepts the logs, traces, and metrics your agents already produce, converts them to OpenTelemetry, and stores them in your service. The only change is in the agent configuration. That lets you:

- Evaluate ClickHouse Observability with your real production telemetry rather than a sample dataset.
- Keep sending data to Datadog while you compare the two platforms side by side.
- Migrate gradually. Move agents over group by group, and adopt OpenTelemetry instrumentation at your own pace.

## Prerequisites {#prerequisites}

- A ClickHouse Observability service. If you do not have one yet, follow the [Getting started guide](/clickstack/observability/getting-started).
- Datadog Agent 7 on the hosts, containers, or Kubernetes clusters you want to evaluate with, already collecting the logs and metrics you care about. For traces, your applications must already send traces to the Agent through Datadog tracing libraries.
- Access to the Agent configuration, either `datadog.yaml` or the equivalent environment variables, and permission to restart the Agent.
- Outbound HTTPS access on port `8126` from the agent hosts to your service's telemetry endpoint.

## Connect your Datadog Agents {#connect-your-datadog-agents}

The Datadog-compatible endpoint lives on the same host as the OTLP endpoint, on port `8126` instead of `4318`, and your service's API key doubles as the Datadog API key. The rest of this guide uses these placeholders:

| Placeholder | Value |
| --- | --- |
| `YOUR_API_KEY` | Your service's API key |
| `YOUR_OTEL_HOST` | The hostname from the OTLP endpoint, without `https://` or the port |
| `https://YOUR_OTEL_HOST:8126` | The Datadog-compatible endpoint for metrics and traces |
| `YOUR_OTEL_HOST:8126` | The same endpoint as `host:port`, which the Agent's log settings expect |

You can find the same values at any time under **Team Settings → Managed Telemetry**.

<Step title="Configure your Datadog Agents" id="configure-your-datadog-agents">
Pick how the agents should send data. Both options change only the Agent configuration, in `datadog.yaml` or through environment variables, and neither changes what the Agent collects. Start with one agent, confirm its data arrives, then roll the change out further.

<Tabs>
<Tab title="Alongside Datadog" id="alongside-datadog">

The Agent can ship every payload to more than one destination. Keep your existing `api_key` and `site`, and add your service as an additional endpoint for metrics, traces, and logs. Datadog documents this as [dual shipping](https://docs.datadoghq.com/agent/configuration/dual-shipping/).

```yaml
# datadog.yaml: keep api_key and site as they are, then add these settings.

# Metrics
additional_endpoints:
  "https://YOUR_OTEL_HOST:8126":
    - "YOUR_API_KEY"

# Use the v2 metrics intake.
use_v3_api:
  series:
    enabled: false

# Traces
apm_config:
  additional_endpoints:
    "https://YOUR_OTEL_HOST:8126":
      - "YOUR_API_KEY"

# Logs
logs_config:
  force_use_http: true
  additional_endpoints:
    - api_key: "YOUR_API_KEY"
      Host: "YOUR_OTEL_HOST"
      Port: 8126
      is_reliable: true
```

Datadog keeps receiving everything as before. Each destination has its own API key, so your Datadog key never reaches ClickHouse Observability and your ClickHouse Observability key never reaches Datadog. Logs are only shipped to additional endpoints over HTTP, which `force_use_http` turns on, and `is_reliable: true` makes the Agent buffer and retry logs for the new endpoint rather than drop them if it is briefly unreachable. If `apm_config` or `logs_config` already exist in your file, add the new keys to the existing sections.

</Tab>
<Tab title="Instead of Datadog" id="instead-of-datadog">

To move an agent over completely, point its primary destinations at your service and use your service's API key:

```yaml
api_key: "YOUR_API_KEY"

# Metrics destination
dd_url: "https://YOUR_OTEL_HOST:8126"

# Use the v2 metrics intake.
use_v3_api:
  series:
    enabled: false

# Trace destination
apm_config:
  enabled: true
  apm_dd_url: "https://YOUR_OTEL_HOST:8126"

# Log destination
logs_enabled: true
logs_config:
  logs_dd_url: "YOUR_OTEL_HOST:8126"
  force_use_http: true
  logs_no_ssl: false

remote_updates: false
remote_configuration:
  enabled: false
```

These settings redirect the Agent's logs, traces, and metrics. They do not change which logs the Agent collects or add instrumentation, so keep your existing log collection integrations and tracing setup in place. Remote configuration is turned off because the Agent would otherwise keep asking Datadog for configuration with a key Datadog no longer recognizes.

</Tab>
</Tabs>

<Accordion title="Configure through environment variables">
Container and Kubernetes deployments usually configure the Agent through `DD_` environment variables, which override `datadog.yaml`. Set them in your Docker command, Helm values, or Operator spec.

To send alongside Datadog:

```shell
DD_ADDITIONAL_ENDPOINTS='{"https://YOUR_OTEL_HOST:8126": ["YOUR_API_KEY"]}'
DD_APM_ADDITIONAL_ENDPOINTS='{"https://YOUR_OTEL_HOST:8126": ["YOUR_API_KEY"]}'
DD_LOGS_CONFIG_FORCE_USE_HTTP=true
DD_LOGS_CONFIG_ADDITIONAL_ENDPOINTS='[{"api_key": "YOUR_API_KEY", "Host": "YOUR_OTEL_HOST", "Port": 8126, "is_reliable": true}]'
```

To send instead of Datadog:

```shell
DD_API_KEY=YOUR_API_KEY
DD_DD_URL=https://YOUR_OTEL_HOST:8126
DD_APM_ENABLED=true
DD_APM_DD_URL=https://YOUR_OTEL_HOST:8126
DD_LOGS_ENABLED=true
DD_LOGS_CONFIG_LOGS_DD_URL=YOUR_OTEL_HOST:8126
DD_LOGS_CONFIG_FORCE_USE_HTTP=true
DD_REMOTE_CONFIGURATION_ENABLED=false
```

Agent 7.81 and later send metrics to a newer series intake by default. If metrics do not arrive from an agent configured this way, add `use_v3_api.series.enabled: false` to its `datadog.yaml`, as the file-based examples above do.
</Accordion>
</Step>

<Step title="Restart the Agent and check its status" id="restart-and-check">
Restart the Agent to apply the configuration. On Linux:

```shell
sudo systemctl restart datadog-agent
sudo datadog-agent status
```

On macOS:

```shell
sudo launchctl kickstart -k system/com.datadoghq.agent
datadog-agent status
```

For a containerized Agent, update its environment and redeploy the container or pod, then run `agent status` inside it.

In the status output, the **Forwarder**, **APM Agent**, and **Logs Agent** sections list each destination. A healthy agent shows your endpoint with no errors. `403` responses mean the API key is wrong or was copied before you selected **Reveal key**. Connection errors or timeouts point at a typo in the host, a port other than `8126`, or blocked outbound access.
</Step>
</Steps>

## Confirm data is arriving {#confirm-data-is-arriving}

Return to the **Start sending telemetry** page in your service and select **Check for data**. Once your telemetry has arrived, the service status changes to **Data received** and **Start exploring** becomes available.

Select **Start exploring** to open **Search**. Select the **Logs** source, set the time range to **Last 15 minutes**, and filter `ServiceName` to the `service` tag your Agent applies. Expand a record: the Agent's `host`, `env`, container, and Kubernetes tags appear as resource attributes, and Datadog's `status` is mapped to `SeverityText`, so `level:error` style filters work as they do for OpenTelemetry logs.

## If nothing shows up {#if-nothing-shows-up}

- Read the Agent status first. Authentication, endpoint, and network problems are reported there per destination. In the alongside configuration, errors for your endpoint never stop data from reaching Datadog.
- Check the API key. It must be the full value, which you can copy after selecting **Reveal key**, and it is used as the Datadog `api_key` for your endpoint, not as a header.
- Confirm the endpoint. Metrics and traces use `https://YOUR_OTEL_HOST:8126` with the scheme; the log settings use `YOUR_OTEL_HOST:8126` without it. The hostname is the one from your OTLP endpoint, and the port is `8126`, not `4318`.
- If logs do not arrive, confirm `logs_enabled: true` and that log collection is configured for the integrations or files you expect. The endpoint only accepts logs over HTTP, so `force_use_http` must be `true`.
- If traces do not arrive, confirm `apm_config.enabled: true` and that your applications send traces to the Agent. The endpoint receives what the Agent forwards; it does not instrument applications.
- If metrics do not arrive, confirm the agent uses the v2 series intake with `use_v3_api.series.enabled: false`.
- Widen the time range in **Search** and remove any filters. The default source may be set to **Traces** rather than **Logs**.
- To rule out the service itself, go to **Team Settings → Managed Telemetry** and use **Send a Test Log**. If that log appears in **Search**, the service is receiving data and the problem is between the Agent and the endpoint.

## What the endpoint accepts {#what-the-endpoint-accepts}

The endpoint understands the protocols the Datadog Agent uses and translates each payload into OpenTelemetry before it reaches your service:

- **Logs.** Datadog timestamps, bodies, and statuses become OpenTelemetry timestamps, bodies, and severities. Structured JSON logs are decoded, so their fields are queryable. Hostnames, service names, environments, and known container, cloud, and Kubernetes tags become resource attributes.
- **Traces.** Spans from Datadog tracing libraries keep their service, resource, and tag data, and 128-bit trace IDs are reconstructed so Datadog-sourced logs and spans correlate with services instrumented with OpenTelemetry.
- **Metrics.** Series sent to the v2 intake, including the Agent's host metrics, custom metrics, and DogStatsD gauges and counters. Distributions arrive as sketches.
- **Compression.** Agent 7.59 and later compress HTTP payloads with Zstandard, which the endpoint accepts alongside gzip.

The endpoint is built on the OpenTelemetry Collector's Datadog receiver, an alpha component, and is experimental in ClickHouse Observability. Datadog's own backend features, such as monitors, pipelines, and processors, are outside its scope. For the full migration guide, including a receiver you run yourself in the self-managed experience, see [Migrating from Datadog](/clickstack/observability/migration/datadog).
