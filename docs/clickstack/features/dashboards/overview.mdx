ClickStack supports visualizing events, with built-in support for charting in ClickStack UI. These charts can be added to dashboards for sharing with other users.

Visualizations can be created from traces, metrics, logs, or any user-defined wide event schemas.

## Creating visualizations {#creating-visualizations}

The **Chart Explorer** interface in ClickStack UI allows you to visualize metrics, traces, and logs over time, making it easy to create quick visualizations for data analysis. This interface is also reused when creating dashboards. The following section walks through the process of creating a visualization using Chart Explorer.

Each visualization begins by selecting a **data source**, followed by a **metric**, with optional **filter expressions** and **group by** fields. Conceptually, visualizations in ClickStack UI map to a SQL `GROUP BY` query under the hood — you define metrics to aggregate across selected dimensions.

<Tip>
**AI-powered chart generation**

ClickStack also supports creating charts from natural language prompts using the [text-to-chart](/clickstack/text-to-chart) feature. Describe what you want to see, and ClickStack generates the visualization automatically.
</Tip>

For example, you might chart the number of errors (`count()`) grouped by service name.

For the examples below, we use the remote dataset available at [sql.clickhouse.com](https://sql.clickhouse.com), described in the guide ["Remote Demo Dataset"](/clickstack/example-datasets/remote-demo-data). **You can also reproduce these examples by visiting [play-clickstack.clickhouse.com](https://play-clickstack.clickhouse.com).**

## Creating dashboards {#creating-dashboards}

Dashboards provide a way to group related visualizations, enabling you to compare metrics and explore patterns side by side to identify potential root causes in your systems. These dashboards can be used for ad-hoc investigations or saved for ongoing monitoring.

Global filters can be applied at the dashboard level, automatically propagating to the chart builder visualizations within that dashboard. This allows for consistent drill-down across charts and simplifies correlation of events across services and telemetry types.

Heatmap tiles plot the count of events falling into each (time, value) bucket as a colored grid. Use a heatmap when you want to see the **shape** of a distribution over time, not just the average or a single percentile. A latency heatmap reveals bimodal duration patterns, slow-tail clusters, or sudden spreads that a Line chart would average away.

To add a heatmap tile:
1. Select `Add New Tile`.
2. Choose the `Heatmap` visualization type from the top menu. The data source dropdown only shows sources whose [source type is `Traces`](/clickstack/managing/config#traces). Logs, metrics, and session sources are filtered out, since heatmaps need a span duration column that only traces sources provide.
3. Pick any of your traces sources by name. The name itself is arbitrary, only the type matters.

Once a source is selected, the heatmap pre-fills:

- **Value**: the source's `Duration Expression`, scaled to the current display unit (for example `(Duration)/1e6` to convert each event's span duration from nanoseconds to milliseconds)
- **Count**: `count()`

4. Set a chart name, and use `Where` to scope the heatmap to a specific service or set of operations whose performance you want to observe.
5. Adjust the time range to match the period of interest. Wider ranges expose distribution shifts and bimodal latency patterns that shorter windows can hide.

The example below shows a single service over a 24 hour window, with the fast and slow paths of its span duration clearly separated into two horizontal bands.

To customize the heatmap further, click **Display Settings** to open a drawer for the **Scale** (Log or Linear), **Value**, and **Count** expression. The full list of options are documented in [Customize the heatmap](/clickstack/features/event-deltas#customize) on the Event Deltas page. The same drawer is reused.

Click `Run` to preview the chart, then `Save`.

### Tile display settings {#tile-display-settings}

Each tile has a **Display Settings** drawer for options that control how its value is rendered. Open it from the tile editor by clicking **Display Settings**. The available options depend on the visualization type.

#### Number tile color {#number-tile-color}

Number tiles support a static **Color** choice from the curated chart palette. With a number tile selected, open **Display Settings** and use the **Color** control (labeled **Number tile color** for accessibility) to pick a swatch, or clear the selection to use the default text color.

Colors are stored as palette tokens, not raw hex values, so the same tile reflows correctly across light, dark, and IDE themes.

**Categorical tokens** (multi-series hues):

| Token | Label |
|---|---|
| `chart-blue` | Blue |
| `chart-orange` | Orange |
| `chart-red` | Red |
| `chart-cyan` | Cyan |
| `chart-green` | Green |
| `chart-pink` | Pink |
| `chart-purple` | Purple |
| `chart-light-blue` | Light Blue |
| `chart-brown` | Brown |
| `chart-gray` | Gray |

**Semantic tokens** (status-oriented):

| Token | Label |
|---|---|
| `chart-success` | Success |
| `chart-warning` | Warning |
| `chart-error` | Error |

Use semantic tokens when the number represents a status (for example error count in `chart-error`, or a healthy rate in `chart-success`). Use categorical tokens when you want visual distinction between related KPI tiles without implying status.

Older configs may still store legacy numeric tokens (`chart-1` through `chart-10`). ClickStack maps those to the hue-named tokens above when loading a dashboard.

The same palette powers optional **color rules** in the same drawer: ordered conditions evaluated against the displayed value (last match wins). When no rule matches, the static color applies, then the default text color.

#### Number tile background chart {#number-tile-background-chart}

Number tiles can show a **background chart**: a trend sparkline drawn behind the value, so its movement over the selected time range is visible at a glance. This is useful for SLO and error-budget tiles, where how a value is trending matters as much as its current reading.

With a number tile selected, open **Display Settings** and set **Background chart** to **Line** or **Area** (or **None** to turn it off). The sparkline is derived from a time-bucketed version of the tile's query, so no extra configuration is needed. It inherits the tile color by default; set a **Background color** to override it with a specific palette color.

<div className="ch-image-lg">

<Frame>

![Display Settings drawer for a number tile, with Background chart set to Area](/images/clickstack/dashboards/number-tile-background-chart.webp)

</Frame>

</div>

Background charts apply to query-builder number tiles. Raw SQL number tiles return a single value with no time dimension to bucket, so the option appears but is disabled for them.

Table tiles can stripe their rows with **Alternate Row Background**, which tints every other row so wide tables are easier to scan. It is off by default.

With a table tile selected, open **Display Settings** and turn on **Alternate Row Background**. Striping is purely visual, so it works on both query-builder and raw SQL table tiles.

<div className="ch-image-lg">

<Frame>

![Display Settings drawer for a table tile, with Alternate Row Background turned on](/images/clickstack/dashboards/table-tile-display-settings.webp)

</Frame>

</div>

Table tiles also keep a separator between the header row and the data as you scroll, so the column headers stay distinct.

#### Dashboards API: number tile color {#api-number-tile-color}

When creating or updating dashboards through the external API (`POST` / `PUT` `/api/v2/dashboards`), set `color` on a builder number-tile config to a palette token. Raw hex values are rejected.

```json
{
  "name": "Error rate KPIs",
  "tiles": [
    {
      "id": "65f5e4a3b9e77c001a222222",
      "name": "Errors",
      "x": 0,
      "y": 0,
      "w": 6,
      "h": 4,
      "config": {
        "displayType": "number",
        "sourceId": "<SOURCE_ID>",
        "select": [
          {
            "aggFn": "count",
            "where": "SeverityText:error",
            "whereLanguage": "lucene",
            "alias": "Errors"
          }
        ],
        "color": "chart-error",
        "backgroundChart": {
          "type": "area"
        }
      }
    }
  ]
}
```

`color` accepts any token from the categorical and semantic lists above (for example `chart-blue` or `chart-success`). Optional `backgroundChart.color` overrides the sparkline color with the same token enum. See the [ClickStack API reference](/clickstack/api-reference) for authentication and base URLs.

## Custom filters and variables {#custom-filters}

In addition to the [free-text filters](#filter-dashboards) available on all dashboards, saved dashboards support custom filters and variables. These provide reusable, point-and-click controls so that dashboard viewers can filter without writing expressions manually. Their values can come from a column queried from a source, a hand-written list, a SQL query, Prometheus label values, or freely chosen key-value conditions. Variables can also determine which data source or connection a tile queries. See [Filter types](#filter-types) for the full list.

<div className="ch-image-lg">

<Frame>

![Services dropdown filter showing available service names](/images/clickstack/dashboards/filter-dropdown.webp)

</Frame>

</div>

Each filter allows the viewer to choose one or more values, and does one or both of the following with them:

- **Broadcast** — applies the selection as a filter condition on matching tiles. Tiles do not need to be updated to reference the filter.
- **Variable** — exposes the selection to tile queries as `$variableName`, so each tile decides where and how the value is used.

Which of the two a filter supports depends on its [type](#filter-types). A **SQL expression values** filter must do at least one of the two, and broadcasts by default.

The following steps demonstrate adding a filter to the dashboard created in the ["Creating dashboards"](#creating-dashboards) section.

### Filter types {#filter-types}

The **Type** selector in the filter dialog decides where a filter's values come from and how they reach tiles.

| Type | Values come from | Broadcast | Variable |
|------|------------------|-----------|----------|
| [SQL expression values](#sql-expression-values-filters) | The distinct values of an expression, queried from a source | Optional, enabled by default | Optional |
| [Static values](#static-values-filters) | A hand-written list | No | Always |
| [SQL query values](#sql-query-filters) | The first column of a SQL query | No | Always |
| [PromQL label values](#promql-label-filters) | The values of a Prometheus label | No | Always |
| [Ad hoc keys and values](#adhoc-filters) | `key operator value` conditions built from the keys and values of one or more sources | Always | No |
| [Data source](#data-source-variables) | The team's sources | No | Always, as a [source reference](#source-connection-variables) |
| [Connection](#connection-variables) | The team's ClickHouse connections | No | Always, as a [connection reference](#source-connection-variables) |

#### SQL expression values {#sql-expression-values-filters}

Its dropdown lists the distinct values of the **Filter expression** in the selected **Data source**, optionally narrowed by a **Dropdown values filter**. For metric sources, also choose a **Metric type**. A SQL expression values filter can [broadcast](#broadcast-filters) its selection, be [available as a variable](#dashboard-variables), or both.

#### Static values {#static-values-filters}

Its dropdown offers a hand-written list of values. Type each value in **Options** and press Enter. A filter can hold up to 1000 options.

A static values filter is always a variable and never broadcasts, so tiles use it by referencing its variable, for example `$__filter(SeverityText, $severity)`. This is useful for values that aren't stored in a column, or for a fixed, curated list.

#### SQL query values {#sql-query-filters}

Its dropdown lists the first column returned by a ClickHouse SQL query, in the order the query returns rows, up to 10,000 values. Configure:

- **Connection** — the ClickHouse connection the query runs on, or a [connection variable](#connection-variables).
- **Source** — optional. A source on the same connection, or a [data source variable](#data-source-variables). With a source selected, the query can use `$__sourceTable` and `$__filters`, which applies the dashboard's broadcast filter selections for that source, the same way [raw SQL tiles](/clickstack/features/dashboards/sql-visualizations#dashboard-filter-macro) do.
- **SQL query** — the query itself. It can use the [time macros](/clickstack/features/dashboards/sql-visualizations#time-filter-macros) and reference the dashboard's other variables. The editor previews the values the query returns for the dashboard's current time range.

For example, the following query lists the services that logged events in the dashboard's time range, limited to the environments selected in an `environment` filter:

```sql
SELECT DISTINCT ServiceName
FROM otel_logs
WHERE $__timeFilter(TimestampTime)
  AND $__filter(ResourceAttributes['deployment.environment'], $environment)
ORDER BY ServiceName
```

A SQL query values filter is always a variable and never broadcasts.

#### PromQL label values {#promql-label-filters}

<Note>
PromQL support is in preview. In Open Source deployments, enable it by setting `ENABLE_PROMQL=true` for the API and `NEXT_PUBLIC_ENABLE_PROMQL=true` for the app (see [optional features](/clickstack/managing/config#optional-features-and-deployment-modes)), and enable the PromQL schema in the collector (see [Prometheus-compatible metrics](/clickstack/managing/config#collector-prometheus-metrics)). See [PromQL source settings](/clickstack/managing/config#promql-source-settings) to create a PromQL source.
</Note>

Its dropdown lists the values of a Prometheus label. Select a PromQL **Data source**, and enter the **Label** whose values populate the dropdown, such as `job`, `instance`, or `__name__`. Optionally, enter **Series matchers** — a Prometheus series selector, such as `up{job="api"}`, that narrows which series the values are read from. Series matchers can reference the dashboard's other variables.

A PromQL label values filter is always a variable and never broadcasts. In PromQL tiles, reference it inside a label matcher, for example `rate(http_requests_total{job=~"$job"}[$__rate_interval])`. See [Referencing a variable](#referencing-variables) for how values are rendered.

#### Ad hoc keys and values {#adhoc-filters}

<Note>
Ad hoc filters are experimental. To make them available, set `NEXT_PUBLIC_ENABLE_ADHOC_FILTERS=true` (see [optional features](/clickstack/managing/config#optional-features-and-deployment-modes)).
</Note>

Instead of offering a single dropdown, an ad hoc filter lets the viewer build a list of `key operator value` conditions from the keys of its sources: columns and map keys for SQL sources, or labels for Prometheus sources. Keys and values are suggested as the viewer types. Configure:

- **Source type** — SQL (log, trace, or session sources) or Prometheus.
- **Data sources** — the sources whose keys and values the filter suggests.
- **Keys and values filter** — optional, SQL sources only. A SQL or Lucene condition that narrows the rows keys and values are suggested from. It can reference the dashboard's other variables.
- **Applies to sources** — the sources the conditions are broadcast to. Leave it empty to broadcast to every tile that uses one of the filter's data sources.
- **Unique name** — identifies the filter's conditions in the [dashboard URL](/clickstack/url-parameters#dashboard-filter-values).

Conditions on SQL sources support the following operators: `=`, `!=`, `=~` (regex), `!~` (regex), `LIKE`, `NOT LIKE`, `IN`. Conditions on Prometheus sources support `=`, `!=`, `=~` (regex), `!~` (regex), and `IN` — `LIKE` and `NOT LIKE` are SQL-only.

Viewers can also add a condition by clicking a value in a table, time series, or search tile on the dashboard.

Ad hoc conditions are always broadcast, and can't be referenced as variables. Chart builder tiles and PromQL tiles on the matching sources pick them up automatically, and raw SQL tiles apply them through the [`$__filters` macro](/clickstack/features/dashboards/sql-visualizations#dashboard-filter-macro).

#### Data source {#data-source-variables}

A data source variable lets the viewer choose which source a tile queries. Select the **Source kinds** offered in its dropdown, for example only log sources, and optionally limit them to one **Connection**, which can itself be a connection variable. See [Data source and connection variables](#source-connection-variables) for how tiles and filters use it.

#### Connection {#connection-variables}

A connection variable lets the viewer choose which ClickHouse connection raw SQL tiles, SQL query values filters, and data source variables use. It has no settings beyond its name.

### Data source and connection variables {#source-connection-variables}

Data source and connection variables stand in for a source or connection ID, rather than for a value in query text. Wherever a source or connection picker accepts them, the dashboard's variables are listed under a **Variables** group. Choosing one stores a `$name` reference that resolves to the viewer's current selection. This makes it possible to build one dashboard that switches between, for example, the logs of several environments, or several ClickHouse clusters.

| Used in | Accepts a data source variable | Accepts a connection variable |
|---------|--------------------------------|-------------------------------|
| Chart builder tiles | Source | — |
| Raw SQL tiles | Source | Connection |
| PromQL tiles | Source | — |
| SQL expression values filters | Data source, Applies to sources | — |
| PromQL label values filters | Data source | — |
| Ad hoc filters | Data sources, Applies to sources | — |
| SQL query values filters | Source | Connection |
| Data source variables | — | Connection |

A data source variable is only offered where at least one of its source kinds fits. For example, a PromQL tile only offers data source variables that allow PromQL sources.

Data source and connection variables are always single-select and required, since a tile can't query without a source or connection. Until a value is selected, the tiles and filters that reference the variable wait for it. Enable **Block every tile** to hold the whole dashboard instead. A [dashboard link](/clickstack/url-parameters#dashboard-filter-values) can select a source or connection by name as well as by ID.

<Note>
Alerts aren't available on tiles that use a data source or connection variable. Saving such a tile removes its alert.
</Note>

### Selection options {#filter-selection-options}

SQL expression values, static values, SQL query values, and PromQL label values filters have these additional options:

- **Single select** — only one value can be selected at a time.
- **Required** — tiles that use the filter, through its variable or through broadcast, don't load until the filter has a selection.
  - **Block every tile** — block every tile on the dashboard until the filter has a selection, not only the tiles that use it.

### Chained filters {#chained-filters}

A filter's own configuration can reference the dashboard's other variables, so that its values depend on another filter's selection. For example, a service filter can list only the services in the environment selected by an `environment` filter. Variables can be referenced in:

- A SQL expression values filter's **Dropdown values filter**, for example `$__filter(ResourceAttributes['deployment.environment'], $environment)`.
- A SQL query values filter's **SQL query**.
- A PromQL label values filter's **Series matchers**, for example `up{env="$env"}`.
- An ad hoc filter's **Keys and values filter**.
- Source and connection fields, through [data source and connection variables](#source-connection-variables).

When the referenced filter's selection changes, the dependent filter's values are queried again. While a referenced required filter has nothing selected, an ad hoc filter that depends on it can't add or edit conditions, and names the filter it's waiting on.

### Broadcasting {#broadcast-filters}

SQL expression values filters can broadcast their selection, and ad hoc filters always broadcast their conditions. With **Broadcast filter condition** enabled on a SQL expression values filter, the selected values are applied as a filter condition on the dashboard's tiles, without any tile explicitly referencing the filter. By default the condition reaches every tile. Use **Applies to sources** to restrict it to tiles that use a given set of sources — useful when the filter's expression only makes sense for some of the data on the dashboard.

Chart builder tiles pick up broadcast filters automatically. Raw SQL tiles must include the [`$__filters` macro](/clickstack/features/dashboards/sql-visualizations#dashboard-filter-macro) and have a source selected, since ClickStack cannot infer where the condition belongs in a hand-written query.

### Variables {#dashboard-variables}

Static values, SQL query values, and PromQL label values filters are always variables. A SQL expression values filter becomes a variable when **Available as variable** is enabled. A variable exposes the filter's selection to tile queries as `$variableName`. The **Variable name** defaults to the filter's display name with illegal characters removed, and can be overridden. Names must start with a letter and may contain only letters, digits, and underscores.

Ad hoc filters are never variables, and data source and connection variables are [references to a source or connection](#source-connection-variables) rather than values in query text.

Use a variable when broadcasting a `WHERE` condition is not what you want — for example, to put the value in a `SELECT` expression, a `HAVING` clause, or a join key, or to filter a tile on a column other than the filter's own expression.

#### Referencing a variable {#referencing-variables}

A variable expands to the values currently selected in its dropdown. The reference form controls the rendering:

| Reference             | Expands to                                                                                        | Empty selection |
|-----------------------|---------------------------------------------------------------------------------------------------|-----------------|
| `$name`, `${name}`    | The selected values, in the default format of the input: `sqlstring` in SQL, `lucene` in Lucene, `promql` in PromQL, and `markdown` in Markdown tiles. Braces delimit the name when it is followed by word characters, as in `${name}_total`. | As for that format (`NULL` in SQL) |
| `${name:sqlstring}`   | The selected values, single-quoted, comma-separated, and escaped as SQL values, eg. `'a', 'b'`    | `NULL`          |
| `${name:csv}`         | Unquoted and comma-separated: `a,b`. Not escaped for SQL.                                         | empty string    |
| `${name:regex}`       | A regex alternation, regex-escaped: `(a\|b)`.                                                     | `.*`            |
| `${name:lucene}`      | An `OR` of quoted terms, for Lucene inputs: `("a" OR "b")`.                                       | `("")`          |
| `${name:promql}`      | For a single-select filter, the selected value, for use in `label="$name"`. Otherwise a regex alternation, for use in `label=~"$name"`. | `.*` (empty string when single-select) |
| `${name:markdown}`    | For [Markdown tiles](#variables-in-markdown-tiles). Comma-separated, with Markdown punctuation escaped: `a, b`. | empty string    |

Because `$name` renders as `NULL` before anything is selected, prefer the following macros wherever a SQL predicate is expected. Both macros expand to `1=1` while their variable has no selection, so the query stays valid:

| Macro                                          | Description                                                                                                              |
|------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------|
| `$__filter($<variable>)`                        | Expands to `toString(<filter expression>) IN ($variable)` when values are selected for `variable`, and `1=1` otherwise.  |
| `$__filter(<expression>, $<variable>)`          | Expands to `<expression> IN ($variable)` when values are selected for `variable`, and `1=1` otherwise.                   |
| `$__conditionalAll(<condition>, $<variable>)`   | Expands to `<condition>` when the variable has a selection, `1=1` otherwise.                                             |

#### Using variables in chart builder tiles {#variables-in-builder-tiles}

Every SQL expression input in the chart builder accepts variable references: `SELECT` columns and per-series expressions, `WHERE`, `GROUP BY`, and `HAVING`. The editor autocompletes the dashboard's variables and shows what each reference expands to for the current selection.

Prefer using the `$__filter` and `$__conditionalAll` macros when in SQL mode, so that queries remain valid when variable selections are empty. Macros are not available in Lucene inputs — reference raw variables there instead (eg. `ServiceName:$service`).

In a Lucene input, whether the variable reference itself is quoted controls how a multi-value selection is matched. Given `$service` selected as `a,b`:

| Reference                | Expands to                             | Matching behavior                                                                            |
|---------------------------|-----------------------------------------|-----------------------------------------------------------------------------------------------|
| `ServiceName:$service`    | `ServiceName:("a" OR "b")`             | Substring match — translated to SQL as `ServiceName ILIKE '%a%' OR ServiceName ILIKE '%b%'`   |
| `ServiceName:"$service"`  | `(ServiceName:"a" OR ServiceName:"b")` | Exact match on each selected value                                                            |

Quote the variable reference — `Field:"$var"` — when the selected values should match `Field` exactly rather than as substrings.

#### Using variables in SQL tiles {#variables-in-sql-tiles}

Raw SQL tiles reference variables the same way, anywhere in the query:

```sql
SELECT
  $__timeInterval(TimestampTime) AS ts,
  count() AS count
FROM otel_logs
WHERE $__timeFilter(TimestampTime)
  AND $__filter(ServiceName, $service)
  AND $__conditionalAll(SeverityText NOT IN ($severity), $severity)
GROUP BY ts
ORDER BY ts ASC
```

See [SQL-based visualizations](/clickstack/features/dashboards/sql-visualizations#dashboard-variables) for the full list of macros available to SQL tiles.

<Note>
Alerts on a tile that references a dashboard variable evaluate with every variable in its empty state, not the values selected on the dashboard.

To preview a tile the way an alert evaluates it, turn off **Apply filters** above the chart preview in the tile editor; the switch is always off on a tile that has an alert.
</Note>

#### Using variables in Markdown tiles {#variables-in-markdown-tiles}

Markdown tiles accept variable references in their text and in link targets, for example `[Open the runbook](https://runbooks.example.com/$service)` with a single-select `service` filter. To insert values unescaped, for example inside a code block, use `${name:csv}`.
