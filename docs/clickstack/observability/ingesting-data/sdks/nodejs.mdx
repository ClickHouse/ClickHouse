The ClickStack Node.js SDK builds on the upstream OpenTelemetry SDK and auto-instrumentations. It adds console capture, uncaught exception capture, and telemetry flushing during shutdown. Applications that already configure OpenTelemetry can continue using their existing SDK and [configure OTLP export](/clickstack/observability/ingesting-data/opentelemetry).

<ClickStackIntegrates signals={['logs', 'metrics', 'traces']} />

## Install {#install}

Use Node.js **22.15 or later**. Install the SDK in your application:

```shell
npm install @clickhouse/clickstack-node
```

The package supports ES modules and CommonJS. npm installs its `@opentelemetry/api` peer dependency automatically.

## Configure your destination {#configure-destination}

Set the environment variables before starting your application. Use a base OTLP HTTP endpoint without `/v1/traces`, `/v1/logs`, or `/v1/metrics`; exporters append those paths.

<Tabs>
<Tab title="ClickHouse Observability">

Open **Team Settings → Data → Managed Telemetry** and copy the **OTLP HTTP endpoint** and **API key**. Use the exact HTTPS endpoint and port shown for your service:

```shell
export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
export OTEL_EXPORTER_OTLP_HEADERS='authorization=Bearer%20YOUR_INGESTION_API_KEY'
export OTEL_EXPORTER_OTLP_PROTOCOL='http/protobuf'
export OTEL_SERVICE_NAME='my-node-app'
```

</Tab>
<Tab title="Self configured">

Use your collector's OTLP HTTP endpoint and the ingestion key configured for its OTLP receiver. For collector setup, see [Ingesting with OpenTelemetry](/clickstack/observability/ingesting-data/opentelemetry#self-configured).

```shell
export OTEL_EXPORTER_OTLP_ENDPOINT='http://localhost:4318'
export OTEL_EXPORTER_OTLP_HEADERS='authorization=YOUR_INGESTION_API_KEY'
export OTEL_EXPORTER_OTLP_PROTOCOL='http/protobuf'
export OTEL_SERVICE_NAME='my-node-app'
```

This endpoint assumes the application and collector run on the same host. Replace it with an address reachable from your application when the collector runs elsewhere.

</Tab>
</Tabs>

## Start your application {#start-application}

Preload the SDK before your application imports the libraries it instruments:

```shell
node --import @clickhouse/clickstack-node/register server.js
```

Replace `server.js` with your application’s entry file. This command loads the SDK before your application starts and uses the environment variables configured above. It supports CommonJS and ES module applications.

You can now [verify ingestion](#verify-ingestion). The alternatives below are only needed if you want to start through an npm script or configure the SDK in code.

<Accordion title="Alternative startup methods">

`--require` is also supported. If you use `NODE_OPTIONS`, scope it to the application command so build tools do not start their own telemetry pipelines:

```shell
NODE_OPTIONS='--import @clickhouse/clickstack-node/register' npm start
```

Alternatively, create an instrumentation module and preload it. The environment variables from the previous section still configure export:

```javascript
// instrumentation.mjs
import { init } from '@clickhouse/clickstack-node';

init();
```

```shell
node --import ./instrumentation.mjs server.mjs
```

Use either the package's registration entry point or your own instrumentation module. Do not initialize a second SDK in the application. Static ES module imports run before the module body, so calling `init` above static imports in the same file does not guarantee initialization order.

</Accordion>

## Verify ingestion {#verify-ingestion}

Start your application, make requests to an instrumented route, and emit a console message. In ClickHouse Observability, select a recent time range and search Logs or Traces for `my-node-app`. Allow time for the metrics export interval before checking metrics.

If data is missing, check SDK diagnostics on stderr, the endpoint and authentication, and network connectivity. Ensure instrumentation loads before application dependencies. Bundled libraries cannot be automatically instrumented if the bundler inlines them; keep the SDK and instrumented dependencies external. Consult [SDK compatibility](https://github.com/ClickHouse/clickstack-node#compatibility) for TypeScript, ES module, framework, and bundler requirements.

## Configure instrumentation {#configure-instrumentation}

Standard OpenTelemetry environment variables retain their upstream meaning, including sampling, batching, exporters, and resource attributes. For example:

```shell
export OTEL_RESOURCE_ATTRIBUTES='deployment.environment.name=production'
```

Console output is captured by default. HTTP body capture is disabled by default; enable it only when appropriate for the data your application handles:

```shell
export CLICKSTACK_CAPTURE_HTTP_BODY='true'
```

Captured bodies can contain personal data and credentials. SDK redaction is best effort; retain collector-side redaction where needed. See the [SDK privacy options](https://github.com/ClickHouse/clickstack-node#privacy) for header capture, body limits, and sanitization.

To customize individual instrumentations, pass the upstream configuration map to `init` in your instrumentation module. Environment variables take precedence over the SDK's endpoint, service name, and API-key options.

For explicit process exits or AWS Lambda handlers, see the [SDK lifecycle documentation](https://github.com/ClickHouse/clickstack-node#lifecycle).

## Migrating from the HyperDX Node.js SDK {#migration}

Replace `@hyperdx/node-opentelemetry` with `@clickhouse/clickstack-node` and use the new registration entry point. Replace `HYPERDX_API_KEY` with `OTEL_EXPORTER_OTLP_HEADERS`, using the authorization format for your destination above.

The new SDK does not preserve every HyperDX helper or option. Review the [SDK migration guide](https://github.com/ClickHouse/clickstack-node/blob/main/docs/migration.md) before replacing logger integrations, error handlers, custom trace attributes, or sampling settings.
