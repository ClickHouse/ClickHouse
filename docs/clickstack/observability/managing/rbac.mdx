ClickHouse Observability includes role-based access control (RBAC) so you can define custom roles with fine-grained permissions over [dashboards](/clickstack/observability/features/dashboards/overview), [saved searches](/clickstack/observability/features/search), sources, [alerts](/clickstack/observability/features/alerts), webhooks, and notebooks. Permissions work at two levels: resource-level access (no access, read, or manage per resource type) and optional fine-grained rules that restrict access to individual resources by name, tag, or ID. The service ships with three built-in roles, and you can create custom roles to match your team's needs.

## User access prerequisites {#user-access-prerequisites}

The service authenticates through ClickHouse Cloud. Users must belong to your ClickHouse Cloud organization and have access to the Observability service. See [Manage cloud users](/products/cloud/guides/security/cloud-access-management/manage-cloud-users) for organization membership.

The Cloud SQL Console access levels map to Observability access as follows:

| Cloud SQL Console access | Observability access |
|---|---|
| **SQL Console Admin** (Full Access) | Full access to the service. Required for enabling [alerts](/clickstack/observability/features/alerts). |
| **SQL Console Read Only** (Read Only) | Can view observability data and create dashboards. |
| **No access** | Can't access the service. |

Open **Team Settings → Members & Roles** to view team members and their current Observability roles. Select **Manage in Console** to manage organization membership in ClickHouse Cloud.

## Built-in roles {#built-in-roles}

The service includes three system roles. You can't edit or delete these. The Admin role is assigned to the team creator by default.

| Permission | Admin | Member | ReadOnly |
|---|:---:|:---:|:---:|
| Read all resources | ✓ | ✓ | ✓ |
| Manage dashboards | ✓ | ✓ | |
| Manage saved searches | ✓ | ✓ | |
| Manage sources | ✓ | ✓ | |

| Manage users and invitations | ✓ | | |

## Assigning roles to team members {#assigning-roles}
The **Members & Roles** tab in **Team Settings** lists team members with their current role. To change a role, click **Edit** next to the user's name and select a new role. Each user has exactly one role.

### Default new user role {#default-new-user-role}
Under **Team Settings** → **Members & Roles**, use **Default New User Role** below the roles list to choose the role assigned to users who auto-join the team. If no default is set, new users receive the **Member** role.

## Role permissions {#role-permissions}

### Resource permissions {#resource-permissions}

Each role grants an access level per resource type. The three levels are:

| Access level | What it allows |
|---|---|
| **No Access** | The resource type is hidden from the role entirely. |
| **Read** | View the resource and its configuration, but not create, edit, or delete it. |
| **Manage** | Full control — create, edit, and delete resources of that type. |

The resource types you can control are:

- **[Dashboards](/clickstack/observability/features/dashboards/overview)** — saved dashboard layouts and charts.
- **[Saved searches](/clickstack/observability/features/search)** — persisted log/trace/event queries.
- **Sources** — data sources used to query observability data.
- **[Alerts](/clickstack/observability/features/alerts)** — alert rules and their notification settings.
- **Webhooks** — outbound notification destinations (such as Slack, PagerDuty, and generic HTTP endpoints) that [alerts](/clickstack/observability/features/alerts) deliver to. This doesn't refer to the observability API.
- **Notebooks** — collaborative investigation notebooks.

### Administrative permissions {#administrative-permissions}

In addition to resource permissions, each role includes two administrative settings:

- **Users** (No Access · Read) — controls whether the role can view team members and their roles. Manage organization membership through **Manage in Console**.
- **Team** (Read · Manage) — controls whether the role can view or modify team-level settings such as security policies and RBAC configuration.

### Fine-grained access rules {#fine-grained-access-rules}

Dashboards, Saved Searches, Sources, and Notebooks support fine-grained controls that restrict access to individual resources within a category. Use these when you need to limit a role to specific resources rather than granting blanket access to the entire resource type.

#### Default access vs. fine-grained controls {#access-control-modes}

Each resource type has an **Access Control Mode**:

- **Default Access** — applies a single access level (No Access, Read, or Manage) to all resources of that type.
- **Fine-Grained Controls** — lets you define access rules that match specific resources by condition. Resources that don't match any rule default to no access.

To switch modes, click the chevron to expand a resource type in the role editor, then toggle the **Access Control Mode**.

#### Configuring access rules {#configuring-access-rules}

Each access rule consists of a **condition** and an **access level**. Conditions match resources by their properties:

<div className="ch-image-md">

<Frame>

![Condition tooltip: match resources by Name or Tag (shown by the title) or by ID (found in the URL)](/images/clickstack/rbac/condition-tip.webp)

</Frame>

</div>

| Condition field | Operators | What it matches | Example |
|---|---|---|---|
| **Name** | `is`, `contains` | The display name of the resource — for example, the dashboard title. | Name contains `production` — matches any dashboard with "production" in its title. |
| **Tag** | `is`, `contains` | Tags assigned to the resource via the tag panel in the top-right corner of the resource view. Available for Dashboards, Saved Searches, and Notebooks only. | Tag is `critical` — matches resources tagged "critical." |
| **ID** | `is`, `contains` | The resource identifier, found in the URL bar when you open the resource. | ID is `abc123` — matches a single specific resource. |

The following screenshot shows both the dashboard ID highlighted in the URL bar and a "TESTING" tag visible in the tag panel (top-right).

<div className="ch-image-lg">

<Frame>

![Dashboard showing the resource ID in the URL bar and a tag in the top-right corner](/images/clickstack/rbac/dashboard-id-and-tag-example.webp)

</Frame>

</div>

You can add multiple rules per resource type. Each rule is checked independently using OR logic — a resource is accessible if it matches **any** rule. Resources that don't match any rule aren't accessible.

<div className="ch-image-md">

<Frame>

![Access rules with OR logic tooltip](/images/clickstack/rbac/access-rules-tip.webp)

</Frame>

</div>

**Example**: To give a role read-only access to testing dashboards, expand Dashboards, switch to Fine-Grained Controls, and add two rules:
- **Name** `contains` `testing` with access level **Read**
- **Tag** `is` `testing` with access level **Read**

A dashboard that matches either rule is accessible.

## Security policies {#security-policies}

Under **Team Settings → Members & Roles → Security Policies**, **Disable data exports** hides download and copy controls for log data, including row details, for everyone on the team. Users can still select text on screen, and the API and MCP server still return data. This setting does not prevent access to the underlying data.

Generative AI controls are under **Team Settings → API & Agents → Configure Generative AI**. See [Configure Generative AI](/clickstack/observability/managing/config#generative-ai) for details.
