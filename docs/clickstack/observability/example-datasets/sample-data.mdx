This guide demonstrates fully managed ClickHouse Observability using a sample dataset.

Before you begin, complete the [Getting started guide](/clickstack/observability/getting-started).

<Steps>
<Step title="Copy your connection details" id="copy-connection-details">

Open **Team Settings** and scroll to **Managed Telemetry**. Under **OpenTelemetry Collector**, use the **URL** tab shown below to copy the OTLP HTTP endpoint and API key. Select **Reveal key** to view the full values.

<Image img="/images/clickstack/getting-started/observability-managed-telemetry.png" alt="Team Settings showing Managed Telemetry with masked endpoint and API key connection details" size="lg" />

Set the following variables in the terminal where you will load the sample data. Use the base endpoint without a signal path such as `/v1/logs`, and use the API key as shown in the **URL** tab. The upload command adds the `Bearer` prefix.

```shell
export CLICKSTACK_OTLP_ENDPOINT='<your-otlp-http-endpoint>'
export CLICKSTACK_API_KEY='<your-api-key>'
```

</Step>
<Step title="Download sample data" id="download-sample-data-managed">

In order to populate the UI with sample data, download the following file:

[Sample data](https://storage.googleapis.com/hyperdx/sample.tar.gz)

```shell
# curl
curl -O https://storage.googleapis.com/hyperdx/sample.tar.gz
# or
# wget https://storage.googleapis.com/hyperdx/sample.tar.gz
```

This file contains example logs, metrics, and traces from our public [OpenTelemetry demo](https://github.com/ClickHouse/opentelemetry-demo) - a simple e-commerce store with microservices. Copy this file to a directory of your choosing.
</Step>
<Step title="Load sample data" id="load-sample-data-managed">

Send the downloaded data directly to your managed OTLP HTTP endpoint. You do not need to deploy a collector for this example.

Run the following command from the directory containing `sample.tar.gz`:

```shell
for filename in $(tar -tf sample.tar.gz); do
  endpoint="${CLICKSTACK_OTLP_ENDPOINT%/}/v1/${filename%.json}"
  echo "loading ${filename%.json}"
  tar -xOf sample.tar.gz "$filename" | while read -r line; do
    printf '%s\n' "$line" | curl --fail-with-body -sS -X POST "$endpoint" \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer ${CLICKSTACK_API_KEY}" \
    --data-binary @-
  done
done
```
This simulates OTLP log, trace, and metric sources sending data to the managed endpoint. In production, these sources may be application SDKs, agents, or OpenTelemetry Collectors.

Return to [Search](/clickstack/observability/features/search) to view the loaded data. Select the **Logs** source and a time range that includes the sample events' timestamps. The screenshot below shows sample logs arriving in **Live Tail**:

<Image img="/images/clickstack/getting-started/observability-sample-data-search.png" alt="Search showing loaded sample logs from the e-commerce demo services" size="lg"/>

Data loading will take a few minutes. Allow for the load to be completed before progressing to the next steps.
</Step>
<Step title="Explore sessions" id="explore-sessions-managed">

Suppose we have reports that our users are experiencing issues paying for goods. We can view their experience using session replay.

Select **Client Sessions** from the left menu and set a time range that includes the loaded sample sessions.

<Image img="/images/clickstack/getting-started/observability-sample-data-sessions.png" alt="Client Sessions showing sample sessions with an error count highlighted" size="lg"/>

This view lists sessions from the demo store, including anonymous sessions and sessions identified by an email address.

Some sessions have a nonzero error count. In this example, the highlighted session has one error.

Select the highlighted session to open its replay. Use the play button at the bottom of the player to watch the session.

<Image img="/images/clickstack/getting-started/observability-sample-data-replay.png" alt="Session replay showing the OpenTelemetry demo storefront and navigation events" size="lg"/>

The replay shows the user navigating the site, adding items to their cart. Feel free to skip to later in the session where they attempt to complete a payment.

<Tip>
Error events are marked in red in the event list.
</Tip>

Scroll to the bottom of the event list on the left. The highlighted `POST /api/checkout` request returned HTTP `500`, with a console error recorded at the same time.

<Image img="/images/clickstack/getting-started/observability-sample-data-checkout-error.png" alt="Session replay highlighting the failed POST request to /api/checkout and associated console error" size="lg"/>

Select the failed `POST /api/checkout` event to inspect the request and its trace.
</Step>
<Step title="Explore traces" id="explore-traces-managed">

Open the **Trace** tab to see the distributed trace, including related spans and correlated logs.

<Image img="/images/clickstack/getting-started/observability-sample-data-trace.png" alt="Trace waterfall showing the checkout request with its spans, correlated logs, and errors" size="lg"/>

Scroll down the trace and select the `oteldemo.PaymentService/Charge` span in the `checkout` service.

<Image img="/images/clickstack/getting-started/observability-sample-data-payment-span.png" alt="Selected payment request span showing an expired-card error in its attributes" size="lg"/>

In the **Overview** tab, inspect **Top Level Attributes**. The `StatusCode` is `Error`, and the `StatusMessage` indicates that the credit card has expired.

<Image img="/images/clickstack/getting-started/observability-sample-data-span-attributes.png" alt="Overview attributes showing an Error status and a message that the credit card has expired" size="lg"/>

In the trace, select the `payment` error log beneath the payment service span. Its row has a log icon, distinguishing it from the error span event. In **Overview**, the log's **Body** confirms that the credit card has expired. The attributes identify the `payment` service and an `error` severity, providing context alongside the trace.

<Image img="/images/clickstack/getting-started/observability-sample-data-correlated-log.png" alt="Correlated payment error log showing the expired-card message and log attributes" size="lg"/>

We've traced this failed checkout to a payment request rejected because the credit card had expired.
</Step>
<Step title="Explore logs" id="explore-logs-managed">

To investigate other payment failures, return to [Search](/clickstack/observability/features/search).

Select **Logs** as the source and choose `payment` under the **ServiceName** filter. Use a time range that includes the session you investigated.

<Image img="/images/clickstack/getting-started/observability-sample-data-payment-logs.png" alt="Search filtered to the payment service showing expired-card and Visa cache-full errors alongside successful transactions" size="lg"/>

The results include the expired-card error from the session we investigated, as well as repeated `Visa cache full: cannot add new item.` errors. To see when errors occur across the payment service, chart these error logs over time.
</Step>
<Step title="Chart payment errors" id="chart-payment-errors">

Open **Chart Explorer**, select **Time Series**, and choose **Logs** as the data source. Select **Count of Events** as the aggregation.

In **Where**, select **Lucene** and enter the following filter:

```text
SeverityText:"error" ServiceName:"payment"
```

Set a time range covering the sample data and select **Run**.

<Image img="/images/clickstack/getting-started/observability-sample-data-payment-errors-chart.png" alt="Chart Explorer counting payment service error logs over time using a Lucene filter" size="lg"/>

The chart shows the number of matching error logs in each time interval. It includes all errors from the `payment` service, including expired-card and cache-full errors. These are log-event counts, not a count of unique failed payments.
</Step>
</Steps>
