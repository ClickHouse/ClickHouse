This guide has been adapted for Self Configured ClickHouse Observability and requires verification. Confirm SDK compatibility, feature differences, collector endpoints, and authentication before using the migration examples.

The Elastic Stack provides two types of language SDKs for instrumenting applications:

1. **[Elastic Official APM agents](https://www.elastic.co/docs/reference/apm-agents/)** – These are built specifically for use with the Elastic Stack. There is currently no direct migration path for these SDKs. Applications using them will need to be re-instrumented using the corresponding [Self Configured ClickHouse Observability SDKs](/clickstack/self-configured/ingesting-data/sdks/index).

2. **[Elastic Distributions of OpenTelemetry (EDOT SDKs)](https://www.elastic.co/docs/reference/opentelemetry/edot-sdks/)** – These are Elastic's distributions of the standard OpenTelemetry SDKs, available for .NET, Java, Node.js, PHP, and Python. If your application is already using an EDOT SDK, you don't need to re-instrument your code. Instead, you can simply reconfigure the SDK to export telemetry data to the ClickHouse Observability Collector that you operate. See ["Migrating EDOT SDKs"](#migrating-edot-sdks) for further details.

<Info>
**Use Self Configured ClickHouse Observability SDKs where possible**

While standard OpenTelemetry SDKs are supported, we strongly recommend using the [**SDKs documented for Self Configured ClickHouse Observability**](/clickstack/self-configured/ingesting-data/sdks/index) for each language. These distributions include additional instrumentation, enhanced defaults, and custom extensions designed to work seamlessly with the Self Configured ClickHouse Observability pipeline and UI. By using the Self Configured ClickHouse Observability SDKs, you can unlock advanced features such as exception stack traces that aren't available with vanilla OpenTelemetry or EDOT SDKs.
</Info>

## Migrating EDOT SDKs {#migrating-edot-sdks}

Similar to the Self Configured ClickHouse Observability OpenTelemetry-based SDKs, the Elastic Distributions of the OpenTelemetry SDKs (EDOT SDKs) are customized versions of the official OpenTelemetry SDKs. For example, the [EDOT Python SDK](https://www.elastic.co/docs/reference/opentelemetry/edot-sdks/python/) is a vendor-customized distribution of the [OpenTelemetry Python SDK](https://opentelemetry.io/docs/languages/python/) designed to work seamlessly with Elastic Observability.

Because these SDKs are based on standard OpenTelemetry libraries, migration to Self Configured ClickHouse Observability is straightforward - no re-instrumentation is required. You only need to adjust the configuration to direct telemetry data to the ClickHouse Observability Collector.

Configuration follows the standard OpenTelemetry mechanisms. For Python, this is typically done via environment variables, as described in the [OpenTelemetry Zero-Code Instrumentation docs](https://opentelemetry.io/docs/zero-code/python/configuration/).

A typical EDOT SDK configuration might look like this:

```shell
export OTEL_RESOURCE_ATTRIBUTES=service.name=<app-name>
export OTEL_EXPORTER_OTLP_ENDPOINT=https://my-deployment.ingest.us-west1.gcp.cloud.es.io
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=ApiKey P....l"
```

To migrate to Self Configured ClickHouse Observability, point the endpoint to your collector. The example below assumes an HTTP OTLP collector running on the same host as the application. For a remote collector, replace the URL with its reachable endpoint and appropriate TLS configuration:

```shell
export OTEL_RESOURCE_ATTRIBUTES=service.name=<app-name>
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
# If authentication is enabled, set OTLP_AUTH_TOKEN in this shell
# to the same token configured on the receiving collector.
export OTEL_EXPORTER_OTLP_HEADERS="authorization=${OTLP_AUTH_TOKEN}"
```

The authorization header uses the token you configured on the collector with `OTLP_AUTH_TOKEN`; it is not a key generated by the observability UI. See [Securing the collector](/clickstack/self-configured/ingesting-data/collector#securing-the-collector).

If collector authentication is not enabled, omit the authorization header and clear the previous Elastic header from the sending process:

```shell
unset OTEL_EXPORTER_OTLP_HEADERS
```
