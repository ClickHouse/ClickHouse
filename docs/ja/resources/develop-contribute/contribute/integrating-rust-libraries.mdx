ここでは、BLAKE3ハッシュ関数の連携を例に、Rustライブラリの連携方法を説明します。

連携の最初の手順は、`contrib/<library>-cmake` に空のRustプロジェクトを作成し、必要なライブラリをその Cargo.toml に追加することです。このプロジェクトは、`contrib/rust-contrib-workspace` にある cargo ワークスペースのメンバーになります。`[package]` の下に `workspace = "../rust-contrib-workspace"` を追加し、`contrib/rust-contrib-workspace/Cargo.toml` の `members` にそのフォルダーを追加してください。`crate-type` は指定せず、通常のライブラリのままにします。各メンバーは単独のライブラリとしてはビルドされません。ワークスペースのルートパッケージである `_ch_rust_workspace` が有効なすべてのメンバーを再エクスポートし、これが ClickHouse がリンクする唯一の静的ライブラリとなります。`contrib/rust-contrib-workspace/Cargo.toml` で、ルートパッケージにそのメンバー用の機能と任意の依存関係 (`blake3 = ["dep:_ch_rust_blake3"]` および `_ch_rust_blake3 = { path = "../blake3-cmake", optional = true }`) を追加し、`contrib/rust-contrib-workspace/src/lib.rs` で再エクスポートします (`#[cfg(feature = "blake3")] pub use _ch_rust_blake3;`)。

次に、Corrosion ライブラリを使用して、そのライブラリを CMake にリンクする必要があります。まず、`add_contrib` を使って、ワークスペースの他のメンバーと並べる形でライブラリフォルダーを `contrib/CMakeLists.txt` に追加します。その後、ライブラリディレクトリに CMakeLists.txt ファイルを追加する必要があります。その中で、`clickhouse_add_rust_member` を使ってメンバーを追加します。これにより、ワークスペースの静的ライブラリをリンクするインターフェイスターゲットが作成され、ルートパッケージの機能が有効化されます。ルートパッケージは、`contrib/rust-contrib-workspace/CMakeLists.txt` がすべてのメンバーの後に Corrosion で import します。BLAKE3 の場合は、次のようになります。

```CMake
clickhouse_add_rust_member(_ch_rust_blake3 FEATURE blake3)

target_include_directories(_ch_rust_blake3 INTERFACE include)
add_library(ch_rust::blake3 ALIAS _ch_rust_blake3)
```

したがって、このメンバー用の CMake ターゲットを作成し、その後でより扱いやすい名前を付けます。`_ch_rust_blake3` という名前は Cargo.toml に由来しており、そこではプロジェクト名 (`name = "_ch_rust_blake3"`) として使われていることに注意してください。

Rust のデータ型は C/C++ のデータ型と互換性がないため、この空のライブラリプロジェクトを使って、C/C++ から受け取ったデータを変換し、ライブラリのメソッドを呼び出し、さらに出力データを逆変換するためのシムメソッドを作成します。たとえば、BLAKE3 では次のメソッドを実装しました。

```rust
#[no_mangle]
pub unsafe extern "C" fn blake3_apply_shim(
    begin: *const c_char,
    _size: u32,
    out_char_data: *mut u8,
```

```rust
#[no_mangle]
pub unsafe extern "C" fn blake3_apply_shim(
    begin: *const c_char,
    _size: u32,
    out_char_data: *mut u8,
) -> *mut c_char {
    if begin.is_null() {
        let err_str = CString::new("input was a null pointer").unwrap();
        return err_str.into_raw();
    }
    let mut hasher = blake3::Hasher::new();
    let input_bytes = CStr::from_ptr(begin);
    let input_res = input_bytes.to_bytes();
    hasher.update(input_res);
    let mut reader = hasher.finalize_xof();
    reader.fill(std::slice::from_raw_parts_mut(out_char_data, blake3::OUT_LEN));
    std::ptr::null_mut()
}
```

このメソッドは、C互換の文字列、そのサイズ、出力文字列へのポインタを入力として受け取ります。次に、C互換の入力を実際のライブラリメソッドで使われる型に変換してそれらを呼び出します。その後、ライブラリメソッドの出力を再びC互換の型に変換する必要があります。このケースでは、ライブラリが `fill()` メソッドによるポインタへの直接書き込みをサポートしていたため、変換は不要でした。ここでの主なアドバイスは、メソッド数をできるだけ少なくすることです。そうすれば、各メソッド呼び出しで必要になる変換が減り、オーバーヘッドも抑えられます。

`#[no_mangle]` 属性と `extern "C"` は、この種のすべてのメソッドで必須である点にも注意してください。これらがないと、C/C++互換で正しくコンパイルできません。さらに、これらは連携の次のステップでも必要になります。

シムメソッドのコードを記述したら、次はライブラリ用のヘッダーファイルを準備する必要があります。これは手動で行うこともできますし、cbindgen ライブラリを使って自動生成することもできます。cbindgen を使用する場合は、build.rs のビルドスクリプトを作成し、cbindgen を build-dependency に追加する必要があります。

ヘッダーファイルを自動生成できるビルドスクリプトの例:

```rust
    let crate_dir = env::var("CARGO_MANIFEST_DIR").unwrap();

    let package_name = env::var("CARGO_PKG_NAME").unwrap();
    let output_file = ("include/".to_owned() + &format!("{}.h", package_name)).to_string();

    match cbindgen::generate(&crate_dir) {
        Ok(header) => {
            header.write_to_file(&output_file);
        }
        Err(err) => {
            panic!("{}", err)
        }
    }
```

## このリポジトリでのヘッダー生成 {#generating-the-header-in-this-repository}

上記のビルドスクリプトはビルドのたびにヘッダーをソースツリーに書き込むため、チェックすべきものが何も残りません。Rust 側と一致しなくなったコミット済みのヘッダーは、ローカルで単に上書きされるだけで、他の全員にとっては誤ったままになります。そのため、このリポジトリのクレートでは、代わりに次の 2 つの方式のいずれかを使用しています。

* `contrib/delta-kernel-rs` のように、ヘッダーをビルドディレクトリに生成し、`target_include_directories` でそのディレクトリを指定する方式。何もコミットされないため、古くなることもありません。
* `contrib/vortex-cmake` のように、ヘッダーをコミットしておき、ビルドスクリプトで新たに生成したヘッダーと比較して、差異がある場合はビルドを失敗させる方式。FFI の両側はシンボル名でリンクされる別々の翻訳単位であるため、片側だけでシグネチャを変更してもコンパイルエラーにはならず、気付かれないまま未定義動作となります。この比較があるからこそ、再生成し忘れることがなくなります。コミット済みファイルを書き換える環境変数を用意しておき、更新が 1 つのコマンドで済むようにしてください。

`contrib/rust-contrib-workspace` のクレートに `cbindgen` を追加する前に、次の 2 点を把握しておいてください。

* バージョンは厳密に固定してください。出力はパッチリリース間でも変わるため、緩いバージョン指定にすると、チェックが実際の差分ではなくジェネレーターのバージョンの違いを報告するようになります。また、そのバージョンは `contrib/rust_vendor` に含まれているものである必要があります。そうでない場合は、`contrib/rust-contrib-workspace/vendor.sh` を再実行し、サブモジュールを更新する必要があります。
* `cbindgen::generate` でクレートを処理するのではなく、`Builder::with_src` でソースファイルをパースしてください。クレートを指定する方法では、cbindgen がネストされたプロセスで `cargo metadata` を実行しますが、そのプロセスは cargo にベンダリングされたソースを参照させる `--config` を引き継ぎません。

また、C 互換にするすべての要素には、属性 #[no&#95;mangle] と `extern "C"` を使用してください。これがないと、ライブラリが正しくコンパイルされず、cbindgen によるヘッダーの自動生成も行われません。

これらの手順をひととおり終えたら、小規模なプロジェクトでライブラリをテストし、互換性やヘッダー生成に関する問題がないか確認できます。ヘッダー生成中に問題が発生した場合は、`cbindgen.toml` ファイルで設定を調整してみてください (テンプレートはこちらです: [https://github.com/eqrion/cbindgen/blob/master/template.toml](https://github.com/eqrion/cbindgen/blob/master/template.toml)) 。

BLAKE3 の統合時に発生した問題についても、触れておく必要があります。
MemorySanitizer は、Rust の一部の変数が初期化されているかどうかを判別できないため、誤検知を引き起こすことがあります。この問題は、一部の変数についてより明示的に定義した メソッド を記述することで解決されました。ただし、この メソッド の実装は低速であり、MemorySanitizer のビルドを修正するためにのみ使用されます。
