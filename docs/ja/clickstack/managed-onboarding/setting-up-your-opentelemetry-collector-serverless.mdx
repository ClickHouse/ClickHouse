<Info>
  **概要**

  既に OpenTelemetry Collector を運用している場合は、サービスの「はじめに」ページにあるエクスポーターのスニペットを Collector の設定にコピーし、そのエクスポーターをパイプラインに追加して再読み込みしてください。既存のレシーバーとプロセッサはそのまま動作し、収集されたデータはすべて ClickHouse オブザーバビリティに送信されます。

  所要時間: 約 10 分
</Info>

ClickHouse オブザーバビリティのサービスは作成済みであるものとします。このガイドは、データ収集を担う OpenTelemetry Collector を既に環境内で運用している場合を対象としています。たとえば次のようなケースです。

* **インフラストラクチャのテレメトリー。** ホストの CPU、メモリ、ディスク、ネットワークのメトリクス、およびディスク上のログファイル。
* **Kubernetes。** コンテナログ、kubelet およびクラスターのメトリクス、Kubernetes イベント。
* **既存のメトリクスエンドポイント。** サービスが既に公開している Prometheusエンドポイントのスクレイピング。
* **[ゲートウェイ](/ja/clickstack/ingesting-data/collector#collector-roles)。** ネットワーク内に置かれた単一のエンドポイントで、SDK やエージェント型コレクターから OTLP を受信し、バッチ処理したうえで 1 か所から転送します。

collector が何を収集していても、接続方法は同じです。サービスのマネージド OTLP エンドポイントを宛先とする `otlp_http` エクスポーターを 1 つ追加するだけです。レシーバー、プロセッサ、既存のエクスポーターは変更不要なため、評価期間中は現在のバックエンドと ClickHouse オブザーバビリティの両方に並行して送信できます。その後のインジェスト、スキーマ、ストレージ、最適化、スケーリングは ClickHouse オブザーバビリティが担います。

<Note>
  **collector をまだ導入していない場合**

  使い始めるのに collector は必須ではありません。アプリケーションから OpenTelemetry データをマネージドエンドポイントに直接エクスポートできます。詳しくは [OpenTelemetry によるアプリケーションの計装](/ja/clickstack/managed-onboarding/instrument-application-serverless) を参照してください。インフラストラクチャのテレメトリー収集を始めたい場合は、[ローカルのログとメトリクス](/ja/clickstack/observability/example-datasets/local-data) と [Kubernetesの監視](/ja/clickstack/observability/example-datasets/kubernetes) に、そのままデプロイできる完全なコレクター設定がそれぞれ掲載されています。
</Note>

## 前提条件 {#prerequisites}

* ClickHouse オブザーバビリティのサービス。まだお持ちでない場合は、[Getting Started ガイド](/ja/clickstack/observability/getting-started)の手順に従って作成してください。
* 設定の変更と再起動が可能な OpenTelemetry Collector。`otlp_http` エクスポーターはコアの collector に含まれているため、ベンダー提供のビルドを含め、どのディストリビューションでも使用できます。
* collector のホストからサービスのテレメトリーエンドポイントに対して、ポート `4318` でアウトバウンドの HTTPS 通信が可能であること。

## collector を接続する {#connect-your-collector}

<Steps>
  <Step title="エクスポーター設定をコピーする" id="copy-exporter-configuration">
    ClickHouse オブザーバビリティのサービスを開きます。データが届くまでは、**Start sending telemetry** ページが表示されます。

    <div className="ch-image-lg">
      <Frame>
        ![現在のサービスにまだデータがなく、Use an existing OpenTelemetry setup、Instrument with AI、Follow setup guides の3つのオプションが表示されている Start sending telemetry ページ](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    **Use an existing OpenTelemetry setup** で **View connection details** を選択し、**Collector config** タブを開きます。サービス用にあらかじめ用意されたエクスポーターブロックが表示されます。**Reveal key** を選択して API キー全体を表示してから、コピーボタンでコピーします。

    <div className="ch-image-md">
      <Frame>
        ![Collector config タブが選択された Set up OpenTelemetry ダイアログ。マスクされたエンドポイントと Bearer 認証ヘッダーを含む otlphttp エクスポーターが表示されている](/images/clickstack/getting-started/observability-collector-config.png)
      </Frame>
    </div>

    スニペットは次のような形式です:

    ```yaml
    exporters:
      otlphttp:
        endpoint: https://YOUR_OTEL_ENDPOINT:4318
        headers:
          authorization: Bearer <your-api-key>
    ```

    ここで重要な点が2つあります。1つ目に、エンドポイントはベース URL です。シグナルパスはエクスポーターが自動的に付加するため、`/v1/logs`、`/v1/traces`、`/v1/metrics` を追記しないでください。2つ目に、ヘッダーの値には `Bearer` プレフィックスが含まれます。

    UI ではエクスポーター名が `otlphttp` と表示されます。最近の collector リリースでは `otlp_http` という名前になっており、`otlphttp` は非推奨のエイリアスとして残されているため、どちらでも動作します。以下の例では現在の名前を使用します。

    同じ値は、**チーム設定 → マネージドテレメトリー** でいつでも確認できます。
  </Step>

  <Step title="エクスポーターを追加する" id="add-the-exporter">
    コレクター設定の `exporters` セクションにこのブロックを追加します。キーを環境変数から渡せば、ファイルに直接記載せずに済みます:

    ```yaml
    exporters:
      otlp_http:
        endpoint: ${env:CLICKSTACK_OTLP_ENDPOINT}
        headers:
          authorization: "Bearer ${env:CLICKSTACK_API_KEY}"
    ```

    設定に `otlp_http` という名前のエクスポーターがすでに存在する場合は、`otlp_http/clickhouse` のような別の名前を付け、次のステップではその名前を使用してください。

    collector を Kubernetes 上で実行している場合は、キーをシークレットに保存し、`extraEnvs` または Pod spec で両方の値を渡します。OpenTelemetry Helm チャートを使ったこの構成例は、[Kubernetes の監視](/ja/clickstack/observability/example-datasets/kubernetes) ガイドで紹介しています。
  </Step>

  <Step title="パイプラインに追加する" id="add-to-pipelines">
    ClickHouse オブザーバビリティに送りたいデータを扱うすべてのパイプラインに、エクスポーターを追記します。既存のエクスポーターを残しておけば、両方の送信先を並行して運用できます:

    ```yaml
    service:
      pipelines:
        logs:
          receivers: [otlp, file_log]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        metrics:
          receivers: [otlp, host_metrics, prometheus]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
    ```

    レシーバーとプロセッサは変更不要です。変更するのはエクスポーターのリストだけです。

    <Info>
      **エージェントとゲートウェイの役割**

      各ホストでエージェント コレクターを実行し、中央のゲートウェイに転送している場合は、ゲートウェイのみを変更してください。エージェントはこれまでどおりゲートウェイへ送信し続けます。
    </Info>
  </Step>

  <Step title="再読み込みしてログを確認する" id="reload-and-check">
    collector の設定の渡し方(systemd ユニット、Docker の `-e` フラグ、Kubernetes シークレットなど)に応じて、collector の環境で `CLICKSTACK_OTLP_ENDPOINT` にエンドポイント URL を、`CLICKSTACK_API_KEY` にキーを設定します。その後、collector を再起動または再読み込みし、ログにエクスポートエラーが出ていないか確認します:

    * `401` または `403` 応答は、API キーが誤っているか、`Bearer` プレフィックスが欠けていることを示します。
    * `404` 応答は通常、`/v1/logs` などのシグナルパスがエンドポイントに追記されていることを示します。
    * `no such host` や TLS エラーは、エンドポイントの入力ミス、またはポート `4318` でのアウトバウンド接続がブロックされていることが原因と考えられます。

    これで、collector がすでに収集していたすべてのデータが、サービスにも送信されるようになります。
  </Step>
</Steps>

## データの受信を確認する {#confirm-data-is-arriving}

サービスの **Start sending telemetry** ページに戻り、**Check for data** を選択します。テレメトリーが届くと、サービスの状態が **Data received** に変わり、**Start exploring** が選択できるようになります。

**Start exploring** を選択して **検索** を開きます。**Logs** ログソースを選択し、時間範囲を **Last 15 minutes** に設定したうえで、collector が送信している `ServiceName` でフィルタします。続いて **Chart Explorer** でログソースを **Metrics** に切り替え、メトリクスのレシーバーからもデータが届いていることを確認します。

## 何も表示されない場合 {#if-nothing-shows-up}

* まず collector のログを確認してください。認証、エンドポイント、TLS に関する問題は、いずれも上記のエラーコードとともにログに出力されます。
* データの送信元となるすべてのパイプラインで、`exporters` に `otlp_http` が含まれていることを確認してください。定義されていてもパイプラインから参照されていない receiver は、何も収集しません。
* collector が実際に再読み込みされたことを確認してください。ディストリビューションによっては、新しいエクスポーターを反映するために、設定の再読み込みではなく再起動が必要な場合があります。
* **検索** で時間範囲を広げ、フィルタをすべて解除してください。デフォルトのログソースが **Logs** ではなく **Traces** に設定されている可能性があります。
* サービス自体に問題がないかを確認するには、**チーム設定 → マネージドテレメトリー** に移動し、**Send a Test Log** を使用してください。そのログが **検索** に表示されれば、サービスはデータを受信しているため、問題は collector とエンドポイントの間にあります。
* collector 側の問題を切り分けるには、[サンプルデータの送信](#send-sample-data) の `telemetrygen` ジェネレーターの送信先を、サービスではなく collector 自身の OTLP レシーバーに変更してください。送信先は認証スキームを付けずに `host:port` 形式で指定し、`--otlp-http` は付けません(例: `--otlp-endpoint localhost:4317 --otlp-insecure`)。そのデータが届けば collector のエクスポーターは正常であり、問題はそれより上流にあります。

## collector でさらに多くのデータを収集する {#collect-more}

エクスポーターを設定しておけば、receiver を追加するたびに、そのデータが同じパイプラインを通じてサービスに送られます。

* [ローカルのログとメトリクス](/ja/clickstack/observability/example-datasets/local-data): `file_log` receiver でログファイルを追跡し、`host_metrics` receiver で CPU、メモリ、ディスク、ネットワークのメトリクスを収集する完全な設定例です。
* [Kubernetesの監視](/ja/clickstack/observability/example-datasets/kubernetes): コンテナログと kubelet メトリクスを収集するデーモンセットと、クラスターのメトリクスおよびイベントを収集するデプロイメントを、OpenTelemetry Helm チャートでインストールします。
* **Prometheusエンドポイント。** 既存の `scrape_configs` を指定した [`prometheus` receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/prometheusreceiver) を `metrics` パイプラインに追加します。スクレイプされた系列は OpenTelemetry メトリクスとして取り込まれ、Chart Explorer に表示されます。
* **ゲートウェイ経由の SDK。** `OTEL_EXPORTER_OTLP_ENDPOINT` に collector のアドレス (例: `http://otel-collector.observability.svc:4318`) を設定して、アプリケーションの送信先を collector にします。デモアプリをインストルメントする手順は [OpenTelemetry によるアプリケーションの計装](/ja/clickstack/managed-onboarding/instrument-application-serverless) で解説しています。その際、マネージドエンドポイントを collector のアドレスに置き換え、API キーは削除してください。API キーはゲートウェイが付与するようになります。
* **ゲートウェイでの処理。** [`filter`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/filterprocessor)、[`transform`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/transformprocessor)、[`resourcedetection`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/resourcedetectionprocessor) の各プロセッサを使用すると、テレメトリーがネットワーク外に送信される前に、ノイズの除去、属性の整形、クラウドおよびホストのメタデータによるタグ付けを行えます。

collector 自体については、[OpenTelemetry Collector のドキュメント](https://opentelemetry.io/docs/collector/)にデプロイメントパターン、スケーリング、設定の完全なリファレンスが掲載されています。

## ライブテレメトリーがまだない場合: サンプルデータを送信する {#send-sample-data}

collector は接続済みでもソースからデータが届いていない場合や、より充実したデータで UI を探索したい場合は、合成したログ、トレース、メトリクスをまとめてサービスに直接送信できます。この方法では collector を経由せず、**Env vars** タブの接続情報をそのまま使用するため、値を入力し直す必要はありません。

**Start sending telemetry** ページの **View connection details**、または **チーム設定 → マネージドテレメトリー** を開き、**Env vars** タブを選択します。**Reveal key** を選択してタブの内容をコピーし、シェルで `set -a` と `set +a` の間に貼り付けます。こうすることで、すべての行がエクスポートされます。

<div className="ch-image-md">
  <Frame>
    ![Env vars タブが選択された Set up OpenTelemetry ダイアログ。OTEL_EXPORTER_OTLP_ENDPOINT、マスクされた Bearer キーを含む OTEL_EXPORTER_OTLP_HEADERS、OTEL_EXPORTER_OTLP_PROTOCOL が表示されている](/images/clickstack/getting-started/observability-env-vars.png)
  </Frame>
</div>

```shell
set -a
# Paste the Env vars tab here. It looks like this:
OTEL_EXPORTER_OTLP_ENDPOINT=https://YOUR_OTEL_ENDPOINT:4318
OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer <your-api-key>"
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
set +a
```

OpenTelemetry Collector Contrib のデータジェネレーターである [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen) を Docker イメージから実行します。

```shell
telemetrygen() {
  docker run --rm \
    ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
}
```

または、Go でバイナリをインストールします:

```shell
go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
```

簡単な `tg` ヘルパーを定義します。`telemetrygen` のエンドポイントフラグは URL スキームを受け付けないため、このヘルパーは `OTEL_EXPORTER_OTLP_ENDPOINT` からホストとポートを、`OTEL_EXPORTER_OTLP_HEADERS` からキーを取り出します。OTLP は証明書検証を有効にした HTTPS で送信され、1 回の実行時間は 20 秒です：

```shell
tg() { local signal=$1; shift; telemetrygen "$signal" \
  --otlp-endpoint "${OTEL_EXPORTER_OTLP_ENDPOINT#*://}" --otlp-http \
  --otlp-header "authorization=\"${OTEL_EXPORTER_OTLP_HEADERS#authorization=}\"" \
  --rate 5 --duration 20s "$@"; }
```

`telemetrygen` を直接呼び出さず、必ず `tg` を使用してください。`telemetrygen` に `https://` を含む完全な URL を渡すと、`too many colons in address` エラーで失敗します。

3 つのサービスから、実運用に近いさまざまな重大度のログを送信します:

```shell
tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="POST"'
tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.status_code="500"'
```

各コマンドの最後には、`logs generated` というサマリーが出力されます。キーが誤っている場合は即座に失敗し、エラーメッセージに `401` が表示されます。

トレース、サービスマップ、メトリクスにもデータを投入する場合は、以下のコマンドを展開し、同じシェルで実行してください。

<Accordion title="より充実したテレメトリーを生成する（任意）">
  複数の正常なサービスと、低速でエラーを返す依存サービス 1 つから、複数のスパンで構成されるトレースを送信します。

  ```shell
  for svc in frontend checkout cart; do
    tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
      --otlp-attributes 'deployment.environment="production"' \
      --telemetry-attributes "http.route=\"/$svc\""
  done

  tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
    --otlp-attributes 'deployment.environment="production"' \
    --telemetry-attributes 'http.route="/charge"'
  ```

  カウンター、Gauge、ヒストグラムを送信します。

  ```shell
  tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
  tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
  tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
  ```
</Accordion>

サービスに戻り、**Check for data** を選択してから **Start exploring** を選択します。**検索** で `ServiceName` を `frontend`、`checkout`、`payment` のいずれかに、`SeverityText` を `Error` に絞り込むと、決済ゲートウェイのタイムアウトを確認できます。より充実したデータを生成した場合は、**Traces** ログソースで `payment` のトレースを開いて子スパンとエラーステータスを確認し、さらに **Chart Explorer** で `http.server.requests` をチャートに表示して、メトリクスが取り込まれていることを確認してください。
