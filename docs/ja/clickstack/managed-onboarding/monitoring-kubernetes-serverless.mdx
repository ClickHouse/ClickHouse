<Info>
  **TL;DR**

  サービスのエンドポイントとAPIキーをクラスターに保存し、以下の values ファイルを使って公式の Helm チャートから 2 つの OpenTelemetry コレクターをインストールしたら、Kubernetesダッシュボードを開きます。コンテナログ、ノードおよびクラスターのメトリクス、Kubernetes イベントが ClickHouse オブザーバビリティに直接送信されます。クラスター内でそれ以外のコンポーネントを実行する必要はありません。

  所要時間: 約 15 分
</Info>

ClickHouse オブザーバビリティのサービスを作成したら、次はこのガイドに進みます。このガイドは、ワークロードを Kubernetes 上で実行していて、クラスター自体の状態を把握したい場合を対象としています。コンテナログ、ポッドおよびノードの CPU とメモリ、Kubernetes イベントに送信元の名前空間、ポッド、ノードのタグを付けて収集し、組み込みの Kubernetesダッシュボードで相互に関連付けて確認できるようにします。

構成は OpenTelemetry の標準的なパターンです。[OpenTelemetry Helm チャート](https://github.com/open-telemetry/opentelemetry-helm-charts/tree/main/charts/opentelemetry-collector)から 2 つのコレクターをデプロイします。1 つはコンテナログとノードメトリクスを収集するために全ノード上で動作する **デーモンセット**、もう 1 つは Kubernetes イベントとクラスターメトリクスを収集する単一レプリカの **デプロイメント** です。どちらもサービスの OTLP エンドポイントに直接データを送信します。

<Note>
  **クラスター内ですでに OpenTelemetry コレクターを実行している場合**

  既存のコレクターはそのまま残し、[OpenTelemetry Collector の接続](/ja/clickstack/managed-onboarding/setting-up-your-opentelemetry-collector-serverless)の説明に従ってエクスポーターを追加してください。
</Note>

## 前提条件 {#prerequisites}

* ClickHouse オブザーバビリティのサービス。まだお持ちでない場合は、[Getting Started ガイド](/ja/clickstack/observability/getting-started)の手順に従って作成してください。
* 監視対象のワークロードが稼働している Kubernetes クラスターと、そのクラスターに接続するよう設定済みの `kubectl`。名前空間、Secrets、ConfigMap、クラスターロールを作成するアクセス許可が必要です。
* [Helm](https://helm.sh/)。チャートの README では、前提条件として Helm 4.0 以降が挙げられています。
* collector ポッドからサービスのテレメトリーエンドポイントへ、ポート `4318` でアウトバウンド HTTPS 通信ができること。

## コレクターのデプロイ {#deploy-the-collectors}

<Steps>
  <Step title="接続情報をコピー" id="copy-connection-details">
    ClickHouse オブザーバビリティのサービスを開きます。データが届くまでは、**Start sending telemetry** ページが表示されます。

    <div className="ch-image-lg">
      <Frame>
        ![まだデータがない現在のサービスと、Use an existing OpenTelemetry setup、Instrument with AI、Follow setup guides の 3 つのオプションが表示された Start sending telemetry ページ](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    **Use an existing OpenTelemetry setup** で **View connection details** を選択し、**Collector config** タブを開きます。このタブには、サービス用のエクスポーターブロック (エンドポイント URL と、APIキーを含む `authorization` ヘッダー) が表示されます。**Reveal key** を選択すると、キー全体が表示されます。

    <div className="ch-image-md">
      <Frame>
        ![Collector config タブが選択された Set up OpenTelemetry ダイアログ。マスクされたエンドポイントと Bearer 認証ヘッダーを含む otlphttp エクスポーターが表示されている](/images/clickstack/getting-started/observability-collector-config.png)
      </Frame>
    </div>

    次のステップでは、2 つの値を個別に使用します。1 つは `https://` 認証スキームではなくスキームとポートを含むエンドポイント、もう 1 つは `Bearer` プレフィックスを除いた APIキーのみです。プレフィックスは、後述の values ファイルで付加されます。

    これらの値は、**Team Settings → Managed Telemetry** からいつでも確認できます。
  </Step>

  <Step title="これらをクラスターに保存します" id="store-connection-details">
    コレクター用の名前空間、APIキーを格納する Secret、エンドポイントを格納する ConfigMap を作成します。どちらのコレクターも `extraEnvs` 経由でこれらを読み込むため、APIキーが values ファイルに記載されることはありません。2 つのプレースホルダーをご自身の値に置き換えてください。

    ```shell
    kubectl create namespace otel-collectors

    kubectl create secret generic hyperdx-secret \
      --namespace otel-collectors \
      --from-literal=HYPERDX_API_KEY='<your-api-key>'

    kubectl create configmap otel-config-vars \
      --namespace otel-collectors \
      --from-literal=YOUR_OTEL_COLLECTOR_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    ```

    エンドポイントはベースURLのまま指定してください。シグナルのパスはエクスポーターが自動的に付加するため、`/v1/logs`、`/v1/traces`、`/v1/metrics` は付け加えないでください。別のネームスペースを使用する場合は、以下のすべてのコマンドで同じネームスペースを指定してください。Secret と ConfigMap は、Helm リリースと同じネームスペースに配置する必要があります。
  </Step>

  <Step title="OpenTelemetry Helm リポジトリを追加する" id="add-helm-repository">
    ```shell
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update open-telemetry
    ```
  </Step>

  <Step title="クラスターcollectorをデプロイする" id="deploy-cluster-collector">
    この単一レプリカのデプロイメントは、**Kubernetes イベント**と**クラスター全体のメトリクス** (ノードの状態、ポッドのフェーズ、デプロイメントおよびレプリカのステータス) を収集します。レプリカは 1 つで十分です。2 つ目を追加するとデータが重複して生成されます。

    values ファイルをダウンロードしてインストールします:

    ```shell
    curl -fSL -o k8s_deployment.yaml \
      https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_deployment.yaml

    helm install --namespace otel-collectors k8s-otel-deployment open-telemetry/opentelemetry-collector \
      --version 0.175.0 -f k8s_deployment.yaml
    ```

    <Accordion title="k8s_deployment.yaml">
      ```yaml
      # k8s_deployment.yaml
      mode: deployment

      image:
        repository: otel/opentelemetry-collector-contrib
        tag: 0.161.0

      # このコレクターは 1 つだけにします。複数あるとデータが重複して生成されます
      replicaCount: 1

      presets:
        kubernetesAttributes:
          enabled: true
          # 有効にすると、プロセッサーは関連するポッドのすべてのラベルを抽出し、リソース属性として追加します。
          # ラベル名がそのままキーになります。
          extractAllPodLabels: true
          # 有効にすると、プロセッサーは関連するポッドのすべてのアノテーションを抽出し、リソース属性として追加します。
          # アノテーション名がそのままキーになります。
          extractAllPodAnnotations: true
        # Kubernetes イベントを収集するように collector を設定します。
        # k8sobject receiver を logs パイプラインに追加し、デフォルトで Kubernetes イベントを収集します。
        # 詳細: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-objects-receiver
        kubernetesEvents:
          enabled: true
        # クラスターレベルのメトリクスを収集するように Kubernetes Cluster Receiver を設定します。
        # k8s_cluster receiver を metrics パイプラインに追加し、必要なルールをクラスター ロールに追加します。
        # 詳細: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-cluster-receiver
        clusterMetrics:
          enabled: true

      extraEnvs:
        - name: HYPERDX_API_KEY
          valueFrom:
            secretKeyRef:
              name: hyperdx-secret
              key: HYPERDX_API_KEY
        - name: YOUR_OTEL_COLLECTOR_ENDPOINT
          valueFrom:
            configMapKeyRef:
              name: otel-config-vars
              key: YOUR_OTEL_COLLECTOR_ENDPOINT

      config:
        exporters:
          otlp_http:
            endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
            compression: gzip
            headers:
              authorization: "Bearer ${env:HYPERDX_API_KEY}"
        service:
          pipelines:
            logs:
              exporters:
                - otlp_http
            metrics:
              exporters:
                - otlp_http

      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          memory: 512Mi
      ```
    </Accordion>

    `presets` は、チャートに組み込まれたレシーバーを、必要な RBAC ルールとあわせて有効化します。`config` ブロックでは、環境変数からエンドポイントと API キーを読み取る `otlp_http` エクスポーターを 1 つ追加し、`logs` および `metrics` パイプラインのエクスポーターとして設定しています。`memory_limiter` や `batch` プロセッサを含むその他の設定には、すべてチャートのデフォルトが使用されます。
  </Step>

  <Step title="ノードcollectorをデプロイする" id="deploy-node-collector">
    このデーモンセットはノードごとに 1 つの collector を実行し、`/var/log/pods` からの**コンテナログ**、ノードの**ホストメトリクス**、そして**キューブレットメトリクス**を収集します。キューブレットメトリクスには、すべてのポッドとコンテナの CPU とメモリ (リクエストおよび制限に対する使用率を含む) が含まれます。

    ```shell
    curl -fSL -o k8s_daemonset.yaml \
      https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_daemonset.yaml

    helm install --namespace otel-collectors k8s-otel-daemonset open-telemetry/opentelemetry-collector \
      --version 0.175.0 -f k8s_daemonset.yaml
    ```

    <Accordion title="k8s_daemonset.yaml">
      ```yaml
      # k8s_daemonset.yaml
      mode: daemonset

      image:
        repository: otel/opentelemetry-collector-contrib
        tag: 0.161.0

      # Required to use the kubeletstats cpu/memory utilization metrics
      clusterRole:
        create: true
        rules:
          - apiGroups:
              - ''
            resources:
              - nodes/proxy
            verbs:
              - get

      presets:
        logsCollection:
          enabled: true
        hostMetrics:
          enabled: true
        # Configures the Kubernetes Processor to add Kubernetes metadata.
        # Adds the k8sattributes processor to all the pipelines and adds the necessary rules to ClusterRole.
        # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-attributes-processor
        kubernetesAttributes:
          enabled: true
          # When enabled, the processor will extract all labels for an associated pod and add them as resource attributes.
          # The label's exact name will be the key.
          extractAllPodLabels: true
          # When enabled, the processor will extract all annotations for an associated pod and add them as resource attributes.
          # The annotation's exact name will be the key.
          extractAllPodAnnotations: true
        # Configures the collector to collect node, pod, and container metrics from the kubelet API.
        # Adds the kubeletstats receiver to the metrics pipeline and adds the necessary rules to ClusterRole.
        # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubeletstats-receiver
        kubeletMetrics:
          enabled: true

      extraEnvs:
        - name: HYPERDX_API_KEY
          valueFrom:
            secretKeyRef:
              name: hyperdx-secret
              key: HYPERDX_API_KEY
        - name: YOUR_OTEL_COLLECTOR_ENDPOINT
          valueFrom:
            configMapKeyRef:
              name: otel-config-vars
              key: YOUR_OTEL_COLLECTOR_ENDPOINT

      config:
        receivers:
          kubeletstats:
            insecure_skip_verify: true
        exporters:
          otlp_http:
            endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
            compression: gzip
            headers:
              authorization: "Bearer ${env:HYPERDX_API_KEY}"

        service:
          pipelines:
            logs:
              exporters:
                - otlp_http
            metrics:
              exporters:
                - otlp_http

      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          memory: 512Mi
      ```
    </Accordion>

    `kubernetesAttributes` プリセットは、すべてのログ行とメトリクスに、その送信元となるポッド、ネームスペース、ノード、ワークロードに加え、ポッドのラベルとアノテーションをタグとして付与します。Kubernetesダッシュボードでは、これらの属性を使ってフィルタリングを行います。

    多くのクラスターでは、ノードのアドレスを含まないキューブレット証明書が発行されるため、このファイルでは collector からローカルのキューブレットへの接続に `insecure_skip_verify: true` を設定しています。これはサービスのエンドポイントに対する TLS 検証には影響しません。本番環境では、信頼できるキューブレット証明書を設定したうえで、この設定を削除してください。

    コレクターが稼働していることを確認し、ログを確認します。

    ```shell
    kubectl get pods --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector
    kubectl logs --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector --prefix --tail=50
    ```

    デプロイメントのポッドが 1 つ、デーモンセットのポッドがノードごとに 1 つずつあり、すべて `Running` になっていれば正常です。ただし、ポッドが稼働しているだけではデータが送信されているとは限らないため、ログにエクスポートエラーが出ていないか確認してください:

    * `401` または `403` が返される場合は、Secret 内のAPIキーが誤っているか、キーが `Bearer` プレフィックス付きで保存されており、values ファイル側でもプレフィックスが重複して付与されています。
    * `404` が返される場合は通常、ConfigMap 内のエンドポイントに `/v1/logs` などのシグナルパスが追記されています。
    * `no such host` または TLS エラーが発生する場合は、エンドポイントの入力ミスか、ポート `4318` へのアウトバウンドアクセスがブロックされていることが考えられます。
  </Step>
</Steps>

## 何も表示されない場合 {#if-nothing-shows-up}

* まず、前述の `kubectl logs` コマンドで collector のログを確認します。認証、エンドポイント、TLS に関する問題は、いずれも前述のエラーコードとともにここに出力されます。
* ポッドが `CreateContainerConfigError` のまま停止している場合は、Secret または ConfigMap が存在しないか、Helm リリースとは異なる名前空間に配置されています。`kubectl describe pod` を実行すると、不足しているオブジェクトの名前が表示されます。
* デーモンセットのポッドが `path "/" is mounted on "/" but it is not a shared or slave mount` というメッセージとともに `CreateContainerError` のまま停止している場合は、ノードのルートファイルシステムが共有マウントになっていません。ホストメトリクスのプリセットでは共有マウントが必須です。この問題は、ノードがコンテナ内で動作するローカルクラスターで発生します。ノード上で `mount --make-rshared /` を実行してから、ポッドを削除して再作成させてください。
* ログは届いているのにメトリクスが届かない場合は、デーモンセットのログで `kubeletstats` のエラーを確認してください。この receiver には、values ファイルに含まれる `nodes/proxy` のクラスターロールルールと、ポート `10250` でキューブレットにアクセスできることが必要です。
* メトリクスは届いているのにログが届かない場合は、1 分ほど待ってください。ログの receiver は各ファイルの末尾から読み取りを開始するため、表示されるのは collector の起動後に書き込まれた行のみです。また、ログを何も出力しないポッドからは何も収集されません。
* **検索** で時間範囲を広げ、フィルタをすべて解除してください。デフォルトのログソースが **Logs** ではなく **Traces** に設定されている可能性があります。
* サービス自体に問題がないかを切り分けるには、**チーム設定 → マネージドテレメトリー** を開き、**Send a Test Log** を使用します。そのログが **検索** に表示されれば、サービスはデータを正常に受信しており、問題はクラスターとエンドポイントの間にあります。

## アプリケーションのテレメトリーを追加する {#add-application-telemetry}

2つのコレクターでクラスター全体をカバーできます。一方、トレースや、アプリケーションが OpenTelemetry SDK を通じて出力するログ・メトリクスは、アプリケーション側でエクスポートする必要があります。その方法は2通りあります。

<Tabs>
  <Tab title="サービスへ直接送信" id="directly-to-your-service">
    [OpenTelemetry によるアプリケーションの計装](/ja/clickstack/managed-onboarding/instrument-application-serverless) の手順に従ってアプリケーションをインストルメントし、マネージドのエンドポイントへ直接エクスポートします。**Env vars** タブに表示される `OTEL_EXPORTER_OTLP_ENDPOINT` と `OTEL_EXPORTER_OTLP_HEADERS` の値を Secret に保存し、環境変数としてポッドに渡します。

    Downward API で Kubernetes の属性を追加し、テレメトリーを Kubernetesダッシュボード上のインフラストラクチャデータと相関付けられるようにします。

    ```yaml
    env:
      - name: POD_NAME
        valueFrom:
          fieldRef:
            fieldPath: metadata.name
      - name: POD_UID
        valueFrom:
          fieldRef:
            fieldPath: metadata.uid
      - name: POD_NAMESPACE
        valueFrom:
          fieldRef:
            fieldPath: metadata.namespace
      - name: NODE_NAME
        valueFrom:
          fieldRef:
            fieldPath: spec.nodeName
      - name: OTEL_RESOURCE_ATTRIBUTES
        value: k8s.pod.name=$(POD_NAME),k8s.pod.uid=$(POD_UID),k8s.namespace.name=$(POD_NAMESPACE),k8s.node.name=$(NODE_NAME)
    ```
  </Tab>

  <Tab title="ノードの collector を経由して送信" id="through-the-node-collector">
    もう1つの方法は、デーモンセットを経由して送信することです。デーモンセットは、各ノードのホストポート `4317` (gRPC) と `4318` (HTTP) ですでに OTLP を受信しています。この方法には2つの利点があります。1つは、collector が APIキーを付与するため、ポッドに APIキーを持たせる必要がないことです。もう1つは、collector の `k8s_attributes` プロセッサーが各スパンとログレコードに送信元ポッドの名前空間、ノード、ワークロード、ラベルをタグ付けするため、アプリケーションのトレースをインフラストラクチャデータと突き合わせられることです。

    ダウンロードした values ファイルでは、ログとメトリクスのみが振り分けられるよう設定されています。`traces` パイプラインにもエクスポーターを追加し、リリースをアップグレードします。

    ```yaml
    # k8s_daemonset.yaml の service.pipelines セクションに追加
          traces:
            exporters:
              - otlp_http
    ```

    ```shell
    helm upgrade --namespace otel-collectors k8s-otel-daemonset open-telemetry/opentelemetry-collector \
      --version 0.175.0 -f k8s_daemonset.yaml
    ```

    次に、各アプリケーションの送信先を、それぞれが稼働するノード上の collector に設定します。ノードのアドレスとポッドの UID は Downward API から取得できます。

    ```yaml
    env:
      - name: HOST_IP
        valueFrom:
          fieldRef:
            fieldPath: status.hostIP
      - name: POD_UID
        valueFrom:
          fieldRef:
            fieldPath: metadata.uid
      - name: OTEL_EXPORTER_OTLP_ENDPOINT
        value: http://$(HOST_IP):4318
      - name: OTEL_EXPORTER_OTLP_PROTOCOL
        value: http/protobuf
      - name: OTEL_SERVICE_NAME
        value: <your-service-name>
      - name: OTEL_RESOURCE_ATTRIBUTES
        value: k8s.pod.uid=$(POD_UID)
    ```

    クラスター内では APIキーは不要です。collector は `OTEL_RESOURCE_ATTRIBUTES` の UID からポッドを特定し、`k8s.pod.name`、`k8s.namespace.name`、`k8s.node.name`、所有元のワークロード、ポッドのラベルを自ら付与します。接続の送信元アドレスでポッドを照合することもできますが、これはホストポートを経由する経路でクラスターネットワークがポッド IP を保持するかどうかに左右されるため、UID を渡すようにしてください。
  </Tab>
</Tabs>
