この**ガイドは ClickHouse Cloud の既存ユーザーを対象としています**。ClickHouse Cloud を初めて利用する場合は、Self-managed ClickHouse Observability 向けの[はじめに](/ja/clickstack/self-configured/getting-started/managed)ガイドを参照することをお勧めします。

このデプロイメントパターンでは、ClickHouse と ClickStack UI の両方が ClickHouse Cloud 上でホストされるため、ユーザーがセルフホストする必要のあるコンポーネントを最小限に抑えられます。

このデプロイメントパターンでは、インフラストラクチャ管理の負担が軽減されるだけでなく、認証が ClickHouse Cloud の SSO/SAML と統合されます。また、セルフホスト型のデプロイメントとは異なり、ダッシュボード、保存済み検索、ユーザー設定、アラートなどのアプリケーションの状態を保存するための MongoDB インスタンスをプロビジョニングする必要もありません。さらに、次のようなメリットもあります。

* ストレージから独立したコンピュートの自動スケーリング
* オブジェクトストレージを基盤とした、低コストかつ実質的に無制限のデータ保持
* Warehouses による[読み取りワークロードと書き込みワークロードの分離](/ja/clickstack/self-configured/managing/isolating-read-write)
* 統合された認証
* 自動バックアップ
* セキュリティおよびコンプライアンス機能
* シームレスなアップグレード

このモードでは、データ取り込みは完全にユーザー側で行います。Self-managed ClickHouse Observability には、独自にホストした OpenTelemetry collector、クライアントライブラリからの直接インジェスト、ClickHouse ネイティブのテーブルエンジン (Kafka や S3 など) 、ETL パイプライン、または ClickHouse Cloud のマネージドインジェストサービスである ClickPipes を使用してデータを取り込めます。このアプローチは、ClickStack を運用するうえで最もシンプルかつ高性能な方法です。

### 適したユースケース {#suitable-for}

このデプロイメントパターンは、次のようなケースに最適です。

1. ClickHouse Cloud にすでにオブザーバビリティデータがあり、それを ClickStack で可視化したい場合。
2. 大規模なオブザーバビリティ環境を運用しており、ClickHouse Cloud 上で動作する ClickStack の専用リソースによるパフォーマンスとスケーラビリティが必要な場合。
3. すでに分析用途で ClickHouse Cloud を使用しており、ClickStack のインストルメンテーションライブラリでアプリケーションをインストルメントして、同じクラスターにデータを送信したい場合。この場合は、[warehouse](/ja/products/cloud/features/infrastructure/warehouses) を使用して、オブザーバビリティのワークロード用にコンピュートを分離することを推奨します。

### データベースとテーブルを作成する {#create-database-and-tables}

            Vector では、データ取り込みの前にテーブルとスキーマを定義しておく必要があります。

            まず、データベースを作成します。これは [ClickHouse Cloud コンソール](/ja/products/cloud/features/sql-console-features/sql-console)から行えます。

            たとえば、ログ用のデータベースを次のように作成します。

            ```sql
            CREATE DATABASE IF NOT EXISTS logs
            ```

            次に、ログデータの構造に一致するスキーマを持つテーブルを作成します。以下の例では、標準的な Nginx アクセスログ形式を想定しています。

            ```sql
            CREATE TABLE logs.nginx_logs
            (
                `time_local` DateTime,
                `remote_addr` IPv4,
                `remote_user` LowCardinality(String),
                `request` String,
                `status` UInt16,
                `body_bytes_sent` UInt64,
                `http_referer` String,
                `http_user_agent` String,
                `http_x_forwarded_for` LowCardinality(String),
                `request_time` Float32,
                `upstream_response_time` Float32,
                `http_host` String
            )
            ENGINE = MergeTree
            ORDER BY (toStartOfMinute(time_local), status, remote_addr);
            ```

            テーブルは、Vector が出力するスキーマと一致している必要があります。推奨される[スキーマのベストプラクティス](/ja/concepts/best-practices/select-data-type)に従い、データに合わせて必要に応じてスキーマを調整してください。

            ClickHouse における[主キー](/ja/concepts/core-concepts/primary-indexes)の仕組みを理解したうえで、アクセスパターンに基づいて順序キーを選択することを強く推奨します。主キーの選び方については、[ClickStack 固有](/ja/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key)のガイダンスを参照してください。

            テーブルを作成したら、表示されている設定スニペットをコピーします。既存のパイプラインからデータを消費するように入力を調整し、必要に応じてターゲットテーブルとデータベースも変更してください。認証情報はあらかじめ入力されています。

            <div className="ch-image-lg">
              <Frame>
                ![Vector の設定](/images/clickstack/vector-config-clickstack-ui.webp)
              </Frame>
            </div>

            Vector によるデータの取り込みのその他の例については、[「Vector によるデータの取り込み」](/ja/clickstack/observability/ingesting-data/vector#self-managed)を参照してください。高度なオプションについては、[Vector ClickHouse シンクのドキュメント](https://vector.dev/docs/reference/configuration/sinks/clickhouse/)を参照してください。

## その他のタスク {#additional-tasks}

### Self-managed ClickHouse Observability へのアクセス権の付与 {#configure-access}

1. ClickHouse Cloud コンソールで対象のサービスを開きます
2. **設定** → **SQL コンソールのアクセス権** に移動します
3. 各ユーザーに適切なアクセス許可レベルを設定します。
   * **Service Admin → Full Access** - アラートを有効化するために必要
   * **Service Read Only → Read Only** - オブザーバビリティデータの閲覧とダッシュボードの作成が可能
   * **No access** - ClickStack UI にはアクセス不可

<div className="ch-image-md">
  <Frame>
    ![ClickHouse Cloud 読み取り専用](/images/clickstack/read-only-access.webp)
  </Frame>
</div>

<Warning>
  **アラートには管理者アクセスが必要です**

  アラートを有効化するには、**Service Admin** のアクセス許可を持つユーザー (SQL コンソールのアクセス権のドロップダウンでは **Full Access** に対応) のうち、少なくとも 1 人が一度以上 ClickStack UI にログインする必要があります。これにより、アラートクエリを実行する専用ユーザーがデータベース内にプロビジョニングされます。
</Warning>

### 読み取り専用コンピュートで ClickStack を使用する {#clickstack-read-only-compute}

ClickStack UI は、読み取り専用の ClickHouse Cloud サービス上だけで完結して動作させることができます。インジェストとクエリのワークロードを分離したい場合は、この構成を推奨します。

#### ClickStack がコンピュートを選択する仕組み {#how-clickstack-selects-compute}

ClickStack UI は常に、ClickHouse Cloud コンソールで起動元となった ClickHouse サービスに接続します。

つまり、次のようになります。

* 読み取り専用サービスから ClickStack を開いた場合、ClickStack UI が発行するすべてのクエリは、その読み取り専用コンピュート上で実行されます。
* 読み書きサービスから ClickStack を開いた場合は、そのサービスのコンピュートが使用されます。

読み取り専用の動作を強制するために、ClickStack 側で追加の設定を行う必要はありません。

#### 推奨構成 {#recommended-setup}

読み取り専用コンピュート上で ClickStack を実行するには、次の手順に従います。

1. 読み取り専用として設定された warehouse 内の ClickHouse Cloud サービスを作成するか、既存のサービスを特定します。
2. ClickHouse Cloud コンソールで、読み取り専用サービスを選択します。
3. 左側のナビゲーションメニューから ClickStack を起動します。

起動すると、ClickStack UI はこの読み取り専用サービスに自動的にバインドされます。

なお、ダッシュボード、保存済み検索、アラート、ソースのスコープは ClickStack を起動したサービスに限定されます。そのため、warehouse 内の別のサービスで保存したものはここでは利用できず、再作成する必要があります。標準の OpenTelemetry スキーマを使用するソースは自動検出されるため、そのデータはすぐに検索できます。一方、カスタムソースや手動で設定したソースは自動検出されないため、改めて設定する必要があります。

インジェストの送信先、DDL を実行するサービス、アラートの動作などを含むトポロジー全体については、「[読み取りワークロードと書き込みワークロードの分離](/ja/clickstack/self-configured/managing/isolating-read-write)」を参照してください。

### データソースの追加 {#adding-data-sources}

ClickStack は OpenTelemetry ネイティブですが、OpenTelemetry 専用ではありません。必要に応じて独自のテーブルスキーマを使用することもできます。

以下では、自動的に設定されるデータソース以外に、データソースを追加する方法について説明します。

#### OpenTelemetry スキーマの使用 {#using-otel-schemas}

ClickStack は、標準の OpenTelemetry スキーマを使用するテーブルを自動的に検出し、ログ、トレース、メトリクスに対応するデータソースを作成します。確認ダイアログでの操作や手動でのソース作成は必要ありません。

自動作成されたソースを確認または調整するには、**チーム設定 → Data → Sources** を開き、対象のソースを展開します。次の例は、`otel_logs` テーブルのログソースです。

#### カスタムスキーマの使用 {#using-custom-schemas}

カスタムテーブルを使用する場合は、[データソース設定リファレンス](/ja/clickstack/self-configured/managing/config#datasource-settings)を参照してデータソースを設定してください。

## スキーマの選択: Map と JSON {#schema-choice-map-vs-json}

ClickStack は、デフォルトで属性を `Map(LowCardinality(String), String)` カラムとして保存します。これはオブザーバビリティのワークロードに推奨されるスキーマです。[バケット化されたマップのシリアライズ](/ja/reference/data-types/map#bucketed-map-serialization)と、Map のキーと値に対するテキストインデックスを組み合わせることで、動的な JSON サブカラムで生じるキーごとの取り込みオーバーヘッドなしに、選択的なルックアップを実現できます。

`JSON` 型のスキーマは、属性キーの集合が小規模かつ安定しているワークロードでの評価用に、ベータ版として提供されています。デフォルトとして使用することは**推奨されません**。詳細な比較と、JSON サポートを有効化するために必要な環境変数については、[Map と JSON型の比較](/ja/clickstack/self-configured/ingesting-data/schema/map-vs-json)を参照してください。
