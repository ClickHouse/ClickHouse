## Elastic Stack と Self-managed ClickHouse Observability の比較 {#elastic-vs-clickstack}

Elastic Stack と Self-managed ClickHouse Observability は、いずれもオブザーバビリティプラットフォームの中核となる役割を担っていますが、その実現方法は異なる設計思想に基づいています。主な役割は次のとおりです。

* **UI とアラート**: データのクエリ、ダッシュボードの構築、アラートの管理を行うためのツール。
* **ストレージとクエリエンジン**: オブザーバビリティデータを保存し、分析クエリを処理するバックエンドシステム。
* **データ収集と ETL**: テレメトリーデータを収集し、インジェスト前に処理するエージェントおよびパイプライン。

次の表は、各スタックのコンポーネントがこれらの役割にどのように対応するかを示しています。

| **ロール**              | **Elastic Stack**                                    | **Self-managed ClickHouse Observability**                               | **備考**                                                                                                                                                                 |
| -------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **UI とアラート**         | **Kibana** — ダッシュボード、検索、アラート                         | **オブザーバビリティ UI** — リアルタイム UI、検索、アラート                                    | どちらも、可視化やアラート管理を含むユーザー向けの主要なインターフェイスとして機能します。オブザーバビリティ UI はオブザーバビリティ専用に設計されており、OpenTelemetry のセマンティクスと密接に連携しています。                                                      |
| **ストレージとクエリエンジン**    | **Elasticsearch** — 転置索引を備えた JSON ドキュメントストア          | **ClickHouse** — ベクトル化エンジンを備えたカラム指向データベース                               | Elasticsearch は検索に最適化された転置索引を使用します。一方、ClickHouse はカラム型ストレージと SQL により、構造化データおよび半構造化データに対する高速な分析を実現します。                                                                  |
| **データ収集**            | **Elastic Agent**、**Beats** (例: Filebeat、Metricbeat) | **ClickHouse Observability Collector** (エッジ + ゲートウェイ)                   | Elastic は、カスタムシッパーと、Fleet で管理される統合エージェントをサポートしています。Self-managed ClickHouse Observability は OpenTelemetry を基盤としており、ベンダーに依存しないデータ収集と処理が可能です。                             |
| **インストルメンテーション SDK** | **Elastic APM エージェント** (プロプライエタリ)                    | **OpenTelemetry SDKs** (Self-managed ClickHouse Observability により配布)    | Elastic の SDK は Elastic Stack に依存しています。Self-managed ClickHouse Observability は、主要言語向けの OpenTelemetry SDKs を基盤として、ログ、メトリクス、トレースを扱います。                                   |
| **ETL / データ処理**      | **Logstash**、取り込みパイプライン                              | **ClickHouse Observability Collector** + ClickHouse の materialized view | Elastic は、取り込みパイプラインと Logstash を使用してデータを変換します。Self-managed ClickHouse Observability は、materialized view と OTel collector のプロセッサによって処理を挿入時に移し、データを効率的かつインクリメンタルに変換します。 |
| **アーキテクチャの思想**       | 垂直統合型、プロプライエタリなエージェントとフォーマット                         | オープン標準ベース、疎結合なコンポーネント                                                   | Elastic は緊密に統合されたエコシステムを構築しています。Self-managed ClickHouse Observability は、柔軟性とコスト効率を高めるため、モジュール性と標準 (OpenTelemetry、SQL、オブジェクトストレージ) を重視しています。                            |

Self-managed ClickHouse Observability はオープン標準と相互運用性を重視しており、収集から UI まで完全に OpenTelemetry ネイティブです。これに対して Elastic は、プロプライエタリなエージェントとフォーマットを用いた、密結合で垂直統合型のエコシステムを提供しています。

**Elasticsearch** と **ClickHouse** は、それぞれのスタックでデータの保存、処理、クエリを担う中核エンジンであるため、両者の違いを理解しておくことが重要です。これらのシステムは、オブザーバビリティアーキテクチャ全体のパフォーマンス、スケーラビリティ、柔軟性を支えています。次のセクションでは、データモデル、インジェストの処理方法、クエリの実行方法、ストレージの管理方法など、Elasticsearch と ClickHouse の主な違いを説明します。

## Elasticsearch と ClickHouse の比較 {#elasticsearch-vs-clickhouse}

ClickHouse と Elasticsearch は、データの整理やクエリに異なる基盤モデルを採用していますが、多くの中核的な概念は同様の役割を果たします。このセクションでは、Elastic に慣れている方に向けて、主な概念とそれに相当する ClickHouse の概念との対応関係を説明します。用語こそ異なりますが、ほとんどのオブザーバビリティのワークフローは Self-managed ClickHouse Observability で再現でき、多くの場合はより効率的に実現できます。

### 主要な構造的概念 {#core-structural-concepts}

| **Elasticsearch** | **ClickHouse / SQL** | **説明**                                                                                                                                                                                                                                                                                                    |
| ----------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **フィールド**         | **カラム**              | データの基本単位で、特定の型の値を 1 つ以上保持します。Elasticsearch のフィールドには、プリミティブ型に加えて配列やオブジェクトも格納できます。ただし、1 つのフィールドが持てる型は 1 つだけです。ClickHouse も配列やオブジェクト (`Tuples`、`Maps`、`Nested`) をサポートしており、さらに [`Variant`](/ja/reference/data-types/variant) や [`Dynamic`](/ja/reference/data-types/dynamic) といった動的な型を使えば、1 つのカラムに複数の型を持たせることができます。 |
| **ドキュメント**        | **行**                | フィールド (カラム) の集合です。Elasticsearch のドキュメントはデフォルトで柔軟性が高く、データに応じて新しいフィールドが動的に追加されます (型はデータから推論されます) 。一方、ClickHouse の行はデフォルトでスキーマに縛られており、ユーザーは行のすべてのカラム、またはその一部を指定して挿入する必要があります。ClickHouse の [`JSON`](/ja/guides/clickhouse/data-formats/json/intro) 型を使えば、挿入されたデータに基づいて半構造化の動的なカラムを作成する、同等の機能を利用できます。             |
| **インデックス**        | **テーブル**             | クエリ実行とストレージの単位です。どちらのシステムでも、クエリは行／ドキュメントを格納するインデックスまたはテーブルに対して実行されます。                                                                                                                                                                                                                                     |
| *暗黙的*             | スキーマ (SQL)           | SQL スキーマはテーブルを名前空間ごとにまとめるもので、主にアクセス制御に使用されます。Elasticsearch と ClickHouse にはスキーマはありませんが、どちらもロールと RBAC による行レベルおよびテーブルレベルのセキュリティをサポートしています。                                                                                                                                                                   |
| **クラスター**         | **クラスター / データベース**   | Elasticsearch のクラスターは、1 つ以上のインデックスを管理するランタイムインスタンスです。ClickHouse では、データベースが論理的な名前空間内でテーブルを整理し、Elasticsearch のクラスターと同様の論理的なグループ化を実現します。ClickHouse クラスターは Elasticsearch と同じくノードの分散集合ですが、データそのものとは切り離されており、独立しています。                                                                                           |

### データモデリングと柔軟性 {#data-modeling-and-flexibility}

Elasticsearch は、[dynamic mappings](https://www.elastic.co/docs/manage-data/data-store/mapping/dynamic-mapping) によるスキーマの柔軟性で知られています。スキーマを指定しない限り、フィールドはドキュメントの取り込み時に作成され、型は自動的に推論されます。ClickHouse はデフォルトではより厳格で、テーブルは明示的なスキーマで定義されますが、[`Dynamic`](/ja/reference/data-types/dynamic)、[`Variant`](/ja/reference/data-types/variant)、[`JSON`](/ja/guides/clickhouse/data-formats/json/intro) 型によって柔軟性も備えています。これらの型を使えば、Elasticsearch と同様に動的なカラム作成と型推論を行いながら、半構造化データをインジェストできます。同様に、[`Map`](/ja/reference/data-types/map) 型を使用すると任意のキー・バリューのペアを保存できます。ただし、キーと値にはそれぞれ単一の型が強制されます。

ClickHouse における型の柔軟性へのアプローチは、より透過的で制御しやすいものです。型の競合がインジェストエラーの原因となり得る Elasticsearch とは異なり、ClickHouse では [`Variant`](/ja/reference/data-types/variant) カラムに異なる型が混在したデータを格納できます。また、[`JSON`](/ja/guides/clickhouse/data-formats/json/intro) 型を使用することでスキーマ進化にも対応できます。

[`JSON`](/ja/guides/clickhouse/data-formats/json/intro) を使用しない場合、スキーマは静的に定義されます。ある行に値が指定されていない場合、その値は [`Nullable`](/ja/reference/data-types/nullable) として定義される(Self-managed ClickHouse Observability では使用されません)か、型のデフォルト値(例: `String` の場合は空の値)にフォールバックします。

### インジェストと変換 {#ingestion-and-transformation}

Elasticsearch では、インデックス作成前にドキュメントを変換するために、プロセッサ (例: `enrich`、`rename`、`grok`) を組み込んだ取り込みパイプラインを使用します。ClickHouse では、同様の機能を [**インクリメンタルmaterialized view**](/ja/concepts/features/materialized-views/incremental-materialized-view) で実現できます。インクリメンタルmaterialized view を使うと、受信データを [フィルタ・変換](/ja/concepts/features/materialized-views/incremental-materialized-view#filtering-and-transformation) したり、[データを拡充](/ja/concepts/features/materialized-views/incremental-materialized-view#lookup-table) したりして、その結果を宛先テーブルに挿入できます。materialized view の出力だけを保存できればよい場合は、`Null` テーブルエンジンにデータを挿入することもできます。この場合、materialized view の結果だけが保持され、元のデータは破棄されるため、ストレージ容量を節約できます。

エンリッチメントについては、Elasticsearch ではドキュメントにコンテキストを付加するための専用の [enrich プロセッサ](https://www.elastic.co/docs/reference/enrich-processor/enrich-processor) が用意されています。ClickHouse では、[**Dictionary**](/ja/concepts/features/dictionaries/index) を [クエリ実行時](/ja/concepts/features/dictionaries/index#query-time-enrichment) と [取り込み時](/ja/concepts/features/dictionaries/index#index-time-enrichment) のどちらでも使用して、行のデータを拡充できます。たとえば、INSERT 時に [IP アドレスを地域にマッピング](/ja/guides/use-cases/observability/build-your-own/schema-design#using-ip-dictionaries) したり、[ユーザーエージェントのルックアップ](/ja/guides/use-cases/observability/build-your-own/schema-design#using-regex-dictionaries-user-agent-parsing) を行ったりできます。

### クエリ言語 {#query-languages}

Elasticsearch は、[DSL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/querydsl)、[ES|QL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/esql)、[EQL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/eql)、[KQL](https://www.elastic.co/docs/explore-analyze/query-filter/languages/kql) (Lucene スタイル) クエリなど、[複数のクエリ言語](https://www.elastic.co/docs/explore-analyze/query-filter/languages)をサポートしていますが、結合のサポートは限定的で、利用できるのは [`ES|QL`](https://www.elastic.co/docs/reference/query-languages/esql/commands/lookup-join) による **左外部結合** のみです。一方、ClickHouse は **完全な SQL 構文** をサポートしており、[すべての結合の種類](/ja/reference/statements/select/join#supported-types-of-join)、[ウィンドウ関数](/ja/reference/functions/window-functions/index)、サブクエリ (相関サブクエリを含む) 、CTE を利用できます。オブザーバビリティシグナルをビジネスデータやインフラストラクチャデータと相関付ける必要がある場合、これは大きな利点となります。

Self-managed ClickHouse Observability では、移行しやすいように [UI で Lucene 互換の検索インターフェイスを提供](/ja/clickstack/observability/features/search)しているほか、ClickHouse バックエンドを通じて完全な SQL もサポートしています。この構文は [Elastic のクエリ文字列](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-query-string-query#query-string-syntax)構文に相当します。両者の構文の詳細な比較については、[「Self-managed ClickHouse Observability と Elastic での検索」](/ja/clickstack/observability/migration/elastic/search)を参照してください。

### ファイルフォーマットとインターフェイス {#file-formats-and-interfaces}

Elasticsearch は JSON(および[限定的な CSV](https://www.elastic.co/docs/reference/enrich-processor/csv-processor))のインジェストをサポートしています。一方、ClickHouse は Parquet、Protobuf、Arrow、CSV などを含む **70 種類以上のファイルフォーマット** に対応しており、インジェストとエクスポートのどちらにも利用できます。そのため、外部のパイプラインやツールと容易に連携できます。

どちらのシステムも REST API を提供していますが、ClickHouse はさらに、低レイテンシーかつ高スループットな通信を可能にする **ネイティブプロトコル** も備えています。ネイティブインターフェイスは、クエリの進捗通知、圧縮、ストリーミングを HTTP よりも効率的に処理でき、本番環境におけるインジェストの大半で標準的に使用されています。

### インデックス作成とストレージ {#indexing-and-storage}

シャーディングの概念は、Elasticsearch のスケーラビリティモデルの根幹をなしています。各 ① [**インデックス**](https://www.elastic.co/blog/what-is-an-elasticsearch-index) は **分片** に分割され、各分片はディスク上にセグメントとして保存される物理的な Lucene インデックスです。分片は耐障害性を確保するため、レプリカ分片と呼ばれる 1 つ以上の物理コピーを持つことができます。また、スケーラビリティのために、分片とレプリカを複数のノードに分散させることができます。1 つの分片 ② は、1 つ以上のイミュータブルなセグメントで構成されます。セグメントは Lucene の基本的なインデックス構造です。Lucene は、Elasticsearch の基盤となるインデックス作成機能と検索機能を提供する Java ライブラリです。

<Info>
  **Elasticsearch における挿入処理**

  Ⓐ 新たに挿入されたドキュメントは、Ⓑ まずインメモリのインデックス作成バッファに格納されます。このバッファはデフォルトで 1 秒に 1 回フラッシュ済みになります。フラッシュ済みのドキュメントの格納先となる分片はルーティング式によって決定され、その分片用の新しいセグメントがディスクに書き込まれます。クエリ効率の向上と、削除・更新されたドキュメントの物理削除を可能にするため、セグメントはバックグラウンドで継続的にマージされ、最大サイズの 5 GB に達するまでより大きなセグメントへと統合されます。ただし、より大きなセグメントへのマージを強制的に実行することも可能です。
</Info>

Elasticsearch では、[JVM ヒープとメタデータのオーバーヘッド](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards#each-shard-has-overhead)を考慮し、分片のサイズを [50 GB または 2 億ドキュメント](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards)程度に抑えることが推奨されています。また、[分片あたり 20 億ドキュメント](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards#troubleshooting-max-docs-limit)というハードリミットも存在します。Elasticsearch はクエリを分片間で並列処理しますが、各分片は **単一スレッド** で処理されるため、過剰なシャーディングはコストが高くつくうえに逆効果となります。そのため、シャーディングとスケーリングは本質的に密結合しており、パフォーマンスをスケールさせるにはより多くの分片 (およびノード) が必要になります。

Elasticsearch は高速な検索を実現するため、すべてのフィールドを [**転置索引**](https://www.elastic.co/docs/manage-data/data-store/index-basics) に登録し、集計、ソート、スクリプトによるフィールドアクセスには必要に応じて [**doc values**](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/doc-values) を使用します。数値フィールドと Geo フィールドでは、地理空間データや数値・日付範囲の検索に [Block K-D trees](https://users.cs.duke.edu/~pankaj/publications/papers/bkd-sstd.pdf) が使用されます。

重要な点として、Elasticsearch は元のドキュメント全体を [`_source`](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field) に (`LZ4`、`Deflate`、または `ZSTD` で圧縮して) 保存しますが、ClickHouse はドキュメント表現を別途保存しません。データはクエリ実行時にカラムから再構築されるため、ストレージ容量を節約できます。Elasticsearch でも [Synthetic `_source`](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field#synthetic-source) を使えば同様のことが可能ですが、いくつかの[制限](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field#synthetic-source-restrictions)があります。また、`_source` を無効化すると、ClickHouse には当てはまらない[影響](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-source-field#include-exclude)も生じます。

Elasticsearch では、[インデックスマッピング](https://www.elastic.co/guide/en/elasticsearch/reference/current/mapping.html) (ClickHouse のテーブルスキーマに相当) によって、フィールドの型や、永続化とクエリに使用されるデータ構造が制御されます。

これに対して ClickHouse は **カラム指向** であり、各カラムは独立して保存されますが、常にテーブルのプライマリキー/ソートキーの順に並べられています。この順序付けによって [スパースなプライマリインデックス](/ja/concepts/core-concepts/primary-indexes) が可能になり、ClickHouse はクエリ実行時に不要なデータを効率的にスキップできます。クエリがプライマリキーのフィールドでフィルタリングする場合、ClickHouse は各カラムの該当部分のみを読み取るため、すべてのカラムに完全な索引を持たなくても、ディスク I/O を大幅に削減し、パフォーマンスを向上させることができます。

    ![ClickHouse](/images/use-cases/observability/clickhouse.webp)

</div>

ClickHouse は [**スキップ索引**](/ja/concepts/features/performance/skip-indexes/skipping-indexes) もサポートしています。これは、選択したカラムの索引データを事前に計算しておくことでフィルタリングを高速化する仕組みです。スキップ索引は明示的に定義する必要がありますが、パフォーマンスを大幅に向上させられます。さらに、ClickHouse ではカラムごとに [圧縮コーデック](/ja/guides/use-cases/observability/build-your-own/schema-design#using-codecs) と圧縮アルゴリズムを指定できます。これは Elasticsearch にはない機能です (Elasticsearch の [圧縮](https://www.elastic.co/docs/reference/elasticsearch/index-settings/index-modules) は `_source` の JSON ストレージにのみ適用されます) 。

ClickHouse もシャーディングをサポートしていますが、そのモデルは **垂直スケーリング** を優先するよう設計されています。単一の分片に **数兆行** を格納でき、メモリ、CPU、ディスクが許す限り効率的に動作し続けます。Elasticsearch とは異なり、分片あたりの **行数にハードリミットはありません**。ClickHouse の分片は論理的なもの (実質的には個々のテーブル) であり、データセットが単一ノードの容量を超えない限り分割する必要はありません。容量超過は通常、ディスクサイズの制約によって発生します。シャーディングは水平スケールアウトが必要な場合にのみ ①  導入されるため、複雑さとオーバーヘッドを抑えられます。この場合、Elasticsearch と同様に、各分片はデータのサブセットを保持します。単一の分片内のデータは、③ 複数のデータ構造を含む ② イミュータブルなパーツの集まりとして構成されます。

ClickHouse の分片内の処理は **完全に並列化** されています。ノード間でのデータ移動に伴うネットワークコストを避けるため、垂直スケーリングが推奨されます。

<Info>
  **ClickHouse における挿入処理**

  ClickHouse の挿入処理は **デフォルトで同期** であり、書き込みはコミット後に初めて確認応答されます。ただし、Elastic と同様のバッファリングやバッチ処理を行うために、**非同期挿入** を使用するよう設定することもできます。[非同期データ挿入](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse) を使用する場合、Ⓐ 新たに挿入された行はまず Ⓑ インメモリの挿入バッファに格納され、デフォルトでは 200 ミリ秒ごとにフラッシュ済みになります。複数の分片を使用する場合は、[分散テーブル](/ja/reference/engines/table-engines/special/distributed) によって、新たに挿入された行が対象の分片にルーティングされます。その後、その分片のディスク上に新しいパーツが書き込まれます。
</Info>

### 分散とレプリケーション {#distribution-and-replication}

Elasticsearch と ClickHouse はいずれも、スケーラビリティと耐障害性を確保するためにクラスター、分片、レプリカを使用しますが、そのモデルは実装とパフォーマンス特性の面で大きく異なります。

Elasticsearch はレプリケーションに **プライマリ-セカンダリ** モデルを使用します。データがプライマリ分片に書き込まれると、1 つ以上のレプリカへ同期的にコピーされます。これらのレプリカ自体も完全な分片であり、冗長性を確保するために複数のノードに分散配置されます。Elasticsearch は、必要なすべてのレプリカが操作を確認した時点で初めて書き込みを確認応答します。このモデルはほぼ **逐次整合性** を実現しますが、完全に同期されるまでの間はレプリカから **ダーティリード** が発生する可能性があります。クラスターの協調は **マスターノード** が担い、分片の割り当て、ヘルス、リーダー選出を管理します。

一方、ClickHouse はデフォルトで **結果整合性** を採用しており、ZooKeeper の軽量な代替である **Keeper** によって協調されます。書き込みは任意のレプリカに直接送信することも、レプリカを自動的に選択する [**分散テーブル**](/ja/reference/engines/table-engines/special/distributed) を介して送信することもできます。レプリケーションは非同期で、変更は書き込みの確認応答後に他のレプリカへ伝播されます。より厳格な保証が必要な場合に備えて、ClickHouse は [**逐次整合性**もサポート](/ja/get-started/migrate/postgres/appendix#sequential-consistency)しています。この場合、書き込みはすべてのレプリカでコミットされた後に初めて確認応答されます。ただし、パフォーマンスへの影響が大きいため、このモードが使われることはまれです。分散テーブルは複数の分片へのアクセスを一元化し、`SELECT` クエリをすべての分片に転送して結果をマージします。`INSERT` 操作では、データを各分片へ均等に振り分けることで負荷を分散します。ClickHouse のレプリケーションは非常に柔軟で、任意のレプリカ (分片のコピー) が書き込みを受け付けられ、すべての変更は他のレプリカへ非同期に同期されます。このアーキテクチャにより、障害発生時やメンテナンス中もクエリ処理を中断せずに継続でき、再同期も自動的に行われます。そのため、データ層でプライマリ-セカンダリ構成を強制する必要はありません。

<Info>
  **ClickHouse Cloud**

  **ClickHouse Cloud** では、単一の **分片をオブジェクトストレージで支える** shared-nothing コンピュートモデルを採用しています。これにより従来のレプリカベースの高可用性が不要となり、**複数のノードから同じ分片を同時に読み書き** できます。ストレージとコンピュートの分離により、レプリカを明示的に管理することなく弾力的にスケーリングできます。
</Info>

まとめると、次のとおりです。

* **Elastic**: 分片は JVM メモリに紐づく物理的な Lucene 構造です。分片を過剰に作成するとパフォーマンスが低下します。レプリケーションは同期的で、マスターノードによって協調されます。
* **ClickHouse**: 分片は論理的で垂直方向にスケーラブルであり、ローカル実行は非常に効率的です。レプリケーションは非同期 (ただしシーケンシャルにすることも可能) で、協調の仕組みは軽量です。

結局のところ、ClickHouse は分片のチューニングの必要性を最小限に抑えることで、大規模環境でのシンプルさとパフォーマンスを重視しつつ、必要に応じて強力な整合性保証も提供します。

### 重複排除とルーティング {#deduplication-and-routing}

Elasticsearch はドキュメントを `_id` に基づいて重複排除し、それに応じて分片へルーティングします。ClickHouse はデフォルトの行識別子を保持しませんが、**insert-time の重複排除**をサポートしているため、失敗した挿入処理を安全に再試行できます。より細かく制御したい場合は、`ReplacingMergeTree` などのテーブルエンジンを使用して、特定のカラムに基づく重複排除を行えます。

Elasticsearch のインデックスルーティングにより、特定のドキュメントは常に特定の分片へルーティングされます。ClickHouse では、**分片キー**を定義するか `Distributed` テーブルを使用することで、同様のデータ局所性を実現できます。

### 集計と実行モデル {#aggregations-execution-model}

どちらのシステムもデータの集計をサポートしていますが、ClickHouse は統計関数、近似関数、特化型の分析関数を含め、はるかに[多くの関数](/ja/reference/functions/aggregate-functions/reference-index)を提供しています。

オブザーバビリティのユースケースにおける集計の代表的な用途の 1 つは、特定のログメッセージやイベントの発生回数をカウントすること(および頻度が異常な場合にアラートを発報すること)です。

ClickHouse の `SELECT count(*) FROM ... GROUP BY ...` という SQLクエリに相当する Elasticsearch の機能は [terms 集計](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html) で、これは Elasticsearch の [bucket 集計](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket.html) の一種です。

ClickHouse の `count(*)` を用いた `GROUP BY` と Elasticsearch の terms 集計は、機能面では概ね同等ですが、実装、パフォーマンス、結果の品質には大きな違いがあります。

Elasticsearch のこの集計は、クエリ対象のデータが複数の分片にまたがる場合、[「top-N」クエリの結果を推定します](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-terms-aggregation#terms-agg-doc-count-error)(例: カウント上位 10 件のホスト)。この推定によって速度は向上しますが、精度が犠牲になる可能性があります。[`doc_count_error_upper_bound` を確認](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#terms-agg-doc-count-error)し、`shard_size` パラメータを増やすことでこの誤差を小さくできますが、その代わりにメモリ使用量が増え、クエリパフォーマンスが低下します。

また、Elasticsearch ではすべてのバケット集計に [`size` 設定](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-terms-aggregation.html#search-aggregations-bucket-terms-aggregation-size)が必要で、上限を明示的に指定せずにすべての一意なグループを返すことはできません。high-cardinality な集計では [`max_buckets` の制限](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-settings.html#search-settings-max-buckets)に達するおそれがあるほか、[composite 集計](https://www.elastic.co/docs/reference/aggregations/search-aggregations-bucket-composite-aggregation)によるページネーションが必要になる場合もありますが、これは多くの場合、複雑かつ非効率です。

これに対し ClickHouse は、追加設定なしで正確な集計を実行します。`count(*)` などの関数は設定を調整しなくても正確な結果を返すため、クエリの挙動がシンプルで予測しやすくなります。

ClickHouse にはサイズ制限がなく、大規模なデータセットに対して無制限の group-by クエリを実行できます。メモリのしきい値を超えた場合は、[ディスクへスピル](/ja/reference/statements/select/group-by#group-by-in-external-memory)させることも可能です。主キーのプレフィックスでグループ化する集計は特に効率的で、多くの場合、最小限のメモリ消費量で実行されます。

#### 実行モデル {#execution-model}

上記の違いは、Elasticsearch と ClickHouse の実行モデルの違いに起因します。両者は、クエリ実行と並列度に対して根本的に異なるアプローチを採用しています。

ClickHouse は、最新のハードウェア上で最大限の効率を発揮するように設計されています。デフォルトでは、ClickHouse は N 個の CPU コアを持つマシン上で、N 本の同時実行レーンを使って SQL クエリを実行します。

  <Frame>
    ![ClickHouse の実行](/images/use-cases/observability/clickhouse-execution.webp)
  </Frame>
</div>

単一ノード上では、実行レーンがデータを独立した範囲に分割し、複数の CPU スレッドで同時に処理できるようにします。この処理にはフィルタリング、集約、ソートが含まれます。各レーンのローカル結果は最終的にマージされ、クエリに LIMIT 句が含まれる場合は limit 演算子が適用されます。

クエリ実行は、さらに次の仕組みによって並列化されます。

1. **SIMD ベクトル化**: 列指向データに対する演算には [CPU SIMD 命令](https://en.wikipedia.org/wiki/Single_instruction,_multiple_data) (例: [AVX512](https://en.wikipedia.org/wiki/AVX-512)) が使用され、値をまとめてバッチ処理できます。
2. **クラスターレベルの並列度**: 分散構成では、各ノードがローカルでクエリ処理を行います。[部分集約状態](https://clickhouse.com/blog/aggregate-functions-combinators-in-clickhouse-for-arrays-maps-and-states#working-with-aggregation-states)はクエリを発行したノードにストリーミングされ、そこでマージされます。クエリの `GROUP BY` キーがシャーディングキーと一致する場合、マージを[最小限に抑える、または完全に省く](/ja/reference/settings/session-settings/distributed#distributed_group_by_no_merge)ことができます。

<br />

このモデルにより、コアやノードをまたいで効率的にスケールできるため、ClickHouse は大規模な分析に適しています。*部分集約状態*を使用することで、異なるスレッドやノードの中間結果を、精度を損なうことなくマージできます。

一方、Elasticsearch は、利用可能な CPU コアの数に関係なく、ほとんどの集計で分片ごとに 1 つのスレッドしか割り当てません。これらのスレッドは分片単位の上位 N 件の結果を返し、それらがコーディネーターノードでマージされます。この方式ではシステムリソースを十分に活用できないうえ、特に出現頻度の高い term が複数の分片に分散している場合、グローバルな集計結果が不正確になる可能性があります。`shard_size` パラメータを大きくすれば精度は向上しますが、その代わりにメモリ使用量とクエリレイテンシが増加します。

<div className="ch-image-lg">
  <Frame>
    ![Elasticsearch の実行](/images/use-cases/observability/elasticsearch-execution.webp)
  </Frame>
</div>

まとめると、ClickHouse はよりきめ細かな並列度でハードウェアリソースを柔軟に制御しながら集計とクエリを実行するのに対し、Elasticsearch は制約の多い分片ベースの実行に依存しています。

それぞれの技術における集計の仕組みの詳細については、ブログ記事 [&quot;ClickHouse vs. Elasticsearch: The Mechanics of Count Aggregations&quot;](https://clickhouse.com/blog/clickhouse_vs_elasticsearch_mechanics_of_count_aggregations#elasticsearch) をご覧ください。

### データ管理 {#data-management}

Elasticsearch と ClickHouse では、時系列のオブザーバビリティデータの管理に対するアプローチが根本的に異なります。特にデータ保持、ロールオーバー、階層型ストレージの扱いにその違いが顕著に表れます。

#### インデックスライフサイクル管理とネイティブ 有効期限 (TTL) の比較 {#lifecycle-vs-ttl}

Elasticsearch では、長期的なデータ管理は **Index Lifecycle Management (ILM)** と **Data Streams** によって行われます。これらの機能を使用すると、インデックスをロールオーバーするタイミング (例：一定のサイズや経過期間に達した時点) 、古いインデックスを低コストのストレージ (例：warm ティアや cold ティア) へ移動するタイミング、そして最終的に削除するタイミングを制御するポリシーを定義できます。これが必要なのは、Elasticsearch が**再シャーディングをサポートしていない**ためです。また、分片はパフォーマンスを低下させずに際限なく大きくすることはできません。そのため、分片のサイズを管理し、効率的な削除を実現するには、新しいインデックスを定期的に作成し、古いインデックスを削除する必要があります。つまり、実質的にインデックス単位でデータをローテーションしていることになります。

ClickHouse のアプローチは異なります。データは通常**単一のテーブル**に保存され、カラムレベルまたはパーティションレベルの **有効期限 (TTL) 式**によって管理されます。データを**日付でパーティション分割**しておけば、新しいテーブルの作成やインデックスのロールオーバーを行わずに効率よく削除できます。データが古くなって 有効期限 (TTL) の条件を満たすと、ClickHouse が自動的に削除するため、ローテーション管理のための追加のインフラストラクチャは不要です。

#### ストレージ階層とホット・ウォームアーキテクチャ {#storage-tiers}

Elasticsearch は **hot-warm-cold-frozen** ストレージアーキテクチャをサポートしており、データはパフォーマンス特性の異なるストレージ階層間で移動されます。これは通常 ILM によって設定され、クラスター内のノードロールと紐付けられます。

ClickHouse は、`MergeTree` などのネイティブなテーブルエンジンによって **階層型ストレージ** をサポートしており、カスタムルールに基づいて古いデータを異なる **ボリューム** 間 (例: SSD から HDD、さらにオブジェクトストレージへ) で自動的に移動できます。これにより、複数のノードロールやクラスターを管理する手間をかけずに、Elastic の hot-warm-cold 方式と同様の構成を実現できます。

<Info>
  **ClickHouse Cloud**

  **ClickHouse Cloud** では、これがさらにシームレスになります。すべてのデータは **オブジェクトストレージ (例: S3)&#x20;**&#x20;に保存され、コンピュートはストレージから分離されています。データはクエリされるまでオブジェクトストレージに置かれたままで、クエリ時にフェッチされてローカル (または分散キャッシュ) にキャッシュされます。そのため、Elastic の frozen ティアと同等のコストで、より優れたパフォーマンスを得られます。この方式ではストレージ階層間でデータを移動する必要がないため、ホット・ウォームアーキテクチャそのものが不要になります。
</Info>

### ロールアップとインクリメンタル集約 {#rollups-vs-incremental-aggregates}

Elasticsearch では、**ロールアップ** や **集約** は [**トランスフォーム**](https://www.elastic.co/guide/en/elasticsearch/reference/current/transforms.html) と呼ばれる仕組みで実現されます。トランスフォームは、**スライディングウィンドウ** モデルを用いて、時系列データを一定の時間間隔 (例：1時間ごとや1日ごと) で要約するために使用されます。トランスフォームは定期実行されるバックグラウンドジョブとして構成され、あるインデックスのデータを集約して、その結果を別の **ロールアップインデックス** に書き込みます。これにより、high-cardinality の生データを繰り返しスキャンせずに済むため、長期間を対象とするクエリのコストを削減できます。

継続的トランスフォームは、設定可能なチェック間隔 (トランスフォームの [frequency](https://www.elastic.co/guide/en/elasticsearch/reference/current/put-transform.html)、デフォルト値は1分) に基づいて、トランスフォームの [チェックポイント](https://www.elastic.co/guide/en/elasticsearch/reference/current/transform-checkpoints.html) を使用します。上の図では、① チェック間隔が経過した後に新しいチェックポイントが作成されると仮定しています。このとき Elasticsearch はトランスフォームのソースインデックスの変更を確認し、前回のチェックポイント以降に追加された3つの新しい `blue` ドキュメント (11、12、13) を検出します。そこで、ソースインデックスから既存のすべての `blue` ドキュメントが抽出され、 (結果の [ページネーション](https://www.elastic.co/guide/en/elasticsearch/reference/current/paginate-search-results.html) を利用するために) [composite 集約](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-aggregations-bucket-composite-aggregation.html) によって集約値が再計算されます (宛先インデックスでは、以前の集約値を含むドキュメントが新しいドキュメントで置き換えられます) 。② と ③ でも同様に、変更を確認したうえで、同じ &#39;blue&#39; バケットに属する既存のすべてのドキュメントから集約値を再計算することで、新しいチェックポイントが処理されます。

ClickHouse は根本的に異なるアプローチを採用しています。データを定期的に再集約するのではなく、ClickHouse は **インクリメンタルmaterialized view** をサポートしており、データを **挿入時** に変換・集約します。新しいデータがソーステーブルに書き込まれると、materialized view は新しく **挿入されたブロック** のみに対して事前定義された SQL 集約クエリを実行し、集約結果をターゲットテーブルに書き込みます。

このモデルを可能にしているのが、ClickHouse がサポートする [**部分集約状態**](/ja/reference/data-types/aggregatefunction) です。これは集約関数の中間表現であり、保存しておいて後からマージできます。これにより、高速にクエリでき、低コストで更新できる部分集約結果を維持できます。集約はデータの到着時に行われるため、コストの高い定期ジョブを実行したり、古いデータを再要約したりする必要はありません。

インクリメンタルmaterialized view の仕組みを抽象的に示します (集約値を事前計算したい同一グループに属するすべての行を青色で示しています) 。

  </Frame>
</div>

上の図では、materialized view のソーステーブルに、同じグループに属するいくつかの `blue` 行 (1〜10) を格納したデータパーツがすでに存在します。このグループについては、ビューのターゲットテーブルにも、`blue` グループの [部分集計状態](https://www.youtube.com/watch?v=QDAJTKZT8y4) を格納したデータパーツがすでに存在します。① ② ③ で新しい行がソーステーブルに挿入されると、挿入ごとに対応するソーステーブルのデータパーツが作成されます。それと並行して、新しく挿入された行のブロックごとに (そのブロックのみを対象に) 部分集計状態が計算され、データパーツとして materialized view のターゲットテーブルに挿入されます。④ バックグラウンドでのパーツのマージ時に部分集約状態がマージされ、データのインクリメンタル集約が実現されます。

なお、90 を超えるすべての [集約関数](/ja/reference/functions/aggregate-functions/reference-index) は、集約関数の [コンビネータ](https://www.youtube.com/watch?v=7ApwD0cfAFI) と組み合わせた場合も含めて、[部分集約状態](/ja/reference/data-types/aggregatefunction) をサポートしています。

インクリメンタル集約における Elasticsearch と ClickHouse のより具体的な比較については、こちらの [例](https://github.com/ClickHouse/examples/tree/main/blog-examples/clickhouse-vs-elasticsearch/continuous-data-transformation#continuous-data-transformation-example) を参照してください。

ClickHouse のアプローチには、次のような利点があります。

* **常に最新の集約**: materialized view は常にソーステーブルと同期しています。
* **バックグラウンドジョブが不要**: 集計はクエリ実行時ではなく挿入時に行われます。
* **優れたリアルタイムパフォーマンス**: 最新の集約結果を即座に必要とするオブザーバビリティのワークロードやリアルタイム分析に最適です。
* **組み合わせ可能**: materialized view は他のビューやテーブルと多段に重ねたり結合したりできるため、より高度なクエリ高速化戦略を実現できます。
* **個別の有効期限 (TTL)**: materialized view のソーステーブルとターゲットテーブルに、それぞれ異なる有効期限 (TTL) 設定を適用できます。

このモデルは、クエリのたびに数十億件の未加工レコードをスキャンすることなく、1分あたりのエラー率、レイテンシ、上位 N 件の内訳といったメトリクスを算出する必要があるオブザーバビリティのユースケースで、特に威力を発揮します。

### レイクハウスのサポート {#lakehouse-support}

ClickHouse と Elasticsearch では、レイクハウスとのインテグレーションに対するアプローチが根本的に異なります。ClickHouse は本格的なクエリ実行エンジンであり、[Iceberg](/ja/reference/functions/table-functions/iceberg) や [Delta Lake](/ja/reference/functions/table-functions/deltalake) などのレイクハウスフォーマットに対してクエリを実行できるほか、[AWS Glue](/ja/guides/use-cases/data-warehousing/glue-catalog) や [Unity catalog](/ja/guides/use-cases/data-warehousing/unity-catalog) などのデータレイクカタログとも連携できます。これらのフォーマットでは [Parquet](/ja/reference/formats/Parquet/Parquet) ファイルを効率的にクエリできることが前提となりますが、ClickHouse はこれを完全にサポートしています。ClickHouse は Iceberg テーブルと Delta Lake テーブルのどちらも直接読み取れるため、最新のデータレイクアーキテクチャとシームレスに統合できます。

一方、Elasticsearch は独自の内部データフォーマットと Lucene ベースのストレージエンジンに密結合しています。レイクハウスフォーマットや Parquet ファイルに直接クエリを実行できないため、最新のデータレイクアーキテクチャへの組み込みには制約があります。Elasticsearch では、クエリを実行する前にデータを変換し、独自フォーマットに取り込む必要があります。

ClickHouse のレイクハウス機能は、データの読み取りだけにとどまりません。

* **データカタログとの連携**: ClickHouse は [AWS Glue](/ja/guides/use-cases/data-warehousing/glue-catalog) などのデータカタログとの連携をサポートしており、オブジェクトストレージ内のテーブルを自動的に検出してアクセスできます。
* **オブジェクトストレージのサポート**: [S3](/ja/reference/engines/table-engines/integrations/s3)、[GCS](/ja/reference/functions/table-functions/gcs)、[Azure Blob Storage](/ja/reference/engines/table-engines/integrations/azureBlobStorage) 上のデータを、移動することなく直接クエリできるネイティブサポートを備えています。
* **クエリフェデレーション**: [外部辞書](/ja/concepts/features/dictionaries/index)や[テーブル関数](/ja/reference/functions/table-functions/index)を使用して、レイクハウステーブル、従来型データベース、ClickHouse テーブルなど、複数のソースにまたがるデータを関連付けられます。
* **増分読み込み**: [S3Queue](/ja/reference/engines/table-engines/integrations/s3queue) や [ClickPipes](/ja/integrations/clickpipes/home) などの機能を使用して、レイクハウステーブルからローカルの [MergeTree](/ja/reference/engines/table-engines/mergetree-family/mergetree) テーブルへ継続的にデータを取り込めます。
* **パフォーマンスの最適化**: [クラスター関数](/ja/reference/functions/table-functions/cluster)を使用してレイクハウスデータに対するクエリを分散実行し、パフォーマンスを向上させます。

これらの機能により、ClickHouse はレイクハウスアーキテクチャを採用する組織に最適な選択肢となり、データレイクの柔軟性と列指向データベースのパフォーマンスを両立できます。
