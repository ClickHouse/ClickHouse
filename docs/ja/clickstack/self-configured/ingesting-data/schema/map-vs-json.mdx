<Note>
  このページでは **Self-managed ClickHouse Observability** について説明します。推奨される完全マネージド型の環境については、[こちら](/ja/clickstack/observability/overview)のドキュメントを参照してください。
</Note>

[デフォルトのスキーマ](/ja/clickstack/self-configured/ingesting-data/schemas)では、リソース、スコープ、ログ、スパンの各属性を `Map(LowCardinality(String), String)` カラムとして保存します。ClickHouse は強く型付けされた [`JSON` 型](/ja/reference/formats/JSON/JSON) もサポートしており、Self-managed ClickHouse Observability では、`Map` の代わりにこの型を使用する機能をベータサポートとして提供しています。

**一般的なオブザーバビリティのワークロードでは、[デフォルトの `Map` ベースのスキーマ](/ja/clickstack/self-configured/ingesting-data/schemas)をそのまま使用することを推奨します。** JSON型は、属性キーの種類が少なく安定しているワークロードで評価を行いたいユーザー向けに提供されていますが、一般的な用途には推奨されません。

## Map が推奨されるデフォルトである理由 {#why-map}

オブザーバビリティデータの大部分を占めるのは、リソース属性、スコープ属性、スパン属性、ログ属性といった属性です。これらの属性セットは通常、規模が大きく high-cardinality であり、高スループットで取り込まれます。これらの属性にどのスキーマを選ぶかが、取り込みコストとストレージレイアウトを左右する最大の要因となります。

`Map(LowCardinality(String), String)` は、キーと値を単一の構造として格納します。従来の `Map` の欠点は、単一のキーを読み取るだけでも Map のカラム全体を読み取る必要があることでした。しかし、現在はそうではありません。ClickHouse は [バケット化された Map のシリアライズ](/ja/reference/data-types/map#bucketed-map-serialization) をサポートしており、Map をバケットに分割するため、クエリは必要なバケットのみを読み取ります。さらに、[デフォルトのスキーマ](/ja/clickstack/self-configured/ingesting-data/schemas) の設定のように、Map のキーと値に [テキストインデックス](/ja/reference/engines/table-engines/mergetree-family/textindexes) を組み合わせることで、`Map` は新しいキーによる取り込み時のペナルティを一切負わずに、読み取り時には選択的かつ高速に動作します。

具体的には、次のような利点があります。

* **キーが増えても取り込みコストが安定。** 新しい属性キーを追加しても、on-disk のカラムレイアウトは変わらず、新しいカラムファイルも作成されません。取り込みコストを決めるのはキーのカーディナリティではなく、データ量です。
* **メタデータの肥大化が起きない。** ディスク上のカラムファイルの数は、一意な属性キーの数に応じて増えることはありません。
* **索引による選択的なルックアップ。** Map のキーと値に対するテキストインデックスにより、全行をスキャンすることなくポイントルックアップを実行できます。
* **高スループットでも予測可能な動作。** Map は、トレーシングやログでよく見られるバースト的でスキーマレスな属性セットを、キーごとのオーバーヘッドなしで処理します。

## JSON をデフォルトにしない理由 {#why-not-json}

`JSON` 型は異なるアプローチを採用しています。挿入時に、ClickHouse は検出したパスごとに、強く型付けされた専用のサブカラムを動的に作成します。これは読み取り時には魅力的です。要求されたサブカラムのみが読み取られ、型が保持され、クエリ実行時のキャストも不要だからです。

その代償は取り込み時に生じます。多数の動的サブカラムを作成・管理するため、書き込み時のオーバーヘッドが発生し、メタデータも複雑になります。属性セットが非常に大きい、あるいは変動が激しいことが常態化しており、取り込みスループットも高いオブザーバビリティのワークロードでは、このオーバーヘッドは無視できません。[`max_dynamic_paths`](/ja/reference/data-types/newjson#reading-json-paths-as-sub-columns) の上限を設定すれば、超過したパスを共有カラムにスピルさせて影響を抑えられます。しかし、共有カラムへのアクセスは専用サブカラムより遅いため、そもそも JSON を採用する動機となった読み取り時の利点が損なわれてしまいます。

バケット化されたマップのシリアライズによって、`Map` が従来抱えていた読み取り時のオーバーヘッドの大部分が解消されました。そのため、一般的なオブザーバビリティのワークロードでは、`JSON` の読み取り時の利点が取り込み時のコストを上回ることはもはやありません。

## それでも JSON を検討する価値がある場合 {#when-to-consider-json}

次の条件を*すべて*満たす場合は、JSON型も妥当な選択肢となり得ます。

* 属性キーの集合が**小規模かつ安定している**。つまり、重複のないキーが数千にも及ぶことはなく、新しいキーが追加されることもまれである。
* 取り込みスループットが、属性のカーディナリティに比べて**それほど高くない**。
* クエリ時にキャストすることなく、属性に**強く型付けされた形でアクセス**したい(数値は数値のまま、ブール値はブール値のまま扱われる)。
* Self-managed ClickHouse Observability で**ベータ機能**を運用することを許容し、連携が今後変更される可能性も受け入れられる。

これらの条件の一部でも満たさない場合は、引き続き[デフォルトの `Map`ベースのスキーマ](/ja/clickstack/self-configured/ingesting-data/schemas)を使用してください。

## ベータステータス {#beta-status}

<BetaBadge />

<Warning>
  **ベータ機能のため、本番環境での利用には対応していません**

  **Self-managed ClickHouse Observability** における JSON型のサポートは**ベータ機能**です。JSON型自体は ClickHouse 25.3 以降で本番環境に対応していますが、本サービスへの連携はまだ活発に開発が進められている段階であり、制限がある、今後仕様が変更される、あるいはバグが含まれる可能性があります。
</Warning>

ClickStack は、バージョン `2.0.4` 以降で JSON型をベータサポートしています。

## JSON サポートの有効化 {#enabling-json-support}

[デフォルトの `Map`ベースのスキーマ](/ja/clickstack/self-configured/ingesting-data/schemas)ではなく JSON型のスキーマを使用するには、次の環境変数を設定します。

| 変数                                                              | 設定先                                | 目的                                 |
| --------------------------------------------------------------- | ---------------------------------- | ---------------------------------- |
| `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'` | ClickHouse Observability Collector | JSON型を使用して ClickHouse にスキーマを作成します。 |

<a id="managed-clickstack" />

Self-managed ClickHouse Observability で JSON サポートを有効化するには、collector を設定する前に support@clickhouse.com までお問い合わせください。あわせて、ClickHouse Cloud のオブザーバビリティ UI でもこの機能を有効にする必要があります。

collector に `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'` を設定します。例:

```shell
docker run -e OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json' -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
```

## Map ベースのスキーマから JSON への移行 {#migrating-from-map-to-json}

<Warning>
  **後方互換性**

  [JSON型](/ja/reference/formats/JSON/JSON)は、既存の Map ベースのスキーマとの**後方互換性がありません**。この機能を有効にすると `JSON` 型を使用する新しいテーブルが作成されるため、データを手動で移行する必要があります。
</Warning>

[デフォルトの Map ベースのスキーマ](/ja/clickstack/self-configured/ingesting-data/schemas)から移行するには、次の手順を実行します。

<Steps>
  <Step title="OTel collector を停止する" id="stop-the-collector" />

  <Step title="既存のテーブルをリネームしてソースを更新する" id="rename-existing-tables-sources">
    既存のテーブルをリネームし、オブザーバビリティ UI でデータソースを更新します。

    例:

    ```sql
    RENAME TABLE otel_logs TO otel_logs_map;
    RENAME TABLE otel_metrics TO otel_metrics_map;
    ```
  </Step>

  <Step title="collector をデプロイする" id="deploy-the-collector">
    `OTEL_AGENT_FEATURE_GATE_ARG` を設定して collector をデプロイします。
  </Step>

  <Step title="JSON スキーマ対応が有効になっていることを確認する" id="restart-the-hyperdx-container">
    新しいデータソースを作成する前に、オブザーバビリティ UI で JSON スキーマ対応が有効になっているかどうかを support@clickhouse.com に問い合わせて確認してください。
  </Step>

  <Step title="新しいデータソースを作成する" id="create-new-data-sources">
    オブザーバビリティ UI で、JSON テーブルを参照する新しいデータソースを作成します。
  </Step>
</Steps>

### 既存データの移行 (任意) {#migrating-existing-data}

既存のデータを新しい JSON テーブルへ移動するには、次の手順を実行します。

```sql
INSERT INTO otel_logs SELECT * FROM otel_logs_map;
INSERT INTO otel_metrics SELECT * FROM otel_metrics_map;
```

<Warning>
  この方法は、データセットが約100億行未満の場合にのみ推奨されます。Map型で保存された既存のデータでは、型の精度が保持されていません(すべての値が文字列として保存されています)。そのため、この古いデータは保持期間を過ぎて削除されるまで、新しいスキーマでは文字列として表示され、フロントエンド側で一部キャストが必要になります。新しいデータについては、JSON型によって型が保持されます。
</Warning>
