<Note>
  このページでは **Self-managed ClickHouse Observability** について説明します。推奨される完全マネージド型の環境については、[こちら](/ja/clickstack/observability/getting-started)のドキュメントを参照してください。
</Note>

このガイドでは、空の Self-managed ClickHouse Observability サービスから始めて、実際のアプリケーションからログ、メトリクス、トレース、セッションリプレイが流れ込む状態になるまでを順を追って説明します。サービスに接続する新しい OpenTelemetry collector をデプロイし(既存のものがあればそれを流用し)、ビジネスロジックに一切手を加えずにサンプルの Node.js アプリケーションをインストルメントしたうえで、ClickStack UI でテレメトリーを探索します。

<Note>
  新しい collector をセットアップする場合も、独自の collector を使用する場合も、**ゲートウェイ**として実行する必要があります。ゲートウェイとは、アプリケーション、SDK、エージェントコレクターの送信先となる単一の OTLP エンドポイントです。ゲートウェイはイベントをバッチ処理し、設定済みの処理を適用したうえで、[ClickHouse exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) を介して ClickHouse に書き込みます。
</Note>

インストルメント対象のアプリケーションは [HackerNews Analyzer](https://github.com/ClickHouse/hn-news-analyzer) です。これは、パブリックな ClickHouse デモでホストされている HackerNews データセットにクエリを実行する Node.js アプリです。すべてのチャート、テーブル、検索ボックスは実際の ClickHouse クエリで動作しているため、操作のたびにトレースが生成されます。そのメインスパンは、バックエンドから ClickHouse への HTTPS 呼び出しです。

## 前提条件 {#prerequisites}

* [ClickHouse Cloud](https://console.clickhouse.cloud) 上の **Self-managed ClickHouse Observability サービス**。
* サンプルアプリケーションを実行するための **Node 18+ と npm**。
* **Docker** (collector をまだ用意しておらず、後述の新しい collector を使う手順に沿って進める場合) 。

  <Step title="collectorをデプロイする" id="deploy-collector">
    ご自身の状況に合ったオプションを選択してください。

    <Info>
      **既存の collector**

      既存の OpenTelemetry collector を使用する場合は、その collector がすでに**ゲートウェイ**ロールとして設定済みであることを前提とします。**エージェント**ロールのコレクターを再設定する目的で、この手順を使用することは推奨しません。
    </Info>

    <Tabs>
      <Tab title="collector がありません">
        セルフマネージドな ClickHouse オブザーバビリティ向けに事前設定された **OpenTelemetry collector の ClickStack ディストリビューション**をデプロイします。以下の例では、説明を簡単にするため collector をローカルで実行します。

        <Note>
          本番環境では通常、collector を Kubernetes クラスター内、または OpenTelemetry SDKs、エージェント、その他のコレクターから到達可能な仮想マシン上にデプロイします。これにより、環境全体のテレメトリーを一元的に収集し、ClickStack に転送できます。
        </Note>

        collector にデータを送信するクライアントを認証するための共有シークレットを決め、接続情報および `hyperdx_ingest` ユーザー用に設定したパスワードとあわせて環境変数としてエクスポートします。

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        ClickStack OTel コレクターを起動します：

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        これで collector は、OTLP gRPC をポート `4317` で、OTLP HTTP をポート `4318` で公開するようになりました。アプリケーション、SDK、およびエージェントとして動作するコレクターは、リクエストヘッダーに `authorization: $OTLP_AUTH_TOKEN` を含めて、これらのポートにデータを送信する必要があります。次のステップでアプリケーションの送信先として指定するため、OTLP エンドポイントと `OTLP_AUTH_TOKEN` を控えておいてください。

        <Info>
          **本番環境へのデプロイメント**

          本番環境では、OTLP エンドポイントで TLS を有効にすることを推奨します。詳しくは [collector のセキュリティ保護](/ja/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured)を参照してください。
        </Info>
      </Tab>

      <Tab title="すでに collector を使用している">
        既存のコレクター設定を拡張し、[ClickHouse exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) を使用して Self-managed ClickHouse Observability にデータを書き込むようにします。

        <Info>
          **ClickHouse exporter が必要です**

          独自のディストリビューションを使用している場合は、ClickHouse exporter が含まれていることを確認してください。アップストリームの [contrib イメージ](https://github.com/open-telemetry/opentelemetry-collector-contrib) には、すでに含まれています。
        </Info>

        以下は、ClickStack UI が前提とするレシーバー、プロセッサ、パイプラインと組み合わせて ClickHouse exporter を使用する設定例です。セッションリプレイ (`rrweb`) のルーティングパスも含め、ClickStack ディストリビューションと同じ動作になります。`<clickhouse_cloud_endpoint>` と `<your_password_here>` は、前の手順で作成した `hyperdx_ingest` ユーザーの認証情報に置き換えてください。

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        注意点は次のとおりです。

        * `otlp/hyperdx` receiver は gRPC (`4317`) と HTTP (`4318`) の両方で待ち受けます。アプリケーションやエージェントからは、collector ホスト上のこれらのポートに送信してください。
        * `clickhouse` エクスポーターは、ログ、トレース、メトリクスを ClickStack UI が想定するレイアウトで `otel` データベースに書き込みます。`clickhouse/rrweb` エクスポーターは、`routing/logs` コネクタによって `otel.hyperdx_sessions` に振り分けられたセッションリプレイのイベントを処理します。
        * OTLP レシーバーの認証は、既存の環境の構成に委ねられています。インジェスト用トークンを必須にする場合は、collector の[拡張機能](https://opentelemetry.io/docs/collector/configuration/#extensions) (例: `bearertokenauth`) を使用するか、TLS 終端を担うリバースプロキシを前段に配置して設定してください。

        新しい設定で collector を再読み込みします。OTLP エンドポイントと、環境で必要となる認証ヘッダーを控えておいてください。次のステップで、アプリケーションの送信先として指定します。

        Self-managed ClickHouse Observability 向けの OpenTelemetry コレクターの設定について詳しくは、[OpenTelemetry を使用したデータ取り込み](/ja/clickstack/observability/ingesting-data/opentelemetry#self-managed)を参照してください。
      </Tab>
    </Tabs>
  </Step>

  <Step title="アプリケーションのクローンと実行" id="clone-and-run-the-application">
    リポジトリをクローンし、依存関係をインストールして、`.env` ファイルを作成します。

    ```bash
    git clone https://github.com/ClickHouse/hn-news-analyzer.git
    cd hn-news-analyzer
    npm install
    cp .env.example .env
    ```

    ClickHouse データソースはデフォルトでパブリックな読み取り専用のデモクラスターに接続するため、追加の設定なしでアプリを実行できます。次のコマンドで起動します。

    ```bash
    ./run.sh
    ```

    [http://localhost:5001](http://localhost:5001) を開きます。年のセレクター、概要統計、アクティビティチャート、上位ユーザーおよび上位ドメインのテーブル、検索ボックスが表示されます。年を切り替えたり、ストーリーの詳細を開いたりして、自由に操作してみてください。

    <div className="ch-image-lg">
      <Frame>
        ![ローカルで実行中の HackerNews Analyzer アプリケーション](/images/clickstack/getting-started/hackernews_main.webp)
      </Frame>
    </div>

    この時点では、アプリケーションは動作していますが、まだインストルメントされていません。ClickStack にはデータが表示されず、テレメトリーの受信を待っている状態です。これが「導入前」の状態です。
  </Step>

  <Step title="アプリケーションをcollectorに接続する" id="connect-the-application">
    アプリケーションが上記でデプロイした collector に接続するには、次の 2 つの値が必要です。

    * `OTEL_EXPORTER_OTLP_ENDPOINT`: collector が公開している OTLP エンドポイント (OTLP over HTTPS の場合、通常はポート `4318`) 。
    * `OTEL_EXPORTER_OTLP_HEADERS`: インジェストトークンを含む認証ヘッダー。形式は `authorization=<ingestion_token>` です。上記で collector に設定した `OTLP_AUTH_TOKEN`、または既存の collector が要求する認証ヘッダーを指定してください。

    `.env.example` を `.env` としてコピーし、ファイルを開いて次の変数を設定します。

    ```bash
    OTEL_SERVICE_NAME=hn-analyzer-api
    OTEL_EXPORTER_OTLP_ENDPOINT=https://<your-collector-endpoint>:4318
    OTEL_EXPORTER_OTLP_HEADERS=authorization=<ingestion_token>
    ```

    SDK は `OTEL_EXPORTER_OTLP_HEADERS` を使用して、トレース、メトリクス、ログの 3 つすべてのシグナルに対する認証ヘッダーを設定します。collector をローカルで実行していて認証を必須としていない場合は、値を空のままにしても構いません (`OTEL_EXPORTER_OTLP_HEADERS=authorization=`) 。ただし、変数自体は必ず定義しておく必要があります。変数が未設定の場合や完全に空の場合、SDK は初期化処理を一切行いません。また、collector を TLS なしで実行する場合は、正しい HTTP プロトコル (例: `http://localhost:4318`) を使用していることを確認してください。
  </Step>

  <Step title="アプリケーションをインストルメントする" id="instrument-the-application">
    インストルメンテーションは 3 つの手順で構成されます。SDK のインストール、起動コマンドの切り替え、ブラウザー SDK の有効化です。いずれもアプリケーションのビジネスロジックを変更するものではありません。

### SDK をインストールする {#install-sdks}

    バックエンド用とブラウザー用の両方の OpenTelemetry SDKs をインストールします。

    ```bash
    npm install @hyperdx/node-opentelemetry @hyperdx/browser
    ```

### opentelemetry-instrument CLI を使用する {#use-open-telemetry-cli}

    アプリケーションは `run.sh` によって起動されます。このファイルの末尾には `exec` 行が 2 つあり、一方は有効、もう一方はコメントアウトされています。Node が `opentelemetry-instrument` でラップされるように、有効にする行を入れ替えます:

    ```diff
     # BEFORE: plain node, no instrumentation, collector stays silent:
    -exec node scripts/entrypoint.js
    +# exec node scripts/entrypoint.js

     # AFTER: same source, wrapped by opentelemetry-instrument CLI.
    -# exec npx opentelemetry-instrument scripts/entrypoint.js
    +exec npx opentelemetry-instrument scripts/entrypoint.js
    ```

    バックエンドの変更はこれだけです。自動計装は、プロセスの起動時に `opentelemetry-instrument` によって読み込まれます。

### ブラウザー SDK を有効化する {#enable-browser-sdk}

    分散トレース (ブラウザーからバックエンドまで) とセッションリプレイを収集するには、`src/web/telemetry.ts` でブラウザー SDK を有効化します。import 文と `HyperDX.init({...})` ブロックのコメントアウトを解除してください。

    ```javascript
    import HyperDX from '@hyperdx/browser';

    export function initTelemetry(): void {
      HyperDX.init({
        url: __OTLP_ENDPOINT__,
        apiKey: __OTLP_AUTH_TOKEN__,
        service: 'hn-analyzer-web',
        tracePropagationTargets: [/localhost:5001/i, /\/api\//i],
        consoleCapture: true,
        advancedNetworkCapture: true,
      });
    }
    ```

    `.env` を追加で編集する必要はありません。`__OTLP_ENDPOINT__` と `__OTLP_AUTH_TOKEN__` は、`vite.config.ts` によって注入されるコンパイル時定数です。エンドポイントには `OTEL_EXPORTER_OTLP_ENDPOINT` が使われ、トークンは `OTEL_EXPORTER_OTLP_HEADERS` からパースされます。いずれもバックエンドが使用するものと同じ値です。

    <Warning>
      インジェスト用トークンは公開されるブラウザバンドルに埋め込まれるため、ネットワークタブを確認すれば誰でも読み取ることができます。
    </Warning>
  </Step>

  <Step title="トラフィックを生成する" id="generate-traffic">
    新しい起動コマンドと新たにビルドしたブラウザバンドルを反映させるため、アプリケーションを再起動します。

    ```bash
    # Ctrl-C the previous run, then:
    ./run.sh
    ```

    ブラウザのタブを再読み込みして Vite に更新後のバンドルを配信させたら、アプリを何度かリロードしたり、年を切り替えたり、ストーリーを開いたりしてトラフィックを発生させます。操作のたびに、ログ、メトリクス、トレース、セッションリプレイのイベントが collector を経由して ClickStack に送信されます。
  </Step>

  <Step title="ClickStack を起動してテレメトリーを探索する" id="launch-clickstack">
    [ClickHouse Cloud コンソール](https://console.clickhouse.cloud)でサービスを開き、左側のメニューから **ClickStack** を選択して、**Start Ingestion** をクリックします。

    <div className="ch-image-lg">
      <Frame>
        ![ClickStack を起動](/images/use-cases/observability/clickstack-cloud-first-time.webp)
      </Frame>
    </div>

    collector はすでに設定済みのため、次のステップはスキップできます。**Launch ClickStack** をクリックして続行します。

    ClickStack が新しいタブで開き、自動的に **Getting Started** ページへ移動します。移動しない場合は、左側のメニューから **Getting Started** を選択し、**Start Ingestion**、**Next** の順にクリックします。

    <div className="ch-image-lg">
      <Frame>
        ![ClickStack のインジェスト開始](/images/use-cases/observability/clickstack-start-ingestion.webp)
      </Frame>
    </div>

    ClickStack がテーブルとテレメトリデータを自動的に検出するので、そのまま次に進めます。**Start Exploring** を選択して、データの探索を開始します。

    <div className="ch-image-lg">
      <Frame>
        ![ClickStack の探索開始](/images/use-cases/observability/clickstack-start-exploring.webp)
      </Frame>
    </div>

    それでは、アプリケーションが生成しているデータを確認しましょう。

    1. **Search** に移動し、直近 5 分間で絞り込みます。`hn-analyzer-api` のログが次々と表示されます。

    <div className="ch-image-lg">
      <Frame>
        ![ClickStack のログ](/images/clickstack/getting-started/instrument_app_clickstack_logs.webp)
      </Frame>
    </div>

    2. リクエストをクリックし、トレースを遡って確認します。Express ハンドラーのスパン、実際のネットワーク所要時間を示す ClickHouse クラスター宛ての子 HTTP スパン、そして同じトレースに関連付けられた `console.log` レコードが表示されます。

    <div className="ch-image-lg">
      <Frame>
        ![ClickStack のトレース](/images/clickstack/getting-started/instrument_app_clickstack_traces.webp)
      </Frame>
    </div>

    3. **Session Replay** を開くと、トレースのタイムラインと同期したブラウザセッションの動画を、シークしながら再生できます。

    <div className="ch-image-lg">
      <Frame>
        ![ClickStack のセッション](/images/clickstack/getting-started/instrument_app_clickstack_sessions.webp)
      </Frame>
    </div>

    ログ、メトリクス、トレース、セッションリプレイはすべて同じ UI に集約され、共通のクエリ言語で扱えるうえ、自動的に相関付けられます。

    何も表示されない場合:

    * `OTEL_EXPORTER_OTLP_HEADERS` に設定した認証ヘッダー値が、collector 側で想定している値と一致しているか確認します。
    * collector のログを tail で監視し、エクスポートエラーが出ていないか確認します。
    * collector に設定した ClickHouse のエンドポイントに、プロトコルとポートの両方 (`https://...:8443`) が含まれているか確認します。
  </Step>
</Steps>
