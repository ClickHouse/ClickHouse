<Note>
  このページでは **セルフマネージド ClickHouse オブザーバビリティ** について説明します。推奨される完全マネージド型のエクスペリエンスについては、[こちら](/ja/clickstack/observability/overview)のドキュメントを参照してください。
</Note>

ClickStack をしばらく運用していれば、デフォルトのスキーマのままでもほとんどのオブザーバビリティワークロードに対応できることにお気付きでしょう。このページは、それでは不十分になってきた場合、つまりクエリのレイテンシが上昇し始めた場合や、アクセスパターンがデフォルトの想定から外れてきた場合を対象としています。

実際に効果のある施策は、ほぼ次の 4 つの最適化に集約されます。おおむね作業量の少ない順に並べています。最初の 2 つは局所的な `ALTER TABLE` による変更で、段階的に適用できます。3 つ目は、ダッシュボード上で同じ集約が繰り返し実行される場合に効果を発揮します。4 つ目はテーブル移行が必要なため、最も手間がかかります。

以下の概要はあえて簡潔にまとめています。各変更の背景にある考え方、ベンチマーク、既存データへの適用手順については、[パフォーマンスチューニング](/ja/clickstack/self-configured/managing/performance-tuning)を参照してください。

<Steps>
  <Step title="頻繁にクエリされる属性をマテリアライズする" id="materialize-attributes">
    `LogAttributes['service.version']` でフィルタすると、ClickHouse は検査対象のすべての行について `LogAttributes` Map 全体を読み込んでデコードする必要があります。この属性を `MATERIALIZED` カラムに昇格させると、同じフィルタが単一カラムの読み取りで済むようになり、通常は 1 桁程度高速になります。カラムを作成すると ClickStack がフィルタを自動的に書き換えるため、保存済みの検索やダッシュボードは変更なしでそのまま動作します。

    実際に頻繁にクエリする属性を選んでください。マテリアライズされたカラムはそれぞれストレージと挿入時の処理コストを伴うため、「すべてを昇格する」のではなく「使うものだけを昇格する」という方針で進めてください。

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    既存の行については、`ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion` を別途実行するまで新しいカラムは空のままです。

    詳細: [頻繁にクエリされる属性をマテリアライズする](/ja/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes)
  </Step>

  <Step title="スキップ索引を追加する" id="add-skip-indexes">
    スキップ索引を使うと、ClickHouse はフィルタに一致し得ないデータのグラニュールを除外できるため、スキャンを対象を絞った小規模な読み取りに置き換えられます。押さえておきたい種類は次の 3 つです。

    * **テキストインデックス** (`text(tokenizer = ...)`) : 文字列カラムおよび `mapKeys`/`*AttributeItems` 配列に対して使用します。デフォルトのログスキーマにはすでに含まれています。
    * **Min-max 索引**: 範囲でフィルタされる数値カラムに使用します。トレースの `Duration` が典型例です。
    * **Bloom フィルタ**: テキストインデックスをまだサポートしていない ClickHouse バージョンで、高カーディナリティの等価検索に使用します。

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    スキップ索引は、実際にグラニュールを除外できる場合にのみ、評価コストに見合う効果を発揮します。効果があったと判断する前に、代表的なクエリで `EXPLAIN indexes = 1` を実行して確認してください。

    詳細: [スキップ索引の追加](/ja/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes)
  </Step>

  <Step title="繰り返し実行される集約を事前計算する" id="materialized-views">
    ダッシュボード上で同じ集約が何度も実行される場合 (エラー率上位のサービス、エンドポイントごとの p99 レイテンシ、1 分あたりのリクエスト数など) 、materialized view を使えば挿入時に結果を計算し、小さなロールアップテーブルに書き込めます。ダッシュボードは生のログやトレースではなくロールアップを参照するため、はるかに低コストで済みます。

    この手法は、ダッシュボードの利用頻度が高く、元のテーブルが大きい場合に効果を発揮します。その代わり、挿入時に多少の CPU 負荷がかかり、管理するテーブルが 1 つ増えます。

    詳細: [materialized view の活用](/ja/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views)
  </Step>

  <Step title="アクセスパターンに合った主キーを選択する" id="choose-primary-key">
    主キーは、ディスク上での行の並び順を決定します。キーの先頭カラムに対するフィルタであれば ClickHouse は該当範囲へ直接シークできますが、これらのカラムを先頭に含まないフィルタではパーティション全体をスキャンすることになります。

    デフォルトのログのキー `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)` は、「サービス X で直近 N 分間に何が起きたか」というクエリに適しています。クエリの大半が別のカラム (tenant ID、顧客 ID、リージョンなど) を起点にしている場合は、そのカラムを先頭に置くよう主キーを変更するのが最も効果の大きい改善策です。

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- otel_logs と同じカラム
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse では主キーをその場で変更できないため、単純な `ALTER` ではなくテーブルの移行作業が必要です。パフォーマンスチューニングガイドでは、新しいテーブルの作成、取り込み先の切り替え、そして既存のダッシュボードが新旧両方のデータで引き続き動作するよう `Merge` テーブルを使用する手順を説明しています。

    詳細: [主キーの変更](/ja/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key)
  </Step>
</Steps>
