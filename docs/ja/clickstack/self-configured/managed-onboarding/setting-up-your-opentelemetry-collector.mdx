このガイドでは、既存の Self-managed ClickHouse Observability サービスに OpenTelemetry collector をデプロイする手順、または既存の collector を適合させる手順を説明し、最後にデータが正しく流れていることを確認します。

セットアップアシスタントを使用する前に、公式の ClickHouse agent skills をインストールしてください。

```bash
npx skills add clickhouse/agent-skills
```

collector は **ゲートウェイ** として動作します。ゲートウェイとは、アプリケーション、SDK、エージェントとして動作するコレクターからのデータを受け取る単一の OTLP エンドポイントです。ゲートウェイはイベントをバッチ化し、設定済みの処理を適用したうえで、[ClickHouse exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) 経由で ClickHouse に書き込みます。この構成により、収集ロジックをアプリケーションコードから切り離し、データを生成するワークロードとは独立してインジェストをスケールできます。ゲートウェイとエージェントの役割の違いについては、[コレクターの役割](/ja/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured)を参照してください。

<Info>
  **既存の collector**

  既存の OpenTelemetry collector を使用している場合は、すでに **ゲートウェイ** の役割で設定されていることを前提とします。**エージェント** の役割で動作しているコレクターの再設定に、この手順を使用することは推奨しません。
</Info>

      <Step title="collectorをデプロイする" id="deploy-the-collector">
        セルフマネージドの ClickHouse オブザーバビリティ向けに事前設定された **OpenTelemetry collector の ClickStack ディストリビューション**をデプロイします。以下の例では、簡単のため collector をローカルで実行し、同じマシン上で疑似的なテレメトリーを生成します。

        <Note>
          本番環境では通常、collector を Kubernetes クラスター内、または OpenTelemetry SDKs、エージェント、その他のコレクターから到達可能な仮想マシン上にデプロイします。これにより、環境全体のテレメトリーを一元的に収集し、ClickStack に転送できます。
        </Note>

        collector にデータを送信するクライアントの認証に使用する共有シークレットを決め、接続情報および `hyperdx_ingest` ユーザーに設定したパスワードとともに環境変数としてエクスポートします:

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        ClickStack OTel コレクターを起動します。

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        これで collector は、OTLP gRPC をポート `4317` で、OTLP HTTP をポート `4318` で公開するようになりました。アプリケーション、SDK、およびエージェントとして動作するコレクターは、リクエストヘッダーに `authorization: $OTLP_AUTH_TOKEN` を含めて、これらのポートにデータを送信してください。

        <Info>
          **本番環境へのデプロイメント**

          本番環境では、OTLP エンドポイントで TLS を有効にすることを推奨します。詳しくは [collector のセキュリティ保護](/ja/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured)を参照してください。
        </Info>
      </Step>

      <Step title="エンドポイントを確認する" id="verify-the-endpoint">
        collector に合成トラフィックを送信し、パイプライン全体が正常に動作することを確認します。ここでは、OpenTelemetry Collector Contrib のジェネレーターである [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen) を使用します。このツールは OTLP のログ、トレース、メトリクスを出力し、サービス、重大度、スパンのステータス、メトリクスの型ごとにデータの内容を調整できるフラグを備えています。

        Docker イメージから実行します (インストールは不要です) 。以下のコマンドを読みやすくするため、簡単なラッパーを定義します。`--add-host` を指定すると、コンテナからホスト上でリッスンしている collector にアクセスできます。

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        または、Go でバイナリをインストールし、接続先として `localhost` を指定します:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```

        <Info>
          **想定される動作**

          `tg` の各実行は約 20 秒間続き (`--duration 20s` で指定) 、その間は詳細なログが出力され続けますが、これは想定どおりの動作です。各実行は 20 秒が経過すると自動的に終了します。パイプラインの動作確認には以下のログで十分です。任意で実行できる、より充実したセットではさらに数回の実行が追加されるため、数分かかります。
        </Info>

        各コマンドで異なる部分 (サービス、重大度、ステータス、属性) だけを指定すれば済むように、小さな `tg` ヘルパーを定義します。

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        エラーだけを一様に送るのではなく、複数のサービスにまたがって現実的な重大度が混在するようにログを送信します。大半は情報レベルとし、警告とエラーをそれぞれ含めます。

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        エンドポイントが動作していることは、ログだけでも確認できます。より充実したデモデータセット、複数サービスにまたがるサービスマップ、各種メトリクス型のチャートを確認するには、以下のコマンドも展開して実行してください。これらのコマンドは `tg` ヘルパーを再利用するため、同じシェルで実行する必要があります。

        <Accordion title="より充実したテレメトリーを生成する（任意）">
          正常な複数のサービスと、障害が発生している 1 つの依存先から、複数のスパンを含むトレースを送信します。これにより、サービスマップは大部分が正常で 1 つのサービスだけがエラーを返すという現実的な構成になり、エラー関連のビューにもデータが表示されます：

          ```shell
          # Healthy services: the bulk of the traffic, all spans Ok
          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          チャートにカウンター、Gauge、分布 (distribution) の3種類がそろうよう、代表的な3つの型でメトリクスを送信します：

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          さらにバリエーションを増やすため、サービスをいくつか追加し、指数ヒストグラムも加えます。

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        利用可能なすべてのフラグやその他の使用例については、[telemetrygen による合成データ](/ja/clickstack/observability/example-datasets/telemetrygen#self-managed)を参照してください。
      </Step>

      <Step title="コレクター設定を調整する" id="adapt-collector">
        既存のコレクター設定を拡張し、[ClickHouse exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) を使用して Self-managed ClickHouse Observability に書き込めるようにします。

        <Info>
          **ClickHouse exporter が必要です**

          独自のディストリビューションを使用している場合は、ClickHouse exporter が含まれていることを確認してください。アップストリームの [contrib イメージ](https://github.com/open-telemetry/opentelemetry-collector-contrib) にはすでに含まれています。
        </Info>

        以下は、ClickStack UI が想定するレシーバー、プロセッサ、パイプラインと組み合わせて ClickHouse exporter を使用する設定例です。この設定は、セッションリプレイ (`rrweb`) のルーティングパスを含め、ClickStack ディストリビューションと同等の動作をします。`<clickhouse_cloud_endpoint>` と `<your_password_here>` を、上記で作成した `hyperdx_ingest` ユーザーの認証情報に置き換えてください。

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        注意点は次のとおりです。

        * `otlp/hyperdx` receiver は gRPC (`4317`) と HTTP (`4318`) の両方でリッスンします。アプリケーションおよびエージェントからは、collector ホスト上のこれらのポートに送信してください。
        * `clickhouse` エクスポーターは、ログ、トレース、メトリクスを `otel` データベースに書き込みます。このレイアウトは ClickStack UI が想定するものと一致しています。`clickhouse/rrweb` エクスポーターは、`routing/logs` コネクタによって `otel.hyperdx_sessions` に振り分けられたセッションリプレイのイベントを処理します。
        * OTLP レシーバーの認証は、既存の環境の設定に委ねられています。インジェストトークンを必須にする場合は、collector の[拡張機能](https://opentelemetry.io/docs/collector/configuration/#extensions)(例: `bearertokenauth`)、または TLS 終端を行うリバースプロキシを前段に配置して設定してください。

        新しい設定で collector を再読み込みします。その後、アプリケーション、SDK、およびエージェント collector から、環境で求められる認証ヘッダーを付与して、collector が公開する OTLPエンドポイントにデータを送信してください。

        Self-managed ClickHouse Observability 向けに OpenTelemetry コレクターを設定する方法の詳細については、[OpenTelemetry を使用したデータ取り込み](/ja/clickstack/observability/ingesting-data/opentelemetry#self-managed)を参照してください。
      </Step>

      <Step title="エンドポイントを確認する" id="verify-the-endpoint-existing">
        collector に対して合成トラフィックを生成し、パイプライン全体が正しく動作することを確認します。ここでは OpenTelemetry Collector Contrib のジェネレーターである [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen) を使用します。このツールは OTLP のログ、トレース、メトリクスを送出し、サービス、重大度、スパンのステータス、メトリクスの型ごとにデータを調整するためのフラグを備えています。

        Docker イメージから実行します (インストール不要) 。`<your-collector-host>` を collector がリッスンしているホストに置き換え、`authorization` ヘッダー (または別の認証方式) を collector 側で想定している値に設定してください：

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=<your-collector-host>:4317
        export OTLP_AUTH_TOKEN=<your-auth-token>
        ```

        または、Go でバイナリをインストールします。

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        ```

        <Info>
          **想定される動作**

          `tg` の各実行は約 20 秒間続き (`--duration 20s` で設定) 、その間は verbose ログが出力され続けますが、これは想定どおりの動作です。各実行は 20 秒が経過すると自動的に終了します。パイプラインの動作確認には以下のログで十分です。任意で追加できる、より充実したデータセットでは実行回数がさらに増え、完了まで数分かかります。
        </Info>

        各コマンドでは変化する部分 (サービス、重大度、ステータス、属性) だけを指定すれば済むよう、小さな `tg` ヘルパーを定義します。

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        エラーだけの一様なストリームではなく、複数のサービスにわたって重大度が現実的に混在するようにログを送信します。大半を情報レベルとし、警告とエラーをそれぞれ1件ずつ含めます：

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        エンドポイントが動作していることは、ログだけでも確認できます。より充実したデモデータセット、複数サービスにまたがるサービスマップ、さまざまなメトリクス型のチャートを確認したい場合は、以下のコマンドも展開して実行してください。これらのコマンドは `tg` ヘルパーを再利用するため、同じシェルで実行する必要があります。

        <Accordion title="より充実したテレメトリーを生成する（任意）">
          複数の正常なサービスと、障害が発生している1つの依存先から、複数のスパンを含むトレースを送信します。これにより、サービスマップは大半が正常で1つのサービスのみがエラーを返すという現実的な形になり、エラー関連のビューにもデータが投入されます。

          ```shell

          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          チャートでカウンター、Gauge、分布の3種類がそろうように、一般的な3つの型のメトリクスをそれぞれ送信します。

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          データのバリエーションをさらに増やすため、サービスをいくつか追加し、指数ヒストグラムも加えます。

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        利用可能なすべてのフラグやその他の使用例については、[telemetrygen による合成データ](/ja/clickstack/observability/example-datasets/telemetrygen#self-managed)を参照してください。

## 次のステップ：独自のデータを送信する {#next-steps}

上記の合成バーストは、パイプラインが動作することを確認したにすぎません。実際のテレメトリーを送信するには、[ClickStack SDK](/ja/clickstack/observability/ingesting-data/sdks) を使用して自社のサービスをインストルメントしてください。ClickStack SDK は Node.js、Python、Go、Java などの言語向けのインストルメンテーションを提供しており、先ほど動作を確認した collector エンドポイントへ OTLP でデータをエクスポートします。一連の手順を通した具体例については、[アプリケーションをインストルメントする](/ja/clickstack/self-configured/managed-onboarding/instrument-application)を参照してください。

アプリケーションコードではなくインフラストラクチャからデータを収集する場合は、次のガイドを参照してください。

* [Kubernetesの監視](/ja/clickstack/self-configured/managed-onboarding/monitoring-kubernetes)：クラスターからログ、インフラストラクチャメトリクス、Kubernetes イベントを収集します。
* [AWS CloudWatch ログの監視](/ja/clickstack/self-configured/managed-onboarding/monitoring-aws-cloudwatch-logs)：OpenTelemetry の CloudWatchレシーバーを介して CloudWatch のログを転送します。
