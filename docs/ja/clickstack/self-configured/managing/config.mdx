<Note>
  このページでは **Self-managed ClickHouse Observability** について説明します。推奨される完全マネージド型の環境については、[こちら](/ja/clickstack/observability/managing/config)のドキュメントを参照してください。
</Note>

このガイドでは、Self-managed ClickHouse Observability におけるデータソースの設定、自身で運用する collector、およびデータベーススキーマの設定について説明します。

## ユーザーインターフェイス {#hyperdx}

### データソース設定 {#datasource-settings}

UI を利用するには、オブザーバビリティの各データ型 (柱) ごとに、ユーザーがソースを定義しておく必要があります。

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

ソースを設定するには、**Team Settings → Data → Sources** を開きます。追加の設定を表示するには、**Configure Optional Fields** を選択します。以下はログの例です。

<div className="ch-image-md">
  <Frame>
    ![Configure Optional Fields が強調表示されたログソース設定](/images/clickstack/source-settings-optional-fields.png)
  </Frame>
</div>

UI が各ソースのデータをクエリするには、テーブルとカラムのマッピングが必要です。OTel のメトリクスソースでは、メトリクスの種類ごとに別々のテーブルを使用するため、収集しているメトリクスを含むテーブルを選択してください。

ClickStack に同梱されている[デフォルトの OpenTelemetry (OTel) スキーマ](/ja/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema)を使用している場合、これらのカラムは各ソースについて自動的に推論されます。[スキーマを変更する](#clickhouse)場合やカスタムスキーマを使用する場合は、ユーザー自身がこれらのマッピングを指定・更新する必要があります。

<Note>
  ClickStack コレクターは、同梱のスキーマ移行によってデフォルトのテーブルを作成します。これらのスキーマは、[OTel collector 向けの ClickHouse exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) と [OpenTelemetry データモデル](https://opentelemetry.io/docs/specs/otel/logs/data-model/)をベースにしています。
</Note>

以下の表にソース設定を示します。推論される値は、データベース内に存在するカラムとテーブルによって異なります。任意のマッピングを設定すると、トレースの相関付けなどの対応する機能が有効になりますが、ソースの保存には必須ではありません。

#### materialized view {#materialized-views-settings}

materialized view をログおよびトレースのデータソースに登録すると、対象となる集計クエリには、ソーステーブルではなく事前集約済みのビューから結果が返されます。ビューの作成と登録の方法については、[&quot;Materialized views&quot;](/ja/clickstack/self-configured/managing/materialized-views) を参照してください。

登録した各ビューには、次の設定を行います。

| 設定                       | 説明                                                                                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Database`               | materialized view のターゲットテーブルが存在する ClickHouseデータベース。                                                                                                     |
| `Table`                  | materialized view のターゲットテーブル (ビュー自体ではありません) 。                                                                                                           |
| `Timestamp Column`       | ターゲットテーブルのタイムスタンプ列。                                                                                                                                     |
| `Granularity`            | ターゲットテーブルのタイムスタンプ列の時間バケット (例: `1 minute`) 。クエリがビューを使用できるのは、そのクエリ自体の時間バケットがこれと同じか、より粗い場合に限られます。                                                          |
| `Minimum Date`           | 任意。ビューがデータを保持している最も古い日付と時刻。指定しない場合、ClickStack は、ソーステーブルにデータが存在するすべての日付についてビューにもデータが存在するものとみなします。                                                        |
| `Dimension Columns`      | ビューで事前集約されていないカラムのカンマ区切りリスト。これらのカラムはフィルタリングやグループ化に使用できます。                                                                                               |
| `Pre-aggregated Columns` | ビューで事前集約されているカラム。各エントリでは、集約関数 (`avg`、`count`、`max`、`min`、`quantile`、`sum`、`histogram`) とソーステーブルのカラムの組み合わせを、ビュー内の対応するカラムにマッピングします。`count` の場合、ソース列は不要です。 |

ターゲットテーブルを選択すると、UI がビューのスキーマからこれらの設定を推論します。推論された値を確認し、欠損フィールドを入力してください。

#### メタデータ用 materialized view {#metadata-materialized-views-settings}

メタデータ用 materialized view は、フィルタや自動補完で使用するフィールドの検出を高速化する materialized view です。ログおよびトレースのデータソースで設定できます。

| 設定                 | 説明                                        |
| ------------------ | ----------------------------------------- |
| `Key Rollup Table` | 任意 (非推奨)。ソーステーブルに含まれるキーのロールアップテーブルです。     |
| `KV Rollup Table`  | ソーステーブルに含まれるキーと値のペアのロールアップテーブルです。         |
| `Granularity`      | ロールアップテーブルで使用する時間バケットです (例: `15 minute`)。 |

#### 強調表示する属性 {#highlighted-attributes}

強調表示する属性と強調表示するトレース属性は、ログおよびトレースのデータソースで設定できます。

* 強調表示する属性は、ログまたはスパンの詳細を表示する際に、各ログまたはスパンに対して表示されるカラムまたは式です。

### 相関ソース {#correlated-sources}

ソース間の相関を最大限に活用するには、ログ、トレース、メトリクス、セッションの各ソースに相関ソースを設定する必要があります。これにより、UI は関連するデータを紐付け、イベントのレンダリング時に充実したコンテキストを提供できるようになります。

* `Logs`: トレースおよびメトリクスと相関付けることができます。
* `Traces`: ログ、セッション、メトリクスと相関付けることができます。
* `Metrics`: ログと相関付けることができます。
* `Sessions`: トレースと相関付けることができます。

これらの相関を設定すると、さまざまな機能が利用可能になります。たとえば、UI 上でトレースと並べて関連するログを表示したり、関連するソース間を行き来したりできます。なお、相関には適切な ID および属性のマッピングも必要です。ソースを選択するだけでは、これらのリレーションシップは作成されません。

## OpenTelemetry collector {#otel-collector}

詳細については、[&quot;ClickStack OpenTelemetry Collector&quot;](/ja/clickstack/self-configured/ingesting-data/collector) を参照してください。

* `CLICKHOUSE_ENDPOINT`
  * **デフォルト:** スタンドアロンの collector イメージでは *None (必須)&#x20;*。
  * **説明:** エクスポーターが使用する ClickHouse 接続 URL。
  * **ガイダンス:**
    * `https://<host>:8443` や `tcp://<host>:9440?secure=true` などの、セキュアな ClickHouse Cloud エンドポイントを使用してください
    * collector が ClickHouse にデータを送信するために必要です

* `CLICKHOUSE_USER`
  * **デフォルト:** 移行ツールでは `default`。スタンドアロンの collector では明示的に設定してください。
  * **説明:** ClickHouseインスタンスでの認証に使用するユーザー名。
  * **ガイダンス:**
    * このユーザーには、テレメトリーを挿入するアクセス許可が必要です。スキーマ作成または移行が有効な場合は、必要なデータベースオブジェクトを作成・変更するアクセス許可も必要です
    * インジェスト専用のユーザーを作成することを推奨します

* `CLICKHOUSE_PASSWORD`
  * **デフォルト:** *None (認証が有効な場合は必須)&#x20;*
  * **説明:** 指定した ClickHouse ユーザーのパスワード。
  * **ガイダンス:**
    * ユーザーアカウントにパスワードが設定されている場合は必須です
    * 本番環境のデプロイメントでは、シークレットを使用して安全に保管してください

* `HYPERDX_LOG_LEVEL`
  * **デフォルト:** デプロイメントによって異なります。`info` などの値を明示的に設定してください。
  * **説明:** collector のログ出力の詳細レベル。
  * **ガイダンス:**
    * `debug`、`info`、`warn`、`error` などの値を指定できます
    * トラブルシューティング時は `debug` を使用してください

* `OTLP_AUTH_TOKEN`
  * **デフォルト:** *None*。スタンドアロンイメージでのみ使用されます。
  * **説明:** スタンドアロンでの OTLP インジェストに必要なトークンを設定します。現行の collector は、`Authorization` ヘッダーの値として、トークンをそのまま、または `Bearer` プレフィックス付きで受け付けます。古いバージョンの collector では、プレフィックスなしのトークンのみ受け付ける場合があります。OIDC 認証が設定されている場合は無視されます。
  * **ガイダンス:**
    * collector を外部に公開する前に認証を設定してください。トークンも OIDC も設定されていない場合、スタンドアロンの OTLP レシーバーは認証なしのリクエストを受け付けてしまいます。

* `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`
  * **デフォルト:** 移行ツールでは `default`。スタンドアロンの collector では明示的に設定してください。
  * **説明:** collector がテレメトリデータを書き込む ClickHouseデータベース。
  * **ガイダンス:**
    * カスタムのデータベース名を使用する場合に設定してください
    * 指定したユーザーがこのデータベースへのアクセス権を持っていることを確認してください

## ClickHouse {#clickhouse}

ClickHouse を効果的にチューニングするには、[パーツ](/ja/concepts/core-concepts/parts)、[パーティション](/ja/concepts/core-concepts/partitions)、[分片とレプリカ](/ja/guides/oss/deployment-and-scaling/shards)といった主要なストレージの概念に加え、挿入時に[マージ](/ja/concepts/core-concepts/merges)がどのように行われるかを理解しておく必要があります。[プライマリインデックス](/ja/concepts/core-concepts/primary-indexes)、[スパースなセカンダリ索引](/ja/concepts/features/performance/skip-indexes/skipping-indexes)、データスキッピングインデックスの基礎に加え、TTL ライフサイクルの利用など[データライフサイクルの管理](/ja/guides/use-cases/observability/build-your-own/managing-data)の手法についても確認しておくことを推奨します。

[スキーマのカスタマイズ](/ja/guides/use-cases/observability/build-your-own/schema-design)も可能です。カラム型の変更、 (ログなどからの) 新しいフィールドの抽出、コーデックや Dictionary の適用、プロジェクションによるクエリの高速化などを行えます。

さらに、materialized view を使用すると、[インジェスト時にデータを変換またはフィルタリング](/ja/guides/use-cases/observability/build-your-own/schema-design#materialized-views)できます。ただし、データはビューのソーステーブルに書き込み、アプリケーションはターゲットテーブルから読み取る必要があります。また、materialized view はサービス内で[クエリをネイティブに高速化](/ja/clickstack/self-configured/managing/materialized-views)する用途にも使用できます。

詳細については、スキーマ設計、インデックス作成戦略、データ管理のベストプラクティスに関する ClickHouse のドキュメントを参照してください。その大部分は、セルフマネージドのデプロイメントにもそのまま当てはまります。
