<Note>
  このページでは**セルフマネージドの ClickHouse オブザーバビリティ**について説明します。推奨される完全マネージド型のエクスペリエンスについては、[こちら](/ja/clickstack/observability/overview)のドキュメントを参照してください。
</Note>

オブザーバビリティのワークロードは、同じデータに対して性質の大きく異なる 2 種類の負荷をかけます。インジェストは継続的かつ書き込み中心で、挿入が完了した後も長時間にわたり、バックグラウンドマージが CPU とメモリを消費し続けます。一方、クエリ負荷には波があり、ダッシュボードや検索の利用はインシデント発生時、つまり応答の遅さが最も許されないタイミングにピークを迎えます。

ClickHouse Cloud の [warehouse](/ja/products/cloud/features/infrastructure/warehouses) を使用すると、同じデータに対する両方のワークロードを別々のコンピュートで処理できるため、両者が CPU とメモリを奪い合うことはありません。

<ScalePlanFeatureBadge feature="Compute-compute separation" />

warehouse は ClickHouse Cloud の機能であるため、ここで説明する構成は Self-managed ClickHouse Observability に適用されます。分割した各サービスは、単一のデータコピーを共有しながら、それぞれ独立してサイジング、スケーリング、アイドル状態への移行を行えます。

<Note>
  **分離が有効なケース**

  分離は、継続的インジェストを行う大規模なデプロイメントを想定しています。保存済みデータが月あたりおよそ 100 TB 未満であれば、通常は単一の読み書きサービスで両方のワークロードを処理でき、2 つ目のサービスはおそらく不要です。月あたりの圧縮済みボリュームを見積もるには、[サイジングモデル](/ja/clickstack/self-configured/managing/estimating-resources)を使用してください。
</Note>

## 読み取りと書き込みを分離する理由 {#why-isolate}

* **書き込みによって読み取り性能が低下しなくなります。** OpenTelemetry の継続的なインジェスト (挿入処理そのものと、それに続くバックグラウンドマージ) は、ダッシュボードや検索のクエリと CPU およびメモリを奪い合います。インジェストの実行中は読み取りレイテンシが目に見えて悪化することがあり、インジェストが停止すると回復します。
* **読み取りによって書き込みが妨げられなくなります。** リソースの競合は双方向に発生します。負荷の高いアドホッククエリやコストの大きいダッシュボードの描画によってサービスのメモリが枯渇すると、挿入処理は単に遅くなるだけでなく、完全に失敗する場合があります。
* **読み取り専用コンピュートをクエリ専用に充てられます。** 読み取り専用サービスは、システムテーブル以外ではバックグラウンドマージを実行しません。また、マージによって稼働状態が維持されることがある読み書きサービスとは異なり、すぐにアイドル状態に移行します。
* **それぞれを個別にサイジングできます。** [サイジングモデル](/ja/clickstack/self-configured/managing/estimating-resources)では取り込みコンピュートとクエリ用コンピュートを別々に見積もり、warehouse を使用するとそれぞれを個別のサービスとしてプロビジョニングできます。モデルのベースラインである 1 QPS を超えると、クエリ用コンピュートが大半を占めるようになります。たとえば 5 QPS での[計算例](/ja/clickstack/self-configured/managing/estimating-resources#worked-example)では、インジェスト用の 58 vCPU に対してクエリ用は 290 vCPU となります。そのため、小規模な書き込みサービスで、はるかに大規模な読み取りサービスにデータを供給できます。
* **アイドル化とオートスケーリングはサービスごとに設定します。** 各サービスはそれぞれ独自のレプリカ数、オートスケーリング、自動アイドル化の設定を持つため、書き込みサービスは継続的インジェストのために常時稼働させつつ、読み取りサービスは業務時間外にアイドル化させることができます。
* **ストレージは重複しません。** warehouse 内のサービスは同じオブジェクトストレージのフォルダと同じテーブルを共有し、[ストレージの課金は 1 回のみ](/ja/products/cloud/features/infrastructure/warehouses#pricing)です。
* **エンドポイントごとにアクセスを制限できます。** IP Access List はサービスごとに適用されるため、書き込みエンドポイントにはコレクターからのみ、読み取りエンドポイントにはオブザーバビリティ UI からのみアクセスできるように設定できます。詳しくは[ネットワークアクセス制御](/ja/products/cloud/features/infrastructure/warehouses#network-access-control)に関するガイドを参照してください。

## アーキテクチャ {#architecture}

推奨されるトポロジーは、インジェスト用の読み書きサービス 1 つと、オブザーバビリティ UI 用の読み取り専用サービス 1 つで構成される warehouse です。

| サービス  | 種別          | 役割                                                    | クライアント                                                            |
| ----- | ---------- | ----------------------------------------------------- | ----------------------------------------------------------------- |
| プライマリ | read-write | インジェスト、バックグラウンドマージ、DDL (テーブル作成、有効期限 (TTL)、materialized view) | OpenTelemetry collector、ClickPipes、Vector、管理用の SQL コンソール / クライアント |
| セカンダリ | 読み取り専用     | 検索、ダッシュボード、ノートブック、アラート評価                              | オブザーバビリティ UI                                                      |

トポロジーを計画する際は、次の点に留意してください。

* warehouse 内の最初のサービスは常に read-write であり、サービスの種類は**作成時に固定**されます。読み取り専用と read-write を切り替えるには、warehouse 内に新しいサービスを作成してください。
* warehouse 内のすべてのサービスは、同じクラウドプロバイダー、リージョン、ClickHouse バージョン、Keeper に加え、プライマリサービスのアップグレードスケジュールを共有します。
* インジェストに使用する読み書きサービスは **1 つ**にしてください。マージはストレージを共有するすべての読み書きサービスに割り当てられるため、あるサービスへの挿入に伴うマージが別のサービスで実行されることがあります。その別のサービスが負荷の高いクエリも処理していると、マージを実行しているサービス上でクエリとマージが CPU とメモリを奪い合います。その結果、最初のサービスの挿入処理に伴うマージが遅れ、挿入パフォーマンスも低下します。クエリのワークロードは読み取り専用サービスに任せ、2 つ目の読み書きサービスは[マージをインジェストから分離する](#separating-merges)必要がある場合にのみ追加してください。

## 分離されたデプロイメントのセットアップ {#setup}

<Steps>
  <Step title="読み書きサービスの準備" id="prepare-read-write-service">
    インジェストには、既存のサービス、または新しい warehouse のプライマリサービスを使用し、[サイジングモデル](/ja/clickstack/self-configured/managing/estimating-resources) で見積もった取り込みコンピュートに応じたサイズに設定します。

    このサービス上に、データベースとインジェスト専用ユーザーを作成します。warehouse 内のすべてのサービスはアクセス制御を共有するため、ここで作成したユーザーは warehouse 内のどのサービスでも利用できます。

    ```sql
    CREATE DATABASE otel;
    CREATE USER hyperdx_ingest IDENTIFIED WITH sha256_password BY '<strong-password>';
    GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO hyperdx_ingest;
    ```

    パスワードは `openssl rand -base64 24` などのツールで生成し、マニフェストやシェル履歴ではなくシークレットマネージャーに保存してください。詳細については、[インジェスト用ユーザーの作成](/ja/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured)に関するガイドを参照してください。

    このサービスがすでに warehouse に属している場合、同じ warehouse 内の別のサービスがアイドル状態に移行済みだと、データベースレベルの DDL がハングすることがある点に注意してください。詳しくは[管理と DDL](#administration)を参照してください。
  </Step>

  <Step title="warehouseに読み取り専用サービスを追加する" id="add-read-only-service">
    ClickHouse Cloud コンソールで、先ほど準備したサービスのプラス記号をクリックし、そのデータを共有する 2 つ目のサービスを作成します。サービス種別には **読み取り専用** を選択し、サイジングモデルで算出したクエリ用コンピュートに合わせてサイズを設定します。

    詳しい手順については、ガイド「[warehouse のセットアップ方法](/ja/products/cloud/features/infrastructure/warehouses#setup-warehouses)」を参照してください。
  </Step>

  <Step title="インジェスト先を読み書きサービスに設定する" id="point-ingestion">
    collector がインジェスト用ユーザーとして認証し、**read-write** サービスエンドポイントにエクスポートするよう設定します：

    ```shell
    CLICKHOUSE_ENDPOINT=https://<read-write-service>.clickhouse.cloud:8443
    CLICKHOUSE_USER=hyperdx_ingest
    CLICKHOUSE_PASSWORD=<strong-password>
    HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel
    ```

    詳細については[コレクター設定オプション](/ja/clickstack/self-configured/managing/config#otel-collector)を参照してください。[Vector](/ja/clickstack/observability/ingesting-data/vector) やその他のインジェストパスを使用する場合は、それぞれの同等の設定を参照してください。

    読み取り専用エンドポイントへの書き込みは拒否されるため、collector の送信先は必ず読み書きサービスに設定する必要があります。
  </Step>

  <Step title="オブザーバビリティUIの接続先を読み取り専用サービスに設定する" id="point-clickstack">
    オブザーバビリティ UI は、常に ClickHouse Cloud コンソールで起動元となった ClickHouse サービスに接続します。読み取り専用コンピュート上で実行するには、次の手順に従います。

    1. ClickHouse Cloud コンソールで読み取り専用サービスを選択します。
    2. 左側のナビゲーションメニューから **ClickStack** を選択します。

    これで、UI が発行するすべてのクエリがその読み取り専用コンピュート上で実行されます。オブザーバビリティ UI 側での設定は不要です。詳しくは、ガイド「[読み取り専用コンピュートでオブザーバビリティ UI を使用する](/ja/clickstack/self-configured/deployment/managed#clickstack-read-only-compute)」を参照してください。

    <Warning>
      **オブザーバビリティ UI のステートはサービスごとに管理されます**

      ダッシュボード、保存済み検索、アラート、ソースは、オブザーバビリティ UI の起動元となったサービスに属します。同じ warehouse 内の別のサービスとデータを共有していても、これらが別のサービスに引き継がれることはありません。[デフォルトの OpenTelemetry スキーマ](/ja/clickstack/self-configured/deployment/managed#adding-data-sources)を使用するソースは新しいサービスで自動検出されるため、そのデータはすぐに検索できます。ただし、カスタムソースや手動で設定したソース、およびその他の保存済みの項目はすべて再作成する必要があります。

      ダッシュボードを作成する前に、オブザーバビリティ UI を実行するサービスを決めておいてください。既存のデプロイメントを切り替える場合は、以前のサービスで作成したアラートが、削除されるまでそのサービス上で (そのサービスのコンピュートを使って) 評価され続ける点に注意してください。
    </Warning>
  </Step>

  <Step title="分割を確認する" id="verify">
    オブザーバビリティ UI で検索を実行するか、ダッシュボードを開いてから、クエリがどのサービスで実行されたかを確認します。`system` テーブルはクエリを実行したノード上に書き込まれるため、複数のレプリカを持つサービスでは、すべてのレプリカを対象とするために、`default` クラスター名を指定して [`clusterAllReplicas`](/ja/reference/system-tables/overview#querying-across-nodes) を使用する必要があります。**読み取り専用**サービスでは、次のようにオブザーバビリティのクエリが記録されているはずです:

    ```sql
    SELECT
        user,
        query_kind,
        http_user_agent,
        count()
    FROM clusterAllReplicas('default', system.query_log)
    WHERE event_time > now() - toIntervalMinute(10)
      AND type = 'QueryFinish'
      AND is_initial_query = 1
    GROUP BY ALL
    ORDER BY count() DESC;
    ```

    ここで結果が空であっても、それだけでクエリが別の場所に送られたとは限りません。`system.query_log` は定期的に (デフォルトでは 7.5 秒ごとに) flush されるため、検索の直後にクエリを実行しても、まだ反映されていない場合があります。しばらく待ってから再度実行するか、権限があれば [`SYSTEM FLUSH LOGS`](/ja/reference/statements/system#flush-logs) で強制的に flush してください。

    トラフィックの発生元を特定できるのは、`user` と `http_user_agent` でグループ化しているためです。これにより、ソースがどのテーブルを参照しているかにかかわらず、UI からのクエリを、SQL コンソールやエンドポイントに接続するその他のクライアントからのクエリと区別できます。`is_initial_query = 1` でフィルタリングすると、送信されたクエリごとに 1 行だけが残ります。分散実行によるセカンダリクエリや、[materialized view](/ja/reference/system-tables/query_views_log) を評価する内部クエリは、`is_initial_query = 0` として別途ログに記録されます。

    **read-write** サービスで同じクエリを実行すると、インジェスト用ユーザーによる挿入処理のみが表示され、オブザーバビリティ関連のクエリトラフィックは表示されないはずです。

    `default` クラスターには接続中のサービスのレプリカしか含まれないため、各サービスで順にクエリを実行するのが確実なチェック方法です。warehouse 全体を集約して確認するには、代わりに `all_groups.default` クラスター名を使用してください。

    ```sql
    SELECT
        hostName() AS host,
        query_kind,
        count()
    FROM clusterAllReplicas('all_groups.default', system.query_log)
    WHERE event_time > now() - toIntervalMinute(10)
      AND type = 'QueryFinish'
      AND is_initial_query = 1
    GROUP BY ALL;
    ```

    このクエリについては、次の 2 点に注意してください。アイドル状態に移行済みのサービスは行を返せないため、完全な結果が必要な場合は事前にサービスを起動してください。また、`hostName()` が識別するのはサービスではなくレプリカです。アクティビティを特定のサービスに紐付けるには、そのサービスに対して直接クエリを実行してください。
  </Step>
</Steps>

## マージとインジェストの分離 {#separating-merges}

非常に高い取り込みレートが継続する環境では、挿入処理そのものではなくマージがインジェストサービスの主要な負荷になります。マージはストレージを共有するすべての読み書きサービスに割り当てられるため、本来別の用途を想定していたサービスにマージが割り当てられることもあります。

このようなデプロイメントでは、マージをインジェストサービスから完全に切り離し、3つのサービスからなるトポロジーを構成できます。

| サービス   | 種別              | 役割                                         |
| ------ | ---------------- | ------------------------------------------ |
| Ingest | read-write、マージ無効 | 挿入処理のみを受け付ける                               |
| Merge  | read-write       | warehouse のすべてのバックグラウンドマージおよびミューテーションを実行する |
| Query  | 読み取り専用           | オブザーバビリティ UI にデータを提供する                     |

<Info>
  **サポートへのリクエストが必要です**

  読み書きサービスでのマージの無効化は、クラウドコンソールからは設定できません。サービスに適用するには[サポートに問い合わせて](https://clickhouse.com/support/program)ください。
</Info>

このトポロジーは、インジェストだけでサービスが飽和する場合や、両方のサービスで書き込みが必要なために2つの読み書きサービスが必要な場合に検討する価値があります。クエリワークロードが、読み取りのみを行うオブザーバビリティ UI だけで構成される場合は、よりシンプルな[読み書き + 読み取り専用の分割構成](#architecture)で要件を満たせます。こちらのほうがサポートも充実しているため、推奨される構成です。

このトポロジーを運用する際は、以下の点に注意してください。

* **どちらの読み書きサービスについても自動アイドル化を前提にしないでください。** マージが無効化されたサービスでも、warehouse 内の他のサービスで行われた挿入処理によって発生するパーツのダウンロードおよび削除イベントは処理されます。また、未マージのパーツ数が多いと、それだけでアイドル化が妨げられる場合があります。両方の読み書きサービスが常時稼働している前提で計画してください。
* **どちらの読み書きサービスでもクエリを実行しないでください。** 読み書きサービス上の重い `SELECT` クエリは、CPU とメモリをマージ処理と奪い合います。これこそ、このトポロジーが回避しようとしている障害パターンです。[前述](#point-clickstack)のとおり、オブザーバビリティ UI の接続先は読み取り専用サービスにしてください。
* **ミューテーションを使用する場合、その追跡は実行したサービス上で行われます。** オブザーバビリティの用途でミューテーションが発生することはまれです。デフォルトのオブザーバビリティスキーマでは [`ttl_only_drop_parts = 1`](/ja/clickstack/self-configured/managing/ttl) が設定されているため、通常の保持期間処理では、行をミューテーションで削除するのではなく、有効期限 (TTL) マージ時に期限切れのパーツ全体が削除されます。ミューテーションを発生させる `ALTER` をインジェストサービスに送信した場合、その処理はマージサービスで実行され、進捗はインジェストサービスではなくマージサービスの [`system.mutations`](/ja/reference/system-tables/mutations) に表示されます。

## 管理と DDL {#administration}

すべてのスキーマ変更は **読み書き** サービスに対して実行する必要があります。対象には次のものが含まれます。

* テーブルの作成 - 初回の取り込み時に ClickStack コレクターによって自動的に実行されます
* 保持期間を変更するための [有効期限 (TTL) の変更](/ja/clickstack/self-configured/managing/ttl#modifying-ttl)
* クエリ高速化のための [materialized view](/ja/clickstack/self-configured/managing/materialized-views) の作成
* [スキップインデックス、プロジェクション、その他のパフォーマンス最適化](/ja/clickstack/self-configured/managing/performance-tuning) の追加

ユーザー、ロール、権限はスキーマ変更には該当しません。これらは warehouse 内のすべてのサービスで共有されるため、任意のサービスから一度作成するだけで済みます。インジェスト用ユーザーは、前述の [セットアップ手順](#prepare-read-write-service) で作成済みです。読み取り専用サービスに接続するその他のクライアントは、前述のインジェスト用権限ではなく、[オブザーバビリティ UI に必要なアクセス許可](/ja/clickstack/self-configured/managing/production#user-permissions) を持つ別の読み取り専用クエリユーザーとして認証してください。

[SQL コンソール](/ja/products/cloud/features/sql-console-features/sql-console) または [ClickHouse クライアント](/ja/concepts/features/interfaces/client) を使用して読み書きサービスに接続します。warehouse ではストレージとアクセス制御が共有されているため、変更は読み取り専用サービスにも即座に反映されます。[マージをインジェストから分離](#separating-merges)している場合は、どちらの読み書きサービスに対しても文を送信できます。ただし、ミューテーションはマージ用サービス上で実行・追跡される点に注意してください。

<Warning>
  **他のサービスがアイドル状態の場合、データベース DDL がハングすることがあります**

  `CREATE`、`RENAME`、`DROP DATABASE` 文は、warehouse 内でアイドル状態に移行済みのサービスや停止中のサービスによってブロックされ、ハングする可能性があります。読み取り専用サービスは即座にアイドル状態に移行するため、この構成ではこの問題が発生しやすくなります。データベースレベルの文は、クエリ単位または session 単位で [`distributed_ddl_task_timeout=0`](/ja/reference/settings/session-settings/distributed-ddl#distributed_ddl_task_timeout) を設定して実行してください。

  ```sql
  CREATE DATABASE otel
  SETTINGS distributed_ddl_task_timeout=0
  ```

  手動で停止したサービスに対してクエリを実行するには、そのサービスを再起動する必要があります。
</Warning>

materialized view は挿入をトリガーとして動作するため、読み書きサービスで実行されます。読み取り専用サービスは、そのターゲットテーブルを他のテーブルと同様にクエリします。クエリ高速化のために [データソースに登録された](/ja/clickstack/self-configured/managing/config#materialized-views-settings) ビューも同様です。

## エージェント型ワークロードの分離 {#agentic-workloads}

[MCPサーバー](/ja/clickstack/observability/mcp) を介して接続された AIアシスタントも、ダッシュボードと同じく読み取りトラフィックですが、負荷パターンは異なります。インシデントを調査するエージェントは、事前に誰も決めていない時間範囲に対して、探索的なクエリを短時間に次々と発行します。1 つの読み取り専用サービスをエージェントと UI で共有すると、同じインシデントの対応中にエンジニアが見ているダッシュボードが、そのバースト負荷の影響をまともに受けることになります。

ここでも同じ warehouse パターンを適用できます。エージェント専用の読み取り専用コンピュートを用意してください。

<Steps>
  <Step title="2 つ目の読み取り専用サービスを追加する" id="agentic-add-service">
    [前述のセットアップ](#add-read-only-service) とまったく同じ手順で、warehouse 内に別の読み取り専用サービスを作成します。このサービスは UI を提供しているサービスと同じテーブルを読み取るため、データをコピーする必要はありません。

    次に、[オブザーバビリティ UI を読み取り専用サービスに向ける](#point-clickstack) と同様に、クラウドコンソールからこのサービス上でオブザーバビリティ UI を一度起動します。Cloud MCP を使用するには、MCP 自体に加えてオブザーバビリティ UI も有効になっているサービスが必要です。詳しくは [MCP の前提条件](/ja/clickstack/observability/mcp#managed-prerequisites) を参照してください。

    サイズは、サイジングモデルのダッシュボード QPS ではなく、エージェントから想定されるクエリ負荷に基づいて決定し、自動アイドル化は有効のままにしておきます。エージェント型の利用は通常断続的なため、調査の合間にサービスをアイドル状態にできます。
  </Step>

  <Step title="そのサービスで MCP を有効化する" id="agentic-enable-mcp">
    ClickHouse Cloud コンソールで読み取り専用サービスを開き、**Connect** をクリックして **Connect with MCP** を選択し、オンに切り替えます。詳しくは [リモートMCPサーバーの有効化](/ja/products/cloud/features/ai-ml/mcp/remote-mcp#enable-remote-mcp-server) を参照してください。
  </Step>

  <Step title="MCPクライアントの接続先をそのサービスに設定する" id="agentic-point-clients">
    クラウドMCPエンドポイントはすべてのサービスで共通です。リクエストは `x-service-id` ヘッダーによって振り分けられ、このヘッダーがない場合は、アカウントで最初に使用されたオブザーバビリティサービスに送信されます。既存の MCP 設定をコピーし、新しい読み取り専用サービスの ID を指定したヘッダーを追加してください。

    ```shell
    claude mcp add --transport http clickstack https://mcp.clickhouse.cloud/clickstack \
      --header "x-service-id: <read-only-agent-service-id>"
    ```

    このヘッダーはどの MCPクライアントでも付与できます。Cursor、VS Code などでの同等の設定については、[特定のサービスを対象にする](/ja/clickstack/observability/mcp#managed-service-override) を参照してください。
  </Step>
</Steps>

<Warning>
  **MCP は対象サービスにステートを書き込みます**

  MCPサーバーはクエリの実行だけでなく、ダッシュボード、アラート、保存済み検索の作成も行えます。これらのステートは、他のすべての [オブザーバビリティ UI のステート](#point-clickstack) と同様に、リクエストの振り分け先のサービスに紐づきます。エージェントがエージェント用サービス上で作成したダッシュボードは、エンジニア向けのサービスから起動したオブザーバビリティ UI には表示されません。また、そこで作成されたアラートはそのサービスのコンピュート上で評価されるため、[後述](#isolating-alerts) のとおり、エージェント用サービスがアイドル状態だと評価が遅れたり、実行されなかったりします。永続的な成果物を作成することが想定されるエージェントは、チームが使用しているのと同じサービスに振り分けてください。
</Warning>

## アラート {#alerts}

アラートは、そのアラートを作成したサービス上で評価されます。そのため、アラートは UI と同じコンピュート、つまりこのトポロジーでは読み取り専用サービス上で実行されます。

<Note>
  **Self-managed ClickHouse Observability**

  アラートを有効化するには、**サービス管理者** のアクセス許可を持つユーザーのうち少なくとも 1 人が、オブザーバビリティ UI に一度サインインする必要があります。これにより、アラートクエリを実行する専用のデータベースユーザーがプロビジョニングされます。このユーザーは warehouse 内のすべてのサービスで共有されます。詳しくは、[Self-managed ClickHouse Observability へのアクセス権限の付与](/ja/clickstack/self-configured/deployment/managed#configure-access) のガイドを参照してください。
</Note>

アラートの評価は、定期的に実行されるクエリワークロードです。読み取り専用サービスのサイジングで想定する QPS に、これも含めてください。[サイジングモデル](/ja/clickstack/self-configured/managing/estimating-resources#refining-sizing-assumptions) では、検索、ダッシュボード、アラートのクエリを 1 つの集約値として扱います。

### アラート評価の分離 {#isolating-alerts}

アラートはユーザーが作成するものであるため、アラートの負荷を一元的に振り分けることはできません。オブザーバビリティ UI でアラートを追加すると、そのアラートはユーザーが作業しているサービスに追加され、そのサービスのコンピュート上で評価されます。サービスのアラートを別の場所へ移す設定はありません。

分離できるのは、一元的に管理しているアラートです。つまり、プラットフォームチームが組織全体向けに維持しているアラートであり、通常は評価頻度が最も高いアラートでもあります。これらのアラート専用の読み取り専用サービスを warehouse 内に用意し、そのサービスから起動したオブザーバビリティ UI でアラートを作成してください。

| サービス     | 種別          | 用途                               |
| -------- | ---------- | -------------------------------- |
| Ingest   | read-write | OpenTelemetry collector          |
| Query    | 読み取り専用     | オブザーバビリティ UI、およびユーザーが自身で作成するアラート |
| Alerting | 読み取り専用     | プラットフォームチームが管理する共通アラート           |

<Warning>
  **アラート用サービスでは自動アイドル化を無効化してください**

  サービスにアラートが設定されていても、そのサービスが起動状態に保たれるわけではありません。アイドル状態のサービスに対するアラート評価は、復帰を待つ分だけ遅延するか、そのまま失敗します。そのため、自動アイドル化を有効にしたままのアラート用サービスでは、評価が漏れる可能性があります。このサービスでは自動アイドル化を無効にし、常時稼働を前提に計画してください。これはアラートをどこで評価する場合でも同様です。UI を提供するサービス上でアラートを実行する場合は、そのサービスもアイドル状態にすることはできません。
</Warning>

残るトレードオフは、ステートがサービスごとに保持されることに起因するものです。

* 共通アラートと、それに付随するダッシュボードはアラート用サービス上にのみ存在し、Query サービスで作業しているユーザーからは見えません。通知はいずれの場合も同じ[宛先](/ja/clickstack/observability/features/alerts)に配信されるため、ユーザーが失うのはアラート定義の可視性であり、アラート機能そのものではありません。
* アラート用サービス上のソースは別個のオブジェクトです。[デフォルトの OpenTelemetry スキーマ](/ja/clickstack/self-configured/deployment/managed#adding-data-sources)を使用するソースは自動検出されますが、カスタムソースは、アラートから参照する前にそのサービス上でも設定しておく必要があります。

アラートの集合が小さく、その評価負荷がダッシュボードのトラフィックに比べて誤差の範囲であれば、すべてを 1 つの読み取り専用サービスにまとめてください。その場合は、定義を 2 か所で管理する運用コストのほうが大きくなります。

## その他の考慮事項 {#considerations}

**自動アイドル化。** アイドル状態に移行済みの読み取り専用サービスに最初のクエリを送ると、サービスが起動するまで待機が発生します。つまり、断続的な利用では、多少のレイテンシーと引き換えにコストを抑えられます。アラートによってアイドル化が防止されることは期待しないでください。アラートの評価に使用するサービスでは、[前述](#isolating-alerts)のとおり自動アイドル化を無効化してください。継続的インジェストを行っていれば読み書きサービスはアクティブな状態に保たれますが、インジェストが断続的またはスケジュール実行の場合は、アイドル期間後の最初のバッチでも同様に待機が発生し、テレメトリーの遅延として表れます。

**バックアップ。** バックアップはプライマリサービスでのみ取得され、warehouse 全体のデータが対象となります。バックアップを復元すると、既存の warehouse とは接続されていない、まったく新しいサービスが作成されます。

**レプリカ数の制限。** warehouse 内の全サービスのレプリカ数の合計には、デフォルトで上限が設定されています。詳しくは[使用制限](/ja/products/cloud/guides/best-practices/usagelimits)を参照してください。

**オブザーバビリティと他のワークロードの分離。** リアルタイムのアプリケーション分析など、すでに他のワークロードを実行しているサービスにオブザーバビリティ UI を追加する場合も、同じ warehouse 機能を使ってオブザーバビリティ専用のコンピュートを割り当てます。詳しくは[オブザーバビリティワークロードの分離](/ja/clickstack/self-configured/managing/estimating-resources#isolating-workloads)に関するガイドを参照してください。

warehouse の動作と制限事項の詳細については、[Warehouses](/ja/products/cloud/features/infrastructure/warehouses) に関するガイドを参照してください。
