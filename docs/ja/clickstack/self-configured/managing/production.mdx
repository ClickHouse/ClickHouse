本番環境で Self-managed ClickHouse Observability を使用する場合は、セキュリティ、安定性、設定に関する以下のプラクティスを考慮してください。

[Self-managed ClickHouse Observability](/ja/clickstack/self-configured/getting-started/managed) では、業界標準の[セキュリティプラクティス](/ja/products/cloud/features/security)がデフォルトで適用されています。これには強化された暗号化、認証と接続、マネージドなアクセス制御が含まれます。さらに、次のようなメリットもあります。

* ストレージから独立したコンピュートの自動スケーリング
* オブジェクトストレージによる低コストかつ実質無制限のデータ保持
* Warehouse による[読み取りと書き込みのワークロードの分離](/ja/clickstack/self-configured/managing/isolating-read-write)
* 統合された認証
* 自動[バックアップ](/ja/products/cloud/features/backups/overview)
* シームレスなアップグレード

**Self-managed ClickHouse Observability を使用する場合は、ClickHouse Cloud 向けの[ベストプラクティス](/ja/products/cloud/guides/production-readiness)に従ってください。**

## インジェストのセキュリティ保護 {#secure-ingestion-managed}

ClickStack OpenTelemetryコレクターは、オープンソースのディストリビューション以外でデプロイした場合、デフォルトではセキュリティ保護されておらず、OTLPポートでの認証も不要です。

インジェストを保護するには、collectorのデプロイ時に `OTLP_AUTH_TOKEN` 環境変数で認証トークンを指定してください。詳細については、[「collectorのセキュリティ保護」](/ja/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured)を参照してください。

### インジェスト用ユーザーを作成する {#create-a-database-ingestion-user-managed}

ClickHouse Cloud へのインジェストには OTel collector 専用のユーザーを作成し、データが特定のデータベース (例: `otel`) に送信されるようにすることを推奨します。詳細は[「インジェスト用ユーザーの作成」](/ja/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured)を参照してください。

## 有効期限 (TTL) を設定する {#configure-ttl-managed}

Self-managed ClickHouse Observability のデプロイメントで、[有効期限 (TTL)](/ja/clickstack/self-configured/managing/ttl) が[適切に設定されている](/ja/clickstack/self-configured/managing/ttl#modifying-ttl)ことを確認してください。TTL はデータの保持期間を制御します。デフォルトの 30 日間は、必要に応じて調整してください。

### オブザーバビリティワークロードの分離 {#isolating-workloads}

リアルタイムのアプリケーション分析など、他のワークロードをすでに処理している**既存の ClickHouse Cloud サービス**に Self-managed ClickHouse Observability を追加する場合は、オブザーバビリティのトラフィックを分離することを強く推奨します。

[**Managed Warehouses**](/ja/products/cloud/features/infrastructure/warehouses) を使用して、オブザーバビリティ専用の**子サービス**を作成してください。これにより、次のことが可能になります。

* 取り込みおよびクエリの負荷を既存のアプリケーションから分離する
* オブザーバビリティワークロードを独立してスケールさせる
* オブザーバビリティのクエリが本番環境の分析に影響を及ぼすのを防ぐ
* 必要に応じて、同じ基盤データセットを複数のサービス間で共有する

この構成により、既存のワークロードに影響を与えることなく、オブザーバビリティデータの増加に応じてオブザーバビリティワークロードを独立してスケールさせることができます。

### 読み取りワークロードと書き込みワークロードの分離 {#isolating-read-write}

warehouse を使用すると、取り込みワークロードとクエリワークロードをそれぞれ専用のコンピュートに分離することもできます。この構成では、インジェストは読み書きサービスに送信し、オブザーバビリティ UI は読み取り専用サービス上で実行します。大規模なデプロイメントでは、これが本番環境で推奨されるトポロジーです。詳しくは[「読み取りワークロードと書き込みワークロードの分離」](/ja/clickstack/self-configured/managing/isolating-read-write)を参照してください。

大規模なデプロイメントやカスタムのサイジングについてのガイダンスが必要な場合は、サポートにお問い合わせください。より精密な見積もりをご提示します。

## クエリユーザーのアクセス許可 {#user-permissions}

外部クエリクライアントが使用する ClickHouse ユーザーには、`readonly = 2` を設定してください。UI はすべてのクエリで `date_time_output_format` などの独自の設定を指定します。また、生のSQLチャートも `readonly = 2` を設定します。そのため、`readonly = 1` のユーザーでは、これらのクエリが `Cannot modify '...' setting in readonly mode` で失敗します。`readonly = 2` であれば、UI は `max_rows_to_read`、`read_overflow_mode`、`cancel_http_readonly_queries_on_client_close` も設定できます。`max_rows_to_read` を制限する場合は、少なくとも 100 万を許容してください。`wait_end_of_query` は設定ではなく HTTP インターフェースのパラメータであるため、権限を付与する必要はありません。

例:

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

ClickHouse Cloud の `default` ユーザーにはデフォルトでこれらのアクセス許可が付与されていますが、専用ユーザーを作成することを推奨します。
