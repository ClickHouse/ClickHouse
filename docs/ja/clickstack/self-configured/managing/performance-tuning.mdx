## はじめに {#introduction}

このガイドでは、Self-managed ClickHouse Observability における最も一般的かつ効果的なパフォーマンス最適化について説明します。これらの最適化を行えば、実環境におけるオブザーバビリティのワークロードの大半 (通常は 1 日あたり数十テラバイト規模のデータまで) に十分対応できます。

最適化は意図的に順序立てて紹介しており、最もシンプルで効果の大きい手法から始め、より高度で専門的なチューニングへと進みます。まずは前半の最適化から適用してください。多くの場合、それだけでも大幅な改善が得られます。データ量が増え、ワークロードの負荷が高まるにつれて、後半の手法を検討する価値も高まっていきます。

## ClickHouse の概念 {#clickhouse-concepts}

本ガイドで説明する最適化を適用する前に、ClickHouse の中核となるいくつかの概念を理解しておくことが重要です。

このサービスでは、**各データソースは 1 つ以上の ClickHouse テーブルに直接対応します**。OpenTelemetry を使用する場合、サービスはログ、トレース、メトリクスのデータを格納するデフォルトのテーブル群を作成・管理します。カスタムスキーマを使用している場合や独自にテーブルを管理している場合は、これらの概念をすでにご存じかもしれません。一方、OpenTelemetry Collector 経由でデータを送信しているだけの場合は、これらのテーブルが自動的に作成され、以下で説明する最適化はすべてこれらのテーブルに対して適用されます。

| データ型             | テーブル                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| ログ               | [otel&#95;logs](/ja/clickstack/self-configured/ingesting-data/schemas#logs)                                               |
| トレース             | [otel&#95;traces](/ja/clickstack/self-configured/ingesting-data/schemas#traces)                                           |
| メトリクス (Gauge)    | [otel&#95;metrics&#95;gauge](/ja/clickstack/self-configured/ingesting-data/schemas#gauge)                                 |
| メトリクス (合計)       | [otel&#95;metrics&#95;sum](/ja/clickstack/self-configured/ingesting-data/schemas#sum)                                     |
| メトリクス (ヒストグラム)   | [otel&#95;metrics&#95;histogram](/ja/clickstack/self-configured/ingesting-data/schemas#histogram)                         |
| メトリクス (指数ヒストグラム) | [otel&#95;metrics&#95;exponentialhistogram](/ja/clickstack/self-configured/ingesting-data/schemas#exponential-histograms) |
| メトリクス (サマリー)     | [otel&#95;metrics&#95;summary](/ja/clickstack/self-configured/ingesting-data/schemas#summary-table)                       |
| セッション            | [hyperdx&#95;sessions](/ja/clickstack/self-configured/ingesting-data/schemas#sessions)                                    |

ClickHouse では、テーブルは[データベース](/ja/reference/statements/create/database)に割り当てられます。デフォルトでは `default` データベースが使用されますが、これは [OpenTelemetry collector で変更](/ja/clickstack/self-configured/managing/config#otel-collector)できます。

<Warning>
  **ログとトレースを重点的に**

  ほとんどの場合、パフォーマンスチューニングの対象はログテーブルとトレーステーブルです。メトリクステーブルもフィルタリング向けに最適化できますが、そのスキーマは Prometheus スタイルのワークロードに合わせて意図的に設計されており、標準的なチャート作成であれば通常は変更する必要はありません。一方、ログとトレースはより幅広いアクセスパターンに対応するため、チューニングによる効果が最も大きくなります。セッションデータはユーザーエクスペリエンスが固定されており、スキーマを変更する必要はほとんどありません。
</Warning>

最低限、以下の ClickHouse の基本事項を理解しておく必要があります。

| 概念              | 説明                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **テーブル**        | サービス内のデータソースが基盤となる ClickHouse テーブルにどのように対応するか。ClickHouse のテーブルは主に [MergeTree](/ja/reference/engines/table-engines/mergetree-family/mergetree) エンジンを使用します。 |
| **パーツ**         | データが不変のパーツとして書き込まれ、時間の経過とともにマージされる仕組み。                                                                                                                 |
| **パーティション**     | テーブルのデータパーツを整理された論理単位にグループ化したもの。管理、クエリ、最適化が容易になります。                                                                                                    |
| **マージ**         | パーツ同士を結合し、クエリ対象のパーツ数を減らす内部プロセス。クエリパフォーマンスの維持に不可欠です。                                                                                                    |
| **グラニュール**      | クエリ実行時に ClickHouse が読み取りおよび枝刈りを行うデータの最小単位。                                                                                                          |
| **主キー (ソートキー)** | `ORDER BY` キーがディスク上のデータレイアウト、圧縮、クエリの枝刈りをどのように決定するか。                                                                                                 |

これらの概念は ClickHouse のパフォーマンスの要です。データがどのように書き込まれ、ディスク上でどのように構造化され、クエリ時に ClickHouse がどれだけ効率よくデータの読み取りをスキップできるかは、これらによって決まります。マテリアライズドカラム、スキップ索引、主キー、プロジェクション、マテリアライズドビューなど、本ガイドで紹介する最適化はすべてこれらの中核的な仕組みの上に成り立っています。

* [ClickHouse でのテーブル作成](/ja/get-started/quickstarts/creating-tables) - テーブルの簡単な入門です。
* [パーツ](/ja/concepts/core-concepts/parts)
* [パーティション](/ja/concepts/core-concepts/partitions)
* [マージ](/ja/concepts/core-concepts/merges)
* [主キー/索引](/ja/concepts/core-concepts/primary-indexes)
* [ClickHouse のデータ格納方法: パーツとグラニュール](/ja/guides/clickhouse/data-modelling/sparse-primary-indexes) - ClickHouse でデータがどのように構造化され、クエリされるかを解説する上級ガイドです。グラニュールと主キーについて詳しく説明しています。
* [MergeTree](/ja/reference/engines/table-engines/mergetree-family/mergetree)- コマンドや内部仕様の確認に役立つ、MergeTree の上級リファレンスガイドです。

## 最適化 1. 頻繁にクエリされる属性をマテリアライズする {#materialize-frequently-queried-attributes}

最初に取り組むべき最もシンプルな最適化は、`LogAttributes`、`ScopeAttributes`、`ResourceAttributes` の中で頻繁にクエリされる属性を特定し、マテリアライズドカラムを使ってそれらを top-level のカラムに昇格させることです。

多くの場合、この最適化だけで 1 日あたり数十テラバイト規模のデプロイメントにも対応できます。より高度なチューニング手法を検討する前に、まずこの最適化を適用してください。

### 属性をマテリアライズする理由 {#why-materialize-attributes}

このサービスは、Kubernetes ラベル、サービスのメタデータ、カスタム属性などのメタデータを `Map(String, String)` カラムに格納します。これにより柔軟性が得られる一方で、Map のサブキーに対するクエリはパフォーマンスに大きな影響を及ぼします。

Map カラムから単一のキーをクエリする場合でも、ClickHouse は Map カラム全体をディスクから読み取る必要があります。Map に多数のキーが含まれていると、専用のカラムを読み取る場合に比べて不要な I/O が発生し、クエリが遅くなります。

頻繁にアクセスされる属性をマテリアライズすれば、挿入時に値を抽出して独立したカラムとして格納するため、このオーバーヘッドを回避できます。

マテリアライズドカラムには次の特徴があります。

* 挿入処理の際に自動的に計算される
* INSERT文で明示的に値を設定することはできない
* 任意の ClickHouse の式を使用できる
* String から、より効率的な数値型や日付型へ型変換できる
* スキップ索引や主キーを利用できるようになる
* Map 全体へのアクセスを回避し、ディスクの読み取りを削減する

<Note>
  このサービスは、Map から抽出されたマテリアライズドカラムを自動的に検出し、ユーザーが元の属性パスに対してクエリを実行し続けている場合でも、クエリ実行時にそれらを透過的に使用します。
</Note>

### 例 {#materialize-column-example}

トレース用のデフォルトのオブザーバビリティスキーマを例に考えてみます。このスキーマでは、Kubernetes のメタデータは `ResourceAttributes` に保存されます。

<OtelTracesSchema />

ユーザーは Lucene 構文を使ってトレースをフィルタできます (例: `ResourceAttributes.k8s.pod.name:"checkout-675775c4cc-f2p9c"`) 。

<div className="ch-image-lg">
  <Frame>
    ![トレースのフィルタリング](/images/clickstack/performance_guide/trace_filtering.webp)
  </Frame>
</div>

この場合、次のような SQL 述語が生成されます。

```sql
ResourceAttributes['k8s.pod.name'] = 'checkout-675775c4cc-f2p9c'
```

これは Map のキーにアクセスするため、ClickHouse は一致する各行について `ResourceAttributes` カラム全体を読み取る必要があります。Map に多数のキーが含まれている場合、読み取るデータ量が非常に大きくなる可能性があります。

この属性を頻繁にクエリする場合は、top-level のカラムとしてマテリアライズすべきです。

挿入時にポッド名を抽出するには、次のようにマテリアライズドカラムを追加します。

```sql
ALTER TABLE otel_v2.otel_traces
ADD COLUMN PodName String
MATERIALIZED ResourceAttributes['k8s.pod.name']
```

これ以降、**新しい**データでは ポッド名が専用のカラム `PodName` として保存されます。

これにより、Lucene 構文 (例: `PodName:"checkout-675775c4cc-f2p9c"`) を使用して、ポッド名を効率的にクエリできるようになります。

<div className="ch-image-lg">
  <Frame>
    ![トレースのフィルタリング v2](/images/clickstack/performance_guide/trace_filtering_v2.webp)
  </Frame>
</div>

新たに挿入されたデータでは Map へのアクセスが一切不要になり、I/O が大幅に削減されます。

なお、元の属性パス (例: `ResourceAttributes.k8s.pod.name:"checkout-675775c4cc-f2p9c"`) で引き続きクエリした場合でも、**サービスが内部でクエリを自動的に書き換え**、マテリアライズされた `PodName` カラムを使用します。具体的には、次の述語が使用されます:

```sql
PodName = 'checkout-675775c4cc-f2p9c'
```

これにより、ユーザーはダッシュボード、アラート、保存クエリを変更することなく、この最適化の恩恵を受けられます。

<Note>
  デフォルトでは、マテリアライズドカラムは `SELECT * queries` の結果に含まれません。これにより、クエリ結果を常にテーブルへ再挿入できるという不変条件が保たれます。
</Note>

### 履歴データのマテリアライズ {#materializing-historical-data}

マテリアライズドカラムが自動的に適用されるのは、カラムの作成後に挿入されたデータのみです。既存のデータについては、マテリアライズドカラムに対するクエリは、透過的に元の Map からの読み取りにフォールバックします。

履歴データに対するクエリのパフォーマンスが重要な場合は、次のようにミューテーションを使用してカラムをバックフィルできます。

```sql
ALTER TABLE otel_v2.otel_traces
MATERIALIZE COLUMN PodName
```

これにより既存の[パーツ](/ja/concepts/core-concepts/parts)が書き換えられ、カラムにデータが投入されます。ミューテーションはパーツごとにシングルスレッドで実行されるため、大規模なデータセットでは時間がかかる場合があります。影響を抑えるには、次のようにミューテーションの対象を特定のパーティションに限定できます：

```sql
ALTER TABLE otel_v2.otel_traces
MATERIALIZE COLUMN PodName
IN PARTITION '2026-01-02'
```

ミューテーションの進捗は、`system.mutations` テーブルを使用して監視できます。例:

```sql
SELECT *
FROM system.mutations
WHERE database = 'otel'
  AND table = 'otel_traces'
ORDER BY create_time DESC;
```

対応するミューテーションの `is_done = 1` になるまで待ちます。

<Warning>
  ミューテーションは I/O と CPU のオーバーヘッドを増加させるため、使用は必要最小限にとどめてください。多くの場合、古いデータは自然に期限切れになるのを待ち、新たに取り込まれたデータでパフォーマンス改善の効果を得るだけで十分です。
</Warning>

## 最適化 2. スキップ索引の追加 {#adding-skip-indexes}

頻繁にクエリされる属性をマテリアライズしたら、次の最適化としてデータスキッピングインデックスを追加し、クエリ実行時に ClickHouse が読み取る必要のあるデータ量をさらに削減します。

スキップ索引を使用すると、一致する値が存在しないと判断できる場合に、ClickHouse はデータのブロック全体をスキャンせずに済みます。従来のセカンダリ索引とは異なり、スキップ索引はグラニュール単位で動作し、クエリのフィルタによってデータセットの大部分が除外される場合に最も効果を発揮します。適切に使用すれば、クエリのセマンティクスを変えることなく、high-cardinality な属性に対するフィルタリングを大幅に高速化できます。

スキップ索引を含むデフォルトのトレーススキーマを例に見てみましょう。

<OtelTracesSchema />

これらの索引は、主に次の 3 つのパターンを対象としています。

* TraceId、セッション識別子、属性キー、属性値など、high-cardinality な文字列のフィルタリング
* [`*AttributeItems`](#map-direct-read-optimization) カラムに対する[テキストインデックス](#text-indexes)で高速化される、Map のサブキーのフィルタリング
* span の所要時間などの数値範囲のフィルタリング

ログテーブルでは、ブルームフィルタの代わりにすべて `text(tokenizer = 'array')` 索引を使用し、さらに全文検索用として `lower(Body)` に `text(tokenizer = 'splitByNonAlpha')` 索引を追加しています。DDL の全体については、[「テーブルとスキーマ」](/ja/clickstack/self-configured/ingesting-data/schemas#logs) を参照してください。

### ブルームフィルタ {#bloom-filters}

ブルームフィルターインデックスは、このサービスで最もよく使用されるスキップ索引のタイプです。高カーディナリティの String 型のカラム、一般的には異なる値が少なくとも数万個あるカラムに適しています。偽陽性率 0.01、粒度 1 は、ストレージのオーバーヘッドと効果的な枝刈りのバランスが取れた、デフォルトの始点として適した設定です。

最適化 1 の例の続きとして、Kubernetes のポッド名が ResourceAttributes からマテリアライズされているものとします。

```sql
ALTER TABLE otel_traces
ADD COLUMN PodName String
MATERIALIZED ResourceAttributes['k8s.pod.name']
```

続いて、このカラムに対するフィルタを高速化するために、ブルームフィルタのスキップ索引を追加できます。

```sql
ALTER TABLE otel_traces
ADD INDEX idx_pod_name PodName
TYPE bloom_filter(0.01)
GRANULARITY 1
```

スキップ索引は追加後にマテリアライズする必要があります。詳しくは [&quot;スキップインデックスのマテリアライズ&quot;](#materialize-skip-index) を参照してください。

作成とマテリアライズが完了すると、ClickHouse は要求されたポッド名を含まないことが確実なグラニュールを丸ごとスキップできます。これにより、`PodName:"checkout-675775c4cc-f2p9c"` のようなクエリで読み取るデータ量を削減できる可能性があります。

ブルームフィルタが最も効果を発揮するのは、特定の値が比較的少数のパーツにしか出現しないような値の分布になっている場合です。オブザーバビリティのワークロードでは、ポッド名、トレースID、セッション識別子などのメタデータが時刻と相関しているため、テーブルの順序キーによって自然にまとまって格納されることが多く、このような分布になりやすい傾向があります。

他のスキップ索引と同様に、ブルームフィルタは必要な箇所に絞って追加し、実際のクエリパターンで検証して、測定可能な効果が得られることを確認してください。詳しくは [&quot;スキップ索引の有効性の評価&quot;](#evaluating-skip-index-effectiveness) を参照してください。

### テキストインデックス {#text-indexes}

[テキストインデックス](/ja/reference/engines/table-engines/mergetree-family/textindexes)は、ブルームフィルタに代わる選択肢です。ブルームフィルタはグラニュールを確実に除外できる確率的データ構造ですが、偽陽性が発生しうるため、除外されなかったグラニュールは読み込んだうえで `WHERE` 条件に照らして評価する必要があります。テキストインデックスは、トークンをパーツ内の正確なオフセットに対応付ける転置索引です。グラニュール単位ではなくオフセット単位で評価し、偽陽性も生じないため、通常は元のカラムを読み込まずに `WHERE` 条件を判定できます。この最適化は [direct read](https://github.com/ClickHouse/clickhouse-docs/pull/6356/%E2%80%A6) と呼ばれます。クエリ実行時間の大部分はデータの読み込みが占めることが多いため、direct read によってクエリのレイテンシを大幅に低減できます。

さらに、テキストインデックスはそれ自体をクエリすることもでき、サービスにおける自動補完やその他のイントロスペクション機能を支えています。

オブザーバビリティにおけるクエリパターンの大半は、次の 2 つのトークナイザーでカバーできます。

| トークナイザー           | 用途                                       | 主な対象カラム                           |
| ----------------- | ---------------------------------------- | --------------------------------- |
| `array`           | `Array(String)` の各要素を 1 つのトークンとしてインデックス化 | `mapKeys(...)`, `*AttributeItems` |
| `splitByNonAlpha` | 文章形式の文字列に対する単語単位の全文検索                    | `Body`, `lower(Body)`, `SpanName` |

#### Map および Array カラム向けの Array トークナイザー {#array-tokenizer}

デフォルトのログスキーマでは、`mapKeys` とマテリアライズされた要素の配列に対し、
`array` トークナイザーを用いて索引を作成します。

```sql
INDEX idx_log_attr_key mapKeys(LogAttributes) TYPE text(tokenizer = 'array'),
INDEX idx_log_attr_items LogAttributeItems TYPE text(tokenizer = 'array')
```

Map の各キー (または配列要素) は、それぞれ単一のトークンになります。そのため、既知の
属性キーでフィルタリングすると、Map カラム全体をスキャンすることなく、そのキーを含まない行を
除外できます。この仕組みこそが、[Mapの直接読み取り最適化](#map-direct-read-optimization)の
効果を生み出しています。

#### ログボディ向けの `splitByNonAlpha` {#text-index-body}

`Body` カラムに対する全文検索には、`splitByNonAlpha` を用いたテキスト
索引が効果的です。サービスではこの索引を `lower(Body)` に対して定義しているため、大文字と小文字を区別しない
Lucene 検索でもこの索引を利用できます。

```sql
INDEX idx_lower_body lower(Body) TYPE text(tokenizer = 'splitByNonAlpha')
```

サービスが `lower(Body)` に対する `text(tokenizer = 'splitByNonAlpha')` 索引を検出すると、
`error` や `"connection refused"` のような暗黙的カラムを対象とする Lucene クエリを
`hasAllTokens(lower(Body), lower(...))` に書き換えます。これにより、`Body` カラム全体を読み取ることなく、
索引だけでクエリを処理できます。ほとんどの
オブザーバビリティのログワークロードでは、これが最も大きな効果を得られるフィルタリング高速化手法です。

<Info>
  **テキストインデックスと `tokenbf_v1` の比較**

  従来の `tokenbf_v1` インデックスの種類 (デフォルトのトレーススキーマでは
  `lower(SpanName)` に対して現在も使用されています) は機能的にはほぼ同等ですが、ClickHouse 26.2
  以降では非推奨となっています。全文検索用の索引を新たに作成する場合は、`text(tokenizer = ...)` を使用してください。
</Info>

トークナイザーのオプション、プリプロセッサ、検証方法の詳細については、[全文検索のドキュメント](/ja/reference/engines/table-engines/mergetree-family/textindexes)を参照してください。

### MinMax インデックス {#min-max-indexes}

MinMax インデックスはグラニュールごとに最小値と最大値を保存するもので、非常に軽量です。特に数値カラムや範囲クエリで効果を発揮します。すべてのクエリを高速化できるわけではありませんが、コストが低いため、数値フィールドであればほぼ常に追加する価値があります。

MinMax インデックスが最も効果を発揮するのは、数値が自然に順序付けられている場合、または各パーツ内で狭い範囲に収まっている場合です。

たとえば、`SpanAttributes` 内の Kafka のオフセットに対して頻繁にクエリを実行するとします。

```sql
SpanAttributes['messaging.kafka.offset']
```

この値はマテリアライズして、数値型にキャストできます:

```sql
ALTER TABLE otel_traces
ADD COLUMN KafkaOffset UInt64
MATERIALIZED toUInt64(SpanAttributes['messaging.kafka.offset'])
```

続いて、MinMax インデックスを追加します:

```sql
ALTER TABLE otel_traces
ADD INDEX idx_kafka_offset KafkaOffset TYPE minmax GRANULARITY 1
```

これにより、ClickHouse は Kafka のオフセット範囲でフィルタリングする際にパーツを効率的にスキップできます。これは、たとえばコンシューマーラグや再適用時の挙動をデバッグする場合に役立ちます。

前述のとおり、この索引を利用可能にするには、事前に[マテリアライズ](#materialize-skip-index)しておく必要があります。

### スキップインデックスのマテリアライズ {#materialize-skip-index}

スキップ索引を追加しても、適用されるのは新たに取り込まれたデータのみです。履歴データは、明示的にマテリアライズするまでこの索引の恩恵を受けられません。

たとえば、次のようにスキップ索引をすでに追加している場合:

```sql
ALTER TABLE otel_traces ADD INDEX idx_kafka_offset KafkaOffset TYPE minmax GRANULARITY 1;
```

既存のデータについては、索引を明示的に構築する必要があります：

```sql
ALTER TABLE otel_traces MATERIALIZE INDEX idx_kafka_offset;
```

<Info>
  **スキップ索引のマテリアライズ**

  スキップ索引のマテリアライズは通常軽量で、安全に実行できます。MinMax インデックスの場合は特にそうです。大規模なデータセットでブルームフィルターインデックスをマテリアライズする場合は、リソース使用量をより適切に制御できるよう、パーティション単位で実行する方法もあります。例:

  ```sql
  ALTER TABLE otel_v2.otel_traces
  MATERIALIZE INDEX idx_kafka_offset
  IN PARTITION '2026-01-02';
  ```
</Info>

スキップ索引のマテリアライズはミューテーションとして実行されます。進捗はシステムテーブルで監視できます。

```sql

SELECT *
FROM system.mutations
WHERE database = 'otel'
  AND table = 'otel_traces'
ORDER BY create_time DESC;
```

対象のミューテーションで `is_done = 1` になるまで待ちます。

完了したら、索引データが作成されていることを確認します:

```sql
SELECT database, table, name,
       data_compressed_bytes,
       data_uncompressed_bytes,
       marks_bytes
FROM system.data_skipping_indices
WHERE database = 'otel'
  AND table = 'otel_traces'
  AND name = 'idx_kafka_offset';
```

ゼロ以外の値は、索引が正常にマテリアライズされたことを示します。

スキップ索引のサイズはクエリパフォーマンスに直接影響する点に注意してください。数十〜数百ギガバイト規模の非常に大きなスキップ索引は、クエリ実行時の評価に無視できない時間がかかることがあり、その効果が低下したり、場合によっては完全に失われたりする可能性があります。

実際には、MinMax インデックスは通常非常に小さく評価コストも低いため、ほぼ常に問題なくマテリアライズできます。一方、ブルームフィルターインデックスは、カーディナリティ、粒度、偽陽性確率によっては大幅に肥大化する可能性があります。

ブルームフィルタのサイズは、許容する偽陽性率を引き上げることで削減できます。例えば、確率パラメータを `0.01` から `0.05` に引き上げると、索引が小さくなり評価も高速になりますが、その代わりに枝刈りの効果は弱まります。スキップされるグラニュールは少なくなるものの、索引の評価が高速化されることで、クエリ全体のレイテンシは改善される場合があります。

したがって、ブルームフィルタのパラメータ調整はワークロードに依存する最適化であり、実際のクエリパターンと本番環境に近いデータボリュームを用いて検証する必要があります。

スキップ索引の詳細については、ガイド[「ClickHouse のデータスキッピングインデックスを理解する」](/ja/concepts/features/performance/skip-indexes/skipping-indexes-examples)を参照してください。

### スキップ索引の有効性の評価 {#evaluating-skip-index-effectiveness}

スキップ索引による枝刈りの効果を評価する最も確実な方法は、`EXPLAIN indexes = 1` を使用することです。これにより、クエリプランの各ステージで除外される[パーツ](/ja/concepts/core-concepts/parts)と[グラニュール](/ja/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-organized-into-granules-for-parallel-data-processing)の数を確認できます。多くの場合、Skip ステージでグラニュール数が大幅に減っていることが望ましく、理想的には、主キーによって検索範囲がすでに絞り込まれた状態でさらに削減されていることが望まれます。スキップ索引はパーティションプルーニングと主キーによる枝刈りの後に評価されるため、その効果は、残っているパーツとグラニュールを基準に測定するのが最適です。

`EXPLAIN` で枝刈りが行われているかどうかは確認できますが、全体として高速化されるとは限りません。スキップ索引の評価にはコストがかかり、索引が大きい場合は特にその影響が大きくなります。索引の追加およびマテリアライズの前後で必ずクエリのベンチマークを行い、実際にパフォーマンスが改善されていることを確認してください。

例として、デフォルトの トレース スキーマに含まれている、TraceId に対するデフォルトのブルームフィルタスキップ索引を見てみましょう。

```sql
INDEX idx_trace_id TraceId TYPE bloom_filter(0.001) GRANULARITY 1
```

`EXPLAIN indexes = 1` を使用すると、選択性の高いクエリに対してこの索引がどの程度効果的かを確認できます。

```sql
EXPLAIN indexes = 1
SELECT *
FROM otel_v2.otel_traces
WHERE (ServiceName = 'accounting')
  AND (TraceId = 'aeea7f401feb75fc5af8eb25ebc8e974');

ReadFromMergeTree (otel_v2.otel_traces)
Indexes:
  PrimaryKey
    Keys:
      ServiceName
    Parts: 6/18
    Granules: 255/35898
  Skip
    Name: idx_trace_id
    Description: bloom_filter GRANULARITY 1
    Parts: 1/6
    Granules: 1/255
```

この例では、まず主キーによるフィルタでデータセットが大幅に絞り込まれ (35898 グラニュールから 255 グラニュールへ) 、さらにブルームフィルタによって単一のグラニュール (1/255) まで枝刈りされます。これはスキップ索引の理想的なパターンです。主キーによる枝刈りで検索範囲を絞り込み、残りの大部分をスキップ索引で除外します。

実際の効果を検証するには、安定した設定でクエリのベンチマークを行い、実行時間を比較します。結果のシリアライゼーションによるオーバーヘッドを避けるために `FORMAT Null` を使用し、実行の再現性を確保するためにクエリ条件キャッシュを無効化します。

```sql
SELECT *
FROM otel_traces
WHERE (ServiceName = 'accountingservice') AND (TraceId = '4512e822ca3c0c68bbf5d4a263f9943d')
SETTINGS use_query_condition_cache = 0
```

```response
2 rows in set. Elapsed: 0.025 sec. Processed 8.52 thousand rows, 299.78 KB (341.22 thousand rows/s., 12.00 MB/s.)
Peak memory usage: 41.97 MiB.
```

次に、スキップ索引を無効化した状態で同じクエリを実行します。

```sql
SELECT *
FROM otel_traces
WHERE (ServiceName = 'accountingservice') AND (TraceId = '4512e822ca3c0c68bbf5d4a263f9943d')
FORMAT Null
SETTINGS use_query_condition_cache = 0, use_skip_indexes = 0;
```

```response
0 rows in set. Elapsed: 0.702 sec. Processed 1.62 million rows, 56.62 MB (2.31 million rows/s., 80.71 MB/s.)
Peak memory usage: 198.39 MiB.
```

`use_query_condition_cache` を無効にすると、キャッシュされたフィルタリングの判定が結果に影響しなくなります。また、`use_skip_indexes = 0` を設定することで、比較用のクリーンなベースラインが得られます。枝刈りが効果的に機能し、索引の評価コストが低ければ、上記の例のように、索引を使用したクエリは大幅に高速になるはずです。

<Tip>
  `EXPLAIN` でグラニュールの枝刈りがほとんど見られない場合や、スキップ索引が非常に大きい場合は、索引の評価コストによって効果が相殺されることがあります。`EXPLAIN indexes = 1` で枝刈りを確認したうえで、ベンチマークを実行してエンドツーエンドでのパフォーマンス改善を確認してください。
</Tip>

### スキップ索引を追加すべき場合 {#when-to-add-skip-indexes}

スキップ索引は、ユーザーが最も頻繁に実行するフィルタの種類や、パーツおよびグラニュール内のデータの分布に基づいて、選択的に追加する必要があります。目的は、索引自体の評価コストを上回るだけのグラニュールを除外することです。そのため、本番環境に近いデータでのベンチマーク測定が不可欠です。

**フィルタで使用される数値カラムには、ほとんどの場合 minmax スキップ索引が適しています。** minmax は軽量で評価コストが低く、範囲述語に効果を発揮します。特に、値がおおまかに順序付けられている場合や、パーツ内で狭い範囲に収まっている場合に有効です。特定のクエリパターンで minmax が効果を発揮しない場合でも、通常はオーバーヘッドが十分に小さいため、そのまま残しておいて問題ありません。

**String 型のカラムには、サポートされている場合はテキストインデックスを優先し、そうでない場合はブルームフィルタにフォールバックしてください。** テキストインデックスは、ブルームフィルタと同様に等値比較や `IN` フィルタを高速化するだけでなく、全文検索や [Mapの直接読み取り最適化](#map-direct-read-optimization) で使用されるトークンベースの述語 (`hasToken`、`hasAllTokens`、`has`) も利用可能にします。テキストインデックスにまだ対応していない古いクラスターでは、ブルームフィルタが引き続き有力な選択肢です。

ブルームフィルタは、各値の出現頻度が比較的低い high-cardinality な String 型のカラム、つまりほとんどのパーツやグラニュールに検索対象の値が含まれていない場合に最も効果を発揮します。目安として、ブルームフィルタはカラムの異なる値が少なくとも 10,000 個ある場合に効果が期待でき、100,000 個以上ある場合に最も高い性能を発揮することが多くなります。また、一致する値が少数の連続したパーツに集中している場合にも効果が高まります。これは通常、カラムが順序キーと相関している場合に起こります。ただし、結果は環境によって異なるため、実環境でのテストに勝るものはありません。

## 最適化 3. Mapの直接読み取り {#map-direct-read-optimization}

`LogAttributes['k8s.pod.name'] =
'checkout'` のようなMapのサブキーでフィルタする場合、ClickHouseは
`LogAttributes` Mapカラム全体をディスクから読み取り、述語を評価するためにすべての行を展開する必要があります。[頻繁にクエリされる属性のマテリアライズ](#materialize-frequently-queried-attributes)
を使えば、事前に把握しているキーについてはこの問題を解決できますが、ユーザーがその場でフィルタする
任意の属性にまでは対応できません。

スキーマに `mapKeys` と `mapValues` の索引があったとしても、それらの索引からわかるのは、ある行に特定のキーが含まれるかどうか、特定の値が含まれるかどうかだけであり、そのキーと値が同じエントリに属しているかどうかはわかりません。つまり、`mapKeys` で `mapContainsKey(ResourceAttributes, 'foo')` を、`mapValues` で `mapContainsValue(ResourceAttributes, 'bar')` を判定することはできますが、どちらを使っても `ResourceAttributes['foo'] = 'bar'` は判定できません。

Mapの直接読み取り最適化では、キーと値を単一の `Array(String)` カラムに連結することで、
元のMapを読み込まずに `ResourceAttributes['foo'] = 'bar'` を
評価できるようにします。Mapはサイズが大きくなりがちで、データ量の増加に伴ってさらに
肥大化します。アプリケーションレベルでのクエリの書き換えと組み合わせることで、
任意のMapのサブキーに対する等値比較フィルタは、この索引を利用する単一の `has(...)` 呼び出しに置き換えられ、
クエリ実行時にMapのデシリアライズは発生しません。さらに、
元のカラムは `ALIAS` カラムであり保存されないため、追加で必要となるストレージコストは
テキスト索引の分のみです。

この最適化は自動的に適用されます。サービスのデフォルトのログテーブルおよびトレーステーブルには必要なカラムと
索引があらかじめ含まれており、接続先のClickHouseサーバーが基盤となる
プリミティブをサポートしている場合は、ランタイムにMapの添字によるフィルタが書き換えられます。スキーマにこれらのカラムが含まれていない場合や、
デフォルト以外にも高速化したいMapカラムがある場合は、以下の手順に従って
有効化してください。

### スキーマ {#map-direct-read-schema}

高速化したい Map カラムごとに、サービスは各キーと値を `=` で連結した
`Array(String)` 型の `ALIAS` カラムを定義します。

```sql
ALTER TABLE otel_logs
ADD COLUMN LogAttributeItems Array(String)
ALIAS arrayMap(
  (arr) -> concat(arr.1, '=', arr.2),
  LogAttributes::Array(Tuple(String, String))
)
```

ALIAS 形式では、配列はディスク上で追加のバイトを一切消費しません。ClickHouse はこの配列を
クエリ実行時と索引のビルド時に計算します。`ALIAS` カラムに定義した `text(tokenizer = 'array')` スキップ索引は、
`key=value` のペアごとに 1 つのトークンを格納します。ClickHouse はこれを利用して、
元の Map を読み取ることなくグラニュールを除外します。

```sql
ALTER TABLE otel_logs
ADD INDEX idx_log_attr_items LogAttributeItems
TYPE text(tokenizer = 'array')
```

既存のテーブルに索引を作成した後は、過去のデータでもその索引を利用できるようにマテリアライズしてください ([&quot;スキップインデックスのマテリアライズ&quot;](#materialize-skip-index) を参照) 。

デフォルトのオブザーバビリティスキーマには、以下のカラムと索引があらかじめ含まれています。

| テーブル          | ALIAS カラム                                                            | テキストインデックス                                                         |
| ------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `otel_logs`   | `ResourceAttributeItems`, `ScopeAttributeItems`, `LogAttributeItems` | `idx_res_attr_items`, `idx_scope_attr_items`, `idx_log_attr_items` |
| `otel_traces` | `ResourceAttributeItems`, `SpanAttributeItems`                       | `idx_res_attr_items`, `idx_span_attr_items`                        |

### クエリの書き換え {#map-direct-read-rewrite}

ユーザーが UI または SDK から Map のサブキーでフィルタすると、サービスはクエリを次のように
書き換えます:

```sql
LogAttributes['k8s.pod.name'] = 'checkout'
```

次のように書き換えます:

```sql
has(LogAttributeItems, concat('k8s.pod.name', '=', 'checkout'))
```

書き換え後の形式では `LogAttributeItems` のテキスト索引が使用され、`key=value` トークンを含まない
行はまるごと除外されます。また、一致しない行については元の `LogAttributes` Map がデシリアライズされることもありません。high-cardinality な
オブザーバビリティのワークロードでは、Mapの添字によるアクセスと比べて、I/O が
通常 1 桁程度削減されます。

この書き換えは自動的に行われます。`LogAttributes['key']` を参照する保存クエリ、ダッシュボード、アラートは、
何も変更することなく高速化の恩恵を受けられます。

### ClickHouse のバージョン要件 {#map-direct-read-version}

このクエリの書き換えを行うには、テキスト索引付きの Array カラムに対してトークンレベルで直接枝刈りを行える
ClickHouse バージョンが必要です。サービスは接続先のサーバーバージョン (`SELECT version()`、接続ごとにキャッシュ) を検出し、
サーバーが以下の対応するしきい値を満たす場合にのみ、書き換え後の形式を出力します。
それより古いバージョンでは、自動的に元の Map の添字形式にフォールバックします。

<Tabs>
  <Tab title="ClickHouse Cloud">
    ClickHouse Cloud のビルドとオープンソースのリリースは、それぞれ独立したバージョン系列を採用しています。
    以下の Cloud 向け最小バージョンを参照してください。

    | ClickHouse ブランチ | Cloud の最小バージョン |
    | --------------- | -------------- |
    | 26.2            | `26.2.1.307`   |
    | 26.3            | `26.3.0.0`     |
    | 26.4            | `26.4.1.1740`  |
    | 26.5+           | すべてのバージョン      |

    最小バージョン `26.3.0.0` はこのブランチの最初のバージョンであるため、`26.3` のビルドはすべて
    サポート対象です。
  </Tab>

  <Tab title="オープンソース">
    | ClickHouse ブランチ | オープンソースの最小バージョン |
    | --------------- | --------------- |
    | 26.2            | `26.2.19.43`    |
    | 26.3            | `26.3.12.3`     |
    | 26.4            | `26.4.3.37`     |
    | 26.5+           | すべてのバージョン       |
  </Tab>
</Tabs>

<Info>
  **MATERIALIZED ではなく ALIAS を使用する理由**

  items 配列は、すでに Map カラムに格納されているデータを別の形で見せるためのウィンドウにすぎません。
  Map と配列の両方に二重に保存しても、新たなクエリパターンが利用可能になるわけではなく、
  書き込み I/O が倍増するだけです。`ALIAS` カラム上のテキスト索引は、挿入時に同じソースデータから
  構築されます。そのため、この最適化で増えるディスク使用量は索引の分だけです。
</Info>

## 最適化 4. 主キーの変更 {#modifying-the-primary-key}

主キーは、ほとんどのワークロードにおいて ClickHouse のパフォーマンスチューニングで最も重要な要素の 1 つです。効果的にチューニングするには、主キーの仕組みと、それがクエリパターンとどのように関係するかを理解する必要があります。結局のところ、主キーはユーザーがデータにアクセスする方法、特に最も頻繁にフィルタ条件として使用されるカラムに合わせて設計すべきです。

主キーは圧縮やストレージのレイアウトにも影響しますが、その主な目的はクエリのパフォーマンスです。このサービスでは、標準で用意されている主キーが、最も一般的なオブザーバビリティのアクセスパターンと高い圧縮率に向けてすでに最適化されています。ログ、トレース、メトリクスの各テーブルのデフォルトのキーは、一般的なワークフローで良好なパフォーマンスを発揮するよう設計されています。

主キーの前方にあるカラムでのフィルタリングは、後方にあるカラムでのフィルタリングよりも効率的です。ほとんどのユーザーにとってはデフォルトの設定で十分ですが、特定のワークロードでは主キーを変更することでパフォーマンスが向上する場合があります。

<Info>
  **用語に関する注記**

  本ドキュメントでは、「順序キー」という用語を「主キー」と同じ意味で使用します。厳密には ClickHouse ではこれらは異なりますが、Self-managed ClickHouse Observability では、通常どちらもテーブルの `ORDER BY` 句で指定された同じカラムを指します。詳細については、sorting key とは異なる主キーの選択に関する [ClickHouse ドキュメント](/ja/reference/engines/table-engines/mergetree-family/mergetree#choosing-a-primary-key-that-differs-from-the-sorting-key)を参照してください。
</Info>

主キーを変更する前に、ClickHouse における[プライマリインデックスの仕組みを理解するためのガイド](/ja/concepts/core-concepts/primary-indexes)に目を通すことを強く推奨します。

主キーのチューニングは、テーブルおよびデータ型ごとに異なります。あるテーブルとデータ型に有効な変更が、他にも有効とは限りません。目標は常に、特定のデータ型 (例：ログ) に合わせて最適化することです。

**通常、最適化の対象となるのはログとトレースのテーブルです。その他のデータ型で主キーの変更が必要になることはまれです。**

以下は、ログとトレースのオブザーバビリティテーブルにおけるデフォルトの主キーです。

* ログ ([`otel_logs`](/ja/clickstack/self-configured/ingesting-data/schemas#logs))  - `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)`
* トレース ([`otel_traces`](/ja/clickstack/self-configured/ingesting-data/schemas#traces))  - `(ServiceName, SpanName, toDateTime(Timestamp))`

その他のデータ型のテーブルで使用される主キーについては、[「テーブルとスキーマ」](/ja/clickstack/self-configured/ingesting-data/schemas)を参照してください。トレーステーブルは、サービス名とスパン名、続いてタイムスタンプによるフィルタリング向けに最適化されています。ログテーブルは先頭に 5 分単位の時間バケットを置いているため、時間範囲のスキャンではまずプライマリインデックスが使われ、その後各バケット内でサービス名による絞り込みが行われます。このレイアウトは、「サービス X で直近 N 分間に何が起きたか」を調べるという一般的なワークフローに適しています。主キーの順序どおりにフィルタを適用するのが最適ですが、これらのカラムをどの順序でフィルタリングしても、ClickHouse が[読み取り前にデータを枝刈り](/ja/concepts/features/performance/skip-indexes/skipping-indexes)するため、クエリは大きな恩恵を受けます。

主キーを選択する際には、カラムの最適な順序を決めるうえで考慮すべき点が他にもあります。[「主キーの選択」](#choosing-a-primary-key)を参照してください。

**主キーはテーブルごとに個別に変更してください。ログに適した設定が、トレースやメトリクスにも適しているとは限りません。**

### 主キーの選択 {#choosing-a-primary-key}

まず、特定のテーブルについて、アクセスパターンがデフォルトから大きく異なるかどうかを確認します。たとえば、ログをサービス名よりも先に Kubernetes ノードでフィルタすることが最も多く、それが主要なワークフローになっている場合は、主キーを変更する価値があるかもしれません。

<Info>
  **デフォルトの主キーの変更**

  ほとんどの場合、デフォルトの主キーで十分です。変更は慎重に行い、クエリパターンを明確に把握している場合に限ってください。主キーを変更すると他のワークフローのパフォーマンスが低下する可能性があるため、テストは欠かせません。
</Info>

必要なカラムを抽出したら、順序キー/主キーの最適化に取りかかれます。

順序キーを選ぶ際には、いくつかの簡単なルールが役立ちます。これらのルールは互いに矛盾する場合があるため、記載順に検討してください。このプロセスで選ぶキーは、最大 4〜5 個を目安とします。

1. よく使うフィルタやアクセスパターンに合ったカラムを選択します。オブザーバビリティの調査を、普段から特定のカラム (例: pod 名) でのフィルタリングから始めている場合、そのカラムは `WHERE` 句で頻繁に使用されます。使用頻度の低いカラムよりも、こうしたカラムを優先してキーに含めてください。
2. フィルタリング時に全行の大部分を除外でき、読み取るデータ量を減らせるカラムを優先します。サービス名やステータスコードは良い候補になることが多いですが、後者については、大部分の行を除外できる値でフィルタリングする場合に限ります。たとえば、200 コードでフィルタリングすると、ほとんどのシステムでは大部分の行に一致しますが、500 エラーであればごく一部の行にしか該当しません。
3. テーブル内の他のカラムと強く相関する可能性が高いカラムを優先します。これにより、それらの値も連続して格納されやすくなり、圧縮効率が向上します。
4. 順序キーに含まれるカラムに対する `GROUP BY` (チャート用の集計) や `ORDER BY` (ソート) の操作は、メモリ効率を高めることができます。

順序キーに使うカラムの部分集合が決まったら、それらを特定の順序で宣言する必要があります。この順序は、クエリにおけるセカンダリキー列での条件に基づくフィルタリングの効率と、テーブルのデータファイルの圧縮率の両方に大きく影響します。一般に、キーはカーディナリティの昇順に並べるのが最適です。ただし、順序キーの後方にあるカラムでのフィルタリングは、タプルの前方にあるカラムでのフィルタリングよりも効率が落ちる点も考慮する必要があります。これらのトレードオフを踏まえ、アクセスパターンを考慮してください。そして何より、複数のパターンを実際にテストしてください。順序キーとその最適化方法について理解を深めるには、[&quot;Choosing a Primary Key.&quot;](/ja/concepts/best-practices/choosing-a-primary-key) をお読みください。主キーのチューニングや内部のデータ構造についてさらに詳しく知りたい場合は、[&quot;A practical introduction to primary indexes in ClickHouse.&quot;](/ja/guides/clickhouse/data-modelling/sparse-primary-indexes) を参照してください。

### 主キーの変更 {#changing-the-primary-key}

データ取り込みを開始する前にアクセスパターンが確定している場合は、該当するデータ型のテーブルを削除して再作成するだけで済みます。

以下の例は、既存のスキーマはそのままに、`ServiceName` の前に `SeverityText` カラムを含む新しい主キーを持つログテーブルを作成する簡単な方法を示しています。

<Steps>
  <Step title="新しいテーブルを作成する" id="create-new-table-with-key">
    ```sql
    CREATE TABLE otel_logs_temp AS otel_logs
    PRIMARY KEY (SeverityText, ServiceName, Timestamp)
    ORDER BY (SeverityText, ServiceName, Timestamp)
    ```

    <Info>
      **順序キーと主キー**

      上記の例では、`PRIMARY KEY` と `ORDER BY` の両方を指定する必要がある点に注意してください。
      サービスでは、両者はほぼ常に同じになります。
      `ORDER BY` は物理的なデータ配置を制御し、`PRIMARY KEY` はスパースインデックスを定義します。
      非常に大規模なワークロードではまれに両者が異なる場合もありますが、ほとんどのユーザーは両者を一致させておくことをお勧めします。
    </Info>
  </Step>

  <Step title="テーブルを交換して削除する" id="exhange-and-drop-table">
    `EXCHANGE` 文を使用すると、テーブル名を[アトミック](/ja/concepts/core-concepts/glossary#atomicity)に入れ替えられます。入れ替え後、一時テーブル(元のデフォルトテーブル)は削除して構いません。

    ```sql
    EXCHANGE TABLES otel_logs_temp AND otel_logs
    DROP TABLE otel_logs_temp
    ```
  </Step>
</Steps>

ただし、**既存のテーブルの主キーは変更できません**。主キーを変更するには、新しいテーブルを作成する必要があります。

以下の手順に従うと、古いデータを保持したまま透過的にクエリできる状態を維持しつつ(必要に応じて UI では既存のキーを使用)、新しいデータはユーザーのアクセスパターンに最適化された新しいテーブルで提供できます。この方法では、データは引き続きデフォルトのテーブル名に送信されるため取り込みパイプラインを変更する必要がなく、すべての変更はユーザーから透過的に行われます。

<Note>
  大規模環境では、既存データを新しいテーブルにバックフィルする価値はほとんどありません。通常はコンピュートと I/O のコストが高く、得られるパフォーマンス上の利点に見合わないためです。代わりに、古いデータは[有効期限 (TTL) によって](/ja/clickstack/self-configured/managing/ttl)期限切れになるのに任せ、新しいデータで改善されたキーの恩恵を受けるようにしてください。
</Note>

以下では、同じく `SeverityText` を主キーの先頭カラムに追加する例を使用します。ここでは新しいデータ用のテーブルを作成し、古いテーブルは過去データの分析用に残しておきます。

<Steps>
  <Step title="新しいテーブルを作成する" id="create-new-table-with-key-2">
    目的の主キーを持つ新しいテーブルを作成します。接尾辞 `_23_01_2025` は、現在の日付に合わせて変更してください。例:

    ```sql
    CREATE TABLE otel_logs_23_01_2025 AS otel_logs
    PRIMARY KEY (SeverityText, ServiceName, Timestamp)
    ORDER BY (SeverityText, ServiceName, Timestamp)
    ```
  </Step>

  <Step title="Merge テーブルを作成する" id="create-merge-table">
    [Merge エンジン](/ja/reference/engines/table-engines/special/merge) (MergeTree と混同しないでください) は、自身ではデータを保存せず、任意の数の他のテーブルから同時に読み取ることができます。

    ```sql
    CREATE TABLE otel_logs_merge
    AS otel_logs
    ENGINE = Merge(currentDatabase(), 'otel_logs*')
    ```

    <Note>
      `currentDatabase()` は、コマンドが正しいデータベースで実行されることを前提としています。そうでない場合は、データベース名を明示的に指定してください。
    </Note>

    このテーブルにクエリを実行し、`otel_logs` のデータが返されることを確認してください。
  </Step>

  <Step title="Merge テーブルから読み取るように UI を更新する" id="update-clickstack-ui-to-read-from-merge-tree">
    ログのデータソースのテーブルとして `otel_logs_merge` を使用するよう UI を設定します。

    <div className="ch-image-lg">
      <Frame>
        ![Merge テーブルを選択](/images/clickstack/performance_guide/select_merge_table.webp)
      </Frame>
    </div>

    この時点では、書き込みは引き続き元の主キーを持つ `otel_logs` に対して行われ、読み取りには Merge テーブルが使用されます。ユーザーから見た変化はなく、インジェストへの影響もありません。
  </Step>

  <Step title="テーブルを入れ替える" id="exchange-the-tables">
    次に、`EXCHANGE` 文を使用して、`otel_logs` テーブルと `otel_logs_23_01_2025` テーブルの名前をアトミックに入れ替えます。

    ```sql
    EXCHANGE TABLES otel_logs AND otel_logs_23_01_2025
    ```

    以降、書き込みは更新後の主キーを持つ新しい `otel_logs` テーブルに対して行われます。既存のデータは `otel_logs_23_01_2025` に残り、引き続き Merge テーブル経由でアクセスできます。接尾辞は変更を適用した日付を示しており、そのテーブルに含まれる最新のタイムスタンプを表します。

    この手順により、インジェストを中断することなく、ユーザーに影響を与えずに主キーを変更できます。
  </Step>
</Steps>

主キーをさらに変更する必要が生じた場合も、この手順を応用できます。たとえば、1 週間後に、主キーには `SeverityText` ではなく `SeverityNumber` を含めるべきだと判断した場合などです。以下の手順は、主キーの変更が必要になるたびに何度でも適用できます。

<Steps>
  <Step title="新しいテーブルを作成する" id="create-new-table-with-key-3">
    目的の主キーを持つ新しいテーブルを作成します。
    以下の例では、テーブルの日付を示す接尾辞として `30_01_2025` を使用しています。例:

    ```sql
    CREATE TABLE otel_logs_30_01_2025 AS otel_logs
    PRIMARY KEY (SeverityNumber, ServiceName, TimestampTime)
    ORDER BY (SeverityNumber, ServiceName, TimestampTime)
    ```
  </Step>

  <Step title="テーブルを入れ替える" id="exchange-the-tables-v2">
    次に、`EXCHANGE` 文を使用して、`otel_logs` テーブルと `otel_logs_30_01_2025` テーブルの名前をアトミックに入れ替えます。

    ```sql
    EXCHANGE TABLES otel_logs AND otel_logs_30_01_2025
    ```

    以降、書き込みは更新後の主キーを持つ新しい `otel_logs` テーブルに対して行われます。古いデータは `otel_logs_30_01_2025` に残り、Merge テーブル経由でアクセスできます。
  </Step>
</Steps>

<Info>
  **不要になったテーブル**

  推奨どおり 有効期限 (TTL) ポリシーを設定している場合、書き込みが行われなくなった古い主キーのテーブルは、データの有効期限切れに伴って徐々に空になります。これらのテーブルを監視し、データがなくなったら定期的に削除してください。現時点では、このクリーンアップは手動で行う必要があります。
</Info>

### ブロック列による行ルックアップの高速化 {#row-lookup-block-columns}

デフォルトのオブザーバビリティ向けログスキーマでは、2 つの MergeTree の設定が有効になっています。これらはクエリパフォーマンスに直接影響するものではありませんが、
UI での行詳細のルックアップを大幅に高速化します。

```sql
SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1
```

これらの設定により、テーブル内のすべての行は、パーツ内で行を一意に識別する暗黙的な
`(_block_number, _block_offset)` のペアを持つようになります。UI でログの行をクリックして詳細パネルを開くと、サービスは
その行だけをフェッチするための追加クエリを発行します。ブロック列がない場合、
行の `WHERE` 句には、行を一意に特定できるだけのカラム (通常は主キーに
加えて `Body` と `SeverityText`) を含める必要があります。ブロック列がある場合は、
主キーに `_block_number` と `_block_offset` を加えるだけで済みます。`Body` のような大きな
カラムはルックアップ時に一切読み込まれないため、クエリが大幅に高速化されます。

サービスはテーブルの `CREATE` ステートメントからこの設定を検出し、両方のカラムが有効な場合には、
より簡潔な WHERE 句を自動的に生成します。アプリケーション側の
設定変更は不要です。

既存のログテーブルまたはトレーステーブルでこの最適化を有効にするには、次の手順を実行します。

```sql
ALTER TABLE otel_logs
MODIFY SETTING enable_block_number_column = 1, enable_block_offset_column = 1
```

これらの設定は、`ALTER` 以降に書き込まれたデータに適用されます。既存のパーツは、マージによって書き換えられるまで、
引き続き従来の行単位のルックアップを使用します。

## 最適化 5. materialized view の活用 {#exploiting-materialized-views}

<BetaBadge />

このサービスでは、[増分マテリアライズドビュー](/ja/concepts/features/materialized-views/incremental-materialized-view)を活用することで、1 分ごとの平均リクエスト所要時間の推移を算出するといった、集約負荷の高いクエリに依存する可視化を高速化できます。この機能によりクエリパフォーマンスが大幅に向上します。特に 1 日あたり約 10 TB 以上の大規模なデプロイメントで効果を発揮しやすく、1 日あたり PB 規模までのスケーリングも可能になります。増分マテリアライズドビューはベータ版のため、慎重に使用してください。

このサービスでこの機能を使用する方法の詳細については、専用ガイド[「materialized view」](/ja/clickstack/self-configured/managing/materialized-views)を参照してください。

## 最適化 6. プロジェクションの活用 {#exploting-projections}

プロジェクションは、マテリアライズドカラム、スキップ索引、主キー、materialized view の検討を終えた後に取り組む、最終段階の高度な最適化です。プロジェクションと materialized view は一見似ていますが、このサービスでは用途が異なり、適したシナリオもそれぞれ異なります。

<Frame>
  <iframe src="https://www.youtube.com/embed/6CdnUdZSEG0?si=1zUyrP-tCvn9tXse" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

実質的には、**プロジェクションはテーブルの隠れた追加コピー**であり、同じ行を**異なる物理的な順序**で格納するものと考えることができます。これによりプロジェクションは、基となるテーブルの `ORDER BY` キーとは別に独自のプライマリインデックスを持つため、ClickHouse は元の並び順に沿わないアクセスパターンに対しても、より効果的にデータをプルーニングできます。

materialized view でも、異なる順序キーを持つ別のターゲットテーブルに行を明示的に書き込むことで、同様の効果が得られます。主な違いは、**プロジェクションは ClickHouse によって自動的かつ透過的に管理される**のに対し、materialized view は明示的なテーブルであり、サービス側で登録し、意図的に選択しなければならないという点です。

基となるテーブルに対してクエリが実行されると、ClickHouse は基本レイアウトと利用可能なすべてのプロジェクションを評価し、それぞれのプライマリインデックスをサンプリングしたうえで、正しい結果を返せるレイアウトのうち、読み取るグラニュール数が最も少ないものを選択します。この判断はクエリ アナライザによって自動的に行われます。

したがって、このサービスにおいてプロジェクションは、次のような**純粋なデータの並べ替え**に最適です。

* アクセスパターンがデフォルトの主キーと根本的に異なる場合
* 単一の順序キーですべてのワークフローに対応するのが現実的でない場合
* 最適な物理レイアウトの選択を ClickHouse に透過的に任せたい場合

事前集約やメトリクスの高速化には、このサービスでは**明示的な materialized view** の使用を強く推奨しています。これにより、アプリケーションレイヤーがビューの選択と使用を完全に制御できます。

詳細については、以下を参照してください。

* [プロジェクションガイド](/ja/concepts/features/projections/projections)
* [プロジェクションを使用すべき場面](/ja/concepts/features/projections/projections#when-to-use-projections)
* [materialized view とプロジェクションの比較](/ja/concepts/features/projections/materialized-views-versus-projections)

### プロジェクションの例 {#example-projections}

トレーステーブルが、オブザーバビリティにおける標準的なアクセスパターン向けに最適化されているとします。

```sql
ORDER BY (ServiceName, SpanName, toDateTime(Timestamp))
```

TraceId でフィルタする (または TraceId を軸にグループ化やフィルタを頻繁に行う) ワークフローが主流である場合は、TraceId と時刻でソート済みの行を格納するプロジェクションを追加することもできます。

```sql
ALTER TABLE otel_v2.otel_traces
ADD PROJECTION prj_traceid_time
(
    SELECT *
    ORDER BY (TraceId, toDateTime(Timestamp))
);
```

<Info>
  **ワイルドカードを使用する**

  上記のプロジェクションの例では、ワイルドカード (`SELECT *`) を使用しています。カラムの部分集合のみを選択すると書き込みのオーバーヘッドを削減できますが、それらのカラムだけで完全に処理できるクエリしか対象にならないため、プロジェクションが使用される場面も限られます。サービスでは、これによりプロジェクションの利用がごく限られたケースに制限されることがよくあります。そのため、適用範囲を最大限に広げるには、通常はワイルドカードの使用を推奨します。
</Info>

他のデータ配置の変更と同様に、プロジェクションは新たに書き込まれたパーツにのみ適用されます。既存のデータに対してプロジェクションをビルドするには、次のようにマテリアライズします：

```sql
ALTER TABLE otel_v2.otel_traces
MATERIALIZE PROJECTION prj_traceid_time;
```

<Note>
  プロジェクションのマテリアライズには長い時間がかかり、大量のリソースを消費する可能性があります。オブザーバビリティデータは通常、有効期限 (TTL) によって削除されるため、この操作は本当に必要な場合にのみ実行してください。ほとんどの場合、プロジェクションを新たに取り込まれたデータにのみ適用するだけで十分です。これにより、直近 24 時間など、最も頻繁にクエリされる時間範囲を最適化できます。
</Note>

ClickHouse は、プロジェクションのほうが基本レイアウトよりもスキャンするグラニュールが少ないと見積もった場合、そのプロジェクションを自動的に選択することがあります。プロジェクションが最も確実に機能するのは、全行セット (`SELECT *`) を単純に並べ替えたものであり、かつクエリのフィルタがプロジェクションの `ORDER BY` とよく合致している場合です。

TraceId でフィルタ (特に等値比較) し、時間範囲を指定するクエリでは、上記のプロジェクションが効果を発揮します。例:

```sql
-- Fetch a specific trace quickly
SELECT *
FROM otel_traces
WHERE TraceId = 'aeea7f401feb75fc5af8eb25ebc8e974'
  AND Timestamp >= now() - INTERVAL 1 DAY
ORDER BY Timestamp;

-- Trace-scoped aggregation
SELECT
  toStartOfMinute(Timestamp) AS t,
  count() AS spans
FROM otel_traces
WHERE TraceId = 'aeea7f401feb75fc5af8eb25ebc8e974'
  AND Timestamp >= now() - INTERVAL 1 DAY
GROUP BY t
ORDER BY t;
```

`TraceId` を条件に含まないクエリや、プロジェクションの順序キーの先頭にない他の次元で主にフィルタするクエリは、通常このプロジェクションの恩恵を受けません (代わりに基本レイアウトから読み取られる場合があります) 。

<Note>
  プロジェクションには集計を格納することもできます (materialized view と同様) 。ただし、サービスではプロジェクションベースの集計は一般的に推奨されません。プロジェクションが選択されるかどうかは ClickHouse のアナライザに依存するので、その使用を制御したり挙動を把握したりするのが難しくなることがあります。代わりに、サービスがアプリケーションレイヤーで登録し、意図的に選択できる明示的な materialized view を使用することを推奨します。
</Note>

実際には、プロジェクションは、広範な検索からトレース中心のドリルダウンへ頻繁に切り替えるワークフロー (たとえば、特定の TraceId に対応するすべてのスパンを取得する場合) に最適です。

### コストとガイダンス {#projection-costs-and-guidance}

* **挿入時のオーバーヘッド**: 異なる順序キーを持つ `SELECT *` プロジェクションでは、実質的にデータを 2 回書き込むことになります。そのため書き込み I/O が増加し、インジェストを維持するために CPU とディスクのスループットが追加で必要になる場合があります。
* **使用は最小限に**: プロジェクションは、2 つ目の物理的な並び順によって多くのクエリで効果的な枝刈りが可能になるような、アクセスパターンが本当に多様な場合に限って使用するのが最適です。たとえば、2 つのチームが同じデータセットに対して根本的に異なる方法でクエリを実行するようなケースです。
* **ベンチマークで検証する**: 他のチューニングと同様に、プロジェクションの追加およびマテリアライズの前後で、実際のクエリレイテンシとリソース使用量を比較してください。

詳しい背景については、以下を参照してください。

* [ClickHouse プロジェクションガイド](/ja/concepts/features/projections/projections#when-to-use-projections)
* [materialized view とプロジェクションの比較](/ja/concepts/features/projections/materialized-views-versus-projections)

### `_part_offset` を使用した軽量プロジェクション {#lightweight-projections}

<BetaBadge />

<Info>
  **Self-managed ClickHouse Observability における軽量プロジェクションはベータ版です**

  `_part_offset-based` の軽量プロジェクションは、オブザーバビリティのワークロードには推奨されません。ストレージと書き込み I/O は削減できるものの、クエリ実行時のランダムアクセスが増える可能性があり、オブザーバビリティ規模の本番環境での挙動はまだ評価段階にあります。この推奨事項は、機能の成熟や運用データの蓄積に応じて変更される可能性があります。
</Info>

新しいバージョンの ClickHouse では、行全体を複製するのではなく、プロジェクションの sorting key と、基となるテーブルを指す `_part_offset` ポインタのみを格納する、より軽量なプロジェクションもサポートされています。これによりストレージのオーバーヘッドを大幅に削減できます。さらに最近の改善でグラニュール単位の枝刈りが可能になり、本来のセカンダリ索引に近い動作をするようになりました。詳細は以下を参照してください。

* [&#95;part&#95;offset によるよりスマートなストレージ](/ja/concepts/features/projections/projections#smarter_storage_with_part_offset)
* [ブログでの解説と例](https://clickhouse.com/blog/projections-secondary-indices#example-combining-multiple-projection-indexes)

### 代替手段 {#projection-alternatives}

複数の順序キーが必要な場合、選択肢はプロジェクションだけではありません。運用上の制約や、サービスにクエリをどのように振り分けたいかに応じて、次の方法も検討してください。

* OpenTelemetry collector を設定して、`ORDER BY` キーの異なる 2 つのテーブルに書き込み、テーブルごとに個別のデータソースを作成する。
* コピー用パイプラインとして materialized view を作成する。具体的には、メインテーブルに materialized view をアタッチし、未加工の行を SELECT して、順序キーの異なるセカンダリテーブルに書き込みます (非正規化またはルーティングのパターン) 。このターゲットテーブルに対してログソースを作成します。例は[こちら](/ja/concepts/features/materialized-views/incremental-materialized-view#filtering-and-transformation)を参照してください。
