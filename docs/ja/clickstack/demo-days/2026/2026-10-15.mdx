## 保存前に Webhook のボディテンプレートを検証 {#validating-webhook-body-templates-before-they-save}

*デモ担当者: [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

これまでは、ボディテンプレートに不備のある Generic または incident.io の Webhook を保存しても、警告は表示されませんでした。その結果、アラートの配信はすべて失敗し、エラーは ClickStack のトレースとサーバーログにしか記録されませんでした。よくある原因は、`{{#if (eq state \"ALERT\")}}` のように Handlebars の 式 内で引用符を JSON エスケープしてしまうことです。これは JSON としては有効ですが、テンプレートとしては無効です。

Webhook フォームでは、編集中にテンプレートがチェックされ、`Template error on line 1, column 29` のように行番号とカラム番号を含むエラーがエディタの下に表示されるようになりました。チェックは入力が 300 ms 止まってから行われるため、`{{ … }}` の 式 を入力している途中でエラーが表示されることはありません。空のボディはサービスのデフォルトテンプレートが使用されるためスキップされます。レンダリングされない Slack のボディも同様にスキップされます。また、エディタの下には `{{alertId}}`、`{{status}}`、`{{value}}`、`{{groupKey}}` など、使用できる変数が簡単な説明とともに表示されます。

同じ検証は、内部 API、外部 API v2、MCP の `clickstack_save_webhook` ツールのすべてにおいて、サーバー側でも実行されるようになりました。作成・更新・テスト時に無効なテンプレートが指定されると、Handlebars のエラーとその行番号・カラム番号を含む 400 が返されます。テストの場合は、何も送信されないうちに失敗します。なお、検証ではテンプレートがコンパイルできるかどうかのみを確認し、結果のレンダリングや、出力が有効な JSON かどうかの確認は行いません。

自動化されたワークフロー向けには、新しい `POST /api/v2/webhooks/validate` エンドポイントが追加され、Terraform で plan 時に Webhook の設定をチェックできるようになりました。`POST /api/v2/dashboards/validate` と同様に、保存は行わずに検証のみを実行します。作成時と同じ URL およびボディのチェックを行い、常に `{ valid, errors, normalized }` を含む 200 を返します。名前の一意性はチェックされません。

**関連 PR:** [#3350](https://github.com/hyperdxio/hyperdx/pull/3350) Webhook ボディテンプレートのコンパイルエラーをエディタに表示、[#3365](https://github.com/hyperdxio/hyperdx/pull/3365) コンパイルできない Webhook ボディテンプレートを拒否し、/api/v2/webhooks/validate を追加

## オンボーディング時の PromQL ログソースの自動検出 {#auto-detecting-a-promql-source-during-onboarding}

*デモ担当者: [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=96" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

接続にログソースが存在しない場合、ClickStack は OpenTelemetry テーブルを探索し、Logs、Traces、Metrics、Sessions の各ログソースを自動的に作成します。PromQL が有効な場合 (`NEXT_PUBLIC_ENABLE_PROMQL=true`)、ClickHouse の `TimeSeries` テーブルが見つかれば PromQL ログソースも作成されるようになりました。

検出処理では `engine = 'TimeSeries'` のテーブルを探し、それらが内部に作成する MergeTree テーブルは対象外とします。候補が複数ある場合は、次の順序で確認します。

* `prometheus.metrics`。[ClickHouse Prometheus ドキュメント](https://clickhouse.com/docs/concepts/features/interfaces/prometheus#create-a-timeseries-table)で使用されているテーブルです。
* OpenTelemetry テーブルと同じデータベース内の `metrics_ts`。collector の PromQL マイグレーションによって作成されます。
* 任意のデータベース内の `metrics_ts`。

`TimeSeries` テーブルが 1 つしかない場合、ClickStack は名前に関係なくそのテーブルを使用します。

`TimeSeries` テーブルしかない接続でも、手動セットアップに回されることなく PromQL ログソースが作成されるようになりました。検出または PromQL ログソースの作成に失敗しても、他のログソースはそのまま維持されます。

**関連 PR:** [#3310](https://github.com/hyperdxio/hyperdx/pull/3310) オンボーディング時に PromQL ログソースを自動検出、[#3311](https://github.com/hyperdxio/hyperdx/pull/3311) 開発用デフォルトログソースに PromQL ログソースをプロビジョニング

## PromQL チャートの系列数上限と最小粒度 {#series-limits-and-minimum-granularity-for-promql-charts}

*デモ担当者: [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=176" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

PromQL の折れ線グラフおよび積み上げ棒グラフに、ビルダーや生のSQLのチャートと同じ **Series Limit** 表示設定が追加されました。これまではブラウザ上でレンダリングされる系列が 250 件までに制限され、残りを読み込むオプションはあったものの、この設定は表に出ておらず、タイルにも保存されませんでした。

この上限は、生のSQLのチャートと同様にブラウザ側で適用されます。Prometheus 自体の `limit` パラメータは、値の大きい上位の系列ではなく、ラベルでソート済みの部分集合を返すうえ、ClickHouse テーブル関数によるフォールバックではこのパラメータが無視されるためです。非表示の系列に関するヒントも PromQL に即した内容になり、`GROUP BY` や `WHERE` の代わりに、ラベルマッチャーを絞り込むか `sum by (...)` を追加するよう案内します。

PromQL ログソースにも、メトリクスログソースと同様に **Minimum auto granularity** 設定が追加されました。この設定では、折れ線グラフ、数値、テーブル、円グラフ、棒グラフ (生成される PromQL プレビューを含む) において、自動粒度で選択される最小のバケットサイズを指定します。`$__rate_interval` もこの値をスクレイプ間隔として使用し、未設定の場合は 15s にフォールバックします。タイルで明示的に指定した粒度設定には影響しません。

**関連 PR:** [#3292](https://github.com/hyperdxio/hyperdx/pull/3292) PromQL ログソースで最小自動粒度をサポート、[#3294](https://github.com/hyperdxio/hyperdx/pull/3294) PromQL の時系列チャートで系列数上限をサポート

## PromQL ログソースに対するログソースレベルのアクセス制御 {#source-level-access-control-for-promql-sources}

*デモ担当者: [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=301" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**この機能は Managed ClickStack でのみ利用できます。**

ログ、トレース、メトリクスと同様に、PromQL ログソースにもロールベースのアクセス制御が適用されるようになりました。きめ細かなログソースロールを使えば、ある PromQL ログソースには **閲覧** アクセスを付与し、別のログソースへのアクセスは制限するといった設定が可能です。

すべての `/v1/prometheus/*` ルートでログソースに対する **閲覧** アクセスがチェックされるようになり、アクセス権がない場合は 403 `RBAC_PERMISSION_DENIED` が返されます。呼び出し元のログソースアクセスルールによってログソース自体が非表示になっている場合は、ログソース API と同じく 404 `Source not found` が返されます。なお、この変更で ClickHouse 側でのロールの適用が追加されるわけではありません。ClickStack Cloud では、PromQL クエリはもともとユーザー自身のトークンで実行されているためです。

## ダッシュボード向けアドホックフィルタ {#ad-hoc-filters-for-dashboards}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=401" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

ダッシュボードでは、既存の変数およびフィルタに加えて、**Ad hoc keys and values** フィルタタイプを利用できるようになりました。各アドホックフィルタは、ログやトレースなど 1 つ以上の ClickHouse ログソース、または Prometheus ログソースをもとに、利用可能なキーと値を候補として表示します。デフォルトでは、条件はそれらのログソースを使用するすべてのタイルに適用されますが、適用対象のログソースを絞り込むこともできます。この機能は `NEXT_PUBLIC_ENABLE_ADHOC_FILTERS` で有効化でき、予定されている作業のおよそ半分が完了しています。

ダッシュボードのフィルタバーにあるフィルタの入力欄をクリックし、キー、オペレーター、値を選択します。キーと値はいずれも候補が表示されます。SQL ログソースでは equals、not equals、regex、not regex、`LIKE`、`NOT LIKE` を使用できます。PromQL ログソースでは、カラムキーではなく Prometheus のラベルを使用します。適用した条件はピルとして表示され、編集、除外条件への切り替え、クリアができます。選択内容は URL に保存されるほか、ダッシュボードのデフォルトのフィルタ状態として保存することもできます。

条件がタイルにどのように適用されるかは、タイルの種類によって異なります。

* ビルダータイルは既存の `filter` 設定プロパティを使用するため、`WHERE` 句に変数を追加する必要はありません。
* 生のSQLタイルは `$__filters` を使用します。クエリにこのマクロを含める必要があり、含まれていない場合は警告が表示されます。条件が適用されていない場合は `1 = 1` に展開されます。
* PromQL タイルは Grafana と同じパーサーライブラリを使用し、すべてのメトリクスセレクターに条件をラベルマッチャーとして追加します。

適用された条件は、生成された SQL および PromQL のプレビューで確認できます。

**検索タイル**から直接フィルタリングすることもできます。セルにカーソルを合わせると、検索ページと同じコピー、フィルタ、除外のオプションが表示されます。フィルタリングすると、その値が該当するアドホックフィルタに追加され、同じ値をもう一度クリックすると削除されます。サイドパネルで行を開いた場合も、そこにあるフィルタボタンはダッシュボードに適用されます。現時点では、クリックによるフィルタリングは検索タイルでのみ利用できます。

ダッシュボードをインポートする際には、アドホックフィルタのクエリ対象のログソースと適用対象のログソースの両方を再マッピングできます。外部 API および MCP は、まだアドホックフィルタに対応していません。

**関連 PR:** [#3335](https://github.com/hyperdxio/hyperdx/pull/3335) アドホックダッシュボードフィルタ用のスキーマと型を追加、[#3317](https://github.com/hyperdxio/hyperdx/pull/3317) FilterPill を抽出し、フィルタエディタコンポーネントを追加、[#3341](https://github.com/hyperdxio/hyperdx/pull/3341) アドホックダッシュボードフィルタを設定する UI を追加、[#3343](https://github.com/hyperdxio/hyperdx/pull/3343) アドホックダッシュボードフィルタの入力欄を描画、[#3366](https://github.com/hyperdxio/hyperdx/pull/3366) アドホックダッシュボードフィルタの条件をブロードキャスト、[#3367](https://github.com/hyperdxio/hyperdx/pull/3367) アドホックフィルタのインポート時のログソース再マッピングをサポート、[#3380](https://github.com/hyperdxio/hyperdx/pull/3380) 検索タイルでのクリックによるアドホックフィルタをサポート

## SELECT と ORDER BY を結果テーブルへ移動 {#moving-select-and-order-by-into-the-results-table}

*デモ担当者: [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=636" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**これは検討段階の取り組みであり、リリースを確約するものではありません。**

現在の検索ページでは、`SELECT` と `ORDER BY` が `WHERE` の隣に配置されていますが、実際に影響するのは結果テーブルだけです。イベントパターンやイベントデルタに切り替えても表示されたままで、変更しても何も反映されません。また、ヒアリングしたユーザーの中には、`SELECT` でカラムを選択できることに気付いていない方もいました。ユーザーが探していたのは、カラムやソートを操作するためのコントロールでした。

このプロトタイプでは、両方を **カラム** と **ソート** として結果テーブルのツールバーに移し、イベントデルタとイベントパターンでは非表示にしています。**カラム** には現在の `SELECT` 項目が一覧表示され、ドラッグで並べ替えたり、削除したりできます。候補から選ぶか、`upper(Body) as message` のような式を入力して **Add** をクリックします。**SQL** タブでは、`SELECT` 全体を直接編集できます。

**ソート** には、各 `ORDER BY` フィールドとその並び順が一覧表示されます。`(toDateTime(Timestamp), Timestamp) DESC` のようなタプルにも対応しています。**SQL** から句をそのまま編集することも可能です。`Timestamp DESC NULLS LAST` のように、コントロールで分解できない式は SQL タブで開きます。コントロールで変更すると SQL が自動生成されますが、これまでどおり自分で記述することもできます。

**Apply** をクリックすると句が更新されて検索が実行され、**Cancel** で変更を破棄し、**Reset to default** でログソースのデフォルトに戻ります。カラム幅のリセット、行の折り返し、生成された SQL の表示、CSV のエクスポートといったテーブル操作は、ツールバー右側のアイコンボタンに移動します。

これにより、検索フォームにも少し余裕が生まれます。1 行目の左側にはログソース、右側には **Update** と **アラート** が配置されます。`WHERE` 句は全幅の専用行となり、Live Tail、リフレッシュ間隔、**Run** と同じ行に並びます。

この PR はまだドラフト段階です。使い心地についてぜひご意見をお聞かせください。

## スマートフォンでも使える検索ページ {#a-usable-search-page-on-a-phone}

*デモ担当者: [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=843" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

スマートフォンでアラートを開いたら、すぐにログを確認できるのが理想です。これまでは、フィルタのサイドバーが 200px 未満に縮まらず、クエリの行も折り返されず、結果は `100vh` のフレーム内でクリッピングされていました。そのため、ログまでスクロールすることすらできませんでした。

検索ページは、幅が 900px 未満になるとコンパクトなレイアウトに切り替わるようになりました (この幅ではナビゲーションもすでに折りたたまれます) 。フィルタは初期状態では閉じており、**Show filters** からドロワーで開けるため、ログテーブルに画面の全幅を使えます。`SELECT` と `ORDER BY` は **カラム** トグルの中に収められますが、検索ボックスは常に表示されます。ヒストグラムも高さを 72px に縮めて表示され、結果はツールバー下の領域でスクロールします。フィルタのドロワーを開いてもデスクトップ版の設定は変わらず、ウィンドウ幅を 900px より広げるとデスクトップ用のレイアウトに戻ります。

コンパクトなビューポート用のフックとレスポンシブなサイドパネルは `packages/app/src/components/CompactViewport/` に置かれており、他のページでも再利用できます。最初にこれらを採用したのが検索ページです。この変更は、本記事で紹介しているカラムとソートのプロトタイプよりも前に取り込まれました。このプロトタイプは、画面幅にかかわらず `SELECT` と `ORDER BY` を結果テーブル内に移すものです。

## フィルタのキーと値をサイドバーにストリーミング表示 {#streaming-filter-keys-and-values-into-the-sidebar}

*デモ担当者: [@knudtty](https://github.com/knudtty)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=899" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

これまで、検索ページのフィルタサイドバーには、すべてのフィルタクエリが完了するまでスピナーが 1 つ表示されるだけでした。クエリ自体はすでに結果をストリーミングしていましたが、フィルタを使えるようになるには、最も遅いクエリの完了を待つ必要がありました。

現在は、まずキーがそれぞれの読み込みインジケーター付きで表示され、各クエリの結果が返るたびに値が順次表示されます。クエリ自体に変更はなく、サイドバーが結果を受け取った時点で表示するようになっただけです。この違いは、2 日間の検索など、長い時間範囲で特に顕著に表れます。

また、サイドバーが離れたときの状態を保持しない問題も修正しました。ブラウザの応答性を保つため、フィルタグループは画面外にスクロールされると DOM から削除されます。以前は、スクロールして戻ると、展開していたグループが折りたたまれ、読み込み済みの分布も消えていました。現在は、どちらも離れたときの状態のまま保持されます。

**関連 PR:** [#3348](https://github.com/hyperdxio/hyperdx/pull/3348) Stream filter keys and value results to UI, [#3377](https://github.com/hyperdxio/hyperdx/pull/3377) Persist filter expand state upon scrolling
