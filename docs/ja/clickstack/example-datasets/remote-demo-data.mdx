**以下のガイドは、[all-in-one image の手順](/ja/clickstack/getting-started/oss)または [Local Mode Only](/ja/clickstack/deployment/local-mode-only) を使用して Open Source ClickStack をデプロイし、初期ユーザーの作成を完了していることを前提としています。あるいは、ローカル環境でのセットアップをすべて省略し、このデータセットを使用している ClickStack のホストデモ [play-clickstack.clickhouse.com](https://play-clickstack.clickhouse.com) に接続することもできます。**

このガイドでは、公開 ClickHouse playground の [sql.clickhouse.com](https://sql.clickhouse.com) でホストされているサンプルデータセットを使用します。このデータセットには、ローカルの ClickStack デプロイメントから接続できます。

<Warning>
  **Managed ClickStack ではサポートされていません**

  Managed ClickStack ではリモートデータベースはサポートされていません。そのため、このデータセットもサポート対象外です。
</Warning>

このデータセットには、公式 OpenTelemetry (OTel) デモの ClickHouse 版から取得した約 40 時間分のデータが含まれています。データは毎晩再生され、タイムスタンプは現在の時間帯に合わせて調整されるため、HyperDX に統合されたログ、トレース、メトリクスを使ってシステムの挙動を確認できます。

<Info>
  **データの違いについて**

  このデータセットは毎日午前 0 時から再生されるため、デモを確認するタイミングによって表示される可視化は異なる場合があります。
</Info>

<div id="demo-scenario">
  ## デモシナリオ
</div>

このデモでは、望遠鏡や関連アクセサリを販売するEC サイトで発生したインシデントを調査します。

カスタマーサポートチームから、ユーザーがチェックアウト時の支払いを完了できない問題が発生しているとの報告がありました。この問題は、調査のために Site Reliability Engineering (SRE) チームにエスカレーションされています。

SRE チームは HyperDX を使用してログ、トレース、メトリクスを分析し、問題の診断と解決を進めます。その後、セッションデータを確認し、導き出した結論が実際のユーザー行動と一致しているかどうかを確かめます。

<div id="demo-steps">
  ## デモの手順
</div>

**このデモでは、[ClickStack SDKs](/ja/clickstack/ingesting-data/sdks/index) を使ってインストルメントを行い、Kubernetes にサービスをデプロイしています。また、そこからメトリクスとログも収集しています。**

<Steps>
  <Step>
    ### デモサーバーに接続する

    <Info>
      **ローカル専用モード**

      Local Mode でデプロイする際に `Connect to Demo Server` をクリックした場合は、この手順をスキップできます。このモードを使用する場合、ログソースには `Demo_` プレフィックスが付きます (例: `Demo_Logs`) 。
    </Info>

    `Team Settings` に移動し、`Local Connection` の `Edit` をクリックします。

    <Image img="/images/use-cases/observability/edit_connection.webp" alt="接続を編集" size="lg" />

    接続名を `Demo` に変更し、続いて表示されるフォームにデモサーバー用の以下の接続情報を入力します。

    * `Connection Name`: `Demo`
    * `Host`: `https://sql-clickhouse.clickhouse.com`
    * `Username`: `otel_demo`
    * `Password`: 空欄のままにする

    <Image img="/images/use-cases/observability/hyperdx-demo/edit_demo_connection.webp" alt="デモ接続を編集" size="lg" />
  </Step>

  <Step>
    ### ログソースを変更する

    <Info>
      **ローカル専用モード**

      Local Mode でデプロイする際に `Connect to Demo Server` をクリックした場合、この手順は省略できます。このモードを使用している場合、ログソースには `Demo_` というプレフィックスが付きます (例: `Demo_Logs`) 。
    </Info>

    上にスクロールして `Sources` に戻り、各ログソース (`Logs`、`Traces`、`Metrics`、`Sessions`) が `otel_v2` データベースを使用するように変更します。

    <Image img="/images/use-cases/observability/hyperdx-demo/edit_demo_source.webp" alt="デモのログソースを編集" size="lg" />

    <Note>
      各ログソースでデータベースの一覧がすべて表示されるようにするには、ページの再読み込みが必要な場合があります。
    </Note>
  </Step>

  <Step>
    ### 時間範囲を調整する

    右上のタイムピッカーを使って、直前の `1 day` のすべてのデータが表示されるように時間範囲を調整します。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_2.webp" alt="ステップ 2" size="lg" />

    概要バーグラフでは、エラー数にわずかな差が見られる場合があり、いくつかの連続したバーで赤色が少し増えています。

    <Note>
      バーの位置は、データセットをクエリするタイミングによって異なります。
    </Note>
  </Step>

  <Step>
    ### エラーで絞り込む

    エラーを目立たせるには、`SeverityText` フィルターを使用し、`error` を選択してエラーレベルのエントリのみを表示します。

    これで、エラーがよりはっきりと確認できるようになります。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_3.webp" alt="ステップ 3" size="lg" />
  </Step>

  <Step>
    ### エラーパターンを特定する

    HyperDX の Clustering 機能を使うと、エラーを自動的に検出し、意味のあるパターンに自動でグループ化できます。これにより、大量のログやトレースを扱う際の分析を効率化できます。使用するには、左側のパネルにある `Analysis Mode` メニューから `イベントパターン` を選択します。

    これらのエラークラスターからは、`Failed to place order` という名前のパターンを含む、決済失敗に関連する問題が確認できます。さらに、カード請求時の問題や cache の容量超過を示すクラスターもあります。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_4.webp" alt="Step 4" size="lg" />

    これらのエラークラスターは、異なるサービスに由来している可能性が高い点に注意してください。
  </Step>

  <Step>
    ### エラーパターンを調査する

    報告されている「ユーザーが支払いを完了できる」問題と相関している、最もわかりやすいエラークラスター `Failed to place order` をクリックします。

    これにより、`frontend` サービスに関連付けられたこのエラーの全発生一覧が表示されます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_5.webp" alt="Step 5" size="lg" />

    表示されたエラーのいずれかを選択します。ログのメタデータが詳細に表示されます。`概要` と `Column Values` の両方をスクロールして確認すると、cache が原因でカード請求に問題が発生していることが示唆されます。

    `failed to charge card: could not charge the card: rpc error: code = Unknown desc = Visa cache full: cannot add new item.`

    <Image img="/images/use-cases/observability/hyperdx-demo/step_6.webp" alt="Step 6" size="lg" />
  </Step>

  <Step>
    ### インフラストラクチャを調査する

    支払いの失敗を引き起こしている可能性が高い cache 関連のエラーは特定できましたが、この問題がマイクロサービス アーキテクチャのどこで発生しているのかは、まだ突き止める必要があります。

    cache の問題を踏まえると、基盤となるインフラストラクチャを調べるのが自然です。関連するポッドでメモリの問題が発生している可能性もあります。ClickStack では、ログとメトリクスが統合され、コンテキストの中で表示されるため、根本原因をすばやく見つけやすくなります。

    `Infrastructure` タブを選択して、`frontend` service の基盤となるポッドに関連するメトリクスを表示し、期間を `1d` に広げます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_7.webp" alt="ステップ 7" size="lg" />

    この問題はインフラストラクチャに起因しているようには見えません。エラーの前後を含め、この期間を通してメトリクスに目立った変化はありません。Infrastructure タブを閉じます。
  </Step>

  <Step>
    ### トレースを調べる

    ClickStack では、トレースはログとメトリクスの両方にも自動的に相関付けられます。原因となっているサービスを特定するために、選択したログに関連付けられたトレースを見てみましょう。

    関連するトレースを可視化するには、`Trace` を選択します。続いて表示されるビューを下にスクロールすると、各サービス内のスパンをつなぎながら、HyperDX がマイクロサービス全体にまたがる分散トレースをどのように可視化しているかを確認できます。支払い処理には、チェックアウト処理や通貨換算を行うサービスを含む、複数のマイクロサービスが関与していることがわかります。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_8.webp" alt="ステップ 8" size="lg" />

    ビューの一番下までスクロールすると、`payment` サービスがエラーの原因になっており、その影響が呼び出しチェーンをさかのぼって伝播していることがわかります。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_9.webp" alt="ステップ 9" size="lg" />
  </Step>

  <Step>
    ### トレースの検索

    ユーザーが購入を完了できない原因が、payment サービスの cache の問題にあることは確認できました。根本原因についてさらに詳しく把握するため、このサービスのトレースを詳しく見ていきましょう。

    `Search` を選択して、メインの Search view に切り替えます。`Traces` のデータソースに切り替え、`Results table` ビューを選択します。**時間範囲が引き続き過去1日になっていることを確認してください。**

    <Image img="/images/use-cases/observability/hyperdx-demo/step_10.webp" alt="ステップ 10" size="lg" />

    このビューには、過去1日間のすべてのトレースが表示されます。問題は payment サービスで発生していることがわかっているため、`ServiceName` に `payment` filter を適用します。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_11.webp" alt="ステップ 11" size="lg" />

    `Event Patterns` を選択してトレースにイベントクラスタリングを適用すると、`payment` サービスの cache の問題をすぐに確認できます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_12.webp" alt="ステップ 12" size="lg" />
  </Step>

  <Step>
    ### トレースのインフラストラクチャを調査する

    `Results table` をクリックして結果ビューに切り替えます。`StatusCode` フィルターで `Error` 値を指定し、エラーに絞り込みます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_13.webp" alt="ステップ 13" size="lg" />

    `Error: Visa cache full: cannot add new item.` のエラーを選択し、`Infrastructure` タブに切り替えて、時間範囲を `1d` に広げます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_14.webp" alt="ステップ 14" size="lg" />

    トレースとメトリクスを関連付けると、`payment` サービスでメモリと CPU が増加した後に `0` まで低下していることがわかります (これはポッドの再起動によるものと考えられます) 。このことから、cache の問題がリソース問題を引き起こしたことが示唆されます。結果として、支払い完了時間に影響している可能性があります。
  </Step>

  <Step>
    ### より迅速に原因を特定するためのイベントデルタ

    イベントデルタは、パフォーマンスやエラー率の変化を特定のデータサブセットに関連付けることで異常を可視化し、根本原因をすばやく特定しやすくします。

    `payment` サービスに cache の問題があり、その結果リソース消費が増加していることはわかっていますが、根本原因はまだ完全には特定できていません。

    結果テーブルビューに戻り、エラーを含む時間範囲を選択してデータを絞り込みます。エラー発生前の数時間分を左側に含め、可能であれば後の時間帯も選択してください (issue がまだ継続している可能性があります) 。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_15.webp" alt="Step 15" size="lg" />

    エラーフィルターを削除し、左側の `Analysis Mode` メニューから `Event Deltas` を選択します。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_16.webp" alt="Step 16" size="lg" />

    上部のパネルには処理時間の分布が表示され、色はイベント密度 (スパン数) を示します。主な集中領域の外側にあるイベントのサブセットは、通常、調査対象として有力です。

    `1ms` を超える duration のイベントを選択し、`Filter by selection` フィルターを適用すると、「normal」なイベントと、duration が約 0ms のスパンから成る高密度グループとの差異を分析できます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_17.webp" alt="Step 17" size="lg" />

    このデータサブセットに対して分析を行うと、選択範囲外の「background」スパンの大半が Visa トランザクションであり、cache errors によって 0ms の応答に関連していることがわかります。
  </Step>

  <Step>
    ### より詳しいコンテキストを把握するためのチャートの活用

    ClickStack では、ログ、トレース、またはメトリクス内の任意の数値をチャート化して、より詳しいコンテキストを把握できます。

    ここまでで、次のことが分かりました。

    * 問題は payment サービスにある
    * cache がいっぱいになっている
    * その結果、リソース消費が増加した
    * この問題により、Visa での支払いが完了しなくなったか、少なくとも完了までに非常に長い時間がかかるようになった

    <br />

    左側のメニューから `Chart Explorer` を選択します。支払いの完了にかかる時間をチャート化するため、次の値を設定します。

    * `Data Source`: `Traces`
    * `Metric`: `Maximum`
    * `SQL Column`: `Duration`
    * `Where`: `ServiceName: payment`
    * `Timespan`: `Last 1 day`

    <br />

    `▶️` をクリックすると、支払いのパフォーマンスが時間の経過とともにどのように低下したかを確認できます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_18.webp" alt="ステップ 18" size="lg" />

    `Group By` を `SpanAttributes['app.payment.card_type']` に設定すると (オートコンプリートを使うには `card` と入力するだけです) 、Mastercard と比較して Visa トランザクションでサービスのパフォーマンスがどのように低下したかを確認できます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_19.webp" alt="ステップ 19" size="lg" />

    なお、error が発生するとレスポンスは `0s` で返るようになります。
  </Step>

  <Step>
    ### メトリクスをさらに確認して、より多くのコンテキストを得る

    最後に、キャッシュサイズをメトリクスとしてプロットし、時間の経過とともにどのように推移したかを確認して、より多くのコンテキストを得ましょう。

    以下の値を入力してください:

    * `Data Source`: `Metrics`
    * `Metric`: `Maximum`
    * `SQL Column`: `visa_validation_cache.size (gauge)` (`cache` と入力するだけでオートコンプリートされます)
    * `Where`: `ServiceName: payment`
    * `Group By`: `<empty>`

    キャッシュサイズが 4～5 時間かけて増加し (おそらくソフトウェアのデプロイ後) 、その後最大サイズの `100,000` に達したことがわかります。`Sample Matched Events` から、エラーはキャッシュがこの上限に達したことと相関しており、その後はサイズが `0` と記録され、レスポンスも `0s` で返っていることが確認できます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_20.webp" alt="Step 20" size="lg" />

    要約すると、ログ、トレース、そして最後にメトリクスを調べた結果、次のことがわかりました:

    * 問題は payment サービスにあります
    * おそらくデプロイに伴うサービスの挙動変化により、4～5 時間かけて visa キャッシュが徐々に増加し、最大サイズの `100,000` に達しました
    * これにより、キャッシュのサイズが増えるにつれてリソース消費も増加しました。実装に問題がある可能性が高いです
    * キャッシュが増えるにつれて、Visa 決済のパフォーマンスは低下しました
    * 最大サイズに達すると、キャッシュは決済を拒否し、自身のサイズを `0` と報告しました。
  </Step>

  <Step>
    ### セッションを使う

    セッションを使うとユーザー体験を再生でき、ユーザー視点でエラーがどのように発生したかを視覚的に確認できます。通常、根本原因の特定に直接使うことはあまりありませんが、カスタマーサポートに報告された問題の確認には有用であり、さらに詳しい調査の出発点にもなります。

    HyperDX では、セッションはトレースやログに関連付けられているため、原因の全体像を把握できます。

    たとえば、サポートチームから支払いの問題が発生したユーザーのメールアドレス `Ronny.Windler@gmail.com` が共有された場合、ログやトレースを直接検索するよりも、まずそのユーザーのセッションから確認するほうが効果的なことがよくあります。

    左側のメニューから `Client Sessions` タブに移動し、データソースが `Sessions` に、時間範囲が `Last 1 day` に設定されていることを確認します。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_21.webp" alt="ステップ 21" size="lg" />

    `SpanAttributes.userEmail: Ronny.Windler` を検索して、対象の顧客のセッションを見つけます。セッションを選択すると、左側にその顧客のセッションにおけるブラウザーイベントと関連するスパンが表示され、右側にはユーザーのブラウザー操作が再現表示されます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_22.webp" alt="ステップ 22" size="lg" />
  </Step>

  <Step>
    ### セッションのリプレイ

    ▶️ ボタンを押すと、セッションをリプレイできます。`Highlighted` と `All Events` を切り替えることで、スパンの粒度を変えられます。前者では、主要なイベントとエラーが強調表示されます。

    スパンの一番下までスクロールすると、`/api/checkout` に関連する `500` エラーを確認できます。この特定のスパンの ▶️ ボタンを選択すると、リプレイがセッション内のその時点に移動するため、顧客の体験を確認できます。支払いは単に機能していないように見える一方で、エラーは表示されていません。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_23.webp" alt="ステップ 23" size="lg" />

    このスパンを選択すると、原因が内部エラーであったことを確認できます。`Trace` タブをクリックし、接続されたスパンをたどっていくことで、顧客が実際に cache の問題の影響を受けていたことを確認できます。

    <Image img="/images/use-cases/observability/hyperdx-demo/step_24.webp" alt="ステップ 24" size="lg" />
  </Step>
</Steps>
