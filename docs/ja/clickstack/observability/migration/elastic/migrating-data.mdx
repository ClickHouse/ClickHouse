このガイドでは、Elastic から、デフォルトのエクスペリエンスである**完全マネージド型の ClickHouse オブザーバビリティ**への移行を中心に説明します。基盤となるスキーマとストレージは ClickHouse が管理します。インジェストパイプラインは、テレメトリーを **OpenTelemetry Protocol (OTLP)** フォーマットで送信する必要があります。Elasticsearch のドキュメントを完全マネージド型サービスに直接インポートすることはできません。

セルフマネージドのデプロイメントについては、[Elasticsearch と ClickHouse の同等の概念](/ja/clickstack/self-configured/migration/elastic/concepts)および[型マッピング](/ja/clickstack/self-configured/migration/elastic/types)を参照してください。セルフマネージド環境向けのデータ移行手順は、以下で区別して記載しています。

## 並行稼働戦略 {#parallel-operation-strategy-self-configured}

オブザーバビリティのユースケースで Elastic から ClickHouse オブザーバビリティへ移行する場合は、履歴データを移行するのではなく、**並行稼働**のアプローチを推奨します。この戦略には次のような利点があります。

1. **リスクの最小化**: 両方のシステムを並行して稼働させることで、既存のデータやダッシュボードへのアクセスを維持したまま、ClickHouse オブザーバビリティを検証し、ユーザーに新しいシステムに慣れてもらうことができます。
2. **データの自然な失効**: ほとんどのオブザーバビリティデータは保持期間が限られている (通常 30 日以下) ため、Elastic 上のデータが失効していくのに合わせて自然に移行できます。
3. **移行の簡素化**: システム間で履歴データを移動するための複雑なデータ転送ツールやプロセスが不要です。

<br />

<Info>
  **データの移行**

  セルフマネージドのデプロイメントでは、`Elasticsearch` テーブルエンジンを使用して履歴ドキュメントを読み取り、ClickHouse テーブルにコピーできます。詳しくは[データの移行](#migrating-data-self-configured)を参照してください。これは、完全マネージド型の ClickHouse オブザーバビリティで使用される OTLP インジェストのパスとは別の方法です。
</Info>

### 実装手順 {#implementation-steps-self-configured}

<Steps>
  <Step title="二重インジェストを設定する" id="configure-dual-ingestion-self-configured">
    データ収集パイプラインを設定し、Elastic と ClickHouse オブザーバビリティの両方へ同時にデータを送信します。完全マネージド型の ClickHouse オブザーバビリティを使用する場合、パイプラインはインジェスト API key を使用して、マネージドエンドポイントへ OTLP でエクスポートする必要があります。Elasticsearch の JSON ドキュメントをそのエンドポイントへ転送するだけでは不十分です。

    具体的な方法は、現在使用している収集用エージェントによって異なります。詳細は「[エージェントの移行](/ja/clickstack/observability/migration/elastic/migrating-agents)」を参照してください。
  </Step>

  <Step title="保持期間を調整する" id="adjust-retention-period-self-configured">
    移行期間中も履歴データを引き続き参照できるよう、両システムの保持期間を見直します。デプロイメントごとのガイダンスについては、[保持期間と有効期限 (TTL)](#retention-and-ttl-self-configured) を参照してください。
  </Step>

  <Step title="検証と比較" id="validate-and-compare-self-configured">
    * 両システムに対してクエリを実行し、データの整合性を確認します
    * クエリパフォーマンスと結果を比較します
    * ダッシュボードとアラートを ClickHouse オブザーバビリティへ移行します。現時点では手動で行う必要があります。
    * 重要なダッシュボードとアラートがすべて ClickHouse オブザーバビリティで想定どおりに動作することを確認します
  </Step>

  <Step title="段階的な移行" id="graudal-transition-self-configured">
    * Elastic 側のデータが保持期間の経過とともに失効していくにつれ、ClickHouse オブザーバビリティへの依存度が高まっていきます
    * ClickHouse オブザーバビリティの信頼性を十分に確認できたら、クエリとダッシュボードの切り替えを開始できます
  </Step>
</Steps>

### 長期保持 {#long-term-retention-self-configured}

より長い保持期間が必要な組織の場合:

* Elastic 上のすべてのデータが期限切れになるまで、両方のシステムを並列に運用し続けます
* セルフマネージドのデプロイメントでは、[materialized view](/ja/concepts/features/materialized-views/incremental-materialized-view) を使用して、生データは期限切れにしつつ、集計済みまたはフィルタ済みの履歴データを保持することを検討してください。

### 移行スケジュール {#migration-timeline-self-configured}

移行スケジュールは、データ保持期間の要件によって異なります。

* **30日間の保持期間**: 1か月以内に移行を完了できます。
* **より長い保持期間**: Elastic 内のデータが期限切れになるまで並行稼働を継続します。
* **履歴データ**: インポートを計画する前に、[データの移行](#migrating-data-self-configured)にあるデプロイメント形態ごとのガイダンスを確認してください。

## 保持期間と有効期限 (TTL) {#retention-and-ttl-self-configured}

<Tabs>
  <Tab title="完全マネージド型">
    <BetaBadge label="ベータ版" />

    <Note>
      完全マネージド型の ClickHouse オブザーバビリティでは、ベータ期間中のデータ保持期間は 30 日間です。保持期間は一般提供 (GA) の時点で変更される予定であり、詳細な手順は追ってお知らせします。
    </Note>

    この 30 日間の保持期間と Elastic 側の保持期間を踏まえて、移行計画を立ててください。履歴データの検索が不要になるまでは、Elastic を引き続き利用できる状態にしておいてください。
  </Tab>

  <Tab title="セルフマネージド">
    ClickHouse では、`MergeTree` テーブルの [有効期限 (TTL)句](/ja/clickstack/self-configured/managing/production#configure-ttl-managed) によって、期限切れのデータを自動的に削除します。

    テーブルの保持期間は、移行要件に合わせて設定してください。例については、[セルフマネージドの本番環境における 有効期限 (TTL) 設定](/ja/clickstack/self-configured/managing/production#configure-ttl-managed) を参照してください。
  </Tab>
</Tabs>

## データの移行 {#migrating-data-self-configured}

<Tabs>
  <Tab title="完全マネージド型">
    <BetaBadge label="ベータ版" />

    <Note>
      現在、Elasticsearch から完全マネージド型の ClickHouse オブザーバビリティへ履歴データを直接移行する手段はありません。マネージドエンドポイントが受け付けるのは OTLP テレメトリーのみで、Elasticsearch のドキュメントや JSON エクスポートは受け付けません。セルフマネージドのタブで説明している `Elasticsearch` テーブルエンジンを使用するワークフローは、完全マネージド型のサービスには適用できません。
    </Note>

    並行インジェストを利用し、履歴データは Elastic に保持したまま、新しいテレメトリーを **OTLP フォーマット** でマネージドサービスに送信してください。マネージドエンドポイントと認証の設定については [OpenTelemetry によるデータの取り込み](/ja/clickstack/observability/ingesting-data/opentelemetry) を、収集方法の選択肢については [エージェントの移行](/ja/clickstack/observability/migration/elastic/migrating-agents) を参照してください。

    履歴データのインポートが必要な場合は、Elasticsearch のドキュメントを適切な OpenTelemetry のログ、トレース、またはメトリクスに変換し、OTLP 経由でエクスポートするカスタムパイプラインを用意する必要があります。本ガイドでは既製のコンバーターは提供していません。バックフィルを計画する際は、事前にマネージドサービスの保持期間を考慮してください。
  </Tab>

  <Tab title="セルフマネージド">
    [`Elasticsearch` テーブルエンジン](/ja/reference/engines/table-engines/integrations/elasticsearch)を使用して Elasticsearch からドキュメントを直接読み取り、`INSERT INTO ... SELECT` でローカルの ClickHouse テーブルにコピーします。エクスポートファイルや `elasticdump` のインストールは不要です。

    このエンジンは読み取り専用です。`Elasticsearch` テーブルを作成すると、リモートのドキュメントをクエリできるようになりますが、ClickHouse のストレージにはコピーされません。

    <Note>
      Elasticsearch インテグレーションは実験的機能であり、対応する ClickHouse バージョンで `enable_elasticsearch = 1` を設定する必要があります。Elasticsearch 7.12 以降が必要で、OpenSearch には対応していません。ClickHouse サービスから Elasticsearch のエンドポイントに接続できる必要があります。また、ドキュメントの内容を読み取るには、インデックスで `_source` が有効になっている必要があります。
    </Note>

    <Steps>
      <Step title="Elasticsearch インデックスに接続する" id="connect-elasticsearch-self-managed">
        セルフマネージドの ClickHouse Cloud サービスで次の SQL を実行します。エンドポイント、インデックス、認証情報はご自身の値に置き換えてください。

        ```sql
        SET enable_elasticsearch = 1;

        CREATE TABLE elasticsearch_source
        ENGINE = Elasticsearch(
            'https://<elasticsearch-host>:9200',
            '<index-name>',
            '<username>',
            '<password>'
        );

        SELECT _index, _id, document
        FROM elasticsearch_source
        LIMIT 10;
        ```

        このテーブルでは、各ドキュメントの `_source` が `JSON` 型の `document` カラムとして公開されます。仮想カラム `_id` と `_index` により、元のドキュメントとインデックスを識別できます。宛先のスキーマを決める前に、サンプルデータを確認してください。

        このエンジンは API キーと名前付きコレクションにも対応しています。詳細は[認証リファレンス](/ja/reference/functions/table-functions/elasticsearch#authentication)を参照してください。
      </Step>

      <Step title="ドキュメントを ClickHouse にコピーする" id="copy-documents-self-managed">
        この例では、ドキュメントを `JSON` としてステージングテーブルに保存します。これにより、オブザーバビリティのログソースを設定する前に内容を確認・変換できます。`elasticsearch_source` と同じデータベースで次のステートメントを実行してください。

        ```sql
        CREATE TABLE migrated_elasticsearch_documents
        (
            source_index String,
            document_id String,
            document JSON
        )
        ENGINE = MergeTree
        ORDER BY (source_index, document_id);

        INSERT INTO migrated_elasticsearch_documents
        SELECT _index, _id, document
        FROM elasticsearch_source;
        ```

        各読み取りでは Elasticsearch の point in time を使用するため、そのクエリでは一貫したスナップショットが得られます。これは一度限りのコピーであり、継続的なレプリケーションではありません。挿入を再実行すると行が重複して追加されます。ソートキーによるドキュメントの重複排除は行われません。

        大規模なインポートでは、エンジンの `query` 引数を使用して、範囲が重複しないバッチに分割してください。その際、Elasticsearch Query DSL で絶対的なタイムスタンプの境界を指定します。ClickHouse の `WHERE` 句ではフィルターが Elasticsearch にプッシュダウンされません。詳細は[エンジンの例](/ja/reference/engines/table-engines/integrations/elasticsearch#usage-example)と[制限事項](/ja/reference/functions/table-functions/elasticsearch#limitations)を参照してください。
      </Step>

      <Step title="インポートしたデータをマッピングして検証する" id="validate-import-self-managed">
        ドキュメント数と代表的なレコードを、元のスナップショットと比較します。検索やダッシュボードでデータを使用する前に、タイムスタンプ、欠落しているフィールド、ネストされた値を確認してください。`JSON` 型はタイムスタンプを含め値から型を推論する場合があるため、テキスト表現が変わることがあります。フィールドの型を制御したい場合は、JSON の型ヒントを明示的に指定してください。

        クエリと保持期間の要件に合わせて宛先のオブザーバビリティスキーマを設計し、`INSERT INTO ... SELECT` を使用してステージングテーブルからフィールドを抽出・変換します。[Elasticsearch と ClickHouse の概念](/ja/clickstack/self-configured/migration/elastic/concepts)、[型マッピング](/ja/clickstack/self-configured/migration/elastic/types)、[スキーマ設計ガイド](/ja/guides/clickhouse/data-formats/json/schema)もあわせて参照してください。

        ドキュメントをコピーしても、OpenTelemetry スキーマへの自動変換や UI でのログソースの設定は行われません。[設定オプション](/ja/clickstack/self-configured/managing/config)を参照し、テーブルと、タイムスタンプ、メッセージなどのフィールドのマッピングを設定してください。
      </Step>
    </Steps>
  </Tab>
</Tabs>
