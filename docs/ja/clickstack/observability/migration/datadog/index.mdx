既存の Datadog エージェントから ClickHouse オブザーバビリティへ、ログ、トレース、メトリクスを送信できます。アプリケーション側では、引き続き Datadog SDK をそのまま使用できます。マネージドエンドポイントを選択するか、独自の collector で Datadogレシーバーを設定したうえで、以下の共通のエージェント設定手順を実行してください。

## 前提条件 {#prerequisites}

* マネージドまたはセルフマネージドの ClickHouse オブザーバビリティサービス。
* 移行したいシグナルを収集している、稼働中の Datadog エージェント。トレースを移行する場合は、アプリケーションが Datadog SDK を介して、すでにそのエージェントへトレースを送信している必要があります。
* エージェントから Datadogレシーバーのエンドポイントへのネットワークアクセス。

## 宛先を設定する {#connection-details}

<Tabs>
  <Tab title="フルマネージド">
    <BetaBadge label="ベータ版" />

    サービスを開き、**Team Settings → Data → Managed Telemetry** に移動します。**OTLP HTTP endpoint** と **APIキー** をコピーします。

    <div className="ch-image-lg">
      <Frame>
        ![マスクされた OTLP HTTP エンドポイントと APIキーが表示された Managed Telemetry](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Datadog エンドポイントは、同じホスト名でポート `8126` を使用します。追加の collector は不要です。以下の エージェント 設定では、次の値を使用してください。

    | 設定                       | 値                             |
    | ------------------------ | ----------------------------- |
    | `YOUR_API_KEY`           | サービスの取り込み用APIキー               |
    | `YOUR_DATADOG_URL`       | `https://YOUR_OTEL_HOST:8126` |
    | `YOUR_DATADOG_HOST_PORT` | `YOUR_OTEL_HOST:8126`         |
    | `logs_no_ssl`            | `false`                       |
  </Tab>

  <Tab title="セルフマネージド" id="self-managed">
    [ClickStack OpenTelemetryコレクター](/ja/clickstack/self-configured/ingesting-data/collector)には [Datadogレシーバー](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/datadogreceiver)が含まれています。この receiver を設定し、ログ、トレース、メトリクスの各パイプラインに接続します。

    次の設定オーバーレイを `datadog-collector.yaml` として保存します。この設定により、OTLP receiver はそのままに、collector の既存のログ、トレース、メトリクスの各パイプラインに Datadogレシーバーが追加されます。

    ```yaml
    receivers:
      datadog:
        endpoint: 0.0.0.0:8126

    service:
      pipelines:
        logs/in:
          receivers: [otlp/hyperdx, datadog]
        traces:
          receivers: [otlp/hyperdx, datadog]
        metrics:
          receivers: [otlp/hyperdx, datadog]
    ```

    ClickHouse の接続情報を設定し、collector を起動します。通常の起動処理では、`HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE` で指定したデータベースにテレメトリースキーマが作成されるため、ClickHouse ユーザーにはデータベースとテーブルを作成する権限が必要です。既存のテレメトリーデータベースがある場合は、そのデータベース名を指定してください。

    この例では Docker が必要です。collector バージョン `2.40.0` を使用し、Datadogレシーバーはローカルホストでのみ公開します。

    ```shell
    export CLICKHOUSE_ENDPOINT='https://YOUR_CLICKHOUSE_HOST:8443'
    export CLICKHOUSE_USER='YOUR_CLICKHOUSE_USER'
    export CLICKHOUSE_PASSWORD='YOUR_CLICKHOUSE_PASSWORD'
    export HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE='default'

    docker run --rm --name datadog-collector \
      -e CLICKHOUSE_ENDPOINT \
      -e CLICKHOUSE_USER \
      -e CLICKHOUSE_PASSWORD \
      -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE \
      -e CUSTOM_OTELCOL_CONFIG_FILE=/etc/datadog-collector.yaml \
      -v "$(pwd)/datadog-collector.yaml:/etc/datadog-collector.yaml:ro" \
      -p 127.0.0.1:18126:8126 \
      clickhouse/clickstack-otel-collector:2.40.0
    ```

    エージェント の設定と動作確認が終わるまで、この端末で collector を実行したままにしておきます。以降のコマンドは別の端末で実行してください。

    同じホスト上で実行する エージェント には、次の値を使用します。

    | 設定                       | 値                                                    |
    | ------------------------ | ---------------------------------------------------- |
    | `YOUR_API_KEY`           | `local-test` などの空でない任意の文字列。このローカル receiver では検証されません |
    | `YOUR_DATADOG_URL`       | `http://localhost:18126`                             |
    | `YOUR_DATADOG_HOST_PORT` | `localhost:18126`                                    |
    | `logs_no_ssl`            | `true`                                               |

    ホストポートに `18126` を使用することで、この宛先を、ポート `8126` で待ち受ける エージェント のアプリケーショントレース用リスナーと分離できます。コンテナ化された エージェント の場合は、両方のコンテナを同じ Docker ネットワークに接続し、宛先の値として `http://datadog-collector:8126` と `datadog-collector:8126` を使用してください。

    この例では、ローカルホストに限定した認証なしの HTTP リスナーを使用しています。他のホスト上の エージェント から送信する場合は、receiver を公開する前に保護されたネットワーク経路を用意し、イングレスで TLS と認証を設定してください。なお、`OTLP_AUTH_TOKEN` は collector の OTLP 認証を設定するものであり、この Datadog リスナーを保護するものではありません。
  </Tab>
</Tabs>

## Datadog エージェントを設定する {#configure-datadog-agent}

エージェントの [`datadog.yaml` 設定ファイル](https://docs.datadoghq.com/agent/configuration/agent-configuration-files/)を更新します。一般的な配置場所は、Linux では `/etc/datadog-agent/datadog.yaml`、macOS では `/opt/datadog-agent/etc/datadog.yaml` です。

上のタブに表示されている宛先の値を使って、次の設定を既存の設定にマージします。

```yaml
api_key: "YOUR_API_KEY"

# Metrics destination
dd_url: "YOUR_DATADOG_URL"

# Use the v2 metrics intake.
use_v3_api:
  series:
    enabled: false

# Trace destination
apm_config:
  enabled: true
  apm_dd_url: "YOUR_DATADOG_URL"
  features:
    - disable-convert-traces

# Log destination
logs_enabled: true
logs_config:
  logs_dd_url: "YOUR_DATADOG_HOST_PORT"
  force_use_http: true
  logs_no_ssl: false # Set to true for the local HTTP receiver.

remote_updates: false
remote_configuration:
  enabled: false
```

`YOUR_DATADOG_URL` を宛先の完全な URL に、`YOUR_DATADOG_HOST_PORT` をスキームを含まない `hostname:port` 形式の値に置き換えてください。`logs_no_ssl` には、宛先に対して指定された値を設定します。

<Note>
  `disable-convert-traces` を指定すると、エージェント のトレースペイロードが Datadogレシーバーと互換性のある形式に保たれます。Datadog エージェント 7.85.2 と collector core 0.155.0 の組み合わせでは、エージェント のデフォルトのインデックス付きペイロードが HTTP 200 で受け付けられたにもかかわらず、スパンが生成されませんでした。トレースの転送には上記の設定を使用し、既存の `apm_config.features` リスト内のその他のエントリはそのまま残してください。
</Note>

既存のログ収集インテグレーションおよびアプリケーションのトレーシング設定は、そのまま維持してください。これらの設定は エージェント がテレメトリーを送信する宛先を変更するだけであり、個々のアプリケーションのログ収集を有効化したり、インストルメンテーションを追加したりするものではありません。[環境変数](https://docs.datadoghq.com/agent/guide/environment-variables/)で エージェント を設定している場合は、`DD_API_KEY` を含め、対応する設定もそちらで更新してください。

この設定により、エージェント のログ、トレース、メトリクスの送信先が Datadog から ClickHouse オブザーバビリティに切り替わります。事前に検証したい場合は、デプロイメント全体を更新する前に、まずテスト用の エージェント に適用してください。

## 再起動と確認 {#restart-and-verify}

設定を反映させるため、エージェントを再起動します。Linux の場合:

```shell
sudo systemctl restart datadog-agent
sudo datadog-agent status
```

MacOS の場合:

```shell
sudo launchctl kickstart -k system/com.datadoghq.agent
```

コンテナ化された エージェント の場合は、設定を更新してからコンテナを再デプロイしてください。

アプリケーションで新たなアクティビティを発生させてから ClickHouse オブザーバビリティを開き、直近の時間範囲を選択します。

* **ログ:** ログソースを選択し、アプリケーションの `ServiceName` でフィルタします。
* **トレース:** トレースソースを選択し、アプリケーションの `ServiceName` でフィルタします。
* **メトリクス:** アプリケーションまたは エージェント が送信するメトリクスを検索します。DogStatsD でテストする場合は、名前を付けた Gauge を送信し、その値を確認します。

データが表示されない場合は、エージェント のステータスで配信エラーが発生していないか確認してください。ホスト名、ポート、APIキー、およびサービスのネットワークアクセス設定を確認します。また、エージェント が対象のシグナルを収集していること、環境変数によるオーバーライドが同じ宛先を指していることも確認してください。

トレースについては、エージェント の配信成功カウンターだけで判断せず、既知のトレースIDで確認してください。サービスのフィルタによってトレースが表示されない場合は、`TraceId` で検索します。receiver は、トレーサーのベースサービスをリソースのサービス名として使用しつつ、スパン単位のサービスのオーバーライドを `service.name` スパン属性に保持する場合があります。ベースサービス名を明示するには、アプリケーションのトレーシング設定で `DD_SERVICE` を設定してください。

## サポートされるシグナル {#supported-signals}

Datadogレシーバーは実験的な機能です。Datadog のログ、トレース、およびサポート対象のメトリクスを、ClickHouse オブザーバビリティで使用される OpenTelemetry データモデルに変換します。上記の設定では v2 メトリクスインテークを選択しています。その他の Datadog バックエンドの機能は、この移行フローの対象外です。

既存の Datadog インストルメンテーションはそのまま維持しつつ、アプリケーションを段階的に OpenTelemetry へ移行できます。

セルフマネージドの ClickStack コレクターを使用する場合、アプリケーションから DogStatsD のカスタムメトリクスを collector に直接送信することもできます。また、collector ではトレースからリクエスト数、エラー数、所要時間のメトリクスを導出できます。詳しくは [StatsD メトリクスの受信](/ja/clickstack/self-configured/ingesting-data/collector#statsd-receiver) および [スパンからのメトリクスの導出](/ja/clickstack/self-configured/ingesting-data/collector#span-metrics) を参照してください。
