## PromQL と Lucene におけるダッシュボード変数 {#dashboard-variables-in-promql-and-lucene}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/q5pP20p4nY4" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

ダッシュボード変数が PromQL チャートで利用できるようになりました。変数参照の自動補完に対応したほか、存在しない変数や、マクロ、引用符が必要な参照といった非サポートの使い方に対しては警告が表示されます。既存の生成された SQL パネルの横には、生成された PromQL のプレビューが表示され、現在の選択内容を代入したクエリを確認できます。

Lucene 変数で完全一致がサポートされました。これまでは、`ServiceName:$service` は `ServiceName:("add" OR "cart")` に展開されていました。引用符で囲まれていない Lucene のフィールド一致は部分文字列一致となるため、これは `ServiceName ILIKE '%add%' OR ServiceName ILIKE '%cart%'` になります。そのため、2 つのサービスを選択したのに 4 つのサービスが返されることがありました。

今後は、変数を `ServiceName:"$service"` のように引用符で囲むと `(ServiceName:"add" OR ServiceName:"cart")` に展開され、選択した各値に完全一致します。これは、変数を使わない引用符付きフィールド一致の既存の動作と同じです。自動補完でも引用符付きの形式が候補として表示されます。

チャートのツールチップやテーブル行から検索ページへドリルダウンする際、遷移前に変数とマクロが展開されるようになりました。検索ページは変数を解釈できないため、これまでは `$service` がそのまま渡され、誤った結果やクエリエラーの原因となっていました。選択のないマクロは `(1=1)` に展開されます。検索ページの `WHERE` 入力欄での見た目はやや不格好になりますが、クエリの有効性は保たれます。

フィルタの選択内容は、expression ではなく変数名をキーとして保持されるようになりました。そのため、異なるソースの `ServiceName` のように同じ expression を使う 2 つのフィルタが、選択内容を共有することはなくなりました。

Brandon の提案を受け、フィルタの編集中に Escape キーを押すと、変更を破棄する前に確認が表示されるようになりました。これまでは、ツールチップを閉じようとしただけで編集内容がすべて失われることがありました。

ダッシュボード変数は今週、本番環境にリリースされました。機能トグルは削除され、参照形式とマクロについては[公開ドキュメント](https://clickhouse.com/docs/clickstack/features/dashboards/overview#dashboard-variables)で説明しています。

## スパンリンクの双方向表示 {#span-links-in-both-directions}

*デモ担当者: [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/tdK9JU6unoE" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

スパンリンクは以前から表示できましたが、コンシューマー側からしか確認できませんでした。各リンクは「Open trace」アクションとして表示されるだけで、プロデューサーのスパンを起点に、そのスパンへリンクしているスパンを探すことはできませんでした。この機能は GitHub のイシューでユーザーから要望されていたものです。

Span Links セクションに、各リンク先スパンの名前、サービス、所要時間、タイムスタンプが表示されるようになりました。リンクが複数ある場合でも、1 つずつ開かずにどれを選ぶか判断しやすくなります。リンク先のスパンが見つからない場合は、従来どおり「Open trace」がフォールバックとして使用されます。

新たに追加された「Linked from」セクションには、現在のスパンにリンクしているスパンが一覧表示されます。これにより、コンシューマーのリンクをたどってプロデューサーに移動し、そこにそのコンシューマーが表示されていることを確認できるようになりました。

パンくずリストで直前のスパンへのリンクをたどると、そのエントリに戻ります。そのため、リンクされた 2 つのスパン間を行き来しても、重複したエントリが増え続けることはありません。両者の間に他のエントリがある場合は、通常どおり新しいエントリが追加されます。

逆方向のルックアップでは、スパンリンクに選択したスパン ID を含む行を検索したうえで、トレースIDが一致するかをチェックします。トレースIDのルックアップではそのカラムのブルームフィルター索引を活用できますが、逆方向のルックアップではスキャンが必要になるため、デモ環境よりも大きなトレーステーブルでは遅くなる可能性があります。これが問題になる場合は、コード内のコメントにあるとおり、リンク先スパン ID に索引を追加することで対応できます。

## すぐに使える LLM オブザーバビリティ {#llm-observability-out-of-the-box}

*デモ担当者: [@wrn14897](https://github.com/wrn14897)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/m49DZ5cuI64" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

すでに多くのチームが LLM やコーディングエージェントのテレメトリーを ClickStack に送信していますが、これまでは専用のサポートがなく、チャットのレンダリング、トークンやコストの追跡、モデル分析といった機能はありませんでした。

既存の ClickHouse、Kubernetes、サービスのプリセットに加えて、LLM ダッシュボードが新たに追加されました。トークン使用量、コスト、モデル呼び出し、ツール呼び出し、キャッシュヒット、応答時間を確認でき、ユーザー属性がある場合はユーザー別の内訳も表示されます。

このダッシュボードは、既存のトレースとログをクエリ実行時に読み取るため、固定のスキーマや専用のテーブル、取り込み時の処理は必要ありません。一般的な規約、OpenLLMetry、OpenInference に準拠したテレメトリーに対応しており、OpenAI および Anthropic の SDK、Vercel AI SDK、LangChain、Claude Code、opencode からのデータも利用できます。収集済みのテレメトリーにもそのまま適用できます。

レイテンシビューでは AI 関連のスパンが上位に表示されるため、トレース全体をたどらなくても、遅いモデル呼び出しを簡単に見つけられます。

セッションビューでは、スパンを会話単位でグループ化して表示します。セッションを開くとそのスパンが表示され、スパンを選択すると詳細を確認できます (プロンプトが記録されていればプロンプトも含まれます) 。エージェントの実行をデバッグする際に便利で、同じセッションフィルタでログを検索することもできます。

対象範囲は、評価機能をはじめ幅広い機能を備えた Langfuse などの専用 LLM オブザーバビリティツールと比べて、意図的に絞り込んでいます。ClickStack に取り込み済みのテレメトリーを活用し、エラー率、コスト、トークン、レイテンシといった一般的な監視ニーズに対応します。

**関連 プルリクエスト:** [#2990](https://github.com/hyperdxio/hyperdx/pull/2990) LLM オブザーバビリティダッシュボード、スパンのチャットビュー、セッション

## チャートエディターでのメトリクスの閲覧 {#browsing-metrics-in-the-chart-editor}

*デモ担当者: [@MikeShi42](https://github.com/MikeShi42)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/TkFa6Zzq23o" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

これまでメトリクスを選ぶには、種類ごとに最大 3,000 件の名前が並ぶフラットなリストから探す必要がありました。探しているものがおおよそ分かっていれば自動補完が役立ちますが、一覧から閲覧したいという要望がフィードバックで何度も寄せられていました。

メトリクス選択欄の横にある「Browse metrics」コントロールから、エクスプローラーを開けるようになりました。左側にカタログ、右側に選択したメトリクスの詳細が表示されます。メトリクス名はドットとアンダースコアで分割され、ツリー構造で表示されます。子が 1 つしかないセグメントは、余計なクリックを省くためにまとめて折りたたまれます。`Metric`、`Type`、`Unit` のカラムはどの階層でも揃って表示されます。カタログ全体を検索することも、フラットなリスト表示に切り替えることもできます。

以前は、単位、説明、タグはメトリクスを選択した後に、系列の行の下にある折りたたまれたパネルでしか確認できませんでした。詳細ペインを使えば選択前にこれらを確認できるため、デプロイメントがどのメトリクスを出力しているか、どのタグでグループ化できるかを把握できます。「Use metric」をクリックすると、編集中の系列に選択したメトリクスが適用されます。

この機能は動作が安定するまでの間、目立たない場所に配置されています。

## Grafana の生の SQL クエリにおけるログボリューム {#log-volume-for-raw-sql-queries-in-grafana}

*デモ担当者: [@SpencerTorres](https://github.com/SpencerTorres)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/uehh44q56yE" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

見た目上は小さな変更ですが、想定以上に手間のかかる作業でした。

Grafana では、クエリビルダーで作成したログクエリの場合、使用すべきカラムをプラグインが把握しているため、結果の上部にボリュームのヒストグラムが表示されます。一方、同じクエリを SQL エディタで実行した場合は、どのカラムを選択したかをプラグインが判別できないため、ヒストグラムは表示されませんでした。また、探索では代わりに Grafana の行ベースのヒストグラムが表示されていましたが、これはクエリの `LIMIT` で件数が制限され、選択した時間範囲にも追従していませんでした。

現在は、プラグインが末尾の `ORDER BY` と `LIMIT` を取り除き、SQL を派生テーブルとしてラップしたうえで、時間範囲全体で集約するようになりました。ここで `LIMIT` を除去することが重要です。残したままにすると、件数が元のクエリで返される行に限定されてしまいます。

ヒストグラムには SQL のフィルタが反映され、時間範囲を変更すると更新されます。自分で記述した SQL だけでなく、クエリビルダーの「Edit as SQL」から開いたクエリでも動作します。

クエリの書き換えがうまく機能しないエッジケースは、まだ残っている可能性があります。

**関連するプルリクエスト:** [grafana/clickhouse-datasource#2141](https://github.com/grafana/clickhouse-datasource/pull/2141) SQL エディタのクエリでログボリュームを表示 (オープン)

## アラートページの通知チャネル {#notification-channels-on-the-alerts-pages}

*デモ担当者: [@jordan-simonovski](https://github.com/jordan-simonovski)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Gr-QkVVWam8" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

1 つのアラートから最大 10 個の Webhook に通知できますが、アラート一覧と詳細ヘッダーには最初の 1 つしか表示されず、しかもその名前ではなく「Webhook」というラベルで表示されていました。どちらもレガシーな単一チャネル用のフィールドを読み取ったままだったためです。

複数の通知先へのディスパッチ自体は機能していましたが、表示上は追加したチャネルが保存されていないように見えていました。

一覧と詳細ヘッダーには、設定済みのすべてのチャネルが名前で表示されるようになりました。Webhook や incident.io インテグレーションを含め、チャネルの追加と削除も簡単になりました。また、通知時刻が通知先ごとに記録されるため、遅延しているインテグレーションを特定できます。

設定済みのチャネルには直接通知されるようになりました。以前は Webhook メンションに変換されてメッセージ本文に追記されていたため、通知が欠落することがありました。本文にアドホックなメンションがイベントごとの上限に達するほど含まれていると、アラートに設定済みのチャネルがスキップされていたのです。

コントロールが増えてページが煩雑になってきたため、エクスポートや Terraform などの行アクションを 1 つのメニューにまとめました。

## 数万件のアラートのレンダリング {#rendering-1000s-alerts}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/P9BPD9yoElo" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

アラートの評価は 16,000 件のアラートを同時実行する条件でテスト済みで、安定して動作します。一方、これほど多くのアラートがある状態でアラートページを開くと、ページがクラッシュしていました。

現在は一覧が仮想化され、16,000 件のアラートをレンダリングできるようになりました。ただし、すべてのアラートを取得してからクライアント側でフィルタリングしているため、読み込みには依然として時間がかかります。この問題を解消するため、ページネーションの実装を進めています。

今回の変更には、MongoDB に大量のアラートを seed したり、それらをクリーンアップしたりするためのスクリプトも含まれており、この規模でのページの動作をローカル環境で手軽にテストできます。

## APIキーを表示操作の背後に隠す {#hiding-api-keys-behind-a-reveal}

*デモ担当者: [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/MNXABmTVEkE" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

これまで、認証情報はアプリ内の各所で平文のまま表示されていました。チーム設定ではインジェスト API key がすべて表示され、MCP のインストールスニペットではコマンド内に個人アクセスキーがそのまま含まれていました。いずれも、画面共有中やスクリーンショットで容易に漏洩するおそれがありました。

現在、キーはデフォルトでマスクされ、必要なときだけ表示できる操作が用意されています。インジェストキー、個人アクセスキー、MCP インストールスニペット (コミュニティから提供されたものを含む) では、共通のコンポーネントでこの処理を行います。

コピー時には引き続き実際の値がコピーされるため、キーを表示しなくてもコピーできます。同様の変更は、ClickStack Cloud のオンボーディングにも近日中に適用される予定です。

**関連 プルリクエスト:** [#2988](https://github.com/hyperdxio/hyperdx/pull/2988) 共通の RevealSnippet を使用して、APIキーおよび MCP インストールスニペット内のシークレットをマスク

## 製品内のリリースノート {#release-notes-in-the-product}

*デモ担当者: [@jordan-simonovski](https://github.com/jordan-simonovski)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/4vrzXy8JwZY" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Help メニューの「What&#39;s new」パネルは、これまで PR ごとの changeset を参照し、`feat:` プレフィックスの付いたエントリを抽出していました。そのため v2.36.0 では、ダッシュボード変数が 3 回も掲載される一方で、このリリースの主な変更点である数式やアラート関連の改修が抜け落ちていました。

現在は、リリースPRの一部として作成・レビューされるルートの `CHANGELOG.md` を読み取るようになりました。また、パネル内の各リリースの見出しはリリースジェネレーターが生成します。見出しの下には破壊的変更、新機能、バグ修正、改善が並び、変更ログへのリンクも用意されています。

未読のリリースノートがあると、Help ボタンがきらめくようになりました。このアニメーションは JavaScript を使わず、SVG で実装されています。

未読状態の追跡にも修正が必要でした。以前はアプリのビルドバージョンを基準にしていたため、git の短縮 SHA や CI のビルド番号を含むデプロイメントでは、新しいリリースがなくてもデプロイのたびにきらめきが表示されていました。現在は変更ログ内の最新のリリースバージョンを基準にしています。

リリースノートのフォーマットも見直しが進んでいるため、今後はより多くの内容がパネルに表示される予定です。
