## 指数ヒストグラムメトリクス {#exponential-histogram-metrics}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/w45v3IMcXTY" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

OpenTelemetry の指数ヒストグラムメトリクスに対するクエリの初期サポートが追加されました。これまでもこれらのメトリクスをログソースに登録することはできましたが、クエリする手段はありませんでした。今回から、クエリビルダーで出現回数と分位点を利用できるようになりました。

指数ヒストグラムは明示的バケットヒストグラムと似ていますが、バケットの上限と下限はバケットごとに保存されるのではなく、2 のべき乗から算出されます。どの 2 のべき乗を使用するかは scale によって決まります。scale が大きいほどバケットは細かくなり、オフセットは境界をより大きい倍数またはより小さい倍数の方向へシフトします。各バケット数には、その範囲内に収まる観測値の数が記録されます。

max、min、sum、avg は、既存の明示的ヒストグラムの実装と同様に引き続き非サポートです。これらのフィールドは OpenTelemetry のデータモデルでは任意であるため、存在することを前提としていません。

デモのとおり、生成された SQL は長く、お世辞にも見やすいとは言えません。パフォーマンスは許容範囲内で、メモリ不足に陥ることもありませんが、現時点ではあくまで機能面の初期サポートにとどまります。次はパフォーマンスの改善に取り組む予定で、これらのクエリを大幅に高速化する新しいスキーマの開発もすでに進んでいます。

現時点で正しくレンダリングされる表示形式は時系列のみです。これは既存のヒストグラムメトリクス型と同じ挙動です。

## 生のSQLチャートの検証 {#validation-for-raw-sql-charts}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/zfZsehTqeCQ" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

生のSQLチャートで、必要なマクロが欠けている場合に警告が表示されるようになりました。この機能は、大量の生のSQLチャートを作成していたユーザーが、原因の分かりにくい結果に何度も悩まされたというサポートケースをきっかけに実装されました。

ダッシュボードのクエリには、フィルタマクロとソーステーブルマクロを含める必要があります。時系列チャートの場合は、これに加えて時間範囲マクロと時間間隔マクロも必要です。これまで、これらのチェックはタイルにアラートがアタッチされた後にしか実行されませんでした。現在はすべての生のSQLチャートで実行されるため、マクロを削除すると、後になって不可解なチャートが表示されるのではなく、その場でエディタに警告が表示されます。

この検証では、各マクロの依存関係も考慮されます。生のSQLチャート自体には本来ログソースの選択は不要ですが、ソーステーブルマクロとフィルタマクロを使用するにはログソースの選択が必要です。そのため、ログソースを選択せずにいずれかのマクロを使用すると、警告ではなくエラーになります。

小さな変更ですが、サポートに問い合わせなくても、生のSQLの問題を見つけやすくなるはずです。

## ID ではなく名前でログソースにリンクする {#link-to-sources-by-name-not-id}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/r2uNmcJXGSM" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

LogHouse チームから、ログソースへのリンクをより安定させたいという要望がありました。同チームは ClickHouse Cloud のログ環境を運用しており、infrastructure-as-code を用いてプログラムでログソースをプロビジョニングしています。ログソース ID はログソースを再作成すると変わり、開発・ステージング・本番環境の間でも異なるため、ID に基づくリンクは壊れやすいものでした。同チームはアラートシステムや Grafana から ClickStack へリンクしているため、環境ごとに別々のログソース ID を管理するのは現実的ではありませんでした。

`source` URL パラメータで、ID に加えてログソース名も指定できるようになりました。名前はログソースのプロビジョニング時に制御できるため、同じリンクをすべての環境で利用できます。当初は検索ページのみが対応していましたが、後続の PR により、Chart Explorer、サービスマップ、セッション、サービスダッシュボード、Kubernetesダッシュボードなど、ログソースパラメータを持つすべてのページに対応が拡張されました。

その後の議論は、主にこの機能をいかに見つけてもらうかに集中しました。これは実質的に URL API であり、ユーザーが偶然見つけることはまずありません。デフォルトで ID の代わりに名前を使用する案もありますが、名前が重複する可能性があるため安全ではありません。ほかにも、共有ボタンからリンクを取得できるようにする、MCP を通じてエージェントにリンクを生成させる、URL API をきちんとドキュメント化する、といった提案がありました。相対的な時間範囲についても、同様にドキュメント化されると便利です。

名前ベースの参照は、ダッシュボードにも拡張できる可能性があります。そうなれば、infrastructure-as-code のワークフローでログソースのプロビジョニングやダッシュボードのインポートを行い、すべてを自動的に連携させられるようになります。UI からのダッシュボードのインポートでは、すでに名前でログソースが照合されるため、残る課題は主にプログラムによるワークフローです。

## 新しい探索ページ {#new-explore-page}

*デモ担当者: [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/E1vEjJBw1gs" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

これは、統合された探索ページに関する初期段階の試みです。将来的には、検索、保存済み検索、Chart Explorer を置き換え、単一のエントリーポイントに集約できる可能性があります。

ロールアウトの進め方は、トレースビューアの再設計から得た教訓を踏まえています。全ユーザーの体験を一度に変えるのではなく、新しいページはまず機能フラグで制御し、一部のユーザー向けに公開する予定です。その期間中に問題を洗い出して修正し、そのうえでより広く展開します。アイデアがうまくいかなければ、実験のまま終わり、リリースはしません。それもまったく問題のない結果です。

ページでは、まずシグナルタイプを選択します。トレース、ログ、メトリクスのいずれを選ぶかによって、以降の画面がそれに合わせて切り替わります。たとえばログを選択すると、リストビュー、イベントパターン、時系列のほか、現在 Chart Explorer で利用できるその他の可視化を使えます。

調査は、ページを切り替えることなく継続できるべきです。たとえば、リストから始めて数値表示やグループ化済みテーブルに切り替え、結果をダッシュボードに追加し、さらに細かく制御したい場合はカスタムクエリを記述する、といった流れです。

このほか、いくつかの小さなアイデアも盛り込まれており、その多くはユーザーからのフィードバックがきっかけです。クエリエディターは SQL エディタに近い動作になり、現在ある自動補完の挙動の違いが解消されます。また、エラーや警告はクエリの実行を待たず、編集中に表示されるようになります。

カラムには専用のピッカーが用意されます。`SELECT` 句を変更するとテーブルに表示されるカラムが変わることに気付かなかったユーザーが、少なくとも 1 人いました。ピッカーでフィールドをクリックすると SQL が更新され、そのフィールドで並べ替えることもできます。上級ユーザーは引き続き `SELECT` 句を利用できます。

保存済みビューもこのページに統合されるため、保存せずに探索を進め、その後で現在のビューをその場で保存できます。生成された SQL はインラインで表示されます。

現在 Chart Explorer で利用できる可視化の一部をはじめ、まだ実装されていない部分も少なくありません。これらの追加に伴い、デザインも引き続き変わっていきます。

## ダッシュボードフィルタの関連付け {#dashboard-filter-linking}

*デモ担当者: [@teeohhem](https://github.com/teeohhem)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/IQ4WtnNYS5s" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

ダッシュボードフィルタの関連付け機能がマージされました。数か月前にドラフト段階で初めてデモを行った後、パフォーマンスへの影響を検討するためにいったん保留していました。関連付けを使うとダッシュボードクエリの形が変わり、materialized view を常に最適に活用できるとは限りません。そのため、デフォルトでは無効とし、オプトイン方式のトグルとしてリリースされます。

関連付けを有効にすると、あるフィルタで値を選択した際に、他のフィルタで選択できる値が絞り込まれます。たとえばサービスを選択すると、そのサービスで見つかった severity の値だけが残ります。トレースIDを選択すると、関連する親トレースIDだけが残ります。これにより、データが返らない組み合わせをユーザーが選択してしまうことを防げます。

後続の PR では、関連付けがログソースを考慮するようになりました。フィルタはログソースごとにグループ化され、互いに絞り込める隣接フィルタの間にはチェーンアイコンが表示されます。ログフィルタとトレースフィルタが2つずつあるダッシュボードでも、どのフィルタが相互に作用するかがひと目でわかります。

もともとのユースケースは Kubernetesダッシュボードでした。ポッドを選択すると、そのポッドを含むデプロイメントとノードだけが残るようにする必要があります。絞り込まれた値はドロップダウンを開いた時点で遅延フェッチされるため、追加のルックアップにかかるコストを抑えられます。

議論では、未解決の課題が2つ残りました。1つは設定の保存先です。現在、この設定はユーザーごとにブラウザストレージに保存されています。打ち合わせでは、いずれダッシュボード単位で保存したいという要望が出るだろうという見方が示されました。その場合、ユーザー単位の設定は一時的なものにとどめ、将来ダッシュボード単位の動作と競合しないようにする方がよいかもしれません。

もう1つの課題は、依存するフィルタが値を読み込んでいる間の動作です。現在は値を選択すると、依存するドロップダウンをブロックせず、その中に読み込み中の状態を表示します。ただし、依存フィルタが2つ目にある場合の動作はまだ検証が必要です。方針としては、絞り込みの処理中もフィルタを操作できる状態を保ちつつ、リストの更新が完了していないことを示すのが望ましいとされました。目的の値がすでにわかっているユーザーを、メタデータの取得で待たせるべきではないためです。

## 最後に開いたサイドパネルのタブを記憶 {#remember-the-last-side-panel-tab}

*デモ担当者: [@MikeShi42](https://github.com/MikeShi42)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/FlDWN7sGHMo" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

今週最も小さな PR ですが、地味ながら解消する価値のある不便さを修正した好例でもあります。

行のサイドパネルはこれまで常に「概要」タブで開いていましたが、このタブは OpenTelemetry のログフィールドを前提に設計されています。そのため、OTel 形式ではないログでは、有用な情報がほとんど表示されません。結果として、行を開くたびに「カラム値」タブへ切り替える必要がありました。

今回の変更により、パネルは最後に使用したタブを記憶し、次回もそのタブで開くようになりました。設定は一切不要です。OTel 以外のログを扱うユーザーは一度「カラム値」に切り替えればそのまま使い続けられ、「概要」を使っているユーザーにはこれまでどおりの動作が維持されます。
