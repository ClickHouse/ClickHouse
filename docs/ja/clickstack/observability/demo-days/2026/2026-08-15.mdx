## ダッシュボード変数 {#dashboard-variables}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/gY2Kej-EYx4" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

今週の主な変更点はダッシュボード変数です。ダッシュボード変数は、ダッシュボードで既に使われているフィルタの仕組みを基盤としており、既存のフィルタでも新規のフィルタでも、変数として利用可能にできます。

変数には、デフォルトでフィルタの表示名が使われます。表示名に特殊文字が含まれている場合や、2 つのフィルタの表示名が重複している場合は、カスタム変数名を割り当てられます。カスタム名は、後からフィルタの名前を変更しても変わりません。参照時に指定すべき名前は設定ページに表示され、変数を有効にすると、フィルタのツールチップにも表示されます。

生のSQLチャートでは、変数をいくつかの方法で使用できます。`$__filter($var)` は、1 つの変数の現在の選択範囲を展開します。これは、すべてのフィルタを展開する既存の `$__filters` マクロを、単一の変数向けにしたものです。

さらに注目すべき追加機能が `$__conditionalAll(condition, $var)` です。第 1 引数に条件、第 2 引数に変数を指定します。変数で値が選択されている場合は、その条件がクエリに含まれます。何も選択されていない場合は expression 全体が `1 = 1` となり、フィルタリングには影響しません。

これにより、異なるソース間のマッピングが可能になります。たとえば、ダッシュボードでトレースのステータスコードを `error` または `info` にマッピングすれば、ログテーブルに対して定義した重大度フィルタでトレーステーブルを絞り込めます。ダッシュボードレベルで `error` を選択すると、トレースクエリはエラーステータスで絞り込まれます。

自動補完では、利用可能なすべての変数と、各変数がサポートするフォーマットが候補として表示されます。Brandon の提案を受けて、現在の選択範囲に基づく実際の展開結果もインラインで表示されるようになりました。マクロの候補にも展開結果が表示されるほか、各マクロの動作を説明するドキュメントセクションも新たに追加されました。検証機能は、存在しない変数への参照や、誤った引数で呼び出されたマクロを検出します。

ビルダーチャートでも、SQL 入力と Lucene 入力の両方で、編集可能なほとんどのフィールドに同じ変数置換が適用されます。変数は `WHERE`、`GROUP BY`、`HAVING`、`ORDER BY` で使用でき、同様に自動補完と検証も機能します。Lucene フィールドでは変数を使用できますが、マクロは使用できません。SQL ビルダーのフィールドで使えるのは、生のSQLで利用できるすべてのマクロではなく、変数関連のマクロのみです。

アラートには厳格なルールが 1 つあります。すべての変数は空の値で評価されるという点です。アラートクエリが変数を参照している場合は、保存前にエディタで警告が表示されます。プレビューと生成された SQL には、アラート詳細ページも含めて空の展開結果が表示され、アラートタスクも実行時にこの空の値を適用します。

変数の設定は、引き続き `NEXT_PUBLIC_ENABLE_DASHBOARD_VARIABLES` で制御されます。変数を設定していない場合、ダッシュボードの動作は従来どおりです。

## 評価履歴を備えたアラート詳細ページ {#alert-detail-page-with-evaluation-history}

*デモ担当者: [@wrn14897](https://github.com/wrn14897)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Y0entaRF-R8" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

これまで、アラートで確認できるのは履歴ストリップ程度でした。アラートが実際にどのように動作しているかを把握しようとしても、調べられる情報はほとんどありませんでした。

新しい詳細ページでは、すべての評価が表示されます。グループ化されたアラートでは、どのグループが発報したか、そしてしきい値を超えた値がグループごとに表示されます。各エントリには ClickHouse クエリの所要時間も含まれ、アラートの設定も併せて確認できます。

バックフィル済みバケットのカラムについては補足が必要です。評価が実行されなかった場合、次回の実行時に欠損したバケットを処理してギャップを埋めます。つまり、バックフィル済みバケットがある場合、そのアラートはスケジュールより遅れて実行されているということです。これにより、ClickHouse クエリが遅い場合も、後続の評価が気付かれないまま遅延するのではなく、その痕跡が目に見える形で残るようになりました。

チャートのマーカーは評価対象バケットの開始時刻に揃えて表示されるため、アラートがいつ発報し、いつ OK に戻ったかを把握しやすくなりました。

また、詳細ページから直接アラートを編集・削除することもできます。保存済み検索のモーダルやダッシュボードタイルのエディタに戻る必要はありません。アラート設定のより多くの項目をこのページで扱えるようにすることについては、引き続き検討を進めています。

このページは引き続き `NEXT_PUBLIC_ENABLE_ALERT_DETAILS` で有効化する必要があります。

## アラートの調査と MCP ツールのアノテーション {#investigating-alerts-and-mcp-tool-annotations}

*デモ担当者: [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/942yeJitK4Q" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**ClickHouse オブザーバビリティのみ:** 発報中のアラートに Investigate ボタンが追加されました。アラートページまたはアラート詳細ページでこのボタンをクリックすると、ノートブックでの調査が開始されます。

最終的には、アラートの発報と同時に調査を自動で開始することを目指しています。このボタンはそこに至るまでの有用な中間段階であり、最終形ではありません。

また、ClickStack の MCPサーバーのすべてのツールに、アノテーションによるヒントが付与されるようになりました。これまでサーバーは、どのツールが読み取り専用で、どのツールがデータを変更・削除するのかを一切示していませんでした。

`readOnlyHint` と `destructiveHint` が追加されたことで、クライアントはこれらのツールを区別して扱えるようになります。読み取りはそのまま実行し、破壊的なアクションは明示的な承認を得るまで保留できます。典型的な例がアラートの削除で、実行前に確認を求められるべき操作です。

最後の変更は、エージェントがそもそもどのツールを選ぶかに関するものです。明確な選択ポリシーがないままツールが増えていった結果、`clickstack_sql` の利用が徐々に増加していました。ビルダーツールのほうが適している場面でも、エージェントが生のSQLに頼っていたのです。

これはクエリの正確性だけの問題ではありません。生のSQLからは静的な結果タイルしか生成されません。一方、ビルダーツール (`clickstack_table`、`clickstack_timeseries`、`clickstack_search`) が生成するタイルは、クリックして掘り下げたり、そこから別の切り口で分析したりできます。

現在の MCP は、エージェントにまずビルダーツールを使うよう促し、生のSQLはビルダーツールでは本当に表現できないクエリに限定しています。この変更により、Eval のスコアは目に見えて向上しました。

**関連 PR:** [#2838](https://github.com/hyperdxio/hyperdx/pull/2838) すべてのツールに MCP ツールのアノテーション (`readOnlyHint` など) を追加、[#2840](https://github.com/hyperdxio/hyperdx/pull/2840) 生のSQLではなくビルダークエリツールを使うようエージェントを誘導、[#2870](https://github.com/hyperdxio/hyperdx/pull/2870) ダッシュボードのエージェントを系列ごとのタイルフィルタへ誘導。Investigate ボタン自体については、リンク可能なパブリック PR はありません。

## 単一クエリによる複数系列メトリクスチャート {#multi-series-metric-charts-in-a-single-query}

*デモ担当者: [@wrn14897](https://github.com/wrn14897)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/jJKgFrMfGjU" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

これまで、複数のメトリクスを 1 つのチャートに表示するには、系列ごとに ClickHouse クエリを 1 つずつ実行し、その結果セットを Node またはブラウザ上でマージする必要がありました。つまり、N 個の系列を持つチャートでは N 個のクエリが発行されていました。

現在、複数系列チャートは単一の SQLクエリにコンパイルされます。各系列は CTE となり、最後に ClickHouse がそれらをマージします。比率も同じ仕組みで処理され、両方の系列が 1 つのクエリで生成されたうえで、比率は最終的なプロジェクションで計算されます。

すぐに得られるメリットはクエリ数の削減です。さらに、このクエリ形状はメトリクスの数式機能の基盤にもなります。数式を最終的な `SELECT` で表現するには、すべての系列が 1 つの relation 内のカラムとして揃っている必要があります。現在のコンパイラが生成するのはまさにその形であり、数式機能の開発もすでにこれに続いて進められています。

この変更によって、1 件のリグレッションが見つかりました。浮動小数点数を返す集計と整数を返す集計が混在する複数系列タイルが、レンダリングに失敗していたのです。`Float64` を返すヒストグラムの `quantile` と、`Int64` を返すヒストグラムの `count` を組み合わせるだけで、この問題が発生していました。

合成された `UNION ALL` とピボットがすべての系列を同じカラムに流し込んでいたため、ClickHouse が型を `Variant(Float64, Int64)` に拡張していたことが原因です。この問題はすでに修正されています。

## Lucene の自動補完とパスワード要件に関する修正 {#lucene-autocomplete-and-password-requirement-fixes}

*デモ担当者: [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/8MODmM5RT6Q" title="YouTube ビデオプレーヤー" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

ダッシュボード変数のテスト中に、別のリグレッションが見つかりました。Lucene の自動補完が、いつの間にかほぼすべての場所で動作しなくなっていたのです。正常に動作していたのは検索ページだけでした。

もう 1 つの変更は、招待されたユーザーがパスワードを設定する Join Team ページに関するものです。このページでは、バックエンドでパスワード要件が適用されているにもかかわらず、その要件が表示されていませんでした。無効なパスワードを入力しても「Password is invalid」という汎用的なメッセージが表示されるだけで、ユーザーはポリシーを推測するしかありませんでした。

現在は、これらの要件が表示されるようになっています。また、要件を表示する共有コンポーネントを調べたところ、バックエンドとの食い違いが 2 点見つかりました。特殊文字として扱われる文字の範囲と、パスワードの最大長です。いずれも修正済みです。
