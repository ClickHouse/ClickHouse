ClickHouse Observability は **ClickHouse Cloud** 上で完結して動作し、ClickStack と同じデータモデルおよびユーザーエクスペリエンスを維持したまま、完全マネージド型のオブザーバビリティバックエンドを提供します。セルフマネージドのデプロイメントについては、[セルフマネージドアーキテクチャ](/ja/clickstack/self-configured/architecture)を参照してください。

このモデルでは、**ClickHouse、ClickStack UI、および OpenTelemetry (OTel) インジェスト用 collector** のホスティング、運用、セキュリティ確保はすべて ClickHouse Cloud が担います。ユーザーが担当するのは、アプリケーションのインストルメントと、自身の環境からマネージドサービスへのテレメトリー送信です。

### OpenTelemetry collector: データ取り込み {#open-telemetry-collector-managed}

ClickHouse Observability には、オープンで標準化された方法でテレメトリーを取り込むためのマネージド OpenTelemetry (OTel) collector が含まれています。サービスで **チーム設定 → Data → Managed Telemetry** を開き、OTLP エンドポイントと APIキーをコピーしてください。接続と認証の手順については、[OpenTelemetry データの送信](/ja/clickstack/observability/ingesting-data/opentelemetry)を参照してください。

collector は、テレメトリーを効率的なバッチ単位で ClickHouse Cloud にエクスポートします。その際、テレメトリーシグナルごとに最適化されたテーブルスキーマが使用されます。

インジェスト用の collector は ClickHouse Cloud によって管理されます。ただし、ホストメトリクスや Kubernetes ログなどのテレメトリーを収集してマネージドエンドポイントに転送するために、ご自身の環境にもコレクターが必要になる場合があります。

### ClickHouse Cloud: エンジン {#clickhouse-cloud}

ClickHouse Observability の中核を担うのは ClickHouse Cloud です。ClickHouse Cloud は、大規模なリアルタイム分析向けに設計されたカラム指向データベースである ClickHouse のサーバーレス版です。オブザーバビリティデータのインジェストとクエリ実行を支え、次のことを実現します。

* 大量のイベントに対する高速な検索
* high-cardinality なテレメトリーの大規模なインジェスト
* オブザーバビリティデータに対する列指向の圧縮
* 半構造化 JSON データのネイティブサポートによる動的なスキーマ進化
* 数百もの組み込み分析関数を備えた強力な SQL エンジン

ClickHouse Cloud はオブザーバビリティデータをワイドイベントとして扱うため、ログ、メトリクス、トレースを単一の統合された構造で深く相関付けることができます。

また、ClickHouse Open Source と比べて、オブザーバビリティの用途で次のような多くの利点があります。

* ストレージとは独立したコンピュートの自動スケーリング
* コンピュート容量に依存せずにテレメトリーを保持できるオブジェクトストレージ
* 統合された認証
* セキュリティおよびコンプライアンス機能
* シームレスなアップグレード

### ClickStack UI: インターフェイス {#hyperdx}

ClickStack UI は ClickStack のユーザーインターフェイスで、次の機能を備えています。

* 自然言語および Lucene 形式の検索
* リアルタイムデバッグのためのライブテーリング
* ログ、メトリクス、トレースの統合ビュー
* フロントエンドのオブザーバビリティを実現するセッションリプレイ
* ダッシュボードの作成とアラートの設定
* 高度な分析のための SQL クエリインターフェイス

ClickHouse 専用に設計された ClickStack UI は、強力な検索機能と直感的なワークフローを兼ね備えており、異常の発見、問題の調査、インサイトの獲得をすばやく行えます。

ClickHouse Observability では、UI は ClickHouse Cloud コンソールの認証システムに統合されています。

### インジェストとクエリの分離 {#ingestion-query-isolation}

ClickHouse Observability では、インジェストとクエリの実行に別々のコンピュートを使用します。書き込み用コンピュートは、受信したテレメトリーの処理とバックグラウンドでのデータメンテナンスを担います。読み取り用コンピュートは、検索、ダッシュボード、ノートブック、アラートのクエリを処理します。どちらも同じ基盤となるオブジェクトストレージにアクセスします。

この分離により、インジェストとクエリのワークロード間でのリソース競合が軽減されます。書き込み用コンピュートが一時的に使用不可になっても、読み取り用コンピュートは保存済みデータへのクエリを継続できます。ただし、最新のテレメトリーの反映が遅れる場合があります。読み取り用コンピュートが使用不可になった場合は、インジェストは継続できますが、検索やアラートの評価が中断される可能性があります。

### スケーリング {#scaling}

ClickHouse Cloud は、ワークロードの変化に応じてキャパシティを管理します。マネージドコレクターはインジェストのトラフィックに応じて水平スケーリングし、書き込み用と読み取り用のコンピュートは、互いに、またストレージからも独立してスケーリングします。

スケーリングは即座には行われません。インジェストが急増すると、新しいテレメトリーが検索可能になるまでに時間がかかることがあり、クエリが急増すると、キャパシティの調整中に応答時間が長くなることがあります。ワークロードを分離することで、一方のワークロードが他方に及ぼす影響を抑えられます。

### インジェストのバッファリングと復旧 {#ingestion-buffering-recovery}

マネージド collector は、まずテレメトリーを ClickHouse に書き込もうとします。ClickHouse が一時的に書き込みを受け付けられない場合、インジェストパイプラインはバッチを Amazon S3 に保存し、後から再適用できるようにします。この一時的なインジェストバッファは、ClickHouse がテレメトリーの保存に使用するオブジェクトストレージとは別のものです。書き込みが再開されると、バッファリングされたデータが ClickHouse に取り込まれます。

復旧中はバックログが順次処理されるため、直近のテレメトリーの表示が遅れたり、順序が前後したりすることがあります。このバッファリングは一時的な書き込み中断からの復旧を支援するものであり、cross-region のフェイルオーバーを提供するものではありません。また、あらゆる障害シナリオでデータの配信を保証するものでもありません。

collector の停止時にメモリ内にのみ保持されていたデータや、ClickHouse と S3 のどちらにも書き込めなかったバッチなど、一部のデータは失われる可能性があります。送信元のエージェントやコレクターでは、失敗したエクスポートを再試行するよう設定してください。また、対応している場合は永続キューを使用し、中断中もテレメトリーを保持できるようにしてください。
