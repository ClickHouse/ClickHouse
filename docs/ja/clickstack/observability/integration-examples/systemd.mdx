OpenTelemetry の journald レシーバーを使用して systemd ジャーナルのログを収集し、ClickHouse オブザーバビリティに送信します。Linux ホストがない場合でも、[デモデータセット](#demo-dataset)を使用してこのインテグレーションを試せます。

## 前提条件 {#prerequisites}

* ClickHouse オブザーバビリティのサービス
* 自身のログを使用する場合は、systemd が稼働しており、`journalctl` が利用可能で、そのジャーナルを読み取るアクセス許可を持つ Linux ホスト
* `curl`、およびデモ用の Docker

### 接続情報 {#connection-details}

<Tabs>
  <Tab title="完全マネージド型">
    <BetaBadge label="ベータ版" />

    ClickHouse オブザーバビリティを開き、**チーム設定 → Data → Managed Telemetry** に移動します。OTLP HTTP エンドポイントと APIキーをコピーしてください。**Copy connection details** で設定をまとめてコピーするか、**Reveal key** でマスクされたキーを表示できます。

    <div className="ch-image-lg">
      <Frame>
        ![Managed Telemetry の接続情報](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    以下の OTLP エクスポーターの例で使用するため、collector を実行する端末で次の変数を設定します。

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    プレースホルダーは、サービスの正確なエンドポイント (ポートを含む) と APIキーに置き換えてください。エンドポイントには `/v1/logs` などの接尾辞を付けず、ベースの HTTP エンドポイントを指定します。シグナルのパスはエクスポーターが自動的に付加します。
  </Tab>

  <Tab title="セルフマネージド">
    collector の接続可能な OTLP HTTP エンドポイント (例: `http://YOUR_COLLECTOR_HOST:4318`) と認証設定を使用します。collector で認証が不要な場合は、以下の構成からエクスポーターの `headers` ブロックを削除してください。セットアップ手順については、[セルフマネージド版スタートガイド](/ja/clickstack/self-configured/getting-started/managed)を参照してください。

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

エンドポイントには、監視対象ホストまたはデモ用 collector から接続できる必要があります。宛先の collector を Docker ホスト上で実行している場合は、`http://host.docker.internal:4318` を使用してください。

## 既存システムとの連携 {#existing-systems}

<Steps>
  <Step title="ジャーナルを確認する" id="verify-systemd">
    監視対象の Linux ホスト上で、次の手順を実行します。

    ```bash
    systemctl --version
    sudo journalctl -n 20
    sudo journalctl --disk-usage
    ```

    この receiver は、ホストの `journalctl` を使用して利用可能なジャーナルを読み取ります。永続ストレージと揮発性ストレージのどちらのジャーナルにも対応しているため、ストレージ設定を変更する必要はありません。
  </Step>

  <Step title="collector をダウンロード" id="download-collector">
    監視対象の Linux ホストで、次のコマンドを実行します。

    ```bash
    case "$(uname -m)" in
      x86_64) arch=amd64 ;;
      aarch64|arm64) arch=arm64 ;;
      *) echo "Unsupported architecture"; exit 1 ;;
    esac
    curl -fL -o otelcol-contrib.tar.gz \
      "https://github.com/open-telemetry/opentelemetry-collector-releases/releases/download/v0.161.0/otelcol-contrib_0.161.0_linux_${arch}.tar.gz"
    tar -xzf otelcol-contrib.tar.gz otelcol-contrib
    ```

    collector はホスト上で直接実行されるため、ホストにインストール済みの `journalctl` を利用できます。標準の Contrib Docker イメージには、このバイナリが含まれていません。
  </Step>

  <Step title="collector を設定する" id="configure-collector">
    次の内容を `systemd-monitoring.yaml` として保存します。

    ```yaml
    receivers:
      journald:
        start_at: end
        priority: info
        convert_message_bytes: true
    processors:
      transform/journald:
        error_mode: ignore
        log_statements:
          - context: log
            statements:
              - merge_maps(log.attributes, log.body, "upsert")
              - set(resource.attributes["host.name"], log.attributes["_HOSTNAME"])
              - set(resource.attributes["service.name"], "systemd-logs")
              - set(log.attributes["unit"], log.attributes["SYSLOG_IDENTIFIER"])
              - set(log.attributes["unit"], log.attributes["_SYSTEMD_UNIT"]) where log.attributes["_SYSTEMD_UNIT"] != nil
              - set(log.attributes["priority"], log.attributes["PRIORITY"])
              - set(log.body, log.attributes["MESSAGE"])
              - set(log.severity_text, "info")
              - set(log.severity_number, SEVERITY_NUMBER_INFO)
              - set(log.severity_text, "warn") where Int(log.attributes["PRIORITY"]) == 4
              - set(log.severity_number, SEVERITY_NUMBER_WARN) where log.severity_text == "warn"
              - set(log.severity_text, "error") where Int(log.attributes["PRIORITY"]) == 3
              - set(log.severity_number, SEVERITY_NUMBER_ERROR) where log.severity_text == "error"
              - set(log.severity_text, "fatal") where Int(log.attributes["PRIORITY"]) < 3
              - set(log.severity_number, SEVERITY_NUMBER_FATAL) where log.severity_text == "fatal"
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [journald]
          processors: [transform/journald, batch]
          exporters: [otlp_http/observability]
    ```

    ジャーナルのフィールドはログ属性として保持され、メッセージはログ本文に、ホスト名はリソース属性になります。この receiver は、優先度が `info` 以上のすべてのユニットを収集します。収集対象を絞り込むには、`journald` の配下に `units` リストを追加し、`ssh.service` や `nginx.service` など、ホスト上に実在するユニット名を指定してください。
  </Step>

  <Step title="collectorを起動する" id="run-collector">
    [接続変数](#connection-details)を設定してから、ダウンロード先のディレクトリで実行します。このコマンドは管理者のアクセス許可でシステムジャーナルを読み取り、2 つの接続変数のみを引き継ぎます。

    ```bash
    sudo --preserve-env=OTEL_EXPORTER_OTLP_ENDPOINT,OTEL_EXPORTER_OTLP_AUTHORIZATION \
      ./otelcol-contrib --config=systemd-monitoring.yaml
    ```

    この端末は開いたままにしておきます。別の端末で、ジャーナルエントリを生成します：

    ```bash
    echo 'ClickHouse Observability journal ingestion test' | systemd-cat -t observability-test -p info
    ```

    テストが終わったら、**Ctrl+C** で collector を停止します。継続的に収集する場合は、ジャーナルへのアクセス権を持つ systemd サービスとして実行し、再起動後も収集を再開できるように [カーソルストレージ](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.161.0/receiver/journaldreceiver#cursor-tracking) を設定してください。
  </Step>

  <Step title="ログを確認する" id="verify-logs">
    **検索** を開いて **Logs** を選択し、`ServiceName:systemd-logs` でフィルタして **Last 15 minutes** を選択します。テストメッセージと、`unit` や `priority` などの属性が表示されていることを確認してください。
  </Step>
</Steps>

## デモデータセット {#demo-dataset}

このサンプルには、約48時間分のテキストログエントリ1,334件が含まれており、SSH アクティビティ、スケジュールされたジョブ、サービスイベントなどが記録されています。`filelog` receiver を使用するため、systemd や `journalctl` をインストールする必要はありません。collector は、元のメッセージ本文とイベント間の間隔を維持したまま、タイムスタンプを現在時刻に合わせて更新します。

<Steps>
  <Step title="サンプルをダウンロードする" id="download-sample">
    ```bash
    curl -fL -o systemd-demo.log \
      https://datasets-documentation.s3.eu-west-3.amazonaws.com/clickstack-integrations/systemd/systemd-demo.log
    ```
  </Step>

  <Step title="デモ用 collector を設定する" id="configure-demo">
    以下を `systemd-demo.yaml` として保存します。

    ```yaml
    receivers:
      filelog/systemd:
        include:
          - /var/log/demo/systemd-demo.log
        start_at: beginning
        operators:
          - type: regex_parser
            regex: '^(?P<timestamp>\S+) (?P<hostname>\S+) (?P<unit>\S+?)(?:\[(?P<pid>\d+)\])?: (?P<message>.*)$'
            parse_from: body
            parse_to: attributes
          - type: time_parser
            parse_from: attributes.timestamp
            layout: '%Y-%m-%dT%H:%M:%S%z'
          - type: add
            field: attributes.source
            value: systemd-demo
          - type: add
            field: resource["service.name"]
            value: systemd-demo
    processors:
      transform/demo_timestamps:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(resource.attributes["host.name"], log.attributes["hostname"])
              - set(log.time, Now() - Duration("2m") - (Time("2025-11-16T23:45:00Z", "%Y-%m-%dT%H:%M:%SZ") - log.time))
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [filelog/systemd]
          processors: [transform/demo_timestamps, batch]
          exporters: [otlp_http/observability]
    ```

    このテキストサンプルにはジャーナルの priority フィールドがないため、デモではメッセージテキストから重大度を設定しません。
  </Step>

  <Step title="デモ用 collector を実行する" id="run-demo">
    [接続用の変数](#connection-details)を設定してから、両方のファイルがあるディレクトリで次のコマンドを実行します。

    ```bash
    docker run --rm --name systemd-demo-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/systemd-demo.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      -v "$(pwd)/systemd-demo.log:/var/log/demo/systemd-demo.log:ro" \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```

    取り込みを確認するまでは、端末を開いたままにしておいてください。終了したら **Ctrl+C** で停止します。デモを再実行すると、タイムスタンプが更新された状態でサンプルが改めて取り込まれます。
  </Step>

  <Step title="デモログを確認する" id="verify-demo">
    **検索** を開いて **Logs** を選択し、`ServiceName:systemd-demo` でフィルタリングしたうえで **Last 2 days** を選択します。`unit`、`hostname`、`message` 属性を持つサンプルエントリが表示されます。

    <div className="ch-image-lg">
      <Frame>
        ![ClickHouse オブザーバビリティの検索画面に表示された systemd デモログ](/images/clickstack/observability-systemd-demo-logs.png)
      </Frame>
    </div>
  </Step>
</Steps>

## トラブルシューティング {#troubleshooting}

### journalctl が見つからない {#journalctl-not-found}

本番用の collector は、`journalctl` がインストールされ、実行パスから利用できる監視対象の Linux ホスト上で実行してください。デモでは `filelog` を使用するため、`journalctl` は不要です。

### ログが表示されない {#no-logs}

collector の出力に、ジャーナルへのアクセス、認証、またはエクスポートに関するエラーが出ていないか確認してください。監視対象のホストで `sudo journalctl -n 20` を実行し、エントリが返されることを確認します。ユニットフィルタを設定している場合は、そのフィルタがサービス名と一致しているかを確認してください。収集を開始した後で、新しいエントリを生成してください。

ClickHouse オブザーバビリティでは、**Logs** ログソース、サービス名フィルタ、時間範囲を確認してください。デモの場合は **Last 2 days** を選択し、サンプルファイルが設定済みのパスにマウントされていることを確認します。
