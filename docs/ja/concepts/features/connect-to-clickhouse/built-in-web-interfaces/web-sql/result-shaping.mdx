組み込みの Web SQL UI (`play.html`。任意の ClickHouse HTTP ポートの [`/play`](/ja/concepts/features/connect-to-clickhouse/protocols/http) パスで提供されます) では、クエリを編集することなく、結果をカラムでソートしたり、カラムの値でフィルタリングしたり、ページ単位で閲覧したりできます。

これらの処理はいずれもブラウザ側では行われません。操作のたびに、対応するクエリ構築設定を付けてクエリが再実行されます。サーバーはクエリを派生テーブルとしてラッピングし、外側に `ORDER BY`、`WHERE`、`LIMIT` を付加することで、この設定をマテリアライズします。そのため、画面に表示される結果は、そのページにたまたま保持されていた行を並べ替えたものではなく、クエリ全体の結果をソート、フィルタリング、ページングしたものになります。

## ソート {#sorting}

すべてのカラムヘッダーの右側には2つの矢印が表示されます。▲ はそのカラムで結果を昇順にソートし、▼ は降順にソートします。矢印をクリックするとそのソートが有効になり、クエリが再実行されます。すでに有効な方向の矢印をクリックするとソートが解除され、反対方向の矢印をクリックするとその方向に切り替わります。これらの矢印は実際のボタンなので、キーボードユーザーも Tab キーで矢印に移動し、キーボードで操作できます。また、各矢印は自身の状態を支援技術に公開します (ヘッダー自体には `aria-sort` が設定されます)。

ホバー可能なポインター (マウス) を備えたデバイスでは、矢印はヘッダーにホバーしている間、または矢印にフォーカスがある間だけ表示されるため、それ以外のときは邪魔になりません。ホバー操作のないタッチデバイスなど、粗いポインターのデバイスでは、直接タップできるよう常に表示されます。ソート対象のカラムでは、ホバーしなくても両方の矢印が表示されます。一方はソート状態をひと目で把握できるようにするため、もう一方は方向の反転が次に最も行われやすい操作であるためです。

カラムヘッダー内のアイコンは、どの機能を制御するものであっても同じ規則で表示されます。その機能がカラムに適用されていない間は控えめな色で表示され、適用されると、有効なコントロール用に予約された色 (ライトテーマではマゼンタ、ダークテーマでは黄色) で描画されます。この状態では、ホバーしなくてもアイコンが表示されたままになります。控えめな表示は色を抑えるだけで、透明度は変えません。そのため、カラム名やセルの色分けの上でアイコンが薄れて見えることはありません。

### 複数のカラムでソートする {#sorting-by-several-columns}

ソートを有効にすると、現在のソートは置き換えられます。それまでソートされていたカラムは無効になり、クリックしたカラムだけがソートキーになります。<kbd>Shift</kbd> キーを押しながらクリックすると、すでに有効なソートキーを維持したまま、そのカラムが既存のキーの後ろに追加されます。この順序は `ORDER BY` と同じで、最初のキーが優先され、後続の各キーはそれより前のキーで同順位になった行の並び順を決定します。ソートキーが複数ある場合、有効な各矢印には、その順序におけるカラムの位置が上付き文字で表示されます (▼¹、▲²、…) 。

すでにソートキーになっているカラムを <kbd>Shift</kbd> キーを押しながらクリックすると、ソート方向だけが切り替わり、順序内の位置は変わりません。カラムのソートを無効にすると、そのカラムだけがソートキーから外れ、残りのキーはそのまま維持されます。

## フィルタリング {#filtering}

### 列ヘッダーから {#filtering-from-a-column-header}

すべての列ヘッダーには、ソート矢印の隣にファネルアイコンがあり、ソート矢印と同じ操作で表示されます。これをクリックすると、そのカラムに対する述語の入力欄が開き、そのすぐ右側に適用ボタン (▶) が付いています。プレースホルダーには、カラムの型に応じた述語の形が示されます。たとえば数値なら `> 10`、文字列なら `LIKE '%test%'` です。入力欄は列ヘッダーのセル内に開き、セルはその分のスペースを確保するために 2 行目に広がります。この行は、フィルタを設定した後にそのフィルタ自体が表示される行と同じなので、フィルタは表示されているその場所で編集できます。入力する内容は列名に続く部分で、`> 10` は `WHERE column > 10` になります。その位置でサーバーが受け付ける式であれば何でも使用でき、たとえば `BETWEEN 1 AND 5`、`IN (1, 2, 3)`、`IS NOT NULL`、`% 2 = 0` などが利用できます。

適用ボタン (または <kbd>Enter</kbd>) を押すと、フィルタが適用され、クエリが再実行されます。<kbd>Esc</kbd> を押すか、他の場所をクリックするか、Tab キーでフォーカスを移動すると、編集は破棄されて入力欄が閉じます。適用する内容がない場合、つまりフィルタが設定されていないカラムで入力欄が空の場合は、適用ボタンは無効になります。ただし、フィルタが設定されているカラムでは、入力欄が空でも適用ボタンは有効なままです。入力欄を空にして適用することで、入力欄からフィルタを削除できるためです。複数のカラムに設定されたフィルタは `AND` で結合されます。

### セルから {#filtering-from-a-cell}

セルを選択すると、その値でのフィルタがカラムでサポートされている場合は、コピーアイコンの横にファネルアイコンも表示されます。これをクリックすると、その値に適した比較演算子が表示されます。

| 値                                                     | 表示される演算子                                                        |
| ----------------------------------------------------- | --------------------------------------------------------------- |
| 数値                                                    | `=`, `!=`, `>`, `<`, `>=`, `<=`                                 |
| 日付または時刻 (`Date`, `Date32`, `DateTime`, `DateTime64`)  | `=`, `!=`, `>`, `<`, `>=`, `<=`                                 |
| 100 文字以下の文字列                                          | `=`, `!=`, `contains` — 空文字列はどの文字列にも含まれるため、`=` と `!=` のみが表示されます |
| `Bool`                                                | `true`, `false` — このセルの値との比較ではなく、2 つの値そのものが表示されます               |
| `Enum`                                                | `=`, `!=` — 名前の集合が固定されているため、部分一致ではフィルタとして役に立ちません                |
| `NULL`                                                | `IS NULL`, `IS NOT NULL`                                        |

いずれかを選ぶと、すぐに適用されます。日付、時刻、enum は、サーバーがレンダリングしたテキストそのものと比較され、ClickHouse がそれをカラム本来の型としてパースし直します (enum の場合は値の名前) 。`contains` は、値に含まれる `%` と `_` をエスケープした `LIKE` パターンに変換されるため、値と文字どおりに一致します。値が上記のいずれにも該当しないセル (配列、タプル、Map、長いテキストなど) ではメニューは表示されませんが、そのカラムはヘッダーの入力欄から通常どおりフィルタリングできます。

### 適用中のフィルタ {#the-filter-in-effect}

フィルタが適用されているカラムでは、フィルタが設定されている間、カラム名の下に述語が表示されます。そのため、画面上の行が結果の部分集合であることを見落とすことはありません。また、そのカラムのファネルアイコンは下へ移動し、ヘッダーの左下隅に表示されます。述語をクリックすると、その位置で入力欄が再び開きます。述語の横にある ✕ をクリックするとフィルタが解除されます。空の入力を適用した場合も同様です。いずれの操作でもクエリが再実行されます。

フィルタは、どこから設定したかにかかわらず、1 つのカラムにつき 1 つです。セルからフィルタを設定すると、ヘッダーの入力欄で設定されていたフィルタは置き換えられます。ヘッダーには常に適用中のフィルタが表示されます。

フィルタを適用した結果が空になった場合も、列ヘッダーはそのまま表示されます (フィルタを適用していない空の結果は垂直レイアウトで表示されます) 。これにより、何にも一致しなかったフィルタを確認し、そこから解除できます。

## ページネーション {#pagination}

結果は上限まで表示されます。上限は 1000 行ですが、列数が非常に多い結果ではそれより少なくなります。結果がこの上限で切り詰められた場合は、まだ表示されていない部分があるため、テーブルの下にページャーが表示されます：

```text
Page: 1 2 …   Per page: 1000
```

ページ番号をクリックすると、ページサイズが表示上限に設定され、そのページが [`page`](/ja/reference/settings/session-settings/other#page) 設定に指定されたうえで、クエリが再実行されます。サーバーはそのページを対応する `OFFSET` に変換します。以降、結果がページ分割されている間はページャーが表示され続けます。各ページはちょうど満杯になるため、結果が切り詰められているようには見えなくなりますが、それでもページャーは残ります。

ページ数は表示されません。ページ数は不明であり、結果の行数を数えるには別のクエリをもう1つ実行する必要があるためです。ページャーには、現在のページより前の10ページ、現在のページ、次のページが表示され、その後に `…` が続きます。`…` をクリックすると任意のページ番号を入力できる入力欄に切り替わり、入力欄からフォーカスが外れた時点で値が確定します (<kbd>Enter</kbd> を押しても確定します) 。

次のページは、現在のページが満杯である場合にのみ表示されます。ページに収まる数より少ない行しか返されなかったページは結果の末尾であるため、それ以降のページは存在しません (結果の長さがたまたまページサイズのちょうど倍数である場合は、さらに1ページが表示され、そのページは空で返されます。このケースを判別するには、やはり行数を数える必要があるためです) 。

`Per page` は1ページあたりの行数を示し、同じ方法で編集できます。値をクリックして別の値を入力してください。この値は、結果を一度に表示できる行数を超えることはできません。それより大きなページサイズにすると、テーブル側で切り詰められてしまう行まで返され、次のページはそれらの行の後から始まるため、ページを進めると表示しきれなかった行が警告なく飛ばされてしまいます。そのため、より大きな数値を入力した場合は最大値として扱われ、値の表示もその最大値になります。この値を変更すると最初のページに戻ります。ページサイズが変わると、各ページに含まれる行も変わるためです。

ソートやフィルタを変更すると、最初のページに戻ります。どちらも結果に含まれる行やその順序を変えるため、ユーザーが表示していたページが結果の同じスライスを指さなくなるためです。

## 適用方法 {#how-it-is-applied}

形状は、[`order`](/ja/reference/settings/session-settings/other#order)、[`filter`](/ja/reference/settings/session-settings/other#filter)、[`limit`](/ja/reference/settings/session-settings/other#limit)、[`page`](/ja/reference/settings/session-settings/other#page) の各クエリ構築設定として送信されます。サーバーはこれらをクエリのテキストではなくパース済みクエリに適用するため、元のクエリがどのような形であっても組み合わせて使用できます。`UNION`、末尾の `FORMAT` 句、クエリ自体に含まれる `ORDER BY` や `LIMIT` もすべてそのまま機能し、エディタ内のクエリが書き換えられることもありません。

カラム名は引用符で囲まれた識別子として渡されます。そのため、名前が 式 (`count()`) である結果カラムや、名前にスペースを含む結果カラムも、ソートキーやフィルタキーとして使用できます。

## 利用できる条件 {#when-it-is-available}

形状は、これらの設定の対象となる文、つまり `SELECT` クエリと `UNION` クエリ (`WITH` 句または `FROM` で始まるクエリを含む) でのみ利用できます。`SHOW`、`DESCRIBE`、`EXISTS`、`EXPLAIN` では利用できません。これらもテーブルを返しますが、設定が適用されないため、コントロールを表示すると、実際の行では実現できない結果を約束することになってしまいます。

形状は単一のステートメントの結果に適用されるため、「Run all」による複数ステートメントの一括実行では利用できません。この場合、各ステートメントはそれぞれ異なるカラムを持つ別個のクエリになるためです。

また、最初のページが 1 行以下の結果でも利用できません。1 行しかなければどう並べ替えても順序は変わらず、その行に対するフィルタも行を残すか除外するかのどちらかしかないため、コントロールでできるのは同じ行を得るためにクエリを再実行することだけです。さらに、空の結果には除外する行すらありません。[色分け](/ja/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/color-coding)のトグルがこの場合に非表示になるのも同じ理由で、1 行以下では比較する対象がないからです。

ただし、次の 2 種類の単一行の結果ではコントロールが残ります。これらの場合、コントロールが元に戻す唯一の手段となるためです。

* すでにソートまたはフィルタが適用されている結果。ソートは元に戻せる状態に、フィルタは解除できる状態に保たれている必要があります。単一行に一致するフィルタは、長い結果が短くなる典型的なケースであり、それと同時にコントロールを取り除いてしまうと、ユーザーはフィルタが有効なまま身動きが取れなくなります。
* 表示上限で切り詰められた結果。これはより長い結果の最初のページです。ページサイズはテーブルが一度に表示できるセル数で制限されるため、非常に列数の多い結果は 1 行に切り詰められることがあり、それ以降の行こそ、ソートやページングで表示させるべき対象です。

形状は、それを設定したステートメントに紐づきます。別のステートメントを実行すると (クエリを編集した後や、複数ステートメントのエディタでカーソルを別のステートメントに移動した場合など) 、新しいステートメントに存在しない可能性のあるカラムに `ORDER BY` や `WHERE` を適用するのではなく、形状は破棄されます。

形状は、そのステートメントを実行したコンテキストにも紐づきます。すなわち、選択されているデータベース、送信先のサーバーとユーザー、そしてクエリパラメータの値です。これらのいずれかが変わると、同じテキストでも異なるカラムを指すことになります。たとえば、データベースを切り替えた後の `SELECT * FROM events` や、パラメータを編集した後の `SELECT * FROM {tbl:Identifier}` がこれにあたります。そのため、この場合も形状は破棄され、次回の実行では形状が適用されていない結果が返されます。

## ダウンロードとコピー {#downloading-and-copying}

ダウンロード時は、結果を生成したクエリを同じ形状で再実行するため、エクスポートされるファイルには画面上の結果と同じ行が同じ順序で含まれます。コピーはレンダリング済みの結果をそのまま使用するため、こちらも画面上の結果と一致します。

## 永続化 {#persistence}

形状はページのURL (`sort_columns`、`filters`、`page`、`page_size`) 、ブラウザの履歴、および所属するセルの結果スナップショットに記録されます。そのため、ページを再読み込みしたり、リンクを共有したり、ブラウザで戻る・進むの操作をしたりしても形状は保持されます。形状は表示方法だけでなく行そのものを決定するため、クエリを自動実行する共有リンク (`run=1`) は同じ形状でクエリを再実行し、結果そのものを再現します。URLと履歴ステートをコンパクトに保つため、保存されるのは有効な形状のみです。整形されていない結果は、URLにも履歴ステートにも何も追加しません。

前述のとおり、復元済みの結果では、形状はそれを生成したコンテキストに紐付けられたままになります。スナップショットには、行の生成時に使用されたデータベース、接続、およびパラメータの値が記録されます。そのため、これらのいずれかを変更した後にステートメントを再実行すると、形状は別の結果に適用されることなく破棄されます。

[色分けモード](/ja/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/color-coding)や[ピン留めされたカラム](/ja/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/pinned-columns)と同様に、形状は整形対象の結果に属します。つまり、形状はクエリタブに属し、[ノートブック](/ja/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/notebook)のタブでは個々のセルに属します。そのため、ある結果をソートまたはフィルタリングしても、別のタブや別のセルの結果が変更されたり再実行されたりすることはありません。セルの結果を整形した場合は、そのセルが再実行されます。

## 制限事項 {#limitations}

* サーバーが適用できない形状を指定するとクエリは失敗し、そのエラーは他の失敗したクエリと同様に表示されます。その後、この形状は削除されます。失敗した実行では、形状をクリアするためのヘッダーもページャーもレンダリングされないためです。
* ソートとフィルタリングでは、結果内のカラム名によってカラムを識別します。結果には同じ名前が2回含まれることがあり (`SELECT 1 AS x, 2 AS x` や、カラム名が共通するテーブル同士の結合など) 、そのようなカラムは名前で区別できないため、ソートやフィルタのコントロールは表示されません。同じ結果内でも、名前が重複していないカラムには引き続きコントロールが表示されます。
* 複数カラムのソートには <kbd>Shift</kbd> キーが必要なため、タッチデバイスでは利用できません。単一カラムのソートは利用できます。
* 1行のみの結果を縦方向 (転置) レイアウトで表示した場合は列ヘッダーがないため、コントロールも表示されません。そのため、ユーザーがすでに形状を指定した結果は水平レイアウトのまま表示されます。
