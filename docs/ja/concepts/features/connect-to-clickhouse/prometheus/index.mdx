ClickHouse は、[`TimeSeries`](/ja/reference/engines/table-engines/integrations/time-series) テーブル上に Prometheus HTTP API を実装しています。リモート書き込み、リモート読み取り、インスタント PromQL クエリ、範囲 PromQL クエリは、すべて 1 つのハンドラーで処理されます。

ClickHouse 自身のメトリクスを公開して Prometheus サーバーからスクレイプできるようにする方法については、[Prometheus メトリクスエンドポイント](/ja/concepts/features/connect-to-clickhouse/prometheus/metrics)を参照してください。

## 前提条件 {#prerequisites}

セットアップ手順は ClickHouse Cloud と自己管理型 ClickHouse とで異なります。ご利用のデプロイ環境に応じたセクションの手順に従ってください。

### ClickHouse Cloud {#prerequisites-cloud}

<Note>
  ClickHouse Cloud における PromQL のサポートは現在プライベートプレビュー段階です。プライベートプレビューに参加しているサービスでは、`enable_time_series_table` 設定と Prometheus APIエンドポイントがすでに設定済みです。それ以外の ClickHouse Cloudサービスにはこの設定がなく、ユーザー自身がそれらのサービスでこの機能を有効化することはできません。以降のセクションで説明する `SET enable_time_series_table` ステートメントと `http_handlers` 設定は、セルフマネージドのデプロイメントを対象としています。
</Note>

プライベートプレビューに参加しているサービスをご利用の場合は、[TimeSeries テーブルを作成する](#create-a-timeseries-table)に進んでください。サービスでは、[エンドポイント一覧表](#configure-prometheus-api)に記載されているエンドポイントのパスが利用できます。

### セルフマネージド: TimeSeries 設定を有効化する {#enable-the-timeseries-setting}

テーブルを作成・アクセスするユーザーに対して、`enable_time_series_table` 設定を有効にします。

```sql
SET enable_time_series_table = 1;
```

HTTP APIリクエストを使用する場合は、APIユーザーのプロファイルで `enable_time_series_table` を有効にしてください。

### セルフマネージド: Prometheus APIエンドポイントを設定する {#configure-prometheus-api}

ClickHouse のメイン HTTP ポート上に、プレフィックスでリクエストを振り分けるハンドラーを 1 つ設定します。

```xml
<http_handlers>
    <defaults/>
    <rule>
        <url_prefix>/prometheus/api/v1</url_prefix>
        <handler>
            <type>prometheus_api_v1</type>
        </handler>
    </rule>
</http_handlers>
```

`<defaults/>` は、`/ping` などのエンドポイントや SQL リクエスト向けの組み込みハンドラーをそのまま維持します。上記のプレフィックスを設定すると、次のエンドポイントが 1 つのハンドラーで公開されます。

| エンドポイント                                  | 用途                        |
| ---------------------------------------- | ------------------------- |
| `/prometheus/api/v1/write`               | Prometheus リモート書き込み       |
| `/prometheus/api/v1/read`                | Prometheus リモート読み取り       |
| `/prometheus/api/v1/query`               | インスタント PromQL クエリ         |
| `/prometheus/api/v1/query_range`         | 範囲 PromQL クエリ             |
| `/prometheus/api/v1/format_query`        | PromQL 式 のフォーマット |
| `/prometheus/api/v1/series`              | 系列のメタデータ                  |
| `/prometheus/api/v1/labels`              | ラベル名                      |
| `/prometheus/api/v1/label/<name>/values` | ラベル値                      |
| `/prometheus/api/v1/metadata`            | メトリクスファミリーのメタデータ          |
| `/prometheus/api/v1/federate`            | 最新サンプルのフェデレーション           |

この例では、ハンドラーに `database` と `table` を指定していません。そのため、各リクエストで `table` クエリパラメータを指定する必要があります (ただし `/format_query` は、指定された PromQL 式 をパースするだけでテーブルを必要としないため対象外です) 。あわせて `database` を指定するか、`prometheus.metrics` のような修飾付きテーブル名を使用することもできます。データベースを省略した場合は `default` が使用されます。これにより、1 つのハンドラーで複数の `TimeSeries` テーブルを扱えます。

すべてのリクエストで 1 つの固定テーブルを使用する場合は、ハンドラーでそのテーブルを設定します。

```xml
<handler>
    <type>prometheus_api_v1</type>
    <database>prometheus</database>
    <table>metrics</table>
</handler>
```

ハンドラーで設定したテーブルは、リクエストパラメータでオーバーライドできません。

ルーティングとハンドラーの設定:

| 名前           | デフォルト | 説明                                                                                                                              |
| ------------ | ----- | ------------------------------------------------------------------------------------------------------------------------------- |
| `url_prefix` | なし    | 設定したプレフィックスで始まるすべてのリクエストパスに一致するルールフィルタです。                                                                                       |
| `table`      | なし    | `TimeSeries` テーブルの名前です。省略した場合は、リクエストで `table` クエリパラメータを指定する必要があります。設定する名前にはデータベース名を含めることができます。                                  |
| `database`   | なし    | テーブルが属するデータベースです。リクエストでクエリパラメータとして指定することもできます。省略した場合、ClickHouse は修飾名で指定された `table` 値のデータベースを使用し、それもない場合は `default` にフォールバックします。 |

### TimeSeries テーブルを作成する {#create-a-timeseries-table}

データベースと `TimeSeries` テーブルを作成します。

```sql
CREATE DATABASE prometheus;
CREATE TABLE prometheus.metrics ENGINE = TimeSeries;
```

## リモート書き込みでメトリクスを取り込む {#remote-write}

ClickHouse は [Prometheus remote-write プロトコル](https://prometheus.io/docs/specs/remote_write_spec/) をサポートしています。Prometheus を設定して、このハンドラーに書き込むようにします。

```yaml
remote_write:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/write?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

Prometheus はサンプルを `prometheus.metrics` テーブルに送信します。

多数の同時実行される remote-write リクエストのデータをバッチにまとめ、より少ないパーツとして書き込むために、ClickHouse は[非同期挿入](/ja/reference/settings/session-settings/async-insert#async_insert)を使用します。非同期挿入はデフォルトで有効になっており、URL (またはユーザープロファイル) の `async_insert` 設定で有効・無効を切り替えられます。

ClickHouse は、[`wait_for_async_insert`](/ja/reference/settings/session-settings/wait-for#wait_for_async_insert) 設定に関係なく、データが `TimeSeries` テーブルのすべての内部テーブルにフラッシュされた後でのみ、非同期の remote-write リクエストに確認応答を返します。remote-write プロトコルでは、確認応答済みの書き込みは永続化済みとみなされるためです。flush が失敗した場合、リクエストはエラーを返し、Prometheus がそのリクエストを再試行します。

各リクエストは自身の flush を待機するため、非同期挿入を使用すると 1 つの送信元が書き込める速度に上限が生じます。Prometheus は remote-write の分片ごとに一度に 1 つのリクエストを送信します。複数の分片が同時に送信すると、保留中のリクエストが先に [`async_insert_max_data_size`](/ja/reference/settings/session-settings/async-insert#async_insert_max_data_size) に達しない限り、アダプティブな flush タイムアウトは [`async_insert_busy_timeout_max_ms`](/ja/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms) まで延びます。リクエストは自身のバッチがフラッシュされるまで待機し、その flush はバッチ開始から最大でこの時間が経過した時点で行われます。そのため、負荷が継続する状況では、各分片の書き込み速度はおおよそ `samples per request / async_insert_busy_timeout_max_ms` になります。なお、Prometheus はデフォルトで 1 リクエストあたり最大 2,000 サンプルを送信します。この速度を上げるには、次のいずれかの方法を使用します。

* [`remote_write`](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write) の `queue_config` で `max_shards` (デフォルトは 50) または `max_samples_per_send` を引き上げます。Prometheus は処理が追いつかなくなると、`max_shards` を上限として自動的に分片を追加します。
* URL またはユーザープロファイルで `async_insert_busy_timeout_max_ms` を引き下げます (例: `&async_insert_busy_timeout_max_ms=50`) 。これにより flush の頻度が上がり、flush のたびに内部テーブルに新しいパーツが作成されます。
* `async_insert=0` を指定して非同期挿入を無効化します。この場合、リクエストごとに内部テーブルに個別のパーツが作成されます。

## PromQL によるクエリ {#promql-query-support}

単一の時点で PromQL 式を評価するには、instant-query エンドポイントを使用します:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

range-query エンドポイントを使用すると、指定した時間範囲で式を評価できます。

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

クエリエンドポイントは、パラメータをフォームボディで受け取ることもできます。`--get` を指定しない場合、curl はパラメータを `application/x-www-form-urlencoded` 形式で `POST` 送信します。

```bash
curl --user default:<password> \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

format-query エンドポイントを使用すると、PromQL の式を評価せずにパースして整形できます：

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/format_query" \
  --data-urlencode "query=sum by(job)(http_requests_total{code=\"200\"})/2"
```

式は、パース済みクエリをシリアル化した形で返されます。その際、空白文字は正規化され、コメントは除去され、冗長な括弧は削除され、期間はパーサーが受け付ける単位で出力されます (例: `sum by (job) (http_requests_total{code="200"}) / 2`) 。期間は秒数の数値には変換されず単位がそのまま保持されるため、`rate(x[5m])` は `rate(x[5m])` として返されます。また、単一の単位の整数倍で表せない期間は、必要な単位をすべて組み合わせて表記されるため、`rate(x[90s])` は `rate(x[1m30s])` として返されます。このエンドポイントは式を評価しないため、`database` および `table` パラメータは不要です。

HTTP API、`promql` ダイアレクト、およびテーブル関数で使用される関数と集約演算子の一覧については、[サポートされている PromQL の機能](/ja/reference/functions/table-functions/prometheusQueryRange#supported-promql-features)を参照してください。

その他のリクエストパラメータは、ClickHouse 設定として適用されます (例: `max_execution_time=10`)。クエリエンドポイントは、VictoriaMetrics および Thanos の一部のパラメータも受け付けます。`nocache=1` を指定すると `use_query_cache=0` が、`partial_response=false` を指定すると `skip_unavailable_shards=0` が設定されます。また、`dedup=false`、`trace`、`round_digits` は無視されます。一方、`extra_label` と `extra_filters` は、ClickHouse がこれらのフィルタを適用しないため、エラーとして拒否されます。同様に、`dedup=true` と `partial_response=true` も、ClickHouse が Thanos の重複排除や部分レスポンスを実装していないため拒否されます。

### Grafana {#grafana}

Prometheus データソースを設定し、ベースURLには `/api/v1` の手前までを指定します：

```yaml
apiVersion: 1
datasources:
  - name: ClickHouse Prometheus
    type: prometheus
    access: proxy
    url: https://clickhouse.example.com:8443/prometheus
    basicAuth: true
    basicAuthUser: default
    jsonData:
      httpMethod: POST
      customQueryParameters: database=prometheus&table=metrics
    secureJsonData:
      basicAuthPassword: <password>
```

Grafana は、このベースURLの末尾に `/api/v1/query` または `/api/v1/query_range` を付加し、各リクエストに `customQueryParameters` を追加します。

`httpMethod: POST` を指定すると、Grafana はクエリパラメータをリクエストボディで送信します。ClickHouse はリクエストボディと URLクエリ文字列の両方を読み取るため、この場合も `customQueryParameters` は適用されます。URL には長さの上限があるため、長い PromQL 式には `POST` を使用してください。

<Note>
  実装されているのは、クエリエンドポイント `/api/v1/query`、`/api/v1/query_range`、`/api/v1/format_query`、メタデータエンドポイント `/api/v1/series`、`/api/v1/labels`、`/api/v1/label/<name>/values`、`/api/v1/metadata`、および [フェデレーション](#federation) エンドポイント `/api/v1/federate` のみです。`/api/v1/series` には少なくとも 1 つの `match[]` 系列セレクターが必要です。任意の `start`、`end`、`limit` パラメータをサポートし、各セレクターに一致した系列のユニオンを返します。`/api/v1/labels` は同じパラメータを受け付けますが、`match[]` は任意です。一致した系列 (セレクターが指定されていない場合はすべての系列) のラベル名をソート済みで返します。`/api/v1/label/<name>/values` は `/api/v1/labels` と同じパラメータを受け付け、1 つのラベルの値をソート済みで返します。`<name>` には、`[a-zA-Z0-9_]` 以外の文字を含むラベル名に対して、Prometheus の `U__...` エスケープ処理を任意で使用できます。これらのエンドポイントにより、Grafana の Prometheus データソースがラベルの閲覧、テンプレート変数、クエリビルダーの自動補完に使用する機能をカバーしています。
</Note>

### SQL のエントリーポイント {#sql-entry-points}

ClickHouse は、HTTP API、`promql` ダイアレクト、そして [`prometheusQuery`](/ja/reference/functions/table-functions/prometheusQuery) および [`prometheusQueryRange`](/ja/reference/functions/table-functions/prometheusQueryRange) テーブル関数のいずれにおいても、同じ PromQL コンバーターを使用します。

`clickhouse-client` を使って PromQL を直接実行します。

```bash
clickhouse-client \
  --dialect promql \
  --promql_database prometheus \
  --promql_table metrics \
  --query 'rate(http_requests_total[5m])'
```

テーブル関数を使用すると、SQLクエリにPromQLを埋め込めます。

```sql
SELECT *
FROM prometheusQuery(
    prometheus.metrics,
    'rate(http_requests_total[5m])',
    now()
);
```

## メトリクスのメタデータをクエリする {#metadata}

`/prometheus/api/v1/metadata` エンドポイントは、`TimeSeries` テーブルの `Metrics` ターゲットテーブルに保存されているメトリクスのメタデータ、つまり各メトリクスファミリーの型、ヘルプテキスト、単位を返します。URLクエリ文字列では、次の Prometheus パラメータを指定できます。

| パラメーター             | 説明                                                              |
| ------------------ | --------------------------------------------------------------- |
| `metric`           | 指定したメトリクスファミリーのメタデータのみを返します。                                    |
| `limit`            | 返すメトリクスファミリーの数を制限します。負の値を指定すると無制限になり、0 を指定するとメトリクスファミリーは返されません。 |
| `limit_per_metric` | メトリクスファミリーごとに返すメタデータオブジェクトの数を制限します。0 または負の値を指定すると無制限になります。      |

デフォルトの `Metrics` ターゲットテーブルは、メトリクスファミリー名で順序付けされた `ReplacingMergeTree` であり、メトリクスファミリーごとに最後に書き込まれたメタデータエントリを保持します。1 つのファミリーについて複数のエントリが返されるのは、ターゲットテーブルにそれらが保存されている場合に限られます。具体的には、パーツがマージされる前、またはそれらを保持するエンジンでテーブルが定義されている場合です。

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/metadata" \
  --data-urlencode "metric=http_requests_total" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

## メトリクスのフェデレーション {#federation}

ClickHouse は、`/prometheus/api/v1/federate`(または `query` 型のハンドラーが提供する、`/federate` で終わる任意のパス)で [Prometheus フェデレーション](https://prometheus.io/docs/prometheus/latest/federation/) エンドポイントをサポートしています。`match[]` セレクターに一致した各系列について、直近 5 分間の最新サンプルを Prometheus テキストフォーマットで返します。これにより、Prometheus サーバーからスクレイプできます:

```yaml
scrape_configs:
  - job_name: clickhouse-federate
    honor_labels: true
    scheme: https
    metrics_path: /prometheus/api/v1/federate
    params:
      'match[]': ['{job="node"}']
      table: ['prometheus.metrics']
    static_configs:
      - targets: ['clickhouse.example.com:8443']
```

## リモート読み取りでメトリクスを読み取る {#remote-read}

ClickHouse は、`/prometheus/api/v1/read` で [Prometheus リモート読み取りプロトコル](https://prometheus.io/docs/prometheus/latest/querying/remote_read_api/) をサポートしています。

同じ `TimeSeries` テーブルからデータを読み取るように、Prometheus サーバーを設定します。

```yaml
remote_read:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/read?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

## 記録ルール {#recording-rules}

ClickHouse は Prometheus のルールファイルを評価しません。代わりに、[リフレッシャブルmaterialized view](/ja/reference/statements/create/view#refreshable-materialized-view) で [記録ルール](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/) と同等の処理を実現できます。リフレッシャブルmaterialized view は、PromQL の式をスケジュールに従って評価し、その結果を `TimeSeries` テーブルに追記します。次のビューは、`sum by (job) (rate(http_requests_total[5m]))` を 1 分ごとに `job:http_requests:rate5m` として記録します。

```sql
CREATE MATERIALIZED VIEW prometheus.job_http_requests_rate5m
REFRESH EVERY 1 MINUTE APPEND TO prometheus.metrics (tags, samples) AS
SELECT
    mapUpdate(CAST(tags, 'Map(String, String)'), map('__name__', 'job:http_requests:rate5m')) AS tags,
    [(timestamp, value)] AS samples
FROM prometheusQuery(prometheus.metrics, 'sum by (job) (rate(http_requests_total[5m]))', toStartOfMinute(now()));
```

各リフレッシュでは、現在の分の開始時点で 式 を評価し、`mapUpdate` でメトリクス名を設定したうえで、結果の系列ごとにサンプルを 1 つ追記します。同じ Map には追加ラベルを含めることもできます (例: `map('__name__', 'job:http_requests:rate5m', 'team', 'web')`) 。記録された系列は、他のメトリクスと同じようにクエリできます。

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=job:http_requests:rate5m" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

最後の評価の時刻とエラーは [`system.view_refreshes`](/ja/reference/system-tables/view_refreshes) で確認できます。

ビューは、Prometheus の記録ルールと次の点で異なります。

* 評価時刻は、リフレッシュが実行された時点の `now()` です。ビューはスケジュールによるリフレッシュに加えて、作成直後 (`EMPTY` を指定して作成した場合を除く) 、リフレッシュが協調されていない場合のサーバー再起動後 (Replicated または Shared データベース以外にあるビューや、`all_replicas = 1` を指定したビューは、最後のリフレッシュを記憶しません) 、およびスケジュールされたリフレッシュを逃した後に `SYSTEM START VIEW` で再開されたときにもリフレッシュされます。これらのリフレッシュによって、スケジュールされたサンプルの間に余分なサンプルが追加されないよう、例のように `now()` を時間間隔単位で切り捨ててください。ただし、追加のリフレッシュによって、同じ丸められたタイムスタンプに 2 つ目のサンプルが書き込まれる可能性は残ります。5 分間隔のルールであれば、`toStartOfInterval(now(), INTERVAL 5 MINUTE)` を使用します。
* 実行されなかった評価が後から補完されることはありません。サーバーが停止していた場合やビューが停止されていた場合、ビューは現在の時間間隔のみを評価し、それ以前の時間間隔は空のままになります。リフレッシュに時間間隔より長い時間がかかった場合も同様です。
* 結果から消えた系列にはデータの有効期間に関するマーカー (staleness marker) が付与されないため、クエリはルックバック期間 (デフォルトでは 5 分) の間、その系列の最後に記録された値を返し続けます。
* ルールファイルは存在せず、各ルールはそれぞれ個別のビューとなります。また、ルールは `/api/v1/rules` に一覧表示されません。
