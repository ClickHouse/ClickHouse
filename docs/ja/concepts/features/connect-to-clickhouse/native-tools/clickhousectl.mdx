`clickhousectl` (別名 `chctl`) は、ローカル開発から ClickHouse Cloud までをカバーする ClickHouse 公式の CLI です。端末で操作するユーザー、スクリプト、コーディングエージェントのいずれからも利用できます。

`clickhousectl` では次のことができます。

* ローカルの ClickHouse バージョンのインストールと切り替え、分離されたローカルサーバーの実行、SQL の実行
* Docker ベースの Postgres のローカル実行
* ClickHouse Cloud サービスの作成、設定、スケーリング、バックアップ、クエリ実行
* [ClickHouse Managed Postgres](/ja/products/managed-postgres/overview) サービスの作成、監視、設定、復元
* オブジェクトストレージ、Kafka、Kinesis、Pub/Sub、Postgres、MySQL、MongoDB、BigQuery をソースとする ClickPipes の作成と運用
* [Self-managed ClickHouse Observability](/ja/clickstack/self-configured/deployment/managed) サービス上のソース、ダッシュボード、アラート、Webhook、保存済み検索、ロールの管理
* 実行可能 UDF のローカルでの開発と ClickHouse Cloud へのデプロイ
* 組織のメンバー、招待、APIキー、ロールの管理
* 公式の ClickHouse agent skills のコーディングエージェントへのインストール

このページでは代表的な例を紹介します。すべてのコマンドとフラグに関する正式なリファレンスは `clickhousectl <command> --help` です。ほとんどのコマンドのヘルプの末尾には `CONTEXT FOR AGENTS` ブロックがあり、Cloud コマンドでは必要な APIキーのアクセス許可も記載されています。タスクごとの手順については、各セクションのガイドへのリンクを参照してください。Cloud を中心とした概要については、[ClickHouse CLI](/ja/products/cloud/features/cli) を参照してください。

## インストール {#installation}

`clickhousectl` は macOS および Linux 上で動作し、ARM64 と x86&#95;64 の両アーキテクチャに対応しています。

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

このスクリプトは `~/.local/bin/clickhousectl` をインストールし、別名 `chctl` を作成します。`~/.local/bin` が `PATH` に含まれていることを確認してください。

パッケージマネージャーを使用してインストールすることもできます。

| ツール                            | コマンド                            |
| ------------------------------ | ------------------------------- |
| npm                            | `npm install -g clickhousectl`  |
| uv                             | `uv tool install clickhousectl` |
| pipx                           | `pipx install clickhousectl`    |
| pip                            | `pip install clickhousectl`     |
| cargo-binstall                 | `cargo binstall clickhousectl`  |
| Cargo、ソースコードから (Rust 1.94.1+)  | `cargo install clickhousectl`   |

別名 `chctl` を作成するのは、インストールスクリプトと npm のみです。インストール済みのバージョンを更新するには、`clickhousectl update` を実行してください ([自己更新](#self-update)を参照) 。ただし、npm、uv、pipx、pip でインストールした場合は、更新の代わりに、そのパッケージマネージャーのアップグレードコマンドが表示されます。

### シェル補完 {#shell-completions}

Tab キーでコマンド、フラグ、ローカルサーバー名、インストール済みのバージョンを補完するには、シェルの起動ファイルに次の 1 行を追加します。これで `clickhousectl` と `chctl` の両方に補完が登録されます。

```bash
eval "$(clickhousectl completions bash)"   # ~/.bashrc
eval "$(clickhousectl completions zsh)"    # ~/.zshrc, after compinit
clickhousectl completions fish | source    # ~/.config/fish/config.fish
```

補完機能は Tab キーを押すたびにインストール済みの CLI を実行するため、`update` 後も常に最新の状態が保たれます。

## 要件 {#requirements}

* Docker (ローカルの Postgres を使用する場合のみ)
* Cloud コマンドを使用するには、[ClickHouse Cloud](https://clickhouse.com/cloud) アカウントが必要です。読み取り系のコマンドは、ブラウザベースのOAuth (`cloud auth login`) で利用できます。リソースの作成や変更には [APIキー](/ja/products/cloud/features/admin-features/api/openapi) が必要です。詳しくは [認証](#authentication) を参照してください。

## ローカル {#local}

Git で `.git/` を含むディレクトリがプロジェクトルートとなるのと同様に、`.clickhouse/` を含むディレクトリがプロジェクトルートとなります。ローカルコマンドは、現在のディレクトリまたはその上位にある最も近いプロジェクトルートを使用するため、プロジェクト内のどのサブディレクトリからでも実行できます。プロジェクト外で実行した場合は、現在のディレクトリが使用されます。スクリプトや CI ジョブなどでプロジェクトルートを明示的に指定するには、`CLICKHOUSECTL_PROJECT_DIR` を設定してください。サーバーデータはプロジェクトごとに `.clickhouse/` に保存され、ClickHouse バイナリは `~/.clickhouse/` でグローバルに共有されます。ワークフロー全体については、[ローカル開発ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md)を参照してください。

### バージョンのインストールと選択 {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
clickhousectl local install --binary ~/ClickHouse/build/programs/clickhouse   # A build of your own
```

| セレクター         | 意味                                                  |
| ------------- | --------------------------------------------------- |
| `latest`      | 最新の ClickHouse ビルド。インストール、使用、起動のたびにリモートで確認されます (推奨) |
| `stable`      | 最新の安定版リリース                                          |
| `lts`         | 最新の長期サポートリリース                                       |
| `26.8`        | 一致する最新のリリース                                         |
| `26.8.1.1760` | 完全一致するバージョン                                         |

`local use` は、必要に応じてバージョンをインストールし、以降のサーバー起動時のデフォルトとして設定したうえで、`~/.local/bin/clickhouse` にシンボリックリンクを作成します。これにより、`clickhouse client` と `clickhouse local` が `PATH` 上で使用できるようになります。シンボリックリンクを作成しない場合は `--no-global` を指定します。そのパスに通常のファイルがすでに存在する場合は、変更されません。

`local remove` では、デフォルトのバージョンや、いずれかのプロジェクトで実行中のサーバーが使用しているバージョンは削除できません。`--force` を指定すると、それらのサーバーを停止してバージョンを削除し、デフォルト設定とシンボリックリンクも解除します。

`local install --binary <path>` は、自分でビルドした ClickHouse バイナリをコピーし、そのバイナリが報告するバージョンとしてインストールします。これにより、他のインストール済みバージョンと同様に、`local use` や `--version` で選択できるようになります。再ビルドしても通常は同じバージョンが報告されるため、インストール済みのコピーを置き換えるには `--force` を指定してください。

### プロジェクトの初期化 {#initializing-project}

```bash
clickhousectl local init
```

`init` は、現在のディレクトリ (`CLICKHOUSECTL_PROJECT_DIR` が設定されている場合はそのディレクトリ) をプロジェクトのルートとして設定します。ランタイムデータ用に git の管理対象外となる `.clickhouse/` ディレクトリを作成するほか、コミット可能なスキャフォールドとして `clickhouse/` (`tables/`、`materialized_views/`、`queries/`、`seed/`、`udfs/`、`config.d/`) および `postgres/` (`tables/`、`views/`、`functions/`、`queries/`、`seed/`) を作成します。再実行しても不足しているものだけが作成されるため、プロジェクトをクローンした後に一度実行してください。なお、`init` を実行せずにサーバーを起動することも可能で、その場合は現在のディレクトリに `.clickhouse/` が作成されます。

### ローカルサーバーを起動する {#managing-servers}

```bash
clickhousectl local clickhouse start dev --version latest   # Background start; waits for readiness
clickhousectl local clickhouse start dev --no-wait          # Return after spawning
clickhousectl local clickhouse start dev --foreground       # Run in the foreground
clickhousectl local clickhouse start dev --http-port 8124 --tcp-port 9001
clickhousectl local clickhouse list                         # ClickHouse servers in this project
clickhousectl local clickhouse list --global                # Servers across all projects
clickhousectl local status                                  # Every ClickHouse server and Postgres instance in this project
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse stop-all                     # Stop every ClickHouse server in this project
clickhousectl local clickhouse remove dev                   # Permanently delete a stopped server's data
```

`local ch` は `local clickhouse` の短縮形で、以前の名前である `local server` も別名として引き続き使用できます。名前付きの各サーバーは `.clickhouse/servers/<name>/data/` に独自のデータを持ち、サーバーを停止してもデータは次回の起動に備えて保持されます。名前を指定せずに起動すると `default` が使用されます。`default` がすでに実行中の場合は、新しい名前が生成されます。デフォルトのポートは HTTP が 8123、TCP が 9000 で、これらが使用中の場合は空いているポートが割り当てられます。

既存のサーバーを操作するコマンド (`stop`、`client`、`dotenv`、`local client`、`local udf --server`) は、名前を省略すると `default` を選択し、`default` がない場合は、プロジェクト内でそのエンジンを使う唯一のサーバーを選択します。サーバーが複数あり、`default` という名前のものがない場合、これらのコマンドは `server_selection_required` で失敗し、サーバー名の一覧を表示します。`remove` は推測を行いません。名前を指定しない場合は `default` のみを削除します。スクリプトでは名前を明示的に指定してください。

`--version` を指定すると、デフォルトを変更せずに、その起動で使用するバージョンを選択できます。バージョンを指定せず、デフォルトも設定されていない状態で単に起動すると、`latest` がインストールされますが、デフォルトには設定されません。デフォルトにするには、先に `local use latest` を実行してください。

### ローカルクライアントで SQL を実行する {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` は、指定した名前のサーバーに、そのサーバーを実行しているものと同じ ClickHouse バイナリを使って接続します。名前を指定しない場合は、上記の選択ルールに従います。`--` の後の引数は、そのまま `clickhouse client` に渡されます。JSON モードでも、出力と終了ステータスは `clickhouse client` のものになるため、スクリプトで使用する際は SQL の出力フォーマットを明示的に設定してください。

### カスタムサーバー構成 {#custom-config-files}

次の3つの場所にある XML または YAML 形式の部分設定で、組み込みのデフォルト設定をオーバーライドできます。

| 場所                                | 適用対象                                   | 適用タイミング               |
| --------------------------------- | -------------------------------------- | --------------------- |
| `~/.clickhouse/config.d/`         | このマシン上のすべてのサーバー                        | 起動時に毎回                |
| プロジェクトルートの `clickhouse/config.d/` | プロジェクト内のすべてのサーバー。バージョン管理にコミットすると共有できます | 起動時に毎回                |
| `~/.clickhouse/configs/`          | その設定で起動するサーバー                          | `--config NAME` 指定時のみ |

```bash
cat > clickhouse/config.d/logging.xml <<'XML'
<clickhouse>
    <logger><level>debug</level></logger>
</clickhouse>
XML
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local clickhouse configs          # List both config.d directories and the named configs
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse start dev --config analytics
```

起動のたびに表に記載された順序でマージされ、後のファイルが優先されるため、各ファイルには変更する設定だけを記述すれば十分です。編集内容や `--config` の指定の削除は、次回の起動時に反映されます。管理対象のデータパスとポートは、常に設定ファイルの値よりも優先されます。

### 接続情報を dotenv ファイルに書き込む {#dotenv}

```bash
clickhousectl local clickhouse dotenv dev                                     # Writes .env
clickhousectl local clickhouse dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` は実行中のサーバーが実際に使用しているポートを読み取り、`CLICKHOUSE_HOST`、`CLICKHOUSE_PORT`、`CLICKHOUSE_HTTP_PORT` を書き込みます。ユーザー、パスワード、データベースを指定した場合は、それらも書き込まれます。既存ファイル内のその他の行はそのまま保持されます。ファイルはアプリケーションの dotenv ローダーで読み込んでください。出力されたプレビューを `eval` することは絶対に避けてください。

### ローカル Postgres {#local-postgres}

ローカル Postgres は Docker 上で動作するため、Docker が起動している必要があります。Postgres 17 および 18 をサポートしており、`18-alpine` などのイメージタグも指定できます。新しいインスタンスではデフォルトで 18 が使用されます。

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres list                       # Postgres instances in this project
clickhousectl local postgres stop app
clickhousectl local postgres stop-all                   # Stop every Postgres instance in this project
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

`local pg` は `local postgres` の略です。インスタンスは名前とメジャーバージョンで識別されます。停止中のインスタンスを再開すると、元のポート、ユーザー、パスワード、データベースが再利用されるため、作成用のフラグは再開時には無効です。パスワードを指定しない場合は、ランダムなパスワードが生成されます。`.env.local` にはパスワードが含まれるため、バージョン管理の対象から除外してください。

### ローカル UDFs {#local-udfs}

`local udf` は、`clickhouse/udfs/<name>/` にある[実行可能 UDF](/ja/reference/functions/regular-functions/udf#executable-user-defined-functions) をローカルサーバーにデプロイします。`cloud udf` は同じディレクトリを Cloud にアップロードします ([Cloud の UDFs](#cloud-udfs) を参照) 。

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local clickhouse start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

`init` を除くすべてのコマンドで `--server <name>` を指定できます。指定しない場合は、[選択ルール](#managing-servers)に従ってサーバーが選ばれます。`deploy` は Cloud と同じ方法で `udf.json` を検証します。サーバーが稼働中であれば、関数を再読み込みし、関数が正しく読み込まれたことを確認します。`native` ランタイムをローカルにデプロイできるのは、Linux amd64 または arm64 のホストに限られます。詳しくは[ユーザー定義関数ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)を参照してください。

## 認証 {#authentication}

Cloudコマンドでは、次の2種類の認証情報のいずれかを使用します。

| 認証情報          | 利用可能な操作                                              | 保存先                                                                     |
| ------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- |
| ブラウザベースのOAuth | ユーザーのアイデンティティに基づき、所属するすべての組織で読み取り専用のCloud操作とSQLを実行可能 | `~/.clickhouse/tokens.json`にグローバルに保存され、プロジェクト間で共有                       |
| APIキー         | 対象は1つの組織に限定され、読み取りと書き込みの権限はキーのロールによって決まる             | 保存する場合はプロジェクトルートの`.clickhouse/credentials.json`に格納され、どのサブディレクトリからでも検出可能 |

ClickHouse Cloudのアカウントをまだお持ちでない場合は、`clickhousectl cloud auth signup`を実行すると、ブラウザでサインアップページが開きます。

### OAuth ログイン {#oauth-login}

```bash
clickhousectl cloud auth login
```

これによりブラウザが開き、OAuthデバイスフローが開始されます。トークンはグローバル設定として `~/.clickhouse/tokens.json` に保存され、自動的に更新されます。

<Note>
  OAuthは**読み取り専用**です。リソースを作成または変更するには、[APIキー](#api-key)でログインしてください。
</Note>

### APIキー {#api-key}

コマンドに必要なロールを付与した[APIキーを作成](/ja/products/cloud/features/admin-features/api/openapi)し、保存しておきます。対話型プロンプトで入力すれば、シークレットがシェルの履歴に残りません：

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

ログイン時にキーが検証され、そのキーに紐づくアイデンティティが表示されます。API に拒否されたキーは保存されず、コマンドは終了コード 4 で終了します。API に接続できない場合は、警告を表示したうえでキーが保存されます。

CI やその他の自動化環境では、キーを保存せず、シークレットマネージャー経由で注入してください。

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

開発時には、CLI はこれらの変数を現在のディレクトリにある `.env` ファイルからも読み取ります。現在のディレクトリに `.env` ファイルがない場合は、[プロジェクトのルート](#local)にあるファイルから読み取ります。`.env` はバージョン管理の対象外にしてください。

### 認証情報の確認と削除 {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` はどちらの種類の認証情報でも動作し、認証情報が拒否された場合は終了コード 4 で終了します。`status` は有効な認証情報がひとつもない場合でも終了コード 0 で終了することがあるため、アクセスできるかどうかの確認には `whoami` を使用してください。ログアウトしても環境変数は解除されず、`.env` も編集されません。

### 認証情報の優先順位 {#credential-precedence}

以下の順で、最初に利用可能な認証情報が使用されます。

1. `--api-key` および `--api-secret` フラグ
2. プロジェクトルートの `.clickhouse/credentials.json`
3. エクスポートされた環境変数
4. 現在のディレクトリの `.env` に定義された変数、見つからない場合はプロジェクトルートの `.env` に定義された変数
5. グローバル OAuth トークン

任意の `cloud` コマンドに `--debug` を指定すると、選択された認証情報の取得元と API URL が標準エラー出力に表示されます。

```bash
clickhousectl cloud clickhouse list --debug
```

### 組織を選択する {#organizations}

組織スコープのコマンドは、認証情報でアクセスできる組織が1つだけの場合に限り、その組織を自動的に選択します。それ以外の場合は、`--org-id` を指定するか、`--org-name` に組織名を正確に指定してください。どちらも指定しない場合、コマンドは終了コード 2 で終了し、各組織の ID と名前を一覧表示します：

```bash
clickhousectl cloud org list
clickhousectl cloud clickhouse list --org-id <org-id>
clickhousectl cloud clickhouse list --org-name "My Org"
```

ほとんどのリソース操作コマンドでは、位置引数として ID を指定するか、`--name` で完全一致する名前を指定します。アクセス許可、制限付きキー、ログアウト時のクリーンアップについては、[認証とアクセス](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md)を参照してください。

## Cloud {#cloud}

Cloud コマンドは [ClickHouse Cloud API](/ja/products/cloud/features/admin-features/api/api-overview) を呼び出します。作成および更新のリクエストは、API に受け付けられた時点で応答を返します。そのため、リソースが目的の状態になるまで `get` をポーリングしてください。

### サービス {#services}

`cloud clickhouse` は ClickHouse Cloudサービスを管理するコマンドです。`cloud ch` はその省略形です。また、以前の名前である `cloud service` も別名として引き続き使用できます。

```bash
clickhousectl cloud clickhouse create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud clickhouse create --name app-dev \
  --ip-allow 203.0.113.10/32 --dotenv .env.local          # Password goes only to the file
clickhousectl cloud clickhouse list
clickhousectl cloud clickhouse get <service-id>
clickhousectl cloud clickhouse start <service-id>
clickhousectl cloud clickhouse stop <service-id>
clickhousectl cloud clickhouse wake <service-id>             # Wake an idle service
clickhousectl cloud clickhouse reset-password <service-id>
clickhousectl cloud clickhouse delete <service-id>           # Must be stopped; --force stops it first
```

作成時に表示される初期パスワードは必ず保存してください。パスワードが返されるのはこの一度だけです。`--dotenv [file]`(デフォルトは `.env`)を指定した場合、パスワードはそのファイルにのみ書き込まれ、端末や JSON 出力には表示されません。作成コマンドはプロビジョニングの完了を待たずに返るため、ステートが `running` になるまで `get` を繰り返し実行してください。**`--ip-allow` を省略すると、すべての IP(`0.0.0.0/0`)が許可されます。** エントリは `IP_OR_CIDR=DESCRIPTION` の形式で指定します。`--region` にはプライベートリージョンを含む任意のリージョン ID を指定でき、その値は Cloud 側で検証されます。`--backup-id` を指定するとバックアップを新しいサービスに復元でき、`--byoc-id` を指定するとサービスを BYOC インフラストラクチャに配置できます。

実行中のサービスに接続するには、次のようにします。

```bash
clickhousectl cloud clickhouse client <service-id>                     # Interactive clickhouse client
clickhousectl cloud clickhouse client --name analytics -q "SELECT version()"
clickhousectl cloud clickhouse dotenv <service-id> --local             # Write .env.local, without a password
```

`client` はネイティブ TLS プロトコルで `clickhouse client` を起動し、ブラウザ経由で Cloud ユーザーとしてサインインするため、サービスのパスワードは不要です。ClickHouse 25.12 以降がインストールされている必要があり (`clickhousectl local install latest`) 、ブラウザで操作する人が必要となるため、CI やエージェントでは [`query`](#query-api) を使用してください。`dotenv` は `CLICKHOUSE_HOST`、`CLICKHOUSE_PORT`、`CLICKHOUSE_HTTP_PORT`、`CLICKHOUSE_USER`、`CLICKHOUSE_SECURE` を書き込みます。置き換えるのはこれらのキーのみのため、`create --dotenv` で書き込まれたパスワードはそのまま保持されます。

サービスの更新、スケーリング、設定:

```bash
clickhousectl cloud clickhouse update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud clickhouse update <service-id> --deletion-protection true
clickhousectl cloud clickhouse profile list --region us-east-1
clickhousectl cloud clickhouse scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud clickhouse scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud clickhouse scale <service-id> --profile v1-highmem-s
clickhousectl cloud clickhouse settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud clickhouse upgrade-window set <service-id> --weekday 0 --start-hour 6
```

レプリカあたりのメモリは4 GBの倍数で、無料サービスでは最大120 GB、有料サービスでは最大356 GBです。レプリカ数は最大50です。組織とwarehouseの制限により、これらの上限が低くなる場合があります。水平オートスケーリングを利用するには、組織で該当の機能を有効にする必要があります。`scale --profile`は、EnterpriseおよびBYOCの組織でインスタンスプロファイルを変更します。`update`は、指定したフラグのみを変更します。

削除保護 (`create --deletion-protection`、または`update --deletion-protection true|false`) を有効にすると、`--force`を指定しても、`delete`はエラーコード`deletion_protected`でサービスの削除を拒否します。削除する前に削除保護を無効にしてください。

その他のサービスコマンドグループには、`settings` (list、get、schema、set、unset)、`scaling-schedule`、`upgrade-window`、`replica-aware-routing` (ベータ)、`jwt-provider` (ベータ、Enterprise tier)、`snapshot` (ベータ)、`private-endpoint`、`query-endpoint`、`backup-config`、`prometheus` があります。詳しくは [Cloud サービスの作成と運用](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md) を参照してください。

### クエリ API {#query-api}

`cloud clickhouse query` は、ローカルの `clickhouse` バイナリやサービスのパスワードを必要とせず、HTTP 経由で 1 つの SQL ステートメントを実行します。

```bash
clickhousectl cloud clickhouse query <service-id> --query "SELECT version()"
clickhousectl cloud clickhouse query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud clickhouse query <service-id>
```

* **OAuth** は、ユーザー自身のアイデンティティで、読み取り専用の SQL アクセスを使用してクエリを実行します。サービスへのバインドは行われません。
* **APIキー：** クエリは常に有効な APIキーを使用します。必要に応じて、clickhousectl はそのキーをサービスのクエリ API エンドポイントに追加します。エンドポイントが存在しない場合は、`sql_console_admin` ロールを持つエンドポイントを作成します。既存のロール、オリジン、その他のキーのバインドは保持され、新しいキーは作成されません。この自動処理を行わずエラーで終了させるには、`--no-auto-enable` を指定してください。

バインドは書き込み操作のため、読み取り専用の APIキーは自身をバインドできません。その場合、クエリは `query_key_bind_forbidden` エラーと終了コード 1 で終了し、何も変更されません。書き込みアクセス権を持つキーを使い、`query-endpoint create <service-id> --role <role> --open-api-key <key-id>` で一度バインドしてください (サービスにエンドポイントがまだない場合は、`--allowed-origins '*'` も指定します) 。

クエリ API が受け付けるステートメントは、リクエストごとに 1 つです。SQL の実行が続いていても約 30 秒でタイムアウトすることがあるため、書き込みを再試行する前に結果を確認してください。複数のステートメントを含むスクリプト、一括ロード、長時間実行されるクエリには、[`cloud clickhouse client`](#services) を使用してください。サービスの IP 許可リストは直接接続を制限しますが、プロキシ経由のクエリ API へのアクセスは制限しません。アイドル状態のサービスにクエリを実行すると、そのサービスは起動します。停止中のサービスは `cloud clickhouse start` で起動する必要があります。

サービスのクエリ API エンドポイント、名前付き SQL エンドポイント、保存クエリを管理します：

```bash
clickhousectl cloud clickhouse query-endpoint get <service-id>
clickhousectl cloud clickhouse query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` は、エンドポイントに紐付けられたすべてのキーのロールを置き換えます。詳細は [SQL とクエリ API の動作](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md)を参照してください。

### Managed Postgres {#postgres-services}

`cloud postgres`(別名 `cloud pg`)は [ClickHouse Managed Postgres](/ja/products/managed-postgres/overview) を管理するためのコマンドです。GCP はプライベートプレビュー段階です。

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> --ha-type sync --standby-count 2
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres update <postgres-id> --deletion-protection true
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

AWSでは、`m6gd.large`、`c6gd.xlarge`、`r6gd.xlarge` などのサイズを利用できます。GCPでは、`--provider gcp` とともにGCPのリージョンと `c4-standard-lssd-4` などのサイズを指定します。

`create` で返されるパスワードと接続文字列を保存してください。それ以降の `get` の応答には認証情報は含まれず、新しい認証情報を取得するには `reset-password` を使用する必要があります。`sslmode=verify-full` とCAファイルを指定し、`psql` で接続します。

**作成時にアクセスフラグを省略すると、Postgres (5432) とPgBouncer (6432) へのアクセスが、すべてのIPv4アドレスとIPv6アドレスから許可されます。** ルールごとに `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` を1つ指定するか、ルールを設定しない場合は `--block-public-access` を指定します。ルールを1つでも指定すると、指定したルールのみが適用されます。

`--standby-count` は、`create` または `update` でホットスタンバイの数を設定します。`--ha-type none` では0、`async` では1、`sync` では1または2を指定できます。削除保護機能を利用できる組織で削除保護が有効になっている場合、`--deletion-protection false` を設定するまで、APIは `delete` を拒否します。AWSでのプライベート接続には、PrivateLinkのエンドポイントサービス (ベータ) を管理する `private-endpoint` (create、get、update、delete) を使用します。各VPC エンドポイントから接続するには、事前に `private-endpoint update --add-vpc-endpoint` でそのエンドポイントを承認する必要があります。

監視と復旧：

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` は OAuth にのみ対応しているため、より優先度の高い APIキーの認証ソースが有効になっている間は失敗します。監視には `metrics`、`slow-queries`、`prometheus` を使用します。また、`logs`、`metrics`、`slow-queries`、`backup list` では、ID の代わりに `--name` も指定できます。`restore` は、`--ip-allow` または `--block-public-access` を指定しない限り、復元元の現在の IPv4 アクセスルールを復元済みサービスにコピーします。復元およびレプリカの作成時には、パスワードは返されません。`promote` と `switchover` は、リクエストが受け付けられた時点で応答を返します。promote の実行後は、レプリカが `isPrimary: true` を返すまで `postgres get --json` をポーリングしてください。詳しくは [Managed Postgres ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md)を参照してください。

### ClickPipes {#clickpipes}

`cloud clickpipe` は、オブジェクトストレージ、Kafka、Kinesis、Pub/Sub、Postgres、MySQL、MongoDB、BigQuery からデータを取り込みます。作成とスキーマ検出には、APIキーと稼働中の宛先サービスが必要です。ソースごとに専用の `clickpipe create <source>` サブコマンドが用意されており、`--help` を付けて実行すると利用可能なフラグを確認できます。

IAM role を使用して S3 からファイルを読み込みます。まずスキーマを検出して内容を確認し、保存しておいた検出結果の出力をもとにパイプを作成します:

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" --json > discovery.json
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --columns-from discovery.json
```

`--columns-from` は検出されたフィールドを格納先カラムに変換するため、先にファイルを編集して不要なフィールドを削除しておいてください。オブジェクトストレージ、Kafka、Kinesis、Pub/Sub の作成には、`--columns-from` と 1 つ以上の `--column name:type` のいずれか、またはその両方が必要です。`--column` を指定すると、ファイルから取得したカラムに加えてカラムが追加されます。

CDC (変更データキャプチャ)  を使用して Postgres を複製します。TLS はデフォルトで検証されます。Managed Postgres ソースの場合は、その CA をエクスポートして指定してください。

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud clickhouse query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` は `ReplacingMergeTree` テーブルを作成するため、現在の状態を読み取るには `FINAL WHERE _peerdb_is_deleted = 0` を使用します。Postgres および MySQL の作成コマンドでは `--use-json-native-format true` を指定すると、JSON カラムを `String` ではなく ClickHouse ネイティブの `JSON` 型として保存できます (ClickHouse 25.3 以降が必要で、組織に対してこの機能が有効になっている必要があります) 。Kafka パイプの手順はオブジェクトストレージと同じパターンです。同じソース用フラグを指定して `clickpipe schema-discover kafka` を実行し、その後 `--column` または `--columns-from` でカラムを指定します。

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

BigQueryのパイプは、デフォルトでスナップショットを実行します。CDC (変更データキャプチャ)  を使用するには、`--replication-mode cdc`と`--replication-method`を指定し、`--table-mapping-json`でテーブルごとにウォーターマークカラムまたはイベント関数を指定します。同期のスケジュールは、`--sync-cron`または`--sync-interval-seconds`で設定します。既存のパイプは次のように操作します。

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

CDC (変更データキャプチャ)  パイプは、`update` の前に `Paused` 状態にしておく必要があります。パイプを停止し、`Paused` になるまで `get` でポーリングしてから更新してください。サービスが更新処理の一環としてパイプを再開する場合があるため、`start` は `get` がまだ `Paused` を返す場合にのみ実行してください。`--start-paused` は、オブジェクトストレージ、Kafka、Kinesis、Pub/Sub で使用できます。その他のコマンドグループには、`cdc-scaling`、`context get` (GCP Workload Identity の準備状態とプリンシパル) 、`reverse-private-endpoint` があります。詳しくは、[ClickPipes ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md)および [ClickPipe 設定リファレンス](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md)を参照してください。

### ClickStack {#clickstack}

`cloud clickstack` は、既存の [Self-managed ClickHouse Observability](/ja/clickstack/self-configured/deployment/managed) サービス上のソース、ダッシュボード、アラート、Webhook、保存済み検索、ロールを管理します。リソースは JSONファイルで指定します (`--file` を使用するか、stdin から読み込む場合は `-` を指定) 。読み取りは OAuth で認証できますが、書き込みには APIキーが必要です。

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**ClickStack を更新するたびに、リソース全体が置き換えられます。** `get --json` で現在の状態を保存し、変更したフィールドだけでなく定義全体を送信してください。詳しくは [ClickStack ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md) を参照してください。

### Cloud での UDFs {#cloud-udfs}

`cloud udf` は、組織単位の実行可能 UDF とそのバージョン、およびサービスとの関連付けを管理します。`deploy` は、`local udf` でテストしたディレクトリをアップロードし、ビルドの完了を待ってから、そのバージョンをサービスに関連付け、デプロイが完了するまで待機します：

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud clickhouse query <service-id> --query "SELECT my_udf(1)"
```

各手順を手動で実行するには、`udf create`、`udf version create`、`udf attach` (アイドル状態のサービスには `--wake` を指定) 、`udf detach`、`udf delete` を使用します。これらのコマンドはリクエストが受理された時点で戻るため、`udf get` と `udf attachment get` でポーリングして状態を確認してください。読み取り操作は OAuth に対応していますが、書き込み操作には APIキーが必要です。詳しくは、[ユーザー定義関数ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)を参照してください。

### 組織とアクセス {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

`cloud org`サブコマンドでは`--org-id`を指定し、IDを位置引数として指定することはできません。`org usage`で確認できる期間は最大31日間です。`org`には、`quota`、`balance`、`notification-types`、`role` (カスタム組織ロール) 、`preview` (プレビュー機能の一覧表示と有効・無効の切り替え、ベータ) 、`byoc` (BYOC インフラストラクチャの管理。ClickHouseの担当者がアクセスできるタイミングを制御する`byoc access`を含む、ベータ) もあります。通知機能はベータです。

メンバー、招待、APIキーを管理するには：

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

`member notification-settings` (ベータ) は、メンバー自身の通知設定のオーバーライドを一覧表示・更新します。サービスの作成とは異なり、**`key create` で `--ip-allow` を省略すると、すべてのネットワークアクセスが拒否されます**。シークレットは一度だけ表示されます。`key list` は、`--all` を指定しない限り、1 ページのみを返します。`key update` では、省略したフラグに対応する設定は維持され、`--clear-expiry`、`--clear-roles`、`--clear-ip-allow` を指定すると、それぞれに対応する設定が削除されます。

### バックアップ {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud clickhouse create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud clickhouse backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
clickhousectl cloud backup bucket get <service-id>
```

復元すると、常に新しいサービスが作成されます。`cloud backup bucket` (get、create、update、delete) は、プロバイダー固有のJSONファイルを使用して、ユーザーが用意したバックアップ用バケットを設定します。[Cloud サービスガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore)のバックアップに関するセクションを参照してください。

## JSON 出力 {#json-output}

ローカル、Cloud、`skills`、`update`、`telemetry` など、構造化されたデータを返すコマンドでは `--json` を指定できます。

```bash
clickhousectl cloud clickhouse list --json
clickhousectl cloud key list --all --json
clickhousectl local clickhouse list --json
```

CLI は、コーディングエージェント (Claude Code、Cursor、Codex、Gemini CLI、Goose、Devin など、または `AI_AGENT` を設定する任意のツール) を検出すると、自動的に JSON を選択します。SQL クライアントとネイティブクライアントは、それぞれ固有のフォーマットを使用します。`cloud clickhouse query` は JSON モードでは `JSONEachRow` を返し、`local client` の出力は常にネイティブ形式です。クエリ出力をパースするスクリプトでは、`--format` を明示的に指定してください。エージェントが検出された場合でも人間向けの出力を維持するには、`CLICKHOUSECTL_AUTO_JSON=0` を設定してください。ただし、`--json` を明示的に指定すると JSON が選択されます。

`clickhouse create`、`postgres create`、`clickpipe start` などの非同期 Cloud コマンドは、実行すべきポーリング操作を示す `next` オブジェクトを JSON 出力に追加します。このオブジェクトには、`command` (解決済みの ID と `--org-id` を含む) 、監視対象の `field`、完了を示す `until` の値、`fail_on` の値、推奨される `interval_seconds` が含まれます。コマンド自体は、API がリクエストを受け付けるとすぐに制御を返します。

JSON モードでは、実行時エラーは、安定したエラーコードを表す `code` と `message` を持つオブジェクトとして stderr に出力されます。

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

メッセージではなく、`error.code` に基づいて処理を分岐してください。使用方法に関するエラーは引き続きテキストで表示され、終了コードは 2 となり、何も送信されません。出力形式とエラーコードについては、[自動化と出力仕様](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md)を参照してください。

## 終了コード {#exit-codes}

| コード | 意味                                                         |
| --- | ---------------------------------------------------------- |
| `0` | 成功。非同期の Cloud 操作では、リクエストが受け付けられたことを示し、処理の完了を意味するものではありません  |
| `1` | エラー。リクエストを拒否する HTTP 403 (コード `http_4xx`) を含みます             |
| `2` | 使用方法のエラー。無効なフラグ値や、パース後の検証で処理が成功し得ないと判定された入力を含みます。何も送信されません |
| `3` | `skills` ピッカーなどの対話型プロンプトがキャンセルされました                        |
| `4` | 認証が必要か、認証が拒否されました。OAuth を使用して書き込みを試みた場合も含みます               |

`local client`、`local postgres client` など、ネイティブクライアントに処理を引き渡す場合は、そのクライアントの終了ステータスがそのまま返されます。

## エージェントスキル {#skills}

[公式の ClickHouse agent skills](https://github.com/ClickHouse/agent-skills) をコーディングエージェントにインストールします。

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

スキルはデフォルトで現在のプロジェクトにインストールされます。`--global` を指定すると、ホームディレクトリにインストールされます。共有の `.agents/skills/` ディレクトリは常に含まれます。端末がない場合は、`--agent`、`--all`、`--detected-only` のいずれかを指定する必要があります。サポートされているエージェント名を確認するには、`clickhousectl skills --help` を実行してください。

## 検索とフィードバック {#search-and-feedback}

```bash
clickhousectl search ip allow                   # Find commands and flags by keyword
clickhousectl search idle timeout --limit 10
clickhousectl feedback "cloud clickhouse create should accept a --wait flag"
```

`search <words>` は、コマンド名、説明、フラグ、エージェントのコンテキストを検索し、一致度の高いコマンドを一覧表示します (デフォルトは5件) 。一致するものがない場合は、結果を表示せずに終了コード0で終了します。

`feedback` は、入力や確認を求めずに、短いメッセージ (最大500文字) をclickhousectlチームに送信します。CLIでできなかったことや、期待していた動作を伝えるために使用してください。`--json` などのオプションはメッセージの前に指定し、認証情報、SQL、ホスト名、個人データは含めないでください。Cloudの認証情報を使用する場合、メッセージにはその認証情報が属する組織のIDが含まれます。[フィードバックで送信される情報](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/feedback.md)を参照してください。

## 自己更新 {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

`update` は、インストールスクリプト、ダウンロード、または Cargo でインストールしたものを置き換えます。npm、uv、pipx、pip でインストールした場合は、終了コード 1 で終了し、代わりに実行すべきパッケージマネージャーのアップグレードコマンドを表示します。

CLI はバックグラウンドでも更新を確認します。確認は 24 時間に 1 回を上限に行われ (失敗した場合は 1 時間後に再試行されます) 、新しいバージョンが利用可能になると通知を表示します。確認と通知を無効にするには、`CLICKHOUSECTL_NO_UPDATE_CHECK=1` を設定してください。

## テレメトリー {#telemetry}

`clickhousectl` は、開発に役立てるために匿名の使用状況データを収集します。初回実行時は通知を表示するだけで、データは送信しません。収集を無効化しない限り、次回以降の実行時から収集が始まります。

各イベントには以下が含まれます。

* コマンドのパスと、明示的に渡されたフラグおよび引数の**名前**。値は含まれません
* 実行結果と終了コード
* コマンドの入力ミスに対して CLI が提案したコマンド名またはフラグ名。実際に入力した内容は含まれません
* 実行時の障害に関する、あらかじめ定められたカテゴリの情報：障害が発生したステージと種別、許可リストに含まれる HTTP ステータス、および再試行、プロビジョニング状態、所要時間のカテゴリ
* CLI のバージョン、OS とアーキテクチャ、CI 環境で実行されているかどうか、および検出されたコーディングエージェント

引数値、SQL、認証情報、リソース識別子、`--` 以降の引数、エラーメッセージは一切記録されません。インストール ID やデバイス ID も使用しません。

収集を無効化するには：

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

`CHCTL_TELEMETRY_DEBUG=1` を設定すると、何も送信せずにペイロードを標準エラー出力に表示できます。オプトアウトしても、明示的に実行したときにのみ送信を行う [`feedback`](#search-and-feedback) は無効になりません。詳しくは、[テレメトリーの詳細](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md)を参照してください。
