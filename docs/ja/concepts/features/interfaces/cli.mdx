`clickhousectl` (別名 `chctl`) は、ローカル開発から ClickHouse Cloud までをカバーする ClickHouse 公式の CLI です。端末で操作するユーザー、スクリプト、コーディングエージェントのいずれからも利用できます。

`clickhousectl` では、次のことができます。

* ローカルの ClickHouse バージョンのインストールと切り替え、分離されたローカルサーバーの実行、SQL の実行
* Docker を利用した Postgres のローカル実行
* ClickHouse Cloud サービスの作成、設定、スケーリング、バックアップ、クエリ実行
* [ClickHouse Managed Postgres](/ja/products/managed-postgres/overview) サービスの作成、監視、設定、復元
* オブジェクトストレージ、Kafka、Kinesis、Pub/Sub、Postgres、MySQL、MongoDB、BigQuery をソースとする ClickPipes の作成と運用
* [Managed ClickStack](/ja/clickstack/deployment/managed) サービス上のソース、ダッシュボード、アラート、Webhook、保存済み検索、ロールの管理
* 実行可能 UDF のローカル開発と ClickHouse Cloud へのデプロイ
* 組織のメンバー、招待、APIキー、ロールの管理
* 公式の ClickHouse agent skills のコーディングエージェントへのインストール

このページでは代表的な例を紹介します。すべてのコマンドとフラグについての正式なリファレンスは `clickhousectl <command> --help` です。ほとんどのコマンドのヘルプの末尾には `CONTEXT FOR AGENTS` ブロックがあり、Cloud コマンドではそのコマンドに必要な APIキーのアクセス許可も記載されています。タスクごとの手順については、各セクションに記載されているガイドへのリンクを参照してください。Cloud を中心とした概要については、[ClickHouse CLI](/ja/products/cloud/features/cli) を参照してください。

## インストール {#installation}

`clickhousectl` は macOS および Linux 上で動作し、ARM64 と x86&#95;64 の両アーキテクチャに対応しています。

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

このスクリプトは `~/.local/bin/clickhousectl` をインストールし、`chctl` という別名を作成します。`~/.local/bin` が `PATH` に含まれていることを確認してください。

パッケージマネージャーを使ってインストールすることもできます。

| ツール                               | コマンド                            |
| --------------------------------- | ------------------------------- |
| npm                               | `npm install -g clickhousectl`  |
| uv                                | `uv tool install clickhousectl` |
| pipx                              | `pipx install clickhousectl`    |
| pip                               | `pip install clickhousectl`     |
| cargo-binstall                    | `cargo binstall clickhousectl`  |
| Cargo (ソースコードからビルド、Rust 1.94 以降)  | `cargo install clickhousectl`   |

`chctl` という別名が作成されるのは、インストールスクリプトまたは npm でインストールした場合のみです。既存のインストールを更新するには、`clickhousectl update` を実行してください ([自己更新](#self-update)を参照) 。

## 要件 {#requirements}

* Docker (ローカルの Postgres を使用する場合のみ)
* Cloud コマンドを使用する場合は、[ClickHouse Cloud](https://clickhouse.com/cloud) アカウントが必要です。閲覧系のコマンドは、ブラウザ経由の OAuth 認証 (`cloud auth login`) で実行できます。リソースの作成や変更を行うには [APIキー](/ja/products/cloud/features/admin-features/api/openapi) が必要です。詳しくは [認証](#authentication) を参照してください。

## ローカル {#local}

ローカルコマンドは現在のディレクトリを対象に動作します。各プロジェクトのサーバーデータは `.clickhouse/` に保存され、ClickHouse バイナリは `~/.clickhouse/` に置かれてすべてのプロジェクトで共有されます。CLI は親ディレクトリを検索しないため、ローカルコマンドはプロジェクトのルートディレクトリで実行してください。ワークフロー全体については、[ローカル開発ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md)を参照してください。

### インストールとバージョンの選択 {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
```

| セレクター         | 意味                                                   |
| ------------- | ---------------------------------------------------- |
| `latest`      | 最新の ClickHouse ビルド。インストール、使用、起動のたびにリモートで確認されます (推奨)  |
| `stable`      | 最新の安定版リリース                                           |
| `lts`         | 最新の長期サポートリリース                                        |
| `26.8`        | 指定に一致する最新のリリース                                       |
| `26.8.1.1760` | 指定したバージョンそのもの                                        |

`local use` は、必要に応じてバージョンをインストールし、以降のサーバー起動時のデフォルトに設定したうえで、`~/.local/bin/clickhouse` にシンボリックリンクを作成します。これにより、`clickhouse client` と `clickhouse local` を `PATH` 経由で利用できるようになります。シンボリックリンクを作成しない場合は `--no-global` を指定してください。そのパスに通常のファイルがすでに存在する場合、そのファイルには手を加えません。

`local remove` では、デフォルトのバージョンや、いずれかのプロジェクトで実行中のサーバーが使用しているバージョンは削除できません。`--force` を指定すると、該当するサーバーを停止してからバージョンを削除し、デフォルト設定とシンボリックリンクも解除します。

### プロジェクトを初期化する {#initializing-project}

```bash
clickhousectl local init
```

`init` の実行は任意です。ランタイムデータ用に git の管理対象外となる `.clickhouse/` ディレクトリを作成するほか、コミット可能な SQL スキャフォールドとして `clickhouse/` (`tables/`、`materialized_views/`、`queries/`、`seed/`、`udfs/`) と `postgres/` (`tables/`、`views/`、`functions/`、`queries/`、`seed/`) を作成します。再実行した場合は、不足しているものだけが作成されます。

### ローカルサーバーを起動する {#managing-servers}

```bash
clickhousectl local server start dev --version latest   # Background start; waits for readiness
clickhousectl local server start dev --no-wait          # Return after spawning
clickhousectl local server start dev --foreground       # Run in the foreground
clickhousectl local server start dev --http-port 8124 --tcp-port 9001
clickhousectl local server list                         # Servers in this project
clickhousectl local server list --global                # Servers across all projects
clickhousectl local server stop dev
clickhousectl local server stop-all                     # Stop all ClickHouse and Postgres servers in this project
clickhousectl local server remove dev                   # Permanently delete a stopped server's data
```

名前付きの各サーバーは `.clickhouse/servers/<name>/data/` に専用のデータを持ち、サーバーを停止してもデータは次回の起動に備えて保持されます。名前を指定しない場合、最初のサーバーは `default` になります。`default` がすでに実行中であれば、新しい名前が自動生成されます。デフォルトのポートは HTTP が 8123、TCP が 9000 で、これらが使用中の場合は空いているポートが割り当てられます。

`--version` を指定すると、デフォルトを変更せずに、その起動時に使用するバージョンを選択できます。バージョンを指定せず、デフォルトも設定されていない状態で起動すると、`latest` がインストールされますが、デフォルトには設定されません。`latest` をデフォルトにするには、先に `local use latest` を実行してください。

### ローカルクライアントで SQL を実行する {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` は、名前付きサーバーを実行しているのと同じ ClickHouse バイナリを使用して、そのサーバーに接続します (デフォルト名: `default`) 。`--` 以降の引数は、そのまま `clickhouse client` に渡されます。出力と終了ステータスは JSON モードでも `clickhouse client` のものがそのまま返されるため、スクリプトで使用する場合は SQL の出力フォーマットを明示的に指定してください。

### カスタムサーバー構成 {#custom-config-files}

XML または YAML 形式の部分的な設定ファイルを `~/.clickhouse/configs/` に配置し、サーバー起動時にその名前を指定して選択します:

```bash
mkdir -p ~/.clickhouse/configs
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local server configs
clickhousectl local server stop dev
clickhousectl local server start dev --config analytics
```

このファイルは組み込みのデフォルト設定の上にオーバーレイとして適用されるため、変更したい設定だけを記述すれば十分です。この指定は保持されません。後で `--config` を付けずに起動すると、オーバーレイは解除されます。管理対象のデータパスとポートは、設定ファイルの値よりも常に優先されます。

### 接続情報を dotenv ファイルに書き込む {#dotenv}

```bash
clickhousectl local server dotenv dev                                     # Writes .env
clickhousectl local server dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` は、実行中のサーバーが実際に使用しているポートを読み取り、`CLICKHOUSE_HOST`、`CLICKHOUSE_PORT`、`CLICKHOUSE_HTTP_PORT` を書き込みます。ユーザー、パスワード、データベースを指定した場合は、それらも併せて書き込まれます。既存のファイルにあるその他の行はそのまま保持されます。ファイルはアプリケーションの dotenv ローダーで読み込んでください。出力されたプレビューを `eval` で実行してはいけません。

### ローカル Postgres {#local-postgres}

ローカル Postgres は Docker 上で動作するため、Docker が起動している必要があります。Postgres 17 と 18 がサポートされており、`18-alpine` などのイメージタグも使用できます。新しいインスタンスではデフォルトで 18 が使用されます。

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres stop app
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

インスタンスは、名前とメジャーバージョンによって識別されます。停止したインスタンスを再開すると、元のポート、ユーザー、パスワード、データベースがそのまま再利用されるため、作成時に指定したフラグは再開時には反映されません。パスワードを指定しない場合は、ランダムなパスワードが生成されます。`.env.local` にはパスワードが含まれるため、バージョン管理の対象から除外してください。

### ローカル UDFs {#local-udfs}

`local udf` は、`clickhouse/udfs/<name>/` 内の[実行可能 UDF](/ja/reference/functions/regular-functions/udf#executable-user-defined-functions) をローカルサーバーにデプロイします。`cloud udf` は同じディレクトリを Cloud にアップロードします ([Cloud での UDFs](#cloud-udfs) を参照) 。

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local server start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

`init` 以外のすべてのコマンドは `--server <name>`(デフォルトは `default`)を指定できます。`deploy` は Cloud と同じ方法で `udf.json` を検証します。サーバーが稼働中の場合は、関数を再読み込みし、関数が読み込まれたことを確認します。`native` ランタイムをローカルにデプロイできるのは、Linux の amd64 または arm64 ホストのみです。詳しくは [ユーザー定義関数ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md) を参照してください。

## 認証 {#authentication}

Cloud のコマンドでは、次の 2 種類の認証情報のいずれかを使用します。

| 認証情報          | ケーパビリティ                                                            | 保存先                                                 |
| ------------- | ------------------------------------------------------------------ | --------------------------------------------------- |
| Browser OAuth | ユーザー自身のアイデンティティ: 所属するすべての組織に対して、読み取り専用の Cloud 操作と読み取り専用の SQL を実行可能 | `~/.clickhouse/tokens.json` (グローバル、プロジェクト間で共有)      |
| APIキー         | 1 つの組織にスコープが限定され、読み取りと書き込みの可否はキーのロールによって決まる                        | 保存した場合は `.clickhouse/credentials.json` (プロジェクトローカル) |

まだClickHouse Cloudのアカウントをお持ちでない場合は、`clickhousectl cloud auth signup` を実行すると、ブラウザでサインアップページが開きます。

### OAuthログイン {#oauth-login}

```bash
clickhousectl cloud auth login
```

これにより、OAuth デバイスフローのためにブラウザが開きます。トークンは `~/.clickhouse/tokens.json` にグローバルに保存され、自動的にリフレッシュされます。

<Note>
  OAuth は **読み取り専用** です。リソースを作成または変更するには、[API キー](#api-key) でログインしてください。
</Note>

### APIキー {#api-key}

コマンドの実行に必要なロールを付与した[APIキーを作成](/ja/products/cloud/features/admin-features/api/openapi)し、保存します。対話型プロンプトで入力すれば、シークレットがシェルの履歴に残りません：

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

ログイン時にはキーが検証され、そのキーに紐づくアイデンティティが表示されます。API に拒否されたキーは保存されず、コマンドは終了コード 4 で終了します。API に到達できない場合は、警告を表示したうえでキーが保存されます。

CI やその他の自動化環境では、キーを保存せずに、シークレットマネージャー経由でキーを注入してください。

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

開発時には、CLI は現在のディレクトリにある `.env` ファイルからもこれらの変数を読み取ります。`.env` はバージョン管理の対象に含めないでください。

### 認証情報の確認と削除 {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` はどちらの種類の認証情報でも動作し、認証情報が拒否された場合は終了コード 4 で終了します。`status` は有効な認証情報が 1 つもない場合でも終了コード 0 を返すことがあるため、アクセスできるかどうかの確認には `whoami` を使用してください。ログアウトしても、環境変数の設定は解除されず、`.env` も変更されません。

### 認証情報の優先順位 {#credential-precedence}

利用可能なソースのうち、最初に見つかったものが使用されます:

1. `--api-key` および `--api-secret` フラグ
2. `.clickhouse/credentials.json`
3. エクスポートされた環境変数
4. 現在のディレクトリにある `.env` 内の変数
5. グローバル OAuth トークン

任意の `cloud` コマンドに `--debug` を指定すると、選択された認証情報のソースと API URL が stderr に出力されます:

```bash
clickhousectl cloud service list --debug
```

### 組織を選択する {#organizations}

組織スコープのコマンドが組織を自動的に選択するのは、認証情報でアクセスできる組織が 1 つだけの場合に限られます。それ以外の場合は、`--org-id` を指定するか、`--org-name` に組織名を正確に指定してください:

```bash
clickhousectl cloud org list
clickhousectl cloud service list --org-id <org-id>
clickhousectl cloud service list --org-name "My Org"
```

ほとんどのリソースコマンドでは、位置引数として ID を指定するか、`--name` で正確な名前を指定します。アクセス許可、制限付きキー、ログアウト時のクリーンアップについては、[認証とアクセス](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md)を参照してください。

## Cloud {#cloud}

Cloud コマンドは [ClickHouse Cloud API](/ja/products/cloud/features/admin-features/api/api-overview) を呼び出します。作成および更新のリクエストは、API に受け付けられた時点で応答が返されます。そのため、リソースが目的のステートに達するまで `get` をポーリングしてください。

### サービス {#services}

```bash
clickhousectl cloud service create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud service list
clickhousectl cloud service get <service-id>
clickhousectl cloud service start <service-id>
clickhousectl cloud service stop <service-id>
clickhousectl cloud service wake <service-id>             # Wake an idle service
clickhousectl cloud service reset-password <service-id>
clickhousectl cloud service delete <service-id>           # Must be stopped; --force stops it first
```

作成時に表示される初期パスワードは必ず控えておいてください。このパスワードが返されるのは一度だけです。作成コマンドはプロビジョニングの完了を待たずに終了するため、ステートが `running` になるまで `get` を繰り返し実行してください。**`--ip-allow` を省略すると、すべての IP (`0.0.0.0/0`) が許可されます。** エントリは `IP_OR_CIDR=DESCRIPTION` の形式で指定します。`--backup-id` を使用するとバックアップを新しいサービスに復元でき、`--byoc-id` を使用するとサービスを BYOC インフラストラクチャに配置できます。

サービスの更新、スケーリング、設定は次のように行います:

```bash
clickhousectl cloud service update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud service profile list --region us-east-1
clickhousectl cloud service scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud service scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud service settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud service upgrade-window set <service-id> --weekday 0 --start-hour 6
```

レプリカあたりのメモリは 4 GB の倍数で指定し、上限は無償サービスで 120 GB、有償サービスで 356 GB です。レプリカは最大 50 個まで設定できます。ただし、組織や warehouse の制限によって、これらの上限がさらに低くなる場合があります。水平オートスケーリングを利用するには、組織で該当する機能が有効になっている必要があります。`update` は、指定したフラグのみを変更します。

サービス関連のその他のコマンドグループとして、`settings` (list、get、schema、set、unset)、`scaling-schedule`、`upgrade-window`、`replica-aware-routing` (ベータ)、`snapshot` (ベータ)、`private-endpoint`、`backup-config`、`prometheus` があります。詳しくは [Cloud サービスの作成と運用](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md) を参照してください。

### クエリ API {#query-api}

`cloud service query` を使うと、ローカルの `clickhouse` バイナリやサービスのパスワードを用意しなくても、HTTP 経由で SQL ステートメントを 1 つ実行できます。

```bash
clickhousectl cloud service query <service-id> --query "SELECT version()"
clickhousectl cloud service query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud service query <service-id>
```

* **OAuth** では、読み取り専用の SQL アクセス権限を持つユーザー自身のアイデンティティでクエリが実行されます。サービスには何もバインドされません。
* **APIキー:** 初回の呼び出し時に、clickhousectl はユーザーのAPIキーをサービスのクエリ API エンドポイントに追加します。エンドポイントが存在しない場合は、`sql_console_admin` ロールを付与して作成します。既存のロール、オリジン、その他のキーのバインドはそのまま保持され、新しいキーは作成されません。CLI がエンドポイントを変更した場合は、stderr に `Binding the authenticated API key to the Query API endpoint for service '<name>'...` が出力されます。この処理を行わずにエラーとするには、`--no-auto-enable` を指定します。

以前のバージョンの CLI で保存されたサービス単位のキーがある場合、そのサービスでは引き続きそのキーが優先されます。API がそのキーを拒否した場合は、`cloud service repair-query-key <service-id>` を実行して明示的に置き換えてください。

クエリ API が受け付けるのは、1 リクエストにつき 1 ステートメントのみです。SQL の実行が継続していても約 30 秒でタイムアウトすることがあるため、書き込みを再試行する前に結果を確認してください。複数ステートメントを含むスクリプト、一括ロード、長時間実行されるクエリには `clickhouse client` を使用してください。サービスの IP 許可リストで制限されるのは直接接続のみで、プロキシ経由のクエリ API の経路は対象外です。アイドル状態のサービスにクエリを実行するとサービスが起動しますが、停止中のサービスは `cloud service start` で起動する必要があります。

サービスのクエリ API エンドポイント、名前付き SQL エンドポイント、保存クエリを管理します:

```bash
clickhousectl cloud service query-endpoint get <service-id>
clickhousectl cloud service query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` は、エンドポイントに紐付けられたすべてのキーのロールを置き換えます。詳細は [SQL とクエリ API の動作](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md)を参照してください。

### Managed Postgres {#postgres-services}

`cloud postgres` は [ClickHouse Managed Postgres](/ja/products/managed-postgres/overview) を管理するためのコマンドです。これらのコマンドはベータ版で、GCP はプライベートプレビュー段階です。

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

AWS のサイズには `m6gd.large`、`c6gd.xlarge`、`r6gd.xlarge` などがあります。GCP では `--provider gcp` を指定し、GCP のリージョンと `c4-standard-lssd-4` などのサイズを指定します。

`create` で返されるパスワードと接続文字列は必ず保存してください。以降の `get` の応答では認証情報は返されず、新しい認証情報を取得するには `reset-password` を使用するしかありません。`psql` で接続する際は、`sslmode=verify-full` と CA ファイルを使用してください。

**create 時にアクセス関連のフラグを省略すると、Postgres (5432) と PgBouncer (6432) に対して、すべての IPv4 アドレスおよび IPv6アドレスからのアクセスが許可されます。** ルールごとに `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` を 1 つずつ指定するか、ルールを設定しない場合は `--block-public-access` を指定してください。ルールを 1 つでも指定すると、指定したルールのみが適用されます。

監視と復旧:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` は OAuth 認証のみに対応しているため、より優先度の高い APIキーのソースが有効になっている間は失敗します。監視には `metrics`、`slow-queries`、`prometheus` を使用します。`restore` は、`--ip-allow` または `--block-public-access` を指定しない限り、ソースの現在の IPv4 アクセスルールを復元済みサービスにコピーします。復元およびレプリカの作成では、パスワードは返されません。`promote` と `switchover` は、リクエストが受け付けられた時点で応答を返します。promote の実行後は、レプリカが `isPrimary: true` を返すまで `postgres get --json` をポーリングしてください。詳しくは [Managed Postgres ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md) を参照してください。

### ClickPipes {#clickpipes}

`cloud clickpipe` は、オブジェクトストレージ、Kafka、Kinesis、Pub/Sub、Postgres、MySQL、MongoDB、BigQuery からデータを取り込みます。ClickPipe の作成とスキーマ検出には、APIキーと稼働中の宛先サービスが必要です。ソースごとに専用の `clickpipe create <source>` サブコマンドが用意されています。使用できるフラグは、`--help` を付けて実行すると確認できます。

IAM role を使用して S3 からファイルを読み込みます。まずスキーマを検出してから、カラムを選択します。

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN"
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --column 'event_id:Int64' --column 'event_type:String'
```

CDC (変更データキャプチャ) を使用して Postgres を複製します。TLS はデフォルトで検証されます。Managed Postgres ソースを使用する場合は、その CA 証明書をエクスポートして指定します：

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud service query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` は `ReplacingMergeTree` テーブルを作成するため、現在のステートを読み取る際は `FINAL WHERE _peerdb_is_deleted = 0` を指定してください。Kafka パイプも同じ手順です。同じソース用フラグを指定して `clickpipe schema-discover kafka` を実行し、続いてカラムを渡します。

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

BigQuery のパイプは、デフォルトではスナップショットを実行します。CDC (変更データキャプチャ) を使用する場合は、`--replication-mode cdc` と `--replication-method` を指定し、`--table-mapping-json` でテーブルごとにウォーターマークカラムまたはイベント関数を指定します。同期のスケジュールは `--sync-cron` または `--sync-interval-seconds` で設定します。既存のパイプは、次のように操作します。

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

CDC パイプは、`update` の前に `Paused` 状態にしておく必要があります。パイプを停止し、`Paused` になるまで `get` でポーリングしてから更新してください。サービスが更新処理の一環としてパイプを再開する場合があるため、`start` は `get` がまだ `Paused` を返す場合にのみ実行してください。`--start-paused` は、オブジェクトストレージ、Kafka、Kinesis、Pub/Sub で使用できます。その他のコマンドグループには、`cdc-scaling`、`context get` (GCP のワークロードアイデンティティの準備状態とプリンシパル) 、`reverse-private-endpoint` があります。詳細は [ClickPipes ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) および [ClickPipe 設定リファレンス](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md) を参照してください。

### ClickStack {#clickstack}

`cloud clickstack` は、既存の [Managed ClickStack](/ja/clickstack/deployment/managed) サービスのソース、ダッシュボード、アラート、Webhook、保存済み検索、ロールを管理します。リソースはJSONファイルで指定します (`--file` を使用するか、stdin から読み込む場合は `-` を指定) 。読み取りは OAuth 認証に対応していますが、書き込みにはAPIキーが必要です。

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**ClickStack を更新するたびに、リソース全体が置き換えられます。** `get --json` で現在のステートを保存し、変更したフィールドだけでなく定義全体を送信してください。詳しくは [ClickStack ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md) を参照してください。

### Cloud の UDFs {#cloud-udfs}

`cloud udf` は、組織スコープの実行可能 UDF とそのバージョン、およびサービスへの関連付けを管理します。`deploy` は、`local udf` でテストしたディレクトリをアップロードしてビルドの完了を待ち、そのバージョンを関連付けたうえで、デプロイが完了するまで待機します。

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud service query <service-id> --query "SELECT my_udf(1)"
```

各ステップを個別に実行するには、`udf create`、`udf version create`、`udf attach` (アイドルステートのサービスに対しては `--wake` を指定) 、`udf detach`、`udf delete` を使用します。これらのコマンドはリクエストが受理された時点で処理を返すため、`udf get` と `udf attachment get` をポーリングしてステートを確認してください。読み取り操作では OAuth を利用できますが、書き込み操作には APIキーが必要です。詳しくは[ユーザー定義関数ガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)を参照してください。

### 組織とアクセス {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

`cloud org` のサブコマンドでは `--org-id` を指定します。ID を位置引数として渡すことはできません。`org usage` で取得できる期間は最大 31 日です。`org` には、`quota`、`balance`、`notification-types`、`role`(カスタム組織ロール)、`byoc`(BYOC インフラストラクチャ)のサブコマンドもあります。通知機能はベータ版です。

メンバー、招待、APIキーを管理します:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

**`key create` で `--ip-allow` を省略すると、すべてのネットワークアクセスが拒否されます**。この点はサービス作成時とは異なります。シークレットは一度しか表示されません。`key list` は、`--all` を指定しない限り 1 ページ分のみを返します。`key update` では、省略したフラグの設定はそのまま維持されますが、`--clear-expiry`、`--clear-roles`、`--clear-ip-allow` を指定すると、対応する設定が削除されます。

### バックアップ {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud service create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud service backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
clickhousectl cloud backup bucket get <service-id>
```

復元を行うと、常に新しいサービスが作成されます。`cloud backup bucket` (get、create、update、delete) を使用すると、プロバイダー固有のJSONファイルをもとに、ユーザー所有のバックアップバケット (BYOB) を設定できます。詳しくは、[Cloud サービスガイド](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore)のバックアップのセクションを参照してください。

## JSON 出力 {#json-output}

構造化されたデータを返すコマンドでは `--json` を指定できます。対象には、ローカル、Cloud、`skills`、`update`、`telemetry` の各コマンドが含まれます。

```bash
clickhousectl cloud service list --json
clickhousectl cloud key list --all --json
clickhousectl local server list --json
```

CLI がコーディングエージェント (Claude Code、Cursor、Codex、Gemini CLI、Goose、Devin、または `AI_AGENT` を設定する任意のツールなど) を検出すると、自動的に JSON が選択されます。ただし、SQL クライアントとネイティブクライアントはそれぞれ独自のフォーマットを維持します。`cloud service query` は JSON モードでは `JSONEachRow` を返し、`local client` の出力は常にネイティブフォーマットです。クエリの出力をパースするスクリプトでは、`--format` を明示的に指定してください。

JSON モードでは、ランタイムエラーは、安定した `code` と `message` を含むオブジェクトとして stderr に出力されます。

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

分岐処理はメッセージではなく `error.code` に基づいて行ってください。使用方法に関するエラーは従来どおりテキストで出力され、終了コードは 2 になります。出力形式とエラーコードについては、[自動化と出力の契約](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md)を参照してください。

## 終了コード {#exit-codes}

| コード | 意味                                                             |
| --- | -------------------------------------------------------------- |
| `0` | 成功。Cloud の非同期操作の場合は、リクエストが受け付けられたことを示すもので、完了したことを意味するものではありません |
| `1` | エラー                                                            |
| `2` | 使用方法のエラー (無効なフラグ値を含む)                                          |
| `3` | キャンセル                                                          |
| `4` | 認証が必要、または認証が拒否された (OAuth での書き込みを試みた場合を含む)                      |

`local client`、`local postgres client` など、ネイティブクライアントに処理を引き渡すコマンドでは、そのクライアント自身の終了ステータスがそのまま返されます。

## エージェントスキル {#skills}

[公式の ClickHouse agent skills](https://github.com/ClickHouse/agent-skills) をコーディングエージェントにインストールします。

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

スキルはデフォルトでは現在のプロジェクトにインストールされますが、`--global` を指定するとホームディレクトリにインストールされます。共有の `.agents/skills/` ディレクトリは常にインストール対象に含まれます。端末を使用しない環境では、`--agent`、`--all`、`--detected-only` のいずれかを指定する必要があります。サポートされているエージェント名を確認するには、`clickhousectl skills --help` を実行してください。

## セルフアップデート {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

また、CLI はバックグラウンドで更新の有無を確認し (最大で 24 時間に 1 回) 、新しいバージョンが利用可能な場合は通知を表示します。

## テレメトリー {#telemetry}

`clickhousectl` は、開発の参考にするため匿名の使用状況データを収集します。初回実行時は通知が表示されるだけで、データは一切送信されません。無効化しない限り、次回以降の実行から収集が始まります。

各イベントには以下の情報が含まれます。

* コマンドパスと、明示的に指定されたフラグおよび引数の**名前**(値は一切含みません)
* 実行結果と終了コード
* コマンドを打ち間違えた場合は、CLI が提案したコマンド名またはフラグ名(入力した内容は一切含みません)
* ランタイムエラー発生時は、範囲が限定されたカテゴリ情報(失敗したステージと種類、許可リストに含まれる HTTP ステータス、再試行・プロビジョニングステート・所要時間の各カテゴリ)
* CLI のバージョン、OS とアーキテクチャ、CI 上での実行かどうか、検出されたコーディングエージェント

引数値、SQL、認証情報、リソース識別子、`--` 以降の引数、エラーメッセージが記録されることはありません。インストール ID やデバイス ID も使用しません。

オプトアウトするには:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

`CHCTL_TELEMETRY_DEBUG=1` を設定すると、データを一切送信せずにペイロードを stderr に出力します。詳しくは [テレメトリーの詳細](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md) を参照してください。
