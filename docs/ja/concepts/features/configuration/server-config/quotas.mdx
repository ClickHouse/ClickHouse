<Info>
  **ClickHouse Cloud の QUOTA**

  ClickHouse Cloud では QUOTA がサポートされていますが、作成には [DDL 構文](/ja/reference/statements/create/quota) を使用する必要があります。以下で説明する XML 設定の方法は **サポートされていません**。
</Info>

QUOTA を使用すると、一定期間にわたるリソース使用量を制限したり、リソースの使用状況を追跡したりできます。
QUOTA はユーザー設定で構成し、通常は &#39;users.xml&#39; に設定します。

システムには、単一のクエリ複雑性を制限する機能もあります。[クエリ複雑性に関する制限](/ja/concepts/features/configuration/settings/query-complexity) のセクションを参照してください。

クエリ複雑性に関する制限とは異なり、QUOTA には次の特徴があります。

* 単一のクエリを制限するのではなく、一定期間内に実行される一連のクエリに制限を課します。
* 分散クエリ処理において、すべてのリモートサーバーで消費されたリソースを計上します。

それでは、QUOTA を定義する &#39;users.xml&#39; ファイル内のセクションを見ていきましょう。

```xml
<!-- Quotas -->
<quotas>
    <!-- Quota name. -->
    <default>
        <!-- Restrictions for a time period. You can set many intervals with different restrictions. -->
        <interval>
            <!-- Length of the interval. -->
            <duration>3600</duration>

            <!-- Unlimited. Just collect data for the specified time interval. -->
            <queries>0</queries>
            <query_selects>0</query_selects>
            <query_inserts>0</query_inserts>
            <errors>0</errors>
            <result_rows>0</result_rows>
            <read_rows>0</read_rows>
            <execution_time>0</execution_time>
        </interval>
    </default>
</quotas>
```

デフォルトでは、QUOTA は使用量を制限せずに、1時間ごとのリソース消費量を追跡します。
各インターバルごとに計算されたリソース消費量は、各リクエストの後にサーバーログに出力されます。

```xml
<statbox>
    <!-- Restrictions for a time period. You can set many intervals with different restrictions. -->
    <interval>
        <!-- Length of the interval. -->
        <duration>3600</duration>

        <queries>1000</queries>
        <query_selects>100</query_selects>
        <query_inserts>100</query_inserts>
        <written_bytes>5000000</written_bytes>
        <written_rows>100000</written_rows>
        <errors>100</errors>
        <result_rows>1000000000</result_rows>
        <read_rows>100000000000</read_rows>
        <execution_time>900</execution_time>
        <failed_sequential_authentications>5</failed_sequential_authentications>
    </interval>

    <interval>
        <duration>86400</duration>

        <queries>10000</queries>
        <query_selects>10000</query_selects>
        <query_inserts>10000</query_inserts>
        <errors>1000</errors>
        <result_rows>5000000000</result_rows>
        <result_bytes>160000000000</result_bytes>
        <read_rows>500000000000</read_rows>
        <result_bytes>16000000000000</result_bytes>
        <execution_time>7200</execution_time>
    </interval>
</statbox>
```

`statbox` QUOTA では、1 時間ごとおよび 24 時間ごと (86,400 秒) に制限が設定されます。このインターバルは、実装で定義された固定の時点を起点として計算されます。言い換えると、24 時間のインターバルは必ずしも午前 0 時に始まるわけではありません。

このインターバルが終了すると、蓄積されたすべての値はクリアされます。次の 1 時間については、QUOTA の計算が最初からやり直されます。

制限できる項目は次のとおりです。

`queries` – リクエストの総数。

`query_selects` – SELECT リクエストの総数。

`query_inserts` – INSERT リクエストの総数。

`errors` – 例外を発生させたクエリの数。

`result_rows` – 結果として返された行の総数。

`result_bytes` - 結果として返された行の合計サイズ。

`read_rows` – すべてのリモートサーバーでクエリを実行するために、テーブルから読み取られた行の総数。

`read_bytes` - すべてのリモートサーバーでクエリを実行するために、テーブルから読み取られた合計サイズ。

`written_bytes` - 書き込み操作の合計サイズ。

`written_rows` - `INSERT` クエリによって書き込まれた行の総数。

`execution_time` – 秒単位のクエリの総実行時間 (実時間) 。

`failed_sequential_authentications` - 連続した認証エラーの総数。

`queries_per_normalized_hash` – 任意の単一の正規化クエリにおける実行回数の最大値。正規化クエリとは、リテラルをプレースホルダーに置換したクエリのことで、たとえば `SELECT 1` と `SELECT 2` は同一の正規化クエリとみなされます。この上限は、異なる正規化されたクエリパターンごとに個別に追跡されます。

上記の定義済みの量に加えて、イベント名をタグとして指定することで、任意のプロファイルイベント ([system.events](/ja/reference/system-tables/events) テーブルを参照) に上限を設定できます。例:

```xml
<interval>
    <duration>86400</duration>
    <!-- At most 100000 S3 GET requests and 50 failed queries per day. -->
    <S3GetObject>100000</S3GetObject>
    <FailedQuery>50</FailedQuery>
</interval>
```

同じ内容は、DDL構文を使って次のように記述することもできます。

```sql
CREATE QUOTA s3_reads FOR INTERVAL 1 day MAX S3GetObject = 100000, FailedQuery = 50 TO my_user;
```

事前定義された量とは異なり、プロファイルイベントはクエリごとに 1 回、クエリが終了した時点 (成功・エラーを問わず) で計上されます。上限を超えたクエリも最後まで実行でき、以降のクエリはインターバルが終了するまで拒否されます。消費量は [system.quotas&#95;usage](/ja/reference/system-tables/quotas_usage) テーブルの `profile_events` 列で確認できます。クエリ外で蓄積されたプロファイルイベント (たとえばバックグラウンドマージによるもの) はクォータに計上されません。

分散クエリの場合、リモートサーバーがイニシエーターに報告するプロファイルイベントは、ローカルのものとあわせてクエリを開始したユーザーのクォータに計上されます。リモートサーバーは、クエリ内の設定、その `SETTINGS` 句、またはリモートサーバー上のユーザーの設定制約で `send_profile_events` がどのように指定されていても、分散クエリでは常にこれらの報告を送信するため、ユーザーがこれを無効にすることはできません。これには `Distributed` テーブルまたは `remote` テーブル関数への同期 `INSERT` も含まれ、この場合リモートサーバーはすべてのデータを受信した時点でプロファイルイベントを報告します。一方、`distributed_foreground_insert = 0` の `Distributed` テーブルによるバックグラウンド送信は、どのユーザークエリにも属さないため計上されません。[非同期挿入](/ja/reference/settings/session-settings/async-insert#async_insert)の遅延 flush は、`SYSTEM FLUSH ASYNC INSERT QUEUE` のように flush を強制したクエリではなく、挿入を送信したユーザーのクォータに、挿入時のチェックと同じバケットで計上されます (`ip_address` または `forwarded_ip_address` をキーとするクォータではクライアントアドレスのバケット、`normalized_query_hash` をキーとするクォータでは送信された `INSERT` のバケット)。分散 `INSERT` を受信したリモートサーバーがそれを非同期挿入としてキューに入れた場合、そのサーバーでの遅延 flush はそのサーバー上で、イニシエーターが接続に使用するユーザーのクォータに計上され、イニシエーターには報告されません。なお、二重に計上されることはありません。分散 `INSERT` のイニシエーターがリモートサーバーに送信する行は `InsertedRows` と `InsertedBytes` に 1 回だけ計上され、リモートサーバーがそれ以外に書き込む分 (たとえば materialized view の宛先テーブルへの書き込み) は追加で計上されます。

いずれか 1 つ以上の時間間隔で上限を超えた場合、どの制限をどのインターバルで超過したか、および新しいインターバルがいつ始まるか (クエリを再び送信できるようになる時刻) を示すメッセージとともに例外がスローされます。

<Note>
  **クォータの計上から除外されるクエリ**

  クォータを使い切った状態でもクォータの設定と使用量を確認できるよう、以下のいずれかのシステムテーブルのみを読み取る `SELECT` クエリはクォータに計上されず、クエリの複雑さに関する制限も適用されません。

  * `system.quotas`
  * `system.quota_limits`
  * `system.quota_usage`
  * `system.quotas_usage`
  * `system.one`
</Note>

クォータでは「クォータキー」機能を使用して、複数のキーごとにリソース使用量を個別に集計できます。以下にその例を示します。

```xml
<!-- For the global reports designer. -->
<web_global>
    <!-- keyed – The quota_key "key" is passed in the query parameter,
            and the quota is tracked separately for each key value.
        For example, you can pass a username as the key,
            so the quota will be counted separately for each username.
        Using keys makes sense only if quota_key is transmitted by the program, not by a user.

        You can also write <keyed_by_ip />, so the IP address is used as the quota key.
        (But keep in mind that users can change the IPv6 address fairly easily.)

        Instead of <keyed_by_ip /> you can use <keyed_by_forwarded_ip />, so the address
        from the X-Forwarded-For header is used as the quota key.

        For both <keyed_by_ip /> and <keyed_by_forwarded_ip /> you can additionally specify
        <ipv4_prefix_bits> and <ipv6_prefix_bits> to group clients by subnet instead of by a
        single address: the IP address is masked to the given prefix length before being used
        as the quota key. For example, <ipv4_prefix_bits>24</ipv4_prefix_bits> shares one bucket
        across a /24 IPv4 subnet, and <ipv6_prefix_bits>64</ipv6_prefix_bits> across a /64 IPv6
        subnet. These elements can only be used together with <keyed_by_ip /> or
        <keyed_by_forwarded_ip />.
    -->
    <keyed />
</web_global>
```

正規化クエリハッシュをキーとしてクォータを設定することもできます。これにより、異なる各クエリパターンごとに独立したクォータバケットが割り当てられます。XML設定では、`<keyed_by_normalized_query_hash />` と記述します:

```xml
<my_quota>
    <keyed_by_normalized_query_hash />
    <interval>
        <duration>3600</duration>
        <queries>100</queries>
    </interval>
</my_quota>
```

同じことはDDL構文でも記述できます。

```sql
CREATE QUOTA my_quota KEYED BY normalized_query_hash FOR INTERVAL 1 hour MAX queries = 100 TO my_user;
```

この例では、ユーザーは1時間あたり、個々の正規化クエリごとに最大100回まで実行できます。`SELECT number FROM numbers(1)` と `SELECT number FROM numbers(2)` は同じバケットを共有します (正規化形式が同じであるため) が、`SELECT number, number FROM numbers(1)` は別のバケットを使用します。

クォータ は、設定 の &#39;users&#39; セクションでユーザーに割り当てられます。&quot;アクセス権&quot; のセクションを参照してください。

分散クエリ処理では、累積値はリクエスト元のサーバーに保存されます。そのため、ユーザーが別のサーバーに移ると、そのサーバーのクォータは &quot;最初から&quot; になります。

サーバーを再起動すると、クォータ はリセットされます。
