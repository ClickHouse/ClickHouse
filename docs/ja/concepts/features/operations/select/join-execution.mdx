ほとんどの JOIN アルゴリズムは、2 つのフェーズで実行されます。

* **ビルドフェーズ。** ClickHouse は一方の入力をすべて読み込み、ハッシュテーブルやソート済みブロックの集合など、照合に適したデータ構造に格納します。この入力をビルド側と呼びます。
* **プローブフェーズ。** ClickHouse はもう一方の入力をブロック単位でストリーミングし、各行をビルドフェーズで作成したデータ構造と照合します。この入力をプローブ側と呼びます。

プローブフェーズは、ビルドフェーズが完了するまで開始されません。そのため、JOIN に必要なメモリ量は主にビルド側のサイズによって決まります。

デフォルトでは、JOIN の右側がビルド側、左側がプローブ側になります。ただし、このモデルに当てはまらないアルゴリズムもあります。[`direct` アルゴリズム](/ja/concepts/features/operations/select/join-algorithms#direct) では、右側がすでにキー・バリュー構造として存在するため、ビルドフェーズがありません。[`full_sorting_merge` アルゴリズム](/ja/concepts/features/operations/select/join-algorithms#full-sorting-merge) は、両方の入力をソートしてからマージします。[`ie_join` アルゴリズム](/ja/concepts/features/operations/select/join-algorithms#ie-join) は、両方の入力を蓄積してから結合します。

## クエリプランナーの動作 {#query-planner-behavior}

クエリプランナーは、結合アルゴリズムの実行前に JOIN の入力を変更することがあります。適用される最適化は次のとおりです。

### build-side の自動選択 {#automatic-build-side-selection}

バージョン 24.12 以降、プランナーは JOIN の 2 つの入力を入れ替えて、小さい方の入力をビルド側にできます。プランナーは両方の入力の推定行数を比較し、左側の入力の方が小さいと推定された場合に、ハッシュベースの JOIN で入力を入れ替えます。この動作は [`query_plan_join_swap_table`](/ja/reference/settings/session-settings/query-plan#query_plan_join_swap_table) 設定で制御できます。

入力が入れ替えられた場合、`LEFT` JOIN は `RIGHT` JOIN として実行されます (逆の場合も同様です) 。入れ替え後の順序は `EXPLAIN` の出力で確認できます。

### 複数テーブルにおけるJOINの順序変更 {#multi-table-join-reordering}

同一のサブクエリ内で複数のテーブルを結合するクエリでは、プランナーがテーブルの結合順序を変更できます。[`query_plan_optimize_join_order_limit`](/ja/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_limit) 設定では、プランナーによる順序変更の対象となるテーブル数の最大値を指定します。デフォルト値は `10` です。`1` を指定すると、順序変更は無効になります。

### カラム統計の利用 {#use-of-column-statistics}

build-side の選択と JOIN の順序変更は、行数の推定値に依存します。カラム統計がない場合、プランナーはプライマリインデックスから推定値を算出しますが、この推定値は不正確になる場合があります。[カラム統計](/ja/reference/engines/table-engines/mergetree-family/mergetree#column-statistics)がある場合、プランナーは統計を用いてフィルタの選択度や結合キーのカーディナリティを推定します。

[`use_statistics`](/ja/reference/settings/session-settings/use-statistics#use_statistics) 設定は、オプティマイザが統計を使用するかどうかを制御します。[`materialize_statistics_on_insert`](/ja/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert) 設定は、新たに挿入されたデータについて統計を構築するかどうかを制御します。

### フィルタのプッシュダウン {#filter-pushdown}

[`query_plan_filter_push_down`](/ja/reference/settings/session-settings/query-plan#query_plan_filter_push_down) が有効な場合、プランナーは `WHERE` の条件を JOIN の下位に移動し、ビルドフェーズおよびプローブフェーズの前に各入力がフィルタされるようにします。

* 一方の入力のカラムのみを参照する条件は、その入力に適用されます。
* `LEFT` JOIN の場合、条件は右側の入力にはプッシュダウンされません。`RIGHT` JOIN の場合、条件は左側の入力にはプッシュダウンされません。
* 一方の入力の結合キーに対する条件は、もう一方の入力にも適用できます。一致したすべての行において、両方の入力のキーカラムの値は等しいためです。
* Dictionary のようにデータが既に格納されている右側や、`ASOF` JOIN の右側には、条件はプッシュダウンされません。
