JOIN のメモリは 2 種類の設定によって制御されます。ほとんどのアルゴリズムでは、JOIN のステートが大きくなりすぎると、ハードリミットによってクエリが停止されます。一方、スピル threshold に達すると、JOIN はステートの一部をディスクに書き出し、クエリの処理を継続できます。

## ハードリミット {#hard-limits}

* [`max_rows_in_join`](/ja/reference/settings/session-settings/max-rows#max_rows_in_join) は、JOIN の右側のデータ構造 (通常はハッシュテーブル) に格納される行数を制限します。
* [`max_bytes_in_join`](/ja/reference/settings/session-settings/max-bytes#max_bytes_in_join) は、同じデータ構造のサイズをバイト単位で制限します。
* [`join_overflow_mode`](/ja/reference/settings/session-settings/join#join_overflow_mode) は、いずれかの制限に達したときの動作を定義します。

どちらの制限も [`Join` テーブルエンジン](/ja/reference/engines/table-engines/special/join) にも適用されます。クエリに複数の JOIN が含まれる場合、ClickHouse は JOIN ごとに制限をチェックします。

ハッシュベースのアルゴリズム (ディスクへスピルするアルゴリズムを含む) では、制限に達するとクエリが停止し、JOIN がスピルすることはありません。そのため、制限がスピル threshold 以下に設定されている場合、通常は JOIN がスピルする前にクエリが停止します。

この動作は、次の 2 つの設定で変更できます。

* [`enable_adaptive_memory_spill_scheduler`](/ja/reference/settings/session-settings/enable#enable_adaptive_memory_spill_scheduler) は、クエリのメモリ逼迫時に、対象となるプロセッサをディスクへスピルします。JOIN の場合、この設定はもともとスピル可能な JOIN にのみ適用されます。具体的には、[スピル threshold](#spill-thresholds) が 0 以外に設定された `hash`、`parallel_hash`、`auto` の JOIN、`grace_hash` の JOIN、および一時ストレージが設定済みの場合のブロックネステッドループのフォールバックです。こうした JOIN は、スピル threshold やハードリミットに達する前にスピルされる場合があります。
* [`legacy_join_size_limits_trigger_spilling`](/ja/reference/settings/session-settings/other#legacy_join_size_limits_trigger_spilling) は、バージョン 26.10 より前の動作を復元します。この動作では、ハードリミットに達してもクエリは停止せず、JOIN のうちすでにディスク上で実行されている部分がさらにスピルします。この設定を有効にすると、`grace_hash` はスピル threshold を無視し、ハードリミットのみに基づいてスピルします。`hash` と `parallel_hash` は従来どおりスピル threshold でスピルを開始し、インメモリフェーズの間はハードリミットを上限として扱います。

その他のアルゴリズムでは、制限の動作が異なります。

* [`inequality`](/ja/concepts/features/operations/select/join-algorithms#inequality) では、制限は両側の入力を合わせた累積量に適用されます。
* [ブロックネステッドループのフォールバック](/ja/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback) では、制限はディスクに退避されたブロックを含む、マテリアライズされた右側全体に適用されます。
* [`partial_merge`](/ja/concepts/features/operations/select/join-algorithms#partial-merge) では、制限に達してもクエリは停止せず、代わりに実行戦略が切り替わります。JOIN は、ソート済みの右側のブロックをディスクへ書き込み始めます。

## スピル threshold {#spill-thresholds}

* [`max_bytes_before_external_join`](/ja/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) は、ハッシュベースの JOIN の右側に対するスピル threshold を、バイト単位の絶対値で設定します。
* [`max_bytes_ratio_before_external_join`](/ja/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join) は、クエリの `max_memory_usage`、ならびにユーザーおよびサーバーのメモリ制限に対する残りメモリの比率として、スピル threshold を設定します。メモリ制限が設定されていない場合、この比率は無効です。

両方の設定を指定した場合は、算出されたしきい値のうち小さい方が適用されます。これらのしきい値は、`hash`、`parallel_hash`、`grace_hash`、`auto` 値、およびブロックネステッドループのフォールバックに適用されます。利用するには、一時データパスが設定されている必要があります。

## スピルの仕組み {#how-spilling-works}

スピルに対応する各アルゴリズムは、ステートのうちそれぞれ異なる部分を一時ファイルに書き込みます。

* **`hash` と `parallel_hash`。** JOIN はハッシュテーブルをメモリ上に構築します。右側がスピル threshold を超えると、JOIN は `grace_hash` に切り替わります。右側の行を JOIN キーのハッシュに基づいてバケットに分割し、1 つのバケットをメモリ上に保持して、残りのバケットを一時ファイルに書き込みます。左側の行も同じハッシュ関数で分割されます。メモリ上のバケットに属する行はその場で結合され、それ以外の行は一時ファイルに書き込まれます。左側の読み込みが完了すると、ClickHouse は残りのバケットのペアを 1 つずつ読み込んで結合します。
* **`grace_hash`。** JOIN は最初のブロックから同じ手順で処理されます。あるバケットのハッシュテーブルがしきい値を超えると、バケット数は `grace_hash_join_max_buckets` を上限として倍増します。この上限を超えると、クエリはエラーで失敗します。
* **`full_sorting_merge`。** 各入力のソート処理は、`max_bytes_before_external_sort` または `max_bytes_ratio_before_external_sort` を超えると、ソート済みブロックを一時ファイルに書き込みます。その後、これらのソート済みファイルがマージされます。
* **`partial_merge`。** 右側がハードリミットに達すると、ソート済みの右側ブロックとその min-max 索引が一時ファイルに書き込まれます。
* **ブロックネステッドループのフォールバック。** スピル threshold に達すると、右側のブロックはメモリ上で圧縮されたうえで一時ファイルに書き込まれます。

[`direct`](/ja/concepts/features/operations/select/join-algorithms#direct) および [`inequality`](/ja/concepts/features/operations/select/join-algorithms#inequality) アルゴリズムはディスクへのスピルを行いません。

一時ファイルは、[`tmp_path`](/ja/reference/settings/server-settings/settings/tmp#tmp_path)、[`tmp_policy`](/ja/reference/settings/server-settings/settings/tmp#tmp_policy)、または [`temporary_data_in_cache`](/ja/reference/settings/server-settings/settings/temporary-data#temporary_data_in_cache) サーバー設定で指定されたストレージに書き込まれます。一時ファイルの読み書きによってディスク I/O が発生するため、スピルする JOIN は、同じ JOIN をメモリ上だけで実行する場合よりも低速になります。

`ExternalJoinWritePart`、`ExternalJoinCompressedBytes`、`ExternalJoinUncompressedBytes` の各プロファイルイベントは、JOIN が書き込んだ一時ファイルの数と、そこに含まれるデータ量を示します。これらは [`system.query_log`](/ja/reference/system-tables/query_log) の `ProfileEvents` カラムで確認できます。
