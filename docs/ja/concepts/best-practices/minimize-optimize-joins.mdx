このページでは、可能な限り JOIN を避け、JOIN が必要な場合にはそのコストを抑えるための具体的な指針を示します。構文とセマンティクスについては、[`JOIN` 句リファレンス](/ja/reference/statements/select/join)を参照してください。実行アルゴリズムとその選択方法については、[テーブルの結合](/ja/concepts/features/operations/select/joining-tables)を参照してください。

## JOINはできるだけ避ける {#prefer-avoiding-joins}

ClickHouse は多種多様な JOINの種類とアルゴリズムをサポートしています。ただし、JOIN は本質的に、単一の非正規化されたテーブルに対するクエリよりもコストが高くなります。非正規化では、計算処理をクエリ実行時から INSERT 時または前処理時に移すため、実行時のレイテンシを大幅に低減できることがよくあります。リアルタイム処理やレイテンシに敏感な分析クエリでは、**非正規化を強く推奨します**。

一般に、次のような場合は非正規化を検討してください。

* テーブルの更新頻度が低い、またはバッチ更新を許容できる。
* 関係が多対多ではなく、カーディナリティも極端に高くない。
* クエリされるカラムが一部に限られており、つまり特定のカラムは非正規化の対象から外せる。
* [Flink](/ja/integrations/connectors/data-ingestion/apache-flink) のような上流システムに処理を移し、リアルタイムの enrichment やフラット化を管理できる体制がある。

すべてのデータを非正規化する必要はありません。頻繁にクエリされる属性に絞って対応してください。また、サブテーブル全体を複製する代わりに、集計をインクリメンタルに計算する方法として [materialized view](/ja/concepts/best-practices/use-materialized-views) も検討してください。スキーマ更新がまれで、レイテンシが重要な場合、非正規化はパフォーマンス面で最も優れたトレードオフをもたらします。

ClickHouse でのデータの非正規化について詳しくは、[こちら](/ja/guides/clickhouse/data-modelling/denormalization) を参照してください。

## JOIN が必要な場合 {#when-joins-are-required}

<Tip>
  **ClickHouse 26.8 以降を使用してください。**

  複数テーブルの JOIN の順序変更と、オプティマイザによる利用可能な統計情報の活用は、25.12 以降デフォルトで有効になっています。[カラム統計](/ja/reference/settings/session-settings/allow-statistics#allow_statistics)は 26.3 で一般提供となり、デフォルトで有効になりました。26.8 以降は、対象となるテーブルで[挿入時にカラム統計をマテリアライズ](/ja/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert)する動作がデフォルトとなり、コストベースの JOIN 最適化における推定精度が向上しています。
</Tip>

JOIN のパフォーマンスを向上させるには、以下のベストプラクティスに従ってください。

* **一致が 1 件あれば十分な場合は `ANY` JOIN を使用します。** 通常の JOIN は一致するすべての行を返すため、キーが重複しているとデカルト積が生じる可能性があります。1 件の一致で十分な場合は、`LEFT ANY JOIN` または `ANY INNER JOIN` を使用して、結果のサイズとメモリ使用量を削減してください。
* **JOIN の前に両側のデータを絞り込みます。** `WHERE` 句および `JOIN ON` 句で選択性の高い条件を適用してください。ClickHouse は可能な限りフィルタをプッシュダウンしますが、明示的にサブクエリを使用すれば、JOIN の前に各入力を確実にフィルタできます。
* **`INNER JOIN` の代わりに `IN` を検討します。** 相手テーブルにキーが存在するかどうかを確認するだけでよいクエリでは、`IN` サブクエリを使うとその意図を直接表現でき、`INNER JOIN` の結果を生成するよりもメモリ使用量を抑えられる場合があります。
* **繰り返し使用するルックアップには `Join` テーブルエンジンを使用します。** [`Join` テーブルエンジン](/ja/reference/engines/table-engines/special/join)は、宣言された JOINの種類、strictness、キーに基づいて、事前計算済みのインメモリ構造を保持します。ClickHouse Cloud では、`MergeTree` をバックエンドテーブルとする `SharedJoin` として実装されており、`Join(ANY, LEFT, key)` を使うとキー単位で更新可能なルックアップを実現できます。詳細は [Fast, updatable lookups with the Join table engine](https://clickhouse.com/blog/join-table-engine) を参照してください。
* **可能であればテーブルの sorting key で結合します。** 両方のテーブルが JOIN キーで物理的にソートされている場合、`full_sorting_merge` はソート処理を省略でき、メモリ使用量を削減できます。実行計画を確認したうえで、代表的なデータを用いてこのアルゴリズムとデフォルトのアルゴリズムをベンチマークで比較してください。
* **ディスクへのスピルが発生する JOIN は避けます。** JOIN の中間状態をディスクにスピルすればクエリをメモリ制限内に収められますが、通常はディスク I/O によってレイテンシが増加します。`grace_hash`、`partial_merge`、`full_sorting_merge` などの一部の JOIN アルゴリズムは、中間状態をディスクにスピルしてクエリ実行を継続できます。ただし、ディスクアクセスによって結合処理が大幅に遅くなる可能性があるため、これらの JOIN アルゴリズムは慎重に使用してください。スピルに頼る前に、入力の行数やカラム数を減らす、可能な場合は `ANY` セマンティクスを使用する、あるいはデータモデルを見直すといった対策を検討してください。
* **必要に応じてデフォルト値を不一致のマーカーとして利用します。** デフォルトの [`join_use_nulls = 0`](/ja/reference/settings/session-settings/join#join_use_nulls) では、外部 JOIN で一致しなかったカラムはそのデータ型のデフォルト値で埋められるため、`Nullable` でラップされずに済みます。一致しなかった行と、デフォルト値を含む一致した行をクエリで区別する必要がある場合にのみ、`join_use_nulls` を有効化してください。

## JOIN の最適化の例 {#join-optimization-examples}

以下の例では [Stack Overflow データセット](/ja/getting-started/example-datasets/stackoverflow) を使用し、推奨事項を段階的に適用していきます。
以下の測定値は、ClickHouse 26.8.1 が稼働する ClickHouse Cloud サービス上で `max_threads = 4` を設定し、5 回実行した結果の中央値です。各クエリは事前に 1 回ウォームアップし、クエリの実行順序を交互に入れ替えたうえで、`use_query_cache` と `use_query_condition_cache` を無効化して計測しています。

### `ANY INNER JOIN` を `IN` に置き換える {#replace-any-inner-join-with-in}

このテストでは、`IN` を使用したクエリのほうが 2.7 倍高速で、ピークメモリ使用量も 83% 少なくなりました。
このクエリは、本文では ClickHouse に言及していないものの、ClickHouse に言及しているコメントが少なくとも 1 件ある投稿の数をカウントします。

```sql
SELECT count()
FROM stackoverflow.posts AS p
ANY INNER JOIN stackoverflow.comments AS c ON p.Id = c.PostId
WHERE
    p.Title != ''
    AND p.Title NOT ILIKE '%clickhouse%'
    AND p.Body NOT ILIKE '%clickhouse%'
    AND c.Text ILIKE '%clickhouse%'
```

このクエリは結果として `86` を返します。経過時間の中央値は 27.101 秒、ピークメモリ使用量は 970.01 MiB でした。読み取ったデータは 1億5,020万行、51.77 GiB です。

このクエリでは、一致するコメントが存在するかどうかさえわかれば十分です。`IN` サブクエリを使用すれば、JOIN結果を生成せずに済みます。

```sql
SELECT count()
FROM stackoverflow.posts
WHERE
    Title != ''
    AND Title NOT ILIKE '%clickhouse%'
    AND Body NOT ILIKE '%clickhouse%'
    AND Id IN
    (
        SELECT PostId
        FROM stackoverflow.comments
        WHERE Text ILIKE '%clickhouse%'
    )
```

`IN` クエリも `86` を返します。経過時間の中央値は 10.206 秒、ピークメモリ使用量は 162.81 MiB でした。読み取ったデータは 1 億 7,420 万行、19.02 GiB です。

### JOIN を置き換える前に両側をフィルタする {#filter-both-sides-before-replacing-the-join}

このテストでは、書き換えによって経過時間の中央値が 18%、ピークメモリ使用量が 14% 削減されました。
このクエリは、2020 年以降に作成された Java 関連の投稿に対する賛成票の数を集計します。日付の条件は、JOIN の前に両方の入力に適用されています。

```sql
SELECT countIf(v.VoteTypeId = 2) AS upvotes
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.votes AS v ON p.Id = v.PostId
WHERE
    p.CreationDate >= '2020-01-01'
    AND v.CreationDate >= '2020-01-01'
    AND has(arrayFilter(t -> t != '', splitByChar('|', p.Tags)), 'java')
```

このクエリは結果として `261915` を返します。経過時間の中央値は 0.850 秒、ピークメモリ使用量は 59.96 MiB でした。読み取った行数は 8,094 万行、データ量は 1.13 GiB です。

各投票について必要なのは一致する投稿が存在するかどうかだけなので、両方の入力に対するフィルタを維持したまま、JOIN を `IN` に置換できます。

```sql
SELECT count() AS upvotes
FROM stackoverflow.votes
WHERE
    VoteTypeId = 2
    AND CreationDate >= '2020-01-01'
    AND PostId IN
    (
        SELECT Id
        FROM stackoverflow.posts
        WHERE
            CreationDate >= '2020-01-01'
            AND has(arrayFilter(t -> t != '', splitByChar('|', Tags)), 'java')
    )
```

`IN` クエリも `261915` を返します。経過時間の中央値は 0.696 秒、ピークメモリ使用量は 51.70 MiB でした。読み取ったのは 4,620 万行、817.49 MiB のデータです。

## JOIN アルゴリズムの選択 {#choosing-the-right-join-algorithm}

ClickHouse は、速度とメモリ使用量のトレードオフがそれぞれ異なる複数の JOIN アルゴリズムをサポートしています。
[`join_algorithm`](/ja/reference/settings/session-settings/join#join_algorithm) のデフォルト値は `direct,parallel_hash,hash,ie_join` で、ClickHouse は JOINの種類、strictness、条件、テーブルエンジンに応じて、適用可能な最初のアルゴリズムを選択します。この設定の変更を検討するのは、まず両方の入力を削減し、そのうえで代表的なデータを用いた測定によって別のメモリ戦略や実行戦略が必要だと判明した場合に限ってください。アルゴリズムの詳細と選び方の指針については、[JOIN アルゴリズムの選択](/ja/concepts/features/operations/select/joining-tables#choosing-a-join-algorithm)を参照してください。
