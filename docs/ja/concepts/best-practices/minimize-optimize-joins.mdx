このページでは、可能な限り JOIN を避け、JOIN が必要な場合にはそのコストを抑えるための具体的な指針を示します。構文とセマンティクスについては、[`JOIN` 句リファレンス](/ja/reference/statements/select/join)を参照してください。実行アルゴリズムとその選択方法については、[JOIN アルゴリズム](/ja/concepts/features/operations/select/join-algorithms)を参照してください。

## JOINはできるだけ避ける {#prefer-avoiding-joins}

ClickHouse は多種多様な JOINの種類とアルゴリズムをサポートしています。ただし、JOIN は本質的に、単一の非正規化されたテーブルに対するクエリよりもコストが高くなります。非正規化では、計算処理をクエリ実行時から INSERT 時または前処理時に移すため、実行時のレイテンシを大幅に低減できることがよくあります。リアルタイム処理やレイテンシに敏感な分析クエリでは、**非正規化を強く推奨します**。

一般に、次のような場合は非正規化を検討してください。

* テーブルの更新頻度が低い、またはバッチ更新を許容できる。
* 関係が多対多ではなく、カーディナリティも極端に高くない。
* クエリされるカラムが一部に限られており、つまり特定のカラムは非正規化の対象から外せる。
* [Flink](/ja/integrations/connectors/data-ingestion/apache-flink) のような上流システムに処理を移し、リアルタイムの enrichment やフラット化を管理できる体制がある。

すべてのデータを非正規化する必要はありません。頻繁にクエリされる属性に絞って対応してください。また、サブテーブル全体を複製する代わりに、集計をインクリメンタルに計算する方法として [materialized view](/ja/concepts/best-practices/use-materialized-views) も検討してください。スキーマ更新がまれで、レイテンシが重要な場合、非正規化はパフォーマンス面で最も優れたトレードオフをもたらします。

ClickHouse でのデータの非正規化について詳しくは、[非正規化](/ja/guides/clickhouse/data-modelling/denormalization) のガイドを参照してください。

## JOIN が必要な場合 {#when-joins-are-required}

<Tip>
  **ClickHouse 26.8 以降を使用してください。**

  複数テーブルの JOIN の順序変更と、オプティマイザによる利用可能な統計情報の活用は、25.12 以降デフォルトで有効になっています。[カラム統計](/ja/reference/settings/session-settings/allow-statistics#allow_statistics)は 26.3 で一般提供となり、デフォルトで有効になりました。26.8 以降は、対象となるテーブルで[挿入時にカラム統計をマテリアライズ](/ja/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert)する動作がデフォルトとなり、コストベースの JOIN 最適化における推定精度が向上しています。
</Tip>

JOIN のパフォーマンスを向上させるには、以下のベストプラクティスに従ってください。

* **一致が 1 件あれば十分な場合は `ANY` JOIN を使用します。** 通常の JOIN は一致するすべての行を返すため、キーが重複しているとデカルト積が生じる可能性があります。左側の各行に右側の一致する行を 1 件だけ付加する場合は `LEFT ANY JOIN` を使用すると、結果のサイズとメモリ使用量を削減できます。一致する行が存在するかどうかだけを確認する場合は、`IN` または `LEFT SEMI JOIN` を使用してください。デフォルトの [`any_join_distinct_right_table_keys = 0`](/ja/reference/settings/session-settings/other#any_join_distinct_right_table_keys) では、`INNER ANY JOIN` は左側もキーごとに 1 行に制限するため、同じキーを持つ左側の行が除外される可能性があります。詳細は [`ALL` と `ANY` の strictness](/ja/concepts/features/operations/select/joining-tables#all-and-any-strictness) を参照してください。
* **JOIN の前に両側のデータを絞り込みます。** `WHERE` 句および `JOIN ON` 句で選択性の高い条件を適用してください。ClickHouse は可能な限りフィルタをプッシュダウンしますが、明示的にサブクエリを使用すれば、JOIN の前に各入力を確実にフィルタできます。
* **`INNER JOIN` の代わりに `IN` を検討します。** 相手テーブルにキーが存在するかどうかを確認するだけでよいクエリでは、`IN` サブクエリを使うとその意図を直接表現でき、`INNER JOIN` の結果を生成するよりもメモリ使用量を抑えられる場合があります。
* **繰り返し行うキー・バリューのルックアップには Dictionary を使用します。** `HASHED` や `COMPLEX_KEY_HASHED` などのレイアウトを使用すると、[Dictionary](/ja/concepts/features/dictionaries) はクエリ実行前にメモリへロードされ、`LIFETIME` に従って更新されます。[`dictGetOrDefault`](/ja/reference/functions/regular-functions/ext-dict-functions#dictGetOrDefault) 関数を使うと、JOIN を使わずに各キーを Dictionary でルックアップできます。例: `dictGetOrDefault('stackoverflow.users_dict', 'DisplayName', tuple(p.OwnerUserId), '')`。
* **繰り返し使用するルックアップには `Join` テーブルエンジンを使用します。** [`Join` テーブルエンジン](/ja/reference/engines/table-engines/special/join)は、宣言された JOINの種類、strictness、キーに基づいて、事前計算済みのインメモリ構造を保持します。ClickHouse Cloud では、`MergeTree` をバックエンドテーブルとする `SharedJoin` として実装されており、`Join(ANY, LEFT, key)` を使うとキー単位で更新可能なルックアップを実現できます。詳細は [Fast, updatable lookups with the Join table engine](https://clickhouse.com/blog/join-table-engine) を参照してください。
* **可能であればテーブルの sorting key で結合します。** 両方のテーブルが 結合キーで物理的にソートされている場合、`full_sorting_merge` はソート処理を省略でき、メモリ使用量を削減できます。実行計画を確認したうえで、代表的なデータを用いてこのアルゴリズムとデフォルトのアルゴリズムをベンチマークで比較してください。
* **ディスクへのスピルが発生する JOIN は避けます。** JOIN の中間状態をディスクにスピルすればクエリをメモリ制限内に収められますが、通常はディスク I/O によってレイテンシが増加します。ハッシュ結合は設定されたスピル threshold に達すると grace hash に切り替えることができ、マージ結合は外部ソートを使用できます。スピルに頼る前に、入力の行数やカラム数を減らす、あるいはデータモデルを見直すといった対策を検討してください。詳細は [最適な JOIN アルゴリズムの選択](#choosing-the-optimal-join-algorithm) を参照してください。
* **必要に応じてデフォルト値を不一致のマーカーとして利用します。** デフォルトの [`join_use_nulls = 0`](/ja/reference/settings/session-settings/join#join_use_nulls) では、外部 JOIN で一致しなかったカラムはそのデータ型のデフォルト値で埋められるため、`Nullable` でラップされずに済みます。一致しなかった行と、デフォルト値を含む一致した行をクエリで区別する必要がある場合にのみ、`join_use_nulls` を有効化してください。

## 最適な 結合アルゴリズムの選択 {#choosing-the-optimal-join-algorithm}

ClickHouse は、速度とメモリのトレードオフが異なる複数の 結合アルゴリズムをサポートしています。
[`join_algorithm`](/ja/reference/settings/session-settings/join#join_algorithm) のデフォルト値は `direct,hash,inequality` で、ClickHouse は JOIN の種類、strictness、条件、テーブルエンジンに対して適用可能な最初のアルゴリズムを選択します。この設定の変更を検討するのは、両方の入力を削減したうえで、代表的なデータでの計測により別のメモリ戦略または実行戦略が必要だと判明した場合に限ってください。アルゴリズムの実行の詳細とサポートされる JOIN の種類については、[結合アルゴリズム](/ja/concepts/features/operations/select/join-algorithms)を参照してください。

最適化で最も重視する指標がパフォーマンスであり、結合をできるだけ高速に実行したい場合は、次の決定木を使って適切な結合アルゴリズムを選択できます。

<br />

<div className="ch-image-lg">
  <Frame>
    ![結合パフォーマンス最適化の決定木](/images/guides/joins-4.webp)
  </Frame>
</div>

<br />

* **(1)** 右側が Dictionary、または低レイテンシなキー・バリュールックアップが可能な別のストレージである場合は、[`direct`](/ja/concepts/features/operations/select/join-algorithms#direct) アルゴリズムを適用できます。多くの場合、これが最も高速な方法です。このアルゴリズムを使用するには、`ON` 句にストレージの単一カラムキーに対する等価条件が 1 つだけ含まれる `INNER JOIN`、`LEFT JOIN`、`LEFT ANY JOIN`、`LEFT SEMI JOIN`、または `LEFT ANTI JOIN` である必要があります。条件を満たさない場合、ClickHouse はエラーを出さずに [`join_algorithm`](/ja/reference/settings/session-settings/join#join_algorithm) 内の次のアルゴリズムを使用します。

* **(2)** テーブルの[物理的な行の順序](/ja/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns)が結合キーのソート順と一致する場合は、状況次第です。この場合、**完全ソートマージ結合** はソートフェーズを[スキップ](https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order)するため、メモリ使用量が大幅に削減されます。さらに、データサイズや結合キーの値の分布によっては、一部のハッシュ結合アルゴリズムより実行時間が短くなります。

* **(3)** 右テーブルがメモリに収まる場合は、[`hash`](/ja/concepts/features/operations/select/join-algorithms#hash) アルゴリズムを使用してください。データサイズ、データ型、および結合キーカラムの値の分布にもよりますが、通常はこれが最も高速なインメモリの選択肢です。ClickHouse はクエリごとに、単一のハッシュテーブルを構築するか、ハッシュテーブルを複数のパーツに分割して複数のスレッドで並行して構築するかを判断します。後者は決定木では並列ハッシュとして示されています。この判断は [`parallel_hash_join_threshold`](/ja/reference/settings/session-settings/parallel#parallel_hash_join_threshold) 設定で制御されます。右テーブルの推定行数がしきい値に達した場合、または推定値が利用できない場合に、ハッシュテーブルが分割されます。26.11 以降、`parallel_hash` は `hash` の廃止されたエイリアスであるため、`join_algorithm` に指定してもこの判断は変わりません。

* **(4)** 右テーブルがメモリに収まらない場合、ハッシュ結合 と 並列ハッシュ結合 は、[`max_bytes_before_external_join`](/ja/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) または [`max_bytes_ratio_before_external_join`](/ja/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join) に達した時点で grace hash に切り替え、ディスクへスピルできます。完全ソートマージ結合 と 部分マージ結合 も外部ストレージを使用できます。どの方法が最も高速かは、データ量、データ型、および結合キーカラムの値の分布によって決まります。

部分マージ結合は、大きなテーブルを結合する際のメモリ使用量を最小限に抑えるよう最適化されていますが、その代償として結合速度はかなり遅くなります。特に、左テーブルの物理的な行の順序が結合キーのソート順と一致しない場合にこの傾向が顕著です。

Grace Hash Join は、メモリに制約されない 3 つの結合アルゴリズムの中で最も柔軟性が高く、設定によるきめ細かな制御が可能です。[`grace_hash_join_initial_buckets`](/ja/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets) 設定は初期バケット数を制御するもので、メモリ使用量と結合速度のバランスを調整できます。

3 つのディスクベースのアルゴリズムのうちどれが最も高速かは、データ量、データ型、および結合キーカラムの値の分布によって決まります。最速のアルゴリズムを見極めるには、実運用に近いデータ量でベンチマークを実施するのが最善です。

### 決定木の例 {#decision-tree-examples}

以下の例では、決定木の各ステップを [Stack Overflow データセット](/ja/getting-started/example-datasets/stackoverflow) に当てはめていきます。JOIN でどのアルゴリズムが使われるかを確認するには、`EXPLAIN actions = 1` を付けてクエリを実行し、出力の `Algorithm` 行を確認してください。

**(1) `direct`。** 次の Dictionary には各ユーザーの表示名が格納されており、クエリでは高評価の投稿それぞれについて著者を検索します。

```sql
CREATE DICTIONARY stackoverflow.users_dict
(
    Id Int32,
    DisplayName String
)
PRIMARY KEY Id
SOURCE(CLICKHOUSE(DB 'stackoverflow' TABLE 'users'))
LAYOUT(COMPLEX_KEY_HASHED())
LIFETIME(MIN 600 MAX 900);

SELECT p.Id, p.Score, u.DisplayName
FROM stackoverflow.posts AS p
LEFT JOIN stackoverflow.users_dict AS u ON p.OwnerUserId = u.Id
WHERE p.Score > 1000;
```

`Algorithm` 行には `DirectKeyValueJoin` と表示されます。この Dictionary では、`users.Id` の `Int32` 型を維持するために `COMPLEX_KEY_HASHED` レイアウトを使用しています。`HASHED` のような単純キーのレイアウトではキーが `UInt64` に変換されてしまい、`Int32` 型のカラムである `posts.OwnerUserId` と結合できなくなります。

**(2) `full_sorting_merge`。** `badges` テーブルは `UserId` でソート済みであり、`users` テーブルの sorting key は `Id` から始まります。そのため、両テーブルとも結合キーの順に物理的に並んでいます。

```sql
SELECT u.Location, count() AS famous_questions
FROM stackoverflow.badges AS b
INNER JOIN stackoverflow.users AS u ON b.UserId = u.Id
WHERE b.Name = 'Famous Question'
GROUP BY u.Location
ORDER BY famous_questions DESC
LIMIT 5
SETTINGS join_algorithm = 'full_sorting_merge';
```

`Algorithm` 行には `FullSortingMergeJoin` が表示され、2 つの `ReadFromMergeTree` 処理ステップはいずれも読み取り種別として `InOrder` を示しています。つまり ClickHouse は、両方のテーブルをソートせずに結合キーの順序で読み取っています。

**(3) `hash`。** デフォルトの `join_algorithm` では、次の JOIN は `hash` で実行されます。

```sql
SELECT u.Location, count() AS popular_posts
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.users AS u ON p.OwnerUserId = u.Id
WHERE p.Score > 1000
GROUP BY u.Location
ORDER BY popular_posts DESC
LIMIT 5
SETTINGS parallel_hash_join_threshold = 0;
```

`SETTINGS` 句を指定しない場合、ClickHouse がハッシュテーブルを分割するのは、右側のテーブルの推定行数が `parallel_hash_join_threshold` のデフォルト値である 100,000 に達した場合のみです。`parallel_hash_join_threshold = 0` を指定すると、推定値にかかわらずハッシュテーブルを分割します。

**(4) スピル。** 次のクエリでは、ハッシュテーブルがメモリ上で最大 10 GiB まで拡大できるようにしています。このサイズを超えると、ClickHouse は JOIN を `grace_hash` に切り替え、データの一部を一時ストレージに書き込みます：

```sql
SELECT u.Location, count() AS popular_posts
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.users AS u ON p.OwnerUserId = u.Id
WHERE p.Score > 1000
GROUP BY u.Location
ORDER BY popular_posts DESC
LIMIT 5
SETTINGS max_bytes_before_external_join = '10Gi';
```

## メモリ最適化 {#optimizing-for-memory}

結合の最適化において、実行時間の短さよりもメモリ使用量の少なさを優先したい場合は、代わりに次の決定木を利用できます。

<br />

<div className="ch-image-lg">
  <Frame>
    ![結合のメモリ最適化に関する決定木](/images/guides/joins-5.webp)
  </Frame>
</div>

<br />

* **(1)** テーブルの物理的な行順序が結合キーのソート順と一致している場合、**完全ソートマージ結合**のメモリ使用量は最小限に抑えられます。さらに、ソートフェーズが[無効化](https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order)されるため、良好な結合速度も得られます。
* **(2)** [`grace_hash`](/ja/concepts/features/operations/select/join-algorithms#grace-hash) アルゴリズムは、[`grace_hash_join_initial_buckets`](/ja/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets)を増やすことで、JOIN の速度と引き換えにメモリ使用量を非常に低く抑えるようチューニングできます。[`partial_merge`](/ja/concepts/features/operations/select/join-algorithms#partial-merge) アルゴリズムは、主記憶の使用量が少なくなるよう意図的に設計されています。外部ソートを有効にした [`full_sorting_merge`](/ja/concepts/features/operations/select/join-algorithms#full-sorting-merge) アルゴリズムは、行順序がキーのソート順と一致しない場合、一般に `partial_merge` よりも多くのメモリを使用しますが、その代わりに JOIN の実行時間は大幅に短縮されます。[`hash`](/ja/concepts/features/operations/select/join-algorithms#hash) アルゴリズムも、設定済みのスピル threshold に達した時点で `grace_hash` に切り替えることで、メモリ逼迫を軽減できます。

## JOIN の最適化の例 {#join-optimization-examples}

以下の例では [Stack Overflow データセット](/ja/get-started/sample-datasets/stackoverflow) を使用し、推奨事項を段階的に適用していきます。
以下の測定値は、ClickHouse 26.8.1 が稼働する ClickHouse Cloud サービス上で `max_threads = 4` を設定し、5 回実行した結果の中央値です。各クエリは事前に 1 回ウォームアップし、クエリの実行順序を交互に入れ替えたうえで、`use_query_cache` と `use_query_condition_cache` を無効化して計測しています。

### `ANY INNER JOIN` を `IN` に置き換える {#replace-any-inner-join-with-in}

このテストでは、`IN` を使用したクエリのほうが 2.7 倍高速で、ピークメモリ使用量も 83% 少なくなりました。
このクエリは、本文では ClickHouse に言及していないものの、ClickHouse に言及しているコメントが少なくとも 1 件ある投稿の数をカウントします。

```sql
SELECT count()
FROM stackoverflow.posts AS p
ANY INNER JOIN stackoverflow.comments AS c ON p.Id = c.PostId
WHERE
    p.Title != ''
    AND p.Title NOT ILIKE '%clickhouse%'
    AND p.Body NOT ILIKE '%clickhouse%'
    AND c.Text ILIKE '%clickhouse%'
```

このクエリは結果として `86` を返します。経過時間の中央値は 27.101 秒、ピークメモリ使用量は 970.01 MiB でした。読み取ったデータは 1億5,020万行、51.77 GiB です。

このクエリでは、一致するコメントが存在するかどうかさえわかれば十分です。`IN` サブクエリを使用すれば、JOIN結果を生成せずに済みます。

```sql
SELECT count()
FROM stackoverflow.posts
WHERE
    Title != ''
    AND Title NOT ILIKE '%clickhouse%'
    AND Body NOT ILIKE '%clickhouse%'
    AND Id IN
    (
        SELECT PostId
        FROM stackoverflow.comments
        WHERE Text ILIKE '%clickhouse%'
    )
```

`IN` クエリも `86` を返します。経過時間の中央値は 10.206 秒、ピークメモリ使用量は 162.81 MiB でした。読み取ったデータは 1 億 7,420 万行、19.02 GiB です。

`posts.Id` は重複のない値であるため、2 つのクエリは同じ結果を返します。この書き換えが同等になるのは、左側の結合キーが重複のない値である場合に限られます。`ANY INNER JOIN` はキーごとに左側の行を最大 1 行しか返さないのに対し、`IN` は一致する左側の行をすべて返すためです。

### JOIN を置き換える前に両側をフィルタする {#filter-both-sides-before-replacing-the-join}

このテストでは、書き換えによって経過時間の中央値が 18%、ピークメモリ使用量が 14% 削減されました。
このクエリは、2020 年以降に作成された Java 関連の投稿に対する賛成票の数を集計します。日付の条件は、JOIN の前に両方の入力に適用されています。

```sql
SELECT countIf(v.VoteTypeId = 2) AS upvotes
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.votes AS v ON p.Id = v.PostId
WHERE
    p.CreationDate >= '2020-01-01'
    AND v.CreationDate >= '2020-01-01'
    AND has(arrayFilter(t -> t != '', splitByChar('|', p.Tags)), 'java')
```

このクエリは結果として `261915` を返します。経過時間の中央値は 0.850 秒、ピークメモリ使用量は 59.96 MiB でした。読み取った行数は 8,094 万行、データ量は 1.13 GiB です。

各投票について必要なのは一致する投稿が存在するかどうかだけなので、両方の入力に対するフィルタを維持したまま、JOIN を `IN` に置換できます。

```sql
SELECT count() AS upvotes
FROM stackoverflow.votes
WHERE
    VoteTypeId = 2
    AND CreationDate >= '2020-01-01'
    AND PostId IN
    (
        SELECT Id
        FROM stackoverflow.posts
        WHERE
            CreationDate >= '2020-01-01'
            AND has(arrayFilter(t -> t != '', splitByChar('|', Tags)), 'java')
    )
```

`IN` クエリも `261915` を返します。経過時間の中央値は 0.696 秒、ピークメモリ使用量は 51.70 MiB でした。読み取ったのは 4,620 万行、817.49 MiB のデータです。

`posts.Id` は重複のない値であり、各投票に一致する投稿は最大 1 件に限られるため、この書き換えは元のクエリと同等です。
