<Note>
  **このページは Scale および Enterprise サービスを対象としています。**

  * **Basicティア:** Basic サービスはサイズが固定されており、スケーリングできません。Basic サービスをご利用中でトラフィックスパイクが予想される場合は、[Cloud ティア](/ja/products/cloud/features/cloud-tiers)をアップグレードしてください。
  * **Bring Your Own Cloud (BYOC):** 以下の手順はそのまま適用されます。ただし、サービスはお客様自身のクラウドアカウントで実行されるため、想定されるピークに対応できる十分なクォータとキャパシティがアカウントにあることを確認してください。
</Note>

多くのワークロードでは、需要が高まる時期をあらかじめ予測できます。たとえば、小売・ショッピングイベント、製品ローンチ、四半期末のレポーティング、マーケティングキャンペーンなどです。オートスケーリングは負荷の発生に応じて対応しますが、事前にわかっているピークに対しては、通常は前もってスケールアップしておくほうが適切です。

全体的に需要が高まる時期には、特に大きなインスタンスサイズや一部のリージョンで、各クラウドプロバイダーのキャパシティが通常より逼迫することがあります。早めにスケールアップしておけば、必要なキャパシティを確保できるうえ、ピークを迎える前にサービスの準備が整っていることを確認する時間も確保できます。

<Note>
  **今後のピーク: 2026 年のブラックフライデーおよびサイバーマンデー**

  2026 年 11 月 27 日〜30 日前後にトラフィックの増加が見込まれる場合は、**11 月 20 日**までにスケールアップし、**12 月 1 日**までその状態を維持することを推奨します。サービスで許可されているレプリカ数を超えてスケーリングする予定がある場合は、**11 月 13 日**までにお問い合わせください (後述のステップ 3 を参照) 。
</Note>

## ピーク前 {#before-the-peak}

1. ピーク時の変化をすばやく検知できるよう、監視とアラートを設定します。スケーリングイベント、エラー、請求に関するメールや Slack の[通知](/ja/products/cloud/features/monitoring/notifications)を設定してください。外部の監視ツールを使用している場合は、[Prometheus エンドポイント](/ja/products/cloud/features/monitoring/prometheus)経由で接続し、CPU とメモリの使用率に対するアラートを設定します。
2. 想定される負荷を見積もります。過去のピーク時にサービスがどのように動作したかを確認し、クエリ量と挿入量がどの程度増加しうるかを見積もります。各レプリカの CPU とメモリの使用率の履歴は、サービスの Infrastructure ダッシュボード (**監視 &gt; Infrastructure**) で確認できます。[ワークロードのスパイクへの対応](/ja/products/cloud/features/autoscaling/scheduled-scaling#handling-bursty-workloads)もあわせて参照してください。
3. 大規模なスケールアップは事前にお知らせください。サービスで許可されているレプリカ数を超えてスケールする予定がある場合は、ピークの少なくとも 2 週間前までにアカウントチームまたは ClickHouse Support にご連絡ください。これにより、クラウドプロバイダーと事前にキャパシティを調整できます。リクエストには以下の情報を含めてください。

   1. サービス名とリージョン
   2. 目標サイズ (レプリカあたりのメモリとレプリカ数)
   3. 開始日と終了日

   <Note>
     キャパシティはクラウドプロバイダー側の空き状況に左右されるため、特定のサイズを特定の時点で確実に利用できることは保証できません。早めにお知らせいただくほど、キャパシティを確保できる可能性が高くなります。
   </Note>
4. 事前にスケールアップします。ピーク当日ではなく、数日前にスケールアップしてください。これにより、サービスが新しいサイズで正常に稼働していることを確認し、必要に応じて調整する時間を確保できます。サービスのスケーリング設定は、ClickHouse Cloud コンソールの **設定 &gt; スケーリング**、または [ClickHouse Cloud API](/ja/products/cloud/features/admin-features/api/api-overview) で変更できます。
5. オートスケーリングの設定を見直します。サービスでオートスケーリング (垂直または水平) が有効になっている場合は、ピーク前に上限と下限を確認してください。
   1. オートスケーリングの反応を待たずにピーク期間中を通してキャパシティを維持できるよう、**最小値を引き上げます**。
   2. 負荷が見積もりを上回った場合でもオートスケーリングで拡張できる余地を残すため、**最大値を引き上げます**。
   3. **アイドル化を見直します。** レイテンシーが重要なサービスでは、トラフィック到着時にサービスの起動を待たずに済むよう、ピーク期間中はアイドル化を無効にすることを検討してください。
   4. **スケーリングスケジュールを見直します。** スケーリングスケジュールは、トリガーされるとオートスケーリングの設定よりも優先されます。週末や夜間の scale-down など、ピーク期間中にサービスをスケールダウンさせるスケジュールがあれば、一時停止または調整してください。
6. 新しいサイズでテストします。サービスのスケールアップが完了したら、可能であればピーク時のトラフィックを再現した負荷テストを実施してください。これにより、新しいサイズで想定される急増に対応できるかを確認でき、必要に応じて対策を講じることができます。

## ピーク後の対応 {#after-the-peak}

需要が通常の水準に戻ったら、コンソールまたは API から、サービスを通常のスケーリング設定に戻してください。必要以上に長くスケールアップされたままにならないよう、終了日にリマインダーを設定しておくことをおすすめします。

夜間のバッチジョブや営業時間帯のトラフィックなど、日次または週次で規則的なパターンを持つワークロードには、[スケジュールスケーリング](/ja/products/cloud/features/autoscaling/scheduled-scaling) を使用すると、スケールアップとスケールダウンを自動的に行えます。

## 請求 {#billing}

サービスは、スケールアップ後のサイズで稼働している間、そのサイズに応じて課金されます。ピーク時に合わせてスケールアップすると、その期間の請求額が増加します。
