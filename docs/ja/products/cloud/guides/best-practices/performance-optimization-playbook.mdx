ClickHouse Cloud の新規デプロイメントを設計する際や、既存のワークロードを改善する際に、このプレイブックを活用してください。スキーマ、クエリ、インジェスト、インフラストラクチャに関する判断を、検証可能な測定結果と結び付けて解説します。スキーマおよびクエリに関する推奨事項の大半は、自己管理型 ClickHouse にも当てはまります。

## 出発点を選ぶ {#choose-a-starting-point}

| 目的              | 最初に読むセクション                                                                                                              |
| --------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 新しいデプロイメントを設計する | まず[ワークロードをプロファイリング](#profile-the-workload)し、次に[スキーマを設計](#design-the-schema)して[Cloud リソースを計画](#plan-cloud-resources)します。 |
| 既存のワークロードを改善する  | [ボトルネックを診断](#diagnose-the-bottleneck)し、要素を 1 つだけ変更してから[結果をベンチマーク](#benchmark-the-result)します。                            |
| スロークエリを調査する     | [クエリ最適化ガイド](/ja/guides/clickhouse/performance-and-monitoring/query-optimization)を参考に、クエリの履歴と実行計画を確認します。                    |
| 本番リリースに備える      | [デプロイメントチェックリスト](#deployment-checklist)と[本番運用への準備ガイド](/ja/products/cloud/guides/production-readiness)の項目をすべて完了します。         |

## ワークロードのプロファイリング {#profile-the-workload}

現在のレイテンシ、スループット、リソース使用量を記録し、測定可能な目標を設定します。クエリのレイテンシ、インジェストのレイテンシ、データの鮮度は区別して扱ってください。いずれかを改善すると、他の処理の負荷が増える場合があります。

代表的なクエリとフィルタ値、実行頻度、同時実行数、インジェストレート、データボリューム、増加量、保持期間を把握します。tenant 間の差異やピーク時の負荷も含めてください。リグレッションの場合は、データ、スキーマ、バージョン、サービスサイズ、またはクライアントの動作の変更内容を記録します。

Cloud では、[クエリインサイト](/ja/products/cloud/features/sql-console-features/query-insights) でクエリパターンとリソース消費量を確認できます。独自に分析する場合は、すべてのレプリカを対象に [`system.query_log`](/ja/reference/system-tables/query_log) をクエリします。

```sql
SELECT
    normalized_query_hash,
    count() AS executions,
    round(avg(query_duration_ms)) AS avg_ms,
    quantile(0.95)(query_duration_ms) AS p95_ms,
    sum(query_duration_ms) AS total_duration_ms,
    avg(read_rows) AS avg_read_rows,
    max(memory_usage) AS max_memory_bytes,
    any(query) AS example_query
FROM clusterAllReplicas('default', merge('system', '^query_log'))
WHERE event_time >= now() - INTERVAL 1 DAY
    AND type = 'QueryFinish'
    AND is_initial_query = 1
    AND query_kind = 'Select'
GROUP BY normalized_query_hash
ORDER BY total_duration_ms DESC
LIMIT 20;
```

このクエリは、成功したクエリパターンを累積所要時間の順にランク付けします。クエリインサイトでは失敗したクエリも確認してください。成功した実行だけを見ていると、タイムアウトやメモリ上限超過による例外を見落とすおそれがあります。このクエリの実行には、各レプリカのシステムテーブルへのアクセス権が必要です。ログは非同期で flush されるため、最近の実行がすぐには反映されない場合があります。

`default` クラスターは ClickHouse Cloud で利用できます。シングルノード構成の場合は、`FROM` 式を `system.query_log` に置き換えてください。詳しい分析方法については、[遅いクエリの診断](/ja/guides/clickhouse/performance-and-monitoring/diagnose-slow-queries)を参照してください。

## ボトルネックを診断する {#diagnose-the-bottleneck}

ClickHouse は `MergeTree` のデータを、ソート済みかつ圧縮済みのパーツとして保存します。パーツはバックグラウンドマージによって統合されます。スパースプライマリインデックスを利用することで、クエリは各パーツ内のグラニュールをスキップできます。効果的な最適化とは、読み取るデータ量、またはそのデータに対する処理量を削減することです。

まずはテーブル定義とクエリプランを確認します。以下のテーブルとクエリは、ご自身のものに置き換えてください。

```sql
SHOW CREATE TABLE database_name.table_name;

EXPLAIN indexes = 1
SELECT column_name
FROM database_name.table_name
WHERE filter_column = 'value';
```

選択されたパーツとグラニュールを全体の総数と比較して確認します。さらに、クエリログに記録された実際の読み取り行数、読み取りバイト数、所要時間、メモリ使用量と照らし合わせます。テーブル全体を対象とする集約であれば、大規模なスキャンが妥当な場合もあります。クエリの要件に照らして判断してください。

| 観察された事象                        | 調査対象                                                                 | 考えられる次のステップ                                               |
| ------------------------------ | -------------------------------------------------------------------- | --------------------------------------------------------- |
| 選択性の高いフィルタなのに大半のグラニュールを読み取っている | `EXPLAIN` におけるプライマリキーの枝刈り                                            | 順序キーをフィルタに合わせるか、プロジェクションまたはスキッピングインデックスを検討します。            |
| アクティブなデータパーツが増え続けている           | `system.parts` および `system.merges` における挿入サイズ、パーティションの fan-out、マージの状況 | バッチ挿入や非同期挿入を利用するか、パーティションの断片化を抑えます。                       |
| 繰り返し実行すると大幅に高速化する              | キャッシュの動作とサービスのライフサイクル                                                | コールド実行とウォーム実行を分けて比較します。ワーキングセットを縮小するか、繰り返し行われる処理を事前計算します。 |
| 結合が過剰にメモリを消費している               | 結合のカーディナリティ、入力、アルゴリズム                                                | 入力を削減するか、Dictionary の利用を検討するか、メモリ使用量に上限のあるアルゴリズムを試します。    |
| 同時実行時にレイテンシが増大する               | CPU、メモリ、インジェスト、競合するクエリ                                               | まずクエリごとの処理量を削減し、そのうえでスケーリングまたは分離を検討します。                   |

スキーマや設定を変更する前に、[クエリのボトルネックを特定する](/ja/guides/clickhouse/performance-and-monitoring/isolate-query-bottlenecks)の手順で仮説を検証してください。

## スキーマの設計 {#design-the-schema}

### 正確性を考慮したエンジンの選択 {#choose-an-engine-for-correctness}

レコードがどのように変化し、クエリでそれをどう解釈する必要があるかに応じてエンジンを選択します。

| エンジン                                                     | 主な用途                                                                               |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `MergeTree`                                              | 一般的な追記専用の分析。                                                                       |
| `ReplacingMergeTree`                                     | 1 つのレコードに複数のバージョンがあり、最終的に sorting key で重複排除する場合。正確性が求められる場合は、クエリ時に適切な重複排除を行ってください。 |
| `AggregatingMergeTree`                                   | 集約状態。通常はインクリメンタルmaterialized view によってデータが投入されます。                                  |
| `SummingMergeTree`                                       | 加算可能なカウンターおよびロールアップ。まだマージされていない行をクエリ側で集約する必要がある場合があります。                            |
| `CollapsingMergeTree` または `VersionedCollapsingMergeTree` | 明示的なステートレコードおよびキャンセルレコード。クエリにはエンジン固有の要件があります。                                      |

バックグラウンドマージでは、クエリ実行前にすべてのバージョンや集約行が統合されていることは保証されません。エンジンのセマンティクスについては、[`MergeTree`ファミリーのリファレンス](/ja/reference/engines/table-engines/mergetree-family)を参照してください。

### 順序キーをクエリに合わせる {#align-the-ordering-key-with-queries}

テーブルの `ORDER BY` は物理的なソート順を定義します。主キーはデフォルトでは sorting key と同じで、スパースインデックスを決定します。いずれも一意性を保証するものではありません。

頻繁に使われ、かつ選択性の高いフィルタに用いられるカラムを優先してください。有用なフィルタカラムのうち、カーディナリティの低いものをキーの前方に置くと、局所性と圧縮率が向上することがあります。ただし、カーディナリティだけを理由にカラムをキーに含めるべきではありません。

例えば、常に tenant と時刻で絞り込むクエリには、`(tenant_id, event_time)` が有効な場合があります。一方、すべての tenant を横断するクエリでは、別の順序が必要になることもあります。アクセスパターンから見て妥当であれば、タイムスタンプや識別子を先頭カラムにしても構いません。

キーに含めるカラムは必要最小限に絞り、代表的なクエリで候補を検証してください。`ORDER BY tuple()` ではプライマリインデックスによる枝刈りが行われないため、そのトレードオフを承知のうえで使用してください。詳しくは [主キーの選択](/ja/concepts/best-practices/choosing-a-primary-key) を参照してください。

### 意味を保持する型を使用する {#use-types-that-preserve-meaning}

よりコンパクトな表現を使うと、ストレージ、メモリ、スキャンのコストを削減できます。ただし、情報が失われない範囲で選択してください。

* 将来の増加も見込んだ想定範囲をカバーできるビット幅の整数型を使用し、10進数の厳密な演算が必要な場合は `Decimal` を使用します。
* 繰り返し出現する文字列には `LowCardinality(String)` を、取りうる値が限定された集合には `Enum` を検討します。
* 秒未満の精度が必要な場合は `DateTime64` を使用し、それ以外の場合は `DateTime` または `Date` を検討します。
* 値が存在しないこと自体に固有の意味がある場合は `Nullable` を使用します。欠損値をゼロや空文字列で置換するのは、それらがドメインにおけるデフォルト値として妥当な場合に限ります。
* 構造が安定していて頻繁にクエリされるフィールドには、明示的な型付きカラムを使用します。構造が変化していくデータには `JSON` を、キー・バリュー形式に適したデータには `Map` を検討してください。

変更後は圧縮サイズとクエリパフォーマンスを測定してください。詳しくは [データ型の選択](/ja/concepts/best-practices/select-data-type)、[JSON の使用](/ja/concepts/best-practices/json-type)、[ClickHouse における圧縮](/ja/guides/clickhouse/data-modelling/compression/compression-in-clickhouse) を参照してください。

### データ管理のためのパーティション設計 {#partition-for-data-management}

パーティションは、保持期間やデータ管理操作を基準に設計してください。異なるパーティションに属するパーツ同士がマージされることはないため、パーティションのカーディナリティが過剰になると、小さなデータパーツが大量に生成され、オーバーヘッドが増大する可能性があります。

まずは、パーティション化なし、月単位のパーティション化、年単位のパーティション化のいずれかから始めるのが適切です。データ量と保持期間に見合う場合は、日単位のパーティションも選択肢になります。high-cardinality な識別子でパーティション化する場合は、事前にパーツの数とサイズを評価してください。

パーティションプルーニングは、クエリの条件でパーティション式が絞り込まれる場合に効果を発揮しますが、適切な順序キーの代わりにはなりません。詳しくは [パーティションキーの選択](/ja/concepts/best-practices/partitioning-keys) を参照してください。

### 繰り返し発生する処理を事前計算する {#precompute-repeated-work}

| アプローチ                     | 適した場面                                              | 考慮すべき点                                                                                            |
| ------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| インクリメンタルmaterialized view | 繰り返し実行される集計や変換を挿入時に移せる場合。                          | 書き込み先テーブルのストレージ、挿入時の処理、既存データのバックフィル。新たに挿入されたブロックを処理する仕組みのため、ソーステーブルに対するすべての変更が自動的に反映されるわけではありません。 |
| プロジェクション                  | 別のアクセスパターンに対して、異なるソート順またはサポートされている事前計算済みの表現が必要な場合。 | ストレージと挿入時のオーバーヘッド、既存データのマテリアライズ、クエリおよび ClickHouse のバージョンとの互換性。                                    |

クエリが意図したプロジェクションを使用していることを確認してください。materialized view については、集約と更新のセマンティクスを検証してください。詳しくは [materialized view とプロジェクションの比較](/ja/concepts/features/projections/materialized-views-versus-projections) および [データのバックフィル](/ja/guides/clickhouse/data-modelling/backfilling) を参照してください。

### 結合とスキャンの処理量を削減する {#reduce-join-and-scan-work}

更新モデル上問題がなければ、頻繁にアクセスされる属性を非正規化します。キー・バリューのルックアップには Dictionary の利用を検討してください。その際、重複キーや変化する次元に対して必要な動作が維持されるようにします。

それでも残る結合については、クエリプランと入力のカーディナリティを確認します。最近の ClickHouse のバージョンでは結合の順序が入れ替えられることがあるため、SQL の記述順序だけに頼らず、実際のビルド側を確認してください。まずはデフォルトのアルゴリズムを使用します。メモリや実行時間に具体的な問題が見つかった場合は、別のアルゴリズムを試してください。なお、サポートされる結合の種類はアルゴリズムによって異なります。

必要なカラムのみを選択します。選択性の高いフィルタを適用し、`PREWHERE` とプライマリインデックスによる枝刈りで読み取りが削減されているかを確認します。データの分布と述語によって十分な数のグラニュールをスキップでき、ストレージと評価のコストを相殺できる場合は、スキッピングインデックスを追加してください。

詳しくは、[結合の最小化と最適化](/ja/concepts/best-practices/minimize-optimize-joins)、[データスキッピングインデックス](/ja/concepts/best-practices/using-data-skipping-indices)、[クエリ最適化](/ja/guides/clickhouse/performance-and-monitoring/query-optimization)を参照してください。

## インジェストと保持期間の最適化 {#optimize-ingestion-and-retention}

小さな挿入処理を高頻度で実行すると、マージによる統合が追いつかないペースでパーツが作成されることがあります。クライアント側でのバッチ処理、または[非同期挿入](/ja/concepts/features/operations/insert/asyncinserts)の利用を推奨します。行サイズ、スループット、鮮度の要件に基づいてバッチサイズを決定し、アクティブなデータパーツとマージの状況を監視してください。

デフォルト値を前提とせず、実際に適用されている設定を確認してください:

```sql
SELECT name, value, changed
FROM system.settings
WHERE name IN
(
    'async_insert',
    'wait_for_async_insert',
    'async_insert_max_data_size',
    'async_insert_busy_timeout_ms'
);
```

非同期挿入を使用する場合は、`wait_for_async_insert = 1` を維持してください。これにより、確認応答は flush の完了を待ってから返されるため、クライアントは flush 時のエラーを受け取れます。`0` の場合、確認応答はバッファリングの完了を示すにすぎず、クライアントが成功を受け取った後にエラーが発生する可能性があります。

third-party のインジェストツールを使用する場合は、バッチ処理、再試行、重複排除、エラー処理、バックプレッシャーをエンドツーエンドで検証してください。再試行で重複が発生しないと決めつけず、コネクタの配信保証を確認してください。詳細は [挿入戦略の選択](/ja/concepts/best-practices/selecting-an-insert-strategy) を参照してください。

大規模なミューテーションの頻繁な実行や、`OPTIMIZE TABLE ... FINAL` のルーチン的な実行は避けてください。いずれも大量の書き換えやマージ処理を発生させる可能性があります。更新戦略は、クエリの正確性要件を満たすものを選択してください。サポートされている保持ポリシーには `TTL` を使用し、パーティション全体を削除する場合はパーティション単位の削除を使用してください。Cloud では、ストレージのティア化に `TTL ... TO VOLUME` を使用しません。

[ミューテーションを避ける](/ja/concepts/best-practices/avoid-mutations)、[OPTIMIZE FINAL を避ける](/ja/concepts/best-practices/avoid-optimize-final)、[TTL によるデータ管理](/ja/concepts/features/operations/delete/ttl) も参照してください。

## Cloud リソースの計画 {#plan-cloud-resources}

### キャッシュの状態を考慮する {#account-for-cache-state}

ClickHouse Cloud ではコンピュートとオブジェクトストレージが分離されているため、キャッシュの状態によってレイテンシーが大きく変わることがあります。クエリ結果キャッシュが無効であっても、繰り返し実行されたクエリはキャッシュされたデータを読み取る場合があります。

初回実行時と繰り返し実行時の挙動は、それぞれ個別に測定してください。また、比較結果に影響しうるサービスのアイドル化、リサイズ、ルーティング、バックグラウンド処理も記録してください。[自動アイドル化](/ja/products/cloud/features/autoscaling/idling)を利用するかどうかは、許容できる起動時のレイテンシーを踏まえて判断してください。

リソースを増強する前に、まず枝刈りや事前集約によってワーキングセットを削減してください。プリウォームが必要な場合は、代表的なクエリを使用し、それに伴うリソース消費もコスト評価に含めてください。

クエリ結果キャッシュはデータキャッシュとは別の仕組みです。キャッシュされた結果の利用がアプリケーションの鮮度要件上問題ない場合にのみ有効化してください。詳しくは [キャッシュ](/ja/concepts/features/performance/caches/caches) および [query cache](/ja/concepts/features/performance/caches/query-cache) を参照してください。

### 計測したワークロードに基づくサイジング {#size-for-the-measured-workload}

CPU、メモリ、同時実行数、インジェストを総合的に評価してください。単独のクエリだけでなく、ピーク負荷時の挙動もテストしてください。単一クエリでは目標を満たすサービスでも、クエリの同時実行やインジェストが重なると目標を達成できない場合があります。

垂直スケーリングではレプリカあたりのリソースが、水平スケーリングではレプリカ数が変わります。利用できる機能や自動化の範囲は、ティアおよびプロファイルによって異なります。以前のシステムのメモリ量から固定比率でサイジングするのではなく、[スケーリングの概要](/ja/products/cloud/features/autoscaling/overview)および[サービス制限](/ja/products/cloud/guides/best-practices/usagelimits)を参照してください。

ワークロードと予算に見合ったスケーリングの上限と下限を設定してください。また、リソースの総消費量を計測してください。クエリが高速になっても、コンピュートを大幅に多く消費する場合は、かえってコストが増える可能性があります。

### 競合するワークロードを分離する {#isolate-competing-workloads}

インジェスト、対話型クエリ、バッチ分析にそれぞれ専用のコンピュートが必要な場合は、[warehouse](/ja/products/cloud/features/infrastructure/warehouses) を使用します。warehouse 内のサービスはデータを共有しながら、それぞれ独立したコンピュートリソースとエンドポイントを持ちます。

アプリケーションや third-party ツールは、それぞれ対象とするサービスに振り分けます。負荷をかけた状態で、同時実行数、コネクションプーリング、タイムアウト、再試行を検証してください。分離したワークロードと本番環境のワークロードの両方を計測し、分離によって目標を達成できていることを確認します。

## 結果をベンチマークする {#benchmark-the-result}

1. **ベースラインを保存します。** ClickHouse のバージョン、サービス設定、テーブル定義、設定、データボリューム、および代表的なパラメータを含むクエリテキストを記録します。
2. **ワークロードを統制します。** データ量と同時実行数を同等の条件に保ちます。インジェスト、マージ、バックグラウンド処理の状況を記録します。アプリケーションのレイテンシを測定する場合は、クライアントとネットワーク経路も測定対象に含めます。
3. **キャッシュの条件を分けて測定します。** 初回実行と繰り返し実行の結果は分けて報告します。実行性能の改善を測定する際はクエリ結果キャッシュを無効化し、そのうえでデータキャッシュの影響も考慮します。ベンチマークのために本番環境の共有キャッシュをクリアしないでください。
4. **変更する要素は1つに絞ります。** 「順序キーを変更して読み取るグラニュール数を削減する」といった仮説を明示します。
5. **測定を繰り返します。** ばらつきを把握できるだけの回数を実行します。最速の実行結果だけを示すのではなく、実行回数とあわせて分布やパーセンタイルを報告します。
6. **正確性とトレードオフを確認します。** 結果、鮮度、挿入スループット、メモリ、ストレージ、リソース消費量を比較します。該当する場合は、バックフィルとマテリアライズのコストも含めます。
7. **代表的な負荷の下で検証します。** ロールアウト前に同時実行数とインジェストを再テストし、ロールバック計画を用意しておきます。

顧客やパートナーと調査結果を共有する際は、データセットまたは再現可能な生成方法、使用したクエリそのもの、設定、測定手順を含めてください。また、結果の適用範囲を明記してください。あるワークロードで高速化が得られたとしても、パフォーマンスが一般的に向上することを保証するものではありません。

再現可能な出発点として、[クエリ最適化の実践例](/ja/guides/clickhouse/performance-and-monitoring/query-optimization-example)を参照してください。

## デプロイメントチェックリスト {#deployment-checklist}

* レイテンシ、スループット、鮮度、可用性の目標値を定義します。
* 更新および重複データに関するエンジンのセマンティクスと正確性を検証します。
* 代表的なフィルタを用いて順序キーをテストし、枝刈りの状況を確認します。
* データ型、パーティション数、パーツサイズ、保持期間を見直します。
* 挿入時のバッチ処理、再試行の挙動、マージ負荷を測定します。
* ビュー、プロジェクション、索引の効果と保守コストを確認します。
* キャッシュの挙動、ピーク時の同時実行数、競合するワークロードをテストします。
* スケーリングの上限と下限を設定し、インテグレーションを適切なエンドポイントに振り分けます。
* 再現可能なベースライン、監視基準、ロールバック手順を記録します。
