## コンポーネント {#components}

ClickHouse Connector は 3 つのデーモンを実行します。いずれも `clicklink` バイナリに組み込まれています。

* **executor** は、コネクタ エンドポイント への アウトバウンド コマンドチャネルを保持し、ClickHouse Cloud がクラスター内で管理する サービス 向けに送信するライフサイクルコマンドを適用します。対象となるコマンドは、作成、scale、停止と開始、再起動、バックアップ と バックアップ の削除、削除、および承認済みのプラットフォーム更新 です。すべての操作は Kubernetes API 呼び出しです。ClickHouse への 接続 は開かず、バケット や IAM の認証情報も保持しません。managed モードでのみ実行されます。
* **スクレイパー** は、ClickHouse システムテーブルの allowlist を一定の interval で読み取り、結果をローカルに buffer します。その結果を、インフラストラクチャのメタデータおよびヘルスステータスとともに コネクタ エンドポイント へ送信します。
* **トラブルシューティングツール** は、コネクタ エンドポイント への アウトバウンド コマンドチャネルを保持し、アクティブな [サポートセッション](/ja/products/bring-your-own-cloud/connector/support-sessions) 中に読み取り専用の診断を実行します。session 外では何も実行しません。

Kubernetes では、`clicklink-connector` Helm チャートが、任意に選択した名前空間 (デフォルトは `clicklink`) にデーモンをデプロイします。executor は単一レプリカの Deployment で、コマンドの state を永続 volume 上に保持します。Linux VM では、デーモンは非特権の `clicklink` システムユーザーのもとで `clicklink-scraper`、`clicklink-troubleshooter`、`clicklink-executor` の systemd unit として実行されます。

## 接続 {#connections}

コネクタが確立する接続はすべてアウトバウンドです。全接続の一覧は次のとおりです。

| 宛先                                                      | 方向                       | プロトコル                 | 認証                                                                                                  | 目的                                                                                                                                                                                    |
| ------------------------------------------------------- | ------------------------ | --------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| コネクタエンドポイント (API)                                       | アウトバウンド                  | HTTPS                 | mTLS クライアント証明書と HMAC 署名付きリクエスト                                                                      | メトリクス、コネクタ自身のメトリクス、ステータスの送信、サービス・インフラストラクチャ・バックアップのメタデータの同期、クライアント証明書の更新                                                                                                              |
| コネクタエンドポイント (API、`clicklink clctl` から)                  | アウトバウンド                  | HTTPS                 | コネクタの mTLS クライアント証明書と HMAC 署名付きリクエスト                                                                | `clicklink clctl instances create` の実行時にサービス定義を送信 (`POST /v1/pcm/instances`)                                                                                                          |
| コネクタエンドポイント (トラブルシューターのコマンドチャネル)                        | アウトバウンド                  | WebSocket over TLS    | mTLS クライアント証明書と HMAC 署名付きハンドシェイク                                                                    | サポートセッションがアクティブな間のみ診断コマンドを伝送                                                                                                                                                          |
| コネクタエンドポイント (executor のコマンドチャネル)                        | アウトバウンド                  | WebSocket over TLS    | mTLS クライアント証明書と HMAC 署名付きハンドシェイク                                                                    | マネージドサービスのライフサイクルコマンドを伝送し、その進捗と結果を返却。トラブルシューターのチャネルとは別                                                                                                                                |
| 登録エンドポイント                                               | アウトバウンド                  | HTTPS                 | 使い捨ての登録トークン (引き換え時) または HMAC (初回の証明書署名時)。mTLS は使用しない                                                | セットアップ時のトークン引き換えと初回の証明書発行                                                                                                                                                             |
| ClickHouse クラスター                                        | アウトバウンド (お客様の環境内)        | ClickHouse ネイティブプロトコル | 専用の読み取り専用ユーザー `pcm_scraper` および `pcm_troubleshooter` (bcrypt ハッシュとして保存)                             | スクレイプおよびセッション診断のためのシステムテーブルの読み取りと、scraper によるログテーブルのフラッシュ。executor は ClickHouse への接続を一切確立しない                                                                                          |
| Kubernetes API サーバー (プロビジョニングされたすべてのデプロイメント、両方のインストール先) | アウトバウンド (お客様の環境内)        | HTTPS                 | ロールにバインドされた ServiceAccount。managed モードでは、アドミッションポリシーで制限された `pcm-executor` ServiceAccount            | トラブルシューター向けのワークロードの読み取り専用参照、サービスの名前空間内での executor によるライフサイクル関連の書き込み、および承認されたプラットフォーム更新中のプラットフォーム名前空間内でのワークロードの書き込み。Kubernetes へのインストールでは、デーモンが自動更新されたクライアント証明書を mTLS Secret に書き戻して永続化 |
| Amazon ECR (executor、managed モードのみ)                     | アウトバウンド                  | HTTPS                 | プラットフォームへの直接アクセスでは、コネクタ EC2 VM のインスタンスプロファイルを使用して引き受ける読み取り専用のプルロール。その他の ECR チャートレジストリでは環境の AWS 認証情報 | プラットフォームの同期または作成時にチャートをプルするためのレジストリログイン。プラットフォーム更新中にイメージの存在を確認するための `DescribeImages`                                                                                                  |
| AWS STS (executor、managed モードのみ)                        | アウトバウンド                  | HTTPS                 | プラットフォームへの直接アクセスではコネクタ EC2 VM のインスタンスプロファイル。その他の ECR チャートレジストリでは設定済みの AWS 認証情報チェーン                  | プラットフォームチャートへの直接ログインとイメージ確認のために読み取り専用のプルロールを引き受ける。その他の ECR ログイン用の認証情報を提供する場合もある。executor が呼び出すクラウド API は ECR と STS のみ                                                                 |
| コンテナレジストリ                                               | アウトバウンド (お客様のクラスターノードから) | HTTPS                 | ノードのアイデンティティ: 登録したノードロールに ClickHouse が付与する読み取り専用のプルロール、またはイメージをインポートした後はお客様独自のレジストリ                 | マネージドサービスおよびプラットフォームコンポーネントのイメージのプル。プルするのはお客様のクラスターであり、ClickHouse がそこへ何かをプッシュすることはない                                                                                                  |
| アイデンティティプロバイダーの JWKS エンドポイント (ゲートウェイが有効な場合のみ)           | アウトバウンド                  | HTTPS                 | なし (公開署名鍵)                                                                                          | セッションゲートウェイに提示された OIDC ID トークンの検証                                                                                                                                                     |

すべての API リクエストには、メソッド、パス、タイムスタンプ、ボディのハッシュを対象とした HMAC-SHA256 署名を含む `Authorization` ヘッダーが付与されます。これにより、TLS チャネル内であっても、転送中のリクエストのリプレイや改ざんは不可能です。

インバウンドについては、各デーモンがローカルのヘルスポートを 1 つずつ公開しています。scraper は 8082、トラブルシューターは 8084、executor は 8086 です。このポートでは `/livez`、`/readyz`、`/healthz` に加え、`/metrics` でデーモンの Prometheus メトリクスを提供します。メトリクス専用のポートはありません。executor のローカルコマンド API はループバックにのみバインドされ、どの Service からも公開されません。これ以外のリスナーは、オプトインのセッションゲートウェイのみです。詳細は [サポートセッション](/ja/products/bring-your-own-cloud/connector/support-sessions) を参照してください。ClickHouse Cloud がこれらのいずれかに接続することはありません。

## 証明書のライフサイクル {#certificate-lifecycle}

コネクタは、自身で取得・維持するクライアント証明書を使用してエンドポイントに対して認証を行います。3 つのデーモンはいずれも同じ証明書を提示します。

* **登録。** `clicklink clctl init` は、秘密鍵と証明書署名要求 (CSR) をローカルで生成します。CSR には、コモンネームとして組織 ID が、唯一の DNS SAN としてエンドポイントのホストが設定されます。秘密鍵が環境外に出ることはありません。
* **初回発行。** `init` は、HMAC で認証したうえで `/v1/pcm/cert/sign` の登録用署名エンドポイントに CSR を送信します。対象の組織に有効期限内の証明書がすでに存在する場合、エンドポイントは 409 を返して拒否します。その際 CLI は、既存の証明書のまま完了する方法と、`--force` で置き換える方法を表示します。
* **自動更新。** 3 つのデーモンはいずれも 12 時間ごとに証明書の有効期間を確認します。残り 10 日になると、`/v1/pcm/cert/renew` (mTLS と HMAC) を通じて有効期間 30 日の更新済み証明書を要求します。Kubernetes では、更新された証明書は名前を厳密に指定した RBAC の権限を通じて `clicklink-mtls` Secret に書き戻されます。VM では各デーモンが `/etc/clicklink/tls` に書き込みます。更新にあたって運用担当者の操作は不要です。

コネクタは、エンドポイントのサーバー証明書をシステムのトラストストアに照らして検証します。`api.tls.ca_file` (VM) または `api.tls.caFile` (Helm) が設定されている場合は、登録バンドルに含まれる CA チェーンがこれらのルート証明書に追加されます。

### 環境外に送信されるデータ {#what-leaves}

* **許可リストに登録されたシステムテーブルのメトリクス。** スクレイパーがデフォルトで対象とするのは `metric_log`、`asynchronous_metric_log`、`tables`、`warnings`、`server_settings` です。許可リストは明示的な設定であり、スクレイパーはリスト外のデータを一切読み取りません。
* **インフラストラクチャのメタデータ。** API を通じて同期されるサービス、インフラストラクチャ、バックアップのインベントリです。マネージドサービスの場合は、その状態、現在のレプリカ数と想定レプリカ数、実行中のサーバーバージョンと設定バージョンが含まれます。
* **ヘルス情報とセルフメトリクス。** コンポーネントのステータスと、コネクタ自体の運用メトリクスです。executor のハートビートでは、コマンドチャネルが接続中かどうかも報告されます。さらに、直近のプラットフォーム更新の結果、プラットフォームのコンポーネントのバージョン、直近に適用したバンドルのダイジェストも含まれます。VM にインストールした場合は、Kubernetes アクセスバンドルの状態が `ok`、`expiring`、`expired` のいずれか、あるいはバンドルが存在しないかも報告されます。
* **コマンドの結果。** executor が実行する各ライフサイクルコマンドについて、収束中の進捗と、最終的な成功または失敗(失敗時はエラーテキストを含む)が送信されます。
* **ユーザーが送信したサービス定義。** `clicklink clctl instances create` は、環境 ID、クラウドとリージョン、サービス名、サービスのバケット名と IAM ロール ARN、および冪等性キーを送信します。また、defaultユーザーのパスワードの 2 種類のハッシュ(SHA-256 とダブル SHA-1)も送信されます。
* **サポートセッションの出力。** ユーザーが有効化したセッション中に実行された読み取り専用の診断結果が、マスキング処理を施したうえで送信されます。

### デフォルトで外部に出ないもの {#what-never-leaves}

* **生のクエリテキスト (scrape パス上) 。** `system.query_log` はデフォルトの scrape 対象セットから除外されています。クエリ関連のカラムにはリテラル値が含まれる可能性があり、それに伴って PII やシークレットが含まれることがあるためです。これを再度追加する場合は、デプロイメントごとの override となります。デフォルトのセッションテーブル allowlist には `system.processes` が含まれており、生存中のクエリのテキストが表示されます。その絞り込み方法については [support sessions](/ja/products/bring-your-own-cloud/connector/support-sessions) を参照してください。
* **テーブルのデータおよびバックアップ。** これらはお客様のアカウント内の バケット に留まります。executor はお客様の バケット への認証情報を保持しておらず、読み取ることもできません。
* **認証情報。** `init` は設定ファイルに認証情報を書き込みません。ClickHouse が保存するのはコネクタユーザーのパスワードの bcrypt ハッシュのみで、シークレットは Kubernetes Secrets またはホスト上の root のみが読み取れるファイルに留まります。マネージドサービスの default user のパスワードはお客様側で生成され、一度だけ表示されます。送信されるのはそのハッシュのみです。scrape パスにも同期パスにも、認証情報を送信する処理はありません。
* **マスキングされていない トラブルシューター の出力。** トラブルシューター が返す内容はすべて、外部に出る前に マスキング patterns (組み込みのものとお客様独自のもの) を通過します。[support sessions](/ja/products/bring-your-own-cloud/connector/support-sessions) を参照してください。

## 信頼境界 {#trust-boundaries}

* **お客様の環境が境界です。** ClickHouse Cloud が受け取るのは、コネクタが送信するもの、すなわちスクレイプ結果、ハートビートとステータス、コマンド結果、およびアクティブなサポートセッションが返すデータだけです。ClickHouse Cloud 側からお客様の環境内へ接続を開始することはありません。
* **セッションゲートウェイはお客様が管理します。** Ingress を介した公開を選択しない限り、ゲートウェイにはお客様の環境内からのみ到達できます (Kubernetes では `kubectl port-forward` 経由、VM ではローカル)。ClickHouse Cloud がゲートウェイに接続することはありません。
* **ClickHouse へのアクセスは読み取り専用です。** `pcm_scraper` ユーザーと `pcm_troubleshooter` ユーザーが保持するのは、テーブル単位の `SELECT` 権限、スクレイパー の `READ ON REMOTE` (`clusterAllReplicas()` に必要)、および スクレイパー 専用の `SYSTEM FLUSH LOGS` 権限 1 つのみです。`INSERT`、DDL、ユーザー管理の権限はありません。executor には ClickHouse ユーザーがありません。正確な一覧は[権限モデル](/ja/products/bring-your-own-cloud/connector/reference/privilege-model)に記載されています。
* **スクレイパー と トラブルシューティングツール はクラスターを変更できません。** これらの RBAC は、コネクタおよびサービスの名前空間内の Roles によって定義されます。これらの Roles が付与するのは、ワークロードリソースに対する読み取り専用の verb と、コネクタ自身の Secrets に対する名前を限定したアクセスのみです。`exec`、`delete`、`patch` の権限はありません。
* **executor は `pcm-executor` として、サービスの名前空間内のクラスター状態を変更します。** executor はサービスプレフィックス (デフォルトは `ns-`) を持つ名前空間を作成・削除し、ポッドを再起動する際にはポッドを削除します。これらの名前空間内では、ClickHouseCluster、Backup、ScalingOverride オブジェクトと、サービスに必要な Secrets、ServiceAccount、Service を書き込みます。また、スクレイパー に読み取りアクセスを付与する Role と RoleBinding も書き込みます。ValidatingAdmissionPolicy は、その ServiceAccount によるプレフィックス外への書き込みをすべて拒否します。例外はいずれも executor のホーム名前空間内にあり、自身のトークン更新、`clicklink-instance-registry` ConfigMap、および Kubernetes の場合は mTLS Secret 内の更新されたクライアント証明書が該当します。このポリシーは、評価できない場合はフェイルクローズします。アドミッションは読み取りには適用されないため、これらのリソース種別に対する executor の読み取りはプレフィックスで制限されません。
* **executor がプラットフォームの名前空間を変更するのは、お客様が承認した更新の実行中に `pcm-platform` として動作する場合のみです。** `clicklink clctl platform approve` は、この ID 用に有効期間 2 時間のトークンを発行します。このトークンが更新されることはありません。このトークンで executor が書き込めるのは、Deployment、Service、ConfigMap、Secrets、Job、PodDisruptionBudget のみです。Namespace、CRD、ServiceAccount、RBAC、Webhook およびアドミッションの設定、PriorityClass、StorageClass は、承認時にお客様の認証情報で適用されます。詳しくは[プラットフォーム更新](/ja/products/bring-your-own-cloud/connector/platform-updates)を参照してください。
* **executor はお客様のバケットや IAM に対する認証情報を保持しません。** `clicklink clctl executor prepare` は、サービスのデータ用およびバックアップ用のバケットと IAM ロールを作成し、`clicklink clctl executor teardown` はそれらを削除します。どちらもお客様の認証情報で実行されます。このロールはそのサービスのポッドのみを信頼するため、executor も ClickHouse もこのロールを引き受けることはできません。executor が呼び出すクラウド API は Amazon ECR と STS のみです。プラットフォームの同期または作成時にチャートをプルする際にはレジストリにログインし、プラットフォーム更新中は読み取り専用のプル用ロールでイメージを確認します。
* **ネットワークポリシー。** Kubernetes では、チャートが各デーモンに対してデフォルト拒否の NetworkPolicy を生成します。エグレスが許可されるのは、DNS、コネクタエンドポイント用に指定した CIDR、および Kubernetes API サーバーの CIDR のみです。スクレイパー と トラブルシューティングツール のポリシーでは、これに加えて、executor が管理する名前空間 (executor が付与するラベルで選択) またはお客様が名前で指定した名前空間内の ClickHouse Service への通信も許可されます。executor のポリシーには ClickHouse 向けのルールはありません。プラットフォームバンドルのチャートが Amazon ECR にある場合は、ECR と STS のアドレス範囲 (またはレジストリミラー) を `allowEgressCIDRs` に追加してください。追加しないと、ポリシーを強制する CNI の環境では同期時にチャートをプルできません。ポリシーを強制する CNI がない場合、このポリシーは機能しません。詳しくは[設定](/ja/products/bring-your-own-cloud/connector/configuration)を参照してください。
* **VM におけるホストの堅牢化。** 各ユニットは、ログイン不可のシステムユーザーとして実行され、`ProtectSystem=strict`、`NoNewPrivileges`、読み取り専用の設定パスが適用され、FIPS モードが有効になっています。

コネクタの正確な権限と RBAC ルールについては、[権限モデル](/ja/products/bring-your-own-cloud/connector/reference/privilege-model)のリファレンスを参照してください。ClickHouse 自身がクラスターをプロビジョニング・運用する場合は信頼モデルが異なります。[BYOC アーキテクチャ](/ja/products/bring-your-own-cloud/overview/architecture)および [BYOC 権限](/ja/products/bring-your-own-cloud/reference/privilege)のページを参照してください。
