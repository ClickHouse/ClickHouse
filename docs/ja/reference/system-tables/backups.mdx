<div id="description">
  ## 説明
</div>

現在の状態やその他の属性を含む、すべての `BACKUP` または `RESTORE` 操作の一覧です。なお、このテーブルは永続的ではなく、最後にサーバーを再起動して以降に実行された操作のみが表示されます。

<div id="restore-atomicity">
  ## 復元のアトミック性
</div>

`RESTORE` はトランザクション処理ではないため、失敗してもロールバックされません。各テーブルでは、選択したすべてのパーツが、どのパーツもアタッチされる前にコピーされますが、アタッチのフェーズ自体にはトランザクション性がありません。つまり、パーツは 1 つずつ順に可視状態になります。テーブルはそれぞれ独立して処理されます。

**テーブルは独立しています。** あるテーブルの復元が完了した場合、同じコマンド内の別のテーブルがその後失敗しても、そのテーブルはそのまま残ります。

```sql
RESTORE TABLE db.t0, TABLE db.t1
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

このコマンドが、`db.t0` の復元が完全に完了したあとで、`db.t1` の復元が完了する前に失敗した場合、`db.t0` は復元されたまま残ります。

**`PARTITIONS` 句はコミット境界ではありません。** これは、テーブルのどのパーツを復元するかを選択するだけです。

```sql
RESTORE TABLE db.t0 PARTITIONS '2026-06-01', '2026-06-02', '2026-06-03'
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

選択したテーブル内のパーツは、まずすべてコピーされ、すべての準備が整ってからまとめて一度だけアタッチされます。したがって、このコマンドがコピーのフェーズ中に失敗した場合、たとえばパーティション `2026-06-01` のコピーは完了していても、`2026-06-02` と `2026-06-03` がまだ完了していなければ、`2026-06-01` は**コミットされず**、このコマンドで復元されたデータはテーブルに一切反映されません。コピーのフェーズが完了してアタッチの手順が始まると、パーツは 1 つずつコミットされるため、アタッチ中に失敗すると、ロールバックされないままテーブルが部分的に復元された状態になる可能性があります。

パーティションごとに独立してコミットしたい場合 (つまり、完了したパーティションが後続の失敗後も保持され、個別に再試行できるようにしたい場合) は、パーティションごとに `RESTORE` を個別に実行し、最初の実行以降は `SETTINGS allow_non_empty_tables = true` を使用してください。
