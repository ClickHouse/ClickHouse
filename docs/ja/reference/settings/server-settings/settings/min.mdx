これらの設定は ClickHouse server を構成するためのもので、ClickHouse のソースコードから自動生成されています。

## min_allocation_size_to_log_stack_trace {#min_allocation_size_to_log_stack_trace}

<SettingsInfoBlock type="UInt64" default_value="0" changeable_without_restart="Yes" />

グローバル (サーバー全体) のメモリトラッカーへの 1 回の計上について、stack trace を取得し、`Warning` レベルでサーバーログに書き込み、トレースタイプ `MemoryLargeAllocation` として [`system.trace_log`](/ja/reference/system-tables/trace_log) に挿入する対象となる最小サイズ (バイト単位) です。

しきい値と比較され、報告されるサイズは、トラッカー呼び出し 1 回が計上する量であり、必ずしも 1 回の割り当てに対応するとは限りません。スレッドは小さな割り当てを遅延させ、まとめて 1 回の計上としてフラッシュするため、報告されるサイズは、報告されたスタックの最上位にある割り当てを最大で `max_untracked_memory` 分だけ上回ることがあります。しきい値を `max_untracked_memory` より十分大きく保てば、この差は無視できる程度に収まります。

これは、グローバルに追跡されている合計値がプロセスの実際のメモリ使用量をはるかに超えて増大した状態を診断するためのものです。この状態では、サーバーは上限のごく一部しか使用していないにもかかわらず、0 バイトのものまで含めてすべての割り当てを拒否します。しかも、通常のテレメトリーではその増加の原因を特定できません。`MemoryTrackerBlockerInThread` の下で計上された割り当ては上限チェックとそれに伴うトレースをスキップし、残りを伝えるはずの `system.trace_log` への挿入も、サーバーが行き詰まった時点で失敗するためです。サーバーログへの書き込みは続くため、stack trace はそこに残ります。

スタックの取得とシンボル化はコストが高く、トリガーは繰り返し発生しがちであるため、サーバーの 1 回の実行につき取得されるトレースは最大 10 件です。この設定を実行時にどちら方向へ変更しても、この上限が引き上げられることはありません。

`trace_log` が設定されている必要があります。トレース collector が動作していない場合、トレースを取得しても破棄するほかないため、この値は無視され、[`system.server_settings`](/ja/reference/system-tables/server_settings) では `0` として報告されます。起動処理の後半で行われるこのテーブルの attach よりも前に collector が処理したトレースは、サーバーログにのみ記録されます。

`0` (デフォルト) を指定すると、この診断は無効になります。サーバーが正当に行う最大の割り当てよりも十分大きな値を設定してください。そうしないと、通常の大きな割り当てまでログに記録され、起動時に上限枠をすべて使い切ってしまう可能性があります。

## min_allocation_size_to_throw_on_memory_limit {#min_allocation_size_to_throw_on_memory_limit}

<SettingsInfoBlock type="UInt64" default_value="0" changeable_without_restart="Yes" />

`max_server_memory_usage` に達した際に `MEMORY_LIMIT_EXCEEDED` の発生を許可する、汎用的な C++ の割り当て (標準コンテナー、文字列、`std::vector` の拡張、スマートポインターなどで行われる種類) の最小サイズを、バイト単位で指定します。これより小さい汎用割り当ても引き続きメモリトラッカーに計上されますが、制限超過後も成功が許可されるため、OOM 近傍でのクリーンアップや例外処理の経路における不要な失敗を減らせます。

ClickHouse 自身の大きなバッファ — カラムデータ、ハッシュテーブル、アリーナ、クエリパイプライン、I/O バッファ — による割り当ては常にメモリ制限に従うため、この値に関係なく例外を発生させることがあります。この設定が影響するのは、`operator new` を通る暗黙的な割り当てだけです。

値 `0` (デフォルト) では、従来の動作が維持されます。つまり、暗黙的な `operator new` の割り当てはメモリトラッカーによって拒否されず、`MEMORY_LIMIT_EXCEEDED` を発生させられるのは明示的な ClickHouse の割り当てだけです。

副作用を避けるため、値は `max_untracked_memory` より大きく設定することを推奨します。

## min_os_cpu_wait_time_ratio_to_drop_connection {#min_os_cpu_wait_time_ratio_to_drop_connection}

<SettingsInfoBlock type="Float" default_value="0" changeable_without_restart="Yes" />

接続を切断対象と見なすための、OS の CPU 待機時間 (`OSCPUWaitMicroseconds` Metric) と稼働時間 (`OSCPUVirtualTimeMicroseconds` Metric) の最小比率です。確率の計算には最小比率と最大比率の間の線形補間が使用され、この時点での確率は 0 です。
詳細については、[サーバーの CPU 過負荷時の動作制御](/ja/concepts/features/configuration/settings/server-overload) を参照してください。
