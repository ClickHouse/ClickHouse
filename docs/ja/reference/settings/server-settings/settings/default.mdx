これらの設定は ClickHouse サーバー を設定するもので、ClickHouse のソースコードから自動生成されています。

<div id="default_password_type">
  ## default_password_type
</div>

`CREATE USER u IDENTIFIED BY 'p'` のようなクエリで自動的に設定されるパスワードの種類を指定します。

使用できる値は次のとおりです。

* `plaintext_password`

* `sha256_password`

* `double_sha1_password`

* `bcrypt_password`

* **デフォルト:** `sha256_password`

```xml
<default_password_type>sha256_password</default_password_type>
```

<div id="default_profile">
  ## default_profile
</div>

デフォルトの設定プロファイルです。設定プロファイルは、`user_config` 設定で指定したファイルにあります。

* **デフォルト:** `default`

**例**

```xml
<default_profile>default</default_profile>
```

<div id="default_session_timeout">
  ## default_session_timeout
</div>

デフォルトのセッションタイムアウト。単位はSeconds。

* **デフォルト:** `60`

```xml
<default_session_timeout>60</default_session_timeout>
```

<div id="default_session_user">
  ## default_session_user
</div>

<SettingsInfoBlock type="String" default_value="default" changeable_without_restart="No" />

クライアントがユーザー名を指定せずに接続した場合に認証で使用されるユーザー名です。該当するのは、`user` パラメータおよび `X-ClickHouse-User` ヘッダーがない HTTP リクエスト、ユーザー名が空のネイティブプロトコル `Hello` パケット、ユーザー名が空の MySQL または PostgreSQL ハンドシェイク、`user_name` がない gRPC クエリ、`authorization` ヘッダーがない Arrow Flight 呼び出し (またはユーザー名が空の Basic 認証情報を含む呼び出し) 、あるいは `user` フィールドが省略されているか空である [ウェブターミナル](/ja/concepts/features/interfaces/web-terminal) の WebSocket `auth` メッセージです。

空のユーザー名は認証前にこの値に解決されるため、接続には置き換え後のユーザーの認証が引き続き適用されます。パスワード、ネットワーク、その他のアクセスチェックは通常どおり適用されます。空のユーザー名は設定されたユーザー名の単なるエイリアスであり、これを受け入れても、同じユーザー名を明示的に指定した場合にすでに得られる以上のアクセスが付与されることはありません。この設定が導入される前のバージョンでは、空のユーザー名を `default` にフォールバックする仕組みは、通常の HTTP クエリパラメータ経路、gRPC クエリ、Arrow Flight 呼び出し、およびウェブターミナルにのみ存在し、ネイティブ、MySQL、PostgreSQL プロトコルでは空のユーザー名は拒否されていました。現在はすべてで受け入れられます。この設定が導入される前は、ユーザー名が空の HTTP Basic 認証、および `X-ClickHouse-Key` を含み `X-ClickHouse-User` を含まないリクエストでも、空のユーザー名は拒否されていました。

空文字列に設定した場合、ユーザー名なしの接続は拒否されます。固定ユーザーを持つ HTTP ハンドラー (`http_handlers` ルールの `handler` 内の `user` キー、または `prometheus.handlers` ルールの `handler` 内の `user` キー) は、設定されたユーザーとして認証されるため、影響を受けません。

サーバー設定で `session_log` セクションが有効になっている場合、このような拒否はすべて、空の `user` を持つ `LoginFailure` イベントとして [`system.session_log`](/ja/reference/system-tables/session_log) に記録されます。そのため、ユーザー名なしで拒否された接続をすべてのインターフェイスで監査できます。

デフォルトセッションユーザーが interserver 接続に適用されることはありません。これらはユーザー名の代わりに特別なマーカーで自身を識別し、クラスターシークレットと初期ユーザーによって認証されます。

この値は、`protocols` セクションの `default_session_user` キーを使用して、コンポーザブルプロトコルの特定のエンドポイントに対してオーバーライドできます。詳細は[コンポーザブルプロトコル](/ja/concepts/features/configuration/server-config/composable-protocols)を参照してください。
