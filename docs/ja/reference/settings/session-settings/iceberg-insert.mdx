## iceberg_insert_commit_retry_initial_backoff_ms {#iceberg_insert_commit_retry_initial_backoff_ms}

<SettingsInfoBlock type="UInt64" default_value="10" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "10"},{"label": "新しい設定。Iceberg への `INSERT` のコミットが同時実行のコミットとの競合に敗れた場合、即座にではなく、ランダムな指数バックオフによる遅延の後に再試行されます。"}]}]} />

Iceberg テーブルへの `INSERT` のコミットが同時実行のコミットとの競合に敗れた場合に、最初の再試行までに入れる遅延の上限です。
この上限は再試行のたびに 2 倍になり、最大で `iceberg_insert_commit_retry_max_backoff_ms` まで増加します。各遅延は 0 から上限までの範囲でランダムに選ばれるため、
同じ競合に敗れたライター同士が同時に再試行して再び衝突することを防げます。
遅延は最新のメタデータを参照する前に入るため、同時実行のライターが多い場合には、メタデータ
ディレクトリの一覧取得の頻度を抑える効果もあります。`0` を指定すると遅延なしで再試行します。

## iceberg_insert_max_bytes_in_data_file {#iceberg_insert_max_bytes_in_data_file}

<SettingsInfoBlock type="UInt64" default_value="536870912" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "536870912"},{"label": "Iceberg テーブルプロパティ `write.target-file-size-bytes` のドキュメント記載のデフォルト値（512 MiB）に合わせました。https:\/\/iceberg.apache.org\/docs\/1.5.2\/configuration\/ を参照してください。"}]}, {"id": "row-2","items": [{"label": "25.9"},{"label": "1073741824"},{"label": "新しい設定"}]}]} />

挿入操作時の iceberg parquet データファイルの最大バイト数です。

デフォルト値は、Iceberg テーブルプロパティ `write.target-file-size-bytes` のドキュメント記載のデフォルト値 (512 MiB) に合わせています。
https://iceberg.apache.org/docs/1.5.2/configuration/ を参照してください。この上限は、それまでにファイルへ書き込まれたサイズ、つまり圧縮サイズと比較されます。
そのため、未完了の Parquet 行グループやエンコード中の行グループなど、ライターがまだバッファに保持している分だけ、ファイルが上限を超える場合があります。
なお、`iceberg_insert_max_rows_in_data_file` は
サイズとは無関係にファイルを制限します。

## iceberg_insert_max_data_files_in_upload {#iceberg_insert_max_data_files_in_upload}

<SettingsInfoBlock type="UInt64" default_value="8" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "8"},{"label": "新しい設定。S3 または Azure 上の Iceberg への INSERT で、書き込みが完了したデータファイルごとにアップロードを待機しなくなりました。"}]}]} />

バックグラウンドでアップロードを行うオブジェクトストレージ (S3、Azure) において、`INSERT` が次のファイルを書き込んでいる間、アップロード完了を待たずに保持できる、1 つの挿入ストリーム内の書き込み完了済みデータファイルの最大数です。
このようなファイルは、アップロードが完了するまでアップロード用のバッファを保持します。
そのため、値を大きくするとメモリ消費量は増えますが、より多くのアップロードのレイテンシを隠蔽できます。`0` を指定すると、各データファイルのアップロード完了を待ってから
次のデータファイルを書き込みます。

## iceberg_insert_max_sort_buffer_bytes {#iceberg_insert_max_sort_buffer_bytes}

<SettingsInfoBlock type="UInt64" default_value="1073741824" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "1073741824"},{"label": "新しい設定"}]}]} />

ソート順が定義されたIcebergテーブルへの `INSERT` において、データをソートして書き込む前に、全パーティション合計でバッファに保持できる非圧縮バイト数の上限です。
この上限を超えると、最も大きいバッファが前倒しで書き込まれ、サイズの小さいソート済みデータファイルになります。0 の場合は無制限です。

## iceberg_insert_single_manifest_for_all_partitions {#iceberg_insert_single_manifest_for_all_partitions}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "新しい設定"}]}]} />

パーティション分割されたIcebergテーブルへの `INSERT` で、パーティションごとに1つずつマニフェストファイルを書き込むのではなく、Spark
や PyIceberg と同様に、対象となるすべてのパーティションをまとめて1つのマニフェストファイルに書き込みます。これは挿入ストリーム単位で適用されます。各ストリームは独自のマニフェストを持つ独自の
スナップショットをそれぞれコミットするため、`INSERT` で書き込まれるマニフェストが厳密に1つになるのは `max_insert_threads = 1` の場合に限られます。
さらに、`OPTIMIZE TABLE ... MANIFEST` によって、異なるパーティションのマニフェストも1つにマージされます。
`ALTER TABLE ... DROP PARTITION` では、マニフェストを他のパーティションと共有しているパーティションは削除できません。
