## external_storage_max_read_bytes {#external_storage_max_read_bytes}

<SettingsInfoBlock type="UInt64" default_value="0" />

外部エンジンを使用するテーブルで履歴データをフラッシュする際の最大バイト数を制限します。現在サポートされているのは、MySQL table engine、データベースエンジン、Dictionary のみです。0 の場合、この設定は無効です

## external_storage_max_read_rows {#external_storage_max_read_rows}

<SettingsInfoBlock type="UInt64" default_value="0" />

外部エンジンを使用するテーブルが履歴データをフラッシュする際の最大行数を制限します。現在サポートされているのは、MySQL table engine、データベースエンジン、および Dictionary のみです。0 の場合、この設定は無効です

## external_storage_push_down_limit {#external_storage_push_down_limit}

<SettingsInfoBlock type="Bool" default_value="1" />

クエリの `LIMIT` 句を、外部データベース (MySQL、PostgreSQL、SQLite など) へ送信されるクエリにプッシュダウンできるようにします。

汎用の ODBC/JDBC ブリッジではプッシュダウンは行われません。これらのブリッジはリモート側の `LIMIT` 構文を公開しておらず、またサポート対象のデータベースの中には `LIMIT` 句自体を受け付けないものもあるためです。

`LIMIT` がプッシュダウンされるのは、安全であることが保証される場合、つまり論理的に `LIMIT` より前に適用されるすべての句が、そのまま外部クエリにコピーされる場合に限られます。具体的には、クエリが単一テーブルに対する単純な `SELECT` であり、次の条件を満たす必要があります。

* `JOIN`、`ARRAY JOIN`、`SAMPLE`、`FINAL` を含まないこと (含む場合、行がローカルで削除または変換される可能性があるため、事前に件数を制限するのは望ましくありません) 。
* `WHERE` 句がある場合、その句が完全に互換性を持ち、書き換えられたクエリにそのままコピーされること (そうでない場合、リモートで `LIMIT` を適用した後にフィルタリングすることで、一部の行が失われます) 。
* データの並べ替え、集約、フィルタリングによってリモートでの事前制限のロジックを損なうおそれのある、その他の句や修飾子 (`DISTINCT`、`GROUP BY`、`ORDER BY`、`LIMIT BY`、`WITH TIES` など) を含まないこと。
* `OFFSET` は使用できます。`OFFSET` はローカルで適用されるため、スキップされる行も読み取る必要があり、外部データベースに送信される上限は `offset + length` になります。
* `SELECT` リストがソースの 1 行を結果の 1 行に対応付けること。つまり、集約関数、ウィンドウ関数、`arrayJoin` (`unnest` とも表記) を含まないこと (これらは外部テーブルから読み取ったすべての行に対してローカルで評価されます) 。
* 行ポリシーや `additional_table_filters` など、外部テーブルから読み取った行に対してローカルで適用されるフィルタが存在しないこと (このようなフィルタは `LIMIT` より前に実行されるため、リモートで事前に件数を制限すると、本来残るはずの行が破棄される可能性があります) 。

これにより、外部データベースから読み取られ送信されるデータ量が削減されます。互換性の問題が発生した場合は、この設定を無効化して以前の動作に戻してください。
