## log_query_plans {#log_query_plans}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "実際に実行されたクエリプランを、処理ステップごとのランタイム統計とともに収集するための新しい設定。"}]}]} />

実行されたクエリプランを、処理ステップごとのランタイム統計とともに [`system.query_log`](/ja/reference/system-tables/query_log) の `query_plan` カラムに書き込みます。このカラムは `JSON` 型であるため、統計は数値として保存され、読み取るだけでなくクエリで集計することもできます。

このプランには、[`EXPLAIN ANALYZE`](/ja/reference/statements/explain#explain-analyze) で表示されるものと同じ情報、すなわち処理ステップのツリー、各処理ステップの処理内容、および処理ステップごとの行数、バイト数、ローカル時刻、並列度が含まれます。

収集対象となるのは、アナライザ (`enable_analyzer = 1`、デフォルト) で実行された `SELECT` クエリのみで、さらにその行自体が書き込まれる場合に限られます。そのため、[`log_queries`](/ja/reference/settings/session-settings/log-queries#log_queries) も有効にする必要があります。実行中に失敗したクエリは、実行中だったプランとともに収集されますが、統計は含まれません。`QueryStart` 行では、書き込み時点でまだプランが存在しないため、このカラムは空になります。

プランは、`query` カラムと同様に、サーバーの [`query_masking_rules`](/ja/reference/settings/server-settings/settings/query#query_masking_rules) によってマスキングされます。クエリのテキストまたはクエリパラメータでいずれかのルールに一致したクエリについては、プランは保存されません。定数畳み込みによって、マスキング対象のテキストがどのルールにも一致しない形でプランに入り込む可能性があるためです。それ以外の場合は、フィルター条件、`IN` リスト、出力カラム名など、プランに含まれるすべてのテキストが保存前にマスキングされます。`encrypt` のキーのようなシークレット引数を含むクエリも、プラン内でそれらを確実に隠すことができないため、プランは保存されません。

この設定を有効にすると、収集対象のクエリではプロセッサーごとのタイミングが収集されます。これは [`log_processors_profiles`](/ja/reference/settings/session-settings/log#log_processors_profiles) が使用するものと同じインストルメンテーションであり、オーバーヘッドが発生します。収集対象外のクエリには影響しません。クエリのランダムなサンプルのみを収集するには、[`log_query_plans_probability`](/ja/reference/settings/session-settings/log-query#log_query_plans_probability) を使用してください。

このコストはクエリの実行前に決定されるため、収集対象のクエリは、その行が後から [`log_queries_min_type`](/ja/reference/settings/session-settings/log-queries#log_queries_min_type) や [`log_queries_min_query_duration_ms`](/ja/reference/settings/session-settings/log-queries#log_queries_min_query_duration_ms) によって破棄される場合でもコストが発生します。これらの条件は、その時点ではまだ判断できないためです。[query cache](/ja/concepts/features/performance/caches/query-cache) から結果が返されたクエリはプランを実行しないため、保存するプランもありません。

また、プランの最適化によって生成された処理ステップの説明 (たとえば統合された式) が破棄されずに保持されるようになり、`system.processors_profile_log.plan_step_description` でも確認できるようになります。

## log_query_plans_join_matches {#log_query_plans_join_matches}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "0"},{"label": "`system.query_log` に書き込まれるクエリプランについて、結合の正確な一致行数メトリクスを収集するための新しい設定。"}]}]} />

[`log_query_plans`](/ja/reference/settings/session-settings/log-query#log_query_plans) によってクエリが記録される際、一致行数メトリクスを結合の出力から導出できない場合に限り、そのメトリクスの算出に必要な追加の集計処理を結合で実行します。これは [`EXPLAIN ANALYZE`](/ja/reference/statements/explain#explain-analyze-join-steps) の `matches` 設定と同じ動作です。メトリクスを導出できる場合は、この設定を有効にしなくても保存されます。

`log_query_plans` が有効で、かつクエリが記録対象となっている場合にのみ効果があります。

## log_query_plans_max_size {#log_query_plans_max_size}

<ExperimentalBadge />

<SettingsInfoBlock type="UInt64" default_value="1048576" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "1048576"},{"label": "`system.query_log` に保存されるクエリプランのサイズに上限を設ける新しい設定です。この上限は、以前のバージョンに対する `compatibility` の下でも維持されます。カラム自体が新しく、復元すべき以前の動作が存在しないうえ、サーバーリソースを保護するための設定であるためです。"}]}]} />

[`log_query_plans`](/ja/reference/settings/session-settings/log-query#log_query_plans) によって [`system.query_log`](/ja/reference/system-tables/query_log) の `query_plan` カラムに書き込まれるドキュメントの最大サイズ (バイト単位) です。

プランに含まれるテキストの量は、そのクエリ自体によって決まります。大きな `IN` リスト、長い別名、折り畳まれた定数はいずれもプランにレンダリングされます。この設定により、1 つのクエリが自身の行に保存できる量が制限されます。また、ドキュメントはこのサイズのバッファに書き込まれるため、1 つのプランのレンダリング時に割り当てられるメモリ量も制限されます。

上限に収まらないプランは、切り詰められた状態では保存されません。途中で切れたドキュメントはプランとして成立しないためです。代わりに、カラムには `{"Error": ...}` の形式でその理由が格納されます。

`0` を指定すると上限なしになります。

## log_query_plans_probability {#log_query_plans_probability}

<ExperimentalBadge />

<SettingsInfoBlock type="Float" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "1"},{"label": "`log_query_plans` が有効な場合に、ランダムに抽出したクエリのサンプルについてのみクエリプランを収集するための新しい設定。"}]}]} />

[`log_query_plans`](/ja/reference/settings/session-settings/log-query#log_query_plans) で有効化されるクエリプランの収集を、指定した確率でランダムに選ばれたクエリのサンプルに限定して行います。選ばれなかったクエリでは [`log_query_plans`](/ja/reference/settings/session-settings/log-query#log_query_plans) によるプロファイリングのコストが発生しません。その場合も `system.query_log` の行は書き込まれますが、`query_plan` カラムは空になります。

この選択は、クエリのプランを収集できることが判明した時点でクエリごとに行われます。そのため、収集の対象にならないクエリ (例えば `SELECT` 以外のクエリ) はサンプリングの対象外です。

この設定は [`log_queries_probability`](/ja/reference/settings/session-settings/log-queries#log_queries_probability) に重ねて適用されます。行が書き込まれないクエリはプランも収集されないため、両方の設定を `0.5` にすると、プランが収集されるのは全クエリの約 4 分の 1 になります。

選択はクエリの実行前に行われるため、クエリの所要時間に応じて選択を変えることはできません。[`log_queries_min_query_duration_ms`](/ja/reference/settings/session-settings/log-queries#log_queries_min_query_duration_ms) と併用した場合、スロークエリの行はすべて書き込まれますが、プランを含むのはそのうち指定した割合の行だけです。一方、プロファイリングのコストは、高速なクエリも含めた全クエリのうち同じ割合で発生します。

設定可能な値:

* 0 — クエリプランを収集しません。
* 範囲 [0..1] の正の floating-point 数値。例えば、設定値が `0.1` の場合、およそ 10 件に 1 件のクエリのプランが収集されます。
* 1 — すべてのクエリのプランを収集します。

## log_query_plans_time {#log_query_plans_time}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "0"},{"label": "`system.query_log` に書き込まれるクエリプランについて、処理ステップごとのローカル時刻と同時実行数を収集する新しい設定です。"}]}]} />

[`log_query_plans`](/ja/reference/settings/session-settings/log-query#log_query_plans) がクエリを収集する際に、そのプロセッサーの作業インターバルもあわせて収集します。これは [`EXPLAIN ANALYZE`](/ja/reference/statements/explain#explain-analyze-concurrency) の `time` 設定と同じ動作です。これにより、`system.query_log.query_plan` に保存されるプランでは、各処理ステップに `Time` グループと `Concurrency` グループが追加され、各処理ステップおよびそのブランチのローカル時刻と同時実行数が記録されます。さらに、プランのルートには `ExecutionTimeBreakdown` が追加されます。これは実行時間を、プランの処理ステップ内で費やされた時間、処理ステップ外で費やされた時間、およびどのスレッドも何も実行していなかった時間に分割したものです。

これらの収集では、クエリが実行するプロセッサータスクの数に比例してメモリと CPU を消費するため、クエリが長くなるほどコストも増大します。また、クエリ終了後にこれらを処理する分だけ、クエリの所要時間も長くなります。

この設定は、`log_query_plans` が有効で、かつクエリが収集される場合にのみ効果があります。

## log_query_threads {#log_query_threads}

<SettingsInfoBlock type="Bool" default_value="0" />

クエリスレッドのログ記録を設定します。

クエリスレッドは [system.query&#95;thread&#95;log](/ja/reference/system-tables/query_thread_log) テーブルに記録されます。この設定は、[log&#95;queries](/ja/reference/settings/session-settings/log-queries#log_queries) が true の場合にのみ有効です。この設定を有効にすると、ClickHouse が実行するクエリのスレッドが、サーバー設定パラメータ [query&#95;thread&#95;log](/ja/reference/settings/server-settings/settings/query#query_thread_log) のルールに従って記録されます。

設定可能な値:

* 0 — 無効。
* 1 — 有効。

**例**

```text
log_query_threads=1
```

## log_query_views {#log_query_views}

<SettingsInfoBlock type="Bool" default_value="1" />

クエリビューのログ記録を設定します。

この設定を有効にして ClickHouse が実行するクエリに関連するビュー (materialized view または live view) がある場合、それらはサーバー設定パラメータ [query&#95;views&#95;log](/ja/reference/settings/server-settings/settings/query#query_views_log) に記録されます。

例:

```text
log_query_views=1
```
