## iceberg_list_only_v_prefixed_metadata_files {#iceberg_list_only_v_prefixed_metadata_files}

S3 または Azure 上のIcebergテーブルをパス指定で読み取る際、キープレフィックス `metadata/v` のみを一覧表示して最新のメタデータファイルを探します。これにより、同じ `metadata` ディレクトリに保存されているマニフェストは一覧表示の対象外となります。このプレフィックス配下に `.metadata.json` ファイルが存在する場合はそれらのみが候補となり、存在しない場合はディレクトリ全体が一覧表示されます。`iceberg_use_version_hint`、`iceberg_metadata_file_path`、`iceberg_metadata_table_uuid`、`iceberg_recent_metadata_file_by_last_updated_ms_field` のいずれかと併用した場合や、データレイクカタログデータベースのテーブルには適用されません。

この設定は、すべてのメタデータファイルが `v<N>...` という形式の名前 (ClickHouse および Hadoop カタログが使用する命名規則) であるテーブルに対してのみ有効化してください。`<N>-<uuid>.metadata.json` ファイルが混在するディレクトリでは、それらのファイルが候補になることはないため、それらを書き込んだライターによるコミットは認識されません。

テーブルの読み取り中に同時実行でデコードされる Iceberg マニフェストファイルの最大数です。

削除マニフェストは、データファイルが 1 つでも読み取られる前にすべてデコードされます。データマニフェストは、クエリ対象のデータファイル一覧が生成される間にデコードされ、クエリがデコード済みのエントリを消費するのに合わせて新たなものがデコードされます。複数のマニフェストを同時にデコードすることで、object storage へのラウンドトリップとエントリごとの pruning 処理を重ね合わせることができます。

ゼロより大きい値である必要があります。`1` の場合はマニフェストを 1 つずつデコードします。

## iceberg_tolerate_conflicting_manifest_schemas {#iceberg_tolerate_conflicting_manifest_schemas}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "1"},{"label": "新しい設定: Iceberg のマニフェストファイルヘッダーが、metadata.json から同じ schema-id に対して登録されているスキーマと競合するスキーマを持つ場合、クエリを失敗させるのではなく、metadata.json のスキーマを優先し、他のクエリエンジンの挙動に合わせます。`compatibility` を 26.10 未満に設定すると、従来の厳格な挙動に戻ります。"}]}]} />

有効な場合、Iceberg のマニフェストファイルの schema-id が metadata.json からすでに登録されていれば、metadata.json のスキーマが使用され、マニフェストファイルヘッダーの `schema` キーにあるコピーは比較されずに無視されます。無効な場合、マニフェストヘッダー側のコピーは metadata.json のスキーマと比較され、競合が発生するとクエリは ICEBERG&#95;SPECIFICATION&#95;VIOLATION エラーで失敗します。

マニフェストヘッダーのスキーマは、マニフェストが書き込まれた時点のテーブルスキーマのコピーにすぎず、一部の writer (例: AWS S3 Tables のメンテナンスジョブ) がそこに劣化したコピーを保存する事例が確認されています。他のクエリエンジンは metadata.json からスキーマを解決し、内容が食い違うヘッダー側のコピーを無視するため、デフォルトの挙動もそれに倣っています。なお、2 つの metadata.json のスキーマ定義間に競合がある場合は、引き続き常にクエリが失敗します。
