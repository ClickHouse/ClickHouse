## min_compress_block_size {#min_compress_block_size}

<SettingsInfoBlock type="UInt64" default_value="65536" />

[MergeTree](/ja/reference/engines/table-engines/mergetree-family/mergetree) テーブルで使用されます。クエリ処理時のレイテンシを抑えるため、サイズが `min_compress_block_size` 以上の block は、次の mark の書き込み時に圧縮されます。デフォルト値は 65,536 です。

非圧縮データが `max_compress_block_size` 未満の場合、実際の block サイズはこの値以上であり、かつ 1 つの mark 分のデータ量以上になります。

例を見てみましょう。テーブル作成時に `index_granularity` が 8192 に設定されているとします。

UInt32 型のカラム (値 1 つあたり 4 バイト) を書き込む場合、8192 行を書き込むと合計 32 KB のデータになります。min&#95;compress&#95;block&#95;size = 65,536 であるため、圧縮 block は 2 つの mark ごとに作成されます。

String 型の URL カラム (値 1 つあたりの平均サイズが 60 バイト) を書き込む場合、8192 行を書き込むと平均で 500 KB 弱のデータになります。これは 65,536 を超えるため、圧縮 block は mark ごとに作成されます。この場合、ディスクから 1 つの mark の範囲のデータを読み取る際に、余分なデータが展開されることはありません。

<Note>
  これは上級者向けの設定です。ClickHouse を使い始めたばかりであれば、変更しないでください。
</Note>

## min_marks_per_part_to_load_statistics {#min_marks_per_part_to_load_statistics}

<SettingsInfoBlock type="UInt64" default_value="64" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "64"},{"label": "主キーによって読み取り量が小さく絞り込まれる場合に、統計の読み込みをスキップするための新しい設定。"}]}]} />

パーツの枝刈りおよび `PREWHERE` の条件の順序付けのためにカラム統計を読み込む際の、主キー解析後に読み取り対象として残るマーク数の最小値です (統計がまだメモリ上にないデータパーツあたりの値)。

統計の読み込みにはデータパーツごとに数回の読み取りが必要です。主キーによって読み取り対象がすでに少数のグラニュールに絞り込まれている場合、コールドスタート時にはデータそのものを読み取るよりも時間がかかることがあります。読み取り対象として残るマーク数が、この設定値と統計の読み込み対象となるパーツ数の積より少ない場合、これらの最適化のための統計は読み込まれません。つまり、統計によるパーツの除外は行われず、`PREWHERE` の条件は統計を持たないテーブルと同様に、カラムのサイズに基づいて順序付けされます。すでにメモリ上にある統計は、読み取り量にかかわらず使用されます。

統計から `min`、`max`、`count` を算出する処理 (`use_statistics_for_min_max_aggregation` を参照) は読み取り自体を置き換えるものであるため、この設定の影響を受けません。

設定可能な値:

* 0 — 読み取り量にかかわらず統計を読み込みます。
* 正の整数 — データパーツあたりのマーク数。

## min_outstreams_per_resize_after_split {#min_outstreams_per_resize_after_split}

<SettingsInfoBlock type="UInt64" default_value="24" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.6"},{"label": "24"},{"label": "新しい設定"}]}]} />

パイプライン生成時に分割が実行された後の、`Resize` または `StrictResize` プロセッサの出力ストリーム数の最小値を指定します。結果のストリーム数がこの値未満の場合、分割操作は実行されません。

### Resize ノードとは {#what-is-a-resize-node}

`Resize` ノードは、クエリパイプライン内を流れるデータストリーム数を調整するプロセッサです。複数のスレッドやプロセッサ間でワークロードのバランスを取るために、ストリーム数を増減できます。たとえば、クエリでより高い並列度が必要な場合、`Resize` ノードは単一ストリームを複数のストリームに分割できます。逆に、複数のストリームをより少ない数のストリームにマージして、データ処理を集約することもできます。

`Resize` ノードは、データブロックの構造を維持したまま、データが各ストリームに均等に分配されるようにします。これにより、リソース使用状況を最適化し、クエリパフォーマンスを向上させることができます。

### Resize ノードを分割する必要がある理由 {#why-the-resize-node-needs-to-be-split}

パイプラインの実行中、中央ハブとなる `Resize` ノードの ExecutingGraph::Node::status&#95;mutex では、特にコア数の多い環境で深刻な contention が発生し、この contention によって次のような問題が生じます。

1. ExecutingGraph::updateNode のレイテンシが増加し、クエリパフォーマンスに直接影響します。
2. スピンロックの contention (native&#95;queued&#95;spin&#95;lock&#95;slowpath) によって過剰な CPU サイクルが浪費され、効率が低下します。
3. CPU 使用率が低下し、並列度とスループットが制限されます。

### Resize ノードの分割方法 {#how-the-resize-node-gets-split}

1. まず出力ストリーム数を確認し、分割を実行可能かどうかを判定します。各分割 プロセッサ の出力ストリーム数は、`min_outstreams_per_resize_after_split` のしきい値以上である必要があります。
2. `Resize` ノードは、同じ数のポートを持つ複数の小さな `Resize` ノードに分割され、それぞれが入力ストリームと出力ストリームの一部を処理します。
3. 各グループは独立して処理されるため、ロック競合が軽減されます。

### 任意の入力/出力を持つ Resize ノードの分割 {#splitting-resize-node-with-arbitrary-inputsoutputs}

入力/出力の数が分割された `Resize` ノードの数で割り切れない場合、一部の入力は `NullSource` に、一部の出力は `NullSink` に接続されます。これにより、全体のデータフローに影響を与えることなく分割できます。

### 設定の目的 {#purpose-of-the-setting}

`min_outstreams_per_resize_after_split` 設定は、`Resize` ノードの分割が適切に機能するようにし、ストリーム数が少なすぎて並列処理の効率が低下するのを防ぎます。出力ストリームの最小数を確保することで、ストリームの分割やマージを伴うシナリオでも並列度とオーバーヘッドのバランスを維持し、クエリ実行を最適化します。

### 設定を無効にする {#disabling-the-setting}

`Resize` ノードの分割を無効にするには、この設定を 0 に設定します。これにより、パイプライン生成時に `Resize` ノードが分割されなくなり、より小さなノードに分けられることなく、元の構造を維持できます。

## min_rows_for_packed_string_keys_in_hash_join {#min_rows_for_packed_string_keys_in_hash_join}

<SettingsInfoBlock type="UInt64" default_value="100000" />

右側の行数の推定値があるハッシュ結合では、正確なキーを保持するハッシュテーブルが CPU の L2 キャッシュをおおよそ上回る場合、またはこの設定が 0 の場合にのみ、`String` キーをパックします (`enable_packed_string_keys_in_hash_join` を参照) 。テーブルのサイズは、右側の行数に 1 行あたりのバイト数を掛けた値です。1 行あたりのバイト数は、32 バイトのセルにキーの平均長を加えた値で、平均長が不明な場合は 0 として扱います。小さな結合ではキーをパックしてもほとんど効果がなく、かえって遅くなる場合があります。

15 バイトを超えるパック済みキーは、左側のすべての行についてハッシュされます。主に一致する行を通過させるランタイムフィルタ (`enable_join_runtime_filters` を参照) を持つ結合では、一致する行のみがハッシュされるため、最小値は必要ありません。そのようなフィルタがない場合、この設定は右側の行数の最小値として機能します。この設定は、キーの平均長が 15 バイトを超える場合と、長さが不明な場合に適用されます。長さが不明なキーは長いキーとして扱われるためです。長さはキーの `basic` カラム STATISTICS から取得されます。`MergeTree` テーブルではデフォルトで収集されます (`auto_statistics_types` を参照) 。

キーが `Memory` テーブルのカラムである場合、サブクエリの集約関数の結果である場合、または `concat(k, 'x')` や `hex(k)` のような `ON` 内の式の結果である場合、キーには統計情報がありません。`OR` を含む結合では統計情報は使用されません。カラムをそのまま受け渡すだけのサブクエリや、そのカラムでグループ化するサブクエリでは、統計情報が保持されます。

`SEMI` および `ANTI` 以外の `LEFT` 結合と `FULL` 結合は、左側のすべての行を保持するため、ランタイムフィルタは適用されません。`LEFT ANTI` 結合のフィルタは一致しない行を通過させるため、対象外です。

`collect_hash_table_stats_during_joins` が有効な場合、行数には同じ結合の過去の実行時における右側の行数が使用されます。それ以外の場合は、クエリオプティマイザーの推定値 (`parallel_hash_join_threshold` でも使用されるもの) が使用されます。オプティマイザの推定値がない場合は、このサーバー自身が右テーブルを読み取る際の推定値が使用されます。いずれもない結合では、クエリを計画したサーバーが右側の行数をこの最小値未満と推定した場合を除き、キーをパックします。分散クエリでは、各サーバーがそれぞれの推定値、統計情報、キャッシュサイズに基づいて判断します。

0 の場合は、すべての結合でキーをパックします。
