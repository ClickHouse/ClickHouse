## enable_join_runtime_filters_index_analysis {#enable_join_runtime_filters_index_analysis}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "JOINランタイムフィルタがProduction tierの機能になりました。"}]}, {"id": "row-2","items": [{"label": "26.7"},{"label": "0"},{"label": "動的な索引解析による結合時のフィルタリングを有効にする新しい設定"}]}, {"id": "row-3","items": [{"label": "26.10"},{"label": "1"},{"label": "ビルド側（右側）で収集したランタイムフィルタを使い、JOINのプローブ側（左側）のグラニュールを刈り込みます。"}]}]} />

ビルド側で収集したランタイムフィルタを使い、JOINのプローブ側のグラニュールを刈り込みます。`enable_join_runtime_filters`を参照してください。
`use_skip_indexes_on_data_read = 1`の場合にのみ効果があります。
刈り込みの対象となるのは、プローブ側の主キー列であるか、`minmax`、`set`、`bloom_filter`のいずれかのスキップ索引でカバーされている結合キーのみです。
ランタイムフィルタがキーの正確な値を保持している場合、それらの値を含む`IN`集合を刈り込み条件に使用します。それ以外の場合はキーの最小値から最大値までの範囲を使用しますが、刈り込み効果は低くなります。

結合のプローブ側をローカルで読み取る場合にのみ有効です。刈り込みを制御するディスクリプタは、クエリプランの最適化時に読み取りステップに付与されますが、そのステップをリモート実行用に再構築する際には引き継がれません。そのため、並列レプリカ (`enable_parallel_replicas = 1`) または分散クエリプラン (`make_distributed_plan = 1`) では、グラニュールの刈り込みは行われません。これらのモードでは、この設定は効果を持ちません。クエリの結果は変わらず、JOINランタイムフィルタ自体もこの設定を無効にした場合とまったく同じように動作します。行われなくなるのはグラニュールの刈り込みだけです。

プローブ側を`FINAL`で読み取る場合も、グラニュールの刈り込みは行われません (`FINAL`を使用した読み取りでは刈り込みが実装されておらず、`optimizeLazyFinal`はディスクリプタなしで読み取りを再構築します) 。処理待ちのデータ、`ALTER`ミューテーション、またはパッチパートがあるテーブルでも同様です。これらの場合も、この設定は効果を持ちません。

## enable_join_transitive_predicates {#enable_join_transitive_predicates}

<BetaBadge />

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.6"},{"label": "1"},{"label": "enable_join_transitive_predicates をデフォルトで有効化"}]}, {"id": "row-2","items": [{"label": "26.4"},{"label": "0"},{"label": "JOIN 順序最適化のために、推移的な等値 JOIN 述語を推論する新しい設定。"}]}]} />

既存の JOIN 条件から、推移的な等値 JOIN 述語を推論します。
たとえば、`A.x = B.x` と `B.x = C.x` が与えられている場合、新たに `A.x = C.x` という述語
が追加され、JOIN 順序オプティマイザが (A JOIN C) のような直接的なプランを検討できるようになります。
