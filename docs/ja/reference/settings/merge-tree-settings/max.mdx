## max_avg_part_size_for_too_many_parts {#max_avg_part_size_for_too_many_parts}

<SettingsInfoBlock type="UInt64" default_value="1073741824" />

`parts_to_delay_insert` および
`parts_to_throw_insert` に基づく「パーツが多すぎる」チェックは、平均パーツサイズ (該当する
パーティション内) が指定したしきい値以下の場合にのみ有効になります。平均パーツサイズが
指定したしきい値を上回る場合、INSERT は遅延も拒否もされません。
これにより、パーツがより大きなパーツへ正常にマージされている限り、単一の
サーバー上の単一のテーブルで数百テラバイトを扱えるようになります。これは
非アクティブなパーツ数や総パーツ数に対するしきい値には影響しません。

## max_compress_block_size {#max_compress_block_size}

## max_concurrent_queries {#max_concurrent_queries}

<SettingsInfoBlock type="UInt64" default_value="0" />

MergeTree テーブル に関連して同時実行されるクエリの最大数です。
クエリは、他の `max_concurrent_queries` 設定によっても引き続き制限されます。

設定可能な値:

* 正の整数。
* `0` — 制限なし。

デフォルト値: `0` (制限なし) 。

**例**

```xml
<max_concurrent_queries>50</max_concurrent_queries>
```

## max_file_name_length {#max_file_name_length}

<SettingsInfoBlock type="UInt64" default_value="127" />

ハッシュ化せずにそのまま保持するファイル名の最大長です。
この設定は、設定 `replace_long_file_name_to_hash` が有効な場合にのみ機能します。
この設定の値にはファイル拡張子の長さは含まれません。そのため、
filesystem エラーを避けるには、最大ファイル名長 (通常は 255
バイト) よりも、ある程度のギャップを持たせて小さめに設定することを推奨します。

## max_table_size_bytes_compressed {#max_table_size_bytes_compressed}

<SettingsInfoBlock type="UInt64" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "テーブルのすべてのアクティブおよび非アクティブなデータパーツにわたる圧縮バイト数の合計を制限する新しい設定。"}]}]} />

テーブルのすべてのアクティブおよび非アクティブなデータパーツにわたる圧縮バイト数 (ディスク上のサイズ) の合計がこの値を超えると、`INSERT` は `Table size limit exceeded` 例外により中断されます。この設定の目的はディスク使用量を制限することであるため、非アクティブなパーツも計上されます。なお、非アクティブなパーツはバックグラウンドで削除されるため (`old_parts_lifetime` 設定を参照) 、観測されるサイズは時間の経過とともに減少することがあります。この制限は `INSERT` の開始時と、新しいデータパーツがワーキングセットにコミットされるとき (バックグラウンドマージやミューテーションの結果を含む) にチェックされます。materialized view による挿入もチェック対象です。一方、レプリケーションフェッチではチェックされないため、複数のレプリカへ並列に挿入した場合に制限を超過してしまうレースコンディションが起こり得ます。空のデータパーツのコミットは常に許可されるため、制限を超えたテーブルからでも、たとえば `TRUNCATE` や `ALTER TABLE ... DROP PARTITION` でデータを削除できます。

設定可能な値:

* 任意の正の整数。
* 0 — 無制限。

マルチテナント、一時的な用途、デモ用のサービスで有用です。

## max_table_size_bytes_uncompressed {#max_table_size_bytes_uncompressed}

<SettingsInfoBlock type="UInt64" default_value="0" />

## max_table_size_rows {#max_table_size_rows}

<SettingsInfoBlock type="UInt64" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "テーブルのアクティブなデータパーツに含まれる行の総数を制限する新しい設定。"}]}]} />

テーブルのアクティブなデータパーツに含まれる行の総数がこの値を超えると、
`INSERT` は `Table size limit exceeded` 例外で中断されます。この制限は
`INSERT` の開始時、および新しいデータパーツがワーキングセットにコミットされる際
(バックグラウンドマージおよびミューテーションの結果を含む) にチェックされます
(したがって、テーブルサイズを制限を超えて増加させるミューテーションは、完了しないまま
リトライされ続けます) 。materialized view による挿入もチェック対象です。一方、
レプリケーションフェッチではチェックされないため、複数のレプリカへ並列に挿入した場合に
制限を超過してしまうレースコンディションが発生し得ます。空のデータパーツのコミットは常に許可
されるため、制限を超えたテーブルからデータを削除することは可能です。たとえば
`TRUNCATE` や `ALTER TABLE ... DROP PARTITION` を使用できます。

設定可能な値:

* 任意の正の整数。
* 0 — 無制限。

マルチテナント、一時的、デモ用のサービスで有用です。
