このページでは、`KILL QUERY`、`KILL MUTATION`、`KILL TRANSACTION`、`KILL PART_MOVE_TO_SHARD` の各ステートメントについて説明します。

デフォルトでは、`KILL QUERY` は、現在の `KILL` ステートメントを除いた結果、`WHERE` 式の条件を満たす対象行が `system.processes` に残らない場合に `NOTHING_TO_KILL` 例外をスローします。また `KILL MUTATION` は、`WHERE` 式に一致する行が `system.mutations` に 1 行もない場合に例外をスローします。一致する対象がない場合でも例外を発生させないようにするには、[`kill_throw_if_noop`](/ja/operations/settings/settings#kill_throw_if_noop) を `false` に設定します。
`KILL TRANSACTION` と `KILL PART_MOVE_TO_SHARD` は、一致する対象がなくても例外をスローせず、空の結果を返します。
`ON CLUSTER` で実行した場合は、一致結果がホスト間で集計されないため、一致する対象がなくても例外はスローされません。

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

現在実行中のクエリを強制終了しようとします。
終了対象のクエリは、`KILL` クエリの `WHERE` 句で定義された条件を使用して、system.processes テーブルから選択されます。

例:

まず、未完了のクエリの一覧を取得する必要があります。この SQL クエリでは、実行時間が長い順に表示されます。

単一の ClickHouse ノードでの一覧:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

ClickHouseクラスターの一覧:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

クエリを強制終了します。

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  ClickHouse Cloud またはセルフマネージドのクラスターでクエリを停止する場合は、すべてのレプリカでクエリが停止されるよう、必ず `ON CLUSTER [cluster-name]` オプションを使用してください
</Tip>

読み取り専用ユーザーは、自分自身のクエリしか停止できません。

`system.processes` に対する `SELECT` 権限が付与されていないユーザーでも、クエリ ID を指定すれば自分自身のクエリを停止できます。
`KILL QUERY WHERE query_id = '<id>'`。その権限も `KILL QUERY` 権限も持たないユーザーが、自分が実行していない
クエリの ID を指定した場合、クエリは停止されず、デフォルトでは `NOTHING_TO_KILL` 例外がスローされます。
[`kill_throw_if_noop`](/ja/operations/settings/settings#kill_throw_if_noop) が `false` に設定されている場合は、例外の代わりに、結果の行が返されないだけになります。
一方、`KILL QUERY` 権限を持っていてもその `SELECT` 権限を持たないユーザーは、`SELECT` 権限がないため拒否されます。
その他の `WHERE` 条件と `ON CLUSTER` には、引き続き上記の権限が必要です。

デフォルトでは、クエリの非同期バージョン (`ASYNC`) が使用され、クエリが停止したことの確認は待機しません。

同期バージョン (`SYNC`) は、すべてのクエリが停止するまで待機し、各プロセスの停止時にその情報を表示します。
レスポンスには `kill_status` カラムが含まれ、このカラムは次の値を取ります。

1. `finished` – クエリは正常に停止されました。
2. `waiting` – クエリに停止シグナルを送信した後、その終了を待機しています。
3. その他の値は、クエリを停止できない理由を示します。

テストクエリ (`TEST`) は、ユーザーの権限を確認し、停止対象のクエリの一覧を表示するだけです。

## KILL MUTATION {#kill-mutation}

長時間実行されている、または完了していない ミューテーション がある場合、ClickHouseサービスの動作状態が悪化している可能性があります。ミューテーション は非同期で実行されるため、システム上の利用可能なリソースをすべて消費してしまうことがあります。必要に応じて、次のいずれかを行ってください。

* 新しい ミューテーション、`INSERT`、`SELECT` をすべて一時停止し、ミューテーション の queue が処理を完了するまで待ちます。
* または、`KILL` コマンドを送信して、これらの ミューテーション の一部を手動で停止します。

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

現在実行中の[ミューテーション](/ja/reference/statements/alter/index#mutations)のキャンセルと削除を試みます。キャンセルするミューテーションは、`KILL` クエリの `WHERE` 句で指定したフィルタを使用して [`system.mutations`](/ja/reference/system-tables/mutations) テーブルから選択されます。

テストクエリ (`TEST`) は、ユーザーの権限を確認し、停止対象のミューテーションの一覧を表示するだけです。

例:

未完了のミューテーション数の `count()` を取得します:

単一の ClickHouse ノードにおけるミューテーション数:

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

ClickHouseレプリカクラスターのミューテーション数:

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

未完了のミューテーションの一覧をクエリします:

単一のClickHouseノードのミューテーション一覧:

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

ClickHouse クラスター内のミューテーション一覧:

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

必要に応じてミューテーションを強制終了します:

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

このクエリは、ミューテーションが停止して完了できなくなった場合に有用です (たとえば、ミューテーションのクエリ内の関数が、テーブル内のデータに適用された際に例外をスローする場合) 。

ミューテーションによってすでに行われた変更はロールバックされません。

<Note>
  [system.mutations](/ja/reference/system-tables/mutations) テーブルの `is_killed=1` カラム (ClickHouse Cloud のみ) は、必ずしもそのミューテーションが完全に終了したことを意味するわけではありません。ミューテーションが `is_killed=1` かつ `is_done=0` の状態のまま、長時間残ることがあります。これは、別の長時間実行中のミューテーションが、強制終了されたミューテーションをブロックしている場合に発生する可能性があります。これは正常な状態です。
</Note>

## KILL TRANSACTION {#kill-transaction}

導入バージョン: v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  このステートメントは実験的機能群の一部です。
  実験的なトランザクションサポートを有効化するには、次の設定を[設定ファイル](/ja/concepts/features/configuration/server-config/configuration-files)に追加してください。

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  詳細については、[トランザクション (ACID) のサポート](/ja/concepts/features/operations/insert/transactions#transactions-commit-and-rollback)のページを参照してください。
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

`WHERE` 句で [`system.transactions`](/ja/reference/system-tables/transactions) テーブルから選択された実行中の[トランザクション](/ja/reference/statements/transactions)をロールバックします。
強制終了されたトランザクションの session は、[`COMMIT`](/ja/reference/statements/transactions#commit) で説明されているクエリ失敗後と同じステートになります。つまり、`ROLLBACK` を実行するまでは、`COMMIT` が `INVALID_TRANSACTION` 例外をスローします。

このステートメントを実行するには、`KILL TRANSACTION` 権限と、`system.transactions` に対する `SELECT` 権限が必要です。
応答には `kill_status` カラムが含まれ、ロールバックされたトランザクションでは値が `waiting` になります。その後に、`system.transactions` の `tid`、`tid_hash`、`elapsed`、`is_readonly`、`state` カラムが続きます。

テストクエリ (`TEST`) では、ユーザーの権限をチェックし、ロールバック対象のトランザクションの一覧を表示するだけです。

例:

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

導入バージョン: v21.11.0

<ExperimentalBadge />

<Note>
  分片間でのパーツの移動は実験的機能です。MergeTree 設定 [`part_moves_between_shards_enable`](/ja/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable) により、テーブルごとに有効化します。
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

`ALTER TABLE ... MOVE PART ... TO SHARD` によって開始された分片間のパーツの移動のうち、`WHERE` 句で [`system.part_moves_between_shards`](/ja/reference/system-tables/part_moves_between_shards) テーブルから選択したものをキャンセルします。
キャンセルされた移動はバックグラウンドでロールバックされ、`system.part_moves_between_shards` 内の `state` が `CANCELLED` になります。
`SOURCE_DROP` ステートに達した移動はキャンセルできず、完了まで実行されます。

このステートメントを実行するには、`system.part_moves_between_shards` に対する `SELECT` 権限が必要です。さらに、移動をキャンセルするには、対象テーブルに対する `ALTER MOVE PARTITION` 権限と `MOVE PARTITION BETWEEN SHARDS` 権限が必要です。
`ON CLUSTER` を使用する場合は、`*.*` に対して両方の移動権限が必要です。
応答には `kill_status` カラムが含まれ、その値はキャンセルされた移動では `waiting`、キャンセルできなくなった移動では `cant_cancel` になります。その後に `system.part_moves_between_shards` の `database`、`table`、`task_name`、`task_uuid`、`part_name`、`to_shard`、`state` カラムが続きます。

テストクエリ (`TEST`) では、キャンセル対象の移動の一覧が表示されるだけです。`SYNC` 修飾子はサポートされていません。指定すると `NOT_IMPLEMENTED` 例外がスローされます。

例:

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
