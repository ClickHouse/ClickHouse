`JOIN` 句は、共通する値を使って 1 つ以上のテーブルのカラムを結合し、新しいテーブルを生成します。これは SQL をサポートするデータベースで一般的な操作であり、[関係代数](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators)における join に対応します。1 つのテーブルをそれ自身と結合する特殊なケースは、しばしば &quot;自己結合&quot; と呼ばれます。

**構文**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

`ON` 句の式と `USING` 句のカラムは、&quot;結合キー&quot; と呼ばれます。特に明記しない限り、`JOIN` は 結合キーが一致する行から [デカルト積](https://en.wikipedia.org/wiki/Cartesian_product) を生成するため、結果の行数が元のテーブルより大幅に多くなることがあります。

このページでは、`JOIN` 句の構文とセマンティクスについて説明します。ClickHouse における JOIN の実行、JOINの種類、設定、メモリに関する考慮事項、および最適化については、[関連コンテンツ](#related-content)を参照してください。

## サポートされる JOIN の種類 {#supported-types-of-join}

標準的な [SQL JOIN](https://en.wikipedia.org/wiki/Join_\(SQL\)) の種類はすべてサポートされています。

| Type               | Description                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | 一致する行のみが返されます。                                                                                                                                                             |
| `LEFT OUTER JOIN`  | 一致する行に加えて、左テーブルで一致しない行も返されます。                                                                                                                                              |
| `RIGHT OUTER JOIN` | 一致する行に加えて、右テーブルで一致しない行も返されます。                                                                                                                                              |
| `FULL OUTER JOIN`  | 一致する行に加えて、両方のテーブルで一致しない行も返されます。                                                                                                                                            |
| `CROSS JOIN`       | テーブル全体のデカルト積を生成します。結合キーは**指定しません**。                                                                                                                                        |
| `NATURAL JOIN`     | 両方のテーブルで同じ名前を持つすべてのカラムを使って自動的に結合します。共通カラムは結果に 1 回だけ現れます。`INNER` (デフォルト) 、`LEFT`、`RIGHT`、`FULL` の各バリアントをサポートします。カラムのリストが自動的に導出される `JOIN ... USING (col1, col2, ...)` と同等です。 |

* 種類を指定しない `JOIN` は `INNER` を意味します。
* キーワード `OUTER` は省略できます。
* `CROSS JOIN` の別構文として、[`FROM` 句](/ja/reference/statements/select/from) で複数のテーブルをカンマ区切りで指定できます。
* `NATURAL JOIN` で一致するカラムがない場合は、`CROSS JOIN` のように動作します。

ClickHouse では、次の追加の JOIN 種類も利用できます。

| Type                                                | Description                                                                                                                                                                  |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | デカルト積を生成せずに、結合キーに対する許可リストとして機能します。                                                                                                                                           |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | デカルト積を生成せずに、結合キーに対する拒否リストとして機能します。                                                                                                                                           |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | 標準の `JOIN` 種類に対して、デカルト積を部分的に (`LEFT` と `RIGHT` の反対側) または完全に (`INNER`) 無効にします。`ANY FULL JOIN` はサポートされていません。                                                                   |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | 完全一致ではない条件で数列を結合します。[ASOF JOIN の使い方](#asof-join-usage)を参照してください。                                                                                                             |
| `PASTE JOIN`                                        | 2 つのテーブルを水平方向に連結します。[PASTE JOIN の使い方](#paste-join-usage)を参照してください。                                                                                                           |
| `INNER JOIN LATERAL`, `LEFT JOIN LATERAL`           | 左側のテーブルのカラムを参照するサブクエリを結合します。実験的機能であり、[`enable_lateral_join`](/ja/reference/settings/session-settings/enable#enable_lateral_join) が必要です。[LATERAL JOIN](#lateral-join) を参照してください。 |

各 JOIN の種類と strictness の図は、[ClickHouse での JOIN の使用](/ja/concepts/features/operations/select/joining-tables#join-types-and-strictness)に掲載されています。

<Note>
  `semi_join_include_columns_from_both_sides` または `anti_join_include_columns_from_both_sides` 設定を無効にすると、該当する結合では、JOIN 結果の生成後に解決される式から参照できるのは保持される側のみになります。

  * `LEFT SEMI JOIN` と `LEFT ANTI JOIN` では、左側のカラムのみが公開されます。
  * `RIGHT SEMI JOIN` と `RIGHT ANTI JOIN` では、右側のカラムのみが公開されます。
  * これは `SELECT`、`PREWHERE`、`WHERE`、`GROUP BY`、`HAVING`、`QUALIFY`、`ORDER BY`、`LIMIT BY` などの句に影響し、`t1.*` のような修飾付きワイルドカードも対象となります。
  * 同じ `JOIN` の `ON` 式からは、引き続き両側を参照できます。

  これらの設定が有効な場合 (デフォルト) 、ClickHouse は従来の動作を維持します。つまり両側に引き続きアクセスでき、`SELECT *` は両方のテーブルのカラムに展開されます。
</Note>

すべての結合アルゴリズムが、JOIN の種類と strictness のすべての組み合わせをサポートしているわけではありません。サポートされる組み合わせは、[アルゴリズムごとにサポートされる JOIN の種類](/ja/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm)に記載されています。

### `CROSS JOIN` から `INNER JOIN` への書き換え {#cross-join-rewrite}

`CROSS JOIN` またはカンマ区切りのテーブルリストを使用するクエリで、`WHERE` 句にテーブル間の等価条件が含まれている場合、ClickHouse はその JOIN を、これらの条件を結合キーとして使用する `INNER JOIN` に書き換えることができます。この書き換えは [`cross_to_inner_join_rewrite`](/ja/reference/settings/session-settings/other#cross_to_inner_join_rewrite) 設定で制御します。

* `0`: 書き換えは無効です。
* `1`: `WHERE` 句にテーブル間の等価条件が含まれている場合、カンマ区切りのテーブルリストまたは `CROSS JOIN` を書き換えます。それ以外の場合、JOIN は `CROSS JOIN` として実行されます。
* `2`: `1` と同様ですが、クエリに `WHERE` 句がある場合、書き換えできないカンマ区切りのテーブルリストがあると、クエリは `INCORRECT_QUERY` エラーで失敗します。`CROSS JOIN` キーワードで記述された JOIN を書き換えできない場合は、`CROSS JOIN` として実行されます。

値が `0` の場合でも、[`query_plan_merge_filter_into_join_condition`](/ja/reference/settings/session-settings/query-plan#query_plan_merge_filter_into_join_condition) で制御されるクエリプランの最適化によって、等値比較のフィルタが JOIN にマージされ、`INNER JOIN` として実行される場合があります。

## ON 部分の条件 {#on-section-conditions}

`ON` 部分には、`AND` 演算子および `OR` 演算子で組み合わせた複数の条件を含めることができます。結合キーを指定する条件は、次を満たす必要があります。

* 左右両方のテーブルを参照していること
* 等価演算子を使用していること

それ以外の条件ではほかの演算子も使用でき、クエリの左側または右側のいずれかのテーブル、あるいはその両方を参照できます。

複合条件全体が満たされた場合に、行が結合されます。条件が満たされない場合でも、`JOIN` の種類によっては行が結果に含まれることがあります。同じ条件を `WHERE` セクションに置いた場合、それらの条件が満たされなければ、行は常に結果から除外されます。

`OR` で組み合わせた 結合キーは [`hash`](/ja/concepts/features/operations/select/join-algorithms#hash) アルゴリズムでのみサポートされます。このアルゴリズムは、結合キーを含む `OR` の各引数ごとに個別のハッシュテーブルを構築します。

<Note>
  条件を 結合キーとして扱わせるのは等価演算子 (`=`) だけです。異なるテーブルのカラム間でその他の演算子を使用することもできますが、等価条件が 1 つもない場合、JOIN ではすべての行の組み合わせを調べる必要があります。詳しくは [任意の ON 条件による JOIN](#join-with-an-arbitrary-on-condition) を参照してください。
</Note>

**例**

`table_1` と `table_2` を考えます。

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

1 つの 結合キー条件と、`table_2` に対する追加条件を含むクエリ:

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

結果には、名前が `C` で、text カラムが空の行も含まれています。これは、`OUTER` 型の JOIN を使用しているためです。

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

`INNER` 型の JOIN と複数の条件を含むクエリ:

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```response title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴───────┴────────┘
```

join の種類が `INNER` で、条件に `OR` を使ったクエリ：

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

`OR` と `AND` 条件を含む `INNER` JOIN のクエリ:

<Note>
  `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c` のように、単一のテーブルのカラムのみを使用する非等価条件は、そのテーブル単体に適用されます。`t1.b > 0` は `t1` のカラムのみを、`t2.b > t2.c` は `t2` のカラムのみを使用します。
  `t1.a = t2.key AND t1.b > t2.key` のように、異なるテーブルのカラム同士を比較する非等価条件もサポートされています。以下の各セクションを参照してください。
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## 異なるテーブルのカラムに対する不等号条件付き JOIN {#join-with-inequality-conditions-for-columns-from-different-tables}

`ON` 部分には、等価条件に加えて、異なるテーブルのカラムを他の演算子で比較する条件を含めることができます。このような条件は、`ALL`、`ANY`、`SEMI`、`ANTI` の strictness において、その strictness が許可するすべての結合の種類でサポートされています。`ASOF` strictness ではサポートされていません。

`ON` 部分に不等式に加えて 2 つのテーブル間の等価条件が含まれている場合、その等価条件が結合キーとなり、不等式はそれによってマッチした行に対して評価されます。このような混在した条件は、[`hash`](/ja/concepts/features/operations/select/join-algorithms#hash)、[`parallel_hash`](/ja/concepts/features/operations/select/join-algorithms#parallel-hash)、および [`grace_hash`](/ja/concepts/features/operations/select/join-algorithms#grace-hash) アルゴリズムによって実行されます。[`join_algorithm`](/ja/reference/settings/session-settings/join#join_algorithm) で [`ie_join`](/ja/concepts/features/operations/select/join-algorithms#ie-join) がこれらのアルゴリズムより前に指定されており、かつ `ON` 部分に 2 つの不等号条件が含まれている場合は、代わりに `ie_join` が JOIN を実行し、等価条件をフィルタとして適用します。

`ON` 部分に 2 つのテーブル間の等価条件が含まれていない場合、マッチに使用する結合キーは存在しません。このような JOIN は、条件が不等式のペアである場合は [`ie_join`](/ja/concepts/features/operations/select/join-algorithms#ie-join) によって実行され、それ以外の場合は [block nested loop join](#join-with-an-arbitrary-on-condition) として実行されます。

JOIN 中に評価される条件には `arrayJoin` を含めることはできません。このような条件では行数を維持する必要があるためです。代わりにサブクエリ内で `ARRAY JOIN` を使用してください。

**例**

テーブル `t1`:

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

テーブル `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response
key1    a    1    1    2    key1    B    2    1    2
key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
key1    e    5    5    5            0    0    \N
key2    a2    1    1    1            0    0    \N
key4    f    2    3    4            0    0    \N
```

## 任意の ON 条件による JOIN {#join-with-an-arbitrary-on-condition}

`ON` 部分には、範囲チェック、算術比較、スカラー関数の呼び出しなど、両方のテーブルのカラムを対象とした任意のブール式を指定できます。2 つのテーブル間の等値比較が含まれていない場合、行の照合に使う 結合キーは存在しません。不等号条件の組は、[`join_algorithm`](/ja/reference/settings/session-settings/join#join_algorithm) に `ie_join` が含まれていれば、先頭に指定されていなくても `ie_join` によって実行されます。このような条件を実行できる `join_algorithm` の値は、ほかに存在しないためです。バージョン 26.8 以降、`join_algorithm` のデフォルト値には `ie_join` が含まれています。それ以外の条件は [block nested loop join](https://en.wikipedia.org/wiki/Nested_loop_join) として実行されます。この場合、右テーブルがマテリアライズされ、すべての行の組に対して条件が評価されます。`ALL INNER JOIN` は、条件をフィルタとする `CROSS JOIN` と同等の形式になります。

block nested loop join は、`ASOF JOIN`、`PASTE JOIN`、`ANY FULL JOIN` を除くすべての JOIN 種別とstrictnessをサポートします。これは `join_algorithm` に指定できる値ではなく、他のどのアルゴリズムでも条件を実行できない場合にのみ使われる最後の手段です。`EXPLAIN` の出力では `BlockNestedLoopJoin` ステップとして表示されます。[`allow_block_nested_loop_join`](/ja/reference/settings/session-settings/allow#allow_block_nested_loop_join) が無効の場合、これを必要とするクエリは `INVALID_JOIN_ON_EXPRESSION` エラーで拒否されます。

**例**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

どの行にもマッチしなかった行は、他の JOIN と同様に [`join_use_nulls`](/ja/reference/settings/session-settings/join#join_use_nulls) に従ってパディングされます。上記の例ではデフォルト値で埋められ、この設定が有効な場合は `NULL` で埋められます。

**strictness**

`ANY` と `SEMI` は通常、同じ 結合キーを持つ行のグループごとに 1 行を保持します。ここではそのようなグループが存在しないため、JOIN を駆動する側のテーブルの各行につき 1 行を保持します。`LEFT ANY` と `LEFT SEMI` は左側の各行を最大 1 回、`RIGHT ANY` と `RIGHT SEMI` は右側の各行を最大 1 回出力します。`ANY INNER` は両側を同時に制限します。つまり、どちらのテーブルの行も最大 1 回しか使用されないため、結果の行数は小さい方のテーブルの行数以下になります。そうした結果がどのペアで構成されるかは、`ANY` が意味するとおり任意であり、同じクエリを 2 回実行しても異なる場合があります。`ANY INNER` では、これが行数にも及びます。両側の行は、調べられた順序に従って貪欲にペアにされるため、ペアにならずに残る行の数が変わる可能性があります。そのため、結合キーのない `ANY INNER` JOIN に対する `count()` の結果には再現性がなく、スレッド数や右テーブルの物理的な順序に左右されます。

**パフォーマンス**

block nested loop join はすべての行のペアを調べるため、[block nested loop へのフォールバック](/ja/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback) で説明しているとおり、そのコストは両テーブルの行数の積に比例して増加します。マテリアライズされた右テーブルには、[JOIN のメモリ管理とスピル](/ja/concepts/features/operations/select/join-memory-management) で説明しているハードリミットとスピルのしきい値が適用されます。

## 結合キーにおける NULL 値と NaN 値 {#null-values-in-join-keys}

`NULL` は、自身を含め、どの値とも等しくありません。あるテーブルの 結合キーが `NULL` 値であっても、もう一方のテーブルの `NULL` 値とは一致しません。結合キーが [Nullable](/ja/reference/data-types/nullable) カラムの場合、少なくとも 1 つのキーが [NULL](/ja/reference/syntax#null) である行は結合されません。

**例**

テーブル `A`:

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

テーブル `B`：

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

`A` テーブルの `Charlie` の行と、`B` テーブルのスコア 88 の行は、結合キーが `NULL` 値であるため一致しません。

一致しなかった行では、[空または NULL のセルの処理](#processing-of-empty-or-null-cells) で説明しているとおり、`score` カラムに値 `0` が設定されます。

`NULL` 値同士を一致させるには、`isNotDistinctFrom` 関数を使用して 結合キーを比較してください:

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

浮動小数点の 結合キーに含まれる `NaN` 値には、上記の `NULL` ルールは適用されません。
2 つの `NaN` 値をスカラーとして比較した場合 (`NaN = NaN`) 、結果は `0` です。ただし、結合キーはスカラーのセマンティクスでは比較されないため、`NaN` キーが一致する可能性があります。
一致するかどうかは規定されておらず、結合アルゴリズム、キーの型、セッション設定によって異なります。
`NaN` キーを一致の対象から除外するには、`NULL` 値にマッピングしてください。例: `ON if(isNaN(A.id), NULL, A.id) = B.id`。
`ASOF JOIN` では、最も近い一致を判定するカラムは順序に基づいて比較されますが、`NaN` 値に対しては順序が定義されていません。

## 暗黙的な型変換 {#implicit-type-conversion}

左テーブルと右テーブルの 結合キーの型が異なる場合、ClickHouse は比較を行う前に、それらを最小共通スーパータイプに変換します。これはすべての JOIN の種類および strictness に適用されます:

* `ON` を使用する場合、変換は比較にのみ適用されます。結果では、キーカラムは元の型を保持します。
* `USING` を使用する場合、結果では、マージ済みカラムは共通の型になります。`semi_join_include_columns_from_both_sides` または `anti_join_include_columns_from_both_sides` が無効化されている場合、`SEMI JOIN` または `ANTI JOIN` のマージ済みカラムは、保持される側のテーブルの型を維持します。

キーの型に共通のスーパータイプが存在せず、`UInt64` と `Int64` のように両方が整数型または整数型のタプルである場合、ClickHouse は両方のキーを、両方のキーの型に共通する値を保持できる型に変換します。`UInt64` と `Int64` の場合、この型は `UInt64` です。この型で表現できないキーの値は、どの値とも一致しません。この変換は、`ON` 内の等価条件 (`isNotDistinctFrom` を除く) と、`INNER JOIN` または `SEMI JOIN` における `USING` に使用されます。`ASOF JOIN` の最近傍一致条件、`ie_join` が実行する不等号条件、およびその他の JOIN における `USING` には使用されません。これらの場合、結果カラムには一致しなかった値も保持する必要があるためです。この変換はバージョン 26.9 以降で利用できます。

キーの型に共通のスーパータイプが存在せず、かつ `String` と `Int32`、あるいは `UInt64` と `Float64` のようにこの変換が適用されない場合、クエリは `NO_COMMON_TYPE` などの例外で失敗します。

**例**

テーブル `t_1` を考えます:

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

および、テーブル `t_2`:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

クエリ

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b) ORDER BY ALL;
```

次の集合を返します:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## ASOF JOIN の使い方 {#asof-join-usage}

`ASOF JOIN` は、完全一致するレコードがない場合にレコードを結合します。`ASOF` は `INNER` または `LEFT` 結合と組み合わせて使用する 結合の strictness であり、結合アルゴリズムではありません。

`ASOF JOIN` では、両方のテーブルに最も近い一致を判定するためのカラムが必要です。このカラムは次の条件を満たしている必要があります。

* 順序が定義された型である必要があります。
* [`hash`](/ja/concepts/features/operations/select/join-algorithms#hash) アルゴリズムでは、次の型を使用できます: [Int, UInt](/ja/reference/data-types/int-uint), [Float](/ja/reference/data-types/float), [Decimal](/ja/reference/data-types/decimal), [Date](/ja/reference/data-types/date), [Date32](/ja/reference/data-types/date32), [DateTime](/ja/reference/data-types/datetime), [DateTime64](/ja/reference/data-types/datetime64), [Time](/ja/reference/data-types/time), [Enum](/ja/reference/data-types/enum), [Bool](/ja/reference/data-types/boolean)、およびこれらの型の [Nullable](/ja/reference/data-types/nullable)。`String` や `Time64` などのその他の型は、`BAD_TYPE_OF_FIELD` エラーとなり拒否されます。
* [`full_sorting_merge`](/ja/concepts/features/operations/select/join-algorithms#full-sorting-merge) アルゴリズムでは、`String` などのその他の比較可能な型も使用できます。
* `hash` アルゴリズムでは、`JOIN` 句内で唯一のカラムにすることはできません。少なくとも 1 つの等値条件が必要です。`full_sorting_merge` アルゴリズムにはこの制約はありません。

構文 `ASOF JOIN ... ON`:

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

等価条件は任意の数だけ使用でき、最も近い一致条件はちょうど 1 つだけ使用できます。たとえば、`SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t` です。

最も近い一致条件で使用できる演算子: `>`, `>=`, `<`, `<=`。

構文 `ASOF JOIN ... USING`:

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

`ASOF JOIN` は、等価条件での結合に `equi_columnX` を使用し、`table_1.asof_column >= table_2.asof_column` 条件のもとで最も近い一致による結合に `asof_column` を使用します。`asof_column` カラムは、`USING` 句では常に最後になります。

たとえば、次のテーブルを考えます。

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

`ASOF JOIN` では、`table_1` のユーザーイベントのタイムスタンプを基に、最も近い一致条件に対応する `table_1` のイベントのタイムスタンプに最も近いタイムスタンプを持つ `table_2` のイベントを見つけることができます。利用可能であれば、同じタイムスタンプ値が最も近いものとして扱われます。ここでは、等値で 結合するために `user_id` カラムを使用でき、最も近い一致で 結合するために `ev_time` カラムを使用できます。この例では、`event_1_1` は `event_2_1` と 結合でき、`event_1_2` は `event_2_3` と 結合できますが、`event_2_2` は 結合できません。

<Note>
  結合アルゴリズムのうち、`ASOF` strictness をサポートしているのは [`hash`](/ja/concepts/features/operations/select/join-algorithms#hash) と [`full_sorting_merge`](/ja/concepts/features/operations/select/join-algorithms#full-sorting-merge) のみです。詳しくは[アルゴリズムごとにサポートされる 結合の種類](/ja/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm)を参照してください。
  [Join](/ja/reference/engines/table-engines/special/join) テーブルエンジンでは、`ASOF` は**サポートされていません**。
</Note>

## PASTE JOIN の使用法 {#paste-join-usage}

`PASTE JOIN` の結果は、左側のサブクエリのすべてのカラムに、右側のサブクエリのすべてのカラムを続けて含むテーブルです。
行は元のテーブル内での位置に基づいて対応付けられます (行の順序が定義されている必要があります) 。
サブクエリが返す行数が異なる場合、余分な行は切り捨てられます。

例:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

注: この場合、読み取りが並列に行われると、結果は非決定論的になる可能性があります。例:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## LATERAL JOIN {#lateral-join}

`JOIN LATERAL` を使用すると、結合の右側にあるサブクエリから、その左側にあるテーブル
式のカラムを参照できます。結果は、サブクエリが参照する左側のカラム値の相異なる組み合わせごとにサブクエリを評価し、
その結果を、同じ組み合わせを持つすべての左側の行に結合した場合と同じになります：

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

他の `INNER` または `LEFT JOIN` と同様に、`ON true` 述語は必須であり、省略すると構文エラーになります。

この機能はバージョン 26.10 以降で利用できます。実験的な機能であり、デフォルトでは無効になっています。有効にするには
[`enable_lateral_join`](/ja/reference/settings/session-settings/enable#enable_lateral_join) 設定を使用してください。

ラテラルサブクエリは、左側の行ごと、あるいは値の組み合わせごとに 1 回ずつ実行されるわけではありません。他の相関
サブクエリと同様に、すべての左側の行を対象とする単一のクエリへと非相関化されます。具体的には、サブクエリが参照する左側のカラムは、サブクエリが集約を行う場合はその `GROUP BY` キーに
追加され、`LIMIT` がある場合はこれらのカラムによる `LIMIT ... BY` に変換されます。そして、サブクエリの
結果はこれらのカラムをキーとして左側の行と結合されます。`orders.user_id = u.id` のように相関が単純な等値比較である場合、
左側のカラムはサブクエリ側の等しいカラムで置換できます
(`correlated_subqueries_substitute_equivalent_expressions`、デフォルトで有効)。これにより、サブクエリが
左側の行を読み取らずに済む場合があります。ただし、これは保証されません。たとえば、`GROUP BY` のない集約 (`count` など) は、
一致する行がない左側の値に対しても結果を返す必要があるため、依然として左側の重複を除いた値を読み取ります。左側の重複を除いた
値がサブクエリに渡される場合、デフォルト設定ではインメモリバッファを経由します。また、このバッファが実際に使用される
場合に限り、結合は常にハッシュ結合になります。それ以外のすべてのケース、たとえば等値
置換によって左側の行の読み取りが回避される場合や、バッファが無効化されている場合
(`correlated_subqueries_use_in_memory_buffer = 0` または `correlated_subqueries_default_join_kind = 'left'`) には、
アルゴリズムは `join_algorithm` 設定によって決まります。たとえば、`LIMIT` を含むラテラルサブクエリの `EXPLAIN` では、
`LimitBy (LIMIT BY for decorrelated correlated subquery)` ステップの上に `Join` ステップが表示されます。
`LIMIT` を含まないサブクエリには、このステップはありません。

現時点でサポートされているのは以下の部分集合のみであり、それ以外はエラーとして拒否されます。

* サポートされるのは `INNER JOIN LATERAL` と `LEFT JOIN LATERAL` のみです。`RIGHT`、`FULL`、`PASTE`、`NATURAL` の結合はサポートされていません。また、`LATERAL` を `CROSS` 結合やカンマ結合と組み合わせることは一切できません。
* サポートされる strictness はデフォルトの `ALL` のみです。`ANY`、`SEMI`、`ANTI`、`ASOF` はサポートされていません。
* `ON true` 以外の結合述語は使用できません (`ON 1` も使用可能です) 。`USING` はサポートされておらず、述語を
  省略することもできません。両側を関連付けるフィルタは、ラテラルサブクエリの `WHERE` 句に記述してください。
* `GLOBAL` および `LOCAL` 結合修飾子はサポートされていません。
* ラテラルサブクエリは、左側のカラムを少なくとも 1 つ参照する必要があります。相関のないサブクエリには
  通常の結合を使用してください。
* ラテラルサブクエリは、左側の値ごとに個別に評価されるのではなく非相関化されるため、
  `rand` や `generateUUIDv4` のようにクエリ内で非決定論的な関数や、`generateRandom` のように
  ランダムな行を生成するテーブル関数を含めることはできません。
  `now` のようにクエリ内で値が一定の関数は使用できます。
* ラテラルテーブル式としてサポートされるのはサブクエリのみです。PostgreSQL のテーブルソース形式である
  `LATERAL unnest(...)` および `CROSS JOIN UNNEST(...)` はサポートされていません。代わりに
  [`ARRAY JOIN`](/ja/reference/statements/select/array-join) 句を使用してください。
* ラテラルサブクエリの `GROUP BY` と `ORDER BY` は、すべての左側の値に対してまとめて 1 回だけ実行されます。そのため、
  `max_rows_to_group_by`、`max_rows_to_sort`、`max_bytes_to_sort` の制限では、1 つの値の分ではなくすべての左側の値に対する行がカウントされます。
  これらの制限は `throw` オーバーフローモードでのみサポートされ、`any` と `break` は拒否されます。
* 非相関化されたサブクエリの結果は、単一の結合によって左側の行と照合されます。他のハッシュ結合と同様に、
  `max_rows_in_join` と `max_bytes_in_join` はこの結合のうちメモリ上に保持される側を制限し、どちらの側を保持するかは
  プランナーが決定します。前述のインメモリバッファが実際に使用される場合は、
  ラテラルサブクエリを評価する前に左側の行をすべて読み込む必要があるため、`JOIN LATERAL` の左側が保持されます。
  それ以外の場合は、非相関化されたサブクエリの結果が保持されることがあります。これらの制限は常に
  `join_overflow_mode` が `throw` であるものとして適用されます。`break` では、無関係な左側の行が結合によって警告なく破棄されてしまうためです。

**例**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS enable_lateral_join = 1;
```

## 分散 結合 {#distributed-join}

分散テーブルを含む 結合を実行する方法は 2 つあります。

* 通常の `JOIN` を使用する場合、クエリはリモートサーバーに送信されます。右テーブルを作成するために、各サーバー上でサブクエリが実行され、そのテーブルと 結合が行われます。つまり、右テーブルは各サーバーごとに個別に作成されます。
* `GLOBAL ... JOIN` を使用する場合、まずリクエスト元のサーバーがサブクエリを実行して 結合の片側を計算し、その結果を一時テーブルに格納します。次に、この一時テーブルが各リモートサーバーに渡され、転送された一時データを使ってそれらのサーバー上でクエリが実行されます。`LEFT` および `INNER` 結合では、右テーブルがサブクエリとして計算されます。

strictness が `ALL`、`ANY`、`SEMI`、`ANTI` のいずれかである `GLOBAL RIGHT JOIN` において、左テーブルが複数の分片を持つ `Distributed`テーブルである場合、ClickHouse は左右を入れ替えて 結合を `LEFT JOIN` として実行します。これにより、保持される右テーブルの行は 1 回だけ返されます。この場合、左テーブルがサブクエリとして計算され、右テーブルは、複数の分片を持つ `Distributed`テーブルであればその各分片から、そうでなければリクエスト元のサーバー上で読み取られます。このような入れ替えができない `GLOBAL RIGHT JOIN` または `GLOBAL FULL JOIN` は、リクエスト元のサーバー上で実行されます。この動作はバージョン 26.9 以降で適用されます。

`GLOBAL` を使用する際は注意してください。詳しくは、[分散サブクエリ](/ja/reference/statements/in#distributed-subqueries) のセクションを参照してください。

## 空またはNULLのセルの処理 {#processing-of-empty-or-null-cells}

OUTER JOIN の結果では、一致しない行について、もう一方のテーブルのカラムは空になります。これらのセルを ClickHouse がどのように補完するかは、[`join_use_nulls`](/ja/reference/settings/session-settings/join#join_use_nulls) 設定で決まります。

* `0`: セルは列の型のデフォルト値で補完されます。
* `1`: セルは `NULL` で補完され、これらのカラムの型は [Nullable](/ja/reference/data-types/nullable) に変換されます。ただし、`Array` のように `Nullable` で包めない型のカラムは、型を維持したままデフォルト値で補完されます。`FULL` JOIN では、マージ済みの `USING` カラムも `Nullable` に変換されます。

[結合キーにおける NULL 値と NaN 値](#null-values-in-join-keys) で説明しているとおり、結合キーのうち少なくとも 1 つが `NULL` である行は結合されません。

## USING 句 {#using-clause}

`USING` 句は、結合に使用する 1 つ以上のカラムを指定し、それらのカラム同士が等しいことを結合条件とします。

* 各カラムは、左テーブル式と右テーブル式の両方に同じ名前で存在している必要があります。サブクエリでエイリアスを使用すれば、カラムに同じ名前を付けることができます。
* `USING` 句にはカラム名のみを指定できます。式はサポートされていません。
* カラムリストは括弧で囲んでも囲まなくても記述できます。
* `USING` 句の各カラムは、結果に 1 回だけ出現します。その型については [暗黙的な型変換](#implicit-type-conversion) を参照してください。
* それ以外のカラムは、両方のテーブルで同じ名前を持つことができます。`SELECT *` では、右テーブルのカラムはテーブル名またはエイリアスで修飾されます。また、[`single_join_prefer_left_table`](/ja/reference/settings/session-settings/other#single_join_prefer_left_table) が有効な場合、修飾されていない名前は左テーブルのカラムに解決されます。
* [`analyzer_compatibility_join_using_top_level_identifier`](/ja/reference/settings/session-settings/analyzer-compatibility#analyzer_compatibility_join_using_top_level_identifier) が有効な場合、`USING` 内のカラム名は、`SELECT` リスト内のエイリアスなど、クエリ内にある同名のエイリアスから解決されます。

## 例 {#examples}

次のクエリは、カウンターごとの hits 数とカウンターごとの visits 数を結合します。`ANY LEFT JOIN` は左側のサブクエリの各行を 1 回ずつ返し、visits のないカウンターにはデフォルト値 `0` が設定されます。

```sql title="Query"
SELECT
    CounterID,
    hits,
    visits
FROM
(
    SELECT
        CounterID,
        count() AS hits
    FROM VALUES('CounterID UInt32', 1, 1, 1, 2, 2, 3)
    GROUP BY CounterID
) AS h
ANY LEFT JOIN
(
    SELECT
        CounterID,
        sum(Sign) AS visits
    FROM VALUES('CounterID UInt32, Sign Int8', (1, 1), (1, 1), (1, -1), (2, 1), (4, 1))
    GROUP BY CounterID
) AS v USING (CounterID)
ORDER BY hits DESC;
```
