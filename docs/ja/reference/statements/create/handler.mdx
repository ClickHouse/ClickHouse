サーバー設定ファイルを編集せずに、SQL で定義したカスタム HTTP ハンドラーを作成します。SQL で定義したハンドラーは、設定ベースの[HTTP インターフェイスハンドラー](/ja/concepts/features/interfaces/http)の代替手段です。

## 構文 {#syntax}

```sql
CREATE HANDLER [IF NOT EXISTS] name [ON CLUSTER cluster]
[PROTOCOL protocol_name|ANY]
URL [PREFIX|REGEXP] '/path'
[METHODS (GET, POST)]
[TYPE query]
[DEFINER = { user | CURRENT_USER }] [SQL SECURITY { DEFINER | INVOKER | NONE }]
AS [SELECT|INSERT|...] ...
```

指定した`name`のハンドラーを作成します。この名前は、SQLクエリによるハンドラーの管理、診断メッセージ、およびハンドラーの順序付けに使用されます。

## 句 {#clauses}

* `PROTOCOL` — 任意。プロトコル名を指定した場合、ハンドラーは指定された[合成可能プロトコル](/ja/concepts/features/configuration/server-config/composable-protocols)でのみ有効になります。指定しない場合、ハンドラーは組み込みの `http`/`https` ポートと、すべての HTTP 型[合成可能プロトコル](/ja/concepts/features/configuration/server-config/composable-protocols)リスナーを含む、すべての HTTP エンドポイントで有効になります。`PROTOCOL ANY` は後者のデフォルト動作を明示的に選択します。`ALTER HANDLER` では、以前に設定したプロトコル制限を解除します。文字どおり `any` という名前のプロトコルは、バッククォートで参照できます: ``PROTOCOL `any` ``。
* `URL` — 必須。完全一致 URL、`URL PREFIX`、または `URL REGEXP` の形式を指定できます。完全一致 URL とプレフィックスでは、作成時または変更時に曖昧性が検査され、曖昧性がある場合は例外がスローされます。正規表現では、曖昧性を検査できません。URL は、`?` クエリ文字列および `#` フラグメント識別子を除いて照合されます。`URL PREFIX` は、パスセグメントの境界においてベースパスとして照合されます。これは[設定で定義されたハンドラー](/ja/concepts/features/interfaces/http)の `url_prefix` ルールと同じセマンティクスです。`URL PREFIX '/api/v1'` は `/api/v1`、`/api/v1/`、`/api/v1/write` に一致しますが、`/api/v1beta` には一致しません。プレフィックス末尾の `/` は無視されるため、`'/api/v1/'` と `'/api/v1'` は同じように動作します。`URL REGEXP` はアンカー付きで照合され、パス全体に一致する必要があります。そのため、`URL REGEXP '/users/(?P<id>\d+)'` は `/users/42` に一致しますが、`/users/42/roles` には一致しません (サブツリー全体に一致させるには `'/users/(?P<id>\d+).*'` と記述します) 。
* `METHODS` — 任意。許可する HTTP メソッドのリストです。デフォルトは `GET` のみです。サポートされるメソッドは `GET`、`POST`、`PUT`、`DELETE` です。データ変更メソッドである `POST`、`PUT`、`DELETE` では、データを変更するクエリを実行できます。一方、`GET` や `HEAD` などの安全なメソッドは常に `readonly` モードで実行されます。したがって、データを変更するクエリ (たとえば `INSERT` や DDL) を実行するハンドラーでは、少なくとも 1 つのデータ変更メソッドを許可する必要があります。読み取り専用メソッドのみ (たとえばデフォルトの `GET`) を指定してこのようなハンドラーを作成すると、例外がスローされます。`readonly` モードでも副作用が残るクエリは特殊なケースです。`BACKUP` と `RESTORE` には永続的な副作用があり、セッションを変更するステートメント `SET`、`SET ROLE`、`USE`、`BEGIN TRANSACTION`、`COMMIT`、`ROLLBACK`、`SET TRANSACTION SNAPSHOT` は、`session_id` の使用時にリクエスト間で維持されるセッションまたはトランザクションの状態を変更します。また、`CREATE TEMPORARY TABLE` / `CREATE TEMPORARY VIEW` はセッション内に存在するオブジェクトを作成します。しかし、デフォルトでは、安全なメソッドの `readonly` モードでこれらはいずれもブロックされません。`SET ROLE` と `SET DEFAULT ROLE` は、`access_control_improvements.readonly_restricts_set_role` が有効な場合にブロックされます。ハンドラーの制限はこの設定に依存せず、いずれの場合も適用されます。*既存の*一時テーブルに対する変更も `readonly` モードではブロックされないため、そのようなテーブルをターゲットにする可能性があるクエリも同様に扱われます。具体的には、データベースで修飾されていないターゲットテーブルを持つ `INSERT` (修飾されていない名前はセッション一時テーブルに解決される可能性があります) 、`DROP TEMPORARY TABLE`、データベースで修飾されていないテーブルに対する `DROP TABLE` / `TRUNCATE TABLE`、およびデータベースで修飾されていないテーブルに対する `ALTER` (`ALTER TEMPORARY TABLE` は同じステートメントです) が該当します。データベースで修飾されたターゲットが一時テーブルになることはないため、そのようなクエリにはこのルールは適用されません。HTTP では、安全なメソッドに副作用がないことが求められます (`GET` 用に宣言されたハンドラーは `HEAD` にも応答し、その場合レスポンス本文は抑制されるため、副作用は見えません) 。したがって、このようなクエリを実行するハンドラーには、データ変更メソッド*のみ*を列挙する必要があります。安全なメソッドを含めて作成または変更すると、例外がスローされます。複合ステートメントは内部のステートメントまで検査されます。`statement1 PARALLEL WITH statement2 ...` および `EXECUTE AS <user> <statement>` では、実際に実行されるラップされたステートメントに上記のルールが適用されます (各ステートメントは、`readonly` モードを維持するハンドラーのコンテキストのコピーで実行されます) 。単独の `EXECUTE AS <user>` はセッション全体を別のユーザーとして実行するため、それ自体がセッション変更として扱われます。さらに、単独の場合でもステートメントをラップする場合でも、すべての `EXECUTE AS` ハンドラーでは少なくとも 1 つのデータ変更メソッドを許可する必要があります。権限借用には `IMPERSONATE` 権限が必要であり、安全なメソッドの `readonly` モードではこれが拒否されるためです。
* `TYPE` — 任意。現時点でサポートされる唯一の型は `query` です。
* `DEFINER` および `SQL SECURITY` — 任意。クエリをどのユーザーとして実行するかを指定します。[SQLセキュリティ](#sql-security)を参照してください。
* `AS` — このハンドラーで実行されるSQLクエリです。クエリはパラメーター化できます。クエリは、ハンドラーを作成または変更するユーザーの権限に基づいてチェックされます ([SQLセキュリティ](#sql-security)を参照) 。そのユーザーがフルアクセス権を持つ場合、クエリはパースのみが行われ、ハンドラーの作成時点でクエリが参照するテーブルが存在しなくてもかまいません。`FORMAT` 句や類似の句は、`CREATE`/`ALTER` ステートメント全体ではなくクエリに属します。曖昧さを解消するため、クエリを括弧で囲むことができます。`INSERT` クエリには、`VALUES` または `FORMAT` 句の後にインラインデータを含めてはなりません。このようなハンドラーを作成または変更すると、例外がスローされます。インラインペイロードをハンドラー定義に保持できないためです。データはHTTPボディで提供する必要があります (または `INSERT ... SELECT` で生成されます) 。ボディを読み取るクエリを持つハンドラーへのリクエスト、つまりボディからデータを取得する `INSERT`、または `_request_body` パラメーターを使用するクエリでは、長さを宣言する必要があります。`Content-Length` ヘッダーのない非チャンク化リクエストには `411 Length Required` が返されます。そうしないと、ボディがストリーム終端まで読み取られ、接続が切断されても完全なリクエストとして受け入れられてしまうためです。このようなハンドラーのすべてのメソッドも、ボディを伴うメソッド (`POST`、`PUT`、または `DELETE`) である必要があります。`METHODS` 句で安全なメソッド (たとえばデフォルトの `GET`) を指定して作成すると、例外がスローされます。安全なメソッドではリクエストボディが提供されないため、クエリが空のボディを暗黙的に読み取ってしまうからです。宣言された `GET` は `HEAD` に対しても提供されるため、安全なメソッドとボディを伴うメソッドを混在させると、それらの呼び出しが到達可能なままになります。`INSERT ... SELECT` はボディを読み取りません (データは `SELECT` から取得されます) 。したがって、`SELECT` がリクエストボディから供給される `input` テーブル関数を読み取る場合を除き、これらの要件は適用されません。ボディを読み取る `INSERT` は、ハンドラー自身のクエリである必要があります。`EXECUTE AS` および `PARALLEL WITH` は、それらがラップするステートメントをリクエストボディなしで実行するため、これらでラップした場合は、すべてのアップロードが暗黙的に破棄されるのではなく、作成時に拒否されます。ボディを読み取るクエリでは、`_request_body` パラメーターも使用してはなりません。リクエストボディは1つしかなく、`_request_body` をバインドするとクエリが入力データを読み取る前にそのボディが消費されるためです。そのため、このようなハンドラーは、すべてのアップロードが暗黙的に失われるのではなく、作成時に拒否されます。クエリ自身のボディ入力か `_request_body` のいずれか一方のみを使用し、両方を使用しないでください。ボディを読み取らないハンドラーには、このような要件はありません。そのようなハンドラーへのリクエストのボディは無視されます。ボディがハンドラーのクエリに追記されるのは、`INSERT` (または `input` テーブル関数) のデータとしてのみです。`_request_body` パラメーターを通じてボディを読み取るクエリを含め、それ以外のクエリに追記されることはないため、リクエストボディによってハンドラーの SQL が拡張されることはありません。保存されたクエリテキストは、ハンドラーが再ロードまたは呼び出されるたびに、無制限のパーサー深度とバックトラック数、および常にテキスト全体が収まるサイズ制限で、サーバーにより再解析されます。そのため、`max_parser_depth`、`max_parser_backtracks`、または `max_query_size` を引き上げたセッションで作成されたハンドラーは、通常の制限下でもロードおよび呼び出し可能です。また、リクエストによってハンドラーのクエリに対するこれらの制限を引き下げることもできません。さらに、保存されたテキストは、リクエストがどの `dialect` を指定しても常に ClickHouse SQL としてパースされるため、リクエストがダイアレクトを切り替えてハンドラーのクエリを解析不能にすることはできません。リクエストの設定に従うのは、リクエストによって制御される構築スニペット (`select`/`filter`/`order`/`page`) のみです。これらの保証はいずれも、1ホップ先でも維持されます。ハンドラーのクエリが `remote()` または `Distributed`テーブルから読み取る場合や、`ON CLUSTER` ステートメントを発行する場合、他のホストが再パースする SQL はサーバーによって整形されます。そのため、他のホストでも ClickHouse SQL として、かつ呼び出し元リクエストの `max_query_size` の影響を受けずにパースされます。

## 優先順位 {#priority}

server configuration で定義されたハンドラーは、SQL で定義されたハンドラーよりも優先されます。SQL で定義されたハンドラーは、名前の辞書式順序に従って照合されます。

## パラメータ {#parameters}

パラメーター化クエリのクエリパラメータは、設定で定義されたハンドラーと同様に、次の方法で指定します。

* クエリ文字列内の HTTP URL パラメータ。`param_<name>` 形式を使用します (例: `?param_id=42` は `{id:Type}` にバインドされます) 。
* `URL REGEXP` 内の名前付きキャプチャグループ (例: `URL REGEXP '/users/(?P<id>\d+)'` は `{id:Type}` にバインドされます) 。
* クエリでパラメータを宣言しているハンドラーでは、リクエストボディのフォームフィールド。`application/x-www-form-urlencoded` ボディ (例: `curl -d 'param_id=42'`) および `multipart/form-data` ボディのフィールドは、ボディを含む `POST`、`PUT`、`DELETE` メソッドで、URL パラメータと同様に `{name:Type}` パラメータにバインドされます。パラメータが URL とボディの両方に存在する場合は、URL の値が使用されます。フォームとしてパースされたボディはハンドラーレイヤーで消費され、`INSERT` データとしてクエリに渡されません。ボディを `_request_body` にのみ使用するハンドラーは、フォームとしてパースされず、生のボディを受け取ります。ほかのパラメータとともに `_request_body` を宣言するハンドラーは、両方を受け取ります。ボディがフォームとしてパースされる前に、生の未パースボディのコピーが `_request_body` に保持されます (`http_max_request_param_data_size` の制限対象) 。`_request_body` は URL で (`_request_body` または `param__request_body` として) 渡すことはできず、渡した場合は例外が発生して拒否されます。名前付き session で設定された `_request_body` (`SET param__request_body = ...`) も無視されます。`_request_body` は通常リクエストボディからバインドされますが、`URL REGEXP` に `_request_body` という名前付きキャプチャグループがある場合はそのキャプチャからバインドされ、ハンドラーはこのパラメータのためにリクエストボディを読み取りません (そのため、このようなハンドラーでは安全なメソッドを使用でき、`Content-Length` も不要です) 。

ハンドラーの呼び出し時には、標準の ClickHouse HTTP ヘッダー (`X-ClickHouse-Database`、`X-ClickHouse-User`、`X-ClickHouse-Key` など) が通常どおり使用されます。ただし、`SQL SECURITY DEFINER` または `NONE` が指定されたハンドラーは例外です ([SQLセキュリティ](#sql-security) を参照) 。

関数 [`currentHandler`](/ja/reference/functions/regular-functions/other-functions#currentHandler) および [`currentRequestURL`](/ja/reference/functions/regular-functions/other-functions#currentRequestURL) を使用すると、呼び出されたハンドラーとリクエスト URL に応じてクエリの動作をカスタマイズできます。

## アクセス制御 {#access-control}

`CREATE HANDLER`、`DROP HANDLER`、`ALTER HANDLER` を実行するには、それぞれ `CREATE HANDLER`、`DROP HANDLER`、`ALTER HANDLER` 権限が必要です。これらの権限と `SHOW HANDLERS` は `HANDLER ADMIN` 権限グループを構成しており、`CREATE`、`ALTER`、`DROP` の各権限グループには含まれません。

[`system.handlers`](/ja/reference/system-tables/handlers) テーブルを読み取るには、`SHOW HANDLERS` 権限が必要です。ハンドラーのクエリに埋め込まれている可能性のあるシークレットは、ユーザーにシークレットの閲覧も許可されていない限り、このテーブルではマスクされます ([`system.handlers`](/ja/reference/system-tables/handlers) を参照) 。

ハンドラーの呼び出しに個別の権限は必要なく、認証も通常どおり行われます。デフォルトでは、クエリの呼び出し時に通常どおり権限が確認されます。詳細は [SQLセキュリティ](#sql-security) を参照してください。

## SQLセキュリティ {#sql-security}

[ビュー](/ja/reference/statements/create/view#sql_security)と同様に、ハンドラーはクエリを次のいずれかとして実行します。リクエストしたユーザーとして実行する(`SQL SECURITY INVOKER`、デフォルト)、definer として実行する(`SQL SECURITY DEFINER` と `DEFINER = user`、またはデフォルトの definer である `DEFINER = CURRENT_USER`)、ユーザーなしで実行する(`SQL SECURITY NONE`)のいずれかです。現在のユーザー以外を definer にするには、そのユーザーに対する `SET DEFINER` 権限が必要です。また、`SQL SECURITY NONE` には `ALLOW SQL SECURITY NONE` 権限が必要です。ハンドラーを呼び出すための権限は存在しないため、`SQL SECURITY DEFINER` を指定したハンドラーは、その URL をリクエストするすべての認証済みユーザーに対して、definer の権限でクエリを実行します。

クエリは、ハンドラーを作成または変更するユーザーの権限に基づいてチェックされます。ただし、そのユーザーがフルアクセス(grant option 付きのすべての権限。名前付きコレクションの権限は不要ですが、`SQL SECURITY NONE` の場合はすべての名前付きコレクションの使用権限が必要)を持つ場合は除きます。

* ハンドラーがこのユーザーとして実行される場合(`DEFINER = CURRENT_USER`)、クエリパラメータを含まない `SELECT` はビューの `SELECT` と同様に解析され、それ以外のクエリは実行時にチェックされます。
* それ以外の場合、クエリはクエリパラメータおよび `SETTINGS` 句を含まない `SELECT` であり、一時テーブルのない session から保存されたものである必要があります。さらに、ユーザーがそのクエリの実行を許可されている必要があります。

このようなクエリ、および `SQL SECURITY DEFINER` または `NONE` を指定したハンドラーのすべてのクエリでは、ビューと同様に、テーブル名が作成時点の現在のデータベースで修飾されます。SQL のユーザー定義関数はその定義に置き換えられます。`ALTER HANDLER` は変更後のハンドラーを同じ方法でチェックし、さらに保存済みの `DEFINER` または `SQL SECURITY NONE` に対応する権限も必要とします。LDAP ユーザーなどの一時的なユーザーの definer は `<user>:definer` という名前のコピーとして保存されます。そのため、このようなユーザーが自身のハンドラーを変更するには、`DEFINER = CURRENT_USER` を再度指定する必要があります。ハンドラーの definer になっているユーザーは削除できません。

`SQL SECURITY DEFINER` または `NONE` を指定したハンドラーで実行できるのは、`SELECT` クエリとテーブルへの `INSERT` クエリ(`PARALLEL WITH` との組み合わせも可)のみです。このハンドラーへのリクエストで行えるのは、クエリパラメータのバインドと出力フォーマットの選択(`default_format`、`output_format`、または `X-ClickHouse-Format` ヘッダー)のみです。その他の設定、`filter`、`role`、`session_id`、`query_id`、`quota_key`、外部テーブル、あるいは `X-ClickHouse-Database`、`X-ClickHouse-Query-Id`、`X-ClickHouse-Quota` ヘッダーを含むリクエストは拒否されます。definer のプロファイルの設定が、リクエストしたユーザーの `readonly` 制限とあわせて適用され、修飾されていない名前は definer のデフォルトデータベースで解決されます。`NONE` の場合は、definer のものに代わってサーバーの `system_profile` と `default_database` が使用されます。このハンドラーのクエリでは `readonly` や設定プロファイルを変更できません。また、一時テーブルを持つ session では、このようなハンドラーを作成・変更できません。`SQL SECURITY DEFINER` を指定したハンドラーでは、`currentUser` は definer を返し、`authenticatedUser` はハンドラーをリクエストしたユーザーを返します。

`ON CLUSTER` を使用する場合、それが無視されない限り([ストレージ](#storage)を参照)、`DEFINER` と `SQL SECURITY` は使用できず、`CREATE HANDLER` または `ALTER HANDLER` の実行にはフルアクセスを持つユーザーが必要です。

## ストレージ {#storage}

ハンドラーは、[名前付きコレクション](/ja/concepts/features/configuration/server-config/named-collections)と同様に、設定ファイルの`query_rules_storage`セクションで設定されるローカルストレージまたはKeeperストレージに保存されます。

```xml
<query_rules_storage>
    <type>local</type> <!-- or zookeeper -->
    <path>/var/lib/clickhouse/handlers/</path>
</query_rules_storage>
```

Keeper ストレージでは、ハンドラーはすべてのレプリカ間で自動的に同期されるため、明示的な `ON CLUSTER` 句は不要です。指定すると、すべてのレプリカが同じハンドラーを作成しようとします。`ignore_on_cluster_for_replicated_handler_queries` 設定を有効にすると、ストレージがレプリケートされている場合、`CREATE`、`ALTER`、`DROP HANDLER` は `ON CLUSTER` を無視します。これは `ignore_on_cluster_for_replicated_named_collections_queries` と同様の動作です。

## ALTER HANDLER {#alter-handler}

```sql
ALTER HANDLER name [ON CLUSTER cluster]
[PROTOCOL protocol_name|ANY]
[URL [PREFIX|REGEXP] '/path']
[METHODS (GET, POST)]
[TYPE query]
[DEFINER = { user | CURRENT_USER }] [SQL SECURITY { DEFINER | INVOKER | NONE }]
[AS SELECT ...]
```

ハンドラーを新しいものに置き換えます。`ALTER` クエリには一部の句のみを含めることができ、たとえば URL またはクエリだけを変更できます。指定しない句は以前の値を保持します。`PROTOCOL ANY` を指定すると既存のプロトコル制限が解除され、ハンドラーは再びすべての HTTP エンドポイントで有効になります。

## DROP HANDLER {#drop-handler}

```sql
DROP HANDLER [IF EXISTS] name [ON CLUSTER cluster]
```

指定した名前のハンドラーを削除します。

## イントロスペクション {#introspection}

[`system.handlers`](/ja/reference/system-tables/handlers) テーブルには、SQL で定義されたすべてのハンドラーが一覧表示されます。[`system.query_log`](/ja/reference/system-tables/query_log) テーブルには、各クエリのハンドラー名と HTTP リクエストのパス (クエリ文字列を除く) が、`http_handler_name` および `http_request_url` カラムに記録されます。

## 例 {#example}

```sql
CREATE HANDLER my_handler URL '/my_handler' AS SELECT version();
```

```bash
$ curl 'http://localhost:8123/my_handler'
```

正規表現 URL を使用するパラメーター化ハンドラー:

```sql
CREATE HANDLER get_user URL REGEXP '/users/(?P<id>\d+)' AS SELECT * FROM users WHERE id = {id:UInt64};
```

```bash
$ curl 'http://localhost:8123/users/42'
```

## 関連ステートメント {#related-statements}

`CREATE HANDLER` は `CREATE` ステートメントファミリーに属し、`ALTER` および `DROP` と関連しています。
