## Overview {#overview}

ClickHouse provides an experimental `q` dialect: queries are written in
[q](https://code.kx.com/q/), the language of kdb+. A q program is compiled into an
ordinary ClickHouse query, so it runs over ClickHouse tables with the usual query
pipeline (parallel processing, indexes, and so on). There is no q interpreter in the server.

```sql
SET enable_q_dialect = 1;
SET dialect = 'q';
```

```q
select vwap: size wavg price, n: count i by sym from trades where size > 100
```

A plain `SET` query is still parsed as SQL, so `SET dialect = 'clickhouse'` switches back.

## Queries and statements {#queries-and-statements}

In q, `;` separates the statements of a program, so `a: 1; a + 1` is one query.
A query ends at a `;` that is the last character of its line (or at the end of the text):

```q
t: ([] sym: `a`b`a; px: 1 2 3); select sum px by sym from t;
select from trades where sym = `IBM;
```

The assignments of a program are visible to the following statements of the same query,
but not to the following queries. The value of the last statement is the result of the query.
Comments start with `/` after whitespace; `--` comments are accepted as well.
A line with a lone `/` starts a block comment that lasts until a line with a lone `\`,
and a lone `\` outside of a block comment ends the script: the rest of the text is ignored.

## What is supported {#what-is-supported}

- Evaluation from right to left without operator precedence: `2*3+4` is `14`. The arguments of a function and
  the items of a list are evaluated from the last one to the first one as well: `a:0; a+(a:2)` is `4`.
- Literals: numbers with type suffixes, booleans (`101b`), symbols (`` `a`b ``), strings, dates (`2024.01.15`),
  months, timestamps (`2024.01.15D10:30:00`), timespans (`0D01:15:00`), times (`10:30:00.000`), minutes,
  seconds, nulls (`0N`, `0Nd`) and infinities (`0w`).
- Lambdas (`{x*y}`, `{[a;b] a+b}`), which are inlined where they are applied, and projections (`f[;2]`).
- Adverbs: each (`'`, `each`), each-left (`\:`), each-right (`/:`), each-prior (`':`, `prior`), over (`/`, `over`), and scan (`\`, `scan`).
- The q-sql templates `select`, `exec`, `update`, and `delete`, with the `by` and `where` phrases,
  `select[n]`, `select[>col]`, and `select distinct`. `exec` with one phrase without a name returns its value: the list
  of a column, an atom for an aggregate, and a dictionary from the keys to the values with the `by` phrase.
  The order and the limit of `select[n;>col]` apply to the rows that the `where` phrase leaves, before the `by` and
  select phrases: `select[2] sum x from t` is the sum of the first two rows.
- Aggregates (`sum`, `avg`, `count`, `first`, `last`, `med`, `dev`, `var`, `wavg`, `wsum`, `cor`, ...),
  uniform functions (`sums`, `deltas`, `prev`, `next`, `fills`, `mavg`, `msum`, `xprev`, ...),
  `fby`, `xbar`, `within`, `in`, `like`, casts with `$`.
- Tables: table literals (`([] a: 1 2; b: `x`y)`), keyed tables (`([k: 1 2] v: 3 4)`, `` `k xkey t ``, `1!t`),
  `xasc`, `xdesc`, `xcol`, `xcols`, `cols`, `meta`, `count`, `n#t`, `t1,t2`.
- Joins: `lj`, `ij`, `ej`, `uj`, `aj` and `aj0` (an `ASOF JOIN`; `aj0` returns the time of the matched row),
  and `cross`.
- `.ch.sql "SELECT ..."` uses the result of a ClickHouse query as a table. The query can have query parameters
  (`{name:Type}`), which are taken from the request.

## How q values map to ClickHouse {#mapping}

| q | ClickHouse |
|---|------------|
| atom | a value of a single row |
| list | `Array` |
| column of a table in q-sql | column |
| aggregate of a column (`sum x`) | aggregate function; a window function when it is combined with a column |
| uniform function of a column (`sums x`) | window function over the rows in their order |
| symbol, string | `String` |
| boolean, byte, short, int, long, real, float | `Bool`, `UInt8`, `Int16`, `Int32`, `Int64`, `Float32`, `Float64` |
| date, month | `Date32` |
| timestamp, datetime | `DateTime64(9)`, `DateTime64(3)` |
| timespan, time, second, minute | `Time64(9)`, `Time64(3)`, `Time`, `Time` |
| null | `NULL` |

A grouped `select` returns the groups sorted by the keys, like q. A non-aggregated column in a grouped
`select` becomes a list per group. The nulls of the column stay in the list, so the lists of two columns
of one group match item by item; the arithmetic aggregates (`sum`, `avg`, ...) skip the nulls, and `wavg`
skips a pair if either of its values is a null.

The nulls are compared by the rules of q, not of SQL: a null is equal to a null and is less than every other
value, so `0N=0N` is true and `where x=0N` selects the rows with nulls. The same holds for `~`, `differ`,
and the keys of the joins.

A cast with `$` converts like q: a number is rounded when it becomes an integer (`` `int$3.7 `` is `4`), and
a number that becomes a temporal value counts the units of the type since 2000.01.01: `"p"$42` is 42
nanoseconds after 2000.01.01, `"d"$42` is 42 days, `"t"$42` is 42 milliseconds, `"u"$42` is 42 minutes.
The cast of a temporal value to a number is the reverse, and the name of a type (`` `date$42 ``) casts a number like
its letter does. The arithmetic of a temporal value and a number counts the same units: `2024.01m+1` is the next
month, and a timestamp plus one is the next nanosecond.

A month and a minute have no types of their own in ClickHouse: a month is the `Date32` of its first day, and a minute
is a `Time`. Inside of a program, the columns of the tables that the program makes keep these q types, so a column
of months is cast and added to as months. A column of a ClickHouse table has the q type that its type tells: a `Date32`
is a date, a `Time` is a second, a `DateTime64` with up to three digits of the fraction is a datetime, and with more
digits it is a timestamp.

## Differences from q {#differences-from-q}

- A ClickHouse table has no intrinsic row order: uniform functions (`sums`, `prev`, ...), `first`, `last`, and the
  virtual column `i` use the order in which the rows are read. Sort explicitly (`` `time xasc t ``) or use a
  single thread to make it deterministic for `MergeTree` tables.
- Strings are atoms of type `String`, not lists of chars. `count`, `reverse`, `first`, `#`, `_`, and `,` work on them as on
  strings, but atomic functions (`=`, `<`) compare whole strings.
- `n#x` repeats the items of a list or a string when it takes more of them than there are, as in q (`-5#1 2` is
  `2 1 2 1 2`). For a table it takes at most the rows that the table has.
- `xasc`, `xdesc`, and the order of `select[>col]` keep the order of the rows that are equal in the columns, as in q.
  For that, the rows are numbered in the order in which they are read, and the number is the last key of the sorting.
- The values of a program are compiled, not evaluated: recursion, control statements (`if`, `do`, `while`),
  system commands, IPC, files, and the modification of tables in place (`` `t insert ... ``) are not supported.
- General lists must consist of items of the same shape; dictionaries are supported in simple forms.
  `exec` with several phrases, with a named phrase, or without a phrase returns a dictionary of the columns or
  a record in q, and is not supported: use `select`.
- A temporal literal must be in the range of its type in q: the dates within the years 0001..9999, the minutes, seconds,
  and times within 32 bits, and the timestamps and timespans within 64 bits of nanoseconds (`106751D23:47:16.854775807`
  is the longest timespan). A literal out of range is a syntax error. The values that ClickHouse stores are limited by
  the ranges of `Date32`, `DateTime64`, `Time`, and `Time64`.
- The depth of an expression is limited by the setting `max_parser_depth`. A long expression without parentheses counts
  too, because it nests to the right: `1+1+1+...` with a thousand operators is rejected by default. The same setting
  limits the depth of the lists nested in a value, which can grow across the statements (`a:,a`).
- The values of a program are expanded where they are used: after `a:a+a`, the expression of `a` is twice as large, and a
  function is inlined with its argument wherever it mentions the parameter. The size of the expansion is limited by
  the setting `max_expanded_ast_elements`.
- The compilation of a program is under the memory limits of the query and of the user (`max_memory_usage`,
  `max_memory_usage_for_user`): a table literal of ten million items takes its memory even if the program does not
  use the table.
- The compiled query is logged like any other query, without its secrets. When it has none, or when the program
  cannot be compiled, the text of the program is logged, with the queries embedded by `.ch.sql` written without
  their secrets, such as the password of `remote` or the keys of `s3`. `.ch.sql` takes a string literal, also through
  a variable or another name of the function (`s:"SELECT ..."; .ch.sql s`), so in a program that mentions `.ch.sql`
  every string literal that is a query with secrets is written without them, and one that can be an embedded query
  and does not parse is written as `"[HIDDEN]"`. A program that does not parse is logged as it is, like a query in SQL.
- The names starting with `__q` are reserved for the helper columns of the generated query: a table with such a column
  cannot be used in a q program (rename the column with `.ch.sql`).
- The columns of a table are those that the user is allowed to see, as in `system.columns`. A program needs the `SELECT` grant
  only for the columns that it uses. The `MATERIALIZED` and `ALIAS` columns are columns of the table as well, so
  `select from t` returns them, unlike `SELECT *`. The columns of a table of the engine `Alias` are seen through
  the grants on its target too.
- The names of the tables are resolved when the program is compiled: in the database of the request (the setting
  `database` included), with the external tables of the request first.
- `prds` of a column collects the rows before every row, so its memory grows with the square of the number of the rows
  of a group: ClickHouse has no running product. `prds` of a list does not have this cost.
