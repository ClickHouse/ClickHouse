Query optimization starts with understanding why a query is slow. The goal of these guides is not to prescribe a collection of unrelated fixes, but to show how ClickHouse processes a query, how to gather evidence about its performance, and how to validate one targeted improvement.

## Start with a measured problem {#start-with-a-measured-problem}

The best time to consider query performance is while designing the schema, before ingesting data. In practice, workloads and data volumes change in ways that are difficult to predict.

When an existing query becomes slow, begin with a recurring query pattern and a reproducible baseline. An isolated slow run might be an ad hoc query or the result of temporary system load. Avoid choosing an optimization until you have evidence about where a representative query spends time or resources.

## Optimization framework {#optimization-framework}

Approach query optimization in three layers. Start with the fundamentals, then reduce the amount of work performed at query time:

### Minimize the data footprint {#minimize-the-data-footprint}

Use the smallest practical data types, avoid `Nullable` columns when null values are not required, and use `LowCardinality` where it fits the data. A smaller representation reduces storage, I/O, and memory usage.

### Filter efficiently {#filter-efficiently}

Organize data so that ClickHouse reads only the rows and columns required by the query. Start with an effective ordering key. Partition pruning, data-skipping indexes, and projections can support specific access patterns when the measured workload justifies them.

### Move repeatable work to ingestion {#move-repeatable-work-to-ingestion}

When queries repeatedly perform the same transformation or aggregation, consider calculating that result during ingestion. Materialized views and purpose-built tables can exchange ingestion and storage cost for faster queries.

## How ClickHouse processes a query {#general-considerations}

The following simplified model provides enough context to interpret query logs and execution plans. At a high level, ClickHouse processes a query in four stages:

<Steps>
<Step title="Parse and analyze the query" id="parse-and-analyze-the-query">
ClickHouse parses and analyzes the query, then creates a query execution plan.
</Step>

<Step title="Optimize the query plan" id="optimize-the-query-plan">
ClickHouse optimizes the plan, prunes unnecessary data, and builds a query pipeline.
</Step>

<Step title="Execute the query pipeline" id="execute-the-query-pipeline">
ClickHouse reads and processes data in parallel, including filtering, aggregation, and sorting.
</Step>

<Step title="Prepare the result" id="prepare-the-result">
ClickHouse merges, sorts, and formats the result before returning it to the client.
</Step>
</Steps>

For more detail, see the [query analyzer](/guides/clickhouse/performance-and-monitoring/analyzer) and [query execution](/guides/clickhouse/performance-and-monitoring/understanding-query-execution-with-the-analyzer) guides.

## Optimization workflow {#optimization-workflow}

<Steps>
<Step title="Diagnose the slow query" id="diagnose-the-slow-query">
Use bounded query history from one node or the whole cluster to find a recurring slow-query pattern. Choose a representative run, then inspect its duration, resource usage, and query plan to form an initial hypothesis.
</Step>

<Step title="Isolate the bottleneck" id="isolate-the-bottleneck">
Record a repeatable baseline, then compare the original query, a grouped `count`, and an ungrouped `count`. Use consistent timing differences and supporting measurements to identify which operations warrant further investigation.
</Step>

<Step title="Apply and validate one change" id="apply-and-validate-one-change">
Use [Optimization approaches](/guides/clickhouse/performance-and-monitoring/optimization-approaches) to match the suspected bottleneck to one or more interventions. Change one part of the query or schema, repeat the measurement, and compare the results with the baseline.
</Step>
</Steps>
