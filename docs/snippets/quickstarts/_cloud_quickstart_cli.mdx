This page covers provisioning a ClickHouse Cloud service, connecting to it, and loading data, all from the command line with the [ClickHouse CLI](/concepts/features/interfaces/cli) (`clickhousectl`). Apart from the optional `--interactive` login and the browser sign-in for `clickhouse client`, commands are non-interactive. `clickhousectl` emits JSON with `--json`, and automatically when a coding agent runs it.

## Prerequisites {#prerequisites}

Install the ClickHouse CLI:

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

The script installs `~/.local/bin/clickhousectl` and a `chctl` alias. Make sure `~/.local/bin` is on your `PATH`.

You also need `jq`.

You need a ClickHouse Cloud account. If you don't have one yet, `clickhousectl cloud auth signup` opens the sign-up page in your browser.

Browser login (`clickhousectl cloud auth login`) is read-only. Creating and deleting a service, and running SQL with the Query API, need an [API key](/products/cloud/features/admin-features/api/openapi) whose role can create services and manage Query API endpoints; each command's `--help` lists the permissions it needs. Log in with the key; `--interactive` prompts for the key and secret, which keeps the secret out of your shell history:

```bash
clickhousectl cloud auth login --interactive
```

Alternatively, pass `--api-key` and `--api-secret`, or set the `CLICKHOUSE_CLOUD_API_KEY` and `CLICKHOUSE_CLOUD_API_SECRET` environment variables. A coding agent or script should use the environment variables. Login verifies the key and prints its identity; check the active credentials any time with `clickhousectl cloud auth whoami`. If you belong to more than one organization, add `--org-id <org-id>` (or `--org-name <name>`) to each `cloud` command in this guide.

## Create a ClickHouse service {#create-service}

Create the service and save the response. The password for the `default` user is returned only once, so `--dotenv` writes it, with the connection settings, to `.env` in the current directory instead of printing it:

```bash
clickhousectl cloud clickhouse create \
  --name quickstart-ch \
  --region us-east-1 \
  --dotenv \
  --json > ch.json
```

The response includes the service ID, the endpoints, and what was written to `.env` (trimmed here; the full response also contains scaling settings, the IP access list, and tags):

```json
{
  "dotenv": {
    "file": ".env",
    "keys": ["CLICKHOUSE_HOST", "CLICKHOUSE_PORT", "CLICKHOUSE_HTTP_PORT", "CLICKHOUSE_USER", "CLICKHOUSE_SECURE", "CLICKHOUSE_PASSWORD"]
  },
  "service": {
    "id": "4f7b92f3-4163-403a-b538-b9bc6e2e8f66",
    "name": "quickstart-ch",
    "provider": "aws",
    "region": "us-east-1",
    "state": "provisioning",
    "endpoints": [
      {
        "host": "quickstart-abc123.us-east-1.aws.clickhouse.cloud",
        "port": 9440,
        "protocol": "nativesecure"
      },
      {
        "host": "quickstart-abc123.us-east-1.aws.clickhouse.cloud",
        "port": 8443,
        "protocol": "https"
      }
    ],
    "numReplicas": 3,
    "minReplicaMemoryGb": 16.0,
    "maxReplicaMemoryGb": 120.0
  }
}
```

Extract the service ID, which every later command takes:

```bash
CH_ID=$(jq -r .service.id ch.json)
```

The rest of this guide doesn't need the password; your application reads it from `.env` as `CLICKHOUSE_PASSWORD`. The file holds a credential, so keep it out of version control. If the password is lost, generate a new one with `clickhousectl cloud clickhouse reset-password "$CH_ID"`.

Services created with `clickhousectl` default to an IP access list that allows all (`0.0.0.0/0`). To restrict access, pass `--ip-allow` when creating the service; see ["Setting IP filters"](/products/cloud/guides/security/connectivity/setting-ip-filters).

## Wait for the service to provision {#wait-for-provisioning}

Provisioning takes about a minute. Poll until the state is `running`:

```bash
while [ "$(clickhousectl cloud clickhouse get "$CH_ID" --json | jq -r .state)" != "running" ]; do
  sleep 15
done
```

## Run SQL with the Query API {#run-sql}

`clickhousectl cloud clickhouse query` runs SQL over HTTP — no local `clickhouse` binary or service password required. On the first call, clickhousectl adds your API key to the service's Query API endpoint, creating the endpoint if needed; no new key is created. Pass `--no-auto-enable` to fail instead:

```bash
clickhousectl cloud clickhouse query "$CH_ID" --json --query "SHOW databases"
```

The first line of the output below goes to stderr, and appears only when the CLI changes the endpoint:

```text
Binding the authenticated API key to the Query API endpoint for service 'quickstart-ch'...
{"name":"INFORMATION_SCHEMA"}
{"name":"default"}
{"name":"information_schema"}
{"name":"system"}
```

Output defaults to `PrettyCompact` on a terminal, `TabSeparated` when piped, and `JSONEachRow` when a coding agent runs the command. `--json`, used above, selects `JSONEachRow`; for any other format, pass `--format` instead (`--json` and `--format` cannot be combined). A script that parses the output should always pass one of them.

## Create a database and table {#create-database-and-table}

```bash
clickhousectl cloud clickhouse query "$CH_ID" \
  --query "CREATE DATABASE IF NOT EXISTS helloworld"

clickhousectl cloud clickhouse query "$CH_ID" \
  --query "CREATE TABLE helloworld.my_first_table (
    user_id UInt32,
    message String,
    timestamp DateTime,
    metric Float32
  ) ENGINE = MergeTree()
  PRIMARY KEY (user_id, timestamp)"
```

Each command prints `OK` on stderr. Insert a few rows:

```bash
clickhousectl cloud clickhouse query "$CH_ID" <<'SQL'
INSERT INTO helloworld.my_first_table (user_id, message, timestamp, metric) VALUES
  (101, 'Hello, ClickHouse!', now(), -1.0),
  (102, 'Insert a lot of rows per batch', yesterday(), 1.41421),
  (102, 'Sort your data based on your commonly-used queries', today(), 2.718),
  (101, 'Granules are the smallest chunks of data read', now() + 5, 3.14159)
SQL
```

Verify it worked:

```bash
clickhousectl cloud clickhouse query "$CH_ID" --json \
  --query "SELECT * FROM helloworld.my_first_table ORDER BY timestamp"
```

```text
{"user_id":102,"message":"Insert a lot of rows per batch","timestamp":"2026-08-26 00:00:00","metric":1.41421}
{"user_id":102,"message":"Sort your data based on your commonly-used queries","timestamp":"2026-08-27 00:00:00","metric":2.718}
{"user_id":101,"message":"Hello, ClickHouse!","timestamp":"2026-08-27 10:41:28","metric":-1}
{"user_id":101,"message":"Granules are the smallest chunks of data read","timestamp":"2026-08-27 10:41:33","metric":3.14159}
```

The timestamps depend on when you ran the insert, so yours will differ.

## Load a CSV file {#load-csv-file}

Suppose the following text is in a CSV file named `data.csv`:

```text title="data.csv"
102,This is data in a file,2022-02-22 10:43:28,123.45
101,It is comma-separated,2022-02-23 00:00:00,456.78
103,Use FORMAT to specify the format,2022-02-21 10:43:30,678.90
```

`INSERT ... FORMAT` reads the data from stdin, so pipe the query and the file together:

```bash
printf 'INSERT INTO helloworld.my_first_table FORMAT CSV\n' | cat - data.csv \
  | clickhousectl cloud clickhouse query "$CH_ID"
```

The Query API stops waiting after about 30 seconds, and a timed-out `INSERT` may still have run, so check the row count before you retry. For large files, use [`clickhouse client`](#native-client) instead.

Verify the new rows landed:

```bash
clickhousectl cloud clickhouse query "$CH_ID" --json \
  --query "SELECT count() FROM helloworld.my_first_table"
```

```text
{"count()":7}
```

## Connect with clickhouse client {#native-client}

You can also connect over the native protocol with [**clickhouse client**](/concepts/features/interfaces/client). The ClickHouse CLI manages the `clickhouse` binary for you, so you don't need a separate client install. `clickhousectl cloud clickhouse client` needs ClickHouse 25.12 or newer; this installs the latest version and makes it the default:

```bash
clickhousectl local use latest
```

`cloud clickhouse client` looks up the service's host and port and opens `clickhouse client` over native TLS. The client signs you in through a browser as your Cloud user, so no password is needed, but a person must finish the sign-in; scripts and coding agents should use `cloud clickhouse query` instead. With `--query`, the result is printed and the client exits; without it you get the interactive prompt (`:)`), which you leave with `exit`:

```bash
clickhousectl cloud clickhouse client "$CH_ID" \
  --query "SELECT * FROM helloworld.my_first_table ORDER BY timestamp FORMAT TabSeparated"
```

```text
103	Use FORMAT to specify the format	2022-02-21 10:43:30	678.9
102	This is data in a file	2022-02-22 10:43:28	123.45
101	It is comma-separated	2022-02-23 00:00:00	456.78
102	Insert a lot of rows per batch	2026-08-26 00:00:00	1.41421
102	Sort your data based on your commonly-used queries	2026-08-27 00:00:00	2.718
101	Hello, ClickHouse!	2026-08-27 10:41:28	-1
101	Granules are the smallest chunks of data read	2026-08-27 10:41:33	3.14159
```

The same command uploads files, which the client reads from your machine with `FROM INFILE`. It has no Query API timeout, so use it for large files:

```bash
clickhousectl cloud clickhouse client "$CH_ID" \
  --query "INSERT INTO helloworld.my_first_table FROM INFILE 'data.csv' FORMAT CSV"
```

ClickHouse Cloud deduplicates identical inserted blocks, so loading the same `data.csv` a second time adds no rows.

## Cleanup {#cleanup}

Deleting a service removes all of its data permanently. `--force` stops a running service first and waits for the stop to finish, which can take minutes:

```bash
clickhousectl cloud clickhouse delete "$CH_ID" --force
```

To keep the data but stop paying for compute, stop the service with `clickhousectl cloud clickhouse stop "$CH_ID"` instead.
