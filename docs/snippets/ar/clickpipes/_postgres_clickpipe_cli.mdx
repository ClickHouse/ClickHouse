---
title: ClickPipe لـ Postgres عبر واجهة سطر الأوامر
---

تتناول هذه الصفحة إنشاء ClickPipe لالتقاط تغييرات البيانات في Postgres، ومراقبته إلى أن يبدأ النسخ المتماثل، والتحقق من البيانات في ClickHouse، وذلك بالكامل من سطر الأوامر باستخدام [clickhousectl](/ar/concepts/features/interfaces/cli). الأوامر غير تفاعلية، باستثناء تسجيل الدخول الاختياري عبر `--interactive`. يُخرج `clickhousectl` بيانات بصيغة JSON عند استخدام `--json`، ويفعل ذلك تلقائيًا أيضًا عندما يكتشف أنه يعمل ضمن وكيل برمجة؛ وللحصول على القيم كنص عادي، مرّر `--format` إلى `cloud service query`.

## المتطلبات المسبقة {#cli-prerequisites}

ثبّت clickhousectl:

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

يثبّت البرنامج النصي `~/.local/bin/clickhousectl` واسمًا بديلًا هو `chctl`. تأكّد من أن `~/.local/bin` مُضمَّن في `PATH` لديك.

تحتاج أيضًا إلى `jq` و`psql` لخطوة التحقق.

تتطلب عمليات الكتابة (الإنشاء والحذف) [مفتاح API](/ar/products/cloud/features/admin-features/api/openapi)؛ أما تسجيل الدخول عبر OAuth (`clickhousectl cloud auth login` دون أي خيارات سطر الأوامر) فهو للقراءة فقط. سجّل الدخول باستخدام مفتاحك؛ إذ يطالبك الخيار `--interactive` بإدخال المفتاح والـ secret، مما يحول دون ظهور الـ secret في سجل الـ shell لديك:

```bash
clickhousectl cloud auth login --interactive
```

أو مرّر المفتاح والـ secret إلى `clickhousectl cloud auth login` باستخدام `--api-key` و`--api-secret`، أو اضبط متغيّري البيئة `CLICKHOUSE_CLOUD_API_KEY` و`CLICKHOUSE_CLOUD_API_SECRET`. يتحقق تسجيل الدخول من بيانات الاعتماد ويعرض الهوية، ويمكنك التحقق منها مجددًا لاحقًا عبر `clickhousectl cloud auth whoami`. إذا كنت تنتمي إلى أكثر من مؤسسة، فأضف `--org-id <id>` (أو `--org-name <name>`) إلى كل أمر.

يجب أولاً تهيئة قاعدة بيانات Postgres المصدر لديك لتقنية CDC: تفعيل النسخ المنطقي (logical replication)، وإنشاء مستخدم للنسخ، والسماح لعناوين IP الخاصة بـ ClickPipes بالمرور عبر جدار الحماية. اتّبع دليل الإعداد الخاص بمزوّدك — مثل [Amazon RDS](/ar/integrations/clickpipes/postgres/source/rds)، أو [Supabase](/ar/integrations/clickpipes/postgres/source/supabase)، أو [Neon](/ar/integrations/clickpipes/postgres/source/neon-postgres)، أو [دليل مصدر Postgres العام](/ar/integrations/clickpipes/postgres/source/generic) للنشر ذاتي الاستضافة والمزوّدين الآخرين. اتصل بمضيف Postgres الفعلي: إذ إن الوسطاء ومجمّعات الاتصالات مثل PgBouncer وRDS Proxy وSupabase Pooler غير مدعومة مع CDC.

تحتاج أيضاً إلى خدمة ClickHouse Cloud وجهة قيد التشغيل. احصل على معرّفها من `clickhousectl cloud service list --json`، أو أنشئ واحدة أولاً باتّباع [دليل البدء السريع لـ Cloud](/ar/get-started/setup/cloud):

```bash
CH_ID=$(clickhousectl cloud service get --name my-service --json | jq -r .id)
```

اجمع تفاصيل الاتصال بالمصدر من خطوة المتطلبات المسبقة في متغيرات. يستنسخ هذا الشرح التفصيلي جدولاً واحداً هو `public.orders` — استبدل هذا الاسم، وكل إشارة لاحقة إليه (بما في ذلك أسماء الأعمدة في خطوات التحقق)، بجدولك الخاص:

```bash
PG_HOST=postgres.example.com
PG_PORT=5432
PG_DATABASE=postgres
PG_USERNAME=clickpipes_user
PG_PASSWORD='<your-password>'
```

## إنشاء ClickPipe {#create-the-clickpipe}

أنشئ مسار استيعاب البيانات على خدمة الوجهة واحفظ الاستجابة:

```bash
clickhousectl cloud clickpipe create postgres "$CH_ID" \
  --name orders-sync \
  --host "$PG_HOST" \
  --port "$PG_PORT" \
  --pg-database "$PG_DATABASE" \
  --username "$PG_USERNAME" \
  --password "$PG_PASSWORD" \
  --table-mapping public.orders:orders \
  --json > pipe.json

PIPE_ID=$(jq -r .id pipe.json)
```

يتحقّق الأمر من صحة الاتصال بالمصدر قبل إنشاء مسار استيعاب البيانات، وبذلك تظهر مشكلات الاتصال وبيانات الاعتماد وTLS فورًا على شكل خطأ `BAD_REQUEST`. وتُعيد الاستجابة عرض إعدادات مسار استيعاب البيانات (مختصرًا هنا؛ إذ تتضمّن الاستجابة الكاملة كل إعدادات النسخ المتماثل):

```json
{
  "id": "e3d9a1f4-7b2c-4c58-9f6a-0d8b4e2c7a19",
  "name": "orders-sync",
  "serviceId": "7a1c04e2-9b3f-4a86-b21d-6f3e9d5c8a41",
  "state": "Provisioning",
  "destination": {
    "database": "default"
  },
  "source": {
    "postgres": {
      "host": "postgres.example.com",
      "port": 5432,
      "database": "postgres",
      "type": "postgres",
      "settings": {
        "replicationMode": "cdc",
        "syncIntervalSeconds": 60,
        "pullBatchSize": 100000,
        "initialLoadParallelism": 4
      },
      "tableMappings": [
        {
          "sourceSchemaName": "public",
          "sourceTable": "orders",
          "targetTable": "orders",
          "tableEngine": "ReplacingMergeTree"
        }
      ]
    }
  }
}
```

ملاحظات:

* يجب تمرير أحد الخيارين `--table-mapping` أو `--table-mapping-json`. الخيار `--table-mapping` قابل للتكرار، بمعدل `schema.table:target_table` واحد لكل جدول مصدر، ويُبقي جميع الخيارات الأخرى الخاصة بكل جدول على قيمها الافتراضية. ويُنشئ جداول `ReplacingMergeTree` تُسمّى وفقًا لأهداف المطابقة — والمطابقة إلى اسم هدف مختلف هي الطريقة التي تعيد بها تسمية جدول أثناء النسخ المتماثل
* تُنشأ الجداول في قاعدة البيانات المحدّدة بالخيار `--destination-database` (القيمة الافتراضية `default`) على خدمة ClickHouse
* أمر واحد يكفي لعائلة Postgres بأكملها: مرّر `--postgres-type` لمزوّد مُدار (`supabase`، `neon`، `alloydb`، `planetscale`، `rdspostgres`، `aurorapostgres`، `cloudsqlpostgres`، `azurepostgres`، `crunchybridge`، `tigerdata`)؛ والقيمة الافتراضية هي `postgres`
* يتم إنشاء publication وreplication slot تلقائيًا، مع قصر نطاق publication على الجداول المُطابَقة. مرّر `--publication-name` لاستخدام publication أنشأته بنفسك في خطوة المتطلبات المسبقة
* يعيد `--replication-slot-name` استخدام slot أنشأته بنفسك، ولا يُقبل إلا مع `--replication-mode cdc_only`
* يحدد `--replication-mode` إما `cdc` (لقطة أولية مع نسخ متماثل مستمر، وهو الوضع الافتراضي)، أو `snapshot` (نسخ لمرة واحدة)، أو `cdc_only` (تخطّي اللقطة الأولية)
* بالنسبة إلى مصادر Amazon RDS وAurora التي تستخدم مصادقة قاعدة البيانات باستخدام IAM، مرّر `--auth IAM_ROLE --iam-role <role-arn>` بدلًا من `--username` و`--password`

### تشكيل جداول الوجهة {#shaping-the-destination-tables}

يؤدي `--table-mapping` وظيفة إعادة التسمية فقط. أما الخيارات الخاصة بكل جدول والتي تحدد شكل جدول الوجهة، فمرّر المطابقة ككائن JSON عبر `--table-mapping-json`، الذي يقبل كائن مطابقة الجداول الخاص بواجهة برمجة التطبيقات حرفيًا. الحقول `sourceSchemaName` و`sourceTable` و`targetTable` مطلوبة، بينما الحقول `excludedColumns` و`sortingKeys` و`useCustomSortingKey` و`partitionByExpr` و`partitionKey` و`tableEngine` اختيارية. وكلا خياري سطر الأوامر قابل للتكرار ويمكن الجمع بينهما في أمر واحد:

```bash
clickhousectl cloud clickpipe create postgres "$CH_ID" \
  --name orders-sync \
  --host "$PG_HOST" \
  --port "$PG_PORT" \
  --pg-database "$PG_DATABASE" \
  --username "$PG_USERNAME" \
  --password "$PG_PASSWORD" \
  --table-mapping public.orders:orders \
  --table-mapping-json '{"sourceSchemaName":"public","sourceTable":"customers","targetTable":"customers","excludedColumns":["ssn"],"sortingKeys":["created_at","customer_id"]}' \
  --sync-interval-seconds 30 \
  --json
```

تُبقي هذه المطابقة العمود `ssn` خارج الوجهة تمامًا، وترتّب `customers` وفق `(created_at, customer_id)` بدلًا من المفتاح الأساسي في المصدر:

```bash
clickhousectl cloud service query "$CH_ID" \
  --query "SHOW CREATE TABLE customers" --format TSVRaw
```

```text
CREATE TABLE default.customers
(
    `customer_id` Int32,
    `name` String,
    `created_at` DateTime64(6),
    `_peerdb_synced_at` DateTime64(9) DEFAULT now64(),
    `_peerdb_is_deleted` UInt8,
    `_peerdb_version` UInt64
)
ENGINE = SharedReplacingMergeTree('/clickhouse/tables/{uuid}/{shard}', '{replica}', _peerdb_version)
PRIMARY KEY (created_at, customer_id)
ORDER BY (created_at, customer_id)
SETTINGS index_granularity = 8192
```

ملاحظات:

* يُضبط `useCustomSortingKey` تلقائيًا عند تحديد `sortingKeys`، لأن واجهة برمجة التطبيقات تتجاهل المفاتيح من دونه. أما الحقول غير المعروفة فتُرفض في جهة العميل برمز خروج 2 بدلًا من تجاهلها بصمت، لذا فإن خطأً مطبعيًا مثل `excludeColumns` يؤدي إلى الفشل بدلًا من أن يمرّ دون انتباه
* يقسّم `partitionKey` اللقطة الأولية لتحقيق التوازي، ولا علاقة له بـ `PARTITION BY` الخاص بجدول الوجهة، الذي يُحدَّد عبر `partitionByExpr`
* يكون `tableEngine` إما `ReplacingMergeTree` (القيمة الافتراضية، وهي ما تُنشئه الصيغة البسيطة) أو `MergeTree` أو `Null`. يحتفظ `MergeTree` بجميع إصدارات الصف ولا يدعم `FINAL`

### إعدادات CDC {#cdc-settings}

إعدادات النسخ المتماثل عبارة عن flags تُحدَّد عند الإنشاء: `--sync-interval-seconds` و`--pull-batch-size` و`--initial-load-parallelism` و`--snapshot-rows-per-partition` و`--snapshot-parallel-tables` و`--allow-nullable-columns` و`--enable-failover-slots` و`--delete-on-merge`. ولا يمكن تعديل سوى `syncIntervalSeconds` و`pullBatchSize` بعد إنشاء الـ pipe؛ أما إعدادات الـ لقطة والتحميل الأولي فتُثبَّت عند الإنشاء، لذا حدِّدها الآن.

يحتفظ pipe الخاص بـ Postgres CDC بإعداداته على الـ pipe نفسه، لذا يمكنك استعراضها باستخدام `clickpipe get`:

```bash
clickhousectl cloud clickpipe get "$CH_ID" "$PIPE_ID" --json \
  | jq .source.postgres.settings
```

```json
{
  "allowNullableColumns": false,
  "deleteOnMerge": false,
  "enableFailoverSlots": false,
  "initialLoadParallelism": 4,
  "publicationName": "",
  "pullBatchSize": 100000,
  "replicationMode": "cdc",
  "replicationSlotName": "",
  "snapshotNumRowsPerPartition": 100000,
  "snapshotNumberOfParallelTables": 1,
  "syncIntervalSeconds": 30
}
```

إن `clickhousectl cloud clickpipe settings get` هو نقطة نهاية مختلف يغطي إعدادات الاستيعاب الخاصة بـ pipes الـ streaming والتخزين الكائني فقط. أما عند استخدامه مع pipe من نوع Postgres فيُنهي التنفيذ بالرمز 1 ويُحيلك إلى `clickpipe get`.

### صلاحيات الوجهة {#destination-permissions}

يكتب ClickPipes إلى الخدمة بمستخدم خاص به. وافتراضيًا يحصل هذا المستخدم على `default_role` ذي الوصول الكامل؛ أما الخيار `--role <role-name>` (القابل للتكرار) فيحدد أدوار ClickHouse قائمة أخرى بدلًا منه، وهو المكافئ في واجهة سطر الأوامر لخطوة دور الصلاحيات في وحدة التحكم. والأدوار التي تحددها تحلّ محل `default_role`، لذا يجب أن تمنح مجتمعةً كل ما يحتاجه مسار استيعاب البيانات — إنشاء جداول الوجهة والكتابة إليها. أما الدور المخصص للقراءة فقط فيؤدي إلى فشل عملية الإنشاء من أساسها:

```text
Error: BAD_REQUEST: ClickHouse validation failed: failed to create validation table peerdb_validation_tOgS: code: 497, message: clickpipe:...: Not enough privileges. To execute this query, it's necessary to have the grant CREATE TABLE ON default.peerdb_validation_tOgS
```

يحتاج الدور المخصص أيضًا إلى الصلاحية `READ ON S3` التي يستخدمها ClickPipes داخليًا؛ ومن دونها تفشل عملية الإنشاء بالخطأ `failed to validate S3 read grant: user lacks READ on S3 (fix with GRANT READ ON S3)`. الاسمان `clickpipes` و`clickpipes_system` محجوزان ويُرفضان من جهة العميل.

### TLS في المصدر وسلطات إصدار الشهادات {#source-tls}

يكون TLS والتحقّق من الشهادات مُفعّلَين افتراضيًا، والمصدر الذي تكون سلسلة شهاداته موثوقة عالميًا لا يحتاج إلى أي خيارات سطر أوامر إضافية. أمّا إذا قدّم المصدر شهادة موقّعة من CA غير موثوقة عالميًا — ويشمل ذلك [ClickHouse Managed Postgres](/ar/products/managed-postgres/overview) — فسيفشل فحص الاتصال قبل إنشاء مسار استيعاب البيانات، وسيذكر الخطأ اسم الخيار الذي يعالج المشكلة:

```text
Error: BAD_REQUEST: failed to establish connection: failed to connect to `user=postgres database=postgres`: 203.0.113.10:5432 (postgres.example.com): failed to write startup message: write failed: tls: failed to verify certificate: x509: certificate signed by unknown authority

Hint: The source certificate chain is not publicly trusted. For a private or self-signed source CA, pass its PEM CA bundle with `--ca-certificate <PATH>`.
```

مرّر حزمة شهادات CA الخاصة بالمصدر بصيغة PEM عبر `--ca-certificate`. أما مع ClickHouse Managed Postgres، فيتولى `clickhousectl` جلب الحزمة نيابةً عنك:

```bash
clickhousectl cloud postgres certs get <postgres-service-id> --output pg-ca.pem
```

ثم أعد تنفيذ أمر الإنشاء بعد إضافة `--ca-certificate pg-ca.pem`.

أما إذا كانت الشهادة صالحة ولكنها صادرة لاسم مختلف عن الاسم الذي تتصل به، فسيتضمن الخطأ تلميحًا مختلفًا يشير إلى `--tls-host <hostname>` لتحديد اسم المضيف الذي ينبغي استخدامه عند التحقق من الشهادة.

## انتظر حتى يصل مسار استيعاب البيانات إلى Running {#wait-for-running}

يمرّ مسار استيعاب البيانات بالحالات `Provisioning` و`Setup` و(في حالة الجداول الكبيرة) `Snapshot` قبل أن يصل إلى `Running`؛ وتوقّع أن يستغرق أول مسار استيعاب البيانات على الخدمة عدة دقائق. أما `Failed` و`InternalError` فهما حالتان نهائيتان:

```bash
while :; do
  STATE=$(clickhousectl cloud clickpipe get "$CH_ID" "$PIPE_ID" --json | jq -r .state)
  case "$STATE" in
    Running) break ;;
    Failed|InternalError) echo "ClickPipe entered terminal state: $STATE" >&2; break ;;
  esac
  sleep 15
done
```

## التحقق من حالة الـ pipe {#check-pipe-status}

يعرض `clickpipe list` كل pipe في الخدمة، بينما يُرجع `clickpipe get` pipe واحدًا مع التكوين الكامل الخاص به:

```bash
clickhousectl cloud clickpipe list "$CH_ID" --json \
  | jq -r '.[] | [.id, .name, .state] | @tsv'
```

```text
e3d9a1f4-7b2c-4c58-9f6a-0d8b4e2c7a19	orders-sync	Running
```

## التحقق من البيانات في ClickHouse {#verify-the-data-in-clickhouse}

استعلم عن خدمة الوجهة مباشرةً من واجهة سطر الأوامر. عند الاستدعاء الأول، يضيف clickhousectl مفتاح API الخاص بك إلى نقطة نهاية API للاستعلام الخاصة بالخدمة، وينشئ نقطة النهاية إذا لزم الأمر؛ ولا يُنشأ أي مفتاح جديد. مرّر `--no-auto-enable` لكي يفشل الأمر بدلًا من ذلك.

جدول الوجهة من نوع `ReplacingMergeTree`، لذا تصل التحديثات وعمليات الحذف القادمة من المصدر على هيئة إصدارات جديدة من الصفوف. اقرأ الحالة الراهنة باستخدام `FINAL`، واستبعد الصفوف المحذوفة باستخدام `WHERE _peerdb_is_deleted = 0`:

```bash
clickhousectl cloud service query "$CH_ID" --json \
  --query "SELECT order_id, customer, amount FROM orders FINAL WHERE _peerdb_is_deleted = 0 ORDER BY order_id"
```

يُرسَل السطر الأول إلى stderr، ولا يظهر إلا عندما يغيّر clickhousectl نقطة النهاية:

```text
Binding the authenticated API key to the Query API endpoint for service 'my-service'...
{"order_id":1,"customer":"Alice","amount":42.5}
{"order_id":2,"customer":"Bob","amount":17.99}
{"order_id":3,"customer":"Charlie","amount":99}
{"order_id":4,"customer":"Diana","amount":5.25}
{"order_id":5,"customer":"Eve","amount":250}
```

تُنسخ التغييرات في المصدر باستمرار وفق فاصل المزامنة — 60 ثانية افتراضيًا، أو أي قيمة ضُبط عليها `--sync-interval-seconds` وقت الإنشاء. أدرج صفًا في المصدر ثم استعلم دوريًا حتى يصل:

مرّر كلمة المرور عبر `PGPASSWORD` بدلًا من عنوان URI للاتصال، فلا تحتاج المحارف الخاصة فيها إلى إفلات:

```bash
PGPASSWORD="$PG_PASSWORD" psql -h "$PG_HOST" -p "$PG_PORT" -U "$PG_USERNAME" -d "$PG_DATABASE" \
  -c "INSERT INTO orders (customer, amount) VALUES ('Frank', 12.34);"

while [ "$(clickhousectl cloud service query "$CH_ID" --format TabSeparated \
  --query "SELECT count() FROM orders FINAL WHERE _peerdb_is_deleted = 0")" != "6" ]; do
  sleep 10
done
```

## إدارة مسار استيعاب البيانات {#manage-the-pipe}

تُدار دورة حياة مسار استيعاب البيانات عبر الأوامر `clickhousectl cloud clickpipe stop` و`clickhousectl cloud clickpipe start` و`clickhousectl cloud clickpipe resync` (الذي يحذف جداول الوجهة ويعيد أخذ لقطة لها)، ويأخذ كل منها الوسائط نفسها `"$CH_ID" "$PIPE_ID"`.

لتعديل مسار استيعاب البيانات، أوقفه مؤقتًا أولًا؛ إذ يجب أن تكون حالة مسار استيعاب البيانات لالتقاط تغييرات البيانات في Postgres هي `Paused` قبل إجراء أي تحديث. يأخذ الأمر `clickpipe update` ملف تصحيح بصيغة JSON، وتبقى الحقول التي لا تُدرجها فيه دون تغيير. على سبيل المثال، احفظ `{"name":"orders-sync-v2"}` باسم `patch.json` ثم شغّل:

```bash
clickhousectl cloud clickpipe stop "$CH_ID" "$PIPE_ID" &&
until [ "$(clickhousectl cloud clickpipe get "$CH_ID" "$PIPE_ID" --json | jq -r .state)" = "Paused" ]; do
  sleep 10
done

STATE=""
clickhousectl cloud clickpipe update "$CH_ID" "$PIPE_ID" --file patch.json &&
while :; do
  STATE=$(clickhousectl cloud clickpipe get "$CH_ID" "$PIPE_ID" --json | jq -r .state)
  case "$STATE" in Paused|Running|Failed) break ;; esac
  sleep 10
done
[ "$STATE" = "Paused" ] && clickhousectl cloud clickpipe start "$CH_ID" "$PIPE_ID"
```

قد تستأنف الخدمة تشغيل مسار استيعاب البيانات ضمن عملية تحديث ناجحة، كما أن تنفيذ `start` على مسار استيعاب البيانات قيد التشغيل ينتهي برمز الخروج 1 مع الرسالة `ClickPipe is already running`، لذا لا تشغّله إلا إذا كان لا يزال في الحالة `Paused`. وإذا فشل التحديث، فاترك مسار استيعاب البيانات متوقفًا مؤقتًا إلى أن تتحقق من الخطأ. ومن بين إعدادات CDC، لا يمكن بعد الإنشاء تغيير سوى `syncIntervalSeconds` و`pullBatchSize`؛ راجع [مرجع إعدادات ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md#update-a-pipe) للاطلاع على الحقول التي يقبلها التصحيح، بما في ذلك إضافة الجداول وإزالتها.

تُضبط القدرة الحاسوبية لـ CDC على مستوى الخدمة لا على مستوى مسار استيعاب البيانات، وتتشاركها جميع مسارات استيعاب البيانات لـ CDC لقواعد البيانات على الخدمة. اقرأ قيمتها الحالية أولًا، ثم غيّر قيمة CPU أو الذاكرة لكل نسخة متماثلة:

```bash
clickhousectl cloud clickpipe cdc-scaling get "$CH_ID"
clickhousectl cloud clickpipe cdc-scaling update "$CH_ID" --cpu-millicores 4000 --memory-gb 16
```

وإذا كان المصدر متاحًا عبر الشبكة الخاصة فقط، فإن `clickhousectl cloud clickpipe reverse-private-endpoint` يتولى إدارة نقطة نهاية AWS PrivateLink أو Google Private Service Connect؛ ومرّر أحد أسماء DNS التي يعرضها بوصفه `--host` عند إنشاء مسار استيعاب البيانات. أما مصادر Postgres التي تعتمد على SSH tunneling فهي متاحة حاليًا عبر الـ UI فقط: إذ تدعم واجهة سطر الأوامر الاتصالات المباشرة ونقاط النهاية الخاصة العكسية، لكنها لا تستطيع تهيئة SSH tunneling. راجع `clickhousectl cloud clickpipe --help` للاطلاع على القائمة الكاملة للأوامر الفرعية.

## التنظيف {#cleanup}

يؤدي حذف مسار استيعاب البيانات إلى إيقاف النسخ المتماثل:

```bash
clickhousectl cloud clickpipe delete "$CH_ID" "$PIPE_ID"
```

يطبع clickhousectl سطرًا بالصيغة `ClickPipe ... deleted` يتضمن اسم مسار استيعاب البيانات أو الـ ID الخاص به. أما في وضع JSON (عند استخدام `--json`، أو عند تشغيله بواسطة وكيل برمجة) فيطبع ID مسار استيعاب البيانات بدلًا من ذلك:

```json
{"deleted":"e3d9a1f4-7b2c-4c58-9f6a-0d8b4e2c7a19"}
```
