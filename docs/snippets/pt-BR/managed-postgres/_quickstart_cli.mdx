Esta página aborda o provisionamento do ClickHouse Managed Postgres, o carregamento de dados, a replicação para o ClickHouse e a execução de consultas, tudo pela linha de comando com o [clickhousectl](/pt-BR/concepts/features/interfaces/cli) e `psql`. Com exceção do login opcional com `--interactive`, os comandos são não interativos. O `clickhousectl` gera JSON com `--json` e também automaticamente quando detecta um agente de programação; passe `--format` para `cloud service query` para obter valores em texto simples.

## Pré-requisitos {#prerequisites}

Instale o clickhousectl:

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

O script instala `~/.local/bin/clickhousectl` e um alias `chctl`. Certifique-se de que `~/.local/bin` esteja no seu `PATH`.

Você também precisará do `psql` (ferramentas de cliente PostgreSQL; no MacOS, `brew install libpq`) e do `jq`.

Operações de escrita (criar, excluir) exigem uma [chave de API](/pt-BR/products/cloud/features/admin-features/api/openapi); o login via OAuth (`clickhousectl cloud auth login` sem flags) é read-only. Faça login com sua chave; a opção `--interactive` solicita a chave e o secret, evitando que o secret fique registrado no histórico do seu shell:

```bash
clickhousectl cloud auth login --interactive
```

Ou passe a chave e o secret para `clickhousectl cloud auth login` com `--api-key` e `--api-secret`, ou defina as variáveis de ambiente `CLICKHOUSE_CLOUD_API_KEY` e `CLICKHOUSE_CLOUD_API_SECRET`. O login valida as credenciais e exibe a identidade; depois, você pode confirmá-la novamente com `clickhousectl cloud auth whoami`. Se você pertencer a mais de uma organização, adicione `--org-id <id>` (ou `--org-name <name>`) a cada comando.

## Parte 1: Criar o Postgres e carregar os dados {#part-1-create-and-load}

### Crie um Serviço Postgres {#create-postgres-service}

Crie o serviço e salve a resposta, pois a senha é exibida apenas uma vez:

```bash
clickhousectl cloud postgres create \
  --name quickstart-pg \
  --region us-east-1 \
  --size m6gd.large \
  --pg-version 18 \
  --json > pg.json
```

A AWS é o provedor padrão. O GCP está em prévia privada; para usá-lo, passe `--provider gcp` com uma região e um tamanho do GCP, por exemplo, `--region us-central1 --size c4-standard-lssd-4`.

Sem flags de acesso, o serviço aceita conexões de qualquer endereço IPv4 ou IPv6 no Postgres (5432) e no PgBouncer (6432). Para restringir o acesso, passe uma regra `--ip-allow` para cada combinação de CIDR e intervalo de portas, por exemplo, `--ip-allow '203.0.113.0/24:5432..6432=office'`. Assim que você passa uma regra, apenas as regras listadas passam a valer. Para alterar as regras posteriormente, execute `clickhousectl cloud postgres update <postgres-id>` com `--add-ip-allow <rule>` ou `--remove-ip-allow <rule-id>`; o comando `cloud postgres get` lista os IDs das regras.

Extraia as informações necessárias para o restante deste guia:

```bash
PG_ID=$(jq -r .id pg.json)
PG_URL="$(jq -r .connectionString pg.json | sed 's/sslmode=require/sslmode=verify-full/')&sslrootcert=pg-ca.pem"
```

Alterar `sslmode` para `verify-full` e adicionar `sslrootcert` faz com que o `psql` valide o certificado do servidor com base na CA que você baixará a seguir. Com o valor padrão `sslmode=require`, o `psql` criptografa a conexão, mas não verifica a identidade do servidor.

Se você perder a senha, gere uma nova com `clickhousectl cloud postgres reset-password "$PG_ID" --generate`.

### Aguarde o provisionamento do serviço {#wait-for-provisioning}

O Provisioning leva alguns minutos. Verifique periodicamente até que o estado seja `running`:

```bash
while [ "$(clickhousectl cloud postgres get "$PG_ID" --json | jq -r .state)" != "running" ]; do
  sleep 15
done
```

### Baixe o certificado de CA {#download-ca-certificate}

Cada instância do ClickHouse Managed Postgres tem sua própria CA, que não é reconhecida publicamente como confiável. Salve o certificado em um arquivo; tanto o `psql` quanto o ClickPipe da Parte 2 o utilizam para verificar o TLS:

```bash
clickhousectl cloud postgres certs get "$PG_ID" --output pg-ca.pem
```

### Carregar dados de exemplo {#load-sample-data}

Crie duas tabelas e insira 1 milhão de eventos usando o `psql`:

```bash
psql "$PG_URL" <<'SQL'
\timing
CREATE TABLE events (
   event_id SERIAL PRIMARY KEY,
   event_name VARCHAR(255) NOT NULL,
   event_type VARCHAR(100),
   event_timestamp TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
   event_data JSONB,
   user_id INT,
   user_ip INET,
   is_active BOOLEAN DEFAULT TRUE,
   created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
   updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE users (
   user_id SERIAL PRIMARY KEY,
   name VARCHAR(100),
   country VARCHAR(50),
   platform VARCHAR(50)
);

INSERT INTO events (event_name, event_type, event_timestamp, event_data, user_id, user_ip)
SELECT
   'Event ' || gs::text AS event_name,
   CASE
       WHEN random() < 0.5 THEN 'click'
       WHEN random() < 0.75 THEN 'view'
       WHEN random() < 0.9 THEN 'purchase'
       WHEN random() < 0.98 THEN 'signup'
       ELSE 'logout'
   END AS event_type,
   NOW() - INTERVAL '1 day' * (gs % 365) AS event_timestamp,
   jsonb_build_object('key', 'value' || gs::text, 'additional_info', 'info_' || (gs % 100)::text) AS event_data,
   GREATEST(1, LEAST(1000, FLOOR(POWER(random(), 2) * 1000) + 1)) AS user_id,
   ('192.168.1.' || ((gs % 254) + 1))::inet AS user_ip
FROM
   generate_series(1, 1000000) gs;

INSERT INTO users (name, country, platform)
SELECT
    first_names[first_idx] || ' ' || last_names[last_idx] AS name,
    CASE
        WHEN random() < 0.25 THEN 'India'
        WHEN random() < 0.5 THEN 'USA'
        WHEN random() < 0.7 THEN 'Germany'
        WHEN random() < 0.85 THEN 'China'
        ELSE 'Other'
    END AS country,
    CASE
        WHEN random() < 0.2 THEN 'iOS'
        WHEN random() < 0.4 THEN 'Android'
        WHEN random() < 0.6 THEN 'Web'
        WHEN random() < 0.75 THEN 'Windows'
        WHEN random() < 0.9 THEN 'MacOS'
        ELSE 'Linux'
    END AS platform
FROM
    generate_series(1, 1000) AS seq
    CROSS JOIN LATERAL (
        SELECT
            array['Alice', 'Bob', 'Charlie', 'Diana', 'Eve', 'Frank', 'Grace', 'Hank', 'Ivy', 'Jack', 'Liam', 'Olivia', 'Noah', 'Emma', 'Sophia', 'Benjamin', 'Isabella', 'Lucas', 'Mia', 'Amelia', 'Aarav', 'Riya', 'Arjun', 'Ananya', 'Wei', 'Li', 'Huan', 'Mei', 'Hans', 'Klaus', 'Greta', 'Sofia'] AS first_names,
            array['Smith', 'Johnson', 'Williams', 'Brown', 'Jones', 'Garcia', 'Miller', 'Davis', 'Martinez', 'Taylor', 'Anderson', 'Thomas', 'Jackson', 'White', 'Harris', 'Martin', 'Thompson', 'Moore', 'Lee', 'Perez', 'Sharma', 'Patel', 'Gupta', 'Reddy', 'Zhang', 'Wang', 'Chen', 'Liu', 'Schmidt', 'Müller', 'Weber', 'Fischer'] AS last_names,
            1 + (seq % 32) AS first_idx,
            1 + ((seq / 32)::int % 32) AS last_idx
    ) AS names;
SQL
```

A inserção de 1 milhão de linhas leva cerca de 20 segundos no `m6gd.large` (uma das menores configurações), graças ao armazenamento NVMe. Verifique com uma consulta; a contagem de linhas varia entre as execuções porque os dados são gerados com `random()`:

```bash
psql "$PG_URL" -c "SELECT event_type, COUNT(*) FROM events GROUP BY event_type ORDER BY 2 DESC;"
```

## Parte 2: Replicar para o ClickHouse {#part-2-replicate}

### Criar um serviço do ClickHouse {#create-clickhouse-service}

Crie um serviço na mesma região e salve a resposta; a senha aparece apenas na resposta de criação:

```bash
clickhousectl cloud service create \
  --name quickstart-ch \
  --region us-east-1 \
  --json > ch.json

CH_ID=$(jq -r .service.id ch.json)
CH_PASSWORD=$(jq -r .password ch.json)
```

Aguarde até que ele esteja em execução; o ClickPipe requer um destino em execução:

```bash
while [ "$(clickhousectl cloud service get "$CH_ID" --json | jq -r .state)" != "running" ]; do
  sleep 15
done
```

Para usar um serviço existente, defina `CH_ID` a partir de `clickhousectl cloud service list` e `CH_PASSWORD` como a senha do usuário `default`, que é necessária para a etapa `pg_clickhouse`.

### Replicar as tabelas para o ClickHouse {#replicate-to-clickhouse}

Crie um ClickPipe de CDC do Postgres no serviço do ClickHouse, apontando para o hostname do ClickHouse Managed Postgres. O pipe copia as linhas existentes e, em seguida, mantém o ClickHouse sincronizado com as alterações subsequentes. Por padrão, o ClickPipes verifica o certificado da origem, então informe a CA que você baixou na Parte 1 com `--ca-certificate`:

```bash
PG_HOST=$(jq -r .hostname pg.json)
PG_PASSWORD=$(jq -r .password pg.json)

clickhousectl cloud clickpipe create postgres "$CH_ID" \
  --name quickstart-sync \
  --host "$PG_HOST" \
  --pg-database postgres \
  --username postgres \
  --password "$PG_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --table-mapping public.events:public_events \
  --table-mapping public.users:public_users \
  --json > pipe.json

PIPE_ID=$(jq -r .id pipe.json)
```

Notas:

* As tabelas replicadas são criadas no banco de dados `default` do serviço do ClickHouse, com os nomes definidos pelos destinos de `--table-mapping`. Passe `--destination-database <name>` para usar outro banco de dados
* `--table-mapping` cria tabelas `ReplacingMergeTree`. Atualizações e exclusões chegam como novas versões das linhas; por isso, leia o estado atual com `FINAL` e `WHERE _peerdb_is_deleted = 0`, como fazem as consultas abaixo
* A publicação e o slot de replicação são criados automaticamente, com a publicação restrita às tabelas mapeadas; passe `--publication-name` para usar uma publicação gerenciada por você
* Use o hostname direto do Postgres; a replicação não é compatível com o PgBouncer

### Aguarde o pipe atingir o status `Running` {#wait-for-pipe}

O pipe passa por `Provisioning`, `Setup` e, no caso de tabelas maiores, `Snapshot` antes de atingir `Running`, o que leva cerca de 4 minutos para o primeiro pipe em um serviço. `Failed` e `InternalError` são estados terminais:

```bash
while :; do
  STATE=$(clickhousectl cloud clickpipe get "$CH_ID" "$PIPE_ID" --json | jq -r .state)
  case "$STATE" in
    Running) break ;;
    Failed|InternalError) echo "ClickPipe entered terminal state: $STATE" >&2; break ;;
  esac
  sleep 15
done
```

### Consulte os dados replicados no ClickHouse {#query-clickhouse}

Execute SQL diretamente no serviço do ClickHouse pela CLI. Na primeira chamada, o clickhousectl adiciona sua chave de API ao endpoint da Query API do serviço, criando o endpoint se necessário; nenhuma nova chave é criada. Passe `--no-auto-enable` para que o comando falhe nesse caso. `--format TabSeparated` imprime apenas o valor, formato do qual depende a comparação abaixo:

```bash
clickhousectl cloud service query "$CH_ID" --format TabSeparated \
  --query "SELECT count() FROM public_events FINAL WHERE _peerdb_is_deleted = 0"
```

A primeira linha é enviada para o stderr e só aparece quando o clickhousectl altera o endpoint:

```text
Binding the authenticated API key to the Query API endpoint for service 'quickstart-ch'...
1000000
```

Novas gravações no Postgres são replicadas continuamente. Insira uma linha e faça consultas até que a contagem atinja 1,000,001 (normalmente em menos de um minuto):

```bash
psql "$PG_URL" -c "INSERT INTO events (event_name, event_type, user_id, user_ip) VALUES ('cdc-test', 'click', 42, '10.0.0.1');"

while [ "$(clickhousectl cloud service query "$CH_ID" --format TabSeparated \
  --query "SELECT count() FROM public_events FINAL WHERE _peerdb_is_deleted = 0")" != "1000001" ]; do
  sleep 10
done
```

### Consultar o ClickHouse no Postgres {#query-clickhouse-from-postgres}

A extensão [`pg_clickhouse`](/pt-BR/products/managed-postgres/extensions/pg_clickhouse/introduction) permite que o Postgres atue como uma camada unificada de consulta para dados transacionais e analíticos. Obtenha o hostname HTTPS do ClickHouse e, em seguida, configure a extensão usando o `psql`:

```bash
CH_HOST=$(clickhousectl cloud service get "$CH_ID" --json \
  | jq -r '.endpoints[] | select(.protocol=="https") | .host')

psql "$PG_URL" <<SQL
CREATE EXTENSION pg_clickhouse;
CREATE SERVER ch FOREIGN DATA WRAPPER clickhouse_fdw
       OPTIONS(driver 'http', host '$CH_HOST', dbname 'default', port '8443');
CREATE USER MAPPING FOR CURRENT_USER SERVER ch
       OPTIONS (user 'default', password '$CH_PASSWORD');
CREATE SCHEMA organization;
IMPORT FOREIGN SCHEMA "default" FROM SERVER ch INTO organization;
SQL
```

O heredoc está sem aspas de propósito, para que o shell substitua `$CH_HOST` e `$CH_PASSWORD` antes que o SQL chegue ao Postgres. As tabelas replicadas agora estão visíveis como tabelas estrangeiras no schema `organization`; as consultas sobre elas são executadas no ClickHouse.

Em testes no `m6gd.large` com este conjunto de dados, as consultas analíticas são executadas de 6 a 9 vezes mais rápido por meio das tabelas estrangeiras (por exemplo, um GROUP BY com 5 agregações: 176 ms via ClickHouse vs 1.133 ms localmente; um JOIN com agregações: 298 ms vs 2.764 ms).

## Limpeza {#cleanup-resources}

Exclua primeiro o ClickPipe e depois o serviço Postgres. Ao excluir um serviço, todos os dados dele são removidos permanentemente. Um serviço Postgres pode ser excluído mesmo em execução:

```bash
clickhousectl cloud clickpipe delete "$CH_ID" "$PIPE_ID"
clickhousectl cloud postgres delete "$PG_ID"
```

Um serviço do ClickHouse em execução não pode ser excluído diretamente. `--force` para o serviço, aguarda até que a parada seja concluída e depois o exclui:

```bash
clickhousectl cloud service delete "$CH_ID" --force
```
