---
title: 設定可能なバックアップ CLI
---

このページでは、[ClickHouse CLI](/ja/concepts/features/interfaces/cli) (`clickhousectl`) を使用して、コマンドラインから ClickHouse Cloud サービスのバックアップスケジュールを閲覧・変更する方法を説明します。任意で使用できる `--interactive` ログインを除き、コマンドは非対話型です。`clickhousectl` は `--json` を指定すると JSON を出力し、コーディングエージェントから実行された場合は自動的に JSON を出力します。

設定可能なバックアップは、Scale および Enterprise プランで利用できます。

## 前提条件 {#prerequisites}

ClickHouse CLI をインストールします。

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

このスクリプトは `~/.local/bin/clickhousectl` と、その別名である `chctl` をインストールします。`~/.local/bin` が `PATH` に含まれていることを確認してください。

`jq` も必要です。

バックアップ設定の変更は書き込み操作のため、[APIキー](/ja/products/cloud/features/admin-features/api/openapi)が必要です。ブラウザでのログイン (`clickhousectl cloud auth login`) では読み取り専用の権限しか得られません。APIキーを使用してログインしてください。`--interactive` を指定すると、キーとシークレットの入力を求めるプロンプトが表示されるため、シークレットがシェルの履歴に残りません。

```bash
clickhousectl cloud auth login --interactive
```

または、`--api-key` と `--api-secret` を指定するか、環境変数 `CLICKHOUSE_CLOUD_API_KEY` と `CLICKHOUSE_CLOUD_API_SECRET` を設定します。コーディングエージェントやスクリプトから利用する場合は、環境変数を使用してください。ログインするとキーが検証され、そのアイデンティティが表示されます。現在有効な認証情報は、`clickhousectl cloud auth whoami` でいつでも確認できます。以前に `auth login` で保存した認証情報は、環境変数よりも優先されます。`clickhousectl cloud auth status` で環境変数が無効と表示される場合は、保存済みの認証情報が使用されています。環境変数を使用するには、`clickhousectl cloud auth logout --api-keys` を実行してください。

## サービス ID を確認する {#find-the-service-id}

バックアップ設定はサービスごとに行います。サービス名から ID を検索します:

```bash
CH_ID=$(clickhousectl cloud service get --name "<service-name>" --json | jq -r .id)
```

複数の組織に所属している場合、組織を自動検出できないため、このコマンドは ``Multiple organizations found. Specify --org-id or --org-name to choose one. Use `clickhousectl cloud org list` to see your organizations.`` というエラーで失敗します。`clickhousectl cloud org list` で所属する組織を一覧表示し、このコマンドおよび以降のすべての `backup-config` コマンドに `--org-id <org-id>`(または `--org-name <name>`)を指定してください。

## 現在のバックアップ設定を確認する {#read-the-current-backup-configuration}

```bash
clickhousectl cloud service backup-config get "$CH_ID" --json
```

デフォルトのスケジュールをそのまま使用しているサービスでは、次のように報告されます:

```json
{
  "backupPeriodInHours": 24.0,
  "backupRetentionPeriodInHours": 24.0
}
```

`backupStartTime` は、開始時刻が設定されている場合にのみ出力に表示されます。

## 保持期間と頻度の変更 {#change-retention-and-frequency}

`backup-config update` は、コンソールのフォームと同じ設定 (保持期間 (`--backup-retention-period-hours`) 、頻度 (`--backup-period-hours`) 、開始時刻 (`--backup-start-time`) ) を受け取り、適用後の設定を出力します。API で指定できる保持期間は 24～1080 時間で、日単位 (24 の倍数) で指定する必要があります。頻度は 6、8、12、16、20、24、36、48 時間のいずれかを指定できます。省略したフラグの値は現在の設定のまま維持されます:

```bash
clickhousectl cloud service backup-config update "$CH_ID" \
  --backup-period-hours 12 \
  --backup-retention-period-hours 48 \
  --json
```

```json
{
  "backupPeriodInHours": 12.0,
  "backupRetentionPeriodInHours": 48.0
}
```

頻度によって、最新の復元ポイントが最悪の場合にどれだけ古くなるか (RPO) が決まります。保持期間はバックアップデータを保持する長さを決めるもので、最新の復元ポイントが新しくなるわけではありません。たとえば、保持期間が24時間、頻度が48時間の場合、最新の復元ポイントが作成されたのは約48時間前ということもあります。

変更は即座に反映されます。設定を読み出して確認してください:

```bash
clickhousectl cloud service backup-config get "$CH_ID" --json
```

```json
{
  "backupPeriodInHours": 12.0,
  "backupRetentionPeriodInHours": 48.0
}
```

## バックアップ開始時刻を設定する {#set-a-backup-start-time}

`--backup-start-time` は、UTC での 1 日の開始時刻を正時 (`HH:00`) で指定します。開始時刻を指定すると頻度に制約がかかり、バックアップの周期は `24` 時間または `48` 時間である必要があります。周期は同じコマンドで渡すか、あらかじめサービスに保存されていなければなりません。clickhousectl は、更新を送信する前にフォーマットと周期のルールの両方をチェックします。正時でない時刻や、`2:00` のようにゼロ埋めされていない時刻は、引数パーサーに拒否され、終了コード `2` が返されます:

```bash
clickhousectl cloud service backup-config update "$CH_ID" --backup-start-time 02:30 --json
```

```text
error: invalid value '02:30' for '--backup-start-time <BACKUP_START_TIME>': invalid backup start time '02:30': expected HH:00 with HH from 00 to 23
```

`--backup-start-time` を `24` または `48` 以外の `--backup-period-hours` と併せて指定した場合も同様に、リクエストが送信される前に拒否され、終了コード `1` が返されます。

```text
Error: --backup-period-hours must be 24 or 48 when --backup-start-time is set
```

`--backup-period-hours` は省略できます。省略した場合、サービスは現在の周期をそのまま維持しますが、その保存済みの周期自体が `24` または `48` である必要があります。デフォルトのスケジュールのままのサービスでは周期が `24` のため、開始時刻の指定だけで十分です。上記のサービスは前の step で `12` に設定しているため、周期を省略すると失敗します。`clickhousectl` はまず保存されている configuration を読み取り、終了コード `1` で拒否します。この場合も更新リクエストは送信されません:

```bash
clickhousectl cloud service backup-config update "$CH_ID" --backup-start-time 03:00 --json
```

```text
Error: the stored backup period is 12 hours, but --backup-start-time requires 24 or 48. Pass --backup-period-hours 24 or --backup-period-hours 48 in the same call.
```

周期を明示的に指定するのが有効な組み合わせです。

```bash
clickhousectl cloud service backup-config update "$CH_ID" \
  --backup-start-time 02:00 \
  --backup-period-hours 24 \
  --json
```

```json
{
  "backupPeriodInHours": 24.0,
  "backupRetentionPeriodInHours": 48.0,
  "backupStartTime": "02:00"
}
```

逆のケースはクライアント側では検出されません。開始時刻がすでに保存されている状態で、`--backup-period-hours` のみを `24` または `48` 以外の値に変更する更新を行うと、そのリクエストは API まで到達し、そこで失敗して終了コード `1` が返されます:

```bash
clickhousectl cloud service backup-config update "$CH_ID" --backup-period-hours 12 --json
```

```text
Error: BAD_REQUEST: customBackupPeriod must be 24 or 48 hours when customBackupStartTime is set
```

次の例のように、同じコマンド内で開始時刻をクリアすれば、これを回避できます。

## バックアップ開始時刻をクリアする {#clear-the-backup-start-time}

`--clear-backup-start-time` は、保存されている開始時刻を削除し、期間に対する `24`/`48` 時間の制限を解除します。

```bash
clickhousectl cloud service backup-config update "$CH_ID" \
  --clear-backup-start-time \
  --json
```

```json
{
  "backupPeriodInHours": 24.0,
  "backupRetentionPeriodInHours": 48.0
}
```

`backupStartTime` は `null` として報告されるのではなく出力から消え、`backup-config get` でも返されなくなります。一度も設定されていない開始時刻をクリアした場合は no-op となりますが、終了コードは `0` になります。

`--backup-period-hours` と組み合わせれば、開始時刻のクリアと任意の period の設定を1つのコマンドで実行できます。これが上記の API error を解消する方法です。

```bash
clickhousectl cloud service backup-config update "$CH_ID" \
  --clear-backup-start-time \
  --backup-period-hours 12 \
  --json
```

```json
{
  "backupPeriodInHours": 12.0,
  "backupRetentionPeriodInHours": 48.0
}
```

`--clear-backup-start-time` と `--backup-start-time` は併用できません。パーサーはこの組み合わせを終了コード `2` で拒否します:

```text
error: the argument '--clear-backup-start-time' cannot be used with '--backup-start-time <BACKUP_START_TIME>'
```

開始時刻を削除するのではなく変更したい場合は、新しい `--backup-start-time` のみを指定してください。保存されている値が上書きされます。

<Note>
  バックアップスケジュールを変更すると、一部の backups がサービスの既定の backups の対象外となる場合があり、Storage の月額料金が増加する可能性があります。[「backup コストの理解」](/ja/products/cloud/guides/backups/review-and-restore-backups#understanding-backup-cost)を参照してください。
</Note>
