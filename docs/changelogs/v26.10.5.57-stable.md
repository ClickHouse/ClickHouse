# 2026 Changelog

### ClickHouse release v26.10.5.57-stable (25ea79f784e) FIXME as compared to v26.10.4.207-stable (6b3d0460156)

#### Backward Incompatible Change
* Backported in [#131472](https://github.com/ClickHouse/ClickHouse/issues/131472): Settings of type `Seconds` (for example `max_execution_time` or `lock_acquire_timeout`) now reject a negative value with `BAD_ARGUMENTS`. A negative `max_execution_time` meant no limit and passed a `MAX` constraint; a value whose microseconds round to `2^63` (for example `9223372036854.775`) was stored as a large negative number; it is rejected too. Before upgrading, remove negative values of these settings from configuration files, settings profiles, users and table definitions, and let `Distributed` async insert queues drain; otherwise the server can fail to start, a user or table fails to load, or a queued insert is never sent. [#131269](https://github.com/ClickHouse/ClickHouse/pull/131269) ([Groene AI](https://github.com/groeneai)).

#### Performance Improvement
* Backported in [#131602](https://github.com/ClickHouse/ClickHouse/issues/131602): A `SQL SECURITY DEFINER` view queried by its own definer is no longer read as an opaque step, so the optimizations of the query apply to it again, as before 26.10 (for example, `ORDER BY ... LIMIT` reads in order through it). Other users, and sessions of the definer that are limited by the `GRANTS` of their authentication method or use other roles, still read such a view sealed, and such sessions of the definer no longer bypass the check that hides its plan in `EXPLAIN`. [#130552](https://github.com/ClickHouse/ClickHouse/pull/130552) ([Groene AI](https://github.com/groeneai)).
* Backported in [#132049](https://github.com/ClickHouse/ClickHouse/issues/132049): With `use_lightweight_primary_key_index_analysis = 1` (the default), a filter that can never be true on a primary key column that is not kept in memory, such as `c IN (SELECT ...)` over a subquery that returns no rows or only `NULL`, now skips every granule, as it does with the setting at 0, instead of reading the whole table. [#131291](https://github.com/ClickHouse/ClickHouse/pull/131291) ([Groene AI](https://github.com/groeneai)).
* Backported in [#131978](https://github.com/ClickHouse/ClickHouse/issues/131978): A condition on a primary key column that cannot use the primary key, such as a join runtime filter on the join key or `key LIKE '%x'`, no longer moves the other primary key conditions out of the end of `PREWHERE`, so the more selective conditions run first. The second query of [#131131](https://github.com/ClickHouse/ClickHouse/issues/131131) with `enable_join_runtime_filters = 1` is about 1.4x faster. [#131360](https://github.com/ClickHouse/ClickHouse/pull/131360) ([Groene AI](https://github.com/groeneai)).
* Backported in [#132033](https://github.com/ClickHouse/ClickHouse/issues/132033): Query analysis is faster for a condition written as a deeply nested `AND` tree, such as `((a AND b) AND c) AND ...`, when `optimize_and_compare_chain` is enabled (the default). [#131479](https://github.com/ClickHouse/ClickHouse/pull/131479) ([Groene AI](https://github.com/groeneai)).
* Backported in [#131984](https://github.com/ClickHouse/ClickHouse/issues/131984): A multi-step `PREWHERE` over Compact parts no longer reads the granules that an earlier step filtered out completely again in its later steps and in the final read, whatever the read block size. For the query from [#131382](https://github.com/ClickHouse/ClickHouse/issues/131382) this reads 45% fewer compressed bytes and runs up to 1.5x faster. Closes [#131382](https://github.com/ClickHouse/ClickHouse/issues/131382). [#131569](https://github.com/ClickHouse/ClickHouse/pull/131569) ([Groene AI](https://github.com/groeneai)).
* Backported in [#132010](https://github.com/ClickHouse/ClickHouse/issues/132010): Query analysis is faster for queries whose `WHERE` or `JOIN ON` is an `OR` of `AND` chains over columns of a large subquery or CTE: `optimize_extract_common_expressions` now hashes each condition once per extraction instead of on every lookup. Analysis of the query from [#131572](https://github.com/ClickHouse/ClickHouse/issues/131572) is 1.8x faster at default settings. [#131594](https://github.com/ClickHouse/ClickHouse/pull/131594) ([Groene AI](https://github.com/groeneai)).

#### Improvement
* Backported in [#132046](https://github.com/ClickHouse/ClickHouse/issues/132046): `ReplicatedMergeTree` now removes old deduplication blocks from Keeper in batches of `TryRemove` requests instead of one `Remove` request per block. This reduces the number of Raft entries in Keeper for tables with many replicas. [#128645](https://github.com/ClickHouse/ClickHouse/pull/128645) ([Antonio Andelic](https://github.com/antonio2368)).
* Backported in [#131633](https://github.com/ClickHouse/ClickHouse/issues/131633): Automatic parallel replicas can now enable parallel replicas for queries that use direct read from a text index. [#129339](https://github.com/ClickHouse/ClickHouse/pull/129339) ([Nikita Taranov](https://github.com/nickitat)).
* Backported in [#131878](https://github.com/ClickHouse/ClickHouse/issues/131878): Add setting `automatic_parallel_replicas_statistics_drift_ratio` (default 1.5, previously a fixed 2): how much the rows a read selects may differ from the ones its statistics were collected on before automatic parallel replicas collects the statistics again. [#129809](https://github.com/ClickHouse/ClickHouse/pull/129809) ([Nikita Taranov](https://github.com/nickitat)).

DESC` on such tables no longer returns ascending rows. [#113095](https://github.com/ClickHouse/ClickHouse/pull/113095) ([Groene AI](https://github.com/groeneai)).

* Backported in [#131596](https://github.com/ClickHouse/ClickHouse/issues/131596): Fixed a server crash in `INSERT ... [#128005](https://github.com/ClickHouse/ClickHouse/pull/128005) ([Groene AI](https://github.com/groeneai)).
* Backported in [#132067](https://github.com/ClickHouse/ClickHouse/issues/132067): Lazy materialization for LIMIT queries over joins now also works when the query has ARRAY JOIN: the columns of a table below the ARRAY JOIN are read only for the rows that the LIMIT returns.
