# 2026 Changelog

### ClickHouse release v26.3.28.5-lts (5e3081f5df4) FIXME as compared to v26.3.27.3-lts (22b1ff96abf)

#### Performance Improvement
* Backported in [#117289](https://github.com/ClickHouse/ClickHouse/issues/117289): Sped up SQL function `formatDateTime` with non-const timezone arguments. [#116851](https://github.com/ClickHouse/ClickHouse/pull/116851) ([Robert Schulze](https://github.com/rschu1ze)).

#### Improvement
* Backported in [#113850](https://github.com/ClickHouse/ClickHouse/issues/113850): Added fs cache download wait timeout configured by `filesystem_cache_wait_for_concurrent_download_timeout_milliseconds`. This timeout defined only the wait for a single chunk (buffer bytes of ~1mb) of data, not the whole file segment. [#113322](https://github.com/ClickHouse/ClickHouse/pull/113322) ([Kseniia Sumarokova](https://github.com/kssenii)).

#### Bug Fix (user-visible misbehavior in an official stable release)
* Backported in [#117154](https://github.com/ClickHouse/ClickHouse/issues/117154): Fixed a settings-constraint bypass: a `SETTINGS` clause inside a subquery, a CTE or a view's inner query was applied without checking the settings constraints, so it could be used to leave readonly mode or to override a `CONST`, `MIN` or `MAX` constraint (for example `additional_table_filters`, breaking row-level isolation). The nested clause is now clamped to the constraints: violating changes are dropped, out-of-bounds values are clamped into their bounds, and the rest of the clause applies. Existing views whose inner query carries such a clause keep working, with the constraints enforced; a clause on the outer query still throws, as before. [#115397](https://github.com/ClickHouse/ClickHouse/pull/115397) ([Itamar Tempelhof](https://github.com/tempel-it)).

#### NOT FOR CHANGELOG / INSIGNIFICANT

* Backported in [#117360](https://github.com/ClickHouse/ClickHouse/issues/117360): This patch fixes `removePartAndCoveredParts` when it is being called for a part that is actually present in the active data part set. The problem was that part itself will always be in `parts_covered_by,` so the subsequent remove in the loop will not be able to remove it twice. [#115640](https://github.com/ClickHouse/ClickHouse/pull/115640) ([Mikhail Artemenko](https://github.com/Michicosun)).
