# 2026 Changelog

### ClickHouse release v26.10.4.207-stable (6b3d0460156) FIXME as compared to v26.10.3.7-stable (0a1e24c62a8)

#### Backward Incompatible Change
* Backported in [#129966](https://github.com/ClickHouse/ClickHouse/issues/129966): Added the `AI FUNCTIONS` privilege group and per-function privileges (`aiGenerate`, `aiEmbed`, etc.) that control who can call AI functions, e.g. `GRANT AI FUNCTIONS ON *.* TO role` or `GRANT aiGenerate, aiClassify ON *.* TO role`. Calling an AI function now requires its privilege in addition to `NAMED COLLECTION` access to the selected credentials. To keep existing users working, run `GRANT AI FUNCTIONS ON *.* TO <user_or_role>`. Functions used in the keys, TTL, skip indexes and projections of a new `MergeTree` table now require the privileges of the user creating the table. AI functions are rejected in newly defined `MergeTree` keys, TTL expressions, skip indexes and projections, in `DEFAULT` and `MATERIALIZED` expressions computed in the background, and in mutations, even when the user has the AI privilege; use a lightweight `UPDATE` or `INSERT ... SELECT` instead of `ALTER TABLE ... UPDATE` to fill a column with AI function results. [#127057](https://github.com/ClickHouse/ClickHouse/pull/127057) ([George Larionov](https://github.com/george-larionov)).
* Backported in [#128954](https://github.com/ClickHouse/ClickHouse/issues/128954): Setting `after_processing_move_uri` or `after_processing_move_connection_string` of an `S3Queue` or `AzureQueue` table now requires `WRITE ON S3` for the destination URL (or `WRITE ON AZURE`), and `ALTER TABLE ... MODIFY SETTING` also requires `SELECT` on the table. Before, the `ALTER SETTINGS` grant was enough. The destination must also be allowed by `remote_url_allow_hosts`. [#127180](https://github.com/ClickHouse/ClickHouse/pull/127180) ([Antonio Andelic](https://github.com/antonio2368)).
* Backported in [#130478](https://github.com/ClickHouse/ClickHouse/issues/130478): MongoDB connection strings can no longer make the server authenticate with its own credentials: the `MONGODB-OIDC`, `MONGODB-AWS`, `GSSAPI` and `MONGODB-X509` authentication mechanisms and the `tlsCertificateKeyFile` option. In the `mongodb` table function and `MongoDB` tables they are refused unless `s3_allow_server_credentials_in_user_queries` is enabled for the session that reads. In MongoDB dictionaries created with a DDL query they are always refused; define such dictionaries in the server configuration files instead. Existing tables and dictionaries that use them stop working. [#129969](https://github.com/ClickHouse/ClickHouse/pull/129969) ([Groene AI](https://github.com/groeneai)).

#### New Feature
* Backported in [#127829](https://github.com/ClickHouse/ClickHouse/issues/127829): Added the `SHARED` modifier for typed paths of the `JSON` type, for example `JSON(SHARED a UInt32, SHARED b String)`. In `MergeTree` parts such paths are stored together in a constant set of files instead of a set of files per path, which keeps the number of files and object storage requests per part small for columns with many typed paths, while a read of a path still decodes only that path. The on-disk format is controlled by the new `MergeTree` setting `object_typed_shared_data_serialization_version`. Sub-column resolution of `JSON` now prefers a typed path over a same-named sub-column of another typed path, for example `json.a.b` of `JSON(a Tuple(b String), a.b Int64)` is now the typed path `a.b`; `MergeTree` rejects such types, so only other engines and `CAST` see the change. [#127000](https://github.com/ClickHouse/ClickHouse/pull/127000) ([Pavel Kruglov](https://github.com/Avogar)).

#### Experimental Feature
* Backported in [#129413](https://github.com/ClickHouse/ClickHouse/issues/129413): DPsub is now the default join order algorithm (`query_plan_optimize_join_order_algorithm = 'dpsub,greedy'`), together with the CD-C conflict detector, which also lets semi and anti joins take part in reordering. Queries with more than 12 joined tables fall back to the greedy algorithm. [#120110](https://github.com/ClickHouse/ClickHouse/pull/120110) ([Fisnik Kastrati](https://github.com/fkastrati)).

#### Performance Improvement
* Backported in [#130809](https://github.com/ClickHouse/ClickHouse/issues/130809): Fixed a performance regression of `dictGet` with direct dictionaries (and of `x IN (<many literals>)` in general): constant literals are converted to the column type directly instead of through a CAST function per value. Closes [#115803](https://github.com/ClickHouse/ClickHouse/issues/115803). [#117018](https://github.com/ClickHouse/ClickHouse/pull/117018) ([Manuel](https://github.com/raimannma)).
* Backported in [#129406](https://github.com/ClickHouse/ClickHouse/issues/129406): A `JOIN ON` condition that combines an equality with an `OR` without equalities, such as `ON a.id = b.id AND (b.x IS NULL OR b.x < a.y)`, now keeps the equality as the join key of an `ALL INNER` join (and of an outer `ALL` join when a branch of the `OR` only compares both tables), so join reordering can use it. Before, the `OR` was expanded over the rest of the condition and join reordering could pick a near cross product: the query from the issue took 18.6 s instead of 0.04 s. Closes [#122510](https://github.com/ClickHouse/ClickHouse/issues/122510). [#122526](https://github.com/ClickHouse/ClickHouse/pull/122526) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129575](https://github.com/ClickHouse/ClickHouse/issues/129575): A `PREWHERE` condition on a subcolumn (for example `j.kind = 'b'` on a `JSON` column) is again evaluated in its own read step, so the rest of the column is read only for the rows that pass it. `m['key']` is now rewritten to the `Map` key subcolumn only for tables with `with_buckets` `Map` serialization, where it reads a single bucket; with `basic` serialization the whole `Map` is read once, as before 26.3. Closes [#124535](https://github.com/ClickHouse/ClickHouse/issues/124535). [#124553](https://github.com/ClickHouse/ClickHouse/pull/124553) ([Groene AI](https://github.com/groeneai)).
* Backported in [#128035](https://github.com/ClickHouse/ClickHouse/issues/128035): Faster `ORDER BY` over the result of a `JOIN` whose columns are replicated lazily (`enable_lazy_columns_replication`): merging these columns no longer pays a hash table lookup and a memory allocation for every row, and merged blocks without shared values are passed on as plain columns. The query from [#122436](https://github.com/ClickHouse/ClickHouse/issues/122436) became about 9 times faster, and sorting wide replicated values keeps the memory savings of lazy replication. [#124702](https://github.com/ClickHouse/ClickHouse/pull/124702) ([Pavel Kruglov](https://github.com/Avogar)).
* Backported in [#131128](https://github.com/ClickHouse/ClickHouse/issues/131128): Improve parallel replica execution for queries that aggregate over subqueries with redundant ORDER BY clauses by allowing replicas to perform the aggregation. Also enable automatic parallel replica plan matching for these queries. [#125685](https://github.com/ClickHouse/ClickHouse/pull/125685) ([Nikita Taranov](https://github.com/nickitat)).
* Backported in [#129835](https://github.com/ClickHouse/ClickHouse/issues/129835): A two-level `GROUP BY` that holds few keys no longer enables software prefetch only because its preallocated buckets are larger than the L2 cache. Such queries were up to 3x slower since 26.7, for example 13 keys with `group_by_two_level_threshold_bytes = 1`. Closes [#125845](https://github.com/ClickHouse/ClickHouse/issues/125845). [#125897](https://github.com/ClickHouse/ClickHouse/pull/125897) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129326](https://github.com/ClickHouse/ClickHouse/issues/129326): Reading subcolumns (for example, typed paths of a `JSON` column) from MergeTree tables with many parts is faster: a reader now takes the serialization of a static subcolumn from the data part instead of resolving it again every time it is created. [#126077](https://github.com/ClickHouse/ClickHouse/pull/126077) ([Pavel Kruglov](https://github.com/Avogar)).
* Backported in [#129945](https://github.com/ClickHouse/ClickHouse/issues/129945): `BACKUP` uses less memory for backups of many files, especially incremental ones: the backup no longer keeps a finished thread pool task for every file it backs up. [#126130](https://github.com/ClickHouse/ClickHouse/pull/126130) ([Julia Kartseva](https://github.com/jkartseva)).
* Backported in [#128801](https://github.com/ClickHouse/ClickHouse/issues/128801): The row estimate no longer treats an always-true `x = x` condition (one non-`Nullable` column of an integer, `Decimal`, `Enum`, date or time, string, `UUID` or IP type) as selective. A correlated subquery that correlates by equality keeps such a condition for each correlation key, so a multi-key `EXISTS` estimated its inner table several times too small and could get a single-threaded hash join. Closes [#122677](https://github.com/ClickHouse/ClickHouse/issues/122677). [#126131](https://github.com/ClickHouse/ClickHouse/pull/126131) ([Groene AI](https://github.com/groeneai)).
* Backported in [#131280](https://github.com/ClickHouse/ClickHouse/issues/131280): A window function that is referenced several times, for example through a chain of aliases or in both the `SELECT` list and `QUALIFY`, is now computed once instead of once per reference. Such queries became several times slower with the analyzer compared to the old query analysis. [#126209](https://github.com/ClickHouse/ClickHouse/pull/126209) ([Yakov Olkhovskiy](https://github.com/yakov-olkhovskiy)).
* Backported in [#128797](https://github.com/ClickHouse/ClickHouse/issues/128797): A `GROUP BY` whose groups are capped, by the trivial `GROUP BY ... LIMIT` optimization or by `max_rows_to_group_by` with `group_by_overflow_mode` `'any'` or `'break'`, now keeps its own hash table size statistics, and so does an aggregation over such a capped one. It no longer preallocates the hash table of the same aggregation without the cap, and the next uncapped run still preallocates for all its groups. Closes [#122608](https://github.com/ClickHouse/ClickHouse/issues/122608). [#126374](https://github.com/ClickHouse/ClickHouse/pull/126374) ([Groene AI](https://github.com/groeneai)).
* Backported in [#128692](https://github.com/ClickHouse/ClickHouse/issues/128692): Join reordering estimates a relation with `arrayJoin` or `ARRAY JOIN` as 100 rows per input row instead of leaving its size unknown, so a hash join builds its hash table from a small or empty array join input instead of reading the other input into it. Closes [#126481](https://github.com/ClickHouse/ClickHouse/issues/126481). [#126491](https://github.com/ClickHouse/ClickHouse/pull/126491) ([Groene AI](https://github.com/groeneai)).
* Backported in [#128796](https://github.com/ClickHouse/ClickHouse/issues/128796): The replicas of a catalog-less Iceberg read through `icebergS3Cluster`, `icebergAzureCluster`, `icebergHDFSCluster` or `icebergLocalCluster` (or `icebergS3` with `parallel_replicas_for_cluster_engines`) no longer list the table's `metadata` directory to find the latest `metadata.json`: the initiator passes them the metadata file of the snapshot it reads, so they send no `ListObjects` requests for it and read the same snapshot as the initiator. Closes [#127060](https://github.com/ClickHouse/ClickHouse/issues/127060). [#127085](https://github.com/ClickHouse/ClickHouse/pull/127085) ([Groene AI](https://github.com/groeneai)).
* Backported in [#130187](https://github.com/ClickHouse/ClickHouse/issues/130187): Bump jemalloc for the fiber-safe TLS rework (upstream solution). [#127478](https://github.com/ClickHouse/ClickHouse/pull/127478) ([Azat Khuzhin](https://github.com/azat)).
* Backported in [#130356](https://github.com/ClickHouse/ClickHouse/issues/130356): Merging large `uniqExact` states is several times faster with the new Robin Hood hash tables: the destination set now grows before the merge, so its inserts no longer pile up at the higher load factor. This affects `uniqExactMerge`, merges of `AggregatingMergeTree` parts with `uniqExact` states, and `COUNT(DISTINCT)` together with other aggregates on few threads. [#127625](https://github.com/ClickHouse/ClickHouse/pull/127625) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129063](https://github.com/ClickHouse/ClickHouse/issues/129063): Automatic parallel replicas (`automatic_parallel_replicas_mode`) now collects statistics for queries that join an aggregated subquery whose filter goes to PREWHERE. Previously it could not match the two plans for such queries and built the plan with parallel replicas on every execution without ever using it. [#127628](https://github.com/ClickHouse/ClickHouse/pull/127628) ([Nikita Taranov](https://github.com/nickitat)).
* Backported in [#131092](https://github.com/ClickHouse/ClickHouse/issues/131092): A `SELECT ... LIMIT 0` from a MergeTree table no longer runs the primary key and skip index analysis, which took up to seconds on large tables with a filter on the key. Such a query reads nothing, so `max_rows_to_read` and `max_partitions_to_read` no longer reject it. Closes [#125812](https://github.com/ClickHouse/ClickHouse/issues/125812). [#130578](https://github.com/ClickHouse/ClickHouse/pull/130578) ([Groene AI](https://github.com/groeneai)).

#### Improvement
* Backported in [#128319](https://github.com/ClickHouse/ClickHouse/issues/128319): AI functions issue provider requests concurrently from a server-wide thread pool (`ai_function_max_thread_pool_size`), with up to `ai_function_max_concurrent_requests_per_thread` requests in flight per query thread (default 8). `ai_function_max_retries` defaults to 3, and new `ProfileEvents` count retried, failed and throttled provider requests. [#122484](https://github.com/ClickHouse/ClickHouse/pull/122484) ([George Larionov](https://github.com/george-larionov)).
* Backported in [#129323](https://github.com/ClickHouse/ClickHouse/issues/129323): Fixed `DECIMAL_OVERFLOW` thrown by `=`, `!=`, `IN`, `NOT IN` and non-`Nullable` `IS [NOT] DISTINCT FROM` when a decimal is compared with a decimal constant that does not fit its type at its scale, e.g. `d IN (toDecimal128(1000000000, 0))` for `d Decimal(38, 30)`, on sorting and partition keys, `minmax` and `set` indexes, `EmbeddedRocksDB` keys and unindexed columns. Such a constant now equals no value of the column instead of throwing. [#126603](https://github.com/ClickHouse/ClickHouse/pull/126603) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129477](https://github.com/ClickHouse/ClickHouse/issues/129477): The Azure table functions and engines (`azureBlobStorage`, `icebergAzure`, `AzureBlobStorage`, ...) now reject a malformed URL in the `(url, sas_token)` form with `BAD_ARGUMENTS` instead of failing with `std::out_of_range` or a logical error, and a URL that ends right after the host is parsed like the same URL with a trailing slash. [#126984](https://github.com/ClickHouse/ClickHouse/pull/126984) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129171](https://github.com/ClickHouse/ClickHouse/issues/129171): Jemalloc heap profiles in `system.jemalloc_profile_text`, `system.jemalloc_sampled_allocations` and the Keeper `/jemalloc/profile` endpoint no longer contain runtime memory addresses nor the memory map: addresses inside the binary are offsets, others are 0. `jeprof` still analyzes them. [#127596](https://github.com/ClickHouse/ClickHouse/pull/127596) ([Raúl Marín](https://github.com/Algunenano)).
* Backported in [#129782](https://github.com/ClickHouse/ClickHouse/issues/129782): The `ORC` format is now read and written by a native implementation instead of the Apache ORC C++ library, with the same behavior and the same files on output. The values are read and written directly into and from ClickHouse columns: reading is 1.4 to 2.3 times faster and writing is about 25% faster. The build does not need `protoc` for ORC anymore. Fixed writing `Date` values after 2059-09-18 to ORC, which were read back as dates before 1970. [#127690](https://github.com/ClickHouse/ClickHouse/pull/127690) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Backported in [#128530](https://github.com/ClickHouse/ClickHouse/issues/128530): Reading a `LowCardinality` column from a corrupted data part whose indexes point past the dictionary now throws `INCORRECT_DATA` instead of reading past the end of the keys, which could crash the server. [#128476](https://github.com/ClickHouse/ClickHouse/pull/128476) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129118](https://github.com/ClickHouse/ClickHouse/issues/129118): Text formats (`TSV`, `CSV`, `JSONEachRow`, `LineAsString`, ...) read from data compressed with `snappy_mode = 'framed'` with `input_format_parallel_parsing = 0` no longer read past the end of the decompression buffer. [#128567](https://github.com/ClickHouse/ClickHouse/pull/128567) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129286](https://github.com/ClickHouse/ClickHouse/issues/129286): Don't do s3 requests to get metadata in delta tables. [#128604](https://github.com/ClickHouse/ClickHouse/pull/128604) ([Konstantin Vedernikov](https://github.com/scanhex12)).
* Backported in [#129321](https://github.com/ClickHouse/ClickHouse/issues/129321): Initialize parquet reader a bit earlier. [#128607](https://github.com/ClickHouse/ClickHouse/pull/128607) ([Konstantin Vedernikov](https://github.com/scanhex12)).

[#129042](https://github.com/ClickHouse/ClickHouse/pull/129042) ([Sema Checherinda](https://github.com/CheSema)).
* Backported in [#129719](https://github.com/ClickHouse/ClickHouse/issues/129719): Introspection functions and `system.symbols` work only with offsets inside the main binary: `addressToSymbol` no longer accepts absolute addresses, `system.symbols` no longer lists symbols of shared libraries, and `flameGraph` requires the `INTROSPECTION` grant. gRPC library logs are no longer written, and the `grpc.verbose_logs` setting is removed (it is ignored if present). [#129112](https://github.com/ClickHouse/ClickHouse/pull/129112) ([Raúl Marín](https://github.com/Algunenano)).

#### Bug Fix (user-visible misbehavior in an official stable release)
* Backported in [#128619](https://github.com/ClickHouse/ClickHouse/issues/128619): Fix undefined behavior when a refreshable materialized view uses a very large `RANDOMIZE FOR` window. The random offset was converted from `double` to `Int64` milliseconds and widened to microseconds without range checks, so such a window produced a meaningless next refresh time or aborted a sanitizer build. The offset is now capped at about 95 years, so an absurd window behaves like the widest supported jitter. [#113673](https://github.com/ClickHouse/ClickHouse/pull/113673) ([Groene AI](https://github.com/groeneai)).
* Backported in [#128504](https://github.com/ClickHouse/ClickHouse/issues/128504): Fixed a server abort when reading Parquet with a declared structure carrying a `DEFAULT` expression, on a count-only read or with `input_format_defaults_for_omitted_fields` disabled. [#116666](https://github.com/ClickHouse/ClickHouse/pull/116666) ([Groene AI](https://github.com/groeneai)).
* Backported in [#129868](https://github.com/ClickHouse/ClickHouse/issues/129868): Fix lightweight updates on replicated tables silently skipping rows that arrived on the initiating replica during the `update_sequential_consistency` sync. The update reused a storage snapshot taken before the sync, so the `UPDATE` returned success while those acknowledged rows kept their old values. [#117174](https://github.com/ClickHouse/ClickHouse/pull/117174) ([Pratyush Anand](https://github.com/pratyush-anand1444)).
* Backported in [#129272](https://github.com/ClickHouse/ClickHouse/issues/129272): Fixed `Arrow`, `ArrowStream` and Arrow Flight output failing with `Capacity error: array cannot contain more than 2147483646 bytes` or `Arrow IPC string offset exceeds 32 bits` when a block held more than 2 GiB of `String` data. Such a block is now written as several Arrow record batches. [#117754](https://github.com/ClickHouse/ClickHouse/pull/117754) ([Pavel Kruglov](https://github.com/Avogar)).
* Backported in [#128500](https://github.com/ClickHouse/ClickHouse/issues/128500): Fix a privilege escalation where a scheduled refresh of a `SQL SECURITY DEFINER` refreshable materialized view reading from a `Distributed` table over a cluster with an interserver `<secret>` was executed on remote shards without authentication, bypassing the definer's access rights. The remote query now runs as the definer. [#117798](https://github.com/ClickHouse/ClickHouse/pull/117798) ([Michael Kolupaev](https://github.com/al13n321)).
* Backported in [#128864](https://github.com/ClickHouse/ClickHouse/issues/128864): Fixed leftovers of the nested `SETTINGS` constraints fix ([#115397](https://github.com/ClickHouse/ClickHouse/issues/115397)): `use_query_cache` set inside a subquery or a CTE could still enable the query result cache despite a `CONST` or `readonly` constraint, and a nested clause was forwarded to the shards of a `Distributed` query as written, bypassing the initiator's constraints there. An unknown setting name or an uncastable value in a nested `SETTINGS` clause now throws as in a top-level clause instead of being silently ignored. [#118822](https://github.com/ClickHouse/ClickHouse/pull/118822) ([Dmitry Novik](https://github.com/novikd)).
* Backported in [#127965](https://github.com/ClickHouse/ClickHouse/issues/127965): Respect `remote_url_allow_hosts` in the Hive metastore catalog. [#119353](https://github.com/ClickHouse/ClickHouse/pull/119353) ([Smita Kulkarni](https://github.com/SmitaRKulkarni)).
* Backported in [#130474](https://github.com/ClickHouse/ClickHouse/issues/130474): Fixed a privilege check bypass in text index `preprocessor` and `postprocessor` expressions. They were resolved under an internal full-access context, so functions requiring a grant, such as `demangle` and `addressToLine`, could be used without it. These expressions are now authorized against the user who declares the index. Creating or adding a text index with a `preprocessor` or `postprocessor` using `ON CLUSTER` now requires `distributed_ddl_use_initial_user_and_roles = 1` on every host and `distributed_ddl_entry_format_version >= 8`; otherwise the query is rejected. [#120080](https://github.com/ClickHouse/ClickHouse/pull/120080) ([Jimmy Aguilar Mena](https://github.com/Ergus)).
* Backported in [#130288](https://github.com/ClickHouse/ClickHouse/issues/130288): Fixed a wrong result where a `RIGHT`, `LEFT`, `FULL` or `ANY` outer `JOIN` returned too few rows when the `WHERE` value came from `assumeNotNull` of a `NULL`. The query plan converted such a join to `INNER`, `SEMI` or `ANTI` after evaluating the filter over constants, where `assumeNotNull` reads a different value than it does at runtime. Closes [#120204](https://github.com/ClickHouse/ClickHouse/issues/120204). [#120258](https://github.com/ClickHouse/ClickHouse/pull/120258) ([Groene AI](https://github.com/groeneai)).
* Backported in [#130789](https://github.com/ClickHouse/ClickHouse/issues/130789): Fixed wrong results when `WHERE` wraps a `Nullable` partition key in a NULL-erasing function: `assumeNotNull`, `isNull`/`isNotNull` compared with a constant (`(c IS NULL) >= true`), or `ifNull`/`coalesce` under `NOT` or with `allow_key_condition_coalesce_rewrite = 0`. Partition pruning discarded the `NULL` partition instead of evaluating the predicate on its rows, so rows disappeared from both a predicate and its negation. [#121154](https://github.com/ClickHouse/ClickHouse/pull/121154) ([Groene AI](https://github.com/groeneai)).
* Backported in [#128827](https://github.com/ClickHouse/ClickHouse/issues/128827): Fixed a logical error (`Bad cast from type DB::ColumnReplicated to DB::ColumnNullable`) in an `ASOF JOIN` whose right side has a `Nullable` ASOF key produced through lazy column replication, for example by `arrayJoin` or a nested `JOIN`. `enable_lazy_columns_replication` is on by default, and on a release build the cast was unchecked, so the NULL filter on the ASOF key could keep or drop the wrong rows. [#121385](https://github.com/ClickHouse/ClickHouse/pull/121385) ([Groene AI](https://github.com/groeneai)).
* Backported in [#128826](https://github.com/ClickHouse/ClickHouse/issues/128826): Fixes a server abort when a query with `LIMIT AFTER` or `LIMIT UNTIL` has a lambda in its `SELECT` list that the boundary expression repeats, or once its expressions are JIT-compiled (by default on its fourth run). Such a query over remote shards also no longer fails with `Serialization is not implemented for data type Function`. [#122045](https://github.com/ClickHouse/ClickHouse/pull/122045) ([Groene AI](https://github.com/groeneai)).
* Backported in [#128825](https://github.com/ClickHouse/ClickHouse/issues/128825): A valid query over a `JOIN` whose `WHERE` guards a conjunct that can throw could be rejected with an error such as `CANNOT_PARSE_DATETIME`. Filter push-down into the `JOIN`, merging a filter into the `JOIN` condition, and an aggregate projection's residual filter each rebuilt the conjuncts they pushed into a side or left behind in an order that was not the written one, so a guarded conjunct could be evaluated ahead of its guard. Reported in [#121909](https://github.com/ClickHouse/ClickHouse/issues/121909). [#122160](https://github.com/ClickHouse/ClickHouse/pull/122160) ([Groene AI](https://github.com/groeneai)).
