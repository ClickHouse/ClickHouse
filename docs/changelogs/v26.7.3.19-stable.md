# 2026 Changelog

### ClickHouse release v26.7.3.19-stable (c3c4a420478) FIXME as compared to v26.7.2.59-stable (1399e12824d)

#### Performance Improvement
* Backported in [#113467](https://github.com/ClickHouse/ClickHouse/issues/113467): Fixed a performance regression where a single lightweight `DELETE` disabled the query condition cache for the whole table. Repeated selective queries over a table that had ever been touched by a lightweight delete stopped pruning granules and fell back to reading every mark. [#112947](https://github.com/ClickHouse/ClickHouse/pull/112947) ([Nikita Fomichev](https://github.com/fm4v)).

#### Bug Fix (user-visible misbehavior in an official stable release)
* Backported in [#113483](https://github.com/ClickHouse/ClickHouse/issues/113483): Fix server crashes and wrong `NOT_FOUND_COLUMN_IN_BLOCK` / `LOGICAL_ERROR` failures in a `direct` JOIN over a MergeTree right table. The plan is cloned and re-optimized per lookup across threads, but the clone shared two mutable objects with the original: the `PrewhereInfo`/`row_level_filter` DAG, corrupted in place by column pruning, and the `StorageSnapshot`, whose data parts are stripped in place. [#109932](https://github.com/ClickHouse/ClickHouse/pull/109932) ([Groene AI](https://github.com/groeneai)).
* Backported in [#113092](https://github.com/ClickHouse/ClickHouse/issues/113092): With `analyzer_compatibility_join_using_top_level_identifier = 1`, an identifier in `JOIN ... USING` can now be resolved from an alias defined on a subexpression inside the SELECT list (for example, `SELECT uniqExact(lower(x) AS id) FROM t1 JOIN t2 USING (id)`), matching the old analyzer behavior. Previously only top-level projection aliases were considered, and such queries failed with an `UNKNOWN_IDENTIFIER` exception even with the setting enabled. The error hint suggesting the setting is now also produced when the matching alias is nested. [#110739](https://github.com/ClickHouse/ClickHouse/pull/110739) ([Dmitry Novik](https://github.com/novikd)).
* Backported in [#113568](https://github.com/ClickHouse/ClickHouse/issues/113568): Fixed a logical error `Block structure mismatch` (in debug and sanitizer builds) and an `Illegal types of arguments` error for set operations over compatible aggregate-state columns (e.g. `quantileState` and `quantilesState(0.9)`) nested inside container columns such as `Tuple`, `Array`, `Map`, `Nullable`, or `Variant`. [#111191](https://github.com/ClickHouse/ClickHouse/pull/111191) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Backported in [#112545](https://github.com/ClickHouse/ClickHouse/issues/112545): Now RestCatalog throw proper exception instead of silence or "UNKNOWN_TABLE" in case of stale credentials. [#111379](https://github.com/ClickHouse/ClickHouse/pull/111379) ([alesapin](https://github.com/alesapin)).
* Backported in [#113261](https://github.com/ClickHouse/ClickHouse/issues/113261): Fix an out-of-bounds read (a crash in release builds) in insert deduplication when an `INSERT` flows through a materialized view whose inner query changes the number of rows and the deduplicating target table is partitioned. `DeduplicationInfo::filterToPartition` attributed each deduplication token to partitions by walking the token's source-row range over a partition selector sized to the (smaller) view-output block, reading past its bounds. It now keeps every token in every partition for any materialized-view target — where the source-row-to-partition mapping no longer exists after the row count changed — instead of the out-of-bounds walk (and instead of the `NOT_IMPLEMENTED` that a later guard raised for the same insert). [#112649](https://github.com/ClickHouse/ClickHouse/pull/112649) ([Sema Checherinda](https://github.com/CheSema)).
* Backported in [#113356](https://github.com/ClickHouse/ClickHouse/issues/113356): Fixed server startup and `ATTACH` failing with `WITH RECURSIVE is not supported with the old analyzer` for a view with a recursive CTE when `enable_analyzer = 0` is the server default. [#112784](https://github.com/ClickHouse/ClickHouse/pull/112784) ([Nikolay Degterinsky](https://github.com/evillique)).
* Backported in [#113257](https://github.com/ClickHouse/ClickHouse/issues/113257): Fixed an out-of-bounds write when reading a `Parquet` `DECIMAL` column whose physical type is wider than the type its declared precision maps to, for example `DECIMAL(9, 2)` stored as physical `INT64`. Such files are valid `Parquet` and other writers produce them, but the reader sized the destination column from the declared precision while the decoder wrote the physical width, corrupting memory. Reading such a file now also raises `DECIMAL_OVERFLOW` when a value does not fit the declared precision, instead of returning corrupted data, and reads losslessly with a type hint at least as wide as the physical type. [#113046](https://github.com/ClickHouse/ClickHouse/pull/113046) ([Groene AI](https://github.com/groeneai)).
* Backported in [#113498](https://github.com/ClickHouse/ClickHouse/issues/113498): Fix a rare use-after-free bug that is triggered in a rare event of the async insert queue having different entries with identical deadlines. Now it's handled gracefully. [#113363](https://github.com/ClickHouse/ClickHouse/pull/113363) ([Miсhael Stetsyuk](https://github.com/mstetsyuk)).
