You can authenticate connections to ClickHouse with JSON Web Tokens (JWTs) instead of database passwords. Your identity provider issues short-lived tokens. ClickHouse checks each token against the public keys in a JSON Web Key Set (JWKS) document, at a URL that you configure.

This guide covers ClickHouse Cloud and ClickHouse Private. Select **Cloud** or **Private** to show the steps for your deployment. For the structure of a JWT, its required claims, the roles and grants claims, and ephemeral users, see the [JWT Authentication](/concepts/features/security/external-authenticators/jwt) reference.

<Tip>
**Using Microsoft Entra ID?**

Follow [JWT authentication with Microsoft Entra ID](/products/cloud/guides/security/cloud-access-management/jwt-authentication-entra-id). It covers the Entra ID setup, the ClickHouse configuration, and how to map Entra ID app roles to ClickHouse roles.
</Tip>

## How it works {#how-it-works}

Your identity provider or application creates a JWT and signs it with its **private key**. The token must use the [token format](/concepts/features/security/external-authenticators/jwt#token-claims) that ClickHouse expects. ClickHouse then checks the token against the **public** keys at your JWKS URL:

1. ClickHouse reads the `kid` (key ID) header of the token and finds the key with that ID in the JWKS document.
2. ClickHouse checks the token signature with that key. It then compares the `iss` (issuer) and `aud` (audience) claims with the values that you configured.
3. If all checks pass, the connection runs as an ephemeral user. The `clickhouse:grants` and `clickhouse:roles` claims of the token set the access rights of this user. The ephemeral user never gets more privileges than the permission limit. In ClickHouse Cloud, the permission limit is the `default` user. On ClickHouse Private, you set it with `permission_limit`. For details, see [Access rights](/concepts/features/security/external-authenticators/jwt#access-rights).

In ClickHouse Cloud, you configure JWKS providers yourself, per service, from **Settings → Security** in the Cloud console.

## Before you begin {#before-you-begin}

To configure JWT providers for a service, you need:

- An organization on the **Enterprise** plan.
- A service running **ClickHouse version 26.4 or later**.
- A role with the `control-plane:service:manage` permission on the service (for example, **Admin** or **Service admin**). Members without it see the section as read only.
- A publicly reachable **HTTPS** JWKS URL that publishes at least one **RSA** key (`RS256`) or, for services on version 26.8 or later, an **EC** key (`ES256`, `ES384`, `ES512`).

<Note>
JWKS-based providers accept **RSA** keys and, from version 26.8, **EC** keys on the P-256, P-384, and P-521 curves. A JWKS document may contain other key types, but at least one usable key must be present.
</Note>

## Add a JWT provider {#add-a-jwt-provider}

<Steps>
<Step title="Open the service security settings" id="open-security-settings">

Navigate to your service, open **Settings**, and scroll to the **Security** section. Find the **JWT authentication** card.

<div className="ch-image-lg">

<Frame>

![JWT authentication section in service security settings](/images/cloud/security/jwt/jwt-section.png)

</Frame>

</div>
</Step>
<Step title="Open the providers flyout" id="open-flyout">

Select **Set up JWT providers** (or **Manage JWT providers** if you already have some). The flyout opens with a new provider form ready to fill in.
</Step>
<Step title="Fill in the provider details" id="fill-provider-details">

Complete the provider form and select **Save**.

| Field | Description |
|-------|-------------|
| **Name** | A unique name for this provider on the service. Cannot be changed after creation. |
| **Issuer** | The expected `iss` claim of incoming tokens. |
| **Audience** | The expected `aud` claim of incoming tokens. |
| **JWKS URL** | The public HTTPS URL that publishes the public keys used to verify token signatures. |
| **Roles claim** (optional) | The token claim to read ClickHouse roles from. Leave blank to use the default claim name `clickhouse:roles`. Roles named in the token must already exist on the service. |

ClickHouse validates and fetches the JWKS URL when you add or update a provider, so a misconfigured or unreachable URL is rejected up front.

</Step>
<Step title="Add more providers if needed" id="add-more-providers">

Use **Add another provider** to configure additional providers. A service can have at most five JWT providers.
</Step>
</Steps>

<Warning>
Deleting a JWT provider immediately stops accepting tokens issued for it, and any workloads still authenticating with those tokens will stop working.
</Warning>

## Limits {#limits}

- A maximum of **five** JWT providers per service.
- JWKS providers accept **RSA** keys (`RS256`) and, from version 26.8, **EC** keys (`ES256`, `ES384`, `ES512`).
- The JWKS URL must be a public HTTPS endpoint. Private, internal, or link-local addresses are rejected.

</View>

<View title="Private">

On ClickHouse Private, you configure JWT authentication in the server configuration of the cluster, in the `ClickHouseCluster` resource or in the Helm values.

## Before you begin {#before-you-begin}

To configure JWT authentication for a cluster, you need:

- A ClickHouse Private cluster that runs **ClickHouse 26.4 or later**.
- Permission to change the server configuration of the cluster, in the `ClickHouseCluster` resource or in the values of the Helm release.
- An **HTTPS** JWKS URL that the cluster can reach that publishes at least one **RSA** key (`RS256`) or, for services on version 26.8 or later, an **EC** key (`ES256`, `ES384`, `ES512`).

## Configure the JWT authenticator {#configure-jwt-authenticator}

Add a `jwt` entry to `user_directories` in the server configuration of the cluster. The entry has these settings:

| Setting | Description |
|---|---|
| `aud` | The value that the `aud` claim of each token must have. |
| `iss` | The value that the `iss` claim of each token must have. |
| `jwks.url` | The HTTPS URL of the JWKS document. ClickHouse uses the public keys in this document to check token signatures. |
| `jwks.update_interval_ms` | The interval, in milliseconds, at which ClickHouse fetches the keys again. The examples use `300000` (5 minutes). |
| `permission_limit.user` | The user whose privileges are the upper limit for JWT users, for example `default`. This guide calls it the `permission_limit` user. |
| `remap_claims.roles` (optional) | The token claim that contains the ClickHouse role names. If you don't set it, ClickHouse uses the `clickhouse:roles` claim. Each role in the token must already exist on the cluster. |

<Tabs>
<Tab title="ClickHouseCluster resource" id="clickhousecluster-resource">

Put the configuration under `spec.extraConfig.server` in the `ClickHouseCluster` resource:

```yaml
spec:
  extraConfig:
    server:
      user_directories:
        jwt:
          aud: "<AUDIENCE>"
          iss: "<ISSUER>"
          jwks:
            url: "<JWKS_URL>"
            update_interval_ms: 300000
          permission_limit:
            user: default
```

</Tab>
<Tab title="Helm values" id="helm-values">

Put the configuration under `server.config` in the values of the Helm release:

```yaml
server:
  config:
    user_directories:
      jwt:
        aud: "<AUDIENCE>"
        iss: "<ISSUER>"
        jwks:
          url: "<JWKS_URL>"
          update_interval_ms: "300000"
        permission_limit:
          user: default
```

</Tab>
</Tabs>

</View>
