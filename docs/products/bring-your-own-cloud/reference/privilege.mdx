## AWS IAM roles {#aws-iam-roles}

### Bootstrap IAM role {#bootstrap-iam-role}

The bootstrap IAM role has the following permissions:

- **EC2 and VPC operations**: Required for setting up VPC and EKS clusters.
- **S3 operations (e.g., `s3:CreateBucket`)**: Needed to create buckets for ClickHouse BYOC storage.
- **IAM operations (e.g., `iam:CreatePolicy`)**: Needed for controllers to create additional roles (see the next section for details).
- **EKS operations**: Write operations are limited to resources with names starting with the `clickhouse-cloud` prefix.

The following table describes each policy of the bootstrap IAM role, `ClickHouseManagementRole`.

| Policy | Permissions | Scope | Purpose |
|---|---|---|---|
| `BasePolicy` (inline) | Get the identity of the caller. Read the service quotas and the AWS default service quotas. | All resources. Read only. | Health checks and quota checks before provisioning |
| `ClickHouse-IAM-Base-Policy` | Read IAM roles, policies, and instance profiles. Pass roles to AWS services. Create service-linked roles. Create, tag, and delete the OpenID Connect (OIDC) provider of the cluster. | Read: all IAM roles and policies. Pass roles: only the BYOC role names (for example `*-k8s-worker`, `*-karpenter-node`, `*-CH-S3-Role`), and only to EKS, EKS Pod Identity, and EC2. Service-linked roles: only for EKS, EKS node groups, and VPC Lattice. OIDC provider: only with the tag `clickhouse-byoc=true`. | Read IAM state. Give the BYOC roles to EKS and EC2. |
| `ClickHouse-IAM-Extended-Policy` (optional, on by default) | Create, change, and delete IAM roles, policies, and instance profiles | Only resources with the tag `clickhouse-byoc=true`. Not limited: removal of a role from an instance profile. | Create the additional roles (see the next section for details). You do not need it if you [bring your own IAM roles](/products/bring-your-own-cloud/onboarding/customization-aws#customer-managed-iam-roles). |
| `ClickHouse-S3-Policy` | Create buckets. Read and set the bucket configuration: tags, lifecycle, encryption, ownership, public access block, and metrics. List the objects in a bucket. No object read or write. No bucket deletion. | Only buckets named `*.*.aws.clickhouse.cloud-shared`, `*.*.aws.clickhouse.cloud-backup`, and `*.*.aws.clickhouse.cloud-monitoring` | Manage buckets that store ClickHouse table data, backups, and monitoring data |
| `ClickHouse-EKS-Policy` | Create, change, and delete EKS clusters, add-ons, node groups, and Pod Identity associations. Read all EKS resources. | Write: only resources whose names start with `clickhouse-cloud-`. Read: all EKS resources. | Manage the EKS cluster, its add-ons, and its node groups |
| `ClickHouse-EC2-Policy` | Read EC2, Elastic Load Balancing, and Auto Scaling. Launch instances. Manage launch templates, network interfaces, security groups, and Elastic IPs. Change volume attributes. | Security groups: only with the tag `clickhouse-byoc=true` or with the tag `aws:eks:cluster-name` = `clickhouse-cloud-*`. Elastic IPs and tags: only with the tag `clickhouse-byoc=true`. Not limited: instance launch, launch templates, network interfaces, and volume attributes. | Manage the nodes and security groups that control network access to the cluster |
| `ClickHouse-VPCWrite-Policy` (optional, on by default) | Create, change, and delete VPCs, subnets, NAT gateways, internet gateways, route tables, and VPC endpoints | Only resources with the tag `clickhouse-byoc=true` | The BYOC VPC. You do not need it if you [bring your own VPC](/products/bring-your-own-cloud/onboarding/customization-aws#customer-managed-vpc-aws). |
| `ClickHouse-VPCPrivateLink-Policy` | Create, change, and delete VPC endpoint services | Only resources with the tag `clickhouse-byoc=true` | AWS PrivateLink endpoints for your services |
| `ClickHouse-VPCLattice-Policy` | Create, change, and delete VPC Lattice resource gateways and resource configurations, and AWS RAM resource shares. Read VPC Lattice and AWS RAM. | Write: only resources with the tag `clickhouse-byoc=true`. Read: all VPC Lattice and AWS RAM resources. | Private access to the EKS API |
| `ClickHouse-CloudWatch-Policy` | Read CloudWatch Logs. Create log groups. Tag log groups and set their retention. | Create: only with the tag `clickhouse-byoc=true`. Tag and retention: only log groups `/aws/eks/clickhouse-cloud-*`. Read: all log groups. | EKS control plane logs |
| `ClickHouse-KMS-Policy` (optional, off by default) | Read key details. Create grants on keys. | Only KMS keys in the ClickHouse BYOC AWS account | EKS secret encryption |
| `ClickHouse-KMSTDE-Policy` (optional, off by default) | Create KMS keys. Read keys and key policies. Turn on key rotation. Tag keys. No encrypt, decrypt, key policy change, or key deletion. | Only keys with the tag `clickhouse-byoc=true` | Keys for Transparent Data Encryption (TDE) |

For the exact policy documents, see the [Terraform module](https://github.com/ClickHouse/terraform-byoc-onboarding/blob/main/modules/aws/main.tf) or the [CloudFormation template](https://s3.us-east-2.amazonaws.com/clickhouse-public-resources.clickhouse.cloud/cf-templates/byoc_v2.yaml).

### Additional IAM roles created by the controller {#additional-iam-roles-created-by-the-controller}

In addition to the `ClickHouseManagementRole` created via CloudFormation, the controller will create several additional roles.
Each role has the prefix `<infra>-<region>-`. `<infra>` is the name of your BYOC infrastructure, and `<region>` is the AWS region.

| Role | Permissions | Purpose |
|---|---|---|
| `data-plane-mgmt` | Read EKS. List and delete objects, and set encryption, versioning, and lifecycle, on the BYOC buckets. Read load balancers and Auto Scaling groups. The ClickHouse management service assumes it, with your external ID. | Day-to-day management of your ClickHouse services and the cluster |
| `k8s-control-plane` | AWS managed `AmazonEKSClusterPolicy`, `AmazonEKSServicePolicy`, `AmazonEKSVPCResourceController`. Only EKS can assume it. | EKS cluster role |
| `k8s-worker` | AWS managed `AmazonEKSWorkerNodePolicy`, `AmazonEKS_CNI_Policy`, `AmazonEC2ContainerRegistryReadOnly`. Assume a read-only role to pull ClickHouse container images. Only EC2 can assume it. | Node role for the system nodes |
| `karpenter-node` (role and instance profile) | Same as `k8s-worker`, plus `AmazonSSMManagedInstanceCore`. Only EC2 can assume it. | Node role for the ClickHouse server and Keeper nodes |
| `karpenter-controller` | Launch and terminate EC2 instances that have the tags of this cluster. Read EC2 in the BYOC region. Pass only the `karpenter-node` role. Read prices and the EKS AMI parameters. | Karpenter: adds and removes nodes for ClickHouse |
| `cluster-autoscaler` | Read Auto Scaling groups. Set the desired capacity and terminate instances in Auto Scaling groups. | Scales the system node groups |
| `load-balancer-controller` | The AWS Load Balancer Controller policy that AWS publishes. Changes to load balancers need the tag of this cluster. | Creates the network load balancers for your service endpoints |
| `ebs-csi-driver` | The EBS CSI driver policy that AWS publishes. Volume and snapshot deletion needs the driver tags. | Disks for ClickHouse and Keeper |
| `CH-S3-Role` | All S3 actions, only under the ClickHouse prefixes in the BYOC shared and backup buckets. Assume roles that you set up for ClickHouse S3 access. Assume a role to send usage data to ClickHouse. | Identity of the ClickHouse server pods. Reads and writes table data and backups. |
| `thanos` | List, read, write, and delete objects in the BYOC monitoring bucket | Stores metrics for monitoring |
| `state-exporter` | Assume a ClickHouse role. No other permissions. | Sends the health of the infrastructure to ClickHouse |
| `clickhouse-scraper` | Assume a ClickHouse role. No other permissions. | Sends usage data for billing to ClickHouse |
| `kube-metric-forwarder-asc` | Assume a ClickHouse role. No other permissions. | Sends Kubernetes metrics to ClickHouse for autoscaling |

For the exact policy documents, see the [Terraform module](https://github.com/ClickHouse/terraform-byoc-onboarding/blob/main/modules/aws-per-infra-iam/main.tf).

## GCP service accounts {#gcp-service-accounts}

### Bootstrap service account {#bootstrap-service-account}

The bootstrap service account is granted project-scoped custom roles with the following permissions:

- **Common**: Baseline read and identity permissions.
- **VPC**: Manage the VPC, subnets, routing, and Private Service Connect attachments that host your BYOC infrastructure.
- **Cluster**: Manages GKE clusters and in-cluster resources.
- **Storage**: Used to manage Cloud Storage buckets used for ClickHouse backups, shared state, and monitoring data.
- **IAM Role**: Manages service accounts and custom roles inside the project. This role does not grant the ability to create service account keys, bind organization policies, or touch any resources in other projects.

### Additional service accounts created by the controller {#additional-service-accounts-created-by-the-controller}

In addition to the `clickhouse-management` service account created via Terraform as part of onboarding. When you provision your first BYOC service, ClickHouse’s control plane (authenticating as `clickhouse-management`) creates additional service accounts in your project for specific in-cluster workloads. Each of these is created with a narrow, single-purpose permission set.

- **GKE node runtime identity**
  - Attached to every GKE node virtual machine in your BYOC cluster.
  - Used by kubelet, node-local agents, and the Cloud Operations collectors to emit logs and metrics, and by the image pulling subsystem to download container images.
- **Billing scraper identity**
  - Used by standalone scraper workload to collect billing telemetry.
- **Monitoring identity**
  - Target identity for the monitoring stack running in your cluster. Used to read/write long-term metric storage in a GCS bucket dedicated to this deployment.
- **ClickHouse runtime management identity**
  - Used by ClickHouse's runtime data-plane management controller which handles day-2 operations such as Private Service Connect endpoint management, bucket lifecycle adjustments, and service-account rotations.

The state exporter, which publishes service and backup status events to ClickHouse Cloud, is deliberately not in this list: on GCP its publishing identity is a ClickHouse-owned service account in a ClickHouse-owned project, not one created in yours. What is created in your project is a workload identity binding that lets the in-cluster `state-exporter` service account impersonate it. No key material is involved, and the identity that publishes to Pub/Sub holds no permissions in your project.

## Azure roles and identities {#azure-roles-and-identities}

### Onboarding service principal {#onboarding-service-principal}

Onboarding with the [Terraform module for Azure](https://github.com/ClickHouse/terraform-byoc-onboarding/tree/main/modules/azure) provisions a multi-tenant application as an Enterprise Application (service principal) in your tenant, following Azure guidance for cross-tenant authentication. The service principal is assigned a least-privilege custom role scoped to the target subscription, with permissions covering:

- **Networking**: Manage the VNet, subnets, public IPs, NAT gateways, network security groups, and DNS zones that host your BYOC infrastructure.
- **Cluster**: Manage AKS clusters and node pools.
- **Storage**: Manage the storage accounts and blob containers used for ClickHouse data, backups, and monitoring data.
- **Identity**: Manage user-assigned managed identities and their federated identity credentials inside the subscription.
- **Authorization**: Manage custom role definitions and role assignments. All permissions are scoped to the target subscription — the role cannot touch resources in other subscriptions or tenants.

### Additional managed identities created by the controller {#additional-managed-identities-created-by-the-controller}

When you provision BYOC services, ClickHouse's control plane creates user-assigned managed identities in your subscription. Each is federated to a specific Kubernetes service account (workload identity) with a narrow, single-purpose permission set:

- **Per-service identity**
  - Used by each ClickHouse service to access its own storage account for table data and backups, via a custom blob-storage role scoped to that storage account.
  - When a service is restored from a backup, it additionally receives read-only access to the source service's backup container.
- **Shared infrastructure identity**
  - Used by ClickHouse's runtime data-plane management controller for day-2 operations such as Private Link service management.
- **Monitoring identity**
  - Federated to the Thanos workload in your cluster, via a custom role scoped to monitoring storage access.
  - Writes and reads long-term metric retention in your own subscription.

As on GCP, the state exporter is deliberately absent from this list: its publishing identity is a ClickHouse-owned user-assigned managed identity in a ClickHouse-owned subscription. What is created on your side is a federated identity credential allowing the in-cluster `state-exporter` service account to obtain tokens for it, with no secrets exchanged. The identity that publishes to Service Bus holds no permissions in your subscription.

<Note>
This differs from AWS, where the publishing role is created in your own account and assumes a ClickHouse-side role to reach the queue. On GCP and Azure the publishing identity sits entirely on the ClickHouse side and your cluster only federates into it, so there is no additional in-account permission for you to audit for this flow. The egress itself is inventoried in [network boundaries](/products/bring-your-own-cloud/reference/network-security#outbound-connections).
</Note>
