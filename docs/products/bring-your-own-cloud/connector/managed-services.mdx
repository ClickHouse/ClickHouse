In managed mode the connector runs a third component, the executor, and ClickHouse Cloud operates ClickHouse services in your Kubernetes cluster through it. This page covers what the executor does, how to create a service, how to read its status, what ClickHouse does on your behalf once a service exists, and how a service is retired.

## What managed mode does {#what-managed-mode-does}

The executor is a daemon built into the same `clicklink` binary as the scraper and the troubleshooter. It holds an outbound WebSocket channel to your connector endpoint, receives lifecycle commands from ClickHouse Cloud, applies them to the one Kubernetes cluster it is configured for, and reports the outcome back over the same channel. Like the other components it makes only outbound connections: ClickHouse Cloud never connects into your cluster, and the executor's own local API binds to loopback.

Managed mode is available on Amazon EKS with S3 storage and is part of the private preview; your ClickHouse account team enables it when registering your environment. `init` refuses a kube context that does not point at an EKS cluster.

Each service needs three cloud resources you own: a data bucket, a backup bucket, and an IAM role the ClickHouse pods assume to reach them. You create these with your own credentials before the service exists, and you remove them with your own credentials after it is gone. The executor itself creates and deletes nothing in AWS, and it never deletes data.

On a VM the executor runs as the `clicklink-executor` systemd unit next to the other two; on Kubernetes it is a single-replica Deployment in the connector namespace. It serves health and metrics on port 8086 and its local API on `127.0.0.1:9999`.

## Enable managed mode {#enable-managed-mode}

Managed mode is chosen when you enroll: pass `--managed` to `clicklink clctl init`, or answer the prompt on a terminal. On a VM, `init` takes the cluster from this host's kubeconfig (`--cluster-name` when it holds more than one EKS cluster) and grants the executor's cluster-wide access inline. On Kubernetes, pass `--egress-cidrs` with the CIDRs of your connector endpoint so the chart's default-deny NetworkPolicy is staged enabled.

The install itself is unchanged: see [onboarding](/products/bring-your-own-cloud/connector/onboarding#enroll-and-install) for the full flow and the [CLI reference](/products/bring-your-own-cloud/connector/reference/cli#init) for the flags.

## Create a service {#create-a-service}

Creating a service is two commands. On a VM, run both as root on the connector host. On Kubernetes, run both from a workstation: `prepare` needs a kube context for the managed cluster, and `instances create` reads the connector's configuration and credentials from the connector namespace when this host holds no copy of them (`--connector-namespace`, default `clicklink`), announcing each read. Either way the shell needs AWS credentials able to create S3 buckets and an IAM role. The first command prepares everything on your side; the second submits the create to ClickHouse Cloud through your connector endpoint. ClickHouse Cloud renders the service definition and sends the create to the executor over its outbound channel; the executor applies it to your cluster and reports back.

<Image img="/images/cloud/reference/byoc-connector-service-lifecycle.svg" size="lg" alt="ClickHouse Connector service lifecycle in managed mode" />

<Steps>
<Step title="Prepare the service" id="prepare">

```bash
sudo clicklink clctl executor prepare --config /etc/clicklink/config.yaml
```

The command runs in order and stops at the first failure:

1. **Name.** Picks a service name, or validates the one you pass with `--instance <name>`. A generated name is recorded under `/etc/clicklink/access/executor/_prepare/` and resumed by the next run, so a retry reuses the first run's buckets and role instead of orphaning them; `--new-name` picks another. A name the executor still holds, or whose namespace already contains a ClickHouse cluster, is refused.
2. **Storage.** Creates the data and backup buckets (`<cluster>-clickhouse-data-<rand>` and `<cluster>-clickhouse-backup-<rand>` unless you pass `--data-bucket` and `--backup-bucket`) and the IAM role `CH-S3-<name>-<region>-00-Role`. With `--role-arn` it verifies a role you bring instead and writes no IAM.
3. **Grant and apply.** Renders the executor's access bundle for the service namespace (`ns-<name>`), applies its RBAC, and registers the service with the executor.
4. **Summary.** Mints the `default` user's password, writes the create body to `/etc/clicklink/access/executor/_prepare/<name>.create.json` (mode `0600`; it carries only the password's hashes), and prints the exact next command on a `Next:` line.

<Warning>
The `default` user's password is printed once, on the progress output, and never again: neither the create body nor `--output json` contains it, and ClickHouse Cloud receives only its hashes. Store it before moving on. A re-run that finds the create body keeps the hashes already written, and says so.
</Warning>

Pass `--context <name>` when your kubeconfig holds several contexts; the context must point at the EKS cluster named in `executor.cluster` in the config. `--dry-run` runs every step without creating or writing anything. The hashing step uses SHA-1, which Go refuses under `GODEBUG=fips140=only`; run `prepare` on a host without that setting.
</Step>

<Step title="Submit the create" id="create">

```bash
sudo clicklink clctl instances create \
  --from-prepare /etc/clicklink/access/executor/_prepare/<name>.create.json \
  --config /etc/clicklink/config.yaml \
  --wait
```

The command posts the prepared body to your connector endpoint with the connector's own credentials, prints the name and state ClickHouse Cloud returned (`created <name> (state provisioning)`) and a `watch:` hint. A retry with the same inputs is safe: the idempotency key defaults to one derived from your environment and the service name, so resubmitting returns the first create.

`--wait` then polls the executor's local API every 10 seconds until the service is `running`, for up to `--wait-timeout` (default `30m`). It fails fast, with the recorded error, when the executor records a failed create for the name, and when the service turns `terminating`, `terminated`, or `stale`.
</Step>

<Step title="Verify" id="verify">

```bash
clicklink clctl instances get --name <name>
```

The service is ready when its `status` is `running`. Its `default` user takes the password `prepare` printed.
</Step>
</Steps>

## Status {#status}

The executor answers status questions from its local API, which binds to `127.0.0.1:9999` and carries no authentication of its own. On a VM, run the commands on the host. On Kubernetes, open a port-forward first and point the commands at it:

```bash
kubectl -n <connector-namespace> port-forward deployment/clicklink-connector-executor 9999:9999
clicklink clctl instances list --endpoint http://127.0.0.1:9999
```

`clicklink clctl instances list` prints every service the executor knows as JSON; `clicklink clctl instances get --name <name>` prints one, with the storage it was created with. Status reflects the pods the executor sees, refreshed every 30 seconds:

- `provisioning`: pods created but not all ready
- `running`: all pods ready
- `degraded`: some pods not ready
- `terminating`: uninstall in progress
- `terminated`: no pods remain

A terminated service stays listed, with its storage, until [teardown](#delete-a-service) removes its cloud resources.

Every command ClickHouse Cloud sends to the executor is recorded locally. `clicklink clctl commands list` prints them, filtered with `--status` (`pending`, `running`, `completed`, `failed`), `--action` (for example `create_instance`), or `--cluster`; `clicklink clctl commands get <id>` prints one command with its stage and result. A failed command's `result` holds the error, which is where you read why a create did not converge or which [platform update](/products/bring-your-own-cloud/connector/platform-updates) is waiting for your approval.

## Service lifecycle {#service-lifecycle}

Once a service exists, ClickHouse Cloud operates it through the executor. The commands it sends are:

- **Scale.** A service has a fixed replica count, up to 20 server replicas by default; there is no autoscaling.
- **Stop and start.** Stopping scales the servers to zero and keeps Keeper; starting restores the replica counts. Data stays in your buckets throughout.
- **Restart.** The whole service, its Keeper, or a single pod.
- **Backups.** Backups run when ClickHouse Cloud triggers them and are written to your backup bucket; backup deletion removes them.
- **Version upgrades and configuration changes.** ClickHouse Cloud re-applies the service definition with the new version or setting; the executor applies it and waits for the replicas to become ready again.
- **Delete.** Described in [delete a service](#delete-a-service).

<Warning>
Version upgrades and configuration changes have no customer approval step. ClickHouse Cloud applies them to a managed service the same way it applies a scale or a restart: the definition is re-applied and the executor converges the cluster on it.
</Warning>

Creates, scales, and starts complete asynchronously. The executor reports the command as running as soon as the definition is applied, sends a progress report every 2 minutes, and reports the final outcome once the server replicas are ready. If they are not ready within 2 hours the command is reported as failed; should the replicas come up later, the service is moved back to running.

The `instances scale`, `instances patch`, and `instances delete` subcommands post commands straight to the executor's local API, without ClickHouse Cloud's involvement. Leave them alone unless your ClickHouse account team asks you to run one.

## Delete a service {#delete-a-service}

There is no customer delete command through your connector endpoint: ask your ClickHouse account team to delete the service. ClickHouse Cloud terminates it, the executor deletes the workload and its namespace (`terminating`, then `terminated`), and nothing in AWS is touched: the buckets, their data, and the IAM role remain until you remove them.

Once the service reports `terminated`, tear down what `prepare` created, on the same host and with the same credentials:

```bash
sudo clicklink clctl executor teardown --instance <name>
```

The command reads the executor's record of the service (where its data lives and which role it had). It deletes the IAM role that `prepare` created, removes the local access bundle and registry entry, and makes the executor forget the service, which frees the name. By default the service's data and its backups are kept: a kept bucket is re-tagged from `clicklink:deployed-name` to `clicklink:retained-from=<name>` so a re-created service with the same name never inherits it, and the summary says where the data is. To delete them, pass the data flags together with `--yes`:

```bash
sudo clicklink clctl executor teardown --instance <name> --delete-data --delete-backups --yes
```

<Warning>
`--delete-data` and `--delete-backups` empty and delete the buckets they name; there is no recovery afterwards. Confirm the bucket names in the record step before adding `--yes`.
</Warning>

Without `--yes` the run stops after the record step and names the buckets it would empty. `--dry-run` reads everything and writes nothing. A role you brought with `--role-arn`, or a bucket `prepare` did not create, is reported as kept and never touched. The run refuses while the service's namespace still holds a ClickHouse cluster, and everything is read before anything is deleted, so a refused run changes nothing.

## When the connector is offline {#when-the-connector-is-offline}

Running services do not depend on the executor: the ClickHouse operator in your cluster keeps them running, and a disconnected connector interrupts nothing that is already serving queries.

While no executor is connected, ClickHouse Cloud cannot hand it new work. A create or delete already under way is kept and retried within a horizon: 30 minutes from its last progress report for a create, 2 hours for a delete. Past the horizon the command is reported failed. Every other lifecycle command (scale, stop, start, restart, backup, backup deletion) is refused while no executor is connected, not queued. A command the executor has already accepted keeps running to completion, and a result it could not report is sent on its next connection.

The two customer commands have their own dependencies: `instances create` needs your connector endpoint reachable from the host it runs on, and `--wait`, `instances list`, `instances get`, and `commands list` need the executor's local API, so they need the executor running. A platform approval's token expires on its own clock, regardless of connectivity; see [the approval window](/products/bring-your-own-cloud/connector/platform-updates#the-approval-window).
