ClickHouse supports several types of user defined functions (UDFs):

- [Executable UDFs](#executable-user-defined-functions) start an external program or script (Python, Bash, etc.) and stream blocks of data to it over STDIN / STDOUT. Use them to integrate existing code or tooling without recompiling ClickHouse. They have higher per‑call overhead compared to in‑process options and are best for heavier logic or where a different runtime is required.
- [SQL UDFs](#sql-user-defined-functions) are defined with `CREATE FUNCTION` purely in SQL. They are inlined/expanded into the query plan (no process boundary), making them lightweight and ideal for reusing expression logic or simplifying complex calculated columns.
- [Experimental WebAssembly UDFs](#webassembly-user-defined-functions) run code compiled to WebAssembly inside a sandbox within the server process. They offer lower per‑call overhead than external executables with better isolation than native extensions, making them suitable for custom algorithms written in languages that can target WASM (e.g. C/C++/Rust).
- [Experimental driver-based executable UDFs](#driver-based-executable-user-defined-functions) let an operator-supplied "driver" turn a code snippet supplied in `CREATE FUNCTION ... ENGINE = DriverName(...) AS '...'` into an executable UDF at function-creation time (for example, by compiling it). They build on executable UDFs and require server-side driver configuration.

## Executable User Defined Functions {#executable-user-defined-functions}

<BetaBadge/>

<Note>
In ClickHouse Cloud, executable UDFs are in public beta and are created through the Cloud console UI. See [User-defined functions in Cloud](/products/cloud/features/sql-console-features/user-defined-functions) for the Cloud-specific workflow.
</Note>

ClickHouse can call any external executable program or script to process data.

The configuration of executable user defined functions can be located in one or more xml-files.
The path to the configuration is specified in the [`user_defined_executable_functions_config`](/reference/settings/server-settings/settings/user-defined#user_defined_executable_functions_config) parameter.

`shared_memory_size`, `shared_memory_max_size` and `shared_memory_pipeline` mean nothing without `use_shared_memory`, so a function that is not using the shared-memory transport must not spell them out at all: the configuration is rejected on the key being *present*, not on its value. `<shared_memory_pipeline>0</shared_memory_pipeline>` next to a disabled `use_shared_memory` is rejected exactly like a non-zero one would be - writing it down at its default value says just as clearly that its author believed the function used shared memory, and the function would silently have run over the pipes instead. `use_shared_memory` itself may of course be written out as `0`.

### Shared memory mode {#shared-memory-mode}

By default the bulk data is exchanged with the command through the `stdin`/`stdout` pipes. When `use_shared_memory` is enabled, the bulk data is instead placed into a shared-memory region that both the server and the command `mmap`, while the pipes carry only small control commands. The server serializes the input straight into the region and parses the output where the command left it, so the data is written once and never copied, against the two copies and the per-pipeful syscalls a pipe costs. It is most useful with `executable_pool`, where the same process — and the same region — is reused across invocations.

The mode is **Linux-only** - it relies on `memfd_create` with file sealing and on `/proc/self/fd`, and a function that asks for it fails to load on any other platform, or on a Linux system that does not provide them (the loader probes for them when the function is loaded).

`ClickHouse` creates one shared-memory region of `shared_memory_size` bytes per command process - two when `shared_memory_pipeline` is enabled, since the background thread serializes into the second one while the command works on the first. A region is an anonymous file created with `memfd_create`; it has no name in any filesystem. The command's process inherits its descriptor when it is started - as descriptor `3` for the first region and `4` for the second - and the request names the region by that descriptor as `/proc/self/fd/3` or `/proc/self/fd/4`, which the command opens and `mmap`s like any other path. Since the regions must exist before the process starts, the command receives every region it will ever use at once. Control values use the `ClickHouse` native binary encoding (varints and length-prefixed strings).

An executable UDF is server-side code: it is configured by the administrator in the server's configuration files and runs as the ClickHouse user, with everything that implies - including the ability to signal the server it is a child of. The protocol checks described below (region bounds, region size, row counts, exit status) are there to keep a *mistake* in a command from taking the server down or corrupting a result; they do not contain a command that is actively hostile, and they are not a substitute for reviewing what you configure as a UDF. The one thing they do not rely on is winning a race with the command. The command holds the region open for writing, and a server that touched a mapping of a file the command had shortened would take a `SIGBUS` on the pages the command removed - a signal that is fatal for the whole server and cannot be caught. No check could close that, because the command could shorten the file in the instant between the check and the access. The region is therefore *sealed*: it is created with `F_SEAL_SHRINK`, so the kernel refuses any attempt to shorten it, from any process, for as long as it exists, and with `F_SEAL_SEAL`, so the command cannot add seals of its own (against the server's growth, or its writes). That is what lets the server write and read through its mapping without a copy and without ever checking whether the file is still whole - there is nothing to check.

A region is accounted against exactly one memory tracker at a time, never two, so its bytes are counted once. While a query is using the region, its whole size is charged to that query's memory consumption and therefore counts towards `max_memory_usage`. For `type` `executable_pool` the region stays mapped between invocations, with no query to charge; for that time the charge is handed over to the server-wide memory tracker, where it counts towards `max_server_memory_usage`, and it is handed back to the next query that borrows the process.

What is charged for an idle pooled region is the length of its file, re-read whenever the region changes hands - when a query borrows the worker and when it hands the worker back. A command holds a writable descriptor and could, in principle, extend the file (only shrinking is sealed); pages it adds that way are charged from the next hand-over on, not at the moment it adds them, and a command must not do it. It has no reason to: the server sizes the region for the input, and a command whose result does not fit asks for more through the control protocol (`status` `2`, below).

If a chunk's serialized input does not fit into the current region and `shared_memory_max_size` is larger than `shared_memory_size`, the region is grown in place (the file is extended with `posix_fallocate` and re-`mmap`ped, doubling the size until the chunk fits, capped at `shared_memory_max_size`) and the added bytes are charged like the rest of the region. The region is sized for the input only; a command whose result does not fit next to it asks for a larger region through the control protocol (`status` `2`, see below) and the server enlarges it the same way before re-sending the request. Because the descriptor does not change, the command transparently observes the larger region the next time it maps the file. This makes the region size adaptive, so it does not have to be sized for the worst-case chunk up front. When the region cannot grow any further, an exception is raised.

For `type` `executable_pool`, a region that grew stays grown: it is sealed against shrinking, so it keeps the size of the largest chunk it ever held for as long as its worker lives, and that size is what is charged against `max_server_memory_usage` while the worker sits idle in the pool. `shared_memory_max_size` is therefore what every pooled process may end up holding, not what it may temporarily reach - size it with `pool_size` in mind. Conversely, `shared_memory_size` is reserved in full - pages committed - the moment a worker is started, so set it to what a block usually serializes to and let growth handle the occasional larger one: an oversized region costs memory for every worker and time for every worker start. In return, later borrows of that worker find the region already large enough and do not grow it again. A pooled process that is discarded rather than returned to the pool (a protocol failure, a dead command, a cancelled query) releases its regions entirely; `SYSTEM RELOAD FUNCTION` drops the pool and every region with it.

When `shared_memory_pipeline` is enabled, `ClickHouse` keeps **two** shared-memory regions per command process and serializes the next input block into one region on a background thread while the command is still processing the current block from the other region (a depth-1 prefetch pipeline). The control protocol is unchanged — each request already carries the path of the region it refers to, so the command transparently alternates between the two regions (`/proc/self/fd/3` and `/proc/self/fd/4`). This doubles the region memory (both regions are accounted) and adds one thread per call.

The overlap only materializes when a single invocation feeds the command more than one input block. An executable function call currently always passes its arguments as exactly **one** block — a query over many rows issues several independent calls rather than one call with several blocks — so the background thread serializes that single block and then finishes, and there is nothing left to prefetch. Until a caller that feeds multi-block input exists, enabling `shared_memory_pipeline` for an executable function only costs the second region and the thread. Leave it at `false`.

The transport exposes the following `ProfileEvents` for observability: `ExecutableUDFSharedMemoryCalls`, `ExecutableUDFSharedMemoryInputBytes`, `ExecutableUDFSharedMemoryOutputBytes`, `ExecutableUDFSharedMemoryRegionGrowths`, `ExecutableUDFSharedMemoryAllocatedBytes` and `ExecutableUDFSharedMemoryDirtyChannelDiscards` (pooled processes thrown away for leaving unread output behind - see the note on the response frame below; a command that quietly costs itself a worker per call shows up here and nowhere else). The current server-wide charge for regions held by idle pooled processes is the `CurrentMetrics` metric `ExecutableUDFSharedMemoryPooledBytes`.

For each chunk, `ClickHouse` serializes the input into the region in the configured `format` and sends a **request** to the command's `STDIN`:

| Field        | Encoding                 | Description                                                     |
|--------------|--------------------------|-----------------------------------------------------------------|
| `version`    | varint                   | Protocol version, currently `1`                                 |
| `request_id` | varint                   | Identifies this request; the command must echo it in its response |
| `path`       | length-prefixed string   | Path under which the command can open the region: `/proc/self/fd/N`, where `N` is the descriptor the command inherited |
| `offset`     | varint                   | Start offset of the serialized input (typically `0`)            |
| `size`       | varint                   | Size of the serialized input in bytes                           |

The command opens and `mmap`s the file at the given path (it may equally `mmap` the inherited descriptor directly), parses the input, computes the result, writes it into the shared memory (typically after the input data), and sends a **response** to its `STDOUT`:

| Field           | Encoding               | Description                                                                       |
|-----------------|------------------------|-----------------------------------------------------------------------------------|
| `request_id`    | varint                 | The `request_id` of the request being answered, echoed unchanged                  |
| `status`        | varint                 | `0` on success, `2` to ask for a larger region, any other value reports an error  |
| `offset`        | varint                 | Present when `status` is `0`: start offset of the serialized output               |
| `size`          | varint                 | Present when `status` is `0`: size of the serialized output in bytes              |
| `required_size` | varint                 | Present when `status` is `2`: total size in bytes the region must have            |
| `message`       | length-prefixed string | Present for any other `status`: an error message of at most 64 KiB, surfaced by the server |

Notes:

- The `version` field lets a command detect an incompatible protocol version. A command that does not recognize the version must answer with an error `status`.
- The `request_id` field makes an answer provably an answer to the request it is echoing. Without it, anything a command leaves on its `STDOUT` past its response frame is read as the status of the *next* response, and the rest of that frame shifts along with it - the real status becomes the offset, the real offset becomes the size. That is not a malformed frame but a plausible one, and with a matching row count the next query can be handed the region's own input as its result. A command that echoes a different id (or nothing) fails that query with a clear message and is not returned to the pool, so a stray byte costs a query and a worker instead of corrupting an answer.
- Only the server can resize the region, so a command whose result does not fit into it answers with `status` `2` and the total size it needs instead of failing. The server enlarges the region (up to `shared_memory_max_size`, failing the query if the requested size exceeds it) and re-sends the request. It carries a new `request_id` - it is a new request, and the command must echo the new one - but is otherwise identical, down to the offset and size of the input. Enlarging preserves the contents, so the serialized input is still in place and the command sees an identical request over a larger mapping. The requested size must be strictly larger than the current one, otherwise the query fails.
- The region can grow between requests to a pooled command, and never shrinks. A command must therefore map the file for every request, at its current size (`fstat` it, or map the `size` the request names plus room for the output), and should not keep a mapping across requests - a cached mapping stops short of a region that has since grown.
- Only the server resizes the region. The region is sealed against shrinking, so `ftruncate` to a smaller size and `O_TRUNC` fail with `EPERM` rather than harming the server; a command must not extend it either - pages it adds are only picked up by the server's accounting the next time the region changes hands.
- The server validates the returned `offset` and `size` and rejects an out-of-bounds region, so a misbehaving command cannot make the server read past the mapping.
- The response frame is everything the command may write to its `STDOUT`: the bulk output goes into the shared-memory region, so a byte written past the frame - a stray newline, a debug print - would be read as the beginning of the response to the *next* request. Diagnostics belong on `STDERR`, and should be written before the response rather than after it. `STDERR` is read, and put through `stderr_reaction`, while the server is reading the response and once more at the hand-back probe; bytes that land before that probe finishes belong to the current query, and under `throw` fail it - even if the command wrote them after its response. Bytes that land after the probe are nobody's: the next borrow finds them, logs them against the process and does not raise them, but it does not know what the command writes *during* that next request either, so a command that keeps writing after a quiet gap has its output attributed to whichever query is running then. Between borrows nothing reads the pipe under any reaction, `none` included: a command that fills it while idle sits blocked in `write` until the next borrow drains it, and that borrow pays the wait. This is a limit of a protocol without a per-request end-of-stderr marker, and the rule for the command is the same as for `STDOUT`: the response frame is the last thing it writes for a request. For `type` `executable_pool` the server checks both pipes before it returns a process to the pool and discards a process that left something in either of them, so such a command costs itself a worker rather than breaking the next query that would have borrowed it. That check is a probe at one instant, not a guarantee: a command that writes its stray byte a moment after answering, rather than together with its response, still slips past it, and the query that borrows the process next is then the one that fails. Do not treat it as a safety net - the rule is that the response frame is the last thing the command writes. `STDERR` is exempt from that check under `stderr_reaction` `none`, which discards those bytes rather than attributing them to a query - they are still read off the pipe at the probe and while a query is reading, so a command whose diagnostics outgrow the pipe buffer at those times does not block, but they reach nobody; between borrows, as said above, nothing reads it.
- Each subsequent chunk invalidates the previous contents of the region, but does not erase them: for `type` `executable_pool` the region is not cleared between invocations of the *same user*, so a command can read what that user's earlier query left past the end of its current input. When the process is borrowed by a different user than last time, the server zeroes the whole file first - including any tail beyond what it had mapped, which it maps for that (`ExecutableUDFSharedMemoryScrubbedBytes` counts it), so a command never sees another user's data through the region - over the pipes it only ever saw what it was sent, and this keeps that. The scrub costs a `memset` of the region, paid only at a user boundary.
- When the command's `STDIN` reaches EOF (which happens after the last chunk for `type` `executable`), the command should exit. For `type` `executable_pool` the process and its shared-memory region are kept alive and reused for the next invocation.

For `type` `executable`, the region is released when the command process finishes.
For `type` `executable_pool`, the region belongs to the pooled process holder and stays mapped after a single invocation finishes so it can be reused by a later invocation; it is released when the pooled holder is destroyed or the pooled process is discarded.

A region lives exactly as long as the last descriptor to it: it has no name in any filesystem, so a server that is killed without shutting down (by `SIGKILL`, or by the OOM killer) leaves nothing behind, and there is nothing to clean up or reclaim.

## Examples {#examples}

### UDF from inline script {#udf-inline}

Create `test_function_sum` manually specifying `execute_direct` to `0` using either XML or YAML configuration.

<Tabs>
  <Tab title="XML">
File `test_function.xml` (`/etc/clickhouse-server/test_function.xml` with default path settings).

```xml title="/etc/clickhouse-server/test_function.xml"
<functions>
    <function>
        <type>executable</type>
        <name>test_function_sum</name>
        <return_type>UInt64</return_type>
        <argument>
            <type>UInt64</type>
            <name>lhs</name>
        </argument>
        <argument>
            <type>UInt64</type>
            <name>rhs</name>
        </argument>
        <format>TabSeparated</format>
        <command>cd /; clickhouse-local --input-format TabSeparated --output-format TabSeparated --structure 'x UInt64, y UInt64' --query "SELECT x + y FROM table"</command>
        <execute_direct>0</execute_direct>
        <deterministic>true</deterministic>
    </function>
</functions>
```
  </Tab>
  <Tab title="YAML">

File `test_function.yaml` (`/etc/clickhouse-server/test_function.yaml` with default path settings).

```yml title="/etc/clickhouse-server/test_function.yaml"
functions:
  type: executable
  name: test_function_sum
  return_type: UInt64
  argument:
    - type: UInt64
      name: lhs
    - type: UInt64
      name: rhs
  format: TabSeparated
  command: 'cd /; clickhouse-local --input-format TabSeparated --output-format TabSeparated --structure ''x UInt64, y UInt64'' --query "SELECT x + y FROM table"'
  execute_direct: 0
  deterministic: true
```
  </Tab>
</Tabs>

<br/>

```sql title="Query"
SELECT test_function_sum(2, 2);
```

```text title="Result"
┌─test_function_sum(2, 2)─┐
│                       4 │
└─────────────────────────┘
```

### UDF from Python script {#udf-python}

In this example we create a UDF which reads a value from `STDIN` and returns it as a string.

Create `test_function` using either XML OR YAML configuration.

  <Tab title="XML">

```xml title="/etc/clickhouse-server/test_function.xml"
<functions>
    <function>
        <type>executable</type>
        <name>test_function_python</name>
        <return_type>String</return_type>
        <argument>
            <type>UInt64</type>
            <name>value</name>
        </argument>
        <format>TabSeparated</format>
        <command>test_function.py</command>

```
  </Tab>
  <Tab title="YAML">

```yml title="/etc/clickhouse-server/test_function.yaml"
functions:
  type: executable
  name: test_function_python
  return_type: String
  argument:
    - type: UInt64
      name: value
  format: TabSeparated
  command: test_function.py
```
  </Tab>
</Tabs>

<br/>

Create a script file `test_function.py` inside `user_scripts` folder (`/var/lib/clickhouse/user_scripts/test_function.py` with default path settings).

```python
#!/usr/bin/python3

import sys

if __name__ == '__main__':
    for line in sys.stdin:
        print("Value " + line, end='')
        sys.stdout.flush()
```

```sql title="Query"
SELECT test_function_python(toUInt64(2));
```

```text title="Result"
┌─test_function_python(2)─┐
│ Value 2                 │
└─────────────────────────┘
```

```xml title="/etc/clickhouse-server/test_function.xml"

    <function>
        <type>executable</type>
        <name>test_function_sum_json</name>
        <return_type>UInt64</return_type>
        <return_name>result_name</return_name>
        <argument>
            <type>UInt64</type>
            <name>argument_1</name>
        </argument>
        <argument>
            <type>UInt64</type>
```

## Error Handling {#error-handling}

Some functions might throw an exception if the data is invalid.
In this case, the query is canceled and an error text is returned to the client.
For distributed processing, when an exception occurs on one of the servers, the other servers also attempt to abort the query.

## Evaluation of Argument Expressions {#evaluation-of-argument-expressions}

In almost all programming languages, one of the arguments might not be evaluated for certain operators.
This is usually the operators `&&`, `||`, and `?:`.
In ClickHouse, arguments of functions (operators) are always evaluated.
This is because entire parts of columns are evaluated at once, instead of calculating each row separately.

## Performing Functions for Distributed Query Processing {#performing-functions-for-distributed-query-processing}

For distributed query processing, as many stages of query processing as possible are performed on remote servers, and the rest of the stages (merging intermediate results and everything after that) are performed on the requestor server.

This means that functions can be performed on different servers.
For example, in the query `SELECT f(sum(g(x))) FROM distributed_table GROUP BY h(y),`

- if a `distributed_table` has at least two shards, the functions 'g' and 'h' are performed on remote servers, and the function 'f' is performed on the requestor server.
- if a `distributed_table` has only one shard, all the 'f', 'g', and 'h' functions are performed on this shard's server.

The result of a function usually does not depend on which server it is performed on. However, sometimes this is important.
For example, functions that work with dictionaries use the dictionary that exists on the server they are running on.
Another example is the `hostName` function, which returns the name of the server it is running on in order to make `GROUP BY` by servers in a `SELECT` query.

If a function in a query is performed on the requestor server, but you need to perform it on remote servers, you can wrap it in an 'any' aggregate function or add it to a key in `GROUP BY`.

## SQL User Defined Functions {#sql-user-defined-functions}

Custom functions from lambda expressions can be created using the [CREATE FUNCTION](/reference/statements/create/function) statement. To delete these functions use the [DROP FUNCTION](/reference/statements/drop#drop-function) statement.

## Driver-based Executable User Defined Functions {#driver-based-executable-user-defined-functions}

<CloudNotSupportedBadge/>
<ExperimentalBadge/>

<Note>
This is an experimental feature that may change in backward-incompatible ways in future releases. Enable it with the [`allow_experimental_executable_udf_drivers`](/reference/settings/server-settings/settings/allow-experimental#allow_experimental_executable_udf_drivers) server setting.
</Note>

A *driver* is an operator-supplied adapter that turns a user code snippet into a runnable [executable UDF](#executable-user-defined-functions). When a function is created with `ENGINE = DriverName(...)`, ClickHouse runs the driver's `create_command`, passing it the function signature and the code body; the driver compiles or otherwise processes the body and prints an executable UDF configuration, which ClickHouse then stores and loads.

This lets administrators offer users a safe, narrow way to define functions in an arbitrary language (for example, C compiled inside a sandboxed container) without giving them access to the server's configuration files or filesystem. The set of available drivers is entirely controlled by the operator.

### Enabling drivers {#enabling-drivers}

Driver-based executable UDFs are disabled by default. To enable them:

1. Set the experimental gate in the server configuration:

   ```xml
   <clickhouse>
       <allow_experimental_executable_udf_drivers>true</allow_experimental_executable_udf_drivers>
   </clickhouse>
   ```

2. Point `user_defined_executable_function_drivers_config` at one or more driver configuration files (a glob is supported), and optionally set [`dynamic_user_defined_executable_functions_path`](/reference/settings/server-settings/settings/other#dynamic_user_defined_executable_functions_path), the directory where the generated executable UDF configurations are stored:

   ```xml
   <clickhouse>
       <user_defined_executable_function_drivers_config>user_defined_executable_function_drivers_config.d/*_driver.xml</user_defined_executable_function_drivers_config>
       <dynamic_user_defined_executable_functions_path>/var/lib/clickhouse/dynamic_user_defined_executable_functions/</dynamic_user_defined_executable_functions_path>
   </clickhouse>
   ```

The driver registry is loaded on server start and refreshed on `SYSTEM RELOAD CONFIG`, so drivers can be added, changed, or removed without restarting the server.

### Driver configuration {#driver-configuration}

A driver is described by an XML (or YAML) file with a top-level `<driver>` element. The following fields are supported:

| Field              | Description                                                                                                                                                              | Required |
|--------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------|
| `name`             | The driver name, as used in `CREATE FUNCTION ... ENGINE = <name>(...)`.                                                                                                  | Yes      |
| `create_command`   | Path to the program invoked to create a UDF from a code snippet. Relative paths are resolved against the driver configuration file.                                       | Yes      |
| `drop_command`     | Path to the program invoked when a function based on this driver is dropped.                                                                                              | No       |
| `engine_arguments` | Declares the arguments allowed inside `ENGINE = DriverName(...)`. Each child element is an argument name; a `<required>true</required>` child marks it as mandatory.       | No       |
| `env`              | Environment variables exported when invoking the driver commands.                                                                                                         | No       |

Example driver configuration:

```xml
<clickhouse>
    <driver>
        <name>DockerC</name>
        <create_command>../user_defined_executable_function_drivers/docker_c_create.sh</create_command>
        <drop_command>../user_defined_executable_function_drivers/docker_c_drop.sh</drop_command>
        <engine_arguments>
            <opt_level><required>false</required></opt_level>
        </engine_arguments>
        <env>
            <CLICKHOUSE_C_DRIVER_MEMORY>256m</CLICKHOUSE_C_DRIVER_MEMORY>
            <CLICKHOUSE_C_DRIVER_CPUS>1.0</CLICKHOUSE_C_DRIVER_CPUS>
        </env>
    </driver>
</clickhouse>
```

#### Driver invocation contract {#driver-invocation-contract}

When `CREATE FUNCTION` runs, `create_command` is invoked with the configured `env` variables set and the following arguments:

- `--name <function_name>`
- `--return <return_type>` (if a `RETURNS` clause is present)
- `--args <signature>` (if an `ARGUMENTS` clause is present), where the signature is the declared argument list, for example `x UInt8, y DateTime`
- `--<key> <value>` for every declared engine argument supplied in `ENGINE = DriverName(key = value)`

The user code body (the text after `AS`) is sent to the command's standard input. The command must print the configuration of an executable UDF to its standard output. The format is auto-detected: output that starts with `<` is treated as XML, otherwise as YAML. The defined function name in the generated configuration must match the name being created. If `create_command` exits with a non-zero status, the statement fails with an exception that includes the exit code and the driver's standard error.

`drop_command`, when present, is invoked the same way (without a code body on stdin) when the function is dropped.

### Creating a function {#creating-a-function-with-a-driver}

```sql
CREATE [OR REPLACE] FUNCTION [IF NOT EXISTS] name [ON CLUSTER cluster]
    ARGUMENTS (a UInt8, b String) RETURNS UInt64
    ENGINE = DriverName(key1 = 'value1', key2 = 42)
    AS '...code body...'
```

ClickHouse runs the driver's `create_command`, writes the generated configuration into [`dynamic_user_defined_executable_functions_path`](/reference/settings/server-settings/settings/other#dynamic_user_defined_executable_functions_path), and the existing executable UDF loader picks it up. The function can then be called like any other function.

### Dropping a function {#dropping-a-function-with-a-driver}

```sql
DROP FUNCTION [IF EXISTS] name [ON CLUSTER cluster]
```

`DROP FUNCTION` invokes the driver's `drop_command` (if present), removes the generated dynamic configuration and the per-function working directory, reloads the executable UDF loader, and removes the persisted query.

### Persistence and restart {#driver-persistence-and-restart}

The originating query is persisted as an `ATTACH FUNCTION ...` statement in the user-defined SQL objects directory, so the function survives a server restart. On start, the generated configurations in [`dynamic_user_defined_executable_functions_path`](/reference/settings/server-settings/settings/other#dynamic_user_defined_executable_functions_path) are loaded directly without re-running the driver. If a persisted `ATTACH FUNCTION` has no matching generated configuration (for example, the dynamic directory was lost), the driver is re-run to recreate it.

### Limitations {#driver-limitations}

- The feature is experimental and gated behind `allow_experimental_executable_udf_drivers`.
- Driver-based functions are not supported with replicated user-defined function storage (`ON CLUSTER` and `<user_defined_zookeeper_path>`), because only the originating query is replicated, not the generated artifacts.
- `RESTORE` of a backed-up driver-based function persists the query but does not re-run the driver; the generated configuration is materialized later by restart recovery.

### Example C drivers {#example-c-drivers}

The source tree ships proof-of-concept drivers under `programs/server/user_defined_executable_function_drivers_config.d/` that compile and run a C function body. They are examples and are **not installed by packages**:

- `DockerC` - compiles and runs the code inside sandboxed Docker containers (`--network=none --read-only --cap-drop=ALL --security-opt=no-new-privileges`, plus memory/CPU/PID limits), emitting an `executable_pool` UDF.
- `GVisorC` - a variant that runs the compiled binary under the [gVisor](https://gvisor.dev/) `runsc` runtime.
- `UnsafeC` - compiles and runs the code directly on the host without a sandbox. As the name indicates, it provides no isolation and is intended only for trusted environments and testing.

These example drivers are intended as a starting point; review and harden the sandboxing for your environment before exposing them to untrusted users.
