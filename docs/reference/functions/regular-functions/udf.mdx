ClickHouse supports several types of user defined functions (UDFs):

- [Executable UDFs](#executable-user-defined-functions) start an external program or script (Python, Bash, etc.) and stream blocks of data to it over STDIN / STDOUT. Use them to integrate existing code or tooling without recompiling ClickHouse. They have higher per‑call overhead compared to in‑process options and are best for heavier logic or where a different runtime is required.
- [SQL UDFs](#sql-user-defined-functions) are defined with `CREATE FUNCTION` purely in SQL. They are inlined/expanded into the query plan (no process boundary), making them lightweight and ideal for reusing expression logic or simplifying complex calculated columns.
- [Experimental WebAssembly UDFs](#webassembly-user-defined-functions) run code compiled to WebAssembly inside a sandbox within the server process. They offer lower per‑call overhead than external executables with better isolation than native extensions, making them suitable for custom algorithms written in languages that can target WASM (e.g. C/C++/Rust).
- [Experimental driver-based executable UDFs](#driver-based-executable-user-defined-functions) let an operator-supplied "driver" turn a code snippet supplied in `CREATE FUNCTION ... ENGINE = DriverName(...) AS '...'` into an executable UDF at function-creation time (for example, by compiling it). They build on executable UDFs and require server-side driver configuration.

## Executable User Defined Functions {#executable-user-defined-functions}

`shared_memory_size` and `shared_memory_max_size` must not appear in the configuration of a function without `use_shared_memory`, not even with the value `0`: the configuration is rejected if either key is present, because such a function would otherwise silently use the pipes. `use_shared_memory` itself may be written out as `0`.

### Command termination and exit code {#executable-udf-termination}

- When the server closes the command's pipe, the command has `command_termination_timeout` seconds to exit. After that, `SIGTERM` is sent to it, or, with `use_shared_memory`, `SIGKILL` is sent to its whole process group.
- If the query stops reading early (for example, because of `LIMIT`), the server drains up to 64 KiB of extra output, or waits up to `command_termination_timeout`, whichever comes first, and then closes `stdout`, so that a command that keeps writing exits. The resulting `SIGPIPE` (or exit code `141`, as a shell reports it) is not reported as an error even with `check_exit_code` enabled; any other non-zero exit code or signal is.
- With `check_exit_code` enabled, a command that has stopped writing is waited for until it exits, however long that takes, and a command that neither writes nor exits keeps the query waiting until the command is killed or the query is cancelled. Disable `check_exit_code` for a command that is not expected to exit on its own. With `use_shared_memory`, the wait for a command whose answer was abandoned is bounded by `command_termination_timeout`.
- For `type` `executable`, the wait for the exit status after the output completed normally is not bounded.
- For `type` `executable_pool`, a process is meant to outlive the query. Its exit code is checked when it is discarded, or when it has closed its `stdout` by the time its answer is read. Such a process is waited for up to `command_termination_timeout` (`0` gives no grace at all), and if it has not exited by then, the query fails. A pooled process that exits later is replaced before the next query uses it, but its exit code is not reported.

### Handling of stderr {#executable-udf-stderr}

`stderr` is read off the pipe while a query is reading from the command, under every `stderr_reaction`, so a chatty command does not block on a full pipe. With `none`, the output is discarded.

With `check_exit_code` disabled and `stderr_reaction` other than `none`, the server still waits up to `command_termination_timeout` for what the command writes to `stderr` while exiting. Meanwhile it reads and discards up to 64 KiB of further `stdout`. If the command writes more, its `stdout` is closed so that it exits on its next write, and a diagnostic written after that is lost.

For `type` `executable_pool`, `stderr` is read only while a query is reading from the process and once more when the query returns the process to the pool:

- `stderr` that arrives before that final check belongs to the current query: under `throw` it fails the query, even if it was written after the answer.
- `stderr` that arrives later is found by the next query that borrows the process. It is logged and not raised against that query. Under `throw` the process is discarded and replaced (with `use_shared_memory`, counted in `ExecutableUDFSharedMemoryDirtyChannelDiscards`). A process that has exited in the pool is replaced as well, but is not counted there. Output that the command writes while the next request is running is attributed to that query.
- Under `none`, leftover `stderr` is discarded and never causes a process to be replaced.
- Between borrows, nothing reads the pipe, under any `stderr_reaction`. A command that writes while idle can fill the pipe and block in `write` until the next borrow drains it, and that borrow pays for the wait.

So a pooled command should write its diagnostics before its answer, and nothing after it.

### Functions without arguments {#executable-udf-without-arguments}

A function declared without `argument` elements sends the command no data: the command reads an empty input (with `use_shared_memory`, a request with `size` `0`) and is not told how many rows the block holds. The command must still answer with exactly one row per row of the block, so such a function is only usable where the block holds a single row, for example in a query without `FROM`. Called over more rows, as in `SELECT f() FROM numbers(3)`, it fails with `wrong result, expected 3 row(s), actual 1`. Pass a column as an argument to evaluate the function over a table.

### Shared memory mode {#shared-memory-mode}

With `use_shared_memory`, the bulk data is placed in a shared-memory region that both the server and the command `mmap`, and the `stdin`/`stdout` pipes carry only small control messages. The server serializes the input directly into the region and parses the output where the command left it, avoiding the copies and per-pipeful syscalls of the pipes. The mode is most useful with `executable_pool`, where the same process and region are reused across invocations.

Requirements: Linux with `memfd_create` and file sealing, `/proc/self/fd`, and `/sys/kernel/mm` (not available in a chroot or a container without `/sys`). The loader checks them when the function is loaded; a function with `use_shared_memory` fails to load where they are missing.

#### Region {#shared-memory-region}

- Each command process gets one region, initially of `shared_memory_size` bytes. The region is an anonymous file created with `memfd_create`, with no name in any filesystem.
- The process inherits the region's descriptor as descriptor `3`, and requests name it by the path `/proc/self/fd/3`.
- For `type` `executable`, the region is released when the command finishes. For `type` `executable_pool`, it is kept across invocations and released when the process is discarded or the pool is destroyed; `SYSTEM RELOAD FUNCTION` drops the pool and all its regions.
- The region exists as long as any descriptor to it is open: in the server, in the command, or in anything the command started. A server killed without shutdown (by `SIGKILL` or the OOM killer) leaves no files behind. The command sees EOF on `stdin` when the server dies and is expected to exit; a command that keeps running holds the region's pages until it closes the descriptor.

#### Protocol {#shared-memory-protocol}

Control values use the ClickHouse native binary encoding (varints and length-prefixed strings). For each chunk, the server serializes the input into the region in the configured `format` and writes a **request** to the command's `STDIN`:

| Field        | Encoding                 | Description                                                     |
|--------------|--------------------------|-----------------------------------------------------------------|
| `version`    | varint                   | Protocol version, currently `1`                                 |
| `request_id` | varint                   | Identifies this request; the command must echo it in its response |
| `path`       | length-prefixed string   | Path under which the command can open the region: `/proc/self/fd/N`, where `N` is the descriptor the command inherited |
| `offset`     | varint                   | Start offset of the serialized input (typically `0`)            |
| `size`       | varint                   | Size of the serialized input in bytes                           |

The command opens and `mmap`s the file at the given path (or `mmap`s the inherited descriptor directly), parses the input, computes the result, writes it into the region (typically after the input), and writes a **response** to its `STDOUT`:

| Field           | Encoding               | Description                                                                       |
|-----------------|------------------------|-----------------------------------------------------------------------------------|
| `request_id`    | varint                 | The `request_id` of the request being answered, echoed unchanged                  |
| `status`        | varint                 | `0` on success, `2` to ask for a larger region, any other value reports an error  |
| `offset`        | varint                 | Present when `status` is `0`: start offset of the serialized output               |
| `size`          | varint                 | Present when `status` is `0`: size of the serialized output in bytes              |
| `required_size` | varint                 | Present when `status` is `2`: total size in bytes the region must have            |
| `message`       | length-prefixed string | Present for any other `status`: an error message of at most 64 KiB, surfaced by the server |

Rules for the command:

- A command that does not recognize `version` must answer with an error `status`.
- A response with a different `request_id` (or none) fails the query, and the process is not returned to the pool.
- A request with `size` `0` (a [function without arguments](#executable-udf-without-arguments)) must be answered like any other.
- Map the file for every request at its current size (`fstat` it, or map the request's `size` plus room for the output). Do not keep a mapping across requests: the region may have grown since.
- If the result does not fit, answer with `status` `2` and the total size needed, which must be larger than the current size. The server enlarges the region, preserving its contents, and sends the request again with a new `request_id` and the same `offset` and `size`. If the region cannot grow that far (`shared_memory_max_size`, a memory limit), the query fails.
- Compute every answer from the input the request names, as the region holds it now. Do not treat a request as the continuation of an earlier one: after an abandoned request, the next query's request may name an input with the same offset and size but different contents.
- The response frame is the only thing the command may write to `STDOUT`. A stray byte after it would be read as the start of the next response. Write diagnostics to `STDERR`, before the response (see [Handling of stderr](#executable-udf-stderr)).
- Do not resize the region. Shrinking fails with `EPERM`. Extending is possible but is charged at the next hand-over and can cost the process (see [The size cap](#shared-memory-size-cap)).
- Exit when `STDIN` reaches EOF. For `type` `executable`, this happens after the last chunk.

What the server does:

- `command_read_timeout` bounds the time from sending a request to having read the whole response frame, not each read.
- The returned `offset` and `size` are validated, so a command cannot make the server read past the mapping.
- For `type` `executable_pool`, the server checks both pipes before returning a process to the pool, and again before sending the next request. A process that left unread output on its `stdout`, or on its `stderr` under `stderr_reaction` `throw`, is discarded and replaced (counted in `ExecutableUDFSharedMemoryDirtyChannelDiscards`); under the other reactions leftover `stderr` is handled as described in [Handling of stderr](#executable-udf-stderr). These checks are not a safety net: a byte written just before the next request still fails that query through `request_id`.
- The region is not cleared between invocations by the same user with the same current roles, so a command can read what that user's earlier query left there. When the process is borrowed by a different user, or by the same user with a different set of current roles, the server zeroes the whole file first (counted in `ExecutableUDFSharedMemoryScrubbedBytes`). This is done by freeing and re-committing the pages, and is charged to the query.
- Clearing the region does not isolate users from the command: the process already received every input written there and can keep it, and a pooled process serves the queries of every user that can call the function, whichever transport it uses. What clearing prevents is a command bug, such as answering with the `offset` of a previous response or reading past its own input, silently returning one user's data in another user's result.

#### Region size {#shared-memory-region-size}

If a chunk's serialized input does not fit, and `shared_memory_max_size` is larger than the current size, the region is grown in place by doubling until the chunk fits, up to `shared_memory_max_size`. A command that needs more room for its output asks for it with `status` `2` and the size it needs, and the region is grown to exactly that size. The descriptor does not change, so the command sees the larger region the next time it maps the file. When the region cannot grow any further, an exception is raised.

The region is reserved in full: `shared_memory_size` is committed when a process starts, and every growth is committed when it happens.

For `type` `executable_pool`, a region never shrinks. It keeps the size of the largest chunk it held for as long as its process lives, and that size stays charged while the process is idle. Therefore:

- `shared_memory_max_size` is what every pooled process may end up holding permanently. Size it with `pool_size` in mind.
- Set `shared_memory_size` to the size of a typical block and let growth handle the occasional larger one. An oversized initial region costs memory for every process and time for every process start.

#### Memory accounting {#shared-memory-accounting}

- While a query uses a region, the region's whole size is charged to the query and counts towards `max_memory_usage`.
- While a pooled process is idle, its region is charged to the server-wide memory tracker, and handed back to the next query that borrows the process. The `CurrentMetrics` metric `ExecutableUDFSharedMemoryPooledBytes` shows this idle part.
- Either way, the charge counts towards `max_server_memory_usage`. A region is charged to one tracker at a time, so it is counted once.
- Region pages are shared memory, which the background memory worker's measurement (`memory_worker_correct_memory_tracker`) does not see. The charges are therefore also counted in the `CurrentMetrics` metric `MemoryTrackingUnmeasured`, which the memory worker adds to its measurement.
- The charge is the region's footprint: the larger of the file's length and the pages it has committed, including pages committed past the end of the file (`fallocate` with `FALLOC_FL_KEEP_SIZE`). The footprint is re-read whenever the region changes hands (a query borrows or returns the process) and before every growth.

#### The size cap {#shared-memory-size-cap}

The server checks the footprint against `shared_memory_max_size` before and after every growth, and at every hand-over:

- A growth that would take the footprint past the cap is refused before it commits anything, and the process is discarded.
- A growth commits only the new part of the region, so pages the command freed inside the region stay free. After a growth, the footprint is read again. If it has passed the cap anyway, because the command committed pages while the region was growing, those pages are already charged to the query's memory tracker. The query fails with an exception, and the process is discarded together with its region.
- A region whose footprint has passed the cap at a hand-over is not returned to the pool: the process is discarded together with its region.

The cap is enforced at those points, not continuously: between hand-overs, a command can commit pages into the region without the server's memory tracker seeing them, just as it can allocate memory of its own. For a trusted command, the cap bounds what a pooled process may keep; against a command that means harm it is advisory, like any limit on a process running as the server's user.

Footprints and the cap are compared in whole pages of the unit in which the kernel backs the region, and the cap is rounded up to that unit. If transparent huge pages are enabled for `shmem` regardless of file size (`/sys/kernel/mm/transparent_hugepage/shmem_enabled` is `always` or `force`, or, from Linux 6.11, a per-size `hugepages-<size>kB/shmem_enabled` is `always`), the unit is a huge page (2 MiB on x86-64), and every region holds at least one. The file's length is compared in bytes, so a command that extends the file past the cap loses its process even if the file still fits in the last page.

Pages the file holds beyond the length the server committed itself are counted as lying past the end of the file. A command that extends the file and writes into the extension is therefore charged for those pages twice, and reaches the cap sooner.

A process is discarded when the cap is exceeded, on a protocol failure, when the command dies, when its answer does not parse, or when the query stops before the response frame has arrived. A query that stops after the frame arrived but before it has read the whole answer out of the region leaves the process at a protocol boundary, so the process is kept with its region (the next query scrubs it). A shared-memory command runs in its own process group. To discard it, the server closes its `stdin` and gives it the rest of `command_termination_timeout` to exit, then sends `SIGKILL` to the whole group (even if the command already exited, so processes it left running in the group end with it) and reaps it. Only then does the server free every page of the region and drop its charge, so nothing in the group can write into the region afterwards.

Out of reach is a descendant that left the group (`setsid`, `setpgid`) while holding the inherited descriptor. The region's pages are freed under it anyway; whatever it writes there allocates new pages that are not tracked, like any other memory allocated by a process running as the server's user. Since the command's group is not the server's, signals sent to the server's process group (Ctrl-C in a terminal running `clickhouse-local`, `kill(0, ...)`) do not reach the command; the server ends it on its own shutdown.

#### Security model {#shared-memory-security}

An executable UDF is trusted server-side code: it is configured by the administrator and runs as the ClickHouse user, with everything that implies, including the ability to signal the server. The checks described above (region bounds, region size, row counts, exit status) keep a *mistake* in a command from taking the server down or corrupting a result. They do not contain a hostile command and do not replace reviewing what you configure as a UDF.

The region is sealed with `F_SEAL_SHRINK`, so no process can shorten it, and with `F_SEAL_SEAL`, so the command cannot add seals of its own. A shortened file would make the server take an uncatchable `SIGBUS` when accessing the removed pages; the seal lets the server read and write the region without copying it and without checking that it is still whole.

The seals do not prevent a command from:

- extending the file (see [The size cap](#shared-memory-size-cap));
- freeing pages inside it (`fallocate` with `FALLOC_FL_PUNCH_HOLE`, `madvise` with `MADV_REMOVE`). A freed page reads as zeros and is allocated again on the next access. The server does not re-commit such pages, so the function's next call pays for allocating them;
- writing into the region at any moment, including while the server uses it.

One hazard remains: a page the command freed has lost the server's reservation, and if the kernel refuses to allocate it again because the machine is out of memory, the server takes a `SIGBUS`. This requires both a command freeing pages inside the region and memory exhaustion at the moment the server writes there.

Otherwise, a misbehaving command can only slow down or corrupt the results of its own function, which a command running as the server's user could do in simpler ways anyway.

#### Observability {#shared-memory-observability}

`ProfileEvents`:

- `ExecutableUDFSharedMemoryCalls`, `ExecutableUDFSharedMemoryInputBytes`, `ExecutableUDFSharedMemoryOutputBytes`, `ExecutableUDFSharedMemoryRegionGrowths`, `ExecutableUDFSharedMemoryAllocatedBytes`.
- `ExecutableUDFSharedMemoryScrubbedBytes`: bytes zeroed because a pooled region passed to a different user or set of roles.
- `ExecutableUDFSharedMemoryDirtyChannelDiscards`: pooled processes discarded for leaving unread output behind. A command that costs itself a process on every call shows up here and nowhere else.

`CurrentMetrics`:

- `ExecutableUDFSharedMemoryPooledBytes`: the current charge for regions held by idle pooled processes.

## Error Handling {#error-handling}

Some functions might throw an exception if the data is invalid.
In this case, the query is canceled and an error text is returned to the client.
For distributed processing, when an exception occurs on one of the servers, the other servers also attempt to abort the query.

## Evaluation of Argument Expressions {#evaluation-of-argument-expressions}

In almost all programming languages, one of the arguments might not be evaluated for certain operators.
This is usually the operators `&&`, `||`, and `?:`.
In ClickHouse, arguments of functions (operators) are always evaluated.
This is because entire parts of columns are evaluated at once, instead of calculating each row separately.

## Performing Functions for Distributed Query Processing {#performing-functions-for-distributed-query-processing}

For distributed query processing, as many stages of query processing as possible are performed on remote servers, and the rest of the stages (merging intermediate results and everything after that) are performed on the requestor server.

This means that functions can be performed on different servers.
For example, in the query `SELECT f(sum(g(x))) FROM distributed_table GROUP BY h(y),`

- if a `distributed_table` has at least two shards, the functions 'g' and 'h' are performed on remote servers, and the function 'f' is performed on the requestor server.
- if a `distributed_table` has only one shard, all the 'f', 'g', and 'h' functions are performed on this shard's server.

The result of a function usually does not depend on which server it is performed on. However, sometimes this is important.
For example, functions that work with dictionaries use the dictionary that exists on the server they are running on.
Another example is the `hostName` function, which returns the name of the server it is running on in order to make `GROUP BY` by servers in a `SELECT` query.

If a function in a query is performed on the requestor server, but you need to perform it on remote servers, you can wrap it in an 'any' aggregate function or add it to a key in `GROUP BY`.

CREATE FUNCTION my_function

## Driver-based Executable User Defined Functions {#driver-based-executable-user-defined-functions}

<CloudNotSupportedBadge/>
<ExperimentalBadge/>

<Note>
This is an experimental feature that may change in backward-incompatible ways in future releases. Enable it with the [`allow_experimental_executable_udf_drivers`](/reference/settings/server-settings/settings/allow-experimental#allow_experimental_executable_udf_drivers) server setting.
</Note>

A *driver* is an operator-supplied adapter that turns a user code snippet into a runnable [executable UDF](#executable-user-defined-functions). When a function is created with `ENGINE = DriverName(...)`, ClickHouse runs the driver's `create_command`, passing it the function signature and the code body; the driver compiles or otherwise processes the body and prints an executable UDF configuration, which ClickHouse then stores and loads.

This lets administrators offer users a safe, narrow way to define functions in an arbitrary language (for example, C compiled inside a sandboxed container) without giving them access to the server's configuration files or filesystem. The set of available drivers is entirely controlled by the operator.

### Enabling drivers {#enabling-drivers}

Driver-based executable UDFs are disabled by default. To enable them:

1. Set the experimental gate in the server configuration:

   ```xml
   <clickhouse>
       <allow_experimental_executable_udf_drivers>true</allow_experimental_executable_udf_drivers>
   </clickhouse>
   ```

2. Point `user_defined_executable_function_drivers_config` at one or more driver configuration files (a glob is supported), and optionally set [`dynamic_user_defined_executable_functions_path`](/reference/settings/server-settings/settings/other#dynamic_user_defined_executable_functions_path), the directory where the generated executable UDF configurations are stored:

   ```xml
   <clickhouse>
       <user_defined_executable_function_drivers_config>user_defined_executable_function_drivers_config.d/*_driver.xml</user_defined_executable_function_drivers_config>
       <dynamic_user_defined_executable_functions_path>/var/lib/clickhouse/dynamic_user_defined_executable_functions/</dynamic_user_defined_executable_functions_path>
   </clickhouse>
   ```

The driver registry is loaded on server start and refreshed on `SYSTEM RELOAD CONFIG`, so drivers can be added, changed, or removed without restarting the server.

### Driver configuration {#driver-configuration}

A driver is described by an XML (or YAML) file with a top-level `<driver>` element. The following fields are supported:

| Field              | Description                                                                                                                                                              | Required |
|--------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------|
| `name`             | The driver name, as used in `CREATE FUNCTION ... ENGINE = <name>(...)`.                                                                                                  | Yes      |
| `create_command`   | Path to the program invoked to create a UDF from a code snippet. Relative paths are resolved against the driver configuration file.                                       | Yes      |
| `drop_command`     | Path to the program invoked when a function based on this driver is dropped.                                                                                              | No       |
| `engine_arguments` | Declares the arguments allowed inside `ENGINE = DriverName(...)`. Each child element is an argument name; a `<required>true</required>` child marks it as mandatory.       | No       |
| `env`              | Environment variables exported when invoking the driver commands.                                                                                                         | No       |

Example driver configuration:

```xml
<clickhouse>
    <driver>
        <name>DockerC</name>
        <create_command>../user_defined_executable_function_drivers/docker_c_create.sh</create_command>
        <drop_command>../user_defined_executable_function_drivers/docker_c_drop.sh</drop_command>
        <engine_arguments>
            <opt_level><required>false</required></opt_level>
        </engine_arguments>
        <env>
            <CLICKHOUSE_C_DRIVER_MEMORY>256m</CLICKHOUSE_C_DRIVER_MEMORY>
            <CLICKHOUSE_C_DRIVER_CPUS>1.0</CLICKHOUSE_C_DRIVER_CPUS>
        </env>
    </driver>
</clickhouse>
```

#### Driver invocation contract {#driver-invocation-contract}

When `CREATE FUNCTION` runs, `create_command` is invoked with the configured `env` variables set and the following arguments:

- `--name <function_name>`
- `--return <return_type>` (if a `RETURNS` clause is present)
- `--args <signature>` (if an `ARGUMENTS` clause is present), where the signature is the declared argument list, for example `x UInt8, y DateTime`
- `--<key> <value>` for every declared engine argument supplied in `ENGINE = DriverName(key = value)`

The user code body (the text after `AS`) is sent to the command's standard input. The command must print the configuration of an executable UDF to its standard output. The format is auto-detected: output that starts with `<` is treated as XML, otherwise as YAML. The defined function name in the generated configuration must match the name being created. If `create_command` exits with a non-zero status, the statement fails with an exception that includes the exit code and the driver's standard error.

`drop_command`, when present, is invoked the same way (without a code body on stdin) when the function is dropped.

### Creating a function {#creating-a-function-with-a-driver}

```sql
CREATE [OR REPLACE] FUNCTION [IF NOT EXISTS] name [ON CLUSTER cluster]
    ARGUMENTS (a UInt8, b String) RETURNS UInt64
    ENGINE = DriverName(key1 = 'value1', key2 = 42)
    AS '...code body...'
```

ClickHouse runs the driver's `create_command`, writes the generated configuration into [`dynamic_user_defined_executable_functions_path`](/reference/settings/server-settings/settings/other#dynamic_user_defined_executable_functions_path), and the existing executable UDF loader picks it up. The function can then be called like any other function.

### Dropping a function {#dropping-a-function-with-a-driver}

```sql
DROP FUNCTION [IF EXISTS] name [ON CLUSTER cluster]
```

`DROP FUNCTION` invokes the driver's `drop_command` (if present), removes the generated dynamic configuration and the per-function working directory, reloads the executable UDF loader, and removes the persisted query.

### Persistence and restart {#driver-persistence-and-restart}

The originating query is persisted as an `ATTACH FUNCTION ...` statement in the user-defined SQL objects directory, so the function survives a server restart. On start, the generated configurations in [`dynamic_user_defined_executable_functions_path`](/reference/settings/server-settings/settings/other#dynamic_user_defined_executable_functions_path) are loaded directly without re-running the driver. If a persisted `ATTACH FUNCTION` has no matching generated configuration (for example, the dynamic directory was lost), the driver is re-run to recreate it.

### Limitations {#driver-limitations}

- The feature is experimental and gated behind `allow_experimental_executable_udf_drivers`.
- Driver-based functions are not supported with replicated user-defined function storage (`ON CLUSTER` and `<user_defined_zookeeper_path>`), because only the originating query is replicated, not the generated artifacts.
- `RESTORE` of a backed-up driver-based function persists the query but does not re-run the driver; the generated configuration is materialized later by restart recovery.

### Example C drivers {#example-c-drivers}

The source tree ships proof-of-concept drivers under `programs/server/user_defined_executable_function_drivers_config.d/` that compile and run a C function body. They are examples and are **not installed by packages**:

- `DockerC` - compiles and runs the code inside sandboxed Docker containers (`--network=none --read-only --cap-drop=ALL --security-opt=no-new-privileges`, plus memory/CPU/PID limits), emitting an `executable_pool` UDF.
- `GVisorC` - a variant that runs the compiled binary under the [gVisor](https://gvisor.dev/) `runsc` runtime.
- `UnsafeC` - compiles and runs the code directly on the host without a sandbox. As the name indicates, it provides no isolation and is intended only for trusted environments and testing.

These example drivers are intended as a starting point; review and harden the sandboxing for your environment before exposing them to untrusted users.

### Third-party drivers {#third-party-drivers}

Drivers can also come from outside ClickHouse. These are maintained by their authors, not by ClickHouse; review them as you would the example drivers before exposing them to untrusted users:

- [`HyperlightPython`](https://github.com/hyperlight-dev/hyperlight-unikraft/tree/main/integrations/clickhouse) - runs a Python function body in a [Hyperlight](https://github.com/hyperlight-dev/hyperlight) micro-VM with its own kernel. Hyperlight is a [Cloud Native Computing Foundation](https://www.cncf.io/projects/hyperlight/) sandbox project. Each block of rows starts from a snapshot of the guest, so the code has no network, no access to the server's files, and no state between queries. Requires Linux with `/dev/kvm`.

  ```sql
  CREATE FUNCTION py_words ARGUMENTS (s String) RETURNS UInt64
  ENGINE = HyperlightPython AS 'return len(s.split())';
  ```
