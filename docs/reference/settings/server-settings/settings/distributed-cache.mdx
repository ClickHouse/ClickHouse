## distributed_cache_temporary_data_control_hello_timeout_milliseconds {#distributed_cache_temporary_data_control_hello_timeout_milliseconds}

<SettingsInfoBlock type="NonZeroUInt64" default_value="2000" changeable_without_restart="No" />A committed temporary-data control extends the lifetime of a file at most to the time of the control connection hello + this timeout + the TTL, in milliseconds. The client waits for the response for the same time after the hello. The client uses its own value, read when a committed file is created (for background renewals, at startup). A different value on the client and on the distributed cache server does not reduce the lifetime of a file below the hello + the TTL.

## distributed_cache_temporary_data_max_bytes_per_server {#distributed_cache_temporary_data_max_bytes_per_server}

<SettingsInfoBlock type="UInt64" default_value="1099511627776" changeable_without_restart="No" />Maximum total size in bytes of committed temporary files retained by one distributed cache server. Committed temporary files are pinned in the file cache and cannot be evicted until they are released or expire, so this limit bounds how much of the cache they can occupy. The default is 1 TiB. When the limit is reached, the server rejects publication of new committed temporary files. `0` means unlimited.

## distributed_cache_temporary_data_max_connections_bypassing_pool {#distributed_cache_temporary_data_max_connections_bypassing_pool}

<SettingsInfoBlock type="UInt64" default_value="5000" changeable_without_restart="Yes" />Only has an effect in ClickHouse Cloud. Maximum number of connections per distributed cache server that temporary files may open bypassing the connection pool. When the limit is reached, temporary data waits for a pooled connection for `distributed_cache_wait_connection_from_pool_milliseconds` and then fails. `0` means unlimited. The short committed temporary-data control exchanges (confirmation, renewal, release) always open a new connection and are not counted. Can be changed without a restart.

## distributed_cache_temporary_data_max_control_batch_ids {#distributed_cache_temporary_data_max_control_batch_ids}

<SettingsInfoBlock type="NonZeroUInt64" default_value="1024" changeable_without_restart="No" />Maximum committed temporary-data IDs sent by the client in one control request. Values above 65536 are limited to 65536 (the protocol limit).

## distributed_cache_temporary_data_max_files_per_server {#distributed_cache_temporary_data_max_files_per_server}

<SettingsInfoBlock type="UInt64" default_value="100000" changeable_without_restart="No" />Maximum number of committed temporary files retained by one distributed cache server. The default is high because the limit is only a backstop that bounds the memory used to track the files; the capacity is mainly limited by `distributed_cache_temporary_data_max_bytes_per_server`. When the limit is reached, the server rejects publication of new committed temporary files. `0` means unlimited.

## distributed_cache_temporary_data_pool_behaviour_on_limit {#distributed_cache_temporary_data_pool_behaviour_on_limit}

<SettingsInfoBlock type="DistributedCachePoolBehaviourOnLimit" default_value="allocate_bypassing_pool" changeable_without_restart="Yes" />Only has an effect in ClickHouse Cloud. Behaviour of the distributed cache connections for temporary data when the connection pool limit is reached. Temporary data has no object storage to fall back to, so by default it opens a connection that bypasses the pool instead of failing. It applies to the temporary files of queries and of background operations (merges, backups). The short committed temporary-data control exchanges (confirmation, renewal, release) always open a new connection and do not use this setting. With `wait` it waits for a pooled connection for `distributed_cache_wait_connection_from_pool_milliseconds` and then fails. Can be changed without a restart.

Zero means unlimited.

## distributed_cache_write_pool_size {#distributed_cache_write_pool_size}

<SettingsInfoBlock type="UInt64" default_value="100" changeable_without_restart="No" />The maximum number of distributed cache write requests that run on a background thread at the same time (across all queries). When the limit is reached, the write-through cache write is skipped (the data is still written to object storage), so it neither blocks waiting for a slot nor creates an unbounded number of threads. Writes of temporary data do not use background threads and are not affected by the limit.
