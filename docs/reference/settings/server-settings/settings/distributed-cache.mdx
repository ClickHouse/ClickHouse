These settings configure the ClickHouse server and are autogenerated from ClickHouse source.

## distributed_cache_apply_throttling_settings_from_client {#distributed_cache_apply_throttling_settings_from_client}

<SettingsInfoBlock type="Bool" default_value="1" changeable_without_restart="No" />Whether cache server should apply throttling settings received from client.

## distributed_cache_keep_up_free_connections_ratio {#distributed_cache_keep_up_free_connections_ratio}

<SettingsInfoBlock type="Float" default_value="0.1" changeable_without_restart="No" />Soft limit for number of active connection distributed cache will try to keep free. After the number of free connections goes below distributed_cache_keep_up_free_connections_ratio * max_connections, connections with oldest activity will be closed until the number goes above the limit.

## distributed_cache_max_request_processing_time_ms {#distributed_cache_max_request_processing_time_ms}

<SettingsInfoBlock type="UInt64" default_value="60000" changeable_without_restart="No" />Distributed cache server ends a request it has been processing for this many milliseconds since the request's last `StartRequest` or `ContinueRequest`, not counting time spent waiting for the client; a new read range starts a new budget. The request is ended as soon as the server can report it, and a request that never gets there has its connection closed `distributed_cache_stuck_request_scan_interval_ms` later. The value 0 means unbounded.

## distributed_cache_slow_down_min_stuck_requests {#distributed_cache_slow_down_min_stuck_requests}

<SettingsInfoBlock type="UInt64" default_value="10" changeable_without_restart="No" />Distributed cache server asks a client to slow down only once at least this many of its requests are stuck, so that a client with a couple of requests in flight is not asked over a single one. The values 0 and 1 leave the decision to `distributed_cache_slow_down_stuck_requests_ratio` alone.

## distributed_cache_slow_down_stuck_requests_ratio {#distributed_cache_slow_down_stuck_requests_ratio}

<SettingsInfoBlock type="Double" default_value="0.2" changeable_without_restart="No" />Distributed cache server asks a client to slow down once at least this share of its in-flight requests is stuck; idle connections do not count. The value 0 never asks.

## distributed_cache_slow_down_window_ms {#distributed_cache_slow_down_window_ms}

<SettingsInfoBlock type="UInt64" default_value="10000" changeable_without_restart="No" />How long a distributed cache server asks a client to stay away once too many of its requests are stuck, in milliseconds. Must be at least twice `distributed_cache_stuck_request_scan_interval_ms`, so that a window lapses only when a scan does not renew it; the value 0 is rejected.

## distributed_cache_stuck_request_no_progress_timeout_ms {#distributed_cache_stuck_request_no_progress_timeout_ms}

<SettingsInfoBlock type="UInt64" default_value="10000" changeable_without_restart="No" />Distributed cache server closes a connection whose request exchanged no data for this many milliseconds, not counting time spent waiting for the client. The value 0 disables this limit; the stuck-request scan stops only when `distributed_cache_max_request_processing_time_ms` is 0 as well.

## distributed_cache_stuck_request_scan_interval_ms {#distributed_cache_stuck_request_scan_interval_ms}

<SettingsInfoBlock type="NonZeroUInt64" default_value="5000" changeable_without_restart="No" />Interval of the distributed cache server's stuck-request scan, in milliseconds.

## distributed_cache_temporary_data_background_retry_delay_milliseconds {#distributed_cache_temporary_data_background_retry_delay_milliseconds}

<SettingsInfoBlock type="NonZeroUInt64" default_value="30000" changeable_without_restart="No" />Delay before a background committed temporary-data retry in milliseconds.

## distributed_cache_temporary_data_cleanup_period_milliseconds {#distributed_cache_temporary_data_cleanup_period_milliseconds}

<SettingsInfoBlock type="NonZeroUInt64" default_value="1000" changeable_without_restart="No" />Period between committed temporary-data expiry cleanups in milliseconds.

## distributed_cache_temporary_data_confirmation_retry_delay_milliseconds {#distributed_cache_temporary_data_confirmation_retry_delay_milliseconds}

<SettingsInfoBlock type="UInt64" default_value="500" changeable_without_restart="No" />Delay before retrying committed temporary-data publication confirmation in milliseconds.

## distributed_cache_temporary_data_control_hello_timeout_milliseconds {#distributed_cache_temporary_data_control_hello_timeout_milliseconds}

<SettingsInfoBlock type="NonZeroUInt64" default_value="2000" changeable_without_restart="No" />A committed temporary-data control extends the lifetime of a file at most to the time of the control connection hello + this timeout + the TTL, in milliseconds. The client waits for the response for the same time after the hello. The client uses its own value, read when a committed file is created (for background renewals, at startup). A different value on the client and on the distributed cache server does not reduce the lifetime of a file below the hello + the TTL.

## distributed_cache_temporary_data_max_bytes_per_server {#distributed_cache_temporary_data_max_bytes_per_server}

<SettingsInfoBlock type="UInt64" default_value="1099511627776" changeable_without_restart="No" />Maximum total size in bytes of committed temporary files retained by one distributed cache server. Committed temporary files are pinned in the file cache and cannot be evicted until they are released or expire, so this limit bounds how much of the cache they can occupy. The default is 1 TiB. When the limit is reached, the server rejects publication of new committed temporary files. `0` means unlimited.

## distributed_cache_temporary_data_max_connections_bypassing_pool {#distributed_cache_temporary_data_max_connections_bypassing_pool}

<SettingsInfoBlock type="UInt64" default_value="5000" changeable_without_restart="Yes" />Only has an effect in ClickHouse Cloud. Maximum number of connections per distributed cache server that temporary files may open bypassing the connection pool. When the limit is reached, temporary data waits for a pooled connection for `distributed_cache_wait_connection_from_pool_milliseconds` and then fails. `0` means unlimited. The short committed temporary-data control exchanges (confirmation, renewal, release) always open a new connection and are not counted. Can be changed without a restart.

## distributed_cache_temporary_data_max_control_batch_ids {#distributed_cache_temporary_data_max_control_batch_ids}

<SettingsInfoBlock type="NonZeroUInt64" default_value="1024" changeable_without_restart="No" />Maximum committed temporary-data IDs sent by the client in one control request. Values above 65536 are limited to 65536 (the protocol limit).

## distributed_cache_temporary_data_max_files_per_server {#distributed_cache_temporary_data_max_files_per_server}

<SettingsInfoBlock type="UInt64" default_value="100000" changeable_without_restart="No" />Maximum number of committed temporary files retained by one distributed cache server. The default is high because the limit is only a backstop that bounds the memory used to track the files; the capacity is mainly limited by `distributed_cache_temporary_data_max_bytes_per_server`. When the limit is reached, the server rejects publication of new committed temporary files. `0` means unlimited.

## distributed_cache_temporary_data_pool_behaviour_on_limit {#distributed_cache_temporary_data_pool_behaviour_on_limit}

<SettingsInfoBlock type="DistributedCachePoolBehaviourOnLimit" default_value="allocate_bypassing_pool" changeable_without_restart="Yes" />Only has an effect in ClickHouse Cloud. Behaviour of the distributed cache connections for temporary data when the connection pool limit is reached. Temporary data has no object storage to fall back to, so by default it opens a connection that bypasses the pool instead of failing. It applies to the temporary files of queries and of background operations (merges, backups). The short committed temporary-data control exchanges (confirmation, renewal, release) always open a new connection and do not use this setting. With `wait` it waits for a pooled connection for `distributed_cache_wait_connection_from_pool_milliseconds` and then fails. Can be changed without a restart.

## distributed_cache_temporary_data_renewal_period_seconds {#distributed_cache_temporary_data_renewal_period_seconds}

<SettingsInfoBlock type="NonZeroUInt64" default_value="900" changeable_without_restart="No" />Period between committed temporary-data ownership renewals in seconds.

## distributed_cache_temporary_data_ttl_seconds {#distributed_cache_temporary_data_ttl_seconds}

<SettingsInfoBlock type="NonZeroUInt64" default_value="3600" changeable_without_restart="No" />Lifetime of a committed temporary file in seconds.

## distributed_cache_warmer_max_bytes_in_queue {#distributed_cache_warmer_max_bytes_in_queue}

<SettingsInfoBlock type="UInt64" default_value="107374182400" changeable_without_restart="No" />Only has an effect in ClickHouse Cloud. The maximum total size of the ranges the cache warmer keeps queued for a disk without a local filesystem cache; the oldest ranges are discarded beyond it (with a local cache the warmer uses its `max_size`). Zero means unlimited.

## distributed_cache_warmer_max_file_segment_size {#distributed_cache_warmer_max_file_segment_size}

<SettingsInfoBlock type="NonZeroUInt64" default_value="33554432" changeable_without_restart="No" />Only has an effect in ClickHouse Cloud. The size of the ranges in which the cache warmer reads a fetched part into the distributed cache when the disk of the part has no local filesystem cache (with a local cache the warmer uses its `max_file_segment_size`).

## distributed_cache_warmer_max_segments_in_queue {#distributed_cache_warmer_max_segments_in_queue}

<SettingsInfoBlock type="UInt64" default_value="100000" changeable_without_restart="No" />Only has an effect in ClickHouse Cloud. The maximum number of ranges the cache warmer keeps queued for a disk without a local filesystem cache; the oldest ranges are discarded beyond it (with a local cache the warmer uses its `max_elements`). Zero means unlimited.

## distributed_cache_warmer_skip_parts_produced_in_current_availability_zone {#distributed_cache_warmer_skip_parts_produced_in_current_availability_zone}

<SettingsInfoBlock type="Bool" default_value="1" changeable_without_restart="No" />Only has an effect in ClickHouse Cloud. When the cache warmer warms the distributed cache alone (the part's disk has no local filesystem cache, or the cache is disabled for reads), skip the parts that were produced by a replica in the current availability zone: written through the distributed cache, they are already in the cache of this zone. Parts of unknown origin are always warmed.

## distributed_cache_write_pool_size {#distributed_cache_write_pool_size}

<SettingsInfoBlock type="UInt64" default_value="100" changeable_without_restart="Yes" />The maximum number of distributed cache write requests that run on a background thread at the same time (across all queries). When the limit is reached, the write-through cache write is skipped (the data is still written to object storage), so it neither blocks waiting for a slot nor creates an unbounded number of threads. Writes of temporary data do not use background threads and are not affected by the limit.
