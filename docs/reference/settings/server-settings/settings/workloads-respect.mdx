These settings configure the ClickHouse server and are autogenerated from ClickHouse source.

## workloads_respect_server_cpu_limit {#workloads_respect_server_cpu_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />
When enabled, the server-wide CPU concurrency limit is applied through the workload scheduler. A CPU resource `__server_cpu__` (for `MASTER THREAD` and `WORKER THREAD`) is created implicitly if no resource is defined for either role, and the `max_concurrent_threads` of the root workload (the workload with an empty name) is derived from `concurrent_threads_soft_limit_num` and `concurrent_threads_soft_limit_ratio_to_cores`, so every workload shares one CPU-slot budget taken from those settings. CPU scheduling then goes through the workload scheduler instead of the built-in concurrency control.

Enable `implicit_default_workload` together with this setting (or define a `default` workload). Only queries classified into a workload are limited by this budget. Without a `default` workload, a query using the default `workload` setting value, and the background merges and mutations that use the default workload, are not CPU-limited at all: the built-in concurrency control (`concurrent_threads_soft_limit_num`) no longer applies to them either. With `throw_on_unknown_workload = 1`, such queries fail instead.

Changeable at runtime. Disabled by default.

**Example**

```xml
<workloads_respect_server_cpu_limit>true</workloads_respect_server_cpu_limit>
```

## workloads_respect_server_memory_limit {#workloads_respect_server_memory_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />
When enabled, the server-wide memory limit is applied through the workload scheduler as a memory-reservation budget. A `MEMORY RESERVATION` resource `__server_memory__` is created implicitly if none is defined, and the `max_memory` of the root workload (the workload with an empty name) is derived from `max_server_memory_usage` (and its RAM ratio), so every workload shares one memory-reservation budget taken from that setting. This is a reservation-admission budget and does not replace the process-wide memory limit, which continues to apply. The budget is taken from the configured `max_server_memory_usage` when the configuration is loaded or reloaded; it does not follow runtime adjustments of the process-wide limit made by `memory_worker_dynamic_hard_limit`, so between reloads it may be larger than the limit in effect.

Enable `implicit_default_workload` together with this setting (or define a `default` workload). Only queries classified into a workload reserve from this budget: without a `default` workload, a query using the default `workload` setting value does not reserve from it, and with `throw_on_unknown_workload = 1` such a query fails instead. Background merges and mutations never reserve memory from workloads, so their memory is not part of this budget in any case.

Changeable at runtime. Disabled by default.

**Example**

```xml
<workloads_respect_server_memory_limit>true</workloads_respect_server_memory_limit>
```

- [Workload Scheduling](/concepts/features/configuration/server-config/workload-scheduling)
