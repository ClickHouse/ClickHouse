## iceberg_insert_commit_retry_initial_backoff_ms {#iceberg_insert_commit_retry_initial_backoff_ms}

<SettingsInfoBlock type="UInt64" default_value="10" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "10"},{"label": "New setting. A commit of an `INSERT` into Iceberg lost to a concurrent commit is retried after a random exponential delay instead of immediately."}]}]}/>

The upper bound of the delay before the first retry of an `INSERT` into an Iceberg table whose commit was lost to a concurrent commit.
The bound doubles with each next retry, up to `iceberg_insert_commit_retry_max_backoff_ms`, and each delay is chosen at random
between zero and the bound, so that the writers that lost the same race do not retry at the same moment and collide again.
The delay is taken before the latest metadata is looked up, so with many concurrent writers it also limits how often the metadata
directory is listed. `0` retries without a delay.

## iceberg_insert_max_bytes_in_data_file {#iceberg_insert_max_bytes_in_data_file}

<SettingsInfoBlock type="UInt64" default_value="536870912" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "536870912"},{"label": "Aligned with the documented default of the Iceberg table property `write.target-file-size-bytes` (512 MiB), see https:\/\/iceberg.apache.org\/docs\/1.5.2\/configuration\/."}]}, {"id": "row-2","items": [{"label": "25.9"},{"label": "1073741824"},{"label": "New setting."}]}]}/>

Max bytes of iceberg parquet data file on insert operation.

The default mirrors the documented default of the Iceberg table property `write.target-file-size-bytes` (512 MiB),
see https://iceberg.apache.org/docs/1.5.2/configuration/. The limit is compared against the size of the file
written so far, that is, the compressed size, so a file can exceed it by what the writer still buffers, such as
incomplete Parquet row groups and the ones being encoded. `iceberg_insert_max_rows_in_data_file` caps the file
independently of its size.

## iceberg_insert_max_data_files_in_upload {#iceberg_insert_max_data_files_in_upload}

<SettingsInfoBlock type="UInt64" default_value="8" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "8"},{"label": "New setting. An INSERT into Iceberg on S3 or Azure no longer waits for the upload of each finished data file."}]}]}/>

The maximum number of finished data files of one insert stream whose upload is not waited for while the `INSERT` writes the next
file, for object storages that upload in the background (S3, Azure). Such a file holds its upload buffers until its upload
completes, so higher values hide more upload latency at the cost of memory. `0` waits for the upload of each data file before
writing the next one.

## iceberg_insert_single_manifest_for_all_partitions {#iceberg_insert_single_manifest_for_all_partitions}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "New setting."}]}]}/>

An `INSERT` into a partitioned Iceberg table writes one manifest file for all the partitions it touches, like Spark
and PyIceberg, instead of one manifest file per partition. This holds per insert stream: every stream commits its own
snapshot with its own manifest, so an `INSERT` writes exactly one manifest only with `max_insert_threads = 1`.
`OPTIMIZE TABLE ... MANIFEST` then also merges manifests of different partitions into one.
`ALTER TABLE ... DROP PARTITION` cannot drop a partition whose manifest is shared with other partitions.
