## Description {#description}

<Info>
**Experimental**

`ColumnBinary` is experimental and disabled by default; set `allow_experimental_column_binary_format = 1`
to use it. Its layout is not yet frozen. The frame header carries a magic and a format version, and a
reader rejects a version it does not implement, so data written by a different version is refused rather
than misread. What is not promised is that a future version will still read it: an incompatible layout
change bumps the version and makes frames written today unreadable. Use `ColumnBinary` for interchange,
and do not rely on it for long-term storage until the layout is frozen.
</Info>

`ColumnBinary` is a compact columnar binary format. It is also usable as the wire format of a WebAssembly UDF declared with `ABI BUFFERED_V1 ... SETTINGS serialization_format = 'ColumnBinary'` (see [WebAssembly UDFs](/reference/functions/regular-functions/wasm_udf)). Unlike [Native](/reference/formats/Native) and [Buffers](/reference/formats/Buffers), which serialize each column independently one after another, `ColumnBinary` writes a single frame per block: a header, a fixed-size descriptor table (one descriptor per column), and then every column's data packed contiguously. All numeric fields are little-endian.

A frame has the following layout:

```txt
[Header: 16 bytes]
[ColDescriptor × num_columns: 40 bytes each]
[Column data blocks]
```

The 16-byte header contains, in order:

- `magic` (4 bytes) — the ASCII bytes `CBIN`, identifying the frame
- `version` (2 bytes) — `uint16` format version, currently `1`; a reader rejects a version it does not implement
- `reserved` (2 bytes) — written as `0` and required to be `0` on read, reserved for frame-wide flags
- `num_rows` (4 bytes) — `uint32`
- `num_cols` (4 bytes) — `uint32`

The header is 16 bytes rather than the 10 the fields strictly need, so that the descriptor table which follows
starts 8-byte aligned and can be read in place.

Each `ColDescriptor` is exactly 40 bytes and contains five `uint64` fields (all byte offsets are absolute from the start of the frame):

- `type` (8 bytes) — column type identifier (see below)
- `null_offset` (8 bytes) — absolute offset to a per-row side array, or `0` when the column has none
- `offsets_offset` (8 bytes) — absolute offset to a second per-row side array, or `0` when the column has none
- `data_offset` (8 bytes) — absolute offset to the column data block
- `data_size` (8 bytes) — size of the data block in bytes

`data_offset` and `data_size` always mean the same thing, but what the two side arrays hold depends on the
column type. A reader must dispatch on `type` before interpreting them:

| Type | `null_offset` | `offsets_offset` |
|------|---------------|------------------|
| any type with `COL_IS_NULLABLE` | `u8[num_rows]` null map (`1` = null, `0` = non-null) | as below |
| `COL_BYTES` | null map or `0` | `uint64[num_rows+1]` string offsets |
| `COL_VARIANT` | `u8[num_rows]` global discriminators, `0xFF` for a null row | `uint32[num_rows]` position of the row within its sub-column |
| `COL_LOWCARD` | `0` (unused; nullability is carried by the dictionary's reserved slot 0) | `index[num_rows]`, each `index_elem_width` bytes wide |
| `COL_COMPLEX`, fixed-width types | null map or `0` | `0` (an `Array`'s own offsets live at the start of its data block) |

Base column types:

- `0` — `COL_BYTES` — variable-length byte strings (`String`); paired with `offsets_offset` array and a data block of raw bytes (no null terminators)
- `1` — `COL_FIXED8` — 1-byte fixed-width scalars (`Int8`, `UInt8`)
- `2` — `COL_FIXED16` — 2-byte fixed-width scalars (`Int16`, `UInt16`)
- `3` — `COL_FIXED32` — 4-byte fixed-width scalars (`Int32`, `UInt32`, `Float32`)
- `4` — `COL_FIXED64` — 8-byte fixed-width scalars (`Int64`, `UInt64`, `Float64`, `DateTime64`)
- `5` — `COL_COMPLEX` — recursive format for `Array(T)`, `Tuple(T…)`, and `Map(K, V)`
- `6` — `COL_VARIANT` — discriminated union (`Variant(…)`)
- `7` — `COL_FIXEDN` — fixed-width scalars of any other width (`UUID`, `IPv6`, `Int128`/`UInt128`, `Int256`/`UInt256`, `Decimal128`/`Decimal256`, …)
- `8` — `COL_LOWCARD` — top-level `LowCardinality(T)`; dictionary sub-column plus a compact index array (nested `LowCardinality` materializes to `T` instead)

Modifier flags (OR'd onto the base type):

- `COL_IS_NULLABLE` (`0x20`) — nullable column; `null_offset` carries a `u8[num_rows]` null map
- `COL_IS_CONST` (`0x80`) — constant column; only 1 row of data is stored; the reader replicates it to the full row count

`COL_VARIANT` and `COL_LOWCARD` describe their contents with nested descriptors, so their data blocks carry a
small header. All offsets inside these headers are absolute from the start of the frame, exactly like the ones
in the descriptor table, and each header is 4-byte aligned.

A `COL_VARIANT` data block holds a `uint32` count `K` of sub-variants that are actually present, then `K`
records of a `uint8` global discriminator, 3 padding bytes and a 40-byte `ColDescriptor` for that sub-variant's
sub-column, then the sub-column data those descriptors point at. An absent sub-variant gets no record.

A `COL_LOWCARD` data block holds a `uint32` dictionary row count, a `uint8` index element width, 3 padding
bytes and a 40-byte `ColDescriptor` for the dictionary sub-column, then the dictionary data. The index array
itself is at `offsets_offset`, not in the data block.

Because the entire frame is laid out contiguously, a well-formed `data_offset`/`data_size` pair for `COL_BYTES` always starts at byte `0` of the data block and covers it exactly, with no gaps.

## Example usage {#example-usage}

Write to a file:

```sql
SELECT
    number AS num,
    number * number AS num_square
FROM numbers(10)
INTO OUTFILE 'squares.columnbinary'
FORMAT ColumnBinary;
```

Read back with explicit column types:

```sql
SELECT
    *
FROM file(
    'squares.columnbinary',
    'ColumnBinary',
    'col_1 UInt64, col_2 UInt64'
);
```
