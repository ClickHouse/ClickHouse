## Description {#description}

This table contains profiling on processors level (that you can find in [`EXPLAIN PIPELINE`](/reference/statements/explain#explain-pipeline)).

It is safe to truncate or drop this table at any time.

## Columns {#columns}

- `hostname` ([LowCardinality(String)](/reference/data-types/lowcardinality)) — Hostname of the server executing the query.
- `clickhouse_version` ([LowCardinality(String)](/reference/data-types/lowcardinality)) — Version of the ClickHouse server that produced the row.
- `system_processor` ([LowCardinality(String)](/reference/data-types/lowcardinality)) — CPU architecture of the ClickHouse server that produced the row.
- `event_date` ([Date](/reference/data-types/date)) — The date when the event happened.
- `event_time` ([DateTime](/reference/data-types/datetime)) — The date and time when the event happened.
- `event_time_microseconds` ([DateTime64(6)](/reference/data-types/datetime64)) — The date and time with microseconds precision when the event happened.
- `id` ([UInt64](/reference/data-types/int-uint)) — ID of processor, unique within the query. It is the number in `processor_uniq_id`.
- `parent_ids` ([Array(UInt64)](/reference/data-types/array)) — Parent processors IDs.
- `plan_step` ([UInt64](/reference/data-types/int-uint)) — ID of the query plan step which created this processor, unique within the query. It is one plus the number in `step_uniq_id`. The value is zero if the processor was not added from any step.
- `plan_step_name` ([String](/reference/data-types/string)) — Name of the query plan step which created this processor. The value is empty if the processor was not added from any step.
- `plan_step_description` ([String](/reference/data-types/string)) — Description of the query plan step which created this processor. The value is empty if the processor was not added from any step.
- `plan_group` ([UInt64](/reference/data-types/int-uint)) — Group of the processor if it was created by query plan step. A group is a logical partitioning of processors added from the same query plan step. Group is used only for beautifying the result of EXPLAIN PIPELINE result.
- `initial_query_id` ([String](/reference/data-types/string)) — ID of the initial query in the same query chain.
- `query_id` ([String](/reference/data-types/string)) — ID of the query.
- `name` ([LowCardinality(String)](/reference/data-types/lowcardinality)) — Name of the processor.
- `elapsed_us` ([UInt64](/reference/data-types/int-uint)) — Number of microseconds this processor was executed.
- `input_wait_elapsed_us` ([UInt64](/reference/data-types/int-uint)) — Number of microseconds this processor was waiting for data (from other processor).
- `output_wait_elapsed_us` ([UInt64](/reference/data-types/int-uint)) — Number of microseconds this processor was waiting because output port was full.
- `input_rows` ([UInt64](/reference/data-types/int-uint)) — The number of rows consumed by processor.
- `input_bytes` ([UInt64](/reference/data-types/int-uint)) — The number of bytes consumed by processor.
- `output_rows` ([UInt64](/reference/data-types/int-uint)) — The number of rows generated by processor.
- `output_bytes` ([UInt64](/reference/data-types/int-uint)) — The number of bytes generated by processor.
- `processor_uniq_id` ([String](/reference/data-types/string)) — The uniq processor id in pipeline.
- `step_uniq_id` ([String](/reference/data-types/string)) — The uniq step id in plan.
- `exception_code` ([Int32](/reference/data-types/int-uint)) — Code of the exception if the query failed, otherwise 0.
- `exception` ([String](/reference/data-types/string)) — Message of the exception if the query failed, otherwise empty.

## Example {#example}

```sql title="Query"
EXPLAIN PIPELINE
SELECT sleep(1)
┌─explain─────────────────────────┐
│ (Expression)                    │
│ ExpressionTransform             │
│   (SettingQuotaAndLimits)       │
│     (ReadFromStorage)           │
│     SourceFromSingleChunk 0 → 1 │
└─────────────────────────────────┘

SELECT sleep(1)
SETTINGS log_processors_profiles = 1
Query id: feb5ed16-1c24-4227-aa54-78c02b3b27d4
┌─sleep(1)─┐
│        0 │
└──────────┘
1 rows in set. Elapsed: 1.018 sec.

SELECT
    name,
    elapsed_us,
    input_wait_elapsed_us,
    output_wait_elapsed_us
FROM system.processors_profile_log
WHERE query_id = 'feb5ed16-1c24-4227-aa54-78c02b3b27d4'
ORDER BY name ASC
```

```text title="Response"
┌─name────────────────────┬─elapsed_us─┬─input_wait_elapsed_us─┬─output_wait_elapsed_us─┐
│ ExpressionTransform     │    1000497 │                  2823 │                    197 │
│ LazyOutputFormat        │         36 │               1002188 │                      0 │
│ LimitsCheckingTransform │         10 │               1002994 │                    106 │
│ NullSource              │          5 │               1002074 │                      0 │
│ NullSource              │          1 │               1002084 │                      0 │
│ SourceFromSingleChunk   │         45 │                  4736 │                1000819 │
└─────────────────────────┴────────────┴───────────────────────┴────────────────────────┘
```

Here you can see:

- `ExpressionTransform` was executing `sleep(1)` function, so it `work` will takes 1e6, and so `elapsed_us` > 1e6.
- `SourceFromSingleChunk` need to wait, because `ExpressionTransform` does not accept any data during execution of `sleep(1)`, so it will be in `PortFull` state for 1e6 us, and so `output_wait_elapsed_us` > 1e6.
- `LimitsCheckingTransform`/`NullSource`/`LazyOutputFormat` need to wait until `ExpressionTransform` will execute `sleep(1)` to process the result, so `input_wait_elapsed_us` > 1e6.

### Profiling a join {#profiling-a-join}

When a query reads from several tables, every table has its own read pipeline, and rows pass through many processors on their way to the result.
Summing `input_rows` or `output_rows` over all processors therefore counts the same rows several times and does not tell how much was read from each table.
The following example uses two `MergeTree` tables of different sizes on a single server.

```sql title="Query"
CREATE TABLE big (id UInt64, v UInt64) ENGINE = MergeTree ORDER BY id;
CREATE TABLE small (id UInt64, w UInt64) ENGINE = MergeTree ORDER BY id;

INSERT INTO big SELECT number, number FROM numbers(1000000);
INSERT INTO small SELECT number, number FROM numbers(1000);

EXPLAIN PIPELINE
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0;
```

`EXPLAIN PIPELINE` shows one read pipeline for each side of the join (`ReadFromMergeTree`, with `MergeTreeSelect` sources below it), connected by the join processors. `join_algorithm = 'hash'` and `enable_join_runtime_filters = 0` make this example reproducible: a join runtime filter cannot prune `big` before its source emits rows.

```sql title="Query"
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0, log_processors_profiles = 1;
-- Note the query ID printed by the client, or look it up in `system.query_log`.

SYSTEM FLUSH LOGS;

SELECT
    id,
    parent_ids,
    plan_step,
    name,
    plan_step_name,
    plan_step_description,
    input_rows,
    output_rows,
    elapsed_us
FROM system.processors_profile_log
WHERE query_id = '<query_id>'
ORDER BY plan_step, id;
```

To interpret the result:

- Look at the source processors, whose `name` is `MergeTreeSelect(...)` (or `MergeTreeSource`) and whose `plan_step_name` is `ReadFromMergeTree`. Their `output_rows` is the number of rows each source produced. Sum it per read step (`plan_step`), not over the whole query. The value is the number of rows that the read step passed on to the rest of the pipeline.
- Each side of the join has its own `ReadFromMergeTree` step with a different `plan_step`. In the rows from this execution, `parent_ids` lists the IDs of downstream processors. Starting from a source, recursively match every `parent_ids` value to an `id` in the same `query_id` to follow the branch towards the join. This identifies, for example, the branch that feeds `FillingRightJoinSide`.
- Processors above the sources (for example `ExpressionTransform`, `FillingRightJoinSide`, `ConcatProcessor`, or the join transform itself) consume and produce rows derived from the sources. Do not add their counters to the source counters, because that counts the same rows again.
- The step information is not always enough to identify a source. `EXPLAIN PIPELINE` is a separate plan: it helps compare processor names and branch shapes, but its plain-text output has neither the logged `id` values nor `parent_ids`. If both tables have similar step descriptions, use the graph from the executed query and the known row counts. In this example, the read sources for `big` sum to 1,000,000 rows and those for `small` sum to 1,000 rows.
- The row and byte counters of processors describe the data passing through the pipeline, not physical storage reads. They do not include granules or marks that were read and then filtered out, they are affected by the primary key and other index filtering, `PREWHERE`, and column pruning, and they do not reflect compressed bytes read from disk. `SelectedRows`, `SelectedBytes`, and `SelectedMarks` in `system.query_log` are logical selection statistics: they can be nonzero when all data comes from cache. To investigate file reads, use `ReadBufferFromFileDescriptorReadBytes`, which includes reads served by the OS page cache. To investigate local disk or block-device reads that exclude the OS page cache, use `OSReadBytes`.
