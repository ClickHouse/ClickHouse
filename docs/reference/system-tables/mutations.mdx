## Description {#description}

The table contains information about [mutations](/reference/statements/alter/index#mutations) of [MergeTree](/reference/engines/table-engines/mergetree-family/mergetree) tables and their progress. Each mutation command is represented by a single row.

## Columns: {#columns}

{/*AUTOGENERATED_START*/}
- `database` ([String](/reference/data-types/string)) — The name of the database to which the mutation was applied.
- `table` ([String](/reference/data-types/string)) — The name of the table to which the mutation was applied.
- `mutation_id` ([String](/reference/data-types/string)) — The ID of the mutation. For replicated tables these IDs correspond to znode names in the `<table_path_in_clickhouse_keeper>/mutations/` directory in ClickHouse Keeper. For non-replicated tables the IDs correspond to file names in the data directory of the table.
- `command` ([String](/reference/data-types/string)) — The mutation command string (the part of the query after ALTER TABLE [db.]table).
- `create_time` ([DateTime](/reference/data-types/datetime)) — Date and time when the mutation command was submitted for execution.
- `finish_time` ([DateTime](/reference/data-types/datetime)) — Date and time when the mutation was completed. Zero if the mutation is not completed yet or if its completion time is unknown. For non-replicated tables the value is tracked in memory and is reset when the table is reloaded (e.g. on server restart). For replicated tables the value is per-replica; after a restart, the completion time of the most recently completed mutation is restored from Keeper, while older completed mutations report zero.
- `block_numbers.partition_id` ([Array(String)](/reference/data-types/array)) — For mutations of replicated tables, the array contains the partitions' IDs (one record for each partition). For mutations of non-replicated tables the array is empty.
- `block_numbers.number` ([Array(Int64)](/reference/data-types/array)) — For mutations of replicated tables, the array contains one record for each partition, with the block number that was acquired by the mutation. Only parts that contain blocks with numbers less than this number will be mutated in the partition.In non-replicated tables, block numbers in all partitions form a single sequence. This means that for mutations of non-replicated tables, the column will contain one record with a single block number acquired by the mutation.
- `parts_in_progress_names` ([Array(String)](/reference/data-types/array)) — An array of names of data parts that are currently being mutated.
- `parts_to_do_names` ([Array(String)](/reference/data-types/array)) — An array of names of data parts that need to be mutated for the mutation to complete.
- `parts_to_do` ([Int64](/reference/data-types/int-uint)) — The number of data parts that need to be mutated for the mutation to complete. Note: even if `parts_to_do` = 0, a mutation of a replicated table may not be completed yet due to a long-running INSERT that is creating a new data part that will need to be mutated.
- `parts_postpone_reasons` ([Map(String, String)](/reference/data-types/map)) — A map of part names to reasons why they are postponed.
- `is_done` ([UInt8](/reference/data-types/int-uint)) — The flag whether the mutation is done or not. Possible values: 1 if the mutation is completed, 0 if the mutation is still in process.
- `is_killed` ([UInt8](/reference/data-types/int-uint)) — Indicates whether a mutation has been killed. Only available in ClickHouse Cloud.Note: is_killed=1 does not necessarily mean the mutation is completely finalized.It is possible for a mutation to remain in a state where is_killed=1 and is_done=0 for an extended period.This can occur if another long-running mutation is blocking the killed mutation. This is a normal situation.
- `latest_failed_part` ([String](/reference/data-types/string)) — The name of the most recent part that could not be mutated.
- `latest_fail_time` ([DateTime](/reference/data-types/datetime)) — The date and time of the most recent part mutation failure.
- `latest_fail_reason` ([String](/reference/data-types/string)) — The exception message that caused the most recent part mutation failure.
- `latest_fail_error_code_name` ([String](/reference/data-types/string)) — The error code of the exception that caused the most recent part mutation failure.
{/*AUTOGENERATED_END*/}

<Note>
- If a part name is not in `parts_postpone_reasons` and has not yet been mutated, it means the part is yet not scheduled for mutation.
- The part name `all_parts` represents all parts that have not yet been mutated.
</Note>

- `is_killed` ([UInt8](/reference/data-types/int-uint)) — Indicates whether a mutation has been killed. **Only available in ClickHouse Cloud.**

<Note>
`is_killed=1` does not necessarily mean the mutation is completely finalized. It is possible for a mutation to remain in a state where `is_killed=1` and `is_done=0` for an extended period. This can happen if another long-running mutation is blocking the killed mutation. This is a normal situation.
</Note>

- `is_done` ([UInt8](/reference/data-types/int-uint)) — The flag whether the mutation is done or not. Possible values:
  - `1` if the mutation is completed,
  - `0` if the mutation is still in process.

<Note>
Even if `parts_to_do = 0` it is possible that a mutation of a replicated table is not completed yet because of a long-running `INSERT` query, that will create a new data part needed to be mutated.
</Note>

If there were problems with mutating some data parts, the following columns contain additional information:

- `latest_failed_part` ([String](/reference/data-types/string)) — The name of the most recent part that could not be mutated.
- `latest_fail_time` ([DateTime](/reference/data-types/datetime)) — The date and time of the most recent part mutation failure.
- `latest_fail_reason` ([String](/reference/data-types/string)) — The exception message that caused the most recent part mutation failure.

## Monitoring Mutations {#monitoring-mutations}

To track the progress on the `system.mutations` table, use the following query:

```sql
SELECT * FROM clusterAllReplicas('cluster_name', 'system', 'mutations')
WHERE is_done = 0 AND table = 'tmp';

-- or

SELECT * FROM clusterAllReplicas('cluster_name', 'system.mutations')
WHERE is_done = 0 AND table = 'tmp';
```

Note: this requires read permissions on the `system.*` tables.

<Tip>
**Cloud usage**

In ClickHouse Cloud the `system.mutations` table on each node has all the mutations in the cluster, and there is no need for `clusterAllReplicas`.
</Tip>

### Estimating mutation progress {#estimating-mutation-progress}

`parts_to_do` counts data parts, and parts can be wildly unequal in size; a regular merge can also retire many pending parts in one step without doing any mutation work. A percentage computed from part counts (for example `1 - parts_to_do / <part count at submission>`) is therefore not a reliable progress number: it can sit almost frozen while most of the bytes are still unprocessed, and jump forward when parts are merged. An honest estimate weights the remaining parts by their size on disk and adds the live fraction of the part that is being rewritten right now, which [`system.merges`](/reference/system-tables/merges) exposes for rows with `is_mutation = 1`. It also measures that remainder against the mutation's own scope — the parts it currently still has to rewrite, plus the ones it has already rewritten — rather than against every active part, so that a part inserted afterwards does not on its own make a mutation that has done nothing look nearly finished.

For the built-in `progress` column the denominator is a snapshot: the server remembers the byte weight the mutation's remaining parts had when it was submitted, so a finished part keeps its pre-mutation weight whatever size the rewrite left behind — a `DELETE WHERE 1` that has rewritten one of two equal parts reads about `0.5`. The weight is kept in memory only: after a server restart, or on a replica that first sizes the mutation after some parts were already rewritten, it is re-measured from what remains and `progress` restarts as a lower bound for the leftover portion.

Scope follows block numbers: a part is in scope when its `min_block_number` precedes the mutation's block number. If a regular merge combines a part that predates the mutation with one inserted after it was submitted, the merged part keeps the earlier `min_block_number` and the mutation then has to rewrite that whole part. The remembered denominator grows along with such discovered work, so bytes written after the mutation was submitted can reach `progress`.

On a non-replicated `MergeTree` the built-in column stays `NULL` while an operation that took a lower block number has not published its parts yet — an `ATTACH`, `REPLACE` or `MOVE PARTITION` in flight, which holds its block number for the whole operation. Those parts fall inside the scope of every mutation submitted after them, so until they appear the remaining byte weight is a lower bound, and a mutation whose visible parts are all rewritten would otherwise report `1` and then go unfinished again.

Rows of [`system.merges`](/reference/system-tables/merges) with `is_mutation = 1` also carry a genuine live `progress` for the single part currently being mutated; they are joinable to `parts_in_progress_names` / `parts_to_do_names` via `source_part_names`.
