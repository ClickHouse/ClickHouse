## Description {#description}

Contains the query plan that was executed for a query, annotated with per-step runtime statistics, captured while the query ran. Unlike [`EXPLAIN ANALYZE`](/reference/statements/explain#explain-analyze), which executes the query a second time, this table lets you inspect an execution that has already happened — including one that failed partway through.

Capture is disabled by default. Set [`log_query_plans`](/operations/settings/settings) to `1` to enable it, per query, per session or per user.

One row is written per query execution. The following are captured:

- `SELECT` queries executed with the analyzer (`enable_analyzer = 1`, the default). Queries running with `enable_analyzer = 0` are not captured.
- Queries that failed during execution, with the plan they were running, under `status = 'ExceptionWhileProcessing'`. These carry the plan but no runtime statistics, because statistics are collected when the pipeline is finalized, which a failing query never reaches.

The following are not captured: `INSERT`, `EXPLAIN` and other statement kinds, queries answered from the [query result cache](/operations/query-cache) (no plan is built for them), secondary queries of a distributed query on remote shards, and internal queries. A query that fails before a plan exists — a parse error, or an unknown table — leaves no row at all.

`ascii_plan` holds the plan rendered in the same form as [`EXPLAIN ANALYZE`](/reference/statements/explain#explain-analyze): the plan tree, the expressions behind each step, and per-step rows, bytes, time and parallelism.

<Note>
Enabling `log_query_plans` makes the captured query collect per-processor timings, which is the same instrumentation [`log_processors_profiles`](/operations/settings/settings#log_processors_profiles) uses. Queries that are not captured are unaffected.
</Note>

It is safe to truncate or drop this table at any time.

## Example {#example}

```sql title="Query"
SET log_query_plans = 1;

SELECT number FROM numbers(1000000) WHERE number % 7 = 0 ORDER BY number DESC LIMIT 5 FORMAT Null;

SYSTEM FLUSH LOGS query_plan_log;

SELECT ascii_plan
FROM system.query_plan_log
ORDER BY event_time_microseconds DESC
LIMIT 1
FORMAT TSVRaw;
```

```response title="Response"

│  I/O: rows 5 → 5 · 40 B → 40 B
│    time 1.00 us (0.0%) · parallelism 0.81/1
└──Limit (preliminary LIMIT)
   │  Limit 5
   │  Offset 0
   │  I/O: rows 5 → 5 · 40 B → 40 B
   └──Sorting (Sorting for ORDER BY)
      │  Sort description: number DESC
      │  Limit 5
      │  I/O: rows 142.86 thousand → 5 (0.00%) · 1.14 MB → 40 B
      │    Stage (sorting): time 4.04 ms (47.0%) · parallelism 1.00/1
      └──Expression ((Before ORDER BY + Projection))
         │  I/O: rows 142.86 thousand → 142.86 thousand · 1.14 MB → 1.14 MB
         │    time 11.73 us (0.1%) · parallelism 0.91/1
         └──Filter ((WHERE + Change column names to column identifiers))
            │  Filter column: number MOD 7 = 0
            │  I/O: rows 1.00 million → 142.86 thousand (14.29%) · 8.00 MB → 1.14 MB
            │    time 3.53 ms (41.1%) · parallelism 1.00/1
            └──ReadFromSystemNumbers
                  Output: number
                  I/O: rows 0 → 1.00 million · 0 B → 8.00 MB
                    time 336.59 us (3.9%) · parallelism 1.00/1
```

Percentages are relative to the time the pipeline existed, so they do not include parsing and planning and will not sum to 100%.

Plans of queries of the same shape can be compared over time, across hosts or across ClickHouse versions by grouping on `normalized_query_hash`, which holds the same value as in [`system.query_log`](/operations/system-tables/query_log):

```sql title="Query"
SELECT
    normalized_query_hash,
    revision,
    count(),
    quantile(0.95)(query_duration_ms) AS p95_duration_ms
FROM system.query_plan_log
WHERE event_date >= today() - 7
GROUP BY normalized_query_hash, revision
ORDER BY p95_duration_ms DESC
LIMIT 10;
```
