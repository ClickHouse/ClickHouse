El agente de chat de Assistant se puede personalizar para que comprenda su lógica de negocio, sus estructuras de datos y el conocimiento propio de su dominio mediante **AGENTS.md**, una consulta guardada especial que actúa como capa semántica sobre la instrucción del sistema del agente.

Al crear un archivo AGENTS.md, puede proporcionar instrucciones personalizadas que se insertan al inicio de cada conversación para orientar la generación de consultas SQL y el análisis de datos de acuerdo con los requisitos, cálculos y convenciones particulares de su organización.

## Cómo funciona {#how-it-works}

Cuando guarda una consulta con el nombre «AGENTS.md» (sensible a mayúsculas y minúsculas) en la Consola de la nube:

1. El agente de chat de Assistant carga automáticamente este archivo al enviarse un mensaje
2. El contenido se incluye dentro de una etiqueta de contenido estructurado y se inyecta en la instrucción del sistema del agente
3. Las instrucciones se aplican a todas las conversaciones de chat de Assistant en ese servicio

## Creación de AGENTS.md {#creating-agents-md}

<Steps>
  <Step title="Crear la consulta guardada" id="create-query">
    1. En la Consola de la nube, cree una nueva consulta
    2. Asígnele exactamente este nombre: **&quot;AGENTS.md&quot;** (sensible a mayúsculas y minúsculas)
    3. Escriba sus instrucciones personalizadas en el editor de texto de la consulta (no se trata de SQL real)
    4. Guarde la consulta
  </Step>

  <Step title="Agregar sus instrucciones" id="add-instructions">
    Estructure sus instrucciones con un lenguaje claro y práctico. Incluya:

    * Reglas de negocio y cálculos
    * Pautas sobre la estructura de datos
    * Terminología específica del dominio
    * Patrones de consulta habituales
    * Reglas de optimización del rendimiento
  </Step>
</Steps>

## Buenas prácticas {#best-practices}

### Trate el contexto como un recurso finito {#finite-resource}

El contexto es valioso: cada token consume parte del «presupuesto de atención» del agente. Al igual que los humanos, cuya memoria de trabajo es limitada, los modelos de lenguaje sufren una degradación del rendimiento a medida que crece el contexto. Por ello, se trata de encontrar el **conjunto de tokens de alta señal más pequeño posible** que maximice la probabilidad de obtener el resultado deseado.

### Encuentre el nivel de abstracción adecuado {#right-altitude}

Busque un equilibrio entre dos extremos:

* **Demasiado específico**: codificar de forma rígida una lógica if-else frágil, lo que añade fragilidad y complica el mantenimiento
* **Demasiado vago**: orientaciones de alto nivel que no aportan señales concretas o que dan por sentado, erróneamente, un contexto compartido

El nivel óptimo es lo bastante específico como para guiar el comportamiento de forma eficaz, pero lo suficientemente flexible como para que el modelo aplique heurísticas sólidas. Empiece con un prompt mínimo en el mejor modelo disponible y, después, añada instrucciones claras en función de los modos de fallo observados.

### Organiza el contenido en secciones estructuradas {#structured-sections}

Usa etiquetas XML o encabezados de Markdown para crear secciones bien diferenciadas y fáciles de leer de un vistazo:

```xml
<background_information>
Context about your data and domain
</background_information>

<calculation_rules>
Specific formulas and business logic
</calculation_rules>

<tool_guidance>
How to use specific ClickHouse features
</tool_guidance>
```

### Proporcione ejemplos diversos y canónicos {#canonical-examples}

Los ejemplos son esas «imágenes que valen más que mil palabras». En lugar de saturar su prompt con todos los casos extremos posibles, seleccione un conjunto acotado de ejemplos diversos que reflejen con eficacia el comportamiento esperado.

### Mínimo pero completo {#minimal-complete}

* Incluya solo las instrucciones que se necesitan con frecuencia
* Sea conciso: un contexto más extenso degrada el rendimiento debido a la «degradación del contexto» (*context rot*)
* Elimine las reglas obsoletas o que apenas se usan
* Asegúrese de que haya información suficiente para orientar el comportamiento deseado

<Tip>
  Mínimo no significa necesariamente breve. Necesita el detalle suficiente para garantizar que el agente se ajuste al comportamiento esperado; basta con evitar la verbosidad innecesaria.
</Tip>

## Ejemplo: Métricas calculadas a partir de datos sin procesar {#example-calculated-metrics}

Oriente al agente cuando las métricas requieran cálculos específicos en lugar de un acceso directo a las columnas:

```xml
<metric_calculations>
IMPORTANT: "active_sessions" is NOT a column. It must be calculated.

To calculate active sessions:
COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions

This counts unique combinations of session and user identifiers.

When the user asks for "active sessions" or "session count", always use this formula:
SELECT
    date,
    COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions
FROM events
GROUP BY date;

</metric_calculations>
```

## Ejemplo: reglas de lógica de negocio {#example-business-logic}

Defina cálculos y categorizaciones específicos del dominio:

```xml
<business_rules>
Revenue Calculation:
- Exclude refunded transactions: WHERE transaction_status != 'refunded'
- Apply regional tax rates using CASE expressions
- Use MRR for subscriptions:
  SUM(CASE
    WHEN billing_cycle = 'monthly' THEN amount
    WHEN billing_cycle = 'yearly' THEN amount / 12
    ELSE 0
  END) AS mrr

Traffic Source Classification:
Use CASE expression to categorize:
CASE
  WHEN traffic_source IN ('google', 'bing', 'organic') THEN 'Organic Search'
  WHEN traffic_source IN ('facebook', 'instagram', 'social') THEN 'Social Media'
  WHEN traffic_source = 'direct' THEN 'Direct'
  ELSE 'Other'
END AS source_category

Customer Segmentation:
- Enterprise: annual_contract_value >= 100000
- Mid-Market: annual_contract_value >= 10000 AND annual_contract_value < 100000
- SMB: annual_contract_value < 10000

Always include these categorizations when generating traffic or revenue reports.
</business_rules>
```

## Ejemplo: peculiaridades de la estructura de datos {#example-data-quirks}

Documente los formatos de datos poco convencionales o las decisiones de esquema heredadas:

```xml
<data_structure_notes>
The user_status column uses numeric codes, not strings:
- 1 = 'active'
- 2 = 'inactive'
- 3 = 'suspended'
- 99 = 'deleted'

When filtering or displaying user status, always use:
CASE user_status
  WHEN 1 THEN 'active'
  WHEN 2 THEN 'inactive'
  WHEN 3 THEN 'suspended'
  WHEN 99 THEN 'deleted'
END AS status_label

The product_metadata column contains JSON strings that must be parsed:
SELECT
    product_id,
    JSONExtractString(product_metadata, 'category') AS category,
    JSONExtractInt(product_metadata, 'inventory_count') AS inventory
FROM products;
</data_structure_notes>
```

## Ejemplo: terminología del dominio {#example-terminology}

Asocie los términos de negocio con su implementación técnica:

```xml
<terminology>
When users refer to "conversions", they mean:
- For e-commerce: transactions WHERE transaction_type = 'purchase'
- For SaaS: subscriptions WHERE subscription_status = 'active' AND first_payment_date IS NOT NULL

"Churn" is calculated as:
COUNT(DISTINCT user_id) WHERE last_active_date < today() - INTERVAL 90 DAY
AND previous_subscription_status = 'active'

"DAU" (Daily Active Users) means:
COUNT(DISTINCT user_id) WHERE activity_date = today()

"Qualified leads" must meet ALL criteria:
- lead_score >= 70
- company_size >= 50
- budget_confirmed = true
- contact_role IN ('Director', 'VP', 'C-Level')
</terminology>
```
