  En la consola y la documentación de ClickHouse Cloud, &quot;tabla&quot; y &quot;colección&quot; se usan indistintamente para MongoDB.

Puede usar ClickPipes para ingerir datos desde su base de datos de MongoDB a ClickHouse Cloud. La base de datos de MongoDB de origen puede alojarse en instalaciones propias o en la nube mediante servicios como MongoDB Atlas.

Los ClickPipes de MongoDB pueden implementarse y gestionarse manualmente mediante la UI de ClickPipes, así como mediante programación con [OpenAPI](/es/integrations/clickpipes/programmatic-access/openapi) y [Terraform](/es/integrations/clickpipes/programmatic-access/terraform).

## Requisitos previos {#prerequisites}

Antes de empezar, debes asegurarte de que tu base de datos MongoDB esté correctamente configurada para la replicación. Los pasos de configuración dependen de cómo hayas desplegado MongoDB, así que sigue la guía correspondiente a continuación:

1. [MongoDB Atlas](/es/integrations/clickpipes/mongodb/source/atlas)

2. [Generic MongoDB](/es/integrations/clickpipes/mongodb/source/generic)

3. [Amazon DocumentDB](/es/integrations/clickpipes/mongodb/source/documentdb)

Una vez configurada tu base de datos MongoDB de origen, puedes continuar con la creación de tu ClickPipe.

#### Configurar ajustes avanzados {#advanced-settings}

Puede configurar los ajustes avanzados si es necesario. A continuación, se ofrece una breve descripción de cada ajuste:

* **Intervalo de sincronización**: Es el intervalo con el que ClickPipes consultará la base de datos de origen para detectar cambios. Esto influye en el servicio de ClickHouse de destino; para los usuarios con restricciones de costos, recomendamos mantenerlo en un valor más alto (por encima de `3600`).
* **Tamaño del lote de extracción**: El número de filas que se recuperarán en un solo lote. Este ajuste es orientativo y puede que no se respete en todos los casos.
* **Número de tablas de la instantánea en paralelo**: Es el número de tablas que se recuperarán en paralelo durante la instantánea inicial. Resulta útil cuando tiene un gran número de tablas y desea controlar cuántas se recuperan en paralelo.

### Configure las tablas {#configure-the-tables}

5. Aquí puede seleccionar la base de datos de destino para su ClickPipe. Puede seleccionar una base de datos existente o crear una nueva.

   <div className="ch-image-lg">
     <Frame>
       ![Seleccione la base de datos de destino](/images/integrations/data-ingestion/clickpipes/mongodb/select-destination-db.webp)
     </Frame>
   </div>

6. Puede seleccionar las tablas que desea replicar desde la base de datos MongoDB de origen. Al seleccionarlas, también puede cambiar el nombre que tendrán en la base de datos ClickHouse de destino.

Las colecciones se pueden replicar en dos modos:

* **Ingestión predeterminada**: Los documentos se ingestan sin modificaciones en ClickHouse con el Tipo JSON. En este caso, la tabla de destino tendrá una columna específica para `id` y otra, `doc`, que contendrá el documento completo.
* **Ingestión estructurada**: Los documentos se ingestan como filas en una table siguiendo un esquema común para la colección. Este esquema se infiere a partir de una muestra al crear la canalización. Este modo se habilita activando **Asignar documento a columnas** para la colección.

Cuando la ingestión estructurada está habilitada, la sección **Configuración de columnas** muestra los campos encontrados en la muestra junto con los tipos de ClickHouse inferidos. Puede seleccionar qué campos replicar como columnas; la clave `_id` del documento siempre se incluye con el tipo `String`.

<div className="ch-image-md">
  <Frame>
    ![Configuración de ingestión estructurada para una colección](/images/integrations/data-ingestion/clickpipes/mongodb/mongodb-structured-ingestion.webp)
  </Frame>
</div>

El hecho de que las colecciones de MongoDB sean polimórficas (es decir, que los documentos de una misma colección puedan tener esquemas diferentes) implica que la ingestión estructurada debe gestionar registros atípicos:

* **Campos ausentes:** Todas las columnas estructuradas se ingestan como `Nullable`, por lo que, si a un documento le falta un campo, la columna correspondiente tendrá un valor `NULL`.

* **Campos adicionales:** Los campos que no forman parte del esquema inferido se almacenan como JSON en la columna `_peerdb_malformed_data`, con una clave por campo. Cada clave contiene `"unexpected_field": true` y el valor original en `value`:

  ```json
  {
    "rating": {
      "unexpected_field": true,
      "value": 4.5
    }
  }
  ```

  Estos datos se pueden consultar y analizar fácilmente. Por ejemplo, para enumerar los campos inesperados encontrados en una table:

  ```sql
  SELECT DISTINCT arrayJoin(JSONAllPaths(_peerdb_malformed_data)) AS malformed
  FROM movies
  WHERE malformed LIKE '%.unexpected_field';
  ```

  📝 Nota: Si no desea que los valores de los campos adicionales se incluyan en la columna `_peerdb_malformed_data`, puede habilitar la opción **Ocultar valores inesperados** para la colección.

* **Tipo de campo incompatible:** Los valores cuyo tipo no coincide con el de la columna también se almacenan en la columna `_peerdb_malformed_data`, con una clave por campo. Cada clave contiene `"type_mismatch": true` y el valor original en `value`. La columna correspondiente se establece en `NULL`:

  ```json
  {
    "year": {
      "type_mismatch": true,
      "value": "two thousand nineteen"
    }
  }
  ```

  Para leer un campo tanto si su valor coincide con el tipo esperado como si no, combine la columna con su valor alternativo:

  ```sql
  SELECT name, coalesce(year, _peerdb_malformed_data.year.value)
  FROM movies;
  ```

📝 Nota: Puede considerar los campos incluidos en `_peerdb_malformed_data` como valores atípicos que se ingestan en una columna JSON como alternativa.

Dado que la ingestión estructurada infiere el esquema antes de crear la table, habilitarla permite definir expresiones de particionamiento y claves de ordenación personalizadas basadas en las columnas estructuradas.
Todas las columnas estructuradas se ingestan como `Nullable`. Téngalo en cuenta al escribir una expresión para la clave de particionamiento o al usar estas columnas en una clave de ordenación. En estos casos, la tabla de destino se crea con el parámetro de configuración `allow_nullable_key`.

📝 En ambos modos de ingestión, puede activar la opción **Persistir documentos eliminados** si desea que los eventos de eliminación capturen los valores eliminados en la instancia de ClickHouse de destino. Para ello, la colección de origen debe tener habilitado `changeStreamPreAndPostImage`.

## Próximos pasos {#whats-next}

Una vez que haya configurado su ClickPipe para replicar datos de MongoDB a ClickHouse Cloud, puede centrarse en cómo consultar y modelar sus datos para obtener un rendimiento óptimo.

## Consideraciones {#caveats}

Estas son algunas consideraciones que debes tener en cuenta al usar este conector:

* Requerimos MongoDB versión 5.1.0 o superior.
* Usamos la API nativa de Change Streams de MongoDB para CDC, que se basa en el oplog de MongoDB para capturar cambios en tiempo real.
* Los documentos de MongoDB se replican en ClickHouse como JSON type de forma predeterminada. Esto permite una gestión flexible del schema y hace posible usar el amplio conjunto de operadores JSON de ClickHouse para realizar consultas y análisis. Puedes obtener más información sobre cómo consultar datos JSON [aquí](/es/reference/data-types/newjson).
