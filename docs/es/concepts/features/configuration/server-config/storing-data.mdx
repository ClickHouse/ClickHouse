Los datos procesados en ClickHouse suelen almacenarse en el sistema de archivos local de la
máquina en la que se ejecuta el servidor de ClickHouse. Esto requiere discos de gran capacidad,
que pueden resultar costosos. Para evitar almacenar los datos localmente, se admiten varias opciones de almacenamiento:

1. Almacenamiento de objetos [Amazon S3](https://aws.amazon.com/s3/).
2. [Azure Blob Storage](https://azure.microsoft.com/en-us/products/storage/blobs).
3. No compatible: Hadoop Distributed File System ([HDFS](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html))

<br />

<Note>
  ClickHouse también admite motores de tabla externos, que son distintos de
  la opción de almacenamiento externo descrita en esta página, ya que permiten leer datos
  almacenados en formatos de archivo genéricos (como Parquet). En esta página describimos
  la configuración de almacenamiento para las tablas de la familia `MergeTree` o de la familia `Log`.

  1. para trabajar con datos almacenados en discos `Amazon S3`, use el motor de tabla [S3](/es/reference/engines/table-engines/integrations/s3).
  2. para trabajar con datos almacenados en Azure Blob Storage, use el motor de tabla [AzureBlobStorage](/es/reference/engines/table-engines/integrations/azureBlobStorage).
  3. para trabajar con datos en Hadoop Distributed File System (no compatible), use el motor de tabla [HDFS](/es/reference/engines/table-engines/integrations/hdfs).
</Note>

## Configurar almacenamiento externo {#configuring-external-storage}

Los motores de tabla de la familia [`MergeTree`](/es/reference/engines/table-engines/mergetree-family/mergetree) y [`Log`](/es/reference/engines/table-engines/log-family/log)
pueden almacenar datos en `S3`, `AzureBlobStorage` y `HDFS` (no compatible) usando un disco de tipo `s3`,
`azure_blob_storage` o `hdfs` (no compatible), respectivamente.

<Note>
  El tipo de disco `s3` también puede usarse con proveedores de almacenamiento de objetos compatibles con S3, como Alibaba Cloud Object Storage Service. Configure `endpoint` con el endpoint compatible con S3 del proveedor y tenga en cuenta cualquier requisito de compatibilidad específico del proveedor.
</Note>

La configuración del disco requiere:

1. Una sección `type`, igual a uno de `s3`, `azure_blob_storage`, `hdfs` (no compatible), `local_blob_storage`, `web`.
2. La configuración de un tipo específico de almacenamiento externo.

A partir de la versión 24.1 de ClickHouse, es posible usar una nueva opción de configuración.
Requiere especificar:

1. Un `type` igual a `object_storage`
2. `object_storage_type`, igual a uno de `s3`, `azure_blob_storage` (o simplemente `azure` a partir de `24.3`), `hdfs` (no compatible), `local_blob_storage` (o simplemente `local` a partir de `24.3`), `web`.

<br />

Opcionalmente, especifique `metadata_type`. El valor predeterminado es `local` para S3, Azure, HDFS y el almacenamiento de objetos local, y `web` para el almacenamiento web. Los tipos de disco de compatibilidad `s3_plain` y `s3_plain_rewritable` seleccionan los tipos de metadata `plain` y `plain_rewritable`, respectivamente.
El uso del tipo de metadata `plain` se describe en la [sección sobre Plain Storage](/es/concepts/features/configuration/server-config/storing-data#plain-storage); el tipo de metadata `web` solo puede usarse con el tipo de almacenamiento de objetos `web`; el tipo de metadata `local` almacena los archivos de metadata localmente (cada archivo de metadata contiene la asignación a archivos en el almacenamiento de objetos y cierta metainformación adicional sobre ellos).

Por ejemplo:

```xml
<s3>
    <type>s3</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3>
```

equivale a la siguiente configuración (a partir de la versión `24.1`):

```xml
<s3>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>local</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3>
```

La siguiente configuración:

```xml
<s3_plain>
    <type>s3_plain</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

es igual a:

```xml
<s3_plain>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

Un ejemplo de una configuración de almacenamiento completa sería:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
        </disks>
        <policies>
            <s3>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3>
        </policies>
    </storage_configuration>
</clickhouse>
```

A partir de la versión 24.1, también puede tener este aspecto:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>object_storage</type>
                <object_storage_type>s3</object_storage_type>
                <metadata_type>local</metadata_type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
        </disks>
        <policies>
            <s3>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3>
        </policies>
    </storage_configuration>
</clickhouse>
```

Para establecer como opción predeterminada un tipo específico de almacenamiento para todas las tablas `MergeTree`,
agregue la siguiente sección al archivo de configuración:

```xml
<clickhouse>
    <merge_tree>
        <storage_policy>s3</storage_policy>
    </merge_tree>
</clickhouse>
```

Si quieres configurar una política de almacenamiento específica para una tabla concreta,
puedes definirla en la cláusula SETTINGS al crear la tabla:

```sql
CREATE TABLE test (a Int32, b String)
ENGINE = MergeTree() ORDER BY a
SETTINGS storage_policy = 's3';
```

También puede usar `disk` en lugar de `storage_policy`. En este caso, no es necesario
tener la sección `storage_policy` en el archivo de configuración; basta con una sección `disk`.

```sql
CREATE TABLE test (a Int32, b String)
ENGINE = MergeTree() ORDER BY a
SETTINGS disk = 's3';
```

## `refresh_parts_interval` y `table_disk` {#refresh-parts-interval-and-table-disk}

Este parámetro de configuración está pensado para tables MergeTree no replicadas en las que las partes pueden escribirse externamente y la detección de metadata debe actualizarse desde el almacenamiento.

El parámetro de configuración de `MergeTree` `refresh_parts_interval` permite actualizar periódicamente, en discos de solo lectura, la lista de partes de datos desde el almacenamiento subyacente (por ejemplo, para detectar partes escritas externamente). La distinción importante es entre **metadata compartida entre réplicas** y **metadata local de cada réplica** (por ejemplo, S3 con metadata local por réplica): solo cuando la metadata se comparte las partes nuevas serán visibles para todas las réplicas. Usar solo almacenamiento de objetos no implica metadata compartida.

* **Almacenamiento de objetos (por ejemplo, `disk = 's3'`) no implica metadata compartida.** Cuando la metadata se almacena localmente en cada réplica (el comportamiento predeterminado), cada réplica gestiona de forma independiente sus punteros a blobs en almacenamiento de objetos. Los cambios realizados en una réplica no son visibles para las demás. En ese caso, `refresh_parts_interval` no hace que las partes nuevas sean visibles entre réplicas, porque la metadata que lee cada réplica es local a esa réplica.

* **La actualización automática de partes requiere un disco de solo lectura y acceso a la metadata del escritor.** [`table_disk`](/es/reference/settings/merge-tree-settings/table#table_disk) indica que el disco apunta directamente a los datos de una table; no convierte el disco en uno de solo lectura. Configure el acceso de solo lectura por separado, por ejemplo, con `read_only=true` en la definición del disco, y use un tipo de metadata compatible.

* **Con un disco definido globalmente** (por ejemplo, `disk = 's3'` en `storage_configuration`) y la metadata local predeterminada, cada réplica tiene su propio estado de metadata. Aunque los blobs puedan estar en S3, el almacenamiento no se considera compartido a efectos de `refresh_parts_interval`, y las partes nuevas creadas fuera de ClickHouse o en otra réplica no se detectarán.

Para la actualización automática de partes, asegúrese de que el lector tenga acceso a la metadata del escritor y utilice un disco de solo lectura. Compartir un bucket de S3 no basta para compartir la metadata almacenada localmente.

<Note>
  `refresh_parts_interval` no se usa para tables ReplicatedMergeTree.
  Las tables replicadas ya sincronizan las partes mediante el mecanismo de replicación.
  Este parámetro de configuración solo se aplica a tables MergeTree no replicadas en las que las partes se escriben externamente y se requiere actualizar la metadata.
</Note>

## Configuración dinámica {#dynamic-configuration}

También es posible especificar la configuración de almacenamiento sin definir previamente un
disco en el archivo de configuración, ya que puede configurarse en los
ajustes de la consulta `CREATE`/`ATTACH`.

La siguiente consulta adjunta una table de solo lectura almacenada en una URL.

```sql highlight={20-23}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=web,
    endpoint='https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/'
  );
```

El siguiente ejemplo añade una caché al almacenamiento externo.

```sql highlight={20-28}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=cache,
    max_size='1Gi',
    path='custom_disk_cache/',
    disk=disk(
      type=web,
      endpoint='https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/'
      )
  );
```

En la configuración resaltada anteriormente, observe que el disco de `type=web` está anidado dentro
del disco de `type=cache`.

<Note>
  El ejemplo usa `type=web`, pero cualquier tipo de disco puede configurarse como dinámico,
  incluido un disco local. Los discos locales requieren que el argumento `path` esté dentro del
  ajuste del servidor `custom_local_disks_base_directory`, que no tiene ningún valor predeterminado.

  Para un disco de caché dinámico, configure `filesystem_caches_path` o `custom_cached_disks_base_directory` en el servidor. Las rutas relativas de caché se resuelven dentro de ese directorio; las rutas absolutas también deben estar dentro de él.
</Note>

Cada argumento de `disk` solo puede especificarse una vez, salvo aquellos que el disco lee como una lista:
`header` y `access_header` de un disco `s3`, y `key` y `key_hex` de un disco `encrypted`.

También es posible combinar una configuración basada en archivos de configuración con una
configuración definida en SQL:

```sql highlight={20-25}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=cache,
    max_size='1Gi',
    path='custom_disk_cache/',
    disk='web'
  );
```

donde `web` proviene del archivo de configuración del servidor:

```xml
<storage_configuration>
    <disks>
        <web>
            <type>web</type>
            <endpoint>https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/</endpoint>
        </web>
    </disks>
</storage_configuration>
```

### Uso del almacenamiento S3 {#s3-storage}

#### Endpoint y autenticación {#required-parameters-s3}

| Parámetro           | Descripción                                                                                                                                                                                                |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `endpoint`          | URL del endpoint de S3 con estilo `path` o `virtual hosted` [styles](https://docs.aws.amazon.com/AmazonS3/latest/dev/VirtualHosting.html). Debe incluir el bucket y la ruta raíz para almacenar los datos. |
| `access_key_id`     | ID de la clave de acceso de S3. Opcional cuando se utiliza un proveedor de credenciales.                                                                                                                   |
| `secret_access_key` | Clave de acceso secreta de S3, proporcionada junto con `access_key_id` cuando se utilizan credenciales explícitas.                                                                                         |

Los valores predeterminados de S3 han cambiado entre versiones: `use_environment_credentials` pasó de `false` a `true` en `23.4`, `connect_timeout_ms` de `10000` a `1000` en `23.5`, y `request_timeout_ms` de `5000` a `30000` en `22.10`. Estos cambios en los valores predeterminados no afectan a los valores configurados explícitamente.

Las credenciales explícitas tienen prioridad sobre los proveedores de credenciales. Configure `session_token` cuando utilice credenciales explícitas temporales. Con `use_environment_credentials=true`, ClickHouse puede obtener credenciales del entorno, de archivos de credenciales de AWS, mediante identidad web o de roles de instancia o contenedor. Esta opción habilita una cadena de proveedores y no se limita a las variables de entorno.

### Uso de Plain Storage {#plain-storage}

En `22.10` se introdujo un nuevo tipo de disco, `s3_plain`, que proporciona almacenamiento de escritura única.
Sus parámetros de configuración son los mismos que los del tipo de disco `s3`.
A diferencia del tipo de disco `s3`, almacena los datos tal cual. En otras palabras,
en lugar de usar nombres de blob generados aleatoriamente, usa nombres de archivo normales
(de la misma forma en que ClickHouse almacena archivos en el disco local) y no almacena
metadata localmente. Por ejemplo, esta se deriva de los datos en `s3`.

Este tipo de disco permite mantener una versión estática de la table, ya que no
permite ejecutar merges sobre los datos existentes ni insertar nuevos
datos. Un caso de uso de este tipo de disco es crear copias de seguridad en él, lo que puede hacerse
mediante `BACKUP TABLE data TO Disk('plain_disk_name', 'backup_name')`. Después,
puede hacer `RESTORE TABLE data AS data_restored FROM Disk('plain_disk_name', 'backup_name')`
o usar `ATTACH TABLE data (...) ENGINE = MergeTree() SETTINGS disk = 'plain_disk_name'`.

Configuración:

```xml
<s3_plain>
    <type>s3_plain</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

A partir de `24.1`, es posible configurar cualquier disco de almacenamiento de objetos (`s3`, `azure`, `hdfs` (no compatible), `local`) usando
el tipo de metadata `plain`.

Configuración:

```xml
<s3_plain>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

### Uso de almacenamiento S3 plain rewritable {#s3-plain-rewritable-storage}

Se introdujo un nuevo tipo de disco `s3_plain_rewritable` en `24.4`.
Al igual que el tipo de disco `s3_plain`, no requiere almacenamiento adicional para
los archivos de metadatos. En su lugar, los metadatos se almacenan en S3.
A diferencia del tipo de disco `s3_plain`, `s3_plain_rewritable` permite ejecutar merges
y admite operaciones `INSERT`.
No se admite la replicación de tablas.
Las [mutaciones](/es/reference/statements/alter/index#mutations) y las operaciones `ALTER`
solo se admiten si el disco está configurado con `enable_hard_links`, véase más abajo.

Un caso de uso de este tipo de disco es en tablas `MergeTree` no replicadas. Aunque
el tipo de disco `s3` es adecuado para tablas `MergeTree` no replicadas, puede optar
por el tipo de disco `s3_plain_rewritable` si no necesita metadatos locales
para la tabla. Esto puede resultar útil, por ejemplo, para las tablas del sistema.

Configuración:

```xml
<s3_plain_rewritable>
    <type>s3_plain_rewritable</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain_rewritable>
```

es igual a

```xml
<s3_plain_rewritable>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain_rewritable</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain_rewritable>
```

A partir de la versión `24.5`, es posible configurar cualquier disco de almacenamiento de objetos

(`s3`, `azure`, `local`) con el tipo de metadatos `plain_rewritable`.

#### Enlaces físicos en discos plain rewritable {#plain-rewritable-metadata-snapshot}

Las operaciones `ALTER` y las mutaciones de una tabla `MergeTree` comparten mediante enlaces físicos los archivos que no han cambiado
entre una parte y su sucesora mutada, en lugar de copiarlos.
La configuración `enable_hard_links` (`0` de forma predeterminada) permite que un disco con
metadata `plain_rewritable` cree enlaces físicos reales, lo que habilita las siguientes
operaciones:

```xml
<s3_plain_rewritable>
    <type>s3_plain_rewritable</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
    <enable_hard_links>1</enable_hard_links>
</s3_plain_rewritable>
```

Un enlace físico hace que la metadata de un directorio enumere sus archivos de forma explícita, junto
con las claves de los objetos que los almacenan, de modo que un archivo puede hacer referencia a un objeto
almacenado bajo el prefijo de otro directorio. Tenga en cuenta lo siguiente antes
de habilitarlo:

* Un servidor que no admite el ajuste `enable_hard_links` no puede leer un
  directorio en este formato: interpreta toda la metadata del directorio como su
  ruta lógica. Por lo tanto, un disco que contenga este tipo de directorios deja de ser legible si
  se vuelve a una de esas versiones, y no puede compartirse con ella. Los directorios que
  nunca han tenido enlaces físicos conservan la disposición anterior, por lo que los servidores más antiguos pueden seguir leyendo el disco
  hasta la primera operación que cree un enlace físico: una mutación,
  un `ALTER`, un `FREEZE` o una copia de seguridad. Volver a desactivar el ajuste no
  revierte la conversión de los directorios existentes.
* El ajuste solo se lee al crear el disco: cualquier cambio surte efecto tras
  reiniciar el servidor; `SYSTEM RELOAD CONFIG` no lo aplica.
* Cuando se elimina el último enlace de un objeto, este se borra en dos pasos: primero se reescribe la metadata
  del directorio y, después, se elimina el objeto. Si el
  proceso del servidor se termina entre ambos pasos, el objeto queda en el bucket sin que nada
  haga referencia a él, por lo que hay que eliminarlo manualmente.

### Uso de Azure Blob Storage

Los motores de tabla de la familia `MergeTree` pueden almacenar datos en [Azure Blob Storage](https://azure.microsoft.com/en-us/services/storage/blobs/)
mediante un disco de tipo `azure_blob_storage`.

Añada este fragmento dentro del elemento `clickhouse` de la configuración del servidor. Establezca `AZURE_STORAGE_ACCOUNT_KEY` en el entorno del servidor y sustituya los nombres de la cuenta y del contenedor:

```xml
<storage_configuration>
    <disks>
        <blob_storage_disk>
            <type>azure_blob_storage</type>
            <storage_account_url>https://account.blob.core.windows.net</storage_account_url>
            <container_name>container</container_name>
            <account_name>account</account_name>
            <account_key from_env="AZURE_STORAGE_ACCOUNT_KEY"/>
            <metadata_path>/var/lib/clickhouse/disks/blob_storage_disk/</metadata_path>
            <skip_access_check>false</skip_access_check>
        </blob_storage_disk>
    </disks>
</storage_configuration>
```

#### Parámetros de conexión

| Parámetro                  | Descripción                                                                                                                                                                                                                                              | Valor predeterminado |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| `storage_account_url`      | URL de la cuenta de Azure Blob Storage; obligatoria a menos que se proporcione `connection_string` o `endpoint`. Ejemplos: `https://account.blob.core.windows.net` o `http://azurite1:10000/devstoreaccount1`.                                           | -                    |
| `container_name`           | Obligatorio con `storage_account_url` o `connection_string`; de lo contrario, se proporciona en `endpoint`.                                                                                                                                              | Ninguno              |
| `container_already_exists` | Controla el comportamiento de creación del contenedor: <br />- `false`: crea un contenedor nuevo <br />- `true`: se conecta directamente al contenedor existente <br />- Si no se establece: comprueba si el contenedor existe y lo crea si es necesario | -                    |

Antes de `24.3`, si se omitía `container_name`, se seleccionaba `default-container`.

Para la autenticación se selecciona un único método: Shared Key si se proporcionan tanto `account_name` como `account_key`; en su defecto, `connection_string`; si tampoco se proporciona, Workload Identity cuando `use_workload_identity=true` (valor predeterminado: `false`); y, en último lugar, identidad administrada. Si la autenticación falla, no se recurre a otro método. Antes de `24.7`, las cadenas de conexión tenían prioridad sobre las Shared Keys.

Parámetros de autenticación:

| Parámetro           | Descripción                                                            |
| ------------------- | ---------------------------------------------------------------------- |
| `connection_string` | Para la autenticación mediante una cadena de conexión.                 |
| `account_name`      | Para la autenticación mediante Shared Key (se usa con `account_key`).  |
| `account_key`       | Para la autenticación mediante Shared Key (se usa con `account_name`). |

#### Parámetros de límite {#azure-blob-storage-connection-parameters}

| Parámetro                         | Descripción                                                                                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `max_single_part_upload_size`     | Tamaño máximo en bytes de una carga de una sola parte.                                                                                                                       |
| `min_bytes_for_seek`              | Se acepta, pero el búfer de lectura actual no lo utiliza. Use [`remote_read_min_bytes_for_seek`](/es/reference/settings/session-settings/other#remote_read_min_bytes_for_seek). |
| `max_single_read_retries`         | Número máximo de intentos para leer un fragmento de datos desde Blob Storage.                                                                                                |
| `max_single_download_retries`     | Número máximo de intentos para descargar un búfer legible desde Blob Storage.                                                                                                |
| `thread_pool_size`                | Número máximo de threads en el pool de hilos dedicado a las operaciones de copia del disco.                                                                                  |

| `metadata_keep_free_space_bytes` | Bytes que se deben mantener libres en el disco local de metadata.                                                              | `0`                                                                                |

Pueden encontrarse ejemplos de configuraciones funcionales en el directorio de pruebas de integración (consulte, por ejemplo, [test&#95;merge&#95;tree&#95;azure&#95;blob&#95;storage](https://github.com/ClickHouse/ClickHouse/blob/master/tests/integration/test_merge_tree_azure_blob_storage/configs/config.d/storage_conf.xml) o [test&#95;azure&#95;blob&#95;storage&#95;zero&#95;copy&#95;replication](https://github.com/ClickHouse/ClickHouse/blob/master/tests/integration/test_azure_blob_storage_zero_copy_replication/configs/config.d/storage_conf.xml)).

## Uso del almacenamiento HDFS (sin soporte) {#using-hdfs-storage-unsupported}

En esta configuración de ejemplo:

* el disco es de tipo `hdfs` (sin soporte)
* los datos están alojados en `hdfs://hdfs1:9000/clickhouse/`

HDFS no tiene soporte y, por lo tanto, podrían surgir problemas al usarlo. No dudes en enviar una pull request con la corrección si aparece algún problema.

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <hdfs>
                <type>hdfs</type>
                <endpoint>hdfs://hdfs1:9000/clickhouse/</endpoint>
                <skip_access_check>true</skip_access_check>
            </hdfs>
            <hdd>
                <type>local</type>
                <path>/</path>
            </hdd>
        </disks>
        <policies>
            <hdfs>
                <volumes>
                    <main>
                        <disk>hdfs</disk>
                    </main>
                    <external>
                        <disk>hdd</disk>
                    </external>
                </volumes>
            </hdfs>
        </policies>
    </storage_configuration>
</clickhouse>
```

Ten en cuenta que HDFS puede no funcionar en casos límite.

### Uso del cifrado de datos

Puede cifrar los datos almacenados en discos externos [S3](/es/reference/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-s3) o [HDFS](#using-hdfs-storage-unsupported) (no compatible), o en un disco local. Para activar el modo de cifrado, en el archivo de configuración debe definir un disco del tipo `encrypted` y elegir el disco en el que se guardarán los datos. Un disco `encrypted` cifra todos los archivos escritos en tiempo real y, al leer archivos desde un disco `encrypted`, los descifra automáticamente. Así, puede trabajar con un disco `encrypted` como si fuera uno normal.

El siguiente fragmento debe incluirse dentro de `storage_configuration`. Sustituya la clave de ejemplo por su propia clave de la longitud requerida.

```xml
<disks>
  <disk1>
    <type>local</type>
    <path>/path1/</path>
  </disk1>
  <disk2>
    <type>encrypted</type>
    <disk>disk1</disk>
    <path>path2/</path>
    <key>_16_ascii_chars_</key>
  </disk2>
</disks>
```

Por ejemplo, cuando ClickHouse escribe datos de una tabla en un archivo `store/all_1_1_0/data.bin` en `disk1`, en realidad ese archivo se escribirá en el disco físico en la ruta `/path1/store/all_1_1_0/data.bin`.

Al escribir el mismo archivo en `disk2`, en realidad se escribirá en el disco físico en la ruta `/path1/path2/store/all_1_1_0/data.bin`, en modo cifrado.

#### Parámetros obligatorios

| Parámetro | Tipo   | Descripción                                                                                                                                                     |
| --------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`    | String | Debe establecerse en `encrypted` para crear un disco cifrado.                                                                                                   |
| `disk`    | String | Nombre de un disco previamente configurado que se utilizará para el almacenamiento subyacente.                                                                  |
| `key`     | String | Clave para el cifrado y descifrado. Puede especificarse en formato hexadecimal mediante `key_hex`. Se pueden especificar varias claves usando el atributo `id`. |

#### Parámetros opcionales {#required-parameters-encrypted-disk}

| Parámetro        | Tipo   | Predeterminado                                 | Descripción                                                                                                                                                                      |
| ---------------- | ------ | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`           | String | Directorio raíz                                | Directorio relativo en el disco subyacente, que debe terminar en `/` si no está vacío.                                                                                           |
| `current_key_id` | UInt64 | `0` solo cuando la única clave tiene el ID `0` | Selecciona la clave usada para el cifrado. Si hay varias claves, seleccione explícitamente la clave actual. Todas las claves configuradas siguen disponibles para el descifrado. |
| `algorithm`      | Enum   | `AES_128_CTR`                                  | Algoritmo de cifrado. Opciones: <br />- `AES_128_CTR` (clave de 16 bytes) <br />- `AES_192_CTR` (clave de 24 bytes) <br />- `AES_256_CTR` (clave de 32 bytes)                    |

Ejemplo de configuración del disco:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <disk_s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
            </disk_s3>
            <disk_s3_encrypted>
                <type>encrypted</type>
                <disk>disk_s3</disk>
                <algorithm>AES_128_CTR</algorithm>
                <key_hex id="0">00112233445566778899aabbccddeeff</key_hex>
                <key_hex id="1">ffeeddccbbaa99887766554433221100</key_hex>
                <current_key_id>1</current_key_id>
            </disk_s3_encrypted>
        </disks>
    </storage_configuration>
</clickhouse>
```

### Uso de la caché local

Un disco `cache` actúa como envoltorio de un disco de almacenamiento de objetos, como S3, Azure o `web`, y almacena los datos en caché en el sistema de archivos local. No puede envolver un disco `local` normal ni un envoltorio `encrypted`. Defina el disco subyacente antes del disco de caché.

Configuración recomendada para las versiones actuales:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
            <cache>
                <type>cache</type>
                <disk>s3</disk>
                <path>s3_cache/</path>
                <max_size>10Gi</max_size>
            </cache>
        </disks>
        <policies>
            <s3_cache>
                <volumes>
                    <main>
                        <disk>cache</disk>
                    </main>
                </volumes>
            </s3_cache>
        </policies>
    </storage_configuration>
</clickhouse>
```

Configuración antigua, válida solo para las versiones `22.3`–`22.7`. No utilice estas claves `data_cache_*` en las configuraciones actuales; utilice un disco `cache` independiente, como se muestra arriba:

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
                <data_cache_enabled>1</data_cache_enabled>
                <data_cache_max_size>10737418240</data_cache_max_size>
            </s3>
        </disks>
        <policies>
            <s3_cache>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3_cache>
        </policies>
    </storage_configuration>
</clickhouse>
```

| `background_download_max_file_segment_size` | Size    | `4Mi`                | Umbral, redondeado según la alineación, que determina hasta dónde se precarga un segmento en segundo plano. El tamaño de descarga se redondea hacia arriba a `boundary_alignment`, por lo que no es un límite estricto (por ejemplo, `1Mi` con `boundary_alignment` `4Mi` sigue descargando `4Mi`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `load_metadata_asynchronously`              | Boolean | `false`              | Carga los metadatos de la caché de forma asíncrona durante el inicio del servidor.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `use_real_disk_size`                        | Boolean | `false`              | Contabiliza las reservas de la caché en unidades alineadas a los bloques del sistema de archivos en lugar de en bytes reservados. Esto aproxima el espacio que ocupa la reserva en el disco, pero no es el tamaño asignado exacto; afecta a `current_size` de esta caché en `system.filesystem_cache_settings`. La métrica `FilesystemCacheSize`, que abarca todo el proceso, y los eventos de perfilado del tamaño de desalojo se suman para todas las cachés, por lo que solo reflejan de manera uniforme el espacio ocupado por las reservas cuando todas las cachés usan el mismo modo. El `size` por segmento en `system.filesystem_cache` sigue siendo el tamaño lógico del rango; use `downloaded_size` para los bytes escritos en un segmento parcial. Es necesario reiniciar el servidor para cambiar este parámetro de configuración. |
| `use_split_cache`                           | Boolean | `false`              | Separa los archivos entre sistema y datos. No es compatible con `SLRU_OVERCOMMIT` ni con `LRU_OVERCOMMIT`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `split_cache_ratio`                         | Double  | `0.1`                | Proporción del segmento del sistema con respecto al tamaño total de la caché para split&#95;cache.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

> **Nota**: Los valores de tamaño admiten unidades como `ki`, `Mi`, `Gi`, etc. (p. ej., `10Gi`).

## Configuración de consulta/perfil de la caché del sistema de archivos

| Configuración                                                 | Tipo     | Predeterminado          | Descripción                                                                                                                                                                 |
| ------------------------------------------------------------- | -------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `enable_filesystem_cache`                                     | Booleano | `true`                  | Habilita o deshabilita el uso de la caché por consulta, incluso cuando se utiliza un tipo de disco `cache`.                                                                 |
| `read_from_filesystem_cache_if_exists_otherwise_bypass_cache` | Booleano | `false`                 | Cuando está habilitado, usa la caché solo si los datos ya existen; los datos nuevos no se almacenarán en caché.                                                             |
| `enable_filesystem_cache_on_write_operations`                 | Booleano | `false` (Cloud: `true`) | Habilita la caché write-through. Requiere `cache_on_write_operations` en la configuración de la caché.                                                                      |
| `enable_filesystem_cache_log`                                 | Booleano | `false`                 | Habilita el registro detallado del uso de la caché en `system.filesystem_cache_log`.                                                                                        |
| `filesystem_cache_allow_background_download`                  | Booleano | `true`                  | Permite que los segmentos descargados parcialmente se completen en segundo plano. Desactívelo para mantener las descargas en primer plano para la consulta o sesión actual. |

</Warning>

### Uso de almacenamiento web estático (solo lectura)

Este es un disco de solo lectura. Sus datos solo se leen y nunca se modifican. Una tabla nueva
se carga en este disco mediante la consulta `ATTACH TABLE` (consulte el ejemplo a continuación). En realidad, el disco local
no se utiliza; cada consulta `SELECT` dará lugar a una solicitud `http` para
obtener los datos necesarios. Cualquier modificación de los datos de la tabla producirá una
excepción; es decir, no se permiten los siguientes tipos de consultas: [`CREATE TABLE`](/es/reference/statements/create/table),
[`ALTER TABLE`](/es/reference/statements/alter/index), [`RENAME TABLE`](/es/reference/statements/rename#rename-table),
y [`TRUNCATE TABLE`](/es/reference/statements/truncate).
El almacenamiento web puede utilizarse con fines de solo lectura. Un caso de uso
es alojar datos de muestra o migrar datos. Existe una herramienta, `clickhouse-static-files-uploader`,
que prepara un directorio de datos para una tabla determinada (`SELECT data_paths FROM system.tables WHERE name = 'table_name'`).
Para cada tabla que necesite, se obtiene un directorio de archivos. Estos archivos se pueden cargar
en, por ejemplo, un servidor web de archivos estáticos. Después de esta preparación,
puede cargar esta tabla en cualquier servidor de ClickHouse mediante `DiskWeb`.

En esta configuración de ejemplo:

* el disco es de tipo `web`
* los datos están alojados en `http://nginx:80/test1/`
* se utiliza una caché en el almacenamiento local

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <web>
                <type>web</type>
                <endpoint>http://nginx:80/test1/</endpoint>
            </web>
            <cached_web>
                <type>cache</type>
                <disk>web</disk>
                <path>cached_web_cache/</path>
                <max_size>100000000</max_size>
            </cached_web>
        </disks>
        <policies>
            <web>
                <volumes>
                    <main>
                        <disk>web</disk>
                    </main>
                </volumes>
            </web>
            <cached_web>
                <volumes>
                    <main>
                        <disk>cached_web</disk>
                    </main>
                </volumes>
            </cached_web>
        </policies>
    </storage_configuration>
</clickhouse>
```

<Tip>
  El almacenamiento también puede configurarse temporalmente dentro de una consulta, si no se
  prevé usar un conjunto de datos web de forma rutinaria; consulte la [configuración dinámica](#dynamic-configuration) y omita
  editar el archivo de configuración.

  Hay un [conjunto de datos de demostración](https://github.com/ClickHouse/web-tables-demo) alojado en GitHub. Para preparar sus propias tablas para el
  almacenamiento web, consulte la herramienta [clickhouse-static-files-uploader](/es/concepts/features/tools-and-utilities/static-files-disk-uploader)
</Tip>

#### Parámetros opcionales {#static-web-storage-required-parameters}

El storage backend de objetos `web` solo lee el parámetro `endpoint`. No hay parámetros opcionales adicionales específicos de web; las opciones genéricas de disco siguen siendo aplicables.

Para los tiempos de espera de conexión o lectura, consulta [`http_connection_timeout`](/es/reference/settings/session-settings/http#http_connection_timeout) y [`http_receive_timeout`](/es/reference/settings/session-settings/http#http_receive_timeout). Estos ajustes se aplican a las consultas o los perfiles; no son claves de la configuración del disco `web`. Las solicitudes realizadas fuera de una consulta utilizan los ajustes del contexto global. El lector de datos web establece un mínimo de 20 segundos para los tiempos de espera de conexión y recepción; los valores inferiores no reducen estos tiempos de espera de lectura de datos.

Para obtener archivos para la carga, ejecuta:
`clickhouse static-files-disk-uploader --metadata-path <path> --output-dir <dir>` (`--metadata-path` se puede encontrar en la consulta `SELECT data_paths FROM system.tables WHERE name = 'table_name'`).

Al cargar archivos mediante `endpoint`, deben cargarse en la ruta `<endpoint>/store/`, pero la configuración solo debe contener `endpoint`.

Si la URL no es accesible al cargar el disco mientras el servidor inicia las tablas, se capturan todos los errores. Si en este caso hubo errores, las tablas pueden volver a cargarse (hacerse visibles) mediante `DETACH TABLE table_name` -&gt; `ATTACH TABLE table_name`. Si la metadata se cargó correctamente durante el inicio del servidor, las tablas están disponibles de inmediato.

Usa [`http_max_tries`](/es/reference/settings/session-settings/http-max#http_max_tries) para limitar el número de intentos de lectura HTTP, incluido el intento inicial. Usa [`http_retry_initial_backoff_ms`](/es/reference/settings/session-settings/http-retry#http_retry_initial_backoff_ms) y [`http_retry_max_backoff_ms`](/es/reference/settings/session-settings/http-retry#http_retry_max_backoff_ms) para configurar los retardos inicial y máximo entre reintentos.

### Replicación zero-copy (no lista para producción)

La replicación zero-copy es posible, pero no se recomienda, con discos `S3` y `HDFS` (no compatibles). La replicación zero-copy significa que, si los datos se almacenan de forma remota en varias máquinas y es necesario sincronizarlos, solo se replican los metadatos (las rutas a las partes de datos), pero no los datos en sí.

<Info>
  **La replicación zero-copy no está lista para producción**

  La replicación zero-copy está deshabilitada de forma predeterminada en ClickHouse 22.8 y versiones posteriores. Esta funcionalidad no se recomienda para uso en producción.
</Info>
