ClickHouse implementa la API HTTP de Prometheus sobre una tabla [`TimeSeries`](/es/reference/engines/table-engines/integrations/time-series). Un único handler gestiona la escritura remota, la lectura remota, las consultas PromQL instantáneas y las consultas PromQL de rango.

Para exponer las métricas propias de ClickHouse y que un servidor de Prometheus pueda recopilarlas, consulte el [endpoint de métricas de Prometheus](/es/concepts/features/connect-to-clickhouse/prometheus/metrics).

## Requisitos previos {#prerequisites}

Los pasos de configuración varían entre ClickHouse Cloud y ClickHouse autogestionado. Siga la sección que corresponda a su implementación.

### ClickHouse Cloud {#prerequisites-cloud}

<Note>
  La compatibilidad con PromQL en ClickHouse Cloud está en vista previa privada. Los servicios que participan en la vista previa privada ya tienen configurados el parámetro de configuración `enable_time_series_table` y los puntos de conexión de la API de Prometheus. Los demás servicios de ClickHouse Cloud no tienen esta configuración y no es posible activar esta funcionalidad por cuenta propia en ellos. La sentencia `SET enable_time_series_table` y la configuración `http_handlers` de las siguientes secciones se aplican a implementaciones autogestionadas.
</Note>

Si utiliza un servicio que participa en la vista previa privada, continúe en [Crear una table TimeSeries](#create-a-timeseries-table). El servicio atiende las solicitudes en las rutas que figuran en la [tabla de puntos de conexión](#configure-prometheus-api).

### Autogestionado: activar el parámetro de configuración TimeSeries {#enable-the-timeseries-setting}

Active el parámetro de configuración `enable_time_series_table` para el usuario que crea la tabla y accede a ella:

```sql
SET enable_time_series_table = 1;
```

Para las solicitudes a la API HTTP, active `enable_time_series_table` en el perfil del usuario de la API.

### Autogestionado: configurar los puntos de conexión de la API de Prometheus {#configure-prometheus-api}

Configure un handler con enrutamiento por prefijo en el puerto HTTP principal de ClickHouse:

```xml
<http_handlers>
    <defaults/>
    <rule>
        <url_prefix>/prometheus/api/v1</url_prefix>
        <handler>
            <type>prometheus_api_v1</type>
        </handler>
    </rule>
</http_handlers>
```

`<defaults/>` conserva los handlers integrados para puntos de conexión como `/ping` y para solicitudes SQL. El prefijo anterior expone estos puntos de conexión a través de un único handler:

| Endpoint                                 | Propósito                               |
| ---------------------------------------- | --------------------------------------- |
| `/prometheus/api/v1/write`               | Escritura remota de Prometheus          |
| `/prometheus/api/v1/read`                | Lectura remota de Prometheus            |
| `/prometheus/api/v1/query`               | Consultas PromQL instantáneas           |
| `/prometheus/api/v1/query_range`         | Consultas PromQL de rango               |
| `/prometheus/api/v1/format_query`        | Formateo de expresiones PromQL          |
| `/prometheus/api/v1/series`              | Metadata de series                      |
| `/prometheus/api/v1/labels`              | Nombres de etiquetas                    |
| `/prometheus/api/v1/label/<name>/values` | Valores de etiquetas                    |
| `/prometheus/api/v1/metadata`            | Metadata de familias de métricas        |
| `/prometheus/api/v1/federate`            | Federación de las samples más recientes |

En el ejemplo, el handler no incluye `database` ni `table`. Cada solicitud debe indicar el parámetro de consulta `table` (salvo `/format_query`, que solo analiza la expresión PromQL recibida y no necesita una tabla). También puede indicar `database`, usar un nombre de tabla calificado como `prometheus.metrics` u omitir la base de datos para usar `default`. Así, un único handler puede atender varias tablas `TimeSeries`.

Para usar una misma tabla fija en todas las solicitudes, configúrela en el handler:

```xml
<handler>
    <type>prometheus_api_v1</type>
    <database>prometheus</database>
    <table>metrics</table>
</handler>
```

Una tabla configurada en el handler no se puede sobrescribir mediante parámetros de la solicitud.

Ajustes de enrutamiento y del handler:

| Nombre       | Predeterminado | Descripción                                                                                                                                                                                                                        |
| ------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url_prefix` | ninguno        | Filtro de regla que coincide con cualquier ruta de solicitud que empiece por el prefijo configurado.                                                                                                                               |
| `table`      | ninguno        | El nombre de una tabla `TimeSeries`. Si se omite, la solicitud debe proporcionar el parámetro de consulta `table`. El nombre configurado puede incluir una base de datos.                                                          |
| `database`   | ninguno        | La base de datos que contiene la tabla. Una solicitud puede proporcionarla como parámetro de consulta. Si se omite, ClickHouse usa la base de datos indicada en un valor `table` calificado o, en su defecto, recurre a `default`. |

### Crear una table TimeSeries {#create-a-timeseries-table}

Cree una base de datos y una table `TimeSeries`:

```sql
CREATE DATABASE prometheus;
CREATE TABLE prometheus.metrics ENGINE = TimeSeries;
```

## Ingestar métricas con escritura remota {#remote-write}

ClickHouse admite el [protocolo remote-write de Prometheus](https://prometheus.io/docs/specs/remote_write_spec/). Configure Prometheus para que escriba en el handler:

```yaml
remote_write:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/write?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

Prometheus envía las muestras a la tabla `prometheus.metrics`.

Para agrupar en menos partes los datos de muchas solicitudes de remote-write concurrentes, ClickHouse utiliza [inserciones asíncronas](/es/reference/settings/session-settings/async-insert#async_insert). Están habilitadas de forma predeterminada, y el parámetro de configuración `async_insert` en la URL (o en el perfil de usuario) permite activarlas o desactivarlas.

ClickHouse confirma una solicitud de remote-write asíncrona solo después de que los datos se hayan volcado en todas las tablas internas de la tabla `TimeSeries`, independientemente del parámetro de configuración [`wait_for_async_insert`](/es/reference/settings/session-settings/wait-for#wait_for_async_insert), ya que el protocolo remote-write considera duradera toda escritura confirmada. Si el vaciado falla, la solicitud devuelve un error y Prometheus la reintenta.

Como cada solicitud espera a su vaciado, las inserciones asíncronas limitan la velocidad a la que puede escribir un mismo emisor. Prometheus envía una solicitud cada vez por fragmento de remote-write. Cuando varios fragmentos envían a la vez, el tiempo de espera de vaciado adaptativo crece hasta [`async_insert_busy_timeout_max_ms`](/es/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms), salvo que las solicitudes pendientes alcancen antes [`async_insert_max_data_size`](/es/reference/settings/session-settings/async-insert#async_insert_max_data_size). Una solicitud espera hasta que se vacía su lote, lo que ocurre como máximo ese tiempo después de iniciarse el lote; por tanto, con una carga sostenida, cada fragmento escribe aproximadamente `samples per request / async_insert_busy_timeout_max_ms`, y Prometheus envía de forma predeterminada hasta 2,000 muestras por solicitud. Para aumentar este rendimiento:

* Aumente `max_shards` (50 de forma predeterminada) o `max_samples_per_send` en la sección `queue_config` de [`remote_write`](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write). Prometheus añade fragmentos automáticamente cuando se retrasa, hasta `max_shards`.
* Reduzca `async_insert_busy_timeout_max_ms` en la URL o en el perfil de usuario, por ejemplo `&async_insert_busy_timeout_max_ms=50`. De este modo, los vaciados son más frecuentes y cada uno crea nuevas partes en las tablas internas.
* Desactive las inserciones asíncronas con `async_insert=0`. En ese caso, cada solicitud crea sus propias partes en las tablas internas.

## Consultas con PromQL {#promql-query-support}

Use el endpoint de consulta instantánea para evaluar una expresión de PromQL en un momento dado:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

Use el endpoint de consultas por rango para evaluar una expresión sobre un intervalo de tiempo:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

Los endpoints de consultas también aceptan los parámetros en el cuerpo de un formulario. Sin `--get`, curl envía los parámetros como `application/x-www-form-urlencoded` mediante `POST`:

```bash
curl --user default:<password> \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

Utilice el endpoint format-query para analizar y formatear una expresión de PromQL sin evaluarla:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/format_query" \
  --data-urlencode "query=sum by(job)(http_requests_total{code=\"200\"})/2"
```

La expresión se devuelve serializada a partir de la consulta analizada sintácticamente, con los espacios en blanco normalizados, los comentarios eliminados, los paréntesis redundantes suprimidos y las duraciones expresadas en las unidades que acepta el analizador: `sum by (job) (http_requests_total{code="200"}) / 2`. Una duración conserva sus unidades en lugar de convertirse en un número de segundos, de modo que `rate(x[5m])` se devuelve como `rate(x[5m])`; y una duración que no corresponde a un número entero de una sola unidad se escribe con todas las unidades necesarias, de modo que `rate(x[90s])` se devuelve como `rate(x[1m30s])`. Este endpoint no evalúa la expresión, por lo que no requiere los parámetros `database` y `table`.

Consulte las [funcionalidades de PromQL compatibles](/es/reference/functions/table-functions/prometheusQueryRange#supported-promql-features) para ver la lista de funciones y operadores de agregación que utilizan la API HTTP, el dialecto `promql` y las funciones de tabla.

Los demás parámetros de la solicitud se aplican como ajustes de ClickHouse; por ejemplo, `max_execution_time=10`. Los endpoints de consultas también aceptan algunos parámetros de VictoriaMetrics y Thanos: `nocache=1` establece `use_query_cache=0`, `partial_response=false` establece `skip_unavailable_shards=0`, y `dedup=false`, `trace` y `round_digits` se ignoran. En cambio, rechazan con un error `extra_label` y `extra_filters`, porque ClickHouse no aplica estos filtros, así como `dedup=true` y `partial_response=true`, porque ClickHouse no implementa la deduplicación ni las respuestas parciales de Thanos.

### Grafana {#grafana}

Configure un origen de datos de Prometheus con una URL base que termine justo antes de `/api/v1`:

```yaml
apiVersion: 1
datasources:
  - name: ClickHouse Prometheus
    type: prometheus
    access: proxy
    url: https://clickhouse.example.com:8443/prometheus
    basicAuth: true
    basicAuthUser: default
    jsonData:
      httpMethod: POST
      customQueryParameters: database=prometheus&table=metrics
    secureJsonData:
      basicAuthPassword: <password>
```

Grafana añade al final de esta URL base `/api/v1/query` o `/api/v1/query_range` y agrega `customQueryParameters` a cada solicitud.

Con `httpMethod: POST`, Grafana envía los parámetros de consulta en el cuerpo de la solicitud. ClickHouse lee tanto el cuerpo de la solicitud como la cadena de consulta de la URL, por lo que `customQueryParameters` se sigue aplicando. Use `POST` para expresiones PromQL largas, ya que las URL tienen un límite de longitud.

<Note>
  Solo están implementados los endpoints de consultas `/api/v1/query`, `/api/v1/query_range` y `/api/v1/format_query`; los endpoints de metadata `/api/v1/series`, `/api/v1/labels`, `/api/v1/label/<name>/values` y `/api/v1/metadata`, y el endpoint de [federación](#federation) `/api/v1/federate`. `/api/v1/series` requiere al menos un selector de series `match[]`, admite los parámetros opcionales `start`, `end` y `limit`, y devuelve la unión de las series que coinciden con cada selector. `/api/v1/labels` acepta los mismos parámetros, aunque en este caso `match[]` es opcional, y devuelve ordenados los nombres de etiquetas de las series coincidentes (o de todas las series si no se indica ningún selector). `/api/v1/label/<name>/values` acepta los mismos parámetros que `/api/v1/labels` y devuelve ordenados los valores de una etiqueta; opcionalmente, `<name>` puede usar el escape `U__...` de Prometheus para los nombres de etiquetas que contienen caracteres fuera de `[a-zA-Z0-9_]`. Estos endpoints cubren lo que necesita un origen de datos Prometheus de Grafana para explorar etiquetas, usar variables de plantilla y ofrecer autocompletado en el constructor de consultas.
</Note>

### Puntos de entrada de SQL {#sql-entry-points}

ClickHouse utiliza el mismo conversor de PromQL para la API HTTP, el dialecto `promql` y las funciones de tabla [`prometheusQuery`](/es/reference/functions/table-functions/prometheusQuery) y [`prometheusQueryRange`](/es/reference/functions/table-functions/prometheusQueryRange).

Ejecute consultas PromQL directamente con `clickhouse-client`:

```bash
clickhouse-client \
  --dialect promql \
  --promql_database prometheus \
  --promql_table metrics \
  --query 'rate(http_requests_total[5m])'
```

Use las funciones de tabla para incrustar PromQL en una consulta SQL:

```sql
SELECT *
FROM prometheusQuery(
    prometheus.metrics,
    'rate(http_requests_total[5m])',
    now()
);
```

## Consultar la metadata de las métricas {#metadata}

El endpoint `/prometheus/api/v1/metadata` devuelve la metadata de las métricas almacenada en la tabla de destino `Metrics` de la tabla `TimeSeries`: el tipo, el texto de ayuda y la unidad de cada familia de métricas. Admite los siguientes parámetros de Prometheus en la cadena de consulta de la URL:

| Parámetro          | Descripción                                                                                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `metric`           | Devuelve la metadata únicamente de esta familia de métricas.                                                                                         |
| `limit`            | Limita el número de familias de métricas devueltas. Un valor negativo indica que no hay límite; con cero no se devuelve ninguna familia de métricas. |
| `limit_per_metric` | Limita el número de objetos de metadata devueltos por cada familia de métricas. Los valores cero y negativos indican que no hay límite.              |

De forma predeterminada, la tabla de destino `Metrics` es una `ReplacingMergeTree` ordenada por el nombre de la familia de métricas, por lo que conserva la entrada de metadata escrita más recientemente para cada familia de métricas. Solo se devuelven varias entradas por familia mientras la tabla de destino las almacene, es decir, antes de que se fusionen sus partes o cuando la tabla se define con un motor que las conserva.

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/metadata" \
  --data-urlencode "metric=http_requests_total" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

## Federación de métricas {#federation}

ClickHouse admite el endpoint de [federación de Prometheus](https://prometheus.io/docs/prometheus/latest/federation/) en `/prometheus/api/v1/federate` (o en cualquier ruta que termine en `/federate` servida por un handler de tipo `query`). Para cada serie que coincida con los selectores `match[]`, devuelve la muestra más reciente de los últimos 5 minutos en el formato de texto de Prometheus, de modo que un servidor de Prometheus pueda recopilar sus métricas:

```yaml
scrape_configs:
  - job_name: clickhouse-federate
    honor_labels: true
    scheme: https
    metrics_path: /prometheus/api/v1/federate
    params:
      'match[]': ['{job="node"}']
      table: ['prometheus.metrics']
    static_configs:
      - targets: ['clickhouse.example.com:8443']
```

## Lectura de métricas con lectura remota {#remote-read}

ClickHouse admite el [protocolo de lectura remota de Prometheus](https://prometheus.io/docs/prometheus/latest/querying/remote_read_api/) en `/prometheus/api/v1/read`.

Configure un servidor de Prometheus para que lea de la misma tabla `TimeSeries`:

```yaml
remote_read:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/read?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

## Reglas de registro {#recording-rules}

ClickHouse no evalúa archivos de reglas de Prometheus. Una [vista materializada actualizable](/es/reference/statements/create/view#refreshable-materialized-view) puede desempeñar la función de una [regla de registro](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/): evalúa una expresión PromQL de forma programada y añade el resultado al final de una tabla `TimeSeries`. La siguiente vista registra `sum by (job) (rate(http_requests_total[5m]))` como `job:http_requests:rate5m` cada minuto:

```sql
CREATE MATERIALIZED VIEW prometheus.job_http_requests_rate5m
REFRESH EVERY 1 MINUTE APPEND TO prometheus.metrics (tags, samples) AS
SELECT
    mapUpdate(CAST(tags, 'Map(String, String)'), map('__name__', 'job:http_requests:rate5m')) AS tags,
    [(timestamp, value)] AS samples
FROM prometheusQuery(prometheus.metrics, 'sum by (job) (rate(http_requests_total[5m]))', toStartOfMinute(now()));
```

Cada actualización evalúa la expresión al inicio del minuto en curso, establece el nombre de la métrica con `mapUpdate` y añade al final una muestra por cada serie del resultado. Se pueden añadir etiquetas adicionales al mismo mapa, por ejemplo `map('__name__', 'job:http_requests:rate5m', 'team', 'web')`. La serie registrada se consulta como cualquier otra métrica:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=job:http_requests:rate5m" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

El instante y el error de la última evaluación se muestran en [`system.view_refreshes`](/es/reference/system-tables/view_refreshes).

Una vista se diferencia de una regla de registro de Prometheus en los siguientes aspectos:

* El instante de evaluación es `now()` en el momento en que se ejecuta la actualización. Además de hacerlo según la programación, una vista se actualiza justo después de crearse (salvo que se cree con `EMPTY`), tras un reinicio del servidor si sus actualizaciones no están coordinadas (una vista fuera de una base de datos Replicated o Shared, o con `all_replicas = 1`, no recuerda su última actualización), y cuando `SYSTEM START VIEW` la reanuda después de que se haya perdido una actualización programada. Redondee `now()` hacia abajo al intervalo, como hace el ejemplo, para que estas actualizaciones no añadan muestras entre las programadas. Aun así, una actualización adicional puede escribir una segunda muestra con la misma marca de tiempo redondeada. Para una regla de cinco minutos, use `toStartOfInterval(now(), INTERVAL 5 MINUTE)`.
* Las evaluaciones perdidas no se recuperan. Si el servidor ha estado caído o la vista se ha detenido, la vista evalúa solo el intervalo actual y los intervalos anteriores quedan vacíos. Lo mismo ocurre cuando una actualización tarda más que el intervalo.
* Una serie que desaparece del resultado no recibe ningún marcador de antigüedad, por lo que las consultas siguen devolviendo su último valor registrado durante el período de lookback, que es de 5 minutos de forma predeterminada.
* No existe un archivo de reglas: cada regla es una vista independiente. Las reglas no aparecen en `/api/v1/rules`.
