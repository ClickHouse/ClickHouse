El controlador ODBC de ClickHouse proporciona una interfaz conforme a los estándares para conectar aplicaciones compatibles con ODBC a
ClickHouse. Implementa la API de ODBC y permite que aplicaciones, herramientas de BI y entornos de scripting ejecuten consultas
SQL, obtengan resultados e interactúen con ClickHouse mediante mecanismos conocidos.

El controlador se comunica con el servidor de ClickHouse mediante el [protocolo HTTP](/es/concepts/features/connect-to-clickhouse/protocols/http), que es el protocolo
principal compatible con todas las implementaciones de ClickHouse. Gracias a ello, el controlador funciona de forma coherente en entornos
muy diversos, como instalaciones locales, servicios administrados en la nube y entornos en los que solo se dispone de acceso
basado en HTTP.

El código fuente del controlador está disponible en el
[repositorio de GitHub de ClickHouse-ODBC](https://github.com/ClickHouse/clickhouse-odbc).

<Tip>
  Para obtener una mejor compatibilidad, recomendamos encarecidamente actualizar su servidor de ClickHouse a la versión 24.11 o posterior.
</Tip>

<Note>
  Este controlador está en desarrollo activo. Es posible que algunas funcionalidades de ODBC aún no estén completamente implementadas. La versión actual
  se centra en ofrecer la conectividad esencial y la funcionalidad básica de ODBC, y está previsto incorporar funcionalidades adicionales en futuras
  versiones.

  Sus comentarios son muy valiosos y nos ayudan a priorizar nuevas funcionalidades y mejoras. Si encuentra
  limitaciones, funcionalidades ausentes o comportamientos inesperados, comparta sus observaciones o solicitudes de funcionalidades a través
  del sistema de seguimiento de issues en
  [https://github.com/ClickHouse/clickhouse-odbc/issues](https://github.com/ClickHouse/clickhouse-odbc/issues)
</Note>

## Instalación en Windows {#installation-on-windows}

Puede encontrar la versión más reciente del controlador en
[https://github.com/ClickHouse/clickhouse-odbc/releases/latest](https://github.com/ClickHouse/clickhouse-odbc/releases/latest).
Desde allí, puede descargar y ejecutar el instalador MSI y seguir unos sencillos pasos de instalación.

## Pruebas {#testing}

Puede probar el controlador ejecutando este sencillo script de PowerShell. Copie el texto siguiente, configure su URL, usuario y contraseña, y
péguelo en el símbolo del sistema de PowerShell: después de ejecutar `$reader.GetValue(0)`, debería mostrarse la versión del servidor
de ClickHouse.

```powershell
$url = "http://127.0.0.1:8123/"
$username = "default"
$password = ""
$conn = New-Object System.Data.Odbc.OdbcConnection("`
    Driver={ClickHouse ODBC Driver (Unicode)};`
    Url=$url;`
    Username=$username;`
    Password=$password")
$conn.Open()
$cmd = $conn.CreateCommand()
$cmd.CommandText = "select version()"
$reader = $cmd.ExecuteReader()
$reader.Read()
$reader.GetValue(0)
$reader.Close()
$conn.Close()
```

## Parámetros de configuración {#configuration-parameters}

Los siguientes parámetros son los ajustes más utilizados para establecer una conexión con el controlador ODBC de
ClickHouse. Abarcan las opciones esenciales de autenticación, de comportamiento de la conexión y de manejo de datos. La lista completa de
parámetros compatibles está disponible en la página de GitHub del proyecto
[https://github.com/ClickHouse/clickhouse-odbc](https://github.com/ClickHouse/clickhouse-odbc).

* `Url`: Especifica el endpoint HTTP(S) completo del servidor de ClickHouse. Incluye el protocolo, el host, el puerto y
  una ruta opcional.
* `Username`: El nombre de usuario utilizado para autenticarse en el servidor de ClickHouse.
* `Password`: La contraseña asociada al nombre de usuario especificado. Si no se proporciona, el controlador se conecta sin autenticación
  por contraseña.
* `Database`: La base de datos predeterminada que se utilizará en la conexión.
* `Timeout`: El tiempo máximo (en segundos) que el controlador espera una respuesta del servidor antes de cancelar la solicitud.
* `ClientName`: Un identificador personalizado que se envía al servidor de ClickHouse como parte de la metadata del cliente. Resulta útil para rastrear o
  distinguir el tráfico de distintas aplicaciones. Este parámetro formará parte del encabezado User-Agent de las solicitudes HTTP
  generadas por el controlador.
* `Compression`: Activa o desactiva la compresión HTTP de las cargas útiles de solicitudes y respuestas. Si está habilitada, puede reducir
  el uso de ancho de banda y mejorar el rendimiento con conjuntos de resultados grandes.
* `SqlCompatibilitySettings`: Habilita ajustes de consulta que hacen que ClickHouse se comporte más como una base de datos relacional
  tradicional. Resulta útil cuando las consultas las generan automáticamente herramientas de terceros, como Power BI. Estas
  herramientas no suelen tener en cuenta ciertos comportamientos ClickHouse-specific y pueden generar consultas que provoquen errores o
  resultados inesperados. Consulte [Ajustes de ClickHouse utilizados por el parámetro de configuración SqlCompatibilitySettings
  ](#sql-compatibility-settings) para obtener más detalles.

A continuación se muestran algunos ejemplos de la cadena de conexión completa que se pasa al controlador para establecer una conexión.

* Un servidor de ClickHouse instalado localmente en una instancia de WSL

```plaintext
Driver={ClickHouse ODBC Driver (Unicode)};Url=http://localhost:8123/;Username=default
```

* Una instancia de ClickHouse Cloud.

```plaintext
Driver={ClickHouse ODBC Driver (Unicode)};Url=https://you-instance-url.gcp.clickhouse.cloud:8443/;Username=default;Password=your-password
```

## Integración con Microsoft Power BI {#powerbi-integration}

Puede usar el controlador ODBC para conectar Microsoft Power BI a un servidor de ClickHouse. Power BI ofrece dos opciones de
conexión: el conector ODBC genérico y el Conector de ClickHouse, ambos incluidos en las instalaciones estándar de Power BI.

Ambos conectores se basan internamente en ODBC, pero sus capacidades difieren:

* Conector de ClickHouse (recomendado)
  Utiliza ODBC internamente, pero admite el modo DirectQuery. En este modo, Power BI genera automáticamente consultas SQL y
  recupera únicamente los datos necesarios para cada visualización u operación de filtro.

* Conector ODBC
  Solo admite el modo Import. Power BI ejecuta la consulta proporcionada por el usuario (o selecciona la tabla completa) e importa
  el conjunto de resultados completo en Power BI. Cada actualización posterior vuelve a importar todo el conjunto de datos.

Elija el conector en función de su caso de uso. DirectQuery es la mejor opción para dashboards interactivos con grandes conjuntos de datos.
Elija el modo Import cuando necesite copias locales completas de los datos.

Para obtener más información sobre la integración de Microsoft Power BI con ClickHouse, consulte la [página de la documentación de ClickHouse sobre la integración con Power
BI](/es/integrations/connectors/data-visualization/powerbi-and-clickhouse).

## Configuración de compatibilidad con SQL {#sql-compatibility-settings}

ClickHouse tiene su propio dialecto SQL único y, en algunos casos, se comporta de forma distinta a otras bases de datos como MS SQL
Server, MySQL o PostgreSQL. A menudo, estas diferencias suponen una ventaja, ya que introducen una sintaxis mejorada que facilita
el uso de las funcionalidades de ClickHouse.

Sin embargo, el controlador ODBC se utiliza con frecuencia en entornos donde las consultas no las escriben los usuarios, sino que las generan herramientas de terceros, como Power
BI. Estas consultas suelen basarse en un subconjunto mínimo del estándar SQL. En estos casos,
las desviaciones de ClickHouse respecto al estándar SQL pueden no comportarse como se espera y producir resultados o errores inesperados.
El controlador ODBC proporciona un parámetro de configuración adicional, `SqlCompatibilitySettings`, que habilita determinados ajustes de consulta
para que el comportamiento de ClickHouse se ajuste mejor al SQL estándar.

### Ajustes de ClickHouse habilitados por el parámetro de configuración SqlCompatibilitySettings {#sql-compatibility-settings-list}

En esta sección se describe qué ajustes modifica el controlador ODBC y por qué.

**[cast&#95;keep&#95;nullable](/es/reference/settings/session-settings/cast#cast_keep_nullable)**

De forma predeterminada, ClickHouse no permite convertir tipos que admiten valores NULL en tipos que no los admiten. Sin embargo, muchas herramientas de BI no
distinguen entre tipos que admiten valores NULL y tipos que no los admiten al realizar conversiones de tipos. Por ello, no es raro
que las herramientas de BI generen consultas como la siguiente:

```sql
SELECT sum(CAST(value, 'Int32'))
FROM values
```

De forma predeterminada, cuando la columna `value` admite valores NULL, esta consulta falla con el siguiente mensaje:

```plaintext
DB::Exception: Cannot convert NULL value to non-Nullable type: while executing 'FUNCTION CAST(__table1.value :: 2,
'Int32'_String :: 1) -> CAST(__table1.value, 'Int32'_String) Int32 : 0'. (CANNOT_INSERT_NULL_IN_ORDINARY_COLUMN)
```

Al habilitar `cast_keep_nullable`, `CAST` cambia su comportamiento y conserva la nulabilidad de sus argumentos. Esto
acerca el comportamiento de ClickHouse al de otras bases de datos y al estándar SQL para este tipo de conversión.

**[prefer&#95;column&#95;name&#95;to&#95;alias](/es/reference/settings/session-settings/prefer#prefer_column_name_to_alias)**

ClickHouse permite hacer referencia a expresiones de la misma lista `SELECT` mediante sus alias. Por ejemplo, esta consulta evita
repeticiones y es más fácil de escribir:

```sql
SELECT
    sum(value) AS S,
    count() AS C,
    S / C
FROM test
```

Esta funcionalidad se usa ampliamente, pero otras bases de datos normalmente no resuelven los alias de esta forma dentro de la misma lista `SELECT`,
y esas consultas darían un error. Los problemas se hacen más evidentes cuando un alias tiene el mismo nombre que una columna. Por ejemplo:

```sql
SELECT
    sum(value) AS value,
    avg(value)
FROM test
```

¿Qué `value` debería agregar `avg(value)`? De forma predeterminada, ClickHouse da prioridad al alias, lo que en la práctica convierte esto en una
agregación anidada, algo que la mayoría de las herramientas no espera.

Por sí solo, esto rara vez supone un problema, pero algunas herramientas de BI generan consultas con subconsultas que reutilizan alias de columnas. Por
ejemplo, Power BI suele generar consultas similares a la siguiente:

```sql
SELECT
    sum(C1) AS C1,
    count(C1) AS C2
FROM
(
    SELECT sum(value) AS C1
    FROM test
    GROUP BY group_index
) AS TBL
```

Las referencias a `C1` pueden provocar el siguiente error:

```plaintext
Code: 184. DB::Exception: Received from localhost:9000. DB::Exception: Aggregate function sum(C1) AS C1 is found
inside another aggregate function in query. (ILLEGAL_AGGREGATION)
```

Otras bases de datos normalmente no resuelven los alias en el mismo nivel de esta manera, sino que tratan `C1` como una columna de la
subconsulta. Para conservar un comportamiento similar en ClickHouse y permitir que estas consultas se ejecuten sin errores, el controlador ODBC
habilita `prefer_column_name_to_alias`.

En la mayoría de los casos, habilitar estos ajustes no debería suponer ningún problema. Sin embargo, los usuarios que tienen el parámetro de configuración readonly establecido en `1`
no pueden cambiar ningún ajuste, ni siquiera en consultas `SELECT`. Para estos usuarios, habilitar `SqlCompatibilitySettings` producirá
un error. En la siguiente sección se explica cómo hacer que este parámetro de configuración funcione con usuarios de solo lectura.

## Cómo hacer que la configuración de compatibilidad con SQL funcione para usuarios de solo lectura {#readonly-users}

Al conectarse a ClickHouse mediante el controlador ODBC con el parámetro `SqlCompatibilitySettings` habilitado, un usuario con
el parámetro de configuración readonly establecido en `1` obtendrá un error, porque el controlador intenta modificar los ajustes de consulta:

```plaintext
Code: 164. DB::Exception: Cannot modify 'cast_keep_nullable' setting in readonly mode. (READONLY)
Code: 164. DB::Exception: Cannot modify 'prefer_column_name_to_alias' setting in readonly mode. (READONLY)
```

Esto ocurre porque los usuarios en modo de solo lectura no pueden cambiar ajustes, ni siquiera para consultas `SELECT` individuales.
Hay varias formas de solucionarlo.

**Opción 1. Establecer `readonly` en `2`**

Esta es la opción más sencilla. Establecer `readonly` en `2` permite cambiar ajustes sin que el usuario deje de estar en modo de solo
lectura.

```sql
ALTER USER your_odbc_user MODIFY SETTING
    readonly = 2
```

En la mayoría de los casos, establecer `readonly` en 2 es la forma más sencilla y recomendada de resolver este problema. Si
eso no le funciona, utilice la segunda opción.

**Opción 2. Modificar la configuración del usuario para que coincida con los ajustes que establece el controlador ODBC.**

Esto también es sencillo: actualice la configuración del usuario para que ya coincida con lo que el controlador ODBC intenta establecer.

```sql
ALTER USER your_odbc_user MODIFY SETTING
    cast_keep_nullable = 1,
    prefer_column_name_to_alias = 1
```

Con este cambio, el controlador ODBC puede seguir intentando aplicar los ajustes, pero como los valores ya coinciden, no
se produce ningún cambio efectivo y se evita el error.

Esta opción también es sencilla, pero requiere mantenimiento: las versiones más recientes del controlador pueden modificar la lista de ajustes o añadir
otros nuevos por motivos de compatibilidad. Si fija estos ajustes directamente en su usuario ODBC, es posible que tenga que actualizarlos cada vez que el
controlador ODBC empiece a aplicar ajustes adicionales.
