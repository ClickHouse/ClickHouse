`clickhousectl` (alias `chctl`) es la CLI oficial de ClickHouse, desde el desarrollo local hasta ClickHouse Cloud. Está pensada para quienes trabajan en una terminal, para scripts y para agentes de programación.

Con `clickhousectl` puede:

* Instalar versiones locales de ClickHouse y alternar entre ellas, ejecutar servidores locales aislados y ejecutar SQL
* Ejecutar Postgres localmente sobre Docker
* Crear, configurar, escalar, respaldar y consultar servicios de ClickHouse Cloud
* Crear, supervisar, configurar y restaurar servicios de [ClickHouse Managed Postgres](/es/products/managed-postgres/overview)
* Crear y operar ClickPipes desde almacenamiento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB y BigQuery
* Administrar fuentes, dashboards, alertas, webhooks, búsquedas guardadas y roles en un servicio de [Self-managed ClickHouse Observability](/es/clickstack/self-configured/deployment/managed)
* Desarrollar UDF ejecutables localmente y desplegarlas en ClickHouse Cloud
* Administrar los miembros de la organización, las invitaciones, las claves de API y los roles
* Instalar las ClickHouse agent skills oficiales en agentes de programación

Esta página muestra ejemplos representativos. `clickhousectl <command> --help` es la referencia de autoridad para todos los comandos y parámetros. La ayuda de la mayoría de los comandos termina con un bloque `CONTEXT FOR AGENTS`; en los comandos de Cloud, también enumera los permisos de clave de API que requieren. Para ver tutoriales paso a paso, siga los enlaces a las guías de cada sección. Para obtener una descripción general centrada en Cloud, consulte [CLI de ClickHouse](/es/products/cloud/features/cli).

## Instalación {#installation}

`clickhousectl` funciona en MacOS y Linux, en arquitecturas ARM64 y x86&#95;64.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

El script instala `~/.local/bin/clickhousectl` y crea el alias `chctl`. Asegúrese de que `~/.local/bin` esté incluido en su `PATH`.

También puede instalarlo con un gestor de paquetes:

| Herramienta                                      | Comando                         |
| ------------------------------------------------ | ------------------------------- |
| npm                                              | `npm install -g clickhousectl`  |
| uv                                               | `uv tool install clickhousectl` |
| pipx                                             | `pipx install clickhousectl`    |
| pip                                              | `pip install clickhousectl`     |
| cargo-binstall                                   | `cargo binstall clickhousectl`  |
| Cargo, a partir del código fuente (Rust 1.94.1+) | `cargo install clickhousectl`   |

Solo el script de instalación y npm crean el alias `chctl`. Para actualizar una instalación existente, ejecute `clickhousectl update` (consulte [Autoactualización](#self-update)); en las instalaciones realizadas con npm, uv, pipx y pip, el comando muestra en su lugar el comando de actualización correspondiente del gestor de paquetes.

### Autocompletado en el shell {#shell-completions}

Para autocompletar comandos, parámetros, nombres de servidores locales y versiones instaladas con la tecla Tab, añada una línea al archivo de inicio de su shell. Esta línea registra tanto `clickhousectl` como `chctl`:

```bash
eval "$(clickhousectl completions bash)"   # ~/.bashrc
eval "$(clickhousectl completions zsh)"    # ~/.zshrc, after compinit
clickhousectl completions fish | source    # ~/.config/fish/config.fish
```

El autocompletado ejecuta la CLI instalada cada vez que se pulsa Tab, por lo que sigue actualizado tras ejecutar `update`.

## Requisitos {#requirements}

* Docker, solo para Postgres local
* Para los comandos de Cloud, una cuenta de [ClickHouse Cloud](https://clickhouse.com/cloud). Los comandos de lectura funcionan con OAuth basado en navegador (`cloud auth login`). Para crear o modificar recursos, se necesita una [clave de API](/es/products/cloud/features/admin-features/api/openapi). Consulte [Autenticación](#authentication).

## Local {#local}

Un directorio que contiene `.clickhouse/` es la raíz de un proyecto, del mismo modo que un directorio que contiene `.git/` lo es para Git. Los comandos locales usan la raíz más cercana, ya sea en el directorio actual o en uno superior, por lo que funcionan desde cualquier subdirectorio del proyecto; fuera de un proyecto, usan el directorio actual. Establezca `CLICKHOUSECTL_PROJECT_DIR` para indicar explícitamente la raíz del proyecto, por ejemplo, en un script o en una tarea de CI. Cada proyecto guarda los datos de su servidor en `.clickhouse/`, mientras que los binarios de ClickHouse se comparten globalmente en `~/.clickhouse/`. Consulte la [guía de desarrollo local](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md) para ver el flujo de trabajo completo.

### Instalación y selección de versiones {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
clickhousectl local install --binary ~/ClickHouse/build/programs/clickhouse   # A build of your own
```

| Selector      | Significado                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| `latest`      | Última build de ClickHouse, comprobada de forma remota en cada instalación, uso o inicio (recomendado) |
| `stable`      | Última versión estable                                                                                 |
| `lts`         | Última versión con soporte a largo plazo                                                               |
| `26.8`        | Última versión que coincida con el selector                                                            |
| `26.8.1.1760` | Versión exacta                                                                                         |

`local use` instala la versión si es necesario, la establece como predeterminada para los próximos inicios del servidor y crea un enlace simbólico a ella en `~/.local/bin/clickhouse`, de modo que `clickhouse client` y `clickhouse local` estén disponibles en su `PATH`. Use `--no-global` para omitir la creación del enlace simbólico. Si ya existe un archivo normal en esa ruta, no se modifica.

`local remove` no permite eliminar la versión predeterminada ni ninguna que esté utilizando un servidor en ejecución en cualquier proyecto. `--force` detiene esos servidores y elimina la versión, además de quitarla como predeterminada y borrar el enlace simbólico.

`local install --binary <path>` copia un binary de ClickHouse que haya compilado y lo instala con el número de versión que este indica, de modo que pueda seleccionarlo con `local use` o `--version` como cualquier otra instalación. Al volver a compilarlo, normalmente se obtiene el mismo número de versión, por lo que debe usar `--force` para reemplazar la copia instalada.

### Inicializar un proyecto {#initializing-project}

```bash
clickhousectl local init
```

`init` marca el directorio actual (o `CLICKHOUSECTL_PROJECT_DIR`, si está definido) como raíz del proyecto. Crea un directorio `.clickhouse/`, ignorado por git, para los datos de tiempo de ejecución, además de estructuras base que puede incluir en un commit: `clickhouse/` (`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`, `config.d/`) y `postgres/` (`tables/`, `views/`, `functions/`, `queries/`, `seed/`). Si se vuelve a ejecutar, solo crea lo que falta, así que basta con ejecutarlo una vez después de clonar un proyecto. Si se inicia el servidor sin `init`, este funciona igualmente y crea `.clickhouse/` en el directorio actual.

### Ejecutar servidores locales {#managing-servers}

```bash
clickhousectl local clickhouse start dev --version latest   # Background start; waits for readiness
clickhousectl local clickhouse start dev --no-wait          # Return after spawning
clickhousectl local clickhouse start dev --foreground       # Run in the foreground
clickhousectl local clickhouse start dev --http-port 8124 --tcp-port 9001
clickhousectl local clickhouse list                         # ClickHouse servers in this project
clickhousectl local clickhouse list --global                # Servers across all projects
clickhousectl local status                                  # Every ClickHouse server and Postgres instance in this project
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse stop-all                     # Stop every ClickHouse server in this project
clickhousectl local clickhouse remove dev                   # Permanently delete a stopped server's data
```

`local ch` es la abreviatura de `local clickhouse`, y el nombre anterior `local server` sigue funcionando como alias. Cada servidor con nombre tiene sus propios datos en `.clickhouse/servers/<name>/data/`, que se conservan al detenerlo para el siguiente inicio. Al iniciar un servidor sin indicar un nombre, se utiliza `default`; si `default` ya está en ejecución, se genera un nombre nuevo. Los puertos predeterminados son HTTP 8123 y TCP 9000; si están ocupados, se asignan puertos libres.

Los comandos que actúan sobre un servidor existente (`stop`, `client`, `dotenv`, `local client` y `local udf --server`) seleccionan `default` cuando se omite el nombre o, en su defecto, el único servidor del proyecto que utiliza ese motor. Si hay varios servidores y ninguno se llama `default`, fallan con `server_selection_required` y muestran los nombres. `remove` nunca elige por su cuenta: sin un nombre, solo elimina `default`. Los scripts deben pasar los nombres explícitamente.

`--version` permite elegir una versión para ese inicio sin cambiar la predeterminada. Si se inicia un servidor sin especificar una versión y no hay ninguna predeterminada, se instala `latest` sin establecerla como predeterminada; ejecute primero `local use latest` para establecerla como predeterminada.

### Ejecutar SQL con el client local {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` se conecta a un servidor con nombre mediante el mismo binary de ClickHouse que lo ejecuta; si no se indica ningún nombre, aplica la regla de selección descrita anteriormente. Los argumentos que siguen a `--` se pasan sin modificar a `clickhouse client`. La salida y el código de salida proceden de `clickhouse client`, incluso en modo JSON, por lo que, al escribir scripts, debe establecer usted mismo el formato de salida de SQL.

### Configuración personalizada del servidor {#custom-config-files}

Las configuraciones parciales en XML o YAML se cargan desde tres ubicaciones y sobrescriben los valores predeterminados integrados:

| Ubicación                                      | Se aplica a                                                                     | Cuándo                   |
| ---------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------ |
| `~/.clickhouse/config.d/`                      | Todos los servidores de esta máquina                                            | En cada inicio           |
| `clickhouse/config.d/` en la raíz del proyecto | Todos los servidores del proyecto; inclúyalo en el repositorio para compartirlo | En cada inicio           |
| `~/.clickhouse/configs/`                       | El servidor que inicie con esa configuración                                    | Solo con `--config NAME` |

```bash
cat > clickhouse/config.d/logging.xml <<'XML'
<clickhouse>
    <logger><level>debug</level></logger>
</clickhouse>
XML
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local clickhouse configs          # List both config.d directories and the named configs
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse start dev --config analytics
```

En cada inicio se combinan en el orden de la tabla y prevalecen los archivos posteriores, por lo que un archivo solo necesita incluir los ajustes que usted modifique. Las modificaciones y la eliminación de un `--config` surten efecto en el siguiente inicio. Las rutas de datos y los puertos gestionados siempre prevalecen sobre los valores de configuración.

### Guardar los datos de conexión en un archivo dotenv {#dotenv}

```bash
clickhousectl local clickhouse dotenv dev                                     # Writes .env
clickhousectl local clickhouse dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` lee los puertos reales del servidor en ejecución y escribe `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT` y `CLICKHOUSE_HTTP_PORT`, además del usuario, la contraseña y la base de datos si los indicas. Se conservan las demás líneas de un archivo existente. Carga el archivo con el cargador de dotenv de tu aplicación; nunca ejecutes `eval` sobre la vista previa que se muestra en pantalla.

### Postgres local {#local-postgres}

Postgres local se ejecuta en Docker, por lo que Docker debe estar en ejecución. Se admiten las versiones 17 y 18 de Postgres, incluidas etiquetas de imagen como `18-alpine`; las instancias nuevas usan la versión 18 de forma predeterminada.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres list                       # Postgres instances in this project
clickhousectl local postgres stop app
clickhousectl local postgres stop-all                   # Stop every Postgres instance in this project
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

`local pg` es la forma abreviada de `local postgres`. Cada instancia se identifica por su nombre y su versión principal. Al reanudar una instancia detenida, se reutilizan su puerto, usuario, contraseña y base de datos originales, por lo que los parámetros de creación no tienen ningún efecto al reanudarla. Si no proporciona una contraseña, se genera una aleatoria. `.env.local` contiene la contraseña, así que no lo incluya en el control de versiones.

### UDFs locales {#local-udfs}

`local udf` despliega [UDF ejecutables](/es/reference/functions/regular-functions/udf#executable-user-defined-functions) desde `clickhouse/udfs/<name>/` en un servidor local. `cloud udf` carga ese mismo directorio en Cloud (consulte [UDFs en Cloud](#cloud-udfs)).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local clickhouse start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

Todos los comandos, salvo `init`, aceptan `--server <name>`; si no se indica, la [regla de selección](#managing-servers) determina el servidor. `deploy` valida `udf.json` del mismo modo que Cloud. En un servidor en ejecución, recarga las funciones y confirma que la función se ha cargado. El tiempo de ejecución `native` solo se despliega localmente en hosts Linux amd64 o arm64. Consulte la [guía de funciones definidas por el usuario](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

## Autenticación {#authentication}

Los comandos de Cloud usan uno de estos dos tipos de credencial:

| Credencial                | Capacidades                                                                                                                          | Almacenamiento                                                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| OAuth basado en navegador | Tu identidad de usuario: operaciones de Cloud de solo lectura y SQL de solo lectura en todas las organizaciones a las que perteneces | `~/.clickhouse/tokens.json`, global y compartido entre proyectos                                                  |
| Clave de API              | Limitada a una sola organización; las lecturas y escrituras dependen de los roles de la clave                                        | `.clickhouse/credentials.json` en la raíz del proyecto cuando se guarda; se detecta desde cualquier subdirectorio |

Si aún no tienes una cuenta de ClickHouse Cloud, `clickhousectl cloud auth signup` abre la página de registro en tu navegador.

### Inicio de sesión con OAuth {#oauth-login}

```bash
clickhousectl cloud auth login
```

Esto abre el navegador para iniciar el flujo de autorización de dispositivo de OAuth. Los tokens se guardan de forma global en `~/.clickhouse/tokens.json` y se renuevan automáticamente.

<Note>
  OAuth es de **solo lectura**. Para crear o modificar recursos, inicie sesión con una [clave de API](#api-key).
</Note>

### Clave de API {#api-key}

[Cree una clave de API](/es/products/cloud/features/admin-features/api/openapi) con los roles que requieran sus comandos y, a continuación, guárdela. El prompt interactivo evita que el secreto quede registrado en el historial de su shell:

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

El inicio de sesión verifica la clave y muestra la identity a la que pertenece. Si la API rechaza la clave, esta no se guarda y el comando finaliza con el código 4. Si no se puede acceder a la API, la clave se guarda con una advertencia.

Para CI y otros procesos de automatización, inyecte la clave mediante su gestor de secretos en lugar de guardarla:

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

Durante el desarrollo, la CLI también lee estas variables de un archivo `.env` ubicado en el directorio actual o, si no existe ahí, en la [raíz del proyecto](#local). No incluya `.env` en el control de versiones.

### Comprobar y borrar credenciales {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` funciona con cualquiera de los dos tipos de credencial y finaliza con el código 4 si se rechazan las credenciales. `status` puede finalizar con el código 0 aunque ninguna credencial funcione, así que use `whoami` para comprobar el acceso. Cerrar sesión no elimina las variables de entorno ni modifica `.env`.

### Orden de precedencia de las credenciales {#credential-precedence}

Se utiliza la primera fuente disponible:

1. Los parámetros `--api-key` y `--api-secret`
2. `.clickhouse/credentials.json` en la raíz del proyecto
3. Variables de entorno exportadas
4. Variables de `.env` en el directorio actual o, en su defecto, en la raíz del proyecto
5. Tokens OAuth globales

Añada `--debug` a cualquier comando `cloud` para mostrar en stderr la fuente de credenciales seleccionada y la URL de la API:

```bash
clickhousectl cloud clickhouse list --debug
```

### Seleccionar una organización {#organizations}

Los comandos que operan a nivel de organización la seleccionan automáticamente solo cuando sus credenciales dan acceso a exactamente una. En caso contrario, indique `--org-id` o `--org-name` con el nombre exacto; si no indica ninguno de los dos, el comando finaliza con el código 2 y muestra el ID y el nombre de cada organización:

```bash
clickhousectl cloud org list
clickhousectl cloud clickhouse list --org-id <org-id>
clickhousectl cloud clickhouse list --org-name "My Org"
```

La mayoría de los comandos de recursos aceptan un ID posicional o un `--name` exacto. Consulte [autenticación y acceso](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md) para obtener información sobre permisos, claves restringidas y la limpieza al cerrar sesión.

## Cloud {#cloud}

Los comandos de Cloud llaman a la [API de ClickHouse Cloud](/es/products/cloud/features/admin-features/api/api-overview). Las solicitudes de creación y actualización devuelven una respuesta en cuanto la API las acepta, por lo que debe sondear `get` hasta que el recurso alcance el estado que necesite.

### Servicios {#services}

`cloud clickhouse` administra los servicios de ClickHouse Cloud. `cloud ch` es su forma abreviada, y el nombre anterior, `cloud service`, sigue funcionando como alias.

```bash
clickhousectl cloud clickhouse create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud clickhouse create --name app-dev \
  --ip-allow 203.0.113.10/32 --dotenv .env.local          # Password goes only to the file
clickhousectl cloud clickhouse list
clickhousectl cloud clickhouse get <service-id>
clickhousectl cloud clickhouse start <service-id>
clickhousectl cloud clickhouse stop <service-id>
clickhousectl cloud clickhouse wake <service-id>             # Wake an idle service
clickhousectl cloud clickhouse reset-password <service-id>
clickhousectl cloud clickhouse delete <service-id>           # Must be stopped; --force stops it first
```

Guarde la contraseña inicial que se muestra al crear el servicio; solo se devuelve una vez. Con `--dotenv [file]` (por defecto, `.env`), se escribe únicamente en ese archivo, no en el terminal ni en la salida JSON. La operación de creación devuelve el control antes de que finalice el aprovisionamiento, por lo que debe repetir `get` hasta que el estado sea `running`. **Si omite `--ip-allow`, se permiten todas las IP (`0.0.0.0/0`).** Las entradas aceptan el formato `IP_OR_CIDR=DESCRIPTION`. `--region` acepta cualquier ID de región, incluidas las regiones privadas, y Cloud lo valida. Restaure una copia de seguridad en un servicio nuevo con `--backup-id`, o despliegue un servicio en infraestructura BYOC con `--byoc-id`.

Conéctese a un servicio en ejecución:

```bash
clickhousectl cloud clickhouse client <service-id>                     # Interactive clickhouse client
clickhousectl cloud clickhouse client --name analytics -q "SELECT version()"
clickhousectl cloud clickhouse dotenv <service-id> --local             # Write .env.local, without a password
```

`client` abre `clickhouse client` mediante el protocolo TLS nativo e inicia sesión a través del navegador con su usuario de Cloud, por lo que no se necesita la contraseña del servicio. Requiere tener instalado ClickHouse 25.12 o posterior (`clickhousectl local install latest`) y que haya una persona frente al navegador, así que utilice [`query`](#query-api) en CI y en agentes. `dotenv` escribe `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_HTTP_PORT`, `CLICKHOUSE_USER` y `CLICKHOUSE_SECURE` y reemplaza únicamente esas claves, de modo que se conserva cualquier contraseña escrita por `create --dotenv`.

Actualice, escale y configure un servicio:

```bash
clickhousectl cloud clickhouse update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud clickhouse update <service-id> --deletion-protection true
clickhousectl cloud clickhouse profile list --region us-east-1
clickhousectl cloud clickhouse scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud clickhouse scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud clickhouse scale <service-id> --profile v1-highmem-s
clickhousectl cloud clickhouse settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud clickhouse upgrade-window set <service-id> --weekday 0 --start-hour 6
```

La memoria por réplica debe ser un múltiplo de 4 GB, con un máximo de 120 GB en los servicios gratuitos y de 356 GB en los de pago, y hasta 50 réplicas. Los límites de la organización y del almacén pueden reducir estos valores. El escalado automático horizontal requiere que la funcionalidad correspondiente esté habilitada en la organización. `scale --profile` cambia el perfil de instancia en las organizaciones Enterprise y BYOC. `update` modifica únicamente los indicadores que se le pasan.

La protección contra la eliminación (`create --deletion-protection` o `update --deletion-protection true|false`) hace que `delete` se niegue a eliminar el servicio y devuelva el código de error `deletion_protected`, incluso con `--force`; desactívela antes de eliminarlo.

Los demás grupos de comandos de servicio son `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (Beta), `jwt-provider` (Beta, nivel Enterprise), `snapshot` (Beta), `private-endpoint`, `query-endpoint`, `backup-config` y `prometheus`. Consulte [Crear y operar un servicio de Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md).

### API de consultas {#query-api}

`cloud clickhouse query` ejecuta una sola sentencia SQL a través de HTTP, sin necesidad de un binario `clickhouse` local ni de la contraseña del servicio:

```bash
clickhousectl cloud clickhouse query <service-id> --query "SELECT version()"
clickhousectl cloud clickhouse query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud clickhouse query <service-id>
```

* **OAuth** ejecuta la consulta con tu identity, con acceso SQL de solo lectura. No se vincula nada al servicio.
* **Clave de API:** la consulta siempre usa la clave de API activa. Si es necesario, clickhousectl añade esa clave al endpoint de la API de consultas del servicio y, si no existe ninguno, crea el endpoint con los roles `sql_console_admin`. Se conservan los roles, orígenes y demás vinculaciones de claves existentes, y no se crea ninguna clave nueva. Pasa `--no-auto-enable` para que, en cambio, el comando falle.

La vinculación es una operación de escritura, por lo que una clave de API de solo lectura no puede vincularse a sí misma: la consulta termina con código 1 y `query_key_bind_forbidden`, y no se modifica nada. Vincúlala una sola vez con una clave que tenga acceso de escritura mediante `query-endpoint create <service-id> --role <role> --open-api-key <key-id>` (añadiendo `--allowed-origins '*'` si el servicio aún no tiene endpoint).

La API de consultas acepta una sola sentencia por solicitud. Puede agotarse el tiempo de espera tras unos 30 segundos mientras el SQL sigue ejecutándose, así que comprueba el resultado antes de reintentar una escritura. Usa [`cloud clickhouse client`](#services) para scripts con varias sentencias, cargas masivas y consultas largas. La lista de permitidos de IP del servicio restringe las conexiones directas, pero no la ruta de la API de consultas que pasa por el proxy. Consultar un servicio inactivo lo reactiva; un servicio detenido debe iniciarse con `cloud clickhouse start`.

Administra el endpoint de la API de consultas del servicio, los puntos de conexión SQL con nombre y las consultas guardadas:

```bash
clickhousectl cloud clickhouse query-endpoint get <service-id>
clickhousectl cloud clickhouse query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` reemplaza los roles de cada clave vinculada al endpoint. Consulte [Comportamiento de SQL y de la API de consultas](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md).

### Managed Postgres {#postgres-services}

`cloud postgres` (alias `cloud pg`) gestiona [ClickHouse Managed Postgres](/es/products/managed-postgres/overview). La compatibilidad con GCP está en vista previa privada.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> --ha-type sync --standby-count 2
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres update <postgres-id> --deletion-protection true
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

Los tamaños de AWS incluyen `m6gd.large`, `c6gd.xlarge` y `r6gd.xlarge`. En GCP, pase `--provider gcp` con una región de GCP y un tamaño como `c4-standard-lssd-4`.

Guarde la contraseña y la cadena de conexión que devuelve `create`. Las respuestas posteriores de `get` nunca devuelven credenciales, y `reset-password` es la única forma de obtener otras nuevas. Conéctese con `psql` usando `sslmode=verify-full` y el archivo de la CA.

**Si omite los indicadores de acceso al ejecutar create, se permiten todas las direcciones IPv4 e IPv6 en Postgres (5432) y PgBouncer (6432).** Pase un `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` por cada regla, o `--block-public-access` para no definir ninguna regla. En cuanto pase una regla, solo se aplican las reglas indicadas.

`--standby-count` establece el número de réplicas en espera en caliente en `create` o `update`: `--ha-type none` admite 0, `async` admite 1 y `sync` admite 1 o 2. Con la protección contra eliminación activada, la API rechaza `delete` hasta que establezca `--deletion-protection false`, en las organizaciones que disponen de esta funcionalidad. Para la conectividad privada en AWS, `private-endpoint` (create, get, update, delete) administra un servicio de punto de conexión de PrivateLink (Beta); apruebe cada punto de conexión de VPC con `private-endpoint update --add-vpc-endpoint` para que pueda conectarse.

Supervisar y recuperar:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` solo acepta OAuth, por lo que falla mientras haya activa una fuente de clave de API con mayor prioridad. `metrics`, `slow-queries` y `prometheus` cubren la monitorización; `logs`, `metrics`, `slow-queries` y `backup list` también aceptan `--name` en lugar del ID. `restore` copia las reglas de acceso IPv4 actuales del servicio de origen en el servicio restaurado, a menos que se indique `--ip-allow` o `--block-public-access`. Las restauraciones y las réplicas se devuelven sin contraseña. `promote` y `switchover` finalizan en cuanto se aceptan; tras un promote, sondee `postgres get --json` hasta que la réplica indique `isPrimary: true`. Consulte la [Guía de Managed Postgres](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md).

### ClickPipes {#clickpipes}

`cloud clickpipe` ingesta datos desde almacenamiento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB y BigQuery. Para la creación y el descubrimiento del esquema se necesitan una clave de API y un servicio de destino en ejecución. Cada fuente tiene su propio subcomando `clickpipe create <source>`; ejecútelo con `--help` para consultar sus indicadores.

Cargue archivos desde S3 con un rol de IAM. Primero descubra el esquema y revíselo; después, cree la canalización a partir de la salida guardada del descubrimiento:

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" --json > discovery.json
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --columns-from discovery.json
```

`--columns-from` convierte los campos descubiertos en columnas de destino, así que edite primero el archivo para quitar los campos que no necesite. Para crear ClickPipes de almacenamiento de objetos, Kafka, Kinesis y Pub/Sub se requiere `--columns-from`, al menos un `--column name:type`, o ambos; `--column` añade columnas a las que se obtienen del archivo.

Replique Postgres con CDC. La verificación TLS está habilitada de forma predeterminada; para una fuente de Managed Postgres, exporte su CA y pásela como parámetro:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud clickhouse query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` crea tablas `ReplacingMergeTree`, por lo que debe consultar el estado actual con `FINAL WHERE _peerdb_is_deleted = 0`. Las operaciones de creación para Postgres y MySQL aceptan `--use-json-native-format true` para almacenar las columnas JSON con el tipo nativo `JSON` de ClickHouse en lugar de `String` (ClickHouse 25.3+, con la funcionalidad habilitada para la organización). Una canalización de Kafka sigue el mismo procedimiento que el almacenamiento de objetos: ejecute `clickpipe schema-discover kafka` con los mismos indicadores de origen y, a continuación, pase las columnas con `--column` o `--columns-from`:

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

Las canalizaciones de BigQuery realizan una instantánea de forma predeterminada. Para CDC, indique `--replication-mode cdc`, un `--replication-method` y, para cada tabla, una columna de marca de agua o una función de eventos en `--table-mapping-json`; programe las sincronizaciones con `--sync-cron` o `--sync-interval-seconds`. Para gestionar las canalizaciones existentes:

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

Las canalizaciones CDC deben estar en estado `Paused` antes de ejecutar `update`: detenga la canalización, sondee `get` hasta que esté en `Paused` y, a continuación, actualícela. El servicio puede reanudar la canalización durante la actualización, así que ejecute `start` solo si `get` sigue mostrando `Paused`. `--start-paused` está disponible para almacenamiento de objetos, Kafka, Kinesis y Pub/Sub. Otros grupos de comandos son `cdc-scaling`, `context get` (disponibilidad de la workload identity de GCP y entidad de seguridad) y `reverse-private-endpoint`. Consulte la [guía de ClickPipes](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) y la [referencia de configuración de ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md).

### ClickStack {#clickstack}

`cloud clickstack` administra fuentes, dashboards, alertas, webhooks, búsquedas guardadas y roles en un servicio existente de [Self-managed ClickHouse Observability](/es/clickstack/self-configured/deployment/managed). Los recursos se definen como archivos JSON (`--file`, o `-` para stdin). Las operaciones de lectura admiten OAuth; las de escritura requieren una clave de API.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**Cada actualización de ClickStack reemplaza el recurso completo.** Guarde el estado actual con `get --json` y envíe la definición completa, no solo los campos modificados. Consulte la [guía de ClickStack](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md).

### UDFs en Cloud {#cloud-udfs}

`cloud udf` gestiona las UDF ejecutables de ámbito organizativo, sus versiones y sus vinculaciones a servicios. `deploy` carga el directorio que probó con `local udf`, espera a que finalice la build, vincula esa versión y espera a que se complete su despliegue:

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud clickhouse query <service-id> --query "SELECT my_udf(1)"

Estos comandos devuelven el control en cuanto se acepta la solicitud; sondee el estado con `udf get` y `udf attachment get`. Las operaciones de lectura admiten OAuth; las de escritura requieren una clave de API. ### Organizaciones y acceso {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

Los subcomandos de `cloud org` aceptan `--org-id`, nunca un ID posicional. `org usage` abarca como máximo 31 días. `org` también incluye `quota`, `balance`, `notification-types`, `role` (roles personalizados de la organización), `preview` (para listar y activar o desactivar funciones en versión preliminar, Beta) y `byoc` (infraestructura BYOC, incluido `byoc access` para controlar cuándo puede acceder a ella el personal de ClickHouse, Beta). Las notificaciones están en Beta.

Gestione miembros, invitaciones y claves de API:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

`member notification-settings` (Beta) muestra y actualiza las sobrescrituras de notificaciones del propio miembro. **Si se omite `--ip-allow` en `key create`, se deniega todo acceso a la red**, a diferencia de lo que ocurre al crear un servicio. El secreto se muestra una sola vez. `key list` devuelve una sola página, salvo que se especifique `--all`. En `key update`, los ajustes de los indicadores omitidos se mantienen, mientras que `--clear-expiry`, `--clear-roles` y `--clear-ip-allow` los eliminan.

## Salida JSON {#json-output}

Los comandos que devuelven datos estructurados aceptan `--json`, incluidos los comandos locales, los de Cloud y los de `skills`, `update` y `telemetry`:

```bash
clickhousectl cloud clickhouse list --json
clickhousectl cloud key list --all --json
clickhousectl local clickhouse list --json
```

Cuando la CLI detecta un agente de programación (como Claude Code, Cursor, Codex, Gemini CLI, Goose o Devin, o cualquier herramienta que establezca `AI_AGENT`), selecciona JSON automáticamente. Los clientes SQL y nativos conservan sus propios formatos: `cloud clickhouse query` devuelve `JSONEachRow` en modo JSON, y la salida de `local client` es siempre nativa. Los scripts que analicen la salida de las consultas deben especificar `--format` explícitamente. Para mantener la salida legible para personas cuando se detecta un agente, establezca `CLICKHOUSECTL_AUTO_JSON=0`; si se especifica `--json` explícitamente, se sigue seleccionando JSON.

Los comandos asíncronos de Cloud, como `clickhouse create`, `postgres create` y `clickpipe start`, añaden a su salida JSON un objeto `next` que indica cómo realizar el sondeo: `command` (con los ID resueltos y `--org-id`), el campo `field` que se debe supervisar, los valores de `until` que indican que la operación ha finalizado, los valores de `fail_on` y un valor sugerido para `interval_seconds`. El comando devuelve el control en cuanto la API acepta la solicitud, sin esperar a que finalice la operación.

En modo JSON, los errores en tiempo de ejecución se envían a stderr como un objeto con un `code` estable y un `message`:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

Base la lógica condicional en `error.code`, no en el mensaje. Los errores de uso se muestran como texto, con código de salida 2, y no se envía nada. Consulte [automatización y contratos de salida](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md) para conocer las estructuras de salida y los códigos de error.

## Códigos de salida {#exit-codes}

| Código | Significado                                                                                                                                                                   |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`    | Éxito. En las operaciones asíncronas de Cloud, la solicitud se ha aceptado, pero aún no se ha completado                                                                      |
| `1`    | Error, incluida una respuesta HTTP 403 que rechaza una solicitud (código `http_4xx`)                                                                                          |
| `2`    | Error de uso, incluidos valores no válidos de los indicadores y entradas que se comprueban tras el análisis, pero que nunca pueden procesarse correctamente; no se envía nada |
| `3`    | Se canceló una solicitud interactiva, como el selector de `skills`                                                                                                            |
| `4`    | Autenticación requerida o rechazada, incluidos los intentos de escritura con OAuth                                                                                            |

`local client`, `local postgres client` y otras operaciones que delegan la ejecución en clientes nativos devuelven el código de salida del propio cliente.

## Habilidades para agentes {#skills}

Instale el [paquete oficial ClickHouse agent skills](https://github.com/ClickHouse/agent-skills) en sus agentes de programación:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

Las habilidades se instalan de forma predeterminada en el proyecto actual, o en su directorio personal con `--global`. El directorio compartido `.agents/skills/` siempre se incluye. Si no dispone de una terminal, debe especificar `--agent`, `--all` o `--detected-only`. Ejecute `clickhousectl skills --help` para consultar los nombres de los agentes compatibles.

## Búsqueda y comentarios {#search-and-feedback}

```bash
clickhousectl search ip allow                   # Find commands and flags by keyword
clickhousectl search idle timeout --limit 10
clickhousectl feedback "cloud clickhouse create should accept a --wait flag"
```

`search <words>` busca coincidencias en los nombres de comandos, las descripciones, los indicadores y el contexto del agente, y enumera los comandos que mejor coinciden (5 de forma predeterminada). Una búsqueda sin coincidencias finaliza con el código de salida 0 y sin resultados.

`feedback` envía un mensaje breve (de 500 caracteres como máximo) al equipo de clickhousectl, sin solicitar información ni confirmación. Úselo para indicar qué no pudo hacer la CLI o qué esperaba de ella. Coloque opciones como `--json` antes del mensaje y no incluya credenciales, SQL, nombres de host ni datos personales. Si utiliza credenciales de Cloud, el mensaje incluye los ID de las organizaciones a las que pertenecen esas credenciales. Consulte [qué envía feedback](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/feedback.md).

## Autoactualización {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

`update` reemplaza las instalaciones realizadas mediante el script de instalación, una descarga o Cargo. En el caso de las instalaciones con npm, uv, pipx y pip, termina con el código de salida 1 y muestra el comando de actualización del gestor de paquetes que debe ejecutar en su lugar.

La CLI también busca actualizaciones en segundo plano, como máximo una vez cada 24 horas (si la comprobación falla, se reintenta al cabo de una hora), y muestra un aviso cuando hay una versión más reciente disponible. Establezca `CLICKHOUSECTL_NO_UPDATE_CHECK=1` para desactivar la comprobación y el aviso.

## Telemetría {#telemetry}

`clickhousectl` recopila datos de uso anónimos para orientar el desarrollo. En la primera ejecución se muestra un aviso y no se envía nada; la recopilación comienza en una ejecución posterior, a menos que la desactive.

Cada evento contiene:

* La ruta del comando y los **nombres** de los indicadores y argumentos proporcionados explícitamente, nunca sus valores
* El resultado y el código de salida
* Si se escribe mal un comando, el nombre del comando o del indicador sugerido por la CLI, nunca lo que escribió
* En caso de fallos durante la ejecución, categorías predefinidas: la etapa y el tipo de fallo, un código de estado HTTP incluido en una lista de permitidos y las categorías de reintento, estado de aprovisionamiento y duración
* La versión de la CLI, el SO y la arquitectura, si se ejecuta en CI y el agente de programación detectado

Nunca se registran los valores de los argumentos, el SQL, las credenciales, los identificadores de recursos, los argumentos que aparecen después de `--` ni los mensajes de error. No se utiliza ningún ID de instalación ni de dispositivo.

Para desactivar la recopilación:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

Establezca `CHCTL_TELEMETRY_DEBUG=1` para mostrar la carga útil en stderr sin enviar nada. Desactivar la telemetría no bloquea [`feedback`](#search-and-feedback), que solo envía datos cuando lo ejecuta. Consulte los [detalles sobre la telemetría](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md).
