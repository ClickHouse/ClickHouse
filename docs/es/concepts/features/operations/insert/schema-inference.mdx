ClickHouse puede determinar automáticamente la estructura de los datos de entrada en casi todos los [formatos de entrada](/es/reference/formats/index) compatibles.
En este documento se describe cuándo se utiliza la inferencia del esquema, cómo funciona con los distintos formatos de entrada y qué ajustes
permiten controlarla.

## Uso {#usage}

La inferencia del esquema se utiliza cuando ClickHouse necesita leer datos en un formato específico y se desconoce su estructura.

## Funciones de tabla [file](/es/reference/functions/table-functions/file), [s3](/es/reference/functions/table-functions/s3), [url](/es/reference/functions/table-functions/url), [hdfs](/es/reference/functions/table-functions/hdfs), [azureBlobStorage](/es/reference/functions/table-functions/azureBlobStorage). {#table-functions-file-s3-url-hdfs-azureblobstorage}

Estas funciones de tabla tienen el argumento opcional `structure`, que indica la estructura de los datos de entrada. Si este argumento no se especifica o se establece en `auto`, la estructura se inferirá a partir de los datos.

**Ejemplo:**

Supongamos que tenemos en el directorio `user_files` un archivo `hobbies.jsonl` en formato JSONEachRow con el siguiente contenido:

```json
{"id" :  1, "age" :  25, "name" :  "Josh", "hobbies" :  ["football", "cooking", "music"]}
{"id" :  2, "age" :  19, "name" :  "Alan", "hobbies" :  ["tennis", "art"]}
{"id" :  3, "age" :  32, "name" :  "Lana", "hobbies" :  ["fitness", "reading", "shopping"]}
{"id" :  4, "age" :  47, "name" :  "Brayan", "hobbies" :  ["movies", "skydiving"]}
```

ClickHouse puede leer estos datos sin necesidad de especificar su estructura:

```sql
SELECT * FROM file('hobbies.jsonl')
```

```response
┌─id─┬─age─┬─name───┬─hobbies──────────────────────────┐
│  1 │  25 │ Josh   │ ['football','cooking','music']   │
│  2 │  19 │ Alan   │ ['tennis','art']                 │
│  3 │  32 │ Lana   │ ['fitness','reading','shopping'] │
│  4 │  47 │ Brayan │ ['movies','skydiving']           │
└────┴─────┴────────┴──────────────────────────────────┘
```

Nota: el formato `JSONEachRow` se determinó automáticamente a partir de la extensión de archivo `.jsonl`.

Puede consultar la estructura determinada automáticamente mediante la consulta `DESCRIBE`:

```sql
DESCRIBE file('hobbies.jsonl')
```

```response
┌─name────┬─type────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ id      │ Nullable(Int64)         │              │                    │         │                  │                │
│ age     │ Nullable(Int64)         │              │                    │         │                  │                │
│ name    │ Nullable(String)        │              │                    │         │                  │                │
│ hobbies │ Array(Nullable(String)) │              │                    │         │                  │                │
└─────────┴─────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## Motores de tablas [File](/es/reference/engines/table-engines/special/file), [S3](/es/reference/engines/table-engines/integrations/s3), [URL](/es/reference/engines/table-engines/special/url), [HDFS](/es/reference/engines/table-engines/integrations/hdfs), [azureBlobStorage](/es/reference/engines/table-engines/integrations/azureBlobStorage) {#table-engines-file-s3-url-hdfs-azureblobstorage}

Si no se especifica la lista de columnas en la consulta `CREATE TABLE`, la estructura de la tabla se inferirá automáticamente a partir de los datos.

**Ejemplo:**

Usemos el archivo `hobbies.jsonl`. Podemos crear una tabla con el motor `File` a partir de los datos de este archivo:

```sql
CREATE TABLE hobbies ENGINE=File(JSONEachRow, 'hobbies.jsonl')
```

```response

```

```sql
SELECT * FROM hobbies
```


## clickhouse-local {#clickhouse-local}

`clickhouse-local` tiene un parámetro opcional `-S/--structure` que define la estructura de los datos de entrada. Si este parámetro no se especifica o se establece en `auto`, la estructura se inferirá a partir de los datos.

**Ejemplo:**

Usemos el archivo `hobbies.jsonl`. Podemos consultar los datos de este archivo con `clickhouse-local`:

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='DESCRIBE TABLE hobbies'
```

```response
id    Nullable(Int64)
age    Nullable(Int64)
name    Nullable(String)
hobbies    Array(Nullable(String))
```

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='SELECT * FROM hobbies'
```

```response

2    19    Alan    ['tennis','art']
3    32    Lana    ['fitness','reading','shopping']
4    47    Brayan    ['movies','skydiving']
```

## Uso de la estructura de la tabla de inserción {#using-structure-from-insertion-table}

Cuando se usan las funciones de tabla `file/s3/url/hdfs` para insertar datos en una tabla,
existe la opción de usar la estructura de la tabla de inserción en lugar de extraerla de los datos.
Esto puede mejorar el rendimiento de la inserción, ya que la inferencia del esquema puede llevar algo de tiempo. Además, resulta útil cuando la tabla tiene un esquema optimizado, ya que así
no se realiza ninguna conversión entre tipos.

Existe un parámetro de configuración especial, [use&#95;structure&#95;from&#95;insertion&#95;table&#95;in&#95;table&#95;functions](/es/reference/settings/session-settings/use#use_structure_from_insertion_table_in_table_functions),
que controla este comportamiento. Admite 3 valores posibles:

* 0 - la función de tabla extrae la estructura de los datos.
* 1 - la función de tabla usa la estructura de la tabla de inserción.
* 2 - ClickHouse determina automáticamente si es posible usar la estructura de la tabla de inserción o si debe recurrir a la inferencia del esquema. Valor predeterminado.

**Ejemplo 1:**

Creemos la tabla `hobbies1` con la siguiente estructura:

```sql
CREATE TABLE hobbies1
(
    `id` UInt64,
    `age` LowCardinality(UInt8),
    `name` String,
    `hobbies` Array(String)
)
ENGINE = MergeTree
ORDER BY id;
```

A continuación, inserte los datos del archivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies1 SELECT * FROM file(hobbies.jsonl)
```

En este caso, todas las columnas del archivo se insertan en la tabla sin cambios, por lo que ClickHouse usará la estructura de la tabla de inserción en lugar de la inferencia del esquema.

**Ejemplo 2:**

Creemos la tabla `hobbies2` con la siguiente estructura:

```sql
CREATE TABLE hobbies2
(
  `id` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

E inserta los datos del archivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies2 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

En este caso, todas las columnas de la consulta `SELECT` están presentes en la tabla, por lo que ClickHouse utilizará la estructura de la tabla de inserción.
Tenga en cuenta que esto solo funcionará con formatos de entrada que admitan la lectura de un subconjunto de columnas, como JSONEachRow, TSKV, Parquet, etc. (por lo que, por ejemplo, no funcionará con el formato TSV).

**Ejemplo 3:**

Creemos la tabla `hobbies3` con la siguiente estructura:

```sql
CREATE TABLE hobbies3
(
  `identifier` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY identifier;
```

A continuación, inserta los datos del archivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies3 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

En este caso, la columna `id` se usa en la consulta `SELECT`, pero la tabla no tiene esta columna (tiene una columna llamada `identifier`),
por lo que ClickHouse no puede usar la estructura de la tabla de inserción y se recurrirá a la inferencia del esquema.

**Ejemplo 4:**

Creemos la tabla `hobbies4` con la siguiente estructura:

```sql
CREATE TABLE hobbies4
(
  `id` UInt64,
  `any_hobby` Nullable(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

E inserte los datos del archivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies4 SELECT id, empty(hobbies) ? NULL : hobbies[1] FROM file(hobbies.jsonl)
```

En este caso, en la consulta `SELECT` se realizan algunas operaciones sobre la columna `hobbies` para insertarla en la tabla, por lo que ClickHouse no puede usar la estructura de la tabla de inserción y se recurrirá a la inferencia del esquema.

## Caché de inferencia del esquema {#schema-inference-cache}

En la mayoría de los formatos de entrada, la inferencia del esquema lee parte de los datos para determinar su estructura, y este proceso puede llevar cierto tiempo.
Para evitar inferir el mismo esquema cada vez que ClickHouse lee los datos del mismo archivo, el esquema inferido se almacena en caché y, cuando se vuelve a acceder al mismo archivo, ClickHouse usa el esquema de la caché.

Existen ajustes específicos que controlan esta caché:

* `schema_inference_cache_max_elements_for_{file/s3/hdfs/url/azure}`: el número máximo de esquemas almacenados en caché para la función de tabla correspondiente. El valor predeterminado es `4096`. Estos ajustes deben establecerse en la configuración del servidor.
* `schema_inference_use_cache_for_{file,s3,hdfs,url,azure}`: permite activar o desactivar el uso de la caché para la inferencia del esquema. Estos ajustes pueden usarse en consultas.

El esquema del archivo puede cambiar si se modifican los datos o los ajustes de formato.
Por ello, la caché de inferencia del esquema identifica cada esquema por la fuente del archivo, el nombre del formato, los ajustes de formato utilizados y la hora de la última modificación del archivo.

Nota: es posible que algunos archivos a los que se accede por URL mediante la función de tabla `url` no incluyan información sobre la hora de la última modificación; para estos casos existe un parámetro de configuración especial,
`schema_inference_cache_require_modification_time_for_url`. Si se desactiva, se puede usar el esquema de la caché para dichos archivos aunque no se disponga de la hora de la última modificación.

También existe la tabla del sistema [schema&#95;inference&#95;cache](/es/reference/system-tables/schema_inference_cache), que contiene todos los esquemas actualmente en caché, y la consulta del sistema `SYSTEM CLEAR SCHEMA CACHE [FOR File/S3/URL/HDFS]`,
que permite vaciar la caché de esquemas para todas las fuentes o para una fuente concreta.

## Formatos de texto {#text-formats}

En los formatos de texto, ClickHouse lee los datos fila por fila, extrae los valores de columna según el formato
y, a continuación, utiliza analizadores sintácticos recursivos y heurísticas para determinar el tipo de cada valor. El número máximo de filas y bytes que se leen de los datos durante la inferencia del esquema
se controla mediante los ajustes `input_format_max_rows_to_read_for_schema_inference` (25000 de forma predeterminada) y `input_format_max_bytes_to_read_for_schema_inference` (32Mb de forma predeterminada).
De forma predeterminada, todos los tipos inferidos son [Nullable](/es/reference/data-types/nullable), pero puede cambiarlo mediante el parámetro de configuración `schema_inference_make_columns_nullable` (consulte los ejemplos en la sección de [ajustes](#settings-for-text-formats)).

### Formatos JSON {#json-formats}

En los formatos JSON, ClickHouse analiza los valores según la especificación JSON y, a continuación, intenta determinar el tipo de datos más adecuado para ellos.

Veamos cómo funciona, qué tipos se pueden inferir y qué ajustes específicos se pueden usar en los formatos JSON.

**Ejemplos**

### CSV {#csv}

En el formato CSV, ClickHouse extrae los valores de columna de la fila según los delimitadores. ClickHouse espera que todos los tipos, excepto los números y las cadenas, estén entre comillas dobles. Si el valor está entre comillas dobles, ClickHouse intenta analizar
los datos entre comillas mediante el analizador sintáctico recursivo y, a continuación, intenta encontrar el tipo de datos más adecuado para ellos. Si el valor no está entre comillas dobles, ClickHouse intenta analizarlo como un número
y, si el valor no es un número, ClickHouse lo trata como una cadena.

Si no desea que ClickHouse intente determinar tipos complejos mediante analizadores sintácticos y heurísticas, puede desactivar el parámetro de configuración `input_format_csv_use_best_effort_in_schema_inference`
y ClickHouse tratará todas las columnas como cadenas.

Si el parámetro de configuración `input_format_csv_detect_header` está habilitado, ClickHouse intentará detectar el encabezado con los nombres de columnas (y posiblemente los tipos) al inferir el esquema. Este parámetro de configuración está habilitado de forma predeterminada.

### TSV/TSKV {#tsv-tskv}

En los formatos TSV/TSKV, ClickHouse extrae el valor de la columna de la fila según los delimitadores tabulares y, a continuación, analiza el valor extraído mediante
el analizador sintáctico recursivo para determinar el tipo más adecuado. Si no se puede determinar el tipo, ClickHouse trata este valor como cadena.

Si no desea que ClickHouse intente determinar tipos complejos mediante analizadores sintácticos y heurísticas, puede desactivar el parámetro de configuración `input_format_tsv_use_best_effort_in_schema_inference`
y ClickHouse tratará todas las columnas como cadenas.

### Template {#template}

En el formato Template, ClickHouse extrae primero todos los valores de columna de la fila según la plantilla especificada y luego intenta inferir el
tipo de datos de cada valor según su regla de escape.

**Ejemplo**

Supongamos que tenemos un archivo `resultset` con el siguiente contenido:

```bash
<result_before_delimiter>
${data}<result_after_delimiter>
```

Y un archivo `row_format` con el siguiente contenido:

```text
<row_before_delimiter>${column_1:CSV}<field_delimiter_1>${column_2:Quoted}<field_delimiter_2>${column_3:JSON}<row_after_delimiter>
```

A continuación, podemos ejecutar las siguientes consultas:

```sql
SET format_template_rows_between_delimiter = '<row_between_delimiter>\n',
       format_template_row = 'row_format',
       format_template_resultset = 'resultset_format'

DESC format(Template, $$<result_before_delimiter>
```

### Regexp {#regexp}

Al igual que en Template, en el formato Regexp ClickHouse extrae primero todos los valores de columna de la fila según la expresión regular especificada y luego intenta inferir

### Configuración de los formatos de texto {#settings-for-text-formats}

#### input_format_max_rows_to_read_for_schema_inference/input_format_max_bytes_to_read_for_schema_inference {#input-format-max-rows-to-read-for-schema-inference}

Estos ajustes controlan la cantidad de datos que se leen durante la inferencia del esquema.
Cuantas más filas o bytes se lean, más tiempo llevará la inferencia del esquema, pero mayor será la probabilidad de
determinar correctamente los tipos (especialmente cuando los datos contienen muchos NULL).

Valores predeterminados:

* `25000` para `input_format_max_rows_to_read_for_schema_inference`.
* `33554432` (32 Mb) para `input_format_max_bytes_to_read_for_schema_inference`.

#### column_names_for_schema_inference {#column-names-for-schema-inference}

Lista de nombres de columnas que se utilizarán en la inferencia del esquema para formatos sin nombres de columnas explícitos. Los nombres especificados se utilizarán en lugar de los predeterminados `c1,c2,c3,...`. Formato: `column1,column2,column3,...`.

**Ejemplo**

```sql
DESC format(TSV, 'Hello, World!    42    [1, 2, 3]') settings column_names_for_schema_inference = 'str,int,arr'
```

#### schema_inference_make_columns_nullable $ {#schema-inference-make-columns-nullable}

Controla si los tipos inferidos se convierten en `Nullable` durante la inferencia del esquema para formatos sin información sobre la admisión de valores NULL. Valores posibles:

* 0 - el tipo inferido nunca será `Nullable`,
* 1 - todos los tipos inferidos serán `Nullable`,

## Formatos autodescriptivos {#self-describing-formats}

Los formatos autodescriptivos incluyen información sobre la estructura de los datos en los propios datos,
ya sea mediante una cabecera con una descripción, un árbol binario de tipos o algún tipo de tabla.
Para inferir automáticamente un esquema a partir de archivos en estos formatos, ClickHouse lee la parte de los datos que contiene
información sobre los tipos y la convierte en el esquema de la tabla de ClickHouse.

### Formatos con el sufijo -WithNamesAndTypes {#formats-with-names-and-types}

ClickHouse admite algunos formatos de texto con el sufijo -WithNamesAndTypes. Este sufijo indica que los datos contienen dos filas adicionales con los nombres y tipos de las columnas antes de los datos propiamente dichos.
Durante la inferencia del esquema de estos formatos, ClickHouse lee las dos primeras filas y extrae los nombres y tipos de las columnas.

**Ejemplo**

```sql
DESC format(TSVWithNamesAndTypes,
$$num    str    arr
UInt8    String    Array(UInt8)
42    Hello, World!    [1,2,3]
$$)
```

```response
┌─name─┬─type─────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ num  │ UInt8        │              │                    │         │                  │                │
│ str  │ String       │              │                    │         │                  │                │
│ arr  │ Array(UInt8) │              │                    │         │                  │                │
└──────┴──────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Avro {#avro}

En el formato Avro, ClickHouse lee su esquema a partir de los datos y lo convierte a un esquema de ClickHouse mediante las siguientes correspondencias de tipos:

| Tipo de datos de Avro              | Tipo de datos de ClickHouse                                           |
| ---------------------------------- | --------------------------------------------------------------------- |
| `boolean`                          | [Bool](/es/reference/data-types/boolean)                                 |
| `int`                              | [Int32](/es/reference/data-types/int-uint)                               |
| `int (date)` *                     | [Date32](/es/reference/data-types/date32)                                |
| `long`                             | [Int64](/es/reference/data-types/int-uint)                               |
| `float`                            | [Float32](/es/reference/data-types/float)                                |
| `double`                           | [Float64](/es/reference/data-types/float)                                |
| `bytes`, `string`                  | [String](/es/reference/data-types/string)                                |
| `fixed`                            | [FixedString(N)](/es/reference/data-types/fixedstring)                   |
| `enum`                             | [Enum](/es/reference/data-types/enum)                                    |
| `array(T)`                         | [Array(T)](/es/reference/data-types/array)                               |
| `union(null, T)`, `union(T, null)` | [Nullable(T)](/es/reference/data-types/date)                             |
| `null`                             | [Nullable(Nothing)](/es/reference/data-types/special-data-types/nothing) |
| `string (uuid)` *                  | [UUID](/es/reference/data-types/uuid)                                    |
| `binary (decimal)` *               | [Decimal(P, S)](/es/reference/data-types/decimal)                        |

## Formatos binarios fuertemente tipados {#strong-typed-binary-formats}

En estos formatos, cada valor serializado contiene información sobre su tipo (y posiblemente sobre su nombre), pero no hay información sobre la table en su conjunto.
Durante la inferencia del esquema para estos formatos, ClickHouse lee los datos fila por fila (hasta `input_format_max_rows_to_read_for_schema_inference` filas o `input_format_max_bytes_to_read_for_schema_inference` bytes) y extrae
de los datos el tipo (y posiblemente el nombre) de cada valor para después convertir estos tipos en tipos de ClickHouse.

### MsgPack {#msgpack}

En el formato MsgPack no hay delimitadores entre filas. Para usar la inferencia del esquema con este formato, debe especificar el número de columnas de la table
mediante el parámetro de configuración `input_format_msgpack_number_of_columns`. ClickHouse utiliza las siguientes correspondencias de tipos:

| Tipo de datos de MessagePack (`INSERT`)                            | Tipo de datos de ClickHouse                  |
| ------------------------------------------------------------------ | -------------------------------------------- |
| `int N`, `uint N`, `negative fixint`, `positive fixint`            | [Int64](/es/reference/data-types/int-uint)      |
| `bool`                                                             | [UInt8](/es/reference/data-types/int-uint)      |
| `fixstr`, `str 8`, `str 16`, `str 32`, `bin 8`, `bin 16`, `bin 32` | [String](/es/reference/data-types/string)       |
| `float 32`                                                         | [Float32](/es/reference/data-types/float)       |
| `float 64`                                                         | [Float64](/es/reference/data-types/float)       |
| `uint 16`                                                          | [Date](/es/reference/data-types/date)           |
| `uint 32`                                                          | [DateTime](/es/reference/data-types/datetime)   |
| `uint 64`                                                          | [DateTime64](/es/reference/data-types/datetime) |
| `fixarray`, `array 16`, `array 32`                                 | [Array](/es/reference/data-types/array)         |
| `fixmap`, `map 16`, `map 32`                                       | [Map](/es/reference/data-types/map)             |

De forma predeterminada, todos los tipos inferidos están dentro de `Nullable`, pero puede cambiar este comportamiento mediante el parámetro de configuración `schema_inference_make_columns_nullable`.

### BSONEachRow {#bsoneachrow}

En BSONEachRow, cada fila de datos se presenta como un documento BSON. Durante la inferencia del esquema, ClickHouse lee los documentos BSON uno por uno y extrae
los valores, nombres y tipos de los datos. A continuación, convierte estos tipos en tipos de ClickHouse según las siguientes correspondencias de tipos:

| Tipo BSON                                                                                          | Tipo de ClickHouse                                                                                               |
| -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `\x08` boolean                                                                                     | [Bool](/es/reference/data-types/boolean)                                                                            |
| `\x10` int32                                                                                       | [Int32](/es/reference/data-types/int-uint)                                                                          |
| `\x12` int64                                                                                       | [Int64](/es/reference/data-types/int-uint)                                                                          |
| `\x01` double                                                                                      | [Float64](/es/reference/data-types/float)                                                                           |
| `\x09` fecha y hora                                                                                | [DateTime64](/es/reference/data-types/datetime64)                                                                   |
| `\x05` binario con subtipo binario `\x00`, `\x02` cadena, `\x0E` símbolo, `\x0D` código JavaScript | [String](/es/reference/data-types/string)                                                                           |
| `\x07` ObjectId,                                                                                   | [FixedString(12)](/es/reference/data-types/fixedstring)                                                             |
| `\x05` binario con subtipo uuid `\x04`, tamaño = 16                                                | [UUID](/es/reference/data-types/uuid)                                                                               |
| `\x04` array                                                                                       | [Array](/es/reference/data-types/array)/[Tuple](/es/reference/data-types/tuple) (si los tipos anidados son diferentes) |
| `\x03` documento                                                                                   | [Tupla con nombre](/es/reference/data-types/tuple)/[Map](/es/reference/data-types/map) (con claves de tipo String)     |

De forma predeterminada, todos los tipos inferidos están dentro de `Nullable`, pero este comportamiento se puede cambiar mediante el parámetro de configuración `schema_inference_make_columns_nullable`.

## Modos de inferencia del esquema {#schema-inference-modes}

La inferencia del esquema a partir del conjunto de archivos de datos puede realizarse en 2 modos diferentes: `default` y `union`.
El modo se controla mediante el parámetro de configuración `schema_inference_mode`.

### Modo predeterminado {#default-schema-inference-mode}

En el modo predeterminado, ClickHouse supone que todos los archivos tienen el mismo esquema e intenta inferirlo leyendo los archivos uno a uno hasta conseguirlo.

Ejemplo:

Supongamos que tenemos 3 archivos `data1.jsonl`, `data2.jsonl` y `data3.jsonl` con el siguiente contenido:

`data1.jsonl`:

```json
{"field1" :  1, "field2" :  null}
{"field1" :  2, "field2" :  null}
{"field1" :  3, "field2" :  null}
```

`data2.jsonl`:

```json
{"field1" :  4, "field2" :  "Data4"}
{"field1" :  5, "field2" :  "Data5"}
{"field1" :  6, "field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field1" :  7, "field2" :  "Data7", "field3" :  [1, 2, 3]}
{"field1" :  8, "field2" :  "Data8", "field3" :  [4, 5, 6]}
{"field1" :  9, "field2" :  "Data9", "field3" :  [7, 8, 9]}
```

Probemos a utilizar la inferencia del esquema en estos 3 archivos:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='default'
```

```response title="Response"
┌─name───┬─type─────────────┐
│ field1 │ Nullable(Int64)  │
│ field2 │ Nullable(String) │
└────────┴──────────────────┘
```

Como podemos ver, falta el campo `field3` del archivo `data3.jsonl`.
Esto ocurre porque ClickHouse primero intentó inferir el esquema a partir del archivo `data1.jsonl`, pero no pudo porque el campo `field2` solo contenía valores NULL,
y después logró inferirlo a partir de `data2.jsonl`, por lo que no se leyeron los datos del archivo `data3.jsonl`.

### Modo de unión {#default-schema-inference-mode-1}

En el modo de unión, ClickHouse asume que los archivos pueden tener esquemas diferentes, por lo que infiere los esquemas de todos los archivos y luego los combina en un esquema común.

Supongamos que tenemos 3 archivos `data1.jsonl`, `data2.jsonl` y `data3.jsonl` con el siguiente contenido:

`data1.jsonl`:

```json
{"field1" :  1}
{"field1" :  2}
{"field1" :  3}
```

`data2.jsonl`:

```json
{"field2" :  "Data4"}
{"field2" :  "Data5"}
{"field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field3" :  [1, 2, 3]}
{"field3" :  [4, 5, 6]}
{"field3" :  [7, 8, 9]}
```

Probemos la inferencia del esquema con estos 3 archivos:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='union'
```

```response title="Response"
┌─name───┬─type───────────────────┐
│ field1 │ Nullable(Int64)        │
│ field2 │ Nullable(String)       │
│ field3 │ Array(Nullable(Int64)) │
└────────┴────────────────────────┘
```

Como podemos ver, tenemos todos los campos de todos los archivos.

Nota:

* Dado que algunos archivos pueden no contener todas las columnas del esquema resultante, el modo de unión solo es compatible con los formatos que permiten leer un subconjunto de columnas (como JSONEachRow, Parquet, TSVWithNames, etc.) y no funciona con otros formatos (como CSV, TSV, JSONCompactEachRow, etc.).
* Si ClickHouse no puede inferir el esquema de alguno de los archivos, se lanzará una excepción.
* Si tiene muchos archivos, leer el esquema de todos ellos puede llevar mucho tiempo.

## Detección automática del formato {#automatic-format-detection}

Si no se especifica el formato de los datos y tampoco se puede determinar a partir de la extensión del archivo, ClickHouse intentará detectar el formato del archivo a partir de su contenido.

**Ejemplos:**

Supongamos que tenemos `data` con el siguiente contenido:

```csv
"a","b"
1,"Data1"
2,"Data2"
3,"Data3"
```

Podemos inspeccionar este archivo y realizar consultas sobre él sin especificar el formato ni la estructura:

```sql
:) desc file(data);
```

```response
┌─name─┬─type─────────────┐
│ a    │ Nullable(Int64)  │
│ b    │ Nullable(String) │
└──────┴──────────────────┘
```

```sql
:) select * from file(data);
```

```response
┌─a─┬─b─────┐
│ 1 │ Data1 │
│ 2 │ Data2 │
│ 3 │ Data3 │
└───┴───────┘
```

<Note>
  ClickHouse solo puede detectar un subconjunto de formatos y esta detección requiere cierto tiempo, por lo que siempre es mejor especificar el formato explícitamente.
</Note>
