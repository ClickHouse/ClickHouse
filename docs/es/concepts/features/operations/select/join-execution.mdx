La mayoría de los algoritmos de join se ejecutan en dos fases:

* **Fase de build.** ClickHouse lee una de las entradas por completo y la almacena en una estructura de datos que permite buscar coincidencias, como una tabla hash o un conjunto de bloques ordenados. Esta entrada es el lado de build.
* **Fase de sondeo.** ClickHouse lee la otra entrada en streaming, bloque a bloque, y compara cada fila con la estructura de datos creada en la fase de build. Esta entrada es el lado de sondeo.

La fase de sondeo no comienza hasta que termina la fase de build. Por ello, la memoria que necesita un JOIN depende principalmente del tamaño del lado de build.

De forma predeterminada, el lado derecho del JOIN es el lado de build y el lado izquierdo, el lado de sondeo. Algunos algoritmos se apartan de este modelo. El [algoritmo `direct`](/es/concepts/features/operations/select/join-algorithms#direct) no tiene fase de build, ya que el lado derecho ya existe como una estructura clave-valor. El [algoritmo `full_sorting_merge`](/es/concepts/features/operations/select/join-algorithms#full-sorting-merge) ordena ambas entradas y las fusiona. El [algoritmo `ie_join`](/es/concepts/features/operations/select/join-algorithms#ie-join) acumula ambas entradas antes de unirlas.

## Comportamiento del planificador de consultas {#query-planner-behavior}

El planificador de consultas puede modificar las entradas de un JOIN antes de que se ejecute un algoritmo. Se aplican las siguientes optimizaciones.

### Selección automática del lado de construcción {#automatic-build-side-selection}

Desde la versión 24.12, el planificador puede intercambiar las dos entradas de un JOIN para que la entrada más pequeña pase a ser el lado de construcción. Para ello, compara el número de filas estimado de ambas entradas y, en un JOIN hash-based, las intercambia cuando estima que la entrada izquierda es más pequeña. Este comportamiento se controla mediante el parámetro de configuración [`query_plan_join_swap_table`](/es/reference/settings/session-settings/query-plan#query_plan_join_swap_table).

Cuando se intercambian las entradas, un JOIN `LEFT` se ejecuta como un JOIN `RIGHT`, y viceversa. El orden intercambiado puede verse en la salida de `EXPLAIN`.

### Reordenación de JOIN entre varias tablas {#multi-table-join-reordering}

En una consulta que une varias tablas dentro de la misma subconsulta, el planificador puede cambiar el orden en que se unen. El parámetro de configuración [`query_plan_optimize_join_order_limit`](/es/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_limit) define el número máximo de tablas que el planificador puede reordenar. El valor predeterminado es `10`. Con el valor `1`, la reordenación queda deshabilitada.

### Uso de estadísticas de columna {#use-of-column-statistics}

La selección del lado de construcción (build side) y la reordenación de JOIN dependen de las estimaciones del número de filas. Sin estadísticas de columna, el planificador obtiene las estimaciones a partir del índice primario, que pueden ser imprecisas. Con [estadísticas de columna](/es/reference/engines/table-engines/mergetree-family/mergetree#column-statistics), el planificador recurre a las estadísticas para estimar la selectividad de los filtros y la cardinalidad de las claves de join.

El parámetro de configuración [`use_statistics`](/es/reference/settings/session-settings/use-statistics#use_statistics) determina si el optimizador utiliza estadísticas. El parámetro de configuración [`materialize_statistics_on_insert`](/es/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert) determina si se generan estadísticas para los datos recién insertados.

### Pushdown de filtros {#filter-pushdown}

Cuando [`query_plan_filter_push_down`](/es/reference/settings/session-settings/query-plan#query_plan_filter_push_down) está habilitado, el planificador desplaza las condiciones `WHERE` por debajo del JOIN para que cada entrada se filtre antes de las fases de build y de sondeo (probe).

* Una condición que solo hace referencia a columnas de una de las entradas se aplica a esa entrada.
* En un JOIN `LEFT`, las condiciones no se trasladan a la entrada derecha. En un JOIN `RIGHT`, no se trasladan a la entrada izquierda.
* Una condición sobre una clave de JOIN de una entrada también puede aplicarse a la otra, ya que las columnas de clave de ambas entradas son iguales en cada fila coincidente.
* Las condiciones no se trasladan a un lado derecho que ya está rellenado, como un diccionario, ni al lado derecho de un JOIN `ASOF`.
