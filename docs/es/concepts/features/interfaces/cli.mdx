`clickhousectl` (alias `chctl`) es la CLI oficial de ClickHouse, desde el desarrollo local hasta ClickHouse Cloud. Está pensada para personas que trabajan en una terminal, para scripts y para agentes de programación.

Con `clickhousectl` puede:

* Instalar versiones locales de ClickHouse y alternar entre ellas, ejecutar servidores locales aislados y ejecutar SQL
* Ejecutar Postgres localmente con Docker
* Crear, configurar, escalar, hacer copias de seguridad y consultar servicios de ClickHouse Cloud
* Crear, supervisar, configurar y restaurar servicios de [ClickHouse Managed Postgres](/es/products/managed-postgres/overview)
* Crear y operar ClickPipes desde almacenamiento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB y BigQuery
* Administrar fuentes, dashboards, alertas, webhooks, búsquedas guardadas y roles en un servicio de [Managed ClickStack](/es/clickstack/deployment/managed)
* Desarrollar UDF ejecutables localmente y desplegarlas en ClickHouse Cloud
* Administrar miembros de la organización, invitaciones, claves de API y roles
* Instalar las ClickHouse agent skills oficiales en agentes de programación

Esta página muestra ejemplos representativos. `clickhousectl <command> --help` es la referencia de autoridad para cada comando y parámetro. La ayuda de la mayoría de los comandos termina con un bloque `CONTEXT FOR AGENTS`; en los comandos de Cloud, también indica los permisos de clave de API que requieren. Para ver guías paso a paso de cada tarea, siga los enlaces incluidos en cada sección. Para obtener una descripción general centrada en Cloud, consulte [CLI de ClickHouse](/es/products/cloud/features/cli).

## Instalación {#installation}

`clickhousectl` funciona en MacOS y Linux, en arquitecturas ARM64 y x86&#95;64.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

El script instala `~/.local/bin/clickhousectl` y crea el alias `chctl`. Asegúrese de que `~/.local/bin` esté incluido en su `PATH`.

También puede instalarlo con un gestor de paquetes:

| Herramienta                                    | Comando                         |
| ---------------------------------------------- | ------------------------------- |
| npm                                            | `npm install -g clickhousectl`  |
| uv                                             | `uv tool install clickhousectl` |
| pipx                                           | `pipx install clickhousectl`    |
| pip                                            | `pip install clickhousectl`     |
| cargo-binstall                                 | `cargo binstall clickhousectl`  |
| Cargo, a partir del código fuente (Rust 1.94+) | `cargo install clickhousectl`   |

Solo el script de instalación y npm crean el alias `chctl`. Para actualizar una instalación existente, ejecute `clickhousectl update` (consulte [Autoactualización](#self-update)).

## Requisitos {#requirements}

* Docker, solo para Postgres local
* Para los comandos de Cloud, una cuenta de [ClickHouse Cloud](https://clickhouse.com/cloud). Los comandos de lectura funcionan con OAuth a través del navegador (`cloud auth login`). Para crear o modificar recursos se necesita una [clave de API](/es/products/cloud/features/admin-features/api/openapi). Consulte [Autenticación](#authentication).

## Local {#local}

Los comandos locales operan en el directorio actual. Cada proyecto almacena los datos de su servidor en `.clickhouse/`, mientras que los binarios de ClickHouse se comparten de forma global en `~/.clickhouse/`. La CLI no busca en los directorios padre, por lo que debe ejecutar los comandos locales desde la raíz de su proyecto. Consulte la [guía de desarrollo local](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md) para conocer el flujo de trabajo completo.

### Instalar y seleccionar versiones {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
```

| Selector      | Significado                                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `latest`      | El build más reciente de ClickHouse, que se comprueba de forma remota en cada instalación, uso o inicio (recomendado) |
| `stable`      | Última versión estable                                                                                                |
| `lts`         | Última versión con soporte a largo plazo                                                                              |
| `26.8`        | Última versión coincidente                                                                                            |
| `26.8.1.1760` | Versión exacta                                                                                                        |

`local use` instala la versión si es necesario, la establece como predeterminada para los próximos inicios del servidor y crea un enlace simbólico a ella en `~/.local/bin/clickhouse`, de modo que `clickhouse client` y `clickhouse local` queden disponibles en su `PATH`. Pase `--no-global` para omitir el enlace simbólico. Si ya existe un archivo normal en esa ruta, no se modifica.

`local remove` no permite eliminar la versión predeterminada ni ninguna que esté usando un servidor en ejecución en cualquier proyecto. `--force` detiene esos servidores y elimina la versión, además de borrar la versión predeterminada y el enlace simbólico.

### Inicializar un proyecto {#initializing-project}

```bash
clickhousectl local init
```

`init` es opcional. Crea un directorio `.clickhouse/`, ignorado por git, para los datos de tiempo de ejecución, además de estructuras base de SQL que puede confirmar con un commit: `clickhouse/` (`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`) y `postgres/` (`tables/`, `views/`, `functions/`, `queries/`, `seed/`). Si se vuelve a ejecutar, solo crea lo que falta.

### Ejecutar servidores locales {#managing-servers}

```bash
clickhousectl local server start dev --version latest   # Background start; waits for readiness
clickhousectl local server start dev --no-wait          # Return after spawning
clickhousectl local server start dev --foreground       # Run in the foreground
clickhousectl local server start dev --http-port 8124 --tcp-port 9001
clickhousectl local server list                         # Servers in this project
clickhousectl local server list --global                # Servers across all projects
clickhousectl local server stop dev
clickhousectl local server stop-all                     # Stop all ClickHouse and Postgres servers in this project
clickhousectl local server remove dev                   # Permanently delete a stopped server's data
```

Cada servidor con nombre tiene sus propios datos en `.clickhouse/servers/<name>/data/`, y al detener un servidor estos se conservan para el siguiente inicio. Si no se indica un nombre, el primer servidor es `default`; si `default` ya está en ejecución, se genera un nombre nuevo. Los puertos predeterminados son HTTP 8123 y TCP 9000; si están ocupados, se asignan puertos libres.

`--version` elige una versión para ese inicio sin cambiar la predeterminada. Un inicio simple, sin versión indicada y sin versión predeterminada, instala `latest` sin establecerla como predeterminada; ejecute primero `local use latest` para establecerla como predeterminada.

### Ejecutar SQL con el cliente local {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` se conecta a un servidor con nombre mediante el mismo binary de ClickHouse que lo ejecuta (nombre predeterminado: `default`). Los argumentos que siguen a `--` se pasan sin modificar a `clickhouse client`. La salida y el código de estado de salida provienen de `clickhouse client`, incluso en modo JSON, así que, si lo usa en scripts, especifique usted mismo el formato de salida de SQL.

### Configuración personalizada del servidor {#custom-config-files}

Coloque un archivo de configuración parcial en XML o YAML en `~/.clickhouse/configs/` y selecciónelo por su nombre al iniciar un servidor:

```bash
mkdir -p ~/.clickhouse/configs
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local server configs
clickhousectl local server stop dev
clickhousectl local server start dev --config analytics
```

El archivo se superpone a los valores predeterminados integrados, por lo que solo debe incluir los ajustes que quiera cambiar. La selección no se conserva: si después se inicia sin `--config`, se elimina el overlay. Las rutas de datos y los puertos gestionados siempre prevalecen sobre los valores de configuración.

### Escribir los datos de conexión en un archivo dotenv {#dotenv}

```bash
clickhousectl local server dotenv dev                                     # Writes .env
clickhousectl local server dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` lee los puertos reales del servidor en ejecución y escribe `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT` y `CLICKHOUSE_HTTP_PORT`, además del usuario, la contraseña y la base de datos si los proporcionas. Si el archivo ya existe, se conservan sus demás líneas. Carga el archivo con el cargador de dotenv de tu aplicación; nunca ejecutes `eval` sobre la vista previa que se muestra en pantalla.

### Postgres local {#local-postgres}

Postgres local se ejecuta en Docker, por lo que Docker debe estar en ejecución. Se admiten las versiones 17 y 18 de Postgres, incluidas etiquetas de imagen como `18-alpine`; las instancias nuevas usan la versión 18 de forma predeterminada.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres stop app
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

Una instancia se identifica por su nombre y su versión principal. Al reanudar una instancia detenida, se reutilizan su puerto, usuario, contraseña y base de datos originales, por lo que los parámetros de creación no surten efecto al reanudarla. Si no proporcionas una contraseña, se genera una aleatoria. `.env.local` contiene la contraseña, así que no lo incluyas en el control de versiones.

### UDFs locales {#local-udfs}

`local udf` despliega [UDF ejecutables](/es/reference/functions/regular-functions/udf#executable-user-defined-functions) desde `clickhouse/udfs/<name>/` en un servidor local. `cloud udf` sube el mismo directorio a Cloud (consulte [UDFs en Cloud](#cloud-udfs)).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local server start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

Todos los comandos, excepto `init`, aceptan `--server <name>` (valor predeterminado: `default`). `deploy` valida `udf.json` de la misma forma que Cloud. En un servidor en ejecución, recarga las funciones y confirma que la función se ha cargado. El tiempo de ejecución `native` solo puede desplegarse localmente en hosts Linux amd64 o arm64. Consulte la [guía de funciones definidas por el usuario](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

## Autenticación {#authentication}

Los comandos de Cloud utilizan uno de estos dos tipos de credenciales:

| Credencial            | Capacidades                                                                                                                         | Almacenamiento                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| OAuth en el navegador | Su identidad de usuario: operaciones de Cloud de solo lectura y SQL de solo lectura en todas las organizaciones a las que pertenece | `~/.clickhouse/tokens.json`, global y compartido entre proyectos |
| Clave de API          | Limitada a una organización; las lecturas y escrituras dependen de los roles de la clave                                            | `.clickhouse/credentials.json` si se guarda, local al proyecto   |

Si aún no tiene una cuenta de ClickHouse Cloud, `clickhousectl cloud auth signup` abre la página de registro en su navegador.

### Inicio de sesión con OAuth {#oauth-login}

```bash
clickhousectl cloud auth login
```

Esto abre el navegador para el flujo de dispositivos de OAuth. Los tokens se guardan de forma global en `~/.clickhouse/tokens.json` y se actualizan automáticamente.

<Note>
  OAuth es de **solo lectura**. Para crear o modificar recursos, inicia sesión con una [clave de API](#api-key).
</Note>

### Clave de API {#api-key}

[Cree una clave de API](/es/products/cloud/features/admin-features/api/openapi) con los roles que requieran sus comandos y, a continuación, guárdela. El prompt interactivo impide que el secreto quede registrado en el historial de su shell:

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

El inicio de sesión verifica la clave y muestra la identidad a la que pertenece. Si la API rechaza la clave, esta no se guarda y el comando finaliza con el código 4. Si no se puede acceder a la API, la clave se guarda igualmente y se muestra una advertencia.

En CI y otros entornos de automatización, en lugar de guardar la clave, inyéctela mediante su gestor de secretos:

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

En entornos de desarrollo, la CLI también lee estas variables de un archivo `.env` ubicado en el directorio actual. No incluyas `.env` en el control de versiones.

### Verificar y eliminar credenciales {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` funciona con cualquiera de los dos tipos de credencial y termina con el código 4 si se rechazan las credenciales. `status` puede terminar con el código 0 aunque ninguna credencial funcione, así que use `whoami` para comprobar el acceso. Cerrar sesión no elimina las variables de entorno ni modifica `.env`.

### Precedencia de credenciales {#credential-precedence}

Se utiliza la primera fuente disponible:

1. Los parámetros `--api-key` y `--api-secret`
2. `.clickhouse/credentials.json`
3. Variables de entorno exportadas
4. Variables del archivo `.env` del directorio actual
5. Tokens OAuth globales

Pase `--debug` a cualquier comando `cloud` para mostrar en stderr la fuente de credenciales seleccionada y la URL de la API:

```bash
clickhousectl cloud service list --debug
```

### Seleccionar una organización {#organizations}

Los comandos con alcance de organización solo seleccionan la organización automáticamente cuando sus credenciales dan acceso a una única organización. En caso contrario, indique `--org-id`, o bien `--org-name` con el nombre exacto:

```bash
clickhousectl cloud org list
clickhousectl cloud service list --org-id <org-id>
clickhousectl cloud service list --org-name "My Org"
```

La mayoría de los comandos de recursos aceptan un ID posicional o un `--name` exacto. Consulte [autenticación y acceso](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md) para obtener información sobre permisos, claves restringidas y limpieza al cerrar sesión.

## Cloud {#cloud}

Los comandos de Cloud llaman a la [API de ClickHouse Cloud](/es/products/cloud/features/admin-features/api/api-overview). Las solicitudes de creación y actualización devuelven una respuesta en cuanto la API las acepta, por lo que debe sondear `get` hasta que el recurso alcance el estado que necesita.

### Servicios {#services}

```bash
clickhousectl cloud service create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud service list
clickhousectl cloud service get <service-id>
clickhousectl cloud service start <service-id>
clickhousectl cloud service stop <service-id>
clickhousectl cloud service wake <service-id>             # Wake an idle service
clickhousectl cloud service reset-password <service-id>
clickhousectl cloud service delete <service-id>           # Must be stopped; --force stops it first
```

Guarde la contraseña inicial que se muestra al crear el servicio, ya que solo se devuelve una vez. El comando de creación finaliza antes de que termine el aprovisionamiento, por lo que debe repetir `get` hasta que el estado sea `running`. **Si se omite `--ip-allow`, se permiten todas las IP (`0.0.0.0/0`).** Las entradas tienen el formato `IP_OR_CIDR=DESCRIPTION`. Restaure una copia de seguridad en un nuevo servicio con `--backup-id`, o despliegue un servicio en una infraestructura BYOC con `--byoc-id`.

Actualice, escale y configure un servicio:

```bash
clickhousectl cloud service update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud service profile list --region us-east-1
clickhousectl cloud service scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud service scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud service settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud service upgrade-window set <service-id> --weekday 0 --start-hour 6
```

La memoria por réplica debe ser un múltiplo de 4 GB, con un máximo de 120 GB en servicios gratuitos y de 356 GB en servicios de pago, y con hasta 50 réplicas. Los límites de la organización y del almacén pueden reducir estos valores. El escalado automático horizontal requiere que la funcionalidad correspondiente esté habilitada en la organización. `update` modifica únicamente los parámetros que se le pasen.

Otros grupos de comandos de servicio son `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (Beta), `snapshot` (Beta), `private-endpoint`, `backup-config` y `prometheus`. Consulte [crear y operar un Servicio de Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md).

### API de consultas {#query-api}

`cloud service query` ejecuta una sentencia SQL a través de HTTP, sin necesidad de un binario `clickhouse` local ni de la contraseña del servicio:

```bash
clickhousectl cloud service query <service-id> --query "SELECT version()"
clickhousectl cloud service query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud service query <service-id>
```

* **OAuth** ejecuta la consulta con tu identidad, con acceso SQL de solo lectura. No se vincula nada al servicio.
* **Clave de API:** en la primera llamada, clickhousectl añade tu clave de API al endpoint de la API de consultas del servicio y, si es necesario, crea el endpoint con los roles `sql_console_admin`. Se conservan los roles, los orígenes y las demás vinculaciones de claves existentes, y no se crea ninguna clave nueva. Cuando la CLI modifica el endpoint, muestra `Binding the authenticated API key to the Query API endpoint for service '<name>'...` en stderr. Pasa `--no-auto-enable` si prefieres que el comando falle.

Si una versión anterior de la CLI guardó una clave específica para un servicio, esa clave sigue teniendo precedencia para ese servicio. Si la API la rechaza, `cloud service repair-query-key <service-id>` la reemplaza explícitamente.

La API de consultas acepta una sola sentencia por solicitud. Puede agotarse el tiempo de espera tras unos 30 segundos aunque el SQL siga ejecutándose, así que comprueba el resultado antes de reintentar una escritura. Usa `clickhouse client` para scripts con varias sentencias, cargas masivas y consultas de larga duración. La lista de permitidos de IP del servicio restringe las conexiones directas, pero no la ruta de la API de consultas a través del proxy. Consultar un servicio inactivo lo reactiva; un servicio detenido debe iniciarse con `cloud service start`.

Administra el endpoint de la API de consultas del servicio, los puntos de conexión SQL con nombre y las consultas guardadas:

```bash
clickhousectl cloud service query-endpoint get <service-id>
clickhousectl cloud service query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` reemplaza los roles de todas las claves vinculadas al endpoint. Consulte [Comportamiento de SQL y de la API de consultas](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md).

### Managed Postgres {#postgres-services}

`cloud postgres` gestiona [ClickHouse Managed Postgres](/es/products/managed-postgres/overview). Estos comandos están en fase Beta, y GCP se encuentra en vista previa privada.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

Los tamaños de AWS incluyen `m6gd.large`, `c6gd.xlarge` y `r6gd.xlarge`. En GCP, pase `--provider gcp` junto con una región de GCP y un tamaño como `c4-standard-lssd-4`.

Guarde la contraseña y la cadena de conexión que devuelve `create`. Las respuestas posteriores de `get` nunca incluyen credenciales, y `reset-password` es la única forma de obtener unas nuevas. Conéctese con `psql` usando `sslmode=verify-full` y el archivo de la CA.

**Si omite los parámetros de acceso en create, se permiten todas las direcciones IPv4 e IPv6 en Postgres (5432) y PgBouncer (6432).** Pase un `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` por cada regla, o bien `--block-public-access` para no definir ninguna regla. En cuanto pase una regla, solo se aplicarán las reglas indicadas.

Supervisión y recuperación:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` solo acepta OAuth, por lo que falla mientras esté activa una fuente de clave de API con mayor prioridad. `metrics`, `slow-queries` y `prometheus` cubren la monitorización. `restore` copia las reglas de acceso IPv4 actuales del servicio de origen en el servicio restaurado, a menos que pases `--ip-allow` o `--block-public-access`. Las restauraciones y las réplicas se devuelven sin contraseña. `promote` y `switchover` finalizan en cuanto se aceptan; después de una promoción, sondea `postgres get --json` hasta que la réplica indique `isPrimary: true`. Consulta la [guía de Managed Postgres](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md).

### ClickPipes {#clickpipes}

`cloud clickpipe` ingesta datos desde almacenamiento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB y BigQuery. Para la creación y el descubrimiento del esquema se necesitan una clave de API y un servicio de destino en ejecución. Cada fuente tiene su propio subcomando `clickpipe create <source>`; ejecútelo con `--help` para consultar sus parámetros.

Cargue archivos desde S3 mediante un rol de IAM. Primero descubra el esquema y, después, elija las columnas:

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN"
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --column 'event_id:Int64' --column 'event_type:String'
```

Replique Postgres con CDC. La verificación TLS está habilitada de forma predeterminada; para una fuente de Managed Postgres, exporte su CA y proporciónela:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud service query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` crea tablas `ReplacingMergeTree`, así que lea el estado actual con `FINAL WHERE _peerdb_is_deleted = 0`. Una canalización de Kafka sigue el mismo patrón: ejecute `clickpipe schema-discover kafka` con los mismos parámetros de origen y, después, pase las columnas:

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

Las canalizaciones de BigQuery realizan una instantánea de forma predeterminada. Para CDC, pase `--replication-mode cdc`, un `--replication-method` y, para cada tabla, una columna de marca de agua o una función de eventos en `--table-mapping-json`; programe las sincronizaciones con `--sync-cron` o `--sync-interval-seconds`. Para administrar las canalizaciones existentes:

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

Las canalizaciones CDC deben estar en estado `Paused` antes de ejecutar `update`: detenga la canalización, sondee con `get` hasta que su estado sea `Paused` y, a continuación, actualícela. El servicio puede reanudar la canalización durante la actualización, así que ejecute `start` solo si `get` sigue mostrando `Paused`. `--start-paused` está disponible para almacenamiento de objetos, Kafka, Kinesis y Pub/Sub. Otros grupos de comandos son `cdc-scaling`, `context get` (disponibilidad de workload identity de GCP y entidad de seguridad) y `reverse-private-endpoint`. Consulte la [guía de ClickPipes](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) y la [referencia de configuración de ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md).

### ClickStack {#clickstack}

`cloud clickstack` administra fuentes, dashboards, alertas, webhooks, búsquedas guardadas y roles en un servicio de [Managed ClickStack](/es/clickstack/deployment/managed) existente. Los recursos se definen como archivos JSON (`--file`, o `-` para stdin). Las operaciones de lectura admiten OAuth; las de escritura requieren una clave de API.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**Cada actualización de ClickStack reemplaza el recurso completo.** Guarde el estado actual con `get --json` y envíe la definición completa, no solo los campos modificados. Consulte la [guía de ClickStack](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md).

### UDFs en Cloud {#cloud-udfs}

`cloud udf` administra las UDF ejecutables con alcance de organización, sus versiones y sus vinculaciones con servicios. `deploy` carga el directorio que probó con `local udf`, espera a que finalice el build, vincula esa versión y espera a que termine de desplegarse:

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud service query <service-id> --query "SELECT my_udf(1)"
```

Para ejecutar cada paso manualmente, utilice `udf create`, `udf version create`, `udf attach` (con `--wake` si el servicio está inactivo), `udf detach` y `udf delete`. Estos comandos devuelven el control en cuanto se acepta la solicitud; consulte el estado sondeando `udf get` y `udf attachment get`. Las lecturas admiten OAuth; las escrituras requieren una clave de API. Consulte la [guía de funciones definidas por el usuario](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

### Organizaciones y acceso {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

Los subcomandos de `cloud org` reciben `--org-id`, nunca un ID posicional. `org usage` abarca como máximo 31 días. `org` también ofrece `quota`, `balance`, `notification-types`, `role` (roles personalizados de la organización) y `byoc` (infraestructura BYOC). Las notificaciones están en fase Beta.

Administre miembros, invitaciones y claves de API:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

**Si se omite `--ip-allow` en `key create`, se deniega todo el acceso a la red**, a diferencia de lo que ocurre al crear un servicio. El secreto se muestra una sola vez. `key list` devuelve una única página, salvo que se indique `--all`. En `key update`, los parámetros omitidos conservan sus ajustes, mientras que `--clear-expiry`, `--clear-roles` y `--clear-ip-allow` los eliminan.

### Copias de seguridad {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud service create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud service backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
clickhousectl cloud backup bucket get <service-id>
```

La restauración siempre crea un servicio nuevo. `cloud backup bucket` (get, create, update, delete) configura un bucket propio para copias de seguridad a partir de un archivo JSON específico del provider. Consulte la sección de copias de seguridad de la [Guía del Servicio de Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore).

## Salida JSON {#json-output}

Los comandos que devuelven datos estructurados aceptan `--json`, incluidos los comandos locales, de Cloud, `skills`, `update` y `telemetry`:

```bash
clickhousectl cloud service list --json
clickhousectl cloud key list --all --json
clickhousectl local server list --json
```

Cuando la CLI detecta un agente de programación (como Claude Code, Cursor, Codex, Gemini CLI, Goose o Devin, o cualquier herramienta que defina `AI_AGENT`), selecciona JSON automáticamente. Los clientes SQL y nativos mantienen sus propios formatos: `cloud service query` devuelve `JSONEachRow` en modo JSON, y la salida de `local client` siempre está en formato nativo. Los scripts que analicen la salida de las consultas deben indicar `--format` explícitamente.

En modo JSON, los errores en tiempo de ejecución se escriben en stderr como un objeto con un `code` estable y un `message`:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

Base la lógica de bifurcación en `error.code`, no en el mensaje. Los errores de uso se siguen mostrando como texto, con código de salida 2. Consulte [automatización y contratos de salida](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md) para conocer las formas de salida y los códigos de error.

## Códigos de salida {#exit-codes}

| Código | Significado                                                                                                 |
| ------ | ----------------------------------------------------------------------------------------------------------- |
| `0`    | Éxito. En las operaciones asíncronas de Cloud, indica que la solicitud se aceptó, no que se haya completado |
| `1`    | Error                                                                                                       |
| `2`    | Error de uso, incluidos valores de parámetro no válidos                                                     |
| `3`    | Cancelado                                                                                                   |
| `4`    | Autenticación requerida o rechazada, incluidos los intentos de escritura con OAuth                          |

`local client`, `local postgres client` y otros comandos que delegan en clientes nativos devuelven el código de salida del propio cliente.

## Habilidades para agentes {#skills}

Instale las [ClickHouse agent skills oficiales](https://github.com/ClickHouse/agent-skills) en sus agentes de programación:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

Las habilidades se instalan de forma predeterminada en el proyecto actual, o en tu directorio personal si usas `--global`. El directorio compartido `.agents/skills/` siempre se incluye. Si no hay una terminal, debes indicar `--agent`, `--all` o `--detected-only`. Ejecuta `clickhousectl skills --help` para consultar los nombres de los agentes compatibles.

## Autoactualización {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

La CLI también busca actualizaciones en segundo plano, como máximo una vez cada 24 horas, y muestra un aviso cuando hay disponible una versión más reciente.

## Telemetría {#telemetry}

`clickhousectl` recopila datos de uso anónimos para orientar el desarrollo. La primera ejecución muestra un aviso y no envía nada; la recopilación comienza en las ejecuciones siguientes, a menos que la desactive.

Cada evento contiene:

* La ruta del comando y los **nombres** de los parámetros y argumentos pasados explícitamente, nunca sus valores
* El resultado y el código de salida
* En caso de un comando mal escrito, el nombre del comando o parámetro que sugirió la CLI, nunca lo que usted escribió
* En caso de fallos en tiempo de ejecución, categorías acotadas: etapa y tipo de fallo, un código de estado HTTP incluido en una lista de permitidos, y categorías de reintento, estado de aprovisionamiento y duración
* La versión de la CLI, el SO y la arquitectura, si se ejecuta en CI y el agente de programación detectado

Nunca se registran valores de argumentos, SQL, credenciales, identificadores de recursos, argumentos posteriores a `--` ni mensajes de error. No existe ningún ID de instalación ni de dispositivo.

Para desactivar la telemetría:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

Establezca `CHCTL_TELEMETRY_DEBUG=1` para mostrar la carga útil en stderr sin enviar ningún dato. Para más información, consulte los [detalles de telemetría](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md).
