Al desplegar ClickStack Open Source en producción, tenga en cuenta las siguientes prácticas de seguridad, estabilidad y configuración.

## Seguridad de red y puertos {#network-security}

De forma predeterminada, Docker Compose expone puertos en el host y los hace accesibles desde fuera del contenedor, incluso si herramientas como `ufw` (Uncomplicated Firewall) están habilitadas. Este comportamiento se debe a la pila de red de Docker, que puede saltarse las reglas de firewall a nivel de host a menos que se configure explícitamente.

**Recomendación:**

Exponga únicamente los puertos necesarios para uso en producción. Normalmente, los endpoints OTLP, el servidor de API y el frontend.

Por ejemplo, elimine o comente las asignaciones de puertos innecesarias en su archivo `docker-compose.yml`:

```yaml
ports:
  - "4317:4317"  # OTLP gRPC
  - "4318:4318"  # OTLP HTTP
  - "8080:8080"  # Only if needed for the API
# Avoid exposing internal ports like ClickHouse 8123 or MongoDB 27017.
```

Consulte la [documentación de redes de Docker](https://docs.docker.com/network/) para obtener más información sobre el aislamiento de contenedores y el endurecimiento del acceso.

## Configuración del secreto de sesión {#session-secret}

En producción, debe asignar un valor aleatorio y seguro a la variable de entorno `EXPRESS_SESSION_SECRET` de la UI de ClickStack para proteger los datos de sesión y evitar su manipulación.

A continuación se muestra cómo añadirla al servicio `app` en su archivo `docker-compose.yml`:

```yaml
  app:
    image: ${IMAGE_NAME_HDX}:${IMAGE_VERSION}
    ports:
      - ${HYPERDX_API_PORT}:${HYPERDX_API_PORT}
      - ${HYPERDX_APP_PORT}:${HYPERDX_APP_PORT}
    environment:
      FRONTEND_URL: ${HYPERDX_APP_URL}:${HYPERDX_APP_PORT}
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_API_PORT: ${HYPERDX_API_PORT}
      HYPERDX_APP_PORT: ${HYPERDX_APP_PORT}
      HYPERDX_APP_URL: ${HYPERDX_APP_URL}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      MINER_API_URL: 'http://miner:5123'
      MONGO_URI: 'mongodb://db:27017/hyperdx'
      NEXT_PUBLIC_SERVER_URL: http://127.0.0.1:${HYPERDX_API_PORT}
      OTEL_SERVICE_NAME: 'hdx-oss-api'
      USAGE_STATS_ENABLED: ${USAGE_STATS_ENABLED:-true}
      EXPRESS_SESSION_SECRET: "super-secure-random-string"
    networks:
      - internal
    depends_on:
      - ch-server
      - db1
```

Puede generar un secreto robusto con `openssl`:

```shell
openssl rand -hex 32
```

Evite hacer commit de secretos en el control de código fuente. En producción, considere usar herramientas de gestión de variables de entorno (p. ej., Docker Secrets, HashiCorp Vault o configuraciones de CI/CD específicas de cada entorno).

## Ingestión segura {#secure-ingestion}

Toda la ingestión debe realizarse a través de los puertos OTLP que expone la distribución de ClickStack del recolector de OpenTelemetry (OTel). De forma predeterminada, esto requiere una API key de ingesta segura que se genera durante el inicio. Esta clave es necesaria para enviar datos a los puertos de OTel y se puede consultar en la UI de ClickStack, en `Team Settings → API Keys`.

Además, se recomienda habilitar TLS en los endpoints OTLP.

### Crear un usuario de ingestión {#create-a-database-ingestion-user-oss}

Se recomienda crear un usuario dedicado para el OTel collector para la ingestión en ClickHouse y asegurarse de que los datos se envíen a una base de datos específica, por ejemplo, `otel`. Consulte [&quot;Creación de un usuario de ingestión&quot;](/es/clickstack/ingesting-data/collector#creating-an-ingestion-user) para obtener más información.

## ClickHouse {#clickhouse}

Los usuarios que gestionen su propia instancia de ClickHouse deben seguir las buenas prácticas que se indican a continuación.

### Buenas prácticas de seguridad {#self-managed-security}

Si administra su propia instancia de ClickHouse, es fundamental habilitar **TLS**, exigir autenticación y seguir las buenas prácticas para reforzar el acceso. Consulte [esta entrada de blog](https://www.wiz.io/blog/clickhouse-and-wiz) para conocer casos reales de configuraciones incorrectas y cómo evitarlas.

ClickHouse OSS incluye de serie funcionalidades de seguridad sólidas. Sin embargo, es necesario configurarlas:

* **Use TLS** mediante `tcp_port_secure` y `<openSSL>` en `config.xml`. Consulte [guides/sre/configuring-tls](/es/concepts/features/security/tls/configuring-tls).
* **Establezca una contraseña segura** para el usuario `default` o desactívelo.
* **Evite exponer ClickHouse externamente** salvo que sea intencionado. De forma predeterminada, ClickHouse solo escucha en `localhost`, a menos que se modifique `listen_host`.
* **Use métodos de autenticación** como contraseñas, certificados, claves SSH o [autenticadores externos](/es/concepts/features/security/external-authenticators/index).
* **Restrinja el acceso** mediante filtrado por IP y la cláusula `HOST`. Consulte [sql-reference/statements/create/user#user-host](/es/reference/statements/create/user#user-host).
* **Active el Control de Acceso Basado en Roles (RBAC)** para conceder privilegios granulares. Consulte [operations/access-rights](/es/concepts/features/security/access-rights).
* **Aplique cuotas y límites** mediante [cuotas](/es/concepts/features/configuration/server-config/quotas), [perfiles de configuración](/es/concepts/features/configuration/settings/settings-profiles) y modos de solo lectura.
* **Cifre los datos en reposo** y use almacenamiento externo seguro. Consulte [operations/storing-data](/es/concepts/features/configuration/server-config/storing-data) y [cloud/security/CMEK](/es/products/cloud/guides/security/cmek).
* **Evite incluir credenciales directamente en el código.** Use [colecciones con nombre](/es/concepts/features/configuration/server-config/named-collections) o roles de IAM en ClickHouse Cloud.
* **Audite el acceso y las consultas** mediante los [logs del sistema](/es/reference/system-tables/query_log) y los [logs de sesión](/es/reference/system-tables/session_log).

Consulte también [autenticadores externos](/es/concepts/features/security/external-authenticators/index) y [ajustes de complejidad de las consultas](/es/concepts/features/configuration/settings/query-complexity) para gestionar usuarios y garantizar límites de consultas y recursos.

### Permisos de usuario para la UI de ClickStack {#user-permissions}

El usuario de ClickHouse para la UI de ClickStack debe tener `readonly = 2`. La interfaz de usuario establece sus propios ajustes, como `date_time_output_format`, en cada consulta, y los gráficos de SQL directo también establecen `readonly = 2`, por lo que, con un usuario con `readonly = 1`, estas consultas fallan con el error `Cannot modify '...' setting in readonly mode`. Con `readonly = 2`, la interfaz de usuario también puede establecer `max_rows_to_read`, `read_overflow_mode` y `cancel_http_readonly_queries_on_client_close`; si restringe `max_rows_to_read`, permita al menos 1 millón de filas. `wait_end_of_query` es un parámetro de la interfaz HTTP y no un parámetro de configuración, por lo que no requiere ningún permiso.

Por ejemplo:

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

De forma predeterminada, el usuario `default` dispone de estos permisos tanto en OSS como en ClickHouse Cloud, pero recomendamos crear un usuario específico.

## Configurar Time To Live (TTL) {#configure-ttl}

Asegúrese de que el [Time To Live (TTL)](/es/clickstack/managing/ttl) esté [configurado correctamente](/es/clickstack/managing/ttl#modifying-ttl) para su implementación de ClickStack. Esto controla durante cuánto tiempo se retienen los datos; es posible que el valor predeterminado de 30 días deba ajustarse.

## Recomendaciones para MongoDB {#mongodb-guidelines}

Siga la [lista de comprobación de seguridad](https://www.mongodb.com/docs/manual/administration/security-checklist/) oficial de MongoDB.
