Las siguientes opciones de configuración están disponibles para cada componente de ClickStack:

<div id="modifying-settings">
  ## Configuración para distribuciones de código abierto
</div>

<div id="docker">
  ### Docker
</div>

Si usas [Todo en uno](/es/clickstack/deployment/all-in-one), [Solo HyperDX](/es/clickstack/deployment/hyperdx-only) o [Modo local](/es/clickstack/deployment/local-mode-only), solo tienes que pasar la configuración deseada mediante una variable de entorno; por ejemplo:

```shell
docker run  -e HYPERDX_LOG_LEVEL='debug' -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-all-in-one:latest
```

<div id="docker-compose">
  ### Docker Compose
</div>

Si utiliza la guía de implementación de [Docker Compose](/es/clickstack/deployment/docker-compose), puede usar el archivo [`.env`](https://github.com/hyperdxio/hyperdx/blob/main/.env) para modificar la configuración.

Como alternativa, sobrescriba explícitamente la configuración en el archivo [`docker-compose.yaml`](https://github.com/hyperdxio/hyperdx/blob/main/docker-compose.yml); por ejemplo:

Ejemplo:

```yaml
services:
  app:
    environment:
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      # ... otras configuraciones
```

<div id="helm">
  ### Helm
</div>

<div id="customizing-values">
  #### Personalización de los valores (opcional)
</div>

Puede personalizar la configuración con los indicadores `--set`, por ejemplo.

```shell
helm install my-hyperdx hyperdx/hdx-oss-v2 \
  --set replicaCount=2 \
  --set resources.limits.cpu=500m \
  --set resources.limits.memory=512Mi \
  --set resources.requests.cpu=250m \
  --set resources.requests.memory=256Mi \
  --set ingress.enabled=true \
  --set ingress.annotations."kubernetes\.io/ingress\.class"=nginx \
  --set ingress.hosts[0].host=hyperdx.example.com \
  --set ingress.hosts[0].paths[0].path=/ \
  --set ingress.hosts[0].paths[0].pathType=ImplementationSpecific \
  --set env[0].name=CLICKHOUSE_USER \
  --set env[0].value=abc
```

Como alternativa, edita el `values.yaml`. Para obtener los valores predeterminados:

```shell
helm show values hyperdx/hdx-oss-v2 > values.yaml
```

Configuración de ejemplo:

```yaml
replicaCount: 2
resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 250m
    memory: 256Mi
ingress:
  enabled: true
  annotations:
    kubernetes.io/ingress.class: nginx
  hosts:
    - host: hyperdx.example.com
      paths:
        - path: /
          pathType: ImplementationSpecific
  env:
    - name: CLICKHOUSE_USER
      value: abc
```

<div id="hyperdx">
  ## Aplicación ClickStack UI (HyperDX)
</div>

<div id="datasource-settings">
  ### Configuración de las fuentes de datos
</div>

La UI de ClickStack requiere que el usuario defina una fuente para cada uno de los tipos o pilares de datos de observabilidad:

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

Esta configuración puede realizarse dentro de la aplicación desde `Team Settings -> Sources`, como se muestra a continuación para los logs:

<Image img="/images/use-cases/observability/hyperdx-25.webp" alt="Configuración de fuente en HyperDX" size="md" />

Cada una de estas fuentes requiere que se especifique al menos una tabla al crearla, así como un conjunto de columnas que permitan a HyperDX consultar los datos.

Si se utiliza el [esquema predeterminado de OpenTelemetry (OTel)](/es/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema) incluido con ClickStack, estas columnas pueden inferirse automáticamente para cada una de las fuentes. Si se [modifica el esquema](#clickhouse) o se usa un esquema personalizado, los usuarios deben especificar y actualizar estas asignaciones.

<Note>
  El esquema predeterminado de ClickHouse incluido con ClickStack es el esquema creado por el [exporter de ClickHouse para el OTel collector](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter). Estos nombres de columnas se corresponden con la especificación oficial de OTel documentada [aquí](https://opentelemetry.io/docs/specs/otel/logs/data-model/).
</Note>

La siguiente configuración está disponible para cada fuente:

<div id="materialized-views-settings">
  #### Vistas materializadas
</div>

Las vistas materializadas se pueden registrar para las fuentes de datos de Log y traza, de modo que las consultas de agregación aptas se resuelvan a partir de la vista preagregada en lugar de la tabla de origen. Para obtener instrucciones sobre cómo crear y registrar vistas, consulte [&quot;Vistas materializadas&quot;](/es/clickstack/managing/materialized-views).

Cada vista registrada se configura con los siguientes SETTINGS:

| SETTING                  | Descripción                                                                                                                                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Database`               | Base de datos de ClickHouse que contiene la tabla de destino de la vista materializada.                                                                                                                                                                                         |
| `Table`                  | Tabla de destino de la vista materializada, no la vista en sí.                                                                                                                                                                                                                  |
| `Timestamp Column`       | Columna de marca de tiempo de la tabla de destino.                                                                                                                                                                                                                              |
| `Granularity`            | Intervalo de tiempo de la columna de marca de tiempo de la tabla de destino; por ejemplo, `1 minute`. Una consulta solo puede usar la vista si su propio intervalo de tiempo es igual o menos granular que este.                                                                |
| `Minimum Date`           | Opcional. La fecha y hora más tempranas para las que la vista contiene datos. Si no se proporciona, ClickStack asume que la vista contiene datos para todas las fechas presentes en la tabla de origen.                                                                         |
| `Dimension Columns`      | Lista, separada por comas, de las columnas que la vista no preagrega y que, por lo tanto, se pueden usar para filtrar y agrupar.                                                                                                                                                |
| `Pre-aggregated Columns` | Columnas que la vista preagrega. Cada entrada asigna una función de agregación (`avg`, `count`, `max`, `min`, `quantile`, `sum` o `histogram`) y una columna de la tabla de origen a la columna correspondiente de la vista. La columna de origen no es necesaria para `count`. |

La mayoría de estos SETTINGS se infieren del esquema de la vista al seleccionar la tabla de destino.

</div>

Consulta [&quot;ClickStack OpenTelemetry Collector&quot;](/es/clickstack/ingesting-data/collector) para obtener más información.

* `CLICKHOUSE_ENDPOINT`
  * **Predeterminado:** *Ninguno (obligatorio)* si se usa una imagen independiente. Si se usa una distribución All-in-one o Docker Compose, se establece en la instancia integrada de ClickHouse.

  * **Guía:**

  * **Predeterminado:** `default`
  * **Descripción:** Nombre de usuario utilizado para autenticarse con la instancia de ClickHouse.
  * **Guía:**
    * Asegúrate de que el usuario tenga permisos de `INSERT` y `CREATE TABLE`
    * Se recomienda crear un usuario dedicado para la ingestión

* `CLICKHOUSE_PASSWORD`
  * **Predeterminado:** *Ninguno (obligatorio si la autenticación está habilitada)*
  * **Descripción:** Contraseña del usuario de ClickHouse especificado.
  * **Guía:**
    * Es obligatorio si la cuenta de usuario tiene una contraseña configurada
    * Almacénala de forma segura mediante secretos en implementaciones de producción

* `HYPERDX_LOG_LEVEL`
  * **Predeterminado:** `info`
  * **Descripción:** Nivel de verbosidad de los logs del collector.
  * **Guía:**
    * Acepta valores como `debug`, `info`, `warn`, `error`
    * Usa `debug` durante la resolución de problemas

* `OPAMP_SERVER_URL`
  * **Predeterminado:** *Ninguno (obligatorio)* si se usa una imagen independiente. Si se usa una distribución All-in-one o Docker Compose, apunta a la instancia de HyperDX desplegada.
  * **Descripción:** URL del servidor OpAMP utilizado para gestionar el collector (p. ej., una instancia de HyperDX). De forma predeterminada, usa el puerto `4320`.
  * **Guía:**
    * Debe apuntar a tu instancia de HyperDX
    * Habilita la configuración dinámica y la ingestión segura
    * Si se omite, la ingestión segura se desactiva a menos que se especifique un valor para `OTLP_AUTH_TOKEN`.

* `OTLP_AUTH_TOKEN`
  * **Predeterminado:** *Ninguno*. Solo se usa para la imagen independiente.
  * **Descripción:** Permite especificar un token de autenticación OTLP. Si se configura, toda la comunicación requiere este token Bearer.
  * **Guía:**
    * Se recomienda si usas la imagen independiente del collector en producción.

  * **Predeterminado:** `default`
  * **Descripción:** Base de datos de ClickHouse en la que el collector escribe los datos de telemetría.

<div id="clickhouse">
  ## ClickHouse
</div>

ClickStack Open Source incluye una configuración predeterminada de ClickHouse diseñada para escalar a varios terabytes, pero los usuarios pueden modificarla y optimizarla según su carga de trabajo.

Para optimizar ClickHouse de forma eficaz, debe comprender conceptos clave de almacenamiento como las [partes](/es/concepts/core-concepts/parts), las [particiones](/es/concepts/core-concepts/partitions), los [segmentos y réplicas](/es/guides/oss/deployment-and-scaling/shards) y cómo se producen las [fusiones](/es/concepts/core-concepts/merges) durante la inserción. Recomendamos revisar los fundamentos de los [índices primarios](/es/concepts/core-concepts/primary-indexes), los [índices secundarios dispersos](/es/concepts/features/performance/skip-indexes/skipping-indexes) y los índices de omisión de datos, junto con técnicas para [gestionar el ciclo de vida de los datos](/es/guides/use-cases/observability/build-your-own/managing-data), por ejemplo, mediante TTL.

ClickStack admite la [personalización del esquema](/es/guides/use-cases/observability/build-your-own/schema-design): puede modificar los tipos de las columnas, extraer nuevos campos (p. ej., de logs), aplicar codecs y diccionarios, y acelerar las consultas mediante proyecciones.

Además, las vistas materializadas pueden utilizarse para [transformar o filtrar datos durante la ingestión](/es/guides/use-cases/observability/build-your-own/schema-design#materialized-columns), siempre que los datos se escriban en la tabla origen de la vista y la aplicación lea de la tabla de destino. Las vistas materializadas también pueden utilizarse para [acelerar consultas de forma nativa](/es/clickstack/managing/materialized-views) en ClickStack.

Para obtener más información, consulte la documentación de ClickHouse sobre diseño de esquemas, estrategias de indexación y buenas prácticas para la gestión de datos; la mayoría se aplican directamente a las implementaciones de ClickStack.
