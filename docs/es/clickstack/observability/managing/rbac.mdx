ClickHouse Observability incluye control de acceso basado en roles (RBAC), que le permite definir roles personalizados con permisos de granularidad fina sobre [dashboards](/es/clickstack/observability/features/dashboards/overview), [búsquedas guardadas](/es/clickstack/observability/features/search), fuentes, [alertas](/es/clickstack/observability/features/alerts), webhooks y notebooks. Los permisos funcionan en dos niveles: acceso a nivel de recurso (sin acceso, lectura o administración para cada tipo de recurso) y reglas opcionales de granularidad fina que restringen el acceso a recursos concretos por nombre, etiqueta o ID. El servicio incluye de forma predeterminada tres roles predefinidos, y puede crear roles personalizados que se adapten a las necesidades de su equipo.

## Requisitos previos de acceso de usuarios {#user-access-prerequisites}

El servicio se autentica a través de ClickHouse Cloud. Los usuarios deben pertenecer a su organización de ClickHouse Cloud y tener acceso al servicio de Observability. Para obtener información sobre la pertenencia a la organización, consulte [Gestionar usuarios de la nube](/es/products/cloud/guides/security/cloud-access-management/manage-cloud-users).

Los niveles de acceso de la Consola SQL de Cloud se corresponden con el acceso a Observability de la siguiente manera:

| Acceso a la Consola SQL de Cloud                      | Acceso a Observability                                                                                          |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Administrador de la consola SQL** (acceso completo) | Acceso completo al servicio. Necesario para habilitar las [alertas](/es/clickstack/observability/features/alerts). |
| **Consola SQL de solo lectura** (solo lectura)        | Puede ver datos de observabilidad y crear dashboards.                                                           |
| **Sin Acceso**                                        | No puede acceder al servicio.                                                                                   |

Abra **Configuración del equipo → Miembros y roles** para ver los miembros del equipo y sus roles actuales en Observability. Seleccione **Administrar en la Consola** para gestionar la pertenencia a la organización en ClickHouse Cloud.

## Roles predefinidos {#built-in-roles}

El servicio incluye tres roles del sistema, que no se pueden editar ni eliminar. El rol de Admin se asigna de forma predeterminada al creador del equipo.

| Permiso                                | Admin | Member | ReadOnly |
| -------------------------------------- | :---: | :----: | :------: |
| Leer todos los recursos                |   ✓   |    ✓   |     ✓    |
| Administrar dashboards                 |   ✓   |    ✓   |          |
| Administrar búsquedas guardadas        |   ✓   |    ✓   |          |
| Administrar fuentes                    |   ✓   |    ✓   |          |
| Administrar alertas                    |   ✓   |    ✓   |          |
| Administrar webhooks                   |   ✓   |    ✓   |          |
| Administrar notebooks                  |   ✓   |    ✓   |          |
| Actualizar la configuración del equipo |   ✓   |    ✓   |          |
| Crear/eliminar equipos                 |   ✓   |        |          |
| Administrar usuarios e invitaciones    |   ✓   |        |          |

## Asignación de roles a los miembros del equipo {#assigning-roles}

La pestaña **Miembros y roles** de **Configuración del equipo** muestra los miembros del equipo junto con su rol actual. Para cambiar un rol, haga clic en **Edit** junto al nombre del usuario y seleccione el nuevo rol. Cada usuario tiene un único rol.

### Rol predeterminado para nuevo usuario {#default-new-user-role}

En **Configuración del equipo** → **Miembros y roles**, use la opción **Rol predeterminado para nuevo usuario**, situada debajo de la lista de roles, para elegir el rol que se asigna a los usuarios que se unen automáticamente al equipo. Si no se define ningún rol predeterminado, los nuevos usuarios reciben el rol **Miembro**.

## Permisos de rol {#role-permissions}

### Permisos de recursos {#resource-permissions}

Cada rol otorga un nivel de acceso por tipo de recurso. Los tres niveles son:

| Nivel de acceso    | Qué permite                                                                 |
| ------------------ | --------------------------------------------------------------------------- |
| **Sin Acceso**     | El tipo de recurso queda completamente oculto para el rol.                  |
| **Lectura**        | Ver el recurso y su configuración, pero no crearlo, editarlo ni eliminarlo. |
| **Administración** | Control total: crear, editar y eliminar recursos de ese tipo.               |

Los tipos de recurso que puede controlar son:

* **[Dashboards](/es/clickstack/observability/features/dashboards/overview)**: diseños de dashboards y gráficos guardados.
* **[Búsquedas guardadas](/es/clickstack/observability/features/search)**: consultas persistidas de logs, trazas y eventos.
* **Fuentes**: fuentes de datos que se utilizan para consultar datos de observabilidad.
* **[Alertas](/es/clickstack/observability/features/alerts)**: reglas de alerta y su configuración de notificaciones.
* **Webhooks**: destinos de notificación salientes (como Slack, PagerDuty y puntos de conexión HTTP genéricos) a los que las [alertas](/es/clickstack/observability/features/alerts) envían sus notificaciones. No se refiere a la API de observabilidad.
* **Cuadernos**: cuadernos de investigación colaborativos.

### Permisos administrativos {#administrative-permissions}

Además de los permisos sobre recursos, cada rol incluye dos ajustes administrativos:

* **Usuarios** (Sin Acceso · Lectura) — determina si el rol puede ver a los miembros del equipo y sus roles. Gestione los miembros de la organización mediante **Administrar en la Consola**.
* **Equipo** (Lectura · Administración) — determina si el rol puede ver o modificar los ajustes del equipo, como las políticas de seguridad y la configuración de RBAC.

### Reglas de acceso de granularidad fina {#fine-grained-access-rules}

Los dashboards, las búsquedas guardadas, las fuentes y los Cuadernos admiten controles de granularidad fina que restringen el acceso a recursos individuales dentro de una categoría. Utilícelos cuando necesite limitar un rol a recursos concretos en lugar de concederle acceso general a todo el tipo de recurso.

#### Acceso predeterminado frente a control granular {#access-control-modes}

Cada tipo de recurso tiene un **Modo de control de acceso**:

* **Acceso predeterminado**: aplica un único nivel de acceso (Sin Acceso, Lectura o Administración) a todos los recursos de ese tipo.
* **Control granular**: permite definir reglas de acceso que coinciden con recursos específicos según una condición. Los recursos que no coinciden con ninguna regla quedan sin acceso de forma predeterminada.

Para cambiar de modo, haga clic en el chevron para expandir un tipo de recurso en el editor de roles y, a continuación, active o desactive el toggle **Modo de control de acceso**.

#### Configuración de reglas de acceso {#configuring-access-rules}

Cada regla de acceso consta de una **condición** y un **nivel de acceso**. Las condiciones seleccionan los recursos según sus propiedades:

<div className="ch-image-md">
  <Frame>
    ![Tooltip de condición: seleccionar recursos por Name o Tag (mostrados en el título) o por ID (que figura en la URL)](/images/clickstack/rbac/condition-tip.webp)
  </Frame>
</div>

| Campo de condición | Operadores       | Qué selecciona                                                                                                                                                                          | Ejemplo                                                                                                      |
| ------------------ | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Name**           | `is`, `contains` | El nombre visible del recurso; por ejemplo, el título del dashboard.                                                                                                                    | Name contains `production`: selecciona cualquier dashboard que contenga &quot;production&quot; en su título. |
| **Tag**            | `is`, `contains` | Etiquetas asignadas al recurso desde el panel de etiquetas situado en la esquina superior derecha de la vista del recurso. Solo disponible para Dashboards, Saved Searches y Notebooks. | Tag is `critical`: selecciona los recursos con la etiqueta &quot;critical&quot;.                             |
| **ID**             | `is`, `contains` | El identificador del recurso, que aparece en la barra de direcciones al abrir el recurso.                                                                                               | ID is `abc123`: selecciona un único recurso concreto.                                                        |

En la siguiente captura de pantalla se muestran tanto el ID del dashboard, resaltado en la barra de direcciones, como una etiqueta &quot;TESTING&quot; en el panel de etiquetas (arriba a la derecha).

<div className="ch-image-lg">
  <Frame>
    ![Dashboard que muestra el ID de recurso en la barra de direcciones y una etiqueta en la esquina superior derecha](/images/clickstack/rbac/dashboard-id-and-tag-example.webp)
  </Frame>
</div>

Puede añadir varias reglas por tipo de recurso. Cada regla se evalúa de forma independiente con lógica OR: un recurso es accesible si cumple **cualquiera** de las reglas. Los recursos que no cumplen ninguna regla no son accesibles.

<div className="ch-image-md">
  <Frame>
    ![Tooltip de reglas de acceso con lógica OR](/images/clickstack/rbac/access-rules-tip.webp)
  </Frame>
</div>

**Ejemplo**: para conceder a un rol acceso de solo lectura a los dashboards de pruebas, despliegue Dashboards, cambie a Fine-Grained Controls y añada dos reglas:

* **Name** `contains` `testing` con nivel de acceso **Read**
* **Tag** `is` `testing` con nivel de acceso **Read**

Cualquier dashboard que cumpla alguna de las dos reglas será accesible.

<div className="ch-image-md">
  <Frame>
    ![Dos reglas de acceso de granularidad fina unidas por OR: Name contains testing con acceso Read, y Tag is testing con acceso Read](/images/clickstack/rbac/dashboard-fine-grained-example.webp)
  </Frame>
</div>

## Políticas de seguridad {#security-policies}

En **Configuración del equipo → Miembros y roles → Políticas de seguridad**, la opción **Desactivar exportaciones de datos** oculta los controles de descarga y copia de los datos de log, incluidos los detalles de las filas, para todos los miembros del equipo. Los usuarios pueden seguir seleccionando texto en pantalla, y la API y el servidor MCP siguen devolviendo datos. Este parámetro de configuración no impide el acceso a los datos subyacentes.

Los controles de IA generativa se encuentran en **Configuración del equipo → API y agentes → Configurar IA generativa**. Consulte [Configurar IA generativa](/es/clickstack/observability/managing/config#generative-ai) para obtener más información.
