Envíe logs, trazas y métricas desde sus agentes de Datadog existentes a ClickHouse Observability. Sus aplicaciones pueden seguir usando sus SDK de Datadog. Elija un endpoint gestionado o configure un receiver de Datadog en su propio recolector y, a continuación, siga los mismos pasos de configuración del agente que se indican más abajo.

## Requisitos previos {#prerequisites}

* Un servicio de ClickHouse Observability gestionado o autogestionado.
* Un agente de Datadog en ejecución que recopile las señales que desea migrar. En el caso de las trazas, su aplicación ya debe estar enviándolas a ese agente mediante un SDK de Datadog.
* Acceso a la red desde el agente al endpoint de su receiver de Datadog.

## Configure su destino {#connection-details}

<Tabs>
  <Tab title="Totalmente gestionado">
    <BetaBadge label="Oferta Beta" />

    Abra su servicio y vaya a **Team Settings → Data → Managed Telemetry**. Copie el **OTLP HTTP endpoint** y la **clave de API**.

    <div className="ch-image-lg">
      <Frame>
        ![Managed Telemetry con el endpoint OTLP HTTP y la clave de API enmascarados](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    El endpoint de Datadog usa el mismo nombre de host con el puerto `8126`. No se necesita ningún recolector adicional. Use estos valores en la configuración del agente que aparece a continuación:

    | Parámetro de configuración | Valor                                     |
    | -------------------------- | ----------------------------------------- |
    | `YOUR_API_KEY`             | La clave de API de ingesta de su servicio |
    | `YOUR_DATADOG_URL`         | `https://YOUR_OTEL_HOST:8126`             |
    | `YOUR_DATADOG_HOST_PORT`   | `YOUR_OTEL_HOST:8126`                     |
    | `logs_no_ssl`              | `false`                                   |
  </Tab>

  <Tab title="Autogestionado" id="self-managed">
    El [Recopilador de OpenTelemetry de ClickStack](/es/clickstack/self-configured/ingesting-data/collector) incluye el [receiver de Datadog](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/datadogreceiver). Configure el receptor y conéctelo a sus canalizaciones de logs, trazas y métricas.

    Guarde la siguiente superposición de configuración como `datadog-collector.yaml`. Esta añade el receiver de Datadog a las canalizaciones de logs, trazas y métricas ya existentes en el recolector, sin eliminar el receptor OTLP:

    ```yaml
    receivers:
      datadog:
        endpoint: 0.0.0.0:8126

    service:
      pipelines:
        logs/in:
          receivers: [otlp/hyperdx, datadog]
        traces:
          receivers: [otlp/hyperdx, datadog]
        metrics:
          receivers: [otlp/hyperdx, datadog]
    ```

    Defina los datos de conexión de ClickHouse e inicie el recolector. Durante el arranque normal se crea el esquema de telemetría en la base de datos indicada en `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`; el usuario de ClickHouse necesita permisos para crear la base de datos y las tablas. Si ya dispone de una base de datos de telemetría, use su nombre.

    Este ejemplo requiere Docker, usa la versión `2.40.0` del recolector y publica el receiver de Datadog únicamente en el host local:

    ```shell
    export CLICKHOUSE_ENDPOINT='https://YOUR_CLICKHOUSE_HOST:8443'
    export CLICKHOUSE_USER='YOUR_CLICKHOUSE_USER'
    export CLICKHOUSE_PASSWORD='YOUR_CLICKHOUSE_PASSWORD'
    export HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE='default'

    docker run --rm --name datadog-collector \
      -e CLICKHOUSE_ENDPOINT \
      -e CLICKHOUSE_USER \
      -e CLICKHOUSE_PASSWORD \
      -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE \
      -e CUSTOM_OTELCOL_CONFIG_FILE=/etc/datadog-collector.yaml \
      -v "$(pwd)/datadog-collector.yaml:/etc/datadog-collector.yaml:ro" \
      -p 127.0.0.1:18126:8126 \
      clickhouse/clickstack-otel-collector:2.40.0
    ```

    Mantenga el recolector en ejecución en este terminal mientras configura y verifica el agente. Ejecute el resto de comandos en otro terminal.

    Use estos valores para un agente que se ejecute en el mismo host:

    | Parámetro de configuración | Valor                                                                                 |
    | -------------------------- | ------------------------------------------------------------------------------------- |
    | `YOUR_API_KEY`             | Un marcador de posición no vacío, como `local-test`; este receptor local no lo valida |
    | `YOUR_DATADOG_URL`         | `http://localhost:18126`                                                              |
    | `YOUR_DATADOG_HOST_PORT`   | `localhost:18126`                                                                     |
    | `logs_no_ssl`              | `true`                                                                                |

    El puerto de host `18126` evita que este destino entre en conflicto con el listener de trazas de aplicación del agente en el puerto `8126`. Si el agente se ejecuta en un contenedor, conecte ambos contenedores a la misma red de Docker y use `http://datadog-collector:8126` y `datadog-collector:8126` como valores de destino.

    Este ejemplo usa un listener HTTP sin autenticación, restringido al host local. Para agentes en otros hosts, habilite una ruta de red protegida y configure TLS y autenticación en su ingress antes de exponer el receptor. `OTLP_AUTH_TOKEN` configura la autenticación OTLP del recolector, pero no protege este listener de Datadog.
  </Tab>
</Tabs>

## Configurar el agente de Datadog {#configure-datadog-agent}

Actualice el [archivo de configuración `datadog.yaml`](https://docs.datadoghq.com/agent/configuration/agent-configuration-files/) de su agente. Las ubicaciones habituales son `/etc/datadog-agent/datadog.yaml` en Linux y `/opt/datadog-agent/etc/datadog.yaml` en macOS.

Incorpore los siguientes ajustes a su configuración actual, utilizando los valores de destino de la pestaña anterior:

```yaml
api_key: "YOUR_API_KEY"

# Metrics destination
dd_url: "YOUR_DATADOG_URL"

# Use the v2 metrics intake.
use_v3_api:
  series:
    enabled: false

# Trace destination
apm_config:
  enabled: true
  apm_dd_url: "YOUR_DATADOG_URL"
  features:
    - disable-convert-traces

# Log destination
logs_enabled: true
logs_config:
  logs_dd_url: "YOUR_DATADOG_HOST_PORT"
  force_use_http: true
  logs_no_ssl: false # Set to true for the local HTTP receiver.

remote_updates: false
remote_configuration:
  enabled: false
```

Reemplace `YOUR_DATADOG_URL` por la URL completa del destino y `YOUR_DATADOG_HOST_PORT` por su `hostname:port`, sin esquema. Establezca `logs_no_ssl` en el valor indicado para su destino.

<Note>
  `disable-convert-traces` mantiene las cargas útiles de trazas del agente compatibles con el receiver de Datadog. Con Datadog agente 7.85.2 y collector core 0.155.0, la carga útil indexada predeterminada del agente se aceptaba con HTTP 200, pero no generaba ningún span. Use el parámetro de configuración anterior para el reenvío de trazas y conserve las demás entradas de su lista `apm_config.features` existente.
</Note>

Mantenga sus integraciones actuales de recopilación de logs y la configuración de tracing de sus aplicaciones. Estos ajustes cambian el destino al que el agente envía la telemetría; no activan la recopilación de logs para aplicaciones concretas ni añaden instrumentación. Si configura el agente mediante [variables de entorno](https://docs.datadoghq.com/agent/guide/environment-variables/), actualice también allí los ajustes correspondientes, incluido `DD_API_KEY`.

Esta configuración redirige los logs, las trazas y las métricas del agente de Datadog a ClickHouse Observability. Si quiere evaluarla primero, aplíquela a un agente de prueba antes de actualizar el resto de su implementación.

## Reinicio y verificación {#restart-and-verify}

Reinicie el agente para aplicar la configuración. En Linux:

```shell
sudo systemctl restart datadog-agent
sudo datadog-agent status
```

En macOS:

```shell
sudo launchctl kickstart -k system/com.datadoghq.agent
```

Si el agente se ejecuta en un contenedor, actualice su configuración y vuelva a desplegar el contenedor.

Genere nueva actividad en la aplicación y, a continuación, abra ClickHouse Observability y seleccione un intervalo de tiempo reciente:

* **Logs:** seleccione su fuente de logs y filtre por el `ServiceName` de la aplicación.
* **Trazas:** seleccione su fuente de trazas y filtre por el `ServiceName` de la aplicación.
* **Métricas:** busque una métrica emitida por su aplicación o por el agente. Para una prueba con DogStatsD, emita un gauge con nombre y compruebe su valor.

Si los datos no aparecen, revise el estado del agente en busca de errores de entrega. Verifique el nombre del host, el puerto, la clave de API y la configuración de acceso a la red de su servicio. Confirme que el agente recopila la señal correspondiente y que todas las sobrescrituras mediante variables de entorno apuntan al mismo destino.

En el caso de las trazas, compruebe un ID de traza conocido en lugar de fiarse únicamente de los contadores de entregas correctas del agente. Si un filtro de servicio oculta la traza, busque por `TraceId`: el receptor puede usar el servicio base del tracer como nombre del servicio del recurso y, al mismo tiempo, conservar una sobrescritura del servicio por span en el atributo de span `service.name`. Defina `DD_SERVICE` en la configuración de tracing de su aplicación para establecer su nombre de servicio base.

## Señales compatibles {#supported-signals}

El receiver de Datadog es experimental. Convierte los logs, las trazas y las métricas compatibles de Datadog al modelo de datos de OpenTelemetry que utiliza ClickHouse Observability. La configuración anterior selecciona la ingesta de métricas v2; las demás funcionalidades del backend de Datadog quedan fuera de este flujo de migración.

Puede conservar su instrumentación de Datadog actual mientras migra sus aplicaciones a OpenTelemetry de forma gradual.

Con un recopilador de ClickStack autogestionado, las aplicaciones también pueden enviar métricas personalizadas de DogStatsD directamente al recolector, y este puede derivar métricas de solicitudes, errores y duración a partir de las trazas. Consulte [Recepción de métricas de StatsD](/es/clickstack/self-configured/ingesting-data/collector#statsd-receiver) y [Derivación de métricas a partir de spans](/es/clickstack/self-configured/ingesting-data/collector#span-metrics).
