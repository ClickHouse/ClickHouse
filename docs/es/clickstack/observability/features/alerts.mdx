ClickHouse Observability ofrece compatibilidad nativa con alertas, lo que permite a los equipos detectar incidencias y responder a ellas en tiempo real en logs, métricas y trazas.

Las alertas se pueden crear directamente desde la interfaz de usuario y se integran con sistemas de notificación habituales como Slack y PagerDuty.

Las alertas se integran sin fricciones con sus datos de observabilidad, lo que le ayuda a supervisar el estado del sistema, detectar regresiones de rendimiento y monitorizar eventos clave del negocio.

## Tipos de alertas {#types-of-alerts}

Puede crear alertas a partir de una **búsqueda guardada**, directamente en el **Explorador de Gráficos** o desde un **gráfico de un panel de control guardado**. Las alertas de búsqueda cuentan los eventos coincidentes, mientras que las alertas de gráfico evalúan los valores que calcula un gráfico.

### Alertas de búsqueda {#search-alerts}

Las alertas de búsqueda le permiten activar notificaciones en función de los resultados de una búsqueda guardada. Le ayudan a detectar cuándo determinados eventos o patrones se producen con mayor (o menor) frecuencia de lo esperado.

Una alerta se activa cuando el número de resultados coincidentes dentro de una ventana de tiempo definida supera un umbral especificado o queda por debajo de él.

Para crear una alerta de búsqueda:

Para crear una alerta sobre una búsqueda, esta debe estar guardada. Puede crear la alerta para una búsqueda guardada existente o guardar la búsqueda durante el proceso de creación de la alerta. En el ejemplo siguiente, se supone que la búsqueda no está guardada.

### Integraciones por tipo de servicio {#integrations}

Las alertas se integran de forma nativa con los siguientes tipos de servicio:

* **Slack**: envíe notificaciones directamente a un canal mediante un webhook o la API.
* **PagerDuty**: dirija incidentes a los equipos de guardia mediante la API de PagerDuty.
* **incident.io**: envíe alertas a incident.io.
* **Generic**: conecte las alertas a cualquier sistema o flujo de trabajo personalizado mediante un webhook genérico.

<Info>
  **Integraciones disponibles solo en ClickHouse Cloud**

  Las integraciones de la API de Slack y de PagerDuty solo están disponibles en ClickHouse Cloud.
</Info>

Según el tipo de servicio, deberá proporcionar distintos datos. En concreto:

**Slack (Webhook URL)**

* URL del webhook. Por ejemplo: `https://hooks.slack.com/services/<unique_path>`. Consulte la [documentación de Slack](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/) para obtener más información.

**Slack (API)**

* Token del bot de Slack. Consulte la [documentación de Slack](https://docs.slack.dev/authentication/tokens/#bot/) para obtener más información.

**API de PagerDuty**

* Clave de integración de PagerDuty. Consulte la [documentación de PagerDuty](https://support.pagerduty.com/main/docs/api-access-keys) para obtener más información.

**Generic**

* URL del webhook
* Encabezados del webhook (opcional)
* Cuerpo del webhook (opcional). El cuerpo es una plantilla de Handlebars. Además de `{{title}}`, `{{body}}` y `{{link}}`, admite variables que describen la alerta y su activación, como `{{alertId}}`, `{{status}}`, `{{value}}`, `{{threshold}}` y `{{groupKey}}`. Consulte [Variables de plantilla para webhooks de alertas](https://github.com/ClickHouse/ClickStack/blob/main/docs/alert-webhook-template-variables.md) para ver la lista completa.

## Administración de alertas {#managing-alerts}

Seleccione **Alertas** en la barra lateral izquierda para administrar sus alertas. Puede buscar por nombre y filtrar por estado, fuente o tipo.

<div className="ch-image-lg">
  <Frame>
    ![Página de administración de alertas con Alertas resaltado en la barra lateral](/images/clickstack/observability-manage-alerts.png)
  </Frame>
</div>

Esta vista también muestra el historial de evaluaciones de las alertas. Las alertas se evalúan periódicamente, según un intervalo de tiempo definido por el período/duración que se configura al crear la alerta. En cada evaluación, el servicio consulta sus datos para comprobar si se cumple la condición de la alerta:

* **Barra roja**: la condición de umbral se cumplió en esta evaluación y la alerta se activó (se envió una notificación).
* **Barra verde**: la alerta se evaluó, pero no se cumplió la condición de umbral (no se envió ninguna notificación).

Cada evaluación es independiente: la alerta comprueba los datos de esa ventana de tiempo y solo se activa si la condición se cumple en ese momento.

En el ejemplo anterior, **Alert 1** tiene el estado **OK**, con barras verdes que corresponden a evaluaciones recientes en las que no se cumplió la condición de umbral.

Seleccione una alerta para abrir su página de detalles, donde se muestran su condición, el destino de las notificaciones y el historial de evaluaciones.

## Alertas de gráficos basadas en SQL {#sql-based-alerts}

Las alertas de gráficos basadas en SQL le permiten escribir cualquier consulta en SQL de ClickHouse para definir las condiciones de una alerta. Así, obtiene un control total sobre el filtrado, la agregación y los cálculos: todo lo que pueda expresar en SQL puede convertirse en una alerta.

### Tipos de gráfico compatibles {#supported-chart-types}

Las alertas basadas en SQL son compatibles con tres tipos de visualización de gráficos:

| Tipo de gráfico   | Comportamiento                                                                                                                                                             |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **línea**         | Alerta de time-series. La consulta debe generar filas agrupadas en intervalos de tiempo (buckets). Cada intervalo se evalúa de forma independiente con respecto al umbral. |
| **Barra Apilada** | Alerta de time-series. Se comporta igual que línea.                                                                                                                        |
| **Número**        | Alerta de valor único. La consulta devuelve un único resultado numérico, que se compara con el umbral una vez por evaluación.                                              |

Los demás tipos de gráficos basados en SQL (Tabla, Circular, Mapa de calor, etc.) no admiten alertas.

### Crear una alerta SQL {#create-sql-based-alert}

Para crear una alerta en un gráfico basado en SQL:

<Steps>

    Desde un panel de control guardado, [cree un nuevo gráfico con el modo de gráfico **SQL**](/es/clickstack/observability/features/dashboards/sql-visualizations) o abra un gráfico existente basado en SQL para editarlo.

    Elija **línea**, **Barra Apilada** o **Número** como tipo de visualización.

    * **Valor del umbral**: el valor numérico con el que se compara
    * **Interval**: la frecuencia con la que se evalúa la alerta (5m, 15m, 30m, 1h, 6h, 12h o 1d). También determina la ventana de tiempo de cada evaluación.

### Cómo se interpretan los resultados de la consulta {#sql-result-interpretation}

El sistema de alertas examina las columnas que devuelve su consulta SQL para determinar qué valor comparar con el umbral.

* **Columna de valor**: la **última columna numérica** de su cláusula `SELECT` se utiliza como valor de la alerta. Si su consulta devuelve varias columnas numéricas (p. ej., `count, avg_latency, p99_latency`), solo la última (`p99_latency`) se compara con el umbral.
* **Columna de marca de tiempo**: en los gráficos de time-series (línea y Barra Apilada), el sistema identifica la columna Date/DateTime de sus resultados como el intervalo de tiempo (es decir, el eje x de un gráfico de time-series). La columna de valor de cada intervalo de tiempo se evalúa frente al umbral de forma independiente y, si el valor de cualquier intervalo supera el umbral configurado, se disparará la alerta.
* **Columnas de grupo**: cualquier columna que no sea numérica ni de marca de tiempo (p. ej., `ServiceName`, `Environment`) se trata como una dimensión de agrupación. Cuando hay grupos, cada combinación única de valores de grupo se supervisa y genera alertas por separado. El servicio enviará una alerta por cada grupo cuyo valor supere el umbral configurado. Los grupos solo están disponibles en los gráficos de time-series.

### Parámetros de consulta y macros {#query-params}

Las consultas SQL de las alertas admiten parámetros de plantilla y macros que se reemplazan automáticamente en el momento de la evaluación. Son los mismos parámetros y macros disponibles al [crear un gráfico basado en SQL](/es/clickstack/observability/features/dashboards/sql-visualizations).

#### Parámetros obligatorios y recomendados {#required-alert-parameters}

Las consultas utilizadas para alertas de gráficos de líneas o de barras apiladas **deben** incluir un parámetro de intervalo o una macro (`{intervalSeconds:Int64}`, `{intervalMilliseconds:Int64}`, `$__timeInterval(col)` o `$__timeInterval_ms(col)`). Durante la ejecución de la alerta, se reemplazará por el período configurado en la alerta.

Las consultas utilizadas para alertas **deberían** incluir un filtro de intervalo de tiempo (`{startDateMilliseconds:Int64}` y `{endDateMilliseconds:Int64}`, o `$__timeFilter(col)`, etc.). Tanto si la consulta contiene un filtro de intervalo de tiempo como si no, la consulta de la alerta se ejecutará sobre el período configurado en la alerta. Si no hay ningún filtro de intervalo de tiempo, la consulta leerá en cada ejecución todo el intervalo de tiempo disponible en la tabla de origen.

<Warning>
  **Rango temporal de la alerta**

  Normalmente, las consultas de alertas se ejecutan una vez por intervalo. Sin embargo, si se omiten uno o más intervalos debido a errores o a consultas lentas, la siguiente ejecución utilizará un intervalo de tiempo que abarque los intervalos omitidos. En ese caso, los parámetros de intervalo de la consulta seguirán tomando el valor del período configurado en la alerta, pero los parámetros de rango temporal reflejarán el intervalo de tiempo más amplio.
</Warning>

### Ejemplos de consultas de alerta {#example-queries}

#### Tasa de errores por servicio (time-series) {#example-error-rate}

Genera una alerta cuando cualquier servicio tenga una tasa de errores del 5% o superior y más de 10 solicitudes en el período de la alerta, para evitar alertas innecesarias en servicios con poco tráfico.

```sql
WITH error_rates AS (
  SELECT
    $__timeInterval(Timestamp) as ts,
    ServiceName,
    countIf (SpanKind = 'Server') as request_count,
    countIf (
      SpanKind = 'Server'
      and StatusCode = 'Error'
    ) as error_count,
    error_count / request_count * 100 AS error_percent
  FROM $__sourceTable
  WHERE $__timeFilter(Timestamp)
  GROUP BY ts, ServiceName
)
SELECT ts, ServiceName, error_percent
FROM error_rates
WHERE request_count > 10
```

**Tipo de visualización**: línea o Barra Apilada
**Umbral**: `>= 5` (se activa cuando la tasa de errores alcanza el 5%)

En esta consulta, `ServiceName` es una columna que no es numérica ni de marca de tiempo, por lo que cada servicio se supervisa como un grupo de alertas independiente. La alerta se activa de forma independiente para cada servicio.

#### Detección de anomalías con media rezagada (time-series) {#example-anomaly-detection}

Genera una alerta cuando el recuento de errores supere la media móvil en más de dos desviaciones estándar. Así se detectan picos en relación con el valor de referencia del comportamiento reciente, en lugar de con un umbral fijo.

```sql
WITH buckets AS (
  SELECT
    $__timeInterval(Timestamp) AS ts,
    count() AS bucket_count
  FROM $__sourceTable
  WHERE TimestampTime >= fromUnixTimestamp64Milli({startDateMilliseconds:Int64})
        - toIntervalSecond($__interval_s * 30) -- Fetch 30 intervals back
    AND TimestampTime < fromUnixTimestamp64Milli({endDateMilliseconds:Int64})
    AND SeverityText = 'error'
  GROUP BY ts
  ORDER BY ts
  WITH FILL
    FROM toDateTime(fromUnixTimestamp64Milli({startDateMilliseconds:Int64}))
    TO toDateTime(fromUnixTimestamp64Milli({endDateMilliseconds:Int64}))
    STEP toIntervalSecond($__interval_s)
),

anomaly_detection AS (
  SELECT
    ts,
    bucket_count,
    avg(bucket_count) OVER (
      ORDER BY ts ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING
    ) AS previous_30_avg,
    stddevPop(bucket_count) OVER (
      ORDER BY ts ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING
    ) AS previous_30_stddev,
    greatest(
      bucket_count - (previous_30_avg + 2 * previous_30_stddev), 0
    ) AS excess_error_count
  FROM buckets
)

SELECT ts, excess_error_count
FROM anomaly_detection
WHERE ts >= fromUnixTimestamp64Milli({startDateMilliseconds:Int64})
  AND ts < fromUnixTimestamp64Milli({endDateMilliseconds:Int64})
```

**Tipo de visualización**: línea
**Umbral**: `> 0` (se activa cuando se detectan errores por encima del valor de referencia móvil)

Tenga en cuenta que la consulta recupera 30 intervalos *antes* del inicio del rango de fechas para inicializar los cálculos de la ventana móvil y, a continuación, filtra la salida final para que solo incluya la ventana de evaluación.

## Escenarios de alerta comunes {#common-alert-scenarios}

Estos son algunos escenarios de alerta habituales que puede configurar:

**Errores:** Recomendamos configurar alertas para las búsquedas guardadas predeterminadas
`All Error Events` y `HTTP Status >= 400`, de modo que reciba una notificación cuando
se produzca un número excesivo de errores.

**Operaciones lentas:** Puede configurar una búsqueda de operaciones lentas (p. ej.,
`duration:>5000`) y, a continuación, crear una alerta que se active cuando se produzcan demasiadas operaciones
lentas.

**Eventos de usuario:** También puede configurar alertas para que los equipos que trabajan de cara al cliente
reciban una notificación cuando se registren nuevos usuarios o se realice una acción crítica de usuario.
