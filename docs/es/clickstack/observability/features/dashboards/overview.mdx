ClickHouse Observability permite visualizar eventos e incluye compatibilidad nativa con la creación de gráficos en la interfaz de usuario. Estos gráficos pueden añadirse a dashboards para compartirlos con otros usuarios.

Es posible crear visualizaciones a partir de trazas, métricas, logs o cualquier esquema de eventos amplios definido por el usuario.

## Creación de visualizaciones {#creating-visualizations}

La interfaz **Explorador de Gráficos** (Chart Explorer) le permite visualizar métricas, trazas y logs a lo largo del tiempo, lo que facilita la creación de visualizaciones rápidas para el análisis de datos. Esta interfaz también se reutiliza al crear dashboards. En la siguiente sección se describe el proceso de creación de una visualización con Chart Explorer.

Cada visualización comienza con la selección de un **origen de datos**, seguido de una **métrica**, con **expresiones de filtro** y campos de **agrupación** opcionales. Conceptualmente, las visualizaciones se corresponden internamente con una consulta SQL `GROUP BY`: usted define las métricas que se agregarán según las dimensiones seleccionadas.

<Tip>
  **Generación de gráficos y dashboards con IA**

  ClickHouse Observability también permite crear gráficos a partir de instrucciones en lenguaje natural mediante la funcionalidad [De Texto a Gráfico](/es/clickstack/observability/text-to-chart). Describa lo que desea ver y la interfaz de usuario generará la visualización automáticamente. Para generar un dashboard completo con varios paneles, utilice [Text-to-Dashboard](/es/clickstack/observability/text-to-dashboard).
</Tip>

Por ejemplo, podría representar el número de errores (`count()`) agrupados por nombre de servicio.

En los siguientes ejemplos, utilizamos el conjunto de datos remoto disponible en [sql.clickhouse.com](https://sql.clickhouse.com). **También puede reproducir estos ejemplos en [play-clickstack.clickhouse.com](https://play-clickstack.clickhouse.com).**

## Creación de dashboards {#creating-dashboards}

Los dashboards permiten agrupar visualizaciones relacionadas para comparar métricas y explorar patrones en paralelo, con el fin de identificar posibles causas raíz en sus sistemas. Estos dashboards pueden utilizarse para investigaciones ad hoc o guardarse para una monitorización continua.

Los filtros globales pueden aplicarse a nivel de dashboard y se propagan automáticamente a todas sus visualizaciones. Esto permite un desglose coherente entre gráficos y simplifica la correlación de eventos entre servicios y tipos de telemetría.

A continuación, creamos un dashboard con dos visualizaciones a partir de las fuentes de datos de logs y trazas. Estos pasos pueden reproducirse en [play-clickstack.clickhouse.com](https://play-clickstack.clickhouse.com) o en local, conectándose al conjunto de datos alojado en [sql.clickhouse.com](https://sql.clickhouse.com).

  <Step title="Añada un bloque con un mapa de calor de la duración de los spans" id="create-a-tile-heatmap">
    Los bloques de mapa de calor representan como una cuadrícula de colores el número de eventos que caen en cada bucket (tiempo, valor). Use un mapa de calor cuando quiera ver la **forma** de una distribución a lo largo del tiempo, y no solo el promedio o un único percentil. Un mapa de calor de latencia revela patrones de duración bimodales, agrupaciones en la cola lenta o dispersiones repentinas que un gráfico de líneas diluiría al promediar.

    Para añadir un bloque de mapa de calor:

    1. Seleccione `Add`.
    2. Elija el tipo de visualización `Heatmap` en el menú superior. El desplegable de origen de datos solo muestra las fuentes cuyo [tipo de fuente es `Traces`](/es/clickstack/observability/managing/config#datasource-settings). Las fuentes de logs, métricas y sesiones se excluyen, ya que los mapas de calor necesitan una columna de duración de span que solo proporcionan las fuentes de trazas.
    3. Elija cualquiera de sus fuentes de trazas por su nombre. El nombre en sí es arbitrario; solo importa el tipo.

    Una vez seleccionada una fuente, el mapa de calor se rellena automáticamente con:

    * **Valor**: la `Duration Expression` de la fuente, escalada a la unidad de visualización actual (por ejemplo, `(Duration)/1e6` para convertir la duración del span de cada evento de nanosegundos a milisegundos)
    * **Count**: `count()`

    4. Asigne un nombre al gráfico y use `Where` para acotar el mapa de calor a un servicio específico o a un conjunto de operaciones cuyo rendimiento desee observar.
    5. Ajuste el intervalo de tiempo al período que le interese. Los rangos más amplios ponen de manifiesto cambios en la distribución y patrones de latencia bimodales que las ventanas más cortas pueden ocultar.

    El siguiente ejemplo muestra las duraciones de los spans del servicio `payment`: la mayoría se concentran en torno a un milisegundo, con spans más lentos dispersos por encima.

    Para personalizar aún más el mapa de calor, haga clic en **Configuración De Visualización** para abrir un panel deslizante con la **Escala** (Log o Linear) y las expresiones de **Valor** y **Count**. La lista completa de opciones está documentada en [Personalizar el mapa de calor](/es/clickstack/observability/features/event-deltas#customize), en la página de Deltas de eventos, ya que se utiliza el mismo panel deslizante.

    Haga clic en `Run` para previsualizar el gráfico y, a continuación, en `Save`.

    </div>

### Configuración de visualización del bloque {#tile-display-settings}

Cada bloque dispone de un panel deslizante **Configuración De Visualización** con opciones que controlan cómo se muestra su valor. Para abrirlo, haga clic en **Configuración De Visualización** en el editor del bloque. Las opciones disponibles dependen del tipo de visualización.

#### Color del tile numérico {#number-tile-color}

Los mosaicos numéricos admiten un **Color** estático elegido de la paleta de gráficos predefinida. Con un mosaico numérico seleccionado, abra **Configuración De Visualización** y use el control **Color** (etiquetado como **Number tile color** por motivos de accesibilidad) para elegir una muestra, o borre la selección para usar el color de texto predeterminado.

Los colores se almacenan como tokens de paleta, no como valores hexadecimales directos, por lo que el mismo mosaico se adapta correctamente a los temas claro, oscuro e IDE.

**Tokens categóricos** (tonos para varias series):

| Token              | Etiqueta   |
| ------------------ | ---------- |
| `chart-blue`       | Azul       |
| `chart-orange`     | Naranja    |
| `chart-red`        | Rojo       |
| `chart-cyan`       | Cian       |
| `chart-green`      | Verde      |
| `chart-pink`       | Rosa       |
| `chart-purple`     | Morado     |
| `chart-light-blue` | Azul claro |
| `chart-brown`      | Marrón     |
| `chart-gray`       | Gris       |

**Tokens semánticos** (orientados al estado):

| Token           | Etiqueta    |
| --------------- | ----------- |
| `chart-success` | Éxito       |
| `chart-warning` | Advertencia |
| `chart-error`   | Error       |

Use tokens semánticos cuando el número represente un estado (por ejemplo, un recuento de errores en `chart-error` o una tasa satisfactoria en `chart-success`). Use tokens categóricos cuando quiera diferenciar visualmente mosaicos de KPI relacionados sin sugerir un estado.

Es posible que las configuraciones antiguas sigan almacenando tokens numéricos heredados (de `chart-1` a `chart-10`). Al cargar un panel de control, la interfaz de usuario los asigna a los tokens con nombre de tono indicados arriba.

La misma paleta se utiliza en las **reglas de color** opcionales del mismo panel deslizante: condiciones ordenadas que se evalúan sobre el valor mostrado (prevalece la última coincidencia). Si no coincide ninguna regla, se aplica el color estático y, en su defecto, el color de texto predeterminado.

#### Gráfico de fondo del tile numérico {#number-tile-background-chart}

Los mosaicos numéricos pueden mostrar un **gráfico de fondo**: un minigráfico de tendencia dibujado detrás del valor, de modo que su evolución a lo largo del intervalo de tiempo seleccionado se aprecia de un vistazo. Esto resulta útil para los mosaicos de SLO y de presupuesto de errores, donde la tendencia de un valor importa tanto como su lectura actual.

Con un tile numérico seleccionado, abra **Display Settings** y establezca **Background chart** en **Line** o **Area** (o en **None** para desactivarlo). El minigráfico se obtiene a partir de una versión de la consulta del tile agrupada por intervalos de tiempo, por lo que no hace falta ninguna configuración adicional. De forma predeterminada, hereda el color del tile; establezca un **Background color** para sustituirlo por un color específico de la paleta.

<div className="ch-image-lg">
  <Frame>
    ![Panel deslizante de Display Settings de un tile numérico, con Background chart establecido en Area](/images/clickstack/dashboards/number-tile-background-chart.webp)
  </Frame>
</div>

Los gráficos de fondo se aplican a los mosaicos numéricos creados con el constructor de consultas. Los mosaicos numéricos de SQL directo devuelven un único valor sin una dimensión temporal que agrupar, por lo que la opción aparece, pero está deshabilitada.

Los mosaicos de tabla pueden alternar el fondo de sus filas con **Alternate Row Background**, que sombrea una de cada dos filas para facilitar la lectura de tablas anchas. Esta opción está desactivada de forma predeterminada.

Con un mosaico de tabla seleccionado, abra **Display Settings** y active **Alternate Row Background**. El sombreado alterno es puramente visual, por lo que funciona tanto en mosaicos de tabla creados con el constructor de consultas como en los de SQL directo.

<div className="ch-image-lg">
  <Frame>
    ![Panel deslizante de Display Settings de un mosaico de tabla, con Alternate Row Background activado](/images/clickstack/dashboards/table-tile-display-settings.webp)
  </Frame>
</div>

Los mosaicos de tabla también mantienen un separador entre la fila de encabezado y los datos al desplazarse, de modo que los encabezados de columna siguen distinguiéndose con claridad.

#### API de dashboards: color del tile numérico {#api-number-tile-color}

Al crear o actualizar dashboards mediante la API externa (`POST` / `PUT` `/api/v2/dashboards`), asigne a `color` un token de la paleta en la configuración de un tile numérico del constructor. No se admiten valores hexadecimales directos.

```json
{
  "name": "Error rate KPIs",
  "tiles": [
    {
      "id": "65f5e4a3b9e77c001a222222",
      "name": "Errors",
      "x": 0,
      "y": 0,
      "w": 6,
      "h": 4,
      "config": {
        "displayType": "number",
        "sourceId": "<SOURCE_ID>",
        "select": [
          {
            "aggFn": "count",
            "where": "SeverityText:error",
            "whereLanguage": "lucene",
            "alias": "Errors"
          }
        ],
        "color": "chart-error",
        "backgroundChart": {
          "type": "area"
        }
      }
    }
  ]
}
```

`color` acepta cualquier token de las listas categórica y semántica anteriores (por ejemplo, `chart-blue` o `chart-success`). El campo opcional `backgroundChart.color` sobrescribe el color del minigráfico con el mismo enum de tokens. Consulte la [Referencia de la API](/es/clickstack/observability/api-reference) para obtener información sobre la autenticación y las URL base.

## Dashboards: etiquetado {#tagging}

Puede añadir etiquetas a los dashboards y a las búsquedas guardadas para organizarlos mejor.
Las etiquetas ofrecen una forma flexible de clasificarlos y filtrarlos según sus necesidades.

#### Cómo funcionan las etiquetas {#how-tags-work}

* **Organización**: las etiquetas aparecen en la barra lateral izquierda, donde los dashboards y las búsquedas guardadas se agrupan según las etiquetas que tengan asignadas
* **Varias etiquetas**: puede añadir una o varias etiquetas a un mismo elemento para categorizarlo mejor
* **Creación automática**: si asigna una etiqueta que aún no existe, se creará automáticamente
* **Administración sencilla**: puede añadir o quitar etiquetas en cualquier momento para ajustar su forma de organizar el contenido

Así resulta fácil encontrar elementos relacionados y mantener un workspace ordenado a medida que crece su colección.

Abra el menú **Tags** del dashboard para seleccionar o crear etiquetas. Puede asignar varias etiquetas al mismo dashboard, como se muestra a continuación:

## Filtros personalizados y variables {#custom-filters}

Además de los [filtros de texto libre](#filter-dashboards) disponibles en todos los dashboards, los dashboards guardados admiten filtros personalizados y variables. Estos ofrecen controles reutilizables basados en clics, de modo que quienes consultan el dashboard puedan filtrar sin tener que escribir expresiones manualmente. Sus valores pueden proceder de una columna consultada desde una fuente, de una lista escrita a mano, de una consulta SQL, de valores de etiquetas de Prometheus o de condiciones clave-valor elegidas libremente. Las variables también pueden determinar qué origen de datos o conexión consulta un bloque. Consulte [Tipos de filtro](#filter-types) para ver la lista completa.

<div className="ch-image-lg">
  <Frame>
    ![Filtro desplegable de servicios que muestra los nombres de servicio disponibles](/images/clickstack/dashboards/filter-dropdown.webp)
  </Frame>
</div>

Cada filtro permite al usuario elegir uno o varios valores y hacer con ellos una de las siguientes acciones, o ambas:

* **Difusión** — aplica la selección como condición de filtrado en los bloques coincidentes. No es necesario modificar los bloques para que hagan referencia al filtro.
* **Variable** — expone la selección a las consultas de los bloques como `$variableName`, de modo que cada bloque decide dónde y cómo se usa el valor.

Las opciones que admite un filtro dependen de su [tipo](#filter-types). Un filtro **SQL expression values** debe realizar al menos una de las dos y se difunde de forma predeterminada.

Los siguientes pasos muestran cómo añadir un filtro al dashboard creado en la sección [&quot;Creación de dashboards&quot;](#creating-dashboards).

<Steps>

### Tipos de filtro {#filter-types}

El selector **Tipo** del cuadro de diálogo del filtro determina de dónde provienen los valores de un filtro y cómo llegan a los bloques.

| Tipo                                                       | Origen de los valores                                                                                     | Difusión                                     | Variable                                                             |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------- |
| [Valores de expresión SQL](#sql-expression-values-filters) | Los valores distintos de una expresión, consultados en una fuente                                         | Opcional, habilitada de forma predeterminada | Opcional                                                             |
| [Valores estáticos](#static-values-filters)                | Una lista escrita manualmente                                                                             | No                                           | Siempre                                                              |
| [Valores de consulta SQL](#sql-query-filters)              | La primera columna de una consulta SQL                                                                    | No                                           | Siempre                                                              |
| [Valores de etiqueta PromQL](#promql-label-filters)        | Los valores de una etiqueta de Prometheus                                                                 | No                                           | Siempre                                                              |
| [Claves y valores ad hoc](#adhoc-filters)                  | Condiciones `key operator value` construidas a partir de las claves y los valores de una o varias fuentes | Siempre                                      | No                                                                   |
| [Origen de datos](#data-source-variables)                  | Las fuentes del equipo                                                                                    | No                                           | Siempre, como [referencia de fuente](#source-connection-variables)   |
| [Conexión](#connection-variables)                          | Las conexiones de ClickHouse del equipo                                                                   | No                                           | Siempre, como [referencia de conexión](#source-connection-variables) |

#### Valores de expresión SQL {#sql-expression-values-filters}

Su lista desplegable muestra los valores distintos de la **Expresión de filtrado** en el **Origen de datos** seleccionado, que pueden acotarse opcionalmente mediante un **Filtro de valores de la lista desplegable**. Para las fuentes de métricas, elija también un **Tipo de métrica**. Un filtro de valores de expresión SQL puede [difundir](#broadcast-filters) su selección, estar [disponible como variable](#dashboard-variables) o ambas cosas.

#### Valores estáticos {#static-values-filters}

Su lista desplegable ofrece una lista de valores introducidos manualmente. Escriba cada valor en **Options** y pulse Intro. Un filtro puede contener hasta 1000 opciones.

Un filtro de valores estáticos siempre es una variable y nunca se aplica por difusión, por lo que los bloques lo usan haciendo referencia a su variable, por ejemplo, `$__filter(SeverityText, $severity)`. Resulta útil para valores que no están almacenados en una columna o para una lista fija y seleccionada a medida.

#### Valores de consulta SQL {#sql-query-filters}

Su lista desplegable muestra la primera columna devuelta por una consulta en SQL de ClickHouse, en el orden en que la consulta devuelve las filas, hasta un máximo de 10,000 valores. Configure:

* **Conexión**: la conexión de ClickHouse en la que se ejecuta la consulta, o una [variable de conexión](#connection-variables).
* **Fuente**: opcional. Una fuente de la misma conexión, o una [variable de origen de datos](#data-source-variables). Si se selecciona una fuente, la consulta puede usar `$__sourceTable` y `$__filters`, que aplica a esa fuente las selecciones de los filtros de difusión del dashboard, del mismo modo que los [bloques de SQL directo](/es/clickstack/observability/features/dashboards/sql-visualizations#dashboard-filter-macro).
* **Consulta SQL**: la consulta en sí. Puede usar las [macros de tiempo](/es/clickstack/observability/features/dashboards/sql-visualizations#time-filter-macros) y hacer referencia a las demás variables del dashboard. El editor muestra una vista previa de los valores que devuelve la consulta para el intervalo de tiempo actual del dashboard.

Por ejemplo, la siguiente consulta muestra los servicios que registraron eventos en el intervalo de tiempo del dashboard, limitados a los entornos seleccionados en un filtro `environment`:

```sql
SELECT DISTINCT ServiceName
FROM otel_logs
WHERE $__timeFilter(TimestampTime)
  AND $__filter(ResourceAttributes['deployment.environment'], $environment)
ORDER BY ServiceName
```

Un filtro de valores de consulta SQL siempre es una variable y nunca se aplica por difusión.

#### Valores de etiqueta de PromQL {#promql-label-filters}

<PrivatePreviewBadge />

Su lista desplegable muestra los valores de una etiqueta de Prometheus. Seleccione un **Origen de datos** de PromQL e introduzca la **Etiqueta** cuyos valores aparecerán en la lista desplegable, como `job`, `instance` o `__name__`. Opcionalmente, introduzca **Comparadores de series**: un selector de series de Prometheus, como `up{job="api"}`, que limita las series de las que se leen los valores. Los comparadores de series pueden hacer referencia a las demás variables del panel de control.

Un filtro de valores de etiqueta de PromQL siempre es una variable y nunca se aplica por difusión. En los bloques de PromQL, haga referencia a él dentro de un comparador de etiquetas, por ejemplo `rate(http_requests_total{job=~"$job"}[$__rate_interval])`. Consulte [Hacer referencia a una variable](#referencing-variables) para saber cómo se generan los valores.

#### Claves y valores ad hoc {#adhoc-filters}

En lugar de ofrecer una única lista desplegable, un filtro ad hoc permite al usuario crear una lista de condiciones `key operator value` a partir de las claves de sus fuentes: columnas y claves de mapas en las fuentes SQL, o etiquetas en las fuentes de Prometheus. Las claves y los valores se sugieren a medida que el usuario escribe. Opciones de configuración:

* **Tipo de fuente**: SQL (fuentes de logs, trazas o sesiones) o Prometheus.
* **Fuentes de datos**: las fuentes cuyas claves y valores sugiere el filtro.
* **Filtro de claves y valores**: opcional, solo para fuentes SQL. Una condición SQL o Lucene que restringe las filas a partir de las cuales se sugieren claves y valores. Puede hacer referencia a las demás variables del dashboard.
* **Se aplica a las fuentes**: las fuentes a las que se difunden las condiciones. Déjelo vacío para difundirlas a todos los bloques que usen alguna de las fuentes de datos del filtro.
* **Nombre único**: identifica las condiciones del filtro en la [URL del dashboard](/es/clickstack/observability/url-parameters#dashboard-filter-values).

Las condiciones sobre fuentes SQL admiten los siguientes operadores: `=`, `!=`, `=~` (regex), `!~` (regex), `LIKE`, `NOT LIKE`, `IN`. Las condiciones sobre fuentes de Prometheus admiten `=`, `!=`, `=~` (regex), `!~` (regex) e `IN`; `LIKE` y `NOT LIKE` son exclusivos de SQL.

Los usuarios también pueden añadir una condición haciendo clic en un valor de un bloque de tabla, serie temporal o búsqueda del dashboard.

Las condiciones ad hoc siempre se difunden y no se pueden referenciar como variables. Los bloques del creador de gráficos y los bloques PromQL que usan las fuentes correspondientes las aplican automáticamente, y los bloques de SQL directo las aplican mediante la [macro `$__filters`](/es/clickstack/observability/features/dashboards/sql-visualizations#dashboard-filter-macro).

#### Origen de datos {#data-source-variables}

Una variable de origen de datos permite que el usuario elija qué fuente consulta un bloque. Seleccione los **Source kinds** que se ofrecen en su lista desplegable (por ejemplo, solo fuentes de logs) y, opcionalmente, restrínjalos a una única **Connection**, que a su vez puede ser una variable de conexión. Consulte [Variables de origen de datos y de conexión](#source-connection-variables) para ver cómo la utilizan los bloques y los filtros.

#### Conexión {#connection-variables}

Una variable de conexión permite al usuario elegir qué conexión de ClickHouse utilizan los bloques de SQL directo, los filtros de valores de consulta SQL y las variables de origen de datos. No tiene más ajustes que su nombre.

### Variables de origen de datos y de conexión {#source-connection-variables}

Las variables de origen de datos y de conexión sustituyen a una fuente o a un ID de conexión, en lugar de a un valor dentro del texto de la consulta. Allí donde un selector de fuente o de conexión las admite, las variables del panel de control aparecen en un grupo **Variables**. Al elegir una, se almacena una referencia `$name` que se resuelve según la selección actual de quien visualiza el panel. Esto permite crear un único panel de control que alterne, por ejemplo, entre los logs de varios entornos o entre varios clústeres de ClickHouse.

| Se usa en                                | Admite una variable de origen de datos | Admite una variable de conexión |
| ---------------------------------------- | -------------------------------------- | ------------------------------- |
| Bloques del creador de gráficos          | Fuente                                 | —                               |
| Bloques de SQL directo                   | Fuente                                 | Conexión                        |
| Bloques de PromQL                        | Fuente                                 | —                               |
| Filtros de valores de expresión SQL      | Origen de datos, Se aplica a fuentes   | —                               |
| Filtros de valores de etiqueta de PromQL | Origen de datos                        | —                               |
| Filtros ad hoc                           | Fuentes de datos, Se aplica a fuentes  | —                               |
| Filtros de valores de consulta SQL       | Fuente                                 | Conexión                        |
| Variables de origen de datos             | —                                      | Conexión                        |

Una variable de origen de datos solo se ofrece cuando al menos uno de sus tipos de fuente es compatible. Por ejemplo, un bloque de PromQL solo ofrece variables de origen de datos que admitan fuentes de PromQL.

Las variables de origen de datos y de conexión son siempre de selección única y obligatorias, ya que un bloque no puede ejecutar consultas sin una fuente o una conexión. Hasta que se selecciona un valor, los bloques y filtros que hacen referencia a la variable quedan a la espera. Si prefiere que espere todo el panel de control, active **Block every tile**. Un [enlace al panel de control](/es/clickstack/observability/url-parameters#dashboard-filter-values) puede seleccionar una fuente o conexión tanto por nombre como por ID.

<Note>
  Las alertas no están disponibles en los bloques que usan una variable de origen de datos o de conexión. Al guardar un bloque de este tipo, se elimina su alerta.
</Note>

### Opciones de selección {#filter-selection-options}

Los filtros de tipo valores de expresión SQL, valores estáticos, valores de consulta SQL y valores de etiqueta de PromQL tienen estas opciones adicionales:

* **Selección única**: solo se puede seleccionar un valor a la vez.
* **Obligatorio**: los bloques que usan el filtro, ya sea a través de su variable o mediante difusión, no se cargan hasta que el filtro tenga una selección.
  * **Bloquear todos los bloques**: bloquea todos los bloques del panel de control hasta que el filtro tenga una selección, no solo los que lo usan.

### Filtros encadenados {#chained-filters}

La configuración de un filtro puede hacer referencia a otras variables del panel de control, de modo que sus valores dependan de la selección de otro filtro. Por ejemplo, un filtro de servicios puede mostrar solo los servicios del entorno seleccionado en un filtro `environment`. Las variables se pueden referenciar en:

* El campo **Dropdown values filter** de un filtro de valores de expresión SQL, por ejemplo `$__filter(ResourceAttributes['deployment.environment'], $environment)`.
* El campo **SQL query** de un filtro de valores de consulta SQL.
* El campo **Series matchers** de un filtro de valores de etiqueta de PromQL, por ejemplo `up{env="$env"}`.
* El campo **Keys and values filter** de un filtro ad hoc.
* Los campos de fuente y de conexión, mediante las [variables de origen de datos y de conexión](#source-connection-variables).

Cuando cambia la selección del filtro referenciado, los valores del filtro dependiente se vuelven a consultar. Mientras un filtro obligatorio referenciado no tenga ninguna selección, un filtro ad hoc que dependa de él no podrá añadir ni editar condiciones, e indicará el nombre del filtro del que está a la espera.

### Difusión {#broadcast-filters}

Los filtros de valores de expresión SQL pueden difundir su selección, y los filtros ad hoc siempre difunden sus condiciones. Con **Broadcast filter condition** habilitado en un filtro de valores de expresión SQL, los valores seleccionados se aplican como condición de filtrado en los bloques del dashboard, sin que ningún bloque tenga que hacer referencia explícita al filtro. De forma predeterminada, la condición se aplica a todos los bloques. Utilice **Applies to sources** para limitarla a los bloques que usan un conjunto determinado de fuentes, algo útil cuando la expresión del filtro solo tiene sentido para una parte de los datos del dashboard.

Los bloques del creador de gráficos aplican automáticamente los filtros de difusión. Los bloques de SQL directo deben incluir la [macro `$__filters`](/es/clickstack/observability/features/dashboards/sql-visualizations#dashboard-filter-macro) y tener una fuente seleccionada, ya que la interfaz de usuario no puede inferir en qué punto de una consulta escrita manualmente debe ir la condición.

### Variables {#dashboard-variables}

Los filtros de valores estáticos, de valores de consulta SQL y de valores de etiquetas PromQL son siempre variables. Un filtro de valores de expresión SQL se convierte en variable cuando **Available as variable** está habilitado. Una variable expone la selección del filtro a las consultas de los bloques como `$variableName`. De forma predeterminada, **Variable name** toma el nombre visible del filtro sin los caracteres no válidos, y se puede sobrescribir. Los nombres deben comenzar con una letra y solo pueden contener letras, dígitos y guiones bajos.

Los filtros ad hoc nunca son variables, y las variables de origen de datos y de conexión son [referencias a una fuente o conexión](#source-connection-variables), no valores en el texto de la consulta.

Use una variable cuando no le interese difundir una condición `WHERE`; por ejemplo, para incluir el valor en una expresión `SELECT`, en una cláusula `HAVING` o en una join key, o para filtrar un bloque por una columna distinta de la expresión del propio filtro.

#### Referenciar una variable {#referencing-variables}

Una variable se expande a los valores seleccionados en ese momento en su lista desplegable. La forma de la referencia determina el resultado generado:

| Referencia          | Se expande a                                                                                                                                                                                                                       | Selección vacía                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `$name`, `${name}`  | Los valores seleccionados, en formato `sqlstring` o `lucene`, según el contexto. Las llaves delimitan el nombre cuando va seguido de caracteres de palabra, como en `${name}_total`.                                               | `NULL`                                  |
| `${name:sqlstring}` | Los valores seleccionados, entre comillas simples, separados por comas y escapados como valores SQL, p. ej., `'a', 'b'`                                                                                                            | `NULL`                                  |
| `${name:csv}`       | Sin comillas y separados por comas: `a,b`. No se escapan para SQL.                                                                                                                                                                 | cadena vacía                            |
| `${name:regex}`     | Una alternancia de expresión regular, con escapado de expresión regular: `(a\|b)`.                                                                                                                                                 | `.*`                                    |
| `${name:lucene}`    | Un `OR` de términos entre comillas, para entradas Lucene: `("a" OR "b")`.                                                                                                                                                          | `("")`                                  |
| `${name:promql}`    | La forma predeterminada en los bloques PromQL. Para un filtro de selección única, el valor seleccionado, para usarlo en `label="$name"`. En caso contrario, una alternancia de expresión regular, para usarla en `label=~"$name"`. | `.*` (cadena vacía con selección única) |

Dado que `$name` se genera como `NULL` mientras no haya nada seleccionado, es preferible usar las siguientes macros siempre que se espere un predicado SQL. Ambas macros se expanden a `1=1` mientras su variable no tenga ninguna selección, de modo que la consulta sigue siendo válida:

| Macro                                         | Descripción                                                                                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `$__filter($<variable>)`                      | Se expande a `toString(<filter expression>) IN ($variable)` cuando hay valores seleccionados para `variable` y, en caso contrario, a `1=1`. |
| `$__filter(<expression>, $<variable>)`        | Se expande a `<expression> IN ($variable)` cuando hay valores seleccionados para `variable` y, en caso contrario, a `1=1`.                  |
| `$__conditionalAll(<condition>, $<variable>)` | Se expande a `<condition>` cuando la variable tiene una selección y, en caso contrario, a `1=1`.                                            |

#### Uso de variables en bloques del creador de gráficos {#variables-in-builder-tiles}

Todas las entradas de expresión SQL del creador de gráficos aceptan referencias a variables: columnas de `SELECT` y expresiones por serie, `WHERE`, `GROUP BY` y `HAVING`. El editor autocompleta las variables del panel de control y muestra en qué se expande cada referencia para la selección actual.

En modo SQL, es preferible usar las macros `$__filter` y `$__conditionalAll`, para que las consultas sigan siendo válidas cuando no haya ningún valor seleccionado en las variables. Las macros no están disponibles en las entradas de Lucene; en ellas, haga referencia directamente a las variables sin procesar (p. ej., `ServiceName:$service`).

En una entrada de Lucene, el hecho de que la referencia a la variable esté o no entre comillas determina cómo se evalúa la coincidencia de una selección de varios valores. Si `$service` tiene seleccionados `a,b`:

| Referencia               | Se expande a                           | Comportamiento de coincidencia                                                                        |
| ------------------------ | -------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `ServiceName:$service`   | `ServiceName:("a" OR "b")`             | Coincidencia de subcadena: se traduce a SQL como `ServiceName ILIKE '%a%' OR ServiceName ILIKE '%b%'` |
| `ServiceName:"$service"` | `(ServiceName:"a" OR ServiceName:"b")` | Coincidencia exacta con cada valor seleccionado                                                       |

Ponga la referencia a la variable entre comillas (`Field:"$var"`) cuando los valores seleccionados deban coincidir exactamente con `Field` y no como subcadenas.

#### Uso de variables en bloques SQL {#variables-in-sql-tiles}

Los bloques de SQL directo hacen referencia a las variables de la misma forma, en cualquier parte de la consulta:

```sql
SELECT
  $__timeInterval(TimestampTime) AS ts,
  count() AS count
FROM otel_logs
WHERE $__timeFilter(TimestampTime)
  AND $__filter(ServiceName, $service)
  AND $__conditionalAll(SeverityText NOT IN ($severity), $severity)
GROUP BY ts
ORDER BY ts ASC
```

Consulte [Visualizaciones basadas en SQL](/es/clickstack/observability/features/dashboards/sql-visualizations#dashboard-variables) para ver la lista completa de macros disponibles en los bloques SQL.

<Note>
  Las alertas de un bloque que hace referencia a una variable del dashboard se evalúan con todas las variables vacías, no con los valores seleccionados en el dashboard.
</Note>
