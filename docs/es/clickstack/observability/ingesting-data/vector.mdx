    <Note>
      Esta guía solo se aplica a **Self-managed ClickHouse Observability**. El destino de ClickHouse de Vector escribe directamente en tablas que usted administra. La versión totalmente gestionada de ClickHouse Observability requiere ingestión mediante OTLP; consulte [Ingesta con OpenTelemetry](/es/clickstack/observability/ingesting-data/opentelemetry#fully-managed) para conocer los ajustes del endpoint y de autenticación.
    </Note>

    [Vector](https://vector.dev) es una canalización de datos de observabilidad de alto rendimiento e independiente del proveedor. Se utiliza habitualmente para recopilar, transformar y enrutar logs y métricas desde una amplia variedad de fuentes, y es especialmente popular para la ingestión de logs gracias a su flexibilidad y a su bajo consumo de recursos.

    Al usar Vector con Self-managed ClickHouse Observability, los usuarios son responsables de definir sus propios esquemas. Estos esquemas pueden seguir las convenciones de OpenTelemetry, pero también pueden ser completamente personalizados y representar estructuras de eventos definidas por el usuario. En la práctica, la ingestión con Vector se utiliza sobre todo para **logs**, casos en los que los usuarios quieren tener control total sobre el análisis y el enriquecimiento antes de que los datos se escriban en ClickHouse.

    Esta guía se centra en la ingesta de datos en Self-managed ClickHouse Observability mediante Vector. Para simplificar, no trata en profundidad las fuentes de Vector ni la configuración de la canalización, sino que se centra en configurar el **destino** (sink) que escribe los datos en ClickHouse y en garantizar que el esquema resultante sea compatible con Self-managed ClickHouse Observability.

    El único requisito estricto del servicio es que los datos incluyan una **columna de marca de tiempo** (o un campo de tiempo equivalente), que puede declararse al configurar el origen de datos en la interfaz de usuario de observabilidad.

## Envío de datos con Vector {#sending-data-with-vector-self-configured}

    <br />

    En esta guía se da por hecho que ya ha creado un servicio de Self-managed ClickHouse Observability y que ha guardado las credenciales del servicio. Si aún no lo ha hecho, siga la guía de [Primeros pasos](/es/clickstack/self-configured/getting-started/managed) de Self-managed ClickHouse Observability hasta que se le pida configurar Vector.

    <Steps>
      <Step title="Cree una base de datos y una table" id="create-a-database-table-self-configured">
        Vector requiere que se definan una tabla y un esquema antes de la ingesta de datos.

        Primero, cree una base de datos. Puede hacerlo desde la [consola de ClickHouse Cloud](/es/products/cloud/features/sql-console-features/sql-console).

        En el siguiente ejemplo, usamos `logs`:

        ```sql
        CREATE DATABASE IF NOT EXISTS logs
        ```

        Cree una tabla para sus datos. Esta debe coincidir con el esquema de salida de sus datos. En el siguiente ejemplo se asume una estructura clásica de Nginx. Adáptela a sus datos siguiendo las [buenas prácticas de esquema](/es/concepts/best-practices/select-data-type). Le **recomendamos encarecidamente** que se familiarice con el [concepto de claves primarias](/es/concepts/core-concepts/primary-indexes) y que seleccione su clave primaria según las pautas descritas [aquí](/es/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key).

        ```sql
        CREATE TABLE logs.nginx_logs
        (
            `time_local` DateTime,
            `remote_addr` IPv4,
            `remote_user` LowCardinality(String),
            `request` String,
            `status` UInt16,
            `body_bytes_sent` UInt64,
            `http_referer` String,
            `http_user_agent` String,
            `http_x_forwarded_for` LowCardinality(String),
            `request_time` Float32,
            `upstream_response_time` Float32,
            `http_host` String
        )
        ENGINE = MergeTree
        ORDER BY (toStartOfMinute(time_local), status, remote_addr)
        ```

        <Info>
          **Clave primaria de Nginx**

          La clave primaria anterior se basa en los patrones de acceso habituales en la interfaz de usuario de observabilidad para los logs de Nginx, pero es posible que deba ajustarla según su workload en entornos de producción.
        </Info>
      </Step>

      <Step title="Añada un destino de ClickHouse a la configuración de Vector" id="add-clickhouse-sink-to-config-self-configured">
        Modifique su configuración de Vector para incluir el destino de ClickHouse y actualice el campo `inputs` para que reciba eventos de sus canalizaciones existentes.

        Esta configuración supone que su canalización upstream de Vector ya ha **preparado los datos para que coincidan con el esquema de ClickHouse de destino**, es decir, que los campos se han analizado, tienen los nombres correctos y están tipados adecuadamente para la inserción. Consulte el [**ejemplo de Nginx más abajo**](#example-dataset-with-vector-self-configured) para ver un caso completo de cómo analizar y normalizar líneas de registro sin procesar para ajustarlas a un esquema adecuado para el servicio.

        ```yaml
        sinks:
          clickhouse:
            type: clickhouse
            inputs:
              - your_input
            endpoint: "<CLICKHOUSE_ENDPOINT>"
            database: logs
            format: json_each_row
            table: nginx_logs
            skip_unknown_fields: true
            auth:
              strategy: "basic"
              user: "default"
              password: "<CLICKHOUSE_PASSWORD>"
        ```

        De forma predeterminada, recomendamos usar el formato **`json_each_row`**, que codifica cada evento como un único objeto JSON por fila. Este es el formato predeterminado y recomendado por el servicio para ingestar datos JSON, y es preferible a formatos alternativos, como los objetos JSON codificados como cadenas.

        El destino de ClickHouse también admite la **codificación Arrow stream** (actualmente en Beta). Puede ofrecer un mayor caudal, pero conlleva restricciones importantes: la base de datos y la tabla deben ser estáticas, ya que el esquema se recupera una sola vez durante el inicio, y no se admite el enrutamiento dinámico. Por este motivo, la codificación Arrow resulta más adecuada para canalizaciones de ingestión fijas y bien definidas.

        Recomendamos revisar las opciones de configuración disponibles para el destino en la [documentación de Vector](https://vector.dev/docs/reference/configuration/sinks/clickhouse):

        <Note>
          El ejemplo anterior utiliza el usuario `default` de Self-managed ClickHouse Observability. Para implementaciones en producción, recomendamos [crear un usuario de ingestión dedicado](/es/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) con los permisos y límites adecuados.
        </Note>
      </Step>

      <Step title="Acceda a la interfaz de usuario de observabilidad" id="navigate-to-clickstack-ui-self-configured">
        Vaya a su servicio de Self-managed ClickHouse Observability y seleccione &quot;ClickStack&quot; en el menú de la izquierda. Si ya completó el onboarding, se abrirá la interfaz de usuario de observabilidad en una nueva pestaña y la autenticación se realizará automáticamente. De lo contrario, puede continuar con el onboarding y seleccionar “Launch ClickStack” una vez que haya elegido Vector como fuente de entrada.

      </Step>

      <Step title="Crear un origen de datos" id="create-a-datasource-managed-self-configured">
        Cree un origen de datos de logs. Si no existe ningún origen de datos, se le pedirá que cree uno la primera vez que inicie sesión. De lo contrario, vaya a la configuración del equipo y agregue un nuevo origen de datos.

        <div className="ch-image-lg">
          <Frame>
            ![Crear origen de datos - vector](/images/clickstack/create-vector-datasource.webp)
          </Frame>
        </div>

        La configuración anterior presupone un esquema de estilo Nginx con una columna `time_local` como marca de tiempo. Siempre que sea posible, esta debe ser la columna de marca de tiempo declarada en la clave primaria. Esta columna es obligatoria.

        También recomendamos actualizar `Default SELECT` para definir explícitamente qué columnas se devuelven en la vista de logs. Si hay campos adicionales disponibles, como el nombre del servicio, el nivel de registro o una columna de cuerpo, también pueden configurarse. Asimismo, la columna de marca de tiempo que se muestra puede sobrescribirse si difiere de la columna utilizada en la clave primaria de la tabla y configurada anteriormente.

        En el ejemplo anterior, los datos no contienen una columna `Body`. En su lugar, se define mediante una expresión SQL que reconstruye una línea de registro de Nginx a partir de los campos disponibles.

        Para conocer otras opciones, consulte la [referencia de configuración](/es/clickstack/self-configured/managing/config).
      </Step>

## Conjunto de datos de ejemplo con Vector {#example-dataset-with-vector-self-configured}

    En la siguiente guía se da por hecho que ya ha creado un servicio de Self-managed ClickHouse Observability y ha anotado las credenciales del servicio. Si aún no lo ha hecho, siga la guía [Primeros pasos](/es/clickstack/self-configured/getting-started/managed) de Self-managed ClickHouse Observability hasta que se le pida configurar Vector.

      <Step title="Cree una base de datos y una table" id="create-database-table-nginx-managed-self-configured">
        Vector requiere que se definan una tabla y un esquema antes de la ingesta de datos.

        Primero, cree una base de datos. Puede hacerlo desde la [consola de ClickHouse Cloud](/es/products/cloud/features/sql-console-features/sql-console).

        Cree una base de datos llamada `logs`:

        ```sql
        CREATE DATABASE IF NOT EXISTS logs
        ```

        Cree una table para sus datos.

        ```sql
        CREATE TABLE logs.nginx_logs
        (
            `time_local` DateTime,
            `remote_addr` IPv4,
            `remote_user` LowCardinality(String),
            `request` String,
            `status` UInt16,
            `body_bytes_sent` UInt64,
            `http_referer` String,
            `http_user_agent` String,
            `http_x_forwarded_for` LowCardinality(String),
            `request_time` Float32,
            `upstream_response_time` Float32,
            `http_host` String
        )
        ENGINE = MergeTree
        ORDER BY (toStartOfMinute(time_local), status, remote_addr)
        ```

        <Info>
          **Clave primaria de Nginx**

          La clave primaria anterior se basa en los patrones de acceso habituales en la interfaz de usuario de observabilidad para los logs de Nginx, pero es posible que deba ajustarse según su workload en entornos de producción.
        </Info>
      </Step>

      <Step title="Copiar la configuración de Vector" id="copy-vector-configuration-self-configured">
        Copie la configuración de Vector y cree un archivo `nginx.yaml`, configurando `CLICKHOUSE_ENDPOINT` y `CLICKHOUSE_PASSWORD`.

        ```yaml
        data_dir: ./.vector-data
        sources:
          nginx_logs:
            type: file
            include:
              - access.log
            read_from: beginning

        transforms:
          decode_json:
            type: remap
            inputs:
              - nginx_logs
            source: |
              . = parse_json!(to_string!(.message))
              ts = parse_timestamp!(.time_local, format: "%d/%b/%Y:%H:%M:%S %z")
              # ClickHouse-friendly DateTime format
              .time_local = format_timestamp!(ts, format: "%F %T")

        sinks:
          clickhouse:
            type: clickhouse
            inputs:
              - decode_json
            endpoint: "<CLICKHOUSE_ENDPOINT>"
            database: logs
            format: json_each_row
            table: nginx_logs
            skip_unknown_fields: true
            auth:
              strategy: "basic"
              user: "default"
              password: "<CLICKHOUSE_PASSWORD>"
        ```

        <Note>
          El ejemplo anterior utiliza el usuario `default` para Self-managed ClickHouse Observability. En implementaciones de producción, recomendamos [crear un usuario de ingestión dedicado](/es/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) con los permisos y límites adecuados.
        </Note>
      </Step>

      <Step title="Iniciar Vector" id="start-vector-self-configured">
        Inicie Vector con el siguiente comando, no sin antes crear el directorio de datos donde se registrarán los desplazamientos de los archivos.

        ```bash
        mkdir ./.vector-data
        vector --config nginx.yaml
        ```
      </Step>

      <Step title="Acceda a la interfaz de usuario de observabilidad" id="navigate-to-clickstack-ui-nginx-managed-self-configured">
        Vaya a su servicio de Self-managed ClickHouse Observability y seleccione &quot;ClickStack&quot; en el menú de la izquierda. Si ya ha completado el onboarding, se abrirá la interfaz de usuario de observabilidad en una nueva pestaña y se autenticará automáticamente. De lo contrario, puede completar el onboarding y seleccionar “Launch ClickStack” después de elegir Vector como fuente de entrada.

        <div className="ch-image-lg">
          <Frame>

          </Frame>
        </div>
      </Step>

      <Step title="Crear un origen de datos" id="create-a-datasource-nginx-managed-self-configured">
        Cree un origen de datos de logs. Si no existe ningún origen de datos, se le pedirá que cree uno al iniciar sesión por primera vez. De lo contrario, vaya a la configuración del equipo y agregue un nuevo origen de datos.

        <div className="ch-image-lg">
          <Frame>
            ![Crear origen de datos - vector](/images/clickstack/create-vector-datasource.webp)
          </Frame>
        </div>

        La configuración presupone el esquema de Nginx, con una columna `time_local` que se utiliza como marca de tiempo. Esta es la columna de marca de tiempo declarada en la clave primaria y es obligatoria.

        También hemos especificado `time_local, remote_addr, status, request` como selección predeterminada, lo que determina qué columnas se devuelven en la vista de logs.

        En el ejemplo anterior, la columna `Body` no existe en los datos. En su lugar, se define mediante la siguiente expresión SQL:

        ```sql
        concat(
          remote_addr, ' ',
          remote_user, ' ',
          '[', formatDateTime(time_local, '%d/%b/%Y:%H:%M:%S %z'), '] ',
          '"', request, '" ',
          toString(status), ' ',
          toString(body_bytes_sent), ' ',
          '"', http_referer, '" ',
          '"', http_user_agent, '" ',
          '"', http_x_forwarded_for, '" ',
          toString(request_time), ' ',
          toString(upstream_response_time), ' ',
          '"', http_host, '"'
        )
        ```

        Esto reconstruye la línea de registro a partir de los campos estructurados.

        Para ver otras opciones disponibles, consulte la [referencia de configuración](/es/clickstack/self-configured/managing/config).
      </Step>
