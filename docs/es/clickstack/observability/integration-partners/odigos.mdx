<Info>
  **Resumen**

  Esta guía explica cómo exportar la telemetría de Odigos a ClickHouse Observability. Aprenderá a:

  * Desplegar Odigos en Kubernetes con Helm
  * Añadir fuentes en la interfaz de usuario de Odigos
  * Añadir un destino OTLP HTTP que apunte a ClickHouse Observability
  * Verificar los logs, las métricas y las trazas en ClickHouse Observability

  Odigos instrumenta automáticamente las aplicaciones sin necesidad de modificar el código ni de reiniciarlas; ClickHouse Observability almacena y consulta los datos en ClickHouse.

  Tiempo estimado: 10–20 minutos
</Info>

## ¿Qué es Odigos? {#what-is-odigos}

{/* vale on */}

[Odigos](https://odigos.io/) es un plano de control de instrumentación para Kubernetes y máquinas virtuales que instrumenta las aplicaciones desde el núcleo mediante **eBPF**. Como la recopilación se ejecuta en el núcleo, la sobrecarga en las aplicaciones se mantiene baja y la visibilidad, alta. Obtiene trazas, métricas, logs y perfiles de OpenTelemetry aptos para producción sin tener que incorporar nuevos agentes en el código de aplicación ni esperar a que se actualicen las bibliotecas en cada servicio.

Esa capa eBPF es lo que hace posible una telemetría profunda y coherente a gran escala. Odigos puede activar y desactivar automáticamente una instrumentación más detallada cuando sea necesario para ayudar a depurar o diagnosticar problemas:

* **Contexto a nivel de código**: atributos vinculados a funciones y al comportamiento en tiempo de ejecución
* **Tráfico HTTP**: solicitudes y respuestas entre sus servicios
* **Sistemas de mensajería**: cargas útiles y mensajes de Kafka y brókers similares
* **Errores en detalle**: trazas de pila cuando algo falla
* **Instrumentación personalizada**: amplíe la cobertura allí donde no llega la autoinstrumentación, sin necesidad de modificar el código ni de reinicios

Internamente, Odigos crea y administra una canalización completa de OpenTelemetry para su cluster: recolectores que escalan según la carga, enrutamiento hacia los backends que elija y lógica de canalización que usted controla desde la interfaz de usuario. Defina **muestreo** para gestionar el volumen, **enmascaramiento de PII** para evitar que los datos confidenciales lleguen a las exportaciones y **reglas OTTL** para filtrar, transformar o enriquecer la telemetría antes de que salga del cluster.

## ¿Por qué Odigos + ClickHouse Observability? {#why-odigos-clickstack}

{/* vale on */}

Desplegar OpenTelemetry en muchos servicios suele llevar mucho tiempo y solo ofrece una visibilidad superficial de las aplicaciones. Odigos se encarga de la instrumentación con eBPF, que aporta una telemetría más profunda, y de las operaciones del recolector en Kubernetes; ClickHouse Observability ofrece almacenamiento basado en ClickHouse y la UI de ClickStack para consultar telemetría a gran escala.

<Tip>
  **Puntos clave**

  * **Odigos** instrumenta automáticamente cualquier workload de Kubernetes sin necesidad de reinicios y gestiona de forma automática las canalizaciones de OpenTelemetry.
  * **ClickHouse Observability** almacena logs, métricas y trazas en ClickHouse y los muestra en la UI de ClickStack.
</Tip>

## Requisitos previos {#prerequisites}

* Un servicio de ClickHouse Observability accesible desde su clúster de Kubernetes. Consulte [Primeros pasos](/es/clickstack/observability/getting-started). Para implementaciones autogestionadas, consulte [Configuración autogestionada](/es/clickstack/self-configured/deployment/managed).
* Su **endpoint OTLP HTTP** y su API key de ingesta, disponibles en **Team Settings → Data → Managed Telemetry**. Para implementaciones autogestionadas, utilice el endpoint de su recolector independiente y `OTLP_AUTH_TOKEN`.
* Un **clúster de Kubernetes** (nodos Linux con núcleo 4.18 o posterior para la instrumentación con eBPF)
* **Helm**, **kubectl** y credenciales del clúster para instalar en el espacio de nombres `odigos-system`
* Un **token de Odigos Enterprise on-premises**: póngase en contacto con el [equipo de Odigos](https://odigos.io/) para obtener acceso

## Integración de ClickHouse Observability con Odigos {#integrate-odigos-clickstack}

{/* vale on */}

<Steps>
  <Step title="Desplegar Odigos con Helm" id="deploy-odigos">
    Odigos Enterprise requiere un token de licencia on-premises. Expórtelo en su shell:

    ```bash
    export ODIGOS_ONPREM_TOKEN="<your-enterprise-token>"
    ```

    Como alternativa, puede almacenar el token en un secreto de Kubernetes llamado `odigos-pro` antes de la instalación. Consulte la [documentación de Odigos Enterprise](https://enterprise.docs.odigos.io/) (requiere acceso).

    Agregue el repositorio de Helm de Odigos e instale el chart en `odigos-system`:

    ```bash
    helm repo add odigos https://odigos-io.github.io/odigos/
    helm repo update

    helm upgrade --install odigos odigos/odigos \
      --namespace odigos-system \
      --create-namespace \
      --set onPremToken=$ODIGOS_ONPREM_TOKEN
    ```

    Puede pasar sobrescrituras de configuración adicionales mediante indicadores `--set` o un archivo de valores personalizado (`-f`). Para consultar los valores predeterminados del chart, ejecute `helm show values odigos/odigos`.

    Compruebe que los pods de Odigos estén en ejecución:

    ```bash
    kubectl get pods -n odigos-system
    ```
  </Step>

  <Step title="Añada fuentes en la interfaz de usuario de Odigos" id="add-sources">
    1. Configure el reenvío de puertos del servicio de la interfaz de usuario de Odigos:

    ```bash
    kubectl port-forward svc/ui -n odigos-system 3000:3000
    ```

    2. Abra [http://localhost:3000](http://localhost:3000) en su navegador.
    3. Vaya a **Sources** y seleccione los espacios de nombres o workloads que desee instrumentar.
    4. Una vez que haya marcado todos los workloads para su instrumentación, haga clic en Done en la parte inferior.
    5. Compruebe en la columna de fuentes que los workloads se hayan instrumentado correctamente.
  </Step>

  <Step title="Añada ClickHouse Observability como destino en la interfaz de usuario de Odigos" id="add-destination-ui">
    Para enviar telemetría, agregue un destino **OTLP HTTP** en Odigos. Seleccione su tipo de implementación a continuación.

    <Tabs>
      <Tab title="Totalmente gestionado">
        <BetaBadge label="Oferta en fase beta" />

        ClickHouse Observability le proporciona un endpoint OTLP. ClickHouse se encarga de la ingestión, los esquemas y el cómputo. Solo tiene que dirigir Odigos a ese endpoint; no es necesario desplegar ningún recolector.

        1. En la interfaz de usuario de Odigos, haga clic en **Add Destination** y seleccione **OTLP HTTP**.
        2. En **OTLP HTTP Endpoint**, indique el endpoint HTTPS de ClickHouse Cloud, incluido el puerto `4318`. Por ejemplo, `https://<service-id>.otel.<region>.aws.clickhouse.com:4318`.
        3. En **Headers**, agregue:
           * **Key**: `Authorization`
           * **Value**: `Bearer <YOUR_INGESTION_API_KEY>`
        4. Active **Logs**, **Metrics** y **Traces**.
        5. Guarde el destino.
      </Tab>

      <Tab title="Autogestionado">
        <Tip>
          **Alternativa: escribir directamente en ClickHouse**

          En las implementaciones autogestionadas, puede usar el [destino nativo **ClickHouse**](#native-clickhouse-destination) de Odigos en lugar de ejecutar un recolector OTLP, siempre que su servicio de ClickHouse sea accesible desde su clúster de Kubernetes. Las implementaciones totalmente gestionadas deben usar el endpoint OTLP gestionado.
        </Tip>

        En una implementación autogestionada, debe ejecutar usted mismo la [distribución de ClickStack del recolector en modo independiente](/es/clickstack/self-configured/ingesting-data/collector#configuring-the-collector-self-configured) y definir el token de autenticación mediante la variable de entorno `OTLP_AUTH_TOKEN` al iniciar el contenedor. Odigos enviará entonces el tráfico OTLP HTTP a ese recolector con el mismo token en el encabezado `Authorization`.

        1. Inicie el recopilador de ClickStack en modo independiente, apuntando a su servicio de ClickHouse Cloud y protegiéndolo con un `OTLP_AUTH_TOKEN` de su elección:

           ```shell
           export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
           export CLICKHOUSE_USER=<CLICKHOUSE_USER>
           export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
           export OTLP_AUTH_TOKEN="a_very_secure_string"

           docker run \
             -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
             -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
             -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
             -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
             -p 4317:4317 \
             -p 4318:4318 \
             clickhouse/clickstack-otel-collector:latest
           ```

           Para TLS, usuarios de ingestión dedicados y otras recomendaciones para producción, consulte [Protección del recolector](/es/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        2. En la interfaz de usuario de Odigos, haga clic en **Add Destination** y seleccione **OTLP HTTP**.
        3. En **OTLP HTTP Endpoint**, indique el recolector independiente que acaba de iniciar (por ejemplo, `http://my-collector.example.com:4318`).
        4. En **Headers**, agregue:
           * **Key**: `Authorization`
           * **Value**: el valor de `OTLP_AUTH_TOKEN` que definió en el recolector
        5. Active **Logs**, **Metrics** y **Traces**.
        6. Guarde el destino.

        <Info>
          **Opcional: manifiesto de Kubernetes**

          Puede configurar el mismo destino con un manifiesto `Destination` en lugar de la interfaz de usuario. Consulte [Configurar destinos con manifiestos de Kubernetes](#destination-manifest) en Configuración avanzada.
        </Info>
      </Tab>
    </Tabs>
  </Step>

  <Step title="Verifique la telemetría en ClickHouse Observability" id="verify-telemetry">
    1. Abra la UI de ClickStack:
       * **Autogestionado**: abra su servicio en la [consola de ClickHouse Cloud](https://console.clickhouse.cloud) y, a continuación, haga clic en **Launch ClickStack**. Consulte [Navegar a la UI de ClickStack](/es/clickstack/self-configured/deployment/managed) para obtener más información.
       * **Totalmente gestionado**: abra la vista de observabilidad de su servicio de ClickHouse Cloud.
    2. Revise **Logs**, **Metrics** y **Traces** para comprobar que llegan datos de sus servicios instrumentados.
    3. Filtre las trazas por `odigos.version` para validar la exportación de extremo a extremo.

    Si faltan datos, revise los logs del recolector: `kubectl logs deploy/odigos-gateway -n odigos-system`
  </Step>
</Steps>

## Configuración avanzada {#advanced-configuration}

### Destino ClickHouse nativo {#native-clickhouse-destination}

El destino ClickHouse nativo solo está disponible para implementaciones **autogestionadas**. Para implementaciones **totalmente gestionadas**, utilice el destino **OTLP HTTP** con su endpoint gestionado.

<Tabs>
  <Tab title="Autogestionado">
    Si ClickHouse es accesible directamente desde su cluster, puede utilizar el destino **ClickHouse** nativo de Odigos en lugar de OTLP HTTP. Configure el endpoint de ClickHouse, el nombre de la base de datos y las opciones de esquema en la interfaz de usuario o mediante un manifiesto; consulte [Destino ClickHouse de Odigos](https://docs.odigos.io/backends/clickhouse).

    * **Esquema de producción**: establezca `CLICKHOUSE_CREATE_SCHEME` en `false` y aplique su propio DDL.
    * **TLS / autenticación**: utilice `CLICKHOUSE_TLS_ENABLED`, `CLICKHOUSE_USERNAME` y un secreto de Kubernetes para la contraseña.

    **Manifiesto de Kubernetes**

    ```yaml
    apiVersion: odigos.io/v1alpha1
    kind: Destination
    metadata:
      name: clickhouse
      namespace: odigos-system
    spec:
      type: clickhouse
      destinationName: clickhouse
      signals:
        - TRACES
        - METRICS
        - LOGS
      data:
        CLICKHOUSE_ENDPOINT: 'http://clickstack.example.com:8123'
        CLICKHOUSE_DATABASE_NAME: 'otel'
        CLICKHOUSE_CREATE_SCHEME: 'true'
    ```

    Guarde el manifiesto como `destination.yaml` y aplíquelo:

    ```bash
    kubectl apply -f destination.yaml
    ```

#### Normalizador de logs de HyperDX {#hyperdx-log-normalizer}

    En implementaciones autogestionadas que exportan directamente a ClickHouse mediante el destino **ClickHouse** nativo de Odigos, habilite el **Normalizador de logs de HyperDX** (`HYPERDX_LOG_NORMALIZER: true`). Este analiza los cuerpos de log en formato JSON y normaliza sus atributos para facilitar las consultas en la UI de ClickStack. Este parámetro de configuración no se aplica al destino OTLP totalmente gestionado.
  </Tab>
</Tabs>

### Configurar destinos con manifiestos de Kubernetes {#destination-manifest}

**OTLP HTTP (ClickStack)**

```yaml
apiVersion: odigos.io/v1alpha1
kind: Destination
metadata:
  name: clickstack
  namespace: odigos-system
spec:
  type: otlphttp
  destinationName: otlphttp
  signals:
    - TRACES
    - METRICS
    - LOGS
  data:
    OTLP_HTTP_ENDPOINT: 'http://clickstack.example.com:4318'
    # Self-managed: OTLP_AUTH_TOKEN
    # ClickHouse Observability: Bearer <YOUR_INGESTION_API_KEY>
    OTLP_HTTP_HEADERS: 'Authorization:<YOUR_AUTHORIZATION_VALUE>'
```

Aplica el manifiesto:

```bash
kubectl apply -f destination.yaml
```

### Odigos VM Agent {#odigos-vm-agent}

{/* vale on */}

El [Odigos VM Agent](https://docs.odigos.io/vmagent/overview) instrumenta procesos de Linux, servicios de systemd y/o contenedores de Docker mediante eBPF. La telemetría se exporta a los mismos destinos que la versión de Odigos basada en cluster, incluido ClickHouse Observability mediante OTLP HTTP.

El VM Agent forma parte de Odigos Pro. Consulte la [Información general de VM Agent](https://docs.odigos.io/vmagent/overview) para obtener información sobre la configuración inicial, las fuentes y la configuración de destinos.

{/* vale off */}

### Odigos Central {#odigos-central}

{/* vale on */}

[Odigos Central](https://docs.odigos.io/central/overview) es un plano de control centralizado que permite administrar la instrumentación, los destinos y la configuración de canalizaciones de varios clústeres de Kubernetes desde una única interfaz de usuario, en lugar de configurar cada cluster por separado.

Odigos Central está disponible en Odigos Enterprise. Consulte la [Descripción general de Central](https://docs.odigos.io/central/overview) para obtener más información sobre la administración multiclúster, el SSO y las reglas de muestreo unificadas.
