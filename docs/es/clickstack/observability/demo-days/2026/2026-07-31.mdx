## Métricas de histograma exponencial {#exponential-histogram-metrics}

*Demostración a cargo de [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/w45v3IMcXTY" title="Reproductor de vídeo de YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Ya está disponible la compatibilidad inicial de consultas para las métricas de histograma exponencial de OpenTelemetry. Hasta ahora era posible registrar una de estas métricas en una fuente, pero no había forma de consultarla. Los recuentos y los cuantiles ya funcionan desde el generador de consultas.

Los histogramas exponenciales son similares a los histogramas con buckets explícitos, pero los límites de sus buckets se calculan a partir de potencias de dos en lugar de almacenarse para cada bucket. La escala determina qué potencia de dos se utiliza. Una escala mayor genera buckets más pequeños, mientras que el offset desplaza los límites hacia múltiplos mayores o menores. Cada recuento de bucket registra cuántas observaciones caen dentro de ese rango.

Max, min, sum y avg siguen sin ser compatibles, igual que en la implementación actual de histogramas explícitos. Esos campos son opcionales en el modelo de datos de OpenTelemetry, por lo que no contamos con que estén presentes.

Como se ve en la demo, el SQL generado es extenso y poco legible. Su rendimiento es aceptable y no agota la memoria, pero por ahora se trata solo de una compatibilidad funcional inicial. El siguiente paso es mejorar el rendimiento, y ya se está trabajando en un esquema actualizado que debería hacer que estas consultas sean considerablemente más rápidas.

Por ahora, solo el tipo de visualización de serie temporal se renderiza correctamente, al igual que ocurre con el tipo de métrica de histograma existente.

**PR relacionados:** [#2687](https://github.com/hyperdxio/hyperdx/pull/2687) feat: Show exponential histogram metrics in the metric name drop-down, [#2697](https://github.com/hyperdxio/hyperdx/pull/2697) feat: Implement quantile+sum for exponential histogram metrics, [#2705](https://github.com/hyperdxio/hyperdx/pull/2705) feat: Support exponential histograms in MCP, [#2707](https://github.com/hyperdxio/hyperdx/pull/2707) fix: Support grouping histogram quantile aggregations over non-Attribute columns

## Validación de gráficos de SQL directo {#validation-for-raw-sql-charts}

*Demostración a cargo de [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/zfZsehTqeCQ" title="Reproductor de vídeo de YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Los gráficos de SQL directo ahora muestran una advertencia cuando faltan las macros esperadas. Esta mejora surgió de un caso de soporte en el que un usuario que estaba creando muchos gráficos de SQL directo obtenía una y otra vez resultados confusos.

Las consultas de los paneles de control deben incluir las macros de filtros y de tabla de origen. Los gráficos de series temporales también deben incluir las macros de intervalo de tiempo y de intervalo. Hasta ahora, estas comprobaciones solo se ejecutaban después de adjuntar una alerta al bloque. Ahora se ejecutan en todos los gráficos de SQL directo, de modo que, si se elimina una macro, aparece una advertencia en el editor en lugar de obtener más adelante un gráfico desconcertante.

La validación también tiene en cuenta las dependencias de cada macro. Las macros de tabla de origen y de filtros requieren una fuente seleccionada, aunque los gráficos de SQL directo no la necesiten en otros casos. Por ello, usar cualquiera de estas dos macros sin seleccionar una fuente genera un error en lugar de una advertencia.

Es un cambio pequeño, pero debería facilitar la detección de problemas en SQL directo sin necesidad de recurrir a soporte.

**PRs relacionadas:** [#2742](https://github.com/hyperdxio/hyperdx/pull/2742) feat: Warn on missing params/macros in SQL Editor

## Vincular fuentes por nombre, no por ID {#link-to-sources-by-name-not-id}

*Demostración a cargo de [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/r2uNmcJXGSM" title="Reproductor de vídeo de YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

El equipo de LogHouse pidió una forma más estable de enlazar a las fuentes. Este equipo gestiona el entorno de registro de ClickHouse Cloud y aprovisiona las fuentes de forma programática mediante infrastructure-as-code. Los ID de las fuentes cambian cuando se recrea una fuente y difieren entre los entornos de desarrollo, staging y producción, lo que hace que cualquier enlace basado en un ID sea frágil. Como enlazan a ClickStack desde sistemas de alertas y Grafana, mantener un conjunto distinto de ID de fuentes para cada entorno no resultaba práctico.

El parámetro de URL `source` ahora acepta tanto un nombre de fuente como un ID. Los nombres se definen al aprovisionar las fuentes, por lo que el mismo enlace puede funcionar en todos los entornos. La compatibilidad se añadió inicialmente a la página de búsqueda. Un PR posterior la extiende a todas las páginas con un parámetro de fuente, incluidos el Explorador de Gráficos, el mapa de servicios, las sesiones, el panel de control de servicios y el Panel de control de Kubernetes.

La mayor parte del debate posterior se centró en cómo dar a conocer esta funcionalidad. En la práctica, se trata de una API de URL, y es poco probable que alguien la descubra por casualidad. Una opción es usar nombres en lugar de ID de forma predeterminada, aunque las colisiones de nombres lo hacen poco seguro. Otras sugerencias fueron exponer los enlaces mediante un botón Compartir, hacer que los agentes los generen a través del MCP y documentar adecuadamente la API de URL. Los intervalos de tiempo relativos también se beneficiarían de esa documentación.

Las referencias basadas en nombres también podrían extenderse a los paneles de control. Así, un flujo de trabajo de infrastructure-as-code podría aprovisionar fuentes, importar paneles de control y conectarlo todo automáticamente. Las importaciones de paneles de control desde la UI ya asocian las fuentes por nombre, por lo que lo que falta afecta sobre todo a los flujos de trabajo programáticos.

**PR relacionados:** [#2746](https://github.com/hyperdxio/hyperdx/pull/2746) feat: Accept source names in addition to IDs in URL Params, [#2758](https://github.com/hyperdxio/hyperdx/pull/2758) feat: Support source name deeplinks on additional pages

## Rediseño de la configuración de visualización de gráficos {#chart-display-settings-redesign}

*Demostración a cargo de [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/tO5yFKR-MLQ" title="Reproductor de vídeo de YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Se está trabajando para decidir dónde deben ubicarse los ajustes de visualización de los gráficos. El cambio original los integraba en línea a la derecha del editor de bloques, en lugar de abrirlos en un panel deslizante independiente. Antes, el editor de bloques era un modal y la Configuración De Visualización se abría en un panel deslizante superpuesto. Al pulsar Escape una sola vez se cerraban ambos, y un panel deslizante encima de un modal nunca terminó de convencer.

El PR se complicó cuando también hubo que apilar encima los ajustes de las series, así que dimos un paso atrás y empezamos a replantear la página en su conjunto. El trabajo aún está en fase de wireframe. El diseño actual sitúa los ajustes en un panel acoplado y aplica los cambios automáticamente, de modo que se puede ver el resultado en tiempo real sin pulsar ningún botón Aplicar.

El plan es terminar el rediseño antes de volver a incorporarlo al PR existente. Lo que hay ahora se considera un prototipo, sobre todo porque el nuevo diseño también modifica partes de la página del panel de control.

**PRs relacionados:** [#2721](https://github.com/hyperdxio/hyperdx/pull/2721) feat(dashboards): move tile editor to a drawer with docked settings panel

## Nueva página Explorar {#new-explore-page}

*Demostración a cargo de [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/E1vEjJBw1gs" title="Reproductor de vídeo de YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Se trata de una exploración preliminar de una página Explorar unificada que, con el tiempo, podría sustituir a Búsqueda, Búsquedas guardadas y el Explorador de Gráficos con un único punto de entrada.

El despliegue se basa en lo que aprendimos con el rediseño del visor de trazas. En lugar de cambiar la experiencia para todos a la vez, la nueva página se lanzaría tras un feature flag para un grupo reducido de usuarios. Aprovecharíamos ese período para detectar y corregir problemas antes de ampliar su disponibilidad. Si la idea no funciona, se queda en experimento y no se publica. Y eso sería un resultado perfectamente válido.

La página parte de un tipo de señal. Al elegir trazas, logs o métricas, el resto de la experiencia se adapta en consecuencia. Por ejemplo, al seleccionar logs se obtienen la vista de lista, los patrones de eventos, las series temporales y las demás visualizaciones que hoy se encuentran en el Explorador de Gráficos.

Una investigación debería poder continuar sin cambiar de página. Podría empezar con una lista, pasar a un número o a una tabla agrupada, añadir el resultado a un panel de control y, después, escribir una consulta personalizada si necesita más control.

También se incluyen varias ideas menores, la mayoría surgidas de los comentarios de los usuarios. El editor de consultas funcionaría de forma más parecida al editor SQL, lo que eliminaría las diferencias actuales en el comportamiento del autocompletado. Los errores y advertencias aparecerían a medida que edita, sin esperar a que se ejecute la consulta.

Las columnas contarían con un selector propio. Al menos un usuario no se dio cuenta de que, al modificar la cláusula `SELECT`, se controlaba qué columnas aparecían en la tabla. Con el selector, al hacer clic en un campo se actualiza el SQL y se puede ordenar por ese campo. La cláusula `SELECT` sigue disponible para usuarios avanzados.

Las vistas guardadas también estarían en la propia página, de modo que podría explorar sin guardar y luego guardar la vista actual sin salir de ella. El SQL generado se mostraría en línea.

Aún falta bastante, incluidas algunas de las visualizaciones disponibles hoy en el Explorador de Gráficos. El diseño seguirá evolucionando a medida que se incorporen esas piezas.

**PR relacionados:** ninguno por ahora; se trata de una exploración, no de una funcionalidad publicada

## Vinculación de filtros de panel de control {#dashboard-filter-linking}

*Demostración a cargo de [@teeohhem](https://github.com/teeohhem)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/IQ4WtnNYS5s" title="Reproductor de vídeo de YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

La vinculación de filtros de panel de control ya se ha fusionado. La presentamos por primera vez como borrador hace varios meses y luego la pausamos mientras analizábamos su impacto en el rendimiento. La vinculación cambia la forma de las consultas del panel de control y no siempre aprovecha de forma óptima las vistas materializadas, por lo que se publicará como un toggle opcional en lugar de estar activada de forma predeterminada.

Cuando la vinculación está habilitada, elegir un valor en un filtro reduce los valores disponibles en los demás. Al seleccionar un servicio, solo quedan los valores de severidad encontrados para ese servicio. Al seleccionar un ID de traza, solo quedan los ID de traza padre relacionados. Así se evita que los usuarios elijan combinaciones que no devuelven datos.

Un PR posterior hace que la vinculación tenga en cuenta la fuente. Los filtros se agrupan por fuente, con iconos de cadena entre los filtros contiguos que pueden restringirse entre sí. En un panel de control con dos filtros de logs y dos filtros de trazas, debería quedar claro qué filtros interactúan entre sí.

El caso de uso original fue el Panel de control de Kubernetes. Al seleccionar un pod de Kubernetes, solo deberían quedar las implementaciones y los nodos que contienen ese pod. Los valores restringidos se recuperan de forma diferida al abrir una lista desplegable, lo que limita el coste de las búsquedas adicionales.

La conversación dejó dos cuestiones abiertas. Actualmente, el parámetro de configuración se almacena por usuario en el almacenamiento del navegador. En la reunión se planteó que, con el tiempo, probablemente se querrá guardar a nivel de panel de control. En ese caso, quizá convenga mantener la preferencia a nivel de usuario como algo temporal, para que no compita más adelante con el comportamiento a nivel de panel de control.

La otra cuestión es cómo se comportan los filtros dependientes mientras se cargan sus valores. Actualmente, al seleccionar un valor se muestra un estado de carga dentro de la lista desplegable dependiente en lugar de bloquearla, aunque todavía falta verificar el comportamiento con un segundo filtro dependiente. Se prefirió mantener los filtros utilizables mientras se aplica la restricción e indicar que la lista aún no ha terminado de actualizarse. Quien ya sabe qué valor quiere no debería tener que esperar a la metadata.

**PR relacionados:** [#2423](https://github.com/hyperdxio/hyperdx/pull/2423) feat(dashboards): cascading (faceted) filter values, [#2760](https://github.com/hyperdxio/hyperdx/pull/2760) feat(dashboards): persist filter link toggle and clarify within-source linking

## Recordar la última pestaña del panel lateral {#remember-the-last-side-panel-tab}

*Demostración a cargo de [@MikeShi42](https://github.com/MikeShi42)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/FlDWN7sGHMo" title="Reproductor de vídeo de YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

El PR más pequeño de la semana es también un buen ejemplo de una molestia que merecía la pena corregir.

El panel lateral de filas siempre se abría en la pestaña Descripción general, diseñada en torno a los campos de log de OpenTelemetry. Con logs que no siguen la forma de OTel, esta pestaña apenas muestra información útil, así que había que cambiar a Valores de columna cada vez que se abría una fila.

Ahora el panel recuerda la última pestaña utilizada y la vuelve a abrir la próxima vez. No hay nada que configurar. Quienes no usan OTel y cambian a Valores de columna se quedarán en ella, mientras que quienes usan Descripción general mantienen el comportamiento actual.

**PRs relacionados:** [#2752](https://github.com/hyperdxio/hyperdx/pull/2752) feat(app): remember last-used side panel tab across opens
