Recopile los logs de contenedores, las métricas de nodos y del cluster, y los eventos de Kubernetes con dos recolectores de OpenTelemetry: un conjunto de daemon en cada nodo y una única implementación para los datos de todo el cluster.

## Requisitos previos {#prerequisites}

* Un servicio de ClickHouse Observability
* Un clúster de Kubernetes con nodos Linux y permisos para crear workloads, roles de clúster (ClusterRoles) y montajes de rutas del host (host-path)
* `kubectl` configurado para el clúster de destino y Helm 3 instalado
* Acceso a la red desde los recolectores al endpoint OTLP HTTP de su servicio, a la API de Kubernetes y a los agentes kubelet

Estos recolectores recopilan datos de infraestructura. Para enviar métricas y trazas de aplicación, instrumente sus aplicaciones por separado; consulte [Integraciones de OpenTelemetry](/es/clickstack/observability/ingesting-data/opentelemetry).

## Datos de conexión {#connection-details}

<Tabs>
  <Tab title="Totalmente gestionado">
    <BetaBadge label="Oferta en fase beta" />

    Abra ClickHouse Observability y vaya a **Configuración del equipo → Datos → Managed Telemetry**. Copie el endpoint OTLP HTTP y la clave de API.

    <div className="ch-image-lg">
      <Frame>
        ![Datos de conexión de Managed Telemetry](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Defina estas variables en su terminal:

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Use el endpoint exacto, con su puerto incluido y sin el sufijo `/v1/logs` ni `/v1/metrics`.
  </Tab>

  <Tab title="Autogestionado" id="self-managed">
    Use el endpoint OTLP HTTP de su recolector accesible desde el cluster, junto con sus ajustes de autenticación. Si la autenticación está deshabilitada, asigne a `OTEL_EXPORTER_OTLP_AUTHORIZATION` una cadena vacía y omita el bloque `headers` del exportador que se muestra más abajo. Consulte la [guía de configuración autogestionada](/es/clickstack/self-configured/getting-started/managed).

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

## Desplegar los recolectores {#deploy-collectors}

<Steps>
  <Step title="Cree el espacio de nombres y los ajustes de conexión" id="connection-settings">
    Compruebe que `kubectl` apunta al cluster previsto:

    ```bash
    kubectl config current-context
    kubectl create namespace observability --dry-run=client -o yaml | kubectl apply -f -

    kubectl create configmap observability-connection -n observability \
      --from-literal=endpoint="$OTEL_EXPORTER_OTLP_ENDPOINT" \
      --dry-run=client -o yaml | kubectl apply -f -

    kubectl create secret generic observability-connection -n observability \
      --from-literal=authorization="$OTEL_EXPORTER_OTLP_AUTHORIZATION" \
      --dry-run=client -o yaml | kubectl apply -f -
    ```

    Ambos recolectores usan estos ajustes en el espacio de nombres `observability`.
  </Step>

  <Step title="Guarde la configuración compartida" id="shared-configuration">
    Guarde lo siguiente como `k8s_common.yaml`:

    ```yaml
    image:
      repository: otel/opentelemetry-collector-contrib
      tag: "0.161.0"
    command:
      name: otelcol-contrib
    resources:
      limits:
        memory: 512Mi
    presets:
      kubernetesAttributes:
        enabled: true
    extraEnvs:
      - name: OTEL_EXPORTER_OTLP_ENDPOINT
        valueFrom:
          configMapKeyRef:
            name: observability-connection
            key: endpoint
      - name: OTEL_EXPORTER_OTLP_AUTHORIZATION
        valueFrom:
          secretKeyRef:
            name: observability-connection
            key: authorization
    service:
      enabled: false
    ports:
      otlp:
        enabled: false
      otlp-http:
        enabled: false
      jaeger-compact:
        enabled: false
      jaeger-thrift:
        enabled: false
      jaeger-grpc:
        enabled: false
      zipkin:
        enabled: false
    config:
      receivers:
        otlp: null
        jaeger: null
        zipkin: null
        prometheus: null
      exporters:
        debug: null
        otlp_http/observability:
          endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
          headers:
            authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
          compression: gzip
      processors:
        batch:
          timeout: 5s
          send_batch_size: 500
          send_batch_max_size: 500
      service:
        pipelines:
          logs:
            receivers: []
            exporters: [otlp_http/observability]
          metrics:
            receivers: []
            exporters: [otlp_http/observability]
          traces: null
    ```

    Los preajustes del chart añaden los receivers, el procesador de metadata de Kubernetes, las reglas de RBAC y los montajes que necesita cada recolector. La configuración compartida reenvía los logs y las métricas a su servicio y deshabilita los receivers de ingestión de aplicaciones que no se utilizan.
  </Step>

  <Step title="Configure la recopilación de datos de los nodos" id="daemonset-configuration">
    Guarde lo siguiente como `k8s_daemonset.yaml`:

    ```yaml
    mode: daemonset
    presets:
      logsCollection:
        enabled: true
        storeCheckpoints: true
      hostMetrics:
        enabled: true
      kubeletMetrics:
        enabled: true
    config:
      receivers:
        kubeletstats:
          insecure_skip_verify: true
    ```

    El conjunto de daemon lee los logs de los contenedores y recopila métricas del host y del agente kubelet. Los puntos de control conservan las posiciones de lectura de los logs entre reinicios del recolector. Este preajuste ejecuta el recolector como root para poder escribir los puntos de control en el nodo; la configuración de seguridad de pods de Kubernetes de su cluster debe permitir sus montajes del host.

    El ejemplo omite la verificación de certificados del agente kubelet en los clústeres cuyos certificados del agente kubelet no son de confianza para el recolector. Si su cluster proporciona certificados del agente kubelet de confianza, establezca `insecure_skip_verify` en `false` y configure la CA correspondiente.
  </Step>

  <Step title="Configurar la recopilación de datos del cluster" id="deployment-configuration">
    Guarde este contenido como `k8s_deployment.yaml`:

    ```yaml
    mode: deployment
    replicaCount: 1
    presets:
      kubernetesEvents:
        enabled: true
      clusterMetrics:
        enabled: true
    ```

    Mantenga una sola réplica para no recopilar métricas y eventos del cluster por duplicado.
  </Step>

  <Step title="Instale los releases de Helm" id="install-collectors">
    Ejecute los comandos desde el directorio que contiene los tres archivos de configuración. En estos ejemplos se usan la versión `0.175.1` del chart de Helm del Colector de OpenTelemetry y la versión `0.161.0` de Collector Contrib:

    ```bash
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update open-telemetry

    helm upgrade --install observability-nodes open-telemetry/opentelemetry-collector \
      --version 0.175.1 --namespace observability \
      -f k8s_common.yaml -f k8s_daemonset.yaml --wait

    helm upgrade --install observability-cluster open-telemetry/opentelemetry-collector \
      --version 0.175.1 --namespace observability \
      -f k8s_common.yaml -f k8s_deployment.yaml --wait
    ```

    Verifique los recolectores:

    ```bash
    kubectl get pods -n observability
    kubectl logs -n observability -l app.kubernetes.io/instance=observability-nodes --tail=50
    kubectl logs -n observability -l app.kubernetes.io/instance=observability-cluster --tail=50
    ```

    Si sus nodos tienen taints de planificación, agregue las `tolerations` correspondientes en `k8s_daemonset.yaml` para los nodos que desee monitorizar.
  </Step>

  <Step title="Verifique los datos" id="verify-data">
    Espere algunos intervalos de recopilación y, a continuación, abra ClickHouse Observability:

    * En **Búsqueda**, seleccione su fuente **Logs** y **Last 15 minutes**. Expanda un log de contenedor y compruebe atributos como `k8s.namespace.name`, `k8s.pod.name` y `k8s.node.name`.
    * En **Explorador de Gráficos**, seleccione su fuente **Metrics** y busque métricas que empiecen por `k8s.` o `system.`.
    * Consulte su fuente **Logs** para ver los eventos de Kubernetes a medida que se produzcan. El volumen de eventos depende de la actividad del cluster.
  </Step>
</Steps>

## Metadata de la aplicación {#application-metadata}

Para las aplicaciones instrumentadas, añada la metadata del pod de Kubernetes mediante la downward API de Kubernetes. Combine esta lista `env` con la configuración existente del contenedor de su aplicación y conserve los atributos del recurso que ya tenga definidos:

```yaml
env:
  - name: OTEL_SERVICE_NAME
    value: my-app
  - name: POD_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name
  - name: POD_UID
    valueFrom:
      fieldRef:
        fieldPath: metadata.uid
  - name: POD_NAMESPACE
    valueFrom:
      fieldRef:
        fieldPath: metadata.namespace
  - name: NODE_NAME
    valueFrom:
      fieldRef:
        fieldPath: spec.nodeName
  - name: OTEL_RESOURCE_ATTRIBUTES
    value: k8s.pod.name=$(POD_NAME),k8s.pod.uid=$(POD_UID),k8s.namespace.name=$(POD_NAMESPACE),k8s.node.name=$(NODE_NAME)
```

El procesador de metadata de Kubernetes enriquece los logs de contenedores recopilados con la metadata del workload. Estas variables de aplicación asocian la identity del pod de Kubernetes a la telemetría que emite el SDK de OpenTelemetry de su aplicación.

## Resolución de problemas {#troubleshooting}

### Los recolectores no se inician {#collectors-not-starting}

Inspeccione los eventos del pod de Kubernetes con `kubectl describe pod -n observability POD_NAME`. Revise la descarga de imágenes, las restricciones de planificación y las restricciones de seguridad de los pods de Kubernetes, y compruebe que el ConfigMap y el secreto existan en el mismo espacio de nombres que las releases.

### No aparecen logs ni métricas {#no-data}

Revise los logs del recolector en busca de errores de autenticación o de exportación. Confirme que el endpoint de destino es accesible desde el cluster. Si hay errores del agente kubelet, compruebe la conectividad con el puerto `10250`, los ajustes del certificado y los permisos de RBAC generados. La recolección de logs de contenedores requiere acceso al directorio `/var/log/pods` del nodo; es posible que los entornos de nodos restringidos o sin servidor no admitan estos montajes del host.

### Cambios en los ajustes de conexión {#connection-settings-changed}

Tras actualizar el ConfigMap o el secreto, reinicie los recolectores para que recarguen sus variables de entorno:

```bash
kubectl rollout restart daemonset -n observability -l app.kubernetes.io/instance=observability-nodes
kubectl rollout restart deployment -n observability -l app.kubernetes.io/instance=observability-cluster
```
