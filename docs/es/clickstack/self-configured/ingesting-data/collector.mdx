## Roles del recopilador {#collector-roles-self-configured}

Los Colectores de OpenTelemetry pueden desplegarse en dos roles principales:

* **Agente** - Las instancias de agente recopilan datos en el edge, por ejemplo, en servidores o en nodos de Kubernetes, o reciben eventos directamente de aplicaciones instrumentadas con un SDK de OpenTelemetry. En este último caso, la instancia de agente se ejecuta junto con la aplicación o en el mismo host que esta (por ejemplo, como sidecar o como conjunto de daemon). Los agentes pueden enviar sus datos directamente a ClickHouse o a una instancia de puerta de enlace. El primer caso se conoce como [patrón de despliegue de agente](https://opentelemetry.io/docs/collector/deployment/agent/).

* **Puerta de enlace** - Las instancias de puerta de enlace proporcionan un servicio independiente (por ejemplo, una implementación en Kubernetes), normalmente por cluster, por centro de datos o por región. Estas reciben eventos de aplicaciones (o de otros recolectores que actúan como agentes) a través de un único endpoint OTLP. Por lo general, se despliega un conjunto de instancias de puerta de enlace y se utiliza un balanceador de carga estándar para distribuir la carga entre ellas. Si todos los agentes y aplicaciones envían sus señales a este único endpoint, se suele hablar de un [patrón de despliegue de puerta de enlace](https://opentelemetry.io/docs/collector/deployment/gateway/).

**Importante: el recolector, también en las distribuciones predeterminadas de ClickStack, asume el [rol de puerta de enlace descrito a continuación](#collector-roles-self-configured) y recibe datos de agentes o SDKs.**

Los usuarios que despliegan OTel collectors en el rol de agente suelen utilizar la [distribución contrib predeterminada del recolector](https://github.com/open-telemetry/opentelemetry-collector-contrib) en lugar de la versión de ClickStack, aunque pueden usar libremente otras tecnologías compatibles con OTLP, como [Fluentd](https://www.fluentd.org/) y [Vector](https://vector.dev/).

## Implementación del recolector {#configuring-the-collector-self-configured}

<br />

Siempre que sea posible, recomendamos utilizar la distribución oficial de ClickStack del recolector para el rol de puerta de enlace al enviar datos a Self-managed ClickHouse Observability. Si decide utilizar su propio recolector, asegúrese de que incluya el [Exportador de ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

El recolector puede desplegarse mediante Helm (opción recomendada para Kubernetes) o mediante Docker. El [gráfico de Helm de ClickStack](https://github.com/ClickHouse/ClickStack-helm-charts) oficial incorpora como subgráfico el [gráfico de Helm del Colector de OpenTelemetry](https://github.com/open-telemetry/opentelemetry-helm-charts) upstream, con la imagen de la distribución de ClickStack ya preconfigurada. Para una implementación independiente del recolector, puede utilizarse directamente el gráfico upstream con la imagen de ClickStack, como se muestra a continuación.

<Tabs>
  <Tab title="Helm">
    Agregue el repositorio de Helm upstream de OpenTelemetry:

    ```shell
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update
    ```

    Cree un archivo `values.yaml` que configure la imagen de ClickStack y las credenciales de Self-managed ClickHouse Observability:

    ```yaml
    # values.yaml
    mode: deployment

    image:
      repository: docker.clickhouse.com/clickhouse/clickstack-otel-collector
      tag: "2.19.0"

    ports:
      otlp:
        enabled: true
      otlp-http:
        enabled: true

    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "https://your-instance.clickhouse.cloud:8443"
      - name: CLICKHOUSE_USER
        value: "default"
      - name: CLICKHOUSE_PASSWORD
        value: "<password>"
    ```

    Instale el gráfico:

    ```shell
    helm install clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    Para implementaciones en producción, recomendamos almacenar `CLICKHOUSE_PASSWORD` en un secreto de Kubernetes y referenciarlo mediante `extraEnvsFrom` en lugar de escribir el valor directamente en el archivo.
  </Tab>

  <Tab title="Docker">
    Para desplegar la distribución de ClickStack del recolector de OTel en modo independiente, ejecute el siguiente comando de Docker:

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```

    <Info>
      **Cambio en el nombre de la imagen**

      Las imágenes de ClickStack ahora se publican como `clickhouse/clickstack-*` (anteriormente `docker.hyperdx.io/hyperdx/*`).
    </Info>
  </Tab>
</Tabs>

La instancia de ClickHouse de destino se configura mediante las variables de entorno `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER` y `CLICKHOUSE_PASSWORD`. `CLICKHOUSE_ENDPOINT` debe ser el endpoint HTTP completo de ClickHouse Cloud, incluidos el protocolo y el puerto; por ejemplo, `https://99rr6dm6v3.us-central1.gcp.clickhouse.cloud:8443`.

Para saber cómo obtener sus credenciales de Self-managed ClickHouse Observability, consulte [esta guía](/es/products/cloud/guides/sql-console/connection-details).

<Info>
  **Usuario de producción**

  En producción, debe utilizar un usuario con las [credenciales adecuadas](/es/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured).
</Info>

### Modificación de la configuración {#modifying-otel-collector-configuration-managed-self-configured}

#### Configuración de una instancia de Self-managed ClickHouse Observability {#configuring-managed-clickstack-self-configured}

El Colector de OpenTelemetry puede configurarse para usar una instancia de Self-managed ClickHouse Observability mediante las variables de entorno `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER` y `CLICKHOUSE_PASSWORD`. La forma de definirlas depende del método de despliegue que utilice:

<Tabs>
  <Tab title="Helm">
    Sobrescriba las entradas correspondientes en `extraEnvs` de su archivo `values.yaml` y, a continuación, actualice la versión:

    ```yaml
    # values.yaml
    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```
  </Tab>

  <Tab title="Docker">
    La imagen independiente del Colector de OpenTelemetry puede configurarse mediante variables de entorno:

    ```shell
    export CLICKHOUSE_ENDPOINT=<HTTPS ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    ```

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

## Protección del recolector {#securing-the-collector-self-configured}

De forma predeterminada, el Recopilador de OpenTelemetry de ClickStack no está protegido cuando se despliega fuera de las distribuciones de Código Abierto y no requiere autenticación en sus puertos OTLP.

Para proteger la ingestión, especifique un token de autenticación mediante la variable de entorno `OTLP_AUTH_TOKEN` al desplegar el recolector. La forma de definirla depende de su método de implementación:

<Tabs>
  <Tab title="Helm">
    Añada `OTLP_AUTH_TOKEN` a `extraEnvs` en su `values.yaml` y, a continuación, actualice la versión:

    ```yaml
    # values.yaml
    extraEnvs:
      - name: OTLP_AUTH_TOKEN
        value: "a_very_secure_string"
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    Para implementaciones en producción, recomendamos almacenar `OTLP_AUTH_TOKEN` y `CLICKHOUSE_PASSWORD` en un secreto de Kubernetes y hacer referencia a ellos mediante `extraEnvsFrom`.
  </Tab>

  <Tab title="Docker">
    ```sh
    export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    export OTLP_AUTH_TOKEN="a_very_secure_string"

    docker run \
      -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
      -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
      -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
      -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
      -p 4317:4317 \
      -p 4318:4318 \
      clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

Además, recomendamos:

* Configurar el recolector para que se comunique con ClickHouse mediante HTTPS.
* Crear un usuario dedicado para la ingestión con permisos limitados (consulte más abajo).
* Habilitar TLS en el endpoint OTLP para cifrar la comunicación entre los SDK/agentes y el recolector. Esto puede configurarse mediante una [configuración personalizada del recopilador](#extending-collector-config).

### Creación de un usuario de ingestión {#creating-an-ingestion-user-self-configured}

Recomendamos crear una base de datos y un usuario dedicados al OTel collector para la ingestión en Self-managed ClickHouse Observability. Este usuario debe tener permisos para crear las [tablas utilizadas por el recolector](/es/clickstack/self-configured/ingesting-data/schemas) y realizar inserciones en ellas.

```sql
CREATE DATABASE otel;
CREATE USER hyperdx_ingest IDENTIFIED WITH sha256_password BY 'ClickH0u3eRocks123!';
GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO hyperdx_ingest;
```

Esto supone que el recolector se ha configurado para usar la base de datos `otel`, algo que se puede controlar mediante la variable de entorno `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`. Pase esta variable al recolector [igual que el resto de variables de entorno](#modifying-otel-collector-configuration-managed-self-configured).

## Procesamiento: filtrado, transformación y enriquecimiento {#processing-filtering-transforming-enriching-self-configured}

Invariablemente, los usuarios querrán filtrar, transformar y enriquecer los mensajes de eventos durante la ingestión. Los usuarios pueden añadir procesadores y canalizaciones al recopilador de ClickStack mediante una [configuración personalizada](#extending-collector-config). Para mantener este procesamiento fuera del recopilador de ClickStack, recomendamos a los usuarios que:

* Desplieguen su propia versión del OTel collector que realice el filtrado y el procesamiento, y envíe los eventos al recopilador de ClickStack mediante OTLP para su ingestión en ClickHouse.
* Desplieguen su propia versión del OTel collector y envíen los eventos directamente a ClickHouse mediante el exportador de ClickHouse.

Si el procesamiento se realiza con el OTel collector, recomendamos realizar las transformaciones en las instancias de puerta de enlace y minimizar el trabajo en las instancias de agente. De este modo, los recursos que necesitan los agentes en el edge, que se ejecutan en los servidores, serán los mínimos posibles. Por lo general, los usuarios solo realizan en los agentes el filtrado (para minimizar el uso innecesario de la red), la asignación de la marca de tiempo (mediante operadores) y el enriquecimiento que requiere contexto. Por ejemplo, si las instancias de puerta de enlace residen en un clúster de Kubernetes diferente, el enriquecimiento de k8s deberá realizarse en el agente.

OpenTelemetry admite las siguientes funcionalidades de procesamiento y filtrado que puede aprovechar:

* **Procesadores** - Los procesadores toman los datos recopilados por los [receivers y los modifican o transforman](https://opentelemetry.io/docs/collector/transforming-telemetry/) antes de enviarlos a los exportadores. Los procesadores se aplican en el orden configurado en la sección `processors` de la configuración del recopilador. Son opcionales, pero [suele recomendarse](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor#recommended-processors) un conjunto mínimo. Al usar un OTel collector con ClickHouse, recomendamos limitar los procesadores a:

* Un [memory&#95;limiter](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/memorylimiterprocessor/README.md), que se utiliza para evitar situaciones de falta de memoria en el recolector. Consulte [Estimación de recursos](#estimating-resources-self-configured) para ver las recomendaciones.

* Cualquier procesador que realice enriquecimiento basado en el contexto. Por ejemplo, el [Kubernetes Attributes Processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/k8sattributesprocessor) permite asignar automáticamente atributos de recurso a spans, métricas y logs con metadata de k8s, por ejemplo, para enriquecer los eventos con el id del pod de origen.

* [Muestreo tail o head](https://opentelemetry.io/docs/concepts/sampling/), si es necesario para las trazas.

* [Filtrado básico](https://opentelemetry.io/docs/collector/transforming-telemetry/): descartar los eventos innecesarios si no es posible hacerlo mediante un operador (véase más abajo).

* [Agrupación por lotes](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor/batchprocessor): esencial al trabajar con ClickHouse para garantizar que los datos se envíen en lotes. Consulte [&quot;Optimización de inserciones&quot;](#optimizing-inserts-self-configured).

* **Operadores** - Los [operadores](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/pkg/stanza/docs/operators/README.md) constituyen la unidad de procesamiento más básica disponible en el receptor. Admiten un análisis básico que permite establecer campos como Severity y Timestamp. También admiten el análisis de JSON y de expresiones regulares, además del filtrado de eventos y transformaciones básicas. Recomendamos realizar el filtrado de eventos en este punto.

Recomendamos a los usuarios evitar un procesamiento excesivo de eventos mediante operadores o [procesadores de transformación](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/transformprocessor/README.md), ya que pueden suponer una sobrecarga considerable de memoria y CPU, especialmente el análisis de JSON. Es posible realizar todo el procesamiento en ClickHouse en el momento de la inserción con vistas materializadas y columnas, salvo algunas excepciones; en concreto, el enriquecimiento dependiente del contexto, como la adición de metadata de k8s. Para más información, consulte [Extracción de estructura con SQL](/es/guides/use-cases/observability/build-your-own/schema-design#extracting-structure-with-sql).

### Ejemplo {#example-processing-self-configured}

La siguiente configuración muestra la recopilación de este [archivo de registro no estructurado](https://datasets-documentation.s3.eu-west-3.amazonaws.com/http_logs/access-unstructured.log.gz). Un recolector con el rol de agente que envía datos a la puerta de enlace de ClickStack podría utilizar esta configuración.

Observe el uso de operadores para extraer la estructura de las líneas de registro (`regex_parser`) y filtrar eventos, junto con un procesador que agrupa los eventos en batch y limita el uso de memoria.

```yaml file=code_snippets/ClickStack/config-unstructured-logs-with-processor.yaml
receivers:
  filelog:
    include:
      - /opt/data/logs/access-unstructured.log
    start_at: beginning
    operators:
      - type: regex_parser
        regex: '^(?P<ip>[\d.]+)\s+-\s+-\s+\[(?P<timestamp>[^\]]+)\]\s+"(?P<method>[A-Z]+)\s+(?P<url>[^\s]+)\s+HTTP/[^\s]+"\s+(?P<status>\d+)\s+(?P<size>\d+)\s+"(?P<referrer>[^"]*)"\s+"(?P<user_agent>[^"]*)"'
        timestamp:
          parse_from: attributes.timestamp
          layout: '%d/%b/%Y:%H:%M:%S %z'
          #22/Jan/2019:03:56:14 +0330
processors:
  batch:
    timeout: 1s
    send_batch_size: 10000
  memory_limiter:
    check_interval: 1s
    limit_mib: 2048
    spike_limit_mib: 256
exporters:
  # HTTP setup
  otlphttp/hdx:
    endpoint: 'http://localhost:4318'
    headers:
      authorization: <YOUR_INGESTION_API_KEY>
    compression: gzip

  # gRPC setup (alternative)
  otlp/hdx:
    endpoint: 'localhost:4317'
    headers:
      authorization: <YOUR_API_INGESTION_KEY>
    compression: gzip
service:
  telemetry:
    metrics:
      address: 0.0.0.0:9888 # Modified as 2 collectors running on same host
  pipelines:
    logs:
      receivers: [filelog]
      processors: [batch]
      exporters: [otlphttp/hdx]

```

Si ha configurado `OTLP_AUTH_TOKEN`, utilice ese token como valor de la cabecera de autorización en el ejemplo anterior. Consulte [Protección del recolector](#securing-the-collector-self-configured).

Para configuraciones más avanzadas, recomendamos consultar la [documentación del Colector de OpenTelemetry](https://opentelemetry.io/docs/collector/).

## Optimización de las inserciones {#optimizing-inserts-self-configured}

Para lograr un alto rendimiento de inserción y, al mismo tiempo, obtener sólidas garantías de consistencia, debe seguir unas reglas sencillas al insertar datos de observabilidad en ClickHouse mediante el recopilador de ClickStack. Con una configuración adecuada del OTel collector, cumplir las siguientes reglas debería resultar sencillo. Esto también evita los [problemas habituales](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse) con los que se encuentran los usuarios al utilizar ClickHouse por primera vez.

### Agrupación por lotes {#batching-self-configured}

De forma predeterminada, cada inserción enviada a ClickHouse hace que ClickHouse cree inmediatamente una parte de almacenamiento con los datos de la inserción junto con otra metadata que debe almacenarse. Por lo tanto, enviar menos inserciones con más datos cada una, en lugar de muchas inserciones con menos datos cada una, reducirá el número de escrituras necesarias. Recomendamos insertar datos en lotes relativamente grandes, de al menos 1,000 filas a la vez. Encontrará más información [aquí](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance).

De forma predeterminada, las inserciones en ClickHouse son síncronas e idempotentes si son idénticas. En las tablas de la familia de motores merge tree, ClickHouse [elimina automáticamente los duplicados de las inserciones](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#5-deduplication-at-insert-time) de forma predeterminada. Esto significa que las inserciones toleran situaciones como las siguientes:

* (1) Si el nodo que recibe los datos tiene problemas, se agotará el tiempo de espera de la consulta de inserción (o se producirá un error más específico) y no se recibirá una confirmación de recepción.
* (2) Si el nodo escribió los datos, pero la confirmación de recepción no puede devolverse al emisor de la consulta debido a interrupciones de red, el emisor recibirá un error de tiempo de espera agotado o un error de red.

Desde la perspectiva del recolector, puede ser difícil distinguir entre (1) y (2). Sin embargo, en ambos casos, la inserción no confirmada puede simplemente reintentarse de inmediato. Siempre que la consulta de inserción reintentada contenga los mismos datos en el mismo orden, ClickHouse ignorará automáticamente la inserción reintentada si la inserción original (no confirmada) se completó correctamente.

Por este motivo, la distribución de ClickStack del OTel collector utiliza el [procesador por lotes](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/batchprocessor/README.md). Esto garantiza que las inserciones se envíen como lotes de filas uniformes que cumplan los requisitos anteriores. Si se espera que un recolector tenga un alto rendimiento (eventos por segundo) y se pueden enviar al menos 10,000 eventos en cada inserción, esta suele ser la única agrupación por lotes necesaria en la canalización. Se pueden usar valores de hasta 100,000 si la memoria lo permite. En este caso, el recolector vaciará los lotes antes de que se alcance el `timeout` del procesador por lotes, lo que garantiza que la latencia de extremo a extremo de la canalización se mantenga baja y que los lotes tengan un tamaño uniforme.

### Usar inserciones asíncronas {#use-asynchronous-inserts-self-configured}

Normalmente, los usuarios se ven obligados a enviar lotes más pequeños cuando el caudal de un recolector es bajo y, aun así, esperan que los datos lleguen a ClickHouse con una latencia de extremo a extremo mínima. En este caso, se envían lotes pequeños cuando expira el `timeout` del procesador por lotes. Esto puede causar problemas, y es en estos casos cuando se necesitan las inserciones asíncronas. Este problema es poco frecuente si envía datos al recopilador de ClickStack actuando como puerta de enlace: al funcionar como agregadores, mitigan este problema; consulte [Roles del recopilador](#collector-roles-self-configured).

Si no se pueden garantizar lotes grandes, puede delegar la agrupación por lotes a ClickHouse mediante [Inserciones asíncronas](/es/concepts/best-practices/selecting-an-insert-strategy#asynchronous-inserts). Con las inserciones asíncronas, los datos se insertan primero en un búfer y, posteriormente, se escriben en el almacenamiento de la base de datos de forma asíncrona.

<div className="ch-image-md">
  <Frame>
    ![Inserciones asíncronas](/images/use-cases/observability/observability-6.webp)
  </Frame>
</div>

Con las [inserciones asíncronas habilitadas](/es/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts), cuando ClickHouse ① recibe una consulta de inserción, los datos de la consulta se ② escriben inmediatamente en un búfer en memoria. Cuando ③ se produce el siguiente vaciado del búfer, los datos del búfer se [ordenan](/es/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns) y se escriben como una parte en el almacenamiento de la base de datos. Tenga en cuenta que los datos no pueden consultarse hasta que se vuelcan en el almacenamiento de la base de datos; el vaciado del búfer es [configurable](/es/concepts/features/operations/insert/asyncinserts).

Para habilitar las inserciones asíncronas en el recolector, añada `async_insert=1` a la cadena de conexión. Recomendamos usar `wait_for_async_insert=1` (el valor predeterminado) para obtener garantías de entrega; consulte [aquí](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse) para más detalles.

Los datos de una inserción asíncrona se insertan una vez que se vacía el búfer de ClickHouse. Esto ocurre cuando se supera [`async_insert_max_data_size`](/es/reference/settings/session-settings/async-insert#async_insert_max_data_size) o cuando han transcurrido [`async_insert_busy_timeout_ms`](/es/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms) milisegundos desde la primera consulta INSERT. Si `async_insert_stale_timeout_ms` se establece en un valor distinto de cero, los datos se insertan transcurridos `async_insert_stale_timeout_ms milliseconds` desde la última consulta. Puede ajustar estos parámetros para controlar la latencia de extremo a extremo de su canalización. Los demás ajustes que permiten optimizar el vaciado del búfer están documentados [aquí](/es/reference/settings/session-settings/async-insert#async_insert). Por lo general, los valores predeterminados son adecuados.

<Info>
  **Considere las inserciones asíncronas adaptativas**

  Cuando se utiliza un número reducido de agentes, con bajo caudal pero requisitos estrictos de latencia de extremo a extremo, las [inserciones asíncronas adaptativas](https://clickhouse.com/blog/clickhouse-release-24-02#adaptive-asynchronous-inserts) pueden resultar útiles. Por lo general, no son aplicables a casos de uso de observabilidad con alto caudal, como los habituales con ClickHouse.
</Info>

Por último, el comportamiento anterior de eliminación de duplicados asociado a las inserciones síncronas en ClickHouse no está habilitado de forma predeterminada al usar inserciones asíncronas. Si lo necesita, consulte el parámetro de configuración [`async_insert_deduplicate`](/es/reference/settings/session-settings/async-insert#async_insert_deduplicate).

Encontrará todos los detalles sobre cómo configurar esta funcionalidad en esta [página de la documentación](/es/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts) o en una [entrada de blog](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse) con un análisis en profundidad.

## Escalado {#scaling-self-configured}

El colector OTel de ClickStack actúa como una instancia de puerta de enlace; consulte [Roles del recopilador](#collector-roles-self-configured). Las puertas de enlace proporcionan un servicio independiente, normalmente uno por centro de datos o por región, y reciben eventos de las aplicaciones (o de otros recolectores con el rol de agente) a través de un único endpoint OTLP. Lo habitual es desplegar un conjunto de instancias del recolector y utilizar un balanceador de carga estándar para distribuir la carga entre ellas.

<div className="ch-image-lg">
  <Frame>
    ![Escalado con puertas de enlace](/images/use-cases/observability/clickstack-with-gateways.webp)
  </Frame>
</div>

El objetivo de esta arquitectura es liberar a los agentes del procesamiento más intensivo en cómputo y reducir así al mínimo su consumo de recursos. Estas puertas de enlace de ClickStack pueden encargarse de tareas de transformación que, de otro modo, tendrían que realizar los agentes. Además, al agregar eventos de numerosos agentes, las puertas de enlace garantizan que se envíen lotes grandes a ClickHouse, lo que permite una inserción eficiente. Estos recolectores de puerta de enlace se pueden escalar fácilmente a medida que se incorporan más agentes y fuentes de SDK y aumenta el caudal de eventos.

### Incorporación de Kafka {#adding-kafka-self-configured}

Es posible que los lectores hayan observado que las arquitecturas anteriores no utilizan Kafka como cola de mensajes.

Usar una cola de Kafka como búfer de mensajes es un patrón de diseño habitual en las arquitecturas de registro, popularizado por el stack ELK. Ofrece algunas ventajas: principalmente, proporciona garantías de entrega de mensajes más sólidas y ayuda a gestionar la contrapresión. Los mensajes se envían desde los agentes de recolección a Kafka y se escriben en disco. En teoría, una instancia de Kafka en cluster debería proporcionar un búfer de mensajes de alto rendimiento, ya que escribir datos de forma secuencial en disco supone menos sobrecarga computacional que analizar y procesar un mensaje. En Elastic, por ejemplo, la tokenización y la indexación generan una sobrecarga considerable. Al sacar los datos de los agentes, también se reduce el riesgo de perder mensajes a causa de la rotación de logs en el origen. Por último, ofrece ciertas capacidades de reproducción de mensajes y de replicación cross-region, que pueden resultar atractivas para algunos casos de uso.

Sin embargo, ClickHouse puede gestionar la inserción de datos a gran velocidad: millones de filas por segundo en hardware modesto. La contrapresión por parte de ClickHouse es poco frecuente. A menudo, recurrir a una cola de Kafka implica mayor complejidad arquitectónica y mayor coste. Si puede asumir que los logs no necesitan las mismas garantías de entrega que las transacciones bancarias y otros datos críticos, recomendamos evitar la complejidad de Kafka.

No obstante, si necesita garantías de entrega estrictas o la capacidad de reproducir datos (posiblemente hacia varias fuentes), Kafka puede ser un complemento útil para la arquitectura.

<div className="ch-image-lg">
  <Frame>
    ![Incorporación de Kafka](/images/use-cases/observability/observability-8.webp)
  </Frame>
</div>

En este caso, los agentes de OTel pueden configurarse para enviar datos a Kafka mediante el [exportador de Kafka](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/kafkaexporter/README.md). Las instancias de puerta de enlace, a su vez, consumen los mensajes mediante el [receptor de Kafka](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/kafkareceiver/README.md). Para más detalles, recomendamos consultar la documentación de Confluent y de OTel.

<Info>
  **Configuración del OTel collector**

  La distribución del Recopilador de OpenTelemetry de ClickStack puede configurarse con Kafka mediante una [configuración personalizada del recopilador](#extending-collector-config).
</Info>

## Estimación de recursos {#estimating-resources-self-configured}

Los requisitos de recursos del OTel collector dependerán del caudal de eventos, del tamaño de los mensajes y del volumen de procesamiento realizado. El proyecto OpenTelemetry mantiene [pruebas de rendimiento](https://opentelemetry.io/docs/collector/benchmarks/) que los usuarios pueden utilizar para estimar los requisitos de recursos.

[Según nuestra experiencia](https://clickhouse.com/blog/building-a-logging-platform-with-clickhouse-and-saving-millions-over-datadog#architectural-overview), una instancia de puerta de enlace de ClickStack con 3 núcleos y 12GB de RAM puede procesar alrededor de 60k eventos por segundo. Esto presupone una canalización de procesamiento mínima, que se limite a renombrar campos y no utilice expresiones regulares.

Para las instancias de agente que se encargan de enviar eventos a una puerta de enlace y que solo establecen la marca de tiempo en el evento, recomendamos dimensionarlas en función del volumen de logs por segundo previsto. Los siguientes valores aproximados pueden servir como punto de partida:

| Tasa de registro | Recursos para el agente recolector |
| ---------------- | ---------------------------------- |
| 1k/segundo       | 0.2CPU, 0.2GiB                     |
| 5k/segundo       | 0.5 CPU, 0.5GiB                    |
| 10k/segundo      | 1 CPU, 1GiB                        |

## Elección de esquema: Map frente a JSON {#schema-choice-self-configured}

El recopilador de ClickStack crea de forma predeterminada tablas que almacenan los atributos en columnas `Map(LowCardinality(String), String)`. Este es el esquema recomendado para workloads de observabilidad. También hay disponible, en Beta, un esquema basado en el tipo `JSON` para evaluarlo en workloads con un conjunto de claves de atributo reducido y estable.

Para consultar la comparación completa, cuándo conviene cada opción, las variables de entorno necesarias para activar el esquema basado en el tipo JSON y la guía paso a paso de migración, consulte [Map frente a Tipo JSON](/es/clickstack/self-configured/ingesting-data/schema/map-vs-json).
