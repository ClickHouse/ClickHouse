## Retención de datos con TTL {#ttl-clickstack}

Time-to-Live (TTL) es una funcionalidad fundamental en Self-managed ClickHouse Observability para retener y gestionar los datos de forma eficiente, sobre todo teniendo en cuenta los enormes volúmenes de datos que se generan continuamente. TTL permite la expiración y eliminación automáticas de los datos más antiguos, lo que garantiza un uso óptimo del almacenamiento y mantiene el rendimiento sin intervención manual. Esta capacidad es esencial para mantener la base de datos ligera, reducir los costes de almacenamiento y lograr que las consultas sigan siendo rápidas y eficientes al centrarse en los datos más relevantes y recientes. Además, facilita el cumplimiento de las políticas de retención de datos al gestionar de forma sistemática su ciclo de vida, lo que mejora la sostenibilidad y la escalabilidad generales de la solución de observabilidad.

**De forma predeterminada, los datos se conservan durante 30 días. Para modificarlo, consulte [&quot;Modificar TTL&quot;](#modifying-ttl).**

En ClickHouse, TTL se controla a nivel de tabla. Por ejemplo, a continuación se muestra el esquema predeterminado para los log; `${TABLES_TTL}` se sustituye por la retención configurada (30 días, salvo que se modifique) cuando el collector crea la tabla:

La partición en ClickHouse permite separar lógicamente los datos en disco según una columna o una expresión SQL. Al separar los datos de forma lógica, cada partición puede gestionarse de manera independiente; por ejemplo, puede eliminarse cuando expira según una política de TTL.

Como se muestra en el ejemplo anterior, la partición se especifica en una tabla al definirla inicialmente mediante la cláusula `PARTITION BY`. Esta cláusula puede contener una expresión SQL sobre una o varias columnas, cuyo resultado determina a qué partición se envía cada fila. Así, los datos quedan asociados lógicamente (mediante un prefijo común en el nombre de la carpeta) a cada partición en el disco, que después puede consultarse de forma aislada. En el ejemplo anterior, el esquema predeterminado `otel_logs` particiona por día mediante la expresión `toDate(Timestamp)`. A medida que se insertan filas en ClickHouse, esta expresión se evalúa para cada fila y esta se dirige a la partición resultante si existe (si la fila es la primera de un día, se crea la partición). Para obtener más información sobre la partición y sus otras aplicaciones, consulte [&quot;Particiones de tabla&quot;](/es/concepts/core-concepts/partitions).

El esquema de la tabla también incluye `TTL toDateTime(Timestamp) + ${TABLES_TTL}` y el parámetro de configuración `ttl_only_drop_parts = 1`. La primera cláusula garantiza que los datos se eliminen cuando superen el TTL configurado (30 días de forma predeterminada). El parámetro `ttl_only_drop_parts = 1` hace que solo expiren las partes de datos en las que todos los datos han expirado (en lugar de intentar eliminar filas parcialmente). Dado que la partición garantiza que los datos de días distintos nunca se &quot;fusionen&quot;, los datos pueden eliminarse de forma eficiente.

<Warning>
  **`ttl_only_drop_parts`**

  Recomendamos usar siempre el parámetro de configuración [`ttl_only_drop_parts=1`](/es/reference/settings/merge-tree-settings/other#ttl_only_drop_parts). Cuando está habilitado, ClickHouse elimina una parte completa cuando todas sus filas han expirado. Eliminar partes completas en lugar de limpiar parcialmente las filas con TTL vencido (lo que se hace mediante mutaciones costosas en recursos cuando `ttl_only_drop_parts=0`) permite valores de `merge_with_ttl_timeout` más cortos y un menor impacto en el rendimiento del sistema. Si los datos se particionan por la misma unidad con la que se aplica la expiración por TTL (por ejemplo, por día), las partes contendrán de forma natural solo datos del intervalo definido. Esto garantiza que `ttl_only_drop_parts=1` pueda aplicarse de forma eficiente.
</Warning>

De forma predeterminada, los datos con un TTL expirado se eliminan cuando ClickHouse [fusiona partes de datos](/es/reference/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage). Cuando ClickHouse detecta que hay datos expirados, realiza una fusión fuera de programación.

<Info>
  **Programación de TTL**

  Los TTL no se aplican de inmediato, sino según una programación, como se ha indicado anteriormente. El parámetro de configuración de tabla MergeTree `merge_with_ttl_timeout` establece el retraso mínimo, en segundos, antes de repetir una fusión con TTL de eliminación. El valor predeterminado es de 14400 segundos (4 horas). No obstante, se trata solo del retraso mínimo: una fusión por TTL puede tardar más en activarse. Si el valor es demasiado bajo, se realizarán muchas fusiones fuera de programación que pueden consumir muchos recursos. Se puede forzar la expiración por TTL con el comando `ALTER TABLE my_table MATERIALIZE TTL`.
</Info>

## Modificar TTL {#modifying-ttl}

Para modificar el TTL, tiene las siguientes opciones:

1. **Modificar los esquemas de tabla (recomendado)**. Para ello, es necesario conectarse a la instancia de ClickHouse, por ejemplo, mediante [clickhouse-client](/es/concepts/features/interfaces/client) o la [Consola SQL de Cloud](/es/products/cloud/features/sql-console-features/sql-console). Por ejemplo, podemos modificar el TTL de la tabla `otel_logs` con la siguiente sentencia DDL:

```sql
ALTER TABLE default.otel_logs
MODIFY TTL TimestampTime + toIntervalDay(7);
```

2. **Modificar el OTel collector**. El Recopilador de OpenTelemetry de ClickStack crea las tablas en ClickHouse si no existen. Para ello utiliza el Exportador de ClickHouse, que a su vez expone un parámetro `ttl` que permite controlar la expresión TTL predeterminada, p. ej.

```yaml
exporters:
 clickhouse:
   endpoint: tcp://localhost:9000?dial_timeout=10s&compress=lz4&async_insert=1
   ttl: 72h
```

### TTL a nivel de columna {#column-level-ttl}

Los ejemplos anteriores hacen expirar los datos a nivel de tabla, pero también es posible hacerlo a nivel de columna. A medida que los datos envejecen, esto permite eliminar columnas cuyo valor en las investigaciones no justifica la sobrecarga de recursos que supone conservarlas. Por ejemplo, recomendamos conservar la columna `Body` por si se añade nueva metadata dinámica que no se haya extraído en el momento de inserción, como una nueva etiqueta de Kubernetes. Pasado un período, por ejemplo, 1 mes, puede resultar evidente que esta metadata adicional no es útil, lo que reduce el valor de conservar la columna `Body`.

A continuación, mostramos cómo eliminar la columna `Body` transcurridos 30 días.

```sql
CREATE TABLE otel_logs_v2
(
        `Body` String TTL Timestamp + INTERVAL 30 DAY,
        `Timestamp` DateTime,
 ...
)
ENGINE = MergeTree
ORDER BY (ServiceName, Timestamp)
```

<Note>
  Para especificar un TTL a nivel de columna, los usuarios deben definir su propio esquema. Esto no se puede configurar en el OTel collector.
</Note>
