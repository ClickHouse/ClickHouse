<Note>
  Esta página trata sobre **Self-managed ClickHouse Observability**. Si prefiere la experiencia totalmente gestionada, que es la opción recomendada, consulte la documentación [aquí](/es/clickstack/observability/getting-started).
</Note>

Esta guía le acompaña desde un servicio vacío de Self-managed ClickHouse Observability hasta recibir logs, métricas, trazas y reproducciones de sesiones procedentes de una aplicación real. Desplegará un nuevo recolector de OpenTelemetry (o adaptará el que ya tenga) conectado a su servicio, instrumentará una aplicación Node.js de ejemplo sin modificar su lógica de negocio y, por último, explorará la telemetría en la UI de ClickStack.

<Note>
  Tanto si configura un recolector nuevo como si usa el suyo propio, este debe ejecutarse como **puerta de enlace**: un único endpoint OTLP al que sus aplicaciones, SDKs y recolectores agente envían los datos. La puerta de enlace agrupa los eventos en lotes, aplica el procesamiento que haya configurado y los escribe en ClickHouse mediante el [Exportador de ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).
</Note>

La aplicación que instrumentaremos es [HackerNews Analyzer](https://github.com/ClickHouse/hn-news-analyzer), una aplicación Node.js que consulta el conjunto de datos de HackerNews alojado en la demo pública de ClickHouse. Cada gráfico, tabla y cuadro de búsqueda se basa en una consulta de ClickHouse real, de modo que cada interacción genera una traza cuyo span principal es la llamada HTTPS que el backend realiza a ClickHouse.

## Requisitos previos {#prerequisites}

* Un **servicio de Self-managed ClickHouse Observability** en [ClickHouse Cloud](https://console.clickhouse.cloud).
* **Node 18+ y npm** para ejecutar la aplicación de ejemplo.
* **Docker**, si aún no tiene un recolector y desea seguir la opción de un nuevo recolector que se describe a continuación.

  <Step title="Desplegar el recolector" id="deploy-collector">
    Elija la opción que corresponda a su situación.

    <Info>
      **Recolector existente**

      Si utiliza un recolector de OpenTelemetry existente, damos por hecho que ya está configurado con el rol de **puerta de enlace**. No recomendamos seguir este proceso para reconfigurar recolectores con el rol de **agente**.
    </Info>

    <Tabs>
      <Tab title="No tengo un recolector">
        Despliegue la **distribución de ClickStack del recolector de OpenTelemetry**, preconfigurada para ClickHouse Observability autogestionado. Para simplificar, en el siguiente ejemplo ejecutamos el recolector en local.

        <Note>
          En producción, lo habitual es desplegar el recolector en un clúster de Kubernetes o en una máquina virtual accesible desde sus SDK de OpenTelemetry, agentes y otros recolectores. Así, la telemetría de todo su entorno se recopila de forma centralizada y se redirige a ClickStack.
        </Note>

        Elija un secreto compartido para autenticar a los clientes que envían datos al recolector y, a continuación, expórtelo junto con sus datos de conexión y la contraseña elegida para el usuario `hyperdx_ingest`:

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        Ejecute el colector OTel de ClickStack:

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        El recolector ahora expone OTLP gRPC en el puerto `4317` y OTLP HTTP en el `4318`. Las aplicaciones, los SDK y los recolectores en modo agente deben enviar datos a estos puertos incluyendo `authorization: $OTLP_AUTH_TOKEN` en los encabezados de la solicitud. Tenga a mano el endpoint OTLP y el `OTLP_AUTH_TOKEN`, ya que en los próximos pasos configurará la aplicación para que apunte a ellos.

        <Info>
          **Implementaciones en producción**

          En entornos de producción, recomendamos habilitar TLS en el endpoint OTLP. Consulte [Proteger el recolector](/es/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        </Info>
      </Tab>

      <Tab title="Tengo un recolector">
        Amplíe la configuración existente de su recopilador para escribir en Self-managed ClickHouse Observability mediante el [exportador de ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

        <Info>
          **Se requiere el exportador de ClickHouse**

          Si utiliza su propia distribución, asegúrese de que incluya el exportador de ClickHouse. La [imagen contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) upstream ya lo incluye.
        </Info>

        A continuación se muestra un ejemplo de configuración que utiliza el exportador de ClickHouse con los receivers, procesadores y canalizaciones que espera la UI de ClickStack. Reproduce el comportamiento de la distribución de ClickStack, incluida la ruta de enrutamiento de la reproducción de sesiones (`rrweb`). Sustituya `<clickhouse_cloud_endpoint>` y `<your_password_here>` por las credenciales del usuario `hyperdx_ingest` creado anteriormente:

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        Algunos aspectos a tener en cuenta:

        * El receiver `otlp/hyperdx` escucha tanto en gRPC (`4317`) como en HTTP (`4318`); las aplicaciones y los agentes deben apuntar a estos puertos en el host de su recolector.
        * El exportador `clickhouse` escribe logs, trazas y métricas en la base de datos `otel`, con la disposición que espera la UI de ClickStack. El exportador `clickhouse/rrweb` gestiona los eventos de reproducción de sesiones que el connector `routing/logs` dirige hacia `otel.hyperdx_sessions`.
        * La autenticación en los receivers OTLP depende de su configuración actual. Si necesita exigir un token de ingestión, configúrela mediante [extensiones](https://opentelemetry.io/docs/collector/configuration/#extensions) del recolector (por ejemplo, `bearertokenauth`) o mediante un proxy inverso con TLS.

        Recargue su recolector con la nueva configuración. Tenga a mano el endpoint OTLP y el encabezado de autenticación que requiera su configuración: en los siguientes pasos dirigirá la aplicación hacia ellos.

        Para obtener más información sobre cómo configurar los Colectores de OpenTelemetry con Self-managed ClickHouse Observability, consulte [Ingesta con OpenTelemetry](/es/clickstack/observability/ingesting-data/opentelemetry#self-managed).
      </Tab>
    </Tabs>
  </Step>

  <Step title="Clone y ejecute la aplicación" id="clone-and-run-the-application">
    Clona el repositorio, instala las dependencias y crea tu archivo `.env`:

    ```bash
    git clone https://github.com/ClickHouse/hn-news-analyzer.git
    cd hn-news-analyzer
    npm install
    cp .env.example .env
    ```

    La fuente de datos de ClickHouse apunta de forma predeterminada al cluster de demostración público de solo lectura, por lo que la aplicación funciona sin ninguna configuración adicional. Para iniciarla:

    ```bash
    ./run.sh
    ```

    Abra [http://localhost:5001](http://localhost:5001). Verá un selector de año, estadísticas de resumen, un gráfico de actividad, tablas con los principales usuarios y dominios, y un cuadro de búsqueda. Explore la aplicación: cambie de año y profundice en las historias.

    <div className="ch-image-lg">
      <Frame>
        ![La aplicación HackerNews Analyzer ejecutándose en local](/images/clickstack/getting-started/hackernews_main.webp)
      </Frame>
    </div>

    En este punto, la aplicación está en ejecución, pero sin instrumentar. ClickStack no muestra datos: está a la espera de telemetría. Este es el estado &quot;antes&quot;.
  </Step>

  <Step title="Conecte la aplicación a su recolector" id="connect-the-application">
    La aplicación necesita dos valores para conectarse al recolector que desplegó anteriormente:

    * `OTEL_EXPORTER_OTLP_ENDPOINT`: el endpoint OTLP que expone su recolector (normalmente el puerto `4318` para OTLP sobre HTTPS).
    * `OTEL_EXPORTER_OTLP_HEADERS`: la cabecera de autorización que contiene su token de ingestión, con el formato `authorization=<ingestion_token>`. Utilice el `OTLP_AUTH_TOKEN` que configuró anteriormente en el recolector o el encabezado de autenticación que requiera su recolector existente.

    Copie `.env.example` a `.env`, abra el archivo y configure las siguientes variables:

    ```bash
    OTEL_SERVICE_NAME=hn-analyzer-api
    OTEL_EXPORTER_OTLP_ENDPOINT=https://<your-collector-endpoint>:4318
    OTEL_EXPORTER_OTLP_HEADERS=authorization=<ingestion_token>
    ```

    El SDK utiliza `OTEL_EXPORTER_OTLP_HEADERS` para definir la cabecera de autorización de las tres señales: trazas, métricas y logs. Si su recolector se ejecuta localmente y no requiere autenticación, puede dejar el valor vacío (`OTEL_EXPORTER_OTLP_HEADERS=authorization=`), pero la variable debe estar presente: si no está definida o está completamente vacía, el SDK omite por completo la inicialización. Por último, si ejecuta el recolector sin TLS, asegúrese de utilizar el protocolo HTTP correcto (p. ej., `http://localhost:4318`).
  </Step>

  <Step title="Instrumente la aplicación" id="instrument-the-application">
    La instrumentación consta de tres pasos: instalar los SDK, cambiar el comando de inicio y habilitar el SDK para navegador. Nada de esto modifica la lógica de negocio de la aplicación.

### Instalar los SDK {#install-sdks}

    Instale los SDK de OpenTelemetry tanto para el backend como para el navegador:

    ```bash
    npm install @hyperdx/node-opentelemetry @hyperdx/browser
    ```

### Usar la CLI opentelemetry-instrument {#use-open-telemetry-cli}

    La aplicación se inicia mediante `run.sh`, que contiene dos líneas `exec` al final: una activa y otra comentada. Intercambie cuál de las dos está activa para que Node se ejecute envuelto por `opentelemetry-instrument`:

    ```diff
     # BEFORE: plain node, no instrumentation, collector stays silent:
    -exec node scripts/entrypoint.js
    +# exec node scripts/entrypoint.js

     # AFTER: same source, wrapped by opentelemetry-instrument CLI.
    -# exec npx opentelemetry-instrument scripts/entrypoint.js
    +exec npx opentelemetry-instrument scripts/entrypoint.js
    ```

    Ese es el único cambio necesario en el backend. `opentelemetry-instrument` carga la autoinstrumentación al iniciar el proceso.

### Activar el SDK para navegador {#enable-browser-sdk}

    Para capturar trazas distribuidas (del navegador al backend) y reproducciones de sesiones, active el SDK para navegador en `src/web/telemetry.ts`. Descomente la importación y el bloque `HyperDX.init({...})`:

    ```javascript
    import HyperDX from '@hyperdx/browser';

    export function initTelemetry(): void {
      HyperDX.init({
        url: __OTLP_ENDPOINT__,
        apiKey: __OTLP_AUTH_TOKEN__,
        service: 'hn-analyzer-web',
        tracePropagationTargets: [/localhost:5001/i, /\/api\//i],
        consoleCapture: true,
        advancedNetworkCapture: true,
      });
    }
    ```

    No es necesario realizar modificaciones adicionales en `.env`. `__OTLP_ENDPOINT__` y `__OTLP_AUTH_TOKEN__` son constantes de tiempo de compilación inyectadas por `vite.config.ts`: el endpoint es `OTEL_EXPORTER_OTLP_ENDPOINT` y el token se obtiene analizando `OTEL_EXPORTER_OTLP_HEADERS`, es decir, los mismos valores que utiliza el backend.

    <Warning>
      El token de ingestión queda incrustado en el paquete público del navegador, por lo que cualquiera que inspeccione la pestaña Red puede leerlo.
    </Warning>
  </Step>

  <Step title="Generar tráfico" id="generate-traffic">
    Reinicie la aplicación para que se apliquen el nuevo comando de inicio y el paquete del navegador recién compilado:

    ```bash
    # Ctrl-C the previous run, then:
    ./run.sh
    ```

    Recargue la pestaña del navegador para que Vite sirva el bundle actualizado; después, actualice la aplicación varias veces, cambie de año y abra algunas historias para generar tráfico. Cada interacción envía logs, métricas, trazas y eventos de reproducción de sesiones a ClickStack a través de su recolector.
  </Step>

    Si no aparece nada:

    * Confirme que el valor de la cabecera de autenticación definido en `OTEL_EXPORTER_OTLP_HEADERS` coincide con el que espera su recolector.
    * Siga en tiempo real los logs de su recolector y busque errores de exportación.
    * Verifique que el endpoint de ClickHouse configurado en el recolector incluya tanto el protocolo como el puerto (`https://...:8443`).
