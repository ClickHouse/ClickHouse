Esta guía le muestra cómo desplegar un Colector de OpenTelemetry en un servicio de Self-managed ClickHouse Observability ya existente, o cómo adaptar el recolector que ya tiene, y cómo comprobar después que los datos fluyen correctamente.

Instale las ClickHouse agent skills oficiales antes de usar el asistente de configuración:

```bash
npx skills add clickhouse/agent-skills
```

El recolector se ejecuta como **puerta de enlace**: un único endpoint OTLP al que envían datos tus aplicaciones, SDK y recolectores agente. La puerta de enlace agrupa los eventos en lotes, aplica el procesamiento que hayas configurado y los escribe en ClickHouse mediante el [Exportador de ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter). Este patrón mantiene la lógica de recopilación fuera de tu código de aplicación y te permite escalar la ingestión de forma independiente de los workload que generan los datos. Para obtener más información sobre los roles de puerta de enlace y de agente, consulta [Roles del recopilador](/es/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured).

<Info>
  **Recolector existente**

  Si utilizas un Colector de OpenTelemetry existente, damos por hecho que ya está configurado con el rol de **puerta de enlace**. No recomendamos usar este procedimiento para reconfigurar recolectores con el rol de **agente**.
</Info>

      <Step title="Despliegue el recolector" id="deploy-the-collector">
        Despliegue la **distribución de ClickStack del recolector de OpenTelemetry**, que viene preconfigurada para Self-managed ClickHouse Observability. Para simplificar, en el siguiente ejemplo ejecutamos el recolector localmente y generamos telemetría artificial desde la misma máquina.

        <Note>
          En producción, lo habitual es desplegar el recolector en un clúster de Kubernetes o en una máquina virtual accesible para sus SDK de OpenTelemetry, agentes y otros recolectores. De este modo, la telemetría de todo su entorno se recopila de forma centralizada y se reenvía a ClickStack.
        </Note>

        Elija un secreto compartido para autenticar a los clientes que envían datos al recolector y, a continuación, expórtelo junto con sus datos de conexión y la contraseña elegida para el usuario `hyperdx_ingest`:

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        Ejecute el colector OTel de ClickStack:

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        El recolector ahora expone OTLP gRPC en el puerto `4317` y OTLP HTTP en el `4318`. Las aplicaciones, los SDK y los recolectores en modo agente deben enviar datos a estos puertos incluyendo `authorization: $OTLP_AUTH_TOKEN` en los encabezados de la solicitud.

        <Info>
          **Implementaciones en producción**

          En entornos de producción, recomendamos habilitar TLS en el endpoint OTLP. Consulte [Proteger el recolector](/es/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        </Info>
      </Step>

      <Step title="Verifique el endpoint" id="verify-the-endpoint">
        Genere algo de tráfico sintético hacia el recolector para comprobar que toda la canalización funciona correctamente. Usamos [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen), el generador de OpenTelemetry Collector Contrib, que emite logs, trazas y métricas OTLP, y ofrece indicadores para modelar los datos según servicios, niveles de severidad, estados de span y tipos de métrica.

        Ejecútelo desde su imagen de Docker (no requiere instalación). Defina un pequeño envoltorio para que los comandos siguientes resulten legibles; `--add-host` permite que el contenedor acceda a un recolector que escucha en el host:

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        O bien, instale el binary con Go y use `localhost` como destino:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```

        <Info>
          **Qué esperar**

          Cada ejecución de `tg` dura unos 20 segundos (según lo definido por `--duration 20s`) y emite logs detallados durante todo ese tiempo, lo cual es normal; cada ejecución termina por sí sola una vez transcurridos sus 20 segundos. Los logs siguientes bastan para verificar la canalización; el conjunto opcional, más completo, añade varias ejecuciones más y tarda unos minutos.
        </Info>

        Defina un pequeño helper `tg` para que cada comando solo especifique lo que varía (servicio, gravedad, estado, atributos):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        Envíe logs con una combinación realista de niveles de gravedad entre los distintos servicios, en su mayoría informativos, junto con una advertencia y un error, en lugar de un único flujo uniforme de errores:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        Los logs por sí solos bastan para confirmar que el endpoint funciona. Para obtener un conjunto de datos de demostración más completo, un mapa de servicios con varios servicios y gráficos de distintos tipos de métricas, despliegue y ejecute también los comandos siguientes. Reutilizan el helper `tg`, así que ejecútelos en la misma shell.

        <Accordion title="Genere telemetría más detallada (opcional)">
          Envíe trazas con varios spans desde distintos servicios en buen estado, además de una dependencia que falla. Así, el mapa de servicios adopta una forma realista (la mayoría de los servicios en buen estado y uno que genera errores) y, aun así, se rellenan las vistas de errores:

          ```shell
          # Healthy services: the bulk of the traffic, all spans Ok
          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          Envíe métricas de los tres tipos habituales para que los gráficos dispongan de un contador, un gauge y una distribución:

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          Para obtener aún más variedad, añada un par de servicios más y un histograma exponencial:

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        Para consultar todos los indicadores disponibles y otras variantes, consulte [Datos sintéticos con telemetrygen](/es/clickstack/observability/example-datasets/telemetrygen#self-managed).
      </Step>

      <Step title="Adapte la configuración del recopilador" id="adapt-collector">
        Amplíe su configuración del recopilador existente para que escriba en Self-managed ClickHouse Observability mediante el [exportador de ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

        <Info>
          **Se requiere el exportador de ClickHouse**

          Si utiliza su propia distribución, asegúrese de que incluya el exportador de ClickHouse. La [imagen contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) upstream ya lo incluye.
        </Info>

        A continuación se muestra una configuración de ejemplo que utiliza el exportador de ClickHouse con los receivers, procesadores y canalizaciones que espera la UI de ClickStack. Reproduce el comportamiento de la distribución de ClickStack, incluida la ruta de enrutamiento de la reproducción de sesiones (`rrweb`). Sustituya `<clickhouse_cloud_endpoint>` y `<your_password_here>` por las credenciales del usuario `hyperdx_ingest` creado anteriormente:

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        Algunos aspectos a tener en cuenta:

        * El receptor `otlp/hyperdx` escucha tanto en gRPC (`4317`) como en HTTP (`4318`); las aplicaciones y los agentes deben apuntar a estos puertos en el host de su recolector.
        * El exportador `clickhouse` escribe logs, trazas y métricas en la base de datos `otel`, siguiendo la disposición que espera la UI de ClickStack. El exportador `clickhouse/rrweb` gestiona los eventos de reproducción de sesiones que el connector `routing/logs` enruta hacia `otel.hyperdx_sessions`.
        * La autenticación en los receivers OTLP depende de su configuración actual. Configúrela mediante [extensiones](https://opentelemetry.io/docs/collector/configuration/#extensions) del recolector (por ejemplo, `bearertokenauth`) o mediante un proxy inverso con terminación TLS si necesita exigir un token de ingestión.

        Recargue su recolector con la nueva configuración. A partir de ese momento, las aplicaciones, los SDKs y los recolectores que actúan como agente deben enviar datos a los endpoints OTLP que expone su recolector, con el encabezado de autenticación que requiera su configuración.

        Para obtener más información sobre cómo configurar los Colectores de OpenTelemetry con Self-managed ClickHouse Observability, consulte [Ingesta con OpenTelemetry](/es/clickstack/observability/ingesting-data/opentelemetry#self-managed).
      </Step>

      <Step title="Verifique el endpoint" id="verify-the-endpoint-existing">

Usamos [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen), el generador de OpenTelemetry Collector Contrib, que emite logs, trazas y métricas OTLP y ofrece indicadores para modelar los datos por servicio, nivel de severidad, estado de span y tipo de métrica.

## Siguientes pasos: envíe sus propios datos {#next-steps}

La ráfaga sintética anterior solo demuestra que la canalización funciona. Para empezar a enviar telemetría real, instrumente sus propios servicios con los [SDK de ClickStack](/es/clickstack/observability/ingesting-data/sdks), que ofrecen instrumentación para Node.js, Python, Go, Java y otros lenguajes, y exportan OTLP al endpoint del recolector que acaba de verificar. Para ver un ejemplo completo, consulte [Instrumentar una aplicación](/es/clickstack/self-configured/managed-onboarding/instrument-application).

Para recopilar datos de la infraestructura en lugar del código de aplicación:

* [Monitorización de Kubernetes](/es/clickstack/self-configured/managed-onboarding/monitoring-kubernetes): recopile logs, métricas de infraestructura y eventos de Kubernetes de un cluster.
* [Monitorización de logs de AWS CloudWatch](/es/clickstack/self-configured/managed-onboarding/monitoring-aws-cloudwatch-logs): reenvíe los logs de CloudWatch mediante el receptor de CloudWatch de OpenTelemetry.
