## Descripción {#description}

Muestra al usuario actual sus propios registros de consultas. Lee la tabla de registro de consultas configurada mediante los ajustes del servidor `query_log.database` y `query_log.table` (`system.query_log` de forma predeterminada) y devuelve únicamente las filas cuyo usuario iniciador es igual a `currentUser()` (el usuario iniciador se toma de `initial_user` cuando está establecido; de lo contrario, de `user`). Un usuario actual autenticado no puede estar vacío y debe coincidir con el usuario inicial registrado. El cliente `clickhouse-local`, que no está autenticado, es la excepción: puede leer filas con un usuario iniciador vacío solo cuando ambas identidades de usuario están vacías y la consulta usa la interfaz `LOCAL`. En los demás casos, la tabla no devuelve ninguna fila.

A diferencia de la propia tabla de registro de consultas, `system.user_query_log` puede leerse sin ningún permiso, por lo que los usuarios pueden inspeccionar sus propias consultas sin que se les conceda acceso a las consultas de otros.

Solo se devuelven las filas de nivel superior (`is_initial_query = 1`). Se omiten las filas hijas, como las consultas que una consulta distribuida envía a otros servidores o lo que se ejecuta bajo la identidad de las vistas `SQL SECURITY DEFINER` y `NONE`.

Una política de filas que expone filas de `system.query_log` por usuario (`user`, `initial_user` o `authenticated_user`) también expone esas filas hijas, por lo que conviene añadirle la condición `is_initial_query = 1` o usar `system.user_query_log`.

Esto solo se admite cuando el registro de consultas se almacena localmente. Si `query_log.engine` está configurado como `Distributed` o cualquier otro motor que delegue las lecturas en otro servidor, `system.user_query_log` se niega a leer de ella y genera una excepción, ya que la comprobación de acceso requerida no puede aplicarse a través de un límite entre servidores que usan el protocolo ClickHouse. En ese caso, deshabilite la tabla con `query_log.enable_user_query_log = 0`.

**Disponibilidad**

`system.user_query_log` solo se adjunta cuando el ajuste del servidor `query_log.enable_user_query_log` está habilitado, que es el valor predeterminado. Cuando el ajuste es `0`, la tabla no existe y las consultas contra ella fallan con `UNKNOWN_TABLE`.

Cuando `query_log.enable_user_query_log` está habilitado pero el registro de consultas subyacente no está configurado o su tabla aún no se ha creado, `system.user_query_log` existe pero está vacía.

Las condiciones sobre la partición y las columnas clave del registro de consultas (`event_date`, `event_time`, `query_start_time`, `query_id`, `type` y columnas escalares similares) comparadas con constantes se hacen pushdown a la tabla de registro de consultas subyacente, por lo que las búsquedas habituales, como la del ejemplo siguiente, mantienen la poda de particiones y no examinan todo el registro conservado.

Si se creó una tabla llamada `system.user_query_log` antes de actualizar a una versión de ClickHouse que proporciona esta tabla, el servidor no se iniciará hasta que se cambie el nombre de la tabla existente o se elimine, o se establezca `query_log.enable_user_query_log` en `0`.

Un join se contabiliza sea cual sea su nivel de anidamiento: las subconsultas, las expresiones de tabla comunes, las vistas, las vistas de vistas y el SELECT de una vista materializada activada por un INSERT se registran en la fila de la consulta enviada, por lo que este valor puede ser distinto de cero en una consulta cuyo propio texto no contiene ningún JOIN. * `query_plan` (`JSON`) — El plan de consulta de la consulta que describe esta fila, serializado como JSON, con estadísticas de tiempo de ejecución por paso. Solo se rellena cuando el parámetro de configuración `log_query_plans` está habilitado, y está vacío en las filas `QueryStart`, ya que en ese momento todavía no existe ningún plan. En una fila correspondiente a una consulta que lanzó una excepción, el plan es el que la consulta había construido en el momento de lanzarla y no incluye estadísticas: si la consulta falló durante su ejecución, su plan se ejecutó solo en parte, y si falló antes de ejecutarse, el plan nunca llegó a ejecutarse. El plan se enmascara con `query_masking_rules`; una consulta en la que alguna regla encuentra una coincidencia, o que tiene argumentos secretos, no almacena ningún plan.
