## Descripción {#description}

Esta tabla contiene datos de perfilado a nivel de procesadores (que puede encontrar en [`EXPLAIN PIPELINE`](/es/reference/statements/explain#explain-pipeline)).

Es seguro truncar o eliminar esta tabla en cualquier momento.

## Columnas {#columns}

* `hostname` ([LowCardinality(String)](/es/reference/data-types/lowcardinality)) — Hostname del servidor que ejecuta la consulta.
* `clickhouse_version` ([LowCardinality(String)](/es/reference/data-types/lowcardinality)) — Versión del servidor ClickHouse que produjo la fila.
* `system_processor` ([LowCardinality(String)](/es/reference/data-types/lowcardinality)) — Arquitectura de CPU del servidor ClickHouse que produjo la fila.
* `event_date` ([Date](/es/reference/data-types/date)) — La fecha en la que ocurrió el evento.
* `event_time` ([DateTime](/es/reference/data-types/datetime)) — La fecha y hora en la que ocurrió el evento.
* `event_time_microseconds` ([DateTime64(6)](/es/reference/data-types/datetime64)) — La fecha y hora, con precisión de microsegundos, en la que ocurrió el evento.
* `id` ([UInt64](/es/reference/data-types/int-uint)) — ID del procesador, único dentro de la consulta. Es el número que aparece en `processor_uniq_id`.
* `parent_ids` ([Array(UInt64)](/es/reference/data-types/array)) — IDs de los procesadores padre.
* `plan_step` ([UInt64](/es/reference/data-types/int-uint)) — ID del paso del plan de consulta que creó este procesador, único dentro de la consulta. Es el número que aparece en `step_uniq_id` más uno. El valor es cero si el procesador no se añadió a partir de ningún paso.
* `plan_step_name` ([String](/es/reference/data-types/string)) — Nombre del paso del plan de consulta que creó este procesador. El valor está vacío si el procesador no se añadió a partir de ningún paso.
* `plan_step_description` ([String](/es/reference/data-types/string)) — Descripción del paso del plan de consulta que creó este procesador. El valor está vacío si el procesador no se añadió a partir de ningún paso.
* `plan_group` ([UInt64](/es/reference/data-types/int-uint)) — Grupo del procesador si fue creado por un paso del plan de consulta. Un grupo es una partición lógica de los procesadores añadidos desde el mismo paso del plan de consulta. El grupo se usa solo para mejorar la presentación del resultado de EXPLAIN PIPELINE.
* `initial_query_id` ([String](/es/reference/data-types/string)) — ID de la consulta inicial en la misma cadena de consultas.
* `query_id` ([String](/es/reference/data-types/string)) — ID de la consulta.
* `name` ([LowCardinality(String)](/es/reference/data-types/lowcardinality)) — Nombre del procesador.
* `elapsed_us` ([UInt64](/es/reference/data-types/int-uint)) — Número de microsegundos durante los que se ejecutó este procesador.
* `input_wait_elapsed_us` ([UInt64](/es/reference/data-types/int-uint)) — Número de microsegundos que este procesador estuvo esperando datos (de otro procesador).
* `output_wait_elapsed_us` ([UInt64](/es/reference/data-types/int-uint)) — Número de microsegundos que este procesador estuvo esperando porque el puerto de salida estaba lleno.
* `input_rows` ([UInt64](/es/reference/data-types/int-uint)) — Número de filas consumidas por el procesador.
* `input_bytes` ([UInt64](/es/reference/data-types/int-uint)) — Número de bytes consumidos por el procesador.
* `output_rows` ([UInt64](/es/reference/data-types/int-uint)) — Número de filas generadas por el procesador.
* `output_bytes` ([UInt64](/es/reference/data-types/int-uint)) — Número de bytes generados por el procesador.
* `processor_uniq_id` ([String](/es/reference/data-types/string)) — ID único del procesador en el pipeline.
* `step_uniq_id` ([String](/es/reference/data-types/string)) — ID único del paso en el plan.
* `exception_code` ([Int32](/es/reference/data-types/int-uint)) — Código de la excepción si la consulta falló; en caso contrario, 0.
* `exception` ([String](/es/reference/data-types/string)) — Mensaje de la excepción si la consulta falló; en caso contrario, vacío.

## Ejemplo {#example}

```sql title="Query"
EXPLAIN PIPELINE
SELECT sleep(1)
┌─explain─────────────────────────┐
│ (Expression)                    │
│ ExpressionTransform             │
│   (SettingQuotaAndLimits)       │
│     (ReadFromStorage)           │
│     SourceFromSingleChunk 0 → 1 │
└─────────────────────────────────┘

SELECT sleep(1)
SETTINGS log_processors_profiles = 1
Query id: feb5ed16-1c24-4227-aa54-78c02b3b27d4
┌─sleep(1)─┐
│        0 │
└──────────┘
1 rows in set. Elapsed: 1.018 sec.

SELECT
    name,
    elapsed_us,
    input_wait_elapsed_us,
    output_wait_elapsed_us
FROM system.processors_profile_log
WHERE query_id = 'feb5ed16-1c24-4227-aa54-78c02b3b27d4'
ORDER BY name ASC
```

```text title="Response"
┌─name────────────────────┬─elapsed_us─┬─input_wait_elapsed_us─┬─output_wait_elapsed_us─┐
│ ExpressionTransform     │    1000497 │                  2823 │                    197 │
│ LazyOutputFormat        │         36 │               1002188 │                      0 │
│ LimitsCheckingTransform │         10 │               1002994 │                    106 │
│ NullSource              │          5 │               1002074 │                      0 │
│ NullSource              │          1 │               1002084 │                      0 │
│ SourceFromSingleChunk   │         45 │                  4736 │                1000819 │
└─────────────────────────┴────────────┴───────────────────────┴────────────────────────┘
```

Aquí puedes ver:

* `ExpressionTransform` estaba ejecutando la función `sleep(1)`, por lo que su `work` tardará 1e6 y, por tanto, `elapsed_us` &gt; 1e6.
* `SourceFromSingleChunk` necesita esperar porque `ExpressionTransform` no acepta ningún dato durante la ejecución de `sleep(1)`, por lo que permanecerá en estado `PortFull` durante 1e6 us y, por tanto, `output_wait_elapsed_us` &gt; 1e6.
* `LimitsCheckingTransform`/`NullSource`/`LazyOutputFormat` necesitan esperar hasta que `ExpressionTransform` ejecute `sleep(1)` para procesar el resultado, por lo que `input_wait_elapsed_us` &gt; 1e6.

### Perfilado de una unión {#profiling-a-join}

Cuando una consulta lee de varias tablas, cada tabla tiene su propia canalización de lectura y las filas pasan por muchos procesadores antes de llegar al resultado.
Por eso, sumar `input_rows` u `output_rows` de todos los procesadores cuenta las mismas filas varias veces y no indica cuánto se leyó de cada tabla.
El siguiente ejemplo utiliza dos tablas `MergeTree` de distinto tamaño en un solo servidor.

```sql title="Query"
CREATE TABLE big (id UInt64, v UInt64) ENGINE = MergeTree ORDER BY id;
CREATE TABLE small (id UInt64, w UInt64) ENGINE = MergeTree ORDER BY id;

INSERT INTO big SELECT number, number FROM numbers(1000000);
INSERT INTO small SELECT number, number FROM numbers(1000);

EXPLAIN PIPELINE
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0;
```

`EXPLAIN PIPELINE` muestra una canalización de lectura para cada lado de la unión (`ReadFromMergeTree`, con fuentes `MergeTreeSelect` por debajo), conectadas entre sí por los procesadores de la unión. `join_algorithm = 'hash'` y `enable_join_runtime_filters = 0` hacen que este ejemplo sea reproducible: un filtro en tiempo de ejecución de JOIN no puede descartar `big` antes de que su fuente emita filas.

```sql title="Query"
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0, log_processors_profiles = 1;
-- Note the query ID printed by the client, or look it up in `system.query_log`.

SYSTEM FLUSH LOGS;

SELECT
    id,
    parent_ids,
    plan_step,
    name,
    plan_step_name,
    plan_step_description,
    input_rows,
    output_rows,
    elapsed_us
FROM system.processors_profile_log
WHERE query_id = '<query_id>'
ORDER BY plan_step, id;
```

Para interpretar el resultado:

* Fíjese en los procesadores de fuente, cuyo `name` es `MergeTreeSelect(...)` (o `MergeTreeSource`) y cuyo `plan_step_name` es `ReadFromMergeTree`. Su `output_rows` es el número de filas que produjo cada fuente. Súmelo por paso de lectura (`plan_step`), no para toda la consulta. El valor resultante es el número de filas que el paso de lectura transmitió al resto de la canalización.
* Cada lado de la unión tiene su propio paso `ReadFromMergeTree` con un `plan_step` distinto. En las filas de esta ejecución, `parent_ids` enumera los ID de los procesadores posteriores. Partiendo de una fuente, haga coincidir recursivamente cada valor de `parent_ids` con un `id` del mismo `query_id` para seguir la rama hasta la unión. Así se identifica, por ejemplo, la rama que alimenta `FillingRightJoinSide`.
* Los procesadores situados por encima de las fuentes (por ejemplo, `ExpressionTransform`, `FillingRightJoinSide`, `ConcatProcessor` o la propia transformación de la unión) consumen y producen filas derivadas de las fuentes. No sume sus contadores a los de las fuentes, ya que se contarían de nuevo las mismas filas.
* La información del paso no siempre basta para identificar una fuente. `EXPLAIN PIPELINE` es un plan independiente: ayuda a comparar nombres de procesadores y formas de las ramas, pero su salida en texto plano no incluye ni los valores `id` registrados ni `parent_ids`. Si ambas tablas tienen descripciones de pasos similares, utilice el grafo de la consulta ejecutada y los números de filas conocidos. En este ejemplo, las fuentes de lectura de `big` suman 1,000,000 filas y las de `small`, 1,000 filas.
* Los contadores de filas y bytes de los procesadores describen los datos que pasan por la canalización, no las lecturas físicas del almacenamiento. No incluyen los gránulos ni las marcas que se leyeron y luego se descartaron por filtrado; se ven afectados por la clave primaria y otros filtrados por índices, `PREWHERE` y la poda de columnas, y no reflejan los bytes comprimidos leídos del disco. `SelectedRows`, `SelectedBytes` y `SelectedMarks` en `system.query_log` son estadísticas lógicas de selección: pueden ser distintas de cero aunque todos los datos provengan de la caché. Para analizar las lecturas de archivos, utilice `ReadBufferFromFileDescriptorReadBytes`, que incluye las lecturas atendidas por la caché de páginas del sistema operativo. Para analizar las lecturas del disco local o de dispositivos de bloques sin contar la caché de páginas del sistema operativo, utilice `OSReadBytes`.
