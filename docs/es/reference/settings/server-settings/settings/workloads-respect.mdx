Estos ajustes configuran el servidor de ClickHouse y se generan automáticamente a partir del código fuente de ClickHouse.

## workloads_respect_server_cpu_limit {#workloads_respect_server_cpu_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />

Cuando está habilitado, el límite de concurrencia de CPU de todo el servidor se aplica a través del planificador de workload. Si no se ha definido ningún recurso para ninguno de los dos roles, se crea implícitamente un recurso de CPU `__server_cpu__` (para `MASTER THREAD` y `WORKER THREAD`), y el valor `max_concurrent_threads` del workload raíz (el workload con nombre vacío) se deriva de `concurrent_threads_soft_limit_num` y `concurrent_threads_soft_limit_ratio_to_cores`, de modo que todos los workloads comparten un único presupuesto de cupos de CPU obtenido de esos ajustes. A partir de ese momento, la planificación de CPU se realiza mediante el planificador de workload en lugar del control de concurrencia integrado.

Active `implicit_default_workload` junto con este parámetro de configuración (o defina un workload `default`). Este presupuesto solo limita las consultas clasificadas en un workload. Sin un workload `default`, ni las consultas que utilicen el valor predeterminado del parámetro de configuración `workload` ni las fusiones y mutaciones en segundo plano que usan el workload predeterminado tienen límite alguno de CPU: tampoco se les aplica ya el control de concurrencia integrado (`concurrent_threads_soft_limit_num`). Con `throw_on_unknown_workload = 1`, dichas consultas fallan.

Se puede modificar en tiempo de ejecución. Deshabilitado de forma predeterminada.

**Ejemplo**

```xml
<workloads_respect_server_cpu_limit>true</workloads_respect_server_cpu_limit>
```

## workloads_respect_server_memory_limit {#workloads_respect_server_memory_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />

Cuando está habilitado, el límite de memoria global del servidor se aplica a través del planificador de workload como un presupuesto de reserva de memoria. Si no hay ninguno definido, se crea implícitamente un recurso `MEMORY RESERVATION` `__server_memory__`, y el `max_memory` del workload raíz (el workload con nombre vacío) se deriva de `max_server_memory_usage` (y de su proporción de RAM), de modo que todos los workloads comparten un único presupuesto de reserva de memoria obtenido de ese parámetro de configuración. Se trata de un presupuesto de admisión de reservas y no reemplaza el límite de memoria global del proceso, que sigue aplicándose. El presupuesto se obtiene del valor configurado de `max_server_memory_usage` cuando la configuración se carga o se recarga; no refleja los ajustes en tiempo de ejecución que `memory_worker_dynamic_hard_limit` realiza sobre el límite global del proceso, por lo que entre recargas puede ser mayor que el límite vigente.

Active `implicit_default_workload` junto con este parámetro de configuración (o defina un workload `default`). Solo las consultas clasificadas en un workload reservan memoria de este presupuesto: sin un workload `default`, una consulta que utilice el valor predeterminado del parámetro de configuración `workload` no reserva memoria de él y, con `throw_on_unknown_workload = 1`, dicha consulta falla. Las fusiones y mutaciones en segundo plano nunca reservan memoria de los workloads, por lo que su memoria no forma parte de este presupuesto en ningún caso.

Modificable en tiempo de ejecución. Deshabilitado de forma predeterminada.

**Ejemplo**

```xml
<workloads_respect_server_memory_limit>true</workloads_respect_server_memory_limit>
```
