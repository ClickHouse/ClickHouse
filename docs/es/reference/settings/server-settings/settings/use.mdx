Estos ajustes configuran el servidor de ClickHouse y se generan automáticamente a partir del código fuente de ClickHouse.

## use_minimalistic_part_header_in_zookeeper {#use_minimalistic_part_header_in_zookeeper}

Configuración obsoleta; no tiene ningún efecto. Las tablas [replicadas](/es/reference/engines/table-engines/mergetree-family/replication) siempre almacenan el encabezado de una parte de datos de forma compacta en un único `znode`. Se siguen pudiendo leer los encabezados de partes escritos por versiones anteriores con `znodes` hijos independientes para `columns` y `checksums`.

## use_separate_cache_arena {#use_separate_cache_arena}

<SettingsInfoBlock type="Bool" default_value="1" changeable_without_restart="No" />

Habilita una arena dedicada de jemalloc para las asignaciones de caché (caché de marcas, caché sin comprimir, caché de páginas).
Aísla los datos de la caché de las asignaciones para el procesamiento de consultas, lo que reduce la fragmentación de memoria.

## use_shared_merge_tree_log_pipeline {#use_shared_merge_tree_log_pipeline}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="No" />

Solo disponible en ClickHouse Cloud. Cuando está habilitado, los registros del sistema se escriben a través de una canalización `SharedMergeTree`
y la base de datos `system` se convierte en una Base de datos Shared, de modo que todas las réplicas ven las mismas tablas de registros.

Cada vaciado de un log escribe un archivo `Native` mediante la función de tabla `s3` (o `azureBlobStorage`) en la carpeta de la
generación del log, es decir, el hash de sus columnas y claves. Para cada generación, la canalización mantiene la cola `system._<log>_s3queue_<hash>`
que lee esa carpeta, la vista materializada `system._<log>_mv_<hash>` y la tabla `SharedMergeTree` `system.<log>_<hash>`.
`system.<log>` es una tabla `Merge` sobre todas las generaciones. Un esquema nuevo crea una generación nueva; los ajustes, el TTL y los índices
se toman de las claves `smt_settings`, `smt_ttl` y `smt_indices` de la configuración del log y se modifican in situ.
Los objetos se crean en el primer vaciado de un log, o durante el inicio con `prepare_system_log_tables_on_startup`.
La clave de ordenación de una tabla es la clave del log precedida por `hostname`, de modo que las filas de una réplica se leen por clave.
Las claves `smt_order_by` y `smt_partition_by` de la configuración del log reemplazan las claves de la tabla.

Mientras el parámetro de configuración está habilitado, la base de datos local `system` se renombra a `system_local`. Requiere `shared_database_catalog`
y `<shared_log_pipeline><endpoint>` en la configuración del servidor.
Véase también: `shared_log_pipeline.enable_sync_flush`, `shared_log_pipeline.flush_timeout_seconds`.
