## use_columns_cache {#use_columns_cache}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "0"},{"label": "Nueva configuración experimental para habilitar la caché de columnas en tablas MergeTree, deshabilitada de forma predeterminada."}]}]} />

Indica si se debe usar la caché de columnas. Acepta 0 o 1. De forma predeterminada, 0 (deshabilitada).
La caché de columnas almacena columnas deserializadas de tablas `MergeTree`, lo que evita tener que descomprimir y deserializar repetidamente los datos de acceso frecuente. Esto puede reducir significativamente la latencia de las consultas que se repiten sobre los mismos datos. La clave de la caché se compone del UUID de la tabla, el nombre de la parte de datos, el nombre de la columna y un segmento (stripe) de gránulos consecutivos de aproximadamente 65536 filas.

Dado que la clave de las entradas incluye el UUID de la tabla, la caché solo está activa para tablas de bases de datos que asignan UUID, como `Atomic`, `Replicated` y `Shared` (el motor de base de datos predeterminado en ClickHouse Cloud); las tablas `MergeTree` de las bases de datos `Ordinary` heredadas tienen un UUID nulo e ignoran esta configuración de forma silenciosa.

La caché se aplica tanto a las partes anchas (wide) como a las partes compactas, incluidas las partes de las proyecciones.

Cada entrada contiene un rango contiguo de gránulos de un mismo segmento: un gránulo solo entra en la caché una vez que se ha leído de la primera a la última fila, las lecturas se sirven desde la caché gránulo a gránulo y los rangos escritos por distintas lecturas se fusionan, de modo que las lecturas que dividen una parte en distintos rangos de marcas comparten las mismas entradas.

La caché también se aplica a los archivos `Parquet` leídos desde el sistema de archivos local (la función de tabla `file` y el motor de tabla `File`), desde sistemas de almacenamiento de objetos (`s3`, `azureBlobStorage` y sus motores de tabla) y por tablas de lago de datos. En este caso, cada entrada contiene un fragmento de 65536 filas de una columna de un grupo de filas (el último fragmento de un grupo de filas puede ser más corto), y su clave se compone de la ruta del archivo, su versión (el ETag de un objeto, o la hora de modificación, el inode y el tamaño de un archivo local), la columna del archivo y el tipo con el que se lee. Un grupo de filas que usa la caché se lee en estos fragmentos, independientemente de los ajustes de tamaño de bloque. Un fragmento se escribe en la caché a medida que se decodifica, sin realizar ninguna copia, si todas sus filas se leyeron antes de aplicarles cualquier filtro: con `PREWHERE`, esto ocurre con las columnas del filtro, mientras que las demás columnas solo se leen para las filas que lo cumplen. Una columna de un grupo de filas se sirve desde la caché cuando todos sus fragmentos están en ella, por lo que, si no se pueden escribir todos los fragmentos de una columna, los que ya se escribieron se retiran de la caché. Un archivo local solo se almacena en caché cuando lleva unos segundos sin modificarse, de modo que su versión identifique su contenido.

## use_concurrency_control_for_max_threads {#use_concurrency_control_for_max_threads}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "1"},{"label": "Nueva configuración para determinar el paralelismo de una consulta a partir de la cuota equitativa de slots de CPU del control de concurrencia"}]}]} />

Determina el paralelismo de una consulta (el número de flujos y threads con los que se planifica) a partir de la cuota equitativa de slots de CPU del control de concurrencia del Servidor, en lugar del número de núcleos de CPU. La cuota equitativa es el límite de slots (consulte los ajustes globales del Servidor `concurrent_threads_soft_limit_num` y `concurrent_threads_soft_limit_ratio_to_cores`) repartido a partes iguales entre las canalizaciones que se están ejecutando y la nueva consulta.

De este modo, cuando se ejecutan muchas consultas de forma concurrente, cada una se planifica con menos flujos: usa menos memoria y dedica menos CPU a la fusión de los resultados parciales de sus threads (p. ej., estados de agregación), lo que aumenta el caudal total. Una consulta que se planifica mientras el Servidor está inactivo sigue usando todos los núcleos de CPU, como hasta ahora.

La cuota equitativa se calcula una sola vez por consulta, al construir su plan, de modo que todas las partes de la consulta (subconsultas, conjuntos, tablas de la unión) se planifiquen con el mismo número de flujos.

Solo se aplica si `max_threads` es `auto` (es decir, no se ha establecido explícitamente) y `use_concurrency_control` está habilitado.

## use_constant_folding_in_index_analysis {#use_constant_folding_in_index_analysis}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.7"},{"label": "0"},{"label": "Nueva configuración para incorporar constantes a nivel de partición en el predicado de filtro para cada parte durante el análisis de índices de MergeTree, lo que mejora la poda en filtros cuyas ramas dependen de valores de partición."}]}]} />

Sustituye constantes a nivel de partición en el predicado de filtro al analizar, para cada parte, la clave primaria y los skip indexes.

Cuando la clave de partición aparece en el filtro junto con columnas de la clave primaria o de skip indexes, esto permite que el análisis de índices incorpore el valor de la partición por separado dentro de cada parte. Resulta especialmente útil para filtros disyuntivos cuyas ramas se dirigen a distintas particiones. Por ejemplo, con `PARTITION BY a` y `ORDER BY b`:

```sql
SELECT * FROM t WHERE (a = 1 AND b >= 1) OR (a = 2 AND b > 10) OR (a = 3 AND b > 10)
```

Para la parte de la partición `a = 1`, la condición se simplifica a `b >= 1`, mientras que para las particiones `a = 2` y `a = 3` se simplifica a `b > 10`, por lo que cada parte se analiza con el predicado que realmente se le aplica.

Valores posibles:

* 0 — Deshabilitado.
* 1 — Habilitado.

## use_datalake_metadata_statistics {#use_datalake_metadata_statistics}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Nueva configuración para estimar, a partir de la metadata de la tabla, las filas y las estadísticas de columna de las lecturas de lagos de datos (por ahora, solo Iceberg) para el reordenamiento de JOIN."}]}]} />

## use_uncompressed_cache {#use_uncompressed_cache}

<SettingsInfoBlock type="Bool" default_value="0" />

Indica si se debe usar una caché de bloques sin comprimir. Acepta 0 o 1. De forma predeterminada, 0 (deshabilitado).
Usar la caché sin comprimir (solo para tablas de la familia MergeTree) puede reducir significativamente la latencia y aumentar el rendimiento al trabajar con una gran cantidad de consultas cortas. Habilite esta configuración para los usuarios que envían solicitudes cortas con frecuencia. Preste atención también al parámetro de configuración [uncompressed&#95;cache&#95;size](/es/reference/settings/server-settings/settings/uncompressed-cache#uncompressed_cache_size) (solo se establece en el archivo de configuración), que define el tamaño de los bloques de la caché sin comprimir. De forma predeterminada, es de 8 GiB. La caché sin comprimir se rellena según sea necesario y los datos menos utilizados se eliminan automáticamente.

En las consultas que leen un volumen de datos relativamente grande (un millón de filas o más), la caché sin comprimir se deshabilita automáticamente para ahorrar espacio para las consultas realmente pequeñas. Esto significa que puede mantener la configuración `use_uncompressed_cache` siempre establecida en 1.
