## iceberg_insert_commit_retry_initial_backoff_ms {#iceberg_insert_commit_retry_initial_backoff_ms}

<SettingsInfoBlock type="UInt64" default_value="10" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "10"},{"label": "Nuevo ajuste. Cuando el commit de un `INSERT` en Iceberg pierde frente a un commit concurrente, se reintenta tras un retraso exponencial aleatorio en lugar de hacerlo de inmediato."}]}]} />

Cota superior del retraso antes del primer reintento de un `INSERT` en una tabla Iceberg cuyo commit ha perdido frente a un commit concurrente.
El límite se duplica con cada reintento sucesivo, hasta `iceberg_insert_commit_retry_max_backoff_ms`, y cada retraso se elige al azar
entre cero y el límite, de modo que los escritores que perdieron la misma condición de carrera no vuelvan a intentarlo en el mismo instante y colisionen de nuevo.
El retraso se aplica antes de consultar la metadata más reciente, por lo que, con muchos escritores concurrentes, también limita la frecuencia con la que se lista el directorio
de metadata. Con `0`, se reintenta sin retraso.

## iceberg_insert_max_bytes_in_data_file {#iceberg_insert_max_bytes_in_data_file}

Número máximo de bytes del archivo de datos Parquet de Iceberg en una operación de inserción.

El valor predeterminado refleja el valor predeterminado documentado de la propiedad de tabla Iceberg `write.target-file-size-bytes` (512 MiB);
consulte https://iceberg.apache.org/docs/1.5.2/configuration/. El límite se compara con el tamaño del archivo
escrito hasta ese momento, es decir, el tamaño comprimido, por lo que un archivo puede superarlo en la cantidad de datos que el escritor aún mantiene en búfer, como
los grupos de filas de Parquet incompletos y los que se están codificando. `iceberg_insert_max_rows_in_data_file` limita el archivo
con independencia de su tamaño.

## iceberg_insert_max_data_files_in_upload {#iceberg_insert_max_data_files_in_upload}

<SettingsInfoBlock type="UInt64" default_value="8" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "8"},{"label": "Nuevo ajuste. Una inserción en Iceberg sobre S3 o Azure ya no espera a que finalice la carga de cada archivo de datos terminado."}]}]} />

Número máximo de archivos de datos terminados de un mismo stream de inserción cuya carga no se espera mientras el `INSERT` escribe el siguiente
archivo, en sistemas de almacenamiento de objetos que realizan la carga en segundo plano (S3, Azure). Cada uno de estos archivos mantiene sus búferes de carga hasta que esta
finaliza, por lo que los valores más altos ocultan más latencia de carga a costa de consumir más memoria. Con `0`, se espera a que finalice la carga de cada archivo de datos antes de
escribir el siguiente.

## iceberg_insert_single_manifest_for_all_partitions {#iceberg_insert_single_manifest_for_all_partitions}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Nuevo ajuste."}]}]} />

Un `INSERT` en una tabla Iceberg particionada escribe un único archivo de manifiesto para todas las particiones que modifica, al igual que Spark
y PyIceberg, en lugar de un archivo de manifiesto por partición. Esto se aplica a cada stream de inserción: cada stream hace commit de su propia
instantánea con su propio manifiesto, por lo que un `INSERT` solo escribe exactamente un manifiesto con `max_insert_threads = 1`.
Además, `OPTIMIZE TABLE ... MANIFEST` fusiona en uno solo los manifiestos de distintas particiones.
`ALTER TABLE ... DROP PARTITION` no puede eliminar una partición cuyo manifiesto se comparte con otras particiones.
