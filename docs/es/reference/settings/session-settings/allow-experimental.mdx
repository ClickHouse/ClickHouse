## allow_experimental_analyzer {#allow_experimental_analyzer}

**Aliases**: `enable_analyzer`

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "1"},{"label": "El ajuste es obsoleto: el analizador es obligatorio y el antiguo análisis de consultas ya no es compatible. Obsoleto desde v26.9: el analizador ya no se puede desactivar.

El analizador es la infraestructura de análisis y planificación de consultas que se utiliza de forma predeterminada desde v24.3. En v26.9 este ajuste quedó fijado en su único valor admitido, `1`, y el ajuste `compatibility` ya no lo revierte. En v26.10 se eliminó el análisis de consultas al que solía cambiar. Por compatibilidad con versiones anteriores, se acepta el valor `0`, que se sustituye por `1`, de modo que las consultas, los ajustes de sesión, los perfiles de configuración y las configuraciones de client que todavía establecen `enable_analyzer = 0` siguen funcionando, con el analizador. Para comparar el comportamiento o el rendimiento de una consulta con el antiguo análisis de consultas, utilice una versión de ClickHouse anterior a v26.9.

## allow_experimental_logsql_dialect {#allow_experimental_logsql_dialect}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "0"},{"label": "Nueva configuración para habilitar el dialecto LogsQL (el lenguaje de consulta de logs de VictoriaLogs)."}]}]} />

Habilita LogsQL, el lenguaje de consulta de logs de VictoriaLogs. Las consultas escritas en este dialecto se traducen a consultas SELECT sobre la tabla especificada en la configuración `logsql_table`.

Uso:

```sql
SET allow_experimental_logsql_dialect = 1;
SET logsql_table = 'logs';
SET dialect = 'logsql';

_time:1h error | stats by (host) count()
```

Una consulta `SET` completa e independiente se sigue analizando como SQL sin procesar para que se pueda
volver a cambiar de dialecto; una consulta LogsQL que simplemente empieza con la palabra `set` conserva su significado.
Los ajustes `logsql_time_column` y `logsql_message_column` definen las columnas
a las que hacen referencia el campo `_time` y el campo predeterminado (mensaje).

A diferencia de VictoriaLogs, que almacena todos los campos como cadenas, las consultas traducidas se ejecutan
sobre el esquema de tabla existente. Las principales desviaciones del contrato que se derivan de ello son:

* Los filtros de texto (palabras, frases, prefijos, expresiones regulares) requieren columnas de tipo `String` y no convierten las columnas numéricas a texto.
* Los filtros de comparación numérica comparan las columnas numéricas de forma nativa (de forma exacta para valores enteros y decimales, siempre que el literal comparado quepa en `Int128` o `Decimal256(38)`; un valor de mayor rango, p. ej., un entero mayor que 1e38 en un campo `UInt256`, se compara con precisión `Float64`, al igual que los pasos enteros de los buckets de `stats by (<field>:<step>)`). En las columnas `String`, solo se analiza fila por fila el texto numérico simple; los valores expresados en la gramática numérica de LogsQL (p. ej., `10KiB`, `1h30m`) no se analizan fila por fila.
* Las funciones estadísticas numéricas (`sum`, `avg`, `median`, `quantile`, `stddev`, `rate_sum`) analizan el valor numérico de cada campo y omiten los valores que no son números, igual que VictoriaLogs. Los valores son de tipo `Float64`, por lo que una columna numérica se agrega con precisión `Float64` y no de forma exacta.
* El pipe `math` requiere que las columnas de los operandos sean numéricas; las columnas `String` no se convierten implícitamente.
* Los resultados de las consultas se devuelven con los tipos de las columnas subyacentes, no como cadenas.
