## prefer_column_name_to_alias {#prefer_column_name_to_alias}

<SettingsInfoBlock type="Bool" default_value="0" />

Habilita o deshabilita el uso de los nombres de columna originales en lugar de alias en las expresiones y cláusulas de la consulta. Esto es especialmente importante cuando el alias es el mismo que el nombre de la columna; consulta [Alias de expresiones](/es/reference/syntax#notes-on-usage). Active este SETTING para que las reglas de sintaxis de los alias en ClickHouse sean más compatibles con la mayoría de los demás motores de base de datos.

Valores posibles:

* 0 — El nombre de la columna se sustituye por el alias.
* 1 — El nombre de la columna no se sustituye por el alias.

Si el nombre de la columna es ambiguo entre las tablas unidas mediante join y existe un alias con el mismo nombre, se utiliza el alias:

```sql
SET prefer_column_name_to_alias = 1;
SELECT t1.id + 10 AS id, id AS x
FROM (SELECT 1 AS id) AS t1, (SELECT 1 AS k) AS t2, (SELECT 2 AS id) AS t3;
```

```text
┌─id─┬──x─┐
│ 11 │ 11 │
└────┴────┘
```

Aquí `id` en `id AS x` es una columna tanto de `t1` como de `t3`, por lo que se resuelve al alias `t1.id + 10`.

**Ejemplo**

Diferencia con la configuración activada y desactivada:

Consulta:

```sql
SET prefer_column_name_to_alias = 0;
SELECT avg(number) AS number, max(number) FROM numbers(10);
```

Resultado:

```text
Received exception from server (version 21.5.1):
Code: 184. DB::Exception: Received from localhost:9000. DB::Exception: Aggregate function avg(number) is found inside another aggregate function in query: While processing avg(number) AS number.
```

Consulta:

```sql
SET prefer_column_name_to_alias = 1;
SELECT avg(number) AS number, max(number) FROM numbers(10);
```

Resultado:

```text
┌─number─┬─max(number)─┐
│    4.5 │           9 │
└────────┴─────────────┘
```

## prefer_global_in_and_join {#prefer_global_in_and_join}

<SettingsInfoBlock type="Bool" default_value="0" />

Habilita el reemplazo de los operadores `IN`/`JOIN` por `GLOBAL IN`/`GLOBAL JOIN`.

Valores posibles:

* 0 — Deshabilitado. Los operadores `IN`/`JOIN` no se reemplazan por `GLOBAL IN`/`GLOBAL JOIN`.
* 1 — Habilitado. Los operadores `IN`/`JOIN` se reemplazan por `GLOBAL IN`/`GLOBAL JOIN`.

**Uso**

Aunque `SET distributed_product_mode=global` puede cambiar el comportamiento de las consultas para las tablas distribuidas, no es adecuado para las tablas locales ni para las tablas procedentes de recursos externos. Aquí es donde entra en juego el SETTING `prefer_global_in_and_join`.

Por ejemplo, podemos tener nodos que atienden consultas y contienen tablas locales, que no se prestan a la distribución. Necesitamos distribuir sus datos sobre la marcha durante el procesamiento distribuido con la palabra clave `GLOBAL`: `GLOBAL IN`/`GLOBAL JOIN`.

Otro caso de uso de `prefer_global_in_and_join` es acceder a tablas creadas por motores externos. Este SETTING ayuda a reducir el número de llamadas a fuentes externas al hacer join con esas tablas: solo una llamada por consulta.

**Véase también:**

* [Subconsultas distribuidas](/es/reference/statements/in#distributed-subqueries) para obtener más información sobre cómo usar `GLOBAL IN`/`GLOBAL JOIN`

## prefer_localhost_replica {#prefer_localhost_replica}

<SettingsInfoBlock type="Bool" default_value="1" />

Habilita o deshabilita el uso preferente de la réplica localhost al procesar consultas distribuidas.

Valores posibles:

* 1 — ClickHouse siempre envía una consulta a la réplica localhost si existe.
* 0 — ClickHouse usa la estrategia de balanceo especificada por el SETTING [load&#95;balancing](/es/reference/settings/session-settings/load-balancing#load_balancing).

<Note>
  Desactive este SETTING si usa [max&#95;parallel&#95;replicas](/es/reference/settings/session-settings/max#max_parallel_replicas) sin [parallel&#95;replicas&#95;custom&#95;key](/es/reference/settings/session-settings/parallel-replicas#parallel_replicas_custom_key).
  Si [parallel&#95;replicas&#95;custom&#95;key](/es/reference/settings/session-settings/parallel-replicas#parallel_replicas_custom_key) está configurado, desactive este SETTING solo si se usa en un clúster con varios segmentos que contienen varias réplicas.
  Si se usa en un clúster con un solo segmento y varias réplicas, desactivar este SETTING tendrá efectos negativos.
</Note>

## prefer_optimize_projection {#prefer_optimize_projection}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "0"},{"label": "Nueva SETTING: elige una projection utilizable sin importar su costo estimado, al igual que `force_optimize_projection`, pero sin que la consulta falle cuando no se usa ninguna projection."}]}]} />

Hace que la optimización por projections prefiera las [projections](/es/reference/engines/table-engines/mergetree-family/mergetree#projections) frente a la tabla en las consultas `SELECT`, cuando dicha optimización está habilitada (consulte la SETTING [optimize&#95;use&#95;projections](/es/reference/settings/session-settings/optimize-use#optimize_use_projections)).

Cuando está habilitada, se utiliza una projection capaz de resolver la consulta aunque requiera leer más marks que la propia tabla, igual que con [force&#95;optimize&#95;projection](/es/reference/settings/session-settings/force-optimize#force_optimize_projection), pero la consulta no falla cuando no puede usarse ninguna projection.

Valores posibles:

* 0 — Las projections se eligen según su costo estimado.
* 1 — Se elige una projection utilizable sin importar su costo estimado.

## prefer_warmed_unmerged_parts_seconds {#prefer_warmed_unmerged_parts_seconds}

<CloudOnlyBadge />

<SettingsInfoBlock type="Int64" default_value="0" />

Solo tiene efecto en ClickHouse Cloud. Si una parte fusionada tiene menos de esta cantidad de segundos de antigüedad y no está precalentada (ver [cache&#95;populated&#95;by&#95;fetch](/es/reference/settings/merge-tree-settings/cache-populated-by-fetch#cache_populated_by_fetch)), pero todas sus partes de origen están disponibles y precalentadas, las consultas SELECT leerán de esas partes en su lugar. Ten en cuenta que esto solo comprueba si CacheWarmer procesó la parte; si la parte se cargó en la caché por otro mecanismo, se seguirá considerando fría hasta que CacheWarmer la procese; si se precalentó y luego fue expulsada de la caché, se seguirá considerando caliente.
