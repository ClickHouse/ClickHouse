## enable_join_runtime_filters_index_analysis {#enable_join_runtime_filters_index_analysis}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "Los filtros en tiempo de ejecución de JOIN pasaron a ser una funcionalidad del nivel Production."}]}, {"id": "row-2","items": [{"label": "26.7"},{"label": "0"},{"label": "Nueva configuración para habilitar el filtrado de JOIN mediante el análisis dinámico de índices"}]}, {"id": "row-3","items": [{"label": "26.10"},{"label": "1"},{"label": "Permite descartar gránulos del lado de sondeo (izquierdo) de un JOIN mediante el filtro en tiempo de ejecución generado a partir del lado de construcción (derecho)."}]}]} />

Descarta gránulos del lado de sondeo de un JOIN mediante el filtro en tiempo de ejecución generado a partir del lado de construcción; consulta `enable_join_runtime_filters`.
Solo tiene efecto si `use_skip_indexes_on_data_read = 1`.
Solo se pueden descartar gránulos si la join key es una columna de la clave primaria del lado de sondeo o está cubierta por un índice de omisión `minmax`, `set` o `bloom_filter`.
Si el filtro en tiempo de ejecución conserva los valores exactos de la clave, el predicado utilizado para descartar gránulos es un conjunto `IN` de esos valores; de lo contrario, se utiliza el rango entre el valor mínimo y el máximo de la clave (lo que permite descartar menos gránulos).

Solo tiene efecto cuando el lado de sondeo del JOIN se lee localmente. Los descriptores que determinan qué gránulos se descartan se asocian al paso de lectura durante la optimización del plan de consulta, pero no se transfieren cuando ese paso se reconstruye para ejecutarlo de forma remota. Por tanto, no se descartan gránulos con réplicas paralelas (`enable_parallel_replicas = 1`) ni con un plan de consulta distribuido (`make_distributed_plan = 1`). En esos modos, la configuración no tiene efecto: la consulta devuelve el mismo resultado y el filtro en tiempo de ejecución de JOIN se comporta exactamente igual que si esta configuración estuviera deshabilitada; únicamente se pierde la posibilidad de descartar gránulos.

Tampoco se descartan gránulos cuando el lado de sondeo se lee con `FINAL` (esta operación no está implementada para las lecturas con `FINAL`, y `optimizeLazyFinal` reconstruye la lectura sin los descriptores), ni en tablas con datos pendientes, mutaciones `ALTER` o partes de parche. En estos casos, la configuración tampoco tiene efecto.

## enable_join_transitive_predicates {#enable_join_transitive_predicates}

<BetaBadge />

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.6"},{"label": "1"},{"label": "Activa enable_join_transitive_predicates de forma predeterminada"}]}, {"id": "row-2","items": [{"label": "26.4"},{"label": "0"},{"label": "Nueva configuración para inferir predicados transitivos de igualdad en JOIN para la optimización del orden de join."}]}]} />

Infiere predicados transitivos de igualdad en JOIN a partir de las condiciones de join existentes.
Por ejemplo, dados `A.x = B.x` y `B.x = C.x`, se añade un predicado sintético `A.x = C.x`
para que el optimizador del orden de join pueda considerar planes directos de (A JOIN C).
