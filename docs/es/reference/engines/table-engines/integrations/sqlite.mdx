El motor permite importar y exportar datos a SQLite y admite consultas directas a tablas de SQLite desde ClickHouse.

## Crear una tabla {#creating-a-table}

```sql
    CREATE TABLE [IF NOT EXISTS] [db.]table_name
    (
        name1 [type1],
        name2 [type2], ...
    ) ENGINE = SQLite('db_path', 'table')
```

**Parámetros del motor**

* `db_path` — Ruta del archivo SQLite que contiene una base de datos.
* `table` — Nombre de una tabla en la base de datos SQLite, o una consulta que se pasa a SQLite tal cual (consulte [Pasar una consulta en lugar de un nombre de tabla](#passing-a-query)).

## Pasar una consulta en lugar de un nombre de tabla {#passing-a-query}

En lugar de un nombre de tabla, el argumento `table` puede ser una consulta `SELECT` que se pasa a SQLite tal cual. La estructura de la tabla se infiere a partir del resultado de la consulta. SQLite solo informa de un tipo declarado para una columna del resultado que sea directamente una columna de una tabla; para una expresión, un literal o una agregación no informa de nada. Un tipo declarado que se corresponde con `String` (consulte la [correspondencia de tipos](/es/reference/engines/database-engines/sqlite#data_types-support)) se utiliza tal cual. Cualquier otra columna (ya sea una con un tipo declarado numérico o una sin tipo declarado) se resuelve según la clase de almacenamiento de su valor en la primera fila del resultado de la consulta: un valor `INTEGER` da `Int64`, un valor `REAL` da `Float64` y cualquier otro valor (`TEXT`, `BLOB`, `NULL`), así como un resultado vacío, da `String`. Un tipo declarado numérico solo se conserva si la clase de almacenamiento de esa fila concuerda con él, porque SQLite informa asimismo de un tipo declarado para un `SELECT` compuesto, tomado de una de sus ramas, mientras que las filas proceden de todas ellas; en caso contrario, a la columna se le asigna el tipo según la clase de almacenamiento, igual que a una columna sin tipo declarado. Por tanto, el tipo inferido solo puede ampliarse, nunca reducirse. Inferir una columna de este tipo inicia la ejecución de la consulta en SQLite. La primera fila no es representativa del resto: SQLite puede devolver una clase de almacenamiento distinta en cada fila (por ejemplo, `CASE WHEN id = 1 THEN 1 ELSE 1.5 END`), por lo que una lectura basada en una consulta es de tipo fail-closed para todas las columnas leídas mediante un tipo numérico, y no solo para las que carecen de tipo declarado. Si un valor tiene una clase de almacenamiento que no coincide con ese tipo, o no puede representarse exactamente en él (una celda `INTEGER` con `300` en una columna `UInt8`, una celda `REAL` con `16777217` en una columna `Float32`), la lectura falla en lugar de convertirlo de forma silenciosa. Para leer una columna con valores de clases de almacenamiento mixtas, declárela como `String` o conviértala a texto en la consulta de SQLite. Todas las columnas inferidas son `Nullable`. La consulta puede escribirse como una subconsulta o envolverse en la función `query`:

```sql
CREATE TABLE sqlite_table ENGINE = SQLite('sqlite.db', (SELECT col1, col2 FROM table1 WHERE col2 > 1));
CREATE TABLE sqlite_table ENGINE = SQLite('sqlite.db', query('SELECT col1, col2 FROM table1 WHERE col2 > 1'));
```

Una tabla de este tipo es de solo lectura: no se permite ejecutar `INSERT` en ella. La función de tabla [`sqlite`](/es/reference/functions/table-functions/sqlite) también es compatible con esta misma sintaxis.

<Note>
  La forma de subconsulta `(SELECT ...)` es analizada por ClickHouse y se vuelve a serializar antes de enviarse a SQLite. Por lo tanto, debe ser ClickHouse SQL válido. Para pasar sintaxis específica de SQLite que ClickHouse no analiza, use la forma `query('...')`, cuyo texto se envía literalmente a SQLite.

  Cualquier `WHERE`, `LIMIT`, agregación, etc. externo de la consulta de ClickHouse circundante **no** se hace pushdown en la consulta pasada; se aplica en ClickHouse después de recuperar el resultado completo de la consulta. Para restringir los datos leídos desde SQLite, coloque el filtro dentro de la consulta pasada. Con [`external_table_strict_query = 1`](/es/reference/settings/session-settings/external-table#external_table_strict_query), un filtro externo sobre las columnas de la tabla se rechaza con una excepción en lugar de aplicarse localmente, porque no se puede hacer pushdown de él a la consulta pasada. La comprobación abarca el predicado `WHERE` de nivel superior y cada conjunción de un `AND` de nivel superior. Un `PREWHERE` sobre las columnas de esta tabla no es un caso de esta configuración: este motor de tabla no admite `PREWHERE`, y dicha consulta se rechaza con `ILLEGAL_PREWHERE` independientemente de la configuración. La comprobación se ejecuta únicamente allí donde realmente se podría hacer pushdown de un filtro: cuando esta tabla es la única tabla de la consulta, en cualquiera de los lados de un `INNER JOIN`, o en el lado preservado de un outer join (el lado izquierdo de un `LEFT JOIN`, el lado derecho de un `RIGHT JOIN`). En el lado no preservado de un `LEFT`/`RIGHT JOIN` y en cualquiera de los lados de un `FULL JOIN` no se hace pushdown de nada ni se comprueba nada, por lo que un filtro sobre las columnas de esta tabla se aplica localmente después del join incluso en modo estricto. Allí donde la comprobación se ejecuta, un predicado que hace referencia a otras tablas unidas en la consulta circundante no se hace pushdown y queda excluido de la comprobación, tanto si hace referencia solo al lado unido como si lo mezcla con esta tabla dentro de una única expresión que no sea `AND` (por ejemplo, un `OR`); dicho predicado mantiene su punto de evaluación habitual en ClickHouse (`WHERE` después del join, `PREWHERE` antes de él) y no se rechaza.
</Note>

## Compatibilidad con tipos de datos {#data-types-support}

Cuando se especifican explícitamente los tipos de columna de ClickHouse en la definición de la tabla, los siguientes tipos de ClickHouse se pueden analizar a partir de columnas TEXT de SQLite:

* [Date](/es/reference/data-types/date), [Date32](/es/reference/data-types/date32)
* [DateTime](/es/reference/data-types/datetime), [DateTime64](/es/reference/data-types/datetime64)
* [UUID](/es/reference/data-types/uuid)
* [Enum8, Enum16](/es/reference/data-types/enum)
* [Decimal32, Decimal64, Decimal128, Decimal256](/es/reference/data-types/decimal)
* [FixedString](/es/reference/data-types/fixedstring)
* Todos los tipos enteros ([UInt8, UInt16, UInt32, UInt64, UInt128, UInt256, Int8, Int16, Int32, Int64, Int128, Int256](/es/reference/data-types/int-uint))
* [Float32, Float64](/es/reference/data-types/float)

Consulte [motor de base de datos SQLite](/es/reference/engines/database-engines/sqlite#data_types-support) para ver la correspondencia de tipos predeterminada.

Si se lee un `NULL` de SQLite en una columna de ClickHouse que no sea explícitamente `Nullable`, se lanza la excepción `CANNOT_INSERT_NULL_IN_ORDINARY_COLUMN`. Para leer valores `NULL`, declare la columna como [Nullable](/es/reference/data-types/nullable). Un esquema inferido se basa en los metadata de SQLite: una columna es `Nullable`, salvo que esté declarada como `NOT NULL`.

## Ejemplo de uso {#usage-example}

Muestra una consulta para crear la tabla en SQLite:

```sql
SHOW CREATE TABLE sqlite_db.table2;
```

```text
CREATE TABLE SQLite.table2
(
    `col1` Nullable(Int64),
    `col2` Nullable(String)
)
ENGINE = SQLite('sqlite.db','table2');
```

Devuelve los datos de la tabla:

```sql
SELECT * FROM sqlite_db.table2 ORDER BY col1;
```

```text
┌─col1─┬─col2──┐
│    1 │ text1 │
│    2 │ text2 │
│    3 │ text3 │
└──────┴───────┘
```
