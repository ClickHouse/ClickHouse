Esta página describe las sentencias `KILL QUERY`, `KILL MUTATION`, `KILL TRANSACTION` y `KILL PART_MOVE_TO_SHARD`.

De forma predeterminada, `KILL QUERY` lanza una excepción `NOTHING_TO_KILL` cuando su expresión `WHERE` no deja filas elegibles en `system.processes` tras excluir la propia sentencia `KILL`, y `KILL MUTATION` lanza una excepción cuando su expresión `WHERE` no coincide con ninguna fila de `system.mutations`. Para que no se lance ninguna excepción cuando no haya coincidencias, establezca [`kill_throw_if_noop`](/es/operations/settings/settings#kill_throw_if_noop) en `false`.
`KILL TRANSACTION` y `KILL PART_MOVE_TO_SHARD` nunca lanzan excepciones cuando no hay coincidencias, sino que devuelven un resultado vacío.
La ejecución con `ON CLUSTER` no lanza excepciones cuando no hay coincidencias, ya que los resultados de las coincidencias no se agregan entre los hosts.

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

Intenta finalizar por la fuerza las consultas que se están ejecutando actualmente.
Las consultas que se van a finalizar se seleccionan de la tabla `system.processes` mediante los criterios definidos en la cláusula `WHERE` de la consulta `KILL`.

Ejemplos:

Primero, tendrás que obtener la lista de consultas incompletas. Esta consulta SQL las muestra empezando por las que llevan más tiempo en ejecución:

Lista de un solo nodo de ClickHouse:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Listado de un clúster de ClickHouse:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Cancele la consulta:

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  Si está terminando una consulta en ClickHouse Cloud o en un clúster autogestionado, asegúrese de usar la opción `ON CLUSTER [cluster-name]` para garantizar que la consulta se termine en todas las réplicas.
</Tip>

Los usuarios de solo lectura solo pueden detener sus propias consultas.

Un usuario al que no se le ha concedido `SELECT` sobre `system.processes` aún puede cancelar su propia consulta especificando su identificador:
`KILL QUERY WHERE query_id = '<id>'`. Para un usuario que no tiene ni ese permiso ni `KILL QUERY`, un id que
no se esté ejecutando con su identidad no cancela nada y, de forma predeterminada, lanza una excepción `NOTHING_TO_KILL`. Si
[`kill_throw_if_noop`](/es/operations/settings/settings#kill_throw_if_noop) se establece en `false`, no devuelve filas en su lugar;
a un usuario que tiene `KILL QUERY` pero no ese `SELECT` se le deniega la operación por carecer del `SELECT`.
Cualquier otra condición `WHERE`, así como `ON CLUSTER`, siguen requiriendo los permisos descritos anteriormente.

De forma predeterminada, se usa la versión asíncrona de las consultas (`ASYNC`), que no espera la confirmación de que las consultas se hayan detenido.

La versión síncrona (`SYNC`) espera a que todas las consultas se detengan y muestra información sobre cada proceso a medida que se detiene.
La respuesta contiene la columna `kill_status`, que puede tomar los siguientes valores:

1. `finished` – La consulta se terminó correctamente.
2. `waiting` – Esperando a que la consulta finalice después de enviarle una señal de terminación.
3. Los demás valores explican por qué la consulta no puede detenerse.

Una consulta de prueba (`TEST`) solo comprueba los permisos del usuario y muestra una lista de las consultas que se van a detener.

## KILL MUTATION {#kill-mutation}

La presencia de mutaciones de larga duración o incompletas suele indicar que un servicio de ClickHouse funciona mal. La naturaleza asíncrona de las mutaciones puede hacer que consuman todos los recursos disponibles del sistema. Puede que necesite hacer una de estas dos cosas:

* Pausar todas las mutaciones nuevas, los `INSERT` y los `SELECT`, y permitir que la cola de mutaciones termine de procesarse.
* O cancelar manualmente algunas de estas mutaciones enviando un comando `KILL`.

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

Intenta cancelar y eliminar las [mutaciones](/es/reference/statements/alter/index#mutations) que se están ejecutando en ese momento. Las mutaciones que se van a cancelar se seleccionan de la tabla [`system.mutations`](/es/reference/system-tables/mutations) mediante el filtro especificado en la cláusula `WHERE` de la consulta `KILL`.

Una consulta de prueba (`TEST`) solo verifica los permisos del usuario y muestra una lista de mutaciones que se deben detener.

Ejemplos:

Obtener un `count()` del número de mutaciones incompletas:

Cantidad de mutaciones de un único nodo de ClickHouse:

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

Número de mutaciones de un clúster de réplicas de ClickHouse:

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

Consulta la lista de mutaciones incompletas:

Lista de mutaciones de un solo nodo de ClickHouse:

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

Lista de mutaciones de un clúster de ClickHouse:

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

Cancele las mutaciones según sea necesario:

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

La consulta es útil cuando una mutación está bloqueada y no puede finalizar (p. ej., si alguna función de la consulta de mutación lanza una excepción al aplicarse a los datos contenidos en la tabla).

Los cambios ya realizados por la mutación no se revierten.

<Note>
  La columna `is_killed=1` (solo ClickHouse Cloud) de la tabla [system.mutations](/es/reference/system-tables/mutations) no significa necesariamente que la mutación haya finalizado por completo. Es posible que una mutación permanezca durante un período prolongado en un estado en el que `is_killed=1` e `is_done=0`. Esto puede ocurrir si otra mutación de larga duración está bloqueando la mutación terminada. Esta es una situación normal.
</Note>

## KILL TRANSACTION {#kill-transaction}

Introducido en: v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  Esta sentencia forma parte de un conjunto de funcionalidades experimentales.
  Active el soporte experimental de transacciones añadiendo este parámetro a su [configuración](/es/concepts/features/configuration/server-config/configuration-files):

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  Para obtener más información, consulte la página [Soporte transaccional (ACID)](/es/concepts/features/operations/insert/transactions#transactions-commit-and-rollback).
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

Revierte las [transacciones](/es/reference/statements/transactions) en ejecución que la cláusula `WHERE` selecciona de la tabla [`system.transactions`](/es/reference/system-tables/transactions).
La sesión de una transacción terminada queda entonces en el mismo estado que tras una consulta fallida, tal como se describe en [`COMMIT`](/es/reference/statements/transactions#commit): hasta que se ejecute `ROLLBACK`, `COMMIT` lanza una excepción `INVALID_TRANSACTION`.

La sentencia requiere el privilegio `KILL TRANSACTION` y `SELECT` sobre `system.transactions`.
La respuesta contiene la columna `kill_status`, cuyo valor es `waiting` para una transacción que se ha revertido, seguida de las columnas `tid`, `tid_hash`, `elapsed`, `is_readonly` y `state` de `system.transactions`.

Una consulta de prueba (`TEST`) solo comprueba los permisos del usuario y muestra una lista de las transacciones que se revertirían.

Ejemplo:

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

Introducido en: v21.11.0

<ExperimentalBadge />

<Note>
  El movimiento de partes entre fragmentos es una funcionalidad experimental que se habilita por tabla mediante el ajuste de MergeTree [`part_moves_between_shards_enable`](/es/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable).
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

Cancela los movimientos de partes entre fragmentos, iniciados con `ALTER TABLE ... MOVE PART ... TO SHARD`, que la cláusula `WHERE` selecciona de la tabla [`system.part_moves_between_shards`](/es/reference/system-tables/part_moves_between_shards).
Un movimiento cancelado se revierte en segundo plano y su `state` en `system.part_moves_between_shards` cambia a `CANCELLED`.
Un movimiento que ha alcanzado el estado `SOURCE_DROP` ya no se puede cancelar y se ejecuta hasta completarse.

La sentencia requiere `SELECT` sobre `system.part_moves_between_shards` y, para cancelar un movimiento, el privilegio `ALTER MOVE PARTITION` sobre su tabla y el privilegio `MOVE PARTITION BETWEEN SHARDS`.
Con `ON CLUSTER`, la sentencia requiere ambos privilegios de movimiento sobre `*.*`.
La respuesta contiene la columna `kill_status`, cuyo valor es `waiting` para un movimiento cancelado y `cant_cancel` para un movimiento que ya no se puede cancelar, seguida de las columnas `database`, `table`, `task_name`, `task_uuid`, `part_name`, `to_shard` y `state` de `system.part_moves_between_shards`.

Una consulta de prueba (`TEST`) solo muestra la lista de movimientos que se cancelarían. El modificador `SYNC` no es compatible y lanza una excepción `NOT_IMPLEMENTED`.

Ejemplo:

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
