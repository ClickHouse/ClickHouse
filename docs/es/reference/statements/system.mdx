## SYSTEM RELOAD EMBEDDED DICTIONARIES {#reload-embedded-dictionaries}

Recarga todos los [diccionarios internos](/es/reference/statements/create/dictionary).
De forma predeterminada, los diccionarios internos están deshabilitados.
Siempre devuelve `Ok.` independientemente del resultado de la actualización de los diccionarios internos.

## SYSTEM RELOAD DICTIONARIES {#reload-dictionaries}

La consulta `SYSTEM RELOAD DICTIONARIES` recarga los diccionarios con estado `LOADED` (consulte la columna `status` de [`system.dictionaries`](/es/reference/system-tables/dictionaries)); es decir, los diccionarios que ya se habían cargado correctamente.
De forma predeterminada, los diccionarios se cargan de forma diferida (consulte [dictionaries&#95;lazy&#95;load](/es/reference/settings/server-settings/settings/dictionaries#dictionaries_lazy_load)), por lo que, en lugar de cargarse automáticamente al inicio, se inicializan en el primer acceso, ya sea al usar la función [`dictGet`](/es/reference/functions/regular-functions/ext-dict-functions#dictGet) o al ejecutar `SELECT` sobre tablas con `ENGINE = Dictionary`.

**Sintaxis**

```sql
SYSTEM RELOAD DICTIONARIES [ON CLUSTER cluster_name]
```

## SYSTEM RELOAD DICTIONARY {#reload-dictionary}

Recarga por completo un diccionario `dictionary_name`, independientemente del estado del diccionario (LOADED / NOT&#95;LOADED / FAILED).
Siempre devuelve `Ok.`, independientemente del resultado de la actualización del diccionario.

```sql
SYSTEM RELOAD DICTIONARY [ON CLUSTER cluster_name] dictionary_name
```

El estado del diccionario se puede comprobar consultando la tabla `system.dictionaries`.

```sql
SELECT name, status FROM system.dictionaries;
```

## SYSTEM UNLOAD DICTIONARY {#unload-dictionary}

Descarga un diccionario `dictionary_name` para liberar la memoria que ocupa, si el estado del diccionario es `LOADED`.
El diccionario se recarga de forma diferida cuando sea necesario de nuevo.

```sql
SYSTEM UNLOAD DICTIONARY dictionary_name
```

El estado del diccionario puede comprobarse consultando la tabla `system.dictionaries`.

```sql
SELECT name, status FROM system.dictionaries;
```

## SYSTEM UNLOAD DICTIONARIES {#unload-dictionaries}

La `consulta` `SYSTEM UNLOAD DICTIONARIES` descarga de la memoria todos los diccionarios con estado `LOADED` (consulte la columna `status` de [`system.dictionaries`](/es/reference/system-tables/dictionaries)); es decir, los diccionarios que se habían cargado correctamente con anterioridad.

```sql
SYSTEM UNLOAD DICTIONARIES
```

## SYSTEM RELOAD FUNCTIONS {#reload-functions}

Recarga todas las [funciones ejecutables definidas por el usuario](/es/reference/functions/regular-functions/udf#executable-user-defined-functions) registradas, o una de ellas, desde un archivo de configuración.

**Sintaxis**

```sql
SYSTEM RELOAD FUNCTIONS [ON CLUSTER cluster_name]
SYSTEM RELOAD FUNCTION [ON CLUSTER cluster_name] function_name
```

## SYSTEM RELOAD ASYNCHRONOUS METRICS {#reload-asynchronous-metrics}

Vuelve a calcular todas las [métricas asíncronas](/es/reference/system-tables/asynchronous_metrics). Dado que las métricas asíncronas se actualizan periódicamente según la configuración [asynchronous&#95;metrics&#95;update&#95;period&#95;s](/es/reference/settings/server-settings/settings/asynchronous-metrics#asynchronous_metrics_update_period_s), por lo general no es necesario actualizarlas manualmente mediante esta sentencia.

```sql
SYSTEM RELOAD ASYNCHRONOUS METRICS [ON CLUSTER cluster_name]
```

## SYSTEM RELOAD DELTA KERNEL TRACING {#reload-delta-kernel-tracing}

Introducido en: v26.2.0

Habilita los mensajes de registro de la biblioteca Delta Kernel, que lee tablas [`DeltaLake`](/es/reference/engines/table-engines/integrations/deltalake), a partir del nivel indicado: `ERROR`, `WARN`, `INFO`, `DEBUG` o `TRACE` (en mayúsculas). Los mensajes se escriben en el registro del servidor con el nombre de logger `DeltaKernelTracing`. Tras iniciarse el servidor, la biblioteca no escribe ningún mensaje hasta que se ejecuta la sentencia. Para cambiar el nivel, vuelva a ejecutarla.

```sql
SYSTEM RELOAD DELTA KERNEL TRACING level
```

La sentencia no requiere ningún privilegio. En un build sin compatibilidad con Delta Kernel, falla con el error `SUPPORT_IS_DISABLED`.

## SYSTEM CLEAR|DROP DNS CACHE {#drop-dns-cache}

Borra la caché DNS interna de ClickHouse. A veces (en versiones antiguas de ClickHouse) es necesario usar este comando al modificar la infraestructura (por ejemplo, al cambiar la dirección IP de otro servidor de ClickHouse o del servidor usado por los diccionarios).

Para una gestión más práctica (automática) de la caché, consulte los parámetros `disable_internal_dns_cache`, `dns_cache_max_entries`, `dns_cache_update_period`.

Resulta útil cuando se eliminó o reescribió un esquema en el registro, o para verificar la idempotencia del registro en las pruebas.

## SYSTEM RESTART DISK {#restart-disk}

Introducido en: v21.6.0

Recarga la metadata del disco `disk_name`. En una tabla `MergeTree` cuyos discos sean todos de solo lectura, también vuelve a escanear el directorio de datos de la tabla y carga las partes de datos que hayan aparecido allí desde el último escaneo, de modo que las partes escritas en el mismo almacenamiento por otro proceso de escritura pasen a ser visibles sin necesidad de volver a adjuntar la tabla. Las partes eliminadas del almacenamiento no se detectan. El ajuste de MergeTree [`refresh_parts_interval`](/es/reference/settings/merge-tree-settings/refresh#refresh_parts_interval) hace lo mismo de forma periódica.

```sql
SYSTEM RESTART DISK [ON CLUSTER cluster_name] disk_name
```

Requiere el privilegio `SYSTEM RESTART DISK`.

## SYSTEM CLEAR|DROP TIME SERIES CACHES {#drop-time-series-caches}

Vacía las cachés de una tabla `TimeSeries` que permiten a las inserciones omitir las filas que ya existen en sus tablas de destino. Hay dos cachés de este tipo: la caché de deduplicación de la tabla de familias de métricas y la caché de deduplicación de la tabla de etiquetas; consulte las opciones de configuración `metric_families_deduplication_cache_expiration_seconds` y `tags_deduplication_cache_expiration_seconds` de la tabla. Las cachés son locales de cada servidor y no detectan los cambios realizados directamente en las tablas de destino. Esta discrepancia desaparece por sí sola cuando las entradas caducan; utilice esta sentencia para que la siguiente inserción escriba todas sus filas sin tener que esperar (por ejemplo, después de truncar la tabla de familias de métricas). `TRUNCATE TABLE` sobre una tabla `TimeSeries` vacía únicamente las cachés del servidor que lo ejecuta, por lo que, si las tablas de destino están replicadas, ejecute a continuación la sentencia con `ON CLUSTER` para vaciar las cachés de las demás réplicas.

```sql
SYSTEM DROP TIME SERIES CACHES [ON CLUSTER cluster_name] [db.]table
```

## SYSTEM SYNC FILESYSTEM CACHE {#sync-filesystem-cache}

Sincroniza el estado en memoria de la caché del sistema de archivos de ClickHouse con los archivos de caché realmente presentes en disco y devuelve el `cache_name`, la `path` y el `size` descargado de cada segmento de archivo en caché. Un nombre de caché opcional limita la operación a una sola caché.

```sql
SYSTEM SYNC FILESYSTEM CACHE ['<cache_name>']
```

## SYSTEM CLEAR|DROP DISTRIBUTED CACHE {#drop-distributed-cache}

<Note>
  `SYSTEM CLEAR|DROP DISTRIBUTED CACHE` está disponible solo en ClickHouse Cloud.
</Note>

Elimina la caché distribuida. Use `CONNECTIONS` para eliminar únicamente las conexiones en caché a los servidores de la caché distribuida, o pase un identificador de servidor para actuar sobre un solo servidor.

```sql
SYSTEM DROP DISTRIBUTED CACHE [CONNECTIONS | 'server_id']
```

## SYSTEM DROP REPLICA {#drop-replica}

Las réplicas caídas de las tablas `ReplicatedMergeTree` pueden eliminarse con la siguiente sintaxis:

```sql
SYSTEM DROP REPLICA 'replica_name' FROM TABLE database.table;
SYSTEM DROP REPLICA 'replica_name' FROM DATABASE database;
SYSTEM DROP REPLICA 'replica_name';
SYSTEM DROP REPLICA 'replica_name' FROM ZKPATH '/path/to/table/in/zk';
```

Las consultas eliminarán la ruta de la réplica `ReplicatedMergeTree` en ZooKeeper. Esto resulta útil cuando la réplica está inactiva y sus metadatos no pueden eliminarse de ZooKeeper mediante `DROP TABLE` porque esa tabla ya no existe. Solo eliminará la réplica inactiva/obsoleta y no puede eliminar la réplica local; para eso, use `DROP TABLE`. `DROP REPLICA` no elimina ninguna tabla ni quita ningún dato o metadato del disco.

La primera elimina los metadatos de la réplica `'replica_name'` de la tabla `database.table`.
La segunda hace lo mismo para todas las tablas replicadas de la base de datos.
La tercera hace lo mismo para todas las tablas replicadas en el servidor local.
La cuarta es útil para eliminar los metadatos de una réplica inactiva cuando se eliminaron todas las demás réplicas de una tabla. Requiere que la ruta de la tabla se especifique explícitamente. Debe ser la misma ruta que se pasó como primer argumento del motor `ReplicatedMergeTree` al crear la tabla.

## SYSTEM DROP DATABASE REPLICA {#drop-database-replica}

Las réplicas inactivas de las bases de datos `Replicated` pueden eliminarse con la siguiente sintaxis:

```sql
SYSTEM DROP DATABASE REPLICA 'replica_name' [FROM SHARD 'shard_name'] FROM DATABASE database;
SYSTEM DROP DATABASE REPLICA 'replica_name' [FROM SHARD 'shard_name'];
SYSTEM DROP DATABASE REPLICA 'replica_name' [FROM SHARD 'shard_name'] FROM ZKPATH '/path/to/table/in/zk';
```

Similar a `SYSTEM DROP REPLICA`, pero elimina de ZooKeeper la ruta de la réplica de la base de datos `Replicated` cuando no hay ninguna base de datos en la que ejecutar `DROP DATABASE`. Tenga en cuenta que no elimina las réplicas de `ReplicatedMergeTree` (por lo que también podría necesitar `SYSTEM DROP REPLICA`). Los nombres del segmento y de la réplica son los que se especificaron en los argumentos del motor `Replicated` al crear la base de datos. Además, estos nombres pueden obtenerse de las columnas `database_shard_name` y `database_replica_name` de `system.clusters`. Si falta la cláusula `FROM SHARD`, `replica_name` debe ser un nombre de réplica completo con el formato `shard_name|replica_name`.

## SYSTEM CLEAR|DROP UNCOMPRESSED CACHE {#drop-uncompressed-cache}

Borra la caché de datos sin comprimir.
La caché de datos sin comprimir se habilita o deshabilita mediante la configuración [`use_uncompressed_cache`](/es/reference/settings/session-settings/use#use_uncompressed_cache) a nivel de consulta/USER/perfil.
Su tamaño puede configurarse mediante la configuración [`uncompressed_cache_size`](/es/reference/settings/server-settings/settings/uncompressed-cache#uncompressed_cache_size) a nivel de servidor.

## SYSTEM CLEAR|DROP COLUMNS CACHE {#drop-columns-cache}

Vacía la caché de columnas (columnas deserializadas que se mantienen en memoria).
Las lecturas que ya están en curso cuando se vacía la caché no pueden volver a almacenar sus datos en ella, ni siquiera los de las partes de los datos a las que solo llegan después del vaciado, por lo que la caché permanece vacía incluso bajo carga.
La caché de columnas se habilita o deshabilita con el ajuste `use_columns_cache`, configurable a nivel de consulta, usuario o perfil.
Su tamaño puede configurarse mediante el ajuste de nivel de servidor `columns_cache_size`.
Utilice [`system.columns_cache`](/es/reference/system-tables/columns_cache) para inspeccionar el contenido de la caché.

## SYSTEM CLEAR|DROP CACHÉ DE EXPRESIONES COMPILADAS {#drop-compiled-expression-cache}

Borra la caché de expresiones compiladas.
La caché de expresiones compiladas se activa o desactiva con la configuración [`compile_expressions`](/es/reference/settings/session-settings/compile#compile_expressions) de nivel de consulta/usuario/perfil.

## SYSTEM CLEAR|DROP QUERY CONDITION CACHE {#drop-query-condition-cache}

Limpia la caché de condiciones de consulta.

## SYSTEM CLEAR|DROP CACHE DE ENCABEZADOS DE CIFRADO {#drop-encryption-headers-cache}

Borra la caché de encabezados de cifrado. Esta caché almacena los encabezados de cifrado leídos al inicio de los archivos cifrados y la utiliza la ruta de lectura experimental `use_reader_executor` para evitar volver a leerlos; su tamaño se configura mediante la opción del servidor `encryption_header_cache_size`.

```sql

```

Borra la [caché de consultas](/es/concepts/features/performance/caches/query-cache).
Si se especifica una etiqueta, solo se eliminan las entradas de la caché de consultas con esa etiqueta.

## SYSTEM CLEAR|DROP SCHEMA CACHE {#drop-schema-cache}

Introducido en: v22.8.0

Vacía la [caché de inferencia del esquema](/es/concepts/features/interfaces/schema-inference#schema-inference-cache), que contiene las estructuras de tabla inferidas a partir de los datos leídos por las funciones de tabla y los motores de tablas `file`, `s3`, `url`, `hdfs` y `azureBlobStorage`. Las estructuras almacenadas en caché se pueden consultar en [`system.schema_inference_cache`](/es/reference/system-tables/schema_inference_cache). Sin `FOR`, se vacían las cachés de todos estos almacenamientos; con `FOR`, solo se vacía la del almacenamiento indicado.

```sql
SYSTEM CLEAR|DROP SCHEMA CACHE [FOR File | S3 | URL | HDFS | Azure]
```

Requiere el privilegio `SYSTEM DROP SCHEMA CACHE`.

**Ejemplo**

```sql
SELECT * FROM file('data.csv') FORMAT Null;
SELECT storage, format, schema FROM system.schema_inference_cache;
```

```response
   ┌─storage─┬─format─┬─schema────────────────────────────────┐
1. │ File    │ CSV    │ a Nullable(Int64), b Nullable(String) │
   └─────────┴────────┴───────────────────────────────────────┘
```

```sql
SYSTEM CLEAR SCHEMA CACHE FOR File;
SELECT count() FROM system.schema_inference_cache;
```

```response
   ┌─count()─┐
1. │       0 │
   └─────────┘
```

## SYSTEM CLEAR|DROP FORMAT SCHEMA CACHE {#system-drop-schema-format}

Limpia la caché de los esquemas cargados desde [`format_schema_path`](/es/reference/settings/server-settings/settings/format#format_schema_path).

Destinos admitidos:

* Protobuf: Elimina de la memoria las definiciones importadas de mensajes Protobuf.
* Files: Elimina los archivos de esquema en caché almacenados localmente en [`format_schema_path`](/es/reference/settings/server-settings/settings/format#format_schema_path), generados cuando `format_schema_source` se establece en `query`.
  Nota: Si no se especifica ningún destino, se limpian ambas cachés.

```sql
SYSTEM CLEAR|DROP FORMAT SCHEMA CACHE [FOR Protobuf/Files]
```

## SYSTEM FLUSH LOGS {#flush-logs}

Vuelca los mensajes de registro almacenados en búfer en las tablas del sistema, p. ej., system.query&#95;log. Resulta útil sobre todo para la depuración, ya que la mayoría de las tablas del sistema tienen un intervalo de vaciado predeterminado de 7.5 segundos.
Esto también crea las tablas del sistema aunque la cola de mensajes esté vacía.

```sql
SYSTEM FLUSH LOGS [ON CLUSTER cluster_name] [log_name|[database.table]] [, ...]
```

Si no desea volcarlo todo, puede volcar uno o varios logs individuales indicando su nombre o su tabla de destino:

```sql
SYSTEM FLUSH LOGS query_log, system.query_views_log;
```

## SYSTEM FLUSH ASYNC INSERT QUEUE {#flush-async-insert-queue}

Introducido en: v23.7.0

Escribe de inmediato en sus tablas los datos de las [inserciones asíncronas](/es/concepts/features/operations/insert/asyncinserts) pendientes, sin esperar a que venza el tiempo de espera del búfer. Si no se indica una lista de tablas, la sentencia finaliza cuando se han procesado todos los datos en cola, incluidos los lotes que un vaciado en segundo plano ya haya tomado de la cola. Si se indica una lista de tablas, solo se escriben las inserciones en esas tablas, y la sentencia espera únicamente a los lotes que ella misma toma de la cola. Si los datos de una inserción no se pueden escribir, por ejemplo porque no se pueden analizar, la sentencia no falla: las filas de esa inserción no se insertan y el error se registra en [`system.asynchronous_insert_log`](/es/reference/system-tables/asynchronous_insert_log). Las inserciones pendientes se muestran en [`system.asynchronous_inserts`](/es/reference/system-tables/asynchronous_inserts).

```sql
SYSTEM FLUSH ASYNC INSERT QUEUE [ON CLUSTER cluster_name] [[db.]table [, ...]]
```

Requiere el privilegio `SYSTEM FLUSH ASYNC INSERT QUEUE`.

**Ejemplo**

```sql
CREATE TABLE t (x UInt64) ENGINE = MergeTree ORDER BY x;
INSERT INTO t SETTINGS async_insert = 1, wait_for_async_insert = 0, async_insert_use_adaptive_busy_timeout = 0, async_insert_busy_timeout_max_ms = 600000 VALUES (1), (2);
SELECT table, total_bytes FROM system.asynchronous_inserts;
```

```response
   ┌─table─┬─total_bytes─┐
1. │ t     │           8 │
   └───────┴─────────────┘
```

```sql
SYSTEM FLUSH ASYNC INSERT QUEUE t;
SELECT count() FROM t;
```

```response
   ┌─count()─┐
1. │       2 │
   └─────────┘
```

## SYSTEM RELOAD CONFIG {#reload-config}

Recarga la configuración de ClickHouse. Se utiliza cuando la configuración está almacenada en ZooKeeper. Tenga en cuenta que `SYSTEM RELOAD CONFIG` no recarga la configuración de `USER` almacenada en ZooKeeper; solo recarga la configuración de `USER` almacenada en `users.xml`.  Para recargar toda la configuración de `USER`, use `SYSTEM RELOAD USERS`

```sql
SYSTEM RELOAD CONFIG [ON CLUSTER cluster_name]
```

## SYSTEM RELOAD USERS {#reload-users}

Recarga todos los almacenamientos de acceso, incluidos: users.xml, el almacenamiento de acceso en disco local y el almacenamiento de acceso replicado (en ZooKeeper).

```sql
SYSTEM RELOAD USERS [ON CLUSTER cluster_name]
```

## SYSTEM RECONNECT ZOOKEEPER {#reconnect-zookeeper}

Introducido en: v25.10.0

Cierra la sesión del servidor con su ZooKeeper predeterminado (ClickHouse Keeper) para que el servidor abra una nueva sesión. Las sesiones con ZooKeepers auxiliares se conservan. Las sesiones se muestran en [`system.zookeeper_connection`](/es/reference/system-tables/zookeeper_connection).

```sql
SYSTEM RECONNECT ZOOKEEPER [ON CLUSTER cluster_name]
```

Requiere el privilegio `SYSTEM RECONNECT ZOOKEEPER`.

## SYSTEM RESET DDL WORKER {#reset-ddl-worker}

Introducido en: v26.2.0

Solicita que el trabajador que ejecuta las consultas de [DDL distribuido](/es/reference/statements/distributed-ddl) (`ON CLUSTER`) en este servidor se restablezca al estado que tenía en el inicio del servidor: olvida las entradas de la cola que ha procesado u omitido y vuelve a leer la cola DDL en ZooKeeper. La sentencia devuelve el control de inmediato; el trabajador se restablece en segundo plano antes de volver a procesar la cola. Las entradas ya ejecutadas en este servidor no se vuelven a ejecutar.

```sql
SYSTEM RESET DDL WORKER [ON CLUSTER cluster_name]
```

Requiere el privilegio `SYSTEM RESET DDL WORKER`.

## SYSTEM JEMALLOC PURGE {#jemalloc-purge}

Introducido en: v24.1.0

Hace que el asignador de memoria `jemalloc` devuelva al sistema operativo la memoria no utilizada que retiene (purga las páginas sucias no utilizadas de todas sus arenas).

```sql
SYSTEM JEMALLOC PURGE [ON CLUSTER cluster_name]
```

Requiere el privilegio `SYSTEM JEMALLOC`. En un build sin `jemalloc`, falla con el error `SUPPORT_IS_DISABLED`.

## SYSTEM JEMALLOC FLUSH PROFILE {#jemalloc-flush-profile}

Introducido en: v24.1.0

Escribe el perfil de heap actual de `jemalloc` en un archivo de `/tmp` del servidor y devuelve la ruta del archivo en la columna `filename`. Con `ON CLUSTER`, cada servidor escribe su propio archivo y la sentencia devuelve, en lugar de las rutas, el estado de la consulta en cada servidor, según lo establecido por [`distributed_ddl_output_mode`](/es/reference/settings/session-settings/distributed-ddl#distributed_ddl_output_mode). El parámetro de configuración [`jemalloc_profile_text_output_format`](/es/reference/settings/session-settings/jemalloc-profile#jemalloc_profile_text_output_format) permite elegir entre pilas colapsadas (`collapsed`, el valor predeterminado, con sufijo de archivo `.collapsed`), un perfil simbolizado (`symbolized`, con sufijo `.symbolized`) o el perfil sin procesar (`raw`). El perfil contiene las asignaciones muestreadas mientras el perfilador de memoria dinámica está habilitado, ya sea mediante el ajuste del servidor [`jemalloc_enable_global_profiler`](/es/reference/settings/server-settings/settings/jemalloc-enable#jemalloc_enable_global_profiler) o, para una consulta concreta, mediante el parámetro de configuración [`jemalloc_enable_profiler`](/es/reference/settings/session-settings/jemalloc#jemalloc_enable_profiler). Consulte [Vaciado de perfiles de heap a disco](/es/concepts/features/performance/allocation-profiling#flushing-heap-profiles).

```sql
SYSTEM JEMALLOC FLUSH PROFILE [ON CLUSTER cluster_name]
```

Requiere el privilegio `SYSTEM JEMALLOC`. En un build sin `jemalloc`, falla con el error `SUPPORT_IS_DISABLED`.

**Ejemplo**

```sql
SYSTEM JEMALLOC FLUSH PROFILE;
```

```response
   ┌─filename──────────────────────────────────────────┐
1. │ /tmp/jemalloc_clickhouse.3654128.0.heap.collapsed │
   └───────────────────────────────────────────────────┘
```

## SYSTEM JEMALLOC ENABLE|DISABLE PROFILE {#jemalloc-enable-disable-profile}

Introducido en: v24.1.0

Ya no es compatible: `SYSTEM JEMALLOC ENABLE PROFILE` y `SYSTEM JEMALLOC DISABLE PROFILE` devuelven un error. Active el perfilador de memoria dinámica con el ajuste del servidor [`jemalloc_enable_global_profiler`](/es/reference/settings/server-settings/settings/jemalloc-enable#jemalloc_enable_global_profiler) o, para una consulta concreta, con el parámetro de configuración [`jemalloc_enable_profiler`](/es/reference/settings/session-settings/jemalloc#jemalloc_enable_profiler).

```sql
SYSTEM JEMALLOC ENABLE PROFILE
SYSTEM JEMALLOC DISABLE PROFILE
```

## SYSTEM INSTRUMENT {#instrument}

Gestiona los puntos de instrumentación mediante la funcionalidad XRay de LLVM, disponible cuando ClickHouse se compila con `ENABLE_XRAY=1`.
Esto permite depurar y generar perfiles en producción sin modificar el código fuente y con una sobrecarga mínima.
Cuando no se añade ningún punto de instrumentación, la penalización en el rendimiento es insignificante, ya que solo añade un salto adicional a una
dirección cercana en el prólogo y el epílogo de aquellas funciones que superan las 200 instrucciones.

### SYSTEM INSTRUMENT ADD {#instrument-add}

Agrega un nuevo punto de instrumentación. Las funciones instrumentadas pueden inspeccionarse en la tabla del sistema [`system.instrumentation`](/es/reference/system-tables/instrumentation). Se puede agregar más de un manejador a la misma función, y se ejecutarán en el mismo orden en que se añadió la instrumentación.
Las funciones que se van a instrumentar pueden obtenerse de la tabla del sistema [`system.symbols`](/es/reference/system-tables/symbols).

Hay tres tipos diferentes de manejadores que se pueden agregar a las funciones:

**Sintaxis**

```sql
SYSTEM INSTRUMENT ADD FUNCTION HANDLER [ARGUMENTS]
```

donde `FUNCTION` es cualquier función o subcadena de una función, como `QueryMetricLog::startQuery`, y el manejador es uno de los siguientes

#### LOG {#instrument-add-log}

Imprime el texto proporcionado como argumento y la traza de pila, ya sea en `ENTRY` o `EXIT` de la función.

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' LOG ENTRY 'this is a log printed at entry'
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' LOG EXIT 'this is a log printed at exit'
```

#### SLEEP {#instrument-add-sleep}

Espera una cantidad fija de segundos, ya sea en `ENTRY` o en `EXIT`:

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' SLEEP ENTRY 0.5
```

o para una cantidad aleatoria de segundos con distribución uniforme, indicando el mínimo y el máximo separados por un espacio en blanco:

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' SLEEP ENTRY 0 1
```

#### PERFIL {#instrument-add-profile}

Mide el tiempo empleado entre `ENTRY` y `EXIT` de una función.
El resultado del perfilado se almacena en [`system.trace_log`](/es/reference/system-tables/trace_log) y puede convertirse
en [Chrome Event Trace Format](/es/reference/system-tables/trace_log#chrome-event-trace-format).

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' PROFILE
```

### SYSTEM INSTRUMENT REMOVE {#instrument-remove}

Elimina un único punto de instrumentación con:

```sql
SYSTEM INSTRUMENT REMOVE ID
```

todos ellos con la palabra clave `ALL`:

```sql
SYSTEM INSTRUMENT REMOVE ALL
```

un conjunto de ID obtenido de una subconsulta:

```sql
SYSTEM INSTRUMENT REMOVE (SELECT id FROM system.instrumentation WHERE handler = 'log')
```

o todos los puntos de instrumentación que coincidan con un function&#95;name determinado:

```sql
SYSTEM INSTRUMENT REMOVE 'QueryMetricLog::startQuery'
```

La información sobre el punto de instrumentación puede recopilarse de la tabla del sistema [`system.instrumentation`](/es/reference/system-tables/instrumentation).

## Gestión de tablas distribuidas {#managing-distributed-tables}

ClickHouse puede gestionar tablas [distribuidas](/es/reference/engines/table-engines/special/distributed). Cuando un usuario inserta datos en estas tablas, ClickHouse primero crea una cola con los datos que deben enviarse a los nodos del clúster y luego los envía de forma asíncrona. Puede gestionar el procesamiento de la cola con las consultas [`STOP DISTRIBUTED SENDS`](#stop-distributed-sends), [FLUSH DISTRIBUTED](#flush-distributed) y [`START DISTRIBUTED SENDS`](#start-distributed-sends). También puede insertar datos distribuidos de forma síncrona con la configuración [`distributed_foreground_insert`](/es/reference/settings/session-settings/distributed#distributed_foreground_insert).

### SYSTEM STOP DISTRIBUTED SENDS {#stop-distributed-sends}

Desactiva la distribución de datos en segundo plano al insertar datos en tablas distribuidas.

```sql
SYSTEM STOP DISTRIBUTED SENDS [db.]<distributed_table_name> [ON CLUSTER cluster_name]
```

<Note>
  Si [`prefer_localhost_replica`](/es/reference/settings/session-settings/prefer#prefer_localhost_replica) está habilitado (de forma predeterminada), los datos se insertarán igualmente en el segmento local.
</Note>

### SYSTEM FLUSH DISTRIBUTED {#flush-distributed}

Fuerza a ClickHouse a enviar datos a los nodos del clúster de forma síncrona. Si algún nodo no está disponible, ClickHouse lanza una excepción y detiene la ejecución de la consulta. Puede volver a intentar la consulta hasta que se ejecute correctamente, lo que ocurrirá cuando todos los nodos vuelvan a estar en línea.

También puede sobrescribir algunas configuraciones mediante la cláusula `SETTINGS`; esto puede ser útil para evitar ciertas limitaciones temporales, como `max_concurrent_queries_for_all_users` o `max_memory_usage`.

```sql
SYSTEM FLUSH DISTRIBUTED [db.]<distributed_table_name> [ON CLUSTER cluster_name] [SETTINGS ...]
```

<Note>
  Cada bloque pendiente se almacena en disco con la configuración de la consulta INSERT inicial, por eso a veces puede convenir sobrescribir esa configuración.
</Note>

### SYSTEM START DISTRIBUTED SENDS {#start-distributed-sends}

Activa la distribución de datos en segundo plano al insertar datos en tablas distribuidas.

```sql
SYSTEM START DISTRIBUTED SENDS [db.]<distributed_table_name> [ON CLUSTER cluster_name]
```

### SYSTEM STOP LISTEN {#stop-listen}

Cierra el socket y finaliza de forma ordenada las conexiones existentes al servidor en el puerto y con el protocolo especificados.

Sin embargo, si la configuración del protocolo correspondiente no se especificó en la configuración de clickhouse-server, este comando no tendrá efecto.

```sql
SYSTEM STOP LISTEN [ON CLUSTER cluster_name] [QUERIES ALL | QUERIES DEFAULT | QUERIES CUSTOM | TCP | TCP WITH PROXY | TCP SECURE | HTTP | HTTPS | MYSQL | GRPC | POSTGRESQL | PROMETHEUS | CUSTOM 'protocol']
```

* Si se especifica el modificador `CUSTOM 'protocol'`, se detendrá el protocolo personalizado con el nombre indicado, definido en la sección de protocolos de la configuración del servidor.
* Si se especifica el modificador `QUERIES ALL [EXCEPT .. [,..]]`, se detendrán todos los protocolos, salvo los especificados en la cláusula `EXCEPT`.
* Si se especifica el modificador `QUERIES DEFAULT [EXCEPT .. [,..]]`, se detendrán todos los protocolos predeterminados, salvo los especificados en la cláusula `EXCEPT`.
* Si se especifica el modificador `QUERIES CUSTOM [EXCEPT .. [,..]]`, se detendrán todos los protocolos personalizados, salvo los especificados en la cláusula `EXCEPT`.

### SYSTEM START LISTEN {#start-listen}

Permite establecer nuevas conexiones en los protocolos especificados.

Sin embargo, si el servidor del puerto y protocolo especificados no se detuvo mediante el comando SYSTEM STOP LISTEN, este comando no tendrá efecto.

```sql
SYSTEM START LISTEN [ON CLUSTER cluster_name] [QUERIES ALL | QUERIES DEFAULT | QUERIES CUSTOM | TCP | TCP WITH PROXY | TCP SECURE | HTTP | HTTPS | MYSQL | GRPC | POSTGRESQL | PROMETHEUS | CUSTOM 'protocol']
```

## Gestión de tablas MergeTree {#managing-mergetree-tables}

ClickHouse puede gestionar los procesos en segundo plano de las tablas [MergeTree](/es/reference/engines/table-engines/mergetree-family/mergetree).

### SYSTEM STOP MERGES {#stop-merges}

<CloudNotSupportedBadge />

Permite detener las fusiones en segundo plano de las tables de la familia MergeTree:

```sql
SYSTEM STOP MERGES [ON CLUSTER cluster_name] [ON VOLUME <volume_name> | [db.]merge_tree_family_table_name]
```

<Note>
  La operación `DETACH / ATTACH` sobre la table iniciará las fusiones en segundo plano de esa table, incluso si antes se habían detenido las fusiones para todas las tables MergeTree.
</Note>

Sin `ON VOLUME`, las fusiones se detienen solo para las tables que existen en el momento de ejecutar la sentencia, y solo hasta que se reinicia el servidor:

* Sin un nombre de table (y sin `ON VOLUME`), las fusiones se detienen para todas las tables MergeTree que existan en ese momento. En las tables creadas posteriormente, las fusiones siguen produciéndose.
* Con un nombre de table, la sentencia devuelve `Ok.` aunque la table no exista, y no tiene ningún efecto sobre una table que se cree después con ese nombre.
* El estado de detención se mantiene en memoria. Tras un reinicio del servidor, las fusiones vuelven a ejecutarse en todas las tables.

Mientras las fusiones de una table MergeTree no replicada estén detenidas mediante `SYSTEM STOP MERGES [db.]merge_tree_family_table_name`, `OPTIMIZE TABLE` sobre esa table también falla, con o sin `FINAL`, con el error `Cancelled merging parts. (ABORTED)`. Ejecute primero `SYSTEM START MERGES` para esa table.

### SYSTEM START MERGES {#start-merges}

<CloudNotSupportedBadge />

Permite iniciar las fusiones en segundo plano para tablas de la familia MergeTree:

```sql
SYSTEM START MERGES [ON CLUSTER cluster_name] [ON VOLUME <volume_name> | [db.]merge_tree_family_table_name]
```

### SYSTEM SCHEDULE MERGE {#schedule-merge}

Introducido en: v26.5.0

<ExperimentalBadge />

Programa una fusión de las partes de datos indicadas de la table. La fusión se ejecuta en segundo plano. También se puede indicar una parte que generará una fusión programada previamente, de modo que es posible programar varias fusiones encadenadas. Las partes deben ser adyacentes, pertenecer a una misma partición, indicarse en orden y respetar los límites de tamaño del resto de fusiones en segundo plano, como [`max_bytes_to_merge_at_max_space_in_pool`](/es/reference/settings/merge-tree-settings/max-bytes#max_bytes_to_merge_at_max_space_in_pool). Mientras una fusión programada no cumpla estas condiciones, no se realizará ni esa fusión ni ninguna de las programadas después. Las fusiones programadas se conservan únicamente en la memoria del servidor y se pierden al reiniciarse el servidor. Quedan vinculadas al nombre de la table: si se renombra la table o su base de datos, no se realizarán hasta que la table recupere su nombre anterior.

<Note>
  Esta es una funcionalidad experimental. `SYSTEM SCHEDULE MERGE` y `SYSTEM SYNC MERGES` solo funcionan en tables de la familia MergeTree cuyo ajuste de MergeTree experimental [`merge_selector_algorithm`](/es/reference/settings/merge-tree-settings/merge-selector#merge_selector_algorithm) sea `'Manual'`, y fallan con `BAD_ARGUMENTS` en las demás tables. Las fusiones en segundo plano habituales de estas tables solo fusionan las partes programadas; las fusiones por TTL se siguen ejecutando de forma independiente, y `OPTIMIZE TABLE ... FINAL` sigue fusionando todas las partes.
</Note>

```sql
SYSTEM SCHEDULE MERGE [ON CLUSTER cluster_name] [db.]table PARTS 'part_name' [, ...]
```

### SYSTEM SYNC MERGES {#sync-merges}

Introducido en: v26.5.0

<ExperimentalBadge />

Espera hasta que finalicen todas las fusiones de la table programadas con [`SYSTEM SCHEDULE MERGE`](#schedule-merge). Si se establece `max_execution_time`, falla con `TIMEOUT_EXCEEDED` una vez transcurrido ese tiempo. Tiene el mismo requisito que `SYSTEM SCHEDULE MERGE`.

```sql
SYSTEM SYNC MERGES [ON CLUSTER cluster_name] [db.]table
```

Ambas sentencias requieren el privilegio `SYSTEM MERGES` sobre la table.

**Ejemplo**

```sql
CREATE TABLE t (x UInt64) ENGINE = MergeTree ORDER BY x SETTINGS merge_selector_algorithm = 'Manual';
INSERT INTO t VALUES (1);
INSERT INTO t VALUES (2);
INSERT INTO t VALUES (3);
SYSTEM SCHEDULE MERGE t PARTS 'all_1_1_0', 'all_2_2_0';
SYSTEM SCHEDULE MERGE t PARTS 'all_1_2_1', 'all_3_3_0';
SYSTEM SYNC MERGES t;
SELECT name FROM system.parts WHERE database = currentDatabase() AND table = 't' AND active;
```

```response
   ┌─name──────┐
1. │ all_1_3_2 │
   └───────────┘
```

### SYSTEM STOP TTL MERGES {#stop-ttl-merges}

<CloudNotSupportedBadge />

Permite detener la eliminación en segundo plano de datos antiguos según la [expresión TTL](/es/reference/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-ttl) en tablas de la familia MergeTree:
Devuelve `Ok.` incluso si la tabla no existe o no tiene un motor MergeTree. Devuelve un error cuando la base de datos no existe:

```sql
SYSTEM STOP TTL MERGES [ON CLUSTER cluster_name] [[db.]merge_tree_family_table_name]
```

### SYSTEM START TTL MERGES {#start-ttl-merges}

<CloudNotSupportedBadge />

Permite iniciar la eliminación en segundo plano de datos antiguos según la [expresión TTL](/es/reference/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-ttl) en tablas de la familia MergeTree:
Devuelve `Ok.` incluso si la tabla no existe. Devuelve un error cuando la base de datos no existe:

```sql
SYSTEM START TTL MERGES [ON CLUSTER cluster_name] [[db.]merge_tree_family_table_name]
```

### SYSTEM STOP MOVES {#stop-moves}

Permite detener los movimientos de datos en segundo plano según la [expresión TTL de la tabla con la cláusula TO VOLUME o TO DISK](/es/reference/engines/table-engines/mergetree-family/mergetree#mergetree-table-ttl) para las tablas de la familia MergeTree:
Devuelve `Ok.` incluso si la tabla no existe. Devuelve un error cuando la base de datos no existe:

```sql
SYSTEM STOP MOVES [ON CLUSTER cluster_name] [[db.]merge_tree_family_table_name]
```

### SYSTEM START MOVES {#start-moves}

Permite iniciar el movimiento de datos en segundo plano de acuerdo con la [expresión TTL de la tabla con la cláusula TO VOLUME y TO DISK](/es/reference/engines/table-engines/mergetree-family/mergetree#mergetree-table-ttl) para las tablas de la familia MergeTree:
Devuelve `Ok.` incluso si la tabla no existe. Devuelve un error cuando la base de datos no existe:

```sql
SYSTEM START MOVES [ON CLUSTER cluster_name] [[db.]merge_tree_family_table_name]
```

### SYSTEM STOP CLEANUP {#stop-cleanup}

Introducido en: v23.9.0

<CloudNotSupportedBadge />

Detiene la limpieza en segundo plano de las tables de la familia MergeTree, que elimina las partes de datos obsoletas, los directorios temporales y otros datos obsoletos. Mientras la limpieza esté detenida, el proceso en segundo plano no elimina ninguna parte obsoleta. Si ya hay una limpieza en curso cuando se ejecuta la sentencia, esta no se interrumpe.

```sql
SYSTEM STOP CLEANUP [ON CLUSTER cluster_name] [[db.]merge_tree_family_table_name]
```

Al igual que con [`SYSTEM STOP MERGES`](#stop-merges), si no se especifica un nombre de table, la limpieza se detiene únicamente en las tables que existan en el momento de ejecutar la sentencia, y la detención no se conserva tras un reinicio del servidor.

### SYSTEM START CLEANUP {#start-cleanup}

Introducido en: v23.9.0

<CloudNotSupportedBadge />

Reanuda la limpieza en segundo plano tras ejecutar `SYSTEM STOP CLEANUP`.

```sql
SYSTEM START CLEANUP [ON CLUSTER cluster_name] [[db.]merge_tree_family_table_name]
```

Ambas sentencias requieren el privilegio `SYSTEM CLEANUP` sobre la table.

Elimina una copia de seguridad congelada con el nombre especificado de todos los discos. Consulta más información sobre cómo descongelar partes individuales en [ALTER TABLE table&#95;name UNFREEZE WITH NAME ](/es/reference/statements/alter/partition#unfreeze-partition)

### SYSTEM UNLOCK SNAPSHOT {#unlock-snapshot}

Introducido en: v25.3.0

<ExperimentalBadge />

<Note>
  Disponible solo en ClickHouse Cloud. En otras compilaciones, la sentencia falla con `Unknown type of SYSTEM query`.
</Note>

Elimina de ClickHouse Keeper todos los bloqueos de la instantánea `snapshot_id`, una copia de seguridad ligera creada con el parámetro de configuración experimental `experimental_lightweight_snapshot` de `BACKUP`, de modo que los datos del almacenamiento de objetos a los que hace referencia puedan volver a eliminarse. `FROM` indica el destino de la copia de seguridad; puede omitirse si el destino se almacenó en Keeper al crear la instantánea. `ALTER TABLE ... UNLOCK SNAPSHOT` elimina el bloqueo de una sola table. Consulte [Desbloquear una instantánea](/es/concepts/features/backup-restore/snapshot#unlock-snapshot).

```sql

```

Requiere el privilegio `SYSTEM UNLOCK SNAPSHOT`. Al igual que en `RESTORE`, un destino indicado en `FROM` también requiere el permiso [`SOURCES`](/es/reference/statements/grant#sources) `READ` sobre `S3` o `AZURE` y, si se trata de una colección con nombre, el privilegio `NAMED COLLECTION` sobre ella.

### SYSTEM STOP REPLICATED DDL QUERIES {#stop-replicated-ddl-queries}

Mientras las consultas DDL están detenidas:

* Las consultas DDL en bases de datos `Replicated` fallan con el error `QUERY_IS_PROHIBITED`. Esto incluye las consultas DDL que se iniciaron en este servidor y que ya están en cola, pero que aún no se han confirmado (committed).
* Todas las consultas DDL `ON CLUSTER`, salvo las consultas `SYSTEM`, fallan con el error `QUERY_IS_PROHIBITED` cuando se inician en este servidor, independientemente del motor de la base de datos de destino (no solo en bases de datos `Replicated`).
* Las consultas DDL iniciadas en otras réplicas se siguen aplicando en este servidor: la sentencia impide que este servidor inicie DDL, pero no detiene la ejecución de la cola DDL.

Sin `ON CLUSTER`, la sentencia afecta solo al servidor local. Con `ON CLUSTER`, se ejecuta en todos los hosts del cluster (las consultas `SYSTEM` no se rechazan mientras las consultas DDL están detenidas, por lo que `SYSTEM START REPLICATED DDL QUERIES ON CLUSTER` sigue funcionando).

La prohibición no es persistente: se almacena en memoria y en nodos efímeros de Keeper, y se levanta al reiniciar el servidor. No la utilice como barrera de mantenimiento duradera; si es necesario, vuelva a ejecutarla tras un reinicio.

La sentencia requiere el privilegio global `SYSTEM REPLICATION QUEUES`.

### SYSTEM START REPLICATED DDL QUERIES {#start-replicated-ddl-queries}

Anula el efecto de `SYSTEM STOP REPLICATED DDL QUERIES` y vuelve a permitir las consultas DDL en las bases de datos `Replicated` y las consultas DDL distribuidas con `ON CLUSTER`:

```sql

```

La sentencia requiere el privilegio global `SYSTEM REPLICATION QUEUES`.

### SYSTEM SYNC REPLICA {#sync-replica}

Espera hasta que una tabla `ReplicatedMergeTree` se sincronice con otras réplicas de un clúster, pero no más de `receive_timeout` segundos.

```sql
SYSTEM SYNC REPLICA [ON CLUSTER cluster_name] [db.]replicated_merge_tree_family_table_name [IF EXISTS] [STRICT | LIGHTWEIGHT [FROM 'srcReplica1'[, 'srcReplica2'[, ...]]] | PULL]
```

Después de ejecutar esta sentencia, `[db.]replicated_merge_tree_family_table_name` recupera comandos del log replicado común y los incorpora a su propia cola de replicación; luego, la consulta espera hasta que la réplica procese todos los comandos recuperados. Se admiten los siguientes modificadores:

* Con `IF EXISTS` (disponible desde la versión 25.6), la consulta no devolverá ningún error si la tabla no existe. Esto resulta útil al añadir una nueva réplica a un clúster, cuando ya forma parte de la configuración del clúster pero aún está en proceso de crear y sincronizar la tabla.
* Si se especificó un modificador `STRICT`, la consulta espera a que la cola de replicación quede vacía. Es posible que la versión `STRICT` nunca llegue a completarse si siguen apareciendo nuevas entradas en la cola de replicación.
* Si se especificó un modificador `LIGHTWEIGHT`, la consulta espera únicamente a que se procesen las entradas `GET_PART`, `ATTACH_PART`, `DROP_RANGE`, `REPLACE_RANGE` y `DROP_PART`.
  Además, el modificador LIGHTWEIGHT admite una cláusula opcional FROM &#39;srcReplicas&#39;, donde &#39;srcReplicas&#39; es una lista de nombres de réplicas de origen separada por comas. Esta extensión permite una sincronización más específica al centrarse solo en las tareas de replicación procedentes de las réplicas de origen indicadas.
* Si se especificó un modificador `PULL`, la consulta extrae nuevas entradas de la cola de replicación desde ZooKeeper, pero no espera a que se procese nada.

## Gestión de vistas materializadas actualizables {#managing-refreshable-materialized-views}

Comandos para controlar las tareas en segundo plano que realizan las [vistas materializadas actualizables](/es/reference/statements/create/view#refreshable-materialized-view)

Supervise [`system.view_refreshes`](/es/reference/system-tables/view_refreshes) mientras las utiliza.

### SYSTEM STOP [REPLICATED] VIEW, STOP VIEWS {#stop-view-stop-views}

Deshabilita la actualización periódica de la vista indicada o de todas las vistas actualizables. Si hay una actualización en curso, también la cancela.

Si la vista está en una base de datos Replicated o Shared, `STOP VIEW` solo afecta a la réplica actual, mientras que `STOP REPLICATED VIEW` afecta a todas las réplicas.

<Note>

  En las bases de datos Replicated o Shared, `SYSTEM STOP VIEW` solo afecta a la réplica actual. Usa `SYSTEM STOP REPLICATED VIEW` para detener las actualizaciones en todas las réplicas.
</Note>

```sql

```

```sql

```

### SYSTEM START [REPLICATED] VIEW, START VIEWS {#start-view-start-views}

Habilita la actualización periódica de la vista indicada o de todas las vistas actualizables. No se activa ninguna actualización inmediata.

Si la vista está en una base de datos Replicated o Shared, `START VIEW` revierte el efecto de `STOP VIEW` y `START REPLICATED VIEW` revierte el efecto de `STOP REPLICATED VIEW`. `START VIEW` también revierte el efecto de `PAUSE VIEW`.

```sql

```

```sql
SYSTEM START VIEWS
```

Deshabilita la actualización periódica de la vista especificada o de todas las vistas actualizables.
A diferencia de `SYSTEM STOP VIEW`, `SYSTEM PAUSE VIEW` no interrumpe una actualización que ya esté en curso: deja que la actualización en ejecución termine y solo impide las actualizaciones posteriores.

Para revertirlo, use `SYSTEM START VIEW` o `SYSTEM START VIEWS`.

<Note>
  El estado de pausa no se mantiene entre reinicios del servidor. Después de reiniciar, las vistas reanudarán la programación de actualización configurada.
  En bases de datos Replicated o Shared, `SYSTEM PAUSE VIEW` solo afecta a la réplica actual.

```sql

```


```sql
SYSTEM REFRESH VIEW [db.]name
```

Espera a que finalice la actualización en curso. Si no hay ninguna actualización en curso, devuelve el resultado inmediatamente. Si el último intento de actualización falló, devuelve un error.

```sql
SYSTEM WAIT VIEW [db.]name
```

Si hay una actualización en curso de la vista especificada en la réplica actual, se interrumpe y se cancela. En caso contrario, no hace nada.


## Gestión de la actividad en segundo plano {#managing-background-activity}

Comandos independientes del motor para controlar la actividad en segundo plano de una tabla concreta o de todas esas tablas del servidor a la vez. Incluyen:

* [Vistas materializadas actualizables](/es/reference/statements/create/view#refreshable-materialized-view) (la actualización periódica), y
* los motores de tabla de streaming que consumen continuamente desde una fuente externa: [Kafka](/es/reference/engines/table-engines/integrations/kafka), [RabbitMQ](/es/reference/engines/table-engines/integrations/rabbitmq), [NATS](/es/reference/engines/table-engines/integrations/nats), [S3Queue](/es/reference/engines/table-engines/integrations/s3queue) y [AzureQueue](/es/reference/engines/table-engines/integrations/azure-queue).

Para una vista materializada actualizable, cada verbo es un alias del comando `SYSTEM ... VIEW` correspondiente de [Gestión de vistas materializadas actualizables](#managing-refreshable-materialized-views), por lo que `SYSTEM STOP [db.]name` se comporta exactamente igual que `SYSTEM STOP VIEW [db.]name`, y así sucesivamente.

Las formas por tabla y con comodín difieren en el tratamiento de las tablas sin actividad en segundo plano. La forma por tabla (`SYSTEM STOP [db.]table`) genera un error si la tabla indicada no es ni un motor de streaming ni una vista materializada actualizable. La forma con comodín omite silenciosamente dichas tablas, por lo que siempre es seguro ejecutarla.

`STOP` y `CANCEL` interrumpen el consumo lo antes posible. En [Kafka](/es/reference/engines/table-engines/integrations/kafka), [RabbitMQ](/es/reference/engines/table-engines/integrations/rabbitmq) y [NATS](/es/reference/engines/table-engines/integrations/nats), detienen la lectura desde la fuente, pero no interrumpen un insert que ya haya comenzado: un bloque que ya se está escribiendo en las vistas materializadas termina y realiza el commit. [S3Queue](/es/reference/engines/table-engines/integrations/s3queue) y [AzureQueue](/es/reference/engines/table-engines/integrations/azure-queue) leen e insertan en un único pipeline. Con la deduplicación habilitada (valor predeterminado), también se cancela el insert y los archivos se reprocesan más adelante. Con la deduplicación deshabilitada, el lote en curso termina y realiza el commit (como en los motores anteriores) para evitar duplicar filas. Los datos que se leyeron pero aún no se habían confirmado se consumen de nuevo más adelante, por lo que no se pierde nada, salvo en NATS básico (sin JetStream), que no puede volver a entregarlos y los descarta.

`PAUSE` no interrumpe un insert en curso, por lo que normalmente no provoca pérdidas. NATS básico es la excepción: al pausarlo, se detiene el consumo y se descartan los mensajes que ya había recibido pero aún no había insertado, ya que NATS básico no puede volver a entregarlos.

<Note>
  Ninguno de estos estados persiste tras reiniciar el servidor. Después de reiniciarlo, las vistas materializadas actualizables reanudan su programación configurada y los motores de streaming reanudan el consumo.
</Note>

### SYSTEM STOP {#stop-background}

Detiene la actividad en segundo plano y la mantiene detenida: interrumpe lo que se está ejecutando y no ejecuta nada más hasta `SYSTEM START`. Equivale a `PAUSE` + `CANCEL`.

```sql
SYSTEM STOP [db.]table
SYSTEM STOP ALL BACKGROUND
```

### SYSTEM START {#start-background}

Reanuda la actividad tras un `SYSTEM STOP` o `SYSTEM PAUSE`. No se interrumpe ninguna actividad.

```sql
SYSTEM START [db.]table
SYSTEM START ALL BACKGROUND
```

### SYSTEM PAUSE {#pause-background}

Impide que se inicie más actividad en segundo plano, pero deja que finalice primero lo que se esté ejecutando en ese momento.

```sql
SYSTEM PAUSE [db.]table
SYSTEM PAUSE ALL BACKGROUND
```

### SYSTEM CANCEL {#cancel-background}

Interrumpe únicamente la actividad que se está ejecutando en ese momento, sin bloquear actividades futuras; la tabla continúa actualizándose o consumiendo según su programación. No hace nada si no hay ninguna actividad en curso.

```sql
SYSTEM CANCEL [db.]table
SYSTEM CANCEL ALL BACKGROUND
```

### SYSTEM REFRESH {#refresh-background}

Ejecuta un ciclo adicional fuera de la programación. En una tabla de streaming, se ejecuta de inmediato y una única vez, incluso si la tabla está detenida o pausada. En una vista materializada actualizable, se comporta como `SYSTEM REFRESH VIEW`: si la vista está detenida, la actualización queda pendiente y se ejecuta una vez que `SYSTEM START` la reanuda o que otra réplica se hace cargo.

```sql
SYSTEM REFRESH [db.]table
SYSTEM REFRESH ALL BACKGROUND
```

### Privilegios {#background-privileges}

Cada comando requiere el privilegio del motor correspondiente: `SYSTEM VIEWS` para una vista materializada actualizable y `SYSTEM STREAMING ENGINES` para una tabla de streaming. Ambos son privilegios secundarios de `SYSTEM BACKGROUND`, por lo que conceder `SYSTEM BACKGROUND` permite controlar la actividad en segundo plano de todas esas tablas. Las variantes `ALL BACKGROUND` se aplican únicamente a las tablas que el usuario puede controlar y omiten silenciosamente las demás.

## SYSTEM RESET FILELOG {#reset-filelog}

Cambia la posición desde la que una tabla [FileLog](/es/reference/engines/table-engines/special/filelog) continúa leyendo, sin tener que volver a crear la tabla.

```sql
SYSTEM RESET FILELOG [ON CLUSTER cluster_name] [db.]table_name [FILE 'file_name' [OFFSET n | TO END]]
```

Sin `FILE`, todos los archivos de la tabla se vuelven a leer desde el principio. Con `FILE`, solo se ve afectado el archivo indicado (con el nombre que figura en la columna virtual `_filename`): se vuelve a leer desde el principio, desde el byte `n` con `OFFSET n` (el inicio de una línea, como un valor de `_offset`) o, con `TO END`, solo a partir de los datos añadidos después del comando, de modo que se omite el contenido actual del archivo.

El comando espera a que finalice cualquier lectura en curso en segundo plano y falla si una consulta `SELECT` está leyendo de la tabla. Requiere el privilegio `SYSTEM RESET FILELOG` sobre la tabla.

## SYSTEM ENABLE|DISABLE FAILPOINT {#failpoint}

Los failpoints son puntos con nombre dentro del código del servidor en los que se puede inyectar un fallo bajo demanda —un error, un retardo o una pausa del thread en ejecución— con fines de prueba. Se enumeran en la tabla [`system.fail_points`](/es/reference/system-tables/fail_points) junto con su estado actual.

```sql
SYSTEM ENABLE FAILPOINT name
SYSTEM DISABLE FAILPOINT name
SYSTEM DISABLE ALL FAILPOINTS
SYSTEM WAIT FAILPOINT name [PAUSE|RESUME]
SYSTEM NOTIFY FAILPOINT name
```

`SYSTEM ENABLE FAILPOINT` activa un único fail point; `SYSTEM DISABLE FAILPOINT` lo desactiva y reanuda cualquier thread bloqueado en él, y no hace nada si no estaba habilitado.

`SYSTEM DISABLE ALL FAILPOINTS` deshabilita todos los fail points de una vez y reanuda todos los threads bloqueados en alguno que admita pausas. No recibe ningún nombre y es idempotente, por lo que un entorno de pruebas puede usarlo para devolver el servidor a un estado que no inyecte nada sin necesidad de saber qué fail points habilitó la prueba anterior. En un build sin soporte para fail points, la sentencia se ejecuta correctamente y no hace nada.

`SYSTEM WAIT FAILPOINT ... PAUSE` se bloquea hasta que un thread se pausa en el fail point indicado que admita pausas (o hasta que el fail point se deshabilita); `... RESUME` se bloquea hasta que el thread pausado se reanuda, y `SYSTEM NOTIFY FAILPOINT` reanuda los threads pausados sin deshabilitar el fail point.

Los fail points son un estado local del nodo, por lo que ninguna de estas sentencias admite `ON CLUSTER`. Todas ellas requieren el privilegio `SYSTEM FAILPOINT`.
