## Combinar acciones en un solo `ALTER` {#combining-actions}

Una sola sentencia `ALTER TABLE` admite varias acciones separadas por comas, por lo que el trabajo que, de lo contrario, se enviaría como una serie de sentencias puede agruparse en una sola:

```sql
ALTER TABLE visits DROP COLUMN browser, DROP COLUMN referrer;
```

Las acciones no tienen por qué ser del mismo tipo y se aplican de izquierda a derecha, de modo que una acción posterior puede utilizar lo que haya añadido una anterior:

```sql
-- a new column and an index over it
ALTER TABLE visits ADD COLUMN duration UInt32, ADD INDEX idx_duration duration TYPE minmax GRANULARITY 4;

-- a type change together with a new column
ALTER TABLE visits MODIFY COLUMN browser LowCardinality(String), ADD COLUMN page_id UInt64;

-- three actions in one statement
ALTER TABLE visits DROP COLUMN page_id, MODIFY COLUMN duration UInt64, ADD COLUMN region_id UInt32;
```

Cuando un client espera a que finalice un `ALTER`, la configuración que rige esa espera depende de la acción y no de la sentencia: las acciones que siguen la ruta de ejecución de mutaciones, como `MATERIALIZE INDEX`, se rigen por [`mutations_sync`](/es/reference/settings/session-settings/mutations#mutations_sync), mientras que las acciones de metadata se rigen por [`alter_sync`](/es/reference/settings/session-settings/alter#alter_sync), de modo que combinarlas no hace que queden sujetas a una única configuración. Consulte [Sincronía de las consultas ALTER](#synchronicity-of-alter-queries) para saber qué acciones abarca cada configuración, y [Combinación de cláusulas `MATERIALIZE INDEX`](#combining-materialize-index-clauses) para conocer la restricción que se aplica a este tipo de sentencias mixtas en una base de datos `Replicated`.

## Mutaciones {#mutations}

Las consultas `ALTER` destinadas a modificar datos de tablas se implementan mediante un mecanismo llamado &quot;mutaciones&quot;, en particular [ALTER TABLE ... DELETE](/es/reference/statements/alter/delete) y [ALTER TABLE ... UPDATE](/es/reference/statements/alter/update). Son procesos asíncronos en segundo plano, similares a las fusiones en tablas [MergeTree](/es/reference/engines/table-engines/mergetree-family/index), que producen nuevas versiones &quot;mutadas&quot; de las partes.

En las tablas `*MergeTree`, las mutaciones se ejecutan **reescribiendo partes de datos completas**.
No hay atomicidad: las partes se sustituyen por sus versiones mutadas en cuanto están listas, y una consulta `SELECT` que haya comenzado a ejecutarse durante una mutación verá datos de partes que ya han sido mutadas junto con datos de partes que aún no han sido mutadas.

Las mutaciones están totalmente ordenadas según su orden de creación y se aplican a cada parte en ese orden. Las mutaciones también están parcialmente ordenadas con las consultas `INSERT INTO`: los datos que se insertaron en la tabla antes de que se enviara la mutación serán mutados, y los datos que se insertaron después no serán mutados. Tenga en cuenta que las mutaciones no bloquean las inserciones de ninguna manera.

Una consulta de mutación devuelve el resultado inmediatamente después de que se añade la entrada de mutación (en el caso de las tablas replicadas, en ZooKeeper; en las tablas no replicadas, en el sistema de archivos). La mutación en sí se ejecuta de forma asíncrona usando la configuración del perfil del sistema. Para seguir el progreso de las mutaciones, puede usar la tabla [`system.mutations`](/es/reference/system-tables/mutations). Una mutación enviada correctamente seguirá ejecutándose incluso si se reinician los servidores de ClickHouse. No hay forma de revertir la mutación una vez enviada, pero si la mutación se queda atascada por algún motivo, puede cancelarse con la consulta [`KILL MUTATION`](/es/reference/statements/kill#kill-mutation).

Las entradas de las mutaciones finalizadas no se eliminan de inmediato (el número de entradas conservadas lo determina el parámetro del motor de almacenamiento `finished_mutations_to_keep`). Las entradas de mutación más antiguas se eliminan.

## Coste de ejecución y finalización {#execution-cost-and-completion}

Al planificar un `ALTER TABLE`, distinga entre un cambio de metadata y el trabajo necesario sobre las partes de datos existentes. Que el client espere o no a que finalice depende de la operación: [`alter_sync`](/es/reference/settings/session-settings/alter#alter_sync) controla las operaciones de metadata y `MODIFY COLUMN`, incluidas las conversiones de tipo que reescriben datos; [`mutations_sync`](/es/reference/settings/session-settings/mutations#mutations_sync) controla las mutaciones en segundo plano, como `UPDATE`, `DELETE` y `MATERIALIZE ...`. No tome duraciones fijas como referencia operativa: el coste depende del volumen de metadata, de las partes y bytes afectados, del coste de conversión y de la carga actual en segundo plano.

| Operación                                                                                 | Trabajo sobre los datos existentes                                                              | Comportamiento de finalización predeterminado                                | Principales factores de coste                                           |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `ADD COLUMN`                                                                              | Sin reescritura; las partes antiguas proporcionan el valor predeterminado durante la lectura.   | La espera de metadata depende de `alter_sync`.                               | Tamaño de la metadata y disponibilidad de las réplicas.                 |
| `RENAME COLUMN`                                                                           | No reescribe filas, pero actúa como barrera de ordenación respecto a las mutaciones anteriores. | La espera de metadata depende de `alter_sync`.                               | Mutaciones anteriores y disponibilidad de las réplicas.                 |
| `DROP COLUMN`                                                                             | Elimina archivos de columna; no es un cambio exclusivamente de metadata.                        | Se aplica el orden tanto de metadata como de mutaciones.                     | Número y tamaño de los archivos de columna.                             |
| `MODIFY COLUMN` de valor predeterminado, comentario o tipo que conserva la representación | Sin reescritura inmediata.                                                                      | La espera de metadata depende de `alter_sync`.                               | Tamaño de la metadata y disponibilidad de las réplicas.                 |
| Otros cambios de tipo con `MODIFY COLUMN`                                                 | Una mutación `READ_COLUMN` reescribe la columna afectada en las partes existentes.              | La espera depende de `alter_sync` (valor predeterminado `1`; en Cloud, `0`). | Partes y bytes afectados, coste de conversión y carga en segundo plano. |
| `UPDATE`, `DELETE` y `MATERIALIZE ...`                                                    | Las mutaciones en segundo plano reescriben las partes afectadas.                                | Asíncronas de forma predeterminada; `mutations_sync` controla la espera.     | Partes y bytes afectados, y carga en segundo plano.                     |

## Sincronía de las consultas ALTER {#synchronicity-of-alter-queries}

De forma predeterminada, las consultas `ALTER` sobre tablas no replicadas esperan a que su trabajo se complete. Con `alter_sync = 0`, una consulta `ALTER` que realiza trabajo en segundo plano puede finalizar antes de que dicho trabajo termine. Para las tablas replicadas, la consulta agrega en `ZooKeeper` instrucciones para las acciones correspondientes, y dichas acciones se realizan lo antes posible. La consulta puede esperar a que estas acciones se completen en todas las réplicas.

Para las consultas `ALTER` que crean mutaciones a través de la ruta de ejecución de mutaciones (entre otras, `UPDATE`, `DELETE`, `MATERIALIZE INDEX`, `MATERIALIZE PROJECTION`, `MATERIALIZE COLUMN`, `APPLY DELETED MASK`, `APPLY PATCHES`, `CLEAR STATISTIC` y `MATERIALIZE STATISTIC`), la sincronía se define mediante la configuración [mutations&#95;sync](/es/reference/settings/session-settings/mutations#mutations_sync).

Para otras consultas `ALTER`, incluidas las reescrituras de `MODIFY COLUMN`, la espera se controla mediante [alter&#95;sync](/es/reference/settings/session-settings/alter#alter_sync).

Puede especificar cuánto tiempo (en segundos) esperar a que las réplicas inactivas ejecuten todas las consultas `ALTER` con la configuración [replication&#95;wait&#95;for&#95;inactive&#95;replica&#95;timeout](/es/reference/settings/session-settings/other#replication_wait_for_inactive_replica_timeout).

<Note>
  Para todas las consultas `ALTER`, si `alter_sync = 2` y algunas réplicas permanecen inactivas durante más tiempo del especificado en la configuración `replication_wait_for_inactive_replica_timeout`, se lanza una excepción `UNFINISHED`. Con `alter_sync = 3` no se espera a las réplicas inactivas, por lo que no se lanza ninguna excepción.
</Note>

### Asignación concurrente de `ALTER` en una misma tabla {#concurrent-alter-assignment-on-one-table}

En tablas replicadas, enviar varias sentencias `ALTER` independientes contra la misma tabla en rápida sucesión puede generar el error `CANNOT_ASSIGN_ALTER` (código 517). La ruta replicada genera este error cuando la réplica aún no ha aplicado algunos `ALTER` anteriores (la versión de la metadata sigue por detrás de la metadata común; el servidor puede indicar que la réplica &quot;still not applied some of previous alters&quot; o &quot;Probably too many alters executing concurrently&quot;). Esta condición puede persistir incluso después de que se haya asignado un `ALTER` anterior. Se trata de una condición **general de `ALTER` de metadata o mutaciones concurrentes**; no se limita a sentencias que solo producen mutaciones. Las operaciones concurrentes habituales de modificación de metadata (`ADD` / `DROP` / `MODIFY` y similares) pueden generar el mismo código reintentable (consulte, por ejemplo, la ruta de reintento cubierta por `tests/queries/0_stateless/03518_alter_logical_race.sh`).

Enfoques para evitar la condición de carrera:

* Combine operaciones de metadata independientes en un **único** `ALTER` con varias cláusulas cuando la gramática lo permita (por ejemplo, varias cláusulas `ADD INDEX`), tal como se describe en [Combinar acciones en un solo `ALTER`](#combining-actions).
* Serialice las sentencias `ALTER` y vuelva a intentarlo ante el código 517 hasta que los `ALTER` anteriores se hayan aplicado en la réplica.
* Para los `ALTER` que generan mutaciones, espere a que finalice la mutación anterior mediante un indicador observable documentado, como [`mutations_sync`](/es/reference/settings/session-settings/mutations#mutations_sync) o `is_done` en [`system.mutations`](/es/reference/system-tables/mutations), antes de enviar el siguiente.

### Combinación de cláusulas `MATERIALIZE INDEX` {#combining-materialize-index-clauses}

Pueden incluirse varias cláusulas `MATERIALIZE INDEX` en un mismo `ALTER`. El caso cubierto en el código fuente consiste en agrupar varias cláusulas `ADD INDEX` junto con `MATERIALIZE INDEX` para esos mismos índices nuevos en una sola sentencia (consulte `tests/queries/0_stateless/02911_add_index_and_materialize_index.sql`). Esta forma agrupada de `ADD INDEX` + `MATERIALIZE INDEX` combina un segmento `AlterCommand` con un segmento `MutationCommand`, por lo que **`DatabaseReplicated` la rechaza** con `QUERY_IS_PROHIBITED` (`InterpreterAlterQuery::validateReplicatedDatabaseSegments`). Considere válido el ejemplo `02911` para bases de datos ordinarias (distintas de `DatabaseReplicated`); en `DatabaseReplicated`, mantenga los cambios de metadatos y las mutaciones de materialización en sentencias separadas.

En la implementación actual, cada cláusula `MATERIALIZE INDEX` se resuelve respecto a la instantánea de metadatos de la tabla cuando se prepara la mutación, por lo que las formas con varias cláusulas que solo materializan índices ya existentes siguen la misma ruta de preparación (solo mutación, por lo que permanecen dentro de un único segmento). Esta forma exacta aún no está cubierta por una prueba stateless específica; trátela como comportamiento de la implementación actual, no como un contrato garantizado de forma independiente, hasta que exista dicha cobertura.

Si necesita aplicar las mutaciones en orden, puede seguir emitiendo un `MATERIALIZE INDEX` por sentencia y esperar con [`mutations_sync`](/es/reference/settings/session-settings/mutations#mutations_sync).
