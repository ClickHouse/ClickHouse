<div id="new-feature">
  #### Nueva funcionalidad
</div>

* Se añade la función `extractKeyValuePairs` para extraer pares clave-valor de cadenas. Las cadenas de entrada pueden contener ruido (es decir, `log files` / no necesitan estar formateadas al 100 % como pares clave-valor); el algoritmo buscará pares clave-valor que coincidan con los argumentos pasados a la función. Por ahora, la función acepta los siguientes argumentos: `data_column` (obligatorio), `key_value_pair_delimiter` (por defecto `:`), `pair_delimiters` (por defecto `\space \, \;`) y `quoting_character` (por defecto comillas dobles). [#43606](https://github.com/ClickHouse/ClickHouse/pull/43606) ([Arthur Passos](https://github.com/arthurpassos)).
* Se añade MemoryTracker para las tareas en segundo plano (merges y mutations). Introduce la configuración `merges_mutations_memory_usage_soft_limit` y `merges_mutations_memory_usage_to_ram_ratio`, que representan el límite flexible de uso de memoria para merges y mutations. Si se alcanza este límite, ClickHouse no programará nuevas tareas de merge o mutation. También se introduce la métrica `MergesMutationsMemoryTracking` para permitir observar el uso actual de memoria de las tareas en segundo plano. Cierra [#45710](https://github.com/ClickHouse/ClickHouse/issues/45710). [#46089](https://github.com/ClickHouse/ClickHouse/pull/46089) ([Dmitry Novik](https://github.com/novikd)).
* Se admite la nueva función de agregación quantileGK/quantilesGK, similar a [approx&#95;percentile](https://spark.apache.org/docs/latest/api/sql/index.html#approx_percentile) en Spark. Consulte el algoritmo Greenwald-Khanna en [http://infolab.stanford.edu/~datar/courses/cs361a/papers/quantiles.pdf](http://infolab.stanford.edu/~datar/courses/cs361a/papers/quantiles.pdf). [#46428](https://github.com/ClickHouse/ClickHouse/pull/46428) ([李扬](https://github.com/taiyang-li)).
* Se añade la instrucción `SHOW COLUMNS`, que muestra información resumida de system.columns. [#48017](https://github.com/ClickHouse/ClickHouse/pull/48017) ([Robert Schulze](https://github.com/rschu1ze)).
* Se añadieron los modificadores `LIGHTWEIGHT` y `PULL` para la consulta `SYSTEM SYNC REPLICA`. La versión `LIGHTWEIGHT` espera solo fetches y drop-ranges (se ignoran merges y mutations). La versión `PULL` extrae nuevas entradas de ZooKeeper y no espera a que se completen. Corrige [#47794](https://github.com/ClickHouse/ClickHouse/issues/47794). [#48085](https://github.com/ClickHouse/ClickHouse/pull/48085) ([Alexander Tokmakov](https://github.com/tavplubix)).
* Se añade la función kafkaMurmurHash para compatibilidad con Kafka DefaultPartitioner. Cierra [#47834](https://github.com/ClickHouse/ClickHouse/issues/47834). [#48185](https://github.com/ClickHouse/ClickHouse/pull/48185) ([Nikolay Degterinsky](https://github.com/evillique)).
* Permite crear fácilmente un usuario con los mismos grants que el usuario actual mediante `GRANT CURRENT GRANTS`. [#48262](https://github.com/ClickHouse/ClickHouse/pull/48262) ([pufit](https://github.com/pufit)).
* Se añade la función de agregación estadística `kolmogorovSmirnovTest`. Cierra [#48228](https://github.com/ClickHouse/ClickHouse/issues/48228). [#48325](https://github.com/ClickHouse/ClickHouse/pull/48325) ([FFFFFFFHHHHHHH](https://github.com/FFFFFFFHHHHHHH)).
* Se añadió una columna `lost_part_count` a la tabla `system.replicas`. El valor de la columna muestra el número total de lost parts en la tabla correspondiente. El valor se almacena en ZooKeeper y puede usarse en lugar del evento de profile `ReplicatedDataLoss`, que no es persistente, para monitorización. [#48526](https://github.com/ClickHouse/ClickHouse/pull/48526) ([Sergei Trifonov](https://github.com/serxa)).

<div id="performance-improvement">
  #### Mejora del rendimiento
</div>

* La lectura de archivos en formato Parquet ahora es mucho más rápida. Las operaciones de IO y la decodificación se paralelizan (controladas por la configuración `max_threads`), y solo se leen los rangos de datos necesarios. [#47964](https://github.com/ClickHouse/ClickHouse/pull/47964) ([Michael Kolupaev](https://github.com/al13n321)).
* Las dependencias solo se comprueban cuando es necesario al aplicar consultas `ALTER TABLE`. [#48062](https://github.com/ClickHouse/ClickHouse/pull/48062) ([Raúl Marín](https://github.com/Algunenano)).
* Se optimiza la función `mapUpdate`. [#48118](https://github.com/ClickHouse/ClickHouse/pull/48118) ([Anton Popov](https://github.com/CurtizJ)).
* Ahora se envía explícitamente una consulta interna a la réplica local, y los datos se reciben desde ella a través de la interfaz loopback. La configuración `prefer_localhost_replica` no se respeta para las réplicas paralelas. Esto es necesario para una mejor planificación y hace que el código sea más limpio: el iniciador solo se encarga de coordinar el proceso de lectura y fusionar resultados, atendiendo continuamente las solicitudes mientras todas las consultas secundarias leen los datos. Nota: usar la interfaz loopback no ofrece tanto rendimiento; de lo contrario, algunas réplicas podrían quedarse sin tareas, lo que podría provocar una ejecución aún más lenta de la consulta y no aprovechar todos los recursos posibles. La inicialización del coordinador ahora es aún más diferida. Todas las solicitudes entrantes contienen información sobre el algoritmo de lectura; inicializamos el coordinador con ella cuando llega la primera solicitud. Si alguna réplica decide leer con un algoritmo diferente, se lanzará una excepción y se abortará la consulta. [#48246](https://github.com/ClickHouse/ClickHouse/pull/48246) ([Nikita Mikhaylov](https://github.com/nikitamikhaylov)).
* No se construye un Set para la parte derecha de la cláusula `IN` con una subconsulta cuando se usa solo para el análisis de skip indexes y estos están deshabilitados por configuración (`use_skip_indexes=0`). Anteriormente, esto podía afectar al rendimiento de las consultas. [#48299](https://github.com/ClickHouse/ClickHouse/pull/48299) ([Anton Popov](https://github.com/CurtizJ)).
* El procesamiento de consultas se paraleliza justo después de leer `FROM file(...)`. Relacionado con [#38755](https://github.com/ClickHouse/ClickHouse/issues/38755). [#48525](https://github.com/ClickHouse/ClickHouse/pull/48525) ([Igor Nikonov](https://github.com/devcrafter)).
* El procesamiento de consultas se paraleliza justo después de leer desde una fuente de datos. Las fuentes de datos afectadas son, en su mayoría, almacenamientos externos o simples, como las funciones de tabla `url`, `file`. [#48727](https://github.com/ClickHouse/ClickHouse/pull/48727) ([Igor Nikonov](https://github.com/devcrafter)).
* Se usa el orden de memoria correcto para el contador en `numebers_mt()`. [#48729](https://github.com/ClickHouse/ClickHouse/pull/48729) ([Igor Nikonov](https://github.com/devcrafter)).
* Se redujo la contención del mutex de ThreadPool (puede aumentar el rendimiento cuando hay una gran cantidad de trabajos pequeños). [#48750](https://github.com/ClickHouse/ClickHouse/pull/48750) ([Sergei Trifonov](https://github.com/serxa)).
* Se simplifica el cálculo del tamaño aproximado del gránulo en el grupo de lectura con precarga. [#49051](https://github.com/ClickHouse/ClickHouse/pull/49051) ([Nikita Taranov](https://github.com/nickitat)).

* Si ejecutamos una mutation con IN (subquery) como esta: `ALTER TABLE t UPDATE col='new value' WHERE id IN (SELECT id FROM huge_table)` y la tabla `t` tiene múltiples partes, para cada parte se construye en memoria un Set para la subquery `SELECT id FROM huge_table`. La solución consiste en introducir una caché de corta duración de sets que las tasks de mutation están construyendo en ese momento. Si otra task de la misma mutation se ejecuta de forma concurrente, puede hacer lookup del Set en la caché, esperar a que se construya y reutilizarlo.
