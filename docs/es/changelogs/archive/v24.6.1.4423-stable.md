<div id="backward-incompatible-change">
  #### Cambio incompatible con versiones anteriores
</div>

* Se habilita de forma predeterminada la carga asíncrona de bases de datos y tablas. Consulta `async_load_databases` en config.xml. Aunque este cambio es totalmente compatible, puede introducir una diferencia de comportamiento. Cuando `async_load_databases` es false, como en las versiones anteriores, el servidor no aceptará conexiones hasta que se hayan cargado todas las tablas. Cuando `async_load_databases` es true, como en la nueva versión, el servidor puede aceptar conexiones antes de que se hayan cargado todas las tablas. Si se realiza una consulta a una tabla que todavía no se ha cargado, esta esperará a que la tabla termine de cargarse, lo que puede llevar bastante tiempo. Esto puede cambiar el comportamiento del servidor si forma parte de un sistema distribuido grande detrás de un balanceador de carga. En el primer caso, el balanceador de carga puede recibir un rechazo de conexión y hacer failover rápidamente a otro servidor. En el segundo caso, el balanceador de carga puede conectarse a un servidor que todavía está cargando las tablas, y la consulta tendrá una latencia mayor. Además, si muchas consultas se acumulan en estado de espera, esto puede provocar un problema de &quot;thundering herd&quot; cuando empiecen a procesarse simultáneamente. Esto solo puede suponer una diferencia en backends distribuidos con alta carga. Puedes establecer el valor de `async_load_databases` en false para evitar este problema. [#57695](https://github.com/ClickHouse/ClickHouse/pull/57695) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Algunas consultas no válidas fallarán antes, durante el análisis sintáctico. Nota: se deshabilitó la compatibilidad con expresiones KQL Inline (el lenguaje Kusto experimental) cuando se incluyen en una `kql` table function sin un literal de cadena, por ejemplo `kql(garbage | trash)` en lugar de `kql('garbage | trash')` o `kql($$garbage | trash$$)`. Esta funcionalidad se introdujo de forma no intencionada y no debería existir. [#61500](https://github.com/ClickHouse/ClickHouse/pull/61500) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Se cambió el nombre de los &quot;inverted indexes&quot; a &quot;full-text indexes&quot;, que es una denominación menos técnica y más fácil de usar. Esto también cambia los metadatos internos de la tabla y rompe las tablas con inverted indexes (experimentales) existentes. Asegúrate de eliminar esos índices antes de la actualización y volver a crearlos después. [#62884](https://github.com/ClickHouse/ClickHouse/pull/62884) ([Robert Schulze](https://github.com/rschu1ze)).
* Se desaconseja el uso de las funciones `neighbor`, `runningAccumulate`, `runningDifferenceStartingWithFirstValue`, `runningDifference` (porque es propenso a errores). En su lugar, deben usarse window functions adecuadas. Para volver a habilitarlas, establece `allow_deprecated_functions=1`. [#63132](https://github.com/ClickHouse/ClickHouse/pull/63132) ([Nikita Taranov](https://github.com/nickitat)).
* Las consultas a `system.columns` funcionarán más rápido si hay un gran número de columnas, pero no se ha otorgado `SHOW TABLES` para muchas bases de datos o tablas. Ten en cuenta que en versiones anteriores, si otorgas `SHOW COLUMNS` a columnas individuales sin otorgar `SHOW TABLES` a las tablas correspondientes, la tabla `system.columns` mostrará esas columnas, pero en la nueva versión omitirá la tabla por completo. Se eliminaron los mensajes de trace log &quot;Access granted&quot; y &quot;Access denied&quot;, que ralentizaban las consultas. [#63439](https://github.com/ClickHouse/ClickHouse/pull/63439) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Se rehizo el procesamiento paralelo en el modo `Ordered` del storage `S3Queue`. Este PR no es retrocompatible para el modo Ordered si usabas los settings `s3queue_processing_threads_num` o `s3queue_total_shards_num`. El setting `s3queue_total_shards_num` se eliminó; anteriormente solo se permitía usarlo con `s3queue_allow_experimental_sharded_mode`, que ahora está desaconsejado. Se añadió un nuevo setting: `s3queue_buckets`. [#64349](https://github.com/ClickHouse/ClickHouse/pull/64349) ([Kseniia Sumarokova](https://github.com/kssenii)).
* Se añadieron las nuevas funciones `snowflakeIDToDateTime`, `snowflakeIDToDateTime64`, `dateTimeToSnowflakeID` y `dateTime64ToSnowflakeID`. A diferencia de las funciones existentes `snowflakeToDateTime`, `snowflakeToDateTime64`, `dateTimeToSnowflake` y `dateTime64ToSnowflake`, las nuevas funciones son compatibles con la función `generateSnowflakeID`; es decir, aceptan los Snowflake IDs generados por `generateSnowflakeID` y producen Snowflake IDs del mismo tipo que `generateSnowflakeID` (es decir, `UInt64`). Además, las nuevas funciones usan de forma predeterminada el Unix epoch (es decir, 1970-01-01), igual que `generateSnowflakeID`. Si es necesario, se puede pasar un epoch distinto, por ejemplo, el de Twitter/X, 2010-11-04, también conocido como 1288834974657 msec desde el Unix epoch. Las antiguas conversion functions están obsoletas y se eliminarán tras un periodo de transición; para seguir utilizándolas, habilite la configuración `allow_deprecated_snowflake_conversion_functions`. [#64948](https://github.com/ClickHouse/ClickHouse/pull/64948) ([Robert Schulze](https://github.com/rschu1ze)).
