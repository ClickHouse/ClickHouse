本页逐一介绍 [`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 中用于执行 JOIN 的各个取值，以及块嵌套循环 (block nested loop) 回退机制。为使示意图清晰易读，图中均使用 `max_threads = 2`。

## `direct` {#direct}

<div className="ch-image-lg">
  <Frame>
    ![直接 JOIN 流水线：两个并行流读取左表，两个连接阶段在支撑右表的字典中逐行查找，没有构建阶段](/images/guides/join-algorithms/direct-join.png)
  </Frame>
</div>

`direct` 算法会针对左侧的每一行，在右侧执行一次查找。右侧必须是支持低延迟键值查找的存储。ClickHouse 以流式方式并行读取左侧，并在该存储中查找每个块的键，从而完成连接。由于右侧的数据已经存储在键值结构中，因此无需构建阶段。

以下类型可作为右侧：

* [字典](/zh/concepts/features/dictionaries)，但带有范围键的字典除外。
* 使用 [`EmbeddedRocksDB`](/zh/reference/engines/table-engines/integrations/embedded-rocksdb)、[`KeeperMap`](/zh/reference/engines/table-engines/special/keepermap) 或 [`Redis`](/zh/reference/engines/table-engines/integrations/redis) 引擎的表。
* `MergeTree` 表 (自 25.12 起支持) ，且仅当 `join_algorithm` 只设置为 `direct` 这一个值时适用。ClickHouse 会将每个左侧块的 JOIN 键过滤条件下推到对右表的读取中。如果该键能够利用右表的主键索引，这种方式效率较高；否则，ClickHouse 会针对左侧的每个块扫描一次右表。

使用 [`Join` 表引擎](/zh/reference/engines/table-engines/special/join) 的右侧同样从预先准备好的内存结构中读取，无需构建阶段。这种情况与 `join_algorithm` 无关：ClickHouse 始终使用 `Join` 表中存储的哈希表，`EXPLAIN` 会将其显示为 `FilledJoin`，并标注 `Algorithm: HashJoin`。在 ClickHouse Cloud 中，`Join` 表引擎以 `SharedJoin` 的形式实现，底层由一张 `MergeTree` 表提供存储。

满足以下全部条件时，将使用 `direct` 算法：

* 该 JOIN 是严格性为 `ALL` 的 `INNER` JOIN，或严格性为 `ALL`、`ANY`、`SEMI` 或 `ANTI` 的 `LEFT` JOIN。对于 `MergeTree` 表，不支持 `ANY` 严格性。
* `ON` 子句仅包含一个相等条件，且该条件两侧各引用一列，不含其他条件。
* 右侧列是该存储的单列键，且其类型与键类型一致 (忽略 `Nullable` 和 `LowCardinality`) 。

只要有任一条件不满足，ClickHouse 就会尝试 `join_algorithm` 中的下一个算法。

**内存与落盘。** 该查询不会为右侧构建数据结构。字典占用的内存计入字典本身而非查询，并显示在 [`system.dictionaries`](/zh/reference/system-tables/dictionaries) 的 `bytes_allocated` 列中。该算法不会落盘。

**限制。** 该算法仅支持单个相等键，不支持 `RIGHT`、`FULL` 或 `ASOF` JOIN。过滤器不会下推到右侧。

## `hash` {#hash}

<div className="ch-image-lg">
  <Frame>
    ![哈希 JOIN 管道：两个流将右表读入单个 in-memory 哈希表，随后两个并行流读取左表，并通过在该哈希表中查找来连接每一行](/images/guides/join-algorithms/hash-join.png)
  </Frame>
</div>

`hash` 算法会将完整的右侧数据读入内存，并据此构建一个 in-memory 哈希表。随后，它以并行方式流式读取左侧数据，对每一行在哈希表中查找其键以完成连接。ClickHouse 会根据 JOIN 键列的类型和 JOIN 严格性来选择哈希表的具体实现。

对于 `INNER`、`LEFT`、`RIGHT` 和 `FULL` JOIN，由 [`parallel_hash_join_threshold`](/zh/reference/settings/session-settings/parallel#parallel_hash_join_threshold) 决定哈希表的构建方式。如果估计右侧的行数低于该阈值，则由单个线程填充一个哈希表，如上图所示。如果达到或超过该阈值，ClickHouse 会将哈希表拆分为多个部分，由最多 [`max_threads`](/zh/reference/settings/session-settings/max-threads#max_threads) 个线程并发地填充，如 [`parallel_hash`](#parallel-hash) 中所示。如果没有估计值，哈希表同样会被拆分。若右侧使用特殊存储 (例如字典) ，则始终只构建一个哈希表，并由单个线程填充。

**适用场景。** `hash` 算法是最通用的实现，支持 ClickHouse 所实现的所有连接类型与严格性组合，其中 `ASOF` 仅限于 `INNER` 和 `LEFT` JOIN。它是唯一支持在 `ON` 子句中用 `OR` 组合多个 JOIN 键的算法。`auto` 值之所以支持此类 JOIN，是因为它会使用 `hash` 来执行。此外，与 `parallel_hash` 和 `grace_hash` 一样，它除了相等键之外，还支持比较两个表中列的条件。

**内存与溢写。** 哈希表和右侧的行必须能够全部放入内存。内存使用量可能超过右侧数据的未压缩大小，因为哈希表是逐步扩容的，并不总是处于填满状态。如果设置了落盘阈值，JOIN 会先在内存中执行，一旦右侧数据超过该阈值，就切换为 `grace_hash` 算法。请参阅 [JOIN 内存管理与溢写](/zh/concepts/features/operations/select/join-memory-management)。

**限制。** 如果哈希表未被拆分，构建阶段将在单个线程中运行。当右侧数据远大于估计值时，该阶段可能占据查询时间的大部分。

## `parallel_hash` {#parallel-hash}

<div className="ch-image-lg">
  <Frame>
    ![并行哈希 JOIN 管道：右表的行按 JOIN 键的哈希值拆分到两个桶中，两个哈希表被并发填充；左表的行通过同一哈希函数路由到对应的哈希表](/images/guides/join-algorithms/parallel-hash-join.png)
  </Frame>
</div>

`parallel_hash` 是 `hash` 的已废弃别名，仅为兼容性而保留。在 `join_algorithm` 中指定它并不会改变哈希表的构建方式：无论取这两个值中的哪一个，均由 [`parallel_hash_join_threshold`](/zh/reference/settings/session-settings/parallel#parallel_hash_join_threshold) 决定。若要在 JOIN 类型允许时始终拆分哈希表，请将该阈值设为 `0`。若要始终只使用一个哈希表，请将 `hash_join_layout` 设为 `serial`。

上图展示了 `hash` 如何构建拆分后的哈希表。ClickHouse 按 JOIN 键的哈希值将右侧的行分配到各个分片，并由最多 [`max_threads`](/zh/reference/settings/session-settings/max-threads#max_threads) 个线程并发填充这些分片。在探测阶段，同一哈希函数会将左侧的每一行路由到可能包含其匹配项的分片。

## `grace_hash` {#grace-hash}

<div className="ch-image-lg">
  <Frame>
    ![grace_hash_join_initial_buckets = 3 时 Grace 哈希 JOIN 的第一阶段：两张表的行按 JOIN 键的哈希值拆分到各个桶中；第一个桶在内存中完成连接，两张表的其余桶则延迟写入临时存储](/images/guides/join-algorithms/grace-hash-join.png)
  </Frame>
</div>

`grace_hash` 算法是一种哈希 JOIN，不要求右侧数据能完全放入内存。它分两个阶段执行：

1. ClickHouse 按 JOIN 键的哈希值将右侧的行拆分到各个桶中，为第一个桶构建内存哈希表，并将其余桶写入临时存储。随后使用相同的哈希函数拆分左侧数据，立即连接第一个桶中的行，并将其余行写入临时存储。
2. ClickHouse 逐个处理剩余的桶。对每个桶，先基于右侧的行构建哈希表，再连接同一桶中的左侧行。

初始桶数由 [`grace_hash_join_initial_buckets`](/zh/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets) 决定，并向上取整为 2 的幂。如果内存哈希表超过落盘阈值，ClickHouse 会将桶数翻倍，并移出不再属于当前桶的行。桶数不能超过 [`grace_hash_join_max_buckets`](/zh/reference/settings/session-settings/grace-hash#grace_hash_join_max_buckets)。

**适用场景。** 当右侧数据超过落盘阈值时，`hash` 和 `parallel_hash` 算法会自动切换为 `grace_hash`。若显式选择 `grace_hash`，JOIN 会从第一个块开始就对右侧数据进行分区，不经过内存阶段。该算法支持 `INNER`、`LEFT`、`RIGHT` 和 `FULL` JOIN，以及 `ALL`、`ANY`、`SEMI` 和 `ANTI` 严格性。

**内存与溢写。** 内存使用量受落盘阈值约束。初始桶数越大，内存使用量越低，但执行时间越长。该算法要求落盘阈值不为零，且已配置临时存储。若未设置阈值：当 `join_algorithm` 中还列出了其他算法时，ClickHouse 会跳过 `grace_hash`；当 `grace_hash` 是唯一取值时，ClickHouse 会拒绝该查询。

**限制。** 不支持 `ASOF` JOIN，也不支持通过 `OR` 组合的多个 JOIN 键。由于需要读写临时文件，其速度比内存哈希 JOIN 慢。

## `full_sorting_merge` {#full-sorting-merge}

<div className="ch-image-lg">
  <Frame>
    ![全排序合并 JOIN 管道：两个表的块按 JOIN 键并行排序，并可落盘到临时存储；每个表各有一个合并排序 stream，共同输入单个归并连接阶段](/images/guides/join-algorithms/full-sorting-merge-join.png)
  </Frame>
</div>

`full_sorting_merge` 算法是一种排序合并 JOIN。ClickHouse 按 JOIN 键对两个输入分别排序，再交替扫描这两个已排序的 stream 来查找匹配项。排序在内存中进行；输入较大时，则以外部排序的方式在磁盘上进行。如果某个输入是按 JOIN 键的顺序读取的 (例如该键是 `MergeTree` 表 sorting key 的前缀) ，ClickHouse 会跳过对该输入的排序。

**适用场景。** 当一个或两个表在物理上已按 JOIN 键排序，或者输入过大、无法装入 in-memory 哈希表时，适合使用该算法。它支持 `ALL` 严格性的 `INNER`、`LEFT`、`RIGHT` 和 `FULL` JOIN，`ANY` 严格性的 `INNER`、`LEFT` 和 `RIGHT` JOIN，以及 `ASOF` 严格性的 `INNER` 和 `LEFT` JOIN。

合并阶段在单个 stream 中运行。可通过以下两个选项将其并行化：

* 当 JOIN 键包含两个表主键的前缀时，[`query_plan_join_shard_by_pk_ranges`](/zh/reference/settings/session-settings/query-plan#query_plan_join_shard_by_pk_ranges) 会将两个 `MergeTree` 表之间的 JOIN 拆分为多个基于主键范围的独立归并 JOIN。
* [`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 的 `parallel_full_sorting_merge` 值会按 JOIN 键的哈希对输入进行分片，并在每个分片上运行一个归并 JOIN。结果不保证有序。该设置的参考文档列出了会退回为运行单个 `full_sorting_merge` JOIN 的情况。

[`max_rows_in_set_to_optimize_join`](/zh/reference/settings/session-settings/max-rows#max_rows_in_set_to_optimize_join) 设置可在排序前，用另一个输入的 JOIN 键集合对每个输入进行过滤。启用该过滤器后，将无法使用按顺序读取优化。

**内存与落盘。** 内存占用取决于排序。当两个输入都按键顺序读取时，内存中同一时刻只保留少量块。否则，排序会根据 [`max_bytes_before_external_sort`](/zh/reference/settings/session-settings/max-bytes#max_bytes_before_external_sort) 和 [`max_bytes_ratio_before_external_sort`](/zh/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_sort) 落盘。

**限制。** 该算法不支持 `SEMI` 或 `ANTI` 严格性、通过 `OR` 组合的多个 JOIN 键、`ON` 子句中除等值键以外的条件、使用特殊存储的右侧表，也不支持 `USING` 与 `join_use_nulls` 同时使用。只要在 `join_algorithm` 中列出该算法，即使实际由其他算法执行 JOIN，查询规划也会随之改变。请参阅 [`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm)。

## `partial_merge` {#partial-merge}

<div className="ch-image-lg">
  <Frame>
    ![部分合并 JOIN 管道：右表的块经排序后，与每个块对应的最小值-最大值索引一起写入临时存储；左表的块在内存中排序，并与已存储的右侧块进行连接](/images/guides/join-algorithms/partial-merge-join.png)
  </Frame>
</div>

`partial_merge` 算法是排序合并 JOIN 的一种变体，仅对右侧进行完全排序。ClickHouse 将右侧拆分为若干块，每块最多包含 [`partial_merge_join_rows_in_right_blocks`](/zh/reference/settings/session-settings/partial-merge#partial_merge_join_rows_in_right_blocks) 行，按 JOIN 键对每个块排序，并为每个块创建最小值-最大值索引。随后，ClickHouse 在内存中对左侧的每个块进行排序，再将其与右侧块合并。借助最小值-最大值索引，可以跳过不可能包含匹配项的右侧块。

**适用场景。** 该算法以牺牲执行速度为代价，力求在连接大表时将内存占用降至最低。当左侧的物理行顺序与 JOIN 键顺序一致时效率最高，因为此时最小值-最大值索引能够跳过大部分右侧块；当每个左侧块所含键值的范围较广时，效率最低。当 `join_algorithm` 设为 `auto` 时，可能会在运行时切换到 `partial_merge`。该算法支持 `ALL` 严格性的 `INNER`、`LEFT`、`RIGHT` 和 `FULL` JOIN，`ANY` 严格性的 `INNER` 和 `LEFT` JOIN，以及 `SEMI` 严格性的 `LEFT` JOIN。

**内存与溢写。** ClickHouse 会将已排序的右侧块保留在内存中，直到达到 [`max_rows_in_join`](/zh/reference/settings/session-settings/max-rows#max_rows_in_join) 或 [`max_bytes_in_join`](/zh/reference/settings/session-settings/max-bytes#max_bytes_in_join) 的上限。如果两者均未设置，则以 [`default_max_bytes_in_join`](/zh/reference/settings/session-settings/default#default_max_bytes_in_join) 为准。超出上限后，ClickHouse 会将已排序的块及其索引写入临时存储。[`join_on_disk_max_files_to_merge`](/zh/reference/settings/session-settings/join#join_on_disk_max_files_to_merge) 用于限制可并行合并的文件数量。

**限制。** `RIGHT` 和 `FULL` JOIN 仅支持 `ALL` 严格性。不支持 `ANTI` 和 `ASOF` 严格性，不支持以 `OR` 组合的多个 JOIN 键，也不支持对两个表的列进行比较的条件。

## `ie_join` {#ie-join}

`ie_join` 算法实现了基于排序的 [IEJoin](https://vldb.org/pvldb/vol8/p2074-khayyat.pdf) 算法，适用于 `ON` 子句中包含两个不等式比较 (`<`、`<=`、`>` 或 `>=`) 的 JOIN，这两个比较均作用于被连接表的表达式之间。ClickHouse 按这两个比较中的表达式对两个输入分别排序，无需逐一比较所有行对即可找到匹配的行对。该算法自 26.8 版本起可用。

**使用时机。** 该算法在 `join_algorithm` 中的位置决定了其优先级：

* 若排在其他算法之后，则仅当 `ON` 子句中不包含表之间的等值条件时才会使用该算法。
* 若排在首位，则只要 `ON` 子句包含两个不等式条件，就会使用该算法。其他条件 (包括等值条件) 将作为 JOIN 结果上的过滤器应用，或作为算子内部的残余条件应用。以这种方式应用的相等比较通过 `equals` 求值，而不会作为 JOIN 键使用。参见 [JOIN 键的比较](#comparison-of-join-keys)。

当 `ON` 子句包含两个以上符合条件的不等式条件时，ClickHouse 会根据列统计信息估算出的选择性，从中选出两个作为连接键的条件。若没有统计信息，则按语法顺序使用前两个条件。该算法支持 `ALL` 严格性的 `INNER`、`LEFT`、`RIGHT` 和 `FULL` JOIN，以及 `SEMI` 和 `ANTI` 严格性的 `LEFT` 和 `RIGHT` JOIN。

**内存与溢写。** 执行连接前，两个输入都会先累积在内存中，且[硬限制](/zh/concepts/features/operations/select/join-memory-management#hard-limits)按两侧合计生效。该算法不会落盘。

**限制。** JOIN 算子在单个线程中运行，仅输入的排序会并行执行。不支持 `ANY` 和 `ASOF` 严格性。

## 块嵌套循环回退 {#block-nested-loop-fallback}

块嵌套循环 JOIN 用于执行这样一类 JOIN：其 `ON` 子句中不包含表之间的相等条件，且其他算法均无法执行。ClickHouse 会物化右侧数据，并对每一对左侧行与右侧行计算 `ON` 条件。条件内部的相等比较 (例如 `t1.a = t2.a OR t1.b < 0` 中的 `t1.a = t2.a`) 会通过 `equals` 计算，而不会作为 JOIN 键。参见 [JOIN 键的比较](#comparison-of-join-keys)。它不是 `join_algorithm` 的可选值，而是 JOIN 规划的最后手段。

**使用场景。** 当 `ON` 子句是涉及两张表中列的任意布尔表达式 (例如范围检查或函数调用) ，且 `ie_join` 不适用时，会使用该算法。若 `join_algorithm` 中包含 `hash`，则 `ALL` 严格性的 `INNER` JOIN 会改为以 `CROSS JOIN` 执行，并将该条件用作过滤条件。该回退机制自 26.10 起可用，可通过 [`allow_block_nested_loop_join`](/zh/reference/settings/session-settings/allow#allow_block_nested_loop_join) 设置控制是否启用。如果不允许回退，此类查询将被拒绝，并报错 `INVALID_JOIN_ON_EXPRESSION`。除 `ASOF`、`PASTE` 和 `ANY FULL` 之外，它支持所有连接类型和严格性。

**内存与溢写。** 内存占用以物化后的右侧数据为上限，不会随结果规模增长。右侧的块在内存中以压缩形式存储，达到落盘阈值后写入磁盘。[硬限制](/zh/concepts/features/operations/select/join-memory-management#hard-limits)同样适用于右侧数据，包括已溢写到磁盘的块。

**局限性。** 其开销随两张表行数的乘积增长，在相同数据上比哈希 JOIN 高出几个数量级。有关严格性语义的详细信息，请参见[使用任意 ON 条件的 JOIN](/zh/reference/statements/select/join#join-with-an-arbitrary-on-condition)。

## 各算法支持的 JOIN 类型 {#supported-join-types-per-algorithm}

下表列出了每种算法在各严格性取值下所支持的 JOIN 类型，内容依据 ClickHouse 源代码中的支持检查整理而成。空单元格表示不支持该严格性。

| 算法                                                  | `ALL`                            | `ANY`                    | `SEMI`          | `ANTI`          | `ASOF`          |
| --------------------------------------------------- | -------------------------------- | ------------------------ | --------------- | --------------- | --------------- |
| `direct`                                            | `INNER`, `LEFT`                  | `LEFT`                   | `LEFT`          | `LEFT`          |                 |
| `hash`, `parallel_hash`                             | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `INNER`, `LEFT` |
| `grace_hash`                                        | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` |                 |
| `full_sorting_merge`, `parallel_full_sorting_merge` | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` |                 |                 | `INNER`, `LEFT` |
| `partial_merge`                                     | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`          | `LEFT`          |                 |                 |
| `ie_join`                                           | `INNER`, `LEFT`, `RIGHT`, `FULL` |                          | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` |                 |
| 块嵌套循环 (回退)                                          | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` |                 |

此外，还需遵循以下规则：

* 无论使用哪种算法，`ANY FULL` JOIN 都会在选择算法之前被拒绝。
* 只有 `hash` 和 `full_sorting_merge` 支持 `ASOF` JOIN。`parallel_full_sorting_merge` 会将 `ASOF` JOIN 作为单个 `full_sorting_merge` JOIN 执行。
* `partial_merge` 仅在 `ALL` 严格性下支持 `RIGHT` 和 `FULL` JOIN。
* 作为回退方案的块嵌套循环不支持 `ASOF`、`PASTE` 和 `ANY FULL` JOIN。
* 只有 `hash` 及其别名 `parallel_hash` 支持在 `ON` 子句中用 `OR` 组合多个连接键。取值为 `auto` 时，此类 JOIN 会使用 `hash` 执行。
* 只有 `hash`、`parallel_hash` 和 `grace_hash` 支持将相等键与比较两表列的条件组合使用。
* `direct` 算法仅适用于 [`direct`](#direct) 中列出的右侧数据源。对于 `MergeTree` 表，它不支持 `ANY` 严格性。
* `CROSS JOIN`、带常量 `ON` 条件的 JOIN 以及 `PASTE JOIN` 均有各自的专用实现，不受 `join_algorithm` 影响。

## JOIN 键的比较 {#comparison-of-join-keys}

除 `ie_join` 和块嵌套循环回退之外，所有算法都会将 `ON` 子句中两个表的列之间的相等条件用作 JOIN 键。算法会自行比较这些键，而不是借助 [`equals`](/zh/reference/functions/regular-functions/comparison-functions#equals) 函数，因此对于某些 `equals` 不返回 `1` 的值对，键仍会匹配。`ie_join` 会对其两个不等式条件匹配到的值对使用 `equals` 计算此类相等条件，而块嵌套循环回退则会将其作为 `ON` 条件的一部分，使用 `equals` 进行计算。

| 算法                                                                   | 表之间的相等条件 | 两个 `NaN` 值   | 两个 `Tuple` 值 `(1, NULL)` |
| -------------------------------------------------------------------- | -------- | ------------ | ------------------------ |
| `direct`, `hash`, `parallel_hash`, `grace_hash`                      | JOIN 键   | 若两者比特模式相同则匹配 | 匹配                       |
| `full_sorting_merge`, `parallel_full_sorting_merge`, `partial_merge` | JOIN 键   | 匹配           | 匹配                       |
| `ie_join`                                                            | `equals` | 不匹配          | 不匹配                      |
| 块嵌套循环回退                                                              | `equals` | 不匹配          | 不匹配                      |

`Variant` 键的 `NULL` 值，其行为与包含 `NULL` 元素的 `Tuple` 相同。键本身为 `NULL` 时，无论使用哪种算法都不会匹配，这与 `equals` 一致。请参阅 [JOIN 键中的 NULL 和 NaN 值](/zh/reference/statements/select/join#null-values-in-join-keys)。

`ASOF` JOIN 的等值条件取决于实际执行它的算法，遵循 `hash` 或 `full_sorting_merge` 所在行的规则；右侧使用 `Join` 表引擎时，则遵循 `hash` 行的规则。

当 `direct` JOIN 使用布局为 `complex_key_direct`、`complex_key_cache` 或 `complex_key_ssd_cache` 且 source 为 `CLICKHOUSE` 的字典时，键会以文本形式发送到 source，而文本会将所有 `NaN` 都写为 `nan`，因此只有当两个 `NaN` 键都具有 `nan` 的比特模式时才会匹配。当 [`max_rows_in_set_to_optimize_join`](/zh/reference/settings/session-settings/max-rows#max_rows_in_set_to_optimize_join) 不为零时，`full_sorting_merge` 和 `parallel_full_sorting_merge` 可能会先用一个 JOIN 键集合过滤输入，而该集合按比特模式比较 `NaN` 值，因此两个比特模式不同的 `NaN` 值是否匹配，每次执行的结果可能不同。

因此，比较此类值的 JOIN 可能因执行算法不同而返回不同的行。例如，在 `join_algorithm` 中将 `ie_join` 列在首位，可能会使其执行同时包含一个相等条件和两个不等式条件的 JOIN，此时该相等条件会使用 `equals` 计算，而不是作为 JOIN 键。

## `join_algorithm` 设置 {#join-algorithm-setting}

[`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 设置接受以逗号分隔的算法列表。有关默认值及所有可接受的值，请参阅 [`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 参考文档。

ClickHouse 会按列表顺序依次尝试各算法，并选用第一个同时支持该 JOIN 类型、严格性、`ON` 条件以及右侧表存储方式的算法。如果列表中没有任何算法适用，查询将失败，并报错列出已启用的算法。以下情况不受列表顺序影响：

* 右侧为 `Join` 表引擎时，始终使用该表所存储的哈希表进行连接。
* `CROSS JOIN`、带常量 `ON` 条件的 JOIN 以及 `PASTE JOIN` 均使用专门的实现。
* 不包含表间相等条件的 `ON` 子句由 `ie_join` 或块嵌套循环回退机制处理。

当落盘阈值生效且已配置临时存储时，`parallel_hash` 和 `hash` 会以溢写哈希 JOIN 的方式运行，并在右侧超过阈值时切换为 `grace_hash`。请参阅[落盘阈值](/zh/concepts/features/operations/select/join-memory-management#spill-thresholds)。

### `auto` 值 {#the-auto-value}

当 `join_algorithm = 'auto'` 时，ClickHouse 按以下规则选择具体实现：

1. 如果落盘阈值已生效、已配置临时存储，且 `grace_hash` 支持该 JOIN，ClickHouse 会使用哈希 JOIN，并在右侧数据超过阈值时切换到 `grace_hash`。
2. 否则，如果 `partial_merge` 支持该 JOIN，ClickHouse 会先使用 `hash`，并在右侧数据达到[硬限制](/zh/concepts/features/operations/select/join-memory-management#hard-limits)时切换到 `partial_merge`。已存入哈希表的行会被转移到 `partial_merge` JOIN 中。
3. 否则，ClickHouse 使用 `hash`。

在 `EXPLAIN` 输出中，第二种情况显示为 `Algorithm: JoinSwitcher`。
