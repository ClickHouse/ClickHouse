JOIN 的内存使用由两组设置控制。对于大多数算法，硬限制会在 JOIN 状态过大时终止查询；落盘阈值则会让 JOIN 将部分状态写入磁盘，使查询得以继续执行。

## 硬限制 {#hard-limits}

* [`max_rows_in_join`](/zh/reference/settings/session-settings/max-rows#max_rows_in_join) 限制 JOIN 右侧数据结构 (通常是哈希表) 中的行数。
* [`max_bytes_in_join`](/zh/reference/settings/session-settings/max-bytes#max_bytes_in_join) 限制该数据结构的字节大小。
* [`join_overflow_mode`](/zh/reference/settings/session-settings/join#join_overflow_mode) 定义达到任一限制时执行的操作。

这两个限制同样适用于 [`Join` 表引擎](/zh/reference/engines/table-engines/special/join)。如果一个查询包含多个 JOIN，ClickHouse 会对每个 JOIN 分别检查这些限制。

对于基于哈希的算法 (包括可落盘的算法) ，达到限制会直接终止查询，而不会触发 JOIN 落盘。因此，如果限制小于或等于落盘阈值，查询通常会在 JOIN 落盘之前就被终止。

以下两个设置会改变这一行为：

* [`enable_adaptive_memory_spill_scheduler`](/zh/reference/settings/session-settings/enable#enable_adaptive_memory_spill_scheduler) 会在查询面临内存压力时将符合条件的处理器落盘。对于 JOIN，它仅适用于本身已支持落盘的 JOIN：落盘阈值 (参见[落盘阈值](#spill-thresholds)) 不为零的 `hash`、`parallel_hash` 或 `auto` JOIN，`grace_hash` JOIN，以及已配置临时存储时的块嵌套循环回退。这类 JOIN 可以在达到落盘阈值或硬限制之前就落盘。
* [`legacy_join_size_limits_trigger_spilling`](/zh/reference/settings/session-settings/other#legacy_join_size_limits_trigger_spilling) 会恢复 26.10 之前版本的行为：在这些版本中，达到硬限制时，JOIN 中已在磁盘上运行的部分会进一步落盘，而不是终止查询。启用此设置后，`grace_hash` 仅根据硬限制落盘，并忽略落盘阈值。`hash` 和 `parallel_hash` 仍在达到落盘阈值时开始落盘，并在 in-memory 阶段继续将硬限制作为上限。

对于其他算法，这些限制的作用方式有所不同：

* 对于 [`inequality`](/zh/concepts/features/operations/select/join-algorithms#inequality)，限制作用于两侧累积输入的总量。
* 对于[块嵌套循环回退](/zh/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback)，限制作用于已物化的右侧数据，包括已落盘到磁盘的块。
* 对于 [`partial_merge`](/zh/concepts/features/operations/select/join-algorithms#partial-merge)，达到限制不会终止查询，而是改变执行策略：JOIN 会开始将已排序的右侧块写入磁盘。

## 落盘阈值 {#spill-thresholds}

* [`max_bytes_before_external_join`](/zh/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) 为基于哈希的 JOIN 的右侧表设置一个以字节为单位的绝对落盘阈值。
* [`max_bytes_ratio_before_external_join`](/zh/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join) 以比率形式设置落盘阈值，该比率相对于在查询的 `max_memory_usage` 以及用户级和服务器级内存限制下剩余的内存。如果未配置内存限制，则该比率不起作用。

如果同时设置了这两项设置，则以计算得出的较小阈值为准。这些阈值适用于 `hash`、`parallel_hash`、`grace_hash`、`auto` 值，以及块嵌套循环回退。使用这些阈值前，需要先配置临时数据路径。

## 溢写的工作原理 {#how-spilling-works}

每种支持落盘的算法都会将其状态的不同部分写入临时文件：

* **`hash` 和 `parallel_hash`。** JOIN 在内存中构建哈希表。当右侧数据超过落盘阈值时，JOIN 会转换为 `grace_hash`。它按 JOIN 键的哈希值将右侧行拆分到多个桶中，在内存中保留一个桶，并将其他桶写入临时文件。左侧行使用相同的哈希函数进行拆分。属于内存中那个桶的行会立即进行连接，其他行则写入临时文件。左侧数据读取完毕后，ClickHouse 会逐对加载并连接剩余的桶。
* **`grace_hash`。** JOIN 从第一个块开始就遵循相同的流程。如果某个桶的哈希表超过阈值，桶的数量会翻倍，最多增至 `grace_hash_join_max_buckets`。一旦超过该上限，查询将失败并报错。
* **`full_sorting_merge`。** 当每个输入的排序超过 `max_bytes_before_external_sort` 或 `max_bytes_ratio_before_external_sort` 时，会将已排序的块写入临时文件，随后再合并这些已排序的文件。
* **`partial_merge`。** 右侧数据达到硬限制后，已排序的右侧块及其最小值-最大值索引会被写入临时文件。
* **块嵌套循环回退。** 右侧块会先在内存中压缩，达到落盘阈值后再写入临时文件。

[`direct`](/zh/concepts/features/operations/select/join-algorithms#direct) 和 [`inequality`](/zh/concepts/features/operations/select/join-algorithms#inequality) 算法不会落盘。

临时文件会写入由服务器设置 [`tmp_path`](/zh/reference/settings/server-settings/settings/tmp#tmp_path)、[`tmp_policy`](/zh/reference/settings/server-settings/settings/tmp#tmp_policy) 或 [`temporary_data_in_cache`](/zh/reference/settings/server-settings/settings/temporary-data#temporary_data_in_cache) 所配置的存储中。读写临时文件会增加磁盘 I/O，因此发生溢写的 JOIN 比完全在内存中执行的相同 JOIN 更慢。

`ExternalJoinWritePart`、`ExternalJoinCompressedBytes` 和 `ExternalJoinUncompressedBytes` 这几个 profile events 记录了 JOIN 写入的临时文件数量及其包含的数据量，可在 [`system.query_log`](/zh/reference/system-tables/query_log) 的 `ProfileEvents` 列中查看。
