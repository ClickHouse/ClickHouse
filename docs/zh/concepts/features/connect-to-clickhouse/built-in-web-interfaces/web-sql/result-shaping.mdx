内置的 Web SQL 界面 (`play.html`，通过任意 ClickHouse HTTP 端口的 [`/play`](/zh/concepts/features/connect-to-clickhouse/protocols/http) 路径访问) 支持按列对结果排序、按列值过滤结果以及分页浏览结果，且全程无需编辑查询。

这些操作均不在浏览器端完成。每次更改都会结合相应的查询构建设置重新运行查询，服务器会将原查询包装为派生表，并在外层加上 `ORDER BY`、`WHERE` 和 `LIMIT`，从而物化这些设置。因此，屏幕上显示的是整个查询经过排序、过滤和分页后的结果，而不是对当前页面中已有的行重新排列。

## 排序 {#sorting}

每个列标题右侧都有两个箭头：▲ 按该列对结果进行升序排序，▼ 则进行降序排序。点击箭头会启用相应排序并重新运行查询；点击当前排序方向的箭头会取消该排序，点击另一方向的箭头则会切换排序方向。这些箭头都是按钮，键盘用户可以通过 Tab 键将焦点移至按钮，并用键盘激活。每个按钮还会向辅助技术提供自身状态 (列标题本身带有 `aria-sort`) 。

在支持指针悬停的设备 (如使用鼠标的设备) 上，只有当指针悬停在列标题上或某个箭头获得焦点时，箭头才会显示，其余时间保持隐藏，以免干扰；在触摸设备及其他不支持悬停的粗指针设备上，箭头始终显示，方便直接点按。参与排序的列无需悬停便会显示两个箭头——一个用于直观展示当前排序方向，另一个则方便反转方向，因为这最有可能是用户接下来的操作。

列标题中的所有图标都遵循相同的视觉规则，无论其控制哪项功能：功能未在该列上生效时，图标以去色样式显示；功能生效后，图标则使用专门表示控件已生效的颜色——浅色主题下为品红色，深色主题下为黄色——并在未悬停时保持显示。图标的弱化效果仅通过去色实现，不会改变透明度，因此即使叠在列名或单元格的颜色编码上，也不会显得半透明。

### 按多列排序 {#sorting-by-several-columns}

启用某个排序会替换当前排序：之前已排序的列将被停用，所点击的列成为唯一的排序键。点击时按住 <kbd>Shift</kbd>，可保留已生效的排序键，并将该列追加到它们之后，这与 `ORDER BY` 采用的顺序一致——第一个键优先决定顺序，后续每个键用于在前面各键取值相同时进一步区分。当存在多个排序键时，每个处于启用状态的箭头还会以上标形式显示对应列在该顺序中的位置 (▼¹、▲²、…) 。

对已是排序键的列按住 <kbd>Shift</kbd> 点击，只会切换其排序方向，其在顺序中的位置保持不变。停用某一列只会移除该列，其余排序键保持不变。

## 过滤 {#filtering}

### 从列标题筛选 {#filtering-from-a-column-header}

每个列标题中都有一个漏斗图标，位于排序箭头旁边，显示方式与排序箭头相同。点击该图标会打开一个输入框，用于为该列输入谓词，其右侧紧贴着一个应用按钮 (▶) ；占位符会根据列的类型提示谓词的形态——数值类型为 `> 10`，字符串类型为 `LIKE '%test%'`。输入框在标题单元格内打开，单元格会扩展出第二行来容纳它——设置过滤器后，过滤器本身也显示在这一行，因此过滤器在哪里显示，就在哪里编辑。输入的内容是列名之后的部分，因此 `> 10` 会变为 `WHERE column > 10`，凡是服务器在此处接受的表达式都可以使用，例如 `BETWEEN 1 AND 5`、`IN (1, 2, 3)`、`IS NOT NULL`、`% 2 = 0`。

点击应用按钮 (或按 <kbd>Enter</kbd>) 会应用过滤器并重新运行查询；按 <kbd>Esc</kbd>，或者点击其他位置、按 Tab 键移开焦点，都会放弃编辑并收起输入框。没有可应用的内容时 (即未设置过滤器的列上输入框为空) ，应用按钮处于不可用状态；但如果该列已设置过滤器，即使输入框为空，按钮仍保持可用，因为清空输入框后点击应用，正是通过输入框移除过滤器的方式。多个列上的过滤器以 `AND` 组合。

### 从单元格筛选 {#filtering-from-a-cell}

如果该列支持按单元格的值进行过滤，选中单元格后，其复制图标旁还会出现一个漏斗图标。点击该图标会列出适用的比较方式：

| 值                                                | 可用比较                                                       |
| ------------------------------------------------ | ---------------------------------------------------------- |
| 数字                                               | `=`, `!=`, `>`, `<`, `>=`, `<=`                            |
| 日期或时间 (`Date`、`Date32`、`DateTime`、`DateTime64`)  | `=`, `!=`, `>`, `<`, `>=`, `<=`                            |
| 不超过 100 个字符的字符串                                  | `=`, `!=`, `contains` —— 空字符串仅提供 `=` 和 `!=`，因为任何字符串都包含空字符串 |
| `Bool`                                           | `true`, `false` —— 即这两个值本身，而非与该单元格的值进行比较                   |
| `Enum`                                           | `=`, `!=` —— 在封闭的名称集合上做部分匹配，作为过滤条件没有意义                     |
| `NULL`                                           | `IS NULL`, `IS NOT NULL`                                   |

选中某一项后会立即生效。日期、时间或枚举值会与服务器渲染出的原始文本进行比较，ClickHouse 会将该文本解析回该列自身的类型 (对于枚举，即该值的名称) 。`contains` 会转换为 `LIKE` 模式，并对值中自带的 `%` 和 `_` 进行转义，从而按字面匹配该值。如果单元格的值不属于上述任何一种 (例如数组、元组、映射或长文本) ，则不会显示菜单；不过仍可通过列标题的输入框对该列进行过滤。

### 当前生效的过滤器 {#the-filter-in-effect}

对某列设置过滤器后，只要过滤器未被移除，该列名称下方就会一直显示其谓词，让用户始终清楚屏幕上的行只是结果的一个子集；该列的漏斗图标也会随之下移到谓词旁边，即列标题的左下角。点击谓词会在原处重新打开该谓词的输入框；点击旁边的 ✕ 可移除过滤器，提交空输入也有同样效果。这两种操作都会重新运行查询。

无论过滤器从何处设置，每列都只有一个过滤器：从单元格设置的过滤器会替换之前通过列标题输入框设置的过滤器，列标题始终显示当前生效的过滤器。

如果过滤后的结果为空，仍会保留列标题 (而不是像普通空结果那样以垂直布局显示) ，以便用户看到未匹配任何内容的过滤器并将其移除。

## 分页 {#pagination}

结果的显示数量有上限：最多 1000 行；如果结果非常宽 (列很多) ，显示的行数会更少。当结果因达到该上限而被截断时，说明还有更多内容可供查看，此时表格下方会出现分页控件：

```text
Page: 1 2 …   Per page: 1000
```

点击某个页码时，会将每页大小设为显示上限，并将该页码设为 [`page`](/zh/reference/settings/session-settings/other#page) 设置的值，然后重新运行查询；服务器会将页码转换为对应的 `OFFSET`。此后，只要结果仍处于分页状态，分页控件就会一直保留，即使每一页都恰好填满、因而看起来不再像是被截断。

页面不会显示总页数，因为总页数是未知的——要统计结果的行数，就得再运行一次查询。分页控件会列出当前页之前的十页、当前页以及下一页，后面跟着 `…`。点击 `…` 会将其变为输入框，可输入任意页码；输入框失去焦点时即采用所输入的页码 (按下 <kbd>Enter</kbd> 也会使其失去焦点) 。

只有当前页已填满时，才会提供下一页。如果返回的某一页行数少于该页可容纳的行数，说明已到达结果末尾，因此不再有后续页面。 (如果结果的行数恰好是每页大小的整数倍，仍会多提供一页，而该页返回时为空：要区分这种情况，同样需要统计行数。)

`Per page` 显示每页包含的行数，编辑方式相同：点击该值并输入新的数值。该值不能超过结果一次可显示的上限——页面更大时，返回的部分行随后会被表截断，而下一页又会从这些行之后开始，因此继续翻页会在无任何提示的情况下跳过那些从未显示的行；输入更大的数值时，会按该最大值处理，并随即显示为该值。修改此值后会从第一页重新开始，因为每页大小改变后，各页包含的行也会不同。

更改排序或任意过滤器都会回到第一页：两者都会改变结果所包含的行或其顺序，因此用户所在的页面不再对应结果中原来的那一部分。

## 应用方式 {#how-it-is-applied}

形态通过 [`order`](/zh/reference/settings/session-settings/other#order)、[`filter`](/zh/reference/settings/session-settings/other#filter)、[`limit`](/zh/reference/settings/session-settings/other#limit) 和 [`page`](/zh/reference/settings/session-settings/other#page) 查询构建设置传递。服务器将这些设置应用于已解析的查询，而非查询文本，因此它们可以与查询原有的结构配合使用：无论是 `UNION`、末尾的 `FORMAT` 子句，还是查询自身的 `ORDER BY` 和 `LIMIT`，都能正常工作，且编辑器中的查询不会被重写。

列名以用引号括起的标识符形式传递，因此，即使结果列的名称是表达式 (`count()`) 或包含空格，该列也可以用作排序键或过滤键。

## 何时可用 {#when-it-is-available}

结果形态仅适用于这些设置能够作用的语句，即 `SELECT` 和 `UNION` 查询 (包括以 `WITH` 子句或 `FROM` 开头的查询) 。`SHOW`、`DESCRIBE`、`EXISTS` 和 `EXPLAIN` 不提供该功能：这些语句虽然也会生成表，但相关设置对它们不起作用，若在此提供控件，承诺的结果将与实际的行不符。

形态作用于单条语句的结果，因此“全部运行”这类多语句运行不提供该功能，因为其中各条语句是彼此独立的查询，列也各不相同。

如果结果首页最多只有一行，同样不提供该功能：单行无论按何种顺序排列都是同一顺序，对其应用过滤器也只能保留或删除这一行，因此这些控件除了针对相同的行重新运行查询之外别无用处——而空结果甚至连可删除的行都没有。这与此时隐藏[颜色编码](/zh/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/color-coding)开关的原因相同：不超过一行时，没有可比较的对象。

但有两种单行结果会保留控件，因为此时控件是唯一的回退途径：

* 已经排序或过滤的结果：其排序必须能够撤销，其过滤器必须能够清除——长结果正是通过只匹配一行的过滤器变成短结果的，如果随之移除控件，用户就会被困在过滤器生效的状态中；
* 因达到显示上限而被截断的结果，即某个更长结果的第一页：页面大小受表格一次可显示的单元格数量限制，因此列数很多的结果可能被截断到只剩一行，而该行之后的行正是排序和分页要访问的内容。

形态归属于创建它的那条语句。运行另一条语句时——无论是编辑查询之后，还是将光标移到多语句编辑器中的另一条语句——形态都会被删除，而不会对新语句中可能不存在的列应用 `ORDER BY` 或 `WHERE`。

形态同样归属于该语句运行时所处的上下文：所选数据库、语句发往的服务器和用户，以及查询参数的值。其中任何一项发生变化后，相同的文本都可能指向不同的列——例如切换数据库后的 `SELECT * FROM events`，或编辑参数后的 `SELECT * FROM {tbl:Identifier}`——因此这些情况下形态也会被删除，下一次运行将返回未应用形态的结果。

## 下载与复制 {#downloading-and-copying}

下载时会以相同的形态重新执行生成该结果的查询，因此导出的文件与屏幕上的结果包含相同的行，且顺序一致。复制直接使用已渲染的结果，因此同样与屏幕上显示的内容一致。

## 持久化 {#persistence}

形态会记录在页面 URL (`sort_columns`、`filters`、`page` 和 `page_size`) 、浏览器历史记录以及其所属单元的结果快照中，因此无论是重新加载页面、共享链接，还是在页面间前进或后退，形态都会保留下来。由于形态决定的是返回哪些行，而不仅仅是行的呈现方式，因此自动运行查询 (`run=1`) 的共享链接会以相同的形态重新运行该查询，从而重现结果本身。为保持 URL 和历史记录状态的紧凑，只有处于活跃状态的形态才会被存储——未经整形的结果不会向 URL 或历史记录状态添加任何内容。

如上所述，恢复的结果会保持其形态与生成该结果的上下文绑定：快照会记录生成这些行时所用的数据库、连接和参数值，因此更改其中任何一项后再重新运行该语句，形态会被丢弃，而不会被应用到另一个结果上。

与[颜色编码模式](/zh/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/color-coding)和[固定列](/zh/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/pinned-columns)一样，形态隶属于它所整形的结果：即隶属于查询选项卡；若该选项卡是[笔记本](/zh/concepts/features/connect-to-clickhouse/built-in-web-interfaces/web-sql/notebook)，则隶属于其中的各个单元。因此，对某个结果进行排序或过滤，既不会更改也不会重新运行其他选项卡或其他单元的结果——对某个单元的结果进行整形，只会重新运行该单元。

## 限制 {#limitations}

* 如果服务器无法应用某个形态，查询将会失败，错误的显示方式与其他失败查询相同。随后该形态会被删除，因为执行失败时既不会渲染列标题，也不会渲染本可用来清除该形态的分页控件。
* 排序和过滤依据列在结果中的名称来识别列。同一结果中可能出现重名的列 (例如 `SELECT 1 AS x, 2 AS x`，或对含有相同列名的表进行连接) ，这类列无法通过名称区分，因此不提供排序或过滤控件；同一结果中名称唯一的列仍保留这些控件。
* 多列排序需要使用 <kbd>Shift</kbd> 键，因此在触摸设备上不可用，但单列排序仍可使用。
* 单行结果的纵向 (转置) 布局没有列标题，因此也没有这些控件；正因如此，用户已调整过形态的结果会保持横向布局。
