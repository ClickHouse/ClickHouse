## 前置条件 {#prerequisites}

要运行本文中的示例，您需要：

* 一个正在运行的 ClickHouse 服务器实例
* 已安装 `curl`。在 Ubuntu 或 Debian 上，可运行 `sudo apt install curl` 进行安装，或参阅[文档](https://curl.se/download.html)了解安装方法。

## 概览 {#overview}

HTTP 接口允许您以 REST API 的形式，在任何平台上使用任何编程语言访问 ClickHouse。与原生接口相比，HTTP 接口的功能较为有限，但支持的编程语言更多。

默认情况下，`clickhouse-server` 监听以下端口：

* 8123 端口用于 HTTP
* 可启用 8443 端口用于 HTTPS

如果发送不带任何参数的 `GET /` 请求，将返回 200 响应码以及字符串 &quot;Ok.&quot;：

```bash
$ curl 'http://localhost:8123/'
Ok.
```

&quot;Ok.&quot; 是 [`http_server_default_response`](/zh/reference/settings/server-settings/settings/http#http_server_default_response) 中定义的默认值，可按需修改。

另请参阅：[HTTP 响应码注意事项](#http_response_codes_caveats)。

## Web 用户界面 {#web-ui}

ClickHouse 内置 Web 用户界面，可通过以下地址访问：

```text
http://localhost:8123/play
```

网页用户界面支持在查询运行期间显示进度、取消查询以及流式返回结果。
它还有一个隐藏功能，可以为查询管道显示图表和图。

查询成功执行后，界面上会出现一个下载按钮，您可以用它以多种格式下载查询结果，包括 CSV、TSV、JSON、JSONLines、Parquet、Markdown，或 ClickHouse 支持的任何自定义格式。下载功能借助查询缓存高效获取结果，无需重新执行查询。即使 UI 只显示了多页结果中的一页，下载的也是完整的结果集。

网页用户界面专为像您这样的专业人士打造。

  <Frame>
    ![ClickHouse 网页用户界面截图](/images/play.webp)
  </Frame>
</div>

在健康检查脚本中，请使用 `GET /ping` 请求。该处理器始终返回 &quot;Ok.&quot; (末尾带一个换行符) 。自 18.12.13 版本起可用。另请参见 `/replicas_status`，可用于检查副本延迟。


## 通过 HTTP/HTTPS 查询 {#querying}

通过 HTTP/HTTPS 进行查询有三种方式：

* 将请求作为 URL 的 &#39;query&#39; 参数发送
* 使用 POST 方法。
* 在 &#39;query&#39; 参数中发送查询的开头部分，其余部分通过 POST 发送

<Note>
  默认情况下，URL 的大小限制为 1 MiB，可通过 `http_max_uri_size` 设置进行修改。
</Note>

如果成功，您将收到 200 响应码，结果包含在响应体中。
如果发生错误，您将收到 500 响应码，响应体中包含错误描述文本。

使用 GET 的请求为 &#39;readonly&#39;。这意味着对于修改数据的查询，只能使用 POST 方法。
查询本身既可以放在 POST 请求正文中发送，也可以放在 URL 参数中发送。下面来看一些示例。

在下面的示例中，使用 curl 发送查询 `SELECT 1`。请注意，空格使用了 URL 编码：`%20`。

```bash title="command"
curl 'http://localhost:8123/?query=SELECT%201'
```

```response title="Response"
1
```

在此示例中，wget 使用了 `-nv` (非详细模式) 和 `-O-` 参数，将结果输出到终端。
此时无需对空格进行 URL 编码：

```bash title="command"
wget -nv -O- 'http://localhost:8123/?query=SELECT 1'
```

```response
1
```

在此示例中，我们通过管道将一个原始 HTTP 请求传给 netcat：

```bash title="command"
echo -ne 'GET /?query=SELECT%201 HTTP/1.0\r\n\r\n' | nc localhost 8123
```

```response title="response"

X-ClickHouse-Summary: {"read_rows":"1","read_bytes":"1","written_rows":"0","written_bytes":"0","total_rows_to_read":"1","result_rows":"0","result_bytes":"0","elapsed_ns":"4505959","memory_usage":"1111711"}
```

如您所见，`curl` 命令用起来有些不便，因为空格必须进行 URL 转义。
虽然 `wget` 会自行转义所有字符，但我们不建议使用它，因为在 HTTP 1.1 下使用 keep-alive 和 Transfer-Encoding: chunked 时，它的表现不佳。

```bash
$ echo 'SELECT 1' | curl 'http://localhost:8123/' --data-binary @-
1

$ echo 'SELECT 1' | curl 'http://localhost:8123/?query=' --data-binary @-
1

$ echo '1' | curl 'http://localhost:8123/?query=SELECT' --data-binary @-
1
```

如果查询的一部分通过参数发送，另一部分通过 POST 发送，则会在这两部分数据之间插入一个换行符。
例如，以下写法将无法正常工作：

```bash
$ echo 'ECT 1' | curl 'http://localhost:8123/?query=SEL' --data-binary @-

ECT 1
```

如需使用其他格式，可在查询中使用 `FORMAT` 子句指定。例如：

```bash title="command"
wget -nv -O- 'http://localhost:8123/?query=SELECT 1, 2, 3 FORMAT JSON'
```


你可以使用 `default_format` URL 参数指定 `TabSeparated` 以外的默认格式。`X-ClickHouse-Format` 请求头用于显式指定响应的格式：它是 `output_format` 设置的别名，因此也会覆盖查询中的 `FORMAT` 子句。它不会影响 `INSERT` 请求体的解析方式——如需指定请求体的解析格式，请使用 `input_format` 或 `format`。若要恢复 26.8 之前版本的行为 (即该请求头是 `default_format` 的别名，且不会覆盖 `FORMAT` 子句) ，请禁用 `http_x_clickhouse_format_overrides_output_format` 设置 (可在用户配置文件中设置，也可作为 URL 参数传入；与各格式设置本身一样，该设置在只读模式下也可以更改) 。

```bash
$ echo 'SELECT 1 FORMAT Pretty' | curl 'http://localhost:8123/?' --data-binary @-
┏━━━┓

┡━━━┩

```

你可以通过 POST 方法执行参数化查询。参数使用花括号指定，括号内包含参数名称和类型，例如 `{name:Type}`。参数值通过 `param_name` 传递：

```bash
$ curl -X POST -F 'query=select {p1:UInt8} + {p2:UInt8}' -F "param_p1=3" -F "param_p2=4" 'http://localhost:8123/'

7
```

## 通过 URL 路径访问表并构造查询 {#tables-as-files}

适用于 ClickHouse 26.8 及更高版本。

HTTP 接口可以将 URL 路径解析为数据库、表、输出格式和压缩方法，再通过 URL 参数对结果进行调整，因此简单的读取请求无需编写 SQL。自 ClickHouse 26.10 起，这些功能默认启用；在 26.8 和 26.9 中则需要显式启用。

### 路径路由设置 {#enabling-path-routing}

路径解析受两个级别的控制：

1. 服务器级配置项 `http_allow_path_requests` 允许 HTTP 接口将路径样式请求路由到查询处理器。该配置项默认已启用；将其设为 `0` 后，凡是未配置为处理器的路径，都将恢复为返回 `404`：

```xml
<clickhouse>
    <http_allow_path_requests>0</http_allow_path_requests>
</clickhouse>
```

2. 以下用户级设置决定如何解释路由后的路径。除 `http_allow_filters_as_unrecognized_url_parameters` 外，其余设置均默认启用，并且每一项都可以按用户、角色或 profile 单独启用或禁用：

| 设置项                                                 | 作用                                                                |
| --------------------------------------------------- | ----------------------------------------------------------------- |
| `http_allow_table_as_file`                          | 将最后一个路径组件解释为 `table`、`table.format` 或 `table.format.compression`。 |
| `http_allow_database_as_path`                       | 将开头的 `/database/` 路径组件解释为当前数据库。                                   |
| `http_allow_filters_as_path`                        | 将 Hive 风格的 `/name=value/` 路径组件解释为 `WHERE` 过滤器。                    |
| `http_allow_filters_as_unrecognized_url_parameters` | 将无法识别的 URL 参数解释为 `WHERE` 过滤器。默认禁用。                                |

<Note>
  路由发生在身份验证之前，因此无法依赖用户级设置。禁用 `http_allow_path_requests` 时，未知路径会在身份验证前直接返回 `404`。完成路由和身份验证后，再由用户级设置决定如何解释该路径，因此可以针对特定用户、角色或 profile 有选择地启用或禁用此功能。
</Note>

<Note>
  `http_allow_filters_as_unrecognized_url_parameters` 默认处于禁用状态，因为它会作用于 HTTP 接口的所有请求，包括 `/?query=...` 端点：启用后，客户端追加的任何无法识别的 URL 参数都会变成查询的过滤器。这样一来，拼写错误的设置名称将不再报告 `UNKNOWN_SETTING`，而是以 `UNKNOWN_IDENTIFIER` 报错；如果该名称恰好与所查询表中的某一列同名，则会在没有任何提示的情况下对结果进行过滤。
</Note>

### 以文件形式访问表 {#table-as-file-examples}

启用 `http_allow_table_as_file` 后，对 `/table.format.compression` 的请求将按 `SELECT * FROM table` 处理。如果还启用了 `http_allow_database_as_path`，则还可以使用 `/database/table.format.compression`。

```bash
# SELECT * FROM my_db.hits, formatted as CSV
curl 'http://localhost:8123/my_db/hits.csv'

# The same result, compressed with gzip
curl 'http://localhost:8123/my_db/hits.csv.gz' | gzip -d
```

格式和压缩扩展名的识别不区分大小写，因此 `hits.csv` 与 `hits.CSV` 是等价的。

显式指定的 `format` 或 `output_format` URL 参数会覆盖路径中的格式。`default_format` 则不会：它仅在没有其他方式指定格式时提供默认格式，而路径扩展名更为具体，因此优先级更高。显式指定的 `compression` 参数必须与路径中的压缩方式一致；若两者冲突，则会抛出异常。

### 构造查询 {#query-construction}

以下设置会将基础查询包装为派生表。这些设置既可以相互组合，也可以与已有查询组合使用。您可以通过 HTTP URL 参数、查询中的 `SETTINGS` 子句或用户配置文件来指定这些设置。

| 设置项                                                                                                                         | 效果                                                                                               |
| --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `select`                                                                                                                    | `SELECT <expression_list> FROM (…)`                                                              |
| `filter`                                                                                                                    | 添加 `WHERE <expression>`。多个 `filter` URL 参数之间以 `AND` 组合。                                          |
| `order`                                                                                                                     | 添加 `ORDER BY <expression_list>`。                                                                 |
| `sort`                                                                                                                      | 根据以逗号分隔的标识符或列位置列表添加 `ORDER BY`，每一项均可带可选的 `+` (升序) 或 `-` (降序) 前缀，例如 `sort=a,-b`。不能与 `order` 同时使用。 |
| [`limit`](/zh/reference/settings/session-settings/other#limit) 和 [`offset`](/zh/reference/settings/session-settings/other#offset) | 添加 `LIMIT <n> OFFSET <m>`。两者均支持负值 (用于从末尾选取) 以及表示行数占比的小数值。                                        |
| `page`                                                                                                                      | 设置 `offset = limit * (page - 1)`。必须配合 `limit` 使用，且不能与 `offset` 同时使用。                             |

```bash
# Filter my_db.hits, sort by a descending, and return the first 10 rows
curl 'http://localhost:8123/my_db/hits?filter=a%3E0&sort=-a&limit=10'

# Return the second page of 100 rows
curl 'http://localhost:8123/my_db/hits?limit=100&page=2'
```

#### 修改现有查询 {#modify-an-existing-query}

查询构建设置并不局限于路径请求：它们同样会对您自行编写的查询起作用。该查询会成为派生表，因此这些设置作用于其结果，而不会被合并到查询中。例如，`?query=SELECT a, b FROM hits&filter=a > 0&sort=-b&limit=10` 的执行方式如下：

```sql
SELECT * FROM (SELECT a, b FROM hits) WHERE a > 0 ORDER BY b DESC LIMIT 10
```

如果查询已在其他位置固定，例如保存在仪表盘中的查询、`predefined_query_handler`，或只允许追加 URL 参数的客户端，就可以用这种方式对该查询的结果进行分页、排序或筛选：

```bash
# Page through the result of an arbitrary query without editing the query text
curl 'http://localhost:8123/?query=SELECT+a,+b+FROM+hits+GROUP+BY+a,+b&limit=100&page=3'

# Keep only some of the resulting columns and rows
curl -G 'http://localhost:8123/' --data-urlencode 'query=SELECT * FROM hits' --data-urlencode 'select=a, b' --data-urlencode 'filter=b != 0'

# The last 5 rows of an aggregate (a negative `limit` selects from the tail)
curl 'http://localhost:8123/?query=SELECT+a,+count()+FROM+hits+GROUP+BY+a+ORDER+BY+a&limit=-5'
```

由于这些设置是对查询进行包装而非重写，它们可以与 `FORMAT` 子句以及查询内部的 `ORDER BY` 配合使用，并且绝不会改变 `INSERT` 写入的行：放在 `INSERT ... SELECT` 语句上的查询构建设置只作用于该语句自身的 (空) 结果，而不会作用于其源 `SELECT`。若要作用于源查询，请将该设置放在该 `SELECT` 自身的 `SETTINGS` 子句中：

```sql
-- Inserts all 10 rows: `limit` applies to the INSERT statement, not to its SELECT
INSERT INTO t SETTINGS limit = 2 SELECT number FROM numbers(10);

-- Inserts 2 rows: `limit` applies to the SELECT itself
INSERT INTO t SELECT number FROM numbers(10) SETTINGS limit = 2;
```

<Warning>
  `filter` 并非访问控制机制。它会在外层包装的子查询上添加 `WHERE` 子句，因此在应用过滤器之前，底层数据仍可能被读取和处理。如需限制用户可访问的行，请使用[行策略](/zh/concepts/features/security/access-rights#row-policy-management)或 [`additional_table_filters`](/zh/reference/settings/session-settings/additional#additional_table_filters)。
</Warning>

### 覆盖格式与压缩 {#format-and-compression-overrides}

| 设置项              | 作用                                                                                                                                                                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `output_format`  | 覆盖输出格式。其优先级高于查询中的 `FORMAT` 子句、路径扩展名、`format` 和 `default_format`。也可以通过 `X-ClickHouse-Format` 请求头进行设置。当 `http_x_clickhouse_format_overrides_output_format = 0` 时，该请求头改为设置 `default_format`，与 26.8 之前版本的行为一致。 |
| `input_format`   | 覆盖 `INSERT` 的输入格式。其优先级高于查询中的 `FORMAT` 子句和 `format`。                                                                                                                                                        |
| `format`         | 同时覆盖输入和输出两个方向的格式，除非另行提供了针对特定方向的设置。                                                                                                                                                                         |
| `default_format` | 当查询中没有 `FORMAT` 子句、没有路径扩展名，也没有其他格式覆盖时，用于设置输出格式。                                                                                                                                                            |
| `compression`    | 压缩响应体，例如 `compression=gz`。它与 HTTP `Content-Encoding` 以及 ClickHouse 原生的 `compress` 参数相互独立。                                                                                                                  |

这些格式设置同样适用于其他协议，包括原生客户端和 `clickhouse-local`。`input_format` 和 `output_format` 分别对应 `--input-format` 和 `--output-format` 选项。在 `clickhouse-local` 中，`--format` 选项对应双向的 `format` 设置；而在 `clickhouse-client` 中，它沿用了历史上仅作用于输出的含义，对应 `output_format`。

`compression` 专用于 HTTP 响应的结果整形，并在查询执行之前即被消费。可通过 HTTP URL 参数、路径扩展名或用户配置文件提供该设置。若在查询内的 `SETTINGS` 子句中指定该设置，则会被拒绝。

二进制和已压缩的 HTTP 响应会包含 `Content-Disposition: attachment; filename=…` 请求头。文件名根据 URL 路径推导；若路径中未提供文件名，则使用 `result.<format>.<compression>`。

### 将路径指定的表与查询结合使用 {#implicit-table}

当路径标识了一张表，且您同时提供了 `query` 参数时，该路径指定的表会通过 [`implicit_table_at_top_level`](/zh/reference/settings/session-settings/implicit#implicit_table_at_top_level) 公开。不带 `FROM` 子句的 `SELECT` 会从该路径指定的表中读取数据：

```bash
# Read columns a and b from my_db.hits without a FROM clause
curl 'http://localhost:8123/my_db/hits.CSV?query=SELECT+a,+b'
```

如果查询中已包含 `FROM` 子句，则路径组件仅用于指定下载文件名。

### 向路径指定的表上传数据 {#path-table-inserts}

向 `/database/table.format` 发送 HTTP `PUT` 请求，可将请求体插入到已有的表中。默认情况下，输入格式由路径中的扩展名决定。与常规 `INSERT` 一样，`input_format` 设置的优先级高于路径中的格式，其次才是双向的 `format` 设置。请求必须包含至少一个已解码字节，且不得包含 `query` 参数。如果文件名中已同时包含目标表和输入格式，这种方式会非常方便：

```bash
printf '1,"one"\n2,"two"\n' \
  | curl -X PUT -H 'Content-Type: text/csv' --data-binary @- \
      'http://localhost:8123/my_db/hits.CSV'

printf '{"a":3,"b":"three"}\n' \
  | curl -X PUT -H 'Content-Type: application/json' --data-binary @- \
      'http://localhost:8123/my_db/hits.JSONEachRow'
```

目标表必须已存在。对于带数据库前缀的上传，`http_allow_database_as_path` 会启用
`/database/table.format` 路径。不带数据库限定的 `/table.format` 上传仍然需要
`http_allow_table_as_file`。请求体可以使用压缩后缀，例如 `.CSV.gz`；服务器会
先将其解压缩，再插入这些行。路径指定的表 `PUT` 上传采用普通的 `INSERT` 语义，因此重复发送
同一请求可能会导致这些行被再次插入。不支持自动建表、schema 推断和分段上传。如需自定义查询或上传行为，
请使用常规的[通过 HTTP 执行 `INSERT`](#insert-queries) 方式。

最后一个路径组件会在路径拆分之后进行百分号解码，因此像
`hits%2ECSV` 这样对格式前的点号进行编码的写法同样可被接受。

```bash
# The path suffix describes the compressed request body.
gzip -c rows.csv \
  | curl -X PUT --data-binary @- \
      'http://localhost:8123/my_db/hits.CSV.gz'
```

## 通过 HTTP/HTTPS 执行插入查询 {#insert-queries}

当需要显式提供查询时，传统的 `POST` 数据传输方式非常有用。您可以在 URL 参数中写入查询的开头部分，再通过 POST 传递要插入的数据。例如，要插入的数据可以是从 MySQL 导出的制表符分隔转储。这样一来，`INSERT` 查询便可替代 MySQL 中的 `LOAD DATA LOCAL INFILE`。

### 示例 {#examples}

创建表：

```bash
$ echo 'CREATE TABLE t (a UInt8) ENGINE = Memory' | curl 'http://localhost:8123/' --data-binary @-
```

如需使用熟悉的 `INSERT` 查询进行数据插入：

```bash
$ echo 'INSERT INTO t VALUES (1),(2),(3)' | curl 'http://localhost:8123/' --data-binary @-
```

如需将数据与查询分开发送：

```bash
$ echo '(4),(5),(6)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20VALUES' --data-binary @-
```

可以指定任意数据格式。例如，可以指定 &#39;Values&#39; 格式，它与 `INSERT INTO t VALUES` 语句中使用的数据格式相同：

```bash
$ echo '(7),(8),(9)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20Values' --data-binary @-
```

要从制表符分隔的转储文件中插入数据，请指定相应的格式：

```bash
$ echo -ne '10\n11\n12\n' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20TabSeparated' --data-binary @-
```

这一方法同样适用于其他任何[输入格式](/zh/reference/formats)，例如带表头的 CSV，或每行一个 JSON 对象：

```bash
$ echo -ne 'a\n13\n14\n' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20CSVWithNames' --data-binary @-
$ echo '{"a":15} {"a":16}' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20JSONEachRow' --data-binary @-
```

要插入文件内容，请在文件名前加上 `@` 前缀，然后传给 `--data-binary`：

```bash
$ echo -ne '17\n18\n' > data.csv
$ curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20CSV' --data-binary @data.csv
```

<Warning>
  请使用 `--data-binary`，而不是 `-d` (`--data`) 。curl 的 `-d @file` 会移除文件中的换行符，因此上面的两行会合并为单个值 `1718` 传入。
</Warning>

### 插入 Protobuf 数据 {#insert-protobuf}

[`Protobuf`](/zh/reference/formats/Protobuf/Protobuf) 等二进制格式也以相同方式发送，因为 `--data-binary` 会原样传递字节。
格式所需的设置 (例如 [`format_schema`](/zh/reference/settings/formats/format-schema#format_schema)) 与其他设置一样，作为 URL 参数与 `query` 一并传递。

以下示例使用该表以及模式文件 `message.proto`，该文件位于服务器的 [`format_schema_path`](/zh/reference/settings/server-settings/settings/format#format_schema_path) 目录中：

```bash
$ echo 'CREATE TABLE protobuf_messages (name String, surname String, birthDate UInt32, phoneNumbers Array(String)) ENGINE = Memory' | curl 'http://localhost:8123/' --data-binary @-
```

```protobuf
syntax = "proto3";

message MessageType {
  string name = 1;
  string surname = 2;
  uint32 birthDate = 3;
  repeated string phoneNumbers = 4;
}
```

为了准备一个包含待插入 Protobuf 消息的文件，本示例先让 ClickHouse 写入这样一个文件：

```bash
$ echo "SELECT 'Aisha' AS name, 'Khan' AS surname, 19920815 AS birthDate, ['(555) 247-8903', '(555) 612-3457'] AS phoneNumbers FORMAT Protobuf" | curl 'http://localhost:8123/?format_schema=message:MessageType' --data-binary @- > messages.bin
```

要插入该文件，请在 `format_schema` 中指定模式文件和消息类型：

```bash
$ curl 'http://localhost:8123/?query=INSERT%20INTO%20protobuf_messages%20FORMAT%20Protobuf&format_schema=message:MessageType' --data-binary @messages.bin
```

如果无法将模式文件放到服务器上 (例如在 ClickHouse Cloud 中) ，可以将 [`format_schema_source`](/zh/reference/settings/formats/format-schema#format_schema_source) 设置为 `string`，直接发送 schema 内容，并在 [`format_schema_message_name`](/zh/reference/settings/formats/format-schema#format_schema_message_name) 中指定消息类型的名称。
curl 的 `--url-query` 选项 (curl 7.87 及更高版本) 会对每个参数进行 URL 编码，因此查询和 schema 可以按原样书写：

```bash
$ curl 'http://localhost:8123/' \
    --url-query 'query=INSERT INTO protobuf_messages FORMAT Protobuf' \
    --url-query 'format_schema_source=string' \
    --url-query 'format_schema=syntax = "proto3"; message MessageType { string name = 1; string surname = 2; uint32 birthDate = 3; repeated string phoneNumbers = 4; }' \
    --url-query 'format_schema_message_name=MessageType' \
    --data-binary @messages.bin
```

读取表内容：

```bash
$ curl 'http://localhost:8123/?query=SELECT%20*%20FROM%20protobuf_messages'
Aisha	Khan	19920815	['(555) 247-8903','(555) 612-3457']
Aisha	Khan	19920815	['(555) 247-8903','(555) 612-3457']
```

`Protobuf` 要求每条消息都以 varint 编码的消息长度作为前缀。
如果是不带前缀的单条消息，请使用 [`ProtobufSingle`](/zh/reference/formats/Protobuf/ProtobufSingle)；如果各行作为同一个 `Envelope` 消息的子消息发送，请使用 [`ProtobufList`](/zh/reference/formats/Protobuf/ProtobufList)。

## 压缩 {#compression}

传输大量数据时，可以使用压缩来减少网络流量；也可以用它来创建直接以压缩形式保存的转储。

传输数据时，可以使用 ClickHouse 内部的压缩格式。已压缩的数据采用非标准格式，需要借助 `clickhouse-compressor` 程序进行处理。该程序默认随 `clickhouse-client` 软件包一同安装。

为提高数据插入效率，可以通过 [`http_native_compression_disable_checksumming_on_decompress`](/zh/reference/settings/session-settings/http#http_native_compression_disable_checksumming_on_decompress) 设置禁用服务端校验和验证。

如果在 URL 中指定 `compress=1`，服务器会压缩发送给您的数据。如果在 URL 中指定 `decompress=1`，服务器会解压缩您通过 `POST` 方法传入的数据。

您也可以选择使用 [HTTP 压缩](https://en.wikipedia.org/wiki/HTTP_compression)。ClickHouse 支持以下[压缩方法](https://en.wikipedia.org/wiki/HTTP_compression#Content-Encoding_tokens)：

* `gzip`
* `br`
* `deflate`
* `xz`
* `zstd`
* `lz4`
* `bz2`
* `snappy`

要发送已压缩的 `POST` 请求，请添加请求头 `Content-Encoding: compression_method`。

要让 ClickHouse 压缩响应，请在请求中添加 `Accept-Encoding: compression_method` 请求头。

对于所有压缩方法，均可使用 [`http_zlib_compression_level`](/zh/reference/settings/session-settings/http#http_zlib_compression_level) 设置来配置数据压缩级别。

<Info>
  某些 HTTP 客户端可能会默认解压缩来自服务器的数据 (使用 `gzip` 和 `deflate` 时) ，因此即使正确使用了压缩设置，您拿到的也可能是已解压的数据。
</Info>

## 示例 {#examples-compression}

向服务器发送已压缩的数据：

```bash
echo "SELECT 1" | gzip -c | \
curl -sS --data-binary @- -H 'Content-Encoding: gzip' 'http://localhost:8123/'
```

从服务器接收已压缩的数据归档文件：

```bash
curl -vsS "http://localhost:8123/?enable_http_compression=1" \
-H 'Accept-Encoding: gzip' --output result.gz -d 'SELECT number FROM system.numbers LIMIT 3'

zcat result.gz
0
1
2
```

从服务器接收已压缩的数据，并使用 gunzip 获取已解压的数据：

```bash
curl -sS "http://localhost:8123/?enable_http_compression=1" \
-H 'Accept-Encoding: gzip' -d 'SELECT number FROM system.numbers LIMIT 3' | gunzip -
0
1
2
```

## 在 HTTP 协议中使用 ClickHouse 会话 {#using-clickhouse-sessions-in-the-http-protocol}

你也可以在 HTTP 协议中使用 ClickHouse 会话。为此，需要在请求中添加 `session_id` `GET` 参数。会话 ID 可以是任意字符串。

默认情况下，会话在闲置 60 秒后终止。如需更改此超时时间 (单位为秒) ，请修改服务器配置中的 `default_session_timeout` 设置，或在请求中添加 `session_timeout` `GET` 参数。

要检查会话状态，请使用 `session_check=1` 参数。在单个会话中，同一时间只能执行一个查询。

你可以通过 `X-ClickHouse-Progress` 响应头获取查询的进度信息。为此，请启用 [`send_progress_in_http_headers`](/zh/reference/settings/session-settings/send#send_progress_in_http_headers)。

以下是请求头序列的示例：

```text
X-ClickHouse-Progress: {"read_rows":"261636","read_bytes":"2093088","total_rows_to_read":"1000000","elapsed_ns":"14050417","memory_usage":"22205975"}
X-ClickHouse-Progress: {"read_rows":"654090","read_bytes":"5232720","total_rows_to_read":"1000000","elapsed_ns":"27948667","memory_usage":"83400279"}
X-ClickHouse-Progress: {"read_rows":"1000000","read_bytes":"8000000","total_rows_to_read":"1000000","elapsed_ns":"38002417","memory_usage":"80715679"}
```

可能的请求头字段如下：

| 请求头字段                | 描述                                      |
| -------------------- | --------------------------------------- |
| `read_rows`          | 读取的行数。                                  |
| `read_bytes`         | 读取的数据量 (以字节为单位) 。                       |
| `total_rows_to_read` | 待读取的总行数。                                |
| `written_rows`       | 已写入的行数。                                 |
| `written_bytes`      | 已写入的数据量 (以字节为单位) 。                      |
| `elapsed_ns`         | 查询运行时长 (以纳秒为单位) 。                       |
| `memory_usage`       | 查询使用的内存量 (以字节为单位) 。 (**自 v25.11 起可用**)  |

即使 HTTP 连接断开，正在运行的请求也不会自动停止。解析和数据格式化均在服务端执行，因此利用网络状态来控制请求可能无效。

支持以下可选参数：

| 参数                | 描述                                                                                                                                  |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `query_id` (可选)   | 可作为查询 ID 传递 (任意字符串) 。参见 [`replace_running_query`](/zh/reference/settings/session-settings/replace-running-query#replace_running_query) |
| `quota_key` (可选)  | 可作为配额键传递 (任意字符串) 。参见[“配额”](/zh/concepts/features/configuration/server-config/quotas)                                                   |

HTTP 接口支持传递外部数据 (外部临时表) 用于查询。详情请参阅[“用于查询处理的外部数据”](/zh/reference/engines/table-engines/special/external-data)。

## 响应缓冲 {#response-buffering}

可以在服务端启用响应缓冲。为此提供了以下 URL 参数：

* `buffer_size`
* `wait_end_of_query`

也可以使用以下设置：

* [`http_response_buffer_size`](/zh/reference/settings/session-settings/http-response#http_response_buffer_size)
* [`http_wait_end_of_query`](/zh/reference/settings/session-settings/http#http_wait_end_of_query)

`buffer_size` 决定在服务器内存中缓冲的结果字节数。如果结果正文超过此阈值，缓冲区中的内容会被写入 HTTP 通道，剩余数据则直接发送到 HTTP 通道。

如需确保整个响应都被缓冲，请设置 `wait_end_of_query=1`。此时，未存储在内存中的数据将被缓冲到服务器上的临时文件中。

示例：

```bash
curl -sS 'http://localhost:8123/?max_result_bytes=4000000&buffer_size=3000000&wait_end_of_query=1' -d 'SELECT toUInt8(number) FROM system.numbers LIMIT 9000000 FORMAT RowBinary'
```

<Tip>
  使用缓冲可以避免这样一种情况：响应码和 HTTP 请求头已发送给客户端之后，才发生查询处理错误。此时，错误消息会写入响应体末尾，而客户端只能在解析阶段才能检测到该错误。
</Tip>

## 通过查询参数设置角色 {#setting-role-with-query-parameters}

此功能于 ClickHouse 24.4 中引入。

在某些场景下，可能需要先设置已授予的角色，再执行语句本身。
但由于不支持多语句，无法将 `SET ROLE` 与该语句一并发送：

```bash
curl -sS "http://localhost:8123" --data-binary "SET ROLE my_role;SELECT * FROM my_table;"
```

执行上述命令会报错：

```sql
Code: 62. DB::Exception: Syntax error (Multi-statements are not allowed)
```

要绕过这一限制，请改用 `role` 查询参数：

```bash
curl -sS "http://localhost:8123?role=my_role" --data-binary "SELECT * FROM my_table;"
```

这等价于在执行该语句之前先执行 `SET ROLE my_role`。

此外，还可以指定多个 `role` 查询参数：

```bash
curl -sS "http://localhost:8123?role=my_role&role=my_other_role" --data-binary "SELECT * FROM my_table;"
```

在这种情况下，`?role=my_role&role=my_other_role` 的效果类似于在执行该语句之前先执行 `SET ROLE my_role, my_other_role`。

`role` 查询参数不受 `access_control_improvements.readonly_restricts_set_role` 服务器设置的影响，该设置只会拒绝 `SET ROLE` 和 `SET DEFAULT ROLE` 语句。

## HTTP 响应码注意事项 {#http_response_codes_caveats}

由于 HTTP 协议本身的限制，即使返回 HTTP 200 响应码，也不能保证查询已成功执行。

示例如下：

```bash
curl -v -Ss "http://localhost:8123/?max_block_size=1&query=select+sleepEachRow(0.001),throwIf(number=2)from+numbers(5)"
*   Trying 127.0.0.1:8123...
...
< HTTP/1.1 200 OK
...
Code: 395. DB::Exception: Value passed to 'throwIf' function is non-zero: while executing 'FUNCTION throwIf(equals(number, 2) :: 1) -> throwIf(equals(number, 2))
```

出现这种行为的原因在于 HTTP 协议本身的特性。服务器会先发送状态码为 200 的 HTTP 请求头，随后发送 HTTP 请求正文，错误则以明文形式插入到请求正文中。

无论使用哪种格式 (`Native`、`TSV` 还是 `JSON`) ，这种行为都不会改变；错误消息始终会出现在响应流的中间。

您可以通过启用 `wait_end_of_query=1` ([响应缓冲](#response-buffering)) 来缓解此问题。此时，HTTP 请求头会延迟到整个查询处理完成后再发送。不过，这并不能彻底解决问题，因为结果仍需能够容纳在 [`http_response_buffer_size`](/zh/reference/settings/session-settings/http-response#http_response_buffer_size) 之内，而且 [`send_progress_in_http_headers`](/zh/reference/settings/session-settings/send#send_progress_in_http_headers) 等其他设置也可能会影响请求头的延迟发送。

<Tip>
  捕获所有错误的唯一方法，是在按所需格式解析 HTTP 请求正文之前，先对其进行分析。
</Tip>

当 `http_write_exception_in_output_format=0` (默认值) 时，无论使用哪种格式 (例如 `Native`、`TSV`、`JSON` 等) ，ClickHouse 中的此类异常都采用如下统一的异常格式，便于在客户端解析并提取错误消息。

```text
\r\n
__exception__\r\n
<TAG>\r\n
<error message>\r\n
<message_length> <TAG>\r\n
__exception__\r\n

```

其中 `<TAG>` 是一个 16 字节的随机标签，与 `X-ClickHouse-Exception-Tag` 响应头中发送的标签相同。
`<error message>` 是实际的异常消息 (其确切长度见 `<message_length>`) 。上述整个异常块最大可达 16 KiB。

以下是 `JSON` 格式的示例：

### 示例 {#example-3}

```bash
$ curl -sS "<address>?param_id=2&param_phrase=test" -d "SELECT * FROM table WHERE int_column = {id:UInt8} and string_column = {phrase:String}"
```

### URL 参数中的制表符 {#tabs-in-url-parameters}

查询参数按 &quot;escaped&quot; 格式解析。这样做有一些好处，例如可以将 `\N` 明确解析为空值。因此，制表符应编码为 `\t` (或 `\` 后跟一个制表符) 。例如，以下内容在 `abc` 和 `123` 之间包含一个实际的制表符，输入字符串会被拆分为两个值：

```bash
curl -sS "http://localhost:8123" -d "SELECT splitByChar('\t', 'abc      123')"
```

```response
['abc','123']
```

但是，如果您尝试在 URL 参数中用 `%09` 编码一个真正的制表符，该制表符将无法被正确解析：

```bash
curl -sS "http://localhost:8123?param_arg1=abc%09123" -d "SELECT splitByChar('\t', {arg1:String})"
Code: 457. DB::Exception: Value abc    123 cannot be parsed as String for query parameter 'arg1' because it isn't parsed completely: only 3 of 7 bytes was parsed: abc. (BAD_QUERY_PARAMETER) (version 23.4.1.869 (official build))
```

如果使用 URL 参数，需要将 `\t` 编码为 `%5C%09`。例如：

```bash
curl -sS "http://localhost:8123?param_arg1=abc%5C%09123" -d "SELECT splitByChar('\t', {arg1:String})"
```

```response
['abc','123']
```

## 预定义 HTTP 接口 {#predefined_http_interface}

ClickHouse 支持通过 HTTP 接口执行特定查询。例如，可以通过以下方式向表中写入数据：

```bash
$ echo '(4),(5),(6)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20VALUES' --data-binary @-
```

ClickHouse 还支持预定义 HTTP 接口，可帮助您更轻松地与 [Prometheus 导出器](https://github.com/ClickHouse/clickhouse_exporter)等第三方工具集成。下面来看一个示例。

这些处理程序也可以通过 SQL 定义，无需编辑服务器配置文件，参见 [`CREATE HANDLER`](/zh/reference/statements/create/handler)。

首先，将以下配置段添加到服务器配置文件中。

`http_handlers` 可配置多个 `rule`。ClickHouse 会将收到的 HTTP 请求与 `rule` 中的预定义类型进行匹配，并运行第一个匹配规则对应的处理器。匹配成功后，ClickHouse 将执行相应的预定义查询。

```yaml title="config.xml"
<http_handlers>
    <rule>
        <url>/predefined_query</url>
        <methods>POST,GET</methods>
        <handler>
            <type>predefined_query_handler</type>
            <query>SELECT * FROM system.metrics LIMIT 5 FORMAT Template SETTINGS format_template_resultset = 'prometheus_template_output_format_resultset', format_template_row = 'prometheus_template_output_format_row', format_template_rows_between_delimiter = '\n'</query>
        </handler>
    </rule>
    <rule>...</rule>
    <rule>...</rule>
</http_handlers>
```

`http_handlers` 的配置选项说明如下。

`rule` 支持配置以下参数：

* `method`
* `headers`
* `url`
* `full_url`
* `handler`

下文将逐一介绍这些参数：

* `method` 用于匹配 HTTP 请求的方法部分。`method` 完全遵循 HTTP 协议中 [`method`]
  (https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods) 的定义。这是一项可选配置。如果未在
  配置文件中定义，则不对 HTTP 请求的方法部分进行匹配。

* `url` 用于匹配 HTTP 请求的 URL 部分 (路径和查询字符串) 。
  如果 `url` 以 `regex:` 为前缀，则使用 [RE2](https://github.com/google/re2) 正则表达式进行匹配。
  这是一项可选配置。如果未在配置文件中定义，则不对 HTTP 请求的 URL 部分进行匹配。

* `full_url` 与 `url` 相同，但匹配的是完整 URL，即 `schema://host:port/path?query_string`。
  注意，ClickHouse 不支持“虚拟主机”，因此 `host` 是 IP 地址 (而不是 `Host` 请求头的值) 。

* `empty_query_string` - 确保请求中没有查询字符串 (`?query_string`)

* `headers` 用于匹配 HTTP 请求的请求头，支持 RE2 正则表达式。这是一项可选
  配置。如果未在配置文件中定义，则不对 HTTP 请求的请求头进行匹配。

* `handler` 包含主要处理逻辑。

  其 `type` 可以是以下值：

  * [`predefined_query_handler`](#predefined_query_handler)
  * [`dynamic_query_handler`](#dynamic_query_handler)
  * [`static`](#static)
  * [`redirect`](#redirect)

  还支持以下参数：

  * `query` — 与 `predefined_query_handler` 类型配合使用，在调用处理器时执行指定的查询。
  * `query_param_name` — 与 `dynamic_query_handler` 类型配合使用，从 HTTP 请求参数中提取以 `query_param_name` 的值为名称的参数值，
    并将其作为查询执行。
  * `status` — 与 `static` 类型配合使用，指定响应状态码。
  * `content_type` — 适用于任意类型，指定响应的[内容类型](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Type)。
  * `http_response_headers` — 适用于任意类型，指定响应头映射，也可用于设置内容类型。
  * `response_content` — 与 `static` 类型配合使用，指定发送给客户端的响应内容。使用前缀 &#39;file://&#39; 或 &#39;config://&#39; 时，会从文件或配置中读取内容
    并发送给客户端。
  * `user` - 执行查询所使用的用户 (默认为 `default`) 。
    **注意**，无需为此用户指定密码。

接下来将介绍不同 `type` 的配置方法。

### predefined_query_handler {#predefined_query_handler}

`predefined_query_handler` 支持设置 `Settings` 和 `query_params` 的值。您可以在 `predefined_query_handler` 类型中配置 `query`。

`query` 用于指定 `predefined_query_handler` 的预定义查询。当 HTTP 请求匹配时，ClickHouse 会执行该查询并返回查询结果。此项为必填配置。

以下示例设置了 [`max_threads`](/zh/reference/settings/session-settings/max-threads#max_threads) 和 [`max_final_threads`](/zh/reference/settings/session-settings/max#max_final_threads) 的值，然后查询系统表，检查这些设置是否生效。

<Note>
  要保留默认的 `handlers` (例如 ` query`、`play`、` ping`) ，请添加 `<defaults/>` 规则。
</Note>

例如：

```yaml
<http_handlers>
    <rule>
        <url><![CDATA[regex:/query_param_with_url/(?P<name_1>[^/]+)]]></url>
        <methods>GET</methods>
        <headers>
            <XXX>TEST_HEADER_VALUE</XXX>
            <PARAMS_XXX><![CDATA[regex:(?P<name_2>[^/]+)]]></PARAMS_XXX>
        </headers>
        <handler>
            <type>predefined_query_handler</type>
            <query>
                SELECT name, value FROM system.settings
                WHERE name IN ({name_1:String}, {name_2:String})
            </query>
        </handler>
    </rule>
    <defaults/>
</http_handlers>
```

```bash
curl -H 'XXX:TEST_HEADER_VALUE' -H 'PARAMS_XXX:max_final_threads' 'http://localhost:8123/query_param_with_url/max_threads?max_threads=1&max_final_threads=2'
max_final_threads    2
max_threads    1
```

#### 虚拟参数 `_request_body` {#virtual-param-request-body}

除了 URL 参数、请求头和查询参数之外，`predefined_query_handler` 还支持一个特殊的虚拟参数 `_request_body`。
它以字符串形式保存原始 HTTP 请求体。
该参数的值始终取自请求体：在 URL 中传递 `_request_body` (或 `param__request_body`) ，或通过 `url` 或 `headers` 正则表达式的命名捕获组捕获该参数，都会被拒绝并抛出异常。在命名会话中设置的 `_request_body` (`SET param__request_body = ...`) 会被忽略。
借助这一功能，您可以创建灵活的 REST API，接收任意格式的数据并在查询中进行处理。

例如，您可以使用 `_request_body` 实现一个 REST 端点，接收 POST 请求中的 JSON 数据并将其插入表中：

```yaml
<http_handlers>
    <rule>
        <methods>POST</methods>
        <url>/api/events</url>
        <handler>
            <type>predefined_query_handler</type>
            <query>
                INSERT INTO events (id, data)
                SELECT {id:UInt32}, {_request_body:String}
            </query>
        </handler>
    </rule>
    <defaults/>
</http_handlers>
```

然后，您可以向此端点发送数据：

```bash
curl -X POST 'http://localhost:8123/api/events?id=123' \
  -H 'Content-Type: application/json' \
  -d '{"user": "john", "action": "login", "timestamp": "2024-01-01T10:00:00Z"}'
```

<Note>
  每个 `predefined_query_handler` 仅支持一个 `query`。
</Note>

### dynamic_query_handler {#dynamic_query_handler}

在 `dynamic_query_handler` 中，查询通过 HTTP 请求参数传入；而在 `predefined_query_handler` 中，查询则写在配置文件中。可以在 `dynamic_query_handler` 中配置 `query_param_name`。

ClickHouse 从 HTTP 请求的 URL 中提取由 `query_param_name` 指定的参数值，并将其作为查询执行。`query_param_name` 的默认值为 `/query`。此配置项为可选项。如果配置文件中未定义此项，则不会传入该参数。

以下示例演示了如何使用此功能：设置 [`max_threads`](/zh/reference/settings/session-settings/max-threads#max_threads) 和 `max_final_threads` 的值，并通过 `queries` 查询设置是否生效。

示例：

```yaml
<http_handlers>
    <rule>
    <headers>
        <XXX>TEST_HEADER_VALUE_DYNAMIC</XXX>    </headers>
    <handler>
        <type>dynamic_query_handler</type>
        <query_param_name>query_param</query_param_name>
    </handler>
    </rule>
    <defaults/>
</http_handlers>
```

```bash
curl  -H 'XXX:TEST_HEADER_VALUE_DYNAMIC'  'http://localhost:8123/own?max_threads=1&max_final_threads=2&param_name_1=max_threads&param_name_2=max_final_threads&query_param=SELECT%20name,value%20FROM%20system.settings%20where%20name%20=%20%7Bname_1:String%7D%20OR%20name%20=%20%7Bname_2:String%7D'
max_threads 1
max_final_threads   2
```

### static {#static}

`static` 可以返回 [`content_type`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Type)、[状态](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status)和 `response_content`。`response_content` 可以返回指定的内容。

例如，要返回消息 &quot;打个招呼！&quot;：

```yaml highlight={14}
<http_handlers>
        <rule>
            <methods>GET</methods>
            <headers><XXX>xxx</XXX></headers>
            <url>/hi</url>
            <handler>
                <type>static</type>
                <status>402</status>
                <content_type>text/html; charset=UTF-8</content_type>
                <http_response_headers>
                    <Content-Language>en</Content-Language>
                    <X-My-Custom-Header>43</X-My-Custom-Header>
                </http_response_headers>
                <response_content>Say Hi!</response_content>
            </handler>
        </rule>
        <defaults/>
</http_handlers>
```

可以使用 `http_response_headers` 代替 `content_type` 来设置内容类型。

```yaml
<http_handlers>
        <rule>
            <methods>GET</methods>
            <headers><XXX>xxx</XXX></headers>
            <url>/hi</url>
            <handler>
                <type>static</type>
                <status>402</status>
                #begin-highlight
                <http_response_headers>
                    <Content-Type>text/html; charset=UTF-8</Content-Type>
                    <Content-Language>en</Content-Language>
                    <X-My-Custom-Header>43</X-My-Custom-Header>
                </http_response_headers>
                #end-highlight
                <response_content>Say Hi!</response_content>
            </handler>
        </rule>
        <defaults/>
</http_handlers>
```

### redirect {#redirect}

`redirect` 会通过 `302` 重定向到 `location`

例如，可以通过以下方式为 ClickHouse play 自动将用户设置为 `play`：

```xml
<clickhouse>
    <http_handlers>
        <rule>
            <methods>GET</methods>
            <url>/play</url>
            <handler>
                <type>redirect</type>
                <location>/play?user=play</location>
            </handler>
        </rule>
    </http_handlers>
</clickhouse>
```

## HTTP 响应头 {#http-response-headers}

ClickHouse 支持配置自定义 HTTP 响应头，并将其应用于任意可配置的处理器。您可以通过 `http_response_headers` 设置指定这些响应头，其值为表示响应头名称及对应值的键值对。此功能特别适合在整个 ClickHouse HTTP 接口中设置自定义安全响应头、实施 CORS 策略或满足其他 HTTP 请求头要求。

例如，您可以为以下端点或界面配置响应头：

* 常规查询端点
* 网页用户界面
* 健康检查。

您也可以指定 `common_http_response_headers`。这些响应头将应用于配置中定义的所有 HTTP 处理程序。

每个已配置的处理器返回的 HTTP 响应中都会包含这些响应头。

在以下示例中，服务器返回的每个响应都将包含两个自定义响应头：`X-My-Common-Header` 和 `X-My-Custom-Header`。

```xml
<clickhouse>
    <http_handlers>
        <common_http_response_headers>
            <X-My-Common-Header>Common header</X-My-Common-Header>
        </common_http_response_headers>
        <rule>
            <methods>GET</methods>
            <url>/ping</url>
            <handler>
                <type>ping</type>
                <http_response_headers>
                    <X-My-Custom-Header>Custom indeed</X-My-Custom-Header>
                </http_response_headers>
            </handler>
        </rule>
    </http_handlers>
</clickhouse>
```

## HTTP 流式传输期间发生异常时返回有效的 JSON/XML 响应 {#valid-output-on-exception-http-streaming}

通过 HTTP 执行查询时，可能在部分数据已发送后发生异常。通常，异常会以明文形式发送给客户端。
即使数据以特定格式输出，异常仍会以明文形式发送，导致输出不符合指定格式。
为避免这种情况，可以使用设置 [`http_write_exception_in_output_format`](/zh/reference/settings/session-settings/http#http_write_exception_in_output_format) (默认禁用) ，让 ClickHouse 以指定格式写入异常 (目前支持 XML 和 JSON* 格式) 。

示例：

```bash
$ curl 'http://localhost:8123/?query=SELECT+number,+throwIf(number>3)+from+system.numbers+format+JSON+settings+max_block_size=1&http_write_exception_in_output_format=1'
{
    "meta":
    [
        {
            "name": "number",
            "type": "UInt64"
        },
        {
            "name": "throwIf(greater(number, 2))",
            "type": "UInt8"
        }
    ],

    "data":
    [
        {
            "number": "0",
            "throwIf(greater(number, 2))": 0
        },
        {
            "number": "1",
            "throwIf(greater(number, 2))": 0
        },
        {
            "number": "2",
            "throwIf(greater(number, 2))": 0
        }
    ],

    "rows": 3,

    "exception": "Code: 395. DB::Exception: Value passed to 'throwIf' function is non-zero: while executing 'FUNCTION throwIf(greater(number, 2) :: 2) -> throwIf(greater(number, 2)) UInt8 : 1'. (FUNCTION_THROW_IF_VALUE_IS_NON_ZERO) (version 23.8.1.1)"
}
```
