ClickHouse 基于 [`TimeSeries`](/zh/reference/engines/table-engines/integrations/time-series) 表实现了 Prometheus HTTP API。同一个处理器即可处理远程写入、远程读取、PromQL 即时查询以及 PromQL 范围查询。

如需暴露 ClickHouse 自身的指标供 Prometheus 服务器抓取，请参阅 [Prometheus 指标端点](/zh/concepts/features/connect-to-clickhouse/prometheus/metrics)。

## 前置条件 {#prerequisites}

ClickHouse Cloud 与自管理 ClickHouse 的设置步骤有所不同，请根据您的部署方式参阅相应部分。

### ClickHouse Cloud {#prerequisites-cloud}

<Note>
  ClickHouse Cloud 中的 PromQL 支持目前处于私有预览阶段。参与私有预览的服务已预先配置好 `enable_time_series_table` 设置和 Prometheus API 端点。其他 ClickHouse Cloud 服务不具备此配置，您也无法在这些服务上自行启用该功能。后续章节中的 `SET enable_time_series_table` 语句和 `http_handlers` 配置仅适用于自管理部署。
</Note>

如果您的服务已参与私有预览，请直接跳转至[创建 TimeSeries 表](#create-a-timeseries-table)。该服务所提供的端点路径详见[端点表](#configure-prometheus-api)。

### 自管理：启用 TimeSeries 设置 {#enable-the-timeseries-setting}

为负责创建和访问该表的用户启用 `enable_time_series_table` 设置：

```sql
SET enable_time_series_table = 1;
```

对于 HTTP API 请求，请在 API 用户的 profile 中启用 `enable_time_series_table`。

### 自管理：配置 Prometheus API 端点 {#configure-prometheus-api}

在 ClickHouse 主 HTTP 端口上配置一个按前缀路由的处理器：

```xml
<http_handlers>
    <defaults/>
    <rule>
        <url_prefix>/prometheus/api/v1</url_prefix>
        <handler>
            <type>prometheus_api_v1</type>
        </handler>
    </rule>
</http_handlers>
```

`<defaults/>` 会保留 `/ping` 等端点以及 SQL 请求的内置处理程序。上述前缀通过单个处理器公开以下端点：

| 端点                                       | 用途              |
| ---------------------------------------- | --------------- |
| `/prometheus/api/v1/write`               | Prometheus 远程写入 |
| `/prometheus/api/v1/read`                | Prometheus 远程读取 |
| `/prometheus/api/v1/query`               | PromQL 即时查询     |
| `/prometheus/api/v1/query_range`         | PromQL 范围查询     |
| `/prometheus/api/v1/format_query`        | PromQL 表达式格式化   |
| `/prometheus/api/v1/series`              | 数据系列元数据         |
| `/prometheus/api/v1/labels`              | 标签名称            |
| `/prometheus/api/v1/label/<name>/values` | 标签值             |
| `/prometheus/api/v1/metadata`            | 指标族元数据         |
| `/prometheus/api/v1/federate`            | 最新 samples 的联邦  |

该示例未在处理器中指定 `database` 和 `table`。因此，每个请求都必须提供 `table` 查询参数 (`/format_query` 除外，它仅解析给定的 PromQL 表达式，无需指定表) 。请求还可以提供 `database`，或使用限定表名 (如 `prometheus.metrics`) ，也可以省略数据库，此时将使用 `default`。这样，一个处理器即可服务多个 `TimeSeries` 表。

如需让所有请求都使用同一张固定的表，请在处理器中进行配置：

```xml
<handler>
    <type>prometheus_api_v1</type>
    <database>prometheus</database>
    <table>metrics</table>
</handler>
```

在处理器中配置的表不能被请求参数覆盖。

路由和处理器设置：

| 名称           | 默认值  | 描述                                                                              |
| ------------ | ---- | ------------------------------------------------------------------------------- |
| `url_prefix` | none | 规则过滤器，匹配所有以所配置前缀开头的请求路径。                                                        |
| `table`      | none | `TimeSeries` 表的名称。若省略，则请求必须提供 `table` 查询参数。所配置的名称可以包含数据库名。                      |
| `database`   | none | 该表所在的数据库。请求可以通过查询参数提供此值。若省略，ClickHouse 将使用带限定名的 `table` 值中的数据库，否则回退到 `default`。 |

### 创建 TimeSeries 表 {#create-a-timeseries-table}

创建数据库和 `TimeSeries` 表：

```sql
CREATE DATABASE prometheus;
CREATE TABLE prometheus.metrics ENGINE = TimeSeries;
```

## 通过远程写入摄取指标 {#remote-write}

ClickHouse 支持 [Prometheus 远程写入协议](https://prometheus.io/docs/specs/remote_write_spec/)。配置 Prometheus，使其将数据写入该处理器：

```yaml
remote_write:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/write?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

Prometheus 会将 samples 发送到 `prometheus.metrics` 表。

为了将大量并发远程写入请求的数据合并为更少的 parts，ClickHouse 使用了[异步插入](/zh/reference/settings/session-settings/async-insert#async_insert)。该功能默认启用，可通过 URL (或用户配置文件) 中的 `async_insert` 设置开启或关闭。

无论 [`wait_for_async_insert`](/zh/reference/settings/session-settings/wait-for#wait_for_async_insert) 如何设置，ClickHouse 都只会在数据刷盘到 `TimeSeries` 表的所有内部表之后，才确认异步远程写入请求，因为远程写入协议将已确认的写入视为已持久化。如果刷写失败，请求会返回错误，Prometheus 会进行重试。

由于每个请求都要等待其刷写完成，异步插入会限制单个发送方的写入速度。Prometheus 在每个远程写入分片上一次只发送一个请求。当多个分片同时发送时，自适应刷写超时会逐步增长到 [`async_insert_busy_timeout_max_ms`](/zh/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms)，除非待处理请求先达到 [`async_insert_max_data_size`](/zh/reference/settings/session-settings/async-insert#async_insert_max_data_size)。请求会一直等待其所在批次完成刷写，而刷写最晚会在批次开始后经过上述时长才发生，因此在持续负载下，每个分片的写入速率约为 `samples per request / async_insert_busy_timeout_max_ms`，其中 Prometheus 默认每个请求最多发送 2,000 个 samples。如需提高该速率：

* 在 [`remote_write`](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write) 的 `queue_config` 中调高 `max_shards` (默认为 50) 或 `max_samples_per_send`。Prometheus 在处理滞后时会自动增加分片，最多可达 `max_shards`。
* 在 URL 或用户配置文件中调低 `async_insert_busy_timeout_max_ms`，例如 `&async_insert_busy_timeout_max_ms=50`。这样刷写会更频繁，但每次刷写都会在内部表中创建新的 parts。
* 使用 `async_insert=0` 禁用异步插入。这样每个请求都会在内部表中创建各自的 parts。

## 使用 PromQL 查询 {#promql-query-support}

使用即时查询端点，在单个时间点上对 PromQL 表达式求值：

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

使用范围查询端点，在指定时间范围内对表达式求值：

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

这些查询端点也支持通过表单请求正文传递参数。如果不加 `--get`，curl 会以 `POST` 方式、按 `application/x-www-form-urlencoded` 格式发送参数：

```bash
curl --user default:<password> \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

使用 format-query 端点解析并格式化 PromQL 表达式，但不对其求值：

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/format_query" \
  --data-urlencode "query=sum by(job)(http_requests_total{code=\"200\"})/2"
```

返回的表达式由已解析的查询序列化而来：空白字符经过归一化，注释被移除，多余的括号被删除，时长以解析器接受的单位输出：`sum by (job) (http_requests_total{code="200"}) / 2`。时长会保留原有单位，而不会转换为秒数，因此 `rate(x[5m])` 返回的仍是 `rate(x[5m])`；如果某个时长无法用单一单位的整数表示，则会拆分为所需的多个单位，因此 `rate(x[90s])` 返回的是 `rate(x[1m30s])`。此端点不会对表达式求值，因此无需提供 `database` 和 `table` 参数。

有关 HTTP API、`promql` 方言以及表函数所支持的函数和聚合运算符列表，请参阅[支持的 PromQL 功能](/zh/reference/functions/table-functions/prometheusQueryRange#supported-promql-features)。

其他请求参数会作为 ClickHouse 设置应用，例如 `max_execution_time=10`。查询端点还支持 VictoriaMetrics 和 Thanos 的部分参数：`nocache=1` 会设置 `use_query_cache=0`，`partial_response=false` 会设置 `skip_unavailable_shards=0`，而 `dedup=false`、`trace` 和 `round_digits` 会被忽略。对于 `extra_label` 和 `extra_filters`，查询端点会直接返回错误，因为 ClickHouse 不会应用这些筛选条件；`dedup=true` 和 `partial_response=true` 同样会被拒绝，因为 ClickHouse 未实现 Thanos 的去重和部分响应功能。

### Grafana {#grafana}

配置一个 Prometheus 数据源，并将其基准 URL 设置为 `/api/v1` 之前的部分：

```yaml
apiVersion: 1
datasources:
  - name: ClickHouse Prometheus
    type: prometheus
    access: proxy
    url: https://clickhouse.example.com:8443/prometheus
    basicAuth: true
    basicAuthUser: default
    jsonData:
      httpMethod: POST
      customQueryParameters: database=prometheus&table=metrics
    secureJsonData:
      basicAuthPassword: <password>
```

Grafana 会将 `/api/v1/query` 或 `/api/v1/query_range` 追加到此基准 URL 之后，并在每个请求中添加 `customQueryParameters`。

设置 `httpMethod: POST` 后，Grafana 会通过请求体发送查询参数。ClickHouse 会同时读取请求体和 URL 查询字符串，因此 `customQueryParameters` 依然生效。由于 URL 有长度限制，PromQL 表达式较长时请使用 `POST`。

<Note>
  目前仅实现了以下端点：查询端点 `/api/v1/query`、`/api/v1/query_range` 和 `/api/v1/format_query`；元数据端点 `/api/v1/series`、`/api/v1/labels`、`/api/v1/label/<name>/values` 和 `/api/v1/metadata`；以及[联邦](#federation)端点 `/api/v1/federate`。`/api/v1/series` 要求至少提供一个 `match[]` 数据系列选择器，支持可选参数 `start`、`end` 和 `limit`，并返回各选择器所匹配数据系列的并集。`/api/v1/labels` 接受相同的参数 (其中 `match[]` 为可选) ，返回所匹配数据系列的已排序标签名称 (未提供选择器时，则返回所有数据系列的标签名称) 。`/api/v1/label/<name>/values` 接受与 `/api/v1/labels` 相同的参数，返回单个标签的已排序值；若标签名称包含 `[a-zA-Z0-9_]` 以外的字符，`<name>` 可使用 Prometheus 的 `U__...` 转义形式。这些端点涵盖了 Grafana Prometheus 数据源在标签浏览、模板变量和查询构建器自动补全中所需的全部功能。
</Note>

### SQL 入口点 {#sql-entry-points}

ClickHouse 的 HTTP API、`promql` 方言以及 [`prometheusQuery`](/zh/reference/functions/table-functions/prometheusQuery) 和 [`prometheusQueryRange`](/zh/reference/functions/table-functions/prometheusQueryRange) 表函数均使用同一个 PromQL 转换器。

使用 `clickhouse-client` 直接运行 PromQL：

```bash
clickhouse-client \
  --dialect promql \
  --promql_database prometheus \
  --promql_table metrics \
  --query 'rate(http_requests_total[5m])'
```

使用表函数将 PromQL 嵌入 SQL 查询：

```sql
SELECT *
FROM prometheusQuery(
    prometheus.metrics,
    'rate(http_requests_total[5m])',
    now()
);
```

## 查询指标元数据 {#metadata}

`/prometheus/api/v1/metadata` 端点返回存储在 `TimeSeries` 表的 `Metrics` target table 中的指标元数据，即每个指标族的类型、帮助文本和单位。该端点支持在 URL 查询字符串中使用以下 Prometheus 参数：

| 参数                 | 描述                              |
| ------------------ | ------------------------------- |
| `metric`           | 仅返回该指标族的元数据。                    |
| `limit`            | 限制返回的指标族数量。负值表示不限制；为零时不返回任何指标族。 |
| `limit_per_metric` | 限制每个指标族返回的元数据对象数量。零或负值表示不限制。    |

默认的 `Metrics` target table 是一个按指标族名称排序的 `ReplacingMergeTree`，它为每个指标族保留最近写入的元数据条目。只有当 target table 中实际存储了同一指标族的多个条目时，才会返回多个条目，即在其 parts 合并之前，或者该表使用了会保留这些条目的引擎时。

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/metadata" \
  --data-urlencode "metric=http_requests_total" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

## 指标联邦 {#federation}

ClickHouse 支持 [Prometheus 联邦](https://prometheus.io/docs/prometheus/latest/federation/)端点，路径为 `/prometheus/api/v1/federate` (也可以是任何以 `/federate` 结尾、由类型为 `query` 的处理器提供服务的路径) 。对于 `match[]` 选择器匹配到的每个数据系列，该端点会以 Prometheus 文本格式返回其最近 5 分钟内的最新样本，供 Prometheus 服务器抓取：

```yaml
scrape_configs:
  - job_name: clickhouse-federate
    honor_labels: true
    scheme: https
    metrics_path: /prometheus/api/v1/federate
    params:
      'match[]': ['{job="node"}']
      table: ['prometheus.metrics']
    static_configs:
      - targets: ['clickhouse.example.com:8443']
```

## 通过远程读取获取指标 {#remote-read}

ClickHouse 在 `/prometheus/api/v1/read` 端点上支持 [Prometheus 远程读取协议](https://prometheus.io/docs/prometheus/latest/querying/remote_read_api/)。

配置 Prometheus 服务器，使其从同一个 `TimeSeries` 表中读取数据：

```yaml
remote_read:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/read?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

## 记录规则 {#recording-rules}

ClickHouse 不会对 Prometheus 规则文件进行求值。[可刷新materialized view](/zh/reference/statements/create/view#refreshable-materialized-view) 可以实现[记录规则](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/)的功能：它按照调度计划对 PromQL 表达式求值，并将结果追加到 `TimeSeries` 表中。以下视图每分钟将 `sum by (job) (rate(http_requests_total[5m]))` 记录为 `job:http_requests:rate5m`：

```sql
CREATE MATERIALIZED VIEW prometheus.job_http_requests_rate5m
REFRESH EVERY 1 MINUTE APPEND TO prometheus.metrics (tags, samples) AS
SELECT
    mapUpdate(CAST(tags, 'Map(String, String)'), map('__name__', 'job:http_requests:rate5m')) AS tags,
    [(timestamp, value)] AS samples
FROM prometheusQuery(prometheus.metrics, 'sum by (job) (rate(http_requests_total[5m]))', toStartOfMinute(now()));
```

每次刷新都会在当前分钟的起始时刻对表达式求值，通过 `mapUpdate` 设置指标名称，并为结果中的每个数据系列追加一个样本。还可以在同一个 Map 中添加额外标签，例如 `map('__name__', 'job:http_requests:rate5m', 'team', 'web')`。记录下来的数据系列可以像其他任何指标一样查询：

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=job:http_requests:rate5m" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

最近一次求值的时间和错误记录在 [`system.view_refreshes`](/zh/reference/system-tables/view_refreshes) 中。

视图与 Prometheus 记录规则有以下几点不同：

* 求值时间为刷新执行时的 `now()`。除按调度计划刷新外，视图还会在以下情况下刷新：创建后立即刷新 (除非使用 `EMPTY` 创建) ；如果其刷新不是协调式的，则在服务器重启后刷新 (位于 Replicated 或 Shared 数据库之外的视图，或设置了 `all_replicas = 1` 的视图，不会记住其上次刷新) ；以及错过某次调度刷新后，通过 `SYSTEM START VIEW` 恢复时刷新。请像示例那样将 `now()` 向下取整到时间间隔，以免这些刷新在两次调度刷新之间写入额外的样本。即便如此，额外的刷新仍可能在同一个取整后的时间戳上写入第二个样本。对于五分钟的规则，请使用 `toStartOfInterval(now(), INTERVAL 5 MINUTE)`。
* 错过的求值不会补算。服务器宕机或视图停止后，视图只会对当前时间间隔求值，之前的时间间隔将保持为空。刷新耗时超过时间间隔时，也会出现同样的情况。
* 从结果中消失的数据系列不会被打上陈旧标记，因此在回溯期内 (默认 5 分钟) ，查询仍会返回其最后记录的值。
* 没有规则文件：每条规则都是一个独立的视图。`/api/v1/rules` 也不会列出这些规则。
