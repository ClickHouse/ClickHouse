`clickhousectl` (别名 `chctl`) 是 ClickHouse 的官方命令行客户端，覆盖从本地开发到 ClickHouse Cloud 的全流程。无论是在终端中直接操作的用户，还是脚本和编程智能体，都可以使用它。

使用 `clickhousectl`，您可以：

* 安装并切换本地 ClickHouse 版本、运行相互隔离的本地服务器，以及执行 SQL
* 在本地运行基于 Docker 的 Postgres
* 创建、配置、扩缩容、备份和查询 ClickHouse Cloud 服务
* 创建、监控、配置和恢复 [ClickHouse Managed Postgres](/zh/products/managed-postgres/overview) 服务
* 创建并运维以对象存储、Kafka、Kinesis、Pub/Sub、Postgres、MySQL、MongoDB 和 BigQuery 为数据源的 ClickPipes
* 管理 [托管 ClickStack](/zh/clickstack/deployment/managed) 服务上的数据源、仪表盘、告警、Webhook、保存的搜索和角色
* 在本地开发可执行用户定义函数，并将其部署到 ClickHouse Cloud
* 管理组织成员、邀请、API 密钥和角色
* 将官方 ClickHouse agent skills 安装到编程智能体中

本页仅列出典型示例。所有命令和标志均以 `clickhousectl <command> --help` 的输出为准。大多数命令的帮助信息末尾都附有 `CONTEXT FOR AGENTS` 块；对于 Cloud 命令，该部分还会列出所需的 API key 权限。如需了解具体任务的操作步骤，请参阅各节中的指南链接。如需了解面向 Cloud 的概览，请参阅 [ClickHouse 命令行客户端](/zh/products/cloud/features/cli)。

## 安装 {#installation}

`clickhousectl` 支持 MacOS 和 Linux 系统，适用于 ARM64 和 x86&#95;64 架构。

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

该脚本会安装 `~/.local/bin/clickhousectl`，并创建 `chctl` 别名。请确保 `~/.local/bin` 已添加到 `PATH` 中。

你也可以通过包管理器安装：

| 工具                        | 命令                              |
| ------------------------- | ------------------------------- |
| npm                       | `npm install -g clickhousectl`  |
| uv                        | `uv tool install clickhousectl` |
| pipx                      | `pipx install clickhousectl`    |
| pip                       | `pip install clickhousectl`     |
| cargo-binstall            | `cargo binstall clickhousectl`  |
| Cargo，从源码构建 (Rust 1.94+)  | `cargo install clickhousectl`   |

只有安装脚本和 npm 会创建 `chctl` 别名。如需更新已安装的版本，请运行 `clickhousectl update` (参见[自更新](#self-update)) 。

## 前提条件 {#requirements}

* Docker (仅在使用本地 Postgres 时需要)
* 如需使用 Cloud 命令，需要一个 [ClickHouse Cloud](https://clickhouse.com/cloud) 账户。只读类命令可通过浏览器 OAuth 登录 (`cloud auth login`) 后使用；创建或修改资源则需要 [API key](/zh/products/cloud/features/admin-features/api/openapi)。请参阅[身份验证](#authentication)。

## 本地 {#local}

本地命令作用于当前目录。每个项目的服务器数据保存在 `.clickhouse/` 中，而 ClickHouse 二进制文件则全局共享，统一存放在 `~/.clickhouse/` 中。命令行客户端不会向上级目录查找，因此请在项目根目录下运行本地命令。完整工作流请参阅[本地开发指南](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md)。

### 安装并选择版本 {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
```

| 选择器           | 含义                                          |
| ------------- | ------------------------------------------- |
| `latest`      | 最新的 ClickHouse 构建版本，每次安装、使用或启动时都会远程检查 (推荐)  |
| `stable`      | 最新的稳定版本                                     |
| `lts`         | 最新的长期支持版                                    |
| `26.8`        | 与之匹配的最新发行版                                  |
| `26.8.1.1760` | 精确版本                                        |

`local use` 会在需要时安装该版本，将其设为今后启动服务器时使用的默认版本，并为其创建指向 `~/.local/bin/clickhouse` 的符号链接，使 `clickhouse client` 和 `clickhouse local` 可通过 `PATH` 直接调用。传入 `--no-global` 可跳过创建符号链接。如果该路径下已存在普通文件，则保持原样，不做改动。

`local remove` 不允许删除默认版本，也不允许删除任何项目中正在运行的服务器所使用的版本。使用 `--force` 会停止这些服务器并删除该版本，同时清除默认版本设置和符号链接。

### 初始化项目 {#initializing-project}

```bash
clickhousectl local init
```

`init` 为可选步骤。它会创建一个被 git 忽略的 `.clickhouse/` 目录，用于存放运行时数据，同时生成可提交到版本库的 SQL 脚手架：`clickhouse/` (`tables/`、`materialized_views/`、`queries/`、`seed/`、`udfs/`) 和 `postgres/` (`tables/`、`views/`、`functions/`、`queries/`、`seed/`) 。重复运行该命令时，只会补建缺失的部分。

### 运行本地服务器 {#managing-servers}

```bash
clickhousectl local server start dev --version latest   # Background start; waits for readiness
clickhousectl local server start dev --no-wait          # Return after spawning
clickhousectl local server start dev --foreground       # Run in the foreground
clickhousectl local server start dev --http-port 8124 --tcp-port 9001
clickhousectl local server list                         # Servers in this project
clickhousectl local server list --global                # Servers across all projects
clickhousectl local server stop dev
clickhousectl local server stop-all                     # Stop all ClickHouse and Postgres servers in this project
clickhousectl local server remove dev                   # Permanently delete a stopped server's data
```

每个命名服务器的数据都单独存放在 `.clickhouse/servers/<name>/data/` 中，停止服务器后数据会保留，供下次启动时使用。若未指定名称，第一个服务器名为 `default`；如果 `default` 已在运行，则会自动生成一个新名称。默认端口为 HTTP 8123 和 TCP 9000，若这些端口已被占用，则会自动分配空闲端口。

`--version` 用于指定本次启动所用的版本，不会更改默认版本。如果直接启动时既未指定版本，也未设置默认版本，则会安装 `latest`，但不会将其设为默认版本；如需将其设为默认版本，请先运行 `local use latest`。

### 使用本地客户端运行 SQL {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` 会使用运行该服务器的同一个 ClickHouse 二进制文件，连接到指定名称的服务器 (默认名称：`default`) 。`--` 之后的参数会原样传递给 `clickhouse client`。输出和退出状态均来自 `clickhouse client`，即使在 JSON 模式下也是如此，因此在脚本中使用时，请自行设置 SQL 输出格式。

### 自定义服务器配置 {#custom-config-files}

将包含部分配置项的 XML 或 YAML config 文件放入 `~/.clickhouse/configs/`，然后在启动服务器时按名称选用该配置：

```bash
mkdir -p ~/.clickhouse/configs
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local server configs
clickhousectl local server stop dev
clickhousectl local server start dev --config analytics
```

该文件会叠加在内置默认值之上，因此只需包含你要修改的设置。此选择不会被保留：之后若不带 `--config` 启动，覆盖文件将被移除。托管的数据路径和端口始终优先于 config 中的配置值。

### 将连接详情写入 dotenv 文件 {#dotenv}

```bash
clickhousectl local server dotenv dev                                     # Writes .env
clickhousectl local server dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` 会读取当前运行中的服务器的实际端口，并写入 `CLICKHOUSE_HOST`、`CLICKHOUSE_PORT` 和 `CLICKHOUSE_HTTP_PORT`；如果传入了用户、密码和数据库，也会一并写入。已有文件中的其他行将保持不变。请使用应用程序自带的 dotenv 加载器加载该文件；切勿对输出的预览内容执行 `eval`。

### 本地 Postgres {#local-postgres}

本地 Postgres 运行在 Docker 中，因此需要确保 Docker 正在运行。支持 Postgres 17 和 18，包括 `18-alpine` 等镜像标签；新实例默认使用 18。

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres stop app
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

实例通过名称和主版本来标识。恢复已停止的实例时，会沿用其原有的端口、用户、密码和数据库，因此创建时传入的标志对恢复操作无效。如未显式指定密码，系统将自动生成一个随机密码。`.env.local` 中包含该密码，请勿将其纳入版本控制。

### 本地 UDFs {#local-udfs}

`local udf` 会将 `clickhouse/udfs/<name>/` 下的[可执行用户定义函数](/zh/reference/functions/regular-functions/udf#executable-user-defined-functions)部署到本地服务器，而 `cloud udf` 则会将同一目录上传到 Cloud (参见 [Cloud 中的 UDFs](#cloud-udfs)) 。

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local server start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

除 `init` 外，所有命令都支持 `--server <name>` 参数 (默认值为 `default`) 。`deploy` 会采用与 Cloud 相同的方式验证 `udf.json`。如果服务器正在运行，它会重新加载函数，并确认该函数已成功加载。`native` 运行时仅支持在 Linux amd64 或 arm64 主机上本地部署。请参阅[用户自定义函数指南](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)。

## 身份验证 {#authentication}

Cloud 命令支持以下两种凭证类型：

| 凭证        | 能力                                          | 存储                                            |
| --------- | ------------------------------------------- | --------------------------------------------- |
| 浏览器 OAuth | 以您的用户身份执行操作：可在您所属的所有组织中执行只读 Cloud 操作和只读 SQL | `~/.clickhouse/tokens.json`，全局存储，在各项目间共享      |
| API key   | 作用域限定为单个组织；读写权限取决于该 key 所分配的角色              | 保存后位于 `.clickhouse/credentials.json`，仅作用于当前项目 |

如果您还没有 ClickHouse Cloud 账户，`clickhousectl cloud auth signup` 会在浏览器中打开注册页面。

### OAuth 登录 {#oauth-login}

```bash
clickhousectl cloud auth login
```

这会打开浏览器，通过 OAuth device flow 进行身份验证。令牌会全局保存到 `~/.clickhouse/tokens.json`，并自动刷新。

<Note>
  OAuth 访问仅为 **只读**。如需创建或更改资源，请使用 [API key](#api-key) 登录。
</Note>

### API key {#api-key}

[创建一个 API key](/zh/products/cloud/features/admin-features/api/openapi)，为其分配命令所需的角色，然后保存。使用交互式提示输入，可避免密钥被记录到 shell 历史记录中：

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

登录时会校验该密钥，并输出其所属的身份。被 API 拒绝的密钥不会被保存，且命令以退出码 4 退出。如果无法访问 API，密钥仍会被保存，但会输出一条警告。

在 CI 及其他自动化场景中，请通过您的密钥管理器注入密钥，而不要将其保存到本地：

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

在开发环境中，命令行客户端还会从当前目录下的 `.env` 文件中读取这些变量。请勿将 `.env` 文件纳入版本控制。

### 检查并清除凭证 {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` 支持任一类型的凭证；如果凭证被拒绝，则以退出码 4 退出。即使所有凭证均无效，`status` 也可能返回退出码 0，因此请使用 `whoami` 来测试访问权限。注销不会清除环境变量，也不会修改 `.env`。

### 凭证优先级 {#credential-precedence}

系统按以下顺序查找凭证，使用第一个可用的来源：

1. `--api-key` 和 `--api-secret` 标志
2. `.clickhouse/credentials.json`
3. 已导出的环境变量
4. 当前目录下 `.env` 文件中的变量
5. 全局 OAuth 令牌

为任意 `cloud` 命令加上 `--debug`，即可将所选的凭证来源和 API URL 输出到 stderr：

```bash
clickhousectl cloud service list --debug
```

### 选择组织 {#organizations}

对于组织级别的命令，仅当你的凭证恰好只能访问一个组织时，才会自动选择该组织。否则，请传入 `--org-id`，或传入 `--org-name` 并指定完整准确的组织名称：

```bash
clickhousectl cloud org list
clickhousectl cloud service list --org-id <org-id>
clickhousectl cloud service list --org-name "My Org"
```

大多数资源命令接受一个位置参数 ID 或精确的 `--name`。有关权限、受限 API 密钥以及登出清理的说明，请参阅[身份验证与访问](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md)。

## Cloud {#cloud}

Cloud 命令会调用 [ClickHouse Cloud API](/zh/products/cloud/features/admin-features/api/api-overview)。创建和更新请求在被 API 接受后即会返回，因此请轮询 `get`，直到资源达到所需状态。

### 服务 {#services}

```bash
clickhousectl cloud service create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud service list
clickhousectl cloud service get <service-id>
clickhousectl cloud service start <service-id>
clickhousectl cloud service stop <service-id>
clickhousectl cloud service wake <service-id>             # Wake an idle service
clickhousectl cloud service reset-password <service-id>
clickhousectl cloud service delete <service-id>           # Must be stopped; --force stops it first
```

请保存创建时显示的初始密码，该密码仅返回一次。创建命令会在预配完成前返回，因此请反复执行 `get`，直到状态变为 `running`。**省略 `--ip-allow` 将允许所有 IP (`0.0.0.0/0`) 访问。** 条目格式为 `IP_OR_CIDR=DESCRIPTION`。使用 `--backup-id` 可将备份恢复到新服务中，使用 `--byoc-id` 可将服务部署到 BYOC 基础设施中。

更新、扩缩容和配置服务：

```bash
clickhousectl cloud service update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud service profile list --region us-east-1
clickhousectl cloud service scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud service scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud service settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud service upgrade-window set <service-id> --weekday 0 --start-hour 6
```

每个副本的内存须为 4 GB 的整数倍，未付费服务最高 120 GB，付费服务最高 356 GB，副本数最多 50 个。组织和仓库层面的限制可能会使这些上限更低。横向自动扩缩容需要先为组织启用对应功能。`update` 只会更改你传入的标志。

其他服务命令组包括 `settings` (list、get、schema、set、unset) 、`scaling-schedule`、`upgrade-window`、`replica-aware-routing` (Beta) 、`snapshot` (Beta) 、`private-endpoint`、`backup-config` 和 `prometheus`。请参阅[创建和运维 云服务](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md)。

### 查询 API {#query-api}

`cloud service query` 通过 HTTP 执行单条 SQL 语句，既不需要本地 `clickhouse` 二进制文件，也不需要服务密码：

```bash
clickhousectl cloud service query <service-id> --query "SELECT version()"
clickhousectl cloud service query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud service query <service-id>
```

* **OAuth** 以您的身份运行查询，仅具有只读 SQL 访问权限，不会向服务绑定任何内容。
* **API key：** 首次调用时，clickhousectl 会将您的 API key 添加到该服务的查询 API 端点；如果端点尚不存在，则会以 `sql_console_admin` 角色创建该端点。现有的角色、来源及其他 key 绑定均会保留，也不会创建新的 key。命令行客户端更改该端点时，会向 stderr 输出 `Binding the authenticated API key to the Query API endpoint for service '<name>'...`。如需在这种情况下直接报错，请传入 `--no-auto-enable`。

对于由早期版本命令行客户端保存了服务专属 key 的服务，该 key 仍具有更高的优先次序。如果 API 拒绝该 key，可使用 `cloud service repair-query-key <service-id>` 显式将其替换。

查询 API 每个请求仅接受一条语句。请求可能在约 30 秒后超时，但 SQL 仍会继续执行，因此在重试写入操作之前，请先检查结果。对于多语句脚本、批量加载和长时间运行的查询，请使用 `clickhouse client`。服务 IP 允许列表仅限制直接连接，不限制经代理的查询 API 路由。查询处于空闲状态的服务会将其唤醒；已停止的服务则必须先使用 `cloud service start` 启动。

管理服务的查询 API 端点、命名 SQL 端点和已保存的查询：

```bash
clickhousectl cloud service query-endpoint get <service-id>
clickhousectl cloud service query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` 会替换绑定到该端点的所有密钥的角色。请参阅 [SQL 与查询 API 行为](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md)。

### Managed Postgres {#postgres-services}

`cloud postgres` 用于管理 [ClickHouse Managed Postgres](/zh/products/managed-postgres/overview)。这些命令目前处于 Beta 阶段，对 GCP 的支持则处于私有预览阶段。

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

AWS 规格包括 `m6gd.large`、`c6gd.xlarge` 和 `r6gd.xlarge`。在 GCP 上，请传入 `--provider gcp`，并指定 GCP 区域以及 `c4-standard-lssd-4` 等规格。

请妥善保存 `create` 返回的密码和连接字符串。此后的 `get` 响应均不会返回凭证，如需新凭证，只能通过 `reset-password` 获取。使用 `psql` 连接时，请指定 `sslmode=verify-full` 和 CA 文件。

**如果在创建时未指定访问控制标志，Postgres (5432) 和 PgBouncer (6432) 将对所有 IPv4 和 IPv6 地址开放访问。** 每条规则需传入一个 `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]`；如不设置任何规则，请传入 `--block-public-access`。一旦传入规则，便只有所列规则生效。

监控与恢复：

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` 仅支持 OAuth，因此当优先级更高的 API key 来源处于活跃状态时，该命令会执行失败。`metrics`、`slow-queries` 和 `prometheus` 用于监控。`restore` 会将源服务当前的 IPv4 访问规则复制到恢复后的服务上，除非您传入 `--ip-allow` 或 `--block-public-access`。恢复和创建副本操作的返回结果中不包含密码。`promote` 和 `switchover` 在请求被接受后即返回；执行 promote 后，请轮询 `postgres get --json`，直到副本报告 `isPrimary: true`。详见 [Managed Postgres 指南](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md)。

### ClickPipes {#clickpipes}

`cloud clickpipe` 可从对象存储、Kafka、Kinesis、Pub/Sub、Postgres、MySQL、MongoDB 和 BigQuery 摄取数据。创建管道和执行模式发现均需要 API key 以及一个正在运行的目标服务。每种数据源都有对应的 `clickpipe create <source>` 子命令；加上 `--help` 运行该子命令，即可查看其支持的标志。

通过 IAM role 从 S3 加载文件。先发现 schema，再选择所需的列：

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN"
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --column 'event_id:Int64' --column 'event_type:String'
```

使用 CDC (变更数据捕获) 复制 Postgres。TLS 默认会进行验证；如果是 Managed Postgres 数据源，请导出其 CA 证书并传入：

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud service query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` 会创建 `ReplacingMergeTree` 表，因此读取当前状态时请使用 `FINAL WHERE _peerdb_is_deleted = 0`。Kafka 管道的做法与此相同：使用相同的源端标志运行 `clickpipe schema-discover kafka`，然后传入相应的列：

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

BigQuery 数据管道默认执行快照同步。如需使用 CDC (变更数据捕获) ，请传入 `--replication-mode cdc` 和 `--replication-method`，并在 `--table-mapping-json` 中为每个表指定水位线列或事件函数；可通过 `--sync-cron` 或 `--sync-interval-seconds` 设置同步调度计划。管理现有数据管道：

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

CDC 管道必须先处于 `Paused` 状态，才能执行 `update`：先停止管道，轮询 `get` 直到其状态变为 `Paused`，然后再执行更新。服务可能会在更新过程中自动恢复管道，因此只有当 `get` 仍显示 `Paused` 时，才需要运行 `start`。`--start-paused` 适用于对象存储、Kafka、Kinesis 和 Pub/Sub。其他命令组包括 `cdc-scaling`、`context get` (用于查看 GCP 工作负载身份的就绪状态及主体) 以及 `reverse-private-endpoint`。详见 [ClickPipes 指南](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md)和 [ClickPipe 配置参考文档](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md)。

### ClickStack {#clickstack}

`cloud clickstack` 用于管理现有[托管 ClickStack](/zh/clickstack/deployment/managed) 服务中的数据源、仪表盘、告警、Webhook、保存的搜索和角色。资源以 JSON 文件形式提供 (通过 `--file` 指定，或使用 `-` 从 stdin 读取) 。读取操作支持 OAuth 认证，写入操作则需要 API key。

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**每次更新 ClickStack 都会替换整个资源。** 请先使用 `get --json` 保存当前状态，然后提交完整的定义，而不是只提交已更改的字段。请参阅 [ClickStack 指南](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md)。

### Cloud 中的 UDFs {#cloud-udfs}

`cloud udf` 用于管理组织级别的可执行用户定义函数、它们的版本及其与服务的关联。`deploy` 会上传你用 `local udf` 测试过的目录，等待构建版本完成，关联该版本，然后等待部署完成：

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud service query <service-id> --query "SELECT my_udf(1)"
```

如需手动执行各个步骤，请使用 `udf create`、`udf version create`、`udf attach` (若服务处于空闲状态，需加上 `--wake`) 、`udf detach` 和 `udf delete`。这些命令在请求被接受后即会返回，可通过轮询 `udf get` 和 `udf attachment get` 查看进度。读取操作支持 OAuth，写入操作则需要 API key。详情请参阅[用户自定义函数指南](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md)。

### 组织与访问 {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

`cloud org` 子命令通过 `--org-id` 指定组织，不接受位置参数形式的 ID。`org usage` 的查询范围最长为 31 天。`org` 还提供 `quota`、`balance`、`notification-types`、`role` (自定义组织角色) 和 `byoc` (BYOC 基础设施) 子命令。通知功能目前处于 Beta 阶段。

管理成员、邀请和 API 密钥：

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

**在 `key create` 中省略 `--ip-allow` 会拒绝所有网络访问**，这一点与创建服务时不同。密钥仅显示一次。除非传入 `--all`，否则 `key list` 只返回一页结果。执行 `key update` 时，未指定的标志会保留原有设置，而 `--clear-expiry`、`--clear-roles` 和 `--clear-ip-allow` 则会清除相应设置。

### 备份 {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud service create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud service backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
```

恢复操作总是会创建一个新服务。`cloud backup bucket` (get、create、update、delete) 可根据特定提供商的 JSON 文件配置自带 (BYO) 备份桶。详见 [云服务指南](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore) 中的备份部分。

## JSON 输出 {#json-output}

返回结构化数据的命令均支持 `--json` 参数，包括本地命令、Cloud 命令，以及 `skills`、`update` 和 `telemetry` 命令：

```bash
clickhousectl cloud service list --json
clickhousectl cloud key list --all --json
clickhousectl local server list --json
```

当命令行客户端检测到编程智能体 (例如 Claude Code、Cursor、Codex、Gemini CLI、Goose 或 Devin，或任何设置了 `AI_AGENT` 的工具) 时，会自动选择 JSON 格式。SQL 客户端和原生客户端则沿用各自的格式：`cloud service query` 在 JSON 模式下返回 `JSONEachRow`，而 `local client` 的输出始终为原生格式。需要解析查询输出的脚本应显式传入 `--format`。

在 JSON 模式下，运行时错误会以对象形式输出到 stderr，其中包含稳定不变的 `code` 以及 `message`：

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

请根据 `error.code` 而非错误消息进行分支判断。用法错误仍以纯文本形式输出，退出码为 2。有关输出格式和错误码的详细说明，请参阅[自动化与输出约定](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md)。

## 退出码 {#exit-codes}

| 代码  | 含义                                    |
| --- | ------------------------------------- |
| `0` | 成功。对于异步 Cloud 操作，表示请求已被接受，但尚未完成       |
| `1` | 错误                                    |
| `2` | 用法错误，包括无效的标志值                         |
| `3` | 已取消                                   |
| `4` | 需要身份验证或身份验证被拒绝，包括使用 OAuth 尝试执行写入操作的情况 |

`local client`、`local postgres client` 以及其他移交给原生客户端执行的命令，会直接透传该客户端自身的退出状态。

## 智能体技能 {#skills}

将[官方 ClickHouse agent skills](https://github.com/ClickHouse/agent-skills) 安装到你的编程智能体中：

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

技能默认安装到当前项目中，也可以通过 `--global` 安装到您的主目录下。共享的 `.agents/skills/` 目录始终会被包含在内。如果没有终端，则必须传入 `--agent`、`--all` 或 `--detected-only`。运行 `clickhousectl skills --help` 可查看受支持的智能体名称。

## 自动更新 {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

命令行客户端还会在后台检查更新 (每 24 小时最多一次) ，并在有新版本可用时输出提示信息。

## 遥测数据 {#telemetry}

`clickhousectl` 会收集匿名用量数据，用于指导后续开发。首次运行时仅显示一条通知，不会发送任何数据；从之后的运行开始收集数据，除非您将其禁用。

每个事件包含：

* 命令路径，以及显式传入的标志和参数的**名称**，绝不包含其值
* 执行结果和退出码
* 对于输错的命令，记录命令行客户端建议的命令或标志名称，绝不记录您实际输入的内容
* 对于运行时故障，记录有限的分类信息：失败阶段和类型、允许列表内的 HTTP 状态码，以及重试、预配状态和耗时的分类
* 命令行客户端版本、OS 和架构、是否在 CI 中运行，以及检测到的 编程智能体

参数值、SQL、凭证、资源标识符、`--` 之后的参数以及错误消息均不会被记录，也不会使用任何安装 ID 或设备 ID。

如需选择退出：

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

设置 `CHCTL_TELEMETRY_DEBUG=1` 后，载荷将仅打印到 stderr，不会发送任何数据。详情请参见[遥测数据详情](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md)。
