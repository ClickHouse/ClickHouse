本页提供规范性指导，帮助你尽可能避免使用 JOIN，并在必须使用 JOIN 时降低其开销。有关语法和语义，请参阅 [`JOIN` 子句参考文档](/zh/reference/statements/select/join)。有关执行算法及如何选择算法，请参阅 [JOIN 算法](/zh/concepts/features/operations/select/join-algorithms)。

## 尽量避免使用 JOIN {#prefer-avoiding-joins}

ClickHouse 支持多种 JOIN 类型和算法。不过，JOIN 天生就比从单个反规范化表中查询成本更高。反规范化会将计算工作从查询时转移到插入或预处理阶段，这通常会显著降低运行时延迟。对于实时或对延迟敏感的分析查询，**强烈建议采用反规范化**。

一般来说，在以下情况下应进行反规范化：

* 表很少发生变化，或者可以接受批量刷新。
* 关系不是多对多，并且基数不会过高。
* 实际会查询的列只有一小部分，也就是说，某些列可以不纳入反规范化。
* 你具备将处理工作从 ClickHouse 转移到上游系统 (如 [Flink](/zh/integrations/connectors/data-ingestion/apache-flink)) 的能力，在那里可以管理实时富集或扁平化。

并非所有数据都需要反规范化——应重点关注经常查询的属性。还可以考虑使用 [materialized views](/zh/concepts/best-practices/use-materialized-views) 来增量计算聚合，而不是复制整个子表。当 schema 更新很少且延迟至关重要时，反规范化通常能提供最佳的性能权衡。

如需了解在 ClickHouse 中对数据进行反规范化的完整指南，请参见 [反规范化](/zh/guides/clickhouse/data-modelling/denormalization)。

## 何时需要 JOIN {#when-joins-are-required}

<Tip>
  **请使用 ClickHouse 26.8 或更高版本。**

  自 25.12 起，多表 JOIN 重排序以及优化器利用可用统计信息的功能均已默认启用。[列统计信息](/zh/reference/settings/session-settings/allow-statistics#allow_statistics)在 26.3 中正式可用并默认启用。自 26.8 起，符合条件的表默认会[在插入时物化列统计信息](/zh/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert)，从而提升基于代价的 JOIN 优化的估算准确性。
</Tip>

遵循以下最佳实践可提升 JOIN 性能：

* **只需一个匹配项时使用 `ANY` JOIN。** 常规 JOIN 会返回所有匹配的行，若键存在重复，可能产生笛卡尔积。如需为左侧每一行补充一个匹配的右侧行，请使用 `LEFT ANY JOIN`，以减小结果规模并降低内存占用。如只需检查是否存在匹配的行，请使用 `IN` 或 `LEFT SEMI JOIN`。在默认设置 [`any_join_distinct_right_table_keys = 0`](/zh/reference/settings/session-settings/other#any_join_distinct_right_table_keys) 下，`INNER ANY JOIN` 还会将左侧限制为每个键仅保留一行，因此可能丢弃键相同的左侧行。参见 [`ALL` 和 `ANY` 严格性](/zh/concepts/features/operations/select/joining-tables#all-and-any-strictness)。
* **在 JOIN 之前缩减两侧数据。** 在 `WHERE` 和 `JOIN ON` 子句中使用选择性较强的条件。ClickHouse 会尽可能下推过滤器，但显式使用子查询可以确保每个输入在 JOIN 之前都已完成过滤。
* **考虑用 `IN` 代替 `INNER JOIN`。** 如果查询只需检查某个键是否存在于另一张表中，`IN` 子查询能更直接地表达这一需求，并且相比生成 `INNER JOIN` 结果，可能占用更少内存。
* **对于重复的键值查找，使用字典。** 使用 `HASHED` 或 `COMPLEX_KEY_HASHED` 等布局时，[字典](/zh/concepts/features/dictionaries)会在查询之前加载到内存中，并按其 `LIFETIME` 定期刷新。[`dictGetOrDefault`](/zh/reference/functions/regular-functions/ext-dict-functions#dictGetOrDefault) 函数无需 JOIN 即可在字典中查找每个键，例如 `dictGetOrDefault('stackoverflow.users_dict', 'DisplayName', tuple(p.OwnerUserId), '')`。
* **对于可复用的查找，优先使用 `Join` 表引擎。** [`Join` 表引擎](/zh/reference/engines/table-engines/special/join)会根据声明的 JOIN 类型、严格性和键，存储一个预先计算好的 in-memory 结构。在 ClickHouse Cloud 中，它以 `SharedJoin` 实现，底层由 `MergeTree` 表提供存储，`Join(ANY, LEFT, key)` 可提供支持更新的按键查找。参见 [Fast, updatable lookups with the Join table engine](https://clickhouse.com/blog/join-table-engine)。
* **尽可能基于表的 sorting key 进行连接。** 当两张表都已按连接键物理排序时，`full_sorting_merge` 可以跳过排序步骤并降低内存占用。请确认执行计划，并使用具有代表性的数据，将该算法与默认算法进行基准测试对比。
* **避免会溢写到磁盘的 JOIN。** 将 JOIN 的中间状态溢写到磁盘虽然可以让查询不超出内存限制，但磁盘 I/O 通常会增加延迟。哈希连接可在达到配置的落盘阈值时切换为 grace hash，而归并连接则可以使用外部排序。在依赖溢写之前，应先减少输入的行和列，或调整数据模型。详情请参见[选择最优 JOIN 算法](#choosing-the-optimal-join-algorithm)。
* **在合适的情况下，将默认值用作未匹配标记。** 默认设置 [`join_use_nulls = 0`](/zh/reference/settings/session-settings/join#join_use_nulls) 会用对应数据类型的默认值填充外连接中未匹配的列，从而避免使用 `Nullable` 包装。仅当查询必须区分未匹配的行与恰好包含默认值的已匹配行时，才需启用 `join_use_nulls`。

## 选择最佳 JOIN 算法 {#choosing-the-optimal-join-algorithm}

ClickHouse 支持多种 JOIN 算法，它们在速度与内存之间各有取舍。
[`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 的默认值为 `direct,hash,inequality`，ClickHouse 会根据 JOIN 类型、严格性、连接条件和表引擎，选择第一个适用的算法。建议先缩减两侧输入的数据量，并且只有在基于代表性数据的测量结果表明确实需要采用不同的内存或执行策略时，再考虑修改此设置。有关算法执行细节及支持的 JOIN 类型，请参阅 [JOIN 算法](/zh/concepts/features/operations/select/join-algorithms)。

如果您最关注的优化指标是性能，希望连接执行得尽可能快，可以参考以下决策树来选择合适的 JOIN 算法：

<br />

<div className="ch-image-lg">
  <Frame>
    ![连接性能优化决策树](/images/guides/joins-4.webp)
  </Frame>
</div>

<br />

* **(1)** 如果右侧是字典或其他支持低延迟键值查找的存储，则可以使用 [`direct`](/zh/concepts/features/operations/select/join-algorithms#direct) 算法，它通常是最快的方案。该算法要求使用 `INNER JOIN`、`LEFT JOIN`、`LEFT ANY JOIN`、`LEFT SEMI JOIN` 或 `LEFT ANTI JOIN`，且其 `ON` 子句只能包含一个针对该存储单列键的等值条件；否则，ClickHouse 会改用 [`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 中的下一个算法，而不会报错。

* **(2)** 如果表的[物理行顺序](/zh/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns)与连接键的排序顺序一致，则需视具体情况而定。此时，**全排序合并连接** 会[跳过](https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order)排序阶段，从而显著降低内存使用量；此外，视数据大小和连接键值的分布而定，其执行速度可能比某些哈希连接算法更快。

* **(3)** 如果右表能够放入内存，请使用 [`hash`](/zh/concepts/features/operations/select/join-algorithms#hash) 算法。它通常是最快的 in-memory 方案，具体取决于连接键列的数据大小、数据类型以及值分布。对于每个查询，ClickHouse 会决定是构建单个哈希表，还是将哈希表拆分为多个部分、由多个线程并发填充，决策树中将后者标示为 parallel hash。[`parallel_hash_join_threshold`](/zh/reference/settings/session-settings/parallel#parallel_hash_join_threshold) 设置控制这一决策：当右表的估计行数达到该阈值，或无法获得估计值时，哈希表会被拆分。自 26.11 版本起，`parallel_hash` 已成为 `hash` 的废弃别名，因此在 `join_algorithm` 中列出它不会改变这一决策。

* **(4)** 如果右表无法放入内存，当达到 [`max_bytes_before_external_join`](/zh/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) 或 [`max_bytes_ratio_before_external_join`](/zh/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join) 阈值时，哈希连接 和 并行哈希连接 可以切换为 Grace 哈希，将数据溢写到磁盘。全排序合并连接 和 部分合并连接 也可以使用外部存储。哪种方式最快，取决于连接键列的数据量、数据类型以及值分布。

部分合并连接 针对大表连接场景进行了优化，旨在尽量减少内存使用量，但代价是连接速度相当慢。当左表的物理行顺序与连接键的排序顺序不一致时，这一问题尤为突出。

Grace 哈希连接 是三种不受内存限制的 JOIN 算法中最灵活的一种，可通过设置进行精细控制。[`grace_hash_join_initial_buckets`](/zh/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets) 设置用于控制初始桶数量，可在内存使用量与连接速度之间进行权衡。

三种基于磁盘的算法中哪一种最快，取决于数据量、数据类型以及连接键列的值分布。建议始终使用与实际规模相当的数据运行基准测试，以确定最快的算法。

### 决策树示例 {#decision-tree-examples}

以下示例基于 [Stack Overflow 数据集](/zh/getting-started/example-datasets/stackoverflow)，逐一演示决策树中的每个步骤。要查看 JOIN 实际使用的算法，请在查询中加上 `EXPLAIN actions = 1` 运行，并查看输出中的 `Algorithm` 行。

**(1) `direct`。** 以下字典存储了每个用户的显示名称，查询则会查找每个高评分帖子的作者：

```sql
CREATE DICTIONARY stackoverflow.users_dict
(
    Id Int32,
    DisplayName String
)
PRIMARY KEY Id
SOURCE(CLICKHOUSE(DB 'stackoverflow' TABLE 'users'))
LAYOUT(COMPLEX_KEY_HASHED())
LIFETIME(MIN 600 MAX 900);

SELECT p.Id, p.Score, u.DisplayName
FROM stackoverflow.posts AS p
LEFT JOIN stackoverflow.users_dict AS u ON p.OwnerUserId = u.Id
WHERE p.Score > 1000;
```

`Algorithm` 行显示为 `DirectKeyValueJoin`。该字典使用 `COMPLEX_KEY_HASHED` 布局，以保留 `users.Id` 的 `Int32` 类型。若使用简单键布局 (例如 `HASHED`) ，键会被转换为 `UInt64`，从而无法与 `Int32` 类型的列 `posts.OwnerUserId` 进行连接。

**(2) `full_sorting_merge`。** `badges` 表按 `UserId` 排序，而 `users` 表的 sorting key 以 `Id` 开头，因此两张表在物理上都已按连接键有序存储：

```sql
SELECT u.Location, count() AS famous_questions
FROM stackoverflow.badges AS b
INNER JOIN stackoverflow.users AS u ON b.UserId = u.Id
WHERE b.Name = 'Famous Question'
GROUP BY u.Location
ORDER BY famous_questions DESC
LIMIT 5
SETTINGS join_algorithm = 'full_sorting_merge';
```

`Algorithm` 行显示为 `FullSortingMergeJoin`，且两个 `ReadFromMergeTree` 步骤的读取类型均为 `InOrder`。ClickHouse 直接按连接键的顺序读取两张表，无需再进行排序。

**(3) `hash`。** 在默认的 `join_algorithm` 设置下，以下 JOIN 使用 `hash` 执行：

```sql
SELECT u.Location, count() AS popular_posts
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.users AS u ON p.OwnerUserId = u.Id
WHERE p.Score > 1000
GROUP BY u.Location
ORDER BY popular_posts DESC
LIMIT 5
SETTINGS parallel_hash_join_threshold = 0;
```

如果没有 `SETTINGS` 子句，ClickHouse 仅在右表的估计行数达到 `parallel_hash_join_threshold` 的默认值 100,000 时才会拆分哈希表。设置 `parallel_hash_join_threshold = 0` 后，无论估计值是多少，ClickHouse 都会拆分哈希表。

**(4) 溢写。** 以下查询允许哈希表在内存中最多增长到 10 GiB。一旦超过该大小，ClickHouse 会将 JOIN 切换为 `grace_hash`，并将部分数据写入临时存储：

```sql
SELECT u.Location, count() AS popular_posts
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.users AS u ON p.OwnerUserId = u.Id
WHERE p.Score > 1000
GROUP BY u.Location
ORDER BY popular_posts DESC
LIMIT 5
SETTINGS max_bytes_before_external_join = '10Gi';
```

## 针对内存进行优化 {#optimizing-for-memory}

如果您希望优化连接以获得最低的内存使用量，而非最快的执行时间，则可以改用以下决策树：

<br />

<div className="ch-image-lg">
  <Frame>
    ![连接内存优化决策树](/images/guides/joins-5.webp)
  </Frame>
</div>

<br />

* **(1)** 如果表的物理行顺序与连接键的排序顺序一致，**全排序合并连接**的内存使用量即可降至最低；此外，由于排序阶段会被[跳过](https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order)，还能获得良好的连接速度。
* **(2)** 增大 [`grace_hash_join_initial_buckets`](/zh/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets) 可以将 [`grace_hash`](/zh/concepts/features/operations/select/join-algorithms#grace-hash) 算法的内存使用量调至极低，但会牺牲 JOIN 速度。[`partial_merge`](/zh/concepts/features/operations/select/join-algorithms#partial-merge) 算法在设计上就只占用少量主内存。当行顺序与键的排序顺序不一致时，启用了外部排序的 [`full_sorting_merge`](/zh/concepts/features/operations/select/join-algorithms#full-sorting-merge) 算法通常比 `partial_merge` 占用更多内存，但 JOIN 执行时间要短得多。[`hash`](/zh/concepts/features/operations/select/join-algorithms#hash) 算法也可以在达到所配置的落盘阈值时切换为 `grace_hash`，从而缓解内存压力。

## JOIN 优化示例 {#join-optimization-examples}

以下示例使用 [Stack Overflow 数据集](/zh/getting-started/example-datasets/stackoverflow)，并逐步应用上述建议。
下文的测量结果均为在 ClickHouse Cloud 服务 (ClickHouse 26.8.1，`max_threads = 4`) 上运行五次所得的中位数。每个查询均预热一次，并交替调整查询执行顺序，同时禁用了 `use_query_cache` 和 `use_query_condition_cache`。

### 将 `ANY INNER JOIN` 替换为 `IN` {#replace-any-inner-join-with-in}

在本次测试中，`IN` 查询的速度提升了 2.7 倍，峰值内存占用降低了 83%。
该查询统计本身未提及 ClickHouse、但至少有一条评论提及 ClickHouse 的帖子数量：

```sql
SELECT count()
FROM stackoverflow.posts AS p
ANY INNER JOIN stackoverflow.comments AS c ON p.Id = c.PostId
WHERE
    p.Title != ''
    AND p.Title NOT ILIKE '%clickhouse%'
    AND p.Body NOT ILIKE '%clickhouse%'
    AND c.Text ILIKE '%clickhouse%'
```

该查询返回的结果为 `86`。耗时中位数为 27.101 秒，峰值内存占用为 970.01 MiB，共读取 1.5020 亿行、51.77 GiB 数据。

该查询只需确认是否存在匹配的评论即可。改用 `IN` 子查询可以避免生成 JOIN 结果：

```sql
SELECT count()
FROM stackoverflow.posts
WHERE
    Title != ''
    AND Title NOT ILIKE '%clickhouse%'
    AND Body NOT ILIKE '%clickhouse%'
    AND Id IN
    (
        SELECT PostId
        FROM stackoverflow.comments
        WHERE Text ILIKE '%clickhouse%'
    )
```

`IN` 查询同样返回 `86`，耗时中位数为 10.206 秒，峰值内存占用为 162.81 MiB，共读取 1.7420 亿行、19.02 GiB 数据。

由于 `posts.Id` 是唯一的，这两个查询返回的结果相同。只有当左侧的连接键唯一时，这种重写才是等价的，因为 `ANY INNER JOIN` 对每个键最多只返回一个左侧行，而 `IN` 会返回所有存在匹配项的左侧行。

### 在替换 JOIN 之前先过滤两侧 {#filter-both-sides-before-replacing-the-join}

在此测试中，该重写使中位耗时降低了 18%，峰值内存占用降低了 14%。
此查询统计 2020 年以来创建的 Java 相关帖子所获得的赞成票数。日期条件在 JOIN 之前即已同时应用于两个输入：

```sql
SELECT countIf(v.VoteTypeId = 2) AS upvotes
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.votes AS v ON p.Id = v.PostId
WHERE
    p.CreationDate >= '2020-01-01'
    AND v.CreationDate >= '2020-01-01'
    AND has(arrayFilter(t -> t != '', splitByChar('|', p.Tags)), 'java')
```

该查询返回的结果为 `261915`。其耗时中位数为 0.850 秒，峰值内存占用为 59.96 MiB，共读取 8094 万行、1.13 GiB 数据。

对于每条投票，只需确认存在匹配的帖子即可，因此可以将 JOIN 替换为 `IN`，同时保留两侧输入上的过滤器：

```sql
SELECT count() AS upvotes
FROM stackoverflow.votes
WHERE
    VoteTypeId = 2
    AND CreationDate >= '2020-01-01'
    AND PostId IN
    (
        SELECT Id
        FROM stackoverflow.posts
        WHERE
            CreationDate >= '2020-01-01'
            AND has(arrayFilter(t -> t != '', splitByChar('|', Tags)), 'java')
    )
```

`IN` 查询同样返回 `261915`，中位耗时为 0.696 秒，峰值内存占用为 51.70 MiB，共读取 4620 万行、817.49 MiB 数据。

由于 `posts.Id` 是唯一的，每条投票最多只会匹配一个帖子，因此该重写是等价的。
