本页介绍 `KILL QUERY`、`KILL MUTATION`、`KILL TRANSACTION` 和 `KILL PART_MOVE_TO_SHARD` 语句。

默认情况下，对于 `KILL QUERY`，如果在排除当前 `KILL` 语句后，其 `WHERE` 表达式在 `system.processes` 中没有留下任何符合条件的行，则会抛出 `NOTHING_TO_KILL` 异常；对于 `KILL MUTATION`，如果其 `WHERE` 表达式在 `system.mutations` 中匹配到零行，同样会抛出异常。如需在没有匹配到任何内容时不抛出异常，请将 [`kill_throw_if_noop`](/zh/operations/settings/settings#kill_throw_if_noop) 设置为 `false`。
`KILL TRANSACTION` 和 `KILL PART_MOVE_TO_SHARD` 在没有匹配到任何内容时始终不会抛出异常，而是返回空结果。
以 `ON CLUSTER` 方式执行时，即使没有匹配到任何内容也不会抛出异常，因为匹配结果不会跨主机汇总。

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

尝试强制终止当前正在运行的查询。
要终止的查询会根据 `KILL` 查询中 `WHERE` 子句定义的条件，从 system.processes 表中筛选出来。

示例：

首先，您需要获取未完成查询的列表。以下 SQL 查询会按运行时长从长到短列出这些查询：

单个 ClickHouse 节点上的列表：

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

列出 ClickHouse 集群中的项目：

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

终止查询：

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  如果你是在 ClickHouse Cloud 或自管理集群中终止查询，请务必使用 `ON CLUSTER [cluster-name]` 选项，以确保该查询会在所有副本上都被终止
</Tip>

只读用户只能停止自己的查询。

未获得 `system.processes` 上 `SELECT` 授权的用户，仍可通过指定查询 ID 取消自己的查询：
`KILL QUERY WHERE query_id = '<id>'`。对于既没有该授权也没有 `KILL QUERY` 权限的用户，如果指定的 ID 不属于其正在运行的查询，
则不会取消任何查询，并且默认会抛出 `NOTHING_TO_KILL` 异常。如果将
[`kill_throw_if_noop`](/zh/operations/settings/settings#kill_throw_if_noop) 设置为 `false`，则改为不返回任何行；
拥有 `KILL QUERY` 权限但没有该 `SELECT` 授权的用户，会因缺少 `SELECT` 授权而被拒绝。
其他任何 `WHERE` 条件以及 `ON CLUSTER` 仍要求具备上述授权。

默认使用的是查询的异步版本 (`ASYNC`) ，不会等待查询已停止的确认。

同步版本 (`SYNC`) 会等待所有查询停止，并在每个进程停止时显示相关信息。
响应中包含 `kill_status` 列，其可能的取值如下：

1. `finished` – 查询已成功终止。
2. `waiting` – 已向查询发送终止信号，正在等待其结束。
3. 其他值则说明该查询无法被停止的原因。

测试查询 (`TEST`) 仅检查用户权限，并显示将要停止的查询列表。

## KILL MUTATION {#kill-mutation}

存在长时间运行或未完成的变更，通常说明 ClickHouse 服务运行状态不佳。由于变更是异步执行的，它们可能会耗尽系统中的所有可用资源。你可能需要采取以下措施之一：

* 暂停所有新的变更、`INSERT` 和 `SELECT`，并等待变更队列处理完成。
* 或者发送 `KILL` 命令，手动终止其中一部分变更。

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

尝试取消并移除当前正在执行的[变更](/zh/reference/statements/alter/index#mutations)。要取消的变更会根据 `KILL` 查询的 `WHERE` 子句指定的过滤条件，从 [`system.mutations`](/zh/reference/system-tables/mutations) 表中选出。

测试查询 (`TEST`) 仅检查用户权限，并显示将要停止的变更列表。

示例：

统计未完成变更数量的 `count()`：

单个 ClickHouse 节点上的变更数量：

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

ClickHouse 副本集群中的变更数量：

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

查询未完成的变更列表：

单个 ClickHouse 节点上的变更列表：

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

ClickHouse 集群中的变更列表：

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

按需终止这些变更操作：

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

当变更卡住而无法完成时，此查询会很有用 (例如，当变更查询中的某个函数应用到表中数据时抛出异常) 。

变更已完成的修改不会回滚。

<Note>
  [system.mutations](/zh/reference/system-tables/mutations) 表中的 `is_killed=1` 列 (仅 ClickHouse Cloud) 并不一定表示该变更已完全结束。变更有可能长时间处于 `is_killed=1` 且 `is_done=0` 的状态。如果另一个运行时间较长的变更阻塞了这个已被终止的变更，就可能出现这种情况。这是正常现象。
</Note>

## KILL TRANSACTION {#kill-transaction}

引入版本：v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  此语句属于实验性功能集。
  如需启用实验性事务支持，请在[配置](/zh/concepts/features/configuration/server-config/configuration-files)中添加以下设置：

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  更多信息请参阅[事务性 (ACID) 支持](/zh/concepts/features/operations/insert/transactions#transactions-commit-and-rollback)页面。
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

回滚由 `WHERE` 子句从 [`system.transactions`](/zh/reference/system-tables/transactions) 表中选出的正在运行的[事务](/zh/reference/statements/transactions)。
被终止事务所在的会话随后将处于与查询失败后相同的状态，详见 [`COMMIT`](/zh/reference/statements/transactions#commit)：在该会话执行 `ROLLBACK` 之前，`COMMIT` 会抛出 `INVALID_TRANSACTION` 异常。

该语句需要 `KILL TRANSACTION` 特权，以及对 `system.transactions` 的 `SELECT` 权限。
响应包含 `kill_status` 列 (对于已回滚的事务，其值为 `waiting`) ，其后依次为 `system.transactions` 中的 `tid`、`tid_hash`、`elapsed`、`is_readonly` 和 `state` 列。

测试查询 (`TEST`) 仅检查用户权限，并列出将要回滚的事务。

示例：

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

引入版本：v21.11.0

<ExperimentalBadge />

<Note>
  在分片之间移动 parts 是一项实验性功能，需通过 MergeTree 设置 [`part_moves_between_shards_enable`](/zh/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable) 按表单独启用。
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

取消由 `ALTER TABLE ... MOVE PART ... TO SHARD` 发起的分片间 parts 移动操作，具体取消哪些操作由 `WHERE` 子句从 [`system.part_moves_between_shards`](/zh/reference/system-tables/part_moves_between_shards) 表中筛选。
被取消的移动操作会在后台回滚，其在 `system.part_moves_between_shards` 中的 `state` 将变为 `CANCELLED`。
已进入 `SOURCE_DROP` 状态的移动操作无法再取消，会一直执行到完成。

该语句需要对 `system.part_moves_between_shards` 拥有 `SELECT` 特权；若要取消某个移动操作，还需要对其所属表拥有 `ALTER MOVE PARTITION` 特权，以及 `MOVE PARTITION BETWEEN SHARDS` 特权。
使用 `ON CLUSTER` 时，该语句需要在 `*.*` 上同时拥有这两项移动特权。
响应首先包含 `kill_status` 列：已取消的移动操作对应值为 `waiting`，无法再取消的移动操作对应值为 `cant_cancel`；其后是 `system.part_moves_between_shards` 中的 `database`、`table`、`task_name`、`task_uuid`、`part_name`、`to_shard` 和 `state` 列。

测试查询 (`TEST`) 仅显示待取消的移动操作列表。不支持 `SYNC` 修饰符，使用该修饰符会抛出 `NOT_IMPLEMENTED` 异常。

示例：

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
