`JOIN` 子句通过基于各表中的公共值组合一个或多个表的列，生成一张新表。这是在支持 SQL 的数据库中常见的操作，对应于[关系代数](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators)中的 join。一张表与自身进行 join 的特殊情况通常称为&quot;自连接&quot;。

**语法**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

`ON` 子句中的表达式和 `USING` 子句中的列称为&quot;JOIN 键&quot;。除非另有说明，`JOIN` 会对 JOIN 键匹配的行生成 [笛卡儿积](https://en.wikipedia.org/wiki/Cartesian_product)，因此结果中的行数可能远多于源表。

本页介绍 `JOIN` 子句的语法和语义。如需了解 ClickHouse 中 JOIN 的执行方式、JOIN 类型、设置、内存方面的注意事项以及优化，请参阅[相关内容](#related-content)。

## 支持的连接类型 {#supported-types-of-join}

支持所有标准的 [SQL 连接](https://en.wikipedia.org/wiki/Join_\(SQL\)) 类型：

| Type               | Description                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | 仅返回匹配的行。                                                                                                                        |
| `LEFT OUTER JOIN`  | 除返回匹配的行外，还返回左表中不匹配的行。                                                                                                           |
| `RIGHT OUTER JOIN` | 除返回匹配的行外，还返回右表中不匹配的行。                                                                                                           |
| `FULL OUTER JOIN`  | 除返回匹配的行外，还返回两个表中不匹配的行。                                                                                                          |
| `CROSS JOIN`       | 生成整个表的笛卡尔积，**不**指定连接键。                                                                                                          |
| `NATURAL JOIN`     | 自动基于两个表中所有同名列进行连接。每个公共列在结果中只出现一次。支持 `INNER` (默认) 、`LEFT`、`RIGHT` 和 `FULL` 变体。等价于 `JOIN ... USING (col1, col2, ...)`，其中列列表会自动推导。 |

* 未指定类型的 `JOIN` 默认为 `INNER`。
* 关键字 `OUTER` 可以省略。
* `CROSS JOIN` 的另一种语法是在 [`FROM` 子句](/zh/reference/statements/select/from) 中用逗号分隔指定多个表。
* 如果 `NATURAL JOIN` 没有可匹配的列，其行为与 `CROSS JOIN` 相同。

ClickHouse 还支持以下额外的 JOIN 类型：

| Type                                                | Description                                                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | 针对连接键的允许列表，不会生成笛卡尔积。                                                                                                                                               |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | 针对连接键的拒绝列表，不会生成笛卡尔积。                                                                                                                                               |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | 对标准 `JOIN` 类型，部分 (对 `LEFT` 和 `RIGHT` 的对侧) 或完全 (对 `INNER`) 禁用笛卡尔积。不支持 `ANY FULL JOIN`。                                                                              |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | 对序列执行非精确匹配连接。参见 [ASOF JOIN 用法](#asof-join-usage)。                                                                                                                  |
| `PASTE JOIN`                                        | 对两个表执行横向拼接。参见 [PASTE JOIN 用法](#paste-join-usage)。                                                                                                                  |
| `INNER JOIN LATERAL`, `LEFT JOIN LATERAL`           | 连接一个引用其左侧表中列的子查询。该功能为 Experimental，需要启用 [`enable_lateral_join`](/zh/reference/settings/session-settings/enable#enable_lateral_join)。参见 [LATERAL JOIN](#lateral-join)。 |

各 JOIN 类型及严格性的示意图请参见 [在 ClickHouse 中使用 JOIN](/zh/concepts/features/operations/select/joining-tables#join-types-and-strictness)。

<Note>
  如果禁用 `semi_join_include_columns_from_both_sides` 或 `anti_join_include_columns_from_both_sides` 设置，则对于在连接结果生成之后才解析的表达式，相应的连接只会公开其保留侧的列。

  * `LEFT SEMI JOIN` 和 `LEFT ANTI JOIN` 仅公开左侧的列。
  * `RIGHT SEMI JOIN` 和 `RIGHT ANTI JOIN` 仅公开右侧的列。
  * 这会影响 `SELECT`、`PREWHERE`、`WHERE`、`GROUP BY`、`HAVING`、`QUALIFY`、`ORDER BY` 和 `LIMIT BY` 等子句，也包括 `t1.*` 这类限定通配符。
  * 同一 `JOIN` 的 `ON` 表达式仍可引用两侧的列。

  启用这些设置时 (默认启用)，ClickHouse 会保留旧有行为：两侧的列均可访问，且 `SELECT *` 会展开两个表的所有列。
</Note>

并非每种 JOIN 算法都支持所有 JOIN 类型与严格性的组合。支持的组合请参见 [各算法支持的 JOIN 类型](/zh/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm)。

### 将 `CROSS JOIN` 重写为 `INNER JOIN` {#cross-join-rewrite}

如果某个查询使用了 `CROSS JOIN` 或以逗号分隔的表列表，且其 `WHERE` 子句包含表之间的等值条件，ClickHouse 可以将该 JOIN 重写为 `INNER JOIN`，并以这些条件作为 JOIN 连接键。此重写由 [`cross_to_inner_join_rewrite`](/zh/reference/settings/session-settings/other#cross_to_inner_join_rewrite) 设置控制：

* `0`：禁用重写。
* `1`：当 `WHERE` 子句包含表之间的等值条件时，重写以逗号分隔的表列表或 `CROSS JOIN`；否则，该 JOIN 按 `CROSS JOIN` 执行。
* `2`：与 `1` 相同，但如果查询包含 `WHERE` 子句，而以逗号分隔的表列表无法重写，则查询会失败并报 `INCORRECT_QUERY` 错误。使用 `CROSS JOIN` 关键字编写且无法重写的 JOIN 仍按 `CROSS JOIN` 执行。

当该值为 `0` 时，由 [`query_plan_merge_filter_into_join_condition`](/zh/reference/settings/session-settings/query-plan#query_plan_merge_filter_into_join_condition) 控制的查询计划优化仍可将等值过滤器合并到 JOIN 中，并按 `INNER JOIN` 执行。

## `ON` 部分中的条件 {#on-section-conditions}

`ON` 部分可以包含多个通过 `AND` 和 `OR` 运算符组合起来的条件。用于指定连接键的条件必须：

* 同时引用左表和右表
* 使用等值运算符

其他条件可以使用其他运算符，并且可以引用查询中的左表或右表，也可以同时引用两者。

只有整个复合条件都满足时，行才会被连接。如果条件不满足，根据 `JOIN` 类型，这些行仍然可能出现在结果中。如果将相同的条件放在 `WHERE` 部分中且条件不满足，那么这些行始终会被从结果中过滤掉。

通过 `OR` 组合的连接键仅受 [`hash`](/zh/concepts/features/operations/select/join-algorithms#hash) 算法支持，该算法会为每个包含连接键的 `OR` 参数分别构建一张哈希表。

<Note>
  只有等值运算符 (`=`) 才能使条件成为连接键。不同表的列之间也可以使用其他运算符，但如果没有任何等值条件，连接就必须逐一检查每一对行；参见 [使用任意 ON 条件的连接](#join-with-an-arbitrary-on-condition)。
</Note>

**示例**

以 `table_1` 和 `table_2` 为例：

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

带有一个连接键条件以及 `table_2` 的附加条件的查询：

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

结果中包含名称为 `C` 且文本列为空的那一行。之所以会出现在结果中，是因为使用了 `OUTER` 类型的连接。

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

具有 `INNER` 类型且包含多个条件的 `join` 查询：

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```response title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴────────┴────────┘
```

使用 `INNER` 类型连接且条件包含 `OR` 的查询：

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

使用 `INNER` 类型连接且条件包含 `OR` 和 `AND` 的查询：

<Note>
  仅使用单张表中列的非等值条件 (例如 `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c`) 只会作用于该表本身：`t1.b > 0` 只使用了 `t1` 中的列，而 `t2.b > t2.c` 只使用了 `t2` 中的列。
  比较不同表中列的非等值条件 (例如 `t1.a = t2.key AND t1.b > t2.key`) 同样受支持，请参阅下文各节。
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## 对不同表中的列使用带不等条件的连接 {#join-with-inequality-conditions-for-columns-from-different-tables}

除相等条件外，`ON` 子句还可以包含使用其他运算符比较不同表中列的条件。在 `ALL`、`ANY`、`SEMI` 和 `ANTI` 严格性下，只要是该严格性所允许的 JOIN 类型，均支持此类条件。`ASOF` 严格性不支持此类条件。

当 `ON` 子句中除不等条件外还包含两个表之间的相等条件时，该相等条件将作为 JOIN 键，不等条件则在其匹配到的行上进行检查。此类混合条件由 [`hash`](/zh/concepts/features/operations/select/join-algorithms#hash)、[`parallel_hash`](/zh/concepts/features/operations/select/join-algorithms#parallel-hash) 和 [`grace_hash`](/zh/concepts/features/operations/select/join-algorithms#grace-hash) 算法执行。如果在 [`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 中 [`ie_join`](/zh/concepts/features/operations/select/join-algorithms#ie-join) 排在这些算法之前，且 `ON` 子句包含两个不等条件，则改由 `ie_join` 执行该 JOIN，并将相等条件作为过滤器应用。

当 `ON` 子句中不包含两个表之间的相等条件时，就没有可供匹配的 JOIN 键。此时，如果条件是一对不等式，该 JOIN 将由 [`ie_join`](/zh/concepts/features/operations/select/join-algorithms#ie-join) 执行；否则将以 [block nested loop 连接](#join-with-an-arbitrary-on-condition) 方式执行。

连接过程中求值的条件不能包含 `arrayJoin`，因为此类条件必须保持行数不变；请改为在子查询中使用 `ARRAY JOIN`。

**示例**

表 `t1`：

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

表 `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response
key1    a    1    1    2    key1    B    2    1    2
key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
key1    e    5    5    5            0    0    \N
key2    a2    1    1    1            0    0    \N
key4    f    2    3    4            0    0    \N
```

## 使用任意 ON 条件的 JOIN {#join-with-an-arbitrary-on-condition}

`ON` 子句可以是基于两个表中列的任意布尔表达式，例如范围检查、算术比较或标量函数调用。如果其中不包含两个表之间的相等条件，就没有可用于匹配行的 JOIN 键。只要 [`join_algorithm`](/zh/reference/settings/session-settings/join#join_algorithm) 中列出了 `ie_join` 算法，一对不等式条件就会由 `ie_join` 执行，且不要求它排在首位，因为其他任何 `join_algorithm` 值都无法执行此类条件。自 26.8 版本起，`join_algorithm` 的默认值已包含 `ie_join`。其他任何条件都将以 [block nested loop join](https://en.wikipedia.org/wiki/Nested_loop_join) 的方式执行：先物化右表，再对每一对行计算该条件。`ALL INNER JOIN` 则等价于以该条件作为过滤器的 `CROSS JOIN`。

block nested loop join 支持除 `ASOF JOIN`、`PASTE JOIN` 和 `ANY FULL JOIN` 之外的所有 JOIN 类型和严格性。它并不是 `join_algorithm` 的可选值之一，而是最后的兜底方案，仅在没有其他算法能够执行该条件时才会使用。在 `EXPLAIN` 输出中，它显示为 `BlockNestedLoopJoin` 步骤。如果禁用了 [`allow_block_nested_loop_join`](/zh/reference/settings/session-settings/allow#allow_block_nested_loop_join)，则需要使用该算法的查询将被拒绝，并返回 `INVALID_JOIN_ON_EXPRESSION` 错误。

**示例**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

与其他任何 JOIN 一样，未匹配到任何行的那一行会按照 [`join_use_nulls`](/zh/reference/settings/session-settings/join#join_use_nulls) 进行填充：默认情况下如上所示使用默认值填充；启用该设置时，则使用 `NULL` 填充。

**严格性**

`ANY` 和 `SEMI` 通常会为共享同一 JOIN 键的每组行保留一行。此处不存在这样的分组，因此它们会为驱动 JOIN 的那张表的每一行保留一行：`LEFT ANY` 和 `LEFT SEMI` 对每个左表行最多输出一次，`RIGHT ANY` 和 `RIGHT SEMI` 对每个右表行最多输出一次。`ANY INNER` 会同时限制两侧：任一张表的每一行最多只使用一次，因此结果行数不会超过较小那张表的行数。结果具体由哪些行对构成是任意的，这正是 `ANY` 的语义所在，同一查询的两次运行结果也可能不同。对于 `ANY INNER`，这种不确定性还会波及行数：按照行被检查的任意顺序，以贪心方式为两侧的每一行配对，最终未配对的行数可能各不相同。因此，对没有 JOIN 键的 `ANY INNER` JOIN 执行 `count()` 的结果不可复现，具体取决于线程数量以及右表的物理顺序。

**性能**

block nested loop join 会检查每一对行，因此其开销随两张表行数的乘积增长，详见 [Block nested loop 回退](/zh/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback)。物化后的右表受 [JOIN 内存管理与溢写](/zh/concepts/features/operations/select/join-memory-management) 中所述的硬限制和落盘阈值约束。

## JOIN 连接键中的 NULL 和 NaN 值 {#null-values-in-join-keys}

`NULL` 不等于任何值，包括其自身。如果某个 JOIN 连接键在一个表中的值为 `NULL`，它就不会与另一个表中的 `NULL` 值匹配。如果 JOIN 连接键是 [Nullable](/zh/reference/data-types/nullable) 列，那么只要某一行中至少有一个键为 [NULL](/zh/reference/syntax#null)，该行就不会被连接。

**示例**

表 `A`：

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

表 `B`：

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

由于 JOIN 键中存在 `NULL` 值，表 `A` 中包含 `Charlie` 的那一行与表 `B` 中分数为 88 的那一行均未能匹配。

未匹配的行在 `score` 列中的值为 `0`，详见 [空单元或 NULL 单元的处理](#processing-of-empty-or-null-cells)。

如需匹配 `NULL` 值，请使用 `isNotDistinctFrom` 函数来比较 JOIN 键：

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

浮点 JOIN 键中的 `NaN` 值不遵循上述 `NULL` 规则。
两个 `NaN` 值的标量比较 (`NaN = NaN`) 结果为 `0`。但 JOIN 键并非按标量语义比较，因此 `NaN` 键可能会匹配。
它们是否匹配并无明确规定，取决于 JOIN 算法、键类型和会话设置。
如需避免 `NaN` 键参与匹配，请将其映射为 `NULL` 值，例如 `ON if(isNaN(A.id), NULL, A.id) = B.id`。
在 `ASOF JOIN` 中，最近匹配列按排序进行比较，而 `NaN` 值的排序未定义。

## 隐式类型转换 {#implicit-type-conversion}

当左表和右表的 JOIN 键类型不同时，ClickHouse 会先将它们转换为最小共同超类型，再进行比较。此规则适用于所有 JOIN 类型和严格性：

* 使用 `ON` 时，转换仅作用于比较过程，键列在结果中保留其原始类型。
* 使用 `USING` 时，已合并的列在结果中采用公共类型。当 `semi_join_include_columns_from_both_sides` 或 `anti_join_include_columns_from_both_sides` 被禁用时，`SEMI JOIN` 或 `ANTI JOIN` 中已合并的列沿用被保留一侧表的类型。

如果键类型没有共同超类型，且两者均为整数类型或由整数类型组成的元组 (例如 `UInt64` 和 `Int64`) ，ClickHouse 会将两个键都转换为一种能够容纳两种键类型共有取值的类型。对于 `UInt64` 和 `Int64`，该类型为 `UInt64`。该类型无法表示的键值不会与任何值匹配。此转换适用于 `ON` 中的等值条件 (`isNotDistinctFrom` 除外) ，以及 `INNER JOIN` 或 `SEMI JOIN` 中的 `USING`。它不适用于 `ASOF JOIN` 的最近匹配条件、由 `ie_join` 执行的不等式条件，也不适用于其他连接中的 `USING`，因为这些连接的结果列还必须容纳未匹配的值。此转换自 26.9 版本起可用。

如果键类型没有共同超类型，且此转换不适用 (例如 `String` 和 `Int32`，或 `UInt64` 和 `Float64`) ，查询将失败并抛出异常，例如 `NO_COMMON_TYPE`。

**示例**

考虑表 `t_1`：

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

以及 `t_2` 表：

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

此查询

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b) ORDER BY ALL;
```

返回该集合：

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## ASOF JOIN 用法 {#asof-join-usage}

`ASOF JOIN` 用于连接没有精确匹配项的记录。`ASOF` 是一种 JOIN 严格性，需与 `INNER` 或 `LEFT` JOIN 结合使用，它本身并不是一种 JOIN 算法。

`ASOF JOIN` 要求两个表中都有一个用于最近匹配的列。该列：

* 必须是具有确定顺序的类型。
* 使用 [`hash`](/zh/concepts/features/operations/select/join-algorithms#hash) 算法时，可以是以下类型：[Int, UInt](/zh/reference/data-types/int-uint)、[Float](/zh/reference/data-types/float)、[Decimal](/zh/reference/data-types/decimal)、[Date](/zh/reference/data-types/date)、[Date32](/zh/reference/data-types/date32)、[DateTime](/zh/reference/data-types/datetime)、[DateTime64](/zh/reference/data-types/datetime64)、[Time](/zh/reference/data-types/time)、[Enum](/zh/reference/data-types/enum)、[Bool](/zh/reference/data-types/boolean)，以及这些类型对应的 [Nullable](/zh/reference/data-types/nullable) 类型。其他类型 (例如 `String` 和 `Time64`) 会被拒绝，并返回 `BAD_TYPE_OF_FIELD` 错误。
* 使用 [`full_sorting_merge`](/zh/concepts/features/operations/select/join-algorithms#full-sorting-merge) 算法时，还可以是其他可比较类型，例如 `String`。
* 使用 `hash` 算法时，不能是 `JOIN` 子句中的唯一列，至少需要一个相等条件。`full_sorting_merge` 算法则无此限制。

语法 `ASOF JOIN ... ON`：

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

你可以使用任意数量的相等条件，以及恰好一个最近匹配条件。例如，`SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t`。

最近匹配支持的条件：`>`、`>=`、`<`、`<=`。

语法 `ASOF JOIN ... USING`:

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

`ASOF JOIN` 使用 `equi_columnX` 按相等条件进行连接，并使用 `asof_column` 在满足 `table_1.asof_column >= table_2.asof_column` 条件时按最接近匹配进行连接。`asof_column` 列始终是 `USING` 子句中的最后一列。

例如，考虑下面的表：

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

`ASOF JOIN` 可以获取 `table_1` 中用户事件的时间戳，并在 `table_2` 中找到一个事件，使其时间戳在满足最近匹配条件的情况下最接近 `table_1` 中该事件的时间戳。如果存在相同的时间戳值，则优先视为最近匹配。这里，`user_id` 列可用于按相等条件连接，`ev_time` 列可用于按最近匹配条件连接。在我们的示例中，`event_1_1` 可以与 `event_2_1` 连接，`event_1_2` 可以与 `event_2_3` 连接，但 `event_2_2` 无法连接。

<Note>
  在各种 JOIN 算法中，只有 [`hash`](/zh/concepts/features/operations/select/join-algorithms#hash) 和 [`full_sorting_merge`](/zh/concepts/features/operations/select/join-algorithms#full-sorting-merge) 支持 `ASOF` 严格性。请参阅[各算法支持的 JOIN 类型](/zh/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm)。
  [Join](/zh/reference/engines/table-engines/special/join) 表引擎**不**支持 `ASOF`。
</Note>

## PASTE JOIN 用法 {#paste-join-usage}

`PASTE JOIN` 的结果是一张表，包含左侧子查询的所有列，随后是右侧子查询的所有列。
各行会根据其在原始表中的位置进行匹配 (因此必须明确行的顺序) 。
如果子查询返回的行数不同，多出的行会被截掉。

示例：

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

注意：在这种情况下，如果采用并行读取，结果可能是不确定的。例如：

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## LATERAL JOIN {#lateral-join}

`JOIN LATERAL` 允许连接右侧的子查询引用其左侧表
表达式中的列。其效果相当于：针对子查询所引用的左侧列值的每种不同组合
分别对该子查询求值，再将其结果与具有该组合的每个左侧行进行连接：

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

与其他任何 `INNER` 或 `LEFT JOIN` 一样，`ON true` 谓词是必需的；省略它会导致语法错误。

该功能自 26.10 版本起可用。它是实验性功能，默认处于禁用状态；可通过
[`enable_lateral_join`](/zh/reference/settings/session-settings/enable#enable_lateral_join) 设置启用。

lateral 子查询既不会针对每个左侧行执行一次，也不会针对每个不同的组合执行一次。与其他关联子查询一样，
它会被去关联为一个覆盖所有左侧行的单一查询：如果该子查询包含聚合，它所引用的左侧列会被添加到其 `GROUP BY` 键中；其 `LIMIT` (如有) 会变为基于这些列的 `LIMIT ... BY`；
其结果则基于这些列与左侧行进行连接。当关联条件是简单的相等比较 (例如 `orders.user_id = u.id`) 时，
左侧列可以替换为子查询中与之相等的列
(`correlated_subqueries_substitute_equivalent_expressions`，默认已启用) ，从而使子查询有可能无需
读取左侧行。但这一点无法保证：例如，不带 `GROUP BY` 的聚合 (如 `count`) 仍会
读取左侧的不同值，以便为没有匹配行的左侧值生成结果。只要左侧的不同值
被传递给子查询，在默认设置下就会经过一个内存中缓冲区；并且只有在
实际使用了该缓冲区时，连接才必定是哈希连接。在其他所有情况下，例如相等替换使子查询无需读取左侧行，或缓冲区被禁用
(`correlated_subqueries_use_in_memory_buffer = 0` 或 `correlated_subqueries_default_join_kind = 'left'`) 时，
算法由 `join_algorithm` 设置决定。例如，对带有 `LIMIT` 的 lateral 子查询执行 `EXPLAIN`，
会显示一个位于 `LimitBy (LIMIT BY for decorrelated correlated subquery)` 步骤之上的 `Join` 步骤；不带
`LIMIT` 的子查询则没有该步骤。

目前仅支持以下子集；其他任何用法都会被拒绝并报错：

* 仅支持 `INNER JOIN LATERAL` 和 `LEFT JOIN LATERAL`；不支持 `RIGHT`、`FULL`、`PASTE` 和 `NATURAL` 连接，且 `LATERAL` 完全不能与 `CROSS` 连接或逗号连接组合使用。
* 仅支持默认的 `ALL` 严格性；不支持 `ANY`、`SEMI`、`ANTI` 和 `ASOF`。
* 除 `ON true` (也接受 `ON 1`) 外，不支持其他连接谓词；不支持 `USING`，且谓词
  不能省略。请将关联两侧的过滤条件写在 lateral 子查询的 `WHERE` 子句中。
* 不支持 `GLOBAL` 和 `LOCAL` 连接修饰符。
* lateral 子查询必须至少引用左侧的一列。对于非关联子查询，请使用普通连接。
* 由于 lateral 子查询会被去关联化，而不是针对每个左侧取值分别求值，
  因此其中不得包含在单个查询内具有非确定性的函数 (例如
  `rand` 或 `generateUUIDv4`) ，也不得包含生成随机行的表函数 (例如 `generateRandom`) 。
  在单个查询内取值不变的函数 (例如 `now`) 则可以使用。
* 仅支持将子查询用作 lateral 表表达式。不支持 PostgreSQL 的表源写法
  `LATERAL unnest(...)` 和 `CROSS JOIN UNNEST(...)`。请改用
  [`ARRAY JOIN`](/zh/reference/statements/select/array-join) 子句。
* lateral 子查询中的 `GROUP BY` 和 `ORDER BY` 会针对所有左侧取值统一执行一次，因此
  `max_rows_to_group_by`、`max_rows_to_sort` 和 `max_bytes_to_sort` 限制统计的是所有左侧取值对应的总行数，
  而非单个取值的行数。这些限制仅支持 `throw` 溢出模式，使用 `any` 和 `break` 会被拒绝。
* 去关联化子查询的结果通过一次连接与左侧行进行匹配。与任何哈希连接一样，
  `max_rows_in_join` 和 `max_bytes_in_join` 限制的是该连接中驻留在内存中的一侧，具体是哪一侧由
  查询规划器决定：当实际使用了上文所述的内存中缓冲区时，是
  `JOIN LATERAL` 的左侧，因为必须先完整读取左侧行，才能对 lateral 子查询求值；否则，可能是去关联化子查询的结果。这些限制始终
  按照 `join_overflow_mode` 为 `throw` 的方式执行：如果使用 `break`，连接会静默丢弃无关的左侧行。

**示例**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS enable_lateral_join = 1;
```

## Distributed JOIN {#distributed-join}

执行涉及分布式表的 JOIN 有两种方式：

* 使用普通 `JOIN` 时，查询会发送到远程服务器。为了构造右表，子查询会在每台服务器上运行，然后基于该表执行 JOIN。换句话说，右表是在每台服务器上分别构造的。
* 使用 `GLOBAL ... JOIN` 时，请求发起方服务器会先运行一个子查询，计算 JOIN 的一侧，并将结果汇集到一个临时表中。随后，这个临时表会传递给每台远程服务器，并使用传输过去的临时数据在这些服务器上执行查询。对于 `LEFT` 和 `INNER` JOIN，右表由该子查询计算得出。

对于严格性为 `ALL`、`ANY`、`SEMI` 或 `ANTI` 的 `GLOBAL RIGHT JOIN`，如果其左表是包含多个分片的 `Distributed` 表，ClickHouse 会交换左右两侧，将该 JOIN 作为 `LEFT JOIN` 执行，从而确保被保留的右表中的每一行只返回一次。此时左表由子查询计算得出；若右表是包含多个分片的 `Distributed` 表，则从其各个分片读取，否则在请求发起方服务器上读取。无法以这种方式交换的 `GLOBAL RIGHT JOIN` 或 `GLOBAL FULL JOIN` 会在请求发起方服务器上执行。此行为自 26.9 版本起生效。

使用 `GLOBAL` 时请务必小心。更多信息，请参见[分布式子查询](/zh/reference/statements/in#distributed-subqueries)部分。

## 空单元格或 NULL 单元格的处理 {#processing-of-empty-or-null-cells}

在 OUTER JOIN 的结果中，对于没有匹配项的行，另一张表的列为空。[`join_use_nulls`](/zh/reference/settings/session-settings/join#join_use_nulls) 设置决定 ClickHouse 如何填充这些单元格：

* `0`：使用列类型的默认值填充这些单元格。
* `1`：使用 `NULL` 填充这些单元格，并将这些列的类型转换为 [Nullable](/zh/reference/data-types/nullable)。如果列的类型无法包装为 `Nullable` (例如 `Array`) ，则保留原有类型，并使用默认值填充。在 `FULL` JOIN 中，已合并的 `USING` 列也会被转换为 `Nullable`。

如果某一行中至少有一个 JOIN 连接键为 `NULL`，则该行不会参与连接，详见 [JOIN 连接键中的 NULL 和 NaN 值](#null-values-in-join-keys)。

## USING 子句 {#using-clause}

`USING` 子句指定一个或多个用于连接的列，并要求这些列的值相等：

* 每一列都必须在左表表达式和右表表达式中以相同名称存在。可以借助子查询中的别名，使列具有相同的名称。
* `USING` 子句只接受列名，不支持表达式。
* 列列表可以加括号，也可以不加括号。
* `USING` 子句中的每一列在结果中只出现一次，其类型参见[隐式类型转换](#implicit-type-conversion)。
* 两个表中的其他列也可以同名。`SELECT *` 会用表名或别名来限定右表中的列；启用 [`single_join_prefer_left_table`](/zh/reference/settings/session-settings/other#single_join_prefer_left_table) 后，未限定的名称会解析为左表中的列。
* 启用 [`analyzer_compatibility_join_using_top_level_identifier`](/zh/reference/settings/session-settings/analyzer-compatibility#analyzer_compatibility_join_using_top_level_identifier) 后，`USING` 中的列名会根据查询中的同名别名 (例如 `SELECT` 列表中的别名) 进行解析。

## 示例 {#examples}

以下查询将每个计数器的 hits 数与每个计数器的 visits 数进行连接。`ANY LEFT JOIN` 会将左侧子查询中的每一行各返回一次，没有 visits 的计数器则取默认值 `0`：

```sql title="Query"
SELECT
    CounterID,
    hits,
    visits
FROM
(
    SELECT
        CounterID,
        count() AS hits
    FROM VALUES('CounterID UInt32', 1, 1, 1, 2, 2, 3)
    GROUP BY CounterID
) AS h
ANY LEFT JOIN
(
    SELECT
        CounterID,
        sum(Sign) AS visits
    FROM VALUES('CounterID UInt32, Sign Int8', (1, 1), (1, 1), (1, -1), (2, 1), (4, 1))
    GROUP BY CounterID
) AS v USING (CounterID)
ORDER BY hits DESC;
```

```response title="Response"
┌─CounterID─┬─hits─┬─visits─┐
│         1 │    3 │      1 │
│         2 │    2 │      1 │
│         3 │    1 │      0 │
└───────────┴──────┴────────┘
```
