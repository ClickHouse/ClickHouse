事务控制语句 `BEGIN TRANSACTION`、`COMMIT`、`ROLLBACK` 和 `SET TRANSACTION SNAPSHOT` 可将针对 `MergeTree` 表的多个查询组合为一个事务。
同一事务中的查询读取的是其他事务已提交变更的同一个一致性快照。
事务外的写入操作不具备隔离性：在事务外执行的 `INSERT`、`TRUNCATE TABLE` 或 `ALTER TABLE ... DELETE`，对正在运行的事务的下一个查询可见。因此，若要获得稳定的视图，写入方也必须使用事务，例如启用 [`implicit_transaction`](/zh/reference/settings/session-settings/implicit#implicit_transaction)。
其他事务只有在 `COMMIT` 之后才能看到该事务的变更，而 `ROLLBACK` 会丢弃这些变更。
在事务外执行的查询可以在正在运行的事务提交之前就看到其变更。

## 语法 {#syntax}

```sql
BEGIN TRANSACTION
START TRANSACTION
COMMIT
ROLLBACK
SET TRANSACTION SNAPSHOT snapshot
```

事务隶属于某个会话，且每个会话最多只能有一个事务。
通过 HTTP 访问时，同一事务中的所有查询都必须使用相同的 `session_id` 发送：未携带 `session_id` 的请求会在其独立的会话中执行，该会话随请求结束而结束。
如果会话结束时事务仍在执行，该事务将被回滚。

## BEGIN TRANSACTION {#begin-transaction}

在当前会话中开启一个事务。`START TRANSACTION` 是其别名，引入版本为 v24.3.0。

不支持嵌套事务：在事务内执行 `BEGIN TRANSACTION` 会抛出 `INVALID_TRANSACTION` 异常。

## COMMIT {#commit}

提交当前事务，并使其更改对其他事务可见。
在没有当前事务的情况下执行 `COMMIT` 会抛出 `INVALID_TRANSACTION` 异常。

如果事务中的某个查询执行失败，该事务将被回滚。如果查询无法解析 (例如存在语法错误) ，或者其查询参数缺失或无效，则该查询不会被执行，事务仍保持运行状态，因此之后执行 `COMMIT` 仍会提交该事务。
已回滚的事务在通过 `ROLLBACK` 结束之前，`COMMIT` 及其后的其他查询都会抛出 `INVALID_TRANSACTION` 异常。此时只有 `ROLLBACK`、`SET TRANSACTION SNAPSHOT` 以及除 `EXPLAIN ANALYZE` 之外的 `EXPLAIN` 查询仍可执行。

[`wait_changes_become_visible_after_commit_mode`](/zh/reference/settings/session-settings/other#wait_changes_become_visible_after_commit_mode) 设置用于控制 `COMMIT` 需要等待的内容。

## ROLLBACK {#rollback}

回滚当前事务并丢弃其所做的更改。
若当前没有活动事务，执行 `ROLLBACK` 会抛出 `INVALID_TRANSACTION` 异常。

## SET TRANSACTION SNAPSHOT {#set-transaction-snapshot}

将当前事务读取的快照更改为提交序列号 (CSN) `snapshot`，例如之前某个事务中 [`transactionLatestSnapshot`](/zh/reference/functions/regular-functions/other-functions#transactionLatestSnapshot) 返回的值。
此后，该事务能看到其自身的更改、在事务之外写入的数据，以及截至该 CSN 已提交事务所做的更改。
它只会读取服务器仍保留的 parts，且不会阻止这些 parts 被移除：一旦合并、变更或其他查询移除了某个 part，且不存在在此之前启动、仍在运行的事务，服务器就可以删除该 part，此时较早的快照将读取不到其中的行。
请勿依赖 `SET TRANSACTION SNAPSHOT` 实现对历史数据的可重复读取。
在没有当前事务的情况下执行 `SET TRANSACTION SNAPSHOT` 会抛出 `INVALID_TRANSACTION` 异常。

`0` 到 `32` 均为预留值，使用时会抛出 `INVALID_TRANSACTION` 异常，但以下两个值除外：
`1` 仅使在事务之外写入的数据以及该事务自身的更改可见；`3` 使表的所有 parts 可见，包括尚未提交的事务的 parts，以及已被事务移除或回滚的 parts。

## 事务中的查询 {#queries-inside-a-transaction}

事务中可以运行 `SELECT`、`INSERT`、`DELETE`、`OPTIMIZE`、`TRUNCATE TABLE`、`SET` 和 `EXPLAIN` 查询，以及 `ALTER TABLE` 变更和分区操作。
其他查询，例如 `CREATE TABLE`、`UPDATE` 或 `ALTER TABLE ... ADD COLUMN`，会抛出 `NOT_IMPLEMENTED` 异常；针对不支持事务的表 (例如 `ReplicatedMergeTree` 表、`Memory` 表或 `system.transactions`) 执行的查询同样会抛出该异常。

事务中不支持异步插入，而 [`async_insert`](/zh/reference/settings/session-settings/async-insert#async_insert) 默认已启用，因此除非禁用 `async_insert` (例如执行 `SET async_insert = 0`) ，否则在事务中执行 `INSERT ... VALUES` 或 `INSERT ... SELECT` 都会抛出 `NOT_IMPLEMENTED` 异常。

当 [`throw_on_unsupported_query_inside_transaction`](/zh/reference/settings/session-settings/throw-on#throw_on_unsupported_query_inside_transaction) 设置为 `0` 时，其中部分查询不会抛出异常，而是在事务之外运行，因此无法通过 `ROLLBACK` 撤销，例如 `CREATE TABLE`，或向 `Memory` 表执行的 `INSERT`。

启用 [`implicit_transaction`](/zh/reference/settings/session-settings/implicit#implicit_transaction) 后，每个在事务之外运行的查询都会在各自独立的事务中执行：查询成功时提交该事务，失败时则回滚。

## 示例 {#examples}

回滚一次插入操作：

```sql title="Query"
CREATE TABLE t (n UInt64) ENGINE = MergeTree ORDER BY n;
SET async_insert = 0;

BEGIN TRANSACTION;
INSERT INTO t VALUES (1);
SELECT count() FROM t;
ROLLBACK;
SELECT count() FROM t;
```

```text title="Response"
┌─count()─┐
│       1 │
└─────────┘
┌─count()─┐
│       0 │
└─────────┘
```

提交插入操作：

```sql title="Query"
BEGIN TRANSACTION;
INSERT INTO t VALUES (2);
COMMIT;
SELECT * FROM t;
```

```text title="Response"
┌─n─┐
│ 2 │
└───┘
```
