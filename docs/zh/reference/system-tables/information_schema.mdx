`INFORMATION_SCHEMA` (或 `information_schema`) 是一个系统数据库，提供一种近乎标准化的、[与 DBMS 无关的视图](https://en.wikipedia.org/wiki/Information_schema)，用于查看数据库对象的元数据。`INFORMATION_SCHEMA` 中的视图通常不如常规系统表完善，但工具可以借助它们以跨 DBMS 的方式获取基础信息。`INFORMATION_SCHEMA` 中各视图的结构和内容应以向后兼容的方式演进，也就是说，只会添加新功能，而不会更改或移除现有功能。从内部实现来看，`INFORMATION_SCHEMA` 中的视图通常映射到常规系统表，例如 [system.columns](/zh/reference/system-tables/columns)、[system.databases](/zh/reference/system-tables/databases) 和 [system.tables](/zh/reference/system-tables/tables)。

```sql
SHOW TABLES FROM INFORMATION_SCHEMA;

-- or:
SHOW TABLES FROM information_schema;
```

## TABLES {#tables}

包含从 [system.tables](/zh/reference/system-tables/tables) 系统表中读取的各列。

列：

* `table_catalog` ([String](/zh/reference/data-types/string)) — 表所在数据库的名称。
* `table_schema` ([String](/zh/reference/data-types/string)) — 表所在数据库的名称。
* `table_name` ([String](/zh/reference/data-types/string)) — 表名。
* `table_type` ([String](/zh/reference/data-types/string)) — 表类型。可能的值：
  * `BASE TABLE`
  * `VIEW`
  * `FOREIGN TABLE`
  * `LOCAL TEMPORARY`
  * `SYSTEM VIEW`
* `table_rows` ([Nullable](/zh/reference/data-types/nullable)([UInt64](/zh/reference/data-types/int-uint))) — 总行数。若无法确定，则为 NULL。
* `data_length` ([Nullable](/zh/reference/data-types/nullable)([UInt64](/zh/reference/data-types/int-uint))) — 磁盘上数据的大小。若无法确定，则为 NULL。
* `index_length` ([Nullable](/zh/reference/data-types/nullable)([UInt64](/zh/reference/data-types/int-uint))) — 主键、次级索引以及所有标记的总大小。
* `table_collation` ([Nullable](/zh/reference/data-types/nullable)([String](/zh/reference/data-types/string))) — 表的默认排序规则。始终为 `utf8mb4_0900_ai_ci`。
* `table_comment` ([Nullable](/zh/reference/data-types/nullable)([String](/zh/reference/data-types/string))) — 创建表时使用的注释。

**示例**

```sql title="Query"
SELECT table_catalog, 
       table_schema, 
       table_name, 
       table_type, 
       table_collation, 
       table_comment
FROM INFORMATION_SCHEMA.TABLES
WHERE (table_schema = currentDatabase() OR table_schema = '')
  AND table_name NOT LIKE '%inner%'
LIMIT 1 
FORMAT Vertical;
```

## VIEWS {#views}

包含在使用表引擎 [View](/zh/reference/engines/table-engines/special/view) 时，从 [system.tables](/zh/reference/system-tables/tables) 系统表中读取的列。

列：

{/*AUTOGENERATED_START*/}

* `table_catalog` ([String](/zh/reference/data-types/string)) — 表所在数据库的名称。
* `table_schema` ([String](/zh/reference/data-types/string)) — 表所在数据库的名称。
* `table_name` ([String](/zh/reference/data-types/string)) — 表名。
* `view_definition` ([String](/zh/reference/data-types/string)) — 视图的 `SELECT` 查询。
* `check_option` ([String](/zh/reference/data-types/string)) — `NONE`，不进行检查。
* `is_updatable` ([Enum8](/zh/reference/data-types/enum)) — `NO`，视图不可更新。
* `is_insertable_into` ([Enum8](/zh/reference/data-types/enum)) — 显示所创建的视图是否为 [materialized](/zh/reference/statements/create/view#materialized-view)。可能的值：
  * `NO` — 所创建的视图不是 materialized。
  * `YES` — 所创建的视图是 materialized。
* `is_trigger_updatable` ([Enum8](/zh/reference/data-types/enum)) — `NO`，触发器不可更新。
* `is_trigger_deletable` ([Enum8](/zh/reference/data-types/enum)) — `NO`，触发器不可删除。
* `is_trigger_insertable_into` ([Enum8](/zh/reference/data-types/enum)) — `NO`，不会向触发器中插入数据。

{/*AUTOGENERATED_END*/}

**示例**

```sql title="Query"
CREATE VIEW v (n Nullable(Int32), f Float64) AS SELECT n, f FROM t;
CREATE MATERIALIZED VIEW mv ENGINE = Null AS SELECT * FROM system.one;
SELECT table_catalog,
       table_schema,
       table_name,
       view_definition,
       check_option,
       is_updatable,
       is_insertable_into,
       is_trigger_updatable,
       is_trigger_deletable,
       is_trigger_insertable_into
FROM information_schema.views
WHERE table_schema = currentDatabase() 
LIMIT 1
FORMAT Vertical;
```

## COLLATIONS {#collations}

提供有关可用排序规则的信息。除 [system.collations](/zh/reference/system-tables/collations) 中的排序规则外，还包含两个用于兼容 MySQL 的行：`utf8mb4_0900_ai_ci` — MySQL protocol 在 handshake、`SCHEMATA.DEFAULT_COLLATION_NAME` 和 `TABLES.TABLE_COLLATION` 中声明的排序规则 — 以及 `binary` — MySQL protocol 在结果集元数据中标记到数值列及其他非字符串列上的伪排序规则 — 以便支持 MySQL 的 client 在此视图中查找已声明的排序规则时能够找到它们。

列：

* `collation_name` ([String](/zh/reference/data-types/string)) — 排序规则的名称。
* `character_set_name` ([Nullable](/zh/reference/data-types/nullable)([String](/zh/reference/data-types/string))) — 关联的字符集 (`utf8mb4_0900_ai_ci` 对应 `utf8mb4`，`binary` 对应 `binary`，否则为 `NULL`) 。为兼容 MySQL 而提供。
* `id` ([Nullable](/zh/reference/data-types/nullable)([UInt64](/zh/reference/data-types/int-uint))) — MySQL 排序规则 ID (`utf8mb4_0900_ai_ci` 为 `255`，`binary` 为 `63`，否则为 `NULL`) 。为兼容 MySQL 而提供。
* `is_default` ([Nullable](/zh/reference/data-types/nullable)([String](/zh/reference/data-types/string))) — 该排序规则是否为其字符集的默认排序规则 (两个 MySQL 兼容行均为 `Yes`，否则为 `NULL`) 。为兼容 MySQL 而提供。
* `is_compiled` ([Nullable](/zh/reference/data-types/nullable)([String](/zh/reference/data-types/string))) — 该排序规则是否已编译到 server 中 (两个 MySQL 兼容行均为 `Yes`，否则为 `NULL`) 。为兼容 MySQL 而提供。
* `sortlen` ([Nullable](/zh/reference/data-types/nullable)([UInt64](/zh/reference/data-types/int-uint))) — 最小排序长度 (`utf8mb4_0900_ai_ci` 为 `0`，`binary` 为 `1`，否则为 `NULL`) 。为兼容 MySQL 而提供。
* `pad_attribute` ([Nullable](/zh/reference/data-types/nullable)([String](/zh/reference/data-types/string))) — 填充属性，`NO PAD` 或 `PAD SPACE` (两个 MySQL 兼容行均为 `NO PAD`，否则为 `NULL`) 。为兼容 MySQL 而提供。

## CHARACTER_SETS {#character_sets}

提供一个静态字符集列表 (`utf8`、`utf8mb4`、`ascii`、`binary`) ，用于兼容 MySQL 工具。ClickHouse 本身使用 UTF-8 编码。

列：

* `character_set_name` ([String](/zh/reference/data-types/string)) — 字符集名称。

## ENGINES {#engines}

提供可用表引擎的相关信息，数据读取自 [system.table&#95;engines](/zh/reference/system-tables/table_engines) 系统表。该视图用于兼容 MySQL。

列：

* `engine` ([String](/zh/reference/data-types/string)) — 表引擎的名称。
* `support` ([String](/zh/reference/data-types/string)) — 若该引擎被设为 [default&#95;table&#95;engine](/zh/operations/settings/settings#default_table_engine)，则值为 `DEFAULT`，否则为 `YES`。

## USER_PRIVILEGES {#user_privileges}

提供全局特权的相关信息，数据读取自 [system.grants](/zh/reference/system-tables/grants) 系统表 (即未指定数据库的行) 。

`*_PRIVILEGES` 视图仅显示正向的、非通配符的授权：部分撤销、通配符授权 (例如 `GRANT SELECT ON db_prefix*.*`) 以及针对参数化特权类型中特定命名对象的授权 (例如 `GRANT TABLE ENGINE ON TinyLog`) 无法以 MySQL 兼容格式表示，因此会被省略。这意味着受部分撤销限制的被授权者，会显示为拥有不受限制的授权。参数化类型的 `ON *` 授权会显示为普通的全局特权。`system.grants` 才是权威数据来源。与 MySQL 不同，这些视图会显示所有用户和角色的授权，且读取这些视图需要具备 `system.grants` 的访问权限，否则查询会失败并抛出 `ACCESS_DENIED` 异常。由于 ClickHouse 不会记录授权的执行者，因此没有 `GRANTOR` 列。

列：

* `grantee` ([String](/zh/reference/data-types/string)) — 被授予特权的用户或角色，采用 MySQL 格式：`'name'@'%'`。MySQL 中没有与角色对应的概念，因此角色的呈现方式与用户相同。
* `table_catalog` ([String](/zh/reference/data-types/string)) — 始终为 `def`。
* `privilege_type` ([String](/zh/reference/data-types/string)) — 特权名称，例如 `SELECT` 或 `ALTER UPDATE`。完整列表请参见 [system.privileges](/zh/reference/system-tables/privileges)。
* `is_grantable` ([String](/zh/reference/data-types/string)) — 如果特权是通过 `WITH GRANT OPTION` 授予的，则为 `YES`，否则为 `NO`。
* `grantee_type` ([String](/zh/reference/data-types/string)) — `USER` 或 `ROLE`。非标准列：在 ClickHouse 中，用户和角色可以同名，此列用于区分此类被授权者。
