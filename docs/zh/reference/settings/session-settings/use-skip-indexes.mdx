## use_skip_indexes {#use_skip_indexes}

<SettingsInfoBlock type="Bool" default_value="1" />

在查询执行期间使用数据跳过索引。

可能的值：

* 0 — 禁用。
* 1 — 启用。

## use_skip_indexes_for_disjunctions {#use_skip_indexes_for_disjunctions}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.12"},{"label": "1"},{"label": "新增设置"}]}]} />

使用跳过索引评估同时包含 AND 和 OR 条件的 WHERE 过滤器。示例：WHERE A = 5 AND (B = 5 OR C = 5)。
禁用时，跳过索引仍会用于评估 WHERE 条件，但其中只能包含通过 AND 连接的子句。

可能的值：

* 0 — 已禁用。
* 1 — 已启用。

## use_skip_indexes_for_disjunctions_max_rpn_elements {#use_skip_indexes_for_disjunctions_max_rpn_elements}

<SettingsInfoBlock type="UInt64" default_value="128" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "128"},{"label": "新增设置，此前该上限硬编码为 32"}]}]} />

对 WHERE 过滤器应用 `use_skip_indexes_for_disjunctions` 时，其内部表示 (RPN) 所允许的最大元素数。
粗略来说，每个条件以及每个 `AND`、`OR` 和 `NOT` 各计为一个元素：例如，`A = 5 OR B = 5 OR C = 5` 包含 5 个元素。
元素数在过滤器为索引分析完成重写之后才统计：例如，`A = 1 OR A = 2 OR A = 3` 会被重写为 `A IN (1, 2, 3)`，只计为一个元素 (参见 `optimize_min_equality_disjunction_chain_length`) ；而 `coalesce(A, B) = 5` 则会展开为多个条件 (参见 `allow_key_condition_coalesce_rewrite`) 。
对于元素数超过该值的过滤器，各跳过索引将分别独立评估，对于由 `OR` 连接、作用于不同列的条件，无法据此跳过粒度。
在索引分析期间，中间结果在每个数据分区片段的每个粒度上为每个元素占用一个比特，而合并这些结果的耗时与每个粒度的元素数成正比。将其设置为 0 (无限制) 时请注意这一点。

可选值：

* 0 — 无限制。
* 正整数 — 最大元素数。

## use_skip_indexes_for_top_k {#use_skip_indexes_for_top_k}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.5"},{"label": "1"},{"label": "默认启用在 TopK 筛选中使用数据跳过索引"}]}, {"id": "row-2","items": [{"label": "25.12"},{"label": "0"},{"label": "新设置。"}]}]} />

启用在 TopK 筛选中使用数据跳过索引。

启用后，如果 `ORDER BY <column> LIMIT n` 查询中的该列上存在 minmax 跳过索引，优化器会尝试使用该 minmax 索引，跳过与最终结果无关的粒度。这可以降低查询延迟。

可能的值：

* 0 — 已禁用。
* 1 — 已启用。

## use_skip_indexes_if_final {#use_skip_indexes_if_final}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.6"},{"label": "1"},{"label": "设置默认值已更改"}]}]} />

控制在使用 FINAL 修饰符执行查询时是否使用跳过索引。

跳过索引可能会排除包含最新数据的行 (粒度) ，从而导致带有 FINAL 修饰符的查询结果不正确。启用此设置后，即使使用 `FINAL` 修饰符，也会应用跳过索引，这可能提升性能。结果是否正确仍取决于 `use_skip_indexes_if_final_exact_mode` 设置；该设置默认启用，并会扫描与跳过索引返回的范围重叠的额外 parts。仅当该设置被禁用时，才存在遗漏最近更新的风险。

可能的值：

* 0 — 禁用。
* 1 — 启用。

## use_skip_indexes_if_final_exact_mode {#use_skip_indexes_if_final_exact_mode}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.6"},{"label": "1"},{"label": "设置的默认值已更改"}]}, {"id": "row-2","items": [{"label": "25.5"},{"label": "0"},{"label": "引入此设置是为了帮助 FINAL 查询在使用跳过索引时返回正确结果"}]}]} />

控制在使用 FINAL 修饰符执行查询时，是否在较新的 parts 中扩展跳过索引返回的粒度范围，以确保结果正确。

使用跳过索引时，可能会排除包含最新数据的行 (粒度) ，从而导致结果不正确。此设置可通过扫描与跳过索引返回范围重叠的较新 parts，确保返回正确结果。仅当应用可以接受基于跳过索引查找得到的近似结果时，才应禁用此设置。

可选值：

* 0 — 已禁用。
* 1 — 已启用。

## use_skip_indexes_on_data_read {#use_skip_indexes_on_data_read}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.1"},{"label": "1"},{"label": "默认启用"}]}, {"id": "row-2","items": [{"label": "25.9"},{"label": "0"},{"label": "新增设置"}]}]} />

启用在读取数据时使用数据跳过索引。

启用后，跳过索引会在读取每个数据粒度时动态评估，而不是在查询执行开始前预先分析。这可以减少查询启动延迟。

可能值：

* 0 — 禁用。
* 1 — 启用。
