<div id="enable_adaptive_aggregator">
  ## enable_adaptive_aggregator
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "新增设置，用于启用自适应 `GROUP BY` 聚合：每个线程的本地哈希表达到 `adaptive_aggregator_freeze_threshold` 个键后即冻结。高频键继续在较小的本地表中聚合，低频键则根据其哈希值路由到各桶的积压队列，并在桶并行合并期间仅聚合一次；因此低频键只需存储和处理一次，而非每个线程各处理一次。"}]}]} />

启用自适应 `GROUP BY` 算法：每个线程先在本地哈希表中聚合，直至达到 `adaptive_aggregator_freeze_threshold` 个键 (或占用 `adaptive_aggregator_freeze_threshold_bytes` 内存) ，随后该表冻结。已出现过的高频键对应的行会继续原地更新该表；新的低频键则根据其哈希值路由到各桶的积压队列，并在桶并行合并期间仅聚合一次。高频键保留在可驻留于缓存的小型表中，低频键则只需存储和处理一次，而非每个线程各处理一次。

遵循外部聚合设置 (`max_bytes_before_external_group_by`、`max_bytes_ratio_before_external_group_by`) ：超过阈值后，会将积压队列提前排空至共享表；如果仍无法降至阈值以下，则通过常规外部聚合将共享表落盘。

<div id="enable_group_by_top_k_optimization">
  ## enable_group_by_top_k_optimization
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "用于控制 `GROUP BY key ORDER BY key LIMIT N` 查询中聚合阶段 TopK 筛选优化的新设置。"}]}]} />

在 `GROUP BY keys ORDER BY <prefix of keys> LIMIT K` 查询中，以及不含 `ORDER BY` 的 `GROUP BY keys LIMIT K` 查询中启用聚合阶段的 TopK 筛选优化 (后者中任意 `K` 个组都是有效结果，因此会合成为所有键排序) 。

启用后，聚合器会维护一个有界堆，其中保存截至当前排名前 `K` 的键；当新行的分组键无法进入最终结果时，便跳过将其插入哈希表。这样可避免聚合后续会被 `ORDER BY ... LIMIT` 丢弃的行；当堆按完整的 `GROUP BY` 键进行排名时，还会从中间哈希表中移除被逐出的组，使哈希表大小受 `LIMIT` 限制，而非受不同键的数量限制。当 `ORDER BY` 仅覆盖 `GROUP BY` 键的真前缀时，排名无法识别完整的组，因此只能跳过行：哈希表会保留所有已接纳的组，其大小仍可能随其余键列的基数增长。

当请求的 `LIMIT` 大于 [query&#95;plan&#95;max&#95;limit&#95;for&#95;top&#95;k&#95;optimization](/zh/reference/settings/session-settings/query-plan#query_plan_max_limit_for_top_k_optimization) 或硬性上限 `100000` 时，此优化会被禁用，因为堆的内存和 CPU 开销会随请求的 `LIMIT` 增长。

对于修剪组可能改变结果的查询形态，此优化会被跳过，包括 `WITH TOTALS`、`HAVING`、`QUALIFY`、窗口函数、`ROLLUP`/`CUBE`/`GROUPING SETS`、`LIMIT WITH TIES`、任一匹配的 `GROUP BY` 键上的 `COLLATE` (完整键前缀之后的 `ORDER BY` 列上的 `COLLATE` 不会影响哪些组可入选，因此不会禁用此优化) 、按聚合结果或任何并非 `GROUP BY` 键前导前缀的内容执行的 `ORDER BY`，以及设置了 `max_rows_to_group_by` 或 `exact_rows_before_limit` 的情况。

可能的值：

* 0 — 已禁用。
* 1 — 已启用。

<div id="enable_packed_string_keys_in_aggregation">
  ## enable_packed_string_keys_in_aggregation
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "用于切换基于 `PackedStringRef` 的哈希表的新设置，适用于单个 `String` 键的 GROUP BY。previous_value=false，因此设置 `compatibility` 为 26.8 之前的版本时，会恢复基于旧版 `StringHashTable` 的方法，包括其两级分桶机制。"}]}]} />

对于只有一个不可为 NULL 的 `String` 键的 `GROUP BY`，使用以 16 字节压缩字符串引用 (`PackedStringRef`) 为键的哈希表。长度不超过 11 字节的键以内联方式存储在压缩引用中；较长的键则引用 Arena 中的内容。
这对大多数工作负载而言更快，但对于不同键数量极少且键长度超过 11 字节 (尤其是 12..24 字节) 的 `GROUP BY`，其速度可能比旧版方法更慢；旧版哈希表会将键内联保存在单元中，而压缩方法每次探测时都需要解引用 Arena 指针。
禁用时，将使用基于旧版 `StringHashTable` 的方法 (26.8 之前的默认方法) 。

参与分布式查询的所有服务器必须使用相同的值：使用 `distributed_aggregation_memory_efficient` 时，两级桶编号取决于键的哈希值，而两种方法的键哈希不同，因此设置值不一致的服务器可能会将同一个键分到不同桶中，导致合并结果不正确。为确保一致性，发起者始终会随次级查询发送其生效值 (即使该值仅来自服务器/profile 默认值) ，从而覆盖远程服务器自身的默认值。
