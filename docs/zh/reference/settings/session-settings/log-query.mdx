## log_query_plans {#log_query_plans}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "新增设置，用于捕获实际执行的查询计划及各步骤的运行时统计信息。"}]}]} />

将实际执行的查询计划及其各步骤的运行时统计信息写入 [`system.query_log`](/zh/reference/system-tables/query_log) 的 `query_plan` 列。该列为 `JSON` 类型，因此统计信息以数值形式存储，不仅可以直接读取，还可以通过查询进行聚合。

该执行计划包含的信息与 [`EXPLAIN ANALYZE`](/zh/reference/statements/explain#explain-analyze) 显示的信息相同：步骤树、每个步骤的作用，以及每个步骤的行数、字节数、挂钟时间和并行度。

仅捕获使用 analyzer 执行的 `SELECT` 查询 (`enable_analyzer = 1`，即默认值) ，且仅在该行本身会被写入时才捕获，因此还必须启用 [`log_queries`](/zh/reference/settings/session-settings/log-queries#log_queries)。对于执行期间失败的查询，会捕获其失败时正在运行的执行计划，但不包含统计信息。`QueryStart` 行中该列为空，因为写入这些行时尚未生成执行计划。

与 `query` 列一样，执行计划会使用服务器的 [`query_masking_rules`](/zh/reference/settings/server-settings/settings/query#query_masking_rules) 进行脱敏。如果某个查询的文本或查询参数命中了任一规则，则不会存储其执行计划，因为常量折叠可能会将被脱敏的文本以任何规则都无法匹配的形式带入执行计划。对于其他查询，执行计划中的所有文本 (例如过滤条件、`IN` 列表和输出列名) 都会在存储前进行脱敏。包含机密参数 (例如 `encrypt` 的密钥) 的查询同样不会存储执行计划，因为无法在执行计划中可靠地隐藏这些参数。

启用此设置后，被捕获的查询会收集每个处理器的耗时数据，所用插桩与 [`log_processors_profiles`](/zh/reference/settings/session-settings/log#log_processors_profiles) 相同，因此会带来一定开销。未被捕获的查询不受影响。可使用 [`log_query_plans_probability`](/zh/reference/settings/session-settings/log-query#log_query_plans_probability) 仅对查询进行随机抽样捕获。

是否产生该开销在查询运行前就已确定，因此即使被捕获查询的行随后被 [`log_queries_min_type`](/zh/reference/settings/session-settings/log-queries#log_queries_min_type) 或 [`log_queries_min_query_duration_ms`](/zh/reference/settings/session-settings/log-queries#log_queries_min_query_duration_ms) 丢弃，该查询仍需承担这一开销，因为在这么早的阶段还无法判断这两项条件是否满足。直接由[查询缓存](/zh/concepts/features/performance/caches/query-cache)返回结果的查询不会执行任何执行计划，因此也没有可存储的执行计划。

此外，该设置还会保留 (而非丢弃) 执行计划优化所生成的步骤描述 (例如合并后的表达式) ，因此这些描述同样会出现在 `system.processors_profile_log.plan_step_description` 中。

## log_query_plans_join_matches {#log_query_plans_join_matches}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "0"},{"label": "新增设置，用于为写入 `system.query_log` 的查询计划收集连接的精确匹配行数指标。"}]}]} />

当 [`log_query_plans`](/zh/reference/settings/session-settings/log-query#log_query_plans) 捕获某个查询时，如果匹配行数指标无法从连接本身的输出中推导得出，则让该查询中的连接执行额外的统计工作以收集这些指标，作用与 [`EXPLAIN ANALYZE`](/zh/reference/statements/explain#explain-analyze-join-steps) 的 `matches` 设置相同。对于可以推导得出的指标，即使不启用此设置也会存储。

仅当启用了 `log_query_plans` 且该查询被捕获时，此设置才会生效。

## log_query_plans_max_size {#log_query_plans_max_size}

<ExperimentalBadge />

<SettingsInfoBlock type="UInt64" default_value="1048576" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "1048576"},{"label": "新增设置，用于限制存储在 `system.query_log` 中的查询执行计划大小。即使通过 `compatibility` 兼容早期版本，该限制仍会保留：该列本身是新增的，不存在需要恢复的早期行为，而且该限制用于保护服务器资源。"}]}]} />

由 [`log_query_plans`](/zh/reference/settings/session-settings/log-query#log_query_plans) 写入 [`system.query_log`](/zh/reference/system-tables/query_log) 的 `query_plan` 列中的文档的最大大小 (以字节为单位) 。

查询本身决定了其执行计划包含多少文本：较大的 `IN` 列表、较长的别名或折叠后的常量都会被渲染到执行计划中。此设置限制了单个查询可在其所在行中存储的内容；同时，由于文档会被写入该大小的缓冲区，它也限制了渲染单个执行计划时可分配的内存。

超出大小限制的执行计划不会以截断形式存储，因为不完整的文档无法构成有效的执行计划。此时，该列会改为存储原因，格式为 `{"Error": ...}`。

`0` 表示不限制。

## log_query_plans_probability {#log_query_plans_probability}

<ExperimentalBadge />

<SettingsInfoBlock type="Float" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "1"},{"label": "新增设置：在启用 `log_query_plans` 时，仅对随机抽取的查询样本捕获查询计划。"}]}]} />

对于由 [`log_query_plans`](/zh/reference/settings/session-settings/log-query#log_query_plans) 启用的查询计划捕获，仅对按指定概率随机选取的查询样本执行。未被选中的查询无需承担 [`log_query_plans`](/zh/reference/settings/session-settings/log-query#log_query_plans) 带来的性能分析开销，其 `system.query_log` 行仍会照常写入，只是 `query_plan` 列为空。

是否选中按查询逐一判定，且在确认该查询的执行计划可被捕获之后才进行，因此永远不会被捕获的查询 (例如 `SELECT` 以外的查询) 不参与采样。

该设置在 [`log_queries_probability`](/zh/reference/settings/session-settings/log-queries#log_queries_probability) 的基础上叠加生效：未写入行的查询同样不会捕获执行计划，因此当两个设置均为 `0.5` 时，约有四分之一的查询会捕获执行计划。

由于判定在查询运行之前进行，因此无法根据查询耗时来决定。与 [`log_queries_min_query_duration_ms`](/zh/reference/settings/session-settings/log-queries#log_queries_min_query_duration_ms) 搭配使用时，每个慢查询仍会写入其对应的行，但其中只有指定比例的行带有执行计划；与此同时，所有查询 (包括快速查询) 中都有同样比例的查询需要承担性能分析开销。

可选值：

* 0 — 不捕获任何查询计划。
* 范围 [0..1] 内的正浮点数。例如，若设置值为 `0.1`，则大约每十个查询中会有一个捕获执行计划。
* 1 — 捕获所有查询的执行计划。

## log_query_plans_time {#log_query_plans_time}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "0"},{"label": "新增设置，用于为写入 `system.query_log` 的查询计划收集每个步骤的挂钟时间和并发级别。"}]}]} />

当 [`log_query_plans`](/zh/reference/settings/session-settings/log-query#log_query_plans) 捕获某个查询时，还会收集其处理器的工作时间区间，作用与 [`EXPLAIN ANALYZE`](/zh/reference/statements/explain#explain-analyze-concurrency) 的 `time` 设置相同。这样，存储在 `system.query_log.query_plan` 中的执行计划会在各步骤上带有 `Time` 和 `Concurrency` 分组，记录每个步骤及其分支的挂钟时间和并发级别；并在根节点带有一个 `ExecutionTimeBreakdown`，将执行时间拆分为三部分：在计划各步骤中花费的时间、在步骤之外花费的时间，以及没有任何线程运行时的空闲时间。

收集这些数据所消耗的内存和 CPU 与查询运行的处理器任务数量成正比，因此查询越长，开销越大；此外，查询结束后处理这些数据也会增加查询的耗时。

仅当已启用 `log_query_plans` 且该查询被捕获时，此设置才会生效。

<div id="log_query_threads">
  ## log_query_threads {#log_query_threads}
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

设置是否记录查询线程日志。

查询线程会记录到 [system.query&#95;thread&#95;log](/zh/reference/system-tables/query_thread_log) 表中。此设置仅在 [log&#95;queries](/zh/reference/settings/session-settings/log-queries#log_queries) 为 true 时生效。启用此设置后，ClickHouse 运行的查询线程会按照服务器配置参数 [query&#95;thread&#95;log](/zh/reference/settings/server-settings/settings/query#query_thread_log) 中的规则进行记录。

可能的值：

* 0 — 禁用。
* 1 — 启用。

**示例**

```text
log_query_threads=1
```

<div id="log_query_views">
  ## log_query_views {#log_query_views}
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

启用查询视图日志记录。

当 ClickHouse 在启用此设置时执行的查询存在关联视图 (materialized 或 live view) 时，这些视图会记录到 [query&#95;views&#95;log](/zh/reference/settings/server-settings/settings/query#query_views_log) 服务器配置参数中。

示例：

```text
log_query_views=1
```
