## external_storage_push_down_limit {#external_storage_push_down_limit}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "1"},{"label": "新增设置：在安全的情况下，将查询中的 `LIMIT` 下推到发送给外部数据库的查询中。previous_value=false，因此将 `compatibility` 设置为 26.10 之前的版本会恢复原有行为（不下推）。"}]}]} />

允许将查询中的 `LIMIT` 子句下推到发送给外部数据库 (例如 MySQL、PostgreSQL 或 SQLite) 的查询中。

通用的 ODBC/JDBC 桥接器不会执行下推，因为它们无法提供远程端的 `LIMIT` 语法，而且部分受支持的数据库根本不接受 `LIMIT` 子句。

只有在能够确保安全时才会下推 `LIMIT`，即逻辑上先于 `LIMIT` 执行的所有子句都会原样复制到外部查询中。具体而言，该查询必须是简单的单表 `SELECT`：

* 不包含 `JOIN`、`ARRAY JOIN`、`SAMPLE` 或 `FINAL` (否则行可能会在本地被删除或变换，此时不应预先限制行数) ；
* 如果存在 `WHERE` 子句，它必须完全兼容，并原样复制到重写后的查询中 (否则在远程 `LIMIT` 之后再进行过滤会丢失部分行) ；
* 不包含其他可能因数据重排、聚合或过滤而破坏远程预限制逻辑的子句或修饰符 (如 `DISTINCT`、`GROUP BY`、`ORDER BY`、`LIMIT BY`、`WITH TIES` 等) ；
* 允许使用 `OFFSET`：它在本地应用，因此被跳过的行同样需要读取，发送给外部数据库的限制值为 `offset + length`；
* `SELECT` 列表中的每个源行只对应一个结果行，即不包含聚合函数、窗口函数或 `arrayJoin` (也写作 `unnest`)  (它们会在本地基于从外部表读取的全部行进行计算) ；
* 不存在在本地对从外部表读取的行额外应用的过滤器，例如行策略或 `additional_table_filters` (此类过滤器在 `LIMIT` 之前执行，远程预限制可能会丢弃本应保留的行) 。

该设置可以减少从外部数据库读取的数据量及其发送的数据量。如遇兼容性问题，可禁用此设置以恢复之前的行为。
