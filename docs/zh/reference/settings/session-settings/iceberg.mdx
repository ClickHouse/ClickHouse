## iceberg_list_only_v_prefixed_metadata_files {#iceberg_list_only_v_prefixed_metadata_files}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "新增设置：查找按路径读取的 Iceberg 表的最新元数据文件时，仅列出 `metadata\/v` 键前缀。"}]}]} />

在 S3 或 Azure 上查找按路径读取的 Iceberg 表的最新元数据文件时，仅列出键前缀 `metadata/v`，从而避免列出同样存储在 `metadata` 目录中的清单文件。如果该前缀下存在 `.metadata.json` 文件，则仅将这些文件作为候选结果；否则会列出整个目录。使用 `iceberg_use_version_hint`、`iceberg_metadata_file_path`、`iceberg_metadata_table_uuid` 或 `iceberg_recent_metadata_file_by_last_updated_ms_field` 时，该设置不生效；该设置也不适用于数据湖目录数据库中的表。

仅当表的所有元数据文件均以 `v<N>...` 命名时 (ClickHouse 和 Hadoop 目录均采用此命名方式) 才应启用此设置：如果目录中还存在 `<N>-<uuid>.metadata.json` 文件，这些文件永远不会成为候选结果，因此其写入器提交的变更将无法被识别。

## iceberg_tolerate_conflicting_manifest_schemas {#iceberg_tolerate_conflicting_manifest_schemas}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "新增设置：当 Iceberg manifest 文件头中携带的 schema 与 metadata.json 中为同一 schema-id 注册的 schema 冲突时，优先采用 metadata.json 中的 schema，而不是让查询失败，从而与其他查询引擎的行为保持一致。将 `compatibility` 设为低于 26.8 的版本可恢复此前的严格行为。"}]}, {"id": "row-2","items": [{"label": "26.10"},{"label": "1"},{"label": "该变更已回移到 26.8，并记录在该版本中。"}]}]} />

启用时，如果 Iceberg manifest 文件的 schema-id 已在 metadata.json 中注册，则使用 metadata.json 中的 schema，并直接忽略 manifest 文件头 `schema` 键中的副本，不做任何比较。禁用时，会将 manifest 头中的副本与 metadata.json 中的 schema 进行比较，一旦存在冲突，查询将以 ICEBERG&#95;SPECIFICATION&#95;VIOLATION 错误失败。

manifest 头中的 schema 只是 manifest 写入时表 schema 的一份副本，而据观察，某些写入器 (例如 AWS S3 Tables 维护作业) 会在其中存储质量降级的副本。其他查询引擎均从 metadata.json 解析 schema 并忽略存在差异的头部副本，因此这里的默认行为与之保持一致。但两个 metadata.json schema 定义之间的冲突始终仍会导致查询失败。
