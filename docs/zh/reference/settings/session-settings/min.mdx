## min_compress_block_size {#min_compress_block_size}

<SettingsInfoBlock type="UInt64" default_value="65536" />

用于 [MergeTree](/zh/reference/engines/table-engines/mergetree-family/mergetree) 表。为了降低查询处理延迟，在写入下一个标记时，如果某个块的大小至少达到 `min_compress_block_size`，就会对该块进行压缩。默认值为 65,536。

如果未压缩数据小于 `max_compress_block_size`，则块的实际大小不会小于该值，也不会小于一个标记对应的数据量。

我们来看一个示例。假设在创建表时将 `index_granularity` 设为 8192。

假设我们写入的是一个 UInt32 类型的列 (每个值 4 字节) 。写入 8192 行时，总数据量为 32 KB。由于 min&#95;compress&#95;block&#95;size = 65,536，因此每两个标记会形成一个压缩块。

假设我们写入的是一个 String 类型的 URL 列 (每个值平均 60 字节) 。写入 8192 行时，平均数据量会略小于 500 KB。由于这大于 65,536，因此每个标记都会形成一个压缩块。在这种情况下，从磁盘读取单个标记范围内的数据时，不会额外解压其他数据。

<Note>
  这是一个专家级设置；如果你刚开始使用 ClickHouse，不建议修改它。
</Note>

## min_marks_per_part_to_load_statistics {#min_marks_per_part_to_load_statistics}

<SettingsInfoBlock type="UInt64" default_value="64" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "64"},{"label": "新增设置：当主键分析后仅剩少量数据需要读取时，跳过统计信息的加载。"}]}]} />

主键分析之后，对于每个统计信息尚未载入内存的数据分区片段，剩余待读取标记数的最小值。只有达到该值时，才会加载列统计信息，用于裁剪 parts 以及对 `PREWHERE` 条件排序。

加载统计信息需要对每个数据分区片段执行若干次读取。如果主键已将读取范围缩小到少量粒度，在冷启动时，加载统计信息的耗时可能比读取数据本身还长。如果剩余待读取的标记数少于该设置值与需加载统计信息的 parts 数量的乘积，则不会为上述优化加载统计信息：parts 不会基于统计信息进行裁剪，`PREWHERE` 条件将按其列的大小排序，与没有统计信息的表一致。已在内存中的统计信息则无论读取量大小都会被使用。

可选值：

* 0 — 无论读取量大小，均加载统计信息。
* 正整数 — 每个数据分区片段的标记数。

## min_outstreams_per_resize_after_split {#min_outstreams_per_resize_after_split}

<SettingsInfoBlock type="UInt64" default_value="24" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.6"},{"label": "24"},{"label": "新设置。"}]}]} />

指定在管道生成期间执行拆分后，`Resize` 或 `StrictResize` 处理器的最少输出流数量。如果生成的流数量小于该值，则不会执行拆分操作。

### 什么是 Resize 节点 {#what-is-a-resize-node}

`Resize` 节点是查询管道中的一种处理器，用于调整管道中数据流的数量。它既可以增加流的数量，也可以减少流的数量，从而在多个线程或处理器之间平衡工作负载。例如，如果查询需要更高的并行度，`Resize` 节点可以将单个 stream 拆分为多个流。反过来，它也可以将多个流合并为更少的流，以集中处理数据。

`Resize` 节点可确保数据在各个流之间均匀分布，同时保持数据块的结构。这有助于优化资源利用率并提升查询性能。

### 为什么需要拆分 Resize 节点 {#why-the-resize-node-needs-to-be-split}

在管道执行过程中，作为中心枢纽的 `Resize` 节点，其 ExecutingGraph::Node::status&#95;mutex 会出现严重争用，尤其是在高核数环境下。这种争用会导致：

1. ExecutingGraph::updateNode 的延迟升高，直接影响查询性能。
2. 大量 CPU 周期浪费在自旋锁争用 (native&#95;queued&#95;spin&#95;lock&#95;slowpath) 上，降低整体效率。
3. CPU 利用率下降，限制并行度和吞吐量。

### Resize 节点如何拆分 {#how-the-resize-node-gets-split}

1. 首先会检查输出流数量，以确保可以执行拆分：每个拆分后处理器的输出流都必须达到或超过 `min_outstreams_per_resize_after_split` 阈值。
2. `Resize` 节点会被拆分为多个更小的 `Resize` 节点，这些节点的端口数量相同，每个节点分别处理一部分输入流和输出流。
3. 各组会独立处理，从而减少锁竞争。

### 拆分具有任意输入/输出的 Resize 节点 {#splitting-resize-node-with-arbitrary-inputsoutputs}

在某些情况下，如果输入/输出的数量无法被拆分后的 `Resize` 节点数整除，就会将部分输入连接到 `NullSource`，并将部分输出连接到 `NullSink`。这样就能在不影响整体数据流的情况下完成拆分。

### 设置的用途 {#purpose-of-the-setting}

`min_outstreams_per_resize_after_split` 设置可确保对 `Resize` 节点进行拆分是有意义的，并避免生成过少的流，因为这可能导致并行处理效率低下。通过强制设定输出流的最小数量，该设置有助于在并行度与开销之间保持平衡，从而在涉及流拆分与合并的场景中优化查询执行。

### 禁用该设置 {#disabling-the-setting}

要禁用对 `Resize` 节点的拆分，请将此设置设为 0。这样会阻止在管道生成期间拆分 `Resize` 节点，使其保留原有结构，而不会被拆分为更小的节点。

## min_rows_for_packed_string_keys_in_hash_join {#min_rows_for_packed_string_keys_in_hash_join}

对于右侧有行数估算值的哈希连接，仅当使用精确键的哈希表大致超过 CPU 的 L2 缓存时，或此设置为 0 时，才会对其 `String` 键进行打包 (参见 `enable_packed_string_keys_in_hash_join`) 。表的大小等于右侧行数乘以单行字节数，其中单行字节数为 32 字节的单元加上键的平均长度 (长度未知时按 0 计) 。较小的连接从打包键中获益甚微，甚至可能变慢。

超过 15 字节的打包键会针对左侧的每一行计算哈希。若连接带有运行时过滤器，且该过滤器主要只放行有匹配项的行 (参见 `enable_join_runtime_filters`) ，则只需对匹配的行计算哈希，因此无需设定最小值。若没有此类过滤器，此设置即为右侧行数的最小值。此设置在键的平均长度超过 15 字节时生效；长度未知时同样生效，因为此时按长键处理。键的长度可从该键的 `basic` 列统计信息中获知。`MergeTree` 表默认会收集这些统计信息，参见 `auto_statistics_types`。

当键是 `Memory` 表的列、子查询中聚合函数的结果，或 `ON` 中表达式 (例如 `concat(k, 'x')` 或 `hex(k)`) 的结果时，该键没有统计信息。带有 `OR` 的连接不会使用统计信息。仅原样传递该列或按该列分组的子查询会保留统计信息。

除 `SEMI` 和 `ANTI` 之外的 `LEFT` 连接以及 `FULL` 连接会保留左侧的所有行，因此不会生成运行时过滤器。`LEFT ANTI` 连接的过滤器放行的是没有匹配项的行，因此不计在内。

如果启用了 `collect_hash_table_stats_during_joins`，行数取自同一连接上一次执行时的右侧行数；否则取查询优化器的估算值，`parallel_hash_join_threshold` 也使用该估算值。若没有优化器估算值，则取本服务器读取右表时自身的估算值。若两者都没有，连接会对键进行打包，除非规划该查询的服务器估算的右侧行数低于此最小值。分布式查询中的每个服务器都会根据自身的估算值、统计信息和缓存大小各自做出决定。

设为 0 时对所有连接的键都进行打包。
