这些设置用于配置 ClickHouse 服务器，由 ClickHouse 源代码自动生成。

## workloads_respect_server_cpu_limit {#workloads_respect_server_cpu_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />

启用后，服务器级 CPU 并发度限制将通过工作负载调度器实施。如果两个角色均未定义资源，则会隐式创建一个 CPU 资源 `__server_cpu__` (用于 `MASTER THREAD` 和 `WORKER THREAD`) ，同时根工作负载 (名称为空的工作负载) 的 `max_concurrent_threads` 将根据 `concurrent_threads_soft_limit_num` 和 `concurrent_threads_soft_limit_ratio_to_cores` 推导得出，从而使所有工作负载共享由这些设置确定的同一份 CPU 槽位预算。此后，CPU 调度将由工作负载调度器负责，不再使用内置的并发度控制。

请将 `implicit_default_workload` 与此设置一同启用 (或定义一个 `default` 工作负载) 。只有归入某个工作负载的查询才受此预算限制。如果没有 `default` 工作负载，则使用 `workload` 设置默认值的查询，以及使用默认工作负载的后台合并与变更，将完全不受 CPU 限制：内置的并发度控制 (`concurrent_threads_soft_limit_num`) 也不再对它们生效。若设置了 `throw_on_unknown_workload = 1`，此类查询将直接失败。

可在运行时更改。默认禁用。

**示例**

```xml
<workloads_respect_server_cpu_limit>true</workloads_respect_server_cpu_limit>
```

## workloads_respect_server_memory_limit {#workloads_respect_server_memory_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />

启用后，服务器级内存限制将作为内存预留预算，通过工作负载调度器生效。如果未定义任何 `MEMORY RESERVATION` 资源，则会隐式创建资源 `__server_memory__`，并且根工作负载 (名称为空的工作负载) 的 `max_memory` 由 `max_server_memory_usage` (及其 RAM 比率) 推导得出，因此所有工作负载共享取自该设置的同一份内存预留预算。该预算用于预留准入，并不会替代进程级内存限制，后者仍然有效。该预算在加载或重新加载配置时取自已配置的 `max_server_memory_usage`；它不会随 `memory_worker_dynamic_hard_limit` 在运行时对进程级限制所做的调整而变化，因此在两次重新加载之间，它可能大于当前生效的限制。

请将 `implicit_default_workload` 与此设置一同启用 (或定义一个 `default` 工作负载) 。只有被归类到某个工作负载的查询才会从该预算中预留内存：如果没有 `default` 工作负载，使用 `workload` 设置默认值的查询不会从中预留内存；而当 `throw_on_unknown_workload = 1` 时，此类查询会直接失败。后台合并与变更从不从工作负载中预留内存，因此其内存在任何情况下都不计入该预算。

可在运行时更改。默认禁用。

**示例**

```xml
<workloads_respect_server_memory_limit>true</workloads_respect_server_memory_limit>
```
