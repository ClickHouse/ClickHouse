这些设置用于配置 ClickHouse 服务器，并由 ClickHouse 源代码自动生成。

## use_minimalistic_part_header_in_zookeeper {#use_minimalistic_part_header_in_zookeeper}

已废弃的设置，不起任何作用。[复制](/zh/reference/engines/table-engines/mergetree-family/replication)表始终使用单个 `znode` 以紧凑方式存储数据分区片段的头信息。旧版本写入的分区片段头信息 (使用独立的 `columns` 和 `checksums` 子 `znodes` 存储) 仍可正常读取。

## use_separate_cache_arena {#use_separate_cache_arena}

<SettingsInfoBlock type="Bool" default_value="1" changeable_without_restart="No" />

为缓存分配启用专用的 jemalloc arena (标记缓存、未压缩缓存、页缓存) 。
将缓存数据与查询处理中的内存分配隔离开来，从而减少内存碎片。

## use_shared_merge_tree_log_pipeline {#use_shared_merge_tree_log_pipeline}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="No" />

仅在 ClickHouse Cloud 中可用。启用后，系统日志将通过 `SharedMergeTree` 管道写入，
并且 `system` 数据库会变为共享数据库，因此所有副本看到的日志表都是相同的。

每次刷写日志时，都会使用 `s3` (或 `azureBlobStorage`) 表函数将一个 `Native` 文件写入该
日志当前生成所对应的文件夹，生成由日志的列和键的哈希决定。对于每个生成，管道会维护读取该文件夹的队列 `system._<log>_s3queue_<hash>`、
materialized view `system._<log>_mv_<hash>` 以及 `SharedMergeTree` 表 `system.<log>_<hash>`。
`system.<log>` 是基于所有生成的 `Merge` 表。schema 变化时会创建新的生成；设置、生存时间 (TTL) 和索引
则取自日志配置中的 `smt_settings`、`smt_ttl` 和 `smt_indices` 键，并在原表上直接修改。
这些对象会在日志首次刷写时创建，也可以通过 `prepare_system_log_tables_on_startup` 在启动时创建。
表的 sorting key 由 `hostname` 加上日志的键组成，这样即可按键读取某个副本的行。
日志配置中的 `smt_order_by` 和 `smt_partition_by` 键可用于替换表的键。

启用该设置期间，本地 `system` 数据库会被重命名为 `system_local`。需要在服务器配置中设置 `shared_database_catalog`
和 `<shared_log_pipeline><endpoint>`。
另请参阅：`shared_log_pipeline.enable_sync_flush`、`shared_log_pipeline.flush_timeout_seconds`。
