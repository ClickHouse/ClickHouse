在生产环境中部署 ClickStack 开源版时，请参考以下在安全性、稳定性和配置方面的实践建议。

## 网络与端口安全 {#network-security}

默认情况下，Docker Compose 会在宿主机上暴露端口，使其可从容器外部访问——即使启用了 `ufw` (Uncomplicated Firewall) 等工具也不例外。这一行为源于 Docker 网络栈的工作机制：若未进行显式配置，它可以绕过宿主机级别的防火墙规则。

**建议：**

仅开放生产环境所需的端口，通常包括 OTLP 端点、API 服务器和前端。

例如，删除或注释掉 `docker-compose.yml` 文件中不必要的端口映射：

```yaml
ports:
  - "4317:4317"  # OTLP gRPC
  - "4318:4318"  # OTLP HTTP
  - "8080:8080"  # Only if needed for the API
# Avoid exposing internal ports like ClickHouse 8123 or MongoDB 27017.
```

有关隔离容器和加固访问控制的详细信息，请参阅 [Docker 网络文档](https://docs.docker.com/network/)。

## 会话密钥配置 {#session-secret}

在生产环境中，必须为 ClickStack 用户界面的 `EXPRESS_SESSION_SECRET` 环境变量设置一个高强度的随机值，以保护会话数据并防止篡改。

以下示例展示了如何在 `docker-compose.yml` 文件中为 app 服务添加该变量：

```yaml
  app:
    image: ${IMAGE_NAME_HDX}:${IMAGE_VERSION}
    ports:
      - ${HYPERDX_API_PORT}:${HYPERDX_API_PORT}
      - ${HYPERDX_APP_PORT}:${HYPERDX_APP_PORT}
    environment:
      FRONTEND_URL: ${HYPERDX_APP_URL}:${HYPERDX_APP_PORT}
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_API_PORT: ${HYPERDX_API_PORT}
      HYPERDX_APP_PORT: ${HYPERDX_APP_PORT}
      HYPERDX_APP_URL: ${HYPERDX_APP_URL}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      MINER_API_URL: 'http://miner:5123'
      MONGO_URI: 'mongodb://db:27017/hyperdx'
      NEXT_PUBLIC_SERVER_URL: http://127.0.0.1:${HYPERDX_API_PORT}
      OTEL_SERVICE_NAME: 'hdx-oss-api'
      USAGE_STATS_ENABLED: ${USAGE_STATS_ENABLED:-true}
      EXPRESS_SESSION_SECRET: "super-secure-random-string"
    networks:
      - internal
    depends_on:
      - ch-server
      - db1
```

您可以使用 `openssl` 生成一个高强度的密钥：

```shell
openssl rand -hex 32
```

请勿将机密信息提交到源代码管理系统。在生产环境中，建议使用环境变量管理工具 (例如 Docker Secrets、HashiCorp Vault 或针对特定环境的 CI/CD 配置) 。

## 安全摄取 {#secure-ingestion}

所有摄取都应通过 ClickStack 发行版 OpenTelemetry (OTel) 采集器所暴露的 OTLP 端口进行。默认情况下，摄取需要使用启动时生成的安全摄取 API key。向 OTel 端口发送数据时必须提供该 key，可在 ClickStack 用户界面的 `Team Settings → API Keys` 下找到。

### 创建摄取用户 {#create-a-database-ingestion-user-oss}

建议为 OTel collector 创建专用用户，用于将数据摄取到 ClickHouse，并确保摄取数据发送至指定数据库 (例如 `otel`) 。详情请参阅 [&quot;创建摄取用户&quot;](/zh/clickstack/ingesting-data/collector#creating-an-ingestion-user)。

## ClickHouse {#clickhouse}

自行管理 ClickHouse 实例的用户应遵循以下最佳实践。

### 安全最佳实践 {#self-managed-security}

如果您自行管理 ClickHouse 实例，务必启用 **TLS**、强制执行身份验证，并遵循最佳实践来加固访问控制。有关真实环境中常见的错误配置及其规避方法，请参阅[这篇博客文章](https://www.wiz.io/blog/clickhouse-and-wiz)。

ClickHouse OSS 开箱即提供强大的安全功能，但需要经过配置才能生效：

* **使用 TLS**：在 `config.xml` 中通过 `tcp_port_secure` 和 `<openSSL>` 进行配置。请参阅 [guides/sre/configuring-tls](/zh/concepts/features/security/tls/configuring-tls)。
* **为 `default` 用户设置强密码**，或禁用该用户。
* **避免将 ClickHouse 暴露到外部**，除非确有需要。默认情况下，只要未修改 `listen_host`，ClickHouse 仅绑定到 `localhost`。
* **使用身份验证方法**，例如密码、证书、SSH 密钥或[外部身份验证器](/zh/concepts/features/security/external-authenticators/index)。
* **限制访问**：使用 IP 过滤和 `HOST` 子句。请参阅 [sql-reference/statements/create/user#user-host](/zh/reference/statements/create/user#user-host)。
* **启用基于角色的访问控制 (RBAC)**，以授予细粒度权限。请参阅 [operations/access-rights](/zh/concepts/features/security/access-rights)。
* **强制执行配额和限制**：使用[配额](/zh/concepts/features/configuration/server-config/quotas)、[设置 profile](/zh/concepts/features/configuration/settings/settings-profiles) 和只读模式。
* **对静态数据进行加密**，并使用安全的外部存储。请参阅 [operations/storing-data](/zh/concepts/features/configuration/server-config/storing-data) 和 [cloud/security/CMEK](/zh/products/cloud/guides/security/cmek)。
* **避免硬编码凭据。** 请使用[命名集合](/zh/concepts/features/configuration/server-config/named-collections)，或在 ClickHouse Cloud 中使用 IAM 角色。
* **审计访问和查询**：使用[系统日志](/zh/reference/system-tables/query_log)和[会话日志](/zh/reference/system-tables/session_log)。

另请参阅[外部身份验证器](/zh/concepts/features/security/external-authenticators/index)和[查询复杂度设置](/zh/concepts/features/configuration/settings/query-complexity)，了解如何管理用户并实施查询/资源限制。

### ClickStack 用户界面的用户权限 {#user-permissions}

ClickStack 用户界面所使用的 ClickHouse 用户应设置为 `readonly = 2`。UI 会在每个查询中附带自身的设置 (例如 `date_time_output_format`) ，原始 SQL 图表也会设置 `readonly = 2`。因此，`readonly = 1` 的用户执行这些查询时会失败，并报错 `Cannot modify '...' setting in readonly mode`。设置为 `readonly = 2` 后，UI 还可以设置 `max_rows_to_read`、`read_overflow_mode` 和 `cancel_http_readonly_queries_on_client_close`；如需限制 `max_rows_to_read`，请至少允许一百万行。`wait_end_of_query` 是 HTTP 接口参数，而不是设置，因此无需为其授权。

示例：

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

默认情况下，OSS 版和 ClickHouse Cloud 中的 `default` 用户均已具备这些权限，但我们建议创建一个专用用户。

## 配置生存时间 (TTL) {#configure-ttl}

请确保已为您的 ClickStack 部署[适当配置](/zh/clickstack/managing/ttl#modifying-ttl)[生存时间 (TTL)](/zh/clickstack/managing/ttl)。该设置控制数据的保留时长——默认值为 30 天，可能需要根据实际需求进行调整。

## MongoDB 使用准则 {#mongodb-guidelines}

请遵循 MongoDB 官方的[安全检查清单](https://www.mongodb.com/docs/manual/administration/security-checklist/)。
