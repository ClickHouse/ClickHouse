ClickStack 的各个组件均提供以下配置选项：

<div id="modifying-settings">
  ## 开源发行版设置 {#modifying-settings}
</div>

### Docker {#docker}

如果使用 [All in One](/zh/clickstack/deployment/all-in-one)、[仅 ClickStack 用户界面](/zh/clickstack/deployment/hyperdx-only) 或 [Local Mode](/zh/clickstack/deployment/local-mode-only)，只需通过环境变量传入所需设置，例如：

```shell
docker run -e HYPERDX_APP_PORT=8081 -p 8081:8081 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-all-in-one:latest
```

### Docker Compose {#docker-compose}

如果使用 [Docker Compose](/zh/clickstack/deployment/docker-compose) 部署指南，可以通过 [`.env`](https://github.com/ClickHouse/clickstack/blob/main/.env) 文件修改设置。

或者，也可以直接在 [`docker-compose.yml`](https://github.com/ClickHouse/clickstack/blob/main/docker-compose.yml) 文件中显式覆盖这些设置，例如：

示例：

```yaml
services:
  app:
    environment:
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      # ... other settings
```

### Helm {#helm}

请参考 [Helm 部署指南](/zh/clickstack/deployment/helm) 安装 Operator 和 ClickStack chart。自定义部署前，请先获取当前 chart 的配置值：

```shell
helm show values clickstack/clickstack > values.yaml
```

通过 chart 的配置值分别为应用程序和采集器设置环境变量，然后应用您的配置：

```shell
helm upgrade --install my-clickstack clickstack/clickstack -f values.yaml
```

有关支持的配置值、入口、资源以及 Secret 的配置方法，请参阅 [Helm 配置](/zh/clickstack/deployment/helm-configuration)。旧版 `hyperdx/hdx-oss-v2` chart 的配置值结构与此不同。

## ClickStack 用户界面 应用 {#hyperdx}

### 连接 {#connection-settings}

在团队设置中配置数据源所使用的数据库连接。

| 设置项                        | 描述                                                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `Connection Name`          | 在数据源设置中用于标识此连接的名称。                                                                                          |
| `Host`                     | ClickHouse HTTP(S) 端点，需包含端口。该端点与采集器的导出端点相互独立。                                                               |
| `Username`                 | ClickHouse 用户名，默认为 `default`。                                                                               |
| `Password`                 | ClickHouse 密码，默认为空。                                                                                         |
| `Query Log Setting Prefix` | 可选的自定义 ClickHouse 设置前缀，用于在查询日志中记录当前用户的电子邮件。必须在 ClickHouse 的 `custom_settings_prefixes` 配置中加入相同的前缀，否则查询将被拒绝。 |
| `Prometheus compatible`    | 该选项可用时，会将 Host 视为与 Prometheus 兼容的 API 端点，用于代理 PromQL 查询。此连接不能用于基于 ClickHouse 的日志、链路追踪或 OTel 指标数据源。          |

### 数据源设置 {#datasource-settings}

ClickStack 用户界面 依赖用户为每一种可观测性数据类型/支柱定义一个数据源：

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

此配置可在应用内的 `Team Settings -> Sources` 中完成，下面以日志为例：

<div className="ch-image-md">
  <Frame>
    ![ClickStack 用户界面数据源配置](/images/use-cases/observability/hyperdx-25.webp)
  </Frame>
</div>

每个数据源都需要配置表和列的映射，ClickStack 用户界面才能查询其数据。指标数据源可以为不同的指标类型分别使用不同的表。编辑现有数据源时会显示 `Enabled` 开关；数据源级别的 `Query Settings` 最多支持十个名称/值对。

如果使用 ClickStack 附带的[默认 OpenTelemetry (OTel) schema](/zh/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema)，则每个数据源所需的这些列都可以自动推断出来。如果[修改 schema](#clickhouse)或使用自定义 schema，则用户需要指定并更新这些映射。

<Note>
  采集器会根据其 [schema 配置](#collector-schema-and-retention)，通过模式迁移或旧版由导出器管理的 schema 创建方式来建表。列映射遵循 OpenTelemetry 规范，包括[日志数据模型](https://opentelemetry.io/docs/specs/otel/logs/data-model/)。
</Note>

#### PromQL {#promql-source-settings}

启用 PromQL 后，即可创建 PromQL source。除了通用的名称、连接、数据库、表、查询设置和已启用等字段外，它还包含 **Minimum auto granularity** (最小自动粒度) 设置。对于 ClickHouse 连接，请选择使用 `TimeSeries` 引擎的表。时间戳表达式会自动设置。最小自动粒度还决定了计算 `$__rate_interval` 时所用的抓取时间间隔；如果未设置，则默认抓取时间间隔为 15 秒。

`NEXT_PUBLIC_IS_LOCAL_MODE` 是 [Local Mode 发行版](/zh/clickstack/deployment/local-mode-only) 的前端构建标志，并非通用的开发开关。请使用相应的发行版，而不要在现有部署上禁用身份验证。`IS_LOCAL_MODE` 和 `IS_OSS` 是应用程序中的常量名称，而不是需要设置的环境变量。`NEXT_PUBLIC_IS_OSS` 是构建设置，并非企业版开关。当前应用程序已不再使用 `MINER_API_URL`。

如果使用所提供的反向代理配置部署到子路径，请将 `HYPERDX_BASE_PATH` 和 `NEXT_PUBLIC_HYPERDX_BASE_PATH` 设置为相同的前缀 (例如 `/clickstack`) ，并在 `FRONTEND_URL` 中包含该前缀。

部分前端设置在构建时读取。具体来说，若要更改 `NEXT_PUBLIC_HYPERDX_BASE_PATH` (部署路径前缀) 、`NEXT_PUBLIC_NOINDEX` (搜索引擎索引) 或发行版的模式标志，需要使用新值重新构建前端。通过 `next-runtime-env` 读取的运行时设置 (例如 `NEXT_PUBLIC_INSTANCE_LABEL`) 则可以在容器启动时提供。

<div id="clickhouse">
  ## ClickHouse {#clickhouse}
</div>

ClickStack 开源版附带了一个面向多 TB 规模的默认 ClickHouse 配置，但用户也可以根据自身工作负载自由修改和优化。

要有效调优 ClickHouse，你需要理解一些关键存储概念，例如 [parts](/zh/concepts/core-concepts/parts)、[分区](/zh/concepts/core-concepts/partitions)、[分片和副本](/zh/guides/oss/deployment-and-scaling/shards)，以及 [合并](/zh/concepts/core-concepts/merges) 如何在写入时发生。我们建议你先了解 [主索引](/zh/concepts/core-concepts/primary-indexes)、[稀疏二级索引](/zh/concepts/features/performance/skip-indexes/skipping-indexes) 和数据跳过索引的基础知识，以及[管理数据生命周期](/zh/guides/use-cases/observability/build-your-own/managing-data)的相关方法，例如使用生存时间 (TTL) 进行生命周期管理。

ClickStack 支持 [schema 自定义](/zh/guides/use-cases/observability/build-your-own/schema-design)——你可以修改列类型、提取新字段 (例如从日志中提取) 、应用编解码器和字典，并使用 projections 加速查询。

此外，materialized views 可用于[在摄取期间转换或过滤数据](/zh/guides/use-cases/observability/build-your-own/schema-design#materialized-columns)，前提是数据写入该视图的源表，并且应用程序从目标表读取数据。materialized views 也可用于在 ClickStack 中[以原生方式加速查询](/zh/clickstack/managing/materialized-views)。

更多详情请参阅 ClickHouse 关于 schema 设计、索引策略和数据管理最佳实践的文档——其中大部分内容都可直接应用于 ClickStack 部署。
