<Note>
  本页介绍的是 **Self-managed ClickHouse Observability**。如需体验推荐的全托管方案，请参阅[此处](/zh/clickstack/observability/getting-started)的文档。

本**指南面向 ClickHouse Cloud 的现有用户**。如果您是 ClickHouse Cloud 的新用户，建议参阅 Self-managed ClickHouse Observability 的[入门指南](/zh/clickstack/self-configured/getting-started/managed)。

在此部署模式下，ClickHouse 和 ClickStack 用户界面均托管在 ClickHouse Cloud 中，从而最大限度地减少需要用户自行托管的组件数量。

除了减轻基础设施管理负担外，此部署模式还可确保身份验证与 ClickHouse Cloud SSO/SAML 集成。与自托管部署不同，您也无需预配 MongoDB 实例来存储应用程序状态 (例如仪表盘、保存的搜索、用户设置和告警) 。此外，用户还可获得以下优势：

* 计算资源可独立于存储自动扩缩容
* 基于对象存储，实现低成本且几乎无限的数据保留
* 可通过 仓库 [独立隔离读写工作负载](/zh/clickstack/self-configured/managing/isolating-read-write)
* 集成的身份验证
* 自动备份
* 安全与合规功能
* 无缝升级

在此模式下，数据摄取完全由用户负责。您可以通过自行托管的 OpenTelemetry 采集器、客户端库直接摄取、ClickHouse 原生表引擎 (例如 Kafka 或 S3) 、ETL 流水线，或 ClickPipes (ClickHouse Cloud 的托管摄取服务) 将数据摄取到 Self-managed ClickHouse Observability 中。这是运行 ClickStack 最简单、性能最佳的方式。

### 适用场景 {#suitable-for}

此部署模式非常适合以下场景：

1. 您已在 ClickHouse Cloud 中存储了可观测性数据，并希望使用 ClickStack 对其进行可视化。
2. 您运营着大规模的可观测性部署，需要借助运行在 ClickHouse Cloud 上的 ClickStack 获得专属的性能和可扩展性。
3. 您已在使用 ClickHouse Cloud 进行数据分析，并希望使用 ClickStack 插桩库对应用程序进行插桩，将数据发送到同一集群。这种情况下，我们建议使用[仓库](/zh/products/cloud/features/infrastructure/warehouses)为可观测性工作负载隔离计算资源。

### 创建数据库和表 {#create-database-and-tables}

            Vector 要求在数据摄取之前预先定义好表和 schema。

            首先创建一个数据库。此操作可通过 [ClickHouse Cloud 控制台](/zh/products/cloud/features/sql-console-features/sql-console)完成。

            例如，创建一个用于存储日志的数据库：

            ```sql
            CREATE DATABASE IF NOT EXISTS logs
            ```

            然后创建一张表，使其 schema 与日志数据的结构相匹配。以下示例假定使用经典的 Nginx 访问日志格式：

            ```sql
            CREATE TABLE logs.nginx_logs
            (
                `time_local` DateTime,
                `remote_addr` IPv4,
                `remote_user` LowCardinality(String),
                `request` String,
                `status` UInt16,
                `body_bytes_sent` UInt64,
                `http_referer` String,
                `http_user_agent` String,
                `http_x_forwarded_for` LowCardinality(String),
                `request_time` Float32,
                `upstream_response_time` Float32,
                `http_host` String
            )
            ENGINE = MergeTree
            ORDER BY (toStartOfMinute(time_local), status, remote_addr);
            ```

            您的表必须与 Vector 生成的输出 schema 保持一致。请根据您的数据按需调整 schema，并遵循推荐的 [schema 最佳实践](/zh/concepts/best-practices/select-data-type)。

            我们强烈建议您先了解 ClickHouse 中[主键](/zh/concepts/core-concepts/primary-indexes)的工作原理，并根据您的访问模式选择排序键。关于如何选择主键，请参阅 [ClickStack 专用](/zh/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key)指南。

## 其他任务 {#additional-tasks}

### 授予 Self-managed ClickHouse Observability 的访问权限 {#configure-access}

1. 在 ClickHouse Cloud 控制台中进入您的服务
2. 前往 **设置** → **SQL 控制台访问权限**
3. 为每个用户设置相应的权限级别：
   * **服务管理员 → 完全访问** - 启用告警时必需
   * **服务只读 → 只读** - 可查看可观测性数据并创建仪表盘
   * **无权限** - 无法访问 ClickStack 用户界面

<div className="ch-image-md">
  <Frame>
    ![ClickHouse Cloud 只读](/images/clickstack/read-only-access.webp)
  </Frame>
</div>

<Warning>
  **告警需要管理员权限**

  要启用告警，必须至少有一位拥有 **服务管理员** 权限 (在 SQL 控制台访问权限下拉列表中对应 **完全访问**) 的用户登录过一次 ClickStack 用户界面。此操作会在数据库中预配一个专用用户，用于运行告警查询。
</Warning>

### 在只读计算资源上使用 ClickStack {#clickstack-read-only-compute}

ClickStack 用户界面可以完全运行在只读的 ClickHouse Cloud 服务上。如需将摄取工作负载与查询工作负载相互隔离，建议采用此配置。

#### ClickStack 如何选择计算资源 {#how-clickstack-selects-compute}

ClickStack 用户界面始终连接到您在 ClickHouse Cloud 控制台中启动它时所在的 ClickHouse 服务。

这意味着:

* 如果您从只读服务中打开 ClickStack,ClickStack 用户界面发出的所有查询都将在该只读计算资源上运行。
* 如果您从读写服务中打开 ClickStack,ClickStack 则会使用该读写计算资源。

无需在 ClickStack 中进行任何额外配置,即可确保只读行为。

#### 推荐设置 {#recommended-setup}

要在只读计算资源上运行 ClickStack：

1. 在仓库中创建或选定一个配置为只读的 ClickHouse Cloud 服务。
2. 在 ClickHouse Cloud 控制台中，选择该只读服务。
3. 从左侧导航菜单启动 ClickStack。

启动后，ClickStack 用户界面会自动绑定到该只读服务。

请注意，仪表盘、保存的搜索、告警和数据源的作用域仅限于启动 ClickStack 的那个服务，因此在仓库中其他服务上保存的任何内容在此处均不可用，需要重新创建。使用标准 OpenTelemetry schema 的数据源会被自动检测，因此可以立即搜索这些数据；而自定义或手动配置的数据源不会被自动检测，必须重新设置。

有关完整的拓扑 (包括摄取应指向哪个服务、应在哪个服务上执行 DDL，以及告警的行为方式) ，请参阅[“隔离读写工作负载”](/zh/clickstack/self-configured/managing/isolating-read-write)。

### 添加更多数据源 {#adding-data-sources}

ClickStack 原生支持 OpenTelemetry，但并不局限于 OpenTelemetry——如有需要，您也可以使用自己的表结构。

下文介绍如何在自动配置的数据源之外添加其他数据源。

#### 使用 OpenTelemetry schema {#using-otel-schemas}

ClickStack 会自动检测采用标准 OpenTelemetry schema 的表，并为日志、链路追踪和指标创建相应的数据源，无需确认对话框，也无需手动创建 source。

如需查看或调整自动创建的 source，请打开 **团队设置 → 数据 → 数据源**，然后展开对应的 source。以下示例展示了 `otel_logs` 表对应的日志源。

<Info>
  **关联数据源**

## Schema 选择：Map 与 JSON {#schema-choice-map-vs-json}

ClickStack 默认将属性存储在 `Map(LowCardinality(String), String)` 列中，这也是可观测性工作负载推荐使用的 schema。配合[分桶映射序列化](/zh/reference/data-types/map#bucketed-map-serialization)以及针对 Map 键和值构建的文本索引，它能够实现高选择性的查找，同时避免动态 JSON 子列带来的逐键摄取开销。

基于 `JSON` 类型的 schema 目前处于 Beta 阶段，适用于在属性键集合较小且稳定的工作负载上进行评估，**不建议**将其作为默认选项。有关完整对比以及启用 JSON 支持所需的环境变量，请参阅 [Map 与 JSON 类型](/zh/clickstack/self-configured/ingesting-data/schema/map-vs-json)。
