本指南将引导您为现有的 Self-managed ClickHouse Observability 服务部署 OpenTelemetry 采集器，或调整现有采集器，最后验证数据是否正常流入。

```bash
npx skills add clickhouse/agent-skills
```

采集器以 **gateway** 角色运行：它作为单一 OTLP 端点，接收应用程序、SDK 和 agent 采集器发送的数据。gateway 会对事件进行批处理，执行您配置的处理逻辑，然后通过 [ClickHouse 导出器](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) 将其写入 ClickHouse。这种模式可将采集逻辑与应用程序代码分离，使摄取能力能够独立于产生数据的工作负载进行扩展。有关 gateway 与 agent 角色的背景信息，请参阅[采集器角色](/zh/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured)。

<Info>
  **现有采集器**

  如果您使用的是现有的 OpenTelemetry 采集器，我们假定它已配置为 **gateway** 角色。不建议使用此流程重新配置 **agent** 角色的采集器。
</Info>

      <Step title="部署采集器" id="deploy-the-collector">
        部署 **ClickStack 发行版 OpenTelemetry 采集器**，该采集器已针对自管理 ClickHouse Observability 完成预配置。为简单起见，下面的示例在本地运行采集器，并在同一台机器上生成模拟遥测数据。

        <Note>
          在生产环境中，通常会将采集器部署在 Kubernetes 集群中，或部署在 OpenTelemetry SDK、agent 及其他采集器均可访问的虚拟机上。这样即可集中收集整个环境中的遥测数据，并将其转发到 ClickStack。
        </Note>

        选择一个共享密钥，用于对向采集器发送数据的客户端进行身份验证，然后将其与连接详情以及为 `hyperdx_ingest` 用户设置的密码一并导出为环境变量：

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        运行 ClickStack OTel 收集器：

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        采集器现已在端口 `4317` 上提供 OTLP gRPC 服务，在端口 `4318` 上提供 OTLP HTTP 服务。应用程序、SDK 和 agent 采集器应将数据发送到这些端口，并在请求头中携带 `authorization: $OTLP_AUTH_TOKEN`。

        <Info>
          **生产环境部署**

          在生产环境中，建议为 OTLP 端点启用 TLS。请参阅[保护采集器](/zh/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured)。
        </Info>
      </Step>

      <Step title="验证端点" id="verify-the-endpoint">
        向采集器发送一些合成流量，以确认整条管道运行正常。这里我们使用 OpenTelemetry Collector Contrib 提供的生成器 [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen)，它可以发送 OTLP 日志、链路追踪和指标，并提供多个标志，用于按服务、严重级别、跨度状态和指标类型调整所生成数据的分布。

        直接使用其 Docker 镜像运行 (无需安装) 。定义一个简单的包装器，让下文的命令更简洁易读；`--add-host` 使容器能够访问在主机上监听的采集器：

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        或者，也可以使用 Go 安装该二进制文件，并改为指向 `localhost`：

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```

        <Info>
          **预期结果**

          每次 `tg` 运行持续约 20 秒 (由 `--duration 20s` 设定) ，期间会持续输出详细日志，这属于正常现象；每次运行会在 20 秒后自行结束。以下日志足以确认管道正常工作；可选的更丰富数据集会额外进行几次运行，耗时几分钟。
        </Info>

        定义一个小型 `tg` 辅助函数，这样每条命令只需指定各不相同的部分 (服务、严重级别、状态、属性) ：

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        发送来自各个服务、严重级别混合且贴近真实场景的日志：以信息级别为主，外加一条警告和一条错误，而不是清一色的错误日志流：

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        仅靠日志即可确认端点工作正常。如需更丰富的演示数据集、包含多个服务的服务地图以及覆盖各类指标类型的图表，还请展开并运行下方的命令。这些命令会复用 `tg` 辅助函数，因此请在同一个 shell 中运行。

        <Accordion title="生成更丰富的遥测数据（可选）">
          从多个健康的服务和一个出现故障的依赖发送包含多个跨度的链路追踪。这样既能让服务地图呈现贴近真实的形态 (大多数服务运行正常，只有一个服务报错) ，又能为错误视图填充数据：

          ```shell
          # Healthy services: the bulk of the traffic, all spans Ok
          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          发送涵盖三种常见类型的指标，让图表中同时包含计数器、Gauge 和分布：

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          如需让数据更加多样，可以再添加几个服务和一个指数直方图：

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        如需了解完整的标志列表及更多用法，请参阅[使用 telemetrygen 生成合成数据](/zh/clickstack/observability/example-datasets/telemetrygen#self-managed)。
      </Step>

      <Step title="调整采集器配置" id="adapt-collector">
        扩展现有的采集器配置，通过 [ClickHouse 导出器](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) 将数据写入自管理 ClickHouse Observability。

        <Info>
          **需要 ClickHouse 导出器**

          如果您使用的是自己的发行版，请确保其中包含 ClickHouse 导出器。上游的 [contrib 镜像](https://github.com/open-telemetry/opentelemetry-collector-contrib) 已内置该导出器。
        </Info>

        以下示例配置将 ClickHouse 导出器与 ClickStack 用户界面所需的接收器、处理器和流水线搭配使用，其行为与 ClickStack 发行版一致，包括会话回放 (`rrweb`) 的路由路径。请将 `<clickhouse_cloud_endpoint>` 和 `<your_password_here>` 替换为上文所创建的 `hyperdx_ingest` 用户的凭证：

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        需要注意以下几点：

        * `otlp/hyperdx` 接收器同时监听 gRPC (`4317`) 和 HTTP (`4318`) 端口；应用程序和 agent 应将数据发送到采集器主机上的这些端口。
        * `clickhouse` 导出器将日志、链路追踪和指标写入 `otel` 数据库，其布局与 ClickStack 用户界面的要求一致。`clickhouse/rrweb` 导出器负责处理会话回放事件，这些事件由 `routing/logs` 连接器路由至 `otel.hyperdx_sessions`。
        * OTLP 接收器的身份验证沿用您现有的设置。如需强制要求摄取令牌，可通过采集器[扩展](https://opentelemetry.io/docs/collector/configuration/#extensions) (例如 `bearertokenauth`) 或前置 TLS 的反向代理进行配置。

        使用新配置重新加载采集器。之后，应用程序、SDK 和 agent 采集器即可携带您的设置所要求的身份验证请求头，将数据发送到采集器公开的 OTLP 端点。

        有关如何针对 Self-managed ClickHouse Observability 配置 OpenTelemetry 收集器的更多详细信息，请参阅[使用 OpenTelemetry 摄取数据](/zh/clickstack/observability/ingesting-data/opentelemetry#self-managed)。
      </Step>

      <Step title="验证端点" id="verify-the-endpoint-existing">
        向采集器发送一些合成流量，以确认整条管道运行正常。这里使用 [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen)，即 OpenTelemetry Collector Contrib 提供的生成器。它可以发送 OTLP 日志、链路追踪和指标，并提供多个标志，可按服务、严重级别、跨度状态和指标类型来定制生成的数据。

        ```shell
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"

        export OTEL_ENDPOINT=<your-collector-host>:4317
        export OTLP_AUTH_TOKEN=<your-auth-token>
        ```


## 后续步骤：发送您自己的数据 {#next-steps}

上文生成的合成突发数据仅用于验证管道能否正常工作。要开始发送真实的遥测数据，请使用 [ClickStack SDKs](/zh/clickstack/observability/ingesting-data/sdks) 对您自己的服务进行插桩。这些 SDK 为 Node.js、Python、Go、Java 等语言提供插桩支持，可将 OTLP 数据导出到您刚刚验证过的采集器端点。完整示例请参阅[对应用程序进行插桩](/zh/clickstack/self-configured/managed-onboarding/instrument-application)。

如需从基础设施 (而非应用程序代码) 采集数据，请参阅：

* [监控 Kubernetes](/zh/clickstack/self-configured/managed-onboarding/monitoring-kubernetes)：采集集群中的日志、基础设施指标和 Kubernetes 事件。
