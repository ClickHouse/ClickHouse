<Note>
  本页介绍的是 **Self-managed ClickHouse Observability**。如需使用推荐的全托管方案，请参阅[此处](/zh/clickstack/observability/overview)的文档。
</Note>

如果您已运行 ClickStack 一段时间，可能已经注意到，默认 schema 无需任何更改即可应对大多数可观测性工作负载。本页面向默认 schema 已不够用的情况：查询延迟开始上升，或者您的访问模式已逐渐偏离默认设计。

在实践中，以下四种优化基本涵盖了最有效的手段，大致按实施难度由低到高排列。前两种是局部的 `ALTER TABLE` 更改，可以以增量方式逐步推行。第三种适用于仪表盘上反复执行相同聚合的场景，收益明显。第四种需要进行表迁移，因此实施起来最为复杂。

以下摘要特意写得较为简短。有关每项更改的原理、基准测试，以及将其应用于现有数据的具体方法，请参阅[性能调优](/zh/clickstack/self-configured/managing/performance-tuning)。

<Steps>
  <Step title="物化频繁查询的属性" id="materialize-attributes">
    对 `LogAttributes['service.version']` 进行过滤时，ClickHouse 需要为其检查的每一行加载并解码整个 `LogAttributes` Map。将该属性提升为 `MATERIALIZED` 列后，同样的过滤就变成了列读取，速度通常会快一个数量级。列创建后，ClickStack 会自动重写该过滤条件，因此已保存的搜索和仪表盘无需任何改动即可照常使用。

    请只挑选您真正经常查询的属性。每个 materialized 列都会占用存储并增加写入时开销，因此原则是“用什么就提升什么”，而不是“全部提升”。

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    已有行的新列将保持为空，除非您另外执行 `ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion`。

    了解更多：[物化频繁查询的属性](/zh/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes)。
  </Step>

  <Step title="添加跳过索引" id="add-skip-indexes">
    借助跳过索引，ClickHouse 能够排除不可能满足过滤条件的数据粒度，从而将全量扫描变为小范围的定向读取。以下三种类型值得了解：

    * **文本索引** (`text(tokenizer = ...)`) ，用于字符串列以及 `mapKeys`/`*AttributeItems` 数组。默认的日志 schema 已内置此类索引。
    * **Min-max 索引**，用于按范围过滤的数值列。trace 的 `Duration` 就是典型场景。
    * **Bloom filter**，适用于尚不支持文本索引的 ClickHouse 版本，用于高基数等值查找。

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    只有当跳过索引确实能裁剪粒度时，其评估开销才物有所值。在认定其有效之前，请先在具有代表性的查询上使用 `EXPLAIN indexes = 1` 加以确认。

    了解更多：[添加跳过索引](/zh/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes)。
  </Step>

  <Step title="预计算重复的聚合" id="materialized-views">
    当仪表盘上反复运行相同的聚合 (按错误率排列的头部服务、各端点的 p99 延迟、每分钟请求数) 时，materialized view 会在写入时计算结果，并将其写入一张小型 rollup 表。此后仪表盘查询的是 rollup 表，而非原始日志或链路追踪数据，开销相比之下要低得多。

    当仪表盘访问频繁且底层表很大时，这种做法收益最明显。代价是写入时会消耗一定 CPU，并且需要多维护一张表。

    了解更多：[利用 materialized view](/zh/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views)。
  </Step>

  <Step title="根据访问模式选择主键" id="choose-primary-key">
    主键决定了行在磁盘上的排序方式。对主键前导列进行过滤时，ClickHouse 可以直接定位到相关区域；而不以这些列开头的过滤则会扫描整个分区。

    默认的日志主键 `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)` 适合“服务 X 在过去 N 分钟内发生了什么”这类查询。如果您的大多数查询以其他列开头 (例如 tenant id、客户 id、区域) ，那么将主键改为以该列开头，就是收效最显著的优化。

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- 与 otel_logs 相同的列
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse 不允许原地修改主键，因此这需要进行表迁移，而非简单的 `ALTER`。性能调优指南详细介绍了如何创建新表、重定向摄取，以及如何借助 `Merge` 表让现有仪表盘同时覆盖新旧数据并照常使用。

    了解更多：[修改主键](/zh/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key)。
  </Step>
</Steps>
