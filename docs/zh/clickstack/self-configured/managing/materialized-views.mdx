## 简介 {#introduction}

Self-managed ClickHouse Observability 可以使用[增量物化视图 (IMV) ](/zh/concepts/features/materialized-views/incremental-materialized-view)来加速依赖大量聚合查询的可视化，例如按时间计算每分钟的平均请求耗时。该功能可以显著提升查询性能，通常在较大规模的部署中 (每天约 10 TB 及以上) 收益最为明显，同时支持扩缩容至每天 PB 级的数据量。增量物化视图目前处于 Beta 阶段，请谨慎使用。

<Note>
  告警同样可以受益于物化视图，并会自动加以利用。
  这可以降低运行大量告警带来的计算开销，尤其是告警通常执行得非常频繁。
  缩短执行时间既有助于提升响应速度，也有助于降低资源消耗。
</Note>

## 什么是增量物化视图 {#what-are-incremental-materialized-views}

增量物化视图可以将计算开销从查询时转移到写入时，从而显著提升 `SELECT` 查询的速度。

与 Postgres 等事务型数据库不同，ClickHouse 的 materialized view 并不是存储下来的快照，而是充当触发器：每当数据块插入源表时，便对这些数据块运行查询，并将查询输出写入单独的 target table。随着更多数据插入，新的部分结果会被追加并合并到 target table 中。合并后的结果等同于对整个原始数据集执行聚合。

使用物化视图的主要目的在于，写入 target table 的数据是聚合、过滤或转换的结果。在该服务中，物化视图仅用于聚合。这些结果通常比原始输入数据小得多，往往是部分聚合状态。再加上直接查询预聚合 target table 十分简便，与在查询时对原始数据执行相同计算相比，查询延迟可大幅降低。

ClickHouse 中的物化视图会随着数据流入源表而持续更新，其行为更像是始终保持最新的索引。这一点与许多其他数据库不同——在那些数据库中，物化视图是需要定期刷新的静态快照，类似于 ClickHouse 的[可刷新物化视图](/zh/concepts/features/materialized-views/refreshable-materialized-view)。

<div className="ch-image-md">
  <Frame>
    ![Materialized view 示意图](/images/materialized-view/materialized-view-diagram.webp)
  </Frame>
</div>

增量物化视图在新数据到达时仅计算视图的变化部分，从而将计算前移到写入时。由于 ClickHouse 针对数据摄取进行了高度优化，每插入一个数据块所需的视图维护开销，与查询执行时节省的开销相比微不足道。聚合的计算开销被分摊到各次插入中，而不必在每次读取时重复承担。因此，查询预聚合结果的开销远低于重新计算，不仅降低了运维成本，还能让下游可视化即使在 PB 级规模下也获得近乎实时的性能。

这种模型与每次更新都重新计算整个视图、或依赖定时刷新的系统有着本质区别。如需深入了解物化视图的工作原理及创建方法，请参阅上文链接的指南。

每个物化视图都会带来额外的写入开销，因此应有选择地使用。

<Tip>
  仅为最常用的仪表盘和可视化创建视图。
  该功能处于 beta 阶段期间，视图数量应控制在 20 个以内。
  该上限预计会在后续版本中提高。
</Tip>

<Note>
  单个物化视图可以为不同分组计算多个指标，例如按服务名称、以一分钟为时间桶计算耗时的最小值、最大值和 p95。这样，一个视图便可服务于多个可视化，而不仅限于一个。因此，将指标整合到共享视图中十分重要，既能最大化每个视图的价值，又能确保视图在各个仪表盘和工作流中得到复用。
</Note>

在继续之前，建议您先深入了解 ClickHouse 中的物化视图。
更多详细信息，请参阅我们的[增量物化视图](/zh/concepts/features/materialized-views/incremental-materialized-view)指南。

## 选择需要加速的可视化 {#selecting-visualizatons-for-acceleration}

在创建物化视图之前，务必先明确需要加速哪些可视化，以及哪些工作流对用户最为关键。

在该服务中，物化视图旨在**加速以聚合为主的可视化**，即按时间计算一个或多个指标的查询，例如**每分钟平均请求耗时**、**各服务的请求计数**或**随时间变化的错误率**。由于物化视图用于支撑时间序列可视化，因此必须始终包含聚合以及基于时间的分组。

一般建议如下：

### 识别高影响力的可视化 {#identify-high-impact-visualizations}

最适合加速的对象通常属于以下几类：

* 频繁刷新且持续展示的仪表盘可视化，例如投放在大屏上的总览监控仪表板。
* 运行手册中的诊断工作流：在事件响应期间，其中的特定图表会被反复查看，且需要快速返回结果。
* 核心 UI 功能，包括：
  * 搜索页面上的直方图视图。
  * 预设仪表盘中的可视化，例如 APM、Services 或 Kubernetes 视图。

这些可视化通常会被不同用户针对不同时间范围反复执行，因此非常适合将计算从查询时转移到写入时。

### 权衡收益与写入时开销 {#balance-benefit-against-insert-time-cost}

物化视图会在写入时带来额外工作，因此应有选择、审慎地创建。并非所有可视化都能从预聚合中受益，为很少使用的图表做加速通常得不偿失。物化视图的总数应控制在 20 个以内。

<Note>
  在投入生产环境之前，务必验证物化视图带来的资源开销，尤其是 CPU 使用率、磁盘 I/O 以及[合并活动](/zh/resources/support-center/tips-and-tricks/too-many-parts)。每个物化视图都会增加写入时的工作量并产生额外的 parts，因此必须确保合并能够跟上，且数据分片数量保持稳定。在开源 ClickHouse 中，可以通过[系统表](/zh/reference/system-tables/tables)和[内置可观测性仪表板](/zh/guides/oss/deployment-and-scaling/monitoring/monitoring#built-in-advanced-observability-dashboard)进行监控；在 ClickHouse Cloud 中，则可以使用内置指标和[监控仪表板](/zh/products/cloud/features/monitoring/advanced-dashboard)。有关如何诊断和缓解数据分片数量过多的问题，请参阅 [parts 过多](/zh/resources/support-center/knowledge-base/troubleshooting/exception-too-many-parts)。
</Note>

确定最重要的可视化之后，下一步就是进行整合。

### 将可视化整合到共享视图中 {#consolidate-visualizations-into-shared-views}

服务中的所有物化视图都应使用 [`toStartOfMinute`](/zh/reference/functions/regular-functions/date-time-functions#toStartOfMinute) 等函数按时间间隔对数据进行分组。不过，许多可视化还会共用其他分组键，例如服务名称、跨度名称或状态码。当多个可视化使用相同的分组维度时，通常可以由同一个 materialized view 为它们提供数据。

例如 (以链路追踪为例) ：

* 按服务名称统计的平均耗时随时间变化 - `SELECT avg(Duration), toStartOfMinute(Timestamp) as time, ServiceName FROM otel_traces GROUP BY ServiceName, time`
* 按服务名称统计的请求数随时间变化 - `SELECT count() count, toStartOfMinute(Timestamp) as time, ServiceName FROM otel_traces GROUP BY ServiceName, time`
* 按状态码统计的平均耗时随时间变化 - `SELECT avg(Duration), toStartOfMinute(Timestamp) as time, StatusCode FROM otel_traces GROUP BY StatusCode, time`
* 按状态码统计的请求数随时间变化 - `SELECT count() count, toStartOfMinute(Timestamp) as time, StatusCode FROM otel_traces GROUP BY StatusCode, time`

您无需为每个查询和图表分别创建物化视图，而是可以将它们合并为一个按服务名称和状态码聚合的视图。该视图可以同时计算多个指标，例如计数、平均耗时、最大耗时以及百分位数，并可在多个可视化中复用。以下是合并上述查询后的示例查询：

```sql
SELECT avg(Duration), max(Duration), count(), quantiles(0.95,0.99)(Duration), toStartOfMinute(Timestamp) as time, ServiceName, StatusCode
FROM otel_traces
GROUP BY time, ServiceName, StatusCode
```

以这种方式整合视图，可以减少写入时开销、控制物化视图的总数、缓解数据分片数量过多带来的问题，并简化后续维护工作。

在此阶段，请**重点关注您希望加速的可视化所发出的查询**。下一节将通过一个示例，演示如何将多个聚合查询合并到单个 materialized view 中。

### materialized view 示例 {#example-materialized-view}

请看以下原始查询，该查询按服务名称和状态码分组，按分钟计算平均耗时、最大耗时、事件数以及百分位数：

```sql
SELECT
    toStartOfMinute(Timestamp),
    ServiceName,
    StatusCode,
    count() AS count,
    avg(Duration),
    max(Duration),
    quantiles(0.95, 0.99)(Duration)
FROM otel_traces
GROUP BY
    time,
    ServiceName,
    StatusCode
```

为加速此查询，请创建 target table `otel_traces_1m`，用于存储相应的聚合状态：

```sql
CREATE TABLE otel_traces_1m
(
    `Timestamp` DateTime,
    `ServiceName` LowCardinality(String),
    `StatusCode` LowCardinality(String),
    `count` SimpleAggregateFunction(sum, UInt64),
    `avg__Duration` AggregateFunction(avg, UInt64),
    `max__Duration` SimpleAggregateFunction(max, Int64),
    `quantiles__Duration` AggregateFunction(quantiles(0.95, 0.99), Int64)
)
ENGINE = AggregatingMergeTree
ORDER BY (Timestamp, ServiceName, StatusCode);
```

随后，materialized view `otel_traces_1m_mv` 的定义会在插入新数据时计算并写入这些状态：

```sql
CREATE MATERIALIZED VIEW otel_traces_1m_mv TO otel_traces_1m
AS
SELECT
    toStartOfMinute(Timestamp) AS Timestamp,
    ServiceName,
    StatusCode,
    count() AS count,
    avgState(Duration) AS avg__Duration,
    maxSimpleState(Duration) AS max__Duration,
    quantilesState(0.95, 0.99)(Duration) AS quantiles__Duration
FROM otel_v2.otel_traces
GROUP BY
    Timestamp,
    ServiceName,
    StatusCode;
```

该 materialized view 由两部分组成：

1. target table：定义用于存储中间结果的 schema 和聚合状态类型。必须使用 [AggregatingMergeTree](/zh/reference/engines/table-engines/mergetree-family/aggregatingmergetree) 引擎，才能确保这些状态在后台被正确合并。
2. materialized view 查询：在 insert 时自动执行。与原始查询相比，它使用的是 `avgState` 和 `quantilesState` 等状态函数，而非最终聚合函数。

最终得到的是一张紧凑的表，按服务名称和状态码存储每分钟的聚合状态。其大小随时间和基数的增长而可预测地增长；后台合并完成后，它所表示的结果与直接对原始数据运行原始聚合的结果相同。查询该表的开销远低于直接从源链路追踪表进行聚合，因此即使在大规模场景下，也能获得快速、稳定的可视化性能。

### 在仪表盘和可视化中验证加速效果 {#verifying-acceleration-in-dashboards-and-visualizations}

需要注意的是，增量物化视图仅包含**视图创建之后**插入的数据。这类视图不会自动回填历史数据，因此能够保持轻量级，维护成本也很低。正因如此，用户在注册视图时必须显式指定该视图的有效时间范围。

<Note>
  只有当 materialized view 的最小时间戳小于或等于查询时间范围的起始时间时，服务才会使用该视图，以确保视图包含所需的全部数据。尽管查询在内部会被拆分为若干按时间划分的子查询，但 materialized view 要么应用于整个查询，要么完全不使用。未来的改进可能会支持仅对符合条件的子查询选择性地使用视图。
</Note>

服务提供了清晰的可视化标识，便于确认是否正在使用 materialized view。

1. **检查优化状态** 查看仪表盘或可视化时，留意闪电图标或 `Accelerated` 图标：

* **绿色闪电**表示查询已通过 materialized view 加速。
* **橙色闪电**表示查询直接在源表上执行。

<div className="ch-image-lg">
  <Frame>
    ![已加速的可视化](/images/clickstack/materialized_views/accelerated_visual.webp)
  </Frame>
</div>

2. **查看优化详情** 点击闪电图标即可打开详情面板，其中显示：

* **活跃的 materialized view**：为该查询选用的视图，包括其估算行数。
* **已跳过的物化视图**：兼容但未被选用的视图，以及各自的估算扫描量。
* **不兼容的物化视图**：无法使用的视图及具体原因。

3. **了解常见的不兼容原因** 出现以下情况时，可能不会使用 materialized view：

* **查询时间范围**的起始时间早于视图的最小时间戳。
* **可视化粒度**不是视图粒度的整数倍。
* 视图中不包含查询所需的**聚合函数**。
* 查询使用了无法从视图聚合状态推导出的**自定义计数表达式**，例如 `count(if(...))`。

借助这些标识，您可以轻松确认可视化是否已加速、了解某个视图被选用的原因，并排查视图不符合条件的原因。

### 如何为可视化选择物化视图 {#how-views-are-selected}

执行可视化时，服务可能有多个候选结果可用，包括基表和多个物化视图。为确保最佳性能，服务会借助 ClickHouse 的 [`EXPLAIN ESTIMATE`](/zh/reference/statements/explain#explain-estimate) 机制，自动评估并选出最高效的方案。

选择过程按以下明确的顺序进行：

1. **验证兼容性**
   服务首先检查以下各项，以确定物化视图是否适用于该查询：
   * **时间覆盖范围**：查询的时间范围必须完全落在物化视图的可用数据范围之内。
   * **粒度**：可视化的时间桶必须等于或粗于视图的粒度。
   * **聚合**：所请求的指标必须存在于视图中，并且能够由其聚合状态计算得出。

2. **变换查询**
   对于兼容的视图，服务会重写查询，使其改为查询物化视图的表：
   * 将聚合函数映射到相应的物化列。
   * 对聚合状态应用 `-Merge` 组合器。
   * 调整时间分桶，使其与视图的粒度对齐。

3. **选择最佳候选结果**
   如果有多个兼容的物化视图可用，服务会为每个候选结果运行一次 [`EXPLAIN ESTIMATE`](/zh/reference/statements/explain#explain-estimate) 查询，并比较预估扫描的行数和粒度数，最终选择预估扫描成本最低的视图。

4. **平滑回退**
   如果没有兼容的物化视图，服务会自动回退为查询源表。

这种方式始终能将扫描的数据量降至最低，提供可预测的低延迟性能，且无需修改可视化定义。

即使可视化包含筛选条件、搜索约束或时间分桶，只要视图中包含所有必需的维度，物化视图仍然适用。因此，视图可以加速仪表盘、直方图和带筛选条件的图表，且无需修改可视化定义。

#### 物化视图选择示例 {#example-of-choosing-materialized-view}

假设在同一个链路追踪数据源上创建了两个物化视图：

* `otel_traces_1m`，按分钟、`ServiceName` 和 `StatusCode` 分组
* `otel_traces_1m_v2`，按分钟、`ServiceName`、`StatusCode` 和 `SpanName` 分组

第二个视图包含更多分组键，因此会产生更多行，扫描的数据量也更大。

如果某个可视化请求的是**各服务随时间变化的平均耗时**，那么从技术上讲，两个视图都可以使用。服务会针对每个候选视图执行 [`EXPLAIN ESTIMATE`](/zh/reference/statements/explain#explain-estimate) 查询，并比较估算的粒度计数，即：

```sql
EXPLAIN ESTIMATE
SELECT
    toStartOfHour(Timestamp) AS hour,
    ServiceName,
    avgMerge(avg__Duration) AS avg__Duration
FROM otel_v2.otel_traces_1m
GROUP BY
    hour,
    ServiceName
ORDER BY hour DESC
```

```response
┌─database─┬─table──────────┬─parts─┬──rows─┬─marks─┐
│ otel_v2  │ otel_traces_1m │     1 │ 49385 │     6 │
└──────────┴────────────────┴───────┴───────┴───────┘

1 row in set. Elapsed: 0.009 sec.
```

```sql
EXPLAIN ESTIMATE
SELECT
    toStartOfHour(Timestamp) AS hour,
    ServiceName,
    avgMerge(avg__Duration) AS avg__Duration
FROM otel_v2.otel_traces_1m_v2
GROUP BY
    hour,
    ServiceName
ORDER BY hour DESC
```

```response
┌─database─┬─table─────────────┬─parts─┬───rows─┬─marks─┐
│ otel_v2  │ otel_traces_1m_v2 │     1 │ 212519 │    26 │
└──────────┴───────────────────┴───────┴────────┴───────┘

1 row in set. Elapsed: 0.004 sec.
```

由于 `otel_traces_1m` 体积更小，需要扫描的粒度也更少，因此会被自动选中。

两个物化视图的性能都优于直接查询基表，但选择能满足需求的最小视图可获得最佳性能。

### 告警 {#alerts}

在兼容的情况下，告警查询会自动使用物化视图。告警同样适用这套优化逻辑，因而评估速度更快。

## 对 materialized view 进行历史数据回填 {#backfilling-a-materialized-view}

如前所述，增量物化视图只包含**视图创建之后**插入的数据，不会自动进行历史数据回填。这种设计使视图保持轻量级且维护成本低廉，但也意味着，对于需要早于视图最小时间戳数据的查询，视图无法发挥作用。

在大多数情况下，这是可以接受的。常见的可观测性工作负载侧重于近期数据 (例如最近 24 小时) ，因此新创建的视图通常在一天内即可完全投入使用。然而，对于跨越更长时间范围的查询，视图可能需要等待足够长的时间后才能使用。

在这些情况下，用户可以考虑使用历史数据对 materialized view 进行**历史数据回填**。

历史数据回填可能**消耗大量计算资源**。正常运行时，物化视图会随着数据到达而增量填充，计算成本因此均匀分摊到一段时间内。

而历史数据回填会将这些工作压缩到短得多的时间内完成，**显著增加单位时间内的 CPU 和内存使用量。**

根据数据集大小和保留窗口的不同，可能需要临时对集群进行扩缩容 (纵向扩容，或在 ClickHouse Cloud 中进行横向扩缩容) ，以便在合理的时间内完成历史数据回填。

如果未预配额外资源，历史数据回填可能会对生产工作负载造成负面影响，包括查询延迟和摄取吞吐量。对于**超大数据集或较长的历史范围，历史数据回填可能不切实际**，甚至根本不可行。

总之，历史数据回填往往得不偿失，且存在运维风险，仅应在加速历史数据查询至关重要的特殊情况下才考虑。如果您决定继续，建议遵循下文所述的受控方法，以便在性能、成本和对生产环境的影响之间取得平衡。

### 历史数据回填方法 {#backfilling-approaches}

<Info>
  **避免使用 POPULATE**

  除非是在已暂停摄取的情况下处理小型数据集，否则不建议使用 [POPULATE](/zh/reference/statements/create/view#materialized-view) 命令对物化视图进行历史数据回填。该操作可能会遗漏在 populate 完成之后、materialized view 创建之前插入到其源表中的行。此外，populate 会针对全部数据运行，在大型数据集上容易因中断或触及内存限制而失败。
</Info>

假设你希望为以下聚合对应的 materialized view 进行历史数据回填。该聚合按服务名称和状态码分组，计算每分钟的指标：

```sql
SELECT
    toStartOfMinute(Timestamp),
    ServiceName,
    StatusCode,
    count() AS count,
    avg(Duration),
    max(Duration),
    quantiles(0.95, 0.99)(Duration)
FROM otel_traces
GROUP BY
    time,
    ServiceName,
    StatusCode
```

如前所述，增量物化视图不会自动回填。建议采用以下流程，在安全地进行历史数据回填的同时，保留对新数据的增量处理方式。

#### 使用 `INSERT INTO SELECT` 直接回填 {#direct-backfill}

此方法最适用于**较小的数据集**或**相对轻量级的聚合查询**，即能够在合理时间内完成全部历史数据回填、且不会耗尽集群资源的场景。通常，当回填查询可在数分钟 (最多几小时) 内完成，并且可以接受 CPU 和 I/O 使用量暂时升高时，适合采用此方法。对于更大的数据集或开销更高的聚合，请考虑改用下文介绍的增量或基于数据块的历史数据回填方法。

<Steps>
  <Step title="确定视图当前覆盖的数据范围" id="determine-current-coverage-of-view">
    在进行任何回填之前，首先要确认 materialized view 中已包含哪些数据。具体做法是查询 target table 中的最小时间戳：

    ```sql
    SELECT min(Timestamp)
    FROM otel_traces_1m;
    ```

    该时间戳表示视图能够响应查询的最早时间点。服务发出的查询如果请求早于该时间戳的数据，都将回退到基表。
  </Step>

  <Step title="判断是否需要历史数据回填" id="decide-whether-backfilling-is-neccessary">
    在大多数部署中，查询主要集中在近期数据上，例如最近 24 小时。在这种情况下，新建的视图在创建后不久即可完全投入使用，无需进行历史数据回填。

    如果上一步返回的时间戳对于您的使用场景而言已足够早，则无需回填。仅在以下情况下才需考虑历史数据回填：

    * 查询经常跨越较长的历史时间范围。
    * 视图对这些范围内的查询性能至关重要。
    * 数据集规模和聚合开销使历史数据回填切实可行。
  </Step>

  <Step title="回填缺失的历史数据" id="backfill-missing-historical-data">
    如果需要回填，请对视图的查询稍作修改，使其仅读取早于上文所记录时间戳的数据，然后用它为 materialized view 的 target table 填充早于当前最小时间戳的数据。由于 target table 使用 AggregatingMergeTree，回填查询**必须插入聚合状态，而不是最终值**。

    <Warning>
      此查询可能会处理大量数据，资源消耗较高。在运行回填之前，务必确认可用的 CPU、内存和 I/O 容量是否充足。一个实用的技巧是先使用 `FORMAT Null` 执行该查询，以估算运行时间和资源用量。

      如果预计查询本身需要运行数小时以上，则**不建议**使用此方法。
    </Warning>

    请注意，以下查询添加了 `WHERE` 子句，将聚合范围限制为早于视图中最早时间戳的数据：

    ```sql
    INSERT INTO otel_traces_1m
    SELECT
        toStartOfMinute(Timestamp) AS Timestamp,
        ServiceName,
        StatusCode,
        count() AS count,
        avgState(Duration) AS avg__Duration,
        maxSimpleState(Duration) AS max__Duration,
        quantilesState(0.95, 0.99)(Duration) AS quantiles__Duration
    FROM otel_traces
    WHERE Timestamp < (
        SELECT min(Timestamp) FROM otel_traces_1m
    )
    GROUP BY
        Timestamp,
        ServiceName,
        StatusCode;
    ```
  </Step>
</Steps>

#### 使用 Null 表进行增量历史数据回填 {#incremental-backfill-null-table}

对于较大的数据集或资源消耗较高的聚合查询，使用单条 `INSERT INTO SELECT` 直接进行历史数据回填可能并不现实，甚至存在风险。此时，建议采用**增量历史数据回填**方法。该方法更贴近增量物化视图的常规运行方式：以大小可控的块处理数据，而不是一次性聚合全部历史数据。

此方法适用于以下情况：

* 回填查询如果一次性执行，需要运行数小时。
* 完整聚合的峰值内存使用量过高。
* 您希望在回填期间严格控制 CPU 和内存消耗。
* 您需要更稳健的流程，在中断后能够安全地重新启动。

其核心思路是将 [**Null 表**](/zh/reference/engines/table-engines/special/null) 用作摄取缓冲区。Null 表虽然不存储数据，但附加在其上的物化视图仍会执行，因此能在数据流经时以增量方式计算聚合状态。

<Steps>
  <Step title="创建用于历史数据回填的 Null 表" id="create-null-table">
    创建一个轻量级 Null 表，仅包含 materialized view 聚合所需的列，以尽量减少 I/O 和内存使用量。

    ```sql
    CREATE TABLE otel_traces_backfill
    (
        Timestamp DateTime64(9),
        ServiceName LowCardinality(String),
        StatusCode LowCardinality(String),
        Duration UInt64
    )
    ENGINE = Null;
    ```
  </Step>

  <Step title="将 materialized view 附加到 Null 表" id="attach-mv-to-null-table">
    接下来，在 Null 表上创建一个 materialized view，使其写入与主 materialized view 相同的聚合表。

    ```sql
    CREATE MATERIALIZED VIEW otel_traces_1m_mv_backfill
    TO otel_traces_1m
    AS
    SELECT
        toStartOfMinute(Timestamp) AS Timestamp,
        ServiceName,
        StatusCode,
        count() AS count,
        avgState(Duration) AS avg__Duration,
        maxSimpleState(Duration) AS max__Duration,
        quantilesState(0.95, 0.99)(Duration) AS quantiles__Duration
    FROM otel_traces_backfill
    GROUP BY
        Timestamp,
        ServiceName,
        StatusCode;
    ```

    每当有行插入 Null 表时，该 materialized view 都会以增量方式执行，按小块生成聚合状态。
  </Step>

  <Step title="以增量方式回填历史数据" id="incremental-backfill">
    最后，将历史数据插入 Null 表。materialized view 会逐块处理数据，将聚合状态写入 target table，而不会持久化原始行。

    ```sql
    INSERT INTO otel_traces_backfill
    SELECT
        Timestamp,
        ServiceName,
        StatusCode,
        Duration
    FROM otel_traces
    WHERE Timestamp < (
        SELECT min(Timestamp) FROM otel_traces_1m
    );
    ```

    由于数据以增量方式处理，内存使用量始终有上限且可预测，与常规摄取的行为非常接近。

    <Note>
      为进一步确保安全，可以考虑将用于回填的 materialized view 指向一个临时 target table (例如 `otel_traces_1m_v2`) 。回填成功完成后，再将[分区移动](/zh/reference/statements/alter/partition#move-partition-to-table)到主 target table，例如 `ALTER TABLE otel_traces_1m_v2 MOVE PARTITION '2026-01-02' TO otel_traces_1m`。这样，即使回填因资源限制而中断或失败，也能轻松恢复。
    </Note>

    有关调优此流程的更多信息 (包括提升插入性能以及降低和控制资源占用) ，请参阅[“历史数据回填”](/zh/guides/clickhouse/data-modelling/backfilling#tuning-performance--resources)。
  </Step>
</Steps>

## 建议 {#recommendations}

以下建议汇总了在服务中设计和运维物化视图的最佳实践。遵循这些准则有助于确保物化视图高效、行为可预期且具备成本效益。

### 粒度选择与对齐 {#granularity-selection-and-alignment}

只有当可视化或告警的粒度是视图粒度的**整数倍**时，才会使用物化视图。该粒度的确定方式取决于图表类型：

* **时间图表** (x 轴为时间的折线图或条形图) ：
  图表的显式粒度必须是物化视图粒度的整数倍。
  例如，10 分钟粒度的图表可以使用粒度为 10、5、2 或 1 分钟的物化视图，但不能使用 20 分钟或 3 分钟粒度的视图。

* **非时间图表** (数值图表、表格图表或摘要图表) ：
  实际粒度按 `(time range / 80)` 计算得出，并向上取整到 UI 支持的最接近粒度。由此得出的粒度同样必须是物化视图粒度的整数倍。

基于上述规则：

* **不要创建 10 分钟粒度的物化视图**。
  该服务的图表和告警支持 15 分钟粒度，但不支持 10 分钟粒度。因此，10 分钟粒度的物化视图无法兼容常见的 15 分钟粒度可视化和告警。
* 优先选择 **1 分钟**或 **1 小时**粒度，这两种粒度能与大多数图表和告警配置良好匹配。

较粗的粒度 (例如 1 小时) 生成的视图更小，存储开销也更低；较细的粒度 (例如 1 分钟) 则为细粒度分析提供更大的灵活性。请选择能够满足关键工作流需求的最小粒度。

### 限制并整合物化视图 {#limit-and-consolidate-materialized-views}

每个物化视图都会增加额外的写入时开销，并加重 part 数量和合并压力。
建议遵循以下准则：

* 每个 source **最多 20 个物化视图**。
* 通常 **10 个左右的物化视图**最为理想。
* 如果多个可视化共享相同的维度，应将它们整合到同一个视图中。

尽可能利用同一个物化视图计算多个指标，并为多个图表提供数据。

### 谨慎选择维度 {#choose-dimensions-carefully}

仅包含常用于分组或过滤的维度：

* 每增加一个分组列，视图的大小都会随之增加。
* 需要在查询灵活性与存储及写入时开销之间取得平衡。
* 如果筛选条件涉及视图中不存在的列，服务将回退到源表。

<Info>
  **提示**

  一个常见且几乎总能派上用场的基线方案是：按**服务名称分组并带有计数指标**的 materialized view。它可以在搜索和仪表盘中实现快速的直方图和服务级概览。
</Info>

### 聚合列的命名约定 {#naming-conventions-for-aggregation-columns}

materialized view 中的聚合列必须遵循严格的命名约定，才能实现自动推断：

* 模式：`<aggFn>__<sourceColumn>`
* 示例：
  * `avg__Duration`
  * `max__Duration`
  * `count__`：用于行数统计

服务依靠这一约定，将查询正确映射到 materialized view 的列。

### 分位数与 sketch 选择 {#quantiles-and-sketch-selection}

不同的分位数函数在性能和存储方面各有特点：

* `quantiles` 在磁盘上生成的 sketch 较大，但写入时的计算开销较低。
* `quantileTDigest` 在写入时的计算开销较高，但生成的 sketch 较小，通常能加快视图查询。

对于这两个函数，你都可以在写入时指定 sketch 大小 (例如 `quantile(0.5)`。之后仍可基于生成的 sketch 查询其他分位数值，例如 `quantile(0.95)`。建议多做实验，为你的工作负载找到最佳平衡点。

### 持续验证有效性 {#validate-effectiveness-continously}

应始终确认物化视图是否带来了实际收益：

* 通过 UI 中的加速指示器确认物化视图确实被使用。
* 对比启用该视图前后的查询性能。
* 监控资源使用情况和合并行为。

物化视图应被视为一种性能优化手段，需要随着查询模式的变化定期审视和调整。

### 高级配置 {#advanced-configurations}

对于更复杂的工作负载，可以使用多个物化视图来支持不同的访问模式。例如：

* **近期数据采用高分辨率，历史数据采用粗粒度视图**
* **服务级视图用于概览，端点级视图用于深度诊断**

有选择地应用这些模式可以显著提升性能，但应先验证较简单的配置，再考虑引入。

遵循这些建议，有助于确保物化视图始终高效、易于维护，并与查询执行模型保持一致。

## 限制 {#limitations}

### 常见不兼容原因 {#common-incompatibility-reasons}

如果满足以下任一条件，则**不会**使用 materialized view：

* **查询时间范围**
  查询时间范围的起点早于 materialized view 中的最小时间戳。由于视图不会自动回填历史数据，因此只能服务于其完全覆盖的时间范围内的查询。

* **粒度不匹配**
  可视化的实际粒度必须是 materialized view 粒度的整数倍。具体而言：

  * 对于**时间图表** (x 轴为时间的折线图或条形图) ，图表所选粒度必须是视图粒度的整数倍。例如，10 分钟粒度的图表可以使用 10、5、2 或 1 分钟粒度的物化视图，但不能使用 20 分钟或 3 分钟粒度的视图。
  * 对于**非时间图表** (数值图表或表格图表) ，实际粒度按 `(time range / 80)` 计算，并向上取整到 UI 支持的最接近粒度，同样必须是视图粒度的整数倍。

* **不支持的聚合函数**
  查询所需的聚合在 materialized view 中不存在。只有在视图中显式计算并存储的聚合才能使用。

* **自定义计数表达式**
  使用 `count(if(...))` 等表达式或其他条件计数的查询无法从标准聚合状态推导得出，因此无法使用物化视图。

### 设计与运维约束 {#design-and-operational-constraints}

* **不支持自动历史数据回填**
  增量物化视图仅包含创建之后插入的数据。若要加速历史数据查询，需要显式执行历史数据回填；对于大型数据集，这可能代价高昂，甚至不可行。

* **粒度权衡**
  粒度过细的视图会增加存储大小和写入时开销，而粒度过粗的视图则会降低灵活性。必须根据预期的查询模式谨慎选择粒度。

* **维度爆炸**
  添加大量分组维度会显著增大视图体积，并可能削弱其效果。视图应仅包含常用的分组列和过滤列。

* **视图数量的可扩展性有限**
  每个物化视图都会增加写入时开销，并加剧合并压力。创建过多视图可能会对摄取和后台合并产生负面影响。

了解这些限制，有助于确保将物化视图用在真正能带来收益的场景中，并避免采用会在不知不觉中回退到较慢源表查询的配置。

## 故障排查 {#troubleshooting}

### materialized view 未被使用 {#materialied-view-not-being-used}

**检查 1：日期范围**

* 打开优化弹窗，查看是否显示“Date range not supported.”。
* 确保查询的日期范围晚于 materialized view 的最小日期。
* 如果 materialized view 包含全部历史数据，请移除最小日期。

**检查 2：粒度**

* 确认图表粒度是 MV 粒度的整数倍。
* 尝试将图表粒度设置为“Auto”，或手动选择兼容的粒度。

**检查 3：聚合**

* 检查图表使用的聚合是否包含在 MV 中。
* 在优化弹窗中查看“Available aggregated columns”。

**检查 4：维度**

* 确保分组依据列包含在 MV 的维度列中。
* 在优化弹窗中查看“Available group/filter columns”。

### materialized view 查询缓慢 {#slow-mv-queries}

**问题 1：materialized view 粒度过细**

* 粒度过细 (例如 1 秒) 导致 MV 中的行数过多。
* 解决方案：创建粒度更粗的 MV (例如 1 分钟或 1 小时) 。

**问题 2：维度过多**

* 维度列过多导致 MV 的基数过高。
* 解决方案：只保留最常用的维度列。

**问题 3：多个 MV 的行数都很多**

* 系统会对每个 MV 执行 `EXPLAIN`。
* 解决方案：删除很少使用或总是被跳过的 MV。

### 配置错误 {#config-errors}

**错误：&quot;At least one aggregated column is required&quot;**

* 在 MV 配置中至少添加一个已聚合列。

**错误：&quot;Source column is required for non-count aggregations&quot;**

* 指定要聚合的列 (只有 count 聚合可以省略源列) 。

**错误：&quot;Invalid granularity format&quot;**

* 从下拉列表中选择一个预设粒度。
* 格式必须是有效的 SQL 时间间隔 (例如应使用 `1 hour`，而不是 `1 h`) 。
