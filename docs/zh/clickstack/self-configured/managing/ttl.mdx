## 使用 TTL 进行数据保留 {#ttl-clickstack}

Self-managed ClickHouse Observability 中实现高效数据保留与管理的关键功能是生存时间 (TTL),在持续产生海量数据的场景下尤为重要。TTL 可自动使较旧的数据过期并将其删除,从而在无需人工干预的情况下充分利用存储并保持性能。借助这一能力,可以保持数据库精简、降低存储成本,并让查询聚焦于最相关、最新的数据,始终保持快速高效。此外,TTL 以系统化的方式管理数据生命周期,有助于满足数据保留策略的合规要求,进而提升可观测性解决方案的整体可持续性和可扩展性。

**默认情况下,数据保留 30 天。如需修改,请参阅[“修改生存时间 (TTL)”](#modifying-ttl)。**

ClickHouse 中的分区可以根据某一列或 SQL 表达式在磁盘上对数据进行逻辑划分。数据经过逻辑划分后,每个分区都可以独立操作,例如在按照 TTL 策略过期时将其删除。

如上例所示,分区是在最初定义表时通过 `PARTITION BY` 子句指定的。该子句可以包含基于一个或多个任意列的 SQL 表达式,其结果决定每一行数据被写入哪个分区。这样,数据会(通过共同的文件夹名称前缀)与磁盘上的各个分区建立逻辑关联,并可单独查询。在上例中,默认的 `otel_logs` schema 使用表达式 `toDate(Timestamp)` 按天分区。行插入 ClickHouse 时,系统会针对每一行计算该表达式,并将其路由到对应的分区(如果该行是当天的第一行,则会创建该分区)。有关分区及其其他用途的更多信息,请参阅[“表分区”](/zh/concepts/core-concepts/partitions)。

该表 schema 还包含 `TTL toDateTime(Timestamp) + ${TABLES_TTL}` 以及设置 `ttl_only_drop_parts = 1`。前一个子句确保数据一旦超过已配置的 TTL(默认 30 天)就会被删除。设置 `ttl_only_drop_parts = 1` 规定仅当数据分区片段中的所有数据均已过期时才使其过期(而不是尝试删除部分行)。由于分区确保了不同日期的数据永远不会被“合并”,因此可以高效地删除数据。

<Warning>
  **`ttl_only_drop_parts`**

  我们建议始终使用设置 [`ttl_only_drop_parts=1`](/zh/reference/settings/merge-tree-settings/other#ttl_only_drop_parts)。启用该设置后,当一个数据分片中的所有行均已过期时,ClickHouse 会删除整个 part。删除整个 parts,而不是部分清理 TTL 过期的行(当 `ttl_only_drop_parts=0` 时需通过资源密集型的 mutation 实现),可以缩短 `merge_with_ttl_timeout` 时间,并降低对系统性能的影响。如果数据的分区单位与 TTL 过期的单位相同(例如天),parts 自然只会包含所定义时间区间内的数据,从而确保 `ttl_only_drop_parts=1` 能够高效生效。
</Warning>

默认情况下,ClickHouse 会在[合并数据分区片段](/zh/reference/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage)时删除 TTL 已过期的数据。当 ClickHouse 检测到数据已过期时,会执行一次计划外合并。

<Info>
  **TTL 调度计划**

  如上所述,TTL 不会立即生效,而是按调度计划执行。MergeTree 表设置 `merge_with_ttl_timeout` 用于指定再次执行带删除 TTL 的合并前的最小延迟(以秒为单位),默认值为 14400 秒(4 小时)。但这只是最小延迟,实际触发 TTL 合并可能需要更长时间。如果该值设置过低,将会执行大量计划外合并,可能消耗大量资源。可以使用命令 `ALTER TABLE my_table MATERIALIZE TTL` 强制执行 TTL 过期。
</Info>

## 修改生存时间 (TTL) {#modifying-ttl}

修改 TTL 有以下两种方式：

1. **修改表结构 (推荐)&#x20;**。这需要连接到 ClickHouse 实例，例如通过 [ClickHouse 客户端](/zh/concepts/features/interfaces/client) 或 [Cloud SQL 控制台](/zh/products/cloud/features/sql-console-features/sql-console)。例如，可以使用以下 DDL 修改 `otel_logs` 表的 TTL：

```sql
ALTER TABLE default.otel_logs
MODIFY TTL TimestampTime + toIntervalDay(7);
```

2. **修改 OTel collector**。如果 ClickHouse 中尚不存在相应的表，ClickStack OpenTelemetry 采集器会自动创建这些表。该功能由 ClickHouse 导出器实现，该导出器提供了一个 `ttl` 参数，用于控制默认的 TTL 表达式，例如：

```yaml
exporters:
 clickhouse:
   endpoint: tcp://localhost:9000?dial_timeout=10s&compress=lz4&async_insert=1
   ttl: 72h
```

### 列级别生存时间 (TTL) {#column-level-ttl}

上述示例均在表级别使数据过期。您也可以在列级别设置数据过期。随着数据老化，可以借此删除那些在调查中的价值已不足以抵消其保留所需资源开销的列。例如，我们建议保留 `Body` 列，以防出现未在写入时提取的新动态元数据，例如新增的 Kubernetes 标签。经过一段时间 (例如 1 个月) 后，可能会发现这些额外的元数据并无用处，此时继续保留 `Body` 列的价值就很有限了。

下面展示如何在 30 天后删除 `Body` 列。

```sql
CREATE TABLE otel_logs_v2
(
        `Body` String TTL Timestamp + INTERVAL 30 DAY,
        `Timestamp` DateTime,
 ...
)
ENGINE = MergeTree
ORDER BY (ServiceName, Timestamp)
```

<Note>
  如需指定列级生存时间 (TTL)，用户必须自行定义 schema，该设置无法在 OTel collector 中指定。
</Note>
