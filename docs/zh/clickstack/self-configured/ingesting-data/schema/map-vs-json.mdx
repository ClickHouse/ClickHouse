[默认 schema](/zh/clickstack/self-configured/ingesting-data/schemas) 将资源、作用域、日志和跨度属性存储为 `Map(LowCardinality(String), String)` 类型的列。ClickHouse 还支持强类型的 [`JSON` 类型](/zh/reference/formats/JSON/JSON)，Self-managed ClickHouse Observability 也已提供 Beta 支持，可使用该类型替代 `Map`。

**对于常规的可观测性工作负载，我们建议沿用[默认的基于 `Map` 的 schema](/zh/clickstack/self-configured/ingesting-data/schemas)。** 如果您的工作负载中属性键数量少且相对固定，可以试用 JSON 类型进行评估，但它并不是推荐用于一般场景的 schema。

## 为什么推荐默认使用 Map {#why-map}

可观测性数据主要由各类属性构成，例如资源属性、作用域属性，以及跨度和日志属性。这些属性集合通常规模庞大、属于 high-cardinality，并且以高吞吐量摄取。为这些属性选择何种 schema，是决定摄取成本和存储布局的首要因素。

`Map(LowCardinality(String), String)` 将键和值存储在同一个结构中。`Map` 过去的缺点是，读取单个键就必须读取整个 Map 列。如今这一问题已经解决：ClickHouse 现已支持[分桶映射序列化](/zh/reference/data-types/map#bucketed-map-serialization)，它会将 Map 拆分为多个桶，查询只需读取所需的桶即可。再结合在 Map 键和值上构建的[文本索引](/zh/reference/engines/table-engines/mergetree-family/textindexes) ([默认 schema](/zh/clickstack/self-configured/ingesting-data/schemas) 正是这样配置的) ，`Map` 在读取时既有良好的选择性，速度也很快，同时新增键不会带来任何摄取开销。

实际上，这意味着：

* **键数量增长时，摄取成本保持稳定。** 新增属性键不会改变磁盘上的列布局，也不会创建新的列文件。摄取成本取决于数据量，而非键的基数。
* **不会出现元数据膨胀。** 磁盘上列文件的数量不会随唯一属性键数量的增加而增长。
* **借助索引实现选择性查找。** Map 键和值上的文本索引支持点查找，无需扫描所有行。
* **高吞吐量下行为可预测。** 追踪和日志中常见突发性、无 schema 的属性集合，Map 能够从容应对，且不会产生按键计算的开销。

## 为何默认不使用 JSON {#why-not-json}

`JSON` 类型采用了不同的思路：在写入时，ClickHouse 会为遇到的每个路径动态创建一个专用的强类型子列。这在读取时颇具优势：只需读取所请求的子列，类型得以保留，且无需在查询时进行类型转换。

代价则落在摄取阶段。创建和管理大量动态子列会带来写入开销，并增加元数据的复杂度。可观测性工作负载的属性集合通常非常庞大或高度动态，摄取吞吐量也很高，在这类场景下，这种开销相当可观。[`max_dynamic_paths`](/zh/reference/data-types/newjson#reading-json-paths-as-sub-columns) 限制可以将多余的路径溢写到一个共享列中，从而控制影响范围，但访问共享列比访问专用子列更慢，这又会削弱当初选择 JSON 所看重的读取优势。

由于分桶映射序列化消除了 `Map` 以往的大部分读取开销，对于典型的可观测性工作负载而言，`JSON` 在读取时的优势已不足以抵消其摄取成本。

## 何时仍可考虑使用 JSON {#when-to-consider-json}

当以下条件*全部*满足时，JSON 类型可能是合理的选择：

* 你的属性键集合**规模小且稳定**，即不会出现成千上万个唯一键，新键也很少出现。
* 相对于属性基数而言，摄取吞吐量**适中**。
* 你希望以**强类型方式访问**属性，而无需在查询时进行类型转换 (数值仍为数值，布尔值仍为布尔值) 。
* 你愿意在 Self-managed ClickHouse Observability 中使用**测试版功能**，并接受该集成日后可能发生变化。

如果上述条件不能全部满足，请继续使用[默认的基于 `Map` 的 schema](/zh/clickstack/self-configured/ingesting-data/schemas)。

## Beta 状态 {#beta-status}

<BetaBadge />

<Warning>
  **测试版功能，尚不适用于生产环境**

  **Self-managed ClickHouse Observability** 中的 JSON 类型支持是一项**测试版功能**。虽然 JSON 类型本身在 ClickHouse 25.3+ 中已可用于生产环境，但它与该服务的集成仍在积极开发中，可能存在限制、后续可能发生变化，也可能包含缺陷。
</Warning>

ClickStack 自 `2.0.4` 版本起提供对 JSON 类型的 Beta 支持。

## 启用 JSON 支持 {#enabling-json-support}

如需使用 JSON 类型模式，而非[默认的基于 `Map` 的 schema](/zh/clickstack/self-configured/ingesting-data/schemas)，请设置以下环境变量。

| 变量                                                              | 设置位置                         | 用途                                 |
| --------------------------------------------------------------- | ---------------------------- | ---------------------------------- |
| `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'` | ClickHouse Observability 采集器 | 使用 JSON 类型在 ClickHouse 中创建 schema。 |

<a id="managed-clickstack" />

如需在 Self-managed ClickHouse Observability 中启用 JSON 支持，请在配置采集器之前联系 support@clickhouse.com。此外，还需在 ClickHouse Cloud 的可观测性 UI 中启用该功能。

在采集器上设置 `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'`。例如：

```shell
docker run -e OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json' -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
```

## 从基于 Map 的模式迁移到 JSON {#migrating-from-map-to-json}

<Warning>
  **向后兼容性**

  [JSON 类型](/zh/reference/formats/JSON/JSON)与现有基于 Map 的模式**不向后兼容**。启用此功能后，系统会使用 `JSON` 类型创建新表，且需要手动迁移数据。
</Warning>

如需从[默认的基于 Map 的模式](/zh/clickstack/self-configured/ingesting-data/schemas)迁移，请按以下步骤操作：

<Steps>
  <Step title="停止 OTel collector" id="stop-the-collector" />

  <Step title="重命名现有表并更新数据源" id="rename-existing-tables-sources">
    重命名现有表，并在可观测性 UI 中更新数据源。

    例如：

    ```sql
    RENAME TABLE otel_logs TO otel_logs_map;
    RENAME TABLE otel_metrics TO otel_metrics_map;
    ```
  </Step>

  <Step title="部署采集器" id="deploy-the-collector">
    部署采集器，并设置 `OTEL_AGENT_FEATURE_GATE_ARG`。
  </Step>

  <Step title="确认已启用 JSON 模式支持" id="restart-the-hyperdx-container">
    在创建新的数据源之前，请先联系 support@clickhouse.com，确认可观测性 UI 中已启用 JSON 模式支持。
  </Step>

  <Step title="创建新的数据源" id="create-new-data-sources">
    在可观测性 UI 中创建指向 JSON 表的新数据源。
  </Step>
</Steps>

### 迁移现有数据 (可选) {#migrating-existing-data}

如需将旧数据迁移到新的 JSON 表中：

```sql
INSERT INTO otel_logs SELECT * FROM otel_logs_map;
INSERT INTO otel_metrics SELECT * FROM otel_metrics_map;
```

<Warning>
  仅建议用于少于约 100 亿行的数据集。之前以 Map 类型存储的数据未保留类型精度 (所有值均为字符串) 。因此，在这些旧数据过期之前，它们在新的 schema 中将显示为字符串，需要在前端进行一定的类型转换。新数据则会借助 JSON 类型保留其原有类型。
</Warning>
