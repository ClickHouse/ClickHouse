<Note>
  本页介绍 **Self-managed ClickHouse Observability**。如需使用推荐的全托管方案，请参阅[此处](/zh/clickstack/observability/overview)的文档。
</Note>

高吞吐量服务每秒可能产生数百万个跨度。逐一存储所有跨度的成本很高，因此团队通常会运行 OpenTelemetry 收集器的[尾部采样处理器](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/tailsamplingprocessor)，每 N 个跨度只保留 1 个。每个保留下来的跨度都带有一个 `SampleRate` 属性，用于记录 N 值。

数据经过采样后，不加处理的聚合结果就会失真：`count()` 返回的事件数只有实际发生数的 N 分之一，`sum()` 和 `avg()` 会出现偏差，百分位数也会发生偏移。仪表盘上显示的请求计数、吞吐量和错误率都会偏低，从而造成误导。

Self-managed ClickHouse Observability 通过具备采样感知能力的查询引擎解决了这一问题。在链路追踪数据源上配置采样率表达式后，查询构建器会重写 SQL 聚合，按每个跨度的采样率对其加权，该机制适用于仪表盘、告警和即席搜索。

## 工作原理 {#how-it-works}

当链路追踪数据源配置了 `sampleRateExpression` 时，查询构建器会将其包装为：

```sql
greatest(toUInt64OrZero(toString(expr)), 1)
```

不带 `SampleRate` 属性的 span 默认权重为 1，因此对于未采样的数据，结果与原始查询完全相同。

随后，查询构建器会按如下方式重写聚合：

| 聚合                 | 重写前                | 重写后 (经采样校正)                               |
| ------------------ | ------------------ | ----------------------------------------- |
| count              | `count()`          | `sum(weight)`                             |
| count + 条件         | `countIf(cond)`    | `sumIf(weight, cond)`                     |
| avg                | `avg(col)`         | `sum(col * weight) / sum(weight)`         |
| sum                | `sum(col)`         | `sum(col * weight)`                       |
| quantile(p)        | `quantile(p)(col)` | `quantileTDigestWeighted(p)(col, weight)` |
| min / max          | 不变                 | 不变                                        |
| count&#95;distinct | 不变                 | 不变                                        |

<Note>
  在采样场景下，百分位数使用 `quantileTDigestWeighted` 计算，这是一种基于 T-Digest sketch 的近似算法。结果接近真实值，但并不精确。
</Note>

## 配置采样率表达式 {#configuring}

在 **数据源设置** 中打开您的链路追踪数据源，然后在 **采样率表达式** 字段中输入一个 ClickHouse 表达式，其求值结果为每个跨度的采样率。

例如，如果您的 OpenTelemetry 尾部采样处理器将采样率写入 `SpanAttributes['SampleRate']`：

配置完成后，所有图表、仪表盘、告警以及服务仪表盘面板都会自动应用采样加权聚合，无需逐一修改查询。
