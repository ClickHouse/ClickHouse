迁移可观测性平台，通常不只是更换数据存储的位置。Datadog agent 和 SDKs 可能早已部署在成千上万个应用、主机、虚拟机和 Kubernetes Pod (容器组) 中。如果还没来得及评估另一个后端，就得先为所有这些重新做插桩，那么迁移在产生任何价值之前，就已经变成了一个大型项目。

内置于 ClickStack 版 OpenTelemetry (OTel) collector 中的 **Datadog receiver** 消除了这部分前期成本。现有的 Datadog agent 和 SDKs 无需任何改动即可继续运行。你不用再把遥测数据发送到 Datadog，而是将它们指向该 receiver；它会把 Datadog 的原生日志、trace 和指标载荷转换为 OpenTelemetry 数据模型，并通过标准的 collector 管道传递到 ClickStack。

由于该 receiver 位于常规 collector 管道中，你可以用它来：

* **在不改动应用代码的情况下并行评估 ClickStack 和 Datadog**，利用现有 agent 将同一份遥测数据同时发送到两个平台。
* **平滑迁移到 ClickStack**，保留当前采集层，并逐步采用 OpenTelemetry 插桩。
* **长期并行运行两套技术栈**，让每个平台各尽其长。

## 为什么要将 ClickStack 与 Datadog 搭配运行 {#why-run-clickstack-alongside-datadog}

对大多数团队而言，将可观测性数据迁出 Datadog 的主要原因是成本。随着应用规模扩大、插桩的服务越来越多，日志和 trace 的数据量也持续增长，团队只能在增加支出与少保留一部分遥测数据之间做出取舍。而这些成本控制手段又会反过来限制调查时的可见性：经过采样的链路追踪、未建索引的日志、聚合汇总后的指标以及较短的保留窗口，都会在你最需要的时候削减可用的上下文信息。

[ClickStack](/zh/clickstack/overview) 构建于 ClickHouse 之上，在大规模日志和追踪工作负载场景下，其成本效益可比 Datadog 高出 100 倍以上。正是这种存储成本上的差异，让 ClickStack 与 Datadog 搭配运行物有所值：

* **更长的保留期。** 根据运维需求而非预算来设置保留期限，保留数周甚至数月后仍可能需要查阅的事件。
* **全保真数据。** 无需采样即可存储每一条日志和 trace，让调查基于完整数据而非部分数据展开。
* **无 API 速率限制。** 直接像查询数据库一样查询遥测数据，而无需通过按量计费的 API，也不存在按查询或按端点的限流。
* **完整的 SQL 访问能力。** 使用 SQL 分析日志、指标和链路追踪，并将其与 ClickHouse 中已有的业务数据或基础设施数据进行关联。
* **智能体工作负载。** 通过 [ClickStack MCP 服务器](/zh/clickstack/mcp) 将遥测数据开放给 AI 智能体，并直接在 ClickHouse 上运行不限次数的分析查询。

全保真遥测数据对于智能体驱动的调查尤为重要。智能体无法对调查开始前就已被丢弃的事件进行推理；它还需要足够的历史记录，才能将当前事件与以往的故障、行为变化以及更长期的模式进行对比。

## Datadog receiver 的工作原理 {#how-the-datadog-receiver-works}

在典型的 OpenTelemetry 部署中，遥测数据在到达后端之前，会先发送到 OpenTelemetry collector。collector 会从以 agent 模式运行的 collectors，以及为应用埋点的 [OpenTelemetry SDKs](/zh/clickstack/ingesting-data/sdks/index) 接收数据，应用所需的过滤或转换，将事件按批次处理，然后导出到目标端。

<div className="ch-image-lg">
  <Frame>
    ![简单的 OTel 管道](/images/use-cases/observability/simple_otel_pipeline.png)
  </Frame>
</div>

[Datadog receiver](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/datadogreceiver) 为这一架构增加了另一种输入。它提供了一个端点，能够理解 Datadog agents 和 SDKs 使用的协议，并将传入的 Datadog 载荷转换为 OpenTelemetry 数据模型。之后，这些数据会像其他遥测数据一样，通过常规的 collector 管道继续处理。

现有的 Datadog agents 只需重新配置为将日志和链路追踪发送到运行在 ClickStack collector 上的 receiver。应用可以继续使用现有的 Datadog SDKs，而已经部署在整个基础设施中的 agents 也无需改动。

  <Frame>
    ![Datadog 到 OpenTelemetry](/images/use-cases/observability/datadog_to_otel.png)
  </Frame>
</div>

由于 collector 管道可以使用多个 exporter，同一份遥测数据就可以同时发送到 Datadog 和 ClickStack。这也正是并行评估和长期并行运行成为可能的原因：你可以基于完全相同的数据对比两个平台，然后再独立决定是否迁移。

## 接收器处理的内容 {#what-the-receiver-handles}

该接收器会将 Datadog 载荷转换为对应的 OpenTelemetry 表示形式，使 ClickStack 无需任何 Datadog 专用逻辑即可解析、关联和查询这些数据：

* **日志记录。** Datadog 的毫秒级时间戳会被转换为纳秒，并用于填充 OpenTelemetry 的 timestamp、observed timestamp、body 和 severity 字段，因此记录不会再显示在 Unix 纪元时间点上。
* **资源属性与严重级别。** `info`、`warn` 和 `error` 等 Datadog 状态会映射为对应的 OpenTelemetry `SeverityNumber` 和 `SeverityText`。主机名、服务名称、环境，以及已知的容器、云和 Kubernetes 标签都会被提升为标准资源属性。
* **trace 与日志关联。** `dd.trace_id` 和 `dd.span_id` 字段用于填充 OpenTelemetry 的 trace 和 span 标识符，接收器还会根据 Datadog 的拆分表示重建完整的 128 位追踪 ID。此功能默认启用，可将来自 Datadog 的日志和 span 与使用 OpenTelemetry 插桩的服务关联起来。
* **结构化 JSON 日志。** 默认启用的 `decode_json_message` 选项会执行通常由 Datadog 后端完成的 JSON 处理，提取 body、时间戳、严重级别、trace 标识符、资源字段以及其余属性。
* **兼容当前版本的 agent。** Datadog Agent 7.59 及更高版本默认使用 Zstandard 压缩 HTTP 有效载荷。该接收器同时支持 Zstandard 和 gzip，因此当前版本的 agent 可以正常连接，其有效载荷不会被拒绝。

这些改进已包含在 ClickStack 采集器发行版中并会自动配置，也可在 [OpenTelemetry Collector Contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) 项目中获取。

## 启用 Datadog receiver {#enabling-the-datadog-receiver}

Datadog receiver 包含在 ClickStack 发行版的 OpenTelemetry collector 中，监听端口 `8126`。它默认处于禁用状态，可通过 `ENABLE_DATADOG_RECEIVER` 环境变量启用。

启用后，将你的 Datadog agent 指向该 receiver，并使用 ClickStack 界面 (ClickStack 用户界面) 生成的摄取 key 对其进行身份验证。

使用开源 ClickStack 时，collector 会使用在部署时生成的摄取 key 来保护其端点。你需要启用该 receiver，从 ClickStack 界面 (ClickStack 用户界面) 复制该 key，并将其用作 Datadog agent 的 API key。

<Steps>
  <Step title="启动已启用 receiver 的 collector" id="start-collector-oss">
    下面的示例使用的是[all-in-one 镜像](/zh/clickstack/deployment/all-in-one)。如果你使用的是其他部署模式，请确保将相同的 flag 应用于运行 collector 的容器。

    设置 `ENABLE_DATADOG_RECEIVER=true` 并暴露端口 `8126`：

    ```shell
    docker run --name clickstack \
      -p 8080:8080 \
      -p 4317:4317 \
      -p 4318:4318 \
      -p 8126:8126 \
      -e ENABLE_DATADOG_RECEIVER=true \
      clickhouse/clickstack-all-in-one:latest
    ```

    现在可通过 `http://localhost:8126` 访问该 receiver。

    <Note>
      **在本地运行 Datadog agent**

      Datadog agent 也会监听端口 `8126`。如果 agent 和 collector 运行在同一台主机上，请将 collector 映射到其他主机端口以避免冲突，例如 `-p 18126:8126`，并让 agent 改为指向该端口。
    </Note>

    按照[开源入门指南](/zh/clickstack/getting-started/oss#navigate-to-hyperdx-ui)中的说明完成其余设置。
  </Step>

  <Step title="复制你的摄取 API key" id="copy-ingestion-key-oss">
    在 ClickStack 界面 (ClickStack 用户界面) 中，选择左下角的用户菜单，进入 **Team Settings &gt; API Keys**，然后复制 **Ingestion API Key**。

    <div className="ch-image-lg">
      <Frame>
        ![ClickStack 摄取 key](/images/use-cases/observability/hyperdx_ingestion_key.png)
      </Frame>
    </div>
  </Step>

  <Step title="配置 Datadog agent" id="configure-datadog-agent-oss">
    更新 `/opt/datadog-agent/etc/datadog.yaml` 中的 agent 配置文件，将日志、链路追踪和指标发送到该 receiver。使用你的 ClickStack 摄取 key 作为 API key，并将各个目标端指向该 receiver 的端点：

    ```yaml
    api_key: "<YOUR_CLICKSTACK_INGESTION_KEY>"

    # 指标目标端
    dd_url: "http://localhost:8126"

    # ClickStack 当前支持 Datadog v2 指标摄取端点。
    use_v3_api:
      series:
        enabled: false

    # 链路追踪目标端
    apm_config:
      enabled: true
      apm_dd_url: "http://localhost:8126"

    # 日志目标端
    logs_enabled: true

    logs_config:
      logs_dd_url: "http://localhost:8126"
      force_use_http: true

    # 这些功能需要 Datadog 的 backend，而我们并未使用它，因此将其禁用。
    remote_updates: false

    remote_configuration:
      enabled: false
    ```

    此配置将：

    * 将指标、链路追踪和日志发送到该 receiver，而不是 Datadog。
    * 禁用 v3 指标摄取，因为该 receiver 支持 Datadog v2 指标端点。
    * 关闭远程更新和远程配置，因为它们依赖 Datadog 后端。
  </Step>

  <Step title="重启 agent" id="restart-agent-oss">
    重启 Datadog agent 以加载新配置。在 macOS 上：

    ```shell
    sudo launchctl kickstart -k system/com.datadoghq.agent
    ```

    现在，agent 发送的遥测数据会流入 ClickStack，你可以在 ClickStack 用户界面中查看。
  </Step>
</Steps>

<div id="what-you-can-migrate-today">
  ## 当前可迁移的内容 {#what-you-can-migrate-today}
</div>

Datadog 接收器 是 OpenTelemetry Collector Contrib 中的一个 alpha 组件，并且在 ClickStack 采集器 发行版中被标记为 Experimental，因此需要通过特性开关启用。

该 接收器 已针对 **日志和 trace** 工作负载进行了充分测试，推荐用于基于这些信号评估 ClickStack。**指标** 虽然可用，但仍需进一步测试和开发。该 接收器 目前支持 Datadog 的 v1 和 v2 指标摄取 端点；使用更新协议版本的 agent 必须显式配置为通过受支持的端点发送指标。

目前，如果你的应用已经使用 Datadog SDKs，或你的基础设施中正在运行 Datadog agent，这个 接收器 可以帮助你快速评估 ClickStack。并行运行两条管道，验证数据在 ClickStack 中的呈现方式和查询效果，然后再决定是否推进更大范围的迁移。如果评估结果显示出明显优势，同一架构也支持渐进式迁移：在各项服务逐步迁移到 OpenTelemetry 的过程中，保留现有的 Datadog 插桩。

应用还可以将 DogStatsD 自定义指标直接发送到 ClickStack 采集器，采集器也能从接收到的链路追踪数据中派生出请求、错误和耗时指标。请参阅[接收 StatsD 指标](/zh/clickstack/ingesting-data/collector#statsd-receiver)和[从 span 派生指标](/zh/clickstack/ingesting-data/collector#span-metrics)。
