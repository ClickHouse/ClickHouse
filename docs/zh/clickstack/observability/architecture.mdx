ClickHouse Observability 完全运行在 **ClickHouse Cloud** 中，提供全托管的可观测性后端，同时沿用相同的 ClickStack 数据模型和用户体验。如需了解自管理部署，请参阅[自管理架构](/zh/clickstack/self-configured/architecture)。

在此模式下，**ClickHouse、ClickStack 用户界面以及 OpenTelemetry (OTel) 摄取采集器**均由 ClickHouse Cloud 负责托管、运维和安全防护。用户只需对其应用程序进行插桩，并将遥测数据从自身环境发送到该 managed service。

### OpenTelemetry 采集器：数据摄取 {#open-telemetry-collector-managed}

ClickHouse Observability 内置托管的 OpenTelemetry (OTel) 采集器，以开放、标准化的方式摄取遥测数据。在您的服务中，打开 **团队设置 → 数据 → Managed Telemetry**，复制 OTLP 端点和 API key。有关连接和身份验证的说明，请参阅[发送 OpenTelemetry 数据](/zh/clickstack/observability/ingesting-data/opentelemetry)。

该采集器以高效的批次将遥测数据导出到 ClickHouse Cloud，并针对每种遥测信号使用经过优化的表结构。

摄取采集器由 ClickHouse Cloud 托管。不过，您可能仍需在自己的环境中部署采集器，用于收集主机指标、Kubernetes 日志等遥测数据，并将其转发到托管端点。

### ClickHouse Cloud：核心引擎 {#clickhouse-cloud}

ClickHouse Observability 的核心是 ClickHouse Cloud，即 ClickHouse 的无服务器版本。ClickHouse 是一款专为大规模实时分析而设计的列式数据库。ClickHouse Cloud 为可观测性数据的摄取和查询提供支撑，可实现：

* 在海量事件中快速搜索
* 大规模摄取 high-cardinality 遥测数据
* 针对可观测性数据的列式压缩
* 原生支持半结构化 JSON 数据，支持动态模式演进
* 内置数百个分析函数的强大 SQL 引擎

ClickHouse Cloud 以宽事件的形式处理可观测性数据，从而在统一的结构中对日志、指标和链路追踪进行深度关联。

与 ClickHouse 开源版相比，它还为可观测性场景带来多项额外优势：

* 计算资源独立于存储自动扩缩容
* 借助对象存储保留遥测数据，不受计算资源容量限制
* 集成身份验证
* 安全与合规功能
* 无缝升级

### ClickStack 用户界面：交互界面 {#hyperdx}

ClickStack 用户界面是 ClickStack 的前端界面，提供以下功能：

* 自然语言搜索和 Lucene 风格搜索
* 实时追踪日志 (Live tailing) ，便于实时调试
* 日志、指标和链路追踪的统一视图
* 会话回放，实现前端可观测性
* 仪表盘创建与告警配置
* SQL 查询接口，支持高级分析

ClickStack 用户界面专为 ClickHouse 打造，将强大的搜索能力与直观的工作流相结合，帮助您快速发现异常、排查问题并获取洞察。

在 ClickHouse Observability 中，该 UI 已集成到 ClickHouse Cloud 控制台的身份验证体系中。

### 摄取与查询隔离 {#ingestion-query-isolation}

ClickHouse Observability 为摄取和查询分别配备独立的计算资源。写入计算资源负责处理传入的遥测数据以及后台数据维护；读取计算资源负责处理搜索、仪表盘、笔记本和告警查询。两者访问同一底层对象存储。

这种分离减少了摄取工作负载与查询工作负载之间的资源争用。如果写入计算资源暂时不可用，读取计算资源仍可继续查询已存储的数据，但最新的遥测数据可能会出现延迟。如果读取计算资源不可用，摄取仍可继续进行，但搜索和告警评估可能会中断。

### 扩缩容 {#scaling}

ClickHouse Cloud 会根据工作负载的变化自动管理容量。托管采集器通过水平扩展来承载摄取流量，而写入和读取计算资源的扩缩容彼此独立，也与存储相互独立。

扩缩容并非即时完成。摄取量骤增可能会推迟新遥测数据可被搜索的时间；查询高峰则可能在容量调整期间导致响应时间变长。将不同工作负载分离，有助于降低一种工作负载对另一种工作负载的影响。

### 摄取缓冲与恢复 {#ingestion-buffering-recovery}

托管采集器会首先尝试将遥测数据写入 ClickHouse。如果 ClickHouse 暂时无法接受写入，摄取管道可以将批次存储到亚马逊 S3 中，以便稍后重放。此临时摄取缓冲区独立于 ClickHouse 用于存储遥测数据的对象存储。写入恢复后，已缓冲的数据将被摄取到 ClickHouse 中。

在恢复期间，由于需要处理积压数据，近期的遥测数据可能会延迟到达或出现乱序。该缓冲机制可帮助系统从临时写入中断中恢复，但不提供 cross-region 故障转移，也无法保证在所有故障场景下都能成功投递数据。

部分数据仍可能丢失，包括采集器停止时仅保存在其内存中的数据，以及既无法写入 ClickHouse 也无法写入 S3 的批次。请为发送数据的 agent 和采集器配置失败导出重试，并在支持的情况下使用持久化队列，以便在中断期间保留遥测数据。
