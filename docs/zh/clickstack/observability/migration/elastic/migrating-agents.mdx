## 从 Elastic 迁移 agent {#migrating-agents-from-elastic-self-configured}

Elastic Stack 提供了多种可观测性数据采集 agent，具体包括：

* [Beats 家族](https://www.elastic.co/beats)，例如 [Filebeat](https://www.elastic.co/beats/filebeat)、[Metricbeat](https://www.elastic.co/beats/metricbeat) 和 [Packetbeat](https://www.elastic.co/beats/packetbeat)，均基于 `libbeat` 库构建。这些 Beats 支持通过 Lumberjack 协议[将数据发送到 Elasticsearch、Kafka、Redis 或 Logstash](https://www.elastic.co/docs/reference/beats/filebeat/configuring-output)。
* [`Elastic Agent`](https://www.elastic.co/elastic-agent) 是一个统一的 agent，能够采集日志、指标和链路追踪。它可通过 [Elastic Fleet Server](https://www.elastic.co/docs/reference/fleet/manage-elastic-agents-in-fleet) 进行集中管理，并支持将数据输出到 Elasticsearch、Logstash、Kafka 或 Redis。
* Elastic 还提供了一个 [OpenTelemetry 收集器发行版：EDOT](https://www.elastic.co/docs/reference/opentelemetry)。虽然目前尚不支持通过 Fleet Server 编排，但如果您计划迁移到 ClickHouse Observability，它是一条更灵活、更开放的路径。

最佳迁移路径取决于您当前使用的 agent。接下来的各节将针对每种主要 agent 类型分别介绍可用的迁移方案。我们的目标是尽可能降低迁移成本，并在条件允许时，让您在过渡期间继续沿用现有的 agent。

## 推荐的迁移路径 {#prefered-migration-path-self-configured}

我们建议尽可能将所有日志、指标和 trace 的采集迁移到 [OpenTelemetry (OTel) 收集器](https://opentelemetry.io/docs/collector/)，并将采集器[以代理角色部署在边缘](/zh/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured)。这是发送数据最高效的方式，还能避免架构上的复杂性和额外的数据转换。

<Info>
  **为什么选择 OpenTelemetry 收集器？**

  OpenTelemetry 收集器为可观测性数据摄取提供了一种可持续且供应商中立的解决方案。我们了解到，一些组织运营着由数千甚至数万个 Elastic agent 组成的机群。对于这些用户而言，保持与现有 agent 基础设施的兼容可能至关重要。本文档既支持这一需求，也帮助团队逐步过渡到基于 OpenTelemetry 的采集方式。
</Info>

## ClickHouse OpenTelemetry 端点 {#clickhouse-otel-endpoint-self-configured}

在执行 agent 迁移步骤之前，请先配置目标端。以下 Vector 和 EDOT 示例均通过 OTLP HTTP 发送 OpenTelemetry 数据。

<Tabs>
  <Tab title="全托管">
    <BetaBadge label="Beta 版服务" />

    在 **团队设置 → 数据 → Managed Telemetry** 中复制您的 OTLP HTTP 端点和 API key，然后在运行 Vector 或 EDOT 的环境中设置以下变量：

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    请原样使用该端点 (包括端口) ，不要添加 `/v1/logs` 后缀。有关连接详情，请参阅 [发送 OpenTelemetry 数据](/zh/clickstack/observability/ingesting-data/opentelemetry)。
  </Tab>

  <Tab title="自管理">
    按照 [自管理设置指南](/zh/clickstack/self-configured/getting-started/managed) 部署接收端采集器，然后在运行 Vector 或 EDOT 的环境中设置该采集器可访问的 OTLP HTTP 端点和授权请求头：

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_COLLECTOR_TOKEN'
    ```

    如果您已通过 `OTLP_AUTH_TOKEN` 为接收端采集器启用保护，请将该令牌作为授权值。如果已禁用身份验证，请从示例中删除 `authorization` 请求头。详见 [保护采集器](/zh/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured)。

    仅当发送端和接收端位于同一网络命名空间时，才可使用 `localhost`。如果接收端启用了 TLS，请使用其 HTTPS 端点，并配置对其证书的信任。
  </Tab>
</Tabs>

## 从 Beats 迁移 {#migrating-to-beats-self-configured}

已大规模部署 Beat 的用户在迁移到 ClickHouse Observability 时，可能希望保留现有部署。

**目前此方案仅在 Filebeat 上经过测试，因此仅适用于日志。**

Beats agent 使用 [Elastic Common Schema (ECS)](https://www.elastic.co/docs/reference/ecs)，该 schema 目前[正在合并到 ClickHouse Observability 所使用的 OpenTelemetry](https://github.com/open-telemetry/opentelemetry-specification/blob/main/oteps/0199-support-elastic-common-schema-in-opentelemetry.md) 规范中。然而，这两种 [schema 之间仍存在显著差异](https://www.elastic.co/docs/reference/ecs/ecs-otel-alignment-overview)，目前用户需要在将数据摄取到 ClickHouse Observability 之前，自行将 ECS 格式的事件转换为 OpenTelemetry 格式。

我们建议使用 [Vector](https://vector.dev) 完成此转换。Vector 是一款轻量级、高性能的可观测性数据管道，支持一种名为 Vector Remap Language (VRL) 的强大转换语言。

如果您的 Filebeat agent 已配置为将数据发送到 Kafka (Beats 支持的输出之一) ，Vector 可以从 Kafka 消费这些事件，使用 VRL 进行 schema 转换，再通过 OTLP 将其转发到您已配置的 OTLP 端点。

另外，Vector 还支持通过 Logstash 所使用的 Lumberjack 协议接收事件。这样，Beats agent 便可将数据直接发送到 Vector，由 Vector 执行相同的转换，再通过 OTLP 转发到您已配置的 OTLP 端点。

下图展示了这两种架构。

以下示例介绍了配置 Vector 通过 Lumberjack 协议接收 Filebeat 日志事件的初始步骤。我们提供了用于将入站 ECS 事件映射为 OTel 规范的 VRL，映射后的事件将通过 OTLP 发送到您已配置的 OTLP 端点。从 Kafka 消费事件的用户只需将 Vector Logstash source 替换为 [Kafka source](https://vector.dev/docs/reference/configuration/sources/kafka/)，其余步骤均保持不变。

<Steps>
  <Step title="安装 vector" id="install-vector-self-configured">
    请按照[官方安装指南](https://vector.dev/docs/setup/installation/)安装 Vector。

    将 Vector 安装在 Filebeat agent 可访问的主机上。

    在[将 Vector 部署到生产环境](https://vector.dev/docs/setup/going-to-prod/)时，可参考架构和安全方面的最佳实践。
  </Step>

  <Step title="配置 vector" id="configure-vector-self-configured">
    需要将 Vector 配置为通过 Lumberjack 协议接收事件，从而模拟一个 Logstash 实例。为此，可为 Vector 配置一个 [`logstash` 数据源](https://vector.dev/docs/reference/configuration/sources/logstash/)：

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
          # The files below are generated from the steps at https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          # crt_file: logstash.crt
          # key_file: logstash.key
          # ca_file: ca.crt
          # verify_certificate: true
    ```

    <Info>
      **TLS 配置**

      如果需要双向 TLS，请参照 Elastic 指南 [&quot;Configure SSL/TLS for the Logstash output&quot;](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output) 生成证书和私钥，然后按上文所示在配置中指定这些文件。
    </Info>

    事件将以 ECS 格式接收，可使用 Vector Remap Language (VRL) 转换器将其转换为 OpenTelemetry schema。该转换器的配置非常简单，脚本单独保存在一个文件中：

    ```yaml
    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'
    ```

    请注意，它从上文的 `beats` source 接收事件。我们的 remap 脚本如下所示。该脚本仅针对日志事件进行过测试，但可作为处理其他格式的基础。

    <Accordion title="VRL - 将 ECS 转换为 OTel">
      ```javascript
      # Define keys to ignore at root level
      ignored_keys = ["@metadata"]

      # Define resource key prefixes
      resource_keys = ["host", "cloud", "agent", "service"]

      # Create separate objects for resource and log record fields
      resource_obj = {}
      log_record_obj = {}

      # Copy all non-ignored root keys to appropriate objects
      root_keys = keys(.)
      for_each(root_keys) -> |_index, key| {
          if !includes(ignored_keys, key) {
              val, err = get(., [key])
              if err == null {
                  # Check if this is a resource field
                  is_resource = false
                  if includes(resource_keys, key) {
                      is_resource = true
                  }

                  # Add to appropriate object
                  if is_resource {
                      resource_obj = set(resource_obj, [key], val) ?? resource_obj
                  } else {
                      log_record_obj = set(log_record_obj, [key], val) ?? log_record_obj
                  }
              }
          }
      }

      # Flatten both objects separately
      flattened_resources = flatten(resource_obj, separator: ".")
      flattened_logs = flatten(log_record_obj, separator: ".")

      # Process resource attributes
      resource_attributes = []
      resource_keys_list = keys(flattened_resources)
      for_each(resource_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_resources, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  resource_attributes = push(resource_attributes, attribute)
              }
          }
      }

      # Process log record attributes
      log_attributes = []
      log_keys_list = keys(flattened_logs)
      for_each(log_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_logs, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  log_attributes = push(log_attributes, attribute)
              }
          }
      }

      # Get timestamp for timeUnixNano (convert to nanoseconds)
      timestamp_nano = if exists(.@timestamp) {
          to_unix_timestamp!(parse_timestamp!(.@timestamp, format: "%Y-%m-%dT%H:%M:%S%.3fZ"), unit: "nanoseconds")
      } else {
          to_unix_timestamp(now(), unit: "nanoseconds")
      }

      # Get message/body field
      body_value = if exists(.message) {
          to_string!(.message)
      } else if exists(.body) {
          to_string!(.body)
      } else {
          ""
      }

      # Create the OpenTelemetry structure
      . = {
          "resourceLogs": [
              {
                  "resource": {
                      "attributes": resource_attributes
                  },
                  "scopeLogs": [
                      {
                          "scope": {},
                          "logRecords": [
                              {
                                  "timeUnixNano": to_string(timestamp_nano),
                                  "severityNumber": 9,
                                  "severityText": "info",
                                  "body": {
                                      "stringValue": body_value
                                  },
                                  "attributes": log_attributes
                              }
                          ]
                      }
                  ]
              }
          ]
      }
      ```
    </Accordion>

    最后，将转换后的事件发送到您已配置的 OTLP 端点。为此，需要在 Vector 中配置一个 OTLP 数据接收端，并以 `remap_filebeat` 转换输出的事件作为输入：

    ```yaml
    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat] # receives events from a remap transform - see below
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```

    请使用与您的部署对应的[连接变量](#clickhouse-otel-endpoint-self-configured)。由于此输出发送的是日志记录，Vector URI 中需包含 `/v1/logs`。

    最终的完整配置如下所示：

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
            #crt_file: /data/elasticsearch-9.0.1/logstash/logstash.crt
            #key_file: /data/elasticsearch-9.0.1/logstash/logstash.key
            #ca_file: /data/elasticsearch-9.0.1/ca/ca.crt
            #verify_certificate: true

    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'

    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat]
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```
  </Step>

  <Step title="配置 Filebeat" id="configure-filebeat-self-configured">
    配置 Filebeat，使其通过 Logstash 输出将数据发送到 Vector，并替换所有现有的输出配置。将 `YOUR_VECTOR_HOST` 替换为运行 Vector 的主机；仅当两者运行在同一主机上时才使用 `localhost`。配置 TLS，使其与 Vector 输入的设置相匹配：

    ```yaml
    # ------------------------------ Logstash Output -------------------------------
    output.logstash:
      # The Logstash hosts
      hosts: ["YOUR_VECTOR_HOST:5044"]

      # Optional SSL. By default is off.
      # List of root certificates for HTTPS server verifications
      #ssl.certificate_authorities: ["/etc/pki/root/ca.pem"]

      # Certificate for SSL client authentication
      #ssl.certificate: "/etc/pki/client/cert.pem"

      # Client Certificate Key
      #ssl.key: "/etc/pki/client/cert.key"
    ```
  </Step>
</Steps>

## 从 Elastic Agent 迁移 {#migrating-from-elastic-agent-self-configured}

Elastic Agent 将各类 Elastic Beats 整合为单个软件包。该 agent 与 [Elastic Fleet](https://www.elastic.co/docs/reference/fleet/fleet-server) 集成，可实现集中编排和配置。

已部署 Elastic Agent 的用户有以下几种迁移路径：

* 配置该 agent，通过 Lumberjack 协议将数据发送到 Vector 端点。**目前该方式仅针对使用 Elastic Agent 采集日志数据的用户进行过测试。** 可以通过 Kibana 中的 Fleet UI 进行集中配置。
* [将该 agent 作为 Elastic OpenTelemetry Collector (EDOT) 运行](https://www.elastic.co/docs/reference/fleet/otel-agent)。Elastic Agent 内置嵌入式 EDOT Collector，只需对应用程序和基础设施进行一次插桩，即可将数据发送到多个供应商和后端。在此配置下，只需将 EDOT Collector 配置为通过 OTLP 将事件转发到您已配置的 OTLP 端点即可。**此方法支持所有事件类型。**

下面将分别演示这两种方案。

### 通过 Vector 发送数据 {#sending-data-via-vector-self-configured}

<Steps>
  <Step title="安装并配置 Vector" id="install-configure-vector-self-configured">
    按照从 Filebeat 迁移部分所述的[相同步骤](#install-vector-self-configured)安装并配置 Vector。
  </Step>

  <Step title="配置 Elastic Agent" id="configure-elastic-agent-self-configured">
    需要将 Elastic Agent 配置为通过 Logstash 协议 Lumberjack 发送数据。这是一种[受支持的部署模式](https://www.elastic.co/docs/manage-data/ingest/ingest-reference-architectures/ls-networkbridge)，既可以集中配置，也可以在不使用 Fleet 部署时[通过 agent 配置文件 `elastic-agent.yaml`](https://www.elastic.co/docs/reference/fleet/logstash-output) 进行配置。

    如需通过 Kibana 集中配置，可[在 Fleet 中添加 Output](https://www.elastic.co/docs/reference/fleet/fleet-settings#output-settings)。

    <div className="ch-image-md">
      <Frame>
        ![添加 Logstash 输出](/images/use-cases/observability/add-logstash-output.webp)
      </Frame>
    </div>

    随后即可在 [agent 策略](https://www.elastic.co/docs/reference/fleet/agent-policy)中使用此输出。这样，所有使用该策略的 agent 都会自动将数据发送到 Vector。

    <div className="ch-image-md">
      <Frame>
        ![Agent 设置](/images/use-cases/observability/agent-output-settings.webp)
      </Frame>
    </div>

    由于这需要配置基于 TLS 的安全通信，建议参考指南[“为 Logstash 输出配置 SSL/TLS”](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output)进行操作，只需将 Vector 实例视为 Logstash 即可。

    请注意，这还要求在 Vector 中将 Logstash source 同样配置为使用双向 TLS。请使用[该指南中生成的](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs)私钥和证书对输入进行相应配置。

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: true  # 如果使用 TLS，请设置为 true。
          # 以下文件按照 https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs 中的步骤生成
          crt_file: logstash.crt
          key_file: logstash.key
          ca_file: ca.crt
          verify_certificate: true
    ```
  </Step>
</Steps>

### 将 Elastic Agent 作为 OpenTelemetry 收集器运行 {#run-agent-as-otel-self-configured}

Elastic Agent 内置了 EDOT Collector，只需对应用程序和基础设施进行一次插桩，即可将数据发送到多个供应商和后端。

<Info>
  **Agent 集成与编排**

  如果使用随 Elastic Agent 分发的 EDOT Collector，将无法利用 [agent 提供的现有集成](https://www.elastic.co/docs/reference/fleet/manage-integrations)。此外，该采集器无法由 Fleet 集中管理，用户只能以[独立模式运行 agent](https://www.elastic.co/docs/reference/fleet/configure-standalone-elastic-agents)，并自行管理配置。
</Info>

要将 Elastic Agent 与 EDOT Collector 一起运行，请按照 [Elastic 官方指南](https://www.elastic.co/docs/reference/fleet/otel-agent-transform)进行操作。然后使用您的[连接变量](#clickhouse-otel-endpoint-self-configured)配置 OTLP HTTP 导出器：

```yaml
exporters:
  otlphttp/clickhouse:
    endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
    headers:
      authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
```

在每个需要转发的日志、指标或链路追踪管道中，将 `otlphttp/clickhouse` 添加到 `exporters` 列表中，并保留现有的接收器和处理器。如需并行摄取，请在这些管道中保留 Elastic 导出器；准备停止向 Elastic 发送数据时，再将其移除。

该导出器使用基础端点，并自动追加信号路径。如果 HTTPS 接收器使用私有证书颁发机构，请配置 `tls.ca_file`；如果该接收器要求双向 TLS，还需配置 `tls.cert_file` 和 `tls.key_file`。这些设置用于保护 EDOT 到 OTLP 的连接，与 Filebeat 到 Vector 的 TLS 配置相互独立。

## 从 Elastic OpenTelemetry 收集器迁移 {#migrating-from-elastic-otel-collector-self-configured}

已在运行 [Elastic OpenTelemetry 收集器 (EDOT)](https://www.elastic.co/docs/reference/opentelemetry) 的用户，只需重新配置其 agent，通过 OTLP 将数据发送到您已配置的 OTLP 端点即可。具体步骤与上文[将 Elastic Agent 作为 OpenTelemetry 收集器运行](#run-agent-as-otel-self-configured)中所述的步骤完全相同。此方法适用于所有数据类型。
