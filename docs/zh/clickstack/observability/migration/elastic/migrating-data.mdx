本指南重点介绍如何从 Elastic 迁移到**全托管的 ClickHouse Observability**，这也是默认使用方式。ClickHouse 负责管理底层 schema 和存储。您的摄取管道必须以 **OpenTelemetry Protocol (OTLP)** 格式发送遥测数据；Elasticsearch 文档无法直接导入全托管服务。

对于自管理部署，请参阅 [Elasticsearch 与 ClickHouse 的对应概念](/zh/clickstack/self-configured/migration/elastic/concepts)以及[类型映射](/zh/clickstack/self-configured/migration/elastic/types)。自管理部署的数据迁移说明已在下文单独标注。

## 并行运行策略 {#parallel-operation-strategy-self-configured}

在可观测性场景下从 Elastic 迁移到 ClickHouse Observability 时，我们建议采用**并行运行**方式，而不是尝试迁移历史数据。该策略具有以下优势：

1. **风险最低**：两个系统并发运行，您既可以验证 ClickHouse Observability、让用户逐步熟悉新系统，又能继续访问现有数据和仪表盘。
2. **数据自然过期**：大多数可观测性数据的保留期有限 (通常为 30 天或更短) ，随着 Elastic 中的数据逐步过期，即可自然完成过渡。
3. **简化迁移**：无需借助复杂的数据传输工具或流程在系统之间搬迁历史数据。

<br />

<Info>
  **迁移数据**

  自管理部署可以使用 `Elasticsearch` 表引擎读取历史文档，并将其复制到 ClickHouse 表中。请参阅[迁移数据](#migrating-data-self-configured)。此方式独立于全托管 ClickHouse Observability 所使用的 OTLP 摄取路径。
</Info>

### 实施步骤 {#implementation-steps-self-configured}

<Steps>
  <Step title="配置双路摄取" id="configure-dual-ingestion-self-configured">
    设置数据采集管道，使其同时将数据发送到 Elastic 和 ClickHouse Observability。对于全托管的 ClickHouse Observability，管道必须使用您的摄取 API key 将 OTLP 数据导出到托管端点；仅将 Elasticsearch JSON 文档转发到该端点是不够的。

    具体实现方式取决于您当前使用的采集 agent，请参阅[“迁移 Agent”](/zh/clickstack/observability/migration/elastic/migrating-agents)。
  </Step>

  <Step title="调整保留期" id="adjust-retention-period-self-configured">
    检查两个系统的保留期，确保过渡期间历史数据仍然可用。针对不同部署方式的具体说明，请参阅[保留期与生存时间 (TTL)](#retention-and-ttl-self-configured)。
  </Step>

  <Step title="验证与比较" id="validate-and-compare-self-configured">
    * 在两个系统上分别运行查询，确保数据一致性
    * 比较查询性能和结果
    * 将仪表盘和告警迁移到 ClickHouse Observability。目前此过程需要手动完成。
    * 确认所有关键仪表盘和告警在 ClickHouse Observability 中均能按预期工作
  </Step>

  <Step title="逐步过渡" id="graudal-transition-self-configured">
    * 随着 Elastic 中的数据自然过期，您将越来越多地依赖 ClickHouse Observability
    * 在确认 ClickHouse Observability 运行可靠后，即可开始将查询和仪表盘逐步切换过去
  </Step>
</Steps>

### 长期保留 {#long-term-retention-self-configured}

对于需要更长保留期的组织：

* 继续并行运行两套系统，直到 Elastic 中的所有数据均已过期
* 对于自管理部署，可考虑使用[物化视图](/zh/concepts/features/materialized-views/incremental-materialized-view)保留已聚合或过滤后的历史数据，同时让原始数据自然过期。

### 迁移时间线 {#migration-timeline-self-configured}

迁移时间线取决于您的数据保留期要求：

* **30 天保留期**：迁移可在一个月内完成。
* **更长的保留期**：保持并行运行，直至 Elastic 中的数据过期。
* **历史数据**：在规划导入之前，请先查阅[迁移数据](#migrating-data-self-configured)中针对不同部署方式的指导。

## 保留期与生存时间 (TTL) {#retention-and-ttl-self-configured}

<Tabs>
  <Tab title="全托管">
    <BetaBadge label="Beta 版产品" />

    <Note>
      Beta 阶段，全托管的 ClickHouse Observability 会将数据保留 30 天。保留期将在正式可用 (GA) 时调整，届时将提供进一步的指引。
    </Note>

    请结合这 30 天的保留期以及您在 Elastic 中设置的保留期来规划迁移过渡。在历史数据不再需要之前，请继续保留 Elastic，以便查询历史数据。
  </Tab>

  <Tab title="自管理">
    ClickHouse 通过在 `MergeTree` 表上配置 [TTL 子句](/zh/clickstack/self-configured/managing/production#configure-ttl-managed)来自动删除已过期的数据。

    请根据迁移需求设置表的保留期。相关示例请参阅[自管理生产环境 TTL 设置](/zh/clickstack/self-configured/managing/production#configure-ttl-managed)。
  </Tab>
</Tabs>

## 迁移数据 {#migrating-data-self-configured}

<Tabs>
  <Tab title="全托管">
    <BetaBadge label="Beta 版本" />

    <Note>
      目前尚无法将历史数据从 Elasticsearch 直接迁移到全托管的 ClickHouse Observability。托管端点仅接受 OTLP 遥测数据，不接受 Elasticsearch 文档或 JSON 导出文件。自管理选项卡中基于 `Elasticsearch` 表引擎的工作流不适用于全托管服务。
    </Note>

    采用并行摄取方式，将新的遥测数据以 **OTLP 格式**发送到您的 managed service，同时将历史数据保留在 Elastic 中。有关托管端点和身份验证设置，请参阅[使用 OpenTelemetry 摄取数据](/zh/clickstack/observability/ingesting-data/opentelemetry)；有关采集选项，请参阅[迁移 agent](/zh/clickstack/observability/migration/elastic/migrating-agents)。

    如果必须导入历史数据，您需要构建自定义管道，将 Elasticsearch 文档转换为相应的 OpenTelemetry 日志、链路追踪或指标，再通过 OTLP 导出。本指南不提供现成的转换器。在规划历史数据回填之前，请先确认 managed service 的保留期限。
  </Tab>

  <Tab title="自管理">
    使用 [`Elasticsearch` 表引擎](/zh/reference/engines/table-engines/integrations/elasticsearch) 直接从 Elasticsearch 读取文档，然后通过 `INSERT INTO ... SELECT` 将其复制到本地 ClickHouse 表中。无需导出文件，也无需安装 `elasticdump`。

    该引擎为只读引擎：创建 `Elasticsearch` 表只是将远程文档开放用于查询，并不会将其复制到 ClickHouse 存储中。

    <Note>
      Elasticsearch 集成目前处于实验阶段，需要在支持该功能的 ClickHouse 版本上设置 `enable_elasticsearch = 1`。该集成要求 Elasticsearch 7.12 或更高版本，且不支持 OpenSearch。您的 ClickHouse 服务必须能够访问 Elasticsearch 端点，且索引必须启用 `_source`，才能读取文档内容。
    </Note>

    <Steps>
      <Step title="连接到 Elasticsearch 索引" id="connect-elasticsearch-self-managed">
        在您的自管理 ClickHouse Cloud 服务中运行以下 SQL，并将其中的端点、索引和凭据替换为您自己的值：

        ```sql
        SET enable_elasticsearch = 1;

        CREATE TABLE elasticsearch_source
        ENGINE = Elasticsearch(
            'https://<elasticsearch-host>:9200',
            '<index-name>',
            '<username>',
            '<password>'
        );

        SELECT _index, _id, document
        FROM elasticsearch_source
        LIMIT 10;
        ```

        该表将每个文档的 `_source` 映射为 `JSON` 类型的 `document` 列。虚拟列 `_id` 和 `_index` 分别标识源文档和源索引。在确定目标端 schema 之前，请先查看部分样本数据。

        该引擎还支持 API 密钥和命名集合。请参阅[身份验证参考文档](/zh/reference/functions/table-functions/elasticsearch#authentication)。
      </Step>

      <Step title="将文档复制到 ClickHouse" id="copy-documents-self-managed">
        此示例将文档以 `JSON` 形式存储在暂存表中，便于您在配置可观测性 source 之前对其进行检查和转换。请在 `elasticsearch_source` 所在的数据库中运行以下语句：

        ```sql
        CREATE TABLE migrated_elasticsearch_documents
        (
            source_index String,
            document_id String,
            document JSON
        )
        ENGINE = MergeTree
        ORDER BY (source_index, document_id);

        INSERT INTO migrated_elasticsearch_documents
        SELECT _index, _id, document
        FROM elasticsearch_source;
        ```

        每次读取都会使用 Elasticsearch point in time，为该查询提供一致的快照。这是一次性复制，而非持续复制。重复执行插入会再次追加数据行，排序键不会对文档进行去重。

        导入数据量较大时，请使用引擎的 `query` 参数将任务拆分为互不重叠的批次，并在 Elasticsearch Query DSL 中使用绝对时间戳作为边界。ClickHouse 的 `WHERE` 子句不会将过滤条件下推到 Elasticsearch。请参阅[引擎示例](/zh/reference/engines/table-engines/integrations/elasticsearch#usage-example)和[限制](/zh/reference/functions/table-functions/elasticsearch#limitations)。
      </Step>

      <Step title="映射并验证导入的数据" id="validate-import-self-managed">
        将文档数量和代表性记录与源快照进行比对。在将数据用于搜索或仪表板之前，请检查时间戳、缺失字段和嵌套值。`JSON` 类型会根据值推断类型 (包括时间戳) ，因此其文本表示形式可能发生变化。如需控制字段类型，请使用显式的 JSON 类型提示。

        根据您的查询和数据保留需求设计目标端可观测性 schema，然后使用 `INSERT INTO ... SELECT` 从暂存表中提取并转换字段。请参阅 [Elasticsearch 与 ClickHouse 概念](/zh/clickstack/self-configured/migration/elastic/concepts)、[类型映射](/zh/clickstack/self-configured/migration/elastic/types)和 [schema 设计指南](/zh/guides/clickhouse/data-formats/json/schema)。

        复制文档并不会自动将其转换为 OpenTelemetry schema，也不会在 UI 中配置 source。请参阅[配置选项](/zh/clickstack/self-configured/managing/config)，配置该表及其时间戳、消息和其他字段映射。
      </Step>
    </Steps>
  </Tab>
</Tabs>
