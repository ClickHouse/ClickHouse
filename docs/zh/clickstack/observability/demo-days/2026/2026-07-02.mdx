现在可以直接链接到笔记本内容块 (单元) ，并支持跨分支链接。在自定义 Markdown 中，您既可以使用绝对链接，也可以使用相对哈希链接，从而更方便地将他人引导至某个结论背后的确切依据。

更大的变化在 agent 侧。笔记本中生成的摘要现在会引用其所依据的内容块，读者可以直接跳转查看底层数据，而无需盲目相信摘要内容。

我们还调整了已有笔记本的打开方式。摘要卡片现在默认展开，而不再折叠。通常，当您重新打开笔记本时，这正是您所需要的。

## OTel 指标表主键优化 {#otel-metrics-table-primary-key-optimization}

*演示者：[@knudtty](https://github.com/knudtty)*

<Frame>
  <iframe src="https://www.youtube.com/embed/GIwNxRJGQKg" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

本节深入解析如何验证并缩减 OTel 指标表的主键。这里最有参考价值的衡量标准是每个粒度的主键字节数，即主键总大小除以粒度数量。由于较大的表天然拥有更多粒度，采用这一标准可以消除表大小的影响，从而进行公平的比较。

原始 schema 约为每个粒度 148 字节，新 schema 则接近 17 字节，主键大小缩减约 9 倍，生产环境中的内存使用量也有相近幅度的下降。

schema 变更的幅度并不大。`MetricName` 现在使用 `LowCardinality`，除非需要处理数量极其庞大的不同指标名称，否则不会有问题；即便如此，也只有在极端情况下才需要关注。时间戳从纳秒精度的 `DateTime64` 改为秒级精度的普通 `DateTime`，这对指标而言已经绰绰有余。如需保留纳秒精度，您仍可以自行修改 schema。

我们还为时间添加了显式的 min/max 索引，并将主键中的完整属性 map 替换为其哈希值。所有指标表 schema 均已应用相同的变更，我们也正在将这些变更贡献到上游的 OTel Collector。

## 数值背后的趋势线/迷你线图 {#trend-and-spark-lines-behind-numbers}

*演示者 [@alex-fedotyev](https://github.com/alex-fedotyev)*

<Frame>
  <iframe src="https://www.youtube.com/embed/4XwOkyNqDEY" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

数值卡片现在可以在数值背后显示趋势线或面积图。这一直是 Grafana 中广受欢迎的功能，如今 ClickStack 也支持了。

您可以在卡片的显示设置中启用该功能。默认不显示背景图表，也可选择线图或面积图。它几乎无需配置，却能让仪表盘的完成度明显提升。

目前，背景图表仅适用于声明式数值卡片，暂不支持自定义 SQL。有用户反馈希望能更灵活地控制图表绘制的内容，我们正考虑在后续版本中提供这一支持。

## Grafana 插件改进 {#grafana-plugin-improvements}

*演示者：[@alex-fedotyev](https://github.com/alex-fedotyev)*

<Frame>
  <iframe src="https://www.youtube.com/embed/doFNUMZotJU" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

以下汇总了 ClickStack Grafana 插件即将推出的新功能。

数据源配置在现有的多数据库设置之外，新增了单表模式。只需将其指向某一张表 (例如生产环境日志) ，查询编辑器就会切换为专为探索设计的紧凑型构建器。您可以对服务名称等字段使用快速筛选条件，进行包含和排除过滤；需要时也仍可直接使用 SQL。

我们还将推出适用于 OTel 日志和链路追踪的现成仪表盘，沿用大家熟悉的下钻模式。日志仪表盘包含按服务划分的概览、日志量图表以及日志详情。Trace 探索涵盖服务视图、延迟热力图和操作细分。此外还有一个合并的服务仪表盘，将日志和链路追踪整合在一起并按 跨度 名称分组，让您排查单个服务时无需在多个工具之间来回切换。

所有这些仪表盘均可直接配合默认 schema 开箱即用。新用户可以立即上手，再以它们为起点构建自己的仪表盘。

此外还新增了两个向导式构建器。借助变量构建器，您可以直接选择列值，而无需编写自定义 SQL。例如，您可以基于 pod（容器组） 名称创建变量，并预览其返回的值。

注解构建器会基于对所选字段的变更检测查询生成注解。将其指向某个服务的版本属性后，每当该值发生变化，它都会自动添加一个部署标记，无需您亲自编写 SQL。

本次对导航和链路追踪查看体验进行了一系列打磨。

现在，在搜索页面中可以将侧边栏固定为展开状态，无需关闭即可滚动浏览并选择其他行。导航也会记录当前选项卡的上下文。返回按钮会借助面包屑路径将您准确带回之前所在的位置，而不只是关闭面板。

此外还新增了键盘快捷键弹窗，方便查找可用的快捷键绑定。关联了链路追踪的日志现在会显示一个标签，点击即可直接跳转到对应的链路追踪。

跨度视图的升级最为明显。跨度 会按服务名称着色，服务变化时循环使用不同颜色；新增的缩略图让大型 链路追踪 不再是满屏的灰色条形，阅读起来轻松得多。您可以拖动选择时间范围进行放大，并一键重置视图。新的历史记录栈还支持在多个 链路追踪 之间切换，并随时回到之前的位置。

选中的 跨度 提供了更完善的展开和折叠控件，无需再逐个关闭子项。我们还合并了一项社区贡献的修复，为极短的 跨度 设置了最小渲染宽度。例如，仅持续几微秒的 跨度 也能在时间线上保持可见，无需一路放大到底。

## MCP 中的指标查询、仪表盘评估与更完善的告警错误报告 {#metrics-queries-dashboard-evals-and-better-alert-error-reporting-in-mcp}

*演示者：[@brandon-pereira](https://github.com/brandon-pereira)*

<Frame>
  <iframe src="https://www.youtube.com/embed/yjceqgveZr8" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

本周期 MCP 服务器同时上线了三项改进。

MCP 现在可以直接运行指标查询 (包括在笔记本中运行) ，无需再绕道仪表盘来获取底层数据。

我们还为仪表盘构建新增了端到端评估。该评估目前的通过率约为 75%，我们正在持续加入干扰项，使其更难被钻空子。当 MCP 在实际使用中创建出有问题的仪表盘时，这些失败案例可以回流到评估集中。长期来看，这有助于在问题演变为反复出现的故障之前及早发现，例如原始 SQL source 生成错误查询的情况。

工具错误现在会按类别分类，不再全部归入同一个笼统的类别。用户提交的错误 SQL 查询与数据库超时等内部故障会被分开处理。有了这种区分，我们就能围绕 MCP 健康状况构建更有用的告警。

## OTel collector 批处理处理器更新 {#otel-collector-batch-processor-updates}

*演示者：[@SpencerTorres](https://github.com/SpencerTorres)*

<Frame>
  <iframe src="https://www.youtube.com/embed/rlSm_9ivsQ4" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

OpenTelemetry 正在将批处理功能从独立的批处理处理器移至导出器配置中。ClickStack 采集器此前已同时支持这两种方式，因此无需改动代码，最终只需更新文档。

在旧模型中，管道里有一个专门的批处理处理器，负责先缓冲行，再将其传递给导出器。该处理器有自己的批次大小、最大批次大小和超时设置。

OpenTelemetry 正在统一采用的新模型将批处理器与导出器放在一起，而不再置于处理器链中。大部分概念都得以沿用，包括最小和最大批次大小以及队列大小。此外，基于导出器的配置还支持阻塞行为、按字节限制以及持久化，这些都是旧的批处理处理器所不具备的。

文档现在推荐使用基于导出器的配置，并说明了如何迁移现有的批处理处理器设置。文档还建议，对于大多数部署，以至少 5,000 行搭配较短的超时作为合理的默认值。批处理配置不当仍是导致用户初次使用 ClickHouse 时体验不佳的最常见原因之一。

## 基于任意属性的上下文视图 {#surrounding-context-for-arbitrary-attributes}

*演示者：[@MikeShi42](https://github.com/MikeShi42)*

<Frame>
  <iframe src="https://www.youtube.com/embed/BZTG8TTTyoA" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

借助上下文视图 (Surrounding context) ，您可以打开一条日志行，查看其前后发生的其他事件。默认情况下，上下文按服务、pod（容器组） 或节点分组。这对大多数采用 OTel schema 的部署来说效果很好，但使用自定义 schema 的用户此前一直无法便捷地围绕自己的属性构建该视图。

现在，无论属性来自 OTel schema 还是自定义 schema，您都可以使用日志行上的任意属性来驱动上下文视图。常用的服务、pod（容器组） 和节点选项依然保留，同时您也可以轻松地按遥测 SDK 版本或日志行上的任何其他字段分组。您还可以随时清除所选内容，重新开始。

**相关 PRs：** [#2558](https://github.com/hyperdxio/hyperdx/pull/2558) fix: support service name expression and quick attribute filters in surrounding context
