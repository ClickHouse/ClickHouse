如果您已经运行 ClickStack 一段时间，可能已经注意到，默认 schema 无需任何修改即可应对大多数可观测性工作负载。当默认 schema 不再够用时，例如查询延迟开始上升，或者您的访问模式已偏离默认设计，就可以参考本页内容。

在实践中，以下四项优化基本涵盖了最有效的手段，大致按所需工作量从低到高排列。前两项是局部的 `ALTER TABLE` 变更，可以以增量方式逐步推行。第三项在仪表盘反复运行相同聚合时收效显著。第四项需要进行表迁移，因此最为复杂。

以下概述特意保持简短。如需了解每项变更背后的原理、基准测试结果，以及将其应用于现有数据的具体步骤，请参阅[性能调优](/zh/clickstack/self-configured/managing/performance-tuning)。

<Steps>
  <Step title="物化常用查询属性" id="materialize-attributes">
    对 `LogAttributes['service.version']` 进行过滤时，ClickHouse 需要为其检查的每一行加载并解码整个 `LogAttributes` Map。将该属性提升为 `MATERIALIZED` 列后，同样的过滤就变成了列读取，速度通常可提升一个数量级。列创建后，ClickStack 会自动重写过滤条件，因此已保存的搜索和仪表盘无需任何修改即可照常使用。

    只需选择您实际经常查询的属性。每个 materialized 列都会增加存储开销和写入时的成本，因此原则是“用什么就提升什么”，而不是“全部提升”。

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    对于已有的行，新列将保持为空，除非您另外执行 `ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion`。

    了解更多：[物化常用查询属性](/zh/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes)。
  </Step>

  <Step title="添加跳过索引" id="add-skip-indexes">
    跳过索引使 ClickHouse 能够排除不可能匹配过滤条件的数据粒度，从而将全量扫描变为少量有针对性的读取。以下三种类型值得了解：

    * **文本索引** (`text(tokenizer = ...)`) ：适用于字符串列以及 `mapKeys`/`*AttributeItems` 数组。默认的日志 schema 已内置这些索引。
    * **Min-max 索引**：适用于按范围过滤的数值列。trace 的 `Duration` 就是典型示例。
    * **Bloom 过滤器**：在尚不支持文本索引的 ClickHouse 版本上，用于高基数的等值查找。

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    只有当跳过索引确实能裁剪粒度时，其评估开销才物有所值。在认定其有效之前，请先对具有代表性的查询执行 `EXPLAIN indexes = 1` 进行确认。

    了解更多：[添加跳过索引](/zh/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes)。
  </Step>

  <Step title="预计算重复的聚合" id="materialized-views">
    当仪表盘上反复运行相同的聚合 (如按错误率排名的服务、各端点的 p99 延迟、每分钟请求数) 时，materialized view 可在写入时计算结果，并将其写入一张小型 rollup 表。之后仪表盘直接查询该 rollup 表，而非原始日志或链路追踪数据，开销相对低得多。

    当仪表盘访问频繁且底层表很大时，这种做法收益明显。代价是写入时会消耗一些 CPU，并需要额外维护一张表。

    了解更多：[利用 materialized view](/zh/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views)。
  </Step>

  <Step title="根据访问模式选择主键" id="choose-primary-key">
    主键决定了行在磁盘上的排序方式。针对主键前导列的过滤可让 ClickHouse 直接定位到相关区间；而不以这些列开头的过滤则会扫描整个分区。

    默认的日志主键 `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)` 适合“服务 X 在最近 N 分钟内发生了什么”这类查询。如果您的大多数查询以其他列开头 (如 tenant ID、客户 ID、区域) ，那么将主键改为以该列开头，将是效果最显著的优化。

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- 与 otel_logs 相同的列
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse 不支持原地修改主键，因此这需要进行表迁移，而不是简单执行 `ALTER`。性能调优指南详细介绍了如何创建新表、重定向数据摄取，以及如何使用 `Merge` 表让现有仪表盘能够同时查询新旧数据。

    了解更多：[修改主键](/zh/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key)。
  </Step>
</Steps>
