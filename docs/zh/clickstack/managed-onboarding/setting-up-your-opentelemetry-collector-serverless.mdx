<Info>
  **TL;DR**

  已经在运行 OpenTelemetry 收集器？从服务的“入门指南”页面复制导出器代码片段，粘贴到采集器配置中，将该导出器添加到流水线，然后重新加载即可。现有的接收器和处理器照常工作，它们采集的所有数据都会发送到 ClickHouse Observability。

  所需时间：约 10 分钟
</Info>

您已创建 ClickHouse Observability 服务。如果您的环境中已有负责数据采集的 OpenTelemetry 收集器，请参考本指南。常见场景包括：

* **基础设施遥测数据。** 主机 CPU、内存、磁盘和网络指标，以及磁盘上的日志文件。
* **Kubernetes。** 容器日志、kubelet 节点代理和集群指标，以及 Kubernetes 事件。
* **现有指标端点。** 抓取服务已暴露的 Prometheus 端点。
* **[gateway](/zh/clickstack/ingesting-data/collector#collector-roles)。** 位于网络内部的单一端点，接收来自 SDK 和 agent 采集器的 OTLP 数据，批处理后统一转发。

无论采集器收集什么数据，连接方式都一样：只需添加一个指向服务托管 OTLP 端点的 `otlp_http` 导出器。接收器、处理器以及现有导出器均无需改动，因此在评估期间，您可以同时向当前后端和 ClickHouse Observability 发送数据。之后的摄取、schema、存储、优化和扩缩容均由 ClickHouse Observability 负责。

<Note>
  **还没有采集器？**

  入门并不需要采集器。应用程序可以将 OpenTelemetry 数据直接导出到托管端点，请参阅[使用 OpenTelemetry 对应用程序进行插桩](/zh/clickstack/managed-onboarding/instrument-application-serverless)。如果您想开始采集基础设施遥测数据，[本地日志和指标](/zh/clickstack/observability/example-datasets/local-data)和[监控 Kubernetes](/zh/clickstack/observability/example-datasets/kubernetes) 均提供了可直接部署的完整采集器配置。
</Note>

## 前置条件 {#prerequisites}

* 一个 ClickHouse Observability 服务。如果您还没有，请参阅[入门指南](/zh/clickstack/observability/getting-started)进行创建。
* 一个可重新配置并重启的 OpenTelemetry 收集器。任何发行版均可，包括厂商构建，因为 `otlp_http` 导出器属于核心采集器的组成部分。
* 采集器所在主机可通过端口 `4318` 出站 HTTPS 访问您服务的遥测数据端点。

## 连接采集器 {#connect-your-collector}

<Steps>
  <Step title="复制导出器配置" id="copy-exporter-configuration">
    打开您的 ClickHouse Observability 服务。在收到数据之前，该服务会显示 **Start sending telemetry** 页面。

    <div className="ch-image-lg">
      <Frame>
        ![Start sending telemetry 页面，显示当前服务尚无数据，并提供三个选项：Use an existing OpenTelemetry setup、Instrument with AI 和 Follow setup guides](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    在 **Use an existing OpenTelemetry setup** 下，选择 **View connection details**，然后打开 **Collector config** 选项卡。其中会显示为您的服务预先生成的导出器配置块。选择 **Reveal key** 显示完整的 API key，然后点击复制按钮。

    <div className="ch-image-md">
      <Frame>
        ![Set up OpenTelemetry 对话框，已选中 Collector config 选项卡，显示一个带有已遮蔽端点和 Bearer authorization 请求头的 otlphttp 导出器](/images/clickstack/getting-started/observability-collector-config.png)
      </Frame>
    </div>

    该代码片段的结构如下：

    ```yaml
    exporters:
      otlphttp:
        endpoint: https://YOUR_OTEL_ENDPOINT:4318
        headers:
          authorization: Bearer <your-api-key>
    ```

    有两点需要注意。端点是基础 URL：不要追加 `/v1/logs`、`/v1/traces` 或 `/v1/metrics`，因为导出器会自动添加信号路径。请求头的值需包含 `Bearer` 前缀。

    UI 中该导出器的名称为 `otlphttp`。较新的采集器版本将其改名为 `otlp_http`，并保留 `otlphttp` 作为已弃用的别名，因此两者均可使用。以下示例使用当前名称。

    您也可以随时在 **团队设置 → Managed Telemetry** 中查看这些值。
  </Step>

  <Step title="添加导出器" id="add-the-exporter">
    将该配置块添加到采集器配置的 `exporters` 部分。通过环境变量提供密钥，可避免将其明文写入文件：

    ```yaml
    exporters:
      otlp_http:
        endpoint: ${env:CLICKSTACK_OTLP_ENDPOINT}
        headers:
          authorization: "Bearer ${env:CLICKSTACK_API_KEY}"
    ```

    如果您的配置中已有名为 `otlp_http` 的导出器，请为该导出器另起一个名称，例如 `otlp_http/clickhouse`，并在下一步中使用该名称。

    如果采集器运行在 Kubernetes 中，请将密钥存储在 Secret 中，并通过 `extraEnvs` 或 pod spec 注入这两个值。[监控 Kubernetes](/zh/clickstack/observability/example-datasets/kubernetes) 指南演示了如何结合 OpenTelemetry Helm 图表使用这种方式。
  </Step>

  <Step title="将导出器添加到流水线" id="add-to-pipelines">
    将该导出器追加到所有需要向 ClickHouse Observability 发送数据的管道中。保留现有导出器，即可同时向两个目标发送数据：

    ```yaml
    service:
      pipelines:
        logs:
          receivers: [otlp, file_log]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        metrics:
          receivers: [otlp, host_metrics, prometheus]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
    ```

    接收器和处理器无需改动，只需修改导出器列表。

    <Info>
      **agent 与 gateway 角色**

      如果您在每台主机上运行 agent 采集器，并由其将数据转发到中央 gateway，则只需修改 gateway。agent 仍照常向 gateway 发送数据。
    </Info>
  </Step>

  <Step title="重新加载并检查日志" id="reload-and-check">
    根据采集器获取配置的方式 (systemd unit、Docker `-e` 参数或 Kubernetes Secret) ，在其运行环境中将 `CLICKSTACK_OTLP_ENDPOINT` 设置为端点 URL，将 `CLICKSTACK_API_KEY` 设置为密钥。然后重启或重新加载采集器，并查看其日志中是否有导出错误：

    * `401` 或 `403` 响应表示 API key 有误或缺少 `Bearer` 前缀。
    * `404` 响应通常表示端点后追加了信号路径，例如 `/v1/logs`。
    * `no such host` 或 TLS 错误表明端点存在拼写错误，或端口 `4318` 上的出站连接被阻止。

    至此，采集器原本收集的所有数据也会同步发送到您的服务。
  </Step>
</Steps>

## 确认数据已到达 {#confirm-data-is-arriving}

返回服务中的 **Start sending telemetry** 页面，然后点击 **Check for data**。遥测数据到达后，服务状态会变为 **Data received**，同时 **Start exploring** 按钮变为可用。

<div className="ch-image-lg">
  <Frame>
    ![Start sending telemetry 页面，显示服务状态为 Data received，提示您已可以开始探索，且 Start exploring 按钮已启用](/images/clickstack/getting-started/observability-data-received.png)
  </Frame>
</div>

点击 **Start exploring** 打开 **搜索** 页面。选择 **Logs** source，将时间范围设置为 **Last 15 minutes**，并按采集器上报的某个 `ServiceName` 进行过滤。在 **Chart Explorer** 中将 source 切换为 **Metrics**，确认各指标接收器的数据也已正常流入。

如果您的采集器暂时没有数据可发送 (例如其持续读取的日志文件暂无新内容) ，请直接跳转到本指南末尾的[发送样本数据](#send-sample-data)。

## 如果没有显示任何数据 {#if-nothing-shows-up}

* 首先查看采集器日志。身份验证、端点和 TLS 相关问题都会记录在其中，并附带上文列出的错误码。
* 确认每个预期会传入数据的管道都在其 `exporters` 中列出了 `otlp_http`。已定义但未被任何管道引用的接收器不会采集任何数据。
* 确认采集器确实已重新加载。某些发行版需要重启采集器，仅重新加载配置无法使新的导出器生效。
* 在 **搜索** 中扩大时间范围，并移除所有筛选条件。默认 source 可能被设置为 **Traces**，而不是 **Logs**。
* 如需排除服务本身的问题，请前往 **团队设置 → Managed Telemetry**，使用 **Send a Test Log**。如果该日志出现在 **搜索** 中，说明服务能够正常接收数据，问题出在您的采集器与端点之间。
* 如需单独排查采集器，请将 [发送样本数据](#send-sample-data) 中的 `telemetrygen` 生成器指向采集器自身的 OTLP 接收器，而不是服务，地址采用不带认证方案的 `host:port` 格式，例如 `--otlp-endpoint localhost:4317 --otlp-insecure`，且不加 `--otlp-http`。如果这些数据能够到达，说明采集器的导出器工作正常，问题出在导出器的上游环节。

## 使用采集器收集更多数据 {#collect-more}

配置好导出器后，您添加的每个接收器都会经由同一条管道将数据发送到您的服务：

* [本地日志和指标](/zh/clickstack/observability/example-datasets/local-data)：一份完整配置，使用 `file_log` 接收器持续读取日志文件，并使用 `host_metrics` 接收器收集 CPU、内存、磁盘和网络指标。
* [监控 Kubernetes](/zh/clickstack/observability/example-datasets/kubernetes)：通过 OpenTelemetry Helm 图表安装，其中 DaemonSet 守护进程集用于收集容器日志和 kubelet 节点代理指标，部署 (Deployment) 用于收集集群指标和事件。
* **Prometheus 端点。** 将 [`prometheus` 接收器](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/prometheusreceiver)连同您现有的 `scrape_configs` 一起添加到 `metrics` 管道中。抓取到的时间序列将以 OpenTelemetry 指标的形式写入，并可在 Chart Explorer 中查看。
* **通过 gateway 接入 SDK。** 将 `OTEL_EXPORTER_OTLP_ENDPOINT` 设置为采集器的地址 (例如 `http://otel-collector.observability.svc:4318`) ，让应用程序将数据发送到该采集器。[使用 OpenTelemetry 为应用程序插桩](/zh/clickstack/managed-onboarding/instrument-application-serverless) 演示了如何为示例应用插桩；只需将托管端点替换为您的采集器地址，并删除 API key，因为该凭据现在由 gateway 提供。
* **在 gateway 处理数据。** 使用 [`filter`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/filterprocessor)、[`transform`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/transformprocessor) 和 [`resourcedetection`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/resourcedetectionprocessor) 处理器，在遥测数据离开您的网络之前过滤噪声、重塑属性，并为其添加云和主机元数据标签。

有关采集器本身的更多信息，请参阅 [OpenTelemetry 收集器文档](https://opentelemetry.io/docs/collector/)，其中介绍了部署模式、扩缩容以及完整的配置参考文档。

## 还没有实时遥测数据？发送样本数据 {#send-sample-data}

如果您的采集器已连接但其数据源没有数据，或者您希望用更丰富的数据来探索 UI，可以直接向您的服务发送一批合成的日志、链路追踪和指标。这种方式会绕过采集器，并直接使用 **Env vars** 选项卡中的连接详情，因此无需重新输入任何内容。

在 **Start sending telemetry** 页面上打开 **View connection details**，或进入 **团队设置 → Managed Telemetry**，然后选择 **Env vars** 选项卡。点击 **Reveal key**，复制该选项卡中的内容，并粘贴到命令行环境中的 `set -a` 与 `set +a` 之间，以确保每一行都会被导出：

<div className="ch-image-md">
  <Frame>
    ![已选中 Env vars 选项卡的 Set up OpenTelemetry 对话框，显示 OTEL_EXPORTER_OTLP_ENDPOINT、带有已遮盖 Bearer 密钥的 OTEL_EXPORTER_OTLP_HEADERS，以及 OTEL_EXPORTER_OTLP_PROTOCOL](/images/clickstack/getting-started/observability-env-vars.png)
  </Frame>
</div>

```shell
set -a
# Paste the Env vars tab here. It looks like this:
OTEL_EXPORTER_OTLP_ENDPOINT=https://YOUR_OTEL_ENDPOINT:4318
OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer <your-api-key>"
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
set +a
```

使用 Docker 镜像运行 OpenTelemetry Collector Contrib 的数据生成器 [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen)：

```shell
telemetrygen() {
  docker run --rm \
    ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
}
```

或者使用 Go 安装该二进制文件：

```shell
go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
```

定义一个简单的 `tg` 辅助函数。由于 `telemetrygen` 的端点命令行选项不接受 URL 协议，该函数会从 `OTEL_EXPORTER_OTLP_ENDPOINT` 中提取主机和端口，并从 `OTEL_EXPORTER_OTLP_HEADERS` 中提取密钥。它通过 HTTPS 发送 OTLP 数据并启用证书验证，每次运行持续 20 秒：

```shell
tg() { local signal=$1; shift; telemetrygen "$signal" \
  --otlp-endpoint "${OTEL_EXPORTER_OTLP_ENDPOINT#*://}" --otlp-http \
  --otlp-header "authorization=\"${OTEL_EXPORTER_OTLP_HEADERS#authorization=}\"" \
  --rate 5 --duration 20s "$@"; }
```

请始终调用 `tg`，不要直接调用 `telemetrygen`。如果将完整的 `https://` URL 传给 `telemetrygen`，会报错 `too many colons in address`。

为三个服务发送日志，各严重级别按贴近真实的比例混合：

```shell
tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="POST"'
tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.status_code="500"'
```

每条命令执行完毕后都会输出一行 `logs generated` 摘要。如果密钥错误，命令会立即失败，错误消息中会包含 `401`。

如需同时填充链路追踪、服务地图和指标数据，请展开下方的命令，并在同一命令行环境中运行。

<Accordion title="生成更丰富的遥测数据（可选）">
  从多个健康的服务以及一个响应缓慢且出错的依赖服务发送包含多个 span 的链路追踪：

  ```shell
  for svc in frontend checkout cart; do
    tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
      --otlp-attributes 'deployment.environment="production"' \
      --telemetry-attributes "http.route=\"/$svc\""
  done

  tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
    --otlp-attributes 'deployment.environment="production"' \
    --telemetry-attributes 'http.route="/charge"'
  ```

  发送一个计数器、一个 Gauge 和一个直方图：

  ```shell
  tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
  tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
  tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
  ```
</Accordion>

返回您的服务，选择 **Check for data**，然后选择 **Start exploring**。在 **搜索** 中，将 `ServiceName` 筛选为 `frontend`、`checkout` 或 `payment`，并将 `SeverityText` 筛选为 `Error`，即可找到支付网关超时的记录。如果您生成了更丰富的数据集，请在 **Traces** source 下打开一条 `payment` trace，查看其子 span 和错误状态；并在 **Chart Explorer** 中为 `http.server.requests` 绘制图表，确认指标数据正常流入。
