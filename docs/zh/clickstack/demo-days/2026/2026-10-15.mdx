## 在保存前校验 Webhook 请求正文模板 {#validating-webhook-body-templates-before-they-save}

*演示者 [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

此前，即使 Generic 或 incident.io Webhook 的请求正文模板有错误，也能直接保存，且不会有任何提示。此后每次投递告警都会失败，而错误只会出现在 ClickStack 的链路追踪和服务器日志中。一个常见原因是在 Handlebars 表达式中对引号做了 JSON 转义，例如 `{{#if (eq state \"ALERT\")}}`：这是合法的 JSON，却是无效的模板。

现在，Webhook 表单会在您编辑时实时检查模板，并在编辑器下方显示错误及其所在的行和列，例如 `Template error on line 1, column 29`。检查会在您停止输入 300 ms 后才触发，因此不会在您刚输入一半 `{{ … }}` 表达式时就报错。空请求正文会被跳过，因为它们使用服务的默认模板；Slack 请求正文同样会被跳过，因为它们不会被渲染。编辑器下方还列出了受支持的变量，包括 `{{alertId}}`、`{{status}}`、`{{value}}` 和 `{{groupKey}}`，并附有简短说明。

同样的校验现在也会在服务端执行，覆盖内部 API、外部 API v2 以及 MCP `clickstack_save_webhook` 工具。在创建、更新或测试时，无效模板会返回 400，并附带 Handlebars 错误及其所在的行和列。测试会在发送任何内容之前失败。校验仅检查模板能否编译，不会渲染结果，也不会检查输出是否为合法的 JSON。

针对自动化工作流，新增的 `POST /api/v2/webhooks/validate` 端点可让 Terraform 在 plan 阶段检查 Webhook 配置。与 `POST /api/v2/dashboards/validate` 类似，它只做校验而不保存。它执行与创建时相同的 URL 和请求正文检查，并始终返回 200 及 `{ valid, errors, normalized }`。该端点不检查名称是否唯一。

**相关 PR：** [#3350](https://github.com/hyperdxio/hyperdx/pull/3350) 在编辑器中显示 Webhook 请求正文模板的编译错误；[#3365](https://github.com/hyperdxio/hyperdx/pull/3365) 拒绝无法编译的 Webhook 请求正文模板，并新增 /api/v2/webhooks/validate

## 在引导过程中自动检测 PromQL source {#auto-detecting-a-promql-source-during-onboarding}

*演示者：[@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=96" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

当某个连接下没有任何 数据源 时，ClickStack 会查找 OpenTelemetry 表，并自动创建 Logs、Traces、Metrics 和 Sessions 数据源。启用 PromQL (`NEXT_PUBLIC_ENABLE_PROMQL=true`) 后，如果找到 ClickHouse `TimeSeries` 表，ClickStack 现在还会一并创建 PromQL source。

检测时会查找 `engine = 'TimeSeries'` 的表，并忽略这些表自动创建的内部 MergeTree 表。如果存在多个候选结果，则按以下优先级依次检查：

* `prometheus.metrics`，即 [ClickHouse Prometheus 文档](https://clickhouse.com/docs/concepts/features/interfaces/prometheus#create-a-timeseries-table)中使用的表。
* 与 OpenTelemetry 表位于同一数据库中的 `metrics_ts`，由采集器的 PromQL 迁移创建。
* 任意数据库中的 `metrics_ts`。

如果只有一个 `TimeSeries` 表，则无论表名是什么，ClickStack 都会直接使用该表。

对于仅包含 `TimeSeries` 表的连接，现在会直接为其创建 PromQL source，而不再转入手动设置流程。即使检测或 PromQL source 创建失败，其他 数据源 也不受影响。

**相关 PR：** [#3310](https://github.com/hyperdxio/hyperdx/pull/3310) 在引导过程中自动检测 PromQL source，[#3311](https://github.com/hyperdxio/hyperdx/pull/3311) 在开发环境默认 数据源 中预配 PromQL source

## PromQL 图表的数据系列上限与最小粒度 {#series-limits-and-minimum-granularity-for-promql-charts}

*演示者 [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=176" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

PromQL 折线图和堆叠条形图现在也提供 **Series Limit** 显示设置，与构建器图表和原始 SQL 图表一致。此前，这类图表在浏览器中最多渲染 250 个数据系列，并提供加载其余数据系列的选项，但该设置处于隐藏状态，也不会随卡片一起保存。

与原始 SQL 图表一样，该上限在浏览器端生效。Prometheus 自带的 `limit` 参数返回的是按标记排序的子集，而不是按值排序的前几个数据系列；而且 ClickHouse 表函数回退路径会忽略该参数。隐藏数据系列的提示也会给出针对 PromQL 的建议：收窄标记匹配器的范围，或添加 `sum by (...)`，而不是使用 `GROUP BY` 或 `WHERE`。

PromQL 数据源现在同样提供 **Minimum auto granularity** 设置，与指标数据源保持一致。该设置决定自动粒度为折线图、数值图、表格、饼图和条形图 (包括其生成的 PromQL 预览) 所能选择的最小桶大小。`$__rate_interval` 也会将该值用作抓取间隔，未设置时回退为 15s。显式设置的卡片粒度不受影响。

**相关 PR：** [#3292](https://github.com/hyperdxio/hyperdx/pull/3292) 支持在 PromQL 数据源上设置最小自动粒度，[#3294](https://github.com/hyperdxio/hyperdx/pull/3294) 支持在 PromQL 时间图表上设置数据系列上限

## PromQL 数据源的数据源级访问控制 {#source-level-access-control-for-promql-sources}

*演示者 [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=301" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**此功能仅适用于托管 ClickStack。**

基于角色的访问控制现已扩展到 PromQL 数据源，与日志、链路追踪和指标一样。借助细粒度的数据源角色，可以授予对某个 PromQL 数据源的**只读**访问权限，同时限制对另一个数据源的访问。

现在，所有 `/v1/prometheus/*` 路由都会检查调用方是否拥有该数据源的**只读**访问权限，若无此权限则返回 403 `RBAC_PERMISSION_DENIED`。如果调用方的数据源访问规则将该数据源完全隐藏，则返回 404 `Source not found`，与数据源 API 的行为保持一致。此变更不会在 ClickHouse 端新增角色强制校验：在 ClickStack Cloud 中，PromQL 查询本就使用用户自身的令牌。

## 仪表盘临时筛选条件 {#ad-hoc-filters-for-dashboards}

*演示者 [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=401" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

除了已有的变量和筛选条件，仪表盘现在还新增了 **临时键和值** 筛选类型。每个临时筛选条件会借助一个或多个 ClickHouse 数据源 (例如日志和链路追踪) 或一个 Prometheus source 来提示可用的键和值。默认情况下，条件会应用到使用这些 数据源 的所有卡片，但你也可以限定其适用的 数据源。该功能通过 `NEXT_PUBLIC_ENABLE_ADHOC_FILTERS` 开启，目前计划工作已完成约一半。

在仪表盘筛选栏中点击筛选条件的输入框，即可选择键、运算符和值，键和值均提供候选建议。SQL 数据源 支持等于、不等于、正则匹配、正则不匹配、`LIKE` 和 `NOT LIKE`。PromQL 数据源 使用 Prometheus 标记而非列键。已应用的条件会以胶囊标签的形式显示，你可以编辑、将其切换为排除条件或清除。所选内容会保存在 URL 中，也可以作为仪表盘默认筛选状态的一部分保存下来。

条件如何作用于卡片取决于卡片类型：

* 构建器卡片使用现有的 `filter` 配置属性，因此无需在 `WHERE` 子句中添加变量。
* 原始 SQL 卡片使用 `$__filters`。查询中必须包含此宏，缺失时会显示警告。未应用任何条件时，它会展开为 `1 = 1`。
* PromQL 卡片使用与 Grafana 相同的解析库，将条件作为标记匹配器添加到每个指标选择器中。

你可以在生成的 SQL 和 PromQL 预览中查看已应用的条件。

你还可以直接在**搜索卡片**中筛选。将鼠标悬停在单元格上，即可调出与搜索页面相同的复制、筛选和排除选项。筛选时，该值会添加到相应的临时筛选条件中；再次点击同一值即可将其移除。在侧边面板中打开某一行后，其中的筛选按钮同样作用于仪表盘。目前，点击筛选功能仅适用于搜索卡片。

导入仪表盘时，你可以重新映射临时筛选条件所查询的 数据源 及其适用的 数据源。外部 API 和 MCP 暂不支持临时筛选条件。

**相关 PR：** [#3335](https://github.com/hyperdxio/hyperdx/pull/3335) 为临时仪表盘筛选条件添加 schema 和类型，[#3317](https://github.com/hyperdxio/hyperdx/pull/3317) 提取 FilterPill，添加筛选条件编辑器组件，[#3341](https://github.com/hyperdxio/hyperdx/pull/3341) 添加用于配置临时仪表盘筛选条件的 UI，[#3343](https://github.com/hyperdxio/hyperdx/pull/3343) 渲染临时仪表盘筛选条件输入框，[#3366](https://github.com/hyperdxio/hyperdx/pull/3366) 广播临时仪表盘筛选条件，[#3367](https://github.com/hyperdxio/hyperdx/pull/3367) 支持在导入临时筛选条件时重新映射 source，[#3380](https://github.com/hyperdxio/hyperdx/pull/3380) 支持在搜索卡片上点击添加临时筛选条件

## 将 SELECT 和 ORDER BY 移至结果表 {#moving-select-and-order-by-into-the-results-table}

*演示者 [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=636" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**这是一项探索性工作，不承诺一定会发布。**

目前，搜索页面将 `SELECT` 和 `ORDER BY` 放在 `WHERE` 旁边，但它们其实只影响结果表。切换到事件模式或事件差异后，它们依然显示，修改却不起任何作用。我们访谈过的用户也没有意识到可以在 `SELECT` 中选择列，他们一直在找列设置和排序控件。

此原型将两者移至结果表工具栏，分别命名为 **Columns** 和 **Sort**，并在事件差异和事件模式中将其隐藏。**Columns** 列出当前的 `SELECT` 项，支持拖动排序或删除。选择一个建议项或输入表达式 (例如 `upper(Body) as message`) ，然后点击 **Add**。在 **SQL** 选项卡中，您可以直接编辑完整的 `SELECT`。

**Sort** 列出每个 `ORDER BY` 字段及其排序方向，包括 `(toDateTime(Timestamp), Timestamp) DESC` 这样的元组。您也可以在 **SQL** 下编辑原始子句。控件无法拆分的表达式 (例如 `Timestamp DESC NULLS LAST`) 会直接在 SQL 选项卡中打开。通过控件所做的更改会自动生成 SQL，您也仍然可以手动编写。

**Apply** 会更新子句并执行搜索，**Cancel** 会放弃更改，**Reset to default** 会恢复为 source 的默认值。重置列宽、自动换行、查看生成的 SQL 和导出 CSV 等表格操作则改为工具栏右侧的图标按钮。

这样一来，搜索表单也更宽敞了一些。source 位于第一行左侧，**Update** 和 **Alerts** 位于右侧。`WHERE` 子句独占一整行，与 Live Tail、刷新时间间隔和 **Run** 位于同一行。

该 PR 仍处于草稿阶段，欢迎告诉我们您的使用体验。

## 在手机上也能顺畅使用的搜索页面 {#a-usable-search-page-on-a-phone}

*演示者：[@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=843" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

在手机上打开告警后，应当能直接查看日志。此前，筛选侧边栏无法缩小到 200px 以下，查询行不会自动换行，结果也被裁剪在一个 `100vh` 的框内，甚至无法滚动到日志所在位置。

现在，当宽度低于 900px (即导航栏折叠的临界宽度) 时，搜索页面会切换为紧凑布局。筛选条件默认收起，点击 **Show filters** 即可在抽屉面板中展开，从而将全部宽度留给日志表。`SELECT` 和 `ORDER BY` 收进了 **Columns** 开关中，而搜索框始终可见。直方图同样保留，高度缩减为 72px，结果则在工具栏下方的区域内滚动显示。打开筛选抽屉面板不会改变您在桌面端的偏好设置；将窗口拉宽到 900px 以上，即可恢复桌面端布局。

紧凑视口钩子和响应式侧边面板位于 `packages/app/src/components/CompactViewport/` 中，可供其他页面复用，搜索页面是第一个使用它们的页面。此改动先于本文介绍的列与排序原型合入；该原型会在所有屏幕宽度下将 `SELECT` 和 `ORDER BY` 移入结果表。

## 将筛选键和值以流式方式加载到侧边栏 {#streaming-filter-keys-and-values-into-the-sidebar}

*演示者：[@knudtty](https://github.com/knudtty)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=899" title="YouTube 视频播放器" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

此前，搜索页面的筛选侧边栏只会显示一个加载图标，直到所有筛选查询全部完成。虽然这些查询本身已经以流式方式返回结果，但您仍需等到最慢的查询完成后，才能使用任何筛选条件。

现在，键会先行显示，并各自带有加载指示器；值则随着各个查询返回逐步填充。查询本身并未改变，只是侧边栏会在结果到达时即时展示。在较长的时间范围内 (例如搜索两天的数据) ，这一改进尤为明显。

我们还修复了侧边栏无法记住浏览状态的问题。为保证浏览器响应流畅，筛选分组在滚出视图后会从 DOM 中移除。此前，滚动回来时，已展开的分组会变回折叠状态，已加载的分布数据也会消失。现在，两者都会保持您离开时的状态。

**相关 PR：** [#3348](https://github.com/hyperdxio/hyperdx/pull/3348) Stream filter keys and value results to UI，[#3377](https://github.com/hyperdxio/hyperdx/pull/3377) Persist filter expand state upon scrolling
