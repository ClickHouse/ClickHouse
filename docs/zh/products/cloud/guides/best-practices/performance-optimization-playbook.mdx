## 分析工作负载 {#profile-the-workload}

记录当前的延迟、吞吐量和资源使用情况，然后设定一个可衡量的目标。注意区分查询延迟、摄取延迟和数据新鲜度：改善其中一项，可能会增加另一项的工作量。

收集具有代表性的查询及过滤值、执行频率、并发度、摄取速率、数据量、增长情况和保留期限，并考虑各租户之间的差异以及峰值负载。如果是回归问题，请记录数据、schema、版本、服务规格或客户端行为方面的变更。

在 Cloud 中，[查询洞察](/zh/products/cloud/features/sql-console-features/query-insights)可展示查询模式和资源消耗情况。如需进行自定义分析，请跨副本查询 [`system.query_log`](/zh/reference/system-tables/query_log)：

```sql
SELECT
    normalized_query_hash,
    count() AS executions,
    round(avg(query_duration_ms)) AS avg_ms,
    quantile(0.95)(query_duration_ms) AS p95_ms,
    sum(query_duration_ms) AS total_duration_ms,
    avg(read_rows) AS avg_read_rows,
    max(memory_usage) AS max_memory_bytes,
    any(query) AS example_query
FROM clusterAllReplicas('default', merge('system', '^query_log'))
WHERE event_time >= now() - INTERVAL 1 DAY
    AND type = 'QueryFinish'
    AND is_initial_query = 1
    AND query_kind = 'Select'
GROUP BY normalized_query_hash
ORDER BY total_duration_ms DESC
LIMIT 20;
```

此查询按累计耗时对成功执行的查询模式进行排序。此外，还应在查询洞察中检查失败的查询；仅查看成功的执行可能会掩盖超时和超出内存限制的异常。该查询需要访问每个副本上的系统表。日志为异步刷写，因此最近的执行记录可能不会立即显示。

`default` 集群在 ClickHouse Cloud 中可用。如果是单节点部署，请将 `FROM` 表达式替换为 `system.query_log`。如需详细分析，请参阅[诊断慢查询](/zh/guides/clickhouse/performance-and-monitoring/diagnose-slow-queries)。

## 诊断瓶颈 {#diagnose-the-bottleneck}

ClickHouse 将 `MergeTree` 数据存储在已排序、已压缩的 parts 中。后台合并会将多个 parts 整合为更大的 part。稀疏主索引可帮助查询跳过每个 part 中的粒度。有效的优化手段要么减少读取的数据量，要么减少对这些数据执行的计算量。

首先查看表定义和查询计划。请将下方的表和查询替换为您自己的表和查询：

```sql
SHOW CREATE TABLE database_name.table_name;

EXPLAIN indexes = 1
SELECT column_name
FROM database_name.table_name
WHERE filter_column = 'value';
```

对照总数，检查被选中的 parts 和粒度所占的比例。再将其与查询日志中实际的读取的行数、读取字节数、耗时和内存使用量进行比较。对于全表聚合而言，大范围扫描可能是合理的；应结合查询的实际需求进行判断。

| 现象                 | 排查方向                                                      | 可能的后续步骤                            |
| ------------------ | --------------------------------------------------------- | ---------------------------------- |
| 选择性较高的筛选条件仍读取了大部分粒度 | `EXPLAIN` 中的主键裁剪情况                                        | 使排序键与筛选条件保持一致，或评估使用投影或跳过索引。         |
| 活跃 parts 持续增加      | `system.parts` 和 `system.merges` 中的插入大小、分区 fan-out 以及合并活动 | 采用批量插入、使用异步插入，或减少分区碎片化。            |
| 重复执行时明显更快          | 缓存活动和服务生命周期                                               | 分别比较冷启动与预热后的执行情况；缩小工作集，或预先计算重复的工作。 |
| 连接消耗过多内存           | 连接基数、输入和算法                                                | 减少输入、评估使用字典，或测试内存受限的算法。            |
| 并发度升高时延迟上升         | CPU、内存、摄取以及相互竞争的查询                                        | 先减少单个查询的工作量，再评估扩缩容或隔离方案。           |

在更改 schema 或设置之前，请参阅[隔离查询瓶颈](/zh/guides/clickhouse/performance-and-monitoring/isolate-query-bottlenecks)来验证假设。

## 设计 schema {#design-the-schema}

### 选择保证正确性的引擎 {#choose-an-engine-for-correctness}

应根据记录的变更方式以及查询需要如何解读这些记录来选择引擎。

| 引擎                                                     | 典型用途                                                    |
| ------------------------------------------------------ | ------------------------------------------------------- |
| `MergeTree`                                            | 通用的仅追加型数据分析。                                            |
| `ReplacingMergeTree`                                   | 同一记录存在多个版本，并最终按 sorting key 去重。如对正确性有要求，请在查询时采用适当的去重方式。 |
| `AggregatingMergeTree`                                 | 存储聚合状态，通常由增量materialized view 填充。                       |
| `SummingMergeTree`                                     | 可累加的计数器和 rollup。查询时可能仍需对尚未合并的行进行聚合。                     |
| `CollapsingMergeTree` 或 `VersionedCollapsingMergeTree` | 显式的状态记录和取消记录，查询时需满足各引擎特定的要求。                            |

后台合并并不保证在查询之前所有版本或聚合行都已合并完毕。请参阅 [`MergeTree` 系列参考文档](/zh/reference/engines/table-engines/mergetree-family)，了解各引擎的语义。

### 使排序键与查询相匹配 {#align-the-ordering-key-with-queries}

表的 `ORDER BY` 定义了数据的物理排序顺序。主键默认与 sorting key 相同，决定了稀疏索引的构成。二者都不保证唯一性。

应优先选择在高频、高选择性筛选条件中使用的列。在可用作筛选条件的列中，将低基数列放在键的靠前位置，可以改善局部性和压缩效果。但基数本身并不能作为将某列纳入键的理由。

例如，如果查询始终按 tenant 和时间过滤，使用 `(tenant_id, event_time)` 可能会带来收益；而跨所有租户的查询则可能需要不同的顺序。若访问模式确有需要，时间戳或标识符也可以作为首列。

键应保持精简，并使用具有代表性的查询对候选方案进行测试。`ORDER BY tuple()` 无法利用主索引进行裁剪，因此仅应在有意接受这一权衡时使用。请参阅[选择主键](/zh/concepts/best-practices/choosing-a-primary-key)。

### 使用能够保留语义的类型 {#use-types-that-preserve-meaning}

更紧凑的表示形式可以降低存储、内存和扫描开销。选择时应确保不丢失信息：

* 选用足以覆盖预期范围 (包括未来增长) 的整数位宽；需要精确的十进制运算时，使用 `Decimal`。
* 对于重复出现的字符串，可考虑使用 `LowCardinality(String)`；对于受控的值集合，可考虑使用 `Enum`。
* 需要子秒级精度时，使用 `DateTime64`；否则可考虑使用 `DateTime` 或 `Date`。
* 当值的缺失具有特定含义时，使用 `Nullable`。仅当零或空字符串是该业务域中有效的默认值时，才用它们替换缺失值。
* 对于稳定且频繁查询的字段，使用具有明确类型的列。对于不断演进的结构，可评估使用 `JSON`；对于合适的键值数据，可评估使用 `Map`。

完成更改后，请测量压缩后大小和查询性能。参见 [选择数据类型](/zh/concepts/best-practices/select-data-type)、[使用 JSON](/zh/concepts/best-practices/json-type) 以及 [ClickHouse 中的压缩](/zh/guides/clickhouse/data-modelling/compression/compression-in-clickhouse)。

### 按数据管理需求进行分区 {#partition-for-data-management}

应根据数据保留和数据管理操作的需要来选择分区。不同分区中的 parts 永远不会合并，因此分区基数过高会产生大量小数据片段，并增加开销。

不分区、按月分区或按年分区都是不错的起点。如果数据量和保留策略有需要，按天分区也是合适的选择。在按 high-cardinality 标识符进行分区之前，请先评估 parts 的数量和大小。

当查询条件限定了分区表达式时，分区裁剪能够发挥作用，但它无法替代合适的排序键。请参阅[选择分区键](/zh/concepts/best-practices/partitioning-keys)。

### 预计算重复性工作 {#precompute-repeated-work}

| 方法                  | 适用场景                          | 需要考虑的因素                                             |
| ------------------- | ----------------------------- | --------------------------------------------------- |
| 增量materialized view | 重复的聚合或转换可以提前到写入时完成。           | 目标表的存储、插入开销，以及现有数据的历史数据回填。它只处理新插入的块，不会自动反映源表的每一次变更。 |
| 投影                  | 另一种访问模式需要不同的排序顺序或受支持的预计算表示形式。 | 存储和插入开销、现有数据的物化，以及与查询和 ClickHouse 版本的兼容性。           |

检查查询是否使用了预期的投影。验证物化视图的聚合和更新语义。参见[物化视图与投影对比](/zh/concepts/features/projections/materialized-views-versus-projections)和[历史数据回填](/zh/guides/clickhouse/data-modelling/backfilling)。

### 减少连接与扫描开销 {#reduce-join-and-scan-work}

在更新模型允许的情况下，对频繁访问的属性进行反规范化。对于键值查找，可考虑使用字典，但需保留重复键和变化维度所要求的行为。

对于仍需保留的连接，请检查执行计划和输入基数。较新的 ClickHouse 版本可以对连接重新排序，因此应检查实际的构建侧，而不要仅依赖 SQL 中的书写顺序。先使用默认算法；当内存或执行时间暴露出具体问题时，再测试其他算法。注意，不同算法支持的连接类型有所不同。

只查询所需的列。应用选择性高的筛选条件，并检查 `PREWHERE` 和主索引裁剪是否减少了读取量。只有当数据分布和谓词能让跳过索引跳过足够多的粒度，足以抵消其存储和评估开销时，才添加跳过索引。

参见[最小化并优化连接](/zh/concepts/best-practices/minimize-optimize-joins)、[数据跳过索引](/zh/concepts/best-practices/using-data-skipping-indices)和[查询优化](/zh/guides/clickhouse/performance-and-monitoring/query-optimization)。

## 优化摄取与数据保留 {#optimize-ingestion-and-retention}

小批量、高频率的插入操作生成 parts 的速度可能超过合并的速度。建议优先在客户端组织批次，或使用[异步插入](/zh/concepts/features/operations/insert/asyncinserts)。请根据行大小、吞吐量和数据新鲜度要求确定批次大小，并持续监控活跃 parts 数量和合并活动。

请检查实际生效的设置，不要想当然地认为使用的是默认值：

```sql
SELECT name, value, changed
FROM system.settings
WHERE name IN
(
    'async_insert',
    'wait_for_async_insert',
    'async_insert_max_data_size',
    'async_insert_busy_timeout_ms'
);
```

使用异步插入时，请保持 `wait_for_async_insert = 1`，这样确认会等到刷写完成后才返回，客户端也能收到刷写错误。若设置为 `0`，确认仅表示数据已写入缓冲区；客户端收到成功响应后仍可能发生错误。

对于第三方摄取工具，请对批处理、重试、去重、错误处理和背压机制进行端到端验证。请核实连接器的投递保证，不要想当然地认为重试不会产生重复数据。参见[选择插入策略](/zh/concepts/best-practices/selecting-an-insert-strategy)。

避免频繁执行大型变更，也不要将 `OPTIMIZE TABLE ... FINAL` 作为例行操作：二者都可能带来大量重写和合并开销。请选择满足查询正确性要求的更新策略。对于受支持的保留策略，请使用 `TTL`；需要删除整个分区时，请使用分区级删除。Cloud 不使用 `TTL ... TO VOLUME` 实现存储分层。

参见[避免变更](/zh/concepts/best-practices/avoid-mutations)、[避免使用 optimize final](/zh/concepts/best-practices/avoid-optimize-final) 以及[使用生存时间 (TTL) 管理数据](/zh/concepts/features/operations/delete/ttl)。

## 规划 Cloud 资源 {#plan-cloud-resources}

### 考虑缓存状态 {#account-for-cache-state}

ClickHouse Cloud 将计算资源与对象存储分离，缓存状态可能会显著影响延迟。即使已禁用查询结果缓存，重复执行的查询仍可能读取已缓存的数据。

请分别测量首次运行和重复运行时的表现，并记录可能影响对比结果的服务空闲、规格调整、路由以及后台活动。请结合所需的启动延迟来评估是否使用[自动空闲](/zh/products/cloud/features/autoscaling/idling)。

在增加资源之前，先通过裁剪和预聚合来缩小工作集。如果确有必要进行预热，请使用具有代表性的查询，并将其资源消耗计入成本评估。

查询结果缓存不同于数据缓存。仅当应用程序对数据新鲜度的要求允许使用已缓存的结果时，才应启用查询结果缓存。参见[缓存](/zh/concepts/features/performance/caches/caches)和[查询缓存](/zh/concepts/features/performance/caches/query-cache)。

### 根据实测工作负载进行资源规模规划 {#size-for-the-measured-workload}

应综合评估 CPU、内存、并发度和摄取情况。除了单独测试各个查询，还应测试峰值负载。在单查询场景下能达到目标的服务，在查询并发且同时进行摄取时可能无法达到该目标。

垂直扩缩容调整的是每个副本的资源，横向扩缩容调整的是副本数量。可用性和自动化能力取决于层级和 profile。请参阅[扩缩容概览](/zh/products/cloud/features/autoscaling/overview)和[服务限制](/zh/products/cloud/guides/best-practices/usagelimits)，而不要按原有系统内存的固定比率来规划资源规模。

请根据工作负载和预算设置合适的扩缩容范围。应衡量总体资源消耗：即使查询速度更快，如果其占用的计算资源明显增多，成本仍可能更高。

### 隔离相互竞争的工作负载 {#isolate-competing-workloads}

当摄取、交互式查询和批次数据分析需要专用计算资源时，请使用[仓库](/zh/products/cloud/features/infrastructure/warehouses)。同一仓库中的各个服务共享数据，同时各自拥有独立的计算资源和端点。

将应用程序和第三方工具路由到对应的目标服务。在实际负载下验证并发度、连接池、超时和重试。同时测量被隔离的工作负载和生产环境工作负载，以确认隔离效果符合预期目标。

## 对结果进行基准测试 {#benchmark-the-result}

1. **保存基线。** 记录 ClickHouse 版本、服务配置、表定义、设置、数据量，以及带有代表性参数的查询文本。
2. **控制工作负载。** 保持数据和并发度可比。记录摄取、合并以及后台活动。测量应用程序延迟时，应将客户端和网络路径一并纳入。
3. **区分缓存场景。** 分别报告首次运行和重复运行的结果。测量执行层面的改进时，请禁用查询结果缓存，但仍需考虑数据缓存的影响。不要为了基准测试而清除共享的生产环境缓存。
4. **每次只改变一个因素。** 明确提出假设，例如通过更改排序键来减少读取的粒度。
5. **重复测量。** 运行足够多的次数，以刻画结果的波动情况。报告分布或百分位数并注明运行次数，而不是只报告最快的一次执行。
6. **检查正确性与权衡。** 比较结果、数据新鲜度、插入吞吐量、内存、存储以及资源消耗。如有必要，还应计入历史数据回填和物化的成本。
7. **在具有代表性的负载下进行验证。** 滚动发布前重新测试并发度和摄取，并准备好回滚方案。

与客户或合作伙伴共享结论时，请提供数据集或可复现的生成方法、确切的查询、配置以及测量步骤。同时说明适用范围：在某一工作负载上取得的加速并不代表通用的性能保证。

如需可复现的起点，请参阅[查询优化完整示例](/zh/guides/clickhouse/performance-and-monitoring/query-optimization-example)。

## 部署检查清单 {#deployment-checklist}

* 明确延迟、吞吐量、数据新鲜度和可用性目标。
* 验证引擎在更新和重复数据方面的语义与正确性。
* 使用具有代表性的筛选条件测试排序键，并检查裁剪效果。
* 检查数据类型、分区数量、part 大小和保留期限。
* 评估插入批处理、重试行为和合并压力。
* 核实视图、投影和索引带来的收益及其维护成本。
* 测试缓存行为、峰值并发度以及相互争用资源的工作负载。
* 配置扩缩容边界，并将集成路由到相应的端点。
* 记录可复现的基线、监控标准和回滚流程。

## 获取帮助 {#get-help}

如果仍无法确定瓶颈所在，请联系 [ClickHouse 支持团队](https://clickhouse.cloud/support)。联系时请提供查询及查询 ID、表定义、`EXPLAIN indexes = 1` 的输出、时间范围、服务配置以及明确的优化目标。如有可能，请一并提供具有代表性的样本或复现步骤，并事先移除其中的敏感数据。
