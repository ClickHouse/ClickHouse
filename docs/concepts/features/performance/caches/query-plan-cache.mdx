The query plan cache stores the *query plan* of a `SELECT` query so that repeated executions of the same query skip query
analysis and logical planning. The query is still parsed on every execution (the cache key is built from the parsed AST), but the
expensive analysis and planning steps are reused. Unlike the [query cache](/concepts/features/performance/caches/query-cache), which stores query *results*, a query plan cache hit still
executes the query against current data: the cached plan's table reads are storage-agnostic placeholders that are re-bound to fresh data
snapshots on every execution. The plan cache is therefore transactionally consistent and suitable for workloads where the same
analysis-heavy query runs repeatedly over changing data — for example dashboards over deeply nested views. The only exception
is scalar subqueries when caching them is explicitly enabled with `query_plan_cache_allow_scalar_subqueries`: their values are
computed during planning and baked into the cached plan as constants, so a hit reuses them without re-reading the underlying
tables (see [Eligibility](#eligibility)).

The feature is experimental:

```sql
SET allow_experimental_query_plan_cache = 1, enable_query_plan_cache = 1;
```

## Eligibility {#eligibility}

A `SELECT` query can use the plan cache when all of the following hold:

- The query is a top-level `SELECT` (possibly with `UNION`), run with the analyzer (`enable_analyzer = 1`) and without parallel replicas. The plan cache is disabled for the whole session when `allow_experimental_parallel_reading_from_replicas` is nonzero, including for a local query that would not otherwise use parallel replicas.
- Queries over **views, joins, subqueries and `IN` subqueries are supported**: ordinary views are inlined into the cached plan, and
  subquery/`IN`-set sub-plans re-execute on every run. A materialized view is not inlined: the cached plan reads it like a table,
  through its target table, exactly as a query without the cache does.
- The query contains no non-deterministic functions (e.g. `now`, `rand`), including inside expanded view bodies. Queries calling
  SQL user-defined functions (created with `CREATE FUNCTION`) directly are not cached, because the cache key does not include the
  function body, so `CREATE OR REPLACE FUNCTION` could otherwise leave a stale plan under the same key. Queries calling
  executable or WebAssembly user-defined functions (directly or from a row policy) are not cached even when such a function is declared
  deterministic, because a cache hit rebuilds functions through the built-in function factory only. A query reading a table whose
  applicable row policy calls a non-deterministic function (e.g. `today`, `currentUser`) is not cached either. A query reading a
  table whose applicable row policy calls a SQL user-defined function is not cached either: the function body is inlined into the
  filter while the plan is built, and a concurrent `CREATE OR REPLACE FUNCTION` could leave the plan with a body the cache cannot detect.
  A query reading a table with a constraint that calls such a function (e.g. `getSetting`) is not cached either: the constraint-based
  optimizations (`optimize_using_constraints`, ...) fold the constraint into the plan.
- The query contains no call of a function that checks access rights while the query is analyzed (introspection functions such as
  `demangle`, dictionary functions, AI functions, `joinGet`, `getMacro`, ...), including inside expanded view bodies, row policies and
  `ALIAS` columns of tables read inside expanded view bodies. Such a call with constant arguments is folded into a constant, and a cache hit
  could not repeat the access check.
- Only the `SETTINGS` clause of the top-level `SELECT` (of the last `SELECT` of a top-level `UNION`) is allowed. A query with a `SETTINGS`
  clause in a subquery, in another `SELECT` of a `UNION`, or in the body of an expanded view is not cached, because the cached plan cannot
  preserve the settings scoped to that part of the query.
- The query is run without the `additional_table_filters` and `additional_result_filter` settings.
- The session has no temporary tables: a temporary table can shadow a table of the same name, which the cache key does not account for.
- `join_algorithm` is not set to `direct` alone: the cached plan does not prepare the key-value lookups of a direct join.
- All referenced storages are local, non-temporary tables or views (no table functions, no `system` tables except `system.one`,
  no `Merge`/`Distributed`/`Alias` storages), in databases that assign table UUIDs (e.g. `Atomic`; tables in `Ordinary` or `Lazy` databases
  are not cached, because the plan cannot be bound to the analyzed table identity). Among ordinary views, only `SQL SECURITY INVOKER` views (or views without a `SQL SECURITY` clause) are eligible;
  `SQL SECURITY DEFINER` and `SQL SECURITY NONE` views are not cached. A materialized view cannot be `INVOKER`, so it is eligible only
  when it has no `SQL SECURITY` clause (the default with `ignore_empty_sql_security_in_create_view_query = 1`). A read through an `Alias` table is not cached either,
  because the plan bakes in the combined row policies of the alias and its target while only the alias is fingerprinted as a dependency.
- Scalar subqueries (e.g. `(SELECT max(x) FROM t)`) are evaluated once during analysis and baked into the plan as constants. By default
  such queries are not cached; set `query_plan_cache_allow_scalar_subqueries = 1` to cache them when the tables referenced by scalar
  subqueries are static or stale scalar values are acceptable. A scalar subquery reading a `MaterializedView`, `Buffer` or `Dictionary` table
  is never cached, because these engines check access to another object (the source or destination table, the underlying dictionary) while
  reading, which a cache hit could not repeat.
- Streaming reads (`FROM t STREAM ...`) are not cached.

Plans containing a step that does not support serialization are executed normally and simply not cached.

## Invalidation {#invalidation}

Every cache hit revalidates the plan's dependencies before execution. The cached entry is discarded and the query re-planned when any
referenced storage (base table or view, including nested views) was dropped, re-created, or altered (schema change, view body change via
`CREATE OR REPLACE VIEW`), or when an applicable row policy changed. The cache key includes the user, the active roles, the current
database, and a hash of all plan-affecting settings, so plans are never shared across users or incompatible settings. `SELECT` access to
all dependencies is re-checked on every hit.

A view is expanded into the cached plan, and a scalar subquery is folded into a constant, so neither leaves a plan node from which the exact
columns it contributes can be recovered. A hit therefore requires table-level `SELECT` on a view and on every table referenced from a scalar
subquery - even when the same table is also read directly elsewhere in the query, as in `SELECT a, (SELECT sum(b) FROM t) FROM t`.
This is at least as strict as the per-column access a non-cached query checks. As a consequence, a query that a column-level grant on a view
alone makes runnable without the cache is still allowed, but it is neither stored in nor served from the cache - it is re-planned on every
execution; grant table-level `SELECT` on the view to make it cacheable. A materialized view is not expanded - it is read like an ordinary table, from its target table - so its exact columns are known
and a hit re-checks them at the column level, exactly as a non-cached query does.

## Configuration {#configuration}

Server configuration:

```xml
<query_plan_cache>
    <max_size_in_bytes>536870912</max_size_in_bytes>
    <max_entries>1024</max_entries>
</query_plan_cache>
```

Setting either `max_size_in_bytes` or `max_entries` to `0` disables the cache completely: eligible queries then take the normal
planning path, exactly as if `enable_query_plan_cache` were unset.

Per-user quota: `query_plan_cache_size_in_bytes_quota` (0 = no quota). The cache can be cleared with:

```sql
SYSTEM DROP QUERY PLAN CACHE;
```

Monitoring: events `QueryPlanCacheHits`, `QueryPlanCacheMisses`, `QueryPlanCacheValidationMisses`, `QueryPlanCacheStaleMisses` in
[system.events](/operations/system-tables/events) and per query in `system.query_log.ProfileEvents`; metrics `QueryPlanCacheBytes`,
`QueryPlanCacheEntries` in [system.metrics](/operations/system-tables/metrics).
