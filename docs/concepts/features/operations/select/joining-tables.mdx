ClickHouse supports a wide selection of JOIN algorithms that trade execution speed for memory use. For JOIN syntax and semantics, see the [`JOIN` clause reference](/reference/statements/select/join). For prescriptive optimization guidance and worked examples, see [Minimize and optimize JOINs](/concepts/best-practices/minimize-optimize-joins).

This page describes the JOIN types and strictness values, how ClickHouse executes a JOIN, how each JOIN algorithm works, and the settings that select an algorithm and limit its memory use.

## JOIN types and strictness {#join-types-and-strictness}

Every JOIN has a type and a strictness. The type determines which rows without a match are included in the result. The strictness determines how many matches are returned for each row. Which algorithms can execute a JOIN depends on both. For the complete syntax and the additional `SEMI`, `ANTI`, `CROSS`, and `PASTE` JOINs, see the [`JOIN` clause reference](/reference/statements/select/join#supported-types-of-join).

### `INNER JOIN` {#inner-join}

<Image img="/images/guides/join-algorithms/inner-join.png" size="sm" alt="Venn diagram of an INNER JOIN: only the intersection of left and right table rows with matching JOIN keys is returned, as the Cartesian product of the matching rows"/>

An `INNER JOIN` returns, for each pair of rows with matching JOIN keys, the columns of the left-hand row combined with the columns of the right-hand row. If a row has more than one match, all matches are returned, so the result contains the Cartesian product of the rows with the same key. The `INNER` keyword can be omitted.

### `LEFT`, `RIGHT`, and `FULL OUTER JOIN` {#outer-join}

<Image img="/images/guides/join-algorithms/outer-join.png" size="lg" alt="Venn diagrams of LEFT, RIGHT, and FULL OUTER JOIN: each returns the Cartesian product of matching rows, plus the non-matching rows of the left table, the right table, or both tables"/>

An outer JOIN returns the same rows as an `INNER JOIN` and also returns rows without a match:

- A `LEFT OUTER JOIN` also returns each left-hand row without a match, with default values in the columns of the right-hand table.
- A `RIGHT OUTER JOIN` also returns each right-hand row without a match, with default values in the columns of the left-hand table.
- A `FULL OUTER JOIN` returns the rows without a match from both tables.

The [`join_use_nulls`](/reference/settings/session-settings/join#join_use_nulls) setting makes ClickHouse return `NULL` instead of default values. The `OUTER` keyword can be omitted.

### `ALL` and `ANY` strictness {#all-and-any-strictness}

<Image img="/images/guides/join-algorithms/any-join.png" size="lg" alt="Venn diagrams of LEFT, RIGHT, and INNER ANY JOIN: each returns matching rows without a Cartesian product, plus the non-matching rows of the left table or the right table for LEFT and RIGHT"/>

With `ALL` strictness, a JOIN returns every match, as described for the JOIN types above. With `ANY` strictness, a JOIN returns at most one match for each row and does not produce a Cartesian product:

- A `LEFT ANY JOIN` returns each left-hand row once, combined with one matching right-hand row or with default values.
- A `RIGHT ANY JOIN` returns each right-hand row once, combined with one matching left-hand row or with default values.
- An `INNER ANY JOIN` returns only rows with a match and uses each row of either table at most once.

Which of several matching rows `ANY` returns is not defined. The [`join_any_take_last_row`](/reference/settings/session-settings/join#join_any_take_last_row) setting changes which row is taken. `ANY FULL` JOINs are not supported. When a query does not specify a strictness, the [`join_default_strictness`](/reference/settings/session-settings/join#join_default_strictness) setting applies.

The following query shows a `LEFT ANY JOIN`. The right-hand table contains two rows for each of the keys `2` and `3`:

```sql
WITH
    left_table AS (SELECT * FROM VALUES('c UInt32', 1, 2, 3)),
    right_table AS (SELECT * FROM VALUES('c UInt32', 2, 2, 3, 3, 4))
SELECT
    l.c AS l_c,
    r.c AS r_c
FROM left_table AS l
LEFT ANY JOIN right_table AS r ON l.c = r.c;
```

```response
┌─l_c─┬─r_c─┐
│   1 │   0 │
│   2 │   2 │
│   3 │   3 │
└─────┴─────┘
```

With `ALL` strictness, the same query returns five rows, because the keys `2` and `3` each match two right-hand rows. With `INNER ANY JOIN`, it returns only the rows for the keys `2` and `3`.

### `ASOF JOIN` {#asof-join}

<Image img="/images/guides/join-algorithms/asof-join.png" size="sm" alt="Venn diagram of an ASOF JOIN: rows with non-exactly matching JOIN keys are joined, returning the closest match for each row without a Cartesian product"/>

An `ASOF JOIN` joins rows that have no exact match. In ClickHouse, `ASOF` is a strictness that is combined with an `INNER` or `LEFT` JOIN. The `ON` clause contains equality conditions and exactly one closest-match condition that uses `>`, `>=`, `<`, or `<=`. For each left-hand row, ClickHouse selects, among the right-hand rows that satisfy the equality conditions, the row that is closest according to the closest-match condition. Each left-hand row is joined with at most one right-hand row.

`ASOF JOIN` is typically used for time series. The following query joins each trade with the most recent quote for the same symbol at or before the trade time:

```sql
WITH
    trades AS (SELECT * FROM VALUES('symbol String, volume UInt32, time DateTime',
        ('ABC', 200, '2023-02-22 14:09:05'),
        ('ABC', 300, '2023-02-22 14:09:28'))),
    quotes AS (SELECT * FROM VALUES('symbol String, time DateTime, price Decimal(10, 2)',
        ('ABC', '2023-02-22 14:09:00', 32.11),
        ('ABC', '2023-02-22 14:09:10', 32.12),
        ('ABC', '2023-02-22 14:09:20', 32.15),
        ('ABC', '2023-02-22 14:09:30', 32.20)))
SELECT
    t.symbol,
    t.volume,
    t.time AS trade_time,
    q.time AS closest_quote_time,
    q.price AS quote_price,
    t.volume * q.price AS final_price
FROM trades AS t
ASOF LEFT JOIN quotes AS q ON t.symbol = q.symbol AND t.time >= q.time
ORDER BY trade_time;
```

```response
┌─symbol─┬─volume─┬──────────trade_time─┬──closest_quote_time─┬─quote_price─┬─final_price─┐
│ ABC    │    200 │ 2023-02-22 14:09:05 │ 2023-02-22 14:09:00 │       32.11 │        6422 │
│ ABC    │    300 │ 2023-02-22 14:09:28 │ 2023-02-22 14:09:20 │       32.15 │        9645 │
└────────┴────────┴─────────────────────┴─────────────────────┴─────────────┴─────────────┘
```

The trade at `14:09:05` is joined with the quote at `14:09:00`, and the trade at `14:09:28` is joined with the quote at `14:09:20`. The quotes at `14:09:10` and `14:09:30` are not the closest earlier quote for any trade.

For the column types that the closest-match column supports and the `USING` syntax, see [ASOF JOIN usage](/reference/statements/select/join#asof-join-usage).

## How a JOIN executes {#how-a-join-executes}

Most JOIN algorithms execute in two phases:

- **Build phase.** ClickHouse reads one input completely and stores it in a data structure that supports matching, such as a hash table or a set of sorted blocks. This input is the build side.
- **Probe phase.** ClickHouse streams the other input block by block and matches each row against the data structure from the build phase. This input is the probe side.

The probe phase starts only after the build phase finishes. The memory that a JOIN needs is therefore determined mostly by the size of the build side.

By default, the right-hand side of the JOIN is the build side, and the left-hand side is the probe side. Some algorithms differ from this model. The `direct` algorithm has no build phase, because the right-hand side already exists as a key-value structure. The `full_sorting_merge` algorithm sorts both inputs and merges them. The `ie_join` algorithm accumulates both inputs before it joins them.

### Query planner behavior {#query-planner-behavior}

The query planner can change the inputs of a JOIN before an algorithm runs. The following optimizations apply.

#### Automatic build-side selection {#automatic-build-side-selection}

Since version 24.12, the planner can swap the two inputs of a JOIN so that the smaller input becomes the build side. It compares the estimated row counts of both inputs and swaps them for a hash-based JOIN when the left input is estimated to be smaller. The [`query_plan_join_swap_table`](/reference/settings/session-settings/query-plan#query_plan_join_swap_table) setting controls this behavior.

When the inputs are swapped, a `LEFT` JOIN is executed as a `RIGHT` JOIN, and the reverse. The swapped order is visible in `EXPLAIN` output.

#### Multi-table JOIN reordering {#multi-table-join-reordering}

For a query that joins several tables in the same subquery, the planner can change the order in which the tables are joined. The [`query_plan_optimize_join_order_limit`](/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_limit) setting sets the maximum number of tables that the planner reorders. The default value is `10`. The value `1` disables reordering.

#### Use of column statistics {#use-of-column-statistics}

Build-side selection and JOIN reordering depend on row-count estimates. Without column statistics, the planner derives estimates from the primary index, and these estimates can be imprecise. With [column statistics](/reference/engines/table-engines/mergetree-family/mergetree#column-statistics), the planner uses statistics to estimate the selectivity of filters and the cardinality of JOIN keys.

The [`use_statistics`](/reference/settings/session-settings/use-statistics#use_statistics) setting controls whether the optimizer uses statistics. The [`materialize_statistics_on_insert`](/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert) setting controls whether statistics are built for newly inserted data.

#### Filter pushdown {#filter-pushdown}

When [`query_plan_filter_push_down`](/reference/settings/session-settings/query-plan#query_plan_filter_push_down) is enabled, the planner moves `WHERE` conditions below the JOIN so that each input is filtered before the build and probe phases.

- A condition that references columns of only one input is applied to that input.
- For a `LEFT` JOIN, conditions are not pushed to the right input. For a `RIGHT` JOIN, conditions are not pushed to the left input.
- A condition on a JOIN key of one input can also be applied to the other input, because the key columns of both inputs are equal for every matched row.
- Conditions are not pushed into a right-hand side that is already filled, such as a dictionary, or into the right-hand side of an `ASOF` JOIN.

## JOIN algorithms {#join-algorithms}

This section describes each value of [`join_algorithm`](/reference/settings/session-settings/join#join_algorithm) that executes a JOIN, and the block nested loop fallback. The diagrams use `max_threads = 2` to keep the illustrations readable.

### `direct` {#direct}

<Image img="/images/guides/join-algorithms/direct-join.png" size="lg" alt="Direct JOIN pipeline: two parallel streams read the left table, and two join stages look up each row in a dictionary that backs the right table, with no build phase"/>

The `direct` algorithm performs a lookup in the right-hand side for each row of the left-hand side. The right-hand side must be a storage that supports low-latency key-value lookups. ClickHouse streams the left-hand side in parallel and joins each block by looking up its keys in that storage. There is no build phase, because the data of the right-hand side is already stored in a key-value structure.

The following right-hand sides qualify:

- [Dictionaries](/concepts/features/dictionaries), except dictionaries with a range key.
- Tables with the [`EmbeddedRocksDB`](/reference/engines/table-engines/integrations/embedded-rocksdb), [`KeeperMap`](/reference/engines/table-engines/special/keepermap), or [`Redis`](/reference/engines/table-engines/integrations/redis) engine.
- `MergeTree` tables, since 25.12, only when `join_algorithm` is set to `direct` as the single value. ClickHouse pushes the JOIN key filter of each left-hand block into a read of the right-hand table. This is efficient when the key can use the primary key index of the right-hand table. Otherwise, ClickHouse scans the right-hand table for each block of the left-hand side.

A right-hand side that uses the [`Join` table engine](/reference/engines/table-engines/special/join) is also read from a prepared in-memory structure without a build phase. This case does not depend on `join_algorithm`: ClickHouse always uses the hash table that the `Join` table stores, and `EXPLAIN` reports it as `FilledJoin` with `Algorithm: HashJoin`. In ClickHouse Cloud, the `Join` table engine is implemented as `SharedJoin` with a `MergeTree` backing table.

The `direct` algorithm is used when all of the following conditions are met:

- The JOIN is an `INNER` JOIN with `ALL` strictness, or a `LEFT` JOIN with `ALL`, `ANY`, `SEMI`, or `ANTI` strictness. For `MergeTree` tables, `ANY` strictness is not supported.
- The `ON` clause contains exactly one equality condition between one column of each side and no other conditions.
- The right-hand column is the single-column key of the storage, and its type matches the key type, ignoring `Nullable` and `LowCardinality`.

If any condition is not met, ClickHouse tries the next algorithm in `join_algorithm`.

**Memory and spilling.** The query does not build a data structure for the right-hand side. The memory that holds a dictionary is accounted to the dictionary, not to the query, and is reported in the `bytes_allocated` column of [`system.dictionaries`](/reference/system-tables/dictionaries). The algorithm does not spill to disk.

**Limitations.** The algorithm supports only a single equality key and does not support `RIGHT`, `FULL`, or `ASOF` JOINs. Filters are not pushed down into the right-hand side.

### `hash` {#hash}

<Image img="/images/guides/join-algorithms/hash-join.png" size="lg" alt="Hash JOIN pipeline: two streams read the right table into a single in-memory hash table, then two parallel streams read the left table and join each row by a lookup in that hash table"/>

The `hash` algorithm reads the complete right-hand side into memory and builds an in-memory hash table from it. It then streams the left-hand side in parallel and joins each row by looking up its key in the hash table. ClickHouse chooses the hash table implementation from the types of the JOIN key columns and the JOIN strictness.

For `INNER`, `LEFT`, `RIGHT`, and `FULL` JOINs, [`parallel_hash_join_threshold`](/reference/settings/session-settings/parallel#parallel_hash_join_threshold) decides how the hash table is built. If the right-hand side is estimated to have fewer rows than the threshold, a single thread fills one hash table, as in the diagram above. At or above the threshold, ClickHouse splits the hash table into parts that up to [`max_threads`](/reference/settings/session-settings/max-threads#max_threads) threads fill concurrently, as shown for [`parallel_hash`](#parallel-hash). Without an estimate, the hash table is split too, unless the threshold is set to its largest value, `18446744073709551615`. A right-hand side with a special storage, such as a dictionary, always gets one hash table filled by a single thread.

**When it is used.** The `hash` algorithm is the most general implementation. It supports every combination of JOIN type and strictness that ClickHouse implements, with `ASOF` limited to `INNER` and `LEFT` JOINs. It is the only algorithm that supports multiple JOIN keys combined with `OR` in the `ON` clause. The `auto` value supports such JOINs because it executes them with `hash`. Together with `parallel_hash` and `grace_hash`, it also supports conditions that compare columns of both tables in addition to an equality key.

**Memory and spilling.** The hash table and the rows of the right-hand side must fit into memory. Memory use can exceed the uncompressed size of the right-hand side, because the hash table is resized in steps and is not always full. When a spill threshold is set, the JOIN starts in memory and switches to the `grace_hash` algorithm once the right-hand side exceeds the threshold. See [Memory limits and spilling to disk](#memory-limits-and-spilling-to-disk).

**Limitations.** When the hash table is not split, the build phase runs in a single thread. It can dominate the query time when the right-hand side is much larger than its estimate.

### `parallel_hash` {#parallel-hash}

<Image img="/images/guides/join-algorithms/parallel-hash-join.png" size="lg" alt="Parallel hash JOIN pipeline: rows of the right table are split into two buckets by a hash of the JOIN key, and two hash tables are filled concurrently; rows of the left table are routed to the matching hash table by the same hash function"/>

`parallel_hash` is an obsolete alias of `hash`, kept for compatibility. Listing it in `join_algorithm` does not change how the hash table is built: [`parallel_hash_join_threshold`](/reference/settings/session-settings/parallel#parallel_hash_join_threshold) decides that for both values. To split the hash table whenever the JOIN type allows it, set the threshold to `0`. To always keep one hash table, set it to `18446744073709551615`.

The diagram shows how `hash` builds a split hash table. ClickHouse assigns the rows of the right-hand side to parts by a hash of the JOIN key, and up to [`max_threads`](/reference/settings/session-settings/max-threads#max_threads) threads fill the parts concurrently. During the probe phase, the same hash function routes each row of the left-hand side to the part that can contain its matches.

### `grace_hash` {#grace-hash}

<Image img="/images/guides/join-algorithms/grace-hash-join.png" size="lg" alt="Grace hash JOIN first phase with grace_hash_join_initial_buckets = 3: rows of both tables are split into buckets by a hash of the JOIN key; the first bucket is joined in memory, and the other buckets of both tables are delayed to temporary storage"/>

The `grace_hash` algorithm is a hash JOIN that does not require the right-hand side to fit into memory. It runs in two phases:

1. ClickHouse splits the rows of the right-hand side into buckets by a hash of the JOIN key. It builds an in-memory hash table for the first bucket and writes the other buckets to temporary storage. It splits the left-hand side with the same hash function, joins the rows of the first bucket immediately, and writes the other rows to temporary storage.
2. ClickHouse processes the remaining buckets one at a time. For each bucket, it builds a hash table from the right-hand rows and joins the left-hand rows of the same bucket.

The initial number of buckets is [`grace_hash_join_initial_buckets`](/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets), rounded up to a power of two. If the in-memory hash table exceeds the spill threshold, ClickHouse doubles the number of buckets and moves the rows that no longer belong to the current bucket. The number of buckets cannot exceed [`grace_hash_join_max_buckets`](/reference/settings/session-settings/grace-hash#grace_hash_join_max_buckets).

**When it is used.** The `hash` and `parallel_hash` algorithms switch to `grace_hash` automatically when the right-hand side exceeds the spill threshold. Selecting `grace_hash` explicitly makes the JOIN partition the right-hand side from the first block, without an in-memory phase. The algorithm supports `INNER`, `LEFT`, `RIGHT`, and `FULL` JOINs with `ALL`, `ANY`, `SEMI`, and `ANTI` strictness.

**Memory and spilling.** Memory use is bounded by the spill threshold. A larger initial number of buckets reduces memory use and increases execution time. The algorithm requires a non-zero spill threshold and configured temporary storage. Without a threshold, ClickHouse skips `grace_hash` when other algorithms are listed in `join_algorithm`, and rejects the query when `grace_hash` is the only value.

**Limitations.** It does not support `ASOF` JOINs or multiple JOIN keys combined with `OR`. Reading and writing temporary files makes it slower than an in-memory hash JOIN.

### `full_sorting_merge` {#full-sorting-merge}

<Image img="/images/guides/join-algorithms/full-sorting-merge-join.png" size="lg" alt="Full sorting merge JOIN pipeline: blocks of both tables are sorted by the JOIN key in parallel and can be spilled to temporary storage; one merge sort stream per table feeds a single merge join stage"/>

The `full_sorting_merge` algorithm is a sort-merge JOIN. ClickHouse sorts both inputs by the JOIN key and identifies matches by an interleaved scan of the two sorted streams. Sorting runs in memory or, for large inputs, as an external sort on disk. If an input is read in the order of the JOIN key, for example because the key is a prefix of the sorting key of a `MergeTree` table, ClickHouse skips the sort for that input.

**When it is used.** It is appropriate when one or both tables are physically ordered by the JOIN key, or when the inputs are too large for an in-memory hash table. It supports `INNER`, `LEFT`, `RIGHT`, and `FULL` JOINs with `ALL` strictness, `INNER`, `LEFT`, and `RIGHT` JOINs with `ANY` strictness, and `INNER` and `LEFT` JOINs with `ASOF` strictness.

The merge stage runs in a single stream. Two options parallelize it:

- [`query_plan_join_shard_by_pk_ranges`](/reference/settings/session-settings/query-plan#query_plan_join_shard_by_pk_ranges) splits a JOIN of two `MergeTree` tables into independent merge JOINs over primary-key ranges when the JOIN keys contain a prefix of the primary key of both tables.
- The `parallel_full_sorting_merge` value of [`join_algorithm`](/reference/settings/session-settings/join#join_algorithm) shards the inputs by a hash of the JOIN key and runs one merge JOIN per shard. The result is not ordered. The setting reference lists the cases in which a single `full_sorting_merge` JOIN runs instead.

The [`max_rows_in_set_to_optimize_join`](/reference/settings/session-settings/max-rows#max_rows_in_set_to_optimize_join) setting can filter each input by the set of JOIN keys of the other input before sorting. This filter prevents the read-in-order optimization.

**Memory and spilling.** Memory use is determined by the sort. When both inputs are read in key order, only a few blocks are in memory at a time. Otherwise, the sort spills to disk according to [`max_bytes_before_external_sort`](/reference/settings/session-settings/max-bytes#max_bytes_before_external_sort) and [`max_bytes_ratio_before_external_sort`](/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_sort).

**Limitations.** It does not support `SEMI` or `ANTI` strictness, multiple JOIN keys combined with `OR`, conditions in the `ON` clause other than equality keys, a right-hand side with a special storage, or `USING` together with `join_use_nulls`. Listing it in `join_algorithm` changes query planning even when another algorithm executes the JOIN. See [`join_algorithm`](/reference/settings/session-settings/join#join_algorithm).

### `partial_merge` {#partial-merge}

<Image img="/images/guides/join-algorithms/partial-merge-join.png" size="lg" alt="Partial merge JOIN pipeline: blocks of the right table are sorted and written to temporary storage together with a min-max index per block; blocks of the left table are sorted in memory and joined against the stored right-hand blocks"/>

The `partial_merge` algorithm is a variant of the sort-merge JOIN in which only the right-hand side is fully sorted. ClickHouse splits the right-hand side into blocks of up to [`partial_merge_join_rows_in_right_blocks`](/reference/settings/session-settings/partial-merge#partial_merge_join_rows_in_right_blocks) rows, sorts each block by the JOIN key, and creates a min-max index for each block. It then sorts each block of the left-hand side in memory and merges it with the right-hand blocks. The min-max index skips right-hand blocks that cannot contain matches.

**When it is used.** It is designed for the lowest memory use when large tables are joined, at the cost of execution speed. It is most efficient when the physical row order of the left-hand side matches the JOIN key order, because the min-max index then skips most right-hand blocks. It is least efficient when each left-hand block contains a wide range of key values. The `auto` value of `join_algorithm` can switch to `partial_merge` at runtime. The algorithm supports `INNER`, `LEFT`, `RIGHT`, and `FULL` JOINs with `ALL` strictness, `INNER` and `LEFT` JOINs with `ANY` strictness, and `LEFT` JOINs with `SEMI` strictness.

**Memory and spilling.** ClickHouse keeps the sorted right-hand blocks in memory until [`max_rows_in_join`](/reference/settings/session-settings/max-rows#max_rows_in_join) or [`max_bytes_in_join`](/reference/settings/session-settings/max-bytes#max_bytes_in_join) is reached. If neither is set, [`default_max_bytes_in_join`](/reference/settings/session-settings/default#default_max_bytes_in_join) applies. After that, ClickHouse writes the sorted blocks and their indexes to temporary storage. [`join_on_disk_max_files_to_merge`](/reference/settings/session-settings/join#join_on_disk_max_files_to_merge) limits the number of files that are merged in parallel.

**Limitations.** `RIGHT` and `FULL` JOINs are supported only with `ALL` strictness. `ANTI` and `ASOF` strictness, multiple JOIN keys combined with `OR`, and conditions that compare columns of both tables are not supported.

### `ie_join` {#ie-join}

The `ie_join` algorithm implements the sort-based [IEJoin](https://vldb.org/pvldb/vol8/p2074-khayyat.pdf) algorithm for a JOIN whose `ON` clause contains two inequality comparisons, `<`, `<=`, `>`, or `>=`, between expressions of the joined tables. ClickHouse sorts both inputs by the expressions of the two comparisons and finds the matching pairs without comparing every pair of rows. The algorithm is available since 26.8.

**When it is used.** Its position in `join_algorithm` sets its priority:

- Listed after other algorithms, it is used only when the `ON` clause contains no equality condition between the tables.
- Listed first, it is used whenever the `ON` clause contains two inequality conditions. Other conditions, including equality conditions, are applied as a filter over the JOIN result or as a residual condition inside the operator.

When the `ON` clause contains more than two eligible inequality conditions, ClickHouse chooses the two key conditions by their estimated selectivity from column statistics. Without statistics, it uses the first two in syntax order. The algorithm supports `INNER`, `LEFT`, `RIGHT`, and `FULL` JOINs with `ALL` strictness, and `LEFT` and `RIGHT` JOINs with `SEMI` and `ANTI` strictness.

**Memory and spilling.** Both inputs are accumulated in memory before joining, and the [hard limits](#hard-limits) apply to both sides together. The algorithm does not spill to disk.

**Limitations.** The JOIN operator runs in a single thread. Only the sorts of the inputs run in parallel. `ANY` and `ASOF` strictness are not supported.

### Block nested loop fallback {#block-nested-loop-fallback}

The block nested loop JOIN executes a JOIN whose `ON` clause contains no equality condition between the tables and that no other algorithm can execute. ClickHouse materializes the right-hand side and evaluates the `ON` condition on every pair of a left-hand row and a right-hand row. It is not a value of `join_algorithm`. It is the last resort of JOIN planning.

**When it is used.** It applies to an `ON` clause that is an arbitrary boolean expression over columns of both tables, such as a range check or a function call, when `ie_join` does not apply. When `hash` is listed in `join_algorithm`, an `INNER` JOIN with `ALL` strictness is executed as a `CROSS JOIN` with the condition as a filter instead. The fallback is available since 26.10. The [`allow_block_nested_loop_join`](/reference/settings/session-settings/allow#allow_block_nested_loop_join) setting controls whether it can be used. When the fallback is not allowed, such a query is rejected with `INVALID_JOIN_ON_EXPRESSION`. It supports every JOIN type and strictness except `ASOF`, `PASTE`, and `ANY FULL`.

**Memory and spilling.** Memory is bounded by the materialized right-hand side and does not grow with the size of the result. The right-hand blocks are compressed in memory and written to disk after the spill threshold is reached. The [hard limits](#hard-limits) apply to the right-hand side, including spilled blocks.

**Limitations.** The cost grows with the product of the row counts of both tables. It is orders of magnitude more expensive than a hash JOIN on the same data. For details on strictness semantics, see [JOIN with an arbitrary ON condition](/reference/statements/select/join#join-with-an-arbitrary-on-condition).

## Supported JOIN types per algorithm {#supported-join-types-per-algorithm}

The following table lists the JOIN types that each algorithm supports for each strictness value. It is derived from the support checks in the ClickHouse source code. An empty cell means that the strictness is not supported.

| Algorithm | `ALL` | `ANY` | `SEMI` | `ANTI` | `ASOF` |
|---|---|---|---|---|---|
| `direct` | `INNER`, `LEFT` | `LEFT` | `LEFT` | `LEFT` | |
| `hash`, `parallel_hash` | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `INNER`, `LEFT` |
| `grace_hash` | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | |
| `full_sorting_merge`, `parallel_full_sorting_merge` | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | | | `INNER`, `LEFT` |
| `partial_merge` | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT` | `LEFT` | | |
| `ie_join` | `INNER`, `LEFT`, `RIGHT`, `FULL` | | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | |
| Block nested loop fallback | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | |

The following rules also apply:

- `ANY FULL` JOINs are rejected before an algorithm is selected, for every algorithm.
- `ASOF` JOINs are supported only by `hash` and `full_sorting_merge`. `parallel_full_sorting_merge` executes an `ASOF` JOIN as a single `full_sorting_merge` JOIN.
- `partial_merge` supports `RIGHT` and `FULL` JOINs only with `ALL` strictness.
- The block nested loop fallback does not support `ASOF`, `PASTE`, or `ANY FULL` JOINs.
- Only `hash` supports multiple JOIN keys combined with `OR` in the `ON` clause. The `auto` value executes such JOINs with `hash`.
- Only `hash`, `parallel_hash`, and `grace_hash` support an equality key combined with a condition that compares columns of both tables.
- The `direct` algorithm applies only to the right-hand sides listed in [`direct`](#direct). For `MergeTree` tables, it does not support `ANY` strictness.
- `CROSS JOIN`, JOINs with a constant `ON` condition, and `PASTE JOIN` have dedicated implementations that do not depend on `join_algorithm`.

## The `join_algorithm` setting {#join-algorithm-setting}

The [`join_algorithm`](/reference/settings/session-settings/join#join_algorithm) setting accepts a comma-separated list of algorithms. For the default value and all accepted values, see the [`join_algorithm`](/reference/settings/session-settings/join#join_algorithm) reference.

ClickHouse tries the listed algorithms in order and selects the first one that supports the JOIN type, the strictness, the `ON` condition, and the storage of the right-hand side. If no listed algorithm applies, the query fails with an error that lists the enabled algorithms. The following cases do not depend on the order of the list:

- A right-hand side with the `Join` table engine is always joined with the hash table that the table stores.
- `CROSS JOIN`, JOINs with a constant `ON` condition, and `PASTE JOIN` use dedicated implementations.
- An `ON` clause without an equality condition between the tables is handled by `ie_join` or by the block nested loop fallback.

When a spill threshold is in effect and temporary storage is configured, `parallel_hash` and `hash` run as a spilling hash JOIN that switches to `grace_hash` when the right-hand side exceeds the threshold. See [Spill thresholds](#spill-thresholds).

### The `auto` value {#the-auto-value}

With `join_algorithm = 'auto'`, ClickHouse selects the implementation as follows:

1. If a spill threshold is in effect, temporary storage is configured, and `grace_hash` supports the JOIN, ClickHouse uses a hash JOIN that switches to `grace_hash` when the right-hand side exceeds the threshold.
2. Otherwise, if `partial_merge` supports the JOIN, ClickHouse starts with `hash` and switches to `partial_merge` when the right-hand side reaches a [hard limit](#hard-limits). The rows that are already in the hash table are moved to the `partial_merge` JOIN.
3. Otherwise, ClickHouse uses `hash`.

In `EXPLAIN` output, the second case appears as `Algorithm: JoinSwitcher`.

## Memory limits and spilling to disk {#memory-limits-and-spilling-to-disk}

Two groups of settings control JOIN memory. For most algorithms, hard limits stop a query when the JOIN state becomes too large. Spill thresholds make a JOIN write part of its state to disk so that the query can continue.

### Hard limits {#hard-limits}

- [`max_rows_in_join`](/reference/settings/session-settings/max-rows#max_rows_in_join) limits the number of rows in the right-hand data structure of a JOIN, which is typically a hash table.
- [`max_bytes_in_join`](/reference/settings/session-settings/max-bytes#max_bytes_in_join) limits the size in bytes of the same data structure.
- [`join_overflow_mode`](/reference/settings/session-settings/join#join_overflow_mode) defines the action when either limit is reached.

Both limits also apply to the [`Join` table engine](/reference/engines/table-engines/special/join). If a query contains several JOINs, ClickHouse checks the limits for every JOIN.

For hash-based algorithms, including the algorithms that spill to disk, reaching a limit stops the query and never makes a JOIN spill. As a result, a limit at or below the spill threshold normally stops the query before the JOIN can spill.

The limits act differently for other algorithms:

- For `ie_join`, the limits apply to the accumulated input of both sides together.
- For the block nested loop fallback, the limits apply to the materialized right-hand side, including spilled blocks.
- For `partial_merge`, reaching a limit changes the execution strategy instead of stopping the query: the JOIN starts writing its sorted right-hand blocks to disk.

### Spill thresholds {#spill-thresholds}

- [`max_bytes_before_external_join`](/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) sets an absolute spill threshold in bytes for the right-hand side of a hash-based JOIN.
- [`max_bytes_ratio_before_external_join`](/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join) sets the spill threshold as a ratio of the memory that remains under the user and server memory limits. If no memory limit is configured, the ratio has no effect.

If both settings are set, the smaller resulting threshold applies. The thresholds apply to `hash`, `parallel_hash`, `grace_hash`, the `auto` value, and the block nested loop fallback. They require a configured temporary data path.

### How spilling works {#how-spilling-works}

Each algorithm that can spill writes a different part of its state to temporary files:

- **`hash` and `parallel_hash`.** The JOIN builds its hash tables in memory. When the right-hand side exceeds the spill threshold, the JOIN converts to `grace_hash`. It splits the right-hand rows into buckets by a hash of the JOIN key, keeps one bucket in memory, and writes the other buckets to temporary files. The left-hand rows are split with the same hash function. Rows of the in-memory bucket are joined immediately, and the other rows are written to temporary files. After the left-hand side is read, ClickHouse loads and joins the remaining pairs of buckets one at a time.
- **`grace_hash`.** The JOIN follows the same procedure from the first block. If the hash table of a bucket exceeds the threshold, the number of buckets doubles up to `grace_hash_join_max_buckets`. When this maximum is exceeded, the query fails with an error.
- **`full_sorting_merge`.** The sort of each input writes sorted blocks to temporary files when it exceeds `max_bytes_before_external_sort` or `max_bytes_ratio_before_external_sort`. The sorted files are then merged.
- **`partial_merge`.** The sorted right-hand blocks and their min-max indexes are written to temporary files after the right-hand side reaches a hard limit.
- **Block nested loop fallback.** The right-hand blocks are compressed in memory and then written to temporary files after the spill threshold is reached.

The `direct` and `ie_join` algorithms do not spill to disk.

Temporary files are written to the storage that the [`tmp_path`](/reference/settings/server-settings/settings/tmp#tmp_path), [`tmp_policy`](/reference/settings/server-settings/settings/tmp#tmp_policy), or [`temporary_data_in_cache`](/reference/settings/server-settings/settings/temporary-data#temporary_data_in_cache) server setting configures. Reading and writing temporary files adds disk I/O, so a spilling JOIN is slower than the same JOIN in memory.

The `ExternalJoinWritePart`, `ExternalJoinCompressedBytes`, and `ExternalJoinUncompressedBytes` profile events report how many temporary files a JOIN wrote and how much data they contained. They are available in the `ProfileEvents` column of [`system.query_log`](/reference/system-tables/query_log).
