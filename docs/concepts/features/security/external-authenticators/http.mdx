HTTP server can be used to authenticate ClickHouse users. HTTP authentication can only be used as an external authenticator for existing users, which are defined in `users.xml` or in local access control paths. Currently, [Basic](https://datatracker.ietf.org/doc/html/rfc7617) authentication scheme using GET method is supported.

## HTTP authentication server definition {#http-auth-server-definition}

To define HTTP authentication server you must add `http_authentication_servers` section to the `config.xml`.

**Example**
```xml
<clickhouse>
    <!- ... -->
    <http_authentication_servers>
        <basic_auth_server>
          <uri>http://localhost:8000/auth</uri>
          <connection_timeout_ms>1000</connection_timeout_ms>
          <receive_timeout_ms>1000</receive_timeout_ms>
          <send_timeout_ms>1000</send_timeout_ms>
          <max_tries>3</max_tries>
          <retry_initial_backoff_ms>50</retry_initial_backoff_ms>
          <retry_max_backoff_ms>1000</retry_max_backoff_ms>
          <forward_headers>
            <name>Custom-Auth-Header-1</name>
            <name>Custom-Auth-Header-2</name>
          </forward_headers>

        </basic_auth_server>
    </http_authentication_servers>
</clickhouse>

```

Note, that you can define multiple HTTP servers inside the `http_authentication_servers` section using distinct names.

**Parameters**
- `uri` - URI for making authentication request

Timeouts in milliseconds on the socket used for communicating with the server:
- `connection_timeout_ms` - Default: 1000 ms.
- `receive_timeout_ms` - Default: 1000 ms.
- `send_timeout_ms` - Default: 1000 ms.

Retry parameters:
- `max_tries` - The maximum number of attempts to make an authentication request. Default: 3
- `retry_initial_backoff_ms` - The backoff initial interval on retry. Default: 50 ms
- `retry_max_backoff_ms` - The maximum backoff interval. Default: 1000 ms

Forward headers:

The part defines which headers will be forwarded from client request headers to external HTTP authenticator. Note that headers will be matched against config ones in case-insensitive way, but forwarded as-is i.e. unmodified.

### Enabling HTTP authentication in `users.xml` {#enabling-http-auth-in-users-xml}

In order to enable HTTP authentication for the user, specify `http_authentication` section instead of `password` or similar sections in the user definition.

Parameters:
- `server` - Name of the HTTP authentication server configured in the main `config.xml` file as described previously.
- `scheme` - HTTP authentication scheme. `Basic` is only supported now. Default: Basic

Example (goes into `users.xml`):
```xml
<clickhouse>
    <!- ... -->
    <my_user>
        <!- ... -->
        <http_authentication>
            <server>basic_server</server>
            <scheme>basic</scheme>
        </http_authentication>
    </my_user>
</clickhouse>
```

<Note>
Note that HTTP authentication cannot be used alongside with any other authentication mechanism. The presence of any other sections like `password` alongside `http_authentication` will force ClickHouse to shutdown.
</Note>

### Enabling HTTP authentication using SQL {#enabling-http-auth-using-sql}

When [SQL-driven Access Control and Account Management](/concepts/features/security/access-rights#access-control-usage) is enabled in ClickHouse, users identified by HTTP authentication can also be created using SQL statements.

```sql
CREATE USER my_user IDENTIFIED WITH HTTP SERVER 'basic_server' SCHEME 'Basic'
```

...or, `Basic` is default without explicit scheme definition

```sql
CREATE USER my_user IDENTIFIED WITH HTTP SERVER 'basic_server'
```

### Passing session settings {#passing-session-settings}

If a response body from HTTP authentication server has JSON format and contains `settings` sub-object, ClickHouse will try parse its key: value pairs as string values and set them as session settings for authenticated user's current session. If parsing is failed, a response body from server will be ignored.

## HTTP user directory {#http-user-directory}

An HTTP authentication server can also serve as a user directory, similar to the `ldap` one: unlike with `IDENTIFIED WITH HTTP`, no `CREATE USER` is needed. A user that is not defined in ClickHouse authenticates with HTTP Basic against the service and is materialized as an in-memory user without any grants. The service can also return session settings and a list of roles for this login.

### Configuration {#http-user-directory-configuration}

Add an `http` section to `user_directories` in `config.xml`. It refers to a server defined in `http_authentication_servers`.

```xml
<clickhouse>
    <user_directories>
        <users_xml>
            <path>users.xml</path>
        </users_xml>
        <http>
            <server>basic_auth_server</server>
            <allowed_roles>
                <reader/>
                <writer/>
            </allowed_roles>
            <allowed_role_prefix>tenant_</allowed_role_prefix>
            <authentication_cache_ttl>30</authentication_cache_ttl>
        </http>
        <local_directory>
            <path>/var/lib/clickhouse/access/</path>
        </local_directory>
    </user_directories>
</clickhouse>
```

Parameters:
- `server` - Name of the server from `http_authentication_servers`. Required.
- `allowed_roles` - Roles the service may return. Element names are role names. Optional.
- `allowed_role_prefix` - Roles whose names start with this prefix may be returned. Optional.
- `authentication_cache_ttl` - Time in seconds to reuse a successful response. Default: `0` (disabled).

The parameters of the `http` section are read at startup, so changing them requires a restart. The parameters of the server itself (`uri`, timeouts, `forward_headers`) follow config reload. If `server` does not name an entry of `http_authentication_servers`, every authentication through the directory fails.

### Response format {#http-user-directory-response}

The service receives a GET request with Basic credentials and the configured forwarded headers.

- `200` - Success. The body is optional; if present, it must be JSON.
- `404` - The user is not known to this service. Authentication continues with the next user directory.
- Any other status (`401`, `403`, `5xx`) - Authentication fails, the next directories are not tried.

Parsing is strict: a malformed body, a body that is not a JSON object, a `roles` value that is not an array, a non-string role, or an unknown or unparsable setting fails the authentication. The `settings` are applied as [session settings](#passing-session-settings) and are subject to constraints.

```json
{"settings": {"max_threads": "4"}, "roles": ["reader", "tenant_a"]}
```

### Roles {#http-user-directory-roles}

Every returned role must exist in ClickHouse and be listed in `allowed_roles` or start with `allowed_role_prefix`. Otherwise the authentication fails. If neither is configured, any returned role is rejected.

Roles belong to the authentication, not to the user: two logins of one user name may get different roles. The roles are enabled in the session without being granted: `currentRoles` shows them, `SHOW GRANTS` does not, `SET ROLE NONE` does not remove them, and `SET ROLE` with a returned role fails.

<Note>
Anyone who can run `CREATE ROLE` can create a role with a name matching `allowed_role_prefix`, which the service may then return. Restrict `CREATE ROLE`, or prefer `allowed_roles`.
</Note>

### Authentication cache {#http-user-directory-cache}

By default (`authentication_cache_ttl` is `0`), every new authentication makes a request to the HTTP service, which is expensive for clients that open a new connection or send a separate HTTP request for every query.

With `authentication_cache_ttl` greater than zero, a successful validated response, including its roles and settings, is reused for the same user name, password, and forwarded headers until the TTL expires. There is one entry per user name, and the password and header values are kept only as a hash. `404`, rejected credentials, an invalid response, or any other failure is never cached. After the TTL expires, ClickHouse contacts the service again, and the authentication fails if the service cannot be reached. Existence and the allow-list of the roles are checked again on every hit, so changes on the ClickHouse side take effect immediately.

**Keep the TTL short.** While an entry is valid, ClickHouse does not ask the service, so a user who was disabled, whose password was revoked, or whose roles or settings were changed at the service keeps authenticating with the old result for up to the TTL. The TTL is therefore the maximum delay of a revocation for new authentications. Use 30-60 seconds when such a delay is acceptable, not hours, and keep `0` when every authentication must be verified by the service.

The TTL does not affect sessions that are already established. A native protocol connection authenticates once and keeps the roles and settings it got until it is closed, with or without the cache.

### Distributed queries {#http-user-directory-distributed}

Configure the directory and create the roles on every node. The cluster must define a `<secret>`. The initiator pushes the user and its roles to shards, which materialize the user and apply the roles without calling the service. Define the roles identically on all nodes.

### Limitations {#http-user-directory-limitations}

- Settings and settings profiles of returned roles, including their constraints such as `readonly`, are not applied at login, so a login that gets a role with settings or settings profiles (its own, of the roles granted to it, or assigned to it with `TO`) fails. Use the `settings` of the response instead. This check runs only on the node where the user authenticates, and settings of a role on a shard are not applied to the roles pushed by the initiator.
- `INSERT` into a `Distributed` table on a cluster with `<secret>`, both foreground and background, does not carry the roles to shards.
- `ON CLUSTER` queries with `distributed_ddl_use_initial_user_and_roles` fail with `UNKNOWN_USER` on hosts that have not seen the user.
- Such users should not be used as `DEFINER`, because a definer has no session roles.
- Settings returned by the service are applied when a named session (`session_id`) is created, and the session can be reused only by an authentication that returns the same roles and settings.
- Settings returned by the service are not applied to the jobs of a `QueryRunner` table.
- Materialized users stay in memory (`system.users`) until restart.
- A user name that exists in another user directory is never authenticated by this one.
- A user name containing `:` is never authenticated by this directory, because HTTP Basic credentials cannot carry it.
- With several external directories, the order in `user_directories` decides. Every login with an unknown name costs a request, so the service must answer `404` for names it does not own. List `http` after the other user directories, so that names defined elsewhere always take precedence for both authentication and name resolution (e.g. in `GRANT ... TO`): otherwise a user materialized by this directory hides a user with the same name added later to another directory until someone authenticates with that name, which drops the materialized user.
