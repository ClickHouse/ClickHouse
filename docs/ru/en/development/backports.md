В этом документе описаны политика бэкпортов ClickHouse и автоматизированная система, которая её реализует.

<div id="release-model">
  ## Модель релизов
</div>

Версии ClickHouse следуют схеме `YY.M.patch.build-type`, где `YY` — двузначный год, `M` — месяц релиза (без ведущего нуля), `patch` — номер патча в рамках ветки, `build` — монотонно возрастающий номер сборки, а `type` — либо `stable`, либо `lts`.

Пример: `25.3.8.23-lts` — LTS-релиз за март 2025 года, патч 8, сборка 23.

Существует две ветки релизов:

* **Стабильные** релизы публикуются примерно раз в месяц. Патчи выпускаются для трёх последних стабильных релизов, что даёт каждому релизу около трёх месяцев активной поддержки.
* **LTS (Long-Term Support)** релизы публикуются в марте и августе каждого года. Одновременно поддерживаются две LTS-версии, каждая не менее 12 месяцев.

Пользователям, запускающим рабочие нагрузки в продакшн, рекомендуется использовать либо последний стабильный релиз, либо LTS-релиз, и своевременно обновляться до новых версий патчей, поскольку патч-релизы не вносят обратно несовместимых изменений.

<div id="backport-policy">
  ## Политика бэкпортов
</div>

Бэкпортируются не все изменения. Цель — сохранять ветки релиза стабильными, поэтому область бэкпортов намеренно ограничена:

* **Исправления безопасности** — бэкпортируются всегда.
* **Исправления критических ошибок** (исключения (логические ошибки), потеря данных, неверные результаты, проблемы с RBAC) — автоматически отбираются для бэкпорта по общим правилам бэкпортов; определяются по метке `pr-critical-bugfix`, которая автоматически добавляет `pr-must-backport`.
* **Исправления стабильности и регрессий** — бэкпортируются, когда риск изменения ниже, чем риск оставить ошибку без исправления; определяются по метке `pr-must-backport`, которую мейнтейнеры добавляют вручную.
* **Незначительные исправления ошибок при наличии обходного пути** — как правило, не бэкпортируются, чтобы не дестабилизировать ветки релиза.
* **Новые возможности, улучшения, оптимизации производительности** — не бэкпортируются.

Метка `pr-must-backport` — это ручной override, который мейнтейнеры используют, чтобы пометить PR для бэкпорта. Метка `pr-critical-bugfix` приводит к тому, что `pr-must-backport` автоматически добавляется CI-хуком (см. `pr_labels_and_category.py`).

**Эскалация конфликтов.** Если автоматический бэкпорт не может разрешить конфликты слияния, всё равно должен быть создан PR cherry-pick и назначен автору, тому, кто выполнил слияние, и текущим назначенным исполнителям исходного PR, чтобы человек мог разрешить конфликты и завершить бэкпорт.

<div id="backport-tool">
  ## Инструмент бэкпорта
</div>

Описанная выше политика бэкпортов реализована автоматизированным инструментом в `tests/ci/cherry_pick.py`. Инструмент запускается как workflow GitHub Actions в инфраструктуре ClickHouse и охватывает все требования: обнаружение активных релизных веток, выбор PR, подходящих для бэкпорта, выполнение двухэтапной процедуры cherry-pick и бэкпорта, разрешение конфликтов, применение политики задержки и синхронизацию меток.

Долгосрочная цель — выделить эту реализацию в автономный Python-инструмент с открытым исходным кодом, который смогут использовать и другие проекты. Целевая архитектура выглядит так:

* **Настраиваемый** — все параметры политики (подходящие метки, окно задержки, пороги устаревания PR, поведение во время раскатки и т. д.) задаются в файле конфигурации, чтобы инструмент можно было адаптировать под требования бэкпорта любого проекта без изменений в коде.
* **Распространяемый** — упакован как самодостаточный Python wheel, устанавливаемый из PyPI, без зависимости от CI-инфраструктуры ClickHouse.
* **Программируемый** — предоставляет понятную объектную модель для pull request, меток и релизных веток, чтобы пользователи могли писать собственные workflow поверх базового движка.

<div id="testing">
  ### Тестирование
</div>

Планируемой частью автономного инструмента является отдельный набор тестов вместе с легковесной инфраструктурой тестирования. Эта инфраструктура сможет поднимать временные GitHub-репозитории (или их локальные эквиваленты), заранее заполненные:

* настраиваемым набором веток, представляющих релизные линии,
* pull request&#39;ами с различными комбинациями меток бэкпорта,
* релизными PR с меткой `release`, указывающей на релизные ветки.

Это позволит тестам проверять полный цикл автоматизации — обнаружение меток, создание веток для cherry-pick, обработку конфликтов, создание PR бэкпорта, логику назначения ответственных, пропуск во время раскатки и политику задержек — на реальном, но временном репозитории, не затрагивая состояние продакшна. Эту же инфраструктуру можно повторно использовать для регрессионного тестирования изменений политик перед их развертыванием.

<div id="active-release-branches">
  ## Активные релизные ветки
</div>

Активная релизная ветка — это любая ветка, для которой соответствующий релизный PR (с меткой `release`) всё ещё открыт на GitHub. Автоматизация бэкпортов определяет такие ветки динамически при каждом запуске, поэтому при выпуске нового релиза или когда старый достигает статуса end-of-life никаких изменений конфигурации не требуется.

Релизная ветка может находиться в состоянии **раскатки** (если её релизный PR помечен меткой `rolling-out`) в период развёртывания нового релиза. Для веток в состоянии раскатки обычные бэкпорты приостанавливаются, чтобы не усложнять раскатку. Метки, привязанные к конкретной версии (например, `v25.3-must-backport`), отменяют это поведение и принудительно запускают бэкпорт даже во время раскатки.

Метка, привязанная к конкретной версии, задаёт *самый ранний* релиз, в который должен попасть PR: бэкпорт выполняется в этот релиз **и во все более новые активные релизные ветки**, а не только в указанную. Например, `v25.3-must-backport` для PR, слитого в ветку development, приводит к бэкпорту в `25.3` и во все активные релизы после неё (`25.4`, `25.5`, …). Если присутствует несколько меток, привязанных к версиям, выбирается самая низкая версия, поскольку она уже охватывает более новые.

Указанный релиз сам по себе не обязан быть активным. Метка для релиза со статусом end-of-life (то есть без открытого релизного PR) всё равно протягивает исправление вперёд во все активные релизы после него, чтобы при обновлении с этого релиза исправление никогда незаметно не терялось. Например, `v25.12-must-backport` для PR продолжает выполнять бэкпорт в `26.1`, `26.2`, … даже после того, как сам `25.12` достиг статуса end-of-life.

<div id="implementation">
  ## Реализация
</div>

<div id="overview">
  ### Обзор
</div>

Автоматизация бэкпорта запускается каждый час в виде workflow `CherryPick` в GitHub Actions (`.github/workflows/cherry_pick.yml`), реализованного в `tests/ci/cherry_pick.py`. Она работает через GitHub API и локальные операции Git на самоуправляемом раннере `style-checker-aarch64`.

Для каждой пары (исходный PR, релизная ветка) процесс состоит из двух этапов:

1. Создаётся **PR cherry-pick**, чтобы отделить разрешение конфликтов от фактического слияния в целевую ветку. Если конфликтов нет, он сливается автоматически.
2. Создаётся **PR бэкпорта** в реальную релизную ветку, при этом изменения после cherry-pick схлопываются в один коммит.

<div id="labels">
  ### Метки
</div>

Метки в исходном PR определяют, будет ли выполняться бэкпорт и в какие ветки.

| Метка                                                    | Эффект                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pr-must-backport`                                       | Бэкпорт во все активные релизные ветки, кроме веток, помеченных `rolling-out`                                                                                                                                                                                                                                           |
| `pr-must-backport-force`                                 | Бэкпорт во все активные релизные ветки без учёта ограничений `rolling-out`                                                                                                                                                                                                                                              |
| `pr-critical-bugfix`                                     | Автоматически включает `pr-must-backport` (через `AUTO_BACKPORT` в `pr_labels_and_category.py`)                                                                                                                                                                                                                          |
| `v{VER}-must-backport` (например, `v25.3-must-backport`) | Бэкпорт в эту релизную ветку **и во все более новые активные релизные ветки** — версия указывает *самый старый* релиз, в который должен попасть PR, даже если сам указанный релиз уже снят с поддержки. Если таких меток несколько, приоритет у самой низкой версии. Переопределяет пропуск `rolling-out` для этих веток |
| `pr-backports-created`                                   | Устанавливается ботом, когда созданы все необходимые PR бэкпорта; снимается, если PR cherry-pick снова открыт                                                                                                                                                                                                           |
| `pr-cherrypick`                                          | Применяется к PR cherry-pick, созданным ботом                                                                                                                                                                                                                                                                            |
| `pr-backport`                                            | Применяется к PR бэкпорта, созданным ботом                                                                                                                                                                                                                                                                               |
| `do not test`                                            | Применяется к PR cherry-pick, чтобы для них не запускался CI                                                                                                                                                                                                                                                             |
| `rolling-out`                                            | Устанавливается в **релизном PR**, чтобы показать, что его ветка сейчас находится в процессе раскатки; обычные бэкпорты её пропускают                                                                                                                                                                                    |

<div id="branch-and-pr-naming">
  ### Именование веток и PR
</div>

Для каждого номера исходного PR `N` и релизной ветки `release/X.Y`:

* Ветка cherry-pick: `cherrypick/release/X.Y/N`
* Ветка бэкпорта: `backport/release/X.Y/N`
* Заголовок PR cherry-pick: `Cherry pick #N to release/X.Y: <original title>`
* Заголовок PR бэкпорта: `Backport #N to release/X.Y: <original title>`

<div id="step-by-step-process">
  ### Пошаговая инструкция
</div>

<div id="discover-active-releases">
  #### 1. Определение активных релизов
</div>

`BackportPRs.receive_release_prs` запрашивает у GitHub все открытые PR с меткой `release`. Head ref этих PR — имена веток релиза (например, `release/25.3`). На их основе определяется набор version-specific label для поиска: все метки `v{VER}-must-backport`, существующие в репозитории, чья версия не новее самого нового активного релиза. Более старые метки включаются, даже если их релиз уже не активен (метка новее любого активного релиза пропускается, так как она не может быть развернута ни в одну активную ветку), поэтому PR, помеченный для релиза со статусом end-of-life, всё равно будет найден, пока существует более новый активный релиз.

<div id="find-prs-to-backport">
  #### 2. Найдите PR для бэкпорта
</div>

`BackportPRs.receive_prs_for_backport` использует API поиска GitHub, чтобы найти PR, которые:

* имеют как минимум одну метку бэкпорта (`pr-must-backport`, `pr-must-backport-force`, `pr-critical-bugfix` или метку для конкретной версии), и
* **не** имеют `pr-backports-created`, и
* были смержены после самой ранней даты коммита, найденной в любой ветке релиза, и
* обновлялись в течение последних 90 дней (чтобы поисковый запрос оставался эффективным).

<div id="rolling-out-branch-handling">
  #### 3. Обработка ветки во время раскатки
</div>

Когда у релизного PR есть метка `rolling-out`, общие метки бэкпорта (`pr-must-backport`, `pr-critical-bugfix`) пропускают эту ветку. Бот закрывает все ранее созданные для этой ветки PR для cherry-pick или бэкпорта, добавляя поясняющий комментарий. Метка для конкретной версии (например, `v25.3-must-backport`) всегда имеет приоритет над этим правилом — для указанного релиза и всех более новых активных релизных веток, на которые она распространяется. `pr-must-backport-force` отключает проверку `rolling-out` для всех веток.

<div id="cherry-pick-stage">
  #### 4. Этап cherry-pick (`ReleaseBranch.create_cherrypick`)
</div>

Для каждой пары (исходный PR, ветка релиза), для которой ещё не существует PR cherry-pick:

1. Переключитесь на ветку релиза и создайте от неё **ветку бэкпорта** (`backport/release/X.Y/N`).
2. Выполните `git merge -s ours` с первым родителем коммита слияния, чтобы создать синтетическую базу слияния без изменений содержимого.
3. Принудительно создайте **ветку cherry-pick** (`cherrypick/release/X.Y/N`), указывающую непосредственно на коммит слияния исходного PR.
4. Попробуйте выполнить `git merge --no-commit --no-ff` ветки cherry-pick в ветку бэкпорта:
   * Если состояние уже up-to-date, значит изменение уже есть в ветке релиза — пометьте как выполненное и пропустите.
   * В противном случае (с конфликтами или без них) выполните reset и отправьте обе ветки.
5. Создайте PR cherry-pick из `cherrypick/release/X.Y/N` в `backport/release/X.Y/N` с метками `pr-cherrypick` и `do not test`.
6. Перенесите `pr-bugfix` или `pr-critical-bugfix` из исходного PR, если применимо.
7. **Не** назначайте исполнителей на этом этапе; их добавляют только при обнаружении конфликтов.

<div id="auto-merge-conflict-free-cherry-pick-prs">
  #### 5. Автоматическое слияние PR cherry-pick без конфликтов
</div>

Если PR cherry-pick готов к слиянию (конфликтов нет), бот автоматически сливает его через GitHub API и сразу переходит к этапу бэкпорта.

<div id="backport-stage">
  #### 6. Этап бэкпорта (`ReleaseBranch.create_backport`)
</div>

После слияния PR cherry-pick:

1. Переключитесь на ветку бэкпорта и выполните `pull`.
2. Найдите merge-base между релизной веткой и веткой бэкпорта.
3. Выполните `git reset --soft` до merge-base, объединив все cherry-pick коммиты в один.
4. Выполните коммит, используя в качестве сообщения заголовок PR бэкпорта.
5. Выполните принудительный push ветки бэкпорта и откройте PR бэкпорта в реальную релизную ветку.
6. Добавьте к PR метку `pr-backport` (а также `pr-bugfix` / `pr-critical-bugfix`, если применимо).
7. Назначьте PR автору исходного PR, пользователю, выполнившему слияние, и текущим назначенным исполнителям (исключая аккаунты роботов).

<div id="completion">
  #### 7. Завершение
</div>

Когда изменения из данного исходного PR бэкпортированы во все релизные ветки, бот добавляет `pr-backports-created` в исходный PR.

<div id="pre-check">
  #### 8. Предварительная проверка
</div>

Прежде чем начинать какую-либо работу по PR, `ReleaseBranch.pre_check` запускает `git merge-base --is-ancestor`, чтобы проверить, что коммит слияния ещё не входит в историю релизной ветки. Если входит, считается, что PR уже был бэкпортирован, и его пропускают.

<div id="stale-cherry-pick-pr-handling">
  ### Обработка устаревших PR cherry-pick
</div>

Класс `CherryPickPRs` запускается в начале каждого почасового выполнения и обрабатывает два сценария:

* **Осиротевшие PR cherry-pick**: если у релизной ветки, связанной с PR cherry-pick, больше нет открытого релизного PR (то есть релиз закрыт), PR cherry-pick закрывается автоматически.
* **Повторно открытые PR cherry-pick**: если у исходного PR уже есть метка `pr-backports-created`, но PR cherry-pick для него всё ещё открыт, метка `pr-backports-created` удаляется из исходного PR, чтобы его можно было обработать повторно.

Для PR cherry-pick, ожидающих ручного разрешения конфликтов:

* Через **3 дня** без обновлений бот публикует комментарий-пинг с упоминанием назначенных исполнителей.
* Через **7 дней** без обновлений бот публикует комментарий о закрытии и закрывает PR.

<div id="conflict-resolution">
  ### Разрешение конфликтов
</div>

Если при cherry-pick возникают конфликты, PR cherry-pick остаётся открытым, чтобы их мог разрешить человек. Бот назначает его автору исходного PR, тому, кто выполнил слияние, и назначенным исполнителям. После разрешения конфликтов и слияния PR cherry-pick бот создаёт PR бэкпорта при следующем ежечасном запуске.

Чтобы полностью отказаться от бэкпорта, закройте PR cherry-pick. Бот будет считать, что он пропущен намеренно.

Чтобы заново создать некорректный PR cherry-pick с нуля:

1. Удалите метку `pr-cherrypick` из PR cherry-pick.
2. Удалите ветку `cherrypick/...`.
3. Удалите метку `pr-backports-created` из исходного PR, если она есть.

<div id="ci-for-backport-prs">
  ### CI для PR бэкпорта
</div>

PR бэкпорта направляются в релизные ветки, поэтому для них используется отдельный CI workflow (`BackportPR`, определённый в `ci/workflows/backport_branches.py`), а не стандартный workflow для pull request. Этот workflow запускает репрезентативное подмножество CI: сборки ASan/UBSan и TSan, релизные сборки, сборки macOS, функциональные тесты под ASan, стресс-тесты под TSan и интеграционные тесты. Он проверяет, что ветка бэкпорта содержит от 1 до 50 коммитов и как минимум один изменённый файл (это обеспечивается `check_backport_branch.py`).

<div id="authentication">
  ### Аутентификация
</div>

Для операций git push в workflow используется SSH-ключ (`ROBOT_CLICKHOUSE_SSH_KEY`). Вызовы GitHub API аутентифицируются через `get_best_robot_token`, который выбирает токен с наибольшим остатком квоты из пула, хранящегося в SSM (`/github-tokens`). `ROBOT_CLICKHOUSE_COMMIT_TOKEN` используется на этапе checkout в workflow Actions, а не для вызовов API. Robot-аккаунты (`robot-clickhouse`, `clickhouse-gh`) исключаются при назначении ответственного.

<div id="github-api-cache">
  ### Кэш API GitHub
</div>

`GitHubCache` (из `cache_utils.py`) сохраняет кэш объектов PyGithub в S3, уменьшая число вызовов API при ежечасных запусках. Кэш скачивается в начале и загружается обратно в конце каждого запуска.

<div id="error-handling">
  ### Обработка ошибок
</div>

Ошибки при обработке отдельных PR перехватываются и записываются в журнал, но не прерывают выполнение. После обработки всех PR, если возникли какие-либо ошибки, выбрасывается `BackportException`. В CI это приводит к отправке уведомления через `CIBuddy` в командный чат.
