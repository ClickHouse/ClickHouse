<div id="test-types">
  ## Типы тестов
</div>

В ClickHouse есть следующие типы тестов:

* [Функциональные тесты](#functional-tests) — набор запросов и скриптов, включающий следующие частично пересекающиеся подмножества
  * [Быстрый тест](#running-fast-tests) — минимальное подмножество
  * [Тесты без сохранения состояния](#running-stateless-tests), которые не требуют заполнения баз данных данными
  * Последовательные тесты, которые нельзя запускать параллельно
* [Интеграционные тесты](#integration-tests), запускаемые через `pytest` в кластере
* [Модульные тесты](#unit-tests)
* [Тесты производительности](#performance-tests)
* [Тесты сборки](#build-tests)
* [Санитайзеры](#sanitizers)
* [Фаззеры](#fuzzing)
  и некоторые другие — см. разделы ниже.

<div id="functional-tests">
  ## Функциональные тесты
</div>

Функциональные тесты — самые простые и удобные в использовании.
Большинство возможностей ClickHouse можно проверять с помощью функциональных тестов, и их обязательно следует использовать для любых изменений в коде ClickHouse, которые можно протестировать таким способом.

Каждый функциональный тест отправляет один или несколько запросов на работающий сервер ClickHouse и сравнивает результат с эталоном.

Тесты находятся в каталоге `./tests/queries`.

Каждый тест бывает одного из двух типов: `.sql` и `.sh`.

* Тест `.sql` — это простой SQL-скрипт, который передаётся на вход `clickhouse-client`.
* Тест `.sh` — это скрипт, который запускается самостоятельно.

SQL-тесты обычно предпочтительнее тестов `.sh`.
Тесты `.sh` следует использовать только тогда, когда нужно проверить какую-то возможность, недоступную средствами чистого SQL, например передать входные данные на вход `clickhouse-client` или протестировать `clickhouse-local`.

:::note
Распространённая ошибка при тестировании типов данных `DateTime` и `DateTime64` — предполагать, что сервер использует определённый часовой пояс (например, &quot;UTC&quot;). Это не так: часовые пояса в тестовых прогонах CI
намеренно выбираются случайным образом. Самый простой способ обойти это — явно указывать часовой пояс для тестовых значений, например `toDateTime64(val, 3, 'Europe/Amsterdam')`.
:::

<div id="running-a-test-locally">
  ### Локальный запуск теста
</div>

Запустите сервер ClickHouse локально на порту по умолчанию (9000).
Чтобы запустить, например, тест `01428_hash_set_nan_key`, перейдите в папку репозитория и выполните следующую команду:

```sh
PATH=<path to clickhouse-client>:$PATH tests/clickhouse-test 01428_hash_set_nan_key
```

Результаты тестов (`stderr` и `stdout`) записываются в файлы `01428_hash_set_nan_key.[stderr|stdout]`, которые находятся рядом с самими тестами (для `queries/0_stateless/foo.sql` вывод будет записан в `queries/0_stateless/foo.stdout`).

Все параметры `clickhouse-test` можно посмотреть с помощью `tests/clickhouse-test --help`.
Вы можете запустить все тесты или subset тестов, указав filter для имён тестов: `./clickhouse-test substring`.
Также доступны параметры для запуска тестов in parallel или в случайном порядке.

<div id="running-tests-on-macos">
  #### Запуск тестов в macOS (Darwin)
</div>

Многие функциональные тесты через оболочку вызывают GNU-утилиты командной строки (`timeout`, `head`, `sed`, `grep`, `date` и т. д.). В macOS используются BSD-варианты этих утилит, и их поведение и набор опций отличаются (например, BSD `head` не поддерживает `head -c 1G`, в BSD `ps` нет длинных опций `--`, а `timeout` отсутствует вовсе). Если запускать тесты с BSD-утилитами, это приводит к ложным сбоям.

CI-раннеры macOS устанавливают GNU-утилиты через Homebrew и ставят их в `PATH` перед BSD-версиями. Локально нужно воспроизвести ту же конфигурацию:

```sh
brew install coreutils gnu-sed grep
export PATH="$(brew --prefix)/opt/coreutils/libexec/gnubin:$(brew --prefix)/opt/gnu-sed/libexec/gnubin:$(brew --prefix)/opt/grep/libexec/gnubin:$PATH"
```

`coreutils` предоставляет GNU `timeout`, `head`, `date` и другие утилиты; `gnu-sed` и `grep` предоставляют GNU `sed` и `grep`. После этого `which timeout head sed grep` должно указывать на пути `gnubin`.

<div id="running-fast-tests">
  ### Запуск быстрых тестов
</div>

Для запуска части тестов (так называемого &quot;Быстрого теста&quot;) может потребоваться достаточно мощная машина. Приведённый ниже пример работает на AWS-инстансе `t3.2xlarge` amd64 с Ubuntu и 100 ГБ дискового пространства.

1. Установите необходимые компоненты и войдите в систему заново.

```sh
sudo apt-get update
sudo apt-get install docker.io
sudo usermod -aG docker "$USER"
```

2. Скачайте исходный код.

```sh
git clone --single-branch https://github.com/ClickHouse/ClickHouse
cd ClickHouse
```

3. Соберите код и запустите &quot;быстрые тесты&quot;.

```sh
python -m ci.praktika run fast
```

Должно получиться

```sh
Failed: 0, Passed: 7394, Skipped: 1795
```

Если вы оставляете выполнение без присмотра, можно использовать `nohup` или `disown`, чтобы оно продолжалось после разрыва `ssh`-соединения.

<div id="running-stateless-tests">
  ### Запуск тестов без сохранения состояния
</div>

Для запуска тестов без сохранения состояния может потребоваться достаточно мощная машина. Пример ниже работает на AWS-инстансе `m7i.8xlarge` с Ubuntu amd64 и хранилищем на 200 ГБ.

1. Установите необходимые зависимости и заново войдите в систему.

```sh
sudo apt-get update
sudo apt-get install docker.io
sudo usermod -aG docker "$USER"
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "ipv6": true,
  "ip6tables": true
}
EOF
sudo systemctl restart docker
```

2. Скачайте исходный код.

```sh
git clone --single-branch https://github.com/ClickHouse/ClickHouse
cd ClickHouse
```

3. Выполните сборку кода.

```sh
python -m ci.praktika run build_debug
cp ci/tmp/build/programs/clickhouse ci/tmp
```

4. Запустите тесты без сохранения состояния, которые можно выполнять параллельно.

```sh
python -m ci.praktika run functional
```

Должно получиться

```sh
Failed: 0, Passed: 8497, Skipped: 103
```

Примечание. Команда `python -m ci.praktika run` запускает конкретную задачу CI; подробнее о CI ClickHouse можно прочитать [здесь](continuous-integration.md#running-stateless-tests).

<div id="adding-a-new-test">
  ### Добавление нового теста
</div>

Чтобы добавить новый тест, сначала создайте файл `.sql` или `.sh` в каталоге `queries/0_stateless`.
Затем сгенерируйте соответствующий файл `.reference`, выполнив `clickhouse-client < 12345_test.sql > 12345_test.reference` или `./12345_test.sh > ./12345_test.reference`.

Тесты должны только создавать, удалять, выполнять SELECT из таблиц и т. д. в базе данных `test`, которая создаётся автоматически заранее.
Допустимо использовать временные таблицы.

Чтобы локально настроить ту же среду, что и в CI, установите конфигурации для тестов (они используют mock-реализацию ZooKeeper и изменяют некоторые настройки)

```sh
cd <repository>/tests/config
sudo ./install.sh
```

:::note
Тесты должны быть

* минимальными: создавать только минимально необходимые таблицы и столбцы, со сведённой к минимуму сложностью,
* быстрыми: выполняться не дольше нескольких секунд (а лучше — меньше секунды),
* корректными и детерминированными: завершаться с ошибкой тогда и только тогда, когда тестируемая возможность не работает,
* изолированными/stateless: не зависеть от окружения и времени выполнения
* исчерпывающими: покрывать граничные случаи, такие как нули, NULL, пустые множества, исключения (негативные тесты; для этого используйте синтаксис `-- { serverError xyz }` и `-- { clientError xyz }`),
* очищать таблицы в конце теста (на случай, если что-то осталось),
* убедиться, что другие тесты не проверяют то же самое (то есть сначала выполните grep).
  :::

<div id="templated-tests-with-jinja">
  ### Шаблонные тесты с Jinja
</div>

Тест `.sql` можно написать в виде шаблона [Jinja2](https://jinja.palletsprojects.com/), добавив к имени файла суффикс `.j2`, то есть `foo.sql` превращается в `foo.sql.j2`. Перед запуском теста `clickhouse-test` преобразует шаблон в обычный скрипт `.sql` и выполняет его.

Это удобно, когда в тесте один и тот же запрос повторяется с небольшими вариациями: цикл генерирует запросы из компактного шаблона, вместо того чтобы прописывать каждый вручную. Чаще всего используются следующие конструкции:

* `{% for ... %} ... {% endfor %}` — для повторения блока,
* `{{ expression }}` — для подстановки значения в вывод,
* `-%}` и `{%-` — для удаления прилегающих пробельных символов, чтобы сгенерированный скрипт оставался аккуратным.

Например, этот шаблон:

```sql
{% for type in ['UInt8', 'UInt16', 'UInt32'] -%}
SELECT toTypeName(0::{{ type }});
{% endfor -%}
```

будет выглядеть так:

```sql
SELECT toTypeName(0::UInt8);
SELECT toTypeName(0::UInt16);
SELECT toTypeName(0::UInt32);
```

Ожидаемый вывод можно предоставить либо как обычный файл `<name>.reference`, содержащий полностью развёрнутые результаты, либо как шаблон `<name>.reference.j2`, который `clickhouse-test` перед сравнением обрабатывает аналогичным образом. Используйте шаблонную форму, когда ожидаемый вывод тоже имеет повторяющуюся структуру. Больше примеров см. в существующих файлах `*.sql.j2` в `tests/queries/0_stateless/`.

<div id="restricting-test-runs">
  ### Ограничение запусков тестов
</div>

Тест может иметь ноль или несколько *тегов*, задающих ограничения на то, в каких контекстах он запускается в CI.

Для тестов `.sql` теги указываются в первой строке в виде SQL-комментария:

```sql
-- Tags: no-fasttest, no-replicated-database
-- no-fasttest: <provide_a_reason_for_the_tag_here>
-- no-replicated-database: <provide_a_reason_here>

SELECT 1
```

В тестах `.sh` метки указываются в комментарии во второй строке:

```bash
#!/usr/bin/env bash
# Tags: no-fasttest, no-replicated-database
# - no-fasttest: <provide_a_reason_for_the_tag_here>
# - no-replicated-database: <provide_a_reason_here>
```

Список доступных меток:

| Tag name                       | Что делает                                                                          | Пример использования                                                                                            |
| ------------------------------ | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `disabled`                     | Тест не запускается                                                                 |                                                                                                                 |
| `long`                         | Время выполнения теста увеличено с 1 до 10 минут                                    |                                                                                                                 |
| `deadlock`                     | Тест долго выполняется в цикле                                                      |                                                                                                                 |
| `race`                         | То же, что и `deadlock`. Предпочтительно использовать `deadlock`                    |                                                                                                                 |
| `shard`                        | Сервер должен прослушивать `127.0.0.*`                                              |                                                                                                                 |
| `distributed`                  | То же, что и `shard`. Предпочтительно использовать `shard`                          |                                                                                                                 |
| `global`                       | То же, что и `shard`. Предпочтительно использовать `shard`                          |                                                                                                                 |
| `zookeeper`                    | Для запуска теста требуется ZooKeeper или ClickHouse Keeper                         | Тест использует `ReplicatedMergeTree`                                                                           |
| `replica`                      | То же, что и `zookeeper`. Предпочтительно использовать `zookeeper`                  |                                                                                                                 |
| `no-fasttest`                  | Тест не запускается в [Быстром тесте](#test-types)                                  | Тест использует движок таблицы `MySQL`, который отключен в Быстром тесте                                        |
| `fasttest-only`                | Тест запускается только в [Быстром тесте](#test-types)                              |                                                                                                                 |
| `no-[asan, tsan, msan, ubsan]` | Отключает тесты в сборках с [санитайзерами](#sanitizers)                            | Тест запускается в QEMU, который не работает с санитайзерами                                                    |
| `no-replicated-database`       | Отключает тест, если база данных по умолчанию использует `ReplicatedDatabaseEngine` |                                                                                                                 |
| `no-ordinary-database`         | Отключает тест, если движок базы данных по умолчанию — `Ordinary`                   |                                                                                                                 |
| `no-parallel`                  | Запрещает параллельный запуск других тестов вместе с этим                           | Тест читает из таблиц `system`, и инварианты могут нарушаться                                                   |
| `no-parallel-replicas`         | Отключает тест, если включены параллельные реплики                                  |                                                                                                                 |
| `no-debug`                     | Отключает тесты в Debug-сборках                                                     |                                                                                                                 |
| `no-release`                   | Отключает тесты в Release-сборках                                                   |                                                                                                                 |
| `no-darwin`                    | Отключает тест в macOS (Darwin)                                                     | Тест зависит от возможностей, специфичных для Linux, таких как распределенные запросы, `procfs` или HTTP-сервер |

Также поддерживаются следующие параметры: `no-polymorphic-parts`, `no-random-settings`, `no-random-merge-tree-settings`, `no-backward-compatibility-check`, `no-cpu-x86_64`, `no-cpu-aarch64`, `no-cpu-ppc64le`, `no-s3-storage`.

Помимо перечисленных выше настроек, можно использовать флаги `USE_*` из `system.build_options`, чтобы указать использование конкретных возможностей ClickHouse.
Например, если в тесте используется таблица MySQL, следует добавить метку `use-mysql`.

<div id="specifying-limits-for-random-settings">
  ### Указание ограничений для случайных настроек
</div>

В тесте можно указать минимально и максимально допустимые значения для настроек, которые могут быть рандомизированы во время его выполнения.

Для тестов `.sh` ограничения записываются в виде комментария в строке рядом с тегами или во второй строке, если теги не указаны:

```bash
#!/usr/bin/env bash
# Tags: no-fasttest
# Random settings limits: max_block_size=(1000, 10000); index_granularity=(100, None)
```

Для тестов `.sql` теги указываются в виде SQL-комментария в строке с тегами или в первой строке:

```sql
-- Tags: no-fasttest
-- Random settings limits: max_block_size=(1000, 10000); index_granularity=(100, None)
SELECT 1
```

Если нужно указать только одно ограничение, для второго можно использовать `None`.

<div id="choosing-the-test-name">
  ### Выбор имени теста
</div>

Имя теста начинается с пятизначного префикса, после которого идет описательное имя, например `00422_hash_function_constexpr.sql`.
Чтобы выбрать префикс, найдите в каталоге наибольший уже существующий префикс и увеличьте его на единицу.

```sh
ls tests/queries/0_stateless/[0-9]*.reference | tail -n 1
```

Тем временем могут быть добавлены и другие тесты с тем же числовым префиксом, но это нормально и не вызовет никаких проблем — позже вам не придётся его менять.

<div id="checking-for-an-error-that-must-occur">
  ### Проверка ошибки, которая должна возникнуть
</div>

Иногда нужно проверить, что при некорректном запросе возникает ошибка сервера. Для этого в SQL-тестах поддерживаются специальные аннотации следующего вида:

```sql
SELECT x; -- { serverError 49 }
```

Этот тест проверяет, что сервер возвращает ошибку с кодом 49 для неизвестного столбца `x`.
Если ошибки нет или возвращается другая ошибка, тест завершится неудачей.
Если вы хотите убедиться, что ошибка возникает на стороне client, используйте аннотацию `clientError`.

Не проверяйте конкретный текст сообщения об ошибке: в будущем он может измениться, и тест будет ломаться без необходимости.
Проверяйте только код ошибки.
Если существующий код ошибки недостаточно точен для ваших задач, подумайте о добавлении нового.

<div id="testing-a-distributed-query">
  ### Тестирование распределённого запроса
</div>

Если вы хотите использовать распределённые запросы в функциональных тестах, можно воспользоваться табличной функцией `remote` с адресами `127.0.0.{1..2}`, чтобы сервер выполнял запросы к самому себе; либо использовать предопределённые тестовые кластеры из файла конфигурации сервера, например `test_shard_localhost`.
Не забудьте добавить слова `shard` или `distributed` в имя теста, чтобы он запускался в CI в нужных конфигурациях, где сервер настроен для поддержки распределённых запросов.

<div id="working-with-temporary-files">
  ### Работа с временными файлами
</div>

Иногда в shell-тесте может потребоваться на лету создать файл для дальнейшей работы.
Имейте в виду, что некоторые проверки CI запускают тесты параллельно, поэтому если вы создаёте или удаляете временный файл в своём скрипте без уникального имени, это может привести к сбою некоторых проверок CI, например Flaky.
Чтобы избежать этого, используйте переменную окружения `$CLICKHOUSE_TEST_UNIQUE_NAME`, чтобы задавать временным файлам имя, уникальное для выполняемого теста.
Так вы можете быть уверены, что файл, который вы создаёте при подготовке или удаляете при очистке, используется только этим тестом, а не каким-то другим, выполняющимся параллельно.

<div id="known-bugs">
  ## Известные ошибки
</div>

Если нам известны ошибки, которые легко воспроизводятся функциональными тестами, мы помещаем подготовленные функциональные тесты в каталог `tests/queries/bugs`.
После исправления ошибок эти тесты переносятся в `tests/queries/0_stateless`.

<div id="integration-tests">
  ## Интеграционные тесты
</div>

Интеграционные тесты позволяют тестировать ClickHouse в кластерной конфигурации, а также взаимодействие ClickHouse с другими серверами, такими как MySQL, Postgres и MongoDB.
Они полезны для эмуляции разделения сети, потери пакетов и т. д.
Эти тесты запускаются в Docker и создают несколько контейнеров с различным ПО.

См. `tests/integration/README.md`, чтобы узнать, как запускать эти тесты.

Обратите внимание, что интеграция ClickHouse со сторонними драйверами не тестируется.
Кроме того, сейчас у нас нет интеграционных тестов для наших JDBC- и ODBC-драйверов.

<div id="unit-tests">
  ## Модульные тесты
</div>

Модульные тесты полезны, когда нужно тестировать не ClickHouse целиком, а отдельную изолированную библиотеку или класс.
Сборку тестов можно включить или отключить с помощью опции CMake `ENABLE_TESTS`.
Модульные тесты (и другие тестовые программы) расположены в подкаталогах `tests` по всему коду.
Чтобы запустить модульные тесты, выполните `ninja test`.
Некоторые тесты используют `gtest`, а некоторые представляют собой просто программы, которые при сбое теста возвращают ненулевой код завершения.

Модульные тесты не обязательны, если код уже покрыт функциональными тестами (к тому же функциональные тесты обычно гораздо проще использовать).

Отдельные проверки gtest можно запускать, вызывая исполняемый файл напрямую, например:

```bash
$ ./src/unit_tests_dbms --gtest_filter=LocalAddress*
```

<div id="performance-tests">
  ## Тесты производительности
</div>

Тесты производительности позволяют измерять и сравнивать производительность отдельных изолированных частей ClickHouse на синтетических запросах.
Тесты производительности находятся в каталоге `tests/performance/`.
Каждый тест представлен файлом `.xml` с описанием тестового сценария.
Тесты запускаются с помощью инструмента `docker/test/performance-comparison`. Инструкции по запуску см. в файле README.

Каждый тест в цикле выполняет один или несколько запросов (возможно, с различными комбинациями параметров).

Если вы хотите повысить производительность ClickHouse в каком-либо сценарии и улучшения можно увидеть на простых запросах, настоятельно рекомендуется написать тест производительности.
Также рекомендуется писать тесты производительности при добавлении или изменении SQL-функций, которые достаточно изолированы и не слишком узкоспециализированы.
Во время тестирования всегда полезно использовать `perf top` или другие инструменты `perf`.

<div id="manual-testing">
  ## Ручное тестирование
</div>

Когда вы разрабатываете новую возможность, имеет смысл также протестировать её вручную.
Это можно сделать следующим образом:

Соберите ClickHouse. Запустите ClickHouse из терминала: перейдите в каталог `programs/clickhouse-server` и выполните `./clickhouse-server`. По умолчанию он будет использовать конфигурацию (`config.xml`, `users.xml` и файлы в каталогах `config.d` и `users.d`) из текущего каталога. Чтобы подключиться к серверу ClickHouse, запустите `programs/clickhouse-client/clickhouse-client`.

Обратите внимание, что все инструменты ClickHouse (server, client и т. д.) — это просто символические ссылки на один бинарный файл с именем `clickhouse`.
Этот бинарный файл находится по пути `programs/clickhouse`.
Все инструменты также можно запускать как `clickhouse tool` вместо `clickhouse-tool`.

Либо можно установить пакет ClickHouse: либо стабильный релиз из репозитория ClickHouse, либо собрать пакет самостоятельно с помощью `./release` в корневом каталоге исходников ClickHouse.
Затем запустите сервер командой `sudo clickhouse start` (или `stop`, чтобы остановить сервер).
Журнал находится по пути `/etc/clickhouse-server/clickhouse-server.log`.

Если ClickHouse уже установлен в вашей системе, вы можете собрать новый бинарный файл `clickhouse` и заменить существующий бинарный файл:

```bash
$ sudo clickhouse stop
$ sudo cp ./clickhouse /usr/bin/
$ sudo clickhouse start
```

Также можно остановить системный clickhouse-server и запустить собственный с той же конфигурацией, но с выводом логов в терминал:

```bash
$ sudo clickhouse stop
$ sudo -u clickhouse /usr/bin/clickhouse server --config-file /etc/clickhouse-server/config.xml
```

Пример с gdb:

```bash
$ sudo -u clickhouse gdb --args /usr/bin/clickhouse server --config-file /etc/clickhouse-server/config.xml
```

Если служба `clickhouse-server` уже запущена и вы не хотите её останавливать, можно изменить номера портов в `config.xml` (или переопределить их в файле в каталоге `config.d`), указать подходящий путь к данным и запустить сервер.

`clickhouse` бинарный файл почти не имеет зависимостей и работает в широком спектре дистрибутивов Linux.
Чтобы быстро и без лишних формальностей проверить свои изменения на сервере, можно просто скопировать свежесобранный `clickhouse` бинарный файл на сервер с помощью `scp`, а затем запустить его, как в примерах выше.

<div id="build-tests">
  ## Тесты сборки
</div>

Тесты сборки позволяют проверить, что сборка не ломается в различных альтернативных конфигурациях и на некоторых других системах.
Эти тесты тоже автоматизированы.

Примеры:

* кросс-компиляция для Darwin x86&#95;64 (macOS)
* кросс-компиляция для FreeBSD x86&#95;64
* кросс-компиляция для Linux AArch64
* сборка на Ubuntu с библиотеками из системных пакетов (не рекомендуется)
* сборка с динамической компоновкой библиотек (не рекомендуется)

Например, сборка с системными пакетами — плохая практика, потому что мы не можем гарантировать, какие именно версии пакетов будут в системе.
Но это действительно нужно сопровождающим Debian.
Поэтому нам как минимум приходится поддерживать этот вариант сборки.
Другой пример: динамическая компоновка — распространённый источник проблем, но она нужна некоторым энтузиастам.

Хотя мы не можем запускать все тесты на всех вариантах сборки, мы хотим хотя бы проверять, что разные варианты сборки не сломаны.
Для этого мы и используем тесты сборки.

Мы также проверяем, что нет единиц трансляции, которые слишком долго компилируются или требуют слишком много оперативной памяти.

Мы также проверяем, что нет слишком больших фреймов стека.

<div id="testing-for-protocol-compatibility">
  ## Тестирование совместимости протокола
</div>

Когда мы расширяем сетевой протокол ClickHouse, мы вручную проверяем, что старый клиент ClickHouse работает с новым clickhouse-server, а новый клиент ClickHouse — со старым clickhouse-server (для этого достаточно запустить бинарные файлы из соответствующих пакетов).

Некоторые сценарии мы также проверяем автоматически с помощью интеграционных тестов:

* могут ли данные, записанные старой версией ClickHouse, успешно читаться новой версией;
* работают ли распределенные запросы в кластере с разными версиями ClickHouse.

<div id="help-from-the-compiler">
  ## Помощь компилятора
</div>

Основной код ClickHouse (расположенный в каталоге `src`) собирается с флагами `-Wall -Wextra -Werror`, а также с некоторыми дополнительными включенными предупреждениями.
Однако для сторонних библиотек эти параметры не включены.

У Clang есть и другие полезные предупреждения — их можно посмотреть с помощью `-Weverything` и выбрать часть из них для сборки по умолчанию.

Мы всегда используем clang для сборки ClickHouse — как для разработки, так и для продакшн.
Вы можете собирать на своей машине в режиме отладки (чтобы экономить заряд батареи ноутбука), но имейте в виду, что с `-O3` компилятор может выдавать больше предупреждений благодаря более качественному управлению потоком выполнения и межпроцедурному анализу.
При сборке с clang в режиме отладки используется отладочная версия `libc++`, которая позволяет выявлять больше ошибок во время выполнения.

<div id="fuzzing">
  ## Фаззинг
</div>

Фаззинг в ClickHouse реализован как с использованием [libFuzzer](https://llvm.org/docs/LibFuzzer.html), так и с помощью случайных SQL-запросов.
Все фазз-тесты следует выполнять с санитайзерами (Address и Undefined).

LibFuzzer используется для изолированного фазз-тестирования библиотечного кода.
Фаззеры реализованы как часть тестового кода и имеют постфикс &quot;&#95;fuzzer&quot; в имени.
Пример фаззера можно найти в `src/Parsers/fuzzers/lexer_fuzzer.cpp`.
Специфичные для LibFuzzer конфигурации, словари и корпус данных хранятся в `tests/fuzz`.
Мы рекомендуем писать фазз-тесты для любой функциональности, обрабатывающей пользовательский ввод.

Фаззеры по умолчанию не собираются.
Чтобы собрать фаззеры, необходимо установить обе опции: `-DENABLE_FUZZING=1` и `-DENABLE_TESTS=1`.
Мы рекомендуем отключать Jemalloc при сборке фаззеров.
Конфигурацию, используемую для интеграции фаззинга ClickHouse в
Google OSS-Fuzz, можно найти в `docker/fuzz`.

Мы также используем простой фазз-тест для генерации случайных SQL-запросов и проверки того, что сервер не падает при их выполнении.
Вы можете найти его в `00746_sql_fuzzy.pl`.
Этот тест следует запускать непрерывно (всю ночь и дольше).

Мы также используем сложный фаззер запросов на основе AST, который способен находить огромное количество пограничных случаев.
Он выполняет случайные перестановки и подстановки в AST запросов.
Он запоминает узлы AST из предыдущих тестов, чтобы использовать их для фаззинга последующих тестов, обрабатывая их в случайном порядке.
Подробнее об этом фаззере можно узнать в [этой статье в блоге](https://clickhouse.com/blog/fuzzing-click-house).

<div id="stress-test">
  ## Стресс-тест
</div>

Стресс-тесты — ещё одна разновидность фаззинга.
В них все функциональные тесты запускаются параллельно, в случайном порядке, на одном сервере.
Результаты тестов не проверяются.

Проверяется, что:

* сервер не падает и не срабатывают ловушки Debug или sanitizer;
* отсутствуют взаимные блокировки;
* структура базы данных остаётся согласованной;
* после теста сервер можно успешно остановить и затем снова запустить без исключений.

Доступно пять вариантов (Debug, ASan, TSan, MSan, UBSan).

<div id="thread-fuzzer">
  ## Thread fuzzer
</div>

Thread Fuzzer (не путайте его с Thread Sanitizer) — это ещё один вид фаззинга, который позволяет случайным образом менять порядок выполнения потоков.
Он помогает находить ещё больше редких случаев.

<div id="hardening">
  ## Усиление защиты
</div>

В отладочной сборке мы используем собственный аллокатор, который применяет ASLR к пользовательским выделениям памяти.

Мы также вручную защищаем области памяти, которые после выделения должны быть доступны только для чтения.

В отладочной сборке мы также используем модифицированную libc, которая гарантирует, что не будут вызываться «вредные» (устаревшие, небезопасные, не потокобезопасные) функции.

Отладочные проверки assert используются очень широко.

В отладочной сборке, если генерируется исключение с кодом «logical error» (это указывает на ошибку в программе), программа немедленно завершается.
Это позволяет использовать исключения в релизной сборке, а в отладочной трактовать их как assert.

Для отладочных сборок используется отладочная версия jemalloc.
Для отладочных сборок используется отладочная версия libc++.

<div id="runtime-integrity-checks">
  ## Проверки целостности во время выполнения
</div>

Для данных, хранящихся на диске, вычисляются контрольные суммы.
Для данных в таблицах семейства MergeTree контрольные суммы вычисляются одновременно тремя способами* (для сжатых блоков данных, несжатых блоков данных и как общая контрольная сумма по всем блокам).
Для данных, передаваемых по сети между клиентом и сервером или между серверами, также вычисляются контрольные суммы.
Репликация обеспечивает побитовую идентичность данных на репликах.

Это необходимо для защиты от неисправного оборудования (битовой деградации на носителях данных, битовых сбоев в оперативной памяти сервера, битовых сбоев в оперативной памяти сетевого контроллера, битовых сбоев в оперативной памяти сетевого коммутатора, битовых сбоев в оперативной памяти клиента, битовых сбоев при передаче по сети).
Обратите внимание, что битовые сбои — обычное явление и вполне вероятны даже при использовании ECC-памяти и наличии контрольных сумм TCP (если вам удаётся эксплуатировать тысячи серверов, ежедневно обрабатывающих PB данных).
[Смотрите видео (на русском)](https://www.youtube.com/watch?v=ooBAQIe0KlQ).

ClickHouse предоставляет средства диагностики, которые помогут инженерам по эксплуатации выявить неисправное оборудование.

* и это не замедляет работу.

Файл конфигурации `uncrustify.cfg` находится в корне исходников.
