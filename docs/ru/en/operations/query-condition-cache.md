:::note
Кэш условий запроса работает только если [enable&#95;analyzer](https://clickhouse.com/docs/operations/settings/settings#enable_analyzer) имеет значение true, которое используется по умолчанию.
:::

Во многих реальных рабочих нагрузках одни и те же или почти одни и те же данные запрашиваются повторно (например, уже существующие данные вместе с новыми).
ClickHouse предоставляет различные методы оптимизации для таких шаблонов запроса.
Один из вариантов — настроить физическую структуру данных с помощью индексных структур (например, индексов первичного ключа, индексов пропуска данных, проекций) или предварительных вычислений (materialized views).
Другой вариант — использовать [кэш запросов](query-cache.md) ClickHouse, чтобы избежать повторного выполнения запроса.
Недостаток первого подхода в том, что он требует ручного вмешательства и контроля со стороны администратора базы данных.
Второй подход может возвращать устаревшие результаты (поскольку кэш запросов не является транзакционно согласованным), что в зависимости от сценария использования может быть как допустимо, так и нет.

Кэш условий запроса предлагает элегантное решение обеих проблем.
Он основан на том, что вычисление условия фильтрации (например, `WHERE col = 'xyz'`) на одних и тех же данных всегда дает одинаковый результат.
Точнее, кэш условий запроса запоминает для каждого вычисленного фильтра и каждой гранулы (= блока из 8192 строк по умолчанию), нет ли в грануле строк, удовлетворяющих условию фильтрации.
Эта информация сохраняется в виде одного бита: бит 0 означает, что ни одна строка не соответствует фильтру, а бит 1 — что существует хотя бы одна подходящая строка.
В первом случае ClickHouse может пропустить соответствующую гранулу при вычислении фильтра, во втором гранулу нужно загрузить и проверить.

Кэш условий запроса эффективен, если выполняются три условия:

* Во-первых, рабочая нагрузка должна повторно вычислять одни и те же условия фильтрации. Это естественным образом происходит, если один и тот же запрос выполняется несколько раз, но также возможно, если два запроса используют одинаковые фильтры, например `SELECT product FROM products WHERE quality > 3` и `SELECT vendor, count() FROM products WHERE quality > 3`.
* Во-вторых, большая часть данных должна быть неизменяемой, то есть не меняться между запросами. Обычно в ClickHouse это так, поскольку части неизменяемы и создаются только операциями INSERT.
* В-третьих, фильтры должны быть селективными, то есть условию фильтрации должно удовлетворять сравнительно небольшое число строк. Чем меньше строк соответствует условию фильтрации, тем больше гранул будет помечено битом 0 (подходящих строк нет), и тем больше данных можно будет «отсечь» при последующих вычислениях фильтра.

<div id="memory-consumption">
  ## Потребление памяти
</div>

Поскольку кэш условий запроса хранит только один бит для каждого условия фильтрации и гранулы, он потребляет очень мало памяти.
Максимальный размер кэша условий запроса можно настроить с помощью настройки сервера [`query_condition_cache_size`](server-configuration-parameters/settings.md#query_condition_cache_size) (по умолчанию: 100 MB).
Размер кэша в 100 MB соответствует 100 * 1024 * 1024 * 8 = 838,860,800 записям.
Поскольку каждая запись представляет одну метку (по умолчанию 8192 строк), кэш может охватывать до 6,871,947,673,600 (6.8 триллиона) строк одного столбца.
На практике фильтры вычисляются более чем по одному столбцу, поэтому это число нужно разделить на количество столбцов, по которым выполняется фильтрация.

<div id="configuration-settings-and-usage">
  ## Параметры конфигурации и использование
</div>

Параметр [use&#95;query&#95;condition&#95;cache](settings/settings#use_query_condition_cache) управляет тем, должен ли кэш условий запроса использоваться для конкретного запроса или для всех запросов текущего сеанса.

Например, при первом выполнении запроса

```sql
SELECT col1, col2
FROM table
WHERE col1 = 'x'
SETTINGS use_query_condition_cache = true;
```

будет хранить диапазоны таблицы, которые не соответствуют предикату.
При последующих выполнениях того же запроса, также с параметром `use_query_condition_cache = true`, кэш условий запроса будет использоваться для сканирования меньшего объёма данных.

<div id="administration">
  ## Администрирование
</div>

Кэш условий запроса не сохраняется при перезапуске ClickHouse.

Чтобы очистить кэш условий запроса, выполните [`SYSTEM CLEAR QUERY CONDITION CACHE`](../sql-reference/statements/system.md#drop-query-condition-cache).

Содержимое кэша отображается в системной таблице [system.query&#95;condition&#95;cache](system-tables/query_condition_cache.md).
Чтобы вычислить текущий размер кэша условий запроса в МБ, выполните `SELECT formatReadableSize(sum(entry_size)) FROM system.query_condition_cache`.
Если вы хотите исследовать отдельные условия фильтрации, проверьте поле `condition` в `system.query_condition_cache`. Обратите внимание, что это поле доступно только в отладочных сборках.

Количество попаданий и промахов кэша условий запроса с момента запуска базы данных отображается как события &quot;QueryConditionCacheHits&quot; и &quot;QueryConditionCacheMisses&quot; в системной таблице [system.events](system-tables/events.md).
Оба счётчика обновляются только для `SELECT`-запросов, выполняемых с настройкой `use_query_condition_cache = true`; другие запросы не влияют на &quot;QueryCacheMisses&quot;.
