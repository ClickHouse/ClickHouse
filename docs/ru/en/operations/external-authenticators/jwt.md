ClickHouse может аутентифицировать пользователей с помощью JSON Web Token (JWT). В отличие от других внешних аутентификаторов, таких как [LDAP](/ru/operations/external-authenticators/ldap) или [Kerberos](/ru/operations/external-authenticators/kerberos), аутентификация с помощью JWT не проверяет подлинность уже существующих пользователей. Вместо этого она динамически создает **эфемерных пользователей** на основе утверждений, встроенных в каждый токен. Эти пользователи существуют только в памяти, получают права доступа на основе утверждений токена и автоматически удаляются после истечения срока действия токена.

Это принципиально отличает аутентификацию JWT от методов на основе пароля или сертификата: оператора `CREATE USER ... IDENTIFIED WITH jwt` не существует, и попытка его выполнить вызывает исключение. JWT-пользователи полностью управляются жизненным циклом токена.

<div id="overview">
  ## Обзор
</div>

Процесс аутентификации работает следующим образом:

1. Клиент передает подписанный JWT через один из поддерживаемых транспортных механизмов (HTTP-заголовок `Authorization: Bearer`, собственный TCP-протокол или поле gRPC `jwt`).
2. ClickHouse проверяет подпись токена.
3. Проверяются обязательные утверждения (`exp`, `iat`, `iss`, `sub`, `aud`).
4. В памяти создается эфемерный пользователь с правами доступа, сформированными на основе утверждений токена `clickhouse:grants` и `clickhouse:roles` и ограниченными верхней границей разрешений.
5. Когда срок действия токена истекает, фоновая задача сборки мусора удаляет пользователя.

<div id="token-claims">
  ## Утверждения в токене
</div>

<div id="required-claims">
  ### Обязательные утверждения
</div>

Каждый JWT, передаваемый в ClickHouse, должен содержать следующие утверждения:

| Утверждение | Описание                                                                                                                   |
| ----------- | -------------------------------------------------------------------------------------------------------------------------- |
| `alg`       | Алгоритм подписи (поле заголовка). Поддерживаемые значения: `HS256`, `RS256`, `ES256`.                                     |
| `exp`       | Время истечения срока действия. Устанавливает `valid_until` эфемерного пользователя.                                       |
| `iat`       | Время выдачи. Используется для предотвращения повторного использования более старых токенов для одного и того же subject. |
| `iss`       | Издатель. Сверяется с ожидаемым издателем провайдера.                                                                      |
| `sub`       | Subject. Становится частью сгенерированного имени пользователя.                                                            |
| `aud`       | Аудитория. Сверяется с ожидаемой аудиторией провайдера.                                                                    |

Поле заголовка `kid` (ID ключа) также обязательно, когда используется разрешение ключей на основе JWKS.

:::note Режим JWKS поддерживает только ключи RSA
Хотя провайдеры со статическими ключами принимают любые из `HS256`, `RS256` или `ES256`, провайдеры на основе JWKS принимают только JWK, у которых `kty` равно `RSA` (то есть токены, подписанные с помощью `RS256`). Токены, подписанные ключами HMAC (`HS256`) или EC (`ES256`), нельзя проверить через конечную точку JWKS, и они будут отклонены.
:::

<div id="other-recognized-claims">
  ### Другие распознаваемые утверждения
</div>

| Утверждение | Описание                                                                                                                                                          |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nbf`       | Время, раньше которого токен недействителен. Это утверждение не является обязательным, но если оно присутствует, токены отклоняются до наступления этого времени. |
| `jti`       | Зарезервировано. Принимается в токенах, но в настоящее время не проверяется и не используется.                                                                    |

<div id="optional-claims">
  ### Необязательные утверждения
</div>

| Утверждение                                                                                                                                                            | Имя по умолчанию    | Описание                                                                                                                                         |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Привилегии                                                                                                                                                             | `clickhouse:grants` | JSON-массив фрагментов SQL `GRANT`, например `["SELECT ON db.*", "INSERT ON db.table1"]`. Каждый элемент разбирается как тело оператора `GRANT`. |
| Роли                                                                                                                                                                   | `clickhouse:roles`  | JSON-массив имён ролей для назначения, например `["analyst", "reader"]`.                                                                         |
| Имена утверждений по умолчанию можно сопоставить с пользовательскими именами утверждений, если ваш провайдер идентификации использует другие соглашения об именовании. |                     |                                                                                                                                                  |

<div id="example-token-header-and-payload">
  ### Пример заголовка и полезной нагрузки токена
</div>

```json
{
  "alg": "RS256",
  "kid": "my-key-id"
}
```

```json
{
  "iss": "https://idp.example.com",
  "sub": "jane.doe",
  "aud": "my-clickhouse-cluster",
  "exp": 1719504000,
  "iat": 1719500400,
  "clickhouse:grants": ["SELECT ON analytics.*", "INSERT ON analytics.events"],
  "clickhouse:roles": ["analyst"]
}
```

<div id="ephemeral-user-behavior">
  ## Поведение эфемерного пользователя
</div>

Пользователи JWT имеют несколько важных отличий от обычных пользователей ClickHouse.

<div id="identity-and-naming">
  ### Идентификация и именование
</div>

Каждый JWT-пользователь получает детерминированный UUID, вычисляемый на основе утверждений `iss`, `sub` и `aud`. Этот UUID **стабилен** при повторных входах в систему. Пользователь, который входит в систему несколько раз с разными токенами (но с теми же издателем, subject и аудиторией), всегда получает один и тот же UUID.

Однако имя пользователя **изменчиво**. Оно формируется следующим образом:

```text
JWT::<issuer>::<audience>::<subject>::<claims_hash>
```

Часть `<claims_hash>` меняется каждый раз, когда меняются утверждения `clickhouse:roles` или `clickhouse:grants`. Это означает, что токены с разными наборами ролей или привилегий дают разные имена пользователей даже для одной и той же идентичности.

<div id="access-rights">
  ### Права доступа
</div>

Эффективные права доступа вычисляются следующим образом:

```text
effective_rights = permission_limit ∩ (token_grants ∪ token_roles)
```

Где `permission_limit` — это набор прав доступа эталонной роли или пользователя, настроенных как верхняя граница. Права, запрашиваемые токеном сверх этого предела, отбрасываются без уведомления.

<div id="token-freshness">
  ### Актуальность токена
</div>

ClickHouse отслеживает утверждение `iat` (issued-at) токена, который последним был успешно аутентифицирован для каждой стабильной идентичности. Если предъявляется токен со значением `iat`, равным сохранённому или более ранним, сервер повторно использует существующего эфемерного пользователя без повторной оценки утверждений. Это не позволяет более старым токенам снижать разрешения пользователя.

<div id="lifetime-and-garbage-collection">
  ### Время жизни и сборка мусора
</div>

Эфемерные пользователи создаются при первой аутентификации по токену и удаляются фоновой задачей сборки мусора после наступления `valid_until` (вычисляется из `exp`). Интервал GC задаётся параметром `gc_interval` (по умолчанию: 5 минут).

Между запусками GC пользователи с истёкшим сроком действия всё ещё могут отображаться в `system.users`, но аутентифицироваться уже не могут.

<div id="persistent-access-assignments">
  ### Постоянные назначения прав доступа
</div>

Поскольку UUID стабилен, вы можете назначать пользователю JWT профили настроек, квоты, политики строк и политики маскирования столбцов с помощью SQL-команд. Эти назначения сохраняются в хранилище управления доступом (на диске или в ZooKeeper) и не исчезают после истечения срока действия токена и повторной аутентификации.

Указывайте пользователя по его текущему имени пользователя:

```sql
ALTER SETTINGS PROFILE my_profile ADD TO 'JWT::ClickHouse::my-service-id::jane.doe::<claims-hash>';
```

:::note
Имя пользователя и UUID для данной identity можно найти в столбцах `name` и `id` таблицы `system.users`, пока пользователь активен.
:::

Обратите внимание, что `ALTER USER` не работает с JWT-пользователями напрямую, так как они работают в режиме только для чтения. Чтобы назначить профили настроек, квоты или политики, используйте команды `ALTER SETTINGS PROFILE`, `ALTER QUOTA` или `ALTER ROW POLICY`, как показано выше.

<div id="differences-from-regular-users">
  ## Отличия от обычных пользователей
</div>

| Возможность                            | JWT-пользователи                                                               | Обычные пользователи                             |
| -------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------ |
| Создание                               | Автоматически по утверждениям токена                                           | Оператор `CREATE USER`                           |
| Хранение                               | Только в памяти (эфемерно)                                                     | На диске, в ZooKeeper или в файле конфигурации   |
| `CREATE USER ... IDENTIFIED WITH jwt`  | Не поддерживается (вызывает Исключение)                                        | Поддерживаются все остальные типы аутентификации |
| `ALTER USER` / `DROP USER`             | Не поддерживается                                                              | Поддерживается                                   |
| Резервное копирование и восстановление | Не включено                                                                    | Включено                                         |
| Имя пользователя                       | Генерируется автоматически, может меняться                                     | Выбирается администратором, фиксировано          |
| UUID                                   | Детерминированный на основе `iss`+`sub`+`aud`                                  | Случайный при создании                           |
| Срок действия                          | Ограничен значением `exp` токена                                               | До явного удаления                               |
| Права доступа                          | Определяются утверждениями токена и ограничиваются верхней границей разрешений | Явно выдаются через `GRANT`                      |
| Ограничения по хосту                   | Задаются сетевой конфигурацией провайдера                                      | Задаются клаузой `HOST` для пользователя         |
| Профили настроек                       | Можно назначать по UUID (постоянно)                                            | Настраиваются напрямую                           |
| Квоты и политики строк                 | Можно назначать по UUID (постоянно)                                            | Настраиваются напрямую                           |
| Роли по умолчанию                      | Не настраиваются                                                               | Настраиваются                                    |

<div id="sql-security-definer-views">
  ## Представления SQL SECURITY DEFINER
</div>

Когда эфемерный пользователь JWT создает представление с `SQL SECURITY DEFINER`, сервер автоматически создает постоянную теневую копию этого пользователя, которая выступает определителем представления. Этот теневой пользователь:

* Имеет имя `<original_jwt_username>:definer`
* Имеет `NO_AUTHENTICATION` (не может использоваться для входа)
* Сохраняет те же права доступа, что и исходный пользователь JWT на момент создания представления

Это гарантирует, что представление продолжит работать после истечения срока действия токена эфемерного пользователя и удаления исходного пользователя сборщиком мусора.

<div id="client-usage">
  ## Использование клиента
</div>

<div id="passing-token-directly">
  ### Передача токена напрямую
</div>

Используйте флаг `--jwt` с клиентом ClickHouse, чтобы пройти аутентификацию с помощью заранее полученного токена:

```bash
clickhouse-client --host your-instance.clickhouse.cloud --secure --jwt '<your_jwt_token>'
```

:::note
Флаг `--jwt` нельзя использовать одновременно с `--user`. Если указан `--jwt`, имя пользователя берётся из токена.
:::

<div id="http-interface">
  ### HTTP-интерфейс
</div>

Передайте токен в заголовке `Authorization` как Bearer-токен:

```bash
curl -H 'Authorization: Bearer <your_jwt_token>' \
    'https://your-instance.clickhouse.cloud:8443/?query=SELECT+currentUser()'
```

:::warning
Всегда отправляйте JWT по HTTPS. Bearer-токен, переданный по незашифрованному HTTP, виден любому, кто может перехватить трафик, и это равносильно утечке учетных данных.
:::

<div id="oauth2-device-code-login">
  ### Вход по коду устройства OAuth2
</div>

`клиент ClickHouse` поддерживает интерактивный вход по потоку OAuth2 Device Code через флаг `--login`. Для конечных точек ClickHouse Cloud клиент автоматически выполняет обмен токенами, чтобы получить JWT для ClickHouse. Токены прозрачно обновляются в течение сеанса. При получении нового токена клиент автоматически выполняет повторное подключение.

```bash
clickhouse-client --host your-instance.clickhouse.cloud --login
```

<div id="clickhouse-cloud-built-in">
  ## Встроенный JWT-аутентификатор ClickHouse Cloud
</div>

Каждый сервис ClickHouse Cloud имеет предопределенный JWT-аутентификатор, который используется в SQL Console и в процессе входа через `клиент ClickHouse` с флагом `--login`. Этот аутентификатор настроен следующим образом:

| Параметр         | Значение                                                 |
| ---------------- | -------------------------------------------------------- |
| `iss` (издатель)   | `ClickHouse`                                             |
| `aud` (аудитория) | UUID сервиса (виден в URL консоли Cloud)                 |
| `sub` (subject)  | Адрес электронной почты вашего аккаунта ClickHouse Cloud |

Для встроенного аутентификатора верхняя граница разрешений задана ролью `default_role` и пользователем `default`. Это означает, что фактические права любого JWT-пользователя пересекаются с привилегиями этих двух сущностей, поэтому токен не может повысить привилегии сверх того, что разрешено для `default_role` и `default`.

Чтобы использовать этот аутентификатор, ничего настраивать не нужно. Он создается автоматически при создании сервиса.

<div id="interserver-communication">
  ## Межсерверное взаимодействие
</div>

Когда запрос перенаправляется на другой сегмент или реплику, JWT-токен передаётся по межсерверному протоколу. Удалённый узел самостоятельно повторно проверяет токен, создавая собственного эфемерного пользователя.

<div id="troubleshooting">
  ## Устранение неполадок
</div>

* **Права доступа не выданы:** У указанной роли или пользователя может не быть необходимых привилегий. Убедитесь, что роли, указанные в `clickhouse:roles`, существуют и имеют соответствующие привилегии.
* **Токен отклонён:** Убедитесь, что `iss`, `aud` и алгоритм подписи в вашем токене соответствуют ожиданиям провайдера JWT. Если используется JWKS, убедитесь, что `kid` токена соответствует ключу в наборе ключей провайдера.
* **Пользователь исчезает между запросами:** Эфемерные пользователи удаляются после истечения срока действия токена. Для длительных сеансов используйте клиент, поддерживающий обновление токена (например, в режиме `--login`).
* **`CREATE USER ... IDENTIFIED WITH jwt` завершается ошибкой:** Это ожидаемое поведение. Пользователей JWT нельзя создавать через DDL. Они полностью управляются жизненным циклом токена.
