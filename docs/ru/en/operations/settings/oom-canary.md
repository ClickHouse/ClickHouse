<div id="overview">
  ## Обзор
</div>

Когда на хосте или в memory cgroup заканчивается память, Linux OOM (out-of-memory)
killer завершает процесс с помощью `SIGKILL` — обычно самый крупный потребитель,
которым на выделенном хосте является сам `clickhouse-server`. В результате
теряется весь сервер, вместо того чтобы дать ему шанс восстановиться.

OOM канарейка меняет то, кто погибает первым. Он запускает небольшой *жертвенный*
дочерний процесс, который делает себя самой привлекательной целью для OOM, чтобы
ядро завершило его вместо сервера. Затем сервер обнаруживает его гибель,
подтверждает, что это было событие OOM, и снижает давление на память, чтобы
выжить.

Канарейка не увеличивает memory limit и не заменяет правильно заданные
ограничения (см. [оверкоммит памяти](/ru/operations/settings/memory-overcommit) и
`max_server_memory_usage`). Это последний рубеж защиты: он обменивает
небольшой фиксированный объём памяти на шанс пережить всплеск потребления памяти.

<div id="how-it-works">
  ## Как это работает
</div>

Канарейка — это отдельный процесс `clickhouse oom-canary`. Он устанавливает для себя
`oom_score_adj` на максимум (`1000`), чтобы ядро в первую очередь выбрало именно его, затем
выделяет `oom_canary_size` байт (по умолчанию 100 МБ), обращается к этой памяти и применяет `mlock`,
чтобы его резидентный набор действительно находился в памяти. Процесс автоматически завершается, если сервер останавливается.

В сервере поток мониторинга следит за канарейкой (через `pidfd`) и реагирует, когда
она завершается:

* Завершена сигналом `SIGKILL` **при наличии** признаков OOM в cgroup → выполнить реакцию на OOM, затем
  заново запустить новую канарейку.
* Завершена **без** признаков OOM (например, из-за ручного `kill -9`) или завершилась
  из-за временного сбоя → только перезапуск, без реакции.
* Неустранимая ошибка инициализации или остановка сервера → канарейка отключается сама.

Признаки OOM берутся только из счётчика `oom_kill` в `memory.events.local` cgroup v2.
Это сделано намеренно на уровне самой cgroup: иерархические или общесистемные счётчики могут
увеличиваться из-за несвязанных процессов и вызывать ложные срабатывания.

При подтверждённом OOM реакция на OOM выполняет следующие независимые шаги: записывает сообщение `FATAL`
в журнал, очищает арены аллокатора (jemalloc), по возможности отменяет все выполняющиеся
запросы, отменяет все слияния и мутации, а также ставит событие в очередь
[`system.crash_log`](/ru/operations/system-tables/crash_log). Системные журналы не
сбрасываются на диск синхронно, потому что принудительный I/O под давлением памяти может
ухудшить ситуацию.

<div id="requirements">
  ## Требования
</div>

* **Linux ≥ 5.3.** Монитор управляет канарейкой через `pidfd_open`; на более старых ядрах
  канарейка отключается при запуске. На платформах, отличных от Linux, он ничего не делает.
* **cgroup v2 с `memory.events.local`** для реакции на OOM. Без этого
  канарейка всё равно перезапускается после `SIGKILL`, но не может подтвердить OOM, поэтому
  реакция никогда не выполняется (при запуске в журнал записывается предупреждение).
* **Право `mlock` (необязательно).** Для блокировки памяти канарейки требуется
  `CAP_IPC_LOCK` или достаточный `RLIMIT_MEMLOCK`; если это не удаётся, канарейка записывает
  предупреждение, а его память может быть вытеснена в swap, что снижает его эффективность как цели для OOM.

:::warning memory.oom.group
Если для cgroup сервера включён параметр cgroup v2 `memory.oom.group`, ядро
завершает весь cgroup как единое целое при OOM — сервер завершается вместе с
канарейкой, и реакция никогда не выполняется. В этом режиме канарейка не может защитить сервер;
при запуске в журнал записывается предупреждение.
:::

<div id="configuration">
  ## Конфигурация
</div>

OOM canary управляется с помощью [настроек сервера](/ru/operations/server-configuration-parameters/settings),
которые задаются как элементы верхнего уровня в конфигурации сервера и применяются после перезапуска.

| Настройка                            | По умолчанию         | Описание                                                                                                                                                                                                    |
| ------------------------------------ | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `oom_canary_enable`                  | `false`              | Включить OOM canary.                                                                                                                                                                                        |
| `oom_canary_size`                    | `104857600` (100 MB) | Число байт, которые OOM canary выделяет и использует. Чем больше значение, тем более вероятной целью для OOM он становится.                                                                                 |
| `oom_canary_relaunch`                | `true`               | Перезапускать OOM canary после его завершения, если только это не вызвано постоянной ошибкой запуска или остановкой, с учетом указанных ниже ограничений.                                                   |
| `oom_canary_max_rapid_relaunches`    | `10`                 | Максимальное число последовательных *быстрых* перезапусков до отключения автоперезапуска во избежание зацикливания. Счетчик сбрасывается, если OOM canary работает дольше `oom_canary_max_backoff_seconds`. |
| `oom_canary_initial_backoff_seconds` | `1`                  | Начальная задержка между перезапусками; каждый раз удваивается до максимального значения.                                                                                                                   |
| `oom_canary_max_backoff_seconds`     | `60`                 | Максимальная задержка между перезапусками.                                                                                                                                                                  |

```xml
<clickhouse>
    <oom_canary_enable>1</oom_canary_enable>
    <oom_canary_size>104857600</oom_canary_size>
</clickhouse>
```

<div id="observability">
  ## Обсервабилити
</div>

Подтверждённый OOM оставляет строку в
[`system.crash_log`](/ru/operations/system-tables/crash_log) со значением `signal = 9` и
`signal_description` с упоминанием `OOM Canary`:

```sql
SELECT event_time, signal, signal_description
FROM system.crash_log
WHERE signal = 9 AND signal_description LIKE '%OOM Canary%'
ORDER BY event_time DESC;
```

Жизненный цикл канарейки и каждый этап реакции на OOM также записываются в лог сервера.
