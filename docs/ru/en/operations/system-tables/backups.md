<div id="description">
  ## Описание
</div>

Содержит список всех операций `BACKUP` и `RESTORE`, их текущих состояний и других свойств. Обратите внимание: таблица не является постоянной и показывает только операции, выполненные после последнего перезапуска сервера.

<div id="columns">
  ## Столбцы
</div>

{/*AUTOGENERATED_START*/ }

* `id` ([String](/ru/sql-reference/data-types/string)) — Идентификатор операции; может быть либо передан через SETTINGS id=..., либо случайным образом сгенерирован как UUID.
* `name` ([String](/ru/sql-reference/data-types/string)) — Имя операции, строка вида `Disk('backups', 'my_backup')`
* `base_backup_name` ([String](/ru/sql-reference/data-types/string)) — Имя операции базовой резервной копии, строка вида `Disk('backups', 'my_base_backup')`
* `query_id` ([String](/ru/sql-reference/data-types/string)) — Query id запроса, который запустил резервное копирование.
* `status` ([Enum8(&#39;CREATING&#95;BACKUP&#39; = 0, &#39;BACKUP&#95;CREATED&#39; = 1, &#39;BACKUP&#95;FAILED&#39; = 2, &#39;RESTORING&#39; = 3, &#39;RESTORED&#39; = 4, &#39;RESTORE&#95;FAILED&#39; = 5, &#39;BACKUP&#95;CANCELLED&#39; = 6, &#39;RESTORE&#95;CANCELLED&#39; = 7)](/ru/sql-reference/data-types/enum)) — Статус операции резервного копирования или восстановления.
* `error` ([String](/ru/sql-reference/data-types/string)) — Сообщение об ошибке, если оно есть.
* `start_time` ([DateTime64(6)](/ru/sql-reference/data-types/datetime64)) — Время начала операции.
* `end_time` ([DateTime64(6)](/ru/sql-reference/data-types/datetime64)) — Время завершения операции.
* `num_files` ([UInt64](/ru/sql-reference/data-types/int-uint)) — Количество файлов, сохранённых в резервной копии.
* `total_size` ([UInt64](/ru/sql-reference/data-types/int-uint)) — Общий размер файлов, сохранённых в резервной копии.
* `num_entries` ([UInt64](/ru/sql-reference/data-types/int-uint)) — Количество записей в резервной копии, то есть количество файлов в папке, если резервная копия хранится в виде папки.
* `uncompressed_size` ([UInt64](/ru/sql-reference/data-types/int-uint)) — Размер резервной копии в несжатом виде.
* `compressed_size` ([UInt64](/ru/sql-reference/data-types/int-uint)) — Размер резервной копии в сжатом виде.
* `files_read` ([UInt64](/ru/sql-reference/data-types/int-uint)) — Возвращает количество файлов, прочитанных во время RESTORE из этой резервной копии.
* `bytes_read` ([UInt64](/ru/sql-reference/data-types/int-uint)) — Возвращает общий размер файлов, прочитанных во время RESTORE из этой резервной копии.
* `ProfileEvents` ([Map(LowCardinality(String), UInt64)](/ru/sql-reference/data-types/map)) — Все ProfileEvents, зафиксированные во время этой операции.
* `settings` ([Map(LowCardinality(String), String)](/ru/sql-reference/data-types/map)) — Настройки резервного копирования/восстановления, фактически использованные для этой операции (из предложения `SETTINGS`, включая значения по умолчанию). Чувствительные настройки не раскрываются.
* `engine_settings` ([Map(LowCardinality(String), String)](/ru/sql-reference/data-types/map)) — Настройки, фактически использованные компонентами чтения/записи движка резервного копирования (например, S3 `allow_native_copy`). Пусто, если в операции задействовано более одного движка и плоское отображение не может это представить: инкрементные резервные копии и восстановления, восстановления легковесных снимков и невнутренние операции `ON CLUSTER`.

<div id="restore-atomicity">
  ## Атомарность восстановления
</div>

`RESTORE` не является транзакционной операцией и при сбое не выполняет откат. Для каждой таблицы все выбранные части копируются до подключения первой из них, но сам этап подключения не является транзакционным — части становятся видимыми по одной. Таблицы обрабатываются независимо.

**Таблицы независимы.** Таблица, восстановление которой завершилось, остается на месте, даже если другая таблица в той же команде позже завершится ошибкой:

```sql
RESTORE TABLE db.t0, TABLE db.t1
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

Если эта команда завершится с ошибкой после полного восстановления `db.t0`, но до завершения восстановления `db.t1`, `db.t0` останется восстановленной.

**Предложение `PARTITIONS` не является границей коммита.** Она лишь определяет, какие части таблицы восстанавливаются:

```sql
RESTORE TABLE db.t0 PARTITIONS '2026-06-01', '2026-06-02', '2026-06-03'
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

Сначала копируются все выбранные части таблицы, и только после того, как будут готовы все из них, они подключаются. Поэтому, если эта команда завершается с ошибкой на этапе копирования — например, после того как партиция `2026-06-01` уже полностью скопирована, а копирование `2026-06-02` и `2026-06-03` ещё не завершено, — то для `2026-06-01` **не** выполняется коммит, и в таблице не остаётся никаких данных, восстановленных этой командой. После завершения этапа копирования и начала этапа подключения части коммитятся по одной, поэтому сбой во время подключения может оставить таблицу частично восстановленной, без rollback.

Чтобы коммитить партиции независимо (чтобы уже завершённая партиция пережила последующий сбой и её можно было повторно восстановить отдельно), выполняйте отдельный `RESTORE` для каждой партиции, используя `SETTINGS allow_non_empty_tables = true` начиная со второй.
