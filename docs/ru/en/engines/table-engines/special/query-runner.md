<div id="queryrunner-table-engine">
  # Движок таблицы QueryRunner
</div>

Записи, вставленные в таблицу `QueryRunner`, представляют собой запросы, которые выполняются этим движком.
Этот движок можно использовать для асинхронного выполнения запросов, батчевого выполнения сгенерированных запросов,
направления запросов в удалённые кластеры, бенчмарков, фаззинга и тестирования с теневым трафиком.

<div id="creating-a-table">
  ## Создание таблицы
</div>

```sql
CREATE TABLE runner
(
    query String,
    database String,
    settings Map(LowCardinality(String), String)
)
ENGINE = QueryRunner
SETTINGS
    cluster = 'cluster_name',
    shard = '1',
    mode = 'asynchronous',
    threads = 4,
    max_queue_size = 1000
[DEFINER = { user | CURRENT_USER }] [SQL SECURITY { DEFINER | INVOKER | NONE }];
```

Таблица должна быть создана с подмножеством допустимых столбцов: `query`, `database`, `settings`.
Столбец `query` обязателен, остальные столбцы — необязательны.

| Столбец    | Тип                   | Описание                                                                                                   |
| ---------- | --------------------- | ---------------------------------------------------------------------------------------------------------- |
| `query`    | `String`              | Запрос, который нужно выполнить.                                                                           |
| `database` | `String`              | База данных по умолчанию для запроса. Если значение пустое, используется база данных сервера по умолчанию. |
| `settings` | `Map(String, String)` | Настройки, применяемые к запросу.                                                                          |

<div id="engine-settings">
  ## Настройки движка
</div>

| Настройка        | По умолчанию     | Значение                                                                                                                                                                                                                                    |
| ---------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cluster`        | `''`             | Имя кластера, в который отправляются запросы. Если значение пустое, запросы выполняются локально.                                                                                                                                           |
| `shard`          | `'1'`            | Индекс сегмента кластера с нумерацией с 1, в который отправляются запросы, или `'random'`, чтобы выбирать случайный сегмент для каждого запроса, или `'all'`, чтобы выполнять каждый запрос на всех сегментах. Требует настройки `cluster`. |
| `mode`           | `'asynchronous'` | В режиме `synchronous` INSERT возвращает управление после завершения всех запросов из вставляемого батча. В режиме `asynchronous` INSERT возвращает управление, как только запросы поставлены в очередь.                                    |
| `threads`        | `4`              | Количество фоновых потоков, выполняющих запросы.                                                                                                                                                                                            |
| `max_queue_size` | `1000`           | Максимальное количество запросов в очереди. Когда очередь заполнена, новые запросы отбрасываются, и ошибка записывается в журнал.                                                                                                           |

<div id="details">
  ## Подробности
</div>

Таблица поддерживает только запросы `INSERT`.
Запросы выполняются в режиме &quot;fire and forget&quot;: в случае исключения повторные попытки не выполняются,
а результаты запросов `SELECT` отбрасываются (единственный способ сохранить результаты — `INSERT SELECT`).
Успешность каждого запроса можно проверить в таблице `system.query_log`, где запросы, инициированные
этим движком, помечаются как `is_internal = 1` на инициирующем сервере.

Запросы в очереди хранятся в памяти и не сохраняются после перезапуска сервера. При остановке сервера
(или `DROP`/`DETACH` таблицы) запросы, которые еще не начали выполняться, отбрасываются. Из
запросов, которые уже выполняются, отправленные в кластер отменяются, а выполняющиеся
локально продолжают ожидать до завершения.

Если запускаемый запрос сам является `INSERT`, его данные должны быть указаны прямо в запросе — `INSERT ... VALUES (...)`,
`INSERT ... SELECT ...` или `INSERT ... FORMAT ...` с данными в тексте запроса. `INSERT`, который
ожидает получить данные из отдельного потока, не поддерживается.

<div id="local-mode-and-sql-security">
  ## Локальный режим и безопасность SQL
</div>

Без настройки `cluster` запросы выполняются на локальном сервере.
Пользователь, от имени которого они выполняются, определяется предложением `SQL SECURITY`:

* `INVOKER` (по умолчанию): запросы выполняются от имени пользователя, который выполнил `INSERT`.
* `DEFINER`: запросы выполняются от имени пользователя, указанного в `DEFINER`. Поскольку вставляемые запросы могут быть произвольными, выдача `INSERT` для такой таблицы делегирует все привилегии пользователя-определителя.
* `NONE`: запросы выполняются с полным доступом, без пользователя. Требуется grant `ALLOW_SQL_SECURITY_NONE` при создании таблицы.

<div id="cluster-mode">
  ## Режим кластера
</div>

Если указан параметр `cluster`, запросы отправляются в указанный кластер.

Целевой сегмент выбирается параметром `shard`: это может быть фиксированный индекс с нумерацией с 1 (по умолчанию `'1'`), `'random'` для выбора
случайного сегмента для каждого запроса или `'all'` для выполнения каждого запроса на всех сегментах кластера. Реплика внутри
сегмента выбирается в соответствии с настройкой `load_balancing` сервера.

Столбец `database` задаёт базу данных по умолчанию для соединения с удалённым сервером. Поскольку
база данных по умолчанию задаётся один раз для каждого соединения, для каждого отдельного значения `database` используется собственный
пул соединений, который создаётся при первом обращении и затем повторно используется в течение всего времени существования таблицы.

`DEFINER` и `безопасность SQL` действуют только в локальном режиме, и их сочетание с параметром
`cluster` является ошибкой. На удалённых серверах запросы аутентифицируются с использованием
учётных данных из конфигурации кластера и выполняются как обычные исходные запросы: они записываются в
`system.query_log` с `is_initial_query = 1` и собственным `query_id` (не связанным с INSERT, который
их породил). На инициирующем сервере отправленные запросы записываются в `system.query_log`
с `is_internal = 1`.

Поскольку движок отбрасывает результаты запросов, он всегда выполняет отправленные запросы с
`discard_query_data = 1`, поэтому данные результатов запросов SELECT не передаются по сети
(это переопределяет любое значение `discard_query_data`, заданное в столбце `settings`).

<div id="waiting-for-queries-to-finish">
  ## Ожидание завершения запросов
</div>

В асинхронном режиме следующий запрос можно использовать, чтобы ждать, пока не завершатся все запросы, к настоящему моменту отправленные в таблицу:

```sql
SYSTEM WAIT QUERY RUNNER runner;
```

<div id="example">
  ## Пример
</div>

Повторный запуск недавних `SELECT`-запросов из журнала запросов:

```sql
INSERT INTO runner (query, database, settings)
SELECT query, current_database, Settings
FROM system.query_log
WHERE type = 'QueryFinish' AND is_initial_query AND NOT is_internal AND query_kind = 'Select'
  AND event_time > now() - INTERVAL 1 HOUR;
```
