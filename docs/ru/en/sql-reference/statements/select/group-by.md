Секция `GROUP BY` переводит запрос `SELECT` в режим агрегации, который работает следующим образом:

* Секция `GROUP BY` содержит список выражений (или одно выражение, которое рассматривается как список из одного элемента). Этот список служит &quot;ключом группировки&quot;, а каждое отдельное выражение называется &quot;ключевым выражением&quot;.
* Все выражения в секциях [SELECT](/ru/sql-reference/statements/select/index.md), [HAVING](/ru/sql-reference/statements/select/having.md) и [ORDER BY](/ru/sql-reference/statements/select/order-by.md) **должны** вычисляться на основе ключевых выражений **или** с помощью [агрегатных функций](../../../sql-reference/aggregate-functions/index.md) над неключевыми выражениями (включая обычные столбцы). Иными словами, каждый столбец, выбираемый из таблицы, должен использоваться либо в ключевом выражении, либо внутри агрегатной функции, но не в обоих вариантах одновременно.
* Результат агрегации запроса `SELECT` будет содержать столько строк, сколько уникальных значений &quot;ключа группировки&quot; было в исходной таблице. Обычно это значительно уменьшает количество строк, нередко на несколько порядков, но не всегда: число строк остается тем же, если все значения &quot;ключа группировки&quot; различны.

Если вы хотите группировать данные в таблице по номерам столбцов, а не по их именам, включите настройку [enable&#95;positional&#95;arguments](/ru/operations/settings/settings#enable_positional_arguments).

:::note
Есть и другой способ выполнить агрегацию по таблице. Если запрос содержит столбцы таблицы только внутри агрегатных функций, `GROUP BY clause` можно опустить — тогда будет предполагаться агрегация по пустому множеству ключей. Такие запросы всегда возвращают ровно одну строку.
:::

<div id="null-processing">
  ## Обработка NULL
</div>

При группировке ClickHouse интерпретирует [NULL](/ru/sql-reference/syntax#null) как значение, и `NULL==NULL`. Это отличается от обработки `NULL` в большинстве других случаев.

Вот пример, который показывает, что это означает.

Предположим, у вас есть следующая таблица:

```text
┌─x─┬────y─┐
│ 1 │    2 │
│ 2 │ ᴺᵁᴸᴸ │
│ 3 │    2 │
│ 3 │    3 │
│ 3 │ ᴺᵁᴸᴸ │
└───┴──────┘
```

Запрос `SELECT sum(x), y FROM t_null_big GROUP BY y` возвращает следующий результат:

```text
┌─sum(x)─┬────y─┐
│      4 │    2 │
│      3 │    3 │
│      5 │ ᴺᵁᴸᴸ │
└────────┴──────┘
```

Можно заметить, что `GROUP BY` для `y = NULL` просуммировал `x`, как будто `NULL` — это обычное значение.

Если передать в `GROUP BY` несколько ключей, результат будет содержать все сочетания выбранных значений, как если бы `NULL` был конкретным значением.

<div id="rollup-modifier">
  ## Модификатор ROLLUP
</div>

Модификатор `ROLLUP` используется для вычисления промежуточных итогов по ключевым выражениям в соответствии с их порядком в списке `GROUP BY`. Строки промежуточных итогов добавляются после результирующей таблицы.

Промежуточные итоги вычисляются в обратном порядке: сначала для последнего ключевого выражения в списке, затем для предыдущего и так далее, вплоть до первого ключевого выражения.

В строках промежуточных итогов значения уже &quot;сгруппированных&quot; ключевых выражений устанавливаются в `0` или пустую строку.

:::note
Обратите внимание, что оператор [HAVING](/ru/sql-reference/statements/select/having.md) может влиять на результаты промежуточных итогов.
:::

**Пример**

Рассмотрим таблицу t:

```text
┌─year─┬─month─┬─day─┐
│ 2019 │     1 │   5 │
│ 2019 │     1 │  15 │
│ 2020 │     1 │   5 │
│ 2020 │     1 │  15 │
│ 2020 │    10 │   5 │
│ 2020 │    10 │  15 │
└──────┴───────┴─────┘
```

```sql title="Query"
SELECT year, month, day, count(*) FROM t GROUP BY ROLLUP(year, month, day);
```

Поскольку раздел `GROUP BY` содержит три ключевых выражения, результат включает четыре таблицы с промежуточными итогами, «свёрнутыми» справа налево:

* `GROUP BY year, month, day`;
* `GROUP BY year, month` (при этом столбец `day` заполняется нулями);
* `GROUP BY year` (теперь столбцы `month` и `day` заполняются нулями);
* и общим итогом (при этом все три столбца ключевых выражений содержат нули).

```text title="Response"
┌─year─┬─month─┬─day─┬─count()─┐
│ 2020 │    10 │  15 │       1 │
│ 2020 │     1 │   5 │       1 │
│ 2019 │     1 │   5 │       1 │
│ 2020 │     1 │  15 │       1 │
│ 2019 │     1 │  15 │       1 │
│ 2020 │    10 │   5 │       1 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│ 2019 │     1 │   0 │       2 │
│ 2020 │     1 │   0 │       2 │
│ 2020 │    10 │   0 │       2 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│ 2019 │     0 │   0 │       2 │
│ 2020 │     0 │   0 │       4 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│    0 │     0 │   0 │       6 │
└──────┴───────┴─────┴─────────┘
```

Тот же запрос также можно записать с помощью ключевого слова `WITH`.

```sql title="Query"
SELECT year, month, day, count(*) FROM t GROUP BY year, month, day WITH ROLLUP;
```

**См. также**

* настройку [group&#95;by&#95;use&#95;nulls](/ru/operations/settings/settings.md#group_by_use_nulls) для обеспечения совместимости со стандартом SQL.

<div id="cube-modifier">
  ## Модификатор CUBE
</div>

Модификатор `CUBE` используется для вычисления промежуточных итогов для каждой комбинации ключевых выражений в списке `GROUP BY`. Строки с промежуточными итогами добавляются после результирующей таблицы.

В строках с промежуточными итогами значения всех &quot;сгруппированных&quot; ключевых выражений устанавливаются в `0` или пустую строку.

:::note
Обратите внимание, что оператор [HAVING](/ru/sql-reference/statements/select/having.md) может влиять на результаты промежуточных итогов.
:::

**Пример**

Рассмотрим таблицу t:

```text
┌─year─┬─month─┬─day─┐
│ 2019 │     1 │   5 │
│ 2019 │     1 │  15 │
│ 2020 │     1 │   5 │
│ 2020 │     1 │  15 │
│ 2020 │    10 │   5 │
│ 2020 │    10 │  15 │
└──────┴───────┴─────┘
```

```sql title="Query"
SELECT year, month, day, count(*) FROM t GROUP BY CUBE(year, month, day);
```

Поскольку в секции `GROUP BY` три ключевых выражения, результат содержит восемь таблиц с промежуточными итогами для всех комбинаций ключевых выражений:

* `GROUP BY year, month, day`
* `GROUP BY year, month`
* `GROUP BY year, day`
* `GROUP BY year`
* `GROUP BY month, day`
* `GROUP BY month`
* `GROUP BY day`
* и итоги.

Столбцы, не включённые в `GROUP BY`, заполняются нулями.

```text title="Response"
┌─year─┬─month─┬─day─┬─count()─┐
│ 2020 │    10 │  15 │       1 │
│ 2020 │     1 │   5 │       1 │
│ 2019 │     1 │   5 │       1 │
│ 2020 │     1 │  15 │       1 │
│ 2019 │     1 │  15 │       1 │
│ 2020 │    10 │   5 │       1 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│ 2019 │     1 │   0 │       2 │
│ 2020 │     1 │   0 │       2 │
│ 2020 │    10 │   0 │       2 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│ 2020 │     0 │   5 │       2 │
│ 2019 │     0 │   5 │       1 │
│ 2020 │     0 │  15 │       2 │
│ 2019 │     0 │  15 │       1 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│ 2019 │     0 │   0 │       2 │
│ 2020 │     0 │   0 │       4 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│    0 │     1 │   5 │       2 │
│    0 │    10 │  15 │       1 │
│    0 │    10 │   5 │       1 │
│    0 │     1 │  15 │       2 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│    0 │     1 │   0 │       4 │
│    0 │    10 │   0 │       2 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│    0 │     0 │   5 │       3 │
│    0 │     0 │  15 │       3 │
└──────┴───────┴─────┴─────────┘
┌─year─┬─month─┬─day─┬─count()─┐
│    0 │     0 │   0 │       6 │
└──────┴───────┴─────┴─────────┘
```

Тот же запрос также можно записать с помощью ключевого слова `WITH`.

```sql title="Query"
SELECT year, month, day, count(*) FROM t GROUP BY year, month, day WITH CUBE;
```

**См. также**

* настройку [group&#95;by&#95;use&#95;nulls](/ru/operations/settings/settings.md#group_by_use_nulls) для обеспечения совместимости со стандартом SQL.

<div id="with-totals-modifier">
  ## Модификатор WITH TOTALS
</div>

Если указан модификатор `WITH TOTALS`, вычисляется ещё одна строка. В этой строке столбцы ключа содержат значения по умолчанию (нули или пустые строки), а столбцы агрегатных функций — значения, вычисленные по всем строкам (то есть «итоговые» значения).

Эта дополнительная строка выводится только в форматах `JSON*`, `TabSeparated*` и `Pretty*`, отдельно от остальных строк:

* В форматах `XML` и `JSON*` эта строка выводится как отдельное поле `totals`.
* В форматах `TabSeparated*`, `CSV*` и `Vertical` эта строка выводится после основного результата; перед ней добавляется пустая строка (после остальных данных).
* В форматах `Pretty*` эта строка выводится как отдельная таблица после основного результата.
* В формате `Template` эта строка выводится в соответствии с указанным шаблоном.
* В остальных форматах она недоступна.

:::note
`totals` выводится в результатах запросов `SELECT` и не выводится в `INSERT INTO ... SELECT`.
:::

`WITH TOTALS` может работать по-разному при наличии [HAVING](/ru/sql-reference/statements/select/having.md). Поведение зависит от настройки `totals_mode`.

<div id="configuring-totals-processing">
  ### Настройка обработки итогов
</div>

По умолчанию используется `totals_mode = 'before_having'`. В этом случае &#39;totals&#39; вычисляется по всем строкам, включая те, которые не проходят HAVING и `max_rows_to_group_by`.

В остальных вариантах в &#39;totals&#39; включаются только строки, прошедшие HAVING, при этом они по-разному работают с настройкой `max_rows_to_group_by` и `group_by_overflow_mode = 'any'`.

`after_having_exclusive` – Не включать строки, не прошедшие через `max_rows_to_group_by`. Иными словами, в &#39;totals&#39; будет меньше или столько же строк, как если бы `max_rows_to_group_by` не использовался.

`after_having_inclusive` – Включать в &#39;totals&#39; все строки, не прошедшие через `max_rows_to_group_by`. Иными словами, в &#39;totals&#39; будет больше или столько же строк, как если бы `max_rows_to_group_by` не использовался.

`after_having_auto` – Подсчитывать количество строк, прошедших HAVING. Если оно превышает определённый порог (по умолчанию 50%), включать в &#39;totals&#39; все строки, не прошедшие через `max_rows_to_group_by`. В противном случае не включать их.

`totals_auto_threshold` – По умолчанию 0.5. Коэффициент для `after_having_auto`.

Если `max_rows_to_group_by` и `group_by_overflow_mode = 'any'` не используются, все варианты `after_having` эквивалентны, и можно использовать любой из них (например, `after_having_auto`).

Вы можете использовать `WITH TOTALS` в подзапросах, включая подзапросы в предложении [JOIN](/ru/sql-reference/statements/select/join.md) (в этом случае соответствующие итоговые значения объединяются).

<div id="group-by-all">
  ## GROUP BY ALL
</div>

`GROUP BY ALL` эквивалентен перечислению всех выражений в SELECT, которые не являются агрегатными функциями.

Например:

```sql
SELECT
    a * 2,
    b,
    count(c),
FROM t
GROUP BY ALL
```

то же, что и

```sql
SELECT
    a * 2,
    b,
    count(c),
FROM t
GROUP BY a * 2, b
```

В особом случае, когда среди аргументов функции есть и агрегатные функции, и другие поля, ключи `GROUP BY` будут содержать максимально возможное количество неагрегатных полей, которые можно из неё извлечь.

Например:

```sql
SELECT
    substring(a, 4, 2),
    substring(substring(a, 1, 2), 1, count(b))
FROM t
GROUP BY ALL
```

то же, что и

```sql
SELECT
    substring(a, 4, 2),
    substring(substring(a, 1, 2), 1, count(b))
FROM t
GROUP BY substring(a, 4, 2), substring(a, 1, 2)
```

<div id="examples">
  ## Примеры
</div>

Пример:

```sql
SELECT
    count(),
    median(FetchTiming > 60 ? 60 : FetchTiming),
    count() - sum(Refresh)
FROM hits
```

В отличие от MySQL (и в соответствии со стандартом SQL), нельзя получить значение столбца, который не входит в ключ или агрегатную функцию (за исключением константных выражений). Чтобы обойти это ограничение, можно использовать агрегатную функцию &#39;any&#39; (она возвращает первое встретившееся значение) или &#39;min/max&#39;.

Пример:

```sql
SELECT
    domainWithoutWWW(URL) AS domain,
    count(),
    any(Title) AS title -- getting the first occurred page header for each domain.
FROM hits
GROUP BY domain
```

Для каждого различного значения ключа `GROUP BY` вычисляет набор значений агрегатных функций.

<div id="grouping-sets-modifier">
  ## Модификатор GROUPING SETS
</div>

Это наиболее общий модификатор.
Он позволяет вручную задать несколько наборов ключей агрегации (grouping sets).
Агрегация выполняется отдельно для каждого grouping set, после чего все результаты объединяются.
Если столбец отсутствует в grouping set, он заполняется значением по умолчанию.

Иными словами, описанные выше модификаторы можно выразить через `GROUPING SETS`.
Хотя запросы с модификаторами `ROLLUP`, `CUBE` и `GROUPING SETS` синтаксически эквивалентны, они могут выполняться по-разному.
`GROUPING SETS` пытается выполнять всё параллельно, тогда как `ROLLUP` и `CUBE` выполняют итоговое слияние агрегатов в одном потоке.

Если исходные столбцы содержат значения по умолчанию, может быть трудно определить, относится ли строка к агрегации, в которой эти столбцы используются как ключи.
Чтобы решить эту проблему, следует использовать функцию `GROUPING`.

**Пример**

Следующие два запроса эквивалентны.

```sql
-- Query 1
SELECT year, month, day, count(*) FROM t GROUP BY year, month, day WITH ROLLUP;

-- Query 2
SELECT year, month, day, count(*) FROM t GROUP BY
GROUPING SETS
(
    (year, month, day),
    (year, month),
    (year),
    ()
);
```

**См. также**

* настройка [group&#95;by&#95;use&#95;nulls](/ru/operations/settings/settings.md#group_by_use_nulls) для совместимости со стандартом SQL.

<div id="implementation-details">
  ## Подробности реализации
</div>

Агрегация — одна из важнейших возможностей столбцовой СУБД, поэтому её реализация — одна из наиболее тщательно оптимизированных частей ClickHouse. По умолчанию агрегация выполняется в памяти с использованием хеш-таблицы. Для неё существует более 40 специализаций, которые автоматически выбираются в зависимости от типов данных «ключа группировки».

<div id="group-by-optimization-depending-on-table-sorting-key">
  ### Оптимизация GROUP BY в зависимости от ключа сортировки таблицы
</div>

Агрегацию можно выполнять более эффективно, если таблица отсортирована по некоторому ключу, а выражение `GROUP BY` содержит как минимум префикс ключа сортировки или инъективные функции. В этом случае, когда из таблицы считывается новый ключ, промежуточный результат агрегации может быть завершён и отправлен клиенту. Это поведение включается настройкой [optimize&#95;aggregation&#95;in&#95;order](../../../operations/settings/settings.md#optimize_aggregation_in_order). Такая оптимизация снижает использование памяти во время агрегации, но в некоторых случаях может замедлить выполнение запроса.

<div id="group-by-in-external-memory">
  ### GROUP BY во внешней памяти
</div>

Вы можете включить сброс временных данных на диск, чтобы ограничить использование памяти при `GROUP BY`.
Настройка [max&#95;bytes&#95;before&#95;external&#95;group&#95;by](/ru/operations/settings/settings#max_bytes_before_external_group_by) задаёт порог потребления оперативной памяти, при котором временные данные `GROUP BY` сбрасываются в файловую систему. Если установлено значение 0 (по умолчанию), эта возможность отключена.
Либо можно задать [max&#95;bytes&#95;ratio&#95;before&#95;external&#95;group&#95;by](/ru/operations/settings/settings#max_bytes_ratio_before_external_group_by), чтобы использовать `GROUP BY` во внешней памяти только после того, как запрос достигнет определённого порога использования памяти.

При использовании `max_bytes_before_external_group_by` мы рекомендуем установить `max_memory_usage` примерно вдвое выше (или `max_bytes_ratio_before_external_group_by=0.5`). Это необходимо, потому что агрегация проходит в два этапа: чтение данных и формирование промежуточных данных (1), а затем слияние промежуточных данных (2). Сброс данных в файловую систему возможен только на этапе 1. Если временные данные не были сброшены, то на этапе 2 может потребоваться до такого же объёма памяти, как и на этапе 1.

Например, если [max&#95;memory&#95;usage](/ru/operations/settings/settings#max_memory_usage) было установлено в 10000000000 и вы хотите использовать внешнюю агрегацию, разумно установить `max_bytes_before_external_group_by` в 10000000000, а `max_memory_usage` — в 20000000000. Когда срабатывает внешняя агрегация (если был хотя бы один сброс временных данных), максимальное потребление оперативной памяти лишь немного превышает `max_bytes_before_external_group_by`.

При распределённой обработке запросов внешняя агрегация выполняется на удалённых серверах. Чтобы сервер-инициатор запроса использовал лишь небольшой объём оперативной памяти, установите `distributed_aggregation_memory_efficient` в 1.

При слиянии данных, сброшенных на диск, а также при слиянии результатов с удалённых серверов при включённой настройке `distributed_aggregation_memory_efficient`, потребляется до `1/256 * the_number_of_threads` от общего объёма оперативной памяти.

Когда внешняя агрегация включена, если объём данных меньше `max_bytes_before_external_group_by` (то есть данные не были сброшены), запрос выполняется так же быстро, как и без внешней агрегации. Если же какие-либо временные данные были сброшены, время выполнения увеличится в несколько раз (примерно втрое).

Если после `GROUP BY` у вас есть [ORDER BY](/ru/sql-reference/statements/select/order-by.md) с [LIMIT](/ru/sql-reference/statements/select/limit.md), то объём используемой оперативной памяти зависит от объёма данных в `LIMIT`, а не во всей таблице. Но если в `ORDER BY` нет `LIMIT`, не забудьте включить внешнюю сортировку (`max_bytes_before_external_sort`).
