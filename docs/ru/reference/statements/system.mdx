## SYSTEM RELOAD EMBEDDED DICTIONARIES {#reload-embedded-dictionaries}

Перезагружает все [встроенные словари](/ru/reference/statements/create/dictionary).
По умолчанию встроенные словари отключены.
Всегда возвращает `Ok.` независимо от результата обновления встроенных словарей.

## SYSTEM RELOAD DICTIONARIES {#reload-dictionaries}

Запрос `SYSTEM RELOAD DICTIONARIES` перезагружает словари со status `LOADED` (см. столбец `status` в [`system.dictionaries`](/ru/reference/system-tables/dictionaries)), то есть словари, которые ранее уже были успешно загружены.
По умолчанию словари загружаются лениво (см. [dictionaries&#95;lazy&#95;load](/ru/reference/settings/server-settings/settings/dictionaries#dictionaries_lazy_load)), поэтому вместо автоматической загрузки при запуске они инициализируются при первом обращении — через функцию [`dictGet`](/ru/reference/functions/regular-functions/ext-dict-functions#dictGet) или при выполнении `SELECT` из таблиц с `ENGINE = Dictionary`.

**Синтаксис**

```sql
SYSTEM RELOAD DICTIONARIES [ON CLUSTER cluster_name]
```

## SYSTEM RELOAD DICTIONARY {#reload-dictionary}

Полностью перезагружает словарь `dictionary_name` независимо от его состояния (LOADED / NOT&#95;LOADED / FAILED).
Всегда возвращает `Ok.` независимо от результата обновления словаря.

```sql
SYSTEM RELOAD DICTIONARY [ON CLUSTER cluster_name] dictionary_name
```

Статус словаря можно проверить, выполнив запрос к таблице `system.dictionaries`.

```sql
SELECT name, status FROM system.dictionaries;
```

## SYSTEM UNLOAD DICTIONARY {#unload-dictionary}

Выгружает словарь `dictionary_name`, чтобы освободить занимаемую им память, если статус словаря — `LOADED`.
При следующем обращении словарь при необходимости снова загружается отложенно.

```sql
SYSTEM UNLOAD DICTIONARY dictionary_name
```

Статус словаря можно проверить, выполнив запрос к таблице `system.dictionaries`.

```sql
SELECT name, status FROM system.dictionaries;
```

## SYSTEM UNLOAD DICTIONARIES {#unload-dictionaries}

Запрос `SYSTEM UNLOAD DICTIONARIES` выгружает из памяти все словари со статусом `LOADED` (см. столбец `status` в [`system.dictionaries`](/ru/reference/system-tables/dictionaries)), то есть словари, которые ранее были успешно загружены.

```sql
SYSTEM UNLOAD DICTIONARIES
```

## SYSTEM RELOAD FUNCTIONS {#reload-functions}

Перезагружает все зарегистрированные [исполняемые пользовательские функции](/ru/reference/functions/regular-functions/udf#executable-user-defined-functions) или одну из них из файла конфигурации.

**Синтаксис**

```sql
SYSTEM RELOAD FUNCTIONS [ON CLUSTER cluster_name]
SYSTEM RELOAD FUNCTION [ON CLUSTER cluster_name] function_name
```

## SYSTEM RELOAD ASYNCHRONOUS METRICS {#reload-asynchronous-metrics}

Пересчитывает все [асинхронные метрики](/ru/reference/system-tables/asynchronous_metrics). Поскольку асинхронные метрики периодически обновляются в соответствии с настройкой [asynchronous&#95;metrics&#95;update&#95;period&#95;s](/ru/reference/settings/server-settings/settings/asynchronous-metrics#asynchronous_metrics_update_period_s), вручную обновлять их с помощью этого оператора обычно не нужно.

```sql
SYSTEM RELOAD ASYNCHRONOUS METRICS [ON CLUSTER cluster_name]
```

## SYSTEM RELOAD DELTA KERNEL TRACING {#reload-delta-kernel-tracing}

Добавлено в: v26.2.0

Включает сообщения лога библиотеки Delta Kernel, которая читает таблицы [`DeltaLake`](/ru/reference/engines/table-engines/integrations/deltalake), начиная с заданного уровня: `ERROR`, `WARN`, `INFO`, `DEBUG` или `TRACE` (в верхнем регистре). Сообщения записываются в журнал сервера с именем логгера `DeltaKernelTracing`. После запуска сервера библиотека не пишет сообщений, пока не будет выполнен этот оператор. Чтобы изменить уровень, выполните его повторно.

```sql
SYSTEM RELOAD DELTA KERNEL TRACING level
```

Для выполнения этого оператора не требуется никаких привилегий. В сборке без поддержки Delta Kernel он завершается с ошибкой `SUPPORT_IS_DISABLED`.

## SYSTEM CLEAR|DROP DNS CACHE {#drop-dns-cache}

Очищает внутренний DNS-кеш ClickHouse. Иногда (в старых версиях ClickHouse) эту команду необходимо использовать при изменении инфраструктуры (например, при смене IP-адреса другого сервера ClickHouse или сервера, используемого словарями).

Для более удобного (автоматического) управления кешем см. параметры `disable_internal_dns_cache`, `dns_cache_max_entries`, `dns_cache_update_period`.

## SYSTEM CLEAR|DROP AVRO SCHEMA CACHE {#drop-avro-schema-cache}

Очищает кэши Confluent Schema Registry для каждого URL, используемые форматом `AvroConfluent`. Эта команда удаляет как кэш получения схем (id → схема), так и кэш регистрации схем (subject + схема → id), поэтому последующие операции чтения и записи снова будут обращаться к серверу Schema Registry. Полезно, если схема была удалена или перезаписана на стороне реестра, а также для проверки идемпотентности реестра в тестах.

## SYSTEM CLEAR|DROP POINT IN POLYGON CACHE {#drop-point-in-polygon-cache}

Очищает кэш предварительно обработанных константных полигонов, используемых функцией [`pointInPolygon`](/ru/reference/functions/regular-functions/geo/coordinates#pointinpolygon). Настроенное ограничение размера (настройка сервера `point_in_polygon_cache_size`) остаётся без изменений, поэтому после этого кэш продолжает принимать новые записи. Чтобы отключить кэш, установите `point_in_polygon_cache_size` в `0`.

* `SYSTEM CLEAR TEXT INDEX POSTINGS CACHE`

## SYSTEM RESTART DISK {#restart-disk}

Добавлено в: v21.6.0

Перезагружает метаданные диска `disk_name`. Для таблицы `MergeTree`, все диски которой доступны только для чтения, команда также повторно сканирует каталог данных таблицы и загружает части данных, появившиеся там с момента последнего сканирования. Благодаря этому части, записанные в то же хранилище другим процессом записи, становятся видимыми без повторного подключения таблицы. Части, удалённые из хранилища, не обнаруживаются. Настройка MergeTree [`refresh_parts_interval`](/ru/reference/settings/merge-tree-settings/refresh#refresh_parts_interval) делает то же самое периодически.

```sql
SYSTEM RESTART DISK [ON CLUSTER cluster_name] disk_name
```

Требуется привилегия `SYSTEM RESTART DISK`.

## SYSTEM CLEAR|DROP TIME SERIES CACHES {#drop-time-series-caches}

Очищает кэши таблицы `TimeSeries`, которые позволяют при вставке пропускать строки, уже присутствующие в её целевых таблицах. Таких кэшей два: кэш дедупликации таблицы семейств метрик и кэш дедупликации таблицы tags; см. настройки таблицы `metric_families_deduplication_cache_expiration_seconds` и `tags_deduplication_cache_expiration_seconds`. Кэши локальны для сервера и не учитывают изменения, внесённые непосредственно в целевые таблицы. Такое расхождение устраняется само собой по истечении срока действия записей; чтобы следующая вставка записала все свои строки без ожидания (например, после очистки таблицы семейств метрик), используйте этот оператор. `TRUNCATE TABLE` для таблицы `TimeSeries` очищает кэши только на том сервере, где выполняется запрос, поэтому, если целевые таблицы реплицируются, после этого выполните данный оператор с `ON CLUSTER`, чтобы очистить кэши на остальных репликах.

```sql
SYSTEM DROP TIME SERIES CACHES [ON CLUSTER cluster_name] [db.]table
```

## SYSTEM SYNC FILESYSTEM CACHE {#sync-filesystem-cache}

Синхронизирует хранящееся в памяти состояние файлового кэша ClickHouse с файлами кэша, фактически находящимися на диске, и возвращает `cache_name`, `path` и загруженный `size` каждого кэшированного сегмента файла. Необязательное имя кэша ограничивает операцию одним кэшем.

```sql
SYSTEM SYNC FILESYSTEM CACHE ['<cache_name>']
```

## SYSTEM CLEAR|DROP DISTRIBUTED CACHE {#drop-distributed-cache}

<Note>
  `SYSTEM CLEAR|DROP DISTRIBUTED CACHE` доступна только в ClickHouse Cloud.
</Note>

Удаляет распределённый кэш. Используйте `CONNECTIONS`, чтобы удалить только кэшированные соединения с серверами распределённого кэша, либо передайте идентификатор сервера, чтобы выбрать только один сервер.

```sql
SYSTEM DROP DISTRIBUTED CACHE [CONNECTIONS | 'server_id']
```

## SYSTEM DROP REPLICA {#drop-replica}

Недоступные реплики таблиц `ReplicatedMergeTree` можно удалить с помощью следующего синтаксиса:

```sql
SYSTEM DROP REPLICA 'replica_name' FROM TABLE database.table;
SYSTEM DROP REPLICA 'replica_name' FROM DATABASE database;
SYSTEM DROP REPLICA 'replica_name';
SYSTEM DROP REPLICA 'replica_name' FROM ZKPATH '/path/to/table/in/zk';
```

Запросы удаляют путь реплики `ReplicatedMergeTree` в ZooKeeper. Это полезно, когда реплика недоступна, а ее метаданные невозможно удалить из ZooKeeper с помощью `DROP TABLE`, потому что такой таблицы уже не существует. Удалить можно только неактивную/устаревшую реплику; локальную реплику удалить нельзя, для этого используйте `DROP TABLE`. `DROP REPLICA` не удаляет никаких таблиц и не удаляет с диска ни данные, ни метаданные.

Первый удаляет метаданные реплики `'replica_name'` таблицы `database.table`.
Второй делает то же самое для всех реплицируемых таблиц в базе данных.
Третий делает то же самое для всех реплицируемых таблиц на локальном сервере.
Четвертый полезен для удаления метаданных недоступной реплики, когда все остальные реплики таблицы были удалены. Для него нужно явно указать путь к таблице. Это должен быть тот же путь, который был передан в качестве первого аргумента движка `ReplicatedMergeTree` при создании таблицы.

## SYSTEM DROP DATABASE REPLICA {#drop-database-replica}

Неработающие реплики баз данных `Replicated` можно удалить с помощью следующего синтаксиса:

```sql
SYSTEM DROP DATABASE REPLICA 'replica_name' [FROM SHARD 'shard_name'] FROM DATABASE database;
SYSTEM DROP DATABASE REPLICA 'replica_name' [FROM SHARD 'shard_name'];
SYSTEM DROP DATABASE REPLICA 'replica_name' [FROM SHARD 'shard_name'] FROM ZKPATH '/path/to/table/in/zk';
```

Подобно `SYSTEM DROP REPLICA`, удаляет путь реплики базы данных `Replicated` из ZooKeeper, если базы данных, для которой можно выполнить `DROP DATABASE`, больше нет. Обратите внимание: эта команда не удаляет реплики `ReplicatedMergeTree` (поэтому вам также может понадобиться `SYSTEM DROP REPLICA`). Имена сегмента и реплики — это имена, указанные в аргументах движка `Replicated` при создании базы данных. Кроме того, эти имена можно получить из столбцов `database_shard_name` и `database_replica_name` в `system.clusters`. Если предложение `FROM SHARD` отсутствует, то `replica_name` должно быть полным именем реплики в формате `shard_name|replica_name`.

## SYSTEM CLEAR|DROP UNCOMPRESSED CACHE {#drop-uncompressed-cache}

Очищает кэш несжатых данных.
Кэш несжатых данных включается и отключается с помощью настройки уровня запроса, пользователя или профиля [`use_uncompressed_cache`](/ru/reference/settings/session-settings/use#use_uncompressed_cache).
Его размер можно задать с помощью настройки уровня сервера [`uncompressed_cache_size`](/ru/reference/settings/server-settings/settings/uncompressed-cache#uncompressed_cache_size).

## SYSTEM CLEAR|DROP COLUMNS CACHE {#drop-columns-cache}

Очищает кэш столбцов (десериализованные столбцы, хранящиеся в памяти).
Операции чтения, которые уже выполняются в момент очистки кэша, не могут снова поместить свои данные в кэш — в том числе данные из частей, до которых они доходят уже после очистки, поэтому кэш остаётся очищенным даже под нагрузкой.
Кэш столбцов включается и отключается настройкой `use_columns_cache` на уровне запроса, пользователя или профиля.
Его размер задаётся настройкой уровня сервера `columns_cache_size`.
Чтобы исследовать содержимое кэша, используйте [`system.columns_cache`](/ru/reference/system-tables/columns_cache).

## SYSTEM CLEAR|DROP COMPILED EXPRESSION CACHE {#drop-compiled-expression-cache}

Очищает кэш скомпилированных выражений.
Кэш скомпилированных выражений включается и отключается с помощью настройки уровня запроса, пользователя или профиля [`compile_expressions`](/ru/reference/settings/session-settings/compile#compile_expressions).

## SYSTEM CLEAR|DROP QUERY CONDITION CACHE {#drop-query-condition-cache}

Очищает кэш условий запроса.

## SYSTEM CLEAR|DROP ENCRYPTION HEADERS CACHE {#drop-encryption-headers-cache}

Очищает кэш заголовков шифрования. В этом кэше хранятся заголовки шифрования, считываемые из начала зашифрованных файлов. Он используется экспериментальным путём чтения `use_reader_executor`, чтобы избежать их повторного чтения; его размер задаётся настройкой сервера `encryption_header_cache_size`.

## SYSTEM CLEAR|DROP КЭШ ЗАПРОСОВ {#drop-query-cache}

```sql
SYSTEM CLEAR QUERY CACHE;
SYSTEM CLEAR QUERY CACHE TAG '<tag>'
```

Очищает [кэш запросов](/ru/concepts/features/performance/caches/query-cache).
Если указана метка, удаляются только записи кэша запросов с этой меткой.

## SYSTEM CLEAR|DROP SCHEMA CACHE {#drop-schema-cache}

Добавлено в: v22.8.0

Очищает [кэш автоматического определения схемы](/ru/concepts/features/interfaces/schema-inference#schema-inference-cache), в котором хранятся структуры таблиц, автоматически определённые по данным, прочитанным табличными функциями и движками таблиц `file`, `s3`, `url`, `hdfs` и `azureBlobStorage`. Кэшированные структуры можно просмотреть в [`system.schema_inference_cache`](/ru/reference/system-tables/schema_inference_cache). Без `FOR` очищаются кэши всех этих хранилищ, а с `FOR` — только кэш указанного хранилища.

```sql
SYSTEM CLEAR|DROP SCHEMA CACHE [FOR File | S3 | URL | HDFS | Azure]
```

Требуется привилегия `SYSTEM DROP SCHEMA CACHE`.

**Пример**

```sql
SELECT * FROM file('data.csv') FORMAT Null;
SELECT storage, format, schema FROM system.schema_inference_cache;
```

```response
   ┌─storage─┬─format─┬─schema────────────────────────────────┐
1. │ File    │ CSV    │ a Nullable(Int64), b Nullable(String) │
   └─────────┴────────┴───────────────────────────────────────┘
```

```sql
SYSTEM CLEAR SCHEMA CACHE FOR File;
SELECT count() FROM system.schema_inference_cache;
```

```response
   ┌─count()─┐
1. │       0 │
   └─────────┘
```

## SYSTEM CLEAR|DROP FORMAT SCHEMA CACHE {#system-drop-schema-format}

Очищает кэш для схем, загруженных из [`format_schema_path`](/ru/reference/settings/server-settings/settings/format#format_schema_path).

Поддерживаемые цели:

* Protobuf: удаляет импортированные определения сообщений Protobuf из памяти.
* Files: удаляет кэшированные файлы схем, хранящиеся локально в [`format_schema_path`](/ru/reference/settings/server-settings/settings/format#format_schema_path) и создаваемые, когда `format_schema_source` имеет значение `query`.
  Примечание: если цель не указана, очищаются оба кэша.

```sql
SYSTEM CLEAR|DROP FORMAT SCHEMA CACHE [FOR Protobuf/Files]
```

## SYSTEM FLUSH LOGS {#flush-logs}

Сбрасывает буферизованные сообщение лога в системные таблицы, например `system.query_log`. В основном полезно для отладки, поскольку для большинства системных таблиц интервал сброса по умолчанию составляет 7,5 секунды.
Также создаёт системные таблицы, даже если очередь сообщений пуста.

```sql
SYSTEM FLUSH LOGS [ON CLUSTER cluster_name] [log_name|[database.table]] [, ...]
```

Если не нужно сбрасывать всё, можно сбросить один или несколько отдельных журналов, указав либо их имя, либо соответствующую целевую таблицу:

```sql
SYSTEM FLUSH LOGS query_log, system.query_views_log;
```

## SYSTEM FLUSH ASYNC INSERT QUEUE {#flush-async-insert-queue}

Добавлено в: v23.7.0

Немедленно записывает данные ожидающих [асинхронных вставок](/ru/concepts/features/operations/insert/asyncinserts) в соответствующие таблицы, не дожидаясь истечения тайм-аута буфера. Если список таблиц не указан, оператор возвращает управление после обработки всех данных в очереди, включая пакеты, которые фоновый сброс на диск уже забрал из очереди. Если список таблиц указан, записываются только вставки в эти таблицы, а оператор ожидает только те пакеты, которые сам забрал из очереди. Если данные вставки не удаётся записать (например, их не удаётся разобрать), оператор не завершается с ошибкой: строки этой вставки не вставляются, а ошибка записывается в [`system.asynchronous_insert_log`](/ru/reference/system-tables/asynchronous_insert_log). Ожидающие вставки отображаются в [`system.asynchronous_inserts`](/ru/reference/system-tables/asynchronous_inserts).

```sql
SYSTEM FLUSH ASYNC INSERT QUEUE [ON CLUSTER cluster_name] [[db.]table [, ...]]
```

Требуется привилегия `SYSTEM FLUSH ASYNC INSERT QUEUE`.

**Пример**

```sql
CREATE TABLE t (x UInt64) ENGINE = MergeTree ORDER BY x;
INSERT INTO t SETTINGS async_insert = 1, wait_for_async_insert = 0, async_insert_use_adaptive_busy_timeout = 0, async_insert_busy_timeout_max_ms = 600000 VALUES (1), (2);
SELECT table, total_bytes FROM system.asynchronous_inserts;
```

```response
   ┌─table─┬─total_bytes─┐
1. │ t     │           8 │
   └───────┴─────────────┘
```

```sql
SYSTEM FLUSH ASYNC INSERT QUEUE t;
SELECT count() FROM t;
```

```response
   ┌─count()─┐
1. │       2 │
   └─────────┘
```

## SYSTEM RELOAD CONFIG {#reload-config}

Перезагружает конфигурацию ClickHouse. Используется, когда конфигурация хранится в ZooKeeper. Обратите внимание, что `SYSTEM RELOAD CONFIG` не перезагружает конфигурацию `USER`, хранящуюся в ZooKeeper: эта команда перезагружает только конфигурацию `USER`, которая хранится в `users.xml`. Чтобы перезагрузить всю конфигурацию `USER`, используйте `SYSTEM RELOAD USERS`

```sql
SYSTEM RELOAD CONFIG [ON CLUSTER cluster_name]
```

## SYSTEM RELOAD USERS {#reload-users}

Перезагружает все хранилища доступа, включая: users.xml, локальное дисковое хранилище доступа и реплицируемое (в ZooKeeper) хранилище доступа.

```sql
SYSTEM RELOAD USERS [ON CLUSTER cluster_name]
```

## SYSTEM RECONNECT ZOOKEEPER {#reconnect-zookeeper}

Добавлено в: v25.10.0

Закрывает сеанс сервера с основным ZooKeeper (ClickHouse Keeper), после чего сервер открывает новый сеанс. Сеансы со вспомогательными экземплярами ZooKeeper сохраняются. Сеансы отображаются в [`system.zookeeper_connection`](/ru/reference/system-tables/zookeeper_connection).

```sql
SYSTEM RECONNECT ZOOKEEPER [ON CLUSTER cluster_name]
```

Требуется привилегия `SYSTEM RECONNECT ZOOKEEPER`.

## SYSTEM RESET DDL WORKER {#reset-ddl-worker}

Добавлено в: v26.2.0

Запрашивает сброс воркера, который выполняет на этом сервере запросы [распределённого DDL](/ru/reference/statements/distributed-ddl) (`ON CLUSTER`), до состояния на момент запуска сервера: воркер забывает обработанные или пропущенные им записи очереди и заново считывает очередь DDL из ZooKeeper. Оператор сразу возвращает управление; сброс воркера выполняется в фоновом режиме до того, как он снова начнёт обрабатывать очередь. Записи, уже выполненные на этом сервере, повторно не выполняются.

```sql
SYSTEM RESET DDL WORKER [ON CLUSTER cluster_name]
```

Требуется привилегия `SYSTEM RESET DDL WORKER`.

## SYSTEM JEMALLOC PURGE {#jemalloc-purge}

Заставляет аллокатор памяти `jemalloc` вернуть операционной системе удерживаемую им неиспользуемую память (выполняет очистку неиспользуемых грязных страниц во всех своих аренах).

```sql
SYSTEM JEMALLOC PURGE [ON CLUSTER cluster_name]
```

Требуется привилегия `SYSTEM JEMALLOC`. В сборке без `jemalloc` команда завершается с ошибкой `SUPPORT_IS_DISABLED`.

## SYSTEM JEMALLOC FLUSH PROFILE {#jemalloc-flush-profile}

Добавлено в: v24.1.0

Записывает текущий профиль кучи `jemalloc` в файл в каталоге `/tmp` на сервере и возвращает путь к этому файлу в столбце `filename`. При использовании `ON CLUSTER` каждый сервер записывает собственный файл, а оператор вместо путей возвращает статус выполнения запроса на каждом сервере в формате, заданном настройкой [`distributed_ddl_output_mode`](/ru/reference/settings/session-settings/distributed-ddl#distributed_ddl_output_mode). Настройка [`jemalloc_profile_text_output_format`](/ru/reference/settings/session-settings/jemalloc-profile#jemalloc_profile_text_output_format) определяет формат вывода: свёрнутые стеки (`collapsed`, по умолчанию, суффикс файла `.collapsed`), символизированный профиль (`symbolized`, суффикс `.symbolized`) или необработанный профиль (`raw`). Профиль содержит выборочные выделения памяти, собранные за то время, пока профилировщик памяти кучи включен настройкой сервера [`jemalloc_enable_global_profiler`](/ru/reference/settings/server-settings/settings/jemalloc-enable#jemalloc_enable_global_profiler) или (для отдельного запроса) настройкой [`jemalloc_enable_profiler`](/ru/reference/settings/session-settings/jemalloc#jemalloc_enable_profiler). См. раздел [Сброс профилей кучи на диск](/ru/concepts/features/performance/allocation-profiling#flushing-heap-profiles).

```sql
SYSTEM JEMALLOC FLUSH PROFILE [ON CLUSTER cluster_name]
```

Требуется привилегия `SYSTEM JEMALLOC`. В сборке без `jemalloc` команда завершается с ошибкой `SUPPORT_IS_DISABLED`.

**Пример**

```sql
SYSTEM JEMALLOC FLUSH PROFILE;
```

```response
   ┌─filename──────────────────────────────────────────┐
1. │ /tmp/jemalloc_clickhouse.3654128.0.heap.collapsed │
   └───────────────────────────────────────────────────┘
```

## SYSTEM JEMALLOC ENABLE|DISABLE PROFILE {#jemalloc-enable-disable-profile}

Добавлено в: v24.1.0

Больше не поддерживается: команды `SYSTEM JEMALLOC ENABLE PROFILE` и `SYSTEM JEMALLOC DISABLE PROFILE` завершаются с ошибкой. Чтобы включить профилировщик памяти кучи, используйте настройку сервера [`jemalloc_enable_global_profiler`](/ru/reference/settings/server-settings/settings/jemalloc-enable#jemalloc_enable_global_profiler), а для отдельного запроса — настройку [`jemalloc_enable_profiler`](/ru/reference/settings/session-settings/jemalloc#jemalloc_enable_profiler).

```sql
SYSTEM JEMALLOC ENABLE PROFILE
SYSTEM JEMALLOC DISABLE PROFILE
```

## SYSTEM INSTRUMENT {#instrument}

Управляет точками инструментирования с помощью возможности XRay в LLVM, доступной при сборке ClickHouse с `ENABLE_XRAY=1`.
Это позволяет выполнять отладку и профилирование в продакшне без изменения исходного кода и с минимальными накладными расходами.
Если не добавлена ни одна точка инструментирования, потери производительности пренебрежимо малы, поскольку добавляется лишь дополнительный переход на ближайший
адрес в прологе и эпилоге тех функций, которые длиннее 200 инструкций.

### SYSTEM INSTRUMENT ADD {#instrument-add}

Добавляет новую точку инструментирования. Функции, для которых включено инструментирование, можно просматривать в системной таблице [`system.instrumentation`](/ru/reference/system-tables/instrumentation). Для одной и той же функции можно добавить несколько обработчиков, и они будут выполняться в порядке добавления.
Функции для инструментирования можно получить из системной таблицы [`system.symbols`](/ru/reference/system-tables/symbols).

Существует три типа обработчиков, которые можно добавить к функциям:

**Синтаксис**

```sql
SYSTEM INSTRUMENT ADD FUNCTION HANDLER [ARGUMENTS]
```

где `FUNCTION` — это любая функция или её подстрока, например `QueryMetricLog::startQuery`, а обработчик — один из следующих

#### LOG {#instrument-add-log}

Выводит текст, переданный в качестве аргумента, и трассировку стека при `ENTRY` или `EXIT` функции.

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' LOG ENTRY 'this is a log printed at entry'
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' LOG EXIT 'this is a log printed at exit'
```

#### SLEEP {#instrument-add-sleep}

Приостанавливает выполнение на фиксированное количество секунд либо при `ENTRY`, либо при `EXIT`:

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' SLEEP ENTRY 0.5
```

или для случайного числа секунд с равномерным распределением, указав минимальное и максимальное значения через пробел:

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' SLEEP ENTRY 0 1
```

#### PROFILE {#instrument-add-profile}

Измеряет время, затраченное между `ENTRY` и `EXIT` при выполнении функции.
Результат профилирования сохраняется в [`system.trace_log`](/ru/reference/system-tables/trace_log) и может быть преобразован
в [формат трассировки событий Chrome](/ru/reference/system-tables/trace_log#chrome-event-trace-format).

```sql
SYSTEM INSTRUMENT ADD 'QueryMetricLog::startQuery' PROFILE
```

### SYSTEM INSTRUMENT REMOVE {#instrument-remove}

Удаляет либо одну точку инструментирования с помощью:

```sql
SYSTEM INSTRUMENT REMOVE ID
```

все их с помощью ключевого слова `ALL`:

```sql
SYSTEM INSTRUMENT REMOVE ALL
```

набор идентификаторов из подзапроса:

```sql
SYSTEM INSTRUMENT REMOVE (SELECT id FROM system.instrumentation WHERE handler = 'log')
```

или все точки инструментирования, соответствующие указанному function&#95;name:

```sql
SYSTEM INSTRUMENT REMOVE 'QueryMetricLog::startQuery'
```

Информацию о точках инструментирования можно получить из системной таблицы [`system.instrumentation`](/ru/reference/system-tables/instrumentation).

## Управление distributed таблицами {#managing-distributed-tables}

ClickHouse может работать с [distributed](/ru/reference/engines/table-engines/special/distributed) таблицами. Когда пользователь вставляет данные в эти таблицы, ClickHouse сначала создаёт очередь данных, которые должны быть отправлены на узлы кластера, а затем асинхронно отправляет их. Вы можете управлять обработкой очереди с помощью запросов [`STOP DISTRIBUTED SENDS`](#stop-distributed-sends), [FLUSH DISTRIBUTED](#flush-distributed) и [`START DISTRIBUTED SENDS`](#start-distributed-sends). Вы также можете синхронно вставлять распределённые данные с помощью настройки [`distributed_foreground_insert`](/ru/reference/settings/session-settings/distributed#distributed_foreground_insert).

### SYSTEM STOP DISTRIBUTED SENDS {#stop-distributed-sends}

Отключает фоновое распределение данных при вставке в distributed-таблицы.

```sql
SYSTEM STOP DISTRIBUTED SENDS [db.]<distributed_table_name> [ON CLUSTER cluster_name]
```

<Note>
  Если параметр [`prefer_localhost_replica`](/ru/reference/settings/session-settings/prefer#prefer_localhost_replica) включен (по умолчанию), данные всё равно будут вставлены в локальный сегмент.
</Note>

### SYSTEM FLUSH DISTRIBUTED {#flush-distributed}

Принудительно заставляет ClickHouse синхронно отправлять данные на узлы кластера. Если какие-либо узлы недоступны, ClickHouse генерирует исключение и останавливает выполнение запроса. Вы можете повторять запрос, пока он не завершится успешно; это произойдёт, когда все узлы снова будут в сети.

Вы также можете переопределить некоторые настройки с помощью предложения `SETTINGS`; это может быть полезно, чтобы обойти временные ограничения, например `max_concurrent_queries_for_all_users` или `max_memory_usage`.

```sql
SYSTEM FLUSH DISTRIBUTED [db.]<distributed_table_name> [ON CLUSTER cluster_name] [SETTINGS ...]
```

<Note>
  Каждый блок, ожидающий отправки, хранится на диске с настройками из исходного запроса INSERT, поэтому иногда может понадобиться переопределить эти настройки.
</Note>

### SYSTEM START DISTRIBUTED SENDS {#start-distributed-sends}

Включает фоновую отправку данных при вставке в distributed таблицы.

```sql
SYSTEM START DISTRIBUTED SENDS [db.]<distributed_table_name> [ON CLUSTER cluster_name]
```

### SYSTEM STOP LISTEN {#stop-listen}

Закрывает сокет и корректно завершает существующие соединения с сервером на указанном порту по указанному протоколу.

Однако, если соответствующие настройки протокола не были указаны в конфигурации clickhouse-server, эта команда не даст никакого эффекта.

```sql
SYSTEM STOP LISTEN [ON CLUSTER cluster_name] [QUERIES ALL | QUERIES DEFAULT | QUERIES CUSTOM | TCP | TCP WITH PROXY | TCP SECURE | HTTP | HTTPS | MYSQL | GRPC | POSTGRESQL | PROMETHEUS | CUSTOM 'protocol']
```

* Если указан модификатор `CUSTOM 'protocol'`, будет остановлен пользовательский протокол с указанным именем, определённый в разделе `protocols` конфигурации сервера.
* Если указан модификатор `QUERIES ALL [EXCEPT .. [,..]]`, будут остановлены все протоколы, кроме указанных в предложении `EXCEPT`.
* Если указан модификатор `QUERIES DEFAULT [EXCEPT .. [,..]]`, будут остановлены все протоколы по умолчанию, кроме указанных в предложении `EXCEPT`.
* Если указан модификатор `QUERIES CUSTOM [EXCEPT .. [,..]]`, будут остановлены все пользовательские протоколы, кроме указанных в предложении `EXCEPT`.

### SYSTEM START LISTEN {#start-listen}

Позволяет устанавливать новые соединения по указанным протоколам.

Однако если сервер на указанном порту и по указанному протоколу не был остановлен с помощью команды SYSTEM STOP LISTEN, эта команда не возымеет никакого эффекта.

```sql
SYSTEM START LISTEN [ON CLUSTER cluster_name] [QUERIES ALL | QUERIES DEFAULT | QUERIES CUSTOM | TCP | TCP WITH PROXY | TCP SECURE | HTTP | HTTPS | MYSQL | GRPC | POSTGRESQL | PROMETHEUS | CUSTOM 'protocol']
```

## Управление таблицами MergeTree {#managing-mergetree-tables}

ClickHouse позволяет управлять фоновыми процессами в таблицах [MergeTree](/ru/reference/engines/table-engines/mergetree-family/mergetree).

### SYSTEM STOP MERGES {#stop-merges}

<CloudNotSupportedBadge />

Позволяет остановить фоновые слияния для таблиц семейства MergeTree:

```sql
SYSTEM STOP MERGES [ON CLUSTER cluster_name] [ON VOLUME <volume_name> | [db.]merge_tree_family_table_name]
```

<Note>
  `DETACH / ATTACH` для таблицы запустит фоновые слияния, даже если ранее они были остановлены для всех таблиц семейства MergeTree.
</Note>

Без `ON VOLUME` слияния останавливаются только для таблиц, существующих на момент выполнения оператора, и только до перезапуска сервера:

* Без имени таблицы (и без `ON VOLUME`) слияния останавливаются для всех таблиц семейства MergeTree, существующих на этот момент. Для таблиц, созданных позже, слияния по-прежнему выполняются.
* Если указано имя таблицы, оператор возвращает `Ok.`, даже если такой таблицы не существует, и никак не влияет на таблицу с этим именем, созданную позже.
* Состояние остановки хранится в памяти. После перезапуска сервера слияния снова выполняются для всех таблиц.

Пока слияния для non-replicated таблицы семейства MergeTree остановлены с помощью `SYSTEM STOP MERGES [db.]merge_tree_family_table_name`, `OPTIMIZE TABLE` для этой таблицы также завершается ошибкой `Cancelled merging parts. (ABORTED)` — как с `FINAL`, так и без него. Сначала выполните `SYSTEM START MERGES` для этой таблицы.

### SYSTEM START MERGES {#start-merges}

<CloudNotSupportedBadge />

Позволяет запускать фоновые слияния для таблиц семейства MergeTree:

```sql
SYSTEM START MERGES [ON CLUSTER cluster_name] [ON VOLUME <volume_name> | [db.]merge_tree_family_table_name]
```

### SYSTEM SCHEDULE MERGE {#schedule-merge}

Добавлено в: v26.5.0

<ExperimentalBadge />

Планирует слияние указанных частей данных таблицы. Слияние выполняется в фоновом режиме. Можно также указать часть, которую создаст ранее запланированное слияние, — так можно запланировать несколько слияний друг за другом. Части должны быть соседними частями одной партиции, перечисляться по порядку и укладываться в ограничения на размер, действующие для остальных фоновых слияний, например [`max_bytes_to_merge_at_max_space_in_pool`](/ru/reference/settings/merge-tree-settings/max-bytes#max_bytes_to_merge_at_max_space_in_pool). Пока запланированное слияние не удовлетворяет этим условиям, не выполняется ни оно, ни слияния, запланированные после него. Запланированные слияния хранятся только в памяти сервера и теряются при его перезапуске. Они привязаны к имени таблицы: после переименования таблицы или её базы данных они не выполняются, пока таблице не вернут прежнее имя.

<Note>
  Это экспериментальная возможность. `SYSTEM SCHEDULE MERGE` и `SYSTEM SYNC MERGES` работают только для таблиц семейства MergeTree, у которых экспериментальная настройка MergeTree [`merge_selector_algorithm`](/ru/reference/settings/merge-tree-settings/merge-selector#merge_selector_algorithm) имеет значение `'Manual'`; для остальных таблиц они завершаются ошибкой `BAD_ARGUMENTS`. Обычные фоновые слияния такой таблицы объединяют только запланированные части; слияния по TTL по-прежнему выполняются независимо, а `OPTIMIZE TABLE ... FINAL` по-прежнему объединяет все части.
</Note>

```sql
SYSTEM SCHEDULE MERGE [ON CLUSTER cluster_name] [db.]table PARTS 'part_name' [, ...]
```

### SYSTEM SYNC MERGES {#sync-merges}

Добавлено в: v26.5.0

<ExperimentalBadge />

Ожидает завершения всех слияний, запланированных для таблицы с помощью [`SYSTEM SCHEDULE MERGE`](#schedule-merge). Если задан параметр `max_execution_time`, по истечении этого времени команда завершается с ошибкой `TIMEOUT_EXCEEDED`. Требования к ней такие же, как к `SYSTEM SCHEDULE MERGE`.

```sql
SYSTEM SYNC MERGES [ON CLUSTER cluster_name] [db.]table
```

Для выполнения обоих операторов требуется привилегия `SYSTEM MERGES` на таблицу.

**Пример**

```sql
CREATE TABLE t (x UInt64) ENGINE = MergeTree ORDER BY x SETTINGS merge_selector_algorithm = 'Manual';
INSERT INTO t VALUES (1);
INSERT INTO t VALUES (2);
INSERT INTO t VALUES (3);
SYSTEM SCHEDULE MERGE t PARTS 'all_1_1_0', 'all_2_2_0';
SYSTEM SCHEDULE MERGE t PARTS 'all_1_2_1', 'all_3_3_0';
SYSTEM SYNC MERGES t;
SELECT name FROM system.parts WHERE database = currentDatabase() AND table = 't' AND active;
```

```response
   ┌─name──────┐
1. │ all_1_3_2 │
   └───────────┘
```

### SYSTEM STOP TTL MERGES {#stop-ttl-merges}

<CloudNotSupportedBadge />

### SYSTEM STOP REPLICATED DDL QUERIES {#stop-replicated-ddl-queries}

Временно запрещает выполнение DDL-запросов в базах данных [`Replicated`](/ru/reference/engines/database-engines/replicated), а также распределённых DDL-запросов `ON CLUSTER` на сервере, где выполняется команда:

```sql
SYSTEM STOP REPLICATED DDL QUERIES [ON CLUSTER cluster_name]
```

Пока выполнение DDL-запросов остановлено:

* DDL-запросы в базах данных `Replicated` завершаются ошибкой `QUERY_IS_PROHIBITED`. Это относится и к DDL-запросам, которые были инициированы на этом сервере и уже поставлены в очередь, но ещё не закоммичены.
* Все DDL-запросы с `ON CLUSTER`, кроме запросов `SYSTEM`, инициированные на этом сервере, завершаются ошибкой `QUERY_IS_PROHIBITED` независимо от движка целевой базы данных (а не только в базах данных `Replicated`).
* DDL-запросы, инициированные на других репликах, по-прежнему применяются на этом сервере: оператор лишь запрещает этому серверу инициировать DDL, но не останавливает обработку очереди DDL.

Без `ON CLUSTER` оператор действует только на локальном сервере. С `ON CLUSTER` он выполняется на каждом хосте кластера (запросы `SYSTEM` не отклоняются, пока DDL-запросы остановлены, поэтому `SYSTEM START REPLICATED DDL QUERIES ON CLUSTER` продолжает работать).

Запрет не сохраняется надолго: он хранится в памяти и в эфемерных узлах Keeper и снимается при перезапуске сервера. Не полагайтесь на него как на надёжную защиту на время обслуживания; при необходимости выполните оператор повторно после перезапуска.

Для выполнения оператора требуется глобальная привилегия `SYSTEM REPLICATION QUEUES`.

### SYSTEM SYNC REPLICA {#sync-replica}

Ожидать, пока таблица `ReplicatedMergeTree` синхронизируется с другими репликами в кластере, но не дольше `receive_timeout` секунд.

```sql
SYSTEM SYNC REPLICA [ON CLUSTER cluster_name] [db.]replicated_merge_tree_family_table_name [IF EXISTS] [STRICT | LIGHTWEIGHT [FROM 'srcReplica1'[, 'srcReplica2'[, ...]]] | PULL]
```

После выполнения этого оператора `[db.]replicated_merge_tree_family_table_name` получает команды из общего журнала репликации в свою очередь репликации, а затем запрос ждёт, пока реплика не обработает все полученные команды. Поддерживаются следующие модификаторы:

* С `IF EXISTS` (доступно начиная с 25.6) запрос не сгенерирует ошибку, если таблица не существует. Это полезно при добавлении новой реплики в кластер, когда она уже входит в конфигурацию кластера, но таблица для неё всё ещё создаётся и синхронизируется.
* Если указан модификатор `STRICT`, запрос ждёт, пока очередь репликации не опустеет. Вариант `STRICT` может так и не завершиться успешно, если в очереди репликации постоянно появляются новые записи.
* Если указан модификатор `LIGHTWEIGHT`, запрос ждёт только обработки записей `GET_PART`, `ATTACH_PART`, `DROP_RANGE`, `REPLACE_RANGE` и `DROP_PART`.
  Кроме того, модификатор LIGHTWEIGHT поддерживает необязательное выражение FROM &#39;srcReplicas&#39;, где &#39;srcReplicas&#39; — это список имён исходных реплик, разделённых запятыми. Это расширение позволяет точнее настраивать синхронизацию, ограничивая её задачами репликации только от указанных исходных реплик.
* Если указан модификатор `PULL`, запрос получает новые записи очереди репликации из ZooKeeper, но не ждёт их обработки.

Инициализация очереди репликации на основе данных ZooKeeper выполняется так же, как и для оператора `ATTACH TABLE`. На короткое время таблица будет недоступна для выполнения любых операций.

### SYSTEM RESTORE REPLICA {#restore-replica}

Восстанавливает реплику, если данные [возможно] присутствуют, но метаданные ZooKeeper утеряны.

Работает только с таблицами `ReplicatedMergeTree` в режиме только для чтения.

Запрос можно выполнить после:

* Потери корневого пути ZooKeeper `/`.
* Потери пути реплик `/replicas`.
* Потери пути отдельной реплики `/replicas/replica_name/`.

Реплика подключает найденные локально части и отправляет информацию о них в ZooKeeper.
Части, присутствовавшие на реплике до потери метаданных, не загружаются повторно с других реплик, если они не устарели (то есть восстановление реплики не означает повторную загрузку всех данных по сети).

<Note>
  Части во всех состояниях перемещаются в папку `detached/`. Части, которые были активны до потери данных (закоммиченные), подключаются.
</Note>

Оператор также очищает кэши данных на уровне всего сервера: восстановленные части получают новые имена, которые могут совпадать с прежними именами и путями других частей, поэтому записи в кэше для этих имён оказались бы устаревшими.

Это затрагивает все таблицы на сервере, а не только восстановленную: запросам к ним придётся заново заполнять кэши. При использовании `ON CLUSTER` кэши очищаются на каждом сервере, где восстанавливается реплика.

Очищаются следующие кэши:

* [кэш меток](#drop-mark-cache)
* [кэш несжатых данных](#drop-uncompressed-cache)
* [кэш первичного индекса](#drop-primary-index-cache)
* [кэш статистики](#drop-statistics-cache)
* [кэш индексных меток](#drop-index-mark-cache)
* [кэш несжатых данных индексов](#drop-index-uncompressed-cache)
* [кэш индекса векторного сходства](#drop-vector-similarity-index-cache)
* [кэши текстового индекса](#drop-text-index-caches)
* [кэш mmap](#drop-mmap-cache)
* [кэш страниц](#drop-page-cache)
* [кэш столбцов](#drop-columns-cache)
* [кэш условий запросов](#drop-query-condition-cache)
* [кэш заголовков шифрования](#drop-encryption-headers-cache)
* кэши битмапов удалений `UNIQUE KEY`

[Кеш запросов](#drop-query-cache) и [файловый кэш](#drop-filesystem-cache) при этом сохраняются.

### SYSTEM RESTORE DATABASE REPLICA {#restore-database-replica}

Восстанавливает реплику, если данные [возможно] сохранились, но метаданные ZooKeeper утеряны.

**Синтаксис**

```sql
SYSTEM RESTORE DATABASE REPLICA repl_db [ON CLUSTER cluster]
```

**Пример**

```sql
CREATE DATABASE repl_db
ENGINE=Replicated("/clickhouse/repl_db", shard1, replica1);

CREATE TABLE repl_db.test_table (n UInt32)
ENGINE = ReplicatedMergeTree
ORDER BY n PARTITION BY n % 10;

-- zookeeper_delete_path("/clickhouse/repl_db", recursive=True) <- потеря корневого узла.

SYSTEM RESTORE DATABASE REPLICA repl_db;
```

**Синтаксис**

```sql
SYSTEM RESTORE REPLICA [db.]replicated_merge_tree_family_table_name [ON CLUSTER cluster_name]
```

Альтернативный синтаксис:

```sql
SYSTEM RESTORE REPLICA [ON CLUSTER cluster_name] [db.]replicated_merge_tree_family_table_name
```

**Пример**

Создание таблицы на нескольких серверах. Если метаданные реплики в ZooKeeper утеряны, таблица подключится в режиме только для чтения, поскольку метаданные отсутствуют. Последний запрос нужно выполнить на каждой реплике.

```sql
CREATE TABLE test(n UInt32)
ENGINE = ReplicatedMergeTree('/clickhouse/tables/test/', '{replica}')
ORDER BY n PARTITION BY n % 10;

INSERT INTO test SELECT * FROM numbers(1000);

-- zookeeper_delete_path("/clickhouse/tables/test", recursive=True) <- потеря корня.

SYSTEM RESTART REPLICA test;
SYSTEM RESTORE REPLICA test;
```

Ещё один способ:

```sql
SYSTEM RESTORE REPLICA test ON CLUSTER cluster;
```

## Управление Refreshable Materialized Views {#managing-refreshable-materialized-views}

Команды для управления фоновыми задачами, выполняемыми [Refreshable Materialized Views](/ru/reference/statements/create/view#refreshable-materialized-view)

При работе с ними отслеживайте [`system.view_refreshes`](/ru/reference/system-tables/view_refreshes).

### SYSTEM STOP [REPLICATED] VIEW, STOP VIEWS {#stop-view-stop-views}

Останавливает периодическое обновление указанного представления или всех обновляемых представлений. Если обновление уже выполняется, оно также будет отменено.

Если представление находится в базе данных Replicated или Shared, `STOP VIEW` действует только на текущую реплику, а `STOP REPLICATED VIEW` — на все реплики.

<Note>
  Состояние остановки не сохраняется после перезапуска сервера. После перезапуска представления возобновят обновление в соответствии с настроенным для них расписанием.
  В базах данных Replicated или Shared `SYSTEM STOP VIEW` действует только на текущую реплику. Чтобы остановить обновления на всех репликах, используйте `SYSTEM STOP REPLICATED VIEW`.
</Note>

```sql
SYSTEM STOP VIEW [db.]name
```

```sql
SYSTEM STOP VIEWS
```

### SYSTEM START [REPLICATED] VIEW, START VIEWS {#start-view-start-views}

Включает периодическое обновление для указанного представления или для всех обновляемых представлений. Немедленное обновление не запускается.

Если представление находится в базе данных Replicated или Shared, `START VIEW` отменяет действие `STOP VIEW`, а `START REPLICATED VIEW` — действие `STOP REPLICATED VIEW`. `START VIEW` также отменяет действие `PAUSE VIEW`.

```sql
SYSTEM START VIEW [db.]name
```

```sql
SYSTEM START VIEWS
```

### SYSTEM PAUSE VIEW, PAUSE VIEWS {#pause-view-pause-views}

Отключает периодическое обновление указанного представления или всех обновляемых представлений.
В отличие от `SYSTEM STOP VIEW`, команда `SYSTEM PAUSE VIEW` не прерывает уже выполняющееся обновление: текущему обновлению даётся завершиться, а предотвращаются только последующие обновления.

Отменить это действие можно с помощью `SYSTEM START VIEW` или `SYSTEM START VIEWS`.

<Note>
  Состояние паузы не сохраняется после перезапуска сервера. После перезапуска представления возобновят обновление по настроенному расписанию.
  В базах данных Replicated или Shared команда `SYSTEM PAUSE VIEW` влияет только на текущую реплику.
</Note>

```sql
SYSTEM PAUSE VIEW [db.]name
```

```sql
SYSTEM PAUSE VIEWS
```

### SYSTEM REFRESH VIEW {#refresh-view}

Немедленно запускает внеплановое обновление указанного VIEW.

Если VIEW находится в базе данных Replicated или Shared, запрос передаётся всем репликам: обновление может выполняться на другой реплике, например, если на текущей оно остановлено.

```sql
SYSTEM REFRESH VIEW [db.]name
```

### SYSTEM WAIT VIEW {#wait-view}

Ожидает завершения текущего обновления, включая запланированное обновление, которое ещё ожидает истечения задержки `refresh_coordination_jitter_ms`. Если обновление не выполняется и не запланировано, команда сразу возвращает результат. Если последняя попытка обновления завершилась неудачей, возвращается ошибка.

Можно использовать сразу после создания нового refreshable materialized представления (без ключевого слова EMPTY), чтобы дождаться завершения первоначального обновления.

Если представление находится в базе данных Replicated или Shared, команда также ожидает завершения обновления, которое выполняется или было запрошено на другой реплике.

```sql
SYSTEM WAIT VIEW [db.]name
```

### SYSTEM CANCEL VIEW {#cancel-view}

Если на текущей реплике для указанного представления выполняется обновление, прервите его и отмените. В противном случае ничего не произойдет.

```sql
SYSTEM CANCEL VIEW [db.]name
```

## Управление фоновой активностью {#managing-background-activity}

Команды, не зависящие от движка, для управления фоновой активностью одной таблицы или всех таких таблиц на сервере одновременно. Они применяются к:

* [Refreshable materialized views](/ru/reference/statements/create/view#refreshable-materialized-view) (периодическому обновлению), и
* потоковым движкам таблиц, непрерывно считывающим данные из внешнего источника: [Kafka](/ru/reference/engines/table-engines/integrations/kafka), [RabbitMQ](/ru/reference/engines/table-engines/integrations/rabbitmq), [NATS](/ru/reference/engines/table-engines/integrations/nats), [S3Queue](/ru/reference/engines/table-engines/integrations/s3queue) и [AzureQueue](/ru/reference/engines/table-engines/integrations/azure-queue).

Для refreshable materialized view каждый глагол является псевдонимом соответствующей команды `SYSTEM ... VIEW` из раздела [Управление Refreshable Materialized Views](#managing-refreshable-materialized-views), поэтому `SYSTEM STOP [db.]name` работает точно так же, как `SYSTEM STOP VIEW [db.]name`, и так далее.

Варианты для отдельной таблицы и с подстановочным знаком различаются обработкой таблиц без фоновой активности. Вариант для отдельной таблицы (`SYSTEM STOP [db.]table`) генерирует ошибку, если указанная таблица не является ни потоковым движком, ни refreshable materialized view. Вариант с подстановочным знаком молча пропускает такие таблицы, поэтому его всегда можно безопасно выполнять.

`STOP` и `CANCEL` прерывают получение данных при первой возможности. Для [Kafka](/ru/reference/engines/table-engines/integrations/kafka), [RabbitMQ](/ru/reference/engines/table-engines/integrations/rabbitmq) и [NATS](/ru/reference/engines/table-engines/integrations/nats) они прекращают чтение из источника, но не прерывают уже начавшуюся вставку: блок, уже записываемый в materialized views, всё равно дописывается и фиксируется. [S3Queue](/ru/reference/engines/table-engines/integrations/s3queue) и [AzureQueue](/ru/reference/engines/table-engines/integrations/azure-queue) выполняют чтение и вставку в рамках одного конвейера. При включённой дедупликации (по умолчанию) вставка также отменяется, а файлы позже обрабатываются повторно. При отключённой дедупликации текущий батч, напротив, завершается и фиксируется (как и для перечисленных выше движков), чтобы избежать дублирования строк. Данные, которые были прочитаны, но ещё не зафиксированы, позже считываются повторно, поэтому ничего не теряется, кроме core NATS (без JetStream), который не может повторно доставить эти данные и отбрасывает их.

`PAUSE` не прерывает выполняющуюся вставку, поэтому обычно данные не теряются. Исключение — core NATS: приостановка прекращает получение данных и отбрасывает сообщения, которые он уже получил, но ещё не вставил, поскольку core NATS не может доставить их повторно.

<Note>
  Ни одно из этих состояний не сохраняется после перезапуска сервера. После перезапуска refreshable views возобновляют работу по настроенному расписанию, а потоковые движки возобновляют получение данных.
</Note>

### SYSTEM STOP {#stop-background}

Остановить фоновую активность: прервать выполняющиеся задачи и не запускать новые до выполнения `SYSTEM START`. Эквивалентно `PAUSE` + `CANCEL`.

```sql
SYSTEM STOP [db.]table
SYSTEM STOP ALL BACKGROUND
```

### SYSTEM START {#start-background}

Возобновляет работу после выполнения `SYSTEM STOP` или `SYSTEM PAUSE`. Текущая активность не прерывается.

```sql
SYSTEM START [db.]table
SYSTEM START ALL BACKGROUND
```

### SYSTEM PAUSE {#pause-background}

Приостанавливает дальнейшую фоновую активность, но позволяет текущим операциям завершиться.

```sql
SYSTEM PAUSE [db.]table
SYSTEM PAUSE ALL BACKGROUND
```

### SYSTEM CANCEL {#cancel-background}

Прерывает только текущую выполняемую операцию, не блокируя последующие — таблица продолжает обновляться или потреблять данные по расписанию. Если никакая операция не выполняется, ничего не происходит.

```sql
SYSTEM CANCEL [db.]table
SYSTEM CANCEL ALL BACKGROUND
```

### SYSTEM REFRESH {#refresh-background}

Запускает один дополнительный цикл вне расписания. Для потоковой таблицы выполняется немедленно и однократно, даже если таблица остановлена или приостановлена. Для refreshable materialized VIEW действует аналогично `SYSTEM REFRESH VIEW`: если VIEW остановлено, запрос на обновление запоминается и выполняется один раз после запуска с помощью `SYSTEM START` или передачи управления другой реплике.

```sql
SYSTEM REFRESH [db.]table
SYSTEM REFRESH ALL BACKGROUND
```

### Привилегии {#background-privileges}

Для каждой команды требуется привилегия соответствующего движка: `SYSTEM VIEWS` для refreshable materialized view и `SYSTEM STREAMING ENGINES` для потоковой таблицы. Обе привилегии являются дочерними по отношению к `SYSTEM BACKGROUND`, поэтому предоставление `SYSTEM BACKGROUND` позволяет управлять фоновой активностью всех таких таблиц. Варианты `ALL BACKGROUND` применяются только к таблицам, которыми пользователь имеет право управлять, и без уведомления пропускают остальные.

## SYSTEM FLUSH OBJECT STORAGE QUEUE {#flush-object-storage-queue}

Блокирует выполнение до тех пор, пока указанный файл не будет обработан указанной таблицей [S3Queue](/ru/reference/engines/table-engines/integrations/s3queue) или [AzureQueue](/ru/reference/engines/table-engines/integrations/azure-queue), либо пока для него не будет зафиксирована необратимая ошибка. Если файл уже был обработан, управление возвращается немедленно. Вызывает ошибку, если обработка файла завершилась необратимой ошибкой (все повторные попытки исчерпаны).

```sql
SYSTEM FLUSH OBJECT STORAGE QUEUE [db.]table_name PATH 'path'
```

## SYSTEM RESET FILELOG {#reset-filelog}

Изменяет позицию, с которой таблица [FileLog](/ru/reference/engines/table-engines/special/filelog) продолжает чтение, без необходимости пересоздавать таблицу.

```sql
SYSTEM RESET FILELOG [ON CLUSTER cluster_name] [db.]table_name [FILE 'file_name' [OFFSET n | TO END]]
```

Без `FILE` каждый файл таблицы читается заново с самого начала. С `FILE` затрагивается только указанный файл (имя задаётся так же, как в виртуальном столбце `_filename`): он читается заново с начала, с байта `n` при указании `OFFSET n` (это должно быть начало строки, например значение `_offset`) или, при указании `TO END`, только начиная с данных, дописанных после выполнения команды, — то есть текущее содержимое файла пропускается.

Повторно прочитанные строки снова вставляются в materialized view. Новая позиция сохраняется сразу и не теряется после перезапуска сервера. Команда дожидается завершения фонового чтения и завершается с ошибкой, если из таблицы в этот момент читает `SELECT`-запрос. Для её выполнения требуется привилегия `SYSTEM RESET FILELOG` на таблицу.

## SYSTEM WAIT QUERY RUNNER {#wait-query-runner}

Добавлено в: v26.7.0

Ожидает завершения всех запросов, вставленных к текущему моменту в таблицу [`QueryRunner`](/ru/reference/engines/table-engines/special/query-runner). Команда полезна в асинхронном режиме таблицы, в котором `INSERT` возвращает управление сразу после постановки запросов в очередь. Для таблицы с другим движком команда завершается ошибкой `BAD_ARGUMENTS`.

```sql
SYSTEM WAIT QUERY RUNNER [ON CLUSTER cluster_name] [db.]table
```

Требуется привилегия `SYSTEM WAIT QUERY RUNNER` для таблицы.

## SYSTEM ENABLE|DISABLE FAILPOINT {#failpoint}

Failpoint — это именованные места в коде сервера, куда по требованию можно внедрить сбой: ошибку, задержку или приостановку выполняющегося потока — в целях тестирования. Они перечислены в таблице [`system.fail_points`](/ru/reference/system-tables/fail_points) вместе с их текущим состоянием.

```sql
SYSTEM ENABLE FAILPOINT name
SYSTEM DISABLE FAILPOINT name
SYSTEM DISABLE ALL FAILPOINTS
SYSTEM WAIT FAILPOINT name [PAUSE|RESUME]
SYSTEM NOTIFY FAILPOINT name
```

`SYSTEM ENABLE FAILPOINT` активирует один failpoint; `SYSTEM DISABLE FAILPOINT` деактивирует его и возобновляет все заблокированные на нём потоки, а если failpoint не был включён, не делает ничего.

`SYSTEM DISABLE ALL FAILPOINTS` отключает сразу все failpoint&#39;ы и возобновляет все потоки, заблокированные на failpoint&#39;ах с приостановкой. Этот оператор не принимает имени и идемпотентен, поэтому тестовая среда может с его помощью вернуть сервер в состояние без каких-либо инъекций, не зная, какие именно failpoint&#39;ы включил предыдущий тест. В сборке без поддержки failpoint&#39;ов оператор выполняется успешно и не делает ничего.

`SYSTEM WAIT FAILPOINT ... PAUSE` блокируется до тех пор, пока какой-либо поток не приостановится на указанном failpoint&#39;е с приостановкой (или пока этот failpoint не будет отключён), `... RESUME` блокируется до возобновления приостановленного потока, а `SYSTEM NOTIFY FAILPOINT` возобновляет приостановленные потоки, не отключая failpoint.

Failpoint&#39;ы — это локальное состояние узла, поэтому ни один из этих операторов не принимает предложение `ON CLUSTER`. Для всех них требуется привилегия `SYSTEM FAILPOINT`.
