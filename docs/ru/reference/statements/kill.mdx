На этой странице описаны операторы `KILL QUERY`, `KILL MUTATION`, `KILL TRANSACTION` и `KILL PART_MOVE_TO_SHARD`.

По умолчанию `KILL QUERY` выбрасывает исключение `NOTHING_TO_KILL`, если в `system.processes` нет строк, удовлетворяющих его условию `WHERE`, за исключением строки текущего оператора `KILL`, а `KILL MUTATION` выбрасывает исключение, если в `system.mutations` нет строк, удовлетворяющих его условию `WHERE`. Чтобы при отсутствии совпадений оператор завершался без исключения, установите для параметра [`kill_throw_if_noop`](/ru/operations/settings/settings#kill_throw_if_noop) значение `false`.
`KILL TRANSACTION` и `KILL PART_MOVE_TO_SHARD` никогда не выбрасывают исключение при отсутствии совпадений — они возвращают пустой результат.
При выполнении с `ON CLUSTER` отсутствие совпадений не вызывает исключения, поскольку результаты поиска совпадений не агрегируются по всем хостам.

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

Попытка принудительно завершить выполняющиеся в данный момент запросы.
Запросы для завершения выбираются из таблицы system.processes по критериям, заданным в условии `WHERE` запроса `KILL`.

Примеры:

Сначала нужно получить список незавершённых запросов. Этот SQL-запрос выводит их, начиная с тех, которые выполняются дольше всего:

Список с одного узла ClickHouse:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Список в кластере ClickHouse:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Завершите запрос:

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  Если вы завершаете запрос в ClickHouse Cloud или в самоуправляемом кластере, обязательно используйте предложение `ON CLUSTER [cluster-name]`, чтобы запрос был завершён на всех репликах.
</Tip>

Пользователи в режиме только для чтения могут останавливать только собственные запросы.

Пользователь без привилегии `SELECT` на `system.processes` всё равно может отменить собственный запрос, указав его идентификатор:
`KILL QUERY WHERE query_id = '<id>'`. Если у пользователя нет ни этой привилегии, ни привилегии `KILL QUERY`, попытка отменить запрос,
выполняющийся от имени другого пользователя, не приведёт к его отмене и по умолчанию выбросит исключение `NOTHING_TO_KILL`. Если параметр
[`kill_throw_if_noop`](/ru/operations/settings/settings#kill_throw_if_noop) установлен в `false`, вместо этого не будет возвращено ни одной строки;
пользователю с привилегией `KILL QUERY`, но без указанной привилегии `SELECT`, будет отказано из-за отсутствия `SELECT`.
Для любых других условий `WHERE`, а также для `ON CLUSTER` по-прежнему требуются привилегии, описанные выше.

По умолчанию используется асинхронная версия запросов (`ASYNC`), которая не ждёт подтверждения остановки запросов.

Синхронная версия (`SYNC`) ждёт остановки всех запросов и показывает информацию о каждом процессе по мере его остановки.
Ответ содержит столбец `kill_status`, который может принимать следующие значения:

1. `finished` – Запрос был успешно завершён.
2. `waiting` – Ожидание завершения запроса после отправки ему сигнала на завершение.
3. Другие значения объясняют, почему запрос не удаётся остановить.

Тестовый запрос (`TEST`) только проверяет права пользователя и показывает список запросов для остановки.

## KILL MUTATION {#kill-mutation}

Наличие долго выполняющихся или незавершённых мутаций часто указывает на то, что сервис ClickHouse работает некорректно. Асинхронная природа мутаций может приводить к тому, что они потребляют все доступные ресурсы системы. Вам может потребоваться:

* Приостановить все новые мутации, `INSERT`ы и `SELECT`ы и дождаться обработки очереди мутаций.
* Или вручную завершить некоторые из этих мутаций, отправив команду `KILL`.

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

Пытается отменить и удалить [мутации](/ru/reference/statements/alter/index#mutations), которые выполняются в данный момент. Мутации для отмены выбираются из таблицы [`system.mutations`](/ru/reference/system-tables/mutations) с помощью фильтра, заданного в предложении `WHERE` запроса `KILL`.

Тестовый запрос (`TEST`) лишь проверяет права пользователя и выводит список мутаций, которые будут остановлены.

Примеры:

Получить `count()` незавершённых мутаций:

Количество мутаций на отдельном узле ClickHouse:

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

Количество мутаций в кластере реплик ClickHouse:

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

Запросите список незавершённых мутаций:

Список мутаций на одном узле ClickHouse:

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

Список мутаций в кластере ClickHouse:

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

При необходимости завершите мутации:

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

Запрос полезен, когда мутация зависла и не может завершиться (например, если какая-либо функция в запросе мутации генерирует исключение при применении к данным, содержащимся в таблице).

Изменения, уже внесённые мутацией, не откатываются.

<Note>
  столбец `is_killed=1` (Только в ClickHouse Cloud) в таблице [system.mutations](/ru/reference/system-tables/mutations) не обязательно означает, что мутация полностью завершена. В некоторых случаях мутация может долго оставаться в состоянии, когда `is_killed=1`, а `is_done=0`. Это может происходить, если другая долго выполняющаяся мутация блокирует завершённую мутацию. Это нормальная ситуация.
</Note>

## KILL TRANSACTION {#kill-transaction}

Добавлено в: v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  Этот оператор входит в набор экспериментальных функций.
  Чтобы включить экспериментальную поддержку транзакций, добавьте следующую настройку в [конфигурацию](/ru/concepts/features/configuration/server-config/configuration-files):

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  Подробнее см. на странице [Поддержка транзакций (ACID)](/ru/concepts/features/operations/insert/transactions#transactions-commit-and-rollback).
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

Откатывает выполняющиеся [транзакции](/ru/reference/statements/transactions), отобранные из таблицы [`system.transactions`](/ru/reference/system-tables/transactions) с помощью предложения `WHERE`.
После этого сеанс принудительно завершённой транзакции оказывается в том же состоянии, что и после неудачного запроса (см. описание в [`COMMIT`](/ru/reference/statements/transactions#commit)): пока в нём не будет выполнен `ROLLBACK`, `COMMIT` выбрасывает исключение `INVALID_TRANSACTION`.

Для выполнения оператора требуются привилегия `KILL TRANSACTION` и привилегия `SELECT` на `system.transactions`.
Ответ содержит столбец `kill_status`, который принимает значение `waiting` для откаченной транзакции, а за ним следуют столбцы `tid`, `tid_hash`, `elapsed`, `is_readonly` и `state` из `system.transactions`.

Тестовый запрос (`TEST`) только проверяет права пользователя и выводит список транзакций, которые будут откачены.

Пример:

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

Добавлено в: v21.11.0

<ExperimentalBadge />

<Note>
  Перемещение частей между шардами — экспериментальная возможность, которая включается отдельно для каждой таблицы с помощью настройки MergeTree [`part_moves_between_shards_enable`](/ru/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable).
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

Отменяет перемещения частей между шардами, запущенные с помощью `ALTER TABLE ... MOVE PART ... TO SHARD` и отобранные из таблицы [`system.part_moves_between_shards`](/ru/reference/system-tables/part_moves_between_shards) с помощью предложения `WHERE`.
Отменённое перемещение откатывается в фоновом режиме, а его `state` в `system.part_moves_between_shards` принимает значение `CANCELLED`.
Перемещение, достигшее состояния `SOURCE_DROP`, отменить уже нельзя, и оно выполняется до конца.

Для выполнения оператора требуется привилегия `SELECT` на `system.part_moves_between_shards`, а для отмены перемещения — привилегия `ALTER MOVE PARTITION` на соответствующую таблицу и привилегия `MOVE PARTITION BETWEEN SHARDS`.
При использовании `ON CLUSTER` оператору требуются обе привилегии на перемещение для `*.*`.
Ответ содержит столбец `kill_status` со значением `waiting` для отменённого перемещения и `cant_cancel` для перемещения, которое отменить уже нельзя, а также следующие за ним столбцы `database`, `table`, `task_name`, `task_uuid`, `part_name`, `to_shard` и `state` из `system.part_moves_between_shards`.

Тестовый запрос (`TEST`) лишь выводит список перемещений, которые будут отменены. Модификатор `SYNC` не поддерживается: при его использовании выбрасывается исключение `NOT_IMPLEMENTED`.

Пример:

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
