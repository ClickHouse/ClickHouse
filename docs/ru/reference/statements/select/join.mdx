Предложение `JOIN` создает новую таблицу, объединяя столбцы одной или нескольких таблиц на основе общих значений. Это распространенная операция в базах данных с поддержкой SQL, соответствующая операции [JOIN](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators) в реляционной алгебре. Частный случай, когда таблица соединяется сама с собой, часто называют &quot;self-join&quot;.

**Синтаксис**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

Выражения из условия `ON` и столбцы из предложения `USING` называются &quot;ключами JOIN&quot;. Если не указано иное, `JOIN` создаёт [декартово произведение](https://en.wikipedia.org/wiki/Cartesian_product) строк с совпадающими ключами JOIN, из-за чего в результате может оказаться гораздо больше строк, чем в исходных таблицах.

На этой странице описаны синтаксис и семантика предложения `JOIN`. Сведения о выполнении JOIN в ClickHouse, типах JOIN, настройках, использовании памяти и оптимизациях см. в разделе [Связанные материалы](#related-content).

## Поддерживаемые типы JOIN {#supported-types-of-join}

Поддерживаются все стандартные типы [SQL JOIN](https://en.wikipedia.org/wiki/Join_\(SQL\)):

| Тип                | Описание                                                                                                                                                                                                                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | Возвращаются только совпадающие строки.                                                                                                                                                                                                                                                                                      |
| `LEFT OUTER JOIN`  | Помимо совпадающих строк возвращаются несовпадающие строки из левой таблицы.                                                                                                                                                                                                                                                 |
| `RIGHT OUTER JOIN` | Помимо совпадающих строк возвращаются несовпадающие строки из правой таблицы.                                                                                                                                                                                                                                                |
| `FULL OUTER JOIN`  | Помимо совпадающих строк возвращаются несовпадающие строки из обеих таблиц.                                                                                                                                                                                                                                                  |
| `CROSS JOIN`       | Создает декартово произведение всех строк таблиц. Ключи JOIN **не** указываются.                                                                                                                                                                                                                                             |
| `NATURAL JOIN`     | Автоматически выполняет JOIN по всем столбцам с одинаковыми именами в обеих таблицах. Каждый общий столбец появляется в результате только один раз. Поддерживает варианты `INNER` (по умолчанию), `LEFT`, `RIGHT` и `FULL`. Эквивалентен `JOIN ... USING (col1, col2, ...)`, где список столбцов определяется автоматически. |

* `JOIN` без указания типа подразумевает `INNER`.
* Ключевое слово `OUTER` можно опустить.
* Альтернативный синтаксис для `CROSS JOIN` — указать несколько таблиц в [предложении `FROM`](/ru/reference/statements/select/from), разделив их запятыми.
* Если у `NATURAL JOIN` нет совпадающих столбцов, он работает как `CROSS JOIN`.

В ClickHouse также доступны дополнительные типы JOIN:

| Тип                                                 | Описание                                                                                                                                                                                                                                                       |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | Разрешающий список по ключам JOIN без построения декартова произведения.                                                                                                                                                                                       |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | Запрещающий список по ключам JOIN без построения декартова произведения.                                                                                                                                                                                       |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | Частично (для противоположной стороны `LEFT` и `RIGHT`) или полностью (для `INNER`) отключает декартово произведение для стандартных типов `JOIN`. `ANY FULL JOIN` не поддерживается.                                                                          |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | Объединение последовательностей с неточным совпадением. См. [Использование ASOF JOIN](#asof-join-usage).                                                                                                                                                       |
| `PASTE JOIN`                                        | Выполняет горизонтальную конкатенацию двух таблиц. См. [Использование PASTE JOIN](#paste-join-usage).                                                                                                                                                          |
| `INNER JOIN LATERAL`, `LEFT JOIN LATERAL`           | Выполняет JOIN с подзапросом, который ссылается на столбцы таблиц слева от него. Экспериментальная возможность, требует включения [`enable_lateral_join`](/ru/reference/settings/session-settings/enable#enable_lateral_join). См. [LATERAL JOIN](#lateral-join). |

Диаграммы для каждого типа JOIN и строгости приведены в разделе [Использование JOIN в ClickHouse](/ru/concepts/features/operations/select/joining-tables#join-types-and-strictness).

<Note>
  Отключение настройки `semi_join_include_columns_from_both_sides` или `anti_join_include_columns_from_both_sides` ограничивает доступ к столбцам соответствующего JOIN только сохраняемой стороной для выражений, разрешаемых после формирования результата JOIN.

  * `LEFT SEMI JOIN` и `LEFT ANTI JOIN` предоставляют доступ только к столбцам левой стороны.
  * `RIGHT SEMI JOIN` и `RIGHT ANTI JOIN` предоставляют доступ только к столбцам правой стороны.
  * Это влияет на такие секции, как `SELECT`, `PREWHERE`, `WHERE`, `GROUP BY`, `HAVING`, `QUALIFY`, `ORDER BY` и `LIMIT BY`, включая подстановочные шаблоны с квалификатором, такие как `t1.*`.
  * Выражение `ON` того же `JOIN` по-прежнему может ссылаться на обе стороны.

  Когда эти настройки включены (по умолчанию), ClickHouse сохраняет прежнее поведение: обе стороны остаются доступными, а `SELECT *` раскрывается в список столбцов обеих таблиц.
</Note>

Не каждый алгоритм JOIN поддерживает все сочетания типа JOIN и строгости. Поддерживаемые сочетания перечислены в разделе [Поддерживаемые типы JOIN для каждого алгоритма](/ru/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).

### Переписывание `CROSS JOIN` в `INNER JOIN` {#cross-join-rewrite}

Если в запросе с `CROSS JOIN` или перечислением таблиц через запятую предложение `WHERE` содержит условия равенства между таблицами, ClickHouse может переписать JOIN в `INNER JOIN`, используя эти условия в качестве ключей JOIN. Это переписывание управляется настройкой [`cross_to_inner_join_rewrite`](/ru/reference/settings/session-settings/other#cross_to_inner_join_rewrite):

* `0`: переписывание отключено.
* `1`: перечисление таблиц через запятую или `CROSS JOIN` переписывается, если предложение `WHERE` содержит условие равенства между таблицами. В противном случае JOIN выполняется как `CROSS JOIN`.
* `2`: аналогично `1`, но если перечисление таблиц через запятую не удаётся переписать, а в запросе есть предложение `WHERE`, запрос завершается ошибкой `INCORRECT_QUERY`. JOIN, заданный ключевыми словами `CROSS JOIN`, который не удаётся переписать, выполняется как `CROSS JOIN`.

При значении `0` оптимизация плана запроса, управляемая настройкой [`query_plan_merge_filter_into_join_condition`](/ru/reference/settings/session-settings/query-plan#query_plan_merge_filter_into_join_condition), всё равно может перенести фильтр по равенству в условие JOIN и выполнить его как `INNER JOIN`.

## Условия в секции ON {#on-section-conditions}

Секция `ON` может содержать несколько условий, объединённых с помощью операторов `AND` и `OR`. Условия, задающие ключи JOIN, должны:

* ссылаться как на левую, так и на правую таблицу
* использовать оператор равенства

Другие условия могут использовать иные операторы и ссылаться на левую или правую таблицу запроса либо на обе сразу.

Строки объединяются, если выполняется всё составное условие. Если условия не выполняются, строки всё равно могут попасть в результат в зависимости от типа `JOIN`. Если поместить те же условия в раздел `WHERE` и они не выполняются, то строки всегда отфильтровываются из результата.

Ключи JOIN, объединённые с помощью `OR`, поддерживаются только алгоритмом [`hash`](/ru/concepts/features/operations/select/join-algorithms#hash), который строит отдельную хеш-таблицу для каждого аргумента `OR`, содержащего ключи JOIN.

<Note>
  Ключом JOIN условие делает только оператор равенства (`=`). Другие операторы между столбцами разных таблиц поддерживаются, однако если равенства нет, JOIN вынужден перебирать все пары строк; см. [JOIN с произвольным условием ON](#join-with-an-arbitrary-on-condition).
</Note>

**Пример**

Рассмотрим `table_1` и `table_2`:

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

Запрос с одним условием по ключу в JOIN и дополнительным условием для `table_2`:

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

Результат содержит строку с именем `C` и пустым текстовым столбцом. Она включена в результат, поскольку используется JOIN типа `OUTER`.

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

Запрос с JOIN типа `INNER` и несколькими условиями:

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```response title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴────────┴────────┘
```

Запрос с JOIN типа `INNER` и условием с `OR`:

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

Запрос с типом JOIN `INNER` и условиями с `OR` и `AND`:

<Note>
  Условие неравенства, в котором используются столбцы только из одной таблицы, например `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c`, применяется только к этой таблице: в `t1.b > 0` используются только столбцы из `t1`, а в `t2.b > t2.c` — только столбцы из `t2`.
  Условие неравенства, сравнивающее столбцы разных таблиц, например `t1.a = t2.key AND t1.b > t2.key`, также поддерживается; см. разделы ниже.
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## JOIN с условиями неравенства для столбцов из разных таблиц {#join-with-inequality-conditions-for-columns-from-different-tables}

Помимо условий равенства, секция `ON` может содержать условия, сравнивающие столбцы разных таблиц с помощью других операторов. Такие условия поддерживаются со строгостью `ALL`, `ANY`, `SEMI` и `ANTI` для всех типов JOIN, допустимых для данной строгости. Со строгостью `ASOF` они не поддерживаются.

Если секция `ON` наряду с неравенством содержит равенство между двумя таблицами, это равенство служит ключом JOIN, а неравенство проверяется для строк, сопоставленных по этому ключу. Такое смешанное условие выполняется алгоритмами [`hash`](/ru/concepts/features/operations/select/join-algorithms#hash), [`parallel_hash`](/ru/concepts/features/operations/select/join-algorithms#parallel-hash) и [`grace_hash`](/ru/concepts/features/operations/select/join-algorithms#grace-hash). Если в [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm) алгоритм [`ie_join`](/ru/concepts/features/operations/select/join-algorithms#ie-join) указан раньше этих алгоритмов, а секция `ON` содержит два условия неравенства, JOIN вместо них выполняется алгоритмом `ie_join`, а равенство применяется как фильтр.

Если секция `ON` не содержит равенства между двумя таблицами, ключа для сопоставления нет. Такой JOIN выполняется алгоритмом [`ie_join`](/ru/concepts/features/operations/select/join-algorithms#ie-join), если условие представляет собой пару неравенств, а в остальных случаях — как [блочный JOIN с вложенными циклами](#join-with-an-arbitrary-on-condition).

Условие, вычисляемое во время JOIN, не может содержать `arrayJoin`, поскольку оно должно сохранять количество строк; вместо этого используйте `ARRAY JOIN` в подзапросе.

**Пример**

Таблица `t1`:

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

Таблица `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response
key1    a    1    1    2    key1    B    2    1    2
key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
key1    e    5    5    5            0    0    \N
key2    a2    1    1    1            0    0    \N
key4    f    2    3    4            0    0    \N
```

## JOIN с произвольным условием ON {#join-with-an-arbitrary-on-condition}

Секция `ON` может содержать произвольное булево выражение над столбцами обеих таблиц, например проверку вхождения в диапазон, арифметическое сравнение или вызов скалярной функции. Если в ней нет условия равенства между столбцами двух таблиц, ключ JOIN для сопоставления строк отсутствует. Пара условий неравенства обрабатывается алгоритмом `ie_join`, если он указан в [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm), причём не обязательно на первом месте, поскольку ни одно другое значение `join_algorithm` не может обработать такое условие. Начиная с версии 26.8, значение по умолчанию `join_algorithm` включает `ie_join`. Для любого другого условия используется [блочный JOIN с вложенными циклами](https://en.wikipedia.org/wiki/Nested_loop_join): правая таблица материализуется, а условие проверяется для каждой пары строк. `ALL INNER JOIN` в этом случае эквивалентен `CROSS JOIN` с этим условием в качестве фильтра.

Блочный JOIN с вложенными циклами поддерживает все типы JOIN и варианты строгости, кроме `ASOF JOIN`, `PASTE JOIN` и `ANY FULL JOIN`. Он не входит в число значений `join_algorithm` и используется лишь в крайнем случае, когда ни один другой алгоритм не может обработать условие. В выводе `EXPLAIN` он отображается как шаг `BlockNestedLoopJoin`. Если [`allow_block_nested_loop_join`](/ru/reference/settings/session-settings/allow#allow_block_nested_loop_join) отключён, запрос, которому необходим этот алгоритм, отклоняется с ошибкой `INVALID_JOIN_ON_EXPRESSION`.

**Пример**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

Строка, для которой не нашлось соответствия, дополняется в соответствии с [`join_use_nulls`](/ru/reference/settings/session-settings/join#join_use_nulls), как и в любом другом JOIN: значением по умолчанию, как в примере выше, или `NULL`, если этот параметр включён.

**Строгость**

`ANY` и `SEMI` обычно оставляют одну строку на каждую группу строк с общим ключом JOIN. Здесь таких групп нет, поэтому они оставляют одну строку на каждую строку ведущей таблицы JOIN: `LEFT ANY` и `LEFT SEMI` выводят каждую левую строку не более одного раза, `RIGHT ANY` и `RIGHT SEMI` — каждую правую строку не более одного раза. `ANY INNER` ограничивает обе стороны сразу: каждая строка любой из таблиц используется не более одного раза, поэтому в результате строк не больше, чем в меньшей из таблиц. Какие именно пары войдут в такой результат, не определено — ровно так, как и подразумевает `ANY`, — и он может различаться между двумя запусками одного и того же запроса. Для `ANY INNER` это касается и количества строк: при жадном сопоставлении строк обеих сторон в том порядке, в котором они просматриваются, без пары может остаться разное число строк, поэтому результат `count()` для JOIN `ANY INNER` без ключа JOIN невоспроизводим и зависит от количества потоков и физического порядка строк в правой таблице.

**Производительность**

Блочный JOIN с вложенными циклами просматривает каждую пару строк, поэтому его стоимость растёт пропорционально произведению количества строк обеих таблиц, как описано в разделе [Переход на блочный JOIN с вложенными циклами](/ru/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback). На материализованную правую таблицу распространяются жёсткие лимиты и пороги сброса на диск, описанные в разделе [Управление памятью и сброс данных на диск при JOIN](/ru/concepts/features/operations/select/join-memory-management).

## Значения NULL и NaN в ключах JOIN {#null-values-in-join-keys}

`NULL` не равно никакому значению, включая само себя. Если ключ JOIN в одной таблице имеет значение `NULL`, он не будет сопоставлен со значением `NULL` в другой таблице. Если ключи JOIN являются столбцами типа [Nullable](/ru/reference/data-types/nullable), строка, в которой хотя бы один из ключей равен [NULL](/ru/reference/syntax#null), не участвует в соединении.

**Пример**

Таблица `A`:

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

Таблица `B`:

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

Строка с `Charlie` из таблицы `A` и строка с оценкой 88 из таблицы `B` не сопоставляются из-за значения `NULL` в ключе JOIN.

Строки без совпадения получают значение `0` в столбце `score`, как описано в разделе [Обработка пустых ячеек и ячеек со значением NULL](#processing-of-empty-or-null-cells).

Чтобы сопоставлять значения `NULL`, сравнивайте ключи JOIN с помощью функции `isNotDistinctFrom`:

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

Значения `NaN` в ключах JOIN типа float не подчиняются приведённому выше правилу для `NULL`.
Скалярное сравнение двух значений `NaN` (`NaN = NaN`) равно `0`. Однако ключи JOIN сравниваются не по правилам скалярной семантики, и ключи `NaN` могут сопоставляться.
Будут ли они сопоставлены, не определено: это зависит от алгоритма JOIN, типа ключа и настроек сеанса.
Чтобы исключить ключи `NaN` из сопоставления, преобразуйте их в значения `NULL`, например `ON if(isNaN(A.id), NULL, A.id) = B.id`.
В `ASOF JOIN` столбец для поиска ближайшего совпадения сравнивается по порядку, который не определён для значений `NaN`.

## Неявное преобразование типов {#implicit-type-conversion}

Если ключи JOIN левой и правой таблиц имеют разные типы, ClickHouse перед сравнением приводит их к наименьшему общему супертипу. Это относится ко всем типам JOIN и всем вариантам строгости:

* При использовании `ON` преобразование применяется только при сравнении. В результате столбцы ключа сохраняют исходные типы.
* При использовании `USING` слитый столбец в результате имеет общий тип. Если настройка `semi_join_include_columns_from_both_sides` или `anti_join_include_columns_from_both_sides` отключена, слитый столбец `SEMI JOIN` или `ANTI JOIN` имеет тип той таблицы, строки которой попадают в результат.

Если у типов ключей нет общего супертипа и оба являются целочисленными типами или кортежами целочисленных типов, как, например, `UInt64` и `Int64`, ClickHouse приводит оба ключа к типу, который вмещает значения, общие для обоих типов ключей. Для `UInt64` и `Int64` это тип `UInt64`. Значение ключа, которое не может быть представлено этим типом, не совпадает ни с одним значением. Это преобразование применяется к условиям равенства в `ON`, кроме `isNotDistinctFrom`, а также к `USING` в `INNER JOIN` или `SEMI JOIN`. Оно не применяется к условию ближайшего совпадения в `ASOF JOIN`, к условиям неравенства, которые выполняет `ie_join`, и к `USING` в остальных JOIN, поскольку их результирующий столбец должен также хранить значения, не имеющие совпадений. Это преобразование доступно начиная с версии 26.9.

Если у типов ключей нет общего супертипа и это преобразование неприменимо, как, например, для `String` и `Int32` или для `UInt64` и `Float64`, запрос завершается с исключением, например `NO_COMMON_TYPE`.

**Пример**

Рассмотрим таблицу `t_1`:

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

и таблица `t_2`:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

Запрос

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b) ORDER BY ALL;
```

возвращает набор:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## Использование ASOF JOIN {#asof-join-usage}

`ASOF JOIN` соединяет записи без точного совпадения. `ASOF` — это строгость JOIN, которая используется в сочетании с `INNER` или `LEFT` JOIN. Это не алгоритм соединения.

Для `ASOF JOIN` в обеих таблицах требуется столбец для поиска ближайшего совпадения. Этот столбец:

* должен иметь тип с определённым порядком;
* при использовании алгоритма [`hash`](/ru/concepts/features/operations/select/join-algorithms#hash) может иметь следующие типы: [Int, UInt](/ru/reference/data-types/int-uint), [Float](/ru/reference/data-types/float), [Decimal](/ru/reference/data-types/decimal), [Date](/ru/reference/data-types/date), [Date32](/ru/reference/data-types/date32), [DateTime](/ru/reference/data-types/datetime), [DateTime64](/ru/reference/data-types/datetime64), [Time](/ru/reference/data-types/time), [Enum](/ru/reference/data-types/enum), [Bool](/ru/reference/data-types/boolean), а также [Nullable](/ru/reference/data-types/nullable) от этих типов. Другие типы, например `String` и `Time64`, отклоняются с ошибкой `BAD_TYPE_OF_FIELD`;
* при использовании алгоритма [`full_sorting_merge`](/ru/concepts/features/operations/select/join-algorithms#full-sorting-merge) может также иметь другие сравнимые типы, например `String`;
* при использовании алгоритма `hash` не может быть единственным столбцом в условии `JOIN`: требуется как минимум одно условие равенства. Для алгоритма `full_sorting_merge` это требование не действует.

Синтаксис `ASOF JOIN ... ON`:

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

Вы можете использовать любое количество условий равенства и ровно одно условие поиска ближайшего совпадения. Например, `SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t`.

Для поиска ближайшего совпадения поддерживаются следующие условия: `>`, `>=`, `<`, `<=`.

Синтаксис `ASOF JOIN ... USING`:

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

`ASOF JOIN` использует `equi_columnX` для JOIN по равенству и `asof_column` для JOIN по ближайшему совпадению с условием `table_1.asof_column >= table_2.asof_column`. Столбец `asof_column` всегда указывается последним в предложении `USING`.

Например, рассмотрим следующие таблицы:

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

`ASOF JOIN` может брать временную метку пользовательского события из `table_1` и находить событие в `table_2`, временная метка которого наиболее близка к временной метке события из `table_1` в соответствии с условием ближайшего совпадения. Если доступны равные значения временной метки, именно они считаются ближайшими. Здесь столбец `user_id` можно использовать для JOIN по равенству, а столбец `ev_time` — для JOIN по ближайшему совпадению. В нашем примере `event_1_1` можно соединить с `event_2_1`, а `event_1_2` — с `event_2_3`, но `event_2_2` соединить нельзя.

<Note>
  Из алгоритмов соединения строгость `ASOF` поддерживают только [`hash`](/ru/concepts/features/operations/select/join-algorithms#hash) и [`full_sorting_merge`](/ru/concepts/features/operations/select/join-algorithms#full-sorting-merge). См. раздел [Поддерживаемые типы JOIN для каждого алгоритма](/ru/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).
  `ASOF` **не** поддерживается в движке таблицы [Join](/ru/reference/engines/table-engines/special/join).
</Note>

## Использование PASTE JOIN {#paste-join-usage}

Результатом `PASTE JOIN` является таблица, содержащая все столбцы левого подзапроса, а затем все столбцы правого подзапроса.
Строки сопоставляются по их позициям в исходных таблицах (порядок строк должен быть определён).
Если подзапросы возвращают разное количество строк, лишние строки будут отброшены.

Пример:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

Примечание: в этом случае результат может быть недетерминированным при параллельном чтении. Например:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## LATERAL JOIN {#lateral-join}

`JOIN LATERAL` позволяет подзапросу в правой части JOIN ссылаться на столбцы табличных
выражений, расположенных слева от него. Результат получается таким, как если бы подзапрос вычислялся для каждой уникальной комбинации
значений столбцов левой части, на которые он ссылается, а его результат соединялся с каждой строкой слева, содержащей эту комбинацию:

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

Предикат `ON true` обязателен, как и для любого другого `INNER` или `LEFT JOIN`; его отсутствие приводит к синтаксической ошибке.

Эта возможность доступна начиная с версии 26.10. Она является экспериментальной и по умолчанию отключена; чтобы включить её, используйте настройку
[`enable_lateral_join`](/ru/reference/settings/session-settings/enable#enable_lateral_join).

Латеральный подзапрос не выполняется ни отдельно для каждой левой строки, ни отдельно для каждой уникальной комбинации. Как и другие коррелированные
подзапросы, он декоррелируется в единый запрос по всем левым строкам: столбцы левой стороны, на которые он ссылается,
добавляются к его ключам `GROUP BY`, если он агрегирует данные, его `LIMIT` (если есть) превращается в `LIMIT ... BY` по этим столбцам, а его
результат соединяется с левыми строками по этим же столбцам. Если корреляция представляет собой простое равенство, например `orders.user_id = u.id`,
столбец левой стороны может быть заменён равным ему столбцом подзапроса
(`correlated_subqueries_substitute_equivalent_expressions`, по умолчанию включена), благодаря чему подзапрос может обойтись без
чтения левых строк. Это не гарантируется: например, агрегатная функция без `GROUP BY` (такая как `count`) всё равно
читает уникальные левые значения, чтобы вернуть результат для тех левых значений, для которых нет совпадающих строк. Всякий раз, когда уникальные
левые значения передаются в подзапрос, при настройках по умолчанию это происходит через буфер в оперативной памяти, и JOIN гарантированно выполняется как hash JOIN только
в том случае, когда такой буфер действительно используется. Во всех остальных случаях, например когда подстановка
по равенству позволяет не читать левые строки или буфер отключён
(`correlated_subqueries_use_in_memory_buffer = 0` или `correlated_subqueries_default_join_kind = 'left'`),
алгоритм определяется настройкой `join_algorithm`. Например, `EXPLAIN` латерального подзапроса с `LIMIT`
показывает шаг `Join` над шагом `LimitBy (LIMIT BY for decorrelated correlated subquery)`; у подзапроса без
`LIMIT` такого шага нет.

Пока поддерживается только следующее подмножество; всё остальное отклоняется с ошибкой:

* Только `INNER JOIN LATERAL` и `LEFT JOIN LATERAL`; JOIN типов `RIGHT`, `FULL`, `PASTE` и `NATURAL` не поддерживаются, а `LATERAL` нельзя сочетать с `CROSS` или JOIN через запятую.
* Только строгость `ALL`, используемая по умолчанию; `ANY`, `SEMI`, `ANTI` и `ASOF` не поддерживаются.
* Допускается только предикат JOIN `ON true` (также принимается `ON 1`); `USING` не поддерживается, и предикат
  нельзя опускать. Разместите фильтры, связывающие обе стороны JOIN, в предложении `WHERE` латерального подзапроса.
* Модификаторы JOIN `GLOBAL` и `LOCAL` не поддерживаются.
* Латеральный подзапрос должен ссылаться хотя бы на один столбец левой стороны. Для
  некоррелированного подзапроса используйте обычный JOIN.
* Поскольку латеральный подзапрос декоррелируется, а не вычисляется отдельно для каждого значения левой стороны, он
  не должен содержать функции, недетерминированные в пределах запроса, такие как
  `rand` или `generateUUIDv4`, либо табличные функции, генерирующие случайные строки, такие как `generateRandom`.
  Функции, значение которых постоянно в пределах запроса, такие как `now`, допускаются.
* В качестве латерального табличного выражения поддерживается только подзапрос. Формы записи источника данных PostgreSQL
  `LATERAL unnest(...)` и `CROSS JOIN UNNEST(...)` не поддерживаются. Вместо них используйте
  секцию [`ARRAY JOIN`](/ru/reference/statements/select/array-join).
* `GROUP BY` и `ORDER BY` латерального подзапроса выполняются один раз сразу для всех значений левой стороны, поэтому
  ограничения `max_rows_to_group_by`, `max_rows_to_sort` и `max_bytes_to_sort` учитывают строки для всех значений левой стороны,
  а не для одного. Они поддерживаются только с режимом переполнения `throw`; `any` и `break` вызывают ошибку.
* Результат декоррелированного подзапроса сопоставляется со строками левой стороны с помощью одного JOIN. Как и для любого hash join,
  `max_rows_in_join` и `max_bytes_in_join` ограничивают объём данных на стороне JOIN, которая хранится в памяти, а
  планировщик выбирает эту сторону: если описанный выше буфер в оперативной памяти действительно используется, это левая сторона
  `JOIN LATERAL`, поскольку её строки необходимо полностью прочитать до выполнения латерального подзапроса; в противном случае это может быть результат декоррелированного подзапроса. Ограничения всегда
  применяются так, как если бы `join_overflow_mode` имел значение `throw`: при `break` JOIN без предупреждения отбрасывал бы строки левой стороны, не связанные с переполнением.

**Пример**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS enable_lateral_join = 1;
```

## Распределенный JOIN {#distributed-join}

Существует два способа выполнить JOIN с distributed таблицами:

* При использовании обычного `JOIN` запрос отправляется на удаленные серверы. Подзапросы выполняются на каждом из них, чтобы сформировать правую таблицу, после чего выполняется JOIN с этой таблицей. Иными словами, правая таблица формируется отдельно на каждом сервере.
* При использовании `GLOBAL ... JOIN` сервер-инициатор сначала выполняет подзапрос, чтобы вычислить одну из сторон JOIN, и собирает результат во временную таблицу. Затем эта временная таблица передается на каждый удаленный сервер, и на них выполняются запросы с использованием переданных временных данных. Для `LEFT` и `INNER` JOIN правая таблица вычисляется подзапросом.

Если в `GLOBAL RIGHT JOIN` со строгостью `ALL`, `ANY`, `SEMI` или `ANTI` левая таблица является таблицей `Distributed` с несколькими сегментами, ClickHouse меняет стороны местами и выполняет JOIN как `LEFT JOIN`, чтобы строки сохраняемой правой таблицы возвращались только один раз. В этом случае подзапросом вычисляется левая таблица, а правая таблица читается из своих сегментов, если она является таблицей `Distributed` с несколькими сегментами, а в противном случае — на сервере-инициаторе. `GLOBAL RIGHT JOIN` или `GLOBAL FULL JOIN`, для которых такая перестановка сторон невозможна, выполняются на сервере-инициаторе. Это поведение действует начиная с версии 26.9.

Будьте осторожны при использовании `GLOBAL`. Дополнительные сведения см. в разделе [Распределенные подзапросы](/ru/reference/statements/in#distributed-subqueries).

## Обработка пустых ячеек и ячеек со значением NULL {#processing-of-empty-or-null-cells}

В результате внешнего JOIN для строки без совпадения столбцы другой таблицы остаются пустыми. Настройка [`join_use_nulls`](/ru/reference/settings/session-settings/join#join_use_nulls) определяет, как ClickHouse заполняет такие ячейки:

* `0`: ячейки заполняются значением по умолчанию для типа столбца.
* `1`: ячейки заполняются значением `NULL`, а типы этих столбцов преобразуются в [Nullable](/ru/reference/data-types/nullable). Столбец, тип которого не может быть обёрнут в `Nullable` (например, `Array`), сохраняет свой тип и заполняется значением по умолчанию. При `FULL` JOIN объединённый столбец `USING` также преобразуется в `Nullable`.

Строка, в которой хотя бы один из ключей JOIN равен `NULL`, не участвует в соединении, как описано в разделе [Значения NULL и NaN в ключах JOIN](#null-values-in-join-keys).

## Предложение USING {#using-clause}

Предложение `USING` задаёт один или несколько столбцов, по которым выполняется JOIN, и устанавливает равенство этих столбцов:

* Каждый столбец должен присутствовать под одним и тем же именем как в левом, так и в правом табличном выражении. Одинаковые имена столбцам можно задать с помощью псевдонимов в подзапросах.
* Предложение `USING` принимает только имена столбцов. Выражения не поддерживаются.
* Список столбцов можно записывать как в скобках, так и без них.
* Каждый столбец из предложения `USING` встречается в результате один раз. Его тип описан в разделе [Неявное преобразование типов](#implicit-type-conversion).
* Другие столбцы в обеих таблицах тоже могут иметь одинаковые имена. `SELECT *` уточняет столбец правой таблицы именем таблицы или псевдонимом, а неуточнённое имя разрешается в столбец левой таблицы, если включена настройка [`single_join_prefer_left_table`](/ru/reference/settings/session-settings/other#single_join_prefer_left_table).
* Если включена настройка [`analyzer_compatibility_join_using_top_level_identifier`](/ru/reference/settings/session-settings/analyzer-compatibility#analyzer_compatibility_join_using_top_level_identifier), имя столбца в `USING` разрешается по одноимённому псевдониму в запросе, например по псевдониму в списке `SELECT`.

## Примеры {#examples}

Следующий запрос соединяет количество хитов (hits) по каждому счётчику с количеством визитов (visits) по каждому счётчику. `ANY LEFT JOIN` возвращает каждую строку левого подзапроса ровно один раз, а счётчик без визитов получает значение по умолчанию `0`:

```sql title="Query"
SELECT
    CounterID,
    hits,
    visits
FROM
(
    SELECT
        CounterID,
        count() AS hits
    FROM VALUES('CounterID UInt32', 1, 1, 1, 2, 2, 3)
    GROUP BY CounterID
) AS h
ANY LEFT JOIN
(
    SELECT
        CounterID,
        sum(Sign) AS visits
    FROM VALUES('CounterID UInt32, Sign Int8', (1, 1), (1, 1), (1, -1), (2, 1), (4, 1))
    GROUP BY CounterID
) AS v USING (CounterID)
ORDER BY hits DESC;
```

```response title="Response"
┌─CounterID─┬─hits─┬─visits─┐
│         1 │    3 │      1 │
│         2 │    2 │      1 │
│         3 │    1 │      0 │
└───────────┴──────┴────────┘
```
