## Описание {#description}

Показывает текущему пользователю записи из его журнала запросов. Читает таблицу журнала запросов, заданную настройками сервера `query_log.database` и `query_log.table` (по умолчанию — `system.query_log`), и возвращает только строки, в которых пользователь-инициатор равен `currentUser()` (если задан `initial_user`, используется он, иначе — `user`). Аутентифицированный текущий пользователь должен быть непустым и совпадать с пользователем-инициатором, указанным в журнале. Исключение составляет неаутентифицированный клиент `clickhouse-local`: он может читать строки с пустым пользователем-инициатором, только если обе идентичности пользователя пусты и запрос использует интерфейс `LOCAL`. В остальных случаях таблица не возвращает строк.

В отличие от самой таблицы журнала запросов, `system.user_query_log` можно читать без каких-либо привилегий, поэтому пользователи могут просматривать собственные запросы, не получая доступа к запросам других пользователей.

Возвращаются только строки верхнего уровня (`is_initial_query = 1`). Дочерние строки — например, запросы, которые распределённый запрос отправляет на другие серверы, а также всё, что выполняется под идентичностью представлений `SQL SECURITY DEFINER` и `NONE`, — не возвращаются.

Политика доступа к строкам, открывающая строки `system.query_log` по пользователю (`user`, `initial_user` или `authenticated_user`), открывает и эти дочерние строки, поэтому добавьте в неё условие `is_initial_query = 1` или используйте `system.user_query_log`.

Это поддерживается только при локальном хранении журнала запросов. Если для `query_log.engine` задан `Distributed` или другой движок, который делегирует чтение другому серверу, `system.user_query_log` отказывается читать из такой таблицы и генерирует исключение, поскольку требуемую проверку доступа невозможно обеспечить через границу серверов, взаимодействующих по протоколу ClickHouse. В этом случае отключите таблицу, установив `query_log.enable_user_query_log = 0`.

**Доступность**

`system.user_query_log` присоединяется только тогда, когда включена настройка сервера `query_log.enable_user_query_log`, что является значением по умолчанию. Если настройка равна `0`, таблица не существует, и запросы к ней завершаются ошибкой `UNKNOWN_TABLE`.

Если `query_log.enable_user_query_log` включена, но базовый журнал запросов не настроен или его таблица ещё не создана, `system.user_query_log` существует, но пуста.

Условия для партиции и столбцов ключа журнала запросов (`event_date`, `event_time`, `query_start_time`, `query_id`, `type` и аналогичных скалярных столбцов), сравниваемые с константами, передаются в базовую таблицу журнала запросов, поэтому при обычных обращениях, таких как в приведённом ниже примере, сохраняется отсечение партиций и не выполняется сканирование всего хранимого журнала.

Если таблица с именем `system.user_query_log` была создана до обновления до версии ClickHouse, в которой появилась эта таблица, сервер не запустится, пока существующая таблица не будет переименована или удалена либо для `query_log.enable_user_query_log` не будет установлено значение `0`.

* `used_number_of_joins` ([UInt64](/ru/reference/data-types/int-uint)) — Количество физических JOIN, выполненных для этого запроса. Значение собирается из конвейеров по мере их построения, поэтому отражает JOIN, оставшиеся после всех оптимизаций, а не количество предложений JOIN в тексте запроса. JOIN учитывается независимо от глубины вложенности: подзапросы, общие табличные выражения, представления, представления поверх представлений и SELECT materialized view, запускаемый INSERT, — всё это учитывается в строке отправленного запроса, поэтому значение может быть ненулевым даже для запроса, в тексте которого нет ни одного JOIN. Запрос, который строит конвейер, не выполняя его (например, EXPLAIN PIPELINE), возвращает количество JOIN анализируемого запроса. Некоторые конвейеры за время выполнения одного запроса собираются несколько раз: SELECT materialized view собирается для каждого блока запускающего его INSERT и каждым потоком вставки, рекурсивная часть рекурсивного CTE — на каждой итерации, а отношение цикла — заново при каждом перезапуске. Тем не менее JOIN такого конвейера учитываются только один раз, поэтому значение характеризует сам запрос, а не то, сколько раз собирались его конвейеры.
* `used_join_algorithms` ([Array(String)](/ru/reference/data-types/array)) — Алгоритмы JOIN, учтённых в used&#95;number&#95;of&#95;joins: &#39;HASH&#39;, &#39;GRACE&#95;HASH&#39;, &#39;PARTIAL&#95;MERGE&#39;, &#39;FULL&#95;SORTING&#95;MERGE&#39;, &#39;PARALLEL&#95;FULL&#95;SORTING&#95;MERGE&#39;, &#39;INEQUALITY&#39;, &#39;BLOCK&#95;NESTED&#95;LOOP&#39;, &#39;DIRECT&#39;, &#39;PASTE&#39; и &#39;CONSTANT&#39;. Список отсортирован и дедуплицирован, поэтому алгоритм, общий для нескольких JOIN, указывается один раз. Здесь указывается алгоритм, фактически выбранный для выполнения каждого JOIN, а не алгоритмы, разрешённые настройкой join&#95;algorithm. Хеш-JOIN обозначается как &#39;HASH&#39; независимо от того, в одном или в нескольких потоках была построена его хеш-таблица. Алгоритм может смениться другим прямо во время выполнения — в этом случае указываются оба.
* `used_join_kinds` ([Array(String)](/ru/reference/data-types/array)) — Виды JOIN, учтённых в used&#95;number&#95;of&#95;joins, по одному элементу на каждый JOIN, поэтому вид, общий для нескольких JOIN, встречается несколько раз. Элементы отсортированы, а не расположены в порядке выполнения. Указывается фактически выполненный вид JOIN, который может отличаться от указанного в тексте запроса: оптимизатор может выполнить JOIN, поменяв стороны местами, и тем самым превратить LEFT в RIGHT.
* `used_join_strictness` ([Array(String)](/ru/reference/data-types/array)) — Строгость JOIN, учтённых в used&#95;number&#95;of&#95;joins, по одному элементу на каждый JOIN, в том же порядке, что и в used&#95;join&#95;kinds: элементы с одинаковым индексом в обоих массивах описывают один и тот же JOIN.
* `spilled_to_disk` ([Array(String)](/ru/reference/data-types/array)) — Операторы, записывавшие данные во временные файлы на диске (обработка во внешней памяти) во время выполнения запроса; список отсортирован и дедуплицирован. Пустой массив означает, что запрос был полностью выполнен в памяти.
* `transaction_id` ([Tuple(UInt64, UInt64, UUID, Int64)](/ru/reference/data-types/tuple)) — Идентификатор транзакции, в рамках которой был выполнен этот запрос.
* `query_cache_usage` ([Enum8(&#39;Unknown&#39; = 0, &#39;None&#39; = 1, &#39;Write&#39; = 2, &#39;Read&#39; = 3)](/ru/reference/data-types/enum)) — Использование кэша запросов во время выполнения запроса. Значения: &#39;Unknown&#39; — статус неизвестен, &#39;None&#39; — результат запроса не был ни записан в кэш результатов запросов, ни прочитан из него, &#39;Write&#39; — результат запроса был записан в кэш результатов запросов, &#39;Read&#39; — результат запроса был прочитан из кэша результатов запросов.
* `asynchronous_read_counters` ([Map(String, UInt64)](/ru/reference/data-types/map)) — Метрики асинхронного чтения.
* `is_internal` ([UInt8](/ru/reference/data-types/int-uint)) — Указывает, является ли запрос вспомогательным, выполняемым внутри системы.
* `query_plan` (`JSON`) — план запроса, к которому относится эта строка, сериализованный в JSON, со статистикой выполнения для каждого шага. Заполняется только при включенной настройке `log_query_plans` и остаётся пустым для строк `QueryStart`, поскольку на этот момент плана ещё не существует. Для запроса, завершившегося исключением, в строке сохраняется план, который запрос успел построить к моменту исключения, и статистики в нём нет: если запрос завершился сбоем во время выполнения, его план был выполнен лишь частично, а если до начала выполнения — план не выполнялся вовсе. План маскируется с помощью `query_masking_rules`; для запроса, в котором срабатывает какое-либо правило, а также для запроса с секретными аргументами план не сохраняется.
