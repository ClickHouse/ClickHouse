## Описание

Содержит сведения о количестве событий, произошедших в системе. Например, в таблице можно увидеть, сколько запросов `SELECT` было обработано с момента запуска сервера ClickHouse.

## Описания событий

### ACMEAPIRequests

Количество запросов к API ACME.

### ACMECertificateOrders

Количество выданных запросов на сертификаты ACME.

### AdaptiveAggregationBucketsRetired

Количество двухуровневых бакетов, рабочая память которых (слот арены, ссылки на подготовленные фрагменты) была освобождена сразу после завершения слияния и преобразования этого бакета, не дожидаясь окончания всего слияния.

### AdaptiveAggregationDrainedRecords

Сколько отложенных записей адаптивная агрегация перенесла в общую таблицу во время слияния.

### AdaptiveAggregationGiveUps

Сколько потоков отказались от фиксации при адаптивной агрегации, поскольку их поток содержал мало различных keys.

### AdaptiveAggregationLocalFreezes

Количество локальных хеш-таблиц, замороженных адаптивной агрегацией по достижении порога заморозки.

### AdaptiveAggregationPressureDrainedRecords

Сколько записей из промежуточного буфера адаптивная агрегация сбросила досрочно из-за нехватки памяти.

### AdaptiveAggregationPressureStandDowns

Сколько потоков адаптивной агрегации окончательно вышли из фазы обучения из-за того, что нехватка памяти превысила порог внешней агрегации, и поэтому их локальные таблицы сбрасываются на диск обычной внешней агрегацией.

### AdaptiveAggregationPressureSweeps

Сколько раз адаптивная агрегация досрочно сбрасывала записи из промежуточной стадии из-за нехватки памяти.

### AdaptiveAggregationProbeBypasses

Сколько потоков перестали проверять свою замороженную локальную таблицу при адаптивной агрегации, поскольку в неё попадало почти ноль строк.

### AdaptiveAggregationResidueReleases

Сколько раз адаптивная агрегация записывала свою общую таблицу-накопитель, потому что из-за неё поток, работающий по базовому алгоритму, был близок к сбросу данных на диск.

### AdaptiveAggregationSealedChunks

Количество объединённых фрагментов, закрытых адаптивной агрегацией из буферизованных батчей промежуточного хранилища.

### AdaptiveAggregationSealNormalizations

Сколько подготовленных столбцов аргументов адаптивная агрегация при закрытии (seal) нормализовала из обёрнутого представления (Const, Replicated, Sparse, LowCardinality) в плотную форму, которую потребляет слив (drain).

### AdaptiveAggregationSharedTableSpills

Сколько раз адаптивная агрегация сбрасывала на диск свою общую таблицу из-за достижения границы части при нехватке памяти.

### AdaptiveAggregationSpillBacklogSheds

Сколько раз адаптивная агрегация отбрасывала накопленную очередь отложенных записей из-за того, что поток, работающий по базовому алгоритму, — либо возвращённый туда при «оттаивании», либо перешедший на него самостоятельно — был близок к сбросу данных на диск, тогда как промежуточные записи всё ещё находились в памяти.

### AdaptiveAggregationStagedBytes

Сколько байтов ключей адаптивная агрегация подготовила к выгрузке на этапе слияния.

### AdaptiveAggregationStagedChunkPiecesOverBound

Сколько частей разрезанного подготовленного фрагмента, опубликованных адаптивной агрегацией, всё равно оказались больше границы, ради соблюдения которой фрагмент и разрезался. Фрагмент режется по границам бакетов, а внутри бакета, который сам по себе превышает границу, — по отдельным записям, поэтому речь идёт об одной записи, подготовленный объём которой сам по себе превышает границу; такая часть захватывается целиком, и её выгрузка может настолько же превысить часть, отведённую под давление.

### AdaptiveAggregationStagedChunkSplits

Сколько подготовленных фрагментов адаптивная агрегация разделила по границам бакетов при публикации из-за того, что оценка выгрузки одного фрагмента превысила границу части давления.

### AdaptiveAggregationStagedClaimsClosedAtBound

Сколько заявок на подготовленные фрагменты со стороны сливов адаптивной агрегации было закрыто перед фрагментом, добавление которого вывело бы батч за границу pressure part, — такой фрагмент остаётся следующей заявке. Граница проверяется для батча в том виде, в каком он слит, поэтому два фрагмента, каждый из которых лишь чуть её не достигает (две половины разрезанного фрагмента, превышающие половину части на одну запись), сливаются в две таблицы, а не в одну; и только первый фрагмент, который сам по себе выходит за границу, забирается заявкой в любом случае.

### AdaptiveAggregationStagedRecords

Сколько промежуточных записей адаптивная агрегация подготовила в промежуточном буфере перед дедупликацией.

### AdaptiveAggregationStagedRecordsMerged

Сколько промежуточных (staged) записей адаптивная агрегация слила как дублирующиеся ключи при публикации и при закрытии.

### AdaptiveAggregationThaws

Сколько раз адаптивная агрегация размораживала локальные таблицы из-за того, что в поэтапном потоке преобладали повторяющиеся значения.

Либо куча почти ничего не отбросила в пределах своего окна наблюдения (например, число различных ключей группировки не превышает LIMIT), либо множество равных значений на границе кучи — которое никогда не может быть вытеснено — разрослось и переполнило её (см. `enable_group_by_top_k_optimization`).

### Данные после слияния отличаются от данных на реплике

Количество случаев, когда данные после слияния не являются побайтно идентичными данным на другой реплике. Причин может быть несколько:

1. Использование более новой версии библиотеки сжатия после обновления сервера.
2. Использование другого метода сжатия.
3. Недетерминированный алгоритм сжатия (крайне маловероятно).
4. Недетерминированный алгоритм слияния из-за логической ошибки в коде.
5. Повреждение данных в памяти из-за ошибки в коде.
6. Повреждение данных в памяти из-за аппаратной проблемы.
7. Ручное изменение исходных данных после запуска сервера.
8. Ручное изменение контрольных сумм, хранящихся в ZooKeeper.
9. Настройки, связанные с форматом частей, такие как &#39;enable&#95;mixed&#95;granularity&#95;parts&#39;, различаются на разных репликах.
   Сервер обнаружил эту ситуацию и загрузит слитую часть с реплики, чтобы обеспечить побайтно идентичный результат.
