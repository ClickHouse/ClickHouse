## Описание {#description}

Хранит метаданные и статистику о выполненных запросах, такие как время начала, длительность, сообщения об ошибках, использование ресурсов и другие сведения о выполнении. Результаты запросов не сохраняются.

Вы можете изменить настройки логирования запросов в разделе [query&#95;log](/ru/reference/settings/server-settings/settings/query#query_log) конфигурации сервера.

Вы можете отключить логирование запросов, установив [log&#95;queries = 0](/ru/reference/settings/session-settings/log-queries#log_queries). Мы не рекомендуем отключать логирование, поскольку информация в этой таблице важна для устранения проблем.

Период сброса данных задаётся параметром `flush_interval_milliseconds` в разделе настроек сервера [query&#95;log](/ru/reference/settings/server-settings/settings/query#query_log). Чтобы принудительно выполнить сброс, используйте запрос [SYSTEM FLUSH LOGS](/ru/reference/statements/system#flush-logs).

ClickHouse не удаляет данные из таблицы автоматически. Подробнее см. в разделе [Introduction](/ru/reference/system-tables/overview#system-tables-introduction).

Таблица `system.query_log` регистрирует два типа запросов:

1. Исходные запросы (верхнего уровня).
2. Дочерние запросы, инициированные другими запросами, включая запросы для распределённого выполнения и внутренние подзапросы, например при вычислении представлений. Для этих запросов информация об исходном запросе отображается в столбцах `initial_*`.

**По умолчанию фильтруйте исходные запросы**

Как правило, добавляйте `is_initial_query = 1` при каждом запросе к `system.query_log`. Это исключает дочерние запросы, чтобы отдельные этапы обработки не учитывались отдельно от исходного запроса. Этот фильтр не означает, что запрос был отправлен клиентом, поскольку внутренняя работа сервера также может быть исходным запросом.

Вместо этого используйте `initial_query_id`, когда нужно отследить исходный запрос вместе с дочерними запросами, сохраняющими его ID. У исходного запроса значения `initial_query_id` и `query_id` совпадают, тогда как дочерние запросы в той же цепочке сохраняют `initial_query_id` исходного запроса и имеют собственный `query_id`. Не вся работа, порождённая исходным запросом, коррелируется таким образом: работа, запускаемая сервером, может начать новую цепочку исходного запроса с новым `initial_query_id`, как при удалённом запуске [`QueryRunner`](/ru/reference/engines/table-engines/special/query-runner#cluster-mode).

```sql
SELECT
    hostname,
    type,
    query_id,
    initial_query_id,
    is_initial_query,
    query
FROM system.query_log
WHERE initial_query_id = '<query_id_of_initial_query>'
ORDER BY event_time_microseconds;
```

Если коррелированные дочерние запросы могут выполняться на других узлах, запрашивайте `system.query_log` на каждом узле, например с помощью [`clusterAllReplicas`](/ru/reference/functions/table-functions/cluster).

Всё, что запрос выполняет от имени представления или materialized view с `SQL SECURITY DEFINER` или `NONE`, записывается как дочерняя строка этого запроса: чтение представления, чтение через materialized view, вставка в него или выполнение его запроса при `INSERT` в его исходную таблицу. В такой строке `is_initial_query = 0`, `initial_query_id` — это исходный запрос, `user` — владелец (definer; пустое значение для `NONE`), `query` — то, что было выполнено (запрос представления либо чтение или запись целевой таблицы materialized view), а `tables`, `columns`, `partitions`, `projections` и `used_row_policies` — объекты, к которым он обращался. Для каждого уникального тела запроса и места его выполнения создаётся одна строка с типом итоговой строки запроса и без метрик.

Каждый запрос создаёт одну или две строки в таблице `query_log` в зависимости от состояния запроса (см. столбец `type`):

1. Если запрос выполнен успешно, создаются две строки с типами `QueryStart` и `QueryFinish`.
2. Если во время обработки запроса произошла ошибка, создаются два события с типами `QueryStart` и `ExceptionWhileProcessing`.
3. Если ошибка произошла до запуска запроса, создаётся одно событие с типом `ExceptionBeforeStart`.

Вы можете использовать настройку [log&#95;queries&#95;probability](/ru/reference/settings/session-settings/log-queries#log_queries_probability), чтобы уменьшить количество запросов, регистрируемых в таблице `query_log`.

Вы можете использовать настройку [log&#95;formatted&#95;queries](/ru/reference/settings/session-settings/log#log_formatted_queries), чтобы записывать отформатированные запросы в столбец `formatted_query`.

Эту таблицу безопасно очищать (TRUNCATE) или удалять в любой момент.

Сюда входят обычные подзапросы, а также подзапросы для IN и JOIN. Для распределённых запросов read&#95;rows включает общее количество строк, прочитанных на всех репликах. Каждая реплика отправляет своё значение read&#95;rows, а сервер-инициатор запроса суммирует все полученные и локальные значения. Объёмы кэша не влияют на это значение.

Сюда входят обычные подзапросы, а также подзапросы для IN и JOIN. Для распределённых запросов read&#95;bytes включает общее количество строк, прочитанных на всех репликах. Каждая реплика отправляет своё значение read&#95;bytes, а сервер-инициатор запроса суммирует все полученные и локальные значения. Объём кэша не влияет на это значение.

Для запросов, не записывающих строки, значение равно 0.
* `written_bytes` ([UInt64](/ru/reference/data-types/int-uint)) — Количество байтов, записанных запросом (без сжатия), включая байты, записанные последующими вставками, вызванными конвейером, например в attached materialized view. Для синхронной вставки эти последующие байты записываются в запись с `query_kind` = `Insert`; для асинхронной вставки они записываются в запись с `query_kind` = `AsyncInsertFlush`, тогда как клиентская запись `Insert` фиксирует только байты, принятые от клиента, причём лишь при `wait_for_async_insert = 1`, когда вставка ожидает результата сброса на диск; при `wait_for_async_insert = 0` клиентская запись `Insert` возвращается до сброса на диск, и значение этого поля остаётся равным 0. Для запросов, не выполняющих запись данных, значение равно 0.

* `used_number_of_joins` ([UInt64](/ru/reference/data-types/int-uint)) — Количество физических JOIN, выполненных для этого запроса. Значение собирается из конвейеров по мере их построения, поэтому отражает JOIN, оставшиеся после всех оптимизаций, а не количество предложений JOIN в тексте запроса. JOIN учитывается независимо от глубины вложенности: подзапросы, общие табличные выражения (CTE), представления, представления над представлениями и SELECT materialized view, запускаемого запросом INSERT, — все они учитываются в строке отправленного запроса, поэтому значение может быть ненулевым даже для запроса, в тексте которого нет ни одного JOIN. Запрос, который строит конвейер, не выполняя его (например, EXPLAIN PIPELINE), возвращает JOIN того запроса, который он объясняет. Некоторые конвейеры собираются несколько раз в ходе выполнения одного запроса: SELECT materialized view собирается для каждого блока запускающего его INSERT и каждым потоком вставки, рекурсивная часть рекурсивного CTE собирается на каждой итерации, а отношение цикла собирается заново при каждом его перезапуске. Тем не менее JOIN такого конвейера учитываются один раз, поэтому это число характеризует сам запрос, а не то, сколько раз собирались его конвейеры.
* `used_join_algorithms` ([Array(LowCardinality(String))](/ru/reference/data-types/array)) — Алгоритмы JOIN, учтённых в used&#95;number&#95;of&#95;joins: &#39;HASH&#39;, &#39;GRACE&#95;HASH&#39;, &#39;PARTIAL&#95;MERGE&#39;, &#39;FULL&#95;SORTING&#95;MERGE&#39;, &#39;PARALLEL&#95;FULL&#95;SORTING&#95;MERGE&#39;, &#39;INEQUALITY&#39;, &#39;BLOCK&#95;NESTED&#95;LOOP&#39;, &#39;DIRECT&#39;, &#39;PASTE&#39; и &#39;CONSTANT&#39;, отсортированные и без повторов, поэтому алгоритм, общий для нескольких JOIN, указывается один раз. Это алгоритм, фактически выбранный для выполнения каждого JOIN, а не алгоритмы, разрешённые настройкой join&#95;algorithm. Hash JOIN обозначается как &#39;HASH&#39; независимо от того, строилась ли его хеш-таблица в одном потоке или в нескольких. Алгоритм может быть заменён другим в ходе выполнения — в этом случае указываются оба.
* `used_join_kinds` ([Array(LowCardinality(String))](/ru/reference/data-types/array)) — Виды JOIN, учтённых в used&#95;number&#95;of&#95;joins, по одному элементу на каждый JOIN, поэтому вид, общий для нескольких JOIN, встречается несколько раз. Элементы отсортированы, а не перечислены в порядке выполнения. Указывается вид фактически выполненного JOIN, который может отличаться от указанного в тексте запроса: оптимизатор может выполнить JOIN, поменяв стороны местами, и тем самым превратить LEFT в RIGHT.
* `used_join_strictness` ([Array(LowCardinality(String))](/ru/reference/data-types/array)) — Строгость JOIN, учтённых в used&#95;number&#95;of&#95;joins, по одному элементу на каждый JOIN, в том же порядке, что и в used&#95;join&#95;kinds: элементы с одинаковым индексом в обоих массивах описывают один и тот же JOIN.
* `spilled_to_disk` ([Array(LowCardinality(String))](/ru/reference/data-types/array)) — Операторы, которые во время выполнения запроса записывали данные во временные файлы на диске (обработка во внешней памяти), отсортированные и без повторов. Пустой массив означает, что запрос был полностью выполнен в памяти.
* `transaction_id` ([Tuple(UInt64, UInt64, UUID, Int64)](/ru/reference/data-types/tuple)) — Идентификатор транзакции, в рамках которой был выполнен этот запрос.
* `query_cache_usage` ([Enum8(&#39;Unknown&#39; = 0, &#39;None&#39; = 1, &#39;Write&#39; = 2, &#39;Read&#39; = 3)](/ru/reference/data-types/enum)) — Использование кэша запросов во время выполнения запроса. Значения: &#39;Unknown&#39; = статус неизвестен, &#39;None&#39; = результат запроса не был ни записан в кэш результатов запросов, ни прочитан из него, &#39;Write&#39; = результат запроса был записан в кэш результатов запросов, &#39;Read&#39; = результат запроса был прочитан из кэша результатов запросов.
* `asynchronous_read_counters` ([Map(LowCardinality(String), UInt64)](/ru/reference/data-types/map)) — Метрики асинхронного чтения.
* `is_internal` ([UInt8](/ru/reference/data-types/int-uint)) — Указывает, является ли запрос вспомогательным внутренним запросом.
* `query_plan` (`JSON`) — План запроса, к которому относится данная строка, сериализованный в JSON, со статистикой выполнения по каждому шагу. Заполняется только при включённой настройке `log_query_plans` и остаётся пустым для строк `QueryStart`, поскольку на этот момент плана ещё нет. Для строки запроса, завершившегося исключением, сохраняется план, построенный запросом к моменту исключения, и статистики он не содержит: план запроса, завершившегося сбоем во время выполнения, был выполнен лишь частично, а план запроса, завершившегося сбоем до начала выполнения, не выполнялся вовсе. План маскируется с помощью `query_masking_rules`; для запроса, в котором срабатывает какое-либо правило, а также для запроса с секретными аргументами план не сохраняется.

**Пример для Cloud**

В ClickHouse Cloud таблица `system.query_log` локальна для каждого узла; чтобы увидеть все записи, необходимо выполнять запрос через [`clusterAllReplicas`](/ru/reference/functions/table-functions/cluster).

Например, чтобы агрегировать строки из query&#95;log со всех реплик кластера “default”, можно написать:

```sql
SELECT *
FROM clusterAllReplicas('default', system.query_log)
WHERE event_time >= now() - toIntervalHour(1)
LIMIT 10
SETTINGS skip_unavailable_shards = 1;
```
