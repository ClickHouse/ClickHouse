Эти настройки доступны в [system.merge&#95;tree&#95;settings](/ru/reference/system-tables/merge_tree_settings) и автоматически генерируются из исходного кода ClickHouse.

## max_bytes_to_buffer_for_packed_part {#max_bytes_to_buffer_for_packed_part}

<SettingsInfoBlock type="UInt64" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Новая настройка. Ограничивает объём памяти, занимаемый буферизованными данными записываемой упакованной части данных, за счёт их перемещения во временные данные. 0 — все данные хранятся в памяти, как и раньше."}]}]} />

Максимальный объём памяти, занимаемый буферизованными данными упакованной части данных при её записи
в ходе вставки, слияния или мутации. Упакованная часть данных хранит данные всех своих файлов в памяти до тех пор,
пока запись части не будет завершена. Как только объём буферизованных данных превышает этот лимит, данные самых больших файлов
перемещаются во временные файлы во временном хранилище сервера (`tmp_path`, `tmp_policy` или
`temporary_data_in_cache`) и считываются обратно при завершении записи. Временные файлы учитываются в
`max_temporary_data_on_disk_size_for_query` и `max_temporary_data_on_disk_size_for_user`.
Последний блок (до 64 КиБ) каждого файла, запись которого ещё не завершена, переместить нельзя, поэтому часть данных,
в которую одновременно записывается много файлов (например, широкая часть с большим количеством столбцов), может занимать больше памяти.
Данные части перемещаются в один временный файл, буферы записи которого (около 2 МиБ при значении
`temporary_files_buffer_size` по умолчанию) остаются в памяти до завершения записи части.
Лимит применяется отдельно к самой части и к каждой из её проекций. 0 означает отсутствие ограничения.

## max_bytes_to_merge_at_max_space_in_pool {#max_bytes_to_merge_at_max_space_in_pool}

<SettingsInfoBlock type="UInt64" default_value="161061273600" />

Максимальный суммарный размер частей (в байтах), которые могут быть слиты в одну часть, если
доступно достаточно ресурсов. Примерно соответствует максимально возможному
размеру части, создаваемой автоматическим фоновым слиянием. (0 означает, что слияния будут отключены)

Возможные значения:

* Любое неотрицательное целое число.

Планировщик слияний периодически анализирует размеры и количество частей в
партициях и, если в пуле достаточно свободных ресурсов, запускает
фоновые слияния. Слияния выполняются до тех пор, пока суммарный размер исходных частей не
превысит `max_bytes_to_merge_at_max_space_in_pool`.

Слияния, инициированные командой [OPTIMIZE FINAL](/ru/reference/statements/optimize),
игнорируют `max_bytes_to_merge_at_max_space_in_pool` (учитывается только свободное место
на диске).

## max_bytes_to_merge_at_min_space_in_pool {#max_bytes_to_merge_at_min_space_in_pool}

<SettingsInfoBlock type="UInt64" default_value="1048576" />

Максимальный суммарный размер частей (в байтах), которые могут быть
слиты в одну часть, при минимуме доступных ресурсов в фоновом пуле.

Возможные значения:

* Любое положительное целое число.

`max_bytes_to_merge_at_min_space_in_pool` задаёт максимальный суммарный размер
частей, которые могут быть слиты даже при нехватке доступного места на диске (в пуле).
Это необходимо, чтобы уменьшить количество мелких частей и вероятность
ошибок `Too many parts`.
Слияние резервирует место на диске, удваивая общий размер сливаемых частей.
Таким образом, при небольшом объёме свободного места на диске может возникнуть ситуация,
когда свободное место есть, но оно уже зарезервировано текущими крупными слияниями,
поэтому другие слияния не могут начаться, а число мелких частей растёт
с каждой вставкой.
