Эти настройки определяют конфигурацию сервера ClickHouse и автоматически сгенерированы на основе исходного кода ClickHouse.

## workloads_respect_server_cpu_limit {#workloads_respect_server_cpu_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />

Если настройка включена, общесерверный лимит параллелизма CPU применяется через планировщик рабочих нагрузок. Ресурс CPU `__server_cpu__` (для `MASTER THREAD` и `WORKER THREAD`) создаётся неявно, если ни для одной из этих ролей не определён ресурс, а значение `max_concurrent_threads` корневой рабочей нагрузки (рабочей нагрузки с пустым именем) вычисляется на основе `concurrent_threads_soft_limit_num` и `concurrent_threads_soft_limit_ratio_to_cores`. Таким образом, все рабочие нагрузки используют общий бюджет CPU-слотов, определяемый этими настройками. Планирование ресурсов CPU в этом случае выполняет планировщик рабочих нагрузок, а не встроенный механизм управления параллелизмом.

Включайте `implicit_default_workload` вместе с этой настройкой (или определите рабочую нагрузку `default`). Этот бюджет ограничивает только запросы, отнесённые к какой-либо рабочей нагрузке. Если рабочая нагрузка `default` не определена, то запросы со значением настройки `workload` по умолчанию, а также фоновые слияния и мутации, использующие рабочую нагрузку по умолчанию, вообще не ограничиваются по CPU: встроенный механизм управления параллелизмом (`concurrent_threads_soft_limit_num`) на них тоже больше не распространяется. При `throw_on_unknown_workload = 1` такие запросы завершаются с ошибкой.

Может изменяться во время выполнения. По умолчанию отключена.

**Пример**

```xml
<workloads_respect_server_cpu_limit>true</workloads_respect_server_cpu_limit>
```

## workloads_respect_server_memory_limit {#workloads_respect_server_memory_limit}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="Yes" />

Если настройка включена, общесерверное ограничение памяти применяется через планировщик рабочих нагрузок в виде бюджета резервирования памяти. Если ресурс `MEMORY RESERVATION` не определен, неявно создается ресурс `__server_memory__`, а `max_memory` корневой рабочей нагрузки (рабочей нагрузки с пустым именем) вычисляется на основе `max_server_memory_usage` (и соответствующей доли оперативной памяти). Таким образом, все рабочие нагрузки используют общий бюджет резервирования памяти, заданный этой настройкой. Это бюджет допуска резервирований; он не заменяет ограничение памяти на уровне процесса, которое продолжает действовать. Бюджет определяется по настроенному значению `max_server_memory_usage` при загрузке или перезагрузке конфигурации и не отслеживает изменения ограничения на уровне процесса, вносимые во время выполнения через `memory_worker_dynamic_hard_limit`. Поэтому в промежутках между перезагрузками он может превышать действующее ограничение.

Включайте `implicit_default_workload` вместе с этой настройкой (или определите рабочую нагрузку `default`). Память из этого бюджета резервируют только запросы, отнесенные к какой-либо рабочей нагрузке: если рабочая нагрузка `default` не определена, запрос со значением настройки `workload` по умолчанию не резервирует из него память, а при `throw_on_unknown_workload = 1` такой запрос завершается с ошибкой. Фоновые слияния и мутации никогда не резервируют память через рабочие нагрузки, поэтому используемая ими память в любом случае не входит в этот бюджет.

Может изменяться во время выполнения. По умолчанию отключено.

**Пример**

```xml
<workloads_respect_server_memory_limit>true</workloads_respect_server_memory_limit>
```

**См. также**

* [Планирование рабочих нагрузок](/ru/concepts/features/configuration/server-config/workload-scheduling)
