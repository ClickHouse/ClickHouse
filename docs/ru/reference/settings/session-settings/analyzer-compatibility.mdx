<div id="analyzer_compatibility_allow_compound_identifiers_in_unflatten_nested">
  ## analyzer_compatibility_allow_compound_identifiers_in_unflatten_nested
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.8"},{"label": "1"},{"label": "Новая настройка."}]}]} />

Разрешает добавлять составные идентификаторы в Nested. Это настройка совместимости, поскольку она меняет результат запроса. Когда она отключена, `SELECT a.b.c FROM table ARRAY JOIN a` не работает, а `SELECT a FROM table` не включает столбец `a.b.c` в результат `Nested a`.

<div id="analyzer_compatibility_allow_non_aggregate_in_having">
  ## analyzer_compatibility_allow_non_aggregate_in_having
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.7"},{"label": "0"},{"label": "Новая настройка совместимости. Если она включена, анализатор имитирует прежнее преобразование `HAVING` в `WHERE` для неагрегатных AND-конъюнктов вместо выдачи `NOT_AN_AGGREGATE`."}]}]} />

Если параметр включен, анализатор имитирует прежнее поведение, при котором неагрегатные AND-конъюнкты переносятся из `HAVING` в предложение WHERE вместо выдачи `NOT_AN_AGGREGATE`. Отклонение в соответствии со стандартом используется по умолчанию; эта настройка помогает при миграции запросов, которые старый анализатор (`enable_analyzer = 0`) молча принимал. Конъюнкты, содержащие агрегатные функции, `grouping` или недетерминированные функции, остаются в `HAVING`. Если хотя бы один конъюнкт содержит window function или функцию с сохранением состояния (например, `rowNumberInBlock`), преобразование отключается для всего `HAVING`, что соответствует прежнему поведению `PredicateExpressionsOptimizer`. Эта настройка также игнорируется, если в `GROUP BY` используются `WITH CUBE`, `WITH ROLLUP`, `WITH TOTALS` или `GROUPING SETS`.

  ## analyzer_compatibility_apply_final_to_all_joined_tables
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "0"},{"label": "Новая настройка в master (по умолчанию false — исправленное поведение). Добавлена со значением true по умолчанию (прежнее поведение) для бэкпортов в версии до 26.6."}]}]} />

Восстанавливает поведение версий до 26.6, при котором модификатор `FINAL`, указанный для самой левой таблицы в JOIN, ошибочно применялся также ко всем остальным таблицам в JOIN (для движков, поддерживающих `FINAL`, например `ReplacingMergeTree`). По умолчанию `FINAL` применяется только к таблице, для которой он указан. Включите настройку для совместимости с запросами, зависящими от прежнего поведения; рекомендуется явно указывать `FINAL` для каждой таблицы, которой он требуется.

Возможные значения:

* 0 — `FINAL` применяется только к таблице, для которой он указан.
* 1 — `FINAL` для самой левой таблицы в JOIN применяется ко всем таблицам в JOIN.

<div id="analyzer_compatibility_join_using_top_level_identifier">
  ## analyzer_compatibility_join_using_top_level_identifier
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "24.3"},{"label": "0"},{"label": "Принудительно разрешать идентификатор в JOIN USING по проекции"}]}]} />

Принудительно разрешать идентификатор в JOIN USING по проекции (например, в `SELECT a + 1 AS b FROM t1 JOIN t2 USING (b)` JOIN будет выполняться по условию `t1.a + 1 = t2.b`, а не `t1.b = t2.b`). Также учитываются псевдонимы, определённые для подвыражений внутри списка SELECT (например, в `SELECT uniqExact(a + 1 AS b) FROM t1 JOIN t2 USING (b)` JOIN выполняется по условию `t1.a + 1 = t2.b`). Если соответствующий псевдоним определён для подвыражения внутри списка SELECT, а не как псевдоним верхнего уровня, для запроса отключаются параллельные реплики. Для запросов, отправляемых на удалённые серверы (таблицы `Distributed`, табличная функция `remote`), такой запрос отклоняется с исключением, только если идентификатор вообще не может быть разрешён на удалённом сервере; если псевдоним затеняет реальный столбец левой таблицы, удалённый сервер вместо этого выполняет JOIN по этому столбцу, поэтому результаты могут отличаться от локального выполнения.

<div id="analyzer_compatibility_multiple_joins_qualify_column_names">
  ## analyzer_compatibility_multiple_joins_qualify_column_names
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "0"},{"label": "Новая настройка совместимости. Если включена, анализатор воспроизводит квалифицированные имена результирующих столбцов, которые использовал старый анализатор для запросов, в предложении FROM которых есть два или более JOIN."}]}]} />

Если настройка включена и предложение `FROM` запроса содержит два или более `JOIN` (таблицы, перечисленные через запятую, учитываются; `ARRAY JOIN` — нет), анализатор присваивает результирующим столбцам имена так же, как это делало преобразование с несколькими JOIN в старом анализаторе:

* столбцы, полученные при раскрытии `*`, `<table>.*` или `COLUMNS('<regexp>')`, получают имена вида `<alias-or-table>.<column>` (квалификатором служит псевдоним табличного выражения, если он задан, иначе имя таблицы без указания базы данных, иначе имя CTE; столбцы присоединённого подзапроса без псевдонима остаются неквалифицированными). Два типа столбцов сохраняют имя без квалификатора, поскольку относятся к JOIN, а не к отдельному табличному выражению: столбец, полученный с помощью `ARRAY JOIN`, и ключ, объединённый с помощью `JOIN ... USING`. Поэтому внешние ссылки, такие как `SELECT ll.arr` или `SELECT ll.k`, в этих двух случаях не разрешаются;
* форма со списком идентификаторов `COLUMNS(col1, col2)` не является раскрытием по сопоставлению: каждый столбец сохраняет имя в точности в том виде, в котором записан его идентификатор, поэтому `COLUMNS(x)` создаёт `x`, а `COLUMNS(a.x)` создаёт `a.x`;
* ссылка на столбец без псевдонима в списке `SELECT` сохраняет имя в точности в записанном виде (например, `SELECT a.x` создаёт столбец с именем `a.x`, даже если `x` однозначен).

Благодаря этому внешние запросы могут ссылаться на такие столбцы по их квалифицированным именам, например:

```sql
SELECT ll.Date FROM (SELECT * FROM t AS ll LEFT JOIN t1 ON ll.k = t1.k LEFT JOIN t2 ON ll.k = t2.k);
```

Действует, только если включен анализатор (`enable_analyzer = 1`).

<div id="analyzer_compatibility_prefer_alias_over_subcolumn">
  ## analyzer_compatibility_prefer_alias_over_subcolumn
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.6"},{"label": "0"},{"label": "Новая настройка совместимости"}]}]} />

Если составной идентификатор, такой как `b.id`, может ссылаться либо на столбец `id` таблицы с псевдонимом `b`, либо на подстолбец `b.id` типа Tuple другого столбца, будет выбрана интерпретация с префиксом-псевдонимом (столбец `id` таблицы `b`). По умолчанию анализатор предпочитает подстолбец. Включите эту настройку, чтобы использовать правила разрешения имен старого анализатора.
