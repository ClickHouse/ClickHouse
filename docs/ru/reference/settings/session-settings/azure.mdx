## azure_validate_etag_on_read {#azure_validate_etag_on_read}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "1"},{"label": "Новая настройка для обнаружения параллельной перезаписи blob-объектов Azure на месте во время чтения: каждый запрос `GET` привязывается к полученному при листинге `ETag` с помощью `If-Match`, а `ETag` ответа проверяется — аналогично тому, как это делает `s3_validate_etag_on_read` для S3. При значении `compatibility`, соответствующем версиям до 26.10, восстанавливается прежнее поведение (без проверки)."}]}]} />

При чтении blob-объекта из Azure Blob Storage через табличные функции `azureBlobStorage` / `azureBlobStorageCluster` или движок таблицы `AzureBlobStorage` каждый запрос `GET` привязывается к той версии blob-объекта, которая была получена при его листинге: для этого его `ETag` передаётся в заголовке `If-Match`, а `ETag` ответа проверяется. Чтение одного файла порождает множество запросов `GET` с диапазонами; если между ними blob-объект перезаписывается на месте (например, внешней пишущей стороной, перезаписывающей фиксированный ключ), то без этой проверки прочитанные данные могут оказаться склеены из двух разных версий blob-объекта, что проявится как несовпадение контрольной суммы или ошибка разбора. Размер, зафиксированный при листинге, также используется как правая граница чтения, поэтому он корректен только для той версии, для которой был получен. При обнаружении несоответствия чтение завершается ошибкой `AZURE_OBJECT_CHANGED_DURING_READ`, а не возвращает несогласованные данные. Отключайте настройку только для рабочих нагрузок, которые намеренно читают перезаписываемые blob-объекты и допускают несогласованное чтение.
