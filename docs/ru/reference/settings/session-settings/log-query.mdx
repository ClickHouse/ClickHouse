## log_query_plans {#log_query_plans}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Новая настройка для сохранения фактически выполненного плана запроса вместе со статистикой выполнения по каждому шагу."}]}]} />

Записывает выполненный план запроса вместе со статистикой выполнения по каждому шагу в столбец `query_plan` таблицы [`system.query_log`](/ru/reference/system-tables/query_log). Столбец имеет тип `JSON`, поэтому статистика хранится в виде чисел и её можно не только читать, но и агрегировать запросами.

План содержит ту же информацию, что выводит [`EXPLAIN ANALYZE`](/ru/reference/statements/explain#explain-analyze), — дерево шагов, описание действия каждого шага, а также количество строк и байтов, реальное (wall-clock) время и параллелизм для каждого шага.

Сохраняются только `SELECT`-запросы, выполненные с анализатором (`enable_analyzer = 1`, значение по умолчанию), и только если сама строка записывается в журнал, поэтому должна быть также включена настройка [`log_queries`](/ru/reference/settings/session-settings/log-queries#log_queries). Для запроса, завершившегося ошибкой во время выполнения, сохраняется выполнявшийся план, но без статистики. В строках `QueryStart` столбец пуст, так как на момент их записи плана ещё нет.

План маскируется с помощью правил [`query_masking_rules`](/ru/reference/settings/server-settings/settings/query#query_masking_rules) сервера, так же как столбец `query`. Если в тексте запроса или в параметре запроса срабатывает какое-либо правило, план не сохраняется, поскольку свёртка констант может перенести маскируемый текст в план в форме, с которой не совпадает ни одно правило. В остальных случаях весь текст в плане, например условия фильтрации, списки `IN` и имена выходных столбцов, маскируется перед сохранением. Для запроса с секретными аргументами, например ключом функции `encrypt`, план также не сохраняется, поскольку их невозможно надёжно скрыть внутри плана.

При включении этой настройки сохраняемый запрос собирает время выполнения по каждому процессору — это то же инструментирование, что использует [`log_processors_profiles`](/ru/reference/settings/session-settings/log#log_processors_profiles), поэтому оно создаёт дополнительные накладные расходы. На несохраняемые запросы это не влияет. Используйте [`log_query_plans_probability`](/ru/reference/settings/session-settings/log-query#log_query_plans_probability), чтобы сохранять только случайную выборку запросов.

Решение о сборе статистики принимается до выполнения запроса, поэтому сохраняемый запрос всё равно несёт эти затраты, даже если его строка затем отбрасывается настройкой [`log_queries_min_type`](/ru/reference/settings/session-settings/log-queries#log_queries_min_type) или [`log_queries_min_query_duration_ms`](/ru/reference/settings/session-settings/log-queries#log_queries_min_query_duration_ms): на этом этапе ни то, ни другое ещё неизвестно. Запрос, результат которого получен из [кеша запросов](/ru/concepts/features/performance/caches/query-cache), не выполняет план, поэтому сохранять нечего.

Кроме того, описания шагов, созданные оптимизациями плана (например, для объединённых выражений), сохраняются, а не отбрасываются, поэтому они также становятся видны в `system.processors_profile_log.plan_step_description`.

См. также:

* [`system.query_log`](/ru/reference/system-tables/query_log)
* [`EXPLAIN PLAN`](/ru/reference/statements/explain#explain-plan)

## log_query_plans_max_size {#log_query_plans_max_size}

<ExperimentalBadge />

Ограничение действует и при `compatibility` с более ранними версиями: сам столбец новый, поэтому прежнего поведения, которое нужно было бы восстановить, нет, а настройка защищает ресурс сервера."}]}]} />

Максимальный размер в байтах документа, который [`log_query_plans`](/ru/reference/settings/session-settings/log-query#log_query_plans) записывает в столбец `query_plan` таблицы [`system.query_log`](/ru/reference/system-tables/query_log).

Объём текста в плане определяется самим запросом: в план попадают и большой список `IN`, и длинный псевдоним, и свёрнутая константа. Настройка ограничивает объём данных, которые один запрос может сохранить в своей строке, а поскольку документ записывается в буфер этого размера, она также ограничивает объём памяти, выделяемой при рендеринге одного плана.

План, который не помещается в лимит, не сохраняется в усечённом виде, поскольку половина документа — это уже не план. Вместо этого в столбце сохраняется причина в виде `{"Error": ...}`.

`0` означает отсутствие ограничения.

## log_query_plans_probability {#log_query_plans_probability}

<ExperimentalBadge />

<SettingsInfoBlock type="Float" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "1"},{"label": "Новая настройка, позволяющая при включённой `log_query_plans` сохранять план запроса только для случайной выборки запросов."}]}]} />

Сохраняет план запроса, включаемый настройкой [`log_query_plans`](/ru/reference/settings/session-settings/log-query#log_query_plans), только для выборки запросов, отбираемых случайным образом с заданной вероятностью. Запрос, не попавший в выборку, не несёт накладных расходов на сбор данных профилирования, связанных с [`log_query_plans`](/ru/reference/settings/session-settings/log-query#log_query_plans), а его строки в `system.query_log` по-прежнему записываются — с пустым столбцом `query_plan`.

Решение принимается для каждого запроса после того, как становится известно, что его план может быть сохранён, поэтому запросы, план которых не сохраняется в принципе (например, все запросы, кроме `SELECT`), в сэмплировании не участвуют.

Настройка действует поверх [`log_queries_probability`](/ru/reference/settings/session-settings/log-queries#log_queries_probability): если строки запроса не записываются, его план тоже не сохраняется, поэтому при значении `0.5` у обеих настроек план сохраняется примерно для четверти запросов.

Решение принимается до выполнения запроса, поэтому оно не может зависеть от длительности его выполнения. При использовании [`log_queries_min_query_duration_ms`](/ru/reference/settings/session-settings/log-queries#log_queries_min_query_duration_ms) каждый медленный запрос по-прежнему записывает свою строку, но план содержит лишь заданная доля этих строк, тогда как накладные расходы на сбор данных профилирования несёт та же доля всех запросов, включая быстрые.

Возможные значения:

* 0 — планы запросов не сохраняются.
* Положительное число с плавающей точкой в диапазоне [0..1]. Например, если значение настройки равно `0.1`, сохраняются планы примерно одного из десяти запросов.
* 1 — сохраняется план каждого запроса.

## log_query_threads {#log_query_threads}

<SettingsInfoBlock type="Bool" default_value="0" />

Включает журналирование потоков запросов.

Потоки запросов записываются в таблицу [system.query&#95;thread&#95;log](/ru/reference/system-tables/query_thread_log). Эта настройка действует, только если [log&#95;queries](/ru/reference/settings/session-settings/log-queries#log_queries) имеет значение true. Потоки запросов, выполняемых ClickHouse при включенной этой настройке, записываются в соответствии с правилами, заданными параметром конфигурации сервера [query&#95;thread&#95;log](/ru/reference/settings/server-settings/settings/query#query_thread_log).

Возможные значения:

* 0 — Отключено.
* 1 — Включено.

**Пример**

```text
log_query_threads=1
```

## log_query_views {#log_query_views}

<SettingsInfoBlock type="Bool" default_value="1" />

Включает журналирование представлений запросов.

Если у запроса, выполняемого ClickHouse при включенном этом параметре, есть связанные представления (материализованные или live view), они записываются в параметр конфигурации сервера [query&#95;views&#95;log](/ru/reference/settings/server-settings/settings/query#query_views_log).

Пример:

```text
log_query_views=1
```
