Мягкий порог на объём данных в байтах, которые один запрос записывает в кэш столбцов. Байты, записанные во время выполнения запроса, подсчитываются, и как только счётчик достигает этого значения, все последующие записи в кэш до конца запроса пропускаются. Это рекомендательный порог, а не жёсткое ограничение: считыватель накапливает записи прочитанных им гранул и записывает их в кэш одним батчем, причём батч, на котором порог превышается, сохраняется целиком, и лишь затем его объём учитывается счётчиком. Поэтому фактический объём записанных данных может превысить это значение на объём записей, которые один считыватель накапливает между двумя операциями записи (по одной записи на каждую полосу примерно из 65536 строк для каждого читаемого столбца), а при одновременной работе нескольких считывателей — на такой объём для каждого из них. Настройка нужна для того, чтобы одно крупное сканирование не вытесняло из кэша полезные данные, а не для точного ограничения использования кэша.

Значение `0` означает половину текущего ограничения размера кэша столбцов: заданного значения `columns_cache_size` или меньшего, если кэш уменьшен из-за нехватки памяти (см. метрику `ColumnsCacheSizeLimit`).

## columns_cache_max_estimated_bytes_to_write_to_cache {#columns_cache_max_estimated_bytes_to_write_to_cache}

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "0"},{"label": "Новая настройка: ограничение на оценочный объём несжатых байт, читаемых запросом, при котором разрешена запись в кэш столбцов (0 = половина текущего лимита размера кэша столбцов, который уменьшается при нехватке памяти)."}]}]} />

Если оценочный размер данных, которые запрос читает из частей `MergeTree`, превышает это значение, запись в кэш столбцов запрещается для всего запроса. Оценка выполняется в несжатых байтах (именно в них измеряется объём, занимаемый в кэше) на основе размера столбцов, которые читает запрос (включая столбцы `PREWHERE`, мутаций и patch-частей), пропорционально выбранным диапазонам меток, причём весь этот объём засчитывается запросу ещё до начала чтения. Благодаря этому одно крупное сканирование не вытесняет из кэша полезные данные и не копирует в кэш данные, которые всё равно не смогут в нём удержаться.

Значение `0` означает, что используется половина текущего лимита размера кэша столбцов. Пока у сервера достаточно свободной памяти, этот лимит равен заданному значению `columns_cache_size`, однако при нехватке памяти кэш уменьшается (см. метрику `ColumnsCacheSizeLimit`), а вместе с ним уменьшается и бюджет по умолчанию. При значении `columns_cache_size_ratio` по умолчанию половина лимита равна размеру испытательного сегмента кэша, поэтому данные запроса, прошедшего эту проверку, могут быть полностью закэшированы за один проход.

Проверка не применяется к чтению, которое отбрасывает диапазоны меток в процессе выполнения, — так происходит, когда включена настройка `use_indexes_refiner_in_read_pools`: сколько из выбранных меток такое чтение действительно затронет, становится известно только при формировании каждой задачи, поэтому приведённая выше оценка была бы лишь верхней границей и учитывала бы метки, которые запрос так и не прочитает. Для таких чтений объём записываемых данных ограничивается настройкой `columns_cache_max_bytes_to_write_to_cache`.
