## enable_join_runtime_filters_index_analysis {#enable_join_runtime_filters_index_analysis}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "Фильтры JOIN времени выполнения стали возможностью уровня Production."}]}, {"id": "row-2","items": [{"label": "26.7"},{"label": "0"},{"label": "Новая настройка для фильтрации JOIN с помощью динамического анализа индексов"}]}, {"id": "row-3","items": [{"label": "26.10"},{"label": "1"},{"label": "Включает отсечение гранул на проверяемой (левой) стороне JOIN с помощью фильтра времени выполнения, сформированного на стороне построения (правой)."}]}]} />

Отсекает гранулы на проверяемой стороне JOIN с помощью фильтра времени выполнения, сформированного на стороне построения; см. `enable_join_runtime_filters`.
Действует только при `use_skip_indexes_on_data_read = 1`.
Отсечение возможно только по ключу JOIN, который является столбцом первичного ключа проверяемой стороны или охвачен индексом пропуска данных `minmax`, `set` либо `bloom_filter`.
Если фильтр времени выполнения сохранил точные значения ключа, для отсечения используется предикат `IN` с набором этих значений; иначе используется диапазон от минимального до максимального значения ключа, что снижает эффективность отсечения.

Работает с параллельными репликами (`enable_parallel_replicas = 1`): каждая реплика отсекает читаемые ею гранулы с помощью фильтра, который построила сама. Такой фильтр может быть неполным: при `RIGHT` JOIN между репликами распределяется именно сторона построения, поэтому фильтр каждой реплики охватывает только её собственную долю этой стороны. Тем не менее результат остаётся корректным, поскольку разделяется ровно одна сторона JOIN, каждая пара совпадающих строк встречается ровно на одной реплике, а каждая реплика выдаёт непересекающуюся часть результата.

Отсечение гранул не происходит при использовании распределённого плана запроса (`make_distributed_plan = 1`). В этом режиме настройка не имеет эффекта: результат запроса не меняется, а сам фильтр JOIN времени выполнения работает точно так же, как при отключённой настройке; не выполняется только отсечение гранул.

Отсечение гранул также не выполняется при чтении проверяемой стороны с `FINAL` (отсечение для чтения с `FINAL` не реализовано, а `optimizeLazyFinal` перестраивает такой этап чтения без дескрипторов), а также для таблиц с данными, ожидающими обработки, мутациями `ALTER` или патч-частями. В этих случаях настройка тоже не имеет эффекта.

## enable_join_seal_gated_reading {#enable_join_seal_gated_reading}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "0"},{"label": "Новая экспериментальная настройка, которая откладывает чтение на проверяемой стороне в hash JOIN до завершения построения фильтра времени выполнения на стороне построения и отсекает по этому фильтру диапазоны чтения."}]}]} />

Откладывает чтение на проверяемой стороне в hash JOIN до завершения построения фильтра времени выполнения на стороне построения (см. `enable_join_runtime_filters`): пока фильтр не готов, на проверяемой стороне ничего не читается, а затем фильтр используется для отсечения целых диапазонов меток по первичному ключу ещё до создания задач чтения — в дополнение к обычной фильтрации на уровне строки. Это ожидание представлено в виде ребра конвейера запроса. При отложенном чтении анализ индексов по тому же фильтру времени выполнения во время чтения (см. `enable_join_runtime_filters_index_analysis`) пропускается как избыточный.

Экспериментальная настройка. Отложенное чтение применяется к локальным чтениям, в том числе к single-threaded чтению и чтению в порядке ключа. Чтения с FINAL, с параллельными репликами или в JOIN, сегментированном по диапазонам первичного ключа, переключаются на резервный вариант — обычное чтение без ожидания с фильтрацией на уровне строки.

## enable_join_transitive_predicates {#enable_join_transitive_predicates}
