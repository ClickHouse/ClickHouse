## enable_join_key_only_hash_tables {#enable_join_key_only_hash_tables}

<SettingsInfoBlock type="Bool" default_value="1" />

Использовать хеш-таблицы, в которых хранятся только ключи JOIN, без ссылки на правую строку, для тех JOIN, результат которых заведомо не может содержать значение из правой строки: `LEFT ANTI`, а также `LEFT SEMI`, когда не выбран ни один правый столбец. У такой таблицы меньше размер ячейки, и она позволяет отбрасывать правые блоки вместо их хранения.

## enable_join_runtime_filters_index_analysis {#enable_join_runtime_filters_index_analysis}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "JOIN Runtime Filters стали возможностью уровня Production."}]}, {"id": "row-2","items": [{"label": "26.7"},{"label": "0"},{"label": "Новая настройка для фильтрации JOIN с помощью динамического анализа индексов"}]}, {"id": "row-3","items": [{"label": "26.10"},{"label": "1"},{"label": "Включает отсечение гранул на проверяемой (левой) стороне JOIN с помощью фильтра, сформированного во время выполнения на стороне построения (правой)."}]}]} />

Отсекает гранулы на проверяемой стороне JOIN с помощью фильтра, сформированного во время выполнения на стороне построения; см. `enable_join_runtime_filters`.
Действует только при `use_skip_indexes_on_data_read = 1`.
Отсечение возможно только по ключу JOIN, который является столбцом первичного ключа проверяемой стороны или охвачен индексом пропуска данных `minmax`, `set` либо `bloom_filter`.
Если фильтр сохранил точные значения ключа, для отсечения используется предикат `IN` с набором этих значений; иначе используется диапазон от минимального до максимального значения ключа, что снижает эффективность отсечения.

Действует только при локальном чтении проверяемой стороны JOIN. Дескрипторы, управляющие отсечением, привязываются к этапу чтения при оптимизации плана запроса и не переносятся при перестроении этого этапа для удалённого выполнения. Поэтому отсечение гранул не происходит при использовании параллельных реплик (`enable_parallel_replicas = 1`) или распределённого плана запроса (`make_distributed_plan = 1`). В этих режимах настройка не имеет эффекта: результат запроса не меняется, а сам фильтр JOIN, создаваемый во время выполнения, работает точно так же, как при отключённой настройке; не выполняется только отсечение гранул.

Отсечение гранул также не выполняется при чтении проверяемой стороны с `FINAL` (отсечение для чтения с `FINAL` не реализовано, а `optimizeLazyFinal` перестраивает такой этап чтения без дескрипторов), а также для таблиц с данными, ожидающими обработки, мутациями `ALTER` или патч-частями. В этих случаях настройка тоже не имеет эффекта.

## enable_join_transitive_predicates {#enable_join_transitive_predicates}

<BetaBadge />

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.6"},{"label": "1"},{"label": "Параметр enable_join_transitive_predicates включен по умолчанию"}]}, {"id": "row-2","items": [{"label": "26.4"},{"label": "0"},{"label": "Новая настройка для вывода транзитивных предикатов эквисоединения при оптимизации порядка JOIN."}]}]} />

Выводит транзитивные предикаты эквисоединения из существующих условий JOIN.
Например, если заданы `A.x = B.x` и `B.x = C.x`, добавляется синтетический предикат `A.x = C.x`,
чтобы оптимизатор порядка JOIN мог учитывать прямые планы (A JOIN C).
