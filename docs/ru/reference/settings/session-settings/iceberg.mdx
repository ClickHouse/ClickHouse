## iceberg_list_only_v_prefixed_metadata_files {#iceberg_list_only_v_prefixed_metadata_files}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Новая настройка: при поиске последнего файла метаданных таблицы Iceberg, читаемой по пути, получать список только по префиксу ключа `metadata\/v`."}]}]} />

Ищет последний файл метаданных таблицы Iceberg, читаемой по пути в S3 или Azure, получая список только по префиксу ключа `metadata/v`, чтобы не перечислять манифесты, хранящиеся в том же каталоге `metadata`. Если по этому префиксу находятся файлы `.metadata.json`, кандидатами считаются только они; в противном случае запрашивается список всего каталога. Не применяется вместе с `iceberg_use_version_hint`, `iceberg_metadata_file_path`, `iceberg_metadata_table_uuid` или `iceberg_recent_metadata_file_by_last_updated_ms_field`, а также к таблицам базы данных каталога озера данных.

Включайте эту настройку только для таблиц, все файлы метаданных которых имеют имена вида `v<N>...` (так их именуют ClickHouse и каталоги Hadoop): если в каталоге есть также файлы `<N>-<uuid>.metadata.json`, они никогда не становятся кандидатами, и коммиты создающей их пишущей стороны остаются невидимыми.

Задавайте значение больше максимального времени, которое может занять коммит записи в таблицу. 0 отключает проверку.

## iceberg_tolerate_conflicting_manifest_schemas {#iceberg_tolerate_conflicting_manifest_schemas}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "Новая настройка: если заголовок файла манифеста Iceberg содержит схему, конфликтующую со схемой, зарегистрированной для того же schema-id в metadata.json, использовать схему из metadata.json вместо аварийного завершения запроса — так же, как это делают другие движки запросов. Значение `compatibility` ниже 26.8 возвращает прежнее строгое поведение."}]}, {"id": "row-2","items": [{"label": "26.10"},{"label": "1"},{"label": "Изменение было бэкпортировано в 26.8 и зафиксировано там."}]}]} />

Если настройка включена и schema-id файла манифеста Iceberg уже зарегистрирован из metadata.json, используется схема из metadata.json, а копия в ключе `schema` заголовка файла манифеста игнорируется без сравнения. Если настройка отключена, копия из заголовка манифеста сравнивается со схемой из metadata.json, и при конфликте запрос завершается с ошибкой ICEBERG&#95;SPECIFICATION&#95;VIOLATION.

Схема в заголовке манифеста — это лишь копия схемы таблицы на момент записи манифеста, и известны случаи, когда некоторые пишущие стороны (например, обслуживающие задачи AWS S3 Tables) сохраняли там неполноценные копии. Другие движки запросов берут схемы из metadata.json и игнорируют расходящиеся копии из заголовков, поэтому поведение по умолчанию соответствует их логике. Конфликт между двумя определениями схем в самом metadata.json по-прежнему всегда приводит к ошибке запроса.
