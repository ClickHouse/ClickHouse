## allow_experimental_analyzer {#allow_experimental_analyzer}

**Псевдонимы**: `enable_analyzer`

Устарело с v26.9: анализатор больше нельзя отключить.

Анализатор — это инфраструктура для анализа и планирования запросов, используемая по умолчанию с версии v24.3. В v26.9 эта настройка зафиксирована на единственном поддерживаемом значении `1`, а настройка `compatibility` больше не возвращает прежнее поведение. В v26.10 анализ запросов, на который она переключала, был удалён. Для обратной совместимости значение `0` принимается, но заменяется на `1`, поэтому запросы, настройки сеанса, профили настроек и конфигурации клиентов, в которых по-прежнему задано `enable_analyzer = 0`, продолжают работать — но уже с анализатором. Чтобы сравнить поведение или производительность запроса с прежним анализом запросов, используйте версию ClickHouse старше v26.9.

## allow_experimental_logsql_dialect {#allow_experimental_logsql_dialect}

<ExperimentalBadge />

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "0"},{"label": "Новая настройка, включающая диалект LogsQL (язык запросов к журналам VictoriaLogs)."}]}]} />

Включает LogsQL — язык запросов к журналам VictoriaLogs. Запросы на этом диалекте преобразуются в SELECT-запросы к таблице, заданной настройкой `logsql_table`.

Использование:

```sql
SET allow_experimental_logsql_dialect = 1;
SET logsql_table = 'logs';
SET dialect = 'logsql';

_time:1h error | stats by (host) count()
```

Полный самостоятельный запрос `SET` по-прежнему разбирается как обычный SQL, чтобы можно было
вернуться к прежнему диалекту; запрос LogsQL, который лишь начинается со слова `set`, сохраняет своё значение.
Настройки `logsql_time_column` и `logsql_message_column` задают столбцы,
на которые ссылаются поле `_time` и поле по умолчанию (поле сообщения).

В отличие от VictoriaLogs, где каждое поле хранится как строка, транслированные запросы выполняются
над существующей схемой таблицы. Отсюда вытекают основные отступления от контракта:

* Текстовые фильтры (слова, фразы, префиксы, регулярные выражения) рассчитаны на столбцы типа `String` и не преобразуют числовые столбцы в текст.
* Фильтры числового сравнения сравнивают числовые столбцы нативно (точно — для целых и десятичных значений, если сравниваемый литерал помещается в `Int128` или `Decimal256(38)`; более широкое значение, например целое число больше 1e38 в поле `UInt256`, сравнивается с точностью `Float64`, как и целочисленные шаги бакетов в `stats by (<field>:<step>)`). Для столбцов типа `String` построчно разбирается только обычный числовой текст; значения в числовой грамматике LogsQL (например, `10KiB`, `1h30m`) построчно не разбираются.
* Числовые статистические функции (`sum`, `avg`, `median`, `quantile`, `stddev`, `rate_sum`), как и в VictoriaLogs, разбирают числовое значение каждого поля, пропуская нечисловые значения. Значения имеют тип `Float64`, поэтому числовой столбец агрегируется не точно, а с точностью `Float64`.
* Пайп `math` требует числовых столбцов-операндов; столбцы типа `String` к числовому типу не приводятся.
* Результаты запросов возвращаются с типами исходных столбцов, а не в виде строк.
