<div id="backward-incompatible-change">
  #### Обратно несовместимое изменение
</div>

* Теперь реплики, обрабатывающие команду `ALTER TABLE ATTACH PART[ITION]`, ищут данные в своих каталогах `detached/` перед тем, как получать их с других реплик. В рамках реализации в журнал репликации добавлена новая команда `ATTACH_PART`. Части ищутся и сравниваются по их контрольным суммам. [#18978](https://github.com/ClickHouse/ClickHouse/pull/18978) ([Mike Kot](https://github.com/myrrc)).
* Столбец `keys` в таблице `system.dictionaries` заменён столбцами `key.names` и `key.types`. Столбцы `key.names`, `key.types`, `attribute.names`, `attribute.types` из таблицы `system.dictionaries` не требуют загрузки словаря. [#21884](https://github.com/ClickHouse/ClickHouse/pull/21884) ([Maksim Kita](https://github.com/kitaisreal)).
* Исправлена ошибка в `cutToFirstSignificantSubdomainCustom()`/`firstSignificantSubdomainCustom()`, из-за которой функции возвращали неверный результат для доменов третьего и более низких уровней, присутствующих в пользовательском списке доменов верхнего уровня. Для входных доменов, соответствующих этим пользовательским доменам верхнего уровня, домен третьего уровня считался первым значимым. Теперь это исправлено. Это изменение может привести к несовместимости, если функция используется, например, в ключе сегментирования. [#21946](https://github.com/ClickHouse/ClickHouse/pull/21946) ([Azat Khuzhin](https://github.com/azat)).
* `toStartOfIntervalFunction` теперь будет выравнивать часовые интервалы по полуночи (в предыдущих версиях они выравнивались по началу Unix epoch). Например, `toStartOfInterval(x, INTERVAL 11 HOUR)` будет разбивать каждый день на три интервала: 00:00:00..10:59:59, 11:00:00..21:59:59 и 22:00:00..23:59:59. Такое поведение лучше соответствует практическим потребностям. Это закрывает [#9510](https://github.com/ClickHouse/ClickHouse/issues/9510). [#22060](https://github.com/ClickHouse/ClickHouse/pull/22060) ([Alexey Milovidov](https://github.com/alexey-milovidov)).

<div id="performance-improvement">
  #### Повышение производительности
</div>

* Добавлена поддержка параллельного парсинга для форматов `CSVWithNames` и `TSVWithNames`. Это закрывает [#21085](https://github.com/ClickHouse/ClickHouse/issues/21085). [#21149](https://github.com/ClickHouse/ClickHouse/pull/21149) ([Nikita Mikhaylov](https://github.com/nikitamikhaylov)).
* Производительность повышена за счёт замены `memcpy` на другую реализацию. Это закрывает [#18583](https://github.com/ClickHouse/ClickHouse/issues/18583). [#21520](https://github.com/ClickHouse/ClickHouse/pull/21520) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Добавлена поддержка параллельного форматирования в clickhouse-local и в других местах. [#21630](https://github.com/ClickHouse/ClickHouse/pull/21630) ([Nikita Mikhaylov](https://github.com/nikitamikhaylov)).
* Оптимизирована производительность запросов вида `SELECT ... FINAL ... WHERE`. Теперь в запросах с `FINAL` разрешено перемещать в `PREWHERE` столбцы, которые входят в ключ сортировки. ... [#21830](https://github.com/ClickHouse/ClickHouse/pull/21830) ([foolchi](https://github.com/foolchi)).
* Ускорен `GROUP BY` при небольшом `max_rows_to_group_by` и `group_by_overflow_mode='any'`. [#21856](https://github.com/ClickHouse/ClickHouse/pull/21856) ([Nikolai Kochetov](https://github.com/KochetovNicolai)).
* Исключено лишнее копирование данных при использовании кодека `NONE`. Обратите внимание, что кодек `NONE` в большинстве случаев бесполезен — рекомендуется всегда использовать сжатие (`LZ4` используется по умолчанию). Вопреки распространённому мнению, отключение сжатия может не повысить производительность (возможен и обратный эффект). Кодек `NONE` полезен в некоторых случаях: - когда данные не поддаются сжатию; - для синтетических бенчмарков. [#22145](https://github.com/ClickHouse/ClickHouse/pull/22145) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Добавлен кэш для файлов, читаемых с настройкой `min_bytes_to_use_mmap_io`. Это даёт значительный прирост производительности (в 2 раза и более), когда значение настройки мало, за счёт уменьшения числа частых вызовов mmap/munmap и связанных с ними page fault. Обратите внимание, что mmap IO имеет серьёзные недостатки, из-за которых оно менее надёжно в продакшн (например, зависания или SIGBUS на неисправных дисках; менее контролируемое использование памяти). Тем не менее для бенчмарков оно хорошо подходит. [#22206](https://github.com/ClickHouse/ClickHouse/pull/22206) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Включено чтение с mmap IO для диапазонов файлов от 64 MiB (настройка `min_bytes_to_use_mmap_io`). Это может дать умеренный прирост производительности. [#22326](https://github.com/ClickHouse/ClickHouse/pull/22326) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
