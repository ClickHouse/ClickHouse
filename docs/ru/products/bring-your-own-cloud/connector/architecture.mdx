## Компоненты {#components}

Коннектор ClickHouse запускает три демона, все они встроены в бинарный файл `clicklink`:

* **Исполнитель** поддерживает исходящий командный канал к конечной точке вашего коннектора и применяет команды жизненного цикла, которые ClickHouse Cloud отправляет для управляемых им сервисов в вашем кластере. Это команды создания, масштабирования, остановки и запуска, перезапуска, резервного копирования и удаления резервных копий, удаления, а также одобренные вами обновления платформы. Любое действие — это вызов Kubernetes API. Он не открывает соединений с ClickHouse и не хранит учетные данные для доступа к вашим бакетам или IAM. Он работает только в управляемом режиме.
* **Скрапер** с фиксированным интервалом читает список разрешённых системных таблиц ClickHouse и буферизует результаты локально. Затем он отправляет их на конечную точку вашего коннектора вместе с метаданными инфраструктуры и сведениями о работоспособности.
* **Средство диагностики** поддерживает исходящий командный канал к конечной точке вашего коннектора и выполняет диагностику в режиме только для чтения во время активного [сеанса поддержки](/ru/products/bring-your-own-cloud/connector/support-sessions). Вне сеанса оно не выполняет ничего.

В Kubernetes Helm-чарт `clicklink-connector` развертывает демонов в выбранном вами пространстве имен (по умолчанию `clicklink`). Исполнитель — это Развертывание с одной репликой, которое хранит состояние своих команд на постоянном томе. На Linux ВМ демоны работают как юниты systemd `clicklink-scraper`, `clicklink-troubleshooter` и `clicklink-executor` от имени непривилегированного системного пользователя `clicklink`.

Каждый запрос к API содержит заголовок `Authorization` с подписью HMAC-SHA256, вычисленной по методу, пути, метке времени и хешу тела запроса. Запросы невозможно повторно воспроизвести или изменить при передаче — даже внутри канала TLS.

Что касается входящих соединений, каждый демон открывает один локальный порт проверки работоспособности: 8082 — скрапер, 8084 — средство диагностики, 8086 — исполнитель. На этом порту доступны `/livez`, `/readyz`, `/healthz` и метрики Prometheus демона по адресу `/metrics`; отдельного порта для метрик нет. Локальный командный API исполнителя привязан только к loopback-интерфейсу, и ни один Service его не публикует. Единственный другой слушающий компонент — шлюз сеанса, который включается по желанию; см. [сеансы поддержки](/ru/products/bring-your-own-cloud/connector/support-sessions). ClickHouse Cloud никогда не подключается ни к одному из них.

## Жизненный цикл сертификата {#certificate-lifecycle}

Коннектор аутентифицируется на вашей конечной точке с помощью клиентского сертификата, который он получает и обслуживает самостоятельно. Все три демона предъявляют один и тот же сертификат.

* **Регистрация.** `clicklink clctl init` локально генерирует приватный ключ и запрос на подпись сертификата (CSR). В CSR в качестве common name указывается ваш organization ID, а в качестве единственного DNS SAN — хост вашей конечной точки. Приватный ключ никогда не покидает вашу среду.
* **Первичная выдача.** `init` отправляет CSR на конечную точку подписи для регистрации `/v1/pcm/cert/sign` с аутентификацией по HMAC. Если для вашей организации уже есть действующий сертификат, конечная точка возвращает отказ с кодом 409. В этом случае CLI подскажет, как продолжить с существующим сертификатом либо заменить его, указав `--force`.
* **Автоматическое обновление.** Все три демона проверяют срок действия сертификата каждые 12 часов. Когда до истечения остаётся 10 дней, они запрашивают новый сертификат на 30 дней через `/v1/pcm/cert/renew` (mTLS плюс HMAC). В Kubernetes обновлённый сертификат записывается обратно в Secret `clicklink-mtls` через grant RBAC с точным указанием имени; на ВМ каждый демон записывает его в `/etc/clicklink/tls`. Обновление не требует вмешательства оператора.

Коннектор проверяет серверный сертификат вашей конечной точки по системному trust store. Если задан параметр `api.tls.ca_file` (ВМ) или `api.tls.caFile` (Helm), к этим корневым сертификатам добавляется CA chain из вашего пакета регистрации.

### Какие данные покидают ваше окружение {#what-leaves}

* **Метрики из системных таблиц, входящих в список разрешённых.** По умолчанию скрапер собирает данные из `metric_log`, `asynchronous_metric_log`, `tables`, `warnings` и `server_settings`. Список разрешённых явно задаётся в конфигурации; за его пределами скрапер ничего не читает.
* **Метаданные инфраструктуры.** Сведения о сервисах, инфраструктуре и резервных копиях, синхронизируемые через API. Для управляемого сервиса это его состояние, текущее и ожидаемое количество реплик, а также используемая версия сервера и версия конфигурации.
* **Состояние и собственные метрики.** Статус компонентов и собственные операционные метрики коннектора. Сигнал жизнеспособности исполнителя также сообщает, подключён ли его канал команд. Кроме того, он передаёт результат последнего обновления платформы, версии компонентов платформы и дайджест последнего применённого bundle. При установке на VM дополнительно сообщается, находится ли пакет доступа к Kubernetes в состоянии `ok`, `expiring` или `expired` либо отсутствует.
* **Результаты команд.** Для каждой команды управления жизненным циклом, которую выполняет исполнитель, передаётся ход выполнения до достижения целевого состояния, а затем — успех или сбой (при сбое — с текстом ошибки).
* **Отправляемые вами определения сервисов.** Команда `clicklink clctl instances create` отправляет ID вашего окружения, облако и регион, имя сервиса, имена его бакетов и ARN роли IAM, а также ключ идемпотентности. Кроме того, отправляются два хеша пароля пользователя default (SHA-256 и двойной SHA-1).
* **Вывод сеанса поддержки.** Результаты диагностики в режиме только для чтения, выполненной во время включённого вами сеанса, после сокрытия конфиденциальных данных.

### Что по умолчанию никогда не покидает ваш контур {#what-never-leaves}

* **Исходный текст запросов на пути scrape.** `system.query_log` исключена из набора таблиц, опрашиваемых по умолчанию, поскольку её столбцы с запросами могут содержать литеральные значения, а вместе с ними — PII или секреты. Её повторное добавление — это override на уровне конкретного развёртывания. Список разрешённых таблиц для сеансов по умолчанию всё же включает `system.processes`, где отображается текст выполняющихся запросов; о том, как его урезать, см. [сеансы поддержки](/ru/products/bring-your-own-cloud/connector/support-sessions).
* **Данные ваших таблиц и резервные копии.** Они остаются в бакетах вашего аккаунта. У исполнителя нет учётных данных для доступа к вашим бакетам, и читать их он не может.
* **Учётные данные.** `init` не записывает учётные данные в файлы конфигурации. ClickHouse хранит только bcrypt-хеши паролей пользователей коннектора, а секреты остаются в Kubernetes Secrets или в файлах на хосте, доступных для чтения только пользователю root. Пароль пользователя default для управляемого сервиса генерируется на вашей стороне и показывается один раз; передаются только его хеши. Ни на пути scrape, ни на пути синхронизации учётные данные не передаются.
* **Немаскированный вывод средства диагностики.** Всё, что возвращает средство диагностики, перед отправкой проходит через шаблоны маскирования (встроенные и ваши собственные). См. [сеансы поддержки](/ru/products/bring-your-own-cloud/connector/support-sessions).

## Границы доверия {#trust-boundaries}

* **Граница — это ваша среда.** ClickHouse Cloud получает только то, что отправляет коннектор: результаты сбора метрик, сигналы жизнеспособности и статус, результаты команд, а также данные, возвращаемые активным сеансом поддержки. ClickHouse Cloud никогда не инициирует входящее соединение.
* **Шлюз сеансов принадлежит вам.** Он доступен только внутри вашей среды (через `kubectl port-forward` в Kubernetes или локально на ВМ), если только вы явно не решите открыть его через Ingress. ClickHouse Cloud никогда к нему не подключается.
* **Доступ к ClickHouse — только для чтения.** Пользователи `pcm_scraper` и `pcm_troubleshooter` имеют привилегии `SELECT` на уровне отдельных таблиц, скрапер — привилегию `READ ON REMOTE` (необходимую для `clusterAllReplicas()`), а также одну привилегию `SYSTEM FLUSH LOGS`, выданную только скраперу. Привилегий `INSERT`, DDL или управления пользователями нет. У исполнителя нет пользователя ClickHouse. Точный перечень приведён в разделе [модель привилегий](/ru/products/bring-your-own-cloud/connector/reference/privilege-model).
* **Скрапер и средство диагностики не могут изменять ваш кластер.** Их права RBAC определяются ролями (Role) в пространствах имён коннектора и сервисов. Эти роли разрешают только операции чтения для ресурсов рабочих нагрузок и доступ по точному имени к собственным Secrets коннектора. Разрешений `exec`, `delete` или `patch` нет.
* **Исполнитель изменяет состояние кластера в пространствах имён сервисов от имени `pcm-executor`.** Он создаёт и удаляет пространства имён с префиксом сервиса (по умолчанию `ns-`) и удаляет поды, чтобы перезапустить их. Внутри этих пространств имён он записывает объекты ClickHouseCluster, Backup и ScalingOverride, а также Secrets, ServiceAccounts и Services, необходимые сервису. Кроме того, он записывает Role и RoleBinding, предоставляющие скраперу доступ на чтение. ValidatingAdmissionPolicy запрещает любую запись от этого ServiceAccount за пределами префикса. Исключения, все в его собственном пространстве имён: продление его собственного токена, ConfigMap `clicklink-instance-registry` и, в Kubernetes, обновлённый клиентский сертификат в Secret для mTLS. Если политику невозможно вычислить, запрос отклоняется (fail closed). Контроль допуска не применяется к операциям чтения, поэтому чтение ресурсов этих типов префиксом не ограничено.
* **Исполнитель изменяет пространства имён платформы только от имени `pcm-platform` и только во время одобренного вами обновления.** Команда `clicklink clctl platform approve` выпускает токен для этой учётной записи на 2 часа; он никогда не продлевается. С этим токеном исполнитель может записывать только Deployments, Services, ConfigMaps, Secrets, Jobs и PodDisruptionBudgets. Namespaces, CRD, ServiceAccounts, RBAC, конфигурации вебхуков и контроля допуска, PriorityClasses и StorageClass применяются с вашими учётными данными во время одобрения. См. раздел [обновления платформы](/ru/products/bring-your-own-cloud/connector/platform-updates).
* **У исполнителя нет учётных данных для ваших бакетов или IAM.** Команда `clicklink clctl executor prepare` создаёт бакеты данных и резервных копий сервиса, а также его роль IAM. Команда `clicklink clctl executor teardown` удаляет их. Обе выполняются с вашими учётными данными. Роль доверяет только подам этого сервиса, поэтому ни исполнитель, ни ClickHouse не могут её принять. Исполнитель обращается только к облачным API Amazon ECR и STS. Он выполняет вход в registry, когда при синхронизации или создании платформы загружается чарт. Во время обновления платформы он проверяет образы с помощью роли загрузки только для чтения.
* **Сетевая политика.** В Kubernetes чарт создаёт для каждого демона NetworkPolicy с запретом по умолчанию. Исходящий трафик разрешён только к DNS, к CIDR, указанным вами для конечной точки коннектора, и к CIDR API-сервера Kubernetes. Политики скрапера и средства диагностики также разрешают доступ к Services ClickHouse в пространствах имён, которыми управляет исполнитель (они выбираются по метке, которую он на них ставит), или в тех, что вы перечислили по имени. В политике исполнителя нет правила для ClickHouse. Если чарты бандла платформы хранятся в Amazon ECR, добавьте диапазоны ECR и STS (или вашего зеркала registry) в `allowEgressCIDRs`. Без них синхронизация не сможет загрузить чарты, если CNI применяет сетевые политики. Если CNI их не применяет, политика ни на что не влияет. См. раздел [конфигурация](/ru/products/bring-your-own-cloud/connector/configuration).
* **Усиление защиты хоста на ВМ.** Юниты запускаются от имени системного пользователя без возможности входа, с `ProtectSystem=strict`, `NoNewPrivileges`, путями конфигурации только для чтения и включённым режимом FIPS.

Точные привилегии и правила RBAC коннектора см. в справочнике [модель привилегий](/ru/products/bring-your-own-cloud/connector/reference/privilege-model). Если кластер развёртывает и эксплуатирует сам ClickHouse, модель доверия иная; см. страницы [архитектура BYOC](/ru/products/bring-your-own-cloud/overview/architecture) и [привилегии BYOC](/ru/products/bring-your-own-cloud/reference/privilege).
