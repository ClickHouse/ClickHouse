На этой странице приведена сводная информация об идентичностях, которые ClickHouse BYOC использует в вашей учётной записи облачного провайдера. Сведения о разрешениях, области действия и назначении каждой идентичности см. на странице, посвящённой вашему облаку:

* [Привилегии BYOC в AWS](/ru/products/bring-your-own-cloud/reference/privilege-aws)
* [Привилегии BYOC в GCP](/ru/products/bring-your-own-cloud/reference/privilege-gcp)

## Роли IAM в AWS {#aws-iam-roles}

### Роль IAM для начальной настройки {#bootstrap-iam-role}

Роль IAM для начальной настройки, `ClickHouseManagementRole`, имеет следующие разрешения:

* **Операции EC2 и VPC**: требуются для настройки VPC и кластеров EKS.
* **Операции S3 (например, `s3:CreateBucket`)**: нужны для создания бакетов для хранилища ClickHouse BYOC.
* **Операции IAM (например, `iam:CreatePolicy`)**: нужны, чтобы контроллеры могли создавать дополнительные роли (подробности см. в следующем разделе).
* **Операции EKS**: операции записи ограничены ресурсами, имена которых начинаются с префикса `clickhouse-cloud`.

### Дополнительные роли IAM, создаваемые контроллером {#additional-iam-roles-created-by-the-controller}

Помимо `ClickHouseManagementRole`, контроллер создаёт для каждой BYOC infrastructure несколько дополнительных ролей:

* **Управление плоскостью данных**: сервис управления ClickHouse принимает эту роль с вашим внешним ID для повседневного управления вашими сервисами ClickHouse.
* **Роли кластера EKS и узлов**: используются EKS, системными узлами и узлами Karpenter.
* **Контроллеры кластера**: Karpenter, Cluster Autoscaler, AWS Load Balancer Controller и драйвер EBS CSI.
* **Идентичность сервера ClickHouse**: чтение и запись данных таблиц и резервных копий в бакетах BYOC.
* **Хранилище мониторинга (Thanos)**: чтение и запись метрик в бакете мониторинга BYOC.
* **Роли телеметрии**: отправляют в ClickHouse данные о работоспособности инфраструктуры, данные об использовании для биллинга и метрики Kubernetes для автоматического масштабирования. Других разрешений у них нет.

Разрешения и область действия каждой политики и роли описаны в разделе [Привилегии BYOC в AWS](/ru/products/bring-your-own-cloud/reference/privilege-aws).

## Сервисные аккаунты GCP {#gcp-service-accounts}

### Сервисный аккаунт начальной настройки {#bootstrap-service-account}

Сервисному аккаунту начальной настройки, `clickhouse-management`, назначаются пользовательские роли уровня проекта со следующими разрешениями:

* **Общие**: Базовые разрешения на чтение и идентичность.
* **VPC**: Управление VPC, подсетями, маршрутизацией и подключениями Private Service Connect, которые используются для размещения вашей инфраструктуры BYOC.
* **Кластер**: Управление кластерами GKE и ресурсами внутри кластера.
* **Хранилище**: Используется для управления бакетами Cloud Storage, применяемыми для резервных копий ClickHouse, общего состояния и данных мониторинга.
* **Роль IAM**: Управление сервисными аккаунтами и пользовательскими ролями внутри проекта. Эта роль не дает возможности создавать ключи сервисных аккаунтов, привязывать политики организации или изменять какие-либо ресурсы в других проектах.

### Дополнительные сервисные аккаунты, создаваемые контроллером {#additional-service-accounts-created-by-the-controller}

Помимо сервисного аккаунта `clickhouse-management`, контроллер создает несколько дополнительных сервисных аккаунтов для каждой BYOC infrastructure. Каждый из них имеет минимальный набор разрешений для одной конкретной задачи:

* **Идентичность управления плоскостью данных**: сервис управления ClickHouse олицетворяет её для повседневного управления вашими сервисами ClickHouse, в том числе бакетами, доступом для подов сервера и Private Service Connect.
* **Идентичность узлов GKE**: привязывается ко всем узлам GKE. Записывает журналы и метрики, а также загружает образы контейнеров.
* **Идентичность сервера ClickHouse**: читает и записывает данные таблиц и резервные копии в бакетах каждого сервиса ClickHouse.
* **Идентичность мониторинга**: читает и записывает метрики в бакете мониторинга BYOC.
* **Идентичности телеметрии**: отправляют в ClickHouse данные об использовании для биллинга и метрики Kubernetes для автоматического масштабирования. Они не имеют никаких разрешений в вашем проекте.
* **Делегат TDE** (только если TDE включено): шифрует и расшифровывает ключи данных TDE с помощью вашего ключа KMS.

Сведения о разрешениях и области действия каждой роли и сервисного аккаунта см. в разделе [Привилегии BYOC в GCP](/ru/products/bring-your-own-cloud/reference/privilege-gcp).

State exporter, который публикует события состояния сервисов и резервных копий в ClickHouse Cloud, намеренно отсутствует в этом списке: в GCP его публикующей идентичностью является аккаунт, принадлежащий ClickHouse, в проекте ClickHouse, а не аккаунт, созданный в вашем проекте. В вашем проекте создается привязка идентичности рабочей нагрузки, которая позволяет внутрикластерному сервисному аккаунту `state-exporter` олицетворять его. Ключевой материал при этом не используется, а идентичность, публикующая данные в Pub/Sub, не имеет никаких разрешений в вашем проекте.

## Роли и удостоверения в Azure {#azure-roles-and-identities}

### Сервисный субъект онбординга {#onboarding-service-principal}

Онбординг с помощью [модуля Terraform для Azure](https://github.com/ClickHouse/terraform-byoc-onboarding/tree/main/modules/azure) создает в вашем тенанте мультитенантное приложение как Enterprise Application (сервисный субъект) в соответствии с рекомендациями Azure по межтенантной аутентификации. Сервисному субъекту назначается пользовательская роль с минимально необходимыми привилегиями, действующая в рамках целевой подписки и предоставляющая следующие разрешения:

* **Сеть**: управление VNet, подсетями, общедоступными IP-адресами, NAT-шлюзами, группами сетевой безопасности и зонами DNS, в которых размещена ваша инфраструктура BYOC.
* **Кластер**: управление кластерами AKS и пулами узлов.
* **Хранилище**: управление аккаунтами хранилища и контейнерами BLOB-объектов, используемыми для данных ClickHouse, резервных копий и данных мониторинга.
* **Идентификация**: управление назначаемыми пользователем управляемыми идентификаторами и их учетными данными федеративной идентификации в рамках подписки.
* **Авторизация**: управление определениями пользовательских ролей и назначениями ролей. Все разрешения ограничены целевой подпиской — роль не может управлять ресурсами в других подписках или тенантах.

### Дополнительные управляемые удостоверения, создаваемые контроллером {#additional-managed-identities-created-by-the-controller}

При подготовке сервисов BYOC Control Plane ClickHouse создаёт в вашей подписке управляемые идентификаторы, назначаемые пользователем. Каждое из них федеративно связано с определённым сервисным аккаунтом Kubernetes (Workload Identity) и имеет узкий набор разрешений для одной конкретной цели:

* **Удостоверение для каждого сервиса**
  * Используется каждым сервисом ClickHouse для доступа к собственному аккаунту хранилища, содержащему данные таблиц и резервные копии, через пользовательскую роль для хранилища BLOB-объектов, область действия которой ограничена этим аккаунтом хранилища.
  * При восстановлении сервиса из резервной копии он также получает доступ только для чтения к контейнеру резервных копий исходного сервиса.
* **Общее удостоверение инфраструктуры**
  * Используется контроллером управления плоскостью данных среды выполнения ClickHouse для операций второго дня, таких как управление сервисами Private Link.
* **Удостоверение мониторинга**
  * Федеративно связано с рабочей нагрузкой Thanos в вашем кластере через пользовательскую роль, область действия которой ограничена доступом к хранилищу мониторинга.
  * Выполняет запись и чтение долговременного хранения метрик в вашей собственной подписке.

Как и в случае с GCP, state exporter намеренно отсутствует в этом списке: его публикующее удостоверение — это назначаемый пользователем управляемый идентификатор, принадлежащий ClickHouse и находящийся в подписке ClickHouse. На вашей стороне создаются лишь учётные данные федеративной идентификации, позволяющие сервисному аккаунту `state-exporter` внутри кластера получать для него токены без обмена секретами. Удостоверение, публикующее данные в Service Bus, не имеет никаких разрешений в вашей подписке.

<Note>
  Это отличается от AWS, где публикующая роль создаётся в вашем собственном аккаунте и принимает роль на стороне ClickHouse для доступа к очереди. В GCP и Azure публикующее удостоверение полностью находится на стороне ClickHouse, а ваш кластер лишь федеративно связывается с ним, поэтому для этого потока нет дополнительных разрешений в вашем аккаунте, которые вам нужно было бы проверять. Сам исходящий трафик учтён в разделе [сетевые границы](/ru/products/bring-your-own-cloud/reference/network-security#outbound-connections).
</Note>
