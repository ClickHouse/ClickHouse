Аналитика запросов собирает телеметрию по каждому
оператору из вашего инстанса
[ClickHouse Managed Postgres](/ru/products/managed-postgres/overview) и ранжирует каждый шаблон регулярного выражения
запроса по степени влияния, чтобы вы могли перейти от &quot;p99 постепенно растет&quot; к &quot;этот шаблон регулярного выражения запроса
сбрасывает промежуточные данные на диск&quot;, не покидая облачную консоль.

Данные по каждому оператору поступают из [`pg_stat_ch`](https://github.com/clickhouse/pg_stat_ch),
расширения Postgres с открытым исходным кодом, которое передает счетчики по каждому оператору в
ClickHouse Cloud. Телеметрия нормализуется внутри Postgres до того, как покинет
базу данных: литералы удаляются и заменяются плейсхолдерами, поэтому
конкретные значения из ваших запросов никогда не попадают в поток телеметрии.

## Откройте Аналитику запросов {#open}

Откройте свой инстанс ClickHouse Managed Postgres в облачной консоли и нажмите
**Аналитика запросов** на левой боковой панели. Страница разделена на пять
областей в том порядке, в котором вы, скорее всего, будете их использовать:

* **обзор** — сводка, в которой проверка состояния базы данных помещается на одном экране.
* Таблица **Медленные шаблоны регулярного выражения**, где ранжируются все шаблоны регулярного выражения запросов, которые
  выполнялись в вашей базе данных, с сортировкой по любому интересующему вас признаку.
* Панель **Последние запросы**, в которой отдельные выполнения перечислены в обратном
  хронологическом порядке.
* Вкладка **Ожидания**, ранжирующая события ожидания по времени, которое на них
  пришлось у активных сеансов, с таблицей **Блокирующие запросы**, показывающей, какие сеансы
  заблокировали запросы, ожидающие снятия блокировок.
* **Выдвижная панель сведений**, в которой собраны все счётчики для одного шаблона регулярного выражения запроса.

Используйте селектор **Период времени** вверху, чтобы переключаться между последними 15
минутами, часом, днём, неделей или месяцем. Размер бакета агрегации
подбирается автоматически: 1-минутные бакеты для последних 15 минут или часа,
5-минутные — для последнего дня, а 1-часовые — для последней недели или месяца, чтобы
графики оставались отзывчивыми.

## Обзор {#overview}

Обзор представляет собой сетку 3×3 из девяти панелей. Первые две строки посвящены
активности запросов:

| Панель                       | Что она показывает                                                                                                                                 |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Queries / sec**            | Объём запросов, приведённый к частоте за выбранный интервал.                                                                                       |
| **Query latency**            | Среднее, p50, p95 и p99 на одном графике, чтобы было видно, когда хвост распределения начинает расходиться с медианой.                             |
| **Operations breakdown**     | Кольцевая диаграмма, показывающая соотношение `SELECT`, `INSERT`, `UPDATE` и других операций, из которых фактически состоит ваша рабочая нагрузка. |
| **Rows returned / affected** | Общее количество строк, обработанных рабочей нагрузкой за выбранный интервал.                                                                      |
| **Buffer hit ratio**         | Кольцевая диаграмма соотношения попаданий в общие блоки и чтений из них, а в легенде показано суммарное процессорное время.                  |
| **Errors**                   | Общее количество ошибок с разбивкой по времени.                                                                                                    |

Одного экрана достаточно, чтобы понять, здорова ли база данных. Для здорового экземпляра
характерна знакомая картина: коэффициент попаданий в буфер держится на уровне выше 90 %, объём запросов
меняется вместе с трафиком приложения, частота ошибок остаётся ровной или нулевой, а процентильные
задержки остаются близкими друг к другу.

В третьей строке показано, чего ожидали активные сеансы на основном

| Панель                           | Что отображает                                                                                                                                                                                                       |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Active sessions by wait type** | Среднее число активных сеансов с накоплением по типу ожидания. **CPU** означает, что сеанс активен и не ожидает никакого события. Наведите курсор на столбец, чтобы увидеть события ожидания, входящие в каждый тип. |

**Active sessions by wait type**, чтобы открыть вкладку [Ожидания](#waits).

По умолчанию таблица отсортирована по **Общему времени выполнения** по убыванию — при такой
сортировке шаблон вверху списка обычно и отвечает на вопрос «что обходится мне
дороже всего?». При этом сам по себе он не обязательно будет самым медленным шаблоном. Запрос,
который выполняется восемь миллионов раз в день по двенадцать миллисекунд, может
значить больше, чем тот, который выполнился один раз за три секунды.

Каждый вариант сортировки дает свой взгляд:

* **Общее время выполнения** — где база данных потратила больше всего фактического времени.
* **Время CPU** — шаблоны с высокой вычислительной нагрузкой.
* **Вызовы** — часто выполняющиеся шаблоны.
* **Ошибки** — повторяющиеся сбои.
* **Средняя / P50 / P95 / P99 / Максимальная задержка** — выбросы по процентилям.
* **Возвращено строк**, **Прочитано блоков**, **Попаданий блоков**, **Байты WAL** —
  шаблоны, через которые прошло больше всего данных через движок, кэш или
  журнал предзаписи.

Нажмите кнопку **Columns**, чтобы показать или скрыть дополнительные столбцы.
Таблица шаблонов содержит 19 столбцов, включая разбиение по
процентилям, коэффициент попаданий в кэш и время CPU для каждого шаблона.

Отфильтруйте таблицу по интересующему вас срезу рабочей нагрузки:

* **База данных**
* **Пользователь**
* **Операция** (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, …)
* **Приложение** — `application_name` из строки подключения

превращается в два выпадающих списка. Значения фильтров автоматически
заполняются на основе того, что фактически выполнялось в вашем
экземпляре.

Откройте вкладку **Ожидания** или нажмите на **Active sessions by wait type** среди
[чартов ожиданий](#wait-charts), чтобы увидеть тот же чарт и таблицу **Wait events
breakdown**, в которой события ожидания ранжированы по среднему числу активных сеансов за
выбранный период времени.

### Блокирующие запросы {#blocking-queries}

Под таблицей событий ожидания расположен раздел **Блокирующие запросы**: он показывает, какие запросы ожидали
снятия блокировок и какие сеансы их блокировали. Блокирующий сеанс либо
удерживает конфликтующую блокировку, либо стоит раньше в очереди на её получение.
Каждая строка связывает ожидающий запрос с его непосредственным блокировщиком и может
объединять выборки из нескольких сеансов. Чаще всего встречающиеся
пары отображаются первыми.

По умолчанию сбор данных отключён. Чтобы начать сбор, включите
переключатель **Enable** рядом с заголовком **Блокирующие запросы**. Включать и отключать сбор могут только пользователи с правами
управления сервисом, а реплики для чтения
наследуют настройку основного экземпляра. Сэмплирование обычно начинается примерно через минуту.

| Столбец                 | Что отображает                                                                                                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Waiting query**       | Нормализованный текст запроса, ожидавшего блокировку.                                                                                                                         |
| **Blocked by**          | Нормализованный текст текущего или последнего оператора блокировщика.                                                                                                         |
| **Blocker application** | Значение `application_name` блокирующих сеансов.                                                                                                                              |
| **Blocker state**       | Состояние блокировщика в последней выборке, например `active` или `idle in transaction`. **waiting** означает, что блокировщик сам ожидал блокировку хотя бы в одной выборке. |
| **Lock**                | Тип блокировки, например **Row** или **Table**, и режим блокировки, запрошенный ожидающим запросом, в последней выборке.                                                      |
| **Sessions**            | Количество различных ожидавших сеансов.                                                                                                                                       |
| **Longest wait**        | Максимальное время, которое ожидающий сеанс провёл в ожидании на момент выборки.                                                                                              |
| **Last seen**           | Время последней выборки, в которой была обнаружена эта пара.                                                                                                                  |

Откройте элемент выбора **Columns**, чтобы отобразить пользователей, приложения и PID
ожидающих сеансов, а также пользователей и PID блокирующих сеансов. Таблицу можно
отфильтровать по базе данных, пользователю или приложению ожидающих сеансов.

Блокировщик в состоянии `idle in transaction` зачастую нужно устранять в первую очередь: он
открыл транзакцию, захватил блокировки и не выполнил ни коммит, ни откат.
Текст в **Blocked by** для него — это последний выполненный оператор, который не обязательно
захватил блокировку.

**No query text** означает, что у Query Insights нет текста для этого оператора.
Так бывает, если последним оператором блокирующего сеанса была служебная
команда, например `LOCK TABLE`, если запрос ожидает блокировку таблицы
до того, как Postgres назначил ему идентификатор запроса, или если Query Insights
ещё не зафиксировал завершённое выполнение этого оператора. Кроме того, Query Insights
скрывает текст операторов из сеансов, которые сервис использует для внутренних целей,
например для мониторинга и репликации. При этом в строке по-прежнему отображаются
приложение, состояние и блокировка. **Prepared transaction** в **Blocked
by** означает, что блокировку удерживает подготовленная транзакция, поэтому
блокирующего сеанса, который можно было бы описать, нет.

## Выдвижная панель сведений {#detail}

Нажмите любую строку в таблице шаблонов или последних запросов, и справа
откроется выдвижная панель **Сведения о запросе**. На этой панели
собраны все выполнения данного шаблона за выбранный диапазон времени и
агрегированы счётчики, которые помогают понять, почему он работает медленно.

Панель представляет собой одну прокручиваемую область с пятью разделами:

* **Шаблон запроса** — нормализованный SQL, в котором литералы заменены на `$1`,
  `$2`, …, и кнопка копирования в буфер обмена.
* **Агрегированное использование ресурсов** — сетка из 13 карточек
  статистики, включающая общее число вызовов, среднюю/P95/P99/максимальную
  задержку, общее время выполнения, число возвращённых строк, коэффициент попаданий
  в кэш, число прочитанных блоков, число блоков с попаданием в кэш, процессорное время, байты WAL и ошибки.
* **Контекст запроса** — база данных, пользователь, операция и приложение,
  из которых пришёл этот шаблон.
* **Примечательные выполнения** — ошибки, необычно медленные запуски и
  выполнения с большим объёмом результатов, показанные перед полным списком последних.
* **Последние выполнения** — отдельные запуски одного и того же шаблона
  со счётчиками для каждого выполнения.

<div id="counters">
  ### Счетчики по каждому выполнению {#counters}
</div>

Разверните одно из недавних выполнений, и вы увидите счетчики, которые
точно показывают, куда ушло время:

* **Общие блоки** — прочитанные и найденные в кэше показываются всегда; записанные и измененные
  показываются, только если их значение не равно нулю.
* **Операции с локальными и временными блоками** — ненулевые операции с временными блоками означают, что sort или
  hash были выгружены на диск.
* **Время чтения / записи** — время ввода-вывода, отдельно от времени CPU.
* **Время CPU** — пользовательское и системное, по отдельности.
* **Параллельные воркеры** — запланированные и фактически запущенные.
* **JIT** — общее время JIT-компиляции и количество функций.
* **WAL** — количество байтов и записей.

Все, что нужно для диагностики медленного паттерна, собрано в одном
месте, на одном экране.

<div id="how-it-works">
  ## Как это работает {#how-it-works}
</div>

<div id="how-normalized">
  ### Нормализация в Postgres до передачи по сети {#how-normalized}
</div>

`pg_stat_ch` перехватывает фазу parse-analyze, заменяет каждый литерал на
плейсхолдер (`$1`, `$2`, …) и кэширует получившийся шаблон в
отдельном LRU-кэше для каждого backend-соединения с ключом по `queryid`. Когда выполнение
оператора завершается, именно этот кэшированный шаблон прикрепляется к событию. Точный
оператор со значениями никогда не покидает базу данных.

<div id="how-overhead">
  ### Не мешает работе базы данных {#how-overhead}
</div>

Продьюсер добавляет примерно 3% накладных расходов на каждый оператор. Путь добавления в очередь
использует неблокирующий try-lock для кольцевого буфера в общей памяти. При
перегрузке расширение отбрасывает события, увеличивая Counter, вместо того
чтобы создавать обратное давление на Postgres.

### Ожидания собираются выборочно {#how-waits}

[Чарты ожиданий](#wait-charts) и таблица [Ожидания](#waits) строятся по снимкам,
которые собираются каждые 30 секунд на основном сервере. Короткие ожидания могут
целиком уложиться в интервал между снимками и не попасть в них, поэтому эти
отображения лучше всего подходят для выявления продолжительных ожиданий и конкуренции за блокировку.

[Блокирующие запросы](#blocking-queries) тоже собираются выборочно каждые 30 секунд
на каждом инстансе, где включён сбор, поэтому блокировка, удерживаемая лишь несколько
секунд, может в них не попасть. Каждый снимок содержит идентификаторы запросов, а не
их текст. Текст в таблице берётся из нормализованных шаблонов регулярного выражения, которые Query
Insights уже собирает, поэтому значения литералов в нём никогда не отображаются.

<div id="how-raw-events">
  ### Сырые события, а не агрегаты {#how-raw-events}
</div>

`pg_stat_ch` генерирует по одному сырому событию для каждого выполненного оператора (как верхнего уровня, так и
вложенного) с учетом сэмплирования. Перцентили запросов, ранжирование и
разбивки вычисляются в ClickHouse на основе этого потока событий.

<div id="how-engine">
  ### Тот же движок, которым пользуются наши клиенты {#how-engine}
</div>

Бэкенд Insights — это [ClickHouse Cloud](/ru/products/cloud/getting-started/intro).
Телеметрия по каждому запросу от загруженного экземпляра Postgres — это миллионы строк
в день; столбцовое сжатие позволяет недорого хранить детальные данные по каждому выполнению
месяцами, а агрегации по миллиардам строк, выполняющиеся за доли секунды, сохраняют
интерфейс отзывчивым, пока вы анализируете данные за неделю или месяц.

<div id="how-open-source">
  ### С открытым исходным кодом {#how-open-source}
</div>

`pg_stat_ch` распространяется по лицензии Apache 2.0. Запускайте его с любым Postgres и отправляйте данные в любой
ClickHouse. Исходный код и баг-репорты — на
[github.com/clickhouse/pg&#95;stat&#95;ch](https://github.com/clickhouse/pg_stat_ch).
