Операционные данные в SQL Server часто служат источником достоверных данных о заказах, платежах и складских запасах, однако эта СУБД не рассчитана на тяжёлые аналитические запросы. В этом пошаговом руководстве вы реплицируете таблицу SQL Server в ClickHouse с помощью автоматизированного конвейера: Striim загружает существующие строки, а затем в потоковом режиме передаёт каждую вставку, обновление и удаление сразу по мере их выполнения. Затем вы выполните запросы к полученным данным в ClickHouse.

Полное пошаговое руководство см. в статье [Introducing Automated Pipelines for Effortless Data Replication](https://www.striim.com/blog/automated-pipelines-5-0/).

Для CDC (фиксации изменений данных) из SQL Server требуется тарифный план Striim for ClickHouse **Premium**.

## Что вы построите {#what-you-will-build}

SQL Server (`sales.orders`) &gt; первоначальная загрузка через Striim, затем CDC (фиксация изменений данных) &gt; ClickHouse (`sales.orders`, `ReplacingMergeTree`)

## Перед началом работы {#before-you-begin}

* Работающий сервис Striim for ClickHouse на тарифе Premium (см. раздел [Начало работы](/ru/integrations/connectors/data-ingestion/etl-tools/striim/get-started)).
* Инстанс SQL Server, доступный из Striim, с запущенным SQL Server Agent, а также разрешение на включение отслеживания изменений данных. Описанные ниже шаги подходят как для SQL Server на ВМ, так и для Amazon RDS for SQL Server.
* Сервис ClickHouse, база данных с именем `sales`, пользователь Striim с необходимыми привилегиями и профиль подключения к ClickHouse.

## Шаг 1. Подготовка SQL Server {#step-1-prepare-sql-server}

Создайте базу данных и тестовую таблицу с несколькими строками. Эти начальные данные приведены для наглядности, чтобы вы могли воспроизвести пример.

```sql
CREATE DATABASE salesdb;
GO
USE salesdb;
GO
CREATE SCHEMA sales;
GO
CREATE TABLE sales.orders (
  order_id    INT           NOT NULL PRIMARY KEY,
  customer_id INT           NOT NULL,
  status      VARCHAR(20)   NOT NULL,
  total       DECIMAL(10,2) NOT NULL,
  placed_at   DATETIME2     NOT NULL
);
INSERT INTO sales.orders VALUES
  (1, 101, 'NEW',     120.50, SYSDATETIME()),
  (2, 102, 'NEW',      75.00, SYSDATETIME()),
  (3, 103, 'NEW',     310.25, SYSDATETIME());
GO
```

Включите отслеживание изменений данных в базе данных и создайте пользователя для Striim. При запуске приложения Striim включает CDC (фиксация изменений данных) для каждой выбранной таблицы.

<Tabs>
  <Tab title="SQL Server на ВМ" id="enable-cdc-vm">
    ```sql
    USE salesdb;
    EXEC sys.sp_cdc_enable_db;
    ```
  </Tab>

  <Tab title="Amazon RDS for SQL Server" id="enable-cdc-rds">
    ```sql
    EXEC msdb.dbo.rds_cdc_enable_db 'salesdb';
    ```
  </Tab>
</Tabs>

Создайте пользователя Striim в `salesdb`:

```sql
USE salesdb;
CREATE LOGIN striim WITH PASSWORD = '<strong password>';
CREATE USER striim FOR LOGIN striim;
EXEC sp_addrolemember @rolename = db_owner, @membername = striim;
```

Для пользователя Striim должен быть включен режим аутентификации SQL Server. Согласно документации Striim, пользователю, от имени которого работает считыватель, требуется роль `db_owner`. После запуска конвейера можно убедиться, что CDC (фиксация изменений данных) активна, выполнив `EXEC sys.sp_cdc_help_change_data_capture`. Предварительные требования для ВМ Azure и групп доступности Always On см. в разделе [Configuring SQL Server to use MS SQL Reader](https://www.striim.com/docs/striimforclickhouse/en/configuring-sql-server-to-use-ms-sql-reader.html).

## Шаг 2: Создайте автоматизированный конвейер {#step-2-create-the-automated-pipeline}

1. В Striim выберите **Apps &gt; Create an App**.
2. Найдите и выберите **SQL Server** в качестве источника. В качестве целевой системы выберите **ClickHouse**.
3. Нажмите **Get Started** и выберите автоматизированный конвейер (первоначальная загрузка и CDC (фиксация изменений данных)).
4. Задайте имя конвейера, например `SqlServerToClickHouse`, выберите пространство имён и нажмите **Next**.
5. Введите сведения о подключении к SQL Server: хост и порт (`<host>:1433`), имя базы данных `salesdb` и пользователя `striim`. Нажмите **Next**. Striim проверит соединение. Если проверка завершится с ошибкой, нажмите **Back** и исправьте настройки: продолжить можно только после успешной проверки.
6. Выберите схемы для репликации — `sales`. Системные схемы не выбирайте.
7. Выберите таблицы для репликации из каждой схемы — `orders`.
8. Выберите профиль подключения ClickHouse и установите для **Table Engine** значение **`ReplacingMergeTree`**. Этот движок подходит для источников CDC (фиксация изменений данных), которые при обновлении передают полный образ строки.
9. При необходимости отредактируйте сопоставление таблиц. Убедитесь, что `sales.orders` сопоставлена с `sales.orders` в ClickHouse.
10. Проверьте настройки и нажмите **Save &amp; Start**.

![Проверка конфигурации автоматизированного конвейера из SQL Server в ClickHouse](/images/integrations/striim/automated-pipeline-wizard.png)

*Пример экрана проверки в мастере. В этом руководстве используйте `salesdb`, `sales.orders` и `ReplacingMergeTree`, как описано выше.*

Striim создаёт два связанных приложения. Сначала выполняется первоначальная загрузка; после копирования всех строк она приостанавливается, затем автоматически запускается приложение CDC (фиксация изменений данных), которое отображает счётчики событий по мере поступления изменений. Если на любом из этапов возникает проблема, конвейер останавливается и предлагает рекомендуемые способы её устранения.

![Мониторинг работающего приложения отслеживания изменений данных](/images/integrations/striim/pipeline-monitoring.png)

<Warning>
  Не выполняйте DDL-операции над исходными таблицами во время первоначальной загрузки и убедитесь, что SQL Server хранит данные об изменениях (по умолчанию — три дня) с момента начала первоначальной загрузки до тех пор, пока приложение CDC (фиксация изменений данных) не наверстает отставание.
</Warning>

## Шаг 3: Проверьте первоначальную загрузку в ClickHouse {#step-3-verify-the-initial-load-in-clickhouse}

Striim создал целевую таблицу на движке `ReplacingMergeTree` с двумя служебными столбцами метаданных. Просмотрите её:

```sql
SHOW CREATE TABLE sales.orders;
```

Согласно сопоставлению типов данных Striim, столбцы `order_id` и `customer_id` должны иметь тип `Int32`, `status` — `String`, `total` — `Decimal(10, 2)`, `placed_at` — `DateTime64`. Кроме того, в таблице должны быть столбцы `__STRIIM_VERSION` (`UInt64`) и `__STRIIM_ISDELETED` (`UInt8`), а также `ENGINE = ReplacingMergeTree(__STRIIM_VERSION, __STRIIM_ISDELETED)` и `ORDER BY order_id`.

```sql
SELECT order_id, customer_id, status, total
FROM sales.orders FINAL
WHERE __STRIIM_ISDELETED = 0
ORDER BY order_id;
```

Должны отобразиться три строки, загруженные из SQL Server.

## Шаг 4: Потоковая передача изменений {#step-4-stream-changes}

Внесите изменения в SQL Server:

```sql
USE salesdb;
UPDATE sales.orders SET status = 'SHIPPED' WHERE order_id = 2;
DELETE FROM sales.orders WHERE order_id = 3;
INSERT INTO sales.orders VALUES (4, 104, 'NEW', 42.00, SYSDATETIME());
```

Снова выполните тот же запрос в ClickHouse. Заказы 1, 2 и 4 должны присутствовать, заказ 2 должен иметь статус `SHIPPED`, а заказ 3 должен отсутствовать. Удаление сохраняется как строка мягкого удаления (soft delete). Запрос использует `FINAL` для выборки последней версии и условие `__STRIIM_ISDELETED = 0` для исключения удалённых строк. По умолчанию маркеры удаления сохраняются: одни лишь фоновые слияния не гарантируют их физического удаления. Подробнее об очистке см. [`ReplacingMergeTree`](/ru/reference/engines/table-engines/mergetree-family/replacingmergetree#is_deleted). Кроме того, количество событий и актуальность данных в целевой системе можно отслеживать в представлении мониторинга Striim, а текущую задержку — запросить у Clara.

## Создание того же конвейера с помощью Striim Clara {#build-the-same-pipeline-with-striim-clara}

Вместо мастера можно описать конвейер на главной странице, например: «Build a pipeline from SQL Server to ClickHouse with первоначальная загрузка and отслеживание изменений данных for the sales.orders table.» Clara запросит сведения о подключении, сгенерирует план TQL и выполнит развертывание только после того, как вы нажмете **Accept TQL**.

## Очистка {#clean-up}

* Остановите и отмените развертывание обоих приложений Striim на странице Apps.
* SQL Server продолжает фиксировать изменения данных даже после отмены развертывания приложений Striim, если используются настройки считывателя по умолчанию. Чтобы прекратить сбор изменений для этого примера, выполните `sys.sp_cdc_disable_table` для `sales.orders` или `sys.sp_cdc_disable_db`, если CDC (фиксация изменений данных) не требуется другим таблицам в базе данных. Подробнее см. в [документации](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sys-sp-cdc-disable-table-transact-sql) SQL Server. Также можно воспользоваться [процедурой Auto Disable Table CDC](https://www.striim.com/docs/striimforclickhouse/en/sql-server-operational-considerations.html) от Striim.
* Удалите тестовые таблицы: выполните `DROP TABLE sales.orders;` в обеих системах.
