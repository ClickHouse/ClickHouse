ClickHouse Connect включает диалект SQLAlchemy (`clickhousedb`), созданный на базе основного драйвера. Синхронный диалект поддерживает SQLAlchemy 1.4.40 и более поздние версии, включая SQLAlchemy 2.x, с акцентом на запросы Core, DDL ClickHouse, рефлексию и простые ORM-вставки. Для асинхронного диалекта требуется SQLAlchemy версии 2.0.44 или более поздней.

Установите зависимости SQLAlchemy с помощью дополнительного пакета:

```bash
pip install "clickhouse-connect[sqlalchemy]"
```

## Подключение через SQLAlchemy {#sqlalchemy-connect}

Создайте движок, указав URL в формате `clickhousedb://` или `clickhousedb+connect://`:

```python
from sqlalchemy import create_engine, text

engine = create_engine(
    "clickhousedb://user:password@host:8123/mydb?compression=zstd"
)

with engine.connect() as conn:
    version = conn.execute(text("SELECT version()")).scalar_one()
    print(version)
```

Используйте эти явные формы URL, если также установлен `clickhouse-sqlalchemy`.
Импорт `clickhouse_connect.cc_sqlalchemy` не затрагивает регистрацию `clickhouse://`
из этого пакета. Если другой установленный провайдер мешает зарегистрировать наш псевдоним,
при импорте выдаётся `UserWarning` с рекомендацией использовать явный
URL ClickHouse Connect. Уже существующие регистрации во время выполнения остаются без изменений,
и предупреждение не выдаётся. Если `clickhouse://` не занят никаким другим провайдером, этот импорт делает его
доступным в качестве псевдонима ClickHouse Connect для обеспечения совместимости.

### Идентификаторы сеансов ClickHouse {#sqlalchemy-session-ids}

По умолчанию каждое соединение из пула — как в синхронном, так и в асинхронном диалекте — генерирует собственный идентификатор сеанса ClickHouse. Если запросы через это соединение попадают в один и тот же процесс сервера ClickHouse, настройки, изменённые с помощью `SET`, и временные таблицы сохраняются для этого соединения. Состояние именованного сеанса и проверка на пересечение запросов в одном сеансе локальны для процесса. В пределах одного процесса сервера пересекающийся по времени запрос от того же пользователя с тем же идентификатором сеанса не ставится в очередь, а сразу отклоняется с кодом ошибки сервера 373. Если вы задаёте фиксированный `session_id`, используйте `pool_size=1, max_overflow=0` или сериализуйте доступ до того, как запросы попадут в ClickHouse. В ClickHouse Cloud и других развертываниях с балансировкой нагрузки запросы с одним и тем же идентификатором сеанса могут попадать на разные серверы, поэтому не используйте фиксированный `session_id` в качестве распределённого состояния или распределённого мьютекса.

### Асинхронные соединения {#sqlalchemy-async-connections}

Для асинхронного диалекта требуется SQLAlchemy версии 2.0.44 или новее; он использует нативный `AsyncClient` из ClickHouse Connect. Установите необходимые зависимости и создайте асинхронный движок с URL `clickhousedb+async://`:

```bash
pip install "clickhouse-connect[sqlalchemy-async]"
```

```python
import asyncio

from sqlalchemy import text
from sqlalchemy.ext.asyncio import create_async_engine


async def main():
    engine = create_async_engine(
        "clickhousedb+async://user:password@host:8123/mydb"
    )
    try:
        async with engine.connect() as conn:
            version = (await conn.execute(text("SELECT version()"))).scalar_one()
            print(version)
    finally:
        await engine.dispose()


asyncio.run(main())
```

Результаты буферизуются. Серверные курсоры отключены, поэтому `AsyncConnection.stream()` вызывает `InvalidRequestError`. SQLAlchemy допускает вызов `AsyncSession.stream()`, однако диалект буферизует весь результат, прежде чем вернуть его. Для больших объёмов результатов используйте нативные потоковые методы `AsyncClient`. Исходный нативный клиент доступен через `driver_connection`, пока соответствующее соединение SQLAlchemy взято из пула:

```python
async def stream_events(engine):
    async with engine.connect() as conn:
        raw_connection = await conn.get_raw_connection()
        client = raw_connection.driver_connection
        async with await client.query_rows_stream("SELECT * FROM events") as rows:
            async for row in rows:
                print(row)
```

Не используйте соединение SQLAlchemy параллельно с его низкоуровневым клиентом. Завершайте потоки низкоуровневого клиента до выхода из блока соединения SQLAlchemy и не сохраняйте ссылку на низкоуровневый клиент после возврата соединения в пул. Жизненным циклом заимствованного клиента управляет SQLAlchemy, поэтому никогда не вызывайте `client.close()` или какие-либо его приватные методы жизненного цикла. Параллелизмом соединений управляет пул SQLAlchemy. Каждому соединению в пуле принадлежит один нативный асинхронный клиент, и по умолчанию коннектор aiohttp ограничен одним соединением в целом и одним соединением на хост. Чтобы переопределить эти транспортные настройки, задайте `connector_limit`, `connector_limit_per_host` или `keepalive_timeout` в URL или в `connect_args`. При `pool_pre_ping=True` SQLAlchemy проверяет повторно используемые соединения запросом `SELECT 1` при извлечении соединения из пула.

Асинхронные вставки SQLAlchemy через executemany в настоящее время отправляют отдельный HTTP-запрос для каждого набора параметров вместо использования нативного протокола массовой вставки драйвера. Используйте этот способ только для небольших пакетов. Для больших объёмов данных применяйте описанный выше шаблон доступа через `driver_connection`, принадлежащий пулу, и дожидайтесь завершения `client.insert()` до возврата соединения SQLAlchemy в пул. Поскольку асинхронный executemany использует привязку параметров запроса, наивные значения `datetime` обрабатываются согласно настройке `naive_datetime_binding`, а не `naive_datetime_insert`, которая применяется в синхронном нативном executemany. Типизированные привязки SQLAlchemy `DateTime64` сохраняют доли секунды как для клиентских, так и для серверных параметров. Нетипизированные параметры `%s` или `%(name)s`, передаваемые в `exec_driver_sql()`, по умолчанию форматируют наивные значения `datetime` с точностью до целых секунд. Для однозначной обработки часовых поясов используйте значения с явно указанным часовым поясом. Для нативной семантики массовой вставки используйте `client.insert()`.

Создавайте и освобождайте асинхронный движок в том цикле событий, в котором он используется. Верните все извлечённые соединения, а затем дождитесь выполнения `engine.dispose()` при завершении работы и перед использованием движка из другого цикла событий. Если цикл, которому принадлежит движок, уже закрыт, перед повторным использованием дождитесь выполнения `engine.dispose()` в текущем цикле. aiohttp может сообщать о незакрытом транспорте, если очистка начинается уже после закрытия цикла-владельца, поэтому по возможности освобождайте движок до его передачи. `pool_pre_ping=True` не заменяет освобождение при переносе асинхронного движка с пулом между циклами событий. Чтобы использовать один движок в нескольких циклах событий, не удерживая привязанные к циклу соединения, задайте `poolclass=NullPool`. Если освобождение выполняется, пока соединение ещё не возвращено в пул, диалект закроет это соединение при его возврате или сборке мусора. Не вызывайте `engine.sync_engine.dispose()` из синхронного кода: там SQLAlchemy не может дождаться асинхронной очистки соединений и может лишь записать ошибку в журнал, не закрыв транспорты пула.

Параметры запроса в URL могут содержать настройки ClickHouse, параметры клиента ClickHouse Connect, такие как `compression`, `query_limit` и тайм-ауты, или параметры HTTP/TLS, такие как `ca_cert`. При необходимости добавьте к настройке ClickHouse префикс `ch_`, чтобы она принудительно обрабатывалась как настройка сервера, например `ch_http_max_field_name_size=99999`.

Доступные параметры клиента см. в разделе [Аргументы соединения и настройки](/ru/integrations/language-clients/python/driver-api#connection-arguments).

Синхронные вспомогательные операции SQLAlchemy, например DDL и инспекцию схемы, выполняйте через `AsyncConnection.run_sync()`:

```python
from sqlalchemy import inspect


async def prepare_schema(engine, metadata):
    async with engine.begin() as conn:
        await conn.run_sync(metadata.create_all)
        return await conn.run_sync(
            lambda sync_conn: inspect(sync_conn).get_table_names()
        )
```

### Настройки для отдельных запросов {#sqlalchemy-per-query-settings}

Передавайте настройки ClickHouse через параметры выполнения SQLAlchemy. Настройки можно задавать на уровне движка, соединения или оператора. Если один и тот же ключ задан в нескольких местах, значение на уровне оператора имеет приоритет над значением на уровне соединения или движка.

```python
from sqlalchemy import text

stmt = text("SELECT getSetting('max_threads')").execution_options(
    settings={"max_threads": 2}
)

with engine.connect() as conn:
    value = conn.execute(stmt).scalar_one()
```

### Форматы чтения для отдельных запросов {#sqlalchemy-per-query-read-formats}

Задавайте форматы чтения ClickHouse для движка, соединения или оператора с помощью параметра выполнения SQLAlchemy `query_formats`. Форматы оператора применяются первыми и переопределяют соответствующие ключи и подстановочные шаблоны соединения или движка.

```python
from sqlalchemy import text

stmt = text("SELECT user_uuid FROM users").execution_options(
    query_formats={"UUID": "string"}
)

with engine.connect() as conn:
    rows = conn.execute(stmt).all()
```

### Обработка ошибок {#sqlalchemy-error-handling}

Ошибки, которые драйвер выбрасывает через соединение SQLAlchemy, представлены классами DB-API, экспортируемыми из `clickhouse_connect.dbapi`. Это те же самые объекты классов, что и соответствующие классы в `clickhouse_connect.driver.exceptions`, поэтому SQLAlchemy оборачивает их в соответствующий подкласс `sqlalchemy.exc.DBAPIError`. `StreamFailureError` является подклассом `OperationalError` и оборачивается в `sqlalchemy.exc.OperationalError`.

Если таблицы не существует, инспекция столбцов и рефлексия таблицы вызывают исключение `sqlalchemy.exc.NoSuchTableError`. Это исключение также наследуется от `sqlalchemy.exc.NoResultFound`, поэтому существующие обработчики по-прежнему его перехватывают. Текст сообщения: `Table <database>.<table_name> does not exist`.

Выполнение SQL-запросов подчиняется [политике повторных попыток HTTP](/ru/integrations/language-clients/python/driver-api#http-retries) драйвера. Для нативных массовых вставок действует [политика повторных попыток вставки](/ru/integrations/language-clients/python/advanced-inserting#insert-retries-and-deduplication).

Если отмена на стороне вызывающего кода может прервать явный вызов `AsyncConnection.invalidate()`, выполняйте инвалидацию в отдельной собственной задаче и дожидайтесь её завершения, прежде чем передавать отмену дальше. Так SQLAlchemy сможет завершить служебный учёт записей соединений:

```python
import asyncio


async def invalidate_safely(connection):
    invalidate_task = asyncio.create_task(connection.invalidate())
    cancellation = None
    while not invalidate_task.done():
        try:
            await asyncio.wait({invalidate_task})
        except asyncio.CancelledError as ex:
            cancellation = ex
    if cancellation is not None:
        try:
            invalidate_task.result()
        finally:
            raise cancellation
    invalidate_task.result()
```

Не используйте соединение, пока задача его инвалидации ещё выполняется. Если прямой вызов `await connection.invalidate()` был отменён, а `connection.invalidated` по-прежнему равно false, снова выполните `await connection.invalidate()`, чтобы завершить очистку, и только после этого используйте или закрывайте соединение.

### Серверные параметры {#sqlalchemy-server-side-parameters}

SQLAlchemy обычно подставляет параметры на стороне клиента. Чтобы использовать серверные параметры ClickHouse, включите их при создании движка:

```python
engine = create_engine(
    "clickhousedb://user:password@host:8123/mydb",
    server_side_params=True,
)
```

Для асинхронного диалекта передайте тот же аргумент `server_side_params=True` в `create_async_engine()`.

В этом режиме каждому связанному значению должен соответствовать SQLAlchemy-тип, совместимый с ClickHouse. Поддерживаемые списки `IN` преобразуются в типизированные параметры ClickHouse `Array`. Компилятор выдаёт `CompileError`, если не может определить совместимый тип или безопасно обработать привязку.

Имена привязок должны быть ASCII-именами ClickHouse типа BareWord. Имена, которые начинаются и заканчиваются на `$`, отклоняются, поскольку основной драйвер резервирует их для параметров запроса в виде необработанных двоичных данных.

## Основные запросы {#sqlalchemy-core-queries}

Диалект поддерживает запросы `SELECT` в SQLAlchemy Core с JOIN, фильтрами, сортировкой, ограничением и смещением, а также `DISTINCT` и составные SELECT.

SQLAlchemy `union()`, `intersect()` и `except_()` компилируются в ClickHouse `UNION DISTINCT`, `INTERSECT DISTINCT` и `EXCEPT DISTINCT`. Их аналоги `union_all()`, `intersect_all()` и `except_all()` компилируются в соответствующие операторы `ALL`. Это явное сопоставление сохраняет семантику дубликатов SQLAlchemy независимо от настроек по умолчанию для операций над множествами в ClickHouse.

```python
from sqlalchemy import MetaData, Table, select

metadata = MetaData(schema="mydb")
users = Table("users", metadata, autoload_with=engine)
orders = Table("orders", metadata, autoload_with=engine)
events = Table("events", metadata, autoload_with=engine)

stmt = (
    select(users.c.name, orders.c.product)
    .select_from(users.join(orders, users.c.id == orders.c.user_id))
    .order_by(users.c.name)
    .limit(10)
)

with engine.connect() as conn:
    rows = conn.execute(stmt).all()
```

Поддерживается легковесный `DELETE`, требующий явного условия `WHERE`:

```python
from sqlalchemy import delete

stmt = delete(users).where(users.c.name.like("%temporary%"))
with engine.connect() as conn:
    conn.execute(stmt)
```

### Подстановка литералов {#sqlalchemy-literal-rendering}

Когда SQLAlchemy подставляет связанное значение в запрос через `literal_binds` или `literal_execute`, диалект использует правила экранирования ClickHouse для общих строковых типов и типов ClickHouse. Это также относится к обёрткам `TypeDecorator` и вариантам, выбранным с помощью `with_variant()`. Строковые значения сохраняют знаки процента и обратные косые черты, даже если другие связанные параметры не подставляются.

Значения Python `datetime` с типом SQLAlchemy ClickHouse `DateTime64` сохраняют микросекунды как в параметрах на стороне клиента, так и во встроенных литералах, в том числе для значений Nullable и значений, вложенных в массивы и кортежи. ClickHouse применяет объявленную точность. Python `datetime` поддерживает до шести цифр в дробной части. Обычные значения `DateTime` форматируются с точностью до целых секунд. Для оператора `text()` явно укажите тип с помощью `bindparam("ts", type_=DateTime64(6))`, чтобы сохранить доли секунды.

Значение `pandas.Timestamp`, привязанное с типом `DateTime64(9)`, сохраняет наносекунды в параметрах и встроенных литералах.

Типы столбцов SQLAlchemy должны соответствовать схеме на сервере. Если объявить `DateTime64` для серверного столбца типа `DateTime`, в запрос будут подставляться доли секунды, что может приводить к ошибкам преобразования при вставке и в сравнениях `IN`.

В SQLAlchemy 2.x для встроенных литералов общих типов `sqlalchemy.ARRAY`, содержащих элементы ClickHouse `Tuple`, необходимо указать `dimensions=1` (или соответствующую большую размерность для вложенных массивов), чтобы SQLAlchemy рассматривал каждый кортеж как один элемент. SQLAlchemy 1.4 не поддерживает встроенные литералы для общих типов `ARRAY`.

Типизированные именованные параметры `Tuple` принимают словари, ключи которых в точности совпадают с объявленными полями. Для связанных параметров и встроенных литералов клиент использует порядок полей из объявления — в том числе для именованных кортежей внутри массивов и других кортежей. Это относится к синхронным и асинхронным вставкам, предикатам и обоим режимам передачи параметров. Отсутствующие или лишние поля приводят к исключению `ProgrammingError` при привязке параметров запроса. Для массовых вставок в формате Native обработка не меняется. Словари, передаваемые в нетипизированные параметры `exec_driver_sql()`, по-прежнему форматируются как JSON или Map в соответствии с настройками.

Для именованных кортежей внутри значений `Map` задайте `common.set_setting("dict_parameter_format", "map")`. Эта настройка также сохраняет доли секунды для типизированных значений `DateTime64` внутри Map в связанных параметрах и встроенных литералах.

Если именованный параметр даты и времени используется повторно, для сохранения долей секунды каждое его вхождение должно иметь совместимый тип привязки `DateTime64`. Вхождение без типа или с конфликтующим типом форматируется с точностью до целых секунд. Укажите `type_=DateTime64(6)` для каждого `bindparam` или используйте разные имена параметров с соответствующими типами.

То же относится к повторно используемому имени привязки, если в его вхождениях именованный `Tuple` объявлен с разными именами полей. В этом случае клиент обрабатывает такой параметр как позиционный, поэтому значение-словарь не переупорядочивается и сервер его отклоняет. Используйте разные имена параметров или передавайте позиционный кортеж.

### Именованные кортежи {#sqlalchemy-named-tuples}

Поля именованного кортежа объявляются с помощью сопоставления `elements`. Ключи должны быть непустыми строками, а значениями могут быть классы типов ClickHouse SQLAlchemy или их настроенные экземпляры. Поля сохраняют порядок итерации сопоставления, а имена автоматически заключаются в кавычки.

```python
from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import String, Tuple, UInt32

details_type = Tuple(elements={"user_id": UInt32, "display name": String()})
# Tuple(`user_id` UInt32, `display name` String)
```

Для неименованных кортежей используйте `Tuple(UInt32, String)` или `Tuple(elements=[UInt32, String])`. Позиционные элементы и ключевое слово `elements` нельзя использовать совместно.

### Подсказки типов JSON {#sqlalchemy-json-type-hints}

Типизированные JSON-пути объявляются через отображение `typed_paths`. Типом пути может быть класс типа ClickHouse SQLAlchemy, настроенный экземпляр или строка с именем типа ClickHouse. Строки с именами типов позволяют задавать типы, у которых нет конструктора SQLAlchemy, например `Dynamic`, и при этом подходят для сложных настроенных выражений типов.

Строки с именами типов могут содержать настроенные вложенные типы JSON, например ``Array(JSON(`child` UInt32))``. Распознаваемые имена типов ClickHouse в таких строках регистронезависимы и выводятся в канонической капитализации. Строка должна содержать ровно одно полное выражение типа. Завершающий текст и некорректные вложенные аргументы JSON отклоняются.

Пустой `Tuple()` не поддерживается в качестве типизированного JSON-пути, так как ClickHouse не может сериализовать его через Native format JSON-столбца. Основной драйвер поддерживает `Tuple()` в столбцах запроса и вставки в любой позиции, в том числе вложенным в позиционные или именованные кортежи, внутри `Array`, а также как `Nullable(Tuple())` там, где это включено на сервере.

```python
from sqlalchemy import Column, MetaData, Table

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import JSON, UInt32

events = Table(
    "events",
    MetaData(),
    Column(
        "payload",
        JSON(
            typed_paths={
                "event.id": UInt32,
                "details": "Tuple(id UInt32, label Nullable(String))",
                "attributes": "Variant(String, Array(String))",
            },
            max_dynamic_paths=256,
            max_dynamic_types=16,
            skip_paths=["internal.debug"],
            skip_regexps=[r"^private\."],
        ),
    ),
)
```

Для простых путей, являющихся идентификаторами Python, именованные аргументы служат сокращённой записью для `typed_paths`, например `JSON(user_id=UInt32)`. Используйте `typed_paths` для путей с точками, пробелами, обратными кавычками, точками в кодировке `%2E`, а также для имён, совпадающих с параметрами конструктора. Типизированный путь с именем `SKIP` поддерживается через это отображение. Ключи в `typed_paths` и значения в `skip_paths` — это декодированные имена. Обратные и двойные кавычки в начале или в конце имени трактуются как обычные символы пути, а не как заранее применённое SQL-экранирование. Внутри необработанной строки типа обратные и двойные кавычки являются синтаксисом идентификаторов ClickHouse.

Можно задать до 1000 типизированных путей. `max_dynamic_paths` принимает значения от 0 до 10000, `max_dynamic_types` — от 0 до 254. Эти диапазоны действуют и внутри необработанных строк вложенных JSON-типов. Явные серверные значения по умолчанию 1024 и 32 в генерируемый DDL не включаются. Для обычных пропускаемых путей выполняется дедупликация. Строки регулярных выражений не проверяются средствами Python, поскольку ClickHouse использует синтаксис RE2. Дублирующиеся регулярные выражения сохраняются.

Обычный пропускаемый путь не может называться в точности `REGEXP`, так как ClickHouse резервирует этот токен для `SKIP REGEXP`. Имена вида `REGEXP_foo` остаются допустимыми. В необработанной строке JSON-типа операнд обычного `SKIP` должен быть одним идентификатором ClickHouse либо составным идентификатором, разделённым точками. Составной идентификатор без кавычек не может начинаться с `REGEXP`; заключайте первый компонент в кавычки, если он является данными пути. У `SKIP REGEXP` должен быть ровно один строковый литерал в одинарных кавычках. Части идентификатора заключайте в обратные или двойные кавычки, если они содержат пробелы или знаки пунктуации. Необработанные подсказки JSON-типа поддерживают `Variant(...)`; для отдельного `Variant` публичного конструктора SQLAlchemy нет. Члены `Variant` упорядочиваются и дедуплицируются по тем же каноническим именам, которые использует ClickHouse.

Конструктор упорядочивает аргументы в той же канонической форме, которую возвращает ClickHouse. Отражённые типы, копии типов SQLAlchemy и автогенерация Alembic сохраняют эту конфигурацию.

### Подстолбцы JSON {#sqlalchemy-json-subcolumns}

Для столбца, объявленного или представленного как `JSON` в ClickHouse, используйте квадратные скобки, чтобы выбирать по одному сегменту пути к подстолбцу, хранящемуся в базе:

```python
from sqlalchemy import Column, MetaData, Table, select

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import JSON, UInt32

events = Table(
    "events",
    MetaData(),
    Column("payload", JSON),
)

request_id = events.c.payload["context"]["request"].subcolumn(
    "id",
    type_=UInt32,
)

stmt = select(
    events.c.payload["severity"].label("severity"),
    request_id.label("request_id"),
)
```

`payload["severity"]` компилируется в синтаксис точечного идентификатора ClickHouse. Каждая часть заключается в кавычки отдельно, например `` `events`.`payload`.`severity` ``. При этом считывается сохранённый подстолбец JSON ClickHouse без вызова `getSubcolumn`. Для каждого сегмента пути последовательно применяйте `[]` или `.subcolumn()`. Каждый сегмент должен быть непустой строкой.

Передача `type_` в `.subcolumn()` оборачивает точечный путь в SQL `CAST` и назначает этот тип выражению SQLAlchemy. Без `type_` `.subcolumn("segment")` работает так же, как `["segment"]`.

Нетипизированный путь имеет тип `Dynamic` ClickHouse. ClickHouse не допускает использование значений `Dynamic` непосредственно в `ORDER BY` или `GROUP BY`. Передавайте `type_`, если подстолбец используется в них.

Для статически типизированного кода импортируйте `json_subcolumn` из `clickhouse_connect.cc_sqlalchemy`. Эта вспомогательная функция также принимает по одному сегменту за раз и сохраняет тип результата Python из `type_`:

```python
from clickhouse_connect.cc_sqlalchemy import json_subcolumn

context = json_subcolumn(events.c.payload, "context")
request = json_subcolumn(context, "request")
request_id = json_subcolumn(request, "id", type_=UInt32)
```

В этом примере средства проверки типов определяют `request_id` как `ColumnElement[int]`.

Каждый сегмент заключается в кавычки отдельно, в том числе имена с пробелами или обратными кавычками. Обратные кавычки не делают точку литеральной при обработке JSON-путей в ClickHouse. Если включен `json_type_escape_dots_in_keys`, используйте кодирование ClickHouse `%2E` для литеральных точек в ключах. Обращайтесь к ключу с именем `a.b` через `payload["a%2Eb"]`, а не через `payload["a.b"]`.

### Расширения запросов к ClickHouse {#sqlalchemy-query-extensions}

Импортируйте `select` из `clickhouse_connect.cc_sqlalchemy`, чтобы типизированные методы ClickHouse были доступны средствам статической проверки типов. Эти методы также доступны в стандартном `sqlalchemy.select` при выполнении.

```python
from clickhouse_connect.cc_sqlalchemy import select

stmt = (
    select(events.c.user_id, events.c.event_type)
    .final()
    .prewhere(events.c.event_date >= "2026-01-01")
    .sample(0.1)
    .limit_by([events.c.user_id], 3)
)
```

Методы ClickHouse `Select`:

| Method                                   | SQL feature                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------- |
| `.final()`                               | `FINAL` для таблицы                                                             |
| `.sample(value)`                         | `SAMPLE` с использованием доли, количества строк или выражения                  |
| `.prewhere(expression)`                  | `PREWHERE`; повторные вызовы объединяются с помощью `AND`                       |
| `.limit_by(columns, limit, offset=None)` | `LIMIT ... BY`                                                                  |
| `.array_join(...)`                       | `ARRAY JOIN`                                                                    |
| `.left_array_join(...)`                  | `LEFT ARRAY JOIN`                                                               |
| `.ch_join(...)`                          | JOIN в ClickHouse с параметрами `strictness`, `distribution`, `using` и `cross` |
| `.cte(name, materialized=True)`          | `WITH name AS MATERIALIZED (...)`                                               |

`Select.with_hint()` в SQLAlchemy — это API подсказок для таблиц. Диалект ClickHouse не формирует подсказки для таблиц. Подходящая подсказка с wildcard или подсказка `clickhousedb` вызывает `SAWarning` и не изменяет сгенерированный SQL. Для этих секций ClickHouse используйте `final()`, `sample()`, `prewhere()` или `limit_by()`.

`Select.with_statement_hint()` — это API для необработанных завершающих директив. Он добавляет переданный текст в конец `SELECT` без проверки, специфичной для ClickHouse. Этот API по-прежнему доступен для доверенного статического SQL, такого как `SETTINGS max_threads=1`:

```python
stmt = select(events.c.id).with_statement_hint("SETTINGS max_threads=1")
```

Для настроек ClickHouse рекомендуется использовать параметры выполнения, чтобы драйвер обрабатывал их отдельно от текста SQL:

```python
stmt = select(events.c.id).execution_options(settings={"max_threads": 1})
```

Например, `GLOBAL ANY LEFT JOIN` в ClickHouse можно вызывать по цепочке без вложения пользовательского `FromClause`:

```python
stmt = (
    select(events.c.id, users.c.name)
    .select_from(events)
    .ch_join(
        users,
        events.c.user_id == users.c.id,
        isouter=True,
        strictness="ANY",
        distribution="GLOBAL",
    )
)
```

Используйте явную конструкцию `Lambda` для функций высшего порядка в ClickHouse:

```python
from sqlalchemy import column, func

from clickhouse_connect.cc_sqlalchemy import Lambda, select

stmt = select(
    func.arrayMap(
        Lambda("x", column("x") * 2),
        events.c.metrics,
    ).label("doubled")
)
```

Стандартная конструкция SQLAlchemy `values()` компилируется в синтаксис табличной функции ClickHouse `VALUES`, в том числе при использовании в общем табличном выражении (CTE). Для формы CTE требуется SQLAlchemy 2.0.42 или более поздней версии, в которой был добавлен `Values.cte()`.

### Материализованные CTE {#sqlalchemy-materialized-ctes}

По умолчанию ClickHouse подставляет тело общего табличного выражения (CTE), поэтому при каждом обращении к CTE его тело выполняется заново. Передайте `materialized=True` в `.cte()`, чтобы сгенерировать `WITH <name> AS MATERIALIZED (...)`, при котором тело вычисляется один раз:

```python
from sqlalchemy import func

from clickhouse_connect.cc_sqlalchemy import select

ranked = (
    select(book.c.book_id, func.row_number().over(order_by=book.c.score.desc()).label("result_rank"))
    .where(book.c.genre == "sci-fi")
    .order_by(book.c.score.desc())
    .limit(100)
    .cte("ranked", materialized=True)
)

stmt = (
    select(book.c.book_id, ranked.c.result_rank)
    .select_from(book)
    .ch_join(ranked, book.c.book_id == ranked.c.book_id, strictness="ANY")
    .where(book.c.book_id.in_(select(ranked.c.book_id)))
    .execution_options(settings={"enable_materialized_cte": 1, "enable_analyzer": 1})
)
```

Сервер материализует CTE только при наличии ключевого слова `MATERIALIZED`, значении `enable_materialized_cte=1` и включенном analyzer. Установите `enable_materialized_cte` для оператора, подключения или движка, как показано в разделе [Настройки для отдельных запросов](#sqlalchemy-per-query-settings). Analyzer по умолчанию включен на всех серверах, поддерживающих эту возможность, поэтому явная установка `enable_analyzer=1` служит дополнительной мерой предосторожности. `enable_materialized_cte` — экспериментальная настройка ClickHouse. При `enable_materialized_cte=0` или `enable_analyzer=0` запрос успешно выполняется и возвращает те же строки. ClickHouse молча игнорирует `MATERIALIZED` и снова разворачивает CTE, поэтому пропущенная настройка снижает производительность без каких-либо сообщений. Для материализованных CTE требуется ClickHouse 26.3 или более поздней версии. Более старые серверы отклоняют ключевое слово с синтаксической ошибкой.

Для оператора, построенного с помощью стандартного `sqlalchemy.select`, вместо этого используйте `cte()` уровня модуля. В качестве первого аргумента она принимает оператор, а в остальном повторяет `Select.cte()`:

```python
from sqlalchemy import select as sa_select

from clickhouse_connect.cc_sqlalchemy import cte

ranked = cte(sa_select(book.c.book_id), "ranked", materialized=True)
```

Ключевое слово применяется только в диалекте ClickHouse, поэтому оператор, используемый с другим backend-соединением, компилируется там без изменений.

ClickHouse не поддерживает рекурсивные материализованные CTE. Вспомогательные функции SQLAlchemy вызывают `ValueError`, если одновременно заданы `recursive=True` и `materialized=True`.

## DDL и рефлексия {#sqlalchemy-ddl-reflection}

ClickHouse Connect предоставляет типы данных ClickHouse, движки таблиц, конструкции для словарей, DDL для баз данных и рефлексию таблиц.

Для обеспечения совместимости `Inspector.get_table_names()` возвращает представления всех видов. `MetaData.reflect()` по умолчанию также включает их, а с помощью параметра `only` можно выбрать представление по имени. Используйте `Inspector.get_view_names()` для non-materialized представлений и `Inspector.get_materialized_view_names()` для materialized view. Оба метода принимают `schema` и работают в SQLAlchemy 1.4.40 и более поздних версиях, включая 2.x. `Inspector.get_view_definition()` возвращает сохранённый запрос `SELECT` представления или materialized view, а для таблиц и несуществующих имён вызывает `NoSuchTableError`. У отражённого представления нет движка. Его объект `Table` содержит параметр `clickhousedb_table_type` со значением `view`, `materialized_view`, `window_view` или `live_view`.

`Nullable()` и `LowCardinality()` из `clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes` принимают класс или экземпляр типа ClickHouse SQLAlchemy и сохраняют его конкретный тип для средств проверки типов. Например, `Nullable(String)` возвращает экземпляр `String`, который можно напрямую передать в `Column`. Средства проверки типов выводят для `[Nullable(String)]` тип `list[String]`. Если в списке есть и другие типы ClickHouse, аннотируйте его как `list[ChSqlaType]` и импортируйте `ChSqlaType` из `clickhouse_connect.cc_sqlalchemy.datatypes.base`.

Отдельные столбцы `Variant` отражаются через внутренний тип SQLAlchemy, а автогенерация Alembic сохраняет их канонические исходные имена типов без повторяющихся изменений типа. Столбцы `Geometry` и `MultiPoint` отражаются как публичные типы SQLAlchemy.

```python
import sqlalchemy as db
from sqlalchemy import MetaData

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import DateTime64, String, UInt32
from clickhouse_connect.cc_sqlalchemy.ddl.custom import CreateDatabase
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import MergeTree

with engine.connect() as conn:
    conn.execute(CreateDatabase("example_db", exists_ok=True))

    metadata = MetaData(schema="example_db")
    events = db.Table(
        "events",
        metadata,
        db.Column("id", UInt32, primary_key=True),
        db.Column("user", String),
        db.Column("created_at", DateTime64(3)),
        MergeTree(order_by="id"),
    )
    events.create(conn)

    reflected = db.Table("events", MetaData(schema="example_db"), autoload_with=conn)
    assert reflected.engine is not None
```

Отражённые столбцы содержат `server_default` для выражений `DEFAULT`. Отражённые
объекты SQLAlchemy используют специфичные для диалекта параметры, такие как `clickhousedb_codec`,
`clickhousedb_ttl`, `clickhousedb_materialized` и `clickhousedb_alias`, если они заданы.
Публичные словари, возвращаемые `Inspector.get_columns()`, сохраняют
соответствующие ключи `clickhouse_*`. В этих словарях `server_default`,
`clickhouse_materialized`, `clickhouse_alias` и `clickhouse_ttl` являются SQL-строками.
Чтобы построить на их основе `Column`, оберните каждую из них в `sqlalchemy.text()`.

Используйте `clickhousedb_*` в новых объявлениях таблиц и столбцов. Именно эти имена используются
в метаданных, генерируемых драйвером, и в ревизиях Alembic. ClickHouse Connect также читает
явно заданные устаревшие параметры `clickhouse_*`, однако SQLAlchemy проверяет их на соответствие
диалекту, которому принадлежит префикс `clickhouse`. При смешанной установке такие параметры ClickHouse Connect,
как `clickhouse_engine`, `clickhouse_ttl`, `clickhouse_settings`,
`clickhouse_table_type` и `clickhouse_dictionary_*`, могут вызывать `ArgumentError`.
Переименуйте их в `clickhousedb_*`.

ClickHouse Connect читает значения по умолчанию только из `clickhousedb`. Регистрируйте их с помощью
`Table.argument_for("clickhousedb", ...)` или
`Column.argument_for("clickhousedb", ...)`. Аргументы операций Alembic, такие как
`op.add_column(..., clickhouse_settings={...})`, сохраняют прежние имена.

Для строковых значений в секциях `DEFAULT`, `MATERIALIZED`, `ALIAS` и `TTL` используется экранирование строк ClickHouse. Такое же экранирование применяется к комментариям таблиц, словарей и столбцов, включая комментарии, создаваемые Alembic.

Аргументы ключа MergeTree, такие как `order_by`, `partition_by`, `primary_key`, `sample_by` и `ttl`, принимают столбцы SQLAlchemy, SQL-выражения, а также обычные строки.

`Memory()`, `Log()`, `StripeLog()`, `TinyLog()`, `Null()` и `Set()` можно вызывать без аргументов, и они без потерь проходят полный цикл автогенерации Alembic. Существующий аргумент-словарь по-прежнему поддерживается. Для передачи настроек движка используйте `settings={...}`.

`SummingMergeTree` и `ReplicatedSummingMergeTree` принимают необязательный аргумент `columns`, который передаётся только как именованный. Существующие позиционные аргументы сохраняют прежний смысл, поэтому `SummingMergeTree("id")` по-прежнему задаёт `ORDER BY id`.

```python
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import SummingMergeTree

engine_clause = SummingMergeTree("id", columns=("delta", "n_tx"))
# Sum delta and n_tx for rows with the same id.
```

Передайте строку, столбец SQLAlchemy, сопоставленный атрибут столбца или непустой список либо кортеж таких значений. Строковые элементы списка и кортежа заключаются в кавычки как идентификаторы. Скалярная строка задаёт Raw SQL, например `"delta"` или `"(delta, n_tx)"`. Сервер допускает для этих столбцов только идентификаторы. Если не указывать `columns`, ClickHouse сам выберет столбцы для суммирования. Рефлексия и автогенерация Alembic сохраняют явно заданный список столбцов.

## Вставка данных и базовое использование ORM {#sqlalchemy-inserts}

Поддерживаются вставки через Core и простые модели ORM. Для синхронного диалекта при массовой загрузке данных предпочтительнее использовать вставки через Core с executemany там, где это поддерживается. Для асинхронной массовой вставки используйте нативный метод `AsyncClient.insert()`, описанный в разделе [Асинхронные соединения](#sqlalchemy-async-connections).

```python
with engine.connect() as conn:
    conn.execute(
        events.insert(),
        [
            {"id": 13, "user": "user_1"},
            {"id": 79, "user": "user_2"},
        ],
    )
```

Для синхронного диалекта обычные вставки Core через `executemany`, сгенерированные компилятором SQLAlchemy, выполняются как одна массовая вставка в формате Native. Асинхронный executemany отправляет отдельный запрос для каждого набора параметров, как описано в разделе [Асинхронные соединения](#sqlalchemy-async-connections). Raw SQL, а также вставки с выражениями или иной семантикой, которую нельзя безопасно перенаправить, сохраняют исходный SQL и выполняются отдельно для каждого набора параметров. Если один из последующих наборов параметров завершится с ошибкой, строки, записанные предыдущими наборами, останутся закоммиченными.

Явные многострочные операторы `insert(events).values([...])` поддерживают строки в виде словарей, кортежи в порядке столбцов таблицы и SQL-выражения для отдельных строк. Именно эту форму использует Pandas `to_sql(method="multi")`. Строки при этом вставляются, но возвращается `0`, поскольку текстовые операторы INSERT сообщают через курсор DB-API количество строк `0`. SQLAlchemy определяет список столбцов по первой строке. Лишние ключи словарей в последующих строках и значения кортежей, выходящие за пределы этого списка столбцов, игнорируются. Если в одной из последующих строк отсутствует значение для выбранного столбца, компиляция завершается ошибкой. Задавайте во всех строках одинаковый набор столбцов.

При стандартных ограничениях HTTP-формы в ClickHouse 26.4 и новее `server_side_params=True` подходит только для небольших явных батчей — примерно до 1000 привязываемых значений с запасом для других полей. Этот предел можно повысить в конфигурации сервера. Для больших обычных батчей в синхронном диалекте передавайте строки вторым аргументом `execute()`, чтобы драйвер мог выполнить массовую вставку в формате Native. Для асинхронной загрузки больших объёмов данных используйте `await` с нативным методом `AsyncClient.insert()`.

```python
import sqlalchemy as db
from sqlalchemy import MetaData
from sqlalchemy.orm import Session, declarative_base

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import String, UInt32
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import MergeTree

Base = declarative_base(metadata=MetaData(schema="example_db"))


class User(Base):
    __tablename__ = "users"
    __table_args__ = (MergeTree(order_by=["id"]),)

    id = db.Column(UInt32, primary_key=True)
    name = db.Column(String)


Base.metadata.create_all(engine)

with Session(engine) as session:
    session.add(User(id=13, name="user_1"))
    session.bulk_save_objects([User(id=79, name="user_2")])
    session.commit()
```

## Представления и SQL-функции {#sqlalchemy-views-functions}

Alembic предоставляет отдельные вспомогательные функции для создания, замены и удаления обычных представлений и пользовательских SQL-функций:

```python
from alembic import op

op.create_clickhouse_view("active_events", "SELECT id FROM analytics.events", schema="analytics")
op.create_clickhouse_view("active_events", "SELECT id FROM analytics.events WHERE id > 13", schema="analytics", or_replace=True)
op.drop_clickhouse_view("active_events", schema="analytics", if_exists=True)

op.create_clickhouse_function("analytics_increment_v1", "(value) -> value + 13")
op.create_clickhouse_function("analytics_increment_v1", "(value) -> value + 79", or_replace=True)
op.drop_clickhouse_function("analytics_increment_v1", if_exists=True)
```

Обе вспомогательные функции создания принимают `if_not_exists=False` и `or_replace=False`. Если передать оба параметра со значением `True`, будет вызвано исключение `ValueError`. Тела SQL — это строки, которые передаются в ClickHouse без изменений. Имена заключаются в кавычки как идентификаторы, если они ещё не заключены в кавычки; имя функции считается одним идентификатором, даже если содержит точку. SQL-функции глобальны в пределах сервера, поэтому у вспомогательных функций для работы с функциями и у методов инспекции нет аргумента `schema`. Используйте глобально уникальные или версионируемые имена функций во всех базах данных и потоках миграций. Эти операции поддерживают как онлайн-выполнение, так и офлайн-рендеринг SQL, в том числе асинхронные соединения SQLAlchemy через `run_sync`.

`or_replace=True` явно указывает на необходимость замены. ClickHouse может заменить существующую таблицу или materialized view обычным представлением с тем же именем, при этом данные прежнего объекта будут удалены. `DROP VIEW` не удаляет базовые таблицы, но может удалять materialized view. `IF NOT EXISTS` оставляет существующее определение без изменений и не проверяет его. Для замены и создания с проверкой существования невозможно автоматически определить безопасное понижение версии; задайте его явно, используя предыдущее определение. Для операций удаления также требуется явно задавать понижение версии. Восстановление определения не восстанавливает удалённые данные. Для замены SQL-функции требуются обе привилегии: `CREATE FUNCTION` и `DROP FUNCTION`.

ClickHouse разворачивает вызовы SQL UDF при сохранении определения представления. Замена SQL UDF не обновляет существующие представления, которые её используют; пересоздайте эти представления или явно измените их, чтобы они использовали новое определение.

Для инспекции обычных представлений используйте существующие методы `get_view_names(schema=...)` и `get_view_definition(name, schema=...)`. Инспекция SQL-функций доступна только в диалекте ClickHouse:

```python
from sqlalchemy import inspect

inspector = inspect(connection)
names = inspector.get_clickhouse_function_names()
create_sql = inspector.get_clickhouse_function_definition("analytics_increment_v1")
```

Инспекция функций охватывает только функции `SQLUserDefined`; встроенные и исполняемые функции не учитываются. Имена возвращаются в отсортированном виде. Определение — это полный сохранённый оператор `CREATE FUNCTION`, а не только тело лямбда-функции; если имя не найдено, вызывается исключение `sqlalchemy.exc.NoResultFound`. Ошибки доступа к каталогу распространяются дальше. Инспекция метаданных возвращает текст, даже если в пользовательских запросах указаны форматы, возвращающие байты. Эти вспомогательные функции не добавляют ни декларативных сущностей для представлений и функций, ни сравнения через autogenerate, ни упорядочивания по зависимостям. Располагайте явные операции миграции в порядке зависимостей и при их рендеринге используйте `render_as_batch=False`.

## Индексы пропуска данных {#sqlalchemy-skip-indexes}

Индексы пропуска данных ClickHouse объявляются как аргументы таблицы. Для этого API требуется SQLAlchemy, а Alembic не нужен:

```python
from sqlalchemy import Column, MetaData, Table, inspect
from clickhouse_connect.cc_sqlalchemy import ClickHouseIndex, engines, types

metadata = MetaData()
events = Table(
    "events",
    metadata,
    Column("value", types.UInt32),
    Column("label", types.String),
    ClickHouseIndex("value_idx", "value", "minmax"),
    ClickHouseIndex("label_idx", "label", "bloom_filter(0.01)", granularity=4),
    engines.MergeTree(order_by="value"),
)
metadata.create_all(engine)

indexes = inspect(engine).get_clickhouse_indexes("events")
```

Выражения и типы индексов задаются на необработанном ClickHouse SQL. Определения неизменяемы, а имена должны быть уникальными в пределах таблицы. Объявления хранятся в параметре таблицы `clickhousedb_indexes`, который также принимает последовательность определений `ClickHouseIndex`. `Table.to_metadata()` сохраняет их. `CREATE TABLE` выводит их встроенно в определение таблицы. `if_not_exists`, `first` и `after_index` по-прежнему доступны для императивных вспомогательных функций ALTER и не влияют ни на встроенное создание, ни на сравнение схем.

`Inspector.get_clickhouse_indexes()` возвращает определения явных индексов, пригодные для повторного применения. Отражённые выражения заключаются в обёртку `tuple(...)`, чтобы сохранить список выражений индекса ClickHouse, включая вложенные кортежи. Неявные индексы, созданные сервером, исключаются по полю `creation` каталога. При ошибках каталога и неизвестных классификациях вызывается исключение. Каталог должен предоставлять поле `creation`. Согласно примечаниям к выпуску ClickHouse, это поле появилось в версии 26.1.1.912 и в бэкпорте 25.12.2.54. Совместимость проверяется фактическим запросом, а не по строке версии.

Общий метод `Inspector.get_indexes()` по-прежнему возвращает пустой список. `Table(..., autoload_with=engine)` не читает каталог skip-index. Чтобы явно скопировать и столбцы, и индексы:

```python
inspector = inspect(engine)
reflected = Table(
    "events",
    MetaData(),
    autoload_with=engine,
    clickhousedb_indexes=inspector.get_clickhouse_indexes("events"),
)
```

## Проекции {#sqlalchemy-projections}

Проекции SELECT можно объявлять как аргументы таблицы, не прибегая к Alembic:

```python
from sqlalchemy import Column, MetaData, Table, inspect
from clickhouse_connect.cc_sqlalchemy import ClickHouseProjection, engines, types

metadata = MetaData()
events = Table(
    "events",
    metadata,
    Column("value", types.UInt32),
    Column("label", types.String),
    ClickHouseProjection("by_label", "SELECT value, label ORDER BY label, value"),
    engines.MergeTree(order_by="value"),
)
metadata.create_all(engine)

projections = inspect(engine).get_clickhouse_projections("events")
```

`select` — это необработанный SQL-код внутри скобок проекции. Определения неизменяемы, а имена проекций должны быть уникальными в пределах таблицы. Параметр таблицы `clickhousedb_projections` также принимает последовательность определений `ClickHouseProjection`. `Table.to_metadata()` сохраняет объявления, а `CREATE TABLE` выводит их встроенно при рендеринге. Словари не допускают объявления проекций. `if_not_exists`, `first` и `after_projection` по-прежнему доступны для императивных вспомогательных функций ALTER и не влияют на встроенное создание или сравнение. Импорт из `clickhouse_connect.cc_sqlalchemy.alembic` и `.alembic.operations`, включая существующие позиционные аргументы конструктора, по-прежнему поддерживается.

`Inspector.get_clickhouse_projections()` возвращает сохранённые определения SELECT, сохраняя подстановочные шаблоны, псевдонимы, группировку и упорядочивание. Метод отклоняет конструкцию `WITH SETTINGS` на уровне проекции и формы проекций на основе индексов, поскольку API, работающий только с SELECT, не может полностью сохранить такие определения. Сбои при обращении к каталогу также приводят к исключению. Обычный вызов `Table(..., autoload_with=engine)` не считывает каталог проекций. Чтобы явно скопировать столбцы и проекции:

```python
inspector = inspect(engine)
reflected = Table(
    "events",
    MetaData(),
    autoload_with=engine,
    clickhousedb_projections=inspector.get_clickhouse_projections("events"),
)
```

Для проверки требуются видимая целевая таблица и доступ к полям `database`, `table`, `name`, `type`, `query` и `settings` в `system.projections`. Этот каталог появился в ClickHouse в версии 24.9.1.3278. Однако само его наличие ещё не гарантирует поддержку сравнения. Драйвер определяет доступные возможности с помощью каталога и запросов нормализации.

## Миграции Alembic {#sqlalchemy-alembic}

ClickHouse Connect поддерживает интеграцию с Alembic для миграций схем ClickHouse. Установите её с помощью:

```bash
pip install "clickhouse-connect[alembic]"
```

Для миграций через асинхронный диалект установите оба дополнительных модуля:

```bash
pip install "clickhouse-connect[alembic,sqlalchemy-async]"
```

Создайте асинхронный проект Alembic, затем замените сгенерированное окружение примером с поддержкой ClickHouse:

```bash
alembic init -t async alembic
```

Сгенерированный `alembic.ini` использует `script_location = %(here)s/alembic`. Оставьте эту настройку, если каталог миграций называется `alembic`, или укажите в ней каталог, переданный в `alembic init`. Замените `alembic/env.py` на [асинхронный пример `env.py` для Alembic](https://github.com/ClickHouse/clickhouse-connect/blob/main/examples/alembic_async/env.py) из репозитория, затем задайте `sqlalchemy.url` в `alembic.ini`.

Импортируйте `clickhouse_connect.cc_sqlalchemy.alembic` в `env.py` Alembic, чтобы зарегистрировать интеграцию диалекта. Автогенерация поддерживает типовые изменения таблиц, включая создание и удаление таблиц, добавление/изменение/удаление столбцов, значения по умолчанию, комментарии и настройки таблиц MergeTree. Для переименования таблиц и столбцов используйте ручные операции. Проверяйте каждую сгенерированную миграцию перед её применением.

В ClickHouse Cloud добавьте `alter_sync=2` в URL движка миграций, чтобы последующая рефлексия видела завершённые изменения схемы на всех репликах. Это важно, если соединение было заменено или автогенерация запускается сразу после обновления. `select_sequential_consistency=1` распространяется на чтение данных, но не на изменения схемы.

Вставки в таблицу версий выполняются в обход дедупликации вставок, чтобы при понижении версии можно было восстановить ранее записанную ревизию. Сгенерированный офлайн-SQL использует `SETTINGS deduplicate_insert = 'disable'`, поэтому эта настройка должна поддерживаться целевым сервером. Онлайн-миграции используют устаревшую настройку `insert_deduplicate = 0`, если сервер не поддерживает более новую настройку. Для обычных вставок в таблицы сохраняется настроенное поведение дедупликации.

Для таблиц, присутствующих и в метаданных, и на сервере, автогенерация сравнивает объявленный движок таблицы с серверным. Автоматическая миграция изменений семейства движка, позиционных аргументов движка, `ORDER BY`, `PRIMARY KEY`, `PARTITION BY`, `SAMPLE BY` и `TTL` таблицы не поддерживается, поэтому при обнаружении различия выбрасывается `UnsupportedTableChangeError`, а не записывается пустая или вводящая в заблуждение ревизия. Напишите явную миграцию, предварительно изучив поддержку ALTER на сервере и затрагиваемые данные. Исключение содержит кортеж `drifts` из записей `TableOptionDrift` с указанием таблицы, параметра и обоих вариантов записи. Для создания исключения требуется хотя бы одно расхождение, иначе выбрасывается `ValueError`. Выражения сравниваются после нормализации, а если текст всё ещё различается, серверная функция `formatQuerySingleLine` сопоставляет такие варианты записи, как `INTERVAL 30 DAY` и `toIntervalDay(30)`. Аргументы движка в кавычках сравниваются по декодированному содержимому строки посимвольно, включая пробелы и знаки препинания. Выражения TTL форматируются как `ALTER TABLE t MODIFY TTL ...` с сохранением таких действий, как `DELETE WHERE`, `TO VOLUME` и `RECOMPRESS`. `MergeTree` и варианты Cloud `Shared*` и `Replicated*` считаются одним семейством, а аргументы пути репликации не сравниваются.

Объявленные `settings` движка, отличающиеся от серверных, преобразуются в `op.modify_clickhouse_table_settings(...)`, а при понижении версии каждая настройка восстанавливается или сбрасывается. Значения и типы из `system.merge_tree_settings` позволяют определить значения по умолчанию и эквивалентные варианты записи булевых и числовых значений; строковые настройки сохраняют строковое значение. Настройки, не объявленные в модели, сохраняются, в том числе удалённые из модели после предыдущей миграции. Рефлексия не может отличить такие настройки от добавленных сервером, поэтому автогенерация никогда не сбрасывает их автоматически. Если сброс действительно нужен, явно используйте `op.reset_clickhouse_table_settings(...)`. Настройки только для чтения, такие как `index_granularity` и `index_granularity_bytes`, сравниваются и отклоняются так же, как ключи. Чтобы пропустить сравнение, передайте `clickhousedb_compare_table_options=False` в `context.configure()`.

Отражённые представления и materialized view не являются таблицами. `include_object` исключает их, поэтому автогенерация никогда не предлагает `drop_table` для представления, отсутствующего в метаданных. Управляйте ими с помощью обычных хелперов для представлений или materialized view.

`op.alter_column(..., server_default=None)` генерирует `MODIFY COLUMN ... REMOVE DEFAULT` — единственную форму, которую поддерживает сервер. Сервер отклоняет этот оператор, если у столбца нет `DEFAULT` или используется `MATERIALIZED` или `ALIAS`, поэтому запрашивайте удаление, только если значение по умолчанию задано. Изменение одного лишь типа сохраняет существующее значение по умолчанию. Параметры столбцов диалекта подчиняются тому же правилу: передайте `clickhousedb_codec=None`, `clickhousedb_ttl=None`, `clickhousedb_alias=None` или `clickhousedb_materialized=None`, чтобы удалить свойство, либо значение, чтобы задать его. Для установки или удаления только этих свойств `existing_type` не требуется. Используйте `text(...)` для SQL-выражений TTL, псевдонимов и материализованных столбцов, например `clickhousedb_ttl=text("ts + INTERVAL 7 DAY")`. Непереданные параметры остаются без изменений. Принимаются как имена с префиксом `clickhousedb_`, так и устаревшие имена с префиксом `clickhouse_`; если в `alter_column` переданы оба имени, приоритет имеет явное значение `clickhousedb_`, включая `None`.

Если в метаданных не указана версия состояния `AggregateFunction`, автогенерация принимает существующую отражённую версию. Например, `AggregateFunction(uniq, UInt32)` соответствует отражённому типу `AggregateFunction(1, uniq, UInt32)`. Это правило действует и для вложенных типов. Изменение агрегатной функции, её параметров или типов её аргументов по-прежнему приводит к изменению типа.

Версия, явно указанная в метаданных, должна совпадать с отражённой версией. Устаревшие отражённые типы без версии соответствуют явной версии `0`. Если версия не указана, это не означает запроса на обновление существующего формата состояния после обновления сервера. Указывайте версию явно, если намерены изменить формат состояния.

Функции миграций Alembic остаются синхронными. Асинхронное окружение создаёт `AsyncEngine`, открывает `AsyncConnection` и передаёт синхронную функцию миграции в `await connection.run_sync(...)`. Офлайн-миграции напрямую вызывают `context.configure(url=..., literal_binds=True, dialect_opts={"paramstyle": "named"})` и не создают движок. [Асинхронный пример `env.py` для Alembic](https://github.com/ClickHouse/clickhouse-connect/blob/main/examples/alembic_async/env.py) из репозитория поддерживает оба варианта и считывает URL соединения из стандартного параметра конфигурации Alembic `sqlalchemy.url`. В нём сохранены хуки и параметры ClickHouse для Alembic из подробного примера, включая `include_object`, `make_include_name(...)`, `clickhouse_writer` и `version_table`. Не используйте `engine.sync_engine` для запуска асинхронных миграций или освобождения их ресурсов.

Специальные для ClickHouse хелперы `op.*` охватывают:

* Индексы пропуска данных, включая операции добавления, материализации и удаления.
* Проекции, включая операции добавления, материализации и удаления.
* Изменение и сброс настроек таблиц семейства MergeTree.
* Создание, замену и удаление обычных представлений и SQL-функций.
* Создание и удаление materialized view.
* Создание, удаление и перезагрузку словарей.

**Примечание об обновлении:** по умолчанию Alembic сравнивает явно заданные индексы пропуска данных и проекции SELECT. Для объектов, которые были созданы только предыдущими императивными миграциями и отсутствуют в метаданных управляемых таблиц, могут генерироваться операции удаления. Перед обновлением объявите их с помощью `ClickHouseIndex` или `ClickHouseProjection`, исключите неуправляемые объекты с помощью `include_name` или `include_object` либо отключите соответствующее сравнение в `context.configure()`:

```python
context.configure(
    connection=connection,
    target_metadata=metadata,
    clickhousedb_compare_indexes=False,
    clickhousedb_compare_projections=False,
)
```

Каждый параметр отключает соответствующие чтения каталога и снимки для понижения версии при удалении таблиц. Изменения порождают отдельные операции удаления и добавления. При понижении версии определения восстанавливаются, но ни в одном направлении не восстанавливается предыдущая материализация. При замене проекции её существующие части проекций удаляются. Оцените стоимость перестроения и явно выполните `MATERIALIZE PROJECTION`, если замена должна сразу затронуть существующие части. Материализация индексов также выполняется только явно.

Объявляйте индексы пропуска данных с помощью `ClickHouseIndex` для поддержки autogenerate или используйте существующие вспомогательные функции `op.add_clickhouse_index` и `op.drop_clickhouse_index` в явно написанных ревизиях. Импорт из `clickhouse_connect.cc_sqlalchemy.alembic` и `.alembic.operations` по-прежнему поддерживается. Стандартные `Index`, `Column(index=True)`, `op.create_index` и `op.drop_index` из SQLAlchemy по-прежнему отклоняются.

Для управляемых таблиц объявления по умолчанию определяют полный набор явных существующих индексов. Для необъявленного явного индекса создаётся операция удаления — в том числе для индексов, ранее созданных только императивными миграциями. Изменение выражения, типа индекса, параметра или фактической гранулярности приводит к отдельному удалению с последующим добавлением. При понижении версии восстанавливается предыдущее определение. Операции остаются доступными для `process_revision_directives` до рендеринга. Хуки политик должны сопоставлять изменения индексов и проекций по схеме, таблице и имени объекта. Не полагайтесь на порядок следования операций. Ни в одном направлении предыдущая материализация не восстанавливается, и `MATERIALIZE INDEX` не генерируется. Выполните материализацию явно, если индекс должен сразу применяться к существующим частям.

Генерируйте добавление, удаление и изменение индексов с `render_as_batch=False`. Соответствующие вспомогательные функции не поддерживают отложенную batch-очередь Alembic, поэтому при `render_as_batch=True` во время генерации возникает ошибка. Встроенные индексы при создании таблиц и в снимках downgrade для удаления таблиц по-прежнему поддерживаются.

То же ограничение действует и для других пользовательских операций ClickHouse внутри batch-блока, включая настройки таблицы, проекции и материализацию. Генерируйте эти операции вне batch-режима.

Для физического пересоздания таблицы в batch-режиме с помощью `op.batch_alter_table()` передайте в `copy_from` полный объект Table, содержащий столбцы, движок и `clickhousedb_indexes`. Чтобы загрузить и столбцы, и индексы, воспользуйтесь приведённым выше примером явного отражения или передайте полные метаданные для офлайн-миграций. Автоматическое онлайн-пересоздание считывает каталог индексов во время выполнения и отклоняет таблицы с явно заданными индексами ещё до создания или удаления таблиц. Отключение сравнения в autogenerate не позволяет обойти эту проверку.

Стандартные хуки `include_name` и `include_object` получают `type_="index"`. Фильтры по имени применяются как к отражённым, так и к объявленным кандидатам, поэтому исключённое имя остаётся неуправляемым. Фильтры объектов получают обычные значения `reflected` и `compare_to`. Передаваемые им объекты индексов предоставляют поля определения и `.table`. Например, стандартный рецепт Alembic для неуправляемых объектов, `reflected and compare_to is None`, защищает индексы, создаваемые только императивно. Фильтры таблиц учитываются до чтения каталога индексов. Встроенные индексы во вновь создаваемых таблицах также фильтруются до вызова хуков политик.

При сравнении используются форматирование и анализ на стороне сервера, чтобы учитывать варианты написания и значения по умолчанию в ClickHouse. Анализ выражений опирается на текущую таблицу, серверные функции и настройки. Для него требуются анализатор и ожидаемый вывод `EXPLAIN`. Эти возможности проверены на ClickHouse 26.8, а исходный код изучен для версии 26.6. Само по себе наличие поля в каталоге не гарантирует поддержку сравнения на более старом сервере. Если изменённые определения `ALIAS` влияют на индекс, перед сравнением индексов требуется явная миграция столбца.

Изменение индекса может ссылаться на физический столбец, добавленный в той же ревизии. Если анализ сообщает, что такой запланированный новый столбец является неизвестным идентификатором, autogenerate проверяет полное выражение с учётом добавленных столбцов, а затем генерирует добавление столбца перед удалением и добавлением индекса. Другие неизвестные идентификаторы, включая опечатки и столбцы, исключённые фильтрами, по-прежнему приводят к `IndexComparisonError`.

Пустые скобки у типа и различия в регистре, например `minmax()`, `MinMax()` и `minmax`, при сравнении считаются эквивалентными. Опущенные аргументы типа при сравнении не раскрываются: переход между `bloom_filter` и `bloom_filter(0.025)` может привести к однократному удалению и повторному добавлению индекса, даже если сервер использует это значение по умолчанию.

Сравнение не устанавливает эквивалентность произвольных SQL-выражений. Если нормализация прошла успешно, но полученные формы различаются, autogenerate генерирует замену, даже если выражения возвращают одинаковые значения. Проверяйте такие изменения или управляйте этими индексами с помощью явных миграций и фильтров.

Если доступ к каталогу, разрешение выражений или ожидаемый результат нормализации недоступны, autogenerate вызывает исключение `IndexComparisonError` с указанием таблицы, индекса, объявленного и отражённого определений, а также причины. Внимательно проверяйте изменения. Удаление и добавление выполняются отдельными нетранзакционными операторами. Если добавление завершится ошибкой, старого индекса может уже не быть.

### Autogenerate для проекций {#projection-autogenerate}

По умолчанию Alembic сравнивает проекции SELECT в управляемых таблицах. Актуальный набор проекций определяется объявлениями. Для необъявленных проекций генерируются операции удаления, а для изменённых определений — отдельные операции удаления и добавления. Для каждой таблицы autogenerate упорядочивает операции так: удаление проекций, добавление и изменение столбцов, операции с индексами, добавление проекций и затем удаление столбцов. Alembic добавляет удаление столбцов после завершения работы компараторов таблиц. В хуках политик сопоставляйте изменения по схеме, таблице и имени проекции. Между удалением и добавлением могут оказаться другие операции. При понижении версии восстанавливаются предыдущие определения, включая проекции в пересоздаваемых удалённых таблицах. Операции передают полные определения в `process_revision_directives` до рендеринга. `MATERIALIZE PROJECTION` не генерируется, и ни повышение, ни понижение версии не восстанавливает прежнюю материализацию кусков. Выполняйте материализацию явно, если проекция нужна существующим кускам сразу.

Для `AggregatingMergeTree` и других движков с нестандартным поведением слияния ClickHouse отклоняет `ADD PROJECTION`, если `deduplicate_merge_projection_mode='throw'`. Перед добавлением или заменой проекций, в том числе изначально объявленных встроенно, явно установите значение `drop` или `rebuild`.

`include_name` и `include_object` получают `type_="projection"`. Фильтры по имени применяются как к отражённым, так и к объявленным именам. Фильтры объектов получают определения с `.table`, `reflected` и `compare_to`. Стандартный рецепт `reflected and compare_to is None` защищает проекции, создаваемые только императивно. Фильтры таблиц выполняются до чтения каталога, а встроенные определения в новых таблицах фильтруются до хуков политик. Неподдерживаемые определения у отфильтрованных проекций или в несвязанных таблицах не блокируют сравнение.

При сравнении используется форматтер полной грамматики проекций на сервере, а также регистронезависимые имена функций и псевдонимы из `system.functions` — по аналогии с нормализацией CREATE в ClickHouse. Структура SELECT, включая подстановочные символы и агрегатные выражения, сохраняется, а не анализируется как обычный SELECT относительно актуальной таблицы. Различия в форматировании, экранировании идентификаторов и написании зарегистрированных регистронезависимых функций не считаются изменениями. Регистрозависимые имена, такие как `sumIf` и `SumIf`, по-прежнему различаются. Если отформатированные определения различаются, дополнительно проверяется разобранное синтаксическое дерево, в котором группирующие скобки игнорируются. Избыточные скобки, а также варианты записи операторов и функций, например `value + 13` и `plus(value, 13)`, считаются эквивалентными, поскольку разные версии ClickHouse и ClickHouse Cloud хранят избыточные скобки непоследовательно. Прочие структурные различия приводят к генерации операций удаления и добавления. Сравнение не гарантирует эквивалентность произвольного SQL и не проверяет зависимости столбцов. Замена может ссылаться на физический столбец, добавленный ранее в той же ревизии. Перед применением проверьте зависимости, включая изменённые столбцы ALIAS. Некорректные зависимости приводят к ошибке при выполнении DDL, а неудачное добавление может оставить таблицу без старой проекции, поскольку удаление и добавление — отдельные нетранзакционные операторы.

Отсутствующие поля каталога, ошибки доступа к каталогу, недоступность метаданных форматирования или функций, `WITH SETTINGS` на уровне проекции и формы на основе индексов вызывают `ProjectionComparisonError` с указанием таблицы, проекции, объявленного и отражённого определений, а также причины. При неудачной нормализации вместо генерации замены выдаётся эта диагностика. Отфильтруйте неподдерживаемые проекции или управляйте ими с помощью явных миграций. Если `query_masking_rules` изменяет текст SELECT, возвращаемый каталогом, сравнение и воспроизведение могут работать ненадёжно. Для затронутых проекций используйте явные миграции, фильтры или отключение сравнения. Для нормализации функций в `system.functions` должны быть поля `name`, `is_aggregate`, `case_insensitive` и `alias_to`. Поддержка определяется фактическими запросами к каталогу и форматтеру, а не по строкам версий.

Генерируйте добавления, удаления и изменения проекций с `render_as_batch=False`. Встроенные определения в CREATE и снимки для понижения версии при удалении таблиц по-прежнему поддерживаются. Для физического пакетного пересоздания передайте полные метаданные `copy_from`, содержащие столбцы, движок и `clickhousedb_projections`. Автоматическое онлайн-пересоздание считывает каталог проекций и ещё до выполнения DDL отказывается обрабатывать таблицы с проекциями. Отключение сравнения не обходит эту защиту при выполнении.

См. полный [пошаговый пример для Alembic](https://github.com/ClickHouse/clickhouse-connect/blob/main/clickhouse_connect/cc_sqlalchemy/alembic/WORKED_EXAMPLE.md). Пользователям, переходящим с `clickhouse-sqlalchemy`, также следует ознакомиться с [руководством по миграции](https://github.com/ClickHouse/clickhouse-connect/blob/main/clickhouse_connect/cc_sqlalchemy/MIGRATING_FROM_CLICKHOUSE_SQLALCHEMY.md).

### Классификация сгенерированных операций перед рендерингом {#classify-generated-operations-before-rendering}

Все 21 класс операций миграции ClickHouse публично доступны из
`clickhouse_connect.cc_sqlalchemy.alembic` и его модуля `operations`. Используйте
`isinstance`, чтобы проверять их в `process_revision_directives`, или регистрируйте их
через `Rewriter.rewrites` в Alembic. Старые имена с символом подчёркивания остаются псевдонимами
тех же классов, поэтому существующие регистрации и импорты продолжат работать.

Публичные поля для инспекции соответствуют аргументам конструктора. Операции над таблицами предоставляют
`table_name`, `schema` и `clickhouse_settings`. Операции над отдельным индексом предоставляют
`name`. Операции добавления дополнительно предоставляют `expression`, `type_`, `granularity`, `if_not_exists`,
`first` и `after_index`. Операции добавления проекций вместо полей выражения, типа и гранулярности индекса предоставляют `select` и
`after_projection`. Операции удаления
предоставляют `if_exists`, а для отдельных индексов или проекций — также `existing_index` или
`existing_projection`, если доступно предыдущее определение. Операции материализации
предоставляют `if_exists` и `partition`. Сгруппированные операции добавления хранят `indexes` или
`projections` в виде кортежей `ClickHouseIndex` или `ClickHouseProjection`. Сгруппированные
операции удаления хранят `names` в виде кортежа. Проверяйте каждый элемент сгруппированной операции.

`ModifyClickHouseTableSettingsOp` предоставляет `settings` и необязательное поле
`existing_settings`. `ResetClickHouseTableSettingsOp` предоставляет кортеж `names`.
Эти настройки таблицы отличаются от сопоставления `clickhouse_settings` уровня запроса.
Операции создания представлений и функций предоставляют `name`, `select` или `expression`,
`if_not_exists` и `or_replace`. Представления также предоставляют `schema`. Операция создания
материализованного представления предоставляет `name`, `schema`, `to_table`, `to_schema`, `select` и
`if_not_exists`. Операция создания словаря предоставляет `name`, `schema`, кортеж `columns`,
`primary_key`, `source`, `layout`, `lifetime`, `comment`, `if_not_exists` и
`clickhouse_settings`. Операции удаления представлений, функций, материализованных представлений и словарей предоставляют
`name` и `if_exists`, а также `schema` и `clickhouse_settings`, если конструктор их принимает. Операция перезагрузки словаря предоставляет `name` и `schema`. SQL-фрагменты
остаются строками. Сопоставления сохраняют переданные значения. Обратные операции могут
требовать предыдущих определений или выбрасывать `NotImplementedError`. Обратимое определение
не восстанавливает материализованные данные.

Этот пример — политика уровня приложения, а не гарантия безопасности со стороны драйвера. Он разрешает
только явно выбранную форму индекса или настройку таблицы, отправляет замены и
неизвестные операции на проверку и отклоняет отдельные удаления индексов, отдельные
удаления проекций и деструктивные встроенные операции. Адаптируйте эти правила под своё развертывание. Даже
операции создания требуют проверки полей: `or_replace=True` для представления может уничтожить данные
конфликтующей таблицы, а необработанные SQL-тела и источники словарей нужно проверять вручную.

```python
import logging

from alembic.operations import ops
from clickhouse_connect.cc_sqlalchemy import alembic as ch_alembic


def leaves(operation):
    if isinstance(operation, ops.OpContainer):
        for child in operation.ops:
            yield from leaves(child)
    else:
        yield operation


def object_key(operation):
    if isinstance(operation, (ch_alembic.AddClickHouseIndexOp,
                              ch_alembic.DropClickHouseIndexOp)):
        kind = "index"
    elif isinstance(operation, (ch_alembic.AddClickHouseProjectionOp,
                                ch_alembic.DropClickHouseProjectionOp)):
        kind = "projection"
    else:
        return None
    return kind, operation.schema, operation.table_name, operation.name


def classify_tree(tree, direction):
    operations = list(leaves(tree))
    adds = {object_key(op) for op in operations if isinstance(
        op, (ch_alembic.AddClickHouseIndexOp, ch_alembic.AddClickHouseProjectionOp))}
    drops = {object_key(op) for op in operations if isinstance(
        op, (ch_alembic.DropClickHouseIndexOp, ch_alembic.DropClickHouseProjectionOp))}
    replacements = adds & drops
    for operation in operations:
        verdict, reason = "review", "operation needs explicit review"
        if isinstance(operation, (ops.DropTableOp, ops.DropColumnOp, ops.ExecuteSQLOp)):
            verdict, reason = "rejected", "destructive change or opaque SQL"
        elif object_key(operation) in replacements:
            reason = "replacement can discard existing materialization"
        elif isinstance(operation, (ch_alembic.DropClickHouseIndexOp,
                                    ch_alembic.DropClickHouseProjectionOp,
                                    ch_alembic.DropClickHouseIndexesOp,
                                    ch_alembic.DropClickHouseProjectionsOp)):
            verdict, reason = "rejected", "removal requires a separate migration"
        elif direction == "upgrade":
            if isinstance(operation, ch_alembic.AddClickHouseIndexOp):
                if (operation.type_ == "minmax" and operation.expression == "value"
                        and operation.granularity == 1 and not operation.first
                        and operation.after_index is None and not operation.clickhouse_settings):
                    verdict, reason = "allowed", "approved index definition"
            elif isinstance(operation, ch_alembic.ModifyClickHouseTableSettingsOp):
                if (dict(operation.settings) == {"max_bytes_to_merge_at_max_space_in_pool": 107374182400}
                        and not operation.clickhouse_settings):
                    verdict, reason = "allowed", "approved table setting value"
        yield direction, operation, verdict, reason


def review_revision(context, revision, directives):
    # Scope: a single-engine env.py. clickhouse_writer uses singular roots.
    for script in directives:
        if len(script.upgrade_ops_list) != 1 or len(script.downgrade_ops_list) != 1:
            raise ValueError("This policy hook supports one operation stream only")
        findings = [
            *classify_tree(script.upgrade_ops_list[0], "upgrade"),
            *classify_tree(script.downgrade_ops_list[0], "downgrade"),
        ]
        for direction, op, verdict, reason in findings:
            logging.getLogger("alembic.policy").info(
                "%s: %s: %s: %s", direction, type(op).__name__, verdict, reason)
        blocked = [f"{direction}: {type(op).__name__}: {verdict}: {reason}"
                   for direction, op, verdict, reason in findings
                   if direction == "upgrade" and verdict != "allowed"]
        if blocked:
            raise ValueError("Migration requires review:\n" + "\n".join(blocked))
    ch_alembic.clickhouse_writer(context, revision, directives)
```

Передайте `process_revision_directives=review_revision` в `context.configure()`
вместо `clickhouse_writer`. Хук записывает в журнал результаты проверки для обоих направлений и не допускает генерацию ревизии, если
найдены проблемы в обновлении. Проблемы, найденные для понижения версии, требуют отдельной проверки перед
понижением версии, но не блокируют запись одобренного обновления. Хук обходит вложенные контейнеры и сопоставляет замены по
виду, схеме, таблице и имени независимо от того, следуют ли они друг за другом. Сгруппированные добавления и все
нераспознанные операции по умолчанию отправляются на проверку. Этот рецепт поддерживает один движок и
один поток операций для каждого направления. Использование списков корневых элементов в классификаторе не
делает `clickhouse_writer` хуком для нескольких движков. Пустое сгенерированное дерево означает лишь то,
что включенные и поддерживаемые сравнения не обнаружили изменений. Для представлений, функций,
словарей и других объектов с неподдерживаемыми сравнениями по-прежнему нужны явные миграции.

## Область применения и ограничения {#scope-and-limitations}

* ClickHouse не поддерживает традиционные транзакции через этот HTTP-диалект. `engine.begin()` и `Session.commit()` организуют работу на стороне Python, но коммит и rollback на сервере ничего не меняют.
* `UPDATE`, двухфазные транзакции, последовательности, `RETURNING` и расширенные уровни изоляции в этом диалекте не реализованы. При необходимости используйте явный ClickHouse SQL для серверных мутаций.
* `Column(..., primary_key=True)` задает identity объекта SQLAlchemy. Это не создает ограничение уникальности на стороне сервера. Задавайте сортировку и необязательные выражения первичного ключа через движок таблицы.
* Метаданные для традиционных внешних ключей, ограничений уникальности и стандартных индексов недоступны, поскольку ClickHouse не применяет такие ограничения.
* Управление relationship в ORM, обновления unit of work, каскады, а также немедленная или отложенная загрузка relationship не входят в поддерживаемую область ORM.
