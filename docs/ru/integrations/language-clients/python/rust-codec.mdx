ClickHouse Connect может декодировать результаты запросов и кодировать вставки с помощью скомпилированного кодека на Rust вместо реализации на Python и Cython, используемой по умолчанию. Кодек на Rust применяется только к управляемому клиентом трафику `FORMAT Native`: это `query`, `query_np`, `query_df`, их варианты с потоковой передачей блоков и строк, а также вставки, включая `insert_df`. Методы Arrow используют `FORMAT Arrow` и не затрагиваются, равно как и raw-запросы, raw-вставки и форматы, отличные от Native.

Кодек является экспериментальным и включается явно. По умолчанию используется кодек на Python.

## Установка {#installation}

Скомпилированный кодек поставляется в виде отдельного wheel-пакета `clickhouse-connect-core`, содержащего модуль расширения `_ch_core`. Установите кодек вместе с интеграциями, которые использует ваше приложение:

```bash
pip install "clickhouse-connect[rust]"         # Python rows and Native inserts
pip install "clickhouse-connect[rust,numpy]"   # NumPy results
pip install "clickhouse-connect[rust,pandas]"  # Pandas results and inserts
```

Основные wheel-пакеты публикуются для CPython версий с 3.10 по 3.15, а также для CPython 3.14t и 3.15t со свободной многопоточностью (free-threaded) на Linux, macOS и Windows. В Python со свободной многопоточностью импорт основного расширения не приводит к повторному включению GIL.

Для обычного вывода в NumPy и Pandas средствами Rust не требуется PyArrow или какой-либо другой пакет Arrow. Это относится к `query_np`, `query_df`, их потоковым вариантам, а также к `query(..., use_numpy=True)`. Для запросов NumPy пакет Pandas не нужен. Чтобы использовать асинхронный клиент, добавьте дополнительный модуль `async`.

PyArrow по-прежнему необходим для методов Arrow и хранилища Pandas на базе Arrow. Чтобы использовать эти возможности, установите дополнительный модуль `arrow`:

```bash
pip install "clickhouse-connect[rust,pandas,arrow]"
```

Вывод строк в расширенном режиме Pandas определяется параметром Pandas `mode.string_storage`. Если установлен PyArrow, строки преобразуются существующим механизмом Arrow с полной проверкой UTF-8 для любого бэкенда хранилища. Без PyArrow драйвер использует объектное преобразование на Rust, а хранилище Pandas по умолчанию использует строки Python. Явный запрос хранилища строк Arrow без установленного PyArrow вызывает ошибку зависимости. Некорректные данные UTF-8, как и прежде, отображаются в шестнадцатеричном виде при любом бэкенде хранилища.

Кодек, его упаковка и набор зависимостей являются экспериментальными. Прямое преобразование буферов поддерживает столбцы с типами non-nullable 8–64-битных целых чисел, Float32/64, Boolean, BFloat16 и Interval. Скалярные столбцы Date, Date32, DateTime, DateTime64, Time и Time64, в том числе со значениями Nullable, также используют прямые буферы — как и Nullable BFloat16, а также вывод целых чисел, чисел с плавающей точкой и Interval с типом Nullable в расширенном режиме Pandas. Для BFloat16 сохраняются вывод в float32 и прежняя политика обработки отсутствующих значений Pandas Float32. Значения Interval по-прежнему представляются знаковыми счётчиками в объявленной единице измерения. При преобразовании временных типов сохраняются объявленные единицы и прежние правила обработки часовых поясов. Nullable-псевдонимы SimpleAggregateFunction для Time64 возвращают корректные длительности и NaT для значений NULL.

Массивы Time/Time64, включая вложенные массивы и листовые элементы Nullable, а также LowCardinality(Time), в том числе со значениями Nullable, также используют прямые буферы. Вложенность, единицы длительности и представление NULL для них не меняются. LowCardinality(Time64) по-прежнему не поддерживается ядром на Rust.

Для столбцов дат и даты и времени с типом Nullable, обрабатываемых напрямую, а также их одиночных обёрток SimpleAggregateFunction функции `query_df` и `query_df_stream` возвращают те же dtype, что и кодек на Python. В расширенном режиме объявленные часовые пояса сохраняются и для блоков, состоящих только из NULL. В расширенном режиме Date и Date32 используют секунды, а DateTime и DateTime64 сохраняют объявленную точность, включая все девять знаков дробной части для DateTime64(9). В нерасширенном режиме вывод типов соответствует поведению конкретной версии Pandas, включая объектный dtype для блоков, состоящих только из NULL. Если из-за именованного часового пояса наносекундное значение выходит за пределы диапазона Pandas, для этого столбца сохраняются прежнее объектное преобразование и прежнее поведение при выходе за диапазон. Вложенные обёртки SimpleAggregateFunction сохраняют прежнее поведение dtype.

Для этих столбцов объектные поля в `query_np` и `query_np_stream` содержат ячейки `numpy.datetime64` вместо ячеек Python `date` или `datetime`, а для SQL NULL — `None`. Date и Date32 используют дни в качестве единицы измерения. DateTime и DateTime64 сохраняют объявленную точность. Значения с именованным часовым поясом представляются тиками UTC без метаданных часового пояса — так же, как в кодеке на Python. Это позволяет сохранять наносекунды без Pandas. Если вам нужны временные метки с учётом часового пояса, используйте `query_df`. Значения Date32 с годом 0000 также корректно обрабатываются в выводе NumPy и Pandas. Столбцы LowCardinality, а также даты и значения даты и времени с типом Nullable, вложенные в контейнеры, сохраняют прежние пути преобразования.

Запросы NumPy и Pandas для скалярных DateTime64 с точностью, отличной от 0, 3, 6 и 9, завершаются ошибкой `ProgrammingError` — в том числе для столбцов с типом Nullable и псевдонимов SimpleAggregateFunction.

Если выбран Rust codec, а скомпилированный модуль не установлен, при создании клиента возникает ошибка `NotSupportedError` с указанием этой команды установки.

## Включение кодека {#enabling-the-codec}

Выберите кодек с помощью клиентской опции `native_codec`:

```python
import clickhouse_connect

client = clickhouse_connect.get_client(host="localhost", native_codec="rust")
```

Допустимые значения:

| Значение      | Поведение                                                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `python`      | По умолчанию. Существующий кодек на Python и Cython.                                                                                     |
| `rust`        | Предпочитать кодек на Rust. Запросы с неподдерживаемыми параметрами и вставки с неподдерживаемыми типами направляются в кодек на Python. |
| `rust_strict` | Требовать кодек на Rust. Неподдерживаемые параметры и типы приводят к исключению, а не к перенаправлению.                                |

Значение по умолчанию также можно задать через общую настройку `native_codec` или переменную окружения `CLICKHOUSE_CONNECT_NATIVE_CODEC`. Наивысший приоритет имеет именованный аргумент клиента, затем общая настройка и, наконец, переменная окружения.

Для клиентов с `interface="chdb"` этот параметр игнорируется — они всегда используют кодек на Python.

## Когда использовать кодек на Rust {#when-to-use-the-rust-codec}

Кодек на Rust наиболее полезен для больших результатов в виде DataFrame с текстовыми, контейнерными и составными типами, такими как `String`, `LowCardinality`, `Map`, `Array`, `JSON`, `Decimal` и `UUID`. Он также может ускорить работу с большими потоками блоков строк и столбцов, параллельными рабочими нагрузками из запросов и массовыми вставками.

Для небольших результатов и запросов, ограниченных пропускной способностью сети, разница может быть незначительной. Простые числовые результаты уже обрабатываются эффективными пакетными путями в кодеке на Python, поэтому выигрыш для них тоже будет меньше.

Прямые буферы позволяют обойтись без промежуточных массивов Arrow для поддерживаемых типов. При итоговой сборке результата NumPy и Pandas по-прежнему возможны выделение памяти и копирование данных, поэтому не каждый результат запроса становится zero-copy.

Без PyArrow преобразование строк в Rust создаёт строковые объекты Python из каждого декодированного блока. При размерах блоков по умолчанию пиковое потребление памяти для больших результатов типа String сопоставимо с кодеком на Python. Очень большие блоки, например один блок с миллионом строк, удерживают в памяти весь декодированный блок, пока создаются его строки, и могут требовать больше пиковой памяти, чем кодек на Python. Для больших результатов Pandas `StringDtype` установите дополнительный модуль `arrow` и используйте хранение строк в Arrow. Pandas 3 по умолчанию выбирает хранение в Arrow, если установлен PyArrow. Для Pandas 2 требуется `pd.options.mode.string_storage = "pyarrow"`.

Буферизованные вызовы `query()` для очень широких или полностью числовых результатов сейчас могут работать медленнее и давать более высокое пиковое потребление памяти при использовании кодека на Rust. Для таких рабочих нагрузок предпочтительнее `query_df`, `query_row_block_stream` или `query_column_block_stream`. Для NumPy и Pandas снизить пиковое потребление памяти также помогают `query_np_stream` и `query_df_stream`. Обрабатывайте и освобождайте каждый блок, а не накапливайте весь поток. Потребление памяти по-прежнему зависит от размера каждого блока, поэтому стриминг одного большого блока не даёт такого же преимущества.

Прежде чем переходить на этот кодек, протестируйте его на собственной рабочей нагрузке. При замерах используйте `native_codec="rust_strict"`, чтобы неподдерживаемая опция или отсутствующая зависимость приводили к исключению, а не к незаметному перенаправлению запроса в Python.

## Правила перехода на резервный вариант {#fallback-rules}

Решение о переходе на резервный вариант принимается до того, как будут прочитаны или отправлены какие-либо байты, поэтому переключение кодека посреди потока невозможно. Для запросов выбор делается до чтения тела ответа. Для вставок кодировщик на Rust выбирается только в том случае, если поддерживаются все типы столбцов; иначе вся вставка выполняется на кодеке на Python.

Когда активен режим `naive_datetime_insert="server"`, режим `rust` направляет вставку, содержащую хотя бы один столбец типа `DateTime` или `DateTime64`, на кодек на Python, чтобы применялся объявленный часовой пояс столбца или часовой пояс сервера. `rust_strict` отклоняет такое сочетание. Режим по умолчанию `naive_datetime_insert="local"` по-прежнему использует кодировщик на Rust.

Python-запросы, возвращающие строки и столбцы (`query`, `query_row_block_stream`, `query_column_block_stream` и `query_rows_stream`), в которых столбцы `DateTime` или `DateTime64` без часового пояса отображаются в получаемом из окружения часовом поясе, отличном от UTC (часовом поясе сервера или локальном часовом поясе), используют Rust codec, если установленное ядро это поддерживает. Значения при этом совпадают с результатами кодека на Python. Локальный часовой пояс подходит только в том случае, если он разрешается в имя IANA, то есть задана переменная `TZ` или установлен `tzlocal`. В противном случае он представляет собой фиксированное смещение без имени IANA, и запрос направляется на кодек на Python. Запросы NumPy и Pandas (`query_np`, `query_df` и их потоковые варианты) с получаемым из окружения часовым поясом, отличным от UTC, а также запросы, в которых задан `query_tz`, `column_tzs` или отличающийся от значения по умолчанию `tz_mode` либо которые получают заголовок с часовым поясом сервера, по-прежнему направляются на кодек на Python. `rust_strict` отклоняет такие случаи.

Внутренние запросы драйвера к метаданным, включая команды reflection диалекта SQLAlchemy, всегда используют кодек на Python — незаметно для пользователя и во всех режимах.

Некорректные полезные нагрузки Native, обнаруженные Rust codec, приводят к ошибке `DataError`.

## Versioning {#versioning}

`clickhouse-connect-core` версионируется независимо от `clickhouse-connect`. Дополнительный модуль `rust` требует `clickhouse-connect-core>=0.2.1,<0.3`. При выборе Rust codec драйвер проверяет как версию binding API, так и поддержку буфера столбцов. В опубликованном wheel-пакете core 0.2.0 поддержка буфера столбцов отсутствует. Если установленный wheel-пакет несовместим, при создании клиента как для `rust`, так и для `rust_strict` возникает `NotSupportedError` со следующей командой обновления:

```bash
pip install --upgrade clickhouse-connect-core
```

Исправления и повышение производительности скомпилированного кодека выходят в составе релизов `clickhouse-connect-core`, и их можно получить, обновив wheel-пакет core до совместимой версии. Изменения в интеграции драйвера с Rust требуют обновления `clickhouse-connect`.

Для поддержки Rust в построчных и постолбцовых запросах Python при часовом поясе, получаемом из окружения и отличном от UTC, требуются `clickhouse-connect>=1.11.0` и `clickhouse-connect-core>=0.2.3`. Чтобы включить её, обновите оба пакета. Более старые совместимые версии core сохраняют прежнее поведение: в режиме `rust` выполняется переход на резервный вариант на Python, а в режиме `rust_strict` запрос отклоняется.

## Известные различия в поведении {#known-behavior-differences}

Rust codec нацелен на побитовое совпадение с кодеком на Python вплоть до каждой ячейки. Ниже перечислены известные различия.

* Результаты `query_np` и `query_df` для столбцов `Variant` содержат обычные объекты Python, а не скалярные значения numpy. Сами значения совпадают, различаются типы ячеек.
* Значения `Dynamic`, содержащие `Time64`, материализуются как `datetime.timedelta` в результатах `query_np` и `query_df` Rust codec. При scale 0, 3, 6 и 9 значения совпадают с ячейками `numpy.timedelta64` кодека на Python, но типы ячеек различаются. При других значениях scale Rust codec возвращает `datetime.timedelta`, тогда как кодек на Python выбрасывает `ProgrammingError`, поскольку в NumPy нет подходящей единицы измерения. Метаданные членов Dynamic после декодирования на Rust драйверу не передаются, поэтому используйте `native_codec="python"`, если нужны типы ячеек NumPy или проверка неподдерживаемых значений scale.
* Для значений, хранящихся в общих данных JSON, результаты `query_np` и `query_df` кодека на Python содержат скалярные значения numpy, а `max_str_len` обрезает имена путей и строковые значения. Rust codec возвращает обычные объекты Python и не применяет `max_str_len` к общим данным.
* Альтернатива `LowCardinality` внутри контейнера, который материализуется поячеечно, например `Array(Variant(...))`, даёт равные по значению ячейки, которые не разделяют идентичность объекта на слот словаря, характерную для кодека на Python.
* `rust_strict` отклоняет параметры запроса, не реализованные в Rust-пути, например пользовательские `query_formats` для отдельного запроса, вместо того чтобы незаметно менять поведение.
* Ошибки преобразования и проверки при вставке в Rust могут приводить к `DataError` там, где кодек на Python выбрасывает `ValueError`, при этом текст сообщения может отличаться. Например: недопустимые значения `Time` и `Time64`, IPv6-адреса, размерности QBit, длины `FixedString`, строки `Float64`, а также попытки вставить элементы в столбец `Tuple()`.
* Кодировщик на Rust отклоняет `b""` для `FixedString(N)` и числовые строки вида `"2"` для целочисленных столбцов. Кодек на Python дополняет пустое значение `FixedString` нулями и приводит числовые строки к нужному типу.
* Rust codec декодирует некоторые значения общих вариантов `Dynamic` в соответствующие типы Python, тогда как кодек на Python оставляет значение в виде сырых байтов. Например, сохранённое значение `Decimal` из Rust вернётся как `decimal.Decimal`, а из Python — как двоичное значение.
* Для значений `Date` в общем хранилище `Dynamic` методы `query_np` и `query_df` возвращают ячейки `datetime.date` при использовании Rust codec и ячейки `numpy.datetime64` при использовании кодека на Python. Из `query` оба кодека возвращают `datetime.date`.
