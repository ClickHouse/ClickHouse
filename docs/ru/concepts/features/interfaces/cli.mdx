`clickhousectl` (псевдоним `chctl`) — официальный CLI для ClickHouse, от локальной разработки до ClickHouse Cloud. Он подходит как для работы вручную в терминале, так и для скриптов и агентов для программирования.

С помощью `clickhousectl` можно:

* Устанавливать локальные версии ClickHouse и переключаться между ними, запускать изолированные локальные серверы и выполнять SQL-запросы
* Локально запускать Postgres в Docker
* Создавать, настраивать и масштабировать сервисы ClickHouse Cloud, создавать их резервные копии и выполнять к ним запросы
* Создавать, отслеживать, настраивать и восстанавливать сервисы [ClickHouse Managed Postgres](/ru/products/managed-postgres/overview)
* Создавать ClickPipes и управлять ими для приёма данных из объектного хранилища, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB и BigQuery
* Управлять источниками, панелями мониторинга, оповещениями, вебхуками, сохранёнными поисками и ролями в сервисе [Управляемый ClickStack](/ru/clickstack/deployment/managed)
* Разрабатывать исполняемые UDF локально и развертывать их в ClickHouse Cloud
* Управлять участниками организации, приглашениями, ключами API и ролями
* Устанавливать официальные ClickHouse agent skills в агенты для программирования

На этой странице приведены типичные примеры. Исчерпывающую справку по каждой команде и флагу выводит `clickhousectl <command> --help`. Справка большинства команд завершается блоком `CONTEXT FOR AGENTS`; для команд Cloud в нём также перечислены разрешения ключа API, необходимые для их выполнения. Пошаговые инструкции по конкретным задачам доступны по ссылкам на руководства в каждом разделе. Обзор, ориентированный на Cloud, см. в разделе [ClickHouse CLI](/ru/products/cloud/features/cli).

## Установка {#installation}

`clickhousectl` работает в macOS и Linux на архитектурах ARM64 и x86&#95;64.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

Скрипт устанавливает `~/.local/bin/clickhousectl` и создаёт псевдоним `chctl`. Убедитесь, что каталог `~/.local/bin` добавлен в переменную `PATH`.

Его также можно установить с помощью менеджера пакетов:

| Инструмент                            | Команда                         |
| ------------------------------------- | ------------------------------- |
| npm                                   | `npm install -g clickhousectl`  |
| uv                                    | `uv tool install clickhousectl` |
| pipx                                  | `pipx install clickhousectl`    |
| pip                                   | `pip install clickhousectl`     |
| cargo-binstall                        | `cargo binstall clickhousectl`  |
| Cargo, из исходного кода (Rust 1.94+) | `cargo install clickhousectl`   |

Псевдоним `chctl` создают только установочный скрипт и npm. Чтобы обновить уже установленную версию, выполните `clickhousectl update` (см. [Самообновление](#self-update)).

## Требования {#requirements}

* Docker — только для локального Postgres
* Для команд Cloud — аккаунт [ClickHouse Cloud](https://clickhouse.com/cloud). Команды чтения работают с OAuth-аутентификацией через браузер (`cloud auth login`). Для создания или изменения ресурсов нужен [ключ API](/ru/products/cloud/features/admin-features/api/openapi). Подробнее см. в разделе [Аутентификация](#authentication).

## Локальные команды {#local}

Локальные команды выполняются в текущем каталоге. Каждый проект хранит данные своего сервера в `.clickhouse/`, а исполняемые файлы ClickHouse хранятся глобально в `~/.clickhouse/` и используются всеми проектами совместно. CLI не ищет родительские каталоги, поэтому запускайте локальные команды из корневого каталога проекта. Полное описание рабочего процесса приведено в [руководстве по локальной разработке](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md).

### Установка и выбор версий {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
```

| Селектор      | Значение                                                                                                                               |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `latest`      | Последняя сборка ClickHouse; наличие новой версии проверяется удалённо при каждой установке, использовании или запуске (рекомендуется) |
| `stable`      | Последний стабильный релиз                                                                                                             |
| `lts`         | Последний релиз с долгосрочной поддержкой                                                                                              |
| `26.8`        | Последний релиз, соответствующий указанной версии                                                                                      |
| `26.8.1.1760` | Точная версия                                                                                                                          |

`local use` при необходимости устанавливает версию, назначает её версией по умолчанию для последующих запусков сервера и создаёт на неё символическую ссылку `~/.local/bin/clickhouse`, чтобы `clickhouse client` и `clickhouse local` были доступны через `PATH`. Чтобы не создавать символическую ссылку, передайте `--no-global`. Если по этому пути уже находится обычный файл, он не изменяется.

`local remove` не удаляет версию по умолчанию, а также версию, которую использует запущенный сервер в каком-либо проекте. С флагом `--force` такие серверы останавливаются, а версия удаляется; при этом сбрасывается версия по умолчанию и удаляется символическая ссылка.

### Инициализация проекта {#initializing-project}

```bash
clickhousectl local init
```

Команда `init` необязательна. Она создаёт каталог `.clickhouse/` для данных среды выполнения (он добавляется в git-ignore), а также заготовки SQL-файлов, которые можно закоммитить: `clickhouse/` (`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`) и `postgres/` (`tables/`, `views/`, `functions/`, `queries/`, `seed/`). При повторном запуске создаётся только то, чего ещё нет.

### Запуск локальных серверов {#managing-servers}

```bash
clickhousectl local server start dev --version latest   # Background start; waits for readiness
clickhousectl local server start dev --no-wait          # Return after spawning
clickhousectl local server start dev --foreground       # Run in the foreground
clickhousectl local server start dev --http-port 8124 --tcp-port 9001
clickhousectl local server list                         # Servers in this project
clickhousectl local server list --global                # Servers across all projects
clickhousectl local server stop dev
clickhousectl local server stop-all                     # Stop all ClickHouse and Postgres servers in this project
clickhousectl local server remove dev                   # Permanently delete a stopped server's data
```

У каждого именованного сервера есть собственные данные в `.clickhouse/servers/<name>/data/`, и при остановке сервера они сохраняются до следующего запуска. Если имя не указано, первый сервер получает имя `default`; если `default` уже запущен, генерируется новое имя. По умолчанию используются порты HTTP 8123 и TCP 9000; если они заняты, назначаются свободные.

`--version` задаёт версию только для данного запуска, не меняя версию по умолчанию. Если запустить сервер без указания версии, когда версия по умолчанию не задана, будет установлена `latest`, но она не станет версией по умолчанию; чтобы сделать её таковой, сначала выполните `local use latest`.

### Выполнение SQL-запросов с помощью локального клиента {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` подключается к именованному серверу с помощью того же бинарного файла ClickHouse, которым этот сервер запущен (имя по умолчанию: `default`). Аргументы после `--` передаются в `clickhouse client` без изменений. Вывод и код выхода формирует `clickhouse client` — даже в режиме JSON, поэтому в скриптах задавайте формат вывода SQL явно.

### Пользовательская конфигурация сервера {#custom-config-files}

Поместите частичную конфигурацию в формате XML или YAML в каталог `~/.clickhouse/configs/` и укажите её имя при запуске сервера:

```bash
mkdir -p ~/.clickhouse/configs
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local server configs
clickhousectl local server stop dev
clickhousectl local server start dev --config analytics
```

Файл накладывается поверх встроенных значений по умолчанию, поэтому в нём достаточно указать только те настройки, которые вы меняете. Выбор не запоминается: при последующем запуске без `--config` оверлей удаляется. Управляемые пути к данным и порты всегда имеют приоритет над значениями из конфигурации.

### Запись сведений о подключении в файл dotenv {#dotenv}

```bash
clickhousectl local server dotenv dev                                     # Writes .env
clickhousectl local server dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` считывает фактические порты запущенного сервера и записывает `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT` и `CLICKHOUSE_HTTP_PORT`, а также пользователя, пароль и базу данных, если они переданы. Остальные строки в существующем файле сохраняются. Загружайте файл с помощью dotenv-загрузчика вашего приложения; никогда не передавайте выведенный на экран предварительный результат в `eval`.

### Локальный Postgres {#local-postgres}

Локальный Postgres работает в Docker, поэтому Docker должен быть запущен. Поддерживаются Postgres 17 и 18, в том числе теги образов вида `18-alpine`; новые инстансы по умолчанию создаются с версией 18.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres stop app
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

Инстанс определяется своим именем и мажорной версией. При возобновлении остановленного инстанса используются его прежние порт, пользователь, пароль и база данных, поэтому флаги, заданные при создании, на возобновление не влияют. Если пароль не указан явно, генерируется случайный. Файл `.env.local` содержит пароль, поэтому не добавляйте его в систему контроля версий.

### Локальные UDF {#local-udfs}

`local udf` развертывает [исполняемые UDF](/ru/reference/functions/regular-functions/udf#executable-user-defined-functions) из `clickhouse/udfs/<name>/` на локальном сервере. `cloud udf` загружает тот же каталог в Cloud (см. [UDF в Cloud](#cloud-udfs)).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local server start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

Все команды, кроме `init`, принимают параметр `--server <name>` (по умолчанию — `default`). Команда `deploy` проверяет корректность `udf.json` так же, как это делает Cloud. На работающем сервере она перезагружает функции и проверяет, что функция загружена. Локальное развертывание со средой выполнения `native` поддерживается только на хостах Linux с архитектурой amd64 или arm64. См. [руководство по пользовательским функциям](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

## Аутентификация {#authentication}

Команды Cloud используют один из двух типов учётных данных:

| Учётные данные | Возможности                                                                                                                   | Хранилище                                                                   |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Browser OAuth  | Ваша пользовательская идентичность: операции Cloud и SQL-запросы только на чтение во всех организациях, в которых вы состоите | `~/.clickhouse/tokens.json` — глобальное хранилище, общее для всех проектов |
| Ключ API       | Действует в пределах одной организации; права на чтение и запись определяются ролями ключа                                    | `.clickhouse/credentials.json` (при сохранении), локально для проекта       |

Если у вас еще нет аккаунта ClickHouse Cloud, `clickhousectl cloud auth signup` откроет страницу регистрации в вашем браузере.

### Вход через OAuth {#oauth-login}

```bash
clickhousectl cloud auth login
```

Это откроет браузер для прохождения OAuth Device Flow. Токены сохраняются глобально в `~/.clickhouse/tokens.json` и обновляются автоматически.

<Note>
  Доступ через OAuth предоставляется **только для чтения**. Чтобы создавать или изменять ресурсы, войдите с помощью [ключа API](#api-key).
</Note>

### Ключ API {#api-key}

[Создайте ключ API](/ru/products/cloud/features/admin-features/api/openapi) с ролями, которые требуются вашим командам, и сохраните его. При интерактивном вводе секрет не попадает в историю командной оболочки:

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

При входе ключ проверяется, и выводится идентичность, которой он принадлежит. Если API отклоняет ключ, он не сохраняется, а команда завершается с кодом 4. Если API недоступен, ключ сохраняется с предупреждением.

В CI и других сценариях автоматизации не сохраняйте ключ, а передавайте его через менеджер секретов:

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

При разработке CLI также считывает эти переменные из файла `.env` в текущем каталоге. Не добавляйте `.env` в систему контроля версий.

### Проверка и очистка учётных данных {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` работает с учётными данными любого типа и завершается с кодом 4, если учётные данные отклонены. `status` может завершиться с кодом 0, даже если ни одни из учётных данных не подходят, поэтому для проверки доступа используйте `whoami`. Выход из системы не сбрасывает переменные окружения и не изменяет файл `.env`.

### Приоритет учётных данных {#credential-precedence}

Используется первый из доступных источников:

1. Флаги `--api-key` и `--api-secret`
2. `.clickhouse/credentials.json`
3. Экспортированные переменные окружения
4. Переменные из файла `.env` в текущем каталоге
5. Глобальные OAuth-токены

Добавьте флаг `--debug` к любой команде `cloud`, чтобы вывести в stderr выбранный источник учётных данных и URL API:

```bash
clickhousectl cloud service list --debug
```

### Выбор организации {#organizations}

Команды уровня организации выбирают её автоматически, только если ваши учётные данные дают доступ ровно к одной организации. В противном случае укажите `--org-id` или `--org-name` с точным названием организации:

```bash
clickhousectl cloud org list
clickhousectl cloud service list --org-id <org-id>
clickhousectl cloud service list --org-name "My Org"
```

Большинство команд для работы с ресурсами принимают позиционный аргумент ID или точное значение `--name`. О разрешениях, ключах с ограниченными правами и очистке данных при выходе из системы см. раздел [«Аутентификация и доступ»](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md).

## Cloud {#cloud}

Команды Cloud обращаются к [ClickHouse Cloud API](/ru/products/cloud/features/admin-features/api/api-overview). Запросы на создание и обновление завершаются сразу после того, как API их принимает, поэтому периодически опрашивайте `get`, пока ресурс не перейдёт в нужное состояние.

### Сервисы {#services}

```bash
clickhousectl cloud service create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud service list
clickhousectl cloud service get <service-id>
clickhousectl cloud service start <service-id>
clickhousectl cloud service stop <service-id>
clickhousectl cloud service wake <service-id>             # Wake an idle service
clickhousectl cloud service reset-password <service-id>
clickhousectl cloud service delete <service-id>           # Must be stopped; --force stops it first
```

Сохраните начальный пароль, который отображается при создании: он выводится только один раз. Команда создания завершается раньше, чем заканчивается подготовка, поэтому повторно выполняйте `get`, пока состояние не станет `running`. **Если не указать `--ip-allow`, доступ будет разрешён со всех IP-адресов (`0.0.0.0/0`).** Записи задаются в формате `IP_OR_CIDR=DESCRIPTION`. Чтобы восстановить резервную копию в новый сервис, используйте `--backup-id`, а чтобы разместить сервис в BYOC infrastructure — `--byoc-id`.

Обновление, масштабирование и настройка сервиса:

```bash
clickhousectl cloud service update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud service profile list --region us-east-1
clickhousectl cloud service scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud service scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud service settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud service upgrade-window set <service-id> --weekday 0 --start-hour 6
```

Объём памяти на реплику должен быть кратен 4 ГБ и составлять не более 120 ГБ для бесплатных и 356 ГБ для платных сервисов; допускается до 50 реплик. Ограничения на уровне организации и хранилища могут снижать эти значения. Для горизонтального автомасштабирования в организации должна быть включена соответствующая возможность. Команда `update` изменяет только переданные флаги.

Другие группы команд сервиса: `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (бета), `snapshot` (бета), `private-endpoint`, `backup-config` и `prometheus`. Подробнее см. в руководстве [Создание сервиса ClickHouse Cloud и работа с ним](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md).

### API запросов {#query-api}

`cloud service query` выполняет один оператор SQL по HTTP — без локального исполняемого файла `clickhouse` и без пароля сервиса:

```bash
clickhousectl cloud service query <service-id> --query "SELECT version()"
clickhousectl cloud service query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud service query <service-id>
```

* **OAuth** выполняет запрос от вашего имени с доступом к SQL только для чтения. К сервису ничего не привязывается.
* **Ключ API:** при первом вызове clickhousectl добавляет ваш ключ API к конечной точке API запросов сервиса и при необходимости создаёт эту конечную точку с ролями `sql_console_admin`. Существующие роли, источники (origins) и другие привязки ключей сохраняются, новый ключ не создаётся. Изменяя конечную точку, CLI выводит в stderr сообщение `Binding the authenticated API key to the Query API endpoint for service '<name>'...`. Чтобы в этом случае команда завершалась с ошибкой, передайте `--no-auto-enable`.

Ключ для конкретного сервиса, сохранённый более ранней версией CLI, по-прежнему имеет приоритет для этого сервиса. Если API его отклоняет, замените его явно командой `cloud service repair-query-key <service-id>`.

API запросов принимает один оператор на запрос. Примерно через 30 секунд ожидание может прерваться по тайм-ауту, при этом SQL продолжит выполняться, поэтому перед повторной попыткой записи проверьте результат. Для скриптов из нескольких операторов, пакетных загрузок и длительных запросов используйте `clickhouse client`. Список разрешённых IP-адресов сервиса ограничивает прямые подключения, но не проксируемый маршрут API запросов. Запрос к бездействующему сервису пробуждает его; остановленный сервис необходимо запустить командой `cloud service start`.

Управление конечной точкой API запросов сервиса, именованными конечными точками SQL и сохранёнными запросами:

```bash
clickhousectl cloud service query-endpoint get <service-id>
clickhousectl cloud service query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` заменяет роли всех ключей, привязанных к конечной точке. См. [Поведение SQL и API запросов](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md).

### Managed Postgres {#postgres-services}

`cloud postgres` управляет [ClickHouse Managed Postgres](/ru/products/managed-postgres/overview). Эти команды находятся в стадии бета, а поддержка GCP доступна в рамках закрытой предварительной версии.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

Для AWS доступны размеры `m6gd.large`, `c6gd.xlarge` и `r6gd.xlarge`. Для GCP укажите `--provider gcp`, регион GCP и размер, например `c4-standard-lssd-4`.

Сохраните пароль и строку подключения из вывода `create`. Последующие ответы `get` не содержат учётных данных, а получить новые можно только с помощью `reset-password`. Подключайтесь через `psql` с параметром `sslmode=verify-full` и файлом CA.

**Если при создании не указать флаги доступа, к Postgres (5432) и PgBouncer (6432) будет разрешён доступ со всех IPv4- и IPv6-адресов.** Передавайте по одному `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` на каждое правило или `--block-public-access`, чтобы не задавать ни одного правила. Если указано хотя бы одно правило, действуют только явно перечисленные правила.

Мониторинг и восстановление:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` поддерживает только OAuth, поэтому команда завершается ошибкой, пока активен источник ключа API с более высоким приоритетом. Для мониторинга предназначены `metrics`, `slow-queries` и `prometheus`. `restore` копирует текущие правила доступа IPv4 исходного сервиса в восстановленный сервис, если не указаны `--ip-allow` или `--block-public-access`. Операции восстановления и создания реплик возвращают результат без пароля. `promote` и `switchover` завершаются сразу после принятия запроса; после выполнения promote периодически опрашивайте `postgres get --json`, пока реплика не вернёт `isPrimary: true`. См. [руководство по Managed Postgres](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md).

### ClickPipes {#clickpipes}

`cloud clickpipe` выполняет приём данных из объектного хранилища, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB и BigQuery. Для создания ClickPipe и обнаружения схемы требуются ключ API и работающий целевой сервис. Для каждого источника предусмотрена отдельная подкоманда `clickpipe create <source>`; чтобы получить список её флагов, запустите её с `--help`.

Загрузка файлов из S3 с использованием роли IAM. Сначала выполните обнаружение схемы, затем выберите столбцы:

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN"
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --column 'event_id:Int64' --column 'event_type:String'
```

Реплицируйте Postgres с помощью CDC (фиксации изменений данных). По умолчанию TLS-соединение проверяется; если источником служит Managed Postgres, экспортируйте его сертификат CA и передайте его:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud service query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` создаёт таблицы `ReplacingMergeTree`, поэтому текущее состояние следует читать с `FINAL WHERE _peerdb_is_deleted = 0`. Для пайпа Kafka порядок действий тот же: выполните `clickpipe schema-discover kafka` с теми же флагами источника, а затем передайте столбцы:

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

По умолчанию пайпы BigQuery создают снимок. Для CDC (фиксации изменений данных) передайте `--replication-mode cdc`, `--replication-method`, а также в `--table-mapping-json` укажите для каждой таблицы столбец водяной метки или функцию событий; расписание синхронизации задаётся с помощью `--sync-cron` или `--sync-interval-seconds`. Управление существующими пайпами:

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

Перед выполнением `update` CDC-пайпы должны находиться в состоянии `Paused`: остановите пайп, периодически вызывайте `get`, пока пайп не перейдёт в состояние `Paused`, а затем обновите его. Сервис может сам возобновить пайп в ходе обновления, поэтому выполняйте `start`, только если `get` по-прежнему показывает `Paused`. Параметр `--start-paused` доступен для объектного хранилища, Kafka, Kinesis и Pub/Sub. Прочие группы команд: `cdc-scaling`, `context get` (готовность GCP workload identity и субъект) и `reverse-private-endpoint`. Подробнее см. [руководство по ClickPipes](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) и [справочник по конфигурации ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md).

### ClickStack {#clickstack}

`cloud clickstack` управляет источниками, панелями мониторинга, оповещениями, вебхуками, сохранёнными поисками и ролями в существующем сервисе [Управляемый ClickStack](/ru/clickstack/deployment/managed). Ресурсы описываются в JSON‑файлах (`--file` или `-` для stdin). Для операций чтения поддерживается OAuth, а для операций записи требуется ключ API.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**Каждое обновление ClickStack полностью перезаписывает ресурс.** Сохраните текущее состояние с помощью `get --json` и передавайте полное определение, а не только изменённые поля. Подробнее см. [руководство по ClickStack](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md).

### UDF в Cloud {#cloud-udfs}

`cloud udf` управляет исполняемыми UDF уровня организации, их версиями и привязками к сервисам. `deploy` загружает каталог, протестированный с помощью `local udf`, дожидается завершения сборки, подключает эту версию и ждёт, пока она не будет развернута:

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud service query <service-id> --query "SELECT my_udf(1)"
```

Чтобы выполнить каждый шаг вручную, используйте `udf create`, `udf version create`, `udf attach` (с флагом `--wake` для бездействующего сервиса), `udf detach` и `udf delete`. Эти команды возвращают управление сразу после принятия запроса; чтобы отслеживать состояние, периодически опрашивайте `udf get` и `udf attachment get`. Операции чтения поддерживают OAuth, а для операций записи требуется ключ API. Подробнее см. [руководство по пользовательским функциям](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

### Организации и доступ {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

Подкоманды `cloud org` принимают `--org-id`, а не позиционный ID. `org usage` охватывает период не более 31 дня. Кроме того, у `org` есть подкоманды `quota`, `balance`, `notification-types`, `role` (пользовательские роли организации) и `byoc` (BYOC infrastructure). Уведомления находятся в статусе бета.

Управление участниками, приглашениями и ключами API:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

**Если при выполнении `key create` не указать `--ip-allow`, любой сетевой доступ будет запрещён**, — в отличие от создания сервиса. Секрет отображается только один раз. Команда `key list` возвращает только одну страницу, если не передать `--all`. При выполнении `key update` неуказанные флаги сохраняют текущие значения, а `--clear-expiry`, `--clear-roles` и `--clear-ip-allow` сбрасывают соответствующие настройки.

### Резервные копии {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud service create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud service backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
clickhousectl cloud backup bucket get <service-id>
```

При восстановлении всегда создаётся новый сервис. Команда `cloud backup bucket` (get, create, update, delete) настраивает собственный бакет для резервных копий с помощью JSON‑файла, формат которого зависит от провайдера. Подробнее см. раздел о резервном копировании в [руководстве по сервису ClickHouse Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore).

## Вывод в формате JSON {#json-output}

Команды, возвращающие структурированные данные, поддерживают флаг `--json`. К ним относятся локальные команды, команды Cloud, а также команды `skills`, `update` и `telemetry`:

```bash
clickhousectl cloud service list --json
clickhousectl cloud key list --all --json
clickhousectl local server list --json
```

Когда CLI обнаруживает агента для программирования (например, Claude Code, Cursor, Codex, Gemini CLI, Goose или Devin, а также любой инструмент, задающий `AI_AGENT`), он автоматически переключается на JSON. SQL-клиенты и нативные клиенты используют собственные форматы: `cloud service query` в режиме JSON возвращает `JSONEachRow`, а `local client` всегда выводит данные в нативном формате. Скрипты, которые разбирают вывод запросов, должны явно указывать `--format`.

В режиме JSON ошибки среды выполнения выводятся в stderr в виде объекта со стабильным полем `code` и полем `message`:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

Ветвите логику по `error.code`, а не по тексту сообщения. Ошибки использования (usage errors) по-прежнему выводятся в виде текста с кодом выхода 2. Описание форм вывода и кодов ошибок см. в разделе [контракты автоматизации и вывода](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md).

## Коды выхода {#exit-codes}

| Код | Значение                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------- |
| `0` | Успешное выполнение. Для асинхронных операций Cloud это означает, что запрос принят, но ещё не завершён |
| `1` | Ошибка                                                                                                  |
| `2` | Ошибка использования, в том числе недопустимые значения флагов                                          |
| `3` | Операция отменена                                                                                       |
| `4` | Требуется аутентификация или она отклонена, в том числе при попытке выполнить операции записи с OAuth   |

`local client`, `local postgres client` и другие команды, передающие управление нативным клиентам, возвращают собственный код выхода клиента.

## Навыки для агентов {#skills}

Установите [официальный пакет ClickHouse agent skills](https://github.com/ClickHouse/agent-skills) в используемые вами агенты для программирования:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

По умолчанию навыки устанавливаются в текущий проект, а с флагом `--global` — в ваш домашний каталог. Общий каталог `.agents/skills/` подключается всегда. При запуске без терминала необходимо указать `--agent`, `--all` или `--detected-only`. Чтобы получить список имён поддерживаемых агентов, выполните `clickhousectl skills --help`.

## Самообновление {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

CLI также проверяет наличие обновлений в фоновом режиме (не чаще одного раза в 24 часа) и выводит уведомление, если доступна новая версия.

## Телеметрия {#telemetry}

`clickhousectl` собирает анонимные данные об использовании, которые помогают определять направление разработки. При первом запуске выводится уведомление, и никакие данные не отправляются; сбор начинается со следующего запуска, если вы его не отключите.

Каждое событие содержит:

* Путь команды и **имена** явно переданных флагов и аргументов — но не их значения
* Результат выполнения и код выхода
* Для команды с опечаткой — имя команды или флага, предложенное CLI, но не то, что вы ввели
* Для сбоев во время выполнения — ограниченный набор категорий: стадия и вид сбоя, HTTP-статус из списка разрешённых, а также категории повторных попыток, состояния подготовки ресурсов и длительности
* Версия CLI, ОС и архитектура, признак запуска в CI и обнаруженный агент для программирования

Значения аргументов, SQL-запросы, учётные данные, идентификаторы ресурсов, аргументы после `--` и сообщения об ошибках никогда не записываются. Идентификатор установки или устройства не используется.

Чтобы отказаться от сбора данных:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

Задайте `CHCTL_TELEMETRY_DEBUG=1`, чтобы выводить полезную нагрузку в stderr, ничего не отправляя. Подробнее см. в [описании телеметрии](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md).
