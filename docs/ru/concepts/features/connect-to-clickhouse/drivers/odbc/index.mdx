ODBC-драйвер ClickHouse предоставляет соответствующий стандартам интерфейс для подключения ODBC-совместимых приложений к
ClickHouse. Он реализует ODBC API и позволяет приложениям, инструментам бизнес-аналитики и скриптовым средам выполнять SQL-запросы,
получать результаты и работать с ClickHouse с помощью привычных механизмов.

Драйвер взаимодействует с сервером ClickHouse по [HTTP-протоколу](/ru/concepts/features/connect-to-clickhouse/protocols/http) — основному
протоколу, который поддерживается во всех развертываниях ClickHouse. Благодаря этому драйвер работает одинаково в самых разных
средах, включая локальные установки, управляемые облачные сервисы и среды, где доступ возможен только
по HTTP.

Исходный код драйвера доступен в
[репозитории ClickHouse-ODBC на GitHub](https://github.com/ClickHouse/clickhouse-odbc).

<Tip>
  Для лучшей совместимости настоятельно рекомендуем обновить сервер ClickHouse до версии 24.11 или более поздней.
</Tip>

<Note>
  Драйвер находится в стадии активной разработки. Некоторые возможности ODBC пока реализованы не полностью. Текущая версия
  обеспечивает базовое подключение и основную функциональность ODBC; дополнительные возможности запланированы в будущих
  выпусках.

  Ваши отзывы очень ценны: они помогают нам расставлять приоритеты при разработке новых возможностей и улучшений. Если вы столкнулись с
  ограничениями, отсутствующей функциональностью или неожиданным поведением, сообщите о своих наблюдениях или предложите новые возможности в
  трекере задач по адресу
  [https://github.com/ClickHouse/clickhouse-odbc/issues](https://github.com/ClickHouse/clickhouse-odbc/issues).
</Note>

## Тестирование {#testing}

Драйвер можно протестировать с помощью этого простого скрипта PowerShell. Скопируйте приведённый ниже текст, укажите свои URL, имя пользователя и пароль, а затем
вставьте текст в командную строку PowerShell — после выполнения `$reader.GetValue(0)` должна отобразиться версия
сервера ClickHouse.

```powershell
$url = "http://127.0.0.1:8123/"
$username = "default"
$password = ""
$conn = New-Object System.Data.Odbc.OdbcConnection("`
    Driver={ClickHouse ODBC Driver (Unicode)};`
    Url=$url;`
    Username=$username;`
    Password=$password")
$conn.Open()
$cmd = $conn.CreateCommand()
$cmd.CommandText = "select version()"
$reader = $cmd.ExecuteReader()
$reader.Read()
$reader.GetValue(0)
$reader.Close()
$conn.Close()
```

## Параметры конфигурации {#configuration-parameters}

Ниже приведены наиболее часто используемые параметры для установки соединения с ODBC-драйвером ClickHouse. Они охватывают основные параметры аутентификации, поведения соединения и обработки данных. Полный список поддерживаемых
параметров доступен на странице проекта на GitHub
[https://github.com/ClickHouse/clickhouse-odbc](https://github.com/ClickHouse/clickhouse-odbc).

* `Url`: задает полный HTTP(S)-адрес конечной точки сервера ClickHouse, включая протокол, хост, порт и
  необязательный путь.
* `Username`: имя пользователя для аутентификации на сервере ClickHouse.
* `Password`: пароль для указанного имени пользователя. Если он не задан, драйвер подключается без аутентификации
  по паролю.
* `Database`: база данных по умолчанию для соединения.
* `Timeout`: максимальное время (в секундах), в течение которого драйвер ожидает ответа сервера, прежде чем прервать запрос.
* `ClientName`: произвольный идентификатор, передаваемый на сервер ClickHouse в составе метаданных клиента. Полезен для трассировки или
  разграничения трафика от разных приложений. Этот параметр включается в заголовок User-Agent HTTP-запросов,
  формируемых драйвером.
* `Compression`: включает или отключает HTTP-сжатие полезных нагрузок запросов и ответов. Если сжатие включено, оно позволяет снизить
  нагрузку на пропускную способность сети и повысить производительность при работе с большими наборами результатов.
* `SqlCompatibilitySettings`: включает настройки запроса, при которых поведение ClickHouse становится ближе к традиционной реляционной
  базе данных. Это полезно, когда запросы автоматически генерируются сторонними инструментами, например Power BI. Такие
  инструменты, как правило, не учитывают некоторые особенности поведения, специфичные для ClickHouse, и могут формировать запросы, приводящие к ошибкам или
  неожиданным результатам. Подробнее см. в разделе [Настройки ClickHouse, используемые параметром конфигурации SqlCompatibilitySettings
  ](#sql-compatibility-settings).

Ниже приведены примеры полной строки подключения, которая передается драйверу для установки соединения.

* Сервер ClickHouse, установленный локально на инстансе WSL

```plaintext
Driver={ClickHouse ODBC Driver (Unicode)};Url=http://localhost:8123/;Username=default
```

* Инстанс ClickHouse Cloud.

```plaintext
Driver={ClickHouse ODBC Driver (Unicode)};Url=https://you-instance-url.gcp.clickhouse.cloud:8443/;Username=default;Password=your-password
```

## Интеграция с Microsoft Power BI {#powerbi-integration}

С помощью драйвера ODBC можно подключить Microsoft Power BI к серверу ClickHouse. Power BI предлагает два варианта
подключения: универсальный коннектор ODBC и коннектор ClickHouse; оба входят в стандартную установку Power BI.

Оба коннектора работают через ODBC, но различаются по возможностям:

* Коннектор ClickHouse (рекомендуется)
  Использует ODBC «под капотом», но поддерживает режим DirectQuery. В этом режиме Power BI автоматически формирует SQL-запросы и
  извлекает только те данные, которые нужны для конкретной визуализации или операции фильтрации.

* Коннектор ODBC
  Поддерживает только режим Import. Power BI выполняет заданный пользователем запрос (или выбирает всю таблицу) и импортирует
  весь результирующий набор в Power BI. При каждом последующем обновлении весь набор данных импортируется заново.

Выбирайте коннектор в зависимости от сценария использования. DirectQuery лучше всего подходит для интерактивных панелей мониторинга с большими наборами данных.
Режим Import подойдёт, если вам нужны полные локальные копии данных.

Подробнее об интеграции Microsoft Power BI с ClickHouse см. на [странице документации ClickHouse, посвящённой интеграции с Power
BI](/ru/integrations/connectors/data-visualization/powerbi-and-clickhouse).

## Настройки совместимости с SQL {#sql-compatibility-settings}

ClickHouse использует собственный диалект SQL и в некоторых случаях ведёт себя иначе, чем другие базы данных, такие как MS SQL
Server, MySQL или PostgreSQL. Часто эти различия дают преимущество: более удобный синтаксис
упрощает использование возможностей ClickHouse.

Однако драйвер ODBC часто используется в средах, где запросы не пишутся пользователями, а генерируются сторонними инструментами, такими как Power
BI. Эти запросы обычно используют лишь небольшое подмножество возможностей стандарта SQL. В таких случаях
отклонения ClickHouse от стандарта SQL могут приводить к неожиданному поведению, непредвиденным результатам или ошибкам.
Драйвер ODBC предоставляет дополнительный параметр конфигурации `SqlCompatibilitySettings`, который включает определённые настройки
запросов, чтобы приблизить поведение ClickHouse к стандартному SQL.

### Настройки ClickHouse, включаемые параметром конфигурации SqlCompatibilitySettings {#sql-compatibility-settings-list}

В этом разделе описано, какие настройки изменяет драйвер ODBC и зачем.

**[cast&#95;keep&#95;nullable](/ru/reference/settings/session-settings/cast#cast_keep_nullable)**

По умолчанию ClickHouse не позволяет преобразовывать типы, допускающие NULL, в типы, не допускающие NULL. Однако многие инструменты бизнес-аналитики при преобразовании типов
не различают типы, допускающие и не допускающие NULL. Поэтому инструменты бизнес-аналитики нередко
генерируют запросы наподобие следующего:

```sql
SELECT sum(CAST(value, 'Int32'))
FROM values
```

По умолчанию, если столбец `value` допускает NULL, этот запрос завершится ошибкой со следующим сообщением:

```plaintext
DB::Exception: Cannot convert NULL value to non-Nullable type: while executing 'FUNCTION CAST(__table1.value :: 2,
'Int32'_String :: 1) -> CAST(__table1.value, 'Int32'_String) Int32 : 0'. (CANNOT_INSERT_NULL_IN_ORDINARY_COLUMN)
```

Включение `cast_keep_nullable` изменяет поведение `CAST`: функция сохраняет допустимость NULL для своих аргументов. Благодаря этому
поведение ClickHouse при таком преобразовании становится ближе к другим базам данных и стандарту SQL.

**[prefer&#95;column&#95;name&#95;to&#95;alias](/ru/reference/settings/session-settings/prefer#prefer_column_name_to_alias)**

ClickHouse позволяет ссылаться на выражения в том же списке `SELECT` по их псевдонимам. Например, такой запрос избавляет от
повторений, и его проще писать:

```sql
SELECT
    sum(value) AS S,
    count() AS C,
    S / C
FROM test
```

Эта возможность широко используется, однако другие базы данных, как правило, не разрешают псевдонимы подобным образом в пределах одного списка `SELECT`,
и такие запросы завершаются ошибкой. Проблемы особенно заметны, когда псевдоним совпадает с именем столбца. Например:

```sql
SELECT
    sum(value) AS value,
    avg(value)
FROM test
```

Какой `value` должна агрегировать функция `avg(value)`? По умолчанию ClickHouse отдаёт предпочтение псевдониму, и выражение фактически превращается во
вложенный агрегат, чего большинство инструментов не ожидает.

Само по себе это редко становится проблемой, однако некоторые инструменты бизнес-аналитики генерируют запросы с подзапросами, в которых повторно используются псевдонимы столбцов. Например,
Power BI часто генерирует запросы примерно такого вида:

```sql
SELECT
    sum(C1) AS C1,
    count(C1) AS C2
FROM
(
    SELECT sum(value) AS C1
    FROM test
    GROUP BY group_index
) AS TBL
```

Обращения к `C1` могут приводить к следующей ошибке:

```plaintext
Code: 184. DB::Exception: Received from localhost:9000. DB::Exception: Aggregate function sum(C1) AS C1 is found
inside another aggregate function in query. (ILLEGAL_AGGREGATION)
```

Другие базы данных обычно не разрешают псевдонимы таким образом на том же уровне запроса, а рассматривают `C1` как столбец из
подзапроса. Чтобы обеспечить аналогичное поведение в ClickHouse и позволить выполнять такие запросы без ошибок, драйвер ODBC
включает `prefer_column_name_to_alias`.

В большинстве случаев включение этих настроек не должно вызывать проблем. Однако пользователи, у которых настройка readonly имеет значение `1`,
не могут изменять никакие настройки, даже для запросов `SELECT`. Для таких пользователей включение `SqlCompatibilitySettings` приведёт
к ошибке. В следующем разделе объясняется, как настроить этот параметр конфигурации для работы с пользователями с правом только на чтение.

## Как обеспечить работу настроек совместимости с SQL для пользователей с правом только на чтение {#readonly-users}

При подключении к ClickHouse через драйвер ODBC с включенным параметром `SqlCompatibilitySettings` пользователь, у которого
настройка readonly равна `1`, получит ошибку, поскольку драйвер пытается изменить настройки запроса:

```plaintext
Code: 164. DB::Exception: Cannot modify 'cast_keep_nullable' setting in readonly mode. (READONLY)
Code: 164. DB::Exception: Cannot modify 'prefer_column_name_to_alias' setting in readonly mode. (READONLY)
```

Это происходит потому, что пользователям в режиме только для чтения запрещено изменять настройки, даже для отдельных `SELECT`-запросов.
Решить эту проблему можно несколькими способами.

**Вариант 1. Установка `readonly` в значение `2`**

Это самый простой вариант. Если установить `readonly` в значение `2`, пользователь сможет изменять настройки, оставаясь при этом в режиме только для чтения.

```sql
ALTER USER your_odbc_user MODIFY SETTING
    readonly = 2
```

В большинстве случаев установка `readonly` в значение 2 — самый простой и рекомендуемый способ решить эту проблему. Если
этот вариант вам не подходит, воспользуйтесь вторым.

**Вариант 2. Изменение настроек пользователя в соответствии с настройками, которые задаёт драйвер ODBC.**

Этот способ тоже несложен: измените настройки пользователя так, чтобы они заранее совпадали с теми, которые пытается установить драйвер ODBC.

```sql
ALTER USER your_odbc_user MODIFY SETTING
    cast_keep_nullable = 1,
    prefer_column_name_to_alias = 1
```

После этого изменения драйвер ODBC по-прежнему может пытаться применить настройки, но, поскольку их значения уже совпадают,
фактически ничего не меняется и ошибка не возникает.

Этот вариант тоже прост, но требует сопровождения: в новых версиях драйвера список настроек может измениться или пополниться
новыми настройками для обеспечения совместимости. Если вы жёстко задаёте эти настройки для пользователя ODBC, вам может потребоваться обновлять их всякий раз, когда
драйвер ODBC начинает применять дополнительные настройки.
