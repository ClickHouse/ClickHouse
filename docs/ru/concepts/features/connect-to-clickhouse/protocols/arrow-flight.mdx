## Обзор {#overview}

ClickHouse поддерживает протокол [Apache Arrow Flight](https://arrow.apache.org/docs/format/Flight.html) — высокопроизводительный RPC-фреймворк для эффективной передачи столбцовых данных в формате [Arrow IPC](https://arrow.apache.org/docs/format/Columnar.html#serialization-and-interprocess-communication-ipc) поверх [gRPC](https://grpc.io/).

Реализация включает поддержку [Arrow Flight SQL](https://arrow.apache.org/docs/format/FlightSql.html), благодаря чему инструменты бизнес-аналитики и приложения, работающие по протоколу Flight SQL, могут напрямую выполнять запросы к ClickHouse.

Ключевые возможности:

* Выполнение SQL-запросов и получение результатов в формате Apache Arrow.
* Вставка данных в таблицы в формате Arrow.
* Запрос метаданных (каталогов, схем, таблиц, первичных ключей) с помощью команд Flight SQL.
* Создание, привязка, выполнение и закрытие подготовленных SQL-запросов на стороне сервера через Flight SQL.
* Управление сеансами и настройками с помощью действий Flight SQL.
* Шифрование TLS и аутентификация по имени пользователя и паролю.
* Инкрементальное получение результатов через `PollFlightInfo`.
* Отмена запросов через `CancelFlightInfo`.

<Note>
  В ClickHouse Cloud интерфейс Arrow Flight по умолчанию отключен: чтобы использовать его в вашем сервисе, необходимо включить соответствующий feature flag Cloud. Приведённые ниже примеры конфигурации сервера относятся к самоуправляемому ClickHouse.
</Note>

## Включение сервера Arrow Flight {#enabling-server}

Чтобы включить сервер Arrow Flight, добавьте настройку `arrowflight_port` в конфигурацию сервера ClickHouse:

```xml
<clickhouse>
    <arrowflight_port>9090</arrowflight_port>
</clickhouse>
```

При запуске в журнале появляется сообщение, подтверждающее, что интерфейс активен:

```text
{} <Information> Application: Arrow Flight compatibility protocol: 0.0.0.0:9090
```

## Настройка TLS {#tls-configuration}

Чтобы включить TLS для интерфейса Arrow Flight, задайте следующие настройки:

```xml
<clickhouse>
    <arrowflight_port>9090</arrowflight_port>
    <arrowflight>
        <enable_ssl>true</enable_ssl>
        <ssl_cert_file>/path/to/server-cert.pem</ssl_cert_file>
        <ssl_key_file>/path/to/server-key.pem</ssl_key_file>
    </arrowflight>
</clickhouse>
```

Если TLS включен, клиенты должны подключаться по схеме `grpc+tls://`, а не `grpc://`.

## Аутентификация {#authentication}

Интерфейс Arrow Flight поддерживает два метода аутентификации:

### Базовая аутентификация {#basic-auth}

Клиенты проходят аутентификацию с помощью имени пользователя и пароля, передаваемых в стандартном HTTP-заголовке `Authorization: Basic`. При успешной аутентификации сервер возвращает Bearer-токен в заголовке ответа.

### Аутентификация с помощью Bearer-токена {#bearer-auth}

В последующих запросах можно использовать Bearer-токен, полученный при базовой аутентификации, передавая его в заголовке `Authorization: Bearer <token>`. Токен автоматически обновляется при каждом использовании, а срок его действия определяется настройкой сервера `default_session_timeout` (по умолчанию — 60 секунд).

### Вызовы без имени пользователя {#auth-without-user-name}

Вызов без заголовка `authorization` или с учётными данными Basic, в которых указано пустое имя пользователя, аутентифицируется от имени пользователя, заданного настройкой сервера [`default_session_user`](/ru/reference/settings/server-settings/settings/default#default_session_user) (`default`, если не настроено иное), с переданным (возможно, пустым) паролем. Это работает точно так же, как HTTP-запрос без параметра `user`.

Пустое имя пользователя — лишь псевдоним этого пользователя. Его пароль, `networks` и другие проверки доступа применяются как обычно, поэтому именно конфигурация этого пользователя определяет, будет ли принят вызов без учётных данных.

Если для `default_session_user` задана пустая строка, такие вызовы отклоняются с ошибкой `Unauthenticated`. Если в конфигурации сервера включён раздел `session_log`, отказ записывается в [`system.session_log`](/ru/reference/system-tables/session_log) как событие `LoginFailure` с пустым значением `user`.

### Пример на Python {#auth-python-example}

```python
import pyarrow.flight as flight

client = flight.FlightClient("grpc://localhost:9090")

# Basic auth returns a bearer token for subsequent calls
token_pair = client.authenticate_basic_token("default", "")
options = flight.FlightCallOptions(headers=[token_pair])
```

С TLS:

```python
import pyarrow.flight as flight

with open("ca-cert.pem", "rb") as f:
    tls_root_certs = f.read()

client = flight.FlightClient(
    "grpc+tls://localhost:9090",
    tls_root_certs=tls_root_certs,
)

token_pair = client.authenticate_basic_token("default", "password")
options = flight.FlightCallOptions(headers=[token_pair])
```

## Управление сеансами {#session-management}

Интерфейс Arrow Flight поддерживает сеансы ClickHouse с помощью пользовательских заголовков метаданных gRPC:

| Заголовок                      | Описание                                                                                                                                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `x-clickhouse-session-id`      | Идентификатор сеанса. Если он указан, несколько запросов используют общее состояние сеанса (временные таблицы, настройки).                                                  |
| `x-clickhouse-session-timeout` | Тайм-аут сеанса в секундах. Не должен превышать `max_session_timeout`.                                                                                                      |
| `x-clickhouse-session-check`   | Установите значение `1`, чтобы проверить, существует ли сеанс, не создавая его.                                                                                             |
| `x-clickhouse-session-close`   | Установите значение `1`, чтобы закрыть сеанс после завершения запроса. Для этого в конфигурации сервера параметр `enable_arrow_close_session` должен иметь значение `true`. |

<Note>
  Поскольку Arrow Flight использует gRPC поверх HTTP/2, имена заголовков метаданных чувствительны к регистру и должны указываться в нижнем регистре в точности так, как показано (например, `x-clickhouse-session-id`, а не `X-ClickHouse-Session-Id`). Этого требует [RFC 9113, раздел 8.2](https://www.rfc-editor.org/rfc/rfc9113#section-8.2), согласно которому имена полей HTTP/2 должны состоять только из символов в нижнем регистре. В этом отличие от HTTP/1.1, где имена заголовков регистронезависимы.
</Note>

Сеансы позволяют задавать постоянные настройки ClickHouse с помощью действия `SetSessionOptions` (см. [DoAction](#doaction)).

## Поддерживаемые RPC-методы {#rpc-methods}

### GetFlightInfo {#getflightinfo}

Выполняет запрос и возвращает `FlightInfo`, содержащий схему результата, конечные точки с билетами для получения данных, количество строк и количество байт.

Принимает `FlightDescriptor` одного из следующих видов:

* **Дескриптор PATH**: путь из одного компонента, который интерпретируется как имя таблицы. Генерирует `SELECT * FROM <table>`.
* **Дескриптор CMD**: либо необработанная строка SQL-запроса, либо сериализованная команда Flight SQL в формате protobuf (см. [Команды Flight SQL](#flight-sql-commands)).

Запрос выполняется полностью, а результаты сохраняются в билетах на стороне сервера (server-side). Для каждого блока данных создаётся отдельная конечная точка/билет, что позволяет клиентам получать данные параллельно.

```python
# Query by table name
descriptor = flight.FlightDescriptor.for_path("my_table")
info = client.get_flight_info(descriptor, options)

# Query by SQL
descriptor = flight.FlightDescriptor.for_command(
    "SELECT * FROM my_table WHERE id > 100"
)
info = client.get_flight_info(descriptor, options)

# Retrieve results
for endpoint in info.endpoints:
    reader = client.do_get(endpoint.ticket, options)
    table = reader.read_all()
    print(table.to_pandas())
```

### PollFlightInfo {#pollflightinfo}

Обеспечивает инкрементальное получение результатов для long-running запросов. Вместо ожидания полного завершения запроса (как в `GetFlightInfo`) `PollFlightInfo` возвращает результаты поблочно.

При первом вызове запускается выполнение запроса. Ответ содержит:

* `FlightInfo` с конечными точками для всех блоков данных, доступных на текущий момент.
* `FlightDescriptor` для следующего опроса (если ожидаются дополнительные результаты).

Последующие вызовы с полученным дескриптором возвращают дополнительные блоки. Когда данных больше нет, ответ не содержит дескриптора для следующего опроса.

<Note>
  В текущей реализации вызов блокируется до появления блока данных, а не возвращается сразу без данных.
</Note>

### GetSchema {#getschema}

Возвращает схему Arrow для результата запроса, не выполняя сам запрос полностью. Принимает те же типы дескрипторов, что и `GetFlightInfo`.

```python
descriptor = flight.FlightDescriptor.for_command(
    "SELECT 1 AS x, 'hello' AS y"
)
schema_result = client.get_schema(descriptor, options)
schema = schema_result.schema
print(schema)  # x: int32, y: string
```

### DoGet {#doget}

Получает данные по указанному билету. Принимает один из следующих вариантов:

* Билет, возвращённый `GetFlightInfo` или `PollFlightInfo`.
* Необработанную строку SQL-запроса в качестве значения билета.

```python
# Using a ticket from GetFlightInfo
reader = client.do_get(endpoint.ticket, options)
table = reader.read_all()

# Using a raw SQL query as ticket
ticket = flight.Ticket("SELECT number FROM system.numbers LIMIT 10")
reader = client.do_get(ticket, options)
table = reader.read_all()
```

### DoPut {#doput}

Отправляет данные в ClickHouse. Принимает `FlightDescriptor` и поток батчей записей Arrow.

**Вставка по имени таблицы** (дескриптор PATH):

```python
schema = pa.schema([("id", pa.int64()), ("name", pa.string())])
batch = pa.record_batch(
    [pa.array([1, 2, 3]), pa.array(["Alice", "Bob", "Charlie"])],
    schema=schema,
)

descriptor = flight.FlightDescriptor.for_path("my_table")
writer, _ = client.do_put(descriptor, schema, options)
writer.write_batch(batch)
writer.close()
```

**Вставка с помощью SQL** (дескриптор CMD):

```python
descriptor = flight.FlightDescriptor.for_command(
    "INSERT INTO my_table FORMAT Arrow"
)
writer, _ = client.do_put(descriptor, schema, options)
writer.write_batch(batch)
writer.close()
```

**Выполнение DDL/DML через Flight SQL `CommandStatementUpdate`:**

Клиенты Flight SQL используют `CommandStatementUpdate` для выполнения операторов DDL/DML (CREATE, INSERT, ALTER и т. д.). Ответ содержит количество затронутых строк.

**Массовый приём данных через Flight SQL `CommandStatementIngest`:**

Поддерживается только добавление данных в конец существующих таблиц (`TABLE_NOT_EXIST_OPTION_FAIL` + `TABLE_EXISTS_OPTION_APPEND`). Каталоги и временные таблицы для этой команды не поддерживаются.

`transaction_id` не поддерживается для `CommandStatementUpdate` и `CommandStatementIngest`. Если он указан, ClickHouse возвращает ошибку `NotImplemented`.

<Note>
  Для передачи данных допускается только формат `Arrow`. Указание других форматов в SQL (например, `FORMAT JSON`) приводит к ошибке.
</Note>

### DoAction {#doaction}

Выполняет именованные действия. Поддерживаются следующие действия:

#### CancelFlightInfo {#cancelflightinfo}

Отменяет выполняющийся запрос, связанный с `FlightInfo`. Идентификатор запроса извлекается из поля `app_metadata` объекта `FlightInfo`. Также отменяются все дескрипторы опроса, связанные с этим запросом.

```python
# Start a long-running query via PollFlightInfo, then cancel it
cancel_request = flight.CancelFlightInfoRequest(info)
result = client.cancel_flight_info(cancel_request, options)
# result.status is CancelStatus.CANCELLED if successful
```

#### SetSessionOptions {#setsessionoptions}

Задаёт настройки сервера ClickHouse для текущего сеанса. Требуется, чтобы идентификатор сеанса был задан в заголовке `x-clickhouse-session-id`.

Поддерживаемые типы значений: строка, логический тип, целое число, Double и списки строк.

Если имя настройки неизвестно, возвращается ошибка `INVALID_NAME`. Если значение не удаётся разобрать, возвращается ошибка `INVALID_VALUE`.

#### GetSessionOptions {#getsessionoptions}

Возвращает все текущие настройки ClickHouse и их значения для сеанса. Возвращает ассоциативный массив, в котором именам настроек сопоставлены строковые значения (внутри выполняет запрос к `system.settings`).

#### CreatePreparedStatement {#createpreparedstatement}

Создаёт server-side подготовленный запрос и возвращает дескриптор запроса. Запрос содержит текст SQL-запроса с плейсхолдерами `?`.

`transaction_id` для этого действия не поддерживается. Если он указан, ClickHouse возвращает ошибку `NotImplemented`.

Для операторов запросов ответ может содержать:

* `dataset_schema`: схему результирующего набора.
* `parameter_schema`: схему параметров запроса.

Если для корректного запроса не удаётся автоматически определить схему (например, когда замена плейсхолдеров на `NULL` для этого запроса недопустима), ClickHouse всё равно создаёт подготовленный запрос и возвращает дескриптор без `dataset_schema`.

`dataset_schema` — лишь наилучшее предположение, как и предусмотрено спецификацией Flight SQL: в ней сказано, что схема результата может зависеть от параметров, что сервер должен выдавать наилучшее предположение и что клиенты не должны считать схему точной. Не полагайтесь на неё: чтобы получить схему, описывающую данные, выполните запрос. В ClickHouse она может отличаться от фактически возвращаемой по двум причинам:

* При автоматическом определении каждый `?` заменяется на `NULL`, поэтому плейсхолдер, определяющий столбец результата, получает тип по этому `NULL`, а не по значению, которое вы привяжете позже. Для `SELECT ? AS x` определяется столбец типа `Nothing`, но при привязке `5` возвращается `UInt8`. У плейсхолдера, используемого только в предикате, как в `SELECT id, name FROM t WHERE id = ?`, этой проблемы нет, поскольку типы результата берутся из таблицы.
* Столбец, не имеющий эквивалента в Arrow, получает тип Arrow согласно настройке [`output_format_arrow_unsupported_types`](/ru/reference/settings/formats/output-format), значение которой каждый вызов берёт из сеанса, в котором он выполняется. Поскольку дескриптор принадлежит пользователю, а не одному сеансу, последующий вызов может получить другое значение и вернуть `binary` там, где был объявлен `utf8`, или наоборот. Чтобы зафиксировать режим для обоих случаев, задайте его внутри самого подготовленного запроса.

Подготовленные запросы принадлежат аутентифицированному пользователю, а не отдельному сеансу. Если открыть несколько сеансов от имени одного пользователя, один и тот же дескриптор запроса можно выполнять, повторно привязывать и закрывать из любого из этих сеансов.

Другие пользователи не могут выполнять, привязывать или закрывать дескриптор запроса, который они не создавали.

`arrowflight.prepared_statements_lifetime_seconds` управляет истечением срока действия:

* `> 0`: заданное значение используется как время жизни запроса. Срок действия продлевается при каждом запросе как для запросов, привязанных к сеансу, так и для запросов без привязки к сеансу.
* `0`: срок действия подготовленных запросов автоматически не истекает.
* `-1` (по умолчанию): если запрос создан в сеансе, его время жизни определяется тайм-аутом этого сеанса и продлевается при каждом запросе в этом сеансе. Если запрос создан вне сеанса, его срок действия автоматически не истекает.

Запросы с истёкшим сроком действия удаляются и больше не учитываются в `arrowflight.max_prepared_statements_per_user`.

#### ClosePreparedStatement {#closepreparedstatement}

Закрывает подготовленный запрос и освобождает связанные с ним server-side ресурсы, если запрос содержит непустой дескриптор запроса.

ClickHouse также поддерживает массовое закрытие с помощью `ClosePreparedStatement`, если дескриптор пуст:

* Если указан `x-clickhouse-session-id`, закрываются все подготовленные запросы аутентифицированного пользователя в этом сеансе.
* Если идентификатор сеанса не указан, закрываются только подготовленные запросы аутентифицированного пользователя, не привязанные к сеансу.

Если подготовленный запрос создан в сеансе (с помощью `x-clickhouse-session-id`), он также автоматически закрывается при закрытии этого сеанса.

## Команды Flight SQL {#flight-sql-commands}

Если дескриптор `CMD` содержит сериализованное сообщение [Flight SQL Protobuf](https://arrow.apache.org/docs/format/FlightSql.html), ClickHouse обрабатывает следующие команды:

### Поддерживаемые через GetFlightInfo / GetSchema {#flightsql-getflightinfo}

| Команда                         | Описание                                                                                                                          |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `CommandStatementQuery`         | Выполняет произвольный SQL-запрос. `transaction_id` не поддерживается.                                                            |
| `CommandGetSqlInfo`             | Возвращает метаданные сервера (имя, версия, версия Arrow, возможности).                                                           |
| `CommandGetCatalogs`            | Возвращает список каталогов. Результат всегда пустой (ClickHouse не использует каталоги).                                         |
| `CommandGetDbSchemas`           | Возвращает список баз данных. Поддерживает необязательный параметр `db_schema_filter_pattern` (шаблон SQL `LIKE`).                |
| `CommandGetTables`              | Возвращает список таблиц. Поддерживает фильтрацию по схеме, имени таблицы и типам таблиц, а также необязательное включение схемы. |
| `CommandGetTableTypes`          | Возвращает список типов движков таблиц (из `system.table_engines`).                                                               |
| `CommandGetPrimaryKeys`         | Возвращает столбцы первичного ключа указанной таблицы.                                                                            |
| `CommandPreparedStatementQuery` | Выполняет подготовленный оператор вида `SELECT` по дескриптору.                                                                   |

### Поддерживаемые через DoPut {#flightsql-doput}

| Команда                          | Описание                                                                                                                                                                                                                                                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CommandStatementUpdate`         | Выполняет оператор DDL/DML (CREATE, INSERT, ALTER и т. д.). Возвращает количество затронутых строк. `transaction_id` не поддерживается.                                                                                                                                                                                |
| `CommandStatementIngest`         | Выполняет массовую вставку данных Arrow в существующую таблицу. Поддерживается только режим добавления в конец. `transaction_id` не поддерживается.                                                                                                                                                                    |
| `CommandPreparedStatementQuery`  | При отправке через `DoPut` привязывает значения параметров к подготовленному оператору, после чего возвращает `DoPutPreparedStatementResult` с дескриптором оператора. Принимается только один набор параметров (одна строка), а количество связанных значений должно точно совпадать с количеством плейсхолдеров `?`. |
| `CommandPreparedStatementUpdate` | Выполняет подготовленный оператор DDL/DML по дескриптору и возвращает количество затронутых строк.                                                                                                                                                                                                                     |

### Не поддерживается в ClickHouse {#flightsql-not-implemented}

Эти команды соответствуют возможностям, которых нет в ClickHouse, поэтому интерфейс Arrow Flight SQL их не поддерживает.

| Команда                         | Причина                                                                                                                                         |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `CommandGetCrossReference`      | ClickHouse не является реляционной базой данных и не реализует ограничения внешних ключей, поэтому метаданные перекрёстных ссылок недоступны.   |
| `CommandGetExportedKeys`        | ClickHouse не является реляционной базой данных и не реализует ограничения внешних ключей, поэтому метаданные экспортируемых ключей недоступны. |
| `CommandGetImportedKeys`        | ClickHouse не является реляционной базой данных и не реализует ограничения внешних ключей, поэтому метаданные импортируемых ключей недоступны.  |
| `CommandStatementSubstraitPlan` | ClickHouse не поддерживает планы Substrait.                                                                                                     |

## Полный пример {#complete-example}

```python title="Query"
import pyarrow as pa
import pyarrow.flight as flight

# Connect and authenticate
client = flight.FlightClient("grpc://localhost:9090")
token = client.authenticate_basic_token("default", "")
options = flight.FlightCallOptions(headers=[token])

# Insert data using DoPut with a PATH descriptor
schema = pa.schema([("id", pa.uint32()), ("value", pa.string())])
batch = pa.record_batch(
    [pa.array([1, 2, 3], type=pa.uint32()), pa.array(["a", "b", "c"])],
    schema=schema,
)
descriptor = flight.FlightDescriptor.for_path("test")
writer, _ = client.do_put(descriptor, schema, options)
writer.write_batch(batch)
writer.close()

# Query data using GetFlightInfo + DoGet
descriptor = flight.FlightDescriptor.for_command(
    "SELECT * FROM test ORDER BY id"
)
info = client.get_flight_info(descriptor, options)
for endpoint in info.endpoints:
    reader = client.do_get(endpoint.ticket, options)
    table = reader.read_all()
    print(table.to_pandas())
```

```text title="Response"
   id value
0   1     a
1   2     b
2   3     c
```

## Формат данных {#data-format}

Все данные передаются в формате Apache Arrow IPC. Поддерживается только формат `Arrow` — указание других форматов ClickHouse (например, `FORMAT JSON`, `FORMAT CSV`) приводит к ошибке.

При сериализации типы данных ClickHouse сопоставляются с типами Arrow. Arrow Flight всегда использует каноническое сопоставление Arrow и, в отличие от форматов вывода `Arrow` и `ArrowStream`, **не** учитывает настройки `output_format_arrow_*`, которые изменяют представление типа: `output_format_arrow_string_as_string`, `output_format_arrow_low_cardinality_as_dictionary`, `output_format_arrow_date_as_uint16`, `output_format_arrow_fixed_string_as_fixed_byte_array` и настройки индексов словаря здесь не действуют. Поэтому один и тот же запрос может возвращать через Arrow Flight схему, отличающуюся от схемы при использовании `FORMAT Arrow`. Такое поведение предусмотрено по двум причинам:

* Flight SQL задаёт фиксированную схему ответов с метаданными. Например, `CommandGetTables` должен возвращать `catalog_name: utf8, db_schema_name: utf8, table_name: utf8 not null, table_type: utf8 not null, table_schema: bytes not null`. Если бы настройка сеанса могла превращать эти столбцы `utf8` в `binary`, ClickHouse нарушал бы требования Flight SQL при работе с любым драйвером; кроме того, это изменяло бы схему каждой таблицы, которую ClickHouse передаёт в `table_schema`.
* Клиент Flight получает схему и данные отдельными вызовами (`GetFlightInfo` или `GetSchema`, затем `DoGet`). Любая настройка, способная изменить схему, может привести к несоответствию между объявленной схемой и передаваемым потоком, если настройки сеанса изменятся между вызовами.

Единственное исключение — типы, у которых вообще нет эквивалента в Arrow, например `JSON`, `Dynamic`, `QBit` или `AggregateFunction`. Для них нет канонического сопоставления, которого можно было бы придерживаться, поэтому ClickHouse должен выбрать представление, а настройка [`output_format_arrow_unsupported_types`](/ru/reference/settings/formats/output-format) позволяет указать, какое именно:

| Значение                | Поведение                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `throw`                 | Запрос отклоняется.                                                                                                      |
| `text`                  | Одно значение на строку в текстовом представлении, в столбце Arrow `Utf8` — результат `CAST(col AS String)`.             |
| `binary` (по умолчанию) | Одно значение на строку в двоичном представлении, в столбце Arrow `Binary` — с кодированием, используемым в `RowBinary`. |

`AggregateFunction` — единственный тип, столбец которого остаётся столбцом Arrow `Binary` даже в режиме `text`: его текстовое представление — это необработанное состояние агрегатной функции, которое не является корректным UTF-8, а столбец Arrow `Utf8` должен содержать корректный UTF-8. Чтобы получить читаемое значение, используйте `finalizeAggregation`.

По той же причине ClickHouse заменяет каждую недопустимую последовательность UTF-8 в значении в режиме `text` на U+FFFD (`�`) перед записью в столбец `Utf8`. Значение `Dynamic`, содержащее `String`, сериализует его байты без изменений, а они могут быть произвольными. Без такой замены столбец нарушал бы спецификацию Arrow и мог бы быть отклонён клиентом со строгой проверкой. Изменяются только значения, которые изначально не являются корректным текстом. Используйте режим `binary`, если байты необходимо сохранить в точности.

Настройка `output_format_arrow_string_as_string` никогда не применяется к этим столбцам, в том числе в `FORMAT Arrow`: она управляет только столбцами собственно типов `String` и `FixedString`. Поэтому тип Arrow столбца `clickhouse.opaque` всегда указывает, какое кодирование используется для его содержимого: `Utf8` для текстового представления, `Binary` — для двоичного.

Именно поэтому состояние агрегатной функции, хранящееся в `Dynamic`, передаётся с потерями в режиме `text`, хотя в столбце `AggregateFunction` потерь нет. Тип столбца определяется типом `Dynamic`, который ничего не говорит о содержимом строк, а схема фиксируется ещё до обработки значений, поэтому для состояния нельзя выделить отдельный столбец `Binary`. Чтобы сохранить его без потерь, используйте режим `binary`. Тип `Variant` перечисляет свои альтернативы, поэтому входящий в их число `AggregateFunction` получает собственный дочерний элемент `Binary` и не подвергается такому преобразованию.

В остальном такой столбец неотличим от обычного столбца `Utf8`/`Binary`, поэтому он объявляется типом расширения Arrow: метаданные поля содержат `ARROW:extension:name` = `clickhouse.opaque` и исходное имя типа ClickHouse в `ARROW:extension:metadata`. Клиент, который не распознаёт имя расширения, видит обычный тип хранения, как и предписывает спецификация Arrow. Вложенные столбцы помечаются на уровне их собственных полей, поэтому метку получает дочерний элемент `Array(JSON)`, а также ключ `Map(JSON, ...)`, а не сам контейнер.

Прежний параметр логического типа `output_format_arrow_unsupported_types_as_binary` по-прежнему работает: значение `0` эквивалентно `throw`, а `1` — `binary`. Он учитывается только в том случае, если для `output_format_arrow_unsupported_types` оставлено значение по умолчанию.

## Совместимость {#compatibility}

Интерфейс Arrow Flight совместим с любым клиентом или инструментом, поддерживающим протокол Arrow Flight или Arrow Flight SQL, в том числе:

* Python (`pyarrow`)
* Java (`org.apache.arrow.flight`)
* C++ (`arrow::flight`)
* Go (`apache/arrow/go`)
* Драйверы ADBC (Arrow Database Connectivity)
* DBeaver и другие инструменты с поддержкой Flight SQL

Если для вашего инструмента доступен нативный коннектор ClickHouse (например, JDBC, ODBC или собственный протокол), отдавайте ему предпочтение, кроме случаев, когда Arrow Flight необходим для достижения нужной производительности или обеспечения совместимости форматов.
