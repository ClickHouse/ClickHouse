Потребление памяти при выполнении JOIN регулируется двумя группами настроек. Для большинства алгоритмов жёсткие лимиты прерывают запрос, если состояние JOIN становится слишком большим. Пороги сброса на диск заставляют JOIN записывать часть состояния на диск, чтобы выполнение запроса могло продолжиться.

## Жёсткие лимиты {#hard-limits}

* [`max_rows_in_join`](/ru/reference/settings/session-settings/max-rows#max_rows_in_join) ограничивает число строк в структуре данных для правой части JOIN — как правило, это хеш-таблица.
* [`max_bytes_in_join`](/ru/reference/settings/session-settings/max-bytes#max_bytes_in_join) ограничивает размер этой же структуры данных в байтах.
* [`join_overflow_mode`](/ru/reference/settings/session-settings/join#join_overflow_mode) определяет, что происходит при достижении любого из лимитов.

Оба лимита также действуют для [движка таблицы `Join`](/ru/reference/engines/table-engines/special/join). Если запрос содержит несколько JOIN, ClickHouse проверяет лимиты для каждого из них.

Для алгоритмов, основанных на хешировании, в том числе для алгоритмов со сбросом данных на диск, достижение лимита останавливает запрос и никогда не приводит к сбросу JOIN на диск. Поэтому если лимит равен порогу сброса на диск или меньше него, запрос, как правило, останавливается раньше, чем JOIN успевает сбросить данные на диск.

Это поведение меняют две настройки:

* [`enable_adaptive_memory_spill_scheduler`](/ru/reference/settings/session-settings/enable#enable_adaptive_memory_spill_scheduler) сбрасывает данные подходящих процессоров на диск при нехватке памяти у запроса. Для JOIN она действует только в том случае, если JOIN уже поддерживает сброс данных на диск: это JOIN типа `hash`, `parallel_hash` или `auto` с ненулевым [порогом сброса на диск](#spill-thresholds), JOIN типа `grace_hash` или переход на резервный вариант block nested loop при настроенном временном хранилище. Такой JOIN может сбросить данные на диск ещё до достижения порога сброса или жёсткого лимита.
* [`legacy_join_size_limits_trigger_spilling`](/ru/reference/settings/session-settings/other#legacy_join_size_limits_trigger_spilling) восстанавливает поведение версий до 26.10: при достижении жёстких лимитов часть JOIN, которая уже выполняется на диске, продолжает сбрасывать данные на диск, а запрос не останавливается. С этой настройкой `grace_hash` сбрасывает данные на диск только по жёстким лимитам и игнорирует пороги сброса. `hash` и `parallel_hash` по-прежнему начинают сброс на диск при достижении порога, а на этапе работы в памяти продолжают считать жёсткие лимиты верхними границами.

Для других алгоритмов лимиты действуют иначе:

* Для [`inequality`](/ru/concepts/features/operations/select/join-algorithms#inequality) лимиты применяются к суммарному объёму накопленных входных данных обеих сторон.
* Для [перехода на резервный вариант block nested loop](/ru/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback) лимиты применяются к материализованной правой стороне, включая блоки, выгруженные на диск.
* Для [`partial_merge`](/ru/concepts/features/operations/select/join-algorithms#partial-merge) достижение лимита не останавливает запрос, а меняет стратегию выполнения: JOIN начинает записывать свои отсортированные правые блоки на диск.

## Пороги сброса на диск {#spill-thresholds}

* [`max_bytes_before_external_join`](/ru/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) задаёт абсолютный порог сброса на диск в байтах для правой части JOIN, основанного на хешировании.
* [`max_bytes_ratio_before_external_join`](/ru/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join) задаёт порог сброса на диск как долю памяти, остающейся в пределах `max_memory_usage` запроса, а также ограничений памяти пользователя и сервера. Если ограничение памяти не настроено, эта доля ни на что не влияет.

Если заданы обе настройки, применяется меньший из получившихся порогов. Пороговые значения действуют для `hash`, `parallel_hash`, `grace_hash`, значения `auto`, а также при переходе на резервный вариант block nested loop. Для их работы необходимо настроить путь для временных данных.

## Как работает сброс данных на диск {#how-spilling-works}

Каждый алгоритм, поддерживающий сброс данных на диск, записывает во временные файлы свою часть состояния:

* **`hash` и `parallel_hash`.** JOIN строит хеш-таблицы в памяти. Когда правая сторона превышает порог сброса на диск, JOIN переключается на `grace_hash`. Строки правой стороны распределяются по корзинам на основе хеша ключа JOIN: одна корзина остаётся в памяти, а остальные записываются во временные файлы. Строки левой стороны распределяются с помощью той же хеш-функции. Строки, попавшие в корзину в памяти, соединяются сразу, а остальные записываются во временные файлы. После чтения левой стороны ClickHouse поочерёдно загружает и соединяет оставшиеся пары корзин.
* **`grace_hash`.** JOIN выполняет ту же процедуру, начиная с первого блока. Если хеш-таблица корзины превышает порог, количество корзин удваивается, но не более чем до `grace_hash_join_max_buckets`. При превышении этого максимума запрос завершается с ошибкой.
* **`full_sorting_merge`.** При превышении `max_bytes_before_external_sort` или `max_bytes_ratio_before_external_sort` сортировка каждого входного потока записывает отсортированные блоки во временные файлы. Затем эти файлы объединяются слиянием.
* **`partial_merge`.** Когда правая сторона достигает жёсткого лимита, отсортированные блоки правой стороны и их индексы минимумов и максимумов записываются во временные файлы.
* **Переход на резервный вариант block nested loop.** Блоки правой стороны сжимаются в памяти, а после достижения порога сброса на диск записываются во временные файлы.

Алгоритмы [`direct`](/ru/concepts/features/operations/select/join-algorithms#direct) и [`inequality`](/ru/concepts/features/operations/select/join-algorithms#inequality) не сбрасывают данные на диск.

Временные файлы записываются в хранилище, заданное настройкой сервера [`tmp_path`](/ru/reference/settings/server-settings/settings/tmp#tmp_path), [`tmp_policy`](/ru/reference/settings/server-settings/settings/tmp#tmp_policy) или [`temporary_data_in_cache`](/ru/reference/settings/server-settings/settings/temporary-data#temporary_data_in_cache). Чтение и запись временных файлов создают дополнительную нагрузку на дисковый ввод-вывод, поэтому JOIN со сбросом данных на диск выполняется медленнее, чем тот же JOIN в памяти.

События профилирования `ExternalJoinWritePart`, `ExternalJoinCompressedBytes` и `ExternalJoinUncompressedBytes` показывают, сколько временных файлов записал JOIN и какой объём данных в них содержится. Эти события доступны в столбце `ProfileEvents` таблицы [`system.query_log`](/ru/reference/system-tables/query_log).
