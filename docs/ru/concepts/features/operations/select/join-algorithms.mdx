На этой странице описаны все значения настройки [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm), задающие алгоритм выполнения JOIN, а также резервный вариант — блочный JOIN с вложенными циклами. Для наглядности на диаграммах используется `max_threads = 2`.

## `direct` {#direct}

<div className="ch-image-lg">
  <Frame>
    ![Конвейер прямого JOIN: два параллельных потока читают левую таблицу, а два этапа JOIN ищут каждую строку в словаре, на котором основана правая таблица; этап построения отсутствует](/images/guides/join-algorithms/direct-join.png)
  </Frame>
</div>

Алгоритм `direct` выполняет поиск в правой части для каждой строки левой части. Правая часть должна быть хранилищем, поддерживающим поиск по схеме ключ-значение с низкой задержкой. ClickHouse параллельно читает левую часть в потоковом режиме и соединяет каждый блок, выполняя поиск его ключей в этом хранилище. Этап построения отсутствует, поскольку данные правой части уже хранятся в структуре ключ-значение.

В качестве правой части подходят:

* [Словари](/ru/concepts/features/dictionaries), за исключением словарей с ключом-диапазоном.
* Таблицы с движком [`EmbeddedRocksDB`](/ru/reference/engines/table-engines/integrations/embedded-rocksdb), [`KeeperMap`](/ru/reference/engines/table-engines/special/keepermap) или [`Redis`](/ru/reference/engines/table-engines/integrations/redis).
* Таблицы `MergeTree` — начиная с версии 25.12 и только если `join_algorithm` имеет единственное значение `direct`. ClickHouse передаёт фильтр по ключу JOIN для каждого левого блока в операцию чтения правой таблицы. Это эффективно, если для ключа может использоваться индекс первичного ключа правой таблицы. В противном случае ClickHouse сканирует правую таблицу для каждого блока левой части.

Правая часть с [движком таблицы `Join`](/ru/reference/engines/table-engines/special/join) также читается из подготовленной структуры в памяти без этапа построения. Этот случай не зависит от `join_algorithm`: ClickHouse всегда использует хеш-таблицу, хранящуюся в таблице `Join`, а `EXPLAIN` отображает её как `FilledJoin` с `Algorithm: HashJoin`. В ClickHouse Cloud движок таблицы `Join` реализован как `SharedJoin` с базовой таблицей `MergeTree`.

Алгоритм `direct` используется при выполнении всех следующих условий:

* JOIN является `INNER` JOIN со строгостью `ALL` или `LEFT` JOIN со строгостью `ALL`, `ANY`, `SEMI` или `ANTI`. Для таблиц `MergeTree` строгость `ANY` не поддерживается.
* Секция `ON` содержит ровно одно условие равенства между одним столбцом с каждой стороны и никаких других условий.
* Правый столбец является одностолбцовым ключом хранилища, и его тип совпадает с типом ключа без учёта `Nullable` и `LowCardinality`.

Если какое-либо условие не выполнено, ClickHouse пробует следующий алгоритм из `join_algorithm`.

**Память и сброс данных на диск.** Запрос не строит структуру данных для правой части. Память, занимаемая словарём, учитывается за словарём, а не за запросом, и отображается в столбце `bytes_allocated` таблицы [`system.dictionaries`](/ru/reference/system-tables/dictionaries). Алгоритм не сбрасывает данные на диск.

**Ограничения.** Алгоритм поддерживает только один ключ равенства и не поддерживает `RIGHT`, `FULL` и `ASOF` JOIN. Фильтры не проталкиваются в правую часть.

## `hash` {#hash}

<div className="ch-image-lg">
  <Frame>
    ![Конвейер hash JOIN: два потока считывают правую таблицу в единую хеш-таблицу в памяти, затем два параллельных потока считывают левую таблицу и соединяют каждую строку путём поиска в этой хеш-таблице](/images/guides/join-algorithms/hash-join.png)
  </Frame>
</div>

Алгоритм `hash` целиком загружает правую часть в память и строит на её основе хеш-таблицу в памяти. Затем он параллельно читает левую часть в потоковом режиме и соединяет каждую строку, выполняя поиск её ключа в хеш-таблице. ClickHouse выбирает реализацию хеш-таблицы в зависимости от типов столбцов ключа JOIN и строгости JOIN.

Для JOIN типов `INNER`, `LEFT`, `RIGHT` и `FULL` способ построения хеш-таблицы определяется настройкой [`parallel_hash_join_threshold`](/ru/reference/settings/session-settings/parallel#parallel_hash_join_threshold). Если оценочное число строк правой части меньше порога, одну хеш-таблицу заполняет один поток, как показано на схеме выше. Если оно равно порогу или превышает его, ClickHouse разделяет хеш-таблицу на части, которые конкурентно заполняют до [`max_threads`](/ru/reference/settings/session-settings/max-threads#max_threads) потоков, как показано для [`parallel_hash`](#parallel-hash). Если оценка отсутствует, хеш-таблица также разделяется. Если правая часть использует специальное хранилище, например словарь, всегда создаётся одна хеш-таблица, которую заполняет один поток.

**Когда используется.** Алгоритм `hash` — наиболее универсальная реализация. Он поддерживает все сочетания типа соединения и строгости, реализованные в ClickHouse; при этом `ASOF` доступен только для JOIN типов `INNER` и `LEFT`. Это единственный алгоритм, поддерживающий несколько ключей JOIN, объединённых через `OR` в предложении `ON`. Значение `auto` поддерживает такие JOIN, поскольку выполняет их с помощью `hash`. Наряду с `parallel_hash` и `grace_hash` он также поддерживает условия, сравнивающие столбцы обеих таблиц, в дополнение к ключу равенства.

**Память и сброс данных на диск.** Хеш-таблица и строки правой части должны помещаться в память. Потребление памяти может превышать размер несжатых данных правой части, поскольку хеш-таблица увеличивается ступенчато и не всегда заполнена полностью. Если задан порог сброса на диск, JOIN начинает выполняться в памяти и переключается на алгоритм `grace_hash`, как только правая часть превышает этот порог. См. [Управление памятью и сброс данных на диск при JOIN](/ru/concepts/features/operations/select/join-memory-management).

**Ограничения.** Если хеш-таблица не разделяется, фаза построения выполняется в одном потоке. Она может занимать основную часть времени выполнения запроса, если правая часть значительно превышает оценку.

## `parallel_hash` {#parallel-hash}

<div className="ch-image-lg">
  <Frame>
    ![Конвейер параллельного hash JOIN: строки правой таблицы разделяются на две корзины по хешу ключа JOIN, и две хеш-таблицы заполняются параллельно; строки левой таблицы направляются в соответствующую хеш-таблицу той же хеш-функцией](/images/guides/join-algorithms/parallel-hash-join.png)
  </Frame>
</div>

`parallel_hash` — устаревший псевдоним `hash`, сохранённый для совместимости. Если указать его в `join_algorithm`, способ построения хеш-таблицы не изменится: для обоих значений его определяет [`parallel_hash_join_threshold`](/ru/reference/settings/session-settings/parallel#parallel_hash_join_threshold). Чтобы хеш-таблица разделялась всякий раз, когда это допускает тип JOIN, установите порог в `0`. Чтобы всегда использовалась одна хеш-таблица, установите для `hash_join_layout` значение `serial`.

На схеме показано, как `hash` строит разделённую хеш-таблицу. ClickHouse распределяет строки правой части по частям на основе хеша ключа JOIN, и до [`max_threads`](/ru/reference/settings/session-settings/max-threads#max_threads) потоков конкурентно заполняют эти части. На этапе проверки (probe) та же хеш-функция направляет каждую строку левой части в ту часть, где могут находиться совпадающие с ней строки.

## `grace_hash` {#grace-hash}

<div className="ch-image-lg">
  <Frame>
    ![Первый этап Grace hash JOIN с grace_hash_join_initial_buckets = 3: строки обеих таблиц разделяются на корзины по хешу ключа JOIN; первая корзина соединяется в памяти, а остальные корзины обеих таблиц откладываются во временное хранилище](/images/guides/join-algorithms/grace-hash-join.png)
  </Frame>
</div>

Алгоритм `grace_hash` — это hash JOIN, для которого не требуется, чтобы правая часть помещалась в память. Он выполняется в два этапа:

1. ClickHouse разделяет строки правой части на корзины по хешу ключа JOIN. Для первой корзины строится хеш-таблица в памяти, а остальные корзины записываются во временное хранилище. Левая часть разделяется с помощью той же хеш-функции: строки первой корзины сразу участвуют в соединении, а остальные строки записываются во временное хранилище.
2. ClickHouse обрабатывает оставшиеся корзины по очереди. Для каждой корзины строится хеш-таблица из строк правой части, после чего с ней соединяются строки левой части из той же корзины.

Начальное количество корзин задаётся настройкой [`grace_hash_join_initial_buckets`](/ru/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets) и округляется вверх до степени двойки. Если хеш-таблица в памяти превышает порог сброса на диск, ClickHouse удваивает количество корзин и перемещает строки, которые больше не относятся к текущей корзине. Количество корзин не может превышать [`grace_hash_join_max_buckets`](/ru/reference/settings/session-settings/grace-hash#grace_hash_join_max_buckets).

**Когда используется.** Алгоритмы `hash` и `parallel_hash` автоматически переключаются на `grace_hash`, когда правая часть превышает порог сброса на диск. Если явно выбрать `grace_hash`, JOIN будет партиционировать правую часть уже с первого блока, минуя этап обработки в памяти. Алгоритм поддерживает JOIN типов `INNER`, `LEFT`, `RIGHT` и `FULL` со строгостью `ALL`, `ANY`, `SEMI` и `ANTI`.

**Память и сброс данных на диск.** Потребление памяти ограничено порогом сброса на диск. Чем больше начальное количество корзин, тем ниже потребление памяти, но тем больше время выполнения. Для работы алгоритма требуются ненулевой порог сброса на диск и настроенное временное хранилище. Если порог не задан, ClickHouse пропускает `grace_hash`, когда в `join_algorithm` указаны другие алгоритмы, и отклоняет запрос, если `grace_hash` — единственное значение.

**Ограничения.** Алгоритм не поддерживает JOIN типа `ASOF`, а также несколько ключей JOIN, объединённых через `OR`. Из-за чтения и записи временных файлов он работает медленнее, чем hash JOIN в памяти.

## `full_sorting_merge` {#full-sorting-merge}

<div className="ch-image-lg">
  <Frame>
    ![Конвейер JOIN с полным сортирующим соединением слиянием: блоки обеих таблиц параллельно сортируются по ключу JOIN и могут сбрасываться во временное хранилище; по одному потоку сортировки слиянием на каждую таблицу передают данные на единственную стадию соединения слиянием](/images/guides/join-algorithms/full-sorting-merge-join.png)
  </Frame>
</div>

Алгоритм `full_sorting_merge` — это JOIN методом сортировки и слияния. ClickHouse сортирует оба входа по ключу JOIN и находит совпадения, попеременно просматривая два отсортированных потока. Сортировка выполняется в памяти, а для больших входных данных — как внешняя сортировка на диске. Если вход читается в порядке ключа JOIN (например, потому что ключ является префиксом ключа сортировки таблицы `MergeTree`), ClickHouse пропускает сортировку для этого входа.

**Когда используется.** Алгоритм подходит, если одна или обе таблицы физически упорядочены по ключу JOIN или если входные данные слишком велики для хеш-таблицы в памяти. Он поддерживает `INNER`, `LEFT`, `RIGHT` и `FULL` JOIN со строгостью `ALL`, `INNER`, `LEFT` и `RIGHT` JOIN со строгостью `ANY`, а также `INNER` и `LEFT` JOIN со строгостью `ASOF`.

Стадия слияния выполняется в одном потоке. Распараллелить её можно двумя способами:

* [`query_plan_join_shard_by_pk_ranges`](/ru/reference/settings/session-settings/query-plan#query_plan_join_shard_by_pk_ranges) разбивает JOIN двух таблиц `MergeTree` на независимые JOIN слиянием по диапазонам первичного ключа, если ключи соединения содержат префикс первичного ключа обеих таблиц.
* Значение `parallel_full_sorting_merge` настройки [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm) распределяет входные данные по сегментам на основе хеша ключа JOIN и выполняет отдельный JOIN слиянием для каждого сегмента. Результат не упорядочен. В справочнике по настройке перечислены случаи, когда вместо этого выполняется один JOIN `full_sorting_merge`.

Настройка [`max_rows_in_set_to_optimize_join`](/ru/reference/settings/session-settings/max-rows#max_rows_in_set_to_optimize_join) позволяет перед сортировкой отфильтровать каждый вход по множеству ключей JOIN другого входа. Такой фильтр исключает оптимизацию чтения в порядке ключа.

**Память и сброс данных на диск.** Потребление памяти определяется сортировкой. Если оба входа читаются в порядке ключа, в памяти одновременно находится лишь несколько блоков. В противном случае сортировка сбрасывает данные на диск в соответствии с настройками [`max_bytes_before_external_sort`](/ru/reference/settings/session-settings/max-bytes#max_bytes_before_external_sort) и [`max_bytes_ratio_before_external_sort`](/ru/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_sort).

**Ограничения.** Алгоритм не поддерживает строгость `SEMI` и `ANTI`, несколько ключей JOIN, объединённых через `OR`, условия в предложении `ON`, кроме ключей равенства, правую часть со специальным хранилищем, а также `USING` совместно с `join_use_nulls`. Указание алгоритма в `join_algorithm` влияет на планирование запроса, даже если JOIN выполняется другим алгоритмом. См. [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm).

## `partial_merge` {#partial-merge}

<div className="ch-image-lg">
  <Frame>
    ![Конвейер JOIN с частичным слиянием: блоки правой таблицы сортируются и записываются во временное хранилище вместе с индексом min-max для каждого блока; блоки левой таблицы сортируются в памяти и соединяются с сохранёнными блоками правой стороны](/images/guides/join-algorithms/partial-merge-join.png)
  </Frame>
</div>

Алгоритм `partial_merge` — это разновидность JOIN методом сортировки и слияния, в которой полностью сортируется только правая сторона. ClickHouse разбивает правую сторону на блоки размером до [`partial_merge_join_rows_in_right_blocks`](/ru/reference/settings/session-settings/partial-merge#partial_merge_join_rows_in_right_blocks) строк, сортирует каждый блок по ключу соединения и создаёт для каждого блока индекс min-max. Затем каждый блок левой стороны сортируется в памяти и сливается с блоками правой стороны. Индекс min-max позволяет пропускать блоки правой стороны, в которых заведомо нет совпадений.

**Когда используется.** Алгоритм рассчитан на минимальное потребление памяти при соединении больших таблиц ценой скорости выполнения. Он наиболее эффективен, когда физический порядок строк левой стороны совпадает с порядком ключа соединения: в этом случае индекс min-max позволяет пропустить большинство блоков правой стороны. Наименее эффективен он, когда каждый блок левой стороны охватывает широкий диапазон значений ключа. При значении `auto` настройки `join_algorithm` ClickHouse может переключиться на `partial_merge` во время выполнения. Алгоритм поддерживает JOIN типов `INNER`, `LEFT`, `RIGHT` и `FULL` со строгостью `ALL`, JOIN типов `INNER` и `LEFT` со строгостью `ANY`, а также JOIN типа `LEFT` со строгостью `SEMI`.

**Память и сброс данных на диск.** ClickHouse хранит отсортированные блоки правой стороны в памяти, пока не будет достигнут лимит [`max_rows_in_join`](/ru/reference/settings/session-settings/max-rows#max_rows_in_join) или [`max_bytes_in_join`](/ru/reference/settings/session-settings/max-bytes#max_bytes_in_join). Если ни один из них не задан, применяется [`default_max_bytes_in_join`](/ru/reference/settings/session-settings/default#default_max_bytes_in_join). После этого ClickHouse записывает отсортированные блоки и их индексы во временное хранилище. Настройка [`join_on_disk_max_files_to_merge`](/ru/reference/settings/session-settings/join#join_on_disk_max_files_to_merge) ограничивает число файлов, сливаемых параллельно.

**Ограничения.** JOIN типов `RIGHT` и `FULL` поддерживаются только со строгостью `ALL`. Строгость `ANTI` и `ASOF`, несколько ключей соединения, объединённых через `OR`, а также условия, сравнивающие столбцы обеих таблиц, не поддерживаются.

## `inequality` {#inequality}

Алгоритм `inequality` реализует основанный на сортировке алгоритм [соединения по неравенству](https://vldb.org/pvldb/vol8/p2074-khayyat.pdf), также известный как IEJoin, для JOIN, у которого предложение `ON` содержит два сравнения-неравенства (`<`, `<=`, `>` или `>=`) между выражениями соединяемых таблиц. ClickHouse сортирует оба входных набора по выражениям этих двух сравнений и находит совпадающие пары, не сравнивая все пары строк между собой. Алгоритм доступен начиная с версии 26.8. До версии 26.12 он назывался `ie_join`; это имя по-прежнему принимается.

**Когда используется.** Приоритет алгоритма определяется его позицией в `join_algorithm`:

* Если он указан после других алгоритмов, он используется, только когда предложение `ON` не содержит условий равенства между таблицами.
* Если он указан первым, он используется всегда, когда предложение `ON` содержит два условия неравенства. Остальные условия, включая условия равенства, применяются как фильтр к результату JOIN или как остаточное условие внутри оператора. Равенство, применяемое таким образом, вычисляется с помощью `equals`, а не как ключ соединения. См. [Сравнение ключей соединения](#comparison-of-join-keys).

Если предложение `ON` содержит более двух подходящих условий неравенства, ClickHouse выбирает два ключевых условия по их оценочной селективности на основе статистики столбцов. Если статистики нет, используются первые два условия в порядке их записи. Алгоритм поддерживает `INNER`, `LEFT`, `RIGHT` и `FULL` JOIN со строгостью `ALL`, а также `LEFT` и `RIGHT` JOIN со строгостью `SEMI` и `ANTI`.

**Память и сброс данных на диск.** Перед соединением оба входных набора накапливаются в памяти, и [жёсткие лимиты](/ru/concepts/features/operations/select/join-memory-management#hard-limits) применяются к обеим сторонам в сумме. Сброс данных на диск алгоритм не выполняет.

**Ограничения.** Оператор JOIN выполняется в одном потоке; параллельно выполняются только сортировки входных наборов. Строгость `ANY` и `ASOF` не поддерживается.

## Резервный вариант — блочный JOIN с вложенными циклами {#block-nested-loop-fallback}

Блочный JOIN с вложенными циклами выполняет JOIN, предложение `ON` которого не содержит условия равенства между таблицами и который не может выполнить ни один другой алгоритм. ClickHouse материализует правую часть и вычисляет условие `ON` для каждой пары из строки левой части и строки правой части. Равенство внутри условия, например `t1.a = t2.a` в `t1.a = t2.a OR t1.b < 0`, вычисляется с помощью `equals`, а не как ключ JOIN. См. [Сравнение ключей JOIN](#comparison-of-join-keys). Это не значение `join_algorithm`, а крайняя мера при планировании соединений.

**Когда используется.** Применяется к предложению `ON`, представляющему собой произвольное булево выражение над столбцами обеих таблиц, например проверку диапазона или вызов функции, если `inequality` неприменим. Если `hash` указан в `join_algorithm`, то `INNER` JOIN со строгостью `ALL` вместо этого выполняется как `CROSS JOIN` с условием в качестве фильтра. Переход на резервный вариант доступен начиная с версии 26.10. Возможность его использования определяется настройкой [`allow_block_nested_loop_join`](/ru/reference/settings/session-settings/allow#allow_block_nested_loop_join). Если переход на резервный вариант запрещён, такой запрос отклоняется с ошибкой `INVALID_JOIN_ON_EXPRESSION`. Поддерживаются все типы соединения и все виды строгости, кроме `ASOF`, `PASTE` и `ANY FULL`.

**Память и сброс данных на диск.** Объём потребляемой памяти ограничен материализованной правой частью и не зависит от размера результата. Блоки правой части хранятся в памяти в сжатом виде и записываются на диск после достижения порога сброса на диск. [Жёсткие лимиты](/ru/concepts/features/operations/select/join-memory-management#hard-limits) распространяются на правую часть, включая выгруженные на диск блоки.

**Ограничения.** Стоимость растёт пропорционально произведению количества строк обеих таблиц. Этот алгоритм на порядки дороже, чем hash JOIN на тех же данных. Подробнее о семантике строгости см. [JOIN с произвольным условием ON](/ru/reference/statements/select/join#join-with-an-arbitrary-on-condition).

## Типы соединения, поддерживаемые каждым алгоритмом {#supported-join-types-per-algorithm}

В следующей таблице перечислены типы соединения, которые поддерживает каждый алгоритм при каждом значении строгости. Таблица составлена на основе проверок поддержки в исходном коде ClickHouse. Пустая ячейка означает, что данная строгость не поддерживается.

| Алгоритм                                            | `ALL`                            | `ANY`                    | `SEMI`          | `ANTI`          | `ASOF`          |
| --------------------------------------------------- | -------------------------------- | ------------------------ | --------------- | --------------- | --------------- |
| `direct`                                            | `INNER`, `LEFT`                  | `LEFT`                   | `LEFT`          | `LEFT`          |                 |
| `hash`, `parallel_hash`                             | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `INNER`, `LEFT` |
| `grace_hash`                                        | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` |                 |
| `full_sorting_merge`, `parallel_full_sorting_merge` | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` |                 |                 | `INNER`, `LEFT` |
| `partial_merge`                                     | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`          | `LEFT`          |                 |                 |
| `inequality`                                        | `INNER`, `LEFT`, `RIGHT`, `FULL` |                          | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` |                 |
| Резервный вариант — блочный JOIN с вложенными циклами                | `INNER`, `LEFT`, `RIGHT`, `FULL` | `INNER`, `LEFT`, `RIGHT` | `LEFT`, `RIGHT` | `LEFT`, `RIGHT` |                 |

Кроме того, действуют следующие правила:

* Соединения типа `ANY FULL` отклоняются ещё до выбора алгоритма, независимо от того, какой алгоритм используется.
* Соединения типа `ASOF` поддерживаются только алгоритмами `hash` и `full_sorting_merge`. `parallel_full_sorting_merge` выполняет `ASOF` JOIN как единый JOIN `full_sorting_merge`.
* `partial_merge` поддерживает соединения типов `RIGHT` и `FULL` только при строгости `ALL`.
* Резервный вариант — блочный JOIN с вложенными циклами не поддерживает соединения типов `ASOF`, `PASTE` и `ANY FULL`.
* Только `hash` и его псевдоним `parallel_hash` поддерживают несколько ключей соединения, объединённых через `OR` в предложении `ON`. При значении `auto` такие JOIN выполняются с помощью `hash`.
* Только `hash`, `parallel_hash` и `grace_hash` поддерживают ключ равенства в сочетании с условием, сравнивающим столбцы обеих таблиц.
* Алгоритм `direct` применим только к правым частям, перечисленным в разделе [`direct`](#direct). Для таблиц `MergeTree` он не поддерживает строгость `ANY`.
* `CROSS JOIN`, JOIN с постоянным условием `ON` и `PASTE JOIN` имеют собственные реализации, не зависящие от `join_algorithm`.

## Сравнение ключей соединения {#comparison-of-join-keys}

Все алгоритмы, кроме `inequality` и резервного варианта — блочного JOIN с вложенными циклами, используют в качестве ключа соединения равенство между столбцами обеих таблиц в предложении `ON`. Алгоритм сравнивает ключи самостоятельно, а не с помощью функции [`equals`](/ru/reference/functions/regular-functions/comparison-functions#equals), поэтому ключи совпадают и для некоторых пар значений, для которых `equals` не возвращает `1`. `inequality` вычисляет такое равенство с помощью `equals` для пар, отобранных двумя его условиями неравенства, а резервный вариант — блочный JOIN с вложенными циклами вычисляет его с помощью `equals` в составе условия `ON`.

| Алгоритм                                                             | Равенство между таблицами | Два значения `NaN`                                     | Два значения `Tuple` `(1, NULL)` |
| -------------------------------------------------------------------- | ------------------------- | ------------------------------------------------------ | -------------------------------- |
| `direct`, `hash`, `parallel_hash`, `grace_hash`                      | Ключ соединения                 | Совпадают, если у них одинаковое битовое представление | Совпадают                        |
| `full_sorting_merge`, `parallel_full_sorting_merge`, `partial_merge` | Ключ соединения                 | Совпадают                                              | Совпадают                        |
| `inequality`                                                         | `equals`                  | Не совпадают                                           | Не совпадают                     |
| Резервный вариант — блочный JOIN с вложенными циклами                       | `equals`                  | Не совпадают                                           | Не совпадают                     |

Значение `NULL` ключа типа `Variant` ведёт себя так же, как `Tuple` с элементом `NULL`. Ключ, который сам равен `NULL`, не совпадает ни при каком алгоритме — так же, как и при использовании `equals`. См. [Значения NULL и NaN в ключах соединения](/ru/reference/statements/select/join#null-values-in-join-keys).

Условия равенства в `ASOF` JOIN ведут себя согласно строке `hash` или `full_sorting_merge` — в зависимости от того, какой алгоритм его выполняет, а при правой части с движком таблицы `Join` действует строка `hash`.

`direct` JOIN со словарём, имеющим структуру `complex_key_direct`, `complex_key_cache` или `complex_key_ssd_cache` и источник `CLICKHOUSE`, передаёт ключи в источник в виде текста, в котором каждое `NaN` записывается как `nan`, поэтому два ключа `NaN` совпадают, только если оба имеют битовое представление `nan`. При ненулевом значении [`max_rows_in_set_to_optimize_join`](/ru/reference/settings/session-settings/max-rows#max_rows_in_set_to_optimize_join) алгоритмы `full_sorting_merge` и `parallel_full_sorting_merge` могут предварительно фильтровать входные данные по множеству ключей соединения, в котором значения `NaN` сравниваются по битовому представлению, поэтому результат сравнения двух значений `NaN` с разным битовым представлением может меняться от запуска к запуску.

Таким образом, JOIN, сравнивающий такие значения, может возвращать разные строки в зависимости от того, какой алгоритм его выполняет. Например, если указать `inequality` первым в `join_algorithm`, он может выполнить JOIN, содержащий равенство наряду с двумя условиями неравенства, и тогда равенство вычисляется с помощью `equals`, а не как ключ соединения.

## Настройка `join_algorithm` {#join-algorithm-setting}

Настройка [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm) принимает список алгоритмов через запятую. Значение по умолчанию и все допустимые значения приведены в справочнике по [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm).

ClickHouse перебирает перечисленные алгоритмы по порядку и выбирает первый, который поддерживает тип соединения, строгость, условие `ON` и хранилище правой части. Если ни один из перечисленных алгоритмов не подходит, запрос завершается ошибкой со списком включенных алгоритмов. Следующие случаи не зависят от порядка алгоритмов в списке:

* Если правая часть использует движок таблицы `Join`, соединение всегда выполняется с помощью хеш-таблицы, хранящейся в этой таблице.
* Для `CROSS JOIN`, JOIN с постоянным условием `ON` и `PASTE JOIN` используются специальные реализации.
* Предложение `ON` без условия равенства между таблицами обрабатывается алгоритмом `inequality` либо резервным вариантом — блочным JOIN с вложенными циклами.

Если действует порог сброса на диск и настроено временное хранилище, `parallel_hash` и `hash` работают как hash JOIN со сбросом данных на диск и переключаются на `grace_hash`, когда правая часть превышает порог. См. раздел [Пороги сброса на диск](/ru/concepts/features/operations/select/join-memory-management#spill-thresholds).

### Значение `auto` {#the-auto-value}

При `join_algorithm = 'auto'` ClickHouse выбирает реализацию следующим образом:

1. Если действует порог сброса на диск, настроено временное хранилище и `grace_hash` поддерживает данный JOIN, ClickHouse использует hash JOIN, который переключается на `grace_hash`, когда правая часть превышает порог.
2. Иначе, если `partial_merge` поддерживает данный JOIN, ClickHouse начинает с `hash` и переключается на `partial_merge`, когда правая часть достигает [жёсткого лимита](/ru/concepts/features/operations/select/join-memory-management#hard-limits). Строки, уже находящиеся в хеш-таблице, переносятся в JOIN `partial_merge`.
3. В остальных случаях ClickHouse использует `hash`.

В выводе `EXPLAIN` второй случай отображается как `Algorithm: JoinSwitcher`.
