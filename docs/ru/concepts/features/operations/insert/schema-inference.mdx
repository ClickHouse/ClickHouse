ClickHouse может автоматически определять структуру входных данных практически во всех поддерживаемых [входных форматах](/ru/reference/formats/index).
В этом документе описывается, когда применяется автоматическое определение схемы, как оно работает с различными входными форматами и какие настройки
позволяют им управлять.

## Использование {#usage}

Автоматическое определение схемы используется, когда ClickHouse нужно прочитать данные в определённом формате данных, а их структура неизвестна.

## Табличные функции [file](/ru/reference/functions/table-functions/file), [s3](/ru/reference/functions/table-functions/s3), [url](/ru/reference/functions/table-functions/url), [hdfs](/ru/reference/functions/table-functions/hdfs), [azureBlobStorage](/ru/reference/functions/table-functions/azureBlobStorage). {#table-functions-file-s3-url-hdfs-azureblobstorage}

У этих табличных функций есть необязательный аргумент `structure`, задающий структуру входных данных. Если этот аргумент не указан или имеет значение `auto`, структура автоматически определяется по данным.

**Пример:**

Предположим, что в каталоге `user_files` находится файл `hobbies.jsonl` в формате JSONEachRow со следующим содержимым:

```json
{"id" :  1, "age" :  25, "name" :  "Josh", "hobbies" :  ["football", "cooking", "music"]}
{"id" :  2, "age" :  19, "name" :  "Alan", "hobbies" :  ["tennis", "art"]}
{"id" :  3, "age" :  32, "name" :  "Lana", "hobbies" :  ["fitness", "reading", "shopping"]}
{"id" :  4, "age" :  47, "name" :  "Brayan", "hobbies" :  ["movies", "skydiving"]}
```

ClickHouse может прочитать эти данные без явного указания их структуры:

```sql
SELECT * FROM file('hobbies.jsonl')
```

```response
┌─id─┬─age─┬─name───┬─hobbies──────────────────────────┐
│  1 │  25 │ Josh   │ ['football','cooking','music']   │
│  2 │  19 │ Alan   │ ['tennis','art']                 │
│  3 │  32 │ Lana   │ ['fitness','reading','shopping'] │
│  4 │  47 │ Brayan │ ['movies','skydiving']           │
└────┴─────┴────────┴──────────────────────────────────┘
```

Примечание: формат `JSONEachRow` был автоматически определён по расширению файла `.jsonl`.

Автоматически определённую структуру можно посмотреть с помощью запроса `DESCRIBE`:

```sql
DESCRIBE file('hobbies.jsonl')
```

```response
┌─name────┬─type────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ id      │ Nullable(Int64)         │              │                    │         │                  │                │
│ age     │ Nullable(Int64)         │              │                    │         │                  │                │
│ name    │ Nullable(String)        │              │                    │         │                  │                │
│ hobbies │ Array(Nullable(String)) │              │                    │         │                  │                │
└─────────┴─────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## Движки таблиц [File](/ru/reference/engines/table-engines/special/file), [S3](/ru/reference/engines/table-engines/integrations/s3), [URL](/ru/reference/engines/table-engines/special/url), [HDFS](/ru/reference/engines/table-engines/integrations/hdfs), [azureBlobStorage](/ru/reference/engines/table-engines/integrations/azureBlobStorage) {#table-engines-file-s3-url-hdfs-azureblobstorage}

Если в запросе `CREATE TABLE` не указан список столбцов, структура таблицы будет автоматически определена на основе данных.

**Пример:**

Возьмём файл `hobbies.jsonl`. Создадим таблицу с движком `File` на основе данных из этого файла:

```sql
CREATE TABLE hobbies ENGINE=File(JSONEachRow, 'hobbies.jsonl')
```


```sql
SELECT * FROM hobbies
```


## clickhouse-local {#clickhouse-local}

У `clickhouse-local` есть необязательный параметр `-S/--structure`, задающий структуру входных данных. Если этот параметр не указан или имеет значение `auto`, структура будет автоматически определена по данным.

**Пример:**

Возьмём файл `hobbies.jsonl`. Выполним запрос к данным из этого файла с помощью `clickhouse-local`:

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='DESCRIBE TABLE hobbies'
```

```response
id    Nullable(Int64)
age    Nullable(Int64)
name    Nullable(String)
hobbies    Array(Nullable(String))
```

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='SELECT * FROM hobbies'
```

```response
1    25    Josh    ['football','cooking','music']
2    19    Alan    ['tennis','art']
3    32    Lana    ['fitness','reading','shopping']
4    47    Brayan    ['movies','skydiving']
```

## Использование структуры из таблицы для вставки {#using-structure-from-insertion-table}

Когда табличные функции `file/s3/url/hdfs` используются для вставки данных в таблицу,
можно взять структуру из таблицы для вставки вместо того, чтобы извлекать её из данных.
Это может повысить производительность вставки, поскольку автоматическое определение схемы может занимать некоторое время. Кроме того, это полезно, когда у таблицы оптимизированная схема: в этом случае
преобразования между типами выполняться не будут.

Это поведение управляется специальной настройкой [use&#95;structure&#95;from&#95;insertion&#95;table&#95;in&#95;table&#95;functions](/ru/reference/settings/session-settings/use#use_structure_from_insertion_table_in_table_functions).
У неё есть 3 возможных значения:

* 0 — табличная функция извлекает структуру из данных.
* 1 — табличная функция использует структуру из таблицы для вставки.
* 2 — ClickHouse автоматически определяет, можно ли использовать структуру из таблицы для вставки или нужно применить автоматическое определение схемы. Значение по умолчанию.

**Пример 1:**

Создадим таблицу `hobbies1` со следующей структурой:

```sql
CREATE TABLE hobbies1
(
    `id` UInt64,
    `age` LowCardinality(UInt8),
    `name` String,
    `hobbies` Array(String)
)
ENGINE = MergeTree
ORDER BY id;
```

Затем вставим данные из файла `hobbies.jsonl`:

```sql
INSERT INTO hobbies1 SELECT * FROM file(hobbies.jsonl)
```

В этом случае все столбцы из файла вставляются в таблицу без изменений, поэтому ClickHouse будет использовать structure таблицы для вставки вместо автоматического определения схемы.

**Пример 2:**

Создадим таблицу `hobbies2` со следующей structure:

```sql
CREATE TABLE hobbies2
(
  `id` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

Затем вставьте данные из файла `hobbies.jsonl`:

```sql
INSERT INTO hobbies2 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

В этом случае все столбцы из `SELECT`-запроса присутствуют в таблице, поэтому ClickHouse будет использовать структуру таблицы для вставки.
Обратите внимание, что это работает только для входных форматов, которые поддерживают чтение подмножества столбцов, таких как JSONEachRow, TSKV, Parquet и т. д. (например, для формата TSV это работать не будет).

**Пример 3:**

Создадим таблицу `hobbies3` со следующей структурой:

```sql
CREATE TABLE hobbies3
(
  `identifier` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY identifier;
```

Затем вставьте данные из файла `hobbies.jsonl`:

```sql
INSERT INTO hobbies3 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

В этом случае в `SELECT`-запросе используется столбец `id`, но в таблице такого столбца нет (в ней есть столбец с именем `identifier`),
поэтому ClickHouse не может использовать structure из таблицы для вставки, и будет применено автоматическое определение схемы.

**Пример 4:**

Создадим таблицу `hobbies4` со следующей структурой:

```sql
CREATE TABLE hobbies4
(
  `id` UInt64,
  `any_hobby` Nullable(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

Затем вставьте данные из файла `hobbies.jsonl`:

```sql
INSERT INTO hobbies4 SELECT id, empty(hobbies) ? NULL : hobbies[1] FROM file(hobbies.jsonl)
```

В данном случае в `SELECT`-запросе над столбцом `hobbies` перед вставкой в таблицу выполняются некоторые операции, поэтому ClickHouse не может использовать structure из таблицы для вставки, и будет применено автоматическое определение схемы.

## Кэш автоматического определения схемы {#schema-inference-cache}

Для большинства входных форматов автоматическое определение схемы считывает часть данных, чтобы определить их структуру, и этот процесс может занять некоторое время.
Чтобы не определять одну и ту же схему каждый раз, когда ClickHouse читает данные из одного и того же файла, автоматически определённая схема кэшируется, и при повторном обращении к тому же файлу ClickHouse использует схему из кэша.

Этим кэшем управляют специальные настройки:

* `schema_inference_cache_max_elements_for_{file/s3/hdfs/url/azure}` — максимальное количество кэшированных схем для соответствующей табличной функции. Значение по умолчанию — `4096`. Эти настройки следует задавать в конфигурации сервера.
* `schema_inference_use_cache_for_{file,s3,hdfs,url,azure}` — позволяет включать и отключать использование кэша при автоматическом определении схемы. Эти настройки можно использовать в запросах.

Схема файла может измениться при изменении данных или настроек формата.
Поэтому кэш автоматического определения схемы идентифицирует схему по источнику файла, названию формата, используемым настройкам формата и времени последнего изменения файла.

Примечание: для некоторых файлов, к которым обращается табличная функция `url`, информация о времени последнего изменения может отсутствовать; для этого случая предусмотрена специальная настройка
`schema_inference_cache_require_modification_time_for_url`. Если её отключить, для таких файлов схема из кэша будет использоваться без учёта времени последнего изменения.

Также существует системная таблица [schema&#95;inference&#95;cache](/ru/reference/system-tables/schema_inference_cache), содержащая все текущие схемы в кэше, и системный запрос `SYSTEM CLEAR SCHEMA CACHE [FOR File/S3/URL/HDFS]`,
который позволяет очистить кэш схем для всех источников или для конкретного источника.

## Текстовые форматы {#text-formats}

Для текстовых форматов ClickHouse читает данные построчно, извлекает значения столбцов в соответствии с форматом,
а затем с помощью рекурсивных парсеров и эвристик определяет тип каждого значения. Максимальное количество строк и байтов, считываемых из данных при автоматическом определении схемы,
задаётся настройками `input_format_max_rows_to_read_for_schema_inference` (по умолчанию 25000) и `input_format_max_bytes_to_read_for_schema_inference` (по умолчанию 32Mb).
По умолчанию все выведенные типы являются [Nullable](/ru/reference/data-types/nullable), но это можно изменить с помощью настройки `schema_inference_make_columns_nullable` (см. примеры в разделе [Настройки](#settings-for-text-formats)).

### Форматы JSON {#json-formats}

В форматах JSON ClickHouse разбирает значения в соответствии со спецификацией JSON, а затем пытается подобрать для них наиболее подходящий тип данных.

Рассмотрим, как это работает, какие типы могут быть автоматически определены и какие специальные настройки можно использовать в форматах JSON.

**Примеры**

Здесь и далее в примерах будет использоваться табличная функция [format](/ru/reference/functions/table-functions/format).

Целые числа, числа с плавающей точкой, булевы значения, строки:

```sql
DESC format(JSONEachRow, '{"int" : 42, "float" : 42.42, "string" : "Hello, World!"}');
```

```response
│ float  │ Nullable(Float64) │              │                    │         │                  │                │
│ bool   │ Nullable(Bool)    │              │                    │         │                  │                │
│ string │ Nullable(String)  │              │                    │         │                  │                │
└────────┴───────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

Массивы:

Если массив содержит `null`, ClickHouse использует типы остальных элементов массива:

```sql
SET input_format_json_infer_array_of_dynamic_from_array_of_different_types=1;
```

Именованные кортежи:

Если включена настройка `input_format_json_try_infer_named_tuples_from_objects`, то при автоматическом определении схемы ClickHouse будет пытаться определить именованный Tuple на основе объектов JSON.
Полученный именованный Tuple будет содержать все элементы из всех соответствующих объектов JSON в выборке данных.

```sql
SET input_format_json_try_infer_named_tuples_from_objects = 1;
DESC format(JSONEachRow, '{"obj" : {"a" : 42, "b" : "Hello"}}, {"obj" : {"a" : 43, "c" : [1, 2, 3]}}, {"obj" : {"d" : {"e" : 42}}}')
```

```sql
SET input_format_json_infer_array_of_dynamic_from_array_of_different_types = 0;
```


```sql
SET input_format_json_infer_array_of_dynamic_from_array_of_different_types=0;
DESC format(JSONEachRow, $$
```


В JSON объекты, все значения которых имеют один и тот же тип, можно считывать как тип Map.
Примечание: это работает, только если настройки `input_format_json_read_objects_as_strings` и `input_format_json_try_infer_named_tuples_from_objects` отключены.




##### input_format_json_try_infer_named_tuples_from_objects {#input_format_json_try_infer_named_tuples_from_objects}

Включение этой настройки позволяет автоматически определять именованные Кортежи (Tuple) на основе объектов JSON. Полученный именованный Кортеж будет содержать все элементы из всех соответствующих объектов JSON в выборке данных.
Это может быть полезно, если данные JSON не являются разреженными, то есть выборка данных будет содержать все возможные ключи объектов.

Эта настройка включена по умолчанию.

**Пример**

```sql title="Query"
SET input_format_json_try_infer_named_tuples_from_objects = 1;
DESC format(JSONEachRow, '{"obj" : {"a" : 42, "b" : "Hello"}}, {"obj" : {"a" : 43, "c" : [1, 2, 3]}}, {"obj" : {"d" : {"e" : 42}}}')
```

```response title="Response"
┌─name─┬─type───────────────────────────────────────────────────────────────────────────────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ obj  │ Tuple(a Nullable(Int64), b Nullable(String), c Array(Nullable(Int64)), d Tuple(e Nullable(Int64))) │              │                    │         │                  │                │
└──────┴────────────────────────────────────────────────────────────────────────────────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

```sql title="Query"
SET input_format_json_try_infer_named_tuples_from_objects = 1;
DESC format(JSONEachRow, '{"array" : [{"a" : 42, "b" : "Hello"}, {}, {"c" : [1,2,3]}, {"d" : "2020-01-01"}]}')
```

```markdown title="Response"
┌─name──┬─type────────────────────────────────────────────────────────────────────────────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ array │ Array(Tuple(a Nullable(Int64), b Nullable(String), c Array(Nullable(Int64)), d Nullable(Date))) │              │                    │         │                  │                │
```

##### input_format_json_use_string_type_for_ambiguous_paths_in_named_tuples_inference_from_objects {#input_format_json_use_string_type_for_ambiguous_paths_in_named_tuples_inference_from_objects}

Если эта настройка включена, то при автоматическом определении именованных Кортежей из объектов JSON (когда включена настройка `input_format_json_try_infer_named_tuples_from_objects`) для неоднозначных путей используется тип String, а не выбрасывается исключение.
Это позволяет читать объекты JSON как именованные Кортежи даже при наличии неоднозначных путей.

По умолчанию отключено.

**Примеры**

При отключённой настройке:

```sql title="Query"
SET input_format_json_try_infer_named_tuples_from_objects = 1;
SET input_format_json_use_string_type_for_ambiguous_paths_in_named_tuples_inference_from_objects = 0;
DESC format(JSONEachRow, '{"obj" : {"a" : 42}}, {"obj" : {"a" : {"b" : "Hello"}}}');
```


С включённой настройкой:

```sql title="Query"
SET input_format_json_try_infer_named_tuples_from_objects = 1;
SET input_format_json_use_string_type_for_ambiguous_paths_in_named_tuples_inference_from_objects = 1;
DESC format(JSONEachRow, '{"obj" : "a" : 42}, {"obj" : {"a" : {"b" : "Hello"}}}');
```

##### input_format_json_infer_incomplete_types_as_strings {#input_format_json_infer_incomplete_types_as_strings}

Включение этой настройки позволяет использовать тип String для ключей JSON, которые в выборке данных содержат только `Null`/`{}`/`[]`, при автоматическом определении схемы.
В форматах JSON любое значение может быть прочитано как String, если включены все соответствующие настройки (по умолчанию все они включены). Поэтому, используя тип String для ключей с неизвестными типами, можно избежать при автоматическом определении схемы ошибок вида `Cannot determine type for column 'column_name' by first 25000 rows of data, most likely this column contains only Nulls or empty Arrays/Maps`.

Пример:

```sql title="Query"
SET input_format_json_infer_incomplete_types_as_strings = 1, input_format_json_try_infer_named_tuples_from_objects = 1;
DESCRIBE format(JSONEachRow, '{"obj" : {"a" : [1,2,3], "b" : "hello", "c" : null, "d" : {}, "e" : []}}');
SELECT * FROM format(JSONEachRow, '{"obj" : {"a" : [1,2,3], "b" : "hello", "c" : null, "d" : {}, "e" : []}}');
```

```markdown title="Response"
┌─name─┬─type───────────────────────────────────────────────────────────────────────────────────────────────────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ obj  │ Tuple(a Array(Nullable(Int64)), b Nullable(String), c Nullable(String), d Nullable(String), e Array(Nullable(String))) │              │                    │         │                  │                │
└──────┴────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘

┌─obj────────────────────────────┐
│ ([1,2,3],'hello',NULL,'{}',[]) │
└────────────────────────────────┘
```

### CSV {#csv}

В формате CSV ClickHouse извлекает значения столбцов из строки по разделителям. ClickHouse ожидает, что значения всех типов, кроме чисел и строк, заключены в двойные кавычки. Если значение заключено в двойные кавычки, ClickHouse пытается разобрать
данные внутри кавычек с помощью рекурсивного парсера, а затем подобрать для них наиболее подходящий тип данных. Если значение не заключено в двойные кавычки, ClickHouse пытается разобрать его как число,
а если значение не является числом, ClickHouse интерпретирует его как строку.

Если вы не хотите, чтобы ClickHouse пытался определять сложные типы с помощью парсеров и эвристик, отключите настройку `input_format_csv_use_best_effort_in_schema_inference`,
и ClickHouse будет интерпретировать все столбцы как строки.

Если включена настройка `input_format_csv_detect_header`, при автоматическом определении схемы ClickHouse попытается обнаружить заголовок с именами столбцов (и, возможно, их типами). Эта настройка включена по умолчанию.

#### Настройки CSV {#csv-settings}

##### input_format_csv_try_infer_numbers_from_strings {#input_format_csv_try_infer_numbers_from_strings}

Если эта настройка включена, числа могут автоматически определяться по строковым значениям.

По умолчанию эта настройка отключена.

**Пример:**

```sql
SET input_format_json_try_infer_numbers_from_strings = 1;
DESC format(CSV, '42,42.42');
```

```response

│ c2   │ Nullable(Float64) │              │                    │         │                  │                │
└──────┴───────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### TSV/TSKV {#tsv-tskv}

В форматах TSV/TSKV ClickHouse извлекает значение столбца из строки по символам табуляции, а затем разбирает извлечённое значение с помощью
рекурсивного парсера, чтобы определить наиболее подходящий тип. Если определить тип не удаётся, ClickHouse считает значение строкой типа String.

Если вы не хотите, чтобы ClickHouse пытался определять сложные типы с помощью парсеров и эвристик, отключите настройку `input_format_tsv_use_best_effort_in_schema_inference`,
и ClickHouse будет считать все столбцы строками (String).

Если включена настройка `input_format_tsv_detect_header`, при автоматическом определении схемы ClickHouse попытается обнаружить заголовок с именами столбцов (и, возможно, их типами). Эта настройка включена по умолчанию.

### Значения {#values}

В формате Values ClickHouse извлекает значение столбца из строки, а затем разбирает его с помощью
рекурсивного парсера аналогично тому, как разбираются литералы.

### CustomSeparated {#custom-separated}

В формате CustomSeparated ClickHouse сначала извлекает из строки все значения столбцов в соответствии с заданными разделителями, а затем пытается автоматически определить
тип данных каждого значения согласно правилу экранирования.

Если включена настройка `input_format_custom_detect_header`, при автоматическом определении схемы ClickHouse попытается обнаружить заголовок с именами столбцов (и, возможно, их типами). По умолчанию эта настройка включена.

**Пример**

```sql
SET format_custom_row_before_delimiter = '<row_before_delimiter>',
       format_custom_row_after_delimiter = '<row_after_delimiter>\n',
       format_custom_row_between_delimiter = '<row_between_delimiter>\n',
       format_custom_result_before_delimiter = '<result_before_delimiter>\n',
       format_custom_result_after_delimiter = '<result_after_delimiter>\n',
       format_custom_field_delimiter = '<field_delimiter>',
       format_custom_escaping_rule = 'Quoted'

DESC format(CustomSeparated, $$<result_before_delimiter>
<row_before_delimiter>42.42<field_delimiter>'Some string 1'<field_delimiter>[1, NULL, 3]<row_after_delimiter>
<row_between_delimiter>
<row_before_delimiter>NULL<field_delimiter>'Some string 3'<field_delimiter>[1, 2, NULL]<row_after_delimiter>
<result_after_delimiter>
$$)
```

```response
┌─name─┬─type───────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ c1   │ Nullable(Float64)      │              │                    │         │                  │                │
│ c2   │ Nullable(String)       │              │                    │         │                  │                │
│ c3   │ Array(Nullable(Int64)) │              │                    │         │                  │                │
└──────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

Пример автоматического определения заголовка (при включенном параметре `input_format_custom_detect_header`):

```sql

<row_between_delimiter>
```

### Template {#template}

В формате Template ClickHouse сначала извлекает все значения столбцов из строки согласно заданному шаблону, а затем пытается автоматически определить
тип данных каждого значения согласно его правилу экранирования.

**Пример**

Предположим, у нас есть файл `resultset` со следующим содержимым:

```bash
<result_before_delimiter>
${data}<result_after_delimiter>
```

И файл `row_format` со следующим содержимым:

```text
<row_before_delimiter>${column_1:CSV}<field_delimiter_1>${column_2:Quoted}<field_delimiter_2>${column_3:JSON}<row_after_delimiter>
```

Затем можно выполнить следующие запросы:

```sql
SET format_template_rows_between_delimiter = '<row_between_delimiter>\n',
       format_template_row = 'row_format',
       format_template_resultset = 'resultset_format'

DESC format(Template, $$<result_before_delimiter>
<row_before_delimiter>42.42<field_delimiter_1>'Some string 1'<field_delimiter_2>[1, null, 2]<row_after_delimiter>
<row_between_delimiter>
<row_before_delimiter>\N<field_delimiter_1>'Some string 3'<field_delimiter_2>[1, 2, null]<row_after_delimiter>
<result_after_delimiter>
$$)
```

```response
┌─name─────┬─type───────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ column_1 │ Nullable(Float64)      │              │                    │         │                  │                │
│ column_2 │ Nullable(String)       │              │                    │         │                  │                │
│ column_3 │ Array(Nullable(Int64)) │              │                    │         │                  │                │
└──────────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Regexp {#regexp}

Как и в формате Template, в формате Regexp ClickHouse сначала извлекает все значения столбцов из строки с помощью заданного регулярного выражения, а затем пытается автоматически определить
тип данных каждого значения в соответствии с заданным правилом экранирования.

**Пример**


### Настройки текстовых форматов {#settings-for-text-formats}

#### input_format_max_rows_to_read_for_schema_inference/input_format_max_bytes_to_read_for_schema_inference {#input-format-max-rows-to-read-for-schema-inference}

Эти настройки определяют объём данных, считываемых при автоматическом определении схемы.
Чем больше строк/байтов считывается, тем больше времени уходит на автоматическое определение схемы, но тем выше вероятность
правильно определить типы (особенно если в данных много значений NULL).

Значения по умолчанию:

* `25000` для `input_format_max_rows_to_read_for_schema_inference`.
* `33554432` (32 МБ) для `input_format_max_bytes_to_read_for_schema_inference`.

#### column_names_for_schema_inference {#column-names-for-schema-inference}

Список имён столбцов, используемых при автоматическом определении схемы для форматов, в которых имена столбцов не заданы явно. Указанные имена будут использоваться вместо имён по умолчанию `c1,c2,c3,...`. Формат: `column1,column2,column3,...`.

#### schema_inference_hints {#schema-inference-hints}

#### schema_inference_make_columns_nullable $ {#schema-inference-make-columns-nullable}

* 0 — выведенный тип никогда не будет `Nullable`,
* 1 — все выведенные типы будут `Nullable`,
* 2 или &#39;auto&#39; — для текстовых форматов выведенный тип будет `Nullable` только в том случае, если столбец содержит `NULL` в выборке, которая разбирается в процессе автоматического определения схемы; для строго типизированных форматов (Parquet, ORC, Arrow) информация о допустимости NULL берётся из метаданных файла,

#### input_format_try_infer_integers {#input-format-try-infer-integers}

<Note>
  Эта настройка не применяется к типу данных `JSON`.

#### input_format_try_infer_datetimes_only_datetime64 {#input-format-try-infer-datetimes-only-datetime64}

Если параметр включен и при этом включен `input_format_try_infer_datetimes`, ClickHouse всегда будет автоматически определять тип `DateTime64(9)`, даже если значения даты и времени не содержат дробной части.

По умолчанию отключено.

**Примеры**

```sql
SET input_format_try_infer_datetimes = 1;
SET input_format_try_infer_datetimes_only_datetime64 = 1;
DESC format(JSONEachRow, $$
                                {"datetime" : "2021-01-01 00:00:00", "datetime64" : "2021-01-01 00:00:00.000"}
                                {"datetime" : "2022-01-01 00:00:00", "datetime64" : "2022-01-01 00:00:00.000"}
                         $$)
```

```response
┌─name───────┬─type────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ datetime   │ Nullable(DateTime64(9)) │              │                    │         │                  │                │
│ datetime64 │ Nullable(DateTime64(9)) │              │                    │         │                  │                │
└────────────┴─────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

Примечание: при разборе значений даты и времени в ходе автоматического определения схемы учитывается настройка [date&#95;time&#95;input&#95;format](/ru/reference/settings/formats/date-time#date_time_input_format)

#### input_format_try_infer_dates {#input-format-try-infer-dates}

Если параметр включён, ClickHouse при автоматическом определении схемы для текстовых форматов пытается автоматически определять тип `Date` по строковым полям.
Если все поля столбца в выборке данных были успешно разобраны как даты, типом результата будет `Date`;

```sql
SET input_format_try_infer_datetimes = 0, input_format_try_infer_dates = 0
DESC format(JSONEachRow, $$
```

```response
└──────┴──────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

```sql
SET input_format_try_infer_dates = 1
```

```response
│ date │ Nullable(Date) │              │                    │         │                  │                │
└──────┴────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```



## Самоописывающиеся форматы {#self-describing-formats}

Самоописывающиеся форматы хранят информацию о структуре данных непосредственно в самих данных:
это может быть заголовок с описанием, двоичное дерево типов или своего рода таблица.
Чтобы автоматически определить схему по файлам в таких форматах, ClickHouse считывает часть данных, содержащую
информацию о типах, и преобразует её в схему таблицы ClickHouse.

### Форматы с суффиксом -WithNamesAndTypes {#formats-with-names-and-types}

ClickHouse поддерживает ряд текстовых форматов с суффиксом -WithNamesAndTypes. Этот суффикс означает, что перед самими данными идут две дополнительные строки с именами и типами столбцов.
При автоматическом определении схемы для таких форматов ClickHouse считывает первые две строки и извлекает из них имена и типы столбцов.

**Пример**

```sql
DESC format(TSVWithNamesAndTypes,
$$num    str    arr
UInt8    String    Array(UInt8)
42    Hello, World!    [1,2,3]
$$)
```

```response
┌─name─┬─type─────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ num  │ UInt8        │              │                    │         │                  │                │
│ str  │ String       │              │                    │         │                  │                │
│ arr  │ Array(UInt8) │              │                    │         │                  │                │
└──────┴──────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Форматы JSON с метаданными {#json-with-metadata}

Некоторые входные форматы JSON ([JSON](/ru/reference/formats/JSON/JSON), [JSONCompact](/ru/reference/formats/JSON/JSONCompact), [JSONColumnsWithMetadata](/ru/reference/formats/JSON/JSONColumnsWithMetadata)) содержат метаданные с именами и типами столбцов.
При автоматическом определении схемы для таких форматов ClickHouse использует эти метаданные.

**Пример**

```sql
DESC format(JSON, $$
{
    "meta":
    [
        {
            "name": "num",
            "type": "UInt8"
        },
        {
            "name": "str",
            "type": "String"
        },
        {
            "name": "arr",
            "type": "Array(UInt8)"
        }
    ],

    "data":
    [
        {
            "num": 42,
            "str": "Hello, World",
            "arr": [1,2,3]
        }
    ],

    "rows": 1,

    "statistics":
    {
        "elapsed": 0.005723915,
        "rows_read": 1,
        "bytes_read": 1
    }
}
$$)
```

```response
┌─name─┬─type─────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ num  │ UInt8        │              │                    │         │                  │                │
│ str  │ String       │              │                    │         │                  │                │
│ arr  │ Array(UInt8) │              │                    │         │                  │                │
└──────┴──────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## Строго типизированные двоичные форматы {#strong-typed-binary-formats}

В таких форматах каждое сериализованное значение содержит информацию о своём типе (а иногда и о своём имени), но информации о таблице в целом нет.
При автоматическом определении схемы для таких форматов ClickHouse читает данные построчно (до `input_format_max_rows_to_read_for_schema_inference` строк или `input_format_max_bytes_to_read_for_schema_inference` байт), извлекает
из данных тип (а иногда и имя) каждого значения, а затем преобразует эти типы в типы ClickHouse.

### MsgPack {#msgpack}

В формате MsgPack между строками нет разделителя, поэтому, чтобы использовать автоматическое определение схемы для этого формата, необходимо указать количество столбцов в таблице
с помощью настройки `input_format_msgpack_number_of_columns`. ClickHouse использует следующие соответствия типов:

| Тип данных MessagePack (`INSERT`)                                  | Тип данных ClickHouse                        |
| ------------------------------------------------------------------ | -------------------------------------------- |
| `int N`, `uint N`, `negative fixint`, `positive fixint`            | [Int64](/ru/reference/data-types/int-uint)      |
| `bool`                                                             | [UInt8](/ru/reference/data-types/int-uint)      |
| `fixstr`, `str 8`, `str 16`, `str 32`, `bin 8`, `bin 16`, `bin 32` | [String](/ru/reference/data-types/string)       |
| `float 32`                                                         | [Float32](/ru/reference/data-types/float)       |
| `float 64`                                                         | [Float64](/ru/reference/data-types/float)       |
| `uint 16`                                                          | [Date](/ru/reference/data-types/date)           |
| `uint 32`                                                          | [DateTime](/ru/reference/data-types/datetime)   |
| `uint 64`                                                          | [DateTime64](/ru/reference/data-types/datetime) |
| `fixarray`, `array 16`, `array 32`                                 | [Array](/ru/reference/data-types/array)         |
| `fixmap`, `map 16`, `map 32`                                       | [Map](/ru/reference/data-types/map)             |

По умолчанию все автоматически определённые типы обёрнуты в `Nullable`, но это можно изменить с помощью настройки `schema_inference_make_columns_nullable`.

### BSONEachRow {#bsoneachrow}

В формате BSONEachRow каждая строка данных представлена в виде документа BSON. При автоматическом определении схемы ClickHouse считывает документы BSON один за другим, извлекает
из данных значения, имена и типы, а затем преобразует эти типы в типы ClickHouse в соответствии со следующей таблицей соответствия типов:

| Тип BSON                                                                                       | Тип ClickHouse                                                                                              |
| ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `\x08` boolean                                                                                 | [Bool](/ru/reference/data-types/boolean)                                                                       |
| `\x10` int32                                                                                   | [Int32](/ru/reference/data-types/int-uint)                                                                     |
| `\x12` int64                                                                                   | [Int64](/ru/reference/data-types/int-uint)                                                                     |
| `\x01` double                                                                                  | [Float64](/ru/reference/data-types/float)                                                                      |
| `\x09` datetime                                                                                | [DateTime64](/ru/reference/data-types/datetime64)                                                              |
| `\x05` binary с двоичным подтипом `\x00`, `\x02` string, `\x0E` symbol, `\x0D` JavaScript code | [String](/ru/reference/data-types/string)                                                                      |
| `\x07` ObjectId,                                                                               | [FixedString(12)](/ru/reference/data-types/fixedstring)                                                        |
| `\x05` binary с подтипом uuid `\x04`, размер = 16                                              | [UUID](/ru/reference/data-types/uuid)                                                                          |
| `\x04` array                                                                                   | [Array](/ru/reference/data-types/array)/[Tuple](/ru/reference/data-types/tuple) (если вложенные типы различаются) |
| `\x03` документ                                                                                | [Именованный Tuple](/ru/reference/data-types/tuple)/[Map](/ru/reference/data-types/map) (с ключами типа String)   |

По умолчанию все автоматически определённые типы обёрнуты в `Nullable`, но это поведение можно изменить с помощью настройки `schema_inference_make_columns_nullable`.

## Форматы с постоянной схемой {#formats-with-constant-schema}

Данные в таких форматах всегда имеют одну и ту же схему.

### LineAsString {#line-as-string}

В этом формате ClickHouse считывает каждую строку данных целиком в один столбец с типом данных `String`. Выведенный тип для этого формата всегда `String`, а имя столбца — `line`.

**Пример**

```sql
DESC format(LineAsString, 'Hello\nworld!')
```

```response
┌─name─┬─type───┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ line │ String │              │                    │         │                  │                │
└──────┴────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### JSONAsString {#json-as-string}

В этом формате ClickHouse считывает весь объект JSON из данных в один столбец с типом данных `String`. Для этого формата выведенный тип всегда `String`, а столбец называется `json`.

**Пример**

```sql
DESC format(JSONAsString, '{"x" : 42, "y" : "Hello, World!"}')
```

```response
┌─name─┬─type───┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ json │ String │              │                    │         │                  │                │
└──────┴────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### JSONAsObject {#json-as-object}

В этом формате ClickHouse считывает весь объект JSON из данных в один столбец с типом данных `JSON`. Выведенный тип для этого формата всегда `JSON`, а имя столбца — `json`.

**Пример**

```sql
DESC format(JSONAsObject, '{"x" : 42, "y" : "Hello, World!"}');
```

```response
┌─name─┬─type─┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ json │ JSON │              │                    │         │                  │                │
└──────┴──────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## Режимы автоматического определения схемы {#schema-inference-modes}

Автоматическое определение схемы по набору файлов данных может работать в двух режимах: `default` и `union`.
Режим задаётся настройкой `schema_inference_mode`.

### Режим по умолчанию {#default-schema-inference-mode}

В режиме по умолчанию ClickHouse предполагает, что все файлы имеют одинаковую схему, и пытается автоматически определить её, читая файлы по очереди, пока это не удастся.

Пример:

Предположим, у нас есть 3 файла `data1.jsonl`, `data2.jsonl` и `data3.jsonl` со следующим содержимым:

`data1.jsonl`:

```json
{"field1" :  1, "field2" :  null}
{"field1" :  2, "field2" :  null}
{"field1" :  3, "field2" :  null}
```

`data2.jsonl`:

```json
{"field1" :  4, "field2" :  "Data4"}
{"field1" :  5, "field2" :  "Data5"}
{"field1" :  6, "field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field1" :  7, "field2" :  "Data7", "field3" :  [1, 2, 3]}
{"field1" :  8, "field2" :  "Data8", "field3" :  [4, 5, 6]}
{"field1" :  9, "field2" :  "Data9", "field3" :  [7, 8, 9]}
```

Попробуем применить автоматическое определение схемы к этим 3 файлам:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='default'
```

```response title="Response"
┌─name───┬─type─────────────┐
│ field1 │ Nullable(Int64)  │
│ field2 │ Nullable(String) │
└────────┴──────────────────┘
```

Как видно, в результате отсутствует `field3` из файла `data3.jsonl`.
Это происходит потому, что ClickHouse сначала попытался автоматически определить схему по файлу `data1.jsonl`, но не смог, так как поле `field2` содержало только значения NULL,
а затем попытался определить схему по `data2.jsonl` и успешно это сделал, поэтому данные из файла `data3.jsonl` не были прочитаны.

### Режим union {#default-schema-inference-mode-1}

В режиме union ClickHouse исходит из того, что файлы могут иметь разные схемы, поэтому автоматически определяет схемы всех файлов, а затем объединяет их в общую схему.

Предположим, у нас есть 3 файла `data1.jsonl`, `data2.jsonl` и `data3.jsonl` со следующим содержимым:

`data1.jsonl`:

```json
{"field1" :  1}
{"field1" :  2}
{"field1" :  3}
```

`data2.jsonl`:

```json
{"field2" :  "Data4"}
{"field2" :  "Data5"}
{"field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field3" :  [1, 2, 3]}
{"field3" :  [4, 5, 6]}
{"field3" :  [7, 8, 9]}
```

Попробуем применить автоматическое определение схемы к этим 3 файлам:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='union'
```

```response title="Response"
┌─name───┬─type───────────────────┐
│ field1 │ Nullable(Int64)        │
│ field2 │ Nullable(String)       │
│ field3 │ Array(Nullable(Int64)) │
└────────┴────────────────────────┘
```

Как видим, мы получили все поля из всех файлов.

Примечание:

* Поскольку в некоторых файлах могут отсутствовать отдельные столбцы из итоговой схемы, режим union поддерживается только для форматов, позволяющих читать подмножество столбцов (например, JSONEachRow, Parquet, TSVWithNames и т. д.), и не работает с другими форматами (например, CSV, TSV, JSONCompactEachRow и т. д.).
* Если ClickHouse не может автоматически определить схему по одному из файлов, будет выброшено исключение.
* Если файлов много, чтение схемы из каждого из них может занять много времени.

## Автоматическое определение формата {#automatic-format-detection}

Если формат данных не указан и его нельзя определить по расширению файла, ClickHouse попытается определить формат файла по его содержимому.

**Примеры:**

Предположим, у нас есть файл `data` со следующим содержимым:

```csv
"a","b"
1,"Data1"
2,"Data2"
3,"Data3"
```

Мы можем просмотреть этот файл и выполнить к нему запрос, не указывая ни формат, ни structure:

```sql
:) desc file(data);
```

```response
┌─name─┬─type─────────────┐
│ a    │ Nullable(Int64)  │
│ b    │ Nullable(String) │
└──────┴──────────────────┘
```

```sql
:) select * from file(data);
```

```response
┌─a─┬─b─────┐
│ 1 │ Data1 │
│ 2 │ Data2 │
│ 3 │ Data3 │
└───┴───────┘
```

<Note>
  ClickHouse умеет автоматически определять лишь часть форматов, и на такое определение требуется время, поэтому формат всегда лучше указывать явно.
</Note>
