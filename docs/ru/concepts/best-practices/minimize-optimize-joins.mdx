На этой странице приведены практические рекомендации о том, как по возможности избегать JOIN, а если без них не обойтись — снижать их стоимость. Синтаксис и семантика описаны в [справочнике по предложению `JOIN`](/ru/reference/statements/select/join). Алгоритмы выполнения и выбор алгоритма описаны в разделе [Соединение таблиц](/ru/concepts/features/operations/select/joining-tables).

## Старайтесь избегать JOIN {#prefer-avoiding-joins}

ClickHouse поддерживает широкий спектр типов соединения и алгоритмов JOIN. Однако JOIN по своей природе затратнее, чем запросы к одной денормализованной таблице. Денормализация переносит вычислительную нагрузку с этапа выполнения запроса на этап вставки или предварительной обработки, что часто существенно снижает задержку во время выполнения. Для аналитических запросов в реальном времени или запросов, чувствительных к задержке, **денормализация настоятельно рекомендуется**.

В общем случае денормализация оправдана, если:

* Таблицы изменяются редко или допустимо пакетное обновление.
* Связи не являются многие-ко-многим и не имеют чрезмерно высокой мощности.
* В запросах будет использоваться только ограниченное подмножество столбцов, то есть некоторые столбцы можно исключить из денормализации.
* У вас есть возможность перенести обработку из ClickHouse во внешние системы, такие как [Flink](/ru/integrations/connectors/data-ingestion/apache-flink), где можно выполнять обогащение или уплощение в реальном времени.

Денормализовать нужно не все данные — сосредоточьтесь на атрибутах, которые чаще всего используются в запросах. Также рассмотрите [materialized views](/ru/concepts/best-practices/use-materialized-views), чтобы инкрементально вычислять агрегаты вместо дублирования целых подтаблиц. Если схема обновляется редко, а задержка критична, денормализация обеспечивает наилучший компромисс по производительности.

Полное руководство по денормализации данных в ClickHouse см. в разделе [денормализация](/ru/guides/clickhouse/data-modelling/denormalization).

## Когда без JOIN не обойтись {#when-joins-are-required}

<Tip>
  **Используйте ClickHouse 26.8 или новее.**

  Начиная с версии 25.12, переупорядочивание JOIN для нескольких таблиц и использование оптимизатором доступной статистики включены по умолчанию. В версии 26.3 [статистика столбцов](/ru/reference/settings/session-settings/allow-statistics#allow_statistics) стала общедоступной и включена по умолчанию. Начиная с версии 26.8, подходящие таблицы по умолчанию [материализуют статистику столбцов при вставке](/ru/reference/settings/session-settings/materialize-statistics-on-insert#materialize_statistics_on_insert), что повышает точность оценок для стоимостной оптимизации JOIN.
</Tip>

Чтобы повысить производительность JOIN, следуйте этим рекомендациям:

* **Используйте `ANY` JOIN, когда достаточно одного совпадения.** Обычный JOIN возвращает все совпадающие строки и при дублирующихся ключах может дать декартово произведение. Если достаточно одного совпадения, используйте `LEFT ANY JOIN` или `ANY INNER JOIN`: это уменьшит размер результата и потребление памяти.
* **Сокращайте обе стороны до выполнения JOIN.** Применяйте селективные условия в предложениях `WHERE` и `JOIN ON`. ClickHouse по возможности проталкивает фильтры вниз, но явные подзапросы гарантируют, что каждая из входных сторон будет отфильтрована до JOIN.
* **Рассмотрите `IN` вместо `INNER JOIN`.** Если запросу нужно лишь проверить, есть ли ключ в другой таблице, подзапрос `IN` выражает это требование напрямую и может потреблять меньше памяти, чем формирование результата `INNER JOIN`.
* **Для многократно используемого поиска выбирайте движок таблицы `Join`.** [Движок таблицы `Join`](/ru/reference/engines/table-engines/special/join) хранит заранее вычисленную структуру в памяти для заданных типа соединения, строгости и ключа. В ClickHouse Cloud он реализован как `SharedJoin` с базовой таблицей `MergeTree`, а `Join(ANY, LEFT, key)` обеспечивает обновляемый поиск по ключу. См. [Fast, updatable lookups with the Join table engine](https://clickhouse.com/blog/join-table-engine).
* **По возможности выполняйте JOIN по ключам сортировки таблиц.** Если обе таблицы физически упорядочены по ключу JOIN, `full_sorting_merge` может пропустить сортировку и снизить потребление памяти. Проверьте план выполнения и сравните этот алгоритм с алгоритмом по умолчанию на репрезентативных данных.
* **Избегайте JOIN со сбросом данных на диск.** Сброс промежуточного состояния JOIN на диск позволяет запросу уложиться в ограничение памяти, но дисковый ввод-вывод обычно увеличивает задержку. Хеш-соединения при достижении настроенных порогов сброса на диск могут переключаться на grace hash, а соединения слиянием — использовать внешнюю сортировку. Прежде чем полагаться на сброс данных на диск, сократите количество входных строк и столбцов или измените модель данных. Подробнее см. в разделе [Выбор оптимального алгоритма JOIN](#choosing-the-optimal-join-algorithm).
* **При необходимости используйте значения по умолчанию как маркеры отсутствия совпадения.** Значение по умолчанию [`join_use_nulls = 0`](/ru/reference/settings/session-settings/join#join_use_nulls) заполняет несопоставленные столбцы внешнего JOIN значением по умолчанию для их типа данных и позволяет обойтись без обёрток `Nullable`. Включайте `join_use_nulls`, только если запросу нужно отличать несопоставленную строку от сопоставленной строки, содержащей значение по умолчанию.

## Выбор оптимального алгоритма JOIN {#choosing-the-optimal-join-algorithm}

ClickHouse поддерживает несколько алгоритмов JOIN, каждый из которых по-своему балансирует между скоростью и потреблением памяти.
Значение [`join_algorithm`](/ru/reference/settings/session-settings/join#join_algorithm) по умолчанию — `direct,parallel_hash,hash,ie_join`: ClickHouse выбирает первый алгоритм, применимый с учётом типа соединения, строгости, условия и движка таблицы. Менять эту настройку имеет смысл только после того, как оба входных набора данных уже сокращены, и лишь если измерения на репрезентативных данных показывают, что нужна другая стратегия использования памяти или выполнения. Подробнее о выполнении алгоритмов и поддерживаемых типах соединения см. в разделе [Выбор алгоритма JOIN](/ru/concepts/features/operations/select/joining-tables#choosing-a-join-algorithm).

Если ваша главная метрика оптимизации — производительность и нужно выполнить JOIN как можно быстрее, выбрать подходящий алгоритм соединения поможет следующее дерево решений:

<br />

<Image img="/images/guides/joins-4.webp" size="lg" alt="Дерево решений для оптимизации производительности JOIN" />

<br />

* **(1)** Если данные правой таблицы можно заранее загрузить в находящуюся в памяти структуру данных ключ-значение с низкой задержкой (например, в словарь), ключ JOIN совпадает с ключевым атрибутом этого хранилища ключ-значение, а семантики `LEFT ANY JOIN` достаточно, то можно использовать **direct join** — зачастую это самый быстрый вариант.

* **(2)** Если [физический порядок строк](/ru/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns) в таблице совпадает с порядком сортировки по ключу JOIN, всё зависит от конкретного случая. Здесь **полное сортирующее соединение слиянием** [пропускает](https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order) фазу сортировки, что значительно снижает использование памяти, а в зависимости от объёма данных и распределения значений ключа JOIN может работать и быстрее некоторых алгоритмов хеш-соединения.

* **(3)** Если правая таблица помещается в память даже с учётом [дополнительных накладных расходов на память](https://clickhouse.com/blog/clickhouse-fully-supports-joins-hash-joins-part2#summary) у **параллельного hash JOIN**, то этот алгоритм или хеш-соединение могут оказаться быстрее. Это зависит от объёма данных, типов данных и распределения значений в столбцах ключа JOIN.

* **(4)** Если правая таблица не помещается в память, хеш-соединение и параллельный hash JOIN могут сбрасывать данные на диск, переключаясь на хеш-соединение Grace при достижении порога [`max_bytes_before_external_join`](/ru/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) или [`max_bytes_ratio_before_external_join`](/ru/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join). Полное сортирующее соединение слиянием и частичное соединение слиянием также умеют использовать внешнее хранилище. Какой подход окажется самым быстрым, зависит от объёма данных, типов данных и распределения значений в столбцах ключа JOIN.

Частичное соединение слиянием оптимизировано для минимального использования памяти при соединении больших таблиц, но за счёт скорости: оно работает довольно медленно. Особенно это заметно, когда физический порядок строк левой таблицы не совпадает с порядком сортировки по ключу JOIN.

Хеш-соединение Grace — самое гибкое из трёх алгоритмов соединения, не ограниченных объёмом памяти, и хорошо поддаётся настройке. Параметр [`grace_hash_join_initial_buckets`](/ru/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets) задаёт начальное количество корзин и позволяет подобрать баланс между использованием памяти и скоростью соединения.

Какой из трёх дисковых алгоритмов окажется самым быстрым, зависит от объёма данных, типов данных и распределения значений в столбцах ключа JOIN. Чтобы это выяснить, лучше всего провести бенчмарки на реалистичных объёмах ваших данных.

## Оптимизация по памяти {#optimizing-for-memory}

Если вы хотите оптимизировать JOIN не по минимальному времени выполнения, а по минимальному использованию памяти, воспользуйтесь следующим деревом решений:

<br />

<Image img="/images/guides/joins-5.webp" size="lg" alt="Дерево решений для оптимизации JOIN по памяти" />

<br />

* **(1)** Если физический порядок строк в таблице совпадает с порядком сортировки по ключу JOIN, **полное сортирующее соединение слиянием** использует минимально возможный объём памяти и при этом обеспечивает высокую скорость JOIN, поскольку этап сортировки [пропускается](https://clickhouse.com/blog/clickhouse-fully-supports-joins-full-sort-partial-merge-part3#utilizing-physical-row-order).
* **(2)** **Хеш-соединение Grace** можно настроить на очень низкое использование памяти, увеличив значение [`grace_hash_join_initial_buckets`](/ru/reference/settings/session-settings/grace-hash#grace_hash_join_initial_buckets), но ценой снижения скорости JOIN. **Частичное соединение слиянием** намеренно расходует мало оперативной памяти. **Полное сортирующее соединение слиянием** с включённой внешней сортировкой, как правило, потребляет больше памяти, чем частичное соединение слиянием, если порядок строк не совпадает с порядком сортировки по ключу, зато JOIN выполняется значительно быстрее. Хеш-соединение и параллельный hash JOIN также позволяют снизить нехватку памяти: при достижении настроенного порога сброса на диск они переключаются на хеш-соединение Grace.

## Примеры оптимизации JOIN {#join-optimization-examples}

В следующих примерах используется [набор данных Stack Overflow](/ru/getting-started/example-datasets/stackoverflow), а рекомендации применяются поэтапно.
Приведённые ниже результаты — медианные значения по пяти запускам на сервисе ClickHouse Cloud с ClickHouse 26.8.1 и `max_threads = 4`. Каждый запрос предварительно прогревался один раз, порядок выполнения запросов чередовался, а `use_query_cache` и `use_query_condition_cache` были отключены.

### Замена `ANY INNER JOIN` на `IN` {#replace-any-inner-join-with-in}

В этом тесте запрос с `IN` выполнился в 2,7 раза быстрее, а пиковое потребление памяти снизилось на 83%.
Этот запрос подсчитывает посты, в которых не упоминается ClickHouse, но есть хотя бы один комментарий с таким упоминанием:

```sql
SELECT count()
FROM stackoverflow.posts AS p
ANY INNER JOIN stackoverflow.comments AS c ON p.Id = c.PostId
WHERE
    p.Title != ''
    AND p.Title NOT ILIKE '%clickhouse%'
    AND p.Body NOT ILIKE '%clickhouse%'
    AND c.Text ILIKE '%clickhouse%'
```

Этот запрос возвращает результат `86`. Медианное затраченное время выполнения составило 27,101 секунды, пиковое потребление памяти — 970,01 МиБ. Запрос прочитал 150,20 миллиона строк и 51,77 ГиБ данных.

Запросу достаточно лишь установить наличие подходящего комментария. Подзапрос с `IN` позволяет обойтись без формирования результата JOIN:

```sql
SELECT count()
FROM stackoverflow.posts
WHERE
    Title != ''
    AND Title NOT ILIKE '%clickhouse%'
    AND Body NOT ILIKE '%clickhouse%'
    AND Id IN
    (
        SELECT PostId
        FROM stackoverflow.comments
        WHERE Text ILIKE '%clickhouse%'
    )
```

Запрос с `IN` также возвращает `86`. Медианное затраченное время составило 10,206 секунды, пиковое потребление памяти — 162,81 МиБ. Было прочитано 174,20 миллиона строк и 19,02 ГиБ данных.

### Фильтрация обеих сторон перед заменой JOIN {#filter-both-sides-before-replacing-the-join}

В этом тесте переписывание сократило медианное затраченное время на 18%, а пиковое потребление памяти — на 14%.
Этот запрос подсчитывает голоса «за» для постов о Java, созданных начиная с 2020 года. Условие по дате применяется к обоим входным наборам данных ещё до выполнения JOIN:

```sql
SELECT countIf(v.VoteTypeId = 2) AS upvotes
FROM stackoverflow.posts AS p
INNER JOIN stackoverflow.votes AS v ON p.Id = v.PostId
WHERE
    p.CreationDate >= '2020-01-01'
    AND v.CreationDate >= '2020-01-01'
    AND has(arrayFilter(t -> t != '', splitByChar('|', p.Tags)), 'java')
```

Этот запрос возвращает результат `261915`. Медианное затраченное время составило 0,850 секунды, пиковое потребление памяти — 59,96 МиБ. Было прочитано 80,94 миллиона строк и 1,13 ГиБ данных.

Для каждого голоса достаточно лишь наличия соответствующего поста, поэтому JOIN можно заменить на `IN`, сохранив фильтры на обеих входных сторонах:

```sql
SELECT count() AS upvotes
FROM stackoverflow.votes
WHERE
    VoteTypeId = 2
    AND CreationDate >= '2020-01-01'
    AND PostId IN
    (
        SELECT Id
        FROM stackoverflow.posts
        WHERE
            CreationDate >= '2020-01-01'
            AND has(arrayFilter(t -> t != '', splitByChar('|', Tags)), 'java')
    )
```

Запрос с `IN` также возвращает `261915`. Медианное затраченное время его выполнения составило 0,696 секунды, пиковое потребление памяти — 51,70 МиБ. Было прочитано 46,20 миллиона строк и 817,49 МиБ данных.
