ClickHouse Observability работает целиком в **ClickHouse Cloud** и представляет собой полностью управляемый бэкенд для обсервабилити, сохраняя при этом ту же модель данных и тот же пользовательский опыт ClickStack. Описание самоуправляемых развертываний см. в разделе [Архитектура самоуправляемого развертывания](/ru/clickstack/self-configured/architecture).

В этой модели размещение, эксплуатацию и защиту **ClickHouse, интерфейса ClickStack и коллектора OpenTelemetry (OTel) для ингестии** берет на себя ClickHouse Cloud. Пользователи отвечают за инструментирование своих приложений и отправку телеметрии из своей среды в управляемый сервис.

### Коллектор OpenTelemetry: ингестия данных {#open-telemetry-collector-managed}

ClickHouse Observability включает управляемый коллектор OpenTelemetry (OTel) для приёма телеметрии открытым стандартизированным способом. В своём сервисе откройте **Team Settings → Data → Managed Telemetry** и скопируйте конечную точку OTLP и ключ API. Инструкции по настройке соединения и аутентификации см. в разделе [Отправка данных OpenTelemetry](/ru/clickstack/observability/ingesting-data/opentelemetry).

Коллектор экспортирует телеметрию в ClickHouse Cloud эффективными пакетами, используя схемы таблиц, оптимизированные для каждого типа телеметрического сигнала.

Коллектор для ингестии управляется ClickHouse Cloud. Тем не менее в вашем собственном окружении могут понадобиться коллекторы, которые будут собирать телеметрию, например метрики хоста или журналы Kubernetes, и пересылать её на управляемую конечную точку.

### ClickHouse Cloud: движок {#clickhouse-cloud}

В основе ClickHouse Observability лежит ClickHouse Cloud — бессерверная версия ClickHouse, столбцовой базы данных, предназначенной для real-time аналитики в больших масштабах. ClickHouse Cloud обеспечивает ингестию данных обсервабилити и выполнение запросов к ним, предоставляя:

* Быстрый поиск по большим объёмам событий
* Ингестию high-cardinality телеметрии в больших масштабах
* Столбцовое сжатие данных обсервабилити
* Нативную поддержку полуструктурированных данных JSON с возможностью динамического изменения схемы
* Мощный SQL-движок с сотнями встроенных аналитических функций

ClickHouse Cloud обрабатывает данные обсервабилити как широкие события, что позволяет глубоко сопоставлять журналы, метрики и трассировку в рамках единой структуры.

По сравнению с ClickHouse с открытым исходным кодом ClickHouse Cloud даёт ряд преимуществ для обсервабилити:

* Автоматическое масштабирование вычислительных ресурсов независимо от хранилища
* Объектное хранилище для хранения телеметрии независимо от объёма вычислительных ресурсов
* Встроенная аутентификация
* Возможности обеспечения безопасности и соответствия требованиям
* Обновления без простоя

### Интерфейс ClickStack {#hyperdx}

Интерфейс ClickStack — это пользовательский интерфейс ClickStack. Его возможности:

* Поиск на естественном языке и в стиле Lucene
* Просмотр поступающих данных в реальном времени (live tailing) для отладки
* Единое представление журналов, метрик и трассировок
* Воспроизведение сеансов для обсервабилити фронтенда
* Создание панелей мониторинга и настройка оповещений
* Интерфейс SQL-запросов для углублённого анализа

Интерфейс ClickStack разработан специально для ClickHouse и сочетает мощный поиск с интуитивно понятными рабочими процессами. Он позволяет быстро выявлять аномалии, расследовать проблемы и получать ценные инсайты.

В ClickHouse Observability интерфейс интегрирован с системой аутентификации консоли ClickHouse Cloud.

### Изоляция ингестии и запросов {#ingestion-query-isolation}

В ClickHouse Observability для ингестии и выполнения запросов используются раздельные вычислительные ресурсы. Вычислительные ресурсы для записи принимают входящую телеметрию и выполняют фоновое обслуживание данных. Вычислительные ресурсы для чтения обрабатывают поиск, панели мониторинга, блокноты и запросы оповещений. И те и другие работают с одним и тем же объектным хранилищем.

Такое разделение снижает конкуренцию между рабочими нагрузками ингестии и запросов. Если вычислительные ресурсы для записи временно недоступны, ресурсы для чтения продолжают выполнять запросы к сохранённым данным, хотя самая свежая телеметрия может поступать с задержкой. Если же недоступны ресурсы для чтения, ингестия может продолжаться, но работа поиска и проверка условий оповещений могут прерываться.

### Масштабирование {#scaling}

ClickHouse Cloud управляет ресурсами по мере изменения рабочей нагрузки. Управляемые коллекторы масштабируются горизонтально, чтобы справляться с трафиком ингестии, а вычислительные ресурсы для записи и чтения масштабируются независимо друг от друга и от хранилища.

Масштабирование происходит не мгновенно. При резком росте ингестии новая телеметрия может становиться доступной для поиска с задержкой, а при всплесках запросов, пока ресурсы перестраиваются, может увеличиваться время ответа. Разделение рабочих нагрузок помогает ограничить влияние одной нагрузки на другую.

### Буферизация при ингестии и восстановление {#ingestion-buffering-recovery}

Управляемый коллектор сначала пытается записать телеметрию в ClickHouse. Если ClickHouse временно не может принимать операции записи, конвейер ингестии может сохранять пакеты в Amazon S3 для последующего повторного применения. Этот временный буфер ингестии не связан с объектным хранилищем, в котором ClickHouse хранит телеметрию. Когда операции записи возобновляются, буферизованные данные загружаются в ClickHouse.

Во время восстановления, пока обрабатываются накопившиеся данные, недавняя телеметрия может поступать с задержкой или не по порядку. Такая буферизация помогает восстановиться после временных перебоев с записью, однако не обеспечивает межрегиональное переключение при отказе и не гарантирует доставку при любом сценарии сбоя.

Часть данных всё же может быть потеряна — например, данные, которые на момент остановки коллектора хранились только в его памяти, или пакеты, которые не удалось записать ни в ClickHouse, ни в S3. Настройте отправляющие агенты и коллекторы на повторные попытки при сбоях экспорта и, где это поддерживается, используйте персистентные очереди, чтобы сохранять телеметрию во время перебоев.
