## Миграция агентов из Elastic {#migrating-agents-from-elastic-self-configured}

Elastic Stack предлагает ряд агентов для сбора данных обсервабилити, а именно:

* [Семейство Beats](https://www.elastic.co/beats), например [Filebeat](https://www.elastic.co/beats/filebeat), [Metricbeat](https://www.elastic.co/beats/metricbeat) и [Packetbeat](https://www.elastic.co/beats/packetbeat), — все они построены на библиотеке `libbeat`. Эти Beats поддерживают [отправку данных в Elasticsearch, Kafka, Redis или Logstash](https://www.elastic.co/docs/reference/beats/filebeat/configuring-output) по протоколу Lumberjack.
* [`Elastic Agent`](https://www.elastic.co/elastic-agent) — единый агент для сбора журналов, метрик и трассировки. Им можно централизованно управлять через [Elastic Fleet Server](https://www.elastic.co/docs/reference/fleet/manage-elastic-agents-in-fleet); он поддерживает отправку данных в Elasticsearch, Logstash, Kafka или Redis.
* Кроме того, Elastic предоставляет собственный дистрибутив [OpenTelemetry Collector — EDOT](https://www.elastic.co/docs/reference/opentelemetry). Хотя пока им нельзя управлять через Fleet Server, он открывает более гибкий и открытый путь для миграции на ClickHouse Observability.

Оптимальный путь миграции зависит от того, какие агенты используются сейчас. В следующих разделах описаны варианты миграции для каждого основного типа агентов. Наша цель — максимально упростить переход и по возможности сохранить возможность использовать уже развёрнутые агенты на время миграции.

## Рекомендуемый путь миграции {#prefered-migration-path-self-configured}

По возможности мы рекомендуем перейти на [OpenTelemetry (OTel) Collector](https://opentelemetry.io/docs/collector/) для сбора всех журналов, метрик и трассировок, развернув коллектор [на периферии в роли агента](/ru/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured). Это наиболее эффективный способ отправки данных, который позволяет избежать усложнения архитектуры и преобразования данных.

<Info>
  **Почему OpenTelemetry Collector?**

  OpenTelemetry Collector — это устойчивое и независимое от поставщиков решение для ингестии данных обсервабилити. Мы понимаем, что в некоторых организациях работают парки из тысяч, а то и десятков тысяч агентов Elastic. Для таких пользователей сохранение совместимости с существующей инфраструктурой агентов может быть критически важным. Эта документация помогает решить эту задачу и вместе с тем постепенно перевести сбор данных на OpenTelemetry.
</Info>

## Конечная точка OpenTelemetry в ClickHouse {#clickhouse-otel-endpoint-self-configured}

Прежде чем переходить к шагам по миграции агента, настройте пункт назначения. Приведённые ниже примеры для Vector и EDOT отправляют данные OpenTelemetry по протоколу OTLP через HTTP.

<Tabs>
  <Tab title="Полностью управляемый">
    <BetaBadge label="Сервис в стадии бета-тестирования" />

    Скопируйте конечную точку OTLP по HTTP и ключ API в разделе **Team Settings → Data → Managed Telemetry**. Задайте следующие переменные в окружении, где запущен Vector или EDOT:

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Указывайте конечную точку в точности как есть, включая порт, но без суффикса `/v1/logs`. Сведения о подключении см. в разделе [Отправка данных OpenTelemetry](/ru/clickstack/observability/ingesting-data/opentelemetry).
  </Tab>

  <Tab title="Самоуправляемый">
    Разверните принимающий коллектор по [руководству по настройке самоуправляемой версии](/ru/clickstack/self-configured/getting-started/managed). Задайте его доступную конечную точку OTLP по HTTP и заголовок авторизации в окружении, где запущен Vector или EDOT:

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_COLLECTOR_TOKEN'
    ```

    Если принимающий коллектор защищён с помощью `OTLP_AUTH_TOKEN`, укажите этот токен в качестве значения авторизации. Если аутентификация отключена, уберите заголовок `authorization` из примеров. См. раздел [Защита коллектора](/ru/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).

    Используйте `localhost` только в том случае, если отправитель и приёмник находятся в одном сетевом пространстве имён. Если на приёмнике включён TLS, используйте его конечную точку HTTPS и настройте доверие к его сертификату.
  </Tab>
</Tabs>

## Миграция с Beats {#migrating-to-beats-self-configured}

Пользователи с крупными развертываниями Beats могут сохранить их при миграции на ClickHouse Observability.

**На данный момент этот вариант протестирован только с Filebeat, поэтому подходит только для журналов.**

Агенты Beats используют [Elastic Common Schema (ECS)](https://www.elastic.co/docs/reference/ecs), которая сейчас [находится в процессе слияния со спецификацией OpenTelemetry](https://github.com/open-telemetry/opentelemetry-specification/blob/main/oteps/0199-support-elastic-common-schema-in-opentelemetry.md), используемой в ClickHouse Observability. Однако эти [схемы по-прежнему существенно различаются](https://www.elastic.co/docs/reference/ecs/ecs-otel-alignment-overview), поэтому пока пользователям приходится самостоятельно преобразовывать события в формате ECS в формат OpenTelemetry перед ингестией в ClickHouse Observability.

Для такого преобразования мы рекомендуем использовать [Vector](https://vector.dev) — легковесный и высокопроизводительный конвейер данных обсервабилити с мощным языком преобразований Vector Remap Language (VRL).

Если ваши агенты Filebeat настроены на отправку данных в Kafka (один из поддерживаемых в Beats выходов), Vector может читать и обрабатывать эти события из Kafka, преобразовывать схему с помощью VRL, а затем пересылать их по OTLP на настроенную вами конечную точку OTLP.

Кроме того, Vector поддерживает приём событий по протоколу Lumberjack, который использует Logstash. Это позволяет агентам Beats отправлять данные напрямую в Vector, где применяется тот же процесс преобразования, после чего события пересылаются по OTLP на настроенную вами конечную точку OTLP.

В следующем примере приведены начальные шаги по настройке Vector для приёма событий журналов от Filebeat по протоколу Lumberjack. Мы также приводим VRL-код для сопоставления входящих событий ECS со спецификацией OTel перед их отправкой по OTLP на настроенную вами конечную точку OTLP. Пользователи, получающие события из Kafka, могут заменить источник Logstash в Vector на [источник Kafka](https://vector.dev/docs/reference/configuration/sources/kafka/) — все остальные шаги остаются без изменений.

<Steps>
  <Step title="Установите vector" id="install-vector-self-configured">
    Установите Vector, следуя [официальному руководству по установке](https://vector.dev/docs/setup/installation/).

    Установите Vector на хост, доступный для ваших агентов Filebeat.

    При [переводе Vector в продакшн](https://vector.dev/docs/setup/going-to-prod/) рекомендуется следовать рекомендуемым практикам в части архитектуры и безопасности.
  </Step>

  <Step title="Настройте Vector" id="configure-vector-self-configured">
    Vector необходимо настроить на приём событий по протоколу Lumberjack, имитируя инстанс Logstash. Для этого настройте для Vector [источник `logstash`](https://vector.dev/docs/reference/configuration/sources/logstash/):

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
          # The files below are generated from the steps at https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          # crt_file: logstash.crt
          # key_file: logstash.key
          # ca_file: ca.crt
          # verify_certificate: true
    ```

    <Info>
      **Настройка TLS**

      Если требуется взаимный TLS, сгенерируйте сертификаты и ключи в соответствии с руководством Elastic [&quot;Configure SSL/TLS for the Logstash output&quot;](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output). Затем укажите их в конфигурации, как показано выше.
    </Info>

    События будут поступать в формате ECS. Их можно преобразовать в схему OpenTelemetry с помощью преобразователя на Vector Remap Language (VRL). Настроить этот преобразователь несложно — сам скрипт хранится в отдельном файле:

    ```yaml
    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'
    ```

    Обратите внимание, что он получает события из указанного выше источника `beats`. Наш скрипт remap приведён ниже. Он протестирован только на событиях логов, но может послужить основой для других форматов.

    <Accordion title="VRL — из ECS в OTel">
      ```javascript
      # Define keys to ignore at root level
      ignored_keys = ["@metadata"]

      # Define resource key prefixes
      resource_keys = ["host", "cloud", "agent", "service"]

      # Create separate objects for resource and log record fields
      resource_obj = {}
      log_record_obj = {}

      # Copy all non-ignored root keys to appropriate objects
      root_keys = keys(.)
      for_each(root_keys) -> |_index, key| {
          if !includes(ignored_keys, key) {
              val, err = get(., [key])
              if err == null {
                  # Check if this is a resource field
                  is_resource = false
                  if includes(resource_keys, key) {
                      is_resource = true
                  }

                  # Add to appropriate object
                  if is_resource {
                      resource_obj = set(resource_obj, [key], val) ?? resource_obj
                  } else {
                      log_record_obj = set(log_record_obj, [key], val) ?? log_record_obj
                  }
              }
          }
      }

      # Flatten both objects separately
      flattened_resources = flatten(resource_obj, separator: ".")
      flattened_logs = flatten(log_record_obj, separator: ".")

      # Process resource attributes
      resource_attributes = []
      resource_keys_list = keys(flattened_resources)
      for_each(resource_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_resources, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  resource_attributes = push(resource_attributes, attribute)
              }
          }
      }

      # Process log record attributes
      log_attributes = []
      log_keys_list = keys(flattened_logs)
      for_each(log_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_logs, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  log_attributes = push(log_attributes, attribute)
              }
          }
      }

      # Get timestamp for timeUnixNano (convert to nanoseconds)
      timestamp_nano = if exists(.@timestamp) {
          to_unix_timestamp!(parse_timestamp!(.@timestamp, format: "%Y-%m-%dT%H:%M:%S%.3fZ"), unit: "nanoseconds")
      } else {
          to_unix_timestamp(now(), unit: "nanoseconds")
      }

      # Get message/body field
      body_value = if exists(.message) {
          to_string!(.message)
      } else if exists(.body) {
          to_string!(.body)
      } else {
          ""
      }

      # Create the OpenTelemetry structure
      . = {
          "resourceLogs": [
              {
                  "resource": {
                      "attributes": resource_attributes
                  },
                  "scopeLogs": [
                      {
                          "scope": {},
                          "logRecords": [
                              {
                                  "timeUnixNano": to_string(timestamp_nano),
                                  "severityNumber": 9,
                                  "severityText": "info",
                                  "body": {
                                      "stringValue": body_value
                                  },
                                  "attributes": log_attributes
                              }
                          ]
                      }
                  ]
              }
          ]
      }
      ```
    </Accordion>

    Наконец, отправьте преобразованные события на настроенную вами конечную точку OTLP. Для этого необходимо настроить в Vector приёмник OTLP, который принимает на вход события из преобразования `remap_filebeat`:

    ```yaml
    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat] # receives events from a remap transform - see below
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```

    Используйте [переменные подключения](#clickhouse-otel-endpoint-self-configured) для своего развертывания. URI Vector содержит `/v1/logs`, поскольку этот вывод (output) отправляет записи журнала.

    Итоговая полная конфигурация приведена ниже:

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
            #crt_file: /data/elasticsearch-9.0.1/logstash/logstash.crt
            #key_file: /data/elasticsearch-9.0.1/logstash/logstash.key
            #ca_file: /data/elasticsearch-9.0.1/ca/ca.crt
            #verify_certificate: true

    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'

    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat]
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```
  </Step>

  <Step title="Настройка Filebeat" id="configure-filebeat-self-configured">
    Настройте Filebeat на использование Logstash output для Vector, заменив им существующую конфигурацию вывода. Замените `YOUR_VECTOR_HOST` на хост, на котором запущен Vector; `localhost` используйте, только если оба сервиса работают на одном хосте. Настройте TLS в соответствии с параметрами источника Vector:

    ```yaml
    # ------------------------------ Logstash Output -------------------------------
    output.logstash:
      # The Logstash hosts
      hosts: ["YOUR_VECTOR_HOST:5044"]

      # Optional SSL. By default is off.
      # List of root certificates for HTTPS server verifications
      #ssl.certificate_authorities: ["/etc/pki/root/ca.pem"]

      # Certificate for SSL client authentication
      #ssl.certificate: "/etc/pki/client/cert.pem"

      # Client Certificate Key
      #ssl.key: "/etc/pki/client/cert.key"
    ```
  </Step>
</Steps>

## Миграция с Elastic Agent {#migrating-from-elastic-agent-self-configured}

Elastic Agent объединяет различные Elastic Beats в единый пакет. Этот агент интегрируется с [Elastic Fleet](https://www.elastic.co/docs/reference/fleet/fleet-server), что позволяет централизованно управлять им и настраивать его.

У пользователей с развернутыми Elastic Agent есть несколько вариантов миграции:

* Настроить агент на отправку данных в конечную точку Vector по протоколу Lumberjack. **На данный момент этот вариант протестирован только для сбора данных журналов с помощью Elastic Agent.** Его можно настроить централизованно через интерфейс Fleet в Kibana.
* [Запустить агент в режиме Elastic OpenTelemetry Collector (EDOT)](https://www.elastic.co/docs/reference/fleet/otel-agent). Elastic Agent включает встроенный EDOT Collector, который позволяет один раз инструментировать приложения и инфраструктуру и отправлять данные сразу нескольким поставщикам и в несколько хранилищ. В такой конфигурации достаточно настроить EDOT Collector на пересылку событий по протоколу OTLP в заданную конечную точку OTLP. **Этот подход поддерживает все типы событий.**

Ниже рассмотрены оба варианта.

### Отправка данных через Vector {#sending-data-via-vector-self-configured}

<Steps>
  <Step title="Установка и настройка Vector" id="install-configure-vector-self-configured">
    Установите и настройте Vector, выполнив [те же шаги](#install-vector-self-configured), что описаны для миграции с Filebeat.
  </Step>

  <Step title="Настройка Elastic Agent" id="configure-elastic-agent-self-configured">
    Elastic Agent необходимо настроить на отправку данных по протоколу Logstash — Lumberjack. Это [поддерживаемая схема развёртывания](https://www.elastic.co/docs/manage-data/ingest/ingest-reference-architectures/ls-networkbridge), которую можно настроить централизованно или — при развёртывании без Fleet — [через файл конфигурации агента `elastic-agent.yaml`](https://www.elastic.co/docs/reference/fleet/logstash-output).

    Для централизованной настройки через Kibana добавьте [Output во Fleet](https://www.elastic.co/docs/reference/fleet/fleet-settings#output-settings).

    <div className="ch-image-md">
      <Frame>
        ![Добавление Logstash output](/images/use-cases/observability/add-logstash-output.webp)
      </Frame>
    </div>

    Затем этот output можно использовать в [политике агента](https://www.elastic.co/docs/reference/fleet/agent-policy). В результате все агенты, использующие эту политику, автоматически начнут отправлять данные в Vector.

    <div className="ch-image-md">
      <Frame>
        ![Настройки агента](/images/use-cases/observability/agent-output-settings.webp)
      </Frame>
    </div>

    Поскольку для этого требуется настроить защищённое соединение по TLS, рекомендуем воспользоваться руководством [«Configure SSL/TLS for the Logstash output»](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output), считая, что роль Logstash выполняет ваш инстанс Vector.

    Обратите внимание, что в этом случае источник Logstash в Vector также необходимо настроить на использование взаимного TLS. Для настройки входных данных используйте ключи и сертификаты, [созданные по этому руководству](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs).

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: true  # Установите значение true, если используете TLS.
          # Файлы ниже создаются согласно шагам по ссылке https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          crt_file: logstash.crt
          key_file: logstash.key
          ca_file: ca.crt
          verify_certificate: true
    ```
  </Step>
</Steps>

### Запуск Elastic Agent в качестве коллектора OpenTelemetry {#run-agent-as-otel-self-configured}

Elastic Agent включает встроенный EDOT Collector, который позволяет один раз инструментировать приложения и инфраструктуру и отправлять данные сразу нескольким поставщикам и в разные хранилища.

<Info>
  **Интеграции агента и оркестрация**

  Пользователи, запускающие EDOT Collector, поставляемый с Elastic Agent, не смогут воспользоваться [существующими интеграциями агента](https://www.elastic.co/docs/reference/fleet/manage-integrations). Кроме того, коллектором нельзя централизованно управлять через Fleet, поэтому пользователю придётся запускать [агент в автономном режиме](https://www.elastic.co/docs/reference/fleet/configure-standalone-elastic-agents) и самостоятельно управлять конфигурацией.
</Info>

Чтобы запустить Elastic Agent с EDOT Collector, следуйте [официальному руководству Elastic](https://www.elastic.co/docs/reference/fleet/otel-agent-transform). Настройте экспортер OTLP HTTP, используя ваши [переменные подключения](#clickhouse-otel-endpoint-self-configured):

```yaml
exporters:
  otlphttp/clickhouse:
    endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
    headers:
      authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
```

Добавьте `otlphttp/clickhouse` в список `exporters` каждого конвейера журналов, метрик или трассировки, данные которого нужно пересылать. Существующие приёмники и процессоры оставьте без изменений. Для параллельной ингестии сохраните в этих конвейерах экспортер Elastic; удалите его, когда будете готовы прекратить отправку данных в Elastic.

Экспортер использует базовую конечную точку и автоматически добавляет к ней путь сигнала. Если HTTPS-приёмник использует частный центр сертификации, настройте `tls.ca_file`; если этот приёмник требует взаимного TLS, дополнительно настройте `tls.cert_file` и `tls.key_file`. Эти настройки защищают соединение между EDOT и OTLP-приёмником независимо от настройки TLS между Filebeat и Vector.

## Миграция с Elastic OpenTelemetry Collector {#migrating-from-elastic-otel-collector-self-configured}

Если вы уже используете [Elastic OpenTelemetry Collector (EDOT)](https://www.elastic.co/docs/reference/opentelemetry), достаточно перенастроить агентов на отправку данных по OTLP на настроенную вами конечную точку OTLP. Необходимые шаги полностью совпадают с описанными выше для запуска [Elastic Agent в качестве коллектора OpenTelemetry](#run-agent-as-otel-self-configured). Этот подход применим ко всем типам данных.
