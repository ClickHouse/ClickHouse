Это руководство посвящено миграции с Elastic на **полностью управляемый ClickHouse Observability** — вариант, используемый по умолчанию. ClickHouse сам управляет базовыми схемами и хранилищем. Ваш конвейер ингестии должен отправлять телеметрию в формате **OpenTelemetry Protocol (OTLP)**: документы Elasticsearch нельзя напрямую импортировать в полностью управляемый сервис.

Для самоуправляемых развертываний ознакомьтесь с [соответствием концепций Elasticsearch и ClickHouse](/ru/clickstack/self-configured/migration/elastic/concepts) и [сопоставлением типов](/ru/clickstack/self-configured/migration/elastic/types). Инструкции по миграции данных для самоуправляемых развертываний приведены ниже отдельно.

## Стратегия параллельной эксплуатации {#parallel-operation-strategy-self-configured}

При миграции с Elastic на ClickHouse Observability для сценариев обсервабилити мы рекомендуем не переносить исторические данные, а использовать подход **параллельной эксплуатации**. Эта стратегия даёт ряд преимуществ:

1. **Минимальный риск**: пока обе системы работают конкурентно, вы сохраняете доступ к существующим данным и панелям мониторинга, параллельно проверяя ClickHouse Observability и знакомя пользователей с новой системой.
2. **Естественное устаревание данных**: у большинства данных обсервабилити ограниченный срок хранения (как правило, 30 дней или меньше), поэтому переход происходит естественным образом по мере устаревания данных в Elastic.
3. **Упрощённая миграция**: не нужны сложные инструменты или процессы передачи данных для переноса исторических данных между системами.

<br />

<Info>
  **Миграция данных**

  В самоуправляемых развертываниях можно использовать движок таблицы `Elasticsearch`, чтобы читать исторические документы и копировать их в таблицы ClickHouse. См. раздел [Миграция данных](#migrating-data-self-configured). Этот способ не связан с путём ингестии через OTLP, который используется в полностью управляемом ClickHouse Observability.
</Info>

### Этапы внедрения {#implementation-steps-self-configured}

<Steps>
  <Step title="Настройте двойной приём данных" id="configure-dual-ingestion-self-configured">
    Настройте конвейер сбора данных так, чтобы он одновременно отправлял данные и в Elastic, и в ClickHouse Observability. Для полностью управляемого ClickHouse Observability конвейер должен экспортировать данные по протоколу OTLP на управляемую конечную точку с использованием вашего ключа API для ингестии. Пересылать на эту конечную точку JSON-документы Elasticsearch недостаточно.

    Способ реализации зависит от агентов, которые вы сейчас используете для сбора данных, — см. раздел [«Миграция агентов»](/ru/clickstack/observability/migration/elastic/migrating-agents).
  </Step>

  <Step title="Скорректируйте сроки хранения" id="adjust-retention-period-self-configured">
    Проверьте сроки хранения в обеих системах, чтобы исторические данные оставались доступны на протяжении всего переходного периода. Рекомендации для конкретных вариантов развертывания см. в разделе [Хранение и TTL](#retention-and-ttl-self-configured).
  </Step>

  <Step title="Проверьте и сравните" id="validate-and-compare-self-configured">
    * Выполните запросы к обеим системам, чтобы убедиться в согласованности данных
    * Сравните производительность запросов и их результаты
    * Перенесите панели мониторинга и оповещения в ClickHouse Observability. Пока это делается вручную.
    * Убедитесь, что все критически важные панели мониторинга и оповещения работают в ClickHouse Observability должным образом
  </Step>

  <Step title="Постепенный переход" id="graudal-transition-self-configured">
    * По мере того как данные в Elastic естественным образом устаревают и удаляются, вы будете всё больше опираться на ClickHouse Observability
    * Убедившись в надёжности ClickHouse Observability, можно начать перенаправлять на него запросы и панели мониторинга
  </Step>
</Steps>

### Долгосрочное хранение {#long-term-retention-self-configured}

Для организаций, которым требуются более длительные сроки хранения:

* Продолжайте эксплуатировать обе системы параллельно, пока срок хранения всех данных в Elastic не истечет
* Для самоуправляемых развертываний рассмотрите возможность использования [materialized view](/ru/concepts/features/materialized-views/incremental-materialized-view), чтобы сохранять агрегированные или отфильтрованные исторические данные, позволяя при этом необработанным данным удаляться по истечении срока хранения.

### Сроки миграции {#migration-timeline-self-configured}

Сроки миграции зависят от ваших требований к сроку хранения данных:

* **Срок хранения 30 дней**: миграцию можно завершить в течение месяца.
* **Более длительный срок хранения**: продолжайте параллельную эксплуатацию, пока срок хранения данных в Elastic не истечёт.
* **Исторические данные**: прежде чем планировать импорт, ознакомьтесь с рекомендациями для вашего варианта развертывания в разделе [Миграция данных](#migrating-data-self-configured).

## Срок хранения и TTL {#retention-and-ttl-self-configured}

<Tabs>
  <Tab title="Полностью управляемый">
    <BetaBadge label="Сервис в стадии бета-тестирования" />

    <Note>
      На этапе бета-тестирования полностью управляемый ClickHouse Observability хранит данные в течение 30 дней. Срок хранения будет изменён с выходом в общий доступ (GA); дополнительные инструкции будут опубликованы позже.
    </Note>

    Планируйте переход с учётом этого 30-дневного срока хранения и срока хранения данных в Elastic. Сохраняйте доступ к Elastic для поиска по историческим данным, пока эти данные не перестанут быть нужны.
  </Tab>

  <Tab title="Самоуправляемый">
    ClickHouse использует [секции `TTL`](/ru/clickstack/self-configured/managing/production#configure-ttl-managed) в таблицах `MergeTree` для автоматического удаления данных с истекшим сроком действия.

    Согласуйте срок хранения данных в таблицах с требованиями к миграции. Примеры см. в разделе [Настройка TTL для самоуправляемого продакшн-развёртывания](/ru/clickstack/self-configured/managing/production#configure-ttl-managed).
  </Tab>
</Tabs>

## Миграция данных {#migrating-data-self-configured}

<Tabs>
  <Tab title="Полностью управляемый">
    <BetaBadge label="Сервис в стадии бета-тестирования" />

    <Note>
      В настоящее время не существует прямого способа миграции исторических данных из Elasticsearch в полностью управляемый ClickHouse Observability. Управляемая конечная точка принимает телеметрию в формате OTLP, а не документы Elasticsearch или выгрузки в JSON. Рабочий процесс с движком таблицы `Elasticsearch`, описанный на вкладке для самоуправляемого развёртывания, неприменим к полностью управляемым сервисам.
    </Note>

    Используйте параллельную ингестию: отправляйте новую телеметрию в **формате OTLP** в управляемый сервис, а исторические данные оставьте в Elastic. Сведения об управляемой конечной точке и настройках аутентификации см. в разделе [Загрузка данных с помощью OpenTelemetry](/ru/clickstack/observability/ingesting-data/opentelemetry), а варианты сбора данных — в разделе [Миграция агентов](/ru/clickstack/observability/migration/elastic/migrating-agents).

    Если исторические данные всё же необходимо импортировать, потребуется пользовательский конвейер, который преобразует документы Elasticsearch в соответствующие журналы, трассировки или метрики OpenTelemetry и экспортирует их по OTLP. Готового преобразователя в этом руководстве нет. Прежде чем планировать дозагрузку, учтите срок хранения данных в управляемом сервисе.
  </Tab>

  <Tab title="Самоуправляемый">
    Используйте [движок таблиц `Elasticsearch`](/ru/reference/engines/table-engines/integrations/elasticsearch), чтобы читать документы напрямую из Elasticsearch, а затем копировать их в локальную таблицу ClickHouse с помощью `INSERT INTO ... SELECT`. Ни файл экспорта, ни установка `elasticdump` не требуются.

    Движок работает только на чтение: созданная таблица `Elasticsearch` делает удалённые документы доступными для запросов, но не копирует их в хранилище ClickHouse.

    <Note>
      Интеграция с Elasticsearch является экспериментальной и требует `enable_elasticsearch = 1` в версии ClickHouse, которая её поддерживает. Требуется Elasticsearch 7.12 или новее; OpenSearch не поддерживается. Ваш сервис ClickHouse должен иметь доступ к конечной точке Elasticsearch, а для чтения содержимого документов в индексе должен быть включён `_source`.
    </Note>

    <Steps>
      <Step title="Подключение к индексу Elasticsearch" id="connect-elasticsearch-self-managed">
        Выполните следующий SQL-код в своём самоуправляемом сервисе ClickHouse Cloud, подставив собственные конечную точку, индекс и учётные данные:

        ```sql
        SET enable_elasticsearch = 1;

        CREATE TABLE elasticsearch_source
        ENGINE = Elasticsearch(
            'https://<elasticsearch-host>:9200',
            '<index-name>',
            '<username>',
            '<password>'
        );

        SELECT _index, _id, document
        FROM elasticsearch_source
        LIMIT 10;
        ```

        Таблица представляет `_source` каждого документа в виде столбца `document` типа `JSON`. Виртуальные столбцы `_id` и `_index` указывают на исходный документ и индекс. Прежде чем выбирать целевую схему, изучите образец данных.

        Движок также поддерживает API-ключи и именованные коллекции. См. [справочник по аутентификации](/ru/reference/functions/table-functions/elasticsearch#authentication).
      </Step>

      <Step title="Копирование документов в ClickHouse" id="copy-documents-self-managed">
        В этом примере документы сохраняются как `JSON` в staging-таблице, чтобы их можно было изучить и преобразовать перед настройкой источника обсервабилити. Выполните запросы в той же базе данных, где находится `elasticsearch_source`:

        ```sql
        CREATE TABLE migrated_elasticsearch_documents
        (
            source_index String,
            document_id String,
            document JSON
        )
        ENGINE = MergeTree
        ORDER BY (source_index, document_id);

        INSERT INTO migrated_elasticsearch_documents
        SELECT _index, _id, document
        FROM elasticsearch_source;
        ```

        При каждом чтении используется механизм point in time Elasticsearch, который обеспечивает согласованный снимок в рамках запроса. Это однократное копирование, а не непрерывная репликация. Повторная вставка добавит строки ещё раз: ключ сортировки не устраняет дубликаты документов.

        При импорте больших объёмов разбейте работу на непересекающиеся пакеты с помощью аргумента движка `query`. Задавайте абсолютные границы временных меток в Elasticsearch Query DSL: условие `WHERE` в ClickHouse не передаёт фильтры в Elasticsearch. См. [примеры использования движка](/ru/reference/engines/table-engines/integrations/elasticsearch#usage-example) и [ограничения](/ru/reference/functions/table-functions/elasticsearch#limitations).
      </Step>

      <Step title="Сопоставление и проверка импортированных данных" id="validate-import-self-managed">
        Сравните количество документов и характерные записи с исходным снимком. Прежде чем использовать данные для поиска или дашбордов, проверьте временные метки, отсутствующие поля и вложенные значения. Тип `JSON` может выводить типы из значений, в том числе временных меток, поэтому их текстовое представление может измениться. Чтобы управлять типами полей, используйте явные подсказки типов JSON.

        Спроектируйте целевую схему обсервабилити с учётом ваших запросов и требований к хранению, а затем с помощью `INSERT INTO ... SELECT` извлеките и преобразуйте поля из staging-таблицы. Ознакомьтесь с материалами [Концепции Elasticsearch и ClickHouse](/ru/clickstack/self-configured/migration/elastic/concepts), [Сопоставления типов](/ru/clickstack/self-configured/migration/elastic/types) и [рекомендациями по проектированию схемы](/ru/guides/clickhouse/data-formats/json/schema).

        Копирование документов не преобразует их автоматически в схему OpenTelemetry и не настраивает источник в интерфейсе. Настройте таблицу, а также сопоставления временной метки, сообщения и других полей с помощью [параметров конфигурации](/ru/clickstack/self-configured/managing/config).
      </Step>
    </Steps>
  </Tab>
</Tabs>
