Если вы уже какое-то время используете ClickStack, то, вероятно, заметили, что схема по умолчанию справляется с большинством рабочих нагрузок обсервабилити без каких-либо изменений. Эта страница — для случаев, когда этого уже недостаточно: задержка запросов начинает расти или ваши шаблоны доступа заметно отошли от тех, на которые рассчитаны настройки по умолчанию.

На практике основной эффект дают четыре оптимизации. Они перечислены примерно в порядке возрастания трудозатрат. Первые две — локальные изменения через `ALTER TABLE`, которые можно внедрять инкрементально. Третья окупается, когда на панели мониторинга раз за разом выполняется один и тот же запрос с aggregation. Четвёртая требует миграции таблицы, поэтому она самая трудоёмкая.

Описания ниже намеренно краткие. Обоснование каждого изменения, тесты производительности и пошаговые инструкции по применению изменений к существующим данным см. в разделе [Настройка производительности](/ru/clickstack/self-configured/managing/performance-tuning).

<Steps>
  <Step title="Материализуйте часто запрашиваемые атрибуты" id="materialize-attributes">
    Фильтрация по `LogAttributes['service.version']` заставляет ClickHouse загружать и декодировать весь Map `LogAttributes` для каждой проверяемой строки. Если вынести атрибут в столбец `MATERIALIZED`, тот же фильтр сведётся к чтению одного столбца, что обычно на порядок быстрее. Как только столбец появится, ClickStack начнёт автоматически переписывать фильтр, поэтому сохранённые поиски и панели мониторинга продолжат работать без изменений.

    Выбирайте атрибуты, которые вы действительно часто запрашиваете. Каждый материализованный столбец занимает место на диске и увеличивает время вставки, поэтому принцип здесь — «выносить то, что используется», а не «выносить всё».

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    Для существующих строк новый столбец остаётся пустым, пока вы дополнительно не выполните `ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion`.

    Подробнее: [Материализация часто запрашиваемых атрибутов](/ru/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes).
  </Step>

  <Step title="Добавьте индексы пропуска данных" id="add-skip-indexes">
    Индексы пропуска данных позволяют ClickHouse отбрасывать гранулы, которые заведомо не соответствуют фильтру, и вместо полного сканирования читать лишь небольшую нужную часть данных. Стоит знать о трёх типах:

    * **Текстовые индексы** (`text(tokenizer = ...)`) на строковых столбцах и на массивах `mapKeys`/`*AttributeItems`. В схеме журналов по умолчанию они уже есть.
    * **Min-max-индексы** на числовых столбцах, фильтруемых по диапазону. Классический пример — `Duration` трассы.
    * **Фильтры Блума** для поиска по равенству в столбцах с высокой мощностью в версиях ClickHouse, которые ещё не поддерживают текстовые индексы.

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    Индекс пропуска данных окупает затраты на свою проверку, только если действительно отсекает гранулы. Прежде чем считать, что он помог, проверьте это с помощью `EXPLAIN indexes = 1` на типичном запросе.

    Подробнее: [Добавление индексов пропуска данных](/ru/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes).
  </Step>

  <Step title="Предварительно вычисляйте повторяющиеся агрегации" id="materialized-views">
    Когда одна и та же агрегация раз за разом выполняется на панели мониторинга (топ сервисов по доле ошибок, задержка p99 по эндпоинтам, число запросов в минуту), materialized view вычисляет результат в момент вставки и записывает его в небольшую агрегированную таблицу. В результате панели мониторинга обращаются к ней, а не к исходным журналам или трассировкам, что обходится несравнимо дешевле.

    Это оправдано, когда панелью активно пользуются, а исходная таблица велика. Цена — дополнительная нагрузка на CPU при вставке и ещё одна таблица, которую нужно сопровождать.

    Подробнее: [Использование materialized views](/ru/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views).
  </Step>

  <Step title="Выберите первичный ключ под свой шаблон доступа" id="choose-primary-key">
    Первичный ключ определяет порядок сортировки строк на диске. Фильтры по ведущим столбцам этого ключа позволяют ClickHouse сразу перейти к нужной области данных; если же фильтр не затрагивает ведущие столбцы, сканируется вся партиция.

    Ключ журналов по умолчанию `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)` оптимизирован для запросов вида «что произошло за последние N минут в сервисе X». Если большинство ваших запросов фильтрует по другому столбцу (ID тенанта, ID клиента, регион), то наибольший эффект даст изменение первичного ключа так, чтобы он начинался с этого столбца.

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- те же столбцы, что и в otel_logs
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse не позволяет изменить первичный ключ существующей таблицы, поэтому потребуется миграция таблицы, а не простой `ALTER`. В руководстве по настройке производительности пошагово описано, как создать новую таблицу, перенаправить приём данных и использовать таблицу `Merge`, чтобы существующие панели мониторинга продолжали работать как со старыми, так и с новыми данными.

    Подробнее: [Изменение первичного ключа](/ru/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key).
  </Step>
</Steps>
