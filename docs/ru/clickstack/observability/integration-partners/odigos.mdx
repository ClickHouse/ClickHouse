## Что такое Odigos? {#what-is-odigos}

{/* vale on */}

[Odigos](https://odigos.io/) — это плоскость управления инструментированием для Kubernetes и виртуальных машин, которая инструментирует приложения на уровне ядра с помощью **eBPF**. Поскольку сбор данных выполняется в ядре, накладные расходы для приложений остаются низкими, а наблюдаемость — высокой. Вы получаете трассировку, метрики, журналы и профили OpenTelemetry промышленного уровня без внедрения новых агентов в прикладной код и без ожидания обновлений библиотек во всех сервисах.

Именно слой eBPF позволяет получать глубокую и согласованную телеметрию в больших масштабах. При необходимости Odigos может автоматически включать и отключать более глубокое инструментирование, чтобы упростить отладку и устранение неполадок:

* **Контекст на уровне кода** — атрибуты, связанные с функциями и поведением среды выполнения
* **HTTP-трафик** — запросы и ответы между вашими сервисами
* **Системы обмена сообщениями** — полезные нагрузки и сообщения из Kafka и аналогичных брокеров
* **Подробные сведения об ошибках** — трассировки стека при сбоях
* **Пользовательское инструментирование** — расширение охвата там, где заканчиваются возможности автоматического инструментирования, без изменений кода и перезапусков

Под капотом Odigos создает полноценный конвейер OpenTelemetry для вашего кластера и управляет им: коллекторы, масштабируемые в зависимости от нагрузки, маршрутизация в выбранные вами хранилища и логика конвейера, которой вы управляете через интерфейс. Настройте **сэмплирование** для контроля объема данных, **маскирование PII**, чтобы конфиденциальные данные не попадали в экспорт, и **правила OTTL**, чтобы фильтровать, преобразовывать или обогащать телеметрию до того, как она покинет кластер.

## Почему Odigos + ClickHouse Observability? {#why-odigos-clickstack}

{/* vale on */}

Внедрение OpenTelemetry во множестве сервисов, как правило, отнимает много времени и даёт лишь поверхностное представление о работе приложений. Odigos берёт на себя eBPF-инструментирование для получения более глубокой телеметрии и управление коллекторами в Kubernetes, а ClickHouse Observability предоставляет хранилище на базе ClickHouse и интерфейс ClickStack для выполнения запросов к телеметрии в больших масштабах.

<Tip>
  **Основные выводы**

  * **Odigos** автоматически инструментирует любую рабочую нагрузку Kubernetes без перезапуска и сам управляет конвейерами OpenTelemetry.
  * **ClickHouse Observability** хранит журналы, метрики и трассировки в ClickHouse и отображает их в интерфейсе ClickStack.
</Tip>

## Предварительные требования {#prerequisites}

* Сервис ClickHouse Observability, доступный из вашего кластера Kubernetes. См. раздел [Начало работы](/ru/clickstack/observability/getting-started). Для самоуправляемых развертываний см. раздел [Самоуправляемая настройка](/ru/clickstack/self-configured/deployment/managed).
* **Конечная точка OTLP по HTTP** и ключ API для приёма данных из раздела **Team Settings → Data → Managed Telemetry**. Для самоуправляемых развертываний используйте конечную точку вашего автономного коллектора и `OTLP_AUTH_TOKEN`.
* **Кластер Kubernetes** (узлы Linux с ядром 4.18 или новее для инструментирования на основе eBPF)
* **Helm**, **kubectl** и учётные данные кластера с правами на установку в пространство имён `odigos-system`
* **Токен Odigos Enterprise для развертывания в собственной инфраструктуре** — чтобы получить доступ, свяжитесь с [командой Odigos](https://odigos.io/)

## Интеграция ClickHouse Observability с Odigos {#integrate-odigos-clickstack}

{/* vale on */}

<Steps>
  <Step title="Разверните Odigos с помощью Helm" id="deploy-odigos">
    Для Odigos Enterprise требуется лицензионный токен для развертывания в собственной инфраструктуре. Экспортируйте его в командной оболочке:

    ```bash
    export ODIGOS_ONPREM_TOKEN="<your-enterprise-token>"
    ```

    Также перед установкой можно сохранить токен в секрете Kubernetes с именем `odigos-pro`. Подробнее см. в [документации Odigos Enterprise](https://enterprise.docs.odigos.io/) (требуется доступ).

    Добавьте Helm-репозиторий Odigos и установите чарт в пространство имён `odigos-system`:

    ```bash
    helm repo add odigos https://odigos-io.github.io/odigos/
    helm repo update

    helm upgrade --install odigos odigos/odigos \
      --namespace odigos-system \
      --create-namespace \
      --set onPremToken=$ODIGOS_ONPREM_TOKEN
    ```

    Дополнительные переопределения конфигурации можно передать с помощью флагов `--set` или пользовательского файла значений (`-f`). Чтобы просмотреть значения чарта по умолчанию, выполните `helm show values odigos/odigos`.

    Убедитесь, что поды Odigos запущены:

    ```bash
    kubectl get pods -n odigos-system
    ```
  </Step>

  <Step title="Добавьте источники в интерфейсе Odigos" id="add-sources">
    1. Пробросьте порт сервиса интерфейса Odigos:

    ```bash
    kubectl port-forward svc/ui -n odigos-system 3000:3000
    ```

    2. Откройте [http://localhost:3000](http://localhost:3000) в браузере.
    3. Перейдите в раздел **Sources** и выберите пространства имён или рабочие нагрузки, которые нужно инструментировать.
    4. Отметив все рабочие нагрузки для инструментирования, нажмите кнопку «Done» внизу страницы.
    5. Убедитесь по столбцу Sources, что рабочие нагрузки успешно инструментированы.
  </Step>

  <Step title="Добавьте ClickHouse Observability как пункт назначения в интерфейсе Odigos" id="add-destination-ui">
    Чтобы отправлять телеметрию, добавьте в Odigos пункт назначения **OTLP HTTP**. Выберите ниже свой тип развертывания.

    <Tabs>
      <Tab title="Полностью управляемый">
        <BetaBadge label="Сервис в стадии бета-тестирования" />

        ClickHouse Observability предоставляет конечную точку OTLP. ClickHouse берёт на себя ингестию, схемы и вычислительные ресурсы. Вам остаётся лишь направить Odigos на эту конечную точку — разворачивать коллектор не требуется.

        1. В интерфейсе Odigos нажмите **Add Destination** и выберите **OTLP HTTP**.
        2. В поле **OTLP HTTP Endpoint** укажите конечную точку HTTPS из ClickHouse Cloud вместе с портом `4318`. Например, `https://<service-id>.otel.<region>.aws.clickhouse.com:4318`.
        3. В разделе **Headers** добавьте:
           * **Key**: `Authorization`
           * **Value**: `Bearer <YOUR_INGESTION_API_KEY>`
        4. Включите **Logs**, **Metrics** и **Traces**.
        5. Сохраните пункт назначения.
      </Tab>

      <Tab title="Самоуправляемый">
        <Tip>
          **Альтернатива: запись напрямую в ClickHouse**

          Для самоуправляемых развертываний вместо запуска OTLP-коллектора можно использовать [нативный пункт назначения **ClickHouse**](#native-clickhouse-destination) в Odigos — при условии, что ваш сервис ClickHouse доступен из кластера Kubernetes. В полностью управляемых развертываниях необходимо использовать управляемую конечную точку OTLP.
        </Tip>

        В случае самоуправляемого развертывания самостоятельно запустите [дистрибутив коллектора ClickStack в автономном режиме](/ru/clickstack/self-configured/ingesting-data/collector#configuring-the-collector-self-configured) и при запуске контейнера задайте токен аутентификации в переменной окружения `OTLP_AUTH_TOKEN`. Odigos будет отправлять трафик OTLP HTTP на этот коллектор, передавая тот же токен в заголовке `Authorization`.

        1. Запустите коллектор ClickStack в автономном режиме, указав ваш сервис ClickHouse Cloud и защитив коллектор произвольным значением `OTLP_AUTH_TOKEN`:

           ```shell
           export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
           export CLICKHOUSE_USER=<CLICKHOUSE_USER>
           export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
           export OTLP_AUTH_TOKEN="a_very_secure_string"

           docker run \
             -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
             -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
             -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
             -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
             -p 4317:4317 \
             -p 4318:4318 \
             clickhouse/clickstack-otel-collector:latest
           ```

           О настройке TLS, выделенных пользователях для ингестии и других рекомендациях для продакшна см. раздел [Защита коллектора](/ru/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        2. В интерфейсе Odigos нажмите **Add Destination** и выберите **OTLP HTTP**.
        3. В поле **OTLP HTTP Endpoint** укажите адрес только что запущенного автономного коллектора (например, `http://my-collector.example.com:4318`).
        4. В разделе **Headers** добавьте:
           * **Key**: `Authorization`
           * **Value**: значение `OTLP_AUTH_TOKEN`, заданное для коллектора
        5. Включите **Logs**, **Metrics** и **Traces**.
        6. Сохраните пункт назначения.

        <Info>
          **Необязательно: манифест Kubernetes**

          Вместо интерфейса тот же пункт назначения можно настроить с помощью манифеста `Destination`. См. раздел [Настройка пунктов назначения с помощью манифестов Kubernetes](#destination-manifest) в расширенной конфигурации.
        </Info>
      </Tab>
    </Tabs>
  </Step>

  <Step title="Проверьте телеметрию в ClickHouse Observability" id="verify-telemetry">
    1. Откройте интерфейс ClickStack:
       * **Самоуправляемый вариант**: откройте свой сервис в [консоли ClickHouse Cloud](https://console.clickhouse.cloud) и нажмите **Launch ClickStack**. Подробнее см. в разделе [Переход к интерфейсу ClickStack](/ru/clickstack/self-configured/deployment/managed).
       * **Полностью управляемый вариант**: откройте раздел обсервабилити для своего сервиса ClickHouse Cloud.
    2. Убедитесь, что в разделах **Logs**, **Metrics** и **Traces** появились данные от ваших инструментированных сервисов.
    3. Отфильтруйте трассы по `odigos.version`, чтобы убедиться, что сквозной экспорт работает корректно.

    Если данных нет, проверьте журналы коллектора: `kubectl logs deploy/odigos-gateway -n odigos-system`
  </Step>
</Steps>

## Расширенная конфигурация {#advanced-configuration}

### Нативный пункт назначения ClickHouse {#native-clickhouse-destination}

Нативный пункт назначения ClickHouse доступен только для **самоуправляемых** развертываний. Для **полностью управляемых** развертываний используйте пункт назначения **OTLP HTTP** с конечной точкой вашего управляемого сервиса.

<Tabs>
  <Tab title="Самоуправляемый">
    Если ClickHouse напрямую доступен из вашего кластера, вместо OTLP HTTP можно использовать нативный пункт назначения **ClickHouse** в Odigos. Задайте конечную точку ClickHouse, имя базы данных и параметры схемы в интерфейсе или с помощью манифеста — см. [направление ClickHouse в Odigos](https://docs.odigos.io/backends/clickhouse).

    * **Схема для продакшна**: задайте для `CLICKHOUSE_CREATE_SCHEME` значение `false` и примените собственный DDL.
    * **TLS и аутентификация**: используйте `CLICKHOUSE_TLS_ENABLED`, `CLICKHOUSE_USERNAME`, а пароль храните в секрете Kubernetes.

    **Манифест Kubernetes**

    ```yaml
    apiVersion: odigos.io/v1alpha1
    kind: Destination
    metadata:
      name: clickhouse
      namespace: odigos-system
    spec:
      type: clickhouse
      destinationName: clickhouse
      signals:
        - TRACES
        - METRICS
        - LOGS
      data:
        CLICKHOUSE_ENDPOINT: 'http://clickstack.example.com:8123'
        CLICKHOUSE_DATABASE_NAME: 'otel'
        CLICKHOUSE_CREATE_SCHEME: 'true'
    ```

    Сохраните манифест в файл `destination.yaml` и примените его:

    ```bash
    kubectl apply -f destination.yaml
    ```

#### Нормализатор журналов HyperDX {#hyperdx-log-normalizer}

    Для самоуправляемых развертываний, которые экспортируют данные напрямую в ClickHouse через нативный пункт назначения **ClickHouse** в Odigos, включите **нормализатор журналов HyperDX** (`HYPERDX_LOG_NORMALIZER: true`). Он разбирает JSON в телах журналов и нормализует атрибуты, что упрощает выполнение запросов в интерфейсе ClickStack. Эта настройка не действует для полностью управляемого пункта назначения OTLP.
  </Tab>
</Tabs>

### Настройка пунктов назначения с помощью манифестов Kubernetes {#destination-manifest}

**OTLP HTTP (ClickStack)**

```yaml
apiVersion: odigos.io/v1alpha1
kind: Destination
metadata:
  name: clickstack
  namespace: odigos-system
spec:
  type: otlphttp
  destinationName: otlphttp
  signals:
    - TRACES
    - METRICS
    - LOGS
  data:
    OTLP_HTTP_ENDPOINT: 'http://clickstack.example.com:4318'
    # Self-managed: OTLP_AUTH_TOKEN
    # ClickHouse Observability: Bearer <YOUR_INGESTION_API_KEY>
    OTLP_HTTP_HEADERS: 'Authorization:<YOUR_AUTHORIZATION_VALUE>'
```

Примените манифест:

```bash
kubectl apply -f destination.yaml
```

### Odigos VM Agent {#odigos-vm-agent}

{/* vale on */}

[Odigos VM Agent](https://docs.odigos.io/vmagent/overview) инструментирует процессы Linux, сервисы systemd и/или контейнеры Docker с помощью eBPF. Телеметрия экспортируется в те же пункты назначения, что и при развертывании Odigos в кластере, включая ClickHouse Observability по OTLP HTTP.

VM Agent входит в состав Odigos Pro. Информацию о настройке, источниках и конфигурации пунктов назначения см. в разделе [Обзор VM Agent](https://docs.odigos.io/vmagent/overview).

{/* vale off */}

### Odigos Central {#odigos-central}

{/* vale on */}

[Odigos Central](https://docs.odigos.io/central/overview) — это централизованная плоскость управления, которая позволяет управлять инструментированием, пунктами назначения и конфигурацией конвейеров сразу в нескольких кластерах Kubernetes из единого интерфейса, не настраивая каждый кластер по отдельности.

Odigos Central доступен в Odigos Enterprise. Подробнее об управлении несколькими кластерами, SSO и единых правилах сэмплирования см. в разделе [Обзор Central](https://docs.odigos.io/central/overview).
