## Переменные дашборда в PromQL и Lucene {#dashboard-variables-in-promql-and-lucene}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/q5pP20p4nY4" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Переменные дашборда теперь работают в чартах PromQL: для ссылок на переменные доступно автодополнение, а при отсутствующих переменных или неподдерживаемом использовании (например, макросах или ссылках, которые нужно заключить в кавычки) выводятся предупреждения. Рядом с существующей панелью сгенерированного SQL появился предварительный просмотр сгенерированного PromQL, где отображается запрос с подставленными текущими значениями.

Переменные Lucene теперь поддерживают точное совпадение. Раньше `ServiceName:$service` раскрывалось в `ServiceName:("add" OR "cart")`. Совпадение по полю Lucene без кавычек означает поиск подстроки, поэтому выражение превращалось в `ServiceName ILIKE '%add%' OR ServiceName ILIKE '%cart%'`. В итоге можно было выбрать два сервиса, а получить четыре.

Если заключить переменную в кавычки — `ServiceName:"$service"`, — она теперь раскрывается в `(ServiceName:"add" OR ServiceName:"cart")`, то есть каждое выбранное значение сопоставляется точно. Так же уже работают совпадения по полю в кавычках без переменных. Автодополнение тоже предлагает вариант с кавычками.

При переходе на страницу поиска из всплывающей подсказки чарта или строки таблицы переменные и макросы теперь раскрываются заранее. Страница поиска не поддерживает переменные, поэтому передача необработанного `$service` раньше приводила к некорректным результатам или ошибке запроса. Макросы без выбранных значений раскрываются в `(1=1)`. В поле ввода `WHERE` на странице поиска это выглядит не слишком красиво, зато запрос остаётся корректным.

Выбранные значения фильтров теперь индексируются по имени переменной, а не по выражению. Два фильтра с одинаковым выражением, например `ServiceName` из разных источников, больше не делят общую выборку.

Если нажать Escape при редактировании фильтра, теперь появится запрос подтверждения перед отменой изменений — как и предлагал Brandon. Раньше попытка закрыть всплывающую подсказку могла стереть все правки.

На этой неделе переменные дашборда вышли в продакшн. Переключатель возможности удалён, а формы ссылок и макросы описаны в [публичной документации](https://clickhouse.com/docs/clickstack/features/dashboards/overview#dashboard-variables).

## Ссылки между спанами в обоих направлениях {#span-links-in-both-directions}

*Демо от [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/tdK9JU6unoE" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Ссылки между спанами уже давно можно было просматривать, но только со стороны потребителя. Каждая ссылка отображалась как действие «Open trace», и начать со спана producer и найти ссылающиеся на него спаны было невозможно. Об этой функции попросил один из пользователей в задаче на GitHub.

Теперь в разделе Span Links для каждого целевого спана отображаются его имя, сервис, длительность и временная метка. Благодаря этому проще выбрать нужную ссылку из нескольких, не открывая каждую. Если целевой спан найти не удаётся, в качестве резервного варианта по-прежнему используется «Open trace».

В новом разделе «Linked from» перечислены спаны, которые ссылаются на текущий спан. Теперь можно перейти по ссылке потребителя к его producer и увидеть там этого потребителя в списке.

Если перейти по ссылке на предыдущий спан в цепочке навигации, вы вернётесь к соответствующей записи, поэтому при перемещении между двумя связанными спанами дубликаты больше не накапливаются. Если между ними есть другие записи, новая запись добавляется как обычно.

Обратный поиск находит строки, в ссылках которых содержится идентификатор выбранного спана, а затем проверяет совпадение идентификатора трассы. Поиск по идентификатору трассы ускоряется за счёт индекса bloom-фильтра на этом столбце, однако обратный поиск требует сканирования и на больших таблицах трассировки может работать медленнее, чем в демонстрации. Если это станет проблемой, можно добавить индекс по идентификатору спана в ссылке, как предлагается в комментариях в коде.

## Обсервабилити для LLM из коробки {#llm-observability-out-of-the-box}

*Демо от [@wrn14897](https://github.com/wrn14897)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/m49DZ5cuI64" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Многие команды уже отправляют в ClickStack телеметрию LLM и агентов для написания кода, однако специальной поддержки для неё не было: ни отображения чатов, ни учёта токенов и затрат, ни аналитики по моделям.

Теперь наряду с существующими пресетами для ClickHouse, Kubernetes и сервисов появилась панель мониторинга для LLM. Она показывает расход токенов, затраты, вызовы моделей и инструментов, попадания в кэш и время ответа, а при наличии атрибута пользователя — разбивку по пользователям.

Панель считывает уже имеющиеся трассировки и журналы во время выполнения запроса, не требуя фиксированной схемы, выделенных таблиц или обработки на этапе приёма. Поддерживается телеметрия по общепринятым соглашениям, OpenLLMetry или OpenInference, включая данные из SDK OpenAI и Anthropic, Vercel AI SDK, LangChain, Claude Code и opencode. Это работает и для уже собранной телеметрии.

Представление задержек выводит наверх спаны, связанные с ИИ, поэтому медленный вызов модели легко найти, не просматривая всю трассу.

Представление сеансов группирует спаны по диалогам. Откройте сеанс, чтобы увидеть его спаны, затем выберите нужный, чтобы посмотреть подробности, включая промпт, если он был записан. Это помогает при отладке запусков агентов; кроме того, по журналам можно искать с тем же фильтром сеанса.

Возможности намеренно уже, чем у специализированных инструментов обсервабилити для LLM, таких как Langfuse, который поддерживает также оценки и многое другое. Здесь закрываются типовые задачи мониторинга — частота ошибок, затраты, токены и задержка — на основе телеметрии, уже имеющейся в ClickStack.

**Связанные запросы на слияние:** [#2990](https://github.com/hyperdxio/hyperdx/pull/2990) Панель обсервабилити для LLM, представление чата для спанов и сеансы

## Просмотр метрик в редакторе чартов {#browsing-metrics-in-the-chart-editor}

*Демо от [@MikeShi42](https://github.com/MikeShi42)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/TkFa6Zzq23o" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше, чтобы выбрать метрику, приходилось искать её в плоском списке, где для каждого вида могло быть до 3,000 имён. Автодополнение помогает, если вы примерно представляете, что ищете, но в отзывах не раз просили добавить возможность просмотра.

Теперь рядом с полем выбора метрики есть элемент «Browse metrics», который открывает обозреватель: слева — каталог, справа — сведения о выбранной метрике. Имена метрик разбиваются по точкам и символам подчёркивания и выстраиваются в дерево. Сегменты с единственным дочерним элементом объединяются, чтобы не делать лишних щелчков. Столбцы `Metric`, `Type` и `Unit` остаются выровненными на всех уровнях. Можно искать по всему каталогу или переключиться на плоский список.

Раньше единица измерения, описание и метки становились доступны только после выбора метрики — в свёрнутой панели под строкой серии. Панель сведений позволяет изучить их заранее: вы сразу видите, какие данные отправляет ваше развертывание и по каким меткам можно группировать. Нажмите «Use metric», чтобы применить выбор к редактируемой серии.

Пока функция дорабатывается, она спрятана в неприметном месте.

## Объём журналов для запросов Raw SQL в Grafana {#log-volume-for-raw-sql-queries-in-grafana}

*Демо от [@SpencerTorres](https://github.com/SpencerTorres)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/uehh44q56yE" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Небольшое визуальное изменение, которое потребовало больше усилий, чем ожидалось.

В Grafana над результатами запросов к журналам, созданных в конструкторе запросов, отображается гистограмма объёма, поскольку плагин знает, какие столбцы использовать. Для того же запроса в редакторе SQL гистограмма не отображалась: плагин не мог определить, какие столбцы вы выбрали. В разделе Explore вместо неё выводилась гистограмма Grafana на основе строк, которая ограничивалась значением `LIMIT` в запросе и не учитывала выбранный временной диапазон.

Теперь плагин удаляет концевые `ORDER BY` и `LIMIT`, оборачивает ваш SQL в производную таблицу и выполняет агрегацию по всему временному диапазону. Удаление `LIMIT` здесь принципиально: если его оставить, подсчёт ограничится строками, возвращёнными исходным запросом.

Гистограмма учитывает фильтры из вашего SQL и обновляется при изменении временного диапазона. Это работает как для SQL, написанного вручную, так и для запросов, открытых через «Edit as SQL» в конструкторе запросов.

Вероятно, всё ещё остаются пограничные случаи, в которых переписывание запроса не сработает.

**Связанные запросы на слияние:** [grafana/clickhouse-datasource#2141](https://github.com/grafana/clickhouse-datasource/pull/2141) отображение объёма журналов для запросов в редакторе SQL (открыт)

## Каналы уведомлений на страницах оповещений {#notification-channels-on-the-alerts-pages}

*Демо от [@jordan-simonovski](https://github.com/jordan-simonovski)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Gr-QkVVWam8" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Оповещение может отправлять уведомления на десять вебхуков, однако в списке оповещений и в заголовке страницы оповещения отображался только первый из них, причём с подписью «Webhook» вместо его имени. Оба элемента по-прежнему брали данные из устаревшего поля, рассчитанного на один канал.

Диспетчеризация на несколько каналов работала, но из-за такого отображения казалось, что дополнительные каналы не сохранились.

Теперь в списке и в заголовке страницы оповещения отображаются все настроенные каналы с их именами. Кроме того, стало проще добавлять и удалять каналы, включая вебхуки и интеграции с incident.io. Время отправки уведомления фиксируется для каждого канала отдельно, поэтому медленную интеграцию легко выявить.

Теперь уведомления отправляются в настроенные каналы напрямую. Раньше каналы преобразовывались в упоминания вебхуков и дописывались в тело сообщения. Из-за этого уведомления могли теряться: если в теле уже было столько произвольных упоминаний, что достигался лимит на событие, настроенные каналы оповещения пропускались.

Из-за новых элементов управления страница стала перегруженной, поэтому действия над строками, включая экспорт и Terraform, теперь сгруппированы в одном меню.

**Связанные запросы на слияние:** [#3001](https://github.com/hyperdxio/hyperdx/pull/3001) — отображение всех получателей уведомлений на страницах оповещений, [#2991](https://github.com/hyperdxio/hyperdx/pull/2991) — отображение всех каналов уведомлений в строке сводки, [#2984](https://github.com/hyperdxio/hyperdx/pull/2984) — отправка уведомлений в настроенные каналы напрямую, а не через строки упоминаний, [#2961](https://github.com/hyperdxio/hyperdx/pull/2961) — неудачные упоминания больше не занимают слоты уведомлений, [#3003](https://github.com/hyperdxio/hyperdx/pull/3003) — учёт времени отправки уведомления об оповещении для каждого получателя, [#3002](https://github.com/hyperdxio/hyperdx/pull/3002) — одинаковые концевые элементы управления во всех строках страницы оповещений, [#3016](https://github.com/hyperdxio/hyperdx/pull/3016) — перенос элементов заголовка страницы оповещения в общее меню строки

## Отрисовка десятков тысяч оповещений {#rendering-1000s-alerts}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/P9BPD9yoElo" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Оценку оповещений протестировали на 16,000 параллельных оповещений, и она показала себя хорошо. А вот страница оповещений при таком их количестве переставала работать.

Теперь список виртуализирован и может отрисовать 16,000 оповещений. Загрузка по-прежнему медленная, поскольку все оповещения запрашиваются и фильтруются на стороне клиента. Чтобы решить эту проблему, сейчас реализуется постраничная навигация.

Кроме того, в изменение входит скрипт для массового создания и удаления оповещений в MongoDB, который упрощает локальное тестирование страницы в таком масштабе.

## Скрытие ключей API за кнопкой показа {#hiding-api-keys-behind-a-reveal}

*Демо от [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/MNXABmTVEkE" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше учётные данные отображались в приложении открытым текстом. На странице Team Settings выводился полный ключ API для приёма данных, а в команде из фрагментов для установки MCP присутствовал персональный ключ доступа. И то и другое легко было случайно раскрыть при демонстрации экрана или на скриншоте.

Теперь ключи по умолчанию замаскированы, а при необходимости их можно показать с помощью отдельного элемента управления. Эту логику реализует общий компонент — для ключа приёма данных, персонального ключа доступа и фрагментов установки MCP, в том числе добавленных сообществом.

При копировании по-прежнему копируется настоящее значение, так что показывать ключ, чтобы его скопировать, не нужно. Аналогичное изменение появится и в процессе первоначальной настройки ClickStack Cloud.

## Примечания к выпуску в продукте {#release-notes-in-the-product}

*Демо от [@jordan-simonovski](https://github.com/jordan-simonovski)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/4vrzXy8JwZY" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Панель «What&#39;s new» в меню Help строилась на основе наборов изменений (changesets) отдельных запросов на слияние и отбирала записи с префиксом `feat:`. Из-за этого в версии v2.36.0 переменные дашборда упоминались трижды, а формулы и доработки оповещений — главные изменения релиза — в список не попали.

Теперь панель читает корневой файл `CHANGELOG.md`, который пишется и проходит ревью в рамках релизного запроса на слияние. Генератор релизов также задаёт заголовок для каждого релиза на панели. Под ним перечислены обратно несовместимые изменения, новые возможности, исправления ошибок и улучшения со ссылками на журнал изменений.

Если есть непрочитанные примечания к выпуску, кнопка Help теперь переливается блёстками — с помощью анимированного SVG, без JavaScript.

Пришлось исправить и отслеживание непрочитанного. Раньше оно опиралось на версию сборки приложения, поэтому в развертываниях, где версия содержала короткий SHA коммита git или номер сборки CI, блёстки появлялись после каждого развертывания, даже если нового релиза не было. Теперь используется версия последнего релиза из журнала изменений.

Формат примечаний к выпуску тоже меняется, так что на панели будет появляться больше такого контента.

**Связанные запросы на слияние:** [#2993](https://github.com/hyperdxio/hyperdx/pull/2993) формирование «What&#39;s new» из сгенерированных примечаний к выпуску, [#3042](https://github.com/hyperdxio/hyperdx/pull/3042) привязка блёсток What&#39;s new к релизу, а не к сборке, [#3007](https://github.com/hyperdxio/hyperdx/pull/3007) отдельное предупреждение при сбое запроса маркера релиза
