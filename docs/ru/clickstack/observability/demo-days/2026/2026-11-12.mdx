## Размер блока текстового индекса и ускоренный поиск в фильтрах {#text-index-block-size-and-faster-filter-lookups}

*Демо от [@knudtty](https://github.com/knudtty)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Панель фильтров ClickStack могла медленно загружаться и оставлять поля пустыми, даже если подходящие значения существовали. В продемонстрированном случае для таблицы с 537M строк журнала подсказки появлялись примерно через 30 секунд, причём лишь для 22 из 100 ключей. После этих изменений та же панель выдаёт подсказки для всех 100 ключей и загружается быстрее.

Панель использует текстовые индексы, чтобы обнаруживать ключи Map и их значения. Например, она может найти ключ `service` и предложить значения `checkout` и `billing`. Так не нужно сканировать исходные журналы, однако открытие индексов всё равно обходилось дорого.

Каждый текстовый индекс содержит отсортированный словарь токенов, разделённый на блоки. В заголовке записано, где начинается каждый блок, поэтому ClickHouse может сразу перейти к нужному блоку. Чем крупнее блоки, тем меньше записей в заголовке и тем меньше данных нужно загрузить перед началом поиска. Аарон наглядно объясняет это в видео.

Теперь схема задаёт `text_index_dictionary_block_size = 8192` (вместо прежнего значения по умолчанию 512) для `otel_logs`, `otel_traces` и `hyperdx_sessions`. В локальном бенчмарке это уменьшило заголовок с 17.7 KB до 1.3 KB на часть. Миграция применяется в ClickHouse 26.6 и новее, в том числе к существующим установкам, и сохраняет явно заданные настройки таблиц. Новые части используют более крупные блоки; существующие части сохраняют прежнюю структуру до слияния.

Благодаря уменьшенному заголовку искать по каждому ключу отдельно стало целесообразно. Ранее все ключи обрабатывались одним запросом с лимитом по умолчанию в 3 миллиона записей индекса. Ключ с миллионами различных значений, например идентификатор запроса, мог исчерпать этот лимит, и последующие ключи оставались без подсказок. Такой неполный результат затем мог попасть в кэш.

Для индексов, настроенных с более крупными блоками, у каждого ключа теперь собственный лимит в 20 000 записей индекса. Поиск выполняется параллельными пакетами по 10 ключей, поэтому ключ с большим количеством значений не может израсходовать лимит другого ключа. `topKWeighted` выбирает приблизительно наиболее частые значения среди прочитанных записей — раньше выбирались первые значения в алфавитном порядке. Индексы, настроенные с меньшими блоками, сохраняют прежний подход к поиску внутри каждого пакета.

Начальный поиск ключей и значений также читает меньше частей. По умолчанию проверяется до 20 частей из середины рейтинга по размеру. Параметр **Map key index parts** задаёт их количество, а **Map key index part size** позволяет выбрать части среднего размера, наименьшие или наибольшие. Это сокращает чтения индексов, особенно когда для них требуется загрузка данных из объектного хранилища. Обратная сторона — в подсказках могут отсутствовать ключи или значения из невыбранных частей, а оценки частоты отражают только проверенные записи. Действие Load more для отдельного ключа читает все релевантные части.

Отдельное исправление позволяет одинаковым параллельным вызовам использовать один выполняющийся запрос `getMapKeys`. Ранее при открытии страницы поиска одни и те же чтения могли выполняться дважды. На примере таблицы эти дублирующиеся запросы потребляли в сумме около 47 GiB памяти. Теперь каждое чтение выполняется один раз.

Более крупные блоки также улучшили производительность поиска по текстовому индексу в представленных бенчмарках: некоторые запросы ускорились примерно на 60% при том же количестве частей. Ещё одно изменение, пока не слитое, использует `topKWeighted` для обнаружения распространённых ключей Map без группировки всех различных ключей. На таблице примерно с 5.5M различных ключей на часть, согласно бенчмарку, время запроса сократилось с 9.1 до 2.6 секунды, а потребление памяти — с 14 GiB до 78 MiB.

**Связанные PR:** [#3611](https://github.com/ClickHouse/clickstack/pull/3611) Общее чтение ключей Map для параллельных вызовов, [#3635](https://github.com/ClickHouse/clickstack/pull/3635) Чтение настраиваемого набора частей при поиске ключей и значений в текстовом индексе, [#3617](https://github.com/ClickHouse/clickstack/pull/3617) Отображение наиболее частых значений текстового индекса пакетами по 10 ключей, [#3614](https://github.com/ClickHouse/clickstack/pull/3614) Поиск наиболее частых ключей Map с помощью topKWeighted (открыт)

## Соединения с MCP-сервером без пользовательских заголовков {#mcp-server-connections-without-custom-headers}

*Демо от [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok?start=396" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше для подключения агента к MCP-серверу ClickStack в ClickHouse Cloud приходилось передавать идентификатор сервиса в пользовательском HTTP-заголовке. В большинстве MCP-клиентов задать пользовательские заголовки непросто, а некоторые их вообще не поддерживают, поэтому конфигурацию для каждого агента приходилось править вручную.

Теперь идентификатор сервиса по умолчанию передаётся как параметр запроса в URL MCP — этот подход команда ClickHouse AI уже применяла, чтобы обойти то же ограничение. В клиентах, которые это поддерживают, настройка агента теперь сводится к одной команде (например, для Codex раньше нужно было вставлять блок в его конфигурацию TOML), а клиентам, которые не могут выполнить команду, достаточно передать URL как есть.

Сразу после слияния этого изменения Claude Code убрал поддержку пользовательских заголовков из своей конфигурации MCP, и настройка на основе заголовков перестала работать в продакшне. Соединений через параметр запроса это не коснулось.

Всё это относится к облачной конечной точке MCP. MCP-сервер с открытым исходным кодом использует аутентификацию по Bearer-токену, и идентификатор сервиса ему передавать не нужно. В этом случае команда `npx @hyperdx/cli mcp install` запрашивает личный ключ API или ключ API организации (ввод скрыт), проверяет его и сама прописывает сервер в конфигурации Claude Code, Codex, Cursor и VS Code.

## Настройка агента Datadog в разделе «Начало работы» {#datadog-agent-setup-in-getting-started}

*Демо от [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok?start=469" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

В разделе «Начало работы» агент Datadog теперь отображается наряду с другими SDK и коллекторами, так что существующие агенты Datadog можно направить в ClickStack, не покидая страницу первоначальной настройки.

Показанная там конечная точка ингестии Datadog предоставляется плоскостью данных ClickHouse Cloud, которая теперь передаёт этот URL во фронтенд вместе с остальными конечными точками. Инструкции по настройке, как и для всех остальных SDK, берутся из публичной документации, поэтому страница всегда соответствует [руководству по миграции с Datadog](https://clickhouse.com/docs/clickstack/migration/datadog).

Сам приёмник преобразует полезные нагрузки журналов, трасс и метрик Datadog в модель данных OpenTelemetry внутри коллектора ClickStack, поэтому существующие агенты и SDK продолжают работать без изменений. В ClickStack с открытым исходным кодом он прослушивает порт 8126 и включается параметром `ENABLE_DATADOG_RECEIVER=true`.

## Ключи API организации {#organization-api-keys}

*Демо от [@jordan-simonovski](https://github.com/jordan-simonovski)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok?start=497" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше единственными учётными данными типа bearer для внешнего API и MCP-сервера был персональный ключ доступа. Такой ключ перестаёт работать, когда его владельца удаляют из команды, поэтому Terraform, CI и другая автоматизация, настроенная с этим ключом, ломались, и командам приходилось обходить проблему с помощью пользователей-ботов.

Теперь ключи API, принадлежащие команде, можно создавать в разделе **Team Settings** &gt; **API &amp; Agents**. Для каждого ключа задаются описание и срок действия: 30 дней, один год или бессрочно. Полный ключ показывается только один раз при создании, а хранится в виде хеша SHA-256. В списке видно, кто создал каждый ключ, когда он последний раз использовался и когда истекает срок его действия, — так легко найти редко используемые ключи или ключи с истекающим сроком и отозвать их прямо там же. Отзыв ключа или истечение срока его действия вступает в силу со следующего запроса.

Каждый ключ — это отдельная служебная учётная запись с теми же разрешениями, что и у любого другого пользователя. Всё, что создано с его помощью (оповещения, панели мониторинга, сохранённые поиски), записывается на служебную учётную запись, а не на человека, создавшего ключ. Ключи, созданные пользователем, который впоследствии был удалён, отображаются как «Deleted user» и продолжают работать. Служебные учётные записи не могут входить в систему и не отображаются в разделе **Members**. С помощью ключей нельзя приглашать пользователей, а также создавать или отзывать другие ключи.

Ключи организации работают везде, где работает персональный ключ: во внешнем API v2, в MCP-сервере и в `npx @hyperdx/cli mcp install`. При использовании Terraform-провайдера ключ передаётся вместе с ID вашей команды. Функция рассчитана на самоуправляемые развертывания, и RBAC за ней не стоит: в ClickStack с открытым исходным кодом нет ролей, поэтому любой участник команды может управлять ключами организации, а ключу доступно всё, что доступно пользователю.
