## Режим серий для тепловых карт, тепловые карты PromQL и явная гранулярность {#heatmap-series-mode-promql-heatmaps-and-explicit-granularity}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA" title="YouTube video player" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Ранее тепловые карты отображали только числовые распределения: по оси Y откладывалось значение, разбитое на интервалы (например, длительность span), а цвет показывал количество событий в каждом интервале. Теперь появился режим серий, в котором по оси Y откладывается значение group-by, а цвет отражает выбранную вами агрегатную функцию для каждого временного интервала. Он работает так же, как линейный график с несколькими сериями, только значение передаётся цветом, а не высотой. Построитель и генерируемый запрос устроены так же, как у временных диаграмм.

В демонстрации данные группируются по имени сервиса за последние сутки. На тепловой карте с количеством ошибок легко заметить смоделированный инцидент в демо-среде — две ячейки с явно повышенными значениями. Расположенный рядом такой же чарт, но с агрегатной функцией, не связанной с ошибками, выглядит ровным. Если group-by возвращает более 50 серий, отображается предупреждение и строятся первые 50 — по той же логике ограничения на стороне клиента (client-side), что и во временных диаграммах. Режим серий также работает через внешний API панелей мониторинга и MCP.

Для источников PromQL доступны три режима тепловой карты. Режим серий работает так, как описано выше, и использует range-запрос с поддержкой макросов, переменных и шаблонов легенды. В демонстрации он используется для отображения задержки p95 по каждому эндпоинту.

Режим гистограммы использует метрики, которые Prometheus уже разбил на интервалы. Границы интервалов берутся из меток `le`, а кумулятивные значения преобразуются в значения для каждого отдельного интервала. Используйте `sum by (le) (...)`, чтобы объединить серии с одинаковыми границами интервалов.

Режим распределения предназначен для данных, не являющихся гистограммами, когда всё же требуется числовое распределение. Для каждой временной метки возвращённые выборки разбиваются на интервалы на стороне клиента; линейные или логарифмические интервалы выбираются в настройках чарта. Цвет показывает количество выборок в каждом интервале. В демонстрации показана степень использования 14 ядер CPU во времени, построенная с помощью `sum by (system_cpu_logical_number) (system_cpu_utilization{system_cpu_state!="idle"})`. Запросы на слияние для гистограмм и распределений пока открыты.

Мы также исправили выбор гранулярности. Ранее тепловые карты игнорировали явно заданное значение и всегда использовали auto, рассчитанный на 245 временных интервалов. Теперь выбранное значение учитывается, поэтому гранулярность можно согласовать с другими чартами на панели мониторинга. Режим auto также учитывает минимальную гранулярность источника метрик.

Поля ввода выражений для количества и значения перенесены из настроек отображения в редактор чарта — как на панелях мониторинга, так и в обозревателе диаграмм. Кроме того, тепловые карты теперь поддерживают форматирование чисел.

Наконец, подсветка при наведении теперь центрируется на ячейке, а не смещается вниз и вправо. Выбирается ближайшая ячейка, границы которой попадают в допуск курсора, — центр ячейки больше не обязан находиться в его пределах. Состояние наведения также обновляется при обновлении данных, если курсор остаётся над чартом.

## Переменные дашборда с одиночным выбором {#single-select-dashboard-variables}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=208" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше все переменные дашборда поддерживали только множественный выбор. Теперь для переменной можно настроить одиночный выбор: при выборе другого значения оно заменяет текущее. Если URL содержит несколько значений для переменной с одиночным выбором, используется первое из них.

Это особенно полезно для PromQL. Переменные с множественным выбором разворачиваются в регулярное выражение с альтернацией, которое работает с `=~`, но не с `=`, поэтому удобного способа использовать переменную с оператором проверки на равенство не было.

Мы также добавили формат переменной `promql`, который заменяет `regex` в качестве формата по умолчанию для ссылок на переменные в выражениях PromQL, если формат не указан. Он работает так же, за исключением того, что значения переменных с одиночным выбором не экранируются как регулярные выражения. Таким образом, с переменной с одиночным выбором можно использовать `field="$var"`. Значения переменных с множественным выбором по-прежнему экранируются как регулярные выражения, и для них следует использовать `field=~"$var"`.

**Связанные запросы на слияние:** [#3295](https://github.com/hyperdxio/hyperdx/pull/3295) Поддержка фильтров дашборда с одиночным выбором, [#3297](https://github.com/hyperdxio/hyperdx/pull/3297) Добавление формата переменных promql для гибкого экранирования

## Линейные графики с накоплением {#stacked-line-charts}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=271" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Наряду с `stacked_bar` мы добавили тип чарта временного ряда `stacked_line`. Линейный график можно переключить в режим линейного графика с накоплением в обозревателе диаграмм или на панели мониторинга. В этом режиме серии располагаются одна над другой, а область под каждой из них заливается цветом, поэтому видно как общее значение, так и вклад каждой серии.

В CLI такие графики отображаются как столбчатые диаграммы с накоплением. Оба варианта показывают по сути одно и то же, а в терминале накопление и заливку проще воспринимать в виде столбцов.

## Определение источника, отправившего запросы ClickHouse {#attributing-clickhouse-queries-to-the-surface-that-issued-them}

*Демо от [@tommyzli](https://github.com/tommyzli)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=526" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Каждый SQL-запрос, который ClickStack отправляет в ClickHouse, теперь содержит JSON-поле `log_comment` и `query_id` в формате `hdx-<surface>-<uuid>`. Благодаря этому любую строку в `system.query_log` можно сопоставить с плиткой панели мониторинга, сохранённым поиском, оповещением или инструментом MCP, который отправил запрос. В последующем изменении такие же метки добавлены и для запросов PromQL, которые раньше отправлялись без них.

В демонстрации запрос к журналу запросов со страницы Поиск показал, что все запросы помечены как отправленные из Поиска, включая запросы `EXPLAIN` и запросы столбчатой гистограммы. При открытии встроенной панели мониторинга ClickHouse запросы отображались с меткой `clickhouse`, указывающей на преднастроенную панель мониторинга. Для пользовательской панели мониторинга каждый запрос содержал ID панели мониторинга и ID плитки чарта, который его отправил.

Если ClickStack использует ваш кластер ClickHouse совместно с другими рабочими нагрузками, так проще выделить его запросы, понять, из какой части приложения они пришли, и отслеживать стоимость запросов по источникам. Мы, в свою очередь, можем сопоставлять журнал запросов с конфигурациями панелей мониторинга при анализе использования. Кроме того, это шаг к автоматической оптимизации запросов: теперь медленный запрос можно связать с плиткой, которая его сформировала.

**Связанные запросы на слияние:** [#3155](https://github.com/hyperdxio/hyperdx/pull/3155) Определение источника, отправившего запросы ClickHouse, [#3300](https://github.com/hyperdxio/hyperdx/pull/3300) Определение источника запросов PromQL

## Встроенные поля ввода для именования объектов {#inline-name-inputs-for-naming-objects}

*Демо от [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=296" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше именование работало по-разному в зависимости от того, в какой части приложения вы находились. У панелей мониторинга и сохранённых поисков заголовок редактировался по щелчку: при наведении появлялся значок карандаша, также можно было начать редактирование двойным щелчком, после чего требовалось нажать кнопку **Save Name**. В других местах использовалось текстовое поле с рамкой. Задокументированного шаблона не было, поэтому на новых экранах, как правило, появлялся собственный вариант. Теперь стандартным способом именования объектов служит общий компонент `InlineNameInput`.

Он выглядит как обычный заголовок, пока на него не наведён курсор, — тогда появляется светлая рамка. По щелчку имя можно отредактировать прямо на месте. Клавиша `Enter` или щелчок за пределами поля сохраняет изменения, а `Escape` или пустое имя отменяет их. Ни карандаша, ни отдельной кнопки сохранения больше нет. После сохранения отображается сохранённое значение. Если переименование завершается ошибкой или его перезаписывает параллельное сохранение панели мониторинга, отображаемое имя тоже возвращается к прежнему, чтобы на экране не оставалось несохранённое имя.

Длинные имена усекаются, а сам компонент доступен в размерах `xs`, `sm` и `md`. Для заголовков страниц используется размер `md` — 18px вместо прежних примерно 22px. Как и раньше, они отображаются внутри элемента заголовка, чтобы их могли найти программы чтения с экрана.

Компонент уже используется на страницах панелей мониторинга и сохранённого поиска, а старый компонент `EditablePageName` удалён. Также есть вариант `InlineNameInputControlled`, который сохраняет данные вместе с окружающей формой и предназначен для черновиков в полностраничном редакторе плиток, хотя в приложении он пока не используется. В редакторе чартов пока остаётся прежнее поле **Chart Name**: прежде чем внедрять встроенную версию, нужно доработать структуру интерфейса.

Шаблон описан в `agent_docs/naming_objects.md`, в навыке агента `naming-objects`, а также в разделах Guidelines и Components в Storybook. Цель — чтобы агент для программирования, работающий с репозиторием, мог легко найти и повторно использовать этот компонент, когда нужно добавить ещё одно место для задания имени.

**Связанные запросы на слияние:** [#3278](https://github.com/hyperdxio/hyperdx/pull/3278) Add InlineNameInput as the one way to name objects

## Вложение сохранённых поисков в раздел Поиск {#nesting-saved-searches-under-search}

*Демо от [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=389" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**Это исследовательская работа: выпуск этой возможности не гарантируется.**

Сейчас у сохранённых поисков есть собственная страница со списком и отдельный пункт на боковой панели, не связанные с разделом Поиск. Вы сохраняете поиск в одном месте, а находить его и управлять им приходится в другом. Чтобы дублировать поиск из списка, пользователю приходилось сначала открыть его и уже оттуда создать дубликат. Отдельный список оправдан для панелей мониторинга, но для сохранённых поисков он выглядит менее естественно.

В этом черновике сохранённые поиски перенесены в раздел Поиск. Пункт верхнего уровня **Сохранённые поиски** на боковой панели убран, а избранные поиски отображаются в разделе Поиск — так же, как это уже сделано для панелей мониторинга. Кнопка **Сохранённые поиски** на панели инструментов открывает выдвижную панель справа с поиском, вкладками **All** и **Favorites**, фильтрацией по меткам, а также действиями переименования, дублирования и удаления для каждой строки. Панель открывается справа, чтобы не перекрывать навигацию приложения. Существующие ссылки `/search/list` также открывают выдвижную панель.

При выборе сохранённого поиска на кнопке отображается его имя. Значок рядом с ней показывает статус **Unsaved**, **Saved** или **Edited**; **Edited** появляется после выполнения изменённого запроса. Сравнение выполняется по конфигурации поиска в URL, при этом пустые и отсутствующие значения считаются эквивалентными, поэтому простая загрузка сохранённого поиска не помечает его как изменённый.

Отдельный заголовок сохранённого поиска удалён вместе с навигационной цепочкой, названием и строкой с датами создания/обновления. Избранное, метки, Terraform и меню действий перенесены на панель инструментов, а сведения о создании/обновлении теперь отображаются во всплывающей подсказке на кнопке. Благодаря этому структура интерфейса одинакова для сохранённых и несохранённых поисков. Вместе с заголовком пропадает возможность переименовать поиск двойным щелчком по названию, но это по-прежнему можно сделать через меню строки на выдвижной панели или в модальном окне **Update**. Нужно ли вообще модальное окно для обновления, пока не решено. В идеале обновление должно выполняться одним действием, без попутного предложения переименовать поиск.

Это пока черновик, и мы будем рады отзывам о его работе. Четыре сквозных теста в наборе для выдвижной панели пока не проходят — их нужно исправить, прежде чем работа выйдет из статуса черновика.

**Связанные запросы на слияние:** [#3213](https://github.com/hyperdxio/hyperdx/pull/3213) Вложение сохранённых поисков в раздел Поиск в выдвижной панели (открыт). (черновик). Это исследование, а не выпущенная возможность.
