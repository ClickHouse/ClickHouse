При всплеске задержки или ошибок первым делом обычно выясняют, не выкатывалось ли что-нибудь. Временные чарты панелей мониторинга позволяют ответить на этот вопрос прямо на месте: включите маркеры релизов, и каждая плитка отобразит пунктирную вертикальную линию в момент, когда версия сервиса впервые появилась в её телеметрии.

Версии берутся из уже отправляемой вами телеметрии и считываются с помощью выражения, заданного в источнике плитки. Не нужно ни настраивать интеграцию с CI, ни отправлять что-либо при развертывании.

## Включение маркеров {#turn-on}

По умолчанию маркеры релизов отключены. Чтобы включить их, откройте дополнительное меню панели мониторинга и выберите **Show release markers**.

Переключатель добавляет `releaseMarkers=true` в URL панели мониторинга, поэтому ссылка, которой вы поделитесь, откроется с уже включёнными маркерами. Это состояние отображения, а не конфигурация панели мониторинга: оно не сохраняется вместе с панелью, а при отключении параметр удаляется из URL.

Маркеры отображаются на плитках time-series, источником данных для которых служит источник журналов или трасс. [Аннотации оповещений](/ru/clickstack/observability/features/alerts) включаются в том же меню и могут отображаться одновременно: оба набора маркеров выводятся вместе, и каждый сохраняет собственные метки.

## Настройка источника версии {#version-expression}

По умолчанию ClickHouse Observability считывает `ResourceAttributes['service.version']` — атрибут ресурса OpenTelemetry. Если ваши сервисы соответствуют [семантическим соглашениям для ресурса service](https://opentelemetry.io/docs/specs/semconv/registry/attributes/service/), маркеры работают без дополнительной настройки.

Чтобы брать версию из другого места, задайте **Service Version Expression** в источнике журналов или трасс. Источник можно изменить в разделе **Team Settings → Sources**. В источнике журналов это поле скрыто в разделе **Configure Optional Fields**, а в источнике трасс оно отображается прямо в форме, под **Service Name Expression**.

<div className="ch-image-lg">
  <Frame>
    ![Поле Service Version Expression в необязательных полях источника журналов с плейсхолдером по умолчанию ResourceAttributes\['service.version'\]](/images/clickstack/dashboards/service-version-expression.webp)
  </Frame>
</div>

Значением служит SQL-выражение, а не имя атрибута, поэтому оно подходит для двух распространённых случаев:

* **Идентификатор релиза хранится в другом атрибуте.** При работе по GitOps релиз обычно идентифицируется тегом образа контейнера, который передаётся в атрибуте `container.image.tag`. Указать в источнике `ResourceAttributes['container.image.tag']` гораздо дешевле, чем менять инструментирование во всём парке коллекторов.
* **Сервисы в одной таблице используют разные атрибуты.** С помощью `coalesce` можно переключаться на резервный атрибут:

```sql
coalesce(
  nullIf(ResourceAttributes['service.version'], ''),
  nullIf(ResourceAttributes['container.image.tag'], '')
)
```

Это поле также доступно как `serviceVersionExpression` в источниках журналов и трасс в [API источников](/ru/clickstack/observability/api-reference), поэтому его можно задавать при программном создании источников. Для самоуправляемых развертываний см. полный список настроек источников для [журналов](/ru/clickstack/self-configured/managing/config#logs) и [трассировки](/ru/clickstack/self-configured/managing/config#traces).

## Что означает маркер {#what-a-marker-means}

Маркер фиксирует, что значение версии впервые появилось в данных плитки в пределах видимого окна. Это близко к развертыванию, но намеренно означает не то же самое, поэтому они и называются маркерами релизов, а не маркерами развертываний:

* Развертывание, при котором строка версии не меняется, не создаёт маркер вовсе.
* Для сервиса, который бездействовал дольше периода ретроспективного просмотра, маркер появится, когда сервис снова масштабируется.

Версия, которая уже работала на момент начала окна, распознаётся и отбрасывается, а не отображается как релиз, которого на самом деле не было. Для этого запрос захватывает интервал до начала окна — 30 минут или 10% длины окна, если это больше, — чтобы определить текущую версию.

## Какие релизы отображает плитка {#scoping}

Запрос релизов выполняется к собственному источнику плитки с её собственными предикатами: предложением `WHERE`, фильтром каждой серии и всеми [фильтрами панели мониторинга](/ru/clickstack/observability/features/dashboards/overview#custom-filters). Что именно отображает плитка, зависит от того, какие данные она визуализирует:

| Плитка                                      | Маркеры                                                                      |
| :------------------------------------------ | :--------------------------------------------------------------------------- |
| С фильтром по одному сервису                | Релизы этого сервиса                                                         |
| Сгруппированная по сервису                  | Релизы каждого отображаемого сервиса, окрашенные в цвет его линии            |
| Агрегированная линия по нескольким сервисам | Не отображаются, если только все релизы в окне не относятся к одному сервису |

В третьем случае сервису маркера не соответствует ни одна линия на чарте, поэтому маркеры не отображаются. Если же все релизы в окне относятся к одному сервису, маркеры отображаются в цвете по умолчанию.

## Чтение маркеров на перегруженном чарте {#reading-markers}

Наведите курсор на подпись маркера, чтобы увидеть список всех релизов в этой точке: для каждого указаны сервис, который его выпустил, версия и время.

  <Frame>
    ![Всплывающая подсказка у маркера релиза с названием сервиса frontend, версией 2.0.2 и временем первого появления этой версии на чарте с двумя сервисами](/images/clickstack/dashboards/release-marker-tooltip.webp)
  </Frame>
</div>

Цвет связывает маркер с его серией, однако легенда чарта показывает не более четырёх записей, а остальные сворачивает под «+N more», и тогда на экране уже не по чему сопоставить цвет. Всплывающая подсказка прямо называет сервис, поэтому она работает независимо от того, сколько серий отображает плитка.

Маркеры, расположенные слишком близко друг к другу, чтобы подписать каждый отдельно, объединяются в одну общую метку с текстом `N releases`; при наведении на неё отображаются все входящие в неё релизы. Группа, охватывающая несколько сервисов, отрисовывается нейтральным цветом, а не цветом одного из них: так счётчик остаётся точным и не намекает на принадлежность какому-либо сервису.

Перетаскивание по графику по горизонтали по-прежнему масштабирует его, даже когда маркеры отображаются.

## Ограничения {#limitations}

* **Только плитки time-series.** На таблицах, числах и тепловых картах маркеры не отображаются.
* **Только источники журналов и трасс.** Источник метрик определяет таблицу отдельно для каждого типа метрики, поэтому нет единой таблицы для повторной агрегации, и фильтры плитки нельзя осмысленно к ней применить. Чтобы добавить аннотации к данным метрик, разместите рядом плитку журналов или трасс на той же панели мониторинга.
* **Пустые значения версии пропускаются.** Сервис, который не передаёт версию, не создаёт маркеров. Если плитка не находит ни одного изменения версии, интерфейс выводит сообщение `No releases found` — так сразу понятно, что возможность работает.
* **Для каждого окна считывается не более 500 различных версий.**
