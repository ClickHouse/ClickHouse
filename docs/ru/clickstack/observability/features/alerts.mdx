ClickHouse Observability поддерживает оповещения «из коробки», что позволяет командам в режиме реального времени обнаруживать проблемы в журналах, метриках и трассировках и реагировать на них.

Оповещения создаются прямо в пользовательском интерфейсе и интегрируются с популярными системами уведомлений, такими как Slack и PagerDuty.

Оповещения единообразно работают со всеми вашими данными обсервабилити и помогают отслеживать состояние системы, выявлять регрессии производительности и контролировать ключевые бизнес-события.

## Типы оповещений {#types-of-alerts}

Оповещения можно создавать на основе **сохранённого поиска**, непосредственно в **Обозревателе диаграмм** или на основе **чарта на сохранённой панели мониторинга**. Оповещения по поиску подсчитывают число подходящих событий, а оповещения по чартам проверяют значения, вычисляемые чартом.

### Оповещения по поиску {#search-alerts}

Оповещения по поиску позволяют отправлять уведомления на основе результатов сохранённого поиска. Они помогают выявлять ситуации, когда определённые события или шаблоны встречаются чаще (или реже), чем ожидается.

Оповещение срабатывает, когда количество совпадающих результатов в заданном временном окне превышает указанный порог или опускается ниже него.

Чтобы создать оповещение по поиску:

Оповещение можно создать только для сохранённого поиска. Можно создать оповещение для уже существующего сохранённого поиска либо сохранить поиск в процессе создания оповещения. В примере ниже предполагается, что поиск ещё не сохранён.

    Сначала введите [поисковый запрос](/ru/clickstack/observability/features/search) и нажмите кнопку `Alerts` в правом верхнем углу страницы `Search`.

    <div className="ch-image-lg">

      </Frame>

  <Step title="Создайте оповещение" id="create-the-alert">

    * Задать имя сохранённого поиска, связанного с оповещением.
    * Выбрать оператор сравнения, количество совпадающих событий и временное окно. Например, оповещение может срабатывать при появлении не менее 10 совпадающих событий в течение 5 минут.

    Перед сохранением интерфейс наглядно отображает условие порога, чтобы вы могли убедиться, что оповещение будет работать так, как ожидается.

<Steps>
  <Step title="Постройте чарт" id="build-explorer-alert-chart">
    Выберите **Обозреватель диаграмм** на боковой панели и укажите тип чарта **Time Series**. Выберите источник данных и настройте агрегацию, фильтры и группировку, которые нужно отслеживать. Например, подсчитайте записи журнала с ошибками и сгруппируйте их по `ServiceName`, чтобы оценивать каждый сервис отдельно.

### Оповещения по чартам на панели мониторинга {#dashboard-alerts}

Оповещения на панелях мониторинга позволяют настраивать оповещения для чартов.

Оповещение на основе чарта можно создать непосредственно из сохранённой панели мониторинга, используя полноценные SQL-агрегации и функции ClickHouse для сложных вычислений.

Когда метрика пересекает заданный порог, оповещение срабатывает автоматически. Это позволяет отслеживать KPI, задержки и другие ключевые метрики во времени.

### Интеграции по типам сервисов {#integrations}

Оповещения «из коробки» интегрируются со следующими типами сервисов:

* **Slack**: отправка уведомлений непосредственно в канал через вебхук или API.
* **PagerDuty**: передача инцидентов дежурным командам через PagerDuty API.
* **incident.io**: отправка оповещений в incident.io.
* **Generic**: подключение оповещений к любой пользовательской системе или рабочему процессу через универсальный вебхук.

<Info>
  **Интеграции, доступные только в ClickHouse Cloud**

  Интеграции со Slack API и PagerDuty поддерживаются только в ClickHouse Cloud.
</Info>

В зависимости от типа сервиса потребуется указать разные данные, а именно:

**Slack (Webhook URL)**

* Webhook URL. Например: `https://hooks.slack.com/services/<unique_path>`. Подробнее см. в [документации Slack](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/).

**Slack (API)**

* Токен бота Slack. Подробнее см. в [документации Slack](https://docs.slack.dev/authentication/tokens/#bot/).

**PagerDuty API**

* Ключ интеграции PagerDuty. Подробнее см. в [документации PagerDuty](https://support.pagerduty.com/main/docs/api-access-keys).

**Generic**

* Webhook URL
* Заголовки вебхука (необязательно)
* Тело вебхука (необязательно). Тело представляет собой шаблон Handlebars. Помимо `{{title}}`, `{{body}}` и `{{link}}`, в нём можно использовать переменные, описывающие оповещение и его срабатывание, например `{{alertId}}`, `{{status}}`, `{{value}}`, `{{threshold}}` и `{{groupKey}}`. Полный список см. в разделе [Переменные шаблона вебхука оповещений](https://github.com/ClickHouse/ClickStack/blob/main/docs/alert-webhook-template-variables.md).

Чтобы управлять оповещениями, выберите **Alerts** на левой боковой панели. Оповещения можно искать по имени и фильтровать по состоянию, источнику или типу.

Здесь также отображается история вычислений оповещений. Оповещения оцениваются через регулярный временной интервал (он определяется периодом/длительностью, заданными при создании оповещения). При каждой оценке сервис выполняет запрос к вашим данным и проверяет, выполняется ли условие оповещения:

* **Красный столбец**: при этой оценке условие порога выполнилось, и оповещение сработало (уведомление отправлено)

Выберите оповещение, чтобы открыть страницу с подробной информацией о нём: условием, пунктом назначения уведомлений и историей вычислений.

## Оповещения для чартов на основе SQL {#sql-based-alerts}

Оповещения для чартов на основе SQL позволяют задавать условия оповещений произвольными запросами на ClickHouse SQL. Это даёт полный контроль над фильтрацией, агрегацией и вычислениями: всё, что можно выразить на SQL, можно превратить в оповещение.

### Поддерживаемые типы чартов {#supported-chart-types}

Оповещения на основе SQL поддерживаются для трёх типов отображения чартов:

| Тип чарта                              | Поведение                                                                                                                                                                   |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **линия**                              | Оповещение по time-series. Запрос должен возвращать строки, сгруппированные по временным интервалам (бакетам). Каждый бакет сравнивается с порогом независимо от остальных. |
| **Столбчатая диаграмма с накоплением** | Оповещение по time-series. Работает так же, как тип «линия».                                                                                                                |
| **Число**                              | Оповещение по одному значению. Запрос возвращает единственный числовой результат, который сравнивается с порогом один раз при каждой оценке.                                |

Другие типы чартов на основе SQL (Table, Pie, Heatmap и т. д.) не поддерживают оповещения.

### Создание SQL-оповещения {#create-sql-based-alert}

Чтобы создать оповещение для чарта на основе SQL:

<Steps>
  <Step title="Создайте или откройте чарт на основе SQL на панели мониторинга" id="open-sql-chart">
    На сохранённой панели мониторинга либо [создайте новый чарт в режиме **SQL**](/ru/clickstack/observability/features/dashboards/sql-visualizations), либо откройте существующий чарт на основе SQL для редактирования.

    В качестве типа отображения выберите **линия**, **Столбчатая диаграмма с накоплением** или **Число**.

    <div className="ch-image-lg">
      <Frame>
        ![Редактор SQL-чарта с выделенными SQL и Add alert](/images/clickstack/observability-sql-chart-alert.png)
      </Frame>
    </div>
  </Step>

  <Step title="Добавьте оповещение" id="add-sql-alert">
    Нажмите **Add alert** в разделе оповещений редактора чарта и задайте следующие параметры:

    * **Тип порога**: `>=` (больше или равно), `>` (больше), `<=` (меньше или равно), `<` (меньше), `=` (равно), `!=` (не равно), `≤ x ≤` (в диапазоне) или `< or >` (вне диапазона)
    * **Пороговое значение**: числовое значение, с которым выполняется сравнение
    * **Интервал**: частота проверки оповещения (5m, 15m, 30m, 1h, 6h, 12h или 1d). Этот же параметр задаёт временное окно для каждой проверки.
    * **Вебхук**: канал уведомлений, используемый при срабатывании оповещения. См. раздел [Добавление вебхука](#add-webhook).

    <div className="ch-image-lg">
      <Frame>
        ![Редактор SQL-чарта с открытыми настройками порога оповещения и уведомлений](/images/clickstack/observability-raw-sql-alert.png)
      </Frame>
    </div>

    <Warning>
      **Временной диапазон оповещения**

      Как правило, запросы оповещений выполняются один раз за интервал. Однако если один или несколько интервалов были пропущены из-за ошибок или медленных запросов, при следующем выполнении будет использован временной диапазон, охватывающий пропущенные интервалы. В этом случае параметры интервала в запросе по-прежнему будут равны настроенному периоду оповещения, а параметры временного диапазона будут отражать более длинный диапазон.
    </Warning>
  </Step>

  <Step title="Сохраните панель мониторинга" id="save-sql-dashboard">
    Сохраните панель мониторинга, чтобы активировать оповещение. После этого оповещение будет проверяться с заданным интервалом.
  </Step>
</Steps>

### Как интерпретируются результаты запроса {#sql-result-interpretation}

Система оповещений анализирует столбцы, возвращаемые вашим SQL-запросом, чтобы определить, что именно сравнивать с порогом.

* **Столбец значения**: в качестве значения оповещения используется **последний числовой столбец** в секции `SELECT`. Если запрос возвращает несколько числовых столбцов (например, `count, avg_latency, p99_latency`), с порогом сравнивается только последний из них (`p99_latency`).
* **Столбец временной метки**: для time-series чартов (линия и Столбчатая диаграмма с накоплением) система использует столбец типа Date/DateTime из результатов как временной интервал (т. е. ось X на time-series чарте). Значение для каждого временного интервала сравнивается с порогом независимо, и если значение хотя бы в одном временном интервале нарушает настроенный порог, срабатывает оповещение.
* **Столбцы групп**: все нечисловые столбцы, не являющиеся временными метками (например, `ServiceName`, `Environment`), считаются измерениями группировки. Если группы заданы, каждая уникальная комбинация значений групп отслеживается и проверяется на срабатывание оповещения отдельно. Сервис отправляет оповещение для каждой группы, значение которой нарушает настроенный порог. Группы доступны только для time-series чартов.

### Параметры запроса и макросы {#query-params}

SQL-запросы оповещений поддерживают параметры шаблона и макросы, которые автоматически подставляются во время вычисления. Это те же параметры и макросы, что доступны при [построении чарта на основе SQL](/ru/clickstack/observability/features/dashboards/sql-visualizations).

#### Обязательные и рекомендуемые параметры {#required-alert-parameters}

Запросы для оповещений по линейным чартам и столбчатым диаграммам с накоплением **должны** содержать параметр интервала или макрос (`{intervalSeconds:Int64}`, `{intervalMilliseconds:Int64}`, `$__timeInterval(col)` или `$__timeInterval_ms(col)`). При выполнении оповещения он заменяется настроенным периодом оповещения.

В запросы для оповещений **рекомендуется** включать фильтр временного диапазона (`{startDateMilliseconds:Int64}` и `{endDateMilliseconds:Int64}`, `$__timeFilter(col)` и т. д.). Независимо от того, есть ли в запросе фильтр временного диапазона, запрос оповещения выполняется за настроенный период оповещения. Если фильтра временного диапазона нет, при каждом выполнении запрос будет считывать весь временной диапазон, доступный в исходной таблице.

<Warning>
  **Временной диапазон оповещения**

  Как правило, запросы оповещений выполняются один раз за интервал. Однако если один или несколько интервалов были пропущены из-за ошибок или медленных запросов, при следующем выполнении будет использован временной диапазон, охватывающий пропущенные интервалы. В этом случае параметры интервала запроса по-прежнему будут равны настроенному периоду оповещения, а параметры временного диапазона будут соответствовать более длинному временному диапазону.
</Warning>

### Примеры запросов для оповещений {#example-queries}

#### Доля ошибок по сервисам (time-series) {#example-error-rate}

Оповещение срабатывает, если доля ошибок любого сервиса составляет не менее 5% и за период оповещения поступило более 10 запросов. Это позволяет избежать ложных оповещений по сервисам с низким трафиком.

```sql
WITH error_rates AS (
  SELECT
    $__timeInterval(Timestamp) as ts,
    ServiceName,
    countIf (SpanKind = 'Server') as request_count,
    countIf (
      SpanKind = 'Server'
      and StatusCode = 'Error'
    ) as error_count,
    error_count / request_count * 100 AS error_percent
  FROM $__sourceTable
  WHERE $__timeFilter(Timestamp)
  GROUP BY ts, ServiceName
)
SELECT ts, ServiceName, error_percent
FROM error_rates
WHERE request_count > 10
```

**Тип отображения**: «линия» или «Столбчатая диаграмма с накоплением»
**Порог**: `>= 5` (срабатывает, когда доля ошибок достигает 5%)

В этом запросе `ServiceName` — нечисловой столбец, не являющийся временной меткой, поэтому каждый сервис отслеживается как отдельная группа оповещений. Оповещение срабатывает для каждого сервиса независимо.

#### Обнаружение аномалий с помощью запаздывающего среднего (time-series) {#example-anomaly-detection}

Оповещение срабатывает, когда число ошибок превышает скользящее среднее более чем на два стандартных отклонения. Такой подход выявляет всплески относительно недавнего базового значения, а не фиксированного порога.

```sql
WITH buckets AS (
  SELECT
    $__timeInterval(Timestamp) AS ts,
    count() AS bucket_count
  FROM $__sourceTable
  WHERE TimestampTime >= fromUnixTimestamp64Milli({startDateMilliseconds:Int64})
        - toIntervalSecond($__interval_s * 30) -- Fetch 30 intervals back
    AND TimestampTime < fromUnixTimestamp64Milli({endDateMilliseconds:Int64})
    AND SeverityText = 'error'
  GROUP BY ts
  ORDER BY ts
  WITH FILL
    FROM toDateTime(fromUnixTimestamp64Milli({startDateMilliseconds:Int64}))
    TO toDateTime(fromUnixTimestamp64Milli({endDateMilliseconds:Int64}))
    STEP toIntervalSecond($__interval_s)
),

anomaly_detection AS (
  SELECT
    ts,
    bucket_count,
    avg(bucket_count) OVER (
      ORDER BY ts ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING
    ) AS previous_30_avg,
    stddevPop(bucket_count) OVER (
      ORDER BY ts ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING
    ) AS previous_30_stddev,
    greatest(
      bucket_count - (previous_30_avg + 2 * previous_30_stddev), 0
    ) AS excess_error_count
  FROM buckets
)

SELECT ts, excess_error_count
FROM anomaly_detection
WHERE ts >= fromUnixTimestamp64Milli({startDateMilliseconds:Int64})
  AND ts < fromUnixTimestamp64Milli({endDateMilliseconds:Int64})
```

**Тип отображения**: линия
**Порог**: `> 0` (срабатывает при обнаружении ошибок, количество которых превышает скользящее базовое значение)

Обратите внимание, что запрос извлекает 30 интервалов *до* начала диапазона дат, чтобы инициализировать вычисления в скользящем окне, а затем фильтрует итоговый результат, оставляя только окно оценки.

## Типичные сценарии оповещений {#common-alert-scenarios}

Ниже приведены несколько типичных сценариев оповещений, которые можно настроить:

**Ошибки:** рекомендуем настроить оповещения для стандартных сохранённых поисков
`All Error Events` и `HTTP Status >= 400`, чтобы получать уведомления при
чрезмерном количестве ошибок.

**Медленные операции:** можно настроить поиск медленных операций (например,
`duration:>5000`), а затем отправлять оповещение, когда медленных операций
становится слишком много.

**Пользовательские события:** также можно настроить оповещения для команд, работающих с клиентами, чтобы
они получали уведомления о регистрации новых пользователей или выполнении пользователем критически важного действия.
