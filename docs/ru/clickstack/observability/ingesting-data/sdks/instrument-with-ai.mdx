Добавьте инструментирование в приложение с помощью ИИ-ассистента для программирования, следуя руководству для соответствующего языка или фреймворка. Ассистент может определить точки входа, установить подходящий SDK и настроить экспорт телеметрии.

Автоматическое инструментирование охватывает поддерживаемые библиотеки и фреймворки. В зависимости от языка и приложения вам всё же может потребоваться изменить код или добавить пользовательские спаны для отслеживания бизнес-операций. Перед развертыванием проверьте сгенерированные изменения.

## Перед началом работы {#before-you-begin}

Вам понадобятся исходный код приложения, ИИ-ассистент для программирования с доступом к репозиторию и пункт назначения в ClickHouse Observability. Выберите [руководство по SDK](/ru/clickstack/observability/ingesting-data/sdks) для языка вашего приложения: в нём указаны нужные пакеты SDK, поддерживаемые сигналы и настройки экспортера.

## Передайте ассистенту руководство по языку {#give-your-assistant-the-language-guide}

Откройте репозиторий своего приложения в ИИ-ассистенте для программирования, например в Claude Code, Cursor или Codex. Скопируйте следующий промпт, подставив вместо плейсхолдеров URL руководства по вашему языку, тип развертывания и имя сервиса. Указывайте имена переменных окружения, а не вставляйте учётные данные непосредственно в промпт.

```text wrap
Instrument this application to send telemetry to ClickHouse Observability.

Language or framework guide: <LANGUAGE_SDK_GUIDE_URL>
Destination: <fully managed or self-managed>
Service name: <SERVICE_NAME>
Endpoint environment variable: <ENDPOINT_VARIABLE_NAME>
Ingestion key environment variable: <API_KEY_VARIABLE_NAME>

Read the linked guide and use the instructions for my destination.
Inspect the application's language, framework, dependencies, and startup
commands before making changes. If you cannot read the guide, ask me for
its contents rather than guessing SDK names or configuration.

Reuse existing OpenTelemetry instrumentation where present. Otherwise,
install the SDK and supported automatic instrumentation described in the
guide. Initialize instrumentation at the point required by that SDK.
Use the guide's protocol, endpoint, and authentication format, reading
connection values from the environment. Do not hardcode or print secrets.

Preserve the application's existing behavior. Check for duplicate SDK
initialization, exporters, and logging handlers, including those installed
by automatic instrumentation. If logs are supported, check both the
application's logging level and the SDK's export level so the test log
is captured once. Use the language guide's settings for these checks.

Explain which signals are supported and any operations that need manual
instrumentation. Do not assume every SDK exports logs, metrics, traces,
or session replay.

Update the startup command and document the required environment variables.
Run the application's existing checks and a local startup check. Exercise
an instrumented operation with a unique test marker. If logs are supported,
emit one test log during that operation at an enabled severity. Allow time
for batched export or flush telemetry before shutting down.

When you have destination access, find the test events there and verify
the service name, marker, and absence of duplicates. If log-to-trace
correlation is supported, check that the test log references the operation's
trace and span. Distinguish local export, endpoint acceptance, and events
stored in ClickHouse Observability; startup or an HTTP success response
alone does not prove storage.

Summarize the changes, tests performed, and results. Clearly state which
checks you could not run and give me the remaining verification steps.
```

Имена переменных в этом промпте указывают, где хранятся параметры вашего подключения. Они не заменяют переменные, обязательные для SDK: ассистент должен сопоставить их с настройками, описанными в руководстве для вашего языка. Для браузерных приложений используйте [руководство по браузерному SDK](/ru/clickstack/observability/ingesting-data/sdks/browser), включая описанную в нём настройку конечной точки и ключа, характерную для браузера.

## Проверка и запуск приложения {#review-and-run-the-application}

Проверьте изменения в зависимостях, инициализации и запуске. Убедитесь, что ассистент выбрал правильный пункт назначения и формат аутентификации, сохранил существующее инструментирование и не допустил попадания секретов в закоммиченные файлы.

Выполните существующие тесты приложения, а затем запустите его с обновлённой командой и переменными окружения. Отправьте запрос или выполните действие, задействующее инструментированную библиотеку. Если вам нужна телеметрия для операции, которую автоматическое инструментирование не охватывает, попросите ассистента добавить пользовательский спан с помощью API вашего SDK.

## Проверка телеметрии {#verify-telemetry}

1. Откройте [Поиск](/ru/clickstack/observability/features/search) в ClickHouse Observability.
2. Выберите нужный источник журналов или трассировок и временной диапазон, охватывающий период тестирования.
3. Отфильтруйте данные по имени вашего сервиса и изучите сгенерированные события. Убедитесь, что ожидаемый запрос или операция присутствуют.
4. Если SDK экспортирует метрики, просмотрите их в [Обозревателе диаграмм](/ru/clickstack/observability/features/dashboards/overview#navigate-chart-explorer).

Успешный запуск приложения ещё не означает, что телеметрия доставляется. Если события отсутствуют, проверьте ошибки экспортера в приложении, а также настройки конечной точки, протокола и аутентификации. Для самоуправляемых развертываний также изучите журналы коллектора.

Полный пример приложения приведён в [демонстрации HackerNews Analyzer](/ru/clickstack/observability/example-datasets/instrument-application).
