Собирайте журналы systemd с помощью приёмника journald из OpenTelemetry и отправляйте их в ClickHouse Observability. Чтобы опробовать интеграцию без Linux-хоста, используйте [демо-набор данных](#demo-dataset).

## Предварительные требования {#prerequisites}

* Сервис ClickHouse Observability
* Для отправки собственных журналов — хост Linux с systemd, на котором установлен `journalctl` и есть разрешение на чтение журнала
* `curl`, а для демонстрации — Docker

### Сведения о подключении {#connection-details}

<Tabs>
  <Tab title="Полностью управляемый">
    <BetaBadge label="Сервис в стадии бета-тестирования" />

    Откройте ClickHouse Observability и перейдите в **Team Settings → Data → управляемая телеметрия**. Скопируйте конечную точку OTLP по HTTP и ключ API. Кнопка **Copy connection details** копирует конфигурацию, а **Reveal key** показывает скрытый ключ.

    <div className="ch-image-lg">
      <Frame>
        ![Сведения о подключении управляемой телеметрии](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Для приведённых ниже примеров с экспортером OTLP задайте следующие переменные в терминале, в котором будет запускаться коллектор:

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Замените плейсхолдеры точной конечной точкой (включая порт) и ключом API вашего сервиса. Указывайте базовую конечную точку HTTP без суффикса `/v1/logs`: экспортер сам добавляет путь сигнала.
  </Tab>

  <Tab title="Самоуправляемый">
    Укажите доступную конечную точку OTLP по HTTP вашего коллектора (например, `http://YOUR_COLLECTOR_HOST:4318`) и настройки аутентификации. Если коллектор не требует аутентификации, удалите блок `headers` экспортера из приведённых ниже конфигураций. Инструкции по настройке см. в [руководстве по началу работы с самоуправляемой версией](/ru/clickstack/self-configured/getting-started/managed).

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

Конечная точка должна быть доступна с отслеживаемого хоста или демонстрационного коллектора. Если коллектор-получатель запущен на хосте Docker, используйте `http://host.docker.internal:4318`.

## Интеграция с существующими системами {#existing-systems}

<Steps>
  <Step title="Проверьте журнал" id="verify-systemd">
    На хосте Linux, который нужно отслеживать:

    ```bash
    systemctl --version
    sudo journalctl -n 20
    sudo journalctl --disk-usage
    ```

    Приёмник использует `journalctl` на хосте для чтения доступных журналов. Поддерживается как постоянное, так и энергозависимое хранилище журнала, поэтому менять настройки хранилища не требуется.
  </Step>

  <Step title="Скачайте коллектор" id="download-collector">
    Выполните следующие команды на отслеживаемом хосте Linux:

    ```bash
    case "$(uname -m)" in
      x86_64) arch=amd64 ;;
      aarch64|arm64) arch=arm64 ;;
      *) echo "Unsupported architecture"; exit 1 ;;
    esac
    curl -fL -o otelcol-contrib.tar.gz \
      "https://github.com/open-telemetry/opentelemetry-collector-releases/releases/download/v0.161.0/otelcol-contrib_0.161.0_linux_${arch}.tar.gz"
    tar -xzf otelcol-contrib.tar.gz otelcol-contrib
    ```

    Коллектор работает непосредственно на хосте, поэтому может использовать установленный в системе `journalctl`. В стандартном Docker-образе Contrib этого бинарного файла нет.
  </Step>

  <Step title="Настройте коллектор" id="configure-collector">
    Сохраните следующую конфигурацию в файл `systemd-monitoring.yaml`:

    ```yaml
    receivers:
      journald:
        start_at: end
        priority: info
        convert_message_bytes: true
    processors:
      transform/journald:
        error_mode: ignore
        log_statements:
          - context: log
            statements:
              - merge_maps(log.attributes, log.body, "upsert")
              - set(resource.attributes["host.name"], log.attributes["_HOSTNAME"])
              - set(resource.attributes["service.name"], "systemd-logs")
              - set(log.attributes["unit"], log.attributes["SYSLOG_IDENTIFIER"])
              - set(log.attributes["unit"], log.attributes["_SYSTEMD_UNIT"]) where log.attributes["_SYSTEMD_UNIT"] != nil
              - set(log.attributes["priority"], log.attributes["PRIORITY"])
              - set(log.body, log.attributes["MESSAGE"])
              - set(log.severity_text, "info")
              - set(log.severity_number, SEVERITY_NUMBER_INFO)
              - set(log.severity_text, "warn") where Int(log.attributes["PRIORITY"]) == 4
              - set(log.severity_number, SEVERITY_NUMBER_WARN) where log.severity_text == "warn"
              - set(log.severity_text, "error") where Int(log.attributes["PRIORITY"]) == 3
              - set(log.severity_number, SEVERITY_NUMBER_ERROR) where log.severity_text == "error"
              - set(log.severity_text, "fatal") where Int(log.attributes["PRIORITY"]) < 3
              - set(log.severity_number, SEVERITY_NUMBER_FATAL) where log.severity_text == "fatal"
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [journald]
          processors: [transform/journald, batch]
          exporters: [otlp_http/observability]
    ```

    Поля журнала сохраняются как атрибуты записей журнала, сообщение становится телом записи журнала, а имя хоста — атрибутом ресурса. Приёмник собирает данные всех юнитов с приоритетом `info` и выше. Чтобы ограничить сбор, добавьте список `units` в раздел `journald` и укажите в нём реальные имена юнитов на вашем хосте, например `ssh.service` или `nginx.service`.
  </Step>

  <Step title="Запустите коллектор" id="run-collector">
    Задайте [переменные подключения](#connection-details), затем выполните команду из каталога, в который был загружен файл. Команда выполняется с правами администратора, чтобы читать системный журнал, и сохраняет в окружении только две переменные подключения:

    ```bash
    sudo --preserve-env=OTEL_EXPORTER_OTLP_ENDPOINT,OTEL_EXPORTER_OTLP_AUTHORIZATION \
      ./otelcol-contrib --config=systemd-monitoring.yaml
    ```

    Не закрывайте терминал. В другом терминале создайте запись в журнале:

    ```bash
    echo 'ClickHouse Observability journal ingestion test' | systemd-cat -t observability-test -p info
    ```

    По завершении тестирования остановите коллектор с помощью **Ctrl+C**. Для постоянного сбора данных запустите его как сервис systemd с доступом к журналу и настройте [хранилище курсора](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.161.0/receiver/journaldreceiver#cursor-tracking), чтобы после перезапуска сбор продолжался с того же места.
  </Step>

  <Step title="Проверьте журналы" id="verify-logs">
    Откройте **Поиск**, выберите **Logs**, задайте фильтр `ServiceName:systemd-logs` и выберите **Last 15 minutes**. Найдите тестовое сообщение и такие атрибуты, как `unit` и `priority`.
  </Step>
</Steps>

## Демонстрационный датасет {#demo-dataset}

Выборка содержит 1,334 текстовые записи журнала примерно за 48 часов, включая активность SSH, запланированные задания и события сервисов. В ней используется приёмник `filelog`, поэтому устанавливать systemd или `journalctl` не требуется. Коллектор обновляет временные метки, сохраняя исходное содержимое записей и интервалы между событиями.

<Steps>
  <Step title="Скачайте выборку" id="download-sample">
    ```bash
    curl -fL -o systemd-demo.log \
      https://datasets-documentation.s3.eu-west-3.amazonaws.com/clickstack-integrations/systemd/systemd-demo.log
    ```
  </Step>

  <Step title="Настройте демонстрационный коллектор" id="configure-demo">
    Сохраните следующую конфигурацию в файл `systemd-demo.yaml`:

    ```yaml
    receivers:
      filelog/systemd:
        include:
          - /var/log/demo/systemd-demo.log
        start_at: beginning
        operators:
          - type: regex_parser
            regex: '^(?P<timestamp>\S+) (?P<hostname>\S+) (?P<unit>\S+?)(?:\[(?P<pid>\d+)\])?: (?P<message>.*)$'
            parse_from: body
            parse_to: attributes
          - type: time_parser
            parse_from: attributes.timestamp
            layout: '%Y-%m-%dT%H:%M:%S%z'
          - type: add
            field: attributes.source
            value: systemd-demo
          - type: add
            field: resource["service.name"]
            value: systemd-demo
    processors:
      transform/demo_timestamps:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(resource.attributes["host.name"], log.attributes["hostname"])
              - set(log.time, Now() - Duration("2m") - (Time("2025-11-16T23:45:00Z", "%Y-%m-%dT%H:%M:%SZ") - log.time))
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [filelog/systemd]
          processors: [transform/demo_timestamps, batch]
          exporters: [otlp_http/observability]
    ```

    В текстовой выборке нет поля приоритета журнала, поэтому в демонстрационной конфигурации уровень серьёзности по тексту сообщения не определяется.
  </Step>

  <Step title="Запустите демонстрационный коллектор" id="run-demo">
    Задайте [переменные подключения](#connection-details), затем выполните команду в каталоге, где находятся оба файла:

    ```bash
    docker run --rm --name systemd-demo-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/systemd-demo.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      -v "$(pwd)/systemd-demo.log:/var/log/demo/systemd-demo.log:ro" \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```

    Не закрывайте терминал, пока проверяете приём данных. По завершении остановите коллектор клавишами **Ctrl+C**. При повторном запуске выборка будет загружена заново с обновлёнными временными метками.
  </Step>

  <Step title="Проверьте демонстрационные журналы" id="verify-demo">
    Откройте **Search**, выберите **Logs**, задайте фильтр `ServiceName:systemd-demo` и выберите **Last 2 days**. Должны отобразиться записи выборки с атрибутами `unit`, `hostname` и `message`.

    <div className="ch-image-lg">
      <Frame>
        ![Демонстрационные журналы systemd в разделе Search ClickHouse Observability](/images/clickstack/observability-systemd-demo-logs.png)
      </Frame>
    </div>
  </Step>
</Steps>

## Устранение неполадок {#troubleshooting}

### journalctl не найден {#journalctl-not-found}

Запускайте рабочий коллектор на отслеживаемом хосте Linux, где установлен `journalctl` и путь к нему указан в пути поиска исполняемых файлов. В демонстрационной конфигурации используется `filelog`, поэтому `journalctl` для неё не нужен.

### Журналы не отображаются {#no-logs}

Проверьте вывод коллектора на наличие ошибок доступа к журналу, аутентификации или экспорта. Убедитесь, что команда `sudo journalctl -n 20` возвращает записи на отслеживаемом хосте. Если вы настроили фильтр по единице измерения, убедитесь, что он совпадает с именами ваших сервисов. После запуска сбора создайте новую запись.

В ClickHouse Observability проверьте источник **Logs**, фильтр по имени сервиса и временной диапазон. Для демонстрации выберите **Last 2 days** и убедитесь, что файл с примером данных смонтирован по настроенному пути.
