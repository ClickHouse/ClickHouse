## Режим серий для тепловых карт, тепловые карты PromQL и явная гранулярность {#heatmap-series-mode-promql-heatmaps-and-explicit-granularity}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше тепловые карты отображали только числовые распределения: по оси Y откладывалось значение, разбитое на интервалы (например, длительность спана), а цвет показывал количество событий в каждом интервале. Теперь мы добавили режим серий: по оси Y отображается значение group-by, а цвет показывает выбранную агрегатную функцию для каждого временного интервала. По сути это аналог линейного графика с несколькими сериями, только значение передаётся цветом, а не высотой. Построитель и генерируемый запрос устроены так же, как у временных чартов.

В демонстрации мы группируем данные по имени сервиса за последние сутки. На тепловой карте количества ошибок сразу виден смоделированный инцидент в демонстрационной среде — две ячейки с заметно повышенными значениями. Расположенный рядом такой же чарт, построенный по агрегатной функции, не связанной с ошибками, выглядит ровным. Если group-by возвращает более 50 серий, отображается предупреждение и строятся первые 50 серий — по той же логике ограничения на стороне клиента, что и у временных чартов. Режим серий также доступен через внешний API панелей мониторинга и MCP.

Для источников PromQL доступны три режима тепловой карты. Режим серий работает так, как описано выше: используется range-запрос с поддержкой макросов, переменных и шаблонов легенды. В демонстрации с его помощью показана задержка p95 для каждого эндпоинта.

Режим гистограммы использует метрики, которые Prometheus уже разбил по интервалам. Границы интервалов берутся из меток `le`, а кумулятивные значения преобразуются в значения для каждого отдельного интервала. Чтобы объединить серии с одинаковыми границами интервалов, используйте `sum by (le) (...)`.

Режим распределения предназначен для данных, не являющихся гистограммами, когда всё же нужно получить числовое распределение. В каждой временной точке полученные выборки распределяются по интервалам на стороне клиента; линейные или логарифмические интервалы задаются в настройках чарта. Цвет показывает количество выборок в каждом интервале. В демонстрации показана степень использования 14 ядер CPU во времени с помощью `sum by (system_cpu_logical_number) (system_cpu_utilization{system_cpu_state!="idle"})`. PR для режимов гистограммы и распределения пока открыты.

Мы также исправили выбор гранулярности. Раньше тепловые карты игнорировали явно выбранное значение и всегда использовали auto, ориентируясь на 245 временных интервалов. Теперь выбранное значение учитывается, и гранулярность можно согласовать с другими чартами на панели мониторинга. Режим auto также учитывает минимальную гранулярность источника метрик.

Поля ввода выражений для количества и значения перенесены из настроек отображения в редактор чарта — как на панелях мониторинга, так и в Обозревателе диаграмм. Кроме того, тепловые карты теперь поддерживают форматирование чисел.

Наконец, подсветка при наведении теперь центрируется на ячейке, а не смещается вниз и вправо. Выбирается ближайшая ячейка, границы которой попадают в допустимую область вокруг курсора; попадание в эту область центра ячейки больше не требуется. Кроме того, состояние наведения обновляется при обновлении данных, если курсор по-прежнему находится над чартом.

## Переменные панели мониторинга с одиночным выбором {#single-select-dashboard-variables}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=208" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше все переменные панели мониторинга поддерживали только множественный выбор. Теперь переменную можно настроить на одиночный выбор: при выборе нового значения оно заменяет текущее. Если в URL передано несколько значений для переменной с одиночным выбором, используется первое из них.

Это особенно полезно для PromQL. Переменные с множественным выбором раскрываются в альтернацию регулярного выражения, которая работает с `=~`, но не с `=`, поэтому удобного способа использовать переменную с оператором сопоставления на равенство не существовало.

Мы также добавили формат переменных `promql`: если формат не указан, он вместо `regex` применяется по умолчанию к ссылкам на переменные в выражениях PromQL. Он работает так же, за исключением того, что значения с одиночным выбором не экранируются как регулярные выражения. Благодаря этому с переменной с одиночным выбором можно использовать `field="$var"`. Значения с множественным выбором по-прежнему экранируются как регулярные выражения, и для них следует использовать `field=~"$var"`.

**Связанные PR:** [#3295](https://github.com/hyperdxio/hyperdx/pull/3295) Поддержка фильтров панели мониторинга с одиночным выбором, [#3297](https://github.com/hyperdxio/hyperdx/pull/3297) Добавление формата переменных promql для гибкого экранирования

## Линейные диаграммы с накоплением {#stacked-line-charts}

*Демо от [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=271" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Наряду с `stacked_bar` мы добавили новый тип чарта временного ряда — `stacked_line`. Переключить линейный график в режим накопления можно в Обозревателе диаграмм или на панели мониторинга. В этом режиме серии располагаются одна над другой, а площадь под каждой из них заливается цветом, поэтому видно как итоговое значение, так и вклад каждой серии.

В CLI такие графики отображаются как столбчатые диаграммы с накоплением. Оба представления передают практически одну и ту же информацию, но в терминале накопление и заливку проще воспринимать в виде столбцов.

## Определение источника запросов ClickHouse {#attributing-clickhouse-queries-to-the-surface-that-issued-them}

*Демо от [@tommyzli](https://github.com/tommyzli)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=526" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Каждый SQL-запрос, который ClickStack отправляет в ClickHouse, теперь содержит JSON-поле `log_comment` и `query_id` в формате `hdx-<surface>-<uuid>`. Благодаря этому строку в `system.query_log` можно сопоставить с плиткой панели мониторинга, сохранённым поиском, оповещением или инструментом MCP, отправившим запрос. В последующем изменении такие же метки добавлены и для запросов PromQL, которые раньше отправлялись без них.

В демонстрации запрос к журналу запросов из раздела Search показал, что все запросы помечены как поступившие из Search, включая запросы `EXPLAIN` и столбчатую гистограмму. При открытии встроенной панели мониторинга ClickHouse её запросы отображались с меткой `clickhouse`, указывающей на преднастроенную панель мониторинга. Для пользовательской панели мониторинга каждый запрос содержал ID панели мониторинга и ID плитки чарта, отправившего запрос.

Если ClickStack использует ваш кластер ClickHouse совместно с другими рабочими нагрузками, так проще выделить его запросы, понять, из какой части приложения они пришли, и отслеживать стоимость запросов по источникам. Мы, со своей стороны, можем использовать это для связывания журнала запросов с конфигурациями панелей мониторинга при анализе использования. Кроме того, это шаг к автоматической оптимизации запросов: теперь медленный запрос можно сопоставить с плиткой, которая его сформировала.

**Связанные PR:** [#3155](https://github.com/hyperdxio/hyperdx/pull/3155) Определение источника запросов ClickHouse, [#3300](https://github.com/hyperdxio/hyperdx/pull/3300) Определение источника запросов PromQL

## Встроенные поля ввода для именования объектов {#inline-name-inputs-for-naming-objects}

*Демо от [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=296" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше именование работало по-разному в зависимости от того, в какой части приложения вы находились. У панелей мониторинга и сохранённых поисков заголовок редактировался по клику: при наведении появлялся значок карандаша, а двойной щелчок открывал редактирование, после чего нужно было нажать кнопку **Save Name**. В других местах использовалось текстовое поле с рамкой. Единого задокументированного подхода не было, поэтому на новых экранах обычно появлялся собственный вариант. Теперь стандартным способом именования объектов служит общий компонент `InlineNameInput`.

Он выглядит как обычный заголовок, пока на него не наведён курсор, — тогда появляется светлая рамка. По щелчку имя можно отредактировать прямо на месте. `Enter` или щелчок вне поля сохраняют изменения, а `Escape` или пустое имя отменяют их. Ни карандаша, ни отдельной кнопки сохранения нет. После сохранения отображается сохранённое значение. Если переименование завершается ошибкой или его перезаписывает параллельное сохранение панели мониторинга, отображаемое имя тоже возвращается к прежнему, и несохранённое имя не остаётся на экране.

Длинные имена усекаются; компонент доступен в размерах `xs`, `sm` и `md`. В заголовках страниц используется `md` — 18px вместо прежних примерно 22px. Как и раньше, они отображаются внутри элемента заголовка, чтобы их находили программы чтения с экрана.

Этот компонент теперь используется на страницах панелей мониторинга и сохранённых поисков, а старый компонент `EditablePageName` удалён. Есть также вариант `InlineNameInputControlled`, который сохраняет данные вместе с окружающей формой. Он предназначен для черновиков в полностраничном редакторе плиток, хотя в приложении пока не используется. В редакторе чартов пока остаётся прежнее поле **Chart Name**: сначала нужно доработать его структуру, чтобы туда вписалась встроенная версия.

Этот подход описан в `agent_docs/naming_objects.md`, в навыке агента `naming-objects`, а также в разделах Guidelines и Components в Storybook. Цель — помочь агенту программирования, работающему в репозитории, легко найти и повторно использовать компонент, когда понадобится добавить ещё одно место для задания имени.

**Связанные PR:** [#3278](https://github.com/hyperdxio/hyperdx/pull/3278) Add InlineNameInput as the one way to name objects

## Вложение сохранённых поисков в раздел Search {#nesting-saved-searches-under-search}

*Демо от [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iBMSK9QPXuA?start=389" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**Это исследовательская работа, и её выпуск не гарантирован.**

Сейчас у сохранённых поисков есть собственная страница со списком и отдельный пункт на боковой панели, не связанный с Search. Вы сохраняете поиск в одном месте, а найти его и управлять им приходится в другом. Чтобы дублировать поиск из списка, пользователю приходилось сначала открывать его и дублировать уже оттуда. Для панелей мониторинга отдельный список вполне оправдан, но для сохранённых поисков он выглядит не так естественно.

В этом черновике сохранённые поиски переносятся в Search. Пункт верхнего уровня **Сохранённые поиски** на боковой панели убран, а избранные поиски отображаются под Search — так же, как это уже сделано для панелей мониторинга. Кнопка **Сохранённые поиски** на панели инструментов открывает справа выдвижную панель с поиском, вкладками **All** и **Favorites**, фильтрацией по меткам, а также действиями переименования, дублирования и удаления в каждой строке. Панель открывается справа, чтобы не перекрывать навигацию приложения. Существующие ссылки `/search/list` тоже открывают выдвижную панель.

Если выбрать сохранённый поиск, на кнопке отображается его имя. Рядом с ней значок показывает статус **Unsaved**, **Saved** или **Edited**; **Edited** появляется после выполнения изменённого запроса. Для сравнения используется конфигурация поиска из URL, причём пустые и отсутствующие значения считаются эквивалентными, поэтому простая загрузка сохранённого поиска не помечает его как изменённый.

Отдельный заголовок сохранённого поиска удалён вместе с навигационной цепочкой, названием и строкой с датами создания и обновления. Избранное, метки, Terraform и меню действий переехали на панель инструментов, а сведения о создании и обновлении теперь показываются во всплывающей подсказке на кнопке. Благодаря этому интерфейс выглядит одинаково для сохранённых и несохранённых поисков. Вместе с заголовком пропала возможность переименовать поиск двойным щелчком по названию, однако это по-прежнему можно сделать через меню строки на выдвижной панели или в модальном окне **Update**. Нужно ли вообще модальное окно для обновления — вопрос пока открытый. В идеале обновление должно быть одним действием, без попутного предложения переименовать поиск.

Это всё ещё черновик, и мы будем рады отзывам о его поведении. Четыре сквозных теста в наборе для выдвижной панели пока не проходят — их нужно исправить, прежде чем работа выйдет из статуса черновика.
