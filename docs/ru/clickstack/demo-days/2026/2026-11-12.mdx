## Размер блока текстового индекса и ускорение поиска в фильтрах {#text-index-block-size-and-faster-filter-lookups}

*Демо от [@knudtty](https://github.com/knudtty)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Панель фильтров ClickStack могла медленно загружаться и оставлять поля пустыми, даже если подходящие значения существовали. В продемонстрированном случае для таблицы с 537M строк журнала подсказки возвращались около 30 секунд, причём лишь для 22 из 100 ключей. После внесённых изменений та же панель возвращает подсказки для всех 100 ключей и загружается быстрее.

Панель использует текстовые индексы, чтобы обнаруживать ключи Map и их значения. Например, она может найти ключ `service` и предложить такие значения, как `checkout` и `billing`. Это избавляет от сканирования необработанных журналов, однако открытие индексов всё равно оставалось затратным.

Каждый текстовый индекс содержит отсортированный словарь токенов, разделённый на блоки. В заголовке записано, где начинается каждый блок, что позволяет ClickHouse сразу перейти к нужному блоку. Чем больше блоки, тем меньше записей в заголовке и тем меньше данных нужно загрузить перед началом поиска. Aaron наглядно объясняет это в видео.

Теперь схема задаёт `text_index_dictionary_block_size = 8192` (вместо прежнего значения по умолчанию 512) для `otel_logs`, `otel_traces` и `hyperdx_sessions`. В локальном бенчмарке это уменьшило заголовок с 17.7 KB до 1.3 KB на одну часть. Миграция применяется в ClickHouse 26.6 и более поздних версиях, в том числе к существующим установкам, и сохраняет явно заданные настройки таблиц. Новые части используют более крупные блоки; существующие части сохраняют прежнюю структуру до слияния.

Благодаря уменьшенному заголовку искать по каждому ключу отдельно стало практически целесообразно. Ранее все ключи обрабатывались одним запросом с лимитом по умолчанию в 3 миллиона записей индекса. Ключ с миллионами различных значений, например идентификатор запроса, мог исчерпать этот лимит, оставив последующие ключи без подсказок. Такой неполный результат затем мог попасть в кэш.

Для индексов, настроенных с более крупными блоками, у каждого ключа теперь собственный лимит в 20 000 записей индекса. Поиск выполняется параллельными пакетами по 10 ключей, поэтому ключ с большим числом значений не может израсходовать квоту другого ключа. `topKWeighted` отбирает приблизительно наиболее частые значения среди прочитанных записей вместо прежнего отбора первых значений в алфавитном порядке. Индексы, настроенные с меньшими блоками, сохраняют прежний способ поиска внутри каждого пакета.

Первоначальный поиск ключей и значений также читает меньше частей. По умолчанию просматривается до 20 частей из середины ранжирования по размеру. Параметр **Map key index parts** задаёт их количество, а **Map key index part size** позволяет выбрать части среднего размера, самые маленькие или самые большие. Это сокращает чтения индексов, особенно когда для них требуется загрузка данных из объектного хранилища. Обратная сторона — подсказки могут пропускать ключи или значения за пределами выбранных частей, а оценки частоты отражают только просмотренные записи. Функция Load more для отдельного ключа читает все релевантные части.

Отдельное исправление позволяет параллельным вызывающим сторонам с совпадающими параметрами использовать один выполняющийся запрос `getMapKeys`. Ранее при открытии страницы поиска одни и те же чтения могли выполняться дважды. В примере с таблицей на эти дублирующиеся запросы приходилось около 47 GiB суммарной памяти запросов. Теперь каждое чтение выполняется один раз.

Более крупные блоки также улучшили производительность поиска по текстовому индексу в представленных бенчмарках: некоторые запросы стали быстрее примерно на 60% при том же количестве частей. Ещё одно изменение, пока не влитое, использует `topKWeighted` для обнаружения распространённых ключей Map без группировки всех различных ключей. На таблице примерно с 5.5M различных ключей на часть представленный бенчмарк показал сокращение времени запроса с 9.1 до 2.6 секунды, а потребления памяти — с 14 GiB до 78 MiB.

## Подключения к MCP-серверу без пользовательских заголовков {#mcp-server-connections-without-custom-headers}

*Демо от [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok?start=396" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше для подключения агента к MCP-серверу ClickStack в ClickHouse Cloud приходилось передавать идентификатор сервиса в пользовательском HTTP-заголовке. Большинство MCP-клиентов не позволяют легко задавать пользовательские заголовки, а некоторые не поддерживают их вовсе, поэтому для каждого агента приходилось вручную править отдельную конфигурацию.

Теперь по умолчанию идентификатор сервиса передаётся как параметр запроса в URL MCP — этот подход команда ClickHouse AI уже применяла, чтобы обойти то же ограничение. Для клиентов, которые это поддерживают, настройка агента теперь сводится к одной команде (например, для Codex раньше нужно было вставлять блок в его конфигурацию TOML), а клиенты, которые не могут выполнить команду, просто принимают URL как есть.

Сразу после слияния этого изменения в Claude Code убрали поддержку пользовательских заголовков в конфигурации MCP, и настройка на основе заголовков перестала работать в продакшне. Соединений, использующих параметр запроса, это не коснулось.

Это относится к облачной конечной точке MCP. MCP-сервер с открытым исходным кодом использует аутентификацию по Bearer-токену, и передавать ему идентификатор сервиса не нужно. В этом случае команда `npx @hyperdx/cli mcp install` запрашивает персональный ключ API или ключ API организации (ввод скрыт), проверяет его и автоматически добавляет сервер в конфигурации Claude Code, Codex, Cursor и VS Code.

## Настройка агента Datadog в разделе «Начало работы» {#datadog-agent-setup-in-getting-started}

*Демо от [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok?start=469" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

В разделе «Начало работы» агент Datadog теперь указан рядом с другими SDK и коллекторами, поэтому существующие агенты Datadog можно перенаправить на ClickStack, не покидая страницу первоначальной настройки.

Конечная точка ингестии Datadog, отображаемая на этой странице, предоставляется плоскостью данных ClickHouse Cloud, которая теперь передаёт этот URL во фронтенд вместе с остальными конечными точками. Инструкции по настройке, как и для всех остальных SDK, берутся из публичной документации, поэтому страница всегда соответствует [руководству по миграции с Datadog](https://clickhouse.com/docs/clickstack/migration/datadog).

Сам приёмник преобразует полезные нагрузки журналов, трасс и метрик Datadog в модель данных OpenTelemetry внутри коллектора ClickStack, поэтому существующие агенты и SDK продолжают работать без изменений. В ClickStack с открытым исходным кодом он прослушивает порт 8126 и включается параметром `ENABLE_DATADOG_RECEIVER=true`.

## Ключи API организации {#organization-api-keys}

*Демо от [@jordan-simonovski](https://github.com/jordan-simonovski)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/aQ4d7pFMZok?start=497" title="Видеоплеер YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Раньше единственными учётными данными типа bearer для внешнего API и MCP-сервера был персональный ключ доступа. Такой ключ перестаёт работать, как только его владельца удаляют из команды, поэтому настроенные с ним Terraform, CI и другая автоматизация ломались, а командам приходилось обходить проблему с помощью пользователей-ботов.

Теперь ключи API, принадлежащие команде, можно создавать в разделе **Team Settings** &gt; **API &amp; Agents**. Для каждого ключа задаются описание и срок действия: 30 дней, один год или бессрочно. Полный ключ показывается один раз при создании, а хранится в виде хеша SHA-256. В списке видно, кто создал каждый ключ, когда он последний раз использовался и когда истекает его срок действия, — так можно найти редко используемые ключи или ключи с истекающим сроком и сразу же их отозвать. Отзыв ключа или истечение его срока действия вступает в силу со следующего запроса.

Каждый ключ — это отдельная служебная учётная запись с теми же разрешениями, что и у любого другого пользователя. Всё, что создано с его помощью (оповещения, панели мониторинга, сохранённые поиски), записывается на служебную учётную запись, а не на человека, создавшего ключ. Ключи, созданные пользователем, который впоследствии был удалён, отображаются как «Deleted user» и продолжают работать. Служебные учётные записи не могут входить в систему и не отображаются в разделе **Members**. С помощью ключей нельзя приглашать людей, а также создавать или отзывать другие ключи.

Ключи организации работают везде, где работает персональный ключ: во внешнем API v2, в MCP-сервере и в `npx @hyperdx/cli mcp install`. При использовании Terraform-провайдера ключ передаётся вместе с ID вашей команды. Функция рассчитана на самоуправляемые развертывания, и RBAC за ней не стоит: в ClickStack с открытым исходным кодом нет ролей, поэтому любой участник команды может управлять ключами организации, а ключ может делать всё то же, что и пользователь.
