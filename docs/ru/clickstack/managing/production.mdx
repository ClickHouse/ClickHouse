При развертывании ClickStack с открытым исходным кодом в продакшн-среде учитывайте следующие рекомендации по безопасности, стабильности и конфигурации.

## Безопасность сети и портов {#network-security}

По умолчанию Docker Compose открывает порты на хосте, делая их доступными извне контейнера — даже если такие инструменты, как `ufw` (Uncomplicated Firewall), включены. Такое поведение обусловлено сетевым стеком Docker, который может обходить правила брандмауэра на уровне хоста, если не настроен явным образом.

**Рекомендация:**

Открывайте только те порты, которые необходимы для работы в production-среде. Как правило, это конечные точки OTLP, API-сервер и фронтенд.

Например, удалите или закомментируйте ненужные маппинги портов в файле `docker-compose.yml`:

```yaml
ports:
  - "4317:4317"  # OTLP gRPC
  - "4318:4318"  # OTLP HTTP
  - "8080:8080"  # Only if needed for the API
# Avoid exposing internal ports like ClickHouse 8123 or MongoDB 27017.
```

Подробнее об изоляции контейнеров и усилении защиты доступа см. в [документации по сетям Docker](https://docs.docker.com/network/).

## Настройка секрета сеанса {#session-secret}

В продакшн-среде необходимо задать надёжное случайное значение переменной окружения `EXPRESS_SESSION_SECRET` для интерфейса ClickStack — это защитит данные сеансов от подделки.

Вот как добавить её в файл `docker-compose.yml` для сервиса приложения:

```yaml
  app:
    image: ${IMAGE_NAME_HDX}:${IMAGE_VERSION}
    ports:
      - ${HYPERDX_API_PORT}:${HYPERDX_API_PORT}
      - ${HYPERDX_APP_PORT}:${HYPERDX_APP_PORT}
    environment:
      FRONTEND_URL: ${HYPERDX_APP_URL}:${HYPERDX_APP_PORT}
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_API_PORT: ${HYPERDX_API_PORT}
      HYPERDX_APP_PORT: ${HYPERDX_APP_PORT}
      HYPERDX_APP_URL: ${HYPERDX_APP_URL}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      MINER_API_URL: 'http://miner:5123'
      MONGO_URI: 'mongodb://db:27017/hyperdx'
      NEXT_PUBLIC_SERVER_URL: http://127.0.0.1:${HYPERDX_API_PORT}
      OTEL_SERVICE_NAME: 'hdx-oss-api'
      USAGE_STATS_ENABLED: ${USAGE_STATS_ENABLED:-true}
      EXPRESS_SESSION_SECRET: "super-secure-random-string"
    networks:
      - internal
    depends_on:
      - ch-server
      - db1
```

Надёжный секрет можно сгенерировать с помощью `openssl`:

```shell
openssl rand -hex 32
```

Не добавляйте секреты в систему контроля версий. В продакшне рекомендуется использовать инструменты управления переменными окружения (например, Docker Secrets, HashiCorp Vault или отдельные конфигурации CI/CD для каждого окружения).

## Безопасная ингестия {#secure-ingestion}

Вся ингестия должна выполняться через порты OTLP, которые открывает входящий в ClickStack дистрибутив коллектора OpenTelemetry (OTel). По умолчанию для этого требуется защищённый ключ API для ингестии, который генерируется при запуске. Этот ключ необходим для отправки данных на порты OTel; его можно найти в интерфейсе ClickStack в разделе `Team Settings → API Keys`.

Рекомендуется создать отдельного пользователя для OTel collector для ингестии данных в ClickHouse и настроить отправку данных в конкретную базу данных, например `otel`. ## ClickHouse {#clickhouse}

Пользователям, которые самостоятельно управляют экземпляром ClickHouse, следует придерживаться приведённых ниже рекомендуемых практик.

### Рекомендуемые практики безопасности {#self-managed-security}

Если вы самостоятельно управляете экземпляром ClickHouse, крайне важно включить **TLS**, сделать аутентификацию обязательной и следовать рекомендуемым практикам по усилению защиты доступа. О реальных ошибках конфигурации и способах их избежать читайте в [этой статье в блоге](https://www.wiz.io/blog/clickhouse-and-wiz).

ClickHouse OSS из коробки предоставляет надёжные средства безопасности, однако их необходимо настроить:

* **Используйте TLS** с помощью `tcp_port_secure` и `<openSSL>` в `config.xml`. См. [guides/sre/configuring-tls](/ru/concepts/features/security/tls/configuring-tls).
* **Задайте надёжный пароль** для пользователя `default` или отключите его.
* **Не открывайте доступ к ClickHouse извне**, если это не требуется явно. По умолчанию ClickHouse прослушивает только `localhost`, если не изменён параметр `listen_host`.
* **Используйте методы аутентификации**: пароли, сертификаты, SSH-ключи или [внешние аутентификаторы](/ru/concepts/features/security/external-authenticators/index).
* **Ограничьте доступ** с помощью фильтрации по IP и предложения `HOST`. См. [sql-reference/statements/create/user#user-host](/ru/reference/statements/create/user#user-host).
* **Включите ролевое управление доступом (RBAC)** для детальной выдачи привилегий. См. [operations/access-rights](/ru/concepts/features/security/access-rights).
* **Применяйте квоты и ограничения** с помощью [квот](/ru/concepts/features/configuration/server-config/quotas), [профилей настроек](/ru/concepts/features/configuration/settings/settings-profiles) и режимов только для чтения.
* **Шифруйте хранимые данные** и используйте защищённое внешнее хранилище. См. [operations/storing-data](/ru/concepts/features/configuration/server-config/storing-data) и [cloud/security/CMEK](/ru/products/cloud/guides/security/cmek).
* **Не прописывайте учётные данные в коде.** Используйте [именованные коллекции](/ru/concepts/features/configuration/server-config/named-collections) или роли IAM в ClickHouse Cloud.
* **Проводите аудит доступа и запросов** с помощью [системных журналов](/ru/reference/system-tables/query_log) и [журналов сеансов](/ru/reference/system-tables/session_log).

См. также разделы о [внешних аутентификаторах](/ru/concepts/features/security/external-authenticators/index) и [настройках сложности запросов](/ru/concepts/features/configuration/settings/query-complexity), чтобы узнать, как управлять пользователями и ограничивать запросы и потребление ресурсов.

### Права пользователя для интерфейса ClickStack {#user-permissions}

Пользователь ClickHouse для интерфейса ClickStack должен иметь `readonly = 2`. Интерфейс задаёт собственные настройки, например `date_time_output_format`, в каждом запросе, а чарты Raw SQL также устанавливают `readonly = 2`, поэтому у пользователя с `readonly = 1` такие запросы завершаются ошибкой `Cannot modify '...' setting in readonly mode`. При `readonly = 2` интерфейс также может задавать `max_rows_to_read`, `read_overflow_mode` и `cancel_http_readonly_queries_on_client_close`; если вы ограничиваете `max_rows_to_read`, установите лимит не менее 1 миллиона строк. `wait_end_of_query` — это параметр HTTP-интерфейса, а не настройка, поэтому выдавать для него grant не нужно.

Например:

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

По умолчанию пользователь `default` как в OSS, так и в ClickHouse Cloud обладает этими разрешениями, однако мы рекомендуем создать для этого отдельного пользователя.

## Настройка Time To Live (TTL) {#configure-ttl}

Убедитесь, что для вашего развертывания ClickStack [правильно настроен TTL (Time To Live)](/ru/clickstack/managing/ttl) — [подробнее о настройке](/ru/clickstack/managing/ttl#modifying-ttl). Этот параметр определяет срок хранения данных; значение по умолчанию (30 дней) может потребовать корректировки.
