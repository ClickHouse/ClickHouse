Рабочие нагрузки обсервабилити предъявляют к одним и тем же данным два совершенно разных требования. Ингестия идёт непрерывно и сопряжена с интенсивной записью, а фоновые слияния продолжают потреблять CPU и память ещё долго после завершения вставки. Нагрузка от запросов неравномерна: обращения к панелям мониторинга и поиску достигают пика во время инцидента — именно тогда, когда медленный ответ наименее допустим.

[Хранилища](/ru/products/cloud/features/infrastructure/warehouses) ClickHouse Cloud позволяют обслуживать обе рабочие нагрузки на одних и тех же данных с помощью раздельных вычислительных ресурсов, так что они не конкурируют друг с другом за CPU и память.

<ScalePlanFeatureBadge feature="Compute-compute separation" />

Хранилища — это возможность ClickHouse Cloud, поэтому описанная здесь настройка применима к самостоятельно управляемому ClickHouse Observability: для каждой части разделения независимо задаётся объём ресурсов, настраивается масштабирование и перевод в состояние простоя, при этом обе части работают с единственной копией данных.

<Note>
  **Когда изоляция оправдана**

  Изоляция рассчитана на крупные развертывания с непрерывной загрузкой данных. Если объём хранимых данных не превышает примерно 100 TB в месяц, один сервис чтения и записи обычно справляется с обеими рабочими нагрузками, и второй сервис, скорее всего, не понадобится. Чтобы оценить ежемесячный объём сжатых данных, воспользуйтесь [моделью расчёта ресурсов](/ru/clickstack/self-configured/managing/estimating-resources).
</Note>

## Зачем разделять операции чтения и записи {#why-isolate}

* **Операции записи больше не замедляют чтение.** Непрерывная ингестия данных OpenTelemetry — сами вставки, а также следующие за ними фоновые слияния — конкурирует с запросами панелей мониторинга и поиска за CPU и память. Во время ингестии задержка чтения может заметно возрастать и возвращается к норме после её завершения.
* **Чтение больше не мешает операциям записи.** Конкуренция за ресурсы идёт в обе стороны: тяжёлый ad-hoc-запрос или ресурсоёмкая отрисовка панели мониторинга может исчерпать память сервиса и привести не просто к замедлению вставок, а к их сбою.
* **Вычислительные ресурсы только для чтения целиком выделены под запросы.** Сервисы только для чтения не выполняют фоновых слияний, за исключением системных таблиц. Кроме того, в отличие от сервисов для чтения и записи, которые слияния могут удерживать в активном состоянии, они переходят в состояние простоя без задержки.
* **Ресурсы для каждой стороны рассчитываются отдельно.** [Модель расчёта ресурсов](/ru/clickstack/self-configured/managing/estimating-resources) оценивает вычислительные ресурсы для приёма данных и для выполнения запросов по отдельности, а хранилище позволяет выделить каждую из этих частей в собственный сервис. Выше базового уровня модели в 1 QPS основную долю составляют вычислительные ресурсы для выполнения запросов: в её [разобранном примере](/ru/clickstack/self-configured/managing/estimating-resources#worked-example) при 5 QPS получается 58 vCPU для приёма данных против 290 для запросов. Поэтому небольшой сервис записи может обслуживать значительно более крупный сервис чтения.
* **Переход в состояние простоя и автоматическое масштабирование настраиваются для каждого сервиса отдельно.** У каждого сервиса собственное количество реплик и свои параметры автоматического масштабирования и автоматического перехода в режим ожидания, поэтому сервис записи может работать постоянно, обеспечивая непрерывную ингестию, а сервис чтения — простаивать в нерабочее время.
* **Хранилище не дублируется.** Сервисы в хранилище используют одну и ту же папку объектного хранилища и одни и те же таблицы, а [хранилище оплачивается только один раз](/ru/products/cloud/features/infrastructure/warehouses#pricing).
* **Доступ можно ограничить для каждой конечной точки отдельно.** IP Access List применяются к каждому сервису в отдельности, поэтому конечную точку записи можно сделать доступной только для ваших коллекторов, а конечную точку чтения — только для интерфейса обсервабилити. Подробнее см. в нашем руководстве по [управлению сетевым доступом](/ru/products/cloud/features/infrastructure/warehouses#network-access-control).

## Архитектура {#architecture}

Рекомендуемая топология — хранилище с одним сервисом чтения и записи для ингестии и одним сервисом только для чтения для интерфейса обсервабилити:

| Сервис    | Тип               | Задачи                                                                   | Клиенты                                                                                 |
| --------- | ----------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| Основной  | Чтение и запись   | Ингестия, фоновые слияния, DDL (создание таблиц, TTL, materialized view) | OpenTelemetry collector, ClickPipes, Vector, консоль SQL / клиент для администрирования |
| Вторичный | Только для чтения | Поиск, панели мониторинга, блокноты, оценка оповещений                   | Интерфейс обсервабилити                                                                 |

При планировании топологии учитывайте следующее:

* Первый сервис в хранилище всегда работает в режиме чтения и записи, а тип сервиса **задаётся при создании и не может быть изменён** — чтобы перейти с режима только для чтения на режим чтения и записи или наоборот, создайте в хранилище новый сервис.
* Все сервисы в хранилище используют одного и того же облачного провайдера, регион, версию ClickHouse и Keeper, а также расписание обновлений основного сервиса.
* Используйте для ингестии **один** сервис чтения и записи. Слияния распределяются между всеми сервисами чтения и записи с общим хранилищем, поэтому слияние для вставки, выполненной на одном сервисе, может выполнить другой. Если этот другой сервис также обрабатывает тяжёлые запросы, они конкурируют со слиянием за CPU и память на этом сервисе — в результате слияния для вставок первого сервиса замедляются, а вместе с ними снижается и производительность вставки. Выполняйте запросы на сервисе только для чтения, а второй сервис чтения и записи добавляйте, только если нужно [отделить слияния от ингестии](#separating-merges).

## Настройка изолированного развертывания {#setup}

<Steps>
  <Step title="Подготовьте сервис чтения и записи" id="prepare-read-write-service">
    Используйте для ингестии существующий сервис или основной сервис нового хранилища, выбрав его размер с учётом вычислительных ресурсов для приёма данных, рассчитанных по [модели расчёта ресурсов](/ru/clickstack/self-configured/managing/estimating-resources).

    Создайте на этом сервисе базу данных и выделенного пользователя для ингестии. Поскольку у всех сервисов хранилища общее управление доступом, созданные здесь пользователи будут доступны на каждом сервисе хранилища:

    ```sql
    CREATE DATABASE otel;
    CREATE USER hyperdx_ingest IDENTIFIED WITH sha256_password BY '<strong-password>';
    GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO hyperdx_ingest;
    ```

    Сгенерируйте пароль с помощью утилиты, например `openssl rand -base64 24`, и храните его в менеджере секретов, а не в манифесте или истории командной оболочки. Подробнее см. в руководстве [Создание пользователя для ингестии](/ru/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured).

    Если этот сервис уже входит в хранилище, учтите, что DDL-операции на уровне базы данных могут зависать, если другой сервис этого хранилища находится в состоянии простоя, — см. раздел [Администрирование и DDL](#administration).
  </Step>

  <Step title="Добавьте в хранилище сервис только для чтения" id="add-read-only-service">
    В консоли ClickHouse Cloud нажмите на значок «плюс» у только что подготовленного сервиса, чтобы создать второй сервис, использующий те же данные. В качестве типа сервиса выберите **только для чтения** и задайте его размер исходя из вычислительных ресурсов для выполнения запросов, рассчитанных по модели расчёта ресурсов.

    Подробное пошаговое описание см. в нашем руководстве [Как настроить хранилище](/ru/products/cloud/features/infrastructure/warehouses#setup-warehouses).
  </Step>

  <Step title="Направьте поток ингестии в сервис чтения и записи" id="point-ingestion">
    Настройте коллектор на экспорт данных в конечную точку сервиса **с возможностью чтения и записи**, выполняя аутентификацию от имени пользователя для ингестии:

    ```shell
    CLICKHOUSE_ENDPOINT=https://<read-write-service>.clickhouse.cloud:8443
    CLICKHOUSE_USER=hyperdx_ingest
    CLICKHOUSE_PASSWORD=<strong-password>
    HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel
    ```

    Подробнее см. [параметры конфигурации коллектора](/ru/clickstack/self-configured/managing/config#otel-collector) или аналогичные настройки для [Vector](/ru/clickstack/observability/ingesting-data/vector) и других способов ингестии.

    Операции записи, отправленные на конечную точку только для чтения, отклоняются, поэтому коллектор всегда должен отправлять данные в сервис чтения и записи.
  </Step>

  <Step title="Настройте подключение интерфейса обсервабилити к сервису только для чтения" id="point-clickstack">
    Интерфейс обсервабилити всегда подключается к тому сервису ClickHouse, из которого он запущен в консоли ClickHouse Cloud. Чтобы запускать его на вычислительных ресурсах только для чтения:

    1. Выберите сервис только для чтения в консоли ClickHouse Cloud.
    2. Выберите **ClickStack** в левой панели навигации.

    После этого все запросы, отправляемые интерфейсом, будут выполняться на этих вычислительных ресурсах только для чтения. Дополнительно настраивать что-либо в интерфейсе обсервабилити не требуется. Подробнее см. в руководстве [Использование интерфейса обсервабилити с вычислительными ресурсами только для чтения](/ru/clickstack/self-configured/deployment/managed#clickstack-read-only-compute).

    <Warning>
      **Состояние интерфейса обсервабилити привязано к сервису**

      Панели мониторинга, сохранённые поиски, оповещения и источники принадлежат сервису, из которого был запущен интерфейс обсервабилити, и не переносятся на другой сервис в том же хранилище, хотя оба сервиса используют одни и те же данные. Источники, использующие [схему OpenTelemetry по умолчанию](/ru/clickstack/self-configured/deployment/managed#adding-data-sources), в новом сервисе обнаруживаются автоматически, поэтому поиск по этим данным работает сразу. Однако пользовательские или вручную настроенные источники, а также всё остальное, что вы сохранили, придётся создать заново.

      Определитесь, из какого сервиса будет запускаться интерфейс обсервабилити, до того как создавать панели мониторинга. Если вы переводите на другой сервис уже работающее развертывание, учтите, что оповещения, созданные в предыдущем сервисе, продолжат вычисляться там — на вычислительных ресурсах этого сервиса, — пока вы их не удалите.
    </Warning>
  </Step>

  <Step title="Проверьте разделение" id="verify">
    Выполните поиск или откройте панель мониторинга в интерфейсе обсервабилити, а затем проверьте, где были выполнены запросы. Записи в таблицы `system` попадают на том узле, который выполнил запрос, поэтому если у сервиса несколько реплик, чтобы охватить их все, используйте [`clusterAllReplicas`](/ru/reference/system-tables/overview#querying-across-nodes) с именем кластера `default`. На сервисе **только для чтения** должны отображаться запросы обсервабилити:

    ```sql
    SELECT
        user,
        query_kind,
        http_user_agent,
        count()
    FROM clusterAllReplicas('default', system.query_log)
    WHERE event_time > now() - toIntervalMinute(10)
      AND type = 'QueryFinish'
      AND is_initial_query = 1
    GROUP BY ALL
    ORDER BY count() DESC;
    ```

    Пустой результат здесь сам по себе не означает, что запросы ушли в другое место: `system.query_log` периодически сбрасывается на диск — по умолчанию каждые 7.5 секунды, — поэтому запрос, выполненный сразу после поиска, может ещё не увидеть нужных записей. Подождите немного и выполните его снова или принудительно сбросьте журналы на диск с помощью [`SYSTEM FLUSH LOGS`](/ru/reference/statements/system#flush-logs), если у вас есть соответствующий grant.

    Определить, откуда идёт трафик, позволяет именно группировка по `user` и `http_user_agent`: она отличает интерфейс от консоли SQL и от любых других клиентов, подключающихся к конечной точке, независимо от того, на какие таблицы указывают ваши источники. Фильтрация по `is_initial_query = 1` оставляет по одной строке на каждый запрос в том виде, в каком он был отправлен: вторичные запросы распределённого выполнения, а также внутренние запросы, вычисляющие [materialized view](/ru/reference/system-tables/query_views_log), записываются отдельно с `is_initial_query = 0`.

    На сервисе **с возможностью чтения и записи** тот же запрос должен показать вставки от пользователя ингестии и полное отсутствие трафика запросов обсервабилити.

    Надёжный способ проверки — выполнить запрос поочерёдно на каждом сервисе, поскольку кластер `default` содержит только реплики того сервиса, к которому вы подключены. Чтобы получить агрегированную картину по всему хранилищу, используйте вместо него имя кластера `all_groups.default`:

    ```sql
    SELECT
        hostName() AS host,
        query_kind,
        count()
    FROM clusterAllReplicas('all_groups.default', system.query_log)
    WHERE event_time > now() - toIntervalMinute(10)
      AND type = 'QueryFinish'
      AND is_initial_query = 1
    GROUP BY ALL;
    ```

    При использовании этого запроса учитывайте два момента: сервисы в состоянии простоя не возвращают строки, поэтому, если вам нужен полный результат, сначала выведите их из простоя; кроме того, `hostName()` идентифицирует реплику, а не сервис — чтобы определить, к какому сервису относится активность, выполните запрос непосредственно к этому сервису.
  </Step>
</Steps>

## Отделение слияний от ингестии {#separating-merges}

При очень высокой устойчивой скорости приёма данных основную нагрузку на сервис приёма создают слияния, а не сами вставки. Поскольку слияния распределяются между всеми сервисами чтения и записи, использующими общее хранилище, они могут оказаться и на сервисе, предназначенном для других задач.

В таких развертываниях слияния можно полностью вынести с сервиса приёма и получить топологию из трёх сервисов:

| Сервис  | Тип                                | Обязанности                                           |
| ------- | ---------------------------------- | ----------------------------------------------------- |
| Приём   | Чтение и запись, слияния отключены | Принимает только вставки                              |
| Слияние | Чтение и запись                    | Выполняет все фоновые слияния и мутации для хранилища |
| Запросы | Только для чтения                  | Обслуживает интерфейс обсервабилити                   |

<Info>
  **Требуется обращение в службу поддержки**

  Отключение слияний на сервисе чтения и записи недоступно в Консоли Cloud. [Обратитесь в службу поддержки](https://clickhouse.com/support/program), чтобы применить эту настройку к сервису.
</Info>

Эту топологию стоит рассмотреть, если один только приём данных полностью загружает сервис или если вам нужны два сервиса чтения и записи, поскольку запись должны выполнять оба. Если рабочая нагрузка запросов полностью обслуживается интерфейсом обсервабилити, который только читает данные, то более простого [разделения на сервис чтения и записи и сервис только для чтения](#architecture) достаточно, и этот вариант поддерживается лучше.

При использовании этой топологии учитывайте следующее:

* **Не полагайтесь на автоматический переход в режим ожидания ни для одного из сервисов чтения и записи.** Сервис с отключёнными слияниями по-прежнему обрабатывает события загрузки и удаления частей, порождаемые вставками в других сервисах хранилища, а большое количество неслитых частей само по себе может препятствовать переходу в состояние простоя. Исходите из того, что оба сервиса чтения и записи будут работать непрерывно.
* **Не направляйте запросы ни на один из сервисов чтения и записи.** Тяжёлые `SELECT`-запросы на сервисе чтения и записи конкурируют со слияниями за CPU и память — именно такого сценария сбоя и позволяет избежать эта топология. Направьте интерфейс обсервабилити на сервис только для чтения, как описано [выше](#point-clickstack).
* **Мутации, если они есть, отслеживаются на сервисе, который их выполняет.** В обсервабилити мутации встречаются редко: стандартная схема обсервабилити задаёт [`ttl_only_drop_parts = 1`](/ru/clickstack/self-configured/managing/ttl), поэтому при обычном удалении по сроку хранения во время TTL-слияний отбрасываются целые части с истекшим сроком действия, а строки не удаляются с помощью мутаций. Если вы всё же отправите на сервис приёма `ALTER`, порождающий мутацию, её выполнит сервис слияния, и ход выполнения будет отображаться в [`system.mutations`](/ru/reference/system-tables/mutations) на нём, а не на сервисе приёма.

## Администрирование и DDL {#administration}

Все изменения схемы должны выполняться на сервисе **с возможностью чтения и записи**, в том числе:

* Создание таблиц — выполняется автоматически коллектором ClickStack при первом приёме данных
* [Изменение TTL](/ru/clickstack/self-configured/managing/ttl#modifying-ttl) для настройки срока хранения
* Создание [materialized view](/ru/clickstack/self-configured/managing/materialized-views) для ускорения запросов
* Добавление [индексов пропуска, проекций и других оптимизаций производительности](/ru/clickstack/self-configured/managing/performance-tuning)

Пользователи, роли и привилегии не относятся к изменениям схемы — они общие для всех сервисов хранилища, поэтому каждый из них достаточно создать один раз на любом сервисе. Описанные выше [шаги настройки](#prepare-read-write-service) создают пользователя для ингестии. Любой другой клиент, подключаемый к сервису только для чтения, должен аутентифицироваться под отдельным пользователем для запросов с правами только на чтение и с [разрешениями, необходимыми интерфейсу observability](/ru/clickstack/self-configured/managing/production#user-permissions), а не с показанными выше привилегиями для ингестии.

Подключитесь к сервису чтения и записи через [SQL-консоль](/ru/products/cloud/features/sql-console-features/sql-console) или [клиент ClickHouse](/ru/concepts/features/interfaces/client). Поскольку сервисы хранилища используют общее хранилище данных и общее управление доступом, изменения сразу становятся видны сервису только для чтения. Если вы [отделили слияния от ингестии](#separating-merges), операторы можно отправлять на любой из сервисов чтения и записи, однако учтите, что мутации выполняются и отслеживаются на сервисе слияний.

<Warning>
  **DDL на уровне баз данных может зависать, если другой сервис находится в состоянии простоя**

  Операторы `CREATE`, `RENAME` и `DROP DATABASE` могут блокироваться остановленными или находящимися в состоянии простоя сервисами хранилища и в результате зависать. В этой топологии с этим легко столкнуться, поскольку сервисы только для чтения переходят в простой без задержки. Выполняйте операторы уровня базы данных с [`distributed_ddl_task_timeout=0`](/ru/reference/settings/session-settings/distributed-ddl#distributed_ddl_task_timeout), задавая эту настройку для отдельного запроса или для всего сеанса:

  ```sql
  CREATE DATABASE otel
  SETTINGS distributed_ddl_task_timeout=0
  ```

  Сервис, остановленный вручную, необходимо снова запустить, прежде чем на нём можно будет выполнять запросы.
</Warning>

Materialized view срабатывают при вставке, поэтому выполняются сервисом чтения и записи. Сервис только для чтения обращается к их целевым таблицам так же, как к любым другим, в том числе к представлениям, [зарегистрированным для источника данных](/ru/clickstack/self-configured/managing/config#materialized-views-settings) для ускорения запросов.

## Изоляция агентных рабочих нагрузок {#agentic-workloads}

ИИ-ассистенты, подключённые через [MCP-сервер](/ru/clickstack/observability/mcp), создают такой же трафик чтения, как и любая панель мониторинга, но характер нагрузки у них другой: агент, расследующий инцидент, отправляет множество исследовательских запросов один за другим, причём по диапазонам, которые никто не выбирал заранее. Если агенты и интерфейс используют один и тот же сервис только для чтения, этот всплеск нагрузки ударит по панелям мониторинга, которые инженер просматривает во время того же инцидента.

Здесь применим тот же подход с хранилищем — выделите агентам собственные вычислительные ресурсы только для чтения:

<Steps>
  <Step title="Добавьте второй сервис только для чтения" id="agentic-add-service">
    Создайте в хранилище ещё один сервис только для чтения — точно так же, как [описано выше](#add-read-only-service). Он читает те же таблицы, что и сервис, обслуживающий интерфейс, поэтому копировать данные не нужно.

    Затем один раз запустите на нём интерфейс обсервабилити из консоли Cloud, как описано в разделе [направление интерфейса обсервабилити на сервис только для чтения](#point-clickstack). Для Cloud MCP требуется сервис, на котором включены и интерфейс обсервабилити, и сам MCP, — см. [предварительные требования MCP](/ru/clickstack/observability/mcp#managed-prerequisites).

    Подбирайте размер сервиса исходя из ожидаемой нагрузки запросов от агентов, а не из QPS панелей мониторинга по модели расчёта ресурсов, и оставьте включённым автоматический переход в режим ожидания: агенты, как правило, используются эпизодически, поэтому между расследованиями сервис может простаивать.
  </Step>

  <Step title="Включите MCP на этом сервисе" id="agentic-enable-mcp">
    Откройте сервис только для чтения в консоли ClickHouse Cloud, нажмите **Connect**, выберите **Connect with MCP** и включите переключатель. См. [включение удалённого сервера MCP](/ru/products/cloud/features/ai-ml/mcp/remote-mcp#enable-remote-mcp-server).
  </Step>

  <Step title="Направьте на него MCP-клиенты" id="agentic-point-clients">
    Облачная конечная точка MCP одинакова для всех сервисов — запросы направляются по заголовку `x-service-id`, а без него попадают в первый сервис обсервабилити, который использовала ваша учётная запись. Скопируйте существующую конфигурацию MCP и добавьте заголовок с ID нового сервиса только для чтения:

    ```shell
    claude mcp add --transport http clickstack https://mcp.clickhouse.cloud/clickstack \
      --header "x-service-id: <read-only-agent-service-id>"
    ```

    Заголовок может передавать любой MCP-клиент — эквивалентную конфигурацию для Cursor, VS Code и других клиентов см. в разделе [указание конкретного сервиса](/ru/clickstack/observability/mcp#managed-service-override).
  </Step>
</Steps>

<Warning>
  **MCP записывает состояние в сервис, на который он направлен**

  MCP-сервер может не только выполнять запросы, но и создавать панели мониторинга, оповещения и сохранённые поиски, и это состояние привязано к сервису, на который был направлен запрос, как и всё [состояние интерфейса обсервабилити](#point-clickstack). Панель мониторинга, созданная агентом на сервисе для агентов, не появится в интерфейсе обсервабилити, запущенном с сервиса, которым пользуются ваши инженеры, а созданное там оповещение вычисляется на вычислительных ресурсах этого сервиса — и если сервис для агентов простаивает, проверки оповещений будут задерживаться или пропускаться, как описано [ниже](#isolating-alerts). Агентов, которые должны создавать долговременные артефакты, направляйте на тот же сервис, которым пользуется ваша команда.
</Warning>

## Оповещения {#alerts}

Оповещение вычисляется на том сервисе, в котором оно было создано, поэтому оповещения выполняются на тех же вычислительных ресурсах, что и интерфейс, — в этой топологии это сервис только для чтения.

<Note>
  **Самостоятельно управляемый ClickHouse Observability**

  Чтобы включить оповещения, хотя бы один пользователь с разрешениями **Администратор сервиса** должен хотя бы раз войти в интерфейс обсервабилити. При этом выделяется и настраивается отдельный пользователь базы данных, от имени которого выполняются запросы оповещений; этот пользователь общий для всех сервисов в хранилище. Подробнее см. в руководстве [Выдача доступа к самостоятельно управляемому ClickHouse Observability](/ru/clickstack/self-configured/deployment/managed#configure-access).
</Note>

Вычисление оповещений — это регулярная рабочая нагрузка из запросов. Учитывайте её в значении QPS, на которое вы рассчитываете ресурсы сервиса только для чтения: [модель расчёта ресурсов](/ru/clickstack/self-configured/managing/estimating-resources#refining-sizing-assumptions) учитывает запросы поиска, панелей мониторинга и оповещений как единый агрегированный показатель.

### Изоляция вычисления оповещений {#isolating-alerts}

Нагрузку от оповещений нельзя централизованно перенаправить, поскольку оповещения создают сами пользователи: тот, кто добавляет оповещение в интерфейсе обсервабилити, добавляет его в сервис, с которым работает, и оно вычисляется на вычислительных ресурсах этого сервиса. Настройки, которая переносила бы оповещения сервиса в другое место, не существует.

Изолировать можно те оповещения, которыми вы управляете централизованно, — их команда платформы поддерживает для всей организации, и, как правило, именно они вычисляются чаще всего. Выделите для них отдельный сервис только для чтения в хранилище и создавайте их из интерфейса обсервабилити, запущенного на этом сервисе:

| Сервис     | Тип                            | Обслуживает                                                                 |
| ---------- | ------------------------------ | --------------------------------------------------------------------------- |
| Приём      | С возможностью чтения и записи | OpenTelemetry Collector                                                     |
| Запросы    | Только для чтения              | Интерфейс обсервабилити и оповещения, которые пользователи создают для себя |
| Оповещения | Только для чтения              | Общие оповещения, поддерживаемые командой платформы                         |

<Warning>
  **Отключите автоматический переход в режим ожидания на сервисе оповещений**

  Настроенные на сервисе оповещения не удерживают его в активном состоянии. Вычисления оповещений, приходящиеся на сервис в состоянии простоя, откладываются до его пробуждения или вовсе завершаются ошибкой, поэтому сервис оповещений с включенным автоматическим переходом в режим ожидания может пропускать вычисления. Отключите на этом сервисе автоматический переход в режим ожидания и исходите из того, что он будет работать постоянно. Это касается любого сервиса, где вычисляются ваши оповещения: если они выполняются на сервисе, обслуживающем интерфейс, этому сервису тоже нельзя позволять переходить в состояние простоя.
</Warning>

Остальные компромиссы следуют из того, что состояние хранится отдельно для каждого сервиса:

* Общие оповещения и связанные с ними панели мониторинга существуют только на сервисе оповещений и не видны пользователям, работающим с сервисом запросов. Уведомления в любом случае доставляются в те же [пункты назначения](/ru/clickstack/observability/features/alerts), поэтому пользователи теряют лишь доступ к определениям, а не сами оповещения.
* Источники на сервисе оповещений — это отдельные объекты. Источники, использующие [схему OpenTelemetry по умолчанию](/ru/clickstack/self-configured/deployment/managed#adding-data-sources), обнаруживаются автоматически, а пользовательские источники нужно дополнительно настроить на этом сервисе, прежде чем на них сможет ссылаться оповещение.

Если набор оповещений настолько мал, что нагрузка от их вычисления ничтожна по сравнению с трафиком панелей мониторинга, держите всё на одном сервисе только для чтения: эксплуатационные затраты на поддержку определений в двух местах окажутся выше.

## Дополнительные соображения {#considerations}

**Автоматический переход в режим ожидания.** Первый запрос к сервису только для чтения, находящемуся в состоянии простоя, ожидает запуска сервиса, поэтому при нерегулярном использовании вы получаете небольшую задержку, но снижаете затраты. Не рассчитывайте, что оповещения помешают переходу в состояние простоя: отключите автоматический переход в режим ожидания для каждого сервиса, на котором они вычисляются, как описано [выше](#isolating-alerts). Непрерывная загрузка данных действительно не даёт сервису чтения и записи перейти в режим ожидания, но если ингестия выполняется нерегулярно или по расписанию, первый пакет после периода простоя будет так же ждать запуска сервиса, и телеметрия будет поступать с задержкой.

**Резервные копии.** Резервные копии создаются только на основном сервисе и охватывают данные всего хранилища. При восстановлении резервной копии создаётся совершенно новый сервис, не подключённый к существующему хранилищу.

**Ограничения числа реплик.** Суммарное количество реплик во всех сервисах хранилища по умолчанию ограничено — см. [ограничения использования](/ru/products/cloud/guides/best-practices/usagelimits).

**Изоляция обсервабилити от других рабочих нагрузок.** Если вы добавляете интерфейс обсервабилити к сервису, который уже обслуживает другие рабочие нагрузки, например аналитику приложений в реальном времени, для выделения обсервабилити собственных вычислительных ресурсов используется та же возможность хранилищ. См. наше руководство [Изоляция рабочих нагрузок обсервабилити](/ru/clickstack/self-configured/managing/estimating-resources#isolating-workloads).

Полное описание поведения и ограничений хранилищ см. в нашем руководстве [Хранилища](/ru/products/cloud/features/infrastructure/warehouses).
