<Note>
  На этой странице рассматривается **самостоятельно управляемый ClickHouse Observability**. Рекомендуемый полностью управляемый вариант описан в [этой документации](/ru/clickstack/observability/managing/config).
</Note>

В этом руководстве описаны настройки источников данных, запускаемого вами коллектора и конфигурация схемы базы данных для самостоятельно управляемого ClickHouse Observability.

## Пользовательский интерфейс {#hyperdx}

### Настройки источника данных {#datasource-settings}

Для работы интерфейса пользователь должен определить источник для каждого из типов данных (столпов) обсервабилити:

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

Чтобы настроить источник, откройте **Team Settings → Data → Sources**. Нажмите **Configure Optional Fields**, чтобы открыть дополнительные настройки, как показано ниже на примере журналов:

<div className="ch-image-md">
  <Frame>
    ![Настройки источника журналов с выделенным пунктом Configure Optional Fields](/images/clickstack/source-settings-optional-fields.png)
  </Frame>
</div>

Для каждого источника необходимо указать таблицу и сопоставления столбцов, с помощью которых интерфейс запрашивает его данные. Источники метрик OTel используют отдельные таблицы для каждого типа метрик; выберите таблицы, содержащие собираемые вами метрики.

При использовании [схемы OpenTelemetry (OTel) по умолчанию](/ru/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema), поставляемой с ClickStack, эти столбцы могут определяться автоматически для каждого из источников. При [изменении схемы](#clickhouse) или использовании собственной схемы пользователям необходимо самостоятельно указывать и обновлять эти сопоставления.

<Note>
  Коллектор ClickStack создаёт таблицы по умолчанию с помощью встроенных миграций схемы. Эти схемы основаны на [экспортере ClickHouse для OTel collector](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) и [модели данных OpenTelemetry](https://opentelemetry.io/docs/specs/otel/logs/data-model/).
</Note>

В следующих таблицах перечислены настройки источников. Автоматически определяемые значения зависят от столбцов и таблиц в вашей базе данных. Необязательные сопоставления включают соответствующие возможности, например корреляцию трассировок; для сохранения источника они не требуются.

#### Materialized view {#materialized-views-settings}

Materialized view можно зарегистрировать для источников данных журналов и трассировок, чтобы подходящие запросы агрегации выполнялись по предварительно агрегированному представлению, а не по исходной таблице. Рекомендации по созданию и регистрации представлений см. в разделе [«Materialized views»](/ru/clickstack/self-configured/managing/materialized-views).

Для каждого зарегистрированного представления задаются следующие настройки:

| Настройка                | Описание                                                                                                                                                                                                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Database`               | База данных ClickHouse, в которой находится целевая таблица materialized view.                                                                                                                                                                                                       |
| `Table`                  | Целевая таблица materialized view (не само представление).                                                                                                                                                                                                                           |
| `Timestamp Column`       | Столбец временной метки целевой таблицы.                                                                                                                                                                                                                                             |
| `Granularity`            | Временной интервал столбца временной метки целевой таблицы, например `1 minute`. Запрос может использовать представление, только если его собственный временной интервал равен этому значению или крупнее его.                                                                       |
| `Minimum Date`           | Необязательно. Самые ранние дата и время, за которые в представлении есть данные. Если значение не указано, ClickStack считает, что представление содержит данные за те же даты, что и исходная таблица.                                                                             |
| `Dimension Columns`      | Список столбцов через запятую, которые представление не агрегирует предварительно и которые поэтому можно использовать для фильтрации и группировки.                                                                                                                                 |
| `Pre-aggregated Columns` | Столбцы, предварительно агрегируемые представлением. Каждая запись сопоставляет агрегатную функцию (`avg`, `count`, `max`, `min`, `quantile`, `sum` или `histogram`) и столбец исходной таблицы с соответствующим столбцом представления. Для `count` исходный столбец не требуется. |

При выборе целевой таблицы интерфейс пытается автоматически определить эти настройки по схеме представления. Проверьте выведенные значения и заполните недостающие поля.

#### Materialized view для метаданных {#metadata-materialized-views-settings}

Materialized view для метаданных — это materialized view, ускоряющие обнаружение полей для фильтров и автодополнения. Их можно настроить для источников данных журналов и трассировок.

| Настройка          | Описание                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------- |
| `Key Rollup Table` | Необязательная, устаревшая. Агрегирующая таблица ключей, присутствующих в исходной таблице. |
| `KV Rollup Table`  | Агрегирующая таблица пар «ключ/значение», присутствующих в исходной таблице.                |
| `Granularity`      | Временной интервал, используемый агрегирующими таблицами, например `15 minute`.             |

#### Выделенные Атрибуты {#highlighted-attributes}

Выделенные Атрибуты и Выделенные Атрибуты Трассировки можно настроить для источников данных журналов и трассировок.

* Выделенные Атрибуты — это столбцы или выражения, которые отображаются для каждого журнала или спана при просмотре его подробностей.
* Выделенные Атрибуты Трассировки — это столбцы или выражения, значения которых запрашиваются из каждого журнала или спана в трассе и отображаются над каскадной диаграммой трассировки.

Эти атрибуты задаются в конфигурации источника и могут быть произвольными SQL-выражениями. Если SQL-выражение возвращает значение в формате URL, атрибут отображается как ссылка. Пустые значения не отображаются.

Для каждого атрибута задаются следующие настройки:

| Настройка           | Описание                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| `SQL Expression`    | Запрашиваемый столбец или произвольное SQL-выражение. Обязательно.                                        |
| `Alias`             | Необязательно. Подпись атрибута, отображаемая вместо SQL-выражения.                                       |
| `Lucene Expression` | Необязательно. Вариант SQL-выражения на языке Lucene, используемый при поиске по значению этого атрибута. |

### Коррелированные источники {#correlated-sources}

Для полной корреляции между источниками необходимо настроить коррелированные источники для журналов, трассировок, метрик и сеансов. Это позволяет интерфейсу сопоставлять связанные данные и показывать подробный контекст при отображении событий.

* `Logs`: можно коррелировать с трассировками и метриками.
* `Traces`: можно коррелировать с журналами, сеансами и метриками.
* `Metrics`: можно коррелировать с журналами.
* `Sessions`: можно коррелировать с трассировками.

Настройка этих корреляций открывает ряд возможностей. Например, интерфейс может отображать соответствующие журналы рядом с трассировкой и переходить между связанными источниками. Кроме того, корреляция зависит от правильных сопоставлений ID и атрибутов: сам по себе выбор источника не создаёт этих связей.

## Коллектор OpenTelemetry {#otel-collector}

Подробнее см. в разделе [«Коллектор ClickStack OpenTelemetry»](/ru/clickstack/self-configured/ingesting-data/collector).

* `CLICKHOUSE_ENDPOINT`
  * **По умолчанию:** *None (обязательный параметр)* для образа автономного коллектора.
  * **Описание:** URL подключения к ClickHouse, используемый экспортером.
  * **Рекомендации:**
    * Используйте защищённую конечную точку ClickHouse Cloud, например `https://<host>:8443` или `tcp://<host>:9440?secure=true`
    * Необходим, чтобы коллектор мог отправлять данные в ClickHouse

* `CLICKHOUSE_USER`
  * **По умолчанию:** `default` в инструменте миграции; для автономного коллектора задаётся явно.
  * **Описание:** Имя пользователя для аутентификации в экземпляре ClickHouse.
  * **Рекомендации:**
    * Пользователю необходимо разрешение на вставку телеметрии, а если включены создание схемы или миграции — также на создание и изменение нужных объектов базы данных
    * Рекомендуется создать отдельного пользователя для ингестии

* `CLICKHOUSE_PASSWORD`
  * **По умолчанию:** *None (обязателен, если включена аутентификация)*
  * **Описание:** Пароль указанного пользователя ClickHouse.
  * **Рекомендации:**
    * Обязателен, если для учётной записи пользователя задан пароль
    * В продакшн-развертываниях храните его в секретах

* `HYPERDX_LOG_LEVEL`
  * **По умолчанию:** зависит от развертывания; задайте явно, например `info`.
  * **Описание:** Уровень детализации журналов коллектора.
  * **Рекомендации:**
    * Допустимые значения: `debug`, `info`, `warn`, `error`
    * При устранении неполадок используйте `debug`

* `OTLP_AUTH_TOKEN`
  * **По умолчанию:** *None*. Используется только в автономном образе.
  * **Описание:** Задаёт токен, необходимый для автономной ингестии по OTLP. Текущая версия коллектора принимает его значение в заголовке `Authorization` как без префикса, так и с префиксом `Bearer`. Более старым версиям коллектора может требоваться токен без префикса. Игнорируется, если настроена аутентификация OIDC.
  * **Рекомендации:**
    * Настройте аутентификацию, прежде чем открывать доступ к коллектору. Если не задан ни токен, ни конфигурация OIDC, автономный приёмник OTLP принимает неаутентифицированные запросы.

* `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`
  * **По умолчанию:** `default` в инструменте миграции; для автономного коллектора задаётся явно.
  * **Описание:** База данных ClickHouse, в которую коллектор записывает телеметрические данные.
  * **Рекомендации:**
    * Задайте, если используется база данных с другим именем
    * Убедитесь, что у указанного пользователя есть доступ к этой базе данных

## ClickHouse {#clickhouse}

Для эффективной настройки ClickHouse необходимо понимать ключевые концепции хранения данных, такие как [части](/ru/concepts/core-concepts/parts), [партиции](/ru/concepts/core-concepts/partitions), [шарды и реплики](/ru/guides/oss/deployment-and-scaling/shards), а также то, как [слияния](/ru/concepts/core-concepts/merges) происходят в момент вставки. Рекомендуем ознакомиться с основами [первичных индексов](/ru/concepts/core-concepts/primary-indexes), [разреженных вторичных индексов](/ru/concepts/features/performance/skip-indexes/skipping-indexes) и индексов пропуска данных, а также с методами [управления жизненным циклом данных](/ru/guides/use-cases/observability/build-your-own/managing-data), например с помощью TTL.

Вы можете [адаптировать схему](/ru/guides/use-cases/observability/build-your-own/schema-design): изменять типы столбцов, извлекать новые поля (например, из журналов), применять кодеки и словари, а также ускорять запросы с помощью проекций.

Кроме того, materialized view можно использовать для [преобразования или фильтрации данных во время ингестии](/ru/guides/use-cases/observability/build-your-own/schema-design#materialized-views) — при условии, что данные записываются в исходную таблицу представления, а приложение читает данные из целевой таблицы. Materialized view также позволяют [ускорять запросы нативными средствами](/ru/clickstack/self-configured/managing/materialized-views) сервиса.

Подробнее см. документацию ClickHouse по проектированию схем, стратегиям индексирования и рекомендуемым практикам управления данными — большая часть этих рекомендаций напрямую применима к самоуправляемым развертываниям.
