## Срок хранения данных с помощью TTL {#ttl-clickstack}

Time-to-Live (TTL) — важнейшая функция самостоятельно управляемого ClickHouse Observability, обеспечивающая эффективное хранение данных и управление ими, особенно с учётом того, что данные генерируются непрерывно и в огромных объёмах. TTL позволяет автоматически помечать устаревшие данные как истёкшие и удалять их, обеспечивая оптимальное использование хранилища и сохранение производительности без ручного вмешательства. Эта возможность необходима, чтобы база данных оставалась компактной, расходы на хранилище снижались, а запросы оставались быстрыми и эффективными благодаря работе с наиболее актуальными и свежими данными. Кроме того, она помогает соблюдать политики хранения данных за счёт систематического управления жизненным циклом данных, повышая тем самым общую устойчивость и масштабируемость решения для обсервабилити.

**По умолчанию данные хранятся 30 дней. Чтобы изменить этот срок, см. раздел [«Изменение TTL»](#modifying-ttl).**

В ClickHouse TTL задаётся на уровне таблицы. Например, ниже показана схема журналов по умолчанию; при создании таблицы коллектором `${TABLES_TTL}` заменяется настроенным сроком хранения (30 дней, если он не изменён):

Партиционирование в ClickHouse позволяет логически разделять данные на диске по столбцу или SQL-выражению. Благодаря такому разделению с каждой партицией можно работать независимо, например удалять её по истечении срока, заданного политикой TTL.

Как показано в примере выше, партиционирование задаётся при первоначальном определении таблицы с помощью секции `PARTITION BY`. Эта секция может содержать SQL-выражение над одним или несколькими столбцами, результат которого определяет, в какую партицию попадёт строка. В результате данные логически привязываются к каждой партиции на диске (через общий префикс имени каталога), и к ним можно обращаться изолированно. В приведённом выше примере схема `otel_logs` по умолчанию партиционирует данные по дням с помощью выражения `toDate(Timestamp)`. При вставке строк в ClickHouse это выражение вычисляется для каждой строки, и строка направляется в соответствующую партицию, если та существует (если строка первая за день, партиция будет создана). Подробнее о партиционировании и других его применениях см. в разделе [«Партиции таблиц»](/ru/concepts/core-concepts/partitions).

Схема таблицы также включает `TTL toDateTime(Timestamp) + ${TABLES_TTL}` и настройку `ttl_only_drop_parts = 1`. Первая секция гарантирует, что данные будут удалены, как только станут старше настроенного TTL (по умолчанию 30 дней). Настройка `ttl_only_drop_parts = 1` предписывает удалять только те части данных, в которых истёк срок действия всех данных (вместо попыток частично удалять строки). Поскольку партиционирование гарантирует, что данные за разные дни никогда не участвуют в одном слиянии, их можно удалять эффективно.

<Warning>
  **`ttl_only_drop_parts`**

  Мы рекомендуем всегда использовать настройку [`ttl_only_drop_parts=1`](/ru/reference/settings/merge-tree-settings/other#ttl_only_drop_parts). Когда эта настройка включена, ClickHouse удаляет часть данных целиком, если у всех строк в ней истёк срок действия. Удаление частей целиком вместо частичной очистки строк с истёкшим TTL (которая выполняется ресурсоёмкими мутациями при `ttl_only_drop_parts=0`) позволяет задавать меньшие значения `merge_with_ttl_timeout` и снижает нагрузку на систему. Если данные партиционированы по той же единице, по которой истекает TTL, например по дням, части естественным образом будут содержать только данные за заданный интервал. Это позволит эффективно применять `ttl_only_drop_parts=1`.
</Warning>

По умолчанию данные с истёкшим TTL удаляются, когда ClickHouse [выполняет слияние частей данных](/ru/reference/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage). Обнаружив данные с истёкшим сроком действия, ClickHouse выполняет внеплановое слияние.

<Info>
  **Расписание TTL**

  Как отмечено выше, TTL применяется не сразу, а по расписанию. Настройка таблицы MergeTree `merge_with_ttl_timeout` задаёт минимальную задержку в секундах перед повторным слиянием с удалением по TTL. Значение по умолчанию — 14400 секунд (4 часа). Но это лишь минимальная задержка: до запуска слияния по TTL может пройти больше времени. Если значение слишком мало, будет выполняться много внеплановых слияний, которые могут потреблять значительные ресурсы. Принудительно применить TTL можно командой `ALTER TABLE my_table MATERIALIZE TTL`.
</Info>

## Изменение TTL {#modifying-ttl}

Изменить TTL можно одним из следующих способов:

1. **Изменить схемы таблиц (рекомендуется)**. Для этого необходимо подключиться к экземпляру ClickHouse, например с помощью [клиента ClickHouse](/ru/concepts/features/interfaces/client) или [Консоли SQL в Cloud](/ru/products/cloud/features/sql-console-features/sql-console). Например, изменить TTL для таблицы `otel_logs` можно с помощью следующего DDL-запроса:

```sql
ALTER TABLE default.otel_logs
MODIFY TTL TimestampTime + toIntervalDay(7);
```

2. **Измените OTel collector**. Коллектор ClickStack OpenTelemetry создаёт таблицы в ClickHouse, если они ещё не существуют. За это отвечает экспортер ClickHouse, у которого есть параметр `ttl`, определяющий TTL-выражение по умолчанию, например:

```yaml
exporters:
 clickhouse:
   endpoint: tcp://localhost:9000?dial_timeout=10s&compress=lz4&async_insert=1
   ttl: 72h
```

### TTL на уровне столбца {#column-level-ttl}

В приведённых выше примерах срок хранения данных задаётся на уровне таблицы. Его также можно задать на уровне столбца. По мере устаревания данных это позволяет удалять столбцы, ценность которых для расследований не оправдывает накладных расходов на их хранение. Например, мы рекомендуем сохранять столбец `Body` на случай, если появятся новые динамические метаданные, не извлечённые в момент вставки, например новая метка Kubernetes. По прошествии определённого периода, например 1 месяца, может выясниться, что эти дополнительные метаданные бесполезны, а значит, и хранить столбец `Body` уже нет особого смысла.

Ниже показано, как удалить столбец `Body` через 30 дней.

```sql
CREATE TABLE otel_logs_v2
(
        `Body` String TTL Timestamp + INTERVAL 30 DAY,
        `Timestamp` DateTime,
 ...
)
ENGINE = MergeTree
ORDER BY (ServiceName, Timestamp)
```

<Note>
  Чтобы задать TTL на уровне столбца, необходимо определить собственную схему. Сделать это в OTel collector нельзя.
</Note>
