При использовании самостоятельно управляемого ClickHouse Observability в продакшн-среде учитывайте следующие рекомендации по безопасности, стабильности и конфигурации.

[Самостоятельно управляемый ClickHouse Observability](/ru/clickstack/self-configured/getting-started/managed) по умолчанию применяет отраслевые стандарты [безопасности](/ru/products/cloud/features/security), включая усиленное шифрование, аутентификацию и защищённое подключение, а также централизованное управление доступом, и предоставляет следующие преимущества:

* Автоматическое масштабирование вычислительных ресурсов независимо от хранилища
* Недорогое и практически неограниченное хранение данных на базе объектного хранилища
* Возможность [изолировать рабочие нагрузки чтения и записи друг от друга](/ru/clickstack/self-configured/managing/isolating-read-write) с помощью хранилищ (Warehouses).
* Встроенная аутентификация
* Автоматическое [резервное копирование](/ru/products/cloud/features/backups/overview)
* Бесшовные обновления

**При использовании самостоятельно управляемого ClickHouse Observability следуйте [рекомендуемым практикам](/ru/products/cloud/guides/production-readiness) для ClickHouse Cloud.**

## Защита ингестии {#secure-ingestion-managed}

По умолчанию коллектор ClickStack OpenTelemetry, развёрнутый вне дистрибутивов с открытым исходным кодом, не защищён и не требует аутентификации на своих портах OTLP.

Чтобы защитить ингестию, при развёртывании коллектора укажите токен аутентификации в переменной окружения `OTLP_AUTH_TOKEN`. Подробнее см. в разделе [«Защита коллектора»](/ru/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).

### Создание пользователя для ингестии {#create-a-database-ingestion-user-managed}

Рекомендуется создать для OTel collector отдельного пользователя, который будет выполнять ингестию в ClickHouse Cloud и гарантировать, что данные поступают в определённую базу данных, например `otel`. Подробнее см. в разделе [«Создание пользователя для ингестии»](/ru/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured).

## Настройка времени жизни (TTL) {#configure-ttl-managed}

Убедитесь, что [время жизни (TTL)](/ru/clickstack/self-configured/managing/ttl) [правильно настроено](/ru/clickstack/self-configured/managing/ttl#modifying-ttl) для вашего развертывания Самостоятельно управляемого ClickHouse Observability. Этот параметр определяет срок хранения данных: значение по умолчанию (30 дней), возможно, потребуется изменить.

### Изоляция рабочих нагрузок обсервабилити {#isolating-workloads}

Если вы добавляете Самостоятельно управляемый ClickHouse Observability к **существующему сервису ClickHouse Cloud**, который уже обслуживает другие рабочие нагрузки, например аналитику приложений в реальном времени, настоятельно рекомендуется изолировать трафик обсервабилити.

С помощью [**Managed Warehouses**](/ru/products/cloud/features/infrastructure/warehouses) создайте **дочерний сервис**, предназначенный специально для обсервабилити. Это позволяет:

* Изолировать нагрузку от приёма данных и выполнения запросов от существующих приложений
* Масштабировать рабочие нагрузки обсервабилити независимо от остальных
* Исключить влияние запросов обсервабилити на аналитику в продакшн-среде
* При необходимости совместно использовать одни и те же базовые наборы данных в нескольких сервисах

Такой подход гарантирует, что существующие рабочие нагрузки останутся незатронутыми, а рабочие нагрузки обсервабилити смогут масштабироваться независимо по мере роста объёма данных обсервабилити.

### Изоляция рабочих нагрузок чтения и записи {#isolating-read-write}

Хранилища также позволяют вынести рабочие нагрузки приёма данных и выполнения запросов на отдельные вычислительные ресурсы: ингестия направляется в сервис чтения и записи, а интерфейс обсервабилити работает на сервисе только для чтения. Именно такая топология рекомендуется для продакшна в крупных развертываниях. См. [«Изоляция рабочих нагрузок чтения и записи»](/ru/clickstack/self-configured/managing/isolating-read-write).

Для получения более точной оценки в случае крупных развертываний или рекомендаций по индивидуальному сайзингу обратитесь в службу поддержки.

## Разрешения пользователя для запросов {#user-permissions}

Пользователь ClickHouse, от имени которого внешний клиент выполняет запросы, должен иметь `readonly = 2`. Интерфейс в каждом запросе задаёт собственные настройки, например `date_time_output_format`, а чарты на основе Raw SQL также устанавливают `readonly = 2`, поэтому у пользователя с `readonly = 1` такие запросы завершаются ошибкой `Cannot modify '...' setting in readonly mode`. При `readonly = 2` интерфейс также может задавать `max_rows_to_read`, `read_overflow_mode` и `cancel_http_readonly_queries_on_client_close`; если вы ограничиваете `max_rows_to_read`, установите значение не менее 1 миллиона. `wait_end_of_query` — это параметр HTTP-интерфейса, а не настройка, поэтому grant для него не требуется.

Например:

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

По умолчанию пользователь `default` в ClickHouse Cloud уже обладает этими разрешениями, однако мы рекомендуем создать для этого отдельного пользователя.
