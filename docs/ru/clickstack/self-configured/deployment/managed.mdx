<Note>
  На этой странице описывается **самостоятельно управляемый ClickHouse Observability**. Рекомендуемый полностью управляемый вариант описан в [этой документации](/ru/clickstack/observability/getting-started).

Это **руководство предназначено для тех, кто уже пользуется ClickHouse Cloud**. Если вы впервые работаете с ClickHouse Cloud, рекомендуем руководство [Начало работы](/ru/clickstack/self-configured/getting-started/managed) по самостоятельно управляемому ClickHouse Observability.

В этой схеме развёртывания и ClickHouse, и интерфейс ClickStack размещаются в ClickHouse Cloud, что сводит к минимуму число компонентов, которые пользователю нужно размещать самостоятельно.

Помимо упрощения управления инфраструктурой, эта схема развёртывания обеспечивает интеграцию аутентификации с SSO/SAML ClickHouse Cloud. Кроме того, в отличие от самоуправляемых развёртываний, здесь не нужно подготавливать и настраивать инстанс MongoDB для хранения состояния приложения — панелей мониторинга, сохранённых поисков, настроек пользователя и оповещений. Пользователи также получают:

* Автоматическое масштабирование вычислительных ресурсов независимо от хранилища
* Недорогое и практически неограниченное хранение данных на базе объектного хранилища
* Возможность [независимо изолировать рабочие нагрузки чтения и записи](/ru/clickstack/self-configured/managing/isolating-read-write) с помощью хранилищ.
* Встроенную аутентификацию
* Автоматическое резервное копирование
* Функции безопасности и обеспечения соответствия требованиям
* Обновления без простоев

В этом режиме ингестия данных полностью ложится на пользователя. Загружать данные в самостоятельно управляемый ClickHouse Observability можно с помощью собственного коллектора OpenTelemetry, прямой ингестии из клиентских библиотек, нативных движков таблиц ClickHouse (например, Kafka или S3), ETL-конвейеров или ClickPipes — управляемого сервиса ингестии ClickHouse Cloud. Это самый простой и производительный способ эксплуатации ClickStack.

### Когда подходит {#suitable-for}

Эта схема развёртывания идеально подходит для следующих сценариев:

1. У вас уже есть данные обсервабилити в ClickHouse Cloud, и вы хотите визуализировать их с помощью ClickStack.
2. Вы эксплуатируете крупное развёртывание обсервабилити, и вам нужны выделенная производительность и масштабируемость ClickStack на базе ClickHouse Cloud.
3. Вы уже используете ClickHouse Cloud для аналитики и хотите инструментировать своё приложение с помощью библиотек инструментирования ClickStack, отправляя данные в тот же кластер. В этом случае рекомендуем использовать [хранилища](/ru/products/cloud/features/infrastructure/warehouses), чтобы изолировать вычислительные ресурсы для рабочих нагрузок обсервабилити.

### Создание базы данных и таблицы {#create-database-and-tables}

            Для Vector таблица и схема должны быть определены до начала ингестии данных.

            Сначала создайте базу данных. Это можно сделать в [консоли ClickHouse Cloud](/ru/products/cloud/features/sql-console-features/sql-console).

            Например, создайте базу данных для журналов:

            ```sql
            CREATE DATABASE IF NOT EXISTS logs
            ```

            Затем создайте таблицу, схема которой соответствует структуре ваших логов. В примере ниже используется классический формат журнала доступа Nginx:

            ```sql
            CREATE TABLE logs.nginx_logs
            (
                `time_local` DateTime,
                `remote_addr` IPv4,
                `remote_user` LowCardinality(String),
                `request` String,
                `status` UInt16,
                `body_bytes_sent` UInt64,
                `http_referer` String,
                `http_user_agent` String,
                `http_x_forwarded_for` LowCardinality(String),
                `request_time` Float32,
                `upstream_response_time` Float32,
                `http_host` String
            )
            ENGINE = MergeTree
            ORDER BY (toStartOfMinute(time_local), status, remote_addr);
            ```

            Таблица должна соответствовать выходной схеме, которую формирует Vector. При необходимости адаптируйте схему под свои данные, следуя [рекомендуемым практикам проектирования схем](/ru/concepts/best-practices/select-data-type).

            Настоятельно рекомендуем разобраться, как в ClickHouse работают [первичные ключи](/ru/concepts/core-concepts/primary-indexes), и выбрать ключ сортировки с учётом ваших шаблонов доступа. См. также [рекомендации для ClickStack](/ru/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key) по выбору первичного ключа.

            После создания таблицы скопируйте приведённый фрагмент конфигурации. Настройте источник (input) так, чтобы он читал и обрабатывал данные из ваших существующих конвейеров, а при необходимости также укажите нужные целевую таблицу и базу данных. Учётные данные уже должны быть подставлены.

   * **Service Admin → Full Access** — требуется для включения оповещений
   * **Service Read Only → Read Only** — может просматривать данные обсервабилити и создавать панели мониторинга
   * **No access** — нет доступа к интерфейсу ClickStack

  </Frame>
</div>

  Чтобы включить оповещения, хотя бы один пользователь с разрешениями **Service Admin** (им соответствует **Full Access** в раскрывающемся списке SQL Console Access) должен хотя бы раз войти в интерфейс ClickStack. ### Использование ClickStack с вычислительными ресурсами только для чтения {#clickstack-read-only-compute}

Интерфейс ClickStack может полностью работать на сервисе ClickHouse Cloud в режиме только для чтения. Такая конфигурация рекомендуется, если нужно изолировать рабочие нагрузки ингестии от рабочих нагрузок запросов.

#### Как ClickStack выбирает вычислительные ресурсы {#how-clickstack-selects-compute}

Интерфейс ClickStack всегда подключается к тому сервису ClickHouse, из которого он был запущен в консоли ClickHouse Cloud.

Это означает следующее:

* Если открыть ClickStack из сервиса только для чтения, все запросы интерфейса ClickStack будут выполняться на этих вычислительных ресурсах только для чтения.
* Если открыть ClickStack из сервиса чтения и записи, ClickStack будет использовать вычислительные ресурсы этого сервиса.

Дополнительная настройка ClickStack для работы в режиме только для чтения не требуется.

#### Рекомендуемая настройка {#recommended-setup}

Чтобы запустить ClickStack на вычислительных ресурсах только для чтения:

1. Создайте или выберите в хранилище сервис ClickHouse Cloud, работающий в режиме только для чтения.
2. В консоли ClickHouse Cloud выберите этот сервис только для чтения.
3. Запустите ClickStack из левой панели навигации.

После запуска интерфейс ClickStack автоматически привяжется к этому сервису только для чтения.

Обратите внимание: панели мониторинга, сохранённые поиски, оповещения и источники привязаны к сервису, из которого был запущен ClickStack. Поэтому всё, что сохранено в другом сервисе хранилища, здесь недоступно, и это придётся создать заново. Источники, использующие стандартную схему OpenTelemetry, определяются автоматически, так что поиск по этим данным работает сразу. Пользовательские или настроенные вручную источники автоматически не определяются, и их нужно настроить повторно.

Подробное описание топологии, в том числе куда направлять ингестию, на каком сервисе выполнять DDL и как работают оповещения, см. в разделе [«Разделение рабочих нагрузок чтения и записи»](/ru/clickstack/self-configured/managing/isolating-read-write).

ClickStack автоматически обнаруживает таблицы со стандартной схемой OpenTelemetry и создаёт для них соответствующие источники данных для журналов, трассировок и метрик. Подтверждать что-либо в диалоговом окне или создавать источники вручную не требуется.

Чтобы просмотреть или изменить автоматически созданный источник, откройте **Team Settings → Data → Sources** и разверните нужный источник. В примере ниже показан источник логов для таблицы `otel_logs`.

## Выбор схемы: Map или JSON {#schema-choice-map-vs-json}

По умолчанию ClickStack хранит атрибуты в столбцах типа `Map(LowCardinality(String), String)`. Это рекомендуемая схема для рабочих нагрузок обсервабилити. В сочетании с [сериализацией Map по бакетам](/ru/reference/data-types/map#bucketed-map-serialization) и текстовыми индексами по ключам и значениям Map она обеспечивает избирательный поиск без накладных расходов при приёме данных, которые возникают из-за создания отдельного динамического подстолбца JSON для каждого ключа.

Схема на основе типа `JSON` доступна в статусе бета для оценки на рабочих нагрузках с небольшим и стабильным набором ключей атрибутов. Использовать её по умолчанию **не рекомендуется**. Подробное сравнение и переменные окружения, необходимые для включения поддержки JSON, приведены в разделе [Map или тип JSON](/ru/clickstack/self-configured/ingesting-data/schema/map-vs-json).
