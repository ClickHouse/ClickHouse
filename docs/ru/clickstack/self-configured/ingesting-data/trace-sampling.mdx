  На этой странице рассматривается **самостоятельно управляемый ClickHouse Observability**. О рекомендуемом полностью управляемом варианте см. [документацию](/ru/clickstack/observability/overview).
</Note>

Сервисы с высокой пропускной способностью могут генерировать миллионы спанов в секунду. Хранить каждый спан дорого, поэтому обычно используют [процессор tail-sampling](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/tailsamplingprocessor) из OpenTelemetry Collector, который сохраняет только 1 из N спанов. Каждый сохранённый спан содержит атрибут `SampleRate` со значением N.

После сэмплирования обычные агрегации дают неверные результаты: `count()` возвращает в N раз меньше событий, чем произошло на самом деле, `sum()` и `avg()` дают смещённые оценки, а процентили искажаются. В результате панели мониторинга показывают заниженные значения числа запросов, пропускной способности и доли ошибок.

Самостоятельно управляемый ClickHouse Observability решает эту проблему с помощью движка запросов, учитывающего сэмплирование. Если для источника трасс настроено выражение коэффициента выборки, конструктор запросов переписывает SQL-агрегации так, чтобы вклад каждого спана взвешивался по его коэффициенту выборки. Это работает на панелях мониторинга, в оповещениях и при ad-hoc поиске.

## Как это работает {#how-it-works}

Если для источника трасс настроен параметр `sampleRateExpression`, конструктор запросов оборачивает его следующим образом:

```sql
greatest(toUInt64OrZero(toString(expr)), 1)
```

Спаны без атрибута `SampleRate` по умолчанию получают вес 1, поэтому для данных без сэмплирования результаты совпадают с результатами исходных запросов.

Затем конструктор запросов переписывает агрегации:

| Агрегация          | До                 | После (с поправкой на выборку)            |
| ------------------ | ------------------ | ----------------------------------------- |
| count              | `count()`          | `sum(weight)`                             |
| count + условие    | `countIf(cond)`    | `sumIf(weight, cond)`                     |
| avg                | `avg(col)`         | `sum(col * weight) / sum(weight)`         |
| sum                | `sum(col)`         | `sum(col * weight)`                       |
| quantile(p)        | `quantile(p)(col)` | `quantileTDigestWeighted(p)(col, weight)` |
| min / max          | без изменений      | без изменений                             |
| count&#95;distinct | без изменений      | без изменений                             |

<Note>
  При сэмплировании процентили вычисляются с помощью `quantileTDigestWeighted` — приблизительного скетча T-Digest. Результаты близки к точным, но не совпадают с ними в точности.
</Note>

## Настройка выражения коэффициента выборки {#configuring}

Откройте источник трасс в **Source Settings** и укажите в поле **Выражение коэффициента выборки** выражение ClickHouse, которое вычисляет коэффициент выборки для каждого спана.

Например, если процессор tail-sampling OpenTelemetry записывает коэффициент в `SpanAttributes['SampleRate']`:

После настройки все диаграммы, панели мониторинга, оповещения и панели на панелях мониторинга сервисов автоматически используют агрегации с учётом весов выборки. Изменять отдельные запросы не нужно.
