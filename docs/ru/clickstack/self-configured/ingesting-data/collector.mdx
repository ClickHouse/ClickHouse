## Роли коллектора {#collector-roles-self-configured}

Коллекторы OpenTelemetry можно развернуть в одной из двух основных ролей:

* **Агент** — инстансы агента собирают данные на периферии, например на серверах или узлах Kubernetes, либо получают события непосредственно от приложений, инструментированных с помощью OpenTelemetry SDK. Во втором случае инстанс агента работает вместе с приложением или на том же хосте, что и приложение (например, в виде sidecar или ДемонСета). Агенты могут отправлять данные либо напрямую в ClickHouse, либо в инстанс шлюза. Первый вариант называется [схемой развёртывания «Агент»](https://opentelemetry.io/docs/collector/deployment/agent/).

* **Шлюз** — инстансы шлюза работают как независимый сервис (например, Развертывание в Kubernetes), как правило, по одному на кластер, центр обработки данных или регион. Они получают события от приложений (или от других коллекторов, выступающих в роли агентов) через единую конечную точку OTLP. Обычно развертывается группа инстансов шлюза, а нагрузка между ними распределяется готовым load balancer. Если все агенты и приложения отправляют свои сигналы в эту единую конечную точку, такую конфигурацию часто называют [схемой развёртывания «Шлюз»](https://opentelemetry.io/docs/collector/deployment/gateway/).

**Важно: коллектор, в том числе в стандартных дистрибутивах ClickStack, выполняет [роль шлюза, описанную ниже](#collector-roles-self-configured), и получает данные от агентов или SDK.**

Пользователи, развертывающие OTel collector в роли агента, как правило, используют [стандартный contrib-дистрибутив коллектора](https://github.com/open-telemetry/opentelemetry-collector-contrib), а не версию ClickStack, но при желании могут применять и другие технологии с поддержкой OTLP, например [Fluentd](https://www.fluentd.org/) и [Vector](https://vector.dev/).

## Развертывание коллектора {#configuring-the-collector-self-configured}

<br />

По возможности рекомендуем использовать официальный дистрибутив коллектора ClickStack в роли шлюза при отправке данных в Самостоятельно управляемый ClickHouse Observability. Если вы решите использовать собственный коллектор, убедитесь, что в него входит [экспортер ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

Коллектор можно развернуть с помощью Helm (рекомендуется для Kubernetes) или Docker. Официальный [Helm-чарт ClickStack](https://github.com/ClickHouse/ClickStack-helm-charts) включает вышестоящий [Helm-чарт OpenTelemetry Collector](https://github.com/open-telemetry/opentelemetry-helm-charts) в качестве субчарта с предварительно настроенным образом дистрибутива ClickStack. Для автономного развертывания коллектора вышестоящий чарт можно использовать напрямую с образом ClickStack, как показано ниже.

<Tabs>
  <Tab title="Helm">
    Добавьте вышестоящий Helm-репозиторий OpenTelemetry:

    ```shell
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update
    ```

    Создайте файл `values.yaml` с настройками образа ClickStack и учётных данных Самостоятельно управляемого ClickHouse Observability:

    ```yaml
    # values.yaml
    mode: deployment

    image:
      repository: docker.clickhouse.com/clickhouse/clickstack-otel-collector
      tag: "2.19.0"

    ports:
      otlp:
        enabled: true
      otlp-http:
        enabled: true

    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "https://your-instance.clickhouse.cloud:8443"
      - name: CLICKHOUSE_USER
        value: "default"
      - name: CLICKHOUSE_PASSWORD
        value: "<password>"
    ```

    Установите чарт:

    ```shell
    helm install clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    В продакшн-развертываниях рекомендуем хранить `CLICKHOUSE_PASSWORD` в секрете Kubernetes и ссылаться на него через `extraEnvsFrom`, а не указывать значение напрямую.
  </Tab>

  <Tab title="Docker">
    Чтобы развернуть дистрибутив коннектора OTel от ClickStack в автономном режиме, выполните следующую команду docker:

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```

    <Info>
      **Изменение имени образа**

      Образы ClickStack теперь публикуются под именем `clickhouse/clickstack-*` (ранее `docker.hyperdx.io/hyperdx/*`).
    </Info>
  </Tab>
</Tabs>

Целевой экземпляр ClickHouse задаётся переменными окружения `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER` и `CLICKHOUSE_PASSWORD`. В `CLICKHOUSE_ENDPOINT` нужно указать полную HTTP-конечную точку ClickHouse Cloud, включая протокол и порт, например `https://99rr6dm6v3.us-central1.gcp.clickhouse.cloud:8443`.

Подробнее о том, как получить учётные данные Самостоятельно управляемого ClickHouse Observability, см. [здесь](/ru/products/cloud/guides/sql-console/connection-details).

<Info>
  **Пользователь для продакшна**

  В продакшне следует использовать пользователя с [соответствующими учётными данными](/ru/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured).
</Info>

### Изменение конфигурации {#modifying-otel-collector-configuration-managed-self-configured}

#### Настройка инстанса Самостоятельно управляемого ClickHouse Observability {#configuring-managed-clickstack-self-configured}

OpenTelemetry Collector можно настроить на работу с инстансом Самостоятельно управляемого ClickHouse Observability с помощью переменных окружения `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER` и `CLICKHOUSE_PASSWORD`. Способ их задания зависит от метода развертывания:

<Tabs>
  <Tab title="Helm">
    Переопределите соответствующие записи в разделе `extraEnvs` файла `values.yaml`, затем обновите релиз:

    ```yaml
    # values.yaml
    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```
  </Tab>

  <Tab title="Docker">
    Автономный образ OpenTelemetry Collector настраивается с помощью переменных окружения:

    ```shell
    export CLICKHOUSE_ENDPOINT=<HTTPS ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    ```

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

<ExtendingConfig />

#### Docker Compose {#docker-compose-otel-managed-self-configured}

При использовании Docker Compose измените конфигурацию коллектора с помощью тех же переменных окружения, что и выше:

```yaml
  otel-collector:
    image: clickhouse/clickstack-otel-collector
    environment:
      CLICKHOUSE_ENDPOINT: 'https://mxl4k3ul6a.us-east-2.aws.clickhouse-staging.com:8443'
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      CLICKHOUSE_USER: 'default'
      CLICKHOUSE_PASSWORD: 'password'
      CUSTOM_OTELCOL_CONFIG_FILE: '/etc/otelcol-contrib/custom.config.yaml'
    ports:
      - '13133:13133' # health_check extension
      - '24225:24225' # fluentd receiver
      - '4317:4317' # OTLP gRPC receiver
      - '4318:4318' # OTLP http receiver
      - '8888:8888' # metrics extension
    volumes:
      - ./custom-config.yaml:/etc/otelcol-contrib/custom.config.yaml:ro
    restart: always
    networks:
      - internal
```

## Защита коллектора {#securing-the-collector-self-configured}

По умолчанию коллектор ClickStack OpenTelemetry, развернутый вне дистрибутивов с открытым исходным кодом, не защищён и не требует аутентификации на своих портах OTLP.

Чтобы защитить ингестию, при развертывании коллектора укажите токен аутентификации в переменной окружения `OTLP_AUTH_TOKEN`. Способ её задания зависит от метода развертывания:

<Tabs>
  <Tab title="Helm">
    Добавьте `OTLP_AUTH_TOKEN` в `extraEnvs` в файле `values.yaml`, затем обновите релиз:

    ```yaml
    # values.yaml
    extraEnvs:
      - name: OTLP_AUTH_TOKEN
        value: "a_very_secure_string"
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    В продакшн-развертываниях рекомендуется хранить `OTLP_AUTH_TOKEN` и `CLICKHOUSE_PASSWORD` в секрете Kubernetes и ссылаться на них через `extraEnvsFrom`.
  </Tab>

  <Tab title="Docker">
    ```sh
    export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    export OTLP_AUTH_TOKEN="a_very_secure_string"

    docker run \
      -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
      -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
      -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
      -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
      -p 4317:4317 \
      -p 4318:4318 \
      clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

Также рекомендуется:

* Настроить подключение коллектора к ClickHouse по HTTPS.
* Создать отдельного пользователя для ингестии с ограниченными разрешениями — см. ниже.
* Включить TLS для конечной точки OTLP, чтобы трафик между SDK/агентами и коллектором шифровался. Это можно настроить с помощью [пользовательской конфигурации коллектора](#extending-collector-config).

### Создание пользователя для ингестии {#creating-an-ingestion-user-self-configured}

Для ингестии в Самостоятельно управляемый ClickHouse Observability рекомендуем создать для OTel collector отдельную базу данных и отдельного пользователя. У этого пользователя должны быть права на создание [таблиц, используемых коллектором](/ru/clickstack/self-configured/ingesting-data/schemas), и на вставку данных в них.

```sql
CREATE DATABASE otel;
CREATE USER hyperdx_ingest IDENTIFIED WITH sha256_password BY 'ClickH0u3eRocks123!';
GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO hyperdx_ingest;
```

Предполагается, что коллектор настроен на использование базы данных `otel`. Это задаётся переменной окружения `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`. Передайте её коллектору [так же, как и другие переменные окружения](#modifying-otel-collector-configuration-managed-self-configured).

## Обработка — фильтрация, преобразование и обогащение {#processing-filtering-transforming-enriching-self-configured}

Пользователям неизбежно потребуется фильтровать, преобразовывать и обогащать сообщения о событиях в ходе ингестии. Пользователи могут добавлять процессоры и конвейеры в коллектор ClickStack с помощью [пользовательской конфигурации](#extending-collector-config). Чтобы выполнять такую обработку вне коллектора ClickStack, мы рекомендуем один из следующих вариантов:

* Развернуть собственный экземпляр OTel collector, который выполняет фильтрацию и обработку и отправляет события в коллектор ClickStack по OTLP для ингестии в ClickHouse.
* Развернуть собственный экземпляр OTel collector и отправлять события напрямую в ClickHouse с помощью экспортера ClickHouse.

Если обработка выполняется с помощью OTel collector, мы рекомендуем выполнять преобразования на инстансах-шлюзах и свести к минимуму работу на инстансах-агентах. Так ресурсы, необходимые агентам на периферии (на серверах), будут минимальными. Как правило, в агентах пользователи выполняют только фильтрацию (чтобы сократить лишний сетевой трафик), установку временной метки (с помощью операторов) и обогащение, требующее контекста. Например, если инстансы-шлюзы находятся в другом кластере Kubernetes, обогащение данными k8s должно выполняться в агенте.

OpenTelemetry предоставляет следующие возможности обработки и фильтрации:

* **Процессоры** — процессоры получают данные, собранные [приёмниками, и изменяют или преобразуют](https://opentelemetry.io/docs/collector/transforming-telemetry/) их перед отправкой в экспортеры. Процессоры применяются в порядке, заданном в секции `processors` конфигурации коллектора. Они необязательны, но минимальный набор [обычно рекомендуется](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor#recommended-processors). При использовании OTel collector с ClickHouse мы рекомендуем ограничиться следующими процессорами:

* [memory&#95;limiter](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/memorylimiterprocessor/README.md) — предотвращает нехватку памяти в коллекторе. Рекомендации см. в разделе [Оценка ресурсов](#estimating-resources-self-configured).

* Любой процессор, выполняющий обогащение на основе контекста. Например, [Kubernetes Attributes Processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/k8sattributesprocessor) позволяет автоматически задавать атрибуты ресурса для спанов, метрик и журналов на основе метаданных k8s — например, обогащать события идентификатором исходного пода.

* [Tail- или head-сэмплирование](https://opentelemetry.io/docs/concepts/sampling/), если оно требуется для трейсов.

* [Базовая фильтрация](https://opentelemetry.io/docs/collector/transforming-telemetry/) — отбрасывание ненужных событий, если это невозможно сделать с помощью оператора (см. ниже).

* [Пакетирование](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor/batchprocessor) — необходимо при работе с ClickHouse, чтобы данные отправлялись пакетами. См. раздел [«Оптимизация вставок»](#optimizing-inserts-self-configured).

* **Операторы** — [операторы](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/pkg/stanza/docs/operators/README.md) представляют собой самую базовую единицу обработки, доступную в приёмнике. Поддерживается базовый разбор, позволяющий задавать такие поля, как Severity и временная метка. Здесь также поддерживаются разбор JSON и регулярных выражений, фильтрация событий и базовые преобразования. Фильтрацию событий мы рекомендуем выполнять именно здесь.

Мы рекомендуем избегать избыточной обработки событий с помощью операторов или [transform processors](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/transformprocessor/README.md). Они могут создавать значительную нагрузку на память и CPU, особенно при разборе JSON.  Всю обработку можно выполнять в ClickHouse во время вставки с помощью материализованных представлений и столбцов — за некоторыми исключениями, а именно обогащения с учётом контекста, например добавления метаданных k8s. Подробнее см. в разделе [Извлечение структуры с помощью SQL](/ru/guides/use-cases/observability/build-your-own/schema-design#extracting-structure-with-sql).

### Пример {#example-processing-self-configured}

Следующая конфигурация демонстрирует сбор данных из этого [неструктурированного файла журнала](https://datasets-documentation.s3.eu-west-3.amazonaws.com/http_logs/access-unstructured.log.gz). Такую конфигурацию может использовать коллектор в роли агента, отправляющий данные в шлюз ClickStack.

Обратите внимание, что здесь используются операторы для извлечения структуры из строк журнала (`regex_parser`) и фильтрации событий, а также процессор для объединения событий в пакеты и ограничения использования памяти.

```yaml file=code_snippets/ClickStack/config-unstructured-logs-with-processor.yaml
receivers:
  filelog:
    include:
      - /opt/data/logs/access-unstructured.log
    start_at: beginning
    operators:
      - type: regex_parser
        regex: '^(?P<ip>[\d.]+)\s+-\s+-\s+\[(?P<timestamp>[^\]]+)\]\s+"(?P<method>[A-Z]+)\s+(?P<url>[^\s]+)\s+HTTP/[^\s]+"\s+(?P<status>\d+)\s+(?P<size>\d+)\s+"(?P<referrer>[^"]*)"\s+"(?P<user_agent>[^"]*)"'
        timestamp:
          parse_from: attributes.timestamp
          layout: '%d/%b/%Y:%H:%M:%S %z'
          #22/Jan/2019:03:56:14 +0330
processors:
  batch:
    timeout: 1s
    send_batch_size: 10000
  memory_limiter:
    check_interval: 1s
    limit_mib: 2048
    spike_limit_mib: 256
exporters:
  # HTTP setup
  otlphttp/hdx:
    endpoint: 'http://localhost:4318'
    headers:
      authorization: <YOUR_INGESTION_API_KEY>
    compression: gzip

  # gRPC setup (alternative)
  otlp/hdx:
    endpoint: 'localhost:4317'
    headers:
      authorization: <YOUR_API_INGESTION_KEY>
    compression: gzip
service:
  telemetry:
    metrics:
      address: 0.0.0.0:9888 # Modified as 2 collectors running on same host
  pipelines:
    logs:
      receivers: [filelog]
      processors: [batch]
      exporters: [otlphttp/hdx]

```

Если вы настроили `OTLP_AUTH_TOKEN`, используйте этот токен как значение заголовка авторизации в приведённом выше примере. Подробнее см. в разделе [Защита коллектора](#securing-the-collector-self-configured).

Для более продвинутой настройки рекомендуем обратиться к [документации по OpenTelemetry Collector](https://opentelemetry.io/docs/collector/).

## Оптимизация вставок {#optimizing-inserts-self-configured}

Чтобы добиться высокой производительности вставки и при этом обеспечить строгие гарантии согласованности, при вставке данных обсервабилити в ClickHouse через коллектор ClickStack следует придерживаться нескольких простых правил. При правильной конфигурации OTel collector соблюдать приведённые ниже правила несложно. Кроме того, это помогает избежать [типичных проблем](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse), с которыми пользователи сталкиваются при первом знакомстве с ClickHouse.

### Пакетирование {#batching-self-configured}

По умолчанию каждая вставка, отправленная в ClickHouse, заставляет ClickHouse немедленно создать в хранилище часть данных, содержащую данные этой вставки вместе с другими метаданными, которые необходимо сохранить. Поэтому если отправлять меньше вставок, но с бо́льшим объёмом данных в каждой, а не много вставок с небольшим объёмом данных, число необходимых операций записи сократится. Мы рекомендуем вставлять данные достаточно крупными пакетами — не менее 1,000 строк за раз. Подробнее — [здесь](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance).

По умолчанию вставки в ClickHouse синхронны и идемпотентны, если они идентичны. Для таблиц семейства движков MergeTree ClickHouse по умолчанию автоматически [выполняет дедупликацию вставок](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#5-deduplication-at-insert-time). Благодаря этому вставки устойчивы, например, в следующих случаях:

* (1) Если у узла, получающего данные, возникли проблемы, запрос на вставку завершится по тайм-ауту (или с более конкретной ошибкой) и не получит подтверждения.
* (2) Если узел записал данные, но подтверждение не удалось вернуть отправителю запроса из-за сбоев сети, отправитель получит либо тайм-аут, либо сетевую ошибку.

С точки зрения коллектора случаи (1) и (2) бывает трудно различить. Однако в обоих случаях неподтверждённую вставку можно просто сразу повторить. Если повторный запрос на вставку содержит те же данные в том же порядке, а исходная (неподтверждённая) вставка на самом деле прошла успешно, ClickHouse автоматически проигнорирует повторную вставку.

Поэтому дистрибутив OTel collector от ClickStack использует [пакетный процессор](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/batchprocessor/README.md). Он гарантирует, что вставки отправляются согласованными пакетами строк, удовлетворяющими описанным выше требованиям. Если ожидается, что коллектор будет работать с высокой пропускной способностью (в событиях в секунду) и в каждой вставке можно отправлять не менее 10,000 событий, то обычно другое пакетирование в конвейере не требуется. Если позволяет память, можно использовать значения до 100,000. В этом случае коллектор будет сбрасывать пакеты до истечения `timeout` пакетного процессора, что обеспечивает низкую сквозную задержку конвейера и стабильный размер пакетов.

### Используйте асинхронные вставки {#use-asynchronous-inserts-self-configured}

Как правило, при низкой пропускной способности коллектора пользователям приходится отправлять пакеты меньшего размера, но при этом они всё равно ожидают, что данные будут поступать в ClickHouse с минимальной сквозной задержкой. В этом случае небольшие пакеты отправляются по истечении `timeout` пакетного процессора. Это может вызывать проблемы, и именно в таких ситуациях необходимы асинхронные вставки. Если данные отправляются в коллектор ClickStack, работающий в роли шлюза (Gateway), такая проблема возникает редко: выступая агрегаторами, такие коллекторы её смягчают — см. [Роли коллектора](#collector-roles-self-configured).

Если гарантировать крупные пакеты невозможно, формирование пакетов можно делегировать ClickHouse с помощью [асинхронных вставок](/ru/concepts/best-practices/selecting-an-insert-strategy#asynchronous-inserts). При асинхронных вставках данные сначала помещаются в буфер, а затем записываются в хранилище базы данных позднее, то есть асинхронно.

<div className="ch-image-md">
  <Frame>
    ![Асинхронные вставки](/images/use-cases/observability/observability-6.webp)
  </Frame>
</div>

При [включенных асинхронных вставках](/ru/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts), когда ClickHouse ① получает запрос на вставку, данные запроса ② сразу записываются в буфер в оперативной памяти. При ③ следующем сбросе буфера на диск данные буфера [сортируются](/ru/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns) и записываются в хранилище базы данных в виде части. Обратите внимание: до сброса в хранилище базы данных данные недоступны для запросов; сброс буфера [настраивается](/ru/concepts/features/operations/insert/asyncinserts).

Чтобы включить асинхронные вставки для коллектора, добавьте `async_insert=1` в строку подключения. Для получения гарантий доставки рекомендуем использовать `wait_for_async_insert=1` (значение по умолчанию) — подробнее см. [здесь](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse).

Данные асинхронной вставки вставляются после сброса буфера ClickHouse на диск. Это происходит либо после превышения [`async_insert_max_data_size`](/ru/reference/settings/session-settings/async-insert#async_insert_max_data_size), либо через [`async_insert_busy_timeout_ms`](/ru/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms) миллисекунд после первого запроса INSERT. Если для `async_insert_stale_timeout_ms` задано ненулевое значение, данные вставляются через `async_insert_stale_timeout_ms milliseconds` после последнего запроса. Изменяя эти настройки, можно управлять сквозной задержкой конвейера. Другие настройки, влияющие на сброс буфера, описаны [здесь](/ru/reference/settings/session-settings/async-insert#async_insert). Как правило, значений по умолчанию вполне достаточно.

<Info>
  **Рассмотрите адаптивные асинхронные вставки**

  Если используется небольшое число агентов с низкой пропускной способностью, но со строгими требованиями к сквозной задержке, могут оказаться полезными [адаптивные асинхронные вставки](https://clickhouse.com/blog/clickhouse-release-24-02#adaptive-asynchronous-inserts). Как правило, они неприменимы к сценариям обсервабилити с высокой пропускной способностью, характерным для ClickHouse.
</Info>

Наконец, при использовании асинхронных вставок прежнее поведение дедупликации, свойственное синхронным вставкам в ClickHouse, по умолчанию отключено. При необходимости см. настройку [`async_insert_deduplicate`](/ru/reference/settings/session-settings/async-insert#async_insert_deduplicate).

Подробнее о настройке этой возможности см. на [странице документации](/ru/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts) или в подробной [статье в блоге](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse).

## Масштабирование {#scaling-self-configured}

Коллектор ClickStack OTel выступает в роли инстанса шлюза — см. [Роли коллектора](#collector-roles-self-configured). Такие инстансы работают как независимый сервис, как правило, по одному на центр обработки данных или на регион. Они получают события от приложений (или других коллекторов в роли агента) через единую конечную точку OTLP. Обычно развертывается группа инстансов коллектора, а нагрузка между ними распределяется с помощью стандартного load balancer.

<div className="ch-image-lg">
  <Frame>
    ![Масштабирование с помощью шлюзов](/images/use-cases/observability/clickstack-with-gateways.webp)
  </Frame>
</div>

Цель такой архитектуры — снять с агентов ресурсоемкую обработку и тем самым минимизировать потребление ими ресурсов. Шлюзы ClickStack могут выполнять задачи преобразования, которые иначе пришлось бы выполнять агентам. Кроме того, агрегируя события от множества агентов, шлюзы обеспечивают отправку в ClickHouse крупных пакетов, что делает вставку эффективной. Коллекторы-шлюзы легко масштабируются по мере добавления новых агентов и источников SDK и роста пропускной способности.

### Добавление Kafka {#adding-kafka-self-configured}

Читатели могут заметить, что в приведённых выше архитектурах Kafka не используется в качестве очереди сообщений.

Использование очереди Kafka в качестве буфера сообщений — популярный шаблон проектирования в архитектурах логирования, получивший распространение благодаря стеку ELK. Такой подход даёт ряд преимуществ: прежде всего, он обеспечивает более строгие гарантии доставки сообщений и помогает справляться с обратным давлением (backpressure). Агенты сбора отправляют сообщения в Kafka, где они записываются на диск. Теоретически кластерный инстанс Kafka должен обеспечивать буфер сообщений с высокой пропускной способностью, поскольку последовательная запись данных на диск требует меньше вычислительных накладных расходов, чем разбор и обработка сообщения. Например, в Elastic токенизация и индексирование влекут за собой значительные накладные расходы. Кроме того, перенося данные с агентов, вы снижаете риск потери сообщений из-за ротации журналов на источнике. Наконец, Kafka поддерживает повторное воспроизведение сообщений и межрегиональную репликацию, что может быть полезно в ряде сценариев использования.

Однако ClickHouse способен очень быстро выполнять вставку данных — миллионы строк в секунду на оборудовании средней мощности. Обратное давление со стороны ClickHouse возникает редко. Использование очереди Kafka зачастую означает усложнение архитектуры и дополнительные затраты. Если вы готовы исходить из того, что журналам не нужны такие же гарантии доставки, как банковским транзакциям и другим критически важным данным, мы рекомендуем не усложнять архитектуру добавлением Kafka.

Тем не менее, если вам требуются строгие гарантии доставки или возможность повторного воспроизведения данных (возможно, в несколько источников), Kafka может стать полезным дополнением к архитектуре.

<div className="ch-image-lg">
  <Frame>
    ![Добавление Kafka](/images/use-cases/observability/observability-8.webp)
  </Frame>
</div>

В этом случае агенты OTel можно настроить на отправку данных в Kafka через [экспортер Kafka](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/kafkaexporter/README.md). Инстансы шлюза, в свою очередь, читают и обрабатывают сообщения с помощью [приёмника Kafka](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/kafkareceiver/README.md). Подробнее см. документацию Confluent и OTel.

<Info>
  **Конфигурация OTel collector**

  Дистрибутив коллектора ClickStack OpenTelemetry можно настроить для работы с Kafka с помощью [пользовательской конфигурации коллектора](#extending-collector-config).
</Info>

## Оценка ресурсов {#estimating-resources-self-configured}

Требования OTel collector к ресурсам зависят от пропускной способности по событиям, размера сообщений и объёма выполняемой обработки. Проект OpenTelemetry публикует [тесты производительности](https://opentelemetry.io/docs/collector/benchmarks/), на которые можно опираться при оценке требований к ресурсам.

[По нашему опыту](https://clickhouse.com/blog/building-a-logging-platform-with-clickhouse-and-saving-millions-over-datadog#architectural-overview), инстанс шлюза ClickStack с 3 ядрами и 12GB оперативной памяти способен обрабатывать около 60k событий в секунду. При этом предполагается минимальный конвейер обработки, который только переименовывает поля и не использует регулярные выражения.

Для инстансов агентов, которые лишь отправляют события в шлюз и проставляют для них временную метку, рекомендуется подбирать ресурсы исходя из ожидаемого числа записей журнала в секунду. Ниже приведены приблизительные значения, которые можно использовать в качестве начальной точки:

| Интенсивность логирования | Ресурсы для агента коллектора |
| ------------------------- | ----------------------------- |
| 1k/секунду                | 0.2CPU, 0.2GiB                |
| 5k/секунду                | 0.5 CPU, 0.5GiB               |
| 10k/секунду               | 1 CPU, 1GiB                   |

## Выбор схемы: Map или JSON {#schema-choice-self-configured}

По умолчанию коллектор ClickStack создаёт таблицы, в которых атрибуты хранятся в столбцах типа `Map(LowCardinality(String), String)`. Эта схема рекомендуется для рабочих нагрузок обсервабилити. Схема на основе типа `JSON` доступна в статусе бета: её можно опробовать на рабочих нагрузках с небольшим стабильным набором ключей атрибутов.

Подробное сравнение, рекомендации по выбору варианта, переменные окружения для включения схемы на основе типа JSON, а также пошаговое руководство по миграции приведены в разделе [Map и тип JSON](/ru/clickstack/self-configured/ingesting-data/schema/map-vs-json).
