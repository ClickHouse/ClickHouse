[Схема по умолчанию](/ru/clickstack/self-configured/ingesting-data/schemas) хранит атрибуты ресурсов, областей видимости, журналов и спанов в столбцах типа `Map(LowCardinality(String), String)`. ClickHouse также поддерживает строго типизированный [тип `JSON`](/ru/reference/formats/JSON/JSON), и в самостоятельно управляемом ClickHouse Observability его можно использовать вместо `Map` (поддержка в бета-версии).

**Для типичных рабочих нагрузок обсервабилити мы рекомендуем использовать [схему по умолчанию на основе `Map`](/ru/clickstack/self-configured/ingesting-data/schemas).** Тип JSON доступен пользователям, которые хотят опробовать его на рабочих нагрузках с небольшим стабильным набором ключей атрибутов, однако для общего использования эта схема не рекомендуется.

## Почему Map рекомендуется по умолчанию {#why-map}

Основную часть данных обсервабилити составляют атрибуты: атрибуты ресурса, атрибуты области видимости (scope), а также атрибуты спанов и журналов. Такие наборы, как правило, велики, имеют высокую мощность (high-cardinality) и поступают с высокой пропускной способностью. Именно схема, выбранная для этих атрибутов, в первую очередь определяет стоимость приёма данных и структуру хранения.

`Map(LowCardinality(String), String)` хранит ключи и значения в единой структуре. Исторически недостатком `Map` было то, что для чтения одного ключа приходилось читать весь столбец Map. Теперь это не так: ClickHouse поддерживает [сериализацию Map по бакетам](/ru/reference/data-types/map#bucketed-map-serialization), при которой Map разбивается на бакеты, и запросы читают только нужные из них. В сочетании с [текстовыми индексами](/ru/reference/engines/table-engines/mergetree-family/textindexes) по ключам и значениям Map (именно так настроена [схема по умолчанию](/ru/clickstack/self-configured/ingesting-data/schemas)) это делает `Map` селективным и быстрым при чтении, не создавая никаких дополнительных затрат при приёме новых ключей.

На практике это означает:

* **Стабильная стоимость приёма при росте числа ключей.** Добавление нового ключа атрибута не меняет структуру столбцов на диске и не создаёт новых файлов столбцов. Стоимость приёма зависит от объёма данных, а не от мощности множества ключей.
* **Никакого взрывного роста метаданных.** Количество файлов столбцов на диске не зависит от числа уникальных ключей атрибутов.
* **Селективный поиск с помощью индексов.** Текстовые индексы по ключам и значениям Map обеспечивают точечный поиск без сканирования всех строк.
* **Предсказуемое поведение при высокой пропускной способности.** Map без накладных расходов на каждый ключ справляется с неравномерно поступающими наборами атрибутов без фиксированной схемы, типичными для трассировки и журналов.

## Почему JSON не используется по умолчанию {#why-not-json}

Тип `JSON` устроен иначе: в момент вставки ClickHouse динамически создаёт отдельный строго типизированный подстолбец для каждого обнаруженного пути. При чтении это выгодно: считываются только запрошенные подстолбцы, типы сохраняются, а приводить типы во время выполнения запроса не нужно.

Однако за это приходится платить на этапе приёма данных. Создание большого количества динамических подстолбцов и управление ими увеличивают накладные расходы при записи и усложняют метаданные. В рабочих нагрузках обсервабилити, которым свойственны очень большие или сильно меняющиеся наборы атрибутов и высокая пропускная способность ингестии, эти накладные расходы весьма значительны. Лимит [`max_dynamic_paths`](/ru/reference/data-types/newjson#reading-json-paths-as-sub-columns) позволяет смягчить проблему за счёт сброса лишних путей в общий столбец, однако доступ к общему столбцу медленнее, чем к отдельным подстолбцам, и это сводит на нет преимущество при чтении, ради которого JSON изначально и выбирали.

Поскольку сериализация Map по бакетам устраняет бо́льшую часть накладных расходов при чтении, исторически присущих `Map`, преимущество `JSON` при чтении в типичных рабочих нагрузках обсервабилити больше не перевешивает его издержек при приёме данных.

## Когда всё же стоит рассмотреть JSON {#when-to-consider-json}

Тип JSON может оказаться подходящим вариантом, если выполняются *все* следующие условия:

* Набор ключей атрибутов **небольшой и стабильный**: у вас нет тысяч уникальных ключей, а новые ключи появляются редко.
* Пропускная способность ингестии **умеренная** относительно мощности атрибутов.
* Вам нужен **строго типизированный доступ** к атрибутам без приведения типов во время выполнения запроса (числа остаются числами, логические значения — логическими).
* Вы готовы использовать **функцию в стадии бета-тестирования** в Самостоятельно управляемом ClickHouse Observability и допускаете, что интеграция может измениться.

Если хотя бы одно из этих условий не выполняется, используйте [схему по умолчанию на основе `Map`](/ru/clickstack/self-configured/ingesting-data/schemas).

## Статус бета-версии {#beta-status}

<BetaBadge />

<Warning>
  **Функция в стадии бета-тестирования, не готова для продакшн-среды**

  Поддержка типа JSON в **Самостоятельно управляемом ClickHouse Observability** — это **функция в стадии бета-тестирования**. Хотя сам тип JSON готов к использованию в продакшн-среде начиная с ClickHouse 25.3, его интеграция в сервис всё ещё находится в активной разработке: возможны ограничения, изменения в будущем и ошибки.
</Warning>

В ClickStack поддержка типа JSON в бета-версии доступна начиная с версии `2.0.4`.

## Включение поддержки JSON {#enabling-json-support}

Чтобы использовать схемы с типом данных JSON вместо [схем на основе `Map`, используемых по умолчанию](/ru/clickstack/self-configured/ingesting-data/schemas), задайте следующие переменные окружения.

| Переменная                                                      | Где задаётся                       | Назначение                               |
| --------------------------------------------------------------- | ---------------------------------- | ---------------------------------------- |
| `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'` | Коллектор ClickHouse Observability | Создаёт в ClickHouse схемы с типом JSON. |

<a id="managed-clickstack" />

Чтобы включить поддержку JSON в самостоятельно управляемом ClickHouse Observability, перед настройкой коллектора напишите в службу поддержки по адресу support@clickhouse.com. Кроме того, эту возможность необходимо включить в интерфейсе обсервабилити в ClickHouse Cloud.

Задайте для коллектора переменную `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'`. Например:

```shell
docker run -e OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json' -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
```

## Миграция со схемы на основе Map на JSON {#migrating-from-map-to-json}

<Warning>
  **Обратная совместимость**

  [Тип JSON](/ru/reference/formats/JSON/JSON) **не обладает обратной совместимостью** с существующими схемами на основе Map. При включении этой возможности создаются новые таблицы с типом `JSON`, а данные требуется перенести вручную.
</Warning>

Чтобы перейти со [схем на основе Map, используемых по умолчанию](/ru/clickstack/self-configured/ingesting-data/schemas), выполните следующие шаги:

<Steps>
  <Step title="Остановите OTel collector" id="stop-the-collector" />

  <Step title="Переименуйте существующие таблицы и обновите источники" id="rename-existing-tables-sources">
    Переименуйте существующие таблицы и обновите источники данных в интерфейсе обсервабилити.

    Например:

    ```sql
    RENAME TABLE otel_logs TO otel_logs_map;
    RENAME TABLE otel_metrics TO otel_metrics_map;
    ```
  </Step>

  <Step title="Разверните коллектор" id="deploy-the-collector">
    Разверните коллектор с заданной переменной `OTEL_AGENT_FEATURE_GATE_ARG`.
  </Step>

  <Step title="Убедитесь, что поддержка схем JSON включена" id="restart-the-hyperdx-container">
    Перед созданием новых источников данных уточните через support@clickhouse.com, включена ли поддержка схем JSON в интерфейсе обсервабилити.
  </Step>

  <Step title="Создайте новые источники данных" id="create-new-data-sources">
    Создайте в интерфейсе обсервабилити новые источники данных, указывающие на таблицы JSON.
  </Step>
</Steps>

### Миграция существующих данных (необязательно) {#migrating-existing-data}

Чтобы перенести старые данные в новые таблицы с JSON:

```sql
INSERT INTO otel_logs SELECT * FROM otel_logs_map;
INSERT INTO otel_metrics SELECT * FROM otel_metrics_map;
```

<Warning>
  Рекомендуется только для наборов данных размером менее ~10 миллиардов строк. В данных, ранее сохранённых с типом Map, точность типов не сохранялась (все значения хранились как строки). Поэтому до истечения срока хранения эти старые данные будут отображаться в новой схеме как строки, и на фронтенде потребуется приведение типов. Для новых данных типы будут сохраняться благодаря типу JSON.
</Warning>
