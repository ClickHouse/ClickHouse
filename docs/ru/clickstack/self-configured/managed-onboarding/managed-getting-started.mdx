<Note>
  На этой странице описан **самостоятельно управляемый ClickHouse Observability**. Рекомендуемый вариант с полностью управляемым сервисом описан в документации [здесь](/ru/clickstack/observability/getting-started).
</Note>

Это руководство проведёт вас от пустого сервиса самостоятельно управляемого ClickHouse Observability до полноценного потока журналов, метрик, трассировки и воспроизведения сеансов из реального приложения. Вы развернёте новый коллектор OpenTelemetry (или адаптируете существующий, если он у вас уже есть) для работы с вашим сервисом, инструментируете демонстрационное приложение на Node.js без изменения его бизнес-логики, а затем изучите телеметрию в интерфейсе ClickStack.

<Note>
  Если вы настраиваете новый коллектор или используете собственный, он должен работать как **шлюз** — единая конечная точка OTLP, в которую отправляют данные ваши приложения, SDK и коллекторы-агенты. Шлюз группирует события в пакеты, применяет настроенную вами обработку и записывает их в ClickHouse через [экспортер ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).
</Note>

Инструментировать мы будем [HackerNews Analyzer](https://github.com/ClickHouse/hn-news-analyzer) — приложение на Node.js, которое выполняет запросы к набору данных HackerNews, размещённому в публичной демо-среде ClickHouse. За каждым чартом, таблицей и полем поиска стоит реальный запрос к ClickHouse, поэтому каждое действие пользователя порождает трассу, основной спан которой — HTTPS-вызов от бэкенда к ClickHouse.

## Предварительные требования {#prerequisites}

* **Сервис «Самостоятельно управляемый ClickHouse Observability»** в [ClickHouse Cloud](https://console.clickhouse.cloud).
* **Node 18+ и npm** для запуска демонстрационного приложения.
* **Docker**, если у вас ещё нет коллектора и вы хотите воспользоваться описанным ниже вариантом с новым коллектором.

  <Step title="Разверните коллектор" id="deploy-collector">
    Выберите вариант, подходящий для вашей ситуации.

    <Info>
      **Существующий коллектор**

      Если вы используете существующий коллектор OpenTelemetry, предполагается, что он уже настроен в роли **шлюза**. Мы не рекомендуем применять эту процедуру для перенастройки коллекторов в роли **агента**.
    </Info>

    <Tabs>
      <Tab title="У меня нет коллектора">
        Разверните **дистрибутив ClickStack для OpenTelemetry Collector**, предварительно настроенный для самостоятельно управляемого ClickHouse Observability. Для простоты в примере ниже коллектор запускается локально.

        <Note>
          В продакшн-среде коллектор обычно разворачивают в кластере Kubernetes или на виртуальной машине, доступной для ваших SDK OpenTelemetry, агентов и других коллекторов. Это позволяет централизованно собирать телеметрию со всей инфраструктуры и перенаправлять её в ClickStack.
        </Note>

        Выберите общий секрет для аутентификации клиентов, отправляющих данные в коллектор, а затем экспортируйте его в переменные окружения вместе со сведениями о подключении и выбранным паролем для пользователя `hyperdx_ingest`:

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        Запустите коллектор ClickStack OTel:

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        Теперь коллектор принимает данные по OTLP gRPC на порту `4317` и по OTLP HTTP на порту `4318`. Приложения, SDK и коллекторы-агенты должны отправлять данные на эти порты, передавая `authorization: $OTLP_AUTH_TOKEN` в заголовках запроса. Сохраните конечную точку OTLP и `OTLP_AUTH_TOKEN` — на следующих шагах вы укажете их в настройках приложения.

        <Info>
          **Развертывания в продакшн-среде**

          Для продакшн-среды рекомендуется включить TLS на конечной точке OTLP. См. раздел [Защита коллектора](/ru/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        </Info>
      </Tab>

      <Tab title="У меня есть коллектор">
        Расширьте существующую конфигурацию коллектора, чтобы записывать данные в самостоятельно управляемый ClickHouse Observability с помощью [экспортера ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

        <Info>
          **Требуется экспортер ClickHouse**

          Если вы используете собственный дистрибутив коллектора, убедитесь, что в него входит экспортер ClickHouse. В вышестоящем [образе contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) он уже есть.
        </Info>

        Ниже приведён пример конфигурации, в которой экспортер ClickHouse используется вместе с приёмниками, процессорами и конвейерами, необходимыми интерфейсу ClickStack. Её поведение совпадает с поведением дистрибутива ClickStack, включая путь маршрутизации для воспроизведения сеансов (`rrweb`). Замените `<clickhouse_cloud_endpoint>` и `<your_password_here>` учётными данными созданного ранее пользователя `hyperdx_ingest`:

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        Несколько важных моментов:

        * Приёмник `otlp/hyperdx` принимает данные по gRPC (порт `4317`) и HTTP (порт `4318`); приложения и агенты должны отправлять данные на эти порты хоста вашего коллектора.
        * Экспортер `clickhouse` записывает журналы, трассировки и метрики в базу данных `otel` в соответствии со структурой, которую ожидает интерфейс ClickStack. Экспортер `clickhouse/rrweb` обрабатывает события Session Replay, которые коннектор `routing/logs` направляет в `otel.hyperdx_sessions`.
        * Аутентификация в приёмниках OTLP настраивается в рамках вашей текущей конфигурации. Если требуется токен для ингестии, настройте её с помощью [расширений](https://opentelemetry.io/docs/collector/configuration/#extensions) коллектора (например, `bearertokenauth`) или обратного прокси с терминацией TLS.

        Перезагрузите коллектор с новой конфигурацией. Держите под рукой конечную точку OTLP и заголовок аутентификации, который ожидает ваша конфигурация: на следующих шагах вы укажете их в приложении.

        Подробнее о настройке коллекторов OpenTelemetry для работы с самостоятельно управляемым ClickHouse Observability см. в разделе [Загрузка данных с помощью OpenTelemetry](/ru/clickstack/observability/ingesting-data/opentelemetry#self-managed).
      </Tab>
    </Tabs>
  </Step>

  <Step title="Клонируйте репозиторий и запустите приложение" id="clone-and-run-the-application">
    Клонируйте репозиторий, установите зависимости и создайте файл `.env`:

    ```bash
    git clone https://github.com/ClickHouse/hn-news-analyzer.git
    cd hn-news-analyzer
    npm install
    cp .env.example .env
    ```

    По умолчанию источник данных ClickHouse подключается к публичному демонстрационному кластеру с доступом только для чтения, поэтому приложение работает без дополнительной настройки. Запустите его:

    ```bash
    ./run.sh
    ```

    Откройте [http://localhost:5001](http://localhost:5001). Вы увидите селектор года, сводную статистику, чарт активности, таблицы самых активных пользователей и популярных доменов, а также поле поиска. Изучите интерфейс: переключайте годы, открывайте отдельные публикации.

    <div className="ch-image-lg">
      <Frame>
        ![Приложение HackerNews Analyzer, запущенное локально](/images/clickstack/getting-started/hackernews_main.webp)
      </Frame>
    </div>

    На этом этапе приложение запущено, но ещё не инструментировано. ClickStack не отображает данных: он ожидает поступления телеметрии. Это исходное состояние — «до».
  </Step>

  <Step title="Подключите приложение к коллектору" id="connect-the-application">
    Чтобы приложение могло подключиться к коллектору, развернутому выше, ему нужны два значения:

    * `OTEL_EXPORTER_OTLP_ENDPOINT`: конечная точка OTLP, которую предоставляет ваш коллектор (обычно порт `4318` для OTLP поверх HTTPS).
    * `OTEL_EXPORTER_OTLP_HEADERS`: заголовок авторизации с вашим токеном ингестии в формате `authorization=<ingestion_token>`. Используйте значение `OTLP_AUTH_TOKEN`, заданное для коллектора выше, или тот заголовок аутентификации, который ожидает ваш существующий коллектор.

    Скопируйте `.env.example` в `.env`, затем откройте файл и задайте следующие переменные:

    ```bash
    OTEL_SERVICE_NAME=hn-analyzer-api
    OTEL_EXPORTER_OTLP_ENDPOINT=https://<your-collector-endpoint>:4318
    OTEL_EXPORTER_OTLP_HEADERS=authorization=<ingestion_token>
    ```

    SDK использует `OTEL_EXPORTER_OTLP_HEADERS`, чтобы задать заголовок авторизации для всех трёх сигналов: трассировки, метрик и журналов. Если коллектор работает локально и не требует аутентификации, значение можно оставить пустым (`OTEL_EXPORTER_OTLP_HEADERS=authorization=`), однако сама переменная должна присутствовать: если она не задана или полностью пуста, SDK вообще не выполняет инициализацию. Наконец, если коллектор запущен без TLS, убедитесь, что используется правильный протокол — HTTP (например, `http://localhost:4318`).
  </Step>

  <Step title="Инструментируйте приложение" id="instrument-the-application">
    Инструментирование состоит из трёх этапов: установка SDK, изменение команды запуска и включение браузерного SDK. Ни один из них не затрагивает бизнес-логику приложения.

### Установка SDK {#install-sdks}

    Установите серверный и браузерный SDK OpenTelemetry:

    ```bash
    npm install @hyperdx/node-opentelemetry @hyperdx/browser
    ```

### Использование CLI opentelemetry-instrument {#use-open-telemetry-cli}

    Приложение запускается скриптом `run.sh`, в конце которого есть две строки `exec`: одна активна, другая закомментирована. Переключите их — закомментируйте активную строку и раскомментируйте вторую, — чтобы Node запускался через обёртку `opentelemetry-instrument`:

    ```diff
     # BEFORE: plain node, no instrumentation, collector stays silent:
    -exec node scripts/entrypoint.js
    +# exec node scripts/entrypoint.js

     # AFTER: same source, wrapped by opentelemetry-instrument CLI.
    -# exec npx opentelemetry-instrument scripts/entrypoint.js
    +exec npx opentelemetry-instrument scripts/entrypoint.js
    ```

    На этом изменения на стороне бэкенда завершены. Автоматическое инструментирование загружается командой `opentelemetry-instrument` при запуске процесса.

### Включение браузерного SDK {#enable-browser-sdk}

    Чтобы собирать распределённые трассы (от браузера до бэкенда) и записи для воспроизведения сеансов, включите браузерный SDK в `src/web/telemetry.ts`. Раскомментируйте импорт и блок `HyperDX.init({...})`:

    ```javascript
    import HyperDX from '@hyperdx/browser';

    export function initTelemetry(): void {
      HyperDX.init({
        url: __OTLP_ENDPOINT__,
        apiKey: __OTLP_AUTH_TOKEN__,
        service: 'hn-analyzer-web',
        tracePropagationTargets: [/localhost:5001/i, /\/api\//i],
        consoleCapture: true,
        advancedNetworkCapture: true,
      });
    }
    ```

    Дополнительно редактировать `.env` не требуется. `__OTLP_ENDPOINT__` и `__OTLP_AUTH_TOKEN__` — это константы времени компиляции, которые подставляет `vite.config.ts`: конечная точка берётся из `OTEL_EXPORTER_OTLP_ENDPOINT`, а токен извлекается из `OTEL_EXPORTER_OTLP_HEADERS`, то есть используются те же значения, что и на бэкенде.

    <Warning>
      Токен ингестии встраивается в публичный браузерный бандл, и его может увидеть любой, кто откроет вкладку «Сеть».
    </Warning>
  </Step>

  <Step title="Сгенерируйте трафик" id="generate-traffic">
    Перезапустите приложение, чтобы применились новая команда запуска и заново собранный браузерный бандл:

    ```bash
    # Ctrl-C the previous run, then:
    ./run.sh
    ```

    Перезагрузите вкладку браузера, чтобы Vite отдал обновлённый бандл, затем несколько раз обновите приложение, переключите годы и откройте несколько историй, чтобы создать трафик. При каждом действии журналы, метрики, трассировки и события воспроизведения сеансов отправляются через ваш коллектор в ClickStack.
  </Step>

    Если данные не отображаются:

    * Убедитесь, что значение заголовка аутентификации, заданное в `OTEL_EXPORTER_OTLP_HEADERS`, совпадает с ожидаемым коллектором.
