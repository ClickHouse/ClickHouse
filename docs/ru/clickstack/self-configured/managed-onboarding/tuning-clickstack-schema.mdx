<Note>
  На этой странице описывается **самостоятельно управляемый ClickHouse Observability**. Рекомендуемый полностью управляемый вариант описан в документации [здесь](/ru/clickstack/observability/overview).
</Note>

Если вы уже какое-то время используете ClickStack, то, вероятно, заметили, что схема по умолчанию без каких-либо изменений справляется с большинством рабочих нагрузок обсервабилити. Эта страница — для случаев, когда этого уже недостаточно: задержка запросов начинает расти или ваши шаблоны доступа заметно отличаются от предусмотренных по умолчанию.

На практике основной эффект дают четыре оптимизации. Они перечислены примерно в порядке возрастания трудозатрат. Первые две — локальные изменения через `ALTER TABLE`, которые можно внедрять инкрементально. Третья оправдывает себя, когда одна и та же агрегация раз за разом выполняется на панели мониторинга. Четвёртая требует миграции таблицы, поэтому она самая трудоёмкая.

Описания ниже намеренно краткие. Обоснование каждого изменения, результаты тестов производительности и инструкции по применению изменений к существующим данным см. в разделе [Настройка производительности](/ru/clickstack/self-configured/managing/performance-tuning).

<Steps>
  <Step title="Материализуйте часто запрашиваемые атрибуты" id="materialize-attributes">
    При фильтрации по `LogAttributes['service.version']` ClickHouse приходится загружать и декодировать весь Map `LogAttributes` для каждой проверяемой строки. Если вынести атрибут в столбец `MATERIALIZED`, тот же фильтр сводится к чтению одного столбца, что обычно на порядок быстрее. Как только столбец появляется, ClickStack автоматически переписывает фильтр, поэтому сохранённые поиски и панели мониторинга продолжают работать без изменений.

    Выбирайте только те атрибуты, которые действительно часто запрашиваете. Каждый материализованный столбец увеличивает объём хранилища и время вставки, поэтому принцип здесь — «выносить то, что используется», а не «выносить всё».

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    Для существующих строк новый столбец остаётся пустым, пока вы дополнительно не выполните `ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion`.

    Подробнее: [Материализация часто запрашиваемых атрибутов](/ru/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes).
  </Step>

  <Step title="Добавьте индексы пропуска данных" id="add-skip-indexes">
    Индексы пропуска данных позволяют ClickHouse отбрасывать гранулы, которые заведомо не удовлетворяют фильтру, и вместо полного сканирования читать лишь небольшой объём нужных данных. Стоит знать о трёх типах индексов:

    * **Текстовые индексы** (`text(tokenizer = ...)`) для строковых столбцов и массивов `mapKeys`/`*AttributeItems`. В схеме журналов по умолчанию они уже есть.
    * **Min-max-индексы** для числовых столбцов, по которым фильтруют по диапазону. Классический пример — `Duration` трассы.
    * **Фильтры Блума** для поиска по равенству среди значений с высокой мощностью в версиях ClickHouse, которые ещё не поддерживают текстовые индексы.

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    Индекс пропуска данных окупает затраты на свою проверку, только если действительно отсекает гранулы. Прежде чем считать, что он помог, проверьте это с помощью `EXPLAIN indexes = 1` на типичном запросе.

    Подробнее: [Добавление индексов пропуска данных](/ru/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes).
  </Step>

  <Step title="Вычисляйте повторяющиеся агрегации заранее" id="materialized-views">
    Если на панели мониторинга одна и та же агрегация выполняется снова и снова (топ сервисов по доле ошибок, задержка p99 по эндпоинтам, число запросов в минуту), materialized view вычисляет результат в момент вставки и записывает его в небольшую агрегированную таблицу. Панели мониторинга затем обращаются к ней, а не к исходным журналам или трассировкам, что обходится несравнимо дешевле.

    Это оправдано, когда панелью активно пользуются, а исходная таблица велика. Цена — дополнительная нагрузка на CPU при вставке и ещё одна таблица, которую нужно поддерживать.

    Подробнее: [Использование materialized views](/ru/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views).
  </Step>

  <Step title="Выберите первичный ключ под свой шаблон доступа" id="choose-primary-key">
    Первичный ключ определяет порядок сортировки строк на диске. Фильтры по ведущим столбцам ключа позволяют ClickHouse сразу перейти к нужной области; если же фильтр не начинается ни с одного из этих столбцов, сканируется вся партиция.

    Ключ журналов по умолчанию `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)` оптимизирован под запросы вида «что произошло за последние N минут в сервисе X». Если большинство ваших запросов начинается с другого столбца (ID тенанта, ID клиента, регион), перестройка первичного ключа так, чтобы он начинался с этого столбца, даст наибольший эффект из всех возможных изменений.

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- те же столбцы, что и в otel_logs
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse не позволяет изменить первичный ключ на месте, поэтому потребуется миграция таблицы, а не простой `ALTER`. В руководстве по настройке производительности пошагово описано, как создать новую таблицу, перенаправить приём данных и использовать таблицу `Merge`, чтобы существующие панели мониторинга работали как со старыми, так и с новыми данными.

    Подробнее: [Изменение первичного ключа](/ru/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key).
  </Step>
</Steps>
