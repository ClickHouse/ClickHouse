<Info>
  **Кратко**

  Добавьте Datadog-совместимую конечную точку вашего сервиса в уже работающие агенты Datadog — параллельно с Datadog или вместо него — и перезапустите их. Журналы, трассировка и метрики появятся в ClickHouse Observability. Разворачивать коллектор и изменять приложения не нужно.

  Необходимое время: около 15 минут
</Info>

Вы создали сервис ClickHouse Observability, а ваша телеметрия уже проходит через агенты Datadog. Чтобы посмотреть, как сервис работает с вашими собственными данными, не нужно ни заменять эти агенты, ни вносить изменения в приложения.

В ClickHouse Observability есть Datadog-совместимая конечная точка. Она принимает журналы, трассировку и метрики, которые уже формируют ваши агенты, преобразует их в формат OpenTelemetry и сохраняет в вашем сервисе. Изменить нужно только конфигурацию агентов. Это позволяет:

* Оценить ClickHouse Observability на реальной телеметрии из продакшна, а не на тестовом наборе данных.
* Продолжать отправлять данные в Datadog и параллельно сравнивать обе платформы.
* Выполнять миграцию постепенно: переводить агенты группа за группой и внедрять инструментирование OpenTelemetry в удобном для вас темпе.

## Предварительные требования {#prerequisites}

* Сервис ClickHouse Observability. Если у вас его ещё нет, воспользуйтесь [руководством по началу работы](/ru/clickstack/observability/getting-started).
* Агент Datadog версии 7 на хостах, в контейнерах или кластерах Kubernetes, на которых вы хотите провести оценку, — он уже должен собирать нужные вам журналы и метрики. Для трассировки ваши приложения должны уже отправлять трассировку агенту через библиотеки трассировки Datadog.
* Доступ к конфигурации агента (файлу `datadog.yaml` или эквивалентным переменным окружения), а также разрешение на перезапуск агента.
* Исходящий доступ по HTTPS через порт `8126` с хостов агента к конечной точке телеметрии вашего сервиса.

## Подключение агентов Datadog {#connect-your-datadog-agents}

<Steps>
  <Step title="Скопируйте сведения о подключении" id="copy-connection-details">
    Откройте свой сервис ClickHouse Observability. Пока данные не поступили, в нём отображается страница **Start sending telemetry**.

    <div className="ch-image-lg">
      <Frame>
        ![Страница Start sending telemetry, на которой показан текущий сервис без данных и три варианта: Use an existing OpenTelemetry setup, Instrument with AI и Follow setup guides](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    В разделе **Use an existing OpenTelemetry setup** выберите **View connection details**. На вкладке **URL** отображаются ваша конечная точка OTLP (`https://YOUR_OTEL_HOST:4318`) и ключ API. Нажмите **Reveal key**, чтобы увидеть ключ полностью, а затем скопируйте его с помощью кнопки копирования.

    <div className="ch-image-md">
      <Frame>
        ![Диалоговое окно Set up OpenTelemetry с вариантами URL, Collector config и Env vars и скрытыми сведениями о подключении](/images/clickstack/getting-started/observability-connection-details.png)
      </Frame>
    </div>

    Конечная точка, совместимая с Datadog, находится на том же хосте, что и конечная точка OTLP, но на порту `8126` вместо `4318`, а ключ API вашего сервиса одновременно служит ключом API Datadog. Далее в этом руководстве используются следующие плейсхолдеры:

    | Плейсхолдер                   | Значение                                                                                |
    | ----------------------------- | --------------------------------------------------------------------------------------- |
    | `YOUR_API_KEY`                | Ключ API вашего сервиса                                                                 |
    | `YOUR_OTEL_HOST`              | Имя хоста из конечной точки OTLP без `https://` и порта                                 |
    | `https://YOUR_OTEL_HOST:8126` | Конечная точка, совместимая с Datadog, для метрик и трассировки                         |
    | `YOUR_OTEL_HOST:8126`         | Та же конечная точка в формате `host:port`, которого ожидают настройки журналов в Agent |

    Эти же значения в любой момент можно найти в разделе **Team Settings → Managed Telemetry**.

    <div className="ch-image-lg">
      <Frame>
        ![Страница Managed Telemetry в Team Settings со скрытыми конечной точкой OTLP по HTTP и ключом API](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>
  </Step>

  <Step title="Настройте агентов Datadog" id="configure-your-datadog-agents">
    Выберите, как агенты будут отправлять данные. Оба варианта затрагивают только конфигурацию Agent — в `datadog.yaml` или через переменные окружения — и ни один из них не влияет на то, какие данные собирает Agent. Начните с одного агента, убедитесь, что его данные поступают, и только затем распространяйте изменение на остальные.

    <Tabs>
      <Tab title="Вместе с Datadog" id="alongside-datadog">
        Агент Datadog может отправлять каждую полезную нагрузку сразу в несколько пунктов назначения. Сохраните существующие `api_key` и `site` и добавьте ваш сервис в качестве дополнительной конечной точки для метрик, трассировки и журналов. В документации Datadog этот режим называется [dual shipping](https://docs.datadoghq.com/agent/configuration/dual-shipping/).

        ```yaml
        # datadog.yaml: оставьте api_key и site без изменений, затем добавьте эти настройки.

        # Метрики
        additional_endpoints:
          "https://YOUR_OTEL_HOST:8126":
            - "YOUR_API_KEY"

        # Использовать приём метрик v2.
        use_v3_api:
          series:
            enabled: false

        # Трассировка
        apm_config:
          additional_endpoints:
            "https://YOUR_OTEL_HOST:8126":
              - "YOUR_API_KEY"

        # Журналы
        logs_config:
          force_use_http: true
          additional_endpoints:
            - api_key: "YOUR_API_KEY"
              Host: "YOUR_OTEL_HOST"
              Port: 8126
              is_reliable: true
        ```

        Datadog по-прежнему получает все данные. У каждого пункта назначения свой ключ API, поэтому ваш ключ Datadog никогда не попадает в ClickHouse Observability, а ключ ClickHouse Observability — в Datadog. На дополнительные конечные точки журналы отправляются только по HTTP, который включается параметром `force_use_http`. Параметр `is_reliable: true` заставляет агент буферизовать журналы для новой конечной точки и повторять попытки отправки, а не отбрасывать их, если конечная точка ненадолго становится недоступна. Если в вашем файле уже есть `apm_config` или `logs_config`, добавьте новые ключи в существующие разделы.
      </Tab>

      <Tab title="Вместо Datadog" id="instead-of-datadog">
        Чтобы полностью перевести агент на ваш сервис, укажите сервис в качестве основных пунктов назначения и используйте его ключ API:

        ```yaml
        api_key: "YOUR_API_KEY"

        # Пункт назначения для метрик
        dd_url: "https://YOUR_OTEL_HOST:8126"

        # Использовать приём метрик v2.
        use_v3_api:
          series:
            enabled: false

        # Пункт назначения для трасс
        apm_config:
          enabled: true
          apm_dd_url: "https://YOUR_OTEL_HOST:8126"

        # Пункт назначения для журналов
        logs_enabled: true
        logs_config:
          logs_dd_url: "YOUR_OTEL_HOST:8126"
          force_use_http: true
          logs_no_ssl: false

        remote_updates: false
        remote_configuration:
          enabled: false
        ```

        Эти настройки перенаправляют журналы, трассировку и метрики агента. Они не влияют на то, какие журналы собирает агент, и не добавляют инструментирование, поэтому сохраните существующие интеграции для сбора журналов и настройки трассировки. Удалённая конфигурация отключена, поскольку иначе агент продолжал бы запрашивать конфигурацию у Datadog с ключом, который Datadog больше не распознаёт.
      </Tab>
    </Tabs>

    <Accordion title="Настройка с помощью переменных окружения">
      В контейнерных развертываниях и развертываниях в Kubernetes агент обычно настраивается через переменные окружения `DD_`, которые переопределяют параметры из `datadog.yaml`. Задайте их в команде Docker, в значениях Helm или в спецификации Operator.

      Чтобы отправлять данные параллельно с Datadog:

      ```shell
      DD_ADDITIONAL_ENDPOINTS='{"https://YOUR_OTEL_HOST:8126": ["YOUR_API_KEY"]}'
      DD_APM_ADDITIONAL_ENDPOINTS='{"https://YOUR_OTEL_HOST:8126": ["YOUR_API_KEY"]}'
      DD_LOGS_CONFIG_FORCE_USE_HTTP=true
      DD_LOGS_CONFIG_ADDITIONAL_ENDPOINTS='[{"api_key": "YOUR_API_KEY", "Host": "YOUR_OTEL_HOST", "Port": 8126, "is_reliable": true}]'
      ```

      Чтобы отправлять данные сюда, а не в Datadog:

      ```shell
      DD_API_KEY=YOUR_API_KEY
      DD_DD_URL=https://YOUR_OTEL_HOST:8126
      DD_APM_ENABLED=true
      DD_APM_DD_URL=https://YOUR_OTEL_HOST:8126
      DD_LOGS_ENABLED=true
      DD_LOGS_CONFIG_LOGS_DD_URL=YOUR_OTEL_HOST:8126
      DD_LOGS_CONFIG_FORCE_USE_HTTP=true
      DD_REMOTE_CONFIGURATION_ENABLED=false
      ```

      Агент версии 7.81 и новее по умолчанию отправляет метрики в новый эндпоинт приёма серий. Если от агента с такой конфигурацией метрики не поступают, добавьте `use_v3_api.series.enabled: false` в его файл `datadog.yaml`, как это сделано в приведённых выше примерах с файловой конфигурацией.
    </Accordion>
  </Step>

  <Step title="Перезапустите агент и проверьте его состояние" id="restart-and-check">
    Перезапустите агент, чтобы применить конфигурацию. В Linux:

    ```shell
    sudo systemctl restart datadog-agent
    sudo datadog-agent status
    ```

    В macOS:

    ```shell
    sudo launchctl kickstart -k system/com.datadoghq.agent
    datadog-agent status
    ```

    Если Agent работает в контейнере, обновите его переменные окружения и заново разверните контейнер или под, затем выполните внутри него команду `agent status`.

    В выводе команды status в разделах **Forwarder**, **APM Agent** и **Logs Agent** перечислены все пункты назначения. У работоспособного агента отображается ваша конечная точка без ошибок. Ответы `403` означают, что ключ API указан неверно или был скопирован до того, как вы нажали **Reveal key**. Ошибки соединения или тайм-ауты указывают на опечатку в имени хоста, использование порта, отличного от `8126`, или блокировку исходящего доступа.
  </Step>
</Steps>

## Проверка поступления данных {#confirm-data-is-arriving}

Вернитесь на страницу **Start sending telemetry** в вашем сервисе и нажмите **Check for data**. Когда телеметрия поступит, состояние сервиса изменится на **Data received** и станет доступна кнопка **Start exploring**.

  <Frame>

  </Frame>

Нажмите **Start exploring**, чтобы открыть страницу **Поиск**. Выберите источник **Logs**, задайте временной диапазон **Last 15 minutes** и отфильтруйте `ServiceName` по метке `service`, которую назначает ваш агент. Разверните запись: метки агента `host` и `env`, а также метки контейнера и Kubernetes отображаются как атрибуты ресурса, а поле `status` из Datadog сопоставлено с `SeverityText`, поэтому фильтры вида `level:error` работают так же, как для журналов OpenTelemetry.

## Если данные не отображаются {#if-nothing-shows-up}

* Сначала проверьте статус агента. Проблемы с аутентификацией, конечной точкой и сетью отображаются там отдельно для каждого пункта назначения. В конфигурации параллельной отправки ошибки вашей конечной точки никогда не мешают доставке данных в Datadog.
* Проверьте ключ API. Он должен быть указан полностью (его можно скопировать, нажав **Reveal key**) и передаваться как Datadog `api_key` для вашей конечной точки, а не как заголовок.
* Проверьте конечную точку. Для метрик и трассировки используется `https://YOUR_OTEL_HOST:8126` со схемой, а в настройках журналов — `YOUR_OTEL_HOST:8126` без неё. Имя хоста берётся из вашей конечной точки OTLP, а порт должен быть `8126`, а не `4318`.
* Если журналы не поступают, убедитесь, что задано `logs_enabled: true` и что сбор журналов настроен для нужных интеграций или файлов. Конечная точка принимает журналы только по HTTP, поэтому параметр `force_use_http` должен иметь значение `true`.
* Если трассировка не поступает, убедитесь, что задано `apm_config.enabled: true` и что ваши приложения отправляют трассировку в агент. Конечная точка принимает то, что пересылает агент, но сама не инструментирует приложения.
* Если метрики не поступают, убедитесь, что агент использует приём серий через API v2 с параметром `use_v3_api.series.enabled: false`.
* Расширьте временной диапазон в **Поиске** и сбросьте все фильтры. Возможно, в качестве источника по умолчанию выбран **Трассировка**, а не **Logs**.
* Чтобы исключить проблему на стороне самого сервиса, перейдите в **Team Settings → Managed Telemetry** и нажмите **Send a Test Log**. Если тестовый журнал появится в **Поиске**, значит, сервис получает данные, а проблема возникает на участке между агентом и конечной точкой.

## Что принимает конечная точка {#what-the-endpoint-accepts}

Конечная точка поддерживает протоколы, которые использует агент Datadog, и преобразует каждую полезную нагрузку в формат OpenTelemetry до того, как она попадёт в ваш сервис:

* **Журналы.** Временные метки, тела и статусы Datadog преобразуются во временные метки, тела и уровни серьёзности OpenTelemetry. Структурированные журналы в формате JSON декодируются, поэтому по их полям можно выполнять запросы. Имена хостов, имена сервисов, окружения, а также известные метки контейнеров, облаков и Kubernetes становятся атрибутами ресурса.
* **Трассировка.** Спаны из библиотек трассировки Datadog сохраняют данные о сервисе, ресурсе и метках, а 128-битные идентификаторы трасс восстанавливаются, благодаря чему журналы и спаны из Datadog коррелируют с сервисами, инструментированными с помощью OpenTelemetry.
* **Метрики.** Поддерживаются серии, отправленные в intake v2, включая метрики хоста от агента, пользовательские метрики, а также gauges и счётчики DogStatsD. Распределения поступают в виде скетчей.
* **Сжатие.** Агент версии 7.59 и выше сжимает полезные нагрузки HTTP с помощью Zstandard; конечная точка принимает этот формат наряду с gzip.

Конечная точка построена на основе приёмника Datadog из OpenTelemetry Collector (компонент в статусе alpha) и является экспериментальной возможностью ClickHouse Observability. Собственные серверные возможности Datadog, такие как мониторы, конвейеры и процессоры, она не поддерживает. Полное руководство по миграции, в том числе описание приёмника, который вы запускаете самостоятельно в самоуправляемом варианте, см. в разделе [Миграция с Datadog](/ru/clickstack/observability/migration/datadog).

## Дальнейшие шаги {#next-steps}

* **Расширьте оценку.** Добавьте конфигурацию параллельной отправки на большее число агентов, чтобы сравнить обе платформы на важных для вас рабочих нагрузках, а когда будете готовы — переключите агенты на конфигурацию с заменой. Ни на одном из этих этапов менять что-либо в приложениях не потребуется.
* [Инструментируйте своё приложение с помощью OpenTelemetry](/ru/clickstack/managed-onboarding/instrument-application-serverless): отправляйте данные новых или перенесённых сервисов напрямую в вашу конечную точку OTLP с помощью SDK OpenTelemetry, а остальное по-прежнему будут обслуживать агенты Datadog.
* [Подключение OpenTelemetry Collector](/ru/clickstack/managed-onboarding/setting-up-your-opentelemetry-collector-serverless): если вы также используете коллекторы OpenTelemetry, направьте их на тот же сервис.

* [Панели мониторинга](/ru/clickstack/observability/features/dashboards/overview) и [Оповещения](/ru/clickstack/observability/features/alerts): воссоздайте на тех же данных представления и мониторы, на которые вы опираетесь в Datadog.
