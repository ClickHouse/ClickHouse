Você pode usar o ClickPipes para ingerir dados do seu banco de dados MongoDB no ClickHouse Cloud. O banco de dados MongoDB de origem pode ser hospedado no seu próprio ambiente ou na nuvem, usando serviços como o MongoDB Atlas.

Os ClickPipes para MongoDB podem ser implantados e gerenciados manualmente usando a UI do ClickPipes, bem como de forma programática usando [OpenAPI](/pt-BR/integrations/clickpipes/programmatic-access/openapi) e [Terraform](/pt-BR/integrations/clickpipes/programmatic-access/terraform).

## Pré-requisitos {#prerequisites}

Para começar, primeiro você precisa garantir que seu banco de dados MongoDB esteja configurado corretamente para replicação. As etapas de configuração dependem de como o MongoDB está sendo implantado, portanto siga o guia correspondente abaixo:

1. [MongoDB Atlas](/pt-BR/integrations/clickpipes/mongodb/source/atlas)

2. [MongoDB genérico](/pt-BR/integrations/clickpipes/mongodb/source/generic)

3. [Amazon DocumentDB](/pt-BR/integrations/clickpipes/mongodb/source/documentdb)

Depois que o banco de dados MongoDB de origem estiver configurado, você poderá prosseguir com a criação do ClickPipe.

#### Configure as configurações avançadas {#advanced-settings}

Se necessário, você pode ajustar as configurações avançadas. Uma breve descrição de cada configuração é fornecida abaixo:

* **Intervalo de sincronização**: Este é o intervalo em que o ClickPipes consultará o banco de dados de origem em busca de alterações. Isso afeta o serviço ClickHouse de destino; para usuários com maior sensibilidade a custos, recomendamos manter esse valor mais alto (acima de `3600`).
* **Tamanho do lote de extração**: O número de linhas a serem buscadas em um único lote. Esta é uma configuração de melhor esforço e pode não ser aplicada em todos os casos.
* **Número de tabelas no snapshot em paralelo**: Este é o número de tabelas que serão buscadas em paralelo durante o snapshot inicial. Isso é útil quando você tem um grande número de tabelas e deseja controlar quantas tabelas serão buscadas em paralelo.

### Configure as tabelas {#configure-the-tables}

5. Aqui você pode selecionar o banco de dados de destino do seu ClickPipe. É possível selecionar um banco de dados existente ou criar um novo.

   <div className="ch-image-lg">
     <Frame>
       ![Selecionar o banco de dados de destino](/images/integrations/data-ingestion/clickpipes/mongodb/select-destination-db.webp)
     </Frame>
   </div>

6. Você pode selecionar as tabelas que deseja replicar do banco de dados MongoDB de origem. Ao selecionar as tabelas, você também pode renomeá-las no banco de dados ClickHouse de destino.

As coleções podem ser replicadas em dois modos:

* **Ingestão padrão**: os documentos são ingeridos no ClickHouse como estão, com o Tipo JSON. Nesse caso, a tabela de destino terá uma coluna dedicada para `id` e outra, `doc`, com o documento completo.
* **Ingestão estruturada**: os documentos são ingeridos como linhas em uma tabela que segue um schema comum para a coleção. Esse schema é inferido a partir de uma amostra no momento da criação do pipe. Para habilitar esse modo, ative a opção **Map document to columns** na coleção.

Quando a ingestão estruturada está habilitada, a seção **Column settings** lista os campos encontrados na amostra com seus tipos ClickHouse inferidos. Você pode selecionar quais campos replicar como colunas; a chave de documento `_id` é sempre incluída, com o tipo `String`.

<div className="ch-image-md">
  <Frame>
    ![Configurações de ingestão estruturada para uma coleção](/images/integrations/data-ingestion/clickpipes/mongodb/mongodb-structured-ingestion.webp)
  </Frame>
</div>

Como as coleções do MongoDB são polimórficas (ou seja, documentos de uma mesma coleção podem ter schemas diferentes), a ingestão estruturada precisa lidar com registros atípicos:

* **Campos ausentes:** todas as colunas estruturadas são ingeridas como `Nullable`; assim, se um documento não tiver um campo, a coluna correspondente terá o valor `NULL`.

* **Campos extras:** campos que não fazem parte do schema inferido são armazenados como JSON na coluna `_peerdb_malformed_data`, com uma chave por campo. Cada chave contém `"unexpected_field": true` e o valor original em `value`:

  ```json
  {
    "rating": {
      "unexpected_field": true,
      "value": 4.5
    }
  }
  ```

  Esses dados podem ser facilmente consultados e analisados. Por exemplo, para listar os campos inesperados encontrados em uma tabela:

  ```sql
  SELECT DISTINCT arrayJoin(JSONAllPaths(_peerdb_malformed_data)) AS malformed
  FROM movies
  WHERE malformed LIKE '%.unexpected_field';
  ```

  📝 Nota: se você não quiser que os valores de campos extras apareçam na coluna `_peerdb_malformed_data`, habilite a opção **Hide unexpected values** na coleção.

* **Incompatibilidade de tipo de campo:** valores cujo tipo não corresponde ao tipo da coluna também são armazenados na coluna `_peerdb_malformed_data`, com uma chave por campo. Cada chave contém `"type_mismatch": true` e o valor original em `value`. A coluna correspondente é definida como `NULL`:

  ```json
  {
    "year": {
      "type_mismatch": true,
      "value": "two thousand nineteen"
    }
  }
  ```

  Para ler um campo independentemente de seu valor corresponder ou não ao tipo esperado, combine a coluna com seu valor de fallback:

  ```sql
  SELECT name, coalesce(year, _peerdb_malformed_data.year.value)
  FROM movies;
  ```

📝 Nota: você pode considerar os campos incluídos em `_peerdb_malformed_data` como valores atípicos que recorrem à ingestão em coluna JSON.

Como a ingestão estruturada infere o schema antes da criação da tabela, habilitá-la permite definir expressões de particionamento e sorting keys personalizadas com base nas colunas estruturadas.
Todas as colunas estruturadas são ingeridas como `Nullable`. Leve isso em conta ao escrever uma expressão de chave de particionamento ou ao usá-las em uma sorting key. Nesses casos, a tabela de destino é criada com a configuração `allow_nullable_key`.

📝 Em ambos os modos de ingestão, você pode ativar a opção **Persist deleted documents** se quiser que os eventos de exclusão capturem os valores excluídos no ClickHouse de destino. Observe que isso exige que a coleção de origem tenha `changeStreamPreAndPostImage` habilitado.

## Ressalvas {#caveats}

Aqui estão algumas ressalvas a considerar ao usar este conector:

* Exigimos o MongoDB na versão 5.1.0 ou superior.
* Usamos a API nativa de Change Streams do MongoDB para CDC, que depende do oplog do MongoDB para capturar alterações em tempo real.
* Os documentos do MongoDB são replicados no ClickHouse como JSON type por padrão. Isso permite um gerenciamento flexível do esquema e possibilita o uso do amplo conjunto de operadores JSON do ClickHouse para consultas e análises. Você pode saber mais sobre como consultar dados JSON [aqui](/pt-BR/reference/data-types/newjson).
