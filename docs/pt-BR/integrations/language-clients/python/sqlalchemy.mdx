O ClickHouse Connect inclui o dialect SQLAlchemy `clickhousedb`, baseado no driver principal. O dialect síncrono oferece suporte ao SQLAlchemy 1.4.40 e versões posteriores, incluindo o SQLAlchemy 2.x, com foco em consultas Core, DDL do ClickHouse, reflexão e inserts simples de ORM. O dialect assíncrono requer o SQLAlchemy 2.0.44 ou posterior.

Instale as dependências do SQLAlchemy com o package extra:

```bash
pip install "clickhouse-connect[sqlalchemy]"
```

## Conecte-se ao SQLAlchemy {#sqlalchemy-connect}

Crie um motor usando a URL no formato `clickhousedb://` ou `clickhousedb+connect://`:

```python
from sqlalchemy import create_engine, text

engine = create_engine(
    "clickhousedb://user:password@host:8123/mydb?compression=zstd"
)

with engine.connect() as conn:
    version = conn.execute(text("SELECT version()")).scalar_one()
    print(version)
```

Use esses formatos explícitos de URL quando o `clickhouse-sqlalchemy` também estiver instalado.
Importar `clickhouse_connect.cc_sqlalchemy` mantém o registro de `clickhouse://`
desse pacote. Se outro provedor instalado impedir o registro do nosso alias,
a importação emite um `UserWarning` recomendando o uso de uma URL explícita do
ClickHouse Connect. Registros existentes em tempo de execução permanecem inalterados, sem
nenhum aviso. Se nenhum outro provedor reivindicar `clickhouse://`, essa importação o disponibiliza
como um alias de compatibilidade do ClickHouse Connect.

### IDs de sessão do ClickHouse {#sqlalchemy-session-ids}

Por padrão, cada conexão do pool, tanto no dialect síncrono quanto no assíncrono, gera um ID de sessão do ClickHouse distinto. Quando as requisições dessa conexão chegam ao mesmo processo do servidor ClickHouse, as configurações alteradas com `SET` e as tabelas temporárias persistem nessa conexão. O estado das sessões nomeadas e as verificações de sobreposição dentro da mesma sessão são locais a cada processo. Em um mesmo processo do servidor, uma requisição sobreposta para o mesmo usuário e ID de sessão é rejeitada imediatamente com o código de servidor 373, em vez de ser enfileirada. Se você configurar um `session_id` fixo, use `pool_size=1, max_overflow=0` ou serialize o acesso antes que as requisições cheguem ao ClickHouse. No ClickHouse Cloud ou em outras implantações com balanceamento de carga, requisições com o mesmo ID de sessão podem chegar a servidores diferentes; portanto, não use um `session_id` fixo como estado distribuído nem como mutex distribuído.

### Conexões assíncronas {#sqlalchemy-async-connections}

O dialect assíncrono requer o SQLAlchemy 2.0.44 ou posterior e usa o `AsyncClient` nativo do ClickHouse Connect. Instale as dependências dele e crie um motor assíncrono com a URL `clickhousedb+async://`:

```bash
pip install "clickhouse-connect[sqlalchemy-async]"
```

```python
import asyncio

from sqlalchemy import text
from sqlalchemy.ext.asyncio import create_async_engine


async def main():
    engine = create_async_engine(
        "clickhousedb+async://user:password@host:8123/mydb"
    )
    try:
        async with engine.connect() as conn:
            version = (await conn.execute(text("SELECT version()"))).scalar_one()
            print(version)
    finally:
        await engine.dispose()


asyncio.run(main())
```

Os resultados são armazenados em buffer. Os cursores do lado do servidor estão desabilitados, portanto `AsyncConnection.stream()` gera `InvalidRequestError`. O SQLAlchemy aceita `AsyncSession.stream()`, mas o dialect armazena o resultado completo em buffer antes de retorná-lo. Para resultados grandes, use os métodos de streaming nativos do `AsyncClient`. O cliente nativo bruto fica disponível como `driver_connection` enquanto a conexão SQLAlchemy correspondente estiver em uso:

```python
async def stream_events(engine):
    async with engine.connect() as conn:
        raw_connection = await conn.get_raw_connection()
        client = raw_connection.driver_connection
        async with await client.query_rows_stream("SELECT * FROM events") as rows:
            async for row in rows:
                print(row)
```

Não use a conexão do SQLAlchemy simultaneamente com seu cliente bruto. Conclua os streams do cliente bruto antes de sair do bloco de conexão do SQLAlchemy e não mantenha o cliente bruto depois que a conexão retornar ao pool. O SQLAlchemy é responsável pelo ciclo de vida do cliente emprestado, portanto nunca chame `client.close()` nem qualquer um de seus métodos privados de ciclo de vida. O pool do SQLAlchemy é responsável pela concorrência das conexões. Cada conexão do pool possui um cliente assíncrono nativo e, por padrão, limita o connector aiohttp a uma conexão no total e a uma conexão por host. Defina `connector_limit`, `connector_limit_per_host` ou `keepalive_timeout` na URL ou em `connect_args` para substituir essas configurações de transporte. Com `pool_pre_ping=True`, o SQLAlchemy verifica as conexões reutilizadas com `SELECT 1` sempre que uma conexão é retirada do pool.

Atualmente, inserções assíncronas via executemany do SQLAlchemy enviam uma requisição HTTP para cada conjunto de parâmetros, em vez de usar o protocolo Native de inserção em massa do driver. Use essa abordagem apenas para lotes pequenos. Para grandes volumes de dados, use o padrão de acesso ao `driver_connection` pertencente ao pool, descrito acima, e aguarde (`await`) `client.insert()` antes de devolver a conexão do SQLAlchemy ao pool. Como o executemany assíncrono usa binding de parâmetros de consulta, valores `datetime` sem fuso horário seguem `naive_datetime_binding`, e não a configuração `naive_datetime_insert` usada pelo executemany Native síncrono. Binds tipados de `DateTime64` do SQLAlchemy preservam frações de segundo tanto com parâmetros do lado do cliente quanto do lado do servidor. Parâmetros não tipados `%s` ou `%(name)s` passados para `exec_driver_sql()` mantêm a formatação padrão em segundos inteiros para valores `datetime` sem fuso horário. Use valores com fuso horário para evitar ambiguidades no tratamento de fusos horários. Use `client.insert()` para obter a semântica Native de inserção em massa.

Crie e descarte um motor assíncrono no mesmo event loop em que ele é usado. Devolva todas as conexões obtidas e, em seguida, aguarde `engine.dispose()` durante o encerramento e antes de usar o motor em outro event loop. Se o loop proprietário do motor já tiver sido fechado, aguarde `engine.dispose()` no loop atual antes de reutilizá-lo. O aiohttp ainda pode reportar um transporte não fechado quando a limpeza só começa depois que o loop proprietário foi fechado; portanto, sempre que possível, descarte o motor antes da transferência. `pool_pre_ping=True` não substitui o descarte ao mover um motor assíncrono com pool entre event loops. Para compartilhar um único motor entre event loops sem reter conexões vinculadas a um loop, configure `poolclass=NullPool`. Se o descarte for executado enquanto uma conexão ainda estiver em uso, o dialect fechará essa conexão quando ela for devolvida ou coletada pelo garbage collector. Não chame `engine.sync_engine.dispose()` a partir de código síncrono. Nesse contexto, o SQLAlchemy não consegue aguardar a limpeza assíncrona das conexões e pode apenas registrar o erro em log em vez de fechar os transportes do pool.

Os parâmetros de consulta da URL podem conter configurações do ClickHouse, opções do cliente ClickHouse Connect, como `compression`, `query_limit` e tempos limite, ou opções HTTP/TLS, como `ca_cert`. Quando necessário, adicione o prefixo `ch_` a uma configuração do ClickHouse para forçar que ela seja tratada como configuração de servidor, por exemplo `ch_http_max_field_name_size=99999`.

Consulte [Argumentos de conexão e configurações](/pt-BR/integrations/language-clients/python/driver-api#connection-arguments) para ver as opções de cliente disponíveis.

Execute helpers síncronos do SQLAlchemy, como DDL e inspeção, por meio de `AsyncConnection.run_sync()`:

```python
from sqlalchemy import inspect


async def prepare_schema(engine, metadata):
    async with engine.begin() as conn:
        await conn.run_sync(metadata.create_all)
        return await conn.run_sync(
            lambda sync_conn: inspect(sync_conn).get_table_names()
        )
```

### Configurações por consulta {#sqlalchemy-per-query-settings}

Passe as configurações do ClickHouse nas opções de execução do SQLAlchemy. As configurações podem ser definidas em um engine, em uma conexão ou em uma instrução. O valor definido na instrução tem precedência sobre o valor definido na conexão ou no engine com a mesma chave.

```python
from sqlalchemy import text

stmt = text("SELECT getSetting('max_threads')").execution_options(
    settings={"max_threads": 2}
)

with engine.connect() as conn:
    value = conn.execute(stmt).scalar_one()
```

### Formatos de leitura por consulta {#sqlalchemy-per-query-read-formats}

Defina os formatos de leitura do ClickHouse em um engine, uma conexão ou uma instrução usando as opções de execução do SQLAlchemy com `query_formats`. Os formatos da instrução são aplicados primeiro e substituem as chaves e os wildcards correspondentes da conexão ou do engine.

```python
from sqlalchemy import text

stmt = text("SELECT user_uuid FROM users").execution_options(
    query_formats={"UUID": "string"}
)

with engine.connect() as conn:
    rows = conn.execute(stmt).all()
```

### Tratamento de erros {#sqlalchemy-error-handling}

Os erros gerados pelo driver por meio de uma conexão SQLAlchemy usam as classes DB-API exportadas de `clickhouse_connect.dbapi`. Elas são os mesmos objetos de classe que as classes correspondentes em `clickhouse_connect.driver.exceptions`, portanto o SQLAlchemy as encapsula na subclasse `sqlalchemy.exc.DBAPIError` correspondente. `StreamFailureError` é um `OperationalError` e é encapsulado como `sqlalchemy.exc.OperationalError`.

Se uma tabela não existir, a inspeção de colunas e a reflexão de tabelas lançam `sqlalchemy.exc.NoSuchTableError`. Essa exceção também herda de `sqlalchemy.exc.NoResultFound`, de modo que os handlers existentes continuam a capturá-la. A mensagem é `Table <database>.<table_name> does not exist`.

A execução de SQL segue a [política de retentativas HTTP](/pt-BR/integrations/language-clients/python/driver-api#http-retries) do driver. Inserções em massa Native usam a [política de retentativas de insert](/pt-BR/integrations/language-clients/python/advanced-inserting#insert-retries-and-deduplication).

Se um cancelamento vindo do chamador puder interromper uma chamada explícita a `AsyncConnection.invalidate()`, execute a invalidação em uma tarefa própria e aguarde a conclusão dessa tarefa antes de propagar o cancelamento. Assim, o SQLAlchemy consegue concluir a atualização interna do registro de conexão:

```python
import asyncio


async def invalidate_safely(connection):
    invalidate_task = asyncio.create_task(connection.invalidate())
    cancellation = None
    while not invalidate_task.done():
        try:
            await asyncio.wait({invalidate_task})
        except asyncio.CancelledError as ex:
            cancellation = ex
    if cancellation is not None:
        try:
            invalidate_task.result()
        finally:
            raise cancellation
    invalidate_task.result()
```

Não use a conexão enquanto a tarefa de invalidação ainda estiver em execução. Se uma chamada direta a `await connection.invalidate()` for cancelada e `connection.invalidated` continuar como `false`, execute `await connection.invalidate()` novamente para concluir a limpeza antes de usar ou fechar a conexão.

### Parâmetros do lado do servidor {#sqlalchemy-server-side-parameters}

O SQLAlchemy normalmente renderiza parâmetros do lado do cliente. Ative os parâmetros do lado do servidor do ClickHouse ao criar a engine:

```python
engine = create_engine(
    "clickhousedb://user:password@host:8123/mydb",
    server_side_params=True,
)
```

Use o mesmo argumento `server_side_params=True` com `create_async_engine()` para o dialect assíncrono.

Neste modo, cada valor vinculado deve ter um tipo do SQLAlchemy compatível com o ClickHouse. Listas `IN` compatíveis se tornam parâmetros `Array` tipados do ClickHouse. O compilador gera `CompileError` quando não consegue inferir um tipo compatível nem processar um parâmetro associado com segurança.

Os nomes dos parâmetros associados devem ser nomes ASCII BareWord do ClickHouse. Nomes que começam e terminam com `$` são rejeitados porque o driver Core os reserva para parâmetros de consulta binários brutos.

## Consultas do Core {#sqlalchemy-core-queries}

O dialeto oferece suporte a consultas `SELECT` do SQLAlchemy Core com junções, filtros, ordenação, cláusulas `LIMIT` e `OFFSET`, `DISTINCT` e instruções SELECT compostas.

`union()`, `intersect()` e `except_()` do SQLAlchemy são compilados para `UNION DISTINCT`, `INTERSECT DISTINCT` e `EXCEPT DISTINCT` do ClickHouse. Seus equivalentes `union_all()`, `intersect_all()` e `except_all()` são compilados para os operadores `ALL` correspondentes. Esse mapeamento explícito preserva a semântica de duplicatas do SQLAlchemy independentemente dos padrões de operações de conjunto do ClickHouse.

```python
from sqlalchemy import MetaData, Table, select

metadata = MetaData(schema="mydb")
users = Table("users", metadata, autoload_with=engine)
orders = Table("orders", metadata, autoload_with=engine)
events = Table("events", metadata, autoload_with=engine)

stmt = (
    select(users.c.name, orders.c.product)
    .select_from(users.join(orders, users.c.id == orders.c.user_id))
    .order_by(users.c.name)
    .limit(10)
)

with engine.connect() as conn:
    rows = conn.execute(stmt).all()
```

Há suporte a Lightweight `DELETE` e ele exige uma cláusula `WHERE` explícita:

```python
from sqlalchemy import delete

stmt = delete(users).where(users.c.name.like("%temporary%"))
with engine.connect() as conn:
    conn.execute(stmt)
```

### Renderização de literais {#sqlalchemy-literal-rendering}

Quando o SQLAlchemy insere um valor vinculado diretamente na consulta por meio de `literal_binds` ou `literal_execute`, o dialeto usa a delimitação do ClickHouse para tipos String genéricos e tipos do ClickHouse. Isso também se aplica a wrappers `TypeDecorator` e seleções `with_variant()`. Os valores String preservam sinais de porcentagem e barras invertidas, mesmo quando outros parâmetros vinculados permanecem.

Valores `datetime` do Python com um tipo SQLAlchemy `DateTime64` do ClickHouse preservam os microssegundos em parâmetros do lado do cliente e em literais inseridos diretamente na consulta, incluindo valores Nullable e valores aninhados em arrays e tuplas. O ClickHouse aplica a precisão declarada. O `datetime` do Python fornece até seis dígitos fracionários. Valores `DateTime` simples mantêm a formatação em segundos inteiros. Para uma instrução `text()`, informe o tipo explicitamente com `bindparam("ts", type_=DateTime64(6))` para preservar as frações de segundo.

Um valor `pandas.Timestamp` vinculado com `DateTime64(9)` preserva os nanossegundos em parâmetros e em literais inseridos diretamente na consulta.

Os tipos de coluna do SQLAlchemy devem corresponder ao schema do servidor. Declarar `DateTime64` para uma coluna `DateTime` do servidor faz com que frações de segundo sejam renderizadas e pode gerar erros de conversão na inserção e em comparações `IN`.

No SQLAlchemy 2.x, literais inseridos diretamente na consulta de tipos `sqlalchemy.ARRAY` genéricos que contêm itens `Tuple` do ClickHouse exigem `dimensions=1` (ou uma contagem de dimensões maior, conforme apropriado para arrays aninhados) para que o SQLAlchemy trate cada tupla como um único item. O SQLAlchemy 1.4 não oferece suporte a literais inseridos diretamente na consulta para tipos `ARRAY` genéricos.

Parâmetros `Tuple` nomeados e tipados aceitam dicionários cujas chaves correspondam exatamente aos campos declarados. O cliente usa a ordem dos campos definida na declaração para parâmetros vinculados e literais inseridos diretamente na consulta, incluindo tuplas nomeadas dentro de arrays e de outras tuplas. Isso se aplica a inserções síncronas e assíncronas, a predicados e a ambos os modos de parâmetro. Campos ausentes ou extras lançam `ProgrammingError` na vinculação de parâmetros de consulta. As inserções em lote nativas mantêm o tratamento atual. Dicionários passados para parâmetros sem tipo de `exec_driver_sql()` mantêm a formatação JSON ou map configurada.

Para tuplas nomeadas dentro de valores `Map`, defina `common.set_setting("dict_parameter_format", "map")`. Isso também preserva as frações de segundo de valores `DateTime64` tipados dentro de maps em parâmetros vinculados e em literais inseridos diretamente na consulta.

Se um parâmetro datetime nomeado for reutilizado, cada ocorrência precisa de um tipo de vinculação `DateTime64` compatível para preservar as frações de segundo. Uma ocorrência sem tipo ou com um tipo conflitante mantém a formatação em segundos inteiros. Defina `type_=DateTime64(6)` em cada `bindparam` ou use nomes de parâmetros distintos com os tipos apropriados.

O mesmo vale para um nome de vinculação reutilizado cujas ocorrências de `Tuple` nomeada declaram nomes de campos diferentes. Nesse caso, o cliente passa a tratar esse nome de forma posicional, de modo que um valor de dicionário não é reordenado e o servidor o rejeita. Use nomes de parâmetros distintos ou passe uma tupla posicional.

### Tuplas nomeadas {#sqlalchemy-named-tuples}

Declare os campos de uma tupla nomeada com um mapeamento `elements`. As chaves devem ser strings não vazias, e os valores podem ser classes de tipo do ClickHouse SQLAlchemy ou instâncias já configuradas. Os campos preservam a ordem de iteração do mapeamento, e os nomes são colocados entre aspas automaticamente.

```python
from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import String, Tuple, UInt32

details_type = Tuple(elements={"user_id": UInt32, "display name": String()})
# Tuple(`user_id` UInt32, `display name` String)
```

Use `Tuple(UInt32, String)` ou `Tuple(elements=[UInt32, String])` para tuplas não nomeadas. Não é possível combinar elementos posicionais com a palavra-chave `elements`.

### type hints de JSON {#sqlalchemy-json-type-hints}

Declare JSON paths tipados com o mapeamento `typed_paths`. O tipo de um path pode ser uma classe de tipo do ClickHouse SQLAlchemy, uma instância configurada ou uma string com o nome de um tipo do ClickHouse. Strings com nomes de tipos permitem usar tipos sem construtor no SQLAlchemy, como `Dynamic`, e também podem ser usadas para expressões de tipos configurados complexos.

Strings com nomes de tipos podem conter tipos JSON aninhados configurados, como ``Array(JSON(`child` UInt32))``. Os nomes de tipos reconhecidos do ClickHouse são case-insensitive nessas strings e são emitidos com sua capitalização canônica. Uma string deve conter uma única expressão de tipo completa. Texto trailing e argumentos JSON aninhados malformados são rejeitados.

Um `Tuple()` vazio não é suportado como JSON path tipado, pois o ClickHouse não consegue serializá-lo pelo Native format de uma coluna JSON. O driver principal suporta `Tuple()` em colunas de consulta e de insert em qualquer posição, inclusive aninhado em tuplas positional ou nomeadas, dentro de `Array` e como `Nullable(Tuple())` quando o servidor permitir.

```python
from sqlalchemy import Column, MetaData, Table

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import JSON, UInt32

events = Table(
    "events",
    MetaData(),
    Column(
        "payload",
        JSON(
            typed_paths={
                "event.id": UInt32,
                "details": "Tuple(id UInt32, label Nullable(String))",
                "attributes": "Variant(String, Array(String))",
            },
            max_dynamic_paths=256,
            max_dynamic_types=16,
            skip_paths=["internal.debug"],
            skip_regexps=[r"^private\."],
        ),
    ),
)
```

Para caminhos que sejam identificadores Python simples, os argumentos nomeados são uma forma abreviada de `typed_paths`, por exemplo `JSON(user_id=UInt32)`. Use `typed_paths` para caminhos com pontos, espaços, backticks, pontos codificados como `%2E` ou nomes que coincidam com opções do construtor. Um caminho tipado chamado `SKIP` é suportado por meio do mapeamento. As chaves em `typed_paths` e os valores em `skip_paths` são nomes decodificados. Backticks e aspas duplas no início ou no fim são tratados como caracteres literais do caminho, e não como delimitação SQL já aplicada. Dentro de uma string de tipo bruta, backticks e aspas duplas são sintaxe de identificador do ClickHouse.

É possível configurar até 1000 caminhos tipados. `max_dynamic_paths` aceita valores de 0 a 10000. `max_dynamic_types` aceita valores de 0 a 254. Esses intervalos também se aplicam dentro de strings de tipo JSON aninhado brutas. Os padrões explícitos do servidor, 1024 e 32, são omitidos do DDL gerado. Caminhos de skip simples são deduplicados. As strings de expressão regular não são validadas pelo Python, pois o ClickHouse usa a sintaxe RE2. Expressões regulares duplicadas são preservadas.

Um caminho de skip simples não pode se chamar exatamente `REGEXP`, porque o ClickHouse reserva esse token para `SKIP REGEXP`. Nomes como `REGEXP_foo` continuam válidos. Em uma string de tipo JSON bruta, um operando `SKIP` simples deve ser um identificador do ClickHouse ou um identificador composto separado por pontos. Um identificador composto sem delimitação não pode começar com `REGEXP`; delimite esse primeiro componente quando ele for dado de caminho. `SKIP REGEXP` deve ter um único literal de string entre aspas simples. Delimite as partes do identificador com backticks ou aspas duplas quando elas contiverem espaços ou pontuação. Os type hints de JSON bruto suportam `Variant(...)`; o `Variant` standalone não tem construtor público no SQLAlchemy. Os membros de `Variant` são ordenados e deduplicados pelos mesmos nomes canônicos usados pelo ClickHouse.

O construtor ordena os argumentos na mesma forma canônica retornada pelo ClickHouse. Tipos refletidos, cópias de tipos do SQLAlchemy e a autogeração do Alembic preservam a configuração.

### Subcolunas JSON {#sqlalchemy-json-subcolumns}

Para uma coluna declarada ou refletida como `JSON` do ClickHouse, use colchetes para selecionar, de cada vez, um segmento do caminho de uma subcoluna com suporte de armazenamento:

```python
from sqlalchemy import Column, MetaData, Table, select

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import JSON, UInt32

events = Table(
    "events",
    MetaData(),
    Column("payload", JSON),
)

request_id = events.c.payload["context"]["request"].subcolumn(
    "id",
    type_=UInt32,
)

stmt = select(
    events.c.payload["severity"].label("severity"),
    request_id.label("request_id"),
)
```

`payload["severity"]` é compilado na sintaxe de identificador pontilhado do ClickHouse. Cada parte é colocada entre aspas separadamente, por exemplo `` `events`.`payload`.`severity` ``. Ele lê a subcoluna JSON armazenada do ClickHouse e não chama `getSubcolumn`. Encadeie `[]` ou `.subcolumn()` uma vez para cada segmento do caminho. Cada segmento deve ser uma string não vazia.

Passar `type_` para `.subcolumn()` envolve o caminho pontilhado em um `CAST` SQL e atribui esse tipo à expressão do SQLAlchemy. Sem `type_`, `.subcolumn("segment")` se comporta como `["segment"]`.

Um caminho sem tipo tem o tipo `Dynamic` do ClickHouse. O ClickHouse não permite valores `Dynamic` diretamente em `ORDER BY` ou `GROUP BY`. Passe `type_` quando uma subcoluna for usada nesses contextos.

Para código com tipagem estática, importe `json_subcolumn` de `clickhouse_connect.cc_sqlalchemy`. O auxiliar também aceita um segmento por vez e preserva o tipo de resultado Python de `type_`:

```python
from clickhouse_connect.cc_sqlalchemy import json_subcolumn

context = json_subcolumn(events.c.payload, "context")
request = json_subcolumn(context, "request")
request_id = json_subcolumn(request, "id", type_=UInt32)
```

Neste exemplo, os verificadores de tipo interpretam `request_id` como `ColumnElement[int]`.

Cada segmento é colocado entre backticks independentemente, inclusive nomes com espaços ou backticks. Os backticks não fazem com que um ponto seja tratado como literal pelo processamento de JSON path do ClickHouse. Quando `json_type_escape_dots_in_keys` estiver habilitado, use a codificação `%2E` do ClickHouse para pontos literais em chaves. Acesse uma chave chamada `a.b` como `payload["a%2Eb"]`, e não como `payload["a.b"]`.

### Extensões de consulta do ClickHouse {#sqlalchemy-query-extensions}

Importe `select` de `clickhouse_connect.cc_sqlalchemy` para expor métodos tipados do ClickHouse a verificadores estáticos de tipos. O `sqlalchemy.select` padrão também disponibiliza esses métodos em tempo de execução.

```python
from clickhouse_connect.cc_sqlalchemy import select

stmt = (
    select(events.c.user_id, events.c.event_type)
    .final()
    .prewhere(events.c.event_date >= "2026-01-01")
    .sample(0.1)
    .limit_by([events.c.user_id], 3)
)
```

Os métodos `Select` do ClickHouse são:

| Método                                   | Recurso SQL                                                                         |
| ---------------------------------------- | ----------------------------------------------------------------------------------- |
| `.final()`                               | `FINAL` aplicado a uma tabela                                                       |
| `.sample(value)`                         | `SAMPLE`, usando uma fração, contagem de linhas ou uma expressão                    |
| `.prewhere(expression)`                  | `PREWHERE`; chamadas repetidas são combinadas com `AND`                             |
| `.limit_by(columns, limit, offset=None)` | `LIMIT ... BY`                                                                      |
| `.array_join(...)`                       | `ARRAY JOIN`                                                                        |
| `.left_array_join(...)`                  | `LEFT ARRAY JOIN`                                                                   |
| `.ch_join(...)`                          | junções do ClickHouse com opções de `strictness`, `distribution`, `using` e `cross` |
| `.cte(name, materialized=True)`          | `WITH name AS MATERIALIZED (...)`                                                   |

O `Select.with_hint()` do SQLAlchemy é uma API de indicações de tabela. O dialeto do ClickHouse não renderiza indicações de tabela. Uma indicação wildcard ou `clickhousedb` aplicável emite um `SAWarning` e deixa o SQL gerado inalterado. Use `final()`, `sample()`, `prewhere()` ou `limit_by()` para essas cláusulas do ClickHouse.

`Select.with_statement_hint()` é uma API de diretiva bruta de sufixo. Ela acrescenta o texto fornecido ao final do `SELECT` sem validação específica do ClickHouse. Ela continua disponível para SQL estático confiável, como `SETTINGS max_threads=1`:

```python
stmt = select(events.c.id).with_statement_hint("SETTINGS max_threads=1")
```

Para as configurações do ClickHouse, prefira opções de execução para que o driver as processe separadamente do texto SQL:

```python
stmt = select(events.c.id).execution_options(settings={"max_threads": 1})
```

Por exemplo, é possível encadear um `GLOBAL ANY LEFT JOIN` do ClickHouse sem aninhar uma `FromClause` personalizada:

```python
stmt = (
    select(events.c.id, users.c.name)
    .select_from(events)
    .ch_join(
        users,
        events.c.user_id == users.c.id,
        isouter=True,
        strictness="ANY",
        distribution="GLOBAL",
    )
)
```

Use a construção explícita `Lambda` nas funções de ordem superior do ClickHouse:

```python
from sqlalchemy import column, func

from clickhouse_connect.cc_sqlalchemy import Lambda, select

stmt = select(
    func.arrayMap(
        Lambda("x", column("x") * 2),
        events.c.metrics,
    ).label("doubled")
)
```

A construção padrão `values()` do SQLAlchemy é compilada para a sintaxe da função de tabela `VALUES` do ClickHouse, inclusive quando usada em uma expressão de tabela comum. A forma CTE exige o SQLAlchemy 2.0.42 ou posterior, no qual `Values.cte()` foi adicionada.

### CTEs materializadas {#sqlalchemy-materialized-ctes}

Por padrão, o ClickHouse expande uma expressão de tabela comum em linha; portanto, o corpo de uma CTE referenciada mais de uma vez é executado uma vez para cada referência. Passe `materialized=True` para `.cte()` a fim de gerar `WITH <name> AS MATERIALIZED (...)`, que calcula o corpo uma única vez:

```python
from sqlalchemy import func

from clickhouse_connect.cc_sqlalchemy import select

ranked = (
    select(book.c.book_id, func.row_number().over(order_by=book.c.score.desc()).label("result_rank"))
    .where(book.c.genre == "sci-fi")
    .order_by(book.c.score.desc())
    .limit(100)
    .cte("ranked", materialized=True)
)

stmt = (
    select(book.c.book_id, ranked.c.result_rank)
    .select_from(book)
    .ch_join(ranked, book.c.book_id == ranked.c.book_id, strictness="ANY")
    .where(book.c.book_id.in_(select(ranked.c.book_id)))
    .execution_options(settings={"enable_materialized_cte": 1, "enable_analyzer": 1})
)
```

O servidor materializa a CTE somente quando a palavra-chave está presente, `enable_materialized_cte=1`, e o analyzer está habilitado. Defina `enable_materialized_cte` na instrução, na conexão ou no engine, conforme mostrado em [Configurações por consulta](#sqlalchemy-per-query-settings). O analyzer é habilitado por padrão em todos os servidores compatíveis com esse recurso; portanto, definir explicitamente `enable_analyzer=1` é uma medida de precaução. `enable_materialized_cte` é uma configuração experimental do ClickHouse. Com `enable_materialized_cte=0` ou `enable_analyzer=0`, a consulta é executada com êxito e retorna as mesmas linhas. O ClickHouse ignora silenciosamente `MATERIALIZED` e volta a expandir a CTE inline; assim, esquecer essa configuração prejudica o desempenho sem emitir nenhum aviso. CTEs materializadas exigem o ClickHouse 26.3 ou posterior. Servidores mais antigos rejeitam a palavra-chave com um erro de sintaxe.

Para uma instrução criada com o `sqlalchemy.select` padrão, use `cte()` no nível do módulo. Ela recebe a instrução como primeiro argumento e, no restante, espelha `Select.cte()`:

```python
from sqlalchemy import select as sa_select

from clickhouse_connect.cc_sqlalchemy import cte

ranked = cte(sa_select(book.c.book_id), "ranked", materialized=True)
```

A palavra-chave é renderizada apenas no dialeto ClickHouse, portanto uma instrução compartilhada com outro backend é compilada nele sem alterações.

O ClickHouse não oferece suporte a CTEs materializadas recursivas. Os helpers do SQLAlchemy geram um `ValueError` quando `recursive=True` e `materialized=True` são definidos.

## DDL e reflexão {#sqlalchemy-ddl-reflection}

O ClickHouse Connect fornece tipos de dados do ClickHouse, motores de tabela, estruturas de dicionário, DDL de banco de dados e reflexão de tabela.

`Inspector.get_table_names()` inclui todos os tipos de visão por questões de compatibilidade. `MetaData.reflect()` os inclui por padrão, e `only` permite selecionar uma visão pelo nome. Use `Inspector.get_view_names()` para visões não materializadas e `Inspector.get_materialized_view_names()` para visões materializadas. Ambos os métodos aceitam `schema` e funcionam no SQLAlchemy 1.4.40 e posteriores, incluindo o 2.x. `Inspector.get_view_definition()` retorna o `SELECT` armazenado de uma visão ou visão materializada e lança `NoSuchTableError` para tabelas e nomes inexistentes. Uma visão refletida não possui motor. Sua `Table` contém `clickhousedb_table_type` definido como `view`, `materialized_view`, `window_view` ou `live_view`.

`Nullable()` e `LowCardinality()` de `clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes` aceitam uma classe ou instância de tipo SQLAlchemy do ClickHouse e preservam seu tipo concreto para os verificadores de tipo. Por exemplo, `Nullable(String)` retorna uma instância de `String` e pode ser passada diretamente para `Column`. Os verificadores de tipo inferem `list[String]` para `[Nullable(String)]`. Se a lista também contiver outros tipos do ClickHouse, anote-a como `list[ChSqlaType]` e importe `ChSqlaType` de `clickhouse_connect.cc_sqlalchemy.datatypes.base`.

Colunas `Variant` standalone são refletidas por meio de um tipo interno do SQLAlchemy, e a geração automática do Alembic preserva seus nomes de tipo brutos canônicos sem alterações de tipo repetidas. Colunas `Geometry` e `MultiPoint` são refletidas como tipos públicos do SQLAlchemy.

```python
import sqlalchemy as db
from sqlalchemy import MetaData

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import DateTime64, String, UInt32
from clickhouse_connect.cc_sqlalchemy.ddl.custom import CreateDatabase
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import MergeTree

with engine.connect() as conn:
    conn.execute(CreateDatabase("example_db", exists_ok=True))

    metadata = MetaData(schema="example_db")
    events = db.Table(
        "events",
        metadata,
        db.Column("id", UInt32, primary_key=True),
        db.Column("user", String),
        db.Column("created_at", DateTime64(3)),
        MergeTree(order_by="id"),
    )
    events.create(conn)

    reflected = db.Table("events", MetaData(schema="example_db"), autoload_with=conn)
    assert reflected.engine is not None
```

As colunas refletidas incluem `server_default` para expressões `DEFAULT`. Objetos
refletidos do SQLAlchemy usam opções específicas do dialect, como `clickhousedb_codec`,
`clickhousedb_ttl`, `clickhousedb_materialized` e `clickhousedb_alias`, quando presentes.
Os dicionários públicos retornados por `Inspector.get_columns()` mantêm as
chaves `clickhouse_*` correspondentes. Nesses dicionários, `server_default`,
`clickhouse_materialized`, `clickhouse_alias` e `clickhouse_ttl` são strings SQL.
Para construir uma `Column` a partir delas, envolva cada uma em `sqlalchemy.text()`.

Use `clickhousedb_*` em novas declarações de tabelas e colunas. Os metadados gerados
pelo driver e as revisões do Alembic usam esses nomes. O ClickHouse Connect também lê
opções legadas `clickhouse_*` explícitas, mas o SQLAlchemy as valida em relação ao
dialect ao qual `clickhouse` pertence. Em uma instalação mista, opções do ClickHouse Connect
como `clickhouse_engine`, `clickhouse_ttl`, `clickhouse_settings`,
`clickhouse_table_type` e `clickhouse_dictionary_*` podem lançar `ArgumentError`.
Renomeie-as para `clickhousedb_*`.

O ClickHouse Connect lê valores padrão somente de `clickhousedb`. Registre-os com
`Table.argument_for("clickhousedb", ...)` ou
`Column.argument_for("clickhousedb", ...)`. Argumentos de operações do Alembic, como
`op.add_column(..., clickhouse_settings={...})`, mantêm seus nomes atuais.

Valores de string nas cláusulas `DEFAULT`, `MATERIALIZED`, `ALIAS` e `TTL` usam o escaping de strings do ClickHouse. O mesmo escaping se aplica a comentários de tabelas, dicionários e colunas, incluindo comentários emitidos pelo Alembic.

Argumentos de chave do MergeTree, como `order_by`, `partition_by`, `primary_key`, `sample_by` e `ttl`, aceitam colunas do SQLAlchemy e expressões SQL, bem como strings simples.

`Memory()`, `Log()`, `StripeLog()`, `TinyLog()`, `Null()` e `Set()` aceitam zero argumentos e fazem a ida e volta pela geração automática do Alembic sem perdas. O argumento de dicionário existente continua compatível. Use `settings={...}` para definir configurações do motor.

`SummingMergeTree` e `ReplicatedSummingMergeTree` aceitam um argumento `columns` opcional, que só pode ser passado por palavra-chave. Os argumentos posicionais existentes mantêm o mesmo significado, portanto `SummingMergeTree("id")` continua definindo `ORDER BY id`.

```python
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import SummingMergeTree

engine_clause = SummingMergeTree("id", columns=("delta", "n_tx"))
# Sum delta and n_tx for rows with the same id.
```

Passe uma string, uma coluna do SQLAlchemy, um atributo de coluna mapeada ou uma lista ou tupla não vazia desses valores. Strings em listas e tuplas são colocadas entre aspas como identificadores. Uma string escalar fornece SQL bruto, como `"delta"` ou `"(delta, n_tx)"`. O servidor exige identificadores para essas colunas. Omita `columns` para que o ClickHouse selecione as colunas a serem somadas. A reflexão e a geração automática do Alembic preservam uma lista de colunas explícita.

## Inserções e uso básico de ORM {#sqlalchemy-inserts}

Há suporte a inserções com o Core e a modelos ORM simples. Para o dialect síncrono, prefira inserções com executemany do Core para fluxos de dados em massa compatíveis. Para inserções em massa assíncronas, use o caminho nativo `AsyncClient.insert()` descrito em [Conexões assíncronas](#sqlalchemy-async-connections).

```python
with engine.connect() as conn:
    conn.execute(
        events.insert(),
        [
            {"id": 13, "user": "user_1"},
            {"id": 79, "user": "user_2"},
        ],
    )
```

Com o dialect síncrono, inserções `executemany` simples do Core geradas pelo compilador do SQLAlchemy usam uma única inserção em massa Native. O `executemany` assíncrono envia uma requisição por conjunto de parâmetros, conforme descrito em [Conexões assíncronas](#sqlalchemy-async-connections). SQL bruto e inserções com expressões ou outras semânticas que não podem ser encaminhadas com segurança preservam o SQL original e são executados uma vez para cada conjunto de parâmetros. Se um conjunto de parâmetros posterior falhar, as linhas gravadas pelos conjuntos de parâmetros anteriores permanecem confirmadas.

Instruções explícitas de múltiplas linhas `insert(events).values([...])` funcionam com linhas em formato de dicionário, tuplas na ordem das colunas da tabela e expressões SQL por linha. O `to_sql(method="multi")` do Pandas usa esse formato. Ele insere as linhas, mas retorna `0`, porque instruções INSERT textuais informam uma contagem de linhas igual a `0` por meio do cursor da DB-API. O SQLAlchemy determina a lista de colunas a partir da primeira linha. Chaves de dicionário extras em linhas posteriores e valores de tupla fora da lista de colunas selecionada são ignorados. Se uma linha posterior não tiver um dos valores selecionados, a compilação falha. Use as mesmas colunas em todas as linhas.

Com os limites padrão de formulário HTTP no ClickHouse 26.4 e versões mais recentes, `server_side_params=True` é adequado apenas para lotes explícitos pequenos, abaixo de cerca de 1000 valores vinculados, com margem para outros campos. A configuração do servidor pode elevar esse limite. Para lotes simples grandes com o dialect síncrono, passe as linhas como segundo argumento de `execute()` para que o driver possa usar seu caminho de inserção em massa Native. Para dados em massa assíncronos, use `await` com o método nativo `AsyncClient.insert()`.

```python
import sqlalchemy as db
from sqlalchemy import MetaData
from sqlalchemy.orm import Session, declarative_base

from clickhouse_connect.cc_sqlalchemy.datatypes.sqltypes import String, UInt32
from clickhouse_connect.cc_sqlalchemy.ddl.tableengine import MergeTree

Base = declarative_base(metadata=MetaData(schema="example_db"))


class User(Base):
    __tablename__ = "users"
    __table_args__ = (MergeTree(order_by=["id"]),)

    id = db.Column(UInt32, primary_key=True)
    name = db.Column(String)


Base.metadata.create_all(engine)

with Session(engine) as session:
    session.add(User(id=13, name="user_1"))
    session.bulk_save_objects([User(id=79, name="user_2")])
    session.commit()
```

## Visões e funções SQL {#sqlalchemy-views-functions}

O Alembic oferece funções auxiliares explícitas para criar, substituir e remover (DROP) visões comuns e funções SQL definidas pelo usuário:

```python
from alembic import op

op.create_clickhouse_view("active_events", "SELECT id FROM analytics.events", schema="analytics")
op.create_clickhouse_view("active_events", "SELECT id FROM analytics.events WHERE id > 13", schema="analytics", or_replace=True)
op.drop_clickhouse_view("active_events", schema="analytics", if_exists=True)

op.create_clickhouse_function("analytics_increment_v1", "(value) -> value + 13")
op.create_clickhouse_function("analytics_increment_v1", "(value) -> value + 79", or_replace=True)
op.drop_clickhouse_function("analytics_increment_v1", if_exists=True)
```

Ambas as funções auxiliares de criação aceitam `if_not_exists=False` e `or_replace=False`. Passar ambos como `True` gera `ValueError`. Os corpos SQL são strings repassadas diretamente ao ClickHouse. Os nomes são colocados entre aspas como identificadores, a menos que já estejam entre aspas; um nome de função é um único identificador, mesmo que contenha um ponto. As funções SQL são globais no servidor; por isso, as funções auxiliares de funções e os métodos de inspeção não têm o argumento `schema`. Use nomes de função globalmente únicos ou versionados em todos os bancos de dados e fluxos de migração. Essas operações oferecem suporte à execução online e à renderização de SQL offline, incluindo conexões assíncronas do SQLAlchemy por meio de `run_sync`.

`or_replace=True` solicita explicitamente a substituição. O ClickHouse pode substituir uma tabela ou visão materializada existente por uma visão comum de mesmo nome, descartando os dados do objeto anterior. `DROP VIEW` rejeita tabelas base, mas pode remover visões materializadas. `IF NOT EXISTS` mantém inalterada uma definição existente e não a verifica. A substituição e a criação condicional não permitem inferir um downgrade seguro; escreva-o explicitamente usando a definição anterior. As remoções também exigem definições de downgrade explícitas. Restaurar uma definição não restaura os dados descartados. A substituição de funções SQL exige os privilégios `CREATE FUNCTION` e `DROP FUNCTION`.

O ClickHouse expande as chamadas de UDFs SQL ao armazenar a definição da view. Substituir uma UDF SQL não atualiza as visões existentes que a utilizam; recrie essas visões ou altere-as explicitamente para que usem a nova definição.

Inspecione visões comuns com os métodos existentes `get_view_names(schema=...)` e `get_view_definition(name, schema=...)`. A inspeção de funções SQL é específica do dialect do ClickHouse:

```python
from sqlalchemy import inspect

inspector = inspect(connection)
names = inspector.get_clickhouse_function_names()
create_sql = inspector.get_clickhouse_function_definition("analytics_increment_v1")
```

A inspeção de funções inclui apenas funções `SQLUserDefined`, excluindo funções integradas e executáveis. Os nomes são retornados ordenados. A definição é a instrução `CREATE FUNCTION` completa armazenada, e não apenas o corpo da lambda; nomes ausentes lançam `sqlalchemy.exc.NoResultFound`. Erros de acesso ao catálogo são propagados. A inspeção de metadados continua retornando texto mesmo quando os formatos da consulta do usuário solicitam bytes. Essas funções auxiliares não oferecem entidades declarativas de visão ou função, comparação na geração automática nem ordenação por dependências. Mantenha as operações explícitas de migração em ordem de dependência e use `render_as_batch=False` ao renderizá-las.

## Data skipping indexes {#sqlalchemy-skip-indexes}

Declare os data skipping indexes do ClickHouse como argumentos de tabela. Esta API requer o SQLAlchemy e funciona sem o Alembic:

```python
from sqlalchemy import Column, MetaData, Table, inspect
from clickhouse_connect.cc_sqlalchemy import ClickHouseIndex, engines, types

metadata = MetaData()
events = Table(
    "events",
    metadata,
    Column("value", types.UInt32),
    Column("label", types.String),
    ClickHouseIndex("value_idx", "value", "minmax"),
    ClickHouseIndex("label_idx", "label", "bloom_filter(0.01)", granularity=4),
    engines.MergeTree(order_by="value"),
)
metadata.create_all(engine)

indexes = inspect(engine).get_clickhouse_indexes("events")
```

As expressões e os tipos de índice são SQL do ClickHouse em formato bruto. As definições são imutáveis, e os nomes devem ser únicos dentro de uma tabela. As declarações são armazenadas na opção de tabela `clickhousedb_indexes`, que também aceita uma sequência de definições `ClickHouseIndex`. `Table.to_metadata()` as preserva, e `CREATE TABLE` as renderiza em linha. `if_not_exists`, `first` e `after_index` continuam disponíveis para os helpers imperativos de ALTER e não afetam a criação em linha nem a comparação de schema.

`Inspector.get_clickhouse_indexes()` retorna definições reaplicáveis para índices explícitos. As expressões refletidas usam um contêiner `tuple(...)` para preservar a lista de expressões de índice do ClickHouse, incluindo tuplas aninhadas. Os índices implícitos criados pelo servidor são excluídos com base no campo `creation` do catálogo. Erros do catálogo e classificações desconhecidas lançam um erro. O catálogo precisa expor `creation`. As notas de versão do ClickHouse documentam esse campo na versão 26.1.1.912 e no backport para a 25.12.2.54. A compatibilidade é verificada pela própria consulta, e não por uma string de versão.

O método genérico `Inspector.get_indexes()` continua retornando uma lista vazia. `Table(..., autoload_with=engine)` não lê o catálogo de skip-index. Para copiar explicitamente as colunas e os índices:

```python
inspector = inspect(engine)
reflected = Table(
    "events",
    MetaData(),
    autoload_with=engine,
    clickhousedb_indexes=inspector.get_clickhouse_indexes("events"),
)
```

## Projeções {#sqlalchemy-projections}

Declare projeções SELECT como argumentos da tabela, sem precisar do Alembic:

```python
from sqlalchemy import Column, MetaData, Table, inspect
from clickhouse_connect.cc_sqlalchemy import ClickHouseProjection, engines, types

metadata = MetaData()
events = Table(
    "events",
    metadata,
    Column("value", types.UInt32),
    Column("label", types.String),
    ClickHouseProjection("by_label", "SELECT value, label ORDER BY label, value"),
    engines.MergeTree(order_by="value"),
)
metadata.create_all(engine)

projections = inspect(engine).get_clickhouse_projections("events")
```

`select` é o SQL bruto dentro dos parênteses da projeção. As definições são imutáveis, e os nomes de projeção devem ser únicos dentro de uma tabela. A opção de tabela `clickhousedb_projections` também aceita uma sequência de definições `ClickHouseProjection`. `Table.to_metadata()` preserva as declarações, e `CREATE TABLE` as renderiza em linha. Dicionários rejeitam declarações de projeção. `if_not_exists`, `first` e `after_projection` continuam disponíveis para funções auxiliares imperativas de ALTER e não afetam a criação em linha nem a comparação. As importações de `clickhouse_connect.cc_sqlalchemy.alembic` e `.alembic.operations`, incluindo os argumentos posicionais existentes do construtor, continuam compatíveis.

`Inspector.get_clickhouse_projections()` retorna as definições SELECT armazenadas, preservando caracteres curinga, aliases, agrupamento e ordenação. O método recusa `WITH SETTINGS` no nível da projeção e formas de projeção baseadas em índice, pois a API restrita a SELECT não consegue preservar essas definições por completo. Falhas no catálogo também lançam um erro. Uma `Table(..., autoload_with=engine)` comum não lê o catálogo de projeções. Para copiar colunas e projeções explicitamente:

```python
inspector = inspect(engine)
reflected = Table(
    "events",
    MetaData(),
    autoload_with=engine,
    clickhousedb_projections=inspector.get_clickhouse_projections("events"),
)
```

A inspeção exige uma tabela de destino visível e acesso aos campos `database`, `table`, `name`, `type`, `query` e `settings` em `system.projections`. O ClickHouse adicionou esse catálogo na versão 24.9.1.3278. A presença dele, por si só, não comprova o suporte à comparação. O driver verifica os recursos disponíveis por meio do catálogo e de consultas de normalização.

## Migrações do Alembic {#sqlalchemy-alembic}

O ClickHouse Connect inclui integração com o Alembic para migrações de schema do ClickHouse. Instale-o com:

```bash
pip install "clickhouse-connect[alembic]"
```

Para migrações por meio do dialect assíncrono, instale ambos os extras:

```bash
pip install "clickhouse-connect[alembic,sqlalchemy-async]"
```

Crie um projeto Alembic assíncrono e, em seguida, substitua o ambiente gerado pelo exemplo adaptado ao ClickHouse:

```bash
alembic init -t async alembic
```

O `alembic.ini` gerado usa `script_location = %(here)s/alembic`. Mantenha essa configuração se o diretório de migrações se chamar `alembic` ou atualize-a para o diretório passado ao `alembic init`. Substitua `alembic/env.py` pelo [exemplo assíncrono de `env.py` do Alembic](https://github.com/ClickHouse/clickhouse-connect/blob/main/examples/alembic_async/env.py) disponível no repositório e, em seguida, defina `sqlalchemy.url` em `alembic.ini`.

Importe `clickhouse_connect.cc_sqlalchemy.alembic` no `env.py` do Alembic para registrar a integração com o dialect. A autogeração oferece suporte a alterações comuns em tabelas, incluindo criação e remoção de tabelas, adição/alteração/remoção de colunas, valores padrão, comentários e configurações de tabelas MergeTree. Use operações manuais para renomear tabelas e colunas. Revise cada migração gerada antes de aplicá-la.

No ClickHouse Cloud, adicione `alter_sync=2` à URL do motor de migração para que a reflexão posterior veja as alterações de esquema concluídas em todas as réplicas. Isso é importante quando uma conexão é substituída ou quando a autogeração é executada logo após um upgrade. `select_sequential_consistency=1` abrange leituras de dados, não alterações de esquema.

Os inserts na tabela de versões ignoram a desduplicação de insert para que um downgrade possa restaurar uma revisão registrada anteriormente. O SQL offline gerado usa `SETTINGS deduplicate_insert = 'disable'`, o que exige essa configuração no servidor de destino. As migrações online usam a configuração legada `insert_deduplicate = 0` quando o servidor não possui a configuração mais recente. Os inserts em tabelas comuns mantêm o comportamento de desduplicação configurado.

A autogeração compara o motor de tabela declarado com o do servidor para tabelas presentes em ambos. A migração automática de alterações na família do motor, nos argumentos posicionais do motor, em `ORDER BY`, `PRIMARY KEY`, `PARTITION BY`, `SAMPLE BY` e no `TTL` da tabela não tem suporte; por isso, uma diferença gera `UnsupportedTableChangeError` em vez de gravar uma revisão vazia ou enganosa. Escreva uma migração explícita após revisar o suporte a ALTER do servidor e os dados afetados. A exceção contém uma tupla `drifts` de registros `TableOptionDrift` com a tabela, a opção e ambas as grafias. A construção da exceção exige pelo menos uma divergência; caso contrário, ela gera `ValueError`. As expressões são comparadas após a normalização e, quando o texto ainda difere, a função `formatQuerySingleLine` do servidor decide entre grafias como `INTERVAL 30 DAY` e `toIntervalDay(30)`. Nos argumentos do motor entre aspas, o conteúdo decodificado das strings é comparado exatamente, incluindo espaços em branco e pontuação. As cláusulas TTL são formatadas como `ALTER TABLE t MODIFY TTL ...`, preservando ações como `DELETE WHERE`, `TO VOLUME` e `RECOMPRESS`. `MergeTree` e as variantes `Shared*` e `Replicated*` do Cloud contam como uma única família, e os argumentos de caminho de replicação não são comparados.

As `settings` declaradas do motor que diferem das do servidor são renderizadas como `op.modify_clickhouse_table_settings(...)`, com um downgrade que restaura ou redefine cada configuração. Os valores e tipos de `system.merge_tree_settings` resolvem valores padrão e grafias booleanas e numéricas equivalentes; configurações de string mantêm seu significado de string. As configurações que o modelo não declara são preservadas, incluindo configurações removidas do modelo após uma migração anterior. A reflexão não consegue distinguir essas configurações das injetadas pelo servidor, por isso a autogeração nunca as redefine automaticamente. Use `op.reset_clickhouse_table_settings(...)` explicitamente quando quiser redefini-las. Configurações somente leitura, como `index_granularity` e `index_granularity_bytes`, são comparadas e recusadas da mesma forma que as chaves. Passe `clickhousedb_compare_table_options=False` para `context.configure()` para ignorar a comparação.

Visões e visões materializadas refletidas não são tabelas. `include_object` as exclui, de modo que a autogeração nunca propõe `drop_table` para uma visão ausente dos metadados. Gerencie-as com os helpers comuns de visão ou de visão materializada.

`op.alter_column(..., server_default=None)` emite `MODIFY COLUMN ... REMOVE DEFAULT`, que é a única forma aceita pelo servidor. O servidor rejeita a instrução quando a coluna não tem `DEFAULT` ou usa `MATERIALIZED` ou `ALIAS`; portanto, solicite a remoção somente quando houver um valor padrão. Uma alteração apenas de tipo mantém o valor padrão existente. As opções de coluna do dialect seguem a mesma regra: passe `clickhousedb_codec=None`, `clickhousedb_ttl=None`, `clickhousedb_alias=None` ou `clickhousedb_materialized=None` para remover a propriedade, ou um valor para defini-la. Definir ou remover apenas essas propriedades não exige `existing_type`. Use `text(...)` para expressões SQL de TTL, alias e materializadas, por exemplo, `clickhousedb_ttl=text("ts + INTERVAL 7 DAY")`. As opções não passadas permanecem inalteradas. Tanto os nomes `clickhousedb_` quanto os nomes legados `clickhouse_` são aceitos; quando ambos são passados para `alter_column`, o valor explícito de `clickhousedb_` tem precedência, inclusive `None`.

Quando os metadados omitem a versão de estado de um `AggregateFunction`, a autogeração aceita a versão refletida existente. Por exemplo, `AggregateFunction(uniq, UInt32)` corresponde ao tipo refletido `AggregateFunction(1, uniq, UInt32)`. Isso também vale para tipos aninhados. Alterações na função de agregação, em seus parâmetros ou nos tipos de seus argumentos continuam gerando uma alteração de tipo.

Uma versão explícita nos metadados deve corresponder à versão refletida. Tipos refletidos legados sem versão correspondem à versão explícita `0`. Omitir a versão não solicita o upgrade de um formato de estado existente após um upgrade do servidor. Declare uma versão explícita quando quiser alterar o formato de estado.

As funções de migração do Alembic continuam síncronas. Um ambiente assíncrono cria um `AsyncEngine`, abre uma `AsyncConnection` e passa a função de migração síncrona para `await connection.run_sync(...)`. As migrações offline chamam `context.configure(url=..., literal_binds=True, dialect_opts={"paramstyle": "named"})` diretamente e não criam um motor. O [exemplo assíncrono de `env.py` do Alembic](https://github.com/ClickHouse/clickhouse-connect/blob/main/examples/alembic_async/env.py) disponível no repositório contempla os dois fluxos e lê a URL de conexão por meio da configuração padrão `sqlalchemy.url` do Alembic. Ele mantém os hooks e as opções do Alembic para o ClickHouse usados no exemplo completo, incluindo `include_object`, `make_include_name(...)`, `clickhouse_writer` e `version_table`. Não use `engine.sync_engine` para executar ou descartar migrações assíncronas.

Os helpers `op.*` específicos do ClickHouse abrangem:

* data skipping indexes, incluindo operações de adição, materialização e remoção.
* projeções, incluindo operações de adição, materialização e remoção.
* Modificação e redefinição de configurações de tabela em tabelas MergeTree.
* Criação, substituição e remoção de visões comuns e funções SQL.
* Criação e remoção de visão materializada.
* Criação, remoção e recarregamento de dicionário.

**Nota de upgrade:** por padrão, o Alembic compara skip indexes explícitos e projeções SELECT. Objetos criados apenas por migrações imperativas anteriores podem gerar remoções quando estiverem ausentes dos metadados das tabelas gerenciadas. Antes de fazer o upgrade, declare-os com `ClickHouseIndex` ou `ClickHouseProjection`, exclua objetos não gerenciados com `include_name` ou `include_object` ou desative a comparação correspondente em `context.configure()`:

```python
context.configure(
    connection=connection,
    target_metadata=metadata,
    clickhousedb_compare_indexes=False,
    clickhousedb_compare_projections=False,
)
```

Cada opção ignora suas leituras de catálogo e os snapshots de downgrade de remoção de tabela. Edições geram operações separadas de remoção e adição. O downgrade restaura as definições, mas nenhuma das direções restaura a materialização anterior. Substituir uma projeção descarta suas partes de projeção existentes. Avalie esse custo de reconstrução e execute `MATERIALIZE PROJECTION` explicitamente quando as partes existentes precisarem da substituição imediatamente. A materialização de índices também continua explícita.

Declare índices de salto com `ClickHouseIndex` para obter suporte à autogeração ou use os helpers existentes `op.add_clickhouse_index` e `op.drop_clickhouse_index` em revisões explícitas. As importações de `clickhouse_connect.cc_sqlalchemy.alembic` e `.alembic.operations` continuam compatíveis. `Index`, `Column(index=True)`, `op.create_index` e `op.drop_index` do SQLAlchemy padrão continuam sendo rejeitados.

Para tabelas gerenciadas, as declarações determinam, por padrão, o conjunto de índices explícitos ativos. Um índice explícito não declarado gera uma operação de remoção, incluindo índices criados anteriormente apenas por migrações imperativas. Uma alteração na expressão, no tipo de índice, em um parâmetro ou na granularidade efetiva gera uma remoção separada seguida de uma adição. O downgrade restaura a definição anterior. As operações permanecem visíveis para `process_revision_directives` antes da renderização. Os hooks de política devem associar edições de índices e projeções por schema, tabela e nome do objeto. Não dependa da adjacência. Nenhuma das direções restaura a materialização anterior, e nenhum `MATERIALIZE INDEX` é gerado. Materialize explicitamente se as partes existentes precisarem do índice imediatamente.

Gere adições, remoções e edições de índices com `render_as_batch=False`. Os helpers correspondentes não oferecem suporte à fila de lote adiada do Alembic, portanto `render_as_batch=True` lança um erro durante a geração. Índices em linha na criação de tabelas e nos snapshots de downgrade de remoção de tabelas continuam sendo suportados.

A mesma restrição se aplica a outras operações personalizadas do ClickHouse dentro de um bloco de lote, incluindo configurações da tabela, projeções e materialização. Gere essas operações fora do modo de lote.

Para a recriação física em lote com `op.batch_alter_table()`, passe uma Table `copy_from` completa contendo as colunas, o engine e `clickhousedb_indexes`. Use o exemplo de reflexão explícita acima para carregar tanto as colunas quanto os índices, ou forneça metadados completos para migrations offline. A recriação online automática lê o catálogo de índices em tempo de execução e recusa tabelas com índices explícitos antes de criar ou remover tabelas. Desativar a comparação no autogenerate não contorna essa proteção.

Os hooks padrão `include_name` e `include_object` recebem `type_="index"`. Os filtros de nome se aplicam tanto aos candidatos refletidos quanto aos declarados, de modo que um nome excluído permanece não gerenciado. Os filtros de objeto recebem os valores usuais `reflected` e `compare_to`. Seus objetos de índice expõem os campos de definição e `.table`. Por exemplo, a receita padrão do Alembic para objetos não gerenciados, `reflected and compare_to is None`, protege índices definidos apenas de forma imperativa. Os filtros de tabela são aplicados antes das leituras do catálogo de índices. Índices em linha em tabelas recém-criadas também são filtrados antes dos hooks de política.

A comparação usa a formatação e a análise do servidor para levar em conta as grafias e os valores padrão do ClickHouse. A análise de expressões usa a tabela atual, as funções do servidor e as configurações. Ela requer o analyzer e a saída esperada de `EXPLAIN`. Esses recursos foram verificados no ClickHouse 26.8, com revisão do código-fonte na versão 26.6. O campo do catálogo, por si só, não garante suporte à comparação em um servidor mais antigo. Definições `ALIAS` alteradas que afetam um índice exigem uma migration explícita da coluna antes da comparação de índices.

Uma edição de índice pode referenciar uma coluna física adicionada na mesma revisão. Se a análise reportar essa nova coluna agendada como um identificador desconhecido, o autogenerate valida a expressão completa com as colunas adicionadas disponíveis e, em seguida, emite a adição da coluna antes do DROP e da adição do índice. Outros identificadores desconhecidos, incluindo erros de digitação e colunas excluídas por filtros, continuam lançando `IndexComparisonError`.

Parênteses de tipo vazios e diferenças entre maiúsculas e minúsculas, como `minmax()`, `MinMax()` e `minmax`, são considerados iguais na comparação. Argumentos de tipo omitidos não são expandidos para comparação: alternar entre `bloom_filter` e `bloom_filter(0.025)` pode gerar um DROP e uma adição pontuais, mesmo que o servidor use esse valor padrão.

A comparação não estabelece equivalência para expressões SQL arbitrárias. Quando a normalização é bem-sucedida, mas as formas resultantes diferem, o autogenerate gera uma substituição mesmo que as expressões retornem os mesmos valores. Revise essas alterações ou gerencie esses índices com migrations e filtros explícitos.

Se o acesso ao catálogo, a resolução de expressões ou a saída de normalização esperada não estiverem disponíveis, o autogenerate lança `IndexComparisonError`, informando a tabela, o índice, as definições declarada e refletida e o motivo. Revise as edições com cuidado. O DROP e a adição são instruções separadas e não transacionais. Se a adição falhar, o índice antigo pode deixar de existir.

### Geração automática de projeções {#projection-autogenerate}

Por padrão, o Alembic compara projeções SELECT em tabelas gerenciadas. As declarações definem o conjunto de projeções ativas. Projeções não declaradas geram operações DROP, e definições alteradas geram operações separadas de DROP e de adição. Em cada tabela, a geração automática ordena as operações na seguinte sequência: DROP de projeções, adições e alterações de colunas, operações de índice, adições de projeções e, por fim, DROP de colunas. O Alembic acrescenta os DROP de colunas depois que os comparadores de tabela terminam. Nos hooks de política, associe as edições por schema, tabela e nome da projeção. Outras operações podem aparecer entre o DROP e a adição. Os downgrades restauram as definições anteriores, inclusive as projeções de tabelas removidas que forem recriadas. As operações expõem as definições completas para `process_revision_directives` antes da renderização. Nenhum `MATERIALIZE PROJECTION` é gerado, e nem o upgrade nem o downgrade restauram a materialização anterior das partes. Materialize explicitamente quando as partes existentes precisarem da projeção imediatamente.

Para `AggregatingMergeTree` e outros motores com comportamento de mesclagem não padrão, o ClickHouse rejeita `ADD PROJECTION` quando `deduplicate_merge_projection_mode='throw'`. Defina essa configuração explicitamente como `drop` ou `rebuild` antes de aplicar adições ou substituições de projeções, inclusive substituições de projeções originalmente declaradas em linha.

`include_name` e `include_object` recebem `type_="projection"`. Os filtros de nome se aplicam tanto aos nomes refletidos quanto aos declarados. Os filtros de objeto recebem definições com `.table`, `reflected` e `compare_to`. A receita usual `reflected and compare_to is None` protege projeções criadas apenas de forma imperativa. Os filtros de tabela são executados antes das leituras do catálogo, e as definições em linha em tabelas recém-criadas são filtradas antes dos hooks de política. Definições sem suporte em projeções filtradas ou em tabelas não relacionadas não bloqueiam a comparação.

A comparação usa o formatador da gramática completa de projeções do servidor e os nomes de funções e aliases sem diferenciar maiúsculas de minúsculas em `system.functions`, seguindo a normalização de CREATE do ClickHouse. Ela preserva a estrutura do SELECT, incluindo curingas e expressões de agregação, em vez de analisar um SELECT comum em relação à tabela ativa. Diferenças de formatação, de aspas em identificadores e de grafia de funções registradas sem diferenciação de maiúsculas e minúsculas são consideradas equivalentes. Nomes que diferenciam maiúsculas de minúsculas, como `sumIf` e `SumIf`, continuam sendo distintos. Quando as definições formatadas diferem, a comparação também verifica a árvore sintática analisada, que ignora parênteses de agrupamento. Parênteses redundantes e grafias de operadores e funções, como `value + 13` e `plus(value, 13)`, são considerados equivalentes, porque as versões do ClickHouse e o ClickHouse Cloud armazenam parênteses redundantes de forma inconsistente. Outras diferenças estruturais geram operações de DROP e de adição. A comparação não garante a equivalência de SQL arbitrário nem valida dependências de colunas. Uma substituição pode referenciar uma coluna física adicionada anteriormente na mesma revisão. Revise as dependências, inclusive colunas ALIAS alteradas, antes de aplicá-la. Dependências inválidas falham quando o DDL é executado, e uma adição com falha pode deixar a tabela sem a projeção antiga, porque o DROP e a adição são instruções separadas e não transacionais.

Campos ausentes no catálogo, erros de acesso ao catálogo, metadados de formatação ou de funções indisponíveis, `WITH SETTINGS` no nível da projeção e formas baseadas em índice geram `ProjectionComparisonError` com a tabela, a projeção, as definições declarada e refletida e o motivo. Uma falha na normalização gera esse diagnóstico em vez de produzir uma substituição. Filtre as projeções sem suporte ou gerencie-as com migrations explícitas. Se `query_masking_rules` alterar o texto do SELECT retornado pelo catálogo, a comparação e a reexecução podem não ser confiáveis. Use migrations explícitas, filtros ou a opção de desativar a comparação para as projeções afetadas. A normalização de funções requer os campos `name`, `is_aggregate`, `case_insensitive` e `alias_to` em `system.functions`. A compatibilidade é verificada por consultas reais ao catálogo e ao formatador, e não por strings de versão.

Gere adições, remoções e edições de projeções com `render_as_batch=False`. Definições CREATE em linha e snapshots de downgrade de DROP de tabela continuam compatíveis. Para a recriação física em lote, forneça metadados `copy_from` completos contendo as colunas, o motor e `clickhousedb_projections`. A recriação online automática lê o catálogo de projeções e recusa tabelas com projeções antes do DDL. A opção de desativar a comparação não contorna essa proteção de execução.

Consulte o [exemplo completo do Alembic](https://github.com/ClickHouse/clickhouse-connect/blob/main/clickhouse_connect/cc_sqlalchemy/alembic/WORKED_EXAMPLE.md). Quem estiver migrando do `clickhouse-sqlalchemy` também deve ler o [guia de migração](https://github.com/ClickHouse/clickhouse-connect/blob/main/clickhouse_connect/cc_sqlalchemy/MIGRATING_FROM_CLICKHOUSE_SQLALCHEMY.md).

### Classifique as operações geradas antes da renderização {#classify-generated-operations-before-rendering}

Todas as 21 classes de operação de migração do ClickHouse são públicas em
`clickhouse_connect.cc_sqlalchemy.alembic` e em seu módulo `operations`. Use
`isinstance` para inspecioná-las em `process_revision_directives` ou registre-as
com `Rewriter.rewrites` do Alembic. Os nomes antigos com sublinhado continuam sendo aliases das
mesmas classes, de modo que registros e importações existentes seguem funcionando.

Os campos públicos de inspeção correspondem aos argumentos do construtor. As operações de tabela expõem
`table_name`, `schema` e `clickhouse_settings`. As operações de índice individual expõem
`name`. As adições também expõem `expression`, `type_`, `granularity`, `if_not_exists`,
`first` e `after_index`. As adições de projeção expõem `select` e
`after_projection` em vez dos campos de expressão, tipo e granularidade de índice. As remoções
expõem `if_exists` e, no caso de índices ou projeções individuais, `existing_index` ou
`existing_projection` quando há uma definição anterior disponível. As materializações
expõem `if_exists` e `partition`. As adições agrupadas armazenam `indexes` ou
`projections` como tuplas de `ClickHouseIndex` ou `ClickHouseProjection`. As remoções
agrupadas armazenam `names` como uma tupla. Inspecione cada membro de uma operação agrupada.

`ModifyClickHouseTableSettingsOp` expõe `settings` e, opcionalmente,
`existing_settings`. `ResetClickHouseTableSettingsOp` expõe uma tupla de `names`.
Essas configurações da tabela são diferentes do mapeamento query-level `clickhouse_settings`.
As operações de criação de visão e de função expõem `name`, `select` ou `expression`,
`if_not_exists` e `or_replace`. As visões também expõem `schema`. A criação de visão materializada
expõe `name`, `schema`, `to_table`, `to_schema`, `select` e
`if_not_exists`. A criação de dicionário expõe `name`, `schema`, uma tupla `columns`,
`primary_key`, `source`, `layout`, `lifetime`, `comment`, `if_not_exists` e
`clickhouse_settings`. As remoções de visão, função, visão materializada e dicionário expõem
`name` e `if_exists`, além de `schema` e `clickhouse_settings` quando aceitos pelo
construtor. O recarregamento de dicionário expõe `name` e `schema`. Fragmentos de SQL
permanecem como strings. Os mapeamentos mantêm os valores fornecidos. Operações reversas podem
exigir definições anteriores ou lançar `NotImplementedError`. Uma definição reversível
não restaura dados materializados.

Este exemplo é uma política da aplicação, e não uma garantia de segurança do driver. Ele permite
apenas um formato de índice ou uma configuração da tabela escolhidos explicitamente, encaminha substituições e
operações desconhecidas para revisão e rejeita remoções independentes de índices, remoções independentes
de projeções e operações nativas destrutivas. Adapte essas regras à sua implantação. Até mesmo
a criação exige inspeção de campos: `or_replace=True` em uma visão pode descartar os dados de uma
tabela conflitante, e corpos de SQL bruto e fontes de dicionário precisam ser revisados.

```python
import logging

from alembic.operations import ops
from clickhouse_connect.cc_sqlalchemy import alembic as ch_alembic


def leaves(operation):
    if isinstance(operation, ops.OpContainer):
        for child in operation.ops:
            yield from leaves(child)
    else:
        yield operation


def object_key(operation):
    if isinstance(operation, (ch_alembic.AddClickHouseIndexOp,
                              ch_alembic.DropClickHouseIndexOp)):
        kind = "index"
    elif isinstance(operation, (ch_alembic.AddClickHouseProjectionOp,
                                ch_alembic.DropClickHouseProjectionOp)):
        kind = "projection"
    else:
        return None
    return kind, operation.schema, operation.table_name, operation.name


def classify_tree(tree, direction):
    operations = list(leaves(tree))
    adds = {object_key(op) for op in operations if isinstance(
        op, (ch_alembic.AddClickHouseIndexOp, ch_alembic.AddClickHouseProjectionOp))}
    drops = {object_key(op) for op in operations if isinstance(
        op, (ch_alembic.DropClickHouseIndexOp, ch_alembic.DropClickHouseProjectionOp))}
    replacements = adds & drops
    for operation in operations:
        verdict, reason = "review", "operation needs explicit review"
        if isinstance(operation, (ops.DropTableOp, ops.DropColumnOp, ops.ExecuteSQLOp)):
            verdict, reason = "rejected", "destructive change or opaque SQL"
        elif object_key(operation) in replacements:
            reason = "replacement can discard existing materialization"
        elif isinstance(operation, (ch_alembic.DropClickHouseIndexOp,
                                    ch_alembic.DropClickHouseProjectionOp,
                                    ch_alembic.DropClickHouseIndexesOp,
                                    ch_alembic.DropClickHouseProjectionsOp)):
            verdict, reason = "rejected", "removal requires a separate migration"
        elif direction == "upgrade":
            if isinstance(operation, ch_alembic.AddClickHouseIndexOp):
                if (operation.type_ == "minmax" and operation.expression == "value"
                        and operation.granularity == 1 and not operation.first
                        and operation.after_index is None and not operation.clickhouse_settings):
                    verdict, reason = "allowed", "approved index definition"
            elif isinstance(operation, ch_alembic.ModifyClickHouseTableSettingsOp):
                if (dict(operation.settings) == {"max_bytes_to_merge_at_max_space_in_pool": 107374182400}
                        and not operation.clickhouse_settings):
                    verdict, reason = "allowed", "approved table setting value"
        yield direction, operation, verdict, reason


def review_revision(context, revision, directives):
    # Scope: a single-engine env.py. clickhouse_writer uses singular roots.
    for script in directives:
        if len(script.upgrade_ops_list) != 1 or len(script.downgrade_ops_list) != 1:
            raise ValueError("This policy hook supports one operation stream only")
        findings = [
            *classify_tree(script.upgrade_ops_list[0], "upgrade"),
            *classify_tree(script.downgrade_ops_list[0], "downgrade"),
        ]
        for direction, op, verdict, reason in findings:
            logging.getLogger("alembic.policy").info(
                "%s: %s: %s: %s", direction, type(op).__name__, verdict, reason)
        blocked = [f"{direction}: {type(op).__name__}: {verdict}: {reason}"
                   for direction, op, verdict, reason in findings
                   if direction == "upgrade" and verdict != "allowed"]
        if blocked:
            raise ValueError("Migration requires review:\n" + "\n".join(blocked))
    ch_alembic.clickhouse_writer(context, revision, directives)
```

Passe `process_revision_directives=review_revision` para `context.configure()` no
lugar de `clickhouse_writer`. O hook registra em log as constatações para ambas as direções e condiciona a geração da revisão às
constatações de upgrade. As constatações de downgrade exigem uma revisão à parte antes de executar
um downgrade. Elas não impedem a gravação de um upgrade aprovado. O hook percorre contêineres aninhados e emparelha as substituições por
tipo, schema, tabela e nome, independentemente da adjacência. Adições agrupadas e todas as
operações não reconhecidas são encaminhadas para revisão por padrão. Esta receita oferece suporte a um único motor e
a um único stream de operações por direção. Usar raízes de lista no classificador não
transforma `clickhouse_writer` em um hook multimotor. Uma árvore gerada vazia prova apenas
que as comparações habilitadas e compatíveis não encontraram alterações. Visões, funções,
dicionários e outras comparações sem suporte continuam exigindo migrations explícitas.

## Escopo e limitações {#scope-and-limitations}

* O ClickHouse não oferece transações tradicionais por meio deste dialeto HTTP. `engine.begin()` e `Session.commit()` organizam o trabalho no lado do Python, mas commit e rollback são operações sem efeito no servidor.
* `UPDATE`, transações em duas fases, sequências, `RETURNING` e níveis avançados de isolamento não são implementados por este dialeto. Use ClickHouse SQL explicitamente para mutações no servidor, quando necessário.
* `Column(..., primary_key=True)` fornece a identidade de objeto no SQLAlchemy. Isso não cria uma restrição de unicidade do lado do servidor. Defina as expressões de ordenação e, opcionalmente, de chave primária por meio do engine da tabela.
* Metadados tradicionais de chaves estrangeiras, restrições de unicidade e índices padrão não estão disponíveis, porque o ClickHouse não impõe essas restrições.
* Gerenciamento de relacionamentos do ORM, atualizações de unit of work, cascatas e carregamento imediato ou lazy de relacionamentos estão fora do escopo de ORM suportado.
