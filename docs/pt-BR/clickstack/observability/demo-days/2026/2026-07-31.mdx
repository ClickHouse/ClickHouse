## Métricas de histograma exponencial {#exponential-histogram-metrics}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/w45v3IMcXTY" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Chegou o suporte inicial a consultas para métricas de histograma exponencial do OpenTelemetry. Já era possível registrar uma dessas métricas em uma fonte de dados, mas não havia como consultá-la. Agora, contagens e quantis funcionam pelo construtor de consultas.

Histogramas exponenciais são semelhantes aos histogramas com buckets explícitos, mas os limites de seus buckets são calculados a partir de potências de dois, em vez de serem armazenados para cada bucket. A escala controla qual potência de dois é usada. Uma escala maior gera buckets menores, enquanto o deslocamento move os limites em direção a múltiplos maiores ou menores. A contagem de cada bucket registra quantas observações se enquadram naquele intervalo.

Max, min, sum e avg continuam sem suporte, assim como na implementação existente de histogramas explícitos. Esses campos são opcionais no modelo de dados do OpenTelemetry, portanto não contamos com a presença deles.

Como mostra a demonstração, o SQL gerado é longo e não muito elegante. O desempenho é aceitável e não há esgotamento de memória, mas trata-se apenas de um suporte funcional inicial. O desempenho é a próxima frente de trabalho, e já está em desenvolvimento um schema atualizado que deve tornar essas consultas consideravelmente mais rápidas.

Por enquanto, apenas o tipo de exibição de série temporal é renderizado corretamente. Isso está de acordo com o tipo existente de métrica de histograma.

## Validação para gráficos de SQL bruto {#validation-for-raw-sql-charts}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/zfZsehTqeCQ" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Os gráficos de SQL bruto agora exibem um aviso quando faltam macros esperadas. Essa melhoria surgiu de um chamado de suporte em que um usuário que criava muitos gráficos de SQL bruto obtinha resultados confusos com frequência.

As consultas de dashboard devem incluir as macros de filtros e de tabela de origem. Gráficos de série temporal também devem incluir as macros de intervalo de tempo e de intervalo. Antes, essas verificações só eram executadas depois que um alerta era anexado ao bloco. Agora elas são executadas em todos os gráficos de SQL bruto, de modo que remover uma macro exibe um aviso no editor, em vez de gerar um gráfico difícil de entender mais tarde.

A validação também considera as dependências de cada macro. As macros de tabela de origem e de filtros exigem uma fonte de dados selecionada, embora os gráficos de SQL bruto não precisem de uma em outros casos. Por isso, usar qualquer uma dessas macros sem selecionar uma fonte de dados gera um erro, e não um aviso.

É uma mudança pequena, mas deve facilitar a identificação de problemas em SQL bruto sem precisar recorrer ao suporte.

**PRs relacionados:** [#2742](https://github.com/hyperdxio/hyperdx/pull/2742) feat: Warn on missing params/macros in SQL Editor

## Vincular fontes de dados por nome, não por ID {#link-to-sources-by-name-not-id}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/r2uNmcJXGSM" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

A equipe do LogHouse pediu uma forma mais estável de criar links para fontes de dados. Ela opera o ambiente de logging do ClickHouse Cloud e provisiona fontes de dados programaticamente com infraestrutura como código. Os IDs das fontes de dados mudam quando uma fonte de dados é recriada e variam entre os ambientes de desenvolvimento, staging e produção, o que torna frágil qualquer link baseado em ID. Como a equipe cria links para o ClickStack a partir de sistemas de alerta e do Grafana, manter um conjunto separado de IDs de fontes de dados para cada ambiente não era viável.

O parâmetro de URL `source` agora aceita tanto o nome quanto o ID de uma fonte de dados. Como os nomes são definidos no provisionamento das fontes de dados, o mesmo link funciona em todos os ambientes. O suporte foi adicionado inicialmente à página de busca. Um PR posterior o estendeu a todas as páginas com um parâmetro de fonte de dados, incluindo o Chart Explorer, o mapa de serviços, as sessões, o dashboard de serviços e o Painel do Kubernetes.

A maior parte da discussão que se seguiu girou em torno da facilidade de descoberta. Na prática, trata-se de uma API de URL, e dificilmente alguém a encontrará por acaso. Uma opção seria usar nomes em vez de IDs por padrão, mas colisões de nomes tornam isso inseguro. Outras sugestões incluíram expor os links por meio de um botão Compartilhar, permitir que agentes os gerem via MCP e documentar adequadamente a API de URL. Os intervalos de tempo relativos também se beneficiariam dessa mesma documentação.

As referências por nome também poderiam ser estendidas aos dashboards. Assim, um fluxo de trabalho de infrastructure-as-code poderia provisionar fontes de dados, importar dashboards e conectar tudo automaticamente. A importação de dashboards pela UI já associa as fontes de dados por nome, então a lacuna restante está principalmente nos fluxos de trabalho programáticos.

**PRs relacionados:** [#2746](https://github.com/hyperdxio/hyperdx/pull/2746) feat: Accept source names in addition to IDs in URL Params, [#2758](https://github.com/hyperdxio/hyperdx/pull/2758) feat: Support source name deeplinks on additional pages

## Reformulação das configurações de exibição de gráficos {#chart-display-settings-redesign}

*Demonstração por [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/tO5yFKR-MLQ" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Ainda está em andamento a definição de onde as configurações de exibição de gráficos devem ficar. A alteração original passou a exibi-las em linha, à direita do editor de blocos, em vez de abri-las em um painel deslizante separado. Antes, o editor de blocos era um modal e as Configurações de Exibição abriam em um painel deslizante sobre ele. Pressionar Escape uma única vez fechava os dois, e um painel deslizante sobre um modal nunca pareceu a solução certa.

O PR ficou mais complicado quando as configurações de séries também precisaram ser empilhadas por cima, então demos um passo atrás e começamos a analisar a página como um todo. O trabalho ainda está na etapa de wireframe. O design atual coloca as configurações em um painel fixo e aplica as alterações automaticamente, permitindo ver o resultado em tempo real sem precisar clicar no botão Aplicar.

O plano é concluir a reformulação antes de incorporá-la de volta ao PR existente. O que existe hoje está sendo tratado como um protótipo, principalmente porque o novo design também altera partes da página de dashboard.

**PRs relacionados:** [#2721](https://github.com/hyperdxio/hyperdx/pull/2721) feat(dashboards): move tile editor to a drawer with docked settings panel

## Nova página Explorar {#new-explore-page}

*Demonstração por [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/E1vEjJBw1gs" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Esta é uma exploração inicial de uma página Explorar unificada que poderá, futuramente, substituir Busca, Buscas salvas e Chart Explorer por um único ponto de entrada.

A implantação gradual se baseia no que aprendemos com o redesenho do visualizador de rastros. Em vez de mudar a experiência para todos de uma só vez, a nova página seria lançada atrás de uma feature flag para um pequeno grupo de usuários. Usaríamos esse período para identificar e corrigir problemas antes de disponibilizá-la de forma mais ampla. Se a ideia não funcionar, ela continua sendo um experimento e não é lançada. E esse é um resultado perfeitamente aceitável.

A página começa com a escolha de um tipo de sinal. Ao escolher rastros, logs ou métricas, o restante da experiência se adapta. Ao selecionar logs, por exemplo, você tem acesso à visualização em lista, aos padrões de eventos, às séries temporais e às demais visualizações hoje disponíveis no Chart Explorer.

Uma investigação deve poder seguir sem que seja preciso trocar de página. Você pode começar com uma lista, passar para um número ou uma tabela agrupada, adicionar o resultado a um dashboard e, depois, escrever uma consulta personalizada se precisar de mais controle.

Também foram incluídas várias ideias menores, a maioria motivada por feedback de usuários. O editor de consultas funcionaria de forma mais parecida com o Editor SQL, eliminando as diferenças atuais no comportamento do preenchimento automático. Erros e avisos apareceriam durante a edição, sem precisar esperar a execução da consulta.

As colunas ganhariam um seletor próprio. Pelo menos um usuário não percebeu que alterar a cláusula `SELECT` definia quais colunas apareciam na tabela. Com o seletor, clicar em um campo atualiza o SQL e permite ordenar por esse campo. A cláusula `SELECT` continua disponível para usuários avançados.

As visões salvas também ficariam na própria página, permitindo explorar sem salvar e depois salvar a visão atual ali mesmo. O SQL gerado seria exibido em linha.

Ainda falta bastante coisa, incluindo algumas das visualizações disponíveis hoje no Chart Explorer. O design continuará evoluindo à medida que essas partes forem adicionadas.

**PRs relacionados:** nenhum ainda; trata-se de uma exploração, não de uma funcionalidade lançada

## Vinculação de filtros em dashboards {#dashboard-filter-linking}

*Demonstração por [@teeohhem](https://github.com/teeohhem)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/IQ4WtnNYS5s" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

A vinculação de filtros em dashboards foi mesclada. Nós a demonstramos pela primeira vez como rascunho há alguns meses e, depois, pausamos o trabalho para avaliar as implicações de desempenho. A vinculação altera a estrutura das consultas do dashboard e nem sempre aproveita da melhor forma as visões materializadas, por isso será lançada como um botão de alternância opcional, e não como comportamento padrão.

Com a vinculação habilitada, escolher um valor em um filtro restringe os valores disponíveis nos demais. Ao selecionar um serviço, restam apenas os valores de severidade encontrados para esse serviço. Ao selecionar um ID do rastro, restam apenas os IDs de rastro pai relacionados. Isso impede que os usuários escolham combinações que não retornam dados.

Um PR posterior faz a vinculação levar em conta a fonte de dados. Os filtros são agrupados por fonte de dados, com ícones de corrente entre filtros vizinhos que podem restringir uns aos outros. Em um dashboard com dois filtros de logs e dois filtros de rastros, deve ficar claro quais filtros interagem entre si.

O caso de uso original era o Painel do Kubernetes. Ao selecionar um pod do Kubernetes, devem restar apenas as implantações e os nós que contêm esse pod. Os valores reduzidos são obtidos sob demanda quando uma lista suspensa é aberta, o que limita o custo das consultas adicionais.

A discussão deixou duas questões em aberto. Atualmente, a configuração é armazenada por usuário no armazenamento do navegador. A expectativa levantada na reunião foi de que, com o tempo, as pessoas vão querer salvá-la no nível do dashboard. Nesse caso, talvez seja melhor manter a preferência no nível do usuário como temporária, para que ela não entre em conflito futuramente com o comportamento no nível do dashboard.

A outra questão é como os filtros dependentes se comportam enquanto seus valores estão sendo carregados. Atualmente, selecionar um valor exibe um estado de carregamento dentro da lista suspensa dependente, sem bloqueá-la, embora o comportamento com um segundo filtro dependente ainda precise ser verificado. A preferência foi manter os filtros utilizáveis enquanto a redução está em andamento e indicar que a lista ainda não terminou de ser atualizada. Quem já sabe qual valor quer não deveria ter que esperar pelos metadados.

**PRs relacionados:** [#2423](https://github.com/hyperdxio/hyperdx/pull/2423) feat(dashboards): cascading (faceted) filter values, [#2760](https://github.com/hyperdxio/hyperdx/pull/2760) feat(dashboards): persist filter link toggle and clarify within-source linking

## Lembrar a última aba do painel lateral {#remember-the-last-side-panel-tab}

*Demonstração por [@MikeShi42](https://github.com/MikeShi42)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/FlDWN7sGHMo" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

O menor PR da semana também é um bom exemplo de um incômodo que vale a pena corrigir.

O painel lateral de linha sempre abria na aba Visão geral, que foi pensada com base nos campos de log do OpenTelemetry. Para logs que não seguem a estrutura do OTel, essa aba exibe pouquíssimas informações úteis. Com isso, era preciso alternar para Valores da coluna toda vez que se abria uma linha.

Agora o painel lembra a última aba usada e a abre novamente na próxima vez. Não é preciso configurar nada. Usuários que não utilizam OTel e alternam para Valores da coluna continuarão nela, enquanto quem usa a Visão geral mantém o comportamento atual.

**PRs relacionados:** [#2752](https://github.com/hyperdxio/hyperdx/pull/2752) feat(app): remember last-used side panel tab across opens
