## Filtros de fonte, agora em todos os lugares {#source-filters-now-everywhere}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<Frame>
  <iframe src="https://www.youtube.com/embed/Zl5ymdzoM6U" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Os filtros de fonte agora estão disponíveis em todo o dashboard Services. Ao selecionar uma fonte de dados de trace ou de log com um filtro de nome do serviço, o dashboard aguarda até que você escolha um valor antes de executar as consultas. Esse filtro passa então a ser aplicado de forma consistente em todos os gráficos, consultas e painéis laterais. A visualização de trace em cascata segue o mesmo comportamento: ao abrir um span, ela herda os filtros de fonte da página Search e ainda permite que você adicione outros filtros. A página Sessions também foi atualizada para que os filtros de fonte sejam propagados para a barra lateral, o painel de trace e as visões aninhadas.

O preenchimento automático para filtros de fonte também foi ampliado. Antes disponível apenas na página Search, ele agora funciona em todos os lugares onde há suporte a filtros de fonte, incluindo dashboards. Internamente, o preenchimento automático passou a resolver chaves e valores em várias fontes de dados, mesmo quando cada uma delas tem seu próprio conjunto de filtros. As mesmas melhorias estão disponíveis tanto no editor de SQL bruto quanto em todos os campos de filtro de fonte do construtor de consultas.

**PRs relacionados:** [#2331](https://github.com/hyperdxio/hyperdx/pull/2331) Adiciona escopo por fonte de dados aos filtros de dashboard, [#2459](https://github.com/hyperdxio/hyperdx/pull/2459) Exibe ícone em blocos com filtros com escopo por fonte de dados excluídos

## Dashboards gerados por IA aprimorados para esquemas personalizados {#better-ai-generated-dashboards-for-custom-schemas}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<Frame>
  <iframe src="https://www.youtube.com/embed/LUi5047F3fs" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Um usuário que criava dashboards com IA sobre um esquema personalizado enfrentou sérios problemas de desempenho. A causa raiz era que os blocos de SQL bruto gerados fixavam um intervalo de tempo no código em vez de usar as macros de filtro de tempo do dashboard, de modo que alterar o intervalo de tempo do dashboard não tinha nenhum efeito. Além disso, um dos blocos filtrava uma coluna de timestamp do tipo inteiro de uma forma que ignorava a chave primária, forçando uma varredura completa da tabela.

Para resolver isso, o esquema MCP para blocos de SQL bruto em dashboards agora deixa explícito que os agentes devem usar as macros de filtro de tempo do dashboard. A Interface do ClickStack também exibe um alerta quando um bloco de SQL gerado não contém essas macros, o que facilita identificar o problema antes de salvar o dashboard. Após a implantação das alterações, ao executar novamente o prompt original do cliente, o SQL gerado passou a usar as macros corretas, resultando em um dashboard muito mais rápido.

**PRs relacionados:** [#2473](https://github.com/hyperdxio/hyperdx/pull/2473) Orientar agentes a usar macros em blocos de SQL bruto

## Hashing simplificado para métricas OTel e uma ideia de chave primária {#simpler-hashing-for-otel-metrics-and-a-primary-key-idea}

*Demonstração por [@dhable](https://github.com/dhable)*

<Frame>
  <iframe src="https://www.youtube.com/embed/MjAUdJJbC8M" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Uma contribuição da comunidade corrigiu o hashing de atributos para métricas com colunas de atributos JSON, mas introduziu dois caminhos de código distintos. Os esquemas JSON usavam a forma variádica de `cityHash64`, enquanto os esquemas baseados em Map concatenavam três mapas antes de calcular o hash. No fim, esse trabalho extra não era necessário. Agora, ambos os tipos de esquema usam a mesma implementação de `cityHash64`, o que simplifica o código e evita alocações desnecessárias de mapas durante o hashing.

O trabalho também revelou uma possível otimização para o esquema de métricas do OpenTelemetry. Atualmente, a chave primária armazena o map completo de atributos, o que aumenta o uso de memória, já que o ClickHouse mantém o map em memória como parte do índice. Uma ideia é materializar um hash dos atributos no momento da inserção e usá-lo na chave primária em seu lugar. Nada mudou ainda, mas, com as atualizações do esquema do OpenTelemetry de volta à pauta, essa é uma otimização que vale a pena retomar.

**PRs relacionados:** [#2475](https://github.com/hyperdxio/hyperdx/pull/2475) Unificar AttributesHash para cityHash64 variádico

## Aprimoramentos nas pílulas de filtro e nas fontes de dados {#filter-pill-and-data-source-polish}

*Demonstração por [@alex-fedotyev](https://github.com/alex-fedotyev)*

<Frame>
  <iframe src="https://www.youtube.com/embed/Zi6HPj5_JQg" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Esta semana chegaram duas melhorias de usabilidade pequenas, mas úteis. As pílulas de filtro de exclusão ficaram muito mais legíveis, depois que o feedback de clientes apontou que o estilo anterior deixava o botão de remoção pouco visível. Agora elas usam um tom de vermelho mais suave, que melhora o contraste tanto no modo claro quanto no escuro.

Gerenciar um grande número de fontes de dados também ficou mais fácil. Agora é possível atribuir uma seção opcional a cada fonte de dados, o que permite agrupá-las no seletor de fonte. Fontes de dados sem seção continuam aparecendo em &quot;Outros&quot;, portanto as configurações existentes não são afetadas. A busca também passou a considerar os nomes das seções, o que facilita encontrar fontes de dados relacionadas mesmo quando você só se lembra do grupo ao qual pertencem. No momento, a funcionalidade está sendo usada internamente enquanto a equipe avalia como as pessoas costumam organizar suas fontes de dados, antes de disponibilizá-la de forma mais ampla.

**PRs relacionados:** [#2478](https://github.com/hyperdxio/hyperdx/pull/2478) Torna as pílulas de filtro de exclusão legíveis no tema claro, [#2432](https://github.com/hyperdxio/hyperdx/pull/2432) Adiciona um campo opcional Section às fontes de dados, [#2476](https://github.com/hyperdxio/hyperdx/pull/2476) Agrupa o seletor de fontes de dados por seção, com busca no estilo de rótulos, [#2477](https://github.com/hyperdxio/hyperdx/pull/2477) Sugere nomes de seções existentes no formulário de fonte de dados

## Limites de séries por gráfico para gráficos com high-cardinality {#per-chart-series-limits-for-high-cardinality-charts}

*Demonstração por [@wrn14897](https://github.com/wrn14897)*

<Frame>
  <iframe src="https://www.youtube.com/embed/xKpHvhbo-PI" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Os gráficos agora podem limitar o número de séries retornadas, o que ajuda a evitar problemas de desempenho ao agrupar por campos com high-cardinality, como rota HTTP ou ID de span. Antes, essas consultas podiam gerar centenas de milhares de séries, deixando os dashboards lentos ou sem resposta. Agora é possível limitar um gráfico às primeiras N séries, reduzindo tanto o tempo de renderização quanto o volume de dados transferidos.

Selecionar as principais séries de forma eficiente é mais complexo em consultas divididas em blocos. A implementação atual determina as primeiras N séries a partir do fragmento mais recente e, em seguida, aplica esse mesmo conjunto de séries a toda a consulta, com o processamento feito no ClickHouse, e não no navegador. Essa abordagem ainda está em avaliação e pode mudar à medida que novas otimizações de consultas forem introduzidas.

**PRs relacionados:** [#2449](https://github.com/hyperdxio/hyperdx/pull/2449) Torna o limite de séries opcional e consistente entre blocos, [#2429](https://github.com/hyperdxio/hyperdx/pull/2429) Limita séries temporais com group-by às primeiras N séries para evitar OOM
