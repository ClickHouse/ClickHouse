Agora é possível criar links diretos para blocos (células) de notebooks, inclusive entre ramificações. Em Markdown personalizado, você pode usar um link absoluto ou um link de hash relativo, o que facilita muito indicar a alguém a evidência exata que sustenta uma afirmação.

## Otimização da chave primária das tabelas de métricas do OTel {#otel-metrics-table-primary-key-optimization}

*Demonstração por [@knudtty](https://github.com/knudtty)*

<Frame>
  <iframe src="https://www.youtube.com/embed/GIwNxRJGQKg" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Uma análise aprofundada sobre como validar e reduzir as chaves primárias das tabelas de métricas do OTel. A métrica mais útil aqui é a quantidade de bytes da chave primária por grânulo: o tamanho total da chave primária dividido pelo número de grânulos. Isso compensa o fato de que tabelas maiores naturalmente têm mais grânulos e permite uma comparação justa.

O schema original ficava em torno de 148 bytes por grânulo. O novo schema fica próximo de 17 bytes, uma redução de cerca de 9x no tamanho da chave primária, com uma redução semelhante no uso de memória em produção.

As alterações de esquema são relativamente pequenas. `MetricName` agora usa `LowCardinality`, o que não é problema, a menos que você lide com um número enorme de nomes de métricas distintos. Mesmo assim, isso só deve se tornar uma preocupação em casos extremos. Os timestamps passam de `DateTime64` com precisão de nanossegundos para um `DateTime` simples com precisão de segundos, o que é mais do que suficiente para métricas. Ainda é possível manter a precisão de nanossegundos alterando o schema por conta própria.

Também adicionamos índices min/max explícitos para o tempo e substituímos o mapa completo de atributos na chave primária por um hash. As mesmas alterações foram aplicadas a todos os esquemas das tabelas de métricas, e também estamos levando-as upstream para o OTel Collector.

**PRs relacionados:** [#2545](https://github.com/hyperdxio/hyperdx/pull/2545) fix: change metrics PK for better memory usage

## Linhas de tendência/minigráficos por trás dos números {#trend-and-spark-lines-behind-numbers}

*Demonstração por [@alex-fedotyev](https://github.com/alex-fedotyev)*

<Frame>
  <iframe src="https://www.youtube.com/embed/4XwOkyNqDEY" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Os blocos numéricos agora podem exibir uma linha de tendência ou um gráfico de área por trás do valor. Essa funcionalidade já é popular no Grafana há bastante tempo e agora chegou ao ClickStack.

Para ativá-la, acesse as configurações de exibição do bloco. Por padrão, nenhum gráfico de fundo é exibido; as outras opções disponíveis são linha e área. A configuração é mínima, mas deixa os dashboards com uma aparência visivelmente mais acabada.

Por enquanto, os gráficos de fundo funcionam apenas com blocos numéricos declarativos, portanto ainda não é possível usar SQL personalizado. Estamos avaliando isso como uma próxima etapa, depois de recebermos feedback de usuários que querem mais controle sobre o que o gráfico exibe.

**PRs relacionados:** [#2489](https://github.com/hyperdxio/hyperdx/pull/2489) feat(dashboards): background trend sparkline on number tiles, [#2501](https://github.com/hyperdxio/hyperdx/pull/2501) fix(dashboards): match the number-tile background sparkline to the displayed value, [#2520](https://github.com/hyperdxio/hyperdx/pull/2520) refactor(dashboards): extract shared Sparkline primitive from number tile

## Melhorias no plugin do Grafana {#grafana-plugin-improvements}

*Demonstração por [@alex-fedotyev](https://github.com/alex-fedotyev)*

<Frame>
  <iframe src="https://www.youtube.com/embed/doFNUMZotJU" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Um resumo das novidades que chegarão em breve ao plugin do Grafana para o ClickStack.

A configuração da fonte de dados agora oferece suporte a um modo de tabela única, além da configuração já existente com vários bancos de dados. Basta apontá-la para uma única tabela, como os logs de produção, e o editor de consultas passa a usar um construtor compacto, pensado para exploração. Você conta com filtros rápidos para campos como nome do serviço, filtragem por inclusão e exclusão, e o SQL continua disponível sempre que precisar.

Também estamos lançando dashboards prontos para logs e rastros do OTel, seguindo o mesmo pattern de drill-down com o qual os usuários já estão acostumados. O dashboard de logs inclui uma visão geral por serviço, gráficos de volume e detalhes dos logs. O Trace Explore abrange visões por serviço, mapas de calor de latência e detalhamentos por operação. Há ainda um dashboard combinado por serviço que reúne logs e rastros, agrupados por nome de span, para que você possa investigar um serviço sem ficar alternando entre ferramentas.

Todos esses dashboards funcionam com o schema padrão, sem nenhuma configuração adicional. Novos usuários podem começar a usá-los imediatamente e, depois, aproveitá-los como ponto inicial para criar seus próprios dashboards.

Há também dois novos construtores em formato de assistente. O construtor de variáveis permite selecionar valores da coluna em vez de escrever SQL personalizado. Por exemplo, você pode criar uma variável a partir de nomes de pods do Kubernetes e visualizar uma prévia dos valores que ela retorna.

O construtor de anotações gera anotações a partir de uma consulta de detecção de mudanças em um campo escolhido. Basta apontá-lo para o atributo de versão de um serviço para que ele adicione um marcador de implantação sempre que esse valor mudar, sem que você precise escrever o SQL.

## Consultas de métricas, avaliações de dashboards e relato aprimorado de erros de alertas no MCP {#metrics-queries-dashboard-evals-and-better-alert-error-reporting-in-mcp}

*Demonstração por [@brandon-pereira](https://github.com/brandon-pereira)*

<Frame>
  <iframe src="https://www.youtube.com/embed/yjceqgveZr8" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Três melhorias no servidor MCP chegaram juntas neste ciclo.

O MCP agora pode executar consultas de métricas diretamente, inclusive a partir de notebooks, sem precisar passar por um dashboard só para acessar os dados subjacentes.

Também adicionamos uma avaliação de ponta a ponta para a criação de dashboards. Atualmente, ela é aprovada em cerca de 75% dos casos, e estamos adicionando distratores continuamente para torná-la mais difícil de burlar. Quando o MCP cria um dashboard com defeito em uso real, essa falha pode ser incorporada ao conjunto de avaliações. Com o tempo, isso deve permitir detectar problemas, como fontes de dados de SQL bruto que geram a consulta errada, antes que se tornem falhas recorrentes.

Os erros de ferramentas agora são classificados por categoria, em vez de caírem todos em um único grupo genérico. Uma consulta SQL incorreta enviada por um usuário é tratada separadamente de uma falha interna, como um tempo limite do banco de dados. Isso nos dá a distinção necessária para criar alertas mais úteis sobre a saúde do MCP.

## Atualizações do processador em lote do OTel collector {#otel-collector-batch-processor-updates}

*Demonstração por [@SpencerTorres](https://github.com/SpencerTorres)*

<Frame>
  <iframe src="https://www.youtube.com/embed/rlSm_9ivsQ4" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

O OpenTelemetry está transferindo o agrupamento em lotes do processador em lote independente para a configuração do exportador. O Coletor do ClickStack já era compatível com as duas abordagens, então não foi preciso alterar código. No fim, bastou uma atualização da documentação.

No modelo antigo, um processador em lote dedicado ficava no pipeline e armazenava linhas em buffer antes de repassá-las ao exportador. Ele tinha suas próprias configurações de tamanho do lote, tamanho máximo do lote e tempo limite.

No modelo que o OpenTelemetry está adotando como padrão, o agrupador fica junto ao exportador, em vez de fazer parte da cadeia de processadores. A maioria dos conceitos continua valendo, incluindo os tamanhos mínimo e máximo de lote e o tamanho da fila. A configuração baseada no exportador também oferece comportamento de bloqueio, limites baseados em bytes e persistência, recursos que não existiam no antigo processador em lote.

A documentação agora recomenda a configuração baseada no exportador e explica como migrar as configurações existentes do processador em lote. Ela também sugere um mínimo de 5,000 linhas com um tempo limite curto como um padrão razoável para a maioria das implantações. Uma configuração inadequada de agrupamento em lotes continua sendo uma das causas mais comuns de uma primeira experiência ruim com o ClickHouse.

## Contexto ao redor para atributos arbitrários {#surrounding-context-for-arbitrary-attributes}

*Demonstração por [@MikeShi42](https://github.com/MikeShi42)*

<Frame>
  <iframe src="https://www.youtube.com/embed/BZTG8TTTyoA" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

O contexto ao redor permite abrir uma linha de log e ver o que mais estava acontecendo naquele momento. Por padrão, esse contexto é agrupado por serviço, pod do Kubernetes ou nó. Isso funciona bem para a maioria das implantações com schema OTel, mas quem usava um schema personalizado não tinha uma forma prática de montar a visualização com base nos próprios atributos.

Agora você pode usar qualquer atributo de uma linha de log para definir a visualização de contexto, seja ele de um schema OTel ou de um schema personalizado. As opções habituais de serviço, pod do Kubernetes e nó continuam disponíveis, mas você pode, com a mesma facilidade, agrupar pela versão do SDK de telemetria ou por qualquer outro campo da linha de log. Também é possível limpar a seleção a qualquer momento e recomeçar.

**PRs relacionados:** [#2558](https://github.com/hyperdxio/hyperdx/pull/2558) fix: support service name expression and quick attribute filters in surrounding context
