## Tratamento aprimorado de secrets em webhooks {#improved-handling-of-secrets-in-webhooks}

*Demonstração por [@dhable](https://github.com/dhable)*

<Frame>
  <iframe src="https://www.youtube.com/embed/aD7sT5dc470" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

URLs e cabeçalhos de webhooks frequentemente expõem credenciais à vista de todos. Uma URL de webhook do Slack traz o token secreto no caminho, e um webhook HTTP normalmente precisa de um cabeçalho Authorization para se autenticar. Até este lançamento, a API interna do HyperDX para listagem e edição de webhooks devolvia todas essas informações em cada requisição, o que permitia que qualquer membro autenticado da equipe lesse os secrets simplesmente acessando a API.

Esta alteração aplica o mesmo padrão de ocultação de dados sensíveis que a API pública já utilizava. As URLs de webhooks são retornadas com o caminho substituído por `****`, de modo que o token do Slack (ou qualquer outra chave embutida no caminho) nunca sai do servidor. Os cabeçalhos também são ocultados por padrão, já que não há uma forma confiável de identificar quais deles contêm secrets; por isso, todos os valores são substituídos por `****` e apenas os nomes dos cabeçalhos ficam visíveis.

O formulário de edição trata o valor ocultado como &quot;sem alteração&quot;: se você não mexer nele, o valor armazenado é mantido; se alterá-lo, o novo valor é salvo; se apagá-lo, o campo é removido por completo. Isso mantém o fluxo de trabalho intuitivo para o caso mais comum (editar um único campo), sem que o secret real precise fazer ida e volta pelo navegador.

## Metadados extras em alertas {#extra-metadata-in-alerts}

*Demonstração por [@dhable](https://github.com/dhable)*

<Frame>
  <iframe src="https://www.youtube.com/embed/evEd7Cc9e1c" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Um pedido do Slack da comunidade para adicionar contexto em formato livre aos alertas: um lugar para registrar o histórico de limiares, links para runbooks ou notas para quem está de plantão. Isso também é útil como fonte de verdade para resumos gerados por IA: qualquer LLM que responda a um alerta disparado agora pode se basear no raciocínio do próprio operador, em vez de tentar deduzir a intenção apenas a partir da consulta.

O campo de nota aceita renderização em Markdown, então seções recolhíveis, listas e links funcionam normalmente. Ele faz parte da configuração do alerta e aparece em todos os lugares onde o alerta é exibido. A UX ainda não é definitiva: a superfície em Markdown é o ponto de partida, e sugestões sobre como ela deve ser renderizada são bem-vindas.

Aproveitando a mudança, este PR também aprimora a UX de alertas disparados em pesquisas salvas. O ícone de sino no botão Alertas ganha um ponto vermelho quando há algo disparando, a caixa de diálogo destaca qual alerta está ativo em vez de apenas apontar para ele, e a linguagem visual agora segue o que os painéis do dashboard já fazem para o mesmo estado.

**PRs relacionados:** [#2210](https://github.com/hyperdxio/hyperdx/pull/2210) [HDX-3044] Add optional note field to alertas

## Temas possíveis {#possible-themes}

*Demonstração por [@elizabetdev](https://github.com/elizabetdev)*

<Frame>
  <iframe src="https://www.youtube.com/embed/JZYGz6ZOPf4" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />
</Frame>

Este foi um experimento de hackathon que introduziu três temas inspirados em IDEs na UI do ClickStack: Nord (tons de azul ártico), Catppuccin (pastel) e One Dark (estilo Atom), cada um com variantes clara e escura. Testamos tokens de cor gerados a partir dos temas originais, o que resolveu a maior parte do trabalho, restando algumas arestas a aparar nas cores da barra lateral e no contraste das linhas, que ainda precisariam de ajustes.

O PR acabou sendo fechado em vez de mesclado. A equipe está migrando para o ClickUI, que atualmente oferece suporte a um único tema, e manter vários conjuntos paralelos de tokens geraria trabalho contínuo, especialmente quando se começa a verificar o contraste de forma adequada em cada combinação. A decisão foi aguardar até que o próprio ClickUI ofereça suporte a múltiplos temas.

Consideramos que uma parte da lógica de design do experimento merece ser lembrada para quando a ideia for retomada. A primeira iteração recoloria o logotipo do HyperDX conforme o tema, o que descaracterizava a marca. A abordagem mais limpa: um tema claro exibe o logotipo escuro, um tema escuro exibe o logotipo claro, e a logomarca verde do HyperDX em si permanece inalterada.

**PRs relacionados:** [#2191](https://github.com/hyperdxio/hyperdx/pull/2191) feat: add IDE-inspired temas (Nord, Catppuccin, One Dark)
