## Validação de modelos de corpo de webhook antes de salvar {#validating-webhook-body-templates-before-they-save}

*Demonstração por [@brandon-pereira](https://github.com/brandon-pereira)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Antes, era possível salvar um webhook Generic ou incident.io com um modelo de corpo quebrado sem receber nenhum aviso. A partir daí, todas as entregas de alerta falhavam, e o erro só aparecia nos rastros e nos logs do servidor do ClickStack. Uma causa comum era aplicar escape de JSON às aspas dentro de uma expressão Handlebars, como em `{{#if (eq state \"ALERT\")}}`: um JSON válido, mas um modelo inválido.

Agora, o formulário de webhook verifica o modelo enquanto você edita e exibe os erros abaixo do editor, com a linha e a coluna, como em `Template error on line 1, column 29`. A verificação aguarda 300 ms após você parar de digitar, para não acusar erro no meio de uma expressão `{{ … }}`. Corpos vazios são ignorados, pois usam o modelo padrão do serviço, assim como os corpos do Slack, que não são renderizados. Abaixo do editor, você também encontra as variáveis compatíveis, como `{{alertId}}`, `{{status}}`, `{{value}}` e `{{groupKey}}`, cada uma com uma breve descrição.

A mesma validação agora é executada no lado do servidor na API interna, na API externa v2 e na ferramenta MCP `clickstack_save_webhook`. Modelos inválidos retornam 400 na criação, atualização ou teste, junto com o erro do Handlebars e a respectiva linha e coluna. Os testes falham antes que qualquer coisa seja enviada. A validação apenas verifica se o modelo compila; ela não renderiza o resultado nem verifica se a saída é um JSON válido.

Para fluxos de trabalho automatizados, o novo endpoint `POST /api/v2/webhooks/validate` permite que o Terraform verifique as configurações de webhook durante o plan. Assim como o `POST /api/v2/dashboards/validate`, ele valida sem salvar. O endpoint executa as mesmas verificações de URL e corpo feitas na criação e sempre retorna 200 com `{ valid, errors, normalized }`. A unicidade do nome não é verificada.

**PRs relacionados:** [#3350](https://github.com/hyperdxio/hyperdx/pull/3350) Exibir erros de compilação do modelo de corpo de webhook no editor, [#3365](https://github.com/hyperdxio/hyperdx/pull/3365) Rejeitar modelos de corpo de webhook que não compilam e adicionar /api/v2/webhooks/validate

## Detecção automática de uma fonte de dados PromQL durante a configuração inicial {#auto-detecting-a-promql-source-during-onboarding}

*Demonstração por [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=96" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Quando uma conexão não tem fontes de dados, o ClickStack procura tabelas do OpenTelemetry e cria automaticamente fontes de dados de Logs, Traces, Metrics e Sessions. Com o PromQL habilitado (`NEXT_PUBLIC_ENABLE_PROMQL=true`), ele agora também cria uma fonte de dados PromQL se encontrar uma tabela `TimeSeries` do ClickHouse.

A detecção procura tabelas com `engine = 'TimeSeries'`, ignorando as tabelas MergeTree internas criadas por elas. Se houver mais de um candidato, a verificação segue esta ordem:

* `prometheus.metrics`, a tabela usada na [documentação do ClickHouse sobre Prometheus](https://clickhouse.com/docs/concepts/features/interfaces/prometheus#create-a-timeseries-table).
* `metrics_ts` no mesmo banco de dados das tabelas do OpenTelemetry, criada pela migração PromQL do coletor.
* `metrics_ts` em qualquer banco de dados.

Se houver apenas uma tabela `TimeSeries`, o ClickStack a utiliza, seja qual for o nome dela.

Conexões que têm apenas uma tabela `TimeSeries` agora recebem uma fonte de dados PromQL sem serem encaminhadas para a configuração manual. Se a detecção ou a criação da fonte de dados PromQL falhar, as demais fontes de dados são mantidas.

**PRs relacionados:** [#3310](https://github.com/hyperdxio/hyperdx/pull/3310) Detecção automática de uma fonte de dados PromQL durante a configuração inicial, [#3311](https://github.com/hyperdxio/hyperdx/pull/3311) Provisionamento de uma fonte de dados PromQL nas fontes de dados padrão de desenvolvimento

## Limites de séries e granularidade mínima para gráficos PromQL {#series-limits-and-minimum-granularity-for-promql-charts}

*Demonstração por [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=176" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Os gráficos PromQL de linha e de barras empilhadas agora têm a mesma configuração de exibição **Limite de séries** dos gráficos do construtor e de SQL bruto. Antes, eles limitavam as séries renderizadas a 250 no navegador, com uma opção para carregar o restante, mas a configuração ficava oculta e não era salva com o bloco.

O limite é aplicado no navegador, assim como nos gráficos de SQL bruto. O próprio parâmetro `limit` do Prometheus retorna um subconjunto ordenado por labels, e não as séries com os maiores valores, e o fallback por função de tabela do ClickHouse o ignora. A dica sobre séries ocultas também traz orientações específicas de PromQL: restrinja seus matchers de label ou adicione `sum by (...)`, em vez de usar `GROUP BY` ou `WHERE`.

As fontes de dados PromQL agora também têm a configuração **Granularidade automática mínima**, assim como as fontes de dados de métricas. Ela define o menor tamanho de bucket que a granularidade automática pode escolher para gráficos de linha, número, tabela, pizza e barras, incluindo as prévias PromQL geradas para eles. `$__rate_interval` também usa esse valor como intervalo de scrape, recorrendo a 15s como alternativa quando ele não está definido. As configurações explícitas de granularidade dos blocos não foram alteradas.

**PRs relacionados:** [#3292](https://github.com/hyperdxio/hyperdx/pull/3292) Suporte à granularidade automática mínima em fontes de dados PromQL, [#3294](https://github.com/hyperdxio/hyperdx/pull/3294) Suporte ao limite de séries em gráficos temporais PromQL

## Controle de acesso por fonte de dados para fontes de dados PromQL {#source-level-access-control-for-promql-sources}

*Demonstração por [@karl-power](https://github.com/karl-power)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=301" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**Esta funcionalidade se aplica apenas ao Managed ClickStack.**

O controle de acesso baseado em funções agora também se aplica às fontes de dados PromQL, assim como já acontece com logs, rastros e métricas. Uma função granular de fonte de dados pode conceder acesso de **Leitura** a uma fonte de dados PromQL e, ao mesmo tempo, restringir outra.

Todas as rotas `/v1/prometheus/*` agora verificam o acesso de **Leitura** à fonte de dados e retornam 403 `RBAC_PERMISSION_DENIED` quando esse acesso não existe. Se as regras de acesso a fontes de dados do chamador ocultarem completamente a fonte de dados, a resposta será 404 `Source not found`, o mesmo comportamento da API de fontes de dados. Esta alteração não adiciona a aplicação de funções no lado do ClickHouse: no ClickStack Cloud, as consultas PromQL já usam o próprio token do usuário.

## Filtros ad hoc para dashboards {#ad-hoc-filters-for-dashboards}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=401" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Os dashboards agora contam com o tipo de filtro **Ad hoc chaves e valores**, ao lado das variáveis e dos filtros já existentes. Cada filtro ad hoc usa uma ou mais fontes de dados do ClickHouse, como logs e rastros, ou uma fonte de dados do Prometheus para sugerir as chaves e os valores disponíveis. Por padrão, as condições se aplicam a todos os blocos que usam essas fontes de dados, mas você pode restringir as fontes de dados às quais elas se aplicam. A funcionalidade é habilitada pela flag `NEXT_PUBLIC_ENABLE_ADHOC_FILTERS`, e cerca de metade do trabalho planejado já foi concluída.

Clique no campo de entrada do filtro na barra de filtros do dashboard para escolher uma chave, um operador e um valor, com sugestões tanto para chaves quanto para valores. Fontes de dados SQL oferecem suporte a equals, not equals, regex, not regex, `LIKE` e `NOT LIKE`. Fontes de dados PromQL usam labels do Prometheus em vez de chaves de coluna. As condições aplicadas aparecem como pills que você pode editar, transformar em exclusões ou remover. As seleções ficam armazenadas na URL e podem ser salvas como parte do estado de filtro padrão do dashboard.

A forma como as condições chegam a um bloco depende do tipo dele:

* Blocos do construtor usam a propriedade de configuração `filter` existente, portanto não é necessário adicionar uma variável à sua cláusula `WHERE`.
* Blocos de SQL bruto usam `$__filters`. Sua consulta precisa incluir essa macro, e um aviso será exibido caso ela esteja ausente. Quando nenhuma condição está aplicada, ela é expandida para `1 = 1`.
* Blocos PromQL usam a mesma biblioteca de parser do Grafana para adicionar as condições como matchers de label a cada seletor de métrica.

As condições aplicadas podem ser vistas nas pré-visualizações do SQL gerado e do PromQL.

Também é possível filtrar diretamente a partir de **blocos de busca**. Passe o cursor sobre uma célula para abrir as mesmas opções de copiar, filtrar e excluir da página de busca. Ao filtrar, o valor é adicionado ao filtro ad hoc correspondente; clicar novamente no mesmo valor o remove. Se você abrir uma linha no painel lateral, os botões de filtro dela também se aplicam ao dashboard. Por enquanto, o recurso de clicar para filtrar está disponível apenas em blocos de busca.

Ao importar um dashboard, você pode remapear tanto as fontes de dados consultadas por um filtro ad hoc quanto aquelas às quais ele se aplica. A API externa e o MCP ainda não oferecem suporte a filtros ad hoc.

**PRs relacionados:** [#3335](https://github.com/hyperdxio/hyperdx/pull/3335) Adiciona esquemas e tipos para filtros ad hoc de dashboard, [#3317](https://github.com/hyperdxio/hyperdx/pull/3317) Extrai FilterPill e adiciona componentes do editor de filtros, [#3341](https://github.com/hyperdxio/hyperdx/pull/3341) Adiciona UI para configurar filtros ad hoc de dashboard, [#3343](https://github.com/hyperdxio/hyperdx/pull/3343) Renderiza os campos de entrada dos filtros ad hoc de dashboard, [#3366](https://github.com/hyperdxio/hyperdx/pull/3366) Difunde as condições dos filtros ad hoc de dashboard, [#3367](https://github.com/hyperdxio/hyperdx/pull/3367) Suporte ao remapeamento de fontes de dados durante a importação de filtros ad hoc, [#3380](https://github.com/hyperdxio/hyperdx/pull/3380) Suporte a clicar para aplicar filtro ad hoc em blocos de busca

## Movendo SELECT e ORDER BY para a tabela de resultados {#moving-select-and-order-by-into-the-results-table}

*Demonstração por [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=636" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**Este é um trabalho exploratório, sem compromisso de lançamento.**

Atualmente, a página de busca exibe `SELECT` e `ORDER BY` ao lado de `WHERE`, embora eles afetem apenas a tabela de resultados. Ao alternar para Padrões de eventos ou Deltas de eventos, eles continuam lá, mas alterá-los não surte efeito algum. Os usuários com quem conversamos também não perceberam que era no `SELECT` que podiam escolher as colunas. Eles procuravam controles de colunas e de ordenação.

Este protótipo move ambos para a barra de ferramentas da tabela de resultados como **Columns** e **Sort**, ocultando-os em Deltas de eventos e Padrões de eventos. **Columns** lista os itens atuais do seu `SELECT`, com opções para arrastá-los e reordená-los ou removê-los. Escolha uma sugestão ou digite uma expressão como `upper(Body) as message` e clique em **Add**. Uma aba **SQL** permite editar o `SELECT` completo diretamente.

**Sort** lista cada campo do `ORDER BY` e sua direção, incluindo tuplas como `(toDateTime(Timestamp), Timestamp) DESC`. Você também pode editar a cláusula bruta em **SQL**. Expressões que os controles não conseguem decompor, como `Timestamp DESC NULLS LAST`, são abertas na aba SQL. As alterações feitas nos controles geram o SQL automaticamente, mas você ainda pode escrevê-lo manualmente.

**Apply** atualiza a cláusula e executa a busca, **Cancel** descarta suas alterações e **Reset to default** restaura o padrão da fonte de dados. As ações da tabela para redefinir larguras, quebrar linhas, visualizar o SQL gerado e exportar CSV passam a ser botões de ícone à direita da barra de ferramentas.

Com isso, o formulário de busca também ganha um pouco mais de espaço. A fonte de dados fica à esquerda da primeira linha, com **Update** e **Alerts** à direita. A cláusula `WHERE` ganha uma linha própria de largura total, junto com Live Tail, o intervalo de atualização e **Run**.

O PR ainda é um rascunho, e adoraríamos saber o que você achou da experiência de uso.

**PRs relacionados:** [#3387](https://github.com/hyperdxio/hyperdx/pull/3387) Editar colunas e ordenação da busca a partir da tabela de resultados (aberto)

## Uma página de busca utilizável no celular {#a-usable-search-page-on-a-phone}

*Demonstração por [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=843" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Abrir um alerta no celular deveria levar você direto aos logs. Antes, a barra lateral de filtros não podia ficar com menos de 200px, a linha da consulta não quebrava e os resultados ficavam cortados dentro de um quadro de `100vh`. Não dava nem para rolar até os logs.

Agora, a página de busca passa para um layout compacto abaixo de 900px, largura em que a navegação já é recolhida. Os filtros começam fechados e abrem em um painel deslizante pelo botão **Show filters**, deixando toda a largura livre para a tabela de logs. `SELECT` e `ORDER BY` ficam ocultos atrás de um botão de alternância **Columns**, enquanto a caixa de busca continua visível. O histograma também continua, reduzido para 72px, e os resultados rolam no espaço abaixo da barra de ferramentas. Abrir o painel deslizante de filtros não altera sua preferência no desktop, e alargar a janela para mais de 900px restaura o layout de desktop.

O hook de área de visualização compacta e o painel lateral responsivo ficam em `packages/app/src/components/CompactViewport/`, prontos para serem reaproveitados por outras páginas. A Busca é a primeira a usá-los. Essa mudança foi integrada antes do protótipo de colunas e ordenação abordado nesta publicação, que levaria `SELECT` e `ORDER BY` para a tabela de resultados em qualquer largura de tela.

**PRs relacionados:** [#3376](https://github.com/hyperdxio/hyperdx/pull/3376) Manter a pesquisa salva utilizável no celular

## Streaming de chaves e valores de filtros na barra lateral {#streaming-filter-keys-and-values-into-the-sidebar}

*Demonstração por [@knudtty](https://github.com/knudtty)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/Lb77q9zFVmA?start=899" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Antes, a barra lateral de filtros da página de busca exibia um único indicador de carregamento até que todas as consultas de filtros terminassem. As consultas já transmitiam seus resultados em fluxo, mas ainda era preciso esperar a mais lenta para poder usar qualquer filtro.

Agora, as chaves aparecem primeiro, cada uma com seu próprio indicador de carregamento, e os valores são preenchidos à medida que cada consulta retorna. As consultas em si não mudaram; a barra lateral apenas exibe os resultados conforme eles chegam. A diferença é especialmente perceptível em intervalos de tempo mais longos, como uma busca de dois dias.

Também corrigimos o problema de a barra lateral não lembrar o estado em que você a deixou. Para manter o navegador responsivo, os grupos de filtros são removidos do DOM quando saem da área visível. Antes, ao rolar de volta, os grupos expandidos apareciam recolhidos e as distribuições já carregadas tinham sumido. Agora, ambos permanecem como você os deixou.

**PRs relacionados:** [#3348](https://github.com/hyperdxio/hyperdx/pull/3348) Stream filter keys and value results to UI, [#3377](https://github.com/hyperdxio/hyperdx/pull/3377) Persist filter expand state upon scrolling
