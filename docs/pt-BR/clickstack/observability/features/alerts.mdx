O ClickHouse Observability oferece suporte nativo a alertas, permitindo que as equipes detectem e respondam a problemas em tempo real em logs, métricas e rastros.

Os alertas podem ser criados diretamente na interface do usuário e se integram a sistemas de notificação populares, como Slack e PagerDuty.

Os alertas funcionam de forma integrada em todos os seus dados de observabilidade, ajudando você a acompanhar a integridade do sistema, detectar regressões de desempenho e monitorar eventos de negócio importantes.

## Tipos de alertas {#types-of-alerts}

Você pode criar alertas a partir de uma **pesquisa salva**, diretamente no **Chart Explorer** ou a partir de um **gráfico em um dashboard salvo**. Os alertas de pesquisa contam os eventos correspondentes, enquanto os alertas de gráfico avaliam os valores calculados pelo gráfico.

### Alertas de pesquisa {#search-alerts}

Os alertas de pesquisa permitem disparar notificações com base nos resultados de uma pesquisa salva. Eles ajudam a detectar quando eventos ou padrões específicos ocorrem com mais (ou menos) frequência do que o esperado.

Um alerta é acionado quando a contagem de resultados correspondentes em uma janela de tempo definida fica acima ou abaixo de um limiar especificado.

Para criar um alerta de pesquisa:

Para criar um alerta para uma pesquisa, é preciso que ela esteja salva. Você pode criar o alerta para uma pesquisa salva existente ou salvar a pesquisa durante a criação do alerta. No exemplo abaixo, consideramos que a pesquisa ainda não foi salva.

<Steps>
  <Step title="Abra a caixa de diálogo de criação de alerta" id="open-dialog">
    Comece inserindo uma [pesquisa](/pt-BR/clickstack/observability/features/search) e clicando no botão `Alerts` no canto superior direito da página `Search`.

    <div className="ch-image-lg">
      <Frame>
        ![Visualização de pesquisa com o botão Alerts destacado](/images/clickstack/observability-alerts-search.png)
      </Frame>
    </div>
  </Step>

  <Step title="Crie o alerta" id="create-the-alert">
    No painel de criação de alerta, você pode:

    * Atribuir um nome à pesquisa salva associada ao alerta.
    * Escolher um operador de comparação, uma contagem de eventos correspondentes e uma janela de tempo. Por exemplo, disparar quando pelo menos 10 eventos correspondentes ocorrerem em 5 minutos.
    * Especificar um valor `grouped by`. Isso permite aplicar uma agregação à pesquisa, por exemplo, por `ServiceName`, de modo que vários alertas possam ser acionados a partir da mesma pesquisa.
    * Escolher um destino de notificação, como e-mail ou webhook. Você pode adicionar um novo webhook diretamente nesta tela. Consulte [Adicionando um webhook](#add-webhook) para mais detalhes.

### Integrações por tipo de serviço {#integrations}

Os alertas se integram nativamente aos seguintes tipos de serviço:

* **Slack**: envie notificações diretamente para um canal por meio de webhook ou da API.
* **PagerDuty**: roteie incidentes para equipes de plantão por meio da API do PagerDuty.
* **incident.io**: envie alertas para o incident.io.
* **Generic**: conecte alertas a qualquer sistema ou fluxo de trabalho personalizado por meio de um webhook genérico.

<Info>
  **Integrações exclusivas do ClickHouse Cloud**

  As integrações com a API do Slack e com o PagerDuty estão disponíveis apenas no ClickHouse Cloud.
</Info>

Dependendo do tipo de serviço, você precisará fornecer informações diferentes, a saber:

**Slack (URL do webhook)**

* URL do webhook. Por exemplo: `https://hooks.slack.com/services/<unique_path>`. Consulte a [documentação do Slack](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/) para mais detalhes.

**Slack (API)**

* Token de bot do Slack. Consulte a [documentação do Slack](https://docs.slack.dev/authentication/tokens/#bot/) para mais detalhes.

**API do PagerDuty**

* Chave de integração do PagerDuty. Consulte a [documentação do PagerDuty](https://support.pagerduty.com/main/docs/api-access-keys) para mais detalhes.

**Generic**

* URL do webhook
* Cabeçalhos do webhook (opcional)
* Corpo do webhook (opcional). O corpo é um template Handlebars. Além de `{{title}}`, `{{body}}` e `{{link}}`, ele pode usar variáveis que descrevem o alerta e o disparo, como `{{alertId}}`, `{{status}}`, `{{value}}`, `{{threshold}}` e `{{groupKey}}`. Consulte [Variáveis de template de webhook de alerta](https://github.com/ClickHouse/ClickStack/blob/main/docs/alert-webhook-template-variables.md) para ver a lista completa.

* **Barra vermelha**: a condição de limiar foi atendida nessa avaliação e o alerta disparou (notificação enviada)

## Alertas de gráfico baseados em SQL {#sql-based-alerts}

Os alertas de gráfico baseados em SQL permitem escrever qualquer consulta em SQL do ClickHouse para definir as condições de alerta. Isso oferece controle total sobre filtragem, agregação e cálculos: tudo o que puder ser expresso em SQL pode se tornar um alerta.

### Tipos de gráfico compatíveis {#supported-chart-types}

Alertas baseados em SQL são compatíveis com três tipos de exibição de gráfico:

| Tipo de gráfico     | Comportamento                                                                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **linha**           | Alerta de séries temporais. A consulta deve produzir linhas agrupadas em buckets de tempo. Cada bucket é avaliado de forma independente em relação ao limiar. |
| **Barra Empilhada** | Alerta de séries temporais. Mesmo comportamento do tipo linha.                                                                                                |
| **Número**          | Alerta de valor único. A consulta retorna um único resultado numérico, que é comparado ao limiar uma vez a cada avaliação.                                    |

Os demais tipos de gráfico baseados em SQL (Tabela, Pizza, Mapa de calor etc.) não oferecem suporte a alertas.

Para criar um alerta em um gráfico baseado em SQL:

    Escolha **linha**, **Barra Empilhada** ou **Número** como tipo de exibição.

### Como os resultados da consulta são interpretados {#sql-result-interpretation}

O sistema de alertas inspeciona as colunas retornadas pela sua consulta SQL para determinar o que comparar com o limiar.

* **Coluna de valor**: A **última coluna numérica** da sua cláusula `SELECT` é usada como valor do alerta. Se a sua consulta retornar várias colunas numéricas (por exemplo, `count, avg_latency, p99_latency`), apenas a última (`p99_latency`) será comparada com o limiar.
* **Coluna de timestamp**: Em gráficos de séries temporais (linha e Barra Empilhada), o sistema identifica a coluna Date/DateTime nos seus resultados como o intervalo de tempo (ou seja, o eixo x de um gráfico de séries temporais). A coluna de valor de cada intervalo de tempo é avaliada em relação ao limiar de forma independente e, se o valor de qualquer intervalo de tempo ultrapassar o limiar configurado, o alerta será disparado.
* **Colunas de grupo**: Todas as colunas não numéricas que não sejam de timestamp (por exemplo, `ServiceName`, `Environment`) são tratadas como dimensões de agrupamento. Quando há grupos, cada combinação única de valores de grupo é monitorada e gera alertas separadamente. O serviço enviará um alerta para cada grupo cujo valor ultrapasse o limiar configurado. Grupos estão disponíveis apenas para gráficos de séries temporais.

### Parâmetros de consulta e macros {#query-params}

As consultas SQL de alerta oferecem suporte a parâmetros de template e macros, que são substituídos automaticamente no momento da avaliação. São os mesmos parâmetros e macros disponíveis ao [criar um gráfico baseado em SQL](/pt-BR/clickstack/observability/features/dashboards/sql-visualizations).

#### Parâmetros obrigatórios e recomendados {#required-alert-parameters}

As consultas usadas em alertas de gráficos de linha ou de barras empilhadas **devem** incluir um parâmetro de intervalo ou uma macro (`{intervalSeconds:Int64}`, `{intervalMilliseconds:Int64}`, `$__timeInterval(col)` ou `$__timeInterval_ms(col)`). Durante a execução do alerta, esse valor será substituído pelo período configurado no alerta.

As consultas usadas em alertas **devem, preferencialmente,** incluir um filtro de intervalo de tempo (`{startDateMilliseconds:Int64}` e `{endDateMilliseconds:Int64}`, ou `$__timeFilter(col)` etc.). Com ou sem filtro de intervalo de tempo na consulta, a consulta do alerta será executada sobre o período configurado no alerta. Se não houver filtro de intervalo de tempo, a consulta lerá todo o intervalo de tempo disponível na tabela de origem a cada execução.

<Warning>
  **Intervalo de Tempo do Alerta**

  Normalmente, as consultas de alerta são executadas uma vez por intervalo. No entanto, se um ou mais intervalos forem ignorados devido a erros ou consultas lentas, a execução seguinte usará um intervalo de tempo que abrange os intervalos perdidos. Nesse caso, os parâmetros de intervalo da consulta continuarão definidos com o período configurado no alerta, mas os parâmetros de intervalo de tempo refletirão o intervalo de tempo mais longo.
</Warning>

### Exemplos de consultas de alerta {#example-queries}

#### Taxa de erro por serviço (séries temporais) {#example-error-rate}

Dispare um alerta quando qualquer serviço atingir uma taxa de erro de pelo menos 5%, com mais de 10 requisições no período do alerta, para evitar alertas ruidosos em serviços de baixo tráfego.

```sql
WITH error_rates AS (
  SELECT
    $__timeInterval(Timestamp) as ts,
    ServiceName,
    countIf (SpanKind = 'Server') as request_count,
    countIf (
      SpanKind = 'Server'
      and StatusCode = 'Error'
    ) as error_count,
    error_count / request_count * 100 AS error_percent
  FROM $__sourceTable
  WHERE $__timeFilter(Timestamp)
  GROUP BY ts, ServiceName
)
SELECT ts, ServiceName, error_percent
FROM error_rates
WHERE request_count > 10
```

**Tipo de exibição**: linha ou Barra Empilhada
**Limiar**: `>= 5` (dispara quando a taxa de erros atinge 5%)

Nesta consulta, `ServiceName` é uma coluna não numérica e que não é de timestamp, portanto cada serviço é monitorado como um grupo de alerta distinto. O alerta dispara de forma independente para cada serviço.

#### Detecção de anomalias com média defasada (séries temporais) {#example-anomaly-detection}

Dispare um alerta quando as contagens de erros ultrapassarem uma média deslizante em mais de dois desvios-padrão. Isso detecta picos em relação ao comportamento de referência recente, em vez de depender de um limiar fixo.

```sql
WITH buckets AS (
  SELECT
    $__timeInterval(Timestamp) AS ts,
    count() AS bucket_count
  FROM $__sourceTable
  WHERE TimestampTime >= fromUnixTimestamp64Milli({startDateMilliseconds:Int64})
        - toIntervalSecond($__interval_s * 30) -- Fetch 30 intervals back
    AND TimestampTime < fromUnixTimestamp64Milli({endDateMilliseconds:Int64})
    AND SeverityText = 'error'
  GROUP BY ts
  ORDER BY ts
  WITH FILL
    FROM toDateTime(fromUnixTimestamp64Milli({startDateMilliseconds:Int64}))
    TO toDateTime(fromUnixTimestamp64Milli({endDateMilliseconds:Int64}))
    STEP toIntervalSecond($__interval_s)
),

anomaly_detection AS (
  SELECT
    ts,
    bucket_count,
    avg(bucket_count) OVER (
      ORDER BY ts ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING
    ) AS previous_30_avg,
    stddevPop(bucket_count) OVER (
      ORDER BY ts ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING
    ) AS previous_30_stddev,
    greatest(
      bucket_count - (previous_30_avg + 2 * previous_30_stddev), 0
    ) AS excess_error_count
  FROM buckets
)

SELECT ts, excess_error_count
FROM anomaly_detection
WHERE ts >= fromUnixTimestamp64Milli({startDateMilliseconds:Int64})
  AND ts < fromUnixTimestamp64Milli({endDateMilliseconds:Int64})
```

**Tipo de exibição**: linha
**Limiar**: `> 0` (dispara quando são detectados erros em excesso acima da linha de referência deslizante)

Observe que a consulta busca 30 intervalos *antes* do início do intervalo de datas para inicializar os cálculos da janela deslizante e, em seguida, filtra a saída final para incluir apenas a janela de avaliação.

## Cenários comuns de alertas {#common-alert-scenarios}

Veja alguns cenários comuns de alertas que você pode configurar:

**Erros:** Recomendamos configurar alertas para as buscas salvas padrão
`All Error Events` e `HTTP Status >= 400` para ser notificado quando
ocorrer um volume excessivo de erros.

**Operações lentas:** Você pode configurar uma busca por operações lentas (por exemplo,
`duration:>5000`) e, em seguida, criar um alerta para quando houver operações lentas
em excesso.

**Eventos de usuário:** Você também pode configurar alertas para que equipes que atendem clientes sejam
notificadas quando novos usuários se cadastrarem ou quando uma ação crítica de usuário for realizada.
