Envie logs, rastros e métricas dos seus agentes Datadog existentes para o ClickHouse Observability. Suas aplicações podem continuar usando os SDKs do Datadog. Escolha um endpoint gerenciado ou configure um receptor Datadog no seu próprio coletor e, em seguida, siga as mesmas etapas de configuração do agente descritas abaixo.

## Pré-requisitos {#prerequisites}

* Um serviço ClickHouse Observability gerenciado ou autogerenciado.
* Um agente Datadog em execução, coletando os sinais que você deseja migrar. Para rastros, sua aplicação já deve enviar rastros a esse agente por meio de um SDK do Datadog.
* Acesso à rede do agente até o endpoint do seu receptor Datadog.

## Configure o destino {#connection-details}

<Tabs>
  <Tab title="Totalmente gerenciado">
    <BetaBadge label="Oferta Beta" />

    Abra seu serviço e acesse **Team Settings → Data → Managed Telemetry**. Copie o **OTLP HTTP endpoint** e a **chave de API**.

    <div className="ch-image-lg">
      <Frame>
        ![Managed Telemetry exibindo o endpoint OTLP HTTP e a chave de API mascarados](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    O endpoint do Datadog usa o mesmo hostname, com a porta `8126`. Não é necessário nenhum coletor adicional. Use estes valores na configuração do agente abaixo:

    | Configuração             | Valor                                     |
    | ------------------------ | ----------------------------------------- |
    | `YOUR_API_KEY`           | A chave de API de ingestão do seu serviço |
    | `YOUR_DATADOG_URL`       | `https://YOUR_OTEL_HOST:8126`             |
    | `YOUR_DATADOG_HOST_PORT` | `YOUR_OTEL_HOST:8126`                     |
    | `logs_no_ssl`            | `false`                                   |
  </Tab>

  <Tab title="Autogerenciado" id="self-managed">
    O [Coletor OpenTelemetry do ClickStack](/pt-BR/clickstack/self-configured/ingesting-data/collector) inclui o [receptor Datadog](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/datadogreceiver). Configure o receptor e conecte-o aos seus pipelines de logs, rastros e métricas.

    Salve o overlay de configuração a seguir como `datadog-collector.yaml`. Ele adiciona o receptor Datadog aos pipelines de logs, rastros e métricas já existentes no coletor, mantendo o receptor OTLP:

    ```yaml
    receivers:
      datadog:
        endpoint: 0.0.0.0:8126

    service:
      pipelines:
        logs/in:
          receivers: [otlp/hyperdx, datadog]
        traces:
          receivers: [otlp/hyperdx, datadog]
        metrics:
          receivers: [otlp/hyperdx, datadog]
    ```

    Defina os detalhes de conexão do ClickHouse e inicie o coletor. Na inicialização normal, o schema de telemetria é criado no banco de dados especificado por `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`; o usuário do ClickHouse precisa ter permissão para criar o banco de dados e as tabelas. Se você já tiver um banco de dados de telemetria, use o nome dele.

    Este exemplo requer Docker, usa a versão `2.40.0` do coletor e expõe o receptor Datadog apenas no host local:

    ```shell
    export CLICKHOUSE_ENDPOINT='https://YOUR_CLICKHOUSE_HOST:8443'
    export CLICKHOUSE_USER='YOUR_CLICKHOUSE_USER'
    export CLICKHOUSE_PASSWORD='YOUR_CLICKHOUSE_PASSWORD'
    export HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE='default'

    docker run --rm --name datadog-collector \
      -e CLICKHOUSE_ENDPOINT \
      -e CLICKHOUSE_USER \
      -e CLICKHOUSE_PASSWORD \
      -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE \
      -e CUSTOM_OTELCOL_CONFIG_FILE=/etc/datadog-collector.yaml \
      -v "$(pwd)/datadog-collector.yaml:/etc/datadog-collector.yaml:ro" \
      -p 127.0.0.1:18126:8126 \
      clickhouse/clickstack-otel-collector:2.40.0
    ```

    Deixe o coletor em execução neste terminal enquanto configura e verifica o agente. Use outro terminal para os demais comandos.

    Use estes valores para um agente em execução no mesmo host:

    | Configuração             | Valor                                                                               |
    | ------------------------ | ----------------------------------------------------------------------------------- |
    | `YOUR_API_KEY`           | Qualquer placeholder não vazio, como `local-test`; este receptor local não o valida |
    | `YOUR_DATADOG_URL`       | `http://localhost:18126`                                                            |
    | `YOUR_DATADOG_HOST_PORT` | `localhost:18126`                                                                   |
    | `logs_no_ssl`            | `true`                                                                              |

    A porta `18126` do host mantém este destino separado do listener de rastros de aplicação do agente na porta `8126`. Para um agente em contêiner, conecte os dois contêineres à mesma rede Docker e use `http://datadog-collector:8126` e `datadog-collector:8126` como valores de destino.

    Este exemplo usa um listener HTTP sem autenticação, restrito ao host local. Para agentes em outros hosts, providencie um caminho de rede protegido e configure TLS e autenticação no seu ingress antes de expor o receptor. `OTLP_AUTH_TOKEN` configura a autenticação OTLP do coletor, mas não protege este listener do Datadog.

## Configure o agente Datadog {#configure-datadog-agent}

Atualize o [arquivo de configuração `datadog.yaml`](https://docs.datadoghq.com/agent/configuration/agent-configuration-files/) do seu agente. Normalmente, ele fica em `/etc/datadog-agent/datadog.yaml` no Linux e em `/opt/datadog-agent/etc/datadog.yaml` no MacOS.

Mescle as seguintes configurações à sua configuração existente, usando os valores de destino da aba acima:

```yaml
api_key: "YOUR_API_KEY"

# Metrics destination
dd_url: "YOUR_DATADOG_URL"

# Use the v2 metrics intake.
use_v3_api:
  series:
    enabled: false

# Trace destination
apm_config:
  enabled: true
  apm_dd_url: "YOUR_DATADOG_URL"
  features:
    - disable-convert-traces

# Log destination
logs_enabled: true
logs_config:
  logs_dd_url: "YOUR_DATADOG_HOST_PORT"
  force_use_http: true
  logs_no_ssl: false # Set to true for the local HTTP receiver.

remote_updates: false
remote_configuration:
  enabled: false
```

Substitua `YOUR_DATADOG_URL` pela URL de destino completa e `YOUR_DATADOG_HOST_PORT` pelo respectivo `hostname:port`, sem o esquema. Defina `logs_no_ssl` com o valor especificado para o seu destino.

<Note>
  `disable-convert-traces` mantém as cargas úteis de rastro do agente compatíveis com o receptor Datadog. Com o Datadog agente 7.85.2 e o coletor core 0.155.0, a carga útil indexada padrão do agente foi aceita com HTTP 200, mas não gerou nenhum span. Use a configuração acima para o encaminhamento de rastros e preserve as demais entradas da sua lista `apm_config.features` existente.
</Note>

Mantenha as integrações de coleta de logs e a configuração de tracing de aplicações que você já usa. Essas configurações alteram apenas para onde o agente envia a telemetria; elas não habilitam a coleta de logs para aplicações individuais nem adicionam instrumentação. Se você configura o agente por meio de [variáveis de ambiente](https://docs.datadoghq.com/agent/guide/environment-variables/), atualize também as configurações correspondentes nelas, incluindo `DD_API_KEY`.

Esta configuração redireciona os logs, rastros e métricas do agente do Datadog para o ClickHouse Observability. Para avaliá-la antes, aplique-a a um agente de teste e só depois atualize o restante da sua implantação.

## Reiniciar e verificar {#restart-and-verify}

Reinicie o agente para aplicar a configuração. No Linux:

```shell
sudo systemctl restart datadog-agent
sudo datadog-agent status
```

No MacOS:

```shell
sudo launchctl kickstart -k system/com.datadoghq.agent
```

Para um agente em contêiner, atualize a configuração e implante o contêiner novamente.

Gere nova atividade na aplicação e, em seguida, abra o ClickHouse Observability e selecione um intervalo de tempo recente:

* **Logs:** selecione sua fonte de logs e filtre pelo `ServiceName` da aplicação.
* **Rastros:** selecione sua fonte de rastros e filtre pelo `ServiceName` da aplicação.
* **Métricas:** busque uma métrica emitida pela sua aplicação ou pelo agente. Para um teste com DogStatsD, emita um gauge com nome definido e verifique seu valor.

Se os dados não aparecerem, verifique se há erros de entrega no status do agente. Confira o hostname, a porta, a chave de API e as configurações de acesso à rede do seu serviço. Confirme que o agente está coletando o sinal correspondente e que todas as substituições feitas por variáveis de ambiente apontam para o mesmo destino.

Para rastros, verifique um ID do rastro conhecido em vez de confiar apenas nos contadores de entregas bem-sucedidas do agente. Se um filtro de serviço ocultar o rastro, pesquise por `TraceId`: o receptor pode usar o serviço base do tracer como nome do serviço do recurso e, ao mesmo tempo, manter uma substituição de serviço por span no atributo de span `service.name`. Defina `DD_SERVICE` na configuração de tracing da sua aplicação para estabelecer o nome do serviço base.

## Sinais compatíveis {#supported-signals}

O receptor Datadog é experimental. Ele converte logs, rastros e métricas compatíveis do Datadog para o modelo de dados do OpenTelemetry usado pelo ClickHouse Observability. A configuração acima seleciona a ingestão de métricas v2; as demais funcionalidades do backend do Datadog não fazem parte deste fluxo de migração.

Você pode manter a instrumentação do Datadog que já utiliza enquanto migra gradualmente suas aplicações para o OpenTelemetry.

Com um Coletor do ClickStack autogerenciado, as aplicações também podem enviar métricas personalizadas do DogStatsD diretamente ao coletor, que também pode derivar métricas de requisições, erros e duração a partir dos rastros. Consulte [Recebendo métricas StatsD](/pt-BR/clickstack/self-configured/ingesting-data/collector#statsd-receiver) e [Derivando métricas a partir de spans](/pt-BR/clickstack/self-configured/ingesting-data/collector#span-metrics).
