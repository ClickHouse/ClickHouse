Este guia trata da migração do Elastic para o **ClickHouse Observability totalmente gerenciado**, a experiência padrão. O ClickHouse gerencia os esquemas e o armazenamento subjacentes. Seu pipeline de ingestão deve enviar a telemetria no formato **OpenTelemetry Protocol (OTLP)**; documentos do Elasticsearch não podem ser importados diretamente para o serviço totalmente gerenciado.

Para implantações autogerenciadas, consulte os [conceitos equivalentes entre Elasticsearch e ClickHouse](/pt-BR/clickstack/self-configured/migration/elastic/concepts) e os [mapeamentos de tipos](/pt-BR/clickstack/self-configured/migration/elastic/types). As instruções de migração de dados para ambientes autogerenciados estão indicadas separadamente abaixo.

## Estratégia de operação em paralelo {#parallel-operation-strategy-self-configured}

Ao migrar do Elastic para o ClickHouse Observability em casos de uso de observabilidade, recomendamos uma abordagem de **operação em paralelo** em vez de tentar migrar dados históricos. Essa estratégia oferece diversas vantagens:

1. **Risco mínimo**: ao executar ambos os sistemas concorrentemente, você mantém o acesso aos dados e dashboards existentes enquanto valida o ClickHouse Observability e familiariza seus usuários com o novo sistema.
2. **Expiração natural dos dados**: a maioria dos dados de observabilidade tem um período de retenção limitado (normalmente 30 dias ou menos), o que permite uma transição natural à medida que os dados expiram no Elastic.
3. **Migração simplificada**: dispensa ferramentas ou processos complexos de transferência para mover dados históricos entre os sistemas.

<br />

<Info>
  **Migrando dados**

  Implantações autogerenciadas podem usar o motor de tabela `Elasticsearch` para ler documentos históricos e copiá-los para tabelas do ClickHouse. Consulte [Migrando dados](#migrating-data-self-configured). Esse processo é independente do caminho de ingestão OTLP usado pelo ClickHouse Observability totalmente gerenciado.
</Info>

### Etapas de implementação {#implementation-steps-self-configured}

<Steps>
  <Step title="Configure a ingestão dupla" id="configure-dual-ingestion-self-configured">
    Configure seu pipeline de coleta de dados para enviar dados simultaneamente ao Elastic e ao ClickHouse Observability. No ClickHouse Observability totalmente gerenciado, o pipeline deve exportar OTLP para o endpoint gerenciado usando sua API key de ingestão. Apenas encaminhar documentos JSON do Elasticsearch para esse endpoint não é suficiente.

    A forma de fazer isso depende dos agentes de coleta que você usa atualmente; consulte [&quot;Migração de agentes&quot;](/pt-BR/clickstack/observability/migration/elastic/migrating-agents).
  </Step>

  <Step title="Ajuste os períodos de retenção" id="adjust-retention-period-self-configured">
    Revise os períodos de retenção em ambos os sistemas para que os dados históricos continuem disponíveis durante a transição. Consulte [Retenção e TTL](#retention-and-ttl-self-configured) para orientações específicas de cada tipo de implantação.
  </Step>

  <Step title="Valide e compare" id="validate-and-compare-self-configured">
    * Execute consultas em ambos os sistemas para garantir a consistência dos dados
    * Compare o desempenho das consultas e os resultados
    * Migre dashboards e alertas para o ClickHouse Observability. Atualmente, esse processo é manual.
    * Verifique se todos os dashboards e alertas críticos funcionam como esperado no ClickHouse Observability
  </Step>

  <Step title="Transição gradual" id="graudal-transition-self-configured">
    * À medida que os dados expirarem naturalmente no Elastic, você passará a depender cada vez mais do ClickHouse Observability
    * Depois de ganhar confiança no ClickHouse Observability, você poderá começar a redirecionar consultas e dashboards
  </Step>
</Steps>

### Retenção de longo prazo {#long-term-retention-self-configured}

Para organizações que exigem períodos de retenção mais longos:

* Continue executando ambos os sistemas em paralelo até que todos os dados tenham expirado no Elastic
* Em implantações autogerenciadas, considere usar [visões materializadas](/pt-BR/concepts/features/materialized-views/incremental-materialized-view) para manter dados históricos agregados ou filtrados e, ao mesmo tempo, permitir que os dados brutos expirem.

### Cronograma de migração {#migration-timeline-self-configured}

O cronograma de migração dependerá dos seus requisitos de retenção de dados:

* **Retenção de 30 dias**: a migração pode ser concluída em até um mês.
* **Retenção mais longa**: mantenha a operação em paralelo até que os dados expirem no Elastic.
* **Dados históricos**: consulte as orientações específicas para cada tipo de implantação em [Migrando dados](#migrating-data-self-configured) antes de planejar uma importação.

## Retenção e TTL {#retention-and-ttl-self-configured}

<Tabs>
  <Tab title="Totalmente gerenciado">
    <BetaBadge label="Oferta Beta" />

    <Note>
      O ClickHouse Observability totalmente gerenciado retém os dados por 30 dias durante a fase Beta. A retenção será atualizada na disponibilidade geral (GA), e novas instruções serão divulgadas posteriormente.
    </Note>

    Planeje a transição levando em conta esse período de retenção de 30 dias e a retenção configurada no Elastic. Mantenha o Elastic disponível para buscas históricas até que esses dados não sejam mais necessários.
  </Tab>

  <Tab title="Autogerenciado">
    O ClickHouse usa [cláusulas TTL](/pt-BR/clickstack/self-configured/managing/production#configure-ttl-managed) em tabelas `MergeTree` para excluir automaticamente os dados expirados.

    Alinhe a retenção das suas tabelas aos requisitos da migração. Para ver exemplos, consulte [configuração de TTL em produção autogerenciada](/pt-BR/clickstack/self-configured/managing/production#configure-ttl-managed).
  </Tab>
</Tabs>

## Migrando dados {#migrating-data-self-configured}

<Tabs>
  <Tab title="Totalmente gerenciado">
    <BetaBadge label="Oferta Beta" />

    <Note>
      Atualmente, não há um caminho direto para migrar dados históricos do Elasticsearch para o ClickHouse Observability totalmente gerenciado. O endpoint gerenciado aceita telemetria OTLP, e não documentos do Elasticsearch nem exportações JSON. O fluxo de trabalho com o motor de tabela `Elasticsearch` descrito na aba autogerenciada não se aplica a serviços totalmente gerenciados.
    </Note>

    Use ingestão paralela para enviar novos dados de telemetria no **formato OTLP** ao seu serviço gerenciado, mantendo os dados históricos no Elastic. Consulte [Ingestão com OpenTelemetry](/pt-BR/clickstack/observability/ingesting-data/opentelemetry) para obter o endpoint gerenciado e as configurações de autenticação, e [Migração de agentes](/pt-BR/clickstack/observability/migration/elastic/migrating-agents) para conhecer as opções de coleta.

    Se for necessário importar dados históricos, você precisará de um pipeline personalizado que converta documentos do Elasticsearch em logs, rastros ou métricas do OpenTelemetry adequados e os exporte via OTLP. Este guia não fornece um conversor pronto. Considere o período de retenção do serviço gerenciado antes de planejar uma carga de dados históricos.
  </Tab>

  <Tab title="Autogerenciado">
    Use o [motor de tabela `Elasticsearch`](/pt-BR/reference/engines/table-engines/integrations/elasticsearch) para ler documentos diretamente do Elasticsearch e, em seguida, copie-os para uma tabela local do ClickHouse com `INSERT INTO ... SELECT`. Não é necessário nenhum arquivo de exportação nem a instalação do `elasticdump`.

    O motor é somente leitura: criar uma tabela `Elasticsearch` expõe os documentos remotos para consulta, mas não os copia para o armazenamento do ClickHouse.

    <Note>
      A integração com o Elasticsearch é experimental e requer `enable_elasticsearch = 1` em uma versão do ClickHouse compatível. Ela exige o Elasticsearch 7.12 ou posterior e não é compatível com o OpenSearch. Seu serviço ClickHouse precisa conseguir acessar o endpoint do Elasticsearch, e o índice deve ter `_source` habilitado para que o conteúdo dos documentos possa ser lido.
    </Note>

    <Steps>
      <Step title="Conectar ao índice do Elasticsearch" id="connect-elasticsearch-self-managed">
        Execute o SQL a seguir no seu serviço ClickHouse Cloud autogerenciado, substituindo o endpoint, o índice e as credenciais pelos seus próprios valores:

        ```sql
        SET enable_elasticsearch = 1;

        CREATE TABLE elasticsearch_source
        ENGINE = Elasticsearch(
            'https://<elasticsearch-host>:9200',
            '<index-name>',
            '<username>',
            '<password>'
        );

        SELECT _index, _id, document
        FROM elasticsearch_source
        LIMIT 10;
        ```

        A tabela expõe o `_source` de cada documento como a coluna `document` do tipo `JSON`. As colunas virtuais `_id` e `_index` identificam o documento e o índice de origem. Inspecione uma amostra antes de definir o schema de destino.

        O motor também oferece suporte a chaves de API e named collections. Consulte a [referência de autenticação](/pt-BR/reference/functions/table-functions/elasticsearch#authentication).
      </Step>

      <Step title="Copiar documentos para o ClickHouse" id="copy-documents-self-managed">
        Este exemplo armazena os documentos como `JSON` em uma staging table, para que você possa inspecioná-los e transformá-los antes de configurar uma fonte de dados de observabilidade. Execute as instruções no mesmo banco de dados de `elasticsearch_source`:

        ```sql
        CREATE TABLE migrated_elasticsearch_documents
        (
            source_index String,
            document_id String,
            document JSON
        )
        ENGINE = MergeTree
        ORDER BY (source_index, document_id);

        INSERT INTO migrated_elasticsearch_documents
        SELECT _index, _id, document
        FROM elasticsearch_source;
        ```

        Cada leitura usa um point in time do Elasticsearch para garantir um snapshot consistente para aquela consulta. Trata-se de uma cópia única, não de uma replicação contínua. Repetir o insert adiciona as linhas novamente; a chave de ordenação não remove documentos duplicados.

        Para importações maiores, divida o trabalho em lotes sem sobreposição usando o argumento `query` do motor. Use limites absolutos de timestamp na Query DSL do Elasticsearch, pois uma cláusula `WHERE` do ClickHouse não repassa os filtros para o Elasticsearch. Consulte os [exemplos do motor](/pt-BR/reference/engines/table-engines/integrations/elasticsearch#usage-example) e as [limitações](/pt-BR/reference/functions/table-functions/elasticsearch#limitations).
      </Step>

      <Step title="Mapear e validar os dados importados" id="validate-import-self-managed">
        Compare a contagem de documentos e registros representativos com o snapshot de origem. Verifique timestamps, campos ausentes e valores aninhados antes de usar os dados em buscas ou dashboards. O tipo `JSON` pode inferir tipos a partir dos valores, inclusive timestamps, por isso a representação em texto deles pode mudar. Use dicas de tipo JSON explícitas quando precisar controlar os tipos dos campos.

        Projete o schema de observabilidade de destino de acordo com suas consultas e requisitos de retenção e, em seguida, use `INSERT INTO ... SELECT` para extrair e converter campos da staging table. Consulte os [conceitos de Elasticsearch e ClickHouse](/pt-BR/clickstack/self-configured/migration/elastic/concepts), os [mapeamentos de tipos](/pt-BR/clickstack/self-configured/migration/elastic/types) e as [orientações de design de schema](/pt-BR/guides/clickhouse/data-formats/json/schema).

        Copiar os documentos não os converte automaticamente para o schema do OpenTelemetry nem configura uma fonte de dados na UI. Configure a tabela e os mapeamentos de timestamp, mensagem e demais campos usando as [Opções de configuração](/pt-BR/clickstack/self-configured/managing/config).
      </Step>
    </Steps>
  </Tab>
</Tabs>
