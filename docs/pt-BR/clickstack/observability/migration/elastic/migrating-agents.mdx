## Migração de agentes do Elastic {#migrating-agents-from-elastic-self-configured}

O Elastic Stack oferece diversos agentes de coleta de dados de observabilidade. Especificamente:

* A [família Beats](https://www.elastic.co/beats) — como [Filebeat](https://www.elastic.co/beats/filebeat), [Metricbeat](https://www.elastic.co/beats/metricbeat) e [Packetbeat](https://www.elastic.co/beats/packetbeat) —, todos baseados na biblioteca `libbeat`. Esses Beats oferecem suporte ao [envio de dados para Elasticsearch, Kafka, Redis ou Logstash](https://www.elastic.co/docs/reference/beats/filebeat/configuring-output) por meio do protocolo Lumberjack.
* O [`Elastic Agent`](https://www.elastic.co/elastic-agent) é um agente unificado capaz de coletar logs, métricas e traces. Esse agente pode ser gerenciado de forma centralizada pelo [Elastic Fleet Server](https://www.elastic.co/docs/reference/fleet/manage-elastic-agents-in-fleet) e oferece suporte à saída para Elasticsearch, Logstash, Kafka ou Redis.
* A Elastic também oferece uma distribuição do [Coletor OpenTelemetry - EDOT](https://www.elastic.co/docs/reference/opentelemetry). Embora ainda não possa ser orquestrado pelo Fleet Server, ele oferece um caminho mais flexível e aberto para quem está migrando para o ClickHouse Observability.

O melhor caminho de migração depende dos agentes em uso. Nas seções a seguir, documentamos as opções de migração para cada um dos principais tipos de agente. Nosso objetivo é reduzir ao máximo o atrito e, sempre que possível, permitir que você continue usando seus agentes atuais durante a transição.

## Caminho de migração recomendado {#prefered-migration-path-self-configured}

Sempre que possível, recomendamos migrar para o [Coletor OpenTelemetry (OTel)](https://opentelemetry.io/docs/collector/) para toda a coleta de logs, métricas e traces, implantando o coletor na [borda, no papel de agente](/pt-BR/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured). Essa é a forma mais eficiente de enviar dados, além de evitar complexidade arquitetural e transformações de dados.

<Info>
  **Por que o Coletor OpenTelemetry?**

  O Coletor OpenTelemetry oferece uma solução sustentável e independente de fornecedor para a ingestão de dados de observabilidade. Sabemos que algumas organizações operam frotas de milhares — ou até dezenas de milhares — de agentes Elastic. Para esses usuários, manter a compatibilidade com a infraestrutura de agentes existente pode ser essencial. Esta documentação foi elaborada para atender a esse cenário e, ao mesmo tempo, ajudar as equipes a migrar gradualmente para a coleta baseada em OpenTelemetry.
</Info>

## Endpoint OpenTelemetry do ClickHouse {#clickhouse-otel-endpoint-self-configured}

Configure o destino antes de seguir as etapas de migração do agente. Os exemplos de Vector e EDOT abaixo enviam dados OpenTelemetry via OTLP HTTP.

<Tabs>
  <Tab title="Totalmente gerenciado">
    <BetaBadge label="Oferta Beta" />

    Copie o endpoint OTLP HTTP e a chave de API em **Team Settings → Data → Managed Telemetry**. Defina estas variáveis no ambiente em que o Vector ou o EDOT é executado:

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Use exatamente o endpoint informado, incluindo a porta e sem o sufixo `/v1/logs`. Consulte [Envio de dados OpenTelemetry](/pt-BR/clickstack/observability/ingesting-data/opentelemetry) para obter os detalhes de conexão.
  </Tab>

  <Tab title="Autogerenciado">
    Implante o coletor receptor seguindo o [guia de configuração autogerenciada](/pt-BR/clickstack/self-configured/getting-started/managed). Defina o endpoint OTLP HTTP acessível desse coletor e o cabeçalho de autorização no ambiente em que o Vector ou o EDOT é executado:

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_COLLECTOR_TOKEN'
    ```

    Se você protegeu o coletor receptor com `OTLP_AUTH_TOKEN`, use esse token como valor de autorização. Se a autenticação estiver desabilitada, remova o cabeçalho `authorization` dos exemplos. Consulte [Proteção do coletor](/pt-BR/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).

    Use `localhost` somente quando o remetente e o receptor compartilharem o mesmo namespace de rede. Para um receptor com TLS habilitado, use o endpoint HTTPS dele e configure a confiança no respectivo certificado.
  </Tab>
</Tabs>

## Migração a partir do Beats {#migrating-to-beats-self-configured}

Usuários com implantações extensas de Beats podem querer mantê-las ao migrar para o ClickHouse Observability.

**No momento, esta opção foi testada apenas com o Filebeat e, portanto, é adequada somente para logs.**

Os agentes Beats usam o [Elastic Common Schema (ECS)](https://www.elastic.co/docs/reference/ecs), que está [em processo de incorporação à especificação OpenTelemetry](https://github.com/open-telemetry/opentelemetry-specification/blob/main/oteps/0199-support-elastic-common-schema-in-opentelemetry.md) usada pelo ClickHouse Observability. No entanto, esses [esquemas ainda diferem significativamente](https://www.elastic.co/docs/reference/ecs/ecs-otel-alignment-overview), e, por enquanto, cabe aos usuários converter os eventos no formato ECS para o formato OpenTelemetry antes da ingestão no ClickHouse Observability.

Recomendamos realizar essa transformação com o [Vector](https://vector.dev), um pipeline de dados de observabilidade leve e de alto desempenho que oferece suporte a uma poderosa linguagem de transformação chamada Vector Remap Language (VRL).

Se seus agentes Filebeat estiverem configurados para enviar dados ao Kafka (uma saída compatível com o Beats), o Vector pode consumir esses eventos do Kafka, aplicar transformações de schema com VRL e, em seguida, encaminhá-los via OTLP para o seu endpoint OTLP configurado.

Como alternativa, o Vector também oferece suporte ao recebimento de eventos pelo protocolo Lumberjack usado pelo Logstash. Isso permite que os agentes Beats enviem dados diretamente ao Vector, onde o mesmo processo de transformação pode ser aplicado antes do encaminhamento via OTLP para o seu endpoint OTLP configurado.

Ilustramos ambas as arquiteturas abaixo.

  <Frame>

No exemplo a seguir, apresentamos as etapas iniciais para configurar o Vector para receber eventos de log do Filebeat pelo protocolo Lumberjack. Fornecemos o código VRL para mapear os eventos ECS de entrada para a especificação OTel antes de enviá-los via OTLP para o seu endpoint OTLP configurado. Usuários que consomem eventos do Kafka podem substituir a fonte de dados Logstash do Vector pela [fonte de dados Kafka](https://vector.dev/docs/reference/configuration/sources/kafka/); todas as demais etapas permanecem iguais.

<Steps>
  <Step title="Instale o Vector" id="install-vector-self-configured">
    Instale o Vector seguindo o [guia oficial de instalação](https://vector.dev/docs/setup/installation/).

    Instale o Vector em um host acessível pelos seus agentes do Filebeat.

    Você pode seguir as boas práticas de arquitetura e segurança ao [levar o Vector para produção](https://vector.dev/docs/setup/going-to-prod/).
  </Step>

  <Step title="Configure o Vector" id="configure-vector-self-configured">
    O Vector deve ser configurado para receber eventos pelo protocolo Lumberjack, simulando uma instância do Logstash. Para isso, configure uma [fonte de dados `logstash`](https://vector.dev/docs/reference/configuration/sources/logstash/) no Vector:

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
          # The files below are generated from the steps at https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          # crt_file: logstash.crt
          # key_file: logstash.key
          # ca_file: ca.crt
          # verify_certificate: true
    ```

    <Info>
      **Configuração TLS**

      Se for necessário usar TLS mútuo, gere os certificados e as chaves seguindo o guia da Elastic [&quot;Configure SSL/TLS for the Logstash output&quot;](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output). Em seguida, eles podem ser especificados na configuração, conforme mostrado acima.
    </Info>

    Os eventos serão recebidos no formato ECS. Eles podem ser convertidos para o schema do OpenTelemetry com um transformer de Vector Remap Language (VRL). A configuração desse transformer é simples, com o script mantido em um arquivo separado:

    ```yaml
    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'
    ```

    Observe que ele recebe eventos da fonte `beats` mostrada acima. Nosso script de remapeamento é apresentado a seguir. Este script foi testado apenas com eventos de log, mas pode servir de base para outros formatos.

    <Accordion title="VRL - ECS para OTel">
      ```javascript
      # Define keys to ignore at root level
      ignored_keys = ["@metadata"]

      # Define resource key prefixes
      resource_keys = ["host", "cloud", "agent", "service"]

      # Create separate objects for resource and log record fields
      resource_obj = {}
      log_record_obj = {}

      # Copy all non-ignored root keys to appropriate objects
      root_keys = keys(.)
      for_each(root_keys) -> |_index, key| {
          if !includes(ignored_keys, key) {
              val, err = get(., [key])
              if err == null {
                  # Check if this is a resource field
                  is_resource = false
                  if includes(resource_keys, key) {
                      is_resource = true
                  }

                  # Add to appropriate object
                  if is_resource {
                      resource_obj = set(resource_obj, [key], val) ?? resource_obj
                  } else {
                      log_record_obj = set(log_record_obj, [key], val) ?? log_record_obj
                  }
              }
          }
      }

      # Flatten both objects separately
      flattened_resources = flatten(resource_obj, separator: ".")
      flattened_logs = flatten(log_record_obj, separator: ".")

      # Process resource attributes
      resource_attributes = []
      resource_keys_list = keys(flattened_resources)
      for_each(resource_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_resources, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  resource_attributes = push(resource_attributes, attribute)
              }
          }
      }

      # Process log record attributes
      log_attributes = []
      log_keys_list = keys(flattened_logs)
      for_each(log_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_logs, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  log_attributes = push(log_attributes, attribute)
              }
          }
      }

      # Get timestamp for timeUnixNano (convert to nanoseconds)
      timestamp_nano = if exists(.@timestamp) {
          to_unix_timestamp!(parse_timestamp!(.@timestamp, format: "%Y-%m-%dT%H:%M:%S%.3fZ"), unit: "nanoseconds")
      } else {
          to_unix_timestamp(now(), unit: "nanoseconds")
      }

      # Get message/body field
      body_value = if exists(.message) {
          to_string!(.message)
      } else if exists(.body) {
          to_string!(.body)
      } else {
          ""
      }

      # Create the OpenTelemetry structure
      . = {
          "resourceLogs": [
              {
                  "resource": {
                      "attributes": resource_attributes
                  },
                  "scopeLogs": [
                      {
                          "scope": {},
                          "logRecords": [
                              {
                                  "timeUnixNano": to_string(timestamp_nano),
                                  "severityNumber": 9,
                                  "severityText": "info",
                                  "body": {
                                      "stringValue": body_value
                                  },
                                  "attributes": log_attributes
                              }
                          ]
                      }
                  ]
              }
          ]
      }
      ```
    </Accordion>

    Por fim, envie os eventos transformados para o endpoint OTLP configurado. Isso requer a configuração de um destino OTLP no Vector, que recebe como entrada os eventos da transformação `remap_filebeat`:

    ```yaml
    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat] # receives events from a remap transform - see below
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```

    Use as [variáveis de conexão](#clickhouse-otel-endpoint-self-configured) da sua implantação. A URI do Vector inclui `/v1/logs` porque esta saída envia registros de log.

    A configuração final completa é apresentada a seguir:

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
            #crt_file: /data/elasticsearch-9.0.1/logstash/logstash.crt
            #key_file: /data/elasticsearch-9.0.1/logstash/logstash.key
            #ca_file: /data/elasticsearch-9.0.1/ca/ca.crt
            #verify_certificate: true

    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'

    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat]
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```
  </Step>

  <Step title="Configure o Filebeat" id="configure-filebeat-self-configured">
    Configure o Filebeat para usar a saída do Logstash para o Vector, substituindo qualquer configuração de saída existente. Substitua `YOUR_VECTOR_HOST` pelo host em que o Vector está em execução; use `localhost` somente quando ambos forem executados no mesmo host. Configure o TLS de acordo com a entrada do Vector:

    ```yaml
    # ------------------------------ Logstash Output -------------------------------
    output.logstash:
      # The Logstash hosts
      hosts: ["YOUR_VECTOR_HOST:5044"]

      # Optional SSL. By default is off.
      # List of root certificates for HTTPS server verifications
      #ssl.certificate_authorities: ["/etc/pki/root/ca.pem"]

      # Certificate for SSL client authentication
      #ssl.certificate: "/etc/pki/client/cert.pem"

      # Client Certificate Key
      #ssl.key: "/etc/pki/client/cert.key"
    ```
  </Step>
</Steps>

## Migração do Elastic Agent {#migrating-from-elastic-agent-self-configured}

O Elastic Agent consolida os diferentes Elastic Beats em um único pacote. Esse agente se integra ao [Elastic Fleet](https://www.elastic.co/docs/reference/fleet/fleet-server), o que permite orquestrá-lo e configurá-lo de forma centralizada.

Usuários que já têm Elastic Agents implantados contam com vários caminhos de migração:

* Configurar o agente para enviar dados a um endpoint do Vector por meio do protocolo Lumberjack. **No momento, isso foi testado apenas para usuários que coletam dados de log com o Elastic Agent.** Essa configuração pode ser feita de forma centralizada pela UI do Fleet no Kibana.
* [Executar o agente como Elastic OpenTelemetry Collector (EDOT)](https://www.elastic.co/docs/reference/fleet/otel-agent). O Elastic Agent inclui um EDOT Collector embutido que permite instrumentar suas aplicações e sua infraestrutura uma única vez e enviar os dados para vários fornecedores e backends. Nessa configuração, basta configurar o EDOT Collector para encaminhar eventos via OTLP ao endpoint OTLP configurado. **Essa abordagem oferece suporte a todos os tipos de eventos.**

Demonstramos as duas opções a seguir.

### Enviando dados via Vector {#sending-data-via-vector-self-configured}

<Steps>
  <Step title="Instale e configure o Vector" id="install-configure-vector-self-configured">
    Instale e configure o Vector seguindo as [mesmas etapas](#install-vector-self-configured) documentadas para a migração a partir do Filebeat.
  </Step>

  <Step title="Configure o Elastic Agent" id="configure-elastic-agent-self-configured">
    O Elastic Agent precisa ser configurado para enviar dados por meio do Lumberjack, o protocolo do Logstash. Este é um [padrão de implantação compatível](https://www.elastic.co/docs/manage-data/ingest/ingest-reference-architectures/ls-networkbridge) e pode ser configurado de forma centralizada ou [por meio do arquivo de configuração do agente `elastic-agent.yaml`](https://www.elastic.co/docs/reference/fleet/logstash-output), caso a implantação seja feita sem o Fleet.

    A configuração centralizada pelo Kibana pode ser feita adicionando [uma saída ao Fleet](https://www.elastic.co/docs/reference/fleet/fleet-settings#output-settings).

    <div className="ch-image-md">
      <Frame>
        ![Adicionar saída do Logstash](/images/use-cases/observability/add-logstash-output.webp)
      </Frame>
    </div>

    Essa saída pode então ser usada em uma [política de agente](https://www.elastic.co/docs/reference/fleet/agent-policy). Com isso, todos os agentes que usam essa política passarão a enviar automaticamente seus dados para o Vector.

    <div className="ch-image-md">
      <Frame>
        ![Configurações do agente](/images/use-cases/observability/agent-output-settings.webp)
      </Frame>
    </div>

    Como isso exige configurar a comunicação segura via TLS, recomendamos o guia [&quot;Configure SSL/TLS for the Saída do Logstash&quot;](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output), que pode ser seguido considerando que a instância do Vector assume o papel do Logstash.

    Observe que isso exige que os usuários configurem a fonte de dados Logstash no Vector para também usar TLS mútuo. Use as chaves e os certificados [gerados no guia](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs) para configurar a entrada adequadamente.

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: true  # Defina como true se estiver usando TLS.
          # Os arquivos abaixo são gerados a partir das etapas em https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          crt_file: logstash.crt
          key_file: logstash.key
          ca_file: ca.crt
          verify_certificate: true
    ```
  </Step>
</Steps>

### Executar o Elastic Agent como coletor OpenTelemetry {#run-agent-as-otel-self-configured}

O Elastic Agent inclui um EDOT Collector embutido que permite instrumentar suas aplicações e sua infraestrutura uma única vez e enviar dados para vários fornecedores e backends.

<Info>
  **Integrações e orquestração do agente**

  Usuários que executam o EDOT Collector distribuído com o Elastic Agent não poderão aproveitar as [integrações existentes oferecidas pelo agente](https://www.elastic.co/docs/reference/fleet/manage-integrations). Além disso, o coletor não pode ser gerenciado centralmente pelo Fleet, o que obriga o usuário a executar o [agente em modo independente](https://www.elastic.co/docs/reference/fleet/configure-standalone-elastic-agents) e a gerenciar a configuração por conta própria.
</Info>

Para executar o Elastic Agent com o EDOT Collector, siga o [guia oficial da Elastic](https://www.elastic.co/docs/reference/fleet/otel-agent-transform). Configure um exportador OTLP HTTP usando suas [variáveis de conexão](#clickhouse-otel-endpoint-self-configured):

```yaml
exporters:
  otlphttp/clickhouse:
    endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
    headers:
      authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
```

Adicione `otlphttp/clickhouse` à lista `exporters` de cada pipeline de logs, métricas ou traces que você deseja encaminhar. Mantenha os receptores e processadores existentes. Para ingestão em paralelo, mantenha o exportador do Elastic nesses pipelines; remova-o quando estiver pronto para deixar de enviar dados ao Elastic.

O exportador usa o endpoint base e acrescenta automaticamente o caminho do sinal. Para um receptor HTTPS que usa uma autoridade certificadora privada, configure `tls.ca_file`; se esse receptor exigir TLS mútuo, configure também `tls.cert_file` e `tls.key_file`. Essas configurações protegem a conexão do EDOT com o OTLP independentemente da configuração TLS entre o Filebeat e o Vector.

## Migração a partir do coletor OpenTelemetry da Elastic {#migrating-from-elastic-otel-collector-self-configured}

Usuários que já executam o [Elastic OpenTelemetry Collector (EDOT)](https://www.elastic.co/docs/reference/opentelemetry) podem simplesmente reconfigurar seus agentes para enviar dados via OTLP ao endpoint OTLP configurado. As etapas são idênticas às descritas acima para executar o [Elastic Agent como coletor OpenTelemetry](#run-agent-as-otel-self-configured). Essa abordagem pode ser usada para todos os tipos de dados.
