Colete logs do journal do systemd com o receptor journald do OpenTelemetry e envie-os ao ClickHouse Observability. Use o [conjunto de dados de demonstração](#demo-dataset) para testar a integração sem precisar de um host Linux.

## Pré-requisitos {#prerequisites}

* Um serviço do ClickHouse Observability
* Para usar seus próprios logs, um host Linux com systemd, com `journalctl` e permissão para ler o journal
* `curl` e Docker para a demonstração

### Detalhes de conexão {#connection-details}

<Tabs>
  <Tab title="Totalmente gerenciado">
    <BetaBadge label="Oferta em versão beta" />

    Abra o ClickHouse Observability e acesse **Team Settings → Dados → Telemetria Gerenciada**. Copie o endpoint OTLP HTTP e a chave de API. Você pode usar **Copy connection details** para copiar a configuração ou **Reveal key** para exibir a chave mascarada.

    <div className="ch-image-lg">
      <Frame>
        ![Detalhes de conexão da Telemetria Gerenciada](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Para os exemplos de exportador OTLP a seguir, defina estas variáveis no terminal em que você executará o coletor:

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Substitua os marcadores de posição pelo endpoint exato do seu serviço, incluindo a porta, e pela chave de API. Use o endpoint HTTP base, sem o sufixo `/v1/logs`; o exportador acrescenta o caminho do sinal.
  </Tab>

  <Tab title="Autogerenciado">
    Use o endpoint OTLP HTTP acessível do seu coletor (por exemplo, `http://YOUR_COLLECTOR_HOST:4318`) e as respectivas configurações de autenticação. Se o seu coletor não exigir autenticação, omita o bloco `headers` do exportador nas configurações a seguir. Consulte o [guia de primeiros passos autogerenciado](/pt-BR/clickstack/self-configured/getting-started/managed) para obter orientações de configuração.

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

O endpoint deve estar acessível a partir do host monitorado ou do coletor de demonstração. Para um coletor de destino em execução no host Docker, use `http://host.docker.internal:4318`.

## Integração com sistemas existentes {#existing-systems}

<Steps>
  <Step title="Verifique o journal" id="verify-systemd">
    No host Linux que você deseja monitorar:

    ```bash
    systemctl --version
    sudo journalctl -n 20
    sudo journalctl --disk-usage
    ```

    O receptor usa o `journalctl` do host para ler os journals disponíveis. Há suporte tanto para o armazenamento persistente quanto para o volátil do journal; não é necessário alterar as configurações de armazenamento.
  </Step>

  <Step title="Baixe o coletor" id="download-collector">
    Execute estes comandos no host Linux monitorado:

    ```bash
    case "$(uname -m)" in
      x86_64) arch=amd64 ;;
      aarch64|arm64) arch=arm64 ;;
      *) echo "Unsupported architecture"; exit 1 ;;
    esac
    curl -fL -o otelcol-contrib.tar.gz \
      "https://github.com/open-telemetry/opentelemetry-collector-releases/releases/download/v0.161.0/otelcol-contrib_0.161.0_linux_${arch}.tar.gz"
    tar -xzf otelcol-contrib.tar.gz otelcol-contrib
    ```

    O coletor é executado diretamente no host para poder usar o `journalctl` instalado. A imagem Docker Contrib padrão não inclui esse binário.
  </Step>

  <Step title="Configure o coletor" id="configure-collector">
    Salve o conteúdo a seguir como `systemd-monitoring.yaml`:

    ```yaml
    receivers:
      journald:
        start_at: end
        priority: info
        convert_message_bytes: true
    processors:
      transform/journald:
        error_mode: ignore
        log_statements:
          - context: log
            statements:
              - merge_maps(log.attributes, log.body, "upsert")
              - set(resource.attributes["host.name"], log.attributes["_HOSTNAME"])
              - set(resource.attributes["service.name"], "systemd-logs")
              - set(log.attributes["unit"], log.attributes["SYSLOG_IDENTIFIER"])
              - set(log.attributes["unit"], log.attributes["_SYSTEMD_UNIT"]) where log.attributes["_SYSTEMD_UNIT"] != nil
              - set(log.attributes["priority"], log.attributes["PRIORITY"])
              - set(log.body, log.attributes["MESSAGE"])
              - set(log.severity_text, "info")
              - set(log.severity_number, SEVERITY_NUMBER_INFO)
              - set(log.severity_text, "warn") where Int(log.attributes["PRIORITY"]) == 4
              - set(log.severity_number, SEVERITY_NUMBER_WARN) where log.severity_text == "warn"
              - set(log.severity_text, "error") where Int(log.attributes["PRIORITY"]) == 3
              - set(log.severity_number, SEVERITY_NUMBER_ERROR) where log.severity_text == "error"
              - set(log.severity_text, "fatal") where Int(log.attributes["PRIORITY"]) < 3
              - set(log.severity_number, SEVERITY_NUMBER_FATAL) where log.severity_text == "fatal"
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [journald]
          processors: [transform/journald, batch]
          exporters: [otlp_http/observability]
    ```

    Os campos do journal são mantidos como atributos do log, a mensagem passa a ser o corpo do log e o hostname vira um atributo de recurso. O receptor coleta todas as units com prioridade `info` ou superior. Para restringir a coleta, adicione uma lista `units` em `journald` com os nomes reais das units do seu host, como `ssh.service` ou `nginx.service`.
  </Step>

  <Step title="Execute o coletor" id="run-collector">
    Defina as [variáveis de conexão](#connection-details) e execute o comando a partir do diretório de download. Este comando usa permissões de administrador para ler o journal do sistema e preserva apenas as duas variáveis de conexão:

    ```bash
    sudo --preserve-env=OTEL_EXPORTER_OTLP_ENDPOINT,OTEL_EXPORTER_OTLP_AUTHORIZATION \
      ./otelcol-contrib --config=systemd-monitoring.yaml
    ```

    Mantenha o terminal aberto. Em outro terminal, gere uma entrada no journal:

    ```bash
    echo 'ClickHouse Observability journal ingestion test' | systemd-cat -t observability-test -p info
    ```

    Interrompa o coletor com **Ctrl+C** ao concluir os testes. Para uma coleta contínua, execute-o como um serviço systemd com acesso ao journal e configure o [armazenamento de cursor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.161.0/receiver/journaldreceiver#cursor-tracking) para retomar a leitura após reinicializações.
  </Step>

  <Step title="Verifique os logs" id="verify-logs">
    Abra a página **Busca**, selecione **Logs**, filtre por `ServiceName:systemd-logs` e selecione **Last 15 minutes**. Procure a mensagem de teste e atributos como `unit` e `priority`.
  </Step>
</Steps>

## Conjunto de dados de demonstração {#demo-dataset}

A amostra contém 1,334 entradas de log em texto que abrangem aproximadamente 48 horas, incluindo atividade de SSH, jobs agendados e eventos de serviço. Ela usa o receptor `filelog`, portanto não é necessário instalar o systemd nem o `journalctl`. O coletor atualiza os timestamps, preservando o corpo original de cada evento e o intervalo entre eles.

<Steps>
  <Step title="Baixe a amostra" id="download-sample">
    ```bash
    curl -fL -o systemd-demo.log \
      https://datasets-documentation.s3.eu-west-3.amazonaws.com/clickstack-integrations/systemd/systemd-demo.log
    ```
  </Step>

  <Step title="Configure o coletor de demonstração" id="configure-demo">
    Salve o seguinte como `systemd-demo.yaml`:

    ```yaml
    receivers:
      filelog/systemd:
        include:
          - /var/log/demo/systemd-demo.log
        start_at: beginning
        operators:
          - type: regex_parser
            regex: '^(?P<timestamp>\S+) (?P<hostname>\S+) (?P<unit>\S+?)(?:\[(?P<pid>\d+)\])?: (?P<message>.*)$'
            parse_from: body
            parse_to: attributes
          - type: time_parser
            parse_from: attributes.timestamp
            layout: '%Y-%m-%dT%H:%M:%S%z'
          - type: add
            field: attributes.source
            value: systemd-demo
          - type: add
            field: resource["service.name"]
            value: systemd-demo
    processors:
      transform/demo_timestamps:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(resource.attributes["host.name"], log.attributes["hostname"])
              - set(log.time, Now() - Duration("2m") - (Time("2025-11-16T23:45:00Z", "%Y-%m-%dT%H:%M:%SZ") - log.time))
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [filelog/systemd]
          processors: [transform/demo_timestamps, batch]
          exporters: [otlp_http/observability]
    ```

    A amostra em texto não tem o campo de prioridade do journal, por isso a demonstração não atribui severidade com base no texto da mensagem.
  </Step>

  <Step title="Execute o coletor de demonstração" id="run-demo">
    Defina as [variáveis de conexão](#connection-details) e execute o comando a partir do diretório que contém os dois arquivos:

    ```bash
    docker run --rm --name systemd-demo-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/systemd-demo.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      -v "$(pwd)/systemd-demo.log:/var/log/demo/systemd-demo.log:ro" \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```

    Mantenha o terminal aberto enquanto verifica a ingestão. Ao terminar, interrompa com **Ctrl+C**. Ao executar a demonstração novamente, a amostra é ingerida outra vez com timestamps atualizados.
  </Step>

  <Step title="Verifique os logs de demonstração" id="verify-demo">
    Abra **Busca**, selecione **Logs**, filtre por `ServiceName:systemd-demo` e selecione **Last 2 days**. Você deverá ver as entradas da amostra com os atributos `unit`, `hostname` e `message`.

    <div className="ch-image-lg">
      <Frame>
        ![Logs de demonstração do systemd na Busca do ClickHouse Observability](/images/clickstack/observability-systemd-demo-logs.png)
      </Frame>
    </div>
  </Step>
</Steps>

## Solução de problemas {#troubleshooting}

### journalctl não encontrado {#journalctl-not-found}

Execute o coletor de produção no host Linux monitorado, com o `journalctl` instalado e disponível no caminho de execução. A demonstração usa `filelog` e não depende dele.

### Nenhum log aparecendo {#no-logs}

Verifique a saída do coletor em busca de erros de acesso ao journal, de autenticação ou de exportação. Confirme que `sudo journalctl -n 20` retorna entradas no host monitorado. Se você configurou um filtro por unidade, confirme que ele corresponde aos nomes dos seus serviços. Gere uma nova entrada depois de iniciar a coleta.

No ClickHouse Observability, verifique a fonte de dados **Logs**, o filtro por nome do serviço e o intervalo de tempo. Para a demonstração, selecione **Last 2 days** e confirme que o arquivo de amostra está montado no caminho configurado.
