<Tabs>
  <Tab title="Totalmente gerenciado">
    <BetaBadge label="Oferta em Beta" />

    [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen) é o gerador de dados do OpenTelemetry Collector Contrib. Ele emite logs, rastros e métricas OTLP sintéticos e oferece flags que permitem definir a estrutura dos dados: vários serviços, níveis de severidade de log, status de span e spans filhos, além de diferentes tipos de métrica. Use-o para enviar dados de teste ao ClickHouse Observability totalmente gerenciado e explorar os resultados na Busca e no Chart Explorer.

    <Steps>
      <Step title="Pré-requisitos" id="prerequisites-managed">
        É necessário ter um serviço ClickHouse Observability totalmente gerenciado já existente e acesso à rede do endpoint de telemetria gerenciada desse serviço. Consulte o [Guia de primeiros passos da versão totalmente gerenciada](/pt-BR/clickstack/observability/getting-started).
      </Step>

      <Step title="Instale o telemetrygen" id="install-telemetrygen-managed">
        Com o Docker instalado e em execução, defina um wrapper para executar o `telemetrygen` a partir da imagem de contêiner oficial:

        ```shell
        telemetrygen() {
          docker run --rm \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        ```

        Ou instale o binary com Go:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        ```
      </Step>

      <Step title="Defina as variáveis de ambiente" id="set-env-vars-managed">
        Abra seu serviço ClickHouse Observability e acesse **Team Settings → Managed Telemetry**. Copie o **OTLP HTTP endpoint** e a **API key**.

        <div className="ch-image-lg">
          <Frame>
            ![Managed Telemetry em Team Settings mostrando o endpoint OTLP HTTP e a chave de API mascarados](/images/clickstack/getting-started/observability-managed-telemetry.png)
          </Frame>
        </div>

        Defina o endpoint apenas com o host e a porta, removendo o prefixo `https://`. Por exemplo, `https://YOUR_OTEL_ENDPOINT:4318` passa a ser `YOUR_OTEL_ENDPOINT:4318`. Não acrescente um caminho de sinal, como `/v1/logs`.

        ```shell
        export OTEL_ENDPOINT='YOUR_OTEL_ENDPOINT:4318'
        printf "API key: "
        read -r -s OTEL_API_KEY
        printf "\n"
        export OTEL_API_KEY
        ```

        Defina um pequeno helper `tg` para que cada comando especifique apenas o que muda (serviço, severidade, status, atributos):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint "${OTEL_ENDPOINT}" --otlp-http \
          --otlp-header "authorization=\"Bearer ${OTEL_API_KEY}\"" \
          --rate 5 --duration 30s "$@"; }
        ```

        O helper usa OTLP HTTP sobre TLS com verificação de certificados. Omita `--otlp-insecure` e `--otlp-insecure-skip-verify`. Cada comando é executado por 30 segundos e se autentica com a sua chave de API de telemetria gerenciada.
      </Step>

      <Step title="Gerar logs" id="generate-logs-managed">
        Envie logs informativos, de aviso e de erro de três serviços:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        As flags de log mais úteis:

        * `--service` define `service.name` para que os eventos possam ser atribuídos a um serviço.
        * `--severity-text` e `--severity-number` definem o nível (`severity-number` vai de 1 a 24).
        * `--body` define a mensagem de log.
        * `--otlp-attributes` define atributos no nível do recurso (`key="value"`, `key=true` ou `key=<integer>`).
        * `--telemetry-attributes` define atributos por registro.
      </Step>

      <Step title="Gerar rastros" id="generate-traces-managed">
        Envie traces com vários spans, com status de sucesso e de erro, a partir de diversos serviços. Cada comando gera traces independentes; estes exemplos não criam chamadas entre serviços:

        ```shell
        # Healthy services: the bulk of the traffic, all spans Ok
        for svc in frontend checkout cart; do
          tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes "http.route=\"/$svc\""
        done

        # A service with slower spans and errors
        tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.route="/charge"'
        ```

        As flags de trace mais úteis:

        * `--child-spans` gera essa quantidade de spans filhos por trace, dando a cada trace uma profundidade real.
        * `--span-duration` define a duração de cada span (por exemplo, `120ms`, `2s`).
        * `--status-code` aceita um dos valores `Unset`, `Error` ou `Ok` (ou `0`, `1`, `2`). Use `Error` para testar as visualizações de erros.
        * `--span-links` adiciona links entre spans.
        * `--workers` executa vários geradores em paralelo, gerando um volume maior e mais variado.
      </Step>

      <Step title="Gerar métricas" id="generate-metrics-managed">
        Envie uma métrica do tipo sum, uma gauge e um histograma. Esses valores são sintéticos, e não medições do seu sistema. Cada comando é encerrado automaticamente após 30 segundos:

        ```shell
        tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
        tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
        tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
        ```

        `--metric-type` aceita `Gauge`, `Sum`, `Histogram` ou `ExponentialHistogram`. `--otlp-metric-name` define o nome da série para que você possa encontrá-la na UI, e `--aggregation-temporality` pode ser `delta` ou `cumulative`.
      </Step>

      <Step title="Verifique no ClickHouse Observability" id="verify-managed">
        Abra o seu serviço ClickHouse Observability. Na tela `Search`, defina o intervalo de tempo como `Last 15 minutes` e alterne a fonte de dados entre `Logs` e `Traces`. Filtre por `ServiceName` para ver os serviços `frontend`, `checkout`, `cart` e `payment`, e por `SeverityText` para encontrar as linhas de log de aviso e de erro. Abra um trace de `payment` para ver os spans filhos e o status de erro. Abra o `Chart Explorer`, selecione `Metrics` e crie um gráfico com um dos nomes de métrica que você definiu acima (por exemplo, `http.server.requests`) para verificar a ingestão de métricas.
      </Step>
    </Steps>
  </Tab>

  <Tab title="Autogerenciado" id="self-managed">
    [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen) é o gerador de dados do OpenTelemetry Collector Contrib. Ele emite logs, rastros e métricas OTLP sintéticos e oferece flags que permitem moldar os dados: vários serviços, níveis de severidade de log, status de span e spans filhos, além de diferentes tipos de métrica. Use-o para confirmar que um Coletor OpenTelemetry do ClickStack está aceitando dados e que eventos variados e realistas aparecem na UI de observabilidade.

    Este guia pressupõe que o coletor já esteja em execução com endpoints OTLP nas portas `4317` (gRPC) e `4318` (HTTP).

    <Steps>
      <Step title="Pré-requisitos" id="prerequisites-managed-self-configured">
        Este guia pressupõe que você concluiu o [Guia de primeiros passos do ClickHouse Observability — Self-managed](/pt-BR/clickstack/self-configured/getting-started/managed) e que tem um coletor OpenTelemetry em execução, com os endpoints OTLP gRPC (`4317`) e HTTP (`4318`) acessíveis a partir da máquina em que você executa o `telemetrygen`. Se você [protegeu o coletor](/pt-BR/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured) com um `OTLP_AUTH_TOKEN`, tenha esse valor em mãos.
      </Step>

      <Step title="Instale o telemetrygen" id="install-telemetrygen-managed-self-configured">
        Execute o `telemetrygen` a partir da imagem Docker (sem necessidade de instalação). Defina um pequeno wrapper para manter os comandos abaixo legíveis; o `--add-host` permite que o contêiner acesse um coletor que esteja escutando no host:

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        Ou, em vez disso, instale o binary com Go e aponte para `localhost`:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```
      </Step>

      <Step title="Defina as variáveis de ambiente" id="set-env-vars-managed-self-configured">
        Exporte o token de autenticação caso o coletor esteja protegido:

        ```shell
        export OTLP_AUTH_TOKEN=<your_otlp_auth_token>
        ```

        <Info>
          **Coletor sem proteção**

          O Coletor OpenTelemetry do ClickStack não exige autenticação por padrão. Se você não seguiu as instruções em [Protegendo o coletor](/pt-BR/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured) para definir um `OTLP_AUTH_TOKEN`, remova a linha `--otlp-header` do helper abaixo.
        </Info>

        Defina um pequeno helper `tg` para que cada comando especifique apenas o que muda (serviço, severidade, status, atributos):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 30s "$@"; }
        ```
      </Step>

      <Step title="Gerar logs" id="generate-logs-managed-self-configured">
        Envie logs com uma combinação realista de níveis de severidade entre os serviços, em sua maioria informativos, com um aviso e um erro, em vez de um único fluxo uniforme:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        As flags de log mais úteis:

        * `--service` define `service.name` para que os eventos possam ser atribuídos a um serviço.
        * `--severity-text` e `--severity-number` definem o nível (`severity-number` vai de 1 a 24).
        * `--body` define a mensagem de log.
        * `--otlp-attributes` define atributos no nível do recurso (`key="value"`, `key=true` ou `key=<integer>`).
        * `--telemetry-attributes` define atributos por registro.
      </Step>

      <Step title="Gerar rastros" id="generate-traces-managed-self-configured">
        Envie traces com múltiplos spans de vários serviços saudáveis e de uma dependência com falha. Isso dá ao Service Map um formato realista (a maioria dos serviços saudável e apenas um apresentando erros) e popula as visualizações de erros:

        ```shell
        # Healthy services: the bulk of the traffic, all spans Ok
        for svc in frontend checkout cart; do
          tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes "http.route=\"/$svc\""
        done

        # One slow dependency returning errors
        tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.route="/charge"'
        ```

        As flags de trace mais úteis:

        * `--child-spans` gera essa quantidade de spans filhos por trace, dando profundidade real a cada trace.
        * `--span-duration` define a duração de cada span (por exemplo, `120ms`, `2s`).
        * `--status-code` aceita um dos valores `Unset`, `Error` ou `Ok` (ou `0`, `1`, `2`). Use `Error` para testar as visualizações de erro.
        * `--span-links` adiciona links entre spans.
        * `--workers` executa vários geradores em paralelo para obter um volume maior e mais variado.
      </Step>

      <Step title="Gerar métricas" id="generate-metrics-managed-self-configured">
        Envie os três tipos de métrica mais comuns para que os dashboards tenham contadores, gauges e uma distribuição. Diferentemente de alguns geradores, o `telemetrygen` respeita o `--duration` para métricas, então não é preciso interrompê-lo manualmente:

        ```shell
        tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
        tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
        tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
        ```

        `--metric-type` aceita `Gauge`, `Sum`, `Histogram` ou `ExponentialHistogram`. `--otlp-metric-name` define o nome da série para que você possa encontrá-la na UI, e `--aggregation-temporality` pode ser `delta` ou `cumulative`.
      </Step>

      <Step title="Verifique na UI de observabilidade" id="verify-managed-self-configured">
        Abra a UI de observabilidade pelo console do ClickHouse Cloud. Na tela `Search`, defina o intervalo de tempo como `Last 15 minutes` e alterne a fonte de dados entre `Logs` e `Traces`. Filtre por `ServiceName` para ver os serviços `frontend`, `checkout`, `cart` e `payment`, e por `SeverityText` para encontrar as linhas de log de aviso e de erro. Abra um trace de `payment` para ver os spans filhos e o status de erro. Abra o `Chart Explorer`, selecione `Metrics` e crie um gráfico com um dos nomes de métrica definidos acima (por exemplo, `http.server.requests`) para verificar a ingestão de métricas.
      </Step>
    </Steps>
