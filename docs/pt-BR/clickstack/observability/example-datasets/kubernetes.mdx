Colete logs e métricas do seu cluster do Kubernetes e envie-os para o **ClickHouse Observability**. Use cargas de trabalho existentes ou implante a aplicação de demonstração opcional abaixo. A arquitetura da demonstração e a implantação da aplicação são as mesmas tanto para implantações totalmente gerenciadas quanto para autogerenciadas.

## Pré-requisitos {#prerequisites}

* Um **cluster do Kubernetes** em execução, com capacidade para os coletores e, se for o caso, para a aplicação de demonstração.
* Um serviço ClickHouse Observability. Consulte o [guia de primeiros passos da versão totalmente gerenciada](/pt-BR/clickstack/observability/getting-started) ou o [guia de primeiros passos da versão autogerenciada](/pt-BR/clickstack/self-configured/getting-started/managed).
* **[Helm](https://helm.sh/)** v3+.
* **`kubectl`** configurado para interagir com seu cluster, com permissão para criar namespaces, Secrets, ConfigMaps e funções de cluster (cluster roles).
* Acesso de rede dos seus coletores ao endpoint da implantação escolhida.

## Aplicação de demonstração {#demo-application}

Se você já tiver cargas de trabalho para monitorar, pule a implantação da demonstração e siga para [Configurar a coleta](#configure-collection).

O fork do ClickStack do [OpenTelemetry Demo](https://github.com/ClickHouse/opentelemetry-demo) oferece uma aplicação de e-commerce com microsserviços instrumentados e geração de tráfego.

<DemoArchitecture />

### Implante a demonstração {#deploy-the-demo}

Baixe e implante o manifesto da demonstração:

```shell
curl -fSL -o opentelemetry-demo.yaml \
  https://raw.githubusercontent.com/ClickHouse/opentelemetry-demo/d658416d6b36381126eba4416877b6518c320921/kubernetes/opentelemetry-demo.yaml

kubectl apply --namespace otel-demo -f opentelemetry-demo.yaml
kubectl get pods --namespace otel-demo
```

Aguarde até que os pods da aplicação fiquem prontos. O manifesto cria o namespace `otel-demo` e inclui serviços de apoio.

Os comandos usam uma revisão fixa da demonstração. Depois de implantar a aplicação, siga a aba correspondente ao seu tipo de implantação abaixo para instalar os coletores e conectar a telemetria da demonstração. Os coletores coletam logs do Kubernetes e métricas de infraestrutura, enquanto os serviços instrumentados da demonstração enviam a telemetria da aplicação via OTLP.

## Configurar a coleta {#configure-collection}

<Tabs>
  <Tab title="Totalmente gerenciado">
    <BetaBadge label="Oferta Beta" />

    Implante Coletores OpenTelemetry no seu cluster do Kubernetes para coletar logs e métricas e encaminhá-los ao seu endpoint de telemetria gerenciada. O ClickHouse Observability gerencia a ingestão de dados, o armazenamento e a UI, então não é necessário implantar o ClickHouse, a Interface do ClickStack nem o MongoDB no seu cluster.

    <Steps>
      <Step title="Copie seus detalhes de conexão" id="copy-connection-details">
        Abra seu serviço ClickHouse Observability e acesse **Team Settings → Data → Managed Telemetry**. Em **OpenTelemetry Collector**, selecione a aba **URL** e copie o endpoint OTLP HTTP e a chave de API. Clique em **Reveal key** para ver os valores completos.

        Use esses detalhes de conexão para configurar os coletores do Kubernetes nas etapas a seguir.

        <div className="ch-image-lg">
          <Frame>
            ![Managed Telemetry exibindo os detalhes de conexão: endpoint OTLP e chave de API](/images/clickstack/getting-started/observability-managed-telemetry.png)
          </Frame>
        </div>
      </Step>

      <Step title="Salve seus detalhes de conexão" id="create-api-key-kubernetes-secret">
        Armazene a chave de API da telemetria gerenciada em um Secret do Kubernetes e o endpoint OTLP HTTP em um ConfigMap. Crie ambos no namespace em que você instalará os coletores. Os exemplos a seguir usam um namespace dedicado, `otel-collectors`.

        ```shell
        kubectl create namespace otel-collectors

        kubectl create secret generic hyperdx-secret \
          --namespace otel-collectors \
          --from-literal=HYPERDX_API_KEY='<api-key>'

        kubectl create configmap otel-config-vars \
          --namespace otel-collectors \
          --from-literal=YOUR_OTEL_COLLECTOR_ENDPOINT='<managed-otlp-http-endpoint>'
        ```

        Se o namespace já existir, pule o primeiro comando. Substitua os marcadores de posição pelos valores de **Managed Telemetry**, mantendo o esquema HTTPS e a porta do endpoint.
      </Step>

      <Step title="Adicione o repositório Helm do OpenTelemetry" id="add-otel-helm-repo">
        Use o Chart do Helm oficial do OpenTelemetry para implantar coletores que enviam logs e métricas para o seu endpoint de telemetria gerenciada.

        Adicione o repositório do chart e atualize o índice dele:

        ```shell
        helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
        helm repo update open-telemetry
        ```
      </Step>

      <Step title="Implantar os componentes do coletor para Kubernetes" id="deploy-kubernetes-collector-components">
        Para coletar logs e métricas tanto do próprio cluster quanto de cada nó, precisaremos implantar dois coletores OpenTelemetry separados, cada um com seu próprio arquivo de valores do Helm. Os dois arquivos fornecidos — `k8s_deployment.yaml` e `k8s_daemonset.yaml` — atuam em conjunto para coletar dados de telemetria abrangentes do seu cluster do Kubernetes.

        * `k8s_deployment.yaml` implanta uma **única instância do Coletor OpenTelemetry**, responsável por coletar **eventos e metadados em todo o cluster**. Ela reúne eventos do Kubernetes e métricas do cluster, além de enriquecer os dados de telemetria com labels e anotações dos pods. Esse coletor é executado como uma Implantação independente com uma única réplica, para evitar dados duplicados.

        * `k8s_daemonset.yaml` implanta um **coletor baseado em Conjunto de Daemon**, executado em todos os nós do seu cluster. Ele coleta **métricas no nível de nó e de pod**, além de logs de contêineres, usando componentes como `kubeletstats`, `hostmetrics` e processadores de atributos do Kubernetes. Esses coletores enriquecem os logs com metadados e os enviam para o seu endpoint de telemetria gerenciada por meio do exportador OTLP HTTP.

        Os dois coletores exportam diretamente para o ClickHouse Observability. Em um cluster de nó único, isso resulta em dois pods de coletor. A Implantação também recebe da demonstração logs de aplicação, métricas e rastros via OTLP.

        Os comandos a seguir baixam cada arquivo de valores do Helm antes de instalar o respectivo coletor. Expanda a configuração abaixo de cada comando para conferir seu conteúdo. Estes exemplos usam o chart do Helm `0.175.0` com o Collector `0.161.0`.

        Primeiro, instale o coletor como uma Implantação:

        ```shell
        curl -fSL -o k8s_deployment.yaml \
          https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_deployment.yaml

        helm install --namespace otel-collectors k8s-otel-deployment open-telemetry/opentelemetry-collector \
          --version 0.175.0 -f k8s_deployment.yaml
        ```

        <Accordion title="k8s_deployment.yaml">
          ```yaml
          # k8s_deployment.yaml
          mode: deployment

          image:
            repository: otel/opentelemetry-collector-contrib
            tag: 0.161.0

          # We only want one of these collectors - any more and we'd produce duplicate data
          replicaCount: 1

          presets:
            kubernetesAttributes:
              enabled: true
              # When enabled, the processor will extract all labels for an associated pod and add them as resource attributes.
              # The label's exact name will be the key.
              extractAllPodLabels: true
              # When enabled, the processor will extract all annotations for an associated pod and add them as resource attributes.
              # The annotation's exact name will be the key.
              extractAllPodAnnotations: true
            # Configures the collector to collect Kubernetes events.
            # Adds the k8sobject receiver to the logs pipeline and collects Kubernetes events by default.
            # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-objects-receiver
            kubernetesEvents:
              enabled: true
            # Configures the Kubernetes Cluster Receiver to collect cluster-level metrics.
            # Adds the k8s_cluster receiver to the metrics pipeline and adds the necessary rules to ClusterRole.
            # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-cluster-receiver
            clusterMetrics:
              enabled: true

          extraEnvs:
            - name: HYPERDX_API_KEY
              valueFrom:
                secretKeyRef:
                  name: hyperdx-secret
                  key: HYPERDX_API_KEY
            - name: YOUR_OTEL_COLLECTOR_ENDPOINT
              valueFrom:
                configMapKeyRef:
                  name: otel-config-vars
                  key: YOUR_OTEL_COLLECTOR_ENDPOINT

          config:
            exporters:
              otlp_http:
                endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
                compression: gzip
                headers:
                  authorization: "Bearer ${env:HYPERDX_API_KEY}"
            service:
              pipelines:
                logs:
                  exporters:
                    - otlp_http
                metrics:
                  exporters:
                    - otlp_http
                traces:
                  exporters:
                    - otlp_http

          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              memory: 512Mi
          ```
        </Accordion>

        Em seguida, implante o coletor como um Conjunto de Daemon para coletar métricas e logs no nível de nó e de pod do Kubernetes:

        ```shell
        curl -fSL -o k8s_daemonset.yaml \
          https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_daemonset.yaml

        helm install --namespace otel-collectors k8s-otel-daemonset open-telemetry/opentelemetry-collector \
          --version 0.175.0 -f k8s_daemonset.yaml
        ```

        <Accordion title="k8s_daemonset.yaml">
          ```yaml
          # k8s_daemonset.yaml
          mode: daemonset

          image:
            repository: otel/opentelemetry-collector-contrib
            tag: 0.161.0

          # Required to use the kubeletstats cpu/memory utilization metrics
          clusterRole:
            create: true
            rules:
              - apiGroups:
                  - ''
                resources:
                  - nodes/proxy
                verbs:
                  - get

          presets:
            logsCollection:
              enabled: true
            hostMetrics:
              enabled: true
            # Configures the Kubernetes Processor to add Kubernetes metadata.
            # Adds the k8sattributes processor to all the pipelines and adds the necessary rules to ClusterRole.
            # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-attributes-processor
            kubernetesAttributes:
              enabled: true
              # When enabled, the processor will extract all labels for an associated pod and add them as resource attributes.
              # The label's exact name will be the key.
              extractAllPodLabels: true
              # When enabled, the processor will extract all annotations for an associated pod and add them as resource attributes.
              # The annotation's exact name will be the key.
              extractAllPodAnnotations: true
            # Configures the collector to collect node, pod, and container metrics from the kubelet API.
            # Adds the kubeletstats receiver to the metrics pipeline and adds the necessary rules to ClusterRole.
            # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubeletstats-receiver
            kubeletMetrics:
              enabled: true

          extraEnvs:
            - name: HYPERDX_API_KEY
              valueFrom:
                secretKeyRef:
                  name: hyperdx-secret
                  key: HYPERDX_API_KEY
            - name: YOUR_OTEL_COLLECTOR_ENDPOINT
              valueFrom:
                configMapKeyRef:
                  name: otel-config-vars
                  key: YOUR_OTEL_COLLECTOR_ENDPOINT

          config:
            receivers:
              kubeletstats:
                insecure_skip_verify: true
            exporters:
              otlp_http:
                endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
                compression: gzip
                headers:
                  authorization: "Bearer ${env:HYPERDX_API_KEY}"

            service:
              pipelines:
                logs:
                  exporters:
                    - otlp_http
                metrics:
                  exporters:
                    - otlp_http

          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              memory: 512Mi
          ```
        </Accordion>

        O exemplo de Conjunto de Daemon define `insecure_skip_verify: true` para a conexão local com o agente de nó do Kubernetes, pois clusters locais podem usar certificados que não abrangem o endereço do nó. Em produção, configure um certificado confiável para o agente de nó do Kubernetes e habilite a verificação de certificados. Essa configuração não afeta a verificação TLS do endpoint de telemetria gerenciada.

        Verifique se os coletores estão prontos:

        ```shell
        kubectl get pods --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector
        kubectl logs --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector --prefix --tail=50
        ```

        Procure erros de autenticação, exportação ou scrape nos logs. Um pod do Kubernetes em execução, por si só, não confirma que a telemetria foi entregue.
      </Step>

      <Step title="Conecte a aplicação de demonstração" id="connect-demo-fully-managed">
        Se você implantou a demonstração, aponte os exportadores dela para o coletor in-cluster. O coletor adiciona o cabeçalho de autenticação do endpoint gerenciado ao encaminhar a telemetria.

        ```shell
        kubectl set env deployment --namespace otel-demo \
          -l app.kubernetes.io/part-of=opentelemetry-demo \
          OTEL_COLLECTOR_NAME=k8s-otel-deployment-opentelemetry-collector.otel-collectors.svc.cluster.local

        kubectl rollout status deployment --namespace otel-demo \
          -l app.kubernetes.io/part-of=opentelemetry-demo --timeout=10m
        ```

        A chave de API gerenciada deve ficar no namespace `otel-collectors`, conforme configurado acima. A demonstração envia os dados para o receptor in-cluster e, por isso, não precisa dessa chave.
      </Step>

  <Tab title="Autogerenciado">
    O ClickHouse e a UI de observabilidade são executados no ClickHouse Cloud. Esta configuração implanta um coletor e os componentes auxiliares dele no seu cluster do Kubernetes.

    Os comandos a seguir usam o namespace `otel-demo`. Se você pulou a implantação da demonstração, crie-o primeiro:

    ```shell
    kubectl create namespace otel-demo
    ```

    <Steps>
      <Step title="Adicione o repositório do chart do Helm do ClickStack" id="add-helm-clickstack-self-configured">
        Para implantar o coletor e seus componentes auxiliares, usamos o [chart do Helm oficial](/pt-BR/clickstack/deployment/helm).

        Para isso, é necessário adicionar o repositório Helm do HyperDX:

        ```shell
        helm repo add hyperdx https://hyperdxio.github.io/helm-charts
        helm repo update
        ```
      </Step>

      <Step title="Implante o coletor e os componentes de suporte" id="deploy-clickstack-self-configured">
        Com o Chart do Helm instalado, implante o coletor e os componentes de suporte no seu cluster, usando o ClickHouse Cloud como banco de dados.

        <br />

        Implante o chart e [desative o ClickHouse incluído](/pt-BR/clickstack/deployment/helm#using-clickhouse-cloud).

        <Note>
          Atualmente, o chart sempre implanta a Interface do ClickStack e o MongoDB. Embora esses componentes ofereçam um caminho de acesso alternativo, eles não estão integrados à autenticação do ClickHouse Cloud. Nesse modelo de implantação, esses componentes são destinados a administradores, [fornecendo acesso à chave de ingestão segura](#retrieve-ingestion-api-key-self-configured) necessária para enviar dados pelo OTel collector implantado, mas não devem ser expostos a usuários finais.
        </Note>

        ```shell
        # specify ClickHouse Cloud credentials
        export CLICKHOUSE_URL=<CLICKHOUSE_CLOUD_URL> # full https url
        export CLICKHOUSE_USER=<CLICKHOUSE_USER>
        export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>

        helm install my-hyperdx hyperdx/hdx-oss-v2 --version 0.8.4 --set clickhouse.enabled=false --set clickhouse.persistence.enabled=false --set otel.clickhouseEndpoint=${CLICKHOUSE_URL} --set clickhouse.config.users.otelUserName=${CLICKHOUSE_USER} --set clickhouse.config.users.otelUserPassword=${CLICKHOUSE_PASSWORD} --set global.storageClassName="standard-rwo" -n otel-demo
        ```

        Para verificar o status da implantação, execute o comando a seguir e confirme que todos os componentes estão no estado `Running`. O ClickHouse é executado no ClickHouse Cloud e não aparece na lista de pods:

        ```shell
        kubectl get pods -l "app.kubernetes.io/name=hdx-oss-v2" -n otel-demo

        NAME                                                    READY   STATUS    RESTARTS   AGE
        my-hyperdx-hdx-oss-v2-app-78876d79bb-565tb              1/1     Running   0          14m
        my-hyperdx-hdx-oss-v2-mongodb-984845f96-czb6m           1/1     Running   0          14m
        my-hyperdx-hdx-oss-v2-otel-collector-64cf698f5c-8s7qj   1/1     Running   0          14m
        ```
      </Step>

      <Step title="Acesse a interface do ClickStack" id="access-the-hyperdx-ui-self-configured">
        <Note>
          Mesmo ao usar o ClickHouse Observability — Self-managed, a instância local da Interface do ClickStack implantada no cluster do Kubernetes continua sendo necessária. Ela fornece uma chave de ingestão, gerenciada pelo servidor OpAMP incluído na Interface do ClickStack, que protege a ingestão por meio do OTel collector implantado — um recurso atualmente indisponível no ClickHouse Observability — Self-managed.
        </Note>

        Por motivos de segurança, o serviço usa `ClusterIP` e, por padrão, não é exposto externamente.

        Para acessar a Interface do ClickStack, encaminhe a porta 3000 para a porta local 8080.

        ```shell
        kubectl port-forward \
         deployment/my-hyperdx-hdx-oss-v2-app \
          8080:3000 \
         -n otel-demo
        ```

        Acesse [http://localhost:8080](http://localhost:8080) para abrir a interface do ClickStack.

        Crie um usuário, informando um nome de usuário e uma senha que atendam aos requisitos de complexidade.
      </Step>

      <Step title="Obtenha a API key de ingestão" id="retrieve-ingestion-api-key-self-configured">
        A ingestão no OTel collector implantado pelo Coletor do ClickStack é protegida por uma chave de ingestão.

        Acesse [`Team Settings`](http://localhost:8080/team) e copie a `Ingestion API Key` na seção `API Keys`. Essa chave de API garante que a ingestão de dados pelo Coletor OpenTelemetry seja segura.
      </Step>

      <Step title="Crie um secret do Kubernetes para a chave de API" id="create-api-key-kubernetes-secret-self-configured">
        Crie um novo secret do Kubernetes com a API key de ingestão e um ConfigMap contendo o endereço do OTel collector implantado com o chart do Helm do ClickStack. Os componentes configurados a seguir usarão essas informações para fazer a ingestão de dados no coletor implantado com o chart do Helm do ClickStack:

        ```shell
        # create secret with the ingestion API key
        kubectl create secret generic hyperdx-secret \
        --from-literal=HYPERDX_API_KEY=<ingestion_api_key> \
        -n otel-demo

        # create a ConfigMap pointing to the ClickStack OTel collector deployed above
        kubectl create configmap -n=otel-demo otel-config-vars --from-literal=YOUR_OTEL_COLLECTOR_ENDPOINT=http://my-hyperdx-hdx-oss-v2-otel-collector:4318
        ```

        Se você implantou a demonstração, atualize o nome do serviço do coletor para que corresponda a esta implantação do Helm. Atualizar o ambiente também reinicia os pods da aplicação, para que eles passem a usar a chave de ingestão:

        ```shell
        kubectl set env deployment --namespace otel-demo \
          -l app.kubernetes.io/part-of=opentelemetry-demo \
          OTEL_COLLECTOR_NAME=my-hyperdx-hdx-oss-v2-otel-collector

        kubectl rollout status deployment --namespace otel-demo \
          -l app.kubernetes.io/part-of=opentelemetry-demo --timeout=10m
        ```

        Os exportadores da aplicação de demonstração usam esse nome de serviço para acessar o coletor. Nas suas próprias aplicações, configure separadamente o endpoint OTLP e a autenticação do receptor.
      </Step>

      <Step title="Adicione o repositório Helm do OpenTelemetry" id="add-otel-helm-repo-self-configured">
        Para coletar métricas do Kubernetes, vamos implantar um OTel collector padrão e configurá-lo para enviar dados com segurança ao nosso coletor do ClickStack usando a API key de ingestão criada anteriormente.

        Para isso, é necessário instalar o repositório Helm do OpenTelemetry:

        ```shell
        # Add Otel Helm repo
        helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
        ```
      </Step>

      <Step title="Implantar componentes do coletor no Kubernetes" id="deploy-kubernetes-collector-components-self-configured">
        Para coletar logs e métricas tanto do próprio cluster quanto de cada nó, precisaremos implantar dois Coletores OpenTelemetry distintos, cada um com seu próprio manifesto. Os dois manifestos fornecidos — `k8s_deployment.yaml` e `k8s_daemonset.yaml` — funcionam em conjunto para coletar dados de telemetria abrangentes do seu cluster do Kubernetes.

        * `k8s_deployment.yaml` implanta uma **única instância do Coletor OpenTelemetry**, responsável por coletar **eventos e metadados de todo o cluster**. Ela reúne eventos do Kubernetes e métricas do cluster, além de enriquecer os dados de telemetria com rótulos e anotações dos pods. Esse coletor é executado como uma implantação independente com uma única réplica, para evitar dados duplicados.

        * `k8s_daemonset.yaml` implanta um **coletor baseado em Conjunto de Daemon**, executado em cada nó do seu cluster. Ele coleta **métricas em nível de nó e de pod**, além de logs de contêineres, usando componentes como `kubeletstats`, `hostmetrics` e o Kubernetes Attribute Processor. Esses coletores enriquecem os logs com metadados e os enviam ao ClickStack por meio do exportador OTLP.

        Em conjunto, esses manifestos proporcionam observabilidade full-stack em todo o cluster, da infraestrutura à telemetria no nível da aplicação, e enviam os dados enriquecidos ao seu serviço para análise centralizada.

        Primeiro, instale o coletor como uma implantação (Deployment):

        ```shell
        # download manifest file
        curl -O https://raw.githubusercontent.com/ClickHouse/clickhouse-docs/refs/heads/main/docs/use-cases/observability/clickstack/example-datasets/_snippets/k8s_deployment.yaml
        # install the helm chart
        helm install --namespace otel-demo k8s-otel-deployment open-telemetry/opentelemetry-collector -f k8s_deployment.yaml
        ```

        <Accordion title="k8s_deployment.yaml">
          ```yaml
          # k8s_deployment.yaml
          mode: deployment

          image:
            repository: otel/opentelemetry-collector-contrib
            tag: 0.123.0

          # We only want one of these collectors - any more and we'd produce duplicate data
          replicaCount: 1

          presets:
            kubernetesAttributes:
              enabled: true
              # When enabled, the processor will extract all labels for an associated pod and add them as resource attributes.
              # The label's exact name will be the key.
              extractAllPodLabels: true
              # When enabled, the processor will extract all annotations for an associated pod and add them as resource attributes.
              # The annotation's exact name will be the key.
              extractAllPodAnnotations: true
            # Configures the collector to collect Kubernetes events.
            # Adds the k8sobject receiver to the logs pipeline and collects Kubernetes events by default.
            # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-objects-receiver
            kubernetesEvents:
              enabled: true
            # Configures the Kubernetes Cluster Receiver to collect cluster-level metrics.
            # Adds the k8s_cluster receiver to the metrics pipeline and adds the necessary rules to ClusteRole.
            # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-cluster-receiver
            clusterMetrics:
              enabled: true

          extraEnvs:
            - name: HYPERDX_API_KEY
              valueFrom:
                secretKeyRef:
                  name: hyperdx-secret
                  key: HYPERDX_API_KEY
                  optional: true
            - name: YOUR_OTEL_COLLECTOR_ENDPOINT
              valueFrom:
                configMapKeyRef:
                  name: otel-config-vars
                  key: YOUR_OTEL_COLLECTOR_ENDPOINT

          config:
            exporters:
              otlphttp:
                endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
                compression: gzip
                headers:
                  authorization: "${env:HYPERDX_API_KEY}"
            service:
              pipelines:
                logs:
                  exporters:
                    - otlphttp
                metrics:
                  exporters:
                    - otlphttp
          ```
        </Accordion>

        Em seguida, implante o coletor como um Conjunto de Daemon para coletar métricas e logs no nível de nó e de pod do Kubernetes:

## Explore os dados do Kubernetes {#explore-kubernetes-data}

Abra seu serviço do ClickHouse Observability. Em [Busca](/pt-BR/clickstack/observability/features/search), selecione a fonte de dados **Logs** e um intervalo de tempo que inclua o período em que os coletores estavam em execução. Procure uma mensagem de log de uma das suas cargas de trabalho e inspecione os atributos de recurso do Kubernetes, como `k8s.namespace.name` e `k8s.pod.name`.

O exemplo abaixo mostra logs de um cluster do Kubernetes local, incluindo uma carga de trabalho `sample-logs` que emite mensagens `Kubernetes documentation test`. Os nomes dos seus serviços e as mensagens de log dependerão das suas cargas de trabalho.

<div className="ch-image-lg">
  <Frame>
    ![Busca mostrando logs da carga de trabalho de exemplo e logs do sistema do Kubernetes chegando de um cluster local](/images/clickstack/getting-started/observability-kubernetes-logs.png)
  </Frame>
</div>

No **Chart Explorer**, selecione **Time Series** e a fonte de dados **Métricas**. Escolha **Average** de `k8s.pod.memory.usage`, agrupe por `ResourceAttributes['k8s.pod.name']` e deixe **Delta** desmarcado. Selecione um intervalo de tempo que inclua o período em que os coletores estavam em execução e clique em **Executar** para comparar o uso de memória entre os pods. Se o gráfico apresentar lacunas, escolha uma granularidade de tempo igual ou maior que o intervalo de coleta.

<div className="ch-image-lg">
  <Frame>
    ![Chart Explorer mostrando o uso médio de memória dos pods do Kubernetes agrupado por nome do pod](/images/clickstack/getting-started/observability-kubernetes-metrics.png)
  </Frame>
</div>

Para explorar o painel predefinido do Kubernetes, abra **Dashboards** na barra lateral e selecione **Kubernetes** em **Preset Dashboards**. Selecione as fontes de dados **Logs** e **Métricas** e um intervalo de tempo que inclua o período em que os coletores estavam em execução.

Use as abas **Pods**, **Nodes** e **Namespaces** para explorar seu cluster. Você pode refinar a visualização com os filtros de pod, deployment, nó, namespace e cluster.
