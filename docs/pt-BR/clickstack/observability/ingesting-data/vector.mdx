    <Note>
      Este guia se aplica somente ao **ClickHouse Observability autogerenciado**. O destino ClickHouse do Vector grava diretamente em tabelas gerenciadas por você. O ClickHouse Observability totalmente gerenciado exige ingestão via OTLP; consulte [Ingestão com OpenTelemetry](/pt-BR/clickstack/observability/ingesting-data/opentelemetry#fully-managed) para ver as configurações de endpoint e autenticação.
    </Note>

    [Vector](https://vector.dev) é um pipeline de dados de observabilidade de alto desempenho e independente de fornecedor. É amplamente usado para coletar, transformar e rotear logs e métricas de diversas fontes, sendo especialmente popular na ingestão de logs graças à sua flexibilidade e ao baixo consumo de recursos.

    Ao usar o Vector com o Self-managed ClickHouse Observability, os usuários são responsáveis por definir seus próprios esquemas. Esses esquemas podem seguir as convenções do OpenTelemetry, mas também podem ser totalmente personalizados, representando estruturas de eventos definidas pelo usuário. Na prática, a ingestão via Vector é usada com mais frequência para **logs**, quando os usuários desejam controle total sobre o parsing e o enriquecimento antes que os dados sejam gravados no ClickHouse.

    Este guia trata da ingestão de dados no Self-managed ClickHouse Observability com o Vector. Para simplificar, ele não aborda em detalhes as fontes de dados do Vector nem a configuração do pipeline. O foco está na configuração do **destino** (sink) que grava os dados no ClickHouse e em garantir que o schema resultante seja compatível com o Self-managed ClickHouse Observability.

    O único requisito obrigatório para o serviço é que os dados incluam uma **coluna de timestamp** (ou um campo de tempo equivalente), que pode ser declarada ao configurar a fonte de dados na UI de observabilidade.

## Envio de dados com o Vector {#sending-data-with-vector-self-configured}

    <br />

    Este guia pressupõe que você já criou um serviço do Self-managed ClickHouse Observability e anotou as credenciais do serviço. Caso ainda não tenha feito isso, siga o guia [Primeiros Passos](/pt-BR/clickstack/self-configured/getting-started/managed) do Self-managed ClickHouse Observability até o ponto em que for solicitado a configurar o Vector.

    <Steps>
      <Step title="Crie um banco de dados e uma tabela" id="create-a-database-table-self-configured">
        O Vector exige que uma tabela e um schema sejam definidos antes da ingestão de dados.

        Primeiro, crie um banco de dados. Isso pode ser feito pelo [console do ClickHouse Cloud](/pt-BR/products/cloud/features/sql-console-features/sql-console).

        No exemplo abaixo, usamos `logs`:

        ```sql
        CREATE DATABASE IF NOT EXISTS logs
        ```

        Crie uma tabela para seus dados. Ela deve corresponder ao schema de saída dos seus dados. O exemplo abaixo pressupõe uma estrutura clássica do Nginx. Ajuste conforme seus dados, seguindo as [boas práticas de schema](/pt-BR/concepts/best-practices/select-data-type). **Recomendamos fortemente** que você se familiarize com o [conceito de chaves primárias](/pt-BR/concepts/core-concepts/primary-indexes) e escolha sua chave primária com base nas diretrizes descritas [aqui](/pt-BR/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key).

        ```sql
        CREATE TABLE logs.nginx_logs
        (
            `time_local` DateTime,
            `remote_addr` IPv4,
            `remote_user` LowCardinality(String),
            `request` String,
            `status` UInt16,
            `body_bytes_sent` UInt64,
            `http_referer` String,
            `http_user_agent` String,
            `http_x_forwarded_for` LowCardinality(String),
            `request_time` Float32,
            `upstream_response_time` Float32,
            `http_host` String
        )
        ENGINE = MergeTree
        ORDER BY (toStartOfMinute(time_local), status, remote_addr)
        ```

        <Info>
          **Chave primária do Nginx**

          A chave primária acima pressupõe padrões de acesso típicos na UI de observabilidade para logs do Nginx, mas pode precisar ser ajustada de acordo com a sua carga de trabalho em ambientes de produção.
        </Info>
      </Step>

      <Step title="Adicione o destino ClickHouse à configuração do Vector" id="add-clickhouse-sink-to-config-self-configured">
        Modifique a configuração do Vector para incluir o destino do ClickHouse, atualizando o campo `inputs` para receber eventos dos seus pipelines existentes.

        Esta configuração pressupõe que o seu pipeline upstream do Vector já **preparou os dados de acordo com o schema de destino do ClickHouse**, ou seja, que os campos já foram interpretados, nomeados corretamente e tipados de forma adequada para a inserção. Consulte o [**exemplo do Nginx abaixo**](#example-dataset-with-vector-self-configured) para ver uma demonstração completa de parsing e normalização de linhas de log brutas em um schema adequado para o serviço.

        ```yaml
        sinks:
          clickhouse:
            type: clickhouse
            inputs:
              - your_input
            endpoint: "<CLICKHOUSE_ENDPOINT>"
            database: logs
            format: json_each_row
            table: nginx_logs
            skip_unknown_fields: true
            auth:
              strategy: "basic"
              user: "default"
              password: "<CLICKHOUSE_PASSWORD>"
        ```

        Por padrão, recomendamos usar o formato **`json_each_row`**, que codifica cada evento como um único objeto JSON por linha. Este é o formato padrão e recomendado do serviço para a ingestão de dados JSON e deve ter preferência sobre formatos alternativos, como objetos JSON codificados como strings.

        O destino ClickHouse também oferece suporte à **codificação Arrow stream** (atualmente em Beta). Ela pode proporcionar maior vazão, mas tem restrições importantes: o banco de dados e a tabela devem ser estáticos, já que o schema é obtido uma única vez na inicialização, e o roteamento dinâmico não é suportado. Por isso, a codificação Arrow é mais indicada para pipelines de ingestão fixos e bem definidos.

        Recomendamos consultar as opções de configuração disponíveis para o destino na [documentação do Vector](https://vector.dev/docs/reference/configuration/sinks/clickhouse):

        <Note>
          O exemplo acima usa o usuário default do Self-managed ClickHouse Observability. Para implantações em produção, recomendamos [criar um usuário de ingestão dedicado](/pt-BR/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) com permissões e limites adequados.
        </Note>
      </Step>

      <Step title="Acesse a UI de observabilidade" id="navigate-to-clickstack-ui-self-configured">
        Acesse o seu serviço Self-managed ClickHouse Observability e selecione &quot;ClickStack&quot; no menu à esquerda. Se você já tiver concluído a configuração inicial, a UI de observabilidade será aberta em uma nova aba e você será autenticado automaticamente. Caso contrário, conclua a configuração inicial e selecione “Launch ClickStack” depois de escolher o Vector como fonte de entrada.

          </Frame>
        </div>
      </Step>

      <Step title="Criar uma fonte de dados" id="create-a-datasource-managed-self-configured">
        Crie uma fonte de dados de logs. Se não houver nenhuma fonte de dados, você será solicitado a criar uma no seu primeiro login. Caso contrário, acesse Team Settings e adicione uma nova fonte de dados.

        <div className="ch-image-lg">
          <Frame>
            ![Criar fonte de dados - vector](/images/clickstack/create-vector-datasource.webp)
          </Frame>
        </div>

        A configuração acima pressupõe um schema no estilo Nginx, com uma coluna `time_local` usada como timestamp. Sempre que possível, essa deve ser a coluna de timestamp declarada na chave primária. Essa coluna é obrigatória.

        Também recomendamos atualizar o `Default SELECT` para definir explicitamente quais colunas são retornadas na visualização de logs. Se houver campos adicionais disponíveis, como nome do serviço, nível de log ou uma coluna de corpo, eles também podem ser configurados. A coluna de exibição do timestamp também pode ser sobrescrita caso seja diferente da coluna usada na chave primária da tabela e configurada acima.

        No exemplo acima, não existe uma coluna `Body` nos dados. Em vez disso, ela é definida por meio de uma expressão SQL que reconstrói uma linha de log do Nginx a partir dos campos disponíveis.

        Para conhecer outras opções, consulte a [referência de configuração](/pt-BR/clickstack/self-configured/managing/config).
      </Step>

## Conjunto de dados de exemplo com Vector {#example-dataset-with-vector-self-configured}

    Este guia pressupõe que você já criou um serviço Self-managed ClickHouse Observability e anotou as credenciais do serviço. Caso ainda não tenha feito isso, siga o guia [Primeiros Passos](/pt-BR/clickstack/self-configured/getting-started/managed) do Self-managed ClickHouse Observability até chegar à etapa de configuração do Vector.

      <Step title="Crie um banco de dados e uma tabela" id="create-database-table-nginx-managed-self-configured">
        O Vector exige que uma tabela e um schema sejam definidos antes da ingestão de dados.

        Primeiro, crie um banco de dados. Isso pode ser feito no [console do ClickHouse Cloud](/pt-BR/products/cloud/features/sql-console-features/sql-console).

        Crie o banco de dados `logs`:

        ```sql
        CREATE DATABASE IF NOT EXISTS logs
        ```

        Crie uma tabela para os seus dados.

        ```sql
        CREATE TABLE logs.nginx_logs
        (
            `time_local` DateTime,
            `remote_addr` IPv4,
            `remote_user` LowCardinality(String),
            `request` String,
            `status` UInt16,
            `body_bytes_sent` UInt64,
            `http_referer` String,
            `http_user_agent` String,
            `http_x_forwarded_for` LowCardinality(String),
            `request_time` Float32,
            `upstream_response_time` Float32,
            `http_host` String
        )
        ENGINE = MergeTree
        ORDER BY (toStartOfMinute(time_local), status, remote_addr)
        ```

        <Info>
          **Chave primária do Nginx**

          A chave primária acima pressupõe padrões de acesso típicos na UI de observabilidade para logs do Nginx, mas talvez precise ser ajustada conforme a sua carga de trabalho em ambientes de produção.
        </Info>
      </Step>

      <Step title="Copiar configuração do Vector" id="copy-vector-configuration-self-configured">
        Copie a configuração do Vector e crie um arquivo `nginx.yaml`, definindo `CLICKHOUSE_ENDPOINT` e `CLICKHOUSE_PASSWORD`.

        ```yaml
        data_dir: ./.vector-data
        sources:
          nginx_logs:
            type: file
            include:
              - access.log
            read_from: beginning

        transforms:
          decode_json:
            type: remap
            inputs:
              - nginx_logs
            source: |
              . = parse_json!(to_string!(.message))
              ts = parse_timestamp!(.time_local, format: "%d/%b/%Y:%H:%M:%S %z")
              # ClickHouse-friendly DateTime format
              .time_local = format_timestamp!(ts, format: "%F %T")

        sinks:
          clickhouse:
            type: clickhouse
            inputs:
              - decode_json
            endpoint: "<CLICKHOUSE_ENDPOINT>"
            database: logs
            format: json_each_row
            table: nginx_logs
            skip_unknown_fields: true
            auth:
              strategy: "basic"
              user: "default"
              password: "<CLICKHOUSE_PASSWORD>"
        ```

        <Note>
          O exemplo acima usa o usuário default do Self-managed ClickHouse Observability. Para implantações em produção, recomendamos [criar um usuário dedicado à ingestão](/pt-BR/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) com permissões e limites adequados.
        </Note>
      </Step>

      <Step title="Inicie o Vector" id="start-vector-self-configured">
        Inicie o Vector com o comando a seguir, criando antes o diretório de dados para registrar os offsets dos arquivos.

        ```bash
        mkdir ./.vector-data
        vector --config nginx.yaml
        ```
      </Step>

      <Step title="Acesse a UI de observabilidade" id="navigate-to-clickstack-ui-nginx-managed-self-configured">
        Acesse o seu serviço Self-managed ClickHouse Observability e selecione &quot;ClickStack&quot; no menu à esquerda. Se você já tiver concluído a configuração inicial, a UI de observabilidade será aberta em uma nova aba e você será autenticado automaticamente. Caso contrário, prossiga com a configuração inicial e selecione “Launch ClickStack” depois de escolher Vector como fonte de entrada.

        <div className="ch-image-lg">
          <Frame>
            ![Iniciar o ClickStack para o Vector](/images/clickstack/launch-clickstack-vector.webp)
          </Frame>
        </div>
      </Step>

      <Step title="Criar uma fonte de dados" id="create-a-datasource-nginx-managed-self-configured">
        Crie uma fonte de dados de logs. Se não houver nenhuma fonte de dados, será solicitado que você crie uma no primeiro login. Caso contrário, acesse Team Settings e adicione uma nova fonte de dados.

        <div className="ch-image-lg">
          <Frame>
            ![Criar fonte de dados - vector](/images/clickstack/create-vector-datasource.webp)
          </Frame>
        </div>

        A configuração pressupõe o schema do Nginx, com a coluna `time_local` usada como timestamp. Essa é a coluna de timestamp declarada na chave primária e é obrigatória.

        Também definimos o select padrão como `time_local, remote_addr, status, request`, que determina quais colunas são retornadas na visualização de logs.

        No exemplo acima, não existe uma coluna `Body` nos dados. Em vez disso, ela é definida pela seguinte expressão SQL:

        ```sql
        concat(
          remote_addr, ' ',
          remote_user, ' ',
          '[', formatDateTime(time_local, '%d/%b/%Y:%H:%M:%S %z'), '] ',
          '"', request, '" ',
          toString(status), ' ',
          toString(body_bytes_sent), ' ',
          '"', http_referer, '" ',
          '"', http_user_agent, '" ',
          '"', http_x_forwarded_for, '" ',
          toString(request_time), ' ',
          toString(upstream_response_time), ' ',
          '"', http_host, '"'
        )
        ```

        Isso reconstrói a linha de log a partir dos campos estruturados.

        Para conhecer outras opções disponíveis, consulte a [referência de configuração](/pt-BR/clickstack/self-configured/managing/config).
      </Step>
