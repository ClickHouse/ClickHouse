## Controles de colunas e ordenação na tabela de resultados da busca {#columns-and-sort-controls-on-the-search-results-table}

*Demonstração por [@elizabetdev](https://github.com/elizabetdev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

**Este é um trabalho exploratório, sem compromisso de lançamento.**

Antes, `SELECT` e `ORDER BY` eram campos de texto no formulário de consulta. Para alterar as colunas ou a ordenação, era preciso escrever SQL. Em entrevistas, quando pedimos às pessoas que adicionassem uma coluna, elas não encontravam onde fazer isso. Não havia uma relação clara entre esses campos e a tabela logo abaixo. Os campos também aparecem acima de Padrões de eventos, onde não têm efeito algum.

A proposta leva esses campos para os controles **Colunas** e **Ordenar** na tabela de resultados. Com **Colunas**, você pode arrastar colunas para reordená-las, removê-las, escolher um campo sugerido ou digitar uma expressão como `upper(Body) as message` e clicar em **Add**. **Ordenar** mostra cada campo do `ORDER BY` e sua direção. Ambos têm uma aba **SQL** onde é possível editar a cláusula diretamente. Alterações feitas na visualização de campos atualizam o SQL, então você pode usar qualquer uma das duas. As ações da tabela (quebra de linhas, SQL gerado e CSV) passam para a mesma barra de ferramentas. Antes, elas ficavam no cabeçalho da última coluna e podiam ficar fora de vista se essa coluna fosse larga.

Se você fechar qualquer um dos popovers com alterações não aplicadas, será solicitada uma confirmação antes de descartá-las. Remover uma coluna também a remove da ordenação, caso ela esteja sendo usada ali. Se o analisador sintático não entender uma cláusula, como `Timestamp DESC NULLS LAST`, ele mantém o SQL como foi escrito e abre a aba **SQL**. Esses controles não são exibidos em Deltas de eventos nem em Padrões de eventos.

Isso acrescenta uma linha extra de barra de ferramentas acima da tabela. Os editores já foram mesclados, mas ainda não estão na página de busca. O PR que os adiciona está aberto. Optamos por deixá-lo fora do beta do ClickHouse Observability por se tratar de uma mudança grande. Também poderíamos memorizar a última aba que você usou e reabrir em **SQL**, se essa for sua preferência. Queremos saber sua opinião sobre como isso funciona.

**PRs relacionados:** [#3431](https://github.com/ClickHouse/ClickStack/pull/3431) Adiciona os editores de colunas e ordenação, [#3432](https://github.com/ClickHouse/ClickStack/pull/3432) Monta Colunas e Ordenar na página de busca (aberto)

## Variáveis de conexão e de fonte de dados para dashboards {#connection-and-data-source-variables-for-dashboards}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=276" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

O áudio deste trecho não está muito bom; pedimos desculpas.

Os dashboards ganharam dois novos tipos de variável em **Edit filters and variables**. Uma variável de conexão permite escolher entre as conexões com o ClickHouse da equipe. Uma variável de fonte de dados permite escolher entre as fontes de dados da equipe. É possível limitar os tipos de fonte (por exemplo, apenas logs) e, opcionalmente, restringi-los a uma conexão. Essa conexão pode ser fixa ou uma variável de conexão; assim, ao alterar a conexão, as fontes de dados disponíveis também mudam.

Os blocos podem usar essas variáveis no lugar de uma fonte de dados ou conexão específica. Por exemplo, um bloco do construtor de consultas pode usar `$logSource` como fonte de dados, e um bloco de SQL bruto pode usar `$connection`. A configuração do gráfico armazena `$varName` no campo de ID da fonte de dados ou da conexão. Quando o dashboard é renderizado, esse valor é resolvido para um ID real, e todo o resto funciona como antes.

Outros filtros também podem depender dessas variáveis. Na demonstração, um filtro de valores de expressão SQL obtém os nomes de serviço da fonte de dados selecionada. Ao trocar a conexão de demonstração por uma conexão local, tanto os blocos quanto os nomes de serviço no filtro são atualizados. Se uma seleção estiver ausente ou for inválida, o bloco exibe um marcador de posição ou um erro em vez de executar uma consulta que falharia. Ainda não é possível usar `$source` diretamente no SQL. Para isso, escolha a fonte de dados no bloco e use `$__sourceTable` para referenciar a tabela correspondente.

Normalmente, as seleções entram na URL como IDs de fonte de dados e de conexão, mas também é possível usar nomes. Isso permite compartilhar links entre ambientes em que as fontes de dados têm os mesmos nomes, mas IDs diferentes. A consulta por nome é a mesma usada pelo parâmetro `source=` da página de busca.

Os dois tipos de variável também estão disponíveis na API externa e no MCP. Filtros de consulta SQL também podem referenciar variáveis de fonte de dados e de conexão.

**PRs relacionados:** [#3651](https://github.com/ClickHouse/ClickStack/pull/3651) Adiciona os tipos de variável de fonte de dados e de conexão aos dashboards, [#3652](https://github.com/ClickHouse/ClickStack/pull/3652) Suporte a variáveis de fonte de dados e de conexão na API externa e no MCP, [#3712](https://github.com/ClickHouse/ClickStack/pull/3712) Aceita nomes de fontes de dados e de conexões em variáveis de fonte de dados e de conexão, [#3714](https://github.com/ClickHouse/ClickStack/pull/3714) Permite que o filtro SQL referencie a variável de fonte de dados

## Construtor de apps com reconhecimento de versões {#version-aware-app-builder}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=477" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Os apps do ClickStack já contam com histórico de versões há algum tempo. Sempre que você pede ao agente para construir algo, ele cria uma nova versão, e você pode restaurar uma versão anterior. No entanto, o agente não conseguia ver essas versões nem perceber quando você havia restaurado uma delas. Ele continuava falando de código que já não estava no app, e a conversa deixava de corresponder ao código-fonte. Se você revertesse porque preferia como algo funcionava antes, ele também não conseguia consultar aquela versão.

Agora o agente consegue ver todas as versões, sabe quando você restaurou uma delas e conta com uma ferramenta de diff para comparar duas versões quaisquer. Na demonstração, um trace do Langfuse mostra o agente chamando a ferramenta e o diff que ele recebe como resposta. Assim, se você explicar por que reverteu uma alteração, o agente pode analisar as versões e ver exatamente o que mudou.

## Builds de apps mais rápidos com menos tokens {#faster-app-builds-with-fewer-tokens}

*Demonstração por [@pulpdrew](https://github.com/pulpdrew)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=569" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

O áudio deste trecho também não está dos melhores, pedimos desculpas.

Três mudanças no construtor de apps para acelerar os builds e reduzir o uso de tokens.

A ferramenta que o agente usa para testar SQL antes de adicioná-lo ao app agora pode executar várias consultas em paralelo, em vez de uma consulta por chamada. Agentes que usam o servidor MCP também podem usar essa mesma ferramenta para verificar SQL.

Também mudamos o momento em que compactamos o contexto. Antes, o construtor mantinha apenas as últimas oito etapas, assim como os notebooks. Isso mantinha o contexto pequeno, mas, a partir da nona etapa, cada nova etapa reescrevia o prompt e invalidava o cache do prompt, aumentando o custo e a latência. Agora esperamos até que o contexto atinja 600,000 tokens, 60% da janela de 1M de tokens que configuramos para os modelos Opus. Após a compactação, ele precisa voltar a atingir esse tamanho antes de compactarmos de novo. Até agora, nenhum build em nenhum dos nossos ambientes atingiu esse limite, então ainda não foi necessário compactar.

Por fim, o painel de informações do app mostra as consultas que o app executa. Antes, o agente escrevia essa lista manualmente, embora as consultas já estivessem no código. Se ele errasse a lista, enviávamos um aviso e ele tentava novamente. Em todo o nosso histórico de builds, escrever e corrigir essa lista consumia uma parcela considerável do uso de tokens e do tempo de build. Agora extraímos as consultas do código-fonte. O prompt indica ao agente como formatá-las para que possamos fazer isso de forma confiável, e continuamos enviando um aviso se a formatação precisar de correção. Cada consulta também recebe um número da linha e um link para o ponto do código onde é usada.

Os dashboards já oferecem suporte a links para outros dashboards. Ao clicar em uma linha de um bloco de tabela, é possível passar os valores dessa linha para outro dashboard, e blocos de Markdown e de tabela podem incluir links simples. No entanto, os links simples não preservavam os filtros. ## Filtros ad hoc de dashboard para todas as implantações {#ad-hoc-dashboard-filters-for-every-deployment}

*Demonstração por [@knudtty](https://github.com/knudtty)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=875" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Os filtros ad hoc permitem escolher uma chave, um operador e um valor na barra de filtros durante a investigação, sem que o autor do dashboard precise configurar cada filtro com antecedência. Eles foram introduzidos em outubro sob a flag `NEXT_PUBLIC_ENABLE_ADHOC_FILTERS`, e o [What&#39;s New de outubro](https://clickhouse.com/blog/whats-new-in-clickstack-october-2026#user-content-ad_hoc_dashboard_filters) apresenta o básico. Agora removemos a flag, e eles estão habilitados em todas as implantações.

Desde então, adicionamos algumas novidades. É possível definir o escopo de um filtro ad hoc usando um campo dependente. Por exemplo, um filtro restrito a `ServiceName = api` oferece apenas chaves e valores desse serviço. Um filtro também pode se aplicar a várias fontes de dados. Ao selecionar um `SpanName` para uma fonte de traces, os gráficos e as tabelas que usam essa fonte de dados são filtrados. A API externa de dashboards v2 e as ferramentas de dashboard do MCP agora podem criar, ler e atualizar dashboards com filtros ad hoc. Antes, o MCP os ocultava, e um update via `clickstack_save_dashboard` que incluísse `filters` excluía silenciosamente todos os filtros ad hoc existentes.

O nome de um filtro ad hoc serve apenas como identificador, portanto não é possível referenciá-lo como `$name` em um bloco. Ainda assim, ele precisa ser único, pois é usado para identificar as condições do filtro no parâmetro de URL `filters=`.

**PRs relacionados:** [#3585](https://github.com/ClickHouse/ClickStack/pull/3585) Adiciona filtros ad hoc dependentes, [#3658](https://github.com/ClickHouse/ClickStack/pull/3658) Ajustes finais nos filtros ad hoc, [#3659](https://github.com/ClickHouse/ClickStack/pull/3659) Suporte a filtros ad hoc de dashboard na API externa, [#3660](https://github.com/ClickHouse/ClickStack/pull/3660) Suporte a filtros ad hoc de dashboard nas ferramentas de dashboard do MCP, [#3727](https://github.com/ClickHouse/ClickStack/pull/3727) Remove o botão de alternância da funcionalidade de filtros ad hoc

## Carregamento mais rápido de filtros {#faster-filter-loading}

*Demonstração por [@knudtty](https://github.com/knudtty)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=939" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

A barra lateral de pesquisa obtém chaves e valores de filtro a partir de um índice de texto nos maps de atributos, se a fonte de dados tiver um (modo todos os valores), ou fazendo a varredura da tabela (modo exato). Os dois modos agora estão mais rápidos.

Antes, as consultas no índice de texto liam o dicionário de todas as partes no intervalo de tempo. No ClickHouse Observability, abrir o índice de cada parte implica uma ida e volta ao armazenamento de objetos. Agora lemos 20 partes por padrão, escolhendo as mais próximas da contagem mediana de linhas. Duas novas configurações da fonte de dados controlam esse comportamento: **Map key index parts** (`mapKeyIndexMaxParts`) define quantas partes ler, e **Map key index part size** (`mapKeyIndexPartSelection`) escolhe entre `median`, `smallest` e `largest`. As partes menores geralmente são mais recentes e ainda não mescladas, o que as torna baratas de ler e úteis para encontrar chaves novas. As partes maiores cobrem mais chaves, mas têm dicionários maiores.

Chaves e valores que aparecem apenas em partes fora dessa seleção podem ficar de fora. A opção **Load more** em uma chave lê todas as partes. Essas configurações ficam no formulário da fonte de dados, embora sejam mais avançadas do que o restante da seção avançada. A melhor forma de expô-las ainda está em aberto.

O índice de texto agora retorna os valores mais frequentes, classificados com `topKWeighted`, em vez dos primeiros em ordem alfabética. As consultas são executadas em lotes paralelos de 10 chaves. Uma chave com um valor diferente em cada linha, como um ID de requisição, atrasa apenas o próprio lote, e não todas as chaves que vêm depois dela na ordenação.

A consulta também depende do tamanho do bloco de dicionário do índice. Com blocos de 8,192 tokens, cada chave tem sua própria leitura, que termina após 20,000 linhas do índice. A migração do coletor agora define `text_index_dictionary_block_size = 8192` nas tabelas padrão para o ClickHouse 26.6 e versões posteriores. O padrão do ClickHouse também passa de 512 para 8,192 na versão 26.11. A demonstração carrega 2,000 chaves e valores do índice, mais do que era possível solicitar antes. As configurações da equipe agora permitem até 10,000 chaves por coluna.

O modo exato tinha um bug grave de desempenho. As consultas solicitavam valores para várias chaves de map em uma única consulta. Como um `Map` é armazenado como um array de pares chave-valor, o ClickHouse percorria o array de cada linha uma vez para cada chave solicitada. Agora encontramos as chaves solicitadas em uma única passagem por linha. Restrito a um único serviço, o modo exato ficou rápido o suficiente para talvez ser o melhor padrão. Por padrão, ele lê até 3 milhões de linhas, valor ajustável nas configurações da equipe. Esse limite provavelmente deveria ficar na fonte de dados, já que o ClickHouse Observability nem sequer o expõe aos usuários.

Requisições concorrentes para as mesmas chaves de map agora compartilham uma única consulta do ClickHouse, em vez de cada uma iniciar outra enquanto a primeira ainda está em execução.

**PRs relacionados:** [#3611](https://github.com/ClickHouse/ClickStack/pull/3611) Compartilhar uma única leitura de chaves de Map entre chamadores concorrentes, [#3617](https://github.com/ClickHouse/ClickStack/pull/3617) Exibir os valores mais frequentes do índice de texto, em lotes de 10 chaves, [#3635](https://github.com/ClickHouse/ClickStack/pull/3635) Ler um conjunto configurável de partes para consultas de chaves e valores no índice de texto, [#3657](https://github.com/ClickHouse/ClickStack/pull/3657) Permitir até 10,000 chaves de filtro por coluna nas configurações da equipe, [#3695](https://github.com/ClickHouse/ClickStack/pull/3695) Acelerar filtros exatos, [ClickHouse/ClickHouse#132804](https://github.com/ClickHouse/ClickHouse/pull/132804) Alterar o tamanho padrão do bloco de dicionário do índice de texto

## Filtrando ou excluindo um padrão de eventos {#filtering-for-or-excluding-an-event-pattern}

*Demonstração por [@alex-fedotyev](https://github.com/alex-fedotyev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=1216" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Esta melhoria surgiu de um cliente que gostava de Padrões de eventos, mas só conseguia clicar para ver as amostras de um padrão. Agora, cada linha tem duas ações que aparecem ao passar o mouse. **Exclude this pattern** permanece em Padrões de eventos e executa a análise novamente sem esse padrão. Você pode excluir vários padrões para ir eliminando o ruído. **Filter for this pattern** abre a tabela de resultados apenas com os eventos correspondentes.

Ambas as ações adicionam um filtro de pesquisa com uma condição SQL construída a partir do template do padrão. Trata-se de uma versão mais curta da condição usada pela ferramenta MCP `clickstack_event_patterns` para drill-downs, pequena o suficiente para caber na URL. O ClickHouse a aplica em todo o intervalo de tempo, não apenas às 10,000 linhas amostradas, de modo que a tabela de resultados, o histograma e as contagens são todos atualizados. Esses filtros aparecem como chips **Pattern** ao lado dos demais filtros e são preservados na URL e nas buscas salvas.

Só é possível incluir um padrão por vez. Como os filtros são combinados com `AND`, incluir dois padrões não retornaria nenhum resultado. Escolher outro padrão substitui o filtro de inclusão anterior. Templates com mais de 4,000 caracteres não exibem os botões, de acordo com o limite do MCP.

Há algumas limitações. Templates genéricos como `<*> <*>` podem corresponder a mais eventos do que a linha sugere. Se um template mantiver um timestamp como texto literal, o padrão fica atrelado àquela data e hora. Filtros de exclusão praticamente dobram o tempo de execução da consulta, e os botões ainda não estão disponíveis nos blocos de padrões dos dashboards.

## Métricas RED na busca de traces {#red-metrics-on-trace-search}

*Demonstração por [@alex-fedotyev](https://github.com/alex-fedotyev)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=1308" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Antes, a busca exibia um único histograma de contagem acima dos resultados para todas as fontes de dados. Agora, fontes de traces com uma coluna de duração exibem três blocos: **Throughput** mostra contagens de spans por status, **Errors** alterna entre uma linha de taxa de erros limitada a 100% e o volume de erros, e **Duration** mostra linhas de Avg, P95 e P99 nas unidades definidas pela precisão de duração da fonte de dados.

Você pode exibir um bloco ou os três. Ao passar o mouse sobre um deles, um cursor aparece no mesmo ponto no tempo nos três. Clicar em uma série de status em Throughput ou Errors filtra os resultados, assim como acontecia ao clicar no histograma. O Throughput reaproveita a consulta de contagem de resultados já existente, portanto não gera uma varredura adicional.

O interruptor **RED** / **Mapa de calor** substitui os três blocos por um mapa de calor que mostra a distribuição da duração ao longo do tempo. Trata-se do mesmo mapa de calor usado nos dashboards. A URL preserva sua escolha, de modo que links compartilhados abrem a mesma visualização. O acompanhamento em tempo real fica desativado na visualização de mapa de calor. Ao definir um agrupamento personalizado, como `ServiceName`, o histograma agrupado volta a ser exibido. Fontes de logs e telas estreitas continuam com o histograma atual.

## Configurações pelo menu Cmd+K e um modo CRT oculto {#settings-from-the-cmd-k-menu-and-a-hidden-crt-mode}

*Demonstração por [@MikeShi42](https://github.com/MikeShi42)*

<iframe width="768" height="432" src="https://www.youtube.com/embed/iAkz3igxYgY?start=1381" title="Reprodutor de vídeo do YouTube" frameborder="0" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" referrerpolicy="strict-origin-when-cross-origin" allowfullscreen />

Antes, era preciso acessar Team Settings ou o menu do usuário para encontrar as configurações. Agora você pode pesquisá-las pelo `Cmd+K` (`Ctrl+K` em outros sistemas). O grupo Settings inclui Team Settings, Fontes de dados, Conexões, Team members, API keys, Organization API keys, servidor MCP, Webhooks e Query settings. Cada entrada abre a aba correta e rola até a seção correspondente. Esse grupo fica oculto no modo local, que não tem página de equipe.

O grupo Preferences abre o modal de preferências. Para encontrá-lo, pesquise termos como fuso horário, 12h/24h, fonte ou clique na linha. Também é possível alterar o tema diretamente pelo menu com **Use light mode**, **Use dark mode** e **Use system color mode**.

Se você chegou até aqui, há também um pequeno Easter egg para você, cortesia de [@jordan-simonovski](https://github.com/jordan-simonovski). Abra **User preferences** e digite o código Konami: `Up, Up, Down, Down, Left, Right, Left, Right, B, A`. Uma breve animação de inicialização é exibida e um interruptor **CRT mode** aparece. Ative-o para dar ao app a aparência de uma antiga tela CRT, com linhas de varredura, cantos curvos e texto brilhante.

O efeito é um overlay, então você continua podendo usar o app normalmente. O interruptor permanece em Preferences enquanto o modo estiver ativo, para que você possa desativá-lo sem digitar o código novamente. Ele vem desativado por padrão, e a cintilação e a animação de desbloqueio não são exibidas quando `prefers-reduced-motion` está habilitado. Foram necessárias algumas tentativas para acertar o código na demonstração.

**PRs relacionados:** [#3707](https://github.com/ClickHouse/ClickStack/pull/3707) Encontrar configurações e preferências pelo menu Cmd+K, [#3704](https://github.com/ClickHouse/ClickStack/pull/3704) Modo CRT oculto, desbloqueado pelo código secreto nas preferências
