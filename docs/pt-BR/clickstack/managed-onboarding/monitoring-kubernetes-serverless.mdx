<Info>
  **Resumo**

  Armazene o endpoint e a chave de API do seu serviço no cluster, instale dois Coletores OpenTelemetry a partir do Chart do Helm oficial usando os arquivos de valores abaixo e abra o Painel do Kubernetes. Logs de contêiner, métricas de nós e do cluster e eventos do Kubernetes são enviados diretamente para o ClickHouse Observability. Nenhum outro componente é executado no seu cluster.

  Tempo necessário: cerca de 15 minutos
</Info>

Você já criou seu serviço do ClickHouse Observability. Este guia se aplica quando suas cargas de trabalho são executadas no Kubernetes e você quer visualizar o próprio cluster: logs de contêiner, CPU e memória de pods do Kubernetes e nós e eventos do Kubernetes, rotulados com o namespace, o pod do Kubernetes e o nó de origem, para que sejam correlacionados no Painel do Kubernetes integrado.

A abordagem segue o padrão do OpenTelemetry. Você implanta dois coletores a partir do [Chart do Helm do OpenTelemetry](https://github.com/open-telemetry/opentelemetry-helm-charts/tree/main/charts/opentelemetry-collector): um **Conjunto de Daemon** em cada nó para logs de contêiner e métricas de nós, e uma **Implantação** com uma única réplica para eventos do Kubernetes e métricas do cluster. Ambos enviam os dados diretamente para o endpoint OTLP do seu serviço.

<Note>
  **Já tem coletores OpenTelemetry em execução no seu cluster?**

  Mantenha-os e apenas adicione o exportador, conforme descrito em [Conectando um Coletor OpenTelemetry](/pt-BR/clickstack/managed-onboarding/setting-up-your-opentelemetry-collector-serverless).
</Note>

## Pré-requisitos {#prerequisites}

* Um serviço do ClickHouse Observability. Se você ainda não tiver um, siga o [Guia de primeiros passos](/pt-BR/clickstack/observability/getting-started).
* Um cluster do Kubernetes com cargas de trabalho a serem monitoradas e o `kubectl` configurado para acessá-lo, com permissão para criar namespaces, Secrets, ConfigMaps e funções de cluster.
* [Helm](https://helm.sh/). O README do chart indica o Helm 4.0 ou posterior como pré-requisito.
* Acesso HTTPS de saída na porta `4318` dos pods do Kubernetes do coletor para o endpoint de telemetria do seu serviço.

## Implante os coletores {#deploy-the-collectors}

<Steps>
  <Step title="Copie seus detalhes de conexão" id="copy-connection-details">
    Abra seu serviço ClickHouse Observability. Enquanto nenhum dado for recebido, ele exibirá a página **Start sending telemetry**.

    <div className="ch-image-lg">
      <Frame>
        ![Página Start sending telemetry mostrando o serviço atual ainda sem dados e três opções: Use an existing OpenTelemetry setup, Instrument with AI e Follow setup guides](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    Em **Use an existing OpenTelemetry setup**, selecione **View connection details** e abra a aba **Collector config**. Ela mostra o bloco do exportador do seu serviço: a URL do endpoint e um cabeçalho `authorization` com sua chave de API. Selecione **Reveal key** para exibir a chave completa.

    <div className="ch-image-md">
      <Frame>
        ![Caixa de diálogo Set up OpenTelemetry com a aba Collector config selecionada, mostrando um exportador otlphttp com o endpoint mascarado e um cabeçalho de autorização Bearer](/images/clickstack/getting-started/observability-collector-config.png)
      </Frame>
    </div>

    No próximo passo, você precisará desses dois valores separadamente: o endpoint, incluindo o esquema `https://` e a porta, e apenas a chave de API, sem o prefixo `Bearer`. Os arquivos de valores abaixo adicionam o prefixo.

    Esses mesmos valores ficam disponíveis a qualquer momento em **Team Settings → Managed Telemetry**.
  </Step>

  <Step title="Armazene-os no seu cluster" id="store-connection-details">
    Crie um namespace para os coletores, um Secret com a chave de API e um ConfigMap com o endpoint. Os dois coletores leem esses recursos por meio de `extraEnvs`, de modo que a chave nunca aparece em um arquivo de valores. Substitua os dois marcadores de posição pelos seus valores:

    ```shell
    kubectl create namespace otel-collectors

    kubectl create secret generic hyperdx-secret \
      --namespace otel-collectors \
      --from-literal=HYPERDX_API_KEY='<your-api-key>'

    kubectl create configmap otel-config-vars \
      --namespace otel-collectors \
      --from-literal=YOUR_OTEL_COLLECTOR_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    ```

    Mantenha o endpoint como URL base. Não acrescente `/v1/logs`, `/v1/traces` ou `/v1/metrics`, pois o próprio exportador adiciona o caminho do sinal. Se preferir outro namespace, use-o de forma consistente em todos os comandos abaixo: o Secret e o ConfigMap devem ficar no mesmo namespace das releases do Helm.
  </Step>

  <Step title="Adicione o repositório Helm do OpenTelemetry" id="add-helm-repository">
    ```shell
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update open-telemetry
    ```
  </Step>

  <Step title="Implante o coletor do cluster" id="deploy-cluster-collector">
    Esta Implantação com uma única réplica coleta **eventos do Kubernetes** e **métricas de todo o cluster**: condições dos nós, fases dos pods e status de implantações e réplicas. Uma réplica é suficiente; uma segunda geraria dados duplicados.

    Baixe o arquivo de valores e instale-o:

    ```shell
    curl -fSL -o k8s_deployment.yaml \
      https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_deployment.yaml

    helm install --namespace otel-collectors k8s-otel-deployment open-telemetry/opentelemetry-collector \
      --version 0.175.0 -f k8s_deployment.yaml
    ```

    <Accordion title="k8s_deployment.yaml">
      ```yaml
      # k8s_deployment.yaml
      mode: deployment

      image:
        repository: otel/opentelemetry-collector-contrib
        tag: 0.161.0

      # Queremos apenas um destes coletores - mais do que isso produziria dados duplicados
      replicaCount: 1

      presets:
        kubernetesAttributes:
          enabled: true
          # Quando habilitado, o processador extrairá todos os labels do pod associado e os adicionará como atributos de recurso.
          # O nome exato do label será a chave.
          extractAllPodLabels: true
          # Quando habilitado, o processador extrairá todas as anotações do pod associado e as adicionará como atributos de recurso.
          # O nome exato da anotação será a chave.
          extractAllPodAnnotations: true
        # Configura o coletor para coletar eventos do Kubernetes.
        # Adiciona o k8sobject receiver ao pipeline de logs e coleta eventos do Kubernetes por padrão.
        # Mais informações: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-objects-receiver
        kubernetesEvents:
          enabled: true
        # Configura o Kubernetes Cluster Receiver para coletar métricas no nível do cluster.
        # Adiciona o k8s_cluster receiver ao pipeline de métricas e inclui as regras necessárias na ClusterRole.
        # Mais informações: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-cluster-receiver
        clusterMetrics:
          enabled: true

      extraEnvs:
        - name: HYPERDX_API_KEY
          valueFrom:
            secretKeyRef:
              name: hyperdx-secret
              key: HYPERDX_API_KEY
        - name: YOUR_OTEL_COLLECTOR_ENDPOINT
          valueFrom:
            configMapKeyRef:
              name: otel-config-vars
              key: YOUR_OTEL_COLLECTOR_ENDPOINT

      config:
        exporters:
          otlp_http:
            endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
            compression: gzip
            headers:
              authorization: "Bearer ${env:HYPERDX_API_KEY}"
        service:
          pipelines:
            logs:
              exporters:
                - otlp_http
            metrics:
              exporters:
                - otlp_http

      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          memory: 512Mi
      ```
    </Accordion>

    Os `presets` ativam os receptores pré-configurados do chart, junto com as regras de RBAC de que eles precisam. O bloco `config` adiciona um exportador `otlp_http`, que lê o endpoint e a chave do ambiente, e o define como exportador dos pipelines `logs` e `metrics`. Todo o resto, incluindo os processadores `memory_limiter` e `batch`, vem dos valores padrão do chart.
  </Step>

  <Step title="Implante o coletor do nó" id="deploy-node-collector">
    Este Conjunto de Daemon executa um coletor por nó para coletar **logs de contêineres** de `/var/log/pods`, **métricas de host** do nó e **métricas do agente de nó do Kubernetes**: CPU e memória de cada pod do Kubernetes e de cada contêiner, incluindo a utilização em relação às requisições e aos limites.

    ```shell
    curl -fSL -o k8s_daemonset.yaml \
      https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_daemonset.yaml

    helm install --namespace otel-collectors k8s-otel-daemonset open-telemetry/opentelemetry-collector \
      --version 0.175.0 -f k8s_daemonset.yaml
    ```

    <Accordion title="k8s_daemonset.yaml">
      ```yaml
      # k8s_daemonset.yaml
      mode: daemonset

      image:
        repository: otel/opentelemetry-collector-contrib
        tag: 0.161.0

      # Required to use the kubeletstats cpu/memory utilization metrics
      clusterRole:
        create: true
        rules:
          - apiGroups:
              - ''
            resources:
              - nodes/proxy
            verbs:
              - get

      presets:
        logsCollection:
          enabled: true
        hostMetrics:
          enabled: true
        # Configures the Kubernetes Processor to add Kubernetes metadata.
        # Adds the k8sattributes processor to all the pipelines and adds the necessary rules to ClusterRole.
        # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-attributes-processor
        kubernetesAttributes:
          enabled: true
          # When enabled, the processor will extract all labels for an associated pod and add them as resource attributes.
          # The label's exact name will be the key.
          extractAllPodLabels: true
          # When enabled, the processor will extract all annotations for an associated pod and add them as resource attributes.
          # The annotation's exact name will be the key.
          extractAllPodAnnotations: true
        # Configures the collector to collect node, pod, and container metrics from the kubelet API.
        # Adds the kubeletstats receiver to the metrics pipeline and adds the necessary rules to ClusterRole.
        # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubeletstats-receiver
        kubeletMetrics:
          enabled: true

      extraEnvs:
        - name: HYPERDX_API_KEY
          valueFrom:
            secretKeyRef:
              name: hyperdx-secret
              key: HYPERDX_API_KEY
        - name: YOUR_OTEL_COLLECTOR_ENDPOINT
          valueFrom:
            configMapKeyRef:
              name: otel-config-vars
              key: YOUR_OTEL_COLLECTOR_ENDPOINT

      config:
        receivers:
          kubeletstats:
            insecure_skip_verify: true
        exporters:
          otlp_http:
            endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
            compression: gzip
            headers:
              authorization: "Bearer ${env:HYPERDX_API_KEY}"

        service:
          pipelines:
            logs:
              exporters:
                - otlp_http
            metrics:
              exporters:
                - otlp_http

      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          memory: 512Mi
      ```
    </Accordion>

    O preset `kubernetesAttributes` rotula cada linha de log e métrica com o pod, o namespace, o nó e a carga de trabalho de origem, além dos labels e das anotações do pod. São esses atributos que o Painel do Kubernetes usa como filtros.

    O arquivo define `insecure_skip_verify: true` para a conexão do coletor com o agente de nó do Kubernetes (kubelet) local, pois muitos clusters emitem certificados do kubelet que não abrangem o endereço do nó. Isso não afeta a verificação TLS do endpoint do seu serviço. Em produção, configure certificados confiáveis para o kubelet e remova essa configuração.

    Verifique se os coletores estão em execução e, em seguida, consulte os logs:

    ```shell
    kubectl get pods --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector
    kubectl logs --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector --prefix --tail=50
    ```

    Você deve ver um pod do Kubernetes da Implantação e um pod do Kubernetes do Conjunto de Daemon por nó, todos com status `Running`. Um pod do Kubernetes em execução, por si só, não garante que os dados estejam sendo entregues; por isso, verifique se há erros de exportação nos logs:

    * Respostas `401` ou `403` indicam que a chave de API no Secret está incorreta ou foi armazenada com o prefixo `Bearer`, que o arquivo de valores acaba repetindo.
    * Respostas `404` geralmente indicam que um caminho de sinal, como `/v1/logs`, foi anexado ao endpoint no ConfigMap.
    * Erros `no such host` ou de TLS indicam um erro de digitação no endpoint ou acesso de saída bloqueado na porta `4318`.
  </Step>
</Steps>

## Se nada aparecer {#if-nothing-shows-up}

* Comece lendo os logs do coletor com o comando `kubectl logs` mostrado acima. Problemas de autenticação, endpoint e TLS são todos relatados ali, com os códigos de erro listados acima.
* Se um pod do Kubernetes ficar travado em `CreateContainerConfigError`, o Secret ou o ConfigMap está ausente ou está em um namespace diferente do release do Helm. O comando `kubectl describe pod` informa o nome do objeto ausente.
* Se o pod do Kubernetes do Conjunto de Daemon ficar travado em `CreateContainerError` com `path "/" is mounted on "/" but it is not a shared or slave mount`, o sistema de arquivos raiz do nó não é uma montagem compartilhada, requisito do preset de métricas do host. Isso acontece em clusters locais cujos nós são executados dentro de contêineres. Execute `mount --make-rshared /` no nó e, em seguida, exclua o pod do Kubernetes para que ele seja recriado.
* Se os logs chegarem, mas as métricas não, procure erros de `kubeletstats` nos logs do Conjunto de Daemon. O receptor precisa da regra de função de cluster `nodes/proxy` definida no arquivo de valores e de acesso ao agente de nó do Kubernetes na porta `10250`.
* Se as métricas chegarem, mas os logs não, aguarde um minuto. O receptor de logs começa a leitura pelo final de cada arquivo; portanto, só aparecem as linhas gravadas depois que o coletor foi iniciado, e pods do Kubernetes que não registram nada não geram nenhum dado.
* Amplie o intervalo de tempo em **Busca** e remova todos os filtros. A fonte de dados padrão pode estar definida como **Traces** em vez de **Logs**.
* Para descartar um problema no próprio serviço, acesse **Team Settings → Managed Telemetry** e use **Send a Test Log**. Se esse log aparecer em **Busca**, o serviço está recebendo dados e o problema está entre o seu cluster e o endpoint.

## Adicionar telemetria de aplicações {#add-application-telemetry}

Os dois coletores cobrem o cluster. Já os rastros, assim como quaisquer logs ou métricas que suas aplicações emitam por meio de um SDK do OpenTelemetry, precisam ser exportados pela própria aplicação. Há duas formas de fazer isso.

<Tabs>
  <Tab title="Diretamente para o seu serviço" id="directly-to-your-service">
    Instrumente a aplicação e exporte diretamente para o endpoint gerenciado, conforme descrito em [Instrumente sua aplicação com OpenTelemetry](/pt-BR/clickstack/managed-onboarding/instrument-application-serverless). Armazene os valores de `OTEL_EXPORTER_OTLP_ENDPOINT` e `OTEL_EXPORTER_OTLP_HEADERS` da aba **Env vars** em um Secret e exponha-os ao pod do Kubernetes como variáveis de ambiente.

    Adicione os atributos do Kubernetes por meio da downward API para que a telemetria seja correlacionada com os dados de infraestrutura no Painel do Kubernetes:

    ```yaml
    env:
      - name: POD_NAME
        valueFrom:
          fieldRef:
            fieldPath: metadata.name
      - name: POD_UID
        valueFrom:
          fieldRef:
            fieldPath: metadata.uid
      - name: POD_NAMESPACE
        valueFrom:
          fieldRef:
            fieldPath: metadata.namespace
      - name: NODE_NAME
        valueFrom:
          fieldRef:
            fieldPath: spec.nodeName
      - name: OTEL_RESOURCE_ATTRIBUTES
        value: k8s.pod.name=$(POD_NAME),k8s.pod.uid=$(POD_UID),k8s.namespace.name=$(POD_NAMESPACE),k8s.node.name=$(NODE_NAME)
    ```
  </Tab>

  <Tab title="Por meio do coletor do nó" id="through-the-node-collector">
    Como alternativa, envie os dados por meio do Conjunto de Daemon, que já recebe OTLP em cada nó nas portas de host `4317` (gRPC) e `4318` (HTTP). Essa abordagem tem duas vantagens: o coletor adiciona a chave de API, de modo que seus pods do Kubernetes nunca precisam armazená-la, e o processador `k8s_attributes` marca cada span e registro de log com o namespace, o nó, a carga de trabalho e os labels do pod do Kubernetes de origem, alinhando os rastros da aplicação aos dados de infraestrutura.

    O arquivo de valores baixado roteia apenas logs e métricas. Adicione também o exportador ao pipeline `traces` e, em seguida, faça o upgrade da release:

    ```yaml
    # Adicione à seção service.pipelines de k8s_daemonset.yaml
          traces:
            exporters:
              - otlp_http
    ```

    ```shell
    helm upgrade --namespace otel-collectors k8s-otel-daemonset open-telemetry/opentelemetry-collector \
      --version 0.175.0 -f k8s_daemonset.yaml
    ```

    Em seguida, aponte cada aplicação para o coletor em execução no próprio nó. A downward API fornece o endereço do nó e o UID do pod do Kubernetes:

    ```yaml
    env:
      - name: HOST_IP
        valueFrom:
          fieldRef:
            fieldPath: status.hostIP
      - name: POD_UID
        valueFrom:
          fieldRef:
            fieldPath: metadata.uid
      - name: OTEL_EXPORTER_OTLP_ENDPOINT
        value: http://$(HOST_IP):4318
      - name: OTEL_EXPORTER_OTLP_PROTOCOL
        value: http/protobuf
      - name: OTEL_SERVICE_NAME
        value: <your-service-name>
      - name: OTEL_RESOURCE_ATTRIBUTES
        value: k8s.pod.uid=$(POD_UID)
    ```

    Não é necessária nenhuma chave de API dentro do cluster. O coletor localiza o pod do Kubernetes pelo UID em `OTEL_RESOURCE_ATTRIBUTES` e adiciona automaticamente `k8s.pod.name`, `k8s.namespace.name`, `k8s.node.name`, a carga de trabalho proprietária e os labels do pod do Kubernetes. Ele também pode identificar pods do Kubernetes pelo endereço de origem da conexão, mas isso depende de a rede do cluster preservar o IP do pod do Kubernetes no caminho até a porta de host; por isso, informe o UID.
  </Tab>
</Tabs>
