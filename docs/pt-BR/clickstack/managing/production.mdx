Ao implantar o ClickStack Open Source em produção, leve em conta as seguintes práticas de segurança, estabilidade e configuração.

## Segurança de rede e portas {#network-security}

Por padrão, o Docker Compose expõe portas no host, tornando-as acessíveis de fora do contêiner — mesmo que ferramentas como `ufw` (Uncomplicated Firewall) estejam habilitadas. Esse comportamento se deve à pilha de rede do Docker, que pode contornar as regras de firewall no nível do host, a menos que seja explicitamente configurada.

**Recomendação:**

Exponha apenas as portas necessárias para uso em produção. Normalmente os endpoints OTLP, o servidor de API e o frontend.

Por exemplo, remova ou comente os mapeamentos de porta desnecessários no seu arquivo `docker-compose.yml`:

```yaml
ports:
  - "4317:4317"  # OTLP gRPC
  - "4318:4318"  # OTLP HTTP
  - "8080:8080"  # Only if needed for the API
# Avoid exposing internal ports like ClickHouse 8123 or MongoDB 27017.
```

Consulte a [documentação de rede do Docker](https://docs.docker.com/network/) para obter detalhes sobre isolamento de contêineres e reforço de acesso.

## Configuração do segredo de sessão {#session-secret}

Em produção, você deve definir um valor forte e aleatório para a variável de ambiente `EXPRESS_SESSION_SECRET` da Interface do ClickStack, a fim de proteger os dados de sessão e evitar adulterações.

Veja como adicioná-la ao arquivo `docker-compose.yml` no serviço app:

```yaml
  app:
    image: ${IMAGE_NAME_HDX}:${IMAGE_VERSION}
    ports:
      - ${HYPERDX_API_PORT}:${HYPERDX_API_PORT}
      - ${HYPERDX_APP_PORT}:${HYPERDX_APP_PORT}
    environment:
      FRONTEND_URL: ${HYPERDX_APP_URL}:${HYPERDX_APP_PORT}
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_API_PORT: ${HYPERDX_API_PORT}
      HYPERDX_APP_PORT: ${HYPERDX_APP_PORT}
      HYPERDX_APP_URL: ${HYPERDX_APP_URL}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      MINER_API_URL: 'http://miner:5123'
      MONGO_URI: 'mongodb://db:27017/hyperdx'
      NEXT_PUBLIC_SERVER_URL: http://127.0.0.1:${HYPERDX_API_PORT}
      OTEL_SERVICE_NAME: 'hdx-oss-api'
      USAGE_STATS_ENABLED: ${USAGE_STATS_ENABLED:-true}
      EXPRESS_SESSION_SECRET: "super-secure-random-string"
    networks:
      - internal
    depends_on:
      - ch-server
      - db1
```

Você pode gerar um segredo forte com o `openssl`:

```shell
openssl rand -hex 32
```

Evite fazer commit de secrets no controle de versão. Em produção, considere usar ferramentas de gerenciamento de variáveis de ambiente (por exemplo, Docker Secrets, HashiCorp Vault ou configurações de CI/CD específicas para cada ambiente).

## Ingestão segura {#secure-ingestion}

Toda a ingestão deve ser feita pelas portas OTLP expostas pela distribuição do coletor OpenTelemetry (OTel) do ClickStack. Por padrão, isso exige uma API key de ingestão segura, gerada na inicialização. Essa chave é necessária para enviar dados às portas OTel e pode ser encontrada na Interface do ClickStack em `Team Settings → API Keys`.

### Criar um usuário de ingestão {#create-a-database-ingestion-user-oss}

Recomenda-se criar um usuário dedicado para o OTel collector para ingestão no ClickHouse e garantir que a ingestão seja direcionada a um banco de dados específico, por exemplo, `otel`. Consulte [&quot;Criando um usuário de ingestão&quot;](/pt-BR/clickstack/ingesting-data/collector#creating-an-ingestion-user) para mais detalhes.

## ClickHouse {#clickhouse}

Usuários que gerenciam a própria instância do ClickHouse devem seguir as boas práticas abaixo.

### Boas práticas de segurança {#self-managed-security}

Se você gerencia sua própria instância do ClickHouse, é essencial habilitar o **TLS**, exigir autenticação e seguir as boas práticas de proteção de acesso. Consulte [esta postagem do blog](https://www.wiz.io/blog/clickhouse-and-wiz) para conhecer casos reais de configurações incorretas e saber como evitá-los.

O ClickHouse OSS já vem com recursos de segurança robustos. No entanto, eles precisam ser configurados:

* **Use TLS** por meio de `tcp_port_secure` e `<openSSL>` em `config.xml`. Consulte [guides/sre/configuring-tls](/pt-BR/concepts/features/security/tls/configuring-tls).
* **Defina uma senha forte** para o usuário `default` ou desabilite-o.
* **Evite expor o ClickHouse externamente**, a menos que isso seja intencional. Por padrão, o ClickHouse escuta apenas em `localhost`, a menos que `listen_host` seja modificado.
* **Use métodos de autenticação** como senhas, certificados, chaves SSH ou [autenticadores externos](/pt-BR/concepts/features/security/external-authenticators/index).
* **Restrinja o acesso** usando filtragem por IP e a cláusula `HOST`. Consulte [sql-reference/statements/create/user#user-host](/pt-BR/reference/statements/create/user#user-host).
* **Habilite o Controle de Acesso Baseado em Funções (RBAC)** para conceder privilégios granulares. Consulte [operations/access-rights](/pt-BR/concepts/features/security/access-rights).
* **Aplique cotas e limites** usando [cotas](/pt-BR/concepts/features/configuration/server-config/quotas), [settings profiles](/pt-BR/concepts/features/configuration/settings/settings-profiles) e modos somente leitura.
* **Criptografe os dados em repouso** e use armazenamento externo seguro. Consulte [operations/storing-data](/pt-BR/concepts/features/configuration/server-config/storing-data) e [cloud/security/CMEK](/pt-BR/products/cloud/guides/security/cmek).
* **Evite credenciais fixas no código.** Use [coleções nomeadas](/pt-BR/concepts/features/configuration/server-config/named-collections) ou funções IAM no ClickHouse Cloud.
* **Audite acessos e consultas** usando [logs do sistema](/pt-BR/reference/system-tables/query_log) e [logs de sessão](/pt-BR/reference/system-tables/session_log).

Consulte também [autenticadores externos](/pt-BR/concepts/features/security/external-authenticators/index) e [configurações de complexidade de consultas](/pt-BR/concepts/features/configuration/settings/query-complexity) para gerenciar usuários e garantir limites de consultas e de recursos.

### Permissões de usuário para a Interface do ClickStack {#user-permissions}

O usuário do ClickHouse usado pela Interface do ClickStack deve ter `readonly = 2`. A UI define suas próprias configurações, como `date_time_output_format`, em todas as consultas, e os gráficos de SQL bruto também definem `readonly = 2`; por isso, com um usuário `readonly = 1`, essas consultas falham com `Cannot modify '...' setting in readonly mode`. Com `readonly = 2`, a UI também pode definir `max_rows_to_read`, `read_overflow_mode` e `cancel_http_readonly_queries_on_client_close`; se você restringir `max_rows_to_read`, permita pelo menos 1 milhão. `wait_end_of_query` é um parâmetro da interface HTTP, e não uma configuração, portanto não exige concessão.

Por exemplo:

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

Por padrão, o usuário `default`, tanto no OSS quanto no ClickHouse Cloud, já tem essas permissões, mas recomendamos criar um usuário dedicado.

## Configurar Time To Live (TTL) {#configure-ttl}

Certifique-se de que o [Time To Live (TTL)](/pt-BR/clickstack/managing/ttl) foi [configurado adequadamente](/pt-BR/clickstack/managing/ttl#modifying-ttl) para a sua implantação do ClickStack. Isso controla por quanto tempo os dados são retidos — o padrão de 30 dias pode precisar de ajustes.

## Diretrizes para o MongoDB {#mongodb-guidelines}

Siga a [lista de verificação de segurança oficial do MongoDB](https://www.mongodb.com/docs/manual/administration/security-checklist/).
