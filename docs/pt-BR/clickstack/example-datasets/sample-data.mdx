Este guia demonstra o ClickStack Open Source usando um conjunto de dados de exemplo.

O exemplo a seguir pressupõe que você iniciou o ClickStack Open Source usando a [imagem tudo em um](/pt-BR/clickstack/getting-started/oss) e copiou a [API key de ingestão](/pt-BR/clickstack/getting-started/oss#copy-ingestion-api-key).

<Steps>
  <Step title="Acesse a Interface do ClickStack" id="navigate-to-the-hyperdx-ui">
    Acesse [http://localhost:8080](http://localhost:8080) para abrir a interface do ClickStack.

    <div className="ch-image-lg">
      <Frame>
        ![Interface do ClickStack](/images/use-cases/observability/hyperdx.webp)
      </Frame>
    </div>
  </Step>

  <Step title="Copiar API key de ingestão" id="copy-ingestion-api-key">
    Acesse [`Team Settings`](http://localhost:8080/team) e copie a `Ingestion API Key` na seção `API Keys`. Essa chave de API garante a segurança da ingestão de dados por meio do coletor OpenTelemetry.

    <div className="ch-image-lg">
      <Frame>
        ![Copiar chave de API](/images/use-cases/observability/copy_api_key.webp)
      </Frame>
    </div>
  </Step>

  <Step title="Baixar dados de amostra" id="download-sample-data">
    Para popular a UI com dados de amostra, baixe o seguinte arquivo:

    [Dados de amostra](https://storage.googleapis.com/hyperdx/sample.tar.gz)

    ```shell
    # curl
    curl -O https://storage.googleapis.com/hyperdx/sample.tar.gz
    # or
    # wget https://storage.googleapis.com/hyperdx/sample.tar.gz
    ```

    Este arquivo contém exemplos de logs, métricas e rastros do nosso [OpenTelemetry demo](https://github.com/ClickHouse/opentelemetry-demo) público — uma loja virtual simples baseada em microsserviços. Copie este arquivo para um diretório de sua escolha.
  </Step>

  <Step title="Carregar dados de amostra" id="load-sample-data">
    Para carregar esses dados, basta enviá-los para o endpoint HTTP do coletor OpenTelemetry (OTel) implantado.

    Primeiro, exporte a chave de API copiada anteriormente.

    ```shell
    # export API key
    export CLICKSTACK_API_KEY=<YOUR_INGESTION_API_KEY>
    ```

    Execute o seguinte comando para enviar os dados ao OTel collector:

    ```shell
    for filename in $(tar -tf sample.tar.gz); do
      endpoint="http://localhost:4318/v1/${filename%.json}"
      echo "loading ${filename%.json}"
      tar -xOf sample.tar.gz "$filename" | while read -r line; do
        printf '%s\n' "$line" | curl -s -o /dev/null -X POST "$endpoint" \
        -H "Content-Type: application/json" \
        -H "authorization: ${CLICKSTACK_API_KEY}" \
        --data-binary @-
      done
    done
    ```

    Isso simula fontes de dados OTLP de logs, traces e métricas enviando dados para o OTel collector. Em produção, essas fontes de dados podem ser clientes de linguagem ou até mesmo outros OTel collectors.

    Ao voltar para a visualização `Search`, você verá que os dados começaram a ser carregados (ajuste o intervalo de tempo para `Last 1 hour` se os dados não forem exibidos):

    <div className="ch-image-lg">
      <Frame>
        ![Busca na Interface do ClickStack](/images/use-cases/observability/hyperdx-10.webp)
      </Frame>
    </div>

    O carregamento dos dados levará alguns minutos. Aguarde a conclusão do carregamento antes de passar para as próximas etapas.
  </Step>

  <Step title="Explorar sessões" id="explore-sessions">
    Suponha que recebemos relatos de que nossos usuários estão tendo problemas para pagar pelos produtos. Podemos visualizar a experiência deles usando os recursos de reprodução de sessão da Interface do ClickStack.

    Selecione [`Client Sessions`](http://localhost:8080/sessions?from=1747312320000\&to=1747312920000\&sessionSource=l1324572572) no menu à esquerda.

    <div className="ch-image-lg">
      <Frame>
        ![Sessões](/images/use-cases/observability/hyperdx-11.webp)
      </Frame>
    </div>

    Esta visualização nos permite ver as sessões de front-end da nossa loja de e-commerce. As sessões permanecem anônimas até que os usuários façam o checkout e tentem concluir uma compra.

    Observe que algumas sessões com e-mails têm um erro associado, o que pode confirmar os relatos de transações com falha.

    Selecione um trace com falha e um e-mail associado. A visualização seguinte nos permite reproduzir a sessão do usuário e analisar o problema. Clique em play para assistir à sessão.

    <div className="ch-image-lg">
      <Frame>
        ![Reprodução de sessão](/images/use-cases/observability/hyperdx-12.webp)
      </Frame>
    </div>

    A reprodução mostra o usuário navegando pelo site e adicionando itens ao carrinho. Fique à vontade para avançar até o momento da sessão em que ele tenta concluir o pagamento.

    <Tip>
      Os erros são marcados em vermelho na linha do tempo.
    </Tip>

    O usuário não conseguiu finalizar o pedido, sem nenhum erro aparente. Role até o final do painel esquerdo, que contém os eventos de rede e de console do navegador do usuário. Você verá que um erro 500 foi lançado ao fazer uma chamada para `/api/checkout`.

    <div className="ch-image-lg">
      <Frame>
        ![Erro na sessão](/images/use-cases/observability/hyperdx-13.webp)
      </Frame>
    </div>

    Selecione esse erro `500`. Nem a `Overview` nem os `Column Values` indicam a origem do problema, exceto pelo fato de que o erro é inesperado e causa um `Internal Error`.
  </Step>

  <Step title="Explorar rastros" id="explore-traces">
    Acesse a aba `Trace` para ver o trace distribuído completo.

    <div className="ch-image-lg">
      <Frame>
        ![Trace da sessão](/images/use-cases/observability/hyperdx-14.webp)
      </Frame>
    </div>

    Role o trace para baixo até a origem do erro: o span do serviço `checkout`. Selecione o span do serviço `Payment`.

    <div className="ch-image-lg">
      <Frame>
        ![Span](/images/use-cases/observability/hyperdx-15.webp)
      </Frame>
    </div>

    Selecione a aba `Column Values` e role para baixo. Vemos que o problema está associado a um cache cheio.

    <div className="ch-image-lg">
      <Frame>
        ![Valores da coluna](/images/use-cases/observability/hyperdx-16.webp)
      </Frame>
    </div>

    Rolando de volta para cima até o trace, vemos que os logs estão correlacionados com o span, graças à configuração feita anteriormente. Eles fornecem mais contexto.

    <div className="ch-image-lg">
      <Frame>
        ![Log correlacionado](/images/use-cases/observability/hyperdx-17.webp)
      </Frame>
    </div>

    Constatamos que um cache está ficando cheio no serviço de pagamento, o que impede a conclusão dos pagamentos.
  </Step>

  <Step title="Explorar logs" id="explore-logs">
    Para obter mais detalhes, podemos voltar à [visualização `Search`](http://localhost:8080/search):

    Selecione `Logs` nas fontes de dados e aplique um filtro para o serviço `payment`.

    <div className="ch-image-lg">
      <Frame>
        ![Logs](/images/use-cases/observability/hyperdx-18.webp)
      </Frame>
    </div>

    Podemos ver que, embora o problema seja recente, o número de pagamentos afetados é alto. Além disso, um cache relacionado aos pagamentos com Visa parece estar causando problemas.
  </Step>

  <Step title="Métricas do gráfico" id="chart-metrics">
    Embora um erro tenha claramente sido introduzido no código, podemos usar métricas para confirmar o tamanho do cache. Acesse a visualização `Chart Explorer`.

    Selecione `Metrics` como fonte de dados. Preencha o criador de gráficos para plotar o `Maximum` de `visa_validation_cache.size (Gauge)` e clique no botão de executar. O cache claramente aumentou até atingir um tamanho máximo e, a partir daí, passaram a ser gerados erros.

    <div className="ch-image-lg">

      </Frame>
    </div>
  </Step>
