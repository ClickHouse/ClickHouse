## Funções do coletor {#collector-roles-self-configured}

Os Coletores OpenTelemetry podem ser implantados em duas funções principais:

* **Agente** - Instâncias de agente coletam dados na borda, por exemplo, em servidores ou em nós do Kubernetes, ou recebem eventos diretamente de aplicações instrumentadas com um SDK do OpenTelemetry. Neste último caso, a instância de agente é executada junto com a aplicação ou no mesmo host que ela (como um sidecar ou um Conjunto de Daemon). Os agentes podem enviar seus dados diretamente ao ClickHouse ou a uma instância de gateway. No primeiro caso, isso é chamado de [padrão de implantação de agente](https://opentelemetry.io/docs/collector/deployment/agent/).

* **Gateway** - Instâncias de gateway fornecem um serviço independente (por exemplo, uma Implantação no Kubernetes), normalmente por cluster, por data center ou por região. Elas recebem eventos de aplicações (ou de outros coletores atuando como agentes) por meio de um único endpoint OTLP. Em geral, implanta-se um conjunto de instâncias de gateway, com um balanceador de carga pronto para uso distribuindo a carga entre elas. Quando todos os agentes e aplicações enviam seus sinais para esse único endpoint, isso costuma ser chamado de [padrão de implantação de gateway](https://opentelemetry.io/docs/collector/deployment/gateway/).

**Importante: o coletor, inclusive nas distribuições padrão do ClickStack, assume a [função de gateway descrita abaixo](#collector-roles-self-configured), recebendo dados de agentes ou SDKs.**

Usuários que implantam OTel collectors no papel de agente normalmente utilizam a [distribuição contrib padrão do coletor](https://github.com/open-telemetry/opentelemetry-collector-contrib), e não a versão do ClickStack, mas também podem usar outras tecnologias compatíveis com OTLP, como [Fluentd](https://www.fluentd.org/) e [Vector](https://vector.dev/).

## Implantação do coletor {#configuring-the-collector-self-configured}

<br />

Sempre que possível, recomendamos usar a distribuição oficial do coletor do ClickStack na função de gateway ao enviar dados para o Self-managed ClickHouse Observability. Se optar por usar o seu próprio coletor, certifique-se de que ele inclua o [exportador do ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

O coletor pode ser implantado via Helm (recomendado para Kubernetes) ou via Docker. O [Chart do Helm do ClickStack](https://github.com/ClickHouse/ClickStack-helm-charts) oficial incorpora o [Chart Helm do Coletor OpenTelemetry](https://github.com/open-telemetry/opentelemetry-helm-charts) upstream como subchart, com a imagem da distribuição do ClickStack já pré-configurada. Para uma implantação independente do coletor, o chart upstream pode ser usado diretamente com a imagem do ClickStack, conforme mostrado abaixo.

<Tabs>
  <Tab title="Helm">
    Adicione o repositório Helm upstream do OpenTelemetry:

    ```shell
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update
    ```

    Crie um arquivo `values.yaml` que configure a imagem do ClickStack e as credenciais do Self-managed ClickHouse Observability:

    ```yaml
    # values.yaml
    mode: deployment

    image:
      repository: docker.clickhouse.com/clickhouse/clickstack-otel-collector
      tag: "2.19.0"

    ports:
      otlp:
        enabled: true
      otlp-http:
        enabled: true

    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "https://your-instance.clickhouse.cloud:8443"
      - name: CLICKHOUSE_USER
        value: "default"
      - name: CLICKHOUSE_PASSWORD
        value: "<password>"
    ```

    Instale o chart:

    ```shell
    helm install clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    Para implantações em produção, recomendamos armazenar `CLICKHOUSE_PASSWORD` em um secret do Kubernetes e referenciá-lo via `extraEnvsFrom`, em vez de definir o valor diretamente no arquivo.
  </Tab>

  <Tab title="Docker">
    Para implantar a distribuição do ClickStack do coletor OTel em modo independente, execute o seguinte comando docker:

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```

    <Info>
      **Atualização do nome da imagem**

      As imagens do ClickStack agora são publicadas como `clickhouse/clickstack-*` (anteriormente `docker.hyperdx.io/hyperdx/*`).
    </Info>
  </Tab>
</Tabs>

A instância do ClickHouse de destino é configurada por meio das variáveis de ambiente `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER` e `CLICKHOUSE_PASSWORD`. O `CLICKHOUSE_ENDPOINT` deve ser o endpoint HTTP completo do ClickHouse Cloud, incluindo o protocolo e a porta — por exemplo, `https://99rr6dm6v3.us-central1.gcp.clickhouse.cloud:8443`.

Para saber como obter suas credenciais do Self-managed ClickHouse Observability, consulte [esta página](/pt-BR/products/cloud/guides/sql-console/connection-details).

<Info>
  **Usuário de produção**

  Em produção, use um usuário com as [credenciais apropriadas](/pt-BR/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured).
</Info>

### Modificação da configuração {#modifying-otel-collector-configuration-managed-self-configured}

#### Configurando uma instância Self-managed ClickHouse Observability {#configuring-managed-clickstack-self-configured}

O coletor OpenTelemetry pode ser configurado para usar uma instância Self-managed ClickHouse Observability por meio das variáveis de ambiente `CLICKHOUSE_ENDPOINT`, `CLICKHOUSE_USER` e `CLICKHOUSE_PASSWORD`. A forma de defini-las depende do seu método de implantação:

<Tabs>
  <Tab title="Helm">
    Substitua as entradas correspondentes em `extraEnvs` no seu `values.yaml` e, em seguida, faça o upgrade da release:

    ```yaml
    # values.yaml
    extraEnvs:
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```
  </Tab>

  <Tab title="Docker">
    A imagem independente do coletor OpenTelemetry pode ser configurada por meio de variáveis de ambiente:

    ```shell
    export CLICKHOUSE_ENDPOINT=<HTTPS ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    ```

    ```shell
    docker run -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

## Protegendo o coletor {#securing-the-collector-self-configured}

Por padrão, o Coletor OpenTelemetry do ClickStack não é protegido quando implantado fora das distribuições Open Source e não exige autenticação em suas portas OTLP.

Para proteger a ingestão, especifique um token de autenticação ao implantar o coletor usando a variável de ambiente `OTLP_AUTH_TOKEN`. A forma de defini-la depende do seu método de implantação:

<Tabs>
  <Tab title="Helm">
    Adicione `OTLP_AUTH_TOKEN` a `extraEnvs` no seu `values.yaml` e, em seguida, faça o upgrade da release:

    ```yaml
    # values.yaml
    extraEnvs:
      - name: OTLP_AUTH_TOKEN
        value: "a_very_secure_string"
      - name: CLICKHOUSE_ENDPOINT
        value: "<HTTPS_ENDPOINT>"
      - name: CLICKHOUSE_USER
        value: "<CLICKHOUSE_USER>"
      - name: CLICKHOUSE_PASSWORD
        value: "<CLICKHOUSE_PASSWORD>"
    ```

    ```shell
    helm upgrade clickstack-otel-collector open-telemetry/opentelemetry-collector -f values.yaml
    ```

    Para implantações em produção, recomendamos armazenar `OTLP_AUTH_TOKEN` e `CLICKHOUSE_PASSWORD` em um secret do Kubernetes e referenciá-los via `extraEnvsFrom`.
  </Tab>

  <Tab title="Docker">
    ```sh
    export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
    export CLICKHOUSE_USER=<CLICKHOUSE_USER>
    export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
    export OTLP_AUTH_TOKEN="a_very_secure_string"

    docker run \
      -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
      -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
      -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
      -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
      -p 4317:4317 \
      -p 4318:4318 \
      clickhouse/clickstack-otel-collector:latest
    ```
  </Tab>
</Tabs>

Também recomendamos:

* Configurar o coletor para se comunicar com o ClickHouse via HTTPS.
* Criar um usuário dedicado à ingestão, com permissões limitadas — veja abaixo.
* Habilitar TLS no endpoint OTLP, garantindo comunicação criptografada entre os SDKs/agentes e o coletor. Isso pode ser feito por meio de uma [configuração personalizada do coletor](#extending-collector-config).

### Criando um usuário de ingestão {#creating-an-ingestion-user-self-configured}

Recomendamos criar um banco de dados e um usuário dedicados para o OTel collector realizar a ingestão no Self-managed ClickHouse Observability. Esse usuário deve ter permissão para criar as [tabelas usadas pelo coletor](/pt-BR/clickstack/self-configured/ingesting-data/schemas) e fazer insert nelas.

```sql
CREATE DATABASE otel;
CREATE USER hyperdx_ingest IDENTIFIED WITH sha256_password BY 'ClickH0u3eRocks123!';
GRANT SELECT, INSERT, CREATE DATABASE, CREATE TABLE, CREATE VIEW ON otel.* TO hyperdx_ingest;
```

Isso pressupõe que o coletor foi configurado para usar o banco de dados `otel`, o que pode ser controlado pela variável de ambiente `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`. Passe-a para o coletor [da mesma forma que as demais variáveis de ambiente](#modifying-otel-collector-configuration-managed-self-configured).

## Processamento - filtragem, transformação e enriquecimento {#processing-filtering-transforming-enriching-self-configured}

Invariavelmente, os usuários vão querer filtrar, transformar e enriquecer as mensagens de eventos durante a ingestão. Os usuários podem adicionar processadores e pipelines ao coletor do ClickStack com uma [configuração personalizada](#extending-collector-config). Para manter esse processamento fora do coletor do ClickStack, recomendamos que os usuários optem por uma das seguintes alternativas:

* Implantar sua própria versão do OTel collector para realizar a filtragem e o processamento, enviando os eventos ao coletor do ClickStack via OTLP para ingestão no ClickHouse.
* Implantar sua própria versão do OTel collector e enviar os eventos diretamente ao ClickHouse usando o exportador do ClickHouse.

Se o processamento for feito com o OTel collector, recomendamos realizar as transformações nas instâncias de gateway e reduzir ao mínimo o trabalho feito nas instâncias de agente. Isso garante que os recursos exigidos pelos agentes na borda, executados nos servidores, sejam os menores possíveis. Normalmente, vemos usuários realizando apenas filtragem (para reduzir o uso desnecessário da rede), definição de timestamp (via operadores) e enriquecimento, que exige contexto nos agentes. Por exemplo, se as instâncias de gateway estiverem em um cluster Kubernetes diferente, o enriquecimento com dados do k8s precisará ocorrer no agente.

O OpenTelemetry oferece os seguintes recursos de processamento e filtragem, que você pode aproveitar:

* **Processadores** - Os processadores recebem os dados coletados pelos [receptores e os modificam ou transformam](https://opentelemetry.io/docs/collector/transforming-telemetry/) antes de enviá-los aos exportadores. Os processadores são aplicados na ordem em que estão configurados na seção `processors` da configuração do coletor. Eles são opcionais, mas o conjunto mínimo é [normalmente recomendado](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor#recommended-processors). Ao usar um OTel collector com o ClickHouse, recomendamos limitar os processadores a:

* Um [memory&#95;limiter](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/memorylimiterprocessor/README.md), usado para evitar situações de falta de memória no coletor. Consulte [Estimando recursos](#estimating-resources-self-configured) para obter recomendações.

* Qualquer processador que realize enriquecimento com base em contexto. Por exemplo, o [Kubernetes Attributes Processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/k8sattributesprocessor) permite definir automaticamente atributos de recurso de spans, métricas e logs com metadados do k8s, por exemplo, enriquecendo eventos com o ID do pod de origem.

* [Amostragem tail ou head](https://opentelemetry.io/docs/concepts/sampling/), se necessária para traces.

* [Filtragem básica](https://opentelemetry.io/docs/collector/transforming-telemetry/) - Descartar eventos desnecessários, caso isso não possa ser feito via operador (veja abaixo).

* [Agrupamento em lote](https://github.com/open-telemetry/opentelemetry-collector/tree/main/processor/batchprocessor) - essencial ao trabalhar com o ClickHouse para garantir que os dados sejam enviados em lotes. Consulte [&quot;Otimizando inserts&quot;](#optimizing-inserts-self-configured).

* **Operadores** - Os [operadores](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/pkg/stanza/docs/operators/README.md) são a unidade de processamento mais básica disponível no receptor. Há suporte a parsing básico, o que permite definir campos como Severity e Timestamp. Também há suporte a parsing de JSON e regex, além de filtragem de eventos e transformações básicas. Recomendamos realizar a filtragem de eventos aqui.

Recomendamos que os usuários evitem processamento excessivo de eventos com operadores ou [transform processors](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/transformprocessor/README.md). Eles podem gerar uma sobrecarga considerável de memória e CPU, especialmente o parsing de JSON.  É possível realizar todo o processamento no ClickHouse no momento do insert, com materialized views e colunas, salvo algumas exceções - especificamente, o enriquecimento dependente de contexto, como a adição de metadados do k8s. Para mais detalhes, consulte [Extraindo estrutura com SQL](/pt-BR/guides/use-cases/observability/build-your-own/schema-design#extracting-structure-with-sql).

### Exemplo {#example-processing-self-configured}

A configuração a seguir mostra a coleta deste [arquivo de log não estruturado](https://datasets-documentation.s3.eu-west-3.amazonaws.com/http_logs/access-unstructured.log.gz). Ela poderia ser usada por um coletor no papel de agente que envia dados para o gateway do ClickStack.

Observe o uso de operadores para extrair estrutura das linhas de log (`regex_parser`) e filtrar eventos, além de um processador para agrupar eventos em lotes e limitar o uso de memória.

```yaml file=code_snippets/ClickStack/config-unstructured-logs-with-processor.yaml
receivers:
  filelog:
    include:
      - /opt/data/logs/access-unstructured.log
    start_at: beginning
    operators:
      - type: regex_parser
        regex: '^(?P<ip>[\d.]+)\s+-\s+-\s+\[(?P<timestamp>[^\]]+)\]\s+"(?P<method>[A-Z]+)\s+(?P<url>[^\s]+)\s+HTTP/[^\s]+"\s+(?P<status>\d+)\s+(?P<size>\d+)\s+"(?P<referrer>[^"]*)"\s+"(?P<user_agent>[^"]*)"'
        timestamp:
          parse_from: attributes.timestamp
          layout: '%d/%b/%Y:%H:%M:%S %z'
          #22/Jan/2019:03:56:14 +0330
processors:
  batch:
    timeout: 1s
    send_batch_size: 10000
  memory_limiter:
    check_interval: 1s
    limit_mib: 2048
    spike_limit_mib: 256
exporters:
  # HTTP setup
  otlphttp/hdx:
    endpoint: 'http://localhost:4318'
    headers:
      authorization: <YOUR_INGESTION_API_KEY>
    compression: gzip

  # gRPC setup (alternative)
  otlp/hdx:
    endpoint: 'localhost:4317'
    headers:
      authorization: <YOUR_API_INGESTION_KEY>
    compression: gzip
service:
  telemetry:
    metrics:
      address: 0.0.0.0:9888 # Modified as 2 collectors running on same host
  pipelines:
    logs:
      receivers: [filelog]
      processors: [batch]
      exporters: [otlphttp/hdx]

```

Se você tiver configurado `OTLP_AUTH_TOKEN`, use esse token como valor do cabeçalho de autorização no exemplo acima. Consulte [Protegendo o coletor](#securing-the-collector-self-configured).

Para configurações mais avançadas, consulte a [documentação do Coletor OpenTelemetry](https://opentelemetry.io/docs/collector/).

## Otimizando inserts {#optimizing-inserts-self-configured}

Para obter alto desempenho de inserção com fortes garantias de consistência, siga algumas regras simples ao inserir dados de observabilidade no ClickHouse por meio do Coletor do ClickStack. Com o OTel collector configurado corretamente, essas regras são fáceis de seguir. Isso também evita [problemas comuns](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse) que os usuários enfrentam ao usar o ClickHouse pela primeira vez.

### Agrupamento em lotes {#batching-self-configured}

Por padrão, cada insert enviado ao ClickHouse faz com que o ClickHouse crie imediatamente uma parte de armazenamento contendo os dados do insert, juntamente com outros metadados que precisam ser armazenados. Portanto, enviar uma quantidade menor de inserts, cada um com mais dados, em vez de uma quantidade maior de inserts, cada um com menos dados, reduzirá o número de gravações necessárias. Recomendamos inserir dados em lotes razoavelmente grandes, de pelo menos 1,000 linhas por vez. Mais detalhes [aqui](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse#data-needs-to-be-batched-for-optimal-performance).

Por padrão, os inserts no ClickHouse são síncronos e idempotentes quando idênticos. Para tabelas da família de motores MergeTree, o ClickHouse irá, por padrão, [deduplicar inserts](https://clickhouse.com/blog/common-getting-started-issues-with-clickhouse#5-deduplication-at-insert-time) automaticamente. Isso significa que os inserts são tolerantes a falhas em casos como os seguintes:

* (1) Se o nó que recebe os dados apresentar problemas, a consulta de inserção atingirá o tempo limite (ou receberá um erro mais específico) e não receberá uma confirmação.
* (2) Se os dados tiverem sido gravados pelo nó, mas a confirmação não puder ser retornada ao remetente da consulta devido a interrupções de rede, o remetente receberá um erro de tempo limite ou de rede.

Do ponto de vista do coletor, pode ser difícil distinguir (1) de (2). No entanto, em ambos os casos, o insert não confirmado pode simplesmente ser tentado novamente de imediato. Desde que a consulta de inserção repetida contenha os mesmos dados na mesma ordem, o ClickHouse ignorará automaticamente o insert repetido caso o insert original (não confirmado) tenha sido bem-sucedido.

Por esse motivo, a distribuição ClickStack do OTel collector utiliza o [processador em lote](https://github.com/open-telemetry/opentelemetry-collector/blob/main/processor/batchprocessor/README.md). Isso garante que os inserts sejam enviados como lotes consistentes de linhas que atendem aos requisitos acima. Se a expectativa for de que um coletor tenha alta vazão (eventos por segundo) e pelo menos 10,000 eventos puderem ser enviados em cada insert, este geralmente é o único agrupamento em lote necessário no pipeline. Valores de até 100,000 podem ser usados se a memória permitir. Nesse caso, o coletor fará o flush dos lotes antes que o `timeout` do processador em lote seja atingido, garantindo que a latência de ponta a ponta do pipeline permaneça baixa e que os lotes tenham um tamanho consistente.

### Use inserções assíncronas {#use-asynchronous-inserts-self-configured}

Normalmente, os usuários são obrigados a enviar lotes menores quando a vazão de um coletor é baixa e, ainda assim, esperam que os dados cheguem ao ClickHouse com uma latência de ponta a ponta mínima. Nesse caso, lotes pequenos são enviados quando o `timeout` do processador em lote expira. Isso pode causar problemas, e é nessas situações que as inserções assíncronas se tornam necessárias. Esse problema é raro se você estiver enviando dados para o Coletor do ClickStack atuando como Gateway: como esses coletores atuam como agregadores, eles atenuam o problema. Consulte [Funções do coletor](#collector-roles-self-configured).

Se não for possível garantir lotes grandes, você pode delegar o agrupamento em lotes ao ClickHouse usando [inserções assíncronas](/pt-BR/concepts/best-practices/selecting-an-insert-strategy#asynchronous-inserts). Com inserções assíncronas, os dados são inseridos primeiro em um buffer e, posteriormente, gravados no armazenamento do banco de dados de forma assíncrona.

<div className="ch-image-md">
  <Frame>
    ![Inserções assíncronas](/images/use-cases/observability/observability-6.webp)
  </Frame>
</div>

Com as [inserções assíncronas habilitadas](/pt-BR/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts), quando o ClickHouse ① recebe uma consulta de inserção, os dados da consulta são ② gravados imediatamente em um buffer em memória. Quando ③ ocorre o próximo flush do buffer, os dados do buffer são [ordenados](/pt-BR/guides/clickhouse/data-modelling/sparse-primary-indexes#data-is-stored-on-disk-ordered-by-primary-key-columns) e gravados como uma parte no armazenamento do banco de dados. Observe que os dados não ficam disponíveis para consultas antes de serem gravados no armazenamento do banco de dados; o flush do buffer é [configurável](/pt-BR/concepts/features/operations/insert/asyncinserts).

Para habilitar inserções assíncronas no coletor, adicione `async_insert=1` à string de conexão. Recomendamos usar `wait_for_async_insert=1` (o padrão) para obter garantias de entrega. Consulte [este artigo](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse) para mais detalhes.

Os dados de uma inserção assíncrona são inseridos assim que ocorre o flush do buffer do ClickHouse. Isso acontece quando [`async_insert_max_data_size`](/pt-BR/reference/settings/session-settings/async-insert#async_insert_max_data_size) é excedido ou após [`async_insert_busy_timeout_ms`](/pt-BR/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms) milissegundos desde a primeira consulta INSERT. Se `async_insert_stale_timeout_ms` estiver definido com um valor diferente de zero, os dados são inseridos após `async_insert_stale_timeout_ms milliseconds` desde a última consulta. Você pode ajustar essas configurações para controlar a latência de ponta a ponta do seu pipeline. Outras configurações que podem ser usadas para ajustar o flush do buffer estão documentadas [aqui](/pt-BR/reference/settings/session-settings/async-insert#async_insert). Em geral, os valores padrão são adequados.

<Info>
  **Considere inserções assíncronas adaptativas**

  Quando há poucos agentes em uso, com baixa vazão, mas requisitos rigorosos de latência de ponta a ponta, as [inserções assíncronas adaptativas](https://clickhouse.com/blog/clickhouse-release-24-02#adaptive-asynchronous-inserts) podem ser úteis. Em geral, elas não se aplicam a casos de uso de observabilidade de alta vazão, como os observados com o ClickHouse.
</Info>

Por fim, o comportamento de deduplicação das inserções síncronas no ClickHouse não é habilitado por padrão ao usar inserções assíncronas. Se necessário, consulte a configuração [`async_insert_deduplicate`](/pt-BR/reference/settings/session-settings/async-insert#async_insert_deduplicate).

Os detalhes completos sobre como configurar essa funcionalidade estão disponíveis nesta [página da documentação](/pt-BR/concepts/features/operations/insert/asyncinserts#enabling-asynchronous-inserts) e em um [post de blog](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse) aprofundado.

## Escalonamento {#scaling-self-configured}

O coletor OTel do ClickStack atua como uma instância Gateway — consulte [Funções do coletor](#collector-roles-self-configured). Essas instâncias fornecem um serviço independente, normalmente uma por data center ou por região. Elas recebem eventos de aplicações (ou de outros coletores no papel de agente) por meio de um único endpoint OTLP. Em geral, implanta-se um conjunto de instâncias do coletor, com um balanceador de carga padrão distribuindo a carga entre elas.

<div className="ch-image-lg">
  <Frame>
    ![Escalonamento com Gateways](/images/use-cases/observability/clickstack-with-gateways.webp)
  </Frame>
</div>

O objetivo dessa arquitetura é retirar dos agentes o processamento computacionalmente intensivo, minimizando assim o uso de recursos por eles. Esses gateways do ClickStack podem executar tarefas de transformação que, de outra forma, precisariam ser realizadas pelos agentes. Além disso, ao agregar eventos de muitos agentes, os gateways garantem o envio de lotes grandes ao ClickHouse, o que torna a inserção mais eficiente. Esses coletores gateway podem ser escalonados facilmente à medida que mais agentes e fontes de dados de SDK são adicionados e a vazão de eventos aumenta.

### Adicionando o Kafka {#adding-kafka-self-configured}

Você pode ter notado que as arquiteturas acima não usam o Kafka como fila de mensagens.

Usar uma fila Kafka como buffer de mensagens é um padrão de design comum em arquiteturas de logging, popularizado pela stack ELK. Essa abordagem oferece alguns benefícios: principalmente, ajuda a fornecer garantias mais fortes de entrega de mensagens e a lidar com backpressure. As mensagens são enviadas dos agentes de coleta para o Kafka e gravadas em disco. Em teoria, uma instância Kafka em cluster deve oferecer um buffer de mensagens de alta vazão, já que gravar dados linearmente em disco gera menos sobrecarga computacional do que analisar e processar uma mensagem. No Elastic, por exemplo, a tokenização e a indexação geram uma sobrecarga significativa. Ao tirar os dados dos agentes, você também reduz o risco de perder mensagens por causa da rotação de logs na origem. Por fim, o Kafka oferece alguns recursos de replay de mensagens e de replicação cross-region, que podem ser interessantes para alguns casos de uso.

No entanto, o ClickHouse consegue inserir dados com muita rapidez — milhões de linhas por segundo em hardware modesto. Backpressure por parte do ClickHouse é raro. Muitas vezes, adotar uma fila Kafka implica mais complexidade arquitetural e mais custo. Se você puder aceitar o princípio de que logs não precisam das mesmas garantias de entrega que transações bancárias e outros dados de missão crítica, recomendamos evitar a complexidade do Kafka.

Por outro lado, se você precisar de garantias de entrega rigorosas ou da capacidade de reprocessar dados (possivelmente para vários destinos), o Kafka pode ser uma adição útil à arquitetura.

<div className="ch-image-lg">
  <Frame>
    ![Adicionando o Kafka](/images/use-cases/observability/observability-8.webp)
  </Frame>
</div>

Nesse caso, os agentes OTel podem ser configurados para enviar dados ao Kafka por meio do [exportador Kafka](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/kafkaexporter/README.md). As instâncias de gateway, por sua vez, consomem as mensagens usando o [receptor Kafka](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/receiver/kafkareceiver/README.md). Para mais detalhes, consulte a documentação da Confluent e do OTel.

<Info>
  **Configuração do OTel collector**

  A distribuição do Coletor OpenTelemetry do ClickStack pode ser configurada com o Kafka usando uma [configuração personalizada do coletor](#extending-collector-config).
</Info>

## Estimativa de recursos {#estimating-resources-self-configured}

Os requisitos de recursos do OTel collector dependem da vazão de eventos, do tamanho das mensagens e da quantidade de processamento realizado. O projeto OpenTelemetry mantém [benchmarks que os usuários](https://opentelemetry.io/docs/collector/benchmarks/) podem utilizar para estimar os requisitos de recursos.

[Em nossa experiência](https://clickhouse.com/blog/building-a-logging-platform-with-clickhouse-and-saving-millions-over-datadog#architectural-overview), uma instância de gateway do ClickStack com 3 núcleos e 12GB de RAM consegue processar cerca de 60k eventos por segundo. Isso pressupõe um pipeline de processamento mínimo, responsável apenas por renomear campos, sem expressões regulares.

Para instâncias de agente responsáveis por enviar eventos a um gateway e que apenas definem o timestamp do evento, recomendamos dimensioná-las com base na quantidade prevista de logs por segundo. Os valores a seguir são aproximados e podem ser usados como ponto inicial:

| Taxa de logs | Recursos para o agente coletor |
| ------------ | ------------------------------ |
| 1k/segundo   | 0.2CPU, 0.2GiB                 |
| 5k/segundo   | 0.5 CPU, 0.5GiB                |
| 10k/segundo  | 1 CPU, 1GiB                    |

## Escolha de schema: Map vs JSON {#schema-choice-self-configured}

Por padrão, o Coletor do ClickStack cria tabelas que armazenam atributos em colunas `Map(LowCardinality(String), String)`. Esse é o schema recomendado para cargas de trabalho de observabilidade. Um schema com tipo `JSON` está disponível em Beta para avaliação em cargas de trabalho com um conjunto pequeno e estável de chaves de atributo.

Para ver a comparação completa, quando usar cada um, as variáveis de ambiente necessárias para habilitar o schema com tipo JSON e o passo a passo da migração, consulte [Map vs Tipo JSON](/pt-BR/clickstack/self-configured/ingesting-data/schema/map-vs-json).
