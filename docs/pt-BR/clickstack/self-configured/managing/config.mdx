  Esta página trata do **Self-managed ClickHouse Observability**. Para a experiência totalmente gerenciada, que é a recomendada, consulte a documentação [aqui](/pt-BR/clickstack/observability/managing/config).

Este guia aborda as configurações de fonte de dados, o coletor que você executa e a configuração do esquema de banco de dados no Self-managed ClickHouse Observability.

## Interface do usuário {#hyperdx}

### Configurações de fonte de dados {#datasource-settings}

A UI exige que o usuário defina uma fonte de dados para cada um dos tipos de dados/pilares de observabilidade:

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

Abra **Team Settings → Data → Sources** para configurar uma fonte de dados. Selecione **Configure Optional Fields** para acessar configurações adicionais, conforme destacado abaixo para logs:

<div className="ch-image-md">
  <Frame>
    ![Configurações da fonte de logs com Configure Optional Fields destacado](/images/clickstack/source-settings-optional-fields.png)
  </Frame>
</div>

Cada fonte de dados precisa de uma tabela e de mapeamentos de colunas que permitam à UI consultar seus dados. Fontes de métricas do OTel usam tabelas separadas para cada tipo de métrica; selecione as tabelas que contêm as métricas que você coleta.

Se você estiver usando o [schema padrão do OpenTelemetry (OTel)](/pt-BR/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema) distribuído com o ClickStack, essas colunas podem ser inferidas automaticamente para cada fonte de dados. Se você estiver [modificando o schema](#clickhouse) ou usando um schema personalizado, será necessário especificar e atualizar esses mapeamentos.

<Note>
  O Coletor do ClickStack cria suas tabelas padrão por meio de migrations de esquema incluídas no pacote. Esses schemas se baseiam no [exportador do ClickHouse para o OTel collector](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) e no [modelo de dados do OpenTelemetry](https://opentelemetry.io/docs/specs/otel/logs/data-model/).
</Note>

As tabelas a seguir listam as configurações de fonte de dados. Os valores inferidos dependem das colunas e tabelas existentes no seu banco de dados. Os mapeamentos opcionais habilitam os recursos correspondentes, como a correlação de traces, mas não são obrigatórios para salvar uma fonte de dados.

| `Query Settings`                 | Até dez [configurações de sessão](/pt-BR/reference/settings/session-settings) no nível de consulta, cada uma informada como nome da configuração e valor, que são adicionadas a todas as consultas executadas nesta fonte de dados.                | Não         | Não                        | –                                        |
| `Enabled`                        | Botão de alternância no topo do formulário da fonte de dados. Uma fonte de dados desabilitada é mantida, mas fica oculta nos seletores de fontes e nunca é escolhida automaticamente. Exibido apenas ao editar uma fonte de dados existente. | Não         | Não                        | Habilitado                               |
| `Correlated Trace Source`        | Fonte de traces vinculada para correlação de sessões.                                                                                                                                                                                        | Sim         | Não                        | –                                        |
| `Timestamp Column`               | Coluna ou expressão de data e hora que faz parte da sua chave primária.                                                                                                                                                                      | Sim         | Sim                        | `TimestampTime`                          |
| `Resource Attributes Expression` | Expressão para extrair metadados no nível do recurso.                                                                                                                                                                                        | Não         | Sim                        | `ResourceAttributes`                     |

#### Visões materializadas {#materialized-views-settings}

Visões materializadas podem ser registradas em fontes de dados de log e de rastreamento para que consultas de agregação elegíveis sejam respondidas a partir da visão pré-agregada, e não da tabela de origem. Para orientações sobre como criar e registrar visões, consulte [&quot;Visões materializadas&quot;](/pt-BR/clickstack/self-configured/managing/materialized-views).

Cada visão registrada é definida pelas seguintes configurações:

| Configuração             | Descrição                                                                                                                                                                                                                                                                    |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Database`               | Banco de dados ClickHouse que contém a tabela de destino da visão materializada.                                                                                                                                                                                             |
| `Table`                  | Tabela de destino da visão materializada — não a visão em si.                                                                                                                                                                                                                |
| `Timestamp Column`       | A coluna de timestamp da tabela de destino.                                                                                                                                                                                                                                  |
| `Granularity`            | O intervalo de tempo da coluna de timestamp da tabela de destino, por exemplo `1 minute`. Uma consulta só pode usar a visão se o seu próprio intervalo de tempo for igual ou maior que este.                                                                                 |
| `Minimum Date`           | Opcional. A data e hora mais antigas para as quais a visão contém dados. Se não for informada, o ClickStack assume que a visão contém dados para todas as datas presentes na tabela de origem.                                                                               |
| `Dimension Columns`      | Lista separada por vírgulas das colunas que não são pré-agregadas pela visão e que, portanto, podem ser usadas para filtragem e agrupamento.                                                                                                                                 |
| `Pre-aggregated Columns` | As colunas pré-agregadas pela visão. Cada entrada mapeia uma função de agregação (`avg`, `count`, `max`, `min`, `quantile`, `sum` ou `histogram`) e uma coluna da tabela de origem para a coluna correspondente na visão. A coluna de origem não é obrigatória para `count`. |

Ao selecionar a tabela de destino, a UI tenta inferir essas configurações a partir do schema da visão. Revise os valores inferidos e preencha os campos ausentes.

#### Visões materializadas de metadados {#metadata-materialized-views-settings}

Visões materializadas de metadados são visões materializadas que aceleram a descoberta de campos para filtros e preenchimento automático. Elas podem ser configuradas em fontes de dados de Log e de rastreamento.

| Configuração       | Descrição                                                                       |
| ------------------ | ------------------------------------------------------------------------------- |
| `Key Rollup Table` | Opcional e obsoleta. Tabela de rollup das chaves presentes na tabela de origem. |
| `KV Rollup Table`  | Tabela de rollup dos pares chave/valor presentes na tabela de origem.           |
| `Granularity`      | O intervalo de tempo usado pelas tabelas de rollup, por exemplo, `15 minute`.   |

#### Atributos Destacados {#highlighted-attributes}

Atributos Destacados e Atributos de Rastreamento Destacados podem ser configurados em fontes de dados de log e de rastreamento.

### Fontes correlacionadas {#correlated-sources}

Para habilitar a correlação completa entre fontes de dados, você deve configurar fontes correlacionadas para logs, rastros, métricas e sessões. Isso permite que a UI associe dados relacionados e ofereça um contexto rico ao renderizar eventos.

* `Logs`: podem ser correlacionados com rastros e métricas.
* `Traces`: podem ser correlacionados com logs, sessões e métricas.
* `Metrics`: podem ser correlacionadas com logs.
* `Sessions`: podem ser correlacionadas com rastros.

Definir essas correlações habilita diversas funcionalidades. Por exemplo, a UI pode exibir logs relevantes junto a um rastro e permitir a navegação entre fontes de dados relacionadas. A correlação também depende dos mapeamentos adequados de ID e de atributos; selecionar uma fonte de dados, por si só, não cria esses relacionamentos.

## Coletor OpenTelemetry {#otel-collector}

Consulte [&quot;Coletor OpenTelemetry do ClickStack&quot;](/pt-BR/clickstack/self-configured/ingesting-data/collector) para mais detalhes.

* `CLICKHOUSE_ENDPOINT`
  * **Padrão:** *None (obrigatório)* para a imagem do coletor independente.
  * **Descrição:** URL de conexão com o ClickHouse usada pelo exportador.
  * **Orientação:**
    * Use um endpoint seguro do ClickHouse Cloud, como `https://<host>:8443` ou `tcp://<host>:9440?secure=true`
    * Obrigatório para que o coletor envie dados ao ClickHouse

* `CLICKHOUSE_USER`
  * **Padrão:** `default` na ferramenta de migração; defina explicitamente para o coletor independente.
  * **Descrição:** Nome de usuário usado para autenticar na instância do ClickHouse.
  * **Orientação:**
    * O usuário precisa de permissão para inserir dados de telemetria e, quando a criação de schema ou as migrations estiverem habilitadas, para criar ou alterar os objetos de banco de dados necessários
    * Recomenda-se criar um usuário dedicado para a ingestão

* `CLICKHOUSE_PASSWORD`
  * **Padrão:** *None (obrigatório se a autenticação estiver habilitada)*
  * **Descrição:** Senha do usuário do ClickHouse especificado.
  * **Orientação:**
    * Obrigatório se a conta de usuário tiver uma senha definida
    * Em implantações de produção, armazene-a com segurança usando secrets

* `HYPERDX_LOG_LEVEL`
  * **Padrão:** Varia conforme a implantação; defina explicitamente, por exemplo, `info`.
  * **Descrição:** Nível de verbosidade dos logs do coletor.
  * **Orientação:**
    * Aceita valores como `debug`, `info`, `warn` e `error`
    * Use `debug` durante a solução de problemas

* `OTLP_AUTH_TOKEN`
  * **Padrão:** *None*. Usado apenas na imagem independente.
  * **Descrição:** Define o token exigido para a ingestão OTLP independente. O coletor atual aceita o valor no cabeçalho `Authorization`, seja diretamente ou com o prefixo `Bearer`. Versões mais antigas do coletor podem exigir apenas o token, sem prefixo. Ignorado quando a autenticação OIDC está configurada.
  * **Orientação:**
    * Configure a autenticação antes de expor o coletor. Sem um token ou uma configuração OIDC, o receptor OTLP independente aceita requisições não autenticadas.

* `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`
  * **Padrão:** `default` na ferramenta de migração; defina explicitamente para o coletor independente.
  * **Descrição:** Banco de dados ClickHouse no qual o coletor grava os dados de telemetria.
  * **Orientação:**
    * Defina-a se estiver usando um nome de banco de dados personalizado
    * Verifique se o usuário especificado tem acesso a esse banco de dados

## ClickHouse {#clickhouse}

Para ajustar o ClickHouse de forma eficaz, é importante entender conceitos-chave de armazenamento, como [partes](/pt-BR/concepts/core-concepts/parts), [partições](/pt-BR/concepts/core-concepts/partitions), [shards e réplicas](/pt-BR/guides/oss/deployment-and-scaling/shards), e como as [mesclagens](/pt-BR/concepts/core-concepts/merges) ocorrem no momento da inserção. Recomendamos revisar os fundamentos de [índices primários](/pt-BR/concepts/core-concepts/primary-indexes), [índices secundários esparsos](/pt-BR/concepts/features/performance/skip-indexes/skipping-indexes) e índices de salto de dados, além de técnicas para [gerenciar o ciclo de vida dos dados](/pt-BR/guides/use-cases/observability/build-your-own/managing-data), por exemplo, usando um ciclo de vida baseado em TTL.

Você pode recorrer à [personalização do schema](/pt-BR/guides/use-cases/observability/build-your-own/schema-design): é possível modificar tipos de coluna, extrair novos campos (por exemplo, de logs), aplicar codecs e dicionários e acelerar consultas com projeções.

Além disso, é possível usar visões materializadas para [transformar ou filtrar dados durante a ingestão](/pt-BR/guides/use-cases/observability/build-your-own/schema-design#materialized-views), desde que os dados sejam gravados na tabela de origem da visão e a aplicação leia da tabela de destino. As visões materializadas também podem ser usadas para [acelerar consultas nativamente](/pt-BR/clickstack/self-configured/managing/materialized-views) no serviço.

Para mais detalhes, consulte a documentação do ClickHouse sobre design de schema, estratégias de indexação e boas práticas de gerenciamento de dados, a maior parte das quais se aplica diretamente a implantações autogerenciadas.
