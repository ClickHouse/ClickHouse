## Retenção de dados com TTL {#ttl-clickstack}

O Time-to-Live (TTL) é um recurso crucial no Self-managed ClickHouse Observability para a retenção e o gerenciamento eficientes de dados, especialmente considerando que grandes volumes de dados são gerados continuamente. O TTL permite a expiração e a exclusão automáticas de dados mais antigos, garantindo que o armazenamento seja utilizado de forma ideal e que o desempenho seja mantido sem intervenção manual. Esse recurso é essencial para manter o banco de dados enxuto, reduzir os custos de armazenamento e garantir que as consultas continuem rápidas e eficientes, concentrando-se nos dados mais relevantes e recentes. Além disso, ele ajuda no cumprimento de políticas de retenção de dados ao gerenciar sistematicamente o ciclo de vida dos dados, aumentando a sustentabilidade e a escalabilidade da solução de observabilidade como um todo.

**Por padrão, os dados são retidos por 30 dias. Para alterar esse período, consulte [&quot;Como modificar o TTL&quot;](#modifying-ttl).**

No ClickHouse, o TTL é controlado no nível da tabela. Por exemplo, o schema padrão para logs é mostrado abaixo; `${TABLES_TTL}` é substituído pela retenção configurada (30 dias, salvo alteração) quando o coletor cria a tabela:

O particionamento no ClickHouse permite que os dados sejam separados logicamente em disco de acordo com uma coluna ou expressão SQL. Com essa separação lógica, cada partição pode ser manipulada de forma independente — por exemplo, excluída quando expirar de acordo com uma política de TTL.

Como mostrado no exemplo acima, o particionamento é especificado em uma tabela no momento de sua definição inicial, por meio da cláusula `PARTITION BY`. Essa cláusula pode conter uma expressão SQL sobre uma ou mais colunas, cujo resultado define para qual partição cada linha será enviada. Assim, os dados ficam associados logicamente (por meio de um prefixo comum de nome de pasta) a cada partição no disco, que pode então ser consultada isoladamente. No exemplo acima, o schema padrão `otel_logs` particiona por dia usando a expressão `toDate(Timestamp)`. À medida que as linhas são inseridas no ClickHouse, essa expressão é avaliada para cada linha, que é encaminhada para a partição resultante, caso ela exista (se a linha for a primeira de um dia, a partição será criada). Para mais detalhes sobre particionamento e suas outras aplicações, consulte [&quot;Partições de tabela&quot;](/pt-BR/concepts/core-concepts/partitions).

O esquema da tabela também inclui `TTL toDateTime(Timestamp) + ${TABLES_TTL}` e a configuração `ttl_only_drop_parts = 1`. A primeira cláusula garante que os dados sejam removidos assim que ultrapassarem o TTL configurado (30 dias por padrão). A configuração `ttl_only_drop_parts = 1` faz com que só expirem as partes de dados em que todos os dados já expiraram (em vez de tentar excluir linhas parcialmente). Como o particionamento garante que dados de dias diferentes nunca sejam &quot;mesclados&quot;, os dados podem ser removidos de forma eficiente.

<Warning>
  **`ttl_only_drop_parts`**

  Recomendamos usar sempre a configuração [`ttl_only_drop_parts=1`](/pt-BR/reference/settings/merge-tree-settings/other#ttl_only_drop_parts). Quando essa configuração está habilitada, o ClickHouse remove uma parte inteira quando todas as suas linhas estão expiradas. Remover partes inteiras, em vez de limpar parcialmente as linhas com TTL expirado (o que é feito por meio de mutações que consomem muitos recursos quando `ttl_only_drop_parts=0`), permite usar valores menores de `merge_with_ttl_timeout` e reduz o impacto no desempenho do sistema. Se os dados forem particionados pela mesma unidade usada na expiração do TTL (por exemplo, dia), as partes conterão naturalmente apenas dados do intervalo definido. Isso garante que `ttl_only_drop_parts=1` possa ser aplicado de forma eficiente.
</Warning>

Por padrão, os dados com TTL expirado são removidos quando o ClickHouse [mescla partes de dados](/pt-BR/reference/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage). Quando o ClickHouse detecta que há dados expirados, ele executa uma mesclagem fora do agendamento.

<Info>
  **Agendamento do TTL**

  Os TTLs não são aplicados imediatamente, e sim conforme um agendamento, como mencionado acima. A configuração de tabela MergeTree `merge_with_ttl_timeout` define o intervalo mínimo, em segundos, antes de repetir uma mesclagem com TTL de exclusão. O valor padrão é 14400 segundos (4 horas). No entanto, esse é apenas o intervalo mínimo; pode demorar mais até que uma mesclagem de TTL seja acionada. Se o valor for muito baixo, serão executadas muitas mesclagens fora do agendamento, o que pode consumir muitos recursos. É possível forçar a expiração do TTL com o comando `ALTER TABLE my_table MATERIALIZE TTL`.
</Info>

## Como modificar o TTL {#modifying-ttl}

Para modificar o TTL, você pode:

1. **Modificar os esquemas das tabelas (recomendado)**. Para isso, é necessário conectar-se à instância do ClickHouse, por exemplo, usando o [clickhouse-client](/pt-BR/concepts/features/interfaces/client) ou o [Console SQL do Cloud](/pt-BR/products/cloud/features/sql-console-features/sql-console). Por exemplo, podemos modificar o TTL da tabela `otel_logs` com a seguinte instrução DDL:

```sql
ALTER TABLE default.otel_logs
MODIFY TTL TimestampTime + toIntervalDay(7);
```

2. **Modifique o OTel collector**. O Coletor OpenTelemetry do ClickStack cria as tabelas no ClickHouse caso elas não existam. Isso é feito por meio do exportador do ClickHouse, que expõe um parâmetro `ttl` para controlar a expressão TTL padrão, por exemplo:

```yaml
exporters:
 clickhouse:
   endpoint: tcp://localhost:9000?dial_timeout=10s&compress=lz4&async_insert=1
   ttl: 72h
```

### TTL em nível de coluna {#column-level-ttl}

Os exemplos acima expiram dados em nível de tabela. Também é possível expirar dados em nível de coluna. À medida que os dados envelhecem, isso pode ser usado para remover colunas cujo valor nas investigações não justifica a sobrecarga de recursos necessária para mantê-las. Por exemplo, recomendamos manter a coluna `Body` caso sejam adicionados novos metadados dinâmicos que não tenham sido extraídos no momento da inserção, como um novo rótulo do Kubernetes. Após um período, por exemplo, 1 mês, pode ficar evidente que esses metadados adicionais não são úteis, o que reduz o valor de manter a coluna `Body`.

A seguir, mostramos como a coluna `Body` pode ser removida após 30 dias.

```sql
CREATE TABLE otel_logs_v2
(
        `Body` String TTL Timestamp + INTERVAL 30 DAY,
        `Timestamp` DateTime,
 ...
)
ENGINE = MergeTree
ORDER BY (ServiceName, Timestamp)
```

<Note>
  Para especificar um TTL em nível de coluna, os usuários precisam definir seu próprio schema. Isso não pode ser feito no OTel collector.
</Note>
