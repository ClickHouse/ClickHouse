Ao usar o Self-managed ClickHouse Observability em produção, considere as seguintes práticas de segurança, estabilidade e configuração.

O [Self-managed ClickHouse Observability](/pt-BR/clickstack/self-configured/getting-started/managed) aplica, por padrão, [práticas de segurança](/pt-BR/products/cloud/features/security) padrão do setor — incluindo criptografia aprimorada, autenticação e conectividade, além de controles de acesso gerenciados — e ainda oferece os seguintes benefícios:

* Escalonamento automático da capacidade computacional, independente do armazenamento
* Retenção de baixo custo e praticamente ilimitada, baseada em armazenamento de objetos
* A capacidade de [isolar de forma independente as cargas de trabalho de leitura e gravação](/pt-BR/clickstack/self-configured/managing/isolating-read-write) com Warehouses.
* Autenticação integrada
* [Backups](/pt-BR/products/cloud/features/backups/overview) automatizados
* Upgrades sem interrupções

**Siga estas [boas práticas](/pt-BR/products/cloud/guides/production-readiness) do ClickHouse Cloud ao usar o Self-managed ClickHouse Observability.**

## Proteção da ingestão {#secure-ingestion-managed}

Por padrão, o Coletor OpenTelemetry do ClickStack não é protegido quando implantado fora das distribuições Open Source e não exige autenticação em suas portas OTLP.

Para proteger a ingestão, especifique um token de autenticação por meio da variável de ambiente `OTLP_AUTH_TOKEN` ao implantar o coletor. Consulte [&quot;Protegendo o coletor&quot;](/pt-BR/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured) para mais detalhes.

### Criar um usuário de ingestão {#create-a-database-ingestion-user-managed}

Recomenda-se criar um usuário dedicado ao OTel collector para a ingestão no ClickHouse Cloud, garantindo que os dados sejam enviados para um banco de dados específico, por exemplo, `otel`. Consulte [&quot;Criando um usuário de ingestão&quot;](/pt-BR/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) para mais detalhes.

## Configure o Time To Live (TTL) {#configure-ttl-managed}

Certifique-se de que o [Time To Live (TTL)](/pt-BR/clickstack/self-configured/managing/ttl) foi [configurado adequadamente](/pt-BR/clickstack/self-configured/managing/ttl#modifying-ttl) para sua implantação do Self-managed ClickHouse Observability. Ele determina por quanto tempo os dados são retidos; o padrão de 30 dias pode precisar de ajustes.

### Isolamento de cargas de trabalho de observabilidade {#isolating-workloads}

Se você estiver adicionando o Self-managed ClickHouse Observability a um **Serviço do ClickHouse Cloud existente** que já atende a outras cargas de trabalho, como analytics de aplicações em real-time, recomendamos fortemente isolar o tráfego de observabilidade.

Use [**Managed Warehouses**](/pt-BR/products/cloud/features/infrastructure/warehouses) para criar um **serviço filho** dedicado à observabilidade. Isso permite:

* Isolar a carga de ingestão e de consultas das aplicações existentes
* Escalar as cargas de trabalho de observabilidade de forma independente
* Evitar que consultas de observabilidade impactem o analytics de produção
* Compartilhar os mesmos conjuntos de dados subjacentes entre serviços, quando necessário

Essa abordagem garante que suas cargas de trabalho existentes não sejam afetadas e, ao mesmo tempo, permite que as cargas de trabalho de observabilidade escalem de forma independente à medida que o volume de dados de observabilidade cresce.

### Isolando cargas de trabalho de leitura e gravação {#isolating-read-write}

Os warehouses também permitem separar as cargas de trabalho de ingestão e de consulta em capacidade computacional dedicada, com a ingestão direcionada a um serviço de leitura e escrita e a UI de observabilidade sendo executada em um serviço somente leitura. Essa é a topologia de produção recomendada para implantações maiores. Consulte [&quot;Isolando cargas de trabalho de leitura e gravação&quot;](/pt-BR/clickstack/self-configured/managing/isolating-read-write).

Para implantações maiores ou orientações de dimensionamento personalizado, entre em contato com o suporte para obter uma estimativa mais precisa.

## Permissões do usuário de consulta {#user-permissions}

Um usuário do ClickHouse utilizado por um cliente de consulta externo deve ter `readonly = 2`. A UI define suas próprias configurações, como `date_time_output_format`, em todas as consultas, e os gráficos de SQL bruto também definem `readonly = 2`; portanto, com um usuário `readonly = 1`, essas consultas falham com o erro `Cannot modify '...' setting in readonly mode`. Com `readonly = 2`, a UI também pode definir `max_rows_to_read`, `read_overflow_mode` e `cancel_http_readonly_queries_on_client_close`; se você restringir `max_rows_to_read`, permita no mínimo 1 milhão. `wait_end_of_query` é um parâmetro da interface HTTP, e não uma configuração, portanto não exige concessão.

Por exemplo:

```sql
CREATE USER clickstack_ui IDENTIFIED BY '<password>' SETTINGS readonly = 2;
GRANT SELECT ON default.* TO clickstack_ui;
```

Por padrão, o usuário `default` no ClickHouse Cloud já tem essas permissões, mas recomendamos criar um usuário dedicado.
