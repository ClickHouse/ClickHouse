O coletor é executado como um **gateway**: um único endpoint OTLP para o qual suas aplicações, SDKs e coletores agentes enviam dados. O gateway agrupa os eventos em lotes, aplica o processamento que você tiver configurado e os grava no ClickHouse por meio do [exportador do ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter). Esse padrão mantém a lógica de coleta fora do código da aplicação e permite escalar a ingestão independentemente das cargas de trabalho que geram os dados. Para mais informações sobre os papéis de gateway e de agente, consulte [Funções do coletor](/pt-BR/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured).

<Info>
  **Coletor existente**

  Se você estiver usando um coletor OpenTelemetry existente, presumimos que ele já esteja configurado no papel de **gateway**. Não recomendamos usar este processo para reconfigurar coletores no papel de **agente**.
</Info>

      <Step title="Implantar o coletor" id="deploy-the-collector">
        Implante a **distribuição ClickStack do coletor OpenTelemetry**, que vem pré-configurada para o Self-managed ClickHouse Observability. No exemplo abaixo, para simplificar, executamos o coletor localmente e geramos telemetria artificial na mesma máquina.

        <Note>
          Em produção, o coletor normalmente é implantado em um cluster do Kubernetes ou em uma máquina virtual acessível pelos seus SDKs do OpenTelemetry, agentes e outros coletores. Isso permite que a telemetria de todo o seu ambiente seja coletada de forma centralizada e encaminhada ao ClickStack.
        </Note>

        Escolha um segredo compartilhado para autenticar os clientes que enviam dados ao coletor e, em seguida, exporte-o junto com seus detalhes de conexão e a senha escolhida para o usuário `hyperdx_ingest`:

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        Execute o coletor OTel do ClickStack:

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        O coletor agora expõe OTLP gRPC na porta `4317` e OTLP HTTP na porta `4318`. Aplicações, SDKs e coletores agentes devem enviar dados para essas portas incluindo `authorization: $OTLP_AUTH_TOKEN` no cabeçalho da requisição.

        <Info>
          **Implantações em produção**

          Em produção, recomendamos habilitar TLS no endpoint OTLP. Consulte [Protegendo o coletor](/pt-BR/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        </Info>
      </Step>

      <Step title="Verifique o endpoint" id="verify-the-endpoint">
        Gere um pouco de tráfego sintético para o coletor e confirme que o pipeline completo está funcionando. Usamos o [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen), o gerador do OpenTelemetry Collector Contrib, que emite logs, rastros e métricas OTLP e oferece flags para distribuir os dados entre serviços, níveis de severidade, status de span e tipos de métrica.

        Execute-o a partir da imagem Docker (não é necessário instalar nada). Defina um pequeno wrapper para manter os comandos abaixo legíveis; `--add-host` permite que o contêiner acesse um coletor que esteja escutando no host:

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        Ou, em vez disso, instale o binary com Go e aponte para `localhost`:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```

        <Info>
          **O que esperar**

          Cada execução do `tg` dura cerca de 20 segundos (definido por `--duration 20s`) e exibe logs detalhados durante todo esse tempo, o que é normal; cada execução termina sozinha ao fim dos seus 20 segundos. Os logs abaixo bastam para confirmar o pipeline; o conjunto opcional mais completo adiciona várias outras execuções e leva alguns minutos.
        </Info>

        Defina um pequeno helper `tg` para que cada comando especifique apenas o que varia (serviço, severidade, status, atributos):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        Envie logs com uma combinação realista de severidades entre os serviços, em sua maioria informativos, com um aviso e um erro, em vez de um fluxo uniforme composto só de erros:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        Apenas os logs já confirmam que o endpoint está funcionando. Para ter um conjunto de dados de demonstração mais completo, um mapa de serviços com vários serviços e gráficos com diferentes tipos de métrica, expanda e execute também os comandos abaixo. Eles reutilizam o helper `tg`, portanto execute-os no mesmo shell.

        <Accordion title="Gere dados de telemetria mais detalhados (opcional)">
          Envie rastros com vários spans de diversos serviços saudáveis, além de uma dependência com falha. Isso dá ao mapa de serviços um formato realista, com a maioria dos serviços saudáveis e um serviço apresentando erros, e ainda preenche as visualizações de erros:

          ```shell
          # Healthy services: the bulk of the traffic, all spans Ok
          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          Envie métricas dos três tipos mais comuns, para que os gráficos tenham um contador, um gauge e uma distribuição:

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          Para ter ainda mais variedade, adicione mais alguns serviços e um histograma exponencial:

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        Para ver o conjunto completo de flags e outras variações, consulte [Dados sintéticos com telemetrygen](/pt-BR/clickstack/observability/example-datasets/telemetrygen#self-managed).
      </Step>

      <Step title="Adapte a configuração do seu coletor" id="adapt-collector">
        Estenda a configuração existente do seu coletor para gravar no Self-managed ClickHouse Observability por meio do [exportador do ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

        <Info>
          **Exportador do ClickHouse obrigatório**

          Se você estiver usando sua própria distribuição, verifique se ela inclui o exportador do ClickHouse. A [imagem contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) upstream já o inclui.
        </Info>

        Veja abaixo um exemplo de configuração que usa o exportador do ClickHouse com os receptores, processadores e pipelines esperados pela Interface do ClickStack. Ela reproduz o comportamento da distribuição do ClickStack, incluindo o caminho de roteamento da reprodução de sessão (`rrweb`). Substitua `<clickhouse_cloud_endpoint>` e `<your_password_here>` pelas credenciais do usuário `hyperdx_ingest` criado anteriormente:

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        Alguns pontos a observar:

        * O receptor `otlp/hyperdx` escuta tanto em gRPC (`4317`) quanto em HTTP (`4318`); aplicações e agentes devem apontar para essas portas no host do seu coletor.
        * O exportador `clickhouse` grava logs, rastros e métricas no banco de dados `otel`, seguindo o layout esperado pela Interface do ClickStack. O exportador `clickhouse/rrweb` processa os eventos de reprodução de sessão roteados pelo connector `routing/logs` para `otel.hyperdx_sessions`.
        * A autenticação nos receptores OTLP fica a cargo da sua configuração atual. Configure-a por meio de [extensões](https://opentelemetry.io/docs/collector/configuration/#extensions) do coletor (por exemplo, `bearertokenauth`) ou de um proxy reverso com TLS posicionado à frente, caso precise exigir um token de ingestão.

        Recarregue o coletor com a nova configuração. Em seguida, aplicações, SDKs e coletores agentes devem enviar dados para os endpoints OTLP expostos pelo seu coletor, usando o cabeçalho de autenticação esperado pela sua configuração.

        Para mais detalhes sobre como configurar Coletores OpenTelemetry com o Self-managed ClickHouse Observability, consulte [Ingestão com OpenTelemetry](/pt-BR/clickstack/observability/ingesting-data/opentelemetry#self-managed).
      </Step>

      <Step title="Verifique o endpoint" id="verify-the-endpoint-existing">
        Gere um pouco de tráfego sintético para o seu coletor a fim de confirmar que todo o pipeline está funcionando. Usamos o [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen), o gerador do OpenTelemetry Collector Contrib, que emite logs, rastros e métricas OTLP e oferece flags para distribuir os dados entre serviços, níveis de severidade, status de span e tipos de métrica.

        Execute-o a partir da imagem Docker (não é necessário instalar nada). Substitua `<your-collector-host>` pelo host em que o seu coletor está escutando e defina o cabeçalho `authorization` (ou outro método de autenticação) com o valor esperado pelo seu coletor:

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=<your-collector-host>:4317
        export OTLP_AUTH_TOKEN=<your-auth-token>
        ```

        Ou instale o binário usando Go:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        ```

        <Info>
          **O que esperar**

          Cada execução do `tg` dura cerca de 20 segundos (definido por `--duration 20s`) e exibe logs detalhados durante todo esse tempo, o que é esperado; cada execução termina sozinha quando seus 20 segundos se esgotam. Os logs abaixo bastam para validar o pipeline; o conjunto opcional mais completo inclui várias outras execuções e leva alguns minutos.
        </Info>

        Defina um pequeno helper `tg` para que cada comando especifique apenas o que varia (serviço, severidade, status, atributos):

        ```shell

          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        Envie logs com uma combinação realista de níveis de severidade entre os serviços, majoritariamente informativos, com um aviso e um erro, em vez de um fluxo uniforme composto apenas por erros:

        ```shell

          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        Só os logs já confirmam que o endpoint está funcionando. Para ter um conjunto de dados de demonstração mais completo, com um mapa de serviços envolvendo vários serviços e gráficos de diferentes tipos de métrica, expanda e execute também os comandos abaixo. Eles reutilizam o helper `tg`, portanto execute-os no mesmo shell.

## Próximos passos: envie seus próprios dados {#next-steps}

O burst sintético acima serve apenas para comprovar que o pipeline funciona. Para começar a enviar telemetria real, instrumente seus próprios serviços com os [SDKs do ClickStack](/pt-BR/clickstack/observability/ingesting-data/sdks), que oferecem instrumentação para Node.js, Python, Go, Java e outras linguagens e exportam OTLP para o endpoint do coletor que você acabou de verificar. Para ver um exemplo completo, siga o guia [Instrumentar uma aplicação](/pt-BR/clickstack/self-configured/managed-onboarding/instrument-application).

Para coletar dados da infraestrutura, e não do código da aplicação:

* [Monitoramento do Kubernetes](/pt-BR/clickstack/self-configured/managed-onboarding/monitoring-kubernetes): colete logs, métricas de infraestrutura e eventos do Kubernetes de um cluster.
* [Monitoramento de logs do AWS CloudWatch](/pt-BR/clickstack/self-configured/managed-onboarding/monitoring-aws-cloudwatch-logs): encaminhe logs do CloudWatch por meio do receptor do CloudWatch do OpenTelemetry.
