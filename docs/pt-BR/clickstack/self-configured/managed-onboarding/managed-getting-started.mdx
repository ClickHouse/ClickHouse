<Note>
  Esta página aborda o **Self-managed ClickHouse Observability**. Para a experiência totalmente gerenciada, que é a recomendada, consulte a documentação [aqui](/pt-BR/clickstack/observability/getting-started).
</Note>

Este guia leva você de um serviço Self-managed ClickHouse Observability vazio até ter logs, métricas, rastros e reproduções de sessão chegando de uma aplicação real. Você vai implantar um novo coletor OpenTelemetry (ou adaptar um já existente, se tiver) apontando para o seu serviço, instrumentar uma aplicação Node.js de exemplo sem nenhuma alteração na regra de negócio e, em seguida, explorar a telemetria na Interface do ClickStack.

<Note>
  Seja configurando um novo coletor ou usando o seu próprio, ele deve ser executado como **gateway**: um único endpoint OTLP para o qual suas aplicações, SDKs e coletores agentes enviam dados. O gateway agrupa os eventos em lotes, aplica o processamento que você tiver configurado e os grava no ClickHouse por meio do [exportador do ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).
</Note>

A aplicação que vamos instrumentar é o [HackerNews Analyzer](https://github.com/ClickHouse/hn-news-analyzer), um app Node.js que consulta o dataset do HackerNews hospedado na demonstração pública do ClickHouse. Cada gráfico, tabela e caixa de busca é alimentado por uma consulta real do ClickHouse, de modo que cada interação gera um trace cujo span principal é a chamada HTTPS do backend para o ClickHouse.

## Pré-requisitos {#prerequisites}

* Um **serviço Self-managed ClickHouse Observability** no [ClickHouse Cloud](https://console.clickhouse.cloud).
* **Node 18+ e npm** para executar a aplicação de exemplo.
* **Docker**, caso você ainda não tenha um coletor e queira seguir o caminho com um novo coletor descrito abaixo.

  <Step title="Implante o coletor" id="deploy-collector">
    Escolha a opção que melhor se aplica à sua situação.

    <Info>
      **Coletor existente**

      Se você estiver usando um Coletor OpenTelemetry já existente, partimos do pressuposto de que ele já está configurado na função de **gateway**. Não recomendamos usar este procedimento para reconfigurar coletores na função de **agente**.
    </Info>

    <Tabs>
      <Tab title="Não tenho um coletor">
        Implante a **distribuição ClickStack do coletor OpenTelemetry**, que já vem pré-configurada para o Self-managed ClickHouse Observability. No exemplo abaixo, executamos o coletor localmente para simplificar.

        <Note>
          Em produção, o coletor normalmente é implantado em um cluster do Kubernetes ou em uma máquina virtual acessível pelos seus SDKs do OpenTelemetry, agentes e outros coletores. Isso permite que a telemetria de todo o seu ambiente seja coletada de forma centralizada e encaminhada ao ClickStack.
        </Note>

        Escolha um segredo compartilhado para autenticar os clientes que enviam dados ao coletor e, em seguida, exporte-o junto com seus detalhes de conexão e a senha escolhida para o usuário `hyperdx_ingest`:

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        Execute o coletor OTel do ClickStack:

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        O coletor agora expõe OTLP gRPC na porta `4317` e OTLP HTTP na porta `4318`. Aplicações, SDKs e coletores agentes devem enviar dados para essas portas incluindo `authorization: $OTLP_AUTH_TOKEN` nos cabeçalhos da requisição. Mantenha à mão o endpoint OTLP e o `OTLP_AUTH_TOKEN`, pois você apontará a aplicação para eles nas próximas etapas.

        <Info>
          **Implantações em produção**

          Em produção, recomendamos habilitar TLS no endpoint OTLP. Consulte [Protegendo o coletor](/pt-BR/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        </Info>
      </Tab>

      <Tab title="Tenho um coletor">
        Amplie a configuração do coletor que você já usa para gravar no Self-managed ClickHouse Observability por meio do [exportador do ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

        <Info>
          **Exportador do ClickHouse obrigatório**

          Se você estiver usando sua própria distribuição, verifique se ela inclui o exportador do ClickHouse. A [imagem contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) upstream já o inclui.
        </Info>

        Veja abaixo um exemplo de configuração que usa o exportador do ClickHouse com os receptores, processadores e pipelines esperados pela interface do ClickStack. Ela reproduz o comportamento da distribuição do ClickStack, incluindo o caminho de roteamento da reprodução de sessão (`rrweb`). Substitua `<clickhouse_cloud_endpoint>` e `<your_password_here>` pelas credenciais do usuário `hyperdx_ingest` criado anteriormente:

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        Alguns pontos a observar:

        * O receptor `otlp/hyperdx` escuta tanto em gRPC (`4317`) quanto em HTTP (`4318`); aplicações e agentes devem apontar para essas portas no host do seu coletor.
        * O exportador `clickhouse` grava logs, rastros e métricas no banco de dados `otel`, seguindo o layout esperado pela Interface do ClickStack. O exportador `clickhouse/rrweb` processa os eventos de reprodução de sessão (Session Replay) roteados pelo connector `routing/logs` para `otel.hyperdx_sessions`.
        * A autenticação nos receptores OTLP fica a cargo da sua configuração atual. Configure-a por meio de [extensões](https://opentelemetry.io/docs/collector/configuration/#extensions) do coletor (por exemplo, `bearertokenauth`) ou de um proxy reverso com TLS, caso precise exigir um token de ingestão.

        Recarregue o coletor com a nova configuração. Tenha em mãos o endpoint OTLP e o cabeçalho de autenticação exigido pela sua configuração, pois você vai apontar a aplicação para eles nas próximas etapas.

        Para mais detalhes sobre como configurar Coletores OpenTelemetry para o Self-managed ClickHouse Observability, consulte [Ingestão com OpenTelemetry](/pt-BR/clickstack/observability/ingesting-data/opentelemetry#self-managed).
      </Tab>
    </Tabs>
  </Step>

  <Step title="Clone e execute a aplicação" id="clone-and-run-the-application">
    Clone o repositório, instale as dependências e crie o seu arquivo `.env`:

    ```bash
    git clone https://github.com/ClickHouse/hn-news-analyzer.git
    cd hn-news-analyzer
    npm install
    cp .env.example .env
    ```

    A fonte de dados do ClickHouse usa por padrão o cluster de demonstração público read-only, então a aplicação funciona sem nenhuma configuração adicional. Para iniciá-la:

    ```bash
    ./run.sh
    ```

    Abra [http://localhost:5001](http://localhost:5001). Você verá um seletor de ano, estatísticas resumidas, um gráfico de atividade, tabelas com os principais usuários e domínios e uma caixa de busca. Explore à vontade: alterne entre os anos e abra as histórias para ver os detalhes.

    <div className="ch-image-lg">
      <Frame>
        ![A aplicação HackerNews Analyzer em execução localmente](/images/clickstack/getting-started/hackernews_main.webp)
      </Frame>
    </div>

    Neste momento, a aplicação está em execução, mas ainda não está instrumentada. O ClickStack não exibe nenhum dado, pois está aguardando telemetria. Este é o estado &quot;antes&quot;.
  </Step>

  <Step title="Conecte a aplicação ao seu coletor" id="connect-the-application">
    A aplicação precisa de dois valores para se conectar ao coletor que você implantou acima:

    * `OTEL_EXPORTER_OTLP_ENDPOINT`: o endpoint OTLP exposto pelo seu coletor (normalmente a porta `4318` para OTLP sobre HTTPS).
    * `OTEL_EXPORTER_OTLP_HEADERS`: o cabeçalho de autorização com o seu token de ingestão, no formato `authorization=<ingestion_token>`. Use o `OTLP_AUTH_TOKEN` que você definiu no coletor acima ou o cabeçalho de autenticação que o seu coletor existente espera receber.

    Copie `.env.example` para `.env`, abra o arquivo e defina as seguintes variáveis:

    ```bash
    OTEL_SERVICE_NAME=hn-analyzer-api
    OTEL_EXPORTER_OTLP_ENDPOINT=https://<your-collector-endpoint>:4318
    OTEL_EXPORTER_OTLP_HEADERS=authorization=<ingestion_token>
    ```

    O SDK usa `OTEL_EXPORTER_OTLP_HEADERS` para definir o cabeçalho de autorização dos três sinais: rastros, métricas e logs. Se o seu coletor for executado localmente e não exigir autenticação, você pode deixar o valor vazio (`OTEL_EXPORTER_OTLP_HEADERS=authorization=`), mas a variável precisa estar presente; se ela não estiver definida ou estiver totalmente vazia, o SDK não é inicializado. Por fim, ao executar o coletor sem TLS, certifique-se de usar o protocolo HTTP correto (por exemplo, `http://localhost:4318`).
  </Step>

  <Step title="Instrumente a aplicação" id="instrument-the-application">
    A instrumentação tem três etapas: instalar os SDKs, trocar o comando de inicialização e habilitar o SDK do navegador. Nada disso altera a regra de negócio da aplicação.

### Instale os SDKs {#install-sdks}

    Instale os SDKs do OpenTelemetry tanto para o backend quanto para o navegador:

    ```bash
    npm install @hyperdx/node-opentelemetry @hyperdx/browser
    ```

### Use a CLI opentelemetry-instrument {#use-open-telemetry-cli}

    A aplicação é iniciada pelo `run.sh`, que tem duas linhas `exec` no final: uma ativa e outra comentada. Inverta qual delas fica ativa para que o Node seja encapsulado pelo `opentelemetry-instrument`:

    ```diff
     # BEFORE: plain node, no instrumentation, collector stays silent:
    -exec node scripts/entrypoint.js
    +# exec node scripts/entrypoint.js

     # AFTER: same source, wrapped by opentelemetry-instrument CLI.
    -# exec npx opentelemetry-instrument scripts/entrypoint.js
    +exec npx opentelemetry-instrument scripts/entrypoint.js
    ```

    Essa é toda a alteração no backend. A instrumentação automática é carregada pelo `opentelemetry-instrument` na inicialização do processo.

### Habilite o SDK do navegador {#enable-browser-sdk}

    Para capturar rastros distribuídos (do navegador ao backend) e reproduções de sessão, habilite o SDK do navegador em `src/web/telemetry.ts`. Descomente o import e o bloco `HyperDX.init({...})`:

    ```javascript
    import HyperDX from '@hyperdx/browser';

    export function initTelemetry(): void {
      HyperDX.init({
        url: __OTLP_ENDPOINT__,
        apiKey: __OTLP_AUTH_TOKEN__,
        service: 'hn-analyzer-web',
        tracePropagationTargets: [/localhost:5001/i, /\/api\//i],
        consoleCapture: true,
        advancedNetworkCapture: true,
      });
    }
    ```

    Não é necessário fazer nenhuma edição adicional no `.env`. `__OTLP_ENDPOINT__` e `__OTLP_AUTH_TOKEN__` são constantes de tempo de compilação injetadas pelo `vite.config.ts`: o endpoint vem de `OTEL_EXPORTER_OTLP_ENDPOINT` e o token é extraído de `OTEL_EXPORTER_OTLP_HEADERS`, os mesmos valores usados pelo backend.

    <Warning>
      O token de ingestão fica embutido no pacote público do navegador e pode ser lido por qualquer pessoa que inspecione a aba Rede.
    </Warning>
  </Step>

  <Step title="Gerar tráfego" id="generate-traffic">
    Reinicie a aplicação para que o novo comando de inicialização e o bundle do navegador recém-gerado passem a valer:

    ```bash
    # Ctrl-C the previous run, then:
    ./run.sh
    ```

    Recarregue a aba do navegador para que o Vite sirva o bundle atualizado. Em seguida, atualize o app algumas vezes, alterne entre os anos e clique nas histórias para gerar tráfego. Cada interação envia logs, métricas, rastros e eventos de reprodução de sessão pelo seu coletor até o ClickStack.
  </Step>

    O ClickStack será aberto em uma nova aba e você deverá ser direcionado automaticamente para a página **Getting Started**. Caso contrário, selecione **Getting Started** no menu à esquerda, clique em **Start Ingestion** e, em seguida, em **Next**.

    Logs, métricas, rastros e reproduções de sessão ficam todos na mesma UI, compartilham a mesma linguagem de consulta e são correlacionados automaticamente.

    Se nada aparecer:

    * Confirme se o valor do cabeçalho de autenticação definido em `OTEL_EXPORTER_OTLP_HEADERS` corresponde ao esperado pelo seu coletor.
    * Acompanhe os logs do seu coletor e procure erros de exportação.
    * Verifique se o endpoint do ClickHouse configurado no coletor inclui tanto o protocolo quanto a porta (`https://...:8443`).
  </Step>
