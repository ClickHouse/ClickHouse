O agente de chat do Assistant pode ser personalizado para entender as regras de negócio, as estruturas de dados e o conhecimento de domínio específicos da sua empresa por meio do **AGENTS.md**, uma consulta salva especial que funciona como uma camada semântica sobre o prompt do sistema do agente.

Ao criar um arquivo AGENTS.md, você pode fornecer instruções personalizadas que são inseridas no início de cada conversa para orientar a geração de consultas SQL e a análise de dados de acordo com os requisitos, cálculos e convenções próprios da sua organização.

## Como funciona {#how-it-works}

Quando você salva uma consulta com o nome &quot;AGENTS.md&quot; (diferenciando maiúsculas de minúsculas) no Console da nuvem:

1. O agente de chat do Assistant carrega esse arquivo automaticamente sempre que uma mensagem é enviada
2. O conteúdo é inserido em uma tag de conteúdo estruturado e injetado no prompt do sistema do agente
3. As instruções são aplicadas a todas as conversas do chat do Assistant nesse serviço

## Criando o AGENTS.md {#creating-agents-md}

<Steps>
  <Step title="Crie a consulta salva" id="create-query">
    1. No Console da nuvem, crie uma nova consulta
    2. Dê a ela exatamente o nome **&quot;AGENTS.md&quot;** (diferencia maiúsculas de minúsculas)
    3. Escreva suas instruções personalizadas no editor de texto da consulta (não é SQL de verdade)
    4. Salve a consulta
  </Step>

  <Step title="Adicione suas instruções" id="add-instructions">
    Estruture suas instruções com uma linguagem clara e objetiva. Inclua:

    * Regras de negócio e cálculos
    * Orientações sobre a estrutura de dados
    * Terminologia específica do domínio
    * Padrões de consulta comuns
    * Regras de otimização de desempenho
  </Step>
</Steps>

## Boas práticas {#best-practices}

### Trate o contexto como um recurso finito {#finite-resource}

O contexto é precioso: cada token consome o &quot;orçamento de atenção&quot; do agente. Assim como os humanos, que têm memória de trabalho limitada, os modelos de linguagem perdem desempenho à medida que o contexto cresce. Por isso, o objetivo é encontrar o **menor conjunto possível de tokens de alto sinal** que maximize a probabilidade de obter o resultado desejado.

### Encontre o nível de abstração adequado {#right-altitude}

Busque um equilíbrio entre dois extremos:

* **Específico demais**: lógica if-else rígida e codificada diretamente (hard-coded), que torna o sistema frágil e difícil de manter
* **Vago demais**: orientações de alto nível que não fornecem sinais concretos ou que pressupõem, equivocadamente, um contexto compartilhado

O nível ideal é específico o suficiente para orientar o comportamento de forma eficaz, mas flexível o bastante para que o modelo aplique heurísticas sólidas. Comece com um prompt mínimo no melhor modelo disponível e, depois, adicione instruções claras com base nos modos de falha observados.

### Organize com seções estruturadas {#structured-sections}

Use tags XML ou títulos Markdown para criar seções distintas e fáceis de examinar rapidamente:

```xml
<background_information>
Context about your data and domain
</background_information>

<calculation_rules>
Specific formulas and business logic
</calculation_rules>

<tool_guidance>
How to use specific ClickHouse features
</tool_guidance>
```

### Forneça exemplos diversos e canônicos {#canonical-examples}

Os exemplos são como &quot;uma imagem que vale mais que mil palavras&quot;. Em vez de entulhar seu prompt com todos os casos extremos possíveis, selecione um conjunto enxuto de exemplos diversos que ilustrem com eficácia o comportamento esperado.

### Mantenha o conteúdo mínimo, porém completo {#minimal-complete}

* Inclua apenas as instruções usadas com frequência
* Seja conciso — um contexto maior prejudica o desempenho devido à &quot;context rot&quot; (deterioração do contexto)
* Remova regras desatualizadas ou raramente usadas
* Garanta informações suficientes para orientar o comportamento desejado

<Tip>
  Mínimo não significa necessariamente curto. É preciso haver detalhes suficientes para garantir que o agente se comporte como esperado; basta evitar verbosidade desnecessária.
</Tip>

## Exemplo: métricas calculadas a partir de dados brutos {#example-calculated-metrics}

Oriente o agente quando as métricas exigirem cálculos específicos, em vez de acesso direto às colunas:

```xml
<metric_calculations>
IMPORTANT: "active_sessions" is NOT a column. It must be calculated.

To calculate active sessions:
COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions

This counts unique combinations of session and user identifiers.

When the user asks for "active sessions" or "session count", always use this formula:
SELECT
    date,
    COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions
FROM events
GROUP BY date;

</metric_calculations>
```

## Exemplo: Regras de negócio {#example-business-logic}

Defina cálculos e categorizações específicos do domínio:

```xml
<business_rules>
Revenue Calculation:
- Exclude refunded transactions: WHERE transaction_status != 'refunded'
- Apply regional tax rates using CASE expressions
- Use MRR for subscriptions:
  SUM(CASE
    WHEN billing_cycle = 'monthly' THEN amount
    WHEN billing_cycle = 'yearly' THEN amount / 12
    ELSE 0
  END) AS mrr

Traffic Source Classification:
Use CASE expression to categorize:
CASE
  WHEN traffic_source IN ('google', 'bing', 'organic') THEN 'Organic Search'
  WHEN traffic_source IN ('facebook', 'instagram', 'social') THEN 'Social Media'
  WHEN traffic_source = 'direct' THEN 'Direct'
  ELSE 'Other'
END AS source_category

Customer Segmentation:
- Enterprise: annual_contract_value >= 100000
- Mid-Market: annual_contract_value >= 10000 AND annual_contract_value < 100000
- SMB: annual_contract_value < 10000

Always include these categorizations when generating traffic or revenue reports.
</business_rules>
```

## Exemplo: peculiaridades da estrutura de dados {#example-data-quirks}

Documente formatos de dados pouco convencionais ou decisões de schema legadas:

```xml
<data_structure_notes>
The user_status column uses numeric codes, not strings:
- 1 = 'active'
- 2 = 'inactive'
- 3 = 'suspended'
- 99 = 'deleted'

When filtering or displaying user status, always use:
CASE user_status
  WHEN 1 THEN 'active'
  WHEN 2 THEN 'inactive'
  WHEN 3 THEN 'suspended'
  WHEN 99 THEN 'deleted'
END AS status_label

The product_metadata column contains JSON strings that must be parsed:
SELECT
    product_id,
    JSONExtractString(product_metadata, 'category') AS category,
    JSONExtractInt(product_metadata, 'inventory_count') AS inventory
FROM products;
</data_structure_notes>
```

## Exemplo: terminologia de domínio {#example-terminology}

Mapeie termos de negócio para a implementação técnica correspondente:

```xml
<terminology>
When users refer to "conversions", they mean:
- For e-commerce: transactions WHERE transaction_type = 'purchase'
- For SaaS: subscriptions WHERE subscription_status = 'active' AND first_payment_date IS NOT NULL

"Churn" is calculated as:
COUNT(DISTINCT user_id) WHERE last_active_date < today() - INTERVAL 90 DAY
AND previous_subscription_status = 'active'

"DAU" (Daily Active Users) means:
COUNT(DISTINCT user_id) WHERE activity_date = today()

"Qualified leads" must meet ALL criteria:
- lead_score >= 70
- company_size >= 50
- budget_confirmed = true
- contact_role IN ('Director', 'VP', 'C-Level')
</terminology>
```
