## Descrição {#description}

[Apache Parquet](https://parquet.apache.org/) é um formato de armazenamento colunar amplamente utilizado no ecossistema Hadoop. O ClickHouse oferece suporte a operações de leitura e gravação nesse formato.

### Inteiros largos {#wide-integers}

Por padrão, o ClickHouse grava `Int128`, `UInt128`, `Int256` e `UInt256` como valores `FIXED_LEN_BYTE_ARRAY(16/32)` sem anotações, em ordem little-endian. Essa representação legada continua sendo o padrão para que os arquivos possam ser lidos por versões mais antigas do ClickHouse.

Defina `output_format_parquet_wide_integer_as_decimal = 1` para usar a representação `DECIMAL` padrão do Parquet:

| Tipo do ClickHouse | Tipo lógico do Parquet | Tipo físico                | Codificação de valor                                                                                  |
| ------------------ | ---------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------- |
| `UInt128`          | `DECIMAL(39, 0)`       | `FIXED_LEN_BYTE_ARRAY(17)` | Um byte de sinal zero seguido do valor sem sinal de 16 bytes em ordem big-endian                      |
| `UInt256`          | `DECIMAL(78, 0)`       | `FIXED_LEN_BYTE_ARRAY(33)` | Um byte de sinal zero seguido do valor sem sinal de 32 bytes em ordem big-endian                      |
| `Int128`           | `DECIMAL(39, 0)`       | `FIXED_LEN_BYTE_ARRAY(17)` | O valor de 16 bytes em complemento de dois, em ordem big-endian e com extensão de sinal para 17 bytes |
| `Int256`           | `DECIMAL(77, 0)`       | `FIXED_LEN_BYTE_ARRAY(33)` | O valor de 32 bytes em complemento de dois, em ordem big-endian e com extensão de sinal para 33 bytes |

A representação decimal fornece ordenação numérica para estatísticas padrão de fragmentos de coluna e índices de página do Parquet, permitindo que o ClickHouse use a poda por mínimo/máximo de grupos de linhas e páginas. O ClickHouse lê ambas as codificações. Para precisão decimal 39, a inferência de schema retorna `Decimal(39, 0)`, com suporte de `Decimal256`; especifique uma estrutura explícita de `Int128` ou `UInt128` para recuperar um tipo de inteiro largo. A precisão decimal 77 ou 78 excede o intervalo de `Decimal256` do ClickHouse, portanto, a leitura desses arquivos exige uma estrutura explícita compatível de `Int256` ou `UInt256`. Com uma estrutura explícita de inteiro largo, o ClickHouse aceita valores decimais padrão armazenados como `BYTE_ARRAY` ou `FIXED_LEN_BYTE_ARRAY` de qualquer largura válida e verifica o intervalo de cada valor após remover a extensão de sinal.

Alguns clientes Parquet oferecem suporte a precisão decimal apenas até 38, enquanto os tipos decimais de alto nível do Arrow oferecem suporte a precisão apenas até 76. Esses clientes podem rejeitar a representação de precisão 77/78, embora seu schema e largura física de 33 bytes estejam em conformidade com o Parquet. Mantenha a configuração desabilitada quando os arquivos precisarem ser lidos por versões mais antigas do ClickHouse ou por clientes com limites decimais menores.

Os tipos de dados das colunas de tabelas do ClickHouse podem diferir dos campos correspondentes dos dados Parquet inseridos. Ao inserir dados, o ClickHouse interpreta os tipos de dados de acordo com a tabela acima e depois [converte](/pt-BR/reference/functions/regular-functions/type-conversion-functions#CAST) os dados para o tipo de dado definido para a coluna da tabela do ClickHouse. Ex.: uma coluna Parquet `UINT_32` pode ser lida em uma coluna ClickHouse [IPv4](/pt-BR/reference/data-types/ipv4).

Para alguns tipos Parquet, não há um tipo ClickHouse com correspondência próxima. Nós os lemos da seguinte forma:

* `TIMESTAMP` com `isAdjustedToUTC=false` é um horário de relógio local (campos de ano, mês, dia, hora, minuto, segundo e fração de segundo em um timezone local, independentemente de qual fuso horário específico seja considerado local), assim como em SQL `TIMESTAMP WITHOUT TIME ZONE`. O ClickHouse o lê como se fosse um timestamp em UTC. Ex.: `2025-09-29 18:42:13.000` (representando a leitura de um relógio local) torna-se `2025-09-29 18:42:13.000` (`DateTime64(3, 'UTC')` representando um ponto no tempo). Se convertido para String, ele mostra o ano, mês, dia, hora, minuto, segundo e fração de segundo corretos, que então podem ser interpretados como pertencentes a algum timezone local em vez de UTC. Contraintuitivamente, mudar o tipo de `DateTime64(3, 'UTC')` para `DateTime64(3)` não ajudaria, pois ambos os tipos representam um ponto no tempo, e não uma leitura de relógio, mas `DateTime64(3)` seria formatado incorretamente usando o timezone local.
* `INTERVAL` no momento é lido como `FixedString(12)`, com a representação binária bruta do intervalo de tempo, conforme codificada no arquivo Parquet.

## Tipo Variant {#variant-type}

O ClickHouse lê colunas armazenadas na codificação [`VARIANT`](https://github.com/apache/parquet-format/blob/master/VariantEncoding.md) do Parquet, como as gravadas pelo Spark 4.0, no tipo [`Dynamic`](/pt-BR/reference/data-types/dynamic). Uma coluna é reconhecida como variant se for um grupo anotado com o tipo lógico `VARIANT` (versão 1 da especificação). O Spark 4.0 grava colunas variant sem essa anotação; por isso, um grupo contendo apenas um campo `metadata` e um campo `value` do tipo `BYTE_ARRAY` também é lido como variant. Esse comportamento pode ser desativado com a configuração `input_format_parquet_detect_variant_by_structure`. Nesse caso, esse grupo é lido como uma `Tuple` dos dois campos brutos, como antes. Solicitar explicitamente o tipo `Dynamic` ou `JSON` para a coluna faz com que ela seja lida como variant, independentemente da configuração.

Cada valor mantém seu próprio tipo. Os tipos primitivos de variant são lidos como os tipos do ClickHouse correspondentes (por exemplo, `int32` como `Int32`, `decimal8` como `Decimal(18, S)`, `timestamp` como `DateTime64(6, 'UTC')`, `timestamp_ntz` como `DateTime64(6)`, `binary` e `string` como `String`, `uuid` como `UUID`). O `null` de variant é lido como `NULL`, e objetos de variant são lidos como [`JSON`](/pt-BR/reference/data-types/newjson), com objetos aninhados achatados em caminhos separados por pontos (um campo `null` é tratado como ausente). Arrays de variant cujos elementos são todos objetos são lidos como `Array(JSON)`, e os demais arrays de variant são lidos como `Array(Dynamic)`. O tipo de nível superior é `Dynamic`, e não `JSON`, porque um valor variant não é necessariamente um objeto.

Uma coluna variant também pode ser lida como [`JSON`](/pt-BR/reference/data-types/newjson) se esse tipo for solicitado explicitamente, por exemplo, na estrutura da tabela ou no argumento `structure` da função de tabela `file`. Nesse caso, todo valor deve ser um objeto; caso contrário, uma exceção é lançada. Tanto um `null` de variant quanto um `null` da coluna inteira são lidos como um objeto vazio. Caminhos tipados do tipo `JSON` solicitado são convertidos para seus respectivos tipos, e os caminhos listados em `SKIP` e `SKIP REGEXP` são ignorados.

Variants fragmentados (grupos com um campo `typed_value`) ainda não são suportados: a leitura de uma coluna desse tipo lança uma exceção, mas as demais colunas do arquivo continuam podendo ser lidas, e a inferência de esquema ignora a coluna se `input_format_parquet_skip_columns_with_unsupported_types_in_schema_inference` estiver habilitada. A gravação de colunas `Dynamic` ou `JSON` no Parquet como `VARIANT` também não é suportada.

## Referências de arquivo {#file-type}

Um grupo anotado com o tipo lógico [`FILE`](https://github.com/apache/parquet-format/blob/master/LogicalTypes.md#file) do Parquet representa uma referência a um intervalo de bytes, armazenado em linha ou em um arquivo externo. Ele é lido como uma `Tuple` nomeada com os campos presentes no arquivo, todos `Nullable`: `uri`, `content_type` e `checksum` como `Nullable(String)`, `offset` e `size` como `Nullable(Int64)`, e `inline` como `Nullable(String)` com bytes brutos. Uma referência de arquivo `null` é lida como uma tupla com todos os elementos `NULL`. Como em qualquer `Tuple`, é possível ler um subconjunto dos campos solicitando uma `Tuple` com menos elementos, ou ler campos individuais como subcolunas, por exemplo, `file.uri`. O schema do grupo é validado: ele deve conter apenas esses campos, todos `OPTIONAL`, com os tipos definidos pela especificação; caso contrário, uma exceção é lançada. Já os valores não são validados: um valor que não forma uma referência válida (por exemplo, `offset` sem `uri`) é retornado tal como foi armazenado. O ClickHouse não resolve as referências, ou seja, não lê os arquivos externos.

Na escrita, uma `Tuple` desse tipo (cujos nomes de elementos formem um subconjunto não vazio dos campos de `FILE`, com `offset` e `size` inteiros e os demais elementos `String` ou `FixedString`) é gravada como um grupo anotado com `FILE` se a configuração [`output_format_parquet_write_file_logical_type`](/pt-BR/reference/settings/formats/output-format#output_format_parquet_write_file_logical_type) estiver habilitada. Caso contrário, ela é gravada como um grupo comum.

## Tipos geométricos (GeoParquet) {#geo-types}

O ClickHouse oferece suporte à leitura e à gravação de colunas de geometria de acordo com a especificação [GeoParquet](https://geoparquet.org/) e com os [tipos lógicos `GEOMETRY` e `GEOGRAPHY`](https://github.com/apache/parquet-format/blob/master/Geospatial.md) do Parquet. As colunas de geometria são armazenadas como payloads `BYTE_ARRAY` codificados em [WKB](https://libgeos.org/specifications/wkb/) (ou WKT na leitura, no caso do GeoParquet). O GeoParquet usa uma chave JSON `geo` nos metadados Parquet em nível de arquivo que descreve a codificação, o tipo de geometria e o CRS de cada coluna de geometria. Já os tipos lógicos anotam a própria coluna, e os metadados do fragmento de coluna contêm `GeospatialStatistics` (uma caixa delimitadora e a lista de tipos de geometria) em vez de estatísticas de mínimo/máximo. Um arquivo pode conter ambos.

### Comportamento de leitura {#read}

Na leitura, as colunas de geometria são mapeadas para os [tipos de dados geo](/pt-BR/reference/data-types/geo) correspondentes no ClickHouse:

* Uma coluna declarada como `Point`, `MultiPoint`, `LineString`, `Polygon`, `MultiLineString` ou `MultiPolygon` é lida como o tipo geométrico correspondente no ClickHouse.
* Uma coluna com tipos de geometria múltiplos ou desconhecidos é lida como o tipo [`Geometry`](/pt-BR/reference/data-types/geo#geometry), que é um `Variant` de todos os tipos geométricos compatíveis.
* Para uma coluna com o tipo lógico `GEOMETRY` ou `GEOGRAPHY`, o tipo de geometria é obtido dos metadados do GeoParquet, se o arquivo os tiver. Caso contrário, se as `GeospatialStatistics` de todos os fragmentos de coluna indicarem o mesmo tipo de geometria 2D único, a coluna é lida como o tipo geométrico correspondente; se não, é lida como `Geometry`. Se um tipo geométrico for solicitado explicitamente, os valores são decodificados diretamente nesse tipo.
* O ClickHouse não tem um tipo específico para geografia; por isso, as colunas `GEOGRAPHY` são lidas como os mesmos tipos geométricos que `GEOMETRY` (as coordenadas são longitude e latitude), e o algoritmo de interpolação de arestas (o parâmetro `algorithm`) não é representado. O CRS (o parâmetro `crs`, `OGC:CRS84` por padrão) também não é representado. Geometrias com coordenadas Z ou M não são suportadas.
* A ordenação dos tipos lógicos `GEOMETRY` e `GEOGRAPHY` é indefinida; por isso, as estatísticas de mín./máx. e o índice de coluna dessas colunas são ignorados. Com [`input_format_parquet_spatial_filter_push_down`](/pt-BR/reference/settings/formats/input-format#input_format_parquet_spatial_filter_push_down), a caixa delimitadora das `GeospatialStatistics` é usada para pular grupos de linhas.
* Se o tipo de coluna solicitado for `String`, os metadados do GeoParquet e o tipo lógico serão ignorados e o payload bruto da geometria codificada será retornado como está — bytes WKB ou WKT, de acordo com a codificação declarada pela coluna do GeoParquet. Isso também se aplica se a configuração [`input_format_parquet_allow_geoparquet_parser`](/pt-BR/reference/settings/formats/input-format#input_format_parquet_allow_geoparquet_parser) estiver definida como `0` e nenhum tipo geométrico for solicitado explicitamente.

### Comportamento de escrita {#write}

Na escrita, colunas de nível superior dos tipos `Point`, `MultiPoint`, `LineString`, `Polygon`, `MultiLineString` ou `MultiPolygon` são codificadas como `BYTE_ARRAY` (WKB), e os metadados JSON `geo` correspondentes são acrescentados ao footer do arquivo Parquet. Um `Variant` [`Geometry`](/pt-BR/reference/data-types/geo#geometry) de nível superior também é codificado como um payload `BYTE_ARRAY` WKB (seus subvalores são convertidos em WKB e armazenados como uma coluna `Nullable(String)`), mas, por padrão, nenhum metadado `geo` é emitido para ele, portanto ele é lido de volta como `String`. Por padrão, essas colunas são gravadas como `BYTE_ARRAY` com estatísticas de mín./máx. Com a configuração [`output_format_parquet_geometry_logical_type`](/pt-BR/reference/settings/formats/output-format#output_format_parquet_geometry_logical_type) habilitada, todas essas colunas são anotadas com o tipo lógico `GEOMETRY` e o CRS padrão (`OGC:CRS84`); os metadados dos seus fragmentos de coluna contêm `GeospatialStatistics` (a caixa delimitadora e os tipos de geometria), mas nenhuma estatística de mín./máx. nem índice de coluna, conforme exigido pela especificação; e uma coluna `Geometry` é descrita nos metadados `geo` com uma lista vazia de tipos de geometria, de modo que é lida de volta como `Geometry`. A configuração vem desabilitada por padrão porque leitores que não conhecem esse tipo lógico (por exemplo, Arrow C++ e `pyarrow` anteriores à versão 20) não conseguem abrir o arquivo inteiro. Outros tipos relacionados a geo, como [`Ring`](/pt-BR/reference/data-types/geo#ring), são gravados usando sua representação nativa subjacente, sem metadados GeoParquet. Esse comportamento pode ser desativado por completo definindo [`output_format_parquet_geometadata`](/pt-BR/reference/settings/formats/output-format#output_format_parquet_geometadata) como `0`; nesse caso, até mesmo os tipos geométricos compatíveis são gravados usando sua representação nativa subjacente (`Point` como `Tuple(Float64, Float64)`, `LineString` como `Array(Point)`, `Polygon` como `Array(Array(Point))`, etc.), e nenhum metadado GeoParquet é emitido.

Colunas de geometria devem aparecer na raiz do schema ou aninhadas em `Tuple` (`struct`); não há suporte para aninhá-las em `Array` ou `Map`. `Nullable` também não tem suporte para colunas geo.

### Leitura de dados {#reading-data}

Leia os dados no formato `Parquet`:

```sql
SELECT *
FROM football
INTO OUTFILE 'football.parquet'
FORMAT Parquet
```

<Tip>
  Parquet é um formato binário que não é exibido no terminal de forma legível para humanos. Use `INTO OUTFILE` para gerar arquivos Parquet.
</Tip>

Para trocar dados com o Hadoop, você pode usar o [`motor de tabela HDFS`](/pt-BR/reference/engines/table-engines/integrations/hdfs).
