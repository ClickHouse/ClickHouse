Essas configurações configuram o servidor ClickHouse e são geradas automaticamente a partir do código-fonte do ClickHouse.

## use_minimalistic_part_header_in_zookeeper {#use_minimalistic_part_header_in_zookeeper}

Configuração obsoleta, sem efeito. As tabelas [replicadas](/pt-BR/reference/engines/table-engines/mergetree-family/replication) sempre armazenam o cabeçalho de uma parte de dados de forma compacta em um único `znode`. Os cabeçalhos de partes gravados por versões mais antigas, com `znodes` filhos `columns` e `checksums` separados, continuam sendo lidos.

## use_separate_cache_arena {#use_separate_cache_arena}

<SettingsInfoBlock type="Bool" default_value="1" changeable_without_restart="Não" />

Ativa uma arena dedicada no jemalloc para alocações de cache (mark cache, cache não comprimido, page cache).
Isola os dados do cache das alocações do processamento de consultas, reduzindo a fragmentação da memória.

## use_shared_merge_tree_log_pipeline {#use_shared_merge_tree_log_pipeline}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="No" />

Disponível apenas no ClickHouse Cloud. Quando habilitada, os logs do sistema são gravados por meio de um pipeline `SharedMergeTree`
e o banco de dados `system` passa a ser um Banco de dados Shared, de modo que todas as réplicas veem as mesmas tabelas de logs.

Cada flush de um log grava um arquivo `Native` com a função de tabela `s3` (ou `azureBlobStorage`) na pasta da
geração do log, que é o hash de suas colunas e chaves. Para cada geração, o pipeline mantém a fila `system._<log>_s3queue_<hash>`,
que lê essa pasta, a visão materializada `system._<log>_mv_<hash>` e a tabela `SharedMergeTree` `system.<log>_<hash>`.
`system.<log>` é uma tabela `Merge` sobre as gerações. Um novo schema cria uma nova geração; configurações, TTL e índices
vêm das chaves `smt_settings`, `smt_ttl` e `smt_indices` da configuração do log e são alterados in-place.
Os objetos são criados no primeiro flush de um log ou na inicialização, com `prepare_system_log_tables_on_startup`.
A sorting key de uma tabela é a chave do log precedida de `hostname`, para que as linhas de uma réplica sejam lidas pela chave.
As chaves `smt_order_by` e `smt_partition_by` da configuração do log substituem as chaves da tabela.

O banco de dados local `system` é renomeado para `system_local` enquanto a configuração estiver habilitada. Requer `shared_database_catalog`
e `<shared_log_pipeline><endpoint>` na configuração do servidor.
Veja também: `shared_log_pipeline.enable_sync_flush`, `shared_log_pipeline.flush_timeout_seconds`.
