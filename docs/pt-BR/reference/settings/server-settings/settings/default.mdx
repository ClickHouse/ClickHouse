Essas configurações definem o servidor ClickHouse e são geradas automaticamente a partir do código-fonte do ClickHouse.

<div id="default_database">
  ## default_database
</div>

<SettingsInfoBlock type="String" default_value="default" changeable_without_restart="No" />O nome do banco de dados padrão.

<div id="default_password_type">
  ## default_password_type
</div>

Define o tipo de senha que será configurado automaticamente em consultas como `CREATE USER u IDENTIFIED BY 'p'`.

Os valores aceitos são:

* `plaintext_password`

* `sha256_password`

* `double_sha1_password`

* `bcrypt_password`

* **Padrão:** `sha256_password`

```xml
<default_password_type>sha256_password</default_password_type>
```

<div id="default_profile">
  ## default_profile
</div>

Perfil de configuração padrão. Os perfis de configuração ficam no arquivo especificado na configuração `user_config`.

* **Padrão:** `default`

**Exemplo**

```xml
<default_profile>default</default_profile>
```

<div id="default_session_timeout">
  ## default_session_timeout
</div>

Tempo limite padrão da sessão, em segundos.

* **Padrão:** `60`

```xml
<default_session_timeout>60</default_session_timeout>
```

<div id="default_session_user">
  ## default_session_user
</div>

<SettingsInfoBlock type="String" default_value="default" changeable_without_restart="No" />

O nome de usuário usado na autenticação quando um cliente se conecta sem especificar um nome de usuário: uma requisição HTTP sem o parâmetro `user` e o cabeçalho `X-ClickHouse-User`, um pacote `Hello` do protocolo nativo com nome de usuário vazio, um handshake MySQL ou PostgreSQL com nome de usuário vazio, uma consulta gRPC sem `user_name`, uma chamada Arrow Flight sem o cabeçalho `authorization` (ou com credenciais Basic com nome de usuário vazio) ou uma mensagem WebSocket `auth` do [terminal web](/pt-BR/concepts/features/interfaces/web-terminal) com o campo `user` omitido ou vazio.

O nome de usuário vazio é resolvido para esse valor antes da autenticação; portanto, a conexão continua sujeita à autenticação do usuário substituído: a senha, a rede e outras verificações de acesso são aplicadas normalmente. Um nome de usuário vazio é apenas um alias do nome de usuário configurado, e aceitá-lo não concede acesso além daquele já obtido ao especificar explicitamente o mesmo nome de usuário. Em versões anteriores à introdução desta configuração, o fallback de um nome de usuário vazio para `default` existia apenas no caminho simples de parâmetros de consulta HTTP, em consultas gRPC, chamadas Arrow Flight e no terminal web, enquanto os protocolos nativo, MySQL e PostgreSQL rejeitavam nomes de usuário vazios; agora todos os aceitam. A autenticação HTTP Basic com nome de usuário vazio e requisições com `X-ClickHouse-Key`, mas sem `X-ClickHouse-User`, também rejeitavam nomes de usuário vazios antes da introdução desta configuração.

Se definido como uma string vazia, conexões sem nome de usuário são rejeitadas. Manipuladores HTTP com um usuário fixo (a chave `user` dentro de `handler` em uma regra `http_handlers` ou a chave `user` dentro de `handler` em uma regra `prometheus.handlers`) são autenticados como o usuário configurado e não são afetados.

Quando a seção `session_log` está habilitada na configuração do servidor, cada rejeição desse tipo é registrada em [`system.session_log`](/pt-BR/reference/system-tables/session_log) como um evento `LoginFailure` com `user` vazio, permitindo auditar conexões proibidas sem nome de usuário em todas as interfaces.

O usuário de sessão padrão nunca é aplicado a conexões entre servidores: elas se identificam com um marcador especial em vez de um nome de usuário e são autenticadas pelo segredo do cluster e pelo usuário inicial.

O valor pode ser substituído para um endpoint específico de um protocolo componível com a chave `default_session_user` na seção `protocols`; consulte [Protocolos componíveis](/pt-BR/concepts/features/configuration/server-config/composable-protocols).
