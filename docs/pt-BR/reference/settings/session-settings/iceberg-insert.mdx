## iceberg_insert_commit_retry_initial_backoff_ms {#iceberg_insert_commit_retry_initial_backoff_ms}

<SettingsInfoBlock type="UInt64" default_value="10" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "10"},{"label": "Nova configuração. Um commit de um `INSERT` no Iceberg que perdeu a disputa para um commit concorrente é tentado novamente após um atraso exponencial aleatório, em vez de imediatamente."}]}]} />

O limite superior do atraso antes da primeira retentativa de um `INSERT` em uma tabela Iceberg cujo commit perdeu a disputa para um commit concorrente.
O limite dobra a cada nova retentativa, até `iceberg_insert_commit_retry_max_backoff_ms`, e cada atraso é escolhido aleatoriamente
entre zero e o limite, para que os processos de gravação que perderam a disputa na mesma condição de corrida não tentem novamente no mesmo instante e entrem em conflito outra vez.
A espera ocorre antes da consulta aos metadados mais recentes; assim, quando há muitos processos de gravação concorrentes, ela também limita a frequência com que o diretório de metadados
é listado. `0` permite retentativas sem atraso.

## iceberg_insert_max_bytes_in_data_file {#iceberg_insert_max_bytes_in_data_file}

Máximo de bytes do arquivo de dados parquet do iceberg em uma operação de insert.

O padrão espelha o padrão documentado da propriedade de tabela do Iceberg `write.target-file-size-bytes` (512 MiB),
consulte https://iceberg.apache.org/docs/1.5.2/configuration/. O limite é comparado com o tamanho do arquivo
gravado até o momento, ou seja, o tamanho comprimido. Por isso, um arquivo pode ultrapassá-lo no volume de dados que o writer ainda mantém em buffer, como
grupos de linhas Parquet incompletos e os que estão sendo codificados. `iceberg_insert_max_rows_in_data_file` limita o arquivo
independentemente de seu tamanho.

## iceberg_insert_max_data_files_in_upload {#iceberg_insert_max_data_files_in_upload}

<SettingsInfoBlock type="UInt64" default_value="8" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "8"},{"label": "Nova configuração. Um INSERT em Iceberg no S3 ou no Azure não aguarda mais o envio de cada arquivo de dados finalizado."}]}]} />

O número máximo de arquivos de dados finalizados de um mesmo stream de insert cujo envio não é aguardado enquanto o `INSERT` grava o próximo
arquivo, em sistemas de armazenamento de objetos que fazem o envio em segundo plano (S3, Azure). Cada um desses arquivos mantém seus buffers de envio até que o envio
seja concluído; portanto, valores mais altos ocultam mais latência de envio, ao custo de maior consumo de memória. Com `0`, o envio de cada arquivo de dados é aguardado antes
da gravação do próximo.

## iceberg_insert_single_manifest_for_all_partitions {#iceberg_insert_single_manifest_for_all_partitions}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Nova configuração."}]}]} />

Um `INSERT` em uma tabela Iceberg particionada grava um único arquivo de manifesto para todas as partições afetadas, como fazem o Spark
e o PyIceberg, em vez de um arquivo de manifesto por partição. Isso se aplica a cada stream de insert: cada stream faz o commit do próprio
snapshot com o próprio manifesto, portanto um `INSERT` só grava exatamente um manifesto com `max_insert_threads = 1`.
Com isso, `OPTIMIZE TABLE ... MANIFEST` passa a mesclar também manifestos de partições diferentes em um só.
`ALTER TABLE ... DROP PARTITION` não consegue remover uma partição cujo manifesto é compartilhado com outras partições.
