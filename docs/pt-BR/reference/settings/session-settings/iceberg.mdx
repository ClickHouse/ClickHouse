## iceberg_list_only_v_prefixed_metadata_files {#iceberg_list_only_v_prefixed_metadata_files}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Nova configuração para listar apenas o prefixo de chave `metadata\/v` ao procurar o arquivo de metadados mais recente de uma tabela Iceberg lida por caminho."}]}]} />

Localiza o arquivo de metadados mais recente de uma tabela Iceberg lida por caminho no S3 ou no Azure listando apenas o prefixo de chave `metadata/v`, de modo que os manifestos armazenados no mesmo diretório `metadata` não sejam listados. Se esse prefixo contiver arquivos `.metadata.json`, somente eles serão candidatos; caso contrário, o diretório inteiro será listado. Não se aplica quando `iceberg_use_version_hint`, `iceberg_metadata_file_path`, `iceberg_metadata_table_uuid` ou `iceberg_recent_metadata_file_by_last_updated_ms_field` são usados, nem às tabelas de um banco de dados de catálogo do lago de dados.

Habilite-a somente para tabelas cujos arquivos de metadados sigam todos o padrão de nome `v<N>...` (como fazem os catálogos do ClickHouse e do Hadoop): em um diretório que também contenha arquivos `<N>-<uuid>.metadata.json`, esses arquivos nunca são considerados candidatos e, portanto, os commits do processo de gravação que os gerou não são detectados.

Número máximo de arquivos de manifesto do Iceberg decodificados de forma concorrente durante a leitura de uma tabela.

Todos os manifestos de exclusão são decodificados antes que qualquer arquivo de dados seja lido; os manifestos de dados são decodificados enquanto a lista de arquivos de dados da consulta é produzida, e novos só são decodificados à medida que a consulta consome as entries já decodificadas. Decodificar vários manifestos ao mesmo tempo sobrepõe os round-trips ao armazenamento de objetos ao trabalho de pruning por entry.

Valores mais altos elevam o pico de memória quando o cache de Iceberg metadata files está desabilitado ou cheio, já que cada manifesto in-flight passa a manter seu próprio conteúdo decodificado.

Deve ser maior que zero; `1` decodifica os manifestos um de cada vez.

## iceberg_tolerate_conflicting_manifest_schemas {#iceberg_tolerate_conflicting_manifest_schemas}

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "1"},{"label": "Nova configuração: quando o cabeçalho de um arquivo de manifesto do Iceberg contém um schema que conflita com o schema registrado para o mesmo schema-id no metadata.json, dá-se preferência ao schema do metadata.json em vez de falhar a consulta, seguindo o comportamento de outras engines de consulta. `compatibility` abaixo de 26.10 restaura o comportamento estrito anterior."}]}]} />

Se habilitado e o schema-id de um arquivo de manifesto do Iceberg já estiver registrado a partir do metadata.json, o schema do metadata.json é utilizado e a cópia presente na chave `schema` do cabeçalho do arquivo de manifesto é ignorada, sem nenhuma comparação. Se desabilitado, a cópia no cabeçalho do manifesto é comparada com o schema do metadata.json, e um conflito faz a consulta falhar com um erro ICEBERG&#95;SPECIFICATION&#95;VIOLATION.

O schema do cabeçalho do manifesto é apenas uma cópia do schema da tabela no momento em que o manifesto foi gravado, e já se observou que alguns writers (por exemplo, jobs de manutenção do AWS S3 Tables) armazenam cópias degradadas ali. Outras engines de consulta resolvem os schemas a partir do metadata.json e ignoram cópias divergentes no cabeçalho, e o padrão segue essa mesma abordagem. Um conflito entre duas definições de schema do metadata.json continua sempre fazendo a consulta falhar.
