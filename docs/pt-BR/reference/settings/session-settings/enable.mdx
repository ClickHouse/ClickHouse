<div id="enable_adaptive_aggregator">
  ## enable_adaptive_aggregator
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "Nova configuração para ativar a agregação adaptativa de `GROUP BY`, que congela a tabela hash local de cada thread quando ela atinge `adaptive_aggregator_freeze_threshold` chaves, permitindo que chaves frequentes continuem sendo agregadas nas pequenas tabelas locais, enquanto chaves raras são direcionadas pelo hash para filas por bucket e agregadas exatamente uma vez durante a mesclagem paralela por bucket; assim, as chaves raras são armazenadas e processadas uma vez, em vez de uma vez por thread."}]}]} />

Ativa o algoritmo adaptativo de `GROUP BY`: cada thread agrega em sua tabela hash local até atingir `adaptive_aggregator_freeze_threshold` chaves (ou `adaptive_aggregator_freeze_threshold_bytes` de memória); então, a tabela é congelada, de modo que as linhas de chaves já vistas (frequentes) continuam sendo atualizadas nela, enquanto chaves novas (raras) são direcionadas pelo hash para filas por bucket e agregadas exatamente uma vez durante a mesclagem paralela por bucket. As chaves frequentes permanecem em pequenas tabelas residentes em cache, e as chaves raras são armazenadas e processadas uma vez, em vez de uma vez por thread.

As configurações de agregação externa (`max_bytes_before_external_group_by`, `max_bytes_ratio_before_external_group_by`) são respeitadas: depois de ultrapassar o limite, as filas são descarregadas antecipadamente na tabela compartilhada e, se isso não for suficiente para voltar a ficar abaixo do limite, a tabela compartilhada é gravada em disco por meio da agregação externa comum.

<div id="enable_group_by_top_k_optimization">
  ## enable_group_by_top_k_optimization
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "Nova configuração para controlar a otimização de filtragem TopK durante a agregação em consultas `GROUP BY key ORDER BY key LIMIT N`."}]}]} />

Habilita a otimização de filtragem TopK durante a agregação em consultas `GROUP BY keys ORDER BY <prefix of keys> LIMIT K` e em consultas `GROUP BY keys LIMIT K` sem `ORDER BY` (nesse caso, quaisquer `K` grupos constituem um resultado válido; portanto, é sintetizada uma ordenação de todas as chaves).

Quando habilitada, o agregador mantém um heap limitado com as `K` principais chaves encontradas até o momento e deixa de inserir novas linhas na tabela hash quando a chave de agrupamento delas não pode fazer parte do resultado final. Isso evita agregar linhas que seriam descartadas pelo `ORDER BY ... LIMIT` subsequente e, quando o heap classifica a chave completa do `GROUP BY`, também remove os grupos expulsos da tabela hash intermediária, limitando seu tamanho ao `LIMIT`, em vez de ao número de chaves distintas. Quando o `ORDER BY` abrange apenas um prefixo próprio das chaves do `GROUP BY`, a classificação não consegue identificar um grupo completo; portanto, aplica-se apenas a omissão de linhas: a tabela hash mantém todos os grupos aceitos e ainda pode crescer conforme a cardinalidade das colunas de chave restantes.

A otimização é desabilitada quando o `LIMIT` solicitado é maior que [query&#95;plan&#95;max&#95;limit&#95;for&#95;top&#95;k&#95;optimization](/pt-BR/reference/settings/session-settings/query-plan#query_plan_max_limit_for_top_k_optimization) ou que o limite máximo de `100000`, pois o custo de memória e CPU do heap cresce com o `LIMIT` solicitado.

A otimização é ignorada para estruturas de consulta em que remover grupos poderia alterar o resultado, incluindo `WITH TOTALS`, `HAVING`, `QUALIFY`, funções de janela, `ROLLUP`/`CUBE`/`GROUPING SETS`, `LIMIT WITH TIES`, um `COLLATE` em qualquer uma das chaves de `GROUP BY` correspondentes (um `COLLATE` em uma coluna posterior do `ORDER BY`, após o prefixo completo da chave, não pode afetar quais grupos se qualificam e, portanto, não desabilita a otimização), `ORDER BY` em um agregado ou em qualquer elemento que não seja um prefixo inicial das chaves de `GROUP BY`, e quando `max_rows_to_group_by` ou `exact_rows_before_limit` está definido.

Valores possíveis:

* 0 — Desabilitado.
* 1 — Habilitado.

<div id="enable_packed_string_keys_in_aggregation">
  ## enable_packed_string_keys_in_aggregation
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "Nova configuração para alternar o uso da tabela hash baseada em `PackedStringRef` em `GROUP BY` com uma única chave `String`. previous_value=false para que a `compatibility` com versões anteriores à 26.8 restaure o método legado baseado em `StringHashTable`, incluindo sua divisão em buckets de dois níveis."}]}]} />

Use uma tabela hash com referências compactadas a strings de 16 bytes (`PackedStringRef`) como chave em `GROUP BY` com uma única chave `String` não anulável. Chaves de até 11 bytes são armazenadas diretamente na referência compactada; chaves mais longas são referenciadas em uma arena.
Esse método é mais rápido para a maioria das cargas de trabalho, mas pode ser mais lento que o método legado em `GROUP BY` com pouquíssimas chaves distintas com mais de 11 bytes (especialmente entre 12 e 24 bytes), pois a tabela hash legada mantém as chaves diretamente na célula, enquanto a compactada desreferencia o ponteiro da arena a cada sondagem.
Quando desativado, é usado o método legado baseado em `StringHashTable` (o padrão antes da versão 26.8).

Todos os servidores que participam de uma consulta distribuída devem usar o mesmo valor: com `distributed_aggregation_memory_efficient`, os números dos buckets de dois níveis dependem do hash da chave, que difere entre os dois métodos. Portanto, servidores com configurações divergentes podem dividir a mesma chave em buckets diferentes e produzir um resultado mesclado incorretamente. Para garantir essa consistência, o iniciador sempre envia seu valor efetivo com as consultas secundárias (mesmo quando ele é proveniente apenas dos valores padrão do servidor/perfil), substituindo os próprios valores padrão dos servidores remotos.

<div id="enable_shared_storage_snapshot_in_query">
  ## enable_shared_storage_snapshot_in_query
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "25.6"},{"label": "0"},{"label": "Uma nova configuração para compartilhar o snapshot de armazenamento na consulta"}]}, {"id": "row-2","items": [{"label": "25.12"},{"label": "1"},{"label": "Habilita por padrão o compartilhamento do snapshot de armazenamento na consulta"}]}]} />

Se estiver habilitada, todas as subconsultas dentro de uma única consulta compartilharão o mesmo StorageSnapshot para cada tabela.
Isso garante uma visão consistente dos dados em toda a consulta, mesmo se a mesma tabela for acessada várias vezes.

Isso é necessário para consultas em que a consistência interna das partes de dados é importante. Exemplo:

```sql
SELECT
    count()
FROM events
WHERE (_part, _part_offset) IN (
    SELECT _part, _part_offset
    FROM events
    WHERE user_id = 42
)
```

Sem essa configuração, as consultas externa e interna podem operar em snapshots de dados diferentes, levando a resultados incorretos.

Valores possíveis:

* 0 - Desativado
* 1 - Ativado
