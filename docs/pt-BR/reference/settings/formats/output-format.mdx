## output_format_arrow_record_batch_size {#output_format_arrow_record_batch_size}

<SettingsInfoBlock type="UInt64" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "0"},{"label": "Nova configuração para combinar blocos pequenos na saída `Arrow` e `ArrowStream` usando uma contagem-alvo de linhas. O padrão `0` preserva um lote de registros por bloco."}]}]} />

Número-alvo de linhas por lote de registros nos formatos de saída `Arrow` e `ArrowStream`. A combinação de blocos pequenos reduz a sobrecarga de metadados e do preenchimento de buffer, especialmente em consultas com filtros seletivos.

Os blocos são acumulados até que essa meta ou [output&#95;format&#95;arrow&#95;record&#95;batch&#95;size&#95;bytes](/pt-BR/reference/settings/formats/output-format#output_format_arrow_record_batch_size_bytes) seja atingida. Um bloco que já atinge a meta de linhas ou bytes é gravado separadamente, sem ser dividido. Se você definir uma meta de linhas, os lotes combinados conterão menos que o dobro desse número de linhas, mas um único bloco de entrada pode ser maior.

A bufferização de blocos pode aumentar o uso de memória e atrasar a saída. Se o resultado não atingir nenhuma das metas, `ArrowStream` gravará o primeiro lote de registros apenas quando a consulta terminar, embora possa gravar o schema antes. Deixe ambas as metas em `0` para gravar os lotes de registros à medida que os blocos chegam.

`0` (o padrão) desabilita a meta de linhas. Experimente `65409` como valor inicial.

## output_format_arrow_unsupported_types {#output_format_arrow_unsupported_types}

<SettingsInfoBlock type="ArrowUnsupportedTypes" default_value="binary" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.10"},{"label": "binary"},{"label": "Nova configuração que substitui `output_format_arrow_unsupported_types_as_binary`, adicionando um modo `text`. Seu padrão corresponde ao comportamento anterior, portanto `compatibility` não deve alterá-lo."}]}]} />

O que gravar para uma coluna cujo tipo não possui um mapeamento nativo no Arrow (por exemplo, `JSON`, `Dynamic`, `QBit` ou `AggregateFunction`):

* `throw` — rejeita a consulta;
* `text` — um valor em forma de texto por linha (o que `CAST(col AS String)` produziria), como uma coluna `Utf8` do Arrow;
* `binary` — a representação binária de cada valor, como uma coluna `Binary` do Arrow (a mesma codificação por valor do `RowBinary`).

Uma coluna `AggregateFunction` também é `Binary` no modo `text`, porque sua forma de texto é o aggregate state bruto, e não texto propriamente dito, e uma coluna `Utf8` do Arrow precisa conter UTF-8 válido. Use `finalizeAggregation` para obter um valor legível.

Todo valor gravado em uma coluna `Utf8` é ajustado para conter UTF-8 válido, com cada sequência inválida substituída por U+FFFD. Isso afeta apenas texto que um leitor não conseguiria interpretar como texto de qualquer forma — um `Dynamic` contendo uma `String` de bytes arbitrários, por exemplo. Use o modo `binary` quando os bytes precisarem ser preservados exatamente.

`output_format_arrow_string_as_string` não se aplica a essas colunas, apenas às colunas `String` e `FixedString` reais. Assim, o tipo Arrow de uma coluna opaca continua sendo uma declaração sobre qual codificação ela contém: `Utf8` é a forma de texto e `Binary` é a binária, independentemente do que essa configuração diga.

O mesmo vale para um aggregate state contido em um `Dynamic`: a coluna é tipada a partir de `Dynamic`, que nada diz sobre o que suas linhas contêm, e o schema Arrow é fixado antes que qualquer valor seja visto, de modo que o state não pode receber uma coluna `Binary` própria como acontece com uma coluna `AggregateFunction`. No modo `text`, portanto, há perda de informação; o modo `binary` a preserva. Um `Variant` não é afetado — ele lista suas alternativas, de modo que um `AggregateFunction` entre elas ganha seu próprio filho `Binary`.

Tanto em `text` quanto em `binary`, o campo é marcado no schema Arrow com o nome de extensão `clickhouse.opaque` e com o nome do tipo ClickHouse original, para que um leitor consiga distingui-lo de uma coluna string ou binária genuína.

O ClickHouse só lê essa coluna de volta no tipo indicado pela marcação quando o lado da leitura já conhece esse tipo, seja porque uma tabela o declara, seja porque um argumento `structure` como o aceito por `file` e `s3` o nomeia; nesse caso, isso também vale dentro de `Array`, `Tuple`, `Map` e `Nullable`. A inferência de esquema não consulta a marcação, portanto uma coluna lida sem um tipo nomeado para ela ainda chega como `String` contendo a carga útil bruta. Uma alternativa de um `Variant` nunca é lida de volta, mesmo com o tipo nomeado, porque a união Arrow formada por suas alternativas é decodificada sem consultar as marcações. Em todos os casos, os dados gravados são bem formados para outros leitores Arrow.

Tem precedência sobre a configuração mais antiga `output_format_arrow_unsupported_types_as_binary`, que só é consultada quando esta configuração permanece em seu valor padrão.
