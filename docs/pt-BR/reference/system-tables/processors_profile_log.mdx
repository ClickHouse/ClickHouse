## Descrição {#description}

Esta tabela contém informações de profiling no nível dos processadores (que você pode encontrar em [`EXPLAIN PIPELINE`](/pt-BR/reference/statements/explain#explain-pipeline)).

É seguro truncar ou remover esta tabela a qualquer momento.

## Colunas {#columns}

* `hostname` ([LowCardinality(String)](/pt-BR/reference/data-types/lowcardinality)) — Hostname do servidor que executa a consulta.
* `clickhouse_version` ([LowCardinality(String)](/pt-BR/reference/data-types/lowcardinality)) — Versão do servidor ClickHouse que produziu a linha.
* `system_processor` ([LowCardinality(String)](/pt-BR/reference/data-types/lowcardinality)) — Arquitetura de CPU do servidor ClickHouse que produziu a linha.
* `event_date` ([Date](/pt-BR/reference/data-types/date)) — A data em que o evento aconteceu.
* `event_time` ([DateTime](/pt-BR/reference/data-types/datetime)) — A data e a hora em que o evento aconteceu.
* `event_time_microseconds` ([DateTime64(6)](/pt-BR/reference/data-types/datetime64)) — A data e a hora, com precisão de microssegundos, em que o evento aconteceu.
* `id` ([UInt64](/pt-BR/reference/data-types/int-uint)) — ID do processador, único dentro da consulta. É o número presente em `processor_uniq_id`.
* `parent_ids` ([Array(UInt64)](/pt-BR/reference/data-types/array)) — IDs dos processadores pais.
* `plan_step` ([UInt64](/pt-BR/reference/data-types/int-uint)) — ID do passo do plano de consulta que criou este processador, único dentro da consulta. É o número presente em `step_uniq_id` mais um. O valor é zero se o processador não foi adicionado a partir de nenhum passo.
* `plan_step_name` ([String](/pt-BR/reference/data-types/string)) — Nome do passo do plano de consulta que criou este processador. O valor fica vazio se o processador não foi adicionado a partir de nenhum passo.
* `plan_step_description` ([String](/pt-BR/reference/data-types/string)) — Descrição do passo do plano de consulta que criou este processador. O valor fica vazio se o processador não foi adicionado a partir de nenhum passo.
* `plan_group` ([UInt64](/pt-BR/reference/data-types/int-uint)) — Grupo do processador, se ele foi criado por um passo do plano de consulta. Um grupo é um particionamento lógico de processadores adicionados a partir do mesmo passo do plano de consulta. O grupo é usado apenas para melhorar a apresentação do resultado de EXPLAIN PIPELINE.
* `initial_query_id` ([String](/pt-BR/reference/data-types/string)) — ID da consulta inicial na mesma cadeia de consultas.
* `query_id` ([String](/pt-BR/reference/data-types/string)) — ID da consulta.
* `name` ([LowCardinality(String)](/pt-BR/reference/data-types/lowcardinality)) — Nome do processador.
* `elapsed_us` ([UInt64](/pt-BR/reference/data-types/int-uint)) — Número de microssegundos durante os quais este processador foi executado.
* `input_wait_elapsed_us` ([UInt64](/pt-BR/reference/data-types/int-uint)) — Número de microssegundos durante os quais este processador ficou esperando por dados (de outro processador).
* `output_wait_elapsed_us` ([UInt64](/pt-BR/reference/data-types/int-uint)) — Número de microssegundos durante os quais este processador ficou esperando porque a porta de saída estava cheia.
* `input_rows` ([UInt64](/pt-BR/reference/data-types/int-uint)) — O número de linhas consumidas pelo processador.
* `input_bytes` ([UInt64](/pt-BR/reference/data-types/int-uint)) — O número de bytes consumidos pelo processador.
* `output_rows` ([UInt64](/pt-BR/reference/data-types/int-uint)) — O número de linhas geradas pelo processador.
* `output_bytes` ([UInt64](/pt-BR/reference/data-types/int-uint)) — O número de bytes gerados pelo processador.
* `processor_uniq_id` ([String](/pt-BR/reference/data-types/string)) — O ID único do processador no pipeline.
* `step_uniq_id` ([String](/pt-BR/reference/data-types/string)) — O ID único do passo no plano.
* `exception_code` ([Int32](/pt-BR/reference/data-types/int-uint)) — Código da exceção se a consulta falhou; caso contrário, 0.
* `exception` ([String](/pt-BR/reference/data-types/string)) — Mensagem da exceção se a consulta falhou; caso contrário, o valor fica vazio.

## Exemplo {#example}

```sql title="Query"
EXPLAIN PIPELINE
SELECT sleep(1)
┌─explain─────────────────────────┐
│ (Expression)                    │
│ ExpressionTransform             │
│   (SettingQuotaAndLimits)       │
│     (ReadFromStorage)           │
│     SourceFromSingleChunk 0 → 1 │
└─────────────────────────────────┘

SELECT sleep(1)
SETTINGS log_processors_profiles = 1
Query id: feb5ed16-1c24-4227-aa54-78c02b3b27d4
┌─sleep(1)─┐
│        0 │
└──────────┘
1 rows in set. Elapsed: 1.018 sec.

SELECT
    name,
    elapsed_us,
    input_wait_elapsed_us,
    output_wait_elapsed_us
FROM system.processors_profile_log
WHERE query_id = 'feb5ed16-1c24-4227-aa54-78c02b3b27d4'
ORDER BY name ASC
```

```text title="Response"
┌─name────────────────────┬─elapsed_us─┬─input_wait_elapsed_us─┬─output_wait_elapsed_us─┐
│ ExpressionTransform     │    1000497 │                  2823 │                    197 │
│ LazyOutputFormat        │         36 │               1002188 │                      0 │
│ LimitsCheckingTransform │         10 │               1002994 │                    106 │
│ NullSource              │          5 │               1002074 │                      0 │
│ NullSource              │          1 │               1002084 │                      0 │
│ SourceFromSingleChunk   │         45 │                  4736 │                1000819 │
└─────────────────────────┴────────────┴───────────────────────┴────────────────────────┘
```

Aqui você pode ver:

* `ExpressionTransform` estava executando a função `sleep(1)`, então seu `work` levará 1e6 e, portanto, `elapsed_us` &gt; 1e6.
* `SourceFromSingleChunk` precisa esperar, porque `ExpressionTransform` não aceita nenhum dado durante a execução de `sleep(1)`, então ficará no estado `PortFull` por 1e6 us e, portanto, `output_wait_elapsed_us` &gt; 1e6.
* `LimitsCheckingTransform`/`NullSource`/`LazyOutputFormat` precisam esperar até que `ExpressionTransform` execute `sleep(1)` para processar o resultado, então `input_wait_elapsed_us` &gt; 1e6.

### Profiling de uma junção {#profiling-a-join}

Quando uma consulta lê dados de várias tabelas, cada tabela tem seu próprio pipeline de leitura, e as linhas passam por muitos processadores até chegar ao resultado.
Por isso, somar `input_rows` ou `output_rows` de todos os processadores conta as mesmas linhas várias vezes e não mostra quanto foi lido de cada tabela.
O exemplo a seguir usa duas tabelas `MergeTree` de tamanhos diferentes em um servidor único.

```sql title="Query"
CREATE TABLE big (id UInt64, v UInt64) ENGINE = MergeTree ORDER BY id;
CREATE TABLE small (id UInt64, w UInt64) ENGINE = MergeTree ORDER BY id;

INSERT INTO big SELECT number, number FROM numbers(1000000);
INSERT INTO small SELECT number, number FROM numbers(1000);

EXPLAIN PIPELINE
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0;
```

`EXPLAIN PIPELINE` mostra um pipeline de leitura para cada lado da junção (`ReadFromMergeTree`, com as fontes de dados `MergeTreeSelect` abaixo dele), conectados pelos processadores de junção. `join_algorithm = 'hash'` e `enable_join_runtime_filters = 0` tornam este exemplo reproduzível: um filtro de junção em tempo de execução não consegue eliminar dados de `big` antes que a respectiva fonte de dados emita linhas.

```sql title="Query"
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0, log_processors_profiles = 1;
-- Note the query ID printed by the client, or look it up in `system.query_log`.

SYSTEM FLUSH LOGS;

SELECT
    id,
    parent_ids,
    plan_step,
    name,
    plan_step_name,
    plan_step_description,
    input_rows,
    output_rows,
    elapsed_us
FROM system.processors_profile_log
WHERE query_id = '<query_id>'
ORDER BY plan_step, id;
```

Para interpretar o resultado:

* Observe os processadores de fonte de dados, cujo `name` é `MergeTreeSelect(...)` (ou `MergeTreeSource`) e cujo `plan_step_name` é `ReadFromMergeTree`. O `output_rows` de cada um é o número de linhas que aquela fonte de dados produziu. Some esse valor por passo de leitura (`plan_step`), e não na consulta inteira. O resultado é o número de linhas que o passo de leitura repassou para o restante do pipeline.
* Cada lado da junção tem seu próprio passo `ReadFromMergeTree`, com um `plan_step` diferente. Nas linhas desta execução, `parent_ids` lista os IDs dos processadores a jusante. Partindo de uma fonte de dados, associe recursivamente cada valor de `parent_ids` a um `id` no mesmo `query_id` para seguir o branch em direção à junção. Assim é possível identificar, por exemplo, o branch que alimenta `FillingRightJoinSide`.
* Os processadores acima das fontes de dados (por exemplo, `ExpressionTransform`, `FillingRightJoinSide`, `ConcatProcessor` ou a própria transformação de junção) consomem e produzem linhas derivadas das fontes de dados. Não some os contadores deles aos das fontes de dados, pois isso contaria as mesmas linhas novamente.
* As informações do passo nem sempre bastam para identificar uma fonte de dados. `EXPLAIN PIPELINE` é um plano separado: ele ajuda a comparar nomes de processadores e formatos de branches, mas sua saída em texto simples não contém os valores de `id` registrados nem `parent_ids`. Se as duas tabelas tiverem descrições de passo semelhantes, use o grafo da consulta executada e as contagens de linhas conhecidas. Neste exemplo, as fontes de dados de leitura de `big` somam 1,000,000 linhas e as de `small` somam 1,000 linhas.
* Os contadores de linhas e de bytes dos processadores descrevem os dados que passam pelo pipeline, e não leituras físicas do armazenamento. Eles não incluem grânulos ou marcas que foram lidos e depois descartados pela filtragem, são afetados pela chave primária e por outras filtragens de índice, por `PREWHERE` e pela poda de colunas, e não refletem os bytes compactados lidos do disco. `SelectedRows`, `SelectedBytes` e `SelectedMarks` em `system.query_log` são estatísticas lógicas de seleção: podem ser diferentes de zero mesmo quando todos os dados vêm do cache. Para investigar leituras de arquivos, use `ReadBufferFromFileDescriptorReadBytes`, que inclui as leituras atendidas pelo cache de páginas do SO. Para investigar leituras do disco local ou de dispositivos de bloco, sem contar o cache de páginas do SO, use `OSReadBytes`.
