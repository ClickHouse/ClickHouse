## Descrição {#description}

Mostra ao usuário atual seus próprios registros do log de consultas. Lê a tabela de log de consultas configurada pelas opções do servidor `query_log.database` e `query_log.table` (`system.query_log` por padrão) e retorna apenas as linhas cujo usuário iniciador é igual a `currentUser()` (o usuário iniciador é obtido de `initial_user` quando definido; caso contrário, de `user`).

Diferentemente da própria tabela de log de consultas, `system.user_query_log` pode ser lida sem nenhuma permissão, permitindo que os usuários inspecionem suas próprias consultas sem receber acesso às consultas de outros usuários.

Isso é compatível apenas quando o log de consultas é armazenado localmente. Se `query_log.engine` estiver configurado como `Distributed` ou qualquer outro engine que delegue leituras a outro servidor, `system.user_query_log` se recusará a ler dela e lançará uma exceção, pois a verificação de acesso necessária não pode ser aplicada entre servidores que se comunicam pelo protocolo ClickHouse. Nesse caso, desative a tabela com `query_log.enable_user_query_log = 0`.

**Disponibilidade**

`system.user_query_log` só é anexada quando a opção do servidor `query_log.enable_user_query_log` está habilitada, o que é o padrão. Quando a opção é `0`, a tabela não existe e as consultas feitas a ela falham com `UNKNOWN_TABLE`.

Quando `query_log.enable_user_query_log` está habilitado, mas o log de consultas subjacente não está configurado ou sua tabela ainda não foi criada, `system.user_query_log` existe, mas está vazia.

As condições nas colunas de partição e de chave do log de consultas (`event_date`, `event_time`, `query_start_time`, `query_id`, `type` e colunas escalares semelhantes) comparadas com constantes são aplicadas à tabela de log de consultas subjacente, de modo que consultas comuns, como o exemplo abaixo, preservam a eliminação de partições e não varrem todo o log retido.

Se uma tabela chamada `system.user_query_log` tiver sido criada antes da atualização para uma versão do ClickHouse que fornece essa tabela, o servidor não será iniciado até que a tabela existente seja renomeada ou removida, ou que `query_log.enable_user_query_log` seja definido como `0`.

Uma junção é contabilizada independentemente do nível de aninhamento: subconsultas, expressões de tabela comuns, views, views de views e o SELECT de uma visão materializada acionada por um INSERT são todos registrados na linha da consulta enviada; por isso, esse valor pode ser diferente de zero mesmo para uma consulta cujo texto não contém nenhum JOIN. Alguns pipelines são montados mais de uma vez durante a execução de uma única consulta: o SELECT de uma visão materializada é montado para cada bloco do INSERT que a aciona e por cada fluxo de insert, o membro recursivo de uma CTE recursiva é montado a cada iteração, e a relação de um loop é montada novamente sempre que é reiniciada. ## Exemplo {#example}

```sql

    query_start_time,
    query_duration_ms,
    query
FROM system.user_query_log
ORDER BY query_start_time DESC
LIMIT 10;
```
