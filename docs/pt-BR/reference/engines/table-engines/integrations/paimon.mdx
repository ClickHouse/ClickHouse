Este motor fornece integração somente leitura com tabelas Apache [Paimon](https://paimon.apache.org/) existentes no Amazon S3, Azure, HDFS e em armazenamento local.
Ele oferece suporte a leituras de snapshot, leituras incrementais e à poda básica de partições.

## Criar tabela {#create-table}

Observe que a tabela Paimon já deve existir no armazenamento; este comando não aceita parâmetros de DDL para criar uma nova tabela.
A criação de tabelas `Paimon*` é condicionada por `allow_experimental_paimon_storage_engine` (desabilitado por padrão), portanto habilite-o antes de executar `CREATE TABLE`.

```sql
SET allow_experimental_paimon_storage_engine = 1;

CREATE TABLE paimon_table_s3
    ENGINE = PaimonS3(url, [, access_key_id, secret_access_key] [,format] [,compression])

CREATE TABLE paimon_table_azure
    ENGINE = PaimonAzure(connection_string|storage_account_url, container_name, blobpath, [,account_name], [,account_key] [,format] [,compression_method])

CREATE TABLE paimon_table_hdfs
    ENGINE = PaimonHDFS(path_to_table, [,format] [,compression_method])

CREATE TABLE paimon_table_local
    ENGINE = PaimonLocal(path_to_table, [,format] [,compression_method])
```

## Argumentos do mecanismo {#engine-arguments}

A descrição dos argumentos corresponde à descrição dos argumentos nos motores `S3`, `AzureBlobStorage`, `HDFS` e `File`, respectivamente.
`format` indica o formato dos arquivos de dados na tabela Paimon.

Os parâmetros do mecanismo podem ser especificados usando [coleções nomeadas](/pt-BR/concepts/features/configuration/server-config/named-collections)

### Exemplo {#example}

```sql
CREATE TABLE paimon_table ENGINE=PaimonS3('http://test.s3.amazonaws.com/clickhouse-bucket/test_table', 'test', 'test')
```

Usando coleções nomeadas:

```xml
<clickhouse>
    <named_collections>
        <paimon_conf>
            <url>http://test.s3.amazonaws.com/clickhouse-bucket/</url>
            <access_key_id>test</access_key_id>
            <secret_access_key>test</secret_access_key>
        </paimon_conf>
    </named_collections>
</clickhouse>
```

```sql
CREATE TABLE paimon_table ENGINE=PaimonS3(paimon_conf, filename = 'test_table')
```

## Recursos {#capabilities}

* Leituras de snapshot a partir do snapshot mais recente da tabela.
* Leituras incrementais com base no ID do snapshot confirmado, quando habilitado.
* Poda de partições quando `use_paimon_partition_pruning` está habilitado.
* Atualização opcional de metadados em segundo plano quando configurada.
* UUID estável da tabela ao usar bancos de dados Atomic/Replicated, permitindo macros `{uuid}` em caminhos do Keeper.

## Tabelas com chave primária {#primary-key-tables}

A mesclagem na leitura (merge-on-read) não está implementada, portanto **tabelas com chave primária não podem ser lidas**: o leitor retorna a união bruta dos
arquivos de dados do snapshot, que ainda contém as versões de linhas substituídas por upserts posteriores. Por isso, ler uma tabela cujo schema
declara `primary-key` lança uma exceção.

## Tabelas com vetores de exclusão {#deletion-vectors}

Os vetores de exclusão não são aplicados, portanto **snapshots com vetores de exclusão não podem ser lidos**: o resultado ainda
conteria as linhas removidas por instruções `DELETE` e `UPDATE` posteriores. Por isso, a leitura de um snapshot cujo manifesto de índice lista
vetores de exclusão lança uma exceção, mesmo depois que `deletion-vectors.enabled` é desabilitado.

Uma compactação completa no Paimon (`compact_strategy => 'full'`) aplica os vetores de exclusão, e os snapshots criados depois
dela voltam a poder ser lidos.

Uma leitura incremental para no primeiro snapshot não consumido com vetores de exclusão e permanece nele mesmo após uma compactação
completa, pois todos os snapshots até essa compactação listam os mesmos vetores de exclusão. O cursor não avança.
A leitura é retomada quando o Paimon expira esses snapshots ou quando eles são abandonados ao mover o cursor para o snapshot da
compactação completa, o que descarta todos os snapshots ainda não consumidos até ele (consulte
[Quando um snapshot não pode ser lido](#when-a-snapshot-cannot-be-read)):

```bash
clickhouse-keeper-client -q "set '<paimon_keeper_path>/committed_snapshot' '<snapshot id of the full compaction>'"
```

Em ambos os casos, as linhas removidas por esses vetores de exclusão continuam presentes no que a leitura incremental já entregou.

## Configurações {#settings}

Este motor usa as mesmas configurações dos motores correspondentes de armazenamento de objetos e adiciona configurações específicas do Paimon:

* `allow_experimental_paimon_storage_engine` — habilita a criação dos motores de tabela `Paimon`, `PaimonS3`, `PaimonAzure`, `PaimonHDFS` e `PaimonLocal`. Padrão: `0` (desabilitado).
* `use_paimon_metadata_files_cache` — habilita o cache de arquivos de metadados do Paimon (armazena em cache listas de manifest e manifests desserializados). Defina como `1` para habilitar e `0` para desabilitar. Padrão: `0`. A forma como essa configuração entra em vigor difere entre funções de tabela e motores de tabela persistentes — veja a observação abaixo.
* `paimon_incremental_read` — habilita o modo de leitura incremental.
* `paimon_metadata_refresh_interval_sec` — intervalo, em segundos, da atualização de metadados em segundo plano. Quando definido como um valor maior que 0, uma tarefa em segundo plano busca periodicamente o snapshot e o esquema mais recentes no armazenamento de objetos. Padrão: 30.
* `paimon_keeper_path` — caminho do Keeper para o estado da leitura incremental. Deve ser definido e ser único por tabela; oferece suporte a macros como `{database}`, `{table}`, `{uuid}`.
* `paimon_replica_name` — nome da réplica para o estado da leitura incremental. Deve ser definido e ser único por réplica; oferece suporte a macros como `{replica}`.

Exemplo (habilite o motor experimental Paimon e o cache de arquivos de metadados):

```sql
SET allow_experimental_paimon_storage_engine = 1;
SET use_paimon_metadata_files_cache = 1;

CREATE TABLE paimon_cached
ENGINE = PaimonS3(paimon_conf, filename = 'paimon_all_types');
```

<Note title="Ciclo de vida de `use_paimon_metadata_files_cache`">
  A forma como `use_paimon_metadata_files_cache` é aplicado depende de como a tabela Paimon é acessada:

  * **Funções de tabela** (por exemplo, `SELECT ... FROM paimonS3(...)`): a decisão de usar o cache é avaliada por consulta, portanto você pode passar `SETTINGS use_paimon_metadata_files_cache = 1` diretamente no `SELECT`.
  * **Motores de tabela persistentes** (`PaimonS3`, `PaimonAzure`, `PaimonHDFS`, `PaimonLocal` e o alias `Paimon`): a decisão de usar o cache é fixada uma única vez quando os metadados da tabela são inicializados e armazenada em componentes persistentes imutáveis; o caminho de atualização de metadados deliberadamente não relê essa configuração. Portanto, passar `SETTINGS use_paimon_metadata_files_cache = 1` em um `SELECT` sobre uma tabela persistente já inicializada não tem efeito — a decisão fixada anteriormente continua sendo usada. Para alterá-la, defina `use_paimon_metadata_files_cache` antes da inicialização dos metadados da tabela ou execute `DROP` e recrie a tabela com `CREATE` usando o valor desejado.

  A capacidade do cache no nível do servidor (`paimon_metadata_files_cache_size`) *não* é fixada: é uma configuração de runtime que pode ser alterada por meio de `SYSTEM RELOAD CONFIG` e entra em vigor imediatamente, mesmo para tabelas já inicializadas.
</Note>

## Exemplos de leitura incremental {#incremental-read-examples}

Leitura incremental com estado do Keeper:

```sql
CREATE TABLE paimon_inc
ENGINE = PaimonS3(paimon_conf, filename = 'paimon_all_types')
SETTINGS
    paimon_incremental_read = 1,
    paimon_keeper_path = '/clickhouse/{database}/{uuid}',
    paimon_replica_name = '{replica}';
```

### Configurações no nível da consulta para leitura incremental {#query-level-settings-for-incremental-read}

As configurações a seguir são **no nível da consulta** (passadas via `SELECT ... SETTINGS`, não em `CREATE TABLE`). Elas controlam o comportamento das leituras incrementais em cada consulta:

* `paimon_target_snapshot_id` — lê apenas o delta do snapshot especificado. O watermark confirmado no Keeper **não** é avançado, portanto o mesmo snapshot pode ser relido quantas vezes for necessário. Padrão: `-1` (desabilitado).
* `max_consume_snapshots` — número máximo de snapshots a consumir em uma única leitura incremental. Quando a source acumula muitos snapshots não lidos, isso limita quantos são consumidos por consulta para controlar o tamanho do lote. `0` significa sem limite. Padrão: `0`.

**Leitura de snapshot direcionada** — sempre retorna o delta do snapshot 1, independentemente do watermark atual:

```sql
SELECT count()
FROM paimon_inc
SETTINGS paimon_target_snapshot_id = 1;
```

**Limitando o número de snapshots por lote** — se houver três novos snapshots pendentes, consuma no máximo dois por consulta:

```sql
SELECT count()
FROM paimon_inc
SETTINGS max_consume_snapshots = 2;
```

### Retrocedendo o warehouse {#rewinding-the-warehouse}

O cursor do Keeper em `paimon_keeper_path` registra até onde o stream já foi consumido, e as leituras incrementais assumem que o warehouse só avança — os ids de snapshot do Paimon aumentam monotonicamente e nunca são reutilizados. Expirar snapshots antigos não causa problemas: isso remove um prefixo e mantém intactos os ids acima dele.

Mover o warehouse *para trás* quebra essa premissa. Restaurar o warehouse a partir de um backup mais antigo, revertê-lo com outro motor ou remover e recriar a tabela Paimon no mesmo caminho são operações que retrocedem os ids de snapshot, e o processo de gravação passa a reutilizar ids que o cursor já consumiu.

**Retroceder o warehouse exige redefinir o cursor na mesma operação.** Depois que os ids são reutilizados, o ClickHouse não tem como reconstruir quais snapshots um consumidor já recebeu. Por isso, um cursor que fica desatualizado após um retrocesso resulta em uma entrega indefinida: snapshots com ids reutilizados podem ser ignorados.

Quando o retrocesso deixa o cursor apontando para além do snapshot mais recente do warehouse, a leitura falha com `INVALID_STATE` em vez de informar que não há dados novos, e o erro indica o comando de recuperação. Nada é lido e o cursor permanece inalterado; assim, todas as consultas seguintes falham da mesma forma até que o problema seja resolvido:

```
clickhouse-keeper-client -q "set '<paimon_keeper_path>/committed_snapshot' '<latest snapshot id>'"
```

Não exclua o nó `committed_snapshot` para fazer a recuperação. A ausência do cursor significa &quot;nunca consumido&quot;, o que faz com que a próxima leitura seja uma releitura completa de toda a tabela, em vez de uma retomada.

Antes de redefinir o cursor, pause todos os consumidores que compartilham o `paimon_keeper_path`, incluindo views materializadas atualizáveis, e aguarde a conclusão das leituras in-flight.

O commit de uma leitura depende do cursor que ela observou. Se o cursor mudar depois dessa observação, mas antes do commit, a leitura falha com `INVALID_STATE`, não entrega nada e preserva o valor que você definiu. Uma leitura que já tenha feito commit ainda pode entregar seu lote depois que o cursor for redefinido; nesse caso, retroceder o cursor pode fazer com que esse lote seja entregue novamente.

Não exclua nem substitua o `processing_lock` manualmente. Trata-se de um nó efêmero pertencente à sessão do ClickHouse Keeper que está executando a leitura incremental; seu ciclo de vida não é uma interface de recuperação a ser manipulada pelo operador.

### Quando um snapshot não pode ser lido {#when-a-snapshot-cannot-be-read}

Snapshots expirados pelo Paimon são ignorados automaticamente: a expiração remove um prefixo dos IDs de snapshot, então sabe-se que tudo abaixo do snapshot mais antigo do warehouse já não existe, e o cursor avança além deles.

Qualquer outra falha ao ler um snapshot — um erro transitório do armazenamento de objetos, um arquivo de snapshot corrompido — faz a consulta falhar e mantém o cursor onde está. Propositalmente, não existe nenhuma configuração para tolerar isso. Ignorar um snapshot não lido significa remover permanentemente os dados confirmados nele, e uma opção fixa de &quot;tolerar erros&quot; transformaria qualquer instabilidade de rede futura em perda silenciosa de dados. Como o cursor permanece inalterado, um erro transitório não exige nenhuma intervenção: a próxima consulta relê o mesmo intervalo e é bem-sucedida.

Se um snapshot for realmente ilegível e o stream precisar avançar, abandone-o explicitamente. A mensagem de erro indica o comando, mas atenção ao custo: como a leitura com falha não entregou nada, mover o cursor para o snapshot ilegível abandona **todos** os snapshots ainda não consumidos até ele, inclusive ele mesmo — e não apenas o ilegível.

Com o cursor em 1 e os snapshots 2, 3 e 4 pendentes, sendo o 3 ilegível:

```bash
# Abandons snapshots 2 and 3; the next read resumes at 4.
clickhouse-keeper-client -q "set '/clickhouse/tables/<uuid>/committed_snapshot' '3'"
```

Para preservar os snapshots legíveis, primeiro faça o escoamento até o snapshot ilegível. Cada consulta consome um snapshot e avança o cursor, até chegar ao snapshot que não pode ser lido:

```sql
-- Delivers snapshot 2 and advances the cursor to 2; the next poll fails on 3 again.
SELECT * FROM paimon_inc SETTINGS max_consume_snapshots = 1;
```

```bash
# Now only snapshot 3 is abandoned.
clickhouse-keeper-client -q "set '/clickhouse/tables/<uuid>/committed_snapshot' '3'"
```

Em qualquer um dos casos, a decisão fica registrada como uma ação explícita do operador, em vez de ser inferida a partir de uma configuração.

## Paimon para MergeTree por meio de view materializada atualizável {#paimon-to-mergetree-via-refresh-mv}

Você pode criar um pipeline de ponta a ponta que sincroniza continuamente dados de uma tabela Paimon com uma tabela MergeTree usando uma view materializada atualizável no modo `APPEND`. Cada ciclo de atualização lê apenas novos dados incrementais do Paimon e os adiciona à tabela de destino.

**Etapa 1 — Crie a tabela de origem do Paimon com leitura incremental e atualização de metadados habilitadas.**

O exemplo abaixo usa `PaimonLocal`. Substitua o motor por `PaimonS3`, `PaimonAzure`, `PaimonHDFS` ou pelo motor `Paimon` com detecção automática, conforme apropriado para seu backend de armazenamento:

```sql
SET allow_experimental_paimon_storage_engine = 1;

-- Local storage
CREATE TABLE paimon_mv_source
ENGINE = PaimonLocal('/path/to/paimon/table')
SETTINGS
    paimon_incremental_read = 1,
    paimon_keeper_path = '/clickhouse/tables/{uuid}',
    paimon_replica_name = '{replica}',
    paimon_metadata_refresh_interval_sec = 1;

-- S3 storage (the `Paimon` engine defaults to the S3 implementation when no `disk` is specified)
CREATE TABLE paimon_mv_source
ENGINE = Paimon('http://minio:9000/bucket/path/to/table', 'access_key', 'secret_key')
SETTINGS
    paimon_incremental_read = 1,
    paimon_keeper_path = '/clickhouse/tables/{uuid}',
    paimon_replica_name = '{replica}',
    paimon_metadata_refresh_interval_sec = 1;
```

`paimon_metadata_refresh_interval_sec` define o intervalo, em segundos, de atualização de metadados em segundo plano. Quando é maior que 0, uma tarefa em segundo plano extrai periodicamente o `snapshot` e o esquema mais recentes do armazenamento de objetos, para que o ciclo de atualização da MV possa ver dados recém-confirmados sem esperar que uma consulta acione a atualização dos metadados. O padrão é 30. Use com cautela em muitas tabelas para evitar E/S excessiva no armazenamento de objetos e no Keeper.

**Etapa 2 — Crie a tabela de destino MergeTree (esquema clonado da tabela Paimon):**

```sql
CREATE TABLE paimon_mv_dest AS paimon_mv_source
ENGINE = MergeTree()
ORDER BY tuple();
```

**Etapa 3 — Crie a view materializada atualizável:**

```sql
CREATE MATERIALIZED VIEW paimon_mv
REFRESH EVERY 10 SECOND
APPEND
TO paimon_mv_dest
AS SELECT * FROM paimon_mv_source;
```

A cada 10 segundos, a MV executa um `SELECT * FROM paimon_mv_source`, que retorna apenas as linhas adicionadas desde o último snapshot confirmado e as adiciona a `paimon_mv_dest`.

**Limpeza:**

```sql
SYSTEM STOP VIEW paimon_mv;
DROP VIEW IF EXISTS paimon_mv SYNC;
DROP TABLE IF EXISTS paimon_mv_dest SYNC;
DROP TABLE IF EXISTS paimon_mv_source SYNC;
```

<Note>
  Interrompa a MV antes de removê-la para evitar que a atualização em segundo plano impeça operações de DDL.
</Note>

## Limitações {#limitations}

* A leitura incremental requer que o Keeper (ZooKeeper) esteja configurado.
* A leitura incremental requer que `paimon_keeper_path` esteja definido e seja único para cada tabela.
* `paimon_replica_name` deve ser único para cada réplica dentro do mesmo caminho do Keeper.
* A leitura incremental usa entrega com garantia de, no máximo, uma vez: o snapshot confirmado avança quando os arquivos de dados são coletados, antes de os dados serem efetivamente consumidos. Se a consulta falhar após a coleta dos arquivos, os snapshots ignorados não serão lidos novamente em uma nova tentativa.
* O motor de tabela é somente leitura; a modificação de dados não é suportada.
* A leitura incremental não lida com exclusões de dados históricos na origem Paimon. Se os dados de upstream do Paimon forem excluídos ou atualizados, as linhas correspondentes já gravadas em uma tabela de destino MergeTree no ClickHouse não serão removidas automaticamente. Você deve executar manualmente `ALTER TABLE ... DELETE` na tabela MergeTree para limpar dados desatualizados.
* Se a tabela Paimon subjacente for removida e recriada no mesmo caminho de armazenamento de objetos (por exemplo, via Flink ou Spark), você deverá executar `DROP` e `CREATE` novamente na tabela ClickHouse correspondente. O ClickHouse detecta a recriação comparando o timestamp de criação do schema-0 e gera um erro; a tabela ClickHouse desatualizada não poderá ser usada até ser recriada.

## Aliases {#aliases}

O `Paimon` motor de tabela detecta automaticamente o backend de armazenamento com base na configuração `disk` e direciona para `PaimonS3`, `PaimonAzure` ou `PaimonLocal`, conforme o caso. Quando nenhum `disk` é especificado, a implementação padrão é `PaimonS3`.

## Colunas virtuais {#virtual-columns}

* `_path` — Caminho do arquivo. Tipo: `LowCardinality(String)`.
* `_file` — Nome do arquivo. Tipo: `LowCardinality(String)`.
* `_size` — Tamanho do arquivo em bytes. Tipo: `Nullable(UInt64)`. Se o tamanho do arquivo for desconhecido, o valor será `NULL`.
* `_time` — Data e hora da última modificação do arquivo. Tipo: `Nullable(DateTime)`. Se a data e hora forem desconhecidas, o valor será `NULL`.
* `_etag` — O etag do arquivo. Tipo: `LowCardinality(String)`. Se o etag for desconhecido, o valor será `NULL`.
