Esta página descreve as instruções `KILL QUERY`, `KILL MUTATION`, `KILL TRANSACTION` e `KILL PART_MOVE_TO_SHARD`.

Por padrão, `KILL QUERY` lança uma exceção `NOTHING_TO_KILL` quando sua expressão `WHERE` não deixa nenhuma linha elegível em `system.processes` após a exclusão da própria instrução `KILL` atual, e `KILL MUTATION` lança uma exceção quando sua expressão `WHERE` não corresponde a nenhuma linha em `system.mutations`. Para permitir que a instrução retorne sem gerar uma exceção quando não houver correspondência, defina [`kill_throw_if_noop`](/pt-BR/operations/settings/settings#kill_throw_if_noop) como `false`.
`KILL TRANSACTION` e `KILL PART_MOVE_TO_SHARD` nunca lançam exceção quando não há correspondências: elas retornam um resultado vazio.
A execução com `ON CLUSTER` não lança exceção quando não há correspondências, pois os resultados não são agregados entre os hosts.

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

Tenta encerrar à força as consultas que estão em execução no momento.
As consultas a serem encerradas são selecionadas na tabela system.processes usando os critérios definidos na cláusula `WHERE` da consulta `KILL`.

Exemplos:

Primeiro, você precisará obter a lista de consultas incompletas. Esta consulta SQL as retorna em ordem das que estão em execução há mais tempo:

Lista de um único nó do ClickHouse:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Lista de um cluster do ClickHouse:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Encerre a consulta:

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  Se você estiver encerrando uma consulta no ClickHouse Cloud ou em um cluster autogerenciado, use a opção `ON CLUSTER [cluster-name]` para garantir que a consulta seja encerrada em todas as réplicas
</Tip>

Usuários com acesso somente leitura só podem interromper as próprias consultas.

Um usuário sem a concessão `SELECT` em `system.processes` ainda pode cancelar a própria consulta informando seu identificador:
`KILL QUERY WHERE query_id = '<id>'`. Se o usuário não tiver essa concessão nem `KILL QUERY`, informar um identificador de consulta
que não esteja em execução em seu nome não cancela nenhuma consulta e, por padrão, lança uma exceção `NOTHING_TO_KILL`. Com
[`kill_throw_if_noop`](/pt-BR/operations/settings/settings#kill_throw_if_noop) definido como `false`, nenhuma linha é retornada;
já um usuário com `KILL QUERY`, mas sem essa concessão `SELECT`, tem a solicitação recusada por falta do `SELECT`.
Qualquer outra condição `WHERE`, assim como `ON CLUSTER`, continua exigindo as concessões descritas acima.

Por padrão, é usada a versão assíncrona das consultas (`ASYNC`), que não espera a confirmação de que as consultas foram interrompidas.

A versão síncrona (`SYNC`) aguarda a interrupção de todas as consultas e exibe informações sobre cada processo à medida que ele é interrompido.
A resposta contém a coluna `kill_status`, que pode assumir os seguintes valores:

1. `finished` – A consulta foi encerrada com sucesso.
2. `waiting` – Aguardando a consulta terminar após o envio de um sinal para encerrá-la.
3. Os outros valores explicam por que a consulta não pode ser interrompida.

Uma consulta de teste (`TEST`) apenas verifica as permissões do usuário e exibe uma lista de consultas a serem interrompidas.

## KILL MUTATION {#kill-mutation}

A presença de mutações de longa duração ou incompletas geralmente indica que um serviço do ClickHouse está com baixo desempenho. A natureza assíncrona das mutações pode fazer com que elas consumam todos os recursos disponíveis de um sistema. Pode ser necessário:

* Pausar todas as novas mutações, `INSERT`s e `SELECT`s e aguardar a conclusão da fila de mutações.
* Ou encerrar manualmente algumas dessas mutações enviando um comando `KILL`.

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

Tenta cancelar e remover [mutações](/pt-BR/reference/statements/alter/index#mutations) que estão em execução no momento. As mutações a cancelar são selecionadas na tabela [`system.mutations`](/pt-BR/reference/system-tables/mutations) usando o filtro especificado pela cláusula `WHERE` da consulta `KILL`.

Uma consulta de teste (`TEST`) apenas verifica as permissões do usuário e exibe uma lista das mutações a serem interrompidas.

Exemplos:

Obtenha a `count()` de mutações incompletas:

Contagem de mutações em um único nó do ClickHouse:

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

Número de mutações em um cluster de réplicas do ClickHouse:

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

Consulte a lista de mutações incompletas:

Lista de mutações de um único nó do ClickHouse:

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

Lista de mutações de um cluster do ClickHouse:

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

Encerre as mutações conforme necessário:

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

A consulta é útil quando uma mutação fica travada e não consegue ser concluída (por exemplo, se alguma função na consulta da mutação lança uma exceção ao ser aplicada aos dados contidos na tabela).

As alterações já feitas pela mutação não são revertidas.

<Note>
  A coluna `is_killed=1` (apenas no ClickHouse Cloud) na tabela [system.mutations](/pt-BR/reference/system-tables/mutations) não significa necessariamente que a mutação tenha sido completamente finalizada. É possível que uma mutação permaneça por um longo período em um estado em que `is_killed=1` e `is_done=0`. Isso pode acontecer se outra mutação de longa duração estiver bloqueando a mutação encerrada. Essa é uma situação normal.
</Note>

## KILL TRANSACTION {#kill-transaction}

Introduzido em: v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  Esta instrução faz parte de um recurso experimental.
  Habilite o suporte experimental a transações adicionando esta configuração à sua [configuração](/pt-BR/concepts/features/configuration/server-config/configuration-files):

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  Para mais informações, consulte a página [Suporte transacional (ACID)](/pt-BR/concepts/features/operations/insert/transactions#transactions-commit-and-rollback).
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

Faz o rollback das [transações](/pt-BR/reference/statements/transactions) em execução selecionadas pela cláusula `WHERE` na tabela [`system.transactions`](/pt-BR/reference/system-tables/transactions).
A sessão de uma transação interrompida fica então no mesmo estado de uma sessão após uma consulta que falhou, conforme descrito em [`COMMIT`](/pt-BR/reference/statements/transactions#commit): até que `ROLLBACK` seja executado, `COMMIT` lança uma exceção `INVALID_TRANSACTION`.

A instrução requer o privilégio `KILL TRANSACTION` e o privilégio `SELECT` em `system.transactions`.
A resposta contém a coluna `kill_status`, cujo valor é `waiting` para uma transação que sofreu rollback, seguida pelas colunas `tid`, `tid_hash`, `elapsed`, `is_readonly` e `state` de `system.transactions`.

Uma consulta de teste (`TEST`) apenas verifica as permissões do usuário e exibe uma lista das transações que sofrerão rollback.

Exemplo:

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

Introduzido em: v21.11.0

<ExperimentalBadge />

<Note>
  A movimentação de partes entre shards é uma funcionalidade experimental, habilitada por tabela por meio da configuração do MergeTree [`part_moves_between_shards_enable`](/pt-BR/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable).
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

Cancela as movimentações de partes entre shards, iniciadas por `ALTER TABLE ... MOVE PART ... TO SHARD`, que forem selecionadas na tabela [`system.part_moves_between_shards`](/pt-BR/reference/system-tables/part_moves_between_shards) pela cláusula `WHERE`.
Uma movimentação cancelada é revertida em segundo plano, e seu `state` em `system.part_moves_between_shards` passa a ser `CANCELLED`.
Uma movimentação que já atingiu o estado `SOURCE_DROP` não pode mais ser cancelada e é executada até o fim.

A instrução requer `SELECT` em `system.part_moves_between_shards` e, para cancelar uma movimentação, o privilégio `ALTER MOVE PARTITION` na tabela correspondente e o privilégio `MOVE PARTITION BETWEEN SHARDS`.
Com `ON CLUSTER`, a instrução requer ambos os privilégios de movimentação em `*.*`.
A resposta contém a coluna `kill_status`, cujo valor é `waiting` para uma movimentação cancelada e `cant_cancel` para uma movimentação que não pode mais ser cancelada, seguida pelas colunas `database`, `table`, `task_name`, `task_uuid`, `part_name`, `to_shard` e `state` de `system.part_moves_between_shards`.

Uma consulta de teste (`TEST`) apenas exibe a lista de movimentações a serem canceladas. O modificador `SYNC` não é suportado e lança uma exceção `NOT_IMPLEMENTED`.

Exemplo:

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
