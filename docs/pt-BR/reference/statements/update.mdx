A instrução `UPDATE` leve atualiza linhas em uma tabela `[db.]table` que correspondem à expressão `filter_expr`.
Ela é chamada de &quot;atualização leve&quot; em contraste com a consulta [`ALTER TABLE ... UPDATE`](/pt-BR/reference/statements/alter/update), que é um processo pesado que reescreve colunas inteiras nas partes de dados.
Ela está disponível apenas para a família de motores de tabela [`MergeTree`](/pt-BR/reference/engines/table-engines/mergetree-family/mergetree).

```sql
UPDATE [db.]table [ON CLUSTER cluster] SET column1 = expr1 [, ...] [IN PARTITION partition_expr] WHERE filter_expr;
```

O `filter_expr` deve ser do tipo `UInt8`. Esta consulta atualiza os valores das colunas especificadas para os valores das expressões correspondentes nas linhas em que o `filter_expr` assume um valor não zero.
Os valores são convertidos para o tipo da coluna usando o operador `CAST`. Não há suporte para a atualização de colunas usadas no cálculo das chaves primária ou de partição.

<div id="examples">
  ## Exemplos
</div>

```sql
UPDATE hits SET Title = 'Updated Title' WHERE EventDate = today();

UPDATE wikistat SET hits = hits + 1, time = now() WHERE path = 'ClickHouse';
```

<div id="lightweight-update-does-not-update-data-immediately">
  ## As atualizações leves não atualizam os dados imediatamente
</div>

O `UPDATE` leve é implementado usando **patch parts** — um tipo especial de parte de dados que contém apenas as colunas e linhas atualizadas.
Um `UPDATE` leve cria patch parts, mas não modifica fisicamente os dados originais no armazenamento de imediato.
O processo de atualização é semelhante ao de uma consulta `INSERT ... SELECT ...`, mas a consulta `UPDATE` aguarda a conclusão da criação da patch part antes de retornar.

Os valores atualizados são:

* **Imediatamente visíveis** em consultas `SELECT` por meio da aplicação de patches
* **Materializados fisicamente** apenas durante mesclagens e mutações subsequentes
* **Removidos automaticamente** assim que todas as partes ativas tiverem os patches materializados

<div id="lightweight-update-requirements">
  ## Requisitos para atualizações leves
</div>

As atualizações leves são suportadas pelos motores [`MergeTree`](/pt-BR/reference/engines/table-engines/mergetree-family/mergetree), [`ReplacingMergeTree`](/pt-BR/reference/engines/table-engines/mergetree-family/replacingmergetree), [`CollapsingMergeTree`](/pt-BR/reference/engines/table-engines/mergetree-family/collapsingmergetree), [`VersionedCollapsingMergeTree`](/pt-BR/reference/engines/table-engines/mergetree-family/versionedcollapsingmergetree) e por suas versões [`Replicated`](/pt-BR/reference/engines/table-engines/mergetree-family/replication) e [`Shared`](/pt-BR/products/cloud/features/infrastructure/shared-merge-tree).

Para usar atualizações leves, a materialização das colunas `_block_number` e `_block_offset` deve estar habilitada por meio das configurações da tabela [`enable_block_number_column`](/pt-BR/reference/settings/merge-tree-settings/enable-block#enable_block_number_column) e [`enable_block_offset_column`](/pt-BR/reference/settings/merge-tree-settings/enable-block#enable_block_offset_column).

<div id="lightweight-delete">
  ## Exclusões leves
</div>

Uma consulta de [`DELETE` leve](/pt-BR/reference/statements/delete) pode ser executada como um `UPDATE` leve em vez de uma mutação `ALTER UPDATE`. A implementação de `DELETE` leve é controlada pela configuração [`lightweight_delete_mode`](/pt-BR/reference/settings/session-settings/lightweight#lightweight_delete_mode).

<div id="performance-considerations">
  ## Considerações de desempenho
</div>

**Vantagens das atualizações leves:**

* A latência da atualização é comparável à latência da consulta `INSERT ... SELECT ...`
* Apenas as colunas e os valores atualizados são gravados, e não colunas inteiras nas partes de dados
* Não é necessário esperar a conclusão das mesclagens/mutações em execução no momento; portanto, a latência de uma atualização é previsível
* É possível executar atualizações leves em paralelo

**Possíveis impactos no desempenho:**

* Adiciona sobrecarga às consultas `SELECT` que precisam aplicar patches
* [Índices de skipping](/pt-BR/reference/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-data_skipping-indexes) não serão usados para colunas em partes de dados que tenham patches a serem aplicados. [Projeções](/pt-BR/reference/engines/table-engines/mergetree-family/mergetree#projections) não serão usadas se houver partes de patch para a tabela, inclusive para partes de dados que não tenham patches a serem aplicados.
* Atualizações pequenas, se frequentes demais, podem levar ao erro &quot;too many parts&quot;. Recomenda-se agrupar várias atualizações em uma única consulta, por exemplo, colocando os IDs a serem atualizados em uma única cláusula `IN` na cláusula `WHERE`
* As atualizações leves foram projetadas para atualizar pequenas quantidades de linhas (até cerca de 10% da tabela). Se você precisar atualizar uma quantidade maior, recomenda-se usar a mutação [`ALTER TABLE ... UPDATE`](/pt-BR/reference/statements/alter/update)

<div id="concurrent-operations">
  ## Operações concorrentes
</div>

As atualizações leves não esperam a conclusão de mesclagens/mutações em execução, ao contrário das mutações pesadas.
A consistência das atualizações leves concorrentes é controlada pelas configurações [`update_sequential_consistency`](/pt-BR/reference/settings/session-settings/update#update_sequential_consistency) e [`update_parallel_mode`](/pt-BR/reference/settings/session-settings/update#update_parallel_mode).

<div id="update-permissions">
  ## Permissões de `UPDATE`
</div>

`UPDATE` requer o privilégio `ALTER UPDATE`. Para habilitar instruções `UPDATE` em uma tabela específica para um determinado usuário, execute:

```sql
GRANT ALTER UPDATE ON db.table TO username;
```

<div id="details-of-the-implementation">
  ## Detalhes da implementação
</div>

As patch parts são iguais às partes regulares, mas contêm apenas as colunas atualizadas, as colunas da chave de ordenação da tabela e as seguintes colunas de sistema:

* `_part` - o nome da parte original
* `_block_number` - o número do bloco da linha na parte original
* `_block_offset` - o offset do bloco da linha na parte original
* `_data_version` - a versão dos dados atualizados (número do bloco alocado para a consulta `UPDATE`)

As colunas de sistema ajudam a localizar as linhas na parte original que devem ser atualizadas.
Elas estão relacionadas às [colunas virtuais](/pt-BR/reference/engines/table-engines/mergetree-family/mergetree#virtual-columns) na parte original e são adicionadas durante a leitura quando as patch parts precisam ser aplicadas.
As patch parts são ordenadas pela chave de ordenação da tabela, com as colunas `_block_number` e `_block_offset` acrescentadas a ela.
A sobrecarga de armazenamento por linha atualizada depende do tamanho dos valores das colunas da chave de ordenação.

As patch parts pertencem a partições diferentes da parte original.
O ID da partição da patch part é `patch-<hash of the patch part structure>-<original_partition_id>`.
Portanto, patch parts com colunas diferentes são armazenadas em partições diferentes.
Por exemplo, três atualizações `SET x = 1 WHERE <cond>`, `SET y = 1 WHERE <cond>` e `SET x = 1, y = 1 WHERE <cond>` criarão três patch parts em três partições diferentes.

As patch parts podem ser mescladas entre si para reduzir a quantidade de patches aplicados em consultas `SELECT` e diminuir a sobrecarga. A mesclagem de patch parts usa o algoritmo de merge [ReplacingMergeTree](/pt-BR/reference/engines/table-engines/mergetree-family/replacingmergetree), com `_data_version` como coluna de versão.
Portanto, as patch parts sempre armazenam a versão mais recente de cada linha atualizada na parte.

Uma patch part é aplicada ao mesclá-la com a parte de dados pela chave de ordenação da tabela: uma linha é atualizada se os valores das colunas da chave de ordenação e das colunas `_block_number` e `_block_offset` forem iguais na parte de dados e na patch part.
A aplicação de patch parts exige a leitura das colunas da chave de ordenação da parte de dados, mesmo que a consulta não as selecione.
O uso de memória para aplicar uma patch part é limitado pelo maior intervalo de linhas com valores iguais da chave de ordenação.

<div id="patch-parts-format-in-mixed-version-clusters">
  ### Formato das patch parts em clusters com versões mistas
</div>

O formato das patch parts recém-gravadas é controlado pela configuração [`patch_parts_version`](/pt-BR/reference/settings/merge-tree-settings), definida no nível da tabela.
Versões do ClickHouse anteriores à 26.8 oferecem suporte apenas ao formato legado `v1` e não conseguem ler patch parts no formato atual `v2` descrito acima.
Durante uma atualização gradual a partir de uma dessas versões, continue gravando no formato `v1` até que todas as réplicas sejam atualizadas: defina `patch_parts_version = 'v1'` para tabelas com atualizações leves ou defina a configuração [`compatibility`](/pt-BR/reference/settings/session-settings/compatibility#compatibility) para a versão da qual está fazendo upgrade.
Após a conclusão do upgrade, remova a substituição para começar a gravar patch parts no formato `v2`.
As patch parts de ambos os formatos continuam legíveis e aplicáveis, independentemente do valor da configuração.
