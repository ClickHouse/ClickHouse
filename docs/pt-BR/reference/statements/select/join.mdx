A cláusula `JOIN` produz uma nova tabela ao combinar colunas de uma ou mais tabelas com base em valores em comum entre elas. É uma operação comum em bancos de dados com suporte a SQL, correspondente à operação de junção da [álgebra relacional](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators). O caso especial de uma junção de uma tabela com ela mesma costuma ser chamado de &quot;self-join&quot;.

**Sintaxe**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

Expressões da cláusula `ON` e colunas da cláusula `USING` são chamadas de &quot;chaves de JOIN&quot;. Salvo indicação em contrário, um `JOIN` produz um [produto cartesiano](https://en.wikipedia.org/wiki/Cartesian_product) entre linhas com chaves de JOIN correspondentes, o que pode gerar resultados com muito mais linhas do que as tabelas de origem.

Esta página descreve a sintaxe e a semântica da cláusula `JOIN`. Para saber mais sobre a execução de JOINs no ClickHouse, tipos de JOIN, configurações, considerações de memória e otimizações, consulte [Conteúdo relacionado](#related-content).

## Tipos de JOIN suportados {#supported-types-of-join}

Todos os tipos padrão de [SQL JOIN](https://en.wikipedia.org/wiki/Join_\(SQL\)) são suportados:

| Tipo               | Descrição                                                                                                                                                                                                                                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | Retorna apenas as linhas correspondentes.                                                                                                                                                                                                                                                                             |
| `LEFT OUTER JOIN`  | Retorna as linhas não correspondentes da tabela à esquerda, além das linhas correspondentes.                                                                                                                                                                                                                          |
| `RIGHT OUTER JOIN` | Retorna as linhas não correspondentes da tabela à direita, além das linhas correspondentes.                                                                                                                                                                                                                           |
| `FULL OUTER JOIN`  | Retorna as linhas não correspondentes de ambas as tabelas, além das linhas correspondentes.                                                                                                                                                                                                                           |
| `CROSS JOIN`       | Produz o produto cartesiano das tabelas inteiras. As chaves de JOIN **não** são especificadas.                                                                                                                                                                                                                        |
| `NATURAL JOIN`     | Faz a junção automaticamente em todas as colunas com o mesmo nome em ambas as tabelas. Cada coluna em comum aparece uma única vez no resultado. Suporta as variantes `INNER` (padrão), `LEFT`, `RIGHT` e `FULL`. Equivale a `JOIN ... USING (col1, col2, ...)`, em que a lista de colunas é derivada automaticamente. |

* `JOIN` sem tipo especificado implica `INNER`.
* A palavra-chave `OUTER` pode ser omitida.
* Uma sintaxe alternativa para `CROSS JOIN` é especificar várias tabelas na [cláusula `FROM`](/pt-BR/reference/statements/select/from), separadas por vírgulas.
* Se não houver colunas correspondentes para um `NATURAL JOIN`, ele funciona como um `CROSS JOIN`.

Os tipos adicionais de JOIN disponíveis no ClickHouse são:

| Tipo                                                | Descrição                                                                                                                                                                                                                                 |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | Uma lista de permissão nas chaves de JOIN, sem produzir um produto cartesiano.                                                                                                                                                            |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | Uma lista de bloqueio nas chaves de JOIN, sem produzir um produto cartesiano.                                                                                                                                                             |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | Desabilita parcialmente (para o lado oposto de `LEFT` e `RIGHT`) ou completamente (para `INNER`) o produto cartesiano dos tipos padrão de `JOIN`. `ANY FULL JOIN` não é suportado.                                                        |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | Junção de sequências com correspondência não exata. Consulte [Uso de ASOF JOIN](#asof-join-usage).                                                                                                                                        |
| `PASTE JOIN`                                        | Executa uma concatenação horizontal de duas tabelas. Consulte [Uso de PASTE JOIN](#paste-join-usage).                                                                                                                                     |
| `INNER JOIN LATERAL`, `LEFT JOIN LATERAL`           | Faz a junção de uma subconsulta que referencia colunas das tabelas à sua esquerda. Experimental; requer [`enable_lateral_join`](/pt-BR/reference/settings/session-settings/enable#enable_lateral_join). Consulte [LATERAL JOIN](#lateral-join). |

Diagramas de cada tipo de JOIN e rigor são mostrados em [Usando JOINs no ClickHouse](/pt-BR/concepts/features/operations/select/joining-tables#join-types-and-strictness).

<Note>
  Desabilitar a configuração `semi_join_include_columns_from_both_sides` ou `anti_join_include_columns_from_both_sides` faz com que a junção correspondente exponha apenas o seu lado preservado às expressões resolvidas após a formação do resultado do JOIN.

  * `LEFT SEMI JOIN` e `LEFT ANTI JOIN` expõem apenas as colunas do lado esquerdo.
  * `RIGHT SEMI JOIN` e `RIGHT ANTI JOIN` expõem apenas as colunas do lado direito.
  * Isso afeta cláusulas como `SELECT`, `PREWHERE`, `WHERE`, `GROUP BY`, `HAVING`, `QUALIFY`, `ORDER BY` e `LIMIT BY`, incluindo curingas qualificados como `t1.*`.
  * A expressão `ON` do mesmo `JOIN` ainda pode referenciar ambos os lados.

  Quando essas configurações estão habilitadas (o padrão), o ClickHouse mantém o comportamento legado, em que ambos os lados permanecem acessíveis e `SELECT *` expande as colunas de ambas as tabelas.
</Note>

Nem todo algoritmo de JOIN suporta todas as combinações de tipo de JOIN e rigor. As combinações suportadas estão listadas em [Tipos de JOIN suportados por algoritmo](/pt-BR/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).

### Reescrita de `CROSS JOIN` como `INNER JOIN` {#cross-join-rewrite}

Quando a cláusula `WHERE` de uma consulta que usa um `CROSS JOIN` ou uma lista de tabelas separadas por vírgula contém condições de igualdade entre as tabelas, o ClickHouse pode reescrever o JOIN como um `INNER JOIN` que usa essas condições como chaves de junção. A configuração [`cross_to_inner_join_rewrite`](/pt-BR/reference/settings/session-settings/other#cross_to_inner_join_rewrite) controla essa reescrita:

* `0`: A reescrita está desabilitada.
* `1`: Uma lista de tabelas separadas por vírgula ou um `CROSS JOIN` é reescrito quando a cláusula `WHERE` contém uma condição de igualdade entre as tabelas. Caso contrário, o JOIN é executado como um `CROSS JOIN`.
* `2`: Igual a `1`, mas, se a consulta tiver uma cláusula `WHERE`, uma lista de tabelas separadas por vírgula que não possa ser reescrita faz a consulta falhar com o erro `INCORRECT_QUERY`. Um JOIN escrito com as palavras-chave `CROSS JOIN` que não possa ser reescrito é executado como um `CROSS JOIN`.

Com o valor `0`, a otimização do plano de consulta controlada por [`query_plan_merge_filter_into_join_condition`](/pt-BR/reference/settings/session-settings/query-plan#query_plan_merge_filter_into_join_condition) ainda pode incorporar um filtro de igualdade ao JOIN e executá-lo como um `INNER JOIN`.

## Condições da seção ON {#on-section-conditions}

Uma seção `ON` pode conter várias condições combinadas com os operadores `AND` e `OR`. As condições que especificam chaves de JOIN devem:

* referenciar as tabelas da esquerda e da direita
* usar o operador de igualdade

Outras condições podem usar outros operadores e podem referenciar a tabela da esquerda, a da direita ou ambas as tabelas de uma consulta.

As linhas são combinadas se toda a condição composta for atendida. Se as condições não forem atendidas, as linhas ainda poderão ser incluídas no resultado, dependendo do tipo de `JOIN`. Se as mesmas condições forem colocadas em uma seção `WHERE` e não forem atendidas, as linhas sempre serão filtradas do resultado.

Chaves de JOIN combinadas com `OR` são compatíveis apenas com o algoritmo [`hash`](/pt-BR/concepts/features/operations/select/join-algorithms#hash), que cria uma tabela hash separada para cada argumento `OR` que contém chaves de JOIN.

<Note>
  Somente o operador de igualdade (`=`) torna uma condição uma chave de JOIN. Há suporte a outros operadores entre colunas de tabelas diferentes, mas, sem nenhuma igualdade, o JOIN precisa examinar cada par de linhas; consulte [JOIN com uma condição ON arbitrária](#join-with-an-arbitrary-on-condition).
</Note>

**Exemplo**

Considere `table_1` e `table_2`:

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

Consulta com uma condição na chave de JOIN e uma condição adicional para `table_2`:

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

O resultado contém a linha com o nome `C` e a coluna de texto vazia. Ela foi incluída no resultado porque foi usada uma junção do tipo `OUTER`.

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

Consulta com junção do tipo `INNER` e múltiplas condições:

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```response title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴────────┴────────┘
```

Consulta com junção do tipo `INNER` e condição com `OR`:

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

Consulta com `INNER` como tipo de junção e condições com `OR` e `AND`:

<Note>
  Uma condição de desigualdade que usa colunas de uma única tabela, como `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c`, é aplicada somente a essa tabela: `t1.b > 0` usa apenas colunas de `t1` e `t2.b > t2.c` usa apenas colunas de `t2`.
  Uma condição de desigualdade que compara colunas de tabelas diferentes, como `t1.a = t2.key AND t1.b > t2.key`, também é aceita; consulte as seções abaixo.
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## Junção com condições de desigualdade para colunas de tabelas diferentes {#join-with-inequality-conditions-for-columns-from-different-tables}

Além das condições de igualdade, a seção `ON` pode conter condições que comparam colunas de tabelas diferentes usando outros operadores. Essas condições são suportadas com rigor `ALL`, `ANY`, `SEMI` e `ANTI` para todo tipo de junção permitido por esse rigor. Elas não são suportadas com rigor `ASOF`.

Quando a seção `ON` contém, além da desigualdade, uma igualdade entre as duas tabelas, a igualdade atua como chave de junção e a desigualdade é verificada nas linhas que ela encontrou correspondência. Essa condição mista é executada pelos algoritmos [`hash`](/pt-BR/concepts/features/operations/select/join-algorithms#hash), [`parallel_hash`](/pt-BR/concepts/features/operations/select/join-algorithms#parallel-hash) e [`grace_hash`](/pt-BR/concepts/features/operations/select/join-algorithms#grace-hash). Quando [`ie_join`](/pt-BR/concepts/features/operations/select/join-algorithms#ie-join) aparece antes desses algoritmos em [`join_algorithm`](/pt-BR/reference/settings/session-settings/join#join_algorithm) e a seção `ON` contém duas condições de desigualdade, o `ie_join` executa a junção no lugar deles e aplica a igualdade como filtro.

Quando a seção `ON` não contém nenhuma igualdade entre as duas tabelas, não há chave de junção para fazer a correspondência. Essa junção é executada por [`ie_join`](/pt-BR/concepts/features/operations/select/join-algorithms#ie-join) quando a condição é um par de desigualdades ou, caso contrário, como uma [junção por laço aninhado em blocos](#join-with-an-arbitrary-on-condition).

Uma condição avaliada durante a junção não pode conter `arrayJoin`, pois deve preservar o número de linhas; em vez disso, use `ARRAY JOIN` em uma subconsulta.

**Exemplo**

Tabela `t1`:

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

Tabela `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response
key1    a    1    1    2    key1    B    2    1    2
key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
key1    e    5    5    5            0    0    \N
key2    a2    1    1    1            0    0    \N
key4    f    2    3    4            0    0    \N
```

## JOIN com uma condição ON arbitrária {#join-with-an-arbitrary-on-condition}

A seção `ON` pode ser uma expressão booleana arbitrária sobre as colunas de ambas as tabelas, como uma verificação de intervalo, uma comparação aritmética ou uma chamada a uma função escalar. Quando ela não contém nenhuma igualdade entre as duas tabelas, não há chave de JOIN para fazer a correspondência das linhas. Um par de condições de desigualdade é executado pelo `ie_join` sempre que esse algoritmo estiver listado em [`join_algorithm`](/pt-BR/reference/settings/session-settings/join#join_algorithm), sem precisar ser o primeiro da lista, porque nenhum outro valor de `join_algorithm` consegue executar esse tipo de condição. O valor default de `join_algorithm` inclui `ie_join` desde a versão 26.8. Qualquer outra condição é executada como uma [junção por laço aninhado em blocos](https://en.wikipedia.org/wiki/Nested_loop_join): a tabela da direita é materializada e a condição é avaliada para cada par de linhas. Um `ALL INNER JOIN` assume a forma equivalente de um `CROSS JOIN` com a condição atuando como filtro.

A junção por laço aninhado em blocos oferece suporte a todos os tipos de JOIN e níveis de rigor, exceto `ASOF JOIN`, `PASTE JOIN` e `ANY FULL JOIN`. Ela não é um dos valores de `join_algorithm`: trata-se do último recurso, usado apenas quando nenhum outro algoritmo consegue executar a condição. Na saída do `EXPLAIN`, ela aparece como um passo `BlockNestedLoopJoin`. Quando [`allow_block_nested_loop_join`](/pt-BR/reference/settings/session-settings/allow#allow_block_nested_loop_join) está desabilitado, uma consulta que dependa dela é rejeitada com `INVALID_JOIN_ON_EXPRESSION`.

**Exemplo**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

A linha que não teve correspondência é preenchida de acordo com [`join_use_nulls`](/pt-BR/reference/settings/session-settings/join#join_use_nulls), como em qualquer outro JOIN: com um valor default no exemplo acima e com `NULL` quando a configuração está habilitada.

**Rigor**

`ANY` e `SEMI` normalmente mantêm uma linha por grupo de linhas que compartilham uma chave de JOIN. Aqui não existe esse grupo, então elas mantêm uma linha por linha da tabela que conduz o JOIN: `LEFT ANY` e `LEFT SEMI` emitem cada linha da esquerda no máximo uma vez, e `RIGHT ANY` e `RIGHT SEMI`, cada linha da direita no máximo uma vez. `ANY INNER` limita os dois lados ao mesmo tempo: cada linha de qualquer uma das tabelas é usada no máximo uma vez, de modo que o resultado tem, no máximo, o mesmo número de linhas da tabela menor. Quais pares compõem esse resultado é algo arbitrário, exatamente como `ANY` sugere, e pode variar entre duas execuções da mesma consulta. No caso de `ANY INNER`, isso se estende ao número de linhas: emparelhar de forma gulosa cada linha dos dois lados, em qualquer ordem em que as linhas sejam examinadas, pode deixar um número diferente de linhas sem par. Portanto, o resultado de `count()` sobre um JOIN `ANY INNER` sem chave de JOIN não é reproduzível e depende do número de threads e da ordem física da tabela da direita.

**Desempenho**

Uma junção por laço aninhado em blocos examina todos os pares de linhas, então seu custo cresce com o produto das contagens de linhas das duas tabelas, conforme descrito em [Fallback para laço aninhado em blocos](/pt-BR/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback). A tabela da direita materializada está sujeita aos limites rígidos e aos limiares de spill descritos em [Gerenciamento de memória e spill em JOIN](/pt-BR/concepts/features/operations/select/join-memory-management).

## Valores NULL e NaN nas chaves de junção {#null-values-in-join-keys}

`NULL` não é igual a nenhum valor, nem a si mesmo. Se uma chave de junção tiver um valor `NULL` em uma tabela, ela não corresponderá a um valor `NULL` na outra tabela. Se as chaves de junção forem colunas [Nullable](/pt-BR/reference/data-types/nullable), uma linha em que pelo menos uma das chaves seja [NULL](/pt-BR/reference/syntax#null) não será incluída na junção.

**Exemplo**

Tabela `A`:

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

Tabela `B`:

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

A linha com `Charlie` da tabela `A` e a linha com pontuação 88 da tabela `B` não têm correspondência por causa do valor `NULL` na chave de junção.

As linhas sem correspondência recebem o valor `0` na coluna `score`, conforme descrito em [Processamento de células vazias ou NULL](#processing-of-empty-or-null-cells).

Para fazer a correspondência de valores `NULL`, compare as chaves de junção com a função `isNotDistinctFrom`:

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

Os valores `NaN` em chaves de junção de ponto flutuante não seguem a regra de `NULL` acima.
A comparação escalar de dois valores `NaN` (`NaN = NaN`) resulta em `0`. No entanto, as chaves de junção não são comparadas usando semântica escalar, e chaves `NaN` podem corresponder.
Se elas correspondem ou não é algo não especificado: depende do algoritmo de junção, do tipo de chave e das configurações da sessão.
Para impedir que chaves `NaN` correspondam, mapeie-as para valores `NULL`, por exemplo `ON if(isNaN(A.id), NULL, A.id) = B.id`.
Em um `ASOF JOIN`, a coluna de correspondência mais próxima é comparada por ordenação, que não é definida para valores `NaN`.

## Conversão implícita de tipos {#implicit-type-conversion}

Quando as chaves de JOIN da tabela à esquerda e da tabela à direita têm tipos diferentes, o ClickHouse as converte para o seu supertipo comum mínimo antes de compará-las. Isso se aplica a todos os tipos de JOIN e níveis de rigor:

* Com `ON`, a conversão se aplica apenas à comparação. As colunas de chave mantêm seus tipos originais no resultado.
* Com `USING`, a coluna mesclada fica com o tipo em comum no resultado. Quando `semi_join_include_columns_from_both_sides` ou `anti_join_include_columns_from_both_sides` está desabilitado, a coluna mesclada de um `SEMI JOIN` ou de um `ANTI JOIN` mantém o tipo da tabela preservada.

Se os tipos das chaves não tiverem um supertipo comum e ambos forem tipos inteiros ou tuplas de tipos inteiros, como no caso de `UInt64` e `Int64`, o ClickHouse converte ambas as chaves para um tipo capaz de comportar os valores que os dois tipos de chave têm em comum. Para `UInt64` e `Int64`, esse tipo é `UInt64`. Um valor da chave que não possa ser representado por esse tipo não corresponde a nenhum valor. Essa conversão é usada nas condições de igualdade em `ON`, exceto `isNotDistinctFrom`, e com `USING` em um `INNER JOIN` ou em um `SEMI JOIN`. Ela não é usada na condição de correspondência mais próxima de um `ASOF JOIN`, nas condições de desigualdade executadas por `ie_join` nem com `USING` em outros JOINs, pois a coluna de resultado deles também precisa comportar os valores sem correspondência. Essa conversão está disponível a partir da versão 26.9.

Se os tipos das chaves não tiverem um supertipo comum e essa conversão não se aplicar, como no caso de `String` e `Int32` ou de `UInt64` e `Float64`, a consulta falha com uma exceção, como `NO_COMMON_TYPE`.

**Exemplo**

Considere a tabela `t_1`:

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

e a tabela `t_2`:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

A consulta

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b) ORDER BY ALL;
```

retorna o conjunto:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## Uso do ASOF JOIN {#asof-join-usage}

`ASOF JOIN` combina registros que não têm correspondência exata. `ASOF` é um rigor de JOIN usado em conjunto com um JOIN `INNER` ou `LEFT`. Não é um algoritmo de junção.

Um `ASOF JOIN` exige uma coluna de correspondência mais próxima em ambas as tabelas. Essa coluna:

* Deve ter um tipo com uma ordem definida.
* Com o algoritmo [`hash`](/pt-BR/concepts/features/operations/select/join-algorithms#hash), pode ser dos seguintes tipos: [Int, UInt](/pt-BR/reference/data-types/int-uint), [Float](/pt-BR/reference/data-types/float), [Decimal](/pt-BR/reference/data-types/decimal), [Date](/pt-BR/reference/data-types/date), [Date32](/pt-BR/reference/data-types/date32), [DateTime](/pt-BR/reference/data-types/datetime), [DateTime64](/pt-BR/reference/data-types/datetime64), [Time](/pt-BR/reference/data-types/time), [Enum](/pt-BR/reference/data-types/enum), [Bool](/pt-BR/reference/data-types/boolean) e [Nullable](/pt-BR/reference/data-types/nullable) desses tipos. Outros tipos, como `String` e `Time64`, são rejeitados com o erro `BAD_TYPE_OF_FIELD`.
* Com o algoritmo [`full_sorting_merge`](/pt-BR/concepts/features/operations/select/join-algorithms#full-sorting-merge), também pode ser de outros tipos comparáveis, como `String`.
* Com o algoritmo `hash`, não pode ser a única coluna na cláusula `JOIN`. É necessária pelo menos uma condição de igualdade. O algoritmo `full_sorting_merge` não tem esse requisito.

Sintaxe `ASOF JOIN ... ON`:

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

Você pode usar qualquer número de condições de igualdade e exatamente uma condição de correspondência mais próxima. Por exemplo, `SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t`.

Condições aceitas para a correspondência mais próxima: `>`, `>=`, `<`, `<=`.

Sintaxe de `ASOF JOIN ... USING`:

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

`ASOF JOIN` usa `equi_columnX` para fazer a junção por igualdade e `asof_column` para fazer a junção pela correspondência mais próxima com a condição `table_1.asof_column >= table_2.asof_column`. A coluna `asof_column` é sempre a última na cláusula `USING`.

Por exemplo, considere as tabelas a seguir:

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

`ASOF JOIN` pode usar o `timestamp` de um evento de usuário de `table_1` e encontrar um evento em `table_2` cujo `timestamp` seja o mais próximo do `timestamp` do evento de `table_1`, de acordo com a condição de correspondência mais próxima. Valores de `timestamp` iguais são considerados os mais próximos, quando disponíveis. Aqui, a coluna `user_id` pode ser usada na junção por igualdade, e a coluna `ev_time` pode ser usada na junção pela correspondência mais próxima. No nosso exemplo, `event_1_1` pode ser unido a `event_2_1` e `event_1_2` pode ser unido a `event_2_3`, mas `event_2_2` não pode ser unido.

<Note>
  Entre os algoritmos de junção, apenas [`hash`](/pt-BR/concepts/features/operations/select/join-algorithms#hash) e [`full_sorting_merge`](/pt-BR/concepts/features/operations/select/join-algorithms#full-sorting-merge) são compatíveis com o rigor `ASOF`. Consulte [Tipos de JOIN compatíveis por algoritmo](/pt-BR/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).
  `ASOF` **não** é compatível com o motor de tabela [Join](/pt-BR/reference/engines/table-engines/special/join).
</Note>

## Uso do PASTE JOIN {#paste-join-usage}

O resultado de `PASTE JOIN` é uma tabela que contém todas as colunas da subconsulta à esquerda, seguidas de todas as colunas da subconsulta à direita.
As linhas são associadas com base em suas posições nas tabelas originais (a ordem das linhas deve estar definida).
Se as subconsultas retornarem números diferentes de linhas, as linhas excedentes serão descartadas.

Exemplo:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

Nota: neste caso, o resultado pode não ser determinístico se a leitura ocorrer em paralelo. Por exemplo:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## LATERAL JOIN {#lateral-join}

`JOIN LATERAL` permite que a subconsulta no lado direito de uma junção faça referência a colunas das expressões
de tabela à sua esquerda. O resultado é equivalente a avaliar a subconsulta para cada combinação distinta
dos valores das colunas do lado esquerdo que ela referencia e, em seguida, unir seu resultado a cada linha da esquerda que tenha essa combinação:

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

O predicado `ON true` é obrigatório, assim como em qualquer outro `INNER` ou `LEFT JOIN`; omiti-lo gera um erro de sintaxe.

Está disponível a partir da versão 26.10. É experimental e vem desabilitado por padrão; habilite-o com a configuração
[`enable_lateral_join`](/pt-BR/reference/settings/session-settings/enable#enable_lateral_join).

A subconsulta lateral não é executada uma vez por linha à esquerda nem uma vez por combinação distinta. Assim como outras subconsultas
correlacionadas, ela é descorrelacionada em uma única consulta sobre todas as linhas à esquerda: as colunas do lado esquerdo que ela referencia são
adicionadas às suas chaves de `GROUP BY` caso ela faça agregação, seu `LIMIT` (se houver) passa a ser `LIMIT ... BY` essas colunas, e seu
resultado é unido às linhas à esquerda por meio delas. Quando a correlação é uma igualdade simples, como `orders.user_id = u.id`,
a coluna do lado esquerdo pode ser substituída pela coluna equivalente da subconsulta
(`correlated_subqueries_substitute_equivalent_expressions`, habilitada por padrão), o que pode permitir que a subconsulta deixe de
ler as linhas à esquerda. Isso não é garantido: por exemplo, uma função agregada sem `GROUP BY` (como `count`) ainda
lê os valores distintos à esquerda para produzir seu resultado para os valores à esquerda sem linhas correspondentes. Sempre que os valores
distintos à esquerda são passados para a subconsulta, com as configurações padrão isso é feito por meio de um buffer em memória, e somente
quando esse buffer é de fato utilizado a junção é sempre uma hash join. Em todos os outros casos, como quando a substituição por
igualdade evita a leitura das linhas à esquerda ou quando o buffer está desabilitado
(`correlated_subqueries_use_in_memory_buffer = 0` ou `correlated_subqueries_default_join_kind = 'left'`), o
algoritmo é escolhido pela configuração `join_algorithm`. Por exemplo, o `EXPLAIN` de uma subconsulta lateral com `LIMIT`
mostra um passo `Join` sobre um passo `LimitBy (LIMIT BY for decorrelated correlated subquery)`; uma subconsulta sem
`LIMIT` não tem esse passo.

Por enquanto, apenas o seguinte subconjunto é compatível; qualquer outro caso é rejeitado com um erro:

* Somente `INNER JOIN LATERAL` e `LEFT JOIN LATERAL`; junções `RIGHT`, `FULL`, `PASTE` e `NATURAL` não são compatíveis, e `LATERAL` não pode, de forma alguma, ser combinado com uma junção `CROSS` ou por vírgula.
* Somente o rigor padrão `ALL`; `ANY`, `SEMI`, `ANTI` e `ASOF` não são compatíveis.
* Nenhum predicado de junção além de `ON true` (`ON 1` também é aceito); `USING` não é compatível, e o predicado
  não pode ser omitido. Coloque os filtros que relacionam os dois lados na cláusula `WHERE` da subconsulta lateral.
* Os modificadores de junção `GLOBAL` e `LOCAL` não são compatíveis.
* A subconsulta lateral deve referenciar pelo menos uma coluna do lado esquerdo. Para uma subconsulta não correlacionada,
  use uma junção comum.
* Como a subconsulta lateral é descorrelacionada, em vez de ser avaliada separadamente para cada valor do lado esquerdo, ela
  não deve conter funções não determinísticas dentro de uma consulta, como
  `rand` ou `generateUUIDv4`, nem funções de tabela que geram linhas aleatórias, como `generateRandom`.
  Funções que são constantes dentro de uma consulta, como `now`, são permitidas.
* Apenas uma subconsulta é compatível como expressão de tabela lateral. As formas de origem de tabela do PostgreSQL
  `LATERAL unnest(...)` e `CROSS JOIN UNNEST(...)` não são compatíveis. Em vez delas, use a cláusula
  [`ARRAY JOIN`](/pt-BR/reference/statements/select/array-join).
* O `GROUP BY` e o `ORDER BY` da subconsulta lateral são executados uma única vez para todos os valores do lado esquerdo em conjunto; assim, os
  limites `max_rows_to_group_by`, `max_rows_to_sort` e `max_bytes_to_sort` contabilizam as linhas de todos os valores do lado esquerdo,
  e não de apenas um. Eles só são compatíveis com o modo de estouro `throw`; `any` e `break` são rejeitados.
* O resultado da subconsulta descorrelacionada é associado às linhas do lado esquerdo por uma única junção. Como em qualquer hash join,
  `max_rows_in_join` e `max_bytes_in_join` limitam o lado dessa junção que é mantido em memória, e cabe ao
  planejador escolher esse lado: quando o buffer em memória descrito acima é de fato utilizado, é o lado esquerdo
  do `JOIN LATERAL`, pois as linhas do lado esquerdo precisam ser lidas por completo antes que a subconsulta lateral seja avaliada; caso contrário, pode ser o resultado da subconsulta descorrelacionada. Os limites são sempre
  aplicados como se `join_overflow_mode` fosse `throw`: com `break`, a junção descartaria silenciosamente linhas do lado esquerdo não relacionadas.

**Exemplo**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS enable_lateral_join = 1;
```

## JOIN distribuído {#distributed-join}

Há duas maneiras de executar um JOIN que envolve tabelas distribuídas:

* Ao usar um `JOIN` normal, a consulta é enviada aos servidores remotos. As subconsultas são executadas em cada um deles para montar a tabela da direita, e a junção é realizada com essa tabela. Em outras palavras, a tabela da direita é formada separadamente em cada servidor.
* Ao usar `GLOBAL ... JOIN`, primeiro o servidor solicitante executa uma subconsulta para calcular um dos lados da junção e armazena o resultado em uma tabela temporária. Essa tabela temporária é então enviada a cada servidor remoto, e as consultas são executadas neles usando os dados temporários transmitidos. Para junções `LEFT` e `INNER`, a tabela da direita é calculada pela subconsulta.

Para um `GLOBAL RIGHT JOIN` com rigor `ALL`, `ANY`, `SEMI` ou `ANTI` cuja tabela da esquerda seja uma tabela `Distributed` com mais de um shard, o ClickHouse inverte os dois lados e executa o JOIN como um `LEFT JOIN`, de modo que as linhas da tabela da direita preservada sejam retornadas uma única vez. A tabela da esquerda é então calculada pela subconsulta, e a tabela da direita é lida a partir dos seus shards, se for uma tabela `Distributed` com vários shards, ou, caso contrário, no servidor solicitante. Um `GLOBAL RIGHT JOIN` ou `GLOBAL FULL JOIN` que não possa ser invertido dessa forma é executado no servidor solicitante. Esse comportamento é válido a partir da versão 26.9.

Tenha cuidado ao usar `GLOBAL`. Para mais informações, consulte a seção [Subconsultas distribuídas](/pt-BR/reference/statements/in#distributed-subqueries).

## Processamento de células vazias ou NULL {#processing-of-empty-or-null-cells}

No resultado de um outer JOIN, as colunas da outra tabela ficam vazias nas linhas sem correspondência. A configuração [`join_use_nulls`](/pt-BR/reference/settings/session-settings/join#join_use_nulls) define como o ClickHouse preenche essas células:

* `0`: As células são preenchidas com o valor default do tipo da coluna.
* `1`: As células são preenchidas com `NULL`, e os tipos dessas colunas são convertidos para [Nullable](/pt-BR/reference/data-types/nullable). Uma coluna de um tipo que não pode ser encapsulado em `Nullable`, como `Array`, mantém seu tipo e é preenchida com o valor default. Em um `FULL` JOIN, a coluna `USING` mesclada também é convertida para `Nullable`.

Uma linha em que pelo menos uma das chaves de junção seja `NULL` não participa da junção, conforme descrito em [Valores NULL e NaN em chaves de junção](#null-values-in-join-keys).

## Cláusula USING {#using-clause}

A cláusula `USING` especifica uma ou mais colunas usadas na junção e estabelece a igualdade entre essas colunas:

* Cada coluna deve existir com o mesmo nome tanto na expressão de tabela à esquerda quanto na da direita. Aliases em subconsultas permitem atribuir o mesmo nome às colunas.
* A cláusula `USING` aceita apenas nomes de colunas. Expressões não são suportadas.
* A lista de colunas pode ser escrita com ou sem parênteses.
* Cada coluna da cláusula `USING` aparece uma única vez no resultado. Seu tipo é descrito em [Conversão implícita de tipo](#implicit-type-conversion).
* Outras colunas podem ter o mesmo nome em ambas as tabelas. `SELECT *` qualifica a coluna da right table com o nome ou alias da tabela, e um nome não qualificado é resolvido para a coluna da tabela à esquerda quando [`single_join_prefer_left_table`](/pt-BR/reference/settings/session-settings/other#single_join_prefer_left_table) está habilitado.
* Quando [`analyzer_compatibility_join_using_top_level_identifier`](/pt-BR/reference/settings/session-settings/analyzer-compatibility#analyzer_compatibility_join_using_top_level_identifier) está habilitado, um nome de coluna em `USING` é resolvido a partir de um alias de mesmo nome na consulta, como um alias na lista do `SELECT`.

## Exemplos {#examples}

A consulta a seguir faz a junção do número de hits por contador com o número de visits por contador. O `ANY LEFT JOIN` retorna cada linha da subconsulta à esquerda uma única vez, e um contador sem visitas recebe o valor default `0`:

```sql title="Query"
SELECT
    CounterID,
    hits,
    visits
FROM
(
    SELECT
        CounterID,
        count() AS hits
    FROM VALUES('CounterID UInt32', 1, 1, 1, 2, 2, 3)
    GROUP BY CounterID
) AS h
ANY LEFT JOIN
(
    SELECT
        CounterID,
        sum(Sign) AS visits
    FROM VALUES('CounterID UInt32, Sign Int8', (1, 1), (1, 1), (1, -1), (2, 1), (4, 1))
    GROUP BY CounterID
) AS v USING (CounterID)
ORDER BY hits DESC;
```

```response title="Response"
┌─CounterID─┬─hits─┬─visits─┐
│         1 │    3 │      1 │
│         2 │    2 │      1 │
│         3 │    1 │      0 │
└───────────┴──────┴────────┘
```
