A cláusula `JOIN` produz uma nova tabela ao combinar colunas de uma ou mais tabelas com base em valores em comum entre elas. É uma operação comum em bancos de dados com suporte a SQL, correspondente à operação de junção da [álgebra relacional](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators). O caso especial de uma junção de uma tabela com ela mesma costuma ser chamado de &quot;self-join&quot;.

**Sintaxe**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

Expressões da cláusula `ON` e colunas da cláusula `USING` são chamadas de &quot;chaves de junção&quot;. Salvo indicação em contrário, um `JOIN` produz um [produto cartesiano](https://en.wikipedia.org/wiki/Cartesian_product) entre linhas com &quot;chaves de junção&quot; correspondentes, o que pode gerar resultados com muito mais linhas do que as tabelas de origem.

## Tipos de JOIN suportados {#supported-types-of-join}

Todos os tipos padrão de [SQL JOIN](https://en.wikipedia.org/wiki/Join_\(SQL\)) são suportados:

| Tipo               | Descrição                                                                                                                                                                                                                                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | retorna apenas as linhas correspondentes.                                                                                                                                                                                                                                                                             |
| `LEFT OUTER JOIN`  | retorna as linhas não correspondentes da tabela à esquerda, além das linhas correspondentes.                                                                                                                                                                                                                          |
| `RIGHT OUTER JOIN` | retorna as linhas não correspondentes da tabela à direita, além das linhas correspondentes.                                                                                                                                                                                                                           |
| `FULL OUTER JOIN`  | retorna as linhas não correspondentes de ambas as tabelas, além das linhas correspondentes.                                                                                                                                                                                                                           |
| `CROSS JOIN`       | produz o produto cartesiano das tabelas inteiras; as **chaves de junção** **não** são especificadas.                                                                                                                                                                                                                  |
| `NATURAL JOIN`     | faz a junção automaticamente em todas as colunas com o mesmo nome em ambas as tabelas; cada coluna em comum aparece uma única vez no resultado. Suporta as variantes `INNER` (padrão), `LEFT`, `RIGHT` e `FULL`. Equivale a `JOIN ... USING (col1, col2, ...)`, em que a lista de colunas é derivada automaticamente. |

* `JOIN` sem tipo especificado implica `INNER`.
* A palavra-chave `OUTER` pode ser omitida com segurança.
* Uma sintaxe alternativa para `CROSS JOIN` é especificar várias tabelas na [cláusula `FROM`](/pt-BR/reference/statements/select/from), separadas por vírgulas.
* Se não houver colunas correspondentes para um `NATURAL JOIN`, ele funciona como um `CROSS JOIN`.

Os tipos adicionais de junção disponíveis no ClickHouse são:

| Tipo                                                | Descrição                                                                                                                                                  |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | Uma lista de permissão nas &quot;chaves de junção&quot;, sem produzir um produto cartesiano.                                                               |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | Uma lista de bloqueio nas &quot;chaves de junção&quot;, sem produzir um produto cartesiano.                                                                |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | Desabilita parcialmente (para o lado oposto de `LEFT` e `RIGHT`) ou completamente (para `INNER` e `FULL`) o produto cartesiano dos tipos padrão de `JOIN`. |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | Junção de sequências com correspondência não exata. O uso de `ASOF JOIN` é descrito abaixo.                                                                |
| `PASTE JOIN`                                        | Executa uma concatenação horizontal de duas tabelas.                                                                                                       |

<Note>
  Ao usar o analyzer, desabilitar a configuração `semi_join_include_columns_from_both_sides` ou `anti_join_include_columns_from_both_sides` faz com que a junção correspondente exponha apenas o seu lado preservado às expressões resolvidas após a formação do resultado do JOIN.

  * `LEFT SEMI JOIN` e `LEFT ANTI JOIN` expõem apenas as colunas do lado esquerdo.
  * `RIGHT SEMI JOIN` e `RIGHT ANTI JOIN` expõem apenas as colunas do lado direito.
  * Isso afeta cláusulas como `SELECT`, `PREWHERE`, `WHERE`, `GROUP BY`, `HAVING`, `QUALIFY`, `ORDER BY` e `LIMIT BY`, incluindo curingas qualificados como `t1.*`.
  * A expressão `ON` do mesmo `JOIN` ainda pode referenciar ambos os lados.

  Quando essas configurações estão habilitadas (o padrão), o ClickHouse mantém o comportamento legado, em que ambos os lados permanecem acessíveis e `SELECT *` expande as colunas de ambas as tabelas.
</Note>

<Note>
  Quando [join&#95;algorithm](/pt-BR/reference/settings/session-settings/join#join_algorithm) está definido como `partial_merge`, `RIGHT JOIN` e `FULL JOIN` são suportados apenas com o rigor `ALL` (`SEMI`, `ANTI`, `ANY` e `ASOF` não são suportados).
</Note>

## LATERAL JOIN {#lateral-join}

`JOIN LATERAL` permite que a subconsulta no lado direito de uma junção faça referência a colunas das expressões de tabela
à sua esquerda; a subconsulta é avaliada para cada combinação distinta dos valores das colunas do lado esquerdo
que ela referencia, e seu resultado é unido a todas as linhas da esquerda que tenham essa combinação:

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

O predicado `ON true` é obrigatório, assim como em qualquer outro `INNER` ou `LEFT JOIN`; omiti-lo gera um erro de sintaxe.

Trata-se de um recurso experimental e desabilitado por padrão; habilite-o com a configuração
[`allow_experimental_lateral_join`](/pt-BR/reference/settings/session-settings/allow-experimental#allow_experimental_lateral_join).

Por enquanto, apenas o subconjunto a seguir é compatível; qualquer outra forma é rejeitada com um erro:

* Somente `INNER JOIN LATERAL` e `LEFT JOIN LATERAL`; junções `RIGHT`, `FULL`, `PASTE` e `NATURAL` não são compatíveis, e `LATERAL` não pode, de forma alguma, ser combinado com uma junção `CROSS` ou por vírgula.
* Somente o rigor padrão `ALL`; `ANY`, `SEMI`, `ANTI` e `ASOF` não são compatíveis.
* Nenhum predicado de junção além de `ON true` (`ON 1` também é aceito); `USING` não é compatível, e o predicado
  não pode ser omitido. Coloque os filtros que relacionam os dois lados na cláusula `WHERE` da subconsulta lateral.
* Os modificadores de junção `GLOBAL` e `LOCAL` não são compatíveis.
* A subconsulta lateral deve referenciar pelo menos uma coluna do lado esquerdo. Para uma subconsulta não correlacionada,
  use uma junção comum.
* A subconsulta lateral é avaliada uma vez para cada valor distinto das colunas do lado esquerdo que ela referencia, e não
  uma vez por linha do lado esquerdo; portanto, ela não deve conter funções não determinísticas dentro de uma consulta, como
  `rand` ou `generateUUIDv4`, nem funções de tabela que geram linhas aleatórias, como `generateRandom`.
  Funções que são constantes dentro de uma consulta, como `now`, são permitidas.
* Apenas uma subconsulta é compatível como expressão de tabela lateral. As formas de origem de tabela do PostgreSQL
  `LATERAL unnest(...)` e `CROSS JOIN UNNEST(...)` não são compatíveis; em vez delas, use a cláusula
  [`ARRAY JOIN`](/pt-BR/reference/statements/select/array-join).
* O `GROUP BY` e o `ORDER BY` da subconsulta lateral são executados uma única vez sobre todas as avaliações em conjunto; assim, os
  limites `max_rows_to_group_by`, `max_rows_to_sort` e `max_bytes_to_sort` contabilizam as linhas de todas as avaliações,
  e não de apenas uma. Eles só são compatíveis com o modo de estouro `throw`; `any` e `break` são rejeitados.
* As linhas de todas as avaliações são associadas às linhas do lado esquerdo por uma única junção. Como em qualquer hash join,
  `max_rows_in_join` e `max_bytes_in_join` limitam o lado dessa junção que é mantido em memória, e cabe ao
  planejador escolher esse lado: com as configurações padrão (`correlated_subqueries_use_in_memory_buffer = 1`),
  é o lado esquerdo do `JOIN LATERAL`, pois as linhas do lado esquerdo precisam ser lidas por completo antes que a subconsulta
  lateral seja avaliada; caso contrário, podem ser os resultados de todas as avaliações em conjunto. Os limites são sempre
  aplicados como se `join_overflow_mode` fosse `throw`: com `break`, a junção descartaria silenciosamente linhas do lado esquerdo não relacionadas.

**Exemplo**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS allow_experimental_lateral_join = 1;
```

## Condições da seção ON {#on-section-conditions}

Uma seção `ON` pode conter várias condições combinadas com os operadores `AND` e `OR`. As condições que especificam chaves de junção devem:

* referenciar as tabelas da esquerda e da direita
* usar o operador de igualdade

Outras condições podem usar outros operadores e podem referenciar a tabela da esquerda, a da direita ou ambas as tabelas de uma consulta.

As linhas são combinadas se toda a condição composta for atendida. Se as condições não forem atendidas, as linhas ainda poderão ser incluídas no resultado, dependendo do tipo de `JOIN`. Observe que, se as mesmas condições forem colocadas em uma seção `WHERE` e não forem atendidas, as linhas sempre serão filtradas do resultado.

O operador `OR` dentro da cláusula `ON` funciona com o algoritmo de hash join — para cada argumento `OR` com chaves de junção para `JOIN`, é criada uma tabela hash separada; assim, o consumo de memória e o tempo de execução da consulta aumentam linearmente à medida que cresce o número de expressões `OR` na cláusula `ON`.

<Note>
  Somente o operador de igualdade (`=`) torna uma condição uma chave de junção. Há suporte a outros operadores entre colunas de tabelas diferentes, mas, sem nenhuma igualdade, a junção precisa examinar cada par de linhas e fica muito mais lenta; consulte [JOIN com uma condição ON arbitrária](#join-with-an-arbitrary-on-condition).
</Note>

**Exemplo**

Considere `table_1` e `table_2`:

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

Consulta com uma condição na chave de junção e uma condição adicional para `table_2`:

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

Observe que o resultado contém a linha com o nome `C` e a coluna de texto vazia. Ela foi incluída no resultado porque foi usada uma junção do tipo `OUTER`.

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

Consulta com junção do tipo `INNER` e múltiplas condições:

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```sql title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴────────┴────────┘
```

Consulta com junção do tipo `INNER` e condição com `OR`:

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

Consulta com `INNER` como tipo de junção e condições com `OR` e `AND`:

<Note>
  Uma condição de desigualdade que usa colunas de uma única tabela, como `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c`, é aplicada somente a essa tabela: `t1.b > 0` usa apenas colunas de `t1` e `t2.b > t2.c` usa apenas colunas de `t2`.
  Uma condição de desigualdade que compara colunas de tabelas diferentes, como `t1.a = t2.key AND t1.b > t2.key`, também é aceita; consulte as seções abaixo para mais detalhes.
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## Junção com condições de desigualdade para colunas de tabelas diferentes {#join-with-inequality-conditions-for-columns-from-different-tables}

O ClickHouse oferece suporte a `ALL/ANY/SEMI/ANTI INNER/LEFT/RIGHT/FULL JOIN` com condições de desigualdade, além das condições de igualdade.

Quando a seção `ON` contém, além da desigualdade, uma igualdade entre as duas tabelas, a igualdade atua como chave de junção e a desigualdade é verificada nas linhas que ela encontrou correspondência. Essa condição mista é executada apenas pelos algoritmos de junção `hash`, `parallel_hash` e `grace_hash`.

Quando a seção `ON` não contém nenhuma igualdade entre as duas tabelas, não há chave de junção para fazer a correspondência. Essa junção é executada por [`ie_join`](/pt-BR/reference/settings/session-settings/join#join_algorithm) quando a condição é um par de desigualdades ou, caso contrário, como uma [junção por laço aninhado em blocos](#join-with-an-arbitrary-on-condition).

Uma condição avaliada durante a junção não pode conter `arrayJoin`, pois deve preservar o número de linhas; em vez disso, use `ARRAY JOIN` em uma subconsulta.

**Exemplo**

Tabela `t1`:

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

Tabela `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response

key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
```

## JOIN com uma condição ON arbitrária {#join-with-an-arbitrary-on-condition}

A seção `ON` pode ser uma expressão booleana arbitrária sobre as colunas de ambas as tabelas, como uma verificação de intervalo, uma comparação aritmética ou uma chamada a uma função escalar. Quando ela não contém nenhuma igualdade entre as duas tabelas, não há chave de junção para fazer a correspondência das linhas. Um par de condições de desigualdade é executado pelo `ie_join` quando esse algoritmo está listado em [`join_algorithm`](/pt-BR/reference/settings/session-settings/join#join_algorithm), o que ocorre por padrão. Qualquer outra condição é executada como uma [junção por laço aninhado em blocos](https://en.wikipedia.org/wiki/Nested_loop_join): a tabela da direita é materializada e a condição é avaliada para cada par de linhas. Um `ALL INNER JOIN` assume a forma equivalente de um `CROSS JOIN` com a condição atuando como filtro.

A junção por laço aninhado em blocos oferece suporte a todos os tipos de junção e níveis de rigor, exceto `ASOF JOIN`, `PASTE JOIN` e `ANY FULL JOIN`. Ela não é um dos valores de `join_algorithm`: trata-se do último recurso, usado apenas quando nenhum outro algoritmo consegue executar a condição. Na saída do `EXPLAIN`, ela aparece como um passo `BlockNestedLoopJoin`. Quando [`allow_block_nested_loop_join`](/pt-BR/reference/settings/session-settings/allow#allow_block_nested_loop_join) está desabilitado, uma consulta que dependa dela é rejeitada com `INVALID_JOIN_ON_EXPRESSION`.

**Exemplo**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

A linha que não teve correspondência é preenchida de acordo com [`join_use_nulls`](/pt-BR/reference/settings/session-settings/join#join_use_nulls), como em qualquer outra junção: com um valor default no exemplo acima e com `NULL` quando a configuração está habilitada.

**Rigor**

`ANY` e `SEMI` normalmente mantêm uma linha por grupo de linhas que compartilham uma chave de junção. Aqui não existe esse grupo, então elas mantêm uma linha por linha da tabela que conduz a junção: `LEFT ANY` e `LEFT SEMI` emitem cada linha da esquerda no máximo uma vez, e `RIGHT ANY` e `RIGHT SEMI`, cada linha da direita no máximo uma vez. `ANY INNER` limita os dois lados ao mesmo tempo — cada linha de qualquer uma das tabelas é usada no máximo uma vez, de modo que o resultado tem, no máximo, o mesmo número de linhas da tabela menor. Quais pares compõem esse resultado é algo arbitrário, exatamente como `ANY` sugere, e pode variar entre duas execuções da mesma consulta. No caso de `ANY INNER`, isso se estende ao número de linhas: emparelhar de forma gulosa cada linha dos dois lados, em qualquer ordem em que as linhas sejam examinadas, pode deixar um número diferente de linhas sem par. Portanto, o resultado de `count()` sobre uma junção `ANY INNER` sem chave de junção não é reproduzível e depende do número de threads e da ordem física da tabela da direita.

**Desempenho**

Todos os pares de linhas são examinados, então o trabalho cresce com o *produto* das contagens de linhas das duas tabelas, e não com a sua soma. Por isso, uma junção por laço aninhado em blocos é ordens de grandeza mais cara do que um hash join sobre os mesmos dados, e a diferença aumenta à medida que as tabelas crescem. Se for possível escrever a consulta com pelo menos uma igualdade na seção `ON`, faça isso.

As junções `LEFT ANY`, `ANY INNER`, `LEFT SEMI` e `LEFT ANTI` param de varrer a tabela da direita ao encontrar a primeira linha correspondente a uma linha da esquerda, o que geralmente as torna mais baratas do que a junção `ALL` equivalente. Suas contrapartes conduzidas pela direita (`RIGHT ANY`, `RIGHT SEMI`, `RIGHT ANTI`) examinam todos os pares, porque o resultado depende de quais linhas da direita tiveram correspondência. [`join_any_take_last_row`](/pt-BR/reference/settings/session-settings/join#join_any_take_last_row) não tem efeito aqui: sem chave de junção, não há um grupo de linhas correspondentes do qual pegar a última.

O uso de memória é limitado pela tabela da direita materializada e não cresce com o tamanho do resultado. A tabela da direita está sujeita às mesmas configurações dos outros algoritmos de junção, listadas em [Limitações de memória](#memory-limitations): [`max_rows_in_join`](/pt-BR/reference/settings/session-settings/max-rows#max_rows_in_join), [`max_bytes_in_join`](/pt-BR/reference/settings/session-settings/max-bytes#max_bytes_in_join) e [`join_overflow_mode`](/pt-BR/reference/settings/session-settings/join#join_overflow_mode) a limitam, enquanto [`max_bytes_before_external_join`](/pt-BR/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) faz com que ela seja despejada (spill) para o disco.

## Valores NULL e NaN nas chaves de junção {#null-values-in-join-keys}

`NULL` não é igual a nenhum valor, nem a si mesmo. Isso significa que, se uma chave de junção tiver um valor `NULL` em uma tabela, ela não corresponderá a um valor `NULL` na outra tabela.

**Exemplo**

Tabela `A`:

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

Tabela `B`:

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

Observe que a linha com `Charlie` da tabela `A` e a linha com pontuação 88 da tabela `B` não aparecem no resultado por causa do valor `NULL` na chave de junção.

Caso você queira fazer a correspondência de valores `NULL`, use a função `isNotDistinctFrom` para comparar as chaves de junção.

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```markdown
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

Os valores `NaN` em chaves de junção de ponto flutuante não seguem a regra de `NULL` acima.
A comparação escalar de dois valores `NaN` (`NaN = NaN`) resulta em `0`; no entanto, as chaves de junção não são comparadas usando semântica escalar — chaves `NaN` podem corresponder.
Se isso de fato ocorre é um detalhe de implementação e depende do algoritmo de junção, do tipo de chave e das configurações da sessão.
Não dependa de um comportamento específico.
Se você precisar que linhas com `NaN` não correspondam, mapeie-as para valores `NULL`: `ON if(isNaN(A.id), NULL, A.id) = B.id`.
Em um `ASOF JOIN`, a coluna de correspondência mais próxima é comparada por ordenação, que `NaN` não suporta — filtre essas linhas em ambos os lados.

## Uso do ASOF JOIN {#asof-join-usage}

`ASOF JOIN` é útil quando você precisa combinar registros que não têm correspondência exata.

Este algoritmo de junção exige uma coluna especial nas tabelas. Essa coluna:

* Deve conter uma sequência ordenada.
* Pode ser de um dos seguintes tipos: [Int, UInt](/pt-BR/reference/data-types/int-uint), [Float](/pt-BR/reference/data-types/float), [Date](/pt-BR/reference/data-types/date), [DateTime](/pt-BR/reference/data-types/datetime), [Decimal](/pt-BR/reference/data-types/decimal).
* No algoritmo de junção `hash`, ela não pode ser a única coluna na cláusula `JOIN`.

Sintaxe `ASOF JOIN ... ON`:

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

Você pode usar qualquer número de condições de igualdade e exatamente uma condição de correspondência mais próxima. Por exemplo, `SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t`.

Condições aceitas para a correspondência mais próxima: `>`, `>=`, `<`, `<=`.

Sintaxe de `ASOF JOIN ... USING`:

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

`ASOF JOIN` usa `equi_columnX` para fazer a junção por igualdade e `asof_column` para fazer a junção pela correspondência mais próxima com a condição `table_1.asof_column >= table_2.asof_column`. A coluna `asof_column` é sempre a última na cláusula `USING`.

Por exemplo, considere as tabelas a seguir:

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

`ASOF JOIN` pode usar o `timestamp` de um evento de usuário de `table_1` e encontrar um evento em `table_2` cujo `timestamp` seja o mais próximo do `timestamp` do evento de `table_1`, de acordo com a condição de correspondência mais próxima. Valores de `timestamp` iguais são considerados os mais próximos, quando disponíveis. Aqui, a coluna `user_id` pode ser usada na junção por igualdade, e a coluna `ev_time` pode ser usada na junção pela correspondência mais próxima. No nosso exemplo, `event_1_1` pode ser unido a `event_2_1` e `event_1_2` pode ser unido a `event_2_3`, mas `event_2_2` não pode ser unido.

<Note>
  `ASOF JOIN` é compatível apenas com os algoritmos de junção `hash` e `full_sorting_merge`.
  **Não** é compatível com o mecanismo de tabela [Join](/pt-BR/reference/engines/table-engines/special/join).
</Note>

## Uso do PASTE JOIN {#paste-join-usage}

O resultado de `PASTE JOIN` é uma tabela que contém todas as colunas da subconsulta à esquerda, seguidas de todas as colunas da subconsulta à direita.
As linhas são associadas com base em suas posições nas tabelas originais (a ordem das linhas deve estar definida).
Se as subconsultas retornarem números diferentes de linhas, as linhas excedentes serão descartadas.

Exemplo:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

Nota: neste caso, o resultado pode não ser determinístico se a leitura ocorrer em paralelo. Por exemplo:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## JOIN distribuído {#distributed-join}

Há duas maneiras de executar um JOIN que envolve tabelas distribuídas:

* Ao usar um `JOIN` normal, a consulta é enviada aos servidores remotos. As subconsultas são executadas em cada um deles para montar a tabela da direita, e a junção é realizada com essa tabela. Em outras palavras, a tabela da direita é formada separadamente em cada servidor.
* Ao usar `GLOBAL ... JOIN`, primeiro o servidor solicitante executa uma subconsulta para calcular um dos lados da junção e armazena o resultado em uma tabela temporária. Essa tabela temporária é então enviada a cada servidor remoto, e as consultas são executadas neles usando os dados temporários transmitidos. Para junções `LEFT` e `INNER`, a tabela da direita é calculada pela subconsulta. Para junções `RIGHT`, a tabela da esquerda é calculada, já que a tabela da direita é a preservada e deve ser lida dos shards.

Tenha cuidado ao usar `GLOBAL`. Para mais informações, consulte a seção [Subconsultas distribuídas](/pt-BR/reference/statements/in#distributed-subqueries).

## Conversão implícita de tipos {#implicit-type-conversion}

Consultas `INNER JOIN`, `LEFT JOIN`, `RIGHT JOIN` e `FULL JOIN` oferecem suporte à conversão implícita de tipos para as &quot;chaves de junção&quot;. No entanto, a consulta não pode ser executada se as chaves de junção das tabelas à esquerda e à direita não puderem ser convertidas para um único tipo (por exemplo, não há nenhum tipo de dado que possa comportar todos os valores de `UInt64` e `Int64`, ou de `String` e `Int32`).

**Exemplo**

Considere a tabela `t_1`:

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

e a tabela `t_2`:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

A consulta

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b);
```

retorna o conjunto:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## Recomendações de uso {#usage-recommendations}

### Processamento de células vazias ou NULL {#processing-of-empty-or-null-cells}

Ao fazer `JOIN` entre tabelas, podem surgir células vazias. A configuração [join&#95;use&#95;nulls](/pt-BR/reference/settings/session-settings/join#join_use_nulls) define como o ClickHouse preenche essas células.

Se as chaves de `JOIN` forem campos [Nullable](/pt-BR/reference/data-types/nullable), as linhas em que pelo menos uma das chaves tem o valor [NULL](/pt-BR/reference/syntax#null) não são unidas.

### Sintaxe {#syntax}

As colunas especificadas em `USING` devem ter os mesmos nomes em ambas as subconsultas, e as demais colunas devem ter nomes diferentes. Você pode usar aliases para alterar os nomes das colunas nas subconsultas.

A cláusula `USING` especifica uma ou mais colunas para unir, estabelecendo a igualdade entre essas colunas. A lista de colunas é definida sem parênteses. Condições de junção mais complexas não são suportadas.

### Limitações de sintaxe {#syntax-limitations}

Para várias cláusulas `JOIN` em uma única consulta `SELECT`:

* Selecionar todas as colunas com `*` só é possível quando há junção entre tabelas, e não subconsultas.
* A cláusula `PREWHERE` não está disponível.
* A cláusula `USING` não está disponível.

Para as cláusulas `ON`, `WHERE` e `GROUP BY`:

* Não é possível usar expressões arbitrárias nas cláusulas `ON`, `WHERE` e `GROUP BY`, mas você pode definir uma expressão em uma cláusula `SELECT` e depois usá-la nessas cláusulas por meio de um alias.

### Desempenho {#performance}

Ao executar um `JOIN`, não há otimização da ordem de execução em relação às outras etapas da consulta. A junção (uma busca na tabela da direita) é executada antes da filtragem em `WHERE` e antes da agregação.

Sempre que uma consulta é executada com o mesmo `JOIN`, a subconsulta é executada novamente, porque o resultado não fica em cache. Para evitar isso, use o mecanismo de tabela especial [Join](/pt-BR/reference/engines/table-engines/special/join), que é um array pré-preparado para junções e permanece sempre na RAM.

Em alguns casos, é mais eficiente usar [IN](/pt-BR/reference/statements/in) em vez de `JOIN`.

Se você precisar de um `JOIN` para fazer junção com tabelas de dimensão (tabelas relativamente pequenas que contêm propriedades de dimensão, como nomes de campanhas publicitárias), um `JOIN` pode não ser muito prático, já que a tabela da direita é acessada novamente a cada consulta. Nesses casos, existe o recurso &quot;dicionários&quot;, que você deve usar em vez de `JOIN`. Para mais informações, consulte a seção [Dicionários](/pt-BR/reference/statements/create/dictionary).

### Limitações de memória {#memory-limitations}

Por padrão, o ClickHouse usa o algoritmo [hash join](https://en.wikipedia.org/wiki/Hash_join). O ClickHouse usa a `right_table` e cria uma tabela hash para ela na RAM. Se `join_algorithm = 'auto'` estiver habilitado, após determinado limite de consumo de memória, o ClickHouse passa a usar o algoritmo [merge](https://en.wikipedia.org/wiki/Sort-merge_join) de junção. Para obter uma descrição dos algoritmos de junção, consulte a configuração [join&#95;algorithm](/pt-BR/reference/settings/session-settings/join#join_algorithm).

Se você precisar restringir o consumo de memória da operação de junção `JOIN`, use as seguintes configurações:

* [max&#95;rows&#95;in&#95;join](/pt-BR/reference/settings/session-settings/max-rows#max_rows_in_join) — Limita o número de linhas na tabela hash.
* [max&#95;bytes&#95;in&#95;join](/pt-BR/reference/settings/session-settings/max-bytes#max_bytes_in_join) — Limita o tamanho da tabela hash.

Quando qualquer um desses limites é atingido, o ClickHouse age conforme instruído pela configuração [join&#95;overflow&#95;mode](/pt-BR/reference/settings/session-settings/join#join_overflow_mode). Esses dois são limites rígidos e nunca fazem uma junção realizar spill para disco, portanto defini-los no limiar de spill ou abaixo dele normalmente interrompe a consulta antes que ela possa fazer spill. Duas configurações mudam esse comportamento:
`enable_adaptive_memory_spill_scheduler` ainda pode fazer spill de uma junção que o limiar abaixo tornou
apta a spill, e
`legacy_join_size_limits_trigger_spilling` transforma os dois limites rígidos novamente em gatilhos de spill em disco.

Para permitir que uma junção continue executando, fazendo spill do lado direito para o disco em vez de falhar, use:

* [max&#95;bytes&#95;before&#95;external&#95;join](/pt-BR/reference/settings/session-settings/max-bytes#max_bytes_before_external_join) — Limiar absoluto de spill.
* [max&#95;bytes&#95;ratio&#95;before&#95;external&#95;join](/pt-BR/reference/settings/session-settings/max-bytes#max_bytes_ratio_before_external_join) — Limiar de spill como uma razão da memória disponível.

Esses são o gatilho de spill baseado em limiar para todo algoritmo baseado em hash, incluindo o `grace_hash`; sob pressão
de memória, `enable_adaptive_memory_spill_scheduler` pode fazer spill antes do que eles determinam — mas somente quando um
deles for diferente de zero, já que uma junção sem limiar algum nunca faz spill. O `join_algorithm` escolhido
determina como uma junção faz spill — o `grace_hash` particiona a tabela da direita desde o primeiro bloco, enquanto `hash` e `parallel_hash` a acumulam
em memória e mudam de estratégia quando o limiar é ultrapassado — e não se essas configurações se aplicam. A única exceção é
`legacy_join_size_limits_trigger_spilling`: com ela ativada, o `grace_hash` independente ignora ambos os limiares e faz spill com base nos dois limites rígidos.
