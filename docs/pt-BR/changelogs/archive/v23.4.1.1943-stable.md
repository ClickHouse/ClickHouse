<div id="new-feature">
  #### Novo recurso
</div>

* Adiciona a função `extractKeyValuePairs` para extrair pares chave-valor de strings. As strings de entrada podem conter ruído (ou seja, arquivos de log / não precisam estar 100% formatadas como pares chave-valor); o algoritmo buscará pares chave-valor correspondentes aos argumentos passados para a função. No momento, a função aceita os seguintes argumentos: `data_column` (obrigatório), `key_value_pair_delimiter` (o padrão é `:`), `pair_delimiters` (o padrão é `\space \, \;`) e `quoting_character` (o padrão são aspas duplas). [#43606](https://github.com/ClickHouse/ClickHouse/pull/43606) ([Arthur Passos](https://github.com/arthurpassos)).
* Adiciona o MemoryTracker para as tarefas em segundo plano (merges e mutações). Introduz as configurações `merges_mutations_memory_usage_soft_limit` e `merges_mutations_memory_usage_to_ram_ratio`, que representam o limite flexível de memória para merges e mutações. Se esse limite for atingido, o ClickHouse não agendará novas tarefas de merge ou mutação. Além disso, a métrica `MergesMutationsMemoryTracking` foi introduzida para permitir observar o uso atual de memória das tarefas em segundo plano. Fecha [#45710](https://github.com/ClickHouse/ClickHouse/issues/45710). [#46089](https://github.com/ClickHouse/ClickHouse/pull/46089) ([Dmitry Novik](https://github.com/novikd)).
* Adiciona suporte à nova função de agregação quantileGK/quantilesGK, semelhante a [approx&#95;percentile](https://spark.apache.org/docs/latest/api/sql/index.html#approx_percentile) no Spark. Para o algoritmo Greenwald-Khanna, consulte [http://infolab.stanford.edu/~datar/courses/cs361a/papers/quantiles.pdf](http://infolab.stanford.edu/~datar/courses/cs361a/papers/quantiles.pdf). [#46428](https://github.com/ClickHouse/ClickHouse/pull/46428) ([李扬](https://github.com/taiyang-li)).
* Adiciona a instrução `SHOW COLUMNS`, que exibe informações resumidas de system.columns. [#48017](https://github.com/ClickHouse/ClickHouse/pull/48017) ([Robert Schulze](https://github.com/rschu1ze)).
* Adiciona os modificadores `LIGHTWEIGHT` e `PULL` para a consulta `SYSTEM SYNC REPLICA`. A versão `LIGHTWEIGHT` espera apenas fetches e drop-ranges (merges e mutações são ignoradas). A versão `PULL` extrai novas entradas do ZooKeeper e não espera por elas. Corrige [#47794](https://github.com/ClickHouse/ClickHouse/issues/47794). [#48085](https://github.com/ClickHouse/ClickHouse/pull/48085) ([Alexander Tokmakov](https://github.com/tavplubix)).
* Adiciona a função kafkaMurmurHash para compatibilidade com o Kafka DefaultPartitioner. Fecha [#47834](https://github.com/ClickHouse/ClickHouse/issues/47834). [#48185](https://github.com/ClickHouse/ClickHouse/pull/48185) ([Nikolay Degterinsky](https://github.com/evillique)).

O valor é armazenado no ZooKeeper e pode ser usado em vez do evento de profile `ReplicatedDataLoss`, que não é persistente, para monitoramento. <div id="performance-improvement">
  #### Melhoria de desempenho
</div>

* A leitura de arquivos no formato Parquet agora está muito mais rápida. A E/S e a decodificação foram paralelizadas (controladas pela configuração `max_threads`), e apenas os intervalos de dados necessários são lidos. [#47964](https://github.com/ClickHouse/ClickHouse/pull/47964) ([Michael Kolupaev](https://github.com/al13n321)).
* Verifica as dependências apenas quando necessário ao aplicar consultas `ALTER TABLE`. [#48062](https://github.com/ClickHouse/ClickHouse/pull/48062) ([Raúl Marín](https://github.com/Algunenano)).
* Otimiza a função `mapUpdate`. [#48118](https://github.com/ClickHouse/ClickHouse/pull/48118) ([Anton Popov](https://github.com/CurtizJ)).
* Agora, uma consulta interna para a réplica local é enviada explicitamente, e os dados dela são recebidos pela interface de loopback. A configuração `prefer_localhost_replica` não é respeitada para réplicas paralelas. Isso é necessário para um melhor agendamento e deixa o código mais limpo: o iniciador fica responsável apenas por coordenar o processo de leitura e mesclar os resultados, respondendo continuamente às solicitações enquanto todas as consultas secundárias leem os dados. Observação: usar a interface de loopback não é tão eficiente em termos de desempenho; caso contrário, algumas réplicas poderiam ficar sem tarefas, o que poderia levar a uma execução de consulta ainda mais lenta e ao não aproveitamento de todos os recursos possíveis. A inicialização do coordinator agora é ainda mais adiada. Todas as solicitações de entrada contêm informações sobre o algoritmo de leitura; inicializamos o coordinator com elas quando a primeira solicitação chega. Se alguma réplica decidir ler com um algoritmo diferente, uma exceção será lançada e a consulta será abortada. [#48246](https://github.com/ClickHouse/ClickHouse/pull/48246) ([Nikita Mikhaylov](https://github.com/nikitamikhaylov)).
* Não constrói um Set para o lado direito da cláusula `IN` com subconsulta quando ele é usado apenas para analisar skip indexes e eles estão desabilitados pela configuração (`use_skip_indexes=0`). Anteriormente, isso podia afetar o desempenho das consultas. [#48299](https://github.com/ClickHouse/ClickHouse/pull/48299) ([Anton Popov](https://github.com/CurtizJ)).
* O processamento de consultas é paralelizado logo após a leitura de `FROM file(...)`. Relacionado a [#38755](https://github.com/ClickHouse/ClickHouse/issues/38755). [#48525](https://github.com/ClickHouse/ClickHouse/pull/48525) ([Igor Nikonov](https://github.com/devcrafter)).
* O processamento de consultas é paralelizado logo após a leitura de uma fonte de dados. As fontes de dados afetadas são, em sua maioria, armazenamentos externos ou fontes simples, como as funções de tabela `url` e `file`. [#48727](https://github.com/ClickHouse/ClickHouse/pull/48727) ([Igor Nikonov](https://github.com/devcrafter)).
* Usa a ordenação de memória correta para o Counter em `numebers_mt()`. [#48729](https://github.com/ClickHouse/ClickHouse/pull/48729) ([Igor Nikonov](https://github.com/devcrafter)).
* Reduz a contenção do mutex do ThreadPool (pode aumentar o desempenho quando há uma grande quantidade de jobs pequenos). [#48750](https://github.com/ClickHouse/ClickHouse/pull/48750) ([Sergei Trifonov](https://github.com/serxa)).
* Simplifica o cálculo do tamanho aproximado do granule no pool de leitura com prefetch. [#49051](https://github.com/ClickHouse/ClickHouse/pull/49051) ([Nikita Taranov](https://github.com/nickitat)).

* Se executarmos uma mutation com IN (subconsulta) assim: `ALTER TABLE t UPDATE col='new value' WHERE id IN (SELECT id FROM huge_table)` e a tabela `t` tiver múltiplas partes, então, para cada parte, um Set para a subconsulta `SELECT id FROM huge_table` é criado na memória. E, se houver muitas partes, isso pode consumir muita memória (e levar a um OOM) e CPU. A solução é introduzir um cache de curta duração dos Sets que estão sendo criados no momento pelas tasks da mutation. Se outra task da mesma mutation for executada de forma concorrente, ela poderá fazer lookup do Set no cache, esperar que ele seja criado e reutilizá-lo. [#46835](https://github.com/ClickHouse/ClickHouse/pull/46835) ([Alexander Gololobov](https://github.com/davenger)).
