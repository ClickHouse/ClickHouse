<div id="backward-incompatible-change">
  #### Alteração incompatível com versões anteriores
</div>

* Menor: Impõe que as configurações do servidor `backup_threads` e `restore_threads` sejam diferentes de zero. [#80224](https://github.com/ClickHouse/ClickHouse/pull/80224) ([Raúl Marín](https://github.com/Algunenano)).
* Corrige `bitNot()` para `String`, para que retorne uma string terminada em zero. [#80791](https://github.com/ClickHouse/ClickHouse/pull/80791) ([Azat Khuzhin](https://github.com/azat)).
* Retroportado em [#82079](https://github.com/ClickHouse/ClickHouse/issues/82079): anteriormente, a função `countMatches` parava de contar na primeira correspondência vazia, mesmo que o padrão a aceitasse. Para contornar esse problema, `countMatches` agora continua a execução avançando um único caractere quando ocorre uma correspondência vazia. Os usuários que desejarem manter o comportamento antigo podem habilitar a configuração `count_matches_stop_at_empty_match`. [#81676](https://github.com/ClickHouse/ClickHouse/pull/81676) ([Elmi Ahmadov](https://github.com/ahmadov)).

<div id="performance-improvement">
  #### Melhoria de desempenho
</div>

* A implementação atual de `Pipe::resize` cria um único nó `Resize` ou `StrictResize` ao inseri-lo na topologia da pipeline, que então atua como um hub central conectando todos os fluxos de entrada (nós upstream) a um conjunto unificado de stream de saída (nós downstream). Esse design leva à contenção no `ExecutingGraph::Node::status_mutex` durante a execução do grafo da pipeline, especialmente em ambientes com muitos núcleos. Quando as pipelines escalam para dezenas ou centenas de streams, essa contenção resulta em:. [#77562](https://github.com/ClickHouse/ClickHouse/pull/77562) ([Zhiguo Zhou](https://github.com/ZhiguoZh)).
* Retroportado em [#81959](https://github.com/ClickHouse/ClickHouse/issues/81959): foi introduzida uma opção para descarregar a (des)compressão e a (des)serialização de blocos para threads da pipeline, em vez de uma única thread associada a uma conexão de rede. Controlado pela configuração `enable_parallel_blocks_marshalling`. Isso deve acelerar consultas distribuídas que transferem quantidades significativas de dados entre o initiator e nós remotos. [#78694](https://github.com/ClickHouse/ClickHouse/pull/78694) ([Nikita Taranov](https://github.com/nickitat)).
* Substitui consultas DELETE FROM ... WHERE 1 por TRUNCATE. (Revertido). [#78739](https://github.com/ClickHouse/ClickHouse/pull/78739) ([scanhex12](https://github.com/scanhex12)).
* Melhorias de desempenho em todos os tipos de filtro de Bloom. [#79800](https://github.com/ClickHouse/ClickHouse/pull/79800) ([Delyan Kratunov](https://github.com/dkratunov)).
* Foi introduzido um caminho otimizado em `UniqExactSet::merge` quando um dos conjuntos está vazio. Além disso, agora, se o conjunto LHS for two-level e o RHS for single-level, não faremos a conversão do RHS para two-level. [#79971](https://github.com/ClickHouse/ClickHouse/pull/79971) ([Nikita Taranov](https://github.com/nickitat)).
* Torna o logging assíncrono por padrão. Você pode desabilitar isso definindo `<async>false</async>` em `<logger>`. [#80125](https://github.com/ClickHouse/ClickHouse/pull/80125) ([Raúl Marín](https://github.com/Algunenano)).
* Melhora a eficiência da reutilização de memória e reduz falhas de página ao usar as tabelas hash twolevel. [#80245](https://github.com/ClickHouse/ClickHouse/pull/80245) ([Jiebin Sun](https://github.com/jiebinn)).
* Evita atualizações desnecessárias e reduz a contenção de lock no QueryConditionCache. [#80247](https://github.com/ClickHouse/ClickHouse/pull/80247) ([Jiebin Sun](https://github.com/jiebinn)).
* Otimização trivial em `concatenateBlocks`. Talvez seja boa para parallel hash join. [#80328](https://github.com/ClickHouse/ClickHouse/pull/80328) ([李扬](https://github.com/taiyang-li)).
* Ao selecionar mark ranges a partir do intervalo da chave primária, a busca binária não pode ser usada se a chave primária estiver encapsulada por funções. Este PR melhora essa limitação: a busca binária ainda pode ser aplicada quando a chave primária está encapsulada por uma cadeia de funções sempre monotônica, ou quando o RPN contém um elemento que é sempre verdadeiro. Este PR fecha [#45536](https://github.com/ClickHouse/ClickHouse/issues/45536). [#80597](https://github.com/ClickHouse/ClickHouse/pull/80597) ([zoomxi](https://github.com/zoomxi)).
* Melhora a velocidade de desligamento do motor Kafka (remove o atraso extra de 3 segundos no caso de múltiplas Kafka tables). [#80796](https://github.com/ClickHouse/ClickHouse/pull/80796) ([Azat Khuzhin](https://github.com/azat)).
* Async insert: reduz o uso de memória e melhora o desempenho das consultas insert. [#80972](https://github.com/ClickHouse/ClickHouse/pull/80972) ([Raúl Marín](https://github.com/Algunenano)).
* Não gera profile dos processors se a tabela de log estiver desabilitada. [#81256](https://github.com/ClickHouse/ClickHouse/pull/81256) ([Raúl Marín](https://github.com/Algunenano)).
* Acelera o toFixedString quando a source é exatamente a solicitada. [#81257](https://github.com/ClickHouse/ClickHouse/pull/81257) ([Raúl Marín](https://github.com/Algunenano)).
* Evita processar valores de cota quando o usuário não está limitado. [#81549](https://github.com/ClickHouse/ClickHouse/pull/81549) ([Raúl Marín](https://github.com/Algunenano)).
* Definiu ProcfsMetricsProvider como thread&#95;local para manter os arquivos abertos entre as tarefas. [#81576](https://github.com/ClickHouse/ClickHouse/pull/81576) ([Raúl Marín](https://github.com/Algunenano)).

* Implementa uma lógica semelhante ao rebalanceamento do Kafka para StorageKafka2 usando ClickHouse Keeper. Para cada réplica, há suporte a dois tipos de bloqueios de partição: permanentes e temporários. A réplica tenta manter os bloqueios permanentes pelo maior tempo possível; em qualquer momento, não há mais de `all_topic_partitions / active_replicas_count` (aqui, `all_topic_partitions` é o número total de partições e `active_replicas_count` é o número de réplicas ativas) bloqueios permanentes na réplica; se houver mais do que isso, a réplica libera algumas partições. Algumas partições são mantidas temporariamente pela réplica. O número máximo de bloqueios temporários em uma réplica muda dinamicamente para dar a outras réplicas a chance de assumir algumas partições como bloqueios permanentes. Ao atualizar os bloqueios temporários, a réplica libera todos eles e tenta assumir outros novamente. [#78726](https://github.com/ClickHouse/ClickHouse/pull/78726) ([Daria Fomina](https://github.com/sinfillo)).
