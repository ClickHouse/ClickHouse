<div id="description">
  ## Descrição
</div>

Contém uma lista de todas as operações `BACKUP` ou `RESTORE`, com seus estados atuais e outras propriedades. Note que a tabela não é persistente e mostra apenas as operações executadas após a última reinicialização do servidor.

  ## Colunas
</div>

<div id="restore-atomicity">
  ## Atomicidade da restauração
</div>

`RESTORE` não é transacional e não reverte em caso de falha. Para cada tabela, todas as partes selecionadas são copiadas antes que qualquer uma seja anexada, mas a própria fase de anexação não é transacional — as partes ficam visíveis uma de cada vez. As tabelas são processadas de forma independente.

**As tabelas são independentes.** Uma tabela cuja restauração é concluída permanece como está, mesmo que outra tabela no mesmo comando falhe mais tarde:

```sql
RESTORE TABLE db.t0, TABLE db.t1
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

Se este comando falhar depois que `db.t0` tiver sido totalmente restaurado, mas a restauração de `db.t1` ainda não tiver sido concluída, `db.t0` permanecerá restaurado.

**A cláusula `PARTITIONS` não é um limite de commit.** Ela apenas seleciona quais partes de uma tabela são restauradas:

```sql
RESTORE TABLE db.t0 PARTITIONS '2026-06-01', '2026-06-02', '2026-06-03'
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

Todas as partes selecionadas da tabela são copiadas primeiro e só são anexadas quando todas estiverem prontas. Portanto, se esse comando falhar durante a fase de cópia — por exemplo, depois que a partição `2026-06-01` tiver sido totalmente copiada, mas `2026-06-02` e `2026-06-03` ainda não tiverem terminado — então `2026-06-01` **não** será confirmada, e a tabela ficará sem nenhum dado restaurado por esse comando. Quando a fase de cópia for concluída e a etapa de anexação começar, as partes serão confirmadas uma a uma, de modo que uma falha durante a anexação pode deixar a tabela parcialmente restaurada, sem rollback.

Para fazer o commit das partições de forma independente (de modo que uma partição concluída sobreviva a uma falha posterior e possa ser tentada novamente de forma isolada), execute um `RESTORE` separado para cada partição, usando `SETTINGS allow_non_empty_tables = true` após a primeira.
