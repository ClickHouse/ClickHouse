`clickhousectl` (alias `chctl`) é a CLI oficial do ClickHouse, do desenvolvimento local ao ClickHouse Cloud. Ela atende tanto pessoas no terminal quanto scripts e agentes de programação.

Com o `clickhousectl`, você pode:

* Instalar e alternar entre versões locais do ClickHouse, executar servidores locais isolados e rodar SQL
* Executar o Postgres localmente com Docker
* Criar, configurar, escalar, fazer backup e consultar serviços do ClickHouse Cloud
* Criar, monitorar, configurar e restaurar serviços do [ClickHouse Managed Postgres](/pt-BR/products/managed-postgres/overview)
* Criar e operar ClickPipes a partir de armazenamento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB e BigQuery
* Gerenciar fontes de dados, dashboards, alertas, webhooks, buscas salvas e funções em um serviço [Managed ClickStack](/pt-BR/clickstack/deployment/managed)
* Desenvolver UDFs executáveis localmente e implantá-las no ClickHouse Cloud
* Gerenciar membros da organização, convites, chaves de API e funções
* Instalar as ClickHouse Agent Skills oficiais em agentes de programação

Esta página apresenta exemplos representativos. `clickhousectl <command> --help` é a referência definitiva para todos os comandos e flags. A ajuda da maioria dos comandos termina com um bloco `CONTEXT FOR AGENTS`; nos comandos do Cloud, esse bloco também lista as permissões de chave de API necessárias. Para guias passo a passo, siga os links indicados em cada seção. Para uma visão geral focada no Cloud, consulte [CLI do ClickHouse](/pt-BR/products/cloud/features/cli).

## Instalação {#installation}

O `clickhousectl` funciona no MacOS e no Linux, em arquiteturas ARM64 e x86&#95;64.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

O script instala `~/.local/bin/clickhousectl` e cria o alias `chctl`. Verifique se `~/.local/bin` está no seu `PATH`.

Você também pode instalá-lo com um gerenciador de pacotes:

| Ferramenta                                   | Comando                         |
| -------------------------------------------- | ------------------------------- |
| npm                                          | `npm install -g clickhousectl`  |
| uv                                           | `uv tool install clickhousectl` |
| pipx                                         | `pipx install clickhousectl`    |
| pip                                          | `pip install clickhousectl`     |
| cargo-binstall                               | `cargo binstall clickhousectl`  |
| Cargo, a partir do código-fonte (Rust 1.94+) | `cargo install clickhousectl`   |

Apenas o script de instalação e o npm criam o alias `chctl`. Para atualizar uma instalação existente, execute `clickhousectl update` (consulte [Autoatualização](#self-update)).

## Requisitos {#requirements}

* Docker, apenas para Postgres local
* Para comandos do Cloud, uma conta do [ClickHouse Cloud](https://clickhouse.com/cloud). Comandos de leitura funcionam com OAuth pelo navegador (`cloud auth login`). Para criar ou alterar recursos, é necessária uma [chave de API](/pt-BR/products/cloud/features/admin-features/api/openapi). Consulte [Autenticação](#authentication).

## Local {#local}

Os comandos locais operam no diretório atual. Cada projeto armazena os dados do servidor em `.clickhouse/`, enquanto os binários do ClickHouse são compartilhados globalmente em `~/.clickhouse/`. A CLI não busca nos diretórios pais; por isso, execute os comandos locais a partir da raiz do seu projeto. Consulte o [guia de desenvolvimento local](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md) para ver o fluxo de trabalho completo.

### Instalar e selecionar versões {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
```

| Seletor       | Significado                                                                                                         |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `latest`      | Compilação mais recente do ClickHouse, verificada remotamente a cada instalação, uso ou inicialização (recomendado) |
| `stable`      | Lançamento estável mais recente                                                                                     |
| `lts`         | Lançamento de suporte de longo prazo mais recente                                                                   |
| `26.8`        | Lançamento correspondente mais recente                                                                              |
| `26.8.1.1760` | Versão exata                                                                                                        |

`local use` instala a versão, se necessário, define-a como padrão para as próximas inicializações do servidor e cria um link simbólico para ela em `~/.local/bin/clickhouse`, para que `clickhouse client` e `clickhouse local` fiquem disponíveis no seu `PATH`. Passe `--no-global` para não criar o link simbólico. Se já existir um arquivo comum nesse caminho, ele será mantido como está.

`local remove` não remove a versão padrão nem uma versão em uso por um servidor em execução em qualquer projeto. Com `--force`, esses servidores são interrompidos e a versão é removida, e a definição de versão padrão e o link simbólico também são removidos.

### Inicializar um projeto {#initializing-project}

```bash
clickhousectl local init
```

`init` é opcional. Ele cria um diretório `.clickhouse/` ignorado pelo git para dados de tempo de execução, além de scaffolds SQL que você pode fazer commit: `clickhouse/` (`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`) e `postgres/` (`tables/`, `views/`, `functions/`, `queries/`, `seed/`). Ao executá-lo novamente, apenas o que estiver faltando é criado.

### Executar servidores locais {#managing-servers}

```bash
clickhousectl local server start dev --version latest   # Background start; waits for readiness
clickhousectl local server start dev --no-wait          # Return after spawning
clickhousectl local server start dev --foreground       # Run in the foreground
clickhousectl local server start dev --http-port 8124 --tcp-port 9001
clickhousectl local server list                         # Servers in this project
clickhousectl local server list --global                # Servers across all projects
clickhousectl local server stop dev
clickhousectl local server stop-all                     # Stop all ClickHouse and Postgres servers in this project
clickhousectl local server remove dev                   # Permanently delete a stopped server's data
```

Cada servidor nomeado tem seus próprios dados em `.clickhouse/servers/<name>/data/`, e esses dados são preservados para a próxima inicialização quando o servidor é parado. Se nenhum nome for informado, o primeiro servidor será `default`; se `default` já estiver em execução, um novo nome será gerado. As portas padrão são HTTP 8123 e TCP 9000; se estiverem ocupadas, portas livres serão atribuídas.

`--version` escolhe uma versão apenas para aquela inicialização, sem alterar a versão padrão. Uma inicialização simples, sem versão informada e sem versão padrão definida, instala `latest` sem defini-la como padrão; para isso, execute `local use latest` antes.

### Executar SQL com o cliente local {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` se conecta a um servidor nomeado usando o mesmo binary do ClickHouse que o executa (nome padrão: `default`). Os argumentos após `--` são repassados ao `clickhouse client` sem alterações. A saída e o status de saída vêm do `clickhouse client`, mesmo no modo JSON; por isso, ao escrever scripts, defina você mesmo o formato de saída SQL.

### Configuração personalizada do servidor {#custom-config-files}

Coloque uma configuração parcial em XML ou YAML em `~/.clickhouse/configs/` e selecione-a pelo nome ao iniciar um servidor:

```bash
mkdir -p ~/.clickhouse/configs
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local server configs
clickhousectl local server stop dev
clickhousectl local server start dev --config analytics
```

O arquivo é sobreposto aos valores padrão internos, portanto só precisa conter as configurações que você alterar. A seleção não é memorizada: uma inicialização posterior sem `--config` remove o overlay. Os caminhos dos dados e as portas gerenciados sempre prevalecem sobre os valores da configuração.

### Gravar os detalhes de conexão em um arquivo dotenv {#dotenv}

```bash
clickhousectl local server dotenv dev                                     # Writes .env
clickhousectl local server dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` lê as portas reais do servidor em execução e grava `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT` e `CLICKHOUSE_HTTP_PORT`, além do usuário, da senha e do banco de dados, quando você os fornece. As demais linhas de um arquivo existente são preservadas. Carregue o arquivo com o carregador de dotenv da sua aplicação; nunca use `eval` na pré-visualização exibida.

### Postgres local {#local-postgres}

O Postgres local roda no Docker, então o Docker precisa estar em execução. As versões 17 e 18 do Postgres são compatíveis, incluindo tags de imagem como `18-alpine`; novas instâncias usam a versão 18 por padrão.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres stop app
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

Uma instância é identificada pelo nome e pela versão principal. Ao retomar uma instância parada, a porta, o usuário, a senha e o banco de dados originais são reutilizados; por isso, as flags de criação não têm efeito na retomada. Uma senha aleatória é gerada, a menos que você informe uma. O arquivo `.env.local` contém a senha, então mantenha-o fora do controle de versão.

### UDFs locais {#local-udfs}

`local udf` implanta [UDFs executáveis](/pt-BR/reference/functions/regular-functions/udf#executable-user-defined-functions) a partir de `clickhouse/udfs/<name>/` em um servidor local. `cloud udf` envia o mesmo diretório para o Cloud (consulte [UDFs no Cloud](#cloud-udfs)).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local server start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

Todos os comandos, exceto `init`, aceitam `--server <name>` (padrão: `default`). O `deploy` valida o `udf.json` da mesma forma que o Cloud. Em um servidor em execução, ele recarrega as funções e confirma que a função foi carregada. O tempo de execução `native` só pode ser implantado localmente em hosts Linux amd64 ou arm64. Consulte o [guia de funções definidas pelo usuário](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

## Autenticação {#authentication}

Os comandos do Cloud usam um de dois tipos de credencial:

| Credencial         | Recursos                                                                                                                 | Armazenamento                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| OAuth no navegador | Sua identidade de usuário: operações read-only no Cloud e SQL read-only, em todas as organizações às quais você pertence | `~/.clickhouse/tokens.json`, global e compartilhado entre projetos |
| Chave de API       | Restrita a uma organização; leituras e gravações dependem das funções atribuídas à chave                                 | `.clickhouse/credentials.json`, quando salva, local ao projeto     |

Se você ainda não tem uma conta no ClickHouse Cloud, `clickhousectl cloud auth signup` abre a página de cadastro no seu navegador.

### Login com OAuth {#oauth-login}

```bash
clickhousectl cloud auth login
```

Isso abre seu navegador para o fluxo de dispositivo do OAuth. Os tokens são salvos globalmente em `~/.clickhouse/tokens.json` e atualizados automaticamente.

<Note>
  O OAuth é **read-only**. Para criar ou alterar recursos, faça login com uma [chave de API](#api-key).
</Note>

### Chave de API {#api-key}

[Crie uma chave de API](/pt-BR/products/cloud/features/admin-features/api/openapi) com as funções necessárias para os seus comandos e, em seguida, salve-a. O prompt interativo evita que o segredo fique registrado no histórico do seu shell:

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

O login verifica a chave e exibe a identidade à qual ela pertence. Se a API rejeitar a chave, ela não é salva e o comando termina com código de saída 4. Se a API estiver inacessível, a chave é salva e um aviso é exibido.

Para CI e outras automações, injete a chave pelo seu gerenciador de segredos em vez de salvá-la:

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

Em desenvolvimento, a CLI também lê essas variáveis de um arquivo `.env` no diretório atual. Não inclua o `.env` no controle de versão.

### Verificar e limpar credenciais {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

O `whoami` funciona com qualquer tipo de credencial e retorna o código de saída 4 se as credenciais forem rejeitadas. O `status` pode retornar o código de saída 0 mesmo quando nenhuma credencial funciona, por isso use o `whoami` para testar o acesso. O logout não remove variáveis de ambiente nem edita o `.env`.

### Precedência de credenciais {#credential-precedence}

A primeira fonte disponível prevalece:

1. Flags `--api-key` e `--api-secret`
2. `.clickhouse/credentials.json`
3. Variáveis de ambiente exportadas
4. Variáveis do arquivo `.env` no diretório atual
5. Tokens OAuth globais

Use `--debug` em qualquer comando `cloud` para exibir no stderr a fonte de credenciais selecionada e a URL da API:

```bash
clickhousectl cloud service list --debug
```

### Selecionar uma organização {#organizations}

Os comandos com escopo de organização selecionam a organização automaticamente somente quando suas credenciais dão acesso a exatamente uma. Caso contrário, informe `--org-id` ou `--org-name` com o nome exato:

```bash
clickhousectl cloud org list
clickhousectl cloud service list --org-id <org-id>
clickhousectl cloud service list --org-name "My Org"
```

A maioria dos comandos de recursos aceita um ID posicional ou um `--name` exato. Consulte [autenticação e acesso](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md) para mais informações sobre permissões, chaves restritas e limpeza ao fazer logout.

## Cloud {#cloud}

Os comandos do Cloud chamam a [API do ClickHouse Cloud](/pt-BR/products/cloud/features/admin-features/api/api-overview). As requisições de criação e atualização retornam assim que a API as aceita; por isso, consulte `get` repetidamente até que o recurso atinja o estado desejado.

### Serviços {#services}

```bash
clickhousectl cloud service create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud service list
clickhousectl cloud service get <service-id>
clickhousectl cloud service start <service-id>
clickhousectl cloud service stop <service-id>
clickhousectl cloud service wake <service-id>             # Wake an idle service
clickhousectl cloud service reset-password <service-id>
clickhousectl cloud service delete <service-id>           # Must be stopped; --force stops it first
```

Salve a senha inicial exibida na criação, pois ela é retornada apenas uma vez. O comando de criação retorna antes de o provisionamento terminar, então repita `get` até que o estado seja `running`. **Se `--ip-allow` for omitido, todos os IPs serão permitidos (`0.0.0.0/0`).** As entradas aceitam o formato `IP_OR_CIDR=DESCRIPTION`. Restaure um backup em um novo serviço com `--backup-id` ou implante um serviço na infraestrutura BYOC com `--byoc-id`.

Atualize, escale e configure um serviço:

```bash
clickhousectl cloud service update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud service profile list --region us-east-1
clickhousectl cloud service scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud service scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud service settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud service upgrade-window set <service-id> --weekday 0 --start-hour 6
```

A memória por réplica deve ser um múltiplo de 4 GB, com no máximo 120 GB em serviços não pagos e 356 GB em serviços pagos, e até 50 réplicas. Os limites da organização e do warehouse podem reduzir esses valores. O escalonamento automático horizontal exige que a funcionalidade correspondente esteja habilitada na organização. `update` altera apenas as flags que você informar.

Os outros grupos de comandos de serviço são `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (Beta), `snapshot` (Beta), `private-endpoint`, `backup-config` e `prometheus`. Consulte [criar e operar um Serviço Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md).

### API de consultas {#query-api}

`cloud service query` executa uma instrução SQL via HTTP, sem exigir um binário `clickhouse` local nem a senha do serviço:

```bash
clickhousectl cloud service query <service-id> --query "SELECT version()"
clickhousectl cloud service query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud service query <service-id>
```

* **OAuth** executa a consulta com a sua identidade, com acesso SQL read-only. Nada é vinculado ao serviço.
* **Chave de API:** na primeira chamada, o clickhousectl adiciona sua chave de API ao endpoint da API de consultas do serviço e, se necessário, cria o endpoint com as funções `sql_console_admin`. As funções, origens e outras vinculações de chaves existentes são mantidas, e nenhuma chave nova é criada. Quando a CLI altera o endpoint, ela exibe `Binding the authenticated API key to the Query API endpoint for service '<name>'...` no stderr. Passe `--no-auto-enable` para que o comando falhe nesse caso.

Uma chave por serviço salva por uma versão anterior da CLI continua tendo precedência para esse serviço. Se a API rejeitá-la, `cloud service repair-query-key <service-id>` a substitui de forma explícita.

A API de consultas aceita uma instrução por requisição. A requisição pode atingir o tempo limite após cerca de 30 segundos enquanto o SQL continua em execução, portanto verifique o resultado antes de repetir uma escrita. Use o `clickhouse client` para scripts com várias instruções, cargas em massa e consultas longas. A allowlist de IPs do serviço restringe conexões diretas, mas não a rota da API de consultas, que passa por proxy. Consultar um serviço idle o reativa; já um serviço parado precisa ser iniciado com `cloud service start`.

Gerencie o endpoint da API de consultas do serviço, os endpoints SQL nomeados e as consultas salvas:

```bash
clickhousectl cloud service query-endpoint get <service-id>
clickhousectl cloud service query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` substitui as funções de todas as chaves vinculadas ao endpoint. Consulte [Comportamento do SQL e da API de consultas](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md).

### Managed Postgres {#postgres-services}

`cloud postgres` gerencia o [ClickHouse Managed Postgres](/pt-BR/products/managed-postgres/overview). Esses comandos estão em Beta, e o suporte ao GCP está em prévia privada.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

Os tamanhos disponíveis na AWS incluem `m6gd.large`, `c6gd.xlarge` e `r6gd.xlarge`. No GCP, passe `--provider gcp` com uma região do GCP e um tamanho como `c4-standard-lssd-4`.

Salve a senha e a string de conexão retornadas pelo `create`. As respostas posteriores do `get` nunca retornam credenciais, e `reset-password` é a única forma de obter novas. Conecte-se com o `psql` usando `sslmode=verify-full` e o arquivo da CA.

**Se você omitir as flags de acesso no create, todos os endereços IPv4 e IPv6 serão permitidos no Postgres (5432) e no PgBouncer (6432).** Passe um `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` por regra ou `--block-public-access` para não definir nenhuma regra. Depois que você passar uma regra, somente as regras listadas serão aplicadas.

Monitore e recupere:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` aceita apenas OAuth, portanto falha enquanto uma fonte de chave de API de maior prioridade estiver ativa. `metrics`, `slow-queries` e `prometheus` cuidam do monitoramento. `restore` copia as regras de acesso IPv4 atuais da origem para o serviço restaurado, a menos que você informe `--ip-allow` ou `--block-public-access`. Restaurações e réplicas são retornadas sem senha. `promote` e `switchover` retornam assim que a operação é aceita; após um promote, consulte `postgres get --json` periodicamente até que a réplica informe `isPrimary: true`. Veja o [guia do Managed Postgres](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md).

### ClickPipes {#clickpipes}

`cloud clickpipe` faz a ingestão de dados de armazenamento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB e BigQuery. A criação e a descoberta de esquema exigem uma chave de API e um serviço de destino em execução. Cada fonte de dados tem seu próprio subcomando `clickpipe create <source>`; execute-o com `--help` para ver as flags disponíveis.

Carregue arquivos do S3 usando uma IAM role. Primeiro, descubra o schema e, depois, escolha as colunas:

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN"
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --column 'event_id:Int64' --column 'event_type:String'
```

Replique o Postgres com CDC. O TLS é verificado por padrão; para uma origem Managed Postgres, exporte a CA dela e informe-a:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud service query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` cria tabelas `ReplacingMergeTree`; por isso, leia o estado atual com `FINAL WHERE _peerdb_is_deleted = 0`. Um pipe do Kafka segue o mesmo padrão: execute `clickpipe schema-discover kafka` com as mesmas flags de origem e, em seguida, passe as colunas:

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

Por padrão, os pipes do BigQuery executam um snapshot. Para CDC, informe `--replication-mode cdc`, um `--replication-method` e, para cada tabela, uma coluna de watermark ou uma função de eventos em `--table-mapping-json`; agende as sincronizações com `--sync-cron` ou `--sync-interval-seconds`. Para operar pipes existentes:

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

Os pipes de CDC precisam estar `Paused` antes do `update`: pare o pipe, consulte `get` repetidamente até que ele esteja `Paused` e, em seguida, atualize-o. O serviço pode retomar o pipe durante a atualização, portanto execute `start` somente se `get` ainda mostrar `Paused`. A opção `--start-paused` está disponível para armazenamento de objetos, Kafka, Kinesis e Pub/Sub. Os demais grupos de comandos são `cdc-scaling`, `context get` (prontidão e principal da identidade de carga de trabalho do GCP) e `reverse-private-endpoint`. Consulte o [guia de ClickPipes](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) e a [referência de configuração de ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md).

### ClickStack {#clickstack}

`cloud clickstack` gerencia fontes de dados, dashboards, alertas, webhooks, buscas salvas e funções em um serviço [Managed ClickStack](/pt-BR/clickstack/deployment/managed) existente. Os recursos são arquivos JSON (`--file`, ou `-` para stdin). As leituras aceitam autenticação via OAuth; as gravações exigem uma chave de API.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**Cada atualização do ClickStack substitui o recurso por inteiro.** Salve o estado atual com `get --json` e envie a definição completa, e não apenas os campos alterados. Consulte o [guia do ClickStack](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md).

### UDFs no Cloud {#cloud-udfs}

`cloud udf` gerencia UDFs executáveis no escopo da organização, suas versões e suas anexações a serviços. `deploy` envia o diretório que você testou com `local udf`, aguarda a conclusão da compilação, anexa essa versão e aguarda até que ela seja implantada:

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud service query <service-id> --query "SELECT my_udf(1)"
```

Para executar cada etapa manualmente, use `udf create`, `udf version create`, `udf attach` (com `--wake` para um serviço idle), `udf detach` e `udf delete`. Esses comandos retornam assim que a solicitação é aceita; consulte periodicamente `udf get` e `udf attachment get` para acompanhar o andamento. As leituras aceitam OAuth; as gravações exigem uma chave de API. Consulte o [guia de funções definidas pelo usuário](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

### Organizações e acesso {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

Os subcomandos de `cloud org` recebem `--org-id`, nunca um ID posicional. `org usage` abrange no máximo 31 dias. `org` também inclui `quota`, `balance`, `notification-types`, `role` (funções personalizadas da organização) e `byoc` (infraestrutura BYOC). As notificações estão em Beta.

Gerencie membros, convites e chaves de API:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

**Omitir `--ip-allow` em `key create` bloqueia todo o acesso à rede**, ao contrário do que ocorre na criação de serviços. O segredo é exibido apenas uma vez. `key list` retorna uma única página, a menos que você informe `--all`. Em `key update`, as flags omitidas mantêm suas configurações, enquanto `--clear-expiry`, `--clear-roles` e `--clear-ip-allow` as removem.

## Saída em JSON {#json-output}

Os comandos que retornam dados estruturados aceitam `--json`, incluindo os comandos locais, do Cloud, `skills`, `update` e `telemetry`:

```bash
clickhousectl cloud service list --json
clickhousectl cloud key list --all --json
clickhousectl local server list --json
```

Quando a CLI detecta um agente de programação (como Claude Code, Cursor, Codex, Gemini CLI, Goose ou Devin, ou qualquer ferramenta que defina `AI_AGENT`), ela seleciona JSON automaticamente. O SQL e os clientes nativos mantêm seus próprios formatos: `cloud service query` retorna `JSONEachRow` no modo JSON, e a saída de `local client` é sempre nativa. Scripts que interpretam a saída de consultas devem informar `--format` explicitamente.

No modo JSON, os erros de tempo de execução são enviados ao stderr como um objeto com um `code` estável e uma `message`:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

Use `error.code` para a lógica de ramificação, e não a mensagem. Erros de uso continuam sendo exibidos como texto, com código de saída 2. Consulte [automação e contratos de saída](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md) para conhecer os formatos de saída e os códigos de erro.

## Códigos de saída {#exit-codes}

| Código | Significado                                                                                             |
| ------ | ------------------------------------------------------------------------------------------------------- |
| `0`    | Sucesso. Em operações assíncronas do Cloud, indica que a requisição foi aceita, mas ainda não concluída |
| `1`    | Erro                                                                                                    |
| `2`    | Erro de uso, incluindo valores inválidos em flags                                  |
| `3`    | Cancelado                                                                                               |
| `4`    | Autenticação necessária ou rejeitada, incluindo tentativas de gravação com OAuth                        |

`local client`, `local postgres client` e outros comandos que delegam a execução a clientes nativos repassam o próprio status de saída do cliente.

## Agent Skills {#skills}

Instale as [ClickHouse Agent Skills oficiais](https://github.com/ClickHouse/agent-skills) nos seus agentes de programação:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

Por padrão, as Skills são instaladas no projeto atual, ou no seu diretório pessoal com `--global`. O diretório compartilhado `.agents/skills/` é sempre incluído. Sem um terminal, você precisa passar `--agent`, `--all` ou `--detected-only`. Execute `clickhousectl skills --help` para ver os nomes de agentes compatíveis.

## Autoatualização {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

A CLI também verifica se há atualizações em segundo plano, no máximo uma vez a cada 24 horas, e exibe um aviso quando uma versão mais recente estiver disponível.

## Telemetria {#telemetry}

O `clickhousectl` coleta dados de uso anônimos para orientar o desenvolvimento. A primeira execução exibe um aviso e não envia nada; a coleta começa a partir da execução seguinte, a menos que você a desative.

Cada evento contém:

* O caminho do comando e os **nomes** das flags e argumentos passados explicitamente, nunca seus valores
* O resultado e o código de saída
* Para um comando digitado incorretamente, o nome do comando ou da flag sugerido pela CLI, nunca o que você digitou
* Para falhas em tempo de execução, categorias limitadas: etapa e tipo da falha, um status HTTP presente em uma allowlist e categorias de nova tentativa, estado de provisionamento e duração
* A versão da CLI, o SO e a arquitetura, se a execução ocorre em CI e o agente de programação detectado

Valores dos argumentos, SQL, credenciais, identificadores de recursos, argumentos após `--` e mensagens de erro nunca são registrados. Não há ID de instalação nem de dispositivo.

Para desativar:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

Defina `CHCTL_TELEMETRY_DEBUG=1` para exibir a carga útil no stderr sem enviar nenhum dado. Consulte os [detalhes da telemetria](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md).
