`clickhousectl` (alias `chctl`) é a CLI oficial do ClickHouse, do desenvolvimento local ao ClickHouse Cloud. Ela foi feita para pessoas no terminal, para scripts e para agentes de programação.

Com o `clickhousectl`, você pode:

* Instalar e alternar entre versões locais do ClickHouse, executar servidores locais isolados e rodar SQL
* Executar Postgres localmente com Docker
* Criar, configurar, escalar, fazer backup e consultar serviços do ClickHouse Cloud
* Criar, monitorar, configurar e restaurar serviços do [ClickHouse Managed Postgres](/pt-BR/products/managed-postgres/overview)
* Criar e operar ClickPipes a partir de armazenamento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB e BigQuery
* Gerenciar fontes, dashboards, alertas, webhooks, pesquisas salvas e funções em um serviço [Self-managed ClickHouse Observability](/pt-BR/clickstack/self-configured/deployment/managed)
* Desenvolver UDFs executáveis localmente e implantá-las no ClickHouse Cloud
* Gerenciar membros da organização, convites, chaves de API e funções
* Instalar as ClickHouse Agent Skills oficiais em agentes de programação

Esta página apresenta exemplos representativos. `clickhousectl <command> --help` é a referência definitiva para cada comando e flag. A ajuda da maioria dos comandos termina com um bloco `CONTEXT FOR AGENTS`; nos comandos do Cloud, esse bloco também lista as permissões de chave de API necessárias. Para instruções passo a passo, siga os links para os guias em cada seção. Para uma visão geral com foco no Cloud, consulte [CLI do ClickHouse](/pt-BR/products/cloud/features/cli).

## Instalação {#installation}

O `clickhousectl` funciona no MacOS e no Linux, em arquiteturas ARM64 e x86&#95;64.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

O script instala `~/.local/bin/clickhousectl` e cria o alias `chctl`. Certifique-se de que `~/.local/bin` esteja no seu `PATH`.

Você também pode instalá-lo com um gerenciador de pacotes:

| Ferramenta                                     | Comando                         |
| ---------------------------------------------- | ------------------------------- |
| npm                                            | `npm install -g clickhousectl`  |
| uv                                             | `uv tool install clickhousectl` |
| pipx                                           | `pipx install clickhousectl`    |
| pip                                            | `pip install clickhousectl`     |
| cargo-binstall                                 | `cargo binstall clickhousectl`  |
| Cargo, a partir do código-fonte (Rust 1.94.1+) | `cargo install clickhousectl`   |

Apenas o script de instalação e o npm criam o alias `chctl`. Para atualizar uma instalação existente, execute `clickhousectl update` (consulte [Autoatualização](#self-update)); nas instalações via npm, uv, pipx e pip, esse comando exibe o comando de upgrade do gerenciador de pacotes em vez de realizar a atualização.

### Autocompletar no shell {#shell-completions}

Para autocompletar comandos, flags, nomes de servidores locais e versões instaladas com Tab, adicione uma linha ao arquivo de inicialização do seu shell. Ela registra tanto o `clickhousectl` quanto o `chctl`:

```bash
eval "$(clickhousectl completions bash)"   # ~/.bashrc
eval "$(clickhousectl completions zsh)"    # ~/.zshrc, after compinit
clickhousectl completions fish | source    # ~/.config/fish/config.fish
```

O preenchimento automático executa a CLI instalada sempre que você pressiona a tecla Tab, por isso permanece atualizado após `update`.

## Requisitos {#requirements}

* Docker, apenas para o Postgres local
* Para os comandos do Cloud, uma conta do [ClickHouse Cloud](https://clickhouse.com/cloud). Os comandos de leitura funcionam com OAuth pelo navegador (`cloud auth login`). Para criar ou alterar recursos, é necessária uma [chave de API](/pt-BR/products/cloud/features/admin-features/api/openapi). Consulte [Autenticação](#authentication).

## Local {#local}

Um diretório que contém `.clickhouse/` é a raiz de um projeto, assim como um diretório que contém `.git/` é a raiz de um repositório Git. Os comandos locais usam a raiz de projeto mais próxima, buscando no diretório atual e nos diretórios acima dele, e por isso funcionam a partir de qualquer subdiretório do projeto; fora de um projeto, usam o diretório atual. Defina `CLICKHOUSECTL_PROJECT_DIR` para indicar explicitamente a raiz do projeto, por exemplo, em um script ou em uma tarefa de CI. Cada projeto mantém os dados do servidor em `.clickhouse/`, enquanto os binários do ClickHouse são compartilhados globalmente em `~/.clickhouse/`. Consulte o [guia de desenvolvimento local](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md) para conhecer o fluxo de trabalho completo.

### Instalação e seleção de versões {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
clickhousectl local install --binary ~/ClickHouse/build/programs/clickhouse   # A build of your own
```

| Seletor       | Significado                                                                                                         |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `latest`      | Compilação mais recente do ClickHouse, verificada remotamente a cada instalação, uso ou inicialização (recomendado) |
| `stable`      | Lançamento estável mais recente                                                                                     |
| `lts`         | Lançamento de suporte de longo prazo mais recente                                                                   |
| `26.8`        | Lançamento correspondente mais recente                                                                              |
| `26.8.1.1760` | Versão exata                                                                                                        |

`local use` instala a versão, se necessário, define-a como padrão para as próximas inicializações do servidor e cria um link simbólico para ela em `~/.local/bin/clickhouse`, de modo que `clickhouse client` e `clickhouse local` fiquem disponíveis no seu `PATH`. Use `--no-global` para não criar o link simbólico. Se já existir um arquivo comum nesse caminho, ele será mantido intacto.

`local remove` não remove a versão padrão nem uma versão em uso por um servidor em execução em qualquer projeto. Com `--force`, esses servidores são interrompidos e a versão é removida, junto com a definição de padrão e o link simbólico.

`local install --binary <path>` copia um binary do ClickHouse compilado por você e o instala sob a versão que ele informa, para que você possa selecioná-lo com `local use` ou `--version`, como qualquer outra instalação. Uma recompilação normalmente informa a mesma versão; portanto, use `--force` para substituir a cópia instalada.

### Inicializar um projeto {#initializing-project}

```bash
clickhousectl local init
```

`init` define o diretório atual (ou `CLICKHOUSECTL_PROJECT_DIR`, quando definido) como a raiz do projeto. Ele cria um diretório `.clickhouse/` ignorado pelo git para dados de tempo de execução, além de estruturas que você pode incluir em commits: `clickhouse/` (`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`, `config.d/`) e `postgres/` (`tables/`, `views/`, `functions/`, `queries/`, `seed/`). Ao ser executado novamente, cria apenas o que estiver faltando, portanto, basta executá-lo uma vez após clonar um projeto. Iniciar um servidor sem `init` também funciona e cria `.clickhouse/` no diretório atual.

### Execute servidores locais {#managing-servers}

```bash
clickhousectl local clickhouse start dev --version latest   # Background start; waits for readiness
clickhousectl local clickhouse start dev --no-wait          # Return after spawning
clickhousectl local clickhouse start dev --foreground       # Run in the foreground
clickhousectl local clickhouse start dev --http-port 8124 --tcp-port 9001
clickhousectl local clickhouse list                         # ClickHouse servers in this project
clickhousectl local clickhouse list --global                # Servers across all projects
clickhousectl local status                                  # Every ClickHouse server and Postgres instance in this project
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse stop-all                     # Stop every ClickHouse server in this project
clickhousectl local clickhouse remove dev                   # Permanently delete a stopped server's data
```

`local ch` é uma abreviação de `local clickhouse`, e o nome anterior `local server` continua funcionando como alias. Cada servidor nomeado tem seus próprios dados em `.clickhouse/servers/<name>/data/`, e esses dados são preservados quando o servidor é parado, ficando disponíveis na próxima inicialização. Uma inicialização sem nome usa `default`; se `default` já estiver em execução, um novo nome é gerado. As portas padrão são HTTP 8123 e TCP 9000; quando estiverem ocupadas, portas livres são atribuídas.

Os comandos que atuam sobre um servidor existente (`stop`, `client`, `dotenv`, `local client` e `local udf --server`) selecionam `default` quando o nome é omitido; caso contrário, selecionam o único servidor do projeto com aquele motor. Se houver vários servidores e nenhum se chamar `default`, eles falham com `server_selection_required` e listam os nomes. `remove` nunca tenta adivinhar: sem um nome, remove apenas `default`. Em scripts, passe os nomes explicitamente.

`--version` escolhe uma versão para aquela inicialização sem alterar a versão padrão. Uma inicialização simples, sem versão informada e sem versão padrão definida, instala `latest` sem torná-la padrão; para defini-la como padrão, execute `local use latest` antes.

### Executar SQL com o cliente local {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` se conecta a um servidor específico, pelo nome, usando o mesmo binary do ClickHouse que o executa; sem um nome, segue a regra de seleção descrita acima. Os argumentos após `--` são repassados ao `clickhouse client` sem alterações. A saída e o status de saída vêm do `clickhouse client`, mesmo no modo JSON, portanto defina você mesmo o formato de saída do SQL ao escrever scripts.

### Configuração personalizada do servidor {#custom-config-files}

Configurações parciais em XML ou YAML substituem os valores padrão integrados e podem estar em três localizações:

| Localização                               | Aplica-se a                                                                  | Quando                      |
| ----------------------------------------- | ---------------------------------------------------------------------------- | --------------------------- |
| `~/.clickhouse/config.d/`                 | Todos os servidores desta máquina                                            | Em toda inicialização       |
| `clickhouse/config.d/` na raiz do projeto | Todos os servidores do projeto; faça commit do diretório para compartilhá-lo | Em toda inicialização       |
| `~/.clickhouse/configs/`                  | O servidor iniciado com a configuração                                       | Somente com `--config NAME` |

```bash
cat > clickhouse/config.d/logging.xml <<'XML'
<clickhouse>
    <logger><level>debug</level></logger>
</clickhouse>
XML
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local clickhouse configs          # List both config.d directories and the named configs
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse start dev --config analytics
```

A cada inicialização, eles são mesclados na ordem da tabela, e os arquivos posteriores prevalecem; assim, um arquivo só precisa conter as configurações que você alterar. Edições e a remoção de um `--config` passam a valer na próxima inicialização. Caminhos dos dados e portas gerenciados sempre prevalecem sobre os valores de configuração.

### Grave os detalhes de conexão em um arquivo dotenv {#dotenv}

```bash
clickhousectl local clickhouse dotenv dev                                     # Writes .env
clickhousectl local clickhouse dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` lê as portas reais do servidor em execução e grava `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT` e `CLICKHOUSE_HTTP_PORT`, além do usuário, da senha e do banco de dados, quando informados. As demais linhas de um arquivo existente são preservadas. Carregue o arquivo com o carregador de dotenv da sua aplicação; nunca use `eval` na prévia exibida.

### Postgres local {#local-postgres}

O Postgres local é executado no Docker, portanto o Docker precisa estar em execução. As versões 17 e 18 do Postgres são compatíveis, incluindo tags de imagem como `18-alpine`; novas instâncias usam a versão 18 por padrão.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres list                       # Postgres instances in this project
clickhousectl local postgres stop app
clickhousectl local postgres stop-all                   # Stop every Postgres instance in this project
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

`local pg` é a forma abreviada de `local postgres`. Uma instância é identificada pelo nome e pela versão principal. Ao retomar uma instância parada, são reutilizados a porta, o usuário, a senha e o banco de dados originais, por isso as flags de criação não têm efeito na retomada. Se você não informar uma senha, uma senha aleatória será gerada. O arquivo `.env.local` contém a senha, portanto mantenha-o fora do controle de versão.

### UDFs locais {#local-udfs}

`local udf` implanta [UDFs executáveis](/pt-BR/reference/functions/regular-functions/udf#executable-user-defined-functions) de `clickhouse/udfs/<name>/` em um servidor local. `cloud udf` envia o mesmo diretório para o Cloud (consulte [UDFs no Cloud](#cloud-udfs)).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local clickhouse start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

Todos os comandos, exceto `init`, aceitam `--server <name>`; sem essa opção, a [regra de seleção](#managing-servers) escolhe o servidor. O comando `deploy` valida `udf.json` da mesma forma que o Cloud. Em um servidor em execução, recarrega as funções e confirma que a função foi carregada. O ambiente de tempo de execução `native` permite a implantação local apenas em hosts Linux amd64 ou arm64. Consulte o [guia de funções definidas pelo usuário](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

## Autenticação {#authentication}

Os comandos do Cloud usam um entre dois tipos de credencial:

| Credencial           | Recursos                                                                                                                   | Armazenamento                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| OAuth pelo navegador | Sua identidade de usuário: operações read-only no Cloud e SQL read-only, em todas as organizações das quais você faz parte | `~/.clickhouse/tokens.json`, global e compartilhado entre projetos                                            |
| Chave de API         | Restrita a uma organização; leituras e gravações dependem das funções da chave                                             | `.clickhouse/credentials.json` na raiz do projeto, quando salva; localizada a partir de qualquer subdiretório |

Se você ainda não tem uma conta no ClickHouse Cloud, o comando `clickhousectl cloud auth signup` abre a página de cadastro no seu navegador.

### Login com OAuth {#oauth-login}

```bash
clickhousectl cloud auth login
```

Isso abre seu navegador para o fluxo de autorização de dispositivo do OAuth. Os tokens são salvos globalmente em `~/.clickhouse/tokens.json` e renovados automaticamente.

<Note>
  O OAuth é **read-only**. Para criar ou alterar recursos, faça login com uma [chave de API](#api-key).
</Note>

### Chave de API {#api-key}

[Crie uma chave de API](/pt-BR/products/cloud/features/admin-features/api/openapi) com as funções exigidas pelos seus comandos e, em seguida, salve-a. O prompt interativo evita que o segredo fique registrado no histórico do seu shell:

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

O login verifica a chave e exibe a identidade à qual ela pertence. Uma chave rejeitada pela API não é salva, e o comando é encerrado com o código de saída 4. Se a API estiver inacessível, a chave é salva e um aviso é exibido.

Em CI e outras automações, injete a chave pelo seu gerenciador de segredos em vez de salvá-la:

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

Em desenvolvimento, a CLI também lê essas variáveis de um arquivo `.env` no diretório atual ou, caso não haja um nele, na [raiz do projeto](#local). Mantenha o `.env` fora do controle de versão.

### Verificar e limpar credenciais {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` funciona com qualquer tipo de credencial e sai com código 4 se as credenciais forem rejeitadas. `status` pode sair com código 0 mesmo quando nenhuma credencial funciona, por isso use `whoami` para testar o acesso. O logout não remove a definição das variáveis de ambiente nem edita o `.env`.

### Ordem de precedência das credenciais {#credential-precedence}

A primeira fonte disponível prevalece:

1. Flags `--api-key` e `--api-secret`
2. `.clickhouse/credentials.json` na raiz do projeto
3. Variáveis de ambiente exportadas
4. Variáveis do arquivo `.env` no diretório atual ou, se ele não existir, na raiz do projeto
5. Tokens OAuth globais

Adicione `--debug` a qualquer comando `cloud` para exibir no stderr a fonte de credenciais selecionada e a URL da API:

```bash
clickhousectl cloud clickhouse list --debug
```

### Selecione uma organização {#organizations}

Os comandos com escopo de organização selecionam a organização automaticamente apenas quando suas credenciais dão acesso a uma única organização. Caso contrário, informe `--org-id` ou `--org-name` com o nome exato; se nenhum deles for informado, o comando encerra com código de saída 2 e lista o ID e o nome de cada organização:

```bash
clickhousectl cloud org list
clickhousectl cloud clickhouse list --org-id <org-id>
clickhousectl cloud clickhouse list --org-name "My Org"
```

A maioria dos comandos de recursos aceita um ID posicional ou um `--name` exato. Consulte [autenticação e acesso](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md) para saber mais sobre permissões, chaves restritas e limpeza ao fazer logout.

## Cloud {#cloud}

Os comandos do Cloud chamam a [API do ClickHouse Cloud](/pt-BR/products/cloud/features/admin-features/api/api-overview). As requisições de criação e atualização retornam assim que são aceitas pela API. Por isso, faça consultas periódicas com `get` até que o recurso atinja o estado desejado.

### Serviços {#services}

`cloud clickhouse` gerencia serviços do ClickHouse Cloud. `cloud ch` é a forma abreviada desse comando, e o nome anterior `cloud service` continua funcionando como alias.

```bash
clickhousectl cloud clickhouse create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud clickhouse create --name app-dev \
  --ip-allow 203.0.113.10/32 --dotenv .env.local          # Password goes only to the file
clickhousectl cloud clickhouse list
clickhousectl cloud clickhouse get <service-id>
clickhousectl cloud clickhouse start <service-id>
clickhousectl cloud clickhouse stop <service-id>
clickhousectl cloud clickhouse wake <service-id>             # Wake an idle service
clickhousectl cloud clickhouse reset-password <service-id>
clickhousectl cloud clickhouse delete <service-id>           # Must be stopped; --force stops it first
```

Salve a senha inicial exibida na criação; ela é retornada apenas uma vez. Com `--dotenv [file]` (padrão: `.env`), ela é gravada apenas nesse arquivo, não no terminal nem na saída JSON. A operação de criação retorna antes da conclusão do provisionamento; por isso, repita `get` até que o estado seja `running`. **Omitir `--ip-allow` permite acesso de todos os IPs (`0.0.0.0/0`).** As entradas aceitam `IP_OR_CIDR=DESCRIPTION`. `--region` aceita qualquer ID de região, incluindo regiões privadas, e o Cloud valida esse ID. Restaure um backup em um novo serviço com `--backup-id` ou implante um serviço na infraestrutura BYOC com `--byoc-id`.

Conecte-se a um serviço em execução:

```bash
clickhousectl cloud clickhouse client <service-id>                     # Interactive clickhouse client
clickhousectl cloud clickhouse client --name analytics -q "SELECT version()"
clickhousectl cloud clickhouse dotenv <service-id> --local             # Write .env.local, without a password
```

`client` abre o `clickhouse client` usando o protocolo TLS nativo e autentica você pelo navegador com seu usuário do Cloud, sem precisar de uma senha de serviço. Ele requer o ClickHouse 25.12 ou mais recente instalado (`clickhousectl local install latest`) e interação humana no navegador; por isso, use [`query`](#query-api) em CI e com agentes. `dotenv` grava `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`, `CLICKHOUSE_HTTP_PORT`, `CLICKHOUSE_USER` e `CLICKHOUSE_SECURE`, substituindo apenas essas chaves e preservando qualquer senha gravada por `create --dotenv`.

Atualize, dimensione e configure um serviço:

```bash
clickhousectl cloud clickhouse update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud clickhouse update <service-id> --deletion-protection true
clickhousectl cloud clickhouse profile list --region us-east-1
clickhousectl cloud clickhouse scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud clickhouse scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud clickhouse scale <service-id> --profile v1-highmem-s
clickhousectl cloud clickhouse settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud clickhouse upgrade-window set <service-id> --weekday 0 --start-hour 6
```

A memória por réplica deve ser múltipla de 4 GB, com no máximo 120 GB em serviços não pagos e 356 GB em serviços pagos, e até 50 réplicas. Os limites da organização e do warehouse podem reduzir esses valores. O escalonamento automático horizontal exige que a funcionalidade correspondente esteja habilitada na organização. `scale --profile` altera o instance profile em organizações Enterprise e BYOC. `update` altera apenas as flags que você informar.

Com a proteção contra exclusão ativada (`create --deletion-protection` ou `update --deletion-protection true|false`), o `delete` se recusa a excluir o serviço e retorna o código de erro `deletion_protected`, mesmo com `--force`; desative-a antes de excluir o serviço.

Outros grupos de comandos de serviço são `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (Beta), `jwt-provider` (Beta, Plano Enterprise), `snapshot` (Beta), `private-endpoint`, `query-endpoint`, `backup-config` e `prometheus`. Consulte [como criar e operar um Serviço Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md).

### API de consultas {#query-api}

`cloud clickhouse query` executa uma instrução SQL via HTTP, sem precisar de um binário `clickhouse` local nem da senha do serviço:

```bash
clickhousectl cloud clickhouse query <service-id> --query "SELECT version()"
clickhousectl cloud clickhouse query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud clickhouse query <service-id>
```

* **OAuth** executa a consulta usando sua identidade, com acesso SQL read-only. Nada é vinculado ao serviço.
* **Chave de API:** a consulta sempre usa a chave de API ativa. Se necessário, o clickhousectl adiciona essa chave ao Endpoint da API de Consultas do serviço, criando o endpoint com as funções `sql_console_admin` caso ainda não exista. As funções, origens e outras vinculações de chave existentes são mantidas, e nenhuma nova chave é criada. Passe `--no-auto-enable` para que a operação falhe em vez de fazer a vinculação automaticamente.

A vinculação é uma operação de gravação, portanto uma chave de API read-only não pode vincular a si mesma: a consulta termina com código de saída 1 e `query_key_bind_forbidden`, e nada é alterado. Faça a vinculação uma vez com uma chave que tenha acesso de gravação, usando `query-endpoint create <service-id> --role <role> --open-api-key <key-id>` (acrescente `--allowed-origins '*'` quando o serviço ainda não tiver um endpoint).

A API de consultas aceita uma instrução por requisição. Ela pode atingir o tempo limite após cerca de 30 segundos enquanto o SQL continua em execução, portanto verifique o resultado antes de repetir uma operação de gravação. Use [`cloud clickhouse client`](#services) para scripts com várias instruções, cargas em massa e consultas longas. A allowlist de IPs do serviço restringe as conexões diretas, não a rota da API de consultas via proxy. Consultar um serviço ocioso o reativa; um serviço parado deve ser iniciado com `cloud clickhouse start`.

Gerencie o Endpoint da API de Consultas do serviço, os endpoints SQL nomeados e as consultas salvas:

```bash
clickhousectl cloud clickhouse query-endpoint get <service-id>
clickhousectl cloud clickhouse query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` substitui as funções de cada chave vinculada ao endpoint. Consulte [Comportamento do SQL e da API de consultas](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md).

### Managed Postgres {#postgres-services}

`cloud postgres` (alias `cloud pg`) gerencia o [ClickHouse Managed Postgres](/pt-BR/products/managed-postgres/overview). O suporte ao GCP está em prévia privada.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> --ha-type sync --standby-count 2
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres update <postgres-id> --deletion-protection true
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

Os tamanhos disponíveis na AWS incluem `m6gd.large`, `c6gd.xlarge` e `r6gd.xlarge`. No GCP, passe `--provider gcp` com uma região do GCP e um tamanho como `c4-standard-lssd-4`.

Guarde a senha e a string de conexão retornadas pelo `create`. As respostas posteriores do `get` nunca retornam credenciais, e o `reset-password` é a única forma de obter novas. Conecte-se com o `psql` usando `sslmode=verify-full` e o arquivo da CA.

**Se você omitir as flags de acesso no create, todos os endereços IPv4 e IPv6 serão permitidos no Postgres (5432) e no PgBouncer (6432).** Passe um `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` por regra, ou `--block-public-access` para não definir nenhuma regra. A partir do momento em que você passa uma regra, somente as regras listadas são aplicadas.

`--standby-count` define o número de instâncias em espera quentes no `create` ou no `update`: `--ha-type none` aceita 0, `async` aceita 1 e `sync` aceita 1 ou 2. Com a proteção contra exclusão ativada, a API rejeita o `delete` até que você defina `--deletion-protection false`, nas organizações que têm essa funcionalidade. Para conectividade privada na AWS, `private-endpoint` (create, get, update, delete) gerencia um serviço de endpoint do PrivateLink (Beta); aprove cada endpoint de VPC com `private-endpoint update --add-vpc-endpoint` para que ele possa se conectar.

Monitoramento e recuperação:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` aceita apenas OAuth, portanto falha enquanto houver uma fonte de chave de API de maior prioridade ativa. `metrics`, `slow-queries` e `prometheus` cobrem o monitoramento; `logs`, `metrics`, `slow-queries` e `backup list` também aceitam `--name` no lugar do ID. `restore` copia as regras de acesso IPv4 atuais da origem para o serviço restaurado, a menos que você informe `--ip-allow` ou `--block-public-access`. Restaurações e réplicas são retornadas sem senha. `promote` e `switchover` retornam assim que são aceitos; após um promote, consulte `postgres get --json` periodicamente até que a réplica informe `isPrimary: true`. Consulte o [guia do Managed Postgres](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md).

### ClickPipes {#clickpipes}

`cloud clickpipe` faz a ingestão de dados de armazenamento de objetos, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB e BigQuery. A criação e a descoberta de esquema exigem uma chave de API e um serviço de destino em execução. Cada origem tem seu próprio subcomando `clickpipe create <source>`; execute-o com `--help` para ver suas flags.

Carregue arquivos do S3 usando uma IAM role. Primeiro, descubra o schema e revise-o; em seguida, crie o pipe a partir da saída salva da descoberta:

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" --json > discovery.json
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --columns-from discovery.json
```

`--columns-from` transforma os campos descobertos em colunas de destino; portanto, edite o arquivo antes para remover os campos que você não quer. A criação de ClickPipes para armazenamento de objetos, Kafka, Kinesis e Pub/Sub exige `--columns-from`, pelo menos um `--column name:type` ou ambos; `--column` adiciona colunas às definidas no arquivo.

Replique o Postgres com CDC. O TLS é verificado por padrão; para uma origem Managed Postgres, exporte a CA correspondente e passe-a como parâmetro:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud clickhouse query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` cria tabelas `ReplacingMergeTree`; portanto, leia o estado atual com `FINAL WHERE _peerdb_is_deleted = 0`. Ao criar pipes de Postgres e MySQL, é possível usar `--use-json-native-format true` para armazenar colunas JSON como o tipo `JSON` nativo do ClickHouse em vez de `String` (ClickHouse 25.3+, com a funcionalidade habilitada para a organização). Um pipe do Kafka segue o mesmo padrão do armazenamento de objetos: execute `clickpipe schema-discover kafka` com as mesmas flags de origem e, em seguida, passe as colunas com `--column` ou `--columns-from`:

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

Por padrão, os pipes do BigQuery executam um snapshot. Para CDC, informe `--replication-mode cdc`, um `--replication-method` e, para cada tabela, uma coluna de watermark ou uma função de eventos em `--table-mapping-json`; agende as sincronizações com `--sync-cron` ou `--sync-interval-seconds`. Para operar pipes existentes:

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

Os pipes CDC devem estar no estado `Paused` antes de executar `update`: pare o pipe, consulte `get` repetidamente até que ele esteja no estado `Paused` e, em seguida, atualize-o. O serviço pode retomar o pipe como parte da atualização, portanto, execute `start` somente se `get` ainda mostrar `Paused`. A opção `--start-paused` está disponível para armazenamento de objetos, Kafka, Kinesis e Pub/Sub. Outros grupos de comandos são `cdc-scaling`, `context get` (prontidão e principal da identidade de carga de trabalho do GCP) e `reverse-private-endpoint`. Consulte o [guia do ClickPipes](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) e a [referência de configuração do ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md).

### ClickStack {#clickstack}

`cloud clickstack` gerencia fontes de dados, dashboards, alertas, webhooks, buscas salvas e funções em um serviço existente do [Self-managed ClickHouse Observability](/pt-BR/clickstack/self-configured/deployment/managed). Os recursos são arquivos JSON (`--file`, ou `-` para stdin). As operações de leitura aceitam OAuth; as de gravação exigem uma chave de API.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**Cada atualização do ClickStack substitui o recurso por completo.** Salve o estado atual com `get --json` e envie a definição completa, não apenas os campos alterados. Consulte o [guia do ClickStack](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md).

clickhousectl cloud udf deploy my_udf --service <service-id>

Em `key update`, as configurações das flags omitidas são mantidas, enquanto `--clear-expiry`, `--clear-roles` e `--clear-ip-allow` as removem.

## Saída JSON {#json-output}

Os comandos que retornam dados estruturados aceitam `--json`, incluindo os comandos locais, do Cloud, `skills`, `update` e `telemetry`:

```bash
clickhousectl cloud clickhouse list --json
clickhousectl cloud key list --all --json
clickhousectl local clickhouse list --json
```

Quando a CLI detecta um agente de programação (como Claude Code, Cursor, Codex, Gemini CLI, Goose ou Devin, ou qualquer ferramenta que defina `AI_AGENT`), ela seleciona JSON automaticamente. Os clientes SQL e nativos mantêm seus próprios formatos: `cloud clickhouse query` retorna `JSONEachRow` no modo JSON, e a saída de `local client` é sempre nativa. Scripts que interpretam a saída de consultas devem passar `--format` explicitamente. Para manter a saída legível por humanos mesmo quando um agente for detectado, defina `CLICKHOUSECTL_AUTO_JSON=0`; a opção explícita `--json` continua selecionando JSON.

Comandos assíncronos do Cloud, como `clickhouse create`, `postgres create` e `clickpipe start`, adicionam à saída JSON um objeto `next` que indica a consulta de acompanhamento a executar: `command` (com IDs resolvidos e `--org-id`), o campo `field` a monitorar, os valores de `until` que indicam a conclusão, os valores de `fail_on` e um valor sugerido para `interval_seconds`. O comando continua retornando assim que a API aceita a requisição.

No modo JSON, os erros em tempo de execução são enviados para stderr como um objeto com um `code` estável e uma `message`:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

Defina o fluxo condicional com base em `error.code`, não na mensagem. Erros de uso continuam em formato de texto, com código de saída 2, e nada é enviado. Consulte [automação e contratos de saída](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md) para saber mais sobre as estruturas de saída e os códigos de erro.

## Códigos de saída {#exit-codes}

| Código | Significado                                                                                                                                                                 |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`    | Sucesso. Para operações assíncronas do Cloud, a requisição foi aceita, mas ainda não foi concluída                                                                          |
| `1`    | Erro, incluindo uma resposta HTTP 403 que recusa uma requisição (código `http_4xx`)                                                                                         |
| `2`    | Erro de uso, incluindo valores inválidos de opções de linha de comando e entradas verificadas após o parsing, mas que não podem ser processadas com sucesso; nada é enviado |
| `3`    | Um prompt interativo foi cancelado, como o seletor de `skills`                                                                                                              |
| `4`    | Autenticação necessária ou rejeitada, incluindo tentativas de gravação com OAuth                                                                                            |

`local client`, `local postgres client` e outras formas de delegação da execução a clientes nativos repassam o status de saída do próprio cliente.

## Habilidades de agentes {#skills}

Instale o [ClickHouse Agent Skills oficial](https://github.com/ClickHouse/agent-skills) nos seus agentes de programação:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

Por padrão, as Skills são instaladas no projeto atual ou, com `--global`, no seu diretório pessoal. O diretório compartilhado `.agents/skills/` é sempre incluído. Sem um terminal, é necessário especificar `--agent`, `--all` ou `--detected-only`. Execute `clickhousectl skills --help` para ver os nomes dos agentes compatíveis.

## Busca e feedback {#search-and-feedback}

```bash
clickhousectl search ip allow                   # Find commands and flags by keyword
clickhousectl search idle timeout --limit 10
clickhousectl feedback "cloud clickhouse create should accept a --wait flag"
```

`search <words>` busca correspondências em nomes de comandos, descrições, flags e contexto do agente e lista os comandos mais relevantes (por padrão, 5). Uma busca sem correspondências termina com código de saída 0 e sem resultados.

`feedback` envia uma mensagem curta (no máximo 500 caracteres) à equipe do clickhousectl, sem solicitar entrada nem confirmação. Use esse comando para informar o que a CLI não conseguiu fazer ou o que você esperava. Coloque opções como `--json` antes da mensagem e não inclua credenciais, SQL, hostnames nem dados pessoais. Ao usar credenciais do Cloud, a mensagem inclui os IDs das organizações às quais essas credenciais pertencem. Consulte [o que é enviado pelo comando feedback](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/feedback.md).

## Autoatualização {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

`update` substitui instalações feitas pelo script de instalação, por download ou pelo Cargo. Para instalações via npm, uv, pipx e pip, o comando termina com código de saída 1 e exibe o comando de upgrade do gerenciador de pacotes a ser executado como alternativa.

A CLI também verifica se há atualizações em segundo plano, no máximo uma vez a cada 24 horas (se a verificação falhar, uma nova tentativa será feita após uma hora), e exibe um aviso quando há uma versão mais recente disponível. Defina `CLICKHOUSECTL_NO_UPDATE_CHECK=1` para desativar a verificação e o aviso.

## Telemetria {#telemetry}

`clickhousectl` coleta dados anônimos de uso para orientar o desenvolvimento. Na primeira execução, exibe um aviso e não envia nada; a coleta começa em uma execução posterior, a menos que você a desative.

Cada evento contém:

* O caminho do comando e os **nomes** das flags e dos argumentos passados explicitamente, nunca seus valores
* O resultado e o código de saída
* Para um comando digitado incorretamente, o nome do comando ou da opção de linha de comando sugerido pela CLI, nunca o que você digitou
* Para falhas em tempo de execução, categorias predefinidas: etapa e tipo da falha, um código de status HTTP presente em uma allowlist e categorias de novas tentativas, estado de provisionamento e duração
* A versão da CLI, o SO e a arquitetura, se a execução ocorre em um ambiente de CI e o agente de programação detectado

Valores dos argumentos, SQL, credenciais, identificadores de recursos, argumentos após `--` e mensagens de erro nunca são registrados. Não há ID de instalação ou de dispositivo.

Para desativar a coleta:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

Defina `CHCTL_TELEMETRY_DEBUG=1` para exibir a carga útil em stderr sem enviar nada. Desativar a telemetria não bloqueia [`feedback`](#search-and-feedback), que só envia dados quando você o executa. Consulte os [detalhes da telemetria](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md).
