## Pré-requisitos {#prerequisites}

Para os exemplos deste artigo, você precisará:

* ter uma instância do servidor do ClickHouse em execução
* ter o `curl` instalado. No Ubuntu ou Debian, execute `sudo apt install curl` ou consulte esta [documentação](https://curl.se/download.html) para ver as instruções de instalação.

## Visão geral {#overview}

A interface HTTP permite usar o ClickHouse em qualquer plataforma e com qualquer linguagem de programação, por meio de uma API REST. A interface HTTP é mais limitada que a interface nativa, mas oferece melhor suporte a linguagens de programação.

Por padrão, o `clickhouse-server` escuta nas seguintes portas:

* porta 8123 para HTTP
* a porta 8443 para HTTPS pode ser habilitada

Ao fazer uma requisição `GET /` sem parâmetros, você recebe o código de resposta 200 junto com a string &quot;Ok.&quot;:

```bash
$ curl 'http://localhost:8123/'
Ok.
```

&quot;Ok.&quot; é o valor default definido em [`http_server_default_response`](/pt-BR/reference/settings/server-settings/settings/http#http_server_default_response) e pode ser alterado, se necessário.

Veja também: [Ressalvas sobre códigos de resposta HTTP](#http_response_codes_caveats).

## Interface web do usuário {#web-ui}

O ClickHouse inclui uma interface web, que pode ser acessada pelo seguinte endereço:

```text
http://localhost:8123/play
```

A interface web permite exibir o progresso durante a execução da consulta, cancelar consultas e fazer streaming de resultados.
Ela tem uma funcionalidade secreta para exibir gráficos e grafos de pipelines de consulta.

Após uma consulta ser executada com sucesso, aparece um botão de download que permite baixar os resultados da consulta em vários formatos, incluindo CSV, TSV, JSON, JSONLines, Parquet, Markdown ou qualquer formato personalizado compatível com o ClickHouse. A funcionalidade de download usa o cache de consultas para recuperar os resultados de forma eficiente, sem executar a consulta novamente. Ela baixa o conjunto de resultados completo, mesmo que a UI tenha exibido apenas uma de várias páginas.

A interface web foi projetada para profissionais como você.

Em scripts de verificação de saúde, use a requisição `GET /ping`. Este handler sempre retorna &quot;Ok.&quot; (com uma quebra de linha no final). Disponível a partir da versão 18.12.13. Veja também `/replicas_status` para verificar o atraso da réplica.

```bash
$ curl 'http://localhost:8123/ping'
Ok.
$ curl 'http://localhost:8123/replicas_status'
Ok.
```

## Execução de consultas via HTTP/HTTPS {#querying}

Há três opções para executar consultas via HTTP/HTTPS:

* enviar a requisição no parâmetro de URL &#39;query&#39;
* usar o método POST.
* Enviar o início da consulta no parâmetro &#39;query&#39; e o restante via POST

<Note>
  Por padrão, o tamanho da URL é limitado a 1 MiB; isso pode ser alterado com a configuração `http_max_uri_size`.
</Note>

Em caso de sucesso, você recebe o código de resposta 200 e o resultado no corpo da resposta.
Se ocorrer um erro, você recebe o código de resposta 500 e um texto descrevendo o erro no corpo da resposta.

Requisições GET são &#39;readonly&#39;. Ou seja, para consultas que modificam dados, só é possível usar o método POST.
Você pode enviar a consulta propriamente dita no corpo do POST ou no parâmetro de URL. Vejamos alguns exemplos.

No exemplo abaixo, o curl é usado para enviar a consulta `SELECT 1`. Observe o uso da codificação de URL para o espaço: `%20`.

```bash title="command"
curl 'http://localhost:8123/?query=SELECT%201'
```

```response title="Response"
1
```

Neste exemplo, o wget é usado com os parâmetros `-nv` (modo não detalhado) e `-O-` para enviar o resultado para o terminal.
Nesse caso, não é necessário usar codificação de URL para o espaço:

```bash title="command"
wget -nv -O- 'http://localhost:8123/?query=SELECT 1'
```

```response
1
```

Neste exemplo, enviamos uma requisição HTTP bruta ao netcat por meio de um pipe:

```bash title="command"
echo -ne 'GET /?query=SELECT%201 HTTP/1.0\r\n\r\n' | nc localhost 8123
```

```response title="response"

X-ClickHouse-Summary: {"read_rows":"1","read_bytes":"1","written_rows":"0","written_bytes":"0","total_rows_to_read":"1","result_rows":"0","result_bytes":"0","elapsed_ns":"4505959","memory_usage":"1111711"}
```

Como você pode ver, o comando `curl` é um tanto inconveniente, pois os espaços precisam ser escapados na URL.
Embora o `wget` escape tudo automaticamente, não recomendamos usá-lo, pois ele não funciona bem com HTTP 1.1 ao usar keep-alive e Transfer-Encoding: chunked.

```bash
$ echo 'SELECT 1' | curl 'http://localhost:8123/' --data-binary @-
1

$ echo 'SELECT 1' | curl 'http://localhost:8123/?query=' --data-binary @-
1

$ echo '1' | curl 'http://localhost:8123/?query=SELECT' --data-binary @-
1
```

Se parte da consulta for enviada no parâmetro e parte no POST, uma quebra de linha será inserida entre essas duas partes de dados.
Por exemplo, isto não funcionará:

```bash
$ echo 'ECT 1' | curl 'http://localhost:8123/?query=SEL' --data-binary @-

ECT 1
, expected One of: SHOW TABLES, SHOW DATABASES, SELECT, INSERT, CREATE, ATTACH, RENAME, DROP, DETACH, USE, SET, OPTIMIZE., e.what() = DB::Exception
```

Por padrão, os dados são retornados no formato [`TabSeparated`](/pt-BR/reference/formats/TabSeparated/TabSeparated).

A cláusula `FORMAT` é usada na consulta para solicitar qualquer outro formato. Por exemplo:

```bash title="command"
wget -nv -O- 'http://localhost:8123/?query=SELECT 1, 2, 3 FORMAT JSON'
```

```response title="Response"

            "type": "UInt8"

```

Você pode usar o parâmetro de URL `default_format` para especificar um formato padrão diferente de `TabSeparated`. O cabeçalho `X-ClickHouse-Format` seleciona explicitamente o formato da resposta: ele é um alias para a configuração `output_format`, portanto também se sobrepõe a uma cláusula `FORMAT` na consulta. Esse cabeçalho nunca altera a forma como o corpo da requisição de um `INSERT` é interpretado — use `input_format` ou `format` para isso. Para restaurar o comportamento das versões anteriores à versão 26.8, nas quais o cabeçalho era um alias para `default_format` e não se sobrepunha a uma cláusula `FORMAT`, desative a configuração `http_x_clickhouse_format_overrides_output_format` (em um perfil de usuário ou como parâmetro de URL; assim como as próprias configurações de formato, ela pode ser alterada no modo somente leitura).

```bash
$ echo 'SELECT 1 FORMAT Pretty' | curl 'http://localhost:8123/?' --data-binary @-
┏━━━┓
┃ 1 ┃
┡━━━┩
│ 1 │
└───┘
```

Você pode usar o método POST com consultas parametrizadas. Os parâmetros são especificados entre chaves, com o nome e o tipo do parâmetro, como em `{name:Type}`. Os valores dos parâmetros são passados por meio de `param_name`:

```bash
$ curl -X POST -F 'query=select {p1:UInt8} + {p2:UInt8}' -F "param_p1=3" -F "param_p2=4" 'http://localhost:8123/'

7
```

## Acesse tabelas por meio de caminhos de URL e construa consultas {#tables-as-files}

Disponível a partir do ClickHouse 26.8.

A interface HTTP pode interpretar um caminho da URL como um banco de dados, uma tabela, um formato de saída e um método de compressão. Em seguida, os parâmetros de URL podem definir a estrutura do resultado, de modo que requisições de leitura simples dispensam SQL. Essas funcionalidades estão habilitadas por padrão desde o ClickHouse 26.10; nas versões 26.8 e 26.9, era necessário habilitá-las explicitamente.

### Configurações de roteamento por caminho {#enabling-path-routing}

A interpretação de caminhos é controlada em dois níveis:

1. O parâmetro de configuração `http_allow_path_requests`, em nível de servidor, permite que a interface HTTP roteie requisições no estilo de caminho para o handler de consultas. Ele vem habilitado por padrão; defina-o como `0` para que todo caminho que não corresponda a um handler configurado volte a retornar `404`:

```xml
<clickhouse>
    <http_allow_path_requests>0</http_allow_path_requests>
</clickhouse>
```

2. As configurações por usuário abaixo determinam como um caminho roteado é interpretado. Todas, exceto `http_allow_filters_as_unrecognized_url_parameters`, vêm habilitadas por padrão, e cada uma pode ser habilitada ou desabilitada por usuário, função ou perfil:

| Configuração                                        | Efeito                                                                                                |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `http_allow_table_as_file`                          | Interpreta o último componente de caminho como `table`, `table.format` ou `table.format.compression`. |
| `http_allow_database_as_path`                       | Interpreta um componente de caminho inicial `/database/` como o banco de dados atual.                 |
| `http_allow_filters_as_path`                        | Interpreta componentes de caminho Hive-style `/name=value/` como filtros `WHERE`.                     |
| `http_allow_filters_as_unrecognized_url_parameters` | Interpreta parâmetros de URL não reconhecidos como filtros `WHERE`. Desabilitado por padrão.          |

<Note>
  O roteamento ocorre antes da autenticação, portanto não pode depender de uma configuração por usuário. Quando `http_allow_path_requests` está desabilitado, um caminho desconhecido retorna um `404` ainda na pré-autenticação. Após o roteamento e a autenticação, as configurações por usuário determinam como o caminho é interpretado, o que permite habilitar ou desativar a funcionalidade seletivamente para um usuário, função ou perfil.
</Note>

<Note>
  `http_allow_filters_as_unrecognized_url_parameters` permanece desabilitado por padrão porque se aplica a todas as requisições da interface HTTP, incluindo o endpoint `/?query=...`: quando habilitado, qualquer parâmetro de URL não reconhecido que um cliente acrescente se torna um filtro da consulta. Com isso, um nome de configuração digitado incorretamente deixa de ser reportado como `UNKNOWN_SETTING` e passa a falhar com `UNKNOWN_IDENTIFIER` — ou, se o nome coincidir com uma coluna da tabela consultada, filtra o resultado silenciosamente.
</Note>

### Acessar tabelas como arquivos {#table-as-file-examples}

Com `http_allow_table_as_file` habilitado, uma requisição para `/table.format.compression` é processada como `SELECT * FROM table`. Além disso, `http_allow_database_as_path` permite `/database/table.format.compression`.

```bash
# SELECT * FROM my_db.hits, formatted as CSV
curl 'http://localhost:8123/my_db/hits.csv'

# The same result, compressed with gzip
curl 'http://localhost:8123/my_db/hits.csv.gz' | gzip -d
```

As extensões de formato e de compressão são reconhecidas sem distinguir maiúsculas de minúsculas, portanto `hits.csv` e `hits.CSV` são equivalentes.

Um parâmetro de URL `format` ou `output_format` explícito substitui o formato indicado no caminho. O `default_format` não tem esse efeito: ele apenas define o formato a ser usado quando nenhum outro o especifica, e a extensão no caminho é mais específica. Um parâmetro `compression` explícito deve corresponder à compressão indicada no caminho; valores conflitantes geram uma exceção.

### Construir uma consulta {#query-construction}

As configurações a seguir envolvem a consulta base como uma tabela derivada. Elas podem ser combinadas entre si e com uma consulta existente. Você pode fornecê-las como parâmetros de URL HTTP, em uma cláusula `SETTINGS` dentro da consulta ou por meio de um perfil de usuário.

| Configuração                                                                                                                | Efeito                                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `select`                                                                                                                    | `SELECT <expression_list> FROM (…)`                                                                                                                                                                                                      |
| `filter`                                                                                                                    | Adiciona `WHERE <expression>`. Vários parâmetros de URL `filter` são combinados com `AND`.                                                                                                                                               |
| `order`                                                                                                                     | Adiciona `ORDER BY <expression_list>`.                                                                                                                                                                                                   |
| `sort`                                                                                                                      | Adiciona `ORDER BY` a partir de uma lista de identificadores ou posições de coluna separados por vírgula, cada um com um prefixo opcional `+` (crescente) ou `-` (decrescente), como em `sort=a,-b`. Não pode ser combinado com `order`. |
| [`limit`](/pt-BR/reference/settings/session-settings/other#limit) e [`offset`](/pt-BR/reference/settings/session-settings/other#offset) | Adicionam `LIMIT <n> OFFSET <m>`. Ambos aceitam valores negativos para selecionar a partir do final e valores fracionários que representam uma proporção das linhas.                                                                     |
| `page`                                                                                                                      | Define `offset = limit * (page - 1)`. Requer `limit` e não pode ser combinado com `offset`.                                                                                                                                              |

```bash
# Filter my_db.hits, sort by a descending, and return the first 10 rows
curl 'http://localhost:8123/my_db/hits?filter=a%3E0&sort=-a&limit=10'

# Return the second page of 100 rows
curl 'http://localhost:8123/my_db/hits?limit=100&page=2'
```

#### Modificar uma consulta existente {#modify-an-existing-query}

As configurações de construção não se limitam a requisições por caminho: elas também moldam uma consulta que você mesmo escreve. A consulta passa a ser a tabela derivada, de modo que as configurações se aplicam ao resultado dela, em vez de serem mescladas a ela. Por exemplo, `?query=SELECT a, b FROM hits&filter=a > 0&sort=-b&limit=10` é executada como:

```sql
SELECT * FROM (SELECT a, b FROM hits) WHERE a > 0 ORDER BY b DESC LIMIT 10
```

Isso é útil para paginar, ordenar ou filtrar o resultado de uma consulta definida em outro lugar — em uma consulta salva de um dashboard, em um `predefined_query_handler` ou em um cliente que só permite acrescentar parâmetros de URL:

```bash
# Page through the result of an arbitrary query without editing the query text
curl 'http://localhost:8123/?query=SELECT+a,+b+FROM+hits+GROUP+BY+a,+b&limit=100&page=3'

# Keep only some of the resulting columns and rows
curl -G 'http://localhost:8123/' --data-urlencode 'query=SELECT * FROM hits' --data-urlencode 'select=a, b' --data-urlencode 'filter=b != 0'

# The last 5 rows of an aggregate (a negative `limit` selects from the tail)
curl 'http://localhost:8123/?query=SELECT+a,+count()+FROM+hits+GROUP+BY+a+ORDER+BY+a&limit=-5'
```

Como as configurações envolvem a consulta em vez de reescrevê-la, elas podem ser combinadas com uma cláusula `FORMAT` e com um `ORDER BY` dentro da consulta, e nunca alteram quais linhas um `INSERT` grava: uma configuração de construção aplicada a uma instrução `INSERT ... SELECT` molda o próprio resultado (vazio) da instrução, e não o seu `SELECT` de origem. Para moldar a origem, coloque a configuração na cláusula `SETTINGS` do próprio `SELECT`:

```sql
-- Inserts all 10 rows: `limit` applies to the INSERT statement, not to its SELECT
INSERT INTO t SETTINGS limit = 2 SELECT number FROM numbers(10);

-- Inserts 2 rows: `limit` applies to the SELECT itself
INSERT INTO t SELECT number FROM numbers(10) SETTINGS limit = 2;
```

<Warning>
  `filter` não é um mecanismo de controle de acesso. Ele adiciona uma cláusula `WHERE` a uma subconsulta que encapsula a consulta original, de modo que os dados subjacentes podem ser lidos e processados antes da aplicação do filtro. Para restringir quais linhas um usuário pode acessar, use [row policies](/pt-BR/concepts/features/security/access-rights#row-policy-management) ou [`additional_table_filters`](/pt-BR/reference/settings/session-settings/additional#additional_table_filters).
</Warning>

### Substituição de formatos e compressão {#format-and-compression-overrides}

| Configuração     | Efeito                                                                                                                                                                                                                                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `output_format`  | Substitui o formato de saída. Tem precedência sobre a cláusula `FORMAT` da consulta, a extensão do caminho, `format` e `default_format`. Também pode ser definida por meio do cabeçalho `X-ClickHouse-Format`. Com `http_x_clickhouse_format_overrides_output_format = 0`, o cabeçalho passa a definir `default_format`, como nas versões anteriores à 26.8. |
| `input_format`   | Substitui o formato de entrada para `INSERT`. Tem precedência sobre a cláusula `FORMAT` da consulta e sobre `format`.                                                                                                                                                                                                                                        |
| `format`         | Substitui o formato em ambas as direções, a menos que seja fornecida uma configuração específica para uma das direções.                                                                                                                                                                                                                                      |
| `default_format` | Define o formato de saída quando a consulta não tem cláusula `FORMAT`, extensão de caminho nem outra substituição de formato.                                                                                                                                                                                                                                |
| `compression`    | Comprime o corpo da resposta, por exemplo, com `compression=gz`. Funciona independentemente do `Content-Encoding` do HTTP e do parâmetro `compress` nativo do ClickHouse.                                                                                                                                                                                    |

As configurações de formato também funcionam com outros protocolos, incluindo o cliente nativo e o `clickhouse-local`. `input_format` e `output_format` correspondem às opções `--input-format` e `--output-format`. No `clickhouse-local`, a opção `--format` corresponde à configuração bidirecional `format`; já no `clickhouse-client`, ela mantém seu significado histórico, restrito à saída, e corresponde a `output_format`.

`compression` é específica da modelagem de respostas HTTP e é consumida antes da execução da consulta. Forneça-a por meio de um parâmetro de URL HTTP, de uma extensão de caminho ou de um perfil de usuário. Ela é rejeitada quando usada em uma cláusula `SETTINGS` dentro da consulta.

Respostas HTTP binárias e comprimidas incluem um cabeçalho `Content-Disposition: attachment; filename=…`. O nome do arquivo é derivado do caminho da URL ou, quando o caminho não fornece um, assume o padrão `result.<format>.<compression>`.

### Usar uma tabela no caminho com uma consulta {#implicit-table}

Quando o caminho identifica uma tabela e você também fornece um parâmetro `query`, a tabela no caminho é exposta por meio de [`implicit_table_at_top_level`](/pt-BR/reference/settings/session-settings/implicit#implicit_table_at_top_level). Um `SELECT` sem cláusula `FROM` lê os dados da tabela no caminho:

```bash
# Read columns a and b from my_db.hits without a FROM clause
curl 'http://localhost:8123/my_db/hits.CSV?query=SELECT+a,+b'
```

Se a consulta já contiver uma cláusula `FROM`, o componente de caminho fornecerá apenas o nome do arquivo a ser baixado.

### Enviar dados para uma tabela no caminho {#path-table-inserts}

Uma requisição HTTP `PUT` para `/database/table.format` insere o corpo da requisição em uma tabela existente. Por padrão, o formato de entrada é definido pela extensão do caminho. Assim como em um `INSERT` comum, a configuração `input_format` tem precedência sobre o formato do caminho e, em seguida, vem a configuração bidirecional `format`. A requisição deve conter pelo menos um byte decodificado e não pode incluir o parâmetro `query`. Isso é útil quando o nome do arquivo já contém tanto a tabela de destino quanto o formato de entrada:

```bash
printf '1,"one"\n2,"two"\n' \
  | curl -X PUT -H 'Content-Type: text/csv' --data-binary @- \
      'http://localhost:8123/my_db/hits.CSV'

printf '{"a":3,"b":"three"}\n' \
  | curl -X PUT -H 'Content-Type: application/json' --data-binary @- \
      'http://localhost:8123/my_db/hits.JSONEachRow'
```

A tabela já deve existir. Para um envio com prefixo de banco de dados, `http_allow_database_as_path` habilita o
caminho `/database/table.format`. Um envio não qualificado para `/table.format` continua exigindo
`http_allow_table_as_file`. O corpo da requisição pode usar um sufixo de compressão, como `.CSV.gz`; o servidor
o descomprime antes de inserir as linhas. Envios `PUT` para tabelas no caminho usam a semântica normal de `INSERT`; portanto, repetir
a mesma requisição pode inserir as linhas novamente. Criação automática, inferência de esquema e upload em múltiplas partes não são
compatíveis. Use a forma padrão de [`INSERT` via HTTP](#insert-queries) quando for necessário personalizar o comportamento da consulta ou do
envio.

O último componente de caminho é decodificado com percent-encoding após a divisão do caminho; portanto, um ponto de formato codificado, como
`hits%2ECSV`, também é aceito.

```bash
# The path suffix describes the compressed request body.
gzip -c rows.csv \
  | curl -X PUT --data-binary @- \
      'http://localhost:8123/my_db/hits.CSV.gz'
```

## Consultas de insert via HTTP/HTTPS {#insert-queries}

O método `POST` tradicional de transmissão de dados é útil quando a consulta precisa ser fornecida explicitamente. Você pode escrever o início da consulta no parâmetro de URL e usar POST para enviar os dados a serem inseridos. Esses dados podem ser, por exemplo, um dump tab-separated do MySQL. Dessa forma, a consulta `INSERT` substitui o `LOAD DATA LOCAL INFILE` do MySQL.

### Exemplos {#examples}

Para criar uma tabela:

```bash
$ echo 'CREATE TABLE t (a UInt8) ENGINE = Memory' | curl 'http://localhost:8123/' --data-binary @-
```

Para inserir dados usando a já conhecida consulta `INSERT`:

```bash
$ echo 'INSERT INTO t VALUES (1),(2),(3)' | curl 'http://localhost:8123/' --data-binary @-
```

Para enviar os dados separadamente da consulta:

```bash
$ echo '(4),(5),(6)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20VALUES' --data-binary @-
```

É possível especificar qualquer formato de dados. Por exemplo, pode-se especificar o formato &#39;Values&#39;, o mesmo usado ao escrever `INSERT INTO t VALUES`:

```bash
$ echo '(7),(8),(9)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20Values' --data-binary @-
```

Para inserir dados de um dump no formato tab-separated, especifique o formato correspondente:

```bash
$ echo -ne '10\n11\n12\n' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20TabSeparated' --data-binary @-
```

O mesmo vale para qualquer outro [formato de entrada](/pt-BR/reference/formats), como CSV com uma linha de cabeçalho ou um objeto JSON por linha:

```bash
$ echo -ne 'a\n13\n14\n' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20CSVWithNames' --data-binary @-
$ echo '{"a":15} {"a":16}' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20JSONEachRow' --data-binary @-
```

Para inserir o conteúdo de um arquivo, passe o nome dele para `--data-binary` com o prefixo `@`:

```bash
$ echo -ne '17\n18\n' > data.csv
$ curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20CSV' --data-binary @data.csv
```

<Warning>

### Inserir dados Protobuf {#insert-protobuf}

Formatos binários como [`Protobuf`](/pt-BR/reference/formats/Protobuf/Protobuf) são enviados da mesma forma, já que `--data-binary` repassa os bytes sem alterações.
As configurações exigidas pelo formato, como [`format_schema`](/pt-BR/reference/settings/formats/format-schema#format_schema), são passadas como parâmetros de URL junto com `query`, assim como qualquer outra configuração.

Os exemplos abaixo usam esta tabela e o arquivo de esquema `message.proto`, localizado no diretório [`format_schema_path`](/pt-BR/reference/settings/server-settings/settings/format#format_schema_path) do servidor:

```bash
$ echo 'CREATE TABLE protobuf_messages (name String, surname String, birthDate UInt32, phoneNumbers Array(String)) ENGINE = Memory' | curl 'http://localhost:8123/' --data-binary @-
```

```protobuf
syntax = "proto3";

message MessageType {
  string name = 1;
  string surname = 2;
  uint32 birthDate = 3;
  repeated string phoneNumbers = 4;
}
```

Para obter um arquivo de mensagens Protobuf a ser inserido, este exemplo usa o ClickHouse para gerá-lo:

```bash
$ echo "SELECT 'Aisha' AS name, 'Khan' AS surname, 19920815 AS birthDate, ['(555) 247-8903', '(555) 612-3457'] AS phoneNumbers FORMAT Protobuf" | curl 'http://localhost:8123/?format_schema=message:MessageType' --data-binary @- > messages.bin
```

Para inserir o arquivo, informe o nome do arquivo de esquema e o tipo de mensagem em `format_schema`:

```bash
$ curl 'http://localhost:8123/?query=INSERT%20INTO%20protobuf_messages%20FORMAT%20Protobuf&format_schema=message:MessageType' --data-binary @messages.bin
```

Quando não for possível colocar um arquivo de esquema no servidor, como no ClickHouse Cloud, envie o próprio schema com [`format_schema_source`](/pt-BR/reference/settings/formats/format-schema#format_schema_source) definido como `string` e informe o nome do tipo de mensagem em [`format_schema_message_name`](/pt-BR/reference/settings/formats/format-schema#format_schema_message_name).
A opção `--url-query` do curl (curl 7.87 ou posterior) aplica a codificação de URL a cada parâmetro, de modo que a consulta e o schema podem ser escritos sem alterações:

```bash
$ curl 'http://localhost:8123/' \
    --url-query 'query=INSERT INTO protobuf_messages FORMAT Protobuf' \
    --url-query 'format_schema_source=string' \
    --url-query 'format_schema=syntax = "proto3"; message MessageType { string name = 1; string surname = 2; uint32 birthDate = 3; repeated string phoneNumbers = 4; }' \
    --url-query 'format_schema_message_name=MessageType' \
    --data-binary @messages.bin
```

Para ler o conteúdo da tabela:

```bash
$ curl 'http://localhost:8123/?query=SELECT%20*%20FROM%20protobuf_messages'
Aisha	Khan	19920815	['(555) 247-8903','(555) 612-3457']
Aisha	Khan	19920815	['(555) 247-8903','(555) 612-3457']
```

`Protobuf` espera que cada mensagem seja precedida por seu comprimento codificado como varint.
Para uma única mensagem sem o prefixo, use [`ProtobufSingle`](/pt-BR/reference/formats/Protobuf/ProtobufSingle); para linhas enviadas como submensagens de uma única mensagem `Envelope`, use [`ProtobufList`](/pt-BR/reference/formats/Protobuf/ProtobufList).

## Compressão {#compression}

A compressão pode ser usada para reduzir o tráfego de rede ao transmitir grandes volumes de dados ou para criar dumps já comprimidos.

Você pode usar o formato de compressão interno do ClickHouse ao transmitir dados. Os dados comprimidos têm um formato não padrão, e é necessário o programa `clickhouse-compressor` para trabalhar com eles. Ele é instalado por padrão com o pacote `clickhouse-client`.

Para aumentar a eficiência da inserção de dados, desative a verificação de checksum no lado do servidor usando a configuração [`http_native_compression_disable_checksumming_on_decompress`](/pt-BR/reference/settings/session-settings/http#http_native_compression_disable_checksumming_on_decompress).

Se você especificar `compress=1` na URL, o servidor comprimirá os dados que enviar para você. Se você especificar `decompress=1` na URL, o servidor descomprimirá os dados que você enviar pelo método `POST`.

Você também pode usar [compressão HTTP](https://en.wikipedia.org/wiki/HTTP_compression). O ClickHouse oferece suporte aos seguintes [métodos de compressão](https://en.wikipedia.org/wiki/HTTP_compression#Content-Encoding_tokens):

* `gzip`
* `br`
* `deflate`
* `xz`
* `zstd`
* `lz4`
* `bz2`
* `snappy`

Para enviar uma requisição `POST` comprimida, adicione o cabeçalho de requisição `Content-Encoding: compression_method`.

Para que o ClickHouse comprima a resposta, adicione o cabeçalho `Accept-Encoding: compression_method` à requisição.

Você pode configurar o nível de compressão de dados de todos os métodos de compressão com a configuração [`http_zlib_compression_level`](/pt-BR/reference/settings/session-settings/http#http_zlib_compression_level).

<Info>
  Alguns clientes HTTP podem descomprimir por padrão os dados recebidos do servidor (com `gzip` e `deflate`), e você pode acabar recebendo dados descompactados mesmo usando as configurações de compressão corretamente.
</Info>

## Exemplos {#examples-compression}

Para enviar dados comprimidos ao servidor:

```bash
echo "SELECT 1" | gzip -c | \
curl -sS --data-binary @- -H 'Content-Encoding: gzip' 'http://localhost:8123/'
```

Para receber o arquivo de dados comprimido do servidor:

```bash
curl -vsS "http://localhost:8123/?enable_http_compression=1" \
-H 'Accept-Encoding: gzip' --output result.gz -d 'SELECT number FROM system.numbers LIMIT 3'

zcat result.gz
0
1
2
```

Para receber dados comprimidos do servidor e usar o gunzip para obter os dados descompactados:

```bash
curl -sS "http://localhost:8123/?enable_http_compression=1" \
-H 'Accept-Encoding: gzip' -d 'SELECT number FROM system.numbers LIMIT 3' | gunzip -
0
1
2
```

## Usando sessões do ClickHouse no protocolo HTTP {#using-clickhouse-sessions-in-the-http-protocol}

Você também pode usar sessões do ClickHouse no protocolo HTTP. Para isso, adicione o parâmetro `GET` `session_id` à requisição. Qualquer string pode ser usada como ID de sessão.

Por padrão, a sessão é encerrada após 60 segundos de inatividade. Para alterar esse tempo limite (em segundos), modifique a configuração `default_session_timeout` na configuração do servidor ou adicione o parâmetro `GET` `session_timeout` à requisição.

Para verificar o status da sessão, use o parâmetro `session_check=1`. Só é possível executar uma consulta por vez em uma mesma sessão.

Você pode receber informações sobre o progresso de uma consulta nos cabeçalhos de resposta `X-ClickHouse-Progress`. Para isso, habilite [`send_progress_in_http_headers`](/pt-BR/reference/settings/session-settings/send#send_progress_in_http_headers).

Veja abaixo um exemplo da sequência de cabeçalhos:

```text
X-ClickHouse-Progress: {"read_rows":"261636","read_bytes":"2093088","total_rows_to_read":"1000000","elapsed_ns":"14050417","memory_usage":"22205975"}
X-ClickHouse-Progress: {"read_rows":"654090","read_bytes":"5232720","total_rows_to_read":"1000000","elapsed_ns":"27948667","memory_usage":"83400279"}
X-ClickHouse-Progress: {"read_rows":"1000000","read_bytes":"8000000","total_rows_to_read":"1000000","elapsed_ns":"38002417","memory_usage":"80715679"}
```

Os campos de cabeçalho possíveis são:

| Campo de cabeçalho   | Descrição                                                                  |
| -------------------- | -------------------------------------------------------------------------- |
| `read_rows`          | Número de linhas lidas.                                                    |
| `read_bytes`         | Volume de dados lidos em bytes.                                            |
| `total_rows_to_read` | Número total de linhas a serem lidas.                                      |
| `written_rows`       | Número de linhas gravadas.                                                 |
| `written_bytes`      | Volume de dados gravados em bytes.                                         |
| `elapsed_ns`         | Tempo de execução da consulta em nanossegundos.                            |
| `memory_usage`       | Memória usada pela consulta, em bytes. (**Disponível a partir da v25.11**) |

As requisições em execução não são interrompidas automaticamente se a conexão HTTP for perdida. O parsing e a formatação dos dados são realizados no lado do servidor, e o uso da rede pode ser ineficiente.

Os seguintes parâmetros opcionais estão disponíveis:

| Parâmetros             | Descrição                                                                                                                                                             |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `query_id` (opcional)  | Pode ser fornecido como ID da consulta (qualquer string). [`replace_running_query`](/pt-BR/reference/settings/session-settings/replace-running-query#replace_running_query) |
| `quota_key` (opcional) | Pode ser fornecido como chave de cota (qualquer string). [&quot;Cotas&quot;](/pt-BR/concepts/features/configuration/server-config/quotas)                                   |

A interface HTTP permite fornecer dados externos (tabelas temporárias externas) para execução de consultas. Para obter mais informações, consulte [&quot;Dados externos para processamento de consultas&quot;](/pt-BR/reference/engines/table-engines/special/external-data).

## Armazenamento em buffer da resposta {#response-buffering}

O armazenamento em buffer da resposta pode ser habilitado no lado do servidor. Para isso, são fornecidos os seguintes parâmetros de URL:

* `buffer_size`
* `wait_end_of_query`

As seguintes configurações podem ser usadas:

* [`http_response_buffer_size`](/pt-BR/reference/settings/session-settings/http-response#http_response_buffer_size)
* [`http_wait_end_of_query`](/pt-BR/reference/settings/session-settings/http#http_wait_end_of_query)

`buffer_size` determina o número de bytes do resultado a serem armazenados em buffer na memória do servidor. Se o corpo do resultado for maior que esse limiar, o buffer será gravado no canal HTTP e os dados restantes serão enviados diretamente para o canal HTTP.

Para garantir que toda a resposta seja armazenada em buffer, defina `wait_end_of_query=1`. Nesse caso, os dados que não estiverem armazenados em memória serão armazenados em buffer em um arquivo temporário no servidor.

Por exemplo:

```bash
curl -sS 'http://localhost:8123/?max_result_bytes=4000000&buffer_size=3000000&wait_end_of_query=1' -d 'SELECT toUInt8(number) FROM system.numbers LIMIT 9000000 FORMAT RowBinary'
```

<Tip>
  Use a bufferização para evitar situações em que ocorre um erro de processamento de consultas depois que o código de resposta e os cabeçalhos HTTP já foram enviados ao cliente. Nesse caso, uma mensagem de erro é gravada no final do corpo da resposta e, no client-side, o erro só pode ser detectado na etapa de parsing.
</Tip>

## Definindo uma função com parâmetros de consulta {#setting-role-with-query-parameters}

Esta funcionalidade foi adicionada no ClickHouse 24.4.

Em situações específicas, pode ser necessário definir a função concedida antes de executar a instrução em si.
No entanto, não é possível enviar `SET ROLE` e a instrução juntos, pois não é permitido enviar múltiplas instruções:

```bash
curl -sS "http://localhost:8123" --data-binary "SET ROLE my_role;SELECT * FROM my_table;"
```

O comando acima gera um erro:

```sql
Code: 62. DB::Exception: Syntax error (Multi-statements are not allowed)
```

Para contornar essa limitação, use o parâmetro de consulta `role`:

```bash
curl -sS "http://localhost:8123?role=my_role" --data-binary "SELECT * FROM my_table;"
```

Isso equivale a executar `SET ROLE my_role` antes da instrução.

Além disso, é possível especificar vários parâmetros de consulta `role`:

```bash
curl -sS "http://localhost:8123?role=my_role&role=my_other_role" --data-binary "SELECT * FROM my_table;"
```

Nesse caso, `?role=my_role&role=my_other_role` funciona de forma semelhante a executar `SET ROLE my_role, my_other_role` antes da instrução.

O parâmetro de consulta `role` não é afetado pela configuração do servidor `access_control_improvements.readonly_restricts_set_role`, que bloqueia apenas as instruções `SET ROLE` e `SET DEFAULT ROLE`.

## Ressalvas sobre códigos de resposta HTTP {#http_response_codes_caveats}

Devido às limitações do protocolo HTTP, um código de resposta HTTP 200 não garante que uma consulta tenha sido bem-sucedida.

Veja um exemplo:

```bash
curl -v -Ss "http://localhost:8123/?max_block_size=1&query=select+sleepEachRow(0.001),throwIf(number=2)from+numbers(5)"
*   Trying 127.0.0.1:8123...
...
< HTTP/1.1 200 OK
...
Code: 395. DB::Exception: Value passed to 'throwIf' function is non-zero: while executing 'FUNCTION throwIf(equals(number, 2) :: 1) -> throwIf(equals(number, 2))
```

O motivo desse comportamento é a natureza do protocolo HTTP. O cabeçalho HTTP é enviado primeiro com o código HTTP 200, seguido pelo corpo HTTP, e então o erro é injetado no corpo como texto simples.

Esse comportamento independe do formato utilizado, seja `Native`, `TSV` ou `JSON`; a mensagem de erro sempre estará no meio do fluxo de resposta.

Você pode mitigar esse problema habilitando `wait_end_of_query=1` ([bufferização de resposta](#response-buffering)). Nesse caso, o envio do cabeçalho HTTP é adiado até que toda a consulta seja concluída. No entanto, isso não resolve completamente o problema, pois o resultado ainda precisa caber em [`http_response_buffer_size`](/pt-BR/reference/settings/session-settings/http-response#http_response_buffer_size), e outras configurações, como [`send_progress_in_http_headers`](/pt-BR/reference/settings/session-settings/send#send_progress_in_http_headers), podem interferir no adiamento do cabeçalho.

<Tip>
  A única forma de capturar todos os erros é analisar o corpo HTTP antes de fazer o parsing com o formato exigido.
</Tip>

Essas exceções no ClickHouse têm um formato consistente, como mostrado abaixo, independentemente do formato utilizado (por exemplo, `Native`, `TSV`, `JSON` etc.) quando `http_write_exception_in_output_format=0` (padrão). Isso facilita interpretar e extrair mensagens de erro no lado do cliente.

```text
\r\n
__exception__\r\n
<TAG>\r\n
<error message>\r\n
<message_length> <TAG>\r\n
__exception__\r\n

```

Aqui, `<TAG>` é uma tag aleatória de 16 bytes, a mesma enviada no cabeçalho de resposta `X-ClickHouse-Exception-Tag`.
O `<error message>` é a mensagem de exceção propriamente dita (o comprimento exato é indicado em `<message_length>`). O bloco de exceção completo descrito acima pode ter até 16 KiB.

Veja a seguir um exemplo no formato `JSON`

### Tabulações em parâmetros de URL {#tabs-in-url-parameters}

Os parâmetros de consulta são interpretados a partir do formato &quot;escapado&quot;. Isso traz alguns benefícios, como a possibilidade de interpretar valores NULL de forma inequívoca como `\N`. Assim, o caractere de tabulação deve ser codificado como `\t` (ou `\` seguido de uma tabulação). Por exemplo, o conteúdo a seguir contém uma tabulação real entre `abc` e `123`, e a string de entrada é dividida em dois valores:

```bash
curl -sS "http://localhost:8123" -d "SELECT splitByChar('\t', 'abc      123')"
```

```response
['abc','123']
```

No entanto, se você tentar codificar um caractere de tabulação usando `%09` em um parâmetro de URL, ele não será interpretado corretamente:

```bash
curl -sS "http://localhost:8123?param_arg1=abc%09123" -d "SELECT splitByChar('\t', {arg1:String})"
Code: 457. DB::Exception: Value abc    123 cannot be parsed as String for query parameter 'arg1' because it isn't parsed completely: only 3 of 7 bytes was parsed: abc. (BAD_QUERY_PARAMETER) (version 23.4.1.869 (official build))
```

Se você estiver usando parâmetros de URL, precisará codificar `\t` como `%5C%09`. Por exemplo:

```bash
curl -sS "http://localhost:8123?param_arg1=abc%5C%09123" -d "SELECT splitByChar('\t', {arg1:String})"
```

```response
['abc','123']
```

## Interface HTTP Predefinida {#predefined_http_interface}

O ClickHouse oferece suporte a consultas específicas por meio da interface HTTP. Por exemplo, você pode gravar dados em uma tabela da seguinte forma:

```bash
$ echo '(4),(5),(6)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20VALUES' --data-binary @-
```

O ClickHouse também oferece uma Interface HTTP Predefinida que facilita a integração com ferramentas de terceiros, como o [exportador do Prometheus](https://github.com/ClickHouse/clickhouse_exporter). Vejamos um exemplo.

Os mesmos manipuladores também podem ser definidos via SQL, sem editar o arquivo de configuração do servidor — consulte [`CREATE HANDLER`](/pt-BR/reference/statements/create/handler).

Primeiro, adicione esta seção ao arquivo de configuração do servidor.

`http_handlers` é configurado para conter várias entradas `rule`. O ClickHouse compara as requisições HTTP recebidas com o tipo predefinido em `rule` e executa o handler da primeira regra correspondente. Se houver uma correspondência, o ClickHouse executa a consulta predefinida correspondente.

```yaml title="config.xml"
<http_handlers>
    <rule>
        <url>/predefined_query</url>
        <methods>POST,GET</methods>
        <handler>
            <type>predefined_query_handler</type>
            <query>SELECT * FROM system.metrics LIMIT 5 FORMAT Template SETTINGS format_template_resultset = 'prometheus_template_output_format_resultset', format_template_row = 'prometheus_template_output_format_row', format_template_rows_between_delimiter = '\n'</query>
        </handler>
    </rule>
    <rule>...</rule>
    <rule>...</rule>
</http_handlers>
```

As opções de configuração de `http_handlers` funcionam da seguinte forma.

`rule` permite configurar os seguintes parâmetros:

* `method`
* `headers`
* `url`
* `full_url`
* `handler`

Cada um deles é abordado a seguir:

* `method` é responsável por verificar a correspondência do método da requisição HTTP. `method` segue integralmente a definição de [`method`]
  (https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods) no protocolo HTTP. É uma configuração opcional. Se não estiver definido no
  arquivo de configuração, não verifica a correspondência do método da requisição HTTP.

* `url` é responsável por verificar a correspondência da URL (caminho e string de consulta) da requisição HTTP.
  Se `url` tiver o prefixo `regex:`, espera-se uma expressão regular do [RE2](https://github.com/google/re2).
  É uma configuração opcional. Se não estiver definido no arquivo de configuração, não verifica a correspondência da URL da requisição HTTP.

* `full_url` funciona como `url`, mas inclui a URL completa, ou seja, `schema://host:port/path?query_string`.
  Observe que o ClickHouse não oferece suporte a &quot;hosts virtuais&quot;, portanto, `host` é um endereço IP (e não o valor do cabeçalho `Host`).

* `empty_query_string` - garante que não haja string de consulta (`?query_string`) na requisição

* `headers` é responsável por verificar a correspondência dos cabeçalhos da requisição HTTP. É compatível com as expressões regulares do RE2. É uma configuração opcional.
  Se não estiver definido no arquivo de configuração, não verifica a correspondência dos cabeçalhos da requisição HTTP.

* `handler` contém a parte principal do processamento.

  Pode ter um dos seguintes valores de `type`:

  * [`predefined_query_handler`](#predefined_query_handler)
  * [`dynamic_query_handler`](#dynamic_query_handler)
  * [`static`](#static)
  * [`redirect`](#redirect)

  E os seguintes parâmetros:

  * `query` — usado com o tipo `predefined_query_handler`; executa a consulta quando o handler é chamado.
  * `query_param_name` — usado com o tipo `dynamic_query_handler`; extrai e executa o valor do parâmetro de requisição HTTP cujo nome é indicado por
    `query_param_name`.
  * `status` — usado com o tipo `static`; define o código de status da resposta.
  * `content_type` — usado com qualquer tipo; define o [tipo de conteúdo](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Type) da resposta.
  * `http_response_headers` — usado com qualquer tipo; define um mapa de cabeçalhos de resposta. Também pode ser usado para definir o tipo de conteúdo.
  * `response_content` — usado com o tipo `static`; define o conteúdo da resposta enviado ao cliente. Ao usar o prefixo &#39;file://&#39; ou &#39;config://&#39;, obtém o conteúdo
    do arquivo ou da configuração e o envia ao cliente.
  * `user` - usuário em nome do qual a consulta será executada (o usuário default é `default`).
    **Nota**: não é necessário especificar a senha desse usuário.

Os métodos de configuração para os diferentes valores de `type` são apresentados a seguir.

### predefined_query_handler {#predefined_query_handler}

`predefined_query_handler` permite definir os valores de `Settings` e `query_params`. Você pode configurar `query` para o tipo `predefined_query_handler`.

O valor de `query` é uma consulta predefinida de `predefined_query_handler`, que o ClickHouse executa quando uma requisição HTTP corresponde à regra, retornando o resultado da consulta. Essa configuração é obrigatória.

O exemplo a seguir define os valores das configurações [`max_threads`](/pt-BR/reference/settings/session-settings/max-threads#max_threads) e [`max_final_threads`](/pt-BR/reference/settings/session-settings/max#max_final_threads) e, em seguida, consulta a tabela de sistema para verificar se essas configurações foram aplicadas corretamente.

<Note>
  Para manter os `handlers` padrão, como ` query`, `play` e ` ping`, adicione a regra `<defaults/>`.
</Note>

Por exemplo:

```yaml
<http_handlers>
    <rule>
        <url><![CDATA[regex:/query_param_with_url/(?P<name_1>[^/]+)]]></url>
        <methods>GET</methods>
        <headers>
            <XXX>TEST_HEADER_VALUE</XXX>
            <PARAMS_XXX><![CDATA[regex:(?P<name_2>[^/]+)]]></PARAMS_XXX>
        </headers>
        <handler>
            <type>predefined_query_handler</type>
            <query>
                SELECT name, value FROM system.settings
                WHERE name IN ({name_1:String}, {name_2:String})
            </query>
        </handler>
    </rule>
    <defaults/>
</http_handlers>
```

```bash
curl -H 'XXX:TEST_HEADER_VALUE' -H 'PARAMS_XXX:max_final_threads' 'http://localhost:8123/query_param_with_url/max_threads?max_threads=1&max_final_threads=2'
max_final_threads    2
max_threads    1
```

#### Parâmetro virtual `_request_body` {#virtual-param-request-body}

Além de parâmetros de URL, cabeçalhos e parâmetros de consulta, `predefined_query_handler` oferece suporte a um parâmetro virtual especial chamado `_request_body`.
Ele contém o corpo bruto da requisição HTTP como uma string.
Seu valor é sempre obtido do corpo da requisição: qualquer tentativa de passar `_request_body` (ou `param__request_body`) na URL ou de capturá-lo com um grupo nomeado nas expressões regulares de `url` ou `headers` é rejeitada com uma exceção. Um valor de `_request_body` definido em uma sessão nomeada (`SET param__request_body = ...`) é ignorado.
Isso permite criar APIs REST flexíveis que aceitam dados em formatos arbitrários e os processam nas suas consultas.

Por exemplo, você pode usar `_request_body` para implementar um endpoint REST que aceita dados JSON em uma requisição POST e os insere em uma tabela:

```yaml
<http_handlers>
    <rule>
        <methods>POST</methods>
        <url>/api/events</url>
        <handler>
            <type>predefined_query_handler</type>
            <query>
                INSERT INTO events (id, data)
                SELECT {id:UInt32}, {_request_body:String}
            </query>
        </handler>
    </rule>
    <defaults/>
</http_handlers>
```

Em seguida, você pode enviar dados para este endpoint:

```bash
curl -X POST 'http://localhost:8123/api/events?id=123' \
  -H 'Content-Type: application/json' \
  -d '{"user": "john", "action": "login", "timestamp": "2024-01-01T10:00:00Z"}'
```

<Note>
  Cada `predefined_query_handler` aceita apenas uma `query`.
</Note>

### dynamic_query_handler {#dynamic_query_handler}

Em `dynamic_query_handler`, a consulta é fornecida como um parâmetro da requisição HTTP. A diferença é que, em `predefined_query_handler`, a consulta é definida no arquivo de configuração. É possível configurar `query_param_name` em `dynamic_query_handler`.

O ClickHouse extrai e executa o valor do parâmetro identificado por `query_param_name` na URL da requisição HTTP. O valor default de `query_param_name` é `/query`. Essa configuração é opcional. Se ela não estiver definida no arquivo de configuração, o parâmetro não será passado.

Para testar essa funcionalidade, o exemplo a seguir define os valores de [`max_threads`](/pt-BR/reference/settings/session-settings/max-threads#max_threads) e `max_final_threads` e usa `queries` para verificar se as configurações foram aplicadas com sucesso.

Exemplo:

```yaml
<http_handlers>
    <rule>
    <headers>
        <XXX>TEST_HEADER_VALUE_DYNAMIC</XXX>    </headers>
    <handler>
        <type>dynamic_query_handler</type>
        <query_param_name>query_param</query_param_name>
    </handler>
    </rule>
    <defaults/>
</http_handlers>
```

```bash
curl  -H 'XXX:TEST_HEADER_VALUE_DYNAMIC'  'http://localhost:8123/own?max_threads=1&max_final_threads=2&param_name_1=max_threads&param_name_2=max_final_threads&query_param=SELECT%20name,value%20FROM%20system.settings%20where%20name%20=%20%7Bname_1:String%7D%20OR%20name%20=%20%7Bname_2:String%7D'
max_threads 1
max_final_threads   2
```

### static {#static}

`static` pode retornar [`content_type`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Type), [status](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status) e `response_content`. `response_content` pode retornar o conteúdo especificado.

Por exemplo, para retornar a mensagem &quot;Diga olá!&quot;:

```yaml highlight={14}
<http_handlers>
        <rule>
            <methods>GET</methods>
            <headers><XXX>xxx</XXX></headers>
            <url>/hi</url>
            <handler>
                <type>static</type>
                <status>402</status>
                <content_type>text/html; charset=UTF-8</content_type>
                <http_response_headers>
                    <Content-Language>en</Content-Language>
                    <X-My-Custom-Header>43</X-My-Custom-Header>
                </http_response_headers>
                <response_content>Say Hi!</response_content>
            </handler>
        </rule>
        <defaults/>
</http_handlers>
```

### redirect {#redirect}

`redirect` faz um redirecionamento `302` para `location`

Por exemplo, para definir automaticamente o usuário como `play` no ClickHouse Play:

```xml
<clickhouse>
    <http_handlers>
        <rule>
            <methods>GET</methods>
            <url>/play</url>
            <handler>
                <type>redirect</type>
                <location>/play?user=play</location>
            </handler>
        </rule>
    </http_handlers>
</clickhouse>
```

## Cabeçalhos de resposta HTTP {#http-response-headers}

O ClickHouse permite configurar cabeçalhos de resposta HTTP personalizados que podem ser aplicados a qualquer tipo de handler configurável. Esses cabeçalhos podem ser definidos com a configuração `http_response_headers`, que aceita pares chave-valor com os nomes dos cabeçalhos e seus respectivos valores. Essa funcionalidade é especialmente útil para implementar cabeçalhos de segurança personalizados, políticas de CORS ou atender a outros requisitos de cabeçalhos HTTP em toda a interface HTTP do ClickHouse.

Por exemplo, você pode configurar cabeçalhos para:

* Endpoints de consulta comuns
* Interface web
* Verificação de integridade.

Também é possível especificar `common_http_response_headers`. Esses cabeçalhos serão aplicados a todos os manipuladores HTTP definidos na configuração.

Os cabeçalhos serão incluídos na resposta HTTP de cada handler configurado.

No exemplo abaixo, cada resposta do servidor conterá dois cabeçalhos personalizados: `X-My-Common-Header` e `X-My-Custom-Header`.

```xml
<clickhouse>
    <http_handlers>
        <common_http_response_headers>
            <X-My-Common-Header>Common header</X-My-Common-Header>
        </common_http_response_headers>
        <rule>
            <methods>GET</methods>
            <url>/ping</url>
            <handler>
                <type>ping</type>
                <http_response_headers>
                    <X-My-Custom-Header>Custom indeed</X-My-Custom-Header>
                </http_response_headers>
            </handler>
        </rule>
    </http_handlers>
</clickhouse>
```

## Resposta JSON/XML válida em caso de exceção durante streaming HTTP {#valid-output-on-exception-http-streaming}

Durante a execução de uma consulta por HTTP, pode ocorrer uma exceção depois que parte dos dados já tiver sido enviada. Normalmente, a exceção é enviada ao cliente em texto simples.
Isso ocorre mesmo quando um formato de dados específico é usado na saída, o que pode torná-la inválida para o formato especificado.
Para evitar isso, você pode usar a configuração [`http_write_exception_in_output_format`](/pt-BR/reference/settings/session-settings/http#http_write_exception_in_output_format) (desabilitada por padrão), que instrui o ClickHouse a gravar a exceção no formato especificado (atualmente disponível para os formatos XML e JSON*).

Exemplos:

```bash
            "number": "0",

        },
        {
            "number": "1",
            "throwIf(greater(number, 2))": 0
        },
        {
            "number": "2",
            "throwIf(greater(number, 2))": 0
        }
    ],

    "rows": 3,

}
```
