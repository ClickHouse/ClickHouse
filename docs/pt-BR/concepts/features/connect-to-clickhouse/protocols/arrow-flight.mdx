## Visão geral {#overview}

O ClickHouse oferece suporte ao protocolo [Apache Arrow Flight](https://arrow.apache.org/docs/format/Flight.html), um framework RPC de alto desempenho para o transporte eficiente de dados colunares que usa o formato [Arrow IPC](https://arrow.apache.org/docs/format/Columnar.html#serialization-and-interprocess-communication-ipc) sobre [gRPC](https://grpc.io/).

A implementação inclui suporte ao [Arrow Flight SQL](https://arrow.apache.org/docs/format/FlightSql.html), o que permite que ferramentas de BI e aplicações compatíveis com o protocolo Flight SQL consultem o ClickHouse diretamente.

Principais recursos:

* Execução de consultas SQL e obtenção de resultados no formato Apache Arrow.
* Inserção de dados em tabelas usando o formato Arrow.
* Consulta de metadados (catálogos, esquemas, tabelas, chaves primárias) por meio de comandos Flight SQL.
* Criação, vinculação, execução e fechamento de instruções preparadas no lado do servidor via Flight SQL.
* Gerenciamento de sessões e configurações por meio de ações Flight SQL.
* Criptografia TLS e autenticação por nome de usuário/senha.
* Obtenção incremental de resultados via `PollFlightInfo`.
* Cancelamento de consultas via `CancelFlightInfo`.

<Note>
  No ClickHouse Cloud, a interface Arrow Flight vem desabilitada por padrão e exige que uma feature flag do Cloud seja habilitada para o seu serviço. Os exemplos de configuração do servidor a seguir se aplicam ao ClickHouse autogerenciado.
</Note>

## Como habilitar o servidor Arrow Flight {#enabling-server}

Para habilitar o servidor Arrow Flight, adicione a configuração `arrowflight_port` às configurações do servidor do ClickHouse:

```xml
<clickhouse>
    <arrowflight_port>9090</arrowflight_port>
</clickhouse>
```

Durante a inicialização, uma mensagem de log confirma que a interface está ativa:

```text
{} <Information> Application: Arrow Flight compatibility protocol: 0.0.0.0:9090
```

## Configuração TLS {#tls-configuration}

Para habilitar o TLS na interface Arrow Flight, configure as seguintes opções:

```xml
<clickhouse>
    <arrowflight_port>9090</arrowflight_port>
    <arrowflight>
        <enable_ssl>true</enable_ssl>
        <ssl_cert_file>/path/to/server-cert.pem</ssl_cert_file>
        <ssl_key_file>/path/to/server-key.pem</ssl_key_file>
    </arrowflight>
</clickhouse>
```

Quando o TLS estiver habilitado, os clientes devem se conectar usando o esquema `grpc+tls://` em vez de `grpc://`.

## Autenticação {#authentication}

A interface Arrow Flight oferece suporte a dois métodos de autenticação:

### Autenticação básica {#basic-auth}

Os clientes se autenticam com nome de usuário e senha por meio do cabeçalho HTTP padrão `Authorization: Basic`. Quando a autenticação é bem-sucedida, o servidor retorna um Token Bearer no cabeçalho de resposta.

### Autenticação com Token Bearer {#bearer-auth}

As requisições seguintes podem usar o Token Bearer retornado pela autenticação básica por meio do cabeçalho `Authorization: Bearer <token>`. O token é renovado automaticamente a cada uso e expira de acordo com a configuração do servidor `default_session_timeout` (padrão: 60 segundos).

### Chamadas sem nome de usuário {#auth-without-user-name}

Uma chamada sem o cabeçalho `authorization`, ou com credenciais Basic cujo nome de usuário esteja vazio, é autenticada como o usuário indicado pela configuração do servidor [`default_session_user`](/pt-BR/reference/settings/server-settings/settings/default#default_session_user) (`default`, salvo configuração em contrário), com a senha fornecida (possivelmente vazia). Isso funciona exatamente como uma requisição HTTP sem o parâmetro `user`.

O nome de usuário vazio é apenas um alias para esse usuário. A senha, `networks` e as demais verificações de acesso desse usuário se aplicam normalmente; portanto, é a configuração dele que determina se uma chamada sem credenciais será aceita.

Se `default_session_user` for definido como uma string vazia, essas chamadas serão rejeitadas com `Unauthenticated`. Quando a seção `session_log` estiver habilitada na configuração do servidor, a rejeição será registrada em [`system.session_log`](/pt-BR/reference/system-tables/session_log) como um evento `LoginFailure` com `user` vazio.

### Exemplo em Python {#auth-python-example}

```python
import pyarrow.flight as flight

client = flight.FlightClient("grpc://localhost:9090")

# Basic auth returns a bearer token for subsequent calls
token_pair = client.authenticate_basic_token("default", "")
options = flight.FlightCallOptions(headers=[token_pair])
```

Com TLS:

```python
import pyarrow.flight as flight

with open("ca-cert.pem", "rb") as f:
    tls_root_certs = f.read()

client = flight.FlightClient(
    "grpc+tls://localhost:9090",
    tls_root_certs=tls_root_certs,
)

token_pair = client.authenticate_basic_token("default", "password")
options = flight.FlightCallOptions(headers=[token_pair])
```

## Gerenciamento de sessões {#session-management}

A interface Arrow Flight oferece suporte a sessões do ClickHouse por meio de cabeçalhos de metadados gRPC personalizados:

| Cabeçalho                      | Descrição                                                                                                                                                               |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `x-clickhouse-session-id`      | Identificador da sessão. Se fornecido, várias requisições compartilham o mesmo estado da sessão (tabelas temporárias, configurações).                                   |
| `x-clickhouse-session-timeout` | Tempo limite da sessão, em segundos. Não pode exceder `max_session_timeout`.                                                                                            |
| `x-clickhouse-session-check`   | Defina como `1` para verificar se a sessão existe sem criar uma nova.                                                                                                   |
| `x-clickhouse-session-close`   | Defina como `1` para encerrar a sessão após a conclusão da requisição. Requer que `enable_arrow_close_session` esteja definido como `true` na configuração do servidor. |

<Note>
  Como o Arrow Flight usa gRPC sobre HTTP/2, os nomes dos cabeçalhos de metadados diferenciam maiúsculas de minúsculas e devem ser especificados em letras minúsculas, exatamente como mostrado (por exemplo, `x-clickhouse-session-id`, e não `X-ClickHouse-Session-Id`). Isso é exigido pela [RFC 9113, Seção 8.2](https://www.rfc-editor.org/rfc/rfc9113#section-8.2), que determina que os nomes de campos HTTP/2 contenham apenas caracteres minúsculos. Já no HTTP/1.1, os nomes de cabeçalhos não diferenciam maiúsculas de minúsculas.
</Note>

As sessões permitem definir configurações persistentes do ClickHouse por meio da ação `SetSessionOptions` (consulte [DoAction](#doaction)).

## Métodos RPC compatíveis {#rpc-methods}

### GetFlightInfo {#getflightinfo}

Executa uma consulta e retorna um `FlightInfo` contendo o schema do resultado, endpoints com tickets para recuperação dos dados, contagem de linhas e contagem de bytes.

Aceita um `FlightDescriptor`, que pode ser:

* **Descritor PATH**: um caminho com um único componente, interpretado como nome de tabela. Gera `SELECT * FROM <table>`.
* **Descritor CMD**: uma string de consulta SQL bruta ou um comando protobuf Flight SQL serializado (consulte [Comandos Flight SQL](#flight-sql-commands)).

A consulta é executada por completo, e os resultados são armazenados em tickets do lado do servidor. Cada bloco de dados gera um endpoint/ticket separado, o que permite que os clientes recuperem os dados em paralelo.

```python
# Query by table name
descriptor = flight.FlightDescriptor.for_path("my_table")
info = client.get_flight_info(descriptor, options)

# Query by SQL
descriptor = flight.FlightDescriptor.for_command(
    "SELECT * FROM my_table WHERE id > 100"
)
info = client.get_flight_info(descriptor, options)

# Retrieve results
for endpoint in info.endpoints:
    reader = client.do_get(endpoint.ticket, options)
    table = reader.read_all()
    print(table.to_pandas())
```

### PollFlightInfo {#pollflightinfo}

Habilita a recuperação incremental de resultados para consultas de longa duração. Em vez de aguardar a conclusão de toda a consulta (como faz o `GetFlightInfo`), o `PollFlightInfo` retorna os resultados bloco a bloco.

Na primeira chamada, a execução da consulta é iniciada. A resposta inclui:

* Um `FlightInfo` com endpoints para os blocos de dados disponíveis até o momento.
* Um `FlightDescriptor` para a próxima consulta (caso mais resultados sejam esperados).

As chamadas seguintes com o descritor retornado recuperam blocos adicionais. Quando não há mais dados disponíveis, a resposta não contém um próximo descritor.

<Note>
  A implementação atual fica bloqueada até que um bloco de dados esteja disponível, em vez de retornar imediatamente sem dados.
</Note>

### GetSchema {#getschema}

Retorna o schema Arrow do resultado de uma consulta sem executar a consulta completa. Aceita os mesmos tipos de descritor que `GetFlightInfo`.

```python
descriptor = flight.FlightDescriptor.for_command(
    "SELECT 1 AS x, 'hello' AS y"
)
schema_result = client.get_schema(descriptor, options)
schema = schema_result.schema
print(schema)  # x: int32, y: string
```

### DoGet {#doget}

Recupera os dados de um determinado ticket. Aceita uma das seguintes opções:

* Um ticket retornado por `GetFlightInfo` ou `PollFlightInfo`.
* Uma string de consulta SQL bruta como valor do ticket.

```python
# Using a ticket from GetFlightInfo
reader = client.do_get(endpoint.ticket, options)
table = reader.read_all()

# Using a raw SQL query as ticket
ticket = flight.Ticket("SELECT number FROM system.numbers LIMIT 10")
reader = client.do_get(ticket, options)
table = reader.read_all()
```

### DoPut {#doput}

Envia dados ao ClickHouse. Aceita um `FlightDescriptor` e um stream de lotes de registros Arrow.

**Insert por nome da tabela** (descritor PATH):

```python
schema = pa.schema([("id", pa.int64()), ("name", pa.string())])
batch = pa.record_batch(
    [pa.array([1, 2, 3]), pa.array(["Alice", "Bob", "Charlie"])],
    schema=schema,
)

descriptor = flight.FlightDescriptor.for_path("my_table")
writer, _ = client.do_put(descriptor, schema, options)
writer.write_batch(batch)
writer.close()
```

**Insert via SQL** (descritor CMD):

```python
descriptor = flight.FlightDescriptor.for_command(
    "INSERT INTO my_table FORMAT Arrow"
)
writer, _ = client.do_put(descriptor, schema, options)
writer.write_batch(batch)
writer.close()
```

**Executar DDL/DML via Flight SQL `CommandStatementUpdate`:**

Os clientes Flight SQL usam `CommandStatementUpdate` para executar instruções DDL/DML (CREATE, INSERT, ALTER etc.). A resposta inclui a contagem de linhas afetadas.

**Ingestão em massa via Flight SQL `CommandStatementIngest`:**

Só é possível acrescentar dados a tabelas existentes (`TABLE_NOT_EXIST_OPTION_FAIL` + `TABLE_EXISTS_OPTION_APPEND`). Catálogos e tabelas temporárias não são suportados por este comando.

`transaction_id` não é suportado em `CommandStatementUpdate` nem em `CommandStatementIngest`. Se for informado, o ClickHouse retorna um erro `NotImplemented`.

<Note>
  Somente o formato `Arrow` é aceito para transferência de dados. Especificar outros formatos no SQL (por exemplo, `FORMAT JSON`) gera um erro.
</Note>

### DoAction {#doaction}

Executa ações nomeadas. As seguintes ações são suportadas:

#### CancelFlightInfo {#cancelflightinfo}

Cancela uma consulta em execução associada a um `FlightInfo`. O ID da consulta é extraído do campo `app_metadata` do `FlightInfo`. Também cancela todos os descritores de sondagem associados à consulta.

```python
# Start a long-running query via PollFlightInfo, then cancel it
cancel_request = flight.CancelFlightInfoRequest(info)
result = client.cancel_flight_info(cancel_request, options)
# result.status is CancelStatus.CANCELLED if successful
```

#### SetSessionOptions {#setsessionoptions}

Define configurações do servidor ClickHouse para a sessão atual. Requer que um ID de sessão seja definido por meio do cabeçalho `x-clickhouse-session-id`.

Tipos de valor compatíveis: string, booleano, inteiro, double e listas de strings.

Se o nome da configuração for desconhecido, será retornado o erro `INVALID_NAME`. Se um valor não puder ser interpretado, será retornado o erro `INVALID_VALUE`.

#### GetSessionOptions {#getsessionoptions}

Retorna todas as configurações atuais do ClickHouse e seus valores para a sessão. Retorna um mapa de nomes de configurações para valores do tipo string (consulta `system.settings` internamente).

#### CreatePreparedStatement {#createpreparedstatement}

Cria uma instrução preparada no lado do servidor e retorna um identificador de instrução. A requisição contém o texto da consulta SQL com marcadores de posição `?`.

`transaction_id` não é suportado nesta ação. Se for informado, o ClickHouse retorna um erro `NotImplemented`.

Para instruções de consulta, a resposta pode incluir:

* `dataset_schema`: schema do conjunto de resultados.
* `parameter_schema`: schema dos parâmetros da instrução.

Se a inferência de esquema falhar para uma consulta válida (por exemplo, quando substituir os marcadores de posição por `NULL` não for válido para essa consulta), o ClickHouse ainda assim cria a instrução preparada e retorna o identificador sem `dataset_schema`.

`dataset_schema` é apenas uma estimativa, como prevê a especificação do Flight SQL: ela estabelece que o schema do resultado pode depender dos parâmetros, que o servidor deve fornecer sua melhor estimativa e que os clientes não devem presumir que o schema seja exato. Não confie nele; execute a instrução para obter o schema que de fato descreve os dados. No ClickHouse, ele pode diferir do que é retornado por dois motivos:

* A inferência substitui cada `?` por `NULL`, de modo que um marcador de posição que determina uma coluna do resultado recebe o tipo desse `NULL`, e não o do valor que você vincular depois. `SELECT ? AS x` infere uma coluna do tipo `Nothing`, mas, ao vincular `5`, o retorno é um `UInt8`. Um marcador de posição usado apenas em um predicado, como em `SELECT id, name FROM t WHERE id = ?`, não tem esse problema, porque os tipos do resultado vêm da tabela.
* Uma coluna sem equivalente em Arrow obtém seu tipo Arrow de [`output_format_arrow_unsupported_types`](/pt-BR/reference/settings/formats/output-format), que cada chamada resolve a partir da sessão que a realiza. Como um identificador pertence ao usuário, e não a uma única sessão, uma chamada posterior pode resolver essa configuração de outra forma e retornar `binary` onde `utf8` foi anunciado, ou vice-versa. Definir o modo dentro da própria consulta preparada o fixa para ambos.

As instruções preparadas pertencem ao usuário autenticado, e não a uma única sessão. Se você abrir várias sessões com o mesmo usuário, poderá executar, vincular novamente e fechar o mesmo identificador de instrução em qualquer uma dessas sessões.

Outros usuários não podem executar, vincular nem fechar um identificador de instrução que não criaram.

`arrowflight.prepared_statements_lifetime_seconds` controla o comportamento de expiração:

* `> 0`: usa o valor configurado como ciclo de vida da instrução. A expiração é renovada a cada requisição, tanto para instruções session-bound quanto session-less.
* `0`: as instruções preparadas não expiram automaticamente.
* `-1` (padrão): se a instrução for criada em uma sessão, seu ciclo de vida acompanha o tempo limite dessa sessão e é renovado a cada requisição nela. Se a instrução for criada sem sessão, ela não expira automaticamente.

As instruções expiradas são removidas e deixam de contar para `arrowflight.max_prepared_statements_per_user`.

#### ClosePreparedStatement {#closepreparedstatement}

Fecha uma instrução preparada e libera os recursos associados no lado do servidor quando a requisição contém um identificador de instrução não vazio.

O ClickHouse também permite o fechamento em massa com `ClosePreparedStatement` quando o identificador está vazio:

* Se `x-clickhouse-session-id` estiver presente, são fechadas todas as instruções preparadas do usuário autenticado nessa sessão.
* Se nenhum ID de sessão estiver presente, são fechadas apenas as instruções preparadas session-less do usuário autenticado.

Se uma instrução preparada for criada em uma sessão (via `x-clickhouse-session-id`), ela também será fechada automaticamente quando essa sessão for encerrada.

## Comandos Flight SQL {#flight-sql-commands}

Quando um descritor `CMD` contém uma mensagem [protobuf do Flight SQL](https://arrow.apache.org/docs/format/FlightSql.html) serializada, o ClickHouse processa os seguintes comandos:

### Compatíveis via GetFlightInfo / GetSchema {#flightsql-getflightinfo}

| Comando                         | Descrição                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `CommandStatementQuery`         | Executa uma consulta SQL arbitrária. `transaction_id` não é suportado.                                              |
| `CommandGetSqlInfo`             | Recupera metadados do servidor (nome, versão, versão do Arrow, capabilities).                                       |
| `CommandGetCatalogs`            | Lista os catálogos. Retorna um resultado vazio (o ClickHouse não usa catálogos).                                    |
| `CommandGetDbSchemas`           | Lista os bancos de dados. Aceita o parâmetro opcional `db_schema_filter_pattern` (pattern SQL `LIKE`).              |
| `CommandGetTables`              | Lista as tabelas. Aceita filtros por schema, nome da tabela e tipos de tabela, além da inclusão opcional do schema. |
| `CommandGetTableTypes`          | Lista os tipos de motor de tabela (a partir de `system.table_engines`).                                             |
| `CommandGetPrimaryKeys`         | Recupera as colunas da chave primária de uma tabela especificada.                                                   |
| `CommandPreparedStatementQuery` | Executa uma instrução preparada do tipo `SELECT` por meio de seu identificador.                                     |

### Compatíveis via DoPut {#flightsql-doput}

| Comando                          | Descrição                                                                                                                                                                                                                                                                                                                               |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CommandStatementUpdate`         | Executa uma instrução DDL/DML (CREATE, INSERT, ALTER etc.). Retorna a contagem de linhas afetadas. `transaction_id` não é suportado.                                                                                                                                                                                                    |
| `CommandStatementIngest`         | Realiza a inserção em massa de dados Arrow em uma tabela existente. Somente o modo de acréscimo é suportado. `transaction_id` não é suportado.                                                                                                                                                                                          |
| `CommandPreparedStatementQuery`  | Vincula valores de parâmetros a uma instrução preparada quando enviado via `DoPut` e, em seguida, retorna `DoPutPreparedStatementResult` com o identificador de instrução. Apenas um conjunto de parâmetros (uma linha) é aceito, e o número de valores vinculados deve corresponder exatamente ao número de marcadores de posição `?`. |
| `CommandPreparedStatementUpdate` | Executa uma instrução DDL/DML preparada a partir do seu identificador e retorna a contagem de linhas afetadas.                                                                                                                                                                                                                          |

### Sem suporte no ClickHouse {#flightsql-not-implemented}

Estes comandos correspondem a funcionalidades que o ClickHouse não oferece e, por isso, não são suportados pela interface Arrow Flight SQL.

| Comando                         | Motivo                                                                                                                                                          |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CommandGetCrossReference`      | O ClickHouse não é um banco de dados relacional e não implementa restrições de chave estrangeira; portanto, não há metadados de referência cruzada disponíveis. |
| `CommandGetExportedKeys`        | O ClickHouse não é um banco de dados relacional e não implementa restrições de chave estrangeira; portanto, não há metadados de chaves exportadas disponíveis.  |
| `CommandGetImportedKeys`        | O ClickHouse não é um banco de dados relacional e não implementa restrições de chave estrangeira; portanto, não há metadados de chaves importadas disponíveis.  |
| `CommandStatementSubstraitPlan` | O ClickHouse não oferece suporte a planos Substrait.                                                                                                            |

## Exemplo completo {#complete-example}

```python title="Query"
import pyarrow as pa
import pyarrow.flight as flight

# Connect and authenticate
client = flight.FlightClient("grpc://localhost:9090")
token = client.authenticate_basic_token("default", "")
options = flight.FlightCallOptions(headers=[token])

# Insert data using DoPut with a PATH descriptor
schema = pa.schema([("id", pa.uint32()), ("value", pa.string())])
batch = pa.record_batch(
    [pa.array([1, 2, 3], type=pa.uint32()), pa.array(["a", "b", "c"])],
    schema=schema,
)
descriptor = flight.FlightDescriptor.for_path("test")
writer, _ = client.do_put(descriptor, schema, options)
writer.write_batch(batch)
writer.close()

# Query data using GetFlightInfo + DoGet
descriptor = flight.FlightDescriptor.for_command(
    "SELECT * FROM test ORDER BY id"
)
info = client.get_flight_info(descriptor, options)
for endpoint in info.endpoints:
    reader = client.do_get(endpoint.ticket, options)
    table = reader.read_all()
    print(table.to_pandas())
```

```text title="Response"
   id value
0   1     a
1   2     b
2   3     c
```

## Formato de dados {#data-format}

Todos os dados são transferidos no formato Apache Arrow IPC. Apenas o formato `Arrow` é compatível — especificar outros formatos do ClickHouse (por exemplo, `FORMAT JSON`, `FORMAT CSV`) resulta em erro.

Os tipos de dados do ClickHouse são mapeados para tipos Arrow durante a serialização. O Arrow Flight sempre usa o mapeamento canônico do Arrow e, diferentemente dos formatos de saída `Arrow` e `ArrowStream`, **não** segue as configurações `output_format_arrow_*` que alteram a forma como um tipo é representado — `output_format_arrow_string_as_string`, `output_format_arrow_low_cardinality_as_dictionary`, `output_format_arrow_date_as_uint16`, `output_format_arrow_fixed_string_as_fixed_byte_array` e as configurações de índice de dicionário não têm efeito aqui. Portanto, a mesma consulta pode produzir, intencionalmente, um schema diferente via Arrow Flight do que via `FORMAT Arrow`, por dois motivos:

* O Flight SQL fixa o schema de suas respostas de metadados. `CommandGetTables`, por exemplo, deve retornar `catalog_name: utf8, db_schema_name: utf8, table_name: utf8 not null, table_type: utf8 not null, table_schema: bytes not null`. Permitir que uma configuração de sessão transformasse essas colunas `utf8` em `binary` tornaria o ClickHouse não conforme para todos os drivers Flight SQL, além de alterar o schema por tabela que o ClickHouse anuncia dentro de `table_schema`.
* Um cliente Flight obtém o schema e os dados em chamadas separadas (`GetFlightInfo` ou `GetSchema`, e depois `DoGet`). Qualquer configuração capaz de alterar o schema permitiria que o schema anunciado e o stream entregue divergissem caso a sessão mudasse nesse intervalo.

A única exceção é um tipo que não tem nenhum equivalente no Arrow, como `JSON`, `Dynamic`, `QBit` ou `AggregateFunction`. Como não há mapeamento canônico a seguir, o ClickHouse precisa escolher uma representação, e [`output_format_arrow_unsupported_types`](/pt-BR/reference/settings/formats/output-format) permite definir qual:

| Valor             | Comportamento                                                                                                  |
| ----------------- | -------------------------------------------------------------------------------------------------------------- |
| `throw`           | A consulta é rejeitada.                                                                                        |
| `text`            | Um valor por linha em sua forma textual, como uma coluna Arrow `Utf8` — o que `CAST(col AS String)` retorna.   |
| `binary` (padrão) | Um valor por linha em sua forma binária, como uma coluna Arrow `Binary` — a codificação usada por `RowBinary`. |

Uma coluna `AggregateFunction` é o único tipo que continua sendo uma coluna Arrow `Binary` mesmo no modo `text`: sua forma textual é o estado de agregação bruto, que não é UTF-8 válido, e uma coluna Arrow `Utf8` deve conter UTF-8 válido. Use `finalizeAggregation` se quiser um valor legível.

Pelo mesmo motivo, o ClickHouse substitui toda sequência UTF-8 inválida em um valor `text` por U+FFFD (`�`) antes de gravá-lo na coluna `Utf8`. Um `Dynamic` contendo uma `String` serializa esses bytes literalmente, e eles podem ser arbitrários; sem essa substituição, a coluna violaria a especificação do Arrow e poderia ser rejeitada por um cliente estrito. Apenas valores que já não são texto válido são alterados. Use o modo `binary` quando os bytes precisarem ser preservados exatamente.

`output_format_arrow_string_as_string` nunca se aplica a essas colunas, nem mesmo em `FORMAT Arrow` — ela rege apenas colunas `String` e `FixedString` de fato. Assim, o tipo Arrow de uma coluna `clickhouse.opaque` sempre indica qual codificação ela contém: `Utf8` para a forma textual, `Binary` para a binária.

É por isso que um estado de agregação armazenado em um `Dynamic` sofre perda no modo `text`, embora uma coluna `AggregateFunction` não sofra. A coluna é tipada a partir de `Dynamic`, que nada informa sobre o conteúdo de suas linhas, e o schema é fixado antes que qualquer valor seja visto; por isso, o estado não pode receber uma coluna `Binary` própria. Use o modo `binary` para preservá-lo. Um `Variant` lista suas alternativas, então um `AggregateFunction` entre elas recebe seu próprio filho `Binary` e não é afetado.

Fora isso, essa coluna seria indistinguível de uma coluna `Utf8`/`Binary` genuína, por isso ela é declarada como um tipo de extensão Arrow: os metadados do campo contêm `ARROW:extension:name` = `clickhouse.opaque` e o nome original do tipo ClickHouse em `ARROW:extension:metadata`. Um cliente que não reconhece o nome da extensão vê o tipo de armazenamento simples, conforme prescreve a especificação do Arrow. Colunas aninhadas são marcadas em seu próprio campo; assim, quem carrega a marcação é o filho de um `Array(JSON)`, bem como a chave de um `Map(JSON, ...)`, e não o contêiner em si.

A opção booleana antiga `output_format_arrow_unsupported_types_as_binary` continua funcionando e equivale a `throw` quando definida como `0` e a `binary` quando definida como `1`. Ela só é consultada enquanto `output_format_arrow_unsupported_types` estiver com o valor padrão.

## Compatibilidade {#compatibility}

A interface Arrow Flight é compatível com qualquer cliente ou ferramenta que ofereça suporte ao protocolo Arrow Flight ou Arrow Flight SQL, incluindo:

* Python (`pyarrow`)
* Java (`org.apache.arrow.flight`)
* C++ (`arrow::flight`)
* Go (`apache/arrow/go`)
* Drivers ADBC (Arrow Database Connectivity)
* DBeaver e outras ferramentas com suporte a Flight SQL

Se houver um conector nativo do ClickHouse disponível para sua ferramenta (por exemplo, JDBC, ODBC, protocolo nativo), dê preferência a ele, a menos que o Arrow Flight seja especificamente necessário por motivos de desempenho ou compatibilidade de formato.
