O ClickHouse implementa a API HTTP do Prometheus com base em uma tabela [`TimeSeries`](/pt-BR/reference/engines/table-engines/integrations/time-series). Um único handler atende à gravação remota, à leitura remota, às consultas PromQL instantâneas e às consultas PromQL de intervalo.

Para expor as métricas do próprio ClickHouse para que um Servidor Prometheus faça scrape delas, consulte o [endpoint de métricas do Prometheus](/pt-BR/concepts/features/connect-to-clickhouse/prometheus/metrics).

## Pré-requisitos {#prerequisites}

As etapas de configuração variam entre o ClickHouse Cloud e o ClickHouse autogerenciado. Siga a seção correspondente à sua implantação.

### ClickHouse Cloud {#prerequisites-cloud}

<Note>
  O suporte a PromQL no ClickHouse Cloud está em prévia privada. Os serviços que participam da prévia privada já vêm com a configuração `enable_time_series_table` e os endpoints da API do Prometheus configurados. Os demais serviços do ClickHouse Cloud não têm essa configuração, e não é possível habilitar a funcionalidade por conta própria nesses serviços. A instrução `SET enable_time_series_table` e a configuração `http_handlers` apresentadas nas próximas seções se aplicam a implantações autogerenciadas.
</Note>

Em um serviço que participa da prévia privada, prossiga para [Criar uma tabela TimeSeries](#create-a-timeseries-table). O serviço disponibiliza os caminhos de endpoint listados na [tabela de endpoints](#configure-prometheus-api).

### Autogerenciado: habilite a configuração TimeSeries {#enable-the-timeseries-setting}

Habilite a configuração `enable_time_series_table` para o usuário que cria e acessa a tabela:

```sql
SET enable_time_series_table = 1;
```

Para requisições à API HTTP, habilite `enable_time_series_table` no perfil do usuário da API.

### Autogerenciado: configure os endpoints da API do Prometheus {#configure-prometheus-api}

Configure um handler roteado por prefixo na porta HTTP principal do ClickHouse:

```xml
<http_handlers>
    <defaults/>
    <rule>
        <url_prefix>/prometheus/api/v1</url_prefix>
        <handler>
            <type>prometheus_api_v1</type>
        </handler>
    </rule>
</http_handlers>
```

`<defaults/>` preserva os handlers integrados para endpoints como `/ping` e para requisições SQL. O prefixo acima expõe estes endpoints por meio de um único handler:

| Endpoint                                 | Finalidade                           |
| ---------------------------------------- | ------------------------------------ |
| `/prometheus/api/v1/write`               | Gravação remota do Prometheus        |
| `/prometheus/api/v1/read`                | Leitura remota do Prometheus         |
| `/prometheus/api/v1/query`               | Consultas PromQL instantâneas        |
| `/prometheus/api/v1/query_range`         | Consultas PromQL por intervalo       |
| `/prometheus/api/v1/format_query`        | Formatação de expressões PromQL      |
| `/prometheus/api/v1/series`              | Metadados de séries                  |
| `/prometheus/api/v1/labels`              | Nomes de labels                      |
| `/prometheus/api/v1/label/<name>/values` | Valores de labels                    |
| `/prometheus/api/v1/metadata`            | Metadados de famílias de métricas    |
| `/prometheus/api/v1/federate`            | Federação das amostras mais recentes |

O exemplo omite `database` e `table` no handler. Cada requisição deve informar o parâmetro de consulta `table` (exceto `/format_query`, que apenas analisa a expressão PromQL fornecida e não precisa de uma tabela). A requisição também pode informar `database`, usar um nome de tabela qualificado, como `prometheus.metrics`, ou omitir o banco de dados para usar `default`. Assim, um único handler pode atender a várias tabelas `TimeSeries`.

Para usar uma tabela fixa em todas as requisições, configure-a no handler:

```xml
<handler>
    <type>prometheus_api_v1</type>
    <database>prometheus</database>
    <table>metrics</table>
</handler>
```

Uma tabela configurada no handler não pode ser sobrescrita por parâmetros da requisição.

Configurações de roteamento e do handler:

| Nome         | Padrão | Descrição                                                                                                                                                                                                                  |
| ------------ | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url_prefix` | nenhum | Filtro de regra que corresponde a todo caminho de requisição que começa com o prefixo configurado.                                                                                                                         |
| `table`      | nenhum | O nome de uma tabela `TimeSeries`. Se omitido, a requisição deve informar o parâmetro de consulta `table`. O nome configurado pode incluir um banco de dados.                                                              |
| `database`   | nenhum | O banco de dados que contém a tabela. A requisição pode informá-lo como parâmetro de consulta. Se omitido, o ClickHouse usa o banco de dados de um valor qualificado de `table` ou, como alternativa, recorre a `default`. |

### Criar uma tabela TimeSeries {#create-a-timeseries-table}

Crie um banco de dados e uma tabela `TimeSeries`:

```sql
CREATE DATABASE prometheus;
CREATE TABLE prometheus.metrics ENGINE = TimeSeries;
```

## Ingestão de métricas com gravação remota {#remote-write}

O ClickHouse oferece suporte ao [protocolo Prometheus remote-write](https://prometheus.io/docs/specs/remote_write_spec/). Configure o Prometheus para gravar no handler:

```yaml
remote_write:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/write?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

O Prometheus envia amostras para a tabela `prometheus.metrics`.

Para agrupar em lotes os dados de muitas requisições concorrentes de remote-write em menos partes, o ClickHouse usa [inserções assíncronas](/pt-BR/reference/settings/session-settings/async-insert#async_insert). Elas vêm habilitadas por padrão, e a configuração `async_insert` na URL (ou no perfil de usuário) as ativa ou desativa.

O ClickHouse só confirma uma requisição assíncrona de remote-write depois que os dados são gravados em disco em todas as tabelas internas da tabela `TimeSeries`, independentemente da configuração [`wait_for_async_insert`](/pt-BR/reference/settings/session-settings/wait-for#wait_for_async_insert): o protocolo remote-write considera durável uma gravação confirmada. Se o flush falhar, a requisição retorna um erro e o Prometheus faz uma nova tentativa.

Como cada requisição aguarda o seu flush, as inserções assíncronas limitam a velocidade de gravação de um único remetente. O Prometheus envia uma requisição por vez para cada shard de remote-write. Quando vários shards enviam ao mesmo tempo, o tempo limite adaptativo de flush aumenta até [`async_insert_busy_timeout_max_ms`](/pt-BR/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms), a menos que as requisições pendentes atinjam antes [`async_insert_max_data_size`](/pt-BR/reference/settings/session-settings/async-insert#async_insert_max_data_size). Uma requisição aguarda até que seu lote seja gravado em disco, o que pode levar até esse intervalo após o início do lote; assim, sob carga sustentada, cada shard grava aproximadamente `samples per request / async_insert_busy_timeout_max_ms`, sendo que, por padrão, o Prometheus envia até 2,000 amostras por requisição. Para aumentar essa taxa:

* Aumente `max_shards` (50 por padrão) ou `max_samples_per_send` no `queue_config` de [`remote_write`](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write). Quando fica para trás, o Prometheus adiciona shards automaticamente, até o limite de `max_shards`.
* Reduza `async_insert_busy_timeout_max_ms` na URL ou no perfil de usuário, por exemplo `&async_insert_busy_timeout_max_ms=50`. Com isso, as operações de persistência ocorrem com mais frequência, e cada flush cria novas partes nas tabelas internas.
* Desative as inserções assíncronas com `async_insert=0`. Com isso, cada requisição cria suas próprias partes nas tabelas internas.

## Consultas com PromQL {#promql-query-support}

Use o endpoint de consulta instantânea para avaliar uma expressão PromQL em um único ponto no tempo:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

Use o endpoint de consulta de intervalo para avaliar uma expressão ao longo de um intervalo de tempo:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

Os endpoints de consulta também aceitam os parâmetros no corpo de um formulário. Sem `--get`, o curl envia os parâmetros como `application/x-www-form-urlencoded` via `POST`:

```bash
curl --user default:<password> \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

Use o endpoint format-query para interpretar e formatar uma expressão PromQL sem avaliá-la:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/format_query" \
  --data-urlencode "query=sum by(job)(http_requests_total{code=\"200\"})/2"
```

A expressão é retornada serializada a partir da consulta analisada sintaticamente, com os espaços em branco normalizados, os comentários removidos, os parênteses redundantes eliminados e as durações representadas nas unidades aceitas pelo analisador sintático: `sum by (job) (http_requests_total{code="200"}) / 2`. As durações mantêm suas unidades em vez de serem convertidas em um número de segundos. Assim, `rate(x[5m])` é retornado como `rate(x[5m])`. Quando uma duração não pode ser expressa como um número inteiro de uma única unidade, ela é representada com a combinação de unidades necessária: `rate(x[90s])` é retornado como `rate(x[1m30s])`. Esse endpoint não avalia a expressão, portanto não precisa dos parâmetros `database` e `table`.

Consulte as [funcionalidades PromQL compatíveis](/pt-BR/reference/functions/table-functions/prometheusQueryRange#supported-promql-features) para ver a lista de funções e operadores de agregação usados pela API HTTP, pelo dialect `promql` e pelas funções de tabela.

Os demais parâmetros da requisição são aplicados como configurações do ClickHouse, por exemplo, `max_execution_time=10`. Os endpoints de consulta também aceitam alguns parâmetros do VictoriaMetrics e do Thanos: `nocache=1` define `use_query_cache=0`, `partial_response=false` define `skip_unavailable_shards=0`, e `dedup=false`, `trace` e `round_digits` são ignorados. Eles retornam um erro para `extra_label` e `extra_filters`, porque o ClickHouse não aplica esses filtros, e também para `dedup=true` e `partial_response=true`, porque o ClickHouse não implementa a desduplicação nem as respostas parciais do Thanos.

### Grafana {#grafana}

Configure uma fonte de dados do Prometheus com a URL base terminando antes de `/api/v1`:

```yaml
apiVersion: 1
datasources:
  - name: ClickHouse Prometheus
    type: prometheus
    access: proxy
    url: https://clickhouse.example.com:8443/prometheus
    basicAuth: true
    basicAuthUser: default
    jsonData:
      httpMethod: POST
      customQueryParameters: database=prometheus&table=metrics
    secureJsonData:
      basicAuthPassword: <password>
```

O Grafana acrescenta `/api/v1/query` ou `/api/v1/query_range` a essa URL base e adiciona `customQueryParameters` a cada requisição.

Com `httpMethod: POST`, o Grafana envia os parâmetros de consulta no corpo da requisição. Como o ClickHouse lê tanto o corpo da requisição quanto a string de consulta da URL, `customQueryParameters` continua sendo aplicado. Use `POST` para expressões PromQL longas, já que URLs têm limite de comprimento.

<Note>
  Apenas os endpoints de consulta `/api/v1/query`, `/api/v1/query_range` e `/api/v1/format_query`, os endpoints de metadados `/api/v1/series`, `/api/v1/labels`, `/api/v1/label/<name>/values` e `/api/v1/metadata`, e o endpoint de [federação](#federation) `/api/v1/federate` estão implementados. `/api/v1/series` exige pelo menos um seletor de séries `match[]`, aceita os parâmetros opcionais `start`, `end` e `limit` e retorna a união das séries correspondentes a cada seletor. `/api/v1/labels` aceita os mesmos parâmetros, sendo `match[]` opcional, e retorna os nomes de label ordenados das séries correspondentes (ou de todas as séries, quando nenhum seletor é informado). `/api/v1/label/<name>/values` aceita os mesmos parâmetros que `/api/v1/labels` e retorna os valores ordenados de um label; `<name>` pode, opcionalmente, usar o escape `U__...` do Prometheus para nomes de label que contenham caracteres fora de `[a-zA-Z0-9_]`. Esses endpoints cobrem o que uma fonte de dados Prometheus do Grafana usa para navegação de labels, variáveis de template e preenchimento automático no construtor de consultas.
</Note>

### Pontos de entrada SQL {#sql-entry-points}

O ClickHouse usa o mesmo conversor de PromQL para a API HTTP, para o dialect `promql` e para as funções de tabela [`prometheusQuery`](/pt-BR/reference/functions/table-functions/prometheusQuery) e [`prometheusQueryRange`](/pt-BR/reference/functions/table-functions/prometheusQueryRange).

Execute consultas PromQL diretamente com o `clickhouse-client`:

```bash
clickhouse-client \
  --dialect promql \
  --promql_database prometheus \
  --promql_table metrics \
  --query 'rate(http_requests_total[5m])'
```

Use as funções de tabela para incorporar PromQL em uma consulta SQL:

```sql
SELECT *
FROM prometheusQuery(
    prometheus.metrics,
    'rate(http_requests_total[5m])',
    now()
);
```

## Consultar metadados de métricas {#metadata}

O endpoint `/prometheus/api/v1/metadata` retorna os metadados de métricas armazenados na tabela de destino `Metrics` da tabela `TimeSeries`: o tipo, o texto de ajuda e a unidade de cada família de métricas. Ele aceita os seguintes parâmetros do Prometheus na string de consulta da URL:

| Parâmetro          | Descrição                                                                                                                                 |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `metric`           | Retorna metadados apenas desta família de métricas.                                                                                       |
| `limit`            | Limita o número de famílias de métricas retornadas. Um valor negativo significa sem limite; zero não retorna nenhuma família de métricas. |
| `limit_per_metric` | Limita o número de objetos de metadados retornados para cada família de métricas. Zero e valores negativos significam sem limite.         |

A tabela de destino `Metrics` padrão é uma `ReplacingMergeTree` ordenada pelo nome da família de métricas: ela mantém a entrada de metadados gravada mais recentemente para cada família de métricas. Várias entradas por família só são retornadas enquanto a tabela de destino as armazena, ou seja, antes de suas partes serem mescladas ou quando a tabela é definida com um motor que as preserva.

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/metadata" \
  --data-urlencode "metric=http_requests_total" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

## Federação de métricas {#federation}

O ClickHouse oferece suporte ao endpoint de [federação do Prometheus](https://prometheus.io/docs/prometheus/latest/federation/) em `/prometheus/api/v1/federate` (ou em qualquer caminho terminado em `/federate` atendido por um handler do tipo `query`). Para cada série que corresponde aos seletores `match[]`, ele retorna a amostra mais recente dos últimos 5 minutos no formato de texto do Prometheus, para que um servidor Prometheus possa fazer o scrape:

```yaml
scrape_configs:
  - job_name: clickhouse-federate
    honor_labels: true
    scheme: https
    metrics_path: /prometheus/api/v1/federate
    params:
      'match[]': ['{job="node"}']
      table: ['prometheus.metrics']
    static_configs:
      - targets: ['clickhouse.example.com:8443']
```

## Leitura de métricas com leitura remota {#remote-read}

O ClickHouse oferece suporte ao [protocolo de leitura remota do Prometheus](https://prometheus.io/docs/prometheus/latest/querying/remote_read_api/) em `/prometheus/api/v1/read`.

Configure um servidor Prometheus para ler dados da mesma tabela `TimeSeries`:

```yaml
remote_read:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/read?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

## Regras de gravação {#recording-rules}

O ClickHouse não avalia arquivos de regras do Prometheus. Uma [view materializada atualizável](/pt-BR/reference/statements/create/view#refreshable-materialized-view) pode cumprir o papel de uma [regra de gravação](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/): ela avalia uma expressão PromQL de forma agendada e acrescenta o resultado a uma tabela `TimeSeries`. A visão a seguir registra `sum by (job) (rate(http_requests_total[5m]))` como `job:http_requests:rate5m` a cada minuto:

```sql
CREATE MATERIALIZED VIEW prometheus.job_http_requests_rate5m
REFRESH EVERY 1 MINUTE APPEND TO prometheus.metrics (tags, samples) AS
SELECT
    mapUpdate(CAST(tags, 'Map(String, String)'), map('__name__', 'job:http_requests:rate5m')) AS tags,
    [(timestamp, value)] AS samples
FROM prometheusQuery(prometheus.metrics, 'sum by (job) (rate(http_requests_total[5m]))', toStartOfMinute(now()));
```

Cada atualização avalia a expressão no início do minuto atual, define o nome da métrica com `mapUpdate` e acrescenta uma amostra para cada série do resultado. Labels adicionais podem ser incluídos no mesmo map, por exemplo `map('__name__', 'job:http_requests:rate5m', 'team', 'web')`. A série registrada é consultada como qualquer outra métrica:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=job:http_requests:rate5m" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

O instante e o erro da última avaliação são exibidos em [`system.view_refreshes`](/pt-BR/reference/system-tables/view_refreshes).

Uma visão difere de uma regra de gravação do Prometheus nos seguintes aspectos:

* O instante de avaliação é `now()` no momento em que a atualização é executada. Além do agendamento, uma visão é atualizada logo após ser criada (a menos que seja criada com `EMPTY`), após um restart do servidor caso suas atualizações não sejam coordenadas (uma visão fora de um Banco de dados Replicated ou Shared, ou uma com `all_replicas = 1`, não guarda o registro de sua última atualização) e quando `SYSTEM START VIEW` a retoma depois de ela ter perdido uma atualização agendada. Arredonde `now()` para baixo até o início do intervalo, como no exemplo, para que essas atualizações não adicionem amostras entre as agendadas. Ainda assim, uma atualização extra pode gravar uma segunda amostra no mesmo timestamp arredondado. Para uma regra de cinco minutos, use `toStartOfInterval(now(), INTERVAL 5 MINUTE)`.
* Avaliações perdidas não são recuperadas. Depois que o servidor fica fora do ar ou a visão é interrompida, a visão avalia apenas o intervalo atual, e os intervalos anteriores permanecem vazios. O mesmo acontece quando uma atualização leva mais tempo do que o intervalo.
* Uma série que deixa de aparecer no resultado não recebe marcador de obsolescência, de modo que as consultas continuam retornando seu último valor registrado durante o período de lookback, que é de 5 minutos por padrão.
* Não há arquivo de regras: cada regra é uma visão separada. As regras não são listadas por `/api/v1/rules`.
