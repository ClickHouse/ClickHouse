O ClickHouse consegue determinar automaticamente a estrutura dos dados de entrada em quase todos os [formatos de entrada](/pt-BR/reference/formats/index) compatíveis.
Este documento descreve quando a inferência de esquema é utilizada, como ela funciona com os diferentes formatos de entrada e quais configurações
permitem controlá-la.

## Uso {#usage}

A inferência de esquema é usada quando o ClickHouse precisa ler dados em um formato de dados específico cuja estrutura é desconhecida.

## Funções de tabela [file](/pt-BR/reference/functions/table-functions/file), [s3](/pt-BR/reference/functions/table-functions/s3), [url](/pt-BR/reference/functions/table-functions/url), [hdfs](/pt-BR/reference/functions/table-functions/hdfs), [azureBlobStorage](/pt-BR/reference/functions/table-functions/azureBlobStorage). {#table-functions-file-s3-url-hdfs-azureblobstorage}

Essas funções de tabela têm o argumento opcional `structure`, que define a estrutura dos dados de entrada. Se esse argumento não for especificado ou for definido como `auto`, a estrutura será inferida a partir dos dados.

**Exemplo:**

Suponha que tenhamos um arquivo `hobbies.jsonl` no formato JSONEachRow no diretório `user_files` com o seguinte conteúdo:

```json
{"id" :  1, "age" :  25, "name" :  "Josh", "hobbies" :  ["football", "cooking", "music"]}
{"id" :  2, "age" :  19, "name" :  "Alan", "hobbies" :  ["tennis", "art"]}
{"id" :  3, "age" :  32, "name" :  "Lana", "hobbies" :  ["fitness", "reading", "shopping"]}
{"id" :  4, "age" :  47, "name" :  "Brayan", "hobbies" :  ["movies", "skydiving"]}
```

O ClickHouse consegue ler esses dados sem que você precise especificar a estrutura deles:

```sql
SELECT * FROM file('hobbies.jsonl')
```

```response
┌─id─┬─age─┬─name───┬─hobbies──────────────────────────┐
│  1 │  25 │ Josh   │ ['football','cooking','music']   │
│  2 │  19 │ Alan   │ ['tennis','art']                 │
│  3 │  32 │ Lana   │ ['fitness','reading','shopping'] │
│  4 │  47 │ Brayan │ ['movies','skydiving']           │
└────┴─────┴────────┴──────────────────────────────────┘
```

Observação: o formato `JSONEachRow` foi determinado automaticamente a partir da extensão de arquivo `.jsonl`.

Você pode ver a estrutura determinada automaticamente usando a consulta `DESCRIBE`:

```sql
DESCRIBE file('hobbies.jsonl')
```

```response
┌─name────┬─type────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ id      │ Nullable(Int64)         │              │                    │         │                  │                │
│ age     │ Nullable(Int64)         │              │                    │         │                  │                │
│ name    │ Nullable(String)        │              │                    │         │                  │                │
│ hobbies │ Array(Nullable(String)) │              │                    │         │                  │                │
└─────────┴─────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## Motores de tabela [File](/pt-BR/reference/engines/table-engines/special/file), [S3](/pt-BR/reference/engines/table-engines/integrations/s3), [URL](/pt-BR/reference/engines/table-engines/special/url), [HDFS](/pt-BR/reference/engines/table-engines/integrations/hdfs), [azureBlobStorage](/pt-BR/reference/engines/table-engines/integrations/azureBlobStorage) {#table-engines-file-s3-url-hdfs-azureblobstorage}

Se a lista de colunas não for especificada na consulta `CREATE TABLE`, a estrutura da tabela será inferida automaticamente a partir dos dados.

**Exemplo:**

Vamos usar o arquivo `hobbies.jsonl`. Podemos criar uma tabela com o motor `File` a partir dos dados desse arquivo:

```sql
CREATE TABLE hobbies ENGINE=File(JSONEachRow, 'hobbies.jsonl')
```


```sql
SELECT * FROM hobbies
```

## clickhouse-local {#clickhouse-local}

O `clickhouse-local` tem um parâmetro opcional `-S/--structure` que define a estrutura dos dados de entrada. Se esse parâmetro não for especificado ou for definido como `auto`, a estrutura será inferida a partir dos dados.

**Exemplo:**

Vamos usar o arquivo `hobbies.jsonl`. Podemos consultar os dados desse arquivo usando o `clickhouse-local`:

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='DESCRIBE TABLE hobbies'
```

```response
id    Nullable(Int64)
age    Nullable(Int64)
name    Nullable(String)
hobbies    Array(Nullable(String))
```

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='SELECT * FROM hobbies'
```

```response
1    25    Josh    ['football','cooking','music']
2    19    Alan    ['tennis','art']
3    32    Lana    ['fitness','reading','shopping']
4    47    Brayan    ['movies','skydiving']
```

## Usando a estrutura da tabela de inserção {#using-structure-from-insertion-table}

Quando as funções de tabela `file/s3/url/hdfs` são usadas para inserir dados em uma tabela,
é possível usar a estrutura da tabela de inserção em vez de extraí-la dos dados.
Isso pode melhorar o desempenho da inserção, pois a inferência de esquema pode levar algum tempo. Além disso, é útil quando a tabela tem um schema otimizado, pois assim
nenhuma conversão entre tipos será realizada.

Existe uma configuração específica, [use&#95;structure&#95;from&#95;insertion&#95;table&#95;in&#95;table&#95;functions](/pt-BR/reference/settings/session-settings/use#use_structure_from_insertion_table_in_table_functions),
que controla esse comportamento. Ela tem 3 valores possíveis:

* 0 - a função de tabela extrairá a estrutura dos dados.
* 1 - a função de tabela usará a estrutura da tabela de inserção.
* 2 - o ClickHouse determinará automaticamente se é possível usar a estrutura da tabela de inserção ou se deve usar a inferência de esquema. Valor default.

**Exemplo 1:**

Vamos criar a tabela `hobbies1` com a seguinte estrutura:

```sql
CREATE TABLE hobbies1
(
    `id` UInt64,
    `age` LowCardinality(UInt8),
    `name` String,
    `hobbies` Array(String)
)
ENGINE = MergeTree
ORDER BY id;
```

Em seguida, insira os dados do arquivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies1 SELECT * FROM file(hobbies.jsonl)
```

Neste caso, todas as colunas do arquivo são inseridas na tabela sem alterações, portanto o ClickHouse usará a estrutura da tabela de inserção em vez da inferência de esquema.

**Exemplo 2:**

Vamos criar a tabela `hobbies2` com a seguinte estrutura:

```sql
CREATE TABLE hobbies2
(
  `id` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

Em seguida, insira os dados do arquivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies2 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

Neste caso, todas as colunas da consulta `SELECT` estão presentes na tabela, portanto o ClickHouse usará a estrutura da tabela de inserção.
Observe que isso só funciona com formatos de entrada que suportam a leitura de um subconjunto de colunas, como JSONEachRow, TSKV, Parquet etc. (portanto, não funcionará, por exemplo, com o formato TSV).

**Exemplo 3:**

Vamos criar a tabela `hobbies3` com a seguinte estrutura:

```sql
CREATE TABLE hobbies3
(
  `identifier` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY identifier;
```

Em seguida, insira os dados do arquivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies3 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

Nesse caso, a coluna `id` é usada na consulta `SELECT`, mas a tabela não tem essa coluna (ela tem uma coluna chamada `identifier`),
então o ClickHouse não consegue usar a estrutura da tabela de inserção e recorre à inferência de esquema.

**Exemplo 4:**

Vamos criar a tabela `hobbies4` com a seguinte estrutura:

```sql
CREATE TABLE hobbies4
(
  `id` UInt64,
  `any_hobby` Nullable(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

Em seguida, insira os dados do arquivo `hobbies.jsonl`:

```sql
INSERT INTO hobbies4 SELECT id, empty(hobbies) ? NULL : hobbies[1] FROM file(hobbies.jsonl)
```

Neste caso, algumas operações são aplicadas à coluna `hobbies` na consulta `SELECT` antes de inseri-la na tabela; portanto, o ClickHouse não pode usar a estrutura da tabela de inserção, e a inferência de esquema será utilizada.

## Cache de inferência de schema {#schema-inference-cache}

Para a maioria dos formatos de entrada, a inferência de schema lê parte dos dados para determinar sua estrutura, e esse processo pode levar algum tempo.
Para evitar inferir o mesmo schema toda vez que o ClickHouse lê os dados do mesmo arquivo, o schema inferido é armazenado em cache e, ao acessar o mesmo arquivo novamente, o ClickHouse usa o schema do cache.

Existem configurações específicas que controlam esse cache:

* `schema_inference_cache_max_elements_for_{file/s3/hdfs/url/azure}` - o número máximo de schemas armazenados em cache para a função de tabela correspondente. O valor default é `4096`. Essas configurações devem ser definidas na configuração do servidor.
* `schema_inference_use_cache_for_{file,s3,hdfs,url,azure}` - permite ativar/desativar o uso do cache na inferência de schema. Essas configurações podem ser usadas em consultas.

O schema do arquivo pode mudar com a modificação dos dados ou com a alteração das configurações de formato.
Por isso, o cache de inferência de schema identifica o schema pela fonte do arquivo, pelo nome do formato, pelas configurações de formato utilizadas e pelo horário da última modificação do arquivo.

Nota: alguns arquivos acessados por URL na função de tabela `url` podem não conter informações sobre o horário da última modificação; para esse caso, existe uma configuração específica,
`schema_inference_cache_require_modification_time_for_url`. Desabilitar essa configuração permite usar o schema do cache sem o horário da última modificação para esses arquivos.

Há também a tabela de sistema [schema&#95;inference&#95;cache](/pt-BR/reference/system-tables/schema_inference_cache), com todos os schemas atualmente em cache, e a consulta de sistema `SYSTEM CLEAR SCHEMA CACHE [FOR File/S3/URL/HDFS]`,
que permite limpar o cache de schema para todas as fontes de dados ou para uma fonte de dados específica.

## Formatos de texto {#text-formats}

Para formatos de texto, o ClickHouse lê os dados linha por linha, extrai os valores das colunas de acordo com o formato
e, em seguida, usa alguns analisadores sintáticos recursivos e heurísticas para determinar o tipo de cada valor. O número máximo de linhas e bytes lidos dos dados durante a inferência de esquema
é controlado pelas configurações `input_format_max_rows_to_read_for_schema_inference` (25000 por padrão) e `input_format_max_bytes_to_read_for_schema_inference` (32Mb por padrão).
Por padrão, todos os tipos inferidos são [Nullable](/pt-BR/reference/data-types/nullable), mas você pode alterar isso com a configuração `schema_inference_make_columns_nullable` (veja exemplos na seção de [configurações](#settings-for-text-formats)).

### Formatos JSON {#json-formats}

Nos formatos JSON, o ClickHouse interpreta os valores de acordo com a especificação JSON e, em seguida, tenta encontrar o tipo de dado mais adequado para eles.

Vamos ver como isso funciona, quais tipos podem ser inferidos e quais configurações específicas podem ser usadas nos Formatos JSON.

**Exemplos**

### CSV {#csv}

No formato CSV, o ClickHouse extrai os valores da coluna de cada linha com base nos delimitadores. O ClickHouse espera que todos os tipos, exceto números e strings, estejam entre aspas duplas. Se o valor estiver entre aspas duplas, o ClickHouse tenta interpretar
os dados entre as aspas usando o analisador sintático recursivo e, em seguida, tenta encontrar o tipo de dado mais adequado para eles. Se o valor não estiver entre aspas duplas, o ClickHouse tenta interpretá-lo como um número
e, se o valor não for um número, o ClickHouse o trata como uma string.

Se você não quiser que o ClickHouse tente determinar tipos complexos usando analisadores sintáticos e heurísticas, pode desativar a configuração `input_format_csv_use_best_effort_in_schema_inference`
e o ClickHouse tratará todas as colunas como Strings.

Se a configuração `input_format_csv_detect_header` estiver habilitada, o ClickHouse tentará detectar o cabeçalho com os nomes de colunas (e, possivelmente, os tipos) ao inferir o schema. Essa configuração vem habilitada por padrão.

### TSV/TSKV {#tsv-tskv}

Nos formatos TSV/TSKV, o ClickHouse extrai o valor da coluna da linha de acordo com os delimitadores tabulares e, em seguida, analisa sintaticamente o valor extraído usando
o analisador sintático recursivo para determinar o tipo mais adequado. Se não for possível determinar o tipo, o ClickHouse trata esse valor como String.

### Template {#template}

No formato Template, o ClickHouse primeiro extrai todos os valores de coluna da linha de acordo com o template especificado e, em seguida, tenta inferir o
tipo de dado de cada valor de acordo com sua regra de escape.

**Exemplo**

Suponha que temos um arquivo `resultset` com o seguinte conteúdo:

```bash
<result_before_delimiter>
${data}<result_after_delimiter>
```

E um arquivo `row_format` com o seguinte conteúdo:

```text
<row_before_delimiter>${column_1:CSV}<field_delimiter_1>${column_2:Quoted}<field_delimiter_2>${column_3:JSON}<row_after_delimiter>
```

Em seguida, podemos executar as seguintes consultas:

```sql
SET format_template_rows_between_delimiter = '<row_between_delimiter>\n',
       format_template_row = 'row_format',
       format_template_resultset = 'resultset_format'

DESC format(Template, $$<result_before_delimiter>
<row_before_delimiter>42.42<field_delimiter_1>'Some string 1'<field_delimiter_2>[1, null, 2]<row_after_delimiter>
<row_between_delimiter>
<row_before_delimiter>\N<field_delimiter_1>'Some string 3'<field_delimiter_2>[1, 2, null]<row_after_delimiter>
<result_after_delimiter>
$$)
```

```response
┌─name─────┬─type───────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ column_1 │ Nullable(Float64)      │              │                    │         │                  │                │
│ column_2 │ Nullable(String)       │              │                    │         │                  │                │
│ column_3 │ Array(Nullable(Int64)) │              │                    │         │                  │                │
└──────────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Regexp {#regexp}

Assim como no formato Template, no formato Regexp o ClickHouse primeiro extrai todos os valores das colunas da linha de acordo com a expressão regular especificada e, em seguida, tenta inferir
o tipo de dado de cada valor de acordo com a regra de escape especificada.

**Exemplo**

```sql
SET format_regexp = '^Line: value_1=(.+?), value_2=(.+?), value_3=(.+?)',

DESC format(Regexp, $$Line: value_1=42, value_2="Some string 1", value_3="[1, NULL, 3]"
Line: value_1=2, value_2="Some string 2", value_3="[4, 5, NULL]"$$)
```

### Configurações para formatos de texto {#settings-for-text-formats}

#### input_format_max_rows_to_read_for_schema_inference/input_format_max_bytes_to_read_for_schema_inference {#input-format-max-rows-to-read-for-schema-inference}

Essas configurações controlam a quantidade de dados lidos durante a inferência de esquema.
Quanto mais linhas/bytes forem lidos, mais tempo será gasto na inferência de esquema, mas maior será a chance de
determinar corretamente os tipos (especialmente quando os dados contêm muitos valores NULL).

Valores default:

* `25000` para `input_format_max_rows_to_read_for_schema_inference`.
* `33554432` (32 Mb) para `input_format_max_bytes_to_read_for_schema_inference`.

#### column_names_for_schema_inference {#column-names-for-schema-inference}

Lista de nomes de colunas a serem usados na inferência de esquema para formatos sem nomes de colunas explícitos. Os nomes especificados serão usados no lugar dos nomes padrão `c1,c2,c3,...`. Formato: `column1,column2,column3,...`.

**Exemplo**

```sql
DESC format(TSV, 'Hello, World!    42    [1, 2, 3]') settings column_names_for_schema_inference = 'str,int,arr'
```

#### schema_inference_make_columns_nullable $ {#schema-inference-make-columns-nullable}

## Formatos autodescritivos {#self-describing-formats}

Formatos autodescritivos contêm, nos próprios dados, informações sobre a estrutura desses dados,
que podem ser um cabeçalho com uma descrição, uma árvore binária de tipos ou algum tipo de tabela.
Para inferir automaticamente um schema a partir de arquivos nesses formatos, o ClickHouse lê uma parte dos dados que contém
informações sobre os tipos e as converte em um schema da tabela do ClickHouse.

### Formatos com o sufixo -WithNamesAndTypes {#formats-with-names-and-types}

O ClickHouse oferece suporte a alguns formatos de texto com o sufixo -WithNamesAndTypes. Esse sufixo indica que os dados contêm duas linhas adicionais, com os nomes e os tipos das colunas, antes dos dados propriamente ditos.
Durante a inferência de esquema para esses formatos, o ClickHouse lê as duas primeiras linhas e extrai delas os nomes e os tipos das colunas.

**Exemplo**

```sql
DESC format(TSVWithNamesAndTypes,
$$num    str    arr
UInt8    String    Array(UInt8)
42    Hello, World!    [1,2,3]
$$)
```

```response
┌─name─┬─type─────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ num  │ UInt8        │              │                    │         │                  │                │
│ str  │ String       │              │                    │         │                  │                │
│ arr  │ Array(UInt8) │              │                    │         │                  │                │
└──────┴──────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## Formatos binários fortemente tipados {#strong-typed-binary-formats}

Nesses formatos, cada valor serializado contém informações sobre seu tipo (e possivelmente sobre seu nome), mas não há informações sobre a tabela como um todo.
Na inferência de esquema para esses formatos, o ClickHouse lê os dados linha por linha (até `input_format_max_rows_to_read_for_schema_inference` linhas ou `input_format_max_bytes_to_read_for_schema_inference` bytes), extrai
dos dados o tipo (e possivelmente o nome) de cada valor e, em seguida, converte esses tipos em tipos do ClickHouse.

### MsgPack {#msgpack}

No formato MsgPack não há delimitador entre linhas. Para usar a inferência de esquema com esse formato, é necessário especificar o número de colunas da tabela
por meio da configuração `input_format_msgpack_number_of_columns`. O ClickHouse usa as seguintes correspondências de tipos:

| Tipo de dados do MessagePack (`INSERT`)                            | Tipo de dados do ClickHouse                  |
| ------------------------------------------------------------------ | -------------------------------------------- |
| `int N`, `uint N`, `negative fixint`, `positive fixint`            | [Int64](/pt-BR/reference/data-types/int-uint)      |
| `bool`                                                             | [UInt8](/pt-BR/reference/data-types/int-uint)      |
| `fixstr`, `str 8`, `str 16`, `str 32`, `bin 8`, `bin 16`, `bin 32` | [String](/pt-BR/reference/data-types/string)       |
| `float 32`                                                         | [Float32](/pt-BR/reference/data-types/float)       |
| `float 64`                                                         | [Float64](/pt-BR/reference/data-types/float)       |
| `uint 16`                                                          | [Date](/pt-BR/reference/data-types/date)           |
| `uint 32`                                                          | [DateTime](/pt-BR/reference/data-types/datetime)   |
| `uint 64`                                                          | [DateTime64](/pt-BR/reference/data-types/datetime) |
| `fixarray`, `array 16`, `array 32`                                 | [Array](/pt-BR/reference/data-types/array)         |
| `fixmap`, `map 16`, `map 32`                                       | [Map](/pt-BR/reference/data-types/map)             |

Por padrão, todos os tipos inferidos estão dentro de `Nullable`, mas isso pode ser alterado por meio da configuração `schema_inference_make_columns_nullable`.

### BSONEachRow {#bsoneachrow}

No BSONEachRow, cada linha de dados é representada como um documento BSON. Na inferência de esquema, o ClickHouse lê os documentos BSON um a um, extrai
valores, nomes e tipos dos dados e, em seguida, converte esses tipos em tipos do ClickHouse usando as seguintes correspondências de tipos:

| Tipo BSON                                                                                        | Tipo do ClickHouse                                                                                                 |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `\x08` booleano                                                                                  | [Bool](/pt-BR/reference/data-types/boolean)                                                                              |
| `\x10` int32                                                                                     | [Int32](/pt-BR/reference/data-types/int-uint)                                                                            |
| `\x12` int64                                                                                     | [Int64](/pt-BR/reference/data-types/int-uint)                                                                            |
| `\x01` double                                                                                    | [Float64](/pt-BR/reference/data-types/float)                                                                             |
| `\x09` data e hora                                                                               | [DateTime64](/pt-BR/reference/data-types/datetime64)                                                                     |
| `\x05` binary com `\x00` subtipo binário, `\x02` string, `\x0E` symbol, `\x0D` código JavaScript | [String](/pt-BR/reference/data-types/string)                                                                             |
| `\x07` ObjectId,                                                                                 | [FixedString(12)](/pt-BR/reference/data-types/fixedstring)                                                               |
| `\x05` binary com `\x04` subtipo uuid, tamanho = 16                                              | [UUID](/pt-BR/reference/data-types/uuid)                                                                                 |
| `\x04` array                                                                                     | [Array](/pt-BR/reference/data-types/array)/[Tuple](/pt-BR/reference/data-types/tuple) (se os tipos aninhados forem diferentes) |
| `\x03` documento                                                                                 | [Named Tuple](/pt-BR/reference/data-types/tuple)/[Map](/pt-BR/reference/data-types/map) (com chaves String)                    |

Por padrão, todos os tipos inferidos estão dentro de `Nullable`, mas isso pode ser alterado com a configuração `schema_inference_make_columns_nullable`.

## Modos de inferência de esquema {#schema-inference-modes}

A inferência de esquema a partir de um conjunto de arquivos de dados pode operar em 2 modos diferentes: `default` e `union`.
O modo é controlado pela configuração `schema_inference_mode`.

### Modo padrão {#default-schema-inference-mode}

No modo padrão, o ClickHouse pressupõe que todos os arquivos têm o mesmo schema e tenta inferir o schema lendo os arquivos um a um até conseguir.

Exemplo:

Suponha que temos 3 arquivos, `data1.jsonl`, `data2.jsonl` e `data3.jsonl`, com o seguinte conteúdo:

`data1.jsonl`:

```json
{"field1" :  1, "field2" :  null}
{"field1" :  2, "field2" :  null}
{"field1" :  3, "field2" :  null}
```

`data2.jsonl`:

```json
{"field1" :  4, "field2" :  "Data4"}
{"field1" :  5, "field2" :  "Data5"}
{"field1" :  6, "field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field1" :  7, "field2" :  "Data7", "field3" :  [1, 2, 3]}
{"field1" :  8, "field2" :  "Data8", "field3" :  [4, 5, 6]}
{"field1" :  9, "field2" :  "Data9", "field3" :  [7, 8, 9]}
```

Vamos tentar usar a inferência de esquema nestes 3 arquivos:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='default'
```

```response title="Response"
┌─name───┬─type─────────────┐
│ field1 │ Nullable(Int64)  │
│ field2 │ Nullable(String) │
└────────┴──────────────────┘
```

Como podemos ver, não temos o `field3` do arquivo `data3.jsonl`.
Isso acontece porque o ClickHouse primeiro tentou inferir o schema a partir do arquivo `data1.jsonl`, falhou porque o campo `field2` continha apenas valores NULL,
e depois tentou inferir o schema a partir de `data2.jsonl` e conseguiu; por isso, os dados do arquivo `data3.jsonl` não foram lidos.

### Modo de união {#default-schema-inference-mode-1}

No modo de união, o ClickHouse considera que os arquivos podem ter esquemas diferentes; por isso, ele infere os esquemas de todos os arquivos e depois os une em um schema comum.

Suponha que temos 3 arquivos, `data1.jsonl`, `data2.jsonl` e `data3.jsonl`, com o seguinte conteúdo:

`data1.jsonl`:

```json
{"field1" :  1}
{"field1" :  2}
{"field1" :  3}
```

`data2.jsonl`:

```json
{"field2" :  "Data4"}
{"field2" :  "Data5"}
{"field2" :  "Data5"}
```

`data3.jsonl`:

```json
{"field3" :  [1, 2, 3]}
{"field3" :  [4, 5, 6]}
{"field3" :  [7, 8, 9]}
```

Vamos tentar usar a inferência de esquema nestes 3 arquivos:

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='union'
```

```response title="Response"
┌─name───┬─type───────────────────┐
│ field1 │ Nullable(Int64)        │
│ field2 │ Nullable(String)       │
│ field3 │ Array(Nullable(Int64)) │
└────────┴────────────────────────┘
```

Como podemos ver, temos todos os campos de todos os arquivos.

Nota:

* Como alguns arquivos podem não conter determinadas colunas do schema resultante, o modo de união é compatível apenas com formatos que permitem a leitura de um subconjunto de colunas (como JSONEachRow, Parquet, TSVWithNames etc.) e não funcionará com outros formatos (como CSV, TSV, JSONCompactEachRow etc.).
* Se o ClickHouse não conseguir inferir o schema de um dos arquivos, uma exceção será lançada.
* Se você tiver muitos arquivos, a leitura do schema de todos eles pode levar bastante tempo.

## Detecção automática de formato {#automatic-format-detection}

Se o formato de dados não for especificado e não puder ser determinado pela extensão do arquivo, o ClickHouse tentará detectar o formato do arquivo com base em seu conteúdo.

**Exemplos:**

Suponha que tenhamos `data` com o seguinte conteúdo:

```csv
"a","b"
1,"Data1"
2,"Data2"
3,"Data3"
```

Podemos inspecionar e consultar este arquivo sem especificar o formato nem a estrutura:

```sql
:) desc file(data);
```

```response
┌─name─┬─type─────────────┐
│ a    │ Nullable(Int64)  │
│ b    │ Nullable(String) │
└──────┴──────────────────┘
```

```sql
:) select * from file(data);
```

```response
┌─a─┬─b─────┐
│ 1 │ Data1 │
│ 2 │ Data2 │
│ 3 │ Data3 │
└───┴───────┘
```

<Note>
  O ClickHouse consegue detectar apenas um subconjunto de formatos, e essa detecção leva algum tempo; por isso, é sempre preferível especificar o formato explicitamente.
</Note>
