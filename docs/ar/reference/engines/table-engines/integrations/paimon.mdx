يوفّر هذا المحرك تكاملًا للقراءة فقط مع جداول Apache [Paimon](https://paimon.apache.org/) الموجودة في Amazon S3 وAzure وHDFS والجداول المخزّنة محليًا.
ويدعم قراءات اللقطات وعمليات القراءة التزايدية واستبعاد الأقسام الأساسي الذي يوفّره المحرك.

## إنشاء جدول {#create-table}

لاحظ أن جدول Paimon يجب أن يكون موجودًا بالفعل في التخزين، إذ لا يدعم هذا الأمر معلمات DDL لإنشاء جدول جديد.
يتطلب إنشاء جداول `Paimon*` تفعيل `enable_paimon_storage_engine` (وهو معطّل افتراضيًا)، لذا قم بتمكينه قبل تشغيل `CREATE TABLE`.

```sql
SET enable_paimon_storage_engine = 1;

CREATE TABLE paimon_table_s3
    ENGINE = PaimonS3(url, [, access_key_id, secret_access_key] [,format] [,compression])

CREATE TABLE paimon_table_azure
    ENGINE = PaimonAzure(connection_string|storage_account_url, container_name, blobpath, [,account_name], [,account_key] [,format] [,compression_method])

CREATE TABLE paimon_table_hdfs
    ENGINE = PaimonHDFS(path_to_table, [,format] [,compression_method])

CREATE TABLE paimon_table_local
    ENGINE = PaimonLocal(path_to_table, [,format] [,compression_method])
```

## وسائط المحرك {#engine-arguments}

يتوافق وصف هذه الوسائط مع وصف الوسائط في المحركات `S3` و`AzureBlobStorage` و`HDFS` و`File`، كلٌّ بحسبه.
يشير `format` إلى تنسيق ملفات البيانات في جدول Paimon.

يمكن تحديد معلمات المحرك باستخدام [المجموعات المسماة](/ar/concepts/features/configuration/server-config/named-collections)

### مثال {#example}

```sql
CREATE TABLE paimon_table ENGINE=PaimonS3('http://test.s3.amazonaws.com/clickhouse-bucket/test_table', 'test', 'test')
```

استخدام المجموعات المُسمّاة:

```xml
<clickhouse>
    <named_collections>
        <paimon_conf>
            <url>http://test.s3.amazonaws.com/clickhouse-bucket/</url>
            <access_key_id>test</access_key_id>
            <secret_access_key>test</secret_access_key>
        </paimon_conf>
    </named_collections>
</clickhouse>
```

```sql
CREATE TABLE paimon_table ENGINE=PaimonS3(paimon_conf, filename = 'test_table')
```

## الإمكانات {#capabilities}

* تتم عمليات قراءة اللقطات من أحدث لقطة للجدول.
* تتم عمليات القراءة التزايدية استنادًا إلى معرّف اللقطة المُثبَّتة عند تفعيلها.
* استبعاد الأقسام عند تمكين `use_paimon_partition_pruning`.
* تحديث اختياري للبيانات الوصفية في الخلفية عند ضبطه.
* معرّف UUID ثابت للجدول عند استخدام قواعد بيانات Atomic/Replicated، مما يتيح وحدات الماكرو `{uuid}` في مسارات Keeper.
* تطور المخطط: يُقرأ كل ملف بيانات وفق المخطط الذي كُتب به، وتُطابَق أعمدته ذات المستوى الأعلى (top-level) مع المخطط الحالي عبر معرّف حقل Paimon، وبذلك تُقرأ الأعمدة التي أُعيدت تسميتها، وكذلك الأعمدة المحذوفة التي أُعيدت إضافتها بالاسم نفسه، كما هو الحال في Spark.

## جداول المفتاح الأساسي {#primary-key-tables}

لم يُنفَّذ الدمج عند القراءة (merge-on-read) بعد، لذا لا يُقرأ جدول المفتاح الأساسي إلا في الحالات التي يقرؤه فيها Paimon دون دمج: إذ تُقرأ الحاوية
عندما تكون جميع ملفات البيانات فيها أعلى من المستوى 0، ومن المعروف أنها لا تحتوي على صفوف سحب (retract)، وتقع كلها في مستوى واحد. أما مع
`deletion-vectors.enabled` أو `'merge-engine' = 'first-row'` فيمكن أن تتوزع الملفات على عدة مستويات، وما لم يُضبط
`batch-scan-mode` على وضع غير `none`، فلن تُقرأ ملفات المستوى 0 إلا بعد دمجها، تمامًا كما في Paimon.
وتؤدي قراءة أي حاوية أخرى إلى رفع استثناء؛ ولجعلها قابلة للقراءة، يمكن إجراء دمج كامل في Paimon (`compact_strategy => 'full'`). أما عمليات القراءة
التزايدية لجداول المفتاح الأساسي فغير مدعومة.

## الجداول التي تحتوي على متجهات الحذف {#deletion-vectors}

لا تُطبَّق متجهات الحذف، ولذلك **يتعذّر قراءة اللقطات التي تحتوي على متجهات حذف**: إذ ستظل النتيجة
تتضمن الصفوف التي أزالتها عبارات `DELETE` و`UPDATE` اللاحقة. لذا فإن قراءة لقطة يُدرج ملف بيان الفهرس الخاص بها
متجهات حذف ترفع استثناءً، حتى بعد إيقاف `deletion-vectors.enabled`.

يُطبِّق الدمج الكامل في Paimon (`compact_strategy => 'full'`) متجهات الحذف، فتصبح اللقطات المُنشأة بعده
قابلة للقراءة من جديد.

تتوقف القراءة التزايدية عند أول لقطة غير مستهلكة تحتوي على متجهات حذف، وتظل متوقفة عندها حتى بعد إجراء دمج
كامل، لأن جميع اللقطات السابقة لهذا الدمج تُدرج متجهات الحذف نفسها. ولا يتقدم المؤشر في هذه الحالة.
وتُستأنف القراءة بمجرد أن يُنهي Paimon صلاحية تلك اللقطات، أو عند التخلي عنها بنقل المؤشر إلى لقطة
الدمج الكامل، مما يؤدي إلى حذف جميع اللقطات التي لم تُستهلك بعد وصولًا إليها (راجع
[عندما يتعذر قراءة لقطة](#when-a-snapshot-cannot-be-read)):

```bash
clickhouse-keeper-client -q "set '<paimon_keeper_path>/committed_snapshot' '<snapshot id of the full compaction>'"
```

وفي كلتا الحالتين، تبقى الصفوف التي أزالتها متجهات الحذف تلك ضمن البيانات التي سبق أن أعادتها القراءة التزايدية.

## الإعدادات {#settings}

يستخدم هذا المحرك الإعدادات نفسها المستخدمة في محركات التخزين الكائني المقابلة، ويضيف إعدادات خاصة بـ Paimon:

* `enable_paimon_storage_engine` — يتيح إنشاء محركات الجداول `Paimon` و`PaimonS3` و`PaimonAzure` و`PaimonHDFS` و`PaimonLocal`. القيمة الافتراضية: `0` (معطّل).
* `use_paimon_metadata_files_cache` — يفعّل ذاكرة التخزين المؤقت لملفات البيانات الوصفية في Paimon (تخزّن `manifest list` و`manifest` بعد فك التسلسل). اضبطه على `1` للتفعيل، و`0` للتعطيل. القيمة الافتراضية: `0`. تختلف كيفية تطبيق هذا الإعداد بين دوال الجداول ومحركات الجداول الدائمة — راجع الملاحظة أدناه.
* `paimon_incremental_read` — يفعّل وضع القراءة التزايدية.
* `paimon_incremental_read_append_overwrite` — تُعيد القراءة التزايدية أيضًا الصفوف التي تكتبها لقطات `OVERWRITE`، على غرار `streaming-read-append-overwrite` في Paimon. القيمة الافتراضية: `0`.
* `paimon_metadata_refresh_interval_sec` — الفاصل الزمني لتحديث البيانات الوصفية في الخلفية، بالثواني. عند ضبطه على قيمة أكبر من 0، تسحب مهمة تعمل في الخلفية أحدث لقطة ومخطط دوريًا من التخزين الكائني. القيمة الافتراضية: 30.
* `paimon_keeper_path` — مسار Keeper لحالة القراءة التزايدية. يجب ضبطه وأن يكون فريدًا لكل جدول؛ ويدعم وحدات الماكرو مثل `{database}` و`{table}` و`{uuid}`.
* `paimon_replica_name` — اسم النسخة المتماثلة لحالة القراءة التزايدية. يجب ضبطه وأن يكون فريدًا لكل نسخة متماثلة؛ ويدعم وحدات الماكرو مثل `{replica}`.

مثال (تفعيل محرك Paimon التجريبي وذاكرة التخزين المؤقت لملفات البيانات الوصفية):

```sql
SET enable_paimon_storage_engine = 1;
SET use_paimon_metadata_files_cache = 1;

CREATE TABLE paimon_cached
ENGINE = PaimonS3(paimon_conf, filename = 'paimon_all_types');
```

<Note title="دورة حياة `use_paimon_metadata_files_cache`">
  تعتمد كيفية تطبيق `use_paimon_metadata_files_cache` على طريقة الوصول إلى جدول Paimon:

  * **دوال الجداول** (مثل `SELECT ... FROM paimonS3(...)`): يُقيَّم قرار استخدام ذاكرة التخزين المؤقت لكل استعلام، لذلك يمكنك تمرير `SETTINGS use_paimon_metadata_files_cache = 1` مباشرةً في عبارة `SELECT`.
  * **محركات الجداول الدائمة** (`PaimonS3` و`PaimonAzure` و`PaimonHDFS` و`PaimonLocal` والاسم البديل `Paimon`): يُثبَّت قرار استخدام ذاكرة التخزين المؤقت مرةً واحدة عند تهيئة البيانات الوصفية للجدول، ويُخزَّن في مكونات دائمة غير قابلة للتغيير؛ كما أن مسار تحديث البيانات الوصفية لا يعيد عمدًا قراءة هذا الإعداد. لذلك، فإن تمرير `SETTINGS use_paimon_metadata_files_cache = 1` ضمن عبارة `SELECT` على جدول دائم جرت تهيئته بالفعل لا يكون له أي تأثير — إذ يستمر استخدام القرار الذي جرى تثبيته سابقًا. ولتغييره، اضبط `use_paimon_metadata_files_cache` قبل تهيئة البيانات الوصفية للجدول، أو نفّذ `DROP` ثم أعد `CREATE` الجدول بالقيمة المطلوبة.

  سعة ذاكرة التخزين المؤقت على مستوى الخادم (`paimon_metadata_files_cache_size`) *ليست* مُثبَّتة: فهي إعداد runtime يمكن تغييره عبر `SYSTEM RELOAD CONFIG`، ويسري مفعوله فورًا حتى على الجداول التي جرت تهيئتها بالفعل.
</Note>

## أمثلة على القراءة التزايدية {#incremental-read-examples}

القراءة التزايدية باستخدام حالة Keeper:

```sql
CREATE TABLE paimon_inc
ENGINE = PaimonS3(paimon_conf, filename = 'paimon_all_types')
SETTINGS
    paimon_incremental_read = 1,
    paimon_keeper_path = '/clickhouse/{database}/{uuid}',
    paimon_replica_name = '{replica}';
```

### إعدادات على مستوى الاستعلام للقراءة التزايدية {#query-level-settings-for-incremental-read}

الإعدادات التالية هي **على مستوى الاستعلام** (تُمرَّر عبر `SELECT ... SETTINGS`، وليس ضمن `CREATE TABLE`). وهي تتحكم في سلوك كل استعلام على حدة لعمليات القراءة التزايدية:

* `paimon_target_snapshot_id` — يقرأ فقط التغييرات الخاصة باللقطة المحددة. لا تتقدّم العلامة المائية المُعتمدة في Keeper، لذا يمكن إعادة قراءة اللقطة نفسها أي عدد من المرات. القيمة الافتراضية: `-1` (معطّل).
* `max_consume_snapshots` — الحد الأقصى لعدد اللقطات التي يمكن استهلاكها في قراءة تزايدية واحدة. عندما يكون المصدر قد راكم عددًا كبيرًا من اللقطات غير المقروءة، يحدّ هذا الإعداد من عدد اللقطات التي تُستهلك في كل استعلام للتحكم في حجم الدفعة. `0` تعني عدم وجود حد. القيمة الافتراضية: `0`.

**قراءة لقطة مستهدفة** — تُرجع دائمًا التغييرات الخاصة باللقطة 1، بغض النظر عن العلامة المائية الحالية:

```sql
SELECT count()
FROM paimon_inc
SETTINGS paimon_target_snapshot_id = 1;
```

**تحديد عدد اللقطات في كل دفعة** — إذا كانت هناك ثلاث لقطات جديدة قيد الانتظار، فلا تستهلك أكثر من اثنتين لكل استعلام:

```sql
SELECT count()
FROM paimon_inc
SETTINGS max_consume_snapshots = 2;
```

### إرجاع المستودع إلى حالة سابقة {#rewinding-the-warehouse}

يسجّل مؤشر Keeper الموجود في `paimon_keeper_path` المدى الذي بلغه استهلاك الدفق، وتفترض عمليات القراءة التزايدية أن المستودع لا يتقدّم إلا إلى الأمام، إذ تتزايد معرّفات لقطات Paimon تزايدًا رتيبًا ولا يُعاد استخدامها أبدًا. ولا ضرر في إنهاء صلاحية اللقطات القديمة، فذلك يزيل بادئة من المعرّفات ويترك المعرّفات التي تليها على حالها.

أما إرجاع المستودع *إلى الوراء* فيُخلّ بهذا الافتراض. فاستعادة المستودع من نسخة احتياطية أقدم، أو التراجع به إلى حالة سابقة باستخدام محرك آخر، أو حذف جدول Paimon وإعادة إنشائه في المسار نفسه، كلها تُرجع معرّفات اللقطات إلى الوراء، فيعيد المثيل الكاتب حينئذٍ استخدام معرّفات سبق أن استهلكها المؤشر.

**يتطلّب إرجاع المستودع إلى الوراء إعادة ضبط المؤشر ضمن العملية نفسها.** ويسجّل المؤشر أيضًا اللقطة التي يشير إليها، لذا فبمجرد أن يعيد المثيل الكاتب استخدام معرّف لقطة المؤشر، تفشل عملية القراءة مع `INVALID_STATE`: فلا يُقرأ شيء ويبقى المؤشر دون تغيير. وللاسترداد، وجّه المؤشر إلى اللقطة التي أُرجع إليها المستودع، فتُقرأ بذلك كل لقطة كُتبت منذ الإرجاع، أو اضبطه على قيمته الحالية، فتُتجاوز بذلك اللقطات ذات المعرّفات المُعاد استخدامها. أما المؤشر المضبوط يدويًا، أو الذي كتبه إصدار أقدم، فيُعتمد كما هو إلى أن تُقدّمه عملية قراءة. ولا يمكن إجراء أي تحقق بعد أن تُنهي Paimon صلاحية اللقطة التي يشير إليها المؤشر، ولا في حالة إرجاع يُبقي على لقطة المؤشر ويقع أثناء تحميل عملية قراءة للّقطات التي تليها.

وإذا ترك الإرجاعُ المؤشرَ يشير إلى ما بعد أحدث لقطة في المستودع، تفشل عملية القراءة مع `INVALID_STATE` بدلًا من الإبلاغ بعدم وجود بيانات جديدة، ويتضمّن الـ error اسم أمر الاسترداد. وفي هذه الحالة لا يُقرأ شيء ويبقى المؤشر دون تغيير، لذا تفشل كل عملية استطلاع لاحقة بالطريقة نفسها إلى أن تُعالَج المشكلة:

```
clickhouse-keeper-client -q "set '<paimon_keeper_path>/committed_snapshot' '<latest snapshot id>'"
```

لا تحذف العقدة `committed_snapshot` بغرض الاسترداد. فغياب المؤشر يعني &quot;لم يُستهلك قط&quot;، ما يجعل عملية القراءة التالية إعادة قراءة كاملة للجدول بأكمله بدلاً من استئناف القراءة.

قبل إعادة ضبط المؤشر، أوقف مؤقتاً جميع المستهلكين الذين يتشاركون `paimon_keeper_path`، بما في ذلك العروض المُجسَّدة القابلة للتحديث، وانتظر حتى تكتمل عمليات القراءة قيد الإرسال.

يتوقف تثبيت عملية القراءة على المؤشر الذي رصدته. فإذا تغيّر المؤشر بعد رصده وقبل التثبيت، تفشل القراءة بالخطأ `INVALID_STATE` دون أن تُسلِّم أي بيانات، وتبقى القيمة التي عيّنتها كما هي. أما القراءة التي ثُبِّتت بالفعل فيظل بإمكانها تسليم دفعتها بعد إعادة ضبط المؤشر؛ ولذا قد يؤدي إرجاع المؤشر إلى الوراء إلى تسليم تلك الدفعة مرة أخرى.

لا تحذف `processing_lock` ولا تستبدله يدوياً. فهو عقدة مؤقتة تملكها session ‏ClickHouse Keeper التي تُشغِّل القراءة التزايدية، ودورة حياتها ليست واجهة استرداد مخصصة للمشغِّل.

### عندما تتعذر قراءة لقطة {#when-a-snapshot-cannot-be-read}

يتخطى النظام تلقائيًا اللقطات التي أنهى Paimon صلاحيتها: فانتهاء الصلاحية يزيل بادئة من معرّفات اللقطات، ومن ثَمّ يُعرف أن كل ما يسبق أقدم لقطة في المستودع قد حُذف، فيتجاوزه المؤشر.

أما أي إخفاق آخر في قراءة لقطة، كخطأ عابر في التخزين الكائني أو ملف لقطة تالف، فيؤدي إلى فشل الاستعلام ويُبقي المؤشر في موضعه. ولا يوجد عن قصد أي إعداد للتغاضي عن ذلك؛ إذ إن تخطي لقطة لم تُقرأ يعني الحذف الدائم للبيانات المُثبَّتة فيها، كما أن وجود خيار دائم لـ&quot;التغاضي عن الأخطاء&quot; من شأنه أن يحوّل كل خلل عابر في الشبكة مستقبلًا إلى فقدان صامت للبيانات. ولأن المؤشر لا يتغير، فإن الخطأ العابر لا يتطلب أي تدخل على الإطلاق: إذ تعيد عملية الاستطلاع التالية قراءة النطاق نفسه وتنجح.

إذا تعذرت قراءة اللقطة فعلًا وكان لا بد من مواصلة الدفق، فتخلَّ عنها صراحةً. تذكر رسالة الخطأ الأمر اللازم، لكن انتبه إلى ثمنه: فعملية القراءة الفاشلة لم تُرجع شيئًا، ولذا فإن نقل المؤشر إلى اللقطة غير القابلة للقراءة يعني التخلي عن **جميع** اللقطات التي لم تُستهلك بعد حتى تلك اللقطة بما فيها، لا عن اللقطة غير القابلة للقراءة وحدها.

لنفترض أن المؤشر عند 1، وأن اللقطات 2 و3 و4 قيد الانتظار، وأن اللقطة 3 غير قابلة للقراءة:

```bash
# Abandons snapshots 2 and 3; the next read resumes at 4.
clickhouse-keeper-client -q "set '/clickhouse/tables/<uuid>/committed_snapshot' '3'"
```

للاحتفاظ باللقطات القابلة للقراءة، نفّذ أولاً عملية تصريف حتى اللقطة غير القابلة للقراءة. تستهلك كل عملية استطلاع لقطةً واحدة وتُحرِّك المؤشر إلى الأمام، إلى أن يبلغ اللقطة التي تتعذّر قراءتها:

```sql
-- Delivers snapshot 2 and advances the cursor to 2; the next poll fails on 3 again.
SELECT * FROM paimon_inc SETTINGS max_consume_snapshots = 1;
```

```bash
# Now only snapshot 3 is abandoned.
clickhouse-keeper-client -q "set '/clickhouse/tables/<uuid>/committed_snapshot' '3'"
```

في كلتا الحالتين، يُسجَّل القرار على أنه إجراء صريح يتخذه المسؤول عن تشغيل النظام، لا على أنه أمر مُستنتَج من أحد الإعدادات.

## من Paimon إلى MergeTree عبر عرض مُجسَّد قابل للتحديث {#paimon-to-mergetree-via-refresh-mv}

يمكنك إنشاء مسار متكامل من المصدر إلى الوجهة يزامن البيانات باستمرار من جدول Paimon إلى جدول MergeTree باستخدام عرض مُجسَّد قابل للتحديث في وضع `APPEND`. في كل دورة تحديث، لا تُقرأ من Paimon إلا البيانات التزايدية الجديدة، ثم تُلحَق بجدول الوجهة.

**الخطوة 1 — أنشئ جدول مصدر Paimon مع تمكين القراءة التزايدية وتحديث البيانات الوصفية.**

يستخدم المثال أدناه `PaimonLocal`. استبدل المحرك بـ `PaimonS3` أو `PaimonAzure` أو `PaimonHDFS` أو المحرك `Paimon` الذي يكتشف الإعدادات تلقائيًا، بحسب ما يناسب الواجهة الخلفية للتخزين لديك:

```sql
SET enable_paimon_storage_engine = 1;

-- Local storage
CREATE TABLE paimon_mv_source
ENGINE = PaimonLocal('/path/to/paimon/table')
SETTINGS
    paimon_incremental_read = 1,
    paimon_keeper_path = '/clickhouse/tables/{uuid}',
    paimon_replica_name = '{replica}',
    paimon_metadata_refresh_interval_sec = 1;

-- S3 storage (the `Paimon` engine defaults to the S3 implementation when no `disk` is specified)
CREATE TABLE paimon_mv_source
ENGINE = Paimon('http://minio:9000/bucket/path/to/table', 'access_key', 'secret_key')
SETTINGS
    paimon_incremental_read = 1,
    paimon_keeper_path = '/clickhouse/tables/{uuid}',
    paimon_replica_name = '{replica}',
    paimon_metadata_refresh_interval_sec = 1;
```

يضبط `paimon_metadata_refresh_interval_sec` الفاصل الزمني لتحديث البيانات الوصفية في الخلفية، بالثواني. وعندما تكون قيمته أكبر من 0، تسحب مهمة تعمل في الخلفية أحدث لقطة ومخطط من التخزين الكائني بشكل دوري، بحيث تتمكن دورة تحديث MV من رؤية البيانات المُثبَّتة حديثًا دون انتظار أن يؤدّي استعلام إلى تشغيل تحديث البيانات الوصفية. القيمة الافتراضية هي 30. استخدمه بحذر عند التعامل مع عدد كبير من الجداول لتجنّب الإفراط في استخدام التخزين الكائني وعمليات الإدخال/الإخراج الخاصة بـ Keeper.

**الخطوة 2 — أنشئ جدول الوجهة من نوع MergeTree (مع استنساخ المخطط من جدول Paimon):**

```sql
CREATE TABLE paimon_mv_dest AS paimon_mv_source
ENGINE = MergeTree()
ORDER BY tuple();
```

**الخطوة 3 — أنشئ العرض المُجسَّد القابل للتحديث:**

```sql
CREATE MATERIALIZED VIEW paimon_mv
REFRESH EVERY 10 SECOND
APPEND
TO paimon_mv_dest
AS SELECT * FROM paimon_mv_source;
```

كل 10 ثوانٍ، ينفّذ الـ MV الاستعلام `SELECT * FROM paimon_mv_source`، الذي يعيد فقط الصفوف المُضافة منذ آخر لقطة تم تثبيتها، ويضيفها إلى `paimon_mv_dest`.

**التنظيف:**

```sql
SYSTEM STOP VIEW paimon_mv;
DROP VIEW IF EXISTS paimon_mv SYNC;
DROP TABLE IF EXISTS paimon_mv_dest SYNC;
DROP TABLE IF EXISTS paimon_mv_source SYNC;
```

<Note>
  أوقِف الـ MV قبل حذفها لمنع التحديث في الخلفية من تعطيل عمليات DDL.
</Note>

## القيود {#limitations}

* تتطلب القراءة التزايدية تهيئة Keeper ‏(ZooKeeper).
* تتطلب القراءة التزايدية ضبط `paimon_keeper_path` بحيث يكون فريدًا لكل جدول.
* يجب أن يكون `paimon_replica_name` فريدًا لكل نسخة متماثلة ضمن مسار Keeper نفسه.
* تستخدم القراءة التزايدية آلية تسليم من نوع at-most-once: إذ تُقدَّم اللقطة المُثبَّتة عند جمع ملفات البيانات، قبل استهلاك البيانات فعليًا. وإذا فشل الاستعلام بعد جمع الملفات، فلن تُعاد قراءة اللقطات التي تم تجاوزها عند إعادة المحاولة.
* محرك الجدول للقراءة فقط؛ ولا يدعم تعديل البيانات.
* لا تتعامل القراءة التزايدية مع حذف البيانات التاريخية من مصدر Paimon. إذا حُذفت بيانات Paimon من المصدر الأصلي أو جرى تحديثها، فلن تُزال تلقائيًا الصفوف المقابلة التي كُتبت بالفعل إلى جدول وجهة من نوع ClickHouse MergeTree. يجب عليك إصدار `ALTER TABLE ... DELETE` يدويًا على جدول MergeTree لتنظيف البيانات القديمة.
* تُعيد القراءة التزايدية الأولى جميع صفوف اللقطة الحالية. وبعد ذلك، لا تُسلِّم القراءة التزايدية إلا صفوف لقطات `APPEND`، على غرار قراءة التدفق في Paimon لجدول إلحاق: إذ تُتجاهَل لقطات `COMPACT` و`OVERWRITE` و`ANALYZE`. ويُثبِّت Paimon كل عملية كتابة تحذف ملفات البيانات أو تعيد كتابتها بوصفها `OVERWRITE` (`INSERT OVERWRITE` و`TRUNCATE`، وعمليات إعادة الكتابة بأسلوب copy-on-write الناتجة عن `DELETE` و`UPDATE` وعن `MERGE INTO` الذي يحدّث الصفوف أو يحذفها)، ولذلك لا تُسلَّم الصفوف التي يكتبها مثل هذا التثبيت، كالإصدارات الجديدة من الصفوف المحدَّثة، ويُسجَّل تحذير لكل لقطة `OVERWRITE` متجاهَلة. أما عند ضبط `paimon_incremental_read_append_overwrite = 1` فتُسلَّم هذه الصفوف، كما هو الحال مع `streaming-read-append-overwrite` في Paimon، إلى جانب الصفوف غير المتغيرة من كل ملف بيانات أعاد التثبيت كتابته، باستثناء ملفات البيانات التي تزيلها لقطة لاحقة يقرؤها الاستعلام نفسه. ولأن لقطات `COMPACT` لا تُقرأ، فإن الاستعلام الذي يقرأ لقطة `APPEND`، ولقطة `COMPACT` تدمج الملف الذي أضافته، ولقطة `OVERWRITE` تعيد كتابة الملف المدمج، يُعيد صفوف كلٍّ من الملف الأصلي والملف المُعاد كتابته: فتظهر الصفوف غير المتغيرة مرتين في نتيجته، وتظهر الصفوف المتغيرة بإصداراتها القديمة والجديدة معًا. ولا يزال `paimon_target_snapshot_id` يُعيد دلتا لأي لقطة.
* بعد القراءة التزايدية الأولى، تؤدي أي لقطة ذات نوع تثبيت لا يعرفه ClickHouse إلى فشل القراءة التزايدية، وتفشل كل قراءة لاحقة كذلك إلى أن تتم ترقية ClickHouse أو يُنقل المؤشر إلى ما بعد هذه اللقطة في Keeper، كما توضح رسالة الخطأ.
* إذا أُسقِط جدول Paimon الأساسي ثم أُعيد إنشاؤه على مسار تخزين الكائنات نفسه (مثلًا عبر Flink أو Spark)، فيجب عليك تنفيذ `DROP` ثم إعادة `CREATE` لجدول ClickHouse المقابل. يكتشف ClickHouse إعادة الإنشاء عبر مقارنة الطابع الزمني لإنشاء schema-0 ويُصدر خطأً؛ ولا يمكن استخدام جدول ClickHouse القديم حتى يُعاد إنشاؤه.
* تُطابَق الحقول داخل عمود `ROW` مع ملفات البيانات حسب الاسم، لا حسب معرّف الحقل في Paimon. لذلك فإن قراءة ملف بيانات كُتب قبل إعادة تسمية حقل داخل `ROW`، أو قبل حذف مثل هذا الحقل وإضافة حقل آخر بالاسم نفسه (مع المقارنة دون اعتبار لحالة الأحرف)، يرفع استثناءً، لأن النتيجة كانت ستحتوي على `NULL` للحقل المُعاد تسميته وعلى قيم الحقل المحذوف للحقل المُعاد إضافته. أما إضافة الحقول وحذفها فمدعومان. ويمكن جعل اللقطات المُنشأة لاحقًا قابلة للقراءة بإعادة كتابة الجدول بالمخطط الحالي في Paimon، على سبيل المثال باستخدام `INSERT OVERWRITE <table> SELECT * FROM <table>`. وعندما تصل قراءة تزايدية إلى ملف بيانات كهذا، فإنها ترفع استثناءً دون تقديم مؤشرها. وللمتابعة، انتظر حتى يُنهي Paimon صلاحية اللقطات المُثبَّتة قبل التغيير، أو تخلَّ عنها بنقل المؤشر إلى آخرها، ما يؤدي إلى حذف كل لقطة لم تُستهلك بعد حتى تلك اللقطة (راجع [عندما تتعذر قراءة لقطة](#when-a-snapshot-cannot-be-read)).

## الأسماء البديلة {#aliases}

يكتشف محرك الجدول `Paimon` تلقائيًا الواجهة الخلفية للتخزين من إعداد `disk`، ثم يوجّه إلى `PaimonS3` أو `PaimonAzure` أو `PaimonLocal` وفقًا لذلك. وعند عدم تحديد `disk`، يُستخدَم `PaimonS3` افتراضيًا.

## الأعمدة الافتراضية {#virtual-columns}

* `_path` — مسار الملف. النوع: `LowCardinality(String)`.
* `_file` — اسم الملف. النوع: `LowCardinality(String)`.
* `_size` — حجم الملف بالبايت. النوع: `Nullable(UInt64)`. إذا كان حجم الملف غير معروف، تكون القيمة `NULL`.
* `_time` — وقت آخر تعديل للملف. النوع: `Nullable(DateTime)`. إذا كان الوقت غير معروف، تكون القيمة `NULL`.
* `_etag` — قيمة etag للملف. النوع: `LowCardinality(String)`. إذا كانت قيمة etag غير معروفة، تكون القيمة `NULL`.
