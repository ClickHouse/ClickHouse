<div id="description">
  ## الوصف
</div>

يحتوي على معلومات عن كل جدول منفصل.

<div id="columns">
  ## الأعمدة
</div>

{/*AUTOGENERATED_START*/}

* `database` ([String](/ar/reference/data-types/string)) — اسم قاعدة البيانات التي ينتمي إليها الجدول.
* `table` ([String](/ar/reference/data-types/string)) — اسم الجدول.
* `uuid` ([UUID](/ar/reference/data-types/uuid)) — معرّف UUID الخاص بالجدول (قاعدة بيانات Atomic).
* `metadata_path` ([String](/ar/reference/data-types/string)) — مسار البيانات الوصفية للجدول في نظام الملفات.
* `is_permanently` ([UInt8](/ar/reference/data-types/int-uint)) — الجدول منفصل نهائيًا.

{/*AUTOGENERATED_END*/}

<div id="notes">
  ## ملاحظات
</div>

بالنسبة إلى `DatabaseMySQL` و`DatabasePostgreSQL`، لا تملك قواعد البيانات هذه البيانات الفعلية، إذ تكون مخزنة على خادم MySQL/PostgreSQL البعيد. لذلك، يُنفَّذ الأمر `DROP TABLE` على جدول تابع لأحد محركات قواعد البيانات هذه داخليًا بوصفه `detachTablePermanently`: فهو لا يزيل سوى التتبّع المحلي للجدول في ClickHouse، ويظهر الجدول في `system.detached_tables` بالقيمة `is_permanently = 1`، تمامًا كما عند تنفيذ `DETACH TABLE PERMANENTLY` صراحةً. ولا تتأثر البيانات البعيدة نفسها. بالنسبة إلى قواعد بيانات MySQL/PostgreSQL المستمرة، تظل حالة الفصل قائمة بعد إعادة تشغيل الخادم وإعادة الاتصال: يخزّن `DatabaseMySQL` وسم `.remove_flag` في دليل البيانات الوصفية، بينما يخزّن `DatabasePostgreSQL` وسم `.removed`. ويُعاد تحميل كليهما بواسطة `loadStoredObjects` عند بدء التشغيل. ولا يظهر الجدول مجددًا إلا إذا أُنشئ تعيين جديد لقاعدة بيانات خارجية من دون دليل البيانات الوصفية القديم، مثلًا عند إزالة البيانات الوصفية أو إنشاء قاعدة البيانات باسم مختلف.

</div>

```sql

```
