تصف هذه الصفحة عبارات `KILL QUERY` و`KILL MUTATION` و`KILL TRANSACTION` و`KILL PART_MOVE_TO_SHARD`.

افتراضيًا، يرفع `KILL QUERY` استثناء `NOTHING_TO_KILL` عندما لا يُبقي تعبير `WHERE` الخاص به أي صفوف مؤهلة في `system.processes` بعد استبعاد عبارة `KILL` الحالية، ويرفع `KILL MUTATION` استثناءً عندما لا يطابق تعبير `WHERE` الخاص به أي صف في `system.mutations`. للسماح بعدم وجود مطابقات دون رفع استثناء، اضبط [`kill_throw_if_noop`](/ar/operations/settings/settings#kill_throw_if_noop) على `false`.
لا يرفع `KILL TRANSACTION` و`KILL PART_MOVE_TO_SHARD` استثناءً أبدًا عند عدم وجود مطابقات، بل يُعيدان نتيجة فارغة.
لا يرفع التنفيذ باستخدام `ON CLUSTER` استثناءً عند عدم وجود مطابقات، لأن نتائج المطابقة لا تُجمَّع عبر المضيفين.

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

تُستخدَم لإنهاء الاستعلامات الجارية حاليًا قسرًا.
تُحدَّد الاستعلامات المطلوب إنهاؤها من جدول system.processes باستخدام المعايير المحددة في عبارة `WHERE` ضمن استعلام `KILL`.

أمثلة:

أولًا، ستحتاج إلى الحصول على قائمة الاستعلامات غير المكتملة. يعرض استعلام SQL هذا هذه القائمة مرتبةً حسب الأطول تشغيلًا:

قائمة من عقدة ClickHouse واحدة:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

قائمة من عنقود ClickHouse:

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

أنهِ الاستعلام:

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  إذا كنت تُنهي استعلامًا في ClickHouse Cloud أو في عنقود مُدار ذاتيًا، فتأكّد من استخدام الخيار `ON CLUSTER [cluster-name]` لضمان إنهاء الاستعلام على جميع النُسخ المتماثلة
</Tip>

لا يمكن للمستخدمين للقراءة فقط إيقاف سوى استعلاماتهم الخاصة.

يمكن للمستخدم الذي لم يُمنح إذن `SELECT` على `system.processes` إلغاء استعلامه الخاص بتحديد معرّفه:
`KILL QUERY WHERE query_id = '<id>'`. إذا لم يكن لدى المستخدم هذا الإذن ولا إذن `KILL QUERY`، فإن تحديد معرّف استعلام
ليس قيد التشغيل باسمه لا يُلغي أي استعلام ويرفع استثناء `NOTHING_TO_KILL` افتراضيًا. أما عند ضبط
الإعداد [`kill_throw_if_noop`](/ar/operations/settings/settings#kill_throw_if_noop) على `false`، فلا يُرجع أي صفوف بدلًا من ذلك؛
أما المستخدم الذي لديه إذن `KILL QUERY` دون إذن `SELECT` المذكور فيُرفَض طلبه لافتقاره إلى إذن `SELECT`.
ويظل أي شرط آخر في `WHERE`، وكذلك `ON CLUSTER`، يتطلب الأذونات الموضّحة أعلاه.

بشكل افتراضي، يُستخدَم الإصدار غير المتزامن من الاستعلامات (`ASYNC`)، وهو لا ينتظر تأكيدًا على توقّف الاستعلامات.

ينتظر الإصدار المتزامن (`SYNC`) حتى تتوقف جميع الاستعلامات، ويعرض معلومات عن كل عملية عند توقفها.
تتضمن الاستجابة العمود `kill_status`، والذي يمكن أن يأخذ القيم التالية:

1. `finished` – تم إنهاء الاستعلام بنجاح.
2. `waiting` – جارٍ انتظار انتهاء الاستعلام بعد إرسال إشارة إليه بإنهائه.
3. تشرح القيم الأخرى سبب تعذّر إيقاف الاستعلام.

لا يتحقق الاستعلام الاختباري (`TEST`) إلا من صلاحيات المستخدم ويعرض قائمة بالاستعلامات المطلوب إيقافها.

## KILL MUTATION {#kill-mutation}

غالبًا ما يشير وجود عمليات mutation تستغرق وقتًا طويلًا أو عمليات mutation غير مكتملة إلى أن خدمة ClickHouse لا تعمل بكفاءة. وقد تتسبب الطبيعة غير المتزامنة لهذه عمليات mutation في استهلاكها جميع الموارد المتاحة على النظام. وقد تحتاج إلى أحد الخيارين التاليين:

* إيقاف جميع عمليات mutation الجديدة وعمليات `INSERT` و`SELECT` مؤقتًا، وترك قائمة انتظار عمليات mutation تكتمل.
* أو إنهاء بعض هذه عمليات mutation يدويًا بإرسال أمر `KILL`.

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

يحاول إلغاء [عمليات mutations](/ar/reference/statements/alter/index#mutations) الجارية حاليًا وإزالتها. تُحدَّد عمليات mutations المطلوب إلغاؤها من جدول [`system.mutations`](/ar/reference/system-tables/mutations) باستخدام عامل التصفية المحدد في عبارة `WHERE` ضمن استعلام `KILL`.

استعلام اختباري (`TEST`) يتحقق فقط من صلاحيات المستخدم ويعرض قائمة بعمليات mutations التي سيتم إيقافها.

أمثلة:

الحصول على `count()` لعدد عمليات mutations غير المكتملة:

عدد عمليات mutations من عقدة ClickHouse واحدة:

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

عدد عمليات mutation في عنقود ClickHouse من النُسخ المتماثلة:

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

استعلم عن قائمة عمليات mutation غير المكتملة:

قائمة عمليات mutation من عقدة ClickHouse واحدة:

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

قائمة عمليات mutation في عنقود ClickHouse:

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

أنهِّ عمليات الـ mutation عند الحاجة:

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

يكون هذا الاستعلام مفيدًا عندما تكون إحدى عمليات mutation عالقة ولا يمكنها الاكتمال (على سبيل المثال، إذا كانت إحدى الدوال في استعلام mutation ترفع استثناءً عند تطبيقها على البيانات الموجودة في الجدول).

لا يُتراجع عن التغييرات التي أجرتها mutation بالفعل.

<Note>
  لا يعني العمود `is_killed=1` (في ClickHouse Cloud فقط) في جدول [system.mutations](/ar/reference/system-tables/mutations) بالضرورة أن mutation قد انتهت بالكامل. فقد تظل mutation في حالة يكون فيها `is_killed=1` و`is_done=0` لفترة طويلة. ويمكن أن يحدث هذا إذا كانت mutation أخرى طويلة التشغيل تحجب mutation التي تم إنهاؤها. هذا وضع طبيعي.
</Note>

## KILL TRANSACTION {#kill-transaction}

أُضيف في: v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  هذه العبارة جزء من مجموعة الميزات التجريبية.
  لتمكين الدعم التجريبي للمعاملات، أضِف هذا الإعداد إلى [ملف التهيئة](/ar/concepts/features/configuration/server-config/configuration-files) لديك:

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  لمزيد من المعلومات، راجع صفحة [الدعم المعاملاتي (ACID)](/ar/concepts/features/operations/insert/transactions#transactions-commit-and-rollback).
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

تتراجع عن [المعاملات](/ar/reference/statements/transactions) الجارية التي تحددها عبارة `WHERE` من جدول [`system.transactions`](/ar/reference/system-tables/transactions).
بعد ذلك تصبح الـ session الخاصة بالمعاملة التي تم إنهاؤها في الحالة نفسها التي تكون عليها بعد فشل استعلام، كما هو موضح في [`COMMIT`](/ar/reference/statements/transactions#commit): فإلى أن تُنفِّذ `ROLLBACK`، يرفع `COMMIT` استثناءً من النوع `INVALID_TRANSACTION`.

تتطلب هذه العبارة امتياز `KILL TRANSACTION` وامتياز `SELECT` على `system.transactions`.
تحتوي الاستجابة على العمود `kill_status`، وتكون قيمته `waiting` للمعاملة التي تم التراجع عنها، ويليه الأعمدة `tid` و`tid_hash` و`elapsed` و`is_readonly` و`state` من `system.transactions`.

يقتصر الاستعلام الاختباري (`TEST`) على التحقق من صلاحيات المستخدم وعرض قائمة بالمعاملات التي سيتم التراجع عنها.

مثال:

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

أُضيف في: v21.11.0

<ExperimentalBadge />

<Note>
  نقل أجزاء البيانات بين المقاطع ميزة تجريبية، وتُفعَّل لكل جدول على حدة عبر إعداد MergeTree [`part_moves_between_shards_enable`](/ar/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable).
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

يُلغي عمليات نقل أجزاء البيانات بين المقاطع، التي بدأتها `ALTER TABLE ... MOVE PART ... TO SHARD`، والمحددة من الجدول [`system.part_moves_between_shards`](/ar/reference/system-tables/part_moves_between_shards) بواسطة عبارة `WHERE`.
يُتراجَع عن عملية النقل الملغاة في الخلفية، وتصبح قيمة `state` الخاصة بها في `system.part_moves_between_shards` هي `CANCELLED`.
أما عملية النقل التي بلغت الحالة `SOURCE_DROP` فلا يمكن إلغاؤها، وتستمر حتى تكتمل.

تتطلب هذه العبارة امتياز `SELECT` على `system.part_moves_between_shards`، كما يتطلب إلغاء أي عملية نقل امتياز `ALTER MOVE PARTITION` على الجدول الخاص بها، إضافةً إلى امتياز `MOVE PARTITION BETWEEN SHARDS`.
وعند استخدام `ON CLUSTER`، تتطلب العبارة امتيازَي النقل كليهما على `*.*`.
تحتوي الاستجابة على العمود `kill_status`، وتكون قيمته `waiting` لعملية النقل الملغاة و`cant_cancel` لعملية النقل التي لم يعد إلغاؤها ممكنًا، تليه الأعمدة `database` و`table` و`task_name` و`task_uuid` و`part_name` و`to_shard` و`state` من `system.part_moves_between_shards`.

يقتصر الاستعلام الاختباري (`TEST`) على عرض قائمة بعمليات النقل المراد إلغاؤها. المُعدِّل `SYNC` غير مدعوم، ويرفع استثناءً من النوع `NOT_IMPLEMENTED`.

مثال:

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
