تُنشئ عبارة `JOIN` جدولًا جديدًا من خلال دمج الأعمدة من جدول واحد أو عدة جداول باستخدام القيم المشتركة بينها. وهي عملية شائعة في قواعد البيانات التي تدعم SQL، وتقابل عملية ربط في [الجبر العلاقي](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators). وغالبًا ما يُشار إلى الحالة الخاصة المتمثلة في ربط جدول بنفسه باسم &quot;ربط ذاتي&quot;.

**البنية**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

تُسمّى التعبيرات الواردة في عبارة `ON` والأعمدة الواردة في عبارة `USING` &quot;مفاتيح الربط&quot;. ما لم يُذكر خلاف ذلك، فإن `JOIN` يُنتج [حاصل ضرب ديكارتيًا](https://en.wikipedia.org/wiki/Cartesian_product) من الصفوف ذات مفاتيح الربط المتطابقة، وقد يؤدي ذلك إلى نتائج تضم عددًا من الصفوف أكبر بكثير من الجداول المصدرية.

تتناول هذه الصفحة صيغة عبارة `JOIN` ودلالاتها. وللاطّلاع على كيفية تنفيذ عمليات الربط في ClickHouse، وأنواع الربط، والإعدادات، واعتبارات الذاكرة، والتحسينات، راجع [المحتوى ذو الصلة](#related-content).

## أنواع الربط المدعومة {#supported-types-of-join}

جميع أنواع [SQL JOIN](https://en.wikipedia.org/wiki/Join_\(SQL\)) القياسية مدعومة:

| Type               | Description                                                                                                                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | تُعاد الصفوف المتطابقة فقط.                                                                                                                                                                                                                       |
| `LEFT OUTER JOIN`  | تُعاد الصفوف غير المتطابقة من الجدول الأيسر بالإضافة إلى الصفوف المتطابقة.                                                                                                                                                                        |
| `RIGHT OUTER JOIN` | تُعاد الصفوف غير المتطابقة من الجدول الأيمن بالإضافة إلى الصفوف المتطابقة.                                                                                                                                                                        |
| `FULL OUTER JOIN`  | تُعاد الصفوف غير المتطابقة من كلا الجدولين بالإضافة إلى الصفوف المتطابقة.                                                                                                                                                                         |
| `CROSS JOIN`       | يُنتج حاصل الضرب الديكارتي للجدولين بالكامل. ولا تُحدَّد مفاتيح الربط **إطلاقًا**.                                                                                                                                                                |
| `NATURAL JOIN`     | يربط تلقائيًا جميع الأعمدة ذات الاسم نفسه في كلا الجدولين. ويظهر كل عمود مشترك مرة واحدة في النتيجة. ويدعم الصيغ `INNER` (الافتراضية) و`LEFT` و`RIGHT` و`FULL`. وهو مكافئ لـ `JOIN ... USING (col1, col2, ...)` حيث تُشتق قائمة الأعمدة تلقائيًا. |

* يشير `JOIN` من دون تحديد نوع إلى `INNER`.
* يمكن حذف الرمز `OUTER`.
* من الصيغ البديلة لـ `CROSS JOIN` تحديد عدة جداول في [عبارة `FROM`](/ar/reference/statements/select/from) مفصولة بفواصل.
* إذا لم تكن هناك أعمدة متطابقة لـ `NATURAL JOIN`، فإنه يعمل مثل `CROSS JOIN`.

تتوفر أيضًا في ClickHouse أنواع ربط إضافية:

| Type                                                | Description                                                                                                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | قائمة سماح على مفاتيح الربط، من دون إنتاج حاصل الضرب الديكارتي.                                                                                                                                                    |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | قائمة حظر على مفاتيح الربط، من دون إنتاج حاصل الضرب الديكارتي.                                                                                                                                                     |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | يعطّل جزئيًا (للجانب المقابل من `LEFT` و`RIGHT`) أو كليًا (بالنسبة إلى `INNER`) حاصل الضرب الديكارتي لأنواع `JOIN` القياسية. و`ANY FULL JOIN` غير مدعوم.                                                           |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | ربط للتسلسلات مع مطابقة غير تامة. راجع [استخدام ASOF JOIN](#asof-join-usage).                                                                                                                                      |
| `PASTE JOIN`                                        | يُجري دمجًا أفقيًا لجدولين. راجع [استخدام PASTE JOIN](#paste-join-usage).                                                                                                                                          |
| `INNER JOIN LATERAL`, `LEFT JOIN LATERAL`           | يربط استعلامًا فرعيًا يشير إلى أعمدة الجداول الواقعة على يساره. ميزة تجريبية، وتتطلب [`enable_lateral_join`](/ar/reference/settings/session-settings/enable#enable_lateral_join). راجع [LATERAL JOIN](#lateral-join). |

تُعرض مخططات توضيحية لكل نوع ربط وكل صرامة في [استخدام JOINs في ClickHouse](/ar/concepts/features/operations/select/joining-tables#join-types-and-strictness).

<Note>
  يؤدي تعطيل الإعداد `semi_join_include_columns_from_both_sides` أو `anti_join_include_columns_from_both_sides` إلى أن يقتصر الربط المعني على إتاحة جانبه المحفوظ فقط للتعابير التي تُحلَّل بعد تكوين نتيجة الربط.

  * يُتيح `LEFT SEMI JOIN` و`LEFT ANTI JOIN` أعمدة الجانب الأيسر فقط.
  * يُتيح `RIGHT SEMI JOIN` و`RIGHT ANTI JOIN` أعمدة الجانب الأيمن فقط.
  * يؤثر ذلك في عبارات مثل `SELECT` و`PREWHERE` و`WHERE` و`GROUP BY` و`HAVING` و`QUALIFY` و`ORDER BY` و`LIMIT BY`، بما في ذلك محارف البدل المؤهَّلة مثل `t1.*`.
  * يظل بإمكان تعبير `ON` الخاص بـ `JOIN` نفسه الإشارة إلى كلا الجانبين.

  عند تمكين هذه الإعدادات (وهو الوضع الافتراضي)، يحافظ ClickHouse على السلوك القديم، إذ يظل كلا الجانبين متاحَين ويُوسِّع `SELECT *` الأعمدة من كلا الجدولين.
</Note>

لا تدعم كل خوارزميات الربط جميع تركيبات نوع الربط والصرامة. وتُسرد التركيبات المدعومة في [أنواع الربط المدعومة لكل خوارزمية](/ar/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).

### إعادة كتابة `CROSS JOIN` على هيئة `INNER JOIN` {#cross-join-rewrite}

عندما تحتوي عبارة `WHERE` في استعلام يستخدم `CROSS JOIN` أو قائمة جداول مفصولة بفواصل على شروط مساواة بين الجداول، يستطيع ClickHouse إعادة كتابة عملية JOIN على هيئة `INNER JOIN` تستخدم هذه الشروط مفاتيحَ ربط. ويتحكم الإعداد [`cross_to_inner_join_rewrite`](/ar/reference/settings/session-settings/other#cross_to_inner_join_rewrite) في إعادة الكتابة هذه:

* `0`: إعادة الكتابة معطّلة.
* `1`: تُعاد كتابة قائمة الجداول المفصولة بفواصل أو `CROSS JOIN` عندما تحتوي عبارة `WHERE` على شرط مساواة بين الجداول، وإلا فتُنفَّذ عملية JOIN على هيئة `CROSS JOIN`.
* `2`: مثل `1`، غير أن قائمة الجداول المفصولة بفواصل التي يتعذّر إعادة كتابتها تؤدي إلى فشل الاستعلام مع الخطأ `INCORRECT_QUERY` إذا كان الاستعلام يحتوي على عبارة `WHERE`. أما عملية JOIN المكتوبة باستخدام الرمزين `CROSS JOIN` والتي يتعذّر إعادة كتابتها، فتُنفَّذ على هيئة `CROSS JOIN`.

وحتى مع القيمة `0`، يظل بإمكان تحسين خطة تنفيذ الاستعلام الذي يتحكم فيه الإعداد [`query_plan_merge_filter_into_join_condition`](/ar/reference/settings/session-settings/query-plan#query_plan_merge_filter_into_join_condition) دمجُ عامل تصفية المساواة في عملية JOIN وتنفيذها على هيئة `INNER JOIN`.

## شروط قسم `ON` {#on-section-conditions}

يمكن أن يحتوي قسم `ON` على عدة شروط مدمجة باستخدام المعاملين `AND` و`OR`. ويجب أن تستوفي الشروط التي تحدد مفاتيح الربط ما يلي:

* أن تشير إلى كلٍّ من الجدول الأيسر والجدول الأيمن
* أن تستخدم معامل المساواة

أما الشروط الأخرى، فيمكنها استخدام معاملات أخرى، ويمكنها أن تشير إلى الجدول الأيسر أو الجدول الأيمن في الاستعلام، أو إلى كليهما.

تُربط الصفوف إذا تحقق الشرط المركب بالكامل. وإذا لم تتحقق الشروط، فقد تظل الصفوف مُضمَّنة في النتيجة بحسب نوع الربط. وإذا وُضعت الشروط نفسها في قسم `WHERE` ولم تتحقق، فستُستبعد الصفوف دائمًا من النتيجة.

لا تدعم مفاتيحَ الربط المدمجة باستخدام `OR` سوى خوارزمية [`hash`](/ar/concepts/features/operations/select/join-algorithms#hash)، التي تُنشئ جدول تجزئة منفصلًا لكل وسيطة `OR` تحتوي على مفاتيح ربط.

<Note>
  معامل المساواة (`=`) وحده هو ما يجعل الشرط مفتاح ربط. والمعاملات الأخرى بين أعمدة من جداول مختلفة مدعومة، لكن في غياب أي شرط مساواة يتعيّن على عملية الربط فحص كل زوج من الصفوف؛ راجع [ربط مع شرط ON عشوائي](#join-with-an-arbitrary-on-condition).
</Note>

**مثال**

لننظر إلى `table_1` و`table_2`:

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

استعلام يتضمن شرطًا واحدًا لمفتاح الربط وشرطًا إضافيًا لـ `table_2`:

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

تتضمن النتيجة الصف الذي يحمل الاسم `C` وعمود النص الفارغ. وقد أُدرجت في النتيجة لأن نوع `OUTER` من `join` مستخدم هنا.

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

استعلام باستخدام عملية ربط من النوع `INNER` وبشروط متعددة:

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```response title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴────────┴────────┘
```

استعلام مع `join` من النوع `INNER` وشرط يستخدم `OR`:

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

استعلام بنوع الربط `INNER` وبشروط تتضمن `OR` و`AND`:

<Note>
  يُطبَّق شرط عدم المساواة الذي يستخدم أعمدة من جدول واحد، مثل `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c`، على ذلك الجدول وحده: إذ يستخدم `t1.b > 0` أعمدة من `t1` فقط، و`t2.b > t2.c` يستخدم أعمدة من `t2` فقط.
  كما أن شروط عدم المساواة التي تقارن أعمدة من جداول مختلفة، مثل `t1.a = t2.key AND t1.b > t2.key`، مدعومة كذلك؛ راجع الأقسام أدناه.
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## JOIN مع شروط عدم المساواة للأعمدة من جداول مختلفة {#join-with-inequality-conditions-for-columns-from-different-tables}

بالإضافة إلى شروط المساواة، يمكن أن يحتوي قسم `ON` على شروط تقارن أعمدة من جداول مختلفة باستخدام مُعامِلات أخرى. وهذه الشروط مدعومة مع صرامة `ALL` و`ANY` و`SEMI` و`ANTI` لكل نوع ربط تسمح به هذه الصرامة، لكنها غير مدعومة مع صرامة `ASOF`.

عندما يحتوي قسم `ON` على شرط مساواة بين الجدولين إلى جانب شرط عدم المساواة، يكون شرط المساواة هو مفتاح الربط، ويُتحقَّق من شرط عدم المساواة على الصفوف التي طابقها. ويُنفَّذ هذا الشرط المختلط بواسطة الخوارزميات [`hash`](/ar/concepts/features/operations/select/join-algorithms#hash) و[`parallel_hash`](/ar/concepts/features/operations/select/join-algorithms#parallel-hash) و[`grace_hash`](/ar/concepts/features/operations/select/join-algorithms#grace-hash). وعندما تُدرَج [`inequality`](/ar/concepts/features/operations/select/join-algorithms#inequality) قبل هذه الخوارزميات في [`join_algorithm`](/ar/reference/settings/session-settings/join#join_algorithm) ويحتوي قسم `ON` على شرطَي عدم مساواة، تتولى `inequality` تنفيذ الربط بدلًا منها وتطبّق شرط المساواة بوصفه عامل تصفية.

عندما لا يحتوي قسم `ON` على أي شرط مساواة بين الجدولين، فلا يوجد مفتاح ربط تُجرى المطابقة على أساسه. ويُنفَّذ هذا الربط بواسطة [`inequality`](/ar/concepts/features/operations/select/join-algorithms#inequality) عندما يكون الشرط زوجًا من شروط عدم المساواة، وإلا فيُنفَّذ بوصفه [ربطًا بحلقات متداخلة على مستوى الكتل](#join-with-an-arbitrary-on-condition).

لا يجوز أن يحتوي الشرط الذي يُقيَّم أثناء الربط على `arrayJoin`، إذ يجب أن يحافظ على عدد الصفوف؛ استخدم بدلًا من ذلك `ARRAY JOIN` في استعلام فرعي.

**مثال**

الجدول `t1`:

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

الجدول `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response
key1    a    1    1    2    key1    B    2    1    2
key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
key1    e    5    5    5            0    0    \N
key2    a2    1    1    1            0    0    \N
key4    f    2    3    4            0    0    \N
```

## JOIN مع شرط ON عشوائي {#join-with-an-arbitrary-on-condition}

يمكن أن يكون قسم `ON` أي تعبير منطقي على أعمدة الجدولين، مثل التحقق من نطاق، أو مقارنة حسابية، أو استدعاء دالة مفردة. وإذا لم يتضمن أي مساواة بين الجدولين، فلن يوجد مفتاح ربط تُطابَق الصفوف على أساسه. ويُنفَّذ زوج من شروط عدم المساواة باستخدام `inequality` متى كانت هذه الخوارزمية مدرجة في [`join_algorithm`](/ar/reference/settings/session-settings/join#join_algorithm)، دون اشتراط أن تأتي في المقدمة، إذ لا توجد قيمة أخرى من قيم `join_algorithm` قادرة على تنفيذ مثل هذا الشرط. وتتضمن القيمة الافتراضية لـ `join_algorithm` الخوارزمية `inequality` بدءًا من الإصدار 26.8. أما أي شرط آخر فيُنفَّذ بوصفه [ربطًا بحلقات متداخلة على مستوى الكتل](https://en.wikipedia.org/wiki/Nested_loop_join)، إذ يُجسَّد الجدول الأيمن ثم يُقيَّم الشرط على كل زوج من الصفوف. ويأخذ `ALL INNER JOIN` في هذه الحالة صيغة مكافئة لـ `CROSS JOIN` يُستخدم فيها الشرط عاملَ تصفية.

يدعم الربط بحلقات متداخلة على مستوى الكتل جميع أنواع الربط ومستويات الصرامة باستثناء `ASOF JOIN` و`PASTE JOIN` و`ANY FULL JOIN`. وهو ليس من قيم `join_algorithm`، بل هو الملاذ الأخير الذي لا يُلجأ إليه إلا عندما تعجز الخوارزميات الأخرى عن تنفيذ الشرط. ويظهر في إخراج `EXPLAIN` على هيئة خطوة `BlockNestedLoopJoin`. وعند تعطيل [`allow_block_nested_loop_join`](/ar/reference/settings/session-settings/allow#allow_block_nested_loop_join)، يُرفض أي استعلام يتطلبه ويُعاد الخطأ `INVALID_JOIN_ON_EXPRESSION`.

**مثال**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

يُكمَّل الصف الذي لم يطابق أي شيء وفقًا للإعداد [`join_use_nulls`](/ar/reference/settings/session-settings/join#join_use_nulls)، كما هو الحال في أي ربط JOIN آخر: بقيمة افتراضية كما في المثال أعلاه، وبـ `NULL` عند تفعيل هذا الإعداد.

**الصرامة**

يحتفظ `ANY` و`SEMI` عادةً بصف واحد لكل مجموعة من الصفوف التي تشترك في مفتاح الربط نفسه. ولمّا كانت هذه المجموعة غير موجودة هنا، فإنهما يحتفظان بصف واحد لكل صف من الجدول الذي يقود الربط: يُخرج `LEFT ANY` و`LEFT SEMI` كل صف أيسر مرة واحدة على الأكثر، ويُخرج `RIGHT ANY` و`RIGHT SEMI` كل صف أيمن مرة واحدة على الأكثر. أما `ANY INNER` فيقيّد الجانبين معًا: إذ يُستخدم كل صف من كلا الجدولين مرة واحدة على الأكثر، فلا يتجاوز عدد صفوف النتيجة عدد صفوف الجدول الأصغر. ويكون اختيار الأزواج التي تُكوّن هذه النتيجة اعتباطيًا، تمامًا كما يقتضي `ANY`، وقد يختلف بين تشغيلين للاستعلام نفسه. وفي حالة `ANY INNER` يمتد ذلك ليشمل عدد الصفوف أيضًا: فإقران صفوف الجانبين بطريقة جشعة، بأي ترتيب تُفحص به الصفوف، قد يترك عددًا مختلفًا من الصفوف دون إقران، ولذلك فإن نتيجة `count()` على ربط `ANY INNER` بلا مفتاح ربط غير قابلة للتكرار، وتتوقف على عدد خيوط التنفيذ وعلى الترتيب الفعلي لصفوف الجدول الأيمن.

**الأداء**

يفحص الربط بالحلقات المتداخلة على مستوى الكتل كل زوج من الصفوف، لذا تتزايد تكلفته بحسب حاصل ضرب عددَي صفوف الجدولين، كما هو موضح في [الآلية الاحتياطية للربط بالحلقات المتداخلة على مستوى الكتل](/ar/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback). ويخضع الجدول الأيمن المُجسَّد للحدود الصارمة وعتبات الكتابة إلى القرص الموضحة في [إدارة الذاكرة والكتابة إلى القرص في JOIN](/ar/concepts/features/operations/select/join-memory-management).

## قيم `NULL` و`NaN` في مفاتيح الربط {#null-values-in-join-keys}

لا تساوي `NULL` أي قيمة، بما في ذلك نفسها. إذا كانت قيمة مفتاح الربط هي `NULL` في أحد الجدولين، فلن تطابق قيمة `NULL` في الجدول الآخر. وإذا كانت مفاتيح الربط أعمدة من النوع [Nullable](/ar/reference/data-types/nullable)، فلن يُربط أي صف يحتوي على قيمة [NULL](/ar/reference/syntax#null) في مفتاح واحد على الأقل من مفاتيحه.

**مثال**

الجدول `A`:

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

الجدول `B`:

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

لا يتطابق الصف الذي يحتوي على `Charlie` من الجدول `A`، والصف الذي درجته 88 من الجدول `B`، بسبب القيمة `NULL` في مفتاح الربط.

تحصل الصفوف التي ليس لها تطابق على القيمة `0` في العمود `score`، كما هو موضح في [معالجة الخلايا الفارغة أو التي تحتوي على NULL](#processing-of-empty-or-null-cells).

لمطابقة قيم `NULL`، قارن مفاتيح الربط باستخدام الدالة `isNotDistinctFrom`:

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

لا تتبع قيم `NaN` في مفاتيح الربط من نوع float قاعدة `NULL` المذكورة أعلاه.
تكون المقارنة المفردة بين قيمتي `NaN` (`NaN = NaN`) هي `0`. لكن لا تُقارن مفاتيح الربط وفق دلالات المقارنة المفردة، وقد تتطابق مفاتيح `NaN`.
أما ما إذا كانت تتطابق فعلًا فغير محدد، إذ يعتمد على خوارزمية الربط ونوع المفتاح وإعدادات الجلسة.
لاستبعاد مفاتيح `NaN` من المطابقة، حوّلها إلى قيم `NULL`، على سبيل المثال: `ON if(isNaN(A.id), NULL, A.id) = B.id`.
في `ASOF JOIN`، يُقارن العمود الخاص بأقرب تطابق وفق الترتيب، وهو ترتيب غير معرّف لقيم `NaN`.

## تحويل النوع الضمني {#implicit-type-conversion}

عندما تختلف أنواع مفاتيح الربط في الجدولين الأيسر والأيمن، يحوّلها ClickHouse إلى النوع الفوقي المشترك الأدنى لها قبل مقارنتها. ينطبق ذلك على كل أنواع الربط وكل مستويات الصرامة:

* مع `ON`، يقتصر التحويل على المقارنة، وتحتفظ أعمدة المفتاح بأنواعها الأصلية في النتيجة.
* مع `USING`، يأخذ العمود المدمج النوع المشترك في النتيجة. وعندما يكون `semi_join_include_columns_from_both_sides` أو `anti_join_include_columns_from_both_sides` معطّلًا، يحتفظ العمود المدمج في `SEMI JOIN` أو `ANTI JOIN` بنوعه في الجدول المحتفَظ بصفوفه.

إذا لم يكن لنوعَي المفتاحين نوع أعلى مشترك، وكان كلاهما من أنواع الأعداد الصحيحة أو صفوفًا مرتبة من أنواع الأعداد الصحيحة، كما هو الحال مع `UInt64` و`Int64`، يحوّل ClickHouse كلا المفتاحين إلى نوع يستوعب القيم المشتركة بين نوعَي المفتاحين. وفي حالة `UInt64` و`Int64`، يكون هذا النوع هو `UInt64`. أما قيمة المفتاح التي لا يستطيع هذا النوع تمثيلها، فلا تتطابق مع أي قيمة. يُستخدم هذا التحويل في شروط المساواة ضمن `ON`، باستثناء `isNotDistinctFrom`، وفي `USING` ضمن `INNER JOIN` أو `SEMI JOIN`. ولا يُستخدم في شرط أقرب تطابق في `ASOF JOIN`، ولا في شروط عدم المساواة التي ينفّذها `inequality`، ولا في `USING` ضمن عمليات الربط الأخرى، لأن عمود النتيجة فيها يجب أن يستوعب أيضًا القيم التي ليس لها تطابق. يتوفر هذا التحويل بدءًا من الإصدار 26.9.

إذا لم يكن لنوعَي المفتاحين نوع أعلى مشترك ولم ينطبق هذا التحويل، كما هو الحال مع `String` و`Int32` أو مع `UInt64` و`Float64`، يفشل الاستعلام ويُطلق استثناءً، مثل `NO_COMMON_TYPE`.

**مثال**

لنأخذ الجدول `t_1`:

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

والجدول `t_2`:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

الاستعلام

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b) ORDER BY ALL;
```

يُعيد المجموعة:

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## استخدام ASOF JOIN {#asof-join-usage}

يربط `ASOF JOIN` السجلات التي لا يوجد بينها تطابق تام. و`ASOF` هي صرامة JOIN تُستخدم مع JOIN من النوع `INNER` أو `LEFT`، وليست خوارزمية ربط.

يتطلب `ASOF JOIN` عمودًا لأقرب تطابق في كلا الجدولين. ويجب أن يكون هذا العمود:

* من نوع له ترتيب محدد.
* عند استخدام خوارزمية [`hash`](/ar/concepts/features/operations/select/join-algorithms#hash)، من أحد الأنواع التالية: [Int, UInt](/ar/reference/data-types/int-uint)، [Float](/ar/reference/data-types/float)، [Decimal](/ar/reference/data-types/decimal)، [Date](/ar/reference/data-types/date)، [Date32](/ar/reference/data-types/date32)، [DateTime](/ar/reference/data-types/datetime)، [DateTime64](/ar/reference/data-types/datetime64)، [Time](/ar/reference/data-types/time)، [Enum](/ar/reference/data-types/enum)، [Bool](/ar/reference/data-types/boolean)، و[Nullable](/ar/reference/data-types/nullable) من هذه الأنواع. أما الأنواع الأخرى، مثل `String` و`Time64`، فتُرفض مع الخطأ `BAD_TYPE_OF_FIELD`.
* عند استخدام خوارزمية [`full_sorting_merge`](/ar/concepts/features/operations/select/join-algorithms#full-sorting-merge)، يمكن أن يكون أيضًا من أنواع أخرى قابلة للمقارنة، مثل `String`.
* عند استخدام خوارزمية `hash`، لا يمكن أن يكون العمود الوحيد في عبارة `JOIN`، إذ يلزم وجود شرط مساواة واحد على الأقل. ولا تفرض خوارزمية `full_sorting_merge` هذا الشرط.

الصيغة `ASOF JOIN ... ON`:

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

يمكنك استخدام أي عدد من شروط المساواة، وشرطًا واحدًا فقط لأقرب تطابق. على سبيل المثال، `SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t`.

الشروط المدعومة لأقرب تطابق: `>`, `>=`, `<`, `<=`.

الصيغة `ASOF JOIN ... USING`:

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

يستخدم `ASOF JOIN` ‏`equi_columnX` للربط وفقًا للمساواة، و`asof_column` للربط بأقرب تطابق مع الشرط `table_1.asof_column >= table_2.asof_column`. ويكون العمود `asof_column` دائمًا هو الأخير في عبارة `USING`.

على سبيل المثال، تأمل الجداول التالية:

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

يمكن لـ `ASOF JOIN` أخذ الطابع الزمني لحدث مستخدم من `table_1` والعثور على حدث في `table_2` يكون طابعه الزمني الأقرب إلى الطابع الزمني لحدث `table_1` وفقًا لشرط أقرب تطابق. وتُعد قيم الطابع الزمني المتساوية هي الأقرب إذا كانت متاحة. هنا، يمكن استخدام العمود `user_id` للربط على أساس المساواة، ويمكن استخدام العمود `ev_time` للربط على أساس أقرب تطابق. في مثالنا، يمكن ربط `event_1_1` مع `event_2_1`، ويمكن ربط `event_1_2` مع `event_2_3`، لكن لا يمكن ربط `event_2_2`.

<Note>
  من بين خوارزميات الربط، لا تدعم صرامة `ASOF` سوى الخوارزميتين [`hash`](/ar/concepts/features/operations/select/join-algorithms#hash) و[`full_sorting_merge`](/ar/concepts/features/operations/select/join-algorithms#full-sorting-merge). راجع [أنواع JOIN المدعومة لكل خوارزمية](/ar/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).
  و`ASOF` **غير** مدعومة في محرك الجدول [Join](/ar/reference/engines/table-engines/special/join).
</Note>

## استخدام PASTE JOIN {#paste-join-usage}

نتيجة `PASTE JOIN` هي جدول يحتوي على جميع الأعمدة من الاستعلام الفرعي الأيسر، ثم جميع الأعمدة من الاستعلام الفرعي الأيمن.
تُطابَق الصفوف بناءً على مواضعها في الجداول الأصلية (يجب أن يكون ترتيب الصفوف محددًا).
إذا أعادت الاستعلامات الفرعية أعدادًا مختلفة من الصفوف، فستُقتطع الصفوف الزائدة.

مثال:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

ملاحظة: في هذه الحالة، قد تكون النتيجة غير حتمية إذا جرت القراءة بالتوازي. على سبيل المثال:

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## LATERAL JOIN {#lateral-join}

يتيح `JOIN LATERAL` للاستعلام الفرعي الواقع على الجانب الأيمن من عملية الربط الإشارةَ إلى أعمدة تعبيرات الجدول
الواقعة على جانبه الأيسر. وتكون النتيجة كما لو أن الاستعلام الفرعي يُقيَّم لكل تركيبة مميزة
من قيم الأعمدة في الجانب الأيسر التي يشير إليها، ثم تُربط نتيجته بكل صف في الجانب الأيسر يحمل تلك التركيبة:

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

المسند `ON true` إلزامي، كما هو الحال في أي `INNER` أو `LEFT JOIN` آخر؛ وحذفه يُعد خطأً في الصيغة.

هذه الميزة متاحة منذ الإصدار 26.10. وهي تجريبية ومعطّلة افتراضيًا؛ ويمكن تمكينها باستخدام الإعداد
[`enable_lateral_join`](/ar/reference/settings/session-settings/enable#enable_lateral_join).

لا يُنفَّذ الاستعلام الفرعي الجانبي مرة واحدة لكل صف من الجانب الأيسر، ولا مرة واحدة لكل تركيبة مميزة. بل يُفكّ ترابطه، كغيره من الاستعلامات الفرعية
المترابطة، إلى استعلام واحد يشمل جميع صفوف الجانب الأيسر: إذ تُضاف أعمدة الجانب الأيسر التي يشير إليها
إلى مفاتيح `GROUP BY` الخاصة به إذا كان يُجري تجميعًا، ويتحول `LIMIT` الخاص به (إن وُجد) إلى `LIMIT ... BY` على هذه الأعمدة، ثم
تُربط نتيجته بصفوف الجانب الأيسر بناءً عليها. وعندما يكون الترابط مساواة بسيطة، مثل `orders.user_id = u.id`،
يمكن استبدال عمود الجانب الأيسر بالعمود المساوي له في الاستعلام الفرعي
(`correlated_subqueries_substitute_equivalent_expressions`، مفعّل افتراضيًا)، مما قد يتيح للاستعلام الفرعي تجنّب
قراءة صفوف الجانب الأيسر. غير أن ذلك ليس مضمونًا: فعلى سبيل المثال، يظل التجميع دون `GROUP BY` (مثل `count`)
يقرأ القيم المميزة للجانب الأيسر كي يُنتج نتيجته لقيم الجانب الأيسر التي لا تقابلها صفوف مطابقة. وكلما مُرِّرت القيم
المميزة للجانب الأيسر إلى الاستعلام الفرعي، فإن ذلك يتم مع الإعدادات الافتراضية عبر مخزن مؤقت في الذاكرة، ولا يكون الربط
دائمًا ربطًا بالتجزئة إلا عند استخدام هذا المخزن المؤقت فعليًا. أما في جميع الحالات الأخرى، كأن يتيح استبدال المساواة
تجنّب قراءة صفوف الجانب الأيسر أو يكون المخزن المؤقت معطّلًا
(`correlated_subqueries_use_in_memory_buffer = 0` أو `correlated_subqueries_default_join_kind = 'left'`)، فتُحدَّد
الخوارزمية بواسطة الإعداد `join_algorithm`. فعلى سبيل المثال، يُظهر `EXPLAIN` لاستعلام فرعي جانبي يحتوي على `LIMIT`
خطوة `Join` فوق خطوة `LimitBy (LIMIT BY for decorrelated correlated subquery)`؛ أما الاستعلام الفرعي الذي لا يحتوي على
`LIMIT` فلا يتضمن هذه الخطوة.

لا تُدعم حتى الآن سوى المجموعة الجزئية التالية؛ وأي شيء آخر يُرفض مع إصدار خطأ:

* `INNER JOIN LATERAL` و`LEFT JOIN LATERAL` فقط؛ ولا تُدعم عمليات الربط من نوع `RIGHT` و`FULL` و`PASTE` و`NATURAL`، ولا يمكن إطلاقًا الجمع بين `LATERAL` وربط `CROSS` أو الربط بالفاصلة.
* الصرامة الافتراضية `ALL` فقط؛ ولا تُدعم `ANY` و`SEMI` و`ANTI` و`ASOF`.
* لا يُسمح بأي مسند ربط غير `ON true` (يُقبل `ON 1` أيضًا)؛ ولا يُدعم `USING`، ولا يمكن
  حذف المسند. ضع شروط التصفية التي تربط بين الطرفين في عبارة `WHERE` الخاصة بالاستعلام الفرعي الجانبي.
* لا تُدعم مُعدِّلات الربط `GLOBAL` و`LOCAL`.
* يجب أن يشير الاستعلام الفرعي الجانبي إلى عمود واحد على الأقل من الطرف الأيسر. أما الاستعلام الفرعي غير المترابط
  فاستخدم معه ربطًا عاديًا.
* نظرًا لأن الاستعلام الفرعي الجانبي يُفكّ ترابطه بدلًا من تقييمه بشكل منفصل لكل قيمة من الطرف الأيسر، فإنه
  يجب ألا يحتوي على دوال غير حتمية ضمن الاستعلام، مثل
  `rand` أو `generateUUIDv4`، ولا على دالات جداول تولّد صفوفًا عشوائية، مثل `generateRandom`.
  أما الدوال الثابتة ضمن الاستعلام، مثل `now`، فمسموح بها.
* لا يُدعم بوصفه تعبير الجدول الجانبي إلا الاستعلام الفرعي. ولا تُدعم صيغ مصادر الجداول المستخدمة في PostgreSQL
  مثل `LATERAL unnest(...)` و`CROSS JOIN UNNEST(...)`. استخدم بدلًا منها
  عبارة [`ARRAY JOIN`](/ar/reference/statements/select/array-join).
* يُنفَّذ `GROUP BY` و`ORDER BY` الخاصان بالاستعلام الفرعي الجانبي مرة واحدة لجميع قيم الطرف الأيسر مجتمعةً، لذا فإن
  الحدود `max_rows_to_group_by` و`max_rows_to_sort` و`max_bytes_to_sort` تحتسب الصفوف لجميع قيم الطرف الأيسر،
  لا لقيمة واحدة فقط. ولا تُدعم هذه الحدود إلا مع وضع التجاوز `throw`؛ أما `any` و`break` فيُرفضان.
* تُطابَق نتيجة الاستعلام الفرعي المفكوك الترابط مع صفوف الطرف الأيسر عبر عملية ربط واحدة. وكما في أي ربط بالتجزئة،
  يقيّد `max_rows_in_join` و`max_bytes_in_join` الطرفَ الذي يُحتفظ به في الذاكرة من هذا الربط، ويتولى
  المخطِّط اختيار هذا الطرف: عندما يُستخدم المخزن المؤقت في الذاكرة الموصوف أعلاه فعليًا، يكون هذا الطرف هو الطرف الأيسر
  من `JOIN LATERAL`، لأن صفوف الطرف الأيسر يجب أن تُقرأ كاملةً قبل تقييم الاستعلام الفرعي الجانبي؛ وإلا فقد يكون نتيجة الاستعلام الفرعي المفكوك الترابط. وتُطبَّق الحدود دائمًا
  كما لو كانت قيمة `join_overflow_mode` هي `throw`، إذ إن الربط مع `break` سيُسقط بصمت صفوفًا من الطرف الأيسر لا علاقة لها بالأمر.

**مثال**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS enable_lateral_join = 1;
```

## JOIN الموزّع {#distributed-join}

توجد طريقتان لتنفيذ `JOIN` يتضمن جداول موزعة:

* عند استخدام `JOIN` عادي، يُرسَل الاستعلام إلى الخوادم البعيدة. وتُشغَّل الاستعلامات الفرعية على كل خادم منها لتكوين الجدول الأيمن، ثم تُنفَّذ عملية الربط باستخدام هذا الجدول. وبعبارة أخرى، يُنشأ الجدول الأيمن على كل خادم على حدة.
* عند استخدام `GLOBAL ... JOIN`، يشغّل الخادم الذي أرسل الطلب أولًا استعلامًا فرعيًا لحساب أحد طرفَي الربط ويجمع النتيجة في جدول مؤقت. ثم يُمرَّر هذا الجدول المؤقت إلى كل خادم بعيد، وتُشغَّل الاستعلامات عليها باستخدام البيانات المؤقتة المنقولة. في عمليتَي الربط `LEFT` و`INNER`، يُحسَب الجدول الأيمن باعتباره الاستعلام الفرعي.

في حالة `GLOBAL RIGHT JOIN` بصرامة `ALL` أو `ANY` أو `SEMI` أو `ANTI` يكون فيها الجدول الأيسر جدول `Distributed` يضم أكثر من مقطع واحد، يبدّل ClickHouse الطرفين وينفّذ JOIN على أنه `LEFT JOIN`، كي تُعاد صفوف الجدول الأيمن المحتفَظ به مرة واحدة فقط. وعندئذٍ يُحسَب الجدول الأيسر باعتباره الاستعلام الفرعي، ويُقرأ الجدول الأيمن من مقاطعه إذا كان جدول `Distributed` يضم عدة مقاطع، وإلا فيُقرأ على الخادم الذي أرسل الطلب. أما `GLOBAL RIGHT JOIN` أو `GLOBAL FULL JOIN` الذي يتعذّر تبديل طرفيه على هذا النحو، فيُنفَّذ على الخادم الذي أرسل الطلب. ينطبق هذا السلوك بدءًا من الإصدار 26.9.

توخَّ الحذر عند استخدام `GLOBAL`. لمزيد من المعلومات، راجع قسم [الاستعلامات الفرعية الموزعة](/ar/reference/statements/in#distributed-subqueries).

## معالجة الخلايا الفارغة أو التي تحتوي على NULL {#processing-of-empty-or-null-cells}

في نتيجة عملية outer JOIN، تكون أعمدة الجدول الآخر فارغة في كل صف ليس له تطابق. ويحدد الإعداد [`join_use_nulls`](/ar/reference/settings/session-settings/join#join_use_nulls) كيفية ملء ClickHouse لهذه الخلايا:

* `0`: تُملأ الخلايا بالقيمة الافتراضية لنوع العمود.
* `1`: تُملأ الخلايا بالقيمة `NULL`، وتُحوَّل أنواع هذه الأعمدة إلى [Nullable](/ar/reference/data-types/nullable). أما العمود الذي لا يمكن تضمين نوعه داخل `Nullable`، مثل `Array`، فيحتفظ بنوعه ويُملأ بالقيمة الافتراضية. وفي عملية `FULL` JOIN، يُحوَّل عمود `USING` المدمج كذلك إلى `Nullable`.

لا يُربط أي صف يحتوي على قيمة `NULL` في مفتاح ربط واحد على الأقل، كما هو موضح في [قيم NULL وNaN في مفاتيح الربط](#null-values-in-join-keys).

## عبارة USING {#using-clause}

تحدد عبارة `USING` عمودًا واحدًا أو أكثر يُجرى الربط على أساسه، وتشترط المساواة بين هذه الأعمدة:

* يجب أن يوجد كل عمود بالاسم نفسه في كلٍّ من تعبير الجدول الأيسر وتعبير الجدول الأيمن. ويمكن استخدام الأسماء البديلة في الاستعلامات الفرعية لمنح الأعمدة الاسم نفسه.
* لا تقبل عبارة `USING` إلا أسماء الأعمدة، ولا تدعم التعبيرات.
* يمكن كتابة قائمة الأعمدة بين أقواس أو من دونها.
* يظهر كل عمود من أعمدة عبارة `USING` مرة واحدة في النتيجة. ويُحدَّد نوعه وفق ما هو موضح في [تحويل النوع الضمني](#implicit-type-conversion).
* يمكن أن تحمل أعمدة أخرى الاسم نفسه في كلا الجدولين. وفي هذه الحالة، يُسبق `SELECT *` اسم عمود الجدول الأيمن باسم الجدول أو اسمه البديل، ويُشير الاسم غير المسبوق ببادئة إلى عمود الجدول الأيسر عندما يكون الإعداد [`single_join_prefer_left_table`](/ar/reference/settings/session-settings/other#single_join_prefer_left_table) مفعّلًا.
* عندما يكون الإعداد [`analyzer_compatibility_join_using_top_level_identifier`](/ar/reference/settings/session-settings/analyzer-compatibility#analyzer_compatibility_join_using_top_level_identifier) مفعّلًا، يُستمد اسم العمود في `USING` من اسم بديل يحمل الاسم نفسه في الاستعلام، مثل اسم بديل في قائمة `SELECT`.

## أمثلة {#examples}

يربط الاستعلام التالي عدد سجلات hits لكل عداد بعدد سجلات visits لكل عداد. يُعيد `ANY LEFT JOIN` كل صف من الاستعلام الفرعي الأيسر مرة واحدة، أما العداد الذي لا تقابله أي سجلات visits فيأخذ القيمة الافتراضية `0`:

```sql title="Query"
SELECT
    CounterID,
    hits,
    visits
FROM
(
    SELECT
        CounterID,
        count() AS hits
    FROM VALUES('CounterID UInt32', 1, 1, 1, 2, 2, 3)
    GROUP BY CounterID
) AS h
ANY LEFT JOIN
(
    SELECT
        CounterID,
        sum(Sign) AS visits
    FROM VALUES('CounterID UInt32, Sign Int8', (1, 1), (1, 1), (1, -1), (2, 1), (4, 1))
    GROUP BY CounterID
) AS v USING (CounterID)
ORDER BY hits DESC;
```

```response title="Response"
┌─CounterID─┬─hits─┬─visits─┐
│         1 │    3 │      1 │
│         2 │    2 │      1 │
│         3 │    1 │      0 │
└───────────┴──────┴────────┘
```
