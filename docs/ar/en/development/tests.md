<div id="functional-tests">
  ## الاختبارات الوظيفية
</div>

تُعد الاختبارات الوظيفية الأبسط والأسهل استخدامًا.
يمكن اختبار معظم ميزات ClickHouse باستخدام الاختبارات الوظيفية، ويُعد استخدامها إلزاميًا لكل تغيير في شيفرة ClickHouse يمكن اختباره بهذه الطريقة.

يرسل كل اختبار وظيفي استعلامًا واحدًا أو عدة استعلامات إلى خادم ClickHouse قيد التشغيل، ثم يقارن النتيجة بالنتيجة المرجعية.

توجد الاختبارات في الدليل `./tests/queries`.

يمكن أن يكون كل اختبار من أحد نوعين: `.sql` و `.sh`.

* اختبار `.sql` هو برنامج SQL نصي بسيط يُمرَّر إلى `clickhouse-client`.
* اختبار `.sh` هو برنامج نصي يُشغَّل مباشرةً.

تُفضَّل اختبارات SQL عمومًا على اختبارات `.sh`.
يجب ألا تستخدم اختبارات `.sh` إلا عندما تضطر إلى اختبار ميزة لا يمكن التحقق منها باستخدام SQL فقط، مثل تمرير بعض بيانات الإدخال إلى `clickhouse-client` أو اختبار `clickhouse-local`.

:::note
من الأخطاء الشائعة عند اختبار أنواع البيانات `DateTime` و `DateTime64` افتراض أن الخادم يستخدم منطقة زمنية محددة (مثل &quot;UTC&quot;). وهذا غير صحيح، إذ تُختار المناطق الزمنية عشوائيًا عمدًا في تشغيلات اختبارات CI.
وأسهل حل بديل هو تحديد المنطقة الزمنية لقيم الاختبار صراحةً، مثل `toDateTime64(val, 3, 'Europe/Amsterdam')`.
:::

<div id="running-a-test-locally">
  ### تشغيل اختبار محليًا
</div>

شغّل خادم ClickHouse محليًا بحيث يستمع على المنفذ الافتراضي (9000).
ولتشغيل الاختبار `01428_hash_set_nan_key`، على سبيل المثال، انتقل إلى مجلد المستودع ونفّذ الأمر التالي:

```sh
PATH=<path to clickhouse-client>:$PATH tests/clickhouse-test 01428_hash_set_nan_key
```

تُكتب نتائج الاختبار (`stderr` و`stdout`) في الملفين `01428_hash_set_nan_key.[stderr|stdout]` الموجودين بجوار الاختبار نفسه (بالنسبة إلى `queries/0_stateless/foo.sql`، سيكون الناتج في `queries/0_stateless/foo.stdout`).

راجع `tests/clickhouse-test --help` للاطلاع على جميع خيارات `clickhouse-test`.
يمكنك تشغيل جميع الاختبارات أو تشغيل مجموعة فرعية منها بتوفير عامل تصفية لأسماء الاختبارات: `./clickhouse-test substring`.
توجد أيضًا خيارات لتشغيل الاختبارات بالتوازي أو بترتيب عشوائي.

<div id="running-tests-on-macos">
  #### تشغيل الاختبارات على macOS ‏(Darwin)
</div>

يعتمد كثير من الاختبارات الوظيفية على استدعاء أدوات GNU لسطر الأوامر (`timeout`, `head`, `sed`, `grep`, `date`، وغيرها). يأتي macOS بإصدارات BSD من هذه الأدوات، لكن سلوكها وخياراتها تختلف (فعلى سبيل المثال، يرفض BSD `head` الأمر `head -c 1G`، ويفتقر BSD `ps` إلى الخيارات الطويلة `--`، ولا تتوفر أداة `timeout` أصلًا). ويؤدي تشغيل الاختبارات باستخدام أدوات BSD إلى حالات فشل زائفة.

تثبّت مشغلات CI على macOS أدوات GNU عبر Homebrew وتضعها قبل أدوات BSD في `PATH`. وأعد تطبيق الإعداد نفسه محليًا:

```sh
brew install coreutils gnu-sed grep
export PATH="$(brew --prefix)/opt/coreutils/libexec/gnubin:$(brew --prefix)/opt/gnu-sed/libexec/gnubin:$(brew --prefix)/opt/grep/libexec/gnubin:$PATH"
```

يوفّر `coreutils` أدوات GNU مثل `timeout` و`head` و`date` وغيرها؛ كما يوفّر `gnu-sed` و`grep` أداتي GNU `sed` و`grep`. بعد ذلك، ينبغي أن يشير `which timeout head sed grep` إلى مسارات `gnubin`.

<div id="running-fast-tests">
  ### تشغيل اختبارات اختبار سريع
</div>

قد تحتاج إلى جهاز بمواصفات جيدة نسبيًا لتشغيل مجموعة فرعية من الاختبارات (تُسمّى &quot;اختبار سريع&quot;). تعمل الخطوات التالية على مثيل AWS من نوع `t3.2xlarge` يعمل بمعمارية amd64 ونظام Ubuntu، مع سعة تخزين تبلغ 100 GB.

1. ثبّت المتطلبات الأساسية ثم سجّل الدخول مرة أخرى.

```sh
sudo apt-get update
sudo apt-get install docker.io
sudo usermod -aG docker "$USER"
```

2. احصل على الشيفرة المصدرية.

```sh
git clone --single-branch https://github.com/ClickHouse/ClickHouse
cd ClickHouse
```

3. قم ببناء الشيفرة وشغّل &quot;الاختبارات السريعة&quot;.

```sh
python -m ci.praktika run fast
```

يُفترض أن تكون النتيجة

```sh
Failed: 0, Passed: 7394, Skipped: 1795
```

إذا تركت العملية تعمل دون متابعة، فيمكنك استخدام `nohup` أو `disown` للإبقاء عليها قيد التشغيل بعد انقطاع اتصال `ssh`.

<div id="running-stateless-tests">
  ### تشغيل الاختبارات عديمة الحالة
</div>

قد تحتاج إلى جهاز بإمكانات جيدة إلى حدّ ما لتشغيل الاختبارات عديمة الحالة. تنجح الخطوات التالية على مثيل `m7i.8xlarge` من AWS بمعمارية amd64 ونظام Ubuntu مع مساحة تخزين قدرها 200 GB.

1. ثبّت المتطلبات الأساسية ثم سجّل الدخول مجددًا.

```sh
sudo apt-get update
sudo apt-get install docker.io
sudo usermod -aG docker "$USER"
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "ipv6": true,
  "ip6tables": true
}
EOF
sudo systemctl restart docker
```

2. اجلب الشيفرة المصدرية.

```sh
git clone --single-branch https://github.com/ClickHouse/ClickHouse
cd ClickHouse
```

3. شغّل عملية بناء الشيفرة.

```sh
python -m ci.praktika run build_debug
cp ci/tmp/build/programs/clickhouse ci/tmp
```

4. شغّل الاختبارات عديمة الحالة، إذ يمكن تشغيلها بالتوازي.

```sh
python -m ci.praktika run functional
```

من المفترض أن تحصل على

```sh
Failed: 0, Passed: 8497, Skipped: 103
```

ملاحظة: تُشغِّل استدعاءات `python -m ci.praktika run` مهمةً محددة من مهام التكامل المستمر، ويمكنك قراءة المزيد عن ClickHouse CI [هنا](continuous-integration.md#running-stateless-tests).

<div id="adding-a-new-test">
  ### إضافة اختبار جديد
</div>

لإضافة اختبار جديد، أنشئ أولًا ملفًا بامتداد `.sql` أو `.sh` في الدليل `queries/0_stateless`.
ثم أنشئ ملف `.reference` المقابل باستخدام `clickhouse-client < 12345_test.sql > 12345_test.reference` أو `./12345_test.sh > ./12345_test.reference`.

يجب أن تقتصر الاختبارات على إنشاء الجداول أو حذفها أو الاستعلام منها، وما إلى ذلك، داخل قاعدة البيانات `test` التي تُنشأ تلقائيًا مسبقًا.
ولا بأس باستخدام الجداول المؤقتة.

لإعداد البيئة نفسها المستخدمة في CI على جهازك المحلي، ثبّت تكوينات الاختبار (إذ ستستخدم تنفيذًا وهميًا لـ ZooKeeper وتعدّل بعض الإعدادات)

```sh
cd <repository>/tests/config
sudo ./install.sh
```

:::note
ينبغي أن تكون الاختبارات

* في حدّها الأدنى: تُنشئ فقط الحد الأدنى اللازم من الجداول والأعمدة وبأقل قدر من التعقيد،
* سريعة: ألّا تستغرق أكثر من بضع ثوانٍ (والأفضل: أقل من ثانية)،
* صحيحة وحتمية: أن تفشل إذا، وفقط إذا، كانت الميزة قيد الاختبار لا تعمل،
* معزولة/عديمة الحالة: ألّا تعتمد على البيئة أو التوقيت،
* شاملة: أن تغطي الحالات الطرفية مثل الأصفار، وNULL، والمجموعات الفارغة، والاستثناءات (الاختبارات السلبية؛ استخدم الصياغة `-- { serverError xyz }` و `-- { clientError xyz }` لذلك)،
* أن تُنظّف الجداول في نهاية الاختبار (في حال وجود بقايا)،
* التأكد من أن الاختبارات الأخرى لا تختبر الشيء نفسه (أي استخدم grep أولًا).
  :::

<div id="templated-tests-with-jinja">
  ### اختبارات مُعلَّمة باستخدام Jinja
</div>

يمكن كتابة اختبار `.sql` على شكل قالب [Jinja2](https://jinja.palletsprojects.com/) بإضافة اللاحقة `.j2` إلى اسم الملف، بحيث يتحول `foo.sql` إلى `foo.sql.j2`. قبل تشغيل الاختبار، يعالج `clickhouse-test` هذا القالب ويحوّله إلى برنامج نصي عادي بامتداد `.sql` ثم ينفّذ الناتج.

يفيد ذلك عندما يكرّر الاختبار الاستعلام نفسه مع اختلافات بسيطة: إذ تُنشئ الحلقة الاستعلامات انطلاقًا من قالب موجز بدلًا من كتابة كل واحد منها يدويًا. وأكثر البُنى استخدامًا هي:

* `{% for ... %} ... {% endfor %}` لتكرار كتلة،
* `{{ expression }}` لإدراج قيمة في الناتج،
* `-%}` و `{%-` لحذف المسافات البيضاء المجاورة حتى يبقى البرنامج النصي الناتج نظيفًا.

على سبيل المثال، هذا القالب:

```sql
{% for type in ['UInt8', 'UInt16', 'UInt32'] -%}
SELECT toTypeName(0::{{ type }});
{% endfor -%}
```

يظهر بالشكل التالي:

```sql
SELECT toTypeName(0::UInt8);
SELECT toTypeName(0::UInt16);
SELECT toTypeName(0::UInt32);
```

يمكن توفير المخرجات المتوقعة إما كملف `<name>.reference` عادي يحتوي على النتائج الموسَّعة بالكامل، أو كقالب `<name>.reference.j2`، والذي يعالجه `clickhouse-test` بالطريقة نفسها قبل المقارنة. استخدم الصيغة المبنية على القالب إذا كانت المخرجات المتوقعة تتبع أيضًا نمطًا متكررًا. لمزيد من الأمثلة، راجع ملفات `*.sql.j2` الموجودة في `tests/queries/0_stateless/`.

<div id="restricting-test-runs">
  ### تقييد تشغيل الاختبارات
</div>

يمكن أن يحمل الاختبار صفرًا أو أكثر من *الوسوم* التي تحدد القيود على السياقات التي يُشغَّل فيها الاختبار في CI.

بالنسبة لاختبارات `.sql`، توضع الوسوم في السطر الأول على شكل تعليق SQL:

```sql
-- Tags: no-fasttest, no-replicated-database
-- no-fasttest: <provide_a_reason_for_the_tag_here>
-- no-replicated-database: <provide_a_reason_here>

SELECT 1
```

في اختبارات `.sh`، تُكتب الوسوم على شكل تعليق في السطر الثاني:

```bash
#!/usr/bin/env bash
# Tags: no-fasttest, no-replicated-database
# - no-fasttest: <provide_a_reason_for_the_tag_here>
# - no-replicated-database: <provide_a_reason_here>
```

قائمة الوسوم المتاحة:

| Tag name                       | What it does                                                                     | Usage example                                                                         |
| ------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `disabled`                     | لا يُشغَّل الاختبار                                                              |                                                                                       |
| `long`                         | يُمدَّد وقت تنفيذ الاختبار من دقيقة واحدة إلى 10 دقائق                           |                                                                                       |
| `deadlock`                     | يُشغَّل الاختبار في حلقة لمدة طويلة                                              |                                                                                       |
| `race`                         | مثل `deadlock`. يُفضَّل `deadlock`                                               |                                                                                       |
| `shard`                        | يجب أن يستمع الخادم على `127.0.0.*`                                              |                                                                                       |
| `distributed`                  | مثل `shard`. يُفضَّل `shard`                                                     |                                                                                       |
| `global`                       | مثل `shard`. يُفضَّل `shard`                                                     |                                                                                       |
| `zookeeper`                    | يتطلب الاختبار تشغيل Zookeeper أو ClickHouse Keeper                              | يستخدم الاختبار `ReplicatedMergeTree`                                                 |
| `replica`                      | مثل `zookeeper`. يُفضَّل `zookeeper`                                             |                                                                                       |
| `no-fasttest`                  | لا يُشغَّل الاختبار ضمن [اختبار سريع](#test-types)                               | يستخدم الاختبار محرك الجداول `MySQL` المعطَّل في اختبار سريع                          |
| `fasttest-only`                | لا يُشغَّل الاختبار إلا ضمن [اختبار سريع](#test-types)                           |                                                                                       |
| `no-[asan, tsan, msan, ubsan]` | يعطّل الاختبارات في build مع [sanitizers](#sanitizers)                           | يُشغَّل الاختبار تحت QEMU، وهو لا يعمل مع sanitizers                                  |
| `no-replicated-database`       | يعطّل الاختبار عندما تستخدم قاعدة البيانات الافتراضية `ReplicatedDatabaseEngine` |                                                                                       |
| `no-ordinary-database`         | يعطّل الاختبار عندما يكون محرك قاعدة البيانات الافتراضية هو `Ordinary`           |                                                                                       |
| `no-parallel`                  | يعطّل تشغيل اختبارات أخرى بالتوازي مع هذا الاختبار                               | يقرأ الاختبار من جداول `system` وقد تختل الثوابت                                      |
| `no-parallel-replicas`         | يعطّل الاختبار عند تمكين parallel replicas                                       |                                                                                       |
| `no-debug`                     | يعطّل الاختبارات في builds من نوع Debug                                          |                                                                                       |
| `no-release`                   | يعطّل الاختبارات في builds من نوع Release                                        |                                                                                       |
| `no-darwin`                    | يعطّل الاختبار على MacOS ‏(Darwin)                                               | يعتمد الاختبار على ميزات خاصة بـ Linux مثل distributed queries و`procfs` أو خادم HTTP |

الخيارات التالية مدعومة أيضًا: `no-polymorphic-parts`, `no-random-settings`, `no-random-merge-tree-settings`, `no-backward-compatibility-check`, `no-cpu-x86_64`, `no-cpu-aarch64`, `no-cpu-ppc64le`, `no-s3-storage`.

بالإضافة إلى الإعدادات المذكورة أعلاه، يمكنك استخدام الرايات `USE_*` من `system.build_options` لتحديد استخدام ميزات معيّنة في ClickHouse.
على سبيل المثال، إذا كان اختبارك يستخدم جدول MySQL، فينبغي إضافة الوسم `use-mysql`.

<div id="specifying-limits-for-random-settings">
  ### تحديد حدود الإعدادات العشوائية
</div>

يمكن للاختبار تحديد الحد الأدنى والحد الأقصى المسموح بهما للإعدادات التي يمكن تعيينها عشوائيًا أثناء تشغيل الاختبار.

بالنسبة لاختبارات `.sh`، تُكتب الحدود على شكل تعليق في السطر المجاور للوسوم، أو في السطر الثاني إذا لم تُحدَّد أي وسوم:

```bash
#!/usr/bin/env bash
# Tags: no-fasttest
# Random settings limits: max_block_size=(1000, 10000); index_granularity=(100, None)
```

بالنسبة إلى اختبارات `.sql`، تُوضَع الوسوم على هيئة تعليق SQL في السطر المجاور للوسوم أو في السطر الأول:

```sql
-- Tags: no-fasttest
-- Random settings limits: max_block_size=(1000, 10000); index_granularity=(100, None)
SELECT 1
```

إذا احتجت إلى تحديد حدّ واحد فقط، يمكنك استخدام `None` للحدّ الآخر.

<div id="choosing-the-test-name">
  ### اختيار اسم الاختبار
</div>

يبدأ اسم الاختبار ببادئة من خمسة أرقام، تليها تسمية وصفية، مثل `00422_hash_function_constexpr.sql`.
ولاختيار البادئة، ابحث عن أكبر بادئة موجودة بالفعل في المجلد، ثم زِدها بمقدار واحد.

```sh
ls tests/queries/0_stateless/[0-9]*.reference | tail -n 1
```

في هذه الأثناء، قد تُضاف اختبارات أخرى بالبادئة الرقمية نفسها، وهذا لا يسبب أي مشكلة، لذا لن تحتاج إلى تغييره لاحقًا.

<div id="checking-for-an-error-that-must-occur">
  ### التحقق من حدوث خطأ متوقَّع
</div>

أحيانًا قد تحتاج إلى اختبار حدوث خطأ من الخادم عند تنفيذ استعلام غير صحيح. نحن ندعم تعليقات توضيحية خاصة لهذا الغرض في اختبارات SQL، بالشكل التالي:

```sql
SELECT x; -- { serverError 49 }
```

يضمن هذا الاختبار أن يعيد الخادم خطأً بالرمز 49 يفيد بأن العمود `x` غير معروف.
إذا لم يظهر أي خطأ، أو كان الخطأ مختلفًا، فسيفشل الاختبار.
إذا كنت تريد التأكد من حدوث خطأ من جهة العميل، فاستخدم تعليق `clientError` التوضيحي بدلًا من ذلك.

لا تتحقق من صياغة محددة لرسالة الخطأ، لأنها قد تتغير مستقبلًا، ما قد يؤدي إلى تعطل الاختبار بلا داعٍ.
تحقق فقط من رمز الخطأ.
إذا لم يكن رمز الخطأ الحالي دقيقًا بما يكفي لاحتياجاتك، ففكّر في إضافة رمز جديد.

<div id="testing-a-distributed-query">
  ### اختبار استعلام موزّع
</div>

إذا كنت تريد استخدام الاستعلامات الموزّعة في الاختبارات الوظيفية، فيمكنك الاستفادة من دالة الجدول `remote` مع العناوين `127.0.0.{1..2}` لكي يجري الخادم استعلامًا على نفسه؛ أو يمكنك استخدام عناقيد الاختبار المعرّفة مسبقًا في ملف تهيئة الخادم مثل `test_shard_localhost`.
تذكّر إضافة الكلمتين `shard` أو `distributed` إلى اسم الاختبار، لكي يُشغَّل في CI ضمن التهيئات الصحيحة التي يكون فيها الخادم مهيّأً لدعم الاستعلامات الموزّعة.

<div id="working-with-temporary-files">
  ### العمل مع الملفات المؤقتة
</div>

أحيانًا، في اختبار shell، قد تحتاج إلى إنشاء ملف أثناء التنفيذ لاستخدامه.
ضع في اعتبارك أن بعض عمليات التحقق في CI تُشغِّل الاختبارات بالتوازي، لذا إذا كنت تُنشئ ملفًا مؤقتًا أو تحذفه في برنامج نصي من دون اسم فريد، فقد يتسبب ذلك في فشل بعض عمليات التحقق في CI، مثل Flaky.
ولتفادي ذلك، ينبغي استخدام متغير البيئة `$CLICKHOUSE_TEST_UNIQUE_NAME` لمنح الملفات المؤقتة اسمًا فريدًا للاختبار الجاري تشغيله.
وبهذه الطريقة، يمكنك التأكد من أن الملف الذي تُنشئه أثناء الإعداد أو تحذفه أثناء التنظيف هو الملف الذي يستخدمه ذلك الاختبار فقط، وليس اختبارًا آخر يعمل بالتوازي.

<div id="known-bugs">
  ## الأخطاء المعروفة
</div>

إذا كنا على علم ببعض الأخطاء التي يمكن إعادة إنتاجها بسهولة عبر الاختبارات الوظيفية، فإننا نضع اختبارات وظيفية مُعَدَّة مسبقًا في الدليل `tests/queries/bugs`.
وتُنقل هذه الاختبارات إلى `tests/queries/0_stateless` عند إصلاح هذه الأخطاء.

<div id="integration-tests">
  ## اختبارات التكامل
</div>

تتيح اختبارات التكامل اختبار ClickHouse في تهيئة عنقودية، واختبار تفاعله مع خوادم أخرى مثل MySQL وPostgres وMongoDB.
وتفيد هذه الاختبارات في محاكاة انقسامات الشبكة، وإسقاط الحزم، وما إلى ذلك.
تُشغَّل هذه الاختبارات ضمن Docker، وتُنشئ عدة حاويات تضم برمجيات متنوعة.

راجع `tests/integration/README.md` لمعرفة كيفية تشغيل هذه الاختبارات.

لاحظ أن تكامل ClickHouse مع برامج تشغيل الجهات الخارجية لا يُختبَر.
كما أننا لا نملك حاليًا اختبارات تكامل لبرامج تشغيل JDBC وODBC الخاصة بنا.

<div id="unit-tests">
  ## اختبارات الوحدة
</div>

تكون اختبارات الوحدة مفيدة عندما تريد اختبار ClickHouse ليس ككل، بل مكتبة واحدة معزولة أو صنفًا واحدًا.
يمكنك تمكين بناء الاختبارات أو تعطيله باستخدام خيار CMake ‏`ENABLE_TESTS`.
توجد اختبارات الوحدة (وبرامج الاختبار الأخرى) في الأدلة الفرعية `tests` في أنحاء الشيفرة.
لتشغيل اختبارات الوحدة، اكتب `ninja test`.
تستخدم بعض الاختبارات `gtest`، بينما يكون بعضها الآخر مجرد برامج تُرجع رمز خروج غير صفري عند فشل الاختبار.

ليس من الضروري أن تكون هناك اختبارات وحدة إذا كانت الشيفرة مغطاة بالفعل بالاختبارات الوظيفية (وعادةً ما تكون الاختبارات الوظيفية أبسط بكثير في الاستخدام).

يمكنك تشغيل عمليات التحقق الفردية في `gtest` عبر استدعاء الملف التنفيذي مباشرةً، على سبيل المثال:

```bash
$ ./src/unit_tests_dbms --gtest_filter=LocalAddress*
```

<div id="performance-tests">
  ## اختبارات الأداء
</div>

تتيح اختبارات الأداء قياس ومقارنة أداء بعض الأجزاء المعزولة من ClickHouse باستخدام استعلامات اصطناعية.
توجد اختبارات الأداء في `tests/performance/`.
ويُمثَّل كل اختبار بملف `.xml` يصف حالة الاختبار.
تُشغَّل الاختبارات باستخدام الأداة `docker/test/performance-comparison`. راجع ملف README لمعرفة كيفية التشغيل.

يشغّل كل اختبار استعلامًا واحدًا أو عدة استعلامات (وربما مع مجموعات من المعلمات) ضمن حلقة.

إذا كنت تريد تحسين أداء ClickHouse في سيناريو معين، وكانت التحسينات تظهر بوضوح في الاستعلامات البسيطة، فمن المستحسن جدًا كتابة اختبار أداء.
كما يُوصى أيضًا بكتابة اختبارات أداء عند إضافة دوال SQL أو تعديلها، إذا كانت معزولة نسبيًا وليست غامضة جدًا.
ومن المفيد دائمًا استخدام `perf top` أو أدوات `perf` الأخرى أثناء اختباراتك.

<div id="test-tools-and-scripts">
  ## أدوات ونصوص برمجية للاختبار
</div>

بعض البرامج في الدليل `tests` ليست اختبارات جاهزة، بل أدوات للاختبار.
فعلى سبيل المثال، بالنسبة إلى `Lexer`، توجد أداة `src/Parsers/tests/lexer` تقتصر على تجزئة `stdin` إلى رموز وكتابة النتيجة الملوّنة إلى `stdout`.
يمكنك استخدام هذا النوع من الأدوات كأمثلة على الشيفرة، وللاستكشاف والاختبار اليدوي.

<div id="miscellaneous-tests">
  ## اختبارات متفرقة
</div>

توجد اختبارات لنماذج التعلّم الآلي في `tests/external_models`.
هذه الاختبارات غير مُحدَّثة ويجب نقلها إلى اختبارات التكامل.

يوجد اختبار منفصل لعمليات الإدراج بالنصاب.
يشغّل هذا الاختبار عنقود ClickHouse على خوادم منفصلة ويحاكي حالات فشل متنوعة: انقسام الشبكة، وإسقاط الحزم (بين عُقد ClickHouse، وبين ClickHouse وZooKeeper، وبين خادم ClickHouse والعميل، وما إلى ذلك)، و`kill -9`، و`kill -STOP`، و`kill -CONT`، على غرار [Jepsen](https://aphyr.com/tags/Jepsen). ثم يتحقق الاختبار من أن جميع عمليات الإدراج التي تم تأكيدها قد كُتبت، وأن جميع عمليات الإدراج المرفوضة لم تُكتب.

<div id="manual-testing">
  ## الاختبار اليدوي
</div>

عند تطوير ميزة جديدة، فمن المنطقي أيضًا اختبارها يدويًا.
يمكنك القيام بذلك باتباع الخطوات التالية:

ابنِ ClickHouse. شغّل ClickHouse من الطرفية: انتقل إلى الدليل `programs/clickhouse-server` ثم شغّله باستخدام `./clickhouse-server`. سيستخدم ملفات الإعداد (`config.xml` و`users.xml` والملفات الموجودة داخل دليلي `config.d` و`users.d`) من الدليل الحالي افتراضيًا. للاتصال بخادم ClickHouse، شغّل `programs/clickhouse-client/clickhouse-client`.

لاحظ أن جميع أدوات clickhouse (الخادم، والعميل، وما إلى ذلك) ليست سوى روابط رمزية لملف تنفيذي واحد باسم `clickhouse`.
يمكنك العثور على هذا الملف التنفيذي في `programs/clickhouse`.
كما يمكن استدعاء جميع الأدوات بصيغة `clickhouse tool` بدلًا من `clickhouse-tool`.

بدلًا من ذلك، يمكنك تثبيت حزمة ClickHouse: إما إصدارًا مستقرًا من مستودع ClickHouse، أو بناء الحزمة بنفسك باستخدام `./release` من جذر الشيفرة المصدرية لـ ClickHouse.
ثم ابدأ الخادم باستخدام `sudo clickhouse start` (أو `stop` لإيقاف الخادم).
ابحث عن السجلات في `/etc/clickhouse-server/clickhouse-server.log`.

عندما يكون ClickHouse مثبتًا بالفعل على نظامك، يمكنك بناء ملف `clickhouse` تنفيذي جديد واستبدال الملف التنفيذي الحالي:

```bash
$ sudo clickhouse stop
$ sudo cp ./clickhouse /usr/bin/
$ sudo clickhouse start
```

يمكنك أيضًا إيقاف clickhouse-server الخاص بالنظام وتشغيل نسختك الخاصة باستخدام الإعدادات نفسها، ولكن مع توجيه السجلات إلى الطرفية:

```bash
$ sudo clickhouse stop
$ sudo -u clickhouse /usr/bin/clickhouse server --config-file /etc/clickhouse-server/config.xml
```

مثال مع gdb:

```bash
$ sudo -u clickhouse gdb --args /usr/bin/clickhouse server --config-file /etc/clickhouse-server/config.xml
```

إذا كانت خدمة `clickhouse-server` قيد التشغيل بالفعل ولا تريد إيقافها، فيمكنك تغيير أرقام المنافذ في ملف `config.xml` لديك (أو إعادة تعريفها في ملف داخل الدليل `config.d`) وتحديد مسار البيانات المناسب، ثم تشغيله.

يكاد الملف التنفيذي `clickhouse` لا يعتمد على أي تبعيات، ويعمل على نطاق واسع من توزيعات Linux.
ولإجراء اختبار سريع ومبدئي لتغييراتك على خادم، يمكنك ببساطة استخدام `scp` لنسخ الملف التنفيذي `clickhouse` الذي بنيته حديثًا إلى خادمك، ثم تشغيله كما في الأمثلة أعلاه.

<div id="build-tests">
  ## اختبارات البناء
</div>

تتيح اختبارات البناء التحقق من أن عملية البناء لا تتعطل في تهيئات بديلة مختلفة وعلى بعض الأنظمة الأخرى.
وهذه الاختبارات مؤتمتة أيضًا.

أمثلة:

* البناء المتقاطع لـ Darwin x86&#95;64 ‏(macOS)
* البناء المتقاطع لـ FreeBSD x86&#95;64
* البناء المتقاطع لـ Linux AArch64
* البناء على Ubuntu باستخدام مكتبات من حزم النظام (غير مستحسن)
* البناء مع الربط المشترك للمكتبات (غير مستحسن)

فعلى سبيل المثال، يُعد البناء باستخدام حزم النظام ممارسة سيئة، لأننا لا نستطيع ضمان الإصدار الدقيق من الحزم المتوفر على أي نظام.
لكن هذا مطلوب فعلًا من مشرفي Debian.
ولهذا السبب، يتعين علينا على الأقل دعم هذا النمط من البناء.
ومثال آخر: يُعد الربط المشترك مصدرًا شائعًا للمشكلات، لكنه مطلوب لبعض المتحمسين.

ومع أننا لا نستطيع تشغيل جميع الاختبارات على جميع أنماط البناء، فإننا نريد على الأقل التحقق من أن أنماط البناء المختلفة لا تتعطل.
ولهذا الغرض نستخدم اختبارات البناء.

ونختبر أيضًا عدم وجود وحدات ترجمة طويلة جدًا بحيث يصعب تجميعها أو تتطلب قدرًا كبيرًا من RAM.

ونختبر أيضًا عدم وجود إطارات مكدس كبيرة جدًا.

<div id="testing-for-protocol-compatibility">
  ## اختبار توافق البروتوكول
</div>

عندما نوسّع بروتوكول شبكة ClickHouse، نتحقق يدويًا من أن `clickhouse-client` القديم يعمل مع `clickhouse-server` الجديد، وأن `clickhouse-client` الجديد يعمل مع `clickhouse-server` القديم (وذلك ببساطة بتشغيل الملفات التنفيذية من الحزم المقابلة).

ونختبر أيضًا بعض الحالات تلقائيًا باستخدام اختبارات التكامل:

* ما إذا كان يمكن للإصدار الجديد قراءة البيانات التي كُتبت بإصدار أقدم من ClickHouse بنجاح؛
* ما إذا كانت الاستعلامات الموزعة تعمل في عنقود يضم إصدارات مختلفة من ClickHouse.

<div id="help-from-the-compiler">
  ## مساعدة من المصرّف
</div>

تُبنى شيفرة ClickHouse الرئيسية (الموجودة في الدليل `src`) باستخدام `-Wall -Wextra -Werror`، إلى جانب بعض التحذيرات الإضافية المفعّلة.
لكن هذه الخيارات لا تكون مفعّلة لمكتبات الطرف الثالث.

يوفّر Clang تحذيرات أكثر فائدة — يمكنك استعراضها باستخدام `-Weverything` واختيار بعضٍ منها لإضافته إلى البناء الافتراضي.

نستخدم دائمًا clang لبناء ClickHouse، سواء في التطوير أو الإنتاج.
يمكنك إجراء البناء على جهازك باستخدام وضع التصحيح (لتوفير بطارية حاسوبك المحمول)، لكن يُرجى ملاحظة أن المصرّف يمكنه توليد المزيد من التحذيرات مع `-O3` بفضل التحليل الأفضل لتدفق التحكم والتحليل بين الإجراءات.
وعند البناء باستخدام clang في وضع التصحيح، يُستخدَم إصدار التصحيح من `libc++`، مما يتيح اكتشاف المزيد من الأخطاء في وقت التشغيل.

<div id="sanitizers">
  ## أدوات كشف الأخطاء
</div>

:::note
إذا انهارت العملية (خادم ClickHouse أو العميل) عند بدء تشغيلها محليًا، فقد تحتاج إلى تعطيل التوزيع العشوائي لتخطيط مساحة العناوين: `sudo sysctl kernel.randomize_va_space=0`

<div id="address-sanitizer">
  ### Address sanitizer
</div>

نُشغِّل الاختبارات الوظيفية والتكامل والضغط والوحدة باستخدام ASan عند كل commit.

<div id="thread-sanitizer">
  ### Thread sanitizer
</div>

نشغّل اختبارات functional والتكامل والضغط واختبارات الوحدة باستخدام TSan مع كل commit.

<div id="memory-sanitizer">
  ### أداة اكتشاف أخطاء الذاكرة
</div>

نُشغّل الاختبارات الوظيفية، واختبارات التكامل، واختبارات الإجهاد، واختبارات الوحدات باستخدام MSan مع كل commit.

<div id="undefined-behaviour-sanitizer">
  ### UBSan لكشف السلوك غير المعرّف
</div>

نُشغّل الاختبارات الوظيفية واختبارات التكامل والإجهاد والوحدة باستخدام UBSan مع كل عملية commit.
ولا تُفحَص شيفرة بعض مكتبات الجهات الخارجية بحثًا عن السلوك غير المعرّف.

<div id="valgrind-memcheck">
  ### Valgrind (memcheck)
</div>

كنّا نشغّل الاختبارات الوظيفية باستخدام Valgrind طوال الليل، لكننا لم نعد نفعل ذلك.
إذ يستغرق الأمر عدة ساعات.
يوجد حاليًا إنذار إيجابي كاذب معروف واحد في مكتبة `re2`، راجع [هذه المقالة](https://research.swtch.com/sparse).

<div id="fuzzing">
  ## التشويش
</div>

يُنفَّذ التشويش في ClickHouse باستخدام كلٍّ من [libFuzzer](https://llvm.org/docs/LibFuzzer.html) واستعلامات SQL العشوائية.
يجب إجراء جميع اختبارات التشويش باستخدام أدوات sanitizers ‏(Address وUndefined).

يُستخدم libFuzzer لإجراء اختبارات تشويش معزولة لشيفرة المكتبات.
تُنفَّذ أدوات التشويش كجزء من شيفرة الاختبار، وتحمل اللاحقة &quot;&#95;fuzzer&quot; في الاسم.
يمكن العثور على مثال لأداة تشويش في `src/Parsers/fuzzers/lexer_fuzzer.cpp`.
تُخزَّن إعدادات libFuzzer الخاصة، والقواميس، وcorpus في `tests/fuzz`.
نشجّعك على كتابة اختبارات تشويش لكل وظيفة تتعامل مع مُدخلات المستخدم.

لا يتم بناء أدوات التشويش افتراضيًا.
ولبناء أدوات التشويش، يجب ضبط الخيارين `-DENABLE_FUZZING=1` و`-DENABLE_TESTS=1`.
نوصي بتعطيل Jemalloc عند بناء أدوات التشويش.
يمكن العثور على الإعدادات المستخدمة لدمج التشويش في ClickHouse مع
Google OSS-Fuzz في `docker/fuzz`.

نستخدم أيضًا اختبار تشويش بسيطًا لتوليد استعلامات SQL عشوائية والتحقق من أن الخادم لا يتعطل أثناء تنفيذها.
يمكنك العثور عليه في `00746_sql_fuzzy.pl`.
يجب تشغيل هذا الاختبار باستمرار (طوال الليل ولمدد أطول).

نستخدم أيضًا أداة تشويش متقدمة للاستعلامات تعتمد على AST، وهي قادرة على اكتشاف عدد هائل من الحالات الطرفية.
فهي تُجري تبديلات واستبدالات عشوائية في AST الخاص بالاستعلامات.
كما أنها تتذكر عُقد AST من الاختبارات السابقة لاستخدامها في تشويش الاختبارات اللاحقة، مع معالجتها بترتيب عشوائي.
يمكنك معرفة المزيد عن أداة التشويش هذه في [هذه المقالة على المدونة](https://clickhouse.com/blog/fuzzing-click-house).

<div id="stress-test">
  ## اختبار الضغط
</div>

اختبارات الضغط هي شكل آخر من التشويش.
وهو يشغّل جميع الاختبارات الوظيفية بالتوازي وبترتيب عشوائي باستخدام خادم واحد.
لا يتم التحقق من نتائج الاختبارات.

ويُتحقَّق مما يلي:

* ألا يتعطل الخادم، وألا يتم تفعيل أي مصائد Debug أو sanitizer؛
* عدم وجود حالات deadlocks؛
* اتساق بنية قاعدة البيانات؛
* أن يتمكن الخادم من التوقف بنجاح بعد الاختبار ثم البدء مجددًا دون استثناءات.

هناك خمسة أنواع (Debug, ASan, TSan, MSan, UBSan).

<div id="thread-fuzzer">
  ## Thread fuzzer
</div>

يُعد Thread Fuzzer (يرجى عدم الخلط بينه وبين Thread Sanitizer) نوعًا آخر من التشويش يتيح عشوائية ترتيب تنفيذ الخيوط.
ويساعد على اكتشاف المزيد من الحالات الخاصة.

<div id="security-audit">
  ## تدقيق أمني
</div>

أجرى فريق الأمن لدينا مراجعة أولية لإمكانات ClickHouse من منظور أمني.

<div id="static-analyzers">
  ## المحللات الثابتة
</div>

نُشغّل `clang-tidy` مع كل `commit`.
كما أن فحوصات `clang-static-analyzer` مفعّلة.
ويُستخدم `clang-tidy` أيضًا لبعض فحوصات التنسيق.

لقد قيّمنا `clang-tidy` و`Coverity` و`cppcheck` و`PVS-Studio` و`tscancode` و`CodeQL`.
ستجد تعليمات الاستخدام في الدليل `tests/instructions/`.

إذا كنت تستخدم `CLion` كبيئة تطوير متكاملة، فيمكنك الاستفادة من بعض فحوصات `clang-tidy` الجاهزة.

ونستخدم أيضًا `shellcheck` للتحليل الثابت للبرامج النصية للصدفة.

<div id="hardening">
  ## التحصين
</div>

في إصدارات التصحيح، نستخدم مُخصِّصًا مخصصًا يطبّق ASLR على تخصيصات مستوى المستخدم.

كما نحمي يدويًا مناطق الذاكرة التي يُفترض أن تصبح للقراءة فقط بعد التخصيص.

وفي إصدارات التصحيح، نستخدم أيضًا نسخة مخصصة من libc تضمن عدم استدعاء أي دوال &quot;ضارة&quot; (متقادمة، غير آمنة، أو غير آمنة للخيوط).

تُستخدم تأكيدات التصحيح على نطاق واسع.

في إصدار التصحيح، إذا تم رمي استثناء برمز &quot;خطأ منطقي&quot; (مما يشير إلى وجود خلل)، فسيتم إنهاء البرنامج فورًا.
وهذا يتيح استخدام الاستثناءات في إصدار الإصدار، مع التعامل معها كتأكيد في إصدار التصحيح.

يُستخدم إصدار التصحيح من jemalloc في إصدارات التصحيح.
ويُستخدم إصدار التصحيح من libc++ في إصدارات التصحيح.

<div id="runtime-integrity-checks">
  ## فحوصات سلامة البيانات أثناء التشغيل
</div>

تُحسب قيم التحقق للبيانات المخزنة على القرص.
تُحسب قيم التحقق للبيانات في جداول MergeTree بثلاث طرق في الوقت نفسه* (كتل البيانات المضغوطة، وكتل البيانات غير المضغوطة، وإجمالي قيمة التحقق عبر الكتل).
وتُحسب أيضًا قيم التحقق للبيانات المنقولة عبر الشبكة بين العميل والخادم أو بين الخوادم.
ويضمن النسخ المتماثل تطابق البيانات على مستوى البتات في النسخ المتماثلة.

وهذا ضروري للحماية من أعطال العتاد (تلف البتات على وسائط التخزين، وانقلاب البتات في RAM على الخادم، وانقلاب البتات في RAM لوحدة تحكم الشبكة، وانقلاب البتات في RAM لمبدّل الشبكة، وانقلاب البتات في RAM لدى العميل، وانقلاب البتات أثناء النقل).
لاحظ أن انقلابات البتات شائعة ومن المحتمل حدوثها حتى مع ECC RAM ومع وجود قيم التحقق الخاصة بـ TCP (إذا كنت تدير آلاف الخوادم التي تعالج petabytes من البيانات يوميًا).
[شاهد الفيديو (بالروسية)](https://www.youtube.com/watch?v=ooBAQIe0KlQ).

يوفّر ClickHouse أدوات تشخيص تساعد مهندسي التشغيل على اكتشاف العتاد المعطوب.

* ومع ذلك، فهذا ليس بطيئًا.

<div id="code-style">
  ## نمط الشيفرة
</div>

قواعد نمط الشيفرة موضحة [هنا](style.md).

للتحقق من بعض مخالفات النمط الشائعة، يمكنك استخدام البرنامج النصي `utils/check-style`.

لفرض النمط الصحيح على شيفرتك، يمكنك استخدام `clang-format`.
يوجد الملف `.clang-format` في جذر المصادر.
وهو يتوافق إلى حد كبير مع نمط الشيفرة المعتمد لدينا.
لكن لا يُنصح بتطبيق `clang-format` على الملفات الموجودة بالفعل لأنه قد يجعل التنسيق أسوأ.
يمكنك استخدام أداة `clang-format-diff`، التي يمكنك العثور عليها في مستودع مصادر clang.

بدلًا من ذلك، يمكنك تجربة أداة `uncrustify` لإعادة تنسيق شيفرتك.
يوجد ملف الإعداد `uncrustify.cfg` في جذر المصادر.
وهو أقل اختبارًا من `clang-format`.

يمتلك `CLion` منسّق شيفرة خاصًا به، ويجب ضبطه ليتوافق مع نمط الشيفرة لدينا.

<div id="test-coverage">
  ## تغطية الاختبارات
</div>

نتتبّع أيضًا تغطية الاختبارات، ولكن للاختبارات الوظيفية فقط، وفقط لـ clickhouse-server.
ويُجرى ذلك يوميًا.

<div id="tests-for-tests">
  ## اختبارات للتحقق من الاختبارات
</div>

يوجد تحقّق آلي من الاختبارات غير المستقرة.
ويُشغِّل جميع الاختبارات الجديدة 100 مرة (بالنسبة إلى الاختبارات الوظيفية) أو 10 مرات (بالنسبة إلى اختبارات التكامل).
إذا فشل الاختبار ولو مرة واحدة، فيُعَدّ غير مستقر.

<div id="test-automation">
  ## أتمتة الاختبارات
</div>

نُجري الاختبارات باستخدام [GitHub Actions](https://github.com/features/actions).

تُشغَّل مهام البناء والاختبارات في Sandbox لكل commit.
تُنشر الحزم الناتجة ونتائج الاختبارات على GitHub، ويمكن تنزيلها عبر روابط مباشرة.
تُحفَظ الـ artifacts لعدة أشهر.
عند إرسال طلب سحب على GitHub، نضع عليه الوسم &quot;can be tested&quot;، ثم يبني نظام CI لدينا حزم ClickHouse (release وdebug ومع address sanitizer وما إلى ذلك) من أجلك.
