<div id="description">
  ## الوصف
</div>

يرث المحرك `CollapsingMergeTree` من [MergeTree](../../../engines/table-engines/mergetree-family/mergetree.md)
ويضيف منطقًا لطيّ الصفوف أثناء عملية الدمج.
يحذف محرك الجدول `CollapsingMergeTree` (يطوي)
أزواجًا من الصفوف على نحو غير متزامن إذا كانت جميع الحقول في مفتاح الفرز (`ORDER BY`) متطابقة، باستثناء الحقل الخاص `Sign`،
الذي يمكن أن تكون قيمته `1` أو `-1`.
ويُحتفَظ بالصفوف التي لا يقابلها صف آخر بقيمة `Sign` معاكسة.

لمزيد من التفاصيل، راجع قسم [Collapsing](#table_engine-collapsingmergetree-collapsing) في هذه الوثيقة.

:::note
قد يقلّل هذا المحرك حجم التخزين بشكل كبير،
مما يزيد تبعًا لذلك من كفاءة استعلامات `SELECT`.
:::

<div id="parameters">
  ## المعلمات
</div>

جميع معلمات محرك الجدول هذا، باستثناء المعلمة `Sign`،
لها المعنى نفسه كما في [`MergeTree`](/ar/engines/table-engines/mergetree-family/mergetree).

* `Sign` — الاسم الذي يُطلق على عمود يحدد نوع الصف، حيث تمثل القيمة `1` صف &quot;حالة&quot; وتمثل القيمة `-1` صف &quot;إلغاء&quot;. النوع: [Int8](/ar/sql-reference/data-types/int-uint).

<div id="creating-a-table">
  ## إنشاء جدول
</div>

```sql
CREATE TABLE [IF NOT EXISTS] [db.]table_name [ON CLUSTER cluster]
(
    name1 [type1] [DEFAULT|MATERIALIZED|ALIAS expr1],
    name2 [type2] [DEFAULT|MATERIALIZED|ALIAS expr2],
    ...
) 
ENGINE = CollapsingMergeTree(Sign)
[PARTITION BY expr]
[ORDER BY expr]
[SAMPLE BY expr]
[SETTINGS name=value, ...]
```

<details markdown="1">
  <summary>طريقة قديمة لإنشاء جدول</summary>

  :::note
  لا يُنصح باستخدام الطريقة أدناه في المشاريع الجديدة.
  ننصح، إن أمكن، بتحديث المشاريع القديمة لاستخدام الطريقة الجديدة.
  :::

  ```sql
  CREATE TABLE [IF NOT EXISTS] [db.]table_name [ON CLUSTER cluster]
  (
      name1 [type1] [DEFAULT|MATERIALIZED|ALIAS expr1],
      name2 [type2] [DEFAULT|MATERIALIZED|ALIAS expr2],
      ...
  ) 
  ENGINE [=] CollapsingMergeTree(date-column [, sampling_expression], (primary, key), index_granularity, Sign)
  ```

  `Sign` — الاسم المُعطى لعمود يحدد نوع الصف، بحيث تمثل القيمة `1` صف «حالة»، وتمثل القيمة `-1` صف «إلغاء». [Int8](/ar/sql-reference/data-types/int-uint).
</details>

* للاطلاع على وصف معلمات الاستعلام، راجع [وصف الاستعلام](../../../sql-reference/statements/create/table.md).
* عند إنشاء جدول `CollapsingMergeTree`، تكون [بنود الاستعلام](../../../engines/table-engines/mergetree-family/mergetree.md#table_engine-mergetree-creating-a-table) نفسها مطلوبة كما هو الحال عند إنشاء جدول `MergeTree`.

<div id="table_engine-collapsingmergetree-collapsing">
  ## طي
</div>

<div id="data">
  ### البيانات
</div>

لنفترض حالة تحتاج فيها إلى حفظ بيانات تتغير باستمرار لكائن معيّن.
قد يبدو من المنطقي أن يكون هناك صف واحد لكل كائن ويُحدَّث كلما تغيّر شيء ما،
لكن عمليات التحديث مكلفة وبطيئة بالنسبة إلى نظام إدارة قواعد البيانات، لأنها تتطلب إعادة كتابة البيانات في التخزين.
إذا كنا بحاجة إلى كتابة البيانات بسرعة، فإن إجراء أعداد كبيرة من عمليات التحديث ليس نهجًا مقبولًا،
لكن يمكننا دائمًا كتابة تغييرات الكائن بشكل تسلسلي.
ولتحقيق ذلك، نستخدم العمود الخاص `Sign`.

* إذا كانت قيمة `Sign` = `1` فهذا يعني أن الصف هو صف &quot;حالة&quot;: *صف يحتوي على حقول تمثل الحالة الحالية الصالحة*.
* إذا كانت قيمة `Sign` = `-1` فهذا يعني أن الصف هو صف &quot;إلغاء&quot;: *صف يُستخدم لإلغاء حالة كائن له السمات نفسها*.

على سبيل المثال، نريد حساب عدد الصفحات التي زارها المستخدمون على موقع ويب معيّن والمدة التي قضوها فيها.
وفي لحظة زمنية معيّنة، نكتب الصف التالي الذي يمثّل حالة نشاط المستخدم:

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         5 │      146 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```

في وقتٍ لاحق، نسجّل التغيّر في نشاط المستخدم ونُدوّنه في الصفّين التاليين:

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         5 │      146 │   -1 │
│ 4324182021466249494 │         6 │      185 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```

يلغي الصف الأول الحالة السابقة للكائن (الذي يمثّل مستخدمًا في هذه الحالة).
يجب أن ينسخ جميع حقول مفتاح الترتيب للصف &quot;الملغى&quot; باستثناء `Sign`.
يحتوي الصف الثاني أعلاه على الحالة الحالية.

ونظرًا لأننا نحتاج فقط إلى آخر حالة لنشاط المستخدم، يمكن حذف صف &quot;الحالة&quot; الأصلي وصف &quot;الإلغاء&quot;
اللذين أدرجناهما كما هو موضح أدناه، مع طيّ الحالة غير الصالحة (القديمة) للكائن:

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         5 │      146 │    1 │ -- old "state" row can be deleted
│ 4324182021466249494 │         5 │      146 │   -1 │ -- "cancel" row can be deleted
│ 4324182021466249494 │         6 │      185 │    1 │ -- new "state" row remains
└─────────────────────┴───────────┴──────────┴──────┘
```

ينفّذ `CollapsingMergeTree` هذا السلوك *طي* تحديدًا أثناء دمج أجزاء البيانات.

:::note
تُناقَش أسباب الحاجة إلى صفّين لكل تغيير
بمزيد من التفصيل في فقرة [الخوارزمية](#table_engine-collapsingmergetree-collapsing-algorithm).
:::

**خصوصيات هذا النهج**

1. يجب أن يتذكر البرنامج الذي يكتب البيانات حالة الكائن حتى يتمكن من إلغائها. ويجب أن يحتوي صف &quot;إلغاء&quot; على نُسخ من حقول مفتاح الفرز الخاصة بـ &quot;حالة&quot;، مع `Sign` معاكس. يزيد هذا من الحجم الأولي للتخزين، لكنه يتيح كتابة البيانات بسرعة.
2. تؤدي المصفوفات الطويلة والمتزايدة في الأعمدة إلى تقليل كفاءة المحرك بسبب زيادة عبء الكتابة. وكلما كانت البيانات أبسط، ارتفعت الكفاءة.
3. تعتمد نتائج `SELECT` بدرجة كبيرة على اتساق سجل تغييرات الكائن. توخَّ الدقة عند إعداد البيانات للإدراج. فقد تؤدي البيانات غير المتسقة إلى نتائج غير متوقعة. على سبيل المثال، قيم سالبة لمقاييس غير سالبة مثل عمق الجلسة.

<div id="table_engine-collapsingmergetree-collapsing-algorithm">
  ### الخوارزمية
</div>

عندما يدمج ClickHouse [الأجزاء](/ar/concepts/glossary#parts) البيانية،
تُختزل كل مجموعة من الصفوف المتتالية التي لها مفتاح الفرز نفسه (`ORDER BY`) إلى صفَّين كحد أقصى،
هما صف &quot;حالة&quot; حيث `Sign` = `1` وصف &quot;إلغاء&quot; حيث `Sign` = `-1`.
وبعبارة أخرى، تُطوى الإدخالات في ClickHouse.

لكل جزء بيانات ناتج، يحفظ ClickHouse ما يلي:

|    |                                                                                                                                                             |
| -- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. | أول صف &quot;إلغاء&quot; وآخر صف &quot;حالة&quot;، إذا كان عدد صفوف &quot;حالة&quot; و&quot;إلغاء&quot; متساويًا وكان الصف الأخير صف &quot;حالة&quot;. |
| 2. | آخر صف &quot;حالة&quot;، إذا كان عدد صفوف &quot;حالة&quot; أكبر من عدد صفوف &quot;إلغاء&quot;.                                                           |
| 3. | أول صف &quot;إلغاء&quot;، إذا كان عدد صفوف &quot;إلغاء&quot; أكبر من عدد صفوف &quot;حالة&quot;.                                                          |
| 4. | لا يحفظ أيًّا من الصفوف، في جميع الحالات الأخرى.                                                                                                            |

إضافةً إلى ذلك، عندما يزيد عدد صفوف &quot;حالة&quot; على صفوف &quot;إلغاء&quot; بمقدار صفَّين على الأقل،
أو يزيد عدد صفوف &quot;إلغاء&quot; على صفوف &quot;حالة&quot; بمقدار صفَّين على الأقل، تستمر عملية الدمج.
ومع ذلك، يتعامل ClickHouse مع هذا الوضع على أنه خطأ منطقي ويسجّله في سجل الخادم.
يمكن أن يحدث هذا الخطأ إذا أُدرجت البيانات نفسها أكثر من مرة.
لذلك، يجب ألّا يغيّر الطي نتائج حساب الإحصاءات.
وتُطوى التغييرات تدريجيًا بحيث لا يبقى في النهاية، في معظم الحالات، سوى الحالة الأخيرة لكل كائن.

العمود `Sign` مطلوب لأن خوارزمية الدمج لا تضمن
أن جميع الصفوف ذات مفتاح الفرز نفسه ستكون في جزء البيانات الناتج نفسه أو حتى على الخادم الفعلي نفسه.
يعالج ClickHouse استعلامات `SELECT` باستخدام خيوط تنفيذ متعددة، ولا يمكنه التنبؤ بترتيب الصفوف في النتيجة.

يكون التجميع مطلوبًا إذا كانت هناك حاجة إلى الحصول على بيانات &quot;مطوية&quot; بالكامل من جدول `CollapsingMergeTree`.
ولإتمام الطي، اكتب استعلامًا يتضمن عبارة `GROUP BY` ودوال تجميع تراعي الإشارة.
فعلى سبيل المثال، لحساب العدد، استخدم `sum(Sign)` بدلًا من `count()`.
ولحساب مجموع قيمة ما، استخدم `sum(Sign * x)` مع `HAVING sum(Sign) > 0` بدلًا من `sum(x)`
كما في [المثال](#example-of-use) أدناه.

يمكن حساب الدوال التجميعية `count` و`sum` و`avg` بهذه الطريقة.
ويمكن حساب الدالة التجميعية `uniq` إذا كان للكائن حالة واحدة غير مطوية على الأقل.
أما الدالتان التجميعيتان `min` و`max` فلا يمكن حسابهما
لأن `CollapsingMergeTree` لا يحفظ سجل الحالات المطوية.

:::note
إذا كنت تحتاج إلى استخراج البيانات من دون تجميع
(على سبيل المثال، للتحقق مما إذا كانت هناك صفوف تتطابق أحدث قيمها مع شروط معيّنة)،
فيمكنك استخدام المُعدِّل [`FINAL`](../../../sql-reference/statements/select/from.md#final-modifier) لعبارة `FROM`. وسيؤدي ذلك إلى دمج البيانات قبل إرجاع النتيجة.
وبالنسبة إلى CollapsingMergeTree، لا يُعاد إلا أحدث صف &quot;حالة&quot; لكل مفتاح.
:::

<div id="examples">
  ## أمثلة
</div>

<div id="example-of-use">
  ### مثال للاستخدام
</div>

استنادًا إلى بيانات المثال التالية:

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         5 │      146 │    1 │
│ 4324182021466249494 │         5 │      146 │   -1 │
│ 4324182021466249494 │         6 │      185 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```

لننشئ جدولًا `UAct` باستخدام `CollapsingMergeTree`:

```sql
CREATE TABLE UAct
(
    UserID UInt64,
    PageViews UInt8,
    Duration UInt8,
    Sign Int8
)
ENGINE = CollapsingMergeTree(Sign)
ORDER BY UserID
```

بعد ذلك، سنُدرج بعض البيانات:

```sql
INSERT INTO UAct VALUES (4324182021466249494, 5, 146, 1)
```

```sql
INSERT INTO UAct VALUES (4324182021466249494, 5, 146, -1),(4324182021466249494, 6, 185, 1)
```

نستخدم استعلامَي `INSERT` لإنشاء جزأَي بيانات مختلفين.

:::note
إذا أدرجنا البيانات عبر استعلام واحد، فسينشئ ClickHouse جزء بيانات واحدًا فقط، ولن يُجري بعد ذلك أي عملية دمج.
:::

يمكننا تحديد البيانات باستخدام:

```sql
SELECT * FROM UAct
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         5 │      146 │   -1 │
│ 4324182021466249494 │         6 │      185 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         5 │      146 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```

لنلقِ نظرة على البيانات المُعادة أعلاه ولنرَ ما إذا كان الطي قد حدث...
باستخدام استعلامَي `INSERT`، أنشأنا جزأين من البيانات.
نُفِّذ استعلام `SELECT` عبر خيطَي تنفيذ، فحصلنا على ترتيب عشوائي للصفوف.
ومع ذلك، **لم يحدث الطي** لأنه لم يكن هناك دمج لأجزاء البيانات بعد،
كما أن ClickHouse يدمج أجزاء البيانات في الخلفية في وقت غير معلوم لا يمكننا التنبؤ به.

لذلك نحتاج إلى تجميع،
ونجريه باستخدام الدالة التجميعية [`sum`](/ar/sql-reference/aggregate-functions/reference/sum)
والبند [`HAVING`](/ar/sql-reference/statements/select/having):

```sql
SELECT
    UserID,
    sum(PageViews * Sign) AS PageViews,
    sum(Duration * Sign) AS Duration
FROM UAct
GROUP BY UserID
HAVING sum(Sign) > 0
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┐
│ 4324182021466249494 │         6 │      185 │
└─────────────────────┴───────────┴──────────┘
```

إذا لم نكن بحاجة إلى التجميع وأردنا فرض الـ طي، فيمكننا أيضًا استخدام المُعدِّل `FINAL` مع بند `FROM`.

```sql
SELECT * FROM UAct FINAL
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         6 │      185 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```

:::note
هذه الطريقة لاختيار البيانات أقل كفاءة، ولا يُنصح بها عند التعامل مع كميات كبيرة من البيانات التي يجري فحصها (ملايين الصفوف).
:::

<div id="example-of-another-approach">
  ### مثال على نهج آخر
</div>

تتمثل فكرة هذا النهج في أن عمليات الدمج لا تراعي إلا حقول المفاتيح.
لذلك يمكننا في صف &quot;إلغاء&quot; تحديد قيم سالبة
تعادل النسخة السابقة من الصف عند الجمع من دون استخدام العمود `Sign`.

في هذا المثال، سنستخدم بيانات العينة أدناه:

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         5 │      146 │    1 │
│ 4324182021466249494 │        -5 │     -146 │   -1 │
│ 4324182021466249494 │         6 │      185 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```

في هذا النهج، يلزم تغيير نوعَي البيانات لـ `PageViews` و`Duration` بحيث يمكنهما تخزين قيم سالبة.
لذلك نغيّر نوع هذين العمودين من `UInt8` إلى `Int16` عند إنشاء الجدول `UAct` باستخدام
`collapsingMergeTree`:

```sql
CREATE TABLE UAct
(
    UserID UInt64,
    PageViews Int16,
    Duration Int16,
    Sign Int8
)
ENGINE = CollapsingMergeTree(Sign)
ORDER BY UserID
```

لنختبر هذا النهج بإدراج البيانات في جدولنا.

ومع ذلك، يُعد هذا مقبولًا في الأمثلة أو عند التعامل مع جداول صغيرة:

```sql
INSERT INTO UAct VALUES(4324182021466249494,  5,  146,  1);
INSERT INTO UAct VALUES(4324182021466249494, -5, -146, -1);
INSERT INTO UAct VALUES(4324182021466249494,  6,  185,  1);

SELECT * FROM UAct FINAL;
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         6 │      185 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```

```sql
SELECT
    UserID,
    sum(PageViews) AS PageViews,
    sum(Duration) AS Duration
FROM UAct
GROUP BY UserID
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┐
│ 4324182021466249494 │         6 │      185 │
└─────────────────────┴───────────┴──────────┘
```

```sql
SELECT COUNT() FROM UAct
```

```text
┌─count()─┐
│       3 │
└─────────┘
```

```sql
OPTIMIZE TABLE UAct FINAL;

SELECT * FROM UAct
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┐
│ 4324182021466249494 │         6 │      185 │    1 │
└─────────────────────┴───────────┴──────────┴──────┘
```
