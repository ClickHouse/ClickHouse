هذا المحرك:

* يتيح كتابة حالات الكائنات التي تتغير باستمرار بسرعة.
* يحذف حالات الكائنات القديمة في الخلفية. وهذا يقلّل حجم التخزين بشكل كبير.

راجع قسم [الطي](#table_engines_versionedcollapsingmergetree) لمزيد من التفاصيل.

يرث هذا المحرك من [MergeTree](/ar/engines/table-engines/mergetree-family/mergetree) ويضيف منطق طيّ الصفوف إلى خوارزمية دمج أجزاء البيانات. ويؤدي `VersionedCollapsingMergeTree` الغرض نفسه الذي يؤديه [CollapsingMergeTree](../../../engines/table-engines/mergetree-family/collapsingmergetree.md)، لكنه يستخدم خوارزمية طيّ مختلفة تسمح بإدراج البيانات بأي ترتيب باستخدام عدة خيوط تنفيذ. وعلى وجه الخصوص، يساعد العمود `Version` على طيّ الصفوف بشكل صحيح حتى إذا أُدرجت بترتيب غير صحيح. في المقابل، لا يتيح `CollapsingMergeTree` إلا الإدراج المتتالي الصارم.

<div id="creating-a-table">
  ## إنشاء جدول
</div>

```sql
CREATE TABLE [IF NOT EXISTS] [db.]table_name [ON CLUSTER cluster]
(
    name1 [type1] [DEFAULT|MATERIALIZED|ALIAS expr1],
    name2 [type2] [DEFAULT|MATERIALIZED|ALIAS expr2],
    ...
) ENGINE = VersionedCollapsingMergeTree(sign, version)
[PARTITION BY expr]
[ORDER BY expr]
[SAMPLE BY expr]
[SETTINGS name=value, ...]
```

للاطلاع على وصف معلمات الاستعلام، راجع [وصف الاستعلام](../../../sql-reference/statements/create/table.md).

<div id="engine-parameters">
  ### معلمات المحرّك
</div>

```sql
VersionedCollapsingMergeTree(sign, version)
```

| المعلمة   | الوصف                                                                                     | النوع                                                                                                                                                                                                                                                                                         |
| --------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sign`    | اسم العمود الذي يحدد نوع الصف: `1` هو صف &quot;حالة&quot;، و`-1` هو صف &quot;إلغاء&quot;. | [`Int8`](/ar/sql-reference/data-types/int-uint)                                                                                                                                                                                                                                                  |
| `version` | اسم العمود الذي يحتوي على إصدار حالة الكائن.                                              | [`Int*`](/ar/sql-reference/data-types/int-uint), [`UInt*`](/ar/sql-reference/data-types/int-uint), [`Date`](/ar/sql-reference/data-types/date), [`Date32`](/ar/sql-reference/data-types/date32), [`DateTime`](/ar/sql-reference/data-types/datetime) أو [`DateTime64`](/ar/sql-reference/data-types/datetime64) |

<div id="query-clauses">
  ### بنود الاستعلام
</div>

عند إنشاء جدول `VersionedCollapsingMergeTree`، يلزم استخدام [البنود](../../../engines/table-engines/mergetree-family/mergetree.md) نفسها كما عند إنشاء جدول `MergeTree`.

<details markdown="1">
  <summary>طريقة قديمة مُهمَلة لإنشاء جدول</summary>

  :::note
  لا تستخدم هذه الطريقة في المشاريع الجديدة. وإذا أمكن، انقل المشاريع القديمة إلى الطريقة الموضحة أعلاه.
  :::

  ```sql
  CREATE TABLE [IF NOT EXISTS] [db.]table_name [ON CLUSTER cluster]
  (
      name1 [type1] [DEFAULT|MATERIALIZED|ALIAS expr1],
      name2 [type2] [DEFAULT|MATERIALIZED|ALIAS expr2],
      ...
  ) ENGINE [=] VersionedCollapsingMergeTree(date-column [, sampling_expression], (primary, key), index_granularity, sign, version)
  ```

  جميع المعلَمات، باستثناء `sign` و`version`، لها المعنى نفسه كما في `MergeTree`.

  * `sign` — اسم العمود الذي يحدد نوع الصف: `1` هو صف &quot;حالة&quot;، و`-1` هو صف &quot;إلغاء&quot;.

    نوع بيانات العمود — `Int8`.

  * `version` — اسم العمود الذي يحتوي على إصدار حالة الكائن.

    يجب أن يكون نوع بيانات العمود `UInt*`.
</details>

<div id="table_engines_versionedcollapsingmergetree">
  ## الطي
</div>

<div id="data">
  ### البيانات
</div>

لنفترض حالة تحتاج فيها إلى حفظ بيانات تتغير باستمرار لكائنٍ ما. من المنطقي أن يكون هناك صف واحد لكل كائن، وأن يُحدَّث هذا الصف كلما طرأت تغييرات. لكن عملية التحديث مكلفة وبطيئة بالنسبة إلى نظام إدارة قواعد البيانات، لأنها تتطلب إعادة كتابة البيانات في وحدة التخزين. ولا يكون التحديث خيارًا مناسبًا إذا كنت بحاجة إلى كتابة البيانات بسرعة، ولكن يمكنك كتابة التغييرات الخاصة بكائن ما بشكل تسلسلي كما يلي.

استخدم العمود `Sign` عند كتابة الصف. إذا كانت `Sign = 1` فهذا يعني أن الصف يمثّل حالة لكائن ما (ولنسمِّه صف &quot;الحالة&quot;). وإذا كانت `Sign = -1` فهذا يشير إلى إلغاء حالة لكائن له السمات نفسها (ولنسمِّه صف &quot;الإلغاء&quot;). واستخدم أيضًا العمود `Version`، الذي ينبغي أن يميّز كل حالة لكائن ما برقم منفصل.

على سبيل المثال، نريد حساب عدد الصفحات التي زارها المستخدمون على موقعٍ ما والمدة التي قضوها هناك. في لحظة زمنية معيّنة، نكتب الصف التالي الذي يمثّل حالة نشاط المستخدم:

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┬─Version─┐
│ 4324182021466249494 │         5 │      146 │    1 │       1 |
└─────────────────────┴───────────┴──────────┴──────┴─────────┘
```

في مرحلة لاحقة، نسجّل التغيّر في نشاط المستخدم وندوّنه في الصفّين التاليين.

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┬─Version─┐
│ 4324182021466249494 │         5 │      146 │   -1 │       1 |
│ 4324182021466249494 │         6 │      185 │    1 │       2 |
└─────────────────────┴───────────┴──────────┴──────┴─────────┘
```

يلغي الصف الأول الحالة السابقة للكائن (المستخدم). ويجب أن ينسخ جميع حقول الحالة الملغاة باستثناء `Sign`.

يحتوي الصف الثاني على الحالة الحالية.

وبما أننا لا نحتاج إلا إلى آخر حالة لنشاط المستخدم، فإن الصفوف

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┬─Version─┐
│ 4324182021466249494 │         5 │      146 │    1 │       1 |
│ 4324182021466249494 │         5 │      146 │   -1 │       1 |
└─────────────────────┴───────────┴──────────┴──────┴─────────┘
```

يمكن حذفه، وبذلك تُطوى الحالة غير الصالحة (القديمة) للكائن. وينفّذ `VersionedCollapsingMergeTree` ذلك أثناء دمج أجزاء البيانات.

لمعرفة سبب حاجتنا إلى صفّين لكل تغيير، راجع [الخوارزمية](#table_engines-versionedcollapsingmergetree-algorithm).

**ملاحظات حول الاستخدام**

1. يجب أن يحتفظ البرنامج الذي يكتب البيانات بحالة الكائن حتى يتمكن من إلغائها. يجب أن تحتوي السلسلة &quot;إلغاء&quot; على نسخ من حقول المفتاح الأساسي، وإصدار السلسلة &quot;حالة&quot;، و`Sign` بالقيمة المعاكسة. يزيد ذلك الحجم الأولي للتخزين، لكنه يتيح كتابة البيانات بسرعة.
2. تقلّل المصفوفات الطويلة والمتزايدة داخل الأعمدة من كفاءة المحرّك بسبب العبء الناتج عن الكتابة. وكلما كانت البيانات أبسط، كانت الكفاءة أفضل.
3. تعتمد نتائج `SELECT` بدرجة كبيرة على اتساق سجل تغييرات الكائن. توخَّ الدقة عند إعداد البيانات من أجل إدراجها. فقد تحصل على نتائج غير متوقعة إذا كانت البيانات غير متسقة، مثل قيم سالبة لمقاييس غير سالبة مثل عمق الجلسة.

<div id="table_engines-versionedcollapsingmergetree-algorithm">
  ### الخوارزمية
</div>

عند دمج ClickHouse لأجزاء البيانات، يحذف كل زوج من الصفوف لهما المفتاح الأساسي والإصدار نفسيهما وتختلف فيهما قيمة `Sign`. ولا يهم ترتيب الصفوف.

عندما يُدرج ClickHouse البيانات، فإنه يرتب الصفوف حسب المفتاح الأساسي. وإذا لم يكن العمود `Version` ضمن المفتاح الأساسي، فإن ClickHouse يضيفه إليه ضمنيًا باعتباره الحقل الأخير ويستخدمه في الترتيب.

<div id="selecting-data">
  ## اختيار البيانات
</div>

لا يضمن ClickHouse أن تكون جميع الصفوف التي تحمل المفتاح الأساسي نفسه في جزء البيانات الناتج نفسه، أو حتى على الخادم الفعلي نفسه. وينطبق ذلك سواء عند كتابة البيانات أو عند الدمج اللاحق لأجزاء البيانات. بالإضافة إلى ذلك، يعالج ClickHouse استعلامات `SELECT` باستخدام عدة خيوط، ولا يمكنه التنبؤ بترتيب الصفوف في النتيجة. وهذا يعني أن التجميع يكون مطلوبًا إذا كانت هناك حاجة إلى الحصول على بيانات &quot;مطوية&quot; بالكامل من جدول `VersionedCollapsingMergeTree`.

لإتمام الطي، اكتب استعلامًا يتضمن عبارة `GROUP BY` ودوال تجميع تراعي الإشارة. على سبيل المثال، لحساب الكمية، استخدم `sum(Sign)` بدلًا من `count()`. ولحساب مجموع قيمة ما، استخدم `sum(Sign * x)` بدلًا من `sum(x)`، وأضف `HAVING sum(Sign) > 0`.

يمكن حساب الدوال التجميعية `count` و`sum` و`avg` بهذه الطريقة. ويمكن حساب الدالة التجميعية `uniq` إذا كان للكائن حالة واحدة على الأقل غير مطوية. أما الدالتان التجميعيتان `min` و`max` فلا يمكن حسابهما، لأن `VersionedCollapsingMergeTree` لا يحتفظ بمحفوظات قيم الحالات المطوية.

إذا كنت بحاجة إلى استخراج البيانات مع &quot;الطي&quot; ولكن من دون تجميع (على سبيل المثال، للتحقق مما إذا كانت هناك صفوف أحدث قيمها تطابق شروطًا معينة)، فيمكنك استخدام المعدِّل `FINAL` لعبارة `FROM`. هذا النهج غير فعّال، ويجب عدم استخدامه مع الجداول الكبيرة.

<div id="example-of-use">
  ## مثال للاستخدام
</div>

بيانات المثال:

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┬─Version─┐
│ 4324182021466249494 │         5 │      146 │    1 │       1 |
│ 4324182021466249494 │         5 │      146 │   -1 │       1 |
│ 4324182021466249494 │         6 │      185 │    1 │       2 |
└─────────────────────┴───────────┴──────────┴──────┴─────────┘
```

إنشاء الجدول:

```sql
CREATE TABLE UAct
(
    UserID UInt64,
    PageViews UInt8,
    Duration UInt8,
    Sign Int8,
    Version UInt8
)
ENGINE = VersionedCollapsingMergeTree(Sign, Version)
ORDER BY UserID
```

إدراج البيانات:

```sql
INSERT INTO UAct VALUES (4324182021466249494, 5, 146, 1, 1)
```

```sql
INSERT INTO UAct VALUES (4324182021466249494, 5, 146, -1, 1),(4324182021466249494, 6, 185, 1, 2)
```

نستخدم استعلامَي `INSERT` لإنشاء جزأَي بيانات مختلفين. وإذا أدرجنا البيانات باستعلام واحد، فسينشئ ClickHouse جزء بيانات واحدًا فقط ولن يُجري أي عملية دمج مطلقًا.

جلب البيانات:

```sql
SELECT * FROM UAct
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┬─Version─┐
│ 4324182021466249494 │         5 │      146 │    1 │       1 │
└─────────────────────┴───────────┴──────────┴──────┴─────────┘
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┬─Version─┐
│ 4324182021466249494 │         5 │      146 │   -1 │       1 │
│ 4324182021466249494 │         6 │      185 │    1 │       2 │
└─────────────────────┴───────────┴──────────┴──────┴─────────┘
```

ماذا نرى هنا، وأين الأجزاء المطوية؟
لقد أنشأنا جزأين من البيانات باستخدام استعلامَي `INSERT`. ونُفِّذ استعلام `SELECT` على خيطَي تنفيذ، فجاءت النتيجة بترتيب عشوائي للصفوف.
لم يحدث الطيّ لأن أجزاء البيانات لم تُدمج بعد. يدمج ClickHouse أجزاء البيانات في وقت غير معلوم لا يمكننا التنبؤ به.

ولهذا نحتاج إلى التجميع:

```sql
SELECT
    UserID,
    sum(PageViews * Sign) AS PageViews,
    sum(Duration * Sign) AS Duration,
    Version
FROM UAct
GROUP BY UserID, Version
HAVING sum(Sign) > 0
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Version─┐
│ 4324182021466249494 │         6 │      185 │       2 │
└─────────────────────┴───────────┴──────────┴─────────┘
```

إذا لم نكن بحاجة إلى التجميع وأردنا فرض عملية الطي، فيمكننا استخدام المُعدِّل `FINAL` في عبارة `FROM`.

```sql
SELECT * FROM UAct FINAL
```

```text
┌──────────────UserID─┬─PageViews─┬─Duration─┬─Sign─┬─Version─┐
│ 4324182021466249494 │         6 │      185 │    1 │       2 │
└─────────────────────┴───────────┴──────────┴──────┴─────────┘
```

هذه طريقة غير فعّالة للغاية لاستخراج البيانات. لا تستخدمها مع الجداول الكبيرة.
