<div id="queryrunner-table-engine">
  # محرك جدول QueryRunner
</div>

تمثل السجلات التي أُدرجت في جدول `QueryRunner` الاستعلامات التي ينفذها المحرك.
يمكن استخدام المحرك للتنفيذ غير المتزامن للاستعلامات، والتنفيذ الدفعي للاستعلامات المُولَّدة،
وتوجيه الاستعلامات إلى المجموعات العنقودية البعيدة، واختبارات الأداء، والتشويش، والاختبار باستخدام حركة المرور الظلية.

<div id="creating-a-table">
  ## إنشاء جدول
</div>

```sql
CREATE TABLE runner
(
    query String,
    database String,
    settings Map(LowCardinality(String), String)
)
ENGINE = QueryRunner
SETTINGS
    cluster = 'cluster_name',
    shard = '1',
    mode = 'asynchronous',
    threads = 4,
    max_queue_size = 1000
[DEFINER = { user | CURRENT_USER }] [SQL SECURITY { DEFINER | INVOKER | NONE }];
```

يجب إنشاء الجدول باستخدام مجموعة فرعية من الأعمدة المسموح بها: `query`، `database`، `settings`.
العمود `query` إلزامي، أما الأعمدة الأخرى فاختيارية.

| العمود     | النوع                 | المعنى                                                                                                    |
| ---------- | --------------------- | --------------------------------------------------------------------------------------------------------- |
| `query`    | `String`              | الاستعلام المطلوب تنفيذه.                                                                                 |
| `database` | `String`              | قاعدة البيانات الافتراضية للاستعلام. إذا كانت فارغة، فستُستخدَم قاعدة البيانات الافتراضية الخاصة بالخادم. |
| `settings` | `Map(String, String)` | الإعدادات المطبَّقة على الاستعلام.                                                                        |

<div id="engine-settings">
  ## إعدادات المحرّك
</div>

| الإعداد          | الافتراضي        | المعنى                                                                                                                                                                                     |
| ---------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `cluster`        | `''`             | اسم العنقود الذي تُرسل إليه الاستعلامات. إذا كانت القيمة فارغة، تُنفَّذ الاستعلامات محليًا.                                                                                                |
| `shard`          | `'1'`            | فهرس الشظية في العنقود ذو الأساس 1 التي تُرسل إليها الاستعلامات، أو `'random'` لاختيار شظية عشوائية لكل استعلام، أو `'all'` لتشغيل كل استعلام على جميع الشظايا. يتطلب ذلك إعداد `cluster`. |
| `mode`           | `'asynchronous'` | في وضع `synchronous`، ترجع عملية INSERT بعد اكتمال جميع استعلامات الدفعة المُدرجة. وفي وضع `asynchronous`، ترجع عملية INSERT بمجرد إدراج الاستعلامات في قائمة الانتظار.                    |
| `threads`        | `4`              | عدد الخيوط الخلفية التي تنفّذ الاستعلامات.                                                                                                                                                 |
| `max_queue_size` | `1000`           | الحد الأقصى لعدد الاستعلامات في قائمة الانتظار. عند امتلاء قائمة الانتظار، تُهمَل الاستعلامات المُضافة حديثًا ويُسجَّل خطأ.                                                                |

<div id="details">
  ## التفاصيل
</div>

لا يسمح الجدول إلا باستعلامات `INSERT`.
تُنفَّذ الاستعلامات في وضع &quot;نفّذ وانسَ&quot;: ففي حال وقوع استثناء، لا تُجرى أي محاولات إعادة،
كما تُهمَل نتائج استعلامات `SELECT` (والطريقة الوحيدة للاحتفاظ بالنتائج هي `INSERT SELECT`).
ويمكن التحقق من نجاح كل استعلام في جدول `system.query_log`، حيث تُوسَم الاستعلامات التي يبدأها
هذا المحرّك بالقيمة `is_internal = 1` على الخادم البادئ.

تُحفَظ الاستعلامات الموجودة في قائمة الانتظار في الذاكرة، ولا تبقى بعد إعادة تشغيل الخادم. وعند إيقاف تشغيل الخادم
(أو عند `DROP`/`DETACH` للجدول)، تُهمَل الاستعلامات التي لم تبدأ بعد. أما
الاستعلامات التي بدأ تنفيذها بالفعل، فتُلغى تلك المُرسَلة إلى العنقود، بينما يُنتظَر اكتمال تلك التي تعمل
محليًا حتى تنتهي.

عندما يكون الاستعلام المراد تشغيله هو نفسه `INSERT`، يجب أن تكون بياناته مضمنة مباشرةً — `INSERT ... VALUES (...)`,
أو `INSERT ... SELECT ...`، أو `INSERT ... FORMAT ...` مع وجود البيانات داخل نص الاستعلام. أما `INSERT` الذي
يتوقع بياناته من تدفق منفصل فهو غير مدعوم.

<div id="local-mode-and-sql-security">
  ## الوضع المحلي و SQL SECURITY
</div>

من دون إعداد `cluster`، تُنفَّذ الاستعلامات على الخادم المحلي.
ويُحدَّد المستخدم الذي تُشَّغَل باسمه بواسطة بند `SQL SECURITY`:

* `INVOKER` (الافتراضي): تُشغَّل الاستعلامات نيابةً عن المستخدم الذي نفّذ عملية INSERT.
* `DEFINER`: تُشغَّل الاستعلامات نيابةً عن مستخدم `DEFINER` المحدد. ونظرًا لأن الاستعلامات المُدرَجة يمكن أن تكون اعتباطية، فإن منح `INSERT` على جدول من هذا النوع يُفوِّض جميع امتيازات المستخدم المعرَّف في `DEFINER`.
* `NONE`: تُشغَّل الاستعلامات بصلاحيات وصول كاملة، من دون مستخدم. ويتطلب ذلك امتياز `ALLOW_SQL_SECURITY_NONE` عند إنشاء الجدول.

<div id="cluster-mode">
  ## وضع العنقود
</div>

عند تحديد الإعداد `cluster`، تُرسَل الاستعلامات إلى العنقود المحدد.

تُحدَّد الشظية المستهدفة بواسطة `shard`: إمّا فهرس ثابت يبدأ من 1 (والقيمة الافتراضية هي `'1'`)، أو `'random'` لاختيار
شظية عشوائية لكل استعلام، أو `'all'` لتشغيل كل استعلام على جميع شظايا العنقود. وتُختار نسخة متماثلة داخل
الشظية وفقًا لإعداد `load_balancing` الخاص بالخادم.

يضبط العمود `database` قاعدة البيانات الافتراضية للاتصال بالخادم البعيد. وبما أن
قاعدة البيانات الافتراضية تُضبط مرة واحدة فقط لكل اتصال، فإن كل قيمة مميزة لـ `database` تستخدم
مجموعة اتصالات خاصة بها، تُنشأ عند أول استخدام ويُعاد استخدامها طوال عمر الجدول.

لا يكون لكلٍّ من `DEFINER` و `SQL SECURITY` تأثير إلا في الوضع المحلي، ويُعد الجمع بينهما وبين
الإعداد `cluster` خطأ. وعلى الخوادم البعيدة، تجري مصادقة الاستعلامات باستخدام
بيانات الاعتماد من إعدادات العنقود، وتُنفَّذ كاستعلامات أولية عادية: إذ تُسجَّل في
`system.query_log` مع `is_initial_query = 1` ومعرّف `query_id` خاص بها (غير مرتبط بعملية INSERT التي
أنتجتها). وعلى الخادم المُبادِر، تُسجَّل الاستعلامات المُرسلة في `system.query_log`
مع `is_internal = 1`.

ولأن المحرّك يتجاهل نتائج الاستعلامات، فإنه يُنفّذ دائمًا الاستعلامات المُرسلة باستخدام
`discard_query_data = 1`، لذا لا تُنقل بيانات نتائج استعلامات SELECT عبر الشبكة
(وهذا يتجاوز أي قيمة `discard_query_data` مُعيَّنة في العمود `settings`).

<div id="waiting-for-queries-to-finish">
  ## انتظار اكتمال الاستعلامات
</div>

في الوضع غير المتزامن، يمكن استخدام الاستعلام التالي للانتظار إلى أن يكتمل كل استعلام أُرسل إلى الجدول حتى الآن:

```sql
SYSTEM WAIT QUERY RUNNER runner;
```

<div id="example">
  ## مثال
</div>

إعادة تنفيذ أحدث استعلامات `SELECT` من سجل الاستعلامات:

```sql
INSERT INTO runner (query, database, settings)
SELECT query, current_database, Settings
FROM system.query_log
WHERE type = 'QueryFinish' AND is_initial_query AND NOT is_internal AND query_kind = 'Select'
  AND event_time > now() - INTERVAL 1 HOUR;
```
