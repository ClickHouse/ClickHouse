يخزّن نوع البيانات `Map(K, V)` أزواج المفتاح والقيمة.

على عكس قواعد البيانات الأخرى، لا تكون قيم Map فريدة في ClickHouse، أي يمكن أن يحتوي Map على عنصرين بالمفتاح نفسه.
(ويعود ذلك إلى أن Map يُنفَّذ داخليًا على هيئة `Array(Tuple(K, V))`.)

يمكنك استخدام الصياغة `m[k]` للحصول على قيمة المفتاح `k` في `m`.
كما أن `m[k]` يفحص Map، أي إن زمن تنفيذ هذه العملية يزداد خطيًا مع حجم Map.

**المعاملات**

* `K` — نوع مفاتيح Map. يمكن أن يكون أي نوع باستثناء [Nullable](../../sql-reference/data-types/nullable.md) و[LowCardinality](../../sql-reference/data-types/lowcardinality.md) المتداخل مع أنواع [Nullable](../../sql-reference/data-types/nullable.md).
* `V` — نوع قيم Map. يمكن أن يكون أي نوع.

**أمثلة**

أنشئ جدولًا يحتوي على عمود من النوع `Map`:

```sql title="Query"
CREATE TABLE tab (m Map(String, UInt64)) ENGINE=Memory;
INSERT INTO tab VALUES ({'key1':1, 'key2':10}), ({'key1':2,'key2':20}), ({'key1':3,'key2':30});
```

لاختيار القيم الخاصة بـ `key2`:

```sql title="Query"
SELECT m['key2'] FROM tab;
```

```text title="Response"
┌─arrayElement(m, 'key2')─┐
│                      10 │
│                      20 │
│                      30 │
└─────────────────────────┘
```

إذا لم يكن المفتاح المطلوب `k` موجودًا في الـ map، فإن `m[k]` تُرجع القيمة الافتراضية لنوع القيمة، مثل `0` للأنواع الصحيحة و`''` لأنواع String.
وللتحقق مما إذا كان المفتاح موجودًا في الـ map، يمكنك استخدام الدالة [mapContains](/ar/sql-reference/functions/tuple-map-functions#mapContainsKey).

```sql title="Query"
CREATE TABLE tab (m Map(String, UInt64)) ENGINE=Memory;
INSERT INTO tab VALUES ({'key1':100}), ({});
SELECT m['key1'] FROM tab;
```

```text title="Response"
┌─arrayElement(m, 'key1')─┐
│                     100 │
│                       0 │
└─────────────────────────┘
```

<div id="converting-tuple-to-map">
  ## تحويل Tuple إلى Map
</div>

يمكن إجراء تحويل للقيم من النوع `Tuple()` إلى قيم من النوع `Map()` باستخدام الدالة [CAST](/ar/sql-reference/functions/type-conversion-functions#CAST):

**مثال**

```sql title="Query"
SELECT CAST(([1, 2, 3], ['Ready', 'Steady', 'Go']), 'Map(UInt8, String)') AS map;
```

```text title="Response"
┌─map───────────────────────────┐
│ {1:'Ready',2:'Steady',3:'Go'} │
└───────────────────────────────┘
```

<div id="reading-subcolumns-of-map">
  ## قراءة الأعمدة الفرعية في Map
</div>

لتجنّب قراءة قيمة Map بالكامل، يمكنك في بعض الحالات استخدام العمودين الفرعيين `keys` و`values`.

**مثال**

```sql title="Query"
CREATE TABLE tab (m Map(String, UInt64)) ENGINE = Memory;
INSERT INTO tab VALUES (map('key1', 1, 'key2', 2, 'key3', 3));

SELECT m.keys FROM tab; --   same as mapKeys(m)
SELECT m.values FROM tab; -- same as mapValues(m)
```

```text title="Response"
┌─m.keys─────────────────┐
│ ['key1','key2','key3'] │
└────────────────────────┘

┌─m.values─┐
│ [1,2,3]  │
└──────────┘
```

<div id="bucketed-map-serialization">
  ## التسلسل المُقسَّم إلى buckets لبيانات Map في MergeTree
</div>

بشكل افتراضي، يُخزَّن عمود `Map` في MergeTree كتدفق `Array(Tuple(K, V))` واحد.
تتطلّب قراءة مفتاح واحد باستخدام `m['key']` فحص العمود بالكامل — أي كل key-value pair في كل row — حتى إذا كان المطلوب مفتاحًا واحدًا فقط.
وبالنسبة إلى maps التي تحتوي على عدد كبير من المفاتيح المميّزة، يصبح ذلك bottleneck.

يُقسِّم bucketed serialization (`with_buckets`) أزواج key-value إلى substreams مستقلة متعددة (buckets) عبر تطبيق hash على المفتاح.
وعندما يصل query إلى `m['key']`، لا يُقرأ من disk إلا الـ bucket التي تحتوي على ذلك المفتاح، مع skipping جميع الـ buckets الأخرى.

<div id="enabling-bucketed-serialization">
  ### تمكين التسلسل بالتقسيم إلى دلاء
</div>

```sql
CREATE TABLE tab (id UInt64, m Map(String, UInt64))
ENGINE = MergeTree ORDER BY id
SETTINGS
    map_serialization_version = 'with_buckets',
    max_buckets_in_map = 32,
    map_buckets_strategy = 'sqrt';
```

لتجنّب إبطاء عمليات insert، يمكنك الإبقاء على تسلسل `basic` للأجزاء من المستوى الصفري (التي تُنشأ أثناء `INSERT`) واستخدام `with_buckets` فقط مع الأجزاء المدمجة:

```sql
CREATE TABLE tab (id UInt64, m Map(String, UInt64))
ENGINE = MergeTree ORDER BY id
SETTINGS
    map_serialization_version = 'with_buckets',
    map_serialization_version_for_zero_level_parts = 'basic',
    max_buckets_in_map = 32,
    map_buckets_strategy = 'sqrt';
```

<div id="how-it-works">
  ### كيف يعمل
</div>

عند كتابة جزء بيانات باستخدام تسلسل `with_buckets`:

1. يُحسَب متوسط عدد المفاتيح لكل صف من إحصاءات الكتلة.
2. يُحدَّد عدد الحاويات وفقًا للاستراتيجية المُعدّة (راجع [الإعدادات](#bucketed-map-settings)).
3. يُسنَد كل زوج مفتاح-قيمة إلى حاوية عبر إجراء hash للمفتاح: `bucket = hash(key) % num_buckets`.
4. تُخزَّن كل حاوية كتدفق فرعي مستقل له مفاتيحه وقيمه وoffsets الخاصة به.
5. يسجّل تدفق البيانات الوصفية `buckets_info` عدد الحاويات والإحصاءات.

عندما يقرأ الاستعلام مفتاحًا محددًا (`m['key']`)، يعيد المُحسِّن كتابة التعبير إلى عمود فرعي للمفتاح (`m.key_<serialized_key>`).
وتحسب طبقة التسلسل الحاوية التي ينتمي إليها المفتاح المطلوب، ثم تقرأ تلك الحاوية وحدها من القرص.

عند قراءة قيمة Map بالكامل (مثلًا، `SELECT m`)، تُقرأ جميع الحاويات ويُعاد تجميعها إلى قيمة Map الأصلية. ويكون هذا أبطأ من تسلسل `basic` بسبب الحمل الإضافي الناتج عن قراءة عدة تدفقات فرعية ودمجها.

:::note
قد يختلف ترتيب المفاتيح داخل قيمة Map عن ترتيب الإدراج الأصلي عند استخدام تسلسل `with_buckets`. إذ تُوزَّع المفاتيح على الحاويات بواسطة hash، ثم يُعاد تجميعها وفق ترتيب الحاويات لا ترتيب الإدراج. ومع تسلسل `basic`، يُحفَظ ترتيب المفاتيح في قيم Map المُدرجة.
:::

يمكن أن يختلف عدد الحاويات بين الأجزاء. وعند دمج أجزاء ذات أعداد حاويات مختلفة، يُعاد احتساب عدد الحاويات في الجزء الجديد استنادًا إلى الإحصاءات المدمجة. ويمكن أن تتعايش الأجزاء ذات التسلسل `basic` و`with_buckets` في الجدول نفسه، كما تُدمَج بشفافية.

<div id="bucketed-map-settings">
  ### الإعدادات
</div>

| الإعداد                                          | الافتراضي | الوصف                                                                                                                                                                                                                                                                             |
| ------------------------------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `map_serialization_version`                      | `basic`   | تنسيق التسلسل لأعمدة `Map`. يخزّن `basic` البيانات كتدفّق `Array` واحد. ويقسّم `with_buckets` المفاتيح إلى حاويات لتسريع عمليات قراءة المفتاح الواحد.                                                                                                                             |
| `map_serialization_version_for_zero_level_parts` | `basic`   | تنسيق التسلسل للأجزاء ذات المستوى الصفري (التي ينشئها `INSERT`). يتيح الإبقاء على `basic` لعمليات الإدراج لتجنّب العبء الإضافي عند الكتابة، بينما تستخدم الأجزاء المدمجة `with_buckets`.                                                                                          |
| `max_buckets_in_map`                             | `32`      | الحد الأعلى لعدد الحاويات. يعتمد العدد الفعلي على `map_buckets_strategy`. والحد الأقصى المسموح به هو 256.                                                                                                                                                                         |
| `map_buckets_strategy`                           | `sqrt`    | الاستراتيجية المستخدمة لحساب عدد الحاويات استنادًا إلى متوسط حجم `Map`: `constant` — استخدم دائمًا `max_buckets_in_map`؛ `sqrt` — استخدم `round(coefficient * sqrt(avg_size))`؛ `linear` — استخدم `round(coefficient * avg_size)`. تُقيَّد النتيجة ضمن `[1, max_buckets_in_map]`. |
| `map_buckets_coefficient`                        | `1.0`     | المعامل المضاعِف لاستراتيجيتي `sqrt` و`linear`. ويُتجاهل عندما تكون الاستراتيجية `constant`.                                                                                                                                                                                      |
| `map_buckets_min_avg_size`                       | `32`      | الحد الأدنى لمتوسط عدد المفاتيح في كل صف لتفعيل التقسيم إلى حاويات. إذا كان المتوسط أقل من هذه العتبة، فستُستخدم حاوية واحدة بغض النظر عن الإعدادات الأخرى. اضبطه على `0` لتعطيل هذه العتبة.                                                                                      |

<div id="performance-trade-offs">
  ### مقايضات الأداء
</div>

يلخّص الجدول التالي أثر `with_buckets` على الأداء مقارنةً بتسلسل `basic` عند أحجام `map` مختلفة (من 10 إلى 10,000 مفتاح لكل صف). وقد حُدِّد عدد الـ bucket باستخدام استراتيجية `sqrt` بحد أقصى 32. وتعتمد الأرقام الدقيقة على أنواع المفتاح/القيمة، وتوزيع البيانات، والعتاد.

| العملية                                        | 10 مفاتيح            | 100 مفتاح            | 1,000 مفتاح          | 10,000 مفتاح         | ملاحظات                                                                                                                                                                                                         |
| ---------------------------------------------- | -------------------- | -------------------- | -------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **lookup لمفتاح واحد** (`m['key']`)            | أسرع بمقدار 1.6–3.2x | أسرع بمقدار 4.5–7.7x | أسرع بمقدار 16–39x   | أسرع بمقدار 21–49x   | يقرأ bucket واحدًا فقط بدلًا من العمود بالكامل.                                                                                                                                                                 |
| **5 عمليات lookup للمفاتيح**                   | ~1x                  | أسرع بمقدار 1.5–3.1x | أسرع بمقدار 2.9–8.3x | أسرع بمقدار 4.5–6.7x | يقرأ كل مفتاح الـ bucket الخاص به؛ وقد تتداخل بعض الـ bucket.                                                                                                                                                   |
| **PREWHERE** (`SELECT m WHERE m['key'] = ...`) | أسرع بمقدار 1.5–3.0x | أسرع بمقدار 2.9–7.3x | أسرع بمقدار 5.3–31x  | أسرع بمقدار 20–45x   | لا يقرأ مرشح PREWHERE إلا bucket واحدًا؛ ولا تُقرأ `map` كاملةً إلا للصفوف المطابقة. وتعتمد زيادة السرعة على الانتقائية — فكلما قلّ عدد الـ granules المطابقة، انخفضت عمليات الإدخال/الإخراج الكاملة للـ `map`. |
| **فحص `map` كاملًا** (`SELECT m`)              | أبطأ بنحو ~2x        | أبطأ بنحو ~2x        | أبطأ بنحو ~2x        | أبطأ بنحو ~2x        | يجب قراءة جميع الـ bucket وإعادة تجميعها.                                                                                                                                                                       |
| **INSERT**                                     | أبطأ بمقدار 1.5–2.5x | أبطأ بمقدار 1.5–2.5x | أبطأ بمقدار 1.5–2.5x | أبطأ بمقدار 1.5–2.5x | الحمل الإضافي الناتج عن تجزئة المفاتيح والكتابة إلى عدة substreams.                                                                                                                                             |

<div id="recommendations">
  ### التوصيات
</div>

* **الخرائط الصغيرة (أقل من 32 مفتاحًا في المتوسط):** أبقِ على التسلسل `basic`. لا تستدعي الخرائط الصغيرة الكلفة الإضافية للتقسيم إلى حاويات. وتفرض القيمة الافتراضية `map_buckets_min_avg_size = 32` ذلك تلقائيًا.
* **الخرائط المتوسطة (32–100 مفتاح):** استخدم `with_buckets` مع استراتيجية `sqrt` إذا كانت الاستعلامات تصل كثيرًا إلى مفاتيح فردية. تتراوح زيادة السرعة بين 4 و8 مرات في عمليات البحث عن مفتاح واحد.
* **الخرائط الكبيرة (100+ مفتاح):** استخدم `with_buckets`. تصبح عمليات البحث عن مفتاح واحد أسرع بمقدار 16–49 مرة. وفكّر في استخدام `map_serialization_version_for_zero_level_parts = 'basic'` للحفاظ على سرعة الإدراج قريبة من خط الأساس.
* **إذا كان الفحص الكامل للخريطة هو المسيطر على عبء العمل:** أبقِ على `basic`. يضيف التسلسل المعتمد على الحاويات كلفة إضافية تقارب الضعف عند الفحص الكامل.
* **عبء عمل مختلط (بعض عمليات البحث عن المفاتيح وبعض عمليات الفحص الكامل):** استخدم `with_buckets` مع ضبط zero-level parts على `basic`. لا يقرأ تحسين `PREWHERE` إلا الحاوية المرتبطة بشرط التصفية، ثم يقرأ الخريطة الكاملة فقط للصفوف المطابقة، ما يحقق تسارعًا إجماليًا ملحوظًا.

<div id="map-alternatives">
  ### الأساليب البديلة
</div>

إذا لم يكن تسلسل `Map` المقسّم إلى دلاء مناسبًا لحالة الاستخدام لديك، فهناك أسلوبان بديلان لتحسين أداء الوصول على مستوى المفاتيح:

<div id="using-the-json-data-type">
  #### استخدام نوع بيانات JSON
</div>

يخزّن [نوع بيانات JSON](/ar/sql-reference/data-types/newjson) كل مسار شائع كعمود فرعي ديناميكي منفصل. أمّا المسارات التي تتجاوز حد `max_dynamic_paths` فتنتقل إلى [بنية البيانات المشتركة](/ar/sql-reference/data-types/newjson#shared-data-structure)، والتي يمكن أن تستخدم التسلسل `advanced` لتحسين قراءة المسارات المفردة. راجع [منشور المدونة](https://clickhouse.com/blog/json-data-type-gets-even-better) للاطلاع على نظرة عامة مفصلة حول التسلسل `advanced`.

| الجانب              | `Map` مع buckets                                                                                       | `JSON`                                                                                                                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| قراءة مفتاح واحد    | يقرأ bucket واحدًا (وقد يحتوي على مفاتيح أخرى). ويُفك تسلسل جميع أزواج المفتاح-القيمة داخل الـ bucket. | تُقرأ المسارات الشائعة مباشرةً من الأعمدة الفرعية الديناميكية. أما المسارات غير الشائعة فتنتقل إلى البيانات المشتركة؛ ومع التسلسل `advanced` لا تُقرأ إلا بيانات المسار المطلوب تحديدًا. |
| أنواع القيم         | تشترك جميع القيم في النوع نفسه `V`                                                                     | يمكن أن يكون لكل مسار نوعه الخاص. والمسارات التي لا تحتوي على تلميح نوع تستخدم `Dynamic`.                                                                                                |
| دعم فهرس التخطي     | يعمل مع بعض أنواع الفهارس المُنشأة على `mapKeys`/`mapValues`                                           | لا يمكن إنشاء فهارس التخطي إلا على أعمدة فرعية لمسارات محددة، وليس على جميع المسارات/القيم دفعةً واحدة.                                                                                  |
| قراءة العمود الكامل | أبطأ بنحو ~2x من `basic` بسبب إعادة تجميع buckets                                                      | توجد كلفة إضافية ناتجة عن ترميز النوع `Dynamic` وإعادة بناء المسارات.                                                                                                                    |
| عبء التخزين         | حد أدنى من البيانات الوصفية الإضافية                                                                   | أعلى بسبب ترميز النوع `Dynamic`، وتخزين أسماء المسارات، وبيانات وصفية إضافية في التسلسل `advanced`.                                                                                      |
| مرونة المخطط        | أنواع المفاتيح والقيم ثابتة عند إنشاء الجدول                                                           | ديناميكي بالكامل — يمكن أن تختلف المفاتيح وأنواع القيم من صف إلى آخر. ويمكن التصريح بتلميحات أنواع لمسارات معروفة للوصول المباشر إلى الأعمدة الفرعية.                                    |

استخدم `JSON` عندما تحتاج المفاتيح المختلفة إلى أنواع قيم مختلفة، أو عندما تختلف مجموعة المفاتيح بشكل كبير بين الصفوف، أو عندما تكون المفاتيح التي يكثر الوصول إليها معروفة مسبقًا ويمكن التصريح بها كمسارات محددة النوع للوصول المباشر إلى الأعمدة الفرعية.

<div id="manual-sharding-into-multiple-map-columns">
  #### التقسيم اليدوي إلى عدة أعمدة من نوع Map
</div>

يمكنك تقسيم `Map` واحدًا يدويًا إلى عدة أعمدة استنادًا إلى تجزئة المفتاح على مستوى التطبيق:

```sql
CREATE TABLE tab (
    id UInt64,
    m0 Map(String, UInt64),
    m1 Map(String, UInt64),
    m2 Map(String, UInt64),
    m3 Map(String, UInt64)
) ENGINE = MergeTree ORDER BY id;
```

أثناء الإدراج، وجّه كل زوج مفتاح-قيمة إلى العمود `m{hash(key) % 4}`. وأثناء الاستعلامات، اقرأ من العمود المحدد: `m{hash('target_key') % 4}['target_key']`.

| الجانب                   | `Map` مع buckets                                 | التقسيم اليدوي                                                       |
| ------------------------ | ------------------------------------------------ | -------------------------------------------------------------------- |
| سهولة الاستخدام          | شفاف — يتولى محرك التخزين ذلك                    | يتطلب منطق توجيه على مستوى التطبيق لعمليات الإدراج وSELECT           |
| الدمج الرأسي             | غير مدعوم — جميع الـ buckets تنتمي إلى عمود واحد | مدعوم — كل عمود `Map` هو عمود مستقل ويمكن دمجه رأسيًا                |
| تغييرات المخطط           | يتكيف عدد الـ buckets تلقائيًا لكل part          | يتطلب تغيير عدد الـ shards إعادة كتابة البيانات أو إضافة أعمدة جديدة |
| صياغة الاستعلام          | `m['key']` تعمل مباشرة                           | يجب حساب العمود الصحيح: `m0['key']`، `m1['key']`، إلخ.               |
| مستوى التفصيل للـ bucket | لكل part، ويتكيف مع إحصاءات البيانات             | ثابت عند إنشاء table                                                 |

يكون التقسيم اليدوي مفيدًا عندما يكون الدمج الرأسي مهمًا لتقليل استخدام الذاكرة أثناء عمليات الدمج للجداول التي تحتوي على عدد كبير من columns، أو عندما يجب تثبيت عدد الـ shards والتحكم فيه صراحةً. وفي معظم حالات الاستخدام، تكون bucketed serialization التلقائية أبسط وكافية.
