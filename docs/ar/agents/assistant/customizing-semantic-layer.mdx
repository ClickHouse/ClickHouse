يمكنك تخصيص وكيل محادثة Assistant ليفهم منطق الأعمال الخاص بك وبنية بياناتك ومعرفتك المتخصصة بمجال عملك، وذلك عبر **AGENTS.md**، وهو استعلام محفوظ خاص يعمل بمثابة طبقة دلالية فوق تعليمة النظام الخاصة بالوكيل.

بإنشاء ملف AGENTS.md، يمكنك تقديم تعليمات مخصصة تُدرَج في بداية كل محادثة لتوجيه توليد استعلامات SQL وتحليل البيانات وفقاً لمتطلبات مؤسستك وحساباتها واصطلاحاتها الخاصة.

## آلية العمل {#how-it-works}

عند حفظ استعلام باسم &quot;AGENTS.md&quot; (حساس لحالة الأحرف) في وحدة تحكم السحابة:

1. يحمّل وكيل محادثة Assistant هذا الملف تلقائيًا عند إرسال أي رسالة
2. يُوضع المحتوى داخل وسم محتوى مهيكل، ثم يُضاف إلى تعليمة النظام الخاصة بالوكيل
3. تُطبَّق التعليمات على جميع محادثات Assistant في تلك الخدمة

## إنشاء AGENTS.md {#creating-agents-md}

<Steps>
  <Step title="إنشاء الاستعلام المحفوظ" id="create-query">
    1. في وحدة تحكم السحابة، أنشئ استعلامًا جديدًا
    2. سمِّه بالاسم التالي حرفيًا: **&quot;AGENTS.md&quot;** (حساس لحالة الأحرف)
    3. اكتب تعليماتك المخصصة في محرر نص الاستعلام (وليس استعلام SQL فعليًا)
    4. احفظ الاستعلام
  </Step>

  <Step title="إضافة تعليماتك" id="add-instructions">
    صُغ تعليماتك بلغة واضحة وقابلة للتنفيذ، على أن تتضمن ما يلي:

    * قواعد العمل والحسابات
    * إرشادات حول بنية البيانات
    * المصطلحات الخاصة بالمجال
    * أنماط الاستعلامات الشائعة
    * قواعد تحسين الأداء
  </Step>
</Steps>

## أفضل الممارسات {#best-practices}

### تعامل مع السياق بوصفه موردًا محدودًا {#finite-resource}

السياق ثمين؛ فكل رمز يستهلك جزءًا من «ميزانية الانتباه» لدى الوكيل. وكما يعاني البشر من محدودية الذاكرة العاملة، يتراجع أداء النماذج اللغوية كلما اتسع السياق. لذا ينبغي البحث عن **أصغر مجموعة ممكنة من الرموز عالية الدلالة** التي ترفع احتمالية تحقيق النتيجة المرجوة إلى أقصى حد.

### اختيار مستوى التفصيل المناسب {#right-altitude}

احرص على تحقيق التوازن بين طرفين متقابلين:

* **التحديد المفرط**: كتابة منطق if-else جامد بشكل ثابت في الموجّه، مما يجعله هشًّا ويزيد من تعقيد صيانته
* **الغموض المفرط**: توجيهات عامة لا تقدّم مؤشرات ملموسة، أو تفترض خطأً وجود سياق مشترك

المستوى الأمثل هو ما يكون محددًا بما يكفي لتوجيه السلوك بفعالية، ومرنًا بما يكفي في الوقت نفسه ليتمكن النموذج من تطبيق آليات استدلالية قوية. ابدأ بموجّه موجز على أفضل نموذج متاح، ثم أضف تعليمات واضحة بناءً على أنماط الإخفاق التي تلاحظها.

### التنظيم باستخدام أقسام مهيكلة {#structured-sections}

استخدم وسوم XML أو عناوين Markdown لإنشاء أقسام واضحة ومتمايزة يسهل تصفّحها:

```xml
<background_information>
Context about your data and domain
</background_information>

<calculation_rules>
Specific formulas and business logic
</calculation_rules>

<tool_guidance>
How to use specific ClickHouse features
</tool_guidance>
```

### قدِّم أمثلة متنوعة ونموذجية {#canonical-examples}

الأمثلة هي &quot;الصورة التي تغني عن ألف كلمة&quot;. فبدلًا من حشو الموجّه بكل حالة استثنائية ممكنة، انتقِ مجموعة مركّزة من الأمثلة المتنوعة التي تُجسّد السلوك المتوقع بوضوح.

### اجعلها موجزة ولكن شاملة {#minimal-complete}

* اقتصر على التعليمات التي يُحتاج إليها كثيرًا
* احرص على الإيجاز، فالسياق الأكبر يُضعف الأداء بسبب ما يُعرف بـ &quot;تآكل السياق&quot; (context rot)
* أزِل القواعد القديمة أو نادرة الاستخدام
* تأكد من توفير معلومات كافية لتوجيه السلوك المطلوب

<Tip>
  الإيجاز لا يعني بالضرورة القِصَر. فأنت بحاجة إلى قدر كافٍ من التفاصيل لضمان التزام الوكيل بالسلوك المتوقع، لكن تجنّب الإسهاب غير الضروري.
</Tip>

## مثال: مقاييس محسوبة من البيانات الخام {#example-calculated-metrics}

وجّه الوكيل عندما تتطلب المقاييس عمليات حسابية محددة بدلاً من الوصول المباشر إلى الأعمدة:

```xml
<metric_calculations>
IMPORTANT: "active_sessions" is NOT a column. It must be calculated.

To calculate active sessions:
COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions

This counts unique combinations of session and user identifiers.

When the user asks for "active sessions" or "session count", always use this formula:
SELECT
    date,
    COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions
FROM events
GROUP BY date;

</metric_calculations>
```

## مثال: قواعد منطق الأعمال {#example-business-logic}

حدِّد العمليات الحسابية والتصنيفات الخاصة بمجال عملك:

```xml
<business_rules>
Revenue Calculation:
- Exclude refunded transactions: WHERE transaction_status != 'refunded'
- Apply regional tax rates using CASE expressions
- Use MRR for subscriptions:
  SUM(CASE
    WHEN billing_cycle = 'monthly' THEN amount
    WHEN billing_cycle = 'yearly' THEN amount / 12
    ELSE 0
  END) AS mrr

Traffic Source Classification:
Use CASE expression to categorize:
CASE
  WHEN traffic_source IN ('google', 'bing', 'organic') THEN 'Organic Search'
  WHEN traffic_source IN ('facebook', 'instagram', 'social') THEN 'Social Media'
  WHEN traffic_source = 'direct' THEN 'Direct'
  ELSE 'Other'
END AS source_category

Customer Segmentation:
- Enterprise: annual_contract_value >= 100000
- Mid-Market: annual_contract_value >= 10000 AND annual_contract_value < 100000
- SMB: annual_contract_value < 10000

Always include these categorizations when generating traffic or revenue reports.
</business_rules>
```

## مثال: خصائص غير مألوفة في بنية البيانات {#example-data-quirks}

وثّق تنسيقات البيانات غير التقليدية أو القرارات القديمة المتعلقة بالمخطط:

```xml
<data_structure_notes>
The user_status column uses numeric codes, not strings:
- 1 = 'active'
- 2 = 'inactive'
- 3 = 'suspended'
- 99 = 'deleted'

When filtering or displaying user status, always use:
CASE user_status
  WHEN 1 THEN 'active'
  WHEN 2 THEN 'inactive'
  WHEN 3 THEN 'suspended'
  WHEN 99 THEN 'deleted'
END AS status_label

The product_metadata column contains JSON strings that must be parsed:
SELECT
    product_id,
    JSONExtractString(product_metadata, 'category') AS category,
    JSONExtractInt(product_metadata, 'inventory_count') AS inventory
FROM products;
</data_structure_notes>
```

## مثال: مصطلحات المجال {#example-terminology}

اربط مصطلحات الأعمال بتطبيقها التقني:

```xml
<terminology>
When users refer to "conversions", they mean:
- For e-commerce: transactions WHERE transaction_type = 'purchase'
- For SaaS: subscriptions WHERE subscription_status = 'active' AND first_payment_date IS NOT NULL

"Churn" is calculated as:
COUNT(DISTINCT user_id) WHERE last_active_date < today() - INTERVAL 90 DAY
AND previous_subscription_status = 'active'

"DAU" (Daily Active Users) means:
COUNT(DISTINCT user_id) WHERE activity_date = today()

"Qualified leads" must meet ALL criteria:
- lead_score >= 70
- company_size >= 50
- budget_confirmed = true
- contact_role IN ('Director', 'VP', 'C-Level')
</terminology>
```
