غالبًا ما تكون البيانات التشغيلية في SQL Server هي المصدر المرجعي المعتمد للطلبات والمدفوعات والمخزون، غير أن SQL Server ليس مصممًا لتنفيذ الاستعلامات التحليلية الثقيلة. في هذا الدليل، ستنسخ جدولًا من SQL Server نسخًا متماثلًا إلى ClickHouse عبر مسار تنفيذ الاستعلام المؤتمت: يحمّل Striim الصفوف الموجودة أولًا، ثم يبثّ كل عملية إدراج وتحديث وحذف لحظة وقوعها. وبعد ذلك، ستستعلم عن النتيجة في ClickHouse.

للاطلاع على شرح تفصيلي كامل، راجع [Introducing Automated Pipelines for Effortless Data Replication](https://www.striim.com/blog/automated-pipelines-5-0/).

يتطلب استخدام CDC (التقاط تغييرات البيانات) مع SQL Server الاشتراك في خطة **Premium** من Striim for ClickHouse.

## ما ستبنيه {#what-you-will-build}

SQL Server (`sales.orders`) &gt; التحميل الأولي عبر Striim، ثم CDC &gt; ClickHouse (`sales.orders`، `ReplacingMergeTree`)

## قبل أن تبدأ {#before-you-begin}

* خدمة Striim for ClickHouse قيد التشغيل ضمن خطة Premium (راجع [بدء الاستخدام](/ar/integrations/connectors/data-ingestion/etl-tools/striim/get-started)).
* مثيل SQL Server يمكن الوصول إليه من Striim، مع تشغيل SQL Server Agent، وصلاحية تمكين التقاط تغييرات البيانات. تنطبق الخطوات التالية على SQL Server المُشغَّل على جهاز افتراضي، وعلى Amazon RDS for SQL Server.
* خدمة ClickHouse، وقاعدة بيانات باسم `sales`، ومستخدم Striim يملك الامتيازات اللازمة، وملف تعريف اتصال ClickHouse.

## الخطوة 1: تجهيز SQL Server {#step-1-prepare-sql-server}

أنشئ قاعدة بيانات وجدولًا نموذجيًا يضم بضعة صفوف. هذه البيانات الأولية لأغراض التوضيح فقط، لتتمكن من إعادة تنفيذ المثال.

```sql
CREATE DATABASE salesdb;
GO
USE salesdb;
GO
CREATE SCHEMA sales;
GO
CREATE TABLE sales.orders (
  order_id    INT           NOT NULL PRIMARY KEY,
  customer_id INT           NOT NULL,
  status      VARCHAR(20)   NOT NULL,
  total       DECIMAL(10,2) NOT NULL,
  placed_at   DATETIME2     NOT NULL
);
INSERT INTO sales.orders VALUES
  (1, 101, 'NEW',     120.50, SYSDATETIME()),
  (2, 102, 'NEW',      75.00, SYSDATETIME()),
  (3, 103, 'NEW',     310.25, SYSDATETIME());
GO
```

فعّل التقاط تغييرات البيانات (CDC) على قاعدة البيانات، وأنشئ مستخدمًا لـ Striim. يفعّل Striim ميزة CDC على كل جدول محدَّد عند بدء تشغيل التطبيق.

<Tabs>
  <Tab title="SQL Server على جهاز افتراضي" id="enable-cdc-vm">
    ```sql
    USE salesdb;
    EXEC sys.sp_cdc_enable_db;
    ```
  </Tab>

  <Tab title="Amazon RDS for SQL Server" id="enable-cdc-rds">
    ```sql
    EXEC msdb.dbo.rds_cdc_enable_db 'salesdb';
    ```
  </Tab>
</Tabs>

أنشئ مستخدم Striim في قاعدة البيانات `salesdb`:

```sql
USE salesdb;
CREATE LOGIN striim WITH PASSWORD = '<strong password>';
CREATE USER striim FOR LOGIN striim;
EXEC sp_addrolemember @rolename = db_owner, @membername = striim;
```

يجب تمكين وضع مصادقة SQL Server لمستخدم Striim. وتوصي وثائق Striim بمنح مستخدم القارئ الدور `db_owner`. بعد بدء تشغيل مسار تنفيذ الاستعلام، يمكنك التحقق من أن CDC (التقاط تغييرات البيانات) نشط باستخدام `EXEC sys.sp_cdc_help_change_data_capture`. راجع [Configuring SQL Server to use MS SQL Reader](https://www.striim.com/docs/striimforclickhouse/en/configuring-sql-server-to-use-ms-sql-reader.html) للاطلاع على المتطلبات المسبقة الخاصة بالأجهزة الافتراضية على Azure وعلى مجموعات التوافر Always On.

## الخطوة 2: إنشاء مسار تنفيذ الاستعلام المؤتمت {#step-2-create-the-automated-pipeline}

1. في Striim، اختر **Apps &gt; Create an App**.
2. ابحث عن **SQL Server** واختره مصدرًا، ثم اختر **ClickHouse** هدفًا.
3. اختر **Get Started** ثم اختر مسار تنفيذ الاستعلام المؤتمت (التحميل الأولي مع CDC).
4. سمِّ مسار تنفيذ الاستعلام، مثل `SqlServerToClickHouse`، واختر مساحة الأسماء، ثم اختر **Next**.
5. أدخل بيانات الاتصال الخاصة بـ SQL Server: المضيف والمنفذ (`<host>:1433`)، واسم قاعدة البيانات `salesdb`، والمستخدم `striim`. اختر **Next**. يتحقق Striim عندئذٍ من صحة الاتصال. وإذا فشل التحقق، فاختر **Back** وصحّح الإعدادات؛ إذ لا يمكنك المتابعة دون اجتياز التحقق من الصحة.
6. اختر المخططات المراد نسخها نسخًا متماثلًا. اختر `sales`، ولا تختر مخططات النظام.
7. اختر الجداول المراد نسخها نسخًا متماثلًا من كل مخطط. اختر `orders`.
8. اختر ملف تعريف الاتصال الخاص بـ ClickHouse واضبط **Table Engine** على **`ReplacingMergeTree`**. يناسب هذا المحرك مصادر CDC التي ترسل صورة كاملة للصف عند كل تحديث.
9. يمكنك تعديل مطابقة الجداول إن أردت. تأكد من أن `sales.orders` يُطابَق مع `sales.orders` في ClickHouse.
10. راجع الإعدادات ثم اختر **Save &amp; Start**.

![مراجعة تهيئة مسار تنفيذ الاستعلام المؤتمت من SQL Server إلى ClickHouse](/images/integrations/striim/automated-pipeline-wizard.png)

*مثال على شاشة المراجعة في المعالج. في هذا الدليل، استخدم `salesdb` و`sales.orders` و`ReplacingMergeTree` كما هو موضح أعلاه.*

ينشئ Striim تطبيقين مرتبطين؛ إذ يُشغّل التحميل الأولي أولًا، ثم يوقفه بعد نسخ جميع الصفوف، وبعدها يبدأ تطبيق CDC تلقائيًا ويعرض أعداد الأحداث مع تدفق التغييرات. وإذا واجهت أيٌّ من المرحلتين مشكلة، يتوقف مسار تنفيذ الاستعلام ويعرض الإصلاحات الموصى بها.

![مراقبة تطبيق التقاط تغييرات البيانات قيد التشغيل](/images/integrations/striim/pipeline-monitoring.png)

<Warning>
  لا تنفّذ أوامر DDL على جداول المصدر أثناء تشغيل التحميل الأولي، وتأكد من أن SQL Server يحتفظ ببيانات التغييرات (مدة الاحتفاظ الافتراضية ثلاثة أيام) من بدء التحميل الأولي حتى يلحق تطبيق CDC بآخر التغييرات.
</Warning>

## الخطوة 3: التحقق من التحميل الأولي في ClickHouse {#step-3-verify-the-initial-load-in-clickhouse}

أنشأ Striim جدول الهدف باستخدام المحرك `ReplacingMergeTree` مع عمودين للبيانات الوصفية. افحص الجدول:

```sql
SHOW CREATE TABLE sales.orders;
```

استنادًا إلى مطابقة أنواع البيانات في Striim، يُتوقع أن يكون كلٌّ من `order_id` و`customer_id` من النوع `Int32`، و`status` من النوع `String`، و`total` من النوع `Decimal(10, 2)`، و`placed_at` من النوع `DateTime64`، فضلًا عن وجود العمودين `__STRIIM_VERSION` (`UInt64`) و`__STRIIM_ISDELETED` (`UInt8`)، مع `ENGINE = ReplacingMergeTree(__STRIIM_VERSION, __STRIIM_ISDELETED)` و`ORDER BY order_id`.

```sql
SELECT order_id, customer_id, status, total
FROM sales.orders FINAL
WHERE __STRIIM_ISDELETED = 0
ORDER BY order_id;
```

ستظهر لك الصفوف الثلاثة التي حُمِّلت من SQL Server.

## الخطوة 4: بث التغييرات {#step-4-stream-changes}

أجرِ بعض التغييرات في SQL Server:

```sql
USE salesdb;
UPDATE sales.orders SET status = 'SHIPPED' WHERE order_id = 2;
DELETE FROM sales.orders WHERE order_id = 3;
INSERT INTO sales.orders VALUES (4, 104, 'NEW', 42.00, SYSDATETIME());
```

شغّل الاستعلام نفسه في ClickHouse مرة أخرى. يُفترض أن تظهر الطلبات 1 و2 و4، وأن تكون حالة الطلب 2 هي `SHIPPED`، وألا يظهر الطلب 3. يُخزَّن الحذف على هيئة صف حذف منطقي. يستخدم الاستعلام `FINAL` لاختيار أحدث إصدار، و`__STRIIM_ISDELETED = 0` لاستبعاد الصفوف المحذوفة. يُحتفظ بوسوم الحذف افتراضيًا، ولا تضمن عمليات الدمج في الخلفية وحدها إزالتها فعليًا. راجع [`ReplacingMergeTree`](/ar/reference/engines/table-engines/mergetree-family/replacingmergetree#is_deleted) لمعرفة آلية التنظيف. يمكنك أيضًا متابعة أعداد الأحداث وحداثة البيانات في الهدف من خلال عرض المراقبة في Striim، أو سؤال Clara عن مقدار التأخر الحالي.

## إنشاء مسار تنفيذ الاستعلام نفسه باستخدام Striim Clara {#build-the-same-pipeline-with-striim-clara}

بدلاً من استخدام المعالج، يمكنك وصف مسار تنفيذ الاستعلام في الصفحة الرئيسية، على سبيل المثال: «أنشئ مسار تنفيذ الاستعلام من SQL Server إلى ClickHouse مع التحميل الأولي والتقاط تغييرات البيانات للجدول sales.orders». تطلب منك Clara بيانات الاتصال، ثم تُنشئ خطة TQL، ولا تنشرها إلا بعد أن تختار **Accept TQL**.

## التنظيف {#clean-up}

* أوقف تطبيقَي Striim وألغِ نشرهما من صفحة Apps.
* يواصل SQL Server التقاط بيانات التغييرات حتى بعد إلغاء نشر تطبيقَي Striim إذا كانت إعدادات القارئ الافتراضية مستخدمة. لإيقاف التقاط البيانات في هذا المثال، شغّل `sys.sp_cdc_disable_table` على `sales.orders`، أو `sys.sp_cdc_disable_db` إذا لم تكن هناك جداول أخرى في قاعدة البيانات تحتاج إلى CDC. لمزيد من التفاصيل، راجع [وثائق](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sys-sp-cdc-disable-table-transact-sql) SQL Server. ويمكنك بدلًا من ذلك اتباع [إجراء Auto Disable Table CDC](https://www.striim.com/docs/striimforclickhouse/en/sql-server-operational-considerations.html) الخاص بـ Striim.
* احذف الجداول النموذجية في كلا النظامين: `DROP TABLE sales.orders;`.
