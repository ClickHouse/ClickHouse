سيُشرح تكامل مكتبات Rust بالاستناد إلى تكامل دالة التجزئة BLAKE3.

تتمثل الخطوة الأولى في التكامل في إنشاء مشروع Rust فارغ في `contrib/<library>-cmake` وإضافة المكتبة المطلوبة إلى ملف Cargo.toml الخاص به. ويكون هذا المشروع عضوًا في مساحة عمل cargo الموجودة في `contrib/rust-contrib-workspace`: أضف `workspace = "../rust-contrib-workspace"` ضمن `[package]`، وأدرج المجلد ضمن `members` في `contrib/rust-contrib-workspace/Cargo.toml`. أبقِه مكتبة عادية، دون `crate-type`. لا تُبنى الأعضاء كمكتبات مستقلة: فالحزمة الجذر لمساحة العمل، `_ch_rust_workspace`، تعيد تصدير كل عضو مفعّل، وهي المكتبة الثابتة الوحيدة التي يربطها ClickHouse. في `contrib/rust-contrib-workspace/Cargo.toml`، أضف إلى الحزمة الجذر ميزة وتبعية اختيارية للعضو (`blake3 = ["dep:_ch_rust_blake3"]` و`_ch_rust_blake3 = { path = "../blake3-cmake", optional = true }`)، ثم أعد تصديره في `contrib/rust-contrib-workspace/src/lib.rs` (`#[cfg(feature = "blake3")] pub use _ch_rust_blake3;`).

بعد ذلك، تحتاج إلى ربط المكتبة بـ CMake باستخدام مكتبة Corrosion. تتمثل الخطوة الأولى في إضافة مجلد المكتبة إلى `contrib/CMakeLists.txt` باستخدام `add_contrib`، بجوار الأعضاء الآخرين في مساحة العمل. بعد ذلك، ينبغي إضافة ملف CMakeLists.txt إلى مجلد المكتبة. وفي هذا الملف، تحتاج إلى إضافة العضو باستخدام `clickhouse_add_rust_member`: إذ تنشئ هدفًا من نوع INTERFACE يربط المكتبة الثابتة لمساحة العمل، وتفعّل ميزة الحزمة الجذر التي يستوردها `contrib/rust-contrib-workspace/CMakeLists.txt` باستخدام Corrosion بعد جميع الأعضاء. بالنسبة إلى BLAKE3، ستكون الأسطر كما يلي:

```CMake
clickhouse_add_rust_member(_ch_rust_blake3 FEATURE blake3)

target_include_directories(_ch_rust_blake3 INTERFACE include)
add_library(ch_rust::blake3 ALIAS _ch_rust_blake3)
```

وبذلك، سننشئ هدف CMake لهذا العضو، ثم نمنحه اسمًا أكثر ملاءمة. لاحظ أن الاسم `_ch_rust_blake3` يأتي من Cargo.toml، حيث يُستخدم بوصفه اسم المشروع (`name = "_ch_rust_blake3"`).

ونظرًا لأن أنواع البيانات في Rust غير متوافقة مع أنواع البيانات في C/C++، فسنستخدم مشروع المكتبة الفارغ لدينا لإنشاء أساليب المواءمة لتحويل البيانات المستلمة من C/C++، واستدعاء دوال المكتبة، وإجراء التحويل العكسي لبيانات الإخراج. على سبيل المثال، كُتبت هذه الدالة لـ BLAKE3:

```rust
#[no_mangle]
pub unsafe extern "C" fn blake3_apply_shim(
    begin: *const c_char,
    _size: u32,
    out_char_data: *mut u8,
```

```rust
#[no_mangle]
pub unsafe extern "C" fn blake3_apply_shim(
    begin: *const c_char,
    _size: u32,
    out_char_data: *mut u8,
) -> *mut c_char {
    if begin.is_null() {
        let err_str = CString::new("input was a null pointer").unwrap();
        return err_str.into_raw();
    }
    let mut hasher = blake3::Hasher::new();
    let input_bytes = CStr::from_ptr(begin);
    let input_res = input_bytes.to_bytes();
    hasher.update(input_res);
    let mut reader = hasher.finalize_xof();
    reader.fill(std::slice::from_raw_parts_mut(out_char_data, blake3::OUT_LEN));
    std::ptr::null_mut()
}
```

تأخذ هذه الدالة سلسلة متوافقة مع C، وحجمها، ومؤشر سلسلة الإخراج كمدخلات. ثم تحوّل المدخلات المتوافقة مع C إلى الأنواع التي تستخدمها دوال المكتبة الفعلية وتستدعيها. بعد ذلك، ينبغي تحويل مخرجات دوال المكتبة مرة أخرى إلى نوع متوافق مع C. في هذه الحالة تحديدًا، كانت المكتبة تدعم الكتابة المباشرة إلى المؤشر عبر الدالة fill()، لذلك لم تكن هناك حاجة إلى هذا التحويل. والنصيحة الأساسية هنا هي تقليل عدد الدوال التي تنشئها، حتى تقلّ التحويلات المطلوبة عند كل استدعاء، ولا تضيف عبئًا إضافيًا كبيرًا.

ومن الجدير بالذكر أن attribute `#[no_mangle]` و`extern "C"` إلزاميتان لجميع هذه الدوال. وبدونهما، لن يكون من الممكن إجراء عملية build صحيحة متوافقة مع C/C++. وإضافة إلى ذلك، فهما ضروريتان للخطوة التالية من التكامل.

بعد كتابة الشيفرة الخاصة بأساليب المواءمة، نحتاج إلى إعداد ملف الترويسة للمكتبة. يمكن تنفيذ ذلك يدويًا، أو يمكنك استخدام مكتبة cbindgen للتوليد التلقائي. وفي حال استخدام cbindgen، ستحتاج إلى كتابة برنامج نصي build.rs للبناء وإضافة cbindgen كتبعية بناء.

مثال على برنامج نصي للبناء يمكنه توليد ملف ترويسة تلقائيًا:

```rust
    let crate_dir = env::var("CARGO_MANIFEST_DIR").unwrap();

    let package_name = env::var("CARGO_PKG_NAME").unwrap();
    let output_file = ("include/".to_owned() + &format!("{}.h", package_name)).to_string();

    match cbindgen::generate(&crate_dir) {
        Ok(header) => {
            header.write_to_file(&output_file);
        }
        Err(err) => {
            panic!("{}", err)
        }
    }
```

## توليد ملف الترويسة في هذا المستودع {#generating-the-header-in-this-repository}

يكتب البرنامج النصي للبناء أعلاه ملف الترويسة في شجرة المصدر مع كل عملية بناء، فلا يبقى بذلك ما يمكن فحصه: إذ إن ملف الترويسة المُثبَّت الذي لم يعد يطابق جانب Rust يُستبدَل ببساطة محليًا ويظل خاطئًا لدى الجميع. لذلك تعتمد حزم Rust هنا أحد أسلوبين بدلًا من ذلك:

* توليد ملف الترويسة داخل دليل البناء وتوجيه `target_include_directories` إليه، كما يفعل `contrib/delta-kernel-rs`. لا يُثبَّت أي شيء، وبالتالي لا يمكن أن يصبح أي شيء متقادمًا؛
* تثبيت ملف الترويسة وجعل البرنامج النصي للبناء يقارنه بالملف المولَّد حديثًا، مع إفشال البناء عند اختلافهما، كما يفعل `contrib/vortex-cmake`. فنصفا واجهة FFI وحدتا ترجمة منفصلتان تُربطان عبر أسماء الرموز، لذا فإن تغيير توقيع الدالة في جانب واحد فقط يؤدي إلى سلوك غير محدد صامت بدلًا من خطأ في التصريف، والمقارنة هي ما يجعل نسيان إعادة التوليد أمرًا مستحيلًا. احتفظ بمتغير بيئة يعيد كتابة الملف المُثبَّت، كي يظل تحديثه ممكنًا بأمر واحد.

أمران ينبغي معرفتهما قبل إضافة `cbindgen` إلى حزمة Rust ضمن `contrib/rust-contrib-workspace`:

* ثبّت الإصدار بدقة. فمخرجاته تتغير بين إصدارات التصحيح، ومع متطلب إصدار غير صارم يبدأ الفحص في الإبلاغ عن اختلاف إصدار المولّد بدلًا من فرق حقيقي. ويجب أيضًا أن يكون الإصدار من الإصدارات المتوفرة في `contrib/rust_vendor`، وإلا فسيلزم إعادة تشغيل `contrib/rust-contrib-workspace/vendor.sh` وتحديث الوحدة الفرعية؛
* حلّل ملف المصدر باستخدام `Builder::with_src` بدلًا من تحليل الحزمة باستخدام `cbindgen::generate`. فمسار الحزمة يجعل cbindgen يشغّل `cargo metadata` في عملية متداخلة، ولا ترث تلك العملية `--config` الذي يوجّه cargo إلى المصادر المضمّنة محليًا.

بالإضافة إلى ذلك، يجب استخدام attribute #[no&#95;mangle] و`extern "C"` لكل attribute متوافق مع C. فبدونها قد تُصرَّف المكتبة بشكل غير صحيح، ولن يبدأ cbindgen التوليد التلقائي لملف الترويسة.

بعد كل هذه الخطوات، يمكنك اختبار مكتبتك ضمن مشروع صغير لاكتشاف أي مشكلات في التوافق أو في توليد ملفات الترويسة. وإذا ظهرت أي مشكلات أثناء توليد ملفات الترويسة، فيمكنك محاولة ضبطه باستخدام ملف `cbindgen.toml` (يمكنك العثور على قالب هنا: [https://github.com/eqrion/cbindgen/blob/master/template.toml](https://github.com/eqrion/cbindgen/blob/master/template.toml)).

ومن المفيد الإشارة إلى المشكلة التي ظهرت عند دمج BLAKE3:
قد يتسبب MemorySanitizer في ظهور تقارير إيجابية كاذبة، لأنه لا يستطيع معرفة ما إذا كانت بعض المتغيرات في Rust مهيأة أم لا. وقد حُلَّت هذه المشكلة بكتابة دالة ذات تعريف أكثر صراحةً لبعض المتغيرات، رغم أن هذا التنفيذ للدالة أبطأ ويُستخدم فقط لمعالجة عمليات بناء MemorySanitizer.
