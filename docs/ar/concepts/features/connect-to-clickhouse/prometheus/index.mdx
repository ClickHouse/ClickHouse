يوفّر ClickHouse تنفيذًا لواجهة برمجة تطبيقات HTTP لـ Prometheus فوق جدول [`TimeSeries`](/ar/reference/engines/table-engines/integrations/time-series)، إذ يتولى معالج واحد كلًّا من الكتابة عن بُعد، والقراءة عن بُعد، واستعلامات PromQL الآنية، واستعلامات PromQL للنطاق.

لإتاحة مقاييس ClickHouse نفسه كي يسحبها خادم Prometheus، راجع [نقطة نهاية مقاييس Prometheus](/ar/concepts/features/connect-to-clickhouse/prometheus/metrics).

## المتطلبات المسبقة {#prerequisites}

تختلف خطوات الإعداد بين ClickHouse Cloud وClickHouse المُدار ذاتيًا. اتبع القسم الذي يناسب طريقة النشر لديك.

### ClickHouse Cloud {#prerequisites-cloud}

<Note>
  يتوفر دعم PromQL في ClickHouse Cloud ضمن المعاينة الخاصة. وتأتي الخدمات المشاركة في المعاينة الخاصة مهيأة مسبقًا بالإعداد `enable_time_series_table` وبنقاط نهاية API الخاصة بـ Prometheus. أما خدمات ClickHouse Cloud الأخرى فلا تتضمن هذه التهيئة، ولا يمكنك تمكين هذه الميزة بنفسك على أي منها. وتنطبق العبارة `SET enable_time_series_table` والتهيئة `http_handlers` الواردتان في الأقسام التالية على عمليات النشر المُدارة ذاتيًا فقط.
</Note>

إذا كانت خدمتك مشاركة في المعاينة الخاصة، فانتقل مباشرةً إلى [إنشاء جدول TimeSeries](#create-a-timeseries-table). إذ توفّر الخدمة مسارات نقاط النهاية المدرجة في [جدول نقاط النهاية](#configure-prometheus-api).

### البيئة المُدارة ذاتيًا: تمكين إعداد TimeSeries {#enable-the-timeseries-setting}

مكِّن الإعداد `enable_time_series_table` للمستخدم الذي يُنشئ الجدول ويصل إليه:

```sql
SET enable_time_series_table = 1;
```

لإرسال طلبات API عبر HTTP، فعّل `enable_time_series_table` في ملف تعريف مستخدم واجهة برمجة التطبيقات.

### النشر المُدار ذاتيًا: تهيئة نقاط نهاية API الخاصة بـ Prometheus {#configure-prometheus-api}

هيّئ معالجًا واحدًا يعتمد التوجيه حسب البادئة على منفذ HTTP الرئيسي في ClickHouse:

```xml
<http_handlers>
    <defaults/>
    <rule>
        <url_prefix>/prometheus/api/v1</url_prefix>
        <handler>
            <type>prometheus_api_v1</type>
        </handler>
    </rule>
</http_handlers>
```

يحافظ `<defaults/>` على معالجات الطلبات المدمجة لنقاط نهاية مثل `/ping` ولطلبات SQL. وتتيح البادئة أعلاه نقاط النهاية التالية عبر معالج واحد:

| نقطة النهاية                             | الغرض                              |
| ---------------------------------------- | ---------------------------------- |
| `/prometheus/api/v1/write`               | الكتابة عن بُعد في Prometheus      |
| `/prometheus/api/v1/read`                | القراءة عن بُعد في Prometheus      |
| `/prometheus/api/v1/query`               | استعلامات PromQL الآنية           |
| `/prometheus/api/v1/query_range`         | استعلامات PromQL ذات النطاق الزمني |
| `/prometheus/api/v1/format_query`        | تنسيق تعبيرات PromQL               |
| `/prometheus/api/v1/series`              | البيانات الوصفية لسلاسل البيانات   |
| `/prometheus/api/v1/labels`              | أسماء الوسوم                       |
| `/prometheus/api/v1/label/<name>/values` | قيم الوسوم                         |
| `/prometheus/api/v1/metadata`            | البيانات الوصفية لعائلات المقاييس  |
| `/prometheus/api/v1/federate`            | الاتحاد لأحدث العينات              |

لا يحدّد المثال `database` و`table` في المعالج، لذا يجب أن يتضمّن كل طلب مَعلمة الاستعلام `table` (باستثناء `/format_query`، إذ تقتصر على تحليل تعبير PromQL المُمرَّر ولا تحتاج إلى جدول). ويمكن للطلب أيضًا تحديد `database`، أو استخدام اسم جدول مؤهَّل مثل `prometheus.metrics`، أو عدم تحديد قاعدة البيانات لاستخدام `default`. وبذلك يمكن لمعالج واحد أن يخدم عدة جداول `TimeSeries`.

لاستخدام جدول ثابت واحد لجميع الطلبات، قم بتهيئته في المعالج:

```xml
<handler>
    <type>prometheus_api_v1</type>
    <database>prometheus</database>
    <table>metrics</table>
</handler>
```

لا يمكن لمعلمات الطلب استبدال الجدول الذي تمت تهيئته في المعالج.

إعدادات التوجيه والمعالج:

| الاسم        | القيمة الافتراضية | الوصف                                                                                                                                                                                     |
| ------------ | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url_prefix` | none              | قاعدة عامل تصفية تطابق كل مسار طلب يبدأ بالبادئة التي تمت تهيئتها.                                                                                                                        |
| `table`      | none              | اسم جدول من نوع `TimeSeries`. إذا لم يُحدَّد، فيجب أن يتضمن الطلب مَعلمة الاستعلام `table`. ويمكن أن يتضمن الاسم الذي تمت تهيئته اسم قاعدة البيانات.                                      |
| `database`   | none              | قاعدة البيانات التي تحتوي على الجدول. ويمكن للطلب تحديدها كمَعلمة استعلام. إذا لم تُحدَّد، يستخدم ClickHouse قاعدة البيانات الواردة في قيمة `table` المؤهلة، أو يلجأ إلى `default` كبديل. |

### إنشاء جدول TimeSeries {#create-a-timeseries-table}

أنشئ قاعدة بيانات وجدولًا من نوع `TimeSeries`:

```sql
CREATE DATABASE prometheus;
CREATE TABLE prometheus.metrics ENGINE = TimeSeries;
```

## استيعاب بيانات المقاييس عبر الكتابة عن بُعد {#remote-write}

يدعم ClickHouse [بروتوكول Prometheus remote-write](https://prometheus.io/docs/specs/remote_write_spec/). هيّئ Prometheus ليكتب إلى المعالج:

```yaml
remote_write:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/write?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

يرسل Prometheus العينات إلى الجدول `prometheus.metrics`.

لتجميع البيانات الواردة من طلبات remote-write المتزامنة العديدة في عدد أقل من أجزاء البيانات، يستخدم ClickHouse [عمليات الإدراج غير المتزامنة](/ar/reference/settings/session-settings/async-insert#async_insert). وهي مفعّلة افتراضيًا، ويتحكم الإعداد `async_insert` في عنوان URL (أو في ملف تعريف المستخدم) في تفعيلها أو تعطيلها.

لا يؤكد ClickHouse استلام طلب remote-write غير متزامن إلا بعد تفريغ البيانات إلى جميع الجداول الداخلية للجدول `TimeSeries`، بصرف النظر عن قيمة الإعداد [`wait_for_async_insert`](/ar/reference/settings/session-settings/wait-for#wait_for_async_insert)؛ إذ يعدّ بروتوكول remote-write أي عملية كتابة تم تأكيد استلامها عمليةً دائمة. وإذا فشل التفريغ، يُعيد الطلب error ويعيد Prometheus محاولة إرساله.

ولأن كل طلب ينتظر اكتمال تفريغه، فإن عمليات الإدراج غير المتزامنة تحدّ من سرعة الكتابة لدى المُرسِل الواحد. يرسل Prometheus طلبًا واحدًا في كل مرة لكل مقطع remote-write. وعندما ترسل عدة مقاطع في الوقت نفسه، تزداد مهلة التفريغ التكيفية حتى تبلغ [`async_insert_busy_timeout_max_ms`](/ar/reference/settings/session-settings/async-insert#async_insert_busy_timeout_max_ms)، ما لم تبلغ الطلبات قيد الانتظار الحد [`async_insert_max_data_size`](/ar/reference/settings/session-settings/async-insert#async_insert_max_data_size) أولًا. وينتظر الطلب حتى تُفرَّغ دفعته، وهو ما يحدث خلال تلك المدة كحدٍّ أقصى من بدء الدفعة؛ لذا يكتب كل مقطع تحت الحمل المستمر ما يقارب `samples per request / async_insert_busy_timeout_max_ms`، علمًا بأن Prometheus يرسل افتراضيًا ما يصل إلى 2,000 عينة لكل طلب. ولزيادة هذا المعدل:

* ارفع قيمة `max_shards` (القيمة الافتراضية 50) أو `max_samples_per_send` في `queue_config` ضمن [`remote_write`](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#remote_write). ويضيف Prometheus مقاطع من تلقاء نفسه عندما يتأخر، حتى يبلغ `max_shards`.
* اخفض قيمة `async_insert_busy_timeout_max_ms` في عنوان URL أو في ملف تعريف المستخدم، مثل `&async_insert_busy_timeout_max_ms=50`. وبذلك تتكرر عمليات التفريغ أكثر، وتُنشئ كل عملية تفريغ أجزاء بيانات جديدة في الجداول الداخلية.
* عطّل عمليات الإدراج غير المتزامنة باستخدام `async_insert=0`. وبذلك يُنشئ كل طلب أجزاء البيانات الخاصة به في الجداول الداخلية.

## الاستعلام باستخدام PromQL {#promql-query-support}

استخدم نقطة نهاية الاستعلام الفوري (instant-query) لتقييم تعبير PromQL في لحظة زمنية واحدة:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

استخدم نقطة نهاية استعلام النطاق (range-query) لتقييم تعبير ضمن نطاق زمني:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

تقبل نقاط نهاية الاستعلامات المعلمات أيضًا ضمن متن نموذج. وبدون الخيار `--get`، يرسل curl المعلمات بترميز `application/x-www-form-urlencoded` عبر `POST`:

```bash
curl --user default:<password> \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query_range" \
  --data-urlencode "query=rate(http_requests_total[5m])" \
  --data-urlencode "start=2026-08-15T12:00:00Z" \
  --data-urlencode "end=2026-08-15T13:00:00Z" \
  --data-urlencode "step=60s" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

استخدم نقطة النهاية format-query لتحليل تعبير PromQL وتنسيقه دون تقييمه:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/format_query" \
  --data-urlencode "query=sum by(job)(http_requests_total{code=\"200\"})/2"
```

يُعاد التعبير بصيغة مُسلسَلة من الاستعلام المُحلَّل نحويًا، بعد توحيد صيغة المسافات البيضاء، وإزالة التعليقات، وحذف الأقواس الزائدة، وكتابة المدد بالوحدات التي يقبلها المحلل النحوي: `sum by (job) (http_requests_total{code="200"}) / 2`. تحتفظ المدة بوحداتها ولا تُحوَّل إلى عدد من الثواني، لذا يُعاد `rate(x[5m])` بالشكل `rate(x[5m])`. أما المدة التي لا تساوي عددًا صحيحًا من وحدة واحدة فتُكتب بكل الوحدات اللازمة لها، لذا يُعاد `rate(x[90s])` بالشكل `rate(x[1m30s])`. ولأن نقطة النهاية هذه لا تُقيّم التعبير، فهي لا تحتاج إلى المعلمتين `database` و`table`.

راجع [ميزات PromQL المدعومة](/ar/reference/functions/table-functions/prometheusQueryRange#supported-promql-features) للاطلاع على قائمة الدوال ومشغّلات التجميع المستخدمة في واجهة برمجة تطبيقات HTTP، ولهجة `promql`، ودالات الجداول.

### Grafana {#grafana}

هيّئ مصدر بيانات prometheus بحيث ينتهي عنوان URL الأساسي قبل المقطع `/api/v1`:

```yaml
apiVersion: 1
datasources:
  - name: ClickHouse Prometheus
    type: prometheus
    access: proxy
    url: https://clickhouse.example.com:8443/prometheus
    basicAuth: true
    basicAuthUser: default
    jsonData:
      httpMethod: POST
      customQueryParameters: database=prometheus&table=metrics
    secureJsonData:
      basicAuthPassword: <password>
```

يُلحق Grafana المسار `/api/v1/query` أو `/api/v1/query_range` بعنوان URL الأساسي هذا، ويضيف `customQueryParameters` إلى كل طلب.

عند استخدام `httpMethod: POST`، يرسل Grafana معلمات الاستعلام في جسم الطلب. ونظرًا لأن ClickHouse يقرأ جسم الطلب وسلسلة استعلام URL معًا، تظل `customQueryParameters` سارية. استخدم `POST` مع تعبيرات PromQL الطويلة، لأن طول عنوان URL محدود.

<Note>
  لم يُنفَّذ سوى نقاط نهاية الاستعلامات `/api/v1/query` و`/api/v1/query_range` و`/api/v1/format_query`، ونقاط نهاية البيانات الوصفية `/api/v1/series` و`/api/v1/labels` و`/api/v1/label/<name>/values` و`/api/v1/metadata`، ونقطة نهاية [الاتحاد](#federation) `/api/v1/federate`. تتطلب `/api/v1/series` محدِّد سلاسل بيانات واحدًا على الأقل من نوع `match[]`، وتدعم المعلمات الاختيارية `start` و`end` و`limit`، وتُعيد اتحاد سلاسل البيانات المطابقة لكل محدِّد. وتقبل `/api/v1/labels` المعلمات نفسها، إلا أن `match[]` فيها اختيارية، وتُعيد أسماء الوسوم مرتّبةً لسلاسل البيانات المطابقة (أو لجميع سلاسل البيانات إذا لم تُحدَّد أي محدِّدات). أما `/api/v1/label/<name>/values` فتقبل المعلمات نفسها التي تقبلها `/api/v1/labels`، وتُعيد قيم وسم واحد مرتّبةً، ويمكن أن يستخدم `<name>` اختياريًا صيغة الإفلات `U__...` الخاصة بـ Prometheus لأسماء الوسوم التي تحتوي على محارف خارج النطاق `[a-zA-Z0-9_]`. وتغطي نقاط النهاية هذه كل ما يحتاجه مصدر بيانات Prometheus في Grafana لتصفح الوسوم، ومتغيرات القوالب، والإكمال التلقائي في منشئ الاستعلامات.
</Note>

### نقاط الدخول في SQL {#sql-entry-points}

يستخدم ClickHouse محوّل PromQL نفسه في واجهة برمجة تطبيقات HTTP، ولهجة `promql`، ودالتَي الجدول [`prometheusQuery`](/ar/reference/functions/table-functions/prometheusQuery) و[`prometheusQueryRange`](/ar/reference/functions/table-functions/prometheusQueryRange).

شغّل استعلامات PromQL مباشرةً باستخدام `clickhouse-client`:

```bash
clickhouse-client \
  --dialect promql \
  --promql_database prometheus \
  --promql_table metrics \
  --query 'rate(http_requests_total[5m])'
```

استخدم دالات الجداول لتضمين PromQL في استعلام SQL:

```sql
SELECT *
FROM prometheusQuery(
    prometheus.metrics,
    'rate(http_requests_total[5m])',
    now()
);
```

## الاستعلام عن البيانات الوصفية للمقاييس {#metadata}

تعيد نقطة النهاية `/prometheus/api/v1/metadata` البيانات الوصفية للمقاييس المخزَّنة في جدول الهدف `Metrics` التابع لجدول `TimeSeries`، وتشمل النوع والنص التوضيحي والوحدة لكل عائلة مقاييس. وتدعم معلمات Prometheus التالية في سلسلة استعلام URL:

| المعلمة            | الوصف                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `metric`           | إرجاع البيانات الوصفية لعائلة المقاييس هذه فقط.                                                                                 |
| `limit`            | تحديد الحد الأقصى لعدد عائلات المقاييس المُعادة. تعني القيمة السالبة عدم وجود حد أقصى؛ أما الصفر فلا تُعاد معه أي عائلة مقاييس. |
| `limit_per_metric` | تحديد الحد الأقصى لعدد كائنات البيانات الوصفية المُعادة لكل عائلة مقاييس. تعني القيم الصفرية والسالبة عدم وجود حد أقصى.         |

جدول الهدف الافتراضي `Metrics` هو جدول يستخدم محرك `ReplacingMergeTree` ومُرتَّب حسب اسم عائلة المقاييس، ويحتفظ بأحدث إدخال بيانات وصفية كُتب لكل عائلة مقاييس. ولا تُعاد إدخالات متعددة لكل عائلة إلا ما دام جدول الهدف يحتفظ بها — أي قبل دمج أجزاء البيانات فيه، أو عندما يكون الجدول مُعرَّفًا بمحرك يحتفظ بتلك الإدخالات.

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/metadata" \
  --data-urlencode "metric=http_requests_total" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

## اتحاد المقاييس {#federation}

يدعم ClickHouse نقطة نهاية [الاتحاد في Prometheus](https://prometheus.io/docs/prometheus/latest/federation/) على المسار `/prometheus/api/v1/federate` (أو على أي مسار ينتهي بـ `/federate` يخدمه معالج من النوع `query`). ولكل سلسلة بيانات تطابق محدِّدات `match[]`، يُعيد أحدث عينة خلال آخر 5 دقائق بتنسيق Prometheus النصي، ليتمكن خادم Prometheus من سحبها:

```yaml
scrape_configs:
  - job_name: clickhouse-federate
    honor_labels: true
    scheme: https
    metrics_path: /prometheus/api/v1/federate
    params:
      'match[]': ['{job="node"}']
      table: ['prometheus.metrics']
    static_configs:
      - targets: ['clickhouse.example.com:8443']
```

## قراءة المقاييس باستخدام القراءة عن بُعد {#remote-read}

يدعم ClickHouse [بروتوكول القراءة عن بُعد الخاص بـ Prometheus](https://prometheus.io/docs/prometheus/latest/querying/remote_read_api/) عبر المسار `/prometheus/api/v1/read`.

هيّئ خادم Prometheus ليقرأ من جدول `TimeSeries` نفسه:

```yaml
remote_read:
  - url: https://clickhouse.example.com:8443/prometheus/api/v1/read?database=prometheus&table=metrics
    basic_auth:
      username: default
      password: <password>
```

## قواعد التسجيل {#recording-rules}

لا يُقيِّم ClickHouse ملفات قواعد Prometheus، لكن يمكن لـ[عرض مُجسَّد قابل للتحديث](/ar/reference/statements/create/view#refreshable-materialized-view) أن يؤدي دور [قاعدة التسجيل](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/)؛ إذ يُقيِّم تعبير PromQL وفق جدول زمني ويُلحق النتيجة بجدول `TimeSeries`. يسجّل العرض التالي `sum by (job) (rate(http_requests_total[5m]))` باسم `job:http_requests:rate5m` كل دقيقة:

```sql
CREATE MATERIALIZED VIEW prometheus.job_http_requests_rate5m
REFRESH EVERY 1 MINUTE APPEND TO prometheus.metrics (tags, samples) AS
SELECT
    mapUpdate(CAST(tags, 'Map(String, String)'), map('__name__', 'job:http_requests:rate5m')) AS tags,
    [(timestamp, value)] AS samples
FROM prometheusQuery(prometheus.metrics, 'sum by (job) (rate(http_requests_total[5m]))', toStartOfMinute(now()));
```

في كل عملية تحديث، يُقيَّم التعبير عند بداية الدقيقة الحالية، ويُعيَّن اسم المقياس باستخدام `mapUpdate`، ثم تُلحَق عينة واحدة لكل سلسلة بيانات في النتيجة. ويمكن إضافة وسوم إضافية إلى الخريطة نفسها، مثل `map('__name__', 'job:http_requests:rate5m', 'team', 'web')`. ويُستعلَم عن السلسلة المسجَّلة كما يُستعلَم عن أي مقياس آخر:

```bash
curl --user default:<password> --get \
  "https://clickhouse.example.com:8443/prometheus/api/v1/query" \
  --data-urlencode "query=job:http_requests:rate5m" \
  --data-urlencode "database=prometheus" \
  --data-urlencode "table=metrics"
```

يُعرَض وقت آخر تقييم والخطأ (error) الناتج عنه في [`system.view_refreshes`](/ar/reference/system-tables/view_refreshes).

يختلف العرض عن قاعدة التسجيل في Prometheus في النقاط التالية:

* وقت التقييم هو `now()` لحظة تشغيل التحديث. فإلى جانب الجدول الزمني، يُحدَّث العرض فور إنشائه (ما لم يُنشأ باستخدام `EMPTY`)، وبعد إعادة تشغيل الخادم إذا لم تكن تحديثاته منسَّقة (إذ لا يتذكّر العرض آخر تحديث له إذا كان خارج قاعدة بيانات بمحرك Replicated أو Shared، أو كان يستخدم `all_replicas = 1`)، وكذلك عندما يستأنفه `SYSTEM START VIEW` بعد أن فاته تحديث مجدول. قرِّب `now()` إلى الأسفل حتى بداية الفاصل الزمني كما في المثال، كي لا تضيف هذه التحديثات عينات بين التحديثات المجدولة. ومع ذلك، قد يكتب تحديث إضافي عينة ثانية عند الطابع الزمني المُقرَّب نفسه. فلقاعدة مدتها خمس دقائق، استخدم `toStartOfInterval(now(), INTERVAL 5 MINUTE)`.
* لا تُعوَّض التقييمات الفائتة. فبعد توقّف الخادم أو إيقاف العرض، لا يقيّم العرض إلا الفاصل الزمني الحالي، وتبقى الفترات الزمنية السابقة له فارغة. ويحدث الأمر نفسه عندما يستغرق التحديث وقتًا أطول من الفاصل الزمني.
* لا تحصل سلسلة البيانات التي تختفي من النتيجة على وسم تقادم البيانات، لذا تظل الاستعلامات تُرجع آخر قيمة مسجّلة لها طوال فترة الاسترجاع (lookback)، وهي 5 دقائق افتراضيًا.
* لا يوجد ملف للقواعد، بل إن كل قاعدة عرضٌ مستقل. ولا تُدرَج هذه القواعد في `/api/v1/rules`.
