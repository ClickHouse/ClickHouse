`clickhousectl` (واسمها البديل `chctl`) هي واجهة سطر الأوامر الرسمية لـ ClickHouse، وتغطي الاستخدامات من التطوير المحلي إلى ClickHouse Cloud. وهي مصممة للاستخدام عبر الطرفية، وفي البرامج النصية، ومن قِبل وكلاء البرمجة.

باستخدام `clickhousectl` يمكنك:

* تثبيت إصدارات ClickHouse محليًا والتبديل بينها، وتشغيل خوادم محلية معزولة، وتنفيذ SQL
* تشغيل Postgres محليًا باستخدام Docker
* إنشاء خدمات ClickHouse Cloud وتهيئتها وتوسيع نطاقها ونسخها احتياطيًا والاستعلام عنها
* إنشاء خدمات [ClickHouse Managed Postgres](/ar/products/managed-postgres/overview) ومراقبتها وتهيئتها واستعادتها
* إنشاء ClickPipes وتشغيلها لاستيعاب البيانات من التخزين الكائني وKafka وKinesis وPub/Sub وPostgres وMySQL وMongoDB وBigQuery
* إدارة المصادر ولوحات المعلومات والتنبيهات وتكاملات webhook وعمليات البحث المحفوظة والأدوار في خدمة [Self-managed ClickHouse Observability](/ar/clickstack/self-configured/deployment/managed)
* تطوير الدوال المعرّفة من قِبل المستخدم القابلة للتنفيذ محليًا ونشرها على ClickHouse Cloud
* إدارة أعضاء المؤسسة والدعوات ومفاتيح API والأدوار
* تثبيت حزمة ClickHouse agent skills الرسمية في وكلاء البرمجة

تعرض هذه الصفحة أمثلة توضيحية. يُعدّ `clickhousectl <command> --help` المرجع المعتمد لكل أمر وعلامة. تنتهي تعليمات المساعدة لمعظم الأوامر بكتلة `CONTEXT FOR AGENTS`؛ وفي أوامر Cloud، تسرد التعليمات أيضًا صلاحيات مفتاح API اللازمة لتنفيذها. للاطلاع على خطوات تنفيذ المهام، راجع روابط الأدلة في كل قسم. وللحصول على نظرة عامة تركز على Cloud، راجع [واجهة سطر الأوامر لـ ClickHouse](/ar/products/cloud/features/cli).

## التثبيت {#installation}

تعمل أداة `clickhousectl` على نظامَي MacOS وLinux، بمعماريتَي ARM64 وx86&#95;64.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

يثبّت البرنامج النصي `~/.local/bin/clickhousectl` وينشئ الاسم البديل `chctl`. تأكد من إضافة `~/.local/bin` إلى متغير `PATH` لديك.

يمكنك أيضًا تثبيته باستخدام مدير حزم:

| الأداة                                    | الأمر                           |
| ----------------------------------------- | ------------------------------- |
| npm                                       | `npm install -g clickhousectl`  |
| uv                                        | `uv tool install clickhousectl` |
| pipx                                      | `pipx install clickhousectl`    |
| pip                                       | `pip install clickhousectl`     |
| cargo-binstall                            | `cargo binstall clickhousectl`  |
| Cargo، من الشيفرة المصدرية (Rust 1.94.1+) | `cargo install clickhousectl`   |

لا يُنشئ الاسم البديل `chctl` سوى برنامج التثبيت النصي وnpm. لتحديث تثبيت قائم، شغّل `clickhousectl update` (راجع [التحديث الذاتي](#self-update))؛ أما في حالات التثبيت عبر npm وuv وpipx وpip، فيعرض الأمر بدلًا من ذلك أمر الترقية الخاص بمدير الحزم.

### الإكمال التلقائي في shell {#shell-completions}

لإكمال الأوامر وعلامات سطر الأوامر وأسماء الخوادم المحلية والإصدارات المثبتة تلقائيًا بالضغط على مفتاح Tab، أضف سطرًا واحدًا إلى ملف بدء التشغيل الخاص بـ shell لديك. يُفعِّل هذا السطر الإكمال لكلٍّ من `clickhousectl` و`chctl`:

```bash
eval "$(clickhousectl completions bash)"   # ~/.bashrc
eval "$(clickhousectl completions zsh)"    # ~/.zshrc, after compinit
clickhousectl completions fish | source    # ~/.config/fish/config.fish
```

يُشغِّل الإكمال التلقائي واجهة سطر الأوامر المثبّتة عند كل ضغطة على مفتاح Tab، ولذا يبقى محدّثًا بعد تنفيذ `update`.

## المتطلبات {#requirements}

* Docker، لتشغيل Postgres محليًا فقط
* لاستخدام أوامر Cloud، يلزم حساب على [ClickHouse Cloud](https://clickhouse.com/cloud). تعمل أوامر القراءة باستخدام مصادقة OAuth عبر المتصفح (`cloud auth login`)، أما إنشاء الموارد أو تعديلها فيتطلب [مفتاح API](/ar/products/cloud/features/admin-features/api/openapi). راجع [المصادقة](#authentication).

## البيئة المحلية {#local}

يُعدّ الدليل الذي يحتوي على `.clickhouse/` جذرًا للمشروع، تمامًا كما يُعدّ الدليل الذي يحتوي على `.git/` جذرًا لمشروع Git. تستخدم الأوامر المحلية أقرب جذر في الدليل الحالي أو في أحد الأدلة الأعلى منه، ولذلك تعمل من أي دليل فرعي داخل المشروع؛ أما خارج أي مشروع فتستخدم الدليل الحالي. اضبط `CLICKHOUSECTL_PROJECT_DIR` لتحديد جذر المشروع صراحةً، كما في برنامج نصي أو مهمة تكامل مستمر مثلًا. يحتفظ كل مشروع ببيانات الخادم الخاصة به في `.clickhouse/`، بينما تُشارَك الملفات التنفيذية لـ ClickHouse على مستوى النظام بأكمله في `~/.clickhouse/`. راجع [دليل التطوير المحلي](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md) للاطلاع على سير العمل الكامل.

### تثبيت الإصدارات واختيارها {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
clickhousectl local install --binary ~/ClickHouse/build/programs/clickhouse   # A build of your own
```

| المحدِّد      | المعنى                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------- |
| `latest`      | أحدث إصدار من ClickHouse، يُتحقَّق منه عن بُعد عند كل تثبيت أو استخدام أو تشغيل (موصى به) |
| `stable`      | أحدث إصدار مستقر                                                                          |
| `lts`         | أحدث إصدار بدعم طويل الأمد                                                                |
| `26.8`        | أحدث إصدار مطابق                                                                          |
| `26.8.1.1760` | إصدار بعينه                                                                               |

يثبّت الأمر `local use` الإصدار عند الحاجة، ويعيّنه إصدارًا افتراضيًا لعمليات تشغيل الخادم اللاحقة، وينشئ له رابطًا رمزيًا في `~/.local/bin/clickhouse`، فيصبح `clickhouse client` و`clickhouse local` متاحين ضمن `PATH` لديك. مرّر `--no-global` لتخطي إنشاء الرابط الرمزي. وإذا كان في ذلك المسار ملف عادي موجود مسبقًا، فإنه يُترك دون تغيير.

يرفض الأمر `local remove` إزالة الإصدار الافتراضي أو أي إصدار يستخدمه خادم قيد التشغيل في أي مشروع. أما الخيار `--force` فيوقف تلك الخوادم ويزيل الإصدار، ويلغي تعيين الإصدار الافتراضي ويحذف الرابط الرمزي.

ينسخ الأمر `local install --binary <path>` ملفًا تنفيذيًا لـ ClickHouse بنيته بنفسك، ويثبّته تحت الإصدار الذي يُبلغ عنه، بحيث يمكنك اختياره باستخدام `local use` أو `--version` كأي إصدار مثبّت آخر. وبما أن إعادة البناء تُبلغ عادةً عن الإصدار نفسه، مرّر `--force` لاستبدال النسخة المثبّتة.

### تهيئة مشروع {#initializing-project}

```bash
clickhousectl local init
```

يحدّد الأمر `init` الدليل الحالي (أو `CLICKHOUSECTL_PROJECT_DIR` إن كان مُعيَّنًا) جذرًا للمشروع. وهو يُنشئ دليل `.clickhouse/` مُستثنًى من git لبيانات بيئة التشغيل، إضافةً إلى هياكل أولية يمكنك تثبيتها في المستودع: `clickhouse/` (`tables/`، `materialized_views/`، `queries/`، `seed/`، `udfs/`، `config.d/`) و`postgres/` (`tables/`، `views/`، `functions/`، `queries/`، `seed/`). ولا تُنشئ إعادة تشغيله سوى ما هو مفقود، لذا شغّله مرة واحدة بعد استنساخ أي مشروع. ويظل بالإمكان بدء تشغيل الخادم دون `init`، وفي هذه الحالة يُنشأ `.clickhouse/` في الدليل الحالي.

### تشغيل خوادم محلية {#managing-servers}

```bash
clickhousectl local clickhouse start dev --version latest   # Background start; waits for readiness
clickhousectl local clickhouse start dev --no-wait          # Return after spawning
clickhousectl local clickhouse start dev --foreground       # Run in the foreground
clickhousectl local clickhouse start dev --http-port 8124 --tcp-port 9001
clickhousectl local clickhouse list                         # ClickHouse servers in this project
clickhousectl local clickhouse list --global                # Servers across all projects
clickhousectl local status                                  # Every ClickHouse server and Postgres instance in this project
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse stop-all                     # Stop every ClickHouse server in this project
clickhousectl local clickhouse remove dev                   # Permanently delete a stopped server's data
```

`local ch` هو اختصار لـ `local clickhouse`، ولا يزال الاسم السابق `local server` يعمل كاسم بديل. لكل خادم مُسمّى بياناته الخاصة في `.clickhouse/servers/<name>/data/`، وعند إيقاف الخادم تُحفَظ هذه البيانات إلى حين تشغيله مجددًا. عند التشغيل دون تحديد اسم، يُستخدم `default`؛ وإذا كان `default` قيد التشغيل بالفعل، يُولَّد اسم جديد. المنافذ الافتراضية هي HTTP 8123 وTCP 9000، وتُخصَّص منافذ متاحة إذا كانت هذه المنافذ مشغولة.

تختار الأوامر التي تعمل على خادم موجود (`stop` و`client` و`dotenv` و`local client` و`local udf --server`) الخادم `default` عند إغفال الاسم، وإلا فالخادم الوحيد في المشروع الذي يستخدم ذلك المحرك. وعند وجود عدة خوادم ليس بينها خادم باسم `default`، تفشل هذه الأوامر بالخطأ `server_selection_required` وتعرض قائمة بالأسماء. أما `remove` فلا يعتمد على التخمين أبدًا: فهو لا يزيل دون تحديد اسم سوى `default`. لذا ينبغي أن تمرّر البرامج النصية الأسماء صراحةً.

يحدد `--version` إصدارًا لهذا التشغيل فقط دون تغيير الإصدار الافتراضي. وعند التشغيل دون تحديد إصدار ودون وجود إصدار افتراضي، يُثبَّت `latest` دون أن يصبح الإصدار الافتراضي؛ لجعله الإصدار الافتراضي، شغّل `local use latest` أولًا.

### تشغيل استعلامات SQL باستخدام العميل المحلي {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

يتصل `local client` بخادم مُسمّى باستخدام الملف التنفيذي نفسه لـ ClickHouse الذي يُشغّل ذلك الخادم؛ وفي حال عدم تحديد اسم، يتبع قاعدة التحديد الموضحة أعلاه. تُمرَّر الوسيطات الواردة بعد `--` إلى `clickhouse client` كما هي دون تغيير. يصدر الإخراج وحالة الخروج عن `clickhouse client`، حتى في وضع JSON، لذا حدّد تنسيق الإخراج لـ SQL بنفسك عند كتابة البرامج النصية.

### تكوين الخادم المخصص {#custom-config-files}

تتجاوز ملفات الإعداد الجزئية بصيغة XML أو YAML القيم الافتراضية المدمجة، ويمكن وضعها في أحد ثلاثة مواقع:

| الموقع                                | ينطبق على                                                  | التوقيت                |
| ------------------------------------- | ---------------------------------------------------------- | ---------------------- |
| `~/.clickhouse/config.d/`             | كل خادم على هذا الجهاز                                     | عند كل تشغيل           |
| `clickhouse/config.d/` في جذر المشروع | كل خادم في المشروع؛ أضِفه إلى المستودع لمشاركته مع الآخرين | عند كل تشغيل           |
| `~/.clickhouse/configs/`              | الخادم الذي تشغّله به                                      | فقط مع `--config NAME` |

```bash
cat > clickhouse/config.d/logging.xml <<'XML'
<clickhouse>
    <logger><level>debug</level></logger>
</clickhouse>
XML
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local clickhouse configs          # List both config.d directories and the named configs
clickhousectl local clickhouse stop dev
clickhousectl local clickhouse start dev --config analytics
```

عند كل تشغيل، تُدمج هذه الملفات وفق ترتيبها في الجدول، وتكون الأولوية للملفات اللاحقة، لذا يكفي أن يتضمن الملف الإعدادات التي تغيّرها فقط. تسري التعديلات وحذف `--config` عند التشغيل التالي. وتكون الأولوية دائمًا لمسارات البيانات والمنافذ المُدارة على قيم الإعداد.

### كتابة بيانات الاتصال في ملف dotenv {#dotenv}

```bash
clickhousectl local clickhouse dotenv dev                                     # Writes .env
clickhousectl local clickhouse dotenv dev --local --user default --database analytics   # Writes .env.local
```

يقرأ `dotenv` المنافذ الفعلية للخادم قيد التشغيل ويكتب `CLICKHOUSE_HOST` و`CLICKHOUSE_PORT` و`CLICKHOUSE_HTTP_PORT`، بالإضافة إلى اسم المستخدم وكلمة المرور وقاعدة البيانات عند تمريرها إليه. ويُبقي على الأسطر الأخرى إذا كان الملف موجودًا بالفعل. حمِّل الملف باستخدام أداة تحميل dotenv الخاصة بتطبيقك؛ ولا تستخدم `eval` مطلقًا لتنفيذ المعاينة المطبوعة.

### Postgres المحلي {#local-postgres}

يعمل Postgres المحلي داخل Docker، لذا يجب أن يكون Docker قيد التشغيل. الإصداران 17 و18 من Postgres مدعومان، بما في ذلك وسوم الصور مثل `18-alpine`؛ وتستخدم المثيلات الجديدة الإصدار 18 افتراضيًا.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres list                       # Postgres instances in this project
clickhousectl local postgres stop app
clickhousectl local postgres stop-all                   # Stop every Postgres instance in this project
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

`local pg` هو اختصار لـ `local postgres`. يُحدَّد المثيل باسمه وإصداره الرئيسي. عند استئناف مثيل متوقف، يُعاد استخدام المنفذ والمستخدم وكلمة المرور وقاعدة البيانات الأصلية الخاصة به، لذا لا تأثير لعلامات سطر الأوامر الخاصة بالإنشاء عند الاستئناف. تُولَّد كلمة مرور عشوائية ما لم تحدد كلمة مرور بنفسك. يحتوي الملف `.env.local` على كلمة المرور، لذا احرص على استبعاده من نظام التحكم في الإصدارات.

### UDFs المحلية {#local-udfs}

ينشر الأمر `local udf` [الدوال المعرّفة من قِبل المستخدم القابلة للتنفيذ](/ar/reference/functions/regular-functions/udf#executable-user-defined-functions) من `clickhouse/udfs/<name>/` إلى خادم محلي. ويحمّل الأمر `cloud udf` الدليل نفسه إلى Cloud (انظر [UDFs في Cloud](#cloud-udfs)).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local clickhouse start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

يقبل كل أمر باستثناء `init` الخيار `--server <name>`؛ وعند عدم تحديده، يُختار الخادم وفقًا لـ[قاعدة الاختيار](#managing-servers). يتحقق `deploy` من صحة `udf.json` بالطريقة نفسها المتّبعة في Cloud. وإذا كان الخادم قيد التشغيل، يعيد تحميل الدوال ويتأكد من نجاح تحميل الدالة. لا تتيح بيئة التشغيل `native` النشر محليًا إلا على مضيفي Linux بمعمارية amd64 أو arm64. راجع [دليل الدوال المعرّفة من قِبل المستخدم](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

## المصادقة {#authentication}

تستخدم أوامر Cloud أحد نوعين من بيانات الاعتماد:

| بيانات الاعتماد          | الصلاحيات                                                                                           | التخزين                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| مصادقة OAuth عبر المتصفح | هوية المستخدم الخاصة بك: عمليات Cloud واستعلامات SQL للقراءة فقط، في جميع المؤسسات التي تنتمي إليها | `~/.clickhouse/tokens.json`، على مستوى النظام ومشترك بين المشاريع                                                  |
| مفتاح API                | يقتصر نطاقه على مؤسسة واحدة؛ وتعتمد عمليات القراءة والكتابة على أدوار المفتاح                       | `.clickhouse/credentials.json` في الدليل الجذري للمشروع عند حفظ بيانات الاعتماد، ويمكن العثور عليه من أي دليل فرعي |

إذا لم يكن لديك حساب في ClickHouse Cloud بعد، فإن الأمر `clickhousectl cloud auth signup` يفتح صفحة التسجيل في متصفحك.

### تسجيل الدخول عبر OAuth {#oauth-login}

```bash
clickhousectl cloud auth login
```

يؤدي هذا إلى فتح متصفحك لبدء تدفق مصادقة الأجهزة عبر OAuth. تُحفظ رموز المصادقة في `~/.clickhouse/tokens.json` لتكون متاحة لجميع الجلسات، وتُجدَّد تلقائيًا.

<Note>
  يتيح OAuth الوصول **للقراءة فقط**. لإنشاء الموارد أو تعديلها، سجّل الدخول باستخدام [مفتاح API](#api-key).
</Note>

### مفتاح API {#api-key}

[أنشئ مفتاح API](/ar/products/cloud/features/admin-features/api/openapi) بالأدوار اللازمة لتنفيذ أوامرك، ثم احفظه. يحول الموجّه التفاعلي دون تسجيل المفتاح السري في سجل أوامر shell:

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

يتحقق أمر تسجيل الدخول من المفتاح ويعرض الهوية التي ينتمي إليها. وإذا رفضت واجهة برمجة التطبيقات المفتاح، فلن يُحفظ، وسينتهي الأمر برمز الخروج 4. أما إذا تعذّر الوصول إلى واجهة برمجة التطبيقات، فسيُحفظ المفتاح مع عرض تحذير.

في بيئات CI وغيرها من أنظمة الأتمتة، مرِّر المفتاح عبر أداة إدارة الأسرار لديك بدلًا من حفظه:

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

لأغراض التطوير، تقرأ واجهة سطر الأوامر هذه المتغيرات أيضًا من ملف `.env` في الدليل الحالي، أو من [جذر المشروع](#local) إن لم يوجد فيه هذا الملف. احرص على إبقاء `.env` خارج نظام التحكم في الإصدارات.

### التحقق من بيانات الاعتماد ومسحها {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

يعمل `whoami` مع أيٍّ من نوعَي بيانات الاعتماد، وينتهي برمز الخروج 4 إذا رُفضت بيانات الاعتماد. أما `status` فقد ينتهي برمز الخروج 0 حتى إن لم تعمل أي بيانات اعتماد، لذا استخدم `whoami` للتحقق من الوصول. ولا يؤدي تسجيل الخروج إلى إلغاء تعيين متغيرات البيئة ولا إلى تعديل الملف `.env`.

### أسبقية بيانات الاعتماد {#credential-precedence}

يُعتمد أول مصدر متاح وفق الترتيب التالي:

1. علامتا سطر الأوامر `--api-key` و`--api-secret`
2. الملف `.clickhouse/credentials.json` في جذر المشروع
3. متغيرات البيئة المُصدَّرة
4. المتغيرات الموجودة في الملف `.env` في الدليل الحالي، وإلا ففي جذر المشروع
5. رموز OAuth العامة

مرِّر العلامة `--debug` إلى أي أمر من أوامر `cloud` لطباعة مصدر بيانات الاعتماد المُختار وعنوان URL الخاص بواجهة برمجة التطبيقات إلى stderr:

```bash
clickhousectl cloud clickhouse list --debug
```

### اختيار مؤسسة {#organizations}

لا تختار الأوامر المرتبطة بنطاق المؤسسة المؤسسةَ تلقائيًا إلا إذا كانت بيانات اعتمادك تتيح الوصول إلى مؤسسة واحدة فقط. وبخلاف ذلك، مرّر `--org-id`، أو `--org-name` مع الاسم المطابق تمامًا؛ وإن لم تمرّر أيًّا منهما، فسينتهي الأمر برمز الخروج 2 ويعرض ID كل مؤسسة واسمها:

```bash
clickhousectl cloud org list
clickhousectl cloud clickhouse list --org-id <org-id>
clickhousectl cloud clickhouse list --org-name "My Org"
```

تقبل معظم أوامر الموارد معرّفًا كوسيط موضعي أو اسمًا مطابقًا تمامًا عبر الخيار `--name`. راجع [المصادقة والوصول](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md) لمعرفة تفاصيل الصلاحيات والمفاتيح المقيّدة وإجراءات التنظيف عند تسجيل الخروج.

## Cloud {#cloud}

تستدعي أوامر Cloud [واجهة برمجة تطبيقات ClickHouse Cloud](/ar/products/cloud/features/admin-features/api/api-overview). تُرجع طلبات الإنشاء والتحديث استجابتها فور قبول واجهة برمجة التطبيقات لها، لذا استطلع `get` بشكل متكرر إلى أن يبلغ المورد الحالة التي تحتاجها.

### الخدمات {#services}

يتولّى الأمر `cloud clickhouse` إدارة خدمات ClickHouse Cloud، والأمر `cloud ch` صيغة مختصرة له، كما لا يزال الاسم السابق `cloud service` صالحًا للاستخدام بوصفه اسمًا بديلًا.

```bash
clickhousectl cloud clickhouse create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud clickhouse create --name app-dev \
  --ip-allow 203.0.113.10/32 --dotenv .env.local          # Password goes only to the file
clickhousectl cloud clickhouse list
clickhousectl cloud clickhouse get <service-id>
clickhousectl cloud clickhouse start <service-id>
clickhousectl cloud clickhouse stop <service-id>
clickhousectl cloud clickhouse wake <service-id>             # Wake an idle service
clickhousectl cloud clickhouse reset-password <service-id>
clickhousectl cloud clickhouse delete <service-id>           # Must be stopped; --force stops it first
```

احفظ كلمة المرور الأولية المعروضة عند الإنشاء، إذ لا تُعاد إلا مرة واحدة. عند استخدام `--dotenv [file]` (القيمة الافتراضية `.env`)، تُكتب كلمة المرور في ذلك الملف فقط، ولا تظهر في الطرفية أو في إخراج JSON. يُعيد أمر الإنشاء النتيجة قبل اكتمال التجهيز، لذا كرّر تنفيذ `get` إلى أن تصبح الحالة `running`. **إغفال `--ip-allow` يسمح بجميع عناوين IP (`0.0.0.0/0`).** تقبل العناصر الصيغة `IP_OR_CIDR=DESCRIPTION`. يقبل `--region` أي معرّف منطقة، بما في ذلك المناطق الخاصة، ويتولى Cloud التحقق من صحته. لاستعادة نسخة احتياطية إلى خدمة جديدة استخدم `--backup-id`، ولوضع خدمة ضمن البنية التحتية لـ BYOC استخدم `--byoc-id`.

الاتصال بخدمة قيد التشغيل:

```bash
clickhousectl cloud clickhouse client <service-id>                     # Interactive clickhouse client
clickhousectl cloud clickhouse client --name analytics -q "SELECT version()"
clickhousectl cloud clickhouse dotenv <service-id> --local             # Write .env.local, without a password
```

يفتح `client` الأداة `clickhouse client` عبر بروتوكول TLS الأصلي، ويُسجّل دخولك عبر المتصفح بصفتك مستخدم Cloud، فلا حاجة إلى كلمة مرور الخدمة. ويعتمد على إصدار مثبَّت من ClickHouse ‏25.12 أو أحدث (`clickhousectl local install latest`)، ويتطلب وجود شخص أمام المتصفح، لذا استخدم [`query`](#query-api) في بيئات CI ومع الوكلاء. ويكتب `dotenv` المتغيرات `CLICKHOUSE_HOST` و`CLICKHOUSE_PORT` و`CLICKHOUSE_HTTP_PORT` و`CLICKHOUSE_USER` و`CLICKHOUSE_SECURE`، ولا يستبدل سوى هذه المفاتيح، وبذلك تبقى كلمة المرور التي كتبها `create --dotenv` محفوظة.

تحديث خدمة وتغيير سعتها وتهيئتها:

```bash
clickhousectl cloud clickhouse update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud clickhouse update <service-id> --deletion-protection true
clickhousectl cloud clickhouse profile list --region us-east-1
clickhousectl cloud clickhouse scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud clickhouse scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud clickhouse scale <service-id> --profile v1-highmem-s
clickhousectl cloud clickhouse settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud clickhouse upgrade-window set <service-id> --weekday 0 --start-hour 6
```

تكون ذاكرة كل نسخة متماثلة من مضاعفات 4 GB، بحد أقصى 120 GB في الخدمات غير المدفوعة و356 GB في الخدمات المدفوعة، وبما لا يزيد على 50 نسخة متماثلة. وقد تفرض حدود المؤسسة والمستودع قيمًا أقل من ذلك. ويتطلب التوسّع الأفقي التلقائي تفعيل الميزة الخاصة به على مستوى المؤسسة. ويغيّر الأمر `scale --profile` ملف تعريف المثيل في مؤسسات Enterprise وBYOC. أما الأمر `update` فلا يغيّر إلا خيارات سطر الأوامر التي تمرّرها إليه.

عند تفعيل الحماية من الحذف (`create --deletion-protection`، أو `update --deletion-protection true|false`)، يرفض الأمر `delete` حذف الخدمة ويُرجع رمز الخطأ `deletion_protected`، حتى عند استخدام `--force`؛ لذا عطّل هذه الحماية قبل الحذف.

تشمل مجموعات أوامر الخدمة الأخرى `settings` ‏(list وget وschema وset وunset)، و`scaling-schedule`، و`upgrade-window`، و`replica-aware-routing` ‏(تجريبي)، و`jwt-provider` ‏(تجريبي، مستوى Enterprise)، و`snapshot` ‏(تجريبي)، و`private-endpoint`، و`query-endpoint`، و`backup-config`، و`prometheus`. لمزيد من التفاصيل، راجع [إنشاء خدمة سحابية وتشغيلها](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md).

### واجهة برمجة تطبيقات الاستعلام {#query-api}

ينفّذ الأمر `cloud clickhouse query` عبارة SQL واحدة عبر HTTP، دون الحاجة إلى ملف تنفيذي محلي لـ `clickhouse` أو كلمة مرور للخدمة:

```bash
clickhousectl cloud clickhouse query <service-id> --query "SELECT version()"
clickhousectl cloud clickhouse query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud clickhouse query <service-id>
```

* **OAuth** يشغّل الاستعلام بهويتك، مع صلاحية وصول SQL للقراءة فقط. لا يُربط أي شيء بالخدمة.
* **مفتاح API:** يستخدم الاستعلام دائمًا مفتاح API النشط. وعند الحاجة، يضيف clickhousectl هذا المفتاح إلى نقطة نهاية API للاستعلام الخاصة بالخدمة، وينشئ نقطة النهاية بأدوار `sql_console_admin` إن لم تكن موجودة. ويُحتفظ بالأدوار والمصادر وروابط المفاتيح الأخرى الموجودة، ولا يُنشأ أي مفتاح جديد. مرّر `--no-auto-enable` لتفشل العملية بدلًا من ذلك.

الربط عملية كتابة، لذا لا يستطيع مفتاح API للقراءة فقط أن يربط نفسه: ينتهي الاستعلام برمز الخروج 1 مع `query_key_bind_forbidden` دون أي تغيير. اربطه مرة واحدة باستخدام مفتاح يملك صلاحية الكتابة، عبر `query-endpoint create <service-id> --role <role> --open-api-key <key-id>` (مع إضافة `--allowed-origins '*'` إن لم تكن للخدمة نقطة نهاية بعد).

تقبل واجهة برمجة تطبيقات الاستعلام عبارة واحدة لكل طلب. وقد تنتهي مهلتها بعد نحو 30 ثانية بينما يظل SQL قيد التنفيذ، لذا تحقّق من النتيجة قبل إعادة محاولة أي عملية كتابة. استخدم [`cloud clickhouse client`](#services) للنصوص البرمجية متعددة العبارات وعمليات التحميل المجمّع والاستعلامات الطويلة. تقيّد قائمة السماح لعناوين IP الخاصة بالخدمة الاتصالات المباشرة فقط، لا مسار واجهة برمجة تطبيقات الاستعلام المارّ عبر الوكيل. ويؤدي الاستعلام عن خدمة خاملة إلى تنشيطها، أما الخدمة المتوقفة فيجب تشغيلها باستخدام `cloud clickhouse start`.

إدارة نقطة نهاية API للاستعلام الخاصة بالخدمة، ونقاط نهاية SQL المسمّاة، والاستعلامات المحفوظة:

```bash
clickhousectl cloud clickhouse query-endpoint get <service-id>
clickhousectl cloud clickhouse query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

يستبدل الأمر `query-endpoint create` الأدوار المُسندة إلى كل مفتاح مرتبط بنقطة النهاية. راجع [سلوك SQL وواجهة برمجة تطبيقات الاستعلام](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md).

### Managed Postgres {#postgres-services}

يُدير الأمر `cloud postgres` (واسمه البديل `cloud pg`) خدمة [ClickHouse Managed Postgres](/ar/products/managed-postgres/overview). أما دعم GCP فهو حاليًا في مرحلة المعاينة الخاصة.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> --ha-type sync --standby-count 2
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres update <postgres-id> --deletion-protection true
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

تشمل أحجام AWS ‏`m6gd.large` و`c6gd.xlarge` و`r6gd.xlarge`. أما على GCP، فمرّر `--provider gcp` مع منطقة GCP وحجم مثل `c4-standard-lssd-4`.

احفظ كلمة المرور وسلسلة الاتصال اللتين يُرجعهما الأمر `create`، إذ لا تُرجع استجابات `get` اللاحقة بيانات الاعتماد مطلقًا، و`reset-password` هو السبيل الوحيد للحصول على بيانات اعتماد جديدة. اتصل باستخدام `psql` مع `sslmode=verify-full` وملف CA.

**إذا أغفلت خيارات سطر الأوامر الخاصة بالوصول عند الإنشاء، فسيُسمح بجميع عناوين IPv4 وعناوين IPv6 بالوصول إلى Postgres ‏(5432) وPgBouncer ‏(6432).** مرّر خيار `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` واحدًا لكل قاعدة، أو `--block-public-access` إن لم ترد أي قواعد. وبمجرد تمرير قاعدة، لا تُطبَّق إلا القواعد المدرجة.

يحدد `--standby-count` عدد النسخ الاحتياطية الجاهزة الساخنة عند `create` أو `update`: إذ يقبل `--ha-type none` القيمة 0، ويقبل `async` القيمة 1، ويقبل `sync` القيمة 1 أو 2. وعند تفعيل الحماية من الحذف، ترفض واجهة برمجة التطبيقات عملية `delete` إلى أن تضبط `--deletion-protection false`، وذلك في المؤسسات التي تتوفر لديها هذه الميزة. وللاتصال عبر شبكة خاصة على AWS، يتولى `private-endpoint` ‏(create وget وupdate وdelete) إدارة خدمة نقطة نهاية PrivateLink ‏(تجريبي)؛ ويجب الموافقة على كل نقطة نهاية VPC باستخدام `private-endpoint update --add-vpc-endpoint` قبل أن تتمكن من الاتصال.

المراقبة والاسترداد:

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

لا يقبل الأمر `cloud postgres query` إلا مصادقة OAuth، ولذلك يفشل ما دام مصدر مفتاح API ذو أولوية أعلى نشطًا. تتولى الأوامر `metrics` و`slow-queries` و`prometheus` جانب المراقبة؛ كما تقبل الأوامر `logs` و`metrics` و`slow-queries` و`backup list` الخيار `--name` بدلًا من الـ ID. ينسخ الأمر `restore` قواعد الوصول الحالية الخاصة بعناوين IPv4 من المصدر إلى الخدمة المستعادة ما لم تمرّر `--ip-allow` أو `--block-public-access`. تُرجع عمليات الاستعادة وإنشاء النسخ المتماثلة نتائجها دون كلمة مرور. ينتهي الأمران `promote` و`switchover` بمجرد قبول الطلب؛ وبعد تنفيذ promote، استطلع `postgres get --json` حتى تُبلغ النسخة المتماثلة عن `isPrimary: true`. راجع [دليل Managed Postgres](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md).

### ClickPipes {#clickpipes}

يستوعب `cloud clickpipe` البيانات من التخزين الكائني وKafka وKinesis وPub/Sub وPostgres وMySQL وMongoDB وBigQuery. تتطلب عمليتا الإنشاء واكتشاف المخطط مفتاح API وخدمة وجهة قيد التشغيل. لكل مصدر أمر فرعي خاص به بصيغة `clickpipe create <source>`؛ شغّله مع `--help` للاطلاع على خيارات سطر الأوامر المتاحة له.

حمّل الملفات من S3 باستخدام دور IAM. اكتشف المخطط أولًا وراجعه، ثم أنشئ مسار استيعاب البيانات باستخدام مخرجات الاكتشاف المحفوظة:

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" --json > discovery.json
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --columns-from discovery.json
```

يحوّل `--columns-from` الحقول المكتشفة إلى أعمدة الوجهة، لذا عدّل الملف أولًا لإزالة الحقول التي لا تريدها. تتطلب عمليات الإنشاء للتخزين الكائني وKafka وKinesis وPub/Sub استخدام `--columns-from`، أو خيار `--column name:type` واحد على الأقل، أو كليهما؛ ويضيف `--column` أعمدة إضافية إلى الأعمدة الواردة من الملف.

انسخ بيانات Postgres نسخًا متماثلًا باستخدام CDC. يجري التحقق من TLS افتراضيًا؛ وعند استخدام مصدر Managed Postgres، صدّر شهادة CA الخاصة به ومرّرها:

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud clickhouse query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

ينشئ `--table-mapping` جداول `ReplacingMergeTree`، لذا استخدم `FINAL WHERE _peerdb_is_deleted = 0` لقراءة الحالة الحالية. تقبل أوامر الإنشاء الخاصة بـ Postgres وMySQL الخيار `--use-json-native-format true` لتخزين أعمدة JSON بنوع `JSON` الأصلي في ClickHouse بدلاً من `String` (يتطلب ClickHouse 25.3+ مع تفعيل الميزة للمؤسسة). يتبع مسار استيعاب البيانات من Kafka النمط نفسه المتبع مع التخزين الكائني: نفّذ `clickpipe schema-discover kafka` باستخدام خيارات سطر الأوامر نفسها للمصدر، ثم مرّر column باستخدام `--column` أو `--columns-from`:

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

تُنشئ مسارات استيعاب البيانات من BigQuery لقطة افتراضيًا. ولاستخدام CDC (التقاط تغييرات البيانات)، مرِّر `--replication-mode cdc` و`--replication-method`، بالإضافة إلى عمود العلامة المائية الزمنية أو دالة الأحداث لكل جدول ضمن `--table-mapping-json`، ثم جدوِل عمليات المزامنة باستخدام `--sync-cron` أو `--sync-interval-seconds`. لإدارة مسارات استيعاب البيانات الحالية:

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

يجب أن تكون مسارات استيعاب البيانات من نوع CDC في الحالة `Paused` قبل تنفيذ `update`: أوقِف مسار استيعاب البيانات، ثم استطلع حالته باستخدام `get` إلى أن تصبح `Paused`، ثم حدّثه. قد تستأنف الخدمة مسار استيعاب البيانات ضمن عملية التحديث، لذا لا تشغّل `start` إلا إذا ظل `get` يُظهر الحالة `Paused`. يتوفر الخيار `--start-paused` للتخزين الكائني وKafka وKinesis وPub/Sub. أما مجموعات الأوامر الأخرى فهي `cdc-scaling` و`context get` (جاهزية workload-identity في GCP والكيان الأمني) و`reverse-private-endpoint`. راجع [دليل ClickPipes](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) و[مرجع تهيئة ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md).

### ClickStack {#clickstack}

يُدير `cloud clickstack` المصادر ولوحات المعلومات والتنبيهات وخطافات الويب وعمليات البحث المحفوظة والأدوار في خدمة [Self-managed ClickHouse Observability](/ar/clickstack/self-configured/deployment/managed) قائمة. تُمثَّل الموارد بملفات JSON (`--file`، أو `-` للإدخال عبر stdin). تدعم عمليات القراءة OAuth، بينما تتطلب عمليات الكتابة مفتاح API.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**يُستبدل المورد بالكامل عند كل تحديث لـ ClickStack.** احفظ الحالة الحالية باستخدام `get --json` وأرسل التعريف كاملًا، لا الحقول المعدّلة فقط. راجع [دليل ClickStack](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md).

### UDFs في Cloud {#cloud-udfs}

يدير `cloud udf` الدوال المعرّفة من قِبل المستخدم القابلة للتنفيذ على مستوى المؤسسة، وإصداراتها وروابطها بالخدمات. يحمّل `deploy` الدليل الذي اختبرته باستخدام `local udf`، وينتظر اكتمال إعداد الإصدار، ثم يربط ذلك الإصدار بالخدمة وينتظر حتى يكتمل نشره:

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud clickhouse query <service-id> --query "SELECT my_udf(1)"
```

لتنفيذ كل خطوة بنفسك، استخدم `udf create` و`udf version create` و`udf attach` (مع `--wake` إذا كانت الخدمة خاملة) و`udf detach` و`udf delete`. تنتهي هذه الأوامر فور قبول الطلب؛ استطلع الحالة باستخدام `udf get` و`udf attachment get`. تدعم عمليات القراءة OAuth، بينما تتطلب عمليات الكتابة مفتاح API. راجع [دليل الدوال المعرّفة من قِبل المستخدم](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

### المؤسسات والوصول {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

تقبل الأوامر الفرعية لـ `cloud org` الخيار `--org-id`، ولا تقبل المعرّف كوسيط موضعي مطلقًا. يغطي `org usage` فترة لا تتجاوز 31 يومًا. يتضمن `org` أيضًا `quota` و`balance` و`notification-types` و`role` (أدوار المؤسسة المخصصة) و`preview` (عرض ميزات المعاينة وتفعيلها أو تعطيلها، تجريبي) و`byoc` (البنية التحتية لـ BYOC، بما في ذلك `byoc access` للتحكم في توقيت السماح لموظفي ClickHouse بالوصول إليها، تجريبي). الإشعارات تجريبية.

إدارة الأعضاء والدعوات ومفاتيح API:

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

يعرض `member notification-settings` (تجريبي) تجاوزات إعدادات الإشعارات الخاصة بالعضو نفسه ويحدّثها. **يؤدي عدم تحديد `--ip-allow` عند تنفيذ `key create` إلى منع الوصول عبر الشبكة بالكامل**، بخلاف ما يحدث عند إنشاء خدمة. تُعرض القيمة السرية مرة واحدة فقط. يعيد `key list` صفحة واحدة ما لم تمرّر `--all`. عند تنفيذ `key update`، تبقى إعدادات خيارات سطر الأوامر التي لم تُحدَّد دون تغيير، بينما تزيل الخيارات `--clear-expiry` و`--clear-roles` و`--clear-ip-allow` الإعدادات المقابلة لها.

### النسخ الاحتياطية {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud clickhouse create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud clickhouse backup-config update <service-id> \
```

تؤدي الاستعادة دائمًا إلى إنشاء خدمة جديدة. يتيح الأمر `cloud backup bucket` ‏(get, create, update, delete) تهيئة حاوية خاصة بك للنسخ الاحتياطي باستخدام ملف JSON خاص بالمزوّد. راجع قسم النسخ الاحتياطي في [دليل الخدمة السحابية](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore).

## إخراج JSON {#json-output}

تدعم الأوامر التي تُرجع بيانات مهيكلة الخيار `--json`، بما في ذلك الأوامر المحلية وأوامر Cloud و`skills` و`update` و`telemetry`:

```bash
clickhousectl cloud clickhouse list --json
clickhousectl cloud key list --all --json
clickhousectl local clickhouse list --json
```

عندما تكتشف واجهة سطر الأوامر وكيل برمجة (مثل Claude Code أو Cursor أو Codex أو Gemini CLI أو Goose أو Devin، أو أي أداة تضبط `AI_AGENT`)، فإنها تختار JSON تلقائيًا. يحتفظ عملاء SQL والعملاء الأصليون بصيغهم الخاصة: يُعيد `cloud clickhouse query` النتائج بصيغة `JSONEachRow` في وضع JSON، ويكون إخراج `local client` دائمًا بالصيغة الأصلية. ينبغي للبرامج النصية التي تحلّل إخراج الاستعلام تمرير `--format` صراحةً. للإبقاء على الإخراج المقروء بشريًا عند اكتشاف وكيل، اضبط `CLICKHOUSECTL_AUTO_JSON=0`؛ لكن تمرير `--json` صراحةً يظل يفعّل إخراج JSON.

تضيف أوامر Cloud غير المتزامنة، مثل `clickhouse create` و`postgres create` و`clickpipe start`، كائن `next` إلى إخراج JSON الخاص بها لتحديد عملية الاستطلاع المطلوب تنفيذها: `command` (مع المعرّفات التي جرى تحديدها و`--org-id`)، والحقل `field` المطلوب مراقبته، وقيم `until` التي تشير إلى الاكتمال، وقيم `fail_on`، والفاصل الزمني المقترح `interval_seconds`. ويظل الأمر يعيد التحكم بمجرد قبول واجهة برمجة التطبيقات للطلب.

في وضع JSON، تُرسَل أخطاء وقت التشغيل إلى stderr على هيئة كائن يحتوي على رمز ثابت في `code` ورسالة في `message`:

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

حدّد مسار التنفيذ بناءً على `error.code`، لا على نص الرسالة. تبقى أخطاء الاستخدام بصيغة نصية، مع رمز الخروج 2، ولا يُرسَل أي شيء. راجع [الأتمتة وعقود الإخراج](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md) للاطلاع على بُنى الإخراج ورموز الخطأ.

## رموز الخروج {#exit-codes}

| الرمز | المعنى                                                                                                                                                |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`   | نجاح. في عمليات Cloud غير المتزامنة، يعني ذلك قبول الطلب، لا اكتماله                                                                                  |
| `1`   | error، بما في ذلك استجابة HTTP 403 التي تشير إلى رفض الطلب (الرمز `http_4xx`)                                                                         |
| `2`   | error في الاستخدام، بما في ذلك القيم غير الصالحة لخيارات سطر الأوامر والإدخال الذي يُفحص بعد التحليل النحوي لكن يستحيل تنفيذه بنجاح؛ لا يُرسَل أي شيء |
| `3`   | أُلغي طلب إدخال تفاعلي، مثل أداة اختيار `skills`                                                                                                      |
| `4`   | المصادقة مطلوبة أو رُفضت، بما في ذلك محاولات الكتابة باستخدام OAuth                                                                                   |

تُمرِّر أوامر تسليم التحكم إلى العملاء الأصليين، مثل `local client` و`local postgres client` وغيرها، حالة الخروج الخاصة بالعميل كما هي.

## مهارات الوكلاء {#skills}

ثبّت [حزمة ClickHouse agent skills الرسمية](https://github.com/ClickHouse/agent-skills) في وكلاء البرمجة لديك:

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

تُثبَّت المهارات في المشروع الحالي افتراضيًا، أو في دليلك الرئيسي باستخدام `--global`. ويُضمَّن الدليل المشترك `.agents/skills/` دائمًا. عند العمل دون طرفية، يجب تمرير `--agent` أو `--all` أو `--detected-only`. نفِّذ `clickhousectl skills --help` للاطلاع على أسماء الوكلاء المدعومين.

## البحث والملاحظات {#search-and-feedback}

```bash
clickhousectl search ip allow                   # Find commands and flags by keyword
clickhousectl search idle timeout --limit 10
clickhousectl feedback "cloud clickhouse create should accept a --wait flag"
```

يطابق `search <words>` كلمات البحث مع أسماء الأوامر وأوصافها وخيارات سطر الأوامر وسياق الوكيل، ويعرض الأوامر الأكثر تطابقًا (5 افتراضيًا). إذا لم يعثر البحث على أي تطابق، ينتهي برمز خروج 0 دون عرض نتائج.

يرسل `feedback` رسالة قصيرة (بحد أقصى 500 محرف) إلى فريق clickhousectl، دون طلب إدخال أو تأكيد. استخدمه لتوضيح ما تعذّر على واجهة سطر الأوامر تنفيذه أو ما كنت تتوقعه منها. ضع الخيارات مثل `--json` قبل الرسالة، ولا تضمّن بيانات اعتماد أو SQL أو أسماء المضيفين أو بيانات شخصية. عند استخدام بيانات اعتماد Cloud، تتضمن الرسالة معرّفات المؤسسات التي تتبع لها بيانات الاعتماد هذه. راجع [ما يُرسَل مع الملاحظات](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/feedback.md).

## التحديث الذاتي {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

يستبدل الأمر `update` النسخ المثبّتة باستخدام برنامج التثبيت النصي أو عن طريق التنزيل أو باستخدام Cargo. أما عند التثبيت باستخدام npm أو uv أو pipx أو pip، فينتهي برمز خروج 1 ويطبع أمر الترقية الخاص بمدير الحزم لتشغيله بدلاً منه.

تتحقق واجهة سطر الأوامر أيضاً من توفر تحديثات في الخلفية، مرة واحدة على الأكثر كل 24 ساعة (تُعاد محاولة التحقق بعد ساعة في حال فشله)، وتطبع إشعاراً عند توفر إصدار أحدث. اضبط `CLICKHOUSECTL_NO_UPDATE_CHECK=1` لتعطيل التحقق والإشعار.

## بيانات القياس عن بُعد {#telemetry}

يجمع `clickhousectl` بيانات استخدام مجهولة الهوية لتوجيه جهود التطوير. عند التشغيل الأول، يعرض إشعارًا ولا يرسل أي بيانات؛ ويبدأ جمع البيانات في تشغيل لاحق ما لم تعطّله.

يتضمن كل حدث ما يلي:

* مسار الأمر و**أسماء** خيارات سطر الأوامر والوسائط المُمرَّرة صراحةً، دون قيمها مطلقًا
* النتيجة ورمز الخروج
* عند كتابة أمر بشكل غير صحيح، اسم الأمر أو خيار سطر الأوامر الذي اقترحته واجهة سطر الأوامر، دون تسجيل ما كتبته مطلقًا
* عند حدوث إخفاقات أثناء التشغيل، فئات محددة: مرحلة الإخفاق ونوعه، ورمز حالة HTTP مدرج في قائمة السماح، وفئات إعادة المحاولة وحالة التجهيز والمدة
* إصدار واجهة سطر الأوامر ونظام التشغيل والمعمارية، وما إذا كانت تعمل ضمن CI، ووكيل البرمجة الذي تم اكتشافه

لا تُسجَّل مطلقًا قيم الوسائط أو SQL أو بيانات الاعتماد أو معرّفات الموارد أو الوسائط التي تلي `--` أو رسائل error. ولا يوجد معرّف للتثبيت أو الجهاز.

لإيقاف جمع البيانات:

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

اضبط `CHCTL_TELEMETRY_DEBUG=1` لطباعة الحمولة إلى stderr دون إرسال أي شيء. لا يؤدي إلغاء الاشتراك إلى تعطيل [`feedback`](#search-and-feedback)، الذي لا يرسل البيانات إلا عند تشغيله. راجع [تفاصيل بيانات القياس عن بُعد](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md).
