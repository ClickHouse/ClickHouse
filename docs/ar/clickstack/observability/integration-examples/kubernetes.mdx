اجمع سجلات الحاويات ومقاييس العُقد والعنقود وأحداث Kubernetes باستخدام مُجمِّعَين من مُجمِّعات OpenTelemetry: مجموعة عمليات خلفية (DaemonSet) على كل عقدة، ونشر (Deployment) واحد لجمع البيانات على مستوى العنقود بأكمله.

## المتطلبات المسبقة {#prerequisites}

* خدمة ClickHouse Observability
* عنقود Kubernetes يضم عُقد Linux، مع صلاحية إنشاء أحمال العمل وموارد ClusterRole وعمليات ربط مسارات المضيف (host-path)
* تهيئة `kubectl` للعنقود المستهدف، وتثبيت Helm 3
* إمكانية الوصول عبر الشبكة من جامعي البيانات إلى نقطة نهاية OTLP عبر HTTP الخاصة بخدمتك، وإلى واجهة برمجة تطبيقات Kubernetes، وإلى مكوّنات كيوبليت

يقتصر دور جامعي البيانات هؤلاء على جمع بيانات البنية التحتية. أمّا لإرسال مقاييس التطبيقات وبيانات التتبّع، فزوّد تطبيقاتك بأدوات جمع بيانات الرصد بشكل منفصل؛ راجع [تكاملات OpenTelemetry](/ar/clickstack/observability/ingesting-data/opentelemetry).

## بيانات الاتصال {#connection-details}

  <Tab title="مُدار بالكامل">

    افتح ClickHouse Observability وانتقل إلى **إعدادات الفريق ← البيانات ← بيانات القياس عن بُعد المُدارة**، ثم انسخ نقطة نهاية OTLP عبر HTTP ومفتاح API.

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    استخدم نقطة النهاية كما هي تمامًا، بما في ذلك المنفذ، ودون إضافة اللاحقة `/v1/logs` أو `/v1/metrics`.
  </Tab>

  <Tab title="مُدار ذاتيًا" id="self-managed">
    استخدم نقطة نهاية OTLP عبر HTTP الخاصة بجامع البيانات لديك، على أن يكون الوصول إليها ممكنًا من العنقود، واستخدم كذلك إعدادات المصادقة الخاصة به. إذا كانت المصادقة معطّلة، فاضبط `OTEL_EXPORTER_OTLP_AUTHORIZATION` على سلسلة فارغة واحذف كتلة `headers` الخاصة بالمُصدِّر أدناه. راجع [دليل الإعداد المُدار ذاتيًا](/ar/clickstack/self-configured/getting-started/managed).

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>

## نشر جامعي البيانات {#deploy-collectors}

<Steps>
  <Step title="أنشئ مساحة الأسماء واضبط إعدادات الاتصال" id="connection-settings">
    تحقق من أن `kubectl` يشير إلى العنقود المطلوب:

    ```bash
    kubectl config current-context
    kubectl create namespace observability --dry-run=client -o yaml | kubectl apply -f -

    kubectl create configmap observability-connection -n observability \
      --from-literal=endpoint="$OTEL_EXPORTER_OTLP_ENDPOINT" \
      --dry-run=client -o yaml | kubectl apply -f -

    kubectl create secret generic observability-connection -n observability \
      --from-literal=authorization="$OTEL_EXPORTER_OTLP_AUTHORIZATION" \
      --dry-run=client -o yaml | kubectl apply -f -
    ```

    يستخدم جامعا البيانات كلاهما هذه الإعدادات في مساحة الأسماء `observability`.
  </Step>

  <Step title="احفظ التهيئة المشتركة" id="shared-configuration">
    احفظ ما يلي في ملف باسم `k8s_common.yaml`:

    ```yaml
    image:
      repository: otel/opentelemetry-collector-contrib
      tag: "0.161.0"
    command:
      name: otelcol-contrib
    resources:
      limits:
        memory: 512Mi
    presets:
      kubernetesAttributes:
        enabled: true
    extraEnvs:
      - name: OTEL_EXPORTER_OTLP_ENDPOINT
        valueFrom:
          configMapKeyRef:
            name: observability-connection
            key: endpoint
      - name: OTEL_EXPORTER_OTLP_AUTHORIZATION
        valueFrom:
          secretKeyRef:
            name: observability-connection
            key: authorization
    service:
      enabled: false
    ports:
      otlp:
        enabled: false
      otlp-http:
        enabled: false
      jaeger-compact:
        enabled: false
      jaeger-thrift:
        enabled: false
      jaeger-grpc:
        enabled: false
      zipkin:
        enabled: false
    config:
      receivers:
        otlp: null
        jaeger: null
        zipkin: null
        prometheus: null
      exporters:
        debug: null
        otlp_http/observability:
          endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
          headers:
            authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
          compression: gzip
      processors:
        batch:
          timeout: 5s
          send_batch_size: 500
          send_batch_max_size: 500
      service:
        pipelines:
          logs:
            receivers: []
            exporters: [otlp_http/observability]
          metrics:
            receivers: []
            exporters: [otlp_http/observability]
          traces: null
    ```

    تضيف الإعدادات المسبقة في مخطط Helm المستقبِلات، ومعالج البيانات الوصفية لـ Kubernetes، وقواعد RBAC، وعمليات الربط التي يحتاجها كل جامع بيانات. أما التهيئة المشتركة فتُعيد توجيه السجلات والمقاييس إلى خدمتك، وتعطّل مستقبِلات إدخال بيانات التطبيقات غير المستخدمة.
  </Step>

  <Step title="تهيئة جمع البيانات من العقد" id="daemonset-configuration">
    احفظ ما يلي في ملف باسم `k8s_daemonset.yaml`:

    ```yaml
    mode: daemonset
    presets:
      logsCollection:
        enabled: true
        storeCheckpoints: true
      hostMetrics:
        enabled: true
      kubeletMetrics:
        enabled: true
    config:
      receivers:
        kubeletstats:
          insecure_skip_verify: true
    ```

    تقرأ مجموعة العمليات الخلفية سجلات الحاويات وتجمع مقاييس المضيف وكيوبليت. وتحفظ نقاط التحقق مواضع قراءة السجلات بحيث لا تضيع عند إعادة تشغيل جامع البيانات. ويشغّل هذا الإعداد المسبق جامع البيانات بصلاحيات root ليتمكّن من كتابة نقاط التحقق على العقدة، لذا يجب أن تسمح إعدادات أمان الـ pod في العنقود لديك بعمليات ربط مسارات المضيف التي يستخدمها.

    يتخطى هذا المثال التحقق من شهادات كيوبليت في العناقيد التي لا يثق فيها جامع البيانات بشهادات كيوبليت. إذا كان العنقود لديك يوفّر شهادات كيوبليت موثوقة، فاضبط `insecure_skip_verify` على `false` وهيّئ الـ CA المناسبة.
  </Step>

  <Step title="تهيئة جمع البيانات من العنقود" id="deployment-configuration">
    احفظ ما يلي باسم `k8s_deployment.yaml`:

    ```yaml
    mode: deployment
    replicaCount: 1
    presets:
      kubernetesEvents:
        enabled: true
      clusterMetrics:
        enabled: true
    ```

    اكتفِ بنسخة واحدة فقط (replica) لتجنّب جمع مقاييس العنقود وأحداثه بشكل مكرّر.
  </Step>

  <Step title="ثبّت إصدارات Helm" id="install-collectors">
    نفّذ الأوامر التالية من الدليل الذي يحتوي على ملفات التهيئة الثلاثة. تستخدم هذه الأمثلة الإصدار `0.175.1` من مخطط Helm الخاص بمُجمِّع OpenTelemetry، والإصدار `0.161.0` من Collector Contrib:

    ```bash
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update open-telemetry

    helm upgrade --install observability-nodes open-telemetry/opentelemetry-collector \
      --version 0.175.1 --namespace observability \
      -f k8s_common.yaml -f k8s_daemonset.yaml --wait

    helm upgrade --install observability-cluster open-telemetry/opentelemetry-collector \
      --version 0.175.1 --namespace observability \
      -f k8s_common.yaml -f k8s_deployment.yaml --wait
    ```

    تحقق من جامعي البيانات:

    ```bash
    kubectl get pods -n observability
    kubectl logs -n observability -l app.kubernetes.io/instance=observability-nodes --tail=50
    kubectl logs -n observability -l app.kubernetes.io/instance=observability-cluster --tail=50
    ```

    إذا كانت عُقدك تحمل علامات taints خاصة بالجدولة، فأضف قيم `tolerations` المناسبة إلى الملف `k8s_daemonset.yaml` للعُقد التي تعتزم مراقبتها.
  </Step>

  <Step title="تحقق من البيانات" id="verify-data">
    انتظر حتى تمر بضع فترات جمع، ثم افتح ClickHouse Observability:

    * في صفحة **بحث**، اختر المصدر **Logs** والمدة **Last 15 minutes**. وسّع أحد سجلات الحاويات وتحقق من السمات مثل `k8s.namespace.name` و`k8s.pod.name` و`k8s.node.name`.
    * في **مستكشف المخططات**، اختر المصدر **Metrics** وابحث عن المقاييس التي تبدأ بـ `k8s.` أو `system.`.
    * راجع المصدر **Logs** لرصد أحداث Kubernetes فور وقوعها. يتوقف حجم الأحداث على مستوى النشاط في العنقود.
  </Step>
</Steps>

## البيانات الوصفية للتطبيق {#application-metadata}

بالنسبة إلى التطبيقات المزوّدة بأدوات الرصد، أضف البيانات الوصفية للـ pod باستخدام واجهة downward API في Kubernetes. ادمج قائمة `env` هذه في التهيئة الحالية لحاوية تطبيقك، مع الإبقاء على سمات الموارد الموجودة مسبقًا:

```yaml
env:
  - name: OTEL_SERVICE_NAME
    value: my-app
  - name: POD_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name
  - name: POD_UID
    valueFrom:
      fieldRef:
        fieldPath: metadata.uid
  - name: POD_NAMESPACE
    valueFrom:
      fieldRef:
        fieldPath: metadata.namespace
  - name: NODE_NAME
    valueFrom:
      fieldRef:
        fieldPath: spec.nodeName
  - name: OTEL_RESOURCE_ATTRIBUTES
    value: k8s.pod.name=$(POD_NAME),k8s.pod.uid=$(POD_UID),k8s.namespace.name=$(POD_NAMESPACE),k8s.node.name=$(NODE_NAME)
```

يُثري معالج البيانات الوصفية في Kubernetes سجلات الحاويات المُجمَّعة بالبيانات الوصفية لعبء العمل. أما متغيرات التطبيق هذه، فتُرفق هوية الـ pod ببيانات القياس عن بُعد التي يُصدرها OpenTelemetry SDK الخاص بتطبيقك.

## استكشاف الأخطاء وإصلاحها {#troubleshooting}

### تعذّر بدء تشغيل جامعي البيانات {#collectors-not-starting}

افحص أحداث الـ pod باستخدام `kubectl describe pod -n observability POD_NAME`. تحقّق من سحب صور الحاويات، وقيود الجدولة، وقيود أمان الـ pod، وتأكّد من وجود الـ ConfigMap والـ Secret في مساحة الأسماء نفسها التي تضم الإصدارات.

### لا تظهر أي سجلات أو مقاييس {#no-data}

افحص سجلات جامع البيانات بحثًا عن أخطاء في المصادقة أو أخطاء التصدير. وتأكد من إمكانية الوصول إلى نقطة نهاية الوجهة من داخل العنقود. أما أخطاء كيوبليت، فافحص الاتصال بالمنفذ `10250`، وإعدادات الشهادة، وصلاحيات RBAC المُنشأة. ويتطلب جمع سجلات الحاويات الوصول إلى الدليل `/var/log/pods` على العقدة؛ وقد لا تدعم بيئات العقد المقيَّدة أو البيئات بلا خوادم عمليات الربط هذه من المضيف.

### تغيير إعدادات الاتصال {#connection-settings-changed}

بعد تحديث ConfigMap أو Secret، أعد تشغيل جامعي البيانات لإعادة تحميل متغيرات البيئة الخاصة بها:

```bash
kubectl rollout restart daemonset -n observability -l app.kubernetes.io/instance=observability-nodes
kubectl rollout restart deployment -n observability -l app.kubernetes.io/instance=observability-cluster
```
