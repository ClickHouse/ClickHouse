اجمع سجلات systemd journal باستخدام مستقبِل journald في OpenTelemetry، ثم أرسلها إلى ClickHouse Observability. ويمكنك استخدام [مجموعة البيانات التجريبية](#demo-dataset) لتجربة التكامل دون الحاجة إلى مضيف Linux.

## المتطلبات المسبقة {#prerequisites}

* خدمة ClickHouse Observability
* لاستخدام سجلاتك الخاصة: مضيف Linux يعمل بنظام systemd، مع توفر `journalctl` وصلاحية قراءة الـ journal الخاص به
* `curl`، وDocker لتشغيل العرض التوضيحي

### بيانات الاتصال {#connection-details}

<Tabs>
  <Tab title="مُدار بالكامل">
    <BetaBadge label="خدمة في المرحلة التجريبية" />

    افتح ClickHouse Observability وانتقل إلى **إعدادات الفريق ← بيانات ← بيانات القياس عن بُعد المُدارة**. انسخ نقطة نهاية OTLP عبر HTTP ومفتاح API الخاصين بك. يمكنك استخدام **نسخ بيانات الاتصال** لنسخ التهيئة، أو **إظهار المفتاح** لعرض المفتاح المحجوب.

    <div className="ch-image-lg">
      <Frame>
        ![بيانات الاتصال في قسم بيانات القياس عن بُعد المُدارة](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    لاستخدام أمثلة مُصدِّر OTLP أدناه، عيّن المتغيرات التالية في الطرفية التي ستشغّل منها جامع البيانات:

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    استبدل العناصر النائبة بنقطة النهاية الدقيقة لخدمتك، بما في ذلك المنفذ، وبمفتاح API الخاص بها. استخدم نقطة نهاية HTTP الأساسية دون اللاحقة `/v1/logs`؛ إذ يُلحق المُصدِّر مسار الإشارة تلقائيًا.
  </Tab>

  <Tab title="مُدار ذاتيًا">
    استخدم نقطة نهاية OTLP عبر HTTP الخاصة بجامع البيانات، على أن يكون الوصول إليها ممكنًا (مثل `http://YOUR_COLLECTOR_HOST:4318`)، إلى جانب إعدادات المصادقة. إذا كان جامع البيانات لا يتطلب المصادقة، فاحذف كتلة `headers` الخاصة بالمُصدِّر من التهيئات أدناه. راجع [دليل البدء للإصدار المُدار ذاتيًا](/ar/clickstack/self-configured/getting-started/managed) للاطلاع على إرشادات الإعداد.

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

يجب أن يكون الوصول إلى نقطة النهاية ممكنًا من المضيف الخاضع للمراقبة أو من جامع البيانات التجريبي. أما إذا كان جامع البيانات الوجهة يعمل على مضيف Docker، فاستخدم `http://host.docker.internal:4318`.

## التكامل مع الأنظمة القائمة {#existing-systems}

<Steps>
  <Step title="تحقّق من journal" id="verify-systemd">
    على مضيف Linux الذي تريد مراقبته:

    ```bash
    systemctl --version
    sudo journalctl -n 20
    sudo journalctl --disk-usage
    ```

    يستخدم المستقبِل الأداة `journalctl` على المضيف لقراءة سجلات journal المتاحة. ويدعم التخزين الدائم والمؤقت لسجلات journal على حدٍّ سواء، لذا لا حاجة إلى تغيير إعدادات التخزين.
  </Step>

  <Step title="نزّل جامع البيانات" id="download-collector">
    شغّل هذه الأوامر على مضيف Linux الخاضع للمراقبة:

    ```bash
    case "$(uname -m)" in
      x86_64) arch=amd64 ;;
      aarch64|arm64) arch=arm64 ;;
      *) echo "Unsupported architecture"; exit 1 ;;
    esac
    curl -fL -o otelcol-contrib.tar.gz \
      "https://github.com/open-telemetry/opentelemetry-collector-releases/releases/download/v0.161.0/otelcol-contrib_0.161.0_linux_${arch}.tar.gz"
    tar -xzf otelcol-contrib.tar.gz otelcol-contrib
    ```

    يعمل جامع البيانات مباشرةً على المضيف ليتمكّن من استخدام الأداة `journalctl` المثبّتة عليه، إذ لا تتضمّن صورة Docker القياسية لإصدار Contrib هذا الملف التنفيذي.
  </Step>

  <Step title="تهيئة جامع البيانات" id="configure-collector">
    احفظ ما يلي في ملف باسم `systemd-monitoring.yaml`:

    ```yaml
    receivers:
      journald:
        start_at: end
        priority: info
        convert_message_bytes: true
    processors:
      transform/journald:
        error_mode: ignore
        log_statements:
          - context: log
            statements:
              - merge_maps(log.attributes, log.body, "upsert")
              - set(resource.attributes["host.name"], log.attributes["_HOSTNAME"])
              - set(resource.attributes["service.name"], "systemd-logs")
              - set(log.attributes["unit"], log.attributes["SYSLOG_IDENTIFIER"])
              - set(log.attributes["unit"], log.attributes["_SYSTEMD_UNIT"]) where log.attributes["_SYSTEMD_UNIT"] != nil
              - set(log.attributes["priority"], log.attributes["PRIORITY"])
              - set(log.body, log.attributes["MESSAGE"])
              - set(log.severity_text, "info")
              - set(log.severity_number, SEVERITY_NUMBER_INFO)
              - set(log.severity_text, "warn") where Int(log.attributes["PRIORITY"]) == 4
              - set(log.severity_number, SEVERITY_NUMBER_WARN) where log.severity_text == "warn"
              - set(log.severity_text, "error") where Int(log.attributes["PRIORITY"]) == 3
              - set(log.severity_number, SEVERITY_NUMBER_ERROR) where log.severity_text == "error"
              - set(log.severity_text, "fatal") where Int(log.attributes["PRIORITY"]) < 3
              - set(log.severity_number, SEVERITY_NUMBER_FATAL) where log.severity_text == "fatal"
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [journald]
          processors: [transform/journald, batch]
          exporters: [otlp_http/observability]
    ```

    تُحفَظ حقول journal بوصفها سمات للسجل، وتصبح الرسالة متن السجل، بينما يصبح اسم المضيف attribute للمورد. يجمع المستقبِل جميع الوحدات ذات الأولوية `info` فما فوق. ولحصر نطاق الجمع، أضف قائمة `units` ضمن `journald` تتضمّن أسماء الوحدات الفعلية على المضيف لديك، مثل `ssh.service` أو `nginx.service`.
  </Step>

  <Step title="شغّل جامع البيانات" id="run-collector">
    اضبط [متغيرات الاتصال](#connection-details)، ثم شغّل الأمر من دليل التنزيل. يستخدم هذا الأمر صلاحيات المسؤول لقراءة journal الخاص بالنظام، ولا يحتفظ إلا بمتغيرَي الاتصال:

    ```bash
    sudo --preserve-env=OTEL_EXPORTER_OTLP_ENDPOINT,OTEL_EXPORTER_OTLP_AUTHORIZATION \
      ./otelcol-contrib --config=systemd-monitoring.yaml
    ```

    أبقِ الطرفية مفتوحة، ثم أنشئ إدخالًا في journal من طرفية أخرى:

    ```bash
    echo 'ClickHouse Observability journal ingestion test' | systemd-cat -t observability-test -p info
    ```

    أوقف جامع البيانات بالضغط على **Ctrl+C** عند الانتهاء من الاختبار. ولجمع البيانات بشكل مستمر، شغّله كخدمة systemd تتمتع بصلاحية الوصول إلى journal، وهيّئ [تخزين المؤشر](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.161.0/receiver/journaldreceiver#cursor-tracking) ليستأنف العمل بعد إعادة التشغيل.
  </Step>

  <Step title="تحقّق من السجلات" id="verify-logs">
    افتح صفحة **بحث**، واختر **Logs**، وطبّق عامل تصفية على `ServiceName:systemd-logs`، ثم اختر **Last 15 minutes**. ابحث عن رسالة الاختبار والسمات مثل `unit` و`priority`.
  </Step>
</Steps>

## مجموعة بيانات تجريبية {#demo-dataset}

تحتوي العينة على 1,334 عنصرًا نصيًا من عناصر السجل تغطي نحو 48 ساعة، وتشمل نشاط SSH والمهام المجدولة وأحداث الخدمات. وتعتمد على المستقبِل `filelog`، لذا لا حاجة إلى تثبيت systemd أو `journalctl`. يحدّث جامع البيانات الطوابع الزمنية مع الحفاظ على النصوص الأصلية للرسائل والفواصل الزمنية بين الأحداث.

<Steps>
  <Step title="تنزيل العينة" id="download-sample">
    ```bash
    curl -fL -o systemd-demo.log \
      https://datasets-documentation.s3.eu-west-3.amazonaws.com/clickstack-integrations/systemd/systemd-demo.log
    ```
  </Step>

  <Step title="تهيئة جامع البيانات التجريبي" id="configure-demo">
    احفظ ما يلي باسم `systemd-demo.yaml`:

    ```yaml
    receivers:
      filelog/systemd:
        include:
          - /var/log/demo/systemd-demo.log
        start_at: beginning
        operators:
          - type: regex_parser
            regex: '^(?P<timestamp>\S+) (?P<hostname>\S+) (?P<unit>\S+?)(?:\[(?P<pid>\d+)\])?: (?P<message>.*)$'
            parse_from: body
            parse_to: attributes
          - type: time_parser
            parse_from: attributes.timestamp
            layout: '%Y-%m-%dT%H:%M:%S%z'
          - type: add
            field: attributes.source
            value: systemd-demo
          - type: add
            field: resource["service.name"]
            value: systemd-demo
    processors:
      transform/demo_timestamps:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(resource.attributes["host.name"], log.attributes["hostname"])
              - set(log.time, Now() - Duration("2m") - (Time("2025-11-16T23:45:00Z", "%Y-%m-%dT%H:%M:%SZ") - log.time))
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [filelog/systemd]
          processors: [transform/demo_timestamps, batch]
          exporters: [otlp_http/observability]
    ```

    لا تتضمن العينة النصية حقل الأولوية الخاص بـ journal، لذا لا يستنتج العرض التوضيحي مستوى الخطورة من نص الرسالة.
  </Step>

  <Step title="تشغيل جامع البيانات التجريبي" id="run-demo">
    اضبط [متغيرات الاتصال](#connection-details)، ثم شغّل الأمر التالي من المجلد الذي يحتوي على الملفين:

    ```bash
    docker run --rm --name systemd-demo-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/systemd-demo.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      -v "$(pwd)/systemd-demo.log:/var/log/demo/systemd-demo.log:ro" \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```

    اترك الطرفية مفتوحة أثناء التحقق من استيعاب البيانات، وأوقف التشغيل بالضغط على **Ctrl+C** عند الانتهاء. وعند تشغيل العرض التوضيحي مجددًا، يُعاد استيعاب العينة بطوابع زمنية محدَّثة.
  </Step>

  <Step title="التحقق من سجلات العرض التوضيحي" id="verify-demo">
    افتح **بحث**، واختر **Logs**، ثم صفِّ النتائج باستخدام `ServiceName:systemd-demo`، واختر **آخر يومين**. من المفترض أن تظهر عناصر العينة مع السمات `unit` و`hostname` و`message`.

    <div className="ch-image-lg">
      <Frame>
        ![سجلات systemd التجريبية في صفحة البحث في ClickHouse Observability](/images/clickstack/observability-systemd-demo-logs.png)
      </Frame>
    </div>
  </Step>
</Steps>

## استكشاف الأخطاء وإصلاحها {#troubleshooting}

### لم يتم العثور على journalctl {#journalctl-not-found}

شغّل جامع البيانات الفعلي على مضيف Linux الخاضع للمراقبة، مع التأكد من تثبيت `journalctl` وإتاحته ضمن مسار التنفيذ الخاص به. أما العرض التوضيحي فيستخدم `filelog` ولا يحتاج إليه.

### عدم ظهور السجلات {#no-logs}

تحقق من مخرجات جامع البيانات بحثًا عن أخطاء في الوصول إلى journal أو في المصادقة أو أخطاء التصدير. تأكد من أن الأمر `sudo journalctl -n 20` يُعيد إدخالات على المضيف الخاضع للمراقبة. وإذا هيّأت عامل تصفية للوحدات، فتأكد من أنه يطابق أسماء خدماتك. ثم أنشئ إدخالًا جديدًا بعد بدء الجمع.

في ClickHouse Observability، تحقق من المصدر **Logs** وعامل تصفية اسم الخدمة والنطاق الزمني. وفي العرض التوضيحي، اختر **آخر يومين** وتأكد من ربط ملف العينة بالمسار الذي هيّأته.
