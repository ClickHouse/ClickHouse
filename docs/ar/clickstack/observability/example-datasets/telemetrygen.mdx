  <Tab title="مُدار بالكامل">
    <BetaBadge label="عرض تجريبي" />

    [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen) هو مولّد البيانات ضمن OpenTelemetry Collector Contrib. يُصدر سجلات وتتبّعات ومقاييس OTLP اصطناعية، ويوفّر خيارات سطر أوامر تتيح لك التحكم في شكل البيانات: خدمات متعددة، ومستويات خطورة السجلات، وحالات span ومقاطع التتبع الفرعية، وأنواع مختلفة من المقاييس. استخدمه لإرسال بيانات اختبار إلى ClickHouse Observability المُدار بالكامل، ثم استكشف النتائج في صفحتَي «بحث» و«مستكشف المخططات».

    <Steps>
      <Step title="متطلبات مسبقة" id="prerequisites-managed">
        يلزمك وجود خدمة ClickHouse Observability مُدارة بالكامل قائمة مسبقًا، وإمكانية الوصول عبر الشبكة إلى نقطة نهاية بيانات القياس عن بُعد المُدارة الخاصة بها. راجع [دليل بدء الاستخدام للخدمة المُدارة بالكامل](/ar/clickstack/observability/getting-started).
      </Step>

      <Step title="ثبّت telemetrygen" id="install-telemetrygen-managed">
        بعد تثبيت Docker وتشغيله، عرِّف غلافًا لتشغيل `telemetrygen` من صورة الحاوية الرسمية الخاصة به:

        ```shell
        telemetrygen() {
          docker run --rm \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        ```

        أو ثبّت الملف التنفيذي باستخدام Go:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        ```
      </Step>

      <Step title="ضبط متغيرات البيئة" id="set-env-vars-managed">
        افتح خدمة ClickHouse Observability وانتقل إلى **إعدادات الفريق → Managed Telemetry**. ثم انسخ **نقطة نهاية OTLP HTTP** و**مفتاح API**.

        <div className="ch-image-lg">
          <Frame>
            ![صفحة Managed Telemetry في إعدادات الفريق، وتظهر فيها نقطة نهاية OTLP HTTP ومفتاح API بقيم مخفية](/images/clickstack/getting-started/observability-managed-telemetry.png)
          </Frame>
        </div>

        اضبط نقطة النهاية بحيث تقتصر على المضيف والمنفذ، مع حذف البادئة `https://`. فمثلًا، تصبح القيمة `https://YOUR_OTEL_ENDPOINT:4318` على النحو `YOUR_OTEL_ENDPOINT:4318`. ولا تُلحق بها مسار إشارة مثل `/v1/logs`.

        ```shell
        export OTEL_ENDPOINT='YOUR_OTEL_ENDPOINT:4318'
        printf "API key: "
        read -r -s OTEL_API_KEY
        printf "\n"
        export OTEL_API_KEY
        ```

        عرّف دالة مساعدة صغيرة باسم `tg` كي لا يحدد كل أمر سوى القيم المتغيرة (الخدمة، ومستوى الخطورة، وstatus، والسمات):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint "${OTEL_ENDPOINT}" --otlp-http \
          --otlp-header "authorization=\"Bearer ${OTEL_API_KEY}\"" \
          --rate 5 --duration 30s "$@"; }
        ```

        تستخدم العملية المساعدة بروتوكول OTLP HTTP عبر TLS مع التحقق من الشهادة، لذا احذف الخيارين `--otlp-insecure` و`--otlp-insecure-skip-verify`. يعمل كل أمر لمدة 30 ثانية، ويُجري التحقق من الهوية باستخدام مفتاح API المُدار الخاص ببيانات القياس عن بُعد.
      </Step>

      <Step title="إنشاء سجلات" id="generate-logs-managed">
        أرسل سجلات بمستوى المعلومات والتحذير والخطأ من ثلاث خدمات:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        أكثر خيارات سطر الأوامر فائدةً للسجلات:

        * يعيّن `--service` قيمة `service.name` لكي يمكن نسب الأحداث إلى خدمة بعينها.
        * يحدّد `--severity-text` و`--severity-number` المستوى (تتراوح قيمة `severity-number` بين 1 و24).
        * يعيّن `--body` رسالة السجل.
        * يعيّن `--otlp-attributes` السمات على مستوى المورد (`key="value"` أو `key=true` أو `key=<integer>`).
        * يعيّن `--telemetry-attributes` السمات الخاصة بكل سجل على حدة.
      </Step>

      <Step title="توليد بيانات التتبّع" id="generate-traces-managed">
        أرسل بيانات تتبّع متعددة الـ span بحالات نجاح وحالات error من عدة خدمات. يُنشئ كل أمر بيانات تتبّع مستقلة؛ ولا تُنشئ هذه الأمثلة استدعاءات بين الخدمات:

        ```shell
        # Healthy services: the bulk of the traffic, all spans Ok
        for svc in frontend checkout cart; do
          tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes "http.route=\"/$svc\""
        done

        # A service with slower spans and errors
        tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.route="/charge"'
        ```

        أكثر خيارات سطر الأوامر فائدةً لبيانات التتبّع:

        * يُنشئ `--child-spans` العدد المحدد من مقاطع التتبع الفرعية لكل تتبّع، مما يمنح كل تتبّع عمقًا فعليًا.
        * يحدد `--span-duration` المدة التي يستغرقها كل span (مثل `120ms` و`2s`).
        * تكون قيمة `--status-code` إحدى القيم `Unset` أو `Error` أو `Ok` (أو `0` أو `1` أو `2`). استخدم `Error` لاختبار طرق عرض الأخطاء.
        * يضيف `--span-links` روابط بين مقاطع التتبع.
        * يُشغّل `--workers` عدة مولّدات بالتوازي للحصول على حجم بيانات أكبر وأكثر تنوعًا.
      </Step>

      <Step title="توليد المقاييس" id="generate-metrics-managed">
        أرسِل مقياسًا من نوع sum، ومقياسًا من نوع gauge، ومُدرَّجًا تكراريًا (histogram). هذه القيم اصطناعية، وليست قياسات فعلية لنظامك. يتوقف كل أمر تلقائيًا بعد 30 ثانية:

        ```shell
        tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
        tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
        tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
        ```

        يقبل الخيار `--metric-type` القيم `Gauge` أو `Sum` أو `Histogram` أو `ExponentialHistogram`. ويحدد `--otlp-metric-name` اسم سلسلة البيانات لتتمكن من العثور عليها في UI، أما `--aggregation-temporality` فقيمته إما `delta` أو `cumulative`.
      </Step>

      <Step title="تحقّق من النتائج في ClickHouse Observability" id="verify-managed">
        افتح خدمة ClickHouse Observability. في عرض `Search`، اضبط النطاق الزمني على `Last 15 minutes` وبدّل المصدر بين `Logs` و`Traces`. طبّق عامل تصفية على `ServiceName` لعرض خدمات `frontend` و`checkout` و`cart` و`payment`، وعامل تصفية آخر على `SeverityText` للعثور على أسطر السجل الخاصة بالتحذيرات والأخطاء. افتح تتبّعًا لخدمة `payment` لعرض مقاطع التتبع الفرعية وحالة الخطأ. افتح `Chart Explorer`، واختر `Metrics`، ثم أنشئ مخططًا لأحد أسماء المقاييس التي ضبطتها سابقًا (مثل `http.server.requests`) للتحقق من إدخال المقاييس.
      </Step>
    </Steps>
  </Tab>

  <Tab title="مُدار ذاتيًا" id="self-managed">
    [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen) هو مولّد البيانات ضمن OpenTelemetry Collector Contrib. يُنتج سجلات وتتبّعات ومقاييس OTLP اصطناعية، ويوفّر خيارات سطر أوامر تتيح لك التحكم في شكل البيانات: خدمات متعددة، ومستويات خطورة السجلات، وحالات span ومقاطع التتبع الفرعية، وأنواع مختلفة من المقاييس. استخدمه للتحقق من أن مُجمِّع OpenTelemetry الخاص بـ ClickStack يستقبل البيانات، وأن أحداثًا متنوعة وواقعية تظهر في UI إمكانية المراقبة.

    يفترض هذا الدليل أن جامع البيانات قيد التشغيل مسبقًا، مع إتاحة نقاط نهاية OTLP على المنفذين `4317` (gRPC) و`4318` (HTTP).

    <Steps>
      <Step title="المتطلبات المسبقة" id="prerequisites-managed-self-configured">
        يفترض هذا الدليل أنك أكملت [دليل البدء الخاص بـ ClickHouse Observability — Self-managed](/ar/clickstack/self-configured/getting-started/managed)، وأن لديك جامع بيانات OpenTelemetry قيد التشغيل، مع إمكانية الوصول إلى نقطتَي النهاية OTLP gRPC (`4317`) وHTTP (`4318`) من الجهاز الذي تشغّل عليه `telemetrygen`. وإذا كنت قد [أمّنت جامع البيانات](/ar/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured) باستخدام `OTLP_AUTH_TOKEN`، فأبقِ هذه القيمة في متناول يدك.
      </Step>

      <Step title="ثبّت telemetrygen" id="install-telemetrygen-managed-self-configured">
        شغّل `telemetrygen` من صورة Docker الخاصة به (دون الحاجة إلى تثبيته). عرّف غلافًا صغيرًا لتبقى الأوامر أدناه سهلة القراءة؛ إذ يتيح الخيار `--add-host` للحاوية الوصول إلى جامع البيانات الذي يستمع على المضيف:

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        أو ثبّت الملف التنفيذي باستخدام Go ووجّهه إلى `localhost` بدلاً من ذلك:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```
      </Step>

      <Step title="ضبط متغيرات البيئة" id="set-env-vars-managed-self-configured">
        صدِّر رمز المصادقة إذا كان جامع البيانات محميًّا:

        ```shell
        export OTLP_AUTH_TOKEN=<your_otlp_auth_token>
        ```

        <Info>
          **جامع بيانات غير مؤمَّن**

          لا يفرض مُجمِّع OpenTelemetry الخاص بـ ClickStack المصادقة افتراضيًا. إذا لم تتبع خطوات [تأمين جامع البيانات](/ar/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured) لتعيين `OTLP_AUTH_TOKEN`، فاحذف السطر `--otlp-header` من الدالة المساعدة أدناه.
        </Info>

        عرِّف دالة مساعدة صغيرة باسم `tg` كي لا يحدد كل أمر سوى القيم المتغيرة (الخدمة، ومستوى الخطورة، والحالة، والسمات):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 30s "$@"; }
        ```
      </Step>

      <Step title="إنشاء سجلات" id="generate-logs-managed-self-configured">
        أرسل السجلات بمزيج واقعي من مستويات الخطورة عبر الخدمات، أغلبها رسائل معلوماتية مع تحذير واحد وخطأ واحد، بدلاً من دفق واحد متجانس:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        أكثر خيارات سطر الأوامر فائدةً للسجلات:

        * يعيّن `--service` قيمة `service.name` لكي تُنسب الأحداث إلى خدمة بعينها.
        * يحدّد `--severity-text` و`--severity-number` المستوى (تتراوح قيمة `severity-number` بين 1 و24).
        * يعيّن `--body` رسالة السجل.
        * يعيّن `--otlp-attributes` السمات على مستوى المورد (`key="value"` أو `key=true` أو `key=<integer>`).
        * يعيّن `--telemetry-attributes` السمات الخاصة بكل سجل على حدة.
      </Step>

      <Step title="توليد التتبّع" id="generate-traces-managed-self-configured">
        أرسل عمليات تتبّع تضم عدة span من عدة خدمات سليمة، إضافةً إلى تبعية واحدة فاشلة. يمنح ذلك خريطة الخدمات (Service Map) شكلًا واقعيًا، إذ تكون معظم الخدمات سليمة باستثناء خدمة واحدة تُصدر أخطاء، كما يملأ طرق عرض الأخطاء بالبيانات:

        ```shell
        # Healthy services: the bulk of the traffic, all spans Ok
        for svc in frontend checkout cart; do
          tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes "http.route=\"/$svc\""
        done

        # One slow dependency returning errors
        tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.route="/charge"'
        ```

        أكثر خيارات سطر الأوامر فائدةً لبيانات التتبّع:

        * يُنشئ `--child-spans` العدد المحدَّد من مقاطع التتبع الفرعية لكل تتبّع، مما يمنح كل تتبّع عمقًا حقيقيًا.
        * يحدّد `--span-duration` مدة كل span (مثل `120ms` أو `2s`).
        * تأخذ `--status-code` إحدى القيم `Unset` أو `Error` أو `Ok` (أو `0` أو `1` أو `2`). استخدم `Error` لاختبار طرق عرض الأخطاء.
        * يضيف `--span-links` روابط بين مقاطع التتبع.
        * يشغّل `--workers` عدة مولّدات بالتوازي لإنتاج حجم بيانات أكبر وأكثر تنوعًا.
      </Step>

      <Step title="توليد المقاييس" id="generate-metrics-managed-self-configured">
        أرسل الأنواع الثلاثة الشائعة من المقاييس لكي تحتوي لوحات المعلومات على عدادات ومقاييس من نوع Gauge وتوزيع (distribution). وبخلاف بعض المولّدات، يلتزم `telemetrygen` بالخيار `--duration` في المقاييس، لذا لا داعي لإيقافه يدويًا:

        ```shell
        tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
        tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
        tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
        ```

        يقبل `--metric-type` القيم `Gauge` أو `Sum` أو `Histogram` أو `ExponentialHistogram`. ويحدد `--otlp-metric-name` اسم سلسلة البيانات لتتمكن من العثور عليها في UI، أما `--aggregation-temporality` فقيمته إما `delta` أو `cumulative`.
      </Step>

      <Step title="تحقّق من خلال UI الخاصة بإمكانية المراقبة" id="verify-managed-self-configured">
        افتح واجهة UI الخاصة بإمكانية المراقبة من وحدة تحكم ClickHouse Cloud. في عرض `Search`، اضبط النطاق الزمني على `Last 15 minutes` وبدّل المصدر بين `Logs` و`Traces`. طبّق عامل تصفية على `ServiceName` لعرض الخدمات `frontend` و`checkout` و`cart` و`payment`، وعلى `SeverityText` للعثور على أسطر السجل الخاصة بالتحذيرات والأخطاء. افتح تتبّعًا لخدمة `payment` لعرض مقاطع التتبع الفرعية وحالة الخطأ. افتح `Chart Explorer`، واختر `Metrics`، ثم أنشئ مخططًا لأحد أسماء المقاييس التي ضبطتها سابقًا (مثل `http.server.requests`) للتحقق من إدخال المقاييس.
      </Step>
    </Steps>
