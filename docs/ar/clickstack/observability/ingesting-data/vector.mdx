    <Note>
      ينطبق هذا الدليل على **ClickHouse Observability المُدار ذاتيًا** فقط. إذ تكتب وجهة بيانات ClickHouse في Vector مباشرةً إلى جداول تديرها بنفسك. أما ClickHouse Observability المُدار بالكامل فيتطلب إدخال البيانات عبر OTLP؛ راجع [استيعاب البيانات باستخدام OpenTelemetry](/ar/clickstack/observability/ingesting-data/opentelemetry#fully-managed) للاطلاع على إعدادات نقطة النهاية والمصادقة.
    </Note>

    [Vector](https://vector.dev) هو خط معالجة بيانات عالي الأداء ومحايد تجاه المورّدين مخصص لبيانات إمكانية المراقبة. يُستخدم عادةً لجمع السجلات والمقاييس وتحويلها وتوجيهها من مجموعة واسعة من المصادر، ويحظى بشعبية خاصة في إدخال السجلات بفضل مرونته وانخفاض استهلاكه للموارد.

    عند استخدام Vector مع Self-managed ClickHouse Observability، يتولى المستخدمون مسؤولية تعريف المخططات الخاصة بهم. ويمكن أن تتبع هذه المخططات اصطلاحات OpenTelemetry، كما يمكن أن تكون مخصصة بالكامل لتمثّل بنى أحداث يحددها المستخدم. وعمليًا، يُستخدم إدخال البيانات عبر Vector في الغالب مع **السجلات**، إذ يرغب المستخدمون في التحكم الكامل في التحليل النحوي والإثراء قبل كتابة البيانات في ClickHouse.

    يركّز هذا الدليل على الإعداد الأولي لاستيعاب البيانات في Self-managed ClickHouse Observability باستخدام Vector. وللتبسيط، لا يتناول بالتفصيل مصادر Vector أو تهيئة مسارات المعالجة، بل يركّز على تهيئة **وجهة البيانات** (sink) التي تكتب البيانات إلى ClickHouse، وعلى ضمان توافق المخطط الناتج مع Self-managed ClickHouse Observability.

    الشرط الأساسي الوحيد للخدمة هو أن تتضمن البيانات **عمودًا للطابع الزمني** (أو حقلًا زمنيًا مكافئًا)، ويمكن تحديده عند تهيئة مصدر البيانات في واجهة UI الخاصة بإمكانية المراقبة.

## إرسال البيانات باستخدام Vector {#sending-data-with-vector-self-configured}

    <br />

    يفترض هذا الدليل أنك أنشأت مسبقًا خدمة Self-managed ClickHouse Observability وسجّلت بيانات اعتماد الخدمة. إن لم تكن قد فعلت ذلك، فاتبع دليل [البدء](/ar/clickstack/self-configured/getting-started/managed) الخاص بـ Self-managed ClickHouse Observability حتى يُطلب منك تهيئة Vector.

    <Steps>
      <Step title="إنشاء قاعدة بيانات وجدول" id="create-a-database-table-self-configured">
        يتطلب Vector تعريف جدول ومخطط قبل استيعاب البيانات.

        أنشئ أولاً قاعدة بيانات، ويمكنك ذلك عبر [وحدة تحكم ClickHouse Cloud](/ar/products/cloud/features/sql-console-features/sql-console).

        نستخدم في المثال أدناه `logs`:

        ```sql
        CREATE DATABASE IF NOT EXISTS logs
        ```

        أنشئ جدولًا لبياناتك، على أن يتطابق مع مخطط الإخراج الخاص ببياناتك. يفترض المثال أدناه بنية Nginx تقليدية، لذا عدّله بما يتلاءم مع بياناتك، مع الالتزام بـ[أفضل ممارسات المخطط](/ar/concepts/best-practices/select-data-type). **نوصي بشدة** بالاطلاع على [مفهوم المفاتيح الأساسية](/ar/concepts/core-concepts/primary-indexes)، واختيار المفتاح الأساسي وفقًا للإرشادات الموضحة [هنا](/ar/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key).

        ```sql
        CREATE TABLE logs.nginx_logs
        (
            `time_local` DateTime,
            `remote_addr` IPv4,
            `remote_user` LowCardinality(String),
            `request` String,
            `status` UInt16,
            `body_bytes_sent` UInt64,
            `http_referer` String,
            `http_user_agent` String,
            `http_x_forwarded_for` LowCardinality(String),
            `request_time` Float32,
            `upstream_response_time` Float32,
            `http_host` String
        )
        ENGINE = MergeTree
        ORDER BY (toStartOfMinute(time_local), status, remote_addr)
        ```

        <Info>
          **المفتاح الأساسي لـ Nginx**

          صُمِّم المفتاح الأساسي أعلاه بناءً على أنماط الوصول المعتادة إلى سجلات Nginx في UI إمكانية المراقبة، لكن قد يلزم تعديله بحسب عبء العمل لديك في بيئات الإنتاج.
        </Info>
      </Step>

      <Step title="أضف ClickHouse كوجهة للبيانات إلى تهيئة vector" id="add-clickhouse-sink-to-config-self-configured">
        عدّل تهيئة Vector لتتضمن وجهة البيانات الخاصة بـ ClickHouse، مع تحديث الحقل `inputs` لاستقبال الأحداث من مسارات معالجة البيانات الحالية لديك.

        تفترض هذه التهيئة أن مسار Vector السابق لديك قد **جهّز البيانات مسبقًا لتطابق مخطط ClickHouse الهدف**، أي أن الحقول قد حُلِّلت وسُمّيت تسمية صحيحة وحُدِّدت أنواعها على النحو المناسب للإدراج. راجع [**مثال Nginx أدناه**](#example-dataset-with-vector-self-configured) للاطلاع على شرح متكامل لتحليل أسطر السجل الخام وتوحيدها وفق مخطط ملائم للخدمة.

        ```yaml
        sinks:
          clickhouse:
            type: clickhouse
            inputs:
              - your_input
            endpoint: "<CLICKHOUSE_ENDPOINT>"
            database: logs
            format: json_each_row
            table: nginx_logs
            skip_unknown_fields: true
            auth:
              strategy: "basic"
              user: "default"
              password: "<CLICKHOUSE_PASSWORD>"
        ```

        نوصي افتراضيًا باستخدام صيغة **`json_each_row`**، التي تُرمِّز كل حدث في صورة كائن JSON واحد لكل صف. وهي الصيغة الافتراضية والموصى بها للخدمة عند إدخال بيانات JSON، ويُفضَّل اعتمادها بدلًا من الصيغ البديلة، مثل كائنات JSON المُرمَّزة كسلاسل نصية.

        تدعم وجهة البيانات ClickHouse أيضًا **ترميز Arrow stream** (حاليًا في المرحلة التجريبية). وقد يوفّر هذا الترميز معدل نقل أعلى، لكنه يخضع لقيود مهمة: يجب أن تكون قاعدة البيانات والجدول ثابتين، إذ يُجلب المخطط مرة واحدة فقط عند بدء التشغيل، كما أن التوجيه الديناميكي غير مدعوم. ولهذا، يُعد ترميز Arrow الأنسب لمسارات الإدخال الثابتة والمحددة بوضوح.

        نوصي بمراجعة خيارات تهيئة وجهة البيانات المتاحة في [وثائق Vector](https://vector.dev/docs/reference/configuration/sinks/clickhouse):

        <Note>
          يستخدم المثال أعلاه المستخدم default في Self-managed ClickHouse Observability. أما في عمليات النشر في بيئة الإنتاج، فنوصي بـ[إنشاء مستخدم مخصص للإدخال](/ar/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) بصلاحيات وحدود مناسبة.
        </Note>
      </Step>

      <Step title="انتقل إلى UI الخاصة بإمكانية المراقبة" id="navigate-to-clickstack-ui-self-configured">
        انتقل إلى خدمة Self-managed ClickHouse Observability الخاصة بك، واختر &quot;ClickStack&quot; من القائمة الجانبية اليسرى. إذا كنت قد أكملت الإعداد الأولي مسبقًا، فستُفتح UI إمكانية المراقبة في علامة تبويب جديدة، وسيتم التحقق من هويتك تلقائيًا. وإن لم تكن قد أكملته، فيمكنك متابعة خطوات الإعداد الأولي، ثم اختيار «Launch ClickStack» بعد تحديد Vector مصدرًا للإدخال.

        <div className="ch-image-lg">
          <Frame>
            ![تشغيل ClickStack لـ Vector](/images/clickstack/launch-clickstack-vector.webp)
          </Frame>
        </div>
      </Step>

      <Step title="إنشاء مصدر بيانات" id="create-a-datasource-managed-self-configured">
        أنشئ مصدر بيانات للسجلات. إذا لم تكن هناك أي مصادر بيانات، فستُطالَب بإنشاء مصدر عند تسجيل الدخول لأول مرة. أما إن وُجدت، فانتقل إلى إعدادات الفريق وأضف مصدر بيانات جديدًا.

        <div className="ch-image-lg">
          <Frame>
            ![إنشاء مصدر بيانات - vector](/images/clickstack/create-vector-datasource.webp)
          </Frame>
        </div>

        تفترض التهيئة أعلاه مخططًا على نمط Nginx يُستخدم فيه العمود `time_local` طابعًا زمنيًا. ويُفضَّل، كلما أمكن، أن يكون هذا العمود هو عمود الطابع الزمني المُعرَّف في المفتاح الأساسي. وهذا العمود إلزامي.

        نوصي أيضًا بتحديث `Default SELECT` لتحديد الأعمدة التي تُعرض في عرض السجلات تحديدًا صريحًا. وإذا توفرت حقول إضافية، مثل اسم الخدمة أو مستوى السجل أو عمود المتن، فيمكن تهيئتها كذلك. كما يمكن استبدال عمود عرض الطابع الزمني إذا كان مختلفًا عن العمود المستخدم في المفتاح الأساسي للجدول والذي تمت تهيئته أعلاه.

        في المثال أعلاه، لا يوجد عمود `Body` في البيانات، بل يُعرَّف باستخدام تعبير SQL يعيد بناء سطر سجل Nginx من الحقول المتاحة.

        للاطلاع على الخيارات الأخرى المتاحة، راجع [مرجع التهيئة](/ar/clickstack/self-configured/managing/config).
      </Step>

      <Step title="أنشئ قاعدة بيانات وجدولًا" id="create-database-table-nginx-managed-self-configured">
        يتطلب Vector تعريف جدول ومخطط قبل استيعاب البيانات.

        أنشئ قاعدة بيانات أولاً، ويمكنك ذلك عبر [وحدة تحكم ClickHouse Cloud](/ar/products/cloud/features/sql-console-features/sql-console).

        أنشئ قاعدة بيانات باسم `logs`:

        ```sql
        CREATE DATABASE IF NOT EXISTS logs
        ```

        أنشئ جدولًا لبياناتك.

        ```sql
        CREATE TABLE logs.nginx_logs
        (
            `time_local` DateTime,
            `remote_addr` IPv4,
            `remote_user` LowCardinality(String),
            `request` String,
            `status` UInt16,
            `body_bytes_sent` UInt64,
            `http_referer` String,
            `http_user_agent` String,
            `http_x_forwarded_for` LowCardinality(String),
            `request_time` Float32,
            `upstream_response_time` Float32,
            `http_host` String
        )
        ENGINE = MergeTree
        ORDER BY (toStartOfMinute(time_local), status, remote_addr)
        ```

        <Info>
          **المفتاح الأساسي لـ Nginx**

          صُمِّم المفتاح الأساسي أعلاه وفقًا لأنماط الوصول المعتادة إلى سجلات Nginx في UI إمكانية المراقبة، لكن قد يلزم تعديله بحسب عبء العمل لديك في بيئات الإنتاج.
        </Info>
      </Step>

      <Step title="نسخ تهيئة Vector" id="copy-vector-configuration-self-configured">
        انسخ تهيئة Vector وأنشئ ملفًا باسم `nginx.yaml`، مع ضبط قيمتَي `CLICKHOUSE_ENDPOINT` و`CLICKHOUSE_PASSWORD`.

        ```yaml
        data_dir: ./.vector-data
        sources:
          nginx_logs:
            type: file
            include:
              - access.log
            read_from: beginning

        transforms:
          decode_json:
            type: remap
            inputs:
              - nginx_logs
            source: |
              . = parse_json!(to_string!(.message))
              ts = parse_timestamp!(.time_local, format: "%d/%b/%Y:%H:%M:%S %z")
              # ClickHouse-friendly DateTime format
              .time_local = format_timestamp!(ts, format: "%F %T")

        sinks:
          clickhouse:
            type: clickhouse
            inputs:
              - decode_json
            endpoint: "<CLICKHOUSE_ENDPOINT>"
            database: logs
            format: json_each_row
            table: nginx_logs
            skip_unknown_fields: true
            auth:
              strategy: "basic"
              user: "default"
              password: "<CLICKHOUSE_PASSWORD>"
        ```

        <Note>
          يستخدم المثال أعلاه المستخدم default الخاص بـ Self-managed ClickHouse Observability. أما في عمليات النشر ضمن بيئة الإنتاج، فنوصي بـ[إنشاء مستخدم مخصص للإدخال](/ar/clickstack/self-configured/ingesting-data/collector#creating-an-ingestion-user-self-configured) بصلاحيات وحدود مناسبة.
        </Note>
      </Step>

      <Step title="بدء تشغيل Vector" id="start-vector-self-configured">
        شغّل Vector باستخدام الأمر التالي، بعد إنشاء دليل البيانات أولاً لتسجيل إزاحات الملفات.

        ```bash
        mkdir ./.vector-data
        vector --config nginx.yaml
        ```
      </Step>

      <Step title="إنشاء مصدر بيانات" id="create-a-datasource-nginx-managed-self-configured">
        أنشئ مصدر بيانات للسجلات. إذا لم تكن هناك أي مصادر بيانات، فستُطالَب بإنشاء مصدر عند تسجيل الدخول لأول مرة. أما إذا كانت موجودة، فانتقل إلى إعدادات الفريق وأضف مصدر بيانات جديدًا.

        <div className="ch-image-lg">
          <Frame>
            ![إنشاء مصدر بيانات - vector](/images/clickstack/create-vector-datasource.webp)

        تفترض هذه التهيئة استخدام مخطط Nginx، مع اعتماد العمود `time_local` طابعًا زمنيًا. وهو عمود الطابع الزمني المُعرَّف في المفتاح الأساسي، وهذا العمود إلزامي.

        كما حدّدنا قائمة الاختيار الافتراضية لتكون `time_local, remote_addr, status, request`، وهي التي تحدّد الأعمدة المُعادة في عرض السجلات.

        في المثال أعلاه، لا يوجد عمود `Body` في البيانات، بل يُعرَّف بوصفه تعبير SQL التالي:

        ```sql
        concat(
          remote_addr, ' ',
          remote_user, ' ',
          '[', formatDateTime(time_local, '%d/%b/%Y:%H:%M:%S %z'), '] ',
          '"', request, '" ',
          toString(status), ' ',
          toString(body_bytes_sent), ' ',
          '"', http_referer, '" ',
          '"', http_user_agent, '" ',
          '"', http_x_forwarded_for, '" ',
          toString(request_time), ' ',
          toString(upstream_response_time), ' ',
          '"', http_host, '"'
        )
        ```

        يُعيد هذا بناء سطر السجل انطلاقًا من الحقول المهيكلة.

        للاطلاع على الخيارات الأخرى المتاحة، راجع [مرجع التهيئة](/ar/clickstack/self-configured/managing/config).
