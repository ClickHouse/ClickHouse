استخدم مساعد برمجة لإضافة أدوات الرصد إلى تطبيقك، مستعينًا بالدليل الخاص بلغته أو إطار عمله. إذ يستطيع المساعد تحديد نقاط الدخول، وتثبيت SDK المناسب، وتهيئة تصدير بيانات القياس عن بُعد.

يرصد التتبّع التلقائي المكتبات وأطر العمل المدعومة. ولكن بحسب لغة تطبيقك وطبيعته، قد تحتاج مع ذلك إلى تعديلات في الشيفرة أو إلى مقاطع تتبع مخصصة لرصد عمليات الأعمال. راجع التعديلات المُولَّدة قبل نشرها.

## قبل أن تبدأ {#before-you-begin}

ستحتاج إلى الشيفرة المصدرية لتطبيقك، ومساعد برمجة لديه صلاحية الوصول إلى المستودع، ووجهة ClickHouse Observability. اختر [دليل SDK الخاص بلغة البرمجة](/ar/clickstack/observability/ingesting-data/sdks) المناسب لتطبيقك؛ إذ يحدّد حزم SDK التي ينبغي استخدامها، والإشارات المدعومة، وإعدادات المُصدِّر اللازمة.

## زوّد مساعدك بدليل اللغة {#give-your-assistant-the-language-guide}

افتح مستودع تطبيقك في مساعد البرمجة الذي تستخدمه، مثل Claude Code أو Cursor أو Codex. انسخ الموجّه التالي، واستبدل العناصر النائبة بعنوان URL لدليل اللغة، ونوع النشر، واسم الخدمة. واكتفِ بذكر أسماء متغيرات البيئة لديك بدلاً من لصق بيانات الاعتماد في الموجّه.

```text wrap
Instrument this application to send telemetry to ClickHouse Observability.

Language or framework guide: <LANGUAGE_SDK_GUIDE_URL>
Destination: <fully managed or self-managed>
Service name: <SERVICE_NAME>
Endpoint environment variable: <ENDPOINT_VARIABLE_NAME>
Ingestion key environment variable: <API_KEY_VARIABLE_NAME>

Read the linked guide and use the instructions for my destination.
Inspect the application's language, framework, dependencies, and startup
commands before making changes. If you cannot read the guide, ask me for
its contents rather than guessing SDK names or configuration.

Reuse existing OpenTelemetry instrumentation where present. Otherwise,
install the SDK and supported automatic instrumentation described in the
guide. Initialize instrumentation at the point required by that SDK.
Use the guide's protocol, endpoint, and authentication format, reading
connection values from the environment. Do not hardcode or print secrets.

Preserve the application's existing behavior. Check for duplicate SDK
initialization, exporters, and logging handlers, including those installed
by automatic instrumentation. If logs are supported, check both the
application's logging level and the SDK's export level so the test log
is captured once. Use the language guide's settings for these checks.

Explain which signals are supported and any operations that need manual
instrumentation. Do not assume every SDK exports logs, metrics, traces,
or session replay.

Update the startup command and document the required environment variables.
Run the application's existing checks and a local startup check. Exercise
an instrumented operation with a unique test marker. If logs are supported,
emit one test log during that operation at an enabled severity. Allow time
for batched export or flush telemetry before shutting down.

When you have destination access, find the test events there and verify
the service name, marker, and absence of duplicates. If log-to-trace
correlation is supported, check that the test log references the operation's
trace and span. Distinguish local export, endpoint acceptance, and events
stored in ClickHouse Observability; startup or an HTTP success response
alone does not prove storage.

Summarize the changes, tests performed, and results. Clearly state which
checks you could not run and give me the remaining verification steps.
```

تحدد أسماء المتغيرات في هذا الموجّه مواضع تخزين قيم الاتصال الخاصة بك، لكنها لا تحل محل المتغيرات التي تتطلبها حزمة SDK؛ إذ يجب على المساعد ربطها بالإعدادات الموثقة في دليل اللغة الخاص بك. أما تطبيقات المتصفح، فاستخدم لها [دليل SDK للمتصفح](/ar/clickstack/observability/ingesting-data/sdks/browser)، بما في ذلك تهيئة نقطة النهاية والمفتاح الخاصة بالمتصفح.

## مراجعة التطبيق وتشغيله {#review-and-run-the-application}

راجِع التغييرات التي طرأت على التبعيات والتهيئة وبدء التشغيل. وتحقّق من أن المساعد اختار الوجهة وصيغة المصادقة الصحيحتين، وحافظ على أدوات الرصد الموجودة، وأبقى الأسرار خارج الملفات المُثبَّتة.

شغّل الاختبارات الحالية لتطبيقك، ثم شغّله باستخدام الأمر والبيئة المحدَّثين. أرسِل طلبًا أو نفّذ إجراءً يستدعي مكتبة مزوّدة بأدوات الرصد. وإذا احتجت إلى بيانات القياس عن بُعد لعملية لا يلتقطها التتبّع التلقائي، فاطلب من المساعد إضافة span مخصص باستخدام واجهة برمجة التطبيقات في حزمة SDK التي تستخدمها.

## التحقق من بيانات القياس عن بُعد {#verify-telemetry}

1. افتح صفحة [بحث](/ar/clickstack/observability/features/search) في ClickHouse Observability.
2. اختر مصدر السجلات أو التتبّعات المناسب، وحدّد نطاقًا زمنيًا يشمل نشاط الاختبار.
3. صفِّ النتائج حسب اسم الخدمة، وافحص الأحداث الناتجة. تحقّق من ظهور الطلب أو العملية المتوقعة.
4. إذا كانت حزمة SDK تُصدِّر مقاييس، فاستخدم [مستكشف المخططات](/ar/clickstack/observability/features/dashboards/overview#navigate-chart-explorer) لفحصها.

نجاح بدء تشغيل التطبيق لا يعني بالضرورة وصول بيانات القياس عن بُعد. إذا لم تظهر الأحداث، فتحقّق من أخطاء المُصدِّر في التطبيق، ومن إعدادات نقطة النهاية والبروتوكول والمصادقة. وفي عمليات النشر المُدارة ذاتيًا، افحص أيضًا سجلات جامع البيانات.

للاطلاع على مثال متكامل لتطبيق، راجع [العرض التوضيحي لـ HackerNews Analyzer](/ar/clickstack/observability/example-datasets/instrument-application).
