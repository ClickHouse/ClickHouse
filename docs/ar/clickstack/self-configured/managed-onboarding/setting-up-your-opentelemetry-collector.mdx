يعمل جامع البيانات بدور **بوابة**، أي أنه نقطة نهاية OTLP واحدة ترسل إليها تطبيقاتك وحِزم SDK وجامعو البيانات العاملون بدور الوكيل. تجمع البوابة الأحداث في دفعات، وتطبّق أي معالجة قمت بتهيئتها، ثم تكتبها إلى ClickHouse عبر [مُصدِّر ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter). يُبقي هذا النمط منطق الجمع بمعزل عن شفرة التطبيق، ويتيح لك توسيع نطاق إدخال البيانات باستقلالية عن أحمال العمل التي تُنتجها. لمزيد من المعلومات حول الفرق بين دوري البوابة والوكيل، راجع [أدوار المجمّع](/ar/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured).

<Info>
  **جامع بيانات قائم**

  إذا كنت تستخدم مُجمِّع OpenTelemetry قائمًا، فإننا نفترض أنه مُهيّأ مسبقًا بدور **بوابة**. ولا نوصي باتباع هذه العملية لإعادة تهيئة جامعي البيانات العاملين بدور **وكيل**.
</Info>

      <Step title="انشر جامع البيانات" id="deploy-the-collector">
        انشر **توزيعة ClickStack من مُجمِّع OpenTelemetry**، وهي مُهيّأة مسبقًا لـ Self-managed ClickHouse Observability. وللتبسيط، نشغّل في المثال أدناه جامع البيانات محليًا ونولّد بيانات قياس عن بُعد اصطناعية من الجهاز نفسه.

        <Note>
          في بيئة الإنتاج، يُنشر جامع البيانات عادةً في عنقود Kubernetes، أو على جهاز افتراضي يمكن الوصول إليه من حزم SDK لـ OpenTelemetry والوكلاء وجامعي البيانات الآخرين. ويتيح ذلك جمع بيانات القياس عن بُعد من مختلف أرجاء بيئتك مركزيًا وتمريرها إلى ClickStack.
        </Note>

        اختر secret مشتركًا للتحقق من هوية العملاء الذين يرسلون البيانات إلى جامع البيانات، ثم صدّره مع بيانات الاتصال وكلمة المرور التي اخترتها للمستخدم `hyperdx_ingest`:

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        شغِّل مُجمِّع OTel الخاص بـ ClickStack:

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        يتيح جامع البيانات الآن OTLP gRPC على المنفذ `4317` وOTLP HTTP على المنفذ `4318`. ينبغي أن ترسل التطبيقات وحزم SDKs وجامعو البيانات العاملون كوكلاء بياناتها إلى هذه المنافذ، مع تضمين `authorization: $OTLP_AUTH_TOKEN` في ترويسات الطلب.

        <Info>
          **عمليات النشر في بيئة الإنتاج**

          في بيئة الإنتاج، نوصي بتفعيل TLS على نقطة نهاية OTLP. راجع [تأمين جامع البيانات](/ar/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        </Info>
      </Step>

      <Step title="تحقق من نقطة النهاية" id="verify-the-endpoint">
        ولّد بعض حركة المرور الاصطناعية نحو جامع البيانات للتحقق من أن المسار بأكمله يعمل كما ينبغي. نستخدم لذلك [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen)، وهو المولّد المضمّن في OpenTelemetry Collector Contrib، إذ يُصدر سجلات وتتبّعات ومقاييس بصيغة OTLP، ويوفّر خيارات سطر الأوامر للتحكم في شكل البيانات وتوزيعها عبر الخدمات ومستويات الخطورة وحالات span وأنواع المقاييس.

        شغّله من صورة Docker الخاصة به (دون الحاجة إلى تثبيت). عرّف غلافًا صغيرًا لتبقى الأوامر أدناه سهلة القراءة؛ إذ يتيح `--add-host` للحاوية الوصول إلى جامع البيانات الذي يستمع على المضيف:

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        أو ثبّت الملف التنفيذي باستخدام Go واستهدف `localhost` بدلاً من ذلك:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```

        <Info>
          **ما المتوقع**

          يستغرق كل تشغيل لـ `tg` نحو 20 ثانية (وفق ما يحدده `--duration 20s`)، ويعرض خلالها سجلات مفصّلة باستمرار، وهذا أمر طبيعي؛ إذ ينتهي كل تشغيل تلقائيًا فور انقضاء ثوانيه الـ 20. وتكفي السجلات أدناه للتحقق من عمل مسار المعالجة، أما المجموعة الاختيارية الأشمل فتضيف عدة تشغيلات أخرى وتستغرق بضع دقائق.
        </Info>

        عرّف دالة مساعدة صغيرة باسم `tg` بحيث لا يحدد كل أمر إلا ما يتغير (الخدمة، ومستوى الخطورة، وstatus، والسمات):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        أرسل السجلات بمزيج واقعي من مستويات الخطورة موزّعة على الخدمات، أغلبها معلوماتية مع سجل تحذير واحد وسجل error واحد، بدلاً من دفق متجانس من سجلات error فقط:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        تكفي السجلات وحدها للتأكد من أن نقطة النهاية تعمل. وللحصول على مجموعة بيانات تجريبية أغنى، وخريطة خدمات (Service Map) تضم خدمات متعددة، ورسوم بيانية تغطي مختلف أنواع المقاييس، وسّع الأوامر أدناه وشغّلها أيضًا. تعيد هذه الأوامر استخدام الدالة المساعدة `tg`، لذا شغّلها في جلسة shell نفسها.

        <Accordion title="توليد بيانات قياس عن بُعد أكثر تفصيلًا (اختياري)">
          أرسل عمليات تتبّع متعددة الـ span من عدة خدمات سليمة، إضافةً إلى تبعية واحدة فاشلة. يمنح ذلك خريطة الخدمات (Service Map) شكلاً واقعياً، إذ تبدو معظم الخدمات سليمة باستثناء خدمة واحدة تُصدر أخطاء، مع الحرص على تعبئة طرق عرض الأخطاء بالبيانات أيضاً:

          ```shell
          # Healthy services: the bulk of the traffic, all spans Ok
          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          أرسل المقاييس من الأنواع الثلاثة الشائعة، لكي تتضمن الرسوم البيانية عدادًا (counter) ومقياسًا (gauge) وتوزيعًا (distribution):

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          ولمزيدٍ من التنوع، أضف بضع خدمات أخرى ومُدرَّجًا تكراريًا أُسّيًا:

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        للاطلاع على القائمة الكاملة لخيارات سطر الأوامر ومزيد من الأمثلة المتنوعة، راجع [بيانات اصطناعية باستخدام telemetrygen](/ar/clickstack/observability/example-datasets/telemetrygen#self-managed).
      </Step>

      <Step title="عدّل تهيئة collector لديك" id="adapt-collector">
        وسّع تهيئة collector الحالية لديك لكتابة البيانات إلى Self-managed ClickHouse Observability عبر [مُصدِّر ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

        <Info>
          **يلزم وجود مُصدِّر ClickHouse**

          إذا كنت تستخدم توزيعتك الخاصة، فتأكد من أنها تتضمن مُصدِّر ClickHouse. علمًا بأن [صورة contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) في المصدر الأصلي تتضمنه بالفعل.
        </Info>

        فيما يلي مثال على تهيئة تستخدم مُصدِّر ClickHouse مع المستقبِلات والمعالجات ومسارات معالجة البيانات التي تتوقعها واجهة مستخدم ClickStack. وتحاكي هذه التهيئة سلوك توزيعة ClickStack، بما في ذلك مسار توجيه إعادة تشغيل الجلسة (`rrweb`). استبدل `<clickhouse_cloud_endpoint>` و`<your_password_here>` ببيانات اعتماد المستخدم `hyperdx_ingest` الذي أنشأته أعلاه:

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        بعض النقاط التي تجدر ملاحظتها:

        * يستمع المستقبِل `otlp/hyperdx` عبر كلٍّ من gRPC (`4317`) وHTTP (`4318`)؛ لذا ينبغي أن توجّه التطبيقات والوكلاء بياناتها إلى هذين المنفذين على مضيف جامع البيانات لديك.
        * يكتب المُصدِّر `clickhouse` السجلات والتتبّعات والمقاييس في قاعدة البيانات `otel`، بما يتوافق مع التخطيط الذي تتوقعه واجهة مستخدم ClickStack. أما المُصدِّر `clickhouse/rrweb` فيتولى معالجة أحداث إعادة تشغيل الجلسة التي يوجّهها الموصل `routing/logs` إلى `otel.hyperdx_sessions`.
        * تُترك المصادقة على مستقبِلات OTLP لإعداداتك الحالية. إذا كنت بحاجة إلى اشتراط رمز إدخال، فهيّئها عبر [الامتدادات](https://opentelemetry.io/docs/collector/configuration/#extensions) الخاصة بجامع البيانات (مثل `bearertokenauth`) أو عبر وكيل عكسي يعمل بـ TLS في الواجهة الأمامية.

        أعد تحميل جامع البيانات بالتهيئة الجديدة. بعد ذلك، ينبغي أن ترسل التطبيقات وحزم SDKs وجامعو البيانات الوكلاء بياناتهم إلى نقاط نهاية OTLP التي يتيحها جامع البيانات لديك، مع ترويسة المصادقة التي تتطلبها إعداداتك.

        لمزيد من التفاصيل حول تهيئة مُجمِّعات OpenTelemetry للعمل مع Self-managed ClickHouse Observability، راجع [استيعاب البيانات باستخدام OpenTelemetry](/ar/clickstack/observability/ingesting-data/opentelemetry#self-managed).
      </Step>

      <Step title="تحقّق من نقطة النهاية" id="verify-the-endpoint-existing">
        وَلِّد بعض حركة المرور الاصطناعية باتجاه جامع البيانات للتحقق من أن مسار المعالجة يعمل بالكامل. نستخدم لهذا الغرض [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen)، وهو المولّد المضمَّن في OpenTelemetry Collector Contrib، إذ يُرسل سجلات وتتبّعات ومقاييس بتنسيق OTLP، ويوفّر خيارات سطر أوامر للتحكم في شكل البيانات من حيث الخدمات ومستويات الخطورة وحالات span وأنواع المقاييس.

        شغّله من صورة Docker الخاصة به (دون الحاجة إلى تثبيت). استبدل `<your-collector-host>` بالمضيف الذي يستمع عليه جامع البيانات لديك، واضبط ترويسة `authorization` (أو أي طريقة مصادقة أخرى) على القيمة التي يتوقعها جامع البيانات لديك:

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=<your-collector-host>:4317
        export OTLP_AUTH_TOKEN=<your-auth-token>
        ```

        أو ثبّت الملف التنفيذي باستخدام Go:

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        ```

        <Info>
          **ما المتوقع**

          يستغرق كل تشغيل لـ `tg` نحو 20 ثانية (وهي المدة المحددة عبر `--duration 20s`)، ويعرض سجلات مفصّلة طوال هذه المدة، وهذا أمر متوقع؛ إذ ينتهي كل تشغيل تلقائيًا بعد انقضاء الثواني العشرين. تكفي السجلات أدناه للتحقق من عمل مسار المعالجة؛ أما المجموعة الاختيارية الأشمل فتضيف عدة عمليات تشغيل أخرى وتستغرق بضع دقائق.
        </Info>

        عرّف دالة مساعدة صغيرة باسم `tg` بحيث لا يحدد كل أمر إلا ما يتغير فيه (الخدمة، ومستوى الخطورة، والحالة، والسمات):

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        أرسل السجلات على هيئة مزيج واقعي من مستويات الخطورة موزّعًا على الخدمات، أغلبها رسائل معلوماتية مع رسالة تحذير واحدة ورسالة error واحدة، بدلًا من تدفق متجانس من رسائل error وحدها:

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        تكفي السجلات وحدها للتأكد من أن نقطة النهاية تعمل. وللحصول على مجموعة بيانات تجريبية أغنى، وخريطة خدمات تضم عدة خدمات، ورسوم بيانية تغطي مختلف أنواع المقاييس، وسِّع الأوامر أدناه وشغِّلها أيضًا. تعيد هذه الأوامر استخدام الدالة المساعدة `tg`، لذا شغِّلها في جلسة الـ shell نفسها.

        <Accordion title="توليد بيانات قياس عن بُعد أكثر تفصيلاً (اختياري)">
          أرسل عمليات تتبّع متعددة الـ span من عدة خدمات سليمة إضافةً إلى تبعية واحدة فاشلة. يمنح ذلك خريطة الخدمات (Service Map) شكلًا واقعيًا، إذ تبدو في معظمها سليمة باستثناء خدمة واحدة تُصدر أخطاء، مع الاستمرار في تعبئة عروض الأخطاء بالبيانات:

          ```shell
          # Healthy services: the bulk of the traffic, all spans Ok
          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          أرسل مقاييس من الأنواع الثلاثة الشائعة، لتتضمن الرسوم البيانية عدادًا (counter) ومقياسًا (gauge) وتوزيعًا (distribution):

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          ولمزيد من التنوع، أضف خدمتين إضافيتين ومُدرَّجًا تكراريًا أُسّيًا:

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        للاطلاع على القائمة الكاملة لخيارات سطر الأوامر ومزيد من الأمثلة المتنوعة، راجع [البيانات الاصطناعية باستخدام telemetrygen](/ar/clickstack/observability/example-datasets/telemetrygen#self-managed).
      </Step>

## الخطوات التالية: إرسال بياناتك الخاصة {#next-steps}

لا تُثبت الدفعة الاصطناعية أعلاه سوى أن مسار تنفيذ الاستعلام يعمل. ولبدء إرسال بيانات القياس عن بُعد الحقيقية، زوِّد خدماتك بأدوات جمع بيانات الرصد باستخدام [حزم SDK لـ ClickStack](/ar/clickstack/observability/ingesting-data/sdks)، التي توفّر أدوات الرصد للغات Node.js وبايثون وGo وJava وغيرها، وتُصدِّر البيانات بتنسيق OTLP إلى نقطة نهاية جامع البيانات التي تحققت منها للتو. وللاطلاع على مثال عملي متكامل، اتبع دليل [تزويد تطبيق بأدوات جمع بيانات الرصد](/ar/clickstack/self-configured/managed-onboarding/instrument-application).

ولجمع البيانات من البنية التحتية بدلاً من شفرة التطبيق:

* [مراقبة Kubernetes](/ar/clickstack/self-configured/managed-onboarding/monitoring-kubernetes): جمع السجلات ومقاييس البنية التحتية وأحداث Kubernetes من العنقود.
* [مراقبة سجلات AWS CloudWatch](/ar/clickstack/self-configured/managed-onboarding/monitoring-aws-cloudwatch-logs): إعادة توجيه سجلات CloudWatch عبر مستقبِل CloudWatch في OpenTelemetry.
