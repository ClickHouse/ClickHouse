تعتمد ClickStack Node.js SDK على OpenTelemetry SDK من المصدر الأصلي وعلى أدوات auto-instrumentation الخاصة به، وتضيف إليها التقاط مخرجات وحدة التحكم، والتقاط الاستثناءات غير الملتقطة، وتفريغ بيانات القياس عن بُعد عند إيقاف التشغيل. أما التطبيقات التي هيّأت OpenTelemetry بالفعل، فيمكنها مواصلة استخدام SDK الحالية لديها و[تهيئة التصدير عبر OTLP](/ar/clickstack/ingesting-data/opentelemetry).

## التثبيت {#install}

استخدم Node.js بالإصدار **22.15 أو أحدث**، ثم ثبّت حزمة SDK في تطبيقك:

```shell
npm install @clickhouse/clickstack-node
```

تدعم هذه الحزمة وحدات ES وCommonJS. ويثبّت npm تلقائيًا التبعية النظيرة (peer dependency) الخاصة بها `@opentelemetry/api`. أما إذا كان تطبيقك يستورد تلك الحزمة مباشرةً، فثبّت `@opentelemetry/api@~1.9.1`؛ إذ يقع الإصدار 1.10 خارج نطاق الإصدارات التي تدعمها حزمة SDK هذه.

## تهيئة الوجهة {#configure-destination}

اضبط متغيرات البيئة قبل تشغيل تطبيقك. استخدم نقطة نهاية OTLP HTTP أساسية دون `/v1/traces` أو `/v1/logs` أو `/v1/metrics`، إذ تُلحق المُصدِّرات هذه المسارات تلقائيًا.

استخدم نقطة نهاية OTLP HTTP الخاصة بجامع البيانات لديك، ومفتاح الإدخال المُهيَّأ لمستقبِل OTLP التابع له. لإعداد جامع البيانات، راجع [إدخال البيانات باستخدام OpenTelemetry](/ar/clickstack/ingesting-data/opentelemetry).

```shell
export OTEL_EXPORTER_OTLP_ENDPOINT='http://localhost:4318'
export OTEL_EXPORTER_OTLP_HEADERS='authorization=YOUR_INGESTION_API_KEY'
export OTEL_EXPORTER_OTLP_PROTOCOL='http/protobuf'
export OTEL_SERVICE_NAME='my-node-app'
```

تفترض نقطة النهاية هذه أن التطبيق وجامع البيانات يعملان على المضيف نفسه. أما إذا كان جامع البيانات يعمل في مكان آخر، فاستبدلها بعنوان يمكن الوصول إليه من تطبيقك.

## بدء تشغيل تطبيقك {#start-application}

حمّل الـ SDK مسبقًا قبل أن يستورد تطبيقك المكتبات التي يزوّدها الـ SDK بأدوات جمع بيانات الرصد:

```shell
node --import @clickhouse/clickstack-node/register server.js
```

استبدل `server.js` بملف الدخول الخاص بتطبيقك. يحمّل هذا الأمر الـ SDK قبل بدء تشغيل تطبيقك، ويستخدم متغيرات البيئة التي تمت تهيئتها أعلاه. وهو يدعم تطبيقات CommonJS وتطبيقات وحدات ES على حد سواء.

يمكنك الآن [التحقق من إدخال البيانات](#verify-ingestion). لن تحتاج إلى البدائل أدناه إلا إذا أردت بدء التشغيل عبر برنامج نصي لـ npm أو تهيئة الـ SDK داخل الشيفرة.

<Accordion title="طرق بديلة لبدء التشغيل">
  الخيار `--require` مدعوم أيضًا. إذا كنت تستخدم `NODE_OPTIONS`، فاقصر نطاقه على أمر التطبيق وحده حتى لا تُشغّل أدوات الإصدار مسارات خاصة بها لبيانات القياس عن بُعد:

  ```shell
  NODE_OPTIONS='--import @clickhouse/clickstack-node/register' npm start
  ```

  أو يمكنك بدلًا من ذلك إنشاء وحدة لإضافة أدوات الرصد وتحميلها مسبقًا. وتظل متغيرات البيئة الواردة في القسم السابق هي التي تتحكم في تهيئة التصدير:

  ```javascript
  // instrumentation.mjs
  import { isMainThread } from 'node:worker_threads';
  import { init } from '@clickhouse/clickstack-node';

  if (isMainThread) {
    init();
  }
  ```

  ```shell
  node --import ./instrumentation.mjs server.mjs
  ```

  يمنع هذا الشرط خيوط التنفيذ العاملة، مثل عمال النقل في Pino، من تشغيل مثيلات إضافية من الـ SDK.

  استخدم إما نقطة دخول التسجيل الخاصة بالحزمة وإما وحدة إضافة أدوات الرصد الخاصة بك، ولا تُهيّئ SDK ثانيًا داخل التطبيق. فعمليات الاستيراد الثابتة لوحدات ES تُنفَّذ قبل متن الوحدة، ولذلك فإن استدعاء `init` قبل عمليات الاستيراد الثابتة في الملف نفسه لا يضمن ترتيب التهيئة.
</Accordion>

## التحقق من إدخال البيانات {#verify-ingestion}

شغّل تطبيقك، وأرسل طلبات إلى مسار مزوّد بأدوات الرصد، واطبع رسالة في وحدة التحكم. في ClickStack، اختر نطاقًا زمنيًا حديثًا وابحث في Logs أو Traces عن `my-node-app`. انتظر انقضاء الفاصل الزمني لتصدير المقاييس قبل التحقق منها.

إذا لم تظهر البيانات، فتحقق من رسائل تشخيص SDK في stderr، ومن نقطة النهاية والمصادقة، ومن الاتصال بالشبكة. تأكد من تحميل إضافة أدوات الرصد قبل تبعيات التطبيق. يتعذّر تزويد المكتبات المجمّعة بأدوات الرصد تلقائيًا إذا كانت أداة التجميع تُضمِّنها مباشرةً؛ لذا أبقِ SDK والتبعيات المزوّدة بأدوات الرصد خارجية. راجع [توافق SDK](https://github.com/ClickHouse/clickstack-node#compatibility) للاطلاع على متطلبات TypeScript ووحدات ES وأطر العمل وأدوات التجميع.

## تهيئة إضافة أدوات الرصد {#configure-instrumentation}

تحتفظ متغيرات البيئة القياسية في OpenTelemetry بمعناها المعتمد في المصدر الأصلي، بما في ذلك ما يتعلق بأخذ العينات، والتجميع في دفعات، والمُصدِّرات، وسمات الموارد. على سبيل المثال:

```shell
export OTEL_RESOURCE_ATTRIBUTES='deployment.environment.name=production'
```

تُلتقط مخرجات وحدة التحكم افتراضيًا. أما التقاط متن طلبات HTTP فمعطّل افتراضيًا؛ لذا لا تُمكّنه إلا إذا كان ذلك مناسبًا لطبيعة البيانات التي يعالجها تطبيقك:

```shell
export CLICKSTACK_CAPTURE_HTTP_BODY='true'
```

قد تحتوي المتون المُلتقطة على بيانات شخصية وبيانات اعتماد. لا يضمن SDK تنقيحًا كاملًا، إذ يُجريه بأفضل جهد ممكن؛ لذا أبقِ على التنقيح من جهة جامع البيانات عند الحاجة. راجع [خيارات الخصوصية في SDK](https://github.com/ClickHouse/clickstack-node#privacy) للاطلاع على إعدادات التقاط الترويسات، وحدود المتن، وتنقية البيانات.

### خيارات التهيئة {#initialization-options}

مرِّر هذه الخيارات إلى `init` في وحدة إضافة أدوات الرصد الخاصة بك:

| الخيار                       | القيمة الافتراضية                                    | الغرض                                                                                                                                    |
| ---------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `endpoint`                   | `http://localhost:4318`                              | عنوان URL الأساسي لـ OTLP عبر HTTP؛ ويُستبدَل بقيمة `OTEL_EXPORTER_OTLP_ENDPOINT`                                                        |
| `serviceName`                | `unknown_service:` متبوعًا باسم الملف القابل للتنفيذ | اسم الخدمة؛ ويُستبدَل بقيمة `OTEL_SERVICE_NAME` أو `service.name` في `OTEL_RESOURCE_ATTRIBUTES`                                          |
| `environment`                | غير معيّن                                            | يعيّن `deployment.environment.name`؛ وتكون الأسبقية للمفتاح نفسه في `OTEL_RESOURCE_ATTRIBUTES`                                           |
| `apiKey`                     | غير معيّن                                            | قيمة ترويسة التفويض؛ ويُتجاهَل إذا كان `OTEL_EXPORTER_OTLP_HEADERS` غير فارغ أصلًا، حتى لو اقتصر على ترويسات لا علاقة لها بالتفويض       |
| `httpBodyCapture`            | `false`                                              | التقاط متن طلبات HTTP واستجاباتها؛ ويُستبدَل بقيمة `CLICKSTACK_CAPTURE_HTTP_BODY`                                                        |
| `instrumentations`           | القيم الافتراضية لتهيئة المصدر الأصلي                | خريطة تهيئة لـ `getNodeAutoInstrumentations`؛ وتتجاوز قيم `enabled` المحدَّدة صراحةً متغيرات البيئة الخاصة بتمكين إضافة أدوات الرصد أو تعطيلها |
| `additionalInstrumentations` | `[]`                                                 | مثيلات إضافية لإضافة أدوات الرصد للمكتبات غير المضمّنة في الحزمة الافتراضية                                                                    |

عندما تكون متغيرات البيئة غير معيّنة أو فارغة، يسري الخيار المقابل لها. ولتعطيل التقاط مخرجات وحدة التحكم، أضِف `console` إلى `OTEL_NODE_DISABLED_INSTRUMENTATIONS`. راجع [مرجع Node.js SDK](https://github.com/ClickHouse/clickstack-node#quick-start) للاطلاع على جميع القيم الافتراضية.

لمعرفة كيفية التعامل مع حالات إنهاء العملية صراحةً أو مع معالجات AWS Lambda، راجع [توثيق دورة حياة SDK](https://github.com/ClickHouse/clickstack-node#lifecycle).

## استخدام SDK من المصدر الأصلي {#using-upstream-sdk}

إذا كان تطبيقك يهيّئ OpenTelemetry بالفعل، أو كان يحتاج إلى معالجات مخصصة أو سلوك يتجاوز خيارات ClickStack SDK، فاستخدم `NodeSDK` من المصدر الأصلي وهيّئ تصدير OTLP إلى الوجهة المذكورة أعلاه. اتبع [مثال إعداد SDK من المصدر الأصلي](https://github.com/ClickHouse/clickstack-node#using-the-upstream-sdk-directly)، الذي يشرح التهيئة الإضافية للمُحمِّل ولدورة الحياة. لا تهيّئ حزمتَي SDK كلتيهما في العملية نفسها.

## الترحيل من HyperDX Node.js SDK {#migration}

استبدل `@hyperdx/node-opentelemetry` بـ `@clickhouse/clickstack-node`، واستخدم نقطة الدخول الجديدة الخاصة بالتسجيل. واستبدل `HYPERDX_API_KEY` بـ `OTEL_EXPORTER_OTLP_HEADERS`، مع استخدام صيغة التفويض الخاصة بالوجهة التي اخترتها أعلاه.

لا يتضمن SDK الجديد جميع الدوال المساعدة والخيارات التي كانت متوفرة في HyperDX. لذا راجع [دليل ترحيل SDK](https://github.com/ClickHouse/clickstack-node/blob/main/docs/migration.md) قبل استبدال تكاملات مسجّل السجلات، أو معالجات الأخطاء، أو سمات التتبّع المخصصة، أو إعدادات أخذ العينات.
