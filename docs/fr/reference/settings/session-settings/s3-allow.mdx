## s3_allow_server_credentials_in_user_queries {#s3_allow_server_credentials_in_user_queries}

**Alias** : `allow_server_credentials_in_user_queries`

Autorise l&#39;accès S3 et Azure Blob Storage provenant du SQL utilisateur à utiliser des informations d&#39;authentification gérées par le Serveur.

Également disponible sous l&#39;alias `allow_server_credentials_in_user_queries`, car il s&#39;applique aussi à Azure.

Lorsqu&#39;il est désactivé (valeur par défaut), les fonctions de table `s3`/`s3Cluster`, les moteurs `S3`/`S3Queue`, les collections nommées S3, les définitions dynamiques `disk(type=s3, ...)`, `BACKUP`/`RESTORE TO S3`, les lectures de données de table DataLake et les bases de données `DataLakeCatalog` (Glue, BigLake) ne peuvent pas résoudre les informations d&#39;authentification à partir de l&#39;environnement, des métadonnées d&#39;instance (IMDS), d&#39;IRSA, d&#39;ECS, du profil d&#39;instance, de SSO, des fichiers AWS de configuration/d&#39;informations d&#39;authentification ou du service de métadonnées OAuth de GCP. Une requête qui demande l&#39;une de ces sources gérées par le Serveur (par exemple `use_environment_credentials = 1` ou `http_client = gcp_oauth`) sans fournir d&#39;informations d&#39;authentification explicites utilisables est rejetée avec `ACCESS_DENIED`. Une requête qui n&#39;en demande aucune est envoyée non signée (anonyme), comme si `NOSIGN` avait été indiqué.

L&#39;assume-role STS basé sur `role_arn` (`extra_credentials(role_arn = '...')`) reste autorisé même lorsque ce paramètre est désactivé : le rôle cible doit explicitement faire confiance à l&#39;identité sous laquelle le Serveur s&#39;exécute, et seules les informations d&#39;authentification du rôle assumé signent les requêtes S3 de la requête, de sorte que les propres informations d&#39;authentification du Serveur ne sont pas exposées à la requête. Il s&#39;agit de la méthode documentée pour accorder à ClickHouse Cloud l&#39;accès à un bucket privé. Le rôle est assumé avec les propres clés de base de la requête lorsque celle-ci fournit une paire complète ; sinon, l&#39;appel STS AssumeRole est signé par l&#39;identité ambiante du Serveur. Les clés statiques de la configuration `<s3>`/endpoint du Serveur ou d&#39;une collection nommée ne sont jamais utilisées comme base STS pour un rôle fourni par la requête, et un `role_arn` configuré dans la configuration `<s3>` du Serveur n&#39;est pas du tout appliqué aux requêtes utilisateur. Les définitions dynamiques `disk(type=s3, role_arn=...)` restent couvertes par la restriction.

Le fait qu&#39;une requête sans informations d&#39;authentification demande des informations d&#39;authentification d&#39;environnement est déterminé par `use_environment_credentials`. Pour les collections nommées, la valeur par défaut est `0`, de sorte qu&#39;une collection qui spécifie uniquement une URL est lue anonymement. Les fonctions de table `s3`/`s3Cluster` et les moteurs `S3`/`S3Queue` utilisent la valeur par défaut intégrée (`1`), sauf si la configuration du Serveur `<s3>` la remplace ; définissez `<s3><use_environment_credentials>0</use_environment_credentials></s3>` pour que leurs lectures sans informations d&#39;authentification soient elles aussi anonymes par défaut (sinon, une telle requête est refusée et doit utiliser `NOSIGN`). Les disques définis dans la configuration du Serveur ne sont pas affectés et continuent d&#39;utiliser par défaut les informations d&#39;authentification d&#39;environnement ; les définitions dynamiques `disk(type = s3, ...)` créées par l&#39;utilisateur sont couvertes par la restriction (voir ci-dessus) et sont rejetées lorsqu&#39;elles s&#39;appuient sur les informations d&#39;authentification par défaut/de l&#39;environnement.

Cela empêche un utilisateur authentifié de faire accéder le Serveur à S3 avec ses propres informations d&#39;authentification (ambiantes). Les informations d&#39;authentification fournies explicitement ne sont pas affectées : les clés passées dans la requête, les clés statiques d&#39;une collection nommée (créée via SQL ou définie dans la configuration) et les clés de la configuration du Serveur `<s3>` continuent toutes de fonctionner.

La méthode recommandée pour donner aux requêtes utilisateur un accès à S3 consiste à utiliser une collection nommée avec des informations d&#39;authentification explicites (ou `NOSIGN` pour les buckets publics) : les clés ne figurent pas dans le texte de la requête, et l&#39;utilisation de chaque collection est contrôlée via RBAC (`GRANT NAMED COLLECTION ON <name> TO <user>`). Vous accordez ainsi à des utilisateurs précis l&#39;accès à des buckets précis, au lieu d&#39;exposer l&#39;identité propre du Serveur.

Portée (volontairement limitée) : ce paramètre bloque uniquement les sources d’informations d’authentification ambiantes du Serveur répertoriées ci-dessus. Il ne bloque pas les `access_key_id`/`secret_access_key` statiques fournis par l’opérateur dans la configuration `<s3>` du Serveur ou dans une collection nommée définie dans la configuration : ceux-ci sont traités comme des informations d’authentification explicites et continuent de fonctionner. Notez toutefois que les éléments de requête issus de la configuration, tels que `access_header` ou les clés de chiffrement côté Serveur, ne sont pas considérés à eux seuls comme des informations d’authentification ici : une requête qui ne comporte que de tels éléments, sans paire de clés explicite (et avec la valeur par défaut `use_environment_credentials = 1`), est tout de même refusée, car elle se rabattrait sinon sur les informations d’authentification ambiantes du Serveur. Un tel endpoint doit également fournir des clés explicites, `NOSIGN`, `use_environment_credentials = 0` ou recourir à l’échappatoire décrite ci-dessous.

Un client administratif de confiance peut avoir besoin d’informations d’authentification gérées par le Serveur pour des opérations légitimes (par exemple, attacher des tables système sur un disque `s3_plain_rewritable` via SQL). Activez ce paramètre dans la session ou le profil de paramètres de ce client pour l’y autoriser.

Pour `BACKUP`/`RESTORE ... ON CLUSTER`, la valeur de ce paramètre définie par l’initiateur est propagée aux autres hôtes et utilisée telle quelle. Ces hôtes exécutent la phase de continuation de l’opération qui leur est propre via la file DDL distribuée, par défaut sans l’utilisateur de l’initiateur ; sans cela, ils évalueraient la restriction par rapport à leur propre profil par défaut. La valeur de l’initiateur est conservée, car celui-ci a déjà ouvert la même destination de sauvegarde avec ses propres paramètres contraints. Une contrainte `readonly` sur l’initiateur s’applique toujours (un initiateur non approuvé ne peut pas activer ce paramètre pour sa propre sauvegarde sur le cluster), de sorte que cela n’affaiblit pas la restriction.

Durabilité des tables persistantes `S3` et `S3Queue` : l’activer uniquement par session ou par profil n’est pas pérenne après un redémarrage. Lorsque le Serveur recharge une telle table à partir de sa définition stockée (au démarrage ou lors d’un `RESTORE`), il reconstruit le client S3 et réapplique la restriction avec le contexte de démarrage. Ainsi, une table qui s’appuyait sur des informations d’authentification gérées par le Serveur et qui a été créée uniquement avec `s3_allow_server_credentials_in_user_queries = 1` au niveau de la session ou du profil est bien créée, mais devient inaccessible après un redémarrage (la table reste en place ; les requêtes qui la ciblent échouent jusqu’à ce que ses informations d’authentification soient de nouveau résolues vers une source autorisée). Le Serveur lui-même démarre toujours. Donnez à ces tables des informations d’authentification explicites pour un accès pérenne ; sinon, activer ce setting à l’échelle du Serveur permet de continuer à les charger après les redémarrages, au prix d’un assouplissement de la restriction pour tous les rechargements.

Azure Blob Storage est également couvert par ce paramètre. Lorsqu’il est désactivé, les fonctions de table `azureBlobStorage`/`azureBlobStorageCluster`, les moteurs `AzureBlobStorage`/`AzureQueue`, les collections nommées Azure, les définitions dynamiques `disk(type = azure_blob_storage, ...)`, `BACKUP`/`RESTORE TO AzureBlobStorage` et les lectures de données de tables DataLake sur Azure ne peuvent pas s’authentifier avec l’identité sous laquelle le Serveur lui-même s’exécute : l’identité de charge de travail AKS (un jeton de compte de service projeté provenant de `AZURE_FEDERATED_TOKEN_FILE`) ou l’identité managée Azure de la machine. Une telle requête est rejetée avec `ACCESS_DENIED`. Les informations d’authentification fournies explicitement ne sont pas concernées : une paire `account_name`/`account_key`, une chaîne de connexion, un jeton SAS et des informations d’authentification statiques dans une collection nommée ou dans la section `<storage_configuration>` du Serveur continuent tous de fonctionner. Azure lie un jeton porteur de stockage au compte pour lequel il a été émis, et non à l’hôte auquel il est envoyé ; une requête vers une URL issue de la requête SQL remettrait donc un jeton utilisable à quiconque contrôle cette URL, tout en permettant de lire des conteneurs sur lesquels l’utilisateur n’a aucun droit.

Pour Azure, une collection nommée qui s’appuie sur une identité de charge de travail ou une identité managée est également restreinte, y compris lorsqu’elle est définie dans la configuration du Serveur, tout comme `extra_credentials(client_id = '...', tenant_id = '...')`, qui échange le jeton fédéré propre au Serveur contre le client nommé. Les disques définis dans la configuration du Serveur continuent d’utiliser l’identité de charge de travail ou l’identité managée. Un disque Azure dynamique est restreint comme une table, sauf pour une table de la base de données `system` lorsque le paramètre du Serveur `s3_allow_server_credentials_for_system_table_disks` est activé ; un disque Azure dynamique créé alors que ce paramètre est activé l’inscrit dans sa définition stockée, de sorte qu’après un redémarrage, il continue d’utiliser l’identité du Serveur. Cette mention est écrite uniquement par le Serveur et est ignorée dans une requête `CREATE` ou `ATTACH`. La destination de `after_processing = 'move'` dans `AzureQueue` doit disposer de ses propres informations d’authentification (une chaîne de connexion ou un jeton SAS), même lorsque ce paramètre est activé, tout comme une destination de déplacement `S3Queue` nécessite ses propres clés. Une table persistante `AzureBlobStorage` ou `AzureQueue`, ou une table sur un disque Azure dynamique, qui s’appuyait sur l’identité du Serveur est chargée au démarrage avec un client dépourvu d’informations d’authentification, conformément à `s3_load_table_anonymously_if_credentials_restricted` ; `RESTORE` crée les tables Azure de la même manière que `CREATE`, de sorte qu’une telle table y est plutôt refusée.

Pour le laisser désactivé pour les utilisateurs non approuvés, fixez-le dans leur profil en définissant explicitement la valeur sur `0` et en le marquant comme `readonly` :

```xml
<profiles>
    <untrusted>
        <!-- The explicit value is required: a `readonly` constraint alone only blocks direct changes,
             but `compatibility` with a version before this setting was introduced would otherwise
             restore the old (allowing) default. Setting the value explicitly defeats `compatibility`. -->
        <s3_allow_server_credentials_in_user_queries>0</s3_allow_server_credentials_in_user_queries>
        <constraints>
            <s3_allow_server_credentials_in_user_queries>
                <readonly/>
            </s3_allow_server_credentials_in_user_queries>
        </constraints>
    </untrusted>
</profiles>
```

Ce paramètre n’a aucun effet dans `clickhouse-local`, où l’utilisateur est l’opérateur.

Les bases de données `DataLakeCatalog` (Glue, BigLake) sont également concernées, avec une différence. Un objet de catalogue est créé une seule fois et partagé entre tous les utilisateurs de la base de données, de sorte que la valeur ne peut pas être lue pour chaque requête ; elle est capturée à partir de la session qui exécute `CREATE DATABASE` (ou un `ATTACH DATABASE` utilisateur). Une base de données créée alors que ce paramètre est activé (par exemple dans une session ou un profil de confiance) peut utiliser les informations d’authentification ambiantes du Serveur pour son catalogue, et tout utilisateur pouvant interroger cette base de données les partage ensuite ; si elle est créée avec la configuration par défaut, le catalogue est restreint pour tout le monde, quel que soit l’utilisateur qui l’interroge. Lorsque le Serveur charge une base de données déjà créée depuis ses propres métadonnées (au démarrage, `RESTORE`), la restriction est réappliquée avec le contexte de démarrage, comme pour les tables persistantes `S3`/`S3Queue` : un catalogue qui résout des informations d’authentification gérées par le Serveur reste indisponible et la base de données devient inaccessible après un redémarrage (le Serveur démarre tout de même ; la base de données est chargée avec un catalogue indisponible conformément à `s3_load_table_anonymously_if_credentials_restricted`, et les requêtes signalent la restriction). Un catalogue doté d’informations d’authentification explicites (Glue : `aws_access_key_id` et `aws_secret_access_key` ; BigLake : un triplet Google ADC complet) fonctionne dans tous les cas et reste disponible après redémarrage.
