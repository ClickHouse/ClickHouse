<div id="enable_adaptive_aggregator">
  ## enable_adaptive_aggregator
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "Nouveau paramètre permettant d’activer l’agrégation `GROUP BY` adaptative, qui fige la table de hachage locale de chaque thread lorsqu’elle atteint `adaptive_aggregator_freeze_threshold` clés, afin que les clés fréquentes continuent d’être agrégées dans les petites tables locales, tandis que les clés rares sont routées selon leur hash vers des files d’attente par bucket et agrégées exactement une fois lors de la fusion parallèle des buckets ; les clés rares sont ainsi stockées et traitées une seule fois au lieu d’une fois par thread."}]}]} />

Active l’algorithme `GROUP BY` adaptatif : chaque thread agrège dans sa table de hachage locale jusqu’à ce qu’elle atteigne `adaptive_aggregator_freeze_threshold` clés (ou `adaptive_aggregator_freeze_threshold_bytes` de mémoire), puis celle-ci est figée. Les lignes associées aux clés déjà rencontrées (fréquentes) continuent alors de la mettre à jour sur place, tandis que les nouvelles clés (rares) sont routées selon leur hash vers des files d’attente par bucket et agrégées exactement une fois lors de la fusion parallèle des buckets. Les clés fréquentes restent dans de petites tables tenant en cache, tandis que les clés rares ne sont stockées et traitées qu’une seule fois, au lieu d’une fois par thread.

Les paramètres d’agrégation externe (`max_bytes_before_external_group_by`, `max_bytes_ratio_before_external_group_by`) sont respectés : au-delà du seuil, les files d’attente sont vidées de manière anticipée dans la table partagée et, si cela ne suffit pas à repasser sous ce seuil, la table partagée est déversée sur disque via l’agrégation externe ordinaire.

<div id="enable_group_by_top_k_optimization">
  ## enable_group_by_top_k_optimization
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "Nouveau paramètre permettant de contrôler l'optimisation du filtrage TopK lors de l'agrégation dans les requêtes `GROUP BY key ORDER BY key LIMIT N`."}]}]} />

Active l&#39;optimisation du filtrage TopK lors de l&#39;agrégation dans les requêtes `GROUP BY keys ORDER BY <prefix of keys> LIMIT K`, ainsi que dans les requêtes `GROUP BY keys LIMIT K` sans `ORDER BY` (dans ce cas, n&#39;importe quels `K` groupes constituent un résultat valide, un tri sur toutes les clés est donc généré).

Lorsqu&#39;elle est activée, l&#39;agrégateur maintient un tas de taille limitée contenant les `K` clés les mieux classées rencontrées jusqu&#39;à présent et n&#39;insère pas de nouvelles lignes dans la table de hachage lorsque leur clé de regroupement ne peut pas figurer dans le résultat final. Cela évite d&#39;agréger des lignes qui seraient écartées par le `ORDER BY ... LIMIT` ultérieur et, lorsque le tas classe la clé `GROUP BY` complète, supprime également les groupes évincés de la table de hachage intermédiaire, dont la taille est alors limitée par le `LIMIT` plutôt que par le nombre de clés distinctes. Lorsque le `ORDER BY` ne couvre qu&#39;un préfixe strict des clés `GROUP BY`, le classement ne peut pas identifier un groupe complet ; seules des lignes sont donc ignorées : la table de hachage conserve chaque groupe admis et peut toujours croître en fonction de la cardinalité des colonnes de clés restantes.

L&#39;optimisation est désactivée lorsque le `LIMIT` demandé est supérieur à [query&#95;plan&#95;max&#95;limit&#95;for&#95;top&#95;k&#95;optimization](/fr/reference/settings/session-settings/query-plan#query_plan_max_limit_for_top_k_optimization) ou au plafond fixe de `100000`, car le coût du tas en mémoire et en CPU augmente avec le `LIMIT` demandé.

L&#39;optimisation est ignorée pour les formes de requêtes où la suppression de groupes pourrait modifier le résultat, notamment avec `WITH TOTALS`, `HAVING`, `QUALIFY`, les fonctions de fenêtre, `ROLLUP`/`CUBE`/`GROUPING SETS`, `LIMIT WITH TIES`, un `COLLATE` sur l&#39;une des clés `GROUP BY` correspondantes (un `COLLATE` sur une colonne `ORDER BY` située après le préfixe de clé complet ne peut pas affecter les groupes retenus et ne désactive donc pas l&#39;optimisation), un `ORDER BY` sur un agrégat ou sur tout élément qui n&#39;est pas un préfixe initial des clés `GROUP BY`, ainsi que lorsque `max_rows_to_group_by` ou `exact_rows_before_limit` est défini.

Valeurs possibles :

* 0 — Désactivé.
* 1 — Activé.

<div id="enable_packed_string_keys_in_aggregation">
  ## enable_packed_string_keys_in_aggregation
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "1"},{"label": "Nouveau paramètre permettant d’activer ou de désactiver la table de hachage basée sur `PackedStringRef` pour les `GROUP BY` avec une seule clé `String`. previous_value=false afin que la `compatibility` avec les versions antérieures à 26.8 rétablisse la méthode legacy basée sur `StringHashTable`, y compris sa répartition en buckets à deux niveaux."}]}]} />

Utilise une table de hachage indexée par des références de chaînes compactes de 16 octets (`PackedStringRef`) pour les `GROUP BY` comportant une seule clé `String` non nullable. Les clés d’au plus 11 octets sont stockées directement dans la référence compacte ; les clés plus longues sont référencées dans une arène.
Cette méthode est plus rapide pour la plupart des workloads, mais peut être plus lente que la méthode legacy pour les `GROUP BY` avec très peu de clés distinctes de plus de 11 octets (en particulier de 12 à 24 octets), car la table de hachage legacy conserve les clés directement dans la cellule, tandis que la table compacte déréférence le pointeur vers l’arène à chaque recherche.
Lorsqu’elle est désactivée, la méthode legacy basée sur `StringHashTable` (celle utilisée par défaut avant la version 26.8) est employée.

Tous les serveurs participant à une requête distribuée doivent utiliser la même valeur : avec `distributed_aggregation_memory_efficient`, les numéros de buckets à deux niveaux dépendent du hash de la clé, qui diffère selon la méthode. Des serveurs utilisant des valeurs différentes pour ce paramètre peuvent donc répartir une même clé dans différents buckets et produire un résultat fusionné incorrect. Pour garantir cette cohérence, l’initiateur transmet toujours sa valeur effective avec les requêtes secondaires (même lorsqu’elle provient uniquement des valeurs par défaut du serveur ou du profil), en remplaçant les valeurs par défaut des serveurs distants.
