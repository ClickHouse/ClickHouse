<div id="adaptive_aggregator_freeze_threshold">
  ## adaptive_aggregator_freeze_threshold
</div>

<SettingsInfoBlock type="UInt64" default_value="16384" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "16384"},{"label": "Nouveau paramètre définissant le nombre de clés à partir duquel l’agrégateur adaptatif (`enable_adaptive_aggregator`) fige la table de hachage locale d’un thread."}]}]} />

Nombre de clés à partir duquel l’agrégateur adaptatif fige la table de hachage locale d’un thread (voir `enable_adaptive_aggregator`). Des valeurs plus faibles maintiennent les tables figées dans le cache, tandis que des valeurs plus élevées leur permettent d’absorber davantage de clés fréquentes. La valeur 0 fige les tables dès que possible, ce qui fait que l’algorithme se comporte de manière similaire à l’agrégateur partitionné (`enable_sharding_aggregator`) : chaque clé est routée selon son hash et agrégée par un seul propriétaire, mais l’opération est reportée à la phase de fusion au lieu d’être échangée entre les threads pendant le parcours.

<div id="adaptive_aggregator_freeze_threshold_bytes">
  ## adaptive_aggregator_freeze_threshold_bytes
</div>

<SettingsInfoBlock type="UInt64" default_value="4194304" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "4194304"},{"label": "Nouveau paramètre limitant, en octets, les tables locales figées de l’agrégateur adaptatif : la première limite atteinte entre celle-ci et le seuil du nombre de clés s’applique ; 0 désactive la limite en octets."}]}]} />

Taille de mémoire à partir de laquelle l’agrégateur adaptatif fige la table de hachage locale d’un thread (voir `enable_adaptive_aggregator`). Une table est figée lorsque cette valeur ou `adaptive_aggregator_freeze_threshold` est atteinte en premier. La taille correspond aux octets effectivement alloués par la table locale (son tampon de table de hachage et ses arènes), vérifiés entre les blocs. La limite en octets est importante lorsque les clés ou les états d’agrégation sont volumineux : le seul seuil du nombre de clés permettrait à ces tables de dépasser la capacité des caches CPU. Avec la valeur par défaut, les tables dont les clés et les états sont de taille habituelle continuent d’être figées en fonction du nombre de clés. 0 désactive la limite en octets ; seul le seuil du nombre de clés s’applique alors.

<div id="any_join_distinct_right_table_keys">
  ## any_join_distinct_right_table_keys
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "19.14"},{"label": "0"},{"label": "Désactive par défaut les JOIN ANY RIGHT et ANY FULL afin d’éviter les incohérences"}]}]} />

Active le comportement legacy du serveur ClickHouse pour les opérations `ANY INNER|LEFT JOIN`.

<Note>
  Utilisez ce paramètre uniquement pour assurer la rétrocompatibilité si vos cas d’usage dépendent du comportement legacy de `JOIN`.
</Note>

Lorsque le comportement legacy est activé :

* Les résultats des opérations `t1 ANY LEFT JOIN t2` et `t2 ANY RIGHT JOIN t1` ne sont pas identiques, car ClickHouse utilise une logique de correspondance des clés entre les tables, de gauche à droite, de plusieurs à un.
* Les résultats des opérations `ANY INNER JOIN` contiennent toutes les lignes de la table de gauche, comme c’est le cas pour les opérations `SEMI LEFT JOIN`.

Lorsque le comportement legacy est désactivé :

* Les résultats des opérations `t1 ANY LEFT JOIN t2` et `t2 ANY RIGHT JOIN t1` sont identiques, car ClickHouse utilise une logique qui permet une correspondance des clés de un à plusieurs dans les opérations `ANY RIGHT JOIN`.
* Les résultats des opérations `ANY INNER JOIN` contiennent une ligne par clé provenant des tables de gauche et de droite.

Valeurs possibles :

* 0 — Le comportement legacy est désactivé.
* 1 — Le comportement legacy est activé.

Voir aussi :

* [strictness des JOIN](/fr/reference/statements/select/join#settings)

<div id="convert_query_to_cnf">
  ## convert_query_to_cnf
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

Lorsqu&#39;elle est définie sur `true`, une requête `SELECT` est convertie en forme normale conjonctive (CNF). Dans certains cas, réécrire une requête en CNF peut accélérer son exécution (voir cette [issue GitHub](https://github.com/ClickHouse/ClickHouse/issues/11749) pour plus d&#39;explications).

Par exemple, notez que la requête `SELECT` suivante n&#39;est pas modifiée (comportement par défaut) :

```sql
EXPLAIN SYNTAX
SELECT *
FROM
(
    SELECT number AS x
    FROM numbers(20)
) AS a
WHERE ((x >= 1) AND (x <= 5)) OR ((x >= 10) AND (x <= 15))
SETTINGS convert_query_to_cnf = false;
```

Le résultat est :

```response
┌─explain────────────────────────────────────────────────────────┐
│ SELECT x                                                       │
│ FROM                                                           │
│ (                                                              │
│     SELECT number AS x                                         │
│     FROM numbers(20)                                           │
│     WHERE ((x >= 1) AND (x <= 5)) OR ((x >= 10) AND (x <= 15)) │
│ ) AS a                                                         │
│ WHERE ((x >= 1) AND (x <= 5)) OR ((x >= 10) AND (x <= 15))     │
│ SETTINGS convert_query_to_cnf = 0                              │
└────────────────────────────────────────────────────────────────┘
```

Définissons `convert_query_to_cnf` à `true` et voyons ce qui change :

```sql
EXPLAIN SYNTAX
SELECT *
FROM
(
    SELECT number AS x
    FROM numbers(20)
) AS a
WHERE ((x >= 1) AND (x <= 5)) OR ((x >= 10) AND (x <= 15))
SETTINGS convert_query_to_cnf = true;
```

Notez que la clause `WHERE` est réécrite en CNF, mais le jeu de résultats reste identique : la logique booléenne est inchangée.

```response
┌─explain───────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│ SELECT x                                                                                                              │
│ FROM                                                                                                                  │
│ (                                                                                                                     │
│     SELECT number AS x                                                                                                │
│     FROM numbers(20)                                                                                                  │
│     WHERE ((x <= 15) OR (x <= 5)) AND ((x <= 15) OR (x >= 1)) AND ((x >= 10) OR (x <= 5)) AND ((x >= 10) OR (x >= 1)) │
│ ) AS a                                                                                                                │
│ WHERE ((x >= 10) OR (x >= 1)) AND ((x >= 10) OR (x <= 5)) AND ((x <= 15) OR (x >= 1)) AND ((x <= 15) OR (x <= 5))     │
│ SETTINGS convert_query_to_cnf = 1                                                                                     │
└───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

Valeurs possibles : true, false

<div id="defer_partition_pruning_after_final">
  ## defer_partition_pruning_after_final
</div>

<SettingsInfoBlock type="Bool" default_value="1" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.5"},{"label": "1"},{"label": "Paramètre ajouté en 26.5 pour contrôler le comportement d'élagage des partitions avec FINAL, introduit discrètement en 26.3 (https:\/\/github.com\/ClickHouse\/ClickHouse\/pull\/98242). Lorsqu&#39;il est activé (par défaut), l&#39;élagage des partitions est ignoré pour les requêtes `FINAL` sur les tables dont les
colonnes de clé de partition ne font pas partie de la clé de tri. Il s&#39;agit du comportement sûr du point de vue de la validité des résultats,
introduit en 26.3 : `FINAL` peut devoir dédupliquer des lignes qui partagent une clé primaire mais se trouvent
dans des partitions différentes, et l&#39;élagage des partitions exclurait silencieusement ces lignes de
l&#39;ensemble d&#39;entrée de la déduplication.

Lorsqu&#39;il est désactivé, l&#39;élagage des partitions s&#39;applique même avec `FINAL`, ce qui rétablit le comportement
antérieur à 26.3. Cela peut être nettement plus rapide pour les requêtes avec des prédicats `WHERE` sur la
colonne de partition, mais n&#39;est correct que lorsque des lignes ayant la même clé primaire ne peuvent pas exister
dans des partitions différentes — par exemple, des tables de journaux d&#39;événements dont la colonne de partition est définie au moment de l&#39;insert
et ne change jamais.

Ce paramètre n&#39;affecte que les tables partitionnées dont les colonnes de clé de partition ne sont pas incluses
dans la clé de tri ; pour les autres tables, l&#39;élagage des partitions est toujours appliqué.

Valeurs possibles :

* 0 — Appliquer l&#39;élagage des partitions avant `FINAL` (comportement antérieur à 26.3, plus rapide mais non sûr dans le cas général).
* 1 — Différer l&#39;élagage des partitions après `FINAL` (par défaut, sûr du point de vue de la validité des résultats).

<div id="filter">
  ## filter
</div>

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": ""},{"label": "Nouveau paramètre permettant d’ajouter une clause WHERE autour d’une requête."}]}]} />

Ajoute une clause `WHERE` à la requête en l’enveloppant dans une sous-requête. Plusieurs filtres sont combinés avec AND. L’interface HTTP autorise plusieurs paramètres d’URL `filter`, combinés avec AND dans l’ordre, ainsi qu’avec la valeur de ce paramètre.

</Danger>

<div id="framing_output_format">
  ## framing_output_format
</div>

<BetaBadge />

<SettingsInfoBlock type="String" default_value="None" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.8"},{"label": "None"},{"label": "Nouveau paramètre permettant de sélectionner un format de tramage qui multiplexe les paquets de données, de totaux, d’extrêmes, de progression, de journaux et d’événements de profilage dans un flux de sortie unique via HTTP."}]}]} />

Permet de multiplexer différentes parties de la réponse à une requête dans un flux unique : fragments de données, totaux et extrêmes, paquets de progression, événements de profilage (métriques) et journaux du serveur — tout ce que prend en charge le protocole natif.

Les formats de tramage sont indépendants des formats de sortie : ils encapsulent les octets produits par n’importe quel format de sortie, en séparant et, éventuellement, en encodant ces fragments d’octets. La concaténation des charges utiles de tous les paquets `data`, `totals` et `extremes` correspond exactement à ce que le format de sortie aurait produit sans tramage. Les paquets auxiliaires (progression, journaux, événements de profilage, exceptions) sont représentés en JSON.

Une exception délibérée : un format de sortie qui omet les totaux et les extrêmes de sa sortie brute parce qu’il ne peut pas les représenter (la famille `JSONCompactEachRow`) les émet malgré tout avec le tramage, dans les paquets `totals` et `extremes`. Pour ces formats, la concaténation des seuls paquets `data` correspond exactement à la sortie sans tramage, tandis que les paquets `totals` et `extremes` contiennent des lignes supplémentaires absentes de cette sortie.

Les journaux du serveur sont inclus si le paramètre `send_logs_level` est défini, et les événements de profilage si le paramètre `send_profile_events` est activé (ils sont envoyés au plus une fois toutes les `interactive_delay` microsecondes, et les paquets de progression sont également limités par `interactive_delay`).

Un flux réussi se termine par un paquet `progress` final contenant les compteurs finaux (`result_rows`, `result_bytes`, `memory_usage`), écrit après les paquets `log` et `profile_events` de fin émis par la journalisation de fin de requête, à l’instar du paquet de progression final du protocole natif. En cas d’échec, le paquet `exception` est le dernier paquet — à une exception près : lorsque l’échec survient après qu’une partie du flux de paquets a déjà été produite dans la réponse et ne peut plus être supprimée (l’écriture d’un paquet échoue en cours de route, la transmission du paquet `exception` lui-même échoue, ou le flux de réponse échoue lors de son vidage ou de sa fermeture), le tramage échoue de manière sécurisée : le flux est interrompu sans paquet `exception` terminal, et le client observe une réponse tronquée ainsi qu’une connexion HTTP interrompue au lieu d’un paquet terminal analysable. Rien n’est jamais ajouté après un flux de paquets partiel ; un corps d’erreur HTTP brut n’y est donc jamais mélangé.

Tout ce qu’une requête active uniquement via sa propre clause `SETTINGS` — un format de tramage, `send_logs_level` ou `send_profile_events` — n’est connu qu’après l’analyse de la requête ; les journaux et événements de profilage correspondants ne sont donc capturés qu’à partir de l’exécution de la requête. Les journaux et événements de profilage des phases d’analyse syntaxique, de planification et d’analyse sont capturés uniquement lorsque le paramètre provient de la session ou de l’URL. Par exemple, une requête qui échoue pendant l’analyse (par exemple, en raison d’une référence à une table inconnue) et n’active `send_logs_level` que dans sa clause `SETTINGS` ne transmet que le paquet `exception`, et non les journaux de la phase d’analyse ; définissez `send_logs_level` dans la session ou l’URL pour les capturer.

La même réserve liée à la découverte tardive s’applique à `send_logs_source_regexp` : la file de journaux filtre les entrées par source au moment où chacune est capturée, de sorte qu’une expression régulière définie uniquement dans la clause `SETTINGS` de la requête ne prend effet qu’à partir de l’exécution de la requête. Les paquets `log` des phases d’analyse syntaxique, de planification et d’analyse sont filtrés selon la valeur du paramètre définie dans la session ou l’URL (ils ne sont pas filtrés si elle n’y est pas définie) ; ils peuvent donc inclure des sources qui ne correspondent pas à l’expression régulière définie au niveau de la requête. Inversement, les entrées ignorées par une expression régulière plus restrictive définie dans la session ou l’URL ne sont pas récupérées par une expression régulière plus large définie au niveau de la requête. Définissez `send_logs_source_regexp` dans la session ou l’URL pour filtrer l’ensemble du cycle de vie de la requête.

Le paramètre s’applique actuellement au protocole HTTP et est ignoré par les autres interfaces.

Valeurs possibles :

* `None` - achemine de manière transparente tous les éléments applicables (données, totaux, extrêmes, progression) vers le format de sortie et ignore ceux qui ne le sont pas (métriques, journaux), de sorte que tout fonctionne comme par défaut.
* `EventStream` - encapsule les paquets sous forme d’événements HTTP envoyés par le serveur (`text/event-stream`). Chaque paquet est envoyé comme un événement portant le nom correspondant : `data`, `totals`, `extremes`, `progress`, `log`, `profile_events`, `exception`. La progression et les autres paquets auxiliaires sont envoyés au format JSON. Comme les événements envoyés par le serveur constituent un protocole texte qui traite les sauts de ligne (y compris les retours chariot, `\r`) comme des délimiteurs, un bloc de données formatées est encodé en base64 dans un unique champ `data` de l’événement. Ce champ se décode en payload entièrement formaté, avec tous ses sauts de ligne ; le `Content-Type` contient un paramètre `payload=base64` pour l’indiquer. Tout format de sortie peut ainsi être transporté exactement octet pour octet, qu’il soit textuel ou binaire.
* `JSONEachPacketBase64` - chaque paquet est un objet JSON sur une ligne distincte et les données formatées sont encodées en base64, par exemple `{"packet":"data","data":"eyJ4IjoxfQo="}`. Convient aux formats de sortie binaires.
* `JSONEachPacketString` - chaque paquet est un objet JSON sur une ligne distincte et les données formatées sont placées dans une chaîne, par exemple `{"packet":"data","data":"{\"x\":1}\n"}`.

`JSONEachPacketString` place les octets du payload dans une chaîne JSON sans les valider ni les réencoder. Les colonnes `String` et `FixedString` peuvent contenir des octets arbitraires ; les formats de sortie textuels (tels que `JSONEachRow`, `TSV` ou `CSV`) peuvent donc émettre des valeurs UTF-8 non valides, tout comme le `JSONEachRow` natif de ClickHouse avec la valeur par défaut `output_format_json_validate_utf8 = 0`. Le flux NDJSON résultant n’est alors pas garanti comme étant en UTF-8 valide. Utilisez `JSONEachPacketBase64` pour transporter des octets arbitraires exactement octet pour octet.

Exemple :

```bash
curl "http://localhost:8123/?framing_output_format=JSONEachPacketString" -d "SELECT number FROM numbers(3) FORMAT JSONEachRow"
```

Résultat :

```text
{"packet":"data","data":"{\"number\":\"0\"}\n{\"number\":\"1\"}\n{\"number\":\"2\"}\n"}
{"packet":"profile_events","profile_events":[{"host_name":"localhost","current_time":"2026-07-11 00:00:00","thread_id":"0","type":"increment","name":"SelectedRows","value":"3"}]}
{"packet":"progress","progress":{"read_rows":"3","read_bytes":"24","total_rows_to_read":"3","result_rows":"3","result_bytes":"24","elapsed_ns":"1265958"}}
```

<div id="session_timezone">
  ## session_timezone
</div>

<BetaBadge />

Définit le fuseau horaire implicite de la session ou de la requête actuelle.
Le fuseau horaire implicite est celui appliqué aux valeurs de type DateTime/DateTime64 pour lesquelles aucun fuseau horaire n’est explicitement spécifié.
Ce paramètre a préséance sur le fuseau horaire implicite configuré globalement (au niveau du serveur).
Une valeur de &#39;&#39; (chaîne vide) signifie que le fuseau horaire implicite de la session ou de la requête actuelle est celui du [fuseau horaire du serveur](/fr/reference/settings/server-settings/settings/other#timezone).

Vous pouvez utiliser les fonctions `timeZone()` et `serverTimeZone()` pour obtenir le fuseau horaire de la session et celui du serveur.

Valeurs possibles :

* N’importe quel nom de fuseau horaire de `system.time_zones`, par exemple `Europe/Berlin`, `UTC` ou `Zulu`

Exemples :

```sql
SELECT timeZone(), serverTimeZone() FORMAT CSV

"Europe/Berlin","Europe/Berlin"
```

```sql
SELECT timeZone(), serverTimeZone() SETTINGS session_timezone = 'Asia/Novosibirsk' FORMAT CSV

"Asia/Novosibirsk","Europe/Berlin"
```

Attribuez au DateTime interne le fuseau horaire de session &#39;America/Denver&#39;, sans fuseau horaire explicitement spécifié :

```sql
SELECT toDateTime64(toDateTime64('1999-12-12 23:23:23.123', 3), 3, 'Europe/Zurich') SETTINGS session_timezone = 'America/Denver' FORMAT TSV

1999-12-13 07:23:23.123
```

<Warning>
  Toutes les fonctions qui analysent des valeurs DateTime/DateTime64 ne respectent pas `session_timezone`. Cela peut entraîner des erreurs subtiles.
  Voir l&#39;exemple et l&#39;explication ci-dessous.
</Warning>

```sql
CREATE TABLE test_tz (`d` DateTime('UTC')) ENGINE = Memory AS SELECT toDateTime('2000-01-01 00:00:00', 'UTC');

SELECT *, timeZone() FROM test_tz WHERE d = toDateTime('2000-01-01 00:00:00') SETTINGS session_timezone = 'Asia/Novosibirsk'
0 rows in set.

SELECT *, timeZone() FROM test_tz WHERE d = '2000-01-01 00:00:00' SETTINGS session_timezone = 'Asia/Novosibirsk'
┌───────────────────d─┬─timeZone()───────┐
│ 2000-01-01 00:00:00 │ Asia/Novosibirsk │
└─────────────────────┴──────────────────┘
```

Cela s’explique par l’utilisation de chaînes d’analyse différentes :

* `toDateTime()` sans fuseau horaire explicitement indiqué, utilisé dans la première requête `SELECT`, respecte le paramètre `session_timezone` et le fuseau horaire global.
* Dans la deuxième requête, une valeur DateTime est analysée à partir d’une String et hérite du type et du fuseau horaire de la colonne existante `d`. Ainsi, le paramètre `session_timezone` et le fuseau horaire global ne sont pas pris en compte.

**Voir aussi**

* [timezone](/fr/reference/settings/server-settings/settings/other#timezone)

<div id="transform_null_in">
  ## transform_null_in
</div>

<SettingsInfoBlock type="Bool" default_value="0" />

Active l&#39;égalité des valeurs [NULL](/fr/reference/syntax#null) pour l&#39;opérateur [IN](/fr/reference/statements/in).

Par défaut, les valeurs `NULL` ne peuvent pas être comparées, car `NULL` désigne une valeur indéfinie. Ainsi, la comparaison `expr = NULL` doit toujours renvoyer `false`. Avec ce paramètre, `NULL = NULL` renvoie `true` pour l&#39;opérateur `IN`.

Valeurs possibles :

* 0 — La comparaison des valeurs `NULL` avec l&#39;opérateur `IN` renvoie `false`.
* 1 — La comparaison des valeurs `NULL` avec l&#39;opérateur `IN` renvoie `true`.

**Exemple**

Considérez la table `null_in` :

```text
┌──idx─┬─────i─┐
│    1 │     1 │
│    2 │  NULL │
│    3 │     3 │
└──────┴───────┘
```

Requête :

```sql
SELECT idx, i FROM null_in WHERE i IN (1, NULL) SETTINGS transform_null_in = 0;
```

Résultat :

```text
┌──idx─┬────i─┐
│    1 │    1 │
└──────┴──────┘
```

Requête :

```sql
SELECT idx, i FROM null_in WHERE i IN (1, NULL) SETTINGS transform_null_in = 1;
```

Résultat :

```text
┌──idx─┬─────i─┐
│    1 │     1 │
│    2 │  NULL │
└──────┴───────┘
```

**Voir aussi**

* [Traitement de NULL dans les opérateurs IN](/fr/reference/statements/in#null-processing)
