## iceberg_insert_commit_retry_initial_backoff_ms {#iceberg_insert_commit_retry_initial_backoff_ms}

<SettingsInfoBlock type="UInt64" default_value="10" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.12"},{"label": "10"},{"label": "Nouveau paramètre. La validation d'un `INSERT` dans Iceberg qui a perdu face à une validation concurrente est réessayée après un délai exponentiel aléatoire plutôt qu'immédiatement."}]}]} />

Borne supérieure du délai avant la première nouvelle tentative d&#39;un `INSERT` dans une table Iceberg dont la validation a perdu face à une validation concurrente.
La borne double à chaque nouvelle tentative, jusqu&#39;à `iceberg_insert_commit_retry_max_backoff_ms`, et chaque délai est choisi aléatoirement
entre zéro et la borne, afin que les rédacteurs ayant perdu la même condition de concurrence ne réessaient pas au même moment et n&#39;entrent pas à nouveau en conflit.
Le délai est appliqué avant la recherche des métadonnées les plus récentes ; avec de nombreux rédacteurs concurrents, il limite donc également la fréquence de listage du répertoire
des métadonnées. Avec `0`, les nouvelles tentatives sont effectuées sans délai.

## iceberg_insert_max_bytes_in_data_file {#iceberg_insert_max_bytes_in_data_file}

<SettingsInfoBlock type="UInt64" default_value="536870912" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.9"},{"label": "536870912"},{"label": "Aligné sur la valeur par défaut documentée de la propriété de table Iceberg `write.target-file-size-bytes` (512 Mio), voir https:\/\/iceberg.apache.org\/docs\/1.5.2\/configuration\/."}]}, {"id": "row-2","items": [{"label": "25.9"},{"label": "1073741824"},{"label": "Nouveau paramètre."}]}]} />

Nombre maximal d&#39;octets d&#39;un fichier de données Parquet Iceberg lors d&#39;une opération d&#39;insertion.

La valeur par défaut reprend la valeur par défaut documentée de la propriété de table Iceberg `write.target-file-size-bytes` (512 Mio),
voir https://iceberg.apache.org/docs/1.5.2/configuration/. La limite est comparée à la taille des données déjà
écrites dans le fichier, c&#39;est-à-dire à leur taille compressée ; un fichier peut donc la dépasser de ce que le writer conserve encore en tampon, comme
les groupes de lignes Parquet incomplets et ceux en cours d&#39;encodage. `iceberg_insert_max_rows_in_data_file` limite le fichier
indépendamment de sa taille.

## iceberg_insert_max_data_files_in_upload {#iceberg_insert_max_data_files_in_upload}

<SettingsInfoBlock type="UInt64" default_value="8" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "8"},{"label": "Nouveau paramètre. Un INSERT dans Iceberg sur S3 ou Azure n'attend plus la fin du téléversement de chaque fichier de données terminé."}]}]} />

Nombre maximal de fichiers de données terminés d&#39;un même flux d&#39;insertion dont le téléversement peut se poursuivre, sans être attendu, pendant que l&#39;`INSERT` écrit le fichier
suivant. S&#39;applique aux stockages d&#39;objet qui effectuent le téléversement en arrière-plan (S3, Azure). Chacun de ces fichiers conserve ses tampons de téléversement jusqu&#39;à la fin
de son téléversement : des valeurs plus élevées masquent donc davantage la latence de téléversement, au prix d&#39;une consommation de mémoire accrue. Avec `0`, l&#39;insertion attend la fin du téléversement de chaque fichier de données avant
d&#39;écrire le suivant.

## iceberg_insert_max_sort_buffer_bytes {#iceberg_insert_max_sort_buffer_bytes}

Nombre maximal d’octets décompressés qu’une opération `INSERT` dans une table Iceberg dotée d’un ordre de tri conserve en tampon, toutes partitions confondues, avant

## iceberg_insert_single_manifest_for_all_partitions {#iceberg_insert_single_manifest_for_all_partitions}

<SettingsInfoBlock type="Bool" default_value="0" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.11"},{"label": "0"},{"label": "Nouveau paramètre."}]}]} />

Un `INSERT` dans une table Iceberg partitionnée écrit un seul fichier manifest pour l’ensemble des partitions concernées, comme le font Spark
et PyIceberg, au lieu d’un fichier manifest par partition. Ce comportement s’applique par flux d’insertion : chaque flux valide son propre
snapshot avec son propre manifest, de sorte qu’un `INSERT` n’écrit exactement un seul manifest qu’avec `max_insert_threads = 1`.
`OPTIMIZE TABLE ... MANIFEST` fusionne alors également les manifests de différentes partitions en un seul.
`ALTER TABLE ... DROP PARTITION` ne peut pas supprimer une partition dont le manifest est partagé avec d’autres partitions.
