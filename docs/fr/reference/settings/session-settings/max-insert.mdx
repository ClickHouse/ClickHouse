<div id="max_insert_block_size">
  ## max_insert_block_size
</div>

**Alias** : `max_insert_block_size_rows`

<SettingsInfoBlock type="NonZeroUInt64" default_value="1048449" />

Taille maximale des blocs (en nombre de lignes) à former pour l&#39;insertion dans une table.

Ce paramètre contrôle la formation des blocs dans deux contextes :

1. Analyse des formats : lorsque le serveur analyse des formats d&#39;entrée orientés lignes (CSV, TSV, JSONEachRow, etc.) depuis n&#39;importe quelle interface (HTTP, clickhouse-client avec des données intégrées, gRPC, protocole wire de PostgreSQL), les blocs sont émis lorsque :

   * Les deux seuils min&#95;insert&#95;block&#95;size&#95;rows AND min&#95;insert&#95;block&#95;size&#95;bytes sont atteints, OR
   * L&#39;un des deux seuils max&#95;insert&#95;block&#95;size&#95;rows OR max&#95;insert&#95;block&#95;size&#95;bytes est atteint

   Remarque : lorsque vous utilisez clickhouse-client ou clickhouse-local pour lire à partir d&#39;un fichier, c&#39;est le client lui-même qui analyse les données, et ce paramètre s&#39;applique côté client.

2. Opérations INSERT : pendant les requêtes INSERT et lorsque les données transitent par des vues matérialisées, le comportement de ce paramètre dépend de `use_strict_insert_block_limits` :

   * Lorsqu&#39;il est activé : les blocs sont émis lorsque :
     * Seuils minimums (AND) : les deux seuils min&#95;insert&#95;block&#95;size&#95;rows AND min&#95;insert&#95;block&#95;size&#95;bytes sont atteints
     * Seuils maximums (OR) : l&#39;un des deux seuils max&#95;insert&#95;block&#95;size&#95;rows OR max&#95;insert&#95;block&#95;size&#95;bytes est atteint

   * Lorsqu&#39;il est désactivé : les blocs sont émis lorsque min&#95;insert&#95;block&#95;size&#95;rows OR min&#95;insert&#95;block&#95;size&#95;bytes est atteint. Les paramètres max&#95;insert&#95;block&#95;size ne sont pas appliqués.

Valeurs possibles :

* Entier positif.

  ## max_insert_threads
</div>

Le nombre maximal de threads utilisés pour exécuter la requête `INSERT`.

Ce paramètre s&#39;applique à la fois à `INSERT SELECT` et à un simple `INSERT` dont les données sont envoyées depuis
`clickhouse-client` ou via l&#39;interface HTTP. La partie écriture du pipeline
(regroupement des blocs et écriture dans la table de destination) est parallélisée
sur un maximum de ce nombre de threads.

Valeurs possibles :

* 0 — Auto. Utilise le nombre de cœurs de processeur disponibles sur le serveur (la même valeur automatique que [`max_threads`](/fr/reference/settings/session-settings/max-threads#max_threads)), réduit en cas de pression mémoire par [`max_insert_threads_min_free_memory_per_thread`](/fr/reference/settings/session-settings/max-insert#max_insert_threads_min_free_memory_per_thread).
* 1 — l&#39;`INSERT` est exécuté dans un seul thread (sans exécution parallèle). Utilisez cette valeur pour préserver l&#39;ordre d&#39;insertion de `INSERT ... SELECT`.
* Entier positif supérieur à 1 — Exécution parallèle avec le nombre de threads indiqué.

Avant la version 26.8, la valeur par défaut était `1` (sans exécution parallèle). Depuis la version 26.8, la valeur par défaut (`0`) correspond au nombre de cœurs de processeur ; `INSERT` est donc parallélisé par défaut. Définissez `max_insert_threads` sur `1` (ou utilisez le paramètre `compatibility`) pour restaurer le comportement précédent.

Valeur par défaut dans Cloud :

* `1` pour les nœuds disposant de 8 Gio de mémoire
* `2` pour les nœuds disposant de 16 Gio de mémoire
* `4` pour les nœuds plus grands

L&#39;`INSERT SELECT` parallèle n&#39;a d&#39;effet que si la partie `SELECT` est exécutée en parallèle ; consultez le paramètre [`max_threads`](/fr/reference/settings/session-settings/max-threads#max_threads).
Pour un simple `INSERT`, les données d&#39;entrée sont lues et analysées dans un seul flux, puis le pipeline est redimensionné en ce nombre de flux pour l&#39;écriture.
La parallélisation de la partie écriture s&#39;applique uniquement aux simples `INSERT` synchrones : les insertions asynchrones ([`async_insert`](/fr/reference/settings/session-settings/async-insert#async_insert) `= 1`) sont placées dans une file d&#39;attente et flushées en arrière-plan ; elles ne sont donc pas affectées par ce paramètre et restent toujours sur un seul flux.
La partie écriture n&#39;est parallélisée que lorsque cela ne pose aucun risque ; sinon, elle reste sur un seul flux et ce paramètre n&#39;a aucun effet. En particulier, l&#39;écriture reste sur un seul flux lorsque [`use_strict_insert_block_limits`](/fr/reference/settings/session-settings/use#use_strict_insert_block_limits) est activé, qu&#39;une table de destination (ou une table vers laquelle elle redirige) déduplique les blocs insérés et que la déduplication des insertions est activée pour la requête (consultez [`deduplicate_insert`](/fr/reference/settings/session-settings/deduplicate-insert#deduplicate_insert)), lorsque la destination possède des vues matérialisées dépendantes — y compris des vues d&#39;une table vers laquelle la destination redirige, par exemple derrière un `Alias` — (sauf si [`parallel_view_processing`](/fr/reference/settings/session-settings/parallel#parallel_view_processing) est activé et que les chaînes de vues dépendantes ne présentent aucun risque de déduplication — la déduplication dans les vues est désactivée ([`deduplicate_blocks_in_dependent_materialized_views`](/fr/reference/settings/session-settings/other#deduplicate_blocks_in_dependent_materialized_views)) ou aucun chemin de vue dépendante ne peut dédupliquer), et systématiquement pour les destinations `Buffer` et `Distributed`. Un `Buffer` effectue son flush dans son propre contexte et un `Distributed` transmet l&#39;écriture à un fragment distant (qui peut lui-même mettre les données en mémoire tampon) ; les paramètres de déduplication de cette requête ne régissent donc pas l&#39;écriture finale, qui reste sur un seul flux indépendamment de ces paramètres. Une insertion par quorum non parallèle ([`insert_quorum`](/fr/reference/settings/session-settings/insert-quorum#insert_quorum) est égal à `2` ou plus, ou à `'auto'`, et [`insert_quorum_parallel`](/fr/reference/settings/session-settings/insert-quorum#insert_quorum_parallel) est désactivé) reste également sur un seul flux, car elle n&#39;autorise qu&#39;une seule part de quorum en cours par table.
Des valeurs plus élevées entraînent une utilisation accrue de la mémoire.

<div id="max_insert_threads_min_free_memory_per_thread">
  ## max_insert_threads_min_free_memory_per_thread
</div>

<SettingsInfoBlock type="UInt64" default_value="4294967296" />

<VersionHistory rows={[{"id": "row-1","items": [{"label": "26.5"},{"label": "4294967296"},{"label": "Nouveau paramètre pour limiter le nombre de threads d’insertion en fonction de la mémoire libre disponible"}]}]} />

Identique à `max_threads_min_free_memory_per_thread`, mais appliqué à `max_insert_threads` plutôt qu’à `max_threads`. La valeur par défaut est plus élevée, car les pipelines d’insertion utilisent généralement des buffers par thread plus volumineux (parts MergeTree, blocs de compression) que les pipelines de lecture.

Si la quantité de mémoire libre est inférieure à `max_insert_threads` multiplié par cette valeur, `max_insert_threads` est réduit en conséquence, avec un minimum de `1`.

Définissez cette valeur sur `0` pour désactiver cette limite.
