Ces paramètres configurent le serveur ClickHouse et sont générés automatiquement à partir du code source de ClickHouse.

## use_minimalistic_part_header_in_zookeeper {#use_minimalistic_part_header_in_zookeeper}

Paramètre obsolète, sans effet. Les tables [répliquées](/fr/reference/engines/table-engines/mergetree-family/replication) stockent toujours l&#39;en-tête d&#39;une partie de données de manière compacte dans un seul `znode`. Les en-têtes de parties écrits par des versions antérieures, avec des `znodes` enfants `columns` et `checksums` distincts, restent lisibles.

## use_separate_cache_arena {#use_separate_cache_arena}

<SettingsInfoBlock type="Bool" default_value="1" changeable_without_restart="No" />

Active une arène jemalloc dédiée pour les allocations de cache (mark cache, uncompressed cache, page cache).
Isole les données de cache des allocations liées au traitement des requêtes, ce qui réduit la fragmentation mémoire.

## use_shared_merge_tree_log_pipeline {#use_shared_merge_tree_log_pipeline}

<SettingsInfoBlock type="Bool" default_value="0" changeable_without_restart="No" />

Disponible uniquement sur ClickHouse Cloud. Lorsque ce paramètre est activé, les logs système sont écrits via un pipeline `SharedMergeTree`
et la base de données `system` devient une base de données Shared : toutes les répliques ont alors accès aux mêmes tables de journaux.

Chaque vidage d’un journal écrit un fichier `Native` à l’aide de la fonction de table `s3` (ou `azureBlobStorage`) dans le dossier correspondant à la
génération du journal et au hachage de ses colonnes et de ses clés. Pour chaque génération, le pipeline maintient la file d’attente `system._<log>_s3queue_<hash>`
qui lit ce dossier, la vue matérialisée `system._<log>_mv_<hash>` et la table `SharedMergeTree` `system.<log>_<hash>`.
`system.<log>` est une table `Merge` regroupant les générations. Un nouveau schéma crée une nouvelle génération ; les paramètres, le TTL et les index
proviennent des clés `smt_settings`, `smt_ttl` et `smt_indices` de la configuration du journal et sont modifiés en place.
Les objets sont créés lors du premier vidage d’un journal, ou au démarrage avec `prepare_system_log_tables_on_startup`.
La clé de tri d’une table est la clé du journal précédée de `hostname`, afin que les lignes d’une réplique soient lues selon cette clé.
Les clés `smt_order_by` et `smt_partition_by` de la configuration du journal remplacent les clés de la table.

La base de données locale `system` est renommée en `system_local` tant que ce paramètre est activé. Ce paramètre nécessite `shared_database_catalog`
et `<shared_log_pipeline><endpoint>` dans la configuration du serveur.
Voir aussi : `shared_log_pipeline.enable_sync_flush`, `shared_log_pipeline.flush_timeout_seconds`.
