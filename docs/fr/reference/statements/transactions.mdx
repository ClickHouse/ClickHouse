Les statements de contrôle des transactions `BEGIN TRANSACTION`, `COMMIT`, `ROLLBACK` et `SET TRANSACTION SNAPSHOT` regroupent plusieurs requêtes portant sur des tables `MergeTree` en une seule transaction.
Les requêtes d&#39;une transaction lisent un même snapshot cohérent des modifications validées par les autres transactions.
Les écritures effectuées hors transaction ne sont pas isolées : un `INSERT`, un `TRUNCATE TABLE` ou un `ALTER TABLE ... DELETE` exécuté hors transaction est visible par la requête suivante d&#39;une transaction en cours. Pour garantir une vue stable, les rédacteurs doivent donc eux aussi passer par des transactions, par exemple avec [`implicit_transaction`](/fr/reference/settings/session-settings/implicit#implicit_transaction).
Les autres transactions ne voient les modifications d&#39;une transaction qu&#39;après son `COMMIT`, tandis que `ROLLBACK` les annule.
Les requêtes exécutées hors transaction peuvent voir les modifications d&#39;une transaction en cours avant sa validation.

  Ces statements font partie d&#39;un ensemble de fonctionnalités expérimentales.

## Syntaxe {#syntax}

```sql
BEGIN TRANSACTION
START TRANSACTION
COMMIT
ROLLBACK
SET TRANSACTION SNAPSHOT snapshot
```

Une transaction appartient à une session, et une session contient au plus une transaction.
Via HTTP, envoyez toutes les requêtes d’une même transaction avec le même `session_id` : une requête sans `session_id` s’exécute dans sa propre session, qui prend fin avec la requête.
Une transaction encore en cours à la fin de sa session est annulée (rollback).

## BEGIN TRANSACTION {#begin-transaction}

Démarre une transaction dans la session en cours. `START TRANSACTION` en est un alias, introduit dans la v24.3.0.

Les transactions imbriquées ne sont pas prises en charge : exécuter `BEGIN TRANSACTION` au sein d&#39;une transaction lève une exception `INVALID_TRANSACTION`.

## COMMIT {#commit}

Valide la transaction en cours et rend ses modifications visibles par les autres transactions.
Exécuter `COMMIT` sans transaction en cours lève une exception `INVALID_TRANSACTION`.

Si une requête au sein de la transaction échoue, la transaction est annulée. Une requête qui ne peut pas être analysée, par exemple en raison d’une erreur de syntaxe, ou dont les paramètres de requête sont manquants ou invalides, n’est pas exécutée et laisse la transaction en cours : un `COMMIT` ultérieur la valide donc malgré tout.
Tant qu’un `ROLLBACK` n’a pas mis fin à une transaction annulée, `COMMIT` et les requêtes suivantes lèvent une exception `INVALID_TRANSACTION`. Seules `ROLLBACK`, `SET TRANSACTION SNAPSHOT` et les requêtes `EXPLAIN` autres que `EXPLAIN ANALYZE` peuvent encore s’exécuter.

Le paramètre [`wait_changes_become_visible_after_commit_mode`](/fr/reference/settings/session-settings/other#wait_changes_become_visible_after_commit_mode) détermine ce que `COMMIT` attend.

## ROLLBACK {#rollback}

Annule la transaction en cours et rejette ses modifications.
Exécuter `ROLLBACK` en l&#39;absence de transaction en cours lève une exception `INVALID_TRANSACTION`.

## SET TRANSACTION SNAPSHOT {#set-transaction-snapshot}

Remplace le snapshot lu par la transaction en cours par le numéro de séquence de validation (CSN) `snapshot`, par exemple une valeur renvoyée par [`transactionLatestSnapshot`](/fr/reference/functions/regular-functions/other-functions#transactionLatestSnapshot) dans une transaction antérieure.
La transaction voit alors ses propres modifications, les données écrites en dehors des transactions et les modifications des transactions validées jusqu&#39;à ce CSN.
Elle ne lit que les parts que le serveur conserve encore, sans pour autant les protéger contre la suppression : dès lors qu&#39;aucune transaction en cours d&#39;exécution n&#39;a démarré avant qu&#39;une fusion, une mutation ou une autre requête ne supprime une part, le serveur peut supprimer cette part, et un snapshot antérieur ne voit alors plus ses lignes.
Ne vous fiez pas à `SET TRANSACTION SNAPSHOT` pour obtenir des lectures reproductibles de données historiques.
Exécuter `SET TRANSACTION SNAPSHOT` en dehors de toute transaction lève une exception `INVALID_TRANSACTION`.

Les valeurs de `0` à `32` sont réservées et lèvent une exception `INVALID_TRANSACTION`, à deux exceptions près :
`1` rend visibles uniquement les données écrites en dehors des transactions et les propres modifications de la transaction, et `3` rend visibles toutes les parts d&#39;une table, y compris les parts des transactions pas encore validées ainsi que les parts que des transactions ont supprimées ou annulées.

## Requêtes au sein d&#39;une transaction {#queries-inside-a-transaction}

Une transaction peut exécuter des requêtes `SELECT`, `INSERT`, `DELETE`, `OPTIMIZE`, `TRUNCATE TABLE`, `SET` et `EXPLAIN`, ainsi que les mutations `ALTER TABLE` et les opérations sur les partitions.
Les autres requêtes, par exemple `CREATE TABLE`, `UPDATE` ou `ALTER TABLE ... ADD COLUMN`, lèvent une exception `NOT_IMPLEMENTED`, tout comme les requêtes portant sur des tables qui ne prennent pas en charge les transactions, par exemple les tables `ReplicatedMergeTree` ou `Memory`, ou encore `system.transactions`.

Les insertions asynchrones ne sont pas prises en charge au sein d&#39;une transaction, et [`async_insert`](/fr/reference/settings/session-settings/async-insert#async_insert) est activé par défaut. Par conséquent, un `INSERT ... VALUES` ou un `INSERT ... SELECT` exécuté au sein d&#39;une transaction lève une exception `NOT_IMPLEMENTED`, sauf si `async_insert` est désactivé, par exemple avec `SET async_insert = 0`.

Lorsque [`throw_on_unsupported_query_inside_transaction`](/fr/reference/settings/session-settings/throw-on#throw_on_unsupported_query_inside_transaction) est défini sur `0`, certaines de ces requêtes s&#39;exécutent en dehors de la transaction au lieu de lever une exception, si bien que `ROLLBACK` ne les annule pas : c&#39;est le cas, par exemple, d&#39;un `CREATE TABLE` ou d&#39;un `INSERT` dans une table `Memory`.

Lorsque [`implicit_transaction`](/fr/reference/settings/session-settings/implicit#implicit_transaction) est activé, chaque requête exécutée en dehors d&#39;une transaction s&#39;exécute dans sa propre transaction, qui est validée si la requête réussit et annulée si elle échoue.

## Exemples {#examples}

Annuler une insertion :

```sql title="Query"
CREATE TABLE t (n UInt64) ENGINE = MergeTree ORDER BY n;
SET async_insert = 0;

BEGIN TRANSACTION;
INSERT INTO t VALUES (1);
SELECT count() FROM t;
ROLLBACK;
SELECT count() FROM t;
```

```text title="Response"
┌─count()─┐
│       1 │
└─────────┘
┌─count()─┐
│       0 │
└─────────┘
```

Valider une insertion :

```sql title="Query"
BEGIN TRANSACTION;
INSERT INTO t VALUES (2);
COMMIT;
SELECT * FROM t;
```

```text title="Response"
┌─n─┐
│ 2 │
└───┘
```
