Syntaxe :

```sql
EXPLAIN [AST | SYNTAX | QUERY TREE | PLAN | PIPELINE | ANALYZE | ESTIMATE | TABLE OVERRIDE | WHATIF] [setting = value, ...]
    [
      SELECT ... |

    ]
    [FORMAT ...]
```

```sql
      └──ReadFromSystemNumbers
```

## Types d’EXPLAIN {#explain-types}

* `AST` — Arbre syntaxique abstrait.
* `SYNTAX` — Texte de la requête après les optimisations au niveau de l’AST.
* `QUERY TREE` — Arbre de requête après les optimisations au niveau de l’Arbre de requête.
* `PLAN` — Plan d’exécution de la requête.
* `PIPELINE` — Pipeline d’exécution de la requête.
* `ANALYZE` — Exécute la requête et annote le plan d’exécution avec les runtime metrics mesurées.
* `ESTIMATE` — Nombre estimé de lignes, de marques et de parts à lire depuis les tables pendant le traitement de la requête.
* `TABLE OVERRIDE` — Résultat validé d’une surcharge de table sur le schéma d’une fonction de table.
* `CURRENT TRANSACTION` - La transaction de la session en cours.

### EXPLAIN AST {#explain-ast}

Affiche l’AST de la requête. Prend en charge tous les types de requêtes, pas uniquement `SELECT`.

Paramètres :

* `graph` – Affiche l’AST sous forme de graphe, décrit dans le langage de description de graphes [DOT](https://en.wikipedia.org/wiki/DOT_\(graph_description_language\)). Par défaut : 0.

Exemples :

```sql
EXPLAIN AST SELECT 1;
```

```sql
SelectWithUnionQuery (children 1)
 ExpressionList (children 1)
  SelectQuery (children 1)
   ExpressionList (children 1)
    Literal UInt64_1
```

```sql
EXPLAIN AST ALTER TABLE t1 DELETE WHERE date = today();
```

```sql
  explain
  AlterQuery  t1 (children 1)
   ExpressionList (children 1)
    AlterCommand 27 (children 1)
     Function equals (children 1)
      ExpressionList (children 2)
       Identifier date
       Function today (children 1)
        ExpressionList
```

### EXPLAIN SYNTAX {#explain-syntax}

Affiche l&#39;arbre syntaxique abstrait (AST) d&#39;une requête après l&#39;analyse syntaxique.

Cela consiste à analyser la requête, à construire l&#39;AST et l&#39;arbre de requête, à exécuter éventuellement l&#39;analyseur de requêtes et les passes d&#39;optimisation, puis à reconvertir l&#39;arbre de requête en AST.

Paramètres :

* `oneline` – Affiche la requête sur une seule ligne. Valeur par défaut : `0`.
* `run_query_tree_passes` – Exécute les passes de l&#39;arbre de requête avant d&#39;en produire le dump. Valeur par défaut : `0`.
* `query_tree_passes` – Si `run_query_tree_passes` est défini, indique combien de passes exécuter. Si `query_tree_passes` n&#39;est pas spécifié, toutes les passes sont exécutées.
* `single_record` – Renvoie la requête reformatée sous la forme d&#39;un seul enregistrement sur plusieurs lignes au lieu d&#39;un enregistrement par ligne. Valeur par défaut : `1` (contrôlée par le paramètre `explain_syntax_single_record`). Définissez cette valeur sur `0` pour restaurer la sortie historique avec un enregistrement par ligne, ou définissez `explain_syntax_single_record = 0` (globalement ou dans `SETTINGS` par requête), ou définissez `compatibility` sur toute version antérieure à `26.8`.

Exemples :

```sql title="Query"
EXPLAIN SYNTAX SELECT * FROM system.numbers AS a, system.numbers AS b, system.numbers AS c WHERE a.number = b.number AND b.number = c.number;
```

```sql title="Response"
SELECT *
FROM system.numbers AS a, system.numbers AS b, system.numbers AS c
WHERE (a.number = b.number) AND (b.number = c.number)
```

Avec `run_query_tree_passes` :

```sql title="Query"
EXPLAIN SYNTAX run_query_tree_passes = 1 SELECT * FROM system.numbers AS a, system.numbers AS b, system.numbers AS c WHERE a.number = b.number AND b.number = c.number;
```

```sql title="Response"
SELECT
    __table1.number AS `a.number`,
    __table2.number AS `b.number`,
    __table3.number AS `c.number`
FROM system.numbers AS __table1
ALL INNER JOIN system.numbers AS __table2 ON __table1.number = __table2.number
ALL INNER JOIN system.numbers AS __table3 ON __table2.number = __table3.number
```

### EXPLAIN QUERY TREE {#explain-query-tree}

Paramètres :

* `run_passes` — Exécute toutes les passes de l&#39;arbre de requête avant d&#39;en afficher le contenu. Valeur par défaut : `1`.
* `dump_passes` — Affiche des informations sur les passes utilisées avant d&#39;afficher l&#39;arbre de requête. Valeur par défaut : `0`.
* `passes` — Indique le nombre de passes à exécuter. S&#39;il est défini sur `-1`, exécute toutes les passes. Valeur par défaut : `-1`.
* `dump_tree` — Affiche l&#39;arbre de requête. Valeur par défaut : `1`.
* `dump_ast` — Affiche l&#39;AST de la requête généré à partir de l&#39;arbre de requête. Valeur par défaut : `0`.

Exemple :

```sql
EXPLAIN QUERY TREE SELECT id, value FROM test_table;
```

```sql
QUERY id: 0
  PROJECTION COLUMNS
    id UInt64
    value String
  PROJECTION
    LIST id: 1, nodes: 2
      COLUMN id: 2, column_name: id, result_type: UInt64, source_id: 3
      COLUMN id: 4, column_name: value, result_type: String, source_id: 3
  JOIN TREE
    TABLE id: 3, table_name: default.test_table
```

### EXPLAIN PLAN {#explain-plan}

Affiche les étapes du plan de requête.

Paramètres :

* `optimize` — Détermine si les optimisations du plan de requête sont appliquées avant l’affichage du plan. Par défaut : 1.
* `header` — Affiche l’en-tête de sortie pour l’étape. Par défaut : 0.
* `description` — Affiche la description de l’étape. Par défaut : 1.
* `indexes` — Affiche les index utilisés, le nombre de parts filtrées et le nombre de granules filtrés pour chaque index appliqué. Par défaut : 0. Pris en charge pour les tables [MergeTree](/fr/reference/engines/table-engines/mergetree-family/mergetree). À partir de ClickHouse &gt;= v25.9, ce statement ne produit un résultat pertinent que lorsqu’il est utilisé avec `SETTINGS use_query_condition_cache = 0, use_skip_indexes_on_data_read = 0`.
* `projections` — Affiche toutes les projections analysées et leur effet sur le filtrage au niveau des parts en fonction des conditions sur la clé primaire de la projection. Pour chaque projection, cette section inclut des statistiques comme le nombre de parts, de lignes, de marques et de plages évaluées à l’aide de la clé primaire de la projection. Elle indique également combien de parts de données ont été ignorées grâce à ce filtrage, sans lecture depuis la projection elle-même. Le champ `description` permet de déterminer si une projection a réellement été utilisée pour la lecture ou seulement analysée pour le filtrage. Par défaut : 0. Pris en charge pour les tables [MergeTree](/fr/reference/engines/table-engines/mergetree-family/mergetree).
* `actions` — Affiche des informations détaillées sur les actions de l’étape. Par défaut : 1.
* `sorting` — Affiche la description du tri pour chaque étape du plan produisant une sortie triée. Par défaut : 0.
* `keep_logical_steps` — Conserve les étapes logiques du plan pour les jointures au lieu de les convertir en implémentations physiques de jointure. Par défaut : 0.
* `json` — Affiche les étapes du plan de requête sous la forme d’une ligne au format [JSON](/fr/reference/formats/JSON/JSON). Par défaut : 0. Il est recommandé d’utiliser le format [TabSeparatedRaw (TSVRaw)](/fr/reference/formats/TabSeparated/TabSeparatedRaw) pour éviter les séquences d’échappement inutiles.
* `input_headers` — Affiche les en-têtes d’entrée pour l’étape. Par défaut : 0. Utile principalement aux développeurs pour le Débogage des problèmes liés à une incompatibilité entre les en-têtes d’entrée et de sortie.
* `column_structure` — Affiche également la structure des colonnes dans les en-têtes, en plus de leur nom et de leur type. Par défaut : 0. Utile principalement aux développeurs pour le Débogage des problèmes liés à une incompatibilité entre les en-têtes d’entrée et de sortie.
* `distributed` — Affiche les plans de requête exécutés sur des nœuds distants pour les tables distribuées ou les répliques parallèles. N’est pas pris en charge avec `json`. Par défaut : 0.
* `fragments` — Pour une requête exécutée par des workers sans état (`make_distributed_plan = 1`), affiche le plan de chaque fragment de requête ainsi que les échanges entre les fragments. Nécessite `optimize = 1`. N’est pas pris en charge avec `distributed`. Par défaut : 0. Voir [Fragments de requête](#explain-plan-fragments) et, avec `json = 1`, [Fragments de requête en JSON](#explain-plan-fragments-json).
* `tree` — Représente chaque étape, à l’exception de `Expression`, sous la forme d’une boîte reliée aux boîtes de ses entrées, avec les détails que `EXPLAIN` affiche sous l’étape. Les plans imbriqués d’une étape, comme les plans par table de `ReadFromMerge`, sont représentés après le schéma principal, chacun comme un plan à part entière. Pour une requête exécutée par des workers sans état (`make_distributed_plan = 1`), représente également les fragments de requête sous forme de cadres entourant leurs étapes et les échanges sous forme d’arêtes entre les fragments, suivis de la liste des échanges et des niveaux. Nécessite `optimize = 1`. N’est pas pris en charge avec `fragments`, `json` ou `distributed`. Par défaut : 0. Voir [Arborescence des fragments de requête](#explain-plan-fragments-tree).
* `compact` — Lorsqu’il est activé, masque dans le plan les étapes d’expression et les informations détaillées sur les actions (entrées, fonctions, alias et positions de sortie). N’a d’effet que lorsque `actions = 1`. Par défaut : 1.
* `pretty` — Affiche l’arbre du plan à l’aide de caractères de dessin de lignes (├──, └──, │) au lieu de l’indentation, afin de visualiser la hiérarchie. Formate également les propriétés des étapes de jointure de manière intégrée. Par défaut : 1.

<Note>
  Par défaut, `explain_query_plan_default = 'pretty'` : `actions`, `compact` et `pretty` sont donc initialisés à `1`, et le plan est généré sous une forme compacte, mise en forme et annotée avec les actions. Si l’une de ces options est spécifiée explicitement dans le statement `EXPLAIN` (par exemple, `EXPLAIN actions = 0, compact = 0, pretty = 0 SELECT ...`), elle remplace toujours la valeur par défaut.

  Avant ClickHouse 26.7, les valeurs par défaut de `actions`, `compact` et `pretty` étaient `0`. Vous pouvez toujours obtenir cette sortie en définissant `explain_query_plan_default = 'legacy'` (globalement ou par requête via `SETTINGS`), ou en définissant `compatibility` sur une version antérieure à `26.7`.

  Les options `json` et `distributed` n’activent pas les valeurs par défaut de `pretty` (`actions`, `compact` et `pretty`), même lorsque `explain_query_plan_default = 'pretty'`. Pour inclure le détail des actions dans leur sortie, définissez manuellement `actions = 1`.
</Note>

Exemple :

```sql
EXPLAIN SELECT sum(number) FROM numbers(10) GROUP BY number % 4  LIMIT 1;
```

```sql
Output: sum(number)

Limit (preliminary LIMIT)
│  Limit 1
│  Offset 0
└──Aggregating
   │  Keys: number MOD 4
   │  Aggregates: sum(number)
   │  Skip merging: 0
   └──ReadFromSystemNumbers
         Output: number
```

<Note>
  L’estimation du coût des étapes et des requêtes n’est pas prise en charge.
</Note>

Lorsque `json = 1`, le plan de requête est représenté au format JSON. Chaque nœud est un dictionnaire qui possède toujours les clés `Node Type`, `Node Id` et `Plans`. `Node Type` est une chaîne contenant le nom de l’étape, et `Node Id` est un identifiant d’étape unique (le nom de l’étape avec un suffixe numérique, par ex. `Union_10`). `Plans` est un tableau contenant les descriptions des étapes enfants. D’autres clés facultatives peuvent être ajoutées selon le type de nœud et les paramètres. Avec `fragments = 1`, le document décrit également les fragments de requête et les échanges entre eux ; voir [Fragments de requête en JSON](#explain-plan-fragments-json).

Avec `distributed` = 1, la sortie inclut non seulement le plan de requête local, mais également les plans de requête qui seront exécutés sur les nœuds distants. Cela s&#39;avère utile pour analyser et déboguer les requêtes distribuées.

<Note>
  `distributed` est affiché uniquement sous la forme `legacy` (non-`pretty`), car la sortie `pretty` n’intègre pas les plans des segments distants dans l’arborescence du plan. Pour cette raison, l’activation de `distributed` désactive automatiquement les options par défaut de `pretty` (`actions`, `compact` et `pretty`), quelle que soit la valeur de `explain_query_plan_default`. Vous pouvez toujours définir `actions=1` manuellement. L’option `distributed` n’est pas non plus prise en charge avec `json`.
</Note>

Exemple avec une table distribuée :

```sql
EXPLAIN distributed=1 SELECT * FROM remote('127.0.0.{1,2}', numbers(2)) WHERE number = 1;
```

```sql

    Filter ((WHERE + Change column names to column identifiers))

  Expression ((Project names + (Projection + Change column names to column identifiers)))
    ReadFromRemote (Read from remote replica)
      Expression ((Project names + Projection))
        Filter ((WHERE + Change column names to column identifiers))
          ReadFromSystemNumbers
```

Dans les deux exemples, le plan de requête affiche le flux d&#39;exécution complet, y compris les étapes locales et distantes.

Avec `pretty` = 1, l’arbre du plan est affiché à l’aide de caractères de dessin de lignes au lieu de l’indentation, et des informations supplémentaires sont affichées pour les étapes clés :

* Les **colonnes de sortie de la requête** sont affichées en haut du plan.
* Les **expressions** dans les filters, les clés d’agrégation, les descriptions de tri et les fonctions de fenêtre sont affichées dans une notation SQL lisible par l’humain (par ex. `a + 1 > 5` au lieu de `greater(plus(a, 1), 5)`). Les préfixes internes des identifiants de colonnes (tels que `__table1.`) sont supprimés pour plus de clarté.
* Les **étapes source** (telles que `ReadFromMergeTree`) affichent leurs colonnes de sortie.
* Les **étapes de filter** affichent la condition de filter en notation SQL. Lorsque des filters de jointure à l’exécution sont présents, ils sont affichés séparément.
* Les **étapes d’agrégation** affichent les clés et les fonctions d’agrégation avec leurs arguments (par ex. `sum(c)`, `count()`).
* Les **ensembles IN** issus de littéraux `Tuple` affichent leurs valeurs (tronquées pour les grands ensembles), les ensembles basés sur des sous-requêtes sont libellés `subquery1`, `subquery2`, etc., et les ensembles provenant de tables utilisant le moteur `Set` affichent le nom de la table.
* Les **étapes de jointure** affichent la relation de jointure à l’aide d’une notation mathématique, les estimations que
  l’optimiseur d’ordre des jointures a établies pour l’étape (coût, sélectivité, lignes de sortie et lignes de chaque côté),
  ainsi que les colonnes d’entrée de chaque côté. Les symboles suivants sont utilisés pour représenter les différents types de
  JOIN :

| Symbole            | Type de JOIN         |
| ------------------ | -------------------- |
| `⋈`                | Jointure interne     |
| `⟕`                | Jointure gauche      |
| `⟖`                | Jointure droite      |
| `⟗`                | Jointure complète    |
| `⋉`                | Jointure semi gauche |
| `⋊`                | Jointure semi droite |
| `⋉` avec une barre | Jointure anti gauche |
| `⋊` avec une barre | Jointure anti droite |
| `×`                | Jointure croisée     |

Par exemple, `t1 ⟕ t2` signifie une jointure gauche entre les tables `t1` et `t2`.
Le nombre entre crochets après le nom de la table (par ex. `t1[100]`) indique le nombre estimé de lignes
lorsque les statistiques de la table sont disponibles.

Sous la relation de jointure, chaque étape de jointure affiche les estimations établies pour elle par l’optimiseur d’ordre des jointures :

```txt
Cost: estimated <cost>
Selectivity: estimated (NDV) <selectivity>
Output rows: estimated <rows>
Left: rows estimated <left_rows>
Right: rows estimated <right_rows>
```

* `Coût` — le coût de l’ensemble du sous-arbre de jointure sous cette étape, qui est la valeur que l’optimiseur
  minimise lorsqu’il compare les ordres de jointure candidats. Le coût d’une jointure est son nombre estimé de
  paires de lignes correspondantes, `<selectivity> * <left_rows> * <right_rows>`, plus le coût de ses entrées.
* `Sélectivité` — la fraction estimée du produit cartésien des deux côtés qui satisfait
  la condition de jointure. Elle est dérivée du nombre de valeurs distinctes (NDV) des clés de jointure :
  une égalité de clé conserve environ `1 / max(NDV_left, NDV_right)` des paires, et la plus petite
  fraction parmi les conditions de jointure est utilisée.
* `Lignes de sortie` — le nombre estimé de lignes produites par la jointure :
  `<selectivity> * <left_rows> * <right_rows>` pour une jointure interne, avec un minimum de `<left_rows>` pour
  `LEFT`, de `<right_rows>` pour `RIGHT` et de `<left_rows> + <right_rows>` pour `FULL`, car une
  jointure externe conserve chaque ligne de son côté préservé. Lorsqu’une jointure `SEMI` ou `ANTI` participe au
  réordonnancement, elle est estimée comme une fraction de son côté préservé,
  `<preserved_rows> * min(1, <selectivity> * <other_rows>)` pour `SEMI` et les lignes restantes pour
  `ANTI` ; sinon, elle utilise la formule correspondant à son type de jointure.
* `Gauche` / `Droite` — le nombre estimé de lignes entrant dans la jointure de chaque côté.

Une valeur que l’optimiseur n’a pas pu estimer est signalée comme `no stats`. Cela se produit lorsque
l’optimisation de l’ordre des jointures n’a pas été exécutée — par exemple, lorsque
[`query_plan_optimize_join_order_limit`](/fr/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_limit)
est défini sur `0` — ou lorsqu’il n’existe aucune base pour l’estimation.

Les lignes `Input (left):` et `Input (right):` répertorient les colonnes que chaque côté transmet à la jointure.

L’option `pretty` fonctionne bien avec `compact = 1`, qui masque les étapes `Expression` et les informations détaillées sur les actions, ce qui rend le plan plus facile à lire.

Un exemple détaillé avec des jointures. Le paramètre
[`join_runtime_filter_min_probe_rows`](/fr/reference/settings/session-settings/join-runtime#join_runtime_filter_min_probe_rows)
est abaissé uniquement pour qu’une table aussi petite génère malgré tout un filtre de jointure à l’exécution :

#### Fragments de requête {#explain-plan-fragments}

Avec `fragments` = 1, une requête exécutée par des workers sans état (`make_distributed_plan = 1`) est affichée telle qu’elle est découpée pour l’exécution : un plan par fragment de requête. Un fragment de requête est une partie du plan exécutée sous la forme d’une ou de plusieurs tâches parallèles. Les fragments sont affichés dans l’ordre inverse de leurs identifiants : le fragment qui produit l’ensemble de résultats de la requête apparaît en premier, et chaque fragment précède ceux dont il lit les données, de sorte que les données remontent comme dans un arbre du plan. Chaque fragment commence par un en-tête `Query fragment <id> (<stage name>) · tasks=<N>` qui indique son identifiant, le nom de son étape et son nombre de tâches. Les étapes d’envoi et de réception indiquent le nom de l’échange dans lequel elles écrivent ou depuis lequel elles lisent.

Les fragments sont suivis de deux sections, dans lesquelles le fragment de requête `<id>` est désigné par `F<id>` :

* `Exchanges` — une ligne par échange, indiquant le fragment qui envoie les données et celui qui les lit (`F0 -> F2`), ainsi que le mode de transfert des données : par hachage des clés (`hash(...)`), vers chaque tâche du consommateur (`broadcast`), vers une seule tâche (`gather`, avec `sorted by` lorsque l’ordre de tri est conservé) ou sans tenir compte des valeurs (`any`) ; si elles sont envoyées sur le réseau au fur et à mesure de leur production (`streaming`) ou d’abord écrites dans des fichiers temporaires (`persisted`, voir [`distributed_plan_force_exchange_kind`](/fr/reference/settings/session-settings/distributed-plan#distributed_plan_force_exchange_kind)), auquel cas le consommateur ne démarre qu’une fois que le producteur a terminé ; et enfin le nombre de compartiments source et destination.
* `Levels` — identifiants des fragments regroupés par profondeur, des fragments sans dépendances jusqu’au fragment qui produit l’ensemble de résultats. Les fragments d’un même niveau sont indépendants les uns des autres.

Les sets des sous-requêtes `IN` ne sont pas encore affichés : le plan nomme un tel set (par exemple `bid IN subquery1`), mais aucun fragment ne le construit.

Une requête distribuée sans échanges est affichée sous la forme d’un seul fragment de requête qui envoie l’ensemble de résultats via l’échange `final_result`.

Lorsque la requête n’est pas distribuée, le plan est affiché comme en l’absence de `fragments`. Si la requête n’a pas pu être distribuée et s’est rabattue sur une exécution locale, la raison est affichée après le plan sous la forme `Not distributed: <reason>`.

Exemple :

```sql
EXPLAIN fragments = 1
SELECT count()
FROM big, small
WHERE small.sid = (big.bid + 1) % 5000
SETTINGS make_distributed_plan = 1, explain_query_plan_default = 'legacy';
```

#### Fragments de requête en JSON {#explain-plan-fragments-json}

Avec `fragments` = 1 et `json` = 1, une requête exécutée par des workers sans état est décrite sous la forme d&#39;un unique document JSON comportant les clés suivantes :

* `resultFragment` — l&#39;id du fragment de requête qui produit l&#39;ensemble de résultats.
* `fragments` — les fragments de requête par id croissant, chacun avec `id`, `stage` (le nom de l&#39;étape), `tasks` (le nombre de tâches), `root` (le `nodeId` de l&#39;étape racine du fragment, c&#39;est-à-dire le premier élément de `steps`) et `steps`.
* `exchanges` — les échanges par id croissant, chacun avec `id`, `name`, `from` et `to` (les ids du fragment qui envoie les données et du fragment qui les lit), `kind` (`hash`, `broadcast`, `gather` ou `any`), `keys` pour `hash`, `sortDescription` pour un `gather` qui conserve l&#39;ordre de tri, `mode` (`streaming` ou `persisted`), `sourceBuckets`, `destinationBuckets` et, avec `estimates` = 1 lorsque le planificateur dispose d&#39;une estimation, `estimatedRows`.
* `levels` — les ids des fragments regroupés par profondeur, sous forme de tableaux, des fragments sans dépendances jusqu&#39;au fragment qui produit l&#39;ensemble de résultats.

`steps` est un tableau plat des étapes du fragment, la racine en premier, chaque parent précédant ses entrées. Une étape possède les mêmes clés qu&#39;avec `json` = 1 sans `fragments`, en camelCase (voir ci-dessous), mais à la place de `plans`, elle possède `children` : le `nodeId` de ses entrées dans l&#39;ordre des entrées, par exemple le côté gauche et le côté droit d&#39;une jointure, puis celui des étapes racines de ses plans imbriqués, dont les étapes figurent dans le même tableau. `nodeId` est unique au sein de la requête.

Les étapes d&#39;envoi et de réception d&#39;un échange possèdent la clé `exchangeId`, qui contient l&#39;id de l&#39;échange. L&#39;étape d&#39;envoi de l&#39;ensemble de résultats (`final_result`) transmet celui-ci au client, et non à un échange ; elle ne possède donc pas de `exchangeId`. Les noms de colonnes ne sont pas raccourcis, quelle que soit la valeur de `pretty`.

Toutes les clés du document sont écrites en camelCase, y compris celles des étapes, comme les clés de `actions` = 1 ou `indexes` = 1 : une clé est découpée en mots à chaque caractère qui n&#39;est ni une lettre ni un chiffre, le premier mot est mis en minuscules, les mots suivants commencent par une majuscule, et un mot entièrement en majuscules est d&#39;abord mis en minuscules. Par exemple, `Node Type` avec `json` = 1 devient `nodeType`, et `HAVING Pre-filter` devient `havingPreFilter`. Les valeurs restent inchangées.

Lorsque la requête n&#39;est pas distribuée, le document est identique à celui obtenu sans `fragments`, avec le `plan` imbriqué, à ceci près que les clés sont en camelCase. Si la requête n&#39;a pas pu être distribuée et s&#39;est repliée sur une exécution locale, le document comporte la clé `fallbackReason` après `plan`.

Exemple (abrégé) :

```sql
EXPLAIN fragments = 1, json = 1, description = 0
SELECT bid % 10 AS k, sum(bid)
FROM big
GROUP BY k
SETTINGS make_distributed_plan = 1
FORMAT TSVRaw;
```

#### Arbre des fragments de requête {#explain-plan-fragments-tree}

Avec `tree` = 1, une requête exécutée par des workers sans état est dessinée telle qu&#39;elle est découpée pour l&#39;exécution. Chaque étape du plan est représentée par une boîte, reliée aux boîtes de ses entrées comme dans l&#39;arbre du plan : les données remontent donc dans le dessin, en aval des lectures vers l&#39;ensemble de résultats. Les étapes d&#39;un fragment de requête sont entourées d&#39;un cadre intitulé `F<id> · <stage name>`, et chaque fragment est dessiné sous le fragment qui le lit. Un échange est une arête qui part de l&#39;étape d&#39;envoi du producteur et remonte jusqu&#39;à l&#39;étape de réception du consommateur, en traversant les deux cadres (`┼`), accompagnée d&#39;une étiquette : le nom de l&#39;échange et le mode de distribution des données, puis le mode et le nombre de compartiments source et destination. L&#39;arête est `│` pour un échange `streaming` et `╎` pour un échange `persisted`, dont le consommateur ne démarre qu&#39;une fois le producteur terminé ; la deuxième ligne de l&#39;étiquette d&#39;un échange persisté commence en outre par `⛁`.

Une boîte affiche le nom de l&#39;étape et, avec `description` = 1, sa description, dans laquelle `pretty` = 1 supprime le préfixe de table des noms de colonnes, comme dans les étiquettes. Sous un séparateur, la boîte affiche les lignes que `EXPLAIN` imprime sous l&#39;étape avec les mêmes options (`header`, `actions`, `indexes`, `projections`, `sorting`), par exemple les clés d&#39;une agrégation ou le nombre de parts et de granules sélectionnés par une lecture. Les plans imbriqués d&#39;une étape, tels que les plans par table de `ReadFromMerge` ou les plans d&#39;un `FINAL` paresseux, sont numérotés `N1`, `N2`, etc., et la boîte de l&#39;étape se termine par leurs identifiants, comme dans `ReadFromMerge ← N1, N2`. Après le dessin principal, chaque plan imbriqué est dessiné de la même manière, sans cadre, sous la ligne `N<id> · nested plan of <step>` ; les plans imbriqués de ses étapes reçoivent les identifiants suivants et sont dessinés après lui. Les étapes `Expression` ne sont pas dessinées, quelle que soit la valeur de `compact` : la boîte de leur entrée prend leur place. Avec `estimates` = 1, l&#39;étiquette d&#39;un échange affiche également le nombre estimé de lignes envoyées par le producteur (`~<N> rows`). Le texte d&#39;une étape est renvoyé à la ligne toutes les 40 colonnes, sur une espace si possible, afin qu&#39;une boîte l&#39;affiche intégralement, la description étant limitée par `query_plan_max_step_description_length` comme dans `EXPLAIN` sans `tree` ; les lignes de détail sont tronquées à 60 colonnes et la première ligne d&#39;une étiquette d&#39;échange à 48, avec `…`, et la section `Exchanges` qui suit le dessin reprend l&#39;étiquette complète. Le dessin ne dépend pas de la largeur du terminal. Lorsque la requête n&#39;est pas distribuée, ses étapes sont dessinées de la même manière, sans cadre et sans les sections `Exchanges` et `Levels`, puis suivies de `Not distributed: <reason>` si la requête s&#39;est rabattue sur une exécution locale. L&#39;option `tree` de `EXPLAIN PLAN` n&#39;a aucun rapport avec l&#39;instruction `EXPLAIN QUERY TREE`.

Exemple :

```sql
EXPLAIN tree = 1
SELECT small.sid, count()
FROM big, small
WHERE small.sid = (big.bid + 1) % 5000
GROUP BY small.sid
SETTINGS make_distributed_plan = 1, distributed_plan_max_rows_to_broadcast = 0;
```

### EXPLAIN PIPELINE {#explain-pipeline}

Paramètres :

* `header` — Affiche l’en-tête de chaque port de sortie. Valeur par défaut : 0.
* `graph` — Affiche un graphe décrit dans le langage de description de graphes [DOT](https://en.wikipedia.org/wiki/DOT_\(graph_description_language\)). Valeur par défaut : 0.
* `compact` — Affiche le graphe en mode compact si le paramètre `graph` est activé. Valeur par défaut : 1.
* `compact_repeated_processor_chains` — Regroupe les chaînes de processeurs répétées et adjacentes dans la sortie texte en n’affichant qu’une seule occurrence de la chaîne avec un nombre de répétitions. Cela peut faciliter la lecture des pipelines parallèles lorsque la même chaîne apparaît de nombreuses fois, par exemple dans des jointures. Cela n’affecte pas la sortie du graphe. Valeur par défaut : 0.

### EXPLAIN ANALYZE {#explain-analyze}

`EXPLAIN ANALYZE` exécute effectivement la requête, ignore les lignes de résultat et affiche la même arborescence du plan que `EXPLAIN PLAN`, avec pour chaque étape des annotations indiquant ce qui s’est réellement produit à l’exécution.

Paramètres :

`EXPLAIN ANALYZE` accepte les mêmes options d’affichage que `EXPLAIN PLAN` (documentées dans la section [EXPLAIN PLAN](#explain-plan)).

* `header` — voir la section [EXPLAIN PLAN](#explain-plan).
* `description` — voir la section [EXPLAIN PLAN](#explain-plan).
* `projections` — voir la section [EXPLAIN PLAN](#explain-plan).
* `sorting` — voir la section [EXPLAIN PLAN](#explain-plan).
* `input_headers` — voir la section [EXPLAIN PLAN](#explain-plan).
* `column_structure` — voir la section [EXPLAIN PLAN](#explain-plan).
* `actions` — voir la section [EXPLAIN PLAN](#explain-plan). Par défaut : 1.
* `indexes` — voir la section [EXPLAIN PLAN](#explain-plan). Par défaut : 1.
* `compact` — voir la section [EXPLAIN PLAN](#explain-plan). Par défaut : 1.
* `pretty` — voir la section [EXPLAIN PLAN](#explain-plan). Par défaut : 1.
* `processors` — Pour `EXPLAIN ANALYZE`, affiche une ligne supplémentaire par étape avec la répartition du temps écoulé par processeur : `min`, `median`, `max` et `sum`. Utile pour repérer un déséquilibre de charge entre les processeurs parallèles. Par défaut : 0.
* `matches` — Pour `EXPLAIN ANALYZE`, permet aux étapes de jointure d’effectuer le suivi supplémentaire nécessaire aux métriques `matched`, `match rate` et `fanout` lorsque ces valeurs ne peuvent pas être déduites de ce que produit la jointure. Lorsqu’elles le peuvent, elles sont signalées sans cette option. Voir [Étapes de jointure](#explain-analyze-join-steps). Par défaut : 0.
* `time` — Pour `EXPLAIN ANALYZE`, affiche des lignes `Time` et `Concurrency` pour chaque étape, indiquant le temps d’horloge et le niveau de concurrence de l’étape et de sa branche. Voir [Temps d’horloge et niveaux de concurrence des étapes et des branches](#explain-analyze-concurrency). Par défaut : 1.

<Note>
  Comme `EXPLAIN ANALYZE` exécute réellement la requête encapsulée, il se comporte comme cette
  requête — et contrairement aux formes `EXPLAIN` qui n’exécutent rien — à plusieurs égards :

  * **Quotas et limites.** Il est comptabilisé dans les mêmes [quotas](/fr/concepts/features/configuration/server-config/quotas)
    et soumis aux mêmes [limites](/fr/concepts/features/configuration/settings/query-complexity)
    (par ex. `query_selects`, `read_rows`) que si la requête était exécutée directement. Les sources exemptées de quotas pendant la planification
    (comme `system.one`) ne sont pas comptabilisées.
  * **Transactions en échec.** À l’intérieur d’une [transaction](/fr/concepts/features/operations/insert/transactions)
    ayant déjà échoué (`ROLLED_BACK`), il est rejeté avec `INVALID_TRANSACTION`,
    tout comme un simple `SELECT` — exécutez d’abord `ROLLBACK`.
  * **Lectures en streaming.** Sur une lecture en streaming (`FROM ... STREAM`), il est rejeté avec
    `NOT_IMPLEMENTED`, car une telle lecture ne se termine jamais.
  * **Requêtes distribuées.** Il n’est pas pris en charge pour les requêtes exécutées en
    mode [distributed](/fr/reference/engines/table-engines/special/distributed).
</Note>

Examinons la sortie. Commençons par l’en-tête.

```txt
   Query summary:
     Time:        <total> (planning <planning> · execution <execution>)
     Execution:   in steps <t> (<share>%) · outside steps <t> (<share>%) · idle <t> (<share>%)
     Read:        <rows> rows, <bytes> (<rows/s>, <bytes/s>)
     Peak memory: <peak>
```

* `Time` — temps total, réparti entre les phases de planification (c.-à-d. création du plan + optimisation du plan + construction du pipeline) et d’exécution (exécution du pipeline).
* `Execution` — non affiché lorsque `time = 0`. Découpe le temps d’exécution en `in steps`, `outside steps` et `idle`. La somme de ces composantes correspond à `execution`. Voir [Temps d’horloge et niveaux de concurrence des étapes et des branches](#explain-analyze-concurrency).
* `Read` — lignes et octets non compressés lus dans les tables, avec leur débit — les mêmes valeurs que celles indiquées dans le pied de page d’une requête classique sous la forme &quot;Processed&quot;.
* `Peak memory` — mémoire maximale utilisée par la requête.

Examinons maintenant les nouvelles lignes qui apparaissent dans le plan de requête.

```txt
I/O: rows <in> → <out> (<selectivity>%) · <bytes_in> → <bytes_out>
  [Stage (<stage>): ]time <t> (<share>%) · parallelism <avg>/<max>
```

Le nombre de lignes et d’octets est indiqué une seule fois pour l’ensemble de l’étape (la ligne `I/O`). Le temps et le parallélisme sont indiqués pour chaque étape de l’étape sur la ou les lignes en retrait qui suivent.

* `rows <in> → <out>` — lignes entrées dans l’étape et qui en sont sorties ; (`<selectivity>`%) indique dans quelle mesure l’étape a filtré (`out/in`) ou étendu les données. Cette information est masquée lorsque le nombre de lignes en entrée est égal au nombre de lignes en sortie, ainsi que lorsque le nombre de lignes en entrée est égal à `0`.
* `<bytes_in> → <bytes_out>` — octets en mémoire non compressés traversant l’étape (omis lorsque les deux valeurs sont nulles).
* `time <t> (<share>%)` — temps d’horloge pendant lequel l’étape a été active, ainsi que sa part du temps d’exécution de la requête (c.-à-d. hors temps de build). Notez que les parts peuvent totaliser plus de 100 % car les étapes et les étapes s’exécutent en parallèle.
* `parallelism <avg>/<max>` — nombre moyen de threads CPU travaillant simultanément dans cette étape, par rapport au maximum qu’elle pouvait utiliser. Cette métrique est propre à l’étape : les threads travaillant au même moment sur d’autres étapes de la requête ne sont pas comptabilisés. Une valeur proche du maximum signifie que l’étape a été bien parallélisée ; une valeur proche de 1 signifie qu’elle s’est exécutée principalement en série.
* `Stage (<stage>)` — le nom de l’étape. Une étape avec une seule étape affiche directement la ligne de temps, sans libellé `Stage (...)`. Les étapes comportant plusieurs étapes affichent une ligne libellée par étape ; par exemple, `Aggregating` affiche `Stage (partial aggregation)` et `Stage (final aggregation)`, et un hash join affiche `Stage (build)` et `Stage (probe)`.

<Note>
  ClickHouse parallélise non seulement l’exécution des tâches au sein d’une étape du plan, mais aussi l’exécution des étapes du plan. La métrique `parallelism` ne reflète que le travail de cette étape. D’autres étapes peuvent s’exécuter en parallèle ; ce nombre n’indique donc pas comment le parallélisme de l’étape se compare à celui de l’ensemble de la requête. Pour une vue à l’échelle de la requête, consultez la métrique `Concurrency` affichée avec `time = 1` ([Temps d’horloge et niveaux de concurrence des étapes et des branches](#explain-analyze-concurrency)).
</Note>

<Note>
  Le nombre maximal dans `parallelism` est calculé comme le minimum entre :

  1. le nombre total de tâches dans l’étape du plan ;
  2. le nombre maximal de threads de traitement des requêtes défini dans `max_threads`.
</Note>

#### Déversement sur le disque dans les étapes d&#39;agrégation, de tri et de dédoublonnage {#explain-analyze-spilling}

Lorsqu&#39;une étape `GROUP BY`, `ORDER BY` ou `DISTINCT` déverse des données dans un stockage temporaire, elle indique :

```txt
Spill: spilled <compressed_bytes>
```

Il s&#39;agit du nombre cumulé d&#39;octets compressés écrits par l&#39;ensemble de l&#39;étape, y compris ses processeurs parallèles.
Ce total inclut les fichiers temporaires déjà consommés ou supprimés, et comptabilise chaque écriture lorsque des données sont déversées sur disque à plusieurs reprises.
Cette ligne est omise si aucune donnée n&#39;a été déversée sur disque.

#### Étapes de jointure {#explain-analyze-join-steps}

Pour une étape de jointure, `EXPLAIN ANALYZE` affiche des lignes comparant les estimations de l’optimiseur d’ordre de jointure avec ce qui s’est réellement produit (voir [Métriques de jointure estimées et réelles](#explain-analyze-join-estimation)), ainsi que, pour chaque côté, des lignes de *participation* — `Left` et `Right` — suivies des éventuelles lignes propres à l’implémentation de la jointure. `Left` et `Right` correspondent aux côtés logiques de la requête SQL. Dans la plupart des cas, `Left` correspond également au côté sonde (probe) de la jointure, et `Right` au côté de construction (build). Ce n’est toutefois pas toujours le cas, en raison de l’inversion (swap) qui peut se produire lors de l’exécution de la jointure. Toutes les valeurs de [`join_algorithm`](/fr/reference/settings/session-settings/join#join_algorithm) sont prises en charge (`hash`, `parallel_hash`, `grace_hash`, `partial_merge`, `full_sorting_merge`, `parallel_full_sorting_merge`, `direct`), de même que les trois implémentations que ce paramètre ne peut pas sélectionner : les jointures `CROSS` ou `COMMA`, la [jointure par boucles imbriquées par blocs](/fr/reference/statements/select/join#join-with-an-arbitrary-on-condition) utilisée pour une section `ON` ne déterminant aucune clé de jointure, et le moteur de table [`Join`](/fr/reference/engines/table-engines/special/join). La plupart indiquent les deux côtés ; certaines n’indiquent que le côté qu’elles matérialisent (par exemple, `direct` affiche uniquement `Left:`).

Les lignes associées à chaque côté ont la même structure :

```txt
Left:  rows estimated <estimated_left_rows>  · rows <left_rows>  · q-error <ratio> · matched <matched_left_rows>  · match rate <match_rate>% · fanout <fanout>
Right: rows estimated <estimated_right_rows> · rows <right_rows> · q-error <ratio> · matched <matched_right_rows> · match rate <match_rate>% · fanout <fanout>
```

Pour chaque côté, `EXPLAIN ANALYZE` indique :

* `rows estimated <estimated_rows>` — l’estimation, par l’optimiseur d’ordre de jointure, du nombre de lignes de ce côté, affichée à titre de comparaison avec la valeur réelle `rows` placée à côté ; `no stats` lorsque l’optimiseur de requêtes n’a produit aucune estimation (voir [Métriques de jointure estimées et réelles](#explain-analyze-join-estimation)).
* `rows <rows>` — le nombre total de lignes de ce côté qui ont été traitées par la jointure.
* `q-error <ratio>` : `max(<estimated_rows> / <rows>, <rows> / <estimated_rows>)` pour ce côté, comme pour `Output rows` ; affiché lorsque les deux valeurs sont non nulles. Pour un côté correspondant à une lecture de table filtrée, il s’agit de la q-error de l’estimation du filter. Les filters JOIN à l’exécution suppriment des lignes du côté auquel ils s’appliquent, ce dont aucune estimation ne tient compte ; définissez `enable_join_runtime_filters = 0` pour comparer l’estimation seule. De même, une jointure par hachage partitionnée par plages de clé primaire (`query_plan_join_shard_by_pk_ranges`) ne lit pas les lignes du côté sonde (probe) d’une plage dont le côté de construction (build) est vide, lorsque ces lignes ne peuvent pas figurer dans l’ensemble de résultats ; définissez `query_plan_join_shard_by_pk_ranges = 0` pour comparer l’estimation seule.
* `matched <matched_rows>` — le nombre de lignes de ce côté qui ont trouvé au moins une ligne correspondante de l’autre côté. Il s’agit bien de *lignes*, et non de clés : si une clé apparaît trois fois à droite et établit une correspondance, les trois lignes de droite sont comptées comme correspondantes.
* `match rate <match_rate>%` — le pourcentage de lignes de ce côté ayant établi une correspondance, calculé comme suit : `100 * <matched_rows> / <rows>`.
* `fanout <fanout>` — le nombre de lignes de sortie produites en moyenne par une ligne correspondante de ce côté.

Toute valeur qui ne peut pas être calculée exactement est indiquée par `not collected` plutôt que par `0`. `match rate` et `fanout` sont calculés à partir de `matched` ; par conséquent, pour un côté dépourvu de cette valeur, ces trois valeurs sont indiquées comme `not collected`.

#### Métriques de jointure estimées et réelles {#explain-analyze-join-estimation}

Une étape de jointure contient les estimations de l&#39;optimiseur d’ordre de jointure — les mêmes que celles affichées par `EXPLAIN PLAN` (voir la section [EXPLAIN PLAN](#explain-plan)) — et `EXPLAIN ANALYZE` affiche chacune d&#39;elles à côté de la valeur mesurée :

```txt
Cost: estimated <cost> · actual <cost>
Selectivity: estimated (NDV) <selectivity> · actual (cartesian) <selectivity>
Output rows: estimated <rows> · actual <rows> · q-error <ratio>
```

* `Cost` — les deux valeurs comptabilisent les lignes de sortie correspondantes. L’estimation est le coût, selon l’optimiseur, du sous-arbre de jointure : `<selectivity> * <left_rows> * <right_rows>`, auquel s’ajoute le coût de ses entrées. La valeur réelle est mesurée de la même manière : les lignes de sortie correspondantes de cette jointure, plus le coût réel de chaque jointure située en dessous et appartenant au même cluster de réordonnancement.
* `Selectivity` — l’estimation est calculée à partir du nombre de valeurs distinctes des clés de jointure ; la valeur réelle est la fraction mesurée du produit cartésien qui se retrouve dans la sortie : `<matched output rows> / (<left rows> * <right rows>)`, puisque c’est ce que l’optimiseur cherche à estimer.
* `Output rows` — le nombre estimé et réel de lignes produites par la jointure. Lorsque les deux valeurs sont non nulles, `q-error` indique `max(estimated / actual, actual / estimated)`, la mesure standard de la qualité de l’estimation de cardinalité : `1.00` correspond à une estimation parfaite, tandis qu’une valeur élevée signifie que l’optimiseur a choisi l’ordre des jointures sur la base d’une estimation de cardinalité très erronée.

Une estimation qui n’a jamais été calculée est signalée par `no stats` — par exemple, lorsque l’optimisation de l’ordre des jointures n’a pas été exécutée parce que [`query_plan_optimize_join_order_limit`](/fr/reference/settings/session-settings/query-plan#query_plan_optimize_join_order_limit) vaut `0`. Cela se distingue de `not collected`, qui indique une valeur réelle que l’exécution n’a pas pu mesurer. Les jointures dont le côté droit est prérempli (le moteur de table [`Join`](/fr/reference/engines/table-engines/special/join), les jointures `direct`) ne passent pas par l’optimiseur d’ordre des jointures et n’affichent que les lignes de participation.

L’étape de jointure affiche également les lignes `Input (left):` et `Input (right):`, avec les colonnes fournies par chaque côté à la jointure.

Pour les tables de l’exemple de jointure [EXPLAIN PLAN](#explain-plan), l’étape de jointure de `EXPLAIN ANALYZE SELECT * FROM t1 INNER JOIN t2 ON t1.id = t2.id` se présente comme suit :

```text
Join (JOIN FillRightFirst)
│  t1[100] ⋈ t2[100]
│  Type: inner | Strictness: all | Algorithm: SpillingHashJoin(HashJoin)
│  Join conditions: id = id
│  Cost: estimated 100.00 · actual 100.00
│  Selectivity: estimated (NDV) 0.01 · actual (cartesian) 0.01
│  Output rows: estimated 100.00 · actual 100.00 · q-error 1.00
│  Left: rows estimated 100.00 · rows 100.00 · q-error 1.00 · matched 100.00 · match rate 100.00% · fanout 1.00
│  Right: rows estimated 100.00 · rows 100.00 · q-error 1.00 · matched not collected · match rate not collected · fanout not collected
│  Hash table: unique keys 100.00 · memory 6.27 KB
│  Input (left): id, value
│  Input (right): id, value
│  I/O: rows 200 → 100 (50.00%) · 3.58 KB → 3.58 KB
│    Stage (build): time 127.45 us (1.2%) · parallelism 0.99/1
│    Stage (probe): time 124.99 us (1.2%) · parallelism 0.99/1
```

#### Fanout {#explain-analyze-fanout}

`fanout` mesure la multiplication des lignes :

```txt
matched output rows = <output_rows> - <NULL-padded rows of both sides>
fanout              = <matched output rows> / <matched_rows of that side>
```

Une jointure externe produit une ligne de sortie complétée par des `NULL` pour chaque ligne d’un côté préservé qui n’a trouvé aucune correspondance. Ces lignes sont soustraites afin de ne pas diluer le ratio. Seul un côté préservé en comporte : le côté droit pour `RIGHT` et `FULL`, le côté gauche pour `LEFT` et `FULL` :

* `fanout = 0` — les lignes correspondantes n’ont produit aucune ligne de sortie, comme dans une jointure `ANTI` : elle ne produit que les lignes qui n’ont trouvé aucune correspondance.
* `fanout = 1` — une jointure 1:1 sans duplication ; chaque ligne correspondante a produit exactement une ligne de sortie.
* `fanout > 1` — une jointure 1:N ; des clés dupliquées de l’autre côté ont multiplié les lignes. Une valeur élevée des deux côtés simultanément indique une explosion cartésienne involontaire.

#### Cas où les nombres nécessitent `matches = 1` {#explain-analyze-matches}

La plupart de ces nombres résultent des données que la jointure produit déjà et sont rapportés par un simple `EXPLAIN ANALYZE`. Les autres nécessitent un suivi que la jointure n’effectuerait pas autrement et ne sont donc rapportés qu’avec `EXPLAIN ANALYZE matches = 1`. Les cas concernés dépendent de l’algorithme ; dans la famille hash, il y en a deux :

* le côté **droit** de `ALL INNER` et `ALL LEFT`, qui nécessite de marquer chaque ligne droite correspondante ;
* le côté **gauche** de `ALL LEFT` et `ALL FULL`, mais uniquement lorsque la requête ne sélectionne aucune donnée de la
  table de droite et que la section `ON` est une simple égalité de clé. Sinon, la sonde enregistre déjà
  les lignes de gauche qui correspondent — soit pour matérialiser les colonnes de droite, soit pour évaluer la condition
  résiduelle — et le décompte est exact sans cette option.

`partial_merge` en a besoin pour le côté **droit** des quatre types `ALL`, pour la même raison.
`full_sorting_merge` et `parallel_full_sorting_merge` en ont besoin pour les **deux** côtés des types `ANY`. Les
types `ALL` n’en ont pas besoin.

<Note>
  L’option est désactivée par défaut, car ce suivi supplémentaire a un coût : il réduit la fidélité des mesures. Le travail est effectué dans la boucle de sonde et augmente avec le nombre de lignes de sortie. Utilisez `matches = 1` lorsque vous devez connaître les correspondances exactes que les lignes de gauche et de droite ont trouvées de l’autre côté.
</Note>

`matches = 1` ne permet pas de collecter toutes les combinaisons. Le côté qu’une jointure peut rapporter découle
de ce que cette jointure doit déjà faire ; cela dépend donc de l’algorithme, ainsi que du type et de la
strictness.

**Famille hash.** `hash`, `parallel_hash` et `grace_hash` donnent toujours les mêmes résultats :

| Jointure                                         | `matched` à gauche | `matched` à droite |
| ------------------------------------------------ | ------------------ | ------------------ |
| `ALL INNER`, `ALL LEFT`, `ALL RIGHT`, `ALL FULL` | oui                | oui                |
| `SEMI LEFT`, `ANTI LEFT`                         | oui                | non                |
| `ANY RIGHT`, `ANTI RIGHT`                        | non                | oui                |
| `ASOF` (inner)                                   | oui                | non                |
| `SEMI RIGHT`                                     | non                | non                |
| `ANY INNER`, `ANY LEFT`, `ASOF LEFT`             | non                | non                |

Le côté droit n’est pas disponible lorsque la jointure ne conserve qu’une ligne par clé dans sa table de hachage, comme le font les jointures `ANY`, `SEMI` et `ANTI` : les lignes de droite dupliquées ne sont jamais stockées et ne peuvent donc pas être comptées. Le côté gauche n’est pas disponible lorsque la jointure supprime la sortie d’une ligne de gauche dont le partenaire a déjà été revendiqué par une autre ligne de gauche, de sorte que les lignes émises sous-estiment les lignes correspondantes.

L’activation de [`any_join_distinct_right_table_keys`](/fr/reference/settings/session-settings/other#any_join_distinct_right_table_keys) fait passer `ANY` à l’ancienne sémantique `RightAny`, qui émet une ligne par ligne de gauche et conserve donc les deux décomptes. `ANY RIGHT` et `ANY FULL` rapportent alors les **deux** côtés, et `ANY INNER` est réécrit en `SEMI LEFT`.

Le moteur de table [`Join`](/fr/reference/engines/table-engines/special/join) suit le même tableau, en utilisant le type et la strictness déclarés dans le moteur : `Join(ALL, INNER, …)` rapporte les deux côtés, `Join(ANY, LEFT, …)` aucun des deux.

**Algorithmes de fusion.** `full_sorting_merge` et `parallel_full_sorting_merge` acceptent les quatre types `ALL`, `ANY INNER`, `ANY LEFT`, `ANY RIGHT`, `ASOF` et `ASOF LEFT`. Ils rapportent les **deux** côtés pour tous les types, sauf `ASOF` et `ASOF LEFT`, pour lesquels le côté droit est `not collected`, et ce sans `matches = 1` — ils parcourent les deux entrées triées et voient chaque ligne d’une plage d’égalité au fur et à mesure qu’ils la consomment ; rien n’a donc besoin d’être reconstruit par la suite.

`partial_merge` accepte `ALL INNER`, `ALL LEFT`, `ALL RIGHT`, `ALL FULL`, `ANY INNER`, `ANY LEFT` et `SEMI LEFT`. Il rapporte les deux côtés pour les quatre types `ALL`, le côté droit avec `matches = 1` ; pour `ANY INNER`, `ANY LEFT` et `SEMI LEFT`, le côté droit est `not collected`.

**`direct`.** Le côté gauche uniquement. Le côté droit est un magasin clé-valeur qui n’est jamais matérialisé sous forme de lignes ; il n’a donc pas de ligne `Right:`.

**`CROSS`, `COMMA` et un `ON` constant.** Aucun côté, comme décrit [ci-dessus](#explain-analyze-join-algorithm-lines).

**Jointure par boucles imbriquées par blocs (block nested loop join).** Il s&#39;agit de l&#39;opérateur qui prend en charge une section `ON` ne déterminant aucune clé de jointure, à moins que l&#39;un des chemins qui le précèdent ne revendique la condition (voir [`allow_block_nested_loop_join`](/fr/reference/settings/session-settings/allow)). Il accepte tous les types et toutes les strictness, à l&#39;exception de `ASOF`, `PASTE` et `ANY FULL` :

| Jointure                                                      | `matched` gauche   | `matched` droite |
| ------------------------------------------------------------- | ------------------ | ---------------- |
| `ALL FULL`                                                    | oui                | oui              |
| `ALL LEFT`, `ANY LEFT`, `SEMI LEFT`, `ANTI LEFT`, `ANY INNER` | oui                | non              |
| `ALL RIGHT`, `ANY RIGHT`, `SEMI RIGHT`, `ANTI RIGHT`          | avec `matches = 1` | oui              |
| `ALL INNER`                                                   | avec `matches = 1` | non              |

Le côté gauche est rapporté sans l&#39;option partout où l&#39;opérateur enregistre déjà quelles lignes de gauche ont trouvé une correspondance : tout type qui conserve les lignes de gauche sans correspondance a besoin de cet enregistrement, tout comme toute strictness qui retient au plus une paire par ligne de gauche. Le côté droit est rapporté partout où l&#39;opérateur conserve ses indicateurs de correspondance, ce qui est nécessaire pour `RIGHT`, `FULL` et pour un `SEMI`/`ANTI` piloté par la droite. `ANY INNER` les conserve aussi, mais uniquement pour attribuer une ligne de droite à une seule ligne de gauche : il cesse de revendiquer pour une ligne de gauche qui a déjà sa paire. Les indicateurs marquent donc les paires du résultat plutôt que chaque correspondance, et ne sont pas rapportés. `ALL INNER` n&#39;atteint l&#39;opérateur que lorsque `hash` est désactivé ; sinon, la condition devient un `CROSS JOIN` assorti d&#39;un filter.

L&#39;activation de [`any_join_distinct_right_table_keys`](/fr/reference/settings/session-settings/other#any_join_distinct_right_table_keys) fait ici aussi basculer `ANY` vers la sémantique `RightAny`, qui rapporte le côté gauche pour tous les types et le côté droit pour `RIGHT` et `FULL` ; `ANY INNER` est réécrit en `SEMI LEFT`.

Lorsque deux algorithmes rapportent chacun un nombre, ces nombres concordent. Les algorithmes de fusion disposent simplement de davantage d&#39;informations ; ils ne divergent pas sur la définition d&#39;une correspondance.

#### Lignes spécifiques à l’algorithme {#explain-analyze-join-algorithm-lines}

Examinons les lignes supplémentaires ajoutées par chaque implémentation de jointure.

Pour les jointures `hash` et `parallel_hash`, ainsi que pour le moteur de table `Join`, une ligne `Hash table:` décrit la table de hachage construite à partir de la table de droite :

```txt
Hash table: unique keys <unique_keys> · memory <peak_memory>
```

* `unique keys <unique_keys>` — le nombre de clés uniques stockées dans la table de hachage pendant la phase de construction.
* `memory <peak_memory>` — le pic de mémoire utilisé par la table de hachage pendant la phase de construction.

Pour la jointure `grace_hash`, la ligne `Hash table:` indique également comment la jointure s&#39;est adaptée à la limite de mémoire, et une ligne `Spill:` indique si des données ont été déversées sur le disque :

```txt
Hash table: unique keys <unique_keys> · memory <peak_memory> · buckets <buckets> · rehashes <rehashes>
Spill: yes · left spilled <left_spilled_bytes> · right spilled <right_spilled_bytes>
```

* `buckets <buckets>` — le nombre de buckets auquel la jointure grace hash join est parvenue à la fin de l’exécution. Il s’agit toujours d’une puissance de `2`.
* `rehashes <rehashes>` — le nombre de fois où le nombre de buckets a dû être doublé pour respecter la limite de mémoire.
* `Spill:` — un indicateur `yes`/`no` précisant si des données ont été écrites sur le disque. Lorsque c’est le cas, `left spilled <left_spilled_bytes>` et `right spilled <right_spilled_bytes>` indiquent le nombre d’octets compressés écrits sur le disque depuis les côtés gauche (sonde) et droit (construction) ; si aucune donnée n’a été écrite sur le disque, la ligne est simplement `Spill: no`.

Pour la jointure `partial_merge`, la ligne `Right:` contient des informations supplémentaires sur la mise en mémoire tampon et le tri de la table de droite, et le temps de tri s’affiche sur les lignes `Stage (build)` et `Stage (probe)` :

```txt
Right: rows estimated <estimated_right_rows> · rows <right_rows> · q-error <ratio> · matched <matched_right_rows> · size <right_size> · blocks <right_blocks> · storage <in-memory|external> · match rate <match_rate>% · fanout <fanout>
  Stage (build): time <t> (<share>%) · parallelism <avg>/<max> · sort time <build_sort_time> · sort share <build_sort_share>%
  Stage (probe): time <t> (<share>%) · parallelism <avg>/<max> · sort time <probe_sort_time> · sort share <probe_sort_share>%
```

* `size <right_size>` — la taille en mémoire des blocs de la table de droite.
* `blocks <right_blocks>` — le nombre de blocs dans lesquels la table de droite a été mise en mémoire tampon.
* `storage <in-memory|external>` — indique si la table de droite tenait en mémoire (`in-memory`) ou devait être déversée sur le disque (`external`). Lorsqu’il est `external`, un champ supplémentaire `spilled <spilled_bytes>` indique le nombre d’octets compressés écrits sur le disque.
* `sort time <sort_time>` — le temps consacré au tri de la table de droite (lors de l’étape de construction) et de chaque bloc gauche entrant (lors de l’étape de sonde).
* `sort share <sort_share>%` — `sort time` en proportion du *temps d’activité de cette étape* (la somme du temps écoulé de ses processeurs), contrairement au pourcentage de `time` de l’étape, qui représente une part du *temps d’exécution de l’ensemble de la requête*.

Pour la jointure `full_sorting_merge`, seules les lignes communes `Left:` et `Right:` sont affichées.

Pour la jointure `direct`, seule la ligne `Left:` est affichée, car le côté droit est un magasin clé-valeur consulté directement plutôt que matérialisé en lignes.

Pour une jointure `CROSS` ou `COMMA`, ainsi que pour une jointure `ALL INNER JOIN` dont la section `ON` ne contient aucune égalité de clés (le planificateur la transforme alors en `CROSS JOIN`, avec cette condition comme filter), une ligne `Buffer:` décrit comment la table de droite a été conservée en mémoire et une ligne `Spill:` indique si elle a été écrite sur le disque :

```txt
Buffer: memory <peak_memory> · compressed <yes|no>
Spill: yes · right spilled <right_spilled_bytes>
```

* `memory <peak_memory>` — le pic de mémoire occupé par la table de droite mise en mémoire tampon.
* `compressed <yes|no>` — indique si au moins un bloc mis en mémoire tampon a été compressé ; les lecteurs décompressent alors chaque bloc stocké.
* `Spill:` — le même indicateur `yes`/`no` que pour `grace_hash`, `right spilled <right_spilled_bytes>` indiquant le nombre d’octets compressés écrits sur le disque.

Les deux côtés indiquent ici `matched not collected` : un prédicat constant associe soit chaque ligne de gauche à chaque ligne de droite, soit aucune ligne ; il n’est donc pas possible d’indiquer quelles lignes individuelles correspondent.

La jointure par boucles imbriquées par blocs, qui traite toutes les autres sections `ON` dépourvues d&#39;égalité de clés, affiche les deux mêmes lignes concernant la table de droite qu&#39;elle matérialise :

```txt
Buffer: memory <peak_memory> · compressed <yes|no>
Spill: yes · right spilled <right_spilled_bytes>
```

* `memory <peak_memory>` — le pic de mémoire occupé par la table de droite stockée. Cette valeur vaut `0` lorsque chaque bloc a été écrit sur disque dès son arrivée, puisqu&#39;aucun d&#39;entre eux n&#39;a jamais été conservé en mémoire.
* `compressed <yes|no>` — indique si au moins un bloc stocké a été compressé ; les lecteurs décompressent alors chacun des blocs stockés.
* `Spill:` — le même indicateur `yes`/`no` que pour `grace_hash`, `right spilled <right_spilled_bytes>` indiquant le nombre d&#39;octets compressés écrits sur disque.

Contrairement au cas `CROSS`, les deux côtés peuvent ici indiquer `matched`, puisque l&#39;opérateur évalue une véritable condition sur chaque paire qu&#39;il examine ; le tableau [ci-dessus](#explain-analyze-matches) précise lequel des deux le fait.

Pour une jointure utilisant le moteur de table [`Join`](/fr/reference/engines/table-engines/special/join), les deux côtés sont indiqués, ainsi que la ligne `Hash table:` qui décrit la table préconstruite. Le côté droit comptabilise les lignes stockées dans le moteur, et non celles créées pour chaque requête.

#### Temps par processeur {#explain-analyze-processors}

Avec `processors = 1`, une ligne supplémentaire est affichée sous chaque étape, montrant la répartition du temps écoulé entre les processeurs de l’étape :

```txt
Time per processor (<n>): min <t> · median <t> · max <t> · sum <t>
```

`<n>` correspond au nombre de processeurs dans l’étape. Un écart important entre `median` et `max` indique un déséquilibre de charge entre les processeurs parallèles.

#### Temps d’horloge et niveaux de concurrence des étapes et des branches {#explain-analyze-concurrency}

Sauf si `time = 0`, deux lignes supplémentaires sont affichées pour chaque étape du plan de requête :

```txt
Time: step <t> (<share>%) · branch <t> (<share>%)
Concurrency: step <n>/<m> · branch <n>/<m>
```

Ici, `step` désigne l’étape elle-même. `branch` désigne le sous-arbre dont cette étape est la racine : l’étape et toutes celles qui se trouvent en dessous dans le plan.

* `Time` — la durée pendant laquelle au moins un thread a travaillé sur l’étape (`step`) ou sur une étape de son sous-arbre (`branch`). `<share>` exprime cette durée en pourcentage du temps d’exécution de la requête.
* `Concurrency` — le nombre moyen de threads occupés à exécuter *n’importe quelle* étape de la requête, et pas seulement celle-ci, pendant que l’étape (`step`) ou son sous-arbre (`branch`) était actif. `<m>` est le nombre maximal de threads que la requête pouvait utiliser. Les étapes qui ne possèdent aucun processeur, par exemple `Union` lorsque ses entrées ont déjà le même en-tête, affichent `Unknown` pour `step` : il n’y a aucun travail à mesurer. La valeur de `branch` reste indiquée.

Ces deux métriques sont calculées à partir des intervalles de travail. Chaque fois qu’un thread termine une tâche, l’executor enregistre un intervalle : l’horodatage de début, l’horodatage de fin et l’étape à laquelle appartient ce travail.

La valeur `Time` d’une étape correspond à la durée de l’union de ses intervalles. Les périodes pendant lesquelles aucun thread ne travaille sur l’étape ne sont pas comptabilisées. Pour calculer la valeur `Time` d’une branche, on réunit d’abord les intervalles de toutes les étapes de son sous-arbre.

Le `branch` de l’étape racine couvre l’ensemble du plan, mais sa part est normalement inférieure à 100 %. La ligne `Execution` du récapitulatif de la requête indique à quoi correspond le reste du temps d’exécution (voir le récapitulatif de la requête dans l’exemple ci-dessus) :

* `in steps` — l’union des intervalles de toutes les étapes du plan. Il s’agit de la durée `branch` de l’étape racine, et la part indiquée est identique.
* `outside steps` — le temps pendant lequel au moins un thread exécutait un processeur, sans qu’aucun de ces processeurs n’appartienne à une étape de ce plan : le sink de sortie, `Resize`, les transformations de conversion et les étapes de plans non accessibles depuis celui-ci.
* `idle` — le temps pendant lequel aucun thread n’exécutait de processeur : le démarrage et l’arrêt de l’executor, ainsi que les moments où tous les threads étaient en attente.

Les parts de `Time`, les parts de `time` par étape et les parts de `Execution` utilisent le même dénominateur ; elles peuvent donc être comparées entre elles.

La valeur `Concurrency` correspond au temps d’activité cumulé de tous les threads de la requête pendant cette union, divisé par la durée de l’union. Elle compte les threads occupés à exécuter *n’importe quelle* étape de la requête, contrairement à la métrique `parallelism` par étape, qui ne compte que les threads de l’étape concernée. Elle répond à la question : &quot;pendant que cette étape (ou branche) était active, dans quelle mesure la requête dans son ensemble mobilisait-elle ses threads ?&quot; Une valeur proche de `<m>` signifie que la requête est restée entièrement parallélisée pendant que cette étape était active. Une valeur proche de `1` signifie que la requête s’exécutait de manière sérialisée pendant cette période : pour `step`, le seul thread occupé travaillait sur cette étape elle-même, ce qui en fait un point de sérialisation ; pour `branch`, le thread travaillait quelque part dans le sous-arbre, pas nécessairement sur cette étape. Une étape sérialisée ne constitue un véritable goulot d’étranglement que si sa part de `Time` est également significative.

### EXPLAIN ESTIMATE {#explain-estimate}

Affiche le nombre estimé de lignes, de marks et de parts à lire dans les tables lors du traitement de la requête. Fonctionne avec les tables de la famille [MergeTree](/fr/reference/engines/table-engines/mergetree-family/mergetree).

**Exemple**

Création d’une table :

```sql title="Query"
CREATE TABLE ttt (i Int64) ENGINE = MergeTree() ORDER BY i SETTINGS index_granularity = 16, write_final_mark = 0;
INSERT INTO ttt SELECT number FROM numbers(128);
OPTIMIZE TABLE ttt;
```

```sql title="Query"
EXPLAIN ESTIMATE SELECT * FROM ttt;
```

```text title="Response"
┌─database─┬─table─┬─parts─┬─rows─┬─marks─┐
│ default  │ ttt   │     1 │  128 │     8 │
└──────────┴───────┴───────┴──────┴───────┘
```

### EXPLAIN WHATIF {#explain-whatif}

Estime le bénéfice qu’un index de saut hypothétique apporterait à une requête `SELECT`, *sans* matérialiser l’index sur disque. Définissez un ou plusieurs candidats avec [`CREATE HYPOTHETICAL INDEX`](/fr/reference/statements/hypothetical-index#create-hypothetical-index), puis exécutez `EXPLAIN WHATIF SELECT ...` pour obtenir, pour chaque candidat : l’applicabilité, le nombre estimé de marques lues, le nombre estimé d’octets et le taux d’exclusion.

Sur les tables volumineuses, l’estimation de l’index lit un échantillon de fenêtres d’index (voir `index_scan_budget_rows`). Une fenêtre correspond aux `GRANULARITY` granules couverts par un granule d’index. L’estimation extrapole le nombre échantillonné à la valeur de référence, et `marks_span` indique la plage permise par l’erreur d’échantillonnage.

Les projections hypothétiques définies avec [`CREATE HYPOTHETICAL PROJECTION`](/fr/reference/statements/hypothetical-projection#create-hypothetical-projection) sont également des candidats. Pour une projection ordinaire, l’estimation construit son index primaire en mémoire sur les parts que la requête lirait. Elle élague l’index comme l’optimiseur de requêtes élague une projection matérialisée. Pour une projection d’agrégation, l’estimation agrège d’abord les lignes de chaque part en une ligne par groupe, comme dans une part de projection matérialisée. Elle n’estime une projection d’agrégation qu’à partir d’un parcours complet. Lorsqu’une part contient plus de groupes que la valeur `max_rows_to_group_by` de la requête, l’estimation est `unsupported`.

Le rapport indique les marques et les lignes que la projection lirait, un `read_ratio` par rapport à la lecture de la table de base, ainsi qu’un `verdict` indiquant si l’optimiseur de requêtes la choisirait. Avec `force_optimize_projection = 1` ou `prefer_optimize_projection = 1`, l’optimiseur de requêtes utilise toute projection exploitable ; une projection qu’il ne retiendrait pas sur la base du coût est donc signalée comme `chosen (forced)`.

Lorsque le résultat dépend de la disposition de la part de projection, `marks_span` indique la plage de valeurs, et une décision trop incertaine pour trancher est signalée comme `too close to call`. Sur les tables volumineuses, l’estimation lit un échantillon de granules (voir `projection_scan_budget_rows`).

WHATIF signale comme `not_applicable` les projections disposant de leurs propres index de saut, ainsi que les projections d’agrégation sans clés `GROUP BY`. Il signale également comme `not_applicable` les projections dont la clé est basée sur l’ordre de commit ou sur une colonne virtuelle, ou qui comportent un `_block_number` stocké. Il en va de même pour les projections ordinaires qui ne contiennent pas toutes les colonnes lues par la requête. WHATIF ignore `force_optimize_projection_name` et `preferred_optimize_projection_name`, et `force_optimize_projection` ne fait pas échouer le statement.

**Syntaxe**

```sql
EXPLAIN WHATIF [empirical = 0] SELECT ...
```

**Paramètres**

* `index_scan_budget_rows` — nombre de lignes qu’une estimation d’index peut lire avant de basculer sur un échantillon de fenêtres d’index. Valeur par défaut : `10000000`. `0` signifie aucune limite. `max_rows_to_read` peut l’abaisser. Un échantillon lit au moins une trentaine de fenêtres, avec au moins une fenêtre par part ; lorsque `max_rows_to_read` ne le permet pas, l’estimation empirique est `unsupported`.
* `projection_scan_budget_rows` — nombre de lignes qu’une estimation de projection peut lire avant de basculer sur un échantillon de granules. Valeur par défaut : `10000000`. `0` signifie aucune limite ; `max_rows_to_read` peut l’abaisser. Un échantillon lit au moins une trentaine de granules, avec au moins un granule par part ; lorsque `max_rows_to_read` ne le permet pas, l’estimation est `unsupported`.
* `empirical` — `1` (par défaut) évalue l’index en mémoire sur les granules conservés après l’élagage de référence pour mesurer le taux d’exclusion (une borne supérieure). `0` saute cette étape. Dans les deux cas, si `empirical` ne produit aucun résultat (parce qu’il est désactivé ou que l’index ne peut pas être évalué en mémoire), l’estimateur utilise les [statistiques](/fr/reference/engines/table-engines/mergetree-family/mergetree#column-statistics) des colonnes. Si elles ne sont pas disponibles non plus, il fournit un résumé indiquant uniquement si l’index est applicable.

**Sortie**

```text
Baseline (after PK + partition + existing indexes):
  table:       db.t
  parts:       1
  marks:       100
  rows:        10000
  est_bytes:   1.50 MiB             (only when the query reads rows)

With idx_b (minmax, hypothetical):
  status:       applicable
  marks:        1
  marks_span:   0 to 3              (only when the estimate used a sample)
  est_bytes:    15.00 KiB           (only when baseline bytes are known)
  skip_ratio:   99.0%

Estimation:
  source:           empirical | statistical | applicability_only
  empirical_status: ok | unsupported | disabled
  empirical_reason: <reason>        (only when empirical_status = unsupported)
  sampled_parts:    50 / 100        (only when source = empirical)
  sampled_marks:    50 / 100        (only when source = empirical)
  elapsed_us:       631             (only when source = empirical)
```

* `source` — indique comment l’estimation a été obtenue.
  * `empirical` : l’index a été construit en mémoire sur les granules conservés après l’élagage de référence, puis les granules que l’index permettrait d’ignorer ont été comptés. Il s’agit d’une borne supérieure — voir les limites dans [`CREATE HYPOTHETICAL INDEX`](/fr/reference/statements/hypothetical-index#limitations).
  * `statistical` : dérivée des statistiques de colonnes. Utilisée lorsque l’estimation empirique est désactivée (`empirical = 0`) ou n’a pas pu produire de résultat, et que des statistiques de colonnes sont définies sur les colonnes concernées.
  * `applicability_only` : l’index s’applique au prédicat, mais ni l’estimation empirique ni l’estimation statistique n’ont produit de résultat (par ex. `empirical = 0` et aucune statistique de colonnes définie). Indique `skip_ratio: 0.0%` comme borne prudente.
* `empirical_reason` — indique pourquoi l’estimation empirique n’a pas pu être exécutée. Affiché uniquement avec `empirical_status: unsupported`. Par exemple, une valeur non nulle de `merge_tree_min_rows_for_seek` ou de `merge_tree_min_bytes_for_seek` entraîne le regroupement des plages de marques lors d’une lecture réelle, ce que le comptage par granule ne modélise pas ; l’estimation se rabat donc sur `statistical` ou `applicability_only`.
* `sampled_parts` / `sampled_marks` — `<baseline-pruned> / <total in the table>`. Indique quelle fraction de la table reste après l’élagage par la PK, la partition et les index existants, c.-à-d. l’entrée de l’index hypothétique. Pour une estimation d’index obtenue à partir d’un échantillon, le premier nombre de `sampled_marks` ne compte que les marques de référence situées dans les fenêtres échantillonnées ; il est donc inférieur à la valeur `marks` de référence. Pour une projection, `sampled_marks` vaut `<marks read> / <marks in the parts the query reads>` ; si le premier nombre est inférieur au second, l’estimation a reposé sur un échantillon.
* `est_bytes` — estimation du nombre d’octets lus, dérivée de la taille moyenne des lignes de la table ; elle est donc approximative et varie selon le stockage et la compression. La ligne de référence n’apparaît que lorsque la requête lit des lignes ; la ligne par candidat n’apparaît que lorsque l’estimation de référence des octets est connue.

Le paramètre est écrit en intégré entre `WHATIF` et `SELECT` — il n’y a pas de mot-clé `SETTINGS` (comme pour les autres variantes de `EXPLAIN`, qui acceptent leurs options de cette manière).

Si ni index hypothétiques ni projections hypothétiques ne sont définis pour la table, `EXPLAIN WHATIF` indique `status: not_applicable` avec une suggestion d’en créer un.

**Ligne combinée (plusieurs candidats)**

Lorsque deux candidats ou plus sont évalués de manière empirique, `EXPLAIN WHATIF` ajoute un bloc nommé `(combined: idx_a, idx_b, ...)` après les lignes de chaque candidat. Ce bloc indique le bénéfice cumulé de *tous* ces index : une lecture réelle ne conserve un granule que s’il n’est écarté par *aucun* des index de saut. L’estimation combinée correspond donc à l’intersection des granules conservés par les candidats. Son `skip_ratio` est ainsi au moins aussi élevé que celui du meilleur candidat pris isolément : des index complémentaires élaguent davantage de données ensemble, tandis que des index redondants ne le modifient pas.

Seuls les candidats avec `source: empirical` y contribuent, car la ligne combinée est construite par intersection de leurs ensembles de granules conservés. Les candidats estimés `statistical` ou `applicability_only` ne disposent d’aucune donnée par granule et sont exclus ; par conséquent, le bloc combiné n’apparaît que lorsqu’au moins deux candidats ont produit une estimation empirique, et il est omis dans le cas contraire (par exemple avec `empirical = 0`). Ses champs d’estimation se lisent comme ceux d’un bloc empirique par candidat, à ceci près que `elapsed_us` vaut `0` : l’estimation combinée est dérivée des parcours de chaque candidat, et non d’un nouveau parcours. Le nom synthétique `(combined: ...)` n’est qu’une étiquette de rapport et ne peut pas être utilisé avec `force_data_skipping_indices`. Lorsque l’estimation d’un candidat contributeur s’est appuyée sur un échantillon, les fenêtres situées hors de l’échantillon sont inconnues. Le bloc combiné affiche alors `empirical_status: unsupported` et aucune valeur `marks`.

**Exemple empirique**

```sql
CREATE TABLE t (a UInt64, b UInt64) ENGINE = MergeTree ORDER BY a
SETTINGS index_granularity = 100;

INSERT INTO t SELECT number, number FROM numbers(10000);

CREATE HYPOTHETICAL INDEX idx_b ON t (b) TYPE minmax GRANULARITY 1;

EXPLAIN WHATIF SELECT * FROM t WHERE b = 42;
```

```text

  table:       default.t
  parts:       1
  marks:       100
  rows:        10000
  est_bytes:   85.52 KiB

With idx_b (minmax, hypothetical):

  marks:        1
  est_bytes:    875.00 B
```

L’index `minmax` hypothétique permettrait d’élaguer de 100 marques à 1 — `skip_ratio: 99.0%`. (`est_bytes` est une estimation calculée à partir de la taille moyenne des lignes ; la valeur exacte peut donc varier.)

**Exemple avec statistiques**

Les [statistiques de colonne](/fr/reference/engines/table-engines/mergetree-family/mergetree#column-statistics) sont désactivées par défaut. Pour utiliser le chemin `statistical`, définissez-les d’abord sur les colonnes concernées, puis attendez que la mutation de matérialisation se termine :

```sql
ALTER TABLE t ADD STATISTICS b TYPE tdigest;
ALTER TABLE t MATERIALIZE STATISTICS b SETTINGS mutations_sync = 1;
```

Désactivez ensuite le chemin empirique afin que l’estimateur revienne aux statistiques de colonne :

```sql
EXPLAIN WHATIF empirical = 0 SELECT * FROM t WHERE b < 10;
```

```text
With idx_b (minmax, hypothetical):
  status:       applicable
  marks:        1
  est_bytes:    1.66 KiB
  skip_ratio:   99.9%

Estimation:
  source:           statistical
  empirical_status: disabled
```

Le nombre provient de la sélectivité des statistiques de colonne pour `b < 10` (environ 10 lignes sur 10 000) et est indiqué comme borne supérieure de `skip_ratio`. Il n’y a ni `sampled_parts` ni `sampled_marks` — aucune donnée n’a été lue.

Si aucun des deux mécanismes n’est disponible (par ex. `empirical = 0` et aucune statistique de colonne définie), l’estimateur indique `source: applicability_only` ainsi qu’un `skip_ratio: 0.0%` conservateur.

**Projections hypothétiques**

Une projection ordinaire est estimée de la même manière, sur les parts que la requête lirait après élagage par clé primaire et par partition :

```sql
CREATE TABLE t (a UInt64, b UInt64, v UInt64) ENGINE = MergeTree ORDER BY a SETTINGS index_granularity = 100;
INSERT INTO t SELECT number, number % 100, number FROM numbers(10000);
CREATE HYPOTHETICAL PROJECTION p_b ON t (SELECT a, b, v ORDER BY b);
EXPLAIN WHATIF SELECT count() FROM t WHERE b = 42;
```

```text
Baseline (after PK + partition + existing indexes):
  table:       default.t
  parts:       1
  marks:       100
  rows:        10000
  est_bytes:   80.79 KiB

With p_b (normal projection, hypothetical):
  status:       applicable
  marks:        2
  rows:         200
  read_ratio:   0.02x
  verdict:      chosen
  reason:       2 marks would be read instead of 100 from the base table

Estimation:
  source:           empirical
  empirical_status: ok
  sampled_parts:    1 / 1
  sampled_marks:    100 / 100
  elapsed_us:       1126
```

`marks` et `rows` indiquent le nombre de marques et de lignes que la lecture de la projection parcourrait elle-même, et non une fraction de la lecture de la table de base, car un granule de projection contient d’autres lignes qu’un granule de base. `read_ratio` rapporte ce nombre de marques à celui de la table de base : `0.02x` correspond donc à cinquante fois moins de travail, et `15x` à quinze fois plus. `verdict` applique la règle de l’optimiseur de requêtes : moins de marques que pour la table de base, ou autant lorsque la projection répond au `ORDER BY` de la requête. Un candidat peut donc être `applicable` sans être retenu.
