Crée un token pour l&#39;utilisateur courant : le serveur génère un secret aléatoire, l&#39;ajoute à l&#39;utilisateur courant en tant que
[méthode d&#39;authentification](/fr/reference/statements/create/user#identification) supplémentaire, puis le renvoie comme
résultat de la requête. Ce secret n&#39;est affiché que par cette requête — il est stocké sous forme hachée et ne peut donc pas
être récupéré par la suite.

Syntaxe :

```sql
CREATE TOKEN
    [{VALID UNTIL datetime | VALID FOR interval}]
    [GRANTS (privilege ON object [,...])]
```

Il s&#39;agit d&#39;un raccourci pour `ALTER USER <current user> ADD IDENTIFIED WITH sha256_password BY '<random secret>'`
avec les mêmes clauses [`VALID UNTIL`](/fr/reference/statements/create/user#valid-until-clause) et
[`GRANTS`](/fr/reference/statements/create/user#grants-clause) : un token se comporte donc comme un mot de passe ordinaire
de l&#39;utilisateur courant :

* il est lié à l&#39;utilisateur — il apparaît dans `system.query_log` et `system.processes` sous le nom de l&#39;utilisateur, il cesse
  de fonctionner lorsque l&#39;utilisateur est supprimé, et il perd les droits d&#39;accès que l&#39;utilisateur perd ;
* il peut être limité dans le temps avec `VALID UNTIL` ou `VALID FOR`, et en privilèges avec `GRANTS` ;
* il peut être utilisé avec tout mécanisme d&#39;authentification acceptant un mot de passe, par exemple le paramètre `password`
  de l&#39;interface HTTP ou l&#39;option `--password` de `clickhouse-client`.

La création d&#39;un token requiert le privilège `CREATE TOKEN`, ou le privilège `ALTER USER` sur l&#39;utilisateur courant.
Il s&#39;agit d&#39;un privilège distinct car un token abaisse le niveau de sécurité du compte auquel il appartient : un utilisateur
authentifié par une clé matérielle ou un certificat peut s&#39;en servir pour créer un mot de passe de longue durée pour ce même
compte. Ce même privilège autorise le statement équivalent
`ALTER USER <current user> ADD IDENTIFIED ...`.

## Résultat {#result}

La requête renvoie une ligne comportant deux colonnes :

| Colonne       | Type            | Description                                                                                                                                                                          |
| ------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `token`       | `String`        | Le secret généré.                                                                                                                                                                    |
| `valid_until` | `DateTime64(0)` | Date d&#39;expiration du token. `0` signifie qu&#39;il n&#39;expire jamais, selon le même encodage que la colonne `valid_until` de [`system.users`](/fr/reference/system-tables/users). |

Pour obtenir le secret sans aucun formatage, sélectionnez-le avec `FORMAT TSVRaw` :

```sql
CREATE TOKEN VALID FOR INTERVAL 30 DAY GRANTS (SELECT ON db.*) FORMAT TSVRaw
```

Le secret comporte 32 caractères et est généré à partir d&#39;une source aléatoire cryptographiquement sûre ; il n&#39;a donc pas besoin d&#39;être (et n&#39;est pas) confronté aux
[règles de complexité des mots de passe](/fr/reference/statements/create/user#identification) — celles-ci existent pour
encadrer les mots de passe choisis par des humains.

## Clauses VALID UNTIL et VALID FOR {#valid-until-clause}

Elles limitent la durée de vie du token. Elles fonctionnent exactement comme les clauses correspondantes d&#39;une méthode d’authentification
de [`CREATE USER`](/fr/reference/statements/create/user#valid-until-clause) : `VALID UNTIL` attend une date et une heure
absolues, `VALID FOR` attend un [interval](/fr/reference/data-types/special-data-types/interval) qui est ajouté à
l&#39;heure courante au moment de l&#39;exécution de la query.

En l&#39;absence de ces deux clauses, la durée de vie du token est déterminée par
[`create_token_default_ttl_seconds`](/fr/reference/settings/session-settings/create), soit
30 minutes par défaut : un token pour lequel aucune durée plus longue n&#39;est demandée est donc éphémère. Définissez ce paramètre à `0`, ou
écrivez `VALID UNTIL 'infinity'`, pour créer un token qui n&#39;expire jamais.

Exemples :

* `CREATE TOKEN VALID UNTIL '2026-12-31'`
* `CREATE TOKEN VALID FOR INTERVAL 30 DAY`
* `CREATE TOKEN VALID UNTIL 'infinity'`

## Clause GRANTS {#grants-clause}

Limite les droits d&#39;accès des sessions authentifiées par le token à l&#39;intersection avec les privilèges
listés. Cette clause fonctionne exactement comme la [clause `GRANTS` de `CREATE USER`](/fr/reference/statements/create/user#grants-clause),
avec les mêmes limitations — en particulier, la restriction est appliquée sur le nœud qui reçoit la requête et n&#39;est
pas propagée aux autres nœuds d&#39;un cluster. La clause n&#39;ajoute jamais de droits d&#39;accès : un privilège qui n&#39;est
pas accordé à l&#39;utilisateur reste indisponible pour le token. Sans cette clause, le token dispose de l&#39;intégralité
des droits d&#39;accès de l&#39;utilisateur.

Exemples :

* `CREATE TOKEN GRANTS (SELECT ON db.table)`
* `CREATE TOKEN VALID FOR INTERVAL 90 DAY GRANTS (SELECT ON db.table, INSERT ON db.table)`

Ni cette restriction ni la limite temporelle ne s&#39;appliquent à ce que les sessions du token laissent derrière elles — voir
[Considérations de sécurité](#security-considerations).

## Gestion des tokens {#managing-tokens}

Un token est une méthode d&#39;authentification de l&#39;utilisateur ; il est donc répertorié par
[`SHOW CREATE USER`](/fr/reference/statements/show#show-create-user) (avec ses clauses `VALID UNTIL` et `GRANTS`,
mais sans le secret) ainsi que dans les colonnes `auth_type`, `auth_params` et `auth_grants` de la table
[`system.users`](/fr/reference/system-tables/users).

Il n&#39;existe aucune instruction permettant de supprimer un token isolé. Pour révoquer tous les tokens d&#39;un
utilisateur, remplacez ses méthodes d&#39;authentification, par exemple avec `ALTER USER <name> IDENTIFIED WITH ...`, ou
utilisez `ALTER USER <name> RESET AUTHENTICATION METHODS TO NEW` pour ne conserver que la plus récemment
ajoutée. Le nombre de méthodes d&#39;authentification qu&#39;un utilisateur peut posséder simultanément est limité par le
paramètre serveur `max_authentication_methods_per_user`.

Le secret est généré et stocké par la requête elle-même : ainsi, un `CREATE TOKEN` dont le résultat n&#39;atteint
jamais le client — une connexion perdue pendant l&#39;envoi de la ligne, ou un `INTO OUTFILE` que le client ne peut
pas ouvrir — laisse derrière lui une méthode d&#39;authentification que personne ne peut utiliser et qui est malgré tout
décomptée de cette limite. Personne ne détient un tel secret : il n&#39;existe que pendant l&#39;exécution de la requête.
Une requête rejetée avant son exécution, y compris lorsque sa clause `FORMAT` désigne un format inutilisable,
n&#39;ajoute rien.

`CREATE TOKEN` ne prend pas en charge la clause `ON CLUSTER`. Utilisez un stockage des accès replicated (ou
exécutez la requête sur chaque nœud avec l&#39;instruction équivalente `ALTER USER ... ADD IDENTIFIED WITH sha256_hash`)
pour qu&#39;un token fonctionne sur l&#39;ensemble d&#39;un cluster dont les entités d&#39;accès sont stockées localement.

## Considérations de sécurité {#security-considerations}

`VALID UNTIL` et `GRANTS` restreignent les sessions qui s&#39;authentifient avec le token. Ils ne restreignent pas
ce que ces sessions laissent derrière elles :

* L&#39;échéance est vérifiée lorsqu&#39;une session s&#39;authentifie avec le token. Une session déjà ouverte, ou une
  query déjà en cours d&#39;exécution, ne sont pas interrompues à l&#39;expiration du token.
* Tout ce qu&#39;une session crée survit au token, et un objet qui travaille de manière autonome poursuit son
  activité : une
  [refreshable materialized view](/fr/reference/statements/create/view#refreshable-materialized-view) continue de
  se rafraîchir, une materialized view attachée à un streaming table engine tel que
  [`Kafka`](/fr/reference/engines/table-engines/integrations/kafka),
  [`RabbitMQ`](/fr/reference/engines/table-engines/integrations/rabbitmq),
  [`NATS`](/fr/reference/engines/table-engines/integrations/nats) ou
  [`S3Queue`](/fr/reference/engines/table-engines/integrations/s3queue) continue de consommer, et un dictionary doté
  d&#39;un [`LIFETIME`](/fr/reference/statements/create/dictionary/lifetime) continue de se recharger, bien après
  l&#39;expiration du token. Une view effectue ce travail avec les droits de son
  [`DEFINER`](/fr/reference/statements/create/view#sql_security), qui est par défaut l&#39;utilisateur ayant créé la
  view — soit les droits complets de cet utilisateur, et non ceux que la clause `GRANTS` du token lui avait laissés.

Un token autorisé à créer des tables, des views ou des dictionaries peut donc, en pratique, repousser ses deux
limites : il peut laisser derrière lui une tâche persistante qui continue de s&#39;exécuter après l&#39;échéance et
qui fait, avec les droits de l&#39;utilisateur, ce que le token lui-même n&#39;avait pas le droit de faire. N&#39;accordez à un
token que ce dont l&#39;application a besoin — généralement `SELECT` et `INSERT` sur des tables nommées — et excluez
`CREATE TABLE`, `CREATE VIEW`, `CREATE DICTIONARY` ainsi que les privilèges `ACCESS MANAGEMENT` de sa
clause `GRANTS` lorsque ces limites doivent réellement tenir.

Une session qui s&#39;est authentifiée avec un token comportant une clause `GRANTS` ne peut émettre aucun token :
l&#39;ajout d&#39;une méthode d’authentification à un utilisateur existant lui est refusé. La clause
`GRANTS` d&#39;une nouvelle méthode d’authentification est croisée, à la connexion, avec les droits d’accès de
l&#39;utilisateur, et non avec ceux de la session qui a créé la method ; ce serait sinon un moyen d&#39;élargir la limite.
