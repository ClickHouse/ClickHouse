Le dictionnaire `xgboost` (`XGBOOST`) entraîne, lors de son chargement, un modèle [XGBoost](https://xgboost.readthedocs.io/) à gradient boosting à partir d&#39;une table source contenant des lignes d&#39;entraînement, puis prédit une cible numérique pour tout vecteur de fonctionnalités que vous lui transmettez. Les colonnes de fonctionnalités constituent la clé du dictionnaire, et l&#39;unique attribut correspond à la cible apprise par le modèle.

Il convient à la régression tabulaire et à la classification binaire lorsque les fonctionnalités sont numériques, par exemple pour prévoir une valeur à partir de plusieurs mesures ou pour attribuer un score à des lignes par rapport à une cible apprise. Les objectifs multiclasses ne sont pas pris en charge (voir [Paramètres de disposition](#layout-parameters)).

<Note>
  L&#39;intégration XGBoost est expérimentale. Activez-la avec le paramètre `enable_xgboost` avant de créer un dictionnaire `XGBOOST` ou d&#39;appeler `predictXGBoost` :

  ```sql
  SET enable_xgboost = 1;
  ```

  Seul `CREATE DICTIONARY` est pris en charge : un dictionnaire `XGBOOST` défini dans un fichier de configuration du serveur ne peut pas être chargé.
</Note>

La fonction [`predictXGBoost`](/fr/reference/functions/regular-functions/machine-learning-functions) est le seul moyen d&#39;interroger le dictionnaire : elle prend les fonctionnalités comme arguments distincts, renvoie la prédiction et accepte des [paramètres de prédiction](#prediction-parameters) supplémentaires. Comme le dictionnaire contient un modèle entraîné et non des lignes, l&#39;interface générique des dictionnaires — [`dictGet`](/fr/reference/functions/regular-functions/ext-dict-functions#dictGet), `dictHas` et `SELECT * FROM dict` — n&#39;est pas prise en charge et renvoie une erreur.

## Guide de démarrage rapide {#quickstart}

Dans cet exemple, nous entraînons un modèle de régression sur la cible linéaire `y = 2*x1 + 3*x2`.

**1. Créez une table source** contenant les lignes d&#39;entraînement, avec les colonnes de fonctionnalités suivies de la cible :

```sql
CREATE TABLE training_data (x1 Float64, x2 Float64, y Float64)
ENGINE = MergeTree ORDER BY tuple();
```

**2. Insérer les données d’entraînement :**

```sql
INSERT INTO training_data
SELECT number AS x1, number * 2 AS x2, 2 * x1 + 3 * x2 AS y
FROM numbers(100);
```

**3. Créez le dictionnaire** avec la disposition `XGBOOST` — les colonnes de fonctionnalités forment la clé et `y` est l&#39;attribut cible :

```sql
CREATE DICTIONARY model (x1 Float64, x2 Float64, y Float64)
PRIMARY KEY (x1, x2)
SOURCE(CLICKHOUSE(TABLE 'training_data'))
LAYOUT(XGBOOST(
    objective 'reg:squarederror'
    num_iterations 100
    max_depth 6
))
LIFETIME(0);
```

`PRIMARY KEY (x1, x2)` fait de `x1` et `x2` les fonctionnalités. La cible apprise par le modèle est `y`, inférée comme étant l&#39;unique colonne qui ne fait pas partie de la clé ; les paramètres de `LAYOUT` sont des hyperparamètres XGBoost (voir [Paramètres de disposition](#layout-parameters)).

**4. Prédire** — `predictXGBoost` prend les fonctionnalités par position et renvoie la prédiction :

```sql
SELECT predictXGBoost('model', 1.0, 2.0) AS prediction;
```

La valeur réelle étant `2*1 + 3*2 = 8`, la prédiction du modèle est proche de `8`.

## Fonctionnement {#how-it-works}

**Entraînement (à l’instant de chargement).** Chaque ligne de la source est une observation `(features..., target)`. Lors du chargement du dictionnaire, la source est lue bloc par bloc, puis le modèle est entraîné une seule fois sur l’ensemble des données. Les valeurs des fonctionnalités et de la cible sont lues comme des nombres à virgule flottante : les colonnes de clé doivent donc être numériques et l’attribut cible doit être à virgule flottante (voir [Structure du dictionnaire](#dictionary-structure)).

<Warning>
  **L’entraînement conserve l’intégralité du jeu d’entraînement en mémoire.** La lecture de la source par blocs ne constitue pas un entraînement hors mémoire (out-of-core) : chaque bloc est accumulé plutôt que consommé, si bien que la totalité du jeu d’entraînement réside en mémoire avant la première itération de boosting et y reste jusqu’à la dernière.
</Warning>

**Prédiction (au moment de l’exécution de la requête).** Pour effectuer une prédiction, le modèle prend le vecteur de fonctionnalités — dans l’ordre de déclaration des colonnes de clé — et le fait passer par le booster entraîné, qui renvoie un `Float64`. Une fonctionnalité `NULL` est transmise au modèle comme valeur manquante, que XGBoost traite de la manière apprise lors de l’entraînement ; la prédiction n’est donc jamais `NULL`. Lorsque toutes les fonctionnalités sont des constantes, le modèle est évalué une seule fois par bloc plutôt qu’une fois par ligne.

**Le modèle n’est pas persisté.** Il ne réside qu’en mémoire, tant que le dictionnaire est chargé, et il est réentraîné à partir de la source à chaque chargement, y compris après un redémarrage du serveur.

**Réentraîner le modèle.** Comme chaque chargement entraîne le modèle à partir de zéro, `SYSTEM RELOAD DICTIONARY` réentraîne le modèle sur le contenu actuel de la table source :

```sql
INSERT INTO training_data VALUES (5, 10, 40);
SYSTEM RELOAD DICTIONARY model;
```

Une valeur `LIFETIME` non nulle déclenche également un réentraînement, puisqu&#39;un rechargement déclenché par l&#39;expiration de la durée de vie est un chargement ordinaire. Utilisez-la pour rafraîchir périodiquement le modèle à mesure que les données d’entraînement s&#39;enrichissent.

## Structure du dictionnaire {#dictionary-structure}

Un dictionnaire `XGBOOST` possède une structure fixe :

* La `PRIMARY KEY` est constituée d&#39;une ou plusieurs colonnes d&#39;un type numérique natif (entiers et nombres à virgule flottante) : ce sont les fonctionnalités. Au moment de l’exécution de la requête, cette « clé » correspond au vecteur de fonctionnalités que vous fournissez pour obtenir une prédiction, et non à une clé de lookup stockée. L&#39;ordre des fonctionnalités suit l&#39;ordre de déclaration des colonnes de clé, et `predictXGBoost` associe ses arguments positionnels selon cet ordre.
* En plus de ces colonnes, déclarez **exactement un attribut de type `Float32` ou `Float64`** : la cible que le modèle apprend. Il est toujours inféré comme l&#39;unique colonne qui ne fait pas partie de la clé de fonctionnalités. Aucun paramètre ne permet de le nommer, et déclarer plus d&#39;un attribut provoque une erreur.

Une colonne qui ne respecte pas ces exigences est rejetée au chargement du dictionnaire, et non lors de sa création.

## Paramètres de disposition {#layout-parameters}

Seuls les paramètres listés ci-dessous sont acceptés ; tout autre nom fait échouer le chargement, de sorte que les fautes de frappe sont détectées dès l’entraînement du modèle au lieu d’être ignorées silencieusement. `num_iterations` est géré par ClickHouse (voir sa description) ; tous les autres paramètres sont transmis tels quels au booster XGBoost, sous forme de chaîne, et reprennent la valeur par défaut et la plage de valeurs propres à XGBoost — consultez la [référence des paramètres XGBoost](https://xgboost.readthedocs.io/en/stable/parameter.html).

| Paramètre                                                     | Description                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `num_iterations`                                              | Nombre d’itérations de boosting (nombre d’arbres à entraîner). Entier positif, utilisé comme nombre d’itérations de la boucle d’entraînement plutôt que transmis au booster. Valeur par défaut : `100`.                                                                                                                                                                                                      |
| `booster`                                                     | Type de booster : `gbtree`, `gblinear` ou `dart`.                                                                                                                                                                                                                                                                                                                                                            |
| `objective`                                                   | Objectif d’apprentissage, par exemple `reg:squarederror` ou `binary:logistic`. Il doit s’agir d’un objectif qui prédit une seule valeur par ligne ; les objectifs multiclasses (`multi:softmax`, `multi:softprob`) sont rejetés.                                                                                                                                                                             |
| `seed`                                                        | Graine du générateur de nombres aléatoires. L’entraînement étant par ailleurs déterministe, ce paramètre ne modifie le modèle que si un paramètre stochastique (`subsample`, `sampling_method`, n’importe quel `colsample_*`) est également défini.                                                                                                                                                          |
| `verbosity`                                                   | Niveau de verbosité de la journalisation de XGBoost : `0` (silencieux), `1` (avertissements, valeur par défaut) ou `2` (informations). Le niveau de débogage `3` est rejeté, car les moniteurs de chronométrage qu’il active ne sont pas thread-safe. N’affecte que les messages journalisés par XGBoost, jamais le modèle entraîné. Consultez les [Notes](#notes) pour savoir où sont envoyés les messages. |
| `nthread`                                                     | Nombre de fils d’exécution parallèles utilisés pour l’entraînement. Accepté et transmis, mais actuellement sans effet : la version de XGBoost intégrée est compilée sans OpenMP, si bien que l’entraînement et la prédiction s’exécutent toujours sur un seul fil d’exécution.                                                                                                                               |
| `eta`                                                         | Facteur de réduction du pas appliqué après chaque itération de boosting. Seule cette orthographe est acceptée ; l’alias `learning_rate` de XGBoost ne l’est pas.                                                                                                                                                                                                                                             |
| `gamma`                                                       | Réduction minimale de la perte requise pour effectuer une division supplémentaire sur une feuille.                                                                                                                                                                                                                                                                                                           |
| `max_depth`                                                   | Profondeur maximale d’un arbre.                                                                                                                                                                                                                                                                                                                                                                              |
| `min_child_weight`                                            | Somme minimale des poids d’instance (hessienne) requise dans un nœud enfant.                                                                                                                                                                                                                                                                                                                                 |
| `max_delta_step`                                              | Pas delta maximal autorisé pour la sortie de chaque feuille.                                                                                                                                                                                                                                                                                                                                                 |
| `subsample`                                                   | Fraction des lignes d’entraînement échantillonnées à chaque itération de boosting.                                                                                                                                                                                                                                                                                                                           |
| `sampling_method`                                             | Méthode d’échantillonnage des lignes : `uniform` ou `gradient_based`. Sans effet tant que `subsample` n’est pas défini à une valeur inférieure à `1`.                                                                                                                                                                                                                                                        |
| `colsample_bytree` / `colsample_bylevel` / `colsample_bynode` | Fraction des colonnes (fonctionnalités) échantillonnées par arbre / par niveau / par division.                                                                                                                                                                                                                                                                                                               |
| `lambda`                                                      | Terme de régularisation L2 sur les poids. Seule cette orthographe est acceptée ; l’alias `reg_lambda` de XGBoost ne l’est pas.                                                                                                                                                                                                                                                                               |
| `alpha`                                                       | Terme de régularisation L1 sur les poids. Seule cette orthographe est acceptée ; l’alias `reg_alpha` de XGBoost ne l’est pas.                                                                                                                                                                                                                                                                                |
| `tree_method`                                                 | Algorithme de construction des arbres : `auto`, `exact`, `approx` ou `hist`.                                                                                                                                                                                                                                                                                                                                 |
| `scale_pos_weight`                                            | Équilibre les poids positifs et négatifs ; utile pour les classes déséquilibrées.                                                                                                                                                                                                                                                                                                                            |
| `grow_policy`                                                 | Manière dont les nouveaux nœuds sont ajoutés à l’arbre : `depthwise` ou `lossguide`.                                                                                                                                                                                                                                                                                                                         |
| `max_leaves`                                                  | Nombre maximal de nœuds feuilles (utilisé avec `grow_policy` `lossguide`).                                                                                                                                                                                                                                                                                                                                   |
| `max_bin`                                                     | Nombre maximal de classes de taille discrètes utilisées pour regrouper les fonctionnalités continues (utilisé avec `tree_method` `hist`).                                                                                                                                                                                                                                                                    |
| `num_parallel_tree`                                           | Nombre d’arbres construits par itération de boosting (une valeur `> 1` entraîne une forêt aléatoire boostée).                                                                                                                                                                                                                                                                                                |

Les noms de paramètres sont case-insensitive, et chacun ne peut être spécifié qu’une seule fois. Les valeurs doivent être un entier positif, un nombre à virgule flottante ou une chaîne entre guillemets : un littéral négatif est rejeté par le DDL du dictionnaire lui-même, avant même que la disposition ne le reçoive ; il est donc impossible de spécifier une `seed` négative.

Par exemple, un dictionnaire qui définit également la taille de pas `eta` :

```sql
CREATE DICTIONARY model_tuned (x1 Float64, x2 Float64, y Float64)
PRIMARY KEY (x1, x2)
SOURCE(CLICKHOUSE(TABLE 'training_data'))
LAYOUT(XGBOOST(
    objective 'reg:squarederror'
    num_iterations 100
    max_depth 6
    eta 0.3
))
LIFETIME(0);
```

## Paramètres de prédiction {#prediction-parameters}

`predictXGBoost` accepte, en dernier argument facultatif après les fonctionnalités, une `Map` constante de paramètres de prédiction XGBoost, construite avec `map` :

```sql
SELECT predictXGBoost('model', 1.0, 2.0, map('type', 0, 'iteration_end', 0));
```

Les noms des paramètres correspondent aux paramètres de prédiction de la fonction `XGBoosterPredictFromDMatrix` de XGBoost. Seules les clés ci-dessous sont acceptées ; toute autre clé fait échouer la requête. Chaque paramètre étant un entier ou un booléen, les valeurs de la `Map` doivent être d&#39;un type entier.

| Paramètre         | Description                                                                                                                                                                                                                                                                                                                       | Valeur par défaut |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `type`            | Type de prédiction. Seules les valeurs `0` (valeur) et `1` (marge) sont acceptées, car `predictXGBoost` renvoie un seul `Float64` par ligne. Les autres types XGBoost (`2`/`3` : contributions SHAP, `4`/`5` : interactions entre fonctionnalités, `6` : index de feuille) produisent plusieurs valeurs par ligne et sont donc rejetés. | `0`               |
| `iteration_begin` | Première itération de boosting à inclure dans la prédiction, numérotée à partir de `0` (incluse). Ne doit pas dépasser le nombre d&#39;itérations de boosting utilisé pour entraîner le modèle (`num_iterations`).                                                                                                                | `0`               |
| `iteration_end`   | Itération qui suit la dernière itération de boosting à inclure (exclue) : ainsi, `iteration_end 1` n&#39;utilise que la première itération, tandis que `0` les utilise toutes. Soumis aux mêmes bornes que `iteration_begin`.                                                                                                     | `0`               |

## Notes {#notes}

* **Sémantique d’un dictionnaire computationnel.** Il s’agit d’un dictionnaire *computationnel* : il contient un modèle entraîné, et non des lignes, et `predictXGBoost` est le seul moyen de l’interroger. L’interface générique des dictionnaires n’est pas prise en charge et renvoie une erreur : `dictGet` (il n’y a aucun attribut stocké à rechercher — la &quot;clé&quot; est un vecteur de fonctionnalités à partir duquel effectuer la prédiction), `dictHas` (aucune clé n’est stockée), `SELECT * FROM dict` ainsi que la jointure du dictionnaire en tant que table. Comme `predictXGBoost` est le seul point d’entrée, le paramètre `enable_xgboost` doit être activé pour chaque prédiction.

* **Colonnes numériques uniquement.** Chaque colonne de fonctionnalité (clé) doit être d’un type numérique natif et l’attribut cible doit être de type `Float32` ou `Float64`. Les valeurs sont lues comme des nombres à virgule flottante lors de l’entraînement et de la prédiction. Les arguments de fonctionnalités de `predictXGBoost` peuvent également être `Nullable` ; voir [Fonctionnement](#how-it-works).

* **`system.dictionaries` n’indique aucun élément stocké.** Le dictionnaire entraîne un modèle au lieu de stocker des lignes : `element_count` vaut donc `0`, comme pour un dictionnaire `direct`, et `bytes_allocated` vaut également `0`, car le modèle entraîné appartient à XGBoost, qui n’indique pas la quantité de mémoire qu’il occupe. `query_count` et `found_rate` comptabilisent les lignes transmises au modèle par `predictXGBoost` ; un appel dont toutes les fonctionnalités sont constantes n’est évalué qu’une fois par bloc et compte donc une ligne par bloc, et non une par ligne.

* **En cas d’échec du rechargement, le modèle précédent est conservé.** Si le réentraînement échoue — table source supprimée, schéma modifié, hyperparamètre qui n’est plus accepté —, les prédictions ne se mettent pas à échouer pour autant. Le dictionnaire continue de servir le dernier modèle entraîné avec succès et enregistre l’erreur. Comparez `last_successful_update_time` et `last_exception` dans `system.dictionaries` pour savoir si le modèle reflète toujours les données sources actuelles :

  ```sql
  SELECT name, status, last_successful_update_time, last_exception
  FROM system.dictionaries
  WHERE name = 'model';
  ```

* **Les messages de XGBoost sont consignés dans le journal du serveur.** Ils sont écrits via le journaliseur `XGBoost`, au niveau défini par XGBoost, et rattachés à la requête qui effectue l’entraînement ou la prédiction ; ils apparaissent donc également dans `system.text_log`. Augmentez `verbosity` pour en afficher davantage.

* **L’ordre des fonctionnalités compte.** `predictXGBoost` associe ses arguments de fonctionnalités positionnels aux colonnes de clé dans l’ordre de leur déclaration, et le nombre d’arguments de fonctionnalités doit correspondre au nombre de colonnes de clé.
