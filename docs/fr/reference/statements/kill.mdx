Cette page décrit les statements `KILL QUERY`, `KILL MUTATION`, `KILL TRANSACTION` et `KILL PART_MOVE_TO_SHARD`.

Par défaut, `KILL QUERY` lève une exception `NOTHING_TO_KILL` lorsque son expression `WHERE` ne laisse aucune ligne éligible dans `system.processes` une fois le statement `KILL` en cours exclu, et `KILL MUTATION` lève une exception lorsque son expression `WHERE` ne correspond à aucune ligne de `system.mutations`. Pour autoriser les correspondances vides sans lever d’exception, définissez le paramètre [`kill_throw_if_noop`](/fr/operations/settings/settings#kill_throw_if_noop) sur `false`.
`KILL TRANSACTION` et `KILL PART_MOVE_TO_SHARD` ne lèvent jamais d’exception en cas de correspondance vide : elles renvoient un ensemble de résultats vide.
L’exécution avec `ON CLUSTER` ne lève pas d’exception en cas de correspondance vide, car les résultats de correspondance ne sont pas agrégés entre les hôtes.

## KILL QUERY {#kill-query}

```sql
KILL QUERY [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.processes query>
  [SYNC|ASYNC|TEST]
  [FORMAT format]
```

Tente de terminer de force les requêtes en cours d&#39;exécution.
Les requêtes à arrêter sont sélectionnées dans la table system.processes à l&#39;aide des critères définis dans la clause `WHERE` de la requête `KILL`.

Exemples :

Tout d&#39;abord, vous devez obtenir la liste des requêtes inachevées. Cette requête SQL les renvoie en les classant selon leur durée d&#39;exécution :

Liste à partir d&#39;un seul nœud ClickHouse :

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM system.processes
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Lister à partir d’un cluster ClickHouse :

```sql
SELECT
  initial_query_id,
  query_id,
  formatReadableTimeDelta(elapsed) AS time_delta,
  query,
  *
  FROM clusterAllReplicas(default, system.processes)
  WHERE query ILIKE 'SELECT%'
  ORDER BY time_delta DESC;
```

Interrompez la requête :

```sql
-- Forcibly terminates all queries with the specified query_id:
KILL QUERY WHERE query_id='2-857d-4a57-9ee0-327da5d60a90'

-- Synchronously terminates all queries run by 'username':
KILL QUERY WHERE user='username' SYNC
```

<Tip>
  Si vous interrompez une requête dans ClickHouse Cloud ou dans un cluster autogéré, veillez à utiliser l’option `ON CLUSTER [cluster-name]` afin de garantir que la requête est interrompue sur toutes les répliques
</Tip>

Les utilisateurs en lecture seule ne peuvent arrêter que leurs propres requêtes.

Un utilisateur qui ne dispose pas du privilège `SELECT` sur `system.processes` peut néanmoins annuler sa propre requête en indiquant son identifiant :
`KILL QUERY WHERE query_id = '<id>'`. Pour un utilisateur qui ne dispose ni de ce privilège ni de `KILL QUERY`, un identifiant correspondant à une requête
qui ne s’exécute pas sous son compte n’annule aucune requête et lève par défaut une exception `NOTHING_TO_KILL`. Si
[`kill_throw_if_noop`](/fr/operations/settings/settings#kill_throw_if_noop) est défini sur `false`, aucune ligne n’est alors renvoyée ;
un utilisateur qui dispose de `KILL QUERY` mais pas de ce privilège `SELECT` voit sa requête refusée faute de privilège `SELECT`.
Toute autre condition `WHERE`, ainsi que `ON CLUSTER`, nécessitent toujours les privilèges décrits ci-dessus.

Par défaut, la version asynchrone des requêtes (`ASYNC`) est utilisée et n’attend pas la confirmation de leur arrêt.

La version synchrone (`SYNC`) attend l’arrêt de toutes les requêtes et affiche des informations sur chaque processus à mesure qu’il s’arrête.
La réponse contient la colonne `kill_status`, qui peut prendre les valeurs suivantes :

1. `finished` – La requête a été interrompue avec succès.
2. `waiting` – En attente de la fin de la requête après l’envoi d’un signal d’arrêt.
3. Les autres valeurs expliquent pourquoi la requête ne peut pas être arrêtée.

Une requête de test (`TEST`) vérifie uniquement les droits de l’utilisateur et affiche la liste des requêtes à arrêter.

## KILL MUTATION {#kill-mutation}

La présence de mutations long-running ou de mutations incomplètes indique souvent qu’un service ClickHouse fonctionne mal. La nature asynchrone des mutations peut les amener à consommer toutes les ressources disponibles du système. Vous devrez peut-être soit :

* Suspendre toutes les nouvelles mutations, les `INSERT` et les `SELECT`, puis laisser la file d’attente des mutations se résorber.
* Ou interrompre manuellement certaines de ces mutations en envoyant une commande `KILL`.

```sql
KILL MUTATION
  WHERE <where expression to SELECT FROM system.mutations query>
  [TEST]
  [FORMAT format]
```

Tente d’annuler et de supprimer les [mutations](/fr/reference/statements/alter/index#mutations) en cours d’exécution. Les mutations à annuler sont sélectionnées dans la table [`system.mutations`](/fr/reference/system-tables/mutations) à l’aide du filtre spécifié par la clause `WHERE` de la requête `KILL`.

Une requête de test (`TEST`) vérifie uniquement les droits de l’utilisateur et affiche la liste des mutations à arrêter.

Exemples :

Obtenir le `count()` du nombre de mutations incomplètes :

Nombre de mutations sur un seul nœud ClickHouse :

```sql
SELECT count(*)
FROM system.mutations
WHERE is_done = 0;
```

Nombre de mutations d’un cluster de répliques ClickHouse :

```sql
SELECT count(*)
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

Consultez la liste des mutations incomplètes :

Liste des mutations pour un seul nœud ClickHouse :

```sql
SELECT mutation_id, *
FROM system.mutations
WHERE is_done = 0;
```

Liste des mutations d’un cluster ClickHouse :

```sql
SELECT mutation_id, *
FROM clusterAllReplicas('default', system.mutations)
WHERE is_done = 0;
```

Interrompez les mutations au besoin :

```sql
-- Cancel and remove all mutations of the single table:
KILL MUTATION WHERE database = 'default' AND table = 'table'

-- Cancel the specific mutation:
KILL MUTATION WHERE database = 'default' AND table = 'table' AND mutation_id = 'mutation_3.txt'
```

La requête est utile lorsqu&#39;une mutation est bloquée et ne peut pas aboutir (par ex. si une fonction de la requête de mutation lève une exception lorsqu&#39;elle est appliquée aux données contenues dans la table).

Les modifications déjà effectuées par la mutation ne sont pas annulées.

<Note>
  La colonne `is_killed=1` (ClickHouse Cloud uniquement) dans la table [system.mutations](/fr/reference/system-tables/mutations) ne signifie pas nécessairement que la mutation est complètement terminée. Il est possible qu&#39;une mutation reste pendant une longue période dans un état où `is_killed=1` et `is_done=0`. Cela peut se produire si une autre mutation long-running bloque la mutation interrompue. Il s&#39;agit d&#39;une situation normale.
</Note>

## KILL TRANSACTION {#kill-transaction}

Introduit dans : v22.4.0

<ExperimentalBadge />

<CloudNotSupportedBadge />

<Note>
  Ce statement fait partie d&#39;un ensemble de fonctionnalités expérimentales.
  Pour activer la prise en charge expérimentale des transactions, ajoutez ce paramètre à votre [configuration](/fr/concepts/features/configuration/server-config/configuration-files) :

  ```xml
  <clickhouse>
      <allow_experimental_transactions>1</allow_experimental_transactions>
  </clickhouse>
  ```

  Pour plus d&#39;informations, consultez la page [Prise en charge transactionnelle (ACID)](/fr/concepts/features/operations/insert/transactions#transactions-commit-and-rollback).
</Note>

```sql
KILL TRANSACTION [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.transactions query>
  [TEST]
  [FORMAT format]
```

Annule les [transactions](/fr/reference/statements/transactions) en cours sélectionnées dans la table [`system.transactions`](/fr/reference/system-tables/transactions) par la clause `WHERE`.
La session d’une transaction interrompue se retrouve alors dans le même état qu’après l’échec d’une requête, comme décrit dans [`COMMIT`](/fr/reference/statements/transactions#commit) : tant qu’elle n’a pas exécuté `ROLLBACK`, `COMMIT` lève une exception `INVALID_TRANSACTION`.

Ce statement nécessite le privilège `KILL TRANSACTION` ainsi que le privilège `SELECT` sur `system.transactions`.
La réponse contient la colonne `kill_status`, qui vaut `waiting` pour une transaction annulée, suivie des colonnes `tid`, `tid_hash`, `elapsed`, `is_readonly` et `state` de `system.transactions`.

Une requête de test (`TEST`) se contente de vérifier les droits de l&#39;utilisateur et affiche la liste des transactions à annuler.

Exemple :

```sql title="Query"
KILL TRANSACTION WHERE tid_hash = 17701405580889899494 FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
tid:         (105,84,'42343455-b083-479e-b5d5-d50cf2ec2f58',3)
tid_hash:    17701405580889899494
elapsed:     0.160418317
is_readonly: 0
state:       RUNNING
```

## KILL PART_MOVE_TO_SHARD {#kill-part-move-to-shard}

Introduit dans : v21.11.0

<ExperimentalBadge />

<Note>
  Le déplacement de parts entre partitionnés est une fonctionnalité expérimentale, activée table par table au moyen du paramètre MergeTree [`part_moves_between_shards_enable`](/fr/reference/settings/merge-tree-settings/part-moves#part_moves_between_shards_enable).
</Note>

```sql
KILL PART_MOVE_TO_SHARD [ON CLUSTER cluster]
  WHERE <where expression to SELECT FROM system.part_moves_between_shards query>
  [TEST]
  [FORMAT format]
```

Annule les déplacements de parts entre partitionnés, lancés par `ALTER TABLE ... MOVE PART ... TO SHARD`, sélectionnés dans la table [`system.part_moves_between_shards`](/fr/reference/system-tables/part_moves_between_shards) par la clause `WHERE`.
Un déplacement annulé est annulé en arrière-plan, et son `state` dans `system.part_moves_between_shards` passe à `CANCELLED`.
Un déplacement ayant atteint l&#39;état `SOURCE_DROP` ne peut plus être annulé et se poursuit jusqu&#39;à son terme.

Le statement requiert le privilège `SELECT` sur `system.part_moves_between_shards` et, pour annuler un déplacement, le privilège `ALTER MOVE PARTITION` sur sa table ainsi que le privilège `MOVE PARTITION BETWEEN SHARDS`.
Avec `ON CLUSTER`, le statement requiert les deux privilèges de déplacement sur `*.*`.
La réponse contient la colonne `kill_status`, qui vaut `waiting` pour un déplacement annulé et `cant_cancel` pour un déplacement qui ne peut plus être annulé, suivie des colonnes `database`, `table`, `task_name`, `task_uuid`, `part_name`, `to_shard` et `state` de `system.part_moves_between_shards`.

Une requête de test (`TEST`) se contente d&#39;afficher la liste des déplacements à annuler. Le modificateur `SYNC` n&#39;est pas pris en charge et lève une exception `NOT_IMPLEMENTED`.

Exemple :

```sql title="Query"
KILL PART_MOVE_TO_SHARD WHERE database = 'default' AND table = 'src' FORMAT Vertical
```

```text title="Response"
Row 1:
──────
kill_status: waiting
database:    default
table:       src
task_name:   task-0000000000
task_uuid:   7e073eb5-be5a-46a9-9538-ea176bd7ebe8
part_name:   all_0_0_0
to_shard:    /clickhouse/tables/s2
state:       SYNC_SOURCE
```
