La clause `JOIN` crée une nouvelle table en combinant des colonnes d&#39;une ou de plusieurs tables à partir de valeurs communes. Il s&#39;agit d&#39;une opération courante dans les bases de données compatibles SQL, qui correspond à la [jointure](https://en.wikipedia.org/wiki/Relational_algebra#Joins_and_join-like_operators) en algèbre relationnelle. Le cas particulier où une table est jointe à elle-même est souvent appelé « self-join ».

**Syntaxe**

```sql
SELECT <expr_list>
FROM <left_table>
[GLOBAL] [INNER|LEFT|RIGHT|FULL|CROSS] [OUTER|SEMI|ANTI|ANY|ALL|ASOF] JOIN <right_table>
(ON <expr_list>)|(USING <column_list>) ...
```

Les expressions de la clause `ON` et les colonnes de la clause `USING` sont appelées « clés de jointure ». Sauf indication contraire, un `JOIN` produit un [produit cartésien](https://en.wikipedia.org/wiki/Cartesian_product) à partir des lignes dont les clés de jointure correspondent, ce qui peut donner des résultats comportant bien plus de lignes que les tables sources.

Cette page décrit la syntaxe et la sémantique de la clause `JOIN`. Pour en savoir plus sur l&#39;exécution des jointures dans ClickHouse, les types de JOIN, les paramètres, les considérations relatives à la mémoire et les optimisations, consultez la section [Contenu associé](#related-content).

## Types de JOIN pris en charge {#supported-types-of-join}

Tous les types standard de [SQL JOIN](https://en.wikipedia.org/wiki/Join_\(SQL\)) sont pris en charge :

| Type               | Description                                                                                                                                                                                                                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INNER JOIN`       | Seules les lignes correspondantes sont renvoyées.                                                                                                                                                                                                                                                                                                             |
| `LEFT OUTER JOIN`  | Les lignes non correspondantes de la table de gauche sont renvoyées en plus des lignes correspondantes.                                                                                                                                                                                                                                                       |
| `RIGHT OUTER JOIN` | Les lignes non correspondantes de la table de droite sont renvoyées en plus des lignes correspondantes.                                                                                                                                                                                                                                                       |
| `FULL OUTER JOIN`  | Les lignes non correspondantes des deux tables sont renvoyées en plus des lignes correspondantes.                                                                                                                                                                                                                                                             |
| `CROSS JOIN`       | Produit le produit cartésien des tables entières. Les clés de jointure ne sont **pas** spécifiées.                                                                                                                                                                                                                                                            |
| `NATURAL JOIN`     | Effectue automatiquement la jointure sur toutes les colonnes portant le même nom dans les deux tables. Chaque colonne commune apparaît une seule fois dans le résultat. Prend en charge les variantes `INNER` (par défaut), `LEFT`, `RIGHT` et `FULL`. Équivalent à `JOIN ... USING (col1, col2, ...)`, où la liste des colonnes est déduite automatiquement. |

* `JOIN` sans type spécifié implique `INNER`.
* Le mot-clé `OUTER` peut être omis.
* Une syntaxe alternative pour `CROSS JOIN` consiste à spécifier plusieurs tables dans la [clause `FROM`](/fr/reference/statements/select/from), séparées par des virgules.
* S&#39;il n&#39;y a pas de colonnes correspondantes pour un `NATURAL JOIN`, il fonctionne comme un `CROSS JOIN`.

D&#39;autres types de JOIN disponibles dans ClickHouse sont :

| Type                                                | Description                                                                                                                                                                                                                                    |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LEFT SEMI JOIN`, `RIGHT SEMI JOIN`                 | Une liste d&#39;autorisation sur les clés de jointure, sans produire de produit cartésien.                                                                                                                                                     |
| `LEFT ANTI JOIN`, `RIGHT ANTI JOIN`                 | Une liste d&#39;exclusion sur les clés de jointure, sans produire de produit cartésien.                                                                                                                                                        |
| `LEFT ANY JOIN`, `RIGHT ANY JOIN`, `INNER ANY JOIN` | Désactive partiellement (pour le côté opposé de `LEFT` et `RIGHT`) ou complètement (pour `INNER`) le produit cartésien pour les types de `JOIN` standard. `ANY FULL JOIN` n&#39;est pas pris en charge.                                        |
| `ASOF JOIN`, `LEFT ASOF JOIN`                       | Joint des séquences avec une correspondance non exacte. Voir [Utilisation de ASOF JOIN](#asof-join-usage).                                                                                                                                     |
| `PASTE JOIN`                                        | Effectue une concaténation horizontale de deux tables. Voir [Utilisation de PASTE JOIN](#paste-join-usage).                                                                                                                                    |
| `INNER JOIN LATERAL`, `LEFT JOIN LATERAL`           | Joint une sous-requête qui fait référence à des colonnes des tables situées à sa gauche. Expérimental, nécessite [`enable_lateral_join`](/fr/reference/settings/session-settings/enable#enable_lateral_join). Voir [LATERAL JOIN](#lateral-join). |

Des diagrammes de chaque type de JOIN et de chaque strictness sont présentés dans [Utiliser les JOIN dans ClickHouse](/fr/concepts/features/operations/select/joining-tables#join-types-and-strictness).

<Note>
  La désactivation du paramètre `semi_join_include_columns_from_both_sides` ou `anti_join_include_columns_from_both_sides` fait que la jointure correspondante n&#39;expose que son côté préservé aux expressions résolues une fois le résultat de la jointure formé.

  * `LEFT SEMI JOIN` et `LEFT ANTI JOIN` n&#39;exposent que les colonnes du côté gauche.
  * `RIGHT SEMI JOIN` et `RIGHT ANTI JOIN` n&#39;exposent que les colonnes du côté droit.
  * Cela concerne les clauses telles que `SELECT`, `PREWHERE`, `WHERE`, `GROUP BY`, `HAVING`, `QUALIFY`, `ORDER BY` et `LIMIT BY`, y compris les jokers qualifiés comme `t1.*`.
  * L&#39;expression `ON` du même `JOIN` peut toujours faire référence aux deux côtés.

  Lorsque ces paramètres sont activés (valeur par défaut), ClickHouse conserve le comportement historique : les deux côtés restent accessibles et `SELECT *` développe les colonnes des deux tables.
</Note>

Les algorithmes de JOIN ne prennent pas tous en charge toutes les combinaisons de type de JOIN et de strictness. Les combinaisons prises en charge sont répertoriées dans [Types de JOIN pris en charge par algorithme](/fr/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).

### Réécriture de `CROSS JOIN` en `INNER JOIN` {#cross-join-rewrite}

Lorsque la clause `WHERE` d’une requête qui utilise un `CROSS JOIN` ou une liste de tables séparées par des virgules contient des conditions d’égalité entre les tables, ClickHouse peut réécrire la jointure en `INNER JOIN` en utilisant ces conditions comme clés de jointure. Le paramètre [`cross_to_inner_join_rewrite`](/fr/reference/settings/session-settings/other#cross_to_inner_join_rewrite) contrôle cette réécriture :

* `0` : la réécriture est désactivée.
* `1` : une liste de tables séparées par des virgules ou un `CROSS JOIN` est réécrit lorsque la clause `WHERE` contient une condition d’égalité entre les tables. Sinon, la jointure est exécutée en tant que `CROSS JOIN`.
* `2` : comme `1`, mais si la requête comporte une clause `WHERE`, une liste de tables séparées par des virgules qui ne peut pas être réécrite fait échouer la requête avec l’erreur `INCORRECT_QUERY`. Une jointure écrite avec les mots-clés `CROSS JOIN` qui ne peut pas être réécrite est exécutée en tant que `CROSS JOIN`.

Avec la valeur `0`, l’optimisation du plan de requête contrôlée par [`query_plan_merge_filter_into_join_condition`](/fr/reference/settings/session-settings/query-plan#query_plan_merge_filter_into_join_condition) peut malgré tout fusionner un filtre d’égalité dans la jointure et exécuter celle-ci en tant que `INNER JOIN`.

## Conditions de la section ON {#on-section-conditions}

Une section `ON` peut contenir plusieurs conditions combinées à l’aide des opérateurs `AND` et `OR`. Les conditions qui spécifient des clés de jointure doivent :

* faire référence à la fois aux tables de gauche et de droite
* utiliser l’opérateur d’égalité

Les autres conditions peuvent utiliser d’autres opérateurs et faire référence à la table de gauche ou à la table de droite d’une requête, ou aux deux.

Les lignes sont jointes si l’ensemble de la condition complexe est rempli. Si les conditions ne sont pas remplies, des lignes peuvent tout de même être incluses dans le résultat selon le type de `JOIN`. Si les mêmes conditions sont placées dans une section `WHERE` et qu’elles ne sont pas remplies, les lignes sont alors toujours exclues du résultat.

Les clés de jointure combinées avec `OR` ne sont prises en charge que par l’algorithme [`hash`](/fr/concepts/features/operations/select/join-algorithms#hash), qui construit une table de hachage distincte pour chaque argument `OR` contenant des clés de jointure.

<Note>
  Seul l’opérateur d’égalité (`=`) fait d’une condition une clé de jointure. Les autres opérateurs entre des colonnes de tables différentes sont pris en charge, mais sans aucune égalité, la jointure doit examiner chaque paire de lignes ; voir [JOIN avec une condition ON arbitraire](#join-with-an-arbitrary-on-condition).
</Note>

**Exemple**

Considérons `table_1` et `table_2` :

```response
┌─Id─┬─name─┐     ┌─Id─┬─text───────────┬─scores─┐
│  1 │ A    │     │  1 │ Text A         │     10 │
│  2 │ B    │     │  1 │ Another text A │     12 │
│  3 │ C    │     │  2 │ Text B         │     15 │
└────┴──────┘     └────┴────────────────┴────────┘
```

Requête avec une condition sur la clé de jointure et une condition supplémentaire sur `table_2` :

```sql title="Query"
SELECT name, text FROM table_1 LEFT OUTER JOIN table_2
    ON table_1.Id = table_2.Id AND startsWith(table_2.text, 'Text');
```

Le résultat contient la ligne nommée `C` ainsi que la colonne de texte vide. Elle est incluse dans le résultat, car une jointure de type `OUTER` est utilisée.

```response title="Response"
┌─name─┬─text───┐
│ A    │ Text A │
│ B    │ Text B │
│ C    │        │
└──────┴────────┘
```

Requête avec une jointure de type `INNER` et plusieurs conditions :

```sql title="Query"
SELECT name, text, scores FROM table_1 INNER JOIN table_2
    ON table_1.Id = table_2.Id AND table_2.scores > 10 AND startsWith(table_2.text, 'Text');
```

```response title="Response"
┌─name─┬─text───┬─scores─┐
│ B    │ Text B │     15 │
└──────┴────────┴────────┘
```

Requête avec une jointure de type `INNER` et une condition avec `OR` :

```sql title="Query"
CREATE TABLE t1 (`a` Int64, `b` Int64) ENGINE = MergeTree() ORDER BY a;

CREATE TABLE t2 (`key` Int32, `val` Int64) ENGINE = MergeTree() ORDER BY key;

INSERT INTO t1 SELECT number as a, -a as b from numbers(5);

INSERT INTO t2 SELECT if(number % 2 == 0, toInt64(number), -number) as key, number as val from numbers(5);

SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 1 │ -1 │   1 │
│ 2 │ -2 │   2 │
│ 3 │ -3 │   3 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

Requête avec une jointure de type `INNER` et des conditions avec `OR` et `AND` :

<Note>
  Une condition d’inégalité qui utilise des colonnes d’une seule table, comme `t1.a = t2.key AND t1.b > 0 AND t2.b > t2.c`, s’applique uniquement à cette table : `t1.b > 0` n’utilise que des colonnes de `t1` et `t2.b > t2.c` n’utilise que des colonnes de `t2`.
  Une condition d’inégalité qui compare des colonnes de tables différentes, comme `t1.a = t2.key AND t1.b > t2.key`, est également prise en charge ; consultez les sections ci-dessous.
</Note>

```sql title="Query"
SELECT a, b, val FROM t1 INNER JOIN t2 ON t1.a = t2.key OR t1.b = t2.key AND t2.val > 3;
```

```response title="Response"
┌─a─┬──b─┬─val─┐
│ 0 │  0 │   0 │
│ 2 │ -2 │   2 │
│ 4 │ -4 │   4 │
└───┴────┴─────┘
```

## JOIN avec des conditions d’inégalité sur des colonnes de tables différentes {#join-with-inequality-conditions-for-columns-from-different-tables}

En plus des conditions d’égalité, la section `ON` peut contenir des conditions qui comparent des colonnes de tables différentes à l’aide d’autres opérateurs. De telles conditions sont prises en charge avec la strictness `ALL`, `ANY`, `SEMI` et `ANTI` pour chaque type de JOIN autorisé par cette strictness. Elles ne sont pas prises en charge avec la strictness `ASOF`.

Lorsque la section `ON` contient, en plus de l’inégalité, une égalité entre les deux tables, cette égalité sert de clé de jointure et l’inégalité est vérifiée sur les lignes qu’elle a fait correspondre. Une telle condition mixte est exécutée par les algorithmes [`hash`](/fr/concepts/features/operations/select/join-algorithms#hash), [`parallel_hash`](/fr/concepts/features/operations/select/join-algorithms#parallel-hash) et [`grace_hash`](/fr/concepts/features/operations/select/join-algorithms#grace-hash). Lorsque [`inequality`](/fr/concepts/features/operations/select/join-algorithms#inequality) figure avant ces algorithmes dans [`join_algorithm`](/fr/reference/settings/session-settings/join#join_algorithm) et que la section `ON` contient deux conditions d’inégalité, c’est `inequality` qui exécute le JOIN et applique l’égalité en tant que filtre.

Lorsque la section `ON` ne contient aucune égalité entre les deux tables, il n’existe aucune clé de jointure sur laquelle effectuer la correspondance. Un tel JOIN est exécuté par [`inequality`](/fr/concepts/features/operations/select/join-algorithms#inequality) si la condition est une paire d’inégalités, et sinon sous forme de [jointure par boucles imbriquées par blocs](#join-with-an-arbitrary-on-condition).

Une condition évaluée lors de la jointure ne peut pas contenir `arrayJoin`, car elle doit préserver le nombre de lignes ; utilisez plutôt `ARRAY JOIN` dans une sous-requête.

**Exemple**

Table `t1`:

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ a    │ 1 │ 1 │ 2 │
│ key1 │ b    │ 2 │ 3 │ 2 │
│ key1 │ c    │ 3 │ 2 │ 1 │
│ key1 │ d    │ 4 │ 7 │ 2 │
│ key1 │ e    │ 5 │ 5 │ 5 │
│ key2 │ a2   │ 1 │ 1 │ 1 │
│ key4 │ f    │ 2 │ 3 │ 4 │
└──────┴──────┴───┴───┴───┘
```

Table `t2`

```response
┌─key──┬─attr─┬─a─┬─b─┬─c─┐
│ key1 │ A    │ 1 │ 2 │ 1 │
│ key1 │ B    │ 2 │ 1 │ 2 │
│ key1 │ C    │ 3 │ 4 │ 5 │
│ key1 │ D    │ 4 │ 1 │ 6 │
│ key3 │ a3   │ 1 │ 1 │ 1 │
│ key4 │ F    │ 1 │ 1 │ 1 │
└──────┴──────┴───┴───┴───┘
```

```sql
SELECT t1.*, t2.* FROM t1 LEFT JOIN t2 ON t1.key = t2.key AND (t1.a < t2.a) ORDER BY (t1.key, t1.attr, t2.key, t2.attr);
```

```response
key1    a    1    1    2    key1    B    2    1    2
key1    a    1    1    2    key1    C    3    4    5
key1    a    1    1    2    key1    D    4    1    6
key1    b    2    3    2    key1    C    3    4    5
key1    b    2    3    2    key1    D    4    1    6
key1    c    3    2    1    key1    D    4    1    6
key1    d    4    7    2            0    0    \N
key1    e    5    5    5            0    0    \N
key2    a2    1    1    1            0    0    \N
key4    f    2    3    4            0    0    \N
```

## JOIN avec une condition ON arbitraire {#join-with-an-arbitrary-on-condition}

La section `ON` peut contenir une expression booléenne arbitraire portant sur les colonnes des deux tables, par exemple une vérification de plage, une comparaison arithmétique ou un appel à une fonction scalaire. Lorsqu&#39;elle ne contient aucune égalité entre les deux tables, il n&#39;existe aucune clé de jointure sur laquelle faire correspondre les lignes. Une paire de conditions d&#39;inégalité est exécutée par `inequality` dès lors que cet algorithme figure dans [`join_algorithm`](/fr/reference/settings/session-settings/join#join_algorithm), sans qu&#39;il doive nécessairement apparaître en premier, car aucune autre valeur de `join_algorithm` ne permet d&#39;exécuter une telle condition. La valeur par défaut de `join_algorithm` inclut `inequality` depuis la version 26.8. Toute autre condition est exécutée sous la forme d&#39;une [jointure par boucles imbriquées par blocs](https://en.wikipedia.org/wiki/Nested_loop_join) : la table de droite est matérialisée, puis la condition est évaluée sur chaque paire de lignes. Un `ALL INNER JOIN` prend alors la forme équivalente d&#39;un `CROSS JOIN` dont la condition sert de filtre.

La jointure par boucles imbriquées par blocs prend en charge tous les types de JOIN et toutes les strictness, à l&#39;exception de `ASOF JOIN`, `PASTE JOIN` et `ANY FULL JOIN`. Elle ne fait pas partie des valeurs de `join_algorithm` : il s&#39;agit d&#39;une solution de dernier recours, utilisée uniquement lorsqu&#39;aucun autre algorithme ne peut exécuter la condition. Dans la sortie de `EXPLAIN`, elle apparaît sous la forme d&#39;une étape `BlockNestedLoopJoin`. Lorsque [`allow_block_nested_loop_join`](/fr/reference/settings/session-settings/allow#allow_block_nested_loop_join) est désactivé, toute requête qui en aurait besoin est rejetée avec l&#39;erreur `INVALID_JOIN_ON_EXPRESSION`.

**Exemple**

```sql title="Query"
CREATE TABLE orders (id UInt32, amount UInt32) ENGINE = Memory;
CREATE TABLE discounts (min_amount UInt32, max_amount UInt32, pct UInt32) ENGINE = Memory;

INSERT INTO orders VALUES (1, 50), (2, 150), (3, 300);
INSERT INTO discounts VALUES (100, 199, 5), (200, 1000, 10);

SELECT o.id, o.amount, d.pct
FROM orders AS o
LEFT JOIN discounts AS d ON o.amount BETWEEN d.min_amount AND d.max_amount
ORDER BY o.id;
```

```response title="Response"
┌─id─┬─amount─┬─pct─┐
│  1 │     50 │   0 │
│  2 │    150 │   5 │
│  3 │    300 │  10 │
└────┴────────┴─────┘
```

La ligne sans correspondance est complétée selon [`join_use_nulls`](/fr/reference/settings/session-settings/join#join_use_nulls), comme pour toute autre jointure : avec une valeur par défaut dans l&#39;exemple ci-dessus, et avec `NULL` lorsque le paramètre est activé.

**Strictness**

`ANY` et `SEMI` conservent normalement une ligne par groupe de lignes partageant une clé de jointure. Comme un tel groupe n&#39;existe pas ici, ils conservent une ligne par ligne de la table qui pilote la jointure : `LEFT ANY` et `LEFT SEMI` émettent chaque ligne de gauche au plus une fois, `RIGHT ANY` et `RIGHT SEMI` chaque ligne de droite au plus une fois. `ANY INNER` limite les deux côtés à la fois : chaque ligne de l&#39;une ou l&#39;autre table est utilisée au plus une fois, de sorte que l’ensemble de résultats contient au plus autant de lignes que la plus petite des deux tables. Les paires qui composent un tel ensemble de résultats sont arbitraires, comme le sous-entend précisément `ANY`, et peuvent varier d&#39;une exécution à l&#39;autre de la même requête. Pour `ANY INNER`, cela vaut aussi pour le nombre de lignes : apparier de manière gloutonne chaque ligne des deux côtés, quel que soit l&#39;ordre dans lequel les lignes sont examinées, peut laisser un nombre variable de lignes non appariées. L’ensemble de résultats de `count()` sur une jointure `ANY INNER` sans clé de jointure n&#39;est donc pas reproductible et dépend du nombre de threads ainsi que de l&#39;ordre physique de la table de droite.

**Performances**

Une jointure par boucles imbriquées par blocs examine chaque paire de lignes : son coût croît donc avec le produit des nombres de lignes des deux tables, comme décrit dans [Repli sur la jointure par boucles imbriquées par blocs](/fr/concepts/features/operations/select/join-algorithms#block-nested-loop-fallback). La table de droite matérialisée est soumise aux limites strictes et aux seuils de déversement sur disque décrits dans [Gestion de la mémoire et déversement sur disque des JOIN](/fr/concepts/features/operations/select/join-memory-management).

## Valeurs NULL et NaN dans les clés de jointure {#null-values-in-join-keys}

`NULL` n’est égal à aucune valeur, pas même à lui-même. Si une clé de JOIN contient une valeur `NULL` dans une table, elle ne correspond pas à une valeur `NULL` dans l’autre table. Si les clés de JOIN sont des colonnes [Nullable](/fr/reference/data-types/nullable), une ligne dont au moins une des clés est [NULL](/fr/reference/syntax#null) n’est pas incluse dans la jointure.

**Exemple**

Table `A` :

```response
┌───id─┬─name────┐
│    1 │ Alice   │
│    2 │ Bob     │
│ ᴺᵁᴸᴸ │ Charlie │
└──────┴─────────┘
```

Table `B` :

```response
┌───id─┬─score─┐
│    1 │    90 │
│    3 │    85 │
│ ᴺᵁᴸᴸ │    88 │
└──────┴───────┘
```

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON A.id = B.id
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │     0 │
└─────────┴───────┘
```

La ligne avec `Charlie` de la table `A` et la ligne avec le score 88 de la table `B` ne trouvent pas de correspondance en raison de la valeur `NULL` dans la clé de JOIN.

Les lignes sans correspondance reçoivent la valeur `0` dans la colonne `score`, comme décrit dans [Traitement des cellules vides ou NULL](#processing-of-empty-or-null-cells).

Pour faire correspondre des valeurs `NULL`, comparez les clés de JOIN à l’aide de la fonction `isNotDistinctFrom` :

```sql
SELECT A.name, B.score FROM A LEFT JOIN B ON isNotDistinctFrom(A.id, B.id)
```

```response
┌─name────┬─score─┐
│ Alice   │    90 │
│ Bob     │     0 │
│ Charlie │    88 │
└─────────┴───────┘
```

Les valeurs `NaN` dans les clés de JOIN de type flottant ne suivent pas la règle relative à `NULL` ci-dessus.
La comparaison scalaire de deux valeurs `NaN` (`NaN = NaN`) renvoie `0`. Toutefois, les clés de JOIN ne sont pas comparées selon une sémantique scalaire, et des clés `NaN` peuvent correspondre.
Le fait qu’elles correspondent ou non n’est pas spécifié : cela dépend de l’algorithme de JOIN, du type de clé et des paramètres de session.
Pour empêcher les clés `NaN` de correspondre, mappez-les à des valeurs `NULL`, par exemple `ON if(isNaN(A.id), NULL, A.id) = B.id`.
Dans un `ASOF JOIN`, la colonne de correspondance la plus proche est comparée selon l’ordre, qui n’est pas défini pour les valeurs `NaN`.

## Conversion implicite de type {#implicit-type-conversion}

Lorsque les clés de jointure de la table de gauche et de la table de droite sont de types différents, ClickHouse les convertit vers leur plus petit supertype commun avant de les comparer. Cela s’applique à tous les types de JOIN et à toutes les strictness :

* Avec `ON`, la conversion ne s’applique qu’à la comparaison. Les colonnes de clé conservent leurs types d’origine dans l’ensemble de résultats.
* Avec `USING`, la colonne fusionnée prend le type commun dans l’ensemble de résultats. Lorsque `semi_join_include_columns_from_both_sides` ou `anti_join_include_columns_from_both_sides` est désactivé, la colonne fusionnée d’un `SEMI JOIN` ou d’un `ANTI JOIN` conserve le type de la table préservée.

Si les types de clé n’ont aucun supertype commun et qu’il s’agit dans les deux cas de types entiers ou de tuples de types entiers, comme c’est le cas pour `UInt64` et `Int64`, ClickHouse convertit les deux clés vers un type capable de contenir les valeurs communes aux deux types de clé. Pour `UInt64` et `Int64`, ce type est `UInt64`. Une valeur de clé que ce type ne peut pas représenter ne correspond à aucune valeur. Cette conversion s’applique aux conditions d’égalité dans `ON`, à l’exception de `isNotDistinctFrom`, ainsi qu’à `USING` dans un `INNER JOIN` ou un `SEMI JOIN`. Elle ne s’applique pas à la condition de correspondance la plus proche d’un `ASOF JOIN`, aux conditions d’inégalité exécutées par `inequality`, ni à `USING` dans les autres JOIN, car leur colonne de l’ensemble de résultats doit également pouvoir contenir les valeurs sans correspondance. Cette conversion est disponible depuis la version 26.9.

Si les types de clé n’ont aucun supertype commun et que cette conversion ne s’applique pas, comme c’est le cas pour `String` et `Int32` ou pour `UInt64` et `Float64`, la requête échoue avec une exception, par exemple `NO_COMMON_TYPE`.

**Exemple**

Considérez la table `t_1` :

```response
┌─a─┬─b─┬─toTypeName(a)─┬─toTypeName(b)─┐
│ 1 │ 1 │ UInt16        │ UInt8         │
│ 2 │ 2 │ UInt16        │ UInt8         │
└───┴───┴───────────────┴───────────────┘
```

et la table `t_2` :

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int16         │ Nullable(Int64) │
│  1 │   -1 │ Int16         │ Nullable(Int64) │
│  1 │    1 │ Int16         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

La requête

```sql
SELECT a, b, toTypeName(a), toTypeName(b) FROM t_1 FULL JOIN t_2 USING (a, b) ORDER BY ALL;
```

renvoie l’ensemble suivant :

```response
┌──a─┬────b─┬─toTypeName(a)─┬─toTypeName(b)───┐
│ -1 │    1 │ Int32         │ Nullable(Int64) │
│  1 │   -1 │ Int32         │ Nullable(Int64) │
│  1 │    1 │ Int32         │ Nullable(Int64) │
│  2 │    2 │ Int32         │ Nullable(Int64) │
└────┴──────┴───────────────┴─────────────────┘
```

## Utilisation de ASOF JOIN {#asof-join-usage}

`ASOF JOIN` joint des enregistrements qui n’ont pas de correspondance exacte. `ASOF` est une strictness de JOIN qui se combine avec un JOIN `INNER` ou `LEFT`. Il ne s’agit pas d’un algorithme de jointure.

Un `ASOF JOIN` nécessite, dans les deux tables, une colonne servant à la correspondance la plus proche. Cette colonne :

* Doit avoir un type doté d’un ordre défini.
* Avec l’algorithme [`hash`](/fr/concepts/features/operations/select/join-algorithms#hash), peut être de l’un des types suivants : [Int, UInt](/fr/reference/data-types/int-uint), [Float](/fr/reference/data-types/float), [Decimal](/fr/reference/data-types/decimal), [Date](/fr/reference/data-types/date), [Date32](/fr/reference/data-types/date32), [DateTime](/fr/reference/data-types/datetime), [DateTime64](/fr/reference/data-types/datetime64), [Time](/fr/reference/data-types/time), [Enum](/fr/reference/data-types/enum), [Bool](/fr/reference/data-types/boolean), ainsi que [Nullable](/fr/reference/data-types/nullable) de ces types. Les autres types, tels que `String` et `Time64`, sont rejetés avec l’erreur `BAD_TYPE_OF_FIELD`.
* Avec l’algorithme [`full_sorting_merge`](/fr/concepts/features/operations/select/join-algorithms#full-sorting-merge), peut également être d’autres types comparables, tels que `String`.
* Avec l’algorithme `hash`, ne peut pas être la seule colonne de la clause `JOIN` : au moins une condition d’égalité est requise. L’algorithme `full_sorting_merge` n’impose pas cette contrainte.

Syntaxe `ASOF JOIN ... ON` :

```sql
SELECT expressions_list
FROM table_1
ASOF LEFT JOIN table_2
ON equi_cond AND closest_match_cond
```

Vous pouvez utiliser autant de conditions d’égalité que nécessaire et exactement une condition de correspondance la plus proche. Par exemple, `SELECT count() FROM table_1 ASOF LEFT JOIN table_2 ON table_1.a == table_2.b AND table_2.t <= table_1.t`.

Conditions prises en charge pour la correspondance la plus proche : `>`, `>=`, `<`, `<=`.

Syntaxe `ASOF JOIN ... USING` :

```sql
SELECT expressions_list
FROM table_1
ASOF JOIN table_2
USING (equi_column1, ... equi_columnN, asof_column)
```

`ASOF JOIN` utilise `equi_columnX` pour les correspondances exactes et `asof_column` pour la correspondance la plus proche avec la condition `table_1.asof_column >= table_2.asof_column`. La colonne `asof_column` est toujours la dernière de la clause `USING`.

Par exemple, considérons les tables suivantes :

```text
         table_1                           table_2
      event   | ev_time | user_id       event   | ev_time | user_id
    ----------|---------|----------   ----------|---------|----------
                  ...                               ...
    event_1_1 |  12:00  |  42         event_2_1 |  11:59  |   42
                  ...                 event_2_2 |  12:30  |   42
    event_1_2 |  13:00  |  42         event_2_3 |  13:00  |   42
                  ...                               ...
```

`ASOF JOIN` peut prendre le timestamp d’un événement utilisateur de `table_1` et trouver un événement dans `table_2` dont le timestamp est le plus proche de celui de l’événement de `table_1`, selon la condition de correspondance la plus proche. Des valeurs de timestamp identiques sont considérées comme les plus proches lorsqu’elles sont disponibles. Ici, la colonne `user_id` peut être utilisée pour une jointure par égalité, et la colonne `ev_time` pour une jointure sur la correspondance la plus proche. Dans notre exemple, `event_1_1` peut être joint à `event_2_1` et `event_1_2` à `event_2_3`, mais `event_2_2` ne peut pas être joint.

<Note>
  Parmi les algorithmes de jointure, seuls [`hash`](/fr/concepts/features/operations/select/join-algorithms#hash) et [`full_sorting_merge`](/fr/concepts/features/operations/select/join-algorithms#full-sorting-merge) prennent en charge la rigueur (strictness) `ASOF`. Voir [Types de JOIN pris en charge par algorithme](/fr/concepts/features/operations/select/join-algorithms#supported-join-types-per-algorithm).
  `ASOF` n’est **pas** pris en charge par le moteur de table [Join](/fr/reference/engines/table-engines/special/join).
</Note>

## Utilisation de PASTE JOIN {#paste-join-usage}

Le résultat de `PASTE JOIN` est une table qui contient toutes les colonnes de la sous-requête de gauche, suivies de toutes les colonnes de la sous-requête de droite.
Les lignes sont appariées en fonction de leur position dans les tables d&#39;origine (l&#39;ordre des lignes doit être défini).
Si les sous-requêtes renvoient un nombre différent de lignes, les lignes supplémentaires seront tronquées.

Exemple :

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers(2)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(2)
    ORDER BY a DESC
) AS t2

┌─a─┬─t2.a─┐
│ 0 │    1 │
│ 1 │    0 │
└───┴──────┘
```

Note : dans ce cas, le résultat peut être non déterministe si la lecture s’effectue en parallèle. Par exemple :

```sql
SELECT *
FROM
(
    SELECT number AS a
    FROM numbers_mt(5)
) AS t1
PASTE JOIN
(
    SELECT number AS a
    FROM numbers(10)
    ORDER BY a DESC
) AS t2
SETTINGS max_block_size = 2;

┌─a─┬─t2.a─┐
│ 2 │    9 │
│ 3 │    8 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 0 │    7 │
│ 1 │    6 │
└───┴──────┘
┌─a─┬─t2.a─┐
│ 4 │    5 │
└───┴──────┘
```

## LATERAL JOIN {#lateral-join}

`JOIN LATERAL` permet à la sous-requête située du côté droit d&#39;une jointure de référencer des colonnes des expressions
de table situées à sa gauche. Tout se passe comme si la sous-requête était évaluée pour chaque combinaison distincte
des valeurs de colonne du côté gauche qu&#39;elle référence, et que son ensemble de résultats était joint à chaque ligne de gauche présentant cette combinaison :

```sql
SELECT ...
FROM <left_table>
[INNER|LEFT] JOIN LATERAL (SELECT ... WHERE <expr referencing left_table>) AS <alias> ON true
```

Le prédicat `ON true` est obligatoire, comme pour toute autre jointure `INNER` ou `LEFT JOIN` ; son omission provoque une erreur de syntaxe.

Elle est disponible depuis la version 26.10. Elle est expérimentale et désactivée par défaut ; activez-la avec le paramètre
[`enable_lateral_join`](/fr/reference/settings/session-settings/enable#enable_lateral_join).

La sous-requête latérale n&#39;est exécutée ni une fois par ligne de gauche, ni une fois par combinaison distincte. Comme les autres sous-requêtes
corrélées, elle est décorrélée en une seule requête portant sur toutes les lignes de gauche : les colonnes de gauche qu&#39;elle référence sont
ajoutées à ses clés `GROUP BY` si elle effectue une agrégation, sa clause `LIMIT` (le cas échéant) devient un `LIMIT ... BY` sur ces colonnes, et son
ensemble de résultats est joint aux lignes de gauche sur ces mêmes colonnes. Lorsque la corrélation est une simple égalité, telle que `orders.user_id = u.id`,
la colonne de gauche peut être remplacée par la colonne qui lui est égale dans la sous-requête
(`correlated_subqueries_substitute_equivalent_expressions`, activé par défaut), ce qui peut permettre à la sous-requête de ne pas
lire les lignes de gauche. Ce n&#39;est toutefois pas garanti : par exemple, un agrégat sans `GROUP BY` (comme `count`) lit tout de même
les valeurs distinctes de gauche afin de produire son résultat pour les valeurs de gauche sans ligne correspondante. Chaque fois que les valeurs distinctes
de gauche sont transmises à la sous-requête, elles passent, avec les paramètres par défaut, par un tampon en mémoire, et ce n&#39;est que
lorsqu&#39;un tel tampon est effectivement utilisé que la jointure est systématiquement une jointure de hachage. Dans tous les autres cas, par exemple lorsque la substitution
par égalité évite la lecture des lignes de gauche ou que le tampon est désactivé
(`correlated_subqueries_use_in_memory_buffer = 0` ou `correlated_subqueries_default_join_kind = 'left'`),
l&#39;algorithme est déterminé par le paramètre `join_algorithm`. Par exemple, la sortie d&#39;`EXPLAIN` pour une sous-requête latérale avec `LIMIT`
affiche une étape `Join` au-dessus d&#39;une étape `LimitBy (LIMIT BY for decorrelated correlated subquery)` ; une sous-requête sans
`LIMIT` ne comporte pas cette étape.

Seul le sous-ensemble suivant est pris en charge pour le moment ; tout le reste est rejeté avec une erreur :

* Uniquement `INNER JOIN LATERAL` et `LEFT JOIN LATERAL` ; les jointures `RIGHT`, `FULL`, `PASTE` et `NATURAL` ne sont pas prises en charge, et `LATERAL` ne peut en aucun cas être combiné avec une jointure `CROSS` ou une jointure par virgule.
* Uniquement la strictness `ALL` par défaut ; `ANY`, `SEMI`, `ANTI` et `ASOF` ne sont pas pris en charge.
* Aucun prédicat de jointure autre que `ON true` (`ON 1` est également accepté) ; `USING` n&#39;est pas pris en charge, et le prédicat
  ne peut pas être omis. Placez les filtres qui relient les deux côtés dans la clause `WHERE` de la sous-requête latérale.
* Les modificateurs de jointure `GLOBAL` et `LOCAL` ne sont pas pris en charge.
* La sous-requête latérale doit référencer au moins une colonne du côté gauche. Pour une
  sous-requête non corrélée, utilisez une jointure classique.
* Comme la sous-requête latérale est décorrélée au lieu d&#39;être évaluée séparément pour chaque valeur de gauche, elle
  ne doit pas contenir de fonctions non déterministes au sein d&#39;une requête, telles que
  `rand` ou `generateUUIDv4`, ni de fonctions de table générant des lignes aléatoires, telles que `generateRandom`.
  Les fonctions constantes au sein d&#39;une requête, telles que `now`, sont autorisées.
* Seule une sous-requête est prise en charge comme expression de table latérale. Les formes de source de table PostgreSQL
  `LATERAL unnest(...)` et `CROSS JOIN UNNEST(...)` ne sont pas prises en charge. Utilisez plutôt la clause
  [`ARRAY JOIN`](/fr/reference/statements/select/array-join).
* Les clauses `GROUP BY` et `ORDER BY` de la sous-requête latérale s&#39;exécutent une seule fois pour l&#39;ensemble des valeurs de gauche ; les limites
  `max_rows_to_group_by`, `max_rows_to_sort` et `max_bytes_to_sort` comptabilisent donc les lignes de toutes les valeurs de gauche,
  et non d&#39;une seule. Elles ne sont prises en charge qu&#39;avec le mode de dépassement de capacité `throw` ; `any` et `break` sont rejetés.
* Le résultat de la sous-requête décorrélée est mis en correspondance avec les lignes de gauche par une seule jointure. Comme pour toute jointure de hachage,
  `max_rows_in_join` et `max_bytes_in_join` limitent le côté de cette jointure conservé en mémoire, et c&#39;est le
  planificateur qui choisit ce côté : lorsque le tampon en mémoire décrit ci-dessus est effectivement utilisé, il s&#39;agit du côté gauche
  de `JOIN LATERAL`, car les lignes de gauche doivent être entièrement lues avant l&#39;évaluation de la sous-requête latérale ; sinon, il peut s&#39;agir du résultat de la sous-requête décorrélée. Les limites sont toujours
  appliquées comme si `join_overflow_mode` valait `throw` : avec `break`, la jointure supprimerait silencieusement des lignes de gauche sans rapport.

**Exemple**

```sql
SELECT u.id, o.total
FROM users AS u
LEFT JOIN LATERAL
(
    SELECT total
    FROM orders
    WHERE orders.user_id = u.id
    ORDER BY total DESC
    LIMIT 1
) AS o ON true
SETTINGS enable_lateral_join = 1;
```

## JOIN distribué {#distributed-join}

Il existe deux façons d’exécuter un JOIN impliquant des tables distribuées :

* Lorsqu’on utilise un `JOIN` normal, la requête est envoyée aux serveurs distants. Les sous-requêtes sont exécutées sur chacun d’eux afin de constituer la table de droite, puis le JOIN est effectué avec cette table. Autrement dit, la table de droite est constituée séparément sur chaque serveur.
* Lorsqu’on utilise `GLOBAL ... JOIN`, le serveur à l’origine de la requête exécute d’abord une sous-requête pour calculer l’un des côtés du JOIN et rassemble le résultat dans une table temporaire. Cette table temporaire est ensuite transmise à chaque serveur distant, et les requêtes y sont exécutées à l’aide des données temporaires transmises. Pour les JOIN `LEFT` et `INNER`, la table de droite est calculée par la sous-requête.

Pour un `GLOBAL RIGHT JOIN` avec une strictness `ALL`, `ANY`, `SEMI` ou `ANTI` dont la table de gauche est une table `Distributed` comportant plus d’un shard, ClickHouse inverse les deux côtés et exécute le JOIN sous forme de `LEFT JOIN`, de sorte que les lignes de la table de droite conservée ne soient renvoyées qu’une seule fois. La table de gauche est alors calculée par la sous-requête, et la table de droite est lue depuis ses shards s’il s’agit d’une table `Distributed` comportant plusieurs shards, ou sur le serveur à l’origine de la requête dans le cas contraire. Un `GLOBAL RIGHT JOIN` ou un `GLOBAL FULL JOIN` dont les côtés ne peuvent pas être inversés de cette manière est exécuté sur le serveur à l’origine de la requête. Ce comportement s’applique à partir de la version 26.9.

Soyez prudent lorsque vous utilisez `GLOBAL`. Pour plus d’informations, consultez la section [Sous-requêtes distribuées](/fr/reference/statements/in#distributed-subqueries).

## Traitement des cellules vides ou NULL {#processing-of-empty-or-null-cells}

Dans le résultat d&#39;une jointure externe (OUTER JOIN), les colonnes de l&#39;autre table sont vides pour toute ligne sans correspondance. Le paramètre [`join_use_nulls`](/fr/reference/settings/session-settings/join#join_use_nulls) détermine la manière dont ClickHouse remplit ces cellules :

* `0` : les cellules sont remplies avec la valeur par défaut du type de colonne.
* `1` : les cellules sont remplies avec `NULL`, et les types de ces colonnes sont convertis en [Nullable](/fr/reference/data-types/nullable). Une colonne dont le type ne peut pas être encapsulé dans `Nullable`, comme `Array`, conserve son type et est remplie avec la valeur par défaut. Dans une jointure `FULL` JOIN, la colonne `USING` fusionnée est également convertie en `Nullable`.

Une ligne dont au moins une des clés de jointure vaut `NULL` n&#39;est pas jointe, comme décrit dans la section [Valeurs NULL et NaN dans les clés de jointure](#null-values-in-join-keys).

## Clause USING {#using-clause}

La clause `USING` indique une ou plusieurs colonnes sur lesquelles effectuer la jointure et établit l&#39;égalité entre ces colonnes :

* Chaque colonne doit exister sous le même nom dans l&#39;expression de table de gauche et dans celle de droite. Les alias définis dans les sous-requêtes permettent de donner le même nom à des colonnes.
* La clause `USING` n&#39;accepte que des noms de colonnes. Les expressions ne sont pas prises en charge.
* La liste de colonnes peut être écrite avec ou sans parenthèses.
* Chaque colonne de la clause `USING` n&#39;apparaît qu&#39;une seule fois dans l&#39;ensemble de résultats. Son type est décrit dans [Conversion de type implicite](#implicit-type-conversion).
* D&#39;autres colonnes peuvent porter le même nom dans les deux tables. `SELECT *` qualifie la colonne de la table de droite avec le nom de table ou l&#39;alias, et un nom non qualifié est résolu vers la colonne de la table de gauche lorsque [`single_join_prefer_left_table`](/fr/reference/settings/session-settings/other#single_join_prefer_left_table) est activé.
* Lorsque [`analyzer_compatibility_join_using_top_level_identifier`](/fr/reference/settings/session-settings/analyzer-compatibility#analyzer_compatibility_join_using_top_level_identifier) est activé, un nom de colonne dans `USING` est résolu à partir d&#39;un alias du même nom dans la requête, par exemple un alias de la liste `SELECT`.

## Exemples {#examples}

La requête suivante joint le nombre de hits par compteur au nombre de visits par compteur. La clause `ANY LEFT JOIN` renvoie chaque ligne de la sous-requête de gauche une seule fois, et un compteur sans visites prend la valeur par défaut `0` :

```sql title="Query"
SELECT
    CounterID,
    hits,
    visits
FROM
(
    SELECT
        CounterID,
        count() AS hits
    FROM VALUES('CounterID UInt32', 1, 1, 1, 2, 2, 3)
    GROUP BY CounterID
) AS h
ANY LEFT JOIN
(
    SELECT
        CounterID,
        sum(Sign) AS visits
    FROM VALUES('CounterID UInt32, Sign Int8', (1, 1), (1, 1), (1, -1), (2, 1), (4, 1))
    GROUP BY CounterID
) AS v USING (CounterID)
ORDER BY hits DESC;
```

```response title="Response"
┌─CounterID─┬─hits─┬─visits─┐
│         1 │    3 │      1 │
│         2 │    2 │      1 │
│         3 │    1 │      0 │
└───────────┴──────┴────────┘
```
