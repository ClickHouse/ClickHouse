## Description {#description}

Cette table contient des données de profilage au niveau des processeurs (que vous pouvez retrouver dans [`EXPLAIN PIPELINE`](/fr/reference/statements/explain#explain-pipeline)).

Vous pouvez tronquer ou supprimer cette table à tout moment sans risque.

## Colonnes {#columns}

* `hostname` ([LowCardinality(String)](/fr/reference/data-types/lowcardinality)) — Nom d’hôte du serveur qui exécute la requête.
* `clickhouse_version` ([LowCardinality(String)](/fr/reference/data-types/lowcardinality)) — Version du serveur ClickHouse qui a produit la ligne.
* `system_processor` ([LowCardinality(String)](/fr/reference/data-types/lowcardinality)) — Architecture CPU du serveur ClickHouse qui a produit la ligne.
* `event_date` ([Date](/fr/reference/data-types/date)) — Date à laquelle l’événement s’est produit.
* `event_time` ([DateTime](/fr/reference/data-types/datetime)) — Date et heure auxquelles l’événement s’est produit.
* `event_time_microseconds` ([DateTime64(6)](/fr/reference/data-types/datetime64)) — Date et heure, avec une précision à la microseconde, auxquelles l’événement s’est produit.
* `id` ([UInt64](/fr/reference/data-types/int-uint)) — ID du processeur, unique au sein de la requête. Il s’agit du nombre figurant dans `processor_uniq_id`.
* `parent_ids` ([Array(UInt64)](/fr/reference/data-types/array)) — ID des processeurs parents.
* `plan_step` ([UInt64](/fr/reference/data-types/int-uint)) — ID de l’étape du plan de requête qui a créé ce processeur, unique au sein de la requête. Il correspond au nombre figurant dans `step_uniq_id`, augmenté de un. La valeur est égale à zéro si le processeur n’a été ajouté par aucune étape.
* `plan_step_name` ([String](/fr/reference/data-types/string)) — Nom de l’étape du plan de requête qui a créé ce processeur. La valeur est vide si le processeur n’a été ajouté par aucune étape.
* `plan_step_description` ([String](/fr/reference/data-types/string)) — Description de l’étape du plan de requête qui a créé ce processeur. La valeur est vide si le processeur n’a été ajouté par aucune étape.
* `plan_group` ([UInt64](/fr/reference/data-types/int-uint)) — Groupe du processeur s’il a été créé par une étape du plan de requête. Un groupe correspond à un partitionnement logique des processeurs ajoutés par la même étape du plan de requête. Il est utilisé uniquement pour rendre plus lisible le résultat de EXPLAIN PIPELINE.
* `initial_query_id` ([String](/fr/reference/data-types/string)) — ID de la requête initiale dans la même chaîne de requêtes.
* `query_id` ([String](/fr/reference/data-types/string)) — ID de la requête.
* `name` ([LowCardinality(String)](/fr/reference/data-types/lowcardinality)) — Nom du processeur.
* `elapsed_us` ([UInt64](/fr/reference/data-types/int-uint)) — Nombre de microsecondes pendant lesquelles ce processeur a été exécuté.
* `input_wait_elapsed_us` ([UInt64](/fr/reference/data-types/int-uint)) — Nombre de microsecondes pendant lesquelles ce processeur a attendu des données (provenant d’un autre processeur).
* `output_wait_elapsed_us` ([UInt64](/fr/reference/data-types/int-uint)) — Nombre de microsecondes pendant lesquelles ce processeur a attendu parce que le port de sortie était plein.
* `input_rows` ([UInt64](/fr/reference/data-types/int-uint)) — Nombre de lignes consommées par le processeur.
* `input_bytes` ([UInt64](/fr/reference/data-types/int-uint)) — Nombre d’octets consommés par le processeur.
* `output_rows` ([UInt64](/fr/reference/data-types/int-uint)) — Nombre de lignes générées par le processeur.
* `output_bytes` ([UInt64](/fr/reference/data-types/int-uint)) — Nombre d’octets générés par le processeur.
* `processor_uniq_id` ([String](/fr/reference/data-types/string)) — ID unique du processeur dans le pipeline.
* `step_uniq_id` ([String](/fr/reference/data-types/string)) — ID unique de l’étape dans le plan.
* `exception_code` ([Int32](/fr/reference/data-types/int-uint)) — Code de l’exception si la requête a échoué, sinon 0.
* `exception` ([String](/fr/reference/data-types/string)) — Message de l’exception si la requête a échoué, sinon vide.

## Exemple {#example}

```sql title="Query"
EXPLAIN PIPELINE
SELECT sleep(1)
┌─explain─────────────────────────┐
│ (Expression)                    │
│ ExpressionTransform             │
│   (SettingQuotaAndLimits)       │
│     (ReadFromStorage)           │
│     SourceFromSingleChunk 0 → 1 │
└─────────────────────────────────┘

SELECT sleep(1)
SETTINGS log_processors_profiles = 1
Query id: feb5ed16-1c24-4227-aa54-78c02b3b27d4
┌─sleep(1)─┐
│        0 │
└──────────┘
1 rows in set. Elapsed: 1.018 sec.

SELECT
    name,
    elapsed_us,
    input_wait_elapsed_us,
    output_wait_elapsed_us
FROM system.processors_profile_log
WHERE query_id = 'feb5ed16-1c24-4227-aa54-78c02b3b27d4'
ORDER BY name ASC
```

```text title="Response"
┌─name────────────────────┬─elapsed_us─┬─input_wait_elapsed_us─┬─output_wait_elapsed_us─┐
│ ExpressionTransform     │    1000497 │                  2823 │                    197 │
│ LazyOutputFormat        │         36 │               1002188 │                      0 │
│ LimitsCheckingTransform │         10 │               1002994 │                    106 │
│ NullSource              │          5 │               1002074 │                      0 │
│ NullSource              │          1 │               1002084 │                      0 │
│ SourceFromSingleChunk   │         45 │                  4736 │                1000819 │
└─────────────────────────┴────────────┴───────────────────────┴────────────────────────┘
```

Ici, vous pouvez voir :

* `ExpressionTransform` exécutait la fonction `sleep(1)`, donc son `work` prendra 1e6, et `elapsed_us` &gt; 1e6.
* `SourceFromSingleChunk` doit attendre, car `ExpressionTransform` n’accepte aucune donnée pendant l’exécution de `sleep(1)` ; il sera donc dans l’état `PortFull` pendant 1e6 us, et `output_wait_elapsed_us` &gt; 1e6.
* `LimitsCheckingTransform`/`NullSource`/`LazyOutputFormat` doivent attendre que `ExpressionTransform` exécute `sleep(1)` pour traiter le résultat, donc `input_wait_elapsed_us` &gt; 1e6.

### Profilage d’une jointure {#profiling-a-join}

Lorsqu’une requête lit plusieurs tables, chaque table dispose de son propre pipeline de lecture, et les lignes traversent de nombreux processeurs avant d’atteindre l’ensemble de résultats.
Additionner `input_rows` ou `output_rows` sur l’ensemble des processeurs revient donc à compter plusieurs fois les mêmes lignes, sans indiquer la quantité de données lue dans chaque table.
L’exemple suivant utilise deux tables `MergeTree` de tailles différentes sur un serveur unique.

```sql title="Query"
CREATE TABLE big (id UInt64, v UInt64) ENGINE = MergeTree ORDER BY id;
CREATE TABLE small (id UInt64, w UInt64) ENGINE = MergeTree ORDER BY id;

INSERT INTO big SELECT number, number FROM numbers(1000000);
INSERT INTO small SELECT number, number FROM numbers(1000);

EXPLAIN PIPELINE
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0;
```

`EXPLAIN PIPELINE` affiche un pipeline de lecture pour chaque côté de la jointure (`ReadFromMergeTree`, avec des sources `MergeTreeSelect` en dessous), reliés entre eux par les processeurs de jointure. `join_algorithm = 'hash'` et `enable_join_runtime_filters = 0` garantissent la reproductibilité de cet exemple : un filtre d’exécution de jointure ne peut pas élaguer `big` avant que sa source n’ait émis des lignes.

```sql title="Query"
SELECT count()
FROM big AS b
INNER JOIN small AS s ON b.id = s.id
SETTINGS join_algorithm = 'hash', enable_join_runtime_filters = 0, log_processors_profiles = 1;
-- Note the query ID printed by the client, or look it up in `system.query_log`.

SYSTEM FLUSH LOGS;

SELECT
    id,
    parent_ids,
    plan_step,
    name,
    plan_step_name,
    plan_step_description,
    input_rows,
    output_rows,
    elapsed_us
FROM system.processors_profile_log
WHERE query_id = '<query_id>'
ORDER BY plan_step, id;
```

Pour interpréter l’ensemble de résultats :

* Examinez les processeurs sources, dont le `name` est `MergeTreeSelect(...)` (ou `MergeTreeSource`) et dont le `plan_step_name` est `ReadFromMergeTree`. Leur `output_rows` correspond au nombre de lignes produites par chaque source. Additionnez ces valeurs par étape de lecture (`plan_step`), et non sur l&#39;ensemble de la requête. Le total obtenu correspond au nombre de lignes que l&#39;étape de lecture a transmises au reste du pipeline.
* Chaque côté de la jointure possède sa propre étape `ReadFromMergeTree`, avec un `plan_step` différent. Dans les lignes de cette exécution, `parent_ids` contient les ID des processeurs en aval. En partant d&#39;une source, faites correspondre récursivement chaque valeur de `parent_ids` à un `id` du même `query_id` afin de suivre la branche jusqu&#39;à la jointure. Vous pouvez ainsi identifier, par exemple, la branche qui alimente `FillingRightJoinSide`.
* Les processeurs situés au-dessus des sources (par exemple `ExpressionTransform`, `FillingRightJoinSide`, `ConcatProcessor` ou la transformation de jointure elle-même) consomment et produisent des lignes dérivées des sources. N&#39;ajoutez pas leurs compteurs à ceux des sources : les mêmes lignes seraient alors comptées deux fois.
* Les informations d&#39;étape ne suffisent pas toujours à identifier une source. `EXPLAIN PIPELINE` est un plan distinct : il permet de comparer les noms des processeurs et la forme des branches, mais sa sortie en texte brut ne contient ni les valeurs `id` journalisées ni `parent_ids`. Si les deux tables ont des descriptions d&#39;étape similaires, appuyez-vous sur le graphe de la requête exécutée et sur les nombres de lignes connus. Dans cet exemple, les sources de lecture de `big` totalisent 1,000,000 lignes et celles de `small`, 1,000 lignes.
* Les compteurs de lignes et d&#39;octets des processeurs décrivent les données qui transitent dans le pipeline, et non les lectures physiques sur le stockage. Ils n&#39;incluent pas les granules ou les marques lues puis écartées par filtrage, ils dépendent de la clé primaire et des autres filtrages par index, de `PREWHERE` et de l&#39;élagage des colonnes, et ils ne reflètent pas les octets compressés lus sur le disque. `SelectedRows`, `SelectedBytes` et `SelectedMarks` dans `system.query_log` sont des statistiques de sélection logique : elles peuvent être non nulles même lorsque toutes les données proviennent du cache. Pour analyser les lectures de fichiers, utilisez `ReadBufferFromFileDescriptorReadBytes`, qui inclut les lectures servies par le cache de pages du système d&#39;exploitation. Pour analyser les lectures sur disque local ou sur périphérique de type bloc, hors cache de pages du système d&#39;exploitation, utilisez `OSReadBytes`.
