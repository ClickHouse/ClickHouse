`clickhousectl` (alias `chctl`) est la CLI officielle de ClickHouse, du développement local à ClickHouse Cloud. Elle s’adresse aussi bien aux utilisateurs dans un terminal qu’aux scripts et aux agents de code.

Avec `clickhousectl`, vous pouvez :

* Installer des versions locales de ClickHouse et passer de l’une à l’autre, lancer des serveurs locaux isolés et exécuter du SQL
* Exécuter Postgres en local via Docker
* Créer, configurer, mettre à l’échelle, sauvegarder et interroger des services ClickHouse Cloud
* Créer, surveiller, configurer et restaurer des services [ClickHouse Managed Postgres](/fr/products/managed-postgres/overview)
* Créer et exploiter des ClickPipes depuis le stockage d’objet, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB et BigQuery
* Gérer les sources, tableaux de bord, alertes, webhooks, recherches enregistrées et rôles d’un service [Managed ClickStack](/fr/clickstack/deployment/managed)
* Développer des UDF exécutables en local et les déployer sur ClickHouse Cloud
* Gérer les membres de l’organisation, les invitations, les clés API et les rôles
* Installer les ClickHouse agent skills officiels dans les agents de code

Cette page présente des exemples représentatifs. `clickhousectl <command> --help` fait référence pour chaque commande et chaque indicateur. L’aide de la plupart des commandes se termine par un bloc `CONTEXT FOR AGENTS` ; pour les commandes Cloud, elle indique également les autorisations requises pour l’API key. Pour des procédures pas à pas, suivez les liens vers les guides dans chaque section. Pour une vue d’ensemble centrée sur Cloud, consultez [Interface en ligne de commande de ClickHouse](/fr/products/cloud/features/cli).

## Installation {#installation}

`clickhousectl` fonctionne sous MacOS et Linux, sur architectures ARM64 et x86&#95;64.

```bash
curl -fsSL https://clickhouse.com/cli | sh
```

Le script installe `~/.local/bin/clickhousectl` et crée l&#39;alias `chctl`. Assurez-vous que `~/.local/bin` figure dans votre `PATH`.

Vous pouvez également l&#39;installer à l&#39;aide d&#39;un gestionnaire de paquets :

| Outil                                       | Commande                        |
| ------------------------------------------- | ------------------------------- |
| npm                                         | `npm install -g clickhousectl`  |
| uv                                          | `uv tool install clickhousectl` |
| pipx                                        | `pipx install clickhousectl`    |
| pip                                         | `pip install clickhousectl`     |
| cargo-binstall                              | `cargo binstall clickhousectl`  |
| Cargo, à partir du code source (Rust 1.94+) | `cargo install clickhousectl`   |

Seuls le script d&#39;installation et npm créent l&#39;alias `chctl`. Pour mettre à jour une installation existante, exécutez `clickhousectl update` (voir [Mise à jour automatique](#self-update)).

## Prérequis {#requirements}

* Docker, uniquement pour Postgres en local
* Pour les commandes Cloud, un compte [ClickHouse Cloud](https://clickhouse.com/cloud). Les commandes de lecture fonctionnent avec une authentification OAuth via le navigateur (`cloud auth login`). La création ou la modification de ressources nécessite une [API key](/fr/products/cloud/features/admin-features/api/openapi). Consultez la section [Authentification](#authentication).

## Local {#local}

Les commandes locales s&#39;exécutent dans le répertoire courant. Chaque projet stocke les données de son serveur dans `.clickhouse/`, tandis que les binaires ClickHouse sont partagés globalement dans `~/.clickhouse/`. La CLI ne parcourt pas les répertoires parents : exécutez donc les commandes locales depuis la racine de votre projet. Consultez le [guide de développement local](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/local-development.md) pour découvrir le flux de travail complet.

### Installer et sélectionner des versions {#installing-versions}

```bash
clickhousectl local use latest              # Install the latest ClickHouse and make it the default (recommended)
clickhousectl local install lts             # Install the latest LTS release
clickhousectl local install 26.8            # Latest 26.8.x.x release
clickhousectl local list                    # Installed versions
clickhousectl local list --remote           # Versions available for download
clickhousectl local which                   # Current default
clickhousectl local remove 26.8.1.1760      # Remove an exact installed version
```

| Sélecteur     | Signification                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `latest`      | Dernière construction de ClickHouse, vérifiée à distance à chaque installation, utilisation ou démarrage (recommandé) |
| `stable`      | Dernière version stable                                                                                               |
| `lts`         | Dernière version avec support à long terme                                                                            |
| `26.8`        | Dernière version correspondante                                                                                       |
| `26.8.1.1760` | Version exacte                                                                                                        |

`local use` installe la version si nécessaire, la définit comme version par défaut pour les prochains démarrages du serveur et crée un lien symbolique vers `~/.local/bin/clickhouse`, afin que `clickhouse client` et `clickhouse local` soient accessibles depuis votre `PATH`. Passez `--no-global` pour ne pas créer le lien symbolique. Si un fichier ordinaire existe déjà à cet emplacement, il est laissé tel quel.

`local remove` refuse de supprimer la version par défaut ou une version utilisée par un serveur en cours d’exécution, quel que soit le projet. `--force` arrête ces serveurs et supprime la version, puis réinitialise la version par défaut et supprime le lien symbolique.

### Initialiser un projet {#initializing-project}

```bash
clickhousectl local init
```

`init` est facultatif. Cette commande crée un répertoire `.clickhouse/` ignoré par git pour les données d’exécution, ainsi que des squelettes SQL que vous pouvez commiter : `clickhouse/` (`tables/`, `materialized_views/`, `queries/`, `seed/`, `udfs/`) et `postgres/` (`tables/`, `views/`, `functions/`, `queries/`, `seed/`). Si vous la relancez, elle ne crée que les éléments manquants.

### Lancer des serveurs locaux {#managing-servers}

```bash
clickhousectl local server start dev --version latest   # Background start; waits for readiness
clickhousectl local server start dev --no-wait          # Return after spawning
clickhousectl local server start dev --foreground       # Run in the foreground
clickhousectl local server start dev --http-port 8124 --tcp-port 9001
clickhousectl local server list                         # Servers in this project
clickhousectl local server list --global                # Servers across all projects
clickhousectl local server stop dev
clickhousectl local server stop-all                     # Stop all ClickHouse and Postgres servers in this project
clickhousectl local server remove dev                   # Permanently delete a stopped server's data
```

Chaque serveur nommé dispose de ses propres données dans `.clickhouse/servers/<name>/data/`, qui sont conservées à l&#39;arrêt du serveur pour le prochain démarrage. Sans nom, le premier serveur s&#39;appelle `default` ; si `default` est déjà en cours d&#39;exécution, un nouveau nom est généré. Les ports par défaut sont 8123 pour HTTP et 9000 pour TCP ; si ceux-ci sont déjà utilisés, des ports libres sont attribués.

`--version` sélectionne une version pour ce démarrage uniquement, sans modifier la version par défaut. Un démarrage sans version spécifiée et sans version par défaut installe `latest` sans en faire la version par défaut ; exécutez d&#39;abord `local use latest` pour la définir comme version par défaut.

### Exécuter des requêtes SQL avec le client local {#running-queries}

```bash
clickhousectl local client dev                                   # Interactive session
clickhousectl local client dev --query "SELECT 1" --query "SELECT 2"
clickhousectl local client dev --queries-file schema.sql seed.sql
clickhousectl local client dev --query "SELECT version()" -- --format JSONEachRow
clickhousectl local client --host localhost --port 9000          # Connect by address
```

`local client` se connecte à un serveur nommé avec le même binaire ClickHouse que celui qui exécute ce serveur (nom par défaut : `default`). Les arguments placés après `--` sont transmis tels quels à `clickhouse client`. La sortie et le code de sortie proviennent de `clickhouse client`, même en mode JSON ; définissez donc vous-même le format de sortie SQL dans vos scripts.

### Configuration personnalisée du serveur {#custom-config-files}

Placez une configuration XML ou YAML partielle dans `~/.clickhouse/configs/` et sélectionnez-la par son nom au démarrage d&#39;un serveur :

```bash
mkdir -p ~/.clickhouse/configs
cat > ~/.clickhouse/configs/analytics.xml <<'XML'
<clickhouse>
    <profiles>
        <default><max_threads>4</max_threads></default>
    </profiles>
</clickhouse>
XML
clickhousectl local server configs
clickhousectl local server stop dev
clickhousectl local server start dev --config analytics
```

Le fichier se superpose aux valeurs par défaut intégrées : il suffit donc d&#39;y indiquer les paramètres que vous modifiez. Ce choix n&#39;est pas mémorisé : un démarrage ultérieur sans `--config` supprime la surcouche. Les chemins des données et les ports gérés l&#39;emportent toujours sur les valeurs de configuration.

### Enregistrer les informations de connexion dans un fichier dotenv {#dotenv}

```bash
clickhousectl local server dotenv dev                                     # Writes .env
clickhousectl local server dotenv dev --local --user default --database analytics   # Writes .env.local
```

`dotenv` lit les ports effectivement utilisés par le serveur en cours d&#39;exécution et écrit `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT` et `CLICKHOUSE_HTTP_PORT`, ainsi que l&#39;utilisateur, le mot de passe et la base de données si vous les fournissez. Les autres lignes d&#39;un fichier existant sont conservées. Chargez le fichier avec le chargeur dotenv de votre application ; ne passez jamais l&#39;aperçu affiché à `eval`.

### Postgres local {#local-postgres}

Postgres local s’exécute dans Docker : Docker doit donc être en cours d’exécution. Les versions 17 et 18 de Postgres sont prises en charge, y compris les étiquettes d’image comme `18-alpine` ; les nouvelles instances utilisent la version 18 par défaut.

```bash
clickhousectl local install postgres@18                 # Optional: pre-pull the image
clickhousectl local postgres start app --version 18
clickhousectl local postgres start app --wait-timeout 120
clickhousectl local postgres client app --query "SELECT version()"
clickhousectl local postgres client app --queries-file pg-schema.sql
clickhousectl local postgres dotenv app --local
clickhousectl local postgres stop app
clickhousectl local postgres remove app                 # Permanently delete the instance and its data
```

Une instance est identifiée par son nom et sa version majeure. Lorsque vous redémarrez une instance arrêtée, elle réutilise son port, son utilisateur, son mot de passe et sa base de données d&#39;origine : les indicateurs de création sont donc sans effet lors d&#39;une reprise. Un mot de passe aléatoire est généré si vous n&#39;en fournissez pas. Le fichier `.env.local` contient le mot de passe ; veillez donc à l&#39;exclure du contrôle de version.

### UDFs locales {#local-udfs}

`local udf` déploie des [UDF exécutables](/fr/reference/functions/regular-functions/udf#executable-user-defined-functions) depuis `clickhouse/udfs/<name>/` sur un serveur local. `cloud udf` téléverse ce même répertoire vers Cloud (voir [UDFs dans Cloud](#cloud-udfs)).

```bash
clickhousectl local udf init my_udf            # udf.json and main.py (python3.11 runtime)
clickhousectl local server start
clickhousectl local udf deploy my_udf
clickhousectl local client --query "SELECT my_udf(1)"
clickhousectl local udf list
clickhousectl local udf remove my_udf
```

Toutes les commandes, à l’exception de `init`, acceptent `--server <name>` (valeur par défaut : `default`). `deploy` valide `udf.json` de la même manière que Cloud. Sur un serveur en cours d’exécution, la commande recharge les fonctions et vérifie que la fonction a bien été chargée. L’environnement d’exécution `native` ne peut être déployé localement que sur des hôtes Linux amd64 ou arm64. Consultez le [guide des fonctions définies par l’utilisateur](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

## Authentification {#authentication}

Les commandes Cloud utilisent l’un des deux types d’informations d’authentification suivants :

| Information d’authentification | Capacités                                                                                                                           | Stockage                                                             |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| OAuth via le navigateur        | Votre identité utilisateur : opérations Cloud et requêtes SQL en lecture seule, dans toutes les organisations dont vous êtes membre | `~/.clickhouse/tokens.json`, global et partagé entre les projets     |
| API key                        | Limitée à une seule organisation ; les lectures et écritures dépendent des rôles de la clé                                          | `.clickhouse/credentials.json` une fois enregistrée, local au projet |

Si vous n’avez pas encore de compte ClickHouse Cloud, `clickhousectl cloud auth signup` ouvre la page d’inscription dans votre navigateur.

### Connexion avec OAuth {#oauth-login}

```bash
clickhousectl cloud auth login
```

Cela ouvre votre navigateur pour le flux OAuth pour appareils. Les jetons sont enregistrés globalement dans `~/.clickhouse/tokens.json` et rafraîchis automatiquement.

<Note>
  OAuth est **en lecture seule**. Pour créer ou modifier des ressources, connectez-vous avec une [API key](#api-key).
</Note>

### API key {#api-key}

[Créez une API key](/fr/products/cloud/features/admin-features/api/openapi) disposant des rôles nécessaires à vos commandes, puis enregistrez-la. L&#39;invite interactive permet d&#39;éviter que le secret n&#39;apparaisse dans l&#39;historique de votre interpréteur de commandes :

```bash
clickhousectl cloud auth login --interactive
clickhousectl cloud auth login --api-key "$KEY_ID" --api-secret "$KEY_SECRET"   # Alternative
```

La connexion vérifie la clé et affiche l&#39;identité à laquelle elle est associée. Si l&#39;API rejette la clé, celle-ci n&#39;est pas enregistrée et la commande se termine avec le code de sortie 4. Si l&#39;API est injoignable, la clé est tout de même enregistrée, avec un avertissement.

Pour l&#39;intégration continue et les autres processus automatisés, injectez la clé via votre gestionnaire de secrets plutôt que de l&#39;enregistrer :

```bash
export CLICKHOUSE_CLOUD_API_KEY=your-api-key
export CLICKHOUSE_CLOUD_API_SECRET=your-api-secret
```

En développement, la CLI lit également ces variables depuis un fichier `.env` situé dans le répertoire courant. Veillez à exclure `.env` du contrôle de version.

### Vérifier et effacer les identifiants {#auth-status}

```bash
clickhousectl cloud auth whoami          # Verify the active credentials and show the orgs they reach
clickhousectl cloud auth status          # Show configured sources and which one is active
clickhousectl cloud auth logout --oauth  # Clear OAuth tokens only
clickhousectl cloud auth logout --api-keys
clickhousectl cloud auth logout          # Clear both
```

`whoami` fonctionne avec les deux types d’identifiants et renvoie le code de sortie 4 si les identifiants sont rejetés. `status` peut renvoyer le code de sortie 0 même si aucun identifiant n’est valide ; utilisez donc `whoami` pour vérifier l’accès. La déconnexion ne supprime pas les variables d’environnement et ne modifie pas le fichier `.env`.

### Ordre de priorité des informations d’authentification {#credential-precedence}

La première source disponible l’emporte :

1. Les indicateurs `--api-key` et `--api-secret`
2. `.clickhouse/credentials.json`
3. Les variables d’environnement exportées
4. Les variables définies dans le fichier `.env` du répertoire courant
5. Les jetons OAuth globaux

Ajoutez `--debug` à n’importe quelle commande `cloud` pour afficher sur stderr la source d’informations d’authentification retenue ainsi que l’URL de l’API :

```bash
clickhousectl cloud service list --debug
```

### Sélectionner une organisation {#organizations}

Les commandes qui portent sur une organisation ne la sélectionnent automatiquement que si vos identifiants donnent accès à une seule organisation. Sinon, indiquez `--org-id`, ou `--org-name` suivi du nom exact :

```bash
clickhousectl cloud org list
clickhousectl cloud service list --org-id <org-id>
clickhousectl cloud service list --org-name "My Org"
```

La plupart des commandes portant sur des ressources acceptent un ID positionnel ou un `--name` exact. Consultez [Authentification et accès](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/authentication.md) pour en savoir plus sur les autorisations, les clés restreintes et le nettoyage à la déconnexion.

## Cloud {#cloud}

Les commandes Cloud appellent l&#39;[API ClickHouse Cloud](/fr/products/cloud/features/admin-features/api/api-overview). Les requêtes de création et de mise à jour se terminent dès que l&#39;API les accepte : interrogez donc `get` jusqu&#39;à ce que la ressource atteigne l&#39;état souhaité.

### Services {#services}

```bash
clickhousectl cloud service create --name analytics \
  --provider aws --region us-east-1 --ip-allow '203.0.113.10/32=Office'
clickhousectl cloud service list
clickhousectl cloud service get <service-id>
clickhousectl cloud service start <service-id>
clickhousectl cloud service stop <service-id>
clickhousectl cloud service wake <service-id>             # Wake an idle service
clickhousectl cloud service reset-password <service-id>
clickhousectl cloud service delete <service-id>           # Must be stopped; --force stops it first
```

Conservez le mot de passe initial affiché lors de la création : il n’est renvoyé qu’une seule fois. La commande de création rend la main avant la fin du provisionnement ; relancez donc `get` jusqu’à ce que l’état soit `running`. **Si vous omettez `--ip-allow`, toutes les adresses IP sont autorisées (`0.0.0.0/0`).** Les entrées sont au format `IP_OR_CIDR=DESCRIPTION`. Restaurez une sauvegarde dans un nouveau service avec `--backup-id`, ou déployez un service dans une infrastructure BYOC avec `--byoc-id`.

Mettre à jour, mettre à l’échelle et configurer un service :

```bash
clickhousectl cloud service update <service-id> --new-name analytics-prod \
  --add-ip-allow '198.51.100.0/24=VPN' --remove-ip-allow 0.0.0.0/0 --add-tag env=prod
clickhousectl cloud service profile list --region us-east-1
clickhousectl cloud service scale <service-id> \
  --min-replica-memory-gb 8 --max-replica-memory-gb 32 --num-replicas 2
clickhousectl cloud service scale <service-id> --autoscaling-mode horizontal \
  --min-replica-memory-gb 16 --max-replica-memory-gb 16 --min-replicas 2 --max-replicas 6
clickhousectl cloud service settings set <service-id> --setting 'enable_analyzer=1'
clickhousectl cloud service upgrade-window set <service-id> --weekday 0 --start-hour 6
```

La mémoire par réplique est un multiple de 4 Go, avec un maximum de 120 Go pour les services non payants et de 356 Go pour les services payants, dans la limite de 50 répliques. Les limites de l&#39;organisation et de l&#39;entrepôt peuvent abaisser ces valeurs. La mise à l’échelle automatique horizontale nécessite que la fonctionnalité correspondante soit activée pour l&#39;organisation. `update` ne modifie que les indicateurs que vous spécifiez.

Les autres groupes de commandes de service sont `settings` (list, get, schema, set, unset), `scaling-schedule`, `upgrade-window`, `replica-aware-routing` (bêta), `snapshot` (bêta), `private-endpoint`, `backup-config` et `prometheus`. Consultez [Créer et exploiter un Service Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md).

### API de requête {#query-api}

`cloud service query` exécute une instruction SQL via HTTP, sans nécessiter de binaire `clickhouse` local ni de mot de passe de service :

```bash
clickhousectl cloud service query <service-id> --query "SELECT version()"
clickhousectl cloud service query <service-id> --queries-file query.sql --format TabSeparated
printf 'INSERT INTO trips FORMAT CSV\n' | cat - data.csv | \
  clickhousectl cloud service query <service-id>
```

* **OAuth** exécute la requête sous votre identity, avec un accès SQL en lecture seule. Rien n&#39;est lié au service.
* **API key :** lors du premier appel, clickhousectl ajoute votre API key au point de terminaison de l’API de requêtes du service et crée cet endpoint avec les rôles `sql_console_admin` si nécessaire. Les rôles, origines et autres liaisons de clés existants sont conservés, et aucune nouvelle clé n&#39;est créée. Lorsque la CLI modifie l&#39;endpoint, elle affiche `Binding the authenticated API key to the Query API endpoint for service '<name>'...` sur stderr. Passez `--no-auto-enable` pour que la commande échoue plutôt.

Une clé propre à un service, enregistrée par une version antérieure de la CLI, reste prioritaire pour ce service. Si l&#39;API la rejette, `cloud service repair-query-key <service-id>` la remplace explicitement.

L&#39;API de requête n&#39;accepte qu&#39;un seul statement par requête. Elle peut expirer au bout d&#39;environ 30 secondes alors que le SQL continue de s&#39;exécuter : vérifiez donc le résultat avant de relancer une écriture. Utilisez `clickhouse client` pour les scripts à plusieurs statements, les chargements en masse et les requêtes longues. La liste d’autorisation d&#39;adresses IP du service restreint les connexions directes, mais pas la route de l&#39;API de requête qui passe par le proxy. Interroger un service inactif le réveille ; un service arrêté doit être démarré avec `cloud service start`.

Gérez le point de terminaison de l’API de requêtes du service, les endpoints SQL nommés et les requêtes enregistrées :

```bash
clickhousectl cloud service query-endpoint get <service-id>
clickhousectl cloud service query-endpoint create <service-id> \
  --role sql_console_read_only --allowed-origins '*'
clickhousectl cloud query-api-endpoint create <service-id> --file endpoint.json
clickhousectl cloud saved-query create <service-id> --name "Order count" \
  --sql 'SELECT count() FROM orders' --database default
```

`query-endpoint create` remplace les rôles de chaque clé associée à l&#39;endpoint. Consultez [Comportement du SQL et de l&#39;API de requête](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/query-api.md).

### Managed Postgres {#postgres-services}

`cloud postgres` permet de gérer [ClickHouse Managed Postgres](/fr/products/managed-postgres/overview). Ces commandes sont en version bêta, et la prise en charge de GCP est en aperçu privé.

```bash
clickhousectl cloud postgres create --name app-db \
  --provider aws --region us-east-1 --size c6gd.xlarge --pg-version 18 \
  --ip-allow '203.0.113.0/24:5432..6432=office'
clickhousectl cloud postgres get <postgres-id>
clickhousectl cloud postgres certs get <postgres-id> --output ca.pem
clickhousectl cloud postgres update <postgres-id> --size c6gd.2xlarge
clickhousectl cloud postgres update <postgres-id> \
  --remove-ip-allow <rule-id> --add-ip-allow '198.51.100.7:5432'
clickhousectl cloud postgres config patch <postgres-id> --set log_min_duration_statement=1000
clickhousectl cloud postgres reset-password <postgres-id> --generate
clickhousectl cloud postgres delete <postgres-id>       # Deletes a running service too
```

Les tailles AWS disponibles incluent `m6gd.large`, `c6gd.xlarge` et `r6gd.xlarge`. Sur GCP, passez `--provider gcp` avec une région GCP et une taille telle que `c4-standard-lssd-4`.

Enregistrez le mot de passe et la chaîne de connexion renvoyés par `create`. Les réponses ultérieures de `get` ne renvoient jamais les identifiants : `reset-password` est le seul moyen d’en obtenir de nouveaux. Connectez-vous avec `psql` en utilisant `sslmode=verify-full` et le fichier de l’AC.

**Si vous omettez les indicateurs d’accès lors de la création, toutes les adresses IPv4 et IPv6 sont autorisées sur Postgres (5432) et PgBouncer (6432).** Passez un `--ip-allow IP_OR_CIDR:PORTS[=DESCRIPTION]` par règle, ou `--block-public-access` pour n’appliquer aucune règle. Dès que vous spécifiez une règle, seules les règles indiquées s’appliquent.

Surveillance et récupération :

```bash
clickhousectl cloud postgres query <postgres-id> --query "SELECT version()"   # OAuth only, read-only
clickhousectl cloud postgres logs <postgres-id> \
  --from-date 2026-10-01T00:00:00Z --to-date 2026-10-02T00:00:00Z
clickhousectl cloud postgres backup list <postgres-id>
clickhousectl cloud postgres restore <postgres-id> \
  --name restored-app --restore-target 2026-10-01T12:00:00Z
clickhousectl cloud postgres read-replica create <postgres-id> --name app-db-replica
clickhousectl cloud postgres promote <replica-id>
```

`cloud postgres query` n&#39;accepte que OAuth : la commande échoue donc tant qu&#39;une source d&#39;API key de priorité supérieure est active. `metrics`, `slow-queries` et `prometheus` couvrent la supervision. `restore` copie les règles d&#39;accès IPv4 actuelles de la source sur le service restauré, sauf si vous passez `--ip-allow` ou `--block-public-access`. Les restaurations et les répliques sont renvoyées sans mot de passe. `promote` et `switchover` rendent la main dès que l&#39;opération est acceptée ; après un `promote`, interrogez `postgres get --json` jusqu&#39;à ce que la réplique indique `isPrimary: true`. Consultez le [guide Managed Postgres](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/managed-postgres.md).

### ClickPipes {#clickpipes}

`cloud clickpipe` ingère des données depuis un stockage d’objet, Kafka, Kinesis, Pub/Sub, Postgres, MySQL, MongoDB et BigQuery. La création et la découverte du schéma nécessitent une API key et un service de destination en cours d’exécution. Chaque source dispose de sa propre sous-commande `clickpipe create <source>` ; exécutez-la avec `--help` pour afficher ses indicateurs.

Chargez des fichiers depuis S3 à l’aide d’un rôle IAM. Commencez par découvrir le schéma, puis sélectionnez les colonnes :

```bash
clickhousectl cloud clickpipe schema-discover object-storage <service-id> \
  --storage-type s3 --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN"
clickhousectl cloud clickpipe create object-storage <service-id> \
  --name s3-events --storage-type s3 \
  --source-url 'https://example-bucket.s3.amazonaws.com/events/**' \
  --format JSONEachRow --iam-role "$S3_IAM_ROLE_ARN" \
  --database default --table s3_events \
  --column 'event_id:Int64' --column 'event_type:String'
```

Répliquez Postgres via CDC. Le certificat TLS est vérifié par défaut ; pour une source Managed Postgres, exportez son AC et transmettez-la :

```bash
clickhousectl cloud postgres certs get <postgres-id> --output pg-ca.pem
clickhousectl cloud clickpipe create postgres <service-id> \
  --name orders-cdc --host "$POSTGRES_HOST" --pg-database postgres \
  --username "$POSTGRES_USERNAME" --password "$POSTGRES_PASSWORD" \
  --ca-certificate pg-ca.pem \
  --replication-mode cdc --destination-database default \
  --table-mapping public.orders:orders
clickhousectl cloud service query <service-id> \
  --query "SELECT id, status FROM default.orders FINAL WHERE _peerdb_is_deleted = 0"
```

`--table-mapping` crée des tables `ReplacingMergeTree` : lisez donc l&#39;état courant avec `FINAL WHERE _peerdb_is_deleted = 0`. Un pipeline d’ingestion Kafka suit le même principe : exécutez `clickpipe schema-discover kafka` avec les mêmes indicateurs de source, puis transmettez les colonnes :

```bash
clickhousectl cloud clickpipe create kafka <service-id> \
  --name kafka-events --brokers 'broker-1.example.com:9092' --topics events \
  --format JSONEachRow --auth SCRAM-SHA-256 \
  --username "$KAFKA_USERNAME" --password "$KAFKA_PASSWORD" \
  --database default --table kafka_events \
  --column 'event_id:Int64' --column 'event_type:String' --start-paused
```

Par défaut, les pipelines d’ingestion BigQuery effectuent un snapshot. Pour la CDC, indiquez `--replication-mode cdc`, une `--replication-method`, ainsi qu’une colonne de watermark ou une fonction d’événements pour chaque table dans `--table-mapping-json`. Planifiez les synchronisations avec `--sync-cron` ou `--sync-interval-seconds`. Gérer les pipelines d’ingestion existants :

```bash
clickhousectl cloud clickpipe list <service-id>
clickhousectl cloud clickpipe get <service-id> <clickpipe-id>
clickhousectl cloud clickpipe stop <service-id> <clickpipe-id>
clickhousectl cloud clickpipe update <service-id> <clickpipe-id> --file patch.json
clickhousectl cloud clickpipe start <service-id> <clickpipe-id>
clickhousectl cloud clickpipe scale <service-id> <clickpipe-id> --replicas 2
clickhousectl cloud clickpipe settings update <service-id> <clickpipe-id> \
  --streaming-max-insert-wait-ms 5000
clickhousectl cloud clickpipe resync <service-id> <clickpipe-id>   # Postgres and MySQL pipes; re-ingests data
```

Les pipelines d’ingestion CDC doivent être à l’état `Paused` avant toute opération `update` : arrêtez le pipeline d’ingestion, interrogez `get` jusqu’à ce qu’il passe à l’état `Paused`, puis mettez-le à jour. Le service pouvant relancer le pipeline d’ingestion au cours de la mise à jour, n’exécutez `start` que si `get` affiche toujours `Paused`. L’option `--start-paused` est disponible pour le stockage d’objet, Kafka, Kinesis et Pub/Sub. Les autres groupes de commandes sont `cdc-scaling`, `context get` (disponibilité de la workload identity GCP et principal de sécurité) et `reverse-private-endpoint`. Consultez le [guide ClickPipes](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickpipes.md) et la [référence de configuration ClickPipe](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/clickpipe-configuration.md).

### ClickStack {#clickstack}

`cloud clickstack` gère les sources, les tableaux de bord, les alertes, les webhooks, les recherches enregistrées et les rôles d&#39;un service [Managed ClickStack](/fr/clickstack/deployment/managed) existant. Les ressources sont des fichiers JSON (`--file`, ou `-` pour stdin). Les lectures prennent en charge OAuth ; les écritures nécessitent une API key.

```bash
clickhousectl cloud clickstack source list <service-id>
clickhousectl cloud clickstack dashboard validate <service-id> --file dashboard.json
clickhousectl cloud clickstack dashboard create <service-id> --file dashboard.json
clickhousectl cloud clickstack webhook validate <service-id> --file webhook.json
clickhousectl cloud clickstack alert create <service-id> --file alert.json
clickhousectl cloud clickstack dashboard get <service-id> <dashboard-id> --json > dashboard-before.json
```

**Chaque mise à jour de ClickStack remplace l&#39;intégralité de la ressource.** Enregistrez l&#39;état actuel avec `get --json` et envoyez la définition complète, pas seulement les champs modifiés. Consultez le [guide ClickStack](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/clickstack.md).

### UDFs dans Cloud {#cloud-udfs}

`cloud udf` gère les UDF exécutables au niveau de l&#39;organisation, leurs versions et leurs associations aux services. `deploy` téléverse le répertoire que vous avez testé avec `local udf`, attend la fin de la construction, associe cette version au service, puis attend que son déploiement soit terminé :

```bash
clickhousectl cloud udf deploy my_udf --service <service-id>
clickhousectl cloud service query <service-id> --query "SELECT my_udf(1)"
```

Pour exécuter chaque étape vous-même, utilisez `udf create`, `udf version create`, `udf attach` (avec `--wake` pour un service inactif), `udf detach` et `udf delete`. Ces commandes rendent la main dès que la requête est acceptée ; interrogez ensuite `udf get` et `udf attachment get` pour suivre leur progression. Les lectures prennent en charge OAuth ; les écritures nécessitent une API key. Consultez le [guide des fonctions définies par l&#39;utilisateur](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/user-defined-functions.md).

### Organisations et accès {#org-and-access}

```bash
clickhousectl cloud org get --org-id <org-id>
clickhousectl cloud org update --org-id <org-id> --new-name "Renamed Org"
clickhousectl cloud org usage --org-id <org-id> --from-date 2026-09-01 --to-date 2026-09-30
clickhousectl cloud org prometheus discovery --org-id <org-id>
clickhousectl cloud org notifications --org-id <org-id> --severity warning
clickhousectl cloud activity list --from-date 2026-09-01 --to-date 2026-09-30
```

Les sous-commandes `cloud org` acceptent `--org-id`, jamais un ID positionnel. `org usage` couvre une période de 31 jours au maximum. `org` propose également `quota`, `balance`, `notification-types`, `role` (rôles d&#39;organisation personnalisés) et `byoc` (infrastructure BYOC). Les notifications sont en bêta.

Gérez les membres, les invitations et les clés API :

```bash
clickhousectl cloud member list
clickhousectl cloud member update <user-id> --role-id <role-id>
clickhousectl cloud invitation create --email dev@example.com --role-id <role-id>
clickhousectl cloud org role list --org-id <org-id>
clickhousectl cloud key create --name ci-key --role-id <role-id> \
  --expires-at 2027-12-31T00:00:00Z --ip-allow '203.0.113.10/32=CI runner'
clickhousectl cloud key list --all
clickhousectl cloud key update <key-id> --new-name ci-key-old --state disabled
```

**Si vous omettez `--ip-allow` lors d’un `key create`, tout accès réseau est refusé**, contrairement à la création d’un service. Le secret n’est affiché qu’une seule fois. `key list` ne renvoie qu’une seule page, sauf si vous passez `--all`. Lors d’un `key update`, les indicateurs omis conservent leurs paramètres, tandis que `--clear-expiry`, `--clear-roles` et `--clear-ip-allow` les suppriment.

### Sauvegardes {#backups}

```bash
clickhousectl cloud backup list <service-id>
clickhousectl cloud backup get <service-id> <backup-id>
clickhousectl cloud service create --name restored-analytics \
  --provider aws --region us-east-1 --ip-allow 203.0.113.10/32 --backup-id <backup-id>
clickhousectl cloud service backup-config update <service-id> \
  --backup-period-hours 24 --backup-retention-period-hours 720
clickhousectl cloud backup bucket get <service-id>
```

La restauration crée toujours un nouveau service. `cloud backup bucket` (get, create, update, delete) configure votre propre bucket de sauvegarde (BYOB) à partir d&#39;un fichier JSON spécifique au fournisseur. Consultez la section consacrée aux sauvegardes dans le [guide du Service Cloud](https://github.com/ClickHouse/clickhousectl/blob/main/docs/guides/cloud-service.md#back-up-and-restore).

## Sortie JSON {#json-output}

Les commandes qui renvoient des données structurées acceptent l&#39;option `--json`, notamment les commandes locales, Cloud, `skills`, `update` et `telemetry` :

```bash
clickhousectl cloud service list --json
clickhousectl cloud key list --all --json
clickhousectl local server list --json
```

Lorsque la CLI détecte un agent de code (comme Claude Code, Cursor, Codex, Gemini CLI, Goose ou Devin, ou tout outil qui définit `AI_AGENT`), elle bascule automatiquement sur le JSON. Les clients SQL et natifs conservent leurs propres formats : `cloud service query` renvoie du `JSONEachRow` en mode JSON, et la sortie de `local client` est toujours au format natif. Les scripts qui analysent la sortie des requêtes doivent spécifier `--format` explicitement.

En mode JSON, les erreurs d’exécution sont écrites sur stderr sous la forme d’un objet comportant un `code` stable et un `message` :

```json
{"error":{"code":"server_not_found","message":"The selected server was not found"}}
```

Basez votre logique conditionnelle sur `error.code`, et non sur le message. Les erreurs d’utilisation restent au format texte, avec le code de sortie 2. Consultez [contrats d’automatisation et de sortie](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/automation.md) pour en savoir plus sur les formes de sortie et les codes d’erreur.

## Codes de sortie {#exit-codes}

| Code | Signification                                                                                      |
| ---- | -------------------------------------------------------------------------------------------------- |
| `0`  | Succès. Pour les opérations Cloud asynchrones, la requête a été acceptée, mais pas encore terminée |
| `1`  | Erreur                                                                                             |
| `2`  | Erreur d&#39;utilisation, notamment des valeurs d&#39;option invalides                             |
| `3`  | Annulé                                                                                             |
| `4`  | Authentification requise ou refusée, notamment pour les tentatives d&#39;écriture avec OAuth       |

`local client`, `local postgres client` et les autres commandes qui délèguent à un client natif renvoient directement le code de sortie de ce client.

## Compétences d&#39;agent {#skills}

Installez les [ClickHouse agent skills officielles](https://github.com/ClickHouse/agent-skills) dans vos agents de code :

```bash
clickhousectl skills                                  # Interactive: choose scope and agents
clickhousectl skills --agent claude --agent codex     # Current project
clickhousectl skills --detected-only --global         # Agents detected in your home directory
clickhousectl skills --all
```

Par défaut, les compétences s&#39;installent dans le projet en cours, ou dans votre répertoire personnel avec `--global`. Le répertoire partagé `.agents/skills/` est toujours inclus. En l&#39;absence de terminal, vous devez spécifier `--agent`, `--all` ou `--detected-only`. Exécutez `clickhousectl skills --help` pour obtenir la liste des noms d&#39;agents pris en charge.

## Mise à jour automatique {#self-update}

```bash
clickhousectl update --check     # Check without installing
clickhousectl update             # Install the latest release
```

La CLI vérifie également en arrière-plan si des mises à jour sont disponibles, au plus une fois toutes les 24 heures, et affiche une notification lorsqu&#39;une version plus récente est disponible.

## Télémétrie {#telemetry}

`clickhousectl` collecte des données d’utilisation anonymes afin d’orienter son développement. La première exécution affiche un avis et n’envoie aucune donnée ; la collecte débute lors d’une exécution ultérieure, sauf si vous la désactivez.

Chaque événement contient :

* Le chemin de la commande et les **noms** des indicateurs et arguments explicitement transmis, jamais leurs valeurs
* Le résultat et le code de sortie
* Pour une commande mal saisie, le nom de la commande ou de l’indicateur suggéré par la CLI, jamais ce que vous avez saisi
* Pour les échecs à l’exécution, des catégories bornées : étape et type d’échec, un statut HTTP figurant dans une liste d’autorisation, ainsi que des catégories de nouvelle tentative, d’état de provisionnement et de durée
* La version de la CLI, l’OS et l’architecture, l’exécution ou non en intégration continue, ainsi que l’agent de code détecté

Les valeurs des arguments, les requêtes SQL, les identifiants, les identifiants de ressources, les arguments placés après `--` et les messages d’erreur ne sont jamais enregistrés. Aucun identifiant d’installation ou d’appareil n’est utilisé.

Pour désactiver la collecte :

```bash
clickhousectl telemetry disable     # Persist the preference on this machine
clickhousectl telemetry status
export DO_NOT_TRACK=1               # Disable for an environment, overriding the saved preference
```

Définissez `CHCTL_TELEMETRY_DEBUG=1` pour afficher la charge utile sur stderr sans rien envoyer. Pour en savoir plus, consultez la [documentation sur la télémétrie](https://github.com/ClickHouse/clickhousectl/blob/main/docs/reference/telemetry.md).
