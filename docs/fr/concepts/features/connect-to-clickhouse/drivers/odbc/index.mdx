Le driver ODBC ClickHouse fournit une interface conforme aux normes permettant de connecter des applications compatibles ODBC à
ClickHouse. Il implémente l’API ODBC et permet aux applications, aux outils de BI et aux environnements de script d’exécuter des requêtes
SQL, de récupérer des résultats et d’interagir avec ClickHouse au moyen de mécanismes familiers.

Le driver communique avec le serveur ClickHouse via le [protocole HTTP](/fr/concepts/features/connect-to-clickhouse/protocols/http), principal
protocole pris en charge par l’ensemble des déploiements ClickHouse. Le driver peut ainsi fonctionner de manière homogène dans des
environnements variés, notamment les installations locales, les services managés dans le cloud et les environnements où seul un accès HTTP est
disponible.

Le code source du driver est disponible dans le
[dépôt GitHub ClickHouse-ODBC](https://github.com/ClickHouse/clickhouse-odbc).

<Tip>
  Pour une meilleure compatibilité, nous vous recommandons vivement de mettre à jour votre serveur ClickHouse vers la version 24.11 ou une version ultérieure.
</Tip>

<Note>
  Ce driver est en cours de développement actif. Certaines fonctionnalités ODBC ne sont peut-être pas encore entièrement implémentées. La version actuelle
  se concentre sur la connectivité essentielle et les fonctionnalités ODBC de base ; d’autres fonctionnalités sont prévues dans de futures
  versions.

  Vos retours sont très précieux et nous aident à définir les priorités des nouvelles fonctionnalités et améliorations. Si vous constatez
  des limitations, des fonctionnalités manquantes ou un comportement inattendu, n’hésitez pas à nous faire part de vos observations ou de vos demandes de fonctionnalités via
  le système de suivi des tickets à l’adresse
  [https://github.com/ClickHouse/clickhouse-odbc/issues](https://github.com/ClickHouse/clickhouse-odbc/issues)
</Note>

Vous trouverez la dernière version du driver à l&#39;adresse

Vous pouvez y télécharger et exécuter le programme d&#39;installation MSI, puis suivre les quelques étapes d&#39;installation, très simples.

## Test {#testing}

Vous pouvez tester le driver en exécutant ce script PowerShell simple. Copiez le texte ci-dessous, renseignez votre URL, votre nom d’utilisateur et votre mot de passe, puis
collez le texte dans votre invite de commandes PowerShell. Après l’exécution de `$reader.GetValue(0)`, la version de votre serveur ClickHouse
devrait s’afficher.

```powershell
$url = "http://127.0.0.1:8123/"
$username = "default"
$password = ""
$conn = New-Object System.Data.Odbc.OdbcConnection("`
    Driver={ClickHouse ODBC Driver (Unicode)};`
    Url=$url;`
    Username=$username;`
    Password=$password")
$conn.Open()
$cmd = $conn.CreateCommand()
$cmd.CommandText = "select version()"
$reader = $cmd.ExecuteReader()
$reader.Read()
$reader.GetValue(0)
$reader.Close()
$conn.Close()
```

## Paramètres de configuration {#configuration-parameters}

Les paramètres ci-dessous sont les plus couramment utilisés pour établir une connexion avec le pilote ODBC
ClickHouse. Ils couvrent les options essentielles d’authentification, de comportement de la connexion et de traitement des données. La liste complète des
paramètres pris en charge est disponible sur la page GitHub du projet
[https://github.com/ClickHouse/clickhouse-odbc](https://github.com/ClickHouse/clickhouse-odbc).

* `Url` : spécifie l’endpoint HTTP(S) complet du serveur ClickHouse, y compris le protocole, l’hôte, le port et un
  chemin facultatif.
* `Username` : nom d’utilisateur utilisé pour l’authentification auprès du serveur ClickHouse.
* `Password` : mot de passe associé au nom d’utilisateur spécifié. S’il n’est pas fourni, le driver se connecte sans authentification
  par mot de passe.
* `Database` : base de données par défaut à utiliser pour la connexion.
* `Timeout` : durée maximale (en secondes) pendant laquelle le driver attend une réponse du serveur avant d’abandonner la requête.
* `ClientName` : identifiant personnalisé envoyé au serveur ClickHouse dans les métadonnées du client. Utile pour tracer ou
  distinguer le trafic provenant de différentes applications. Ce paramètre est inclus dans l’en-tête User-Agent des requêtes
  HTTP émises par le driver.
* `Compression` : active ou désactive la compression HTTP des charges utiles des requêtes et des réponses. Lorsqu’elle est activée, elle peut réduire
  la consommation de débit et améliorer les performances pour les ensembles de résultats volumineux.
* `SqlCompatibilitySettings` : active des paramètres de requête qui rapprochent le comportement de ClickHouse de celui d’une base de données
  relationnelle traditionnelle. C’est utile lorsque les requêtes sont générées automatiquement par des outils tiers, comme Power BI. Ces
  outils ignorent généralement certains comportements spécifiques à ClickHouse et peuvent produire des requêtes qui entraînent des erreurs ou
  des résultats inattendus. Pour plus de détails, consultez [Paramètres ClickHouse utilisés par le paramètre de configuration SqlCompatibilitySettings
  ](#sql-compatibility-settings).

Voici quelques exemples de chaînes de connexion complètes transmises au driver pour établir une connexion.

* Un serveur ClickHouse installé localement sur une instance WSL

```plaintext
Driver={ClickHouse ODBC Driver (Unicode)};Url=http://localhost:8123/;Username=default
```

* Une instance ClickHouse Cloud.

```plaintext
Driver={ClickHouse ODBC Driver (Unicode)};Url=https://you-instance-url.gcp.clickhouse.cloud:8443/;Username=default;Password=your-password
```

## Intégration de Microsoft Power BI {#powerbi-integration}

Vous pouvez utiliser le pilote ODBC pour connecter Microsoft Power BI à un serveur ClickHouse. Power BI propose deux options de connexion :
le connecteur ODBC générique et le Connecteur ClickHouse, tous deux inclus dans les installations standard de Power BI.

Les deux connecteurs s’appuient en interne sur ODBC, mais leurs capacités diffèrent :

* Connecteur ClickHouse (recommandé)
  Repose sur ODBC, mais prend en charge le mode DirectQuery. Dans ce mode, Power BI génère automatiquement des requêtes SQL et
  ne récupère que les données nécessaires à chaque visualisation ou opération de filtrage.

* Connecteur ODBC
  Prend uniquement en charge le mode Import. Power BI exécute la requête fournie par l’utilisateur (ou sélectionne la table entière) et importe
  l’ensemble de résultats complet dans Power BI. Chaque rafraîchissement ultérieur réimporte l’intégralité du jeu de données.

Choisissez le connecteur en fonction de votre cas d’utilisation. DirectQuery est particulièrement adapté aux tableaux de bord interactifs portant sur de grands jeux de données.
Optez pour le mode Import lorsque vous avez besoin de copies locales complètes des données.

Pour plus d’informations sur l’intégration de Microsoft Power BI avec ClickHouse, consultez la [page de documentation ClickHouse consacrée à l’intégration de Power
BI](/fr/integrations/connectors/data-visualization/powerbi-and-clickhouse).

## Paramètres de compatibilité SQL {#sql-compatibility-settings}

ClickHouse dispose de son propre dialecte SQL, et dans certains cas, il se comporte différemment d&#39;autres bases de données telles que MS SQL
Server, MySQL ou PostgreSQL. Ces différences constituent souvent un avantage, car elles apportent une syntaxe améliorée qui facilite
l&#39;utilisation des fonctionnalités de ClickHouse.

Cependant, le pilote ODBC est souvent utilisé dans des environnements où les requêtes sont générées par des outils tiers, tels que Power
BI, plutôt qu&#39;écrites par les utilisateurs. Ces requêtes reposent généralement sur un sous-ensemble minimal de la norme SQL. Dans ce cas,
les écarts de ClickHouse par rapport à la norme SQL peuvent ne pas fonctionner comme prévu et produire des résultats ou des erreurs inattendus.
Le pilote ODBC fournit un paramètre de configuration supplémentaire, `SqlCompatibilitySettings`, qui active certains paramètres de requête
afin de rapprocher le comportement de ClickHouse du SQL standard.

### Paramètres ClickHouse activés par le paramètre de configuration SqlCompatibilitySettings {#sql-compatibility-settings-list}

Cette section décrit les paramètres modifiés par le pilote ODBC et les raisons de ces modifications.

**[cast&#95;keep&#95;nullable](/fr/reference/settings/session-settings/cast#cast_keep_nullable)**

Par défaut, ClickHouse n&#39;autorise pas la conversion de types nullable en types non nullable. Cependant, de nombreux outils de BI ne font pas
la distinction entre types nullable et non nullable lors des conversions de types. Il n&#39;est donc pas rare de
voir des outils de BI générer des requêtes comme celle-ci :

```sql
SELECT sum(CAST(value, 'Int32'))
FROM values
```

Par défaut, lorsque la colonne `value` est nullable, cette requête échoue avec le message d&#39;erreur suivant :

```plaintext
DB::Exception: Cannot convert NULL value to non-Nullable type: while executing 'FUNCTION CAST(__table1.value :: 2,
'Int32'_String :: 1) -> CAST(__table1.value, 'Int32'_String) Int32 : 0'. (CANNOT_INSERT_NULL_IN_ORDINARY_COLUMN)
```

L&#39;activation de `cast_keep_nullable` modifie le comportement de `CAST` afin qu&#39;il conserve le caractère nullable de ses arguments. Cela
rapproche le comportement de ClickHouse de celui des autres bases de données et de la norme SQL pour ce type de conversion.

**[prefer&#95;column&#95;name&#95;to&#95;alias](/fr/reference/settings/session-settings/prefer#prefer_column_name_to_alias)**

ClickHouse permet de faire référence à des expressions de la même liste `SELECT` au moyen de leurs alias. Par exemple, cette requête évite
les répétitions et est plus simple à écrire :

```sql
SELECT
    sum(value) AS S,
    count() AS C,
    S / C
FROM test
```

Cette fonctionnalité est largement utilisée, mais les autres bases de données ne résolvent généralement pas les alias de cette manière au sein d&#39;une même liste `SELECT`,
et de telles requêtes y provoqueraient une erreur. Les problèmes apparaissent surtout lorsqu&#39;un alias porte le même nom qu&#39;une colonne. Par exemple :

```sql
SELECT
    sum(value) AS value,
    avg(value)
FROM test
```

Quelle `value` `avg(value)` doit-elle agréger ? Par défaut, ClickHouse privilégie l&#39;alias, ce qui transforme de fait cette expression en
agrégat imbriqué, ce que la plupart des outils n&#39;attendent pas.

En soi, cela pose rarement problème, mais certains outils de BI génèrent des requêtes contenant des sous-requêtes qui réutilisent des alias de colonnes. Par
exemple, Power BI génère souvent des requêtes semblables à celle-ci :

```sql
SELECT
    sum(C1) AS C1,
    count(C1) AS C2
FROM
(
    SELECT sum(value) AS C1
    FROM test
    GROUP BY group_index
) AS TBL
```

Les références à `C1` peuvent générer l&#39;erreur suivante :

```plaintext
Code: 184. DB::Exception: Received from localhost:9000. DB::Exception: Aggregate function sum(C1) AS C1 is found
inside another aggregate function in query. (ILLEGAL_AGGREGATION)
```

Les autres bases de données ne résolvent généralement pas les alias de cette manière au même niveau et considèrent plutôt `C1` comme une colonne de la
sous-requête. Pour reproduire ce comportement dans ClickHouse et permettre à ces requêtes de s&#39;exécuter sans erreur, le pilote ODBC
active `prefer_column_name_to_alias`.

Dans la plupart des cas, l&#39;activation de ces paramètres ne devrait pas poser de problème. Toutefois, les utilisateurs dont le paramètre readonly est défini sur `1`
ne peuvent modifier aucun paramètre, même pour les requêtes `SELECT`. Pour ces utilisateurs, l&#39;activation de `SqlCompatibilitySettings` provoquera
une erreur. La section suivante explique comment faire fonctionner ce paramètre de configuration pour les utilisateurs en lecture seule.

## Faire fonctionner les paramètres de compatibilité SQL pour les utilisateurs en lecture seule {#readonly-users}

Lorsqu&#39;un utilisateur dont le paramètre readonly est défini sur `1` se connecte à ClickHouse via le driver ODBC avec le paramètre `SqlCompatibilitySettings` activé,
il rencontre une erreur, car le driver tente de modifier les paramètres de requête :

```plaintext
Code: 164. DB::Exception: Cannot modify 'cast_keep_nullable' setting in readonly mode. (READONLY)
Code: 164. DB::Exception: Cannot modify 'prefer_column_name_to_alias' setting in readonly mode. (READONLY)
```

Cela s&#39;explique par le fait que les utilisateurs en mode lecture seule ne sont pas autorisés à modifier les paramètres, même pour des requêtes `SELECT` individuelles.
Il existe plusieurs façons de résoudre ce problème.

**Option 1. Définir `readonly` sur `2`**

C&#39;est l&#39;option la plus simple. Définir `readonly` sur `2` permet de modifier les paramètres tout en conservant l&#39;utilisateur en mode lecture seule.

```sql
ALTER USER your_odbc_user MODIFY SETTING
    readonly = 2
```

Dans la plupart des cas, définir `readonly` sur 2 est la méthode la plus simple et la plus recommandée pour résoudre ce problème. Si
cela ne vous convient pas, utilisez la deuxième option.

**Option 2. Modifier les paramètres utilisateur pour qu’ils correspondent aux paramètres définis par le Driver ODBC.**

Cette méthode est tout aussi simple : modifiez les paramètres utilisateur afin qu’ils correspondent déjà aux valeurs que le Driver ODBC tente de définir.

```sql
ALTER USER your_odbc_user MODIFY SETTING
    cast_keep_nullable = 1,
    prefer_column_name_to_alias = 1
```

Avec cette modification, le driver ODBC peut toujours tenter d&#39;appliquer les paramètres, mais comme les valeurs correspondent déjà, aucune
modification n&#39;est réellement effectuée et l&#39;erreur est évitée.

Cette option est également simple, mais elle demande de la maintenance : les nouvelles versions du driver peuvent modifier la liste des paramètres ou en ajouter
de nouveaux pour des raisons de compatibilité. Si vous codez ces paramètres en dur pour votre utilisateur ODBC, vous devrez peut-être les mettre à jour chaque fois que le
driver ODBC se met à appliquer des paramètres supplémentaires.
