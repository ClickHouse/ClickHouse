## Prérequis {#prerequisites}

Pour suivre les exemples de cet article, vous devez :

* disposer d’une instance du serveur ClickHouse en cours d’exécution
* avoir installé `curl`. Sur Ubuntu ou Debian, exécutez `sudo apt install curl` ou consultez cette [documentation](https://curl.se/download.html) pour connaître la procédure d’installation.

## Vue d’ensemble {#overview}

L’interface HTTP vous permet d’utiliser ClickHouse sur n’importe quelle plateforme et depuis n’importe quel langage de programmation, sous la forme d’une API REST. L’interface HTTP est plus limitée que l’interface native, mais elle est mieux prise en charge par les différents langages.

Par défaut, `clickhouse-server` écoute sur les ports suivants :

* port 8123 pour HTTP
* port 8443 pour HTTPS (peut être activé)

Si vous effectuez une requête `GET /` sans aucun paramètre, un code de réponse 200 est renvoyé avec la chaîne &quot;Ok.&quot; :

```bash
$ curl 'http://localhost:8123/'
Ok.
```

&quot;Ok.&quot; est la valeur par défaut définie dans [`http_server_default_response`](/fr/reference/settings/server-settings/settings/http#http_server_default_response) et peut être modifiée au besoin.

Voir aussi : [Mises en garde concernant les codes de réponse HTTP](#http_response_codes_caveats).

## Interface utilisateur web {#web-ui}

ClickHouse intègre une interface utilisateur web, accessible à l&#39;adresse suivante :

```text
http://localhost:8123/play
```

L&#39;interface utilisateur web permet d&#39;afficher la progression pendant l&#39;exécution d&#39;une requête, d&#39;annuler des requêtes et de diffuser les résultats en continu.
Elle dispose d&#39;une fonctionnalité cachée permettant d&#39;afficher des graphiques et des graphes pour les pipelines de requête.

Une fois une requête exécutée avec succès, un bouton de téléchargement apparaît et vous permet de télécharger le résultat de la requête dans différents formats, notamment CSV, TSV, JSON, JSONLines, Parquet, Markdown ou tout format personnalisé pris en charge par ClickHouse. La fonctionnalité de téléchargement s&#39;appuie sur le cache de requêtes pour récupérer efficacement les résultats sans réexécuter la requête. Elle télécharge l&#39;ensemble de résultats complet, même si l&#39;UI n&#39;en a affiché qu&#39;une seule page parmi plusieurs.

L&#39;interface utilisateur web est conçue pour des professionnels comme vous.

<div className="ch-image-md">
  <Frame>
    ![Capture d'écran de l'interface utilisateur web de ClickHouse](/images/play.webp)
  </Frame>
</div>

Dans les scripts de vérification de l&#39;état de santé, utilisez la requête `GET /ping`. Ce handler renvoie toujours &quot;Ok.&quot; (avec un saut de ligne à la fin). Disponible à partir de la version 18.12.13. Voir aussi `/replicas_status` pour vérifier le retard d&#39;une réplique.

```bash
$ curl 'http://localhost:8123/ping'
Ok.
$ curl 'http://localhost:8123/replicas_status'
Ok.
```

## Exécution de requêtes via HTTP/HTTPS {#querying}

Il existe trois façons d’exécuter des requêtes via HTTP/HTTPS :

* envoyer la requête dans le paramètre d’URL &#39;query&#39;
* utiliser la méthode POST.
* envoyer le début de la requête dans le paramètre &#39;query&#39;, et le reste via POST

<Note>
  Par défaut, la taille de l’URL est limitée à 1 Mio ; cette limite peut être modifiée à l’aide du paramètre `http_max_uri_size`.
</Note>

En cas de succès, vous recevez le code de réponse 200 et l’ensemble de résultats dans le corps de la réponse.
En cas d’erreur, vous recevez le code de réponse 500 et un texte décrivant l’erreur dans le corps de la réponse.

Les requêtes GET sont en mode &#39;readonly&#39;. Autrement dit, pour les requêtes qui modifient des données, seule la méthode POST peut être utilisée.
Vous pouvez envoyer la requête elle-même soit dans le corps de la requête POST, soit dans le paramètre d’URL. Voyons quelques exemples.

Dans l’exemple ci-dessous, curl est utilisé pour envoyer la requête `SELECT 1`. Notez l’encodage URL de l’espace : `%20`.

```bash title="command"
curl 'http://localhost:8123/?query=SELECT%201'
```

```response title="Response"
1
```

Dans cet exemple, wget est utilisé avec les paramètres `-nv` (mode non verbeux) et `-O-` pour afficher l’ensemble de résultats dans le terminal.
Dans ce cas, il n’est pas nécessaire d’encoder l’espace dans l’URL :

```bash title="command"
wget -nv -O- 'http://localhost:8123/?query=SELECT 1'
```

```response
1
```

Dans cet exemple, nous redirigeons une requête HTTP brute vers netcat à l&#39;aide d&#39;un pipe :

```bash title="command"
echo -ne 'GET /?query=SELECT%201 HTTP/1.0\r\n\r\n' | nc localhost 8123
```

```response title="response"
HTTP/1.0 200 OK
X-ClickHouse-Summary: {"read_rows":"1","read_bytes":"1","written_rows":"0","written_bytes":"0","total_rows_to_read":"1","result_rows":"0","result_bytes":"0","elapsed_ns":"4505959","memory_usage":"1111711"}
```

Comme vous pouvez le constater, la commande `curl` est peu pratique, car les espaces doivent être échappés dans l&#39;URL.
Bien que `wget` échappe lui-même tous les caractères, nous déconseillons son utilisation, car il ne fonctionne pas correctement avec HTTP 1.1 lorsque keep-alive et Transfer-Encoding: chunked sont utilisés.

```bash
$ echo 'SELECT 1' | curl 'http://localhost:8123/' --data-binary @-
1

$ echo 'SELECT 1' | curl 'http://localhost:8123/?query=' --data-binary @-
1

$ echo '1' | curl 'http://localhost:8123/?query=SELECT' --data-binary @-
1
```

Si une partie de la requête est envoyée dans le paramètre et l&#39;autre dans le POST, un saut de ligne est inséré entre ces deux parties.
Par exemple, ceci ne fonctionnera pas :

```bash
$ echo 'ECT 1' | curl 'http://localhost:8123/?query=SEL' --data-binary @-
Code: 59, e.displayText() = DB::Exception: Syntax error: failed at position 0: SEL
ECT 1
, expected One of: SHOW TABLES, SHOW DATABASES, SELECT, INSERT, CREATE, ATTACH, RENAME, DROP, DETACH, USE, SET, OPTIMIZE., e.what() = DB::Exception
```

Par défaut, les données sont renvoyées au format [`TabSeparated`](/fr/reference/formats/TabSeparated/TabSeparated).

Pour obtenir un autre format, utilisez la clause `FORMAT` dans la requête. Par exemple :

```bash title="command"
wget -nv -O- 'http://localhost:8123/?query=SELECT 1, 2, 3 FORMAT JSON'
```

```response title="Response"
{

    [
        {
            "name": "1",
            "type": "UInt8"
        },
        {
            "name": "2",
            "type": "UInt8"
        },
        {
            "name": "3",
            "type": "UInt8"
        }
    ],

    "data":
    [
        {
            "1": 1,
            "2": 2,
            "3": 3
        }

    "rows": 1,

    "statistics":
    {
        "elapsed": 0.000515,
        "rows_read": 1,
        "bytes_read": 1

```

Vous pouvez utiliser le paramètre d’URL `default_format` pour définir un format par défaut autre que `TabSeparated`. L’en-tête `X-ClickHouse-Format` sélectionne explicitement le format de la réponse : comme il s’agit d’un alias du paramètre `output_format`, il prend également le pas sur une clause `FORMAT` présente dans la requête. Il ne modifie jamais la manière dont le corps de la requête d’un `INSERT` est analysé ; utilisez pour cela `input_format` ou `format`. Pour rétablir le comportement des versions antérieures à 26.8, dans lesquelles l’en-tête était un alias de `default_format` et ne prenait pas le pas sur une clause `FORMAT`, désactivez le paramètre `http_x_clickhouse_format_overrides_output_format` (dans un profil utilisateur ou en tant que paramètre d’URL ; comme les paramètres de format eux-mêmes, il peut être modifié en mode lecture seule).

```bash
$ echo 'SELECT 1 FORMAT Pretty' | curl 'http://localhost:8123/?' --data-binary @-
┏━━━┓
┃ 1 ┃
┡━━━┩
│ 1 │
└───┘
```

Vous pouvez utiliser la méthode POST avec des requêtes paramétrées. Les paramètres sont indiqués entre accolades avec leur nom et leur type, par exemple `{name:Type}`. Les valeurs des paramètres sont transmises via `param_name` :

```bash
$ curl -X POST -F 'query=select {p1:UInt8} + {p2:UInt8}' -F "param_p1=3" -F "param_p2=4" 'http://localhost:8123/'

7
```

## Accéder aux tables via des Chemins d’URL et construire des requêtes {#tables-as-files}

Disponible à partir de ClickHouse 26.8.

L’interface HTTP peut interpréter un Chemin d’URL comme une base de données, une table, un format de sortie et une méthode de compression. Les paramètres d’URL permettent ensuite d’ajuster la structure de l’ensemble de résultats, si bien que les requêtes de lecture simples ne nécessitent pas de SQL. Ces fonctionnalités sont activées par défaut depuis ClickHouse 26.10 ; dans les versions 26.8 et 26.9, elles devaient être activées explicitement.

### Paramètres de routage des Chemins {#enabling-path-routing}

L’interprétation des Chemins est soumise à deux niveaux de contrôle :

1. Le paramètre de configuration `http_allow_path_requests`, défini au niveau du serveur, permet à l’interface HTTP d’acheminer les requêtes de type Chemin vers le handler de requêtes. Il est activé par défaut ; définissez-le sur `0` pour que tout Chemin ne correspondant pas à un handler configuré renvoie à nouveau une erreur `404` :

```xml
<clickhouse>
    <http_allow_path_requests>0</http_allow_path_requests>
</clickhouse>
```

2. Les paramètres par utilisateur ci-dessous déterminent la manière dont un Chemin routé est interprété. Tous, à l&#39;exception de `http_allow_filters_as_unrecognized_url_parameters`, sont activés par défaut, et chacun peut être activé ou désactivé par utilisateur, rôle ou profil :

| Paramètre                                           | Effet                                                                                                  |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `http_allow_table_as_file`                          | Interprète le dernier composant de Chemin comme `table`, `table.format` ou `table.format.compression`. |
| `http_allow_database_as_path`                       | Interprète un composant de Chemin initial `/database/` comme la base de données courante.              |
| `http_allow_filters_as_path`                        | Interprète les composants de Chemin de type Hive `/name=value/` comme des filtres `WHERE`.             |
| `http_allow_filters_as_unrecognized_url_parameters` | Interprète les paramètres d’URL non reconnus comme des filtres `WHERE`. Désactivé par défaut.          |

<Note>
  Le routage intervient avant l&#39;authentification ; il ne peut donc pas dépendre d&#39;un paramètre par utilisateur. Lorsque `http_allow_path_requests` est désactivé, un Chemin inconnu renvoie une erreur `404` dès le stade pre-authentication. Une fois le routage et l&#39;authentification effectués, les paramètres par utilisateur déterminent la manière dont le Chemin est interprété, ce qui vous permet d&#39;activer ou de désactiver la fonctionnalité de manière sélective pour un utilisateur, un rôle ou un profil.
</Note>

<Note>
  `http_allow_filters_as_unrecognized_url_parameters` reste désactivé par défaut, car il s&#39;applique à toutes les requêtes de l&#39;interface HTTP, y compris à l&#39;endpoint `/?query=...` : lorsqu&#39;il est activé, tout paramètre d’URL non reconnu ajouté par un client devient un filtre de la requête. Un nom de paramètre mal orthographié n&#39;est alors plus signalé par `UNKNOWN_SETTING`, mais provoque une erreur `UNKNOWN_IDENTIFIER` — ou, si le nom correspond par hasard à une colonne de la table interrogée, filtre silencieusement l&#39;ensemble de résultats.
</Note>

### Accéder aux tables comme à des fichiers {#table-as-file-examples}

Lorsque `http_allow_table_as_file` est activé, une requête vers `/table.format.compression` est traitée comme `SELECT * FROM table`. `http_allow_database_as_path` autorise en outre `/database/table.format.compression`.

```bash
# SELECT * FROM my_db.hits, formatted as CSV
curl 'http://localhost:8123/my_db/hits.csv'

# The same result, compressed with gzip
curl 'http://localhost:8123/my_db/hits.csv.gz' | gzip -d
```

Les extensions de format et de compression sont reconnues sans tenir compte de la casse : `hits.csv` et `hits.CSV` sont donc équivalents.

Un paramètre d’URL `format` ou `output_format` explicite surcharge le format indiqué dans le Chemin. Ce n’est pas le cas de `default_format` : il fournit uniquement le format à utiliser lorsqu’aucun autre n’est sélectionné, et l’extension du Chemin est plus spécifique. Un paramètre `compression` explicite doit correspondre à la compression indiquée dans le Chemin ; des valeurs contradictoires déclenchent une exception.

### Construire une requête {#query-construction}

Les paramètres suivants encapsulent la requête de base dans une table dérivée. Ils se combinent entre eux ainsi qu’avec une requête existante. Vous pouvez les fournir sous forme de paramètres d’URL HTTP, dans une clause `SETTINGS` au sein de la requête ou via un profil utilisateur.

| Paramètre                                                                                                                    | Effet                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `select`                                                                                                                     | `SELECT <expression_list> FROM (…)`                                                                                                                                                                                                                                   |
| `filter`                                                                                                                     | Ajoute `WHERE <expression>`. Plusieurs paramètres d’URL `filter` sont combinés avec `AND`.                                                                                                                                                                            |
| `order`                                                                                                                      | Ajoute `ORDER BY <expression_list>`.                                                                                                                                                                                                                                  |
| `sort`                                                                                                                       | Ajoute `ORDER BY` à partir d’une liste d’identifiants ou de positions de colonnes séparés par des virgules, chacun pouvant être précédé d’un préfixe facultatif `+` (croissant) ou `-` (décroissant), par exemple `sort=a,-b`. Ne peut pas être combiné avec `order`. |
| [`limit`](/fr/reference/settings/session-settings/other#limit) et [`offset`](/fr/reference/settings/session-settings/other#offset) | Ajoutent `LIMIT <n> OFFSET <m>`. Tous deux acceptent des valeurs négatives pour sélectionner les dernières lignes, ainsi que des valeurs fractionnaires représentant une proportion des lignes.                                                                       |
| `page`                                                                                                                       | Définit `offset = limit * (page - 1)`. Nécessite `limit` et ne peut pas être combiné avec `offset`.                                                                                                                                                                   |

```bash
# Filter my_db.hits, sort by a descending, and return the first 10 rows
curl 'http://localhost:8123/my_db/hits?filter=a%3E0&sort=-a&limit=10'

# Return the second page of 100 rows
curl 'http://localhost:8123/my_db/hits?limit=100&page=2'
```

#### Modifier une requête existante {#modify-an-existing-query}

Les paramètres de construction ne se limitent pas aux requêtes par Chemin : ils structurent également les requêtes que vous écrivez vous-même. La requête devient alors la table dérivée, de sorte que les paramètres s&#39;appliquent à son ensemble de résultats plutôt que d&#39;y être fusionnés. Par exemple, `?query=SELECT a, b FROM hits&filter=a > 0&sort=-b&limit=10` est exécutée comme suit :

```sql
SELECT * FROM (SELECT a, b FROM hits) WHERE a > 0 ORDER BY b DESC LIMIT 10
```

C’est utile pour paginer, trier ou restreindre l’ensemble de résultats d’une requête définie ailleurs — dans une requête de tableau de bord enregistrée, un `predefined_query_handler` ou un client qui vous permet seulement d’ajouter des paramètres d’URL à la fin :

```bash
# Page through the result of an arbitrary query without editing the query text
curl 'http://localhost:8123/?query=SELECT+a,+b+FROM+hits+GROUP+BY+a,+b&limit=100&page=3'

# Keep only some of the resulting columns and rows
curl -G 'http://localhost:8123/' --data-urlencode 'query=SELECT * FROM hits' --data-urlencode 'select=a, b' --data-urlencode 'filter=b != 0'

# The last 5 rows of an aggregate (a negative `limit` selects from the tail)
curl 'http://localhost:8123/?query=SELECT+a,+count()+FROM+hits+GROUP+BY+a+ORDER+BY+a&limit=-5'
```

Comme ces paramètres encapsulent la requête au lieu de la réécrire, ils se combinent avec une clause `FORMAT` et avec un `ORDER BY` à l&#39;intérieur de la requête, et ils ne modifient jamais les lignes écrites par un `INSERT` : un paramètre de construction appliqué à un statement `INSERT ... SELECT` agit sur l&#39;ensemble de résultats (vide) du statement lui-même, et non sur son `SELECT` source. Pour agir sur la source, placez le paramètre dans la clause `SETTINGS` du `SELECT` lui-même :

```sql
-- Inserts all 10 rows: `limit` applies to the INSERT statement, not to its SELECT
INSERT INTO t SETTINGS limit = 2 SELECT number FROM numbers(10);

-- Inserts 2 rows: `limit` applies to the SELECT itself
INSERT INTO t SELECT number FROM numbers(10) SETTINGS limit = 2;
```

<Warning>
  `filter` n&#39;est pas un mécanisme de contrôle d&#39;accès. Il enveloppe la requête dans une sous-requête à laquelle il applique une clause `WHERE` : les données sous-jacentes peuvent donc être lues et traitées avant l&#39;application du filtre. Pour restreindre les lignes auxquelles un utilisateur peut accéder, utilisez des [politiques de ligne](/fr/concepts/features/security/access-rights#row-policy-management) ou [`additional_table_filters`](/fr/reference/settings/session-settings/additional#additional_table_filters).
</Warning>

### Surcharger les formats et la compression {#format-and-compression-overrides}

| Paramètre        | Effet                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `output_format`  | Surcharge le format de sortie. Il a préséance sur la clause `FORMAT` de la requête, l’extension du Chemin, `format` et `default_format`. Il peut également être défini à l’aide de l’en-tête `X-ClickHouse-Format`. Avec `http_x_clickhouse_format_overrides_output_format = 0`, l’en-tête définit plutôt `default_format`, comme dans les versions antérieures à la 26.8. |
| `input_format`   | Surcharge le format d’entrée pour `INSERT`. Il a préséance sur la clause `FORMAT` de la requête et sur `format`.                                                                                                                                                                                                                                                           |
| `format`         | Surcharge le format dans les deux sens, sauf si un paramètre propre à un sens est fourni.                                                                                                                                                                                                                                                                                  |
| `default_format` | Définit le format de sortie lorsque la requête ne comporte ni clause `FORMAT`, ni extension de Chemin, ni aucune autre surcharge de format.                                                                                                                                                                                                                                |
| `compression`    | Compresse le corps de la réponse, par exemple avec `compression=gz`. Ce paramètre est indépendant de l’en-tête HTTP `Content-Encoding` et du paramètre `compress` natif de ClickHouse.                                                                                                                                                                                     |

Les paramètres de format fonctionnent également avec d’autres protocoles, notamment le client natif et `clickhouse-local`. `input_format` et `output_format` correspondent aux options `--input-format` et `--output-format`. Dans `clickhouse-local`, l’option `--format` correspond au paramètre bidirectionnel `format`, tandis que dans `clickhouse-client` elle conserve sa signification historique, limitée à la sortie, et correspond à `output_format`.

`compression` est propre à la mise en forme des réponses HTTP et est consommé avant l’exécution de la requête. Vous pouvez le fournir via un paramètre d’URL HTTP, une extension de Chemin ou un profil utilisateur. Il est en revanche rejeté s’il figure dans une clause `SETTINGS` au sein de la requête.

Les réponses HTTP binaires et compressées incluent un en-tête `Content-Disposition: attachment; filename=…`. Le nom de fichier est dérivé du Chemin d’URL ; si le Chemin n’en fournit pas, il prend la forme `result.<format>.<compression>`.

### Utiliser une table de Chemin avec une requête {#implicit-table}

Lorsque le Chemin identifie une table et que vous fournissez également un paramètre `query`, la table de Chemin est exposée via [`implicit_table_at_top_level`](/fr/reference/settings/session-settings/implicit#implicit_table_at_top_level). Un `SELECT` sans clause `FROM` lit alors les données de la table de Chemin :

```bash
# Read columns a and b from my_db.hits without a FROM clause
curl 'http://localhost:8123/my_db/hits.CSV?query=SELECT+a,+b'
```

Si la requête contient déjà une clause `FROM`, le composant de Chemin sert uniquement à définir le nom du fichier téléchargé.

### Téléverser des données vers une table de chemin {#path-table-inserts}

Une requête HTTP `PUT` vers `/database/table.format` insère le corps de la requête dans une table existante. Par défaut, c’est l’extension du Chemin qui fournit le format d’entrée. Comme pour un `INSERT` classique, le paramètre `input_format` a préséance sur le format du Chemin, suivi du paramètre bidirectionnel `format`. La requête doit contenir au moins un octet décodé et ne doit pas inclure de paramètre `query`. Cette méthode est utile lorsqu’un nom de fichier contient déjà à la fois la table cible et le format d’entrée :

```bash
printf '1,"one"\n2,"two"\n' \
  | curl -X PUT -H 'Content-Type: text/csv' --data-binary @- \
      'http://localhost:8123/my_db/hits.CSV'

printf '{"a":3,"b":"three"}\n' \
  | curl -X PUT -H 'Content-Type: application/json' --data-binary @- \
      'http://localhost:8123/my_db/hits.JSONEachRow'
```

La table doit déjà exister. Pour un téléversement préfixé par la base de données, `http_allow_database_as_path` active le
Chemin `/database/table.format`. Un téléversement non qualifié vers `/table.format` nécessite toujours
`http_allow_table_as_file`. Le corps de la requête peut utiliser un suffixe de compression tel que `.CSV.gz` ; le serveur
le décompresse avant d&#39;insérer les lignes. Les téléversements `PUT` vers une table de chemin suivent la sémantique `INSERT` ordinaire : répéter
la même requête peut donc insérer les lignes une seconde fois. La création automatique, l&#39;inférence de schéma et les téléversements en plusieurs parties ne sont pas
pris en charge. Utilisez la forme standard [`INSERT` via HTTP](#insert-queries) lorsque le comportement de la requête ou du téléversement doit
être personnalisé.

Le dernier composant de Chemin est décodé (encodage pourcentage) après la division du Chemin ; un point de format encodé tel que
`hits%2ECSV` est donc également accepté.

```bash
# The path suffix describes the compressed request body.
gzip -c rows.csv \
  | curl -X PUT --data-binary @- \
      'http://localhost:8123/my_db/hits.CSV.gz'
```

## Requêtes d’insertion via HTTP/HTTPS {#insert-queries}

La méthode `POST` traditionnelle de transmission des données est utile lorsque la requête doit être fournie explicitement. Vous pouvez écrire le début de la requête dans le paramètre d’URL et utiliser POST pour transmettre les données à insérer. Ces données peuvent être, par exemple, un export de base de données MySQL au format tab-separated. De cette manière, la requête `INSERT` remplace `LOAD DATA LOCAL INFILE` de MySQL.

### Exemples {#examples}

Pour créer une table :

```bash
$ echo 'CREATE TABLE t (a UInt8) ENGINE = Memory' | curl 'http://localhost:8123/' --data-binary @-
```

Pour insérer des données à l&#39;aide de la requête `INSERT` habituelle :

```bash
$ echo 'INSERT INTO t VALUES (1),(2),(3)' | curl 'http://localhost:8123/' --data-binary @-
```

Pour envoyer les données séparément de la requête :

```bash
$ echo '(4),(5),(6)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20VALUES' --data-binary @-
```

Vous pouvez spécifier n’importe quel format de données, par exemple le format &#39;Values&#39;, qui est celui utilisé dans `INSERT INTO t VALUES` :

```bash
$ echo '(7),(8),(9)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20Values' --data-binary @-
```

Pour insérer des données à partir d&#39;un export de base de données au format tab-separated, spécifiez le format correspondant :

```bash
$ echo -ne '10\n11\n12\n' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20TabSeparated' --data-binary @-
```

Il en va de même pour tout autre [format d’entrée](/fr/reference/formats), par exemple CSV avec une ligne d’en-tête, ou un objet JSON par ligne :

```bash
$ echo -ne 'a\n13\n14\n' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20CSVWithNames' --data-binary @-
$ echo '{"a":15} {"a":16}' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20JSONEachRow' --data-binary @-
```

Pour insérer le contenu d&#39;un fichier, passez son nom à `--data-binary` en le préfixant par `@` :

```bash
$ echo -ne '17\n18\n' > data.csv
$ curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20FORMAT%20CSV' --data-binary @data.csv
```

<Warning>
  Utilisez `--data-binary`, et non `-d` (`--data`). L’option `-d @file` de curl supprime les sauts de ligne du fichier : les deux lignes ci-dessus sont donc reçues sous la forme d’une seule valeur, `1718`.
</Warning>

Pour lire le contenu de la table :


Pour supprimer la table :

```bash
$ echo 'DROP TABLE t' | curl 'http://localhost:8123/' --data-binary @-
```

Pour les requêtes qui aboutissent sans renvoyer de table de données, le corps de la réponse est vide.

### Insertion de données Protobuf {#insert-protobuf}

Les formats binaires tels que [`Protobuf`](/fr/reference/formats/Protobuf/Protobuf) s’envoient de la même manière, puisque `--data-binary` transmet les octets tels quels.
Les paramètres requis par le format, comme [`format_schema`](/fr/reference/settings/formats/format-schema#format_schema), sont transmis sous forme de paramètres d’URL, aux côtés de `query`, comme tout autre paramètre.

Les exemples ci-dessous utilisent cette table ainsi que le fichier de schéma `message.proto`, placé dans le répertoire [`format_schema_path`](/fr/reference/settings/server-settings/settings/format#format_schema_path) du serveur :

```bash
$ echo 'CREATE TABLE protobuf_messages (name String, surname String, birthDate UInt32, phoneNumbers Array(String)) ENGINE = Memory' | curl 'http://localhost:8123/' --data-binary @-
```

```protobuf
syntax = "proto3";

message MessageType {
  string name = 1;
  string surname = 2;
  uint32 birthDate = 3;
  repeated string phoneNumbers = 4;
}
```

Pour obtenir un fichier de messages Protobuf à insérer, cet exemple fait générer ce fichier par ClickHouse :

```bash
$ echo "SELECT 'Aisha' AS name, 'Khan' AS surname, 19920815 AS birthDate, ['(555) 247-8903', '(555) 612-3457'] AS phoneNumbers FORMAT Protobuf" | curl 'http://localhost:8123/?format_schema=message:MessageType' --data-binary @- > messages.bin
```

Pour insérer le fichier, indiquez le fichier de schéma et le type de message dans `format_schema` :

```bash
$ curl 'http://localhost:8123/?query=INSERT%20INTO%20protobuf_messages%20FORMAT%20Protobuf&format_schema=message:MessageType' --data-binary @messages.bin
```

Lorsqu&#39;aucun fichier de schéma ne peut être placé sur le serveur, comme c&#39;est le cas dans ClickHouse Cloud, envoyez directement le schéma en définissant [`format_schema_source`](/fr/reference/settings/formats/format-schema#format_schema_source) sur `string`, et indiquez le nom du type de message dans [`format_schema_message_name`](/fr/reference/settings/formats/format-schema#format_schema_message_name).
L&#39;option `--url-query` de curl (curl 7.87 et versions ultérieures) encode chaque paramètre au format URL, ce qui permet d&#39;écrire la requête et le schéma tels quels :

```bash
$ curl 'http://localhost:8123/' \
    --url-query 'query=INSERT INTO protobuf_messages FORMAT Protobuf' \
    --url-query 'format_schema_source=string' \
    --url-query 'format_schema=syntax = "proto3"; message MessageType { string name = 1; string surname = 2; uint32 birthDate = 3; repeated string phoneNumbers = 4; }' \
    --url-query 'format_schema_message_name=MessageType' \
    --data-binary @messages.bin
```

Pour lire le contenu de la table :

```bash
$ curl 'http://localhost:8123/?query=SELECT%20*%20FROM%20protobuf_messages'
Aisha	Khan	19920815	['(555) 247-8903','(555) 612-3457']
Aisha	Khan	19920815	['(555) 247-8903','(555) 612-3457']
```

`Protobuf` attend que chaque message soit préfixé par sa longueur, encodée sous forme de varint.
Pour un message unique sans préfixe, utilisez [`ProtobufSingle`](/fr/reference/formats/Protobuf/ProtobufSingle) ; pour des lignes envoyées sous forme de sous-messages d&#39;un même message `Envelope`, utilisez [`ProtobufList`](/fr/reference/formats/Protobuf/ProtobufList).

## Compression {#compression}

La compression permet de réduire le trafic réseau lors de la transmission d&#39;un grand volume de données, ou de créer des exports de base de données directement compressés.

Vous pouvez utiliser le format de compression interne de ClickHouse pour transmettre des données. Les données compressées sont dans un format non standard et nécessitent le programme `clickhouse-compressor` pour être manipulées. Celui-ci est installé par défaut avec le paquet `clickhouse-client`.

Pour améliorer les performances d&#39;insertion de données, désactivez la vérification des sommes de contrôle côté serveur à l&#39;aide du paramètre [`http_native_compression_disable_checksumming_on_decompress`](/fr/reference/settings/session-settings/http#http_native_compression_disable_checksumming_on_decompress).

Si vous indiquez `compress=1` dans l&#39;URL, le serveur compresse les données qu&#39;il vous envoie. Si vous indiquez `decompress=1` dans l&#39;URL, le serveur décompresse les données que vous transmettez avec la méthode `POST`.

Vous pouvez également utiliser la [compression HTTP](https://en.wikipedia.org/wiki/HTTP_compression). ClickHouse prend en charge les [méthodes de compression](https://en.wikipedia.org/wiki/HTTP_compression#Content-Encoding_tokens) suivantes :

* `gzip`
* `br`
* `deflate`
* `xz`
* `zstd`
* `lz4`
* `bz2`
* `snappy`

Pour envoyer une requête `POST` compressée, ajoutez l&#39;en-tête de requête `Content-Encoding: compression_method`.

Pour que ClickHouse compresse la réponse, ajoutez l&#39;en-tête `Accept-Encoding: compression_method` à la requête.

Le paramètre [`http_zlib_compression_level`](/fr/reference/settings/session-settings/http#http_zlib_compression_level) permet de configurer le niveau de compression des données pour toutes les méthodes de compression.

<Info>
  Certains clients HTTP peuvent décompresser par défaut les données reçues du serveur (avec `gzip` et `deflate`). Vous risquez donc d&#39;obtenir des données décompressées même si vous utilisez correctement les paramètres de compression.
</Info>

## Exemples {#examples-compression}

Pour envoyer des données compressées au serveur :

```bash
echo "SELECT 1" | gzip -c | \
curl -sS --data-binary @- -H 'Content-Encoding: gzip' 'http://localhost:8123/'
```

Pour récupérer l&#39;archive de données compressée depuis le serveur :

```bash
curl -vsS "http://localhost:8123/?enable_http_compression=1" \
-H 'Accept-Encoding: gzip' --output result.gz -d 'SELECT number FROM system.numbers LIMIT 3'

zcat result.gz
0
1
2
```

Pour recevoir des données compressées depuis le serveur, en les décompressant avec gunzip :

```bash
curl -sS "http://localhost:8123/?enable_http_compression=1" \
-H 'Accept-Encoding: gzip' -d 'SELECT number FROM system.numbers LIMIT 3' | gunzip -
0
1
2
```

## Utilisation des sessions ClickHouse avec le protocole HTTP {#using-clickhouse-sessions-in-the-http-protocol}

Vous pouvez également utiliser les sessions ClickHouse avec le protocole HTTP. Pour cela, ajoutez le paramètre `GET` `session_id` à la requête. N’importe quelle chaîne peut servir d’ID de session.

Par défaut, la session se termine après 60 secondes d’inactivité. Pour modifier ce délai d’expiration (en secondes), changez le paramètre `default_session_timeout` dans la configuration du serveur ou ajoutez le paramètre `GET` `session_timeout` à la requête.

Pour vérifier le statut de la session, utilisez le paramètre `session_check=1`. Une session ne peut exécuter qu’une seule requête à la fois.

Vous pouvez suivre la progression d’une requête grâce aux en-têtes de réponse `X-ClickHouse-Progress`. Pour cela, activez [`send_progress_in_http_headers`](/fr/reference/settings/session-settings/send#send_progress_in_http_headers).

Voici un exemple de séquence d’en-têtes :

```text
X-ClickHouse-Progress: {"read_rows":"261636","read_bytes":"2093088","total_rows_to_read":"1000000","elapsed_ns":"14050417","memory_usage":"22205975"}
X-ClickHouse-Progress: {"read_rows":"654090","read_bytes":"5232720","total_rows_to_read":"1000000","elapsed_ns":"27948667","memory_usage":"83400279"}
X-ClickHouse-Progress: {"read_rows":"1000000","read_bytes":"8000000","total_rows_to_read":"1000000","elapsed_ns":"38002417","memory_usage":"80715679"}
```

Les champs d&#39;en-tête possibles sont :

| Champ d&#39;en-tête  | Description                                                                        |
| -------------------- | ---------------------------------------------------------------------------------- |
| `read_rows`          | Nombre de lignes lues.                                                             |
| `read_bytes`         | Volume de données lues, en octets.                                                 |
| `total_rows_to_read` | Nombre total de lignes à lire.                                                     |
| `written_rows`       | Nombre de lignes écrites.                                                          |
| `written_bytes`      | Volume de données écrites, en octets.                                              |
| `elapsed_ns`         | Durée d&#39;exécution de la requête, en nanosecondes.                              |
| `memory_usage`       | Mémoire utilisée par la requête, en octets. (**Disponible à partir de la v25.11**) |

Les requêtes en cours d&#39;exécution ne s&#39;arrêtent pas automatiquement en cas de perte de la connexion HTTP. L&#39;analyse et la mise en forme des données étant effectuées côté serveur, l&#39;utilisation du réseau peut s&#39;avérer inefficace.

Les paramètres facultatifs suivants sont disponibles :

| Paramètres               | Description                                                                                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `query_id` (facultatif)  | Peut être transmis comme identifiant de requête (n&#39;importe quelle chaîne). [`replace_running_query`](/fr/reference/settings/session-settings/replace-running-query#replace_running_query) |
| `quota_key` (facultatif) | Peut être transmis comme clé de quota (n&#39;importe quelle chaîne). [« Quotas »](/fr/concepts/features/configuration/server-config/quotas)                                                   |

L&#39;interface HTTP permet de transmettre des données externes (tables temporaires externes) pour l&#39;exécution de requêtes. Pour plus d&#39;informations, consultez [« Données externes pour le traitement des requêtes »](/fr/reference/engines/table-engines/special/external-data).

## Mise en mémoire tampon de la réponse {#response-buffering}

La mise en mémoire tampon de la réponse peut être activée côté serveur. Les paramètres d’URL suivants sont prévus à cet effet :

* `buffer_size`
* `wait_end_of_query`

Les paramètres suivants peuvent être utilisés :

* [`http_response_buffer_size`](/fr/reference/settings/session-settings/http-response#http_response_buffer_size)
* [`http_wait_end_of_query`](/fr/reference/settings/session-settings/http#http_wait_end_of_query)

`buffer_size` détermine le nombre d’octets de l’ensemble de résultats à mettre en tampon dans la mémoire du serveur. Si le corps de l’ensemble de résultats dépasse ce seuil, le tampon est écrit dans le canal HTTP et les données restantes sont envoyées directement sur ce canal.

Pour que l’intégralité de la réponse soit mise en mémoire tampon, définissez `wait_end_of_query=1`. Dans ce cas, les données qui ne sont pas stockées en mémoire sont mises en tampon dans un fichier temporaire sur le serveur.

Par exemple :

```bash
curl -sS 'http://localhost:8123/?max_result_bytes=4000000&buffer_size=3000000&wait_end_of_query=1' -d 'SELECT toUInt8(number) FROM system.numbers LIMIT 9000000 FORMAT RowBinary'
```

<Tip>
  Utilisez la mise en tampon pour éviter qu’une erreur de traitement des requêtes ne survienne après l’envoi du code de réponse et des en-têtes HTTP au client. Dans ce cas, un message d’erreur est ajouté à la fin du corps de la réponse, et l’erreur ne peut être détectée qu’à l’étape d’analyse client-side.
</Tip>

## Définir un rôle avec des paramètres de requête {#setting-role-with-query-parameters}

Cette fonctionnalité a été ajoutée dans ClickHouse 24.4.

Dans certains cas, il peut être nécessaire de définir au préalable le rôle accordé avant d&#39;exécuter le statement proprement dit.
Toutefois, il n&#39;est pas possible d&#39;envoyer `SET ROLE` et le statement en même temps, car les multi-statements ne sont pas autorisés :

```bash
curl -sS "http://localhost:8123" --data-binary "SET ROLE my_role;SELECT * FROM my_table;"
```

La commande ci-dessus renvoie une erreur :

```sql
Code: 62. DB::Exception: Syntax error (Multi-statements are not allowed)
```

Pour contourner cette limitation, utilisez plutôt le paramètre de requête `role` :

```bash
curl -sS "http://localhost:8123?role=my_role" --data-binary "SELECT * FROM my_table;"
```

Cela équivaut à exécuter `SET ROLE my_role` avant le statement.

Il est également possible d&#39;indiquer plusieurs paramètres de requête `role` :

```bash
curl -sS "http://localhost:8123?role=my_role&role=my_other_role" --data-binary "SELECT * FROM my_table;"
```

Dans ce cas, `?role=my_role&role=my_other_role` produit un effet similaire à l’exécution de `SET ROLE my_role, my_other_role` avant le statement.

Le paramètre de requête `role` n’est pas affecté par le paramètre du serveur `access_control_improvements.readonly_restricts_set_role`, qui interdit uniquement les statements `SET ROLE` et `SET DEFAULT ROLE`.

## Mises en garde concernant les codes de réponse HTTP {#http_response_codes_caveats}

En raison des limites du protocole HTTP, un code de réponse HTTP 200 ne garantit pas qu&#39;une requête a abouti.

Voici un exemple :

```bash
curl -v -Ss "http://localhost:8123/?max_block_size=1&query=select+sleepEachRow(0.001),throwIf(number=2)from+numbers(5)"
*   Trying 127.0.0.1:8123...
...
< HTTP/1.1 200 OK
...
Code: 395. DB::Exception: Value passed to 'throwIf' function is non-zero: while executing 'FUNCTION throwIf(equals(number, 2) :: 1) -> throwIf(equals(number, 2))
```

Ce comportement s&#39;explique par la nature du protocole HTTP. L&#39;en-tête HTTP est envoyé en premier avec un code HTTP 200, suivi du corps HTTP, puis l&#39;erreur est injectée dans le corps sous forme de texte en clair.

Ce comportement est indépendant du format utilisé, qu&#39;il s&#39;agisse de `Native`, `TSV` ou `JSON` : le message d&#39;erreur se trouvera toujours au milieu du flux de réponse.

Vous pouvez atténuer ce problème en activant `wait_end_of_query=1` ([Mise en Mémoire Tampon de la Réponse](#response-buffering)). Dans ce cas, l&#39;envoi de l&#39;en-tête HTTP est différé jusqu&#39;à ce que l&#39;intégralité de la requête soit résolue. Cela ne résout toutefois pas complètement le problème, car l&#39;ensemble de résultats doit toujours tenir dans [`http_response_buffer_size`](/fr/reference/settings/session-settings/http-response#http_response_buffer_size), et d&#39;autres paramètres comme [`send_progress_in_http_headers`](/fr/reference/settings/session-settings/send#send_progress_in_http_headers) peuvent empêcher ce report de l&#39;en-tête.

<Tip>
  La seule façon d&#39;intercepter toutes les erreurs est d&#39;analyser le corps HTTP avant son analyse selon le format requis.
</Tip>

Dans ClickHouse, ces exceptions suivent un format uniforme, présenté ci-dessous, quel que soit le format utilisé (par ex. `Native`, `TSV`, `JSON`, etc.) lorsque `http_write_exception_in_output_format=0` (valeur par défaut). Il est ainsi facile d&#39;analyser et d&#39;extraire les messages d&#39;erreur côté client.

```text
\r\n
__exception__\r\n
<TAG>\r\n
<error message>\r\n
<message_length> <TAG>\r\n
__exception__\r\n

```

Ici, `<TAG>` est une étiquette aléatoire de 16 octets, identique à celle envoyée dans l’en-tête de réponse `X-ClickHouse-Exception-Tag`.
Le champ `<error message>` contient le message d’exception proprement dit (sa longueur exacte est indiquée dans `<message_length>`). L’ensemble du bloc d’exception décrit ci-dessus peut atteindre 16 Kio.

Voici un exemple au format `JSON`

### Tabulations dans les paramètres d’URL {#tabs-in-url-parameters}

Les paramètres de requête sont analysés à partir du format &quot;escaped&quot;. Cela présente certains avantages, notamment la possibilité d’analyser sans ambiguïté `\N` comme une valeur nulle. Le caractère de tabulation doit donc être encodé sous la forme `\t` (ou `\` suivi d’une tabulation). Par exemple, l’entrée ci-dessous contient une tabulation réelle entre `abc` et `123`, et la chaîne d’entrée est scindée en deux valeurs :

```bash
curl -sS "http://localhost:8123" -d "SELECT splitByChar('\t', 'abc      123')"
```

```response
['abc','123']
```

Cependant, si vous essayez d’encoder un caractère de tabulation avec `%09` dans un paramètre d’URL, il ne sera pas analysé correctement :

```bash
curl -sS "http://localhost:8123?param_arg1=abc%09123" -d "SELECT splitByChar('\t', {arg1:String})"
Code: 457. DB::Exception: Value abc    123 cannot be parsed as String for query parameter 'arg1' because it isn't parsed completely: only 3 of 7 bytes was parsed: abc. (BAD_QUERY_PARAMETER) (version 23.4.1.869 (official build))
```

Si vous utilisez des paramètres d’URL, vous devrez encoder `\t` sous la forme `%5C%09`. Par exemple :

```bash
curl -sS "http://localhost:8123?param_arg1=abc%5C%09123" -d "SELECT splitByChar('\t', {arg1:String})"
```

```response
['abc','123']
```

## Interface HTTP prédéfinie {#predefined_http_interface}

ClickHouse prend en charge des requêtes spécifiques via l&#39;interface HTTP. Par exemple, vous pouvez écrire des données dans une table comme suit :

```bash
$ echo '(4),(5),(6)' | curl 'http://localhost:8123/?query=INSERT%20INTO%20t%20VALUES' --data-binary @-
```

ClickHouse prend également en charge une Interface HTTP prédéfinie qui facilite l’intégration avec des outils tiers comme l’[exportateur Prometheus](https://github.com/ClickHouse/clickhouse_exporter). Voyons un exemple.

Les mêmes handlers peuvent également être définis en SQL, sans modifier le fichier de configuration du serveur — voir [`CREATE HANDLER`](/fr/reference/statements/create/handler).

Commencez par ajouter cette section à votre fichier de configuration du serveur.

`http_handlers` est configuré pour contenir plusieurs éléments `rule`. ClickHouse compare les requêtes HTTP reçues au type prédéfini dans `rule` et exécute le handler associé à la première règle correspondante. Si une correspondance est trouvée, ClickHouse exécute alors la requête prédéfinie correspondante.

```yaml title="config.xml"
<http_handlers>
    <rule>
        <url>/predefined_query</url>
        <methods>POST,GET</methods>
        <handler>
            <type>predefined_query_handler</type>
            <query>SELECT * FROM system.metrics LIMIT 5 FORMAT Template SETTINGS format_template_resultset = 'prometheus_template_output_format_resultset', format_template_row = 'prometheus_template_output_format_row', format_template_rows_between_delimiter = '\n'</query>
        </handler>
    </rule>
    <rule>...</rule>
    <rule>...</rule>
</http_handlers>
```

Les options de configuration de `http_handlers` fonctionnent comme suit.

`rule` permet de configurer les paramètres suivants :

* `method`
* `headers`
* `url`
* `full_url`
* `handler`

Chacun de ces paramètres est décrit ci-dessous :

* `method` permet de filtrer les requêtes HTTP selon leur méthode. `method` respecte entièrement la définition de [`method`]
  (https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods) dans le protocole HTTP. Ce paramètre est facultatif. S’il n’est pas défini dans le
  fichier de configuration, aucun filtrage n’est effectué sur la méthode de la requête HTTP.

* `url` permet de filtrer les requêtes HTTP selon leur URL (chemin et chaîne de requête).
  Si `url` est préfixé par `regex:`, une expression régulière [RE2](https://github.com/google/re2) est attendue.
  Ce paramètre est facultatif. S’il n’est pas défini dans le fichier de configuration, aucun filtrage n’est effectué sur l’URL de la requête HTTP.

* `full_url` fonctionne comme `url`, mais prend en compte l’URL complète, c’est-à-dire `schema://host:port/path?query_string`.
  Notez que ClickHouse ne prend pas en charge les « hôtes virtuels » : `host` est donc une adresse IP (et non la valeur de l’en-tête `Host`).

* `empty_query_string` - garantit l’absence de chaîne de requête (`?query_string`) dans la requête

* `headers` permet de filtrer les requêtes HTTP selon leurs en-têtes. Ce paramètre est compatible avec les expressions régulières RE2 et est facultatif.
  S’il n’est pas défini dans le fichier de configuration, aucun filtrage n’est effectué sur les en-têtes de la requête HTTP.

* `handler` contient la logique principale de traitement.

  Il peut avoir les valeurs de `type` suivantes :

  * [`predefined_query_handler`](#predefined_query_handler)
  * [`dynamic_query_handler`](#dynamic_query_handler)
  * [`static`](#static)
  * [`redirect`](#redirect)

  Et les paramètres suivants :

  * `query` — à utiliser avec le type `predefined_query_handler` ; exécute la requête lorsque le handler est appelé.
  * `query_param_name` — à utiliser avec le type `dynamic_query_handler` ; extrait et exécute la valeur du paramètre de requête HTTP dont le nom est
    indiqué par `query_param_name`.
  * `status` — à utiliser avec le type `static` ; code d’état de la réponse.
  * `content_type` — à utiliser avec n’importe quel type ; [type de contenu](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Type) de la réponse.
  * `http_response_headers` — à utiliser avec n’importe quel type ; map des en-têtes de réponse. Peut également servir à définir le type de contenu.
  * `response_content` — à utiliser avec le type `static` ; contenu de la réponse envoyé au client. Avec le préfixe &#39;file://&#39; ou &#39;config://&#39;, le contenu
    est récupéré à partir du fichier ou de la configuration, puis envoyé au client.
  * `user` - utilisateur sous lequel exécuter la requête (par défaut : `default`).
    **Remarque** : il n’est pas nécessaire de spécifier de mot de passe pour cet utilisateur.

Les méthodes de configuration des différentes valeurs de `type` sont présentées ci-après.

### predefined_query_handler {#predefined_query_handler}

`predefined_query_handler` permet de définir les valeurs de `Settings` et de `query_params`. Vous pouvez configurer `query` pour le type `predefined_query_handler`.

La valeur de `query` est une requête prédéfinie de `predefined_query_handler`, exécutée par ClickHouse lorsqu&#39;une requête HTTP correspond aux critères définis. L&#39;ensemble de résultats de la requête est alors renvoyé. Ce paramètre est obligatoire.

L&#39;exemple suivant définit les valeurs des paramètres [`max_threads`](/fr/reference/settings/session-settings/max-threads#max_threads) et [`max_final_threads`](/fr/reference/settings/session-settings/max#max_final_threads), puis interroge la table système pour vérifier que ces paramètres ont bien été définis.

<Note>
  Pour conserver les `handlers` par défaut tels que ` query`, `play`, ` ping`, ajoutez la règle `<defaults/>`.
</Note>

Par exemple :

```yaml
<http_handlers>
    <rule>
        <url><![CDATA[regex:/query_param_with_url/(?P<name_1>[^/]+)]]></url>
        <methods>GET</methods>
        <headers>
            <XXX>TEST_HEADER_VALUE</XXX>
            <PARAMS_XXX><![CDATA[regex:(?P<name_2>[^/]+)]]></PARAMS_XXX>
        </headers>
        <handler>
            <type>predefined_query_handler</type>
            <query>
                SELECT name, value FROM system.settings
                WHERE name IN ({name_1:String}, {name_2:String})
            </query>
        </handler>
    </rule>
    <defaults/>
</http_handlers>
```

```bash
curl -H 'XXX:TEST_HEADER_VALUE' -H 'PARAMS_XXX:max_final_threads' 'http://localhost:8123/query_param_with_url/max_threads?max_threads=1&max_final_threads=2'
max_final_threads    2
max_threads    1
```

#### Paramètre virtuel `_request_body` {#virtual-param-request-body}

Outre les paramètres d’URL, les en-têtes et les paramètres de requête, `predefined_query_handler` prend en charge un paramètre virtuel spécial `_request_body`.
Il contient le corps brut de la requête HTTP sous forme de string.
Sa valeur provient toujours du corps de la requête : toute tentative de transmettre `_request_body` (ou `param__request_body`) dans l’URL, ou de le capturer à l’aide d’un groupe nommé dans les expressions régulières de `url` ou de `headers`, est rejetée et déclenche une exception. Toute valeur de `_request_body` définie dans une session nommée (`SET param__request_body = ...`) est ignorée.
Cela vous permet de créer des API REST souples, capables d’accepter des données dans n’importe quel format et de les traiter dans vos requêtes.

Par exemple, vous pouvez utiliser `_request_body` pour implémenter un point de terminaison REST qui accepte des données JSON dans une requête POST et les insère dans une table :

```yaml
<http_handlers>
    <rule>
        <methods>POST</methods>
        <url>/api/events</url>
        <handler>
            <type>predefined_query_handler</type>
            <query>
                INSERT INTO events (id, data)
                SELECT {id:UInt32}, {_request_body:String}
            </query>
        </handler>
    </rule>
    <defaults/>
</http_handlers>
```

Vous pouvez ensuite envoyer des données à cet endpoint :

```bash
curl -X POST 'http://localhost:8123/api/events?id=123' \
  -H 'Content-Type: application/json' \
  -d '{"user": "john", "action": "login", "timestamp": "2024-01-01T10:00:00Z"}'
```

<Note>
  Un seul paramètre `query` est pris en charge par `predefined_query_handler`.
</Note>

### dynamic_query_handler {#dynamic_query_handler}

Dans `dynamic_query_handler`, la requête est fournie sous forme de paramètre de la requête HTTP, tandis que dans `predefined_query_handler`, elle est écrite dans le fichier de configuration. Le paramètre `query_param_name` peut être configuré dans `dynamic_query_handler`.

ClickHouse extrait et exécute la valeur du paramètre d’URL dont le nom est défini par `query_param_name`. La valeur par défaut de `query_param_name` est `/query`. Ce paramètre de configuration est facultatif. S’il n’est pas défini dans le fichier de configuration, il n’est pas transmis.

Pour tester cette fonctionnalité, l’exemple suivant définit les valeurs de [`max_threads`](/fr/reference/settings/session-settings/max-threads#max_threads) et de `max_final_threads`, puis vérifie à l’aide de `queries` si les paramètres ont bien été définis.

Exemple :

```yaml
<http_handlers>
    <rule>
    <headers>
        <XXX>TEST_HEADER_VALUE_DYNAMIC</XXX>    </headers>
    <handler>
        <type>dynamic_query_handler</type>
        <query_param_name>query_param</query_param_name>
    </handler>
    </rule>
    <defaults/>
</http_handlers>
```

```bash
curl  -H 'XXX:TEST_HEADER_VALUE_DYNAMIC'  'http://localhost:8123/own?max_threads=1&max_final_threads=2&param_name_1=max_threads&param_name_2=max_final_threads&query_param=SELECT%20name,value%20FROM%20system.settings%20where%20name%20=%20%7Bname_1:String%7D%20OR%20name%20=%20%7Bname_2:String%7D'
max_threads 1
max_final_threads   2
```

### static {#static}

`static` peut renvoyer un type de contenu ([`content_type`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Type)), un [code de statut](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status) et un contenu (`response_content`). `response_content` permet de renvoyer le contenu spécifié.

Par exemple, pour renvoyer le message &quot;Dites bonjour !&quot; :

```yaml highlight={14}
<http_handlers>
        <rule>
            <methods>GET</methods>
            <headers><XXX>xxx</XXX></headers>
            <url>/hi</url>
            <handler>
                <type>static</type>
                <status>402</status>
                <content_type>text/html; charset=UTF-8</content_type>
                <http_response_headers>
                    <Content-Language>en</Content-Language>
                    <X-My-Custom-Header>43</X-My-Custom-Header>
                </http_response_headers>
                <response_content>Say Hi!</response_content>
            </handler>
        </rule>
        <defaults/>
</http_handlers>
```

```yaml
                </http_response_headers>
                #end-highlight
                <response_content>Say Hi!</response_content>
```

### redirect {#redirect}

`redirect` effectue une redirection `302` vers `location`

Voici, par exemple, comment définir automatiquement l’utilisateur sur `play` pour ClickHouse play :

```xml
<clickhouse>
    <http_handlers>
        <rule>
            <methods>GET</methods>
            <url>/play</url>
            <handler>
                <type>redirect</type>
                <location>/play?user=play</location>
            </handler>
        </rule>
    </http_handlers>
</clickhouse>
```

## En-têtes de réponse HTTP {#http-response-headers}

ClickHouse vous permet de configurer des en-têtes de réponse HTTP personnalisés applicables à tout type de handler configurable. Ces en-têtes peuvent être définis à l’aide du paramètre `http_response_headers`, qui accepte des paires clé-valeur représentant les noms des en-têtes et leurs valeurs. Cette fonctionnalité est particulièrement utile pour définir des en-têtes de sécurité personnalisés, appliquer des règles CORS ou répondre à toute autre exigence relative aux en-têtes HTTP dans l’ensemble de votre Interface HTTP ClickHouse.

Par exemple, vous pouvez configurer des en-têtes pour :

* Les points de terminaison de requêtes classiques
* L’interface utilisateur web
* Le contrôle de l’état de santé.

Il est également possible de spécifier `common_http_response_headers`. Ces en-têtes seront appliqués à tous les handlers HTTP définis dans la configuration.

Les en-têtes seront inclus dans la réponse HTTP de chaque handler configuré.

Dans l’exemple ci-dessous, chaque réponse du serveur contiendra deux en-têtes personnalisés : `X-My-Common-Header` et `X-My-Custom-Header`.

```xml
<clickhouse>
    <http_handlers>
        <common_http_response_headers>
            <X-My-Common-Header>Common header</X-My-Common-Header>
        </common_http_response_headers>
        <rule>
            <methods>GET</methods>
            <url>/ping</url>
            <handler>
                <type>ping</type>
                <http_response_headers>
                    <X-My-Custom-Header>Custom indeed</X-My-Custom-Header>
                </http_response_headers>
            </handler>
        </rule>
    </http_handlers>
</clickhouse>
```

## Réponse JSON/XML valide en cas d’exception pendant la diffusion en continu HTTP {#valid-output-on-exception-http-streaming}

Lors de l’exécution d’une requête via HTTP, une exception peut se produire alors qu’une partie des données a déjà été envoyée. En général, l’exception est envoyée au client sous forme de texte en clair.
