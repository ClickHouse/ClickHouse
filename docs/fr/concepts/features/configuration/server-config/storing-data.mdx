Les données traitées dans ClickHouse sont généralement stockées dans le système de fichiers local de la
machine sur laquelle s’exécute le serveur ClickHouse. Cela nécessite des disques de grande capacité,
qui peuvent être coûteux. Pour éviter de stocker les données localement, plusieurs options de stockage sont prises en charge :

1. Le stockage d’objet [Amazon S3](https://aws.amazon.com/s3/).
2. [Azure Blob Storage](https://azure.microsoft.com/en-us/products/storage/blobs).
3. Non pris en charge : Hadoop Distributed File System ([HDFS](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html))

<br />

<Note>
  ClickHouse prend également en charge des moteurs de table externes, qui diffèrent de
  l’option de stockage externe décrite sur cette page, car ils permettent de lire des données
  stockées dans un format de fichier générique (comme Parquet). Cette page décrit
  la configuration du stockage pour les tables de la famille `MergeTree` ou de la famille `Log`.

  1. pour utiliser des données stockées sur des disques `Amazon S3`, utilisez le moteur de table [S3](/fr/reference/engines/table-engines/integrations/s3).
  2. pour utiliser des données stockées dans Azure Blob Storage, utilisez le moteur de table [AzureBlobStorage](/fr/reference/engines/table-engines/integrations/azureBlobStorage).
  3. pour utiliser des données dans Hadoop Distributed File System (non pris en charge), utilisez le moteur de table [HDFS](/fr/reference/engines/table-engines/integrations/hdfs).
</Note>

## Configurer le stockage externe {#configuring-external-storage}

Les moteurs de table des familles [`MergeTree`](/fr/reference/engines/table-engines/mergetree-family/mergetree) et [`Log`](/fr/reference/engines/table-engines/log-family/log)
peuvent stocker les données dans `S3`, `AzureBlobStorage`, `HDFS` (non pris en charge) en utilisant respectivement un disque de type `s3`,
`azure_blob_storage`, `hdfs` (non pris en charge).

<Note>
  Le type de disque `s3` peut également être utilisé avec des fournisseurs de stockage d’objet compatibles S3, tels qu’Alibaba Cloud Object Storage Service. Configurez `endpoint` avec l’endpoint compatible S3 du fournisseur et tenez compte de toute exigence de compatibilité propre à ce fournisseur.
</Note>

La configuration du disque nécessite :

1. Une section `type`, égale à l&#39;une des valeurs `s3`, `azure_blob_storage`, `hdfs` (non pris en charge), `local_blob_storage`, `web`.
2. La configuration d&#39;un type spécifique de stockage externe.

À partir de la version 24.1 de ClickHouse, il est possible d&#39;utiliser une nouvelle option de configuration.
Elle nécessite de spécifier :

1. Un `type` égal à `object_storage`
2. `object_storage_type`, égal à l&#39;une des valeurs `s3`, `azure_blob_storage` (ou simplement `azure` à partir de `24.3`), `hdfs` (non pris en charge), `local_blob_storage` (ou simplement `local` à partir de `24.3`), `web`.

<br />

Il est également possible de spécifier `metadata_type`. La valeur par défaut est `local` pour le stockage d’objet S3, Azure, HDFS et local, et `web` pour le stockage web. Les types de disque de compatibilité `s3_plain` et `s3_plain_rewritable` sélectionnent respectivement les métadonnées `plain` et `plain_rewritable`.
L&#39;utilisation du type de métadonnées `plain` est décrite dans la [section sur le stockage simple](/fr/concepts/features/configuration/server-config/storing-data#plain-storage). Le type de métadonnées `web` ne peut être utilisé qu&#39;avec le type de stockage d’objet `web`. Le type de métadonnées `local` stocke les fichiers de métadonnées localement (chaque fichier de métadonnées contient la correspondance avec les fichiers du stockage d’objet, ainsi que des méta-informations supplémentaires à leur sujet).

Par exemple :

```xml
<s3>
    <type>s3</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3>
```

correspond à la configuration suivante (depuis la version `24.1`) :

```xml
<s3>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>local</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3>
```

La configuration suivante :

```xml
<s3_plain>
    <type>s3_plain</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

est égal à :

```xml
<s3_plain>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

Voici un exemple de configuration complète du stockage :

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
        </disks>
        <policies>
            <s3>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3>
        </policies>
    </storage_configuration>
</clickhouse>
```

À partir de la version 24.1, cela peut aussi se présenter ainsi :

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>object_storage</type>
                <object_storage_type>s3</object_storage_type>
                <metadata_type>local</metadata_type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
        </disks>
        <policies>
            <s3>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3>
        </policies>
    </storage_configuration>
</clickhouse>
```

Pour définir un type de stockage spécifique comme option par défaut pour toutes les tables `MergeTree`,
ajoutez la section suivante au fichier de configuration :

```xml
<clickhouse>
    <merge_tree>
        <storage_policy>s3</storage_policy>
    </merge_tree>
</clickhouse>
```

Si vous souhaitez configurer une politique de stockage spécifique pour une table particulière,
vous pouvez la définir dans les paramètres lors de la création de la table :

```sql
CREATE TABLE test (a Int32, b String)
ENGINE = MergeTree() ORDER BY a
SETTINGS storage_policy = 's3';
```

Vous pouvez aussi utiliser `disk` à la place de `storage_policy`. Dans ce cas, il n&#39;est pas nécessaire
d&#39;inclure la section `storage_policy` dans le fichier de configuration : une section `disk`
suffit.

```sql
CREATE TABLE test (a Int32, b String)
ENGINE = MergeTree() ORDER BY a
SETTINGS disk = 's3';
```

## `refresh_parts_interval` et `table_disk` {#refresh-parts-interval-and-table-disk}

Ce paramètre est destiné aux tables MergeTree non répliquées, lorsque des parts peuvent être écrites en externe et que les métadonnées doivent être rechargées depuis le stockage.

Le paramètre `MergeTree` `refresh_parts_interval` active, sur les disques en lecture seule, le rechargement périodique de la liste des data parts depuis le stockage sous-jacent (par ex. pour prendre en compte des parts écrites en externe). La distinction essentielle est la suivante : **métadonnées partagées entre les répliques** vs **métadonnées locales à chaque réplique** (par ex. S3 avec des métadonnées locales par réplique). Les nouvelles parts ne seront visibles par toutes les répliques que si les métadonnées sont partagées. Le simple recours au stockage d’objet n&#39;implique pas des métadonnées partagées.

* **Le stockage d’objet (par ex. `disk = 's3'`) n&#39;implique pas des métadonnées partagées.** Lorsque les métadonnées sont stockées localement sur chaque réplique (par défaut), chaque réplique gère indépendamment ses pointeurs vers les blobs du stockage d’objet. Les modifications effectuées sur une réplique ne sont pas visibles sur les autres. Dans ce cas, `refresh_parts_interval` ne rend pas les nouvelles parts visibles d&#39;une réplique à l&#39;autre, car les métadonnées lues par chaque réplique sont locales.

* **Le rechargement automatique des parts exige un disque en lecture seule et un accès aux métadonnées du rédacteur.** [`table_disk`](/fr/reference/settings/merge-tree-settings/table#table_disk) indique que le disque pointe directement vers les données d&#39;une seule table ; il ne rend pas pour autant le disque accessible en lecture seule. Configurez l&#39;accès en lecture seule séparément, par exemple avec `read_only=true` dans la définition du disque, et utilisez un type de métadonnées pris en charge.

* **Avec un disque défini globalement** (par ex. `disk = 's3'` dans `storage_configuration`) et les métadonnées locales par défaut, chaque réplique possède son propre état de métadonnées. Même si les blobs se trouvent dans S3, le stockage n&#39;est pas considéré comme partagé du point de vue de `refresh_parts_interval`, et les nouvelles parts créées en dehors de ClickHouse ou sur une autre réplique ne seront pas détectées.

Pour le rechargement automatique des parts, assurez-vous que le lecteur a accès aux métadonnées du rédacteur et qu&#39;il utilise un disque en lecture seule. Partager un compartiment S3 ne suffit pas à partager les métadonnées stockées localement.

<Note>
  `refresh_parts_interval` n&#39;est pas utilisé pour les tables ReplicatedMergeTree.
  Les tables répliquées synchronisent déjà les parts via le mécanisme de réplication.
  Ce paramètre s&#39;applique uniquement aux tables MergeTree non répliquées dans lesquelles des parts sont écrites en externe et où un rechargement des métadonnées est nécessaire.
</Note>

## Configuration dynamique {#dynamic-configuration}

Il est également possible de spécifier une configuration du stockage sans
disque prédéfini dans un fichier de configuration, mais aussi de la définir
dans les paramètres de requête `CREATE`/`ATTACH`.

La requête suivante rattache une table en lecture seule stockée à une URL.

```sql highlight={20-23}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=web,
    endpoint='https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/'
  );
```

L’exemple ci-dessous ajoute un cache au stockage externe.

```sql highlight={20-28}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=cache,
    max_size='1Gi',
    path='custom_disk_cache/',
    disk=disk(
      type=web,
      endpoint='https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/'
      )
  );
```

Dans les paramètres mis en évidence ci-dessus, notez que le disque de `type=web` est imbriqué dans
le disque de `type=cache`.

<Note>
  L’exemple utilise `type=web`, mais tout type de disque peut être configuré comme dynamique,
  y compris un disque local. Les disques locaux exigent qu’un argument `path` soit défini dans le
  paramètre du serveur `custom_local_disks_base_directory`, qui n’a pas de valeur par défaut.

  Pour un disque de cache dynamique, configurez `filesystem_caches_path` ou `custom_cached_disks_base_directory` sur le serveur. Les chemins de cache relatifs sont résolus par rapport à ce répertoire ; les chemins absolus doivent également se trouver à l’intérieur de celui-ci.
</Note>

Chaque argument de `disk` ne peut être spécifié qu’une seule fois, à l’exception de ceux qu’un disque lit sous forme de liste :
`header` et `access_header` pour un disque `s3`, ainsi que `key` et `key_hex` pour un disque `encrypted`.

Une combinaison d’une configuration basée sur la configuration et d’une configuration définie en SQL est
également possible :

```sql highlight={20-25}
ATTACH TABLE uk_price_paid UUID 'cf712b4f-2ca8-435c-ac23-c4393efe52f7'
(
    price UInt32,
    date Date,
    postcode1 LowCardinality(String),
    postcode2 LowCardinality(String),
    type Enum8('other' = 0, 'terraced' = 1, 'semi-detached' = 2, 'detached' = 3, 'flat' = 4),
    is_new UInt8,
    duration Enum8('unknown' = 0, 'freehold' = 1, 'leasehold' = 2),
    addr1 String,
    addr2 String,
    street LowCardinality(String),
    locality LowCardinality(String),
    town LowCardinality(String),
    district LowCardinality(String),
    county LowCardinality(String)
)
ENGINE = MergeTree
ORDER BY (postcode1, postcode2, addr1, addr2)
  SETTINGS disk = disk(
    type=cache,
    max_size='1Gi',
    path='custom_disk_cache/',
    disk='web'
  );
```

où `web` provient du fichier de configuration du serveur :

```xml
<storage_configuration>
    <disks>
        <web>
            <type>web</type>
            <endpoint>https://raw.githubusercontent.com/ClickHouse/web-tables-demo/main/web/</endpoint>
        </web>
    </disks>
</storage_configuration>
```

### Utiliser le stockage S3 {#s3-storage}

#### Endpoint et authentification {#required-parameters-s3}

| Paramètre           | Description                                                                                                                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `endpoint`          | URL de l&#39;endpoint S3 de type `path` ou `virtual hosted` [styles](https://docs.aws.amazon.com/AmazonS3/latest/dev/VirtualHosting.html). Elle doit inclure le bucket et le chemin racine de stockage des données. |
| `access_key_id`     | ID de la clé d&#39;accès S3. Facultatif si vous utilisez un fournisseur d&#39;identifiants.                                                                                                  |
| `secret_access_key` | Clé d&#39;accès secrète S3, à fournir avec `access_key_id` si vous utilisez des identifiants explicites.                                                                                     |

Les valeurs par défaut S3 ont évolué au fil des versions : `use_environment_credentials` est passé de `false` à `true` dans la version `23.4`, `connect_timeout_ms` de `10000` à `1000` dans la version `23.5`, et `request_timeout_ms` de `5000` à `30000` dans la version `22.10`. Les valeurs configurées explicitement ne sont pas concernées par ces changements de valeurs par défaut.

Les identifiants explicites priment sur les fournisseurs d&#39;identifiants. Définissez `session_token` si vous utilisez des identifiants explicites temporaires. Avec `use_environment_credentials=true`, ClickHouse peut obtenir les identifiants depuis l&#39;environnement, les fichiers d&#39;identifiants AWS, l&#39;identité web (web identity) ou les rôles d&#39;instance/de conteneur. Cette option active une chaîne de fournisseurs, et pas seulement les variables d&#39;environnement.

Avec l&#39;identité web (variables d&#39;environnement `AWS_ROLE_ARN` et `AWS_WEB_IDENTITY_TOKEN_FILE`), ClickHouse demande les identifiants à AWS STS dans la région définie par `AWS_DEFAULT_REGION` ou par le profil AWS. Si aucun des deux ne définit de région, ClickHouse utilise celle du disque : le paramètre `region`, ou la région déduite de l&#39;endpoint, par exemple `eu-central-1` pour `https://s3.eu-central-1.amazonaws.com/`. Si le disque n&#39;a pas non plus de région, ou si `remote_url_allow_hosts` n&#39;autorise pas l&#39;endpoint STS de cette région (`sts.eu-central-1.amazonaws.com`), STS est appelé dans `us-east-1`. Pour que STS soit toujours appelé dans une région donnée, définissez `AWS_DEFAULT_REGION`. La variable d&#39;environnement `AWS_REGION` ne définit pas la région utilisée par STS.

#### Paramètres facultatifs {#optional-parameters-s3}

Les valeurs par défaut ci-dessous s’appliquent, sauf si elles sont surchargées dans la configuration du disque ou héritées de paramètres `s3_*` modifiés dans le contexte d’initialisation. Les options de client et d’authentification utilisent des clés de disque sans préfixe ; les options de requête, telles que `s3_retry_attempts`, utilisent le préfixe `s3_`. Les requêtes peuvent surcharger les paramètres de requête propres à chaque lecture et à chaque écriture ; en revanche, toute modification des paramètres client nécessite de reconfigurer le client.

| `use_environment_credentials`                   | Active la chaîne de fournisseurs d’identifiants AWS en l’absence d’informations d’authentification explicites. Les identifiants de l’environnement et de l’instance sont partagés entre les disques du processus serveur.                                                                                                                    | `true`                                                                                           |

### Utilisation du stockage simple {#plain-storage}

Dans `22.10`, un nouveau type de disque `s3_plain` a été introduit. Il fournit un stockage en écriture unique.
Ses paramètres de configuration sont les mêmes que pour le type de disque `s3`.
Contrairement au type de disque `s3`, il stocke les données telles quelles. Autrement dit,
au lieu d&#39;utiliser des noms de blob générés aléatoirement, il utilise des noms de fichiers classiques
(de la même manière que ClickHouse stocke les fichiers sur un disque local) et ne stocke
aucune métadonnée localement. Par exemple, ces métadonnées sont déduites des données sur `s3`.

Ce type de disque permet de conserver une version statique de la table, car il ne
permet pas d&#39;exécuter de merges sur les données existantes et n&#39;autorise pas l&#39;insertion de nouvelles
données. Un cas d&#39;utilisation de ce type de disque consiste à y créer des sauvegardes, ce qui peut être fait
via `BACKUP TABLE data TO Disk('plain_disk_name', 'backup_name')`. Ensuite,
vous pouvez exécuter `RESTORE TABLE data AS data_restored FROM Disk('plain_disk_name', 'backup_name')`
ou utiliser `ATTACH TABLE data (...) ENGINE = MergeTree() SETTINGS disk = 'plain_disk_name'`.

Configuration :

```xml
<s3_plain>
    <type>s3_plain</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

À partir de `24.1`, il est possible de configurer n’importe quel disque de stockage objet (`s3`, `azure`, `hdfs` (non pris en charge), `local`) à l’aide
du type de métadonnées `plain`.

Configuration :

```xml
<s3_plain>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain>
```

### Utilisation du stockage S3 Plain Rewritable {#s3-plain-rewritable-storage}

Un nouveau type de disque `s3_plain_rewritable` a été introduit dans `24.4`.
Comme le type de disque `s3_plain`, il ne nécessite pas de stockage supplémentaire pour les
fichiers de métadonnées. À la place, les métadonnées sont stockées dans S3.
Contrairement au type de disque `s3_plain`, `s3_plain_rewritable` permet d’exécuter des merges
et prend en charge les opérations `INSERT`.
La réplication des tables n’est pas prise en charge.
Les [mutations](/fr/reference/statements/alter/index#mutations) et les opérations `ALTER`
ne sont prises en charge que si le disque est configuré avec `enable_hard_links`, voir ci-dessous.

Un cas d’usage de ce type de disque concerne les tables `MergeTree` non répliquées. Bien que
le type de disque `s3` convienne aux tables `MergeTree` non répliquées, vous pouvez opter pour
le type de disque `s3_plain_rewritable` si vous n’avez pas besoin de métadonnées locales
pour la table. Cela peut être utile, par exemple, pour les tables système.

Configuration :

```xml
<s3_plain_rewritable>
    <type>s3_plain_rewritable</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain_rewritable>
```

est égal à

```xml
<s3_plain_rewritable>
    <type>object_storage</type>
    <object_storage_type>s3</object_storage_type>
    <metadata_type>plain_rewritable</metadata_type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
</s3_plain_rewritable>
```

À partir de `24.5`, il est possible de configurer n’importe quel disque de stockage objet
(`s3`, `azure`, `local`) avec le type de métadonnées `plain_rewritable`.

#### Liens physiques sur les disques plain rewritable {#plain-rewritable-metadata-snapshot}

Les opérations `ALTER` et les mutations d&#39;une table `MergeTree` partagent, au moyen de liens physiques, les fichiers inchangés
entre une part et la part mutée qui lui succède, au lieu de les
copier. Le paramètre `enable_hard_links` (`0` par défaut) permet à un disque utilisant des
métadonnées `plain_rewritable` de créer de véritables liens physiques, ce qui rend possibles les
opérations suivantes :

```xml
<s3_plain_rewritable>
    <type>s3_plain_rewritable</type>
    <endpoint>https://s3.eu-west-1.amazonaws.com/clickhouse-eu-west-1.clickhouse.com/data/</endpoint>
    <use_environment_credentials>1</use_environment_credentials>
    <enable_hard_links>1</enable_hard_links>
</s3_plain_rewritable>
```

Un lien physique fait en sorte que les métadonnées d&#39;un répertoire listent explicitement ses fichiers, ainsi
que les clés des objets qui les stockent, de sorte qu&#39;un fichier puisse faire référence à un objet
stocké sous le préfixe d&#39;un autre répertoire. Tenez compte des points suivants avant
de l&#39;activer :

* Un serveur qui ne prend pas en charge le paramètre `enable_hard_links` ne peut pas lire un
  répertoire sous cette forme : il interprète l&#39;intégralité des métadonnées du répertoire comme son
  path logique. Un disque contenant de tels répertoires n&#39;est donc plus lisible après
  un downgrade vers une telle version, et ne peut pas être partagé avec celle-ci. Les répertoires qui
  n&#39;ont jamais eu de liens physiques conservent l&#39;ancienne disposition : un disque reste donc lisible par
  les serveurs plus anciens jusqu&#39;à la première opération qui crée un lien physique, à savoir une mutation,
  un `ALTER`, un `FREEZE` ou une sauvegarde. Désactiver ensuite le paramètre ne
  reconvertit pas les répertoires existants.
* Le paramètre n&#39;est lu qu&#39;à la création du disque : toute modification prend effet après
  un redémarrage du serveur, et `SYSTEM RELOAD CONFIG` ne l&#39;applique pas.
* Un objet dont le dernier lien est supprimé est effacé en deux étapes : les métadonnées du
  répertoire sont d&#39;abord réécrites, puis l&#39;objet est supprimé. Si le
  serveur est arrêté brutalement entre les deux, l&#39;objet reste dans le bucket sans être
  référencé par quoi que ce soit et doit alors être supprimé manuellement.

### Utilisation d’Azure Blob Storage

Les moteurs de table de la famille `MergeTree` peuvent stocker des données dans [Azure Blob Storage](https://azure.microsoft.com/en-us/services/storage/blobs/)
à l’aide d’un disque de type `azure_blob_storage`.

Ajoutez ce fragment dans l’élément `clickhouse` de la configuration du serveur. Définissez la variable d’environnement `AZURE_STORAGE_ACCOUNT_KEY` sur le serveur et remplacez les noms du compte et du conteneur :

```xml
<storage_configuration>
    <disks>
        <blob_storage_disk>
            <type>azure_blob_storage</type>
            <storage_account_url>https://account.blob.core.windows.net</storage_account_url>
            <container_name>container</container_name>
            <account_name>account</account_name>
            <account_key from_env="AZURE_STORAGE_ACCOUNT_KEY"/>
            <metadata_path>/var/lib/clickhouse/disks/blob_storage_disk/</metadata_path>
            <skip_access_check>false</skip_access_check>
        </blob_storage_disk>
    </disks>
</storage_configuration>
```

#### Paramètres de connexion

| Paramètre                  | Description                                                                                                                                                                                                                                           | Valeur par défaut |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `storage_account_url`      | URL du compte de stockage Azure Blob Storage ; obligatoire sauf si `connection_string` ou `endpoint` est fourni. Exemples : `https://account.blob.core.windows.net` ou `http://azurite1:10000/devstoreaccount1`.                                      | -                 |
| `container_name`           | Obligatoire avec `storage_account_url` ou `connection_string` ; sinon, indiqué dans `endpoint`.                                                                                                                                                       | None              |
| `container_already_exists` | Contrôle le comportement lors de la création du conteneur : <br />- `false` : crée un nouveau conteneur <br />- `true` : se connecte directement à un conteneur existant <br />- Non défini : vérifie si le conteneur existe et le crée si nécessaire | -                 |

Avant la version `24.3`, si `container_name` était omis, `default-container` était utilisé.

L’authentification utilise une seule méthode, choisie dans cet ordre : Shared Key lorsque `account_name` et `account_key` sont tous deux présents, sinon `connection_string`, sinon Workload Identity lorsque `use_workload_identity=true` (`false` par défaut), sinon l’identité managée. En cas d’échec de l’authentification, aucune autre méthode n’est utilisée en repli. Avant la version `24.7`, les chaînes de connexion avaient priorité sur l’authentification par Shared Key.

Paramètres d’authentification :

| Paramètre           | Description                                                            |

### Utilisation du chiffrement des données

Vous pouvez chiffrer les données stockées sur des disques externes [S3](/fr/reference/engines/table-engines/mergetree-family/mergetree#table_engine-mergetree-s3) ou [HDFS](#using-hdfs-storage-unsupported) (non pris en charge), ou sur un disque local. Pour activer le mode de chiffrement, vous devez définir dans le fichier de configuration un disque de type `encrypted` et choisir le disque sur lequel les données seront stockées. Un disque `encrypted` chiffre à la volée tous les fichiers qui y sont écrits et, lorsque vous lisez des fichiers depuis un disque `encrypted`, il les déchiffre automatiquement. Vous pouvez donc utiliser un disque `encrypted` comme un disque normal.

Le fragment suivant doit être placé dans `storage_configuration`. Remplacez la clé d’exemple par votre propre clé, de la longueur requise.

```xml
<disks>
  <disk1>
    <type>local</type>
    <path>/path1/</path>
  </disk1>
  <disk2>
    <type>encrypted</type>
    <disk>disk1</disk>
    <path>path2/</path>
    <key>_16_ascii_chars_</key>
  </disk2>
</disks>
```

Par exemple, lorsque ClickHouse écrit des données d’une table dans le fichier `store/all_1_1_0/data.bin` sur `disk1`, ce fichier est en réalité écrit sur le disque physique au chemin `/path1/store/all_1_1_0/data.bin`.

Lors de l’écriture du même fichier sur `disk2`, il est en réalité écrit sur le disque physique au chemin `/path1/path2/store/all_1_1_0/data.bin`, en mode chiffré.

#### Paramètres Obligatoires

| Paramètre | Type   | Description                                                                                                                                                   |
| --------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`    | String | Doit être défini sur `encrypted` pour créer un disque chiffré.                                                                                                |
| `disk`    | String | Nom d’un disque déjà configuré à utiliser comme stockage sous-jacent.                                                                                         |
| `key`     | String | Clé de chiffrement et de déchiffrement. Peut être spécifiée en hexadécimal à l’aide de `key_hex`. Plusieurs clés peuvent être spécifiées via l’attribut `id`. |

#### Paramètres facultatifs {#required-parameters-encrypted-disk}

| Paramètre        | Type   | Par défaut                                        | Description                                                                                                                                                                                        |
| ---------------- | ------ | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`           | String | Répertoire racine                                 | Répertoire relatif sur le disque sous-jacent, se terminant par `/` lorsqu&#39;il n&#39;est pas vide.                                                                                               |
| `current_key_id` | UInt64 | `0` uniquement si l&#39;unique clé a l&#39;ID `0` | Sélectionne la clé utilisée pour le chiffrement. En présence de plusieurs clés, sélectionnez explicitement la clé courante. Toutes les clés configurées restent disponibles pour le déchiffrement. |
| `algorithm`      | Enum   | `AES_128_CTR`                                     | Algorithme de chiffrement. Options : <br />- `AES_128_CTR` (clé de 16 octets) <br />- `AES_192_CTR` (clé de 24 octets) <br />- `AES_256_CTR` (clé de 32 octets)                                    |

Exemple de configuration du disque :

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <disk_s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
            </disk_s3>
            <disk_s3_encrypted>
                <type>encrypted</type>
                <disk>disk_s3</disk>
                <algorithm>AES_128_CTR</algorithm>
                <key_hex id="0">00112233445566778899aabbccddeeff</key_hex>
                <key_hex id="1">ffeeddccbbaa99887766554433221100</key_hex>
                <current_key_id>1</current_key_id>
            </disk_s3_encrypted>
        </disks>
    </storage_configuration>
</clickhouse>
```

### Utilisation du cache local

Un disque `cache` encapsule un disque de stockage d’objet, tel que S3, Azure ou `web`, et stocke les données mises en cache sur le système de fichiers local. Il ne peut pas encapsuler un disque `local` ordinaire ni un wrapper `encrypted`. Définissez le disque sous-jacent avant le disque de cache.

Configuration recommandée pour les versions actuelles :

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
            </s3>
            <cache>
                <type>cache</type>
                <disk>s3</disk>
                <path>s3_cache/</path>
                <max_size>10Gi</max_size>
            </cache>
        </disks>
        <policies>
            <s3_cache>
                <volumes>
                    <main>
                        <disk>cache</disk>
                    </main>
                </volumes>
            </s3_cache>
        </policies>
    </storage_configuration>
</clickhouse>
```

Configuration historique pour les versions `22.3`–`22.7` uniquement. N’utilisez pas ces clés `data_cache_*` dans les configurations actuelles ; utilisez plutôt un disque `cache` distinct, comme ci-dessus :

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <s3>
                <type>s3</type>
                <endpoint>https://s3.eu-west-1.amazonaws.com/example-bucket/data/</endpoint>
                <use_environment_credentials>1</use_environment_credentials>
                <data_cache_enabled>1</data_cache_enabled>
                <data_cache_max_size>10737418240</data_cache_max_size>
            </s3>
        </disks>
        <policies>
            <s3_cache>
                <volumes>
                    <main>
                        <disk>s3</disk>
                    </main>
                </volumes>
            </s3_cache>
        </policies>
    </storage_configuration>
</clickhouse>
```

| `cache_hits_threshold`                      | Integer | `0`        | Deprecated ; sans effet.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `enable_bypass_cache_with_threshold`        | Boolean | `false`    | Ignore le cache pour les grandes plages de lecture.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `bypass_cache_threshold`                    | Size    | `256Mi`    | Taille de plage de lecture qui déclenche le contournement du cache (nécessite `enable_bypass_cache_with_threshold`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `max_file_segment_size`                     | Size    | `32Mi`     | Taille maximale d&#39;un fichier de cache unique en octets ou dans un format lisible. Pour `SLRU` / `SLRU_OVERCOMMIT`, ne doit pas dépasser la taille de chaque file d’attente SLRU, soit `max_size * min(slru_size_ratio, 1 - slru_size_ratio)` (celle de chaque partie avec `use_split_cache`) ; toute valeur supérieure est rejetée.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `boundary_alignment`                        | Size    | `4Mi`      | Alignement des limites des segments de fichier dans le cache. | `max_elements`                              | Integer | `10000000` | Nombre maximal de fichiers de cache.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `load_metadata_threads`                     | Integer | `16`       | Nombre de threads utilisés pour charger les métadonnées du cache au démarrage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `background_download_threads`               | UInt64  | `5`        | Nombre de threads pour le téléchargement en arrière-plan des segments de fichier. `0` désactive le téléchargement en arrière-plan.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `background_download_queue_size_limit`      | UInt64  | `5000`     | Nombre maximal de segments en attente dans la file d’attente de téléchargement en arrière-plan. `0` signifie aucune limite (la file d’attente n’est pas désactivée). | `background_download_max_file_segment_size` | Size    | `4Mi`      | Seuil, arrondi selon l’alignement, déterminant jusqu’où un segment est préchargé en arrière-plan. La taille de téléchargement est arrondie au multiple supérieur de `boundary_alignment` ; il ne s’agit donc pas d’une limite stricte (par exemple, `1Mi` avec un `boundary_alignment` de `4Mi` télécharge tout de même `4Mi`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `load_metadata_asynchronously`              | Boolean | `false`    | Charge les métadonnées du cache de manière asynchrone au démarrage du serveur.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `use_real_disk_size`                        | Boolean | `false`    | Comptabilise les réservations du cache en unités alignées sur les blocs du système de fichiers plutôt qu’en octets réservés. Cela donne une approximation de l’empreinte des réservations sur le disque, sans correspondre exactement à la taille allouée ; cela affecte la valeur `current_size` de ce cache dans `system.filesystem_cache_settings`. La métrique `FilesystemCacheSize`, calculée à l’échelle du processus, et les événements de profilage relatifs à la taille d’éviction sont additionnés sur l’ensemble des caches ; ils ne reflètent donc uniformément l’empreinte des réservations que lorsque tous les caches utilisent le même mode. La valeur `size` de chaque segment dans `system.filesystem_cache` correspond toujours à la taille logique de la plage ; utilisez `downloaded_size` pour connaître le nombre d’octets écrits dans un segment partiel. La modification de ce paramètre nécessite un redémarrage. |
| `use_split_cache`                           | Boolean | `false`    | Sépare les fichiers système des fichiers de données. Non pris en charge avec `SLRU_OVERCOMMIT` ou `LRU_OVERCOMMIT`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `split_cache_ratio`                         | Double  | `0.1`      | Ratio du segment système par rapport à la taille totale du cache pour split&#95;cache.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

> **Remarque** : les valeurs de taille prennent en charge des unités comme `ki`, `Mi`, `Gi`, etc. (par ex. `10Gi`).

### Utilisation du stockage Web statique (lecture seule)

Il s’agit d’un disque en lecture seule. Ses données sont uniquement consultées et ne sont jamais modifiées. Une nouvelle table
est chargée sur ce disque via la requête `ATTACH TABLE` (voir l’exemple ci-dessous). Le disque local
n’est en fait pas utilisé : chaque requête `SELECT` entraîne une requête `http` pour
récupérer les données nécessaires. Toute modification des données de la table entraîne une
exception, c.-à-d. que les types de requêtes suivants ne sont pas autorisés : [`CREATE TABLE`](/fr/reference/statements/create/table),
[`ALTER TABLE`](/fr/reference/statements/alter/index), [`RENAME TABLE`](/fr/reference/statements/rename#rename-table),
et [`TRUNCATE TABLE`](/fr/reference/statements/truncate).
Le stockage Web peut être utilisé en lecture seule. Il peut par exemple servir à héberger
des données d’exemple ou à migrer des données. Il existe un outil `clickhouse-static-files-uploader`,
qui prépare un répertoire de données pour une table donnée (`SELECT data_paths FROM system.tables WHERE name = 'table_name'`).
Pour chaque table dont vous avez besoin, vous obtenez un répertoire de fichiers. Ces fichiers peuvent être téléversés
vers, par exemple, un serveur web servant des fichiers statiques. Après cette préparation,
vous pouvez charger cette table sur n’importe quel serveur ClickHouse via `DiskWeb`.

Dans cet exemple de configuration :

* le disque est de type `web`
* les données sont hébergées à `http://nginx:80/test1/`
* un cache sur le stockage local est utilisé

```xml
<clickhouse>
    <storage_configuration>
        <disks>
            <web>
                <type>web</type>
                <endpoint>http://nginx:80/test1/</endpoint>
            </web>
            <cached_web>
                <type>cache</type>
                <disk>web</disk>
                <path>cached_web_cache/</path>
                <max_size>100000000</max_size>
            </cached_web>
        </disks>
        <policies>
            <web>
                <volumes>
                    <main>
                        <disk>web</disk>
                    </main>
                </volumes>
            </web>
            <cached_web>
                <volumes>
                    <main>
                        <disk>cached_web</disk>
                    </main>
                </volumes>
            </cached_web>
        </policies>
    </storage_configuration>
</clickhouse>
```

<Tip>
  Le stockage peut aussi être configuré temporairement dans une requête. Si un jeu de données web
  n’est pas destiné à être utilisé régulièrement, consultez la [configuration dynamique](#dynamic-configuration) et évitez
  de modifier le fichier de configuration.

  Un [jeu de données de démonstration](https://github.com/ClickHouse/web-tables-demo) est hébergé sur GitHub. Pour préparer vos propres tables pour le
  stockage web, consultez l’outil [clickhouse-static-files-uploader](/fr/concepts/features/tools-and-utilities/static-files-disk-uploader)
</Tip>

#### Paramètres facultatifs {#static-web-storage-required-parameters}

Le storage backend de stockage d’objet `web` ne lit que le paramètre `endpoint`. Il n’existe aucun paramètre facultatif supplémentaire spécifique au web ; les options de disque génériques restent applicables.

Pour les délais d’attente de connexion ou de lecture, consultez [`http_connection_timeout`](/fr/reference/settings/session-settings/http#http_connection_timeout) et [`http_receive_timeout`](/fr/reference/settings/session-settings/http#http_receive_timeout). Il s’agit de paramètres de requête ou de profil, et non de clés de la configuration du disque `web`. Les requêtes HTTP émises en dehors d’une requête SQL utilisent les paramètres du contexte global. Le lecteur de données web impose un minimum de 20 secondes aux délais d’attente de connexion et de réception ; des valeurs inférieures ne réduisent pas ces délais d’attente de lecture des données.

Pour obtenir les fichiers à téléverser, exécutez :
`clickhouse static-files-disk-uploader --metadata-path <path> --output-dir <dir>` (`--metadata-path` peut être trouvé dans la requête `SELECT data_paths FROM system.tables WHERE name = 'table_name'`).

Lors du chargement des fichiers via `endpoint`, ils doivent être chargés dans le chemin `<endpoint>/store/`, mais la configuration ne doit contenir que `endpoint`.

Si l’URL n’est pas accessible lors du chargement du disque pendant le démarrage des tables par le serveur, toutes les erreurs sont interceptées. Si, dans ce cas, des erreurs se sont produites, les tables peuvent être rechargées (et redevenir visibles) via `DETACH TABLE table_name` -&gt; `ATTACH TABLE table_name`. Si les métadonnées ont été chargées avec succès au démarrage du serveur, les tables sont alors disponibles immédiatement.

Utilisez [`http_max_tries`](/fr/reference/settings/session-settings/http-max#http_max_tries) pour limiter le nombre de tentatives de lecture HTTP, y compris la tentative initiale. Utilisez [`http_retry_initial_backoff_ms`](/fr/reference/settings/session-settings/http-retry#http_retry_initial_backoff_ms) et [`http_retry_max_backoff_ms`](/fr/reference/settings/session-settings/http-retry#http_retry_max_backoff_ms) pour configurer les délais initial et maximal entre les tentatives.

### Réplication zero-copy (pas prête pour la production)

La réplication zero-copy est possible, mais déconseillée, avec les disques `S3` et `HDFS` (non pris en charge). La réplication zero-copy signifie que, si les données sont stockées à distance sur plusieurs machines et doivent être synchronisées, seules les métadonnées sont répliquées (les chemins d&#39;accès aux parties de données), et non les données elles-mêmes.

<Info>
  **La réplication zero-copy n&#39;est pas prête pour la production**

  La réplication zero-copy est désactivée par défaut dans ClickHouse version 22.8 et ultérieure. Cette fonctionnalité n&#39;est pas recommandée en production.
</Info>
