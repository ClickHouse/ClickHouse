ClickHouse peut déterminer automatiquement la structure des données d’entrée dans presque tous les [formats d’entrée](/fr/reference/formats/index) pris en charge.
Ce document explique dans quels cas l’inférence de schéma est utilisée, comment elle fonctionne avec les différents formats d’entrée et quels paramètres
permettent de la contrôler.

## Utilisation {#usage}

L&#39;inférence de schéma est utilisée lorsque ClickHouse doit lire des données dans un format de données donné dont la structure est inconnue.

## Fonctions de table [file](/fr/reference/functions/table-functions/file), [s3](/fr/reference/functions/table-functions/s3), [url](/fr/reference/functions/table-functions/url), [hdfs](/fr/reference/functions/table-functions/hdfs), [azureBlobStorage](/fr/reference/functions/table-functions/azureBlobStorage). {#table-functions-file-s3-url-hdfs-azureblobstorage}

Ces fonctions de table acceptent l&#39;argument facultatif `structure`, qui décrit la structure des données d&#39;entrée. Si cet argument n&#39;est pas spécifié ou s&#39;il est défini sur `auto`, la structure est inférée à partir des données.

**Exemple :**

Supposons que le répertoire `user_files` contienne un fichier `hobbies.jsonl` au format JSONEachRow, avec le contenu suivant :

```json
{"id" :  1, "age" :  25, "name" :  "Josh", "hobbies" :  ["football", "cooking", "music"]}
{"id" :  2, "age" :  19, "name" :  "Alan", "hobbies" :  ["tennis", "art"]}
{"id" :  3, "age" :  32, "name" :  "Lana", "hobbies" :  ["fitness", "reading", "shopping"]}
{"id" :  4, "age" :  47, "name" :  "Brayan", "hobbies" :  ["movies", "skydiving"]}
```

ClickHouse peut lire ces données sans que vous ayez à en préciser la structure :

```sql
SELECT * FROM file('hobbies.jsonl')
```

```response
┌─id─┬─age─┬─name───┬─hobbies──────────────────────────┐
│  1 │  25 │ Josh   │ ['football','cooking','music']   │
│  2 │  19 │ Alan   │ ['tennis','art']                 │
│  3 │  32 │ Lana   │ ['fitness','reading','shopping'] │
│  4 │  47 │ Brayan │ ['movies','skydiving']           │
└────┴─────┴────────┴──────────────────────────────────┘
```

Remarque : le format `JSONEachRow` a été déterminé automatiquement d&#39;après l&#39;extension de fichier `.jsonl`.

Vous pouvez afficher la structure déterminée automatiquement à l&#39;aide de la requête `DESCRIBE` :

```sql
DESCRIBE file('hobbies.jsonl')
```

```response
┌─name────┬─type────────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ id      │ Nullable(Int64)         │              │                    │         │                  │                │
│ age     │ Nullable(Int64)         │              │                    │         │                  │                │
│ name    │ Nullable(String)        │              │                    │         │                  │                │
│ hobbies │ Array(Nullable(String)) │              │                    │         │                  │                │
└─────────┴─────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

## Moteurs de table [File](/fr/reference/engines/table-engines/special/file), [S3](/fr/reference/engines/table-engines/integrations/s3), [URL](/fr/reference/engines/table-engines/special/url), [HDFS](/fr/reference/engines/table-engines/integrations/hdfs), [azureBlobStorage](/fr/reference/engines/table-engines/integrations/azureBlobStorage) {#table-engines-file-s3-url-hdfs-azureblobstorage}

Si la liste des colonnes n&#39;est pas spécifiée dans la requête `CREATE TABLE`, la structure de la table est inférée automatiquement à partir des données.

Prenons le fichier `hobbies.jsonl`. Nous pouvons créer une table avec le moteur `File` à partir des données de ce fichier :

```sql

```


## clickhouse-local {#clickhouse-local}

`clickhouse-local` dispose d&#39;un paramètre facultatif `-S/--structure` qui indique la structure des données d&#39;entrée. Si ce paramètre n&#39;est pas spécifié ou s&#39;il est défini sur `auto`, la structure est inférée à partir des données.

**Exemple :**

Prenons le fichier `hobbies.jsonl`. Nous pouvons interroger les données de ce fichier à l&#39;aide de `clickhouse-local` :

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='DESCRIBE TABLE hobbies'
```

```response
id    Nullable(Int64)
age    Nullable(Int64)
name    Nullable(String)
hobbies    Array(Nullable(String))
```

```shell
clickhouse-local --file='hobbies.jsonl' --table='hobbies' --query='SELECT * FROM hobbies'
```

```response
1    25    Josh    ['football','cooking','music']
2    19    Alan    ['tennis','art']
3    32    Lana    ['fitness','reading','shopping']
4    47    Brayan    ['movies','skydiving']
```

## Utilisation de la structure de la table d’insertion {#using-structure-from-insertion-table}

Lorsque les fonctions de table `file/s3/url/hdfs` sont utilisées pour insérer des données dans une table,
il est possible d’utiliser la structure de la table d’insertion au lieu de l’extraire des données.
Cela peut améliorer les performances d’insertion, car l’inférence de schéma peut prendre du temps. Cette option est également utile lorsque la table possède un schéma optimisé, car
elle évite toute conversion entre types.

Le paramètre [use&#95;structure&#95;from&#95;insertion&#95;table&#95;in&#95;table&#95;functions](/fr/reference/settings/session-settings/use#use_structure_from_insertion_table_in_table_functions)
contrôle ce comportement. Il accepte 3 valeurs possibles :

* 0 - la fonction de table extrait la structure des données.
* 1 - la fonction de table utilise la structure de la table d’insertion.
* 2 - ClickHouse détermine automatiquement s’il est possible d’utiliser la structure de la table d’insertion ou s’il faut recourir à l’inférence de schéma. Valeur par défaut.

**Exemple 1 :**

Créons la table `hobbies1` avec la structure suivante :

```sql
CREATE TABLE hobbies1
(
    `id` UInt64,
    `age` LowCardinality(UInt8),
    `name` String,
    `hobbies` Array(String)
)
ENGINE = MergeTree
ORDER BY id;
```

Puis insérez les données du fichier `hobbies.jsonl` :

```sql
INSERT INTO hobbies1 SELECT * FROM file(hobbies.jsonl)
```

Dans ce cas, toutes les colonnes du fichier sont insérées telles quelles dans la table : ClickHouse utilisera donc la structure de la table d’insertion plutôt que l’inférence de schéma.

**Exemple 2 :**

Créons la table `hobbies2` avec la structure suivante :

```sql
CREATE TABLE hobbies2
(
  `id` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

Puis insérez les données du fichier `hobbies.jsonl` :

```sql
INSERT INTO hobbies2 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

Dans ce cas, toutes les colonnes de la requête `SELECT` sont présentes dans la table : ClickHouse utilisera donc la structure de la table d’insertion.
Notez que cela ne fonctionne qu’avec les formats d’entrée qui prennent en charge la lecture d’un sous-ensemble de colonnes, comme JSONEachRow, TSKV, Parquet, etc. (cela ne fonctionnera donc pas, par exemple, avec le format TSV).

**Exemple 3 :**

Créons la table `hobbies3` avec la structure suivante :

```sql
CREATE TABLE hobbies3
(
  `identifier` UInt64,
  `age` LowCardinality(UInt8),
  `hobbies` Array(String)
)
  ENGINE = MergeTree
ORDER BY identifier;
```

Puis insérez les données du fichier `hobbies.jsonl` :

```sql
INSERT INTO hobbies3 SELECT id, age, hobbies FROM file(hobbies.jsonl)
```

Dans ce cas, la colonne `id` est utilisée dans la requête `SELECT`, mais la table ne contient pas cette colonne (elle possède une colonne nommée `identifier`) ;
ClickHouse ne peut donc pas utiliser la structure de la table d&#39;insertion, et c&#39;est l&#39;inférence de schéma qui sera utilisée.

**Exemple 4 :**

Créons la table `hobbies4` avec la structure suivante :

```sql
CREATE TABLE hobbies4
(
  `id` UInt64,
  `any_hobby` Nullable(String)
)
  ENGINE = MergeTree
ORDER BY id;
```

Puis insérez les données du fichier `hobbies.jsonl` :

```sql
INSERT INTO hobbies4 SELECT id, empty(hobbies) ? NULL : hobbies[1] FROM file(hobbies.jsonl)
```

Dans ce cas, la requête `SELECT` applique certaines opérations à la colonne `hobbies` avant de l’insérer dans la table : ClickHouse ne peut donc pas utiliser la structure de la table d’insertion et recourt à l’inférence de schéma.

## Cache d’inférence de schéma {#schema-inference-cache}

Pour la plupart des formats d’entrée, l’inférence de schéma nécessite de lire une partie des données pour en déterminer la structure, ce qui peut prendre du temps.
Pour éviter d’inférer le même schéma chaque fois que ClickHouse lit les données d’un même fichier, le schéma inféré est mis en cache. Lors d’un nouvel accès au fichier, ClickHouse utilise le schéma mis en cache.

Des paramètres spécifiques permettent de contrôler ce cache :

* `schema_inference_cache_max_elements_for_{file/s3/hdfs/url/azure}` - le nombre maximal de schémas mis en cache pour la fonction de table correspondante. La valeur par défaut est `4096`. Ces paramètres doivent être définis dans la configuration du serveur.
* `schema_inference_use_cache_for_{file,s3,hdfs,url,azure}` - permet d’activer ou de désactiver l’utilisation du cache pour l’inférence de schéma. Ces paramètres peuvent être utilisés dans les requêtes.

Le schéma du fichier peut changer si les données ou les paramètres de format sont modifiés.
C’est pourquoi le cache d’inférence de schéma identifie le schéma à partir de la source du fichier, du nom du format, des paramètres de format utilisés et de la date de dernière modification du fichier.

Remarque : certains fichiers accessibles par URL avec la fonction de table `url` peuvent ne pas fournir de date de dernière modification. Un paramètre spécifique est prévu pour ce cas :
`schema_inference_cache_require_modification_time_for_url`. La désactivation de ce paramètre permet d’utiliser le schéma mis en cache pour ces fichiers, même en l’absence de date de dernière modification.

Il existe également une table système [schema&#95;inference&#95;cache](/fr/reference/system-tables/schema_inference_cache) contenant tous les schémas actuellement en cache, ainsi qu’une requête système `SYSTEM CLEAR SCHEMA CACHE [FOR File/S3/URL/HDFS]`
qui permet de vider le cache de schéma pour toutes les sources ou pour une source spécifique.

## Formats texte {#text-formats}

Pour les formats texte, ClickHouse lit les données ligne par ligne, extrait les valeurs de colonne selon le format,
puis utilise des parseurs récursifs et des heuristiques pour déterminer le type de chaque valeur. Le nombre maximal de lignes et d&#39;octets lus dans les données lors de l&#39;inférence de schéma
est contrôlé par les paramètres `input_format_max_rows_to_read_for_schema_inference` (25000 par défaut) et `input_format_max_bytes_to_read_for_schema_inference` (32Mb par défaut).
Par défaut, tous les types inférés sont [Nullable](/fr/reference/data-types/nullable), mais vous pouvez modifier ce comportement à l&#39;aide du paramètre `schema_inference_make_columns_nullable` (voir les exemples dans la section [Paramètres](#settings-for-text-formats)).

### Formats JSON {#json-formats}

Dans les formats JSON, ClickHouse analyse les valeurs conformément à la spécification JSON, puis tente de leur attribuer le type de données le plus approprié.

Voyons comment cela fonctionne, quels types peuvent être inférés et quels paramètres spécifiques sont disponibles pour les formats JSON.

### CSV {#csv}

Au format CSV, ClickHouse extrait les valeurs de colonne de la ligne en fonction des délimiteurs. ClickHouse s&#39;attend à ce que tous les types, à l&#39;exception des nombres et des chaînes de caractères, soient entourés de guillemets doubles. Si la valeur est entre guillemets doubles, ClickHouse tente d&#39;analyser
les données entre guillemets à l&#39;aide de l&#39;analyseur syntaxique récursif, puis tente de déterminer le type de données le plus approprié. Si la valeur n&#39;est pas entre guillemets doubles, ClickHouse tente de l&#39;analyser comme un nombre,
et si la valeur n&#39;est pas un nombre, ClickHouse la traite comme une chaîne de caractères.

Si vous ne souhaitez pas que ClickHouse tente de déterminer des types complexes à l&#39;aide de parseurs et d&#39;heuristiques, vous pouvez désactiver le paramètre `input_format_csv_use_best_effort_in_schema_inference`
et ClickHouse traitera toutes les colonnes comme des chaînes de caractères.

Si le paramètre `input_format_csv_detect_header` est activé, ClickHouse tentera de détecter l&#39;en-tête contenant les noms de colonnes (et éventuellement les types) lors de l&#39;inférence du schéma. Ce paramètre est activé par défaut.

### TSV/TSKV {#tsv-tskv}

Dans les formats TSV/TSKV, ClickHouse extrait la valeur de la colonne à partir de la ligne selon les délimiteurs de tabulation, puis analyse la valeur extraite à l&#39;aide de
l&#39;analyseur syntaxique récursif afin de déterminer le type le plus approprié. Si le type ne peut pas être déterminé, ClickHouse traite cette valeur comme String.

Si vous ne souhaitez pas que ClickHouse tente de déterminer des types complexes à l&#39;aide de certains parseurs et heuristiques, vous pouvez désactiver le paramètre `input_format_tsv_use_best_effort_in_schema_inference`
et ClickHouse traitera toutes les colonnes comme des chaînes de caractères.

type de données de chaque valeur selon sa règle d’échappement.

**Exemple**

Supposons que nous ayons un fichier `resultset` contenant les données suivantes :

```bash
<result_before_delimiter>
${data}<result_after_delimiter>
```

Et un fichier `row_format` avec le contenu suivant :

```text
<row_before_delimiter>${column_1:CSV}<field_delimiter_1>${column_2:Quoted}<field_delimiter_2>${column_3:JSON}<row_after_delimiter>
```

Nous pouvons ensuite exécuter les requêtes suivantes :

```sql
SET format_template_rows_between_delimiter = '<row_between_delimiter>\n',
       format_template_row = 'row_format',
       format_template_resultset = 'resultset_format'

DESC format(Template, $$<result_before_delimiter>
<row_before_delimiter>42.42<field_delimiter_1>'Some string 1'<field_delimiter_2>[1, null, 2]<row_after_delimiter>
<row_between_delimiter>
<row_before_delimiter>\N<field_delimiter_1>'Some string 3'<field_delimiter_2>[1, 2, null]<row_after_delimiter>
<result_after_delimiter>
$$)
```

```response
┌─name─────┬─type───────────────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ column_1 │ Nullable(Float64)      │              │                    │         │                  │                │
│ column_2 │ Nullable(String)       │              │                    │         │                  │                │
│ column_3 │ Array(Nullable(Int64)) │              │                    │         │                  │                │
└──────────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Regexp {#regexp}

Comme pour Template, avec le format Regexp, ClickHouse extrait d’abord toutes les valeurs de colonne de la ligne à l’aide de l’expression régulière spécifiée, puis tente d’inférer
le type de données de chaque valeur selon la règle d’échappement spécifiée.

**Exemple**

```sql
SET format_regexp = '^Line: value_1=(.+?), value_2=(.+?), value_3=(.+?)',
       format_regexp_escaping_rule = 'CSV'

DESC format(Regexp, $$Line: value_1=42, value_2="Some string 1", value_3="[1, NULL, 3]"
Line: value_1=2, value_2="Some string 2", value_3="[4, 5, NULL]"$$)
```

```response

│ c1   │ Nullable(Int64)        │              │                    │         │                  │                │
│ c2   │ Nullable(String)       │              │                    │         │                  │                │
│ c3   │ Array(Nullable(Int64)) │              │                    │         │                  │                │
└──────┴────────────────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Paramètres des formats texte {#settings-for-text-formats}

#### input_format_max_rows_to_read_for_schema_inference/input_format_max_bytes_to_read_for_schema_inference {#input-format-max-rows-to-read-for-schema-inference}

Ces paramètres contrôlent la quantité de données à lire lors de l&#39;inférence de schéma.
Plus le nombre de lignes ou d&#39;octets lus est élevé, plus l&#39;inférence de schéma prend du temps, mais plus les chances de
déterminer correctement les types sont grandes (en particulier lorsque les données contiennent beaucoup de valeurs nulles).

Valeurs par défaut :

* `25000` pour `input_format_max_rows_to_read_for_schema_inference`.
* `33554432` (32 Mo) pour `input_format_max_bytes_to_read_for_schema_inference`.

#### column_names_for_schema_inference {#column-names-for-schema-inference}

La liste des noms de colonnes à utiliser pour l’inférence de schéma dans les formats sans noms de colonnes explicites. Les noms spécifiés seront utilisés à la place des noms par défaut `c1,c2,c3,...`. Format : `column1,column2,column3,...`.

**Exemple**

```sql
DESC format(TSV, 'Hello, World!    42    [1, 2, 3]') settings column_names_for_schema_inference = 'str,int,arr'
```

## Formats autodescriptifs {#self-describing-formats}

Les formats autodescriptifs intègrent des informations sur la structure des données au sein même des données :
il peut s&#39;agir d&#39;un en-tête contenant une description, d&#39;un arbre de types binaire ou d&#39;une sorte de table.
Pour inférer automatiquement un schéma à partir de fichiers dans ces formats, ClickHouse lit la partie des données contenant
les informations sur les types et la convertit en schéma de table ClickHouse.

### Formats avec le suffixe -WithNamesAndTypes {#formats-with-names-and-types}

ClickHouse prend en charge certains formats texte dotés du suffixe -WithNamesAndTypes. Ce suffixe indique que les données comportent deux lignes supplémentaires, contenant les noms de colonnes et les types, avant les données proprement dites.
Lors de l&#39;inférence de schéma pour ces formats, ClickHouse lit les deux premières lignes et en extrait les noms de colonnes et les types.

**Exemple**

```sql
DESC format(TSVWithNamesAndTypes,
$$num    str    arr
UInt8    String    Array(UInt8)
42    Hello, World!    [1,2,3]
$$)
```

```response
┌─name─┬─type─────────┬─default_type─┬─default_expression─┬─comment─┬─codec_expression─┬─ttl_expression─┐
│ num  │ UInt8        │              │                    │         │                  │                │
│ str  │ String       │              │                    │         │                  │                │
│ arr  │ Array(UInt8) │              │                    │         │                  │                │
└──────┴──────────────┴──────────────┴────────────────────┴─────────┴──────────────────┴────────────────┘
```

### Formats JSON avec métadonnées {#json-with-metadata}

Certains formats d’entrée JSON ([JSON](/fr/reference/formats/JSON/JSON), [JSONCompact](/fr/reference/formats/JSON/JSONCompact), [JSONColumnsWithMetadata](/fr/reference/formats/JSON/JSONColumnsWithMetadata)) contiennent des métadonnées indiquant les noms et les types des colonnes.
Lors de l’inférence de schéma pour ces formats, ClickHouse lit ces métadonnées.

**Exemple**

```sql

{
    "meta":

            "name": "num",
            "type": "UInt8"

            "type": "String"
        },

            "name": "arr",
            "type": "Array(UInt8)"
        }
    ],

    "data":
    [
        {
            "num": 42,
            "str": "Hello, World",
            "arr": [1,2,3]
        }
    ],

    "rows": 1,

    "statistics":
    {
        "elapsed": 0.005723915,
        "rows_read": 1,
        "bytes_read": 1
    }
}
$$)
```

### Avro {#avro}

Pour le format Avro, ClickHouse lit le schéma à partir des données et le convertit en schéma ClickHouse selon les correspondances de types suivantes :

| Type de données Avro               | Type de données ClickHouse                                            |
| ---------------------------------- | --------------------------------------------------------------------- |
| `boolean`                          | [Bool](/fr/reference/data-types/boolean)                                 |

## Formats binaires fortement typés {#strong-typed-binary-formats}

Dans ces formats, chaque valeur sérialisée contient des informations sur son type (et éventuellement sur son nom), mais aucune information sur la table dans son ensemble.
Lors de l’inférence de schéma pour ces formats, ClickHouse lit les données ligne par ligne (jusqu’à `input_format_max_rows_to_read_for_schema_inference` lignes ou `input_format_max_bytes_to_read_for_schema_inference` octets) et extrait
le type (et éventuellement le nom) de chaque valeur à partir des données, puis convertit ces types en types ClickHouse.

### MsgPack {#msgpack}

Le format MsgPack ne comporte aucun délimiteur entre les lignes. Pour utiliser l’inférence de schéma avec ce format, vous devez spécifier le nombre de colonnes de la table
à l’aide du paramètre `input_format_msgpack_number_of_columns`. ClickHouse utilise les correspondances de types suivantes :

| Type de données MessagePack (`INSERT`)                             | Type de données ClickHouse                   |
| ------------------------------------------------------------------ | -------------------------------------------- |
| `int N`, `uint N`, `negative fixint`, `positive fixint`            | [Int64](/fr/reference/data-types/int-uint)      |
| `bool`                                                             | [UInt8](/fr/reference/data-types/int-uint)      |
| `fixstr`, `str 8`, `str 16`, `str 32`, `bin 8`, `bin 16`, `bin 32` | [string](/fr/reference/data-types/string)       |
| `float 32`                                                         | [Float32](/fr/reference/data-types/float)       |
| `float 64`                                                         | [Float64](/fr/reference/data-types/float)       |
| `uint 16`                                                          | [Date](/fr/reference/data-types/date)           |
| `uint 32`                                                          | [DateTime](/fr/reference/data-types/datetime)   |
| `uint 64`                                                          | [DateTime64](/fr/reference/data-types/datetime) |
| `fixarray`, `array 16`, `array 32`                                 | [Array](/fr/reference/data-types/array)         |
| `fixmap`, `map 16`, `map 32`                                       | [Map](/fr/reference/data-types/map)             |

Par défaut, tous les types inférés sont encapsulés dans `Nullable`, mais ce comportement peut être modifié à l’aide du paramètre `schema_inference_make_columns_nullable`.

### BSONEachRow {#bsoneachrow}

Dans BSONEachRow, chaque ligne de données est représentée par un document BSON. Lors de l’inférence de schéma, ClickHouse lit les documents BSON un par un et en extrait
les valeurs, les noms et les types, puis convertit ces types en types ClickHouse selon les correspondances de types suivantes :

| Type BSON                                                                                              | Type ClickHouse                                                                                                    |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `\x08` booléen                                                                                         | [Bool](/fr/reference/data-types/boolean)                                                                              |
| `\x10` int32                                                                                           | [Int32](/fr/reference/data-types/int-uint)                                                                            |
| `\x12` int64                                                                                           | [Int64](/fr/reference/data-types/int-uint)                                                                            |
| `\x01` double                                                                                          | [Float64](/fr/reference/data-types/float)                                                                             |
| `\x09` date-heure                                                                                      | [DateTime64](/fr/reference/data-types/datetime64)                                                                     |
| `\x05` binaire avec le sous-type binaire `\x00`, `\x02` string, `\x0E` symbole, `\x0D` code JavaScript | [string](/fr/reference/data-types/string)                                                                             |
| `\x07` ObjectId,                                                                                       | [FixedString(12)](/fr/reference/data-types/fixedstring)                                                               |
| `\x05` binaire avec le sous-type uuid `\x04`, taille = 16                                              | [UUID](/fr/reference/data-types/uuid)                                                                                 |
| `\x04` tableau                                                                                         | [Array](/fr/reference/data-types/array)/[Tuple](/fr/reference/data-types/tuple) (si les types imbriqués sont différents) |

## Modes d’inférence de schéma {#schema-inference-modes}

L’inférence de schéma à partir de l’ensemble des fichiers de données peut s’effectuer selon 2 modes différents : `default` et `union`.
Le mode est défini par le paramètre `schema_inference_mode`.

### Mode par défaut {#default-schema-inference-mode}

En mode par défaut, ClickHouse suppose que tous les fichiers ont le même schéma et tente de l’inférer en lisant les fichiers un par un jusqu’à y parvenir.

Exemple :

Supposons que nous ayons 3 fichiers `data1.jsonl`, `data2.jsonl` et `data3.jsonl` dont le contenu est le suivant :

`data1.jsonl` :

```json
{"field1" :  1, "field2" :  null}
{"field1" :  2, "field2" :  null}
{"field1" :  3, "field2" :  null}
```

`data2.jsonl` :

```json
{"field1" :  4, "field2" :  "Data4"}
{"field1" :  5, "field2" :  "Data5"}
{"field1" :  6, "field2" :  "Data5"}
```

`data3.jsonl` :

```json
{"field1" :  7, "field2" :  "Data7", "field3" :  [1, 2, 3]}
{"field1" :  8, "field2" :  "Data8", "field3" :  [4, 5, 6]}
{"field1" :  9, "field2" :  "Data9", "field3" :  [7, 8, 9]}
```

Essayons d’utiliser l’inférence de schéma sur ces 3 fichiers :

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='default'
```

```response title="Response"
┌─name───┬─type─────────────┐
│ field1 │ Nullable(Int64)  │
│ field2 │ Nullable(String) │
└────────┴──────────────────┘
```

Comme nous pouvons le constater, le champ `field3` du fichier `data3.jsonl` est absent.
En effet, ClickHouse a d’abord tenté d’inférer le schéma à partir du fichier `data1.jsonl`, sans succès, car le champ `field2` ne contenait que des valeurs nulles,
puis y est parvenu à partir de `data2.jsonl`. Les données du fichier `data3.jsonl` n’ont donc pas été lues.

### Mode union {#default-schema-inference-mode-1}

En mode union, ClickHouse considère que les fichiers peuvent avoir des schémas différents. Il infère donc les schémas de tous les fichiers, puis les réunit en un schéma commun.

Supposons que nous ayons 3 fichiers `data1.jsonl`, `data2.jsonl` et `data3.jsonl` dont le contenu est le suivant :

`data1.jsonl` :

```json
{"field1" :  1}
{"field1" :  2}
{"field1" :  3}
```

`data2.jsonl` :

```json
{"field2" :  "Data4"}
{"field2" :  "Data5"}
{"field2" :  "Data5"}
```

`data3.jsonl` :

```json
{"field3" :  [1, 2, 3]}
{"field3" :  [4, 5, 6]}
{"field3" :  [7, 8, 9]}
```

Essayons d’utiliser l’inférence de schéma sur ces 3 fichiers :

```sql title="Query"
:) DESCRIBE file('data{1,2,3}.jsonl') SETTINGS schema_inference_mode='union'
```

```response title="Response"
┌─name───┬─type───────────────────┐
│ field1 │ Nullable(Int64)        │
│ field2 │ Nullable(String)       │
│ field3 │ Array(Nullable(Int64)) │
└────────┴────────────────────────┘
```

Comme nous pouvons le constater, nous retrouvons tous les champs de tous les fichiers.

Remarque :

* Certains fichiers pouvant ne pas contenir toutes les colonnes du schéma obtenu, le mode union n’est pris en charge que pour les formats permettant de lire un sous-ensemble de colonnes (comme JSONEachRow, Parquet, TSVWithNames, etc.). Il ne fonctionne pas avec les autres formats (comme CSV, TSV, JSONCompactEachRow, etc.).
* Si ClickHouse ne peut pas inférer le schéma de l’un des fichiers, une exception est levée.
* Si vous avez un grand nombre de fichiers, la lecture du schéma de chacun d’eux peut prendre beaucoup de temps.

## Détection automatique du format {#automatic-format-detection}

Si le format des données n’est pas spécifié et ne peut pas être déterminé à partir de l’extension du fichier, ClickHouse tentera de le détecter en analysant le contenu du fichier.

**Exemples :**

Supposons que `data` ait le contenu suivant :

```csv
"a","b"
1,"Data1"
2,"Data2"
3,"Data3"
```

Nous pouvons examiner ce fichier et l’interroger sans préciser son format ni sa structure :

```sql
:) desc file(data);
```

```response
┌─name─┬─type─────────────┐
│ a    │ Nullable(Int64)  │
│ b    │ Nullable(String) │
└──────┴──────────────────┘
```

```sql
:) select * from file(data);
```

```response
┌─a─┬─b─────┐
│ 1 │ Data1 │
│ 2 │ Data2 │
│ 3 │ Data3 │
└───┴───────┘
```

<Note>
  ClickHouse ne peut détecter qu&#39;un sous-ensemble des formats, et cette détection prend du temps ; il est donc toujours préférable de préciser explicitement le format.
</Note>
