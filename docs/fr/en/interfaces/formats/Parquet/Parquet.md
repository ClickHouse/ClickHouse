<div id="description">
  ## Description
</div>

[Apache Parquet](https://parquet.apache.org/) est un format de stockage colonnaire largement répandu dans l&#39;écosystème Hadoop. ClickHouse prend en charge la lecture et l&#39;écriture de ce format.

<div id="data-types-matching-parquet">
  ## Correspondance entre les types de données
</div>

Lors de l&#39;écriture d&#39;un fichier Parquet, les types de données qui n&#39;ont pas de type Parquet correspondant sont convertis vers le type disponible le plus proche :

| Type de données ClickHouse                                             | Type Parquet                                         |
| ---------------------------------------------------------------------- | ---------------------------------------------------- |
| [IPv4](/fr/sql-reference/data-types/ipv4.md)                              | `UINT_32`                                            |
| [IPv6](/fr/sql-reference/data-types/ipv6.md)                              | `FIXED_LEN_BYTE_ARRAY` (16 octets)                   |
| [Date](/fr/sql-reference/data-types/date.md) (16 bits)                    | `DATE` (32 bits)                                     |
| [DateTime](/fr/sql-reference/data-types/datetime.md) (32 bits, secondes)  | `TIMESTAMP` (64 bits, millisecondes)                 |
| [Int128/UInt128/Int256/UInt256](/fr/sql-reference/data-types/int-uint.md) | `FIXED_LEN_BYTE_ARRAY` (16/32 octets, little-endian) |
| [Point](/fr/sql-reference/data-types/geo.md#point)                        | `BYTE_ARRAY` (WKB) + métadonnées GeoParquet          |
| [LineString](/fr/sql-reference/data-types/geo.md#linestring)              | `BYTE_ARRAY` (WKB) + métadonnées GeoParquet          |
| [Polygon](/fr/sql-reference/data-types/geo.md#polygon)                    | `BYTE_ARRAY` (WKB) + métadonnées GeoParquet          |
| [MultiLineString](/fr/sql-reference/data-types/geo.md#multilinestring)    | `BYTE_ARRAY` (WKB) + métadonnées GeoParquet          |
| [MultiPolygon](/fr/sql-reference/data-types/geo.md#multipolygon)          | `BYTE_ARRAY` (WKB) + métadonnées GeoParquet          |

Les `Array` peuvent être imbriqués et accepter une valeur de type `Nullable` comme argument. Les types `Tuple` et `Map` peuvent également être imbriqués.

Les types de données des colonnes d&#39;une table ClickHouse peuvent différer des champs correspondants dans les données Parquet insérées. Lors de l&#39;insertion de données, ClickHouse interprète les types de données conformément au tableau ci-dessus, puis [convertit](/fr/sql-reference/functions/type-conversion-functions#CAST) les données vers le type de données défini pour la colonne de la table ClickHouse. Par exemple, une colonne Parquet `UINT_32` peut être lue dans une colonne ClickHouse [IPv4](/fr/sql-reference/data-types/ipv4.md).

Pour certains types Parquet, il n&#39;existe pas de type ClickHouse véritablement équivalent. Nous les lisons comme suit :

* `TIME` (heure de la journée) est lu comme un timestamp. Par exemple, `10:23:13.000` devient `1970-01-01 10:23:13.000`.
* `TIMESTAMP`/`TIME` avec `isAdjustedToUTC=false` correspond à une heure locale d&#39;horloge (champs année, mois, jour, heure, minute, seconde et fraction de seconde dans un fuseau horaire local, quel que soit le fuseau horaire considéré comme local), comme en SQL avec `TIMESTAMP WITHOUT TIME ZONE`. ClickHouse le lit à la place comme s&#39;il s&#39;agissait d&#39;un timestamp UTC. Par exemple, `2025-09-29 18:42:13.000` (représentant la lecture d&#39;une horloge locale) devient `2025-09-29 18:42:13.000` (`DateTime64(3, 'UTC')`, qui représente un point dans le temps). Si cette valeur est convertie en String, elle affiche correctement l&#39;année, le mois, le jour, l&#39;heure, la minute, la seconde et la fraction de seconde, qui peuvent ensuite être interprétés comme appartenant à un fuseau horaire local plutôt qu&#39;à UTC. De façon contre-intuitive, remplacer le type `DateTime64(3, 'UTC')` par `DateTime64(3)` n&#39;aiderait pas, car les deux types représentent un point dans le temps plutôt qu&#39;une heure lue sur une horloge, mais `DateTime64(3)` serait formaté à tort avec le fuseau horaire local.
* `INTERVAL` est actuellement lu comme `FixedString(12)` avec la représentation binaire brute de l&#39;intervalle de temps, telle qu&#39;encodée dans le fichier Parquet.

<div id="geo-types">
  ## Types Geo (GeoParquet)
</div>

ClickHouse prend en charge la lecture et l’écriture des colonnes géométriques conformément à la spécification [GeoParquet](https://geoparquet.org/). Les colonnes géométriques sont stockées sous forme de `BYTE_ARRAY` encodés en [WKB](https://libgeos.org/specifications/wkb/) (ou en WKT à la lecture), avec une clé JSON `geo` dans les métadonnées Parquet au niveau du fichier, qui décrit l’encodage, le type de géométrie et le CRS de chaque colonne géométrique.

<div id="read">
  ### Comportement en lecture
</div>

Lors de la lecture, les colonnes géométriques sont associées aux [types de données Geo](/fr/sql-reference/data-types/geo.md) ClickHouse correspondants :

* Une colonne déclarée comme `Point`, `LineString`, `Polygon`, `MultiLineString` ou `MultiPolygon` est lue dans le type Geo ClickHouse correspondant.
* Une colonne contenant plusieurs types de géométrie ou des types de géométrie inconnus est lue dans le type [`Geometry`](/fr/sql-reference/data-types/geo.md#geometry), qui est un `Variant` de tous les types Geo pris en charge.
* Si le type de colonne demandé est `String`, les métadonnées GeoParquet sont ignorées et la payload de géométrie brute encodée est renvoyée telle quelle — sous forme d’octets WKB ou WKT, selon l’encodage déclaré par la colonne GeoParquet. Cela vaut également si le paramètre [`input_format_parquet_allow_geoparquet_parser`](/fr/operations/settings/settings-formats.md#input_format_parquet_allow_geoparquet_parser) est défini sur `0`.

<div id="write">
  ### Comportement d’écriture
</div>

Lors de l’écriture, les colonnes de premier niveau de type `Point`, `LineString`, `Polygon`, `MultiLineString` ou `MultiPolygon` sont encodées en `BYTE_ARRAY` (WKB), et les métadonnées JSON `geo` appropriées sont ajoutées au pied de page du fichier Parquet. Un [`Geometry`](/fr/sql-reference/data-types/geo.md#geometry) `Variant` de premier niveau est également encodé sous la forme d’une charge utile `BYTE_ARRAY` WKB (ses sous-valeurs sont converties en WKB et stockées dans une colonne `Nullable(String)`), mais aucune métadonnée `geo` n’est émise pour lui ; le résultat n’est donc pas reconnu à la lecture comme une colonne de géométrie GeoParquet. Les autres types liés à la géométrie, tels que [`Ring`](/fr/sql-reference/data-types/geo.md#ring), sont écrits à l’aide de leur représentation native sous-jacente, sans métadonnées GeoParquet. Ce comportement peut être entièrement désactivé en définissant [`output_format_parquet_geometadata`](/fr/operations/settings/settings-formats.md#output_format_parquet_geometadata) sur `0`. Dans ce cas, même les types geo pris en charge sont écrits à l’aide de leur représentation native sous-jacente (`Point` comme `Tuple(Float64, Float64)`, `LineString` comme `Array(Point)`, `Polygon` comme `Array(Array(Point))`, etc.), et aucune métadonnée GeoParquet n’est émise.

Les colonnes géométriques doivent apparaître à la racine du schéma ou être imbriquées dans `Tuple` (`struct`) ; leur imbrication dans `Array` ou `Map` n’est pas prise en charge. `Nullable` n’est pas non plus pris en charge pour les colonnes geo.

Insérez les données :

```sql

```

<div id="reading-data">
  ### Lecture des données
</div>

Lisez les données au format `Parquet` :

```sql
SELECT *
FROM football
INTO OUTFILE 'football.parquet'
FORMAT Parquet
```

:::tip
Parquet est un format binaire qui ne s’affiche pas de façon lisible par l’humain dans le terminal. Utilisez `INTO OUTFILE` pour produire des fichiers Parquet.
:::

Pour échanger des données avec Hadoop, vous pouvez utiliser le [`moteur de table HDFS`](/fr/engines/table-engines/integrations/hdfs.md).
