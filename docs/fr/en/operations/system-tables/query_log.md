<div id="description">
  ## Description
</div>

Stocke des métadonnées et des statistiques sur les requêtes exécutées, telles que l&#39;heure de début, la durée, les messages d&#39;erreur, l&#39;utilisation des ressources et d&#39;autres détails d&#39;exécution. Cette table ne stocke pas les résultats des requêtes.

Vous pouvez modifier les paramètres de journalisation des requêtes dans la section [query&#95;log](../../operations/server-configuration-parameters/settings.md#query_log) de la configuration du serveur.

Vous pouvez désactiver la journalisation des requêtes en définissant [log&#95;queries = 0](/fr/operations/settings/settings#log_queries). Nous vous déconseillons de désactiver la journalisation, car les informations de cette table sont importantes pour résoudre les problèmes.

La fréquence de vidage des données est définie par le paramètre `flush_interval_milliseconds` dans la section des paramètres du serveur [query&#95;log](../../operations/server-configuration-parameters/settings.md#query_log). Pour forcer le vidage, utilisez la requête [SYSTEM FLUSH LOGS](/fr/sql-reference/statements/system#flush-logs).

ClickHouse ne supprime pas automatiquement les données de la table. Voir [Introduction](/fr/operations/system-tables/overview#system-tables-introduction) pour plus de détails.

La table `system.query_log` enregistre deux types de requêtes :

1. Les requêtes initiales exécutées directement par le client.
2. Les requêtes enfants déclenchées par d&#39;autres requêtes (dans le cadre d&#39;une exécution de requête distribuée). Pour ces types de requêtes, les informations sur les requêtes parentes s&#39;affichent dans les colonnes `initial_*`.

Chaque requête crée une ou deux lignes dans la table `query_log`, selon le statut (voir la colonne `type`) de la requête :

1. Si l&#39;exécution de la requête réussit, deux lignes de type `QueryStart` et `QueryFinish` sont créées.
2. Si une erreur se produit pendant le traitement de la requête, deux événements de type `QueryStart` et `ExceptionWhileProcessing` sont créés.
3. Si une erreur se produit avant le lancement de la requête, un seul événement de type `ExceptionBeforeStart` est créé.

Vous pouvez utiliser le paramètre [log&#95;queries&#95;probability](/fr/operations/settings/settings#log_queries_probability) pour réduire le nombre de requêtes enregistrées dans la table `query_log`.

Vous pouvez utiliser le paramètre [log&#95;formatted&#95;queries](/fr/operations/settings/settings#log_formatted_queries) pour consigner les requêtes mises en forme dans la colonne `formatted_query`.

* `query_start_time` ([DateTime](/fr/sql-reference/data-types/datetime)) — Heure de début de l’exécution de la requête.
* `query_start_time_microseconds` ([DateTime64(6)](/fr/sql-reference/data-types/datetime64)) — Heure de début de l’exécution de la requête avec une précision à la microseconde.

* `read_rows` ([UInt64](/fr/sql-reference/data-types/int-uint)) — Nombre total de lignes lues depuis toutes les tables et fonctions de table participant à la requête. Cela inclut les sous-requêtes habituelles, ainsi que les sous-requêtes pour IN et JOIN. Pour les requêtes distribuées, read&#95;rows inclut le nombre total de lignes lues sur toutes les répliques. Chaque réplique envoie sa valeur read&#95;rows, et le serveur initiateur de la requête additionne toutes les valeurs reçues et locales. Les volumes de cache n’affectent pas cette valeur.
* `read_bytes` ([UInt64](/fr/sql-reference/data-types/int-uint)) — Nombre total d’octets lus depuis toutes les tables et fonctions de table participant à la requête. Cela inclut les sous-requêtes habituelles, ainsi que les sous-requêtes pour IN et JOIN. Pour les requêtes distribuées, read&#95;bytes inclut le nombre total d’octets lus sur toutes les répliques. Chaque réplique envoie sa valeur read&#95;bytes, et le serveur initiateur de la requête additionne toutes les valeurs reçues et locales. Les volumes de cache n’affectent pas cette valeur.
* `written_rows` ([UInt64](/fr/sql-reference/data-types/int-uint)) — Nombre de lignes écrites par la requête, y compris les lignes écrites par des insertions en aval déclenchées par le pipeline, comme les vues matérialisées attachées. Pour un insert synchrone, ces lignes en aval sont enregistrées dans l’entrée `query_kind` = `Insert` ; pour un asynchronous insert, elles sont enregistrées dans l’entrée `query_kind` = `AsyncInsertFlush`, tandis que l’entrée `Insert` côté client n’enregistre que les lignes acceptées du client. Pour les requêtes qui n’écrivent pas de lignes, cette valeur est 0.
* `written_bytes` ([UInt64](/fr/sql-reference/data-types/int-uint)) — Nombre d’octets écrits par la requête (non compressés), y compris les octets écrits par des insertions en aval déclenchées par le pipeline, comme les vues matérialisées attachées. Pour un insert synchrone, ces octets en aval sont enregistrés dans l’entrée `query_kind` = `Insert` ; pour un asynchronous insert, ils sont enregistrés dans l’entrée `query_kind` = `AsyncInsertFlush`, tandis que l’entrée `Insert` côté client n’enregistre que les octets acceptés du client. Pour les requêtes qui n’écrivent pas de données, cette valeur est 0.
* `result_rows` ([UInt64](/fr/sql-reference/data-types/int-uint)) — Nombre de lignes dans le résultat d’une requête SELECT, ou nombre de lignes écrites par un insert. Pour un insert synchrone, cela inclut les lignes écrites par des insertions en aval déclenchées par le pipeline (comme les vues matérialisées attachées) dans l’entrée `query_kind` = `Insert` ; pour un asynchronous insert, ces lignes en aval sont enregistrées dans l’entrée `query_kind` = `AsyncInsertFlush`, tandis que l’entrée `Insert` côté client n’enregistre que les lignes acceptées du client.

* `current_database` ([LowCardinality(String)](/fr/sql-reference/data-types/lowcardinality)) — Nom de la base de données courante.
* `query` ([String](/fr/sql-reference/data-types/string)) — Texte de la requête.

**Exemple Cloud**

Dans ClickHouse Cloud, `system.query_log` est propre à chaque nœud ; pour voir toutes les entrées, vous devez interroger via [`clusterAllReplicas`](/fr/sql-reference/table-functions/cluster).

Par exemple, pour agréger les lignes de `query&#95;log` de chaque réplique du cluster « default », vous pouvez écrire :

```sql
SELECT * 
FROM clusterAllReplicas('default', system.query_log)
WHERE event_time >= now() - toIntervalHour(1)
LIMIT 10
SETTINGS skip_unavailable_shards = 1;
```
