<div id="description">
  ## Description
</div>

La table `system.iceberg_metadata_log` enregistre les événements d&#39;accès aux métadonnées et d&#39;analyse des tables Iceberg lues par ClickHouse. Elle fournit des informations détaillées sur chaque fichier de métadonnées ou entrée traitée, ce qui est utile pour le débogage, l&#39;audit et la compréhension de l&#39;évolution de la structure des tables Iceberg.

Cette table consigne chaque fichier de métadonnées et chaque entrée lus à partir de tables Iceberg, y compris les fichiers de métadonnées racine, les listes de manifests et les entrées de manifest. Elle aide les utilisateurs à suivre la manière dont ClickHouse interprète les métadonnées des tables Iceberg et à diagnostiquer les problèmes liés à l&#39;évolution du schéma, à la résolution des fichiers ou à la planification des requêtes.

:::note
Cette table est principalement destinée au débogage.
:::

<div id="controlling-log-verbosity">
  ### Contrôler le niveau de verbosité des journaux
</div>

Vous pouvez définir quels événements de métadonnées sont consignés à l’aide du paramètre [`iceberg_metadata_log_level`](../../operations/settings/settings.md#iceberg_metadata_log_level).

Pour consigner toutes les métadonnées utilisées dans la requête en cours :

```sql
SELECT * FROM my_iceberg_table SETTINGS iceberg_metadata_log_level = 'manifest_file_entry';

SYSTEM FLUSH LOGS iceberg_metadata_log;

SELECT content_type, file_path, row_in_file
FROM system.iceberg_metadata_log
WHERE query_id = '{previous_query_id}';
```

Pour journaliser uniquement le fichier JSON de métadonnées racine utilisé dans la requête en cours :

```sql
SELECT * FROM my_iceberg_table SETTINGS iceberg_metadata_log_level = 'metadata';

SYSTEM FLUSH LOGS iceberg_metadata_log;

SELECT content_type, file_path, row_in_file
FROM system.iceberg_metadata_log
WHERE query_id = '{previous_query_id}';
```

Pour en savoir plus, consultez la description du paramètre [`iceberg_metadata_log_level`](../../operations/settings/settings.md#iceberg_metadata_log_level).

<div id="good-to-know">
  ### Bon à savoir
</div>

* Utilisez `iceberg_metadata_log_level` au niveau de la requête uniquement lorsque vous avez besoin d’examiner votre table Iceberg en détail. Sinon, vous risquez d’alimenter la table de logs avec un volume excessif de métadonnées et d’observer une dégradation des performances.
* La table contient des entrées en double, car elle est principalement destinée au débogage et ne garantit pas l’unicité par entité. Des lignes distinctes stockent le contenu et le statut de pruning, car ils sont collectés à des moments différents dans le programme. Le contenu est collecté lors de la lecture des métadonnées, tandis que le statut de pruning est collecté lorsque les métadonnées sont vérifiées pour le pruning. **Ne vous appuyez jamais sur la table elle-même pour la déduplication.**
* Si vous utilisez un `content_type` plus détaillé que `ManifestListMetadata`, le cache de métadonnées Iceberg est désactivé pour les listes de manifests.
* De même, si vous utilisez un `content_type` plus détaillé que `ManifestFileMetadata`, le cache de métadonnées Iceberg est désactivé pour les fichiers manifestes.
* Si la requête SELECT a été annulée ou a échoué, la table de logs peut tout de même contenir des entrées concernant les métadonnées traitées avant l’échec, mais elle ne contiendra pas d’informations sur les entités de métadonnées qui n’ont pas été traitées.

<div id="content-type-values">
  ### Valeurs de `content_type`
</div>

* `None` : Aucun contenu.
* `Metadata` : Fichier de métadonnées racine.
* `ManifestListMetadata` : Métadonnées de la liste de manifests.
* `ManifestListEntry` : Entrée d’une liste de manifests.
* `ManifestFileMetadata` : Métadonnées du fichier manifeste.
* `ManifestFileEntry` : Entrée d’un fichier manifeste.
