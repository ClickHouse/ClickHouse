<div id="description">
  ## Description
</div>

Contient la liste de toutes les opérations `BACKUP` ou `RESTORE`, avec leur état actuel ainsi que d&#39;autres propriétés. À noter que cette table n&#39;est pas persistante et qu&#39;elle n&#39;affiche que les opérations exécutées depuis le dernier redémarrage du serveur.

<div id="restore-atomicity">
  ## Atomicité de la restauration
</div>

`RESTORE` n&#39;est pas transactionnel et ne revient pas en arrière en cas d&#39;échec. Pour chaque table, toutes les parts sélectionnées sont copiées avant que l&#39;une d&#39;elles soit attachée, mais la phase d&#39;attachement elle-même n&#39;est pas transactionnelle — les parts sont rendues visibles une par une. Les tables sont traitées indépendamment.

**Les tables sont indépendantes.** Une table dont la restauration aboutit reste en place même si une autre table de la même commande échoue ensuite :

```sql
RESTORE TABLE db.t0, TABLE db.t1
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

Si cette commande échoue après la restauration complète de `db.t0`, avant la fin de celle de `db.t1`, `db.t0` reste restaurée.

**La clause `PARTITIONS` ne constitue pas une frontière de commit.** Elle sert uniquement à sélectionner les parts d&#39;une table à restaurer :

```sql
RESTORE TABLE db.t0 PARTITIONS '2026-06-01', '2026-06-02', '2026-06-03'
FROM S3('<endpoint>', '<access_key>', '<secret_key>')
SETTINGS
    allow_non_empty_tables = true;
```

Toutes les parts sélectionnées de la table sont d’abord copiées, puis attachées uniquement lorsqu’elles sont toutes prêtes. Ainsi, si cette commande échoue pendant la phase de copie — par exemple après que la partition `2026-06-01` a été entièrement copiée, alors que `2026-06-02` et `2026-06-03` ne sont pas encore terminées — `2026-06-01` n’est **pas** validée et la table ne conserve aucune donnée restaurée par cette commande. Une fois la phase de copie terminée et l’étape d’attach commencée, les parts sont validées une par une ; ainsi, un échec pendant l’attach peut laisser la table partiellement restaurée, sans rollback.

Pour valider les partitions indépendamment (afin qu’une partition terminée soit conservée en cas d’échec ultérieur et puisse être retentée isolément), exécutez un `RESTORE` distinct par partition, en utilisant `SETTINGS allow_non_empty_tables = true` après la première.
