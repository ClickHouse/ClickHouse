L’intégration de bibliothèques Rust est décrite ici à partir de l’intégration de la fonction de hash BLAKE3.

La première étape de l’intégration consiste à créer un projet Rust vide dans `contrib/<library>-cmake` et à inclure la bibliothèque requise dans son Cargo.toml. Le projet est membre de l’espace de travail cargo situé dans `contrib/rust-contrib-workspace` : ajoutez `workspace = "../rust-contrib-workspace"` sous `[package]`, puis ajoutez le dossier à la liste `members` de `contrib/rust-contrib-workspace/Cargo.toml`. Laissez-le sous forme de bibliothèque simple, sans `crate-type`. Les membres ne sont pas compilés comme des bibliothèques distinctes : le paquet racine de l’espace de travail, `_ch_rust_workspace`, réexporte chaque membre activé et constitue l’unique bibliothèque statique liée par ClickHouse. Dans `contrib/rust-contrib-workspace/Cargo.toml`, déclarez pour le paquet racine une fonctionnalité et une dépendance facultative correspondant au membre (`blake3 = ["dep:_ch_rust_blake3"]` et `_ch_rust_blake3 = { path = "../blake3-cmake", optional = true }`), puis réexportez-le dans `contrib/rust-contrib-workspace/src/lib.rs` (`#[cfg(feature = "blake3")] pub use _ch_rust_blake3;`).

Ensuite, vous devez lier la bibliothèque à CMake à l’aide de la bibliothèque Corrosion. La première étape consiste à ajouter le dossier de la bibliothèque à `contrib/CMakeLists.txt` avec `add_contrib`, à côté des autres membres de l’espace de travail. Vous devez ensuite ajouter le fichier CMakeLists.txt au répertoire de la bibliothèque. Dans ce fichier, ajoutez le membre avec `clickhouse_add_rust_member` : cette fonction crée une cible d’interface liée à la bibliothèque statique de l’espace de travail et active la fonctionnalité correspondante du paquet racine, que `contrib/rust-contrib-workspace/CMakeLists.txt` importe avec Corrosion après l’ensemble des membres. Pour BLAKE3, ces lignes sont les suivantes :

```CMake
clickhouse_add_rust_member(_ch_rust_blake3 FEATURE blake3)

target_include_directories(_ch_rust_blake3 INTERFACE include)
add_library(ch_rust::blake3 ALIAS _ch_rust_blake3)
```

Ainsi, nous allons créer une cible CMake pour le membre, puis lui donner un nom plus pratique. Notez que le nom `_ch_rust_blake3` provient de Cargo.toml, où il est utilisé comme nom de projet (`name = "_ch_rust_blake3"`).

Comme les types de données Rust ne sont pas compatibles avec les types de données C/C++, nous utiliserons notre projet de bibliothèque vide pour créer des méthodes d’adaptation assurant la conversion des données reçues depuis le C/C++, l’appel des méthodes de la bibliothèque, ainsi que la conversion inverse des données de sortie. Par exemple, cette méthode a été écrite pour BLAKE3 :

```rust
#[no_mangle]
pub unsafe extern "C" fn blake3_apply_shim(
    begin: *const c_char,
    _size: u32,
    out_char_data: *mut u8,
```

```rust
#[no_mangle]
pub unsafe extern "C" fn blake3_apply_shim(
    begin: *const c_char,
    _size: u32,
    out_char_data: *mut u8,
) -> *mut c_char {
    if begin.is_null() {
        let err_str = CString::new("input was a null pointer").unwrap();
        return err_str.into_raw();
    }
    let mut hasher = blake3::Hasher::new();
    let input_bytes = CStr::from_ptr(begin);
    let input_res = input_bytes.to_bytes();
    hasher.update(input_res);
    let mut reader = hasher.finalize_xof();
    reader.fill(std::slice::from_raw_parts_mut(out_char_data, blake3::OUT_LEN));
    std::ptr::null_mut()
}
```

Cette méthode prend en entrée une chaîne compatible C, sa taille et un pointeur vers la chaîne de sortie. Elle convertit ensuite les entrées compatibles C en types utilisés par les méthodes réelles de la bibliothèque, puis les appelle. Après cela, elle doit reconvertir les sorties des méthodes de la bibliothèque en types compatibles C. Dans ce cas précis, la bibliothèque permettait l’écriture directe dans le pointeur via la méthode fill(), la conversion n’était donc pas nécessaire. Le principal conseil ici est de créer le moins de méthodes possible, afin de réduire le nombre de conversions à effectuer à chaque appel et de limiter la surcharge.

Il convient de noter que l’attribut `#[no_mangle]` et `extern "C"` sont obligatoires pour toutes ces méthodes. Sans eux, il ne sera pas possible d’effectuer une compilation correctement compatible avec C/C++. De plus, ils sont nécessaires pour l’étape suivante de l’intégration.

Après avoir écrit le code des méthodes d’adaptation, nous devons préparer le fichier d’en-tête de la bibliothèque. Cela peut être fait manuellement, ou vous pouvez utiliser la bibliothèque cbindgen pour le générer automatiquement. Si vous utilisez cbindgen, vous devrez écrire un script de construction build.rs et inclure cbindgen comme dépendance de construction.

Un exemple de script de construction pouvant générer automatiquement un fichier d’en-tête :

```rust
    let crate_dir = env::var("CARGO_MANIFEST_DIR").unwrap();

    let package_name = env::var("CARGO_PKG_NAME").unwrap();
    let output_file = ("include/".to_owned() + &format!("{}.h", package_name)).to_string();

    match cbindgen::generate(&crate_dir) {
        Ok(header) => {
            header.write_to_file(&output_file);
        }
        Err(err) => {
            panic!("{}", err)
        }
    }
```

## Générer le fichier d&#39;en-tête dans ce dépôt {#generating-the-header-in-this-repository}

Le script de construction ci-dessus écrit le fichier d&#39;en-tête dans l&#39;arborescence des sources à chaque construction, si bien qu&#39;il n&#39;y a plus rien à vérifier : un fichier d&#39;en-tête validé qui ne correspond plus au code Rust est simplement écrasé en local et reste incorrect pour tous les autres. Les crates de ce dépôt adoptent plutôt l&#39;une des deux approches suivantes :

* générer le fichier d&#39;en-tête dans le répertoire de construction et y faire pointer `target_include_directories`, comme le fait `contrib/delta-kernel-rs`. Rien n&#39;est validé, donc rien ne peut devenir obsolète ;
* valider le fichier d&#39;en-tête et faire en sorte que le script de construction le compare au fichier fraîchement généré, en faisant échouer la construction en cas de différence, comme le fait `contrib/vortex-cmake`. Les deux moitiés d&#39;une FFI sont des unités de traduction distinctes liées par nom de symbole : une signature modifiée d&#39;un seul côté produit donc silencieusement un comportement indéfini plutôt qu&#39;une erreur de compilation — c&#39;est cette comparaison qui empêche d&#39;oublier de régénérer le fichier. Prévoyez une variable d’environnement qui réécrit le fichier validé, afin que sa mise à jour se fasse en une seule commande.

Deux points à connaître avant d&#39;ajouter `cbindgen` à une crate de `contrib/rust-contrib-workspace` :

* fixez la version de manière exacte. Sa sortie change d&#39;une version corrective à l&#39;autre ; avec une contrainte souple, la vérification finit donc par signaler la version du générateur plutôt qu&#39;une véritable différence. La version doit également faire partie de celles fournies par `contrib/rust_vendor`, faute de quoi il faut réexécuter `contrib/rust-contrib-workspace/vendor.sh` et mettre à jour le sous-module ;
* analysez le fichier source avec `Builder::with_src` plutôt que la crate avec `cbindgen::generate`. Passer par la crate amène cbindgen à exécuter `cargo metadata` dans un processus imbriqué, et ce processus n&#39;hérite pas du `--config` qui fait pointer cargo vers les sources vendorisées.

Par ailleurs, vous devez utiliser l&#39;attribut #[no&#95;mangle] et `extern "C"` pour chaque attribut compatible C. Sans cela, la bibliothèque risque d&#39;être mal compilée et cbindgen ne lancera pas la génération automatique du fichier d&#39;en-tête.

Après toutes ces étapes, vous pouvez tester votre bibliothèque dans un petit projet afin de repérer d&#39;éventuels problèmes de compatibilité ou de génération de fichiers d&#39;en-tête. Si des problèmes surviennent lors de la génération de ces fichiers, vous pouvez essayer d&#39;ajuster cette génération à l&#39;aide du fichier cbindgen.toml (vous trouverez un modèle ici : [https://github.com/eqrion/cbindgen/blob/master/template.toml](https://github.com/eqrion/cbindgen/blob/master/template.toml)).

Il convient également de signaler un problème rencontré lors de l&#39;intégration de BLAKE3 :
MemorySanitizer peut provoquer de faux positifs, car il est incapable de déterminer si certaines variables en Rust sont initialisées ou non. Le problème a été résolu en écrivant une méthode dont la définition est plus explicite pour certaines variables, même si cette implémentation est plus lente et n&#39;est utilisée que pour corriger les builds avec MemorySanitizer.
