<View title="v0.8+">
  Bibliothèque client Java permettant de communiquer avec un serveur de base de données via ses protocoles. L&#39;implémentation actuelle ne prend en charge que l&#39;[interface HTTP](/fr/concepts/features/interfaces/http).
  La bibliothèque fournit sa propre API pour envoyer des requêtes à un serveur, ainsi que des outils pour travailler avec différents formats de données binaires (RowBinary* &amp; Native*).

  ## Initialisation {#initialization}

  L&#39;objet Client est initialisé par `com.clickhouse.client.api.Client.Builder#build()`. Chaque client possède son propre contexte et aucun objet n&#39;est partagé entre eux.
  Le Builder dispose de méthodes de configuration pour en simplifier la mise en œuvre.

  Exemple :

  ```java showLineNumbers
   Client client = new Client.Builder()
                  .addEndpoint("https://clickhouse-cloud-instance:8443/")
                  .setUsername(user)
                  .setPassword(password)
                  .build();
  ```

  `Client` est `AutoCloseable` et doit être fermé lorsqu&#39;il n&#39;est plus nécessaire.

  ### Authentification {#authentication}

  L&#39;authentification est configurée par client lors de la phase d&#39;initialisation. Trois méthodes d&#39;authentification sont prises en charge : par mot de passe, par jeton d&#39;accès ou par certificat client SSL.

  L&#39;authentification par mot de passe nécessite de renseigner le nom d&#39;utilisateur et le mot de passe en appelant `setUsername(String)` et `setPassword(String)` :

  ```java showLineNumbers
   Client client = new Client.Builder()
          .addEndpoint("https://clickhouse-cloud-instance:8443/")
          .setUsername(user)
          .setPassword(password)
          .build();
  ```

  L&#39;authentification par jeton d’accès ou jeton Bearer (tel qu’un JWT) nécessite de configurer le jeton en appelant `useBearerTokenAuth(String)` (ou `setAccessToken(String)` pour les jetons d’accès bruts) :

  ```java showLineNumbers
   Client client = new Client.Builder()
          .addEndpoint("https://clickhouse-cloud-instance:8443/")
          .useBearerTokenAuth(userAccessToken)
          .build();
  ```

  L&#39;authentification par certificat client SSL nécessite de définir le nom d&#39;utilisateur, d&#39;activer l&#39;authentification SSL, de configurer un certificat client et une clé client en appelant respectivement `setUsername(String)`,  `useSSLAuthentication(boolean)`, `setClientCertificate(String)` et `setClientKey(String)` :

  ```java showLineNumbers
  Client client = new Client.Builder()
          .useSSLAuthentication(true)
          .setUsername("some_user")
          .setClientCertificate("some_user.crt")
          .setClientKey("some_user.key")
  ```

  <Note>
    L’authentification SSL peut être difficile à dépanner en production, car de nombreuses erreurs provenant des bibliothèques SSL ne fournissent pas assez d’informations. Par exemple, si le certificat client et la clé ne correspondent pas, le serveur interrompra immédiatement la connexion (dans le cas de HTTP, cela se produira à l’étape d’établissement de la connexion, lorsqu’aucune requête HTTP n’est envoyée, donc aucune réponse n’est renvoyée).

    Veuillez utiliser des outils comme [openssl](https://docs.openssl.org/master/man1/openssl/) pour vérifier les certificats et les clés :

    * vérifier l’intégrité de la clé : `openssl rsa -in [key-file.key] -check -noout`
    * vérifier que le certificat client a un CN correspondant pour un utilisateur :
      * obtenir le CN à partir d’un certificat utilisateur - `openssl x509 -noout -subject -in [user.cert]`
      * vérifier que la même valeur est définie dans la base de données `select name, auth_type, auth_params from system.users where auth_type = 'ssl_certificate'` (la requête affichera `auth_params` avec quelque chose comme ` {"common_names":["some_user"]}`)
  </Note>

  ### Mise en pool des connexions {#connection-pooling}

  Le `Client` utilise Apache HttpClient 5 avec un pool de connexions HTTP interne. Chaque opération emprunte une connexion au pool, envoie la requête, lit la réponse en continu, puis restitue la connexion au pool.

  Principaux paramètres du pool de connexions disponibles dans `Client.Builder` :

  | Paramètre                                     | Méthode du constructeur                                        | Par défaut                   | Description                                                                                                         |
  | --------------------------------------------- | -------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
  | Nombre maximal de connexions                  | `setMaxConnections(int)`                                       | `10`                         | Nombre maximal de connexions HTTP ouvertes par endpoint de serveur.                                                 |
  | TTL de la connexion                           | `setConnectionTTL(long, ChronoUnit)`                           | `-1` (désactivé)             | Time-to-live au terme duquel une connexion active est fermée et recréée.                                            |
  | Délai d’expiration Keep-Alive                 | `setKeepAliveTimeout(long, ChronoUnit)`                        | Valeur par défaut du serveur | Durée de maintien des connexions HTTP inactives mises en pool (Keep-Alive).                                         |
  | Délai d’expiration de la requête de connexion | `setConnectionRequestTimeout(long, ChronoUnit)`                | `10000ms`                    | Durée maximale pendant laquelle un fil d’exécution reste bloqué en attendant une connexion disponible dans le pool. |
  | Stratégie de réutilisation                    | `setConnectionReuseStrategy(ConnectionReuseStrategy strategy)` | `FIFO`                       | Stratégie d&#39;allocation du pool de connexions (`FIFO` ou `LIFO`).                                                |
  | Mise en pool des connexions                   | `enableConnectionPool(boolean enable)`                         | `true`                       | Activer ou désactiver la mise en pool des connexions HTTP.                                                          |

  #### Configuration recommandée du pool de connexions {#recommended-connection-pool-configuration}

  ```java showLineNumbers
  Client client = new Client.Builder()
          .addEndpoint("https://clickhouse-cloud-instance:8443/")
          .setUsername("default")
          .setPassword("secret")
          .setMaxConnections(50)
          .setConnectionRequestTimeout(5, TimeUnit.SECONDS)
          .setKeepAliveTimeout(60, TimeUnit.SECONDS)
          .setConnectionReuseStrategy(ConnectionReuseStrategy.FIFO)
          .build();
  ```

  ## Configuration {#configuration}

  Tous les paramètres sont définis par des méthodes d&#39;instance (aussi appelées méthodes de configuration) qui rendent explicites la portée et le contexte de chaque valeur.
  Les principaux paramètres de configuration sont définis dans une seule portée (client ou opération) et ne se substituent pas mutuellement.

  La configuration est définie lors de la création du client. Voir `com.clickhouse.client.api.Client.Builder`.

  ### Identification du client {#client-identification}

  Le journal de requêtes contient deux champs permettant d&#39;identifier l&#39;application à l&#39;origine d&#39;une requête : `client_name` et `http_user_agent`. Le protocole TCP natif utilise
  `client_name` pour identifier l&#39;application. Le protocole HTTP utilise `http_user_agent` pour identifier l&#39;application. Le builder client dispose de la méthode `setClientName` pour définir les valeurs correctes
  pour les deux protocoles.
  Le champ `http_user_agent` est défini selon le format standard de l&#39;en-tête `User-Agent` : `application-name[/version] [(operating-system; architecture; ...)]`.
  Cet ensemble de valeurs est répété pour chaque couche : application, bibliothèque client, bibliothèque client HTTP. Ce qui est défini par la méthode `setClientName` apparaît en premier dans la liste.

  Par exemple :

  ```java showLineNumbers
  client.setClientName("my-app-01/1.0");
  ```

  donnera la valeur `http_user_agent` suivante :

  ```
  my-app-01/1.0 clickhouse-java-v2/0.9.6-SNAPSHOT (Linux; jvm:17.0.17) Apache-HttpClient/5.4.4
  ```

  L&#39;application peut définir son propre en-tête HTTP `User-Agent` pour s&#39;identifier. Toutefois, la partie `clickhouse-java-v2/0.9.6-SNAPSHOT` sera ajoutée à la fin de l&#39;en-tête.

  ### Identification des opérations {#operation-identification}

  Le journal de requêtes dispose de deux autres champs `query_id` et `log_comment` qui peuvent être utilisés pour identifier une opération et ajouter des informations supplémentaires au journal de requêtes.

  `query_id` est un identifiant unique d&#39;une opération. Il peut être défini par l&#39;application en appelant la méthode `setQueryId` de la classe `QuerySettings`.

  ```java showLineNumbers
  QuerySettings querySettings = new QuerySettings();
  querySettings.setQueryId("some-query-id");
  ```

  `log_comment` est un commentaire pouvant être ajouté au journal des requêtes. Il peut être défini par l&#39;application en appelant la méthode `logComment` de la classe `QuerySettings`.

  ```java showLineNumbers
  QuerySettings querySettings = new QuerySettings();
  querySettings.logComment("some-comment");
  ```

  ### Paramètres du serveur {#server-settings}

  Les paramètres côté serveur peuvent être définis au niveau du client une seule fois lors de sa création (voir la méthode `serverSetting` du `Builder`) et au niveau de l&#39;opération (voir `serverSetting` pour la classe de paramètres d&#39;opération).

  ```java showLineNumbers
   try (Client client = new Client.Builder().addEndpoint(Protocol.HTTP, "localhost", mockServer.port(), false)
          .setUsername("default")
          .setPassword(ClickHouseServerForTest.getPassword())
          .compressClientRequest(true)

          // Client level
          .serverSetting("max_threads", "10")
          .serverSetting("async_insert", "1")
          .serverSetting("roles", Arrays.asList("role1", "role2"))

          .build()) {

  	// Operation level
  	QuerySettings querySettings = new QuerySettings();
  	querySettings.serverSetting("session_timezone", "Europe/Zurich");

  	...
  }
  ```

  ⚠️ Lorsque des options sont définies via la méthode `setOption` (que ce soit via `Client.Builder` ou la classe de paramètres d&#39;opération), le nom des paramètres serveur doit être préfixé de `clickhouse_setting_`. La méthode `com.clickhouse.client.api.ClientConfigProperties#serverSetting()` peut s&#39;avérer utile dans ce cas.

  ### En-têtes HTTP personnalisés {#custom-http-headers}

  Des en-têtes HTTP personnalisés peuvent être définis pour toutes les opérations (au niveau du client) ou pour une seule (au niveau de l&#39;opération). Les paramètres de l’opération remplacent les en-têtes de même nom définis au niveau du client.

  ```java showLineNumbers
  Map<String, String> userHeaders = new HashMap<>();
  userHeaders.put("X-User-Header1", "value1");
  userHeaders.put("X-User-Header2", "value2");

  Client client = new Client.Builder()
          .addEndpoint("https://clickhouse-cloud-instance:8443/")
          .setUsername(user)
          .setPassword(password)
          .httpHeader("X-ClickHouse-Quota", "test")
          .httpHeader("X-Forwarded-For", Arrays.asList("1.2.3.4", "5.6.7.8"))
          .httpHeaders(userHeaders)
          .build();
  ```

  **Important** : Lorsque les options sont définies via `setOption` (sur `Client.Builder` ou une classe de paramètres d’opération), préfixez le nom de l’en-tête par `http_header_`. `ClientConfigProperties.httpHeader(String)` construit cette clé.
  Le nom de l’en-tête étant une simple clé de type String, il doit être entièrement en minuscules ou en majuscules ; sinon, des valeurs en double entraîneront un comportement indéfini. `ClientConfigProperties.httpHeader(String)` corrige ce problème.

  ```java showLineNumbers
  clientBuilder.setOption(ClientConfigProperties.httpHeader("X-ClickHouse-Quota"), "test");
  // equivalent to:
  clientBuilder.setOption("http_header_X-CLICKHOUSE-QUOTA", "test");
  ```

  ## Fonctionnalités de ClickHouse Cloud {#clickhouse-cloud-features}

  Fonctionnalités applicables lors de la connexion à [ClickHouse Cloud](https://clickhouse.com/cloud).

  ### Routage tenant compte des réplicas (CLOUD) {#replica-aware-routing}

  ClickHouse Cloud peut rattacher des requêtes HTTP liées à une même réplique. Envoyez l’en-tête `X-ClickHouse-Replica-Tag` afin qu’un proxy Cloud achemine vers une seule réplique toutes les requêtes partageant la même étiquette. Utilisez ce mécanisme pour les objets limités à une session, tels que les tables temporaires, pour la réutilisation du cache local d’une réplique ou pour garantir la cohérence lecture après écriture.
  En savoir plus : https://clickhouse.com/docs/products/cloud/features/infrastructure/replica-aware-routing.

  **À définir :** l’en-tête HTTP `X-ClickHouse-Replica-Tag` (`com.clickhouse.client.api.http.ClickHouseHttpProto.HEADER_REPLICA_TAG`). Utilisez la même valeur d’étiquette pour toutes les requêtes qui doivent être acheminées vers une même réplique.

  ```java showLineNumbers
  String replicaTag = "my-app-session-1";

  try (Client client = new Client.Builder()
          .addEndpoint("https://your-service.clickhouse.cloud:8443")
          .setUsername(user)
          .setPassword(password)
          .httpHeader(ClickHouseHttpProto.HEADER_REPLICA_TAG, replicaTag)
          .build()) {
      client.query("SELECT hostname()").get();
  }
  ```

  Pour une configuration par opération, définissez l’en-tête sur `QuerySettings`, `InsertSettings` ou `CommandSettings` plutôt que sur le constructeur du client.

  ### Authentification JWT (CLOUD) {#jwt-authentication}

  L&#39;[authentification JWT](/fr/concepts/features/security/external-authenticators/jwt) permet d&#39;authentifier les utilisateurs à l&#39;aide de JSON Web Tokens (JWT) dans ClickHouse Cloud. Au lieu de s&#39;appuyer sur des utilisateurs de base de données préexistants, ClickHouse crée dynamiquement des **utilisateurs éphémères** à partir des revendications intégrées à chaque jeton.

  #### Configuration initiale {#initial-configuration}

  Pour configurer l’authentification JWT initiale côté client, utilisez `useBearerTokenAuth(token)` (qui ajoute automatiquement le préfixe `Bearer_` ;
  voir la [documentation de l’interface HTTP](/fr/concepts/features/security/external-authenticators/jwt#http-interface)) lors de la construction de l’instance `Client` :

  ```java showLineNumbers
  import com.clickhouse.client.api.Client;

  public Client createJwtClient(String jwtToken) {
      return new Client.Builder()
              .addEndpoint("https://your-service.clickhouse.cloud:8443")
              .useBearerTokenAuth(jwtToken)
              .build();
  }
  ```

  <Note>
    `useBearerTokenAuth(token)` ajoute automatiquement le préfixe `Bearer ` à la valeur de l’en-tête HTTP `Authorization`.
  </Note>

  #### Mise à jour du jeton en cours d’exécution {#updating-token-at-runtime}

  Comme les jetons JWT ont une courte durée de vie et que les utilisateurs éphémères n’existent que pendant la durée de vie du jeton, il convient de configurer de nouveaux jetons JWT **avant** que le jeton actuel n’expire afin d’éviter tout échec d’opération.

  Vous pouvez mettre à jour le jeton Bearer d’une instance `Client` existante pendant l’exécution sans recréer le client :

  ```java showLineNumbers
  import com.clickhouse.client.api.Client;

  public void refreshJwtToken(Client client, String newJwtToken) {
      // Set the new JWT before the current token expires
      client.updateBearerToken(newJwtToken);
  }
  ```

  Toutes les requêtes ultérieures effectuées via l’instance `Client` utiliseront le jeton JWT mis à jour.

  ## API d&#39;insertion {#insert-api}

  ### insert(String tableName, InputStream data, ClickHouseFormat format) {#insertstring-tablename-inputstream-data-clickhouseformat-format}

  Accepte des données sous forme d&#39;`InputStream` d&#39;octets dans le format spécifié. `data` doit être encodé dans le `format`.

  **Signatures**

  ```java
  CompletableFuture<InsertResponse> insert(String tableName, InputStream data, ClickHouseFormat format, InsertSettings settings)
  CompletableFuture<InsertResponse> insert(String tableName, InputStream data, ClickHouseFormat format)
  ```

  **Paramètres**

  `tableName` - un nom de table cible.

  `data` - un flux d&#39;entrée de données encodées.

  `format` - le format dans lequel les données sont encodées.

  `settings` - paramètres de la requête.

  **Valeur de retour**

  Future du type `InsertResponse` — résultat de l&#39;opération et informations supplémentaires telles que les métriques côté serveur.

  **Exemples**

  ```java showLineNumbers
  try (InputStream dataStream = getDataStream()) {
      try (InsertResponse response = client.insert(TABLE_NAME, dataStream, ClickHouseFormat.JSONEachRow,
              insertSettings).get(3, TimeUnit.SECONDS)) {

          log.info("Insert finished: {} rows written", response.getMetrics().getMetric(ServerMetrics.NUM_ROWS_WRITTEN).getLong());
      } catch (Exception e) {
          log.error("Failed to write JSONEachRow data", e);
          throw new RuntimeException(e);
      }
  }

  ```

  ### insert(String tableName, List&lt;?&gt; data, InsertSettings settings) {#insertstring-tablename-listlt-data-insertsettings-settings}

  Envoie une requête d&#39;écriture à la base de données. La liste d&#39;objets est convertie dans un format efficace, puis envoyée au serveur. La classe des éléments de la liste doit être enregistrée au préalable à l&#39;aide de la méthode `register(Class, TableSchema)`.

  **Signatures**

  ```java
  client.insert(String tableName, List<?> data, InsertSettings settings)
  client.insert(String tableName, List<?> data)
  ```

  **Paramètres**

  `tableName` - nom de la table cible.

  `data` - objets DTO (Data Transfer Object) de la collection.

  `settings` - paramètres de la requête.

  **Valeur de retour**

  Future du type `InsertResponse` — le résultat de l&#39;opération et des informations supplémentaires telles que les métriques côté serveur.

  **Exemples**

  ```java showLineNumbers
  // Important step (done once) - register class to pre-compile object serializer according to the table schema.
  client.register(ArticleViewEvent.class, client.getTableSchema(TABLE_NAME));

  List<ArticleViewEvent> events = loadBatch();

  try (InsertResponse response = client.insert(TABLE_NAME, events).get()) {
      // handle response, then it will be closed and connection that served request will be released.
  }
  ```

  ### InsertSettings {#insertsettings}

  Options de configuration pour les opérations d&#39;insertion.

  **Méthodes de configuration**

  | Méthode                                         | Description                                                                                                                                                                                      |
  | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | `setQueryId(String queryId)`                    | Définit l’ID de la requête qui sera attribué à l’opération. Par défaut : `null`.                                                                                                                 |
  | `setDeduplicationToken(String token)`           | Définit le jeton de déduplication. Ce jeton est envoyé au serveur et peut être utilisé pour identifier la requête. Par défaut : `null`.                                                          |
  | `setInputStreamCopyBufferSize(int size)`        | Taille du tampon de copie. Le tampon est utilisé lors des opérations d’écriture pour copier les données d’un flux d’entrée fourni par l’utilisateur vers un flux de sortie. Par défaut : `8196`. |
  | `serverSetting(String name, String value)`      | Définit individuellement les paramètres du serveur pour une opération.                                                                                                                           |

  ## API de requête {#query-api}

  **Sélection du format**

  Le Client fournit un accès transparent au flux de réponse du serveur. L’utilisateur peut choisir n’importe quel format ClickHouse dans la requête et lire les données via le flux `InputStream`
  de l’objet `QueryResponse`.
  Le format peut être demandé via :

  * `QuerySettings#setFormat()` définit l’en-tête de format dans une requête.
  * Dans la clause `FORMAT` de la requête elle-même.
  * Paramètre du serveur `default_format` (/reference/settings/session-settings/default#default&#95;format)

  Le comportement varie selon les versions de ClickHouse et de Client :

  * Client &lt; `0.11.0` &amp; ClickHouse &lt; `26.8` - la clause `FORMAT` est prioritaire sur l&#39;en-tête de format de la requête.
  * Client &gt; `0.11.0` &amp; ClickHouse &gt; `26.8` - l&#39;en-tête de la requête est prioritaire sur la clause `FORMAT`.
    * Le client définit l’en-tête lorsqu’aucun format n’est spécifié dans `QuerySettings`, ce qui empêche de surcharger le format dans la requête.
  * Client à partir de la version `0.11.0` : la valeur par défaut de `format` est définie au niveau du client et non plus au niveau de l&#39;opération. Le code existant peut ainsi
    fonctionner sans modification, tandis que le nouveau code peut utiliser la clause `FORMAT` en définissant `format` sur `null` au niveau du client.

  ### query(String sqlQuery) {#querystring-sqlquery}

  Envoie `sqlQuery` tel quel. Le format de réponse est défini par les paramètres de la requête. `QueryResponse` contiendra une référence au flux de réponse qui doit être consommé par un lecteur pour le format pris en charge.

  **Signatures**

  ```java
  CompletableFuture<QueryResponse> query(String sqlQuery, QuerySettings settings)
  CompletableFuture<QueryResponse> query(String sqlQuery)
  ```

  **Paramètres**

  `sqlQuery` - une instruction SQL unique. La requête est envoyée telle quelle au serveur.

  `settings` - paramètres de la requête.

  **Valeur de retour**

  Future du type `QueryResponse` — un jeu de données résultant ainsi que des informations supplémentaires telles que les métriques côté serveur. L&#39;objet Response doit être fermé après consommation du jeu de données.

  **Exemples**

  ```java
  final String sql = "select * from " + TABLE_NAME + " where title <> '' limit 10";

  // Default format is RowBinaryWithNamesAndTypesFormatReader so reader have all information about columns
  try (QueryResponse response = client.query(sql).get(3, TimeUnit.SECONDS);) {

      // Create a reader to access the data in a convenient way
      ClickHouseBinaryFormatReader reader = client.newBinaryFormatReader(response);

      while (reader.hasNext()) {
          reader.next(); // Read the next record from stream and parse it

          // get values
          double id = reader.getDouble("id");
          String title = reader.getString("title");
          String url = reader.getString("url");

          // collecting data
      }
  } catch (Exception e) {
      log.error("Failed to read data", e);
  }

  // put business logic outside of the reading block to release http connection asap.
  ```

  ### query(String sqlQuery, Map&lt;String, Object&gt; queryParams, QuerySettings settings) {#querystring-sqlquery-mapltstring-object-queryparams-querysettings-settings}

  Envoie `sqlQuery` tel quel. Envoie également les paramètres de requête afin que le serveur puisse compiler l&#39;expression SQL.

  **Signatures**

  ```java
  CompletableFuture<QueryResponse> query(String sqlQuery, Map<String, Object> queryParams, QuerySettings settings)
  ```

  **Paramètres**

  `sqlQuery` - expression SQL avec des espaces réservés `{}`.

  `queryParams` - map de variables permettant de compléter l&#39;expression SQL sur le serveur.

  `settings` - paramètres de la requête.

  **Valeur de retour**

  Future du type `QueryResponse` — un jeu de données résultant ainsi que des informations supplémentaires telles que les métriques côté serveur. L&#39;objet Response doit être fermé après consommation du jeu de données.

  **Exemples**

  ```java showLineNumbers

  // define parameters. They will be sent to the server along with the request.
  Map<String, Object> queryParams = new HashMap<>();
  queryParams.put("param1", 2);

  try (QueryResponse response =
          client.query("SELECT * FROM " + table + " WHERE col1 >= {param1:UInt32}", queryParams, new QuerySettings()).get()) {

      // Create a reader to access the data in a convenient way
      ClickHouseBinaryFormatReader reader = client.newBinaryFormatReader(response);

      while (reader.hasNext()) {
          reader.next(); // Read the next record from stream and parse it

          // reading data
      }

  } catch (Exception e) {
      log.error("Failed to read data", e);
  }

  ```

  ### queryAll(String sqlQuery) {#queryallstring-sqlquery}

  Interroge des données au format `RowBinaryWithNamesAndTypes`. Renvoie le résultat sous forme de collection. Les performances de lecture sont identiques à celles du lecteur, mais davantage de mémoire est nécessaire pour conserver l&#39;intégralité du jeu de données.

  **Signatures**

  ```java

  ```

  **Paramètres**

  `sqlQuery` - expression SQL pour interroger des données depuis un serveur.

  **Valeur de retour**

  Jeu de données complet représenté par une liste d&#39;objets `GenericRecord` offrant un accès ligne par ligne aux données de résultat.

  **Exemples**

  ```java showLineNumbers
  try {
      log.info("Reading whole table and process record by record");
      final String sql = "select * from " + TABLE_NAME + " where title <> ''";

      // Read whole result set and process it record by record
      client.queryAll(sql).forEach(row -> {
          double id = row.getDouble("id");
          String title = row.getString("title");
          String url = row.getString("url");

          log.info("id: {}, title: {}, url: {}", id, title, url);
      });
  } catch (Exception e) {
      log.error("Failed to read data", e);
  }
  ```

  ## Lecture des données {#reading-data}

  Il existe deux façons courantes de lire les données :

  * Méthode `query()` qui renvoie un objet `QueryResponse` de bas niveau contenant un `InputStream` avec les données. Généralement combinée à `ClickHouseBinaryFormatReader` pour les lectures en streaming, elle
    peut aussi être utilisée avec toute autre implémentation personnalisée de lecteur. `QueryResponse` donne également accès aux métadonnées du jeu de résultats et aux métriques.
  * Méthode `queryAll()` avec utilisation de `GenericRecord` pour un accès pratique aux lignes. Dans ce cas, l’intégralité du jeu de résultats est chargée en mémoire.
  * Méthode `queryRecords()` qui renvoie `com.clickhouse.client.api.query.Records` - un itérateur pour les objets `GenericRecord`. Cette méthode repose sur une approche en streaming
    (aucune donnée n’est chargée en mémoire) et utilise `GenericRecord` pour accéder aux données.

  **Note :** l&#39;approche en streaming nécessite une lecture rapide, faute de quoi elle peut provoquer un timeout d&#39;écriture sur le serveur, car les données sont lues directement depuis le flux réseau.

  ### Lecture des tableaux {#reading-arrays}

  **Méthodes de `ClickHouseBinaryFormatReader`**

  * `getList(...)` - lit n’importe quel `Array(...)` comme `List<T>`. Bon choix par défaut pour une lecture typée flexible. Prend en charge les tableaux imbriqués.
  * `getByteArray(...)`, `getShortArray(...)`, `getIntArray(...)`, `getLongArray(...)`, `getFloatArray(...)`, `getDoubleArray(...)`, `getBooleanArray(...)` - idéal pour les tableaux 1D de valeurs compatibles avec les types primitifs.
  * `getStringArray(...)` - pour `Array(String)` (et les valeurs d’enum représentées par leur nom).
  * `getObjectArray(...)` - option générique pour tout type d’élément de `Array(...)`, y compris les tableaux imbriqués. À utiliser pour lire des tableaux contenant des valeurs `Nullable` et des tableaux imbriqués.

  Des surcharges par index et par nom sont disponibles pour toutes les méthodes. L&#39;index est indexé à partir de 1. Les surcharges par index accèdent directement à une colonne.
  Les méthodes par nom nécessitent une recherche via l&#39;index à chaque appel.

  ```java
  try (QueryResponse response = client.query("SELECT * FROM my_table").get()) {
      ClickHouseBinaryFormatReader reader = client.newBinaryFormatReader(response);
      while (reader.next() != null) {

          Object[] uint64 = reader.getObjectArray("uint64_arr"); // Array(UInt64) -> BigInteger[]
          Object[] arr2d = reader.getObjectArray("arr2d");       // Array(Array(Int64)) -> Object[]

          // nested arrays are returned as nested Object[]:
          Object[] firstInner = (Object[]) arr2d[0];
          Long firstValue = (Long) firstInner[0];
      }
  }
  ```

  **Méthodes de `GenericRecord`**

  * `getList(...)` - lit n’importe quel `Array(...)` comme `List<T>`. Bon choix par défaut pour une lecture typée flexible. Prend en charge les tableaux imbriqués.
  * `getByteArray(...)`, `getShortArray(...)`, `getIntArray(...)`, `getLongArray(...)`, `getFloatArray(...)`, `getDoubleArray(...)`, `getBooleanArray(...)` - idéal pour les tableaux 1D de valeurs compatibles avec les types primitifs.
  * `getStringArray(...)` - pour `Array(String)` (et les valeurs d’enum représentées par leur nom).
  * `getObjectArray(...)` - option générique pour tout type d’élément de `Array(...)`, y compris les tableaux imbriqués. À utiliser pour lire des tableaux contenant des valeurs `Nullable` et des tableaux imbriqués.

  Des surcharges par index et par nom sont disponibles pour toutes les méthodes. L&#39;index est indexé à partir de 1. Les surcharges par index accèdent directement à une colonne.
  Les méthodes par nom nécessitent une recherche via l&#39;index à chaque appel.

  ```java
  try (QueryResponse response = client.query("SELECT * FROM my_table").get()) {
      List<GenericRecord> rows = client.queryAll(
          "SELECT int_arr, arr2d_nullable FROM test_arrays ORDER BY id");

      for (GenericRecord row : rows) {
          Object[] intArr = row.getObjectArray("int_arr");                 // Array(Int32) -> Integer[]
          Object[] arr2d = row.getObjectArray("arr2d_nullable");           // Array(Array(Nullable(Int32)))

          Object[] inner = (Object[]) arr2d[0];
          Object maybeNull = inner[1]; // may be null
      }
  }
  ```

  ## Observability &amp; Supervision {#v2-o11y}

  Le Client Java ClickHouse (V2) intègre des fonctionnalités d’observability reposant sur les conventions sémantiques d’OpenTelemetry et les metrics de Micrometer. Le client permet de suivre la durée des opérations, le débit, les réessais, les statistiques d’exécution du serveur, l’état du pool de connexions et les spans de traçage distribué.

  Pour découvrir une application Spring Boot complète conçue sur le modèle d’une application de production et illustrant la configuration de Client V2, la gestion d’un pool de connexions, la propagation du contexte de trace lors du passage aux méthodes `@Async` et l’intégration complète de la télémétrie, consultez le module `examples/demo-spring-service` de ce dépôt.

  ### API d’observability du constructeur de client {#v2-o11y-builder-api}

  Le `Client.Builder` expose trois méthodes principales pour configurer l&#39;observability et la collecte des métriques :

  * `setMetricsRecorder(MetricsRecorder recorder)` : enregistre un enregistreur de métriques chargé d’exporter les métriques opérationnelles (durées, nombres d’occurrences, réessais, erreurs). S’il n’est pas défini explicitement, la valeur par défaut est `DefaultMetricsRecorder.NOOP`.
  * `setSpanRecorder(SpanRecorder recorder)` : enregistre un enregistreur de spans pour le traçage distribué (spans d’opération et spans de requêtes de transport). S’il n’est pas défini explicitement, la valeur par défaut est `DefaultSpanRecorder.NOOP`.
  * `registerClientMetrics(Object registry, String groupName)` : associe les métriques du pool de connexions d’Apache HttpClient (par exemple les connexions disponibles et louées, les requêtes en attente et le temps de création des connexions) à un `MeterRegistry` Micrometer.

  **Dépendances requises**

  Les classes intégrées `OpenTelemetrySpanRecorder` et `MicrometerMetricsRecorder` sont fournies dans le paquet `client-v2`. Toutefois, elles nécessitent la présence des bibliothèques OpenTelemetry API (`io.opentelemetry:opentelemetry-api`) et Micrometer (`io.micrometer:micrometer-core`) dans le classpath de l&#39;application à l&#39;exécution. L&#39;artefact principal du client n&#39;embarque pas ces dépendances tierces et ne les récupère pas non plus de manière transitive. Les applications utilisant le traçage OpenTelemetry ou les métriques Micrometer doivent déclarer explicitement ces dépendances dans la configuration de build de leur projet (`pom.xml` ou `build.gradle`).

  **Exemple de configuration du builder**

  ```java
  import com.clickhouse.client.api.Client;
  import com.clickhouse.client.api.observability.micrometer.MicrometerMetricsRecorder;
  import com.clickhouse.client.api.observability.otel.OpenTelemetrySpanRecorder;

  import io.micrometer.core.instrument.MeterRegistry;
  import io.opentelemetry.api.OpenTelemetry;

  public Client createObservedClient(MeterRegistry meterRegistry, OpenTelemetry openTelemetry) {
      return new Client.Builder()
          .addEndpoint("http://localhost:8123")
          .setUsername("default")
          .setPassword("secret")
          .setMetricsRecorder(new MicrometerMetricsRecorder(meterRegistry))
          .setSpanRecorder(new OpenTelemetrySpanRecorder(openTelemetry))
          .registerClientMetrics(meterRegistry, "clickhouse-client-pool")
          .build();
  }
  ```

  **Approches d&#39;intégration**

  Les applications peuvent intégrer l&#39;observability selon deux approches principales :

  1. **Agent OpenTelemetry &amp; autoconfiguration globale** :
     * Pour les applications utilisant l&#39;Agent Java OpenTelemetry ou l&#39;autoconfiguration globale du SDK, instanciez `OpenTelemetrySpanRecorder` et `MicrometerMetricsRecorder` à l&#39;aide de leurs constructeurs par défaut, sans argument.
     * Les constructeurs par défaut se lient automatiquement à `GlobalOpenTelemetry.get()` et au `Metrics.globalRegistry` de Micrometer.
  2. **Intégration explicite client-level** :
     * Transmettez directement aux constructeurs des recorders des instances `OpenTelemetry`, `Tracer` ou Micrometer `MeterRegistry` créées explicitement.
     * Idéal pour gérer plusieurs clients isolés ou des services multi-tenant dotés de destinations de télémétrie indépendantes.

  ```java
  import com.clickhouse.client.api.Client;
  import com.clickhouse.client.api.observability.micrometer.MicrometerMetricsRecorder;
  import com.clickhouse.client.api.observability.otel.OpenTelemetrySpanRecorder;

  public Client.Builder configureGlobalTelemetry(Client.Builder builder) {
      return builder
          .setMetricsRecorder(new MicrometerMetricsRecorder()) // uses Metrics.globalRegistry
          .setSpanRecorder(new OpenTelemetrySpanRecorder());    // uses GlobalOpenTelemetry
  }
  ```

  ### Metrics exposées {#v2-o11y-metrics}

  #### Métriques opérationnelles {#operational-metrics}

  Les métriques exportées via `MetricsRecorder` suivent les conventions sémantiques OpenTelemetry pour les métriques des clients de bases de données (`MetricName` et `MetricAttribute`) :

  | Nom de la métrique                                   | Type / Unité             | Description                                                                                                                               |
  | ---------------------------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
  | `db.client.operation.duration`                       | Timer (`s`)              | Durée d’une opération du client ClickHouse (requêtes et insertions), enregistrée pour les opérations réussies comme pour celles en échec. |
  | `clickhouse.client.operation.serialization.duration` | Timer (`s`)              | Durée de l’étape de sérialisation (par exemple, la sérialisation des POJO lors des insertions).                                           |
  | `clickhouse.client.operation.count`                  | Compteur (`{operation}`) | Nombre total d’opérations du client terminées, regroupées par résultat.                                                                   |
  | `clickhouse.client.operation.retries`                | Compteur (`{retry}`)     | Nombre de nouvelles tentatives effectuées sur l’ensemble des opérations du client.                                                        |

  #### Attributs / étiquettes des métriques {#metric-attributes-tags}

  Les compteurs créés par `MicrometerMetricsRecorder` portent des étiquettes à faible cardinalité (`MetricAttribute`) :

  | Clé d’attribut            | Description                                                                         | Exemples de valeurs                         |
  | ------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------- |
  | `db.system.name`          | Identifiant du système de base de données.                                          | `clickhouse`                                |
  | `db.namespace`            | Nom de la base de données cible.                                                    | `default`, `analytics`                      |
  | `db.operation.name`       | Type d’opération.                                                                   | `query`, `insert`                           |
  | `db.collection.name`      | Nom de la target table (enregistré lors des insertions).                            | `events`                                    |
  | `db.response.status_code` | Code d’erreur du serveur ClickHouse en cas d’échec.                                 | `60`                                        |
  | `error.type`              | Nom de la classe de l&#39;exception en cas d&#39;échec, ou `none` en cas de succès. | `com.clickhouse.client.api.ServerException` |

  #### Métriques du pool de connexions {#connection-pool-metrics}

  Lors de l’appel à `registerClientMetrics(meterRegistry, "groupName")`, les jauges du pool de connexions HTTP sont enregistrées auprès de Micrometer :

  * `httpcomponents.httpclient.pool.total.max` : nombre maximal configuré de connexions persistantes autorisées.
  * `httpcomponents.httpclient.pool.total.connections` (étiqueté avec `state="available"` ou `state="leased"`) : connexions actives dans le pool.
  * `httpcomponents.httpclient.pool.total.pending` : nombre de requêtes de connexion en attente d’une connexion libre.
  * `httpcomponents.httpclient.pool.route.max.default` : nombre maximal de connexions par route configuré par défaut.
  * `httpcomponents.httpclient.connect.time` : moyenne glissante du temps d’établissement des connexions.

  #### API des métriques de réponse {#response-metrics-api}

  Outre les enregistreurs de métriques, des statistiques d&#39;exécution détaillées sont accessibles directement sur les objets de réponse (`QueryResponse`, `InsertResponse`) via `OperationMetrics` :

  ```java
  import com.clickhouse.client.api.Client;
  import com.clickhouse.client.api.metrics.ClientMetrics;
  import com.clickhouse.client.api.metrics.OperationMetrics;
  import com.clickhouse.client.api.metrics.ServerMetrics;
  import com.clickhouse.client.api.query.QueryResponse;

  public void inspectResponseMetrics(Client client) throws Exception {
      try (QueryResponse response = client.query("SELECT * FROM my_table").get()) {
          OperationMetrics metrics = response.getMetrics();
          long readRows = metrics.getMetric(ServerMetrics.NUM_ROWS_READ).getLong();
          long readBytes = metrics.getMetric(ServerMetrics.NUM_BYTES_READ).getLong();
          long durationMs = metrics.getMetric(ClientMetrics.OP_DURATION).getLong();
      }
  }
  ```

  ### Spans remontés {#v2-o11y-spans}

  Le traçage dans Client V2 produit deux types de spans organisés selon une hiérarchie parent-enfant :

  1. **Span d’opération** : représente une opération client de haut niveau (`QUERY <database>` ou `INSERT <database>.<table_name>`). Il est démarré dans le contexte de trace du fil d’exécution courant (`Context.current()`), de sorte que les opérations de base de données s’intègrent au span de trace actif de l’appelant.
  2. **Span de requête de transport** : représente une tentative individuelle de requête de transport HTTP (`POST`). Il est créé en tant qu’enfant du span d’opération correspondant. Chaque nouvelle tentative crée un nouveau span de requête de transport sous le span d’opération.

  #### Attributs de span {#v2-o11y-span-attributes}

  Les spans sont renseignés avec des attributs OpenTelemetry standard (`SpanAttribute`) :

  | Clé d’attribut de span              | Portée / Type                   | Moment de l’enregistrement                                       | Description                                                                                                                                             |
  | ----------------------------------- | ------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `db.system.name`                    | Toutes les opérations           | Avant le début de la requête                                     | Toujours `clickhouse`.                                                                                                                                  |
  | `db.namespace`                      | Toutes les opérations           | Avant le début de la requête                                     | Nom de la base de données cible.                                                                                                                        |
  | `db.query.text`                     | Requête                         | Avant le début de la requête                                     | Texte de l’instruction SQL pour les requêtes ou les commandes.                                                                                          |
  | `db.collection.name`                | Insertion                       | Avant le début de la requête                                     | Nom de la target table.                                                                                                                                 |
  | `db.operation.name`                 | Insertion                       | Avant le début de la requête                                     | Type d’opération (`INSERT`). Renseigné pour les opérations d’insertion, mais non renseigné pour les requêtes, car le SQL n’est pas analysé côté client. |
  | `db.operation.batch.size`           | Insertion                       | Avant le début de la requête                                     | Nombre d’éléments dans le lot d’insertion.                                                                                                              |
  | `db.query.parameter.<name>`         | Requête                         | Avant le début de la requête                                     | Valeurs des paramètres du statement.                                                                                                                    |
  | `clickhouse.query_id`               | Toutes les opérations           | Avant le début de la requête, mis à jour à la fin de l’exécution | Identifiant de requête ClickHouse attribué par le client ou le serveur.                                                                                 |
  | `db.response.returned_rows`         | Requête                         | À la fin de l’exécution, en cas de succès                        | Nombre de lignes renvoyées par le serveur.                                                                                                              |
  | `clickhouse.response.read_rows`     | Requête                         | À la fin de l’exécution, en cas de succès                        | Lignes lues par le serveur depuis le stockage.                                                                                                          |
  | `clickhouse.response.read_bytes`    | Requête                         | À la fin de l’exécution, en cas de succès                        | Octets lus par le serveur depuis le stockage.                                                                                                           |
  | `clickhouse.response.written_rows`  | Insertion                       | À la fin de l’opération, en cas de succès                        | Lignes écrites par le serveur dans le stockage.                                                                                                         |
  | `clickhouse.response.written_bytes` | Insertion                       | À la fin de l’opération, en cas de succès                        | Octets écrits par le serveur dans le stockage.                                                                                                          |
  | `server.address`                    | Requête de transport            | Avant la tentative                                               | Nom d’hôte ou adresse IP du serveur cible.                                                                                                              |
  | `server.port`                       | Requête de transport            | Avant la tentative                                               | Port du serveur cible.                                                                                                                                  |
  | `http.request.method`               | Requête de transport            | Avant la tentative                                               | Méthode HTTP (toujours `POST`).                                                                                                                         |
  | `http.response.status_code`         | Requête de transport            | À la réception d’une réponse / en cas d’échec                    | Code d’état HTTP renvoyé par le serveur (par exemple `200`, `500`).                                                                                     |
  | `db.response.status_code`           | Tous &amp; Requête de transport | En cas d’échec                                                   | Code d’erreur du serveur ClickHouse en cas d’échec.                                                                                                     |
  | `error.type`                        | Tous &amp; Requête de transport | En cas d’échec                                                   | Nom de la classe d’exception en cas d’erreur.                                                                                                           |

  <Note>
    **Propagation du contexte lors des transitions asynchrones :** Comme Client V2 hérite de `Context.current()`, les opérations lancées sur des fils d’exécution où un span de trace est actif sont automatiquement rattachées à la trace. Lorsque vous déléguez des tâches entre pools de threads (par exemple, avec `@Async` de Spring ou un `ExecutorService` personnalisé), propagez explicitement le contexte OpenTelemetry :

    ```java
    import io.opentelemetry.context.Context;
    import io.opentelemetry.context.Scope;
    import com.clickhouse.client.api.Client;
    import com.clickhouse.client.api.insert.InsertResponse;

    public void processBatchAsync(Client client, String table, List<?> data, Context parentContext) throws Exception {
        try (Scope ignored = parentContext.makeCurrent()) {
            try (InsertResponse response = client.insert(table, data).get()) {
                // Background Client V2 span joins parentContext trace
            }
        }
    }
    ```
  </Note>

  ### Développement d’enregistreurs personnalisés {#v2-o11y-custom-recorders}

  Les applications utilisant des backends d’observability personnalisés peuvent implémenter des enregistreurs personnalisés en étendant `DefaultMetricsRecorder` (pour les metrics) ou `DefaultSpanRecorder` (pour le traçage).

  * **`DefaultMetricsRecorder`** : Implémentation de base de `MetricsRecorder`. Redéfinissez certaines fonctions de rappel, comme `recordQuerySuccess` ou `recordQueryFailure`. Utilisez `MetricsSupport.DEFAULT` pour déterminer les noms de métriques standard (`MetricName`), les unités et les maps d’attributs (`MetricAttribute`).
  * **`DefaultSpanRecorder`** : Implémentation de base de `SpanRecorder`. Redéfinissez les fonctions de rappel de création de spans, comme `startQuerySpan`, `startInsertSpan` ou `startRequestSpan`. Utilisez `SpanSupport.DEFAULT` pour déterminer les noms et les attributs standard des spans OpenTelemetry (`SpanAttribute`).

  Pour des implémentations de référence adaptées à la production, consultez les classes client intégrées :

  * `com.clickhouse.client.api.observability.otel.OpenTelemetrySpanRecorder` (intégration du traçage OpenTelemetry)
  * `com.clickhouse.client.api.observability.micrometer.MicrometerMetricsRecorder` (intégration des metrics Micrometer)

  ## Guide de migration {#migration_guide}

  L&#39;ancien client (V1) utilisait `com.clickhouse.client.ClickHouseClient#builder` comme point de départ. Le nouveau client (V2) suit un pattern similaire avec `com.clickhouse.client.api.Client.Builder`. Les principales
  différences sont :

  * aucun service loader n&#39;est utilisé pour charger l&#39;implémentation. Le `com.clickhouse.client.api.Client` sert de classe façade pour toutes sortes d&#39;implémentations à l&#39;avenir.
  * moins de sources de configuration : l&#39;une est fournie au builder et l&#39;autre via les paramètres d&#39;opération (`QuerySettings`, `InsertSettings`). La version précédente avait une configuration par nœud et chargeait
    les variables d&#39;environnement dans certains cas.

  ### Correspondance des paramètres de configuration {#migration_from_v1_config}

  Il existe 3 classes enum liées à la configuration dans V1 :

  * `com.clickhouse.client.config.ClickHouseDefaults` - paramètres de configuration à définir dans la plupart des cas d&#39;utilisation, comme `USER` et `PASSWORD`.
  * `com.clickhouse.client.config.ClickHouseClientOption` - paramètres de configuration spécifiques au client, comme `HEALTH_CHECK_INTERVAL`.
  * `com.clickhouse.client.http.config.ClickHouseHttpOption` - paramètres de configuration spécifiques à l&#39;interface HTTP, comme `RECEIVE_QUERY_PROGRESS`.

  Ils ont été conçus pour regrouper les paramètres et assurer une séparation claire. Cependant, dans certains cas, cela a pu prêter à confusion (y a-t-il une différence entre `com.clickhouse.client.config.ClickHouseDefaults#ASYNC` et
  `com.clickhouse.client.config.ClickHouseClientOption#ASYNC` ?). Le nouveau client V2 utilise `com.clickhouse.client.api.Client.Builder` comme dictionnaire unique de toutes les options de configuration possibles du client. La classe
  `com.clickhouse.client.api.ClientConfigProperties` recense tous les noms de paramètres de configuration.

  ### Différences générales {#general-differences}

  * Client V2 utilise moins de classes propriétaires afin d’améliorer la portabilité. Par exemple, V2 fonctionne avec n’importe quelle implémentation de `java.io.InputStream` pour
    envoyer des données à un serveur.
  * Le paramètre `async` de Client V2 est `off` par défaut. Cela signifie qu’il n’y a pas de thread supplémentaire et que l’application garde davantage de contrôle sur le client. Ce paramètre doit être `off` dans la majorité des cas d’utilisation. L’activation de `async` crée un thread distinct pour chaque requête. Cela n’a de sens que si vous utilisez un
    executor contrôlé par l’application (voir `com.clickhouse.client.api.Client.Builder#setSharedOperationExecutor`)

  ### Écriture des données {#writing-data}

  * utilisez n’importe quelle implémentation de `java.io.InputStream`. La V1 `com.clickhouse.data.ClickHouseInputStream` est prise en charge, mais n’est PAS recommandée.
  * une fois la fin du flux d’entrée détectée, elle est traitée comme telle. Auparavant, il fallait fermer le flux de sortie d’une requête.

  **V1 Insérer des données au format TSV.**

  ```java
  InputStream inData = getInData();
  ```

  ### Paramètres nommés {#v1-named-parameters}

  Vous pouvez passer des paramètres par nom plutôt que de vous fier uniquement à leur position dans la liste de paramètres. Cette fonctionnalité est disponible via la fonction `params`.

  ```java showLineNumbers
  try (ClickHouseClient client = ClickHouseClient.newInstance(ClickHouseProtocol.HTTP);
       ClickHouseResponse response = client.read(servers)
          .format(ClickHouseFormat.RowBinaryWithNamesAndTypes)
          .query("select * from my_table where name=:name limit :limit")
          .params("Ben", 1000)
          .executeAndWait()) {
              //...
          }
  }
  ```

  <Info>
    **Paramètres**

    Toutes les signatures `params` impliquant le type `String` (`String`, `String[]`, `Map<String, String>`) supposent que les clés transmises sont des chaînes SQL ClickHouse valides. Par exemple :

    ```java showLineNumbers
    try (ClickHouseClient client = ClickHouseClient.newInstance(ClickHouseProtocol.HTTP);
         ClickHouseResponse response = client.read(servers)
            .format(ClickHouseFormat.RowBinaryWithNamesAndTypes)
            .query("select * from my_table where name=:name")
            .params(Map.of("name","'Ben'"))
            .executeAndWait()) {
                //...
            }
    }
    ```

    Si vous préférez ne pas convertir manuellement des objets String en SQL ClickHouse, vous pouvez utiliser la fonction utilitaire `ClickHouseValues.convertToSqlExpression` située dans `com.clickhouse.data`:

    ```java showLineNumbers
    try (ClickHouseClient client = ClickHouseClient.newInstance(ClickHouseProtocol.HTTP);
         ClickHouseResponse response = client.read(servers)
            .format(ClickHouseFormat.RowBinaryWithNamesAndTypes)
            .query("select * from my_table where name=:name")
            .params(Map.of("name", ClickHouseValues.convertToSqlExpression("Ben's")))
            .executeAndWait()) {
                //...
            }
    }
    ```

    Dans l’exemple ci-dessus, `ClickHouseValues.convertToSqlExpression` échappera l’apostrophe interne et entourera la variable de guillemets simples valides.

    Les autres types, comme `Integer`, `UUID`, `Array` et `Enum`, seront convertis automatiquement dans `params`.
  </Info>

  ## Découverte des nœuds {#v1-node-discovery}

  Le client Java permet de détecter automatiquement les nœuds ClickHouse. La détection automatique est désactivée par défaut. Pour l&#39;activer manuellement, définissez `auto_discovery` sur `true` :

  ```java
  properties.setProperty("auto_discovery", "true");
  ```

  Ou dans l&#39;URL de connexion :

  ```plaintext
  jdbc:ch://my-server/system?auto_discovery=true
  ```

  Si la découverte automatique est activée, il n&#39;est pas nécessaire de spécifier tous les nœuds ClickHouse dans l&#39;URL de connexion. Les nœuds indiqués dans l&#39;URL seront traités comme des seeds, et le client Java découvrira automatiquement d&#39;autres nœuds à partir des tables système et/ou de ClickHouse Keeper ou ZooKeeper.

  Les options suivantes permettent de configurer la découverte automatique :

  | Propriété                       | Par défaut | Description                                                                                                                  |
  | ------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
  | auto&#95;discovery              | `false`    | Indique si le client doit détecter davantage de nœuds à partir des tables système et/ou de ClickHouse Keeper/ZooKeeper.      |
  | node&#95;discovery&#95;interval | `0`        | Intervalle de détection des nœuds en millisecondes; une valeur nulle ou négative signifie une détection unique.              |
  | node&#95;discovery&#95;limit    | `100`      | Nombre maximal de nœuds pouvant être découverts à la fois ; une valeur nulle ou négative signifie qu’il n’y a pas de limite. |

  ### Équilibrage de charge {#v1-load-balancing}

  Le Java client choisit un nœud ClickHouse auquel envoyer des requêtes, conformément à la politique d&#39;équilibrage de charge. En général, la politique d&#39;équilibrage de charge est responsable des éléments suivants :

  1. Récupérez un nœud dans une liste de nœuds gérés.
  2. Gérer l’état du nœud.
  3. Planifiez éventuellement un processus en arrière-plan pour la découverte de nœuds (si l’auto-découverte est activée) et exécutez un contrôle d’intégrité.

  Voici une liste d&#39;options pour configurer l&#39;équilibrage de charge :

  | Propriété                     | Valeur par défaut                        | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
  | ----------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | load&#95;balancing&#95;policy | `""`                                     | La politique d’équilibrage de charge peut être l’une des suivantes : <li>`firstAlive` - la requête est envoyée au premier nœud sain de la liste des nœuds gérés</li><li>`random` - la requête est envoyée à un nœud choisi aléatoirement dans la liste des nœuds gérés </li><li>`roundRobin` - la requête est envoyée à chaque nœud de la liste des nœuds gérés, à tour de rôle.</li><li>nom de classe pleinement qualifié implémentant `ClickHouseLoadBalancingPolicy` - politique d’équilibrage de charge personnalisée</li>Si elle n’est pas spécifiée, la requête est envoyée au premier nœud de la liste des nœuds gérés |
  | load&#95;balancing&#95;tags   | `""`                                     | Tags d’équilibrage de charge permettant de filtrer les nœuds. Les requêtes sont envoyées uniquement aux nœuds portant les tags spécifiés                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
  | health&#95;check&#95;interval | `0`                                      | Intervalle de vérification de l’état en millisecondes ; une valeur nulle ou négative indique une exécution unique.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
  | health&#95;check&#95;method   | `ClickHouseHealthCheckMethod.SELECT_ONE` | Méthode de vérification de l’état de santé. Peut être l’une des suivantes : <li>`ClickHouseHealthCheckMethod.SELECT_ONE` - vérification via la requête `select 1`</li> <li>`ClickHouseHealthCheckMethod.PING` - vérification spécifique au protocole, généralement plus rapide</li>                                                                                                                                                                                                                                                                                                                                           |
  | node&#95;check&#95;interval   | `0`                                      | Intervalle de vérification des nœuds en millisecondes ; un nombre négatif est traité comme zéro. L’état du nœud est vérifié si le délai spécifié s’est écoulé depuis la dernière vérification.<br />La différence entre `health_check_interval` et `node_check_interval` est que l’option `health_check_interval` planifie la tâche d’arrière-plan qui vérifie l’état de la liste des nœuds (tous ou uniquement les nœuds défaillants), tandis que `node_check_interval` spécifie le délai écoulé depuis la dernière vérification de ce nœud particulier                                                                      |
  | check&#95;all&#95;nodes       | `false`                                  | Indique s’il faut effectuer une vérification d’état sur tous les nœuds ou uniquement sur les nœuds défaillants.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

  ### Basculement et nouvelle tentative {#v1-failover-and-retry}

  Le Java client propose des options de configuration pour paramétrer le comportement de failover et de retry pour les requêtes en échec :

  | Propriété                          | Par défaut | Description                                                                                                                                                                                                                                                                      |
  | ---------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | failover                           | `0`        | Nombre maximal de fois où un basculement peut se produire pour une requête. Zéro ou une valeur négative signifie qu’il n’y a pas de basculement. En cas d’échec, le basculement envoie la requête vers un autre nœud (conformément à la politique d’équilibrage de charge).      |
  | retry                              | `0`        | Nombre maximal de tentatives pour une requête. Zéro ou une valeur négative signifie qu&#39;il n&#39;y a aucune tentative. Une tentative renvoie la requête au même nœud, uniquement si le ClickHouse server renvoie le code d&#39;erreur `NETWORK_ERROR`                         |
  | repeat&#95;on&#95;session&#95;lock | `true`     | Indique s&#39;il faut relancer l&#39;exécution lorsque la session est verrouillée, jusqu&#39;à expiration du délai (selon `session_timeout` ou `connect_timeout`). La requête ayant échoué est relancée si le ClickHouse server renvoie le code d&#39;erreur `SESSION_IS_LOCKED` |

  ### Ajout d&#39;en-têtes HTTP personnalisés {#v1-adding-custom-http-headers}

  Le transport HTTP accepte des en-têtes de requête supplémentaires via la propriété `custom_http_headers` (`ClickHouseHttpOption.CUSTOM_HEADERS`). Chaque en-tête est de la forme `Name=Value`. Séparez les en-têtes par une virgule. Pour inclure une virgule dans une valeur, échappez-la sous la forme `\,`. Un `=` présent dans une valeur est conservé tel quel dans celle-ci.

  **En-tête unique**

  ```java
  options.put("custom_http_headers", "X-ClickHouse-Quota=test");
  // or
  options.put(ClickHouseHttpOption.CUSTOM_HEADERS, "X-ClickHouse-Quota=test");
  ```

  **En-têtes multiples**

  ```java
  options.put("custom_http_headers", "X-ClickHouse-Quota=test, X-ClickHouse-Test=test");
  ```

  Vous pouvez également définir des en-têtes pour une requête :

  ```java
  client.read(server)
          .option(ClickHouseHttpOption.CUSTOM_HEADERS, "X-ClickHouse-Quota=test, X-ClickHouse-Test=test")
          .query("SELECT 1")
          .executeAndWait();
  ```

  ### Routage tenant compte des réplicas (CLOUD) {#v1-replica-aware-routing}

  ClickHouse Cloud peut rattacher des requêtes HTTP liées à une même réplique. Envoyez l&#39;en-tête `X-ClickHouse-Replica-Tag` pour qu&#39;un proxy Cloud achemine vers une seule et même réplique toutes les requêtes partageant la même étiquette. Utilisez ce mécanisme pour les objets limités à une session, comme les tables temporaires, pour la réutilisation du cache local d&#39;une réplique ou pour garantir la cohérence lecture après écriture.
  En savoir plus : https://clickhouse.com/docs/products/cloud/features/infrastructure/replica-aware-routing.

  **Paramètre à définir :** l’en-tête HTTP `X-ClickHouse-Replica-Tag` (`com.clickhouse.client.http.config.ClickHouseHttpOption.HEADER_REPLICA_TAG`) via `custom_http_headers`. Utilisez la même valeur d’étiquette pour toutes les requêtes qui doivent rester sur une même réplique.

  ```java
  String replicaTag = "my-app-session-1";
  options.put("custom_http_headers", "X-ClickHouse-Replica-Tag=" + replicaTag);
  // or
  options.put(ClickHouseHttpOption.CUSTOM_HEADERS,
          ClickHouseHttpOption.HEADER_REPLICA_TAG + "=" + replicaTag);
  ```
