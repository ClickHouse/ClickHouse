Les données opérationnelles stockées dans SQL Server font souvent office de source de vérité pour les commandes, les paiements et les stocks, mais SQL Server n’est pas conçu pour les requêtes analytiques lourdes. Dans ce tutoriel, vous répliquez une table SQL Server dans ClickHouse à l’aide d’un pipeline automatisé : Striim charge les lignes existantes, puis diffuse en continu chaque insertion, mise à jour et suppression dès qu’elle se produit. Vous interrogez ensuite l’ensemble de résultats dans ClickHouse.

Pour un tutoriel complet, consultez [Introducing Automated Pipelines for Effortless Data Replication](https://www.striim.com/blog/automated-pipelines-5-0/).

La capture des données modifiées (CDC, Change Data Capture) pour SQL Server nécessite l’offre **Premium** de Striim for ClickHouse.

## Ce que vous allez mettre en place {#what-you-will-build}

SQL Server (`sales.orders`) &gt; chargement initial avec Striim, puis CDC &gt; ClickHouse (`sales.orders`, `ReplacingMergeTree`)

## Avant de commencer {#before-you-begin}

* Un service Striim for ClickHouse en cours d’exécution avec le forfait Premium (voir [Premiers pas](/fr/integrations/connectors/data-ingestion/etl-tools/striim/get-started)).
* Une instance SQL Server joignable depuis Striim, avec SQL Server Agent en cours d’exécution, ainsi que la permission d’activer la capture des modifications de données. Les étapes ci-dessous s’appliquent aussi bien à SQL Server sur une VM qu’à Amazon RDS for SQL Server.
* Un service ClickHouse, une base de données nommée `sales`, un utilisateur Striim disposant des privilèges requis et un profil de connexion à ClickHouse.

## Étape 1 : Préparer SQL Server {#step-1-prepare-sql-server}

Créez une base de données et une table d’exemple contenant quelques lignes. Ces données d’initialisation sont fournies à titre d’illustration, afin que vous puissiez reproduire l’exemple.

```sql
CREATE DATABASE salesdb;
GO
USE salesdb;
GO
CREATE SCHEMA sales;
GO
CREATE TABLE sales.orders (
  order_id    INT           NOT NULL PRIMARY KEY,
  customer_id INT           NOT NULL,
  status      VARCHAR(20)   NOT NULL,
  total       DECIMAL(10,2) NOT NULL,
  placed_at   DATETIME2     NOT NULL
);
INSERT INTO sales.orders VALUES
  (1, 101, 'NEW',     120.50, SYSDATETIME()),
  (2, 102, 'NEW',      75.00, SYSDATETIME()),
  (3, 103, 'NEW',     310.25, SYSDATETIME());
GO
```

Activez la capture des modifications de données (CDC) sur la base de données et créez un utilisateur pour Striim. Striim active la CDC sur chaque table sélectionnée au démarrage de l&#39;application.

<Tabs>
  <Tab title="SQL Server sur une VM" id="enable-cdc-vm">
    ```sql
    USE salesdb;
    EXEC sys.sp_cdc_enable_db;
    ```
  </Tab>

  <Tab title="Amazon RDS for SQL Server" id="enable-cdc-rds">
    ```sql
    EXEC msdb.dbo.rds_cdc_enable_db 'salesdb';
    ```
  </Tab>
</Tabs>

Créez l&#39;utilisateur Striim dans `salesdb` :

```sql
USE salesdb;
CREATE LOGIN striim WITH PASSWORD = '<strong password>';
CREATE USER striim FOR LOGIN striim;
EXEC sp_addrolemember @rolename = db_owner, @membername = striim;
```

Le mode d’authentification SQL Server doit être activé pour l’utilisateur Striim. La documentation de Striim indique d’attribuer le rôle `db_owner` à l’utilisateur du lecteur. Une fois votre pipeline démarré, vous pouvez vérifier que la CDC est active avec `EXEC sys.sp_cdc_help_change_data_capture`. Consultez [Configuring SQL Server to use MS SQL Reader](https://www.striim.com/docs/striimforclickhouse/en/configuring-sql-server-to-use-ms-sql-reader.html) pour connaître les prérequis applicables aux VM Azure et la configuration des groupes de disponibilité Always On.

## Étape 2 : Créer le pipeline automatisé {#step-2-create-the-automated-pipeline}

1. Dans Striim, sélectionnez **Apps &gt; Create an App**.
2. Recherchez et sélectionnez **SQL Server** comme source. Sélectionnez **ClickHouse** comme cible.
3. Sélectionnez **Get Started** et choisissez le pipeline automatisé (chargement initial puis CDC).
4. Nommez le pipeline, par exemple `SqlServerToClickHouse`, choisissez un namespace, puis sélectionnez **Next**.
5. Saisissez les informations de connexion SQL Server : hôte et port (`<host>:1433`), nom de base de données `salesdb` et utilisateur `striim`. Sélectionnez **Next**. Striim valide la connexion. Si la validation échoue, sélectionnez **Back** et corrigez les paramètres ; la validation doit réussir pour pouvoir continuer.
6. Sélectionnez les schémas à répliquer. Choisissez `sales` ; ne sélectionnez pas les schémas système.
7. Sélectionnez les tables à répliquer dans chaque schéma. Choisissez `orders`.
8. Sélectionnez votre profil de connexion à ClickHouse et définissez **Table Engine** sur **`ReplacingMergeTree`**. Ce moteur est adapté aux sources CDC qui envoient une image complète de la ligne lors d’une mise à jour.
9. Si nécessaire, modifiez la correspondance des tables. Vérifiez que `sales.orders` correspond bien à `sales.orders` dans ClickHouse.
10. Vérifiez les paramètres et sélectionnez **Save &amp; Start**.

![Vérifier la configuration du pipeline automatisé de SQL Server vers ClickHouse](/images/integrations/striim/automated-pipeline-wizard.png)

*Exemple de récapitulatif de l’assistant. Pour ce guide, utilisez `salesdb`, `sales.orders` et `ReplacingMergeTree` comme décrit ci-dessus.*

Striim crée deux applications liées. Il exécute d’abord le chargement initial, le met en veille une fois toutes les lignes copiées, puis démarre automatiquement l’application CDC et affiche le nombre d’événements au fur et à mesure que les modifications sont transmises. Si l’une des phases rencontre un problème, le pipeline s’arrête et propose des correctifs.

![Superviser l’application de capture des modifications de données en cours d’exécution](/images/integrations/striim/pipeline-monitoring.png)

<Warning>
  N’exécutez pas d’instructions DDL sur les tables source pendant le chargement initial, et assurez-vous que SQL Server conserve les données de modification (la rétention par défaut est de trois jours) depuis le début du chargement initial jusqu’à ce que l’application CDC ait rattrapé son retard.
</Warning>

## Étape 3 : Vérifier le chargement initial dans ClickHouse {#step-3-verify-the-initial-load-in-clickhouse}

Striim a créé la table cible avec le moteur `ReplacingMergeTree` et deux colonnes de métadonnées. Examinez-la :

```sql
SHOW CREATE TABLE sales.orders;
```

D&#39;après la correspondance des types de données de Striim, vous devriez obtenir `order_id` et `customer_id` en `Int32`, `status` en `String`, `total` en `Decimal(10, 2)`, `placed_at` en `DateTime64`, ainsi que les colonnes `__STRIIM_VERSION` (`UInt64`) et `__STRIIM_ISDELETED` (`UInt8`), avec `ENGINE = ReplacingMergeTree(__STRIIM_VERSION, __STRIIM_ISDELETED)` et `ORDER BY order_id`.

```sql
SELECT order_id, customer_id, status, total
FROM sales.orders FINAL
WHERE __STRIIM_ISDELETED = 0
ORDER BY order_id;
```

Vous devriez voir les trois lignes chargées depuis SQL Server.

## Étape 4 : diffuser les modifications en continu {#step-4-stream-changes}

Apportez des modifications dans SQL Server :

```sql
USE salesdb;
UPDATE sales.orders SET status = 'SHIPPED' WHERE order_id = 2;
DELETE FROM sales.orders WHERE order_id = 3;
INSERT INTO sales.orders VALUES (4, 104, 'NEW', 42.00, SYSDATETIME());
```

Exécutez à nouveau la même requête dans ClickHouse. Les commandes 1, 2 et 4 doivent être présentes, la commande 2 doit afficher `SHIPPED` et la commande 3 ne doit plus apparaître. La suppression est stockée sous forme de ligne de suppression logique. La requête utilise `FINAL` pour sélectionner la dernière version et `__STRIIM_ISDELETED = 0` pour exclure les lignes supprimées. Les marqueurs de suppression sont conservés par défaut ; les fusions en arrière-plan ne suffisent pas à elles seules à garantir leur suppression physique. Consultez [`ReplacingMergeTree`](/fr/reference/engines/table-engines/mergetree-family/replacingmergetree#is_deleted) pour en savoir plus sur le comportement de nettoyage. Vous pouvez également suivre le nombre d’événements et la fraîcheur des données dans la cible depuis la vue de supervision de Striim, ou demander à Clara le retard actuel.

## Créer le même pipeline avec Striim Clara {#build-the-same-pipeline-with-striim-clara}

Plutôt que de passer par l&#39;assistant, vous pouvez décrire le pipeline depuis la page d&#39;accueil, par exemple : « Crée un pipeline de SQL Server vers ClickHouse avec chargement initial et capture des modifications de données pour la table sales.orders. » Clara vous demande alors les informations de connexion, génère un plan TQL et ne lance le déploiement qu&#39;une fois que vous avez cliqué sur **Accept TQL**.

## Nettoyage {#clean-up}

* Arrêtez les deux applications Striim et annulez leur déploiement depuis la page Apps.
* Avec les paramètres par défaut du lecteur, SQL Server continue de capturer les modifications de données même après l&#39;annulation du déploiement des applications Striim. Pour arrêter la capture des données de cet exemple, exécutez `sys.sp_cdc_disable_table` pour `sales.orders`, ou `sys.sp_cdc_disable_db` si aucune autre table de la base de données ne nécessite la CDC. Pour plus de détails, consultez la [documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sys-sp-cdc-disable-table-transact-sql) de SQL Server. Vous pouvez également suivre la [procédure Auto Disable Table CDC](https://www.striim.com/docs/striimforclickhouse/en/sql-server-operational-considerations.html) de Striim.
* Supprimez les tables d&#39;exemple dans les deux systèmes : `DROP TABLE sales.orders;`.
