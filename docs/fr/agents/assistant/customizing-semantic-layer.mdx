L’agent conversationnel de l’Assistant peut être personnalisé afin de comprendre votre logique métier, vos structures de données et les connaissances propres à votre domaine grâce à **AGENTS.md** — une requête enregistrée spéciale qui agit comme une couche sémantique au-dessus de l’instruction système de l’agent.

En créant un fichier AGENTS.md, vous pouvez fournir des instructions personnalisées, insérées en début de chaque conversation, pour orienter la génération de requêtes SQL et l’analyse des données selon les exigences, les calculs et les conventions propres à votre organisation.

## Fonctionnement {#how-it-works}

Lorsque vous enregistrez une requête nommée « AGENTS.md » (sensible à la casse) dans la Console Cloud :

1. L’agent conversationnel Assistant charge automatiquement ce fichier à chaque envoi de message
2. Le contenu est encapsulé dans une balise de contenu structuré, puis injecté dans l’instruction système de l’agent
3. Les instructions s’appliquent à toutes les conversations avec l’Assistant dans ce service

## Création du fichier AGENTS.md {#creating-agents-md}

<Steps>
  <Step title="Créer la requête enregistrée" id="create-query">
    1. Dans la Console Cloud, créez une nouvelle requête
    2. Nommez-la exactement **« AGENTS.md »** (sensible à la casse)
    3. Rédigez vos instructions personnalisées dans l’éditeur de texte de la requête (il ne s’agit pas de véritable SQL)
    4. Enregistrez la requête
  </Step>

  <Step title="Ajouter vos instructions" id="add-instructions">
    Rédigez vos instructions dans un langage clair et directement exploitable. Indiquez notamment :

    * Les règles métier et les calculs
    * Des indications sur la structure des données
    * La terminologie propre au domaine
    * Les modèles de requêtes courants
    * Les règles d’optimisation des performances
  </Step>
</Steps>

## Bonnes pratiques {#best-practices}

### Considérer le contexte comme une ressource limitée {#finite-resource}

Le contexte est précieux : chaque jeton entame le « budget d’attention » de l’agent. À l’instar des humains, dont la mémoire de travail est limitée, les modèles de langage voient leurs performances se dégrader à mesure que le contexte s’allonge. L’enjeu consiste donc à trouver le **plus petit ensemble possible de jetons à forte valeur informative** qui maximise la probabilité d’obtenir le résultat souhaité.

### Trouver le bon niveau d&#39;abstraction {#right-altitude}

Trouvez le juste équilibre entre deux extrêmes :

* **Trop spécifique** : coder en dur une logique if-else rigide, source de fragilité et de complexité de maintenance
* **Trop vague** : des directives générales qui ne fournissent pas de signaux concrets ou présupposent à tort un contexte partagé

Le niveau optimal est suffisamment précis pour orienter efficacement le comportement, tout en restant assez souple pour permettre au modèle d&#39;appliquer des heuristiques solides. Commencez par un prompt minimal avec le meilleur modèle disponible, puis ajoutez des instructions claires en fonction des modes de défaillance observés.

### Structurer en sections {#structured-sections}

Utilisez des balises XML ou des titres Markdown pour créer des sections distinctes, faciles à parcourir d&#39;un coup d&#39;œil :

```xml
<background_information>
Context about your data and domain
</background_information>

<calculation_rules>
Specific formulas and business logic
</calculation_rules>

<tool_guidance>
How to use specific ClickHouse features
</tool_guidance>
```

### Fournir des exemples variés et canoniques {#canonical-examples}

Les exemples sont ces « images qui valent mille mots ». Plutôt que d’entasser tous les cas limites dans votre prompt, sélectionnez un ensemble restreint d’exemples variés qui illustrent clairement le comportement attendu.

### Rester minimal tout en étant complet {#minimal-complete}

* N&#39;incluez que les instructions dont l&#39;agent a fréquemment besoin
* Soyez concis : un contexte trop volumineux dégrade les performances, un phénomène appelé « context rot »
* Supprimez les règles obsolètes ou rarement utilisées
* Fournissez suffisamment d&#39;informations pour orienter l&#39;agent vers le comportement souhaité

<Tip>
  Minimal ne veut pas forcément dire court. Il faut suffisamment de détails pour que l&#39;agent adopte le comportement attendu ; évitez simplement toute verbosité superflue.
</Tip>

## Exemple : métriques calculées à partir des données brutes {#example-calculated-metrics}

Guidez l&#39;agent lorsque les métriques nécessitent des calculs spécifiques plutôt qu&#39;un simple accès direct aux colonnes :

```xml
<metric_calculations>
IMPORTANT: "active_sessions" is NOT a column. It must be calculated.

To calculate active sessions:
COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions

This counts unique combinations of session and user identifiers.

When the user asks for "active sessions" or "session count", always use this formula:
SELECT
    date,
    COUNT(DISTINCT session_id || '|' || user_id) AS active_sessions
FROM events
GROUP BY date;

</metric_calculations>
```

## Exemple : règles de logique métier {#example-business-logic}

Définissez des calculs et des catégorisations propres à votre domaine métier :

```xml
<business_rules>
Revenue Calculation:
- Exclude refunded transactions: WHERE transaction_status != 'refunded'
- Apply regional tax rates using CASE expressions
- Use MRR for subscriptions:
  SUM(CASE
    WHEN billing_cycle = 'monthly' THEN amount
    WHEN billing_cycle = 'yearly' THEN amount / 12
    ELSE 0
  END) AS mrr

Traffic Source Classification:
Use CASE expression to categorize:
CASE
  WHEN traffic_source IN ('google', 'bing', 'organic') THEN 'Organic Search'
  WHEN traffic_source IN ('facebook', 'instagram', 'social') THEN 'Social Media'
  WHEN traffic_source = 'direct' THEN 'Direct'
  ELSE 'Other'
END AS source_category

Customer Segmentation:
- Enterprise: annual_contract_value >= 100000
- Mid-Market: annual_contract_value >= 10000 AND annual_contract_value < 100000
- SMB: annual_contract_value < 10000

Always include these categorizations when generating traffic or revenue reports.
</business_rules>
```

## Exemple : particularités de la structure de données {#example-data-quirks}

Documentez les formats de données atypiques ou les choix de schéma hérités :

```xml
<data_structure_notes>
The user_status column uses numeric codes, not strings:
- 1 = 'active'
- 2 = 'inactive'
- 3 = 'suspended'
- 99 = 'deleted'

When filtering or displaying user status, always use:
CASE user_status
  WHEN 1 THEN 'active'
  WHEN 2 THEN 'inactive'
  WHEN 3 THEN 'suspended'
  WHEN 99 THEN 'deleted'
END AS status_label

The product_metadata column contains JSON strings that must be parsed:
SELECT
    product_id,
    JSONExtractString(product_metadata, 'category') AS category,
    JSONExtractInt(product_metadata, 'inventory_count') AS inventory
FROM products;
</data_structure_notes>
```

## Exemple : terminologie métier {#example-terminology}

Associez les termes métier à leur implémentation technique :

```xml
<terminology>
When users refer to "conversions", they mean:
- For e-commerce: transactions WHERE transaction_type = 'purchase'
- For SaaS: subscriptions WHERE subscription_status = 'active' AND first_payment_date IS NOT NULL

"Churn" is calculated as:
COUNT(DISTINCT user_id) WHERE last_active_date < today() - INTERVAL 90 DAY
AND previous_subscription_status = 'active'

"DAU" (Daily Active Users) means:
COUNT(DISTINCT user_id) WHERE activity_date = today()

"Qualified leads" must meet ALL criteria:
- lead_score >= 70
- company_size >= 50
- budget_confirmed = true
- contact_role IN ('Director', 'VP', 'C-Level')
</terminology>
```
