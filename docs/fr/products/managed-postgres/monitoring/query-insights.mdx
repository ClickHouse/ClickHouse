Query Insights recueille la télémétrie de chaque statement de votre
instance [ClickHouse Managed Postgres](/fr/products/managed-postgres/overview) et classe chaque
modèle de requête par impact, afin de vous permettre de passer de &quot;le p99 dérive
à la hausse&quot; à &quot;ce modèle écrit sur disque&quot; sans quitter la Console Cloud.

Les données par statement proviennent de [`pg_stat_ch`](https://github.com/clickhouse/pg_stat_ch),
l’extension Postgres open-source qui transmet en flux des compteurs par statement vers
ClickHouse Cloud. La télémétrie est normalisée dans Postgres avant de quitter
la base de données — les littéraux sont supprimés et remplacés par des espaces réservés, afin que les
valeurs exactes utilisées dans vos requêtes n’entrent jamais dans le flux de télémétrie.

## Ouvrir Query insights {#open}

Ouvrez votre instance ClickHouse Managed Postgres dans la Console Cloud, puis cliquez sur
**Query insights** dans la barre latérale gauche. La page se divise en cinq
zones, dans l&#39;ordre où vous les utiliserez réellement :

* Un **vue d’ensemble** qui affiche sur un seul écran un aperçu de l&#39;état de santé de la base de données.
* Une table **Modèles de requêtes lents** qui classe chaque motif de requête exécuté par votre base de données,
  triée selon le critère qui vous semble pertinent.
* Un panneau **Requêtes récentes** qui répertorie les exécutions individuelles dans l&#39;ordre
  chronologique inverse.
* Un onglet **Waits** qui classe les événements d&#39;attente dans lesquels les sessions actives ont passé
  du temps, avec une table **Requêtes bloquantes** qui indique quelles sessions
  ont bloqué des requêtes en attente de verrous.
* Un **panneau latéral de détails** qui agrège tous les compteurs pour un seul motif.

Utilisez le sélecteur **Time period** en haut pour basculer entre les 15
dernières minutes, la dernière heure, le dernier jour, la dernière semaine ou le dernier mois. La taille des buckets d&#39;agrégation s&#39;ajuste
automatiquement : buckets d&#39;1 minute pour les 15 dernières minutes ou la dernière heure,
de 5 minutes pour le dernier jour, et d&#39;1 heure pour la dernière semaine ou le dernier mois, afin que les
graphiques restent réactifs.

## Vue d’ensemble {#overview}

La vue d’ensemble se présente sous la forme d’une grille 3×3 de neuf panneaux. Les deux premières lignes couvrent
l’activité des requêtes :

| Panneau                          | Ce qu’il affiche                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Requêtes / s**                 | Volume de requêtes ramené à un débit sur la fenêtre sélectionnée.                                                                                      |
| **Latence des requêtes**         | Moyenne, p50, p95 et p99 sur un même graphique, pour voir quand la queue de distribution s’écarte de la médiane.                                       |
| **Répartition des opérations**   | Un diagramme en anneau de la répartition entre `SELECT`, `INSERT`, `UPDATE` et les autres opérations qui composent réellement votre charge de travail. |
| **Lignes renvoyées / affectées** | Nombre total de lignes traitées par la charge de travail sur la fenêtre.                                                                               |
| **Taux de succès du tampon**     | Un diagramme en anneau comparant les blocs partagés trouvés dans le cache aux blocs partagés lus, avec le temps CPU total dans la légende.             |
| **Erreurs**                      | Nombre total d’erreurs, ventilé dans le temps.                                                                                                         |

Un seul écran vous permet de voir si la base de données est saine. Une instance saine
présente un profil familier : un taux de succès du tampon proche de 100 %,
un volume de requêtes qui suit le trafic applicatif, un taux d’erreur stable
ou nul, et des latences par percentile qui restent proches les unes des autres.

### Graphiques des attentes {#wait-charts}

La troisième ligne indique ce sur quoi les sessions actives de l’instance principale étaient en attente,
à partir d’[échantillons prélevés toutes les 30 secondes](#how-waits) :

| Panneau                          | Contenu affiché                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Active sessions by wait type** | Nombre moyen de sessions actives, empilées par type d’attente. **CPU** désigne une session active sans événement d’attente. Survolez une barre pour afficher les événements d’attente correspondant à chaque type. |
| **Lock wait time**               | Délai d’attente de verrou écoulé (p50, p95 et maximum) parmi les sessions bloquées échantillonnées sur chaque intervalle.                                                                                          |
| **Blocked sessions**             | Nombre moyen de sessions bloquées par un verrou.                                                                                                                                                                   |

Si **Blocked sessions** reste au-dessus de zéro pendant que **Lock wait
time** augmente, cela peut signaler une contention de verrou persistante. Cliquez sur
**Active sessions by wait type** pour ouvrir l’onglet [Waits](#waits).

## Modèles de requêtes lents {#slow-patterns}

Lorsque la vue d’ensemble signale un problème, c’est dans ce tableau que
l’analyse commence. Une ligne par modèle de requête normalisé, avec les
littéraux supprimés pour que les exécutions d’un même statement se regroupent
sur une seule et même ligne.

<div className="ch-image-lg">
  <Frame>
    ![Tableau des modèles de requêtes lentes affichant une ligne par requête normalisée, avec les colonnes Database, User, Operation, Calls, Errors, Avg latency, P95, Max latency, Durée totale d’exécution, Rows returned et Cache hit](/images/managed-postgres/monitoring/query-insights-patterns.webp)
  </Frame>
</div>

<div id="sort">
  ### Trier selon ce que vous soupçonnez {#sort}
</div>

Le tableau est trié par défaut par **Durée d’exécution totale** par ordre décroissant — de cette
façon, le pattern en tête est généralement la réponse à « qu’est-ce qui me coûte le
plus ? » Il ne s’agit pas forcément du pattern le plus lent pris individuellement. Une requête exécutée
huit millions de fois par jour en douze millisecondes peut compter davantage que
celle qui ne s’est exécutée qu’une seule fois en trois secondes.

Chaque tri vous donne un angle de vue différent :

* **Durée d’exécution totale** — là où la base de données a passé le plus de temps réel.
* **Temps CPU** — patterns gourmands en calcul.
* **Appels** — patterns très fréquents.
* **Erreurs** — échecs répétés.
* **Latence moy / P50 / P95 / P99 / max** — valeurs aberrantes, par percentile.
* **Lignes renvoyées**, **Blocs lus**, **Blocs en cache**, **Octets WAL** —
  patterns qui ont fait transiter le plus de données via le moteur, le cache ou
  le journal de transactions.

Cliquez sur le bouton **Colonnes** pour afficher ou masquer des colonnes supplémentaires.
Le tableau des patterns expose 19 colonnes au total, y compris la ventilation
par percentile, le taux de réussite du cache et le temps CPU par pattern.

<div id="filters">
  ### Affiner la table {#filters}
</div>

Filtrez la table en fonction de la partie de votre charge de travail que vous
êtes en train d&#39;analyser :

* **Base de données**
* **Utilisateur**
* **Opération** (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, …)
* **Application** — le `application_name` de la chaîne de connexion

« Montre-moi uniquement ce que fait le service orders sur la base de données `sales` »
se traduit par deux menus déroulants. Les valeurs de filtre se renseignent automatiquement à partir de ce que votre
instance a réellement exécuté.

## Requêtes récentes {#recent-queries}

Sous le tableau des motifs, le panneau **Requêtes récentes** liste les
exécutions individuelles dans l’ordre chronologique inverse — une ligne par
statement exécuté, et non une ligne par motif. Utilisez-le lorsque vous
voulez le flux brut d’événements plutôt qu’un agrégat, par exemple pour
vérifier rapidement qu’un correctif a bien été pris en compte ou pour trouver
le moment exact où une erreur s’est produite.

<div className="ch-image-lg">
  <Frame>
    ![Table Requêtes récentes avec des listes déroulantes de filtre Database, User, Operation et Application, et des colonnes pour Time, Operation, Query, Duration, Rows, Database, User et Blks read](/images/managed-postgres/monitoring/query-insights-recent-queries.webp)
  </Frame>
</div>

Les colonnes par défaut sont Time, Operation, Query, Duration, Rows,
Database, User et Blks read. Ouvrez le sélecteur **colonne** pour afficher
Application, Blks hit, CPU user, CPU sys et PID. Le tableau accepte
les mêmes filtres Database, User, Operation et Application que le
tableau des motifs, et peut être trié par Time, Duration, Rows, Blks read et
CPU time.

Cliquez sur n’importe quelle ligne pour ouvrir le même panneau latéral de détails que le tableau des motifs,
ciblé sur le motif de cette exécution précise.

## Waits {#waits}

Ouvrez l&#39;onglet **Waits** ou cliquez sur **Active sessions by wait type** dans les
[graphiques des attentes](#wait-charts) pour afficher le même graphique ainsi qu&#39;un tableau **Wait events
breakdown** qui classe les événements d&#39;attente selon le nombre moyen de sessions actives sur
la période sélectionnée.

<div className="ch-image-lg">
  <Frame>
    ![Tableau Waits affichant les événements d'attente classés selon le nombre moyen de sessions actives, avec les colonnes Wait event, Wait type, Avg active sessions et Share of load](/images/managed-postgres/monitoring/query-insights-waits.webp)
  </Frame>
</div>

| Colonne                 | Contenu                                                                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Wait event**          | L&#39;événement d&#39;attente au format `type:event`, par exemple `Lock:relation` ou `IO:WalSync`. **CPU** désigne une session active sans événement d&#39;attente. |
| **Wait type**           | Le type de l&#39;événement d&#39;attente, selon les couleurs utilisées dans **Active sessions by wait type**.                                                       |
| **Avg active sessions** | Le nombre moyen de sessions dans cet événement d&#39;attente sur la période sélectionnée.                                                                           |
| **Share of load**       | La part de cet événement d&#39;attente dans le total des sessions actives moyennes, **CPU** compris.                                                                |

Pour une description de chaque événement, consultez la
[référence des événements d&#39;attente de Postgres](https://www.postgresql.org/docs/current/monitoring-stats.html#WAIT-EVENT-TABLE).

### Requêtes bloquantes {#blocking-queries}

Sous le tableau des événements d’attente, **Requêtes bloquantes** indique quelles requêtes ont attendu
des verrous et quelles sessions les ont bloquées. Une session bloquante
détient soit un verrou incompatible, soit une place plus avancée dans la file d’attente pour l’obtenir.
Chaque ligne associe une requête en attente à son bloqueur direct et peut
regrouper des échantillons provenant de plusieurs sessions. Les paires les plus
fréquemment observées apparaissent en premier.

La collecte est désactivée par défaut. Pour la démarrer, activez le
commutateur **Enable** à côté du titre **Requêtes bloquantes**. Seuls les utilisateurs autorisés à
gérer le service peuvent activer ou désactiver la collecte, et les réplicas de lecture
reprennent le paramètre de l’instance principale. L’échantillonnage démarre généralement en une minute environ.

<div className="ch-image-lg">
  <Frame>
    ![Section Requêtes bloquantes avec la collecte désactivée : le commutateur Enable à côté du titre est désactivé et un message indique que la collecte des requêtes bloquantes est désactivée](/images/managed-postgres/monitoring/query-insights-blocking-queries-off.webp)
  </Frame>
</div>

Lorsque la collecte est activée, le tableau affiche les requêtes bloquantes observées pendant la
période sélectionnée. Pour arrêter la collecte, désactivez le commutateur **Enable**.

<div className="ch-image-lg">
  <Frame>
    ![Section Requêtes bloquantes avec la collecte activée : le commutateur Enable est activé, au-dessus des filtres de base de données, d’utilisateur et d’application et d’un tableau comportant les colonnes Waiting query, Blocked by, Blocker application, Blocker state, Lock, Sessions, Longest wait et Last seen, montrant des attentes de verrous de ligne et de table derrière des bloqueurs active et idle in transaction](/images/managed-postgres/monitoring/query-insights-blocking-queries.webp)
  </Frame>
</div>

| Colonne                 | Contenu                                                                                                                                                                                        |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Waiting query**       | Le texte normalisé de la requête qui a attendu le verrou.                                                                                                                                      |
| **Blocked by**          | Le texte normalisé du statement en cours ou le plus récent du bloqueur.                                                                                                                        |
| **Blocker application** | L’`application_name` des sessions bloquantes.                                                                                                                                                  |
| **Blocker state**       | L’état du bloqueur lors du dernier échantillon, par exemple `active` ou `idle in transaction`. **waiting** signifie que le bloqueur attendait lui-même un verrou dans au moins un échantillon. |
| **Lock**                | Le type de verrou, par exemple **Row** ou **Table**, et le mode de verrou demandé par la requête en attente, lors du dernier échantillon.                                                      |
| **Sessions**            | Le nombre de sessions distinctes ayant attendu.                                                                                                                                                |
| **Longest wait**        | La plus longue durée d’attente relevée pour une session en attente au moment de l’échantillonnage.                                                                                             |
| **Last seen**           | L’heure de l’échantillon le plus récent ayant observé cette paire.                                                                                                                             |

Ouvrez le sélecteur **Colonnes** pour afficher les utilisateurs, applications et PID des
sessions en attente, ainsi que les utilisateurs et PID des sessions bloquantes. Filtrez le
tableau par base de données, utilisateur ou application des sessions en attente.

Un bloqueur à l’état `idle in transaction` est souvent le premier à traiter : il
a ouvert une transaction, pris des verrous, et ne l’a ni validée ni annulée.
Son texte **Blocked by** correspond à son statement le plus récent, qui n’est pas forcément
celui qui a pris le verrou.

**No query text** signifie que Query Insights ne dispose d’aucun texte pour ce statement.
C’est le cas lorsque le dernier statement de la session bloquante était une commande
utilitaire telle que `LOCK TABLE`, lorsqu’une requête attend un verrou de table
avant que Postgres ne lui ait assigné un identifiant de requête, ou lorsque Query Insights
n’a enregistré aucune exécution complète du statement. Query Insights masque également
le texte des statements provenant des sessions que le service utilise en interne,
par exemple pour la supervision et la réplication. La ligne affiche tout de même
l’application, l’état et le verrou. **Prepared transaction** dans **Blocked
by** signifie qu’une transaction préparée détient le verrou ; il n’y a donc aucune
session bloquante à décrire.

## Panneau latéral de détails {#detail}

Cliquez sur n’importe quelle ligne du tableau des motifs ou des requêtes récentes pour ouvrir à droite le panneau latéral de détails **Détail de la
requête**. Ce panneau latéral de détails regroupe toutes les exécutions
de ce motif sur l’intervalle de temps sélectionné et agrège les
compteurs qui expliquent pourquoi il est lent.

Le panneau latéral de détails se présente sous la forme d’une vue unique à défilement comportant cinq sections :

* **Motif de requête** — le SQL normalisé avec les littéraux remplacés par `$1`,
  `$2`, … et un bouton pour copier dans le presse-papiers.
* **Utilisation agrégée des ressources** — une grille de 13 cartes de statistiques couvrant le nombre total
  d’appels, la latence moy/P95/P99/max, la durée totale d’exécution, les lignes renvoyées, le taux de succès du cache,
  les blocs lus, les blocs trouvés dans le cache, le temps CPU, les octets WAL et les erreurs.
* **Contexte de la requête** — la base de données, l’utilisateur, l’opération et l’application
  dont provient ce motif.
* **Exécutions notables** — les erreurs, les exécutions inhabituellement lentes et
  celles qui renvoient de gros volumes de résultats, affichées avant la liste complète des exécutions récentes.
* **Exécutions récentes** — les exécutions individuelles du même motif,
  avec des compteurs par exécution.

<div id="counters">
  ### Compteurs par exécution {#counters}
</div>

Développez une exécution récente pour afficher les compteurs qui
indiquent précisément où le temps a été consacré :

* **Blocs partagés** — lectures et hits toujours affichés ; écritures et
  blocs salis affichés lorsqu&#39;ils sont non nuls.
* **Opérations sur blocs locaux et temporaires** — des opérations sur
  blocs temporaires non nulles signifient qu&#39;un tri ou un hachage a
  débordé sur disque.
* **Temps de lecture / écriture** — temps d&#39;E/S, distinct du temps CPU.
* **Temps CPU** — utilisateur et système, séparément.
* **Workers parallèles** — prévus vs. réellement lancés.
* **JIT** — temps total de compilation JIT et nombre de fonctions.
* **WAL** — octets et nombre d&#39;enregistrements.

Tout ce dont vous avez besoin pour diagnostiquer un problème de lenteur
se trouve au même endroit, sur un seul écran.

## API Query insights {#api}

La télémétrie par statement est également disponible via
[ClickHouse Cloud OpenAPI](/fr/products/managed-postgres/openapi#query-insights).
La table [Modèles de requêtes lents](#slow-patterns) correspond à l’endpoint
[lister les motifs de requêtes lentes](/fr/products/cloud/api-reference/postgres/slow-query-patterns-get-list),
et le [panneau latéral de détails](#detail) correspond à l’endpoint

[lister les requêtes bloquantes](/fr/products/managed-postgres/openapi#list-blocking-queries).

<div id="how-it-works">
  ## Fonctionnement {#how-it-works}
</div>

<div id="how-normalized">
  ### Normalisée dans Postgres, avant le wire {#how-normalized}
</div>

`pg_stat_ch` intercepte la phase parse-analyze, remplace chaque littéral par un
espace réservé (`$1`, `$2`, …) et met en cache le pattern obtenu dans un
cache LRU propre à chaque backend, indexé par `queryid`. Lorsque l&#39;executor termine
l&#39;instruction, c&#39;est ce pattern mis en cache qui est associé à l&#39;événement. L&#39;instruction
exacte avec ses valeurs ne quitte jamais la base de données.

<div id="how-overhead">
  ### Sans impacter la base de données {#how-overhead}
</div>

Le producteur ajoute environ 3 % de surcharge par instruction. Le chemin de mise en file d’attente
utilise un try-lock non bloquant sur un tampon circulaire en mémoire partagée. En cas de
forte charge, l’extension supprime les événements en incrémentant un compteur plutôt que de
ralentir Postgres.

### Les attentes sont échantillonnées {#how-waits}

Les [graphiques des attentes](#wait-charts) et la table [Waits](#waits) s&#39;appuient sur des échantillons
collectés toutes les 30 secondes sur l&#39;instance principale. Les attentes brèves peuvent survenir
entièrement entre deux échantillons et ne pas apparaître : ces vues sont donc surtout
utiles pour repérer les attentes prolongées et la contention de verrou.

Les [requêtes bloquantes](#blocking-queries) sont elles aussi échantillonnées toutes les 30 secondes,
sur chaque instance où la collecte est activée : un verrou détenu quelques
secondes seulement peut donc ne pas apparaître. Chaque échantillon enregistre les identifiants de requêtes, et non le texte
des requêtes. Le texte affiché dans la table provient des motifs normalisés que Query
Insights collecte déjà : les valeurs littérales n&#39;y apparaissent donc jamais.

<div id="how-raw-events">
  ### Événements bruts, non agrégés {#how-raw-events}
</div>

`pg_stat_ch` émet un événement brut par statement exécuté (principal ou
imbriqué), selon l’échantillonnage appliqué. Les percentiles, classements et
ventilations des requêtes sont calculés dans ClickHouse à partir de ce flux d’événements.

<div id="how-engine">
  ### Le même moteur que celui de nos clients {#how-engine}
</div>

Le backend d’Insights, c’est [ClickHouse Cloud](/fr/products/cloud/getting-started/intro).
La télémétrie par requête d’une instance Postgres très sollicitée représente des millions de lignes
par jour ; la compression colonnaire permet de conserver à faible coût des mois de détails par exécution,
et des agrégations en moins d’une seconde sur des milliards de lignes maintiennent
l’UI réactive lorsque vous explorez les données sur une semaine ou un mois.

<div id="how-open-source">
  ### Open source {#how-open-source}
</div>

`pg_stat_ch` est sous licence Apache 2.0. Utilisez-le avec n’importe quel Postgres et envoyez les données vers n’importe quel
ClickHouse. Le code source et les tickets sont disponibles sur
[github.com/clickhouse/pg&#95;stat&#95;ch](https://github.com/clickhouse/pg_stat_ch).
