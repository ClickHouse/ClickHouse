La connectivité réseau sécurisée au sein de l’organisation permet à un service ClickHouse Cloud d’interroger un autre service de la même organisation et de la même région avec [`remoteSecure()`](/fr/reference/functions/table-functions/remote). Le trafic reste sur le réseau privé de ClickHouse Cloud au lieu de transiter par l’Internet public : cela fonctionne donc même lorsque l’accès au service que vous interrogez est verrouillé par [PrivateLink](/fr/products/cloud/guides/security/connectivity/private-networking/aws-privatelink) ou par une [liste d’accès IP](/fr/products/cloud/guides/security/connectivity/setting-ip-filters).

Utilisez cette fonctionnalité lorsque :

* Vos services sont restreints à PrivateLink ou à une liste d’accès IP stricte, si bien qu’utiliser `remoteSecure()` via l’endpoint public n’est pas envisageable.
* Vos exigences de sécurité interdisent le trafic de service à service sur l’Internet public.
* Vos services ne partagent pas de données via des [entrepôts](/fr/products/cloud/features/infrastructure/warehouses) (séparation calcul-calcul), mais vous devez les interroger conjointement.

<Note>
  Cette fonctionnalité est en aperçu privé, et notre équipe configure chaque connexion pour vous. Pour y participer, contactez l’équipe chargée de votre compte chez ClickHouse ou le [ClickHouse Support](https://clickhouse.com/support/program).
</Note>

## Fonctionnement {#how-it-works}

Ce guide emploie deux termes :

* **Producteur** : le service qui contient la table que vous souhaitez lire.
* **Consommateur** : le service qui exécute `remoteSecure()` pour lire les données du Producteur.

ClickHouse Cloud établit une connexion unidirectionnelle du Consommateur vers le Producteur. Le Consommateur s’authentifie à l’aide d’un certificat géré par ClickHouse Cloud, et le Producteur contrôle, au moyen d’un `GRANT` standard, les tables que le Consommateur peut lire. Aucun mot de passe n’est à créer ni à renouveler.

Une requête doit franchir trois vérifications :

1. **Réseau** : seul un Consommateur disposant d’une connexion peut joindre le Producteur via le réseau privé.
2. **Identité** : le Consommateur s’authentifie à l’aide d’un certificat lié à son nom d’hôte.
3. **Autorisations sur les tables** : le Producteur détermine, au moyen de `GRANT`, les tables que le Consommateur peut lire. Toute requête portant sur un élément non accordé renvoie une erreur d’accès refusé.

## Prérequis {#prerequisites}

* Les deux services appartiennent à la même organisation ClickHouse Cloud, au même fournisseur de services cloud et à la même région. Par exemple, un service situé dans la région AWS `us-east-2` ne peut pas se connecter à un service situé dans la région AWS `us-west-2`. Notre équipe vérifiera l’éligibilité de vos services avant de créer la connexion.
* Aucun des deux services n’est un service réglementé (HIPAA ou PCI).
* Vous disposez de l’identifiant de service et du nom d’hôte des deux services. Ces deux informations figurent sur la page **Paramètres** de chaque service dans la console.
* Vous pouvez exécuter des requêtes SQL en tant qu’administrateur sur les deux services.

<Tip>
  Commencez par des services de test afin d’éviter tout impact sur la production. Le service consommateur fait l’objet d’un redémarrage progressif lors de la création de sa première connexion.
</Tip>

## Configurer une connexion {#setup}

### Envoyez-nous les informations sur vos services {#send-service-details}

Pendant l&#39;aperçu privé, la console ne propose aucune UI pour gérer les connexions. Envoyez à votre contact ClickHouse :

* Les identifiants de service du Producteur et du Consommateur. Précisez lequel est lequel, et indiquez si vous devez exécuter des requêtes dans les deux sens.
* Un créneau pendant lequel un redémarrage progressif du Consommateur est acceptable. Les connexions ultérieures n&#39;entraînent aucun redémarrage.

### ClickHouse crée la connexion {#clickhouse-creates-connection}

Nous vérifions que les deux services sont éligibles et créons la connexion. Nous créons ensuite, sur le Producer, un utilisateur authentifié par certificat nommé `rt_<Consumer service ID>` et vous communiquons son nom exact.

### Accorder au Consumer l&#39;accès aux tables {#grant-access}

Exécutez les requêtes de test ci-dessous, ou accordez le privilège SELECT sur vos propres tables côté Producer.

```sql
CREATE TABLE default.rs_demo_events (id UInt32, val String) ENGINE = MergeTree ORDER BY id;

INSERT INTO default.rs_demo_events VALUES (1, 'hello'), (2, 'from the Producer');

GRANT SELECT ON default.rs_demo_events TO `rt_<Consumer service ID>`;

CREATE TABLE default.rs_demo_no_grant (id UInt32) ENGINE = MergeTree ORDER BY id;
```

### Interroger depuis le Consumer {#query-from-consumer}

Exécutez ce qui suit sur le Consumer. Nous activerons pour vous la fonctionnalité Named Collections, actuellement en aperçu privé. Le SQL ci-dessous crée une [collection nommée](/fr/concepts/features/configuration/server-config/named-collections) qui pointe vers le Producer, puis l’utilise pour exécuter des requêtes. Utilisez le nom d’hôte du Producer indiqué dans la console, c’est-à-dire celui que vous utiliseriez pour vous y connecter directement.

```sql
CREATE NAMED COLLECTION IF NOT EXISTS my_producer AS
    host = '<Producer hostname>',
    port = 9440,
    user = 'rt_<Consumer service ID>',
    database = 'default';

SELECT * FROM remoteSecure(my_producer, table = 'rs_demo_events');

SELECT * FROM remoteSecure(my_producer, table = 'rs_demo_no_grant');
```

Si vous avez exécuté les requêtes de test, vous aurez constaté que la première requête renvoie des résultats, tandis que la seconde échoue avec une erreur d&#39;accès refusé en raison d&#39;autorisations insuffisantes.

## Limitations {#limitations}

### Portée {#scope}

* Les requêtes sont en lecture seule. Un Consumer peut exécuter un `SELECT` via `remoteSecure()`, mais ne peut pas effectuer d&#39;`INSERT` dans le Producer.
* Les deux services doivent appartenir à la même organisation et être hébergés chez le même fournisseur de services cloud, dans la même région. La connectivité interrégionale et inter-organisations est prévue.
* Une connexion ne couvre qu&#39;un seul service. Si vous utilisez des [entrepôts](/fr/products/cloud/features/infrastructure/warehouses), une connexion à un service ne s&#39;étend pas aux autres services qui partagent ses données. Chacun nécessite sa propre connexion.
* Les connexions sont unidirectionnelles. Pour exécuter des requêtes dans les deux sens, il faut deux connexions.
* C&#39;est le Producer qui exécute la lecture, comme c&#39;est actuellement le cas avec la fonction de table [`remoteSecure()`](/fr/reference/functions/table-functions/remote).

### Mise en veille {#idling}

* Un Producer inactif ou arrêté ne sort pas de veille pour traiter une requête `remoteSecure()`. La requête renvoie alors une erreur de connexion refusée. Si des Consumers doivent pouvoir interroger le Producer de manière fiable, désactivez la [mise en veille](/fr/products/cloud/features/autoscaling/idling) sur le Producer : il reste alors actif en permanence et sa capacité de calcul est facturée en continu.
* Les requêtes `remoteSecure()` long-running peuvent échouer si le Consumer se met en veille en cours d&#39;exécution.

### Messages d’erreur {#error-messages}

La plupart des échecs se traduisent par une erreur réseau générique, comme une connexion refusée, une poignée de main rejetée ou un délai d’attente dépassé, plutôt que par un message qui en indique la cause. Consultez le tableau de [dépannage](#troubleshooting) ci-dessous et communiquez-nous le texte de l’erreur afin que nous puissions améliorer ces messages.

### Suppression d&#39;un service {#deleting-a-service}

Une connexion n&#39;empêche la suppression d&#39;aucun des deux services. Pendant l&#39;aperçu privé, prévenez-nous si vous supprimez l&#39;un d&#39;eux afin que nous puissions supprimer la connexion correspondante.

## Dépannage {#troubleshooting}

| Ce que vous constatez                                | Cause probable                                                                                  | Que faire                                                                                                            |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Accès refusé                                         | La table n’a aucun grant pour l’utilisateur du Consumer                                         | Exécutez `GRANT SELECT` sur le Producer, comme indiqué dans [Accorder au Consumer l’accès aux tables](#grant-access) |
| Échec de l’authentification                          | L’utilisateur défini dans votre collection nommée ne correspond pas à celui que nous avons créé | Vérifiez le nom d’utilisateur que nous vous avons communiqué                                                         |
| Connexion refusée                                    | Le Producer est inactif ou arrêté, ou aucune connexion n’est configurée dans ce sens            | Démarrez le Producer. S’il est déjà en cours d’exécution, vérifiez avec nous le sens de la connexion                 |
| La requête se bloque ou expire sans erreur explicite | La connexion n’est peut-être pas encore entièrement configurée                                  | Contactez-nous en indiquant les deux identifiants de service                                                         |

## FAQ {#faq}

<AccordionGroup>
  <Accordion title="Cela entraîne-t-il des coûts supplémentaires ?" id="cost">
    Vous ne payez que la capacité de calcul que vous utilisez, y compris le temps pendant lequel le Producer n’est pas en veille.
  </Accordion>

  <Accordion title="Dois-je gérer des mots de passe ou des certificats ?" id="credentials">
    Non. Le Consumer s’authentifie à l’aide d’un certificat que ClickHouse Cloud gère pour vous.
  </Accordion>

  <Accordion title="Le trafic transite-t-il par l’Internet public ?" id="public-internet">
    Non. Le trafic reste sur le réseau privé de ClickHouse Cloud. C’est pourquoi cela fonctionne même lorsque le Producer n’accepte que le trafic PrivateLink ou que sa liste d’accès IP n’autorise aucune adresse.
  </Accordion>

  <Accordion title="Le Producer peut-il lire les données du Consumer ?" id="reverse-reads">
    Non, sauf si vous demandez une seconde connexion dans ce sens.
  </Accordion>

  <Accordion title="L’activation de cette fonctionnalité entraîne-t-elle le redémarrage de mes services ?" id="restarts">
    La première connexion sur un Consumer déclenche un redémarrage progressif. Le Producer ne redémarre pas, et les connexions ou révocations ultérieures n’entraînent aucun redémarrage.
  </Accordion>

  <Accordion title="Comment supprimer l’accès ?" id="remove-access">
    Pour supprimer l’accès à une table, exécutez `REVOKE` sur le Producer. Pour supprimer la connexion elle-même, adressez-vous à votre interlocuteur ClickHouse pendant l’aperçu privé.
  </Accordion>
</AccordionGroup>
