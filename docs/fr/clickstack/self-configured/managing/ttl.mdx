## Conservation des données avec TTL {#ttl-clickstack}

Le Time-to-Live (TTL) est une fonctionnalité essentielle de Self-managed ClickHouse Observability pour conserver et gérer efficacement les données, d&#39;autant plus que d&#39;immenses volumes de données sont générés en continu. Le TTL permet l&#39;expiration et la suppression automatiques des données les plus anciennes, ce qui garantit une utilisation optimale du stockage et le maintien des performances sans intervention manuelle. Cette capacité est indispensable pour garder une base de données légère, réduire les coûts de stockage et préserver la rapidité et l&#39;efficacité des requêtes en les concentrant sur les données les plus pertinentes et les plus récentes. Elle facilite en outre le respect des politiques de conservation des données en gérant de façon systématique le cycle de vie des données, renforçant ainsi la pérennité et la scalabilité globales de la solution d&#39;observability.

**Par défaut, les données sont conservées pendant 30 jours. Pour modifier cette durée, consultez [« Modification du TTL »](#modifying-ttl).**

Dans ClickHouse, le TTL se contrôle au niveau de la table. Par exemple, le schéma par défaut des logs est présenté ci-dessous ; `${TABLES_TTL}` est remplacé par la durée de rétention configurée (30 jours sauf modification) lorsque le collector crée la table :

Dans ClickHouse, le partitionnement permet de séparer logiquement les données sur disque selon une colonne ou une expression SQL. Grâce à cette séparation logique, chaque partition peut être traitée indépendamment, par exemple supprimée lorsqu&#39;elle expire selon une politique TTL.

Comme le montre l&#39;exemple ci-dessus, le partitionnement est défini sur une table lors de sa création, via la clause `PARTITION BY`. Cette clause peut contenir une expression SQL portant sur une ou plusieurs colonnes, dont le résultat détermine la partition vers laquelle une ligne est envoyée. Les données sont ainsi associées logiquement (via un préfixe de nom de dossier commun) à chaque partition sur le disque, qui peut alors être interrogée isolément. Dans l&#39;exemple ci-dessus, le schéma `otel_logs` par défaut partitionne par jour à l&#39;aide de l&#39;expression `toDate(Timestamp)`. Lors de l&#39;insertion de lignes dans ClickHouse, cette expression est évaluée pour chaque ligne, qui est ensuite acheminée vers la partition correspondante si elle existe (si la ligne est la première de la journée, la partition est créée). Pour plus de détails sur le partitionnement et ses autres usages, consultez [« Partitions de table »](/fr/concepts/core-concepts/partitions).

Le schéma de la table inclut également `TTL toDateTime(Timestamp) + ${TABLES_TTL}` et le paramètre `ttl_only_drop_parts = 1`. La première clause garantit que les données sont supprimées dès qu&#39;elles dépassent le TTL configuré (30 jours par défaut). Le paramètre `ttl_only_drop_parts = 1` impose de ne faire expirer que les parts dont toutes les données ont expiré (au lieu de tenter de supprimer partiellement des lignes). Comme le partitionnement garantit que les données de jours différents ne sont jamais « fusionnées », elles peuvent être supprimées efficacement.

<Warning>
  **`ttl_only_drop_parts`**

  Nous recommandons de toujours utiliser le paramètre [`ttl_only_drop_parts=1`](/fr/reference/settings/merge-tree-settings/other#ttl_only_drop_parts). Lorsque ce paramètre est activé, ClickHouse supprime une part entière dès que toutes ses lignes ont expiré. Supprimer des parts entières plutôt que nettoyer partiellement les lignes soumises au TTL (ce qui passe par des mutations gourmandes en ressources lorsque `ttl_only_drop_parts=0`) permet de réduire `merge_with_ttl_timeout` et de limiter l&#39;impact sur les performances du système. Si les données sont partitionnées selon la même unité que celle de l&#39;expiration TTL, par exemple le jour, les parts ne contiendront naturellement que des données de l&#39;intervalle défini. `ttl_only_drop_parts=1` pourra ainsi être appliqué efficacement.
</Warning>

Par défaut, les données dont le TTL a expiré sont supprimées lorsque ClickHouse [fusionne les parts](/fr/reference/engines/table-engines/mergetree-family/mergetree#mergetree-data-storage). Lorsque ClickHouse détecte que des données ont expiré, il effectue une fusion hors planification.

<Info>
  **Planification du TTL**

  Comme indiqué ci-dessus, les TTL ne sont pas appliqués immédiatement, mais selon une planification. Le paramètre de table MergeTree `merge_with_ttl_timeout` définit le délai minimum, en secondes, avant de relancer une fusion avec suppression par TTL. La valeur par défaut est de 14400 secondes (4 heures). Il ne s&#39;agit toutefois que d&#39;un délai minimum : le déclenchement d&#39;une fusion TTL peut prendre plus de temps. Si la valeur est trop faible, de nombreuses fusions hors planification seront effectuées, ce qui peut consommer beaucoup de ressources. Il est possible de forcer l&#39;expiration TTL à l&#39;aide de la commande `ALTER TABLE my_table MATERIALIZE TTL`.
</Info>

## Modification du TTL {#modifying-ttl}

Pour modifier le TTL, deux options s&#39;offrent à vous :

1. **Modifier les schémas de table (recommandé)**. Cela nécessite de se connecter à l&#39;instance ClickHouse, par exemple à l&#39;aide de [clickhouse-client](/fr/concepts/features/interfaces/client) ou de la [Console SQL Cloud](/fr/products/cloud/features/sql-console-features/sql-console). Nous pouvons ainsi modifier le TTL de la table `otel_logs` à l&#39;aide de l&#39;instruction DDL suivante :

```sql
ALTER TABLE default.otel_logs
MODIFY TTL TimestampTime + toIntervalDay(7);
```

2. **Modifier l&#39;OTel collector**. Le collecteur OpenTelemetry ClickStack crée les tables dans ClickHouse si elles n&#39;existent pas. Cette création est assurée par l&#39;exportateur ClickHouse, qui expose lui-même un paramètre `ttl` permettant de contrôler l&#39;expression TTL par défaut, par exemple :

```yaml
exporters:
 clickhouse:
   endpoint: tcp://localhost:9000?dial_timeout=10s&compress=lz4&async_insert=1
   ttl: 72h
```

### TTL au niveau des colonnes {#column-level-ttl}

Les exemples ci-dessus font expirer les données au niveau de la table. Il est également possible de faire expirer les données au niveau des colonnes. À mesure que les données vieillissent, cela permet de supprimer les colonnes dont l&#39;utilité pour les investigations ne justifie plus le surcoût en ressources lié à leur conservation. Par exemple, nous recommandons de conserver la colonne `Body` au cas où de nouvelles métadonnées dynamiques, non extraites au moment de l’insertion, seraient ajoutées, comme une nouvelle étiquette Kubernetes. Au bout d&#39;une certaine période, par exemple 1 mois, il peut s&#39;avérer que ces métadonnées supplémentaires ne sont pas utiles, ce qui réduit l&#39;intérêt de conserver la colonne `Body`.

L&#39;exemple ci-dessous montre comment supprimer la colonne `Body` au bout de 30 jours.

```sql
CREATE TABLE otel_logs_v2
(
        `Body` String TTL Timestamp + INTERVAL 30 DAY,
        `Timestamp` DateTime,
 ...
)
ENGINE = MergeTree
ORDER BY (ServiceName, Timestamp)
```

<Note>
  Pour définir un TTL au niveau des colonnes, les utilisateurs doivent spécifier leur propre schéma. Ce paramètre ne peut pas être défini dans l&#39;OTel collector.
</Note>
