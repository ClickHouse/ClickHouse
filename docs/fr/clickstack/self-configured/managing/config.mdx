<Note>
  Cette page traite de **Self-managed ClickHouse Observability**. Pour l’expérience entièrement gérée, que nous recommandons, consultez la documentation [ici](/fr/clickstack/observability/managing/config).
</Note>

Ce guide présente les paramètres des sources de données, le collecteur que vous exécutez et la configuration du schéma de base de données pour Self-managed ClickHouse Observability.

## Interface utilisateur {#hyperdx}

### Paramètres de la source de données {#datasource-settings}

L’UI exige que l’utilisateur définisse une source pour chacun des types de données (ou piliers) de l’observability :

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

Ouvrez **Team Settings → Data → Sources** pour configurer une source. Sélectionnez **Configure Optional Fields** pour accéder à des paramètres supplémentaires, comme illustré ci-dessous pour les logs :

<div className="ch-image-md">
  <Frame>
    ![Paramètres de la source de journaux avec Configure Optional Fields mis en évidence](/images/clickstack/source-settings-optional-fields.png)
  </Frame>
</div>

Chaque source nécessite une table et des correspondances de colonnes qui permettent à l’UI d’interroger ses données. Les sources de métriques OTel utilisent une table distincte par type de métrique ; sélectionnez les tables qui contiennent les métriques que vous collectez.

Si vous utilisez le [schéma OpenTelemetry (OTel) par défaut](/fr/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema) fourni avec ClickStack, ces colonnes peuvent être inférées automatiquement pour chacune des sources. Si vous [modifiez le schéma](#clickhouse) ou utilisez un schéma personnalisé, vous devez définir et mettre à jour ces correspondances vous-même.

<Note>
  Le collecteur ClickStack crée ses tables par défaut au moyen de migrations de schéma intégrées. Ces schémas reposent sur l’[exportateur ClickHouse pour l’OTel collector](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter) et sur le [modèle de données OpenTelemetry](https://opentelemetry.io/docs/specs/otel/logs/data-model/).
</Note>

Les tableaux suivants répertorient les paramètres des sources. Les valeurs inférées dépendent des colonnes et des tables présentes dans votre base de données. Les correspondances facultatives activent les fonctionnalités associées, comme la corrélation des traces ; elles ne sont pas nécessaires pour enregistrer une source.

#### Vues matérialisées {#materialized-views-settings}

Des vues matérialisées peuvent être enregistrées pour les sources de données Log et Trace afin que les requêtes d’agrégation éligibles soient traitées à partir de la vue pré-agrégée plutôt que de la table source. Pour savoir comment créer et enregistrer des vues, consultez « [Vues matérialisées](/fr/clickstack/self-configured/managing/materialized-views) ».

Chaque vue enregistrée est configurée à l’aide des paramètres suivants :

| Paramètre                | Description                                                                                                                                                                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Database`               | Base de données ClickHouse contenant la target table de la vue matérialisée.                                                                                                                                                                                                          |
| `Table`                  | Target table de la vue matérialisée, et non la vue elle-même.                                                                                                                                                                                                                         |
| `Timestamp Column`       | La colonne de timestamp de la target table.                                                                                                                                                                                                                                           |
| `Granularity`            | L’intervalle temporel de la colonne de timestamp de la target table, par exemple `1 minute`. Une requête ne peut utiliser la vue que si son propre intervalle temporel est égal ou moins fin que celui-ci.                                                                            |
| `Minimum Date`           | Facultatif. La date et l’heure les plus anciennes pour lesquelles la vue contient des données. Si cette valeur n’est pas renseignée, ClickStack considère que la vue contient des données pour toutes les dates présentes dans la table source.                                       |
| `Dimension Columns`      | Liste, séparée par des virgules, des colonnes qui ne sont pas pré-agrégées par la vue et qui peuvent donc servir au filtrage et au regroupement.                                                                                                                                      |
| `Pre-aggregated Columns` | Les colonnes pré-agrégées par la vue. Chaque entrée associe une fonction d’agrégation (`avg`, `count`, `max`, `min`, `quantile`, `sum` ou `histogram`) et une colonne de la table source à la colonne correspondante de la vue. La colonne source n’est pas obligatoire pour `count`. |

Lorsque vous sélectionnez la target table, l’UI tente d’inférer ces paramètres à partir du schéma de la vue. Vérifiez les valeurs inférées et complétez les champs manquants.

#### Vues matérialisées de métadonnées {#metadata-materialized-views-settings}

Les vues matérialisées de métadonnées sont des vues matérialisées qui accélèrent la découverte des champs pour les filtres et la complétion automatique. Elles peuvent être configurées sur les sources de données de logs et de traces.

| Paramètre          | Description                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------ |
| `Key Rollup Table` | Facultatif et déconseillé. Table d&#39;agrégation des clés présentes dans la table source. |
| `KV Rollup Table`  | Table d&#39;agrégation des paires clé/valeur présentes dans la table source.               |
| `Granularity`      | Intervalle temporel utilisé par les tables d&#39;agrégation, par exemple `15 minute`.      |

#### Highlighted Attributes {#highlighted-attributes}

Les Highlighted Attributes et les Highlighted Trace Attributes peuvent être configurés sur les sources de données de logs et de traces.

* Les Highlighted Attributes sont des colonnes ou des expressions affichées pour chaque log ou span lors de la consultation de ses détails.
* Les Highlighted Trace Attributes sont des colonnes ou des expressions interrogées sur chaque log ou span d&#39;une trace, puis affichées au-dessus de la vue en cascade des traces.

Ces attributs sont définis dans la configuration de la source et peuvent être des expressions SQL quelconques. Si l&#39;expression SQL renvoie une valeur au format URL, l&#39;attribut est affiché sous forme de lien. Les valeurs vides ne sont pas affichées.

Chaque attribut est configuré à l&#39;aide des paramètres suivants :

| Paramètre           | Description                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `SQL Expression`    | La colonne ou l&#39;expression SQL quelconque à interroger. Obligatoire.                                                 |
| `Alias`             | Facultatif. Le libellé affiché pour l&#39;attribut à la place de l&#39;expression SQL.                                   |
| `Lucene Expression` | Facultatif. Une version Lucene de l&#39;expression SQL, utilisée lors d&#39;une recherche sur la valeur de cet attribut. |

### Sources corrélées {#correlated-sources}

Pour activer une corrélation complète entre les sources, vous devez configurer des sources corrélées pour les logs, les traces, les métriques et les sessions. L&#39;UI peut ainsi associer les données liées entre elles et fournir un contexte riche lors de l&#39;affichage des événements.

* `Logs` : peuvent être corrélés avec les traces et les métriques.
* `Traces` : peuvent être corrélées avec les logs, les sessions et les métriques.
* `Metrics` : peuvent être corrélées avec les logs.
* `Sessions` : peuvent être corrélées avec les traces.

La définition de ces corrélations active plusieurs fonctionnalités. Par exemple, l&#39;UI peut afficher les logs pertinents à côté d&#39;une trace et permettre de naviguer entre les sources liées. La corrélation dépend également des correspondances d&#39;ID et d&#39;attributs appropriées : la simple sélection d&#39;une source ne suffit pas à créer ces relations.

## Collecteur OpenTelemetry {#otel-collector}

Pour plus de détails, consultez [« Collecteur OpenTelemetry ClickStack »](/fr/clickstack/self-configured/ingesting-data/collector).

* `CLICKHOUSE_ENDPOINT`
  * **Valeur par défaut :** *None (obligatoire)* pour l’image du collecteur autonome.
  * **Description :** URL de connexion à ClickHouse utilisée par l’exportateur.
  * **Recommandations :**
    * Utilisez un endpoint ClickHouse Cloud sécurisé, par exemple `https://<host>:8443` ou `tcp://<host>:9440?secure=true`
    * Obligatoire pour que le collecteur puisse envoyer des données à ClickHouse

* `CLICKHOUSE_USER`
  * **Valeur par défaut :** `default` dans l’outil de migration ; à définir explicitement pour le collecteur autonome.
  * **Description :** Nom d’utilisateur servant à s’authentifier auprès de l’instance ClickHouse.
  * **Recommandations :**
    * L’utilisateur doit disposer de la permission d’insérer des données de télémétrie et, lorsque la création de schéma ou les migrations sont activées, de créer ou de modifier les objets de base de données requis
    * Il est recommandé de créer un utilisateur dédié à l’ingestion

* `CLICKHOUSE_PASSWORD`
  * **Valeur par défaut :** *None (obligatoire si l’authentification est activée)*
  * **Description :** Mot de passe de l’utilisateur ClickHouse spécifié.
  * **Recommandations :**
    * Obligatoire si un mot de passe est défini pour le compte utilisateur
    * En production, stockez-le de manière sécurisée à l’aide de secrets

* `HYPERDX_LOG_LEVEL`
  * **Valeur par défaut :** Dépend du déploiement ; à définir explicitement, par exemple `info`.
  * **Description :** Niveau de verbosité des logs du collecteur.
  * **Recommandations :**
    * Accepte des valeurs telles que `debug`, `info`, `warn` ou `error`
    * Utilisez `debug` pour le dépannage

* `OTLP_AUTH_TOKEN`
  * **Valeur par défaut :** *None*. Utilisé uniquement pour l’image autonome.
  * **Description :** Définit le jeton requis pour l’ingestion OTLP autonome. Le collecteur actuel accepte sa valeur dans l’en-tête `Authorization`, soit telle quelle, soit précédée du préfixe `Bearer`. Les versions plus anciennes du collecteur peuvent exiger le jeton seul. Ignoré lorsque l’authentification OIDC est configurée.
  * **Recommandations :**
    * Configurez l’authentification avant d’exposer le collecteur. Sans jeton ni configuration OIDC, le récepteur OTLP autonome accepte les requêtes non authentifiées.

* `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE`
  * **Valeur par défaut :** `default` dans l’outil de migration ; à définir explicitement pour le collecteur autonome.
  * **Description :** Base de données ClickHouse dans laquelle le collecteur écrit les données de télémétrie.
  * **Recommandations :**
    * À définir si vous utilisez un nom de base de données personnalisé
    * Assurez-vous que l’utilisateur spécifié a accès à cette base de données

## ClickHouse {#clickhouse}

Pour optimiser efficacement ClickHouse, vous devez maîtriser les concepts clés du stockage, tels que les [parts](/fr/concepts/core-concepts/parts), les [partitions](/fr/concepts/core-concepts/partitions), les [shards et répliques](/fr/guides/oss/deployment-and-scaling/shards), ainsi que la manière dont les [fusions](/fr/concepts/core-concepts/merges) se produisent au moment de l’insertion. Nous vous recommandons de revoir les fondamentaux des [index primaires](/fr/concepts/core-concepts/primary-indexes), des [index secondaires épars](/fr/concepts/features/performance/skip-indexes/skipping-indexes) et des index de saut de données, ainsi que les techniques de [gestion du cycle de vie des données](/fr/guides/use-cases/observability/build-your-own/managing-data), par exemple à l’aide d’une politique de cycle de vie TTL.

Vous pouvez recourir à la [personnalisation du schéma](/fr/guides/use-cases/observability/build-your-own/schema-design) : modifier les types de colonnes, extraire de nouveaux champs (par exemple à partir des logs), appliquer des codecs et des dictionnaires, ou encore accélérer les requêtes à l’aide de projections.

Par ailleurs, les vues matérialisées permettent de [transformer ou filtrer les données pendant l’ingestion](/fr/guides/use-cases/observability/build-your-own/schema-design#materialized-views), à condition que les données soient écrites dans la table source de la vue et que l’application lise les données de la table cible (target table). Les vues matérialisées peuvent également servir à [accélérer nativement les requêtes](/fr/clickstack/self-configured/managing/materialized-views) dans le service.

Pour plus de détails, consultez la documentation ClickHouse sur la conception de schémas, les stratégies d’indexation et les bonnes pratiques de gestion des données, dont la plupart s’appliquent directement aux déploiements autogérés.
