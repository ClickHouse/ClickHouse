Le collecteur fonctionne comme une **passerelle** : un point de terminaison OTLP unique auquel vos applications, SDK et collecteurs agents envoient leurs données. La passerelle regroupe les événements en batch, applique les éventuels traitements que vous avez configurés et les écrit dans ClickHouse via l&#39;[exportateur ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter). Cette architecture permet de garder la logique de collecte hors de votre code applicatif et de faire évoluer l&#39;ingestion indépendamment des charges de travail qui produisent les données. Pour en savoir plus sur les rôles de passerelle et d&#39;agent, consultez [Rôles du collecteur](/fr/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured).

<Info>
  **Collecteur existant**

  Si vous utilisez un collecteur OpenTelemetry existant, nous supposons qu&#39;il est déjà configuré dans un rôle de **passerelle**. Nous déconseillons d&#39;utiliser cette procédure pour reconfigurer des collecteurs dans le rôle d&#39;**agent**.
</Info>

      <Step title="Déployer le collecteur" id="deploy-the-collector">
        Déployez la **distribution ClickStack du collecteur OpenTelemetry**, préconfigurée pour Self-managed ClickHouse Observability. Dans l&#39;exemple ci-dessous, par souci de simplicité, nous exécutons le collecteur en local et générons des données de télémétrie artificielles depuis la même machine.

        <Note>
          En production, le collecteur est généralement déployé dans un cluster Kubernetes ou sur une machine virtuelle accessible par vos SDK OpenTelemetry, vos agents et vos autres collecteurs. Les données de télémétrie de l&#39;ensemble de votre environnement peuvent ainsi être collectées de manière centralisée, puis transmises à ClickStack.
        </Note>

        Choisissez un secret partagé pour authentifier les clients qui envoient des données au collecteur, puis exportez-le avec vos informations de connexion et le mot de passe choisi pour l&#39;utilisateur `hyperdx_ingest` :

        ```shell
        export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
        export CLICKHOUSE_USER=hyperdx_ingest
        export CLICKHOUSE_PASSWORD=ClickH0u3eRocks123!
        export OTLP_AUTH_TOKEN="a-strong-shared-secret"
        ```

        Exécutez le collecteur OTel de ClickStack :

        ```shell
        docker run -d \
          -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
          -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
          -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
          -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
          -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE=otel \
          -p 4317:4317 \
          -p 4318:4318 \
          clickhouse/clickstack-otel-collector:latest
        ```

        Le collecteur expose désormais OTLP gRPC sur le port `4317` et OTLP HTTP sur le port `4318`. Les applications, les SDK et les collecteurs agents doivent envoyer leurs données vers ces ports en incluant `authorization: $OTLP_AUTH_TOKEN` dans les en-têtes de requête.

        <Info>
          **Déploiements en production**

          En production, nous vous recommandons d&#39;activer TLS sur le point de terminaison OTLP. Consultez [Sécuriser le collecteur](/fr/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        </Info>
      </Step>

      <Step title="Vérifiez l’endpoint" id="verify-the-endpoint">
        Générez du trafic synthétique vers le collecteur afin de vérifier que l’ensemble du pipeline fonctionne. Nous utilisons [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen), le générateur d’OpenTelemetry Collector Contrib, qui émet des logs, des traces et des métriques OTLP et propose des options pour faire varier les données selon les services, les niveaux de sévérité, les statuts de span et les types de métriques.

        Exécutez-le à partir de son image Docker (aucune installation nécessaire). Définissez un petit wrapper pour que les commandes ci-dessous restent lisibles ; `--add-host` permet au conteneur de joindre un collecteur à l&#39;écoute sur l&#39;hôte :

        ```shell
        telemetrygen() {
          docker run --rm --add-host=host.docker.internal:host-gateway \
            ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
        }
        export OTEL_ENDPOINT=host.docker.internal:4317
        ```

        Vous pouvez également installer le binaire avec Go et cibler `localhost` à la place :

        ```shell
        go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
        export OTEL_ENDPOINT=localhost:4317
        ```

        <Info>
          **À quoi s&#39;attendre**

          Chaque exécution de `tg` dure environ 20 secondes (valeur définie par `--duration 20s`) et affiche en continu des logs verbeux, ce qui est normal ; chaque exécution se termine d&#39;elle-même au bout de ses 20 secondes. Les logs ci-dessous suffisent pour valider le pipeline ; l&#39;ensemble facultatif, plus complet, ajoute plusieurs exécutions et prend quelques minutes.
        </Info>

        Définissez une petite fonction utilitaire `tg` afin que chaque commande n&#39;indique que les éléments qui changent (service, gravité, statut, attributs) :

        ```shell
        tg() { local signal=$1; shift; telemetrygen "$signal" \
          --otlp-endpoint ${OTEL_ENDPOINT} --otlp-insecure \
          --otlp-header "authorization=\"${OTLP_AUTH_TOKEN}\"" \
          --rate 5 --duration 20s "$@"; }
        ```

        Envoyez des logs reflétant un mélange réaliste de niveaux de gravité sur plusieurs services — majoritairement de niveau informatif, avec un avertissement et une erreur — plutôt qu&#39;un flux uniforme d&#39;erreurs :

        ```shell
        tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
        tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.method="POST"'
        tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
          --otlp-attributes 'deployment.environment="production"' \
          --telemetry-attributes 'http.status_code="500"'
        ```

        Les logs suffisent à eux seuls à confirmer que l&#39;endpoint fonctionne. Pour obtenir un jeu de données de démonstration plus riche, une cartographie des services impliquant plusieurs services et des graphiques couvrant différents types de métriques, développez et exécutez également les commandes ci-dessous. Elles réutilisent le processus auxiliaire `tg` : exécutez-les donc dans le même interpréteur de commandes.

        <Accordion title="Générer des données de télémétrie plus riches (facultatif)">
          Envoyez des traces à plusieurs spans provenant de plusieurs services sains et d&#39;une dépendance défaillante. La cartographie des services présente ainsi une configuration réaliste, majoritairement saine avec un seul service en erreur, tout en alimentant les vues d&#39;erreurs :

          ```shell
          # Healthy services: the bulk of the traffic, all spans Ok
          for svc in frontend checkout cart; do
            tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
              --otlp-attributes 'deployment.environment="production"' \
              --telemetry-attributes "http.route=\"/$svc\""
          done

          # One slow dependency returning errors
          tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
            --otlp-attributes 'deployment.environment="production"' \
            --telemetry-attributes 'http.route="/charge"'
          ```

          Envoyez des métriques des trois types courants, afin que les graphiques comportent un compteur, une jauge et une distribution :

          ```shell
          tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
          tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
          tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
          ```

          Pour encore plus de diversité, ajoutez quelques services supplémentaires ainsi qu&#39;un histogramme exponentiel :

          ```shell
          tg traces  --service catalog   --child-spans 2 --span-duration 60ms  --status-code Ok \
            --otlp-attributes 'deployment.environment="production"' --telemetry-attributes 'http.route="/catalog"'
          tg traces  --service inventory --child-spans 2 --span-duration 220ms --status-code Ok \
            --otlp-attributes 'deployment.environment="staging"'   --telemetry-attributes 'http.route="/inventory"'
          tg metrics --service payment   --metric-type ExponentialHistogram --otlp-metric-name db.query.duration
          ```
        </Accordion>

        Pour la liste complète des options et d&#39;autres variantes, consultez [Données synthétiques avec telemetrygen](/fr/clickstack/observability/example-datasets/telemetrygen#self-managed).
      </Step>

      <Step title="Adaptez la configuration de votre collecteur" id="adapt-collector">
        Étendez votre configuration du collecteur existante pour écrire dans Self-managed ClickHouse Observability via l’[exportateur ClickHouse](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/clickhouseexporter).

        <Info>
          **Exportateur ClickHouse requis**

          Si vous utilisez votre propre distribution, assurez-vous qu’elle inclut l’exportateur ClickHouse. C’est déjà le cas de l’[image contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) amont.
        </Info>

        Vous trouverez ci-dessous un exemple de configuration qui utilise l’exportateur ClickHouse avec les récepteurs, processeurs et pipelines attendus par l’interface utilisateur de ClickStack. Elle reproduit le comportement de la distribution ClickStack, y compris le chemin de routage de la relecture de session (`rrweb`). Remplacez `<clickhouse_cloud_endpoint>` et `<your_password_here>` par les identifiants de l’utilisateur `hyperdx_ingest` créé précédemment :

        ```yaml
        receivers:
          otlp/hyperdx:
            protocols:
              grpc:
                include_metadata: true
                endpoint: "0.0.0.0:4317"
              http:
                cors:
                  allowed_origins: ["*"]
                  allowed_headers: ["*"]
                include_metadata: true
                endpoint: "0.0.0.0:4318"

        processors:
          batch:
          memory_limiter:
            # 80% of maximum memory up to 2G, adjust for low memory environments
            limit_mib: 1500
            # 25% of limit up to 2G, adjust for low memory environments
            spike_limit_mib: 512
            check_interval: 5s

        connectors:
          routing/logs:
            default_pipelines: [logs/out-default]
            error_mode: ignore
            table:
              - context: log
                statement: route() where IsMatch(attributes["rr-web.event"], ".*")
                pipelines: [logs/out-rrweb]

        exporters:
          clickhouse:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s
          clickhouse/rrweb:
            database: otel
            endpoint: <clickhouse_cloud_endpoint>
            username: hyperdx_ingest
            password: <your_password_here>
            ttl: 720h
            logs_table_name: hyperdx_sessions
            timeout: 5s
            retry_on_failure:
              enabled: true
              initial_interval: 5s
              max_interval: 30s
              max_elapsed_time: 300s

        service:
          pipelines:
            traces:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            metrics:
              receivers: [otlp/hyperdx]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/in:
              receivers: [otlp/hyperdx]
              exporters: [routing/logs]
            logs/out-default:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse]
            logs/out-rrweb:
              receivers: [routing/logs]
              processors: [memory_limiter, batch]
              exporters: [clickhouse/rrweb]
        ```

        Quelques points à noter :

        * Le récepteur `otlp/hyperdx` écoute à la fois en gRPC (`4317`) et en HTTP (`4318`) ; les applications et les agents doivent cibler ces ports sur l&#39;hôte de votre collecteur.
        * L&#39;exportateur `clickhouse` écrit les logs, les traces et les métriques dans la base de données `otel`, selon la disposition attendue par l&#39;interface utilisateur de ClickStack. L&#39;exportateur `clickhouse/rrweb` traite les événements de relecture de session acheminés par le connector `routing/logs` vers `otel.hyperdx_sessions`.
        * L&#39;authentification sur les récepteurs OTLP relève de votre configuration existante. Si vous devez exiger un jeton d&#39;ingestion, configurez-la via les [extensions](https://opentelemetry.io/docs/collector/configuration/#extensions) du collecteur (par exemple `bearertokenauth`) ou via un proxy inverse avec terminaison TLS.

        Rechargez votre collecteur avec la nouvelle configuration. Les applications, les SDKS et les collecteurs agents doivent ensuite envoyer leurs données aux endpoints OTLP exposés par votre collecteur, avec l&#39;en-tête d&#39;authentification attendu par votre configuration.

        Pour plus de détails sur la configuration des collecteurs OpenTelemetry avec Self-managed ClickHouse Observability, consultez [Ingestion avec OpenTelemetry](/fr/clickstack/observability/ingesting-data/opentelemetry#self-managed).
      </Step>

## Étapes suivantes : envoyer vos propres données {#next-steps}

La rafale de données synthétiques ci-dessus sert uniquement à vérifier que le pipeline fonctionne. Pour commencer à envoyer de la télémétrie réelle, instrumentez vos propres services avec les [SDK ClickStack](/fr/clickstack/observability/ingesting-data/sdks), qui assurent l&#39;instrumentation pour Node.js, Python, Go, Java et d&#39;autres langages, et exportent en OTLP vers l&#39;endpoint du collecteur que vous venez de vérifier. Pour un exemple complet, consultez le guide [Instrumenter une application](/fr/clickstack/self-configured/managed-onboarding/instrument-application).

Pour collecter des données depuis l&#39;infrastructure plutôt que depuis le code applicatif :

* [Supervision de Kubernetes](/fr/clickstack/self-configured/managed-onboarding/monitoring-kubernetes) : collectez les logs, les métriques d&#39;infrastructure et les événements Kubernetes d&#39;un cluster.
* [Supervision des logs AWS CloudWatch](/fr/clickstack/self-configured/managed-onboarding/monitoring-aws-cloudwatch-logs) : transférez les logs CloudWatch via le récepteur CloudWatch d&#39;OpenTelemetry.
