<Note>
  Cette page concerne **Self-managed ClickHouse Observability**. Pour l’expérience entièrement gérée recommandée, consultez la documentation [ici](/fr/clickstack/observability/overview).
</Note>

Si vous utilisez ClickStack depuis un certain temps, vous avez sans doute constaté que le schéma par défaut convient à la plupart des charges de travail d’observability sans aucune modification. Cette page s’adresse aux situations où cela ne suffit plus : la latence des requêtes commence à grimper, ou vos modes d’accès se sont éloignés de ceux prévus par défaut.

En pratique, quatre optimisations apportent l’essentiel des gains. Elles sont classées à peu près par ordre d’effort croissant. Les deux premières sont des modifications locales via `ALTER TABLE` que vous pouvez déployer de manière incrémentielle. La troisième est intéressante lorsque la même agrégation est exécutée à répétition sur un tableau de bord. La quatrième nécessite une migration de table : c’est donc la plus lourde à mettre en œuvre.

Les résumés ci-dessous sont volontairement succincts. Pour connaître la justification de chaque modification, les tests de performance et les procédures pour l’appliquer aux données existantes, consultez [Optimisation des performances](/fr/clickstack/self-configured/managing/performance-tuning).

<Steps>
  <Step title="Matérialiser les attributs fréquemment interrogés" id="materialize-attributes">
    Filtrer sur `LogAttributes['service.version']` oblige ClickHouse à charger et décoder l&#39;intégralité de la map `LogAttributes` pour chaque ligne examinée. Promouvez l&#39;attribut en colonne `MATERIALIZED` : le même filtre devient alors une simple lecture de colonne, généralement plus rapide d&#39;un ordre de grandeur. ClickStack réécrit automatiquement le filtre dès que la colonne existe : les recherches enregistrées et les tableaux de bord continuent donc de fonctionner sans modification.

    Choisissez les attributs que vous interrogez réellement souvent. Chaque colonne matérialisée a un coût, en stockage comme au moment de l’insertion : il s&#39;agit donc de « promouvoir ce que vous utilisez » plutôt que de « tout promouvoir ».

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    Pour les lignes existantes, la nouvelle colonne reste vide tant que vous n&#39;exécutez pas également `ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion`.

    En savoir plus : [Matérialiser les attributs fréquemment interrogés](/fr/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes).
  </Step>

  <Step title="Ajouter des index de saut" id="add-skip-indexes">
    Les index de saut permettent à ClickHouse d&#39;écarter les granules de données qui ne peuvent pas satisfaire un filtre, transformant ainsi un parcours complet en une petite lecture ciblée. Trois types sont à connaître :

    * **Index textuels** (`text(tokenizer = ...)`) sur les colonnes de type chaîne et sur les tableaux `mapKeys`/`*AttributeItems`. Le schéma de logs par défaut les inclut déjà.
    * **Index min-max** sur les colonnes numériques filtrées par plage. La `Duration` des traces en est l&#39;exemple type.
    * **Filtres de Bloom** pour les recherches d&#39;égalité à forte cardinalité, sur les versions de ClickHouse qui ne prennent pas encore en charge les index textuels.

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    Un index de saut n&#39;est rentable que s&#39;il élimine effectivement des granules, compte tenu de son coût d&#39;évaluation. Vérifiez-le avec `EXPLAIN indexes = 1` sur une requête représentative avant de conclure qu&#39;il est utile.

    En savoir plus : [Ajouter des index de saut](/fr/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes).
  </Step>

  <Step title="Précalculer les agrégations répétées" id="materialized-views">
    Lorsque la même agrégation s&#39;exécute en boucle sur un tableau de bord (principaux services par taux d&#39;erreur, latence p99 par endpoint, nombre de requêtes par minute), une vue matérialisée calcule le résultat au moment de l’insertion et l&#39;écrit dans une petite table d&#39;agrégation. Les tableaux de bord interrogent alors cette table plutôt que les logs ou traces bruts, ce qui est bien moins coûteux.

    Cette approche est rentable lorsque le tableau de bord est très sollicité et que la table sous-jacente est volumineuse. En contrepartie, elle consomme un peu de CPU au moment de l’insertion et ajoute une seconde table à maintenir.

    En savoir plus : [Exploiter les vues matérialisées](/fr/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views).
  </Step>

  <Step title="Choisir une clé primaire adaptée à vos modes d’accès" id="choose-primary-key">
    La clé primaire détermine l&#39;ordre de tri des lignes sur disque. Les filtres portant sur les premières colonnes de cette clé permettent à ClickHouse d&#39;accéder directement à la zone pertinente ; les filtres qui ne portent pas sur l&#39;une de ces premières colonnes parcourent toute la partition.

    La clé par défaut des logs `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)` privilégie les requêtes du type « que s&#39;est-il passé au cours des N dernières minutes pour le service X ? ». Si la plupart de vos requêtes filtrent d&#39;abord sur une autre colonne (un identifiant de locataire, un identifiant client, une région), placer cette colonne en tête de la clé primaire est le changement le plus efficace que vous puissiez apporter.

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- mêmes colonnes que otel_logs
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse ne permet pas de modifier la clé primaire sur place : il s&#39;agit donc d&#39;une migration de table et non d&#39;un simple `ALTER`. Le guide d&#39;optimisation des performances détaille la création de la nouvelle table, la redirection de l&#39;ingestion et l&#39;utilisation d&#39;une table `Merge` afin que les tableaux de bord existants continuent de fonctionner sur les anciennes comme sur les nouvelles données.

    En savoir plus : [Modifier la clé primaire](/fr/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key).
  </Step>
</Steps>
