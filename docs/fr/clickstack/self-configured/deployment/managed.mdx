<Note>
  Cette page traite de **Self-managed ClickHouse Observability**. Pour bénéficier de l’expérience entièrement gérée recommandée, consultez la documentation [ici](/fr/clickstack/observability/getting-started).
</Note>

Ce **guide s’adresse aux utilisateurs actuels de ClickHouse Cloud**. Si vous découvrez ClickHouse Cloud, nous vous recommandons notre guide [Premiers pas](/fr/clickstack/self-configured/getting-started/managed) consacré à Self-managed ClickHouse Observability.

Dans ce modèle de déploiement, ClickHouse et l’interface utilisateur de ClickStack sont tous deux hébergés dans ClickHouse Cloud, ce qui réduit au minimum le nombre de composants que l’utilisateur doit auto-héberger.

Outre une gestion de l’infrastructure allégée, ce modèle de déploiement garantit l’intégration de l’authentification au SSO/SAML de ClickHouse Cloud. Contrairement aux déploiements auto-hébergés, il n’est pas non plus nécessaire de provisionner une instance MongoDB pour stocker l’état de l’application (tableaux de bord, recherches enregistrées, paramètres utilisateur, alertes, etc.). Les utilisateurs bénéficient également des avantages suivants :

* Mise à l’échelle automatique de la capacité de calcul, indépendamment du stockage
* Rétention à faible coût et pratiquement illimitée grâce au stockage d’objet
* La possibilité d’[isoler les charges de travail de lecture et d’écriture](/fr/clickstack/self-configured/managing/isolating-read-write) grâce aux entrepôts.
* Authentification intégrée
* Sauvegardes automatisées
* Fonctionnalités de sécurité et de conformité
* Mises à niveau transparentes

Dans ce mode, l’ingestion de données est entièrement à la charge de l’utilisateur. Vous pouvez ingérer des données dans Self-managed ClickHouse Observability à l’aide de votre propre collecteur OpenTelemetry hébergé, par ingestion directe depuis des bibliothèques clientes, via des moteurs de table natifs de ClickHouse (tels que Kafka ou S3), des pipelines ETL ou ClickPipes, le service d’ingestion géré de ClickHouse Cloud. Cette approche constitue la manière la plus simple et la plus performante d’exploiter ClickStack.

### Cas d’usage adaptés {#suitable-for}

Ce modèle de déploiement est idéal dans les scénarios suivants :

1. Vous disposez déjà de données d’observability dans ClickHouse Cloud et souhaitez les visualiser avec ClickStack.
2. Vous exploitez un déploiement d’observability à grande échelle et avez besoin des performances dédiées et de la capacité de mise à l’échelle qu’offre ClickStack exécuté sur ClickHouse Cloud.
3. Vous utilisez déjà ClickHouse Cloud pour l’analyse de données et souhaitez instrumenter votre application avec les bibliothèques d’instrumentation de ClickStack, en envoyant les données vers le même cluster. Dans ce cas, nous vous recommandons d’utiliser des [entrepôts](/fr/products/cloud/features/infrastructure/warehouses) afin d’isoler la capacité de calcul allouée aux charges de travail d’observability.

### Créer une base de données et une table {#create-database-and-tables}

            Vector exige qu&#39;une table et un schéma soient définis avant l&#39;ingestion de données.

            Commencez par créer une base de données, par exemple via la [Console ClickHouse Cloud](/fr/products/cloud/features/sql-console-features/sql-console).

            Par exemple, créez une base de données pour les logs :

            ```sql
            CREATE DATABASE IF NOT EXISTS logs
            ```

            Créez ensuite une table dont le schéma correspond à la structure de vos données de journaux. L&#39;exemple ci-dessous part du principe que vous utilisez le format classique des journaux d&#39;accès Nginx :

            ```sql
            CREATE TABLE logs.nginx_logs
            (
                `time_local` DateTime,
                `remote_addr` IPv4,
                `remote_user` LowCardinality(String),
                `request` String,
                `status` UInt16,
                `body_bytes_sent` UInt64,
                `http_referer` String,
                `http_user_agent` String,
                `http_x_forwarded_for` LowCardinality(String),
                `request_time` Float32,
                `upstream_response_time` Float32,
                `http_host` String
            )
            ENGINE = MergeTree
            ORDER BY (toStartOfMinute(time_local), status, remote_addr);
            ```

            Votre table doit correspondre au schéma de sortie produit par Vector. Adaptez le schéma à vos données si nécessaire, en suivant les [bonnes pratiques recommandées pour les schémas](/fr/concepts/best-practices/select-data-type).

            Nous vous recommandons vivement de bien comprendre le fonctionnement des [clés primaires](/fr/concepts/core-concepts/primary-indexes) dans ClickHouse et de choisir une clé d’ordonnancement adaptée à vos schémas d’accès. Consultez les recommandations [propres à ClickStack](/fr/clickstack/self-configured/managing/performance-tuning#choosing-a-primary-key) sur le choix d’une clé primaire.

            Une fois la table créée, copiez l’extrait de configuration affiché. Adaptez l’entrée pour consommer vos pipelines existants et, si nécessaire, modifiez la table cible et la base de données. Les identifiants devraient être préremplis.

## Tâches supplémentaires {#additional-tasks}

### Attribution de l’accès à Self-managed ClickHouse Observability {#configure-access}

1. Accédez à votre service dans la Console ClickHouse Cloud
2. Allez dans **Paramètres** → **Accès à la console SQL**
3. Définissez le niveau de permission approprié pour chaque utilisateur :
   * **Administrateur du service → Accès complet** - obligatoire pour activer les alertes
   * **Service en lecture seule → Lecture seule** - peut consulter les données d’observability et créer des tableaux de bord
   * **Aucun accès** - n’a pas accès à l’interface utilisateur de ClickStack

<div className="ch-image-md">
  <Frame>
    ![ClickHouse Cloud en lecture seule](/images/clickstack/read-only-access.webp)
  </Frame>
</div>

<Warning>
  **Les alertes nécessitent un accès administrateur**

  Pour activer les alertes, au moins un utilisateur disposant des permissions **Administrateur du service** (correspondant à **Accès complet** dans la liste déroulante Accès à la console SQL) doit se connecter au moins une fois à l’interface utilisateur de ClickStack. Cette connexion provisionne dans la base de données un utilisateur dédié chargé d’exécuter les requêtes d’alerte.
</Warning>

### Utiliser ClickStack avec une capacité de calcul en lecture seule {#clickstack-read-only-compute}

L&#39;interface utilisateur de ClickStack peut fonctionner entièrement sur un service ClickHouse Cloud en lecture seule. C&#39;est la configuration recommandée lorsque vous souhaitez isoler les charges de travail d&#39;ingestion de celles des requêtes.

#### Comment ClickStack choisit la capacité de calcul {#how-clickstack-selects-compute}

L’interface utilisateur de ClickStack se connecte toujours au service ClickHouse à partir duquel elle est lancée dans la Console ClickHouse Cloud.

Concrètement :

* Si vous ouvrez ClickStack depuis un service en lecture seule, toutes les requêtes émises par l’interface utilisateur de ClickStack s’exécuteront sur cette capacité de calcul en lecture seule.
* Si vous ouvrez ClickStack depuis un service de lecture-écriture, ClickStack utilisera alors la capacité de calcul de ce service.

Aucune configuration supplémentaire n’est nécessaire dans ClickStack pour imposer le fonctionnement en lecture seule.

#### Configuration recommandée {#recommended-setup}

Pour exécuter ClickStack sur une capacité de calcul en lecture seule :

1. Créez ou identifiez, dans l&#39;entrepôt, un service ClickHouse Cloud configuré en lecture seule.
2. Dans la Console ClickHouse Cloud, sélectionnez le service en lecture seule.
3. Lancez ClickStack depuis le menu de navigation de gauche.

Une fois lancée, l&#39;interface utilisateur de ClickStack se connecte automatiquement à ce service en lecture seule.

Notez que les tableaux de bord, les recherches enregistrées, les alertes et les sources sont propres au service depuis lequel ClickStack a été lancé : tout élément enregistré sur un autre service de l&#39;entrepôt n&#39;est donc pas disponible ici et doit être recréé. Les sources utilisant le schéma OpenTelemetry standard sont détectées automatiquement, si bien que la recherche sur ces données fonctionne immédiatement ; ce n&#39;est pas le cas des sources personnalisées ou configurées manuellement, qui doivent être reconfigurées.

Pour la topologie complète, notamment la destination de l&#39;ingestion, le service sur lequel exécuter les instructions DDL et le comportement des alertes, consultez [« Isoler les charges de travail de lecture et d&#39;écriture »](/fr/clickstack/self-configured/managing/isolating-read-write).

### Ajouter d&#39;autres sources de données {#adding-data-sources}

ClickStack prend en charge OpenTelemetry de manière native, sans pour autant s&#39;y limiter : vous pouvez utiliser vos propres schémas de table si vous le souhaitez.

La section suivante explique comment ajouter des sources de données en plus de celles configurées automatiquement.

#### Utilisation des schémas OpenTelemetry {#using-otel-schemas}

ClickStack détecte automatiquement les tables qui utilisent le schéma OpenTelemetry standard et crée les sources de données correspondantes pour les logs, les traces et les métriques. Aucune boîte de dialogue de confirmation ni aucune création manuelle de source n’est nécessaire.

Pour vérifier ou modifier une source créée automatiquement, ouvrez **Team Settings → Data → Sources** et dépliez la source. L’exemple ci-dessous présente la source de journaux de la table `otel_logs`.

<Info>

#### Utiliser des schémas personnalisés {#using-custom-schemas}

Pour les tables personnalisées, configurez une source de données en vous appuyant sur la [référence des paramètres de source de données](/fr/clickstack/self-configured/managing/config#datasource-settings).

## Choix du schéma : Map ou JSON {#schema-choice-map-vs-json}

Par défaut, ClickStack stocke les attributs dans des colonnes `Map(LowCardinality(String), String)`. C&#39;est le schéma recommandé pour les charges de travail d&#39;observability. Associé à la [sérialisation des maps par compartiments](/fr/reference/data-types/map#bucketed-map-serialization) et à des index textuels sur les clés et valeurs des maps, il permet des recherches sélectives sans le surcoût d&#39;ingestion par clé propre aux sous-colonnes JSON dynamiques.

Un schéma basé sur le type `JSON` est disponible en bêta, à des fins d&#39;évaluation, pour les charges de travail dont l&#39;ensemble de clés d&#39;attributs est restreint et stable. Il n&#39;est **pas recommandé** comme option par défaut. Consultez [Map ou type JSON](/fr/clickstack/self-configured/ingesting-data/schema/map-vs-json) pour une comparaison complète et la liste des variables d&#39;environnement nécessaires pour activer la prise en charge du JSON.
