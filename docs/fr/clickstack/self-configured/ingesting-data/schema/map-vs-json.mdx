Le [schéma par défaut](/fr/clickstack/self-configured/ingesting-data/schemas) stocke les attributs de ressource, de portée, de journal et de span dans des colonnes `Map(LowCardinality(String), String)`. ClickHouse prend également en charge un [type `JSON`](/fr/reference/formats/JSON/JSON) fortement typé, et Self-managed ClickHouse Observability propose, en version bêta, la possibilité de l’utiliser à la place de `Map`.

**Pour les charges de travail d’observability courantes, nous recommandons de conserver le [schéma par défaut basé sur le type `Map`](/fr/clickstack/self-configured/ingesting-data/schemas).** Le type JSON est disponible pour les utilisateurs qui souhaitent l’évaluer sur des charges de travail comportant un ensemble restreint et stable de clés d’attribut, mais ce n&#39;est pas le schéma recommandé pour un usage général.

## Pourquoi Map est le choix par défaut recommandé {#why-map}

Les données d’observability sont dominées par des attributs tels que les attributs de ressource, les attributs de portée (scope) ainsi que les attributs de span et de journal. Ces ensembles sont généralement volumineux, high-cardinality et ingérés à débit élevé. Le schéma que vous choisissez pour ces attributs est le facteur déterminant du coût d’ingestion et de la disposition du stockage.

`Map(LowCardinality(String), String)` stocke les clés et les valeurs dans une structure unique. L’inconvénient historique de `Map` était que la lecture d’une seule clé imposait de lire l’intégralité de la colonne map. Ce n’est plus le cas : ClickHouse prend désormais en charge la [sérialisation des maps par compartiments](/fr/reference/data-types/map#bucketed-map-serialization), qui répartit la map en compartiments afin que les requêtes ne lisent que ceux dont elles ont besoin. Associée à des [index textuels](/fr/reference/engines/table-engines/mergetree-family/textindexes) sur les clés et les valeurs de la map (c’est ainsi qu’est configuré le [schéma par défaut](/fr/clickstack/self-configured/ingesting-data/schemas)), cette approche rend `Map` sélectif et rapide en lecture, sans aucune pénalité d’ingestion pour les nouvelles clés.

Concrètement, cela se traduit par :

* **Un coût d’ingestion stable à mesure que les clés se multiplient.** L’ajout d’une nouvelle clé d’attribut ne modifie pas la disposition des colonnes sur disque et ne crée pas de nouveaux fichiers de colonnes. Le coût d’ingestion dépend du volume de données, et non de la cardinalité des clés.
* **Aucune explosion des métadonnées.** Le nombre de fichiers de colonnes sur disque n’augmente pas avec le nombre de clés d’attribut uniques.
* **Des lookups sélectifs grâce aux index.** Les index textuels sur les clés et les valeurs de la map permettent des lookups ponctuels sans parcourir toutes les lignes.
* **Un comportement prévisible à débit élevé.** Map gère les ensembles d’attributs irréguliers et sans schéma, courants dans le traçage et les journaux, sans surcoût par clé.

## Pourquoi ne pas utiliser JSON par défaut {#why-not-json}

Le type `JSON` adopte une approche différente : au moment de l’insertion, ClickHouse crée dynamiquement une sous-colonne dédiée et fortement typée pour chaque chemin rencontré. À la lecture, cette approche est séduisante : seules les sous-colonnes demandées sont lues, les types sont préservés et aucune conversion n’est nécessaire au moment de la requête.

La contrepartie se paie à l’ingestion. La création et la gestion de nombreuses sous-colonnes dynamiques entraînent un surcoût à l’écriture et complexifient les métadonnées. Pour les charges de travail d’observability, qui présentent couramment des ensembles d’attributs très volumineux ou très dynamiques ainsi qu’un débit d’ingestion élevé, ce surcoût est considérable. La limite [`max_dynamic_paths`](/fr/reference/data-types/newjson#reading-json-paths-as-sub-columns) permet de limiter les dégâts en déversant les chemins excédentaires dans une colonne partagée, mais l’accès à cette colonne partagée est plus lent que l’accès aux sous-colonnes dédiées, ce qui réduit l’avantage en lecture qui justifiait précisément le recours à JSON.

La sérialisation des maps par compartiments éliminant l’essentiel du surcoût historique de `Map` à la lecture, l’avantage de `JSON` en lecture ne compense plus son coût à l’ingestion pour les charges de travail d’observability typiques.

## Quand envisager malgré tout JSON {#when-to-consider-json}

Le type JSON peut être un choix pertinent lorsque *toutes* les conditions suivantes sont réunies :

* Votre ensemble de clés d’attribut est **réduit et stable** : vous n’observez pas des milliers de clés uniques, et de nouvelles clés n’apparaissent que rarement.
* Le débit d’ingestion est **modéré** par rapport à la cardinalité des attributs.
* Vous souhaitez un **accès fortement typé** aux attributs, sans conversion au moment de la requête (les nombres restent des nombres, les booléens restent des booléens).
* Vous êtes prêt à exploiter une **fonctionnalité bêta** dans Self-managed ClickHouse Observability et à accepter que l’intégration puisse évoluer.

Si ces conditions ne sont pas toutes réunies, conservez le [schéma par défaut basé sur le type `Map`](/fr/clickstack/self-configured/ingesting-data/schemas).

## Statut bêta {#beta-status}

<BetaBadge />

<Warning>
  **Fonctionnalité bêta, non prête pour la production**

  La prise en charge du type JSON dans **Self-managed ClickHouse Observability** est une **fonctionnalité bêta**. Bien que le type JSON lui-même soit prêt pour la production à partir de ClickHouse 25.3+, son intégration dans le service est toujours en cours de développement et peut présenter des limitations, évoluer à l&#39;avenir ou contenir des bogues.
</Warning>

ClickStack prend en charge le type JSON en version bêta depuis la version `2.0.4`.

## Activer la prise en charge du JSON {#enabling-json-support}

Pour utiliser des schémas reposant sur le type JSON plutôt que les [schémas par défaut basés sur le type `Map`](/fr/clickstack/self-configured/ingesting-data/schemas), définissez les variables d’environnement suivantes.

| Variable                                                        | À définir sur                      | Rôle                                                |
| --------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------- |
| `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'` | ClickHouse Observability Collector | Crée les schémas dans ClickHouse avec le type JSON. |

<a id="managed-clickstack" />

Pour activer la prise en charge du JSON dans Self-managed ClickHouse Observability, contactez support@clickhouse.com avant de configurer le collecteur. La fonctionnalité doit également être activée dans l’UI d’observability de ClickHouse Cloud.

Définissez `OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json'` sur le collecteur. Par exemple :

```shell
docker run -e OTEL_AGENT_FEATURE_GATE_ARG='--feature-gates=clickhouse.json' -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} -e CLICKHOUSE_USER=default -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} -p 8080:8080 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-otel-collector:latest
```

## Migration d&#39;un schéma basé sur le type Map vers JSON {#migrating-from-map-to-json}

<Warning>
  **Compatibilité descendante**

  Le [type JSON](/fr/reference/formats/JSON/JSON) n&#39;offre **pas de compatibilité descendante** avec les schémas existants basés sur le type Map. L&#39;activation de cette fonctionnalité crée de nouvelles tables utilisant le type `JSON` et nécessite une migration manuelle des données.
</Warning>

Pour migrer depuis les [schémas par défaut basés sur le type Map](/fr/clickstack/self-configured/ingesting-data/schemas), procédez comme suit :

<Steps>
  <Step title="Arrêter l'OTel collector" id="stop-the-collector" />

  <Step title="Renommer les tables existantes et mettre à jour les sources" id="rename-existing-tables-sources">
    Renommez les tables existantes et mettez à jour les sources de données dans l&#39;UI d&#39;observability.

    Par exemple :

    ```sql
    RENAME TABLE otel_logs TO otel_logs_map;
    RENAME TABLE otel_metrics TO otel_metrics_map;
    ```
  </Step>

  <Step title="Déployer le collecteur" id="deploy-the-collector">
    Déployez le collecteur en définissant `OTEL_AGENT_FEATURE_GATE_ARG`.
  </Step>

  <Step title="Vérifier que la prise en charge du schéma JSON est activée" id="restart-the-hyperdx-container">
    Avant de créer les nouvelles sources de données, vérifiez auprès de support@clickhouse.com que la prise en charge du schéma JSON a bien été activée dans l&#39;UI d&#39;observability.
  </Step>

  <Step title="Créer de nouvelles sources de données" id="create-new-data-sources">
    Dans l&#39;UI d&#39;observability, créez de nouvelles sources de données pointant vers les tables JSON.
  </Step>
</Steps>

### Migration des données existantes (facultatif) {#migrating-existing-data}

Pour migrer les anciennes données vers les nouvelles tables JSON :

```sql
INSERT INTO otel_logs SELECT * FROM otel_logs_map;
INSERT INTO otel_metrics SELECT * FROM otel_metrics_map;
```

<Warning>
  Recommandé uniquement pour les jeux de données de moins d&#39;environ 10 milliards de lignes. Les données précédemment stockées avec le type Map ne conservaient pas la précision des types (toutes les valeurs étaient des chaînes de caractères). Par conséquent, ces anciennes données apparaîtront sous forme de chaînes de caractères dans le nouveau schéma jusqu&#39;à leur expiration, ce qui nécessitera quelques conversions côté frontend. Le type des nouvelles données sera préservé grâce au type JSON.
</Warning>
