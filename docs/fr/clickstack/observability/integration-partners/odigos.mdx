  Ce guide explique comment exporter les données de télémétrie d&#39;Odigos vers ClickHouse Observability. Vous apprendrez à :

  * Ajouter des sources dans l&#39;UI d&#39;Odigos

  Durée : 10 à 20 minutes

## Qu&#39;est-ce qu&#39;Odigos ? {#what-is-odigos}

{/* vale on */}

[Odigos](https://odigos.io/) est un plan de contrôle d’instrumentation pour Kubernetes et les VM, qui instrumente les applications depuis le kernel grâce à **eBPF**. La collecte s’exécutant dans le kernel, le surcoût pour les applications reste faible, tout en offrant une visibilité élevée. Vous obtenez des traces, metrics, logs et profils OpenTelemetry production-grade, sans intégrer de nouveaux agents dans le code applicatif ni attendre la mise à niveau des bibliothèques de chaque service.

C’est cette couche eBPF qui permet une télémétrie approfondie et cohérente à grande échelle. Odigos peut activer et désactiver automatiquement une instrumentation plus poussée en cas de besoin, afin de faciliter le débogage et la résolution de problèmes :

* **Contexte au niveau du code** — attributs liés aux fonctions et au comportement de l’environnement d’exécution
* **Trafic HTTP** — requêtes et réponses entre vos services
* **Systèmes de messagerie** — charges utiles et messages issus de Kafka et de brokers similaires
* **Erreurs détaillées** — traces de pile en cas de défaillance
* **Instrumentation personnalisée** — étendez la couverture au-delà de l’auto-instrumentation, sans modifier le code ni effectuer de restart

En coulisses, Odigos crée et gère un pipeline OpenTelemetry complet pour votre cluster : des collecteurs qui s’adaptent à la charge, un routage vers les backends de votre choix et une logique de pipeline que vous pilotez depuis l’UI. Définissez un **échantillonnage** pour maîtriser le volume, un **masquage des données personnelles (PII)** pour exclure les données sensibles des exportations et des **règles OTTL** pour filtrer, transformer ou enrichir la télémétrie avant qu’elle ne quitte le cluster.

{/* vale off */}

## Pourquoi Odigos + ClickHouse Observability ? {#why-odigos-clickstack}

{/* vale on */}

Déployer OpenTelemetry sur de nombreux services est souvent chronophage et n&#39;offre qu&#39;une visibilité superficielle sur les applications. Odigos prend en charge l&#39;instrumentation eBPF, pour une télémétrie plus approfondie, ainsi que l&#39;exploitation du collecteur sur Kubernetes ; ClickHouse Observability fournit quant à lui un stockage reposant sur ClickHouse et l&#39;interface utilisateur de ClickStack pour interroger la télémétrie à grande échelle.

<Tip>
  **Points clés**

  * **Odigos** instrumente automatiquement n&#39;importe quelle charge de travail Kubernetes sans nécessiter de restart et gère automatiquement les pipelines OpenTelemetry.
  * **ClickHouse Observability** stocke les logs, les metrics et les traces dans ClickHouse et les affiche dans l&#39;interface utilisateur de ClickStack.
</Tip>

## Prérequis {#prerequisites}

* Un service ClickHouse Observability joignable depuis votre cluster Kubernetes. Consultez [Premiers pas](/fr/clickstack/observability/getting-started). Pour les déploiements autogérés, consultez [Configuration autogérée](/fr/clickstack/self-configured/deployment/managed).
* Votre **point de terminaison OTLP HTTP** et votre API key d’ingestion, disponibles dans **Paramètres de l’équipe → Données → Télémétrie gérée**. Pour les déploiements autogérés, utilisez l’endpoint de votre collecteur autonome et `OTLP_AUTH_TOKEN`.
* Un **cluster Kubernetes** (nœuds Linux dotés d’un kernel 4.18 ou version ultérieure pour l’instrumentation eBPF)
* **Helm**, **kubectl** et des identifiants de cluster permettant d’effectuer l’installation dans le namespace `odigos-system`
* Un **jeton Odigos Enterprise on-prem** — contactez l’[équipe Odigos](https://odigos.io/) pour obtenir un accès

## Intégrer ClickHouse Observability à Odigos {#integrate-odigos-clickstack}

{/* vale on */}

<Steps>
  <Step title="Déployer Odigos avec Helm" id="deploy-odigos">
    Odigos Enterprise nécessite un jeton de licence on-prem. Exportez-le dans votre interpréteur de commandes :

    ```bash
    export ODIGOS_ONPREM_TOKEN="<your-enterprise-token>"
    ```

    Vous pouvez également stocker le jeton dans un Secret Kubernetes nommé `odigos-pro` avant l&#39;installation. Consultez la [documentation Odigos Enterprise](https://enterprise.docs.odigos.io/) (accès requis).

    Ajoutez le dépôt Helm d&#39;Odigos et installez le chart dans `odigos-system` :

    ```bash
    helm repo add odigos https://odigos-io.github.io/odigos/
    helm repo update

    helm upgrade --install odigos odigos/odigos \
      --namespace odigos-system \
      --create-namespace \
      --set onPremToken=$ODIGOS_ONPREM_TOKEN
    ```

    Vous pouvez fournir des surcharges de configuration supplémentaires à l’aide d’options `--set` ou d’un fichier de valeurs personnalisé (`-f`). Pour consulter les valeurs par défaut du chart, exécutez `helm show values odigos/odigos`.

    Vérifiez que les groupes de conteneurs Odigos sont en cours d’exécution :

    ```bash
    kubectl get pods -n odigos-system
    ```
  </Step>

  <Step title="Ajouter des sources dans l’UI d’Odigos" id="add-sources">
    1. Effectuez un port-forward du service de l&#39;UI Odigos :

    ```bash
    kubectl port-forward svc/ui -n odigos-system 3000:3000
    ```

    2. Ouvrez [http://localhost:3000](http://localhost:3000) dans votre navigateur.
    3. Accédez à **Sources** et sélectionnez les espaces de noms ou les charges de travail que vous souhaitez instrumenter.
    4. Une fois toutes les charges de travail à instrumenter sélectionnées, cliquez sur « Done » en bas de la page.
    5. Vérifiez dans la colonne des sources que les charges de travail ont bien été instrumentées.
  </Step>

  <Step title="Ajoutez ClickHouse Observability comme destination dans l’UI d’Odigos" id="add-destination-ui">
    Pour envoyer des données de télémétrie, ajoutez une destination **OTLP HTTP** dans Odigos. Sélectionnez votre type de déploiement ci-dessous.

    <Tabs>
      <Tab title="Entièrement géré">
        <BetaBadge label="Offre en version bêta" />

        ClickHouse Observability vous fournit un point de terminaison OTLP. ClickHouse se charge de l’ingestion, des schémas et des ressources de calcul. Il vous suffit de faire pointer Odigos vers ce point de terminaison : aucun collecteur n’est à déployer.

        1. Dans l’UI d’Odigos, cliquez sur **Add Destination** et sélectionnez **OTLP HTTP**.
        2. Renseignez dans **OTLP HTTP Endpoint** le point de terminaison HTTPS fourni par ClickHouse Cloud, en incluant le port `4318`. Par exemple : `https://<service-id>.otel.<region>.aws.clickhouse.com:4318`.
        3. Dans **Headers**, ajoutez :
           * **Key** : `Authorization`
           * **Value** : `Bearer <YOUR_INGESTION_API_KEY>`
        4. Activez **Logs**, **Metrics** et **Traces**.
        5. Enregistrez la destination.
      </Tab>

      <Tab title="Autogéré">
        <Tip>
          **Alternative : écrire directement dans ClickHouse**

          Pour les déploiements autogérés, vous pouvez utiliser la [destination **ClickHouse** native](#native-clickhouse-destination) d’Odigos au lieu d’exécuter un collecteur OTLP, à condition que votre service ClickHouse soit accessible depuis votre cluster Kubernetes. Les déploiements entièrement gérés doivent obligatoirement passer par le point de terminaison OTLP géré.
        </Tip>

        Pour un déploiement autogéré, exécutez vous-même la [distribution ClickStack du collecteur en mode autonome](/fr/clickstack/self-configured/ingesting-data/collector#configuring-the-collector-self-configured) et définissez le jeton d’authentification via la variable d’environnement `OTLP_AUTH_TOKEN` au démarrage du conteneur. Odigos envoie ensuite le trafic OTLP HTTP à ce collecteur en transmettant le même jeton dans l’en-tête `Authorization`.

        1. Démarrez le collecteur ClickStack en mode autonome, en le faisant pointer vers votre service ClickHouse Cloud et en le sécurisant avec un `OTLP_AUTH_TOKEN` de votre choix :

           ```shell
           export CLICKHOUSE_ENDPOINT=<HTTPS_ENDPOINT>
           export CLICKHOUSE_USER=<CLICKHOUSE_USER>
           export CLICKHOUSE_PASSWORD=<CLICKHOUSE_PASSWORD>
           export OTLP_AUTH_TOKEN="a_very_secure_string"

           docker run \
             -e OTLP_AUTH_TOKEN=${OTLP_AUTH_TOKEN} \
             -e CLICKHOUSE_ENDPOINT=${CLICKHOUSE_ENDPOINT} \
             -e CLICKHOUSE_USER=${CLICKHOUSE_USER} \
             -e CLICKHOUSE_PASSWORD=${CLICKHOUSE_PASSWORD} \
             -p 4317:4317 \
             -p 4318:4318 \
             clickhouse/clickstack-otel-collector:latest
           ```

           Pour la configuration TLS, les utilisateurs dédiés à l’ingestion et les autres recommandations pour la production, consultez [Sécuriser le collecteur](/fr/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).
        2. Dans l’UI d’Odigos, cliquez sur **Add Destination** et sélectionnez **OTLP HTTP**.
        3. Renseignez dans **OTLP HTTP Endpoint** l’adresse du collecteur autonome que vous venez de démarrer (par exemple, `http://my-collector.example.com:4318`).
        4. Dans **Headers**, ajoutez :
           * **Key** : `Authorization`
           * **Value** : la valeur de `OTLP_AUTH_TOKEN` définie sur le collecteur
        5. Activez **Logs**, **Metrics** et **Traces**.
        6. Enregistrez la destination.

        <Info>
          **Facultatif : manifest Kubernetes**

          Vous pouvez configurer la même destination à l’aide d’un manifest `Destination` plutôt que via l’UI. Consultez [Configurer les destinations avec des manifests Kubernetes](#destination-manifest) dans la section Configuration avancée.
        </Info>
      </Tab>
    </Tabs>
  </Step>

  <Step title="Vérifiez la télémétrie dans ClickHouse Observability" id="verify-telemetry">
    1. Ouvrez l&#39;interface utilisateur de ClickStack :
       * **Autogéré** : ouvrez votre service dans la [console ClickHouse Cloud](https://console.clickhouse.cloud), puis cliquez sur **Launch ClickStack**. Pour plus de détails, consultez [Accéder à l&#39;interface utilisateur de ClickStack](/fr/clickstack/self-configured/deployment/managed).
       * **Entièrement géré** : ouvrez la vue observability de votre service ClickHouse Cloud.
    2. Dans les sections **Logs**, **Metrics** et **Traces**, vérifiez la présence de données provenant de vos services instrumentés.
    3. Filtrez les traces sur `odigos.version` afin de valider l&#39;exportation de bout en bout.

    Si des données manquent, consultez les logs du collecteur : `kubectl logs deploy/odigos-gateway -n odigos-system`
  </Step>
</Steps>

## Configuration avancée {#advanced-configuration}

### Destination ClickHouse native {#native-clickhouse-destination}

La destination ClickHouse native est disponible uniquement pour les déploiements **autogérés**. Pour les déploiements **entièrement gérés**, utilisez la destination **OTLP HTTP** avec votre endpoint géré.

<Tabs>
  <Tab title="Autogéré">
    Si ClickHouse est directement joignable depuis votre cluster, vous pouvez utiliser la destination native **ClickHouse** d’Odigos plutôt qu’OTLP HTTP. Configurez l’endpoint ClickHouse, le nom de la base de données et les options de schéma dans l’UI ou à l’aide d’un manifest (voir [destination ClickHouse d’Odigos](https://docs.odigos.io/backends/clickhouse)).

    * **Schéma de production** : définissez `CLICKHOUSE_CREATE_SCHEME` sur `false` et appliquez votre propre DDL.
    * **TLS / authentification** : utilisez `CLICKHOUSE_TLS_ENABLED`, `CLICKHOUSE_USERNAME` et un Secret Kubernetes pour le mot de passe.

    **Manifest Kubernetes**

    ```yaml
    apiVersion: odigos.io/v1alpha1
    kind: Destination
    metadata:
      name: clickhouse
      namespace: odigos-system
    spec:
      type: clickhouse
      destinationName: clickhouse
      signals:
        - TRACES
        - METRICS
        - LOGS
      data:
        CLICKHOUSE_ENDPOINT: 'http://clickstack.example.com:8123'
        CLICKHOUSE_DATABASE_NAME: 'otel'
        CLICKHOUSE_CREATE_SCHEME: 'true'
    ```

    Enregistrez le manifest sous le nom `destination.yaml`, puis appliquez-le :

    ```bash
    kubectl apply -f destination.yaml
    ```

#### Normalisateur de journaux HyperDX {#hyperdx-log-normalizer}

    Pour les déploiements autogérés qui exportent directement vers ClickHouse via la destination native **ClickHouse** d’Odigos, activez le **normalisateur de journaux HyperDX** (`HYPERDX_LOG_NORMALIZER: true`). Il analyse les corps de journaux au format JSON et normalise leurs attributs afin de faciliter l’exécution des requêtes dans l’interface utilisateur de ClickStack. Ce paramètre ne s’applique pas à la destination OTLP entièrement gérée.
  </Tab>
</Tabs>

### Configurer les destinations avec des manifestes Kubernetes {#destination-manifest}

**OTLP HTTP (ClickStack)**

```yaml
apiVersion: odigos.io/v1alpha1
kind: Destination
metadata:
  name: clickstack
  namespace: odigos-system
spec:
  type: otlphttp
  destinationName: otlphttp
  signals:
    - TRACES
    - METRICS
    - LOGS
  data:
    OTLP_HTTP_ENDPOINT: 'http://clickstack.example.com:4318'
    # Self-managed: OTLP_AUTH_TOKEN
    # ClickHouse Observability: Bearer <YOUR_INGESTION_API_KEY>
    OTLP_HTTP_HEADERS: 'Authorization:<YOUR_AUTHORIZATION_VALUE>'
```

Appliquez le manifest :

```bash
kubectl apply -f destination.yaml
```

### Odigos VM Agent {#odigos-vm-agent}

{/* vale on */}

L’[Odigos VM Agent](https://docs.odigos.io/vmagent/overview) instrumente les processus Linux, les services systemd et/ou les conteneurs Docker à l’aide d’eBPF. La télémétrie est exportée vers les mêmes destinations qu’avec Odigos déployé dans un cluster, y compris ClickHouse Observability via OTLP HTTP.

Le VM Agent fait partie d’Odigos Pro. Consultez la [Présentation de VM Agent](https://docs.odigos.io/vmagent/overview) pour l’installation ainsi que la configuration des sources et des destinations.

{/* vale off */}

### Odigos Central {#odigos-central}

{/* vale on */}

[Odigos Central](https://docs.odigos.io/central/overview) est un plan de contrôle centralisé qui permet de gérer l’instrumentation, les destinations et la configuration des pipelines de plusieurs clusters Kubernetes depuis une seule UI, sans avoir à configurer chaque cluster séparément.

Odigos Central est disponible avec Odigos Enterprise. Consultez la [Présentation de Central](https://docs.odigos.io/central/overview) pour en savoir plus sur la gestion multicluster, le SSO et les règles d’échantillonnage unifiées.
