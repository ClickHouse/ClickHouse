Si vous utilisez ClickStack depuis un certain temps, vous avez probablement constaté que le schéma par défaut gère la plupart des charges de travail d’observability sans aucune modification. Cette page s’adresse aux cas où cela ne suffit plus : la latence des requêtes commence à augmenter, ou vos modes d’accès se sont éloignés de ceux prévus par défaut.

En pratique, quatre optimisations couvrent l’essentiel des besoins. Elles sont présentées approximativement par ordre d’effort croissant. Les deux premières sont des modifications locales via `ALTER TABLE` que vous pouvez déployer progressivement. La troisième devient rentable lorsque la même agrégation s’exécute de façon répétée dans un tableau de bord. La quatrième nécessite une migration de table, ce qui en fait la plus complexe.

Les résumés ci-dessous sont volontairement succincts. Pour connaître la logique de chaque modification, les tests de performance et les procédures permettant de l’appliquer aux données existantes, consultez [Optimisation des performances](/fr/clickstack/self-configured/managing/performance-tuning).

<Steps>
  <Step title="Matérialiser les attributs fréquemment interrogés" id="materialize-attributes">
    Filtrer sur `LogAttributes['service.version']` oblige ClickHouse à charger et décoder l’intégralité de la map `LogAttributes` pour chaque ligne examinée. En promouvant l’attribut en colonne `MATERIALIZED`, le même filtre devient une simple lecture de colonne, généralement un ordre de grandeur plus rapide. ClickStack réécrit automatiquement le filtre dès que la colonne existe : les recherches enregistrées et les tableaux de bord continuent donc de fonctionner sans modification.

    Choisissez les attributs que vous interrogez réellement souvent. Chaque colonne matérialisée a un coût en stockage et au moment de l’insertion : le principe est de « promouvoir ce que vous utilisez », et non de « tout promouvoir ».

    ```sql
    ALTER TABLE otel_logs
      ADD COLUMN ServiceVersion LowCardinality(String)
      MATERIALIZED LogAttributes['service.version'];
    ```

    Les lignes existantes restent vides pour la nouvelle colonne tant que vous n’exécutez pas également `ALTER TABLE otel_logs MATERIALIZE COLUMN ServiceVersion`.

    En savoir plus : [Matérialiser les attributs fréquemment interrogés](/fr/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes).
  </Step>

  <Step title="Ajouter des index de saut" id="add-skip-indexes">
    Les index de saut permettent à ClickHouse d’écarter les granules de données qui ne peuvent pas correspondre à un filtre, transformant ainsi un parcours complet en une lecture ciblée et limitée. Trois types sont à connaître :

    * **Index textuels** (`text(tokenizer = ...)`) sur les colonnes de type chaîne et sur les tableaux `mapKeys`/`*AttributeItems`. Le schéma de logs par défaut les inclut déjà.
    * **Index min-max** sur les colonnes numériques filtrées par plage. La `Duration` des traces en est l’exemple type.
    * **Filtres de Bloom** pour les recherches d’égalité à forte cardinalité, sur les versions de ClickHouse qui ne prennent pas encore en charge les index textuels.

    ```sql
    ALTER TABLE otel_traces ADD INDEX idx_duration Duration TYPE minmax GRANULARITY 1;
    ALTER TABLE otel_traces MATERIALIZE INDEX idx_duration;
    ```

    Un index de saut ne compense son coût d’évaluation que s’il élimine effectivement des granules. Vérifiez-le avec `EXPLAIN indexes = 1` sur une requête représentative avant de conclure à son efficacité.

    En savoir plus : [Ajouter des index de saut](/fr/clickstack/self-configured/managing/performance-tuning#adding-skip-indexes).
  </Step>

  <Step title="Précalculer les agrégations répétées" id="materialized-views">
    Lorsque la même agrégation est exécutée en boucle sur un tableau de bord (principaux services par taux d’erreur, latence p99 par endpoint, nombre de requêtes par minute), une vue matérialisée calcule le résultat au moment de l’insertion et l’écrit dans une petite table d’agrégation. Les tableaux de bord interrogent alors cette table plutôt que les logs ou traces bruts, ce qui est bien moins coûteux.

    Cette approche est rentable lorsque le tableau de bord est très sollicité et que la table sous-jacente est volumineuse. En contrepartie, elle consomme un peu de CPU au moment de l’insertion et impose de maintenir une seconde table.

    En savoir plus : [Exploiter les vues matérialisées](/fr/clickstack/self-configured/managing/performance-tuning#exploiting-materialized-views).
  </Step>

  <Step title="Choisir une clé primaire adaptée à vos modes d’accès" id="choose-primary-key">
    La clé primaire détermine l’ordre de tri des lignes sur disque. Les filtres portant sur les premières colonnes de cette clé permettent à ClickHouse d’accéder directement à la zone pertinente ; les filtres qui ne portent sur aucune de ces colonnes de tête parcourent toute la partition.

    La clé par défaut des logs, `(toStartOfFiveMinutes(Timestamp), ServiceName, Timestamp)`, privilégie les requêtes du type « que s’est-il passé au cours des N dernières minutes pour le service X ». Si la plupart de vos requêtes filtrent d’abord sur une autre colonne (un identifiant de locataire, un identifiant client, une région), modifier la clé primaire pour qu’elle commence par cette colonne est le changement le plus efficace que vous puissiez apporter.

    ```sql
    CREATE TABLE otel_logs_v2
    (
      -- mêmes colonnes que otel_logs
    )
    ENGINE = MergeTree
    ORDER BY (TenantId, ServiceName, Timestamp);
    ```

    ClickHouse ne permet pas de modifier la clé primaire sur place : il s’agit donc d’une migration de table et non d’un simple `ALTER`. Le guide d’optimisation des performances explique comment créer la nouvelle table, rediriger l’ingestion et utiliser une table `Merge` afin que les tableaux de bord existants continuent de fonctionner sur les anciennes comme sur les nouvelles données.

    En savoir plus : [Modifier la clé primaire](/fr/clickstack/self-configured/managing/performance-tuning#modifying-the-primary-key).
  </Step>
</Steps>
