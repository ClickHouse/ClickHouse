ClickHouse Observability propose une bibliothèque de modèles de tableaux de bord préconfigurés pour visualiser les données de télémétrie courantes de vos infrastructures et de vos applications. Les graphiques affichent des données dès que votre service ClickHouse reçoit la télémétrie requise par le modèle.

## Parcourir les modèles disponibles {#browsing-templates}

Pour parcourir la bibliothèque de modèles intégrée, accédez à **Tableaux de bord** et cliquez sur **Browse modèles de tableaux de bord**.

<div className="ch-image-lg">
  <Frame>
    ![Bouton Browse modèles de tableaux de bord](/images/clickstack/observability-browse-dashboard-templates.png)
  </Frame>
</div>

La galerie de modèles s’ouvre alors ; les modèles y sont classés par catégorie. Cliquez sur **Import** sur le modèle que vous souhaitez utiliser.

<div className="ch-image-lg">
  <Frame>
    ![Galerie de modèles de tableaux de bord](/images/clickstack/observability-dashboard-template-gallery.png)
  </Frame>
</div>

## Importer un modèle {#importing-a-template}

À l’**Étape 2 : Mapper les données**, vérifiez le **Dashboard Name** et les **Tags**, puis confirmez la source de données indiquée dans la colonne **To** pour chaque tuile et chaque filtre. Les sources sont parfois déjà sélectionnées. Dans l’exemple ci-dessous, le modèle Node.js Runtime Metrics associe ses graphiques et son filtre de service à la source **Metrics**. Cliquez sur **Terminer l’Import** pour créer le tableau de bord.

## Modèles préconfigurés {#pre-built-templates}

### Browser RUM {#browser-rum}

Le modèle **Browser RUM** (supervision des utilisateurs réels) fournit les Core Web Vitals, les centiles de temps de chargement des pages, des ventilations du trafic et le suivi des erreurs. Il repose sur des sessions de navigateur instrumentées avec le SDK pour navigateur de HyperDX ou avec une instrumentation OpenTelemetry RUM qui émet `rum.sessionId`.

### Métriques d’exécution OTel {#otel-runtime-metrics}

Les modèles intégrés de métriques d’exécution OTel sont conçus pour les applications instrumentées avec les [métriques de l’environnement d’exécution OpenTelemetry](https://opentelemetry.io/docs/specs/semconv/runtime/).

| Modèle                      | Description                                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **.NET Runtime Metrics**    | Ramasse-miettes, fragmentation du tas, exceptions, utilisation du thread pool et métriques CPU pour les applications .NET            |
| **Go Runtime Metrics**      | Utilisation de la mémoire, allocations, cibles du GC, taux d’utilisation du CPU et métriques des goroutines pour les applications Go |
| **JVM Runtime Metrics**     | Mémoire du tas, taux d’utilisation du CPU, fils d’exécution et métriques du GC pour les applications basées sur la JVM               |
| **Node.js Runtime Metrics** | Latence de la boucle d’événements, utilisation du tas, taux d’utilisation du CPU et mémoire V8 pour les applications Node.js         |
| **Python Runtime Metrics**  | Taux d’utilisation du CPU, utilisation de la mémoire, collectes du GC et nombre de fils d’exécution pour les applications Python     |

Notes :

* Chaque modèle est configuré avec un [filtre personnalisé](/fr/clickstack/observability/features/dashboards/overview#custom-filters) ciblant les services dont l’attribut de ressource [`telemetry.sdk.language`](https://opentelemetry.io/docs/specs/semconv/registry/attributes/telemetry/#telemetry-sdk-language) correspond à l’environnement d’exécution du tableau de bord.
* Les noms des métriques peuvent varier d’une version à l’autre du SDK OpenTelemetry. Si votre SDK émet des noms de métriques différents, [modifiez les visualisations](/fr/clickstack/observability/features/dashboards/overview#dashboards-editing-visualizations) pour les adapter à vos données.

## Schémas autogérés {#self-configured-schemas}

Pour les déploiements autogérés utilisant des schémas de table de métriques personnalisés, adaptez le filtre de service du modèle afin qu&#39;il interroge les colonnes correspondant au nom du service et aux attributs de ressource. Pour les charges de travail à fort volume, envisagez la [matérialisation des attributs fréquemment interrogés](/fr/clickstack/self-configured/managing/performance-tuning#materialize-frequently-queried-attributes), comme `ResourceAttributes['telemetry.sdk.language']`, afin de réduire les temps de chargement des filtres.
