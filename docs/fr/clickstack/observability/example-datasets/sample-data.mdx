Explorez ClickHouse Observability à l&#39;aide d&#39;exemples de logs, de sessions, de traces et de metrics issus d&#39;une boutique en ligne. Les deux modes de déploiement reposent sur le même jeu de données et le même flux de travail d&#39;investigation.

Avant de commencer, suivez le [guide de démarrage de la version entièrement gérée](/fr/clickstack/observability/getting-started) ou le [guide de démarrage de la version autogérée](/fr/clickstack/self-configured/getting-started/managed).

<Steps>
  <Step title="Configurer votre connexion" id="configure-your-connection">
    Choisissez votre déploiement et définissez les variables suivantes dans le terminal depuis lequel vous chargerez les données d’exemple.

    <Tabs>
      <Tab title="Entièrement géré">
        <BetaBadge label="Offre bêta" />

        Ouvrez **Team Settings → Data** et repérez la section **Managed Telemetry**. Sous **OpenTelemetry Collector**, utilisez l’option **URL** pour copier l’endpoint OTLP HTTP et l’API key. Sélectionnez **Reveal key** pour afficher les valeurs complètes.

        Indiquez l’endpoint de base, sans path de signal tel que `/v1/logs`. Incluez le préfixe `Bearer` dans la valeur d’autorisation :

        ```shell
        export CLICKSTACK_OTLP_ENDPOINT='<your-managed-otlp-http-endpoint>'
        export CLICKSTACK_AUTHORIZATION='Bearer <your-api-key>'
        ```

        Il n’est pas nécessaire de déployer un collecteur pour cet exemple.
      </Tab>

      <Tab title="Autogéré" id="self-managed">
        Vous devez disposer d’un collecteur OpenTelemetry ClickStack en cours d’exécution et connecté à votre service ClickHouse Cloud. Suivez le [guide d’ingestion avec OpenTelemetry](/fr/clickstack/observability/ingesting-data/opentelemetry#self-managed) pour configurer la connexion, ou le [guide de déploiement](/fr/clickstack/self-configured/deployment/managed) pour démarrer un collecteur.

        Indiquez l’endpoint OTLP HTTP du collecteur, qui doit être joignable depuis la machine exécutant la commande de téléversement. Utilisez l’URL de base, sans path de signal tel que `/v1/logs` :

        ```shell
        export CLICKSTACK_OTLP_ENDPOINT='http://<collector-host>:4318'
        export CLICKSTACK_AUTHORIZATION=''
        ```

        Si le collecteur exige une authentification, définissez `CLICKSTACK_AUTHORIZATION` sur le jeton de son récepteur. Pour un collecteur ClickStack sécurisé avec `OTLP_AUTH_TOKEN`, utilisez cette valeur sans préfixe `Bearer`. Si le récepteur n’exige pas d’authentification, laissez la valeur vide. N’utilisez pas ici le mot de passe de votre base de données ClickHouse.
      </Tab>
    </Tabs>
  </Step>

  <Step title="Télécharger les données d’exemple" id="download-sample-data">
    Pour remplir l’UI avec des données d’exemple, téléchargez le fichier suivant :

    [Données d’exemple](https://storage.googleapis.com/hyperdx/sample.tar.gz)

    ```shell
    # curl
    curl -O https://storage.googleapis.com/hyperdx/sample.tar.gz
    # or
    # wget https://storage.googleapis.com/hyperdx/sample.tar.gz
    ```

    Ce fichier contient des exemples de logs, de métriques et de traces issus de notre [OpenTelemetry demo](https://github.com/ClickHouse/opentelemetry-demo) publique, une boutique e-commerce simple reposant sur des microservices. Copiez ce fichier dans le répertoire de votre choix.
  </Step>

  <Step title="Charger des données d’exemple" id="load-sample-data">
    Exécutez les commandes suivantes dans **Bash** depuis le répertoire contenant `sample.tar.gz`. Elles envoient les données d’exemple à l’endpoint configuré ci-dessus, en n’ajoutant un en-tête d’autorisation que lorsque celui-ci est requis.

    ```bash
    set -eo pipefail

    auth_headers=()
    if [ -n "${CLICKSTACK_AUTHORIZATION:-}" ]; then
      auth_headers=(-H "Authorization: ${CLICKSTACK_AUTHORIZATION}")
    fi

    for filename in $(tar -tf sample.tar.gz); do
      endpoint="${CLICKSTACK_OTLP_ENDPOINT%/}/v1/${filename%.json}"
      echo "loading ${filename%.json}"
      tar -xOf sample.tar.gz "$filename" | while read -r line; do
        printf '%s\n' "$line" | curl --fail-with-body -sS -X POST "$endpoint" \
          -H "Content-Type: application/json" \
          "${auth_headers[@]}" \
          --data-binary @-
      done
    done
    ```

    Cette opération simule des sources OTLP de logs, de traces et de métriques qui envoient des données. En production, ces sources peuvent être des SDK applicatifs, des agents ou des collecteurs OpenTelemetry.

    Dans la Console ClickHouse Cloud, sélectionnez votre service et ouvrez ClickHouse Observability.

    Revenez à [Recherche](/fr/clickstack/observability/features/search) pour afficher les données chargées. Sélectionnez la source **Logs** et un intervalle de temps qui inclut les timestamps des événements de l&#39;échantillon. La capture d&#39;écran ci-dessous montre l&#39;arrivée des logs d&#39;exemple dans **Live Tail** :

    <div className="ch-image-lg">
      <Frame>
        ![Recherche affichant les logs d'exemple chargés depuis les services de démonstration e-commerce](/images/clickstack/getting-started/observability-sample-data-search.png)
      </Frame>
    </div>

    Le chargement des données prend quelques minutes. Attendez qu&#39;il soit terminé avant de passer aux étapes suivantes.
  </Step>

  <Step title="Explorer les sessions" id="explore-sessions">
    Supposons que nous recevions des signalements indiquant que nos utilisateurs rencontrent des difficultés pour régler leurs achats. La relecture de session nous permet de visualiser leur parcours.

    Sélectionnez **Sessions client** dans le menu de gauche et définissez un intervalle de temps qui inclut les sessions d&#39;exemple chargées.

    <div className="ch-image-lg">
      <Frame>
        ![Sessions client affichant des sessions d'exemple avec un nombre d'erreurs mis en évidence](/images/clickstack/getting-started/observability-sample-data-sessions.png)
      </Frame>
    </div>

    Cette vue répertorie les sessions de la boutique de démonstration, y compris les sessions anonymes et celles identifiées par une adresse e-mail.

    Certaines sessions présentent un nombre d&#39;erreurs non nul. Dans cet exemple, la session mise en évidence comporte une erreur.

    Sélectionnez la session mise en évidence pour ouvrir sa relecture. Utilisez le bouton de lecture en bas du lecteur pour visionner la session.

    <div className="ch-image-lg">
      <Frame>
        ![Relecture de session affichant la boutique de l'OpenTelemetry demo et les événements de navigation](/images/clickstack/getting-started/observability-sample-data-replay.png)
      </Frame>
    </div>

    La relecture montre l&#39;utilisateur qui navigue sur le site et ajoute des articles à son panier. N&#39;hésitez pas à avancer jusqu&#39;au moment où il tente de finaliser son paiement.

    <Tip>
      Les événements d&#39;erreur sont signalés en rouge dans la liste des événements.
    </Tip>

    Faites défiler la liste des événements à gauche jusqu&#39;en bas. La requête `POST /api/checkout` mise en évidence a renvoyé un code HTTP `500`, et une erreur console a été enregistrée au même moment.

    <div className="ch-image-lg">
      <Frame>
        ![Relecture de session mettant en évidence la requête POST en échec vers /api/checkout et l'erreur console associée](/images/clickstack/getting-started/observability-sample-data-checkout-error.png)
      </Frame>
    </div>

    Sélectionnez l&#39;événement `POST /api/checkout` en échec pour inspecter la requête et sa trace.
  </Step>

  <Step title="Explorer les traces" id="explore-traces">
    Ouvrez l’onglet **Trace** pour afficher la trace distribuée, avec les spans associés et les logs corrélés.

    <div className="ch-image-lg">
      <Frame>
        ![Vue en cascade des traces montrant la requête de checkout avec ses spans, ses logs corrélés et ses erreurs](/images/clickstack/getting-started/observability-sample-data-trace.png)
      </Frame>
    </div>

    Faites défiler la trace et sélectionnez le span `oteldemo.PaymentService/Charge` du service `checkout`.

    <div className="ch-image-lg">
      <Frame>
        ![Span de la requête de paiement sélectionné, affichant une erreur de carte expirée dans ses attributs](/images/clickstack/getting-started/observability-sample-data-payment-span.png)
      </Frame>
    </div>

    Dans l’onglet **Overview**, examinez la section **Top Level Attributes**. Le `StatusCode` vaut `Error` et le `StatusMessage` indique que la carte de crédit a expiré.

    <div className="ch-image-lg">
      <Frame>
        ![Attributs de la vue d’ensemble affichant un statut Error et un message indiquant que la carte de crédit a expiré](/images/clickstack/getting-started/observability-sample-data-span-attributes.png)
      </Frame>
    </div>

    Dans la trace, sélectionnez le log d’erreur `payment` situé sous le span du service de paiement. Sa ligne comporte une icône de log, qui la distingue de l’événement de span d’erreur. Dans **Overview**, le **Body** du log confirme que la carte de crédit a expiré. Les attributs indiquent le service `payment` et une sévérité `error`, ce qui apporte du contexte en complément de la trace.

    <div className="ch-image-lg">
      <Frame>
        ![Log d’erreur de paiement corrélé affichant le message de carte expirée et les attributs du log](/images/clickstack/getting-started/observability-sample-data-correlated-log.png)
      </Frame>
    </div>

    Nous avons ainsi pu remonter l’origine de ce checkout en échec : une requête de paiement rejetée parce que la carte de crédit avait expiré.
  </Step>

  <Step title="Explorer les logs" id="explore-logs">
    Pour analyser d&#39;autres échecs de paiement, revenez à la page [Recherche](/fr/clickstack/observability/features/search).

    Sélectionnez **Logs** comme source, puis choisissez `payment` dans le filtre **ServiceName**. Choisissez un intervalle de temps qui couvre la session que vous avez examinée.

    <div className="ch-image-lg">
      <Frame>
        ![Recherche filtrée sur le service payment affichant des erreurs de carte expirée et de cache Visa plein, ainsi que des transactions réussies](/images/clickstack/getting-started/observability-sample-data-payment-logs.png)
      </Frame>
    </div>

    Les résultats comprennent l&#39;erreur de carte expirée issue de la session examinée, ainsi que des erreurs `Visa cache full: cannot add new item.` récurrentes. Pour voir à quels moments les erreurs surviennent dans l&#39;ensemble du service payment, représentez ces logs d&#39;erreurs dans un graphique au fil du temps.
  </Step>

  <Step title="Afficher les erreurs de paiement dans un graphique" id="chart-payment-errors">
    Ouvrez l&#39;**Explorateur de graphiques**, sélectionnez **Série temporelle**, puis choisissez **Logs** comme source de données. Sélectionnez **Count of Events** comme agrégation.

    Dans **Where**, sélectionnez **Lucene** et saisissez le filtre suivant :

    ```text
    SeverityText:"error" ServiceName:"payment"
    ```

    Définissez un intervalle de temps couvrant les données d’exemple, puis cliquez sur **Exécuter**.

    <div className="ch-image-lg">
      <Frame>
        ![Explorateur de graphiques comptabilisant au fil du temps les logs d’erreur du service payment à l’aide d’un filtre Lucene](/images/clickstack/getting-started/observability-sample-data-payment-errors-chart.png)
      </Frame>
    </div>

    Le graphique affiche le nombre de logs d’erreur correspondants pour chaque intervalle de temps. Il inclut toutes les erreurs du service `payment`, y compris les erreurs de carte expirée et de cache plein. Il s’agit de nombres d’occurrences d’événements de log, et non du nombre de paiements uniques en échec.
  </Step>
</Steps>
