Envoyez les logs, traces et metrics de vos agents Datadog existants vers ClickHouse Observability. Vos applications peuvent conserver leurs SDK Datadog. Choisissez un endpoint géré ou configurez un récepteur Datadog dans votre propre collecteur, puis suivez les mêmes étapes de configuration de l&#39;Agent décrites ci-dessous.

## Prérequis {#prerequisites}

* Un service ClickHouse Observability géré ou autogéré.
* Un agent Datadog en cours d’exécution qui collecte les signaux que vous souhaitez migrer. Pour les traces, votre application doit déjà envoyer ses traces à cet agent via un SDK Datadog.
* Un accès réseau entre l’agent et l’endpoint de votre récepteur Datadog.

## Configurer votre destination {#connection-details}

<Tabs>
  <Tab title="Entièrement géré">
    <BetaBadge label="Offre bêta" />

    Ouvrez votre service et accédez à **Team Settings → Data → Managed Telemetry**. Copiez l’**OTLP HTTP endpoint** et l’**API key**.

    <div className="ch-image-lg">
      <Frame>
        ![Managed Telemetry affichant l’endpoint OTLP HTTP et l’API key masqués](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    L’endpoint Datadog utilise le même nom d’hôte, avec le port `8126`. Aucun collecteur supplémentaire n’est nécessaire. Utilisez ces valeurs dans la configuration de l’Agent ci-dessous :

    | Paramètre                | Valeur                                 |
    | ------------------------ | -------------------------------------- |
    | `YOUR_API_KEY`           | L’API key d’ingestion de votre service |
    | `YOUR_DATADOG_URL`       | `https://YOUR_OTEL_HOST:8126`          |
    | `YOUR_DATADOG_HOST_PORT` | `YOUR_OTEL_HOST:8126`                  |
    | `logs_no_ssl`            | `false`                                |
  </Tab>

  <Tab title="Autogéré" id="self-managed">
    Le [Collecteur OpenTelemetry ClickStack](/fr/clickstack/self-configured/ingesting-data/collector) inclut le [récepteur Datadog](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/datadogreceiver). Configurez le récepteur et raccordez-le à vos pipelines de logs, de traces et de metrics.

    Enregistrez la surcouche de configuration suivante sous le nom `datadog-collector.yaml`. Elle ajoute le récepteur Datadog aux pipelines de logs, de traces et de metrics existants du collecteur, tout en conservant le récepteur OTLP :

    ```yaml
    receivers:
      datadog:
        endpoint: 0.0.0.0:8126

    service:
      pipelines:
        logs/in:
          receivers: [otlp/hyperdx, datadog]
        traces:
          receivers: [otlp/hyperdx, datadog]
        metrics:
          receivers: [otlp/hyperdx, datadog]
    ```

    Renseignez les informations de connexion ClickHouse, puis démarrez le collecteur. Lors d’un démarrage normal, le schéma de télémétrie est créé dans la base de données spécifiée par `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE` ; l’utilisateur ClickHouse doit donc disposer des droits nécessaires pour créer la base de données et les tables. Si vous disposez déjà d’une base de données de télémétrie, indiquez son nom.

    Cet exemple nécessite Docker, utilise la version `2.40.0` du collecteur et n’expose le récepteur Datadog que sur l’hôte local :

    ```shell
    export CLICKHOUSE_ENDPOINT='https://YOUR_CLICKHOUSE_HOST:8443'
    export CLICKHOUSE_USER='YOUR_CLICKHOUSE_USER'
    export CLICKHOUSE_PASSWORD='YOUR_CLICKHOUSE_PASSWORD'
    export HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE='default'

    docker run --rm --name datadog-collector \
      -e CLICKHOUSE_ENDPOINT \
      -e CLICKHOUSE_USER \
      -e CLICKHOUSE_PASSWORD \
      -e HYPERDX_OTEL_EXPORTER_CLICKHOUSE_DATABASE \
      -e CUSTOM_OTELCOL_CONFIG_FILE=/etc/datadog-collector.yaml \
      -v "$(pwd)/datadog-collector.yaml:/etc/datadog-collector.yaml:ro" \
      -p 127.0.0.1:18126:8126 \
      clickhouse/clickstack-otel-collector:2.40.0
    ```

    Laissez le collecteur s’exécuter dans ce terminal pendant que vous configurez et vérifiez l’Agent. Utilisez un autre terminal pour les commandes suivantes.

    Utilisez ces valeurs pour un Agent s’exécutant sur le même hôte :

    | Paramètre                | Valeur                                                                                       |
    | ------------------------ | -------------------------------------------------------------------------------------------- |
    | `YOUR_API_KEY`           | Une valeur fictive non vide, par exemple `local-test` ; ce récepteur local ne la vérifie pas |
    | `YOUR_DATADOG_URL`       | `http://localhost:18126`                                                                     |
    | `YOUR_DATADOG_HOST_PORT` | `localhost:18126`                                                                            |
    | `logs_no_ssl`            | `true`                                                                                       |

    Le port hôte `18126` permet de distinguer cette destination du point d’écoute de traces applicatives de l’Agent, sur le port `8126`. Pour un Agent conteneurisé, connectez les deux conteneurs au même réseau Docker et utilisez `http://datadog-collector:8126` et `datadog-collector:8126` comme valeurs de destination.

    Cet exemple utilise un point d’écoute HTTP non authentifié, limité à l’hôte local. Pour des Agents situés sur d’autres hôtes, prévoyez un chemin réseau protégé et configurez TLS ainsi que l’authentification au niveau de votre ingress avant d’exposer le récepteur. `OTLP_AUTH_TOKEN` configure l’authentification OTLP du collecteur, mais ne sécurise pas ce point d’écoute Datadog.
  </Tab>
</Tabs>

## Configurer l&#39;agent Datadog {#configure-datadog-agent}

Mettez à jour le [fichier de configuration `datadog.yaml`](https://docs.datadoghq.com/agent/configuration/agent-configuration-files/) de votre agent. Il se trouve généralement dans `/etc/datadog-agent/datadog.yaml` sous Linux et dans `/opt/datadog-agent/etc/datadog.yaml` sous macOS.

Intégrez les paramètres suivants à votre configuration existante, en utilisant les valeurs de destination indiquées dans l&#39;onglet ci-dessus :

```yaml
api_key: "YOUR_API_KEY"

# Metrics destination
dd_url: "YOUR_DATADOG_URL"

# Use the v2 metrics intake.
use_v3_api:
  series:
    enabled: false

# Trace destination
apm_config:
  enabled: true
  apm_dd_url: "YOUR_DATADOG_URL"
  features:
    - disable-convert-traces

# Log destination
logs_enabled: true
logs_config:
  logs_dd_url: "YOUR_DATADOG_HOST_PORT"
  force_use_http: true
  logs_no_ssl: false # Set to true for the local HTTP receiver.

remote_updates: false
remote_configuration:
  enabled: false
```

Remplacez `YOUR_DATADOG_URL` par l’URL de destination complète et `YOUR_DATADOG_HOST_PORT` par son `hostname:port`, sans schéma. Définissez `logs_no_ssl` sur la valeur indiquée pour votre destination.

<Note>
  `disable-convert-traces` assure la compatibilité des charges utiles de traces de l&#39;Agent avec le récepteur Datadog. Avec l&#39;agent Datadog 7.85.2 et le collecteur core 0.155.0, la charge utile indexée par défaut de l&#39;Agent était acceptée avec un code HTTP 200, mais ne produisait aucun span. Utilisez le paramètre ci-dessus pour le transfert des traces et conservez toutes les autres entrées de votre liste `apm_config.features` existante.
</Note>

Conservez vos intégrations de collecte de logs et votre configuration de traçage applicatif existantes. Ces paramètres modifient uniquement la destination vers laquelle l&#39;Agent envoie la télémétrie : ils n&#39;activent pas la collecte de logs pour des applications individuelles et n&#39;ajoutent aucune instrumentation. Si vous configurez l&#39;Agent au moyen de [variables d’environnement](https://docs.datadoghq.com/agent/guide/environment-variables/), mettez également à jour les paramètres correspondants à ce niveau, y compris `DD_API_KEY`.

Cette configuration redirige les logs, traces et metrics de l&#39;Agent de Datadog vers ClickHouse Observability. Pour l&#39;évaluer au préalable, appliquez-la à un Agent de test avant de l&#39;étendre à l&#39;ensemble de votre déploiement.

## Redémarrage et vérification {#restart-and-verify}

Redémarrez l&#39;Agent pour appliquer la configuration. Sous Linux :

```shell
sudo systemctl restart datadog-agent
sudo datadog-agent status
```

Sous macOS :

```shell
sudo launchctl kickstart -k system/com.datadoghq.agent
```

Pour un Agent conteneurisé, mettez à jour sa configuration et redéployez le conteneur.

Générez une nouvelle activité applicative, puis ouvrez ClickHouse Observability et sélectionnez un intervalle de temps récent :

* **Logs :** sélectionnez votre source de logs et filtrez sur le `ServiceName` de l&#39;application.
* **Traces :** sélectionnez votre source de traces et filtrez sur le `ServiceName` de l&#39;application.
* **Metrics :** recherchez une metric émise par votre application ou par l&#39;Agent. Pour un test DogStatsD, émettez une jauge nommée et vérifiez sa valeur.

Si les données n&#39;apparaissent pas, consultez le statut de l&#39;Agent pour repérer d&#39;éventuelles erreurs d&#39;envoi. Vérifiez le nom d’hôte, le port, l&#39;API key et les paramètres d&#39;accès réseau de votre service. Assurez-vous que l&#39;Agent collecte bien le signal concerné et que toute surcharge définie par variable d&#39;environnement pointe vers la même destination.

Pour les traces, recherchez un ID de trace connu plutôt que de vous fier uniquement aux compteurs d&#39;envois réussis de l&#39;Agent. Si un filtre de service masque la trace, recherchez-la par `TraceId` : le récepteur peut utiliser le service de base du traceur comme nom de service de la ressource, tout en conservant une surcharge de service propre à chaque span dans l&#39;attribut de span `service.name`. Définissez `DD_SERVICE` dans la configuration de traçage de votre application afin de fixer son nom de service de base.

## Signaux pris en charge {#supported-signals}

Le récepteur Datadog est expérimental. Il convertit les logs et les traces Datadog, ainsi que les metrics prises en charge, dans le modèle de données OpenTelemetry utilisé par ClickHouse Observability. La configuration ci-dessus utilise l&#39;ingestion des metrics v2 ; les autres fonctionnalités du backend Datadog sortent du cadre de ce processus de migration.

Vous pouvez conserver votre instrumentation Datadog existante tout en migrant progressivement vos applications vers OpenTelemetry.
