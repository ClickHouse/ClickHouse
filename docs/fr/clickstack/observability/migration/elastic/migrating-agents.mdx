## Migration des agents depuis Elastic {#migrating-agents-from-elastic-self-configured}

L&#39;Elastic Stack propose plusieurs agents de collecte de données d&#39;observability, à savoir :

* La [famille Beats](https://www.elastic.co/beats) — notamment [Filebeat](https://www.elastic.co/beats/filebeat), [Metricbeat](https://www.elastic.co/beats/metricbeat) et [Packetbeat](https://www.elastic.co/beats/packetbeat) —, tous basés sur la bibliothèque `libbeat`. Ces Beats prennent en charge [l&#39;envoi de données vers Elasticsearch, Kafka, Redis ou Logstash](https://www.elastic.co/docs/reference/beats/filebeat/configuring-output) via le protocole Lumberjack.
* L&#39;[`Elastic Agent`](https://www.elastic.co/elastic-agent) est un agent unifié capable de collecter des logs, des metrics et des traces. Il peut être géré de manière centralisée via l&#39;[Elastic Fleet Server](https://www.elastic.co/docs/reference/fleet/manage-elastic-agents-in-fleet) et prend en charge l&#39;envoi vers Elasticsearch, Logstash, Kafka ou Redis.
* Elastic propose également une distribution du [Collecteur OpenTelemetry - EDOT](https://www.elastic.co/docs/reference/opentelemetry). Bien qu&#39;elle ne puisse pas, pour l&#39;instant, être orchestrée par le Fleet Server, elle offre une voie plus souple et plus ouverte si vous migrez vers ClickHouse Observability.

La meilleure stratégie de migration dépend des agents actuellement utilisés. Dans les sections suivantes, nous décrivons les options de migration pour chacun des principaux types d&#39;agents. Notre objectif est de limiter au maximum les frictions et, dans la mesure du possible, de vous permettre de continuer à utiliser vos agents existants pendant la transition.

## Chemin de migration recommandé {#prefered-migration-path-self-configured}

Dans la mesure du possible, nous recommandons de migrer vers le [Collecteur OpenTelemetry (OTel)](https://opentelemetry.io/docs/collector/) pour la collecte de l&#39;ensemble des journaux, métriques et traces, en déployant le collecteur [en périphérie, dans un rôle d’agent](/fr/clickstack/self-configured/ingesting-data/collector#collector-roles-self-configured). C&#39;est le moyen le plus efficace d&#39;envoyer des données, tout en évitant la complexité architecturale et la transformation des données.

<Info>
  **Pourquoi le Collecteur OpenTelemetry ?**

  Le Collecteur OpenTelemetry offre une solution pérenne et indépendante des fournisseurs pour l&#39;ingestion des données d&#39;observability. Nous savons que certaines organisations exploitent des parcs de plusieurs milliers, voire de dizaines de milliers, d&#39;agents Elastic. Pour ces utilisateurs, il peut être essentiel de maintenir la compatibilité avec l&#39;infrastructure d&#39;agents existante. Cette documentation vise à répondre à ce besoin, tout en aidant les équipes à migrer progressivement vers une collecte basée sur OpenTelemetry.
</Info>

## Endpoint OpenTelemetry ClickHouse {#clickhouse-otel-endpoint-self-configured}

Configurez la destination avant de suivre les étapes de migration de l’agent. Les exemples Vector et EDOT ci-dessous envoient des données OpenTelemetry via OTLP HTTP.

<Tabs>
  <Tab title="Entièrement géré">
    <BetaBadge label="Offre bêta" />

    Copiez votre endpoint OTLP HTTP et votre API key depuis **Paramètres de l’équipe → Données → Télémétrie gérée**. Définissez ces variables dans l’environnement d’exécution de Vector ou d’EDOT :

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Utilisez l’endpoint tel quel, port compris, sans le suffixe `/v1/logs`. Pour les informations de connexion, consultez [Envoi de données OpenTelemetry](/fr/clickstack/observability/ingesting-data/opentelemetry).
  </Tab>

  <Tab title="Autogéré">
    Déployez votre collecteur de réception en suivant le [guide de configuration autogéré](/fr/clickstack/self-configured/getting-started/managed). Dans l’environnement d’exécution de Vector ou d’EDOT, définissez l’endpoint OTLP HTTP joignable du collecteur ainsi que son en-tête d’autorisation :

    ```shell
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_COLLECTOR_TOKEN'
    ```

    Si vous avez sécurisé le collecteur de réception avec `OTLP_AUTH_TOKEN`, utilisez ce jeton comme valeur d’autorisation. Si l’authentification est désactivée, retirez l’en-tête `authorization` des exemples. Consultez [Sécuriser le collecteur](/fr/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).

    N’utilisez `localhost` que si l’émetteur et le récepteur partagent le même namespace réseau. Pour un récepteur avec TLS activé, utilisez son point de terminaison HTTPS et configurez l’approbation de son certificat.
  </Tab>
</Tabs>

## Migration depuis Beats {#migrating-to-beats-self-configured}

Les utilisateurs disposant de déploiements Beats à grande échelle peuvent souhaiter les conserver lors de leur migration vers ClickHouse Observability.

**À ce jour, cette option n’a été testée qu’avec Filebeat et ne convient donc qu’aux journaux.**

Les agents Beats utilisent l’[Elastic Common Schema (ECS)](https://www.elastic.co/docs/reference/ecs), qui est actuellement [en cours d’intégration dans la spécification OpenTelemetry](https://github.com/open-telemetry/opentelemetry-specification/blob/main/oteps/0199-support-elastic-common-schema-in-opentelemetry.md) utilisée par ClickHouse Observability. Toutefois, ces [schémas diffèrent encore considérablement](https://www.elastic.co/docs/reference/ecs/ecs-otel-alignment-overview), et il incombe pour l’instant aux utilisateurs de convertir les événements au format ECS en événements au format OpenTelemetry avant leur ingestion dans ClickHouse Observability.

Nous recommandons d’effectuer cette transformation à l’aide de [Vector](https://vector.dev), un pipeline de données d’observability léger et performant qui prend en charge un puissant langage de transformation, le Vector Remap Language (VRL).

Si vos agents Filebeat sont configurés pour envoyer des données vers Kafka (une sortie prise en charge par Beats), Vector peut consommer ces événements depuis Kafka, appliquer les transformations de schéma à l’aide de VRL, puis les transmettre via OTLP à votre point de terminaison OTLP configuré.

Vector prend également en charge la réception d’événements via le protocole Lumberjack utilisé par Logstash. Les agents Beats peuvent ainsi envoyer directement leurs données à Vector, qui leur applique le même processus de transformation avant de les transmettre via OTLP à votre point de terminaison OTLP configuré.

Ces deux architectures sont illustrées ci-dessous.

  <Frame>
    ![Agents Beats envoyant des journaux via Vector au collecteur, à ClickHouse et à l’interface utilisateur de ClickStack](/images/use-cases/observability/clickstack-migrating-agents-ui.png)

</div>

Dans l’exemple suivant, nous présentons les premières étapes de configuration de Vector pour recevoir des événements de journal depuis Filebeat via le protocole Lumberjack. Nous fournissons le code VRL permettant de faire correspondre les événements ECS entrants à la spécification OTel, avant de les envoyer via OTLP à votre point de terminaison OTLP configuré. Les utilisateurs qui consomment des événements depuis Kafka peuvent remplacer la source Logstash de Vector par la [source Kafka](https://vector.dev/docs/reference/configuration/sources/kafka/) ; toutes les autres étapes restent identiques.

<Steps>
  <Step title="Installer Vector" id="install-vector-self-configured">
    Installez Vector en suivant le [guide d&#39;installation officiel](https://vector.dev/docs/setup/installation/).

    Installez Vector sur un hôte joignable par vos agents Filebeat.

    Lors du [passage de Vector en production](https://vector.dev/docs/setup/going-to-prod/), vous pouvez suivre les bonnes pratiques en matière d&#39;architecture et de sécurité.
  </Step>

  <Step title="Configurer Vector" id="configure-vector-self-configured">
    Vector doit être configuré pour recevoir des événements via le protocole Lumberjack, en se faisant passer pour une instance Logstash. Pour cela, configurez une [source `logstash`](https://vector.dev/docs/reference/configuration/sources/logstash/) dans Vector :

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
          # The files below are generated from the steps at https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          # crt_file: logstash.crt
          # key_file: logstash.key
          # ca_file: ca.crt
          # verify_certificate: true
    ```

    <Info>
      **Configuration TLS**

      Si le TLS mutuel est requis, générez les certificats et les clés en suivant le guide Elastic [&quot;Configure SSL/TLS for the Logstash output&quot;](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output). Vous pourrez ensuite les indiquer dans la configuration, comme illustré ci-dessus.
    </Info>

    Les événements seront reçus au format ECS. Ils peuvent être convertis dans le schéma OpenTelemetry à l&#39;aide d&#39;un transformateur VRL (Vector Remap Language). Ce transformateur se configure simplement, le script étant placé dans un fichier distinct :

    ```yaml
    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'
    ```

    Notez qu&#39;il reçoit les événements provenant de la source `beats` définie ci-dessus. Notre script `remap` est présenté ci-dessous. Ce script n&#39;a été testé qu&#39;avec des événements de journal, mais il peut servir de base pour d&#39;autres formats.

    <Accordion title="VRL - ECS vers OTel">
      ```javascript
      # Define keys to ignore at root level
      ignored_keys = ["@metadata"]

      # Define resource key prefixes
      resource_keys = ["host", "cloud", "agent", "service"]

      # Create separate objects for resource and log record fields
      resource_obj = {}
      log_record_obj = {}

      # Copy all non-ignored root keys to appropriate objects
      root_keys = keys(.)
      for_each(root_keys) -> |_index, key| {
          if !includes(ignored_keys, key) {
              val, err = get(., [key])
              if err == null {
                  # Check if this is a resource field
                  is_resource = false
                  if includes(resource_keys, key) {
                      is_resource = true
                  }

                  # Add to appropriate object
                  if is_resource {
                      resource_obj = set(resource_obj, [key], val) ?? resource_obj
                  } else {
                      log_record_obj = set(log_record_obj, [key], val) ?? log_record_obj
                  }
              }
          }
      }

      # Flatten both objects separately
      flattened_resources = flatten(resource_obj, separator: ".")
      flattened_logs = flatten(log_record_obj, separator: ".")

      # Process resource attributes
      resource_attributes = []
      resource_keys_list = keys(flattened_resources)
      for_each(resource_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_resources, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  resource_attributes = push(resource_attributes, attribute)
              }
          }
      }

      # Process log record attributes
      log_attributes = []
      log_keys_list = keys(flattened_logs)
      for_each(log_keys_list) -> |_index, field_key| {
          field_value, err = get(flattened_logs, [field_key])
          if err == null && field_value != null {
              attribute, err = {
                  "key": field_key,
                  "value": {
                      "stringValue": to_string(field_value)
                  }
              }
              if (err == null) {
                  log_attributes = push(log_attributes, attribute)
              }
          }
      }

      # Get timestamp for timeUnixNano (convert to nanoseconds)
      timestamp_nano = if exists(.@timestamp) {
          to_unix_timestamp!(parse_timestamp!(.@timestamp, format: "%Y-%m-%dT%H:%M:%S%.3fZ"), unit: "nanoseconds")
      } else {
          to_unix_timestamp(now(), unit: "nanoseconds")
      }

      # Get message/body field
      body_value = if exists(.message) {
          to_string!(.message)
      } else if exists(.body) {
          to_string!(.body)
      } else {
          ""
      }

      # Create the OpenTelemetry structure
      . = {
          "resourceLogs": [
              {
                  "resource": {
                      "attributes": resource_attributes
                  },
                  "scopeLogs": [
                      {
                          "scope": {},
                          "logRecords": [
                              {
                                  "timeUnixNano": to_string(timestamp_nano),
                                  "severityNumber": 9,
                                  "severityText": "info",
                                  "body": {
                                      "stringValue": body_value
                                  },
                                  "attributes": log_attributes
                              }
                          ]
                      }
                  ]
              }
          ]
      }
      ```
    </Accordion>

    Enfin, envoyez les événements transformés vers votre point de terminaison OTLP configuré. Cela nécessite la configuration d&#39;une destination OTLP dans Vector, qui prend en entrée les événements issus de la transformation `remap_filebeat` :

    ```yaml
    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat] # receives events from a remap transform - see below
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```

    Utilisez les [variables de connexion](#clickhouse-otel-endpoint-self-configured) de votre déploiement. L&#39;URI de Vector inclut `/v1/logs`, car cette sortie envoie des enregistrements de log.

    Voici la configuration finale complète :

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: false  # Set to true if you're using TLS
            #crt_file: /data/elasticsearch-9.0.1/logstash/logstash.crt
            #key_file: /data/elasticsearch-9.0.1/logstash/logstash.key
            #ca_file: /data/elasticsearch-9.0.1/ca/ca.crt
            #verify_certificate: true

    transforms:
      remap_filebeat:
        inputs: ["beats"]
        type: "remap"
        file: 'beat_to_otel.vrl'

    sinks:
      otlp:
        type: opentelemetry
        inputs: [remap_filebeat]
        protocol:
          type: http
          uri: "${OTEL_EXPORTER_OTLP_ENDPOINT}/v1/logs"
          method: post
          encoding:
            codec: json
          framing:
            method: newline_delimited
          headers:
            content-type: application/json
            authorization: "${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
    ```
  </Step>

  <Step title="Configurer Filebeat" id="configure-filebeat-self-configured">
    Configurez Filebeat pour qu’il utilise la sortie Logstash vers Vector, en remplaçant toute configuration de sortie existante. Remplacez `YOUR_VECTOR_HOST` par l’hôte qui exécute Vector ; n’utilisez `localhost` que si les deux s’exécutent sur le même hôte. Configurez TLS de façon à correspondre à l’entrée Vector :

    ```yaml
    # ------------------------------ Logstash Output -------------------------------
    output.logstash:
      # The Logstash hosts
      hosts: ["YOUR_VECTOR_HOST:5044"]

      # Optional SSL. By default is off.
      # List of root certificates for HTTPS server verifications
      #ssl.certificate_authorities: ["/etc/pki/root/ca.pem"]

      # Certificate for SSL client authentication
      #ssl.certificate: "/etc/pki/client/cert.pem"

      # Client Certificate Key
      #ssl.key: "/etc/pki/client/cert.key"
    ```
  </Step>
</Steps>

## Migration depuis Elastic Agent {#migrating-from-elastic-agent-self-configured}

Elastic Agent regroupe les différents Elastic Beats en un seul paquet. Cet agent s&#39;intègre à [Elastic Fleet](https://www.elastic.co/docs/reference/fleet/fleet-server), ce qui permet de l&#39;orchestrer et de le configurer de manière centralisée.

Les utilisateurs ayant déployé des Elastic Agents disposent de plusieurs options de migration :

* Configurer l&#39;agent pour qu&#39;il envoie les données vers un endpoint Vector via le protocole Lumberjack. **Cette approche n&#39;a pour l&#39;instant été testée que pour la collecte de données de journaux avec Elastic Agent.** Elle peut être configurée de manière centralisée depuis l&#39;UI Fleet de Kibana.
* [Exécuter l&#39;agent en tant qu&#39;Elastic OpenTelemetry Collector (EDOT)](https://www.elastic.co/docs/reference/fleet/otel-agent). Elastic Agent inclut un EDOT Collector intégré qui vous permet d&#39;instrumenter une seule fois vos applications et votre infrastructure, puis d&#39;envoyer les données à plusieurs fournisseurs et backends. Dans cette configuration, il suffit de configurer le collecteur EDOT pour qu&#39;il transfère les événements via OTLP vers le point de terminaison OTLP que vous avez configuré. **Cette approche prend en charge tous les types d&#39;événements.**

Nous présentons ces deux options ci-dessous.

### Envoi des données via Vector {#sending-data-via-vector-self-configured}

<Steps>
  <Step title="Installer et configurer Vector" id="install-configure-vector-self-configured">
    Installez et configurez Vector en suivant les [mêmes étapes](#install-vector-self-configured) que celles décrites pour la migration depuis Filebeat.
  </Step>

  <Step title="Configurer Elastic Agent" id="configure-elastic-agent-self-configured">
    Elastic Agent doit être configuré pour envoyer les données via Lumberjack, le protocole de Logstash. Il s&#39;agit d&#39;un [modèle de déploiement pris en charge](https://www.elastic.co/docs/manage-data/ingest/ingest-reference-architectures/ls-networkbridge), qui peut être configuré de manière centralisée ou [via le fichier de configuration de l&#39;agent `elastic-agent.yaml`](https://www.elastic.co/docs/reference/fleet/logstash-output) en cas de déploiement sans Fleet.

    Pour une configuration centralisée via Kibana, il suffit d&#39;ajouter [une sortie à Fleet](https://www.elastic.co/docs/reference/fleet/fleet-settings#output-settings).

    <div className="ch-image-md">
      <Frame>
        ![Ajouter une sortie Logstash](/images/use-cases/observability/add-logstash-output.webp)
      </Frame>
    </div>

    Cette sortie peut ensuite être utilisée dans une [politique d&#39;agent](https://www.elastic.co/docs/reference/fleet/agent-policy). Tous les agents utilisant cette politique enverront alors automatiquement leurs données à Vector.

    <div className="ch-image-md">
      <Frame>
        ![Paramètres de l'agent](/images/use-cases/observability/agent-output-settings.webp)
      </Frame>
    </div>

    Comme cette configuration exige une communication sécurisée via TLS, nous recommandons de suivre le guide [« Configure SSL/TLS for the Logstash output »](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#use-ls-output), en considérant que votre instance Vector joue le rôle de Logstash.

    Notez que la source Logstash dans Vector doit alors elle aussi être configurée pour utiliser le TLS mutuel. Utilisez les clés et certificats [générés dans le guide](https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs) pour configurer l&#39;entrée en conséquence.

    ```yaml
    sources:
      beats:
        type: logstash
        address: 0.0.0.0:5044
        tls:
          enabled: true  # Définir à true si vous utilisez TLS.
          # Les fichiers ci-dessous sont générés en suivant les étapes décrites sur https://www.elastic.co/docs/reference/fleet/secure-logstash-connections#generate-logstash-certs
          crt_file: logstash.crt
          key_file: logstash.key
          ca_file: ca.crt
          verify_certificate: true
    ```
  </Step>
</Steps>

### Exécuter Elastic Agent en tant que collecteur OpenTelemetry {#run-agent-as-otel-self-configured}

Elastic Agent intègre un EDOT Collector qui vous permet d&#39;instrumenter vos applications et votre infrastructure une seule fois, puis d&#39;envoyer les données vers plusieurs fournisseurs et backends.

<Info>
  **Intégrations et orchestration de l&#39;agent**

  Les utilisateurs qui exécutent le collecteur EDOT fourni avec Elastic Agent ne pourront pas tirer parti des [intégrations existantes proposées par l&#39;agent](https://www.elastic.co/docs/reference/fleet/manage-integrations). De plus, le collecteur ne peut pas être géré de manière centralisée par Fleet, ce qui oblige l&#39;utilisateur à exécuter l&#39;[agent en mode autonome](https://www.elastic.co/docs/reference/fleet/configure-standalone-elastic-agents) et à gérer lui-même la configuration.
</Info>

Pour exécuter Elastic Agent avec le collecteur EDOT, suivez le [guide officiel d&#39;Elastic](https://www.elastic.co/docs/reference/fleet/otel-agent-transform). Configurez un exportateur OTLP HTTP à l&#39;aide de vos [variables de connexion](#clickhouse-otel-endpoint-self-configured) :

```yaml
exporters:
  otlphttp/clickhouse:
    endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
    headers:
      authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
```

Ajoutez `otlphttp/clickhouse` à la liste `exporters` de chaque pipeline de logs, de metrics ou de traces que vous souhaitez transférer. Conservez les récepteurs et processeurs existants. Pour une ingestion en parallèle, conservez l’exportateur Elastic dans ces pipelines ; supprimez-le lorsque vous serez prêt à cesser l’envoi vers Elastic.

L’exportateur utilise l’endpoint de base et y ajoute automatiquement le path propre à chaque signal. Pour un récepteur HTTPS utilisant une autorité de certification privée, configurez `tls.ca_file` ; si ce récepteur exige le TLS mutuel, configurez également `tls.cert_file` et `tls.key_file`. Ces paramètres sécurisent la connexion entre EDOT et OTLP indépendamment de la configuration TLS entre Filebeat et Vector.

## Migration depuis l’Elastic OpenTelemetry Collector {#migrating-from-elastic-otel-collector-self-configured}

Si vous utilisez déjà l’[Elastic OpenTelemetry Collector (EDOT)](https://www.elastic.co/docs/reference/opentelemetry), il vous suffit de reconfigurer vos agents pour qu’ils envoient les données via OTLP vers le point de terminaison OTLP que vous avez configuré. La procédure est identique à celle décrite ci-dessus pour exécuter l’[Elastic Agent en tant que collecteur OpenTelemetry](#run-agent-as-otel-self-configured). Cette approche s’applique à tous les types de données.
