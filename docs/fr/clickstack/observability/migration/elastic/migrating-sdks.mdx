L&#39;Elastic Stack propose deux types de SDK par langage pour instrumenter les applications :

1. **[Agents APM officiels d&#39;Elastic](https://www.elastic.co/docs/reference/apm-agents/)** – Ils sont conçus spécifiquement pour l&#39;Elastic Stack. Pour ces agents, prévoyez une transition vers l&#39;[instrumentation OpenTelemetry](https://opentelemetry.io/docs/languages/) propre à votre langage, y compris pour les spans et attributs personnalisés utilisés par votre application.

2. **[Elastic Distributions of OpenTelemetry (SDK EDOT)](https://www.elastic.co/docs/reference/opentelemetry/edot-sdks/)** – Il s&#39;agit des distributions Elastic des SDK OpenTelemetry standard, disponibles pour .NET, Java, Node.js, PHP et Python. Si votre application utilise déjà un SDK EDOT, inutile de réinstrumenter votre code : il vous suffit de reconfigurer le SDK pour qu&#39;il exporte les données de télémétrie vers le point de terminaison OTLP de ClickHouse Observability. Pour plus de détails, consultez la section [« Migration des SDK EDOT »](#migrating-edot-sdks-self-configured).

## Migration des SDK EDOT {#migrating-edot-sdks-self-configured}

Les Elastic Distributions of OpenTelemetry SDKs (SDK EDOT) sont des versions personnalisées des SDK OpenTelemetry officiels. Par exemple, l’[EDOT Python SDK](https://www.elastic.co/docs/reference/opentelemetry/edot-sdks/python/) est une distribution du [SDK OpenTelemetry pour Python](https://opentelemetry.io/docs/languages/python/) adaptée par un fournisseur et conçue pour fonctionner de manière transparente avec Elastic Observability.

Comme ces SDK reposent sur les bibliothèques OpenTelemetry standard, la migration vers ClickHouse Observability est simple : il n’est pas nécessaire de réinstrumenter vos applications. Il vous suffit d’ajuster la configuration afin d’acheminer les données de télémétrie vers votre point de terminaison OTLP ClickHouse Observability.

La configuration repose sur les mécanismes standard d’OpenTelemetry. Pour Python, elle s’effectue généralement au moyen de variables d’environnement, comme décrit dans la [documentation OpenTelemetry sur l’instrumentation sans code](https://opentelemetry.io/docs/zero-code/python/configuration/).

Une configuration typique d’un SDK EDOT peut ressembler à ceci :

```shell
export OTEL_RESOURCE_ATTRIBUTES='service.name=YOUR_APP_NAME'
export OTEL_EXPORTER_OTLP_ENDPOINT=https://my-deployment.ingest.us-west1.gcp.cloud.es.io
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=ApiKey P....l"
```

Pour effectuer la migration, mettez à jour les paramètres de connexion OTLP dans l&#39;environnement de votre application, puis redémarrez celle-ci. Les exemples ci-dessous utilisent OTLP HTTP avec l&#39;encodage protobuf.

<Tabs>
  <Tab title="Entièrement géré">
    <BetaBadge label="Offre bêta" />

    Copiez le point de terminaison OTLP HTTP et l&#39;API key depuis **Team Settings → Data → Managed Telemetry** :

    ```shell
    export OTEL_RESOURCE_ATTRIBUTES='service.name=YOUR_APP_NAME'
    export OTEL_EXPORTER_OTLP_PROTOCOL='http/protobuf'
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_HEADERS='authorization=Bearer%20YOUR_API_KEY'
    ```

    Utilisez l&#39;endpoint exact, port compris, sans suffixe de signal tel que `/v1/traces`. Dans la valeur d’en-tête, `%20` encode l&#39;espace qui suit `Bearer`. Consultez [Envoyer des données OpenTelemetry](/fr/clickstack/observability/ingesting-data/opentelemetry) pour obtenir les informations de connexion.
  </Tab>

  <Tab title="Autogéré">
    Faites pointer le SDK vers le point de terminaison OTLP HTTP joignable de votre collecteur de réception :

    ```shell
    export OTEL_RESOURCE_ATTRIBUTES='service.name=YOUR_APP_NAME'
    export OTEL_EXPORTER_OTLP_PROTOCOL='http/protobuf'
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_HEADERS='authorization=YOUR_COLLECTOR_TOKEN'
    ```

    Si vous avez sécurisé le collecteur de réception avec `OTLP_AUTH_TOKEN`, utilisez ce jeton comme valeur d&#39;autorisation. N&#39;utilisez `localhost` que si l&#39;application et le collecteur partagent le même namespace réseau. Pour un collecteur où TLS est activé, utilisez son point de terminaison HTTPS et configurez le SDK pour qu&#39;il fasse confiance à son certificat. Consultez [Sécuriser le collecteur](/fr/clickstack/self-configured/ingesting-data/collector#securing-the-collector-self-configured).

    Si l&#39;authentification du collecteur est désactivée, supprimez l&#39;ancien en-tête Elastic :

    ```shell
    unset OTEL_EXPORTER_OTLP_HEADERS
    ```
  </Tab>
</Tabs>

Si votre application définit des variables de point de terminaison, de protocole ou d&#39;en-tête OTLP propres à un signal, mettez-les également à jour : elles priment sur les paramètres génériques ci-dessus. Conservez vos attributs de ressource existants lorsque vous définissez le nom du service.
