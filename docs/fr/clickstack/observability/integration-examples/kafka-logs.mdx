Collectez les logs du broker Kafka avec le récepteur OpenTelemetry `filelog` et envoyez-les vers ClickHouse Observability. Utilisez le [jeu de données de démonstration](#demo-dataset) pour tester l&#39;intégration sans avoir à déployer Kafka.

## Prérequis {#prerequisites}

* Un service ClickHouse Observability
* Docker et `curl`
* Pour vos propres logs, un accès aux fichiers de log du broker Kafka respectant le format ci-dessous

### Informations de connexion {#connection-details}

<Tabs>
  <Tab title="Entièrement géré">
    <BetaBadge label="Offre en version bêta" />

    Ouvrez ClickHouse Observability et accédez à **Paramètres de l’équipe → Data → Télémétrie gérée**. Copiez votre point de terminaison OTLP HTTP et votre API key. Vous pouvez utiliser **Copier les informations de connexion** pour copier la configuration, ou **Reveal key** pour afficher la clé masquée.

    <div className="ch-image-lg">
      <Frame>
        ![Informations de connexion de la télémétrie gérée](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Pour les exemples d’exportateur OTLP ci-dessous, définissez ces variables dans le terminal depuis lequel vous exécuterez le collecteur :

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Remplacez les caractères de substitution par l’endpoint exact de votre service, port compris, ainsi que par son API key. Utilisez l’endpoint HTTP de base, sans le suffixe `/v1/logs` : l’exportateur ajoute lui-même le chemin propre à chaque signal.
  </Tab>

  <Tab title="Autogéré">
    Utilisez le point de terminaison OTLP HTTP de votre collecteur, qui doit être joignable (par exemple, `http://YOUR_COLLECTOR_HOST:4318`), ainsi que vos paramètres d’authentification. Si votre collecteur n’exige pas d’authentification, supprimez le bloc `headers` de l’exportateur dans les configurations ci-dessous. Pour la mise en place, consultez le [guide de démarrage autogéré](/fr/clickstack/self-configured/getting-started/managed).

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

L’endpoint doit être joignable depuis le conteneur du collecteur. Si le collecteur de destination s’exécute sur cette même machine, utilisez `http://host.docker.internal:4318`. Les commandes Docker ci-dessous incluent la correspondance d’hôte nécessaire.

## Intégration avec un cluster Kafka existant {#existing-kafka}

<Steps>
  <Step title="Vérifiez la configuration de la journalisation de Kafka" id="verify-kafka">
    Repérez les journaux du broker. Selon votre installation et votre configuration de journalisation, ils se trouvent généralement dans `$KAFKA_HOME/logs` ou `/var/log/kafka` :

    ```bash
    ls "$KAFKA_HOME/logs/"
    ls /var/log/kafka/
    ```

    Les fichiers les plus courants sont `server.log` (événements du broker), `controller.log` (événements du contrôleur) et `state-change.log` (transitions de partitions et de répliques). Ces fichiers distincts n&#39;existent que s&#39;ils sont configurés dans vos appenders de journalisation.

    Le parseur utilisé dans ce guide attend le format texte Log4j suivant :

    ```text
    [2026-03-09 14:23:45,123] INFO [KafkaServer id=0] started (kafka.server.KafkaServer)
    ```

    Si votre broker écrit ses journaux uniquement sur stdout, configurez un appender de fichier dans la configuration de journalisation du broker et partagez ce répertoire avec le collecteur. Le récepteur `filelog` ne lit pas directement la sortie stdout du conteneur. Adaptez le parseur si votre motif de journalisation est différent.
  </Step>

  <Step title="Configurer le collecteur" id="configure-collector">
    Enregistrez ce fichier sous le nom `kafka-logs-monitoring.yaml` :

    ```yaml
    receivers:
      filelog/kafka:
        include:
          - /var/log/kafka/server.log
          - /var/log/kafka/controller.log
          - /var/log/kafka/state-change.log
        start_at: end
        force_flush_period: 1s
        multiline:
          line_start_pattern: '^\[\d{4}-\d{2}-\d{2}'
        operators:
          - type: regex_parser
            regex: '(?s)^\[(?P<timestamp>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2},\d{3})\] (?P<severity>\w+) (?P<message>.*)$'
            parse_from: body
            parse_to: attributes
            timestamp:
              parse_from: attributes.timestamp
              layout: '%Y-%m-%d %H:%M:%S,%L'
              location: UTC
            severity:
              parse_from: attributes.severity
          - type: move
            from: attributes.message
            to: body
          - type: add
            field: attributes.source
            value: kafka
          - type: add
            field: resource["service.name"]
            value: kafka-service
    processors:
      memory_limiter:
        check_interval: 1s
        limit_mib: 400
        spike_limit_mib: 100
      transform/kafka:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(log.severity_text, ToLowerCase(log.severity_text))
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs/kafka:
          receivers: [filelog/kafka]
          processors: [memory_limiter, transform/kafka, batch]
          exporters: [otlp_http/observability]
    ```

    Définissez `location` sur le fuseau horaire utilisé par les journaux de votre broker ; l’exemple part du principe qu’il s’agit d’UTC. Les entrées multilignes conservent l’intégralité de leurs traces de pile. Le collecteur lit les nouvelles entrées avec `start_at: end` et convertit le texte de sévérité en minuscules.
  </Step>

  <Step title="Exécutez le collecteur" id="run-collector">
    Définissez les [variables de connexion](#connection-details), puis exécutez la commande depuis le répertoire de configuration. Adaptez si nécessaire le chemin des journaux sur l&#39;hôte. Pour les fichiers accessibles en lecture par un groupe, ajoutez `--group-add LOG_GROUP_ID` avec l&#39;identifiant numérique du groupe affiché par `ls -ln /var/log/kafka`.

    ```bash
    docker run --rm --name kafka-logs-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/kafka-logs-monitoring.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      -v /var/log/kafka:/var/log/kafka:ro \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```

    Laissez le terminal ouvert et générez de l&#39;activité sur le broker afin de produire de nouvelles entrées de log. Une fois les tests terminés, arrêtez avec **Ctrl+C**.
  </Step>

  <Step title="Vérifier les logs" id="verify-logs">
    Ouvrez **Recherche**, sélectionnez **Logs**, filtrez sur `ServiceName:kafka-service`, puis sélectionnez **Last 15 minutes**. Les messages du broker devraient s&#39;afficher avec leurs timestamps analysés et leur niveau de sévérité.
  </Step>
</Steps>

## Jeu de données de démonstration {#demo-dataset}

L&#39;échantillon contient 6,376 entrées de journal de broker Kafka couvrant environ 24 heures. Le collecteur actualise leurs timestamps tout en conservant les messages et les traces de pile.

<Steps>
  <Step title="Télécharger l'échantillon" id="download-sample">
    ```bash
    curl -fL -o server.log \
      https://datasets-documentation.s3.eu-west-3.amazonaws.com/clickstack-integrations/kafka/server.log
    ```
  </Step>

  <Step title="Configurer le collecteur de démonstration" id="configure-demo">
    Enregistrez ce qui suit sous `kafka-logs-demo.yaml` :

    ```yaml
    receivers:
      filelog/kafka:
        include:
          - /var/log/kafka/server.log
        start_at: beginning
        force_flush_period: 1s
        multiline:
          line_start_pattern: '^\[\d{4}-\d{2}-\d{2}'
        operators:
          - type: regex_parser
            regex: '(?s)^\[(?P<timestamp>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2},\d{3})\] (?P<severity>\w+) (?P<message>.*)$'
            parse_from: body
            parse_to: attributes
            timestamp:
              parse_from: attributes.timestamp
              layout: '%Y-%m-%d %H:%M:%S,%L'
              location: UTC
            severity:
              parse_from: attributes.severity
          - type: move
            from: attributes.message
            to: body
          - type: add
            field: attributes.source
            value: kafka-demo
          - type: add
            field: resource["service.name"]
            value: kafka-demo
    processors:
      memory_limiter:
        check_interval: 1s
        limit_mib: 400
        spike_limit_mib: 100
      transform/kafka:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(log.severity_text, ToLowerCase(log.severity_text))
      transform/demo_timestamps:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(log.time, Now() - Duration("2m") - (Time("2026-03-09T23:59:58.180Z", "%Y-%m-%dT%H:%M:%S.%LZ") - log.time))
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs/kafka:
          receivers: [filelog/kafka]
          processors: [memory_limiter, transform/kafka, transform/demo_timestamps, batch]
          exporters: [otlp_http/observability]
    ```
  </Step>

  <Step title="Exécuter le collecteur de démonstration" id="run-demo">
    Définissez les [variables de connexion](#connection-details), puis exécutez la commande suivante depuis le répertoire contenant les deux fichiers :

    ```bash
    docker run --rm --name kafka-logs-demo-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/kafka-logs-demo.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      -v "$(pwd)/server.log:/var/log/kafka/server.log:ro" \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```

    Laissez le terminal ouvert pendant que vous vérifiez l&#39;ingestion. Une fois terminé, arrêtez le collecteur avec **Ctrl+C**. Si vous relancez la démonstration, l&#39;échantillon est de nouveau ingéré avec des timestamps actualisés.
  </Step>

  <Step title="Vérifier les logs de démonstration" id="verify-demo">
    Ouvrez **Recherche**, sélectionnez **Logs**, filtrez sur `ServiceName:kafka-demo`, puis sélectionnez **Last 2 days**.

    <div className="ch-image-lg">
      <Frame>
        ![Logs de démonstration Kafka avec la sévérité analysée dans la page Recherche de ClickHouse Observability](/images/clickstack/observability-kafka-demo-logs.png)
      </Frame>
    </div>
  </Step>
</Steps>

## Dépannage {#troubleshooting}

### Aucun log n’apparaît {#no-logs}

Consultez la sortie du collecteur pour repérer d’éventuelles erreurs de permission sur les fichiers, d’analyse, d’authentification ou d’exportation. Vérifiez que votre broker écrit bien dans le répertoire monté et que les noms de fichiers correspondent à la liste `include` du récepteur. La configuration active ne lit que les nouvelles entrées.

### Les logs ne sont pas analysés correctement {#parsing-errors}

Comparez une entrée de journal du broker avec le format attendu :

```bash
tail -n 20 /var/log/kafka/server.log
```

Adaptez l&#39;expression régulière et le motif de début multiligne si le format de vos journaux est différent. Définissez le paramètre `location` du parseur de timestamp sur le fuseau horaire utilisé pour la journalisation de votre broker.
