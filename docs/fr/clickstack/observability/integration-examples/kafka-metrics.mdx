Collectez les métriques des brokers Kafka avec le JMX Metric Gatherer d&#39;OpenTelemetry et envoyez-les vers ClickHouse Observability. Utilisez le [jeu de données de démonstration](#demo-dataset) pour tester l&#39;intégration sans avoir à déployer Kafka.

## Prérequis {#prerequisites}

* Un service ClickHouse Observability
* Docker avec Docker Compose, ainsi que `curl`
* Pour collecter vos propres métriques, un broker Kafka dont le JMX distant est activé et joignable depuis le gatherer

### Informations de connexion {#connection-details}

<Tabs>
  <Tab title="Entièrement géré">
    <BetaBadge label="Offre en version bêta" />

    Ouvrez ClickHouse Observability et accédez à **Paramètres de l’équipe → Data → Télémétrie gérée**. Copiez votre point de terminaison OTLP HTTP et votre API key. Vous pouvez utiliser **Copy connection details** pour copier la configuration, ou **Reveal key** pour afficher la clé masquée.

    <div className="ch-image-lg">
      <Frame>
        ![Informations de connexion de la télémétrie gérée](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Définissez ces variables dans le terminal depuis lequel vous exécuterez le gatherer JMX ou le collecteur de démonstration :

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Remplacez les caractères de substitution par l’endpoint exact de votre service, port compris, ainsi que par votre API key. Utilisez l’endpoint HTTP de base, sans le suffixe `/v1/metrics` : l’exportateur ajoute lui-même le chemin du signal.
  </Tab>

  <Tab title="Autogéré">
    Utilisez le point de terminaison OTLP HTTP joignable de votre collecteur (par exemple, `http://YOUR_COLLECTOR_HOST:4318`) ainsi que ses paramètres d’authentification. Si votre collecteur n’exige pas d’authentification, omettez l’argument `-Dotel.exporter.otlp.headers` du gatherer JMX et le bloc `headers` du collecteur de démonstration. Pour la mise en place, consultez le [guide de démarrage en mode autogéré](/fr/clickstack/self-configured/getting-started/managed).

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

L’endpoint doit être joignable depuis le conteneur du gatherer ou du collecteur. Si le collecteur de destination s’exécute sur cette machine, utilisez `http://host.docker.internal:4318`. Les commandes Docker ci-dessous incluent la correspondance d’hôte.

## Intégration avec un déploiement Kafka existant {#existing-kafka}

<Steps>
  <Step title="Vérifier l’endpoint JMX du broker" id="verify-jmx">
    Utilisez l’endpoint JMX distant configuré pour votre broker. Par exemple, pour un broker qui expose JMX sur le port `9999` :

    ```bash
    export KAFKA_JMX_URL='service:jmx:rmi:///jndi/rmi://YOUR_KAFKA_HOST:9999/jmxrmi'
    export KAFKA_BROKER_ID='broker-0'
    ```

    Remplacez le nom d’hôte et l’ID du broker par vos propres valeurs. Le nom d’hôte RMI annoncé par le broker doit également être joignable depuis le gatherer. Si le broker utilise des ports distincts pour le registre et pour RMI, ouvrez-les tous les deux au niveau du réseau. Le gatherer lit uniquement JMX ; il n’a pas besoin du port client Kafka `9092`.

    Pour des conteneurs situés sur un réseau Docker partagé, utilisez le nom d’hôte du conteneur du broker. Pour un broker exécuté sur l’hôte Docker, utilisez `host.docker.internal` et configurez le broker pour qu’il annonce un nom d’hôte joignable par le conteneur. Limitez l’accès JMX à votre réseau de supervision et conservez les paramètres d’authentification et TLS de votre broker.
  </Step>

  <Step title="Télécharger le JMX Metric Gatherer" id="download-jmx">
    ```bash
    curl -fL -o opentelemetry-jmx-metrics.jar \
      https://github.com/open-telemetry/opentelemetry-java-contrib/releases/download/v1.32.0/opentelemetry-jmx-metrics.jar
    ```
  </Step>

  <Step title="Configurer le gatherer" id="configure-gatherer">
    Enregistrez le contenu suivant dans un fichier `compose.yaml`, à côté du JAR téléchargé :

    ```yaml
    services:
      kafka-jmx-gatherer:
        image: eclipse-temurin:11-jre
        extra_hosts:
          - "host.docker.internal:host-gateway"
        environment:
          - KAFKA_JMX_URL
          - KAFKA_BROKER_ID
          - OTEL_EXPORTER_OTLP_ENDPOINT
          - OTEL_EXPORTER_OTLP_AUTHORIZATION
        volumes:
          - ./opentelemetry-jmx-metrics.jar:/app/opentelemetry-jmx-metrics.jar:ro
        command:
          - sh
          - -c
          - >-
            exec java
            -Dotel.jmx.service.url="$${KAFKA_JMX_URL}"
            -Dotel.jmx.target.system=kafka
            -Dotel.jmx.interval.milliseconds=10000
            -Dotel.metrics.exporter=otlp
            -Dotel.exporter.otlp.protocol=http/protobuf
            -Dotel.exporter.otlp.endpoint="$${OTEL_EXPORTER_OTLP_ENDPOINT}"
            -Dotel.exporter.otlp.headers="authorization=$${OTEL_EXPORTER_OTLP_AUTHORIZATION}"
            -Dotel.resource.attributes="service.name=kafka-service,kafka.broker.id=$${KAFKA_BROKER_ID}"
            -jar /app/opentelemetry-jmx-metrics.jar
    ```

    Si le broker se trouve sur un réseau Docker existant, rattachez `kafka-jmx-gatherer` à ce réseau dans votre configuration Compose. Si l’accès JMX est authentifié, ajoutez les propriétés `otel.jmx.username` et `otel.jmx.password` ; pour TLS, configurez le magasin de confiance approprié. Consultez la [configuration de l’authentification et de TLS du gatherer](https://github.com/open-telemetry/opentelemetry-java-contrib/tree/v1.32.0/jmx-metrics#configuration).
  </Step>

  <Step title="Démarrer la collecte" id="run-gatherer">
    Définissez les [variables de connexion](#connection-details) et les variables du broker dans ce terminal, puis exécutez la commande suivante depuis le répertoire contenant `compose.yaml` :

    ```bash
    docker compose up kafka-jmx-gatherer
    ```

    Laissez le terminal ouvert et surveillez d’éventuelles erreurs de connexion JMX ou d’exportation OTLP. Le gatherer effectue une collecte toutes les 10 secondes : attendez au moins deux intervalles de collecte avant de vérifier votre service. Une fois les tests terminés, arrêtez-le avec **Ctrl+C**.

    Si vous avez plusieurs brokers, exécutez un gatherer par broker, chacun avec sa propre URL JMX et son propre `kafka.broker.id`.
  </Step>

  <Step title="Vérifier les métriques" id="verify-metrics">
    Ouvrez l’**Explorateur de graphiques**, sélectionnez votre source **Metrics**, filtrez sur `ServiceName:kafka-service` et sélectionnez **Last 15 minutes**. Recherchez `kafka.partition.count`, `kafka.partition.under_replicated` ou `kafka.message.count`. Les métriques liées au trafic ne produisent des valeurs significatives que si le broker est actif.
  </Step>
</Steps>

## Jeu de données de démonstration {#demo-dataset}

L’échantillon contient 6,282 points de jauge et de somme, relevés toutes les cinq minutes sur environ 29 heures. Il reproduit fidèlement les tendances du jeu de données d’origine : pics de trafic, latence des requêtes, retard du consommateur et état de santé des partitions. Aucun déploiement Kafka ni accès direct à la base de données n’est nécessaire.

Définissez les [variables de connexion](#connection-details) avant de commencer.

<Steps>
  <Step title="Télécharger les métriques d’exemple" id="download-sample">
    [Téléchargez l’archive d’exemple](/fr/assets/kafka-metrics-demo.zip) (environ 53 Ko) et extrayez `kafka-metrics-demo.json` dans votre répertoire de travail.
  </Step>

  <Step title="Configurer le collecteur de démonstration" id="configure-demo-collector">
    Enregistrez ce qui suit sous le nom `kafka-metrics-demo.yaml` :

    ```yaml
    receivers:
      otlp:
        protocols:
          http:
            endpoint: 0.0.0.0:4318
    processors:
      resource/demo:
        attributes:
          - key: service.name
            value: kafka-demo
            action: upsert
      transform/demo_timestamps:
        error_mode: propagate
        metric_statements:
          - context: datapoint
            statements:
              - set(cache["interval_ns"], time_unix_nano - start_time_unix_nano)
              - set(time, Now() - Duration("2m") - (Time("2025-11-06T22:14:00Z", "%Y-%m-%dT%H:%M:%SZ") - time))
              - set(start_time_unix_nano, time_unix_nano - cache["interval_ns"])
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/managed:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        metrics:
          receivers: [otlp]
          processors: [resource/demo, transform/demo_timestamps, batch]
          exporters: [otlp_http/managed]
    ```

    <Note>
      La transformation, propre à la démonstration, actualise les timestamps tout en préservant les valeurs des métriques et l’intervalle entre les timestamps de début et de fin de chaque point. Supprimez-la pour des métriques Kafka réelles. La limite de batch permet de conserver des envois suffisamment petits pour le collecteur de destination.
    </Note>
  </Step>

  <Step title="Exécuter le collecteur de démonstration" id="run-demo-collector">
    Depuis le répertoire contenant la configuration, lancez le collecteur et laissez ce terminal ouvert :

    ```bash
    docker run --rm --name kafka-metrics-demo-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -p 127.0.0.1:14318:4318 \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/kafka-metrics-demo.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```
  </Step>

  <Step title="Envoyer l’échantillon" id="load-metrics">
    Dans un autre terminal, exécutez cette commande depuis le répertoire de téléchargement :

    ```bash
    curl --fail-with-body -sS http://localhost:14318/v1/metrics \
      -H 'Content-Type: application/json' \
      --data-binary @kafka-metrics-demo.json
    ```

    Une réponse telle que `{}` ou `{"partialSuccess":{}}` indique que le collecteur local a accepté la requête. Vérifiez l’absence d’erreurs d’exportation dans le terminal du collecteur et patientez quelques secondes, le temps du transfert. Une fois les données vérifiées, arrêtez le collecteur avec **Ctrl+C**. Renvoyer l’échantillon peut créer des points en double.
  </Step>

  <Step title="Vérifier les métriques" id="verify-demo-metrics">
    Importez le tableau de bord présenté dans la [section suivante](#dashboards), filtrez sur `ServiceName:kafka-demo` et sélectionnez **2 derniers jours**. L’échantillon comprend à la fois des métriques de type jauge et somme ; aucun accès direct à la base de données n’est nécessaire.
  </Step>
</Steps>

## Dépannage {#troubleshooting}

### Échec de la connexion JMX {#jmx-connection-fails}

Vérifiez la sortie du gatherer avec `docker compose logs kafka-jmx-gatherer`. Assurez-vous que JMX est activé, que le registre et l’endpoint RMI annoncé sont tous deux joignables, et que les identifiants JMX et le magasin de confiance configurés correspondent à ceux du broker. Si vous utilisez les noms d’hôte des conteneurs, ceux-ci doivent être connectés au même réseau, comme prévu.

### Aucune métrique n’apparaît {#no-metrics}

* Examinez la sortie du gatherer ou du collecteur de démonstration afin de repérer d’éventuelles erreurs de connexion, d’authentification ou d’exportation.
* Vérifiez le point de terminaison OTLP HTTP et l’authentification à l’aide des informations de connexion de votre service.
* Contrôlez la source **Metrics**, le filtre par nom de service et l’intervalle de temps. Pour la démonstration, sélectionnez **2 derniers jours**.
* Pour un collecteur existant, assurez-vous que son pipeline de métriques comprend le récepteur OTLP et un exportateur de métriques.
* Vérifiez les noms réels des métriques dans l’**Explorateur de graphiques** avant d’utiliser le tableau de bord de démonstration.

### Conflits de port JMX dans les commandes client Kafka {#port-conflicts}

Si vous exécutez des commandes client Kafka dans le conteneur du broker, supprimez pour ces commandes les paramètres JMX hérités du broker, afin que le client ne tente pas de se lier au même port :

```bash
env -u JMX_PORT -u KAFKA_JMX_OPTS kafka-topics --list --bootstrap-server YOUR_KAFKA_HOST:9092
```
