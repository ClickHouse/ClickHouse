Collectez les logs du journal systemd avec le récepteur journald d&#39;OpenTelemetry et envoyez-les vers ClickHouse Observability. Utilisez le [jeu de données de démonstration](#demo-dataset) pour tester l&#39;intégration sans hôte Linux.

## Prérequis {#prerequisites}

* Un service ClickHouse Observability
* Pour vos propres logs, un hôte Linux exécutant systemd, avec `journalctl` et la permission de lire son journal
* `curl`, ainsi que Docker pour la démo

### Informations de connexion {#connection-details}

<Tabs>
  <Tab title="Entièrement géré">
    <BetaBadge label="Offre en version bêta" />

    Ouvrez ClickHouse Observability et accédez à **Paramètres de l’équipe → Données → Télémétrie gérée**. Copiez votre point de terminaison OTLP HTTP et votre API key. Vous pouvez utiliser **Copier les informations de connexion** pour copier la configuration, ou **Afficher la clé** pour afficher la clé masquée.

    <div className="ch-image-lg">
      <Frame>
        ![Informations de connexion de la Télémétrie gérée](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Pour les exemples d’exportateur OTLP ci-dessous, définissez ces variables dans le terminal où vous exécuterez le collecteur :

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Remplacez les caractères de substitution par l’endpoint exact de votre service, port compris, ainsi que par votre API key. Utilisez l’endpoint HTTP de base, sans le suffixe `/v1/logs` : l’exportateur ajoute lui-même le chemin du signal.
  </Tab>

  <Tab title="Autogéré">
    Utilisez le point de terminaison OTLP HTTP joignable de votre collecteur (par exemple, `http://YOUR_COLLECTOR_HOST:4318`) ainsi que vos paramètres d’authentification. Si votre collecteur ne requiert pas d’authentification, supprimez le bloc `headers` de l’exportateur dans les configurations ci-dessous. Pour la mise en place, consultez le [guide de démarrage autogéré](/fr/clickstack/self-configured/getting-started/managed).

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

L’endpoint doit être joignable depuis l’hôte surveillé ou le collecteur de démonstration. Pour un collecteur de destination exécuté sur l’hôte Docker, utilisez `http://host.docker.internal:4318`.

## Intégration aux systèmes existants {#existing-systems}

<Steps>
  <Step title="Vérifiez le journal" id="verify-systemd">
    Sur l&#39;hôte Linux que vous souhaitez surveiller :

    ```bash
    systemctl --version
    sudo journalctl -n 20
    sudo journalctl --disk-usage
    ```

    Le récepteur s&#39;appuie sur la commande `journalctl` de l&#39;hôte pour lire les journaux disponibles. Le stockage persistant comme le stockage volatil des journaux sont pris en charge ; il n&#39;est pas nécessaire de modifier les paramètres de stockage.
  </Step>

  <Step title="Télécharger le collecteur" id="download-collector">
    Exécutez ces commandes sur l&#39;hôte Linux surveillé :

    ```bash
    case "$(uname -m)" in
      x86_64) arch=amd64 ;;
      aarch64|arm64) arch=arm64 ;;
      *) echo "Unsupported architecture"; exit 1 ;;
    esac
    curl -fL -o otelcol-contrib.tar.gz \
      "https://github.com/open-telemetry/opentelemetry-collector-releases/releases/download/v0.161.0/otelcol-contrib_0.161.0_linux_${arch}.tar.gz"
    tar -xzf otelcol-contrib.tar.gz otelcol-contrib
    ```

    Le collecteur s&#39;exécute directement sur l&#39;hôte afin de pouvoir utiliser le binaire `journalctl` qui y est installé. L&#39;image Docker Contrib standard n&#39;inclut pas ce binaire.
  </Step>

  <Step title="Configurer le collecteur" id="configure-collector">
    Enregistrez ce fichier sous le nom `systemd-monitoring.yaml` :

    ```yaml
    receivers:
      journald:
        start_at: end
        priority: info
        convert_message_bytes: true
    processors:
      transform/journald:
        error_mode: ignore
        log_statements:
          - context: log
            statements:
              - merge_maps(log.attributes, log.body, "upsert")
              - set(resource.attributes["host.name"], log.attributes["_HOSTNAME"])
              - set(resource.attributes["service.name"], "systemd-logs")
              - set(log.attributes["unit"], log.attributes["SYSLOG_IDENTIFIER"])
              - set(log.attributes["unit"], log.attributes["_SYSTEMD_UNIT"]) where log.attributes["_SYSTEMD_UNIT"] != nil
              - set(log.attributes["priority"], log.attributes["PRIORITY"])
              - set(log.body, log.attributes["MESSAGE"])
              - set(log.severity_text, "info")
              - set(log.severity_number, SEVERITY_NUMBER_INFO)
              - set(log.severity_text, "warn") where Int(log.attributes["PRIORITY"]) == 4
              - set(log.severity_number, SEVERITY_NUMBER_WARN) where log.severity_text == "warn"
              - set(log.severity_text, "error") where Int(log.attributes["PRIORITY"]) == 3
              - set(log.severity_number, SEVERITY_NUMBER_ERROR) where log.severity_text == "error"
              - set(log.severity_text, "fatal") where Int(log.attributes["PRIORITY"]) < 3
              - set(log.severity_number, SEVERITY_NUMBER_FATAL) where log.severity_text == "fatal"
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [journald]
          processors: [transform/journald, batch]
          exporters: [otlp_http/observability]
    ```

    Les champs du journal sont conservés sous forme d’attributs de journal, le message devient le corps du journal et le nom d’hôte devient un attribut de ressource. Le récepteur collecte toutes les unités de priorité `info` ou supérieure. Pour restreindre la collecte, ajoutez une liste `units` sous `journald` contenant les noms réels des unités de votre hôte, par exemple `ssh.service` ou `nginx.service`.
  </Step>

  <Step title="Exécutez le collecteur" id="run-collector">
    Définissez les [variables de connexion](#connection-details), puis exécutez la commande suivante depuis le répertoire de téléchargement. Cette commande utilise les droits d&#39;administrateur pour lire le journal système et ne conserve que les deux variables de connexion :

    ```bash
    sudo --preserve-env=OTEL_EXPORTER_OTLP_ENDPOINT,OTEL_EXPORTER_OTLP_AUTHORIZATION \
      ./otelcol-contrib --config=systemd-monitoring.yaml
    ```

    Laissez ce terminal ouvert. Dans un autre terminal, générez une entrée dans le journal :

    ```bash
    echo 'ClickHouse Observability journal ingestion test' | systemd-cat -t observability-test -p info
    ```

    Une fois les tests terminés, arrêtez le collecteur avec **Ctrl+C**. Pour une collecte en continu, exécutez-le en tant que service systemd disposant d&#39;un accès au journal et configurez le [stockage du curseur](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.161.0/receiver/journaldreceiver#cursor-tracking) afin qu&#39;il reprenne la lecture là où il s&#39;était arrêté après un redémarrage.
  </Step>

  <Step title="Vérifier les logs" id="verify-logs">
    Ouvrez **Recherche**, sélectionnez **Logs**, filtrez sur `ServiceName:systemd-logs`, puis sélectionnez **Last 15 minutes**. Repérez le message de test ainsi que des attributs tels que `unit` et `priority`.
  </Step>
</Steps>

## Jeu de données de démonstration {#demo-dataset}

L’échantillon contient 1,334 entrées de log textuelles réparties sur environ 48 heures, notamment de l’activité SSH, des tâches planifiées et des événements de service. Il utilise le récepteur `filelog` : aucune installation de systemd ni de `journalctl` n’est donc nécessaire. Le collecteur actualise les timestamp tout en préservant le corps d’origine des messages et l’intervalle entre les événements.

<Steps>
  <Step title="Télécharger l’échantillon" id="download-sample">
    ```bash
    curl -fL -o systemd-demo.log \
      https://datasets-documentation.s3.eu-west-3.amazonaws.com/clickstack-integrations/systemd/systemd-demo.log
    ```
  </Step>

  <Step title="Configurer le collecteur de démonstration" id="configure-demo">
    Enregistrez ce contenu sous `systemd-demo.yaml` :

    ```yaml
    receivers:
      filelog/systemd:
        include:
          - /var/log/demo/systemd-demo.log
        start_at: beginning
        operators:
          - type: regex_parser
            regex: '^(?P<timestamp>\S+) (?P<hostname>\S+) (?P<unit>\S+?)(?:\[(?P<pid>\d+)\])?: (?P<message>.*)$'
            parse_from: body
            parse_to: attributes
          - type: time_parser
            parse_from: attributes.timestamp
            layout: '%Y-%m-%dT%H:%M:%S%z'
          - type: add
            field: attributes.source
            value: systemd-demo
          - type: add
            field: resource["service.name"]
            value: systemd-demo
    processors:
      transform/demo_timestamps:
        error_mode: propagate
        log_statements:
          - context: log
            statements:
              - set(resource.attributes["host.name"], log.attributes["hostname"])
              - set(log.time, Now() - Duration("2m") - (Time("2025-11-16T23:45:00Z", "%Y-%m-%dT%H:%M:%SZ") - log.time))
      batch:
        timeout: 5s
        send_batch_size: 500
        send_batch_max_size: 500
    exporters:
      otlp_http/observability:
        endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
        headers:
          authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
    service:
      pipelines:
        logs:
          receivers: [filelog/systemd]
          processors: [transform/demo_timestamps, batch]
          exporters: [otlp_http/observability]
    ```

    L’échantillon textuel ne comporte pas de champ de priorité du journal ; la démonstration n’attribue donc pas de niveau de sévérité à partir du texte du message.
  </Step>

  <Step title="Exécuter le collecteur de démonstration" id="run-demo">
    Définissez les [variables de connexion](#connection-details), puis exécutez la commande suivante depuis le répertoire contenant les deux fichiers :

    ```bash
    docker run --rm --name systemd-demo-collector \
      --add-host=host.docker.internal:host-gateway \
      --memory=512m \
      -e OTEL_EXPORTER_OTLP_ENDPOINT \
      -e OTEL_EXPORTER_OTLP_AUTHORIZATION \
      -v "$(pwd)/systemd-demo.yaml:/etc/otelcol-contrib/config.yaml:ro" \
      -v "$(pwd)/systemd-demo.log:/var/log/demo/systemd-demo.log:ro" \
      otel/opentelemetry-collector-contrib:0.161.0 \
      --config=/etc/otelcol-contrib/config.yaml
    ```

    Laissez le terminal ouvert pendant que vous vérifiez l’ingestion. Arrêtez le collecteur avec **Ctrl+C** une fois la vérification terminée. Si vous relancez la démonstration, l’échantillon est ingéré de nouveau avec des timestamp actualisés.
  </Step>

  <Step title="Vérifier les logs de démonstration" id="verify-demo">
    Ouvrez **Recherche**, sélectionnez **Logs**, filtrez sur `ServiceName:systemd-demo` et sélectionnez **2 derniers jours**. Les entrées de l’échantillon devraient s’afficher avec les attributs `unit`, `hostname` et `message`.

    <div className="ch-image-lg">
      <Frame>
        ![Logs de démonstration systemd dans la Recherche de ClickHouse Observability](/images/clickstack/observability-systemd-demo-logs.png)
      </Frame>
    </div>
  </Step>
</Steps>

## Dépannage {#troubleshooting}

### journalctl introuvable {#journalctl-not-found}

Exécutez le collecteur réel sur l&#39;hôte Linux surveillé, où `journalctl` doit être installé et accessible dans son chemin d&#39;exécution. La démonstration utilise `filelog` et n&#39;en a pas besoin.

### Aucun log n&#39;apparaît {#no-logs}

Recherchez dans la sortie du collecteur d&#39;éventuelles erreurs d&#39;accès au journal, d&#39;authentification ou d&#39;exportation. Vérifiez que `sudo journalctl -n 20` renvoie bien des entrées sur l&#39;hôte surveillé. Si vous avez configuré un filtre d&#39;unités, vérifiez qu&#39;il correspond à vos noms de service. Générez une nouvelle entrée après le démarrage de la collecte.

Dans ClickHouse Observability, vérifiez la source **Logs**, le filtre par nom de service et l&#39;intervalle de temps. Pour la démonstration, sélectionnez **2 derniers jours** et vérifiez que le fichier d&#39;échantillon est bien monté sur le chemin configuré.
