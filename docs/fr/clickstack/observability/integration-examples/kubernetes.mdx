Collectez les logs des conteneurs, les métriques des nœuds et du cluster ainsi que les événements Kubernetes à l’aide de deux collecteurs OpenTelemetry : un DaemonSet sur chaque nœud et un déploiement unique pour les données à l’échelle du cluster.

## Prérequis {#prerequisites}

* Un service ClickHouse Observability
* Un cluster Kubernetes doté de nœuds Linux, avec la permission de créer des charges de travail, des ClusterRoles et des montages de type host-path
* `kubectl` configuré pour le cluster cible et Helm 3 installé
* Un accès réseau depuis les collecteurs vers le point de terminaison OTLP HTTP de votre service, l&#39;API Kubernetes et les agents de nœud Kubernetes (kubelets)

Ces collecteurs recueillent les données d&#39;infrastructure. Pour envoyer les métriques et les traces applicatives, instrumentez vos applications séparément ; consultez [Intégrations OpenTelemetry](/fr/clickstack/observability/ingesting-data/opentelemetry).

## Informations de connexion {#connection-details}

<Tabs>
  <Tab title="Entièrement géré">
    <BetaBadge label="Offre en version bêta" />

    Ouvrez ClickHouse Observability et accédez à **Paramètres de l’équipe → Données → Télémétrie gérée**. Copiez l’endpoint OTLP HTTP et l’API key.

    <div className="ch-image-lg">
      <Frame>
        ![Informations de connexion de la Télémétrie gérée](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>

    Définissez ces variables dans votre terminal :

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='https://YOUR_OTEL_ENDPOINT:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='Bearer YOUR_API_KEY'
    ```

    Utilisez l’endpoint tel quel, port compris, sans suffixe `/v1/logs` ni `/v1/metrics`.
  </Tab>

  <Tab title="Autogéré" id="self-managed">
    Utilisez l’endpoint OTLP HTTP de votre collecteur, joignable depuis le cluster, ainsi que ses paramètres d’authentification. Si l’authentification est désactivée, définissez `OTEL_EXPORTER_OTLP_AUTHORIZATION` sur une chaîne vide et omettez le bloc `headers` de l’exportateur ci-dessous. Consultez le [guide de configuration en mode autogéré](/fr/clickstack/self-configured/getting-started/managed).

    ```bash
    export OTEL_EXPORTER_OTLP_ENDPOINT='http://YOUR_COLLECTOR_HOST:4318'
    export OTEL_EXPORTER_OTLP_AUTHORIZATION='YOUR_INGESTION_KEY'
    ```
  </Tab>
</Tabs>

## Déployer les collecteurs {#deploy-collectors}

<Steps>
  <Step title="Créez le namespace et définissez les paramètres de connexion" id="connection-settings">
    Vérifiez que `kubectl` pointe vers le bon cluster :

    ```bash
    kubectl config current-context
    kubectl create namespace observability --dry-run=client -o yaml | kubectl apply -f -

    kubectl create configmap observability-connection -n observability \
      --from-literal=endpoint="$OTEL_EXPORTER_OTLP_ENDPOINT" \
      --dry-run=client -o yaml | kubectl apply -f -

    kubectl create secret generic observability-connection -n observability \
      --from-literal=authorization="$OTEL_EXPORTER_OTLP_AUTHORIZATION" \
      --dry-run=client -o yaml | kubectl apply -f -
    ```

    Les deux collecteurs utilisent ces paramètres dans le namespace `observability`.
  </Step>

  <Step title="Enregistrez la configuration partagée" id="shared-configuration">
    Enregistrez ce qui suit sous le nom `k8s_common.yaml` :

    ```yaml
    image:
      repository: otel/opentelemetry-collector-contrib
      tag: "0.161.0"
    command:
      name: otelcol-contrib
    resources:
      limits:
        memory: 512Mi
    presets:
      kubernetesAttributes:
        enabled: true
    extraEnvs:
      - name: OTEL_EXPORTER_OTLP_ENDPOINT
        valueFrom:
          configMapKeyRef:
            name: observability-connection
            key: endpoint
      - name: OTEL_EXPORTER_OTLP_AUTHORIZATION
        valueFrom:
          secretKeyRef:
            name: observability-connection
            key: authorization
    service:
      enabled: false
    ports:
      otlp:
        enabled: false
      otlp-http:
        enabled: false
      jaeger-compact:
        enabled: false
      jaeger-thrift:
        enabled: false
      jaeger-grpc:
        enabled: false
      zipkin:
        enabled: false
    config:
      receivers:
        otlp: null
        jaeger: null
        zipkin: null
        prometheus: null
      exporters:
        debug: null
        otlp_http/observability:
          endpoint: ${env:OTEL_EXPORTER_OTLP_ENDPOINT}
          headers:
            authorization: ${env:OTEL_EXPORTER_OTLP_AUTHORIZATION}
          compression: gzip
      processors:
        batch:
          timeout: 5s
          send_batch_size: 500
          send_batch_max_size: 500
      service:
        pipelines:
          logs:
            receivers: []
            exporters: [otlp_http/observability]
          metrics:
            receivers: []
            exporters: [otlp_http/observability]
          traces: null
    ```

    Les préréglages du chart ajoutent les récepteurs, le processeur de métadonnées Kubernetes, les règles RBAC et les montages dont chaque collecteur a besoin. La configuration partagée transmet les logs et les metrics à votre service et désactive les récepteurs inutilisés destinés à l&#39;ingestion des données applicatives.
  </Step>

  <Step title="Configurer la collecte au niveau des nœuds" id="daemonset-configuration">
    Enregistrez ce fichier sous le nom `k8s_daemonset.yaml` :

    ```yaml
    mode: daemonset
    presets:
      logsCollection:
        enabled: true
        storeCheckpoints: true
      hostMetrics:
        enabled: true
      kubeletMetrics:
        enabled: true
    config:
      receivers:
        kubeletstats:
          insecure_skip_verify: true
    ```

    Le DaemonSet lit les log des conteneurs et collecte les métriques de l&#39;hôte et de l&#39;agent de nœud Kubernetes (kubelet). Les points de contrôle conservent les positions de lecture des log lors des redémarrages du collecteur. Ce préréglage exécute le collecteur en tant que root afin d&#39;écrire les points de contrôle sur le nœud ; les paramètres de sécurité des groupes de conteneurs (pods) de votre cluster doivent autoriser ses montages de chemins de l&#39;hôte.

    L&#39;exemple désactive la vérification du certificat de l&#39;agent de nœud Kubernetes pour les clusters dont les certificats kubelet ne sont pas reconnus comme fiables par le collecteur. Si votre cluster fournit des certificats kubelet reconnus comme fiables, définissez `insecure_skip_verify` sur `false` et configurez l&#39;AC appropriée.
  </Step>

  <Step title="Configurer la collecte au niveau du cluster" id="deployment-configuration">
    Enregistrez ce fichier sous le nom `k8s_deployment.yaml` :

    ```yaml
    mode: deployment
    replicaCount: 1
    presets:
      kubernetesEvents:
        enabled: true
      clusterMetrics:
        enabled: true
    ```

    Conservez une seule réplique pour éviter de collecter en double les métriques et les événements du cluster.
  </Step>

  <Step title="Installez les releases Helm" id="install-collectors">
    Exécutez ces commandes depuis le répertoire contenant les trois fichiers de configuration. Ces exemples utilisent la version `0.175.1` du chart Helm du Collecteur OpenTelemetry et la version `0.161.0` de Collector Contrib :

    ```bash
    helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
    helm repo update open-telemetry

    helm upgrade --install observability-nodes open-telemetry/opentelemetry-collector \
      --version 0.175.1 --namespace observability \
      -f k8s_common.yaml -f k8s_daemonset.yaml --wait

    helm upgrade --install observability-cluster open-telemetry/opentelemetry-collector \
      --version 0.175.1 --namespace observability \
      -f k8s_common.yaml -f k8s_deployment.yaml --wait
    ```

    Vérifiez les collecteurs :

    ```bash
    kubectl get pods -n observability
    kubectl logs -n observability -l app.kubernetes.io/instance=observability-nodes --tail=50
    kubectl logs -n observability -l app.kubernetes.io/instance=observability-cluster --tail=50
    ```

    Si vos nœuds comportent des taints d&#39;ordonnancement, ajoutez les `tolerations` appropriées dans `k8s_daemonset.yaml` pour les nœuds que vous souhaitez surveiller.
  </Step>

  <Step title="Vérifiez les données" id="verify-data">
    Patientez le temps de quelques intervalles de collecte, puis ouvrez ClickHouse Observability :

    * Dans **Recherche**, sélectionnez votre source **Logs** et **Last 15 minutes**. Développez un log de conteneur et vérifiez la présence d&#39;attributs tels que `k8s.namespace.name`, `k8s.pod.name` et `k8s.node.name`.
    * Dans l&#39;**Explorateur de graphiques**, sélectionnez votre source **Metrics** et recherchez les métriques commençant par `k8s.` ou `system.`.
    * Consultez votre source **Logs** pour suivre les événements Kubernetes au fur et à mesure qu&#39;ils se produisent. Le volume d&#39;événements dépend de l&#39;activité du cluster.
  </Step>
</Steps>

## Métadonnées d&#39;application {#application-metadata}

Pour les applications instrumentées, ajoutez les métadonnées du groupe de conteneurs à l&#39;aide de l&#39;API Downward de Kubernetes. Fusionnez cette liste `env` dans la configuration existante du conteneur de votre application, en conservant les attributs de ressource déjà définis :

```yaml
env:
  - name: OTEL_SERVICE_NAME
    value: my-app
  - name: POD_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name
  - name: POD_UID
    valueFrom:
      fieldRef:
        fieldPath: metadata.uid
  - name: POD_NAMESPACE
    valueFrom:
      fieldRef:
        fieldPath: metadata.namespace
  - name: NODE_NAME
    valueFrom:
      fieldRef:
        fieldPath: spec.nodeName
  - name: OTEL_RESOURCE_ATTRIBUTES
    value: k8s.pod.name=$(POD_NAME),k8s.pod.uid=$(POD_UID),k8s.namespace.name=$(POD_NAMESPACE),k8s.node.name=$(NODE_NAME)
```

Le processeur de métadonnées Kubernetes enrichit les logs collectés des conteneurs avec les métadonnées de la charge de travail. Ces variables d&#39;application associent l&#39;identité du groupe de conteneurs à la télémétrie émise par le SDK OpenTelemetry de votre application.

## Dépannage {#troubleshooting}

### Les collecteurs ne démarrent pas {#collectors-not-starting}

Examinez les événements du groupe de conteneurs avec `kubectl describe pod -n observability POD_NAME`. Vérifiez les téléchargements d’images, les contraintes d’ordonnancement et les restrictions de sécurité des groupes de conteneurs, et assurez-vous que le ConfigMap et le Secret existent dans le même namespace que les releases.

### Aucun log ni aucune métrique n&#39;apparaît {#no-data}

Consultez les logs du collecteur pour repérer d&#39;éventuelles erreurs d&#39;authentification ou erreurs d’exportation. Vérifiez que l&#39;endpoint de destination est joignable depuis le cluster. En cas d&#39;erreurs liées à l&#39;agent de nœud Kubernetes, vérifiez la connectivité au port `10250`, les paramètres de certificat ainsi que les autorisations RBAC générées. La collecte des logs des conteneurs nécessite un accès au répertoire `/var/log/pods` du nœud ; les environnements de nœuds restreints ou sans serveur peuvent ne pas prendre en charge ces montages de répertoires de l&#39;hôte.

### Modification des paramètres de connexion {#connection-settings-changed}

Après avoir mis à jour la ConfigMap ou le Secret, redémarrez les collecteurs afin qu’ils rechargent leurs variables d’environnement :

```bash
kubectl rollout restart daemonset -n observability -l app.kubernetes.io/instance=observability-nodes
kubectl rollout restart deployment -n observability -l app.kubernetes.io/instance=observability-cluster
```
