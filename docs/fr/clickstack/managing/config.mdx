Les options de configuration suivantes sont disponibles pour chaque composant de ClickStack :

<div id="modifying-settings">
  ## Paramètres pour les distributions open source {#modifying-settings}
</div>

### Docker {#docker}

Si vous utilisez [Tout-en-un](/fr/clickstack/deployment/all-in-one), [interface utilisateur de ClickStack uniquement](/fr/clickstack/deployment/hyperdx-only) ou le [Mode local](/fr/clickstack/deployment/local-mode-only), il suffit de définir le paramètre souhaité via une variable d’environnement, par exemple.

```shell
docker run -e HYPERDX_APP_PORT=8081 -p 8081:8081 -p 4317:4317 -p 4318:4318 clickhouse/clickstack-all-in-one:latest
```

### Docker Compose {#docker-compose}

Si vous utilisez le guide de déploiement [Docker Compose](/fr/clickstack/deployment/docker-compose), vous pouvez utiliser le fichier [`.env`](https://github.com/ClickHouse/clickstack/blob/main/.env) pour modifier les paramètres.

Vous pouvez également surcharger explicitement les paramètres dans le fichier [`docker-compose.yml`](https://github.com/ClickHouse/clickstack/blob/main/docker-compose.yml), par exemple :

Exemple :

```yaml
services:
  app:
    environment:
      HYPERDX_API_KEY: ${HYPERDX_API_KEY}
      HYPERDX_LOG_LEVEL: ${HYPERDX_LOG_LEVEL}
      # ... other settings
```

### Helm {#helm}

Utilisez le [guide de déploiement Helm](/fr/clickstack/deployment/helm) pour installer les opérateurs et le chart ClickStack. Avant de personnaliser un déploiement, récupérez les valeurs actuelles du chart :

```shell
helm show values clickstack/clickstack > values.yaml
```

Définissez séparément l&#39;environnement de l&#39;application et celui du collecteur à l&#39;aide des valeurs du chart Helm, puis appliquez votre configuration :

```shell
helm upgrade --install my-clickstack clickstack/clickstack -f values.yaml
```

Consultez la page [Configuration Helm](/fr/clickstack/deployment/helm-configuration) pour connaître les valeurs prises en charge ainsi que la configuration de l&#39;Entrée, des ressources et des secrets. L&#39;ancien chart `hyperdx/hdx-oss-v2` utilise une structure de valeurs différente.

## Application interface utilisateur de ClickStack {#hyperdx}

### Connexions {#connection-settings}

Configurez la connexion à la base de données utilisée par vos sources dans Paramètres de l’équipe.

| Paramètre                  | Description                                                                                                                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Connection Name`          | Nom permettant d’identifier cette connexion dans les paramètres de la source.                                                                                                                                                                                                         |
| `Host`                     | Endpoint HTTP(S) de ClickHouse, port inclus. Il est distinct de l’endpoint d’exportation du collecteur.                                                                                                                                                                               |
| `Username`                 | Nom d’utilisateur ClickHouse ; valeur par défaut : `default`.                                                                                                                                                                                                                         |
| `Password`                 | Mot de passe ClickHouse ; vide par défaut.                                                                                                                                                                                                                                            |
| `Query Log Setting Prefix` | Préfixe facultatif d’un paramètre ClickHouse personnalisé qui enregistre l’e-mail de l’utilisateur courant dans les journaux de requêtes. Ajoutez le même préfixe à la configuration `custom_settings_prefixes` de ClickHouse, faute de quoi les requêtes seront rejetées.            |
| `Prometheus compatible`    | Lorsque cette option est disponible, Host est traité comme un point de terminaison API compatible Prometheus pour les requêtes PromQL relayées par proxy. Cette connexion ne peut pas être utilisée pour les sources de logs, de traces ou de métriques OTel reposant sur ClickHouse. |

### Paramètres de la source de données {#datasource-settings}

L’interface utilisateur de ClickStack nécessite que l’utilisateur définisse une source pour chacun des types/piliers de données d’observability :

* `Logs`
* `Traces`
* `Metrics`
* `Sessions`

Cette configuration peut être effectuée dans l’application depuis `Team Settings -> Sources`, comme illustré ci-dessous pour les logs :

<div className="ch-image-md">
  <Frame>
    ![Configuration de la source dans l’interface utilisateur de ClickStack](/images/use-cases/observability/hyperdx-25.webp)
  </Frame>
</div>

Chaque source nécessite des correspondances de tables et de colonnes pour que l’interface utilisateur de ClickStack puisse interroger ses données. Les sources de métriques peuvent utiliser des tables distinctes selon le type de métrique. L’interrupteur `Enabled` s’affiche lors de la modification d’une source existante ; les `Query Settings` définis au niveau de la source acceptent jusqu’à dix paires nom/valeur.

Si vous utilisez le [schéma OpenTelemetry (OTel) par défaut](/fr/guides/use-cases/observability/build-your-own/integrating-opentelemetry#out-of-the-box-schema) fourni avec ClickStack, ces colonnes peuvent être déterminées automatiquement pour chacune des sources. Si vous [modifiez le schéma](#clickhouse) ou utilisez un schéma personnalisé, vous devez spécifier et mettre à jour ces correspondances.

<Note>
  Selon sa [configuration de schéma](#collector-schema-and-retention), le collecteur crée les tables au moyen de migrations de schéma ou du mécanisme legacy de création de schéma géré par l’exportateur. Les correspondances de colonnes suivent les conventions OpenTelemetry, notamment le [modèle de données des logs](https://opentelemetry.io/docs/specs/otel/logs/data-model/).
</Note>

#### Highlighted Attributes {#highlighted-attributes}

Les Highlighted Attributes et les Highlighted Trace Attributes peuvent être configurés dans les sources de données de logs et de traces.

* Les Highlighted Attributes sont des colonnes ou des expressions affichées pour chaque log ou span lors de l’affichage des détails du log ou du span.
* Les Highlighted Trace Attributes sont des colonnes ou des expressions récupérées pour chaque log ou span d’une trace, puis affichées au-dessus de la trace waterfall.

Ces attributs sont définis dans la configuration de la source et peuvent être des expressions SQL arbitraires. Si l’expression SQL renvoie une valeur au format URL, l’attribut sera affiché sous forme de lien. Les valeurs vides ne sont pas affichées.

| `Alias`             | Facultatif. Le libellé affiché pour l’attribut à la place de l’expression SQL.                                |
| `Lucene Expression` | Facultatif. Une version Lucene de l’expression SQL, utilisée lors de la recherche de cette valeur d’attribut. |

### Sources corrélées {#correlated-sources}

Pour activer une corrélation complète entre les sources dans ClickStack, vous devez configurer des sources corrélées pour les logs, les traces, les métriques et les sessions. Cela permet à l’interface utilisateur de ClickStack d’associer les données liées et de fournir un contexte détaillé lors de l’affichage des événements.

* `Logs` : peuvent être corrélés avec les traces et les métriques.
* `Traces` : peuvent être corrélées avec les logs, les sessions et les métriques.
* `Metrics` : peuvent être corrélées avec les logs.
* `Sessions` : peuvent être corrélées avec les traces.

La configuration de ces corrélations active plusieurs fonctionnalités. Par exemple, l’interface utilisateur de ClickStack peut afficher les logs pertinents aux côtés d’une trace ou mettre en évidence des anomalies de métriques liées à une session.

| `NEXT_PUBLIC_INSTANCE_LABEL`       | Vide       | Étiquette ajoutée au titre de l’onglet du navigateur et affichée dans la barre latérale, pratique pour distinguer les instances.                                                                                                                                                                                      |
| `ENABLE_DATADOG_RECEIVER`          | `false`    | Active le récepteur de traces Datadog dans la configuration du collecteur générée par OpAMP. Le récepteur, sur le port `8126`, vérifie `DD-API-KEY` lorsque des clés d’ingestion d’équipe existent et que l’authentification du collecteur est appliquée ; dans le cas contraire, il n’exige aucune authentification. |
| `BETA_CH_OTEL_JSON_SCHEMA_ENABLED` | `false`    | Sélectionne des correspondances de sources par défaut compatibles JSON dans le point d’entrée tout-en-un. À utiliser conjointement avec `HYPERDX_OTEL_EXPORTER_CLICKHOUSE_JSON_ENABLE` sur le collecteur.                                                                                                                    |

`NEXT_PUBLIC_IS_LOCAL_MODE` est l’option de construction du frontend propre à la [distribution Mode local](/fr/clickstack/deployment/local-mode-only). Il ne s’agit pas d’un commutateur de développement générique. Utilisez la distribution adaptée plutôt que de désactiver l’authentification sur un déploiement existant. `IS_LOCAL_MODE` et `IS_OSS` sont des noms de constantes de l’application, et non des variables d’environnement à définir. `NEXT_PUBLIC_IS_OSS` est un paramètre de construction ; ce n’est pas un commutateur d’édition Enterprise. `MINER_API_URL` n’est plus utilisé par la version actuelle de l’application.

Si vous utilisez la configuration de proxy inverse fournie pour un sous-chemin, définissez `HYPERDX_BASE_PATH` et `NEXT_PUBLIC_HYPERDX_BASE_PATH` avec le même préfixe (par exemple `/clickstack`), et incluez ce préfixe dans `FRONTEND_URL`.

Certains paramètres du frontend sont lus au moment de la construction. En particulier, toute modification de `NEXT_PUBLIC_HYPERDX_BASE_PATH` (le préfixe de chemin du déploiement), de `NEXT_PUBLIC_NOINDEX` (indexation par les moteurs de recherche) ou des options de mode de la distribution impose de reconstruire le frontend avec ces valeurs. Les paramètres d’exécution lus via `next-runtime-env`, tels que `NEXT_PUBLIC_INSTANCE_LABEL`, peuvent être fournis au conteneur au démarrage.

<div id="clickhouse">
  ## ClickHouse {#clickhouse}
</div>

ClickStack Open Source est livré avec une configuration ClickHouse par défaut conçue pour fonctionner à l’échelle de plusieurs téraoctets, mais les utilisateurs peuvent librement la modifier et l’optimiser en fonction de leur charge de travail.

Pour optimiser ClickHouse efficacement, vous devez comprendre les principaux concepts de stockage tels que les [parts](/fr/concepts/core-concepts/parts), les [partitions](/fr/concepts/core-concepts/partitions), les [shards et répliques](/fr/guides/oss/deployment-and-scaling/shards), ainsi que la façon dont les [fusions](/fr/concepts/core-concepts/merges) se produisent à l’insertion. Nous vous recommandons de revoir les principes fondamentaux des [index primaires](/fr/concepts/core-concepts/primary-indexes), des [index secondaires creux](/fr/concepts/features/performance/skip-indexes/skipping-indexes) et des index de saut de données, ainsi que les techniques de [gestion du cycle de vie des données](/fr/guides/use-cases/observability/build-your-own/managing-data), par exemple à l’aide d’une politique TTL.

ClickStack prend en charge la [personnalisation du schéma](/fr/guides/use-cases/observability/build-your-own/schema-design) - vous pouvez modifier les types de colonnes, extraire de nouveaux champs (par exemple à partir des logs), appliquer des codecs et des dictionnaires, et accélérer les requêtes à l’aide de projections.

En outre, des vues matérialisées peuvent être utilisées pour [transformer ou filtrer les données pendant l’ingestion](/fr/guides/use-cases/observability/build-your-own/schema-design#materialized-columns), à condition que les données soient écrites dans la table source de la vue et que l’application lise depuis la table cible. Les vues matérialisées peuvent également être utilisées pour [accélérer nativement les requêtes](/fr/clickstack/managing/materialized-views) dans ClickStack.

Pour plus de détails, consultez la documentation ClickHouse sur la conception de schéma, les stratégies d’indexation et les bonnes pratiques de gestion des données — la plupart s’appliquent directement aux déploiements ClickStack.
