ClickStack prend en charge la visualisation des événements, avec une prise en charge native des graphiques dans l’interface utilisateur de ClickStack. Ces graphiques peuvent être ajoutés à des tableaux de bord afin d’être partagés avec d’autres utilisateurs.

Des visualisations peuvent être créées à partir de traces, de métriques, de logs ou de tout schéma d’événements wide défini par l’utilisateur.

## Création de visualisations {#creating-visualizations}

L&#39;interface **Chart Explorer** de l&#39;interface utilisateur de ClickStack vous permet de visualiser les métriques, les traces et les logs dans le temps, ce qui facilite la création rapide de visualisations pour analyser les données. Cette interface est également réutilisée lors de la création de tableaux de bord. La section suivante explique comment créer une visualisation avec Chart Explorer.

Chaque visualisation commence par la sélection d&#39;une **source de données**, suivie d&#39;une **métrique**, avec éventuellement des **expressions de filtrage** et des champs de **groupement**. En pratique, les visualisations dans l&#39;interface utilisateur de ClickStack correspondent en arrière-plan à une requête SQL `GROUP BY` : vous définissez les métriques à agréger selon les dimensions sélectionnées.

<Tip>
  **Génération de graphiques par IA**

  ClickStack permet également de créer des graphiques à partir de descriptions en langage naturel grâce à la fonctionnalité [text-to-chart](/fr/clickstack/text-to-chart). Décrivez ce que vous souhaitez voir, et ClickStack génère automatiquement la visualisation.
</Tip>

Par exemple, vous pouvez représenter le nombre d&#39;erreurs (`count()`) regroupé par nom de service.

Pour les exemples ci-dessous, nous utilisons le jeu de données distant disponible sur [sql.clickhouse.com](https://sql.clickhouse.com), décrit dans le guide [&quot;Remote Demo Dataset&quot;](/fr/clickstack/example-datasets/remote-demo-data). **Vous pouvez également reproduire ces exemples en consultant [play-clickstack.clickhouse.com](https://play-clickstack.clickhouse.com).**

<div id="creating-dashboards">
  ## Création de tableaux de bord {#creating-dashboards}
</div>

Les tableaux de bord permettent de regrouper des visualisations liées afin de comparer les métriques et d’explorer les tendances côte à côte pour identifier les causes profondes potentielles dans vos systèmes. Ces tableaux de bord peuvent être utilisés pour des investigations ad hoc ou enregistrés pour un suivi continu.

Les filtres globaux peuvent être appliqués au niveau du tableau de bord et se répercutent automatiquement sur toutes les visualisations qu’il contient. Cela permet un drill-down cohérent entre les graphiques et simplifie la corrélation des événements entre les services et les types de télémétrie.

Nous créons ci-dessous un tableau de bord avec deux visualisations à l’aide des sources de données de logs et de traces. Ces étapes peuvent être reproduites sur [play-clickstack.clickhouse.com](https://play-clickstack.clickhouse.com) ou localement en vous connectant au dataset hébergé sur [sql.clickhouse.com](https://sql.clickhouse.com), comme décrit dans le guide [&quot;Remote Demo Dataset&quot;](/fr/clickstack/example-datasets/remote-demo-data).

  <Step title="Ajouter une tuile Heatmap pour la durée des spans" id="create-a-tile-heatmap">
    Les tuiles Heatmap représentent, sous forme de grille colorée, le nombre d’événements présents dans chaque bucket (temps, valeur). Utilisez une heatmap lorsque vous voulez voir la **forme** d’une distribution dans le temps, et pas seulement la moyenne ou un percentile unique. Une heatmap de latence révèle des schémas de durée bimodaux, des regroupements dans la queue lente ou des dispersions soudaines qu’un graphique linéaire lisserait.

    Pour ajouter une tuile Heatmap :

    1. Sélectionnez `Add New Tile`.
    2. Choisissez le type de visualization `Heatmap` dans le menu supérieur. La liste déroulante des sources de données n’affiche que les sources dont le [Source Type est `Traces`](/fr/clickstack/managing/config#traces). Les sources de logs, de metrics et de session sont exclues, car les heatmaps nécessitent une colonne de durée de span que seules les sources de traces fournissent.
    3. Choisissez l’une de vos sources de traces par son nom. Le nom lui-même est arbitraire : seul le type compte.

    Une fois une source sélectionnée, la heatmap préremplit :

    * **Value** : la `Duration Expression` de la source, mise à l’échelle selon l’unité d’affichage actuelle (par exemple `(Duration)/1e6` pour convertir la durée de span de chaque événement de nanosecondes en millisecondes)
    * **Count** : `count()`

    4. Définissez un nom de graphique, puis utilisez `Where` pour limiter la heatmap à un service spécifique ou à un ensemble d’opérations dont vous souhaitez observer les performances.
    5. Ajustez l’intervalle de temps pour qu’il corresponde à la période voulue. Des intervalles plus larges font apparaître des variations de distribution et des schémas de latence bimodaux que des fenêtres plus courtes peuvent masquer.

    L’exemple ci-dessous montre un seul service sur une fenêtre de 24 heures, avec les chemins rapides et lents de la durée de ses spans clairement séparés en deux bandes horizontales.

    Pour personnaliser davantage la heatmap, cliquez sur **Display Settings** pour ouvrir un drawer permettant de configurer l’expression **Scale** (Log ou Linear), **Value** et **Count**. La liste complète des options est documentée dans [Customize the heatmap](/fr/clickstack/features/event-deltas#customize) sur la page Event Deltas. Le même drawer est réutilisé.

    Cliquez sur `Run` pour prévisualiser le graphique, puis sur `Save`.

    <div className="ch-image-lg">
      <Frame>
        ![Éditeur de tuile Heatmap avec les valeurs par défaut de durée de span préremplies, le filtre ServiceName payment et le bouton Display Settings](/images/clickstack/dashboards/heatmap-tile-editor.webp)
      </Frame>
    </div>

    La tuile enregistrée s’affiche sous forme de heatmap sur le dashboard. Survolez n’importe quelle cellule pour voir les bornes du bucket et le nombre d’événements.

    <div className="ch-image-lg">
      <Frame>
        ![Tuile de dashboard Heatmap montrant la distribution de durée des spans du service payment sur 24 heures](/images/clickstack/dashboards/heatmap-tile-rendered.webp)
      </Frame>
    </div>

    <Tip>
      **Deux requêtes ClickHouse par heatmap**

      La heatmap s’exécute en deux queries séquentielles : une petite **requête de bornes** qui détermine la plage de valeurs, puis une **requête heatmap** qui compte les événements par bucket. Les deux queries sont visibles dans l’éditeur sous **Generated SQL** si vous voulez les examiner ou les copier.
    </Tip>

  </Step>

<div id="tile-display-settings">
  ### Paramètres d’affichage de la tuile {#tile-display-settings}
</div>

Chaque tuile dispose d’un volet **Paramètres d’affichage** proposant des options qui contrôlent la façon dont sa valeur est rendue. Ouvrez-le depuis l’éditeur de tuiles en cliquant sur **Paramètres d’affichage**. Les options disponibles dépendent du type de visualisation.

<div id="number-tile-color">
  #### Couleur des tuiles Number {#number-tile-color}
</div>

Les tuiles Number prennent en charge un choix de **Couleur** statique issu de la palette de graphiques prédéfinie. Lorsqu&#39;une tuile Number est sélectionnée, ouvrez les **Paramètres d&#39;affichage** et utilisez le contrôle **Couleur** (intitulé **Couleur des tuiles Number** à des fins d&#39;accessibilité) pour choisir un échantillon, ou effacez la sélection afin d&#39;utiliser la couleur de texte par défaut.

Les couleurs sont stockées sous forme de tokens de palette, et non de valeurs hexadécimales brutes, afin que la même tuile s&#39;affiche correctement dans les thèmes clair, sombre et IDE.

**Tokens catégoriels** (teintes pour plusieurs séries) :

| Token              | Libellé    |
| ------------------ | ---------- |
| `chart-blue`       | Bleu       |
| `chart-orange`     | Orange     |
| `chart-red`        | Rouge      |
| `chart-cyan`       | Cyan       |
| `chart-green`      | Vert       |
| `chart-pink`       | Rose       |
| `chart-purple`     | Violet     |
| `chart-light-blue` | Bleu clair |
| `chart-brown`      | Marron     |
| `chart-gray`       | Gris       |

**Tokens sémantiques** (orientés statut) :

| Token           | Libellé       |
| --------------- | ------------- |
| `chart-success` | Succès        |
| `chart-warning` | Avertissement |
| `chart-error`   | Erreur        |

Utilisez des tokens sémantiques lorsque le nombre représente un statut (par exemple, un nombre d&#39;erreurs avec `chart-error` ou un taux de bon fonctionnement avec `chart-success`). Utilisez des tokens catégoriels pour distinguer visuellement des tuiles KPI associées sans indiquer de statut.

Les anciennes configurations peuvent encore stocker des tokens numériques legacy (`chart-1` à `chart-10`). Lors du chargement d&#39;un tableau de bord, ClickStack les associe aux tokens nommés d&#39;après les teintes ci-dessus.

La même palette permet de définir des **règles de couleur** facultatives dans le même volet : des conditions ordonnées évaluées par rapport à la valeur affichée (la dernière correspondance l&#39;emporte). Lorsqu&#39;aucune règle ne correspond, la couleur statique s&#39;applique, puis la couleur de texte par défaut.

#### Graphique d’arrière-plan de la tuile Number {#number-tile-background-chart}

Les tuiles Number peuvent afficher un **graphique d’arrière-plan** : un graphique sparkline de tendance tracé derrière la valeur, pour visualiser d’un coup d’œil son évolution sur l’intervalle de temps sélectionné. C’est utile pour les tuiles de SLO et de budget d’erreur, où la tendance d’une valeur compte autant que sa valeur actuelle.

Avec une tuile Number sélectionnée, ouvrez **Paramètres d’affichage** et définissez **Graphique d’arrière-plan** sur **Ligne** ou **Zone** (ou **Aucun** pour le désactiver). Le graphique sparkline est dérivé d’une version de la requête de la tuile regroupée par intervalles de temps ; aucune configuration supplémentaire n’est donc nécessaire. Il hérite par défaut de la couleur de la tuile ; définissez une **Couleur d’arrière-plan** pour la remplacer par une couleur précise de la palette.

<div className="ch-image-lg">
  <Frame>
    ![Volet Paramètres d’affichage pour une tuile Number, avec Graphique d’arrière-plan défini sur Zone](/images/clickstack/dashboards/number-tile-background-chart.webp)
  </Frame>
</div>

Les graphiques d’arrière-plan s’appliquent aux tuiles Number créées avec le générateur de requêtes. Les tuiles Number en Raw SQL renvoient une valeur unique, sans dimension temporelle à regrouper, donc l’option apparaît mais reste désactivée pour elles.

Les tuiles de tableau peuvent alterner l’arrière-plan de leurs lignes avec **Arrière-plan alterné des lignes**, ce qui teinte une ligne sur deux pour rendre les tables larges plus faciles à parcourir. Cette option est désactivée par défaut.

Avec une tuile de tableau sélectionnée, ouvrez **Paramètres d’affichage** et activez **Arrière-plan alterné des lignes**. Cette alternance est purement visuelle, elle fonctionne donc aussi bien sur les tuiles de tableau du générateur de requêtes que sur celles en Raw SQL.

<div className="ch-image-lg">
  <Frame>
    ![Volet Paramètres d’affichage pour une tuile de tableau, avec Arrière-plan alterné des lignes activé](/images/clickstack/dashboards/table-tile-display-settings.webp)
  </Frame>
</div>

Les tuiles de tableau conservent également un séparateur entre la ligne d’en-tête et les données pendant le défilement, afin que les en-têtes de colonnes restent bien distincts.

<div id="api-number-tile-color">
  #### API des tableaux de bord : couleur des tuiles Number {#api-number-tile-color}
</div>

Lors de la création ou de la mise à jour de tableaux de bord via l’API externe (`POST` / `PUT` `/api/v2/dashboards`), définissez `color` sur un token de palette dans la config du générateur de requêtes d’une tuile Number. Les valeurs hex brutes sont rejetées.

```json
{
  "name": "Error rate KPIs",
  "tiles": [
    {
      "id": "65f5e4a3b9e77c001a222222",
      "name": "Errors",
      "x": 0,
      "y": 0,
      "w": 6,
      "h": 4,
      "config": {
        "displayType": "number",
        "sourceId": "<SOURCE_ID>",
        "select": [
          {
            "aggFn": "count",
            "where": "SeverityText:error",
            "whereLanguage": "lucene",
            "alias": "Errors"
          }
        ],
        "color": "chart-error",
        "backgroundChart": {
          "type": "area"
        }
      }
    }
  ]
}
```

`color` accepte n’importe quel token des listes catégorielles et sémantiques ci-dessus (par exemple `chart-blue` ou `chart-success`). Le paramètre facultatif `backgroundChart.color` remplace la couleur du sparkline par le même enum de token. Consultez la [référence de l’API ClickStack](/fr/clickstack/api-reference) pour l’authentification et les URL de base.

## Filtres personnalisés et variables {#custom-filters}

En plus des [filtres en texte libre](#filter-dashboards) disponibles sur tous les tableaux de bord, les tableaux de bord enregistrés prennent en charge des filtres personnalisés et des variables. Ils offrent des contrôles réutilisables, utilisables en quelques clics, afin que les utilisateurs des tableaux de bord puissent filtrer sans avoir à écrire manuellement des expressions. Leurs valeurs peuvent provenir d’une colonne interrogée depuis une source, d’une liste saisie manuellement, d’une requête SQL, de valeurs de labels Prometheus ou de conditions clé-valeur librement définies. Les variables peuvent également déterminer la source de données ou la connexion interrogée par une tuile. Consultez [Types de filtres](#filter-types) pour la liste complète.

<div className="ch-image-lg">
  <Frame>
    ![Filtre déroulant des services affichant les noms de service disponibles](/images/clickstack/dashboards/filter-dropdown.webp)
  </Frame>
</div>

Chaque filtre permet à l’utilisateur de choisir une ou plusieurs valeurs, puis effectue l’une ou les deux actions suivantes :

* **Diffusion** — applique la sélection comme condition de filtre aux tuiles correspondantes. Les tuiles n’ont pas besoin d’être mises à jour pour référencer le filtre.
* **Variable** — expose la sélection aux requêtes des tuiles sous la forme `$variableName`, afin que chaque tuile décide où et comment la valeur est utilisée.

Les actions prises en charge par un filtre dépendent de son [type](#filter-types). Un filtre **SQL expression values** doit effectuer au moins l’une des deux actions, et la diffusion y est activée par défaut.

Les étapes suivantes montrent comment ajouter un filtre au tableau de bord créé dans la section [« Création de tableaux de bord »](#creating-dashboards).

<Steps>
  <Step title="Ouvrir la boîte de dialogue Modifier les filtres" id="open-edit-filters">
    Ouvrez un tableau de bord enregistré et sélectionnez **Modifier les filtres et les variables** dans la barre d’outils.

    <div className="ch-image-lg">
      <Frame>
        ![Bouton Modifier les filtres et les variables dans la barre d’outils du tableau de bord](/images/clickstack/dashboards/edit-filters.webp)
      </Frame>
    </div>

### Types de filtres {#filter-types}

Le sélecteur **Type** de la boîte de dialogue du filtre détermine la provenance des valeurs d&#39;un filtre et la manière dont elles sont transmises aux tuiles.

| Type                                                           | Provenance des valeurs                                                                                      | Diffusion                       | Variable                                                                       |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------ |
| [Valeurs d&#39;expression SQL](#sql-expression-values-filters) | Les valeurs distinctes d&#39;une expression, récupérées par requête sur une source                          | Facultative, activée par défaut | Facultative                                                                    |
| [Valeurs statiques](#static-values-filters)                    | Une liste saisie manuellement                                                                               | Non                             | Toujours                                                                       |
| [Valeurs de requête SQL](#sql-query-filters)                   | La première colonne d&#39;une requête SQL                                                                   | Non                             | Toujours                                                                       |
| [Valeurs d&#39;étiquette PromQL](#promql-label-filters)        | Les valeurs d&#39;une étiquette Prometheus                                                                  | Non                             | Toujours                                                                       |
| [Clés et valeurs ad hoc](#adhoc-filters)                       | Des conditions `key operator value` construites à partir des clés et valeurs d&#39;une ou plusieurs sources | Toujours                        | Non                                                                            |
| [Source de données](#data-source-variables)                    | Les sources de l&#39;équipe                                                                                 | Non                             | Toujours, sous forme de [référence de source](#source-connection-variables)    |
| [Connexion](#connection-variables)                             | Les connexions ClickHouse de l&#39;équipe                                                                   | Non                             | Toujours, sous forme de [référence de connexion](#source-connection-variables) |

#### Valeurs d&#39;expression SQL {#sql-expression-values-filters}

Sa liste déroulante affiche les valeurs distinctes de l&#39;**Expression de filtrage** dans la **Source de données** sélectionnée, éventuellement restreintes par un **Filtre des valeurs de la liste déroulante**. Pour les sources de métriques, choisissez également un **Type de métrique**. Un filtre de valeurs d&#39;expression SQL peut [diffuser](#broadcast-filters) sa sélection, être [disponible en tant que variable](#dashboard-variables) ou les deux.

#### Valeurs statiques {#static-values-filters}

Sa liste déroulante propose une liste de valeurs saisies manuellement. Saisissez chaque valeur dans **Options** et appuyez sur Entrée. Un filtre peut contenir jusqu&#39;à 1000 options.

Un filtre à valeurs statiques est toujours une variable et n&#39;est jamais diffusé : les tuiles l&#39;utilisent donc en référençant sa variable, par exemple `$__filter(SeverityText, $severity)`. C&#39;est utile pour des valeurs qui ne sont pas stockées dans une colonne, ou pour une liste fixe et soigneusement établie.

#### Valeurs issues d&#39;une requête SQL {#sql-query-filters}

Sa liste déroulante affiche la première colonne renvoyée par une requête SQL ClickHouse, dans l&#39;ordre où la requête renvoie les lignes, dans la limite de 10,000 valeurs. Paramètres à configurer :

* **Connexion** — la connexion à ClickHouse sur laquelle la requête s&#39;exécute, ou une [variable de connexion](#connection-variables).
* **Source** — facultatif. Une source sur la même connexion, ou une [variable de source de données](#data-source-variables). Lorsqu&#39;une source est sélectionnée, la requête peut utiliser `$__sourceTable` et `$__filters`, qui applique les sélections des filtres diffusés du tableau de bord pour cette source, de la même manière que les [tuiles SQL brut](/fr/clickstack/features/dashboards/sql-visualizations#dashboard-filter-macro).
* **Requête SQL** — la requête elle-même. Elle peut utiliser les [macros temporelles](/fr/clickstack/features/dashboards/sql-visualizations#time-filter-macros) et faire référence aux autres variables du tableau de bord. L&#39;éditeur affiche un aperçu des valeurs renvoyées par la requête pour l&#39;intervalle de temps actuel du tableau de bord.

Par exemple, la requête suivante liste les services ayant journalisé des événements dans l&#39;intervalle de temps du tableau de bord, en se limitant aux environnements sélectionnés dans un filtre `environment` :

```sql
SELECT DISTINCT ServiceName
FROM otel_logs
WHERE $__timeFilter(TimestampTime)
  AND $__filter(ResourceAttributes['deployment.environment'], $environment)
ORDER BY ServiceName
```

Un filtre de type valeurs de requête SQL est toujours une variable et n&#39;est jamais diffusé.

#### Valeurs d&#39;étiquette PromQL {#promql-label-filters}

<Note>
  La prise en charge de PromQL est en préversion. Dans les déploiements Open Source, activez-la en définissant `ENABLE_PROMQL=true` pour l&#39;API et `NEXT_PUBLIC_ENABLE_PROMQL=true` pour l&#39;application (voir [fonctionnalités facultatives](/fr/clickstack/managing/config#optional-features-and-deployment-modes)), puis activez le schéma PromQL dans le collecteur (voir [métriques compatibles avec Prometheus](/fr/clickstack/managing/config#collector-prometheus-metrics)). Consultez les [paramètres de la source PromQL](/fr/clickstack/managing/config#promql-source-settings) pour créer une source PromQL.
</Note>

Sa liste déroulante affiche les valeurs d&#39;une étiquette Prometheus. Sélectionnez une **Data source** PromQL, puis saisissez le **Label** dont les valeurs alimentent la liste déroulante, par exemple `job`, `instance` ou `__name__`. Vous pouvez également saisir des **Series matchers** : un sélecteur de séries Prometheus, tel que `up{job="api"}`, qui restreint les séries dont les valeurs sont lues. Les **Series matchers** peuvent faire référence aux autres variables du tableau de bord.

Un filtre de valeurs d&#39;étiquette PromQL est toujours une variable et n&#39;est jamais diffusé. Dans les tuiles PromQL, référencez-le dans un matcher d&#39;étiquette, par exemple `rate(http_requests_total{job=~"$job"}[$__rate_interval])`. Consultez [Référencer une variable](#referencing-variables) pour savoir comment les valeurs sont générées.

#### Clés et valeurs ad hoc {#adhoc-filters}

Au lieu de proposer une seule liste déroulante, un filtre ad hoc permet au lecteur de construire une liste de conditions `key operator value` à partir des clés de ses sources : colonnes et clés de map pour les sources SQL, ou labels pour les sources Prometheus. Les clés et valeurs sont suggérées au fil de la saisie. Paramètres à configurer :

* **Type de source** — SQL (sources de logs, de traces ou de sessions) ou Prometheus.
* **Sources de données** — les sources dont le filtre suggère les clés et valeurs.
* **Filtre des clés et valeurs** — facultatif, sources SQL uniquement. Une condition SQL ou Lucene qui restreint les lignes à partir desquelles les clés et valeurs sont suggérées. Elle peut faire référence aux autres variables du tableau de bord.
* **S&#39;applique aux sources** — les sources auxquelles les conditions sont diffusées. Laissez ce champ vide pour les diffuser à toutes les tuiles qui utilisent l&#39;une des sources de données du filtre.
* **Nom unique** — identifie les conditions du filtre dans l&#39;[URL du tableau de bord](/fr/clickstack/url-parameters#dashboard-filter-values).

Les conditions sur les sources SQL prennent en charge les opérateurs suivants : `=`, `!=`, `=~` (expression régulière), `!~` (expression régulière), `LIKE`, `NOT LIKE`, `IN`. Les conditions sur les sources Prometheus prennent en charge `=`, `!=`, `=~` (expression régulière), `!~` (expression régulière) et `IN` — `LIKE` et `NOT LIKE` sont réservés à SQL.

Les lecteurs peuvent également ajouter une condition en cliquant sur une valeur dans une tuile de table, de série temporelle ou de recherche du tableau de bord.

Les conditions ad hoc sont toujours diffusées et ne peuvent pas être référencées en tant que variables. Les tuiles créées avec l&#39;éditeur de graphiques et les tuiles PromQL portant sur les sources correspondantes les prennent en compte automatiquement, tandis que les tuiles SQL brut les appliquent via la [macro `$__filters`](/fr/clickstack/features/dashboards/sql-visualizations#dashboard-filter-macro).

#### Source de données {#data-source-variables}

Une variable de source de données permet à l&#39;utilisateur de choisir la source interrogée par une tuile. Sélectionnez les **Source kinds** proposés dans sa liste déroulante (par exemple, uniquement les sources de logs) et, si besoin, limitez-les à une seule **Connection**, qui peut elle-même être une variable de connexion. Consultez [Variables de source de données et de connexion](#source-connection-variables) pour savoir comment les tuiles et les filtres l&#39;utilisent.

#### Connexion {#connection-variables}

Une variable de connexion permet à l&#39;utilisateur de choisir la connexion à ClickHouse utilisée par les tuiles SQL brut, les filtres dont les valeurs proviennent d&#39;une requête SQL et les variables de source de données. Elle n&#39;a aucun paramètre hormis son nom.

### Variables de source de données et de connexion {#source-connection-variables}

Les variables de source de données et de connexion remplacent un ID de source ou de connexion, et non une valeur dans le texte de la requête. Partout où un sélecteur de source ou de connexion les accepte, les variables du tableau de bord sont répertoriées sous un groupe **Variables**. Sélectionner l&#39;une d&#39;elles enregistre une référence `$name` qui se résout en la sélection actuelle du lecteur. Il est ainsi possible de créer un seul tableau de bord permettant de basculer, par exemple, entre les logs de plusieurs environnements ou entre plusieurs clusters ClickHouse.

| Utilisé dans                              | Accepte une variable de source de données      | Accepte une variable de connexion |
| ----------------------------------------- | ---------------------------------------------- | --------------------------------- |
| Tuiles de l&#39;éditeur de graphiques     | Source                                         | —                                 |
| Tuiles SQL brut                           | Source                                         | Connexion                         |
| Tuiles PromQL                             | Source                                         | —                                 |
| Filtres de valeurs d&#39;expression SQL   | Source de données, S&#39;applique aux sources  | —                                 |
| Filtres de valeurs d&#39;étiquette PromQL | Source de données                              | —                                 |
| Filtres ad hoc                            | Sources de données, S&#39;applique aux sources | —                                 |
| Filtres de valeurs de requête SQL         | Source                                         | Connexion                         |
| Variables de source de données            | —                                              | Connexion                         |

Une variable de source de données n&#39;est proposée que si au moins l&#39;un de ses types de source est compatible. Par exemple, une tuile PromQL ne propose que les variables de source de données qui autorisent les sources PromQL.

Les variables de source de données et de connexion sont toujours à sélection unique et obligatoires, car une tuile ne peut pas exécuter de requête sans source ni connexion. Tant qu&#39;aucune valeur n&#39;est sélectionnée, les tuiles et les filtres qui font référence à la variable restent en attente. Activez **Block every tile** pour bloquer plutôt l&#39;ensemble du tableau de bord. Un [lien de tableau de bord](/fr/clickstack/url-parameters#dashboard-filter-values) peut sélectionner une source ou une connexion aussi bien par son nom que par son ID.

<Note>
  Les alertes ne sont pas disponibles sur les tuiles qui utilisent une variable de source de données ou de connexion. L&#39;enregistrement d&#39;une telle tuile supprime son alerte.
</Note>

### Options de sélection {#filter-selection-options}

Les filtres de type valeurs d&#39;expression SQL, valeurs statiques, valeurs de requête SQL et valeurs d&#39;étiquette PromQL disposent des options supplémentaires suivantes :

* **Sélection unique** — une seule valeur peut être sélectionnée à la fois.
* **Obligatoire** — les tuiles qui utilisent le filtre, via sa variable ou par diffusion, ne se chargent pas tant qu&#39;aucune valeur n&#39;est sélectionnée dans le filtre.
  * **Bloquer toutes les tuiles** — bloque toutes les tuiles du tableau de bord tant qu&#39;aucune valeur n&#39;est sélectionnée dans le filtre, et pas seulement celles qui l&#39;utilisent.

### Filtres chaînés {#chained-filters}

La configuration d&#39;un filtre peut faire référence aux autres variables du tableau de bord, de sorte que ses valeurs dépendent de la sélection d&#39;un autre filtre. Par exemple, un filtre par service peut ne lister que les services de l&#39;environnement sélectionné par un filtre `environment`. Les variables peuvent être référencées dans :

* Le **Dropdown values filter** d&#39;un filtre de valeurs par expression SQL, par exemple `$__filter(ResourceAttributes['deployment.environment'], $environment)`.
* La **SQL query** d&#39;un filtre de valeurs par requête SQL.
* Les **Series matchers** d&#39;un filtre de valeurs d&#39;étiquettes PromQL, par exemple `up{env="$env"}`.
* Le **Keys and values filter** d&#39;un filtre ad hoc.
* Les champs de source et de connexion, via les [variables de source de données et de connexion](#source-connection-variables).

Lorsque la sélection du filtre référencé change, les valeurs du filtre dépendant sont de nouveau récupérées par une requête. Tant qu&#39;aucune valeur n&#39;est sélectionnée dans un filtre obligatoire référencé, un filtre ad hoc qui en dépend ne peut ni ajouter ni modifier de conditions, et indique le nom du filtre dont il attend la sélection.

<div id="broadcast-filters">
  ### Diffusion {#broadcast-filters}
</div>

Les filtres de valeurs d’expression SQL peuvent diffuser leur sélection, tandis que les filtres ad hoc diffusent toujours leurs conditions. Lorsque l’option **Diffuser la condition de filtre** est activée sur un filtre de valeurs d’expression SQL, les valeurs sélectionnées sont appliquées comme condition de filtre aux tuiles du tableau de bord, sans qu’aucune tuile ne fasse explicitement référence au filtre. Par défaut, la condition s’applique à toutes les tuiles. Utilisez **S’applique aux sources** pour la restreindre aux tuiles utilisant un ensemble donné de sources — ce qui est utile lorsque l’expression du filtre n’a de sens que pour certaines données du tableau de bord.

Les tuiles du générateur de graphiques prennent automatiquement en compte les filtres diffusés. Les tuiles Raw SQL doivent inclure la [macro `$__filters`](/fr/clickstack/features/dashboards/sql-visualizations#dashboard-filter-macro) et avoir une source sélectionnée, car ClickStack ne peut pas déterminer où insérer la condition dans une requête écrite manuellement.

<div id="dashboard-variables">
  ### Variables {#dashboard-variables}
</div>

Les filtres de type valeurs statiques, valeurs de requête SQL et valeurs d’étiquette PromQL sont toujours des variables. Un filtre de type valeurs d’expression SQL devient une variable lorsque l’option **Available as variable** est activée. Une variable rend la sélection du filtre accessible dans les requêtes des tuiles sous la forme de `$variableName`. Le champ **Variable name** reprend par défaut le nom d’affichage du filtre, après suppression des caractères non autorisés, et peut être surchargé. Les noms doivent commencer par une lettre et ne peuvent contenir que des lettres, des chiffres et des traits de soulignement.

Les filtres ad hoc ne sont jamais des variables, et les variables de source de données et de connexion sont des [références à une source ou à une connexion](#source-connection-variables) et non des valeurs insérées dans le texte de la requête.

Utilisez une variable lorsque la diffusion d’une condition `WHERE` ne convient pas — par exemple, pour utiliser la valeur dans une expression `SELECT`, une clause `HAVING` ou une clé de jointure, ou pour filtrer une tuile sur une colonne autre que l’expression du filtre elle-même.

<div id="referencing-variables">
  #### Référencer une variable {#referencing-variables}
</div>

Une variable est remplacée par les valeurs actuellement sélectionnées dans sa liste déroulante. La forme de référence détermine le rendu :

| Référence           | Se développe en                                                                                                                                                                                                            | Sélection vide                                |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `$name`, `${name}`  | Les valeurs sélectionnées, au format `sqlstring` ou `lucene`, selon le contexte. Les accolades délimitent le nom lorsqu&#39;il est suivi de caractères alphanumériques, comme dans `${name}_total`.                        | `NULL`                                        |
| `${name:sqlstring}` | Les valeurs sélectionnées, entre guillemets simples, séparées par des virgules et échappées comme des valeurs SQL, par ex. `'a', 'b'`                                                                                      | `NULL`                                        |
| `${name:csv}`       | Sans guillemets et séparées par des virgules : `a,b`. Non échappées pour SQL.                                                                                                                                              | chaîne vide                                   |
| `${name:regex}`     | Une alternance d&#39;expressions régulières, avec échappement regex : `(a\|b)`.                                                                                                                                            | `.*`                                          |
| `${name:lucene}`    | Un `OR` de termes entre guillemets, pour les entrées Lucene : `("a" OR "b")`.                                                                                                                                              | `("")`                                        |
| `${name:promql}`    | Forme par défaut dans les tuiles PromQL. Pour un filtre à sélection unique, la valeur sélectionnée, à utiliser dans `label="$name"`. Sinon, une alternance d&#39;expressions régulières, à utiliser dans `label=~"$name"`. | `.*` (chaîne vide en cas de sélection unique) |

Comme `$name` est remplacé par `NULL` tant qu&#39;aucune valeur n&#39;est sélectionnée, privilégiez les macros suivantes partout où un prédicat SQL est attendu. Toutes se développent en `1=1` tant que leur variable n&#39;a aucune sélection, afin que la requête reste valide :

| Macro                                         | Description                                                                                                                                                  |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `$__filter($<variable>)`                      | Se développe en `toString(<expression de filtre>) IN ($variable)` lorsque des valeurs sont sélectionnées pour `variable`, et en `1=1` dans le cas contraire. |
| `$__filter(<expression>, $<variable>)`        | Se développe en `<expression> IN ($variable)` lorsque des valeurs sont sélectionnées pour `variable`, et en `1=1` dans le cas contraire.                     |
| `$__conditionalAll(<condition>, $<variable>)` | Se développe en `<condition>` lorsque la variable a une sélection, et en `1=1` dans le cas contraire.                                                        |

<div id="variables-in-builder-tiles">
  #### Utiliser des variables dans les tuiles du générateur de graphiques {#variables-in-builder-tiles}
</div>

Chaque champ d’expression SQL du générateur de graphiques accepte des références à des variables : colonnes `SELECT`, expressions par série, `WHERE`, `GROUP BY` et `HAVING`. L’éditeur complète automatiquement les variables du tableau de bord et indique en quoi chaque référence se développe pour la sélection actuelle.

Privilégiez les macros `$__filter` et `$__conditionalAll` en mode SQL afin que les requêtes restent valides lorsque les sélections de variables sont vides. Les macros ne sont pas disponibles dans les champs Lucene : référencez directement les variables brutes (par ex. `ServiceName:$service`).

Dans un champ Lucene, le fait de mettre ou non la référence à la variable entre guillemets détermine comment une sélection de plusieurs valeurs est mise en correspondance. Si `$service` est sélectionné avec les valeurs `a,b` :

| Référence                | Se développe en                        | Comportement de correspondance                                                                           |
| ------------------------ | -------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `ServiceName:$service`   | `ServiceName:("a" OR "b")`             | Correspondance par sous-chaîne — traduit en SQL par `ServiceName ILIKE '%a%' OR ServiceName ILIKE '%b%'` |
| `ServiceName:"$service"` | `(ServiceName:"a" OR ServiceName:"b")` | Correspondance exacte avec chaque valeur sélectionnée                                                    |

Mettez la référence à la variable entre guillemets — `Field:"$var"` — lorsque les valeurs sélectionnées doivent correspondre exactement à `Field`, plutôt qu’à des sous-chaînes.

<div id="variables-in-sql-tiles">
  #### Utiliser des variables dans les tuiles SQL {#variables-in-sql-tiles}
</div>

Les tuiles Raw SQL référencent les variables de la même manière, où qu’elles se trouvent dans la requête :

```sql
SELECT
  $__timeInterval(TimestampTime) AS ts,
  count() AS count
FROM otel_logs
WHERE $__timeFilter(TimestampTime)
  AND $__filter(ServiceName, $service)
  AND $__conditionalAll(SeverityText NOT IN ($severity), $severity)
GROUP BY ts
ORDER BY ts ASC
```

Consultez les [visualisations SQL](/fr/clickstack/features/dashboards/sql-visualizations#dashboard-variables) pour obtenir la liste complète des macros disponibles dans les tuiles SQL.

<Note>
  Les alertes configurées sur une tuile qui fait référence à une variable de tableau de bord sont évaluées avec chaque variable dans son état vide, et non avec les valeurs sélectionnées dans le tableau de bord.
</Note>

Le tableau de bord des services affiche les services actuellement actifs à partir des données de traces. Cela nécessite d’avoir collecté des traces et configuré une source de données Traces valide.

Les noms des services sont détectés automatiquement à partir des données de traces, avec une série de visualisations prédéfinies réparties sur trois onglets : Services HTTP, Base de données et Erreurs.

Les visualisations peuvent être filtrées à l’aide de la syntaxe Lucene ou SQL, et la fenêtre de temps peut être ajustée pour une analyse ciblée.

### Tableau de bord Kubernetes {#kubernetes-dashboard}

Ce tableau de bord vous permet d’explorer les événements Kubernetes collectés via OpenTelemetry. Il propose des options de filtrage avancées pour filtrer par pod Kubernetes, déploiement, nom de nœud, espace de noms et cluster, ainsi que pour effectuer des recherches en texte libre.

Les données Kubernetes sont organisées en trois onglets pour faciliter la navigation : Pods, Nœuds et Espaces de noms.
