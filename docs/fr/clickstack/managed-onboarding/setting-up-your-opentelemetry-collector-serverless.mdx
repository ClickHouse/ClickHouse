<Info>
  **En bref**

  Vous exécutez déjà un collecteur OpenTelemetry ? Copiez l&#39;extrait de configuration de l&#39;exportateur depuis la page Premiers pas de votre service dans la configuration du collecteur, ajoutez l&#39;exportateur à vos pipelines, puis rechargez la configuration. Vos récepteurs et processeurs existants continuent de fonctionner, et tout ce qu&#39;ils collectent est acheminé vers ClickHouse Observability.

  Temps nécessaire : environ 10 minutes
</Info>

Vous avez créé votre service ClickHouse Observability. Ce guide s&#39;adresse à vous si un collecteur OpenTelemetry assure déjà la collecte dans votre environnement, par exemple pour :

* **La télémétrie d&#39;infrastructure.** Métriques de CPU, de mémoire, de disque et de réseau des hôtes, ainsi que fichiers de log sur disque.
* **Kubernetes.** Logs des conteneurs, métriques du kubelet et du cluster, et événements Kubernetes.
* **Des points de terminaison des métriques existants.** Scraping des points de terminaison Prometheus que vos services exposent déjà.
* **Une [passerelle](/fr/clickstack/ingesting-data/collector#collector-roles).** Un endpoint unique au sein de votre réseau qui reçoit l&#39;OTLP des SDK et des collecteurs agents, le regroupe par lots et le transmet depuis un point centralisé.

Quelles que soient les données recueillies par le collecteur, la connexion se fait de la même manière. Il suffit d&#39;un exportateur `otlp_http` pointant vers le point de terminaison OTLP géré de votre service. Vos récepteurs, processeurs et éventuels exportateurs existants restent inchangés : vous pouvez ainsi envoyer les données en parallèle vers votre backend actuel et vers ClickHouse Observability pendant votre évaluation. ClickHouse Observability prend ensuite en charge l&#39;ingestion, les schémas, le stockage, l&#39;optimisation et la mise à l&#39;échelle.

<Note>
  **Pas encore de collecteur ?**

  Vous n&#39;en avez pas besoin pour commencer. Les applications peuvent exporter leurs données OpenTelemetry directement vers l&#39;endpoint géré : consultez [Instrumenter votre application avec OpenTelemetry](/fr/clickstack/managed-onboarding/instrument-application-serverless). Pour commencer à collecter la télémétrie d&#39;infrastructure, les guides [Logs et métriques locaux](/fr/clickstack/observability/example-datasets/local-data) et [Supervision de Kubernetes](/fr/clickstack/observability/example-datasets/kubernetes) fournissent chacun une configuration complète du collecteur, prête à être déployée telle quelle.
</Note>

## Prérequis {#prerequisites}

* Un service ClickHouse Observability. Si vous n&#39;en avez pas encore, suivez le [Guide de démarrage](/fr/clickstack/observability/getting-started).
* Un collecteur OpenTelemetry que vous pouvez reconfigurer et redémarrer. N&#39;importe quelle distribution convient, y compris les versions compilées proposées par les éditeurs, car l&#39;exportateur `otlp_http` fait partie du collecteur de base.
* Un accès HTTPS sortant sur le port `4318` depuis l&#39;hôte du collecteur vers l&#39;endpoint de télémétrie de votre service.

## Connecter votre collecteur {#connect-your-collector}

<Steps>
  <Step title="Copiez la configuration de l'exportateur" id="copy-exporter-configuration">
    Ouvrez votre service ClickHouse Observability. Tant qu&#39;aucune donnée n&#39;a été reçue, il affiche la page **Start sending telemetry**.

    <div className="ch-image-lg">
      <Frame>
        ![Page Start sending telemetry affichant le service actuel, encore sans données, et trois options : Use an existing OpenTelemetry setup, Instrument with AI et Follow setup guides](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    Sous **Use an existing OpenTelemetry setup**, sélectionnez **View connection details**, puis ouvrez l&#39;onglet **Collector config**. Celui-ci affiche un bloc d&#39;exportateur prêt à l&#39;emploi pour votre service. Sélectionnez **Reveal key** pour afficher l&#39;API key complète, puis cliquez sur le bouton de copie.

    <div className="ch-image-md">
      <Frame>
        ![Boîte de dialogue Set up OpenTelemetry avec l'onglet Collector config sélectionné, montrant un exportateur otlphttp avec l'endpoint masqué et un en-tête d'autorisation Bearer](/images/clickstack/getting-started/observability-collector-config.png)
      </Frame>
    </div>

    L&#39;extrait se présente ainsi :

    ```yaml
    exporters:
      otlphttp:
        endpoint: https://YOUR_OTEL_ENDPOINT:4318
        headers:
          authorization: Bearer <your-api-key>
    ```

    Deux points sont à noter. L&#39;endpoint correspond à l&#39;URL de base : n&#39;y ajoutez pas `/v1/logs`, `/v1/traces` ou `/v1/metrics`, car l&#39;exportateur ajoute lui-même le chemin propre à chaque signal. La valeur de l&#39;en-tête comprend le préfixe `Bearer`.

    L&#39;UI nomme l&#39;exportateur `otlphttp`. Les versions récentes du collecteur l&#39;appellent `otlp_http` et conservent `otlphttp` comme alias obsolète : les deux noms fonctionnent donc. Les exemples ci-dessous utilisent le nom actuel.

    Vous retrouverez ces valeurs à tout moment sous **Paramètres de l’équipe → Télémétrie gérée**.
  </Step>

  <Step title="Ajoutez l'exportateur" id="add-the-exporter">
    Ajoutez le bloc à la section `exporters` de la configuration de votre collecteur. En fournissant la clé par une variable d&#39;environnement, vous évitez de l&#39;inscrire dans le fichier :

    ```yaml
    exporters:
      otlp_http:
        endpoint: ${env:CLICKSTACK_OTLP_ENDPOINT}
        headers:
          authorization: "Bearer ${env:CLICKSTACK_API_KEY}"
    ```

    Si votre configuration comporte déjà un exportateur nommé `otlp_http`, donnez à celui-ci un nom distinct, par exemple `otlp_http/clickhouse`, et utilisez ce nom à l&#39;étape suivante.

    Si le collecteur s&#39;exécute dans Kubernetes, stockez la clé dans un Secret et exposez les deux valeurs via `extraEnvs` ou la spec du pod. Le guide [Supervision de Kubernetes](/fr/clickstack/observability/example-datasets/kubernetes) illustre ce modèle avec le chart Helm OpenTelemetry.
  </Step>

  <Step title="Ajoutez-le à vos pipelines" id="add-to-pipelines">
    Ajoutez l&#39;exportateur à chaque pipeline dont vous souhaitez envoyer les données vers ClickHouse Observability. Conservez vos exportateurs existants pour alimenter les deux destinations en parallèle :

    ```yaml
    service:
      pipelines:
        logs:
          receivers: [otlp, file_log]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
        metrics:
          receivers: [otlp, host_metrics, prometheus]
          processors: [memory_limiter, batch]
          exporters: [otlp_http, your_existing_exporter]
    ```

    Vos récepteurs et processeurs restent inchangés : seules les listes d&#39;exportateurs sont modifiées.

    <Info>
      **Rôles agent et passerelle**

      Si des collecteurs agents s&#39;exécutent sur chaque hôte et transmettent les données à une passerelle centrale, modifiez uniquement la passerelle. Les agents continuent d&#39;envoyer leurs données à la passerelle comme auparavant.
    </Info>
  </Step>

  <Step title="Rechargez et vérifiez les logs" id="reload-and-check">
    Dans l&#39;environnement du collecteur, définissez `CLICKSTACK_OTLP_ENDPOINT` sur l&#39;URL de l&#39;endpoint et `CLICKSTACK_API_KEY` sur la clé, quel que soit le mode de transmission de sa configuration : unité systemd, option Docker `-e` ou Secret Kubernetes. Redémarrez ou rechargez ensuite le collecteur et surveillez ses logs pour repérer d&#39;éventuelles erreurs d&#39;exportation :

    * Des réponses `401` ou `403` indiquent que l&#39;API key est incorrecte ou que le préfixe `Bearer` est absent.
    * Des réponses `404` indiquent généralement qu&#39;un chemin de signal tel que `/v1/logs` a été ajouté à l&#39;endpoint.
    * Des erreurs `no such host` ou TLS signalent une faute de frappe dans l&#39;endpoint ou une connexion sortante bloquée sur le port `4318`.

    Toutes les données que le collecteur recueillait déjà sont désormais également envoyées vers votre service.
  </Step>
</Steps>

## Vérifier la réception des données {#confirm-data-is-arriving}

Revenez à la page **Start sending telemetry** de votre service et sélectionnez **Check for data**. Une fois votre télémétrie reçue, le statut du service passe à **Data received** et le bouton **Start exploring** devient disponible.

<div className="ch-image-lg">
  <Frame>
    ![Page Start sending telemetry affichant le statut du service Data received, une confirmation indiquant que vous êtes prêt à explorer et le bouton Start exploring activé](/images/clickstack/getting-started/observability-data-received.png)
  </Frame>
</div>

Sélectionnez **Start exploring** pour ouvrir **Recherche**. Sélectionnez la source **Logs**, réglez l&#39;intervalle de temps sur **Last 15 minutes** et filtrez sur un `ServiceName` remonté par votre collecteur. Dans l&#39;**Explorateur de graphiques**, basculez la source sur **Metrics** pour vérifier que les données des récepteurs de métriques arrivent également.

## Si rien ne s’affiche {#if-nothing-shows-up}

* Consultez d’abord les logs du collecteur. Les problèmes d’authentification, d’endpoint et de TLS y sont tous signalés, avec les codes d’erreur répertoriés ci-dessus.
* Vérifiez que chaque pipeline censé envoyer des données inclut `otlp_http` dans ses `exporters`. Un récepteur défini mais référencé par aucun pipeline ne collecte rien.
* Vérifiez que le collecteur a bien été rechargé. Certaines distributions nécessitent un redémarrage, et non un simple rechargement de la configuration, pour prendre en compte un nouvel exportateur.
* Élargissez l’intervalle de temps dans **Recherche** et supprimez tous les filtres. Il se peut que la source par défaut soit définie sur **Traces** plutôt que sur **Logs**.
* Pour mettre hors de cause le service lui-même, accédez à **Paramètres de l’équipe → Télémétrie gérée** et utilisez **Send a Test Log**. Si ce log apparaît dans **Recherche**, le service reçoit bien des données et le problème se situe entre votre collecteur et l’endpoint.
* Pour isoler votre collecteur, dirigez le générateur `telemetrygen` de la section [Envoyer des données d’exemple](#send-sample-data) vers le récepteur OTLP du collecteur lui-même plutôt que vers le service, au format `host:port` sans schéma, par exemple `--otlp-endpoint localhost:4317 --otlp-insecure` sans `--otlp-http`. Si ces données arrivent, l’exportateur du collecteur fonctionne correctement et le problème se situe en amont de celui-ci.

## Collecter davantage de données avec votre collecteur {#collect-more}

Une fois l’exportateur en place, chaque récepteur que vous ajoutez envoie ses données vers votre service via le même pipeline :

* [Logs et métriques locaux](/fr/clickstack/observability/example-datasets/local-data) : une configuration complète qui suit les fichiers de log avec le récepteur `file_log` et collecte les métriques CPU, mémoire, disque et réseau avec le récepteur `host_metrics`.
* [Supervision de Kubernetes](/fr/clickstack/observability/example-datasets/kubernetes) : un DaemonSet pour les logs des conteneurs et les métriques kubelet, ainsi qu’un Déploiement pour les métriques et les événements du cluster, installés avec le chart Helm OpenTelemetry.
* **Points de terminaison Prometheus.** Ajoutez au pipeline `metrics` le [récepteur `prometheus`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/prometheusreceiver) avec vos `scrape_configs` existants. Les séries collectées arrivent sous forme de métriques OpenTelemetry et apparaissent dans l’Explorateur de graphiques.
* **SDK via la passerelle.** Faites pointer vos applications vers le collecteur en définissant `OTEL_EXPORTER_OTLP_ENDPOINT` sur son adresse, par exemple `http://otel-collector.observability.svc:4318`. Le guide [Instrumenter votre application avec OpenTelemetry](/fr/clickstack/managed-onboarding/instrument-application-serverless) explique pas à pas comment instrumenter une application de démonstration ; remplacez l’endpoint managé par l’adresse de votre collecteur et supprimez l’API key, désormais fournie par la passerelle.
* **Traitement au niveau de la passerelle.** Utilisez les processeurs [`filter`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/filterprocessor), [`transform`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/transformprocessor) et [`resourcedetection`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/resourcedetectionprocessor) pour éliminer le bruit, restructurer les attributs et enrichir la télémétrie de métadonnées de cloud et d’hôte avant qu’elle ne quitte votre réseau.

Pour en savoir plus sur le collecteur lui-même, la [documentation du Collecteur OpenTelemetry](https://opentelemetry.io/docs/collector/) présente les modèles de déploiement, la mise à l’échelle et la référence complète de configuration.

## Pas encore de télémétrie en direct ? Envoyez des données d’exemple {#send-sample-data}

Si votre collecteur est connecté mais que ses sources restent silencieuses, ou si vous souhaitez disposer de données plus riches pour explorer l’UI, envoyez une rafale de logs, de traces et de métriques synthétiques directement à votre service. Cette méthode contourne votre collecteur et reprend les informations de connexion de l’onglet **Env vars** : vous n’avez donc rien à ressaisir.

Ouvrez **View connection details** depuis la page **Start sending telemetry**, ou **Paramètres de l’équipe → Télémétrie gérée**, puis sélectionnez l’onglet **Env vars**. Cliquez sur **Reveal key**, copiez le contenu de l’onglet et collez-le dans votre interpréteur de commandes entre `set -a` et `set +a`, afin que chaque ligne soit exportée :

<div className="ch-image-md">
  <Frame>
    ![Boîte de dialogue Set up OpenTelemetry avec l’onglet Env vars sélectionné, affichant OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_EXPORTER_OTLP_HEADERS avec une clé Bearer masquée, et OTEL_EXPORTER_OTLP_PROTOCOL](/images/clickstack/getting-started/observability-env-vars.png)
  </Frame>
</div>

```shell
set -a
# Paste the Env vars tab here. It looks like this:
OTEL_EXPORTER_OTLP_ENDPOINT=https://YOUR_OTEL_ENDPOINT:4318
OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer <your-api-key>"
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
set +a
```

Exécutez [`telemetrygen`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/telemetrygen), le générateur de données d&#39;OpenTelemetry Collector Contrib, à partir de son image Docker :

```shell
telemetrygen() {
  docker run --rm \
    ghcr.io/open-telemetry/opentelemetry-collector-contrib/telemetrygen:latest "$@"
}
```

Vous pouvez aussi installer le binaire avec Go :

```shell
go install github.com/open-telemetry/opentelemetry-collector-contrib/cmd/telemetrygen@latest
```

Définissez une petite fonction utilitaire `tg`. Elle extrait l’hôte et le port de `OTEL_EXPORTER_OTLP_ENDPOINT`, ainsi que la clé de `OTEL_EXPORTER_OTLP_HEADERS`, car l’option d’endpoint de `telemetrygen` n’accepte pas de schéma d’URL. Elle envoie les données en OTLP via HTTPS avec vérification du certificat, et chaque exécution dure 20 secondes :

```shell
tg() { local signal=$1; shift; telemetrygen "$signal" \
  --otlp-endpoint "${OTEL_EXPORTER_OTLP_ENDPOINT#*://}" --otlp-http \
  --otlp-header "authorization=\"${OTEL_EXPORTER_OTLP_HEADERS#authorization=}\"" \
  --rate 5 --duration 20s "$@"; }
```

Appelez toujours `tg` plutôt que d&#39;appeler `telemetrygen` directement. Si vous transmettez l&#39;URL complète en `https://` à `telemetrygen`, la commande échoue avec l&#39;erreur `too many colons in address`.

Envoyez des log présentant un mélange réaliste de niveaux de gravité, répartis sur trois services :

```shell
tg logs --service frontend --severity-text Info  --severity-number 9  --body "GET /api/products 200" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="GET"' --telemetry-attributes 'http.status_code="200"'
tg logs --service checkout --severity-text Warn  --severity-number 13 --body "retrying payment authorization" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.method="POST"'
tg logs --service payment  --severity-text Error --severity-number 17 --body "payment gateway timeout" \
  --otlp-attributes 'deployment.environment="production"' \
  --telemetry-attributes 'http.status_code="500"'
```

Chaque commande se termine par un récapitulatif `logs generated`. En cas de clé incorrecte, la commande échoue immédiatement avec un code `401` dans le message d&#39;erreur.

Pour remplir également les traces, la cartographie des services et les métriques, développez et exécutez les commandes ci-dessous dans le même interpréteur de commandes.

<Accordion title="Générer une télémétrie plus riche (facultatif)">
  Envoyez des traces composées de plusieurs spans, issues de plusieurs services sains ainsi que d&#39;une dépendance lente et défaillante :

  ```shell
  for svc in frontend checkout cart; do
    tg traces --service "$svc" --child-spans 3 --span-duration 80ms --status-code Ok \
      --otlp-attributes 'deployment.environment="production"' \
      --telemetry-attributes "http.route=\"/$svc\""
  done

  tg traces --service payment --child-spans 3 --span-duration 450ms --span-links 1 --status-code Error \
    --otlp-attributes 'deployment.environment="production"' \
    --telemetry-attributes 'http.route="/charge"'
  ```

  Envoyez un compteur, une jauge et un histogramme :

  ```shell
  tg metrics --service frontend --metric-type Sum       --otlp-metric-name http.server.requests --aggregation-temporality cumulative
  tg metrics --service frontend --metric-type Gauge     --otlp-metric-name system.memory.usage
  tg metrics --service payment  --metric-type Histogram --otlp-metric-name http.server.duration
  ```
</Accordion>

De retour dans votre service, sélectionnez **Check for data**, puis **Start exploring**. Dans **Recherche**, filtrez `ServiceName` sur `frontend`, `checkout` ou `payment`, et `SeverityText` sur `Error` afin de repérer les dépassements de délai de la passerelle de paiement. Si vous avez généré le jeu de données enrichi, ouvrez une trace `payment` dans la source **Traces** pour afficher ses spans enfants et son statut d&#39;erreur, puis créez un graphique de `http.server.requests` dans **Explorateur de graphiques** pour vérifier que les métriques remontent bien.
