<Info>
  **En bref**

  Choisissez les groupes de journaux CloudWatch souhaités, collez le bloc de l&#39;exportateur depuis l&#39;onglet **Collector config** de votre service dans une configuration minimale du collecteur OpenTelemetry, puis démarrez-le avec Docker Compose. Il interroge les groupes de journaux et envoie chaque événement directement à ClickHouse Observability, étiqueté avec son groupe de journaux et son flux.

  Durée estimée : environ 15 minutes
</Info>

Vous avez créé votre service ClickHouse Observability. Ce guide s&#39;adresse à vous si les logs qui vous intéressent se trouvent déjà dans CloudWatch : fonctions Lambda, tâches ECS, RDS, journaux de flux VPC ou toute autre source qui écrit dans un groupe de journaux.

L&#39;approche repose sur le fonctionnement standard d&#39;OpenTelemetry. Un seul collecteur doté du [récepteur `aws_cloudwatch`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/awscloudwatchreceiver) interroge vos groupes de journaux via l&#39;API CloudWatch Logs et envoie les événements directement au point de terminaison OTLP de votre service. Il peut s&#39;exécuter n&#39;importe où, pourvu que Docker soit disponible et que l&#39;API AWS soit accessible. Une instance EC2 située dans la même région que les groupes de journaux permet de limiter la latence de l&#39;API et les coûts de transfert de données.

## Prérequis {#prerequisites}

* Un service ClickHouse Observability. Si vous n&#39;en avez pas encore, suivez le [guide de démarrage](/fr/clickstack/observability/getting-started).
* Un compte AWS comportant un ou plusieurs groupes de journaux CloudWatch, ainsi que la permission de créer ou d&#39;utiliser des identifiants autorisés à les lire.
* Un hôte disposant de Docker, de l&#39;[AWS CLI](https://aws.amazon.com/cli/) et d&#39;un accès HTTPS sortant sur le port `4318` vers l&#39;endpoint de télémétrie de votre service.

Exécutez les commandes AWS et Docker depuis un même interpréteur de commandes sur cet hôte : le collecteur récupère ses identifiants AWS dans l&#39;environnement de cet interpréteur.

## Configurer le collecteur {#set-up-the-collector}

<Steps>
  <Step title="Configurer les identifiants AWS" id="set-up-aws-credentials">
    Le récepteur utilise la chaîne d’informations d’authentification standard du SDK AWS : tout ce qui fonctionne avec l’AWS CLI fonctionne donc également avec le collecteur. Les identifiants doivent permettre de lister les groupes de journaux et de lire leurs événements :

    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Sid": "CloudWatchLogsList",
          "Effect": "Allow",
          "Action": "logs:DescribeLogGroups",
          "Resource": "*"
        },
        {
          "Sid": "CloudWatchLogsRead",
          "Effect": "Allow",
          "Action": "logs:FilterLogEvents",
          "Resource": "arn:aws:logs:*:YOUR_ACCOUNT_ID:log-group:*"
        }
      ]
    }
    ```

    Remplacez `YOUR_ACCOUNT_ID` par l’ID de votre compte AWS. Exportez les identifiants, puis vérifiez qu’ils fonctionnent :

    <Tabs>
      <Tab title="AWS SSO" id="aws-sso">
        ```shell
        aws sso login --profile YOUR_PROFILE_NAME
        eval $(aws configure export-credentials --profile YOUR_PROFILE_NAME --format env)
        aws sts get-caller-identity
        ```

        Les identifiants SSO expirent, généralement au bout de 8 à 12 heures. Réexécutez ces commandes pour renouveler et exporter les identifiants, puis exécutez `docker compose up -d --force-recreate otel-collector` depuis le répertoire Compose. La recréation du conteneur applique les nouvelles variables d’environnement, alors qu’un simple redémarrage conserve les identifiants expirés. Les clés d’accès ou un rôle d’instance permettent d’éviter cette interruption.
      </Tab>

      <Tab title="Clés d’accès IAM" id="iam-access-keys">
        ```shell
        export AWS_ACCESS_KEY_ID="your-access-key-id"
        export AWS_SECRET_ACCESS_KEY="your-secret-access-key"
        export AWS_REGION="us-east-1"
        aws sts get-caller-identity
        ```
      </Tab>
    </Tabs>

    <Info>
      **Identifiants de production**

      En production, plutôt que d’exporter des clés, rattachez la politique à l’hôte : un rôle IAM sur EC2, IRSA sur EKS ou un rôle de task sur ECS. Le collecteur récupère alors les identifiants auprès du service de métadonnées d’instance, et le fichier Compose ci-dessous ne nécessite aucune variable AWS.
    </Info>
  </Step>

  <Step title="Sélectionnez vos groupes de journaux" id="pick-your-log-groups">
    Listez les groupes de journaux de votre région afin de récupérer leurs noms exacts et de vérifier que vous utilisez la bonne région :

    ```shell
    aws logs describe-log-groups --region us-east-1 \
      --query 'logGroups[].logGroupName' --output table
    ```

    Notez les noms qui vous intéressent. Les groupes qui partagent un même préfixe, comme `/aws/lambda/`, peuvent être sélectionnés ensemble lors de l&#39;écriture de la configuration.
  </Step>

  <Step title="Copiez vos informations de connexion" id="copy-connection-details">
    Ouvrez votre service ClickHouse Observability. Tant qu’aucune donnée n’a été reçue, il affiche la page **Start sending telemetry**.

    <div className="ch-image-lg">
      <Frame>
        ![Page Start sending telemetry affichant le service actuel, encore sans données, et trois options : Use an existing OpenTelemetry setup, Instrument with AI et Follow setup guides](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    Sous **Use an existing OpenTelemetry setup**, sélectionnez **View connection details**, puis ouvrez l’onglet **Collector config**. Celui-ci affiche un bloc d’exportateur prêt à l’emploi pour votre service : l’endpoint, ainsi qu’un en-tête `authorization` qui contient déjà votre API key précédée du préfixe `Bearer`. Sélectionnez **Reveal key** pour afficher la clé en entier, puis cliquez sur le bouton de copie.

    <div className="ch-image-md">
      <Frame>
        ![Boîte de dialogue Set up OpenTelemetry avec l’onglet Collector config sélectionné, affichant un exportateur otlphttp avec l’endpoint masqué et un en-tête d’autorisation Bearer](/images/clickstack/getting-started/observability-collector-config.png)
      </Frame>
    </div>

    Le bloc présente la structure suivante. À l’étape suivante, vous le collerez tel quel dans la configuration du collecteur :

    ```yaml
    exporters:
      otlphttp:
        endpoint: https://YOUR_OTEL_ENDPOINT:4318
        headers:
          authorization: Bearer <your-api-key>
    ```

    Vous pouvez retrouver ces mêmes valeurs à tout moment dans **Paramètres de l’équipe → Télémétrie gérée**.
  </Step>

  <Step title="Rédigez la configuration du collecteur" id="write-the-configuration">
    Créez `otel-collector-config.yaml` à partir de la variante correspondant à la façon dont vous souhaitez sélectionner les groupes de journaux, puis remplacez son bloc `exporters` par celui que vous avez copié. Au démarrage, les deux variantes lisent les événements de la dernière heure.

    <Tabs>
      <Tab title="Groupes de journaux nommés" id="named-log-groups">
        ```yaml
        receivers:
          aws_cloudwatch:
            region: us-east-1
            logs:
              poll_interval: 1m
              initial_lookback: 1h
              groups:
                named:
                  /aws/lambda/payment-processor:
                  /aws/lambda/order-service:
                  /ecs/api-gateway:

        processors:
          batch:
            timeout: 10s

        exporters:
          otlphttp:
            endpoint: https://YOUR_OTEL_ENDPOINT:4318
            headers:
              authorization: Bearer <your-api-key>

        service:
          pipelines:
            logs:
              receivers: [aws_cloudwatch]
              processors: [batch]
              exporters: [otlphttp]
        ```

        Chaque clé sous `named` correspond à un groupe de journaux. Laissez la valeur vide pour lire tous les flux du groupe, ou ajoutez-y `names:` ou `prefixes:` pour ne lire que certains flux.
      </Tab>

      <Tab title="Découverte automatique par préfixe" id="autodiscover-by-prefix">
        ```yaml
        receivers:
          aws_cloudwatch:
            region: us-east-1
            logs:
              poll_interval: 1m
              initial_lookback: 1h
              groups:
                autodiscover:
                  limit: 100
                  prefix: /aws/lambda/

        processors:
          batch:
            timeout: 10s

        exporters:
          otlphttp:
            endpoint: https://YOUR_OTEL_ENDPOINT:4318
            headers:
              authorization: Bearer <your-api-key>

        service:
          pipelines:
            logs:
              receivers: [aws_cloudwatch]
              processors: [batch]
              exporters: [otlphttp]
        ```

        Cette configuration lit tous les groupes de journaux dont le nom commence par le préfixe indiqué, dans la limite fixée par `limit`, y compris ceux créés ultérieurement. Utilisez `pattern` au lieu de `prefix` pour rechercher une sous-chaîne à n’importe quelle position du nom.
      </Tab>
    </Tabs>

    Le nom d’exportateur `otlphttp` correspond à celui fourni par l’onglet. Les versions récentes du collecteur le nomment `otlp_http` et conservent `otlphttp` comme alias : les deux fonctionnent donc, et le collecteur consigne une seule fois au démarrage le message `"otlphttp" alias is deprecated`. Cet avertissement est sans conséquence. Si vous renommez l’exportateur, renommez-le également dans le pipeline. Indiquez l’URL de base comme endpoint : n’y ajoutez pas `/v1/logs`, car l’exportateur ajoute lui-même le chemin propre au signal.

    Le fichier contient désormais votre API key ; ne l&#39;ajoutez donc pas au contrôle de version. Le conteneur du collecteur s&#39;exécute avec l&#39;UID/GID `10001:10001`. Sous Linux, accordez l&#39;accès en lecture à ce groupe tout en laissant le fichier modifiable par son propriétaire sur l&#39;hôte :

    ```shell
    sudo chgrp 10001 otel-collector-config.yaml
    chmod 640 otel-collector-config.yaml
    ```

    Le conteneur peut ainsi lire la configuration montée via un bind mount sans que l&#39;API key soit lisible par tous.

    Paramètres à ajuster :

    * `region` : la région où se trouvent les groupes de journaux.
    * `initial_lookback` : jusqu&#39;où remonter dans le temps lors de la lecture au démarrage du collecteur. Sans ce paramètre, le récepteur lit l&#39;intégralité de l&#39;historique conservé de chaque groupe, ce qui peut entraîner un chargement de données historiques ponctuel volumineux, avec les appels à l&#39;API correspondants. Pour effectuer plutôt un chargement de données historiques à partir d&#39;un point précis, remplacez-le par `start_from` et un timestamp au format RFC 3339.
    * `poll_interval` : `1m` par défaut. Des intervalles plus courts fournissent des logs plus récents, au prix d&#39;un plus grand nombre d&#39;appels à l&#39;API.
    * Chaque redémarrage relit la fenêtre rétrospective : la dernière heure apparaît donc en double après un restart. Pour un déploiement long-running, ajoutez l&#39;extension `file_storage` et définissez l&#39;option `storage` du récepteur afin qu&#39;il reprenne là où il s&#39;était arrêté.

    Le [README](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/awscloudwatchreceiver) du récepteur décrit les autres options, notamment les filtres de flux et la lecture depuis des comptes liés.

    <Accordion title="Facultatif : utilisez le groupe de journaux comme nom du service">
      Les événements CloudWatch ne contiennent aucun nom de service : `ServiceName` est donc vide dans la page Recherche et les filtres de service restent sans effet. Pour le renseigner à partir du groupe de journaux, ajoutez un processeur `transform` et placez-le avant `batch` dans le pipeline :

      ```yaml
      processors:
        transform:
          log_statements:
            - context: resource
              statements:
                - set(attributes["service.name"], attributes["cloudwatch.log.group.name"])
        batch:
          timeout: 10s

      service:
        pipelines:
          logs:
            receivers: [aws_cloudwatch]
            processors: [transform, batch]
            exporters: [otlphttp]
      ```
    </Accordion>
  </Step>

  <Step title="Démarrez-le avec Docker Compose" id="start-with-docker-compose">
    Créez le fichier `docker-compose.yaml` à côté du fichier de configuration. Il monte la configuration dans le conteneur et y transmet vos identifiants AWS depuis l’interpréteur de commandes :

    ```yaml
    services:
      otel-collector:
        image: otel/opentelemetry-collector-contrib:0.162.0
        command: ["--config=/etc/otel-config.yaml"]
        volumes:
          - type: bind
            source: ./otel-collector-config.yaml
            target: /etc/otel-config.yaml
            read_only: true
        environment:
          - AWS_ACCESS_KEY_ID
          - AWS_SECRET_ACCESS_KEY
          - AWS_SESSION_TOKEN
          - AWS_REGION
        restart: unless-stopped
    ```

    Démarrez-le et surveillez les logs :

    ```shell
    docker compose up -d
    docker compose logs -f otel-collector
    ```

    Un démarrage réussi se termine par `Everything is ready. Begin running and processing data.` La première interrogation a lieu un `poll_interval` après le démarrage ; prévoyez donc une minute ou deux. Erreurs courantes à identifier :

    * `panic: runtime error: invalid memory address or nil pointer dereference` dans `ensureSession`, suivi d’un redémarrage du conteneur : le collecteur n’a pas pu s’authentifier auprès d’AWS. Les identifiants sont manquants, invalides ou expirés, ou l’endpoint STS est injoignable. La version 0.162.0 du collecteur signale ce problème par un plantage plutôt que par un message d’erreur, un comportement suivi en amont dans le [ticket 50961](https://github.com/open-telemetry/opentelemetry-collector-contrib/issues/50961). Exécutez `aws sts get-caller-identity` sur l’hôte, rafraîchissez et exportez des identifiants valides, puis exécutez `docker compose up -d --force-recreate otel-collector` depuis le répertoire Compose.
    * `AccessDeniedException` : les identifiants doivent disposer de `logs:DescribeLogGroups` avec `"Resource": "*"` et de `logs:FilterLogEvents` sur les groupes de journaux concernés.
    * `ResourceNotFoundException` : le nom d’un groupe de journaux est mal orthographié ou le groupe se trouve dans une autre région.
    * `401` ou `403` renvoyé par l’exportateur : la valeur `authorization` de la configuration est incorrecte. Elle doit contenir `Bearer` suivi de la clé complète, telle qu’indiquée dans l’onglet de configuration du collecteur. Corrigez le fichier et exécutez `docker compose restart otel-collector`.
    * `404` renvoyé par l’exportateur : un chemin de signal tel que `/v1/logs` a été ajouté à la fin de l’endpoint.
  </Step>
</Steps>

## Vérifier la réception des données {#confirm-data-is-arriving}

Revenez à la page **Start sending telemetry** de votre service et sélectionnez **Check for data**. Dès que la télémétrie est reçue, le statut du service passe à **Data received** et le bouton **Start exploring** devient disponible.

<div className="ch-image-lg">
  <Frame>
    ![Page Start sending telemetry affichant le statut du service Data received, une confirmation que vous êtes prêt à explorer les données et le bouton Start exploring activé](/images/clickstack/getting-started/observability-data-received.png)
  </Frame>
</div>

Sélectionnez **Start exploring** pour ouvrir **Recherche**, choisissez la source **Logs** et réglez l&#39;intervalle de temps sur **Last 15 minutes**. Les événements apparaissent au bout de quelques intervalles d’interrogation. Chacun d&#39;eux indique son origine sous forme d&#39;attributs de ressource :

* `aws.region` : la région que vous avez configurée.
* `cloudwatch.log.group.name` : le groupe de journaux source.
* `cloudwatch.log.stream` : le flux de logs source.
* `cloud.account.id` : le compte AWS d&#39;où proviennent les événements.

Pour les afficher sous forme de colonnes, remplacez le contenu du `SELECT` par `Timestamp, SeverityText as level, ResourceAttributes['aws.region'], ResourceAttributes['cloudwatch.log.group.name'], ResourceAttributes['cloudwatch.log.stream'], Body` :

## Si rien ne s’affiche {#if-nothing-shows-up}

* Consultez d’abord les logs du collecteur avec `docker compose logs -f otel-collector`. Les problèmes liés à AWS comme ceux liés à l’exportateur y sont signalés avec les messages indiqués ci-dessus.
* Exécutez `aws sts get-caller-identity` sur l’hôte pour vérifier que les identifiants sont toujours valides. Les sessions SSO expirent, et lorsque c’est le cas, le collecteur plante au lieu de journaliser une erreur.
* Vérifiez que le groupe a reçu des événements récemment, car le récepteur ne lit que les événements écrits pendant la fenêtre rétrospective ou après. Par exemple : `aws logs filter-log-events --log-group-name /aws/lambda/order-service --region us-east-1 --limit 5`.
* Élargissez l’intervalle de temps dans **Recherche** et supprimez tous les filtres. Il se peut que la source par défaut soit définie sur **Traces** plutôt que sur **Logs**.
* Pour écarter un problème lié au service lui-même, accédez à **Paramètres de l’équipe → Télémétrie gérée** et utilisez **Envoyer un log de test**. Si ce log apparaît dans **Recherche**, le service reçoit bien les données et le problème se situe entre le collecteur et CloudWatch ou l’endpoint.
