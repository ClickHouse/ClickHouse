<Info>
  **En bref**

  Ajoutez l’endpoint compatible Datadog de votre service aux agents Datadog que vous exécutez déjà, en parallèle de Datadog ou à sa place, puis redémarrez-les. Vos logs, traces et metrics apparaissent dans ClickHouse Observability. Aucun collecteur à déployer, aucune modification à apporter à vos applications.

  Durée estimée : environ 15 minutes
</Info>

Vous avez créé votre service ClickHouse Observability, et votre télémétrie transite déjà par des agents Datadog. Nul besoin de remplacer ces agents ni de modifier vos applications pour voir ce que le service fait de vos propres données.

ClickHouse Observability inclut un endpoint compatible Datadog. Il accepte les logs, traces et metrics que vos agents produisent déjà, les convertit au format OpenTelemetry et les stocke dans votre service. Seule la configuration des agents change. Vous pouvez ainsi :

* Évaluer ClickHouse Observability avec vos véritables données de télémétrie de production plutôt qu’avec un jeu de données d’exemple.
* Continuer à envoyer des données à Datadog tout en comparant les deux plateformes côte à côte.
* Migrer progressivement : basculez les agents groupe par groupe et adoptez l’instrumentation OpenTelemetry à votre rythme.

<Note>

  Si votre télémétrie transite par des collecteurs OpenTelemetry, ajoutez plutôt un exportateur : consultez [Connecter un collecteur OpenTelemetry](/fr/clickstack/managed-onboarding/setting-up-your-opentelemetry-collector-serverless). ## Prérequis {#prerequisites}

* Un service ClickHouse Observability. Si vous n’en avez pas encore, suivez le [Guide de démarrage](/fr/clickstack/observability/getting-started).
* L’agent Datadog 7 installé sur les hôtes, conteneurs ou clusters Kubernetes que vous souhaitez utiliser pour l’évaluation, et collectant déjà les logs et les metrics qui vous intéressent. Pour les traces, vos applications doivent déjà envoyer des traces à l’agent via les bibliothèques de traçage Datadog.
* Un accès à la configuration de l’agent, soit via `datadog.yaml`, soit via les variables d’environnement équivalentes, ainsi que la permission de redémarrer l’agent.
* Un accès HTTPS sortant sur le port `8126` depuis les hôtes de l’agent vers l’endpoint de télémétrie de votre service.

## Connecter vos agents Datadog {#connect-your-datadog-agents}

<Steps>
  <Step title="Copiez vos informations de connexion" id="copy-connection-details">
    Ouvrez votre service ClickHouse Observability. Tant qu’aucune donnée n’a été reçue, il affiche la page **Start sending telemetry**.

    <div className="ch-image-lg">
      <Frame>
        ![Page Start sending telemetry affichant le service actuel, encore sans données, et trois options : Use an existing OpenTelemetry setup, Instrument with AI et Follow setup guides](/images/clickstack/getting-started/observability-start-sending-telemetry.png)
      </Frame>
    </div>

    Sous **Use an existing OpenTelemetry setup**, sélectionnez **View connection details**. L’onglet **URL** affiche votre point de terminaison OTLP, `https://YOUR_OTEL_HOST:4318`, ainsi que votre API key. Sélectionnez **Reveal key** pour afficher la clé complète, puis copiez-la à l’aide du bouton de copie.

    <div className="ch-image-md">
      <Frame>
        ![Boîte de dialogue Set up OpenTelemetry avec les options URL, Collector config et Env vars, et des informations de connexion masquées](/images/clickstack/getting-started/observability-connection-details.png)
      </Frame>
    </div>

    L’endpoint compatible Datadog se trouve sur le même hôte que le point de terminaison OTLP, mais sur le port `8126` au lieu de `4318`, et l’API key de votre service fait également office d’API key Datadog. La suite de ce guide utilise les caractères de substitution suivants :

    | Caractère de substitution     | Valeur                                                                                    |
    | ----------------------------- | ----------------------------------------------------------------------------------------- |
    | `YOUR_API_KEY`                | L’API key de votre service                                                                |
    | `YOUR_OTEL_HOST`              | Le nom d’hôte du point de terminaison OTLP, sans `https://` ni le port                    |
    | `https://YOUR_OTEL_HOST:8126` | L’endpoint compatible Datadog pour les métriques et les traces                            |
    | `YOUR_OTEL_HOST:8126`         | Le même endpoint au format `host:port`, attendu par les paramètres de journaux de l’Agent |

    Vous pouvez retrouver ces valeurs à tout moment sous **Team Settings → Managed Telemetry**.

    <div className="ch-image-lg">
      <Frame>
        ![Page Managed Telemetry dans Team Settings affichant le point de terminaison OTLP HTTP et l’API key, masqués](/images/clickstack/getting-started/observability-managed-telemetry.png)
      </Frame>
    </div>
  </Step>

  <Step title="Configurez vos agents Datadog" id="configure-your-datadog-agents">
    Choisissez comment les agents doivent envoyer les données. Les deux options ne modifient que la configuration de l’Agent, dans `datadog.yaml` ou via des variables d’environnement, et aucune ne change ce que l’Agent collecte. Commencez par un seul agent, vérifiez que ses données arrivent bien, puis étendez progressivement la modification aux autres.

    <Tabs>
      <Tab title="En parallèle de Datadog" id="alongside-datadog">
        L&#39;Agent peut envoyer chaque charge utile vers plusieurs destinations. Conservez vos valeurs `api_key` et `site` existantes, puis ajoutez votre service comme endpoint supplémentaire pour les metrics, les traces et les logs. Datadog documente cette fonctionnalité sous le nom de [dual shipping](https://docs.datadoghq.com/agent/configuration/dual-shipping/).

        ```yaml
        # datadog.yaml : conservez api_key et site tels quels, puis ajoutez ces paramètres.

        # Métriques
        additional_endpoints:
          "https://YOUR_OTEL_HOST:8126":
            - "YOUR_API_KEY"

        # Utiliser l'ingestion de métriques v2.
        use_v3_api:
          series:
            enabled: false

        # Traces
        apm_config:
          additional_endpoints:
            "https://YOUR_OTEL_HOST:8126":
              - "YOUR_API_KEY"

        # Logs
        logs_config:
          force_use_http: true
          additional_endpoints:
            - api_key: "YOUR_API_KEY"
              Host: "YOUR_OTEL_HOST"
              Port: 8126
              is_reliable: true
        ```

        Datadog continue de tout recevoir comme auparavant. Chaque destination possède sa propre API key : votre clé Datadog ne parvient donc jamais à ClickHouse Observability, et votre clé ClickHouse Observability ne parvient jamais à Datadog. Les logs ne sont envoyés vers des endpoints supplémentaires que via HTTP, ce qu&#39;active `force_use_http`. Quant à `is_reliable: true`, il amène l&#39;Agent à mettre en tampon les logs destinés au nouvel endpoint et à effectuer de nouvelles tentatives plutôt qu&#39;à les abandonner si celui-ci est momentanément injoignable. Si `apm_config` ou `logs_config` existent déjà dans votre fichier, ajoutez les nouvelles clés aux sections existantes.
      </Tab>

      <Tab title="À la place de Datadog" id="instead-of-datadog">
        Pour migrer entièrement un agent, faites pointer ses destinations principales vers votre service et utilisez l&#39;API key de votre service :

        ```yaml
        api_key: "YOUR_API_KEY"

        # Destination des métriques
        dd_url: "https://YOUR_OTEL_HOST:8126"

        # Utiliser l'ingestion de métriques v2.
        use_v3_api:
          series:
            enabled: false

        # Destination des traces
        apm_config:
          enabled: true
          apm_dd_url: "https://YOUR_OTEL_HOST:8126"

        # Destination des logs
        logs_enabled: true
        logs_config:
          logs_dd_url: "YOUR_OTEL_HOST:8126"
          force_use_http: true
          logs_no_ssl: false

        remote_updates: false
        remote_configuration:
          enabled: false
        ```

        Ces paramètres redirigent les logs, les traces et les metrics de l&#39;Agent. Ils ne modifient pas les logs collectés par l&#39;Agent et n&#39;ajoutent aucune instrumentation : conservez donc en place vos intégrations de collecte de logs et votre configuration de traçage existantes. La configuration à distance est désactivée, faute de quoi l&#39;Agent continuerait de demander sa configuration à Datadog avec une clé que Datadog ne reconnaît plus.
      </Tab>
    </Tabs>

    <Accordion title="Configurer à l’aide de variables d’environnement">
      Les déploiements sur conteneurs et Kubernetes configurent généralement l’Agent au moyen de variables d’environnement `DD_`, qui surchargent `datadog.yaml`. Définissez-les dans votre commande Docker, vos valeurs Helm ou la spec de l’Operator.

      Pour envoyer les données en parallèle de Datadog :

      ```shell
      DD_ADDITIONAL_ENDPOINTS='{"https://YOUR_OTEL_HOST:8126": ["YOUR_API_KEY"]}'
      DD_APM_ADDITIONAL_ENDPOINTS='{"https://YOUR_OTEL_HOST:8126": ["YOUR_API_KEY"]}'
      DD_LOGS_CONFIG_FORCE_USE_HTTP=true
      DD_LOGS_CONFIG_ADDITIONAL_ENDPOINTS='[{"api_key": "YOUR_API_KEY", "Host": "YOUR_OTEL_HOST", "Port": 8126, "is_reliable": true}]'
      ```

      Pour envoyer les données ailleurs que vers Datadog :

      ```shell
      DD_API_KEY=YOUR_API_KEY
      DD_DD_URL=https://YOUR_OTEL_HOST:8126
      DD_APM_ENABLED=true
      DD_APM_DD_URL=https://YOUR_OTEL_HOST:8126
      DD_LOGS_ENABLED=true
      DD_LOGS_CONFIG_LOGS_DD_URL=YOUR_OTEL_HOST:8126
      DD_LOGS_CONFIG_FORCE_USE_HTTP=true
      DD_REMOTE_CONFIGURATION_ENABLED=false
      ```

      Les versions 7.81 et ultérieures de l&#39;agent envoient par défaut les métriques vers un point d&#39;ingestion de séries plus récent. Si les métriques d&#39;un agent configuré de cette manière n&#39;arrivent pas, ajoutez `use_v3_api.series.enabled: false` à son fichier `datadog.yaml`, comme dans les exemples de configuration par fichier ci-dessus.
    </Accordion>
  </Step>

  <Step title="Effectuez un restart de l’Agent et vérifiez son état" id="restart-and-check">
    Redémarrez l&#39;Agent pour appliquer la configuration. Sous Linux :

    ```shell
    sudo systemctl restart datadog-agent
    sudo datadog-agent status
    ```

    Sur macOS :

    ```shell
    sudo launchctl kickstart -k system/com.datadoghq.agent
    datadog-agent status
    ```

    Pour un Agent conteneurisé, mettez à jour son environnement et redéployez le conteneur ou le groupe de conteneurs, puis exécutez `agent status` à l’intérieur de celui-ci.

    Dans la sortie de la commande status, les sections **Forwarder**, **APM Agent** et **Logs Agent** répertorient chaque destination. Un agent en bon état de fonctionnement affiche votre endpoint sans aucune erreur. Des réponses `403` signifient que l’API key est incorrecte ou qu’elle a été copiée avant que vous ne sélectionniez **Reveal key**. Des erreurs de connexion ou des dépassements de délai signalent une faute de frappe dans le nom d’hôte, un port autre que `8126` ou un accès sortant bloqué.
  </Step>
</Steps>

## Vérifier la réception des données {#confirm-data-is-arriving}

Revenez à la page **Start sending telemetry** de votre service et sélectionnez **Check for data**. Une fois votre télémétrie reçue, le statut du service passe à **Data received** et le bouton **Start exploring** devient disponible.

<div className="ch-image-lg">
  <Frame>
    ![Page Start sending telemetry affichant le statut du service Data received, une confirmation indiquant que vous êtes prêt à explorer, et le bouton Start exploring activé](/images/clickstack/getting-started/observability-data-received.png)
  </Frame>
</div>

Sélectionnez **Start exploring** pour ouvrir **Recherche**. Sélectionnez la source **Logs**, réglez l&#39;intervalle de temps sur **Last 15 minutes** et filtrez `ServiceName` sur l&#39;étiquette `service` appliquée par votre Agent. Développez un enregistrement : les étiquettes `host`, `env`, de conteneur et Kubernetes de l&#39;Agent apparaissent sous forme d&#39;attributs de ressource, et le champ `status` de Datadog est associé à `SeverityText`, si bien que les filtres du type `level:error` fonctionnent comme pour les logs OpenTelemetry.

## Si rien ne s’affiche {#if-nothing-shows-up}

* Consultez d’abord le statut de l’Agent. Les problèmes d’authentification, d’endpoint et de réseau y sont signalés pour chaque destination. Dans la configuration en parallèle, les erreurs liées à votre endpoint n’empêchent jamais les données de parvenir à Datadog.
* Vérifiez l’API key. Il doit s’agir de la valeur complète, que vous pouvez copier après avoir sélectionné **Reveal key**. Elle sert de `api_key` Datadog pour votre endpoint, et non d’en-tête.
* Vérifiez l’endpoint. Les metrics et les traces utilisent `https://YOUR_OTEL_HOST:8126`, avec le schéma ; les paramètres des logs utilisent `YOUR_OTEL_HOST:8126`, sans schéma. Le nom d’hôte est celui de votre point de terminaison OTLP, et le port est `8126`, et non `4318`.
* Si les logs n’arrivent pas, vérifiez que `logs_enabled: true` est bien défini et que la collecte des logs est configurée pour les intégrations ou les fichiers attendus. L’endpoint n’accepte les logs que via HTTP ; `force_use_http` doit donc être à `true`.
* Si les traces n’arrivent pas, vérifiez que `apm_config.enabled: true` est bien défini et que vos applications envoient leurs traces à l’Agent. L’endpoint reçoit ce que l’Agent lui transmet ; il n’instrumente pas les applications.
* Si les metrics n’arrivent pas, vérifiez que l’agent utilise l’ingestion des séries v2 avec `use_v3_api.series.enabled: false`.
* Élargissez l’intervalle de temps dans **Recherche** et supprimez tous les filtres. La source par défaut est peut-être définie sur **Traces** plutôt que sur **Logs**.
* Pour écarter un problème lié au service lui-même, accédez à **Paramètres de l’équipe → Télémétrie gérée** et utilisez **Send a Test Log**. Si ce log apparaît dans **Recherche**, le service reçoit bien des données et le problème se situe entre l’Agent et l’endpoint.

## Ce que l’endpoint accepte {#what-the-endpoint-accepts}

L’endpoint prend en charge les protocoles utilisés par l’agent Datadog et convertit chaque charge utile au format OpenTelemetry avant qu’elle n’atteigne votre service :

* **Logs.** Les timestamps, corps et statuts Datadog deviennent des timestamps, corps et niveaux de sévérité OpenTelemetry. Les logs JSON structurés sont décodés, ce qui permet d’interroger leurs champs. Les noms d’hôte, noms de service, environnements ainsi que les étiquettes connues de conteneur, de cloud et de Kubernetes deviennent des attributs de ressource.
* **Traces.** Les spans issus des bibliothèques de traçage Datadog conservent leurs données de service, de ressource et d’étiquettes, et les ID de trace 128 bits sont reconstruits afin que les logs et spans provenant de Datadog puissent être corrélés avec les services instrumentés avec OpenTelemetry.
* **Metrics.** Les séries envoyées à l’intake v2, y compris les metrics d’hôte de l’agent, les metrics personnalisées ainsi que les jauges et compteurs DogStatsD. Les distributions sont reçues sous forme de sketches.
* **Compression.** À partir de la version 7.59, l’agent compresse les charges utiles HTTP avec Zstandard, format que l’endpoint accepte en plus de gzip.

L’endpoint repose sur le récepteur Datadog du collecteur OpenTelemetry, un composant en version alpha, et reste expérimental dans ClickHouse Observability. Les fonctionnalités propres au backend de Datadog, telles que les moniteurs, les pipelines et les processeurs, n’entrent pas dans son périmètre. Pour le guide de migration complet, y compris la mise en place d’un récepteur que vous exécutez vous-même dans l’expérience autogérée, consultez [Migration depuis Datadog](/fr/clickstack/observability/migration/datadog).

## Étapes suivantes {#next-steps}

* **Étendre l’évaluation.** Ajoutez la configuration en parallèle à davantage d’agents afin de comparer les deux plateformes sur les charges de travail qui comptent pour vous, puis basculez les agents vers la configuration de remplacement lorsque vous êtes prêt. Aucune modification de vos applications n’est nécessaire, ni à l’une ni à l’autre de ces étapes.
* [Instrumenter votre application avec OpenTelemetry](/fr/clickstack/managed-onboarding/instrument-application-serverless) : envoyez les services nouveaux ou migrés directement vers votre point de terminaison OTLP à l’aide des SDK OpenTelemetry, tandis que les agents Datadog continuent de couvrir le reste.
* [Connecter un collecteur OpenTelemetry](/fr/clickstack/managed-onboarding/setting-up-your-opentelemetry-collector-serverless) : si vous exploitez également des collecteurs OpenTelemetry, faites-les pointer vers le même service.
* [Recherche](/fr/clickstack/observability/features/search) : interrogez les logs et les traces provenant de Datadog avec une syntaxe de type Lucene ou en SQL.
* [Tableaux de bord](/fr/clickstack/observability/features/dashboards/overview) et [Alertes](/fr/clickstack/observability/features/alerts) : recréez, sur les mêmes données, les vues et les moniteurs sur lesquels vous vous appuyez dans Datadog.
