<Info>
  **En bref**

  Exécutez une petite application de démonstration, instrumentez-la à l’aide du prompt IA proposé sur la page Premiers pas de votre service ou en effectuant deux modifications manuelles, puis observez les logs, traces et métriques arriver dans ClickHouse Observability.

  Durée estimée : environ 10 minutes
</Info>

Vous avez créé votre service ClickHouse Observability. Ce guide vous accompagne pas à pas, d’un service vide jusqu’à la réception de la télémétrie d’une application en cours d’exécution.

ClickHouse Observability fournit un endpoint OpenTelemetry géré, auquel votre application envoie directement sa télémétrie. Aucun collecteur à exécuter, aucun schéma à créer, aucune base de données à dimensionner : l’ingestion, les schémas, le stockage, l’optimisation et la mise à l’échelle sont entièrement pris en charge.

## L&#39;application de démonstration {#the-demo-application}

Pour vous offrir un cas réaliste à instrumenter, ce guide utilise [HackerNews Analyzer](https://github.com/ClickHouse/hn-news-analyzer), une application de démonstration que nous fournissons précisément à cet effet. Il s&#39;agit d&#39;une petite application Node.js et TypeScript qui interroge le jeu de données HackerNews hébergé sur la démo publique de ClickHouse. Chaque graphique, chaque table et chaque champ de recherche s&#39;appuie sur une véritable requête envoyée au backend. Les requêtes qui ne trouvent pas de résultat dans le cache de l&#39;application interrogent également ClickHouse, ce qui ajoute un span HTTPS sortant à chaque trace.

La démo est disponible en deux variantes :

* **Non instrumentée**, sur la branche `main`. Vous ajoutez vous-même l&#39;instrumentation au fil de ce guide, soit à l&#39;aide d&#39;un agent IA, soit manuellement, sans modifier la logique métier de l&#39;application. Les mêmes étapes s&#39;appliquent à vos propres services.
* **Pré-instrumentée**, sur la branche `instrumented`. Choisissez cette branche si vous souhaitez simplement faire remonter rapidement des données de télémétrie et explorer l&#39;UI.

## Prérequis {#prerequisites}

* Un service ClickHouse Observability. Si vous n&#39;en avez pas encore, suivez le [guide de démarrage](/fr/clickstack/observability/getting-started).
* Node.js 18 ou version ultérieure, ainsi que npm.
* Un accès réseau à l&#39;endpoint de télémétrie de votre service, depuis la machine qui exécute la démonstration et depuis votre navigateur.

### Faire pointer la démonstration vers votre service {#configure-environment}

        Ouvrez `.env` et définissez les valeurs suivantes, en remplaçant l’endpoint et l’API key par les valeurs affichées dans la boîte de dialogue :

        ```bash
        OTEL_SERVICE_NAME=hn-analyzer-api
        OTEL_EXPORTER_OTLP_ENDPOINT=https://YOUR_OTEL_ENDPOINT:4318
        OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
        OTEL_EXPORTER_OTLP_HEADERS=authorization=<your-api-key>
        OTEL_TRACES_EXPORTER=otlp
        OTEL_METRICS_EXPORTER=otlp
        OTEL_LOGS_EXPORTER=otlp
        ```

        Il s&#39;agit de variables standard de l&#39;exportateur OpenTelemetry. Rien n&#39;est codé en dur dans le code source de l&#39;application.

        Conservez le préfixe `https://` dans `OTEL_EXPORTER_OTLP_ENDPOINT` et n&#39;ajoutez pas `/v1/logs`, `/v1/traces` ou `/v1/metrics` à la fin. Les SDK ajoutent eux-mêmes les chemins propres à chaque signal. Définissez `OTEL_EXPORTER_OTLP_HEADERS` sur `authorization=<your-api-key>`, sans préfixe `Bearer`.

        L&#39;instrumentation se déroule ensuite en trois étapes : installer le SDK, modifier la commande de lancement et activer le SDK pour navigateur. Aucune de ces étapes ne modifie la logique métier de l&#39;application.

### Installer le SDK Node {#install-node-sdk}

        ```bash
        npm install @hyperdx/node-opentelemetry
        ```

### Activer le wrapper dans run.sh {#enable-run-sh-wrapper}

        À la fin de `run.sh` figurent deux lignes `exec`. Commentez la ligne `node` simple et décommentez la ligne instrumentée :

        ```diff
         # BEFORE: plain node, no instrumentation:
        -exec node scripts/entrypoint.js
        +# exec node scripts/entrypoint.js

         # AFTER: same source, wrapped by opentelemetry-instrument:
        -# exec npx opentelemetry-instrument scripts/entrypoint.js
        +exec npx opentelemetry-instrument scripts/entrypoint.js
        ```

        Continuez à lancer l&#39;application via `scripts/entrypoint.js`. Ce shim appelle `require('console')` afin que la capture de la console encapsule `console.log`. Si vous pointez `opentelemetry-instrument` directement sur `dist/server/index.js`, les traces sont bien transmises, mais les logs sont ignorés sans le moindre avertissement.

### Activer le SDK pour navigateur {#enable-browser-sdk}

        ```bash
        npm install @hyperdx/browser
        ```

        Dans `src/web/telemetry.ts`, décommentez l&#39;import, le bloc `HyperDX.init` ainsi que l&#39;appel à `HyperDX.addAction` dans `recordAction` :

        ```diff
        -// import HyperDX from '@hyperdx/browser';
        +import HyperDX from '@hyperdx/browser';

         export function initTelemetry(): void {
        -  // HyperDX.init({
        -  //   url: __OTLP_ENDPOINT__,
        -  //   apiKey: __OTLP_AUTH_TOKEN__,
        -  //   service: 'hn-analyzer-web',
        -  //   tracePropagationTargets: [/localhost:5001/i, /\/api\//i],
        -  //   consoleCapture: true,
        -  //   advancedNetworkCapture: true,
        -  // });
        +  HyperDX.init({
        +    url: __OTLP_ENDPOINT__,
        +    apiKey: __OTLP_AUTH_TOKEN__,
        +    service: 'hn-analyzer-web',
        +    tracePropagationTargets: [/localhost:5001/i, /\/api\//i],
        +    consoleCapture: true,
        +    advancedNetworkCapture: true,
        +  });
         }
        ```

        `__OTLP_ENDPOINT__` et `__OTLP_AUTH_TOKEN__` sont des constantes de compilation injectées par `vite.config.ts` à partir des mêmes valeurs `OTEL_EXPORTER_OTLP_*` que celles utilisées par le backend.

        <Warning>
          Le SDK pour navigateur intègre l&#39;endpoint et l&#39;API key dans le bundle JavaScript du navigateur, où quiconque inspecte l&#39;onglet Réseau peut les lire. Utilisez un service destiné aux tests et excluez `.env` du contrôle de version.
        </Warning>

        Relancez la démo avec `./run.sh`.
      </Tab>

## Si rien ne s&#39;affiche {#if-nothing-shows-up}

* Vérifiez les valeurs dans `.env`. L&#39;endpoint doit commencer par `https://`, se terminer par le port `4318` et ne comporter aucun suffixe `/v1/...`. L&#39;API key doit correspondre à la valeur complète, que vous pouvez copier après avoir sélectionné **Reveal key**.
* Si vous avez suivi la méthode manuelle, vérifiez que `OTEL_EXPORTER_OTLP_HEADERS` vaut `authorization=<your-api-key>` sans préfixe `Bearer`, et que la bannière de démarrage affiche bien les trois lignes `Health check passed`.
* Assurez-vous d&#39;avoir redémarré l&#39;application de démonstration après l&#39;avoir instrumentée, puis rechargé l&#39;onglet du navigateur. La relecture de session ne démarre qu&#39;une fois le bundle instrumenté servi.
* Élargissez l&#39;intervalle de temps dans **Recherche** et supprimez tous les filtres. La source par défaut est peut-être définie sur **Traces** plutôt que sur **Logs**.
* Pour écarter un problème lié au service lui-même, accédez à **Paramètres de l’équipe → Managed Telemetry** et utilisez **Send a Test Log**. Si ce log apparaît dans **Recherche**, le service reçoit bien des données et le problème vient de la configuration de l&#39;application de démonstration.

## Étapes suivantes {#next-steps}

Votre service contient désormais de la télémétrie issue d’une application réelle. Pour instrumenter vos propres services, réutilisez le prompt **Instrument with AI** de votre service, ou utilisez les [SDK par langage pris en charge](/fr/clickstack/observability/ingesting-data/sdks/index) avec le même endpoint et la même API key.

Pour collecter des données depuis l’infrastructure plutôt que depuis le code applicatif :

* [Supervision de Kubernetes](/fr/clickstack/observability/example-datasets/kubernetes) : collectez les logs et les métriques du cluster, puis explorez le tableau de bord Kubernetes.
* [Logs et métriques locaux](/fr/clickstack/observability/example-datasets/local-data) : collectez des fichiers locaux et des métriques système sous macOS ou Linux.

Pour aller plus loin avec l’UI :

* [Recherche](/fr/clickstack/observability/features/search) : interrogez les logs et les traces avec une syntaxe de type Lucene ou en SQL.
* [Relecture de session](/fr/clickstack/observability/features/session-replay) : présentation de la fonctionnalité, options du SDK et contrôles de confidentialité.
* [Jeux de données d’exemple](/fr/clickstack/observability/example-datasets) : jeux de données plus riches et investigations guidées.
