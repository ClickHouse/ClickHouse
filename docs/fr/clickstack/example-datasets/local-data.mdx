Ce guide de prise en main vous permet de collecter les logs et les métriques locales de votre système, puis de les envoyer à ClickStack pour les visualiser et les analyser.

**Cet exemple fonctionne uniquement sur les systèmes OSX et Linux**

### Créer une configuration OpenTelemetry personnalisée {#create-otel-configuration-oss}

Créez un fichier `custom-local-config.yaml` avec le contenu suivant :

```yaml
receivers:
  filelog:
    include:
      - /host/var/log/**/*.log        # Linux logs from host
      - /host/var/log/syslog
      - /host/var/log/messages
      - /host/private/var/log/*.log   # macOS logs from host
    start_at: beginning
    resource:
      service.name: "system-logs"

  hostmetrics:
    collection_interval: 1s
    scrapers:
      cpu:
        metrics:
          system.cpu.time:
            enabled: true
          system.cpu.utilization:
            enabled: true
      memory:
        metrics:
          system.memory.usage:
            enabled: true
          system.memory.utilization:
            enabled: true
      filesystem:
        metrics:
          system.filesystem.usage:
            enabled: true
          system.filesystem.utilization:
            enabled: true
      paging:
        metrics:
          system.paging.usage:
            enabled: true
          system.paging.utilization:
            enabled: true
          system.paging.faults:
            enabled: true
      disk:
      load:
      network:
      processes:

service:
  pipelines:
    logs/local:
      receivers: [filelog]
      processors:
        - memory_limiter
        - batch
      exporters:
        - clickhouse
    metrics/hostmetrics:
      receivers: [hostmetrics]
      processors:
        - memory_limiter
        - batch
      exporters:
        - clickhouse
```

Cette configuration collecte les logs et les métriques système pour les systèmes OSX et Linux, puis envoie les résultats à ClickStack. Elle étend le ClickStack collector en ajoutant de nouveaux receivers et pipelines : vous réutilisez l’exporter `clickhouse` existant ainsi que les processeurs (`memory_limiter`, `batch`) déjà configurés dans le ClickStack collector de base.

<Info>
  **Timestamps d’ingestion**

  Cette configuration ajuste les timestamps lors de l’ingestion en attribuant à chaque événement une valeur temporelle mise à jour. Idéalement, vous devriez [prétraiter ou analyser les timestamps](/fr/clickstack/ingesting-data/collector#processing-filtering-transforming-enriching) à l’aide de processeurs ou d’operators OTel dans les fichiers de logs afin de préserver le temps réel de l’événement.

  Avec cet exemple de configuration, si le receiver ou le processeur de fichier est configuré pour démarrer au début du fichier, toutes les log entries existantes se verront attribuer le même timestamp ajusté — l’heure du traitement plutôt que le temps d’origine de l’événement. Tous les nouveaux événements ajoutés au fichier recevront des timestamps proches de leur heure réelle de génération.

  Pour éviter ce comportement, vous pouvez définir la position de départ sur `end` dans la configuration du receiver. Cela garantit que seules les nouvelles entrées sont ingérées et horodatées au plus près de leur heure réelle d’arrivée.
</Info>

Pour plus de détails sur la structure de configuration d’OpenTelemetry (OTel), nous recommandons [le guide officiel](https://opentelemetry.io/docs/collector/configuration/).

### Démarrer ClickStack avec une configuration personnalisée {#start-clickstack}

Exécutez la commande Docker suivante pour démarrer le conteneur all-in-one avec votre configuration personnalisée :

```shell
docker run -d --name clickstack \
  -p 8080:8080 -p 4317:4317 -p 4318:4318 \
  --user 0:0 \
  -e CUSTOM_OTELCOL_CONFIG_FILE=/etc/otelcol-contrib/custom.config.yaml \
  -v "$(pwd)/custom-local-config.yaml:/etc/otelcol-contrib/custom.config.yaml:ro" \
  -v /var/log:/host/var/log:ro \
  -v /private/var/log:/host/private/var/log:ro \
  clickhouse/clickstack-all-in-one:latest
```

<Info>
  **Utilisateur root**

  Nous exécutons le collecteur en tant qu&#39;utilisateur root afin d&#39;accéder à l&#39;ensemble des logs système, ce qui est nécessaire pour capturer les logs situés dans des chemins protégés sur les systèmes Linux. Cette approche est toutefois déconseillée en production. Dans les environnements de production, le collecteur OpenTelemetry doit être déployé en tant qu&#39;agent local disposant uniquement des autorisations minimales requises pour accéder aux sources de logs visées.

  Notez que nous montons le répertoire `/var/log` de l&#39;hôte sur `/host/var/log` dans le conteneur afin d&#39;éviter tout conflit avec les fichiers de log propres au conteneur.
</Info>

### Explorer les logs système {#navigate-to-the-hyperdx-ui-oss}

Accédez à [http://localhost:8080](http://localhost:8080) pour accéder à la ClickStack UI si vous déployez en local.

Les sources de données doivent déjà être créées pour vous. La page Search de l&#39;UI doit être peuplée avec les logs système locaux. Développez les filtres pour sélectionner `system.log` :

### Explorer les métriques système {#explore-system-metrics-oss}

Nous pouvons explorer nos métriques à l&#39;aide de graphiques.

Accédez au Chart Explorer via le menu de gauche. Sélectionnez la source `Metrics` et `Maximum` comme type d&#39;agrégation.

Dans le menu `Select a Metric`, saisissez simplement `memory` avant de sélectionner `system.memory.utilization (Gauge)`.

Appuyez sur le bouton `Run` pour visualiser l’utilisation de la mémoire au fil du temps.

<div className="ch-image-lg">
  <Frame>
    ![Mémoire au fil du temps](/images/use-cases/observability/hyperdx-21.webp)
  </Frame>
</div>

Notez que la valeur renvoyée est un `%` en virgule flottante. Pour l&#39;afficher plus clairement, sélectionnez `Set number format`.

  <Frame>
    ![Format numérique](/images/use-cases/observability/hyperdx-22.webp)
  </Frame>
</div>

Dans le menu suivant, vous pouvez sélectionner `Percentage` dans la liste déroulante `Output format`, puis cliquer sur `Apply`.
