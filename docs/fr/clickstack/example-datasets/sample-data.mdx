Ce guide présente ClickStack Open Source à l’aide d’un jeu de données d’exemple.

L’exemple suivant suppose que vous avez démarré ClickStack Open Source avec l’[image tout-en-un](/fr/clickstack/getting-started/oss) et copié l’[API key d’ingestion](/fr/clickstack/getting-started/oss#copy-ingestion-api-key).

<Steps>
  <Step title="Accédez à l’interface utilisateur de ClickStack" id="navigate-to-the-hyperdx-ui">
    Rendez-vous sur [http://localhost:8080](http://localhost:8080) pour accéder à l’interface utilisateur de ClickStack.

    <div className="ch-image-lg">
      <Frame>
        ![Interface utilisateur de ClickStack](/images/use-cases/observability/hyperdx.webp)
      </Frame>
    </div>
  </Step>

  <Step title="Copier l’API key d’ingestion" id="copy-ingestion-api-key">
    Accédez à [`Team Settings`](http://localhost:8080/team) et copiez la `Ingestion API Key` dans la section `API Keys`. Cette API key sécurise l’ingestion de données via le collecteur OpenTelemetry.

    <div className="ch-image-lg">
      <Frame>
        ![Copier l’API key](/images/use-cases/observability/copy_api_key.webp)
      </Frame>
    </div>
  </Step>

  <Step title="Télécharger les données d’exemple" id="download-sample-data">
    Pour remplir l’UI avec des données d’exemple, téléchargez le fichier suivant :

    [Données d’exemple](https://storage.googleapis.com/hyperdx/sample.tar.gz)

    ```shell
    # curl
    curl -O https://storage.googleapis.com/hyperdx/sample.tar.gz
    # or
    # wget https://storage.googleapis.com/hyperdx/sample.tar.gz
    ```

    Ce fichier contient des exemples de logs, de métriques et de traces issus de notre [OpenTelemetry demo](https://github.com/ClickHouse/opentelemetry-demo) publique, une boutique en ligne simple composée de microservices. Copiez ce fichier dans le répertoire de votre choix.
  </Step>

  <Step title="Charger des données d’exemple" id="load-sample-data">
    Pour charger ces données, il suffit de les envoyer à l&#39;endpoint HTTP du collecteur OpenTelemetry (OTel) déployé.

    Commencez par exporter l&#39;API key copiée précédemment.

    ```shell
    # export API key
    export CLICKSTACK_API_KEY=<YOUR_INGESTION_API_KEY>
    ```

    Exécutez la commande suivante pour envoyer les données à l&#39;OTel collector :

    ```shell
    for filename in $(tar -tf sample.tar.gz); do
      endpoint="http://localhost:4318/v1/${filename%.json}"
      echo "loading ${filename%.json}"
      tar -xOf sample.tar.gz "$filename" | while read -r line; do
        printf '%s\n' "$line" | curl -s -o /dev/null -X POST "$endpoint" \
        -H "Content-Type: application/json" \
        -H "authorization: ${CLICKSTACK_API_KEY}" \
        --data-binary @-
      done
    done
    ```

    Cela simule des sources OTLP de journaux, de traces et de métriques qui envoient des données à l&#39;OTel collector. En production, ces sources peuvent être des bibliothèques clientes par langage, voire d&#39;autres OTel collectors.

    De retour dans la vue `Search`, vous devriez constater que les données commencent à se charger (si elles ne s&#39;affichent pas, réglez la période sur `Last 1 hour`) :

    <div className="ch-image-lg">
      <Frame>
        ![Recherche dans l'interface utilisateur de ClickStack](/images/use-cases/observability/hyperdx-10.webp)
      </Frame>
    </div>

    Le chargement des données prend quelques minutes. Attendez qu&#39;il soit terminé avant de passer aux étapes suivantes.
  </Step>

  <Step title="Explorer les sessions" id="explore-sessions">
    Supposons que nous ayons reçu des signalements indiquant que nos utilisateurs rencontrent des problèmes pour payer leurs achats. Nous pouvons observer leur parcours grâce aux fonctionnalités de relecture de session de l&#39;interface utilisateur de ClickStack.

    Sélectionnez [`Client Sessions`](http://localhost:8080/sessions?from=1747312320000\&to=1747312920000\&sessionSource=l1324572572) dans le menu de gauche.

    <div className="ch-image-lg">
      <Frame>
        ![Sessions](/images/use-cases/observability/hyperdx-11.webp)
      </Frame>
    </div>

    Cette vue affiche les sessions front-end de notre boutique en ligne. Les sessions restent anonymes jusqu&#39;à ce que les utilisateurs passent à la caisse et tentent de finaliser un achat.

    Notez que certaines sessions associées à une adresse e-mail présentent une erreur, ce qui pourrait confirmer les signalements de transactions en échec.

    Sélectionnez une trace comportant un échec et associée à une adresse e-mail. La vue qui s&#39;affiche permet de rejouer la session de l&#39;utilisateur et d&#39;examiner son problème. Cliquez sur le bouton de lecture pour visionner la session.

    <div className="ch-image-lg">
      <Frame>
        ![Relecture de session](/images/use-cases/observability/hyperdx-12.webp)
      </Frame>
    </div>

    La relecture montre l&#39;utilisateur en train de naviguer sur le site et d&#39;ajouter des articles à son panier. N&#39;hésitez pas à avancer dans la session jusqu&#39;au moment où il tente d&#39;effectuer un paiement.

    <Tip>
      Les erreurs sont signalées en rouge sur la chronologie.
    </Tip>

    L&#39;utilisateur n&#39;a pas pu passer sa commande, sans qu&#39;aucune erreur ne soit visible. Faites défiler jusqu&#39;au bas du panneau de gauche, qui contient les événements réseau et console du navigateur de l&#39;utilisateur. Vous remarquerez qu&#39;une erreur 500 a été levée lors d&#39;un appel à `/api/checkout`.

    <div className="ch-image-lg">
      <Frame>
        ![Erreur dans la session](/images/use-cases/observability/hyperdx-13.webp)
      </Frame>
    </div>

    Sélectionnez cette erreur `500`. Ni `Overview` ni `Column Values` n&#39;indiquent l&#39;origine du problème, si ce n&#39;est que l&#39;erreur est inattendue et provoque une `Internal Error`.
  </Step>

  <Step title="Explorer les traces" id="explore-traces">
    Accédez à l’onglet `Trace` pour afficher la trace distribuée complète.

    <div className="ch-image-lg">
      <Frame>
        ![Trace de session](/images/use-cases/observability/hyperdx-14.webp)
      </Frame>
    </div>

    Faites défiler la trace vers le bas pour identifier l’origine de l’erreur : le span du service `checkout`. Sélectionnez le span du service `Payment`.

    <div className="ch-image-lg">
      <Frame>
        ![Span](/images/use-cases/observability/hyperdx-15.webp)
      </Frame>
    </div>

    Sélectionnez l’onglet `Column Values` et faites défiler vers le bas. On constate que le problème est lié à un cache plein.

    <div className="ch-image-lg">
      <Frame>
        ![Valeurs de colonne](/images/use-cases/observability/hyperdx-16.webp)
      </Frame>
    </div>

    En remontant jusqu’à la trace, on constate que des logs sont corrélés au span, grâce à la configuration effectuée précédemment. Ils apportent un contexte supplémentaire.

    <div className="ch-image-lg">
      <Frame>
        ![Log corrélé](/images/use-cases/observability/hyperdx-17.webp)
      </Frame>
    </div>

    Nous avons établi qu’un cache se remplit dans le service de paiement, ce qui empêche les paiements d’aboutir.
  </Step>

  <Step title="Explorer les logs" id="explore-logs">
    Pour obtenir plus de détails, nous pouvons revenir à la [vue `Search`](http://localhost:8080/search) :

    Sélectionnez `Logs` parmi les sources et filtrez sur le service `payment`.

    <div className="ch-image-lg">
      <Frame>
        ![Logs](/images/use-cases/observability/hyperdx-18.webp)
      </Frame>
    </div>

    Nous constatons que, bien que le problème soit récent, le nombre de paiements affectés est élevé. En outre, un cache lié aux paiements Visa semble être à l’origine des problèmes.
  </Step>

  <Step title="Metrics du graphique" id="chart-metrics">
    Bien qu&#39;une erreur ait manifestement été introduite dans le code, nous pouvons nous appuyer sur les métriques pour vérifier la taille du cache. Accédez à la vue `Chart Explorer`.

    Sélectionnez `Metrics` comme source de données. Renseignez l&#39;éditeur de graphiques pour tracer le `Maximum` de `visa_validation_cache.size (Gauge)`, puis cliquez sur le bouton d&#39;exécution. On constate nettement que le cache augmentait jusqu&#39;à atteindre une taille maximale, à partir de laquelle des erreurs ont été générées.

    <div className="ch-image-lg">
      <Frame>
        ![Métriques](/images/use-cases/observability/hyperdx-19.webp)
      </Frame>
    </div>
  </Step>
</Steps>
