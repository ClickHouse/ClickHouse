<div id="backward-incompatible-change">
  #### Changement incompatible avec les versions précédentes
</div>

* Modification du paramètre `schema_inference_make_columns_nullable` activé par défaut afin de respecter les informations de `Nullable` des `columns` provenant des métadonnées Parquet/ORC/Arrow, au lieu de tout rendre Nullable. Aucun changement pour les text formats. [#71499](https://github.com/ClickHouse/ClickHouse/pull/71499) ([Michael Kolupaev](https://github.com/al13n321)).
* Cette PR fait en sorte que le query result cache ignore le paramètre `log_comment`, afin que le fait de modifier uniquement le `log_comment` d’une query n’entraîne plus de cache miss. Il existe une faible probabilité que certains utilisateurs aient volontairement segmenté leur cache en faisant varier `log_comment`. Cette modification change ce comportement et n’est donc pas rétrocompatible. Veuillez utiliser le paramètre `query_cache_tag` à cette fin. [#79878](https://github.com/ClickHouse/ClickHouse/pull/79878) ([filimonov](https://github.com/filimonov)).
* Dans les versions précédentes, les queries utilisant des table functions portant le même nom que les fonctions d’implémentation des operators étaient formatées de manière incohérente. Closes [#81601](https://github.com/ClickHouse/ClickHouse/issues/81601). Closes [#81977](https://github.com/ClickHouse/ClickHouse/issues/81977). Closes [#82834](https://github.com/ClickHouse/ClickHouse/issues/82834). Closes [#82835](https://github.com/ClickHouse/ClickHouse/issues/82835). Les queries EXPLAIN SYNTAX ne formateront pas les operators ; ce nouveau comportement reflète mieux l’objectif d’explication de la syntaxe. `clickhouse-format`, `formatQuery` et les outils similaires ne formateront pas les fonctions comme des operators si la query les contenait sous forme fonctionnelle. [#82825](https://github.com/ClickHouse/ClickHouse/pull/82825) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Interdiction d’utiliser le Dynamic type dans les join keys. Cela pouvait conduire à des résultats inattendus lorsqu’un Dynamic type est comparé à un type non-Dynamic. Il est préférable de convertir la Dynamic column dans le type requis. [#86358](https://github.com/ClickHouse/ClickHouse/pull/86358) ([Pavel Kruglov](https://github.com/Avogar)).
* L’option du server Storage&#95;metadata&#95;write&#95;full&#95;object&#95;key est désormais activée par défaut et ne peut plus être désactivée. Il s’agit d’une modification rétrocompatible. J’ai utilisé le label pour attirer l’attention. Cette modification n’est compatible vers l’avant qu’avec les releases 25.x. Cela signifie que vous ne pourrez effectuer un downgrade que vers une release 25.x si vous devez faire un rollback de la nouvelle release. [#87335](https://github.com/ClickHouse/ClickHouse/pull/87335) ([Sema Checherinda](https://github.com/CheSema)).
* Réduction de replicated&#95;deduplication&#95;window&#95;seconds d’une semaine à une heure afin de stocker moins de znode dans ZooKeeper lorsque le taux d’Insertion est faible. [#87414](https://github.com/ClickHouse/ClickHouse/pull/87414) ([Sema Checherinda](https://github.com/CheSema)).
* Le paramètre `query_plan_use_new_logical_join_step` a été renommé en `query_plan_use_logical_join_step`. [#87679](https://github.com/ClickHouse/ClickHouse/pull/87679) ([Vladimir Cherkasov](https://github.com/vdimir)).
* La nouvelle syntaxe permet au parameter tokenizer d’être plus expressif. [#87997](https://github.com/ClickHouse/ClickHouse/pull/87997) ([Elmi Ahmadov](https://github.com/ahmadov)).
* Les fonctions `searchAny` et `searchAll` ont été renommées en `hasAnyTokens` et `hasAllTokens` pour une meilleure cohérence avec la fonction existante `hasToken`. [#88109](https://github.com/ClickHouse/ClickHouse/pull/88109) ([Robert Schulze](https://github.com/rschu1ze)).
* Suppression de `cache_hits_threshold` du filesystem cache. Cette feature a été ajoutée par un contributor externe avant que nous disposions de la cache policy SLRU, et maintenant que c’est le cas, il n’est plus pertinent de prendre en charge les deux. [#88344](https://github.com/ClickHouse/ClickHouse/pull/88344) ([Kseniia Sumarokova](https://github.com/kssenii)).
* Deux légers changements dans le fonctionnement des paramètres `min_free_disk_ratio_to_perform_insert` et `min_free_disk_bytes_to_perform_insert` : - utiliser les octets non réservés plutôt que les octets disponibles pour déterminer si une insertion doit être rejetée. Ce n’est probablement pas crucial si les réservations pour les fusions en arrière-plan et les mutations sont faibles par rapport aux seuils configurés, mais cela semble plus correct. - Ne plus appliquer ces paramètres aux tables système. L’idée est que nous voulons quand même que des tables comme `query_log` continuent d’être mises à jour. Cela aide beaucoup pour le débogage. Les données écrites dans les tables système sont généralement faibles par rapport aux données réelles ; elles devraient donc pouvoir continuer bien plus longtemps avec un seuil `min_free_disk_ratio_to_perform_insert` raisonnable. [#88468](https://github.com/ClickHouse/ClickHouse/pull/88468) ([c-end](https://github.com/c-end)).
* Activer le mode asynchrone pour la réplication interne de Keeper. Keeper conservera le même comportement qu’auparavant, avec d’éventuelles améliorations des performances. Si vous effectuez une mise à jour depuis une version antérieure à 23.9, vous devez soit d’abord passer à la version 23.9+, puis à la version 25.10+. Vous pouvez également définir `keeper_server.coordination_settings.async_replication` sur 0 avant la mise à jour, puis l’activer une fois la mise à jour terminée. [#88515](https://github.com/ClickHouse/ClickHouse/pull/88515) ([Antonio Andelic](https://github.com/antonio2368)).

Comme `GROUP BY ALL` et `ORDER BY ALL`, `LIMIT BY ALL` se développe automatiquement pour utiliser toutes les expressions non agrégées de la clause SELECT comme clés LIMIT BY. Par exemple, `SELECT id, name, count(*) FROM table GROUP BY id LIMIT 1 BY ALL` est équivalent à `SELECT id, name, count(*) FROM table GROUP BY id LIMIT 1 BY id, name`. Cette fonctionnalité simplifie les requêtes lorsque vous souhaitez limiter sur toutes les colonnes non agrégées sélectionnées sans avoir à les lister explicitement. Ferme [#59152](https://github.com/ClickHouse/ClickHouse/issues/59152). [#84079](https://github.com/ClickHouse/ClickHouse/pull/84079) ([Surya Kant Ranjan](https://github.com/iit2009046)).

Son comportement est similaire à celui de la fonction PromQL `histogram_quantile()` sur les histogrammes classiques. <div id="performance-improvement">
  #### Performance Improvement
</div>

* Amélioration des performances des requêtes grâce à une refonte de l’ordre et de l’intégration du Query Condition Cache (QCC) avec l’analyse des index. Le filtrage du QCC est désormais appliqué avant l’analyse de la clé primaire et des skip indexes, ce qui réduit les calculs d’index inutiles. L’analyse des index a été étendue pour prendre en charge plusieurs range filters, et ses résultats de filtrage sont désormais réinjectés dans le QCC. Cela accélère considérablement les requêtes où l’analyse des index domine le temps d’exécution, en particulier celles qui s’appuient sur des skip indexes (par ex. des index vectoriels ou inversés). [#82380](https://github.com/ClickHouse/ClickHouse/pull/82380) ([Amos Bird](https://github.com/amosbird)).
* Ajout d’une sérialisation optionnelle de la subcolumn `.size` pour les colonnes de type String de premier niveau dans les tables MergeTree afin d’améliorer la compression et de permettre un accès efficace aux subcolumns. Introduction de nouveaux MergeTree settings pour le contrôle des versions de sérialisation et l’optimisation des expressions pour les chaînes vides. [#82850](https://github.com/ClickHouse/ClickHouse/pull/82850) ([Amos Bird](https://github.com/amosbird)).
* Une série de micro-optimisations pour accélérer les petites requêtes. [#83096](https://github.com/ClickHouse/ClickHouse/pull/83096) ([Raúl Marín](https://github.com/Algunenano)).
* Compression des logs et des profile events dans le native protocol. Sur les clusters avec plus de 100 répliques, les profile events non compressés représentent 1 à 10 Mo/s, et la barre de progression est lente sur les connexions Internet lentes. Cela clôt [#82533](https://github.com/ClickHouse/ClickHouse/issues/82533). [#83586](https://github.com/ClickHouse/ClickHouse/pull/83586) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Amélioration des performances de la recherche de chaînes sensible à la casse (opérations telles que le filtrage, par ex. `WHERE URL LIKE '%google%'`) grâce à la bibliothèque [StringZilla](https://github.com/ashvardanian/StringZilla), avec utilisation des instructions SIMD du CPU lorsqu’elles sont disponibles. [#84161](https://github.com/ClickHouse/ClickHouse/pull/84161) ([Raúl Marín](https://github.com/Algunenano)).
* Réduction des allocations et des copies mémoire lors d’un select depuis une table aggregating merge tree avec FINAL lorsque la table comporte des colonnes de type `SimpleAggregateFunction(anyLast)`. [#84428](https://github.com/ClickHouse/ClickHouse/pull/84428) ([Duc Canh Le](https://github.com/canhld94)).
* Fournit une logique pour la descente des prédicats disjonctifs de JOIN. Exemple : dans TPC-H Q7, pour une condition sur 2 tables n1 et n2 comme `(n1.n_name = 'FRANCE' AND n2.n_name = 'GERMANY') OR (n1.n_name = 'GERMANY' AND n2.n_name = 'FRANCE')`, nous extrayons des filtres partiels distincts pour chaque table : `n1.n_name = 'FRANCE' OR n1.n_name = 'GERMANY'` pour n1 et `n2.n_name = 'GERMANY' OR n2.n_name = 'FRANCE'` pour n2. [#84735](https://github.com/ClickHouse/ClickHouse/pull/84735) ([Yarik Briukhovetskyi](https://github.com/yariks5s)).
* Améliore les performances de `LIKE` avec préfixe ou suffixe grâce au nouveau setting activé par défaut `optimize_rewrite_like_perfect_affix`. [#85920](https://github.com/ClickHouse/ClickHouse/pull/85920) ([Guang Zhao](https://github.com/zheguang)).
* Correction d’une dégradation des performances causée par une clé sérialisée volumineuse lors d’un regroupement sur plusieurs colonnes de chaînes ou de nombres. Clôture de https://github.com/ClickHouse/ClickHouse/pull/83884#issuecomment-3187972297 cc @mkmkme . Il s’agit d’un suivi de https://github.com/ClickHouse/ClickHouse/pull/83884. [#85924](https://github.com/ClickHouse/ClickHouse/pull/85924) ([李扬](https://github.com/taiyang-li)).
* Améliorations de DB::SharedMutex. [#87491](https://github.com/ClickHouse/ClickHouse/pull/87491) ([Raúl Marín](https://github.com/Algunenano)).
* Amélioration des performances de construction du text index pour les documents contenant principalement des jetons peu fréquents. [#87546](https://github.com/ClickHouse/ClickHouse/pull/87546) ([Anton Popov](https://github.com/CurtizJ)).
* Accélération du cas courant du destructor de Field. [#87631](https://github.com/ClickHouse/ClickHouse/pull/87631) ([Raúl Marín](https://github.com/Algunenano)).
* Ignorer le recalcul des statistiques de la table de hachage à l&#39;exécution pendant l&#39;optimisation de join. Ajout des nouveaux événements de profil `JoinOptimizeMicroseconds` et `QueryPlanOptimizeMicroseconds`. [#87683](https://github.com/ClickHouse/ClickHouse/pull/87683) ([Vladimir Cherkasov](https://github.com/vdimir)).
* Activer la sauvegarde des marks dans le cache et éviter les E/S directes pour le reader MergeTreeLazy. [#87989](https://github.com/ClickHouse/ClickHouse/pull/87989) ([Nikita Taranov](https://github.com/nickitat)).
* La requête SELECT avec la clause `FINAL` sur une table `ReplacingMergeTree` avec la colonne `is_deleted` s&#39;exécute désormais plus rapidement grâce à une meilleure parallélisation issue de 2 optimisations existantes : 1) l&#39;optimisation `do_not_merge_across_partitions_select_final` pour les partitions de la table qui n&#39;ont qu&#39;une seule `part` 2) la division des autres plages sélectionnées de la table en `intersecting / non-intersecting`, seules les plages `intersecting` devant passer par la transformation de fusion FINAL. [#88090](https://github.com/ClickHouse/ClickHouse/pull/88090) ([Shankar Iyer](https://github.com/shankar-iyer)).
* Réduire l&#39;impact de l&#39;absence d&#39;utilisation des fail points. [#88196](https://github.com/ClickHouse/ClickHouse/pull/88196) ([Raúl Marín](https://github.com/Algunenano)).

* Amélioration des performances des fonctions `tokens`, `hasAllTokens`, `hasAnyTokens`. [#88416](https://github.com/ClickHouse/ClickHouse/pull/88416) ([Anton Popov](https://github.com/CurtizJ)).
* Lecture dans l&#39;ordre pour Iceberg. [#88454](https://github.com/ClickHouse/ClickHouse/pull/88454) ([scanhex12](https://github.com/scanhex12)).
* Passage de `AddedColumns::appendFromBlock` en inline pour améliorer légèrement les performances de join dans certains cas. [#88455](https://github.com/ClickHouse/ClickHouse/pull/88455) ([Nikita Taranov](https://github.com/nickitat)).
* Rétroporté dans [#89182](https://github.com/ClickHouse/ClickHouse/issues/89182) : implémentation de la réplication lazy des colonnes dans JOIN et ARRAY JOIN. Évite la conversion de représentations spéciales de colonnes, comme Sparse et Replicated, en full columns dans certains formats de sortie. Cela évite des copies de données inutiles en mémoire. [#88752](https://github.com/ClickHouse/ClickHouse/pull/88752) ([Pavel Kruglov](https://github.com/Avogar)).

* Lorsque des clients HTTP définissent l'en-tête `X-ClickHouse-100-Continue: defer` en plus de `Expect: 100-continue`, ClickHouse n'envoie pas de réponse `100 Continue` au client tant que la validation du quota n'est pas passée, évitant ainsi le gaspillage de bande passante réseau lié à la transmission de corps de requête qui seraient de toute façon rejetés. Cela concerne les requêtes INSERT où la requête peut être envoyée dans la chaîne de paramètres de l'URL et les données dans le corps de la requête. L'abandon d'une requête sans envoi du corps complet empêche la réutilisation de la connexion avec HTTP/1.1, mais la latence supplémentaire induite par l'ouverture de nouvelles connexions est généralement négligeable par rapport à la durée totale d'un INSERT avec de grandes quantités de données. [#84304](https://github.com/ClickHouse/ClickHouse/pull/84304) ([c-end](https://github.com/c-end)).
* L'autocomplétion du client est plus rapide et plus cohérente grâce à l'utilisation de `system.completions` plutôt qu'à l'émission de plusieurs requêtes sur des tables système. [#84694](https://github.com/ClickHouse/ClickHouse/pull/84694) ([|2ustam](https://github.com/RuS2m)).

Cela peut être bénéfique pour des requêtes telles que `SELECT avg(o_totalprice) FROM orders, customer, nation WHERE c_custkey = o_custkey AND c_nationkey=n_nationkey AND n_name = 'FRANCE'`. Fait partie de [#79890](https://github.com/ClickHouse/ClickHouse/issues/79890). [#85455](https://github.com/ClickHouse/ClickHouse/pull/85455) ([Dmitry Novik](https://github.com/novikd)).

[#85637](https://github.com/ClickHouse/ClickHouse/pull/85637) ([Tuan Pham Anh](https://github.com/tuanpach)).
