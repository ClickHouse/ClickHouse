<div id="backward-incompatible-change">
  #### Changement incompatible avec les versions précédentes
</div>

* Mineur : forcer les server settings `backup_threads` et `restore_threads` à ne pas être nuls. [#80224](https://github.com/ClickHouse/ClickHouse/pull/80224) ([Raúl Marín](https://github.com/Algunenano)).
* Correction de `bitNot()` afin que `String` renvoie une chaîne terminée par un zéro. [#80791](https://github.com/ClickHouse/ClickHouse/pull/80791) ([Azat Khuzhin](https://github.com/azat)).
* Rétroporté dans [#82079](https://github.com/ClickHouse/ClickHouse/issues/82079) : auparavant, la fonction `countMatches` s&#39;arrêtait au premier match vide, même si le pattern l&#39;acceptait. Pour corriger ce problème, `countMatches` continue désormais en avançant d&#39;un caractère lorsqu&#39;un match vide se produit. Les utilisateurs qui souhaitent conserver l&#39;ancien comportement peuvent activer le setting `count_matches_stop_at_empty_match`. [#81676](https://github.com/ClickHouse/ClickHouse/pull/81676) ([Elmi Ahmadov](https://github.com/ahmadov)).

<div id="performance-improvement">
  #### Amélioration des performances
</div>

* L’implémentation existante de `Pipe::resize` crée un unique nœud `Resize` ou `StrictResize` en l’insérant dans la topologie du pipeline, qui agit ensuite comme un hub central reliant tous les streams d’entrée (nœuds en amont) à un ensemble unifié d’output streams (nœuds en aval). Cette conception entraîne une contention sur `ExecutingGraph::Node::status_mutex` pendant l’exécution du graphe du pipeline, en particulier dans les environnements comportant un grand nombre de cœurs. Lorsque les pipelines passent à des dizaines ou des centaines de streams, cette contention se traduit par :. [#77562](https://github.com/ClickHouse/ClickHouse/pull/77562) ([Zhiguo Zhou](https://github.com/ZhiguoZh)).
* Rétroporté dans [#81959](https://github.com/ClickHouse/ClickHouse/issues/81959) : introduction d’une option permettant de décharger la (dé)compression et la (dé)sérialisation des blocks vers les threads du pipeline au lieu d’un seul thread associé à une connection réseau. Contrôlé par le setting `enable_parallel_blocks_marshalling`. Cela devrait accélérer les distributed queries qui transfèrent des volumes importants de données entre l’initiator et les nœuds distants. [#78694](https://github.com/ClickHouse/ClickHouse/pull/78694) ([Nikita Taranov](https://github.com/nickitat)).
* Remplace les queries `DELETE FROM ... WHERE 1` par `TRUNCATE`. (Annulé). [#78739](https://github.com/ClickHouse/ClickHouse/pull/78739) ([scanhex12](https://github.com/scanhex12)).
* Améliorations des performances pour tous les types de bloom filter. [#79800](https://github.com/ClickHouse/ClickHouse/pull/79800) ([Delyan Kratunov](https://github.com/dkratunov)).
* Introduction d’un chemin optimisé dans `UniqExactSet::merge` lorsque l’un des Set est vide. De plus, si le Set de gauche est à deux niveaux et celui de droite à un seul niveau, la conversion du RHS en structure à deux niveaux n’est plus effectuée. [#79971](https://github.com/ClickHouse/ClickHouse/pull/79971) ([Nikita Taranov](https://github.com/nickitat)).
* Rend le logging asynchrone par défaut. Vous pouvez désactiver ce comportement en définissant `<async>false</async>` sous `<logger>`. [#80125](https://github.com/ClickHouse/ClickHouse/pull/80125) ([Raúl Marín](https://github.com/Algunenano)).
* Améliore l’efficacité de la réutilisation de la mémoire et réduit les défauts de page lors de l’utilisation des tables de hachage twolevel. [#80245](https://github.com/ClickHouse/ClickHouse/pull/80245) ([Jiebin Sun](https://github.com/jiebinn)).
* Évite les mises à jour inutiles et réduit la contention sur les verrous dans QueryConditionCache. [#80247](https://github.com/ClickHouse/ClickHouse/pull/80247) ([Jiebin Sun](https://github.com/jiebinn)).
* Optimisation mineure de `concatenateBlocks`. Cela pourrait être utile pour parallel hash join. [#80328](https://github.com/ClickHouse/ClickHouse/pull/80328) ([李扬](https://github.com/taiyang-li)).
* Lors de la sélection des mark ranges à partir de la plage de primary key, la binary search ne peut pas être utilisée si la primary key est encapsulée dans des Functions. Cette PR améliore cette limitation : la binary search peut toujours être appliquée lorsque la primary key est encapsulée dans une chain de fonctions toujours monotones, ou lorsque la RPN contient un élément toujours vrai. Cette PR clôt [#45536](https://github.com/ClickHouse/ClickHouse/issues/45536). [#80597](https://github.com/ClickHouse/ClickHouse/pull/80597) ([zoomxi](https://github.com/zoomxi)).
* Améliore la vitesse d’arrêt du Kafka engine (suppression du délai supplémentaire de 3 secondes en cas de multiples Kafka tables). [#80796](https://github.com/ClickHouse/ClickHouse/pull/80796) ([Azat Khuzhin](https://github.com/azat)).
* Async insert : réduit la memory usage et améliore les performances des insert queries. [#80972](https://github.com/ClickHouse/ClickHouse/pull/80972) ([Raúl Marín](https://github.com/Algunenano)).
* Ne profile pas les processors si la table de Log est désactivée. [#81256](https://github.com/ClickHouse/ClickHouse/pull/81256) ([Raúl Marín](https://github.com/Algunenano)).
* Accélère `toFixedString` lorsque la source correspond exactement à la valeur demandée. [#81257](https://github.com/ClickHouse/ClickHouse/pull/81257) ([Raúl Marín](https://github.com/Algunenano)).
* Ne pas traiter les valeurs de quota si l’utilisateur n’est soumis à aucune limite. [#81549](https://github.com/ClickHouse/ClickHouse/pull/81549) ([Raúl Marín](https://github.com/Algunenano)).
* Rendre ProcfsMetricsProvider thread&#95;local afin de conserver les fichiers ouverts entre les tâches. [#81576](https://github.com/ClickHouse/ClickHouse/pull/81576) ([Raúl Marín](https://github.com/Algunenano)).
* Correction d’une régression des performances du suivi de la mémoire. [#81694](https://github.com/ClickHouse/ClickHouse/pull/81694) ([Michael Kolupaev](https://github.com/al13n321)).

* Améliore l’optimisation de la clé de sharding pour les requêtes distribuées. [#78452](https://github.com/ClickHouse/ClickHouse/pull/78452) ([fhw12345](https://github.com/fhw12345)).
* Implémente une logique de type rééquilibrage Kafka pour StorageKafka2 à l’aide de ClickHouse Keeper. Pour chaque réplique, nous prenons en charge deux types de verrous de partition : les verrous permanents et les verrous temporaires. La réplique essaie de conserver les verrous permanents aussi longtemps que possible. À tout moment, il n’y a pas plus de `all_topic_partitions / active_replicas_count` verrous permanents sur une réplique (où `all_topic_partitions` est le nombre total de partitions et `active_replicas_count` le nombre de répliques actives) ; s’il y en a davantage, la réplique libère certaines partitions. Certaines partitions sont détenues temporairement par la réplique. Le nombre maximal de verrous temporaires sur une réplique varie dynamiquement afin de laisser aux autres répliques la possibilité d’obtenir certaines partitions en verrous permanents. Lors de la mise à jour des verrous temporaires, la réplique les libère tous et tente d’en reprendre d’autres. [#78726](https://github.com/ClickHouse/ClickHouse/pull/78726) ([Daria Fomina](https://github.com/sinfillo)).
* Ajoute un avertissement concernant les bases de données potentiellement créées pour sauvegarder des tables corrompues. [#78841](https://github.com/ClickHouse/ClickHouse/pull/78841) ([János Benjamin Antal](https://github.com/antaljanosbenjamin)).
