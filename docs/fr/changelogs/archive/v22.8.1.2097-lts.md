<div id="backward-incompatible-change">
  #### Changement non rétrocompatible
</div>

* Le cache devient composable : il est possible d’empêcher l’éviction de certains fichiers (idx, mrk, etc.) et l’ancienne version du cache est supprimée. Il est désormais possible de configurer le cache sur un disk Azure blob storage, un disk Local, un disk StaticWeb, etc. Cette PR est marquée comme non rétrocompatible, car la configuration du cache change et, pour que le cache fonctionne, il faut mettre à jour le fichier de configuration. L’ancien cache sera toujours utilisé avec la nouvelle configuration. Le server démarrera correctement avec l’ancienne configuration du cache. Clôture [#36140](https://github.com/ClickHouse/ClickHouse/issues/36140). Clôture [#37889](https://github.com/ClickHouse/ClickHouse/issues/37889). [#36171](https://github.com/ClickHouse/ClickHouse/pull/36171) ([Kseniia Sumarokova](https://github.com/kssenii)).
* Désormais, toutes les sources de dictionnaires concernées respectent le paramètre `remote_url_allow_hosts`. C’était déjà le cas pour HTTP, Cassandra et Redis. Ajout de ClickHouse, MongoDB, MySQL et PostgreSQL. L’hôte n’est vérifié que pour les dictionnaires créés à partir de DDL. [#39184](https://github.com/ClickHouse/ClickHouse/pull/39184) ([Nikolai Kochetov](https://github.com/KochetovNicolai)).
* La plage de Date32 et DateTime64 a été étendue pour prendre en charge les dates allant de 1900 à 2299. Dans les versions précédentes, l’intervalle pris en charge allait seulement de 1925 à 2283. L’implémentation utilise le calendrier grégorien proleptique (conforme à [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601):2004 (clause 3.2.1 The Gregorian calendar)) au lieu de tenir compte des transitions historiques du calendrier julien vers le calendrier grégorien. Ce changement affecte le comportement propre à l’implémentation pour les arguments hors plage. Par exemple, si, dans les versions précédentes, la valeur `1899-01-01` était ramenée à `1925-01-01`, dans la nouvelle version elle sera ramenée à `1900-01-01`. Cela modifie le comportement de l’arrondi avec `toStartOfInterval` si vous passez `INTERVAL 3 QUARTER`, jusqu’à un trimestre, car les intervalles sont comptés à partir d’un point dans le temps propre à l’implémentation. Clôture [#28216](https://github.com/ClickHouse/ClickHouse/issues/28216), améliore [#38393](https://github.com/ClickHouse/ClickHouse/issues/38393). [#39425](https://github.com/ClickHouse/ClickHouse/pull/39425) ([Roman Vasin](https://github.com/rvasin)).



<div id="new-feature">
  #### Nouvelle fonctionnalité
</div>

* Ajout d’un paramètre `exact_rows_before_limit` (0/1). Lorsqu’il est activé, ClickHouse fournit la valeur exacte de la statistique `rows_before_limit_at_least`, mais au prix d’une lecture complète des données avant la limite. Cela résout [#6613](https://github.com/ClickHouse/ClickHouse/issues/6613). [#25333](https://github.com/ClickHouse/ClickHouse/pull/25333) ([kevin wan](https://github.com/MaxWk)).
* Ajout d’une cache policy SLRU pour l’uncompressed cache et le cache des marks. [#34651](https://github.com/ClickHouse/ClickHouse/pull/34651) ([alexX512](https://github.com/alexX512)).
* Intel® In-Memory Analytics Accelerator (Intel® IAA) est un accélérateur matériel disponible dans la prochaine génération de processeurs Intel® Xeon® Scalable (&quot;Sapphire Rapids&quot;). Son objectif est d’accélérer les opérations d’analytics courantes, comme la (dé)compression des données et le filtrage. ClickHouse intègre désormais le nouveau compression codec &quot;DeflateQpl&quot;, qui utilise la technologie de déchargement Intel® IAA pour fournir une implémentation DEFLATE haute performance. Le codec utilise la [Intel® Query Processing Library (QPL)](https://github.com/intel/qpl), qui abstrait l’accès à l’accélérateur matériel ou, à défaut, à une solution logicielle de repli si l’accélérateur matériel n’est pas disponible. DEFLATE offre généralement des taux de compression plus élevés que le codec LZ4 par défaut de ClickHouse et permet ainsi de réduire les E/S disque ainsi que la consommation de mémoire principale. [#36654](https://github.com/ClickHouse/ClickHouse/pull/36654) ([jasperzhu](https://github.com/jinjunzh)).
* Ajout du paramètre concurrent&#95;threads&#95;soft&#95;limit pour améliorer les performances en cas de RPS élevé en limitant le nombre total de threads pour toutes les queries. [#37285](https://github.com/ClickHouse/ClickHouse/pull/37285) ([Roman Vasin](https://github.com/rvasin)).
* Ajout d’une logique de contrôle de la concurrence afin de limiter le nombre total de threads concurrents créés par les queries. [#37558](https://github.com/ClickHouse/ClickHouse/pull/37558) ([Sergei Trifonov](https://github.com/serxa)).
* Ajout de la prise en charge des opérations insert select distribuées parallèles dans les tables avec engine Distributed et Replicated [#34670](https://github.com/ClickHouse/ClickHouse/issues/34670). [#39107](https://github.com/ClickHouse/ClickHouse/pull/39107) ([Nikita Mikhaylov](https://github.com/nikitamikhaylov)).
* Ajout de nouveaux paramètres pour contrôler la schema inference à partir des text formats : - `input_format_try_infer_dates` - tenter d’inférer des dates à partir de chaînes. - `input_format_try_infer_datetimes` - tenter d’inférer des DateTimes à partir de chaînes. - `input_format_try_infer_integers` - tenter d’inférer `Int64` au lieu de `Float64`. - `input_format_json_try_infer_numbers_from_strings` - tenter d’inférer des nombres à partir de JSON strings dans les JSON formats. [#39186](https://github.com/ClickHouse/ClickHouse/pull/39186) ([Kruglov Pavel](https://github.com/Avogar)).
* Cette fonctionnalité fournira une sortie de logs au format JSON dans la console. L’objectif est de faciliter l’ingestion et les queries dans les outils d’analyse de logs. [#39277](https://github.com/ClickHouse/ClickHouse/pull/39277) ([Mallik Hassan](https://github.com/SadiHassan)).

<div id="performance-improvement">
  #### Amélioration des performances
</div>

* * Correction d’un blocage de l’analyse sur les requêtes complexes. [#38185](https://github.com/ClickHouse/ClickHouse/pull/38185) ([Vladimir C](https://github.com/vdimir)).
* Déduire la méthode de tri à partir de la description de tri du flux d’entrée. Ignorer le tri si le flux d’entrée est déjà trié. [#38719](https://github.com/ClickHouse/ClickHouse/pull/38719) ([Igor Nikonov](https://github.com/devcrafter)).
* `DISTINCT`, utilisé avec `ORDER BY`, améliore sensiblement l’utilisation mémoire et le temps d’exécution des requêtes si les colonnes `DISTINCT` correspondent aux colonnes `ORDER BY` (ou en forment un préfixe). [#39432](https://github.com/ClickHouse/ClickHouse/pull/39432) ([Igor Nikonov](https://github.com/devcrafter)).
* Utiliser le nœud local en priorité pour obtenir la structure de la table distante lors de l’exécution de `cluster` et de fonctions de table similaires. [#39440](https://github.com/ClickHouse/ClickHouse/pull/39440) ([Mingliang Pan](https://github.com/liangliangpan)).
* Utiliser `DistinctSortedTransform` uniquement lorsque la description de tri s’applique aux colonnes `DISTINCT`, sinon revenir à l’implémentation classique de `DISTINCT`. Cela permet de réduire le nombre de vérifications pendant l’exécution de `DistinctSortedTransform`. [#39528](https://github.com/ClickHouse/ClickHouse/pull/39528) ([Igor Nikonov](https://github.com/devcrafter)).
* `DistinctSortedTransform` n’exploitait pas le tri, c.-à-d. qu’il se comportait comme une implémentation `DISTINCT` classique. Le correctif réduit considérablement l’utilisation mémoire. [#39538](https://github.com/ClickHouse/ClickHouse/pull/39538) ([Igor Nikonov](https://github.com/devcrafter)).
* ColumnVector : optimiser le filtre avec AVX512VBMI2 compress store. [#39633](https://github.com/ClickHouse/ClickHouse/pull/39633) ([Guo Wangyang](https://github.com/guowangy)).
* KeyCondition : optimiser applyFunction dans un scénario multithread. [#39812](https://github.com/ClickHouse/ClickHouse/pull/39812) ([Guo Wangyang](https://github.com/guowangy)).
* Pour les systèmes dotés d’AVX512 VBMI2, cette PR améliore les performances d’environ 6 % pour les requêtes 3.1, 3.2 et 3.3 du benchmark SSB (SF=100). Testé sur un Intel Icelake Xeon 8380 à 2 sockets. [#40033](https://github.com/ClickHouse/ClickHouse/pull/40033) ([Robert Schulze](https://github.com/rschu1ze)).
* * Ne pas parcourir l’AST des UDFs si aucune n’est enregistrée. [#40069](https://github.com/ClickHouse/ClickHouse/pull/40069) ([Raúl Marín](https://github.com/Algunenano)).
