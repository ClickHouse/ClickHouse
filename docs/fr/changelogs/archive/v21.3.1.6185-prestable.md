<div id="backward-incompatible-change">
  #### Changement non rétrocompatible
</div>

* Désormais, tous les noms de fonctions insensibles à la casse seront mis en minuscules lors de l’analyse des requêtes. Cela est nécessaire pour le routage des requêtes de projection. [#20174](https://github.com/ClickHouse/ClickHouse/pull/20174) ([Amos Bird](https://github.com/amosbird)).
* Désormais, il n’est plus possible de créer des tables MergeTree avec l’ancienne syntaxe et un TTL de table, car celui-ci est tout simplement ignoré. L’Attach des anciennes tables reste possible. [#20282](https://github.com/ClickHouse/ClickHouse/pull/20282) ([alesapin](https://github.com/alesapin)).

  #### Amélioration des performances

* Ajout de l’exécution parallèle de SELECT FINAL sur une part avec level&gt;0 lorsque le paramètre `do_not_merge_across_partitions_select_final` vaut 1. [#19375](https://github.com/ClickHouse/ClickHouse/pull/19375) ([Kruglov Pavel](https://github.com/Avogar)).

Cela apporte jusqu’à 1,5× de gain de performances lors de l’insertion de longs enregistrements via HTTP. [#19516](https://github.com/ClickHouse/ClickHouse/pull/19516) ([Ivan](https://github.com/abyss7)).

[#20132](https://github.com/ClickHouse/ClickHouse/pull/20132) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Ajout du paramètre `compress` pour les tables `Memory`. S’il est activé, la table utilisera moins de RAM. Sur certaines machines et certains jeux de données, cela peut aussi accélérer les SELECT, mais ce n’est pas toujours le cas. Cela clôt [#20093](https://github.com/ClickHouse/ClickHouse/issues/20093). Remarque : plusieurs raisons expliquent pourquoi les tables Memory peuvent être plus lentes que MergeTree : (1) absence de compression (2) taille statique des blocs (3) absence d’indices et de prewhere... [#20168](https://github.com/ClickHouse/ClickHouse/pull/20168) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Évite de trop regrouper les blocs lors d’un INSERT SELECT en cas d’insertion dans une table Memory. Dans les versions précédentes, une représentation inefficace des données était créée dans la table Memory après INSERT SELECT. Cela clôt [#13052](https://github.com/ClickHouse/ClickHouse/issues/13052). [#20169](https://github.com/ClickHouse/ClickHouse/pull/20169) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Amélioration des performances de l’agrégation sur plusieurs champs de taille fixe (non confirmé). [#20454](https://github.com/ClickHouse/ClickHouse/pull/20454) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Accélération de la lecture depuis les tables `Memory` dans des cas extrêmes (lorsque la vitesse de lecture est de l’ordre de 50 Go/s) grâce à une simplification du pipeline et, par conséquent, à une moindre contention sur les verrous lors de la planification du pipeline. [#20468](https://github.com/ClickHouse/ClickHouse/pull/20468) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Amélioration des performances de GROUP BY avec plusieurs clés de taille fixe. [#20472](https://github.com/ClickHouse/ClickHouse/pull/20472) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Le paramètre `distributed_aggregation_memory_efficient` est activé par défaut. Il réduira l’utilisation mémoire et améliorera les performances des requêtes distribuées. [#20599](https://github.com/ClickHouse/ClickHouse/pull/20599) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Légère amélioration du code d’agrégation. [#20978](https://github.com/ClickHouse/ClickHouse/pull/20978) ([Alexey Milovidov](https://github.com/alexey-milovidov)).
* Réajout des spécialisations intDiv/module vectorConstant pour de meilleures performances. Cela corrige [#21293](https://github.com/ClickHouse/ClickHouse/issues/21293) .   #### Amélioration

* Correction de la création de `TTL` dans les cas où son expression est une fonction et coïncide avec la clé `ORDER BY`. Il est désormais possible de définir une agrégation personnalisée pour les colonnes de clé primaire dans `TTL` avec `GROUP BY`. Changement non rétrocompatible : pour les colonnes de clé primaire qui ne figurent pas dans `GROUP BY` et ne sont pas définies explicitement, la fonction `any` est désormais appliquée à la place de `max` lorsque le TTL expire. De plus, si vous utilisez `TTL` avec `WHERE` ou `GROUP BY`, des exceptions peuvent se produire lors des merges pendant un rolling update. [#15450](https://github.com/ClickHouse/ClickHouse/pull/15450) ([Anton Popov](https://github.com/CurtizJ)).
* Requêtes hedged pour les requêtes distantes. Lorsque le paramètre `use_hedged_requests` est activé (par défaut), il est possible d’établir plusieurs connexions avec différentes répliques pour une requête. Une nouvelle connexion est établie si la ou les connexions existantes avec la ou les répliques n’ont pas pu être établies dans le délai `hedged_connection_timeout` ou si aucune donnée n’a été reçue dans le délai `receive_data_timeout`. La requête utilise la première connexion qui envoie un packet Progress non vide (ou un packet Data, si `allow_changing_replica_until_first_data_packet`) ; les autres connexions sont annulées. Les requêtes avec `max_parallel_replicas > 1` sont prises en charge. [#19291](https://github.com/ClickHouse/ClickHouse/pull/19291) ([Kruglov Pavel](https://github.com/Avogar)).
* Affichage des frames intégrées pour les stacktraces fatales. [#19317](https://github.com/ClickHouse/ClickHouse/pull/19317) ([Ivan](https://github.com/abyss7)).
* Ne plus ignorer silencieusement les erreurs d’écriture. [#19451](https://github.com/ClickHouse/ClickHouse/pull/19451) ([Azat Khuzhin](https://github.com/azat)).
* Ajout de la prise en charge de `PREWHERE` lorsque des expressions de sécurité row-level sont définies pour les tables. [#19576](https://github.com/ClickHouse/ClickHouse/pull/19576) ([Denis Glazachev](https://github.com/traceon)).

[#19673](https://github.com/ClickHouse/ClickHouse/pull/19673) ([Azat Khuzhin](https://github.com/azat)).
