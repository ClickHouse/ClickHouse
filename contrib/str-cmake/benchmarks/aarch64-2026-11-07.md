# Native AArch64 integration comparison, 2026-11-07

The provider links into ClickHouse and passes the exercised contracts. The
focused comparison does not establish a broad application improvement, so
`ENABLE_PG83_STR` remains off by default. The earlier standalone kernel result
against glibc is not a ClickHouse performance result.

## Configuration

Both binaries used master `0ba40ae088e975ca4b1cb36236db8c39d1ddf037` on the
native `dev` host: Linux AArch64, Neoverse V2, 32 CPUs, glibc 2.35, Clang 21.1.8,
4096-byte pages, and a native SVE vector length of 16 bytes.

Build settings were `Release`, `ENABLE_THINLTO=OFF`, `ENABLE_TESTS=OFF`,
`ENABLE_UTILS=OFF`, `ENABLE_LIBRARIES=OFF`, `ENABLE_ICU=ON`,
`ENABLE_JEMALLOC=ON`, `USE_MUSL=OFF`, and `ENABLE_GPU=OFF`. LLVM libc retained
its normal setting. The preserved CMake caches differed only in
`ENABLE_PG83_STR` and CMake's internal makefile count. This configuration
includes ICU and the normal allocator, but is not the full CI configuration.

The baseline uses ClickHouse's existing providers, including Arm
optimized-routines and LLVM libc; this is not a comparison against bare glibc.

## Method and results

The stock `perf.py` harness ran 13 XML files, expanding to 80 queries, with
seven measured samples per binary per query. Two passes produced 2240 timing
samples; the second pass reversed the file order. Server processes shared CPU
affinity 8-15, used separate data directories, and had `max_threads=1` and
`max_insert_threads=1`. The driver used CPU 24. Harness options were
`--min-runs 7 --cap 7 --cap-fast 7 --tau 0.02 --max-query-seconds 60 --long
--stop-merges --jemalloc-purge before-each-run --result-digest`.

The files were `array_concat_single`, `array_slice_identity`,
`substring_identity`, `pad_substring_skip_ascii_scan`,
`group_by_string_key_count`, `group_by_low_cardinality_short_strings`,
`lower_upper_utf8_mixed_ascii`, `if_array_string`, `if_string_const`,
`uint64_to_string`, `decimal_format`, `sort_string_full`, and `count`.

Repeatable changes required at least 5% and Welch's test with an unadjusted
`p <= 0.05` in each pass, in the same direction. The
[per-query results](aarch64-2026-11-07.csv) report relative changes in median
client time: negative values mean faster.

The improvement was zero-based query 4 in `if_array_string`: 173.29 to
160.92 ms in pass 1 (-7.14%) and 172.59 to 160.13 ms in pass 2 (-7.22%).
All 76 included queries had matching result digests in both passes (152 pairs).
The four excluded `sort_string_full` queries had different randomly generated
input tables, so their timings cannot support an implementation comparison.
Ten mixed results include both apparent gains and slowdowns; they are not
evidence of equivalence or improvement. In particular, query 5 in
`pad_substring_skip_ascii_scan` changed by -0.34% and +11.46% in the two passes;
the second-pass slowdown remains unresolved. No aggregate speedup is reported.

Claude's 11-server fuzz fleet was paused using its owner's reversible scripts
and resumed after timing; both comparison servers were stopped. No integration
build or profiling overlapped this final series. The host was still shared:
an unrelated `tpufch-m003b` process used about 72% of one CPU during the first
`array_concat_single` file and 29% during `array_slice_identity`, with affinity
covering all 32 CPUs. Additional short-lived Python activity was recorded.
These observations limit confidence, especially in those files; this was not
a fully idle host or a CI performance run. Seven samples, fixed baseline and
candidate server order, and a selected workload set further limit the result.

## Dispatch tuning and correctness

The initial full-feature integration had nine repeatable regressions in this
suite. Separate sampling profiles showed more samples in the copy family,
including the public entry and SVE bridge. This motivated inlining lengths up
to 16 bytes and directly calling the existing NEON implementation above 64
bytes in `memcpy`, `memmove`, and `memset`. Kernel bodies were unchanged. The
final series above no longer observed those repeatable regressions above 5%.
An intermediate variant's repeat overlapped a build and was excluded; an
earlier build without ICU and jemalloc was also excluded.

The final archive passed `test_aarch64.c` in five configurations: native SVE
VL16, forced NEON, emulated non-SVE, and emulated SVE VL32 and VL48. Checks
cover all eleven public entry points, overlapping moves, guard pages,
oversized early-match `memchr`, canaries, and calls before constructors.
Emulation was used only for correctness.

The nine actual CMake object files were linked into a proof ELF without
recompiling the C kernels. Z3 proved the public `memcpy`, `memmove`, and
`memset` paths for lengths 0-16: 14 paths, 30 obligations, and 118 solver
queries. Proof ELF SHA-256:
`81aad7f09fdaaa03f9741946e259fd36edcca3e66caadd50cd670cbaec3bd46d`.
The model assumes untagged lower-47-bit addresses, 4096-byte pages, AAPCS64,
and explicit SVE VL16. Provenance checks compare retained function instruction
bits outside relocation fields with the original objects; relocation and
layout correctness trust the linker. Constructor code and metadata were
excluded. Longer paths, other public functions, lifecycle behavior, the model
itself, and binding to the final ClickHouse executable are not certified by
this bounded proof. CI and broader workload validation remain necessary
before considering default enablement.
